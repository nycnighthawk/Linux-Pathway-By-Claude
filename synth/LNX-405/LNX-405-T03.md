# Pinned, hugepage-backed VM that meets a latency target

## Define the problem

Some workloads need predictable latency from a virtual machine: trading, telecom, audio, industrial control. A default VM shares cores, memory and interrupts with other tasks, so its tail latency has spikes. The problem is to tune a VM and its host (CPU pinning, isolated cores, hugepages, interrupt placement, timer settings) until a stated latency target is met, and to prove it with measurements rather than settings.

## History and approaches

Latency tuning began on bare metal with real-time kernels and core isolation. Virtualisation added layers: virtual CPU scheduling, nested page tables, exits and host interrupts. Libvirt and QEMU gained controls for pinning, NUMA placement, hugepages and real-time scheduling, and tools such as cyclictest and kernel tracing made latency measurable.

## Current state

The host reserves cores through boot parameters and the scheduler, keeps interrupts and housekeeping on other cores, and backs guest memory with hugepages allocated on the right NUMA node. Each virtual CPU is pinned to one host core, emulator and I/O threads to others. The guest uses a suitable clock source and, for real-time work, a kernel with real-time settings. A measurement tool in the guest records the worst-case wake-up delay over a long run, with load, and the result is compared with the target. Changes are made one at a time.

## Assessment: the good, the bad and the ugly

These measures cut jitter dramatically. They also cost flexibility: pinned cores are unavailable to others, hugepages are reserved, live migration becomes harder, and mistakes (pinning across NUMA nodes) can worsen performance. The ugly part is measurement itself: noisy neighbours, power management and firmware events (system management interrupts) can ruin results, and short tests miss rare spikes.

## Applications beyond this domain

The same tuning applies to container hosts for latency-sensitive services, to real-time audio, to high-frequency trading systems and to telco network functions.

## Examples

A worked example: a VM with default settings shows a worst-case delay in the milliseconds; after isolating four cores, pinning, hugepages and moving interrupts, the worst case over an hour drops by an order of magnitude and meets the target. A failing example: pinning both hyperthreads of a core to different VMs gave worse results than no pinning.

## Related problems and ideas

Related topics are real-time Linux, SR-IOV and VFIO for device latency, and CPU frequency control. Alternatives are containers on isolated cores, which avoid virtualisation overhead.

## Active research

Active work covers real-time virtualisation, hardware features for interrupt delivery and better tools for finding latency sources (to verify).

## Future direction

Expect real-time kernel features to be mainline and virtualisation features to reduce exits.
