# Feature or test for QEMU or KVM selftests, sent for review

## Define the problem

The strongest evidence of understanding a hypervisor is a change accepted by its developers. For KVM and QEMU, a good first contribution is a test: a selftest for KVM or a qtest or functional test for QEMU. The problem is to design a small, correct test or feature, send it through the project's process and answer review.

## History and approaches

KVM selftests and kvm-unit-tests grew from the need to verify subtle hardware behaviour across architectures. QEMU added qtest to drive device models without a guest and functional tests that boot guests. Both projects review by mail, with maintainers and tooling described in their documents.

## Current state

The contributor picks a gap, such as a missing test for an ioctl or a device register behaviour, reads the existing tests and style, writes the test so it fails when the behaviour is wrong, runs it on the supported architectures, and sends a series with a clear commit message. Review comments are answered and revisions sent. The record of versions and replies is the evidence.

## Assessment: the good, the bad and the ugly

Tests are a good entry point: small, valuable and judged on correctness. Risks are tests that are flaky or depend on the host, and long waits for review. The ugly part is that acceptance depends on maintainer capacity.

## Applications beyond this domain

Contributing tests is also a way into other large projects, where maintainers value reliable tests.

## Examples

A worked example: a selftest checks that an ioctl rejects an invalid argument; review asks for a clearer failure message and a skip when the capability is absent; v2 is applied. A failing example: a test assumed hardware that CI did not have and was asked to skip gracefully.

## Related problems and ideas

Related topics are kvm-unit-tests, QEMU functional testing, and CI in each project.
