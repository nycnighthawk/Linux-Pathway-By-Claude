# A C or Rust VMM that boots Linux with virtio-blk and virtio-net, tested in CI

## Define the problem

Using a hypervisor is easy; building the program that drives one teaches how virtual machines actually work. A virtual machine monitor (VMM) must create the guest's memory, load a kernel, start virtual CPUs, handle the exits they raise and provide devices. The problem is to write a small VMM in C or Rust that boots a Linux guest to a shell with a block device and a network device built on virtio, and to test it automatically so that regressions are caught in CI.

## History and approaches

The first hypervisors were large and tightly bound to hardware. Linux's KVM interface turned the kernel into a hypervisor reachable by ordinary programs through a device file and a set of ioctls, and QEMU used it for full-featured machines. Smaller VMMs followed for focused uses: kvmtool, Firecracker, Cloud Hypervisor and crosvm, several sharing the rust-vmm crates. Virtio gave a standard, efficient device interface so guests need no emulated legacy hardware.

## Current state

The VMM opens the KVM device, creates a virtual machine and maps guest memory, loads the kernel image and an initial ramdisk, sets up registers and page tables or boot parameters, and creates a CPU thread that runs the guest until an exit. Exits for port or memory-mapped input and output are decoded and passed to devices. Virtio devices expose queues in guest memory; the VMM reads descriptor chains, performs the request on a file or a tap interface and signals completion with an interrupt. The CI test boots a tiny guest image, waits for a marker on the serial console, runs a read-write test against the block device and a ping or small transfer on the network, and fails on timeout.

## Assessment: the good, the bad and the ugly

A small VMM is understandable and its attack surface is small; it also lacks the features and testing of established ones. The weak points are guest-controlled input in every device (every length and address from the guest is untrusted), subtle interrupt and timer behaviour, and CI that needs hardware virtualisation support in runners. Rust removes classes of memory errors but not logic errors. The ugly part is the long tail: power management, hotplug and migration.

## Applications beyond this domain

The same structure appears in microVM platforms for serverless computing, in sandboxes for browsers and containers (Kata, gVisor's KVM mode), and in confidential computing launchers.

## Examples

A worked example: a minimal VMM boots a kernel with a single virtual processor, a serial console and one virtio-blk disk; a CI job boots it with a read-only image, reads a sector pattern and prints a success marker. A failing example: a block request with a length larger than the descriptor was trusted and read beyond the buffer; validation of every descriptor before use fixed it and a fuzz test now sends malformed chains.

## Related problems and ideas

Related topics are QEMU's device model, vhost and vhost-user back ends, Firecracker-style minimal machines, and unikernels. Alternatives to writing a VMM are using libvirt with QEMU, which trades control for features.

## Active research

Active work covers rust-vmm components, confidential VM support, device offloading and testing of VMMs with fuzzers (to verify).

## Future direction

Expect more VMMs built from shared Rust crates and more attention to testing guest-facing code.
