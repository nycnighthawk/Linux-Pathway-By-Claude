# One image pipeline deploying to libvirt, VirtualBox and KubeVirt

## Define the problem

Organisations run virtual machines on several platforms: libvirt on Linux servers, VirtualBox on developer machines and KubeVirt on Kubernetes. Maintaining a separate image for each invites drift, and bugs found on one platform stay hidden on another. The problem is to build one image from one source, convert it for each platform, boot each in CI or a lab, and prove that all three behave the same.

## History and approaches

Image building moved from installing by hand to templates (kickstart, preseed) and then to tools such as Packer and virt-builder that produce a disk image. Disk formats multiplied: qcow2 for QEMU, VDI and VMDK for VirtualBox and VMware, raw for clouds. First-boot configuration converged on cloud-init. KubeVirt brought virtual machines into Kubernetes, with disks served from persistent volumes or from container images.

## Current state

The pipeline builds one source image with a defined set of packages and a first-boot agent, records its checksum, and converts it with a conversion tool to the formats each platform needs. For libvirt it imports the qcow2 disk and a domain definition. For VirtualBox it converts to VDI or VMDK and registers the machine through the command-line tool. For KubeVirt it packages the disk in a container image under the conventional path with the expected owner and applies a virtual machine resource. A seed source (cloud-init data) supplies hostname and keys. A smoke test on each platform logs in, checks the kernel version and the image checksum recorded in the guest, and reports the result.

## Assessment: the good, the bad and the ugly

One source means one place to patch, and the comparison shows platform differences early. The costs are conversion fidelity (drivers, network interface names, boot mode), the different ways each platform injects first-boot data, and slow tests. VirtualBox on a KVM host needs care to coexist with other hypervisors. The ugly part is subtle divergence: a guest that expects a particular interface name or firmware type fails on one platform only.

## Applications beyond this domain

The same build-once, convert-per-target pattern is used for cloud machine images (AMIs and equivalents), container images for several architectures, and firmware for several board variants.

## Examples

A worked example: a pipeline builds a base image, converts it to VDI and a container disk, boots all three, and each guest reports the same image identifier. A failing example: the VirtualBox guest got a different network interface name, breaking a static configuration; switching to a name-independent match fixed it.

## Related problems and ideas

Related topics are image signing, reproducible images, bootc image-mode systems, and migration between platforms with conversion tools.

## Active research

Active work covers image-mode systems, cross-platform guest agents and confidential-image attestation (to verify).

## Future direction

Expect more image pipelines to produce OCI artifacts for virtual machines as well as containers.
