# Keeping the running system honest: IMA, EVM and kernel lockdown

## Define the problem

Secure Boot, covered in the previous topic, verifies code up to the point where the kernel starts and the kernel loads its modules. After that the system runs thousands of programs, libraries, scripts and configuration files from a writable filesystem, and nothing in the boot chain notices if one of them changes. An attacker who gains root, or who obtains offline access to the disk, can replace a binary, add a library to an existing service, or edit a policy file, and the next boot will start the altered code with every boot-time check satisfied. The gap is *runtime integrity*: the ability to answer which files were executed or read, whether each matches a known good state, and to refuse access when it does not.

Linux answers with the **Integrity Measurement Architecture** (IMA), the **Extended Verification Module** (EVM), and the kernel **lockdown** mode. IMA can *measure* files, meaning record a cryptographic hash in a log that is extended into a TPM register so that a remote party can verify the history; it can *appraise* files, comparing a hash or signature stored in the file's extended attributes with the actual content and denying access on a mismatch; and it can *audit*, writing events to the audit log. EVM protects the extended attributes themselves, including the security labels used by SELinux and the IMA hash, by attaching a keyed hash or signature over them, so that someone with offline access cannot simply edit the attribute to match a modified file. Lockdown does not verify files at all. It closes the doors through which a root user could bypass those mechanisms by modifying the running kernel: writing to `/dev/mem`, loading unsigned modules, using `kexec` on an unsigned kernel, accessing hibernation images, or unsafe use of debug interfaces.

The practical difficulty is that integrity policy is brittle. A strict appraisal policy blocks everything that is not signed, including software installed from a package manager unless the packages carry signatures, scripts that an interpreter reads, and files that change legitimately. Operators who turn the strictest settings on without a plan generate an unbootable system or an exception list so long that it protects nothing. This slice covers the three mechanisms, the policy language, the signing and labelling workflow, the log and attestation view, and the distribution packaging that makes it workable.

## History and approaches

The earliest approaches to host integrity were file-integrity checkers run from user space on a schedule: Tripwire (1992), AIDE and Samhain compare file hashes against a database, and they are still the practical choice for many compliance programmes. Their weakness is timing and trust. They run at intervals, so a change between runs is found late, and a root attacker can alter the checker, its database or its configuration. Moving the check into the kernel and anchoring the record in hardware was the response. IBM researchers (Reiner Sailer and colleagues) published IMA in 2004 as part of the Trusted Computing work, and it entered mainline Linux in 2.6.30 (2009). In its original form it only measured, producing a log that a verifier could compare with a TPM quote. Mimi Zohar's later work added **appraisal**, **signatures** in `security.ima` and the **EVM** companion. IMA-appraisal and EVM were merged in the 3.x series, and the policy language grew to select files by function (`BPRM_CHECK` for executables, `MMAP_CHECK` for mapped libraries, `FILE_CHECK` for opened files, `MODULE_CHECK`, `FIRMWARE_CHECK`, `KEXEC_KERNEL_CHECK`), by owner, by filesystem magic number or by SELinux label.

Several attempts had mixed success. **Remote attestation** with plain IMA measurement was intended to let a verifier detect any unauthorised code, but real systems produce enormous, ever-changing logs: every package update changes the expected list, and verifiers needed a database of good hashes for the whole distribution. Efforts such as Keylime, discussed under related ideas, make it workable at scale but did not make it routine. **Appraisal with locally generated hashes** (the `fix` mode) protects against offline modification but not against an attacker who can write files while the system runs, because the kernel will happily rebuild the hash. **Signature-based appraisal** is the strong form, because the signing key is not on the machine, but it required distributors to ship file signatures. Fedora and Red Hat began adding IMA signatures inside RPM packages through the `rpm-plugin-ima` plug-in, which writes the file digest signatures into the RPM header so that installation sets the extended attribute [src: man-pages b3e62d08af1688e1]. Debian and Ubuntu have had less packaged support for file signatures; deployments there typically sign locally at build time, in an image pipeline.

Lockdown has a related history. Matthew Garrett's patches that tied root's power to Secure Boot were controversial for years because they made "root can do anything" a conditional statement, and they were first carried by distributions as a Secure Boot-specific restriction. In 2019 they were merged in a form that separates the policy from the trigger: Linux 5.4 introduced the lockdown security module with two levels, `integrity` and `confidentiality`, selectable with the `lockdown=` command-line option or by a kernel configuration that enables it automatically when Secure Boot is active. The `kernel_lockdown(7)` manual lists what each level blocks [src: man-pages 7bf2448616434cf6].

## Current state

**IMA modes and policy.** IMA behaviour is chosen by the kernel command line (`ima_policy=tcb`, `ima_policy=appraise_tcb`, `ima_appraise=fix|log|off|enforce`, `ima_template=`, `ima_hash=sha256`) and by a **policy** loaded at boot from `/etc/ima/ima-policy` (some distributions load a policy from the initramfs or through `ima-evm-utils` or `dracut`'s IMA module) or written to `/sys/kernel/security/ima/policy`. A rule has an action (`measure`, `dont_measure`, `appraise`, `dont_appraise`, `audit`, `hash`) and conditions. Policy files use lines such as:

```
dont_measure fsmagic=0x9fa0        # procfs
dont_measure fsmagic=0x1021994     # tmpfs
measure func=BPRM_CHECK
measure func=MMAP_CHECK mask=MAY_EXEC
appraise func=BPRM_CHECK appraise_type=imasig
appraise func=MODULE_CHECK appraise_type=imasig
```

The order matters: the first matching rule decides. A standard pattern is to exclude pseudo-filesystems first, then measure executed programs and mapped libraries, then appraise executables, libraries and modules against signatures. The Red Hat documentation for kernel parameters lists the `ima-appraise-file` style options for which files are checked [src: rhel-10-docs bf5f8bfae035cb45].

**The measurement list.** `/sys/kernel/security/ima/ascii_runtime_measurements` lists each measured file: the PCR number (10 by default), a template hash, the template name (for example `ima-ng`), the file's digest with its algorithm and the path. The aggregate is extended into TPM PCR 10, so a TPM quote of that register authenticates the list; a verifier replays the list, checks that it reproduces PCR 10 and checks each digest against its own database. `/sys/kernel/security/ima/violations` counts "open writers" and "ToMToU" violations, where a file was measured while someone had it open for writing.

**Appraisal and signatures.** Appraisal stores a value in the `security.ima` extended attribute: a plain hash (type 1) or a signature (type 3, `imasig`). `evmctl ima_sign --key privkey.pem file` from the `ima-evm-utils` package writes a signature; `evmctl ima_verify` and `getfattr -m security -d file` examine it. The kernel verifies the signature against keys in the `.ima` keyring, which a trusted key loaded from the kernel's built-in or secondary trusted keys can populate: in practice the IMA CA certificate is compiled in or loaded into the `.ima` keyring by a signed initramfs step. A file without a valid attribute is refused execution when appraisal is enforced.

**EVM.** EVM adds `security.evm`, a keyed hash (HMAC) or signature over a fixed list of attributes: `security.ima`, `security.selinux`, `security.SMACK64`, `security.capability`, plus the file's inode number, owner, group and mode. The HMAC key is a 32-byte *trusted* or *encrypted* key, kept in the kernel keyring and unwrapped at boot; because the HMAC covers the inode and owner, copying a file's attributes to another file breaks verification. In `x509` mode (signature instead of HMAC) EVM can be used on immutable images where files are signed at build time. EVM's enable state is written to `/sys/kernel/security/evm` and cannot be reverted once set to enforcing, without a reboot.

**Lockdown.** The module has two levels. `integrity` blocks modification of the running kernel: no `/dev/mem`, `/dev/kmem` or `/dev/port` access, no direct PCI BAR access, no unsigned modules, no `kexec_load` of an unsigned image, no hibernation (since the image could be tampered with), no MSR writes, no use of some debugfs files and ACPI table overrides. `confidentiality` also blocks reading kernel memory and secrets, which prevents tracing tools such as kprobes and perf from reading kernel data, and some BPF features. The level is reported in `/sys/kernel/security/lockdown`, shown as `none [integrity] confidentiality`. It can be raised at runtime by writing to that file but never lowered. Many distributions enable `integrity` automatically with Secure Boot.

**Packaging and workflow.** A workable deployment builds files with signatures at image or package time, installs the IMA public certificate into the kernel's `.ima` keyring, starts in `ima_appraise=log` so violations are recorded and not enforced, collects the exceptions, then switches to `enforce`. Mutable paths (`/var`, `/home`, `/tmp`, application caches) are excluded from appraisal and, if anything, mounted `noexec`. Immutable or image-based distributions pair this with dm-verity or fs-verity.

**The generalised pattern.** Integrity enforcement has three parts: a *reference* (hash or signature) stored where an attacker cannot change it without the signing key, a *verifier* in the trusted computing base that compares the reference with the live object at the moment of use, and a *policy* that says which objects are covered and what happens on failure. IMA supplies the verifier, EVM extends the reference to metadata and lockdown protects the verifier from its own privileged user.

## Assessment: the good, the bad and the ugly

**The good.** The checks happen in the kernel, at the moment of use, on the actual bytes read, so a time-of-check gap is small. Signature appraisal is strong against offline modification and against a root attacker who cannot also steal the signing key. The measurement log gives remote verifiers an audit trail that ties to hardware. Lockdown is cheap to turn on and blocks a whole family of post-exploitation methods.

**The bad.** Coverage is partial by design. Interpreters read scripts that are never `exec`ed as such: `python script.py` appraises the interpreter, not the script, unless the interpreter or a policy opt-in (the `BPRM_CHECK` with `check_script`, recent `execveat` `AT_EXECVE_CHECK` work to verify) asks the kernel to check. Memory-only attacks and processes that already run are unaffected. Packaging is the main burden: without per-file signatures in every package, a strict policy cannot be used on a general-purpose server. Appraisal costs a hash on first use of every file, which is noticeable on cold caches and network filesystems. Debuggers and tracing tools lose access under `confidentiality`.

**The ugly.** A policy that refuses to boot is the most common failure. An appraisal rule that covers `FILE_CHECK` on root-owned files in `/etc` can stop `systemd` from reading its own configuration. EVM key setup is intricate: the trusted key must be created, saved, loaded in the initramfs, and enabled before the first appraisal, and a mistake can leave a machine that cannot update its own labels (a relabel after a policy change touches every file and an enforcing EVM refuses the change). Policies loaded too late leave a window; files updated by a package manager need a re-signed attribute or the update fails under enforcement. The measurement list also leaks: it names every executed path, which in multi-tenant environments is information an operator may not want to export.

**Mitigations.** Start with log mode, review with `dmesg` and audit messages, and promote rules one function at a time. Keep a recovery boot entry with `ima_appraise=off`, protected by the bootloader password and reachable only with physical access (in a Secure Boot setup that may require the signed kernel command line to be fixed, so that the entry does not become a bypass; to verify for the distribution used). Use signatures, not local hashes. Exclude mutable data. Pair appraisal with `noexec` mounts where possible. Test package updates on a canary host with the policy enforcing.

## Applications beyond this domain

The same three-part pattern of a protected reference, an in-line verifier and a policy appears across the stack. `dm-verity` verifies every block of a read-only volume against a Merkle tree rooted in a signed hash, and is used by Android, ChromeOS and image-based Linux. `fs-verity` does it per file with a hash tree stored beside the file, which allows verification of large files lazily. Container platforms use image signature verification (cosign) as an admission control and policy engines such as Kyverno or OPA Gatekeeper as the policy layer. Windows Defender Application Control and Apple's code-signing enforcement are close cousins of IMA appraisal. Remote attestation for confidential computing replays the measurement-list idea inside a trusted execution environment. Even file-integrity monitoring in compliance regimes (PCI DSS requirement for change detection on critical files) is the user-space ancestor of the same idea, and a combined design commonly keeps AIDE for reporting and IMA for enforcement.

## Examples

**Enforcing signed executables on an appliance.** A vendor ships a read-only root image whose every executable carries an IMA signature created at build time. The kernel embeds the vendor's certificate, boots with `ima_appraise=enforce` and `lockdown=integrity`, and the policy lists `appraise func=BPRM_CHECK appraise_type=imasig` and the same for modules and mmap. A shell dropped into `/tmp` fails with a permission error because it carries no signature, and a modified `/usr/bin/ssh` fails the same way.

**Attestation of a bare-metal fleet.** Measurement mode records executed files. An agent sends a TPM quote of PCR 10 and the measurement list to a verifier, which checks the quote signature, replays the list, and compares each digest with a database built from the distribution's packages. Unknown digests raise an alert. The operational cost is maintaining that database through updates.

**A failing example: the enforce switch.** An administrator copies a sample policy that includes `appraise func=FILE_CHECK mask=MAY_READ uid=0` and boots with `ima_appraise=enforce`. The init system cannot read its unit files, because they carry no signature, and the machine stops at the initrd. The remedy is a boot in `fix` or `off` mode, a narrower policy, and a staged rollout in `log` mode.

**A failing example: the script bypass.** A policy appraises executables, and an attacker runs a malicious script through the already-signed interpreter with `python3 /dev/shm/x.py`. The kernel sees only the interpreter being executed. The mitigation is to mount scratch space `noexec`, to remove interpreters from machines that do not need them, and, where kernel and interpreter support it, to opt in to script checks (to verify availability for the distribution in use).

## Related problems and ideas

Alternatives and complements include AIDE and Tripwire for reporting-only integrity monitoring; **Keylime**, an open-source remote attestation framework that automates TPM quotes and IMA policy checks and can revoke a node's secrets when it fails; **LSM-based allow lists** such as **SELinux** and **AppArmor**, which restrict what a process may do without checking file contents; **fapolicyd**, a user-space daemon that allows or denies execution by path, package database and hash and is the practical default on Enterprise Linux; **Integrity Policy Enforcement (IPE)**, a Microsoft-contributed LSM merged in Linux 6.12 that expresses allow rules by dm-verity or fs-verity properties of the backing volume; and **immutable operating systems** that make the root read-only and replace it atomically. Newer ideas include transparency logs for file or image signing, hash-chained logs for node attestation, and measured container workloads that extend IMA into namespaces (a still-experimental IMA namespace proposal).

## Active research

Work focuses on making IMA usable in containers (a per-namespace measurement and policy is still unmerged mainline, status to verify), on script and interpreter checking, on reducing the cost of attestation verification through reference-value databases built from package metadata, and on combining fs-verity digests with IMA so signing is per file but verification is incremental. Kernel developers continue to refine EVM with portable signatures for use on network filesystems, and to harden lockdown against paths found by researchers, including BPF and perf facilities. Open questions include how to attest a system whose policy changes by design, and how to bound the measurement list on long-running hosts.

## Future direction

Expect appraisal to be adopted first in image-based and immutable distributions where signing is part of the build, with IPE and dm-verity taking a share of what IMA does for whole volumes. Expect remote attestation to move from research to routine in confidential-computing and edge fleets, with reference values published by vendors. Expect lockdown integrity to become the default posture wherever Secure Boot is active. For administrators on traditional distributions, fapolicyd, SELinux and a signed boot chain together deliver most of the benefit at a manageable operational cost; IMA enforcement is the next step for hosts where the extra cost is justified.
