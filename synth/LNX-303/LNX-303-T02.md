# Encrypting disks so that servers can still boot unattended

## Define the problem

Disk encryption protects data at rest: a stolen laptop, a returned drive, a decommissioned server, a snapshot copied out of a cloud account. The mathematics is mature. The difficulty is the key. A volume that needs a passphrase at every boot is safe and unusable for a rack of servers that restart at three in the morning after a kernel update, while a volume whose key sits in a file on the same disk is not protected at all. The problem is to release the key automatically in the situations where the machine is where it should be and in the state it should be in, and to withhold it in every other situation: the disk in another computer, the machine in another network, the firmware or bootloader replaced.

The topic therefore has three layers. The first is the container format, which on Linux is LUKS2 managed by `cryptsetup`: how the header stores several independently usable keys, how a passphrase is stretched, and how the whole stack is opened early in boot. The second is the key-release policy. A **Trusted Platform Module** (TPM 2.0) can seal a secret to measurements of the boot chain, so that it is released only when firmware, bootloader and kernel are those the administrator expects. A **Tang** server can hold half of a key exchange so that the secret is recoverable only while the machine can reach the server on the corporate network. **Clevis** is the client framework that combines such policies. The third layer is the development environment: real TPMs are not available in every lab, so software TPMs (`swtpm`) are used to practise.

Failure is mostly operational rather than cryptographic. Volumes locked forever because the only key was bound to a firmware state that changed, servers that hang at the initramfs because the network was not up when Tang was queried, recovery passphrases that nobody recorded, headers corrupted with no backup, or TPM bindings that quietly accept a bootloader no one meant to trust. This slice covers LUKS2 on block devices, `systemd-cryptenroll` and Clevis binding, Tang deployment, PCR policy choices, and the software TPM for testing. File-level encryption (fscrypt, eCryptfs) and Secure Boot signing are treated elsewhere.

## History and approaches

Early Linux disk encryption used loop devices with a single key derived from a passphrase, then `dm-crypt` (2004), a device-mapper target that encrypts blocks transparently. Clemens Fruhwirth's **LUKS** (2004) added a standard on-disk header with multiple key slots and an anti-forensic key splitter, so that a passphrase could be changed without re-encrypting the data, because the passphrase unlocks a slot that holds a randomly generated *master key*. LUKS1 fixed PBKDF2 as the key-derivation function, which is cheap to attack with GPUs. **LUKS2** (2018, cryptsetup 2.0) replaced the binary header with a JSON metadata area that is redundant and checksummed, added **Argon2** memory-hard key derivation, allowed authenticated encryption in an experimental form, and introduced *tokens*, metadata attached to key slots that tell tools how a slot is meant to be opened. The token mechanism is what lets Clevis and systemd tools record, inside the header, how a slot is unlocked automatically. The lessons of the format were repeated ones: store metadata in two copies and with checksums, because a damaged header means total loss, and keep an offline header backup (`cryptsetup luksHeaderBackup`).

Automatic unlocking began with keyfiles on a USB stick or on the root volume, which are as good as the stick, and with passphrases embedded in an initramfs, which are no protection at all. Hardware offered better: TPM 1.2 could seal a key to **platform configuration registers** (PCRs), the measurements that firmware and bootloader extend as they run. Sealing to the wrong set was a common failure, because registers that include the kernel command line or the bootloader configuration change with every update, and the volume became unrecoverable except by passphrase. TPM 2.0 (the specification arrived in 2014) added policy sessions that can express either PCR 7 matches or a signed policy is valid, which allows sealing to an authority rather than to one fixed measurement, and the systemd project turned this into `systemd-cryptenroll` and signed PCR policies (`systemd-measure`, `ukify`) for unified kernel images.

The network alternative came from Red Hat engineers, notably Nathaniel McCallum and Harald Hoyer: **Tang** and **Clevis**. A Tang server stores no client secret and keeps no state about clients. It publishes signing and exchange keys, and the client performs an exchange in which the server contributes to the derivation of a key without ever learning it (a variant of the McCallum-Relyea exchange). A machine can therefore rebuild its disk key only while the server answers. The server cannot be asked to unlock a stolen disk unless the thief can also reach it from inside the network. Red Hat documented the arrangement as **network-bound disk encryption** (NBDE) in the policy-based decryption chapter of its security hardening guide, which describes the roles of the Tang server, the Clevis pins and the LUKS volumes [src: rhel-10-docs 75c3005235a1761e]. Clevis generalised the idea through *pins*: `tang`, `tpm2`, and `sss`, which uses Shamir's secret sharing to require any *t* of *n* sub-policies. The combination "TPM2 or Tang" or "TPM2 and Tang" became the standard way of expressing resilience and strength respectively.

The development environment also evolved. Real discrete TPMs and firmware TPMs are scarce in CI. Stefan Berger's **swtpm** implements a TPM 1.2 and 2.0 emulator that QEMU and libvirt connect to through a socket, and recent systemd versions can start it for virtual machines, which the `systemd-tpm2-swtpm.service` manual describes [src: man-pages 83619f73ec9baa0c]. QEMU's own documentation explains the emulator device, the backend socket and the migration considerations [src: qemu-docs 5caf79ae70541a83].

## Current state

**LUKS2 on disk.** `cryptsetup luksFormat --type luks2 /dev/vdb` writes a header with a data segment descriptor, a *digest* that verifies the master key, and up to 32 key slots. Each slot holds the master key encrypted under a key derived from a passphrase or keyfile with the slot's own KDF parameters. Common choices are `aes-xts-plain64` with a 512-bit key for the data and `argon2id` for key derivation, with memory and time cost calibrated on the machine that creates the slot; a slot created on a fast workstation may be too memory-hungry for a small VM, which is a known source of boot failures. `cryptsetup luksDump` lists segments, keyslots, tokens and digests; `luksAddKey` and `luksRemoveKey` manage slots; `luksHeaderBackup` writes the header to a file that must be kept offline and protected, because it contains keyslots that anyone knowing a passphrase could use. Opening happens with `cryptsetup open` or, at boot, through `/etc/crypttab`. The options documented in the crypttab manual include `discard` (for TRIM, with the usual leak of which blocks are used), `tpm2-device=auto`, `tpm2-pcrs=`, `tries=` and `_netdev` for volumes that need the network [src: man-pages f8f6728cf203a604].

**Binding to the TPM.** With systemd, `systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 /dev/vdb` generates a random key, adds it as a LUKS2 slot, seals it in the TPM under a policy requiring PCR 7 to match, and stores the sealed blob in a LUKS2 token. PCR 7 reflects the Secure Boot state: enabled or not, and which certificates and revocation entries are in the key databases. Binding to it means that the machine booted with Secure Boot configured as enrolled, without tying the volume to a specific kernel. Adding PCR 11 (the unified kernel image) or the signed-policy mode ties the secret to a vendor-signed or locally-signed kernel family. Adding `--tpm2-with-pin=yes` requires a PIN in addition, which helps when an attacker holds the whole laptop but not the user. Clevis offers the same through `clevis luks bind -d /dev/vdb tpm2 '{"pcr_ids":"7"}'`.

**Binding to the network.** A Tang server (`tangd` under `systemd` socket activation on port 80, or inside a container) needs a directory of generated keys (`/var/db/tang`). Clients bind with `clevis luks bind -d /dev/vdb tang '{"url":"http://tang.example"}'`, and the command displays the server's key thumbprint, which the administrator must compare with the output of `tang-show-keys` on the server; accepting an unchecked thumbprint trusts whichever machine answered. The transport can be plain HTTP because the protocol does not expose the secret; it is advisable still to serve it on an isolated network. Rotation is done by generating new keys and hiding the old ones (the server continues to answer for old keys until clients rebind with `clevis luks regen`). In the initramfs, a `dracut` module (`clevis-dracut`, with `rd.neednet=1` and network arguments on the kernel command line) brings up networking and calls `clevis-luks-askpass`. Other early-boot systems (initramfs-tools, mkinitcpio, booster) have equivalent hooks; the Arch wiki lists the hooks for each [src: archwiki 1062ebb5e423e477].

**Combining policies.** `clevis luks bind -d /dev/vdb sss '{"t":2,"pins":{"tang":[{"url":"http://tang1"},{"url":"http://tang2"}],"tpm2":{"pcr_ids":"7"}}}'` unlocks if any two of the three succeed. A typical design is two Tang servers and the TPM with threshold two: a stolen machine fails (neither Tang is reachable, the TPM alone is not enough), one Tang server outage does not stop a boot, and a firmware change that invalidates the TPM policy still allows a boot when the network is healthy. A passphrase slot, kept in the vault, remains as the recovery path in every design.

**Testing with swtpm.** `swtpm_setup --tpm2 --tpmstate dir=/tmp/vtpm --createek` initialises a state directory; `swtpm socket --tpm2 --tpmstate dir=/tmp/vtpm --ctrl type=unixio,path=/tmp/vtpm/sock` starts the emulator. QEMU connects with `-chardev socket,id=chrtpm,path=/tmp/vtpm/sock -tpmdev emulator,id=tpm0,chardev=chrtpm -device tpm-tis,tpmdev=tpm0` (the device model differs by architecture), and libvirt expresses the same in domain XML as a `<tpm model='tpm-crb'>` element with an emulator backend. Inside the guest, `systemd-cryptenroll --tpm2-device=list` and `tpm2_pcrread` show what the guest sees. A software TPM offers no protection against an attacker with access to the host, so it is for testing only.

**The generalised pattern.** The volume holds the data under a random master key. Policies each hold a copy of a key that unlocks one slot, and each policy defines *when* it will release it: when a state is verified (TPM), when a party answers (Tang), or when enough parties agree (SSS). Recovery is a policy of last resort that is separately stored.

## Assessment: the good, the bad and the ugly

**The good.** LUKS2 is the Linux standard: the same format works for laptops, servers and cloud images, tools are present in every distribution, and slots mean that a departing administrator's passphrase can be removed without touching the data. Argon2id raises the cost of offline guessing. NBDE removes the main reason that servers keep keys on the disk, and it does so without a central secret store. TPM sealing ties the key to measured state and allows a machine to resist an attacker who swaps the bootloader. The token system makes the unlock method discoverable, so tooling can report the posture of a fleet from headers alone.

**The bad.** Every automatic method trades protection for convenience and the trade should be stated. A TPM-only binding is defeated by an attacker who can boot the genuine software and read memory or sniff the bus between TPM and CPU, attacks that have been demonstrated against discrete TPMs with unencrypted buses (parameter encryption sessions mitigate it, to verify support in the tooling used). A Tang-only binding is defeated by an attacker who can place the stolen machine on the network. PCR choices are a minefield: bind to PCR 0 or PCR 4 and every firmware or bootloader update locks the volume; bind to PCR 7 only and the volume trusts anything signed by a certificate in the database, including third-party shims. Header damage and forgotten recovery keys cause permanent data loss, and neither the TPM nor the Tang server can rescue them.

**The ugly.** The first boot after a change is where it breaks. A firmware update clears the TPM policy match and the host stops at a passphrase prompt in a datacentre. A Tang server in the same failure domain as the machines it protects means that after a power event neither can start: the disks wait for a server that is itself encrypted. DHCP lease timing, bonding, VLAN tagging and IPv6 behaviour in the initramfs differ from the running system and have caused many unattended boots to stall. Containers and cloud images add cases where no TPM exists, and clones that share a LUKS master key until someone runs `cryptsetup reencrypt`. Finally, encryption at rest does not protect running systems: a decrypted volume is as readable as any other, and keys remain in kernel memory.

**Mitigations.** Maintain a recovery passphrase in a vault and test it. Back up headers offline. Use threshold policies that tolerate one failure. Place Tang servers in a separate failure domain with a documented cold-start order. Bind to PCR 7 plus signed policy rather than to raw boot measurements. Rehearse a firmware update in a lab with swtpm and a real binding. Alert on volumes that lack tokens.

## Applications beyond this domain

The pattern of releasing a secret only when conditions hold appears across security engineering. Cloud confidential-computing services release keys to workloads only after remote attestation, which is the TPM idea extended to a whole virtual machine. Hardware security modules and cloud KMS services bind keys to identity and policy rather than to a machine state. Kubernetes secrets encryption and storage-class encryption use envelope keys wrapped by KMS. Shamir's secret sharing, used by the SSS pin, also underpins Vault's unseal procedure, covered later in this course: any three of five key holders can unseal. Tang's non-storing design resembles the zero-knowledge intent of password-authenticated key exchange. Even the logic of a signed PCR policy, which authorises any measurement signed by one key rather than a fixed value, is the same as signed boot chains: trust moves from a list of hashes to an authority.

## Examples

**Unattended server fleet.** A datacentre team encrypts every root volume with LUKS2 and binds each to two Tang servers and the host's TPM with threshold two. A recovery passphrase is stored per host in the secrets vault. The fleet reboots after patching without human input; a stolen server cannot be read; the loss of one Tang server is invisible.

**Laptop with TPM and PIN.** The disk is bound with `systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 --tpm2-with-pin=yes`. A short PIN is enough because the TPM enforces anti-hammering. An attacker who removes the drive learns nothing; one who reflashes the firmware changes PCR 7 and gets no key.

**A failing example: PCR 4.** An administrator binds to PCRs 0, 2, 4 and 7 for strength. Two weeks later a distribution bootloader update changes PCR 4, and 200 machines stop at a passphrase prompt. Recovery requires the passphrases and a rebind. The lesson is to bind to a measurement that identifies the authority, not each component.

**A failing example: Tang unreachable.** After a datacentre power failure the Tang virtual machine sits on an encrypted datastore that needs Tang to unlock. A cold-start runbook with a TPM-only slot for the Tang host breaks the loop.

**A lab pattern.** For tests, a CI job starts `swtpm`, boots a Debian cloud image with a `tpm-tis` device, formats a second disk with LUKS2, enrolls the TPM slot, reboots the guest and asserts that the volume opens without a passphrase and fails after the guest's Secure Boot variables change.

## Related problems and ideas

Alternative approaches include **self-encrypting drives** (OPAL), which move encryption into firmware and have repeatedly been found with weak key handling, so that software encryption is generally preferred; **fscrypt** and per-directory encryption, which allow per-user keys but expose metadata; **dm-integrity** and authenticated modes, which add tamper detection at the cost of performance and write amplification; and **cloud KMS-managed disk encryption**, where the provider holds a key. Ideas on the margin include FIDO2 tokens for LUKS unlocking (supported by `systemd-cryptenroll --fido2-device`), using the TPM to seal a key for an entire dm-verity or home directory setup in `systemd-homed`, and remote attestation services that release keys after a verified measurement, as in Keylime or Confidential Containers.

## Active research

Research and engineering work centres on stronger PCR policy (signed policies that allow updates without rebinding), TPM bus interposition and parameter encryption, the security of firmware TPMs (fTPM) against side channels, and reducing the risk of memory-remanence attacks on decrypted keys. Tang's protocol is being examined for forward secrecy and for multi-server threshold deployments at scale. In the LUKS2 world, work continues on authenticated encryption with dm-integrity, on online re-encryption speed, and on post-quantum considerations: symmetric AES-256 and Argon2 are considered robust, while the TPM's asymmetric primitives and the Tang exchange are not post-quantum safe, so migration plans are an open question (to verify whether the Clevis project has a published roadmap).

## Future direction

Expect unified kernel images with signed PCR policies to become the default on mainstream distributions, which removes most rebind events after kernel updates. Expect Tang and Clevis to coexist with attestation-based release in cloud and confidential environments. Expect FIDO2 and passkey-style unlock for user volumes. For operators, the durable practice is the same whichever product wins: a recovery path tested before it is needed, policies that survive one failure, and a clear statement of which attacker each binding is meant to defeat.
