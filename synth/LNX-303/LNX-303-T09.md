# Keeping secrets out of the wrong places: OpenBao, Vault and sops

## Define the problem

Systems run on secrets: database passwords, API tokens, TLS private keys, SSH keys, signing keys, cloud credentials. Each must be available to the right workload at the right time and to nobody else, and the number of secrets and workloads grows faster than any person can track. Without a system, secrets accumulate in the places that are easiest: environment files in a repository, a shared spreadsheet, a chat message, a container image layer, an Ansible variable file in plain text. They are copied to laptops, they are never rotated because rotation would break something nobody remembers, and a single leak (a public repository, a backup, a compromised build server) exposes everything they unlock.

The problem has several distinct parts. *Storage*: where do secrets live at rest, and who can decrypt them? *Distribution*: how does a workload obtain its secret at start-up without a human, given that obtaining a secret needs credentials of its own (the "secret zero" problem)? *Authorisation*: how is each identity limited to the secrets it needs? *Lifecycle*: how are secrets rotated, revoked and expired? *Audit*: who read what, when? And *configuration management*: how do encrypted secrets live in a repository next to code, so that they are reviewed, versioned and deployed through the same pipeline?

Two families of tools address these parts. A **secrets server**, of which HashiCorp Vault is the original and **OpenBao** the open-source fork, is a network service that stores secrets encrypted, authenticates clients through pluggable methods, enforces path-based policies, issues short-lived dynamic credentials, and keeps an audit log. A **file-encryption tool**, such as Mozilla's **sops** with the modern **age** encryption, encrypts secrets in files so that they can be committed to version control and decrypted only by holders of the right keys. The first is a runtime service with state; the second is a format and a convention that needs no server. Many organisations use both: sops for configuration that must travel with the repository, a secrets server for what workloads fetch at runtime.

Failure is common and expensive. The master key is lost and the secrets are gone. The unseal keys are kept next to the data. A root token created for set-up becomes the day-to-day credential. A policy grants a wildcard path because the specific one was inconvenient. A sops file is committed, a key is removed from the recipients list, and the old encrypted data remains decryptable from history. A pipeline decrypts secrets into plain files on a shared runner. This slice covers the architecture, configuration and operation of Vault-compatible servers, policies, authentication, dynamic secrets, and the file-based approach with sops and age, plus the integration with Kubernetes and configuration management.

## History and approaches

Early practice was to keep configuration files with passwords readable only by root, which treats the file system as the vault. Configuration management brought encrypted variable files: Puppet's hiera-eyaml, Chef's encrypted data bags, and Ansible Vault (2014), which encrypts a whole file with a shared password. They solved committing secrets to Git but not distribution to workloads, key management for teams, or rotation. A shared password for the vault file is itself a secret that has to be stored somewhere. Cloud providers added their own services (AWS Secrets Manager and KMS, Azure Key Vault, Google Secret Manager), each tied to its platform's identity.

HashiCorp **Vault** (2015, Mitchell Hashimoto and Armon Dadgar) generalised the idea into a platform-neutral service. Its design choices shaped the field: all data is encrypted by a data encryption key that is itself encrypted by a **master key**, which is split with Shamir's secret sharing into **unseal key** shares, so that a restarted server remains *sealed* until a quorum of key holders (for example three of five) supply their shares; clients authenticate to get a **token** bound to **policies**; secret *engines* mount at paths and provide key-value storage, **dynamic secrets** (database credentials generated per request with a lease and revoked at expiry), a **transit** engine that encrypts data on behalf of applications without exposing keys, a **PKI** engine that issues certificates (the practice covered in the first topic of this course), and an **SSH** engine that signs short-lived SSH certificates. Later versions added **auto-unseal** through a cloud KMS or an HSM so that restarts need no human, integrated Raft storage that removed the dependence on a separate Consul cluster, namespaces for multi-tenancy, and performance replication in the commercial edition.

The licence history matters for Linux distributions. In August 2023 HashiCorp changed Vault and its other products from the Mozilla Public License 2.0 to the Business Source License 1.1, which restricts use in competing commercial offerings and is not an open-source licence by the OSI definition. A community group forked the last MPL version in December 2023 as **OpenBao** under the Linux Foundation, and it has been developing in the open since, with its first stable release in 2024 and a move to the OpenSSF umbrella; the project has added features of its own, and its API remained compatible with Vault's at the time of fork, though divergence grows with each release (the compatibility status should be checked against current release notes, to verify). IBM completed its acquisition of HashiCorp in 2025, which added corporate-ownership uncertainty to the licence question for some users (to verify the current terms). For a Linux distribution or a team that requires an OSI-approved licence, OpenBao is the practical option, and several distributions have packaged or are considering packaging it.

The file-based line of development took a different path. **sops** (Secrets OPerationS), started at Mozilla in 2015 by Julien Vehent and others and later moved to a community organisation and the CNCF, encrypts the *values* of structured files (YAML, JSON, ENV, INI) while leaving keys in clear, so that diffs and reviews remain meaningful and only the values are secret. It supports multiple key sources: AWS KMS, GCP KMS, Azure Key Vault, HashiCorp Vault transit, PGP, and **age**. **age**, by Filippo Valsorda (2019), is a small modern file-encryption tool with X25519 recipients and no configuration, designed to replace the unpleasant parts of GPG for this use; sops adopted it, and it is now the simplest way to use sops without a cloud account. Wrappers for specific ecosystems followed: Kustomize and Flux support sops-encrypted manifests, Helm has a sops plugin, and Ansible has a vars plugin for it.

Each approach has failed in a way that taught something. Systems that stored the root token in the config management repository had every secret on the first leak. Dynamic secrets that were not renewed correctly caused outages when leases expired in the middle of a batch job. Unseal ceremonies done once and then not rehearsed turned a cluster restart into a two-hour recovery. And sops users learned that removing a recipient does not revoke access to data already encrypted to that recipient: the secret itself must be rotated.

## Current state

**Server architecture (Vault and OpenBao).** The server (`bao server -config=config.hcl` for OpenBao; `vault server` for Vault) has a *storage backend* (integrated Raft is the usual choice, and file and in-memory backends are for development), a *listener* with TLS, and a *seal* configuration. `bao operator init` creates the master key shares and an initial root token and prints them once. With Shamir seal, `bao operator unseal` is run with each share until the threshold is reached; with auto-unseal, a `seal "awskms"` or `seal "transit"` stanza lets the server unseal itself, and recovery keys are used for administrative operations. Once unsealed, the active node serves requests and standbys forward to it; Raft provides replication and leader election, with `bao operator raft snapshot save` for backups. The CLI uses `BAO_ADDR` and `BAO_TOKEN` (Vault's equivalents are `VAULT_ADDR` and `VAULT_TOKEN`), and the HTTP API lives under `/v1/`.

**Policies and authentication.** A policy is an HCL (or JSON) document that grants capabilities on paths:

```hcl
path "secret/data/payments/*" {
  capabilities = ["read"]
}
path "database/creds/payments-ro" {
  capabilities = ["read"]
}
path "sys/*" {
  capabilities = ["deny"]
}
```

Capabilities are `create`, `read`, `update`, `delete`, `list`, `patch`, `sudo` and `deny`; deny overrides everything; paths may use `*` suffix globs and `+` for a single segment. Auth methods turn external identity into a token with attached policies: **AppRole** for machines (a role id plus a secret id, the latter delivered by a trusted orchestrator, ideally wrapped and single-use), **Kubernetes** (validates a pod's service-account token against the cluster), **JWT/OIDC** for CI systems and people, **TLS certificates**, cloud IAM methods, and LDAP. Tokens carry a TTL and can be renewed within a maximum TTL, and a child token cannot exceed its parent's policies. **Response wrapping** returns a single-use token that unwraps to the real secret, which allows an orchestrator to hand a secret to a workload without seeing it.

**Secrets engines.** The key-value engine v2 stores versioned secrets at `secret/data/...` and supports soft delete and check-and-set; the database engine creates a distinct username and password per lease with `CREATE ROLE ... VALID UNTIL` statements and revokes them on expiry; the transit engine offers `encrypt`, `decrypt`, `rewrap`, `sign` and key rotation as an API so that applications never hold keys; the PKI engine acts as an intermediate CA issuing short-lived certificates; the SSH engine signs user and host certificates. Because each issuance is logged with the requesting identity, the revocation of a single lease cuts off a single credential.

**Audit.** Audit devices (file, syslog, socket) record every request and response with sensitive values HMAC-hashed. A server with audit enabled refuses to serve requests if *all* its audit devices fail, which is deliberate: unlogged access is considered worse than none, and operators must configure at least two devices.

**Delivery to workloads.** Vault Agent and the OpenBao equivalent authenticate on behalf of an application and render secrets to templated files or environment, and renew leases. On Kubernetes, the Vault Secrets Operator, the External Secrets Operator and the Secrets Store CSI driver sync or mount secrets from a server (or from cloud secret managers) into pods; the Vault Agent Injector adds a sidecar. The aim in each case is to keep the application unaware of the secrets service.

**sops and age.** A typical workflow: generate a key with `age-keygen -o key.txt` (the public recipient is printed, and `key.txt` stays private), write a `.sops.yaml` that tells sops which keys to use for which files, and encrypt with `sops encrypt --in-place secrets.yaml` (older releases use `sops -e -i`). A configuration looks like:

```yaml
creation_rules:
  - path_regex: secrets/.*\.yaml$
    encrypted_regex: '^(data|stringData|password|token)$'
    age: age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p
```

The decrypting side exports `SOPS_AGE_KEY_FILE=key.txt` and runs `sops decrypt secrets.yaml` or `sops exec-env secrets.yaml 'command'`, which injects values as environment variables without writing a plain file. `sops edit` opens a decrypted view in the editor and re-encrypts on save. `sops updatekeys` changes the recipient list, and `sops rotate` generates a new data key. Each file carries a MAC over its content, so tampering is detected, and its `sops:` metadata block lists the recipients and encrypted data keys. Multiple recipients (each team member and a CI key) allow any of them to decrypt.

**The generalised pattern.** Secret management resolves into *envelope encryption* (data keys wrapped by key-encryption keys), *identity-based release* (a secret is released to an authenticated identity under a policy), *short life* (leases and TTLs bound the damage of any leak) and *audit* (every release is recorded). sops provides envelope encryption in a file, a secrets server adds identity, lifetime and audit.

## Assessment: the good, the bad and the ugly

**The good.** A secrets server centralises policy and audit, replaces long-lived shared credentials with short-lived per-workload ones, and makes rotation routine. The transit and PKI engines let applications use cryptography without holding keys. OpenBao gives an OSI-licensed implementation with a familiar API. Sops is small, needs no server, fits Git workflows, and produces diffs a reviewer can read. Age is simple enough for teams to adopt in an afternoon. The two together allow encrypted bootstrap data in a repository and runtime secrets from a server.

**The bad.** A secrets server is a critical, stateful service: if it is down, workloads that fetch secrets at start cannot start, and recovery requires unseal procedures that few people have practised. It adds operational complexity (Raft quorum, upgrades, backup, certificate rotation of its own TLS). Policies are easy to over-grant and hard to review at scale. Dynamic secrets require applications that can tolerate credential change. Sops keeps keys in clear and so leaks structure (names of secrets, number of entries), has no per-secret access control (anyone able to decrypt the file sees all values in it), and offers no revocation of already-leaked ciphertext. Both approaches depend on a root of trust that must be bootstrapped by a human.

**The ugly.** Secret zero is the unsolved core: to get a secret you need a credential, and whatever delivers that credential is the real target. In practice it is a platform identity (cloud instance metadata, a Kubernetes service-account token, a TPM-attested host), which moves the question to the platform. Unseal keys and root tokens are routinely mishandled: stored together, emailed, left in shell history. A leaked age private key committed beside the encrypted file defeats it entirely; so does a secret that was once committed in plain text and survives in Git history. Audit logs contain request paths and metadata, so they are themselves sensitive. And rotation is mostly a social problem: a secret that nobody knows the consumers of cannot be safely changed.

**Mitigations.** Use auto-unseal with a separate trust domain, keep recovery keys with different custodians, and practise a restore from snapshot. Replace the root token after initialisation and revoke it, creating a break-glass procedure that regenerates one with `operator generate-root`. Write policies per workload with exact paths and review them as code (Terraform or the declarative API). Prefer dynamic, short-lived credentials and AppRole secret ids delivered by wrapping. For sops, store recipients in `.sops.yaml`, require a CI key, rotate secrets when a recipient leaves (and not only the recipient list), scan repositories for plain-text secrets with a pre-commit hook, and keep age identity files in a password manager or hardware-backed store.

## Applications beyond this domain

Envelope encryption and identity-based release show up across systems. Cloud KMS services wrap data keys for databases, object storage and disks in the same way, and the disk-encryption topic earlier in this course uses a master key wrapped by several key slots. Certificate authorities (first topic) are a special case of a secrets engine that issues short-lived credentials. Service meshes issue workload certificates with minute-scale lifetimes. Password managers are secrets servers for humans. Shamir's secret sharing protects root keys for DNSSEC signing ceremonies and certificate authorities, and threshold schemes underlie some hardware-wallet and custody designs. Git-based secret encryption has analogues in Bitnami Sealed Secrets (asymmetric encryption to a cluster key), Kubernetes' own encryption at rest with a KMS provider, and Mozilla's approach in other repositories.

## Examples

**An application fetches database credentials.** A payment service runs in Kubernetes. Its pod authenticates to OpenBao through the Kubernetes auth method; the role maps its service account to the `payments` policy. A Vault-agent-style sidecar requests `database/creds/payments-ro` and renders the username and password into a file with a one-hour lease. When the pod dies, the lease is revoked and the database user is dropped. A leak of the file yields a credential that is already expired.

**Encrypted configuration in Git.** A team stores `values.yaml` for a Helm release as a sops file with three age recipients (two engineers and the CI deploy key). A pull request shows which keys changed and that the values are encrypted. CI decrypts at deploy time with `SOPS_AGE_KEY` from the runner's secret store and runs `sops exec-env`.

**Bootstrap with transit auto-unseal.** A production OpenBao cluster auto-unseals against a smaller "unsealer" OpenBao instance run by another team in a separate account, so that neither a cloud KMS dependency nor a human is needed at a restart. Recovery keys sit with three custodians.

**A failing example: the committed key.** A developer commits `key.txt` along with a sops-encrypted file in a private repository that later becomes public. The history is rewritten, but the key is considered exposed and every secret encrypted to it is rotated.

**A failing example: the broken audit device.** An OpenBao server writes audit logs to a disk that fills. Because it is the only audit device, the server stops answering requests and every service that renews a lease starts failing. A second audit device, a disk alert and a rotation policy prevent the repeat.

## Related problems and ideas

Alternatives include cloud-native managers (AWS Secrets Manager, Azure Key Vault, Google Secret Manager), **CyberArk Conjur**, **Infisical**, **Keycloak** for identity, **Bitnami Sealed Secrets**, **SOPS with Kubernetes operators**, **git-crypt** and **Ansible Vault**, and **SPIFFE/SPIRE** which replaces static secrets with attested workload identities and short-lived certificates. Hardware-backed approaches use TPMs and HSMs for the root of trust. Newer ideas include **secretless access** (proxies that inject credentials so that the application never sees them), **just-in-time access** for humans, and **confidential computing** to protect secrets in use.

## Active research

Open problems include solving secret zero with hardware attestation at scale, safer rotation (discovering consumers automatically), policy analysis (which identities can reach which secrets, given a graph of policies and auth roles), and post-quantum key wrapping for long-lived encrypted archives. In the open-source servers, work centres on compatibility and divergence between Vault and OpenBao, on removing dependence on a single seal key, and on better audit pipelines. For age and sops, post-quantum recipients and plugin ecosystems (age plugins for hardware tokens such as YubiKeys and TPMs) are active.

## Future direction

Expect workload identity (SPIFFE, cloud and Kubernetes tokens) to replace stored credentials where possible, leaving secrets servers for the cases that still need secrets, and issuing short-lived credentials for the rest. Expect OpenBao and Vault to continue to diverge in features, with distribution packaging a deciding factor for adoption on Linux. Expect sops with age or hardware-backed keys to remain the standard way to keep encrypted configuration in Git. For practitioners, the durable principles are least privilege per workload, short lifetimes, an audit trail, a tested recovery path and a plan for what to rotate when a key leaks.
