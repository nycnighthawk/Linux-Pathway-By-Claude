# Compliance as code: turning benchmarks into scans, fixes and evidence

## Define the problem

Organisations are asked to show that their systems follow a standard: the CIS Benchmarks, the DISA STIGs, PCI DSS, HIPAA, ANSSI's guides, a national framework, or the customer's own hardening baseline. In its traditional form this is a document of several hundred numbered controls, a spreadsheet, and an auditor who samples a few servers and takes screenshots. The method fails in predictable ways. Documents are interpreted differently by each reader. Hand-checking does not scale to thousands of hosts or to containers that live for minutes. Evidence is a point in time, and the state of a system a week later is unknown. Remediation by hand is inconsistent and sometimes breaks the service. And benchmark authors, system administrators and auditors each keep their own version of what a control means.

**Compliance as code** is the response: express each control as machine-readable content that can be evaluated against a system, remediated by an automation tool, tailored for a local policy, and reported in a standard format. The same rule then serves as documentation, test, fix and evidence. On Linux the main implementation is the SCAP (Security Content Automation Protocol) family of NIST specifications with the OpenSCAP scanner, and the open-source ComplianceAsCode project that generates content for many distributions from a common source tree. Alternatives include InSpec and other test frameworks, vendor tools (Ubuntu Security Guide, CIS-CAT), configuration-management baselines (Ansible hardening roles) and, for clusters, the Kubernetes Compliance Operator.

The difficulty lies less in running a scan than in deciding what to scan for and what to do with the results. A benchmark applied unmodified can disable a feature the business needs. A rule that checks a configuration file will say pass when the running kernel disagrees. A profile written for one release gives wrong answers on the next. Remediation scripts, run blindly on production, have locked administrators out of SSH. Findings must be reconciled with documented exceptions, risk acceptances and compensating controls, and the evidence must be trusted by an auditor who did not run the scan. This slice covers the content model, scanning and remediation tools, tailoring, integration with image building and configuration management, continuous monitoring, and the limits of automated assurance. The previous topic covered vulnerability scanning; this one covers configuration compliance.

## History and approaches

Hardening checklists predate automation. The US Department of Defense produced Security Technical Implementation Guides from the late 1990s, and the Center for Internet Security issued consensus benchmarks from 2000. Scripts to apply them began as shell, such as the Bastille Linux project (1999) which hardened a system interactively, and Titan, and later Tiger and Lynis, which audited and scored a host. These tools encoded one author's opinions and fell behind new distribution releases.

NIST's SCAP, defined around 2007 to 2009, formalised the idea of standard, interchangeable content. Its parts are **XCCDF** (Extensible Configuration Checklist Description Format), which describes benchmarks as groups of rules, profiles and values; **OVAL**, which holds the machine-evaluable checks; **OCIL** for questionnaires that need a person; **CPE** to say which platforms a rule applies to; **CCE** and **CVE** identifiers; and **ARF** (Asset Reporting Format) for results. A **data stream** bundles these in one file. Red Hat's team created OpenSCAP as an open implementation, and the **SCAP Security Guide** (SSG) as the content for Red Hat and then other distributions. The early lessons were mixed. XCCDF and OVAL XML were laborious to write, so the content lagged behind benchmark updates; vendors published validated content with delays; and the community of authors was small.

The turning point was the move of SSG content to a source tree that *generates* the XML. The **ComplianceAsCode/content** project (2014 onwards, with contributors from Red Hat, Canonical, SUSE, the NSA, DISA, ANSSI and many others) describes each rule as a YAML file with a description, rationale, severity, references to every standard that requires it, an OVAL or Jinja-templated check, and remediation snippets in Bash, Ansible, Puppet, Kubernetes, Kickstart and image-builder blueprint form. A build with CMake and Python produces data streams, Ansible playbooks and Bash scripts per product and profile. Recent releases separate *policies* from *rules*: `controls/*.yml` files list the controls of a standard (for example CIS or STIG) and map each to the rules that implement it, so that a profile is generated from a control file. This is the structure at the heart of the project: rules are written once and shared among many standards.

Other approaches have competed. **Chef InSpec** (and the earlier Serverspec) expresses checks in a Ruby DSL against any target, with profiles shared through a registry, and avoids the XML but also the standardised interchange. **Ansible Lockdown** and the DevSec hardening collection provide roles that apply a benchmark directly. **Open Policy Agent** with Rego checks structured data such as Kubernetes manifests and Terraform plans before they are applied. NIST's **OSCAL** (Open Security Controls Assessment Language, 2019 onwards) addresses the layer above, expressing catalogs, profiles, system security plans and assessment results in JSON, YAML or XML, so that the paperwork of FedRAMP-style authorisation can be generated and exchanged. Each trades coverage, familiarity and standard recognition differently.

## Current state

**Content layout.** In the ComplianceAsCode tree, `linux_os/guide/` holds rules in a directory hierarchy by topic, each with a `rule.yml` and optional `oval/`, `bash/`, `ansible/` and `tests/` folders; `controls/` has policy files; `products/<name>/` configures a product (for example `rhel10`, `ubuntu2404`, `debian12`) with its profiles in `profiles/*.profile`; `shared/templates/` contains templated checks (a file permission, a sysctl value, a package installed or removed) that expand into OVAL, Bash and Ansible for each instance. A rule looks like this in outline: a title, a description, a rationale, a severity, references per standard (`cis@rhel10: 1.1.1.1`, `stigid@ubuntu2404: UBTU-24-100010`, `nist: AC-6`, `srg: SRG-OS-000480-GPOS-00227`), a `template:` section naming a template and its variables, and an optional `ocil` section. For rules that cannot be checked by a template, an OVAL file or a Bash check script is supplied. The rule on exposed kernel pointers shows the shape: a sysctl check for `kernel.kptr_restrict` with its description and references [src: compliance-as-code 543d91c66895efd8].

**Scanning.** On a host, the packages `openscap-scanner` and `scap-security-guide` (or on Ubuntu, `usg`) give the scanner and content in `/usr/share/xml/scap/ssg/content/`. `oscap info FILE` lists profiles; `oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_stig --results results.xml --results-arf arf.xml --report report.html FILE` runs a scan and writes machine and human reports. Each rule reports one of pass, fail, notapplicable, notchecked, informational, error or unknown, and the report shows the rule, its description, the evidence found and the available remediation. `oscap-ssh`, `oscap-podman` and `oscap-vm` scan remote hosts, containers and virtual machine images, and the **OpenSCAP daemon** (`oscapd`) schedules scans. Red Hat Satellite, Insights, Foreman and Ansible Automation Platform provide fleet orchestration and dashboards around the same engine. The documentation walks through the customisation path from the profile list to a tailored profile through the `autotailor` tool and the SCAP Workbench GUI [src: rhel-10-docs a819d3ea3586e4c4].

**Remediation.** The same content generates fixes: `oscap xccdf generate fix --profile PROFILE --fix-type ansible --output fix.yml FILE` writes a playbook (or `bash` or `puppet`), and `oscap xccdf eval --remediate` applies fixes during the scan. Pre-generated playbooks and scripts also ship in `/usr/share/scap-security-guide/ansible/`. A careful workflow is to run in check mode, review the diff, apply to a canary, and re-scan. Fixes that cannot be safely automated (changes to partitioning, disk encryption, banner text that is organisation-specific, accounts) are not generated or require variable values.

**Tailoring.** Policies bend to reality, and the tools support it in a documented way. A **tailoring file** (XCCDF Tailoring) selects or deselects rules and sets variables (password minimum length, session timeout, a list of permitted NTP servers) without editing the data stream. `autotailor --output tailoring.xml --var-value var_accounts_tmout=900 --unselect package_telnet_removed PROFILE-ID BASE-PROFILE` creates one from the command line, and `oscap xccdf eval --tailoring-file tailoring.xml --profile TAILORED-ID` uses it. In the source tree the equivalent is a `.profile` file with `extends:` and a `selections:` list where a line may add a rule, remove a rule with `!rule_id`, or set a variable with `var_name=value`:

```yaml
documentation_complete: true
title: Site baseline, based on CIS Level 1
extends: cis_server_l1
selections:
  - '!service_avahi_disabled'
  - var_accounts_tmout=900
  - sshd_set_idle_timeout
```

Every deviation should have a recorded reason, and the tailoring file belongs in version control with the exception approval.

**Integration with builds.** The best time to harden is at build time. Kickstart can embed a scan and remediation through the `%addon com_redhat_oscap` block; image-building tools take an OpenSCAP profile as part of a blueprint, producing a pre-hardened image, and Red Hat's documentation describes the integration with image builder, where the build applies the profile's configuration and can run the scan to verify it [src: rhel-10-docs b0c0d04a663aa55c]. Packer provisioners, bootc and container builds use the same generated playbooks. The pre-hardened image is scanned again at deploy time so that drift between the golden image and the running host appears. Kubernetes provides the Compliance Operator, which runs OpenSCAP profiles against nodes and platform configuration (including the CIS Kubernetes benchmark and the Red Hat OpenShift STIG) and records results as custom resources.

**Evidence.** ARF files contain the full results with the asset, the profile, the checked values and a timestamp, and can be signed and stored. For auditors, a report listing profile version, scanner version, result per rule, tailoring and exceptions is the artefact. The DISA STIG Viewer and checklists (CKL files) remain the format of record in US defence settings, and tools convert from XCCDF results to them. OSCAL lets the assessment results link to the controls of a framework, so that one scan can feed several frameworks at once.

**The generalised pattern.** The core idea is separation: *what is required* (policy, controls), *how to test it* (checks), *how to fix it* (remediations), *what a given site decided* (tailoring and exceptions), and *what was found* (results). Compliance as code keeps these five artefacts apart, versioned and linked, so that any one can be changed, reviewed and rerun without re-doing the others.

## Assessment: the good, the bad and the ugly

**The good.** A scan of a host against hundreds of rules takes minutes and is repeatable. Rules map to many standards at once, so work done for one profile is reused by another. Remediation generated from the same source as the check has a high chance of matching what the check expects. Tailoring and results are files, so they can be reviewed in pull requests, diffed and attached to tickets. Image-time application removes whole classes of drift. The open development model means that content tracks new releases and benchmark updates quickly, and anyone can read the check for a rule to see what it actually tests.

**The bad.** Coverage is not assurance. A scan reports on the rules in the profile, and a passing score says nothing about the large part of security that benchmarks do not address: application flaws, architecture, access policy. Rules test configuration, not behaviour: a file says the setting is on, while a drop-in or a later directive overrides it. Some controls are inherently manual (physical security, account approval processes) and show as notchecked. Scores invite gaming; teams optimise for the number and defer the controls that are hard. Benchmarks conflict with each other and with applications: a hardening rule that mounts `/tmp` with `noexec` breaks installers, and one that restricts cron to a list breaks a vendor's maintenance job.

**The ugly.** Automated remediation on a live system is a source of outages. Rules that change SSH settings, firewall defaults, PAM stacks or the boot loader can lock out the administrator or stop the machine booting, and the effect may only appear at the next reboot. Content quality varies: a check that is wrong for a given distribution release yields false positives or, worse, false passes, and the volume of rules makes errors hard to spot. A scan run as root on the host to be audited is evidence produced by the system under test; a compromised host can report itself as clean, which is why scans should be paired with independent detection. Version skew between profile, scanner and distribution (a profile for release N scanning release N+1) produces plausible but wrong results. And the human process is fragile: exceptions granted for a year and never revisited, tailoring files copied between teams without understanding, and auditors who accept a green dashboard as the entire control environment.

**Mitigations.** Pin and record the content version, scanner version and tailoring in every result. Test remediation in staging on a clone, and keep a rollback path (console access, snapshots). Apply hardening at image build time and treat runtime remediation as the exception. Review every rule that is deselected, with an owner and an expiry date. Pair the scanner with an independent integrity measure, such as the IMA and attestation mechanisms covered earlier. Sample the results by hand each cycle: choose ten rules, verify the evidence by another route, and record whether the tool was right.

## Applications beyond this domain

The idea of executable policy is used far outside operating-system hardening. Infrastructure-as-code scanners (Checkov, tfsec, Terrascan, KICS) apply rule sets to Terraform and CloudFormation before deployment. Kubernetes admission controllers (Kyverno, OPA Gatekeeper, the built-in ValidatingAdmissionPolicy) enforce rules at the API. Cloud security posture management evaluates account configuration against CIS Cloud benchmarks continuously. Data-protection and privacy controls are being encoded for automated assessment, and financial-sector regulators have begun to publish machine-readable rules (regulation as code). Software supply-chain policy (SLSA levels, Sigstore policy controller) is another instance. The common structure is a catalog of controls, a checker, an exception process and evidence, and OSCAL is an attempt to give them a shared format.

## Examples

**Scanning a server against the STIG.** An administrator installs `openscap-scanner` and `scap-security-guide`, lists profiles with `oscap info`, runs the STIG profile with `--results-arf` and `--report`, and finds 38 failed rules of 400. Fourteen are flagged high severity. She generates a Bash fix for a sample of five, reads them, and applies the ones that do not touch authentication to a staging clone first. The re-scan shows 22 failures remaining, five of which are documented exceptions in the tailoring file.

**A pre-hardened golden image.** A platform team adds a CIS Level 1 profile to the image-builder blueprint for its base image. The build applies the profile, scans the result, and fails if the high-severity rules do not pass. Each virtual machine launched from the image starts compliant, and a weekly scan of running hosts reports drift, which is investigated as an event.

**Compliance across Kubernetes.** The Compliance Operator runs the CIS profile against worker nodes and the cluster configuration. Failures appear as `ComplianceCheckResult` objects, and remediation objects can be reviewed and applied or ignored through a defined process.

**A failing example: the lockout.** A team applies the generated remediation for an SSH profile in one step on a production host. The script sets an idle timeout, disables password authentication and restricts the allowed groups. The administrator's group is not in the list. The next login fails, and the console has no password set either. The correction involves a rescue boot and a rule that no remediation runs without an out-of-band access path.

**A failing example: the stale content.** A scan run with the profile content for the previous release gives a score of 94 percent on a newer distribution. A third of the rules were not applicable because their platform checks failed, and a few checks look at paths that moved. The score was high because rules were skipped, which the report displayed as notapplicable, not fail.

## Related problems and ideas

The neighbouring problem is **drift detection** and the broader question of keeping a configuration in a known state: desired-state configuration (Ansible, Puppet, Salt), immutable and image-based systems, and file-integrity monitoring address it by different means and are the subject of the last topic of this course. **Policy as code with OPA** and **admission control** shift the check from after-the-fact scanning to prevention. **Continuous control monitoring** and **GRC platforms** consume scan results and map them to frameworks. **Threat-informed defence**, using MITRE ATT&CK to select controls by the techniques they prevent, offers a different way to choose which rules matter than the length of a benchmark. Less mainstream: formal verification of configurations against a model, machine-generated exception justifications, and large language models that draft remediation or explain failures, whose output must still be reviewed.

## Active research

Work in this area concerns keeping content in step with fast-moving benchmarks (automatic ingestion of new CIS and STIG releases, differential testing of rules across distributions), measuring rule quality (how often a rule's result disagrees with ground truth), and the semantics of configuration: resolving the real effective value of a setting across drop-in files, includes and environment overrides. The OSCAL community is working on tooling that links catalogs, profiles and results to automated assessment in continuous authorisation programmes. Researchers also study the relation between benchmark compliance and real security outcomes, where the evidence is thinner than the industry's reliance on the practice would suggest.

## Future direction

Expect compliance content to be built into images and platforms by default, with scans in the pipeline rather than quarterly. Expect OSCAL-based exchange to grow in regulated sectors and the STIG and CIS publishers to supply machine-readable content directly. Expect tailoring and exception records to become first-class artefacts with expiry and approval metadata. Expect continuous assurance to rely on attestation (signed results from a measured environment) and not only on the host reporting about itself. For practitioners, the lasting skill is to read a rule's check and remediation critically, to tailor with reasons, and to treat the scan as a regression test for the baseline, not as the definition of security.
