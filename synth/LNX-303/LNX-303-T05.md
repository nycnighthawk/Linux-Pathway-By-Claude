# Seeing what the kernel sees: auditd and Falco for runtime detection

## Define the problem

Prevention fails. A vulnerable web application is exploited, a developer's token leaks, an insider misuses legitimate access. What separates a contained incident from a breach is how quickly someone notices and how much evidence exists afterwards. On Linux the authoritative record of what a process did is the kernel itself: which program was executed with which arguments, which files were opened, which sockets were connected, which privileges were changed. The problem for a defender is to turn this torrent of events into a trustworthy, bounded, searchable record and into a small number of alerts that deserve attention, without slowing the system or drowning the operators in noise.

Two tools approach this from different directions. **The Linux Audit system** is a kernel facility, present since 2.6, that evaluates a list of rules against system calls and file-system watches and emits records through a netlink socket to the `auditd` daemon, which writes them to disk. It was designed for compliance, in the Common Criteria and military tradition, and it can claim completeness: with the right rules every execution or privileged call is recorded, and the system can be configured to halt if the log cannot be written. **Falco**, a CNCF project originally written at Sysdig, was designed for cloud-native detection. It takes a stream of system calls (and, with plugins, cloud and Kubernetes audit events), evaluates them against rules that use a descriptive condition language, and emits alerts to files, syslog, webhooks and message queues. Audit answers *what happened, provably*; Falco answers *what looks wrong, now*.

Failure takes familiar forms. An audit configuration that records everything fills the disk, loses events when the kernel backlog overflows, and produces logs that nobody can read; one that records too little leaves a gap exactly where the attacker worked. Falco rules copied from a repository fire hundreds of times a day on normal behaviour until operators stop reading them, or they miss an attack because the rule keys on a process name the attacker changed. Both tools can be silently disabled by a root attacker unless rules are made immutable and logs are shipped off the host. This slice covers auditd rule design, performance and tamper resistance, log analysis with `ausearch` and `aureport`, Falco's architecture, drivers and rule language, tuning, and the combination of the two in a detection pipeline.

## History and approaches

Auditing is older than Linux. The US government's "Orange Book" (1983) required a trusted system to record security-relevant events, and Unix vendors added BSM-style audit systems. Linux's version was written by Red Hat's Steve Grubb and others from 2004 and merged in 2.6.6, and it was shaped by certification: the Common Criteria's Labeled Security Protection Profile needed an audit trail that included every system call of interest, with the user identity that originally logged in (the **login uid**, `auid`, which survives `su` and `sudo`) recorded in each event. That `auid` field is the audit system's most valuable contribution, because it answers the question "which human started this" even after privilege changes. Subsequent work added file watches (inotify-like `-w` rules), rules by system call and architecture, SELinux AVC messages through the same channel, user-space message injection (PAM, sshd, `sudo`), the `audispd` dispatcher and its plug-ins for remote forwarding, and later the `augenrules` mechanism that concatenates `/etc/audit/rules.d/*.rules` into one loaded file. The Red Hat family and Debian family both ship it, and compliance benchmarks consequently contain dozens of audit rules; the DISA STIG for RHEL 10 requires audit records for successful uses of privileged operations, and ComplianceAsCode generates one rule per privileged command (setuid binaries such as `write`, `utempter` or `fusermount`) to meet them [src: disa-stig 7c3800e4804fe230] [src: compliance-as-code 2aa776a242fcd342].

The approach had well-known costs. The rule matching is in the system call path, so a `-S execve` or `-S open` rule on a busy server adds measurable overhead. The log format is flat key=value text with fields that are hex-encoded when they contain unusual characters, and a single action produces several records (SYSCALL, EXECVE, CWD, PATH) that must be correlated by a serial number. Tools such as `aureport` and `ausearch` and later forwarders (Elastic's auditbeat, `laurel`) address this, but the format has remained awkward. The backlog problem teaches an important lesson: the kernel queue has finite size (`-b 8192` is a common value), and when it overflows the failure mode is set by `-f` (silent, printk, or panic).

Alongside audit came other approaches. **Host-based intrusion detection** tools such as OSSEC and its fork Wazuh read logs and check file integrity from user space. **Sysdig** (2013) captured system calls with a kernel module for troubleshooting and forensic recording, and its open-source security spin-off, **Falco** (2016), added a rules engine; it was donated to the CNCF in 2018 and graduated in 2024. Falco's early kernel module drivers were seen as intrusive, so an **eBPF probe** followed, and then the **modern eBPF** driver using CO-RE (compile once, run everywhere), which does not need a compiler or kernel headers on the host, and requires a reasonably recent kernel with BTF support. The rules and the engine were reworked repeatedly: a "falcoctl" tool distributes signed rule artefacts, plugins extend event sources to AWS CloudTrail, Kubernetes audit logs and GitHub, and in recent releases the event-source and rule-loading machinery has been refactored (specific version milestones should be confirmed, to verify). In the same period other eBPF-based tools appeared with different positions: **Tracee** (Aqua) combines detection and forensics; **Tetragon** (Cilium) can *enforce* by killing a process or overriding a return value in the kernel rather than only alerting; and **KubeArmor** and **Sysmon for Linux** occupy neighbouring niches. The lesson of the whole line is that capturing events is easy and deciding what matters is hard, so the field moved from capture to curated, tunable content.

## Current state

**Audit architecture.** The kernel audit subsystem evaluates rules in a list order for each event class: `task` (at fork), `exit` (system call exit, the usual list), `user` (messages from user space), and `exclude`. The daemon `auditd` receives records through netlink and writes `/var/log/audit/audit.log`, rotating by size and count according to `/etc/audit/auditd.conf`, which also sets the action on a full disk or log error (`disk_full_action`, `disk_error_action`, `admin_space_left_action`) and whether to flush to disk. Rules live in `/etc/audit/rules.d/*.rules` (ordered by file name) and `augenrules --load` compiles and loads them. The common categories are: watches on identity and authentication files (`-w /etc/passwd -p wa -k identity`, `-w /etc/sudoers -p wa -k scope`), time changes, mount operations, kernel module loading (`-a always,exit -F arch=b64 -S init_module,finit_module,delete_module -k modules`), privileged commands by path (`-a always,exit -F path=/usr/bin/sudo -F perm=x -F auid>=1000 -F auid!=unset -k privileged`), network configuration changes, discretionary access control failures (`-S open,openat,truncate -F exit=-EACCES -F auid>=1000 -F auid!=unset -k access`) and, for complete command tracing, `-a always,exit -F arch=b64 -S execve -k exec` (together with the 32-bit counterpart `arch=b32`, a classic omission). The last rule of the file normally is `-e 2`, which makes the configuration **immutable**: it cannot be changed until reboot, so a root attacker who tries `auditctl -D` is refused. Such immutability also means that rule changes need a reboot, which is why changes are tested with `-e 1` first.

**Analysis.** `ausearch -k privileged -ts today -i` searches by key and time and interprets numeric IDs; `ausearch -m EXECVE -ua 1001` finds commands by user; `aureport --auth --failed --summary`, `aureport -x --summary` and `aureport --anomaly` summarise. Because every event carries `auid`, `ses` (session) and `tty`, a reviewer can reconstruct a login session. Remote shipping uses the audisp remote plug-in (`audisp-remote`) or a forwarder reading `/var/log/audit/audit.log`, so that an attacker who deletes the local log has not erased the evidence.

**Performance and volume.** Use filters to keep volume down: exclude noisy events early with `-a never,exit` rules or `-a always,exclude -F msgtype=...`, constrain broad system call rules with `-F auid>=1000 -F auid!=unset` so service accounts do not log, and watch directories instead of full trees. Measure with `auditctl -s`, which reports the backlog and the count of lost messages; a non-zero `lost` value means the configuration is not complete. The backlog limit `-b` should be raised on busy hosts, and `--backlog_wait_time` governs how long the kernel waits when full.

**Falco architecture.** Falco has a driver in the kernel (modern eBPF, classic eBPF, or the kernel module) feeding events to the user-space engine through libscap and libsinsp, which maintain a state table of processes, threads and file descriptors so that a rule can talk about the *container* a process runs in, its parent process chain or the file name behind a descriptor. Rules are written in YAML in files loaded from `/etc/falco/` (the default `falco_rules.yaml` shipped with the project and `falco_rules.local.yaml` or `rules.d/` for local overrides). Three kinds of object appear: **lists** (named collections of strings), **macros** (named conditions), and **rules** with `rule`, `desc`, `condition`, `output`, `priority` and `tags`. A minimal rule that detects a shell started in a container looks like:

```yaml
- rule: Terminal shell in container
  desc: A shell was started with an attached terminal in a container
  condition: evt.type = execve and evt.dir = < and container.id != host and proc.name in (bash, sh, zsh) and proc.tty != 0
  output: Shell in container (user=%user.name container=%container.name cmd=%proc.cmdline)
  priority: NOTICE
  tags: [container, shell, mitre_execution]
```

Fields use `evt.*`, `proc.*`, `fd.*`, `container.*`, `k8s.*` and more. Operators are `=`, `!=`, `in`, `contains`, `startswith`, `pmatch`, and boolean `and`/`or`/`not`. `falco --validate rule.yaml` checks a file, `falco -L` lists loaded rules and `falco -r` adds a rule file. Tuning uses `append: true` to extend a macro or `override:` to change a rule without copying it, so that upstream updates still apply. Alerts are sent to stdout, a file, syslog, a program or HTTP; **Falcosidekick** fans them out to dozens of destinations (Slack, Elasticsearch, object stores, message queues). Falco can also run as a Kubernetes DaemonSet, and its Helm chart deploys the driver and `falcoctl` together.

**Combining them.** Audit is the complete, tamper-evident record, good for compliance and forensics on any Linux host. Falco is the semantic detector, strong where containers and orchestration make "which pod" the question. A typical design keeps a lean audit rule set based on a vendor baseline (the STIG or a community rule set such as `Neo23x0/auditd`), ships both streams to a central store, and uses Falco rules for specific behaviours: reading `/etc/shadow`, spawning a shell from a web server process, outbound connections from a database, writing below `/bin`, loading a kernel module, or changing the `ld.so.preload` file.

**The generalised pattern.** Detection engineering has four stages: *collect* a stream with known gaps, *normalise* it so rules can refer to meaning (user, process lineage, container), *decide* with rules that encode a behaviour and an expected exception, and *respond* by routing to people or automation. Every stage has a failure mode, and the quality of the output depends mainly on the quality of the tuning loop that feeds findings back into rules.

## Assessment: the good, the bad and the ugly

**The good.** Auditd is present everywhere, supported by every compliance framework, and its immutable mode and `auid` give a record that survives privilege changes. Falco's rule language is readable by non-programmers, its container awareness is strong, and the eBPF driver is stable and low-overhead on current kernels. The rule sets of both are community-maintained and mapped to MITRE ATT&CK techniques, which gives teams a vocabulary for coverage.

**The bad.** Both tools produce events, not conclusions. A rule such as "shell in container" fires for every administrator who debugs a pod. Falco's condition language and its state table can disagree with reality: container metadata lookups can lag, so early events lack the container name, and fields can be missing for short-lived processes. Auditd's text format is expensive to parse, its rule syntax has many traps (the `b32` omission above, comparison operators written with the wrong escaping, `-F auid!=unset` versus the old `-1`) and its performance impact on `execve` or `open` rules is non-trivial. Neither tool sees what it does not hook: attacks inside the kernel, in memory-only payloads that avoid system calls, or in an unmonitored namespace.

**The ugly.** The adversary can interfere. A root attacker with the audit rules mutable can delete them, with Falco running can kill it or unload the driver, and with a writable log can edit history. Forwarding events off the host quickly is the main defence, and so is making the host rules immutable. Dropped events are the quiet failure: when the ring buffer or the netlink backlog overflows, events vanish and the tool continues to report a healthy state. Alert fatigue is the human equivalent, and the largest practical cause of missed incidents. Finally, `execve` logging records command-line arguments, which routinely contain passwords, tokens and personal data; the retention and access policy for such logs is a privacy and compliance matter.

**Mitigations.** Write rules from threat scenarios, not from a catalogue. Measure drops (`auditctl -s`, Falco's metrics and `drops` counters) and alert on them. Run in a staging environment and review the first week's output to write exceptions, then keep exceptions in local override files under version control. Make the audit configuration immutable in production, ship events off the host in real time, and protect the Falco service with the same care as a security agent. Redact secrets in the pipeline.

## Applications beyond this domain

The pattern of recording authoritative events and applying rules over them reaches well beyond Linux hosts. Cloud platforms offer audit logs of API calls (CloudTrail, Kubernetes audit, GitHub audit logs), and Falco plugins apply the same rule language to them. SIEM correlation rules and the Sigma open format are the same idea at the log-aggregation layer. Database activity monitoring, Windows event auditing and Sysmon, and endpoint detection and response products all rest on kernel or API event streams and a detection ruleset. In safety engineering, flight data recorders and industrial historians keep a tamper-resistant record for post-incident analysis. The recurring design questions are the same: where is the record kept, how is completeness proven, and who is allowed to turn it off.

## Examples

**A baseline audit configuration.** A compliance team starts from the vendor STIG profile. The rule file begins with `-D` and `-b 8192`, sets `-f 2` on regulated hosts (panic if the log cannot be written, a deliberate choice), includes the identity, privilege and module rules above, and ends in `-e 2`. A scheduled job runs `aureport --summary` and `auditctl -s`, and the report is part of the evidence packet for the auditor.

**Detecting a webshell.** A web server process spawns `/bin/sh`. Audit records the `execve` with the parent process `httpd` and the `auid` of `unset`, since a service has none. A Falco rule `Spawned shell from web server` raises an alert within a second and forwards it to the on-call channel, with the container name and command line. The audit trail then allows investigators to show the full chain of commands that followed.

**A failing example: the `b32` gap.** A team's execve rule contains only `arch=b64`. An attacker compiles a 32-bit binary, which uses the 32-bit system call table, and runs it without any record. The rule must be duplicated with `arch=b32`, and the test suite should include a 32-bit binary.

**A failing example: the silent drop.** A busy host runs a broad `open` rule with a small backlog. During a spike the kernel drops events, and `auditctl -s` shows `lost 41203`. No alert was configured on it. The attacker's activity happened during the spike. The fix is to narrow the rule, raise the backlog, and alert on a rising loss counter.

**A failing example: the noisy default.** A Falco deployment sends all alerts at `NOTICE` and above to a chat channel. Within a day the channel carries thousands of messages from CI runners, which spawn shells in containers legitimately. People mute it, and a genuine compromise is lost in the noise. Tuning by namespace and by image, and sending only high-priority alerts to people, restores trust.

## Related problems and ideas

File-integrity monitors (AIDE, Tripwire, Wazuh's syscheck) look for changes at intervals rather than events as they happen. **eBPF-based enforcement** (Tetragon, KubeArmor) moves from detection to prevention, at the cost of the risk of blocking legitimate work. **Sigma** rules express detections in a vendor-neutral format that compilers translate to various back ends. **Honeytokens** and canary files give very low-noise alerts: a rule on any read of a decoy file almost cannot be a false positive. **Deception technologies**, **UEBA** (behaviour analytics), and **provenance graphs** that connect events into process lineages (research systems such as CamFlow and Tetragon's process tree) are less mainstream approaches to the same problem of making event streams interpretable.

## Active research

Research topics include reducing the cost of in-kernel filtering so more rules can be evaluated before an event reaches user space, handling the container-metadata race, automatically learning baselines of normal behaviour for a workload (profile-based detection from observation), and using machine learning on system call sequences, whose results in practice remain mixed. The security of the monitoring path itself is another area: eBPF programs have been used by attackers for rootkits, and defenders want to detect unexpected BPF programs. Kernel developers continue to extend audit with new record types and to discuss containers-aware audit (per-namespace audit rules), which is not yet fully available in mainline (status to verify).

## Future direction

Expect eBPF to become the default collection layer, with audit retained for compliance records and for its immutable mode. Expect rules to be shared and signed as artefacts, with coverage maps against ATT&CK and with test suites that replay attack traces. Expect more detections to run in-line as enforcement, with careful staging. Operators should plan for event volume, drop monitoring and a tuning budget in the same way they plan for capacity: the technology works, but the value comes from the loop that turns alerts into better rules.
