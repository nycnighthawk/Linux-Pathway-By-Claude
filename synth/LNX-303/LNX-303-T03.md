# Trusting what runs first: Secure Boot and signed kernel code

## Define the problem

Every security control on a Linux machine assumes that the code enforcing it is the code its authors wrote. An attacker who can replace the bootloader, the kernel or a kernel module before or during start-up wins quietly: a **bootkit** runs before any antivirus, a malicious module has full kernel privilege, and a modified initramfs can capture the disk passphrase. The defence is a chain of verification. Each stage of boot checks a cryptographic signature on the next before handing over control, so that code that was not approved by a recognised authority does not run, and the chain begins in firmware, which is the only component an operator cannot reasonably verify by hand.

UEFI **Secure Boot** is that chain's first half: firmware verifies the bootloader and the kernel against keys stored in firmware variables. **Module signing** is the second half: after the kernel is running, it refuses to load kernel modules whose signatures it cannot verify against its own trusted keyring. A third piece, kernel **lockdown**, closes the doors a privileged user could otherwise use to bypass both (writing to memory, loading unsigned code with `kexec`), and appears in the next topic with IMA.

The practical problem for Linux is the political and engineering gap between the keys that firmware trusts and the keys that distributions and administrators use. Almost every PC ships with Microsoft's certificates in the firmware database and no others, so a Linux distribution must pass through Microsoft's signing service for a small first-stage loader, **shim**, and then carry its own trust forward. Administrators who build custom kernels or use out-of-tree drivers (graphics, storage, VPN, DKMS modules) must find a route to sign them that keeps the guarantee intact. Failure looks like a machine that will not boot after a firmware update, an NVIDIA driver that stops loading after a kernel upgrade because it was never signed, a private signing key left in a build tree, or a Secure Boot configuration that is nominally enabled yet trusts a certificate an attacker can obtain. This slice covers UEFI key hierarchy, shim and the machine owner key, signing kernels and modules, revocation through the forbidden signature database and SBAT, and the interaction with disk-encryption policies. Measured boot and the TPM were covered in the encryption topic.

## History and approaches

Before Secure Boot, boot integrity was a matter of convention. The BIOS handed control to whatever was in the first disk sector, and defences such as boot-sector antivirus, BIOS passwords and trusted GRUB (measurement into a TPM through the Trusted Computing Group's static root of trust) detected change but did not prevent it. The UEFI specification added a signature-checking mechanism in version 2.3.1 (2011), and Microsoft required it, enabled by default, for hardware certified for Windows 8. That decision created the Linux problem and drove its solutions. The Linux Foundation and Red Hat, SUSE and Canonical produced shim, a small bootloader signed by Microsoft's third-party certificate that in turn verifies GRUB and the kernel with the distribution's embedded certificate or a key enrolled by the owner. The **Machine Owner Key** (MOK) database, managed by shim and `mokutil`, allows a local administrator to add keys without touching firmware.

The key hierarchy in firmware is simple to describe and hard to manage. The **Platform Key** (PK) identifies the platform owner and authorises changes to the next level; the **Key Exchange Keys** (KEK) authorise updates to the signature databases; the **db** holds certificates and hashes that are allowed to run; the **dbx** holds those that are forbidden. In setup mode the owner can enrol their own PK; many firmware user interfaces made this clumsy, and the standard allowed a vendor to ship a firmware without a user-accessible path. Tools such as `sbctl`, `efitools`, `sbsigntools` and `pesign` came to help owners who want to sign with their own keys.

Failures drove most of the change. In 2020 the **BootHole** vulnerability in GRUB2's configuration parser let an attacker with write access to the EFI system partition run code even with Secure Boot enabled, and the fix required revoking vulnerable GRUB builds, which meant adding hashes to the dbx. Because the dbx is a limited space that shared firmware could not grow indefinitely, the ecosystem introduced **SBAT** (Secure Boot Advanced Targeting), a generation number in a section of each signed binary that shim compares with a policy variable, so that a whole family of vulnerable versions can be revoked in one entry. In 2023 **BlackLotus**, a UEFI bootkit that exploited a Windows boot manager vulnerability, showed that revocation can be incomplete when the cost of a dbx update is a risk of unbootable machines. In early 2024 a shim vulnerability in its HTTP boot handling was disclosed, and in 2025 further issues in GRUB2's file system code (the details should be checked against current advisories, to verify) kept the cycle going. A different class of failure is key management: the 2024 PKfail disclosure, which found firmware shipped with a test platform key labelled as not for production whose private half had leaked, meant that "Secure Boot enabled" was not a trustworthy statement for those machines.

Module signing has a longer story inside the kernel. Linux 3.7 (2012) added `CONFIG_MODULE_SIG`: modules carry a PKCS#7 signature appended to the file, and the kernel verifies it against keys in the built-in `.builtin_trusted_keys` and the secondary keyring. Distribution kernels build their own key at compile time and keep the private half offline, and since kernel 5.x the build removes the ephemeral key after use when `CONFIG_MODULE_SIG_FORCE` is set so that no one can sign extra modules later. Where firmware holds Secure Boot enabled, the kernel's lockdown mode (merged in 5.4 and reachable through `lockdown=` on the command line) makes enforcement unavoidable by forbidding unsigned modules and direct memory access, as the `kernel_lockdown(7)` manual describes [src: man-pages 7bf2448616434cf6].

## Current state

**The boot chain on a typical distribution.** Firmware verifies `shimx64.efi` against the db (which includes Microsoft's third-party certificate). Shim loads and verifies GRUB (or `systemd-boot`) against the distribution's built-in certificate and the MOK list, and checks the SBAT metadata. The bootloader verifies the kernel image through shim's verification protocol. The kernel has the distribution's public key in its built-in keyring, reads the MOK keys passed by shim into its **platform** or **machine** keyring, and loads only modules signed by a key in a trusted ring. An initramfs is not signed by this chain, which is why a unified kernel image (UKI), a single signed PE binary that contains kernel, initramfs and command line, is attractive. Debian's handbook describes the GRUB-on-EFI-with-Secure-Boot setup and how packages `shim-signed` and `grub-efi-amd64-signed` are installed [src: debian-handbook 1ed428421eec7f52]. Libvirt's documentation describes how a guest gets Secure Boot by running OVMF firmware with enrolled keys [src: libvirt-docs 9e871bbb38f3bd4d].

**Inspecting state.** `mokutil --sb-state` prints whether Secure Boot is enabled. `bootctl status` shows the same for systemd-boot. `mokutil --list-enrolled` prints the MOK database; `mokutil --db`, `--dbx`, `--kek` and `--pk` show firmware databases (`efi-readvar` from efitools shows them too). `dmesg | grep -i secure` records what the kernel concluded, and `/sys/kernel/security/lockdown` reports the lockdown mode. `keyctl list %:.platform` or `cat /proc/keys` show the kernel's keyrings.

**Signing a kernel module by hand.** The steps for an administrator who builds an out-of-tree module are: generate a key pair with a certificate carrying the code-signing extended key usage (`openssl req -new -x509 -newkey rsa:2048 -nodes -days 3650 -subj "/CN=Local module signing/" -addext "extendedKeyUsage=codeSigning" -outform DER -out mok.der -keyout mok.priv`), enrol the public certificate with `mokutil --import mok.der` and confirm during the next boot in the blue MOK manager screen using a one-time password, and then sign each module with the kernel's helper `scripts/sign-file sha256 mok.priv mok.der module.ko` (Debian's `kmodsign` and DKMS's built-in signing automate this, using key paths in `/var/lib/shim-signed/mok/` or `/etc/dkms/framework.conf`). `modinfo -F signer module.ko` and `modinfo -F sig_hashalgo` show who signed. Compliance guidance specifies what hash to use; the SCAP rule for module signing hashes asks for SHA-512 in its check text [src: compliance-as-code b2d8c0943afcc66d]. A module signed by a key that is not in a trusted ring fails with "Key was rejected by service" at `modprobe`, and the kernel log names the cause.

**Signing a kernel or bootloader.** To use one's own chain end to end, an owner enrols their keys in firmware (`sbctl create-keys`, `sbctl enroll-keys`, or `efi-updatevar` with signed authenticated-variable files), signs a UKI or kernel with `sbsign --key db.key --cert db.crt --output vmlinuz.signed vmlinuz`, and verifies with `sbverify --cert db.crt vmlinuz.signed`. systemd's `ukify` builds and signs UKIs and can embed signed PCR policy for TPM binding. Enterprises that use their own keys keep Microsoft's keys too, unless the hardware vendor allows removal, since option ROMs on some devices are signed by them.

**Revocation.** Firmware updates to the dbx are delivered through the Linux Vendor Firmware Service: `fwupdmgr get-updates` offers the UEFI dbx update, and `fwupdmgr security` reports a host security attribute for Secure Boot. Shim reads SBAT policies from firmware variables and applies them; distributions ship updated SBAT level files. The cost of a dbx update is that old installation media and rescue discs no longer boot.

**Cloud and virtual machines.** Red Hat's documentation on AWS and Azure explains how a cloud instance image with Secure Boot configured in the platform's UEFI variable store verifies the guest's boot chain in the same way [src: rhel-10-docs 38b832aa8a2d960d]. Cloud variants differ in whether the guest can enrol its own MOK keys, since the interactive MOK manager needs console access (to verify per provider).

**The generalised pattern.** A chain of trust is a list of links in which each link authenticates the next, a small number of anchors at the beginning, a revocation mechanism for each link, and a way to extend trust locally without replacing the anchors. Secure Boot has the anchors in firmware, shim with SBAT as the first link, MOK as the local extension and the kernel keyring as the final anchor.

## Assessment: the good, the bad and the ugly

**The good.** On a configured system, an attacker cannot silently replace the boot components or load a rootkit module through an ordinary privileged process. The chain is auditable (keys can be listed and signatures checked), and the combination with a TPM allows disks to unlock only on a verified boot. Distribution support is mature: mainstream Linux distributions boot with Secure Boot out of the box on commodity hardware, and the shim project's review board vets submissions. The SBAT mechanism, unlike earlier hash-list revocation, scales.

**The bad.** The guarantee is only as strong as every signed component. Any signed binary with an exploitable parser or that offers arbitrary code execution (old GRUB, old shim, signed debuggers, signed kernels without lockdown) is a bypass until it is revoked, and revocation breaks old media. MOK enrolment relies on a person at the console, which is awkward for headless servers and clouds. Out-of-tree modules need a signing workflow that many teams skip by disabling Secure Boot instead, which removes the benefit. Firmware bugs and poor user interfaces for key management make custom keys a risk.

**The ugly.** The trust anchors are mostly controlled by one vendor. Microsoft's 2011 certificates used in the db and KEK are scheduled to expire in 2026, and the replacement 2023 certificates must be present in firmware before binaries signed with only the new key will boot; the details and timelines have been published by Microsoft and by Linux vendors, and any specific claim should be checked against current advisories (to verify). Firmware vendors differ in whether they apply these updates, and some devices will not receive them. A signing key leaked once (for example, a vendor build key or a test platform key) cannot be fully recalled on devices that never update their dbx. And "Secure Boot is on" says nothing about the integrity of the running system after boot: a root user on a system without lockdown can still modify memory or load code through other paths.

**Mitigations.** Keep signing keys on hardware or in an offline CA, use short-lived signing keys for CI-built modules where the workflow allows, enrol keys with the narrowest scope (a dedicated module-signing certificate with only the code-signing usage), enable lockdown in integrity mode, apply dbx and SBAT updates through fwupd, and monitor with `fwupdmgr security` or an equivalent fleet inventory. Test a dbx update on a representative machine first and keep recovery media current.

## Applications beyond this domain

The chain-of-trust design recurs wherever software must prove its provenance before it runs. Android Verified Boot and Apple's secure boot use the same principle from a hardware root. Container image signing (cosign, Notary) applies the idea to filesystem layers, and the Sigstore transparency log applies the revocation and audit lessons of Certificate Transparency to build artefacts. dm-verity and fs-verity extend verification from boot files to whole filesystems and individual files, with root hashes signed through the kernel keyring. UEFI Secure Boot also underlies confidential computing: a confidential VM's firmware measurement is the attestation anchor. In industrial and automotive devices the same ideas appear in code-signing requirements for firmware images. All of them face the same three problems: protect the signing key, handle revocation without bricking devices, and offer a local override that does not undermine the guarantee.

## Examples

**Signing a DKMS module on a laptop.** A laptop with Secure Boot enabled receives a new GPU driver through DKMS. The first installation runs `mokutil --import`, prompts for a one-time password, and on the next boot the administrator confirms enrolment in the MOK manager. Later kernel upgrades rebuild and sign the module automatically with the enrolled key. `modinfo -F signer` shows the local certificate, and `dmesg` shows no rejection.

**Enterprise own-key boot.** A hardened server fleet enrols its own PK, KEK and db through a provisioning step, signs a UKI in CI with the key kept in an HSM, and boots only that image. Microsoft's keys are retained only on hardware where option ROMs require them. The TPM is sealed to PCR 7 with a signed PCR 11 policy, so a kernel update signed by the CI key unlocks the disk without rebinding.

**A failing example: unsigned module after an update.** After a kernel upgrade, a storage driver fails to load: `modprobe: ERROR: could not insert module: Key was rejected by service`. The module was built by DKMS with an ephemeral key that was not enrolled. The cure is a persistent enrolled key and a rebuild, and not the common but wrong remedy of switching Secure Boot off.

**A failing example: leaked key.** A vendor build host's private key is copied to a public repository. Signed binaries made with that key remain accepted until the corresponding certificate or hash is added to the dbx on every machine; any machine that never receives the update stays vulnerable. This is why scoped, short-lived and hardware-held signing keys matter.

## Related problems and ideas

Alternatives that tie trust to measurement instead of to signatures include **measured boot** with a TPM and remote attestation (Keylime, systemd's attestation work), where a verifier decides rather than the machine. **Coreboot with verified boot** and **Heads** put a smaller, open firmware chain in charge for users who distrust the commercial firmware. **Static linking of keys** into a kernel for appliances removes MOK. **Boot with a read-only root and dm-verity** (as in Chrome OS, Android and some immutable distributions) verifies everything that runs rather than only the early boot. Alternatively, **hash-based allow lists** in the db avoid certificate hierarchies at the price of an update for every new binary. Not yet mainstream are firmware-update-signed policy that lets owners restrict MOK, and OpenSSF work on signing for kernel modules with transparency logs.

## Active research

Open problems include making revocation scalable in constrained firmware storage, detecting compromised firmware keys across fleets, verifying the UEFI implementation itself (several academic projects fuzz firmware parsers), and designing local key-enrolment flows that work in headless and cloud settings. The kernel community continues to refine lockdown semantics and the machine keyring, and the Linux Vendor Firmware Service has become a central inventory of firmware security attributes. Post-quantum signatures for firmware are being studied, since firmware is long-lived and the signed chain is hard to rotate (the UEFI forum's position is to be verified).

## Future direction

Expect the migration to the 2023 Microsoft certificates, SBAT-style revocation as the norm, UKIs with signed PCR policies as the default boot format, and tighter coupling between Secure Boot, TPM attestation and disk-unlock policy. Expect more distributions to ship fully signed initrd-less images, reducing the unsigned part of the chain. For administrators, the durable habits are to know which keys the machine trusts, to sign everything that loads in ring zero, and to treat firmware key and dbx updates as scheduled maintenance, not as emergency events.
