# Knowing what you run and what is wrong with it: OVAL, Trivy and SBOMs

## Define the problem

A modern Linux system is an assembly of thousands of components from many authors: kernel, libraries, language packages vendored into applications, container base images, and statically linked binaries whose dependencies are invisible from the outside. New vulnerabilities in those components are published every day. The administrator's question sounds simple, and is hard in practice: *which of my systems contain a component with a known flaw, how severe is it for me, and what do I do about it?* Answering it needs two things that did not exist in usable form until recently: an accurate inventory of what is inside each artefact, and a reliable mapping from inventory entries to vulnerability data that takes into account how distributions actually fix problems.

The inventory is the **software bill of materials** (SBOM), a machine-readable list of components, versions, suppliers and relationships. The mapping is done by scanners, such as OpenSCAP running **OVAL** definitions, Aqua's **Trivy**, Anchore's Grype, or Google's OSV-Scanner, using vulnerability databases fed by the CVE programme, the NVD, vendor advisories and ecosystem advisories. Regulation turns the topic from good practice into obligation: the NIST SP 800-53 control for vulnerability monitoring and scanning (RA-5) requires scanning at defined frequencies, analysing and remediating results, and sharing information [src: nist-sp800-53 31241e40a6655c01]; US federal procurement requires SBOMs from suppliers under the 2021 executive order on cybersecurity; and the EU Cyber Resilience Act requires manufacturers to track the components in their products and to handle vulnerabilities.

The difficulty is not running a scanner. It is that scanner output is noisy and often wrong, in both directions. A distribution backports a security fix into an older version number, so a scanner that compares version strings reports a fixed package as vulnerable. A vulnerable library is present in an image but never loaded, so a finding is true and irrelevant. A statically linked Go binary carries a vulnerable module that no package manager knows about. A critical-rated CVE has no available fix, so the finding cannot be closed. Teams with hundreds of images and tens of thousands of findings need prioritisation that reflects exploitability and exposure, not only a CVSS number. This slice covers the data sources, OVAL and OpenSCAP scanning, SBOM formats and generation, Trivy scanning of filesystems and images, VEX statements, and the process around them. Compliance-profile scanning with SCAP content is the subject of the next topic.

## History and approaches

Vulnerability management started with port scanners and banner checks. Nessus (1998) and OpenVAS, the open-source fork after Nessus went proprietary in 2005, probed running services and matched responses against a plugin database. They found real problems on exposed services but were poor at patch-level questions and at systems behind firewalls, and they needed credentials to inspect local packages. The vocabulary that made data exchange possible came from MITRE: **CVE** identifiers (1999), the **CVSS** severity score from FIRST (2005, now at version 4.0), and **CPE** names, which were meant to identify products but became a notorious source of false matches because their naming is inconsistent. **OVAL** (Open Vulnerability and Assessment Language, MITRE, 2002) took a different approach: a declarative XML language in which a definition states a condition, for example that the installed `openssl` package has an epoch-version-release lower than a given fixed build on a given distribution release, and an interpreter on the host evaluates it. OVAL was folded into the **SCAP** suite, and **OpenSCAP** (`oscap`) is the free implementation. Distributions such as Red Hat, SUSE, Debian and Rocky published OVAL feeds generated from their own advisories, which solved the backport problem because each definition names the exact fixed build in that distribution. Rocky's own guide on CVE hygiene shows the workflow: install the scanner, run `oscap oval eval` with the vendor definitions to produce a result file, render an HTML report, and cross-check results against package changelogs, because definitions may lag the latest advisory state [src: rocky-docs 37b72a826193d1a9].

OVAL's weakness was ecosystem, not design. XML definitions are verbose, the feeds depended on each vendor's effort (several distributions stopped or reduced them; Canonical, for instance, has moved away from OVAL toward other data formats, details to verify), and OVAL covers operating system packages, not the Python, npm or Go modules inside applications. The containers wave exposed that gap. Clair (CoreOS, 2015) scanned image layers for OS package vulnerabilities, and Anchore Engine, Docker's Scout, and Aqua's **Trivy** (2019) followed. Trivy's design choices explain its adoption: a single static binary, no database server, a vulnerability database distributed as an OCI artefact and cached locally, support for OS packages and language lockfiles in one pass, and extra scanners for misconfiguration (Dockerfiles, Kubernetes, Terraform), secrets and licences.

SBOMs have a parallel history. Software composition analysis tools in the 2000s tracked open-source components for licence compliance (Black Duck, FOSSology). Two standards crystallised in the 2010s: **SPDX** from the Linux Foundation, which began as a licence-compliance format and became ISO/IEC 5962 in 2021, and **CycloneDX** from OWASP, designed around security use cases and standardised as ECMA-424 (the ECMA designation should be confirmed, to verify). The log4j incident of December 2021 (Log4Shell) demonstrated the problem in practice: organisations could not quickly say which of their products contained the vulnerable library, and the answer for many was weeks of manual searching. After it, SBOM generation moved from niche to expectation. The NTIA published minimum elements for an SBOM in 2021 (supplier, component name, version, other identifiers, dependency relationships, author of the data, timestamp).

SBOM adoption then met its own lesson: a list of components is not a list of risks. Most listed vulnerabilities are not exploitable in a given product, and producers needed a way to say so. **VEX** (Vulnerability Exploitability eXchange), formalised through CISA's work and implemented in CycloneDX VEX, CSAF and the lightweight **OpenVEX**, lets a vendor state per CVE and product whether it is *not affected*, *affected*, *fixed* or *under investigation*, with a justification such as the vulnerable code never being on an execution path. Trivy can consume VEX documents to suppress findings, and Debian and others publish their own machine-readable security trackers. At the same time, the data supply itself proved fragile: the NVD's backlog of unanalysed CVEs grew sharply in 2024, and uncertainty about the funding of the CVE programme in April 2025 prompted the creation of alternatives such as the EU Vulnerability Database (EUVD) and a stronger role for ecosystem sources like OSV and GitHub's advisory database (details of current status to verify).

## Current state

**Data sources.** A scanner combines several kinds of data. *Distribution security data* is the most accurate for OS packages: Red Hat's OVAL and CSAF feeds, Debian's security tracker, Ubuntu's security notices and their JSON data, SUSE and Rocky advisories. *Ecosystem advisories* cover language packages: GitHub Advisory Database, the OSV schema used by PyPI, Go, Rust and others, and the Go vulnerability database. *The NVD* adds CVSS scores and CPE applicability for CVEs that lack a better source. *Exploitation signals* help prioritise: CISA's Known Exploited Vulnerabilities (KEV) catalogue lists CVEs observed exploited in the wild, and FIRST's EPSS gives a daily probability of exploitation. A prioritisation order that ranks known-exploited entries first, then high EPSS, then CVSS adjusted for exposure outperforms sorting by CVSS alone.

**OpenSCAP and OVAL.** `oscap oval eval --results results.xml definitions.xml` evaluates a definitions file on the local host; `oscap oval generate report results.xml > report.html` renders it; `oscap-ssh` and `oscap-podman` run it against remote hosts and containers; `oscap-vm` and `oscap-chroot` target images. Definitions are fetched from the vendor (for example Red Hat's `security-data` OVAL files, bzip2-compressed). Red Hat's documentation on configuration compliance scanning describes the same tool in its compliance role [src: rhel-10-docs 6028c8077eeb32b0]. An OVAL result lists each definition as true (vulnerable), false, error or not applicable, and each true entry points to the advisory (RHSA, DSA, USN) and CVE identifiers.

**Generating an SBOM.** For an image or directory, `trivy image --format cyclonedx --output sbom.cdx.json IMAGE` or `trivy fs --format spdx-json .` records OS packages and language dependencies it finds. Syft (`syft IMAGE -o spdx-json`) is a dedicated generator that supports many ecosystems. For OS packages, the package manager database is the ground truth (`rpm -qa`, `dpkg-query -W`, `apk info`), and tools wrap it. A component is identified by a **package URL** (purl) such as `pkg:deb/debian/openssl@3.0.15-1~deb12u1?arch=amd64&distro=debian-12` or `pkg:golang/github.com/gin-gonic/gin@v1.9.0`; the purl is what ties an SBOM entry to advisory data. Build-time SBOMs, produced by the build system (BitBake in Yocto, Bazel, Maven, Cargo plugins), are more accurate than SBOMs reverse-engineered from a finished artefact, because they know what went in. SBOMs should be stored with the artefact (attached to an OCI image with `cosign attach sbom` or as an attestation) and signed.

**Scanning with Trivy.** `trivy image IMAGE` downloads the vulnerability database on first run (`--skip-db-update` for offline use, `trivy image --download-db-only` to mirror it), analyses layers, and prints findings with installed and fixed versions and severity. Useful controls: `--severity HIGH,CRITICAL`, `--ignore-unfixed` to hide findings without a fix, `--exit-code 1` to fail CI, `--format json|sarif|cyclonedx`, `--vex file.json` to apply VEX, and `.trivyignore` or a policy file for documented exceptions with an expiry. `trivy sbom sbom.cdx.json` scans an existing SBOM without access to the artefact, which separates generation from analysis. `trivy rootfs /` scans a running host's filesystem, and `trivy k8s` scans a cluster. Trivy matches OS packages using the distribution's own data and so respects backports, which is a main reason its OS results are more accurate than generic CPE matching.

**Process.** A workable programme has five parts: generate SBOMs in CI for every build, scan on build and on a schedule (new CVEs appear after release), triage with exploitation data and context, record decisions as VEX or documented exceptions, and track time to remediate with service-level targets. Rocky's guidance on scanner false positives suggests a verification workflow for any finding: confirm the installed version, read the vendor advisory and changelog for the backported fix, and only then decide [src: rocky-docs 6a2255555d5739aa]. Methods for confirming that a CVE is patched in a distribution package include reading the changelog (`rpm -q --changelog`, `apt changelog`) and checking the vendor's tracker [src: rocky-docs 1e1f354fe5c6e8a6].

**The generalised pattern.** Vulnerability management is a join between two data sets: *what is here* (inventory with stable identifiers) and *what is known to be wrong* (advisories keyed to the same identifiers), followed by a *decision* that adds context (is it reachable, exposed, exploited) and a *record* of that decision that can be audited and reused. Every failure in practice is a failure of identifiers, data quality, context or record-keeping.

## Assessment: the good, the bad and the ugly

**The good.** Scanning is cheap, fast and automatable. Trivy and similar tools give a useful answer in seconds for an image, and vendor OVAL data gives precise, backport-aware answers for the base operating system. SBOMs in SPDX or CycloneDX give a standard way to hand inventory to customers, auditors and regulators, and answering a Log4Shell-class question becomes a search over stored SBOMs. VEX provides a vocabulary for saying that a product is not affected, without silence.

**The bad.** Different tools disagree. Run three scanners on one image and get three lists, because they differ in data sources, in how they handle backports, in which ecosystems they parse and in how they treat unfixed or disputed CVEs. SBOMs generated from a finished image miss statically linked components, vendored code, and anything without a package manager record; stripped Go binaries need embedded build info, which Trivy and Syft read where present. NVD and CPE data produce false positives for any product with an ambiguous name. Scores measure severity in the abstract, not risk to a specific deployment, and most high-severity findings never become incidents.

**The ugly.** Remediation capacity, not detection, is the bottleneck: a scan that produces 4,000 findings across a fleet produces a backlog, not security. Base images age: an image rebuilt yearly accumulates dozens of fixed-upstream-but-not-rebuilt vulnerabilities. Vendor data can be late or absent for a disputed or end-of-life product, and a `unfixed` filter then hides risk that is real. A scanner is itself software with a large attack surface that runs with privileges and parses untrusted images, and the vulnerability database is an update channel that attackers have an interest in: the supply chain of the security tool needs the same controls as everything else. Finally, SBOM and VEX statements can be wrong or stale, and consumers have no standard way to verify them beyond signatures.

**Mitigations.** Prefer distribution data for OS packages and ecosystem data for languages. Generate SBOMs at build time. Pin and verify scanner and database versions in CI, and mirror the database internally. Triage with KEV and EPSS, and record exceptions with expiry dates and reasons. Rebuild images on a schedule so base-layer fixes arrive, and use minimal images to reduce the surface. Use two scanners on critical artefacts when a disagreement matters.

## Applications beyond this domain

The pattern of inventory plus advisory join appears in other fields. Licence compliance uses the same SBOM data to check obligations (FOSSology, ORT, ScanCode). Hardware and firmware supply chains need HBOMs, and machine-learning models are getting ML-BOMs in CycloneDX. Aviation and medical device regulation already require traceability of components, and the FDA's premarket guidance now asks for SBOMs for networked devices. In cloud security, CSPM tools join resource inventory with misconfiguration benchmarks. Provenance attestations (SLSA, in-toto) extend the SBOM idea to record how an artefact was built, and the same signed-statement mechanism carries VEX documents.

## Examples

**Backport false positive.** A scanner reports a critical OpenSSL CVE on a Debian host because the version string is below the upstream fixed version. Debian's tracker shows the fix backported in `3.0.15-1~deb12u1`, which is installed. Trivy, using Debian's data, reports no finding, while a CPE-based tool reports one. The record is a note citing the tracker, not a patch.

**Log4Shell-style query.** A team stores one CycloneDX SBOM per released image. A new advisory names a library version range. A script searches the SBOM store for the purl, produces a list of affected images and owners within minutes, and files tickets, where earlier the same question had taken weeks.

**CI gate.** A pipeline runs `trivy image --severity CRITICAL --ignore-unfixed --exit-code 1` and a VEX document for known non-exploitable cases. A fix has to be released within the service-level target or an exception with an expiry is filed.

**A failing example: the stale database.** An air-gapped environment ships a Trivy database copy that was downloaded once. Six months later scans pass cleanly because the database knows nothing about newer CVEs. The scan exit code was zero and nobody noticed. The pipeline needs a check on the database age and a scheduled mirror update.

**A failing example: the unfixed filter.** A team enables `--ignore-unfixed` globally to quiet noise. A kernel CVE with a published mitigation but no fixed package is hidden for months. The practice is to review unfixed findings separately and to apply mitigations.

## Related problems and ideas

Alternatives to scanning images include **runtime vulnerability prioritisation** (identify which libraries are loaded or reachable, as in eBPF-based tools such as Sysdig or Aqua's runtime features), **reachability analysis** in static analysis (Endor Labs, GitHub CodeQL call graphs), **software composition analysis** in the application security domain, and **rebuild-from-source** approaches: reproducible builds, which let anyone verify that a binary matches its source. Related standards include CSAF for security advisories, **SLSA** for build provenance, **in-toto** attestations, **OSV** as a common schema, and **Sigstore** for signing. Not yet mainstream: SBOM *diffing* to detect supply-chain tampering between releases, and machine-readable **EOL** and **support** data for components.

## Active research

Open questions concern automatic VEX generation (can a tool prove that a vulnerable function is unreachable?), SBOM accuracy measurement (studies repeatedly find large discrepancies among generators for the same artefact), and the quality of CPE and NVD data, which prompted the CVE Programme's push for richer CVE records with machine-readable affected-product data. Researchers also study exploit prediction (EPSS models and their calibration), vulnerability lifetimes in ecosystems, and the effect of dependency pinning on exposure. For OVAL, the open issue is long-term support: whether vendors keep feeds as other formats take over (to verify).

## Future direction

Expect SBOMs to be required by customers and regulators as a matter of course, with CycloneDX and SPDX converging on interoperable profiles and signed, attached SBOMs as the normal delivery. Expect VEX to be produced by vendors by default and consumed by scanners to cut noise. Expect vulnerability data to diversify from a single NVD source to OSV, vendor CSAF feeds and the EUVD. Expect scanners to add reachability and runtime evidence. For the administrator, the durable skills are to read an advisory, to reconcile a version string with a backported fix, to decide on the basis of exposure and exploitation, and to keep an auditable record of why each finding was fixed or accepted.
