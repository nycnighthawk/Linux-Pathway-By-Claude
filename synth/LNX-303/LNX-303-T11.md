# Staying compliant over years: drift, decay and the discipline of continuous assurance

## Define the problem

Passing an audit on a given day proves little about the following day. A server hardened to a benchmark in March is changed by April: an administrator opens a firewall port to debug a problem and forgets to close it, a package update replaces a configuration file, a vendor installer adds a service, a new team member creates a local account, an emergency fix is applied by hand outside the automation. Each change is small and has a reason. Together they carry the system away from its approved state, and nobody notices until an auditor, an attacker or an outage reveals the difference. This gradual divergence between the intended configuration and the real one is **drift**.

Drift is the visible part of a wider problem of *decay*. Standards change underneath a stable system: a new benchmark release tightens a control, a cipher that was recommended becomes deprecated, a certificate authority's root approaches expiry, a distribution release leaves support and stops getting security updates, a regulation adds a requirement. A configuration that was compliant in the year it was built becomes non-compliant without a single change on the host. Add the people dimension: the person who knew why an exception was granted leaves, the ticket that justified it is archived, and the exception outlives its reason.

The practical question for an operator is how to hold a fleet at a known, justified state across years, with evidence, at an acceptable cost. This slice is introductory (awareness depth) and ties together the other topics of this course: the benchmark scans of compliance as code, the integrity mechanisms of IMA and Secure Boot, the detection pipeline, the vulnerability programme and the secrets and key lifecycles. It explains the causes of drift, the main strategies for controlling it, the metrics that show whether control is working, and the governance that keeps exceptions honest. It does not teach a particular tool in depth, since the tools were treated in their own topics.

## History and approaches

Early system administration relied on discipline and documentation: a runbook, a checklist and a periodic audit. Drift was handled by reinstalling when a machine had become too odd to understand. The first mechanisms for continuous enforcement came with **configuration management**. Mark Burgess's **CFEngine** (1993) introduced the idea of *convergence*: describe the desired state declaratively and let an agent repeatedly bring the machine back to it, a promise-theory approach that treats each run as a repair. Puppet (2005), Chef (2009), Salt (2011) and Ansible (2012) followed with different trade-offs: Puppet and Chef run agents that check in every thirty minutes or so and reapply the catalogue, Ansible is agentless and pushes when told to, and Salt supports both. The common lesson is that enforcement frequency defines the drift window: a nightly run bounds drift to a day, a push on demand may leave it indefinite unless something schedules the run.

Detection-only approaches existed in parallel. File integrity checkers (Tripwire, AIDE) compare file hashes with a baseline; compliance scanners (OpenSCAP, Lynis, CIS-CAT) compare settings with a benchmark; both report and do not repair. They are used where the organisation does not trust automatic repair (production systems with change control), or where they provide independent verification of the enforcement system itself. Regulations began to demand continuity: NIST SP 800-137 (2011) defined **information security continuous monitoring** (ISCM) as an organisational programme with defined frequencies for each metric, and FedRAMP requires monthly vulnerability scans and annual assessments with continuous reporting; PCI DSS version 4.0 asks for change-detection mechanisms on critical files and for periodic review that controls remain in place. The vocabulary moved from periodic audit to *continuous assurance*.

A third approach avoids the problem by making hosts disposable. **Immutable infrastructure**, a term associated with the cloud-native movement from about 2013, builds an image once, deploys it unchanged, and replaces instances for any change. Drift cannot accumulate on a host that lives for a day, and the golden image is the single place where compliance is established and scanned. Image-based operating systems (container-optimised distributions, `ostree` and `bootc` image mode, Fedora CoreOS, Flatcar) apply the idea to bare metal: the root file system is read-only and updates are atomic. Red Hat's guidance on securing identity infrastructure makes the system-integrity version of the point, recommending dedicated servers, controlled backups and consistent cryptographic settings, because the most sensitive services are the ones where unreviewed change costs most [src: rhel-10-docs 5a3071a995dd2d06]. For orchestrated environments **GitOps** (Weaveworks, 2017) turned the repository into the declared state and runs a controller (Flux, Argo CD) that continuously reconciles the cluster to it, with an optional self-heal that reverts manual changes.

Failures of each approach are instructive. Convergence tools hide drift by silently fixing it, so that nobody learns why the setting kept changing; run failures went unnoticed for months when an agent stopped checking in; and the catalogue itself decays when nobody updates it for the next distribution release. Detection-only tools produced reports that nobody read, and large backlogs of findings that became permanent. Immutable systems displaced drift from the host to the image pipeline, where it re-emerges as stale base images with unpatched vulnerabilities, and as the pressure to log in and fix a live instance by hand during an incident.

## Current state

**Causes of drift.** It helps to classify what moves a system away from its baseline. *Operator changes* are direct manual edits, usually during troubleshooting, and often without a ticket. *Software changes* come from package updates that alter defaults or replace modified configuration files (`.rpmnew` and `.dpkg-dist` files are the signs), from installers that add users, services or repositories, and from application self-update. *Automation conflicts* arise when two tools manage the same setting, or when a play runs only against some hosts. *Environmental changes* include time, DNS, certificates and licences expiring. *Standard changes* are updated benchmarks and new threat knowledge. *Platform changes* include a hypervisor, firmware or cloud-provider update that alters defaults, such as the metadata service version or the default crypto policy. On Enterprise Linux, system-wide cryptographic policies illustrate the last two: a single setting selects the allowed algorithms for many libraries, and a distribution release may change the default policy or remove a legacy algorithm, so that compatibility with older peers changes without any local edit [src: rhel-10-docs 50a4581cd9b18742].

**Strategies.** Control rests on four strategies, usually combined:

1. *Prevent*: make the baseline hard to leave. Use read-only root file systems, immutable images, removal of interactive access for ordinary changes, SELinux or AppArmor in enforcing mode, and IMA or fapolicyd for executables. Restrict who may use `sudo` and log it.
2. *Converge*: run a configuration-management agent on a schedule that reapplies the desired state, and report each repair as an event, not a silent fix. Reapplication frequency sets the drift window.
3. *Detect*: scan on a schedule and on events. Run OpenSCAP or an equivalent against the baseline weekly or more often, run a file-integrity check, compare package manifests with the image, and alert on settings that the policy marks as critical. Where an authoritative inventory exists (CMDB, SBOM store, Git), compare the live state against it.
4. *Replace*: rebuild hosts and images on a cadence regardless of whether they appear to have drifted. A thirty-day maximum age bounds the accumulation of unknown change.

**Metrics.** Without measurement, claims of control are anecdotes. Useful measures are: the share of hosts that pass the baseline (with the denominator stated); mean time to detect drift; mean time to remediate; the count of drift events per host per month and the settings that drift most often (a ranking that points to the controls worth automating or to a conflicting tool); the age distribution of hosts and images; the number of active exceptions, their age and the number overdue for review; and the freshness of scan data, since a scan from last quarter is not evidence for today. NIST's container guidance makes a closely related point for hosts running containers: tools must be aware of the scale and change rate of containers, automatically profiling the workload and flagging deviations, because manual baselining cannot keep up [src: nist-sp800-guides 76ce8766f24480ef].

**Exceptions and governance.** A baseline without an exception process is either ignored or enforced into outages. A workable process records each exception with the rule, the reason, the compensating control, the owner and an expiry date, as in the profile-tailoring lab of the compliance-as-code topic. Exceptions expire and renew only by explicit review; a monthly report lists those about to lapse. The baseline itself has an owner and a review cycle: when a benchmark is updated (CIS publishes new versions for major releases, DISA issues STIG updates on a regular cadence), the change is assessed, tested on canaries and rolled out, and the tailoring is updated in the same pull request. Changes to the baseline use the same review and testing as application code.

**Lifecycle events.** Some drift is scheduled and predictable. Distribution end-of-life dates, certificate expiries, key rotation periods (the PKI, secrets and encryption topics), cryptographic transitions, and firmware revocation updates (Secure Boot dbx) should be on a calendar with an owner. A fleet inventory that records OS release, support end date and image build date allows a query such as *which hosts run a release that leaves support in six months*. Regulated environments also keep evidence: the signed scan results, the change records and the exception register, stored for the retention period.

**The generalised pattern.** The control loop of any continuous-assurance programme is *define* the desired state, *measure* the actual state, *compare*, *decide* (repair, accept, or change the definition), and *record*. Drift is the gap between the first and second steps. The programme's health depends on the loop's period, the independence of the measurement from the enforcement, and the existence of the last two steps.

## Assessment: the good, the bad and the ugly

**The good.** Continuous approaches make compliance a property of the system and not of the audit calendar. Convergence and immutable images reduce the human work of keeping hundreds of hosts identical. Drift reports expose operational problems (a team that repeatedly opens a port is telling you the baseline blocks a legitimate need). Time-bound exceptions convert vague risk into a managed list. Evidence is produced by the same pipeline that operates the system, so audit preparation shrinks to exporting what already exists.

**The bad.** Every strategy has a blind spot. Convergence hides causes and can fight with a legitimate emergency change; prevention frustrates operators and drives work to shadow systems; detection produces findings faster than people can resolve them; replacement shifts the problem into the image supply chain and requires stateless design that legacy applications lack. Metrics can be gamed, and a high pass rate across a fleet of identical hosts says nothing about the controls that the benchmark does not cover. Baselines that are too strict or poorly tested cause outages, and the response is typically to weaken them for everyone.

**The ugly.** The long-term failures are organisational. Ownership decays: the team that wrote the baseline is reorganised, the exception register becomes a graveyard, the scanner is upgraded and the results change meaning without notice. Legacy systems that cannot be rebuilt or patched collect permanent exceptions, and compensating controls (a network segment, an extra monitor) are not themselves monitored. Scans and agents fail silently; a fleet that reports 98 percent compliance may be reporting on the 70 percent of hosts that still check in. Audit evidence from a stale snapshot is mistaken for current state. And when an incident occurs, the question that cannot be answered is what the system looked like last Tuesday, because configuration history was never kept.

**Mitigations.** Alert on the silence of any agent or scanner, not only on findings. Treat each automatic repair as a logged event and review the top repeating ones monthly. Keep the baseline, tailoring and exceptions in version control with review. Set a maximum host and image age. Calendar every lifecycle event. Measure and publish the metrics above, including exception age. Test baseline changes on canaries before fleet rollout. Keep configuration history and scan results for the retention period so that past states can be reconstructed.

## Applications beyond this domain

Drift is a general property of managed systems. In cloud accounts, **configuration drift** between Terraform state and the real resources is detected with `terraform plan` and drift-detection services; the same GitOps reconciliation applies to Kubernetes clusters, network device configs (with tools such as Batfish or Oxidized), databases (schema drift) and application feature flags. In safety-critical engineering, configuration management and baselining (aircraft software loads, medical device firmware) face the same issues under stricter regimes. In organisations, policy drift between written procedures and actual practice is the human analogue, and the same remedies of ownership, review and measurement apply. Enterprise architecture practice uses "fitness functions" in the evolutionary architecture literature to detect architectural drift automatically.

## Examples

**Weekly scan with an exception clock.** A platform team scans every host weekly with the baseline profile, stores the ARF reports centrally and compares each week's results with the previous week. A dashboard shows pass rate, new failures and exceptions within thirty days of expiry. In the first quarter the top repeating drift is a logging setting changed by a monitoring agent's installer, which leads the team to fix the installer's package, not to fight the setting every week.

**Image rebuild cadence.** A team builds a hardened base image monthly, scans it at build, signs it, and replaces every instance within thirty days. Hosts that fail to roll are flagged to the service owner. A critical vulnerability triggers an out-of-cycle rebuild. The baseline updates when a new benchmark version lands, in the same pull request that updates the profile.

**A failing example: the silent agent.** A configuration-management agent stops on forty hosts after a certificate expires on the server. Because only failures are alerted, nothing is reported, the hosts drift for five months, and the next audit finds them out of compliance. The fix includes an alert on hosts that have not checked in within a day.

**A failing example: the permanent exception.** An exception for an outdated cipher, granted for a legacy partner, has no expiry. Four years later the partner is long gone, the cipher is still enabled on the border service, and a scan finding that the team had learned to ignore becomes a vulnerability in the news. The register required an expiry and a review.

## Related problems and ideas

Neighbouring subjects are **change management** and the question of how to approve emergency changes without losing track of them; **asset management** and the accuracy of inventories; **chaos engineering** and **game days** as exercises that test whether controls and recovery really work; **policy as code** for admission control, which prevents drift on cloud and cluster configuration instead of detecting it; **attestation-based continuous assurance**, where hosts prove their state cryptographically to a verifier (the IMA and TPM topics); and **continuous authorisation** programmes that replace the three-year authority-to-operate cycle with a live feed of evidence, supported by OSCAL. Less established is **self-healing** security automation that reverts a deviation only after consulting a risk model, and the use of language models to summarise drift and propose remediation, which still needs human approval.

## Active research

Open questions include how to measure the *security value* of compliance work (does a higher pass rate lower incident rates?), how to detect semantic drift in configuration (an unchanged file with a changed meaning because of an upgrade), how to scale continuous attestation to millions of devices, and how to represent exceptions and compensating controls in machine-readable form so that tools can reason about them. There is ongoing work on reproducible builds as the basis for trustworthy images, and on benchmark publishers moving to machine-readable updates so that tooling can track change with less lag.

## Future direction

Expect continuous assurance to replace point-in-time audits in more regulated sectors, with evidence generated by pipelines and exchanged in OSCAL or similar formats. Expect more infrastructure to move to image-based and immutable operation, which turns drift control into supply-chain control. Expect lifecycle events, notably certificate lifetimes and cryptographic transitions, to speed up and to be automated. For practitioners the first step is modest and effective: pick a small number of critical controls, measure them continuously, make each exception expire, and treat the silence of a monitor as an incident.
