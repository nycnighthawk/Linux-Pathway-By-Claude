# Investigating a compromised Linux host without destroying the evidence

## Define the problem

When a Linux system is suspected of compromise, two goals pull against each other. The business wants the service back, quickly. The investigator wants to know how the attacker got in, what was touched, whether the attacker still has access elsewhere, and, sometimes, to produce evidence that will stand up with a regulator, an insurer or a court. Every action taken on a live machine changes it: running a command alters memory and access times, rebooting destroys volatile state, reinstalling erases the disk. The art of basic forensics is to collect the most fragile and most informative data first, in a way that is recorded and repeatable, to preserve a copy of the rest, and to analyse the copy rather than the original.

The problem divides into stages. *Triage*: is this really a compromise, and how bad is it, using a small number of safe commands. *Containment*: stopping further damage without wiping evidence, for example by isolating the network port and not by powering off. *Acquisition*: capturing volatile data (processes, connections, memory) and then a disk image, with cryptographic hashes and a record of who handled what. *Analysis*: building a timeline from logs and file-system metadata, finding persistence and attacker tools, and identifying the entry point. *Reporting and recovery*: documenting findings, closing the entry point, and rebuilding from known-good sources. This slice covers a first-responder's technique on a single Linux host, the artefacts that Linux leaves behind, the tools for imaging and analysis, and the limits of what can be concluded. It does not cover malware reverse engineering, network forensics at scale, or legal procedure beyond the basics of chain of custody.

Failure in this area is usually the responder's own. A well-meaning administrator logs in as root, runs `ls -l` through directories, updates packages, and deletes the attacker's files, which overwrites the very timestamps that showed what happened. A machine is rebooted, and the in-memory implant, the open network connections and the deleted-but-running binary all vanish. A tool run from the compromised system's own `PATH` is itself a trojaned program. A disk is imaged without a hash, and later nobody can show that the copy is faithful. The ground rules are therefore as important as the commands.

## History and approaches

Computer forensics began as a law-enforcement discipline in the 1980s, concerned with seized personal computers and evidence rules. The Unix incident-response tradition grew from the 1989 to 1990s cases of academic and government break-ins. Dan Farmer and Wietse Venema's **The Coroner's Toolkit** (1999) and its successor **The Sleuth Kit** by Brian Carrier (2000s), with the Autopsy browser, established the open-source toolchain for file-system analysis: reading the on-disk structures directly, recovering deleted files from unallocated inodes and building a *mactime* timeline of modification, access and change times. Farmer and Venema's 2005 book on forensic discovery set out the principle of the **order of volatility**: gather data in order from the most short-lived (CPU registers and cache, memory, network state, running processes) to the most durable (disk, backups, logs elsewhere). RFC 3227 (2002), *Guidelines for Evidence Collection and Archiving*, codified the same approach and the practice of a documented chain of custody.

Linux's own evolution changed the landscape in ways that taught lessons. File systems with journals (ext3, ext4, XFS) made recovery of deleted files harder, because inode data are zeroed on deletion, and the carving of content from unallocated space replaced inode recovery. SSDs with TRIM and discard make deleted content disappear quickly. Encryption at rest, as covered in the earlier topic on LUKS, means that a powered-off disk is unreadable without the key, so capturing a live system's memory, which holds the key, became more important. Journald's binary logs and then containers (where processes and files vanish with the container) required new approaches. The rootkit threat moved from replacing system binaries (the classic trojaned `ps` and `ls`) to loadable kernel modules and, more recently, eBPF-based hiding, so that user-space tools on the live host cannot be trusted: this is the central reason to prefer analysis of an image and of memory with an independent toolkit.

Memory forensics evolved from carving strings out of `/dev/mem` through **Volatility** (2007), a framework that parses the kernel's data structures from a memory image to list processes, sockets and modules, including those hidden from the live system. Linux memory analysis needs matching kernel symbol information, which is a continuing practical difficulty, and acquisition tools such as **LiME** (a kernel module), **AVML** (Microsoft, user-space, using `/proc/kcore`) and **fmem** rely on the kernel's cooperation. Lockdown mode, discussed in the integrity topic, restricts access to `/dev/mem` and unsigned modules and so affects acquisition choices; a signed acquisition module or a hypervisor-side snapshot may be needed.

Live-response automation matured with the cloud. Instead of a human typing commands, an agent collects a standard set of artefacts from many hosts: GRR (Google), **Velociraptor** (a query-based tool, with a flexible artefact language), osquery (an SQL interface to system state), and the **Unix-like Artifacts Collector** (UAC), a shell-script collector for hosts where no agent exists. Cloud and virtualised hosts can be captured by snapshotting the disk and, for some hypervisors, memory, from outside the guest. The Debian handbook's guidance for a compromised machine is a compact statement of the older, still valid practice: after service restoration, examine disk images mounted read-only, with the options that prevent execution and timestamp changes, look at what was modified and executed, read shell histories and logs, compare against a known-good backup, and use specialised tools such as Sleuth Kit for deleted content [src: debian-handbook b252cc8719ec05e0].

## Current state

**First principles.** Four rules guide any investigation. *Preserve*: avoid changing the evidence, work on copies, mount read-only. *Document*: keep a log of every command, time and observation, from a separate system if possible, and hash everything collected. *Prioritise by volatility*: memory and network state before disk, disk before backups. *Do not trust the host*: run static, trusted binaries from external media, or collect with tools that read raw structures. A responder also decides early whether to isolate the machine (disconnect the network at the switch or firewall, which keeps memory and processes but stops exfiltration) or to leave it running to observe the attacker, which is a business and legal decision.

**Live triage.** A short sequence, run from a mounted read-only toolkit or through a trusted shell and logged to external storage, captures the most volatile state: `date`, `uptime`, `hostname`, `uname -a`; `who`, `w` and `last` for sessions; `ps auxwwf` for the process tree (look for processes with no controlling parent, in odd paths such as `/tmp`, `/dev/shm`, or with names imitating kernel threads); `ss -tulpen` and `ss -tanp` for listeners and connections with their owning processes; `lsof -nP +L1` to find files that are open but deleted from disk, a typical sign of a running binary the attacker removed; `ls -l /proc/PID/exe` and `cat /proc/PID/cmdline` to expose the real binary and arguments (`/proc/PID/exe` can be copied out even if the file on disk is gone: `cp /proc/PID/exe /evidence/`); `lsmod` and `/proc/modules` for unexpected kernel modules, and `/sys/module` against `lsmod` for hidden ones; `mount`, `df`, `ip a`, `ip route`, `iptables-save` or `nft list ruleset`; and `cat /proc/net/*` as a cross-check against the output of tools. Each output is redirected to a file on an external drive or sent to a remote collector, never saved on the suspect disk.

**Persistence and artefacts to examine.** Attackers need to survive reboots, and Linux offers many places: cron (`/etc/crontab`, `/etc/cron.*`, `/var/spool/cron`), systemd units and timers (`/etc/systemd/system`, `~/.config/systemd/user`, generators), init scripts and `rc.local`, shell start-up files (`.bashrc`, `.profile`, `/etc/profile.d`), SSH keys (`~/.ssh/authorized_keys` and `authorized_keys2`, `sshd_config` with `AuthorizedKeysCommand`), the dynamic linker (`/etc/ld.so.preload` and `LD_PRELOAD` in service environments), PAM modules, kernel modules loaded through `/etc/modules-load.d`, user accounts with unexpected UID 0 or empty passwords (`awk -F: '$3==0' /etc/passwd`), setuid files (`find / -xdev -perm -4000 -type f`), `at` jobs and web application directories. For user activity, `.bash_history` (and the equivalents for zsh and python), `/var/log/auth.log` or `/var/log/secure`, `journalctl --since`, `lastlog`, `wtmp` and `btmp` (read with `last -f` and `lastb -f` on a copy), the audit log if enabled, web server access logs and application logs, and package manager logs. Package databases verify binaries: `rpm -Va` and `debsums -c` list files that differ from the packaged version, which finds replaced system binaries, with the caveat that an attacker with root can modify the database as well.

**Time.** Time is the organising dimension. A Linux file has modification time (mtime), access time (atime, often relaxed by `relatime`), inode change time (ctime) and, on ext4 and XFS, a birth or creation time (crtime) that `stat` shows and `debugfs` reads on ext4. Tools that list files by time are `find / -xdev -newermt '2026-11-01' ! -newermt '2026-11-15'`, and the Sleuth Kit's `fls -m / -r image` followed by `mactime -b body -d` builds a body-file timeline. Plaso (`log2timeline.py`) merges file times, logs, browser history and more into one super timeline. Timestamps can be forged (`touch -d`, and `debugfs` writes) but ctime cannot be set from user space, which makes disagreement between mtime and ctime a clue. Clock and time-zone errors contaminate timelines; record the host's offset from a trusted clock at acquisition.

**Disk acquisition.** Prefer a snapshot or image taken from outside the guest (hypervisor snapshot, cloud volume snapshot, a hardware write blocker for physical disks). Where that is impossible, boot a trusted live system and image the block device with `dd if=/dev/sdX of=/evidence/sdX.img bs=4M conv=noerror,sync status=progress`, or better with `ddrescue` or `dc3dd`, which log errors and hash during the copy; compute `sha256sum` of the source and the image, and record both. Encrypted volumes need the key from memory or the recovery passphrase; imaging the live decrypted mapper device may be the only way. Mount the copy read-only with `losetup -rP` and `mount -o ro,noload,nodev,noexec,noatime` (`noload` prevents journal replay on ext4), so that no write changes the evidence.

**Memory acquisition.** On a live host use `avml /evidence/mem.lime` or LiME loaded with `insmod lime.ko "path=/evidence/mem.lime format=lime"`, with the module built for the exact kernel, preferably on another system, because compiling on the suspect host changes it. For Volatility 3, obtain the symbol table (ISF file) for the kernel version from the distribution's debug packages or a generation tool, then run plug-ins such as `linux.pslist`, `linux.psscan`, `linux.sockstat`, `linux.lsmod`, `linux.check_modules`, `linux.bash` and `linux.malfind`; differences between `pslist` (walks the kernel's list) and `psscan` (scans memory for task structures) reveal hidden processes. Virtualised hosts can be paused and dumped from the hypervisor.

**Containers and cloud.** Containers add layers: collect the container's filesystem (`docker export`, `crictl`, or the overlay directories), its configuration (`docker inspect`), logs and the host namespace view with `nsenter`, and capture host evidence, because the attacker may have escaped. In Kubernetes, preserve the pod (cordon the node rather than delete the pod), take the node's disk snapshot, and record the cluster's audit log. In the cloud, API logs (CloudTrail and equivalents) often give the entry point before any host analysis.

**The generalised pattern.** Evidence handling follows a repeating cycle: *identify* sources, *collect* in order of volatility with hashes, *examine* copies with independent tools, *correlate* in a single timeline, and *report* with a reproducible method. The reliability of conclusions depends on the independence of the tools from the compromised system and on the completeness of the record.

## Assessment: the good, the bad and the ugly

**The good.** Linux exposes a great deal: `/proc` shows live process internals, text logs are easy to read and correlate, file-system metadata is rich, and the toolchain is open and scriptable. Collection scripts are easy to prepare in advance, and well-run teams practice with images from known compromises. Agentless collectors and cloud snapshots mean evidence can be captured quickly and at scale.

**The bad.** Much of the evidence is volatile or absent by default. Logs are local and attackers delete them; `relatime` weakens access times; auditing is rarely enabled with useful rules; ephemeral containers and autoscaled hosts disappear before anyone looks. Journals and rotated logs have limited retention. Kernel and eBPF rootkits make live observation unreliable. Memory analysis demands exact symbols and skilled interpretation. Encryption protects the attacker's staging data as well as yours. For most small organisations, no one has practised.

**The ugly.** Responders compromise evidence in the first ten minutes with good intentions, and an investigation that does not preserve evidence may fail legal tests. Conclusions can be over-stated: absence of a log entry is not evidence of absence, a timestamp is only as good as the clock, and a single odd file may be a legitimate administrator's work. Anti-forensics (log wiping, timestomping, secure deletion, in-memory-only payloads, living-off-the-land use of normal tools) means the sure answer to *how did they get in* is sometimes unattainable. Attribution of the attacker is a different and harder question than reconstruction of what happened. And the business pressure to restore service means rebuilds happen before analysis ends, which leaves residual risk if the entry point was never found.

**Mitigations.** Prepare before an incident: central logging with off-host copies, process and network audit rules (see the Falco and auditd topic), a tested collection kit on read-only media, snapshot permissions for responders, and a runbook with decision points and contact lists. Keep time synchronised. In an incident, isolate before touching, capture memory before shutdown, hash everything, and keep a timestamped notebook. Rebuild from known-good sources and rotate credentials the compromised host could read, treating every secret on it as exposed.

## Applications beyond this domain

The same discipline applies to other systems. Windows and macOS forensics follow the same order of volatility with different artefacts (registry, event logs, prefetch, unified logs). Mobile device forensics extends it to phones. Cloud incident response uses control-plane logs and snapshots as the equivalent of a disk image. Digital forensics for IoT and automotive systems uses the same imaging and timeline methods on flash storage. Beyond computing, the principles of preserving a scene, documenting handling and analysing a copy are those of any evidence discipline, and the same thinking underpins reliability engineering post-incident reviews, where timelines built from logs reconstruct failures.

## Examples

**A web server with a webshell.** An alert shows a shell spawned by the web server (as in the detection topic). The responder disconnects the host from the network, captures memory with AVML, snapshots the volume, and records `ss` and `ps` output. In the image, `find -newermt` lists files created at the time of the alert, which includes a PHP file in an upload directory; web logs show the POST request that uploaded it, and `.bash_history` of the web user is empty but cron contains a new entry fetching a script every five minutes. The timeline links the first vulnerable-plug-in request to the upload ten seconds later. Remediation: patch the plug-in, rebuild the host, rotate database credentials.

**Deleted but running.** `lsof +L1` shows a process running from a deleted file `/tmp/.x`. The responder copies `/proc/PID/exe` to evidence storage before anything else, hashes it, and passes it to malware analysis. Killing the process first would have lost the only copy.

**A failing example: the helpful reboot.** An administrator reboots a suspected host to restore the service. Memory is gone, the network connection to the command-and-control address is gone, the attacker's loader was in `/dev/shm`, which is also gone, and the only trace is a cron entry that cannot say what it fetched. The investigation can say that the host was compromised but not how.

**A failing example: the trojaned ps.** A responder runs `ps` and `netstat` on the live host and sees nothing unusual. A user-space rootkit had replaced both binaries and filtered the output. An independent `/proc` walk with a static binary from read-only media shows the extra process and its connection.

## Related problems and ideas

Neighbouring areas are **malware analysis** (static and dynamic study of recovered binaries), **threat hunting** (proactively searching telemetry for compromise before an alert), **network forensics** (full packet capture, NetFlow and DNS logs), **log forensics at scale** in a SIEM, and **eDiscovery**. Alternatives to post-incident imaging include **continuous recording** with eBPF-based tools (Tracee, Tetragon, Falco with capture), which keep a history of process execution off-host, and **immutable infrastructure**, where a suspect instance is replaced by a fresh one and the old one is preserved in quarantine for analysis. Less mature ideas include hardware-assisted introspection from a hypervisor (so that analysis does not depend on the guest kernel) and automated triage with large language models, whose conclusions need verification.

## Active research

Research addresses live memory analysis without symbols (deriving structure layouts from the image itself), detection of eBPF and kernel-module rootkits, forensics for containers and serverless platforms where state is short-lived, and recovery of data from modern file systems (btrfs, ZFS, F2FS) and from encrypted and SSD storage. Standardisation efforts such as the Cyber Observable eXpression (CybOX successors in STIX) and Forensic Data Formats (for example the CASE ontology) address interchange of findings. The practical open question for operators is how much telemetry to keep off-host, for how long, at what cost and privacy exposure.

## Future direction

Expect more investigation to start from cloud and platform snapshots and from always-on telemetry than from a responder at a console. Expect memory acquisition to be integrated with hypervisors and confidential-computing platforms, where the host cannot read guest memory, and so forensics must be planned with the guest owner. Expect tooling for containers to improve, and the Linux kernel to add audit and tracing features designed for evidence. For the administrator, the durable skills are procedural: know the order of volatility, record everything, keep the original untouched, and practise on a lab machine before the real incident.
