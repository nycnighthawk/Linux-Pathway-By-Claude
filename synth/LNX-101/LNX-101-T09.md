# Bundling and shrinking files: archives, compressors and the formats built on them

## Define the problem

Moving or storing a directory tree raises two separate problems that are easy to confuse. The first is packaging. A tree is thousands of separate files, each with a name, an owner, permissions, timestamps and sometimes links, extra attributes or special types. Copying them one by one over a network is slow and loses information; storing them on tape requires a single sequential stream. People need one object that holds the whole tree and can be unpacked into an identical tree elsewhere.

The second problem is size. Text, logs and many binary formats are highly redundant, so a program that squeezes the redundancy out can cut storage and transfer costs severalfold. Compression, however, costs processor time and memory, and the best compressors are the slowest. Different situations want different points on the trade-off curve: a nightly backup wants strong compression, a live-system snapshot wants speed, and a software release wants small files that decompress quickly on every user's machine.

Unix separated these two concerns, which is the key to this topic. One tool packs files into a stream without shrinking it, another shrinks any stream, and the two combine through a pipe. Failure shows up as an archive that restores with the wrong owner or loses links, a file that cannot be unpacked on another system because its format is unknown there, a backup that cannot be read because the compressor is no longer installed, or an extraction that overwrites files outside its destination. The scope here covers the common archive formats and compressors on Linux and their safe use; backup strategy and tools are part of the storage course.

## History and approaches

The tape archiver, tar, appeared in the seventh edition of Unix in 1979 as a way to write file trees to magnetic tape, which accepts only sequential data. It stores each file as a header block followed by the data padded to a fixed block size, and ends with blocks of zeros. Its design is a stream of independent members with no index, which suited tape but means that finding one file in a large archive requires reading through it. A competing archiver, cpio, from the same era and built around file names fed on its input, took a different approach and remains in use for a few specific purposes. The Rocky Linux documentation describes both [src: rocky-docs 16c2c07dd361bb89] [src: rocky-docs f644d85f0dda975f].

The original tar format limited name lengths and lacked fields that later systems needed. Standardisation produced the ustar format in 1988 and then an extensible format with variable-length records, called pax, around 2001. The GNU implementation added its own extensions and became dominant on Linux. Because of the many dialects, modern tools read all of them and write one chosen by an option. A different archive format, ar, with simple headers, is used for static libraries and, perhaps surprisingly, for Debian packages, which are an ar container holding compressed tar members [src: man-pages 7db09f39c3fe628b].

Compression has its own lineage. Early Unix used a program based on the LZW method, which became entangled in a patent dispute in the 1990s. The GNU project responded with gzip, written by Jean-loup Gailly and Mark Adler and released in 1992, which uses the DEFLATE algorithm that combines dictionary matching with Huffman coding and had already appeared in a popular DOS archiver. DEFLATE has been so widely adopted that it is also the basis of the zip format, of web transfer encoding and of the library used inside Git. A few years later the bzip2 tool, by Julian Seward, offered better compression through a block-sorting transform, at a cost in speed. In the 2000s the xz tool arrived, built on the LZMA algorithm from the 7-Zip project, with much smaller output but high memory use for compression. Zstandard, created by Yann Collet and open-sourced in 2015, set out to match or beat gzip's speed while approaching xz's ratio, using a fast entropy-coding technique, and was formalised in an internet standard in 2021.

Not every approach succeeded. Compressing each file separately, as zip does, allows random access but loses the gain from redundancy across files; compressing the whole archive as one stream, as tar does with a compressor, gives better ratios but cannot extract one file without decompressing everything before it. Neither wins in every case. Encryption and compression were sometimes combined in a single tool, which produced security bugs; the modern view is to keep them separate and compress before encrypting.

The pattern that emerged is a toolbox with a clean separation: an archiver that preserves file-system structure, a family of interchangeable stream compressors with different trade-offs, and conventions for naming the combinations.

## Current state

The archiver has a few modes: create, list, extract, and append or update. It takes file names, and recursively archives directories, recording each member's name, type, owner, group, mode and modification time. Options control whether leading slashes are stripped from names, whether owners are recorded by number or name, whether extended attributes, access lists and security labels are saved, how links and sparse files are handled, and which directory to change into before acting. The Rocky Linux documentation lists the common auxiliary options and shows the standard idioms for backing up and restoring with it [src: rocky-docs 175a064141e82aaa] [src: rocky-docs 8d8f74816c9fba3c].

Compressors are all used in the same way: they read a stream, write a stream and use an exit status. The command-line archiver can invoke one by an option, selecting gzip, bzip2, xz or zstd, and recent versions detect the compression automatically when extracting. The file extensions follow convention: the archive suffix plus the compressor's suffix. Each compressor offers a level setting, where higher levels give smaller output at greater cost, and some offer multi-threaded operation and an option to produce output friendly to incremental synchronisation.

The ratio and speed ordering is a rule of thumb. Gzip is fast, ubiquitous and moderately effective. Bzip2 is smaller and slower and has largely lost ground. Xz gives the smallest output at the highest compression time and memory, with fast decompression, which suits software distribution where files are compressed once and read many times. Zstandard offers a wide range of levels, from near-gzip speeds to near-xz sizes, and decompresses very fast at every level, which explains its rapid adoption in package formats, in kernel and initial-ramdisk images, in file systems and in container layers. The dracut documentation shows how the boot image compressor is configured [src: man-pages 9bd0e67cf821dc7e].

Several details matter. Compressed data does not compress again, so recompressing a JPEG or an already-compressed archive wastes time. Integrity matters: compressors store checksums and have a test mode, and archives should be verified after creation. Python's standard library exposes the same formats, with a module for tar and helpers for making archives, along with the security options described below [src: python-docs 369be17e3dd7b76b] [src: python-docs 4e9f3f3150fd9b78].

## Assessment: the good, the bad and the ugly

The good is the flexibility of the separation. Any compressor can be applied to any stream, so improvements arrive without changes to the archiver, and an archive piped over an encrypted network connection copies a whole tree with attributes preserved, in a single command and with no temporary file. Formats are open and implemented by independent tools, so data remains readable decades later. The modern compressors give a free choice of trade-offs.

The bad is that the model puts a heavy burden on the user to choose and to remember. The format is not always obvious from a file's name; extensions can lie. A tar archive has no index, so listing and extracting a single member from a large compressed archive reads the whole stream. Archives are fragile in the face of corruption: damage in the middle of a compressed stream can make everything after it unreadable. Memory and time costs of the strongest settings can overwhelm small machines, especially when decompressing a file created with a very large dictionary. Preserving everything is also not the default: extended attributes, access lists and security labels are omitted unless options request them, and restoring as an ordinary user cannot recreate ownership.

The ugly concerns safety and trust. Extracting an untrusted archive is dangerous, because a member's name can include parent-directory components or be an absolute path, and a link member can point outside the destination, so careless extraction overwrites arbitrary files. Python's tar support added extraction filters to reject such members and has been moving toward making a safe filter the default [src: python-docs 369be17e3dd7b76b]. Decompression bombs are small files that expand to enormous sizes and exhaust disk or memory. The most striking recent case is the 2024 backdoor in the xz library, which was discovered by an engineer who noticed a small slowdown in remote login. The malicious code was added through the project's release tarballs, which differed from the public source repository, and it targeted a library that some systems load into the secure-shell daemon. The incident showed how a compression library with a single overworked maintainer, a build step that pulls in files not in version control, and a long social-engineering campaign can together compromise the wider ecosystem. It prompted renewed attention to reproducible release archives and to checking tarballs against source repositories.

## Applications beyond this domain

The pairing of container and codec appears in many systems. Software packages are archives plus compression: the Debian format described above, the RPM format with a compressed payload, and Arch packages as compressed tar files. Container images are stacks of layers, and each layer is a tar archive compressed with gzip or zstd, so the safety rules for extraction apply to every image pull. The boot process uses a compressed cpio archive as the initial root file system, unpacked by the kernel before the real root is available.

Compression is used throughout infrastructure. File systems such as Btrfs and ZFS and the compressed-memory swap feature use fast compressors transparently. Web servers send compressed pages, databases and columnar data formats compress blocks, version-control systems pack objects with deflate, and log pipelines compress before shipping. Backup tools that deduplicate and compress chunks, rather than making sequential archives, extend the same ideas with an index and with efficiency across versions. Even the choice of the numbers in a stream compressor, like trading speed for ratio, matches choices in video, image and audio encoding.

## Examples

A first exercise is to archive a directory, list the archive, extract it somewhere else and compare the trees with a recursive comparison, then repeat with each of the four compressors and record the time and size of each. Doing it on a mix of text and already compressed files shows how much depends on the data.

A second exercise tests what gets preserved. Make a tree containing a hard link, a symbolic link, a file with an unusual owner, a sparse file and a file with an extended attribute. Archive it with default options, restore it as the superuser and as an ordinary user, and note what was lost. Then repeat with the options for numeric owners, attributes and sparse handling.

A third exercise copies a tree between machines with an archiver on each end joined by a secure-shell connection, with no intermediate file, and compares the speed with a plain recursive copy.

A fourth exercise builds the compressed archive that the kernel accepts as a boot-time file system: list files with a search tool, feed the names to cpio in the format the kernel expects, compress the result and inspect it.

A failing example is a crafted archive whose first member is a link to a system directory and whose second member has a path through that link. Extracting it with an unfiltered tool as the superuser writes outside the target. Another failing example is a file compressed with a strong setting on a large machine that cannot be decompressed on a small one for lack of memory. A third is a release tarball whose contents differ from its tagged source; comparing the two, as security reviewers now do, shows the extra files.

## Related problems and ideas

Neighbouring problems include backup design, where full and incremental sets, retention, encryption and tested restores matter more than the archive format; deduplicating backup tools that store chunks by hash; and transfer tools that send only differences. Seekable compression formats add an index so that single members or ranges can be read without scanning, and multi-threaded compressors split the input into independent blocks. Dictionary training in the newer compressors lets small, similar files, such as many tiny records, compress far better by sharing a trained dictionary.

Ideas for good practice include verifying archives right after creation and again after copying, recording checksums separately, using the same compressor for long-term archives that will be read in the future, preferring formats and options that preserve what you will need on restore, running extraction in an empty scratch directory as an unprivileged user, and making release archives reproducible by fixing member order, timestamps and owners.

## Active research

Research on compression continues along several lines. One is faster entropy coding, building on asymmetric numeral systems, which give near-arithmetic-coding efficiency at Huffman speeds. Another is making strong compressors cheaper in memory and time, including hardware offload for compression in network cards and processors. Seekable and parallel-friendly formats are being standardised for large data sets. Content-defined chunking and deduplication research targets backup and container storage. In security, researchers study the supply-chain lessons of the xz incident, including automated comparison of release archives with source, safer build processes, and funding and support for critical maintainers. Reproducible-build work aims to make a compressed release bit-for-bit repeatable so that any difference signals tampering.

## Future direction

Zstandard is likely to keep replacing gzip and xz where decompression speed and flexible levels matter, as it already has in several distributions' package formats and in the kernel. Gzip will remain for compatibility with the web and with legacy scripts. Safe extraction will become the default in libraries and tools, so that code relying on the old unfiltered behaviour will need updating. Expect release archives to be verified against source repositories as a routine step and package ecosystems to require stronger provenance information. Hardware assistance for compression will spread where throughput matters. What to watch is how maintenance of the foundational compression libraries is supported after the 2024 incident, whether a next-generation archive format with an index and per-file integrity displaces the tape-era layout for general use, and how container registries handle the move from gzip to zstd layers.
