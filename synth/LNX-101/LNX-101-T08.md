# Who may do what to which file: permissions, ownership, umask and the special bits

## Define the problem

A multi-user computer must let people share a machine without being able to read each other's mail, overwrite each other's work or tamper with the operating system. The same machine also runs programs on behalf of those people, and each program must have exactly the authority of its user, no more. Something has to decide, on every attempt to read, change or run a file, whether the attempt is allowed.

That decision has to be cheap, because it happens millions of times a second. It has to be simple enough that an administrator can reason about it without a manual. And it has to be flexible enough to handle real arrangements: a team that shares a project directory, a public directory where everyone may drop files but nobody may remove another's, a program that needs one narrowly defined privilege on behalf of an ordinary user.

When the answer is wrong, the consequences range from the annoying to the catastrophic. A private key readable by everyone is a breach. A system directory writable by everyone is a ready-made privilege escalation. Too-tight permissions produce a different failure: a service that cannot read its own configuration, or a team that cannot collaborate. This topic covers the classic permission model attached to each file, who owns files, how default permissions are chosen when files are created, and the three special bits that modify the model. Extended access lists, mandatory access control and capabilities are touched on as neighbours.

## History and approaches

The model dates from the earliest Unix. Each file records an owning user and an owning group, plus three sets of permission bits: for the owner, for the group and for everyone else. Each set grants or denies reading, writing and executing. The choice of three classes and three operations was deliberately small. It fit in a few bits of a machine word, could be tested with a single comparison, and covered most cases in a small research lab. Early designers also decided that the superuser is exempt from the checks, which kept the model simple and concentrated enormous power in one account.

The first major addition was a way to run a program with its owner's identity instead of the caller's. Dennis Ritchie filed for a patent on this set-user-identifier mechanism in the early 1970s; the patent was granted in 1979 and later placed in the public domain. It solved a real problem: how can an ordinary user change their own password, which lives in a file that ordinary users must not edit? The answer was a program owned by the superuser that runs with the owner's authority for just that task. Its group counterpart followed, and later a third bit gave directories a special role.

Berkeley contributed the sticky bit in its current meaning. Originally a hint to keep a program in memory, it was repurposed so that in a directory writable by many users, an entry can be removed or renamed only by its owner, the directory's owner or the superuser. That is what makes a shared temporary directory workable.

As systems grew, the three-class model strained. People needed to grant access to a specific second person without creating a group, so access control lists were added. A standardisation effort for them was never completed, but implementations spread, and Linux file systems support them through an extended-attribute mechanism and a pair of tools. Another strain was the all-or-nothing nature of the superuser, and Linux responded around 1999 with capabilities, which split the superuser's powers into individually grantable pieces. Mandatory access control frameworks such as SELinux and AppArmor then added policy that even the owner cannot override.

The result is a layered system with a simple core. The classic bits remain the first check, and nearly all additions refine rather than replace them. The pattern that emerged is discretionary control at the bottom, owned by file owners, with administrator-defined mandatory policy above it and capability splitting inside the privileged side.

## Current state

Every file has a numeric owner and a numeric group, and a mode of twelve bits: three sets of read, write and execute, plus the three special bits. A long directory listing shows the nine ordinary bits as a string of letters and the type as the first character. The same mode can be written in octal, where each digit is the sum of read as four, write as two and execute as one, or as symbolic edits that add or remove bits for chosen classes. The Debian handbook walks through reading and changing these modes [src: debian-handbook 5e55391433f1c056] [src: debian-handbook b32049eb0cf722f8].

The check is applied in a fixed order. If the caller is the owner, the owner bits decide; otherwise, if the caller's group matches, the group bits decide; otherwise the other bits decide. The first matching class wins, even if a later class would be more permissive, so an owner can be denied something the world is allowed. The superuser bypasses most checks, with a few exceptions for execution.

The meaning of the bits differs by file type. On a regular file they mean what they say. On a directory, read permission allows listing names, write permission allows creating, deleting and renaming entries, and execute permission, often called search, allows entering the directory and reaching things inside it by name. A file's own bits do not matter if a parent directory cannot be searched, which is the most common reason for a puzzling denial.

Ownership is set by two commands. Only the superuser can give a file to another user, to prevent evading quotas and planting files with someone else's name, while the owner may move a file to any group they belong to. Users and groups are numbers on disk. Names are looked up through the name service configuration, so a restored backup or a mounted disk from another machine may show different names for the same numbers.

The three special bits are set-user-identifier, set-group-identifier and sticky. On an executable, the first runs it with the file owner's identity and the second with the file group's. On a directory, the second makes new entries inherit the directory's group instead of the creator's primary group, which is the standard way to build a shared team directory, and the sticky bit protects entries as described above. Mount options can disable the special-bit behaviour on whole file systems, and Linux ignores them on interpreted scripts for safety [src: man-pages aef8de8197387b2d].

New files get their mode from the program that creates them, minus whatever the umask removes. The umask is a per-process mask inherited from the parent; each set bit in it is cleared from the requested mode. Programs normally request liberal modes, so a file typically starts at read and write for everyone, and a directory with all bits, and the umask trims them. A common default removes write for group and others, and some distributions use a looser default combined with a private group per user so that group-sharing is safe. Hardening guides ask for stricter defaults, for example a mask that removes all access for others and the group, and security benchmark rules check that shell start-up files set it [src: disa-stig efcf6deedcfd65d6]. Programming interfaces expose the same ideas: Python's operating system module offers functions to change modes, owners and the mask, with the same semantics [src: python-docs b5c13d0babd78088].

## Assessment: the good, the bad and the ugly

The good is the simplicity and speed of the core model. A mode fits in a short string that a person can read, the check is trivial and the semantics are the same on every Unix. The special bits let a small number of carefully written programs mediate access to resources that users cannot touch directly, and group inheritance on directories gives teams a workable sharing scheme with no extra tools. Defaults that remove access from others make new data private unless someone opts in.

The bad is that the model is coarse. Three classes cannot express a second person's access without inventing a group, and groups are system-wide objects that need an administrator. Recursive changes are error-prone: applying a mode to a whole tree makes files executable that should not be, unless an option that sets execute only on directories is used. Numeric identifiers cause quiet damage when systems are merged or when accounts are deleted and later numbers are reused, so that new people inherit old files. Access lists add power but also a second, less visible layer: a listing shows a plus sign, and the mode's group bits then describe a mask rather than the group's real access.

The ugly side is that the privilege-granting features are among the most attacked parts of the system. Every program with the set-user-identifier bit and an owner of root is code that attackers study, because any bug in it is a path to full control. Real-world examples include a long-standing flaw in the policy-kit launcher disclosed in 2022 and a heap overflow in the privilege-delegation tool disclosed in 2021, both of which had existed for years and gave any local user root. Administrators are advised to inventory such programs and remove the bit where it is not needed, and the compliance catalogues contain rules for files with no owner or no group, since orphaned files are a sign of an incomplete clean-up [src: compliance-as-code 3456c7dae9ba69af]. Link-related protections in the kernel, which block following or creating links under certain conditions in shared directories, were added because races around permissions were a recurring source of vulnerabilities [src: man-pages 5e89c6437ba4bbcd]. Finally, the habit of making things work by granting everyone full access is common and dangerous, and it hides the real cause of the denial.

## Applications beyond this domain

The same questions recur in every system that shares resources. Cloud identity systems answer who may do what to which object with policy documents that are a generalisation of owner-group-other, and mistakes there, such as publicly readable storage, are the cloud equivalent of a world-writable file. Container platforms give each container a user identity and often map identities between the container and the host, so that a root user inside is an unprivileged user outside; the permission model on files decides what a container can touch on a shared volume. Kubernetes lets a pod declare the group that should own mounted volumes and the user it runs as, which applies the model across a cluster.

Other operating systems made different choices. Windows uses richer access lists on every object, and Android runs each application as its own user so that the Unix model enforces app isolation. The capability idea, splitting a super-privilege into narrow rights, has been applied to processes in Linux, to browsers and to hardware design. Even the sticky directory has a counterpart in object stores that let anyone upload but only the uploader delete.

## Examples

A first exercise is to create files with different umask values and read the resulting modes. With a mask that removes write for group and others, a new file starts at read and write for the owner and read for others, and a new directory at full access for the owner and read and search for others. Changing the mask to remove all access for others shows the effect directly. The exercise shows that the mask subtracts from what the program asks for and cannot add anything; in particular, ordinary file creation never makes a file executable.

A second exercise builds a team directory. Create a group, a directory owned by that group with the set-group-identifier bit and group write permission, and add two users. Create files as each and observe that the group is inherited but that the group write bit depends on each user's mask, which leads to a discussion of why shared directories need a cooperative mask or an access-list default.

A third exercise creates a shared drop box with the sticky bit and shows that one user cannot remove another's file. A fourth uses a command that lists the permissions of every component of a path to find why a file that looks readable is not, because a parent directory cannot be searched. A fifth searches the whole system for files with the owner-privilege bit set, compares the list with a reference list of expected programs, and discusses each unexpected entry.

A failing example is the key file that is too open. A secure-shell client refuses to use a private key that others can read, for good reason. A second is a recursive change to full access made to fix a denial, after which a service refuses to start because its configuration checks its own permissions, and the original problem is still unsolved because its cause was a parent directory.

## Related problems and ideas

Several neighbours deserve study. Access lists give per-user and per-group grants and default entries for new files in a directory. Mandatory policy through SELinux or AppArmor checks every access against rules the owner cannot change, which the security course covers. The immutable attribute lets even the superuser's changes fail until it is cleared. Capabilities allow a program to bind a low port or read raw packets without being fully privileged. Privilege delegation tools allow named people to run named commands as another user and log them, which is a safer substitute for sharing a password.

Ideas for better practice include least privilege by default, a private group for each user so that group sharing is opt-in, regular audits for files with unusual owners or bits, mounting data and temporary file systems with options that disable privilege-granting bits and device nodes, and managing permissions declaratively through configuration management so that drift is visible. Another idea is to run services under dedicated unprivileged accounts or dynamically allocated identities.

## Active research

Work in this area targets the coarseness of the classic model and the danger of ambient authority. The kernel gained a mechanism in 2021 that lets an unprivileged program restrict its own file-system access, allowing applications to sandbox themselves without administrator help. Identity-mapped mounts let the same data be presented with different owners to different containers, which reduces the cost of rootless containers. Hardware capability research, including architectures that make pointers carry rights, aims at removing whole classes of memory-safety bugs that attackers use to bypass permission checks. Programmable security policies attached to the kernel's security hooks allow sites to write custom checks. Researchers also study automatic inference of least-privilege policies from observed behaviour, and verification of access-control configurations.

## Future direction

The classic bits will not go away, as they are part of every file system and every tool, but the surrounding practice is moving. Services are increasingly started with a small, declared set of privileges and a private view of the file system, so that the distinction between what the owner allows and what the service manager grants matters. Rootless operation, in which the entire container stack runs as an ordinary user, is becoming normal. Read-only system images remove the need to guard the operating system's files with permissions alone. People will see more reliance on sandboxing interfaces that programs apply to themselves. What to watch is whether privilege-granting binaries continue to shrink in number as their functions move into services with narrow permissions, and how identity allocation, now often handled by the init system and by network directories, evolves.
