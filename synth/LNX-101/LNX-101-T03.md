# Files, links and the shape of the directory tree

## Define the problem

A computer has disks, memory, terminals, network cards and running programs, and people want to refer to all of them in a consistent, durable way. Unix answered with one organising idea: give nearly everything a name in a single tree and let programs treat those names alike. The problem this topic examines is how that idea is realised: what a file really is underneath its name, how several names can lead to one file, and how thousands of files from hundreds of packages are arranged so that people and programs can find them.

The difficulty is partly technical and partly about convention. Technically, a name has to survive renames, a file has to survive the deletion of one of its names if another remains, and the kernel has to find the data quickly. By convention, a directory tree has no meaning unless everyone agrees where configuration lives, where programs go, where changing data goes and where temporary data may be deleted. A distribution that scatters its parts at random cannot be administered, backed up or secured.

Failure looks like confusion about what a command is acting on. Someone edits a link and not its target, backs up a directory and misses the data that sits on another filesystem, deletes a large log and finds the disk still full, or runs out of space for new names while plenty of room is free. The scope here is the model of files and directories and the standard layout. How storage devices are partitioned and formatted belongs to the storage course, and permissions to the next topic.

## History and approaches

The earliest Unix systems built the structure that survives today: a hierarchy of directories, where a directory is just a list that maps names to numbered records. Each record, the inode, holds the file's metadata and the location of its data, but not its name. That separation is the key design decision. Because the name lives in the directory and the substance lives in the inode, one inode can appear under several names, and removing a name is a different act from removing the file. The file system disappears only when the last name is gone and the last program that has it open has closed it.

Early on the layout was shaped by hardware. The first systems had a small root disk and a second disk for users' files, and the second disk was mounted at a directory whose name abbreviated users. As the root disk filled up, system programs spilled over onto the second disk, and the directory that had held people's home directories became a second, larger home for the system itself. This is why a modern system has a top-level directory for the essential programs needed to boot and repair, and another for everything else: the split was a response to a storage limit that disappeared decades ago.

The second historical thread is standardisation. By the early 1990s Linux distributions had begun to place files differently, which made it hard to ship software for more than one of them. A small group of volunteers published a file system structure standard in 1994, which developed into the Filesystem Hierarchy Standard; version 2 appeared in 1997 and version 3 in 2015, and the standard is now maintained under the Linux Foundation [src: debian-handbook 792a3846561b34f0]. It was a partial success. The top-level directory names are universal and the manual page that describes the layout is still the quickest reference [src: man-pages a2e9665b0d907ee9], but the details drifted, and some parts, such as a directory for server data, are used by few distributions in practice.

Links have their own history. Hard links were in the design from the start. Symbolic links came later, in the Berkeley lineage, to solve what hard links cannot: they may cross file systems and may name a directory. Each solution brought its own hazards, which later security work had to address.

The most recent chapter is consolidation. Starting with the Fedora project in 2012 and followed by the Debian and Ubuntu families, distributions merged the old split by turning the top-level directories for programs, libraries and administrative tools into symbolic links to their counterparts under the second tree. The motive was the end of the old storage constraint and the desire to keep all operating-system content in one place, which simplifies snapshots, atomic updates and reasoning about what is part of the system. The emerging pattern is one of separating three kinds of data: the vendor's immutable content, the machine's local configuration, and the changing state of the running system.

## Current state

The current model has a small number of working parts. A file system is a set of inodes plus directory tables. A regular file holds bytes. A directory holds name-to-inode entries, including two special entries for itself and its parent. A symbolic link is a tiny file whose content is a path, resolved each time it is used. Special files represent devices that transfer blocks or characters, named pipes for local data streams and sockets for local connections. The first character of a long directory listing shows which type each entry has, and the listing's other columns show the inode number, the owner, the size and the number of hard links; that last number is simply how many names point at the inode [src: rocky-docs 2e5f810ec9f51bc6].

A hard link is a second name for the same inode. Both names are equal; neither is the original. Hard links cannot cross a file system boundary, because inode numbers are only meaningful inside one file system, and they cannot point at directories, which protects the tree from loops. A symbolic link has no such restrictions, but it can dangle if its target is removed or moved, and it adds a step to every access. Programs can ask either for the link itself or for what it points at, and the difference matters whenever a command changes permissions, copies or archives.

The standard layout groups the tree by role. Configuration local to the machine lives under one directory, and the programs, libraries and shared data that belong to the operating system live under another, where the program directories hold user commands and administrative commands. A directory exists for locally built software so that it cannot collide with packages, another for optional third-party applications, and another for data served by the machine. Changing state, such as logs, caches, spools and databases, goes under a variable-data directory. Home directories and the administrator's own directory hold personal files. Boot files sit in their own directory, because the boot loader may not be able to read the main file system. Temporary files go to a directory that may be cleared at any time and another that survives reboots. The Debian handbook gives a compact tour of these roles [src: debian-handbook 792a3846561b34f0].

Three top-level entries are not storage at all. One is a tree of device nodes that the kernel and the device manager keep current. Another exposes the kernel's view of processes and tunables as readable and writable files. A third exposes the device model. A fourth, now backed by memory, holds runtime state that is meant to vanish at reboot. In all these cases the file interface is a window on a live system rather than a place where bytes are stored, which is the original Unix idea carried much further than its authors imagined.

Image-based systems extend the pattern. In Red Hat's image mode, the physical root is mounted in a separate location and the running system is a prepared deployment tree. All operating-system content belongs under one directory, the traditional program directories are links into it, and when the integrity layer called composefs is enabled the main tree becomes part of the same immutable image [src: rhel-10-docs 7472ff3bbc4c27c6]. Local configuration is merged at update time and variable data persists across updates, so the three-way separation described above becomes a mechanism, not just a convention.

## Assessment: the good, the bad and the ugly

The good is that a small model scales a long way. Because names and data are separate, renaming is cheap and atomic within a file system, links give flexible aliasing, and the uniform interface means one set of tools handles files, devices and kernel state alike. A standard layout lets software be packaged once and found anywhere, lets administrators know where to look, and lets backup and security tooling make sensible default choices, such as backing up configuration and data but skipping caches.

The bad is that the uniformity hides real differences. A pseudo-file system looks like files but has no storage, so tools that measure or copy it give nonsense results. Links behave differently depending on whether a command follows them, and a recursive copy or archive can duplicate hard-linked data or break links unless told otherwise. Disk usage has two limits, space and inodes, and a file system with millions of tiny files can run out of names while looking half empty. Space is also tied to open files: removing a big file that a running program holds open frees nothing until the program exits, which is why a freshly cleaned disk may stay full. Conventions are only conventions: the standard leaves room for interpretation, distributions differ in details, and applications placed in the optional directory bring their own structure.

The ugly is the security history of links and temporary directories. A shared writable temporary directory invites a race: a program checks that a name is safe and then uses it, and in the gap an attacker replaces the name with a link to a sensitive file. The kernel gained protections that restrict following links in sticky shared directories and restrict creating hard links to files one does not own, and both are now enabled by default in mainstream distributions, but any program that is careless about how it opens files in shared places is still exposed. Archives are a second source of trouble. An archive can contain entries whose names climb out of the destination directory or are links that point outside it, and extraction code that trusts those names can overwrite arbitrary files. Python's archive module responded by adding extraction filters that reject such members, documents them as named defaults, and has announced stricter default behaviour in newer releases [src: python-docs 689558689a267b10]. Merging the top-level directories, finally, was disruptive for years: scripts and package tools that assumed the old split had to be taught that two paths can now name the same place.

## Applications beyond this domain

The idea of a content-addressed or inode-like layer beneath a flexible naming layer recurs widely. Version control systems store file contents under a hash and treat names as entries in a tree object, so identical content is stored once, much as hard links share an inode. Container images are stacks of layers, each a set of file changes, which get merged into one view; the layering mechanism is a union of directory trees that behaves, from inside the container, like an ordinary file system. Package managers that keep every version under a hashed directory name and assemble a working environment from links apply the same idea to software installation, which allows several versions to coexist and rollbacks to be instant.

The "everything is a file" principle also shows up in other operating systems and in cloud tooling. Network and distributed file systems extend the same naming to remote storage, and user-space file system frameworks let a program present a database, an archive or a cloud bucket as a directory. Observability tools read the kernel's process and device files to produce their metrics. Object stores and key-value stores, by contrast, deliberately abandon directories and in-place edits, trading the file model's familiarity for scale, and the contrast is useful for judging which abstraction fits a given problem.

## Examples

A first exercise is to make a file, give it a second hard link and a symbolic link, and list all three with their inode numbers and link counts. The two hard links share a number and show a count of two, while the symbolic link has its own number and a small size equal to the length of the path it holds. Deleting the original name leaves the file readable through the hard link and breaks the symbolic link. The same sequence shows why a hard link cannot be made across a mount point.

A second exercise is to explain a full disk. Start a program that holds a large file open, delete the file and check free space; nothing is released. A listing of open files that have a link count of zero identifies the culprit, and stopping the program returns the space. A parallel exercise creates thousands of empty files in a scratch file system until names are exhausted while the space usage report still shows plenty of room, then compares the output of the two usage commands.

A third exercise is to read the standard layout from the machine itself. Print where the program directories point on the current system, find out which of the temporary directories is memory-backed, and check which directory holds the files of the package manager's cache. On an image-based system, compare the same questions with the layout described in the vendor documentation [src: rhel-10-docs 7472ff3bbc4c27c6].

A failing example is a backup of a home directory that records symbolic links as the files they point to. Restoring it triples the space used and breaks sharing. Another is an archive extraction run as an administrator on an untrusted file: a member with a parent-directory path component writes outside the target directory, which the extraction filters described above are designed to prevent. Working through why each failure happens teaches more than memorising the standard.

## Related problems and ideas

Several neighbouring problems matter in practice. Case sensitivity and name encoding differ between file systems, which causes trouble when data moves between Linux and systems that fold case or normalise accented characters. Length limits on names and paths bite long build trees. Permissions and ownership, the topic that follows, sit on the inode and interact with links. Mount options such as read-only, no-execute and no-device give another layer of control over what a directory tree may do, and the storage course revisits them.

Ideas that follow from the layout problem include treating the operating system as an immutable, signed image and keeping configuration and state in their own explicit locations; giving each application a private tree, as container and sandbox formats do; and describing the layout in a machine-readable way so that tools do not hard-code paths. The systemd project and associated specification groups have published their own description of the hierarchy and of per-user directory conventions, which fill gaps the older standard leaves open.

## Active research

Work in this area concentrates on integrity and on new ways to compose trees. Verified, read-only images with per-file integrity checking, built on read-only image formats and kernel features for file-level verification, are being refined for both servers and appliances. Researchers and engineers continue to improve overlay and union mechanisms, including how to make layered trees fast and consistent. User-space and virtualised file system protocols, which let a guest read a host's directory with near-native speed, are an active engineering area for virtual machines and containers. Security research examines path-resolution races, and the kernel has gained mechanisms that let a program resolve a path under a given root without being tricked by links, so that safe handling of untrusted paths becomes a primitive rather than a convention. A separate line of work formalises file system behaviour after crashes, because the exact guarantees of rename and sync operations are still a source of subtle application bugs.

## Future direction

Three directions look likely. The merge of the top-level directories is essentially complete across mainstream distributions, and the next step is a cleaner division of what belongs to the vendor, what is local configuration, and what is state, with vendor defaults living in the immutable image and local overrides layered on top. Image-based and verified-boot systems will make the immutable part more common on servers, so administrators will increasingly find the system tree read-only and will make changes through configuration layers or by building a new image. The older standard has seen little revision since 2015, so de facto practice, written down by distribution and systemd documentation, will continue to lead. What to watch is how far the "factory defaults plus overrides" model spreads, how tooling for inspecting and backing up such systems matures, and whether file-level integrity checking becomes a default expectation rather than a specialist feature.
