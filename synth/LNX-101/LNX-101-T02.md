# The shell as a language: moving around, expanding words, quoting and remembering

## Define the problem

An administrator spends most of a working day typing short sentences to a machine. The shell is the program that reads those sentences, decides what they mean, and starts the right programs with the right arguments. That sounds simple, but the shell sits at an awkward junction. People want to type very little, so the shell lets one short word stand for many things: a pattern for a whole set of files, a variable, the output of another command. Programs, on the other hand, want an exact list of arguments. Somewhere between the two, a fuzzy human line has to be turned into a precise list, and every step of that translation is a chance for surprise.

Four related problems fall under this topic. Navigation is the problem of knowing where you are in a tree of directories and getting somewhere else cheaply. Globbing is the problem of naming many files without listing them. Quoting is the problem of stopping the shell from interpreting characters that you meant literally, and, equally, of letting it interpret the ones you did not. History is the problem of not retyping, and of finding again the command that worked last Tuesday.

Failure here is rarely dramatic at first. It is a script that works until a file name contains a space, a deletion that removes more than intended because a pattern matched an unexpected file, or a password that lingers in a history file. The scope of this slice is the interactive and scripting behaviour of the common shell found on Linux servers, which is bash, with notes on where other shells differ. Control flow, functions and scripting style belong to later topics.

## History and approaches

The first Unix shell, written by Ken Thompson in the early 1970s, was tiny: it read a line, ran a program, and could redirect input and output. Wildcard expansion was not even part of it. The early systems used a separate helper program to expand patterns, and the pattern matcher was folded into the shell itself in the late 1970s. That move explains a property that still surprises newcomers today: the program being run never sees the pattern, only the list of names the shell produced. Programs do not glob; shells do.

The next step was the Bourne shell, first released with the seventh edition of Unix, which added control flow, variables and the quoting rules that most shells still follow. In parallel, Bill Joy's C shell at Berkeley introduced interactive niceties that the Bourne shell lacked: a history list, aliases, job control and a brace-expansion shorthand. For a decade there were two camps, with the C shell preferred for typing and the Bourne shell for scripts. David Korn's shell in the 1980s merged the two sets of features. Bash, begun by Brian Fox for the GNU project in 1989 and maintained for decades by Chet Ramey, took the same route: Bourne-compatible scripting with the interactive comfort of its rivals, built on a line-editing library that gives command-line editing in an emacs or vi style [src: man-pages f12a19db70f4f63e].

The attempt to stop the shells drifting apart produced the POSIX shell standard in the early 1990s, which fixed a common core of syntax, quoting and expansion rules [web: opengroup.org]. It was a partial success. Scripts written to the standard run on many systems, but the standard leaves out the features people actually enjoy at the prompt, such as arrays, brace expansion and extended patterns, so that most real scripts rely on bash-specific behaviour. When some Debian-family systems chose a small, fast, strict shell for system scripts in the 2000s, thousands of scripts that had been quietly relying on bash features broke, which taught the community the cost of confusing the interactive shell with the scripting shell.

Other approaches kept appearing. Zsh added more powerful globbing and completion, fish rebuilt the interactive experience around sensible defaults at the price of compatibility, and PowerShell and later Nushell argued that pipes should pass structured objects rather than text. None has displaced the Bourne family on servers, because compatibility with the enormous body of existing scripts is worth more than elegance.

The emerging pattern is a layered one. A small standardised core gives portability. Bash adds a large, stable superset that nearly every Linux server has. Everything newer is mostly a front end for interactive use.

## Current state

Reading a command line, bash goes through a fixed sequence, and understanding the sequence is most of the topic. It first splits the line into words, respecting quotes. It then performs expansions in a defined order: brace expansion, then tilde expansion, then the substitution of parameters, arithmetic and commands, then splitting of the results into words, then pathname expansion, which is globbing, and finally removal of the quotes that did their job. Only after all of this does it look up the command and hand it a clean list of arguments. The manual lists this order explicitly, and nearly every shell puzzle is a consequence of it [src: man-pages f12a19db70f4f63e].

Navigation uses a few simple notions. Every process has a current working directory. Absolute paths start at the root, relative paths start from the working directory, and two special names refer to the current and parent directories. A leading tilde stands for a home directory. The shell keeps the previous directory in a variable so that one command can bounce back, and it can keep a stack of directories so that you can dive into one location and return. Symbolic links add a subtlety: the shell can show your location either as the path you typed, which may pass through links, or as the physical path the kernel resolves, and the two can differ. A search path variable for the directory-changing command lets you jump to commonly used parents by short names.

Globbing is a small pattern language, quite separate from regular expressions. A star matches any run of characters, a question mark matches one character, and square brackets match one character from a set or range. A leading star will skip hidden files, meaning those named with an initial dot, unless an option says otherwise. If a pattern matches nothing, the default behaviour is to pass the pattern through unchanged, which is a source of subtle bugs; options can instead make the pattern expand to nothing or raise an error. Optional features add extended patterns and a recursive double-star form. The expansion is sorted by the locale's collation order, which can differ between machines. Other languages copy the idea: Python's standard library has a module that applies Unix-style pathname patterns, with its own documented differences from the shell [src: python-docs fe01e9dfa3147850].

Quoting has three tools. A backslash protects the single character after it. Single quotes protect everything between them, with no exceptions. Double quotes protect most things but still allow variables, command substitution and arithmetic to expand, and, importantly, they stop the result from being split into words or matched against file names. A special form with a dollar sign and single quotes translates escape sequences such as newline and tab. The bash manual's section on quoting is short and worth reading in full, since it states each rule precisely [src: man-pages e36dc291715642a4].

History works through two mechanisms. The line editor keeps previous commands and lets you walk back, search incrementally with a reverse search, and edit before running again. Separately, history expansion is a small text-substitution language that works before the line is even parsed: a double exclamation mark repeats the last command, a form with a dollar sign reuses its last word, and a caret form swaps one string for another in the previous command. The history is kept in memory and written to a file when the shell exits, under the control of several variables for size, file name, duplicate handling and whether commands that start with a space are recorded [src: man-pages 3e4c868a4bc7cbd0].

## Assessment: the good, the bad and the ugly

The good is the economy of the design. A handful of rules, learned once, apply to every command and every script, and the same expansions work at the prompt and in a script. Because the shell expands patterns, no individual tool needs its own wildcard code, and every command that accepts several file names automatically works on a whole set. The reverse search and history substitutions save a large fraction of typing for anyone who learns them, and completion makes long paths and unfamiliar options discoverable.

The bad is that the same economy hides decisions that people do not see. Because patterns are expanded before the command runs, a pattern that matches thousands of files can exceed the kernel's limit on argument size and fail with an error about the length of the argument list, and the usual remedy is to hand the file list to a different tool. Because unquoted results are split on whitespace, a variable holding a name with a space becomes two arguments. Because the default for an unmatched pattern is to pass it through, a command meant for text files may be asked to process a file literally named with a star. Different shells and different locales give subtly different behaviour, and the standard's core is smaller than what scripts rely on.

The ugly is where those behaviours become security problems. A file name beginning with a dash looks like an option to the command that receives it, so a deletion with a bare star can be turned against its author by a file named to look like a flag; the defence is to mark the end of options before the patterns, or to prefix patterns with a directory. File names can also contain newlines, which breaks every tool that assumes one name per line. When a script builds a command from untrusted input without careful quoting, the input can inject extra commands, a flaw of the same family as injection into database queries. History is another quiet hazard: a password typed as part of a command is written to a file that is readable to anyone who later gains access to the account, and a shared account mixes everyone's commands in one file. Finally, interactive conveniences that are harmless at the prompt, such as history expansion triggered by an exclamation mark, produce surprising results when pasted into a script or a message.

## Applications beyond this domain

The central lesson is the same one found wherever text is turned into structured instructions: the point at which data becomes code is the point at which quoting matters. Web applications meet it when user input is placed into a query or a page, and the remedies, escaping and parameter passing, are directly analogous to quoting and to passing arguments as a list instead of a string. In Python, the subprocess module's documentation warns about the difference between passing a command as a list and passing it as a string for the shell to interpret [src: python-docs aeb2900361ce28da].

Container build files expose the same choice. A Dockerfile instruction can be written in a form that runs through a shell, with all the expansion rules above, or in a form that passes an exact argument list with no shell at all, and the reference documents the instruction that selects which shell is used [src: docker-docs 4294f3ff85c1c1de]. Continuous-integration pipelines embed shell fragments inside configuration files, where a second layer of templating adds a second set of quoting rules. Build tools such as make send recipe lines to a shell and so inherit its rules, and package maintainer scripts run under the system shell, which is why portability matters there.

The pattern-versus-regular-expression distinction recurs in ignore files, firewall rules, routing rules and cloud storage policies, many of which use something like globbing and a few of which use something that looks similar but behaves differently. Learning to ask which dialect a tool uses is a general skill.

## Examples

A first example is the space problem. Create two files, one named with a space inside it, and loop over a variable that holds their names. The unquoted loop splits the spaced name into two words and tries to operate on files that do not exist. Quoting the variable keeps each name whole, and storing names in an array instead of a string avoids the issue at its root.

A second example is the empty match. Run a command on a pattern for text files in a directory that has none. In the default mode the command receives the literal pattern as an argument and complains that no such file exists. Turning on the option that expands unmatched patterns to nothing changes the symptom, and turning on the option that raises an error changes it again. Seeing the three behaviours side by side teaches that the shell, not the command, is deciding.

A third example is the hostile file name. In a scratch directory, create a file whose name looks like a forced-deletion flag, then run a recursive deletion on a bare star. The flag-like name is passed to the command as an option. The same command written with an explicit end-of-options marker, or with a path prefix such as the current directory, treats every name as a file.

A fourth example is the history workflow: run a long command, mistype one word, and fix it with a substitution; use the reverse search to find a command from earlier in the day; mark a sensitive command with a leading space and confirm it was not recorded, then check that the relevant variable is actually set, because the feature depends on configuration. A teaching lab from the Rocky Linux documentation walks through navigation and common utilities in a similar progression [src: rocky-docs 720f83c3c22ed96e].

## Related problems and ideas

Neighbouring problems include word splitting in other places, such as options files and environment variables holding lists, where no shell sits in between to help. Another is portability: scripts that must run under the minimal system shell, under a busybox applet set, or on a machine with different tool versions. Another is correctness at scale, where people use static checkers to find unquoted variables, unsafe patterns and non-portable constructs before the script runs.

Ideas for avoiding the problems fall into three groups. The first is discipline: always quote variable expansions, mark the end of options, use arrays, prefer a tool's own recursion over generating long file lists, and use null-separated lists when passing names between programs. The second is tooling: run a linter in the editor and in review, run scripts with strict options that treat unset variables and failed pipelines as errors, and test with awkward file names on purpose. The third is replacement: when a task becomes complicated, move it to a language with real data structures and call the shell only for what it does best, which is starting programs and connecting them.

## Active research

Research on shells is small but real. A group of researchers produced an executable formal semantics of the POSIX shell language in the late 2010s, which exposed ambiguities in the standard text and gave a basis for testing real shells against a precise model. Projects aimed at a cleaner replacement language, such as the Oils effort to parse the existing language exactly while offering a stricter successor, are trying to turn decades of accumulated scripts into something analysable. Static analysis of scripts, including type-like checks of how values flow through expansions, is being explored both academically and in practical linters. A newer driver is the use of automated coding assistants that generate and run shell commands, which makes injection-safe command construction and sandboxing of command execution an active practical question. Work on structured pipelines continues in the object-passing shells.

## Future direction

The shell itself is stable and will remain so. The standard was revised again in the 2020s, and the bash project continues to issue measured updates, so the interactive experience on a server in a few years will look familiar. Change will come from around the edges: better completion and in-line help driven by tool metadata, safer defaults in scripting frameworks, and wider use of strict-mode conventions and linting in continuous integration. The more important trend is a shift in who writes the commands. As more commands are generated by software and then reviewed by people, the skill of reading a command line, predicting what it will expand to and spotting a quoting error before it runs becomes more valuable, not less. What to watch is how the standard, the main shells and the security community converge on guidance for generating commands safely, and whether a stricter successor language gains enough tooling to start displacing fragile scripts.
