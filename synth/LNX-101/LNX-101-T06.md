# Regular expressions: describing text patterns precisely

## Define the problem

People can recognise an address, a date or a failed login at a glance, but they cannot easily tell a program what such a thing looks like. Searching for a literal word is easy. Searching for any line that starts with a timestamp, contains a number between one and three digits and ends with a status word is not. The problem is to write down a class of strings compactly enough to type on one line, precisely enough that a machine can test it, and efficiently enough that the test runs over gigabytes of data.

Plain wildcards are too weak for this. They can say that anything may appear here, but they cannot say that a digit must repeat between one and three times, that one of two alternatives may appear, or that a character seen earlier must reappear. A full programming language is too heavy for a one-line search. Regular expressions occupy the space between: a small notation with a rigorous meaning, built on a mathematical idea from formal language theory.

Failures take three forms. The first is an expression that matches too much or too little, so that a filter lets bad lines through or removes good ones. The second is confusion between dialects, since the same characters mean different things in different tools. The third is an expression that is correct but pathologically slow, so that one unlucky input freezes a service. This topic covers the two dialects defined by the POSIX standard, basic and extended, as used by grep, sed, awk and their relatives, with the differences from the Perl-style dialects found in most programming languages noted where they matter.

## History and approaches

The mathematical origin is the work of Stephen Kleene in the early 1950s, who described a class of simple patterns, which he called regular events, in connection with models of nerve activity. For two decades the idea stayed in theory. Ken Thompson brought it into practice in 1968 with a paper describing how to compile a pattern into a machine that searches text, and built it into the editors he wrote for early time-sharing systems. The editor commands that searched with such patterns led directly to the grep tool, and to the stream editor.

In the 1980s several implementations diverged. Henry Spencer's freely available library spread the notation into many programs. The POSIX standard of the early 1990s tried to settle matters by defining two syntaxes. The basic one, inherited from the original editors, treats most punctuation as literal and requires a backslash to activate groups and repetition. The extended one, derived from the egrep tool, makes those characters special by default and adds alternation. POSIX also fixed the matching rule: among all possible matches starting at the leftmost position, take the longest [src: man-pages f108ddbe23ff3069].

A second family arrived with Perl in the late 1980s and 1990s, which added shorthand classes, non-greedy repetition, lookaround and other features, and a matching strategy that tries alternatives in order and takes the first that works. A library written to bring Perl's notation to other programs, PCRE, spread it further, and Python, Java, JavaScript and most other languages followed with their own variants. The Python documentation describes this dialect and its flags in a long reference and a gentler how-to [src: python-docs 73a67f00eafc7f9e] [src: python-docs 9f1e9f0c082712b5].

The two families took different implementation paths with different consequences. The original approach compiles the pattern to an automaton that reads each input character once and never backs up, so running time grows in proportion to input length. The Perl approach is a backtracking search that explores alternatives one after another. It is easy to extend, which is why it gained features such as backreferences and lookaround, but its running time can grow exponentially for some patterns. A widely read 2007 article by Russ Cox argued that the older method had been unfairly forgotten, and the RE2 library that followed offered Perl-like notation with a linear-time guarantee by leaving out the features that cannot be matched that way.

The emerging pattern is a split: the POSIX tools remain the portable base, Perl-style dialects dominate programming languages, and a growing number of implementations choose guaranteed running time over the more exotic features.

## Current state

The notation is built from a short vocabulary. Ordinary characters match themselves. A dot matches any one character. A bracket expression matches one character from a set or range, or from a named class such as letters or digits, or from the complement of a set. An anchor matches a position rather than a character: the start or end of the line. Repetition operators say how many times the preceding item may occur: zero or more, one or more, zero or one, or an exact or bounded count. Grouping lets an operator apply to a whole sub-pattern, and alternation separates choices. A backreference matches the same text as an earlier group did [src: rocky-docs ee835b630467df8a].

The difference between the basic and extended forms is mostly about which characters need a backslash. In the extended form, the characters for grouping, bounded repetition, alternation, one-or-more and zero-or-one are special by default. In the basic form the same characters are literal, and a backslash turns on their special meaning, with the one-or-more, zero-or-one and alternation operators being GNU extensions that the standard does not require. GNU tools accept either form, selected by an option, and a few add extensions such as word boundaries and shorthand classes. The manual page for grep documents the exact rules and the extended form's option [src: man-pages f108ddbe23ff3069]. The stream editor and awk have their own defaults, so the same expression may need to be written differently for each [src: man-pages d9b6f39b54259e01].

Matching semantics can be summarised in a few rules. Matching is unanchored unless anchors are used, so the pattern may match anywhere in the line. Repetition is greedy, taking as much as it can while still allowing the whole expression to match. Character classes depend on the locale, and a range such as one from a lowercase letter to another may or may not include uppercase letters depending on the collation order, which is why named classes are the safer choice. The dot does not match a newline in line-based tools because they never present one.

The distinction from shell wildcards is essential. In wildcards a star means any run of characters, whereas in a regular expression it repeats the preceding item. A search for a file extension written as a wildcard is a different thing from the same text given to grep. Because the shell expands wildcards before a command runs, an unquoted regular expression can be mangled before the tool sees it, so expressions are normally put in single quotes.

## Assessment: the good, the bad and the ugly

The good is expressive power in a few characters. A pattern can validate, extract and rewrite text in one line, and the same ideas carry across tools and languages. The POSIX forms are everywhere: any minimal system has grep and sed. The theory gives guarantees: for the regular subset, matching can be done in time proportional to input length, with memory independent of it, which is why search tools can run at the speed of storage.

The bad is that the notation is dense, easily misread and dialect-dependent. A backslash before a parenthesis means the opposite in the two POSIX forms. Greedy repetition makes a pattern that works on one line swallow too much on another, and the common workaround of excluding the closing delimiter in a bracket expression is not obvious to beginners. Expressions that try to validate complex formats, such as full email addresses or nested structures, become unreadable and still wrong, since some structures, including balanced nesting, lie beyond what regular expressions can describe at all. Locale-dependent ranges produce different results on different machines. Expressions are hard to test and comment, and without care become write-only code.

The ugly is the performance and security cost of backtracking engines. A pattern with nested repetition, such as one that asks for a repeated group of repeated items followed by a character that cannot match, forces an exponential number of attempts on certain inputs. This is a denial-of-service technique known as regular-expression denial of service. A Q and A website suffered a roughly half-hour outage in 2016 after a post triggered a slow pattern in a whitespace-trimming routine, and a content-delivery company's 2019 global outage was traced to a single rule containing a pattern with this weakness. Inputs controlled by attackers make this a real vulnerability class, with many published advisories. A related hazard is using expressions to parse formats that need a real parser, such as HTML or nested configuration, which produces fragile code that fails on legal input. And a validation pattern that is merely plausible, such as an address-shaped pattern that accepts octets above the legal range, can create a false sense of safety.

## Applications beyond this domain

Regular expressions are one of the most widely reused ideas in computing. Compilers use them to split source code into tokens, with generator tools turning a list of patterns into an automaton. Editors use them for search and replace and for syntax highlighting. Web servers and gateways use them to route requests and to filter malicious input. Intrusion-detection and malware-scanning engines match thousands of patterns at once against network traffic or files, using specialised multi-pattern engines that exploit vector instructions to scan at line rate. Log-processing pipelines use named patterns to turn raw lines into fields, and data scientists use them to clean text.

The underlying theory has uses beyond text search. The automata that implement regular expressions appear in hardware design, protocol parsers, model checking and the specification of allowed behaviour of programs. Bioinformatics describes sequence motifs with patterns of the same kind. Even the tokenisation step of some language-model pipelines splits text using a regular expression, which shows how deep the pattern language runs. Python's re module lets a program use the same notation, with a flag system that includes options for case folding and multi-line behaviour [src: python-docs a8f0e7863b49282d].

## Examples

A first example is extraction by anchors. To list lines that begin with a date and end with the word for failure, one writes an expression with a start anchor, a digit pattern with exact counts, then wildcard text, then the word and an end anchor. Running it first with the basic syntax and then with the extended option shows how the same idea needs a different set of backslashes.

A second example is greedy repetition. Applied to a line containing two quoted strings, a pattern that looks for a quote, then any text, then a quote, matches from the first quote to the last. Replacing the wildcard with a bracket expression that excludes the quote character restricts the match to the first string. In a Perl-style dialect a non-greedy form does the same, which the Python how-to illustrates under the heading of common problems [src: python-docs fc4d0ed952b5a848].

A third example is rewriting with groups. The stream editor can swap two fields by capturing each in a group and referring to them in the replacement in reverse order. A fourth uses a backreference to find lines where a character is doubled. A fifth tests an address-shaped pattern against inputs containing octets above the legal range and shows that the pattern accepts them, which leads to a discussion of when to validate numerically in code instead.

The failing example is the slow pattern. Take a pattern consisting of a repeated group of repeated letters followed by an end anchor and apply it, in a language with a backtracking engine, to a string of the same letter ending with a different one. As the string grows by a character at a time the running time doubles, while a linear-time engine handles it instantly. The comparison is a vivid lesson in why engine choice matters.

## Related problems and ideas

Neighbouring problems include globbing, which is a separate and simpler language, fuzzy matching, which tolerates a number of errors in a match, and full parsing, which handles nested structure with a grammar. Parsing-expression grammars and parser combinators trade the compactness of expressions for the ability to recognise structure, and are better suited to formats such as configuration languages. Another neighbour is structured query over logs and documents, where a field-aware query replaces text patterns.

Practical ideas include writing expressions with the extended option for readability, using named classes rather than ranges, preferring literal-string options when no pattern is needed, commenting and testing expressions as code, and keeping validation in two layers: a simple pattern for shape and code for meaning. For services that accept patterns or inputs from outside, ideas include using a linear-time engine, setting match timeouts and limiting input length. Interactive tools that draw a pattern's matching process help learners see why an expression behaves as it does.

## Active research

Research continues on several fronts. One is efficient matching: engines that use vector instructions to test many patterns at once, and engines that build automata lazily so that the cost is paid only for the paths actually used. A second is extending guaranteed-time matching to features that normally require backtracking, such as limited forms of backreference and lookaround, and developing derivative-based methods that give clean semantics for them. A third is the detection of vulnerable patterns, with static analysis and fuzzing tools that find exponential behaviour in code before attackers do. A fourth is synthesising patterns from examples, so that users can describe what they want by showing positive and negative samples. A fifth concerns correct handling of Unicode, including case folding, normalisation and what a character is, where dialects still differ.

## Future direction

The basic and extended POSIX dialects will remain the portable core, since they are fixed by standards and embedded in countless scripts. Beyond them, the direction is towards engines with guaranteed running time as the default in new languages and libraries, with the backtracking features available as an explicit opt-in. Recent additions to popular languages, including possessive repetition and atomic grouping that limit backtracking, point the same way. Expect better tooling that explains an expression in plain language, warns about risky constructs, and generates test cases, and expect assistants to propose patterns that reviewers must still understand. What to watch is how many mainstream engines adopt linear-time modes, how Unicode behaviour converges, and whether any popular tool changes its default dialect, which would be disruptive.
