# Streams, redirection and pipes: wiring programs together

## Define the problem

A program that reads from the keyboard and writes to the screen is useful once. A program that can read from any source and write to any destination can be reused thousands of times. The problem the Unix designers faced was how to give programs that flexibility without every program needing code for every kind of source and destination: files, terminals, other programs, devices, eventually the network.

Two further questions sit on top of that. When a program produces both results and complaints, how do you keep them apart so that a person sees the complaints while a file receives the results? And when you want to run several programs in sequence on the same data, how do you avoid writing every intermediate result to disk and cleaning it up afterwards?

For an administrator the problem shows up as ordinary frustrations: a script's output is mixed with its error messages; a command that works at the prompt fails under sudo when a redirect is added; a long job's progress is not visible until it finishes; a pipeline reports success although a stage failed. This topic explains the model that makes the plumbing possible and the rules that decide how it behaves. It covers the shell's redirection operators, pipes and the tee utility. The reuse of this plumbing inside scripts, services and containers is touched on where the behaviour changes.

## History and approaches

In the earliest Unix, programs wrote to a terminal directly, and a feature to send output to a file was an early addition by Ken Thompson. The crucial design choice was to make the interface uniform: a program does not open its own input and output but inherits numbered handles from whoever started it. By convention the numbers are zero for standard input, one for standard output and two for standard error. A program that reads handle zero and writes handle one never needs to know whether those are a terminal, a file or something else. The shell, before starting the program, rearranges the handles, and the program is unaware [src: bash d6d05023c21bd0d6].

The pipe came in 1973. Doug McIlroy had argued for years that programs should be connected like garden hoses, and Thompson implemented it in a single night, in the way Unix lore tells it. A pipe is a small in-kernel buffer with a write end and a read end. The writer blocks when the buffer is full, the reader blocks when it is empty, and the two programs run concurrently, so that data flows between them as it is produced. The Bourne shell's notation for the vertical bar, and its operators for duplicating handles, set the syntax that all later shells inherited. The tee utility, named after the plumbing fitting that splits a flow, appeared as a way to write a stream to a file while passing it on [src: man-pages e8f43d2a3fdebbb0].

Approaches that tried to improve on this model include named pipes, which give a pipe a name in the file system so that unrelated programs can connect to it, and sockets, which generalise to bidirectional communication and to other machines. The C shell offered its own notation for combining the two output streams, which was less general. Later shells added conveniences: a short form that redirects both streams, here-documents that embed input text in a script, and process substitution that presents a command's output as if it were a file.

Not every attempt was a success. Text streams are easy to wire but carry no structure, which prompted shells that pass typed objects between stages. Those are valuable inside their own ecosystems but cannot pipe to the millions of ordinary programs. The emerging pattern is that the byte stream, with its three numbered handles, is the lowest common denominator that everything else reuses, so every new environment, from service managers to containers, tends to reproduce it.

## Current state

The model consists of file descriptors and a small set of operators. A file descriptor is a number that indexes a table in each process, with each entry referring to an open file, device, pipe or socket. Redirection is changing what entries zero, one and two, or any higher number, refer to before a command runs. The common operators send standard output to a file, replacing it or appending to it, read standard input from a file, send standard error to a file, and duplicate one descriptor onto another so that two streams share one destination. A special device that discards everything written to it gives a way to silence a stream. A tutorial on these operators is part of the Rocky Linux documentation [src: rocky-docs 1a9cf41534e967a9] [src: rocky-docs f5828b3b0c57114d].

Order matters because redirections are processed left to right. Sending standard output to a file and then pointing standard error at standard output sends both to the file; reversing the two operators sends errors to the terminal, because at that point standard output still pointed there. A here-document supplies a block of text as input, and a here-string supplies a single string. A shell option can forbid overwriting existing files with the plain redirect, and the append form never overwrites.

A pipeline connects each command's standard output to the next command's standard input. All stages start at about the same time and run concurrently; the kernel moves data through pipe buffers of a default size of tens of kilobytes. When the reader exits early, the writer receives a signal on its next write, which is how a command that shows only the first lines of a long stream makes the producer stop. The exit status of a pipeline is, by default, that of the last stage; a shell option changes this so that a failure in any stage becomes the pipeline's status, and the shell also keeps an array of every stage's status for inspection.

Tee reads standard input and writes it both to standard output and to named files, with an option to append. Its most common uses are to save a copy of a stream mid-pipeline and to write to a file that needs elevated privilege, since a redirect is performed by the invoking shell with the invoker's rights, while a tee started under sudo opens the file itself.

Other tools adopt the same conventions. Service managers capture the standard output and error of their services and send them to the journal; the systemd documentation describes the command-line parsing rules for services, which notably involve no shell, so redirection operators have no meaning in a service's command line unless a shell is explicitly started [src: man-pages a9297b5c0d7c0507]. Container runtimes likewise treat a container's standard output and error as its log stream, which is why applications aimed at containers are advised to log to those streams rather than to files.

## Assessment: the good, the bad and the ugly

The good is composability with almost no ceremony. Programs written decades apart interoperate because they agree on three handles and a byte stream. Pipelines use multiple processors, handle data larger than memory and avoid temporary files. Separating results from diagnostics lets scripts capture one and show the other. Because redirection is performed by the shell, no program needs special code, and a command written to read standard input works equally on a file, a pipe and the keyboard.

The bad is that the same simplicity leaves several traps. Buffering is invisible: many programs switch from line-by-line to block buffering when their output is not a terminal, so in a pipeline the downstream stage may see nothing for a long time, and a progress display seems frozen. Redirecting a command's output to the same file it reads truncates the input before it is read. The shell performs a redirect, so prefixing a command with sudo does not elevate the redirect, and the familiar failure with a permission error is the consequence. Variables set inside a pipeline stage live in a subshell and are lost when the pipeline ends, which surprises people who pipe into a loop. The default exit status hides failures in earlier stages.

The ugly cases involve the kernel or resources. A pipe's implementation in the kernel is a performance-critical, complicated piece of code, and in 2022 a flaw in how a buffer's flags were initialised allowed an unprivileged user to overwrite data in files they could only read, a vulnerability widely known by the name Dirty Pipe. It affected a broad range of kernels and showed that this ordinary mechanism is also security-critical. In application code, a parent process that creates a pipe to capture a child's output and then waits for the child before reading can deadlock when the pipe fills; the Python documentation for running subprocesses spends considerable space warning about exactly this pattern [src: python-docs 6dd585c4de5cdf42]. And logs that go to standard output in a container are lost if nobody collects them, a mistake that is discovered only when an incident needs them.

## Applications beyond this domain

The idea of connecting independent components through narrow, uniform channels is general. Message queues and stream-processing platforms offer the same producer and consumer relationship with durability and fan-out. The twelve-factor style of application design treats logs as an event stream written to standard output and leaves routing to the platform, which is the redirection model applied to cloud operation. Build systems and continuous-integration pipelines pass outputs from one job to the next, and language runtimes provide pipe abstractions in their libraries, including in-process pipes between threads.

Testing and automation use the same techniques. Test harnesses capture a program's output streams to compare with expected text, command wrappers record sessions by splitting streams the way tee does, and remote-execution tools carry the three streams across a network connection. Security tools exploit the property that a program's behaviour can be observed by watching its streams. In Python, a process-management module gives programmers direct control of the three handles, mirroring the shell [src: python-docs aeb2900361ce28da].

## Examples

A first exercise is to run a command that writes to both streams, such as a listing of one existing and one missing path, and send each stream to a different file, then to the same file in both orders of the operators, and compare the results. Seeing that the order changes the outcome makes the left-to-right rule memorable.

A second exercise is the privilege problem. Try to append a line to a protected file with a redirect under sudo and observe the refusal. Repeat with the line piped into a tee started with sudo and the append option, and observe success. Discuss which process opened the file in each case.

A third exercise is buffering. Run a command that produces a line per second and pipe it to a search tool; nothing appears until the producer ends. Re-run with the search tool's line-buffering option, or wrap the producer in a utility that changes its buffering, and the lines appear as they are produced.

A fourth exercise is exit status. Run a pipeline whose first stage fails and whose last stage succeeds, read the status, then enable the option that propagates failure and read it again. Examine the per-stage status array.

A fifth exercise combines the remaining tools. Use a here-document to feed a multi-line block to a command inside a script, then compare two sorted listings without creating temporary files by using process substitution, which hands each command's output to the comparison tool as though it were a file. Finally, create a named pipe in a scratch directory, start a reader in one terminal and a writer in another, and watch the writer block until the reader appears. The three parts show that the same stream idea reaches from the prompt to the file system.

A failing example is the self-overwrite: sort a file and redirect the result to the same file. The shell truncates the file before sort reads it, and the data is lost. The remedies are to write to a new file and move it into place, or to use a tool that supports in-place output.

## Related problems and ideas

Neighbouring topics include named pipes for connecting unrelated programs, sockets and the netcat family for sending streams across a network, and pseudo-terminals, which make a program believe it is talking to a person and are used by session recorders and remote shells. Programs behave differently when attached to a terminal, which is why colours and paging turn off in pipelines, and options exist to force them.

Ideas worth practising include logging everything a long job prints with tee while still watching it, putting error output on its own stream consistently in scripts, creating temporary files with proper tools instead of fixed names, setting the pipeline-failure option and unset-variable checks at the top of scripts, and keeping pipelines short enough to understand. For long-running data movement, a progress-viewing utility placed between two stages gives visibility without changing the data.

## Active research

Pipe-related work is mostly in systems engineering. Kernel developers keep refining zero-copy data movement between pipes, files and sockets, trading performance against the kind of safety problem seen in 2022. Newer asynchronous input and output interfaces let programs submit many stream operations at once and reduce the cost of moving data between stages. Language designers explore typed or schema-carrying pipelines that keep the simplicity of pipes while preserving structure, including options for programs to advertise a machine-readable output format. Operations researchers and vendors study log pipelines at scale, including how to guarantee delivery of standard-output streams from large container fleets, and how to attach structure to what is otherwise plain text.

## Future direction

The three-handle model will persist because everything depends on it. Expect the margins to change: more commands will offer a machine-readable output switch so that the consumer need not parse columns; service managers and container platforms will continue to capture streams and turn them into structured events; and shells will keep improving feedback for failures inside pipelines. The shells' defaults are unlikely to change because of the weight of existing scripts, so careful scripts will keep opting into stricter settings explicitly. What to watch is whether a convention for structured output becomes common enough in the base system to reduce text parsing, and how kernel pipe and splice paths continue to be hardened.
