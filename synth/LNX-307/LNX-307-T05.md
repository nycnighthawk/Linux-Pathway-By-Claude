# Looking inside a running system: strace, perf and eBPF tracing with bcc and bpftrace

## Define the problem

Counters and dashboards tell you that something is slow and which resource is stressed. They do not tell you why. Why does one request take two seconds when the CPU is idle? Which file is the program trying to open and failing to find? Which function burns the CPU? Who is issuing these thousands of tiny disk writes? To answer, an engineer has to look at the behaviour of the software itself: its system calls, its stack samples, the kernel events it triggers. This is dynamic analysis of a live system, and it has to be done without stopping the service, preferably without a restart, and without slowing the system enough to change the behaviour being studied (the observer effect).

This slice covers the three tool families used on Linux for that job. **strace** records the system calls a process makes. **perf** samples where the CPU spends time and counts hardware and software events. **eBPF**, with its front ends **bcc** and **bpftrace**, runs small verified programs inside the kernel at chosen events and aggregates results in kernel memory. They sit at different cost and detail levels. The aim is to know which to reach for and what a trustworthy answer looks like. Kernel-module debugging (LNX-330) and full-system kernel crash analysis (LNX-307-T06) are separate topics.

## History and approaches

The first approaches were source-level: add `printf` statements, rebuild, redeploy. Debuggers (gdb) stop the process and inspect it, which is not acceptable for a service under load. Unix systems then gained tracers outside the program. System V's `truss` and BSD's `ktrace` recorded system calls. On Linux, the `ptrace(2)` system call, added in the early kernels, let one process observe and control another, and Paul Kranenburg's `strace` (written for SunOS in 1991 and ported to Linux) used it to print each system call with arguments and results. It is still maintained, with a rewrite of its argument decoding and a `--seccomp-bpf` option that reduces cost when filtering [src: man-pages 09ccebc0bddd1701]. The drawback of `ptrace` is overhead: the tracee stops twice for every system call, so a syscall-heavy process can be slowed by an order of magnitude, and a traced process behaves differently in timing-sensitive cases.

For performance rather than behaviour, sampling profilers came next. `gprof` needed recompilation; `oprofile` (2002) and then the in-kernel **perf_events** subsystem (Linux 2.6.31, 2009) gave sampling of any running program through hardware performance counters and software events, with the user-space `perf` tool (in the kernel tree under `tools/perf`) offering `stat`, `record`, `report`, `top`, `trace` and more [src: man-pages 45283ccfe5b69368]. Alternatives with different goals included SystemTap (Red Hat, 2005), which compiled scripts into kernel modules, and DTrace (Sun, 2004), whose dynamic tracing language influenced everything after it but whose Linux port was held back by licensing for years. LTTng and ftrace provided low-overhead static tracing. Each had a barrier: SystemTap needed kernel debuginfo and a compiler on production hosts and could crash systems, DTrace was not in the mainline kernel, and `ftrace` was powerful but low-level.

The breakthrough was **BPF**. The original Berkeley Packet Filter (1992) was a tiny virtual machine for filtering packets. Alexei Starovoitov's extended BPF (eBPF, Linux 3.18 in 2014 and expanded steadily) turned it into a general in-kernel virtual machine with maps, helper functions and a **verifier** that proves, before loading, that a program terminates and accesses memory safely. Attachment points include kprobes and kretprobes (kernel function entry and return), uprobes (user functions), tracepoints (stable kernel instrumentation points), perf events and network hooks. The documentation for Ubuntu Server introduces how eBPF works and its limitations [src: ubuntu-server-docs b51592cd94c5b56b]. **bcc** (BPF Compiler Collection, 2015) provided a Python and C toolkit and more than a hundred ready-made tools such as `execsnoop`, `opensnoop`, `biolatency`, `tcpconnect` and `runqlat`. **bpftrace** (2016 onward, by Alastair Robertson and others) added a high-level awk-like language in the DTrace tradition for one-liners. Later came **CO-RE** (compile once, run everywhere) and BTF type information, which allow the same program to run across kernel versions without a compiler on the host, and `libbpf`-based tools that replaced many bcc tools to avoid that runtime dependency.

The pattern that emerged is a ladder of cost and specificity: counters first, then sampling, then dynamic tracing. Brendan Gregg's work on flame graphs, a visualisation of sampled stacks introduced in 2011, and his perf and BPF tool charts gave practitioners the map [web: brendangregg.com].

## Current state

### strace

```bash
strace -f -tt -T -o /tmp/app.trace ./app args        # follow forks, time stamps, time in each call
strace -p 1234 -f -e trace=network                   # attach to a running process, only network calls
strace -c -p 1234                                    # summary table on exit: calls, errors, time
strace -e trace=openat,stat -e status=failed cmd     # only failed file lookups
strace -y -P /etc/app.conf cmd                       # show paths for descriptors; filter by path
```

The options that matter: `-f` follow threads and children, `-e trace=` select calls or classes (`file`, `network`, `process`, `memory`), `-e status=failed` select the failing calls, `-T` show the time spent in each call, `-tt` or `-r` timestamps, `-s` string length, `-c` and `-C` summaries, `-o` output file, `-p` attach, and `-k` print a stack trace for each call (if built with support). The Red Hat developer documentation shows recording application interactions with it [src: rhel-10-docs 7ff2f46274860320]. Typical findings: a configuration file looked up in six directories before the real one (the `ENOENT` lines), a `connect` that hangs for 30 seconds on an unreachable address, a `futex` wait that shows lock contention, thousands of `write` calls of a few bytes each (missing buffering), or a program blocked in `read` on a file descriptor that never gets data. Attaching requires ptrace permission: the `kernel.yama.ptrace_scope` sysctl restricts it, and containers need the `SYS_PTRACE` capability.

### perf

```bash
perf stat -d ./app                         # counts: cycles, instructions, IPC, branch and cache misses
perf top                                   # live view of hot functions
perf record -F 99 -g -p 1234 -- sleep 30   # sample 99 times a second with call graphs
perf report --stdio                        # summarise samples by symbol
perf trace -p 1234                         # syscall tracing built on perf events (lower overhead than strace)
perf sched record / perf sched latency     # scheduler delays
```

`perf record` writes `perf.data`; `-g` captures call stacks, which need either frame pointers, DWARF (`--call-graph dwarf`) or LBR to unwind; many distributions build libraries without frame pointers, which is a long-running pain, although Fedora and Ubuntu have recently re-enabled them by default (to verify exact releases). The result is turned into a flame graph with `perf script | stackcollapse-perf.pl | flamegraph.pl > out.svg`, using Gregg's FlameGraph scripts, where width is the share of samples and the x-axis is not time. Choosing 99 Hz instead of 100 avoids lockstep with periodic timers. `perf stat` shows instructions per cycle: values below 1 signal stalls on memory, above 2 mean compute-bound code. In a virtual machine, hardware counters may be unavailable (software events only) unless the hypervisor exposes them, which matters in the VIRT pathway. The sysctl `kernel.perf_event_paranoid` controls what unprivileged users may measure.

### eBPF with bcc and bpftrace

The kernel needs a recent enough version (4.9 for many profiling features, 5.x for BTF and CO-RE) and root or `CAP_BPF` with `CAP_PERFMON`. The tools install as `bcc-tools` (placed in `/usr/share/bcc/tools` on Red Hat family systems, `/usr/sbin/*-bpfcc` on Debian) and `bpftrace`. Common bcc tools:

| Tool | Question it answers |
|---|---|
| `execsnoop` | which processes are being started (catches short-lived ones that `pidstat` misses) |
| `opensnoop` | which files are opened, by whom, with which errors |
| `biolatency`, `biosnoop` | block I/O latency histogram, per I/O trace with latency |
| `runqlat` | how long runnable tasks waited for a CPU (saturation, LNX-307-T01) |
| `tcpconnect`, `tcplife`, `tcpretrans` | connections, their duration and bytes, and retransmissions |
| `cachestat`, `filelife`, `profile` | page cache hit ratio, short-lived files, CPU stack sampling |

bpftrace programs have the form `probe /filter/ { action }`:

```bash
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'
bpftrace -e 'tracepoint:block:block_rq_issue { @bytes = hist(args->bytes); }'
bpftrace -e 'kprobe:vfs_read /pid == 1234/ { @start[tid] = nsecs; }
             kretprobe:vfs_read /@start[tid]/ { @us = hist((nsecs - @start[tid]) / 1000); delete(@start[tid]); }'
bpftrace -l 'tracepoint:sched:*'     # list probes
```

Maps (`@name`) are aggregations kept in the kernel and printed on exit; builtin variables include `pid`, `tid`, `comm`, `nsecs`, `arg0`..`argN`, `retval`, `args` (tracepoint fields) and functions `count`, `sum`, `avg`, `hist`, `lhist`. Because only summaries cross to user space, the overhead is small compared with strace.

The generalised pattern is **choose an event, filter early, aggregate in place, print a summary**. The workflow follows the USE method: a symptom points to a resource (LNX-307-T01 and T02), then a tracer answers which code is responsible.

## Assessment: the good, the bad and the ugly

The good: these tools turn opaque behaviour into visible facts, usually in minutes and with no change to the program. strace is installed everywhere, understandable and exactly right for configuration, permission and "what is it waiting for" problems. perf is the standard CPU profiler and works for any binary. eBPF gives production-safe, low-overhead answers to questions that were impractical before, such as latency distributions per disk or per query, and its verifier prevents the crash risk that SystemTap had.

The bad: each tool has an overhead and a blind spot. strace can slow a process by 10 to 100 times for call-heavy workloads and changes timing, so use it for logic, not performance; `-c` still pays the tracing cost. perf sampling shows where the CPU is, not why a thread is sleeping: off-CPU time (waiting on locks, I/O) needs a different method (off-CPU flame graphs from eBPF scheduler tracing). Missing symbols and frame pointers produce flame graphs full of hex addresses, and JIT languages (Java, Node) need special symbol maps. eBPF has a learning curve: probe names change between kernel versions (a kprobe on an internal function is not a stable interface; a tracepoint is), the verifier rejects loops it cannot bound, and the limits (stack of 512 bytes, instruction counts) are real [src: ubuntu-server-docs 9f6de3fb42995ce1].

The ugly: privilege and risk. Tracing requires powerful capabilities; a BPF program can read all kernel memory it is allowed to probe, so granting `CAP_BPF` is close to granting root in practice, and unprivileged BPF is disabled in most distributions by `kernel.unprivileged_bpf_disabled`. In containers, tracing needs `SYS_ADMIN` or `BPF` plus access to the host's debug interfaces, which security policies often forbid. Tools may refuse to run under Secure Boot lockdown (kernel lockdown mode restricts kprobes in confidentiality mode). Tracing production hosts also carries the risk of high-frequency probes (scheduler events, network packets) that generate millions of events per second; an unfiltered `tracepoint:sched:sched_switch` one-liner can add visible load. Finally, interpretation traps: a histogram's power-of-two buckets hide detail, sampled stacks show proportions rather than counts, and a short capture may miss the rare slow event.

Mitigations: start with the cheapest tool that can answer the question; limit time (`timeout 30`) and scope (a PID, a cgroup, a CPU); use `perf trace` or the `strace --seccomp-bpf` option instead of plain strace on busy processes; keep debug symbols available (debuginfod makes this easier); and rehearse in staging.

## Applications beyond this domain

The idea of attaching small programs to events is the foundation of modern observability and security products. Cilium uses eBPF for Kubernetes networking and observability (its documentation covers Hubble flow monitoring), Falco and Tetragon use it for runtime security, Pixie and Parca/Pyroscope use it for auto-instrumentation and continuous profiling, and Meta's Katran and Cloudflare's DDoS mitigation run packet filters at the NIC driver with XDP. Flame graphs are used outside Linux, for Java, Go (`pprof`), Python and browsers. Sampling profilers and tracers appear in every language runtime (`py-spy`, async-profiler, `go tool trace`) and the same method applies, so what you learn about stacks, sampling frequency and off-CPU analysis carries over. The tracepoint concept appears in Windows ETW and macOS dtrace, and eBPF for Windows exists as a porting project (to verify maturity).

## Examples

**Why does it not start?** A service fails with only "configuration error" in its log. `strace -f -e trace=openat,stat -e status=failed -o /tmp/t systemctl start`-style tracing is awkward through systemd, so run the binary directly: `strace -f -e status=failed ./svc --config /etc/svc.conf` and the tail of the output shows `openat(... "/etc/svc/tls/server.key", ...) = -1 EACCES`. A permissions problem, not a syntax one, found in under a minute. The lab for this topic gives a recorded trace to read the same way.

**Why is it slow but idle?** A job takes four seconds per request, CPU 5%. `strace -c -f -p PID` over ten seconds shows `futex` and `poll` dominating time, and `strace -T -e trace=connect` shows a single DNS lookup of 3.0 seconds before it falls back to a second resolver. The fix is a resolver configuration, not code.

**Where is the CPU going?** `perf record -F 99 -g -p $(pidof app) -- sleep 30`, then a flame graph, shows a plateau in a JSON serialisation function. Rewriting it with a cached encoder cut CPU by 40% in the team's story; the figure is the sort of result such profiles produce rather than a general number.

**Who is hitting the disk?** `biolatency -D 10 1` shows a bimodal histogram, with a second hump at 8 to 16 ms. `biosnoop` names the process issuing the slow reads, and `opensnoop -p PID` names the files. Compare with `iostat -x` from LNX-307-T02, which showed only that the device was busy.

**A failing example.** An engineer attached strace to a production proxy at peak hours to find a timeout. The proxy slowed so much that health checks failed and the load balancer removed it, which hid the original fault and caused a brief outage. The correct approach would have been `perf trace`, or a bpftrace one-liner restricted to the target PID with `timeout 20`, taken on one node removed from rotation.

## Related problems and ideas

For off-CPU analysis, tools such as `offcputime` (bcc) and wakeup graphs help. Language-level profilers handle the managed runtimes that `perf` struggles with. `ltrace` traces library calls, `ftrace` and `trace-cmd` give low-level kernel tracing and are what many `perf` features build on, and `systemtap` remains in enterprise distributions. `gdb` and core files (LNX-307-T06) answer questions about a stopped process. Distributed tracing (OpenTelemetry, Jaeger, Tempo) is the cross-service equivalent, answering which service in a chain is slow, in the sense of the RED method. Not yet mainstream: continuous, always-on profiling in production at 1% overhead, kernel and user stack unwinding using SFrame (a new compact format introduced for the kernel and binutils), and eBPF-based schedulers (sched_ext, merged for Linux 6.12) that let administrators load scheduling policy as a BPF program (to verify).

## Active research

Active topics include verified safety of eBPF (formal proofs about the verifier and attacks against it, since a verifier bug is a kernel exploit), portability across kernels and architectures, and making BPF usable by non-experts through natural-language generation of bpftrace programs, which studies show produces plausible but sometimes wrong probes. Profiling research covers accurate sampling skid-free techniques (precise events such as PEBS and IBS), low-overhead stack walking, and continuous fleet-wide profiling as practised in large companies. Another area is making off-CPU and lock analysis cheaper. The kernel community is also working on tracing for confidential-computing guests, where the host cannot see inside.

## Future direction

Expect eBPF to become the default substrate for observability agents and security enforcement on Linux, with frame pointers and SFrame restoring cheap stack traces, and with more tools shipping as single CO-RE binaries. The command-line one-liners will persist as the exploratory interface, but fleets will rely on always-on, low-overhead profiling and on tracing with trace IDs that tie into the metric and log stacks (LNX-307-T03 and T04). Watch the evolution of unprivileged and delegated BPF (BPF tokens), changes in distribution defaults for frame pointers, and the growth of sched_ext. strace will remain the first, cheapest tool for any behaviour question, with its bpf-assisted filtering reducing its overhead.
