# Reliable benchmarking: measuring Linux performance so that the numbers mean something

## Define the problem

Almost every performance decision on Linux rests on a benchmark: whether this SSD is fast enough, whether the new kernel regressed, whether turning on a tunable helped, whether the cloud instance type is worth the price. And almost every benchmark result that appears in a ticket, a blog or a vendor slide is wrong in some way that the author did not notice. The wrong number may be from a test that measured the page cache instead of the disk, or the loopback interface instead of the network, a single run on a noisy machine, a CPU whose frequency changed halfway, or a workload that nobody in production runs. The error is rarely malice. It is a measuring instrument that was not understood.

The problem has three layers. **Validity**: does the test measure the thing that matters, in a way that resembles real use? **Repeatability**: do two runs under the same conditions give the same answer, within a stated error? **Interpretation**: what do the numbers allow you to conclude, and what do they not? This slice covers the method for getting trustworthy results on a single host or a pair of hosts: defining the question, controlling the system under test, choosing tools (`fio` for storage, `iperf3` for networks, `sysbench` and `stress-ng` for CPU and memory, application-level load generators), running enough repetitions, and reporting honestly. It ties back to the observation tools of LNX-307-T02 and T05, which show *why* a result came out as it did. The associated lab is a guided exercise on two real machines, so it is graded structurally rather than by a numeric answer.

## History and approaches

Benchmarking began as a competition between machine vendors. Whetstone (1972) and Dhrystone (1984) measured synthetic floating-point and integer mixes and were famously gamed: compilers learned to recognise Dhrystone and optimise it away, and a single number (MIPS) ended up standing for a machine's worth. The response was standardised suites built from real programs: SPEC CPU (1989 onward, now by a non-profit consortium) with strict run rules and disclosure of configuration, and the Transaction Processing Performance Council (TPC, 1988) for databases, which required audited results. On Linux, the kernel community leaned on microbenchmarks: LMbench (Larry McVoy, 1996) for latencies of system operations, Bonnie and IOzone for file systems, `netperf` and later `iperf` for network throughput, `sysbench` for CPU, memory and database tests, and Phoronix Test Suite for automated comparison across systems.

Jens Axboe's `fio` (2005, the flexible I/O tester) became the standard storage tool because it exposes the variables that matter: access pattern, block size, queue depth, direct or buffered I/O, I/O engine (`libaio`, `io_uring`), mixed read/write ratios, and latency percentiles. The RHEL network tuning guide documents testing TCP throughput with `iperf3`, which is a successor to the original `iperf` from the ESnet team [src: rhel-10-docs dd7feaf79b3bada6]. Cloud benchmarking, by contrast, discovered that the noisy neighbour problem and instance variability make single results unreliable, which pushed people to run many iterations over different times and instances.

The methodological work came later. Raj Jain's textbook on computer systems performance (1991) laid out experimental design and statistics. In the 2000s researchers identified the "measurement bias" problem, in which innocuous setup differences (the size of the environment variables on the stack, link order of object files) change measured performance by more than the effects being claimed; the 2009 paper by Mytkowicz and colleagues on producing wrong data without doing anything obviously wrong is the classic example (to verify the citation). Brendan Gregg's writings on benchmarking list common failures: not confirming the benchmark tool is the bottleneck, benchmarking the wrong thing, testing without a hypothesis, accepting the first number, and ignoring variance; he promotes an "active benchmarking" practice, in which you observe the system with the other tools *while* the benchmark runs to see what limits it [web: brendangregg.com]. Parallel work in the Java and statistics communities (JMH, Georges, Buytaert and Eeckhout's methodology for statistically rigorous evaluation) stressed warm-up, steady state and confidence intervals.

The pattern: from single number to distribution; from vendor suite to workload-specific test; from stand-alone score to benchmark with simultaneous observation.

## Current state

### A method

1. **State the question and the success measure.** Suitability of a new storage tier for a database becomes a measurable question: at queue depth 16 with 8 KiB random mixed I/O (70/30), is the 99th percentile latency under 5 ms at 20,000 IOPS A benchmark without a decision attached is an exercise.
2. **Characterise the real workload** (T02 `iostat` average request size, read/write mix, concurrency; `ss` for connection counts) and choose parameters to match it.
3. **Control the system under test.** Fix or record: kernel version and command line, firmware and microcode, CPU frequency governor (`cpupower frequency-info`, `tuned-adm active`; the `performance` governor removes frequency noise, and RHEL documents power and performance profiles through tuned [src: rhel-10-docs 6e70f2114bdec98f]), turbo and SMT state, transparent hugepages, NUMA placement (`numactl`), swap, background services (stop timers, indexers, `unattended-upgrades`), thermal state, mount options, filesystem and its fullness, and the storage's preconditioning. For SSDs this means writing the full device twice before a steady-state write test, because fresh drives are faster than aged ones. Record it all in a file next to the result.
4. **Isolate what you are measuring.** Disk tests must bypass the page cache (`--direct=1` in fio) or use a working set much larger than RAM; network tests should use two hosts, since a loopback test measures the CPU and the kernel stack only; CPU tests should pin to cores (`taskset`, `numactl --cpunodebind`) and check that the generator is not the limit.
5. **Warm up, then measure a steady state.** Discard the first seconds (`--ramp_time` in fio), run long enough that periodic effects (SSD garbage collection, TCP slow start, cache fill, power capping) appear in the result, usually 60 seconds to many minutes, longer for SSDs.
6. **Repeat and report variance.** At least three, preferably five to ten runs; report median or mean with min-max or standard deviation and the number of runs. If the spread is above a few percent, find the noise before comparing configurations. Change **one variable at a time** and randomise or interleave runs of A and B (ABABAB) to cancel drift.
7. **Observe while running (active benchmarking).** Run `mpstat -P ALL 1`, `iostat -x 1`, `vmstat 1`, `sar -n DEV 1` alongside (T02), watch the load generator's own CPU use, and check for errors (retransmissions, I/O errors). A result is a *finding* only if you can name the limiting resource.
8. **Report honestly.** Give the question, setup, tool versions and command lines, raw outputs, the statistics, the limiting resource and the caveats. A benchmark that others cannot rerun is an anecdote.

### The common tools and their traps

**fio.** A job file or command line chooses `rw=randread|randwrite|read|write|randrw`, `bs`, `iodepth`, `numjobs`, `ioengine`, `direct`, `runtime`, `time_based`, `ramp_time`, `size`, and `group_reporting`; output includes IOPS, bandwidth and completion latency percentiles (`clat` with `p99`, `p99.9`). Example: `fio --name=rr --filename=/dev/nvme1n1 --rw=randread --bs=4k --iodepth=32 --ioengine=io_uring --direct=1 --runtime=120 --time_based --ramp_time=10 --group_reporting`. Traps: writing to a real device destroys its data (use a file or a scratch device), testing a file smaller than the cache, using `iodepth` with a synchronous engine (it has no effect with `psync`), testing at queue depth 1 and calling it device capability, and reading only the mean when tail latency matters.

**iperf3.** `iperf3 -s` on one host and `iperf3 -c SERVER -t 30 -P 4` on another. Single TCP streams are limited by window size, round-trip time and one CPU core's softirq, so parallel streams (`-P`) reveal link capacity while single stream reveals per-flow behaviour. UDP mode (`-u -b RATE`) shows loss and jitter. Check the Retr column (retransmissions) and the sender and receiver CPU (`-V`, or `mpstat`). Traps: loopback, an MTU mismatch, virtual NICs without offloads, the iperf3 server being single-threaded in older versions (multi-threaded since 3.16, to verify), and rate-limiting by cloud providers.

**CPU and memory.** `sysbench cpu --threads=N run` measures prime-number events per second; `stress-ng --cpu N --metrics-brief` and `--vm` load and measure; `perf stat` (T05) gives instructions per cycle. `lmbench` or `stream` tests memory bandwidth. Traps: compiler optimisation that removes the work, thread counts beyond physical cores, hyperthreads counted as cores, CPU frequency, and shared caches in a VM.

**Application-level load.** `wrk`, `hey`, `ab`, `vegeta` and `k6` for HTTP, `pgbench` for PostgreSQL, `sysbench oltp` for MySQL. The key issue is **coordinated omission**: a closed-loop client that waits for each response before sending the next will slow down exactly when the server slows, so the measured latency understates what a real arrival process would see. Use open-loop (constant arrival rate) tools like `wrk2` or `vegeta` for latency, or correct afterwards with HdrHistogram (Gil Tene's analysis).

**Statistics.** Compute a mean and standard deviation, but for latencies report percentiles from a histogram (never average percentiles across runs; merge the histograms). To compare two configurations use enough runs for a confidence interval, or a non-parametric test such as Mann-Whitney U, and report the effect size, not only a p-value. A difference smaller than the run-to-run spread is not evidence.

The generalised pattern is **question, control, isolate, warm up, repeat, observe, report**.

## Assessment: the good, the bad and the ugly

The good: a disciplined benchmark produces numbers that survive scrutiny and can be repeated by someone else, which makes capacity planning, vendor comparison and regression hunting possible. Active benchmarking doubles as a performance investigation, since it shows which resource is limiting. Modern tools (fio, iperf3, perf) are free, scriptable and emit machine-readable output (`--output-format=json`), which fits continuous benchmarking in CI to catch regressions early, a method used by kernel and database projects.

The bad: the workload mismatch is the commonest failure. A synthetic test with a convenient pattern (sequential 1 MiB reads at queue depth 64) says nothing about a database that does random 8 KiB reads at queue depth 4. Cloud and virtualised environments make the system under test a moving target, with CPU steal, shared storage and network, and instance-to-instance variation of 10 to 30 percent being plausible (to verify for a given provider). Results depend on the full stack: firmware, kernel mitigations for speculative execution vulnerabilities (which cost a few to tens of percent depending on workload and are enabled by default), and power settings. Comparing results from different machines, or the same machine on different days, is rarely valid.

The ugly: the incentives. Vendors tune for the benchmark, publish the best of many runs and omit the configuration. Teams skip the repeated runs because they take time. People run the benchmark, see the result they expected and stop. And benchmark data gets reused outside its validity: a number measured on an idle bare-metal host is used to size a shared virtual cluster. Disk benchmarks can destroy data or wear flash, network benchmarks can disturb production traffic, and benchmarking in production needs the same care as any other change. There is also an environmental issue: precise benchmarks need quiet machines and long runs, which clashes with cost and carbon concerns.

Mitigations: write the question and the decision rule *before* running; use job files and scripts under version control; record the environment automatically (`lscpu`, `uname -a`, `tuned-adm active`, `nvme id-ctrl`); keep raw outputs; require an observation of the limiting resource; use A/B interleaving; use a checklist in review; and pair every benchmark with a claim of what it does not show.

## Applications beyond this domain

The experimental discipline is common to all measurement. Software performance regression testing in language runtimes and databases uses the same warm-up, repetition and statistical comparison. A/B testing of web products uses interleaving and confidence intervals. In machine learning, benchmarking training throughput needs the same control of data loading, thermal throttling and run-to-run variance (MLPerf has strict run rules for this reason). In hardware reviews, in drug trials (randomisation, blinding, pre-registration) and in physics (error bars, systematic uncertainty), the principles are the same: define the hypothesis, control the confounders, report the uncertainty. Coordinated omission has a parallel in survey design: measuring only those who answered. The idea of observing the system while testing it applies to load testing of any service with a metrics stack (LNX-307-T03).

## Examples

**Storage: a result that was cache.** A team reported 2.1 GB/s from `fio --rw=read --bs=1M --size=1G` on a SATA SSD that is rated for 550 MB/s. The file was 1 GB on a host with 64 GB of RAM and the test was buffered; it was reading from the page cache. Re-running with `--direct=1`, a 50 GB file and a 2-minute runtime gave 520 MB/s. `iostat -x` (T02) showed device throughput matching, which confirmed the active benchmark.

**Network: a single stream on a fast link.** `iperf3 -c` between two 25 Gb/s hosts reported 9.4 Gb/s. `mpstat` on the receiver showed one core at 100% in softirq. With `-P 4` the aggregate was 23.5 Gb/s. The limiting resource was a single core handling one flow, not the link; the fix for applications that need more is more streams or tuned receive-side scaling and offloads. This matches the observation in LNX-202's throughput lab.

**CPU: the governor.** Three runs of `sysbench cpu` gave 4,800, 5,300 and 6,100 events per second on the same laptop. `cpupower frequency-info` showed the governor was `powersave` with the clock varying; after switching to `performance` and pinning the process to a core, three runs gave 6,080, 6,110 and 6,095. The spread dropped from 24% to 0.5%.

**Latency: coordinated omission.** A closed-loop client with 50 connections reported a 99th percentile of 40 ms against a service that was stalling for one second every minute. The client simply stopped sending during each stall, so only 50 requests saw the stall. An open-loop generator at 1,000 requests per second recorded about 1,000 stalled requests and a p99 of 900 ms, matching what users saw.

**A failing benchmark report.** A claim that kernel 6.8 beat 5.14 by 12% was based on one run each on two different machines. Repeated on the same machine, five runs each interleaved, the difference was 2% with a standard deviation of 3%: not distinguishable. The original claim was noise plus a hardware difference.

## Related problems and ideas

Neighbouring fields include capacity planning with queueing models (use the measured service time and the arrival rate to predict latency at higher load), load testing in staging with production replay (capturing and replaying real traffic, with privacy care), performance regression testing in CI (continuous benchmarking with noise-aware thresholds), and profile-guided optimisation. Tools worth knowing are `hyperfine` for command-line timing with statistics, `pbench` and `phoronix-test-suite` for automation, `perf bench` in the kernel tree for scheduler and memory microbenchmarks, `will-it-scale` and `lkp-tests` used for kernel regression tracking by Intel's 0-day service, and `stress-ng` for stress and coverage. Not mainstream: statistical methods such as change-point detection that track regressions in a time series of results automatically (used at MongoDB and in the Linux 0-day performance reports; to verify), and benchmarks that report cost or energy per unit of work in addition to speed.

## Active research

Research addresses how to benchmark in the cloud (adaptive repetition schemes to determine how many runs are needed given measured variance), how to detect regressions in noisy CI environments (change-point detection, Bayesian and bootstrap methods), and how benchmark results transfer from microbenchmarks to application performance. Work on measurement bias continues, with tools that randomise environment layout (Stabilizer, Coz causal profiling) to remove layout effects. Energy and carbon measurement of workloads (RAPL counters, power meters) is growing. In storage, the SNIA performance test specifications for steady-state SSD measurement remain a reference, and research asks how to benchmark disaggregated and computational storage.

## Future direction

Expect continuous benchmarking to become standard infrastructure, with change-point detection and automatic bisection of regressions to a commit, and with environment capture built in. Cloud providers will offer more dedicated or bare-metal options for benchmark-grade stability, and tools will report distributions and confidence intervals by default (fio and iperf3 JSON output feed these pipelines). Benchmarks will increasingly include energy and cost. The enduring advice is the same as ever: ask a specific question, control and record the environment, repeat, watch the system while the test runs, and report what the numbers do not show.
