# Capturing and reading a kernel crash: kdump, vmcore and the crash utility

## Define the problem

When a user-space program fails, the operating system can write a core file and carry on. When the kernel itself fails, there is nothing left to catch it. A kernel panic, a hard lockup, a fatal oops, a memory-corruption bug in a driver: each halts the machine, and the only evidence is whatever fits on the console. The usual administrator response, a power cycle, destroys the one thing that could explain the failure, which is the contents of memory at the moment of death. Yet for a crash on a production server, "it happened once and rebooted" is not an acceptable root cause, and a vendor will not accept it as a bug report.

The problem has three parts. First, **capture**: how can a kernel that has just lost its integrity write a trustworthy copy of its own memory? It cannot rely on its own drivers, its own filesystem code or its own locks, since any of them may be the broken piece. Second, **storage**: memory images are as large as the machine's RAM, and the destination (local disk, network, encrypted volume) must be configured in advance. Third, **analysis**: a raw memory image is useless without the matching kernel symbols and the skill to read it. This slice covers the standard Linux solution: kdump, which reserves memory for a second kernel that saves the first one's memory to a file, and the `crash` tool, which opens that file. It covers configuration on Red Hat family and Debian family systems, test procedures, and a first analysis. Writing kernel patches belongs to LNX-330.

## History and approaches

Early Unix systems wrote the whole of memory to the swap area on a panic and recovered it on the next boot, a scheme that survived in the `savecore` utility. Linux's first debugging answer was less structured: the oops message printed to the console and the logs, readable with a serial console or a camera pointed at the screen. Tools such as `ksymoops` decoded the addresses. Netdump and diskdump from Red Hat were the first crash-dump facilities in Linux distributions; LKCD (Linux Kernel Crash Dump) was a patch set that tried to save the dump from the crashing kernel itself. This had the central flaw, that the dumping code ran in the failed kernel, including its disk drivers, in a state where any lock might be held or any structure corrupted. The success rate was disappointing, and LKCD never reached the mainline.

The robust idea, due to Eric Biederman and others in the early 2000s, was to **boot a second kernel** from within the failed one and let it do the saving. The **kexec** mechanism loads a kernel image into memory and jumps to it, bypassing firmware, and the kexec system calls (`kexec_load`, later `kexec_file_load`, which lets the kernel verify a signature) are documented in the manual pages [src: man-pages b2f8f6097993eea2]. In the crash case, the second kernel is loaded ahead of time into a reserved region of memory, so it is not overwritten, and the panic handler jumps into it with the first kernel's memory intact and exported as a read-only ELF file `/proc/vmcore`. The mechanism was merged into the mainline kernel in 2.6.13 (2005; to verify), and the `kdump` service on distributions wraps it. `makedumpfile` (from NEC and others) arrived to compress and filter the image, skipping page-cache pages, zero pages and free pages, so that a 2 TB machine does not need a 2 TB file. The Red Hat documentation describes the core collector and the target configuration in detail [src: rhel-10-docs e6e465c5d63bfea7].

Analysis tools followed. `gdb` can open a vmcore with extra support, but the `crash` utility (David Anderson at Red Hat, 1999 onward) wraps gdb with kernel-aware commands: `bt` for a backtrace, `ps`, `log`, `files`, `vm`, `kmem`, `dev`, `mod`, `sys`. It reads both live memory and vmcore files, and needs the kernel's debuginfo (`vmlinux` with symbols), which is a package on RHEL (`kernel-debuginfo`) and a debug symbols archive on Debian and Ubuntu (`linux-image-*-dbgsym`) [src: rocky-docs 6d847310313ee443]. Newer approaches include `drgn`, a programmable debugger from Meta that uses Python scripts to walk kernel structures, and `systemd-pstore` and the **pstore** mechanism, which saves the last console messages in firmware-backed memory (ACPI ERST, EFI variables, RAM oops) and recovers them after reboot; these are lighter than a full dump.

The pattern that emerged is **a trusted second kernel, a reserved memory region, a filtered image and a kernel-aware debugger**. Remaining failures include crashes that never reach the panic handler, such as hardware failures or watchdog resets with no chance to run any code, and platforms with encrypted disks or complex storage that make the capture kernel's job difficult.

## Current state

### Parts

- **Reserved memory.** A region is set aside at boot with the kernel command line parameter `crashkernel=`. Values are either fixed (`crashkernel=256M`), range-based by RAM size (`crashkernel=1G-4G:192M,4G-64G:256M,64G-:512M`), or `crashkernel=auto` or default sizing on newer RHEL, where `kdumpctl estimate` reports a suggested size. The memory is unusable by the first kernel, so it is a real cost. Setting it needs a reboot and, on RHEL, `kdumpctl reset-crashkernel --kernel=ALL` or `grubby --update-kernel=ALL --args=crashkernel=...` [src: rhel-10-docs f73d57ba06398133]. Rocky's guide shows the same task [src: rocky-docs 03ad5915afbc0eac]. The `kernel.panic_on_oops`, `kernel.softlockup_panic`, `kernel.hardlockup_panic`, `kernel.panic_on_unrecovered_nmi` and `kernel.unknown_nmi_panic` sysctls decide which faults actually lead to a panic and hence a dump.
- **Capture kernel and initramfs.** The `kexec-tools` package builds a special initramfs (`/boot/initramfs-<ver>kdump.img`) that is loaded with the capture kernel by the `kdump` service (`systemctl enable --now kdump`; check with `kdumpctl status`). On Ubuntu, the `kdump-tools` and `linux-crashdump` packages do the same, with configuration in `/etc/default/kdump-tools`.
- **Dump target and collector.** `/etc/kdump.conf` selects where the image goes: `path /var/crash` (default), a separate `ext4 UUID=...` or `xfs` device, or a network target (`nfs host:/export`, `ssh user@host`). `core_collector makedumpfile -l --message-level 7 -d 31` selects compression (`-l` for LZO, `-c` for zlib, `-p` for snappy, `-z` for zstd where available) and the dump level `-d 31` (exclude zero pages, cache, user data, free pages). `failure_action` says what to do if the dump fails: `reboot`, `halt`, `poweroff` or `shell`; `default` is a reboot. The file `/proc/vmcore` is read by the capture kernel only, and the result is a directory like `/var/crash/127.0.0.1-2026-11-14-22:30:11/vmcore` plus `vmcore-dmesg.txt`, a text copy of the kernel log at the time of the failure that is often enough to start diagnosis [src: rhel-10-docs c43a447bd10a6e83].

### Testing a configuration

An untested kdump configuration is an unreliable one: the reserved memory may be too small, the target unreachable, or the initramfs stale after a kernel update. The standard test, on a non-production machine or in a maintenance window, is to trigger a crash deliberately:

```bash
sysctl kernel.sysrq=1
echo c > /proc/sysrq-trigger      # crash the system on purpose
```

The machine reboots into the capture kernel, writes the vmcore, and reboots again; afterwards the file is in the target directory. Other triggers include `echo 1 > /proc/sys/kernel/panic_on_oops` followed by a deliberate oops, and, in virtual machines, an NMI injection (`virsh inject-nmi`, relevant to the VIRT pathway) with `kernel.unknown_nmi_panic=1`, which crashes a hung guest for dump. Hypervisors can also capture guest memory directly (`virsh dump`), which avoids needing kdump in the guest at the cost of a different file format that `crash` can still read (to verify the exact format flags).

### Analysing with crash

```bash
crash "$VMLINUX" /var/crash/<dir>/vmcore   # VMLINUX: matching debug vmlinux
crash> sys          # kernel version, panic string, uptime, memory
crash> log          # kernel ring buffer up to the panic
crash> bt           # backtrace of the panicking task
crash> bt -a        # backtrace on every CPU
crash> ps | grep UN # tasks stuck in uninterruptible sleep
crash> kmem -i      # memory summary
crash> mod -S       # load module symbols
crash> dis -l func+0x30   # disassemble with source lines
```

The first read is nearly always `sys` and `log`, then `bt`. The panic string identifies the class: `Kernel panic - not syncing: Fatal exception`, `Out of memory and no killable processes`, `hung_task: blocked tasks`, `Hard LOCKUP`, `NULL pointer dereference at ...`. The backtrace lists functions; `RIP` (or `PC` on ARM) names the faulting instruction as function plus offset. With the module name in the trace (shown in brackets), the likely owner is a driver, and the `modinfo` details name its vendor. For soft lockups, the other CPUs' `bt -a` shows who holds the lock. For an OOM panic (LNX-307-T08), `kmem -i` and `ps -G` show who held the memory.

The pattern: **panic message, backtrace, owner module, comparison with known bugs**. Many vendors maintain databases that match a signature (function and offset) to a known fix, and Red Hat's kernel debugging tooling and Ubuntu's apport attach vmcores to bug reports.

## Assessment: the good, the bad and the ugly

The good: kdump gives a complete, filtered snapshot from a reliable context and is built into the mainline kernel and every enterprise distribution. It allows root-cause analysis of rare crashes, supports the vendor support model, and the `vmcore-dmesg.txt` file alone often explains the event. The `crash` tool is mature and scriptable. A tested kdump setup converts the sentence "it rebooted by itself" into evidence.

The bad: it has real configuration costs and failure modes. The `crashkernel` memory is withheld from the system, which is awkward on small virtual machines (a 1 GB guest cannot spare 256 MB) and large on machines with many devices, because the capture kernel needs memory for each driver it loads. Too little reserved memory produces a capture kernel that itself runs out of memory and hangs or reboots without a dump. Systems with many devices, SR-IOV virtual functions or large NUMA configurations may take a long time to bring up the capture kernel; limiting the initramfs to the necessary modules (`KDUMP_COMMANDLINE_APPEND="nr_cpus=1 irqpoll"`-style options, `nr_cpus=1` and `reset_devices`) is a regular tuning step. Network and encrypted targets require extra setup of credentials and drivers in the capture environment. Time is also an issue: dumping 1 TB of RAM, even filtered, can take many minutes during which the machine is down; some high-availability clusters (LNX-309) make fencing wait or race with the dump, and the Red Hat cluster documentation discusses how fencing devices can be tested by crashing a node with sysrq [src: rhel-10-docs bdc0eb83afc6af20].

The ugly: the quiet gaps. A kernel update installs a new kernel, and the kdump initramfs is rebuilt only if the service is running and healthy, so a machine can drift into a state where the next crash produces no dump, and nobody finds out until it matters. Secure Boot and kernel lockdown affect kexec: unsigned capture kernels may be refused, requiring `kexec_file_load` with a signed image. Dumps contain everything in memory, including keys, passwords and personal data, so storing and shipping them must be treated as sensitive, and the DISA STIG and similar baselines pay attention to this. A hard hardware fault, a firmware bug or a power loss never produces a dump. And analysis demands the exact matching debuginfo package; a vmcore without it is practically opaque, and storing the debug symbols for every kernel in the fleet is a build-system task.

Mitigations: test after every kernel or hardware change; monitor `kdumpctl status` or `systemctl is-active kdump` with the metrics system (LNX-307-T03); alert if `/proc/cmdline` lacks `crashkernel=`; keep debuginfo mirrors; cap the dump size with `-d 31` and compression; send vmcores to a protected host; and use pstore and a serial or netconsole target as a lightweight fallback for first-look information.

## Applications beyond this domain

The idea of an independent, minimal recovery context that saves state from a failed system has many siblings. User-space core dumps (`core(5)`, `systemd-coredump`, `coredumpctl`) apply the same discipline to processes, and the techniques of reading a backtrace and matching a symbol carry across. Hypervisor-level dumps and VM snapshots give the same evidence for guests. Firmware and hardware have their equivalents: baseboard management controllers record screen captures and "black box" logs on a crash, Android's last_kmsg and ramoops help phone makers, and the Windows kernel's "complete memory dump" and WinDbg are the same pattern, as are mainframe stand-alone dumps. In cloud services, the serial console and NMI-triggered crash dump let providers collect data from wedged instances. The strategic idea (reserve resources ahead of time, because you cannot allocate during a failure) also appears in database crash recovery with reserved log space and in out-of-memory-safe daemons that preallocate memory.

## Examples

**Setting up on RHEL or Rocky.** Install `kexec-tools`, check `cat /proc/cmdline | grep crashkernel`; if absent, run `kdumpctl estimate`, then `kdumpctl reset-crashkernel` (or `grubby ... --args=crashkernel=...`), reboot, enable and start `kdump`, confirm with `kdumpctl status`, and edit `/etc/kdump.conf` if the target should differ. Then test with `echo c > /proc/sysrq-trigger` in a maintenance window and look for the vmcore under `/var/crash` [src: rocky-docs f3b6bce243f6c93f].

**A first read.** After a production crash, `vmcore-dmesg.txt` ends with a `BUG: unable to handle kernel NULL pointer dereference at 0000000000000010` and `RIP: 0010:nfs4_run_state_manager+0x...`. In crash, `bt` shows the frame names in the NFS client, the `mod` line shows no third-party modules, and the kernel version matches a known bug fixed in a later errata. The action is to update the kernel, not to hunt for hardware.

**A hung machine.** A guest stops responding to the network and the console. From the hypervisor, `virsh inject-nmi guest` triggers a panic (with `unknown_nmi_panic` set), kdump records the state, and `crash` shows all CPUs spinning on one spinlock held by a stuck driver thread. Without the NMI step there would have been nothing to analyse.

**A failing example.** A fleet of virtual machines with 2 GB of RAM had `crashkernel=auto` resolved to 160 MB, which was too small for the capture initramfs with the virtio and network drivers. Each time a guest panicked, the capture kernel hit its own out-of-memory condition and the machine rebooted without a file. The problem was discovered only after a real incident. The fix was a documented test in the provisioning pipeline and a size of 256 MB for those images. This exemplifies why the sysrq test is part of acceptance, not an optional extra.

## Related problems and ideas

For crashes that leave no dump, alternatives include pstore with ramoops, `netconsole` (UDP log streaming from the kernel), a serial console captured by a terminal server, and the baseboard controller's logs. For soft hangs where the kernel remains alive, the SysRq keys give stack traces (`echo t > /proc/sysrq-trigger` for all tasks, `w` for blocked tasks) with no reboot; the Arch documentation on debugging freezes describes these [src: archwiki aa7a04ce291e47ef]. Live debugging of a running kernel is possible with `crash` against `/proc/kcore`, `drgn`, and `kgdb` over a serial link. `systemd-coredump` handles user-space; `gdb` and eBPF tools (LNX-307-T05) analyse live. Other related ideas: live patching (kpatch, livepatch) to avoid the reboot, automatic crash reporting to vendors (ABRT, `apport`, `kdump` upload), and not-yet-mainstream approaches such as fast kexec reboots to reduce downtime (kexec-based "soft reboot", also in systemd) and a persistent-memory-based panic log.

## Active research

Work in this area includes shrinking the capture environment (a minimal capture kernel and initramfs, faster device initialisation), crash-dump support for confidential-computing guests, where host-side memory capture is impossible and the guest kernel must dump itself with encrypted or protected memory (to verify current status of upstream support), and dumping with fewer reserved resources, such as the work on reserving memory with CMA or high memory above 4 GB on large systems. Automatic triage is another area: grouping vmcores by backtrace signature and using static analysis plus machine learning to suggest bug-fix candidates. Programmatic analysis with drgn and the use of BTF type data to analyse dumps without full debuginfo are active directions.

## Future direction

Expect kdump to remain the enterprise standard but to become easier: automatic sizing, a status check built into health tools and the installer, and encrypted and network targets with less hand-tuning. The kernel-side effort to make the capture path robust on very large memory machines and on arm64 and RISC-V continues. Analysis will move toward scripted tools (drgn) and cloud-based triage services that receive a filtered dump or just the vmcore-dmesg and backtrace. Watch for the interplay with Secure Boot, signed kexec images and UEFI-based dump facilities, and with live patching, which removes the need for some reboots. The operational rule is unchanged: reserve memory in advance, test the full path, and keep debug symbols for the kernels you run.
