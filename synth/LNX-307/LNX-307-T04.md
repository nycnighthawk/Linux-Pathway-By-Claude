# Central logging: journald, rsyslog forwarding and log aggregation stacks

## Define the problem

Logs are the narrative record of what a system did, and they are the evidence you need most after something has gone wrong. Left on the machine where they were produced they have three weaknesses. They disappear with the machine: a crashed, rebuilt or compromised host loses the very history that would explain it. They are scattered: a request that crosses six hosts leaves six partial trails in six places, in different formats and time zones. And they are mutable: an intruder with root can edit local files to hide their steps. Central logging is the practice of shipping a copy of every log record, as it is written, to a separate system that stores it durably, makes it searchable and enforces retention.

The slice covers the Linux path from a program writing a message to an analyst running a query. That path includes the local layer (the syslog protocol and API, the systemd journal, plain files, log rotation), the transport (rsyslog forwarding over TCP and TLS, journal upload, shipping agents), and the aggregation layer (Elastic, Grafana Loki, Graylog and similar). It treats reliability, security, structure and cost, and ties logs to metrics and traces. Writing a full search backend is out of scope. The related compliance angle, in which controls such as STIG and CIS demand remote logging with authenticated TLS, is covered at its overview level.

## History and approaches

Logging on Unix began with Eric Allman's `syslog` for Sendmail in the early 1980s: a daemon reads a local socket, and a table of facility (the kind of source, such as `auth`, `kern`, `daemon`, `local0` to `local7`) and severity (eight levels from `emerg` to `debug`) routes each message to a file, a terminal or a remote host over UDP port 514. It was standardised after the fact as RFC 3164 (2001) and then properly as RFC 5424 (2009), with RFC 5425 for TLS transport and RFC 6587 for TCP framing. The design had useful ideas, a common API and a routing table, and serious flaws. UDP is lossy. The message was unstructured text with a loosely defined timestamp lacking year and zone. There was no authentication or encryption, and a sender could spoof any host.

Successive daemons repaired this. **syslog-ng** (1998) added content filtering and TCP; **rsyslog** (2004, from Rainer Gerhards) added reliable delivery through RELP, queues with disk assistance, TLS, templates, and modules for databases and message buses, and became the default on Red Hat and Debian systems. The RHEL documentation describes rsyslog configuration, remote logging and its TLS setup as a supported solution [src: rhel-10-docs 736e668198bc6c08]. **Syslog-ng** and **Fluentd/Fluent Bit** (a log router with plugins, designed for containers) and **Logstash** (the L in the ELK stack) added parsing and transformation.

The next shift was the systemd **journal** (2011 onward). It stores records as binary, indexed files with structured fields (`_SYSTEMD_UNIT`, `_PID`, `PRIORITY`, `MESSAGE`) and trusted metadata that the sender cannot forge, captures the standard output of services, and supports Forward Secure Sealing, a cryptographic tamper-evidence scheme. `journalctl` queries by unit, time, priority and field. The journal was criticised for its binary format, for its performance with very large files and for how long it took to offer remote transport; `systemd-journal-remote` and `systemd-journal-upload` provide push and pull over HTTP(S) in the same package family [src: man-pages 683c9ff582507683]. On most distributions today, the journal and rsyslog run together: journald collects, and optionally forwards to rsyslog (`ForwardToSyslog=`), which writes the traditional files under `/var/log` and ships off-host. A compliance rule makes that forwarding explicit [src: compliance-as-code fccc39c90c7fa858].

The aggregation side tried several designs. Grep over rsync'd files did not scale. Splunk (2003) popularised indexing everything, at a price based on volume. The open source Elasticsearch, Logstash and Kibana stack (2010s) gave full-text indexing at the cost of heavy resource use. **Grafana Loki** (2018) took the opposite trade-off, indexing only a small set of labels per stream and storing compressed chunks, so that it is cheap to run and integrates with Prometheus-style labels (LNX-307-T03). Cloud services (CloudWatch, Cloud Logging) and Kubernetes-oriented agents (Promtail, now superseded by Grafana Alloy, to verify) completed the picture. The lesson is that index everything, which is expensive, and index nothing, which is slow to search, are two ends of a trade-off, and structured fields are what make the middle ground workable.

## Current state

### The local layer

Applications send logs in three ways: through the `syslog(3)` call or the `/dev/log` socket, to standard output and error captured by systemd or the container runtime, or to their own files. Services managed by systemd get stdout and stderr in the journal automatically. The journal is controlled by `journald.conf`: `Storage=persistent` (default `auto` stores in `/var/log/journal` only if the directory exists, otherwise in memory under `/run/log/journal`), `SystemMaxUse=`, `MaxRetentionSec=`, `RateLimitIntervalSec=` and `RateLimitBurst=`. Queries are done with `journalctl -u nginx --since "1 hour ago"`, `-p err`, `-b -1` (previous boot), `-f` (follow), `-o json`, `_PID=1234`, and `--disk-usage`; the manual page lists the filters and output modes [src: man-pages 7e378ea252e5f01c]. `logger` writes test messages. Log files are kept from growing forever by `logrotate`, run daily by a timer or cron, with a `/etc/logrotate.d/` file per application: `rotate 14`, `daily`, `compress`, `delaycompress`, `missingok`, `notifempty` and a `postrotate` script to make the service reopen its files, or `copytruncate` where it cannot [src: man-pages 5b4343359894656d].

### rsyslog forwarding

rsyslog reads `/etc/rsyslog.conf` and `/etc/rsyslog.d/*.conf`. The modern syntax is the "RainerScript" form: inputs are loaded with `module(load="imuxsock")` and `module(load="imjournal")`, and actions are written as `action(type="omfwd" ...)`. A client forwarding everything to a collector looks like this:

```text
# /etc/rsyslog.d/10-forward.conf
action(type="omfwd" target="logs.example.org" port="6514" protocol="tcp"
       StreamDriver="gtls" StreamDriverMode="1" StreamDriverAuthMode="x509/name"
       StreamDriverPermittedPeers="logs.example.org"
       queue.type="LinkedList" queue.filename="fwd" queue.saveOnShutdown="on"
       queue.maxDiskSpace="1g" action.resumeRetryCount="-1")
```

The queue parameters matter more than any others: with a disk-assisted queue and unlimited resume retries, a collector outage causes buffered, not lost, messages. Transport over TLS with an authenticated peer is the compliance standard, and the SCAP rules for TLS and authentication mode summarise it [src: compliance-as-code af1a1913298b2239]. The server side loads `imtcp` with a listener on 6514, a certificate, and a template that files each source host into its own directory, for example `template(name="PerHost" type="string" string="/var/log/remote/%HOSTNAME%/%programname%.log")`. A text-based `$template` and the old `*.* @@host` selector lines (single `@` for UDP, double for TCP) still work and appear in older documentation. Tools to test: `rsyslogd -N1` validates the configuration; `logger -p local0.info "test"` generates traffic; `tcpdump` shows whether bytes leave.

### Journal transport and shipping agents

For journal-native transport, `systemd-journal-upload` pushes entries to `systemd-journal-remote` on the collector over HTTPS (port 19532), which writes per-host journal files; this keeps the structured fields intact. The alternative is an agent that reads the journal or files and pushes to a backend: Promtail or Alloy to Loki, Fluent Bit or Filebeat to Elasticsearch, or the OpenTelemetry Collector. In Kubernetes, node-level agents read container logs from the runtime's directory. Agents add metadata labels (host, unit, namespace, pod) so the aggregation system can organise streams.

### Aggregation and querying

In Loki, a query is written in LogQL: a stream selector in braces such as `{job="varlogs", host="web1"}`, line filters (`|= "error"`, `!~`), a parser stage (`| json`, `| logfmt`), label filters, and metric functions like `rate({app="api"} |= "error" [5m])`. That last form turns logs into a metric that can drive an alert (LNX-307-T03). In Elasticsearch, documents are indexed with mappings and queried by KQL or the query DSL; index lifecycle policies move data between hot, warm and delete tiers. In all of them, the discipline is the same: choose a small, bounded set of labels or fields for identification, put variable content in the message, and set retention explicitly.

The generalised pattern is **emit structured events, ship reliably, enrich with identity, store with retention, query by label and time**. Correlation across hosts works only if clocks agree (NTP or chrony) and if a request or trace ID is written into every record.

## Assessment: the good, the bad and the ugly

The good: central logging gives you evidence that survives the host, supports forensic work, serves security and audit requirements and removes the need to log in to servers to read files. rsyslog is mature, light and configurable; the journal gives rich structure with trustworthy metadata; and label-indexed stores like Loki reduce cost sharply. Aggregated logs enable counts and alerts on rare events that metrics do not capture.

The bad: volume and cost. A busy debug-level service can write gigabytes per hour, and ingest, index and retention costs grow linearly with it. Log formats vary by application; without structure, extraction needs fragile regular expressions (grok patterns), which break on format changes. Delivery guarantees are weaker than they look: UDP drops silently; TCP buffers can be lost on a crash unless queues are on disk; at-least-once delivery produces duplicates. Multi-line events (stack traces) are split into several records unless the shipper is told how to join them. Time is a persistent problem: syslog's classic timestamps omit the year and zone, and a skewed clock scrambles the timeline of an incident.

The ugly: security and privacy. Logs are a rich place for leaked secrets, tokens, session identifiers and personal data, so central logging concentrates risk and may carry legal retention and deletion obligations. The collector is a high-value target and a single point of failure; its disk filling stops the whole pipeline (the sender's queue then fills, and backpressure can reach the application). A noisy host can flood the collector (a log storm), so rate limits, such as journald's burst limits, drop messages exactly when something is wrong. Rotation can lose data when a service keeps writing to a rotated file descriptor. The binary journal can be corrupted and is harder to repair than a text file, though `journalctl --verify` detects it. And no log can be relied on for what was not logged: the failure often was not recorded because the level was too high.

Mitigations: use disk-assisted queues and TLS with mutual authentication; apply per-source rate limits at the sender; log in a structured format (JSON or logfmt) with a request ID; scrub sensitive data at the source; keep clocks synchronised; monitor the pipeline itself (queue depth, last-received time per host, with an alert when a host goes quiet, LNX-307-T03); and set retention by class of data.

## Applications beyond this domain

The append-only, immutable record with replay is the basis of event sourcing, database write-ahead logs and replicated state machines; Apache Kafka is essentially a distributed commit log that many logging pipelines use as a buffer between shippers and indexers. Audit systems (the Linux audit framework, `auditd`, which can forward through `audisp`) use the same transport patterns and the same compliance rules. Security information and event management (SIEM) systems are central logging with correlation rules and case management. Kubernetes audit and application logs, cloud provider activity logs and CI/CD build logs all follow the label-and-stream model. Write-ahead logs show the same discipline of a durable queue in front of a slow consumer. The principle of shipping evidence to a place the subject cannot alter is shared with transparency logs, as in certificate transparency.

## Examples

**Forward and verify.** On a client, create the file `10-forward.conf` above, run `rsyslogd -N1`, restart rsyslog, then `logger -p authpriv.notice "test from $(hostname)"`. On the collector, `tail -f /var/log/remote/<host>/root.log` shows the line. Stop the collector for a minute, send ten more messages, restart it and confirm that all ten arrive, which proves the disk queue.

**Finding an incident in the journal.** `journalctl -u myapp --since "2026-11-14 22:00" --until "22:30" -p warning -o short-iso` gives the window. Adding `_PID=` or `-o json | jq` follows one process. `journalctl -b -1 -k` shows the kernel log of the previous boot, which is where you look after an unexplained reboot (LNX-307-T06 for crash dumps).

**LogQL as a metric.** `sum by (host) (rate({unit="sshd.service"} |= "Failed password" [5m]))` converts failed logins into a per-host rate, which Grafana plots and an alert rule can threshold, linking the logging and metrics layers.

**A failing example.** A team rotated an application log with `create` and no `postrotate`, so the service kept writing to the renamed file; the new file stayed empty and the shipper, tailing by name, saw nothing. For three days monitoring reported silence as health. The fixes were `copytruncate` as a stopgap, a reload hook as the cure, and an alert on ten minutes without any log lines for every important stream. Lesson: absence of logs is a signal and needs its own alert.

## Related problems and ideas

Metrics (LNX-307-T03) and traces complete the three pillars of observability, and linking them by labels and trace IDs is a current design aim; logs answer why, metrics answer how much, traces answer where. Structured logging libraries and OpenTelemetry logs aim to replace parsing with emission. Alternatives to heavyweight indexing include columnar stores (ClickHouse-based systems), object-storage-backed designs, and sampling or tiering approaches. Related security tooling includes `auditd`, Wazuh and SIEM products, and tamper-evidence designs (Forward Secure Sealing, hash chains, WORM storage). The `dmesg` and kernel ring buffer (`journalctl -k`) are the lowest layer; the netconsole mechanism ships kernel messages over UDP when the disk is gone, which is helpful before a crash dump (LNX-307-T06). Not mainstream: log-less approaches that rely on continuous tracing, and eBPF-based capture of application events without code changes (LNX-307-T05).

## Active research

Research and engineering effort addresses log compression and parsing at scale: systems that automatically derive templates from raw lines (log parsing benchmarks such as Loghub, to verify) and compress by template and variable columns. Another area is anomaly detection on logs, including deep learning, and the question of whether it beats simple counting; evidence is mixed. Work on privacy-preserving logging (redaction, tokenisation) and on tamper-evident, verifiable logs addresses compliance. Within systemd, the project continues to improve the journal file format, remote support and the structured-log interfaces. OpenTelemetry's logging data model and semantic conventions are still evolving.

## Future direction

Expect convergence on structured, correlated telemetry: logs carrying trace and span IDs, collected by one agent and stored in cheap object storage with label indexes. The classical syslog daemon will remain the transport for network devices and compliance, while containers and services emit JSON to standard output. Expect more storage-tiering and sampling, which will push teams to decide what is evidence (kept in full) and what is noise (sampled). Watch for the replacement of older shippers by the OpenTelemetry Collector and Grafana Alloy, for changes in the journal's remote features and for regulation affecting retention. The enduring design rule is to ship it off the box, make it structured, and watch the pipeline itself.
