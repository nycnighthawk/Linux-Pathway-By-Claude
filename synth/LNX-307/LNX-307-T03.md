# Metrics, dashboards and alerts: Prometheus, Grafana and Alertmanager

## Define the problem

A single host can be examined with the commands of LNX-307-T02, but a fleet cannot. When forty machines and several hundred containers serve one product, three questions appear that no local tool answers. What is the state of everything right now, in one place? What did it look like at the time of the incident, and what was the trend before it? And who should be told, and when, without anyone staring at a screen? A monitoring system has to collect numbers from many sources at a regular rhythm, store them compactly, let people ask questions of them, draw them, and turn some of them into notifications.

Three hard properties make this difficult. Scale: millions of time series with a label for every host, container, endpoint and status. Reliability: the monitoring system must work when everything else is failing, which is the moment it is needed. Judgement: an alert that fires too often is ignored, and one that fires too late is useless. This slice covers the most widely used open source answer on Linux and Kubernetes: Prometheus for collection, storage and querying; exporters that expose host and application metrics; Alertmanager for routing notifications; and Grafana for dashboards. It covers how to install and configure them on a host, write queries and rules, and design alerts. Metrics storage at very large scale and tracing are only mentioned.

## History and approaches

The earliest networks of Unix machines were watched with SNMP and polling tools. MRTG (late 1990s) and RRDtool graphed router interface counters from fixed-size round-robin files; Nagios (1999 as NetSaint) ran check scripts and answered a binary question, whether a service was up. Both models were host-centred and static: a person edited a configuration file when a machine was added. Ganglia (2000s) collected metrics for clusters. Graphite (2008) and StatsD changed the storage model to a metric name path in a time-series database with a push model, which scaled but encoded dimensions in dotted names, making questions about error rates per customer and endpoint awkward. Zabbix and Icinga combined checks and graphs with a central database, which was easy to adopt but became a bottleneck on large installations.

Prometheus began at SoundCloud in 2012, inspired by Google's internal Borgmon, and became the second project to join the Cloud Native Computing Foundation after Kubernetes (2016) and graduated in 2018 (to verify dates). Its design choices answered the failures of earlier systems. A **dimensional data model** stores each series as a metric name plus key-value labels, so queries can slice and aggregate on any label. **Pull-based collection** (the server scrapes an HTTP endpoint) makes it obvious when a target is down (the `up` metric becomes 0) and lets any developer see the same text a scraper sees. **Service discovery** finds targets in Kubernetes, cloud APIs, files and DNS rather than static lists. The query language PromQL lets alert rules and dashboards share one expression language. And each server is autonomous, with local storage, so that a failing network between sites does not take out monitoring.

Grafana (2014), a dashboard and visualisation tool, arrived as a front end for Graphite and became the common face for Prometheus, Loki and many data sources, with its own alerting added in version 8 and 9. The Alertmanager, separate from Prometheus, took over deduplication, grouping, silencing and routing. The Prometheus text exposition format later became the OpenMetrics specification, and OpenTelemetry now offers a vendor-neutral way to emit metrics, traces and logs, with Prometheus compatibility.

The approaches that partly succeeded include push-based systems such as InfluxDB with Telegraf (convenient for short-lived jobs and for devices behind firewalls), commercial agents (Datadog, New Relic) that add hosted storage, and clustered stores like Thanos, Cortex and Mimir, VictoriaMetrics, which add long-term retention and a global view to Prometheus. The failure modes in all of them were similar: cardinality explosions that exhaust memory, alert storms during an outage, and dashboards that nobody can interpret. The pattern that emerged is a split: a simple local collector and store per failure domain, a global layer for long retention and cross-site queries, and a separate alert router.

## Current state

### Components

A Prometheus deployment has these parts, and the Docker documentation gives a minimal example of a configuration file for the first of them [src: docker-docs 1d45b6328cd77443].

- **Prometheus server**: scrapes targets listed in `prometheus.yml` under `scrape_configs`, stores samples in its local time-series database (TSDB) under the directory given by `--storage.tsdb.path`, evaluates rule files, and serves the HTTP API and expression browser on port 9090. Retention defaults to 15 days and is set with `--storage.tsdb.retention.time` or a size limit.
- **Exporters**: processes that translate other systems into the text format. `node_exporter` (port 9100) publishes host metrics from `/proc` and `/sys` (CPU, memory, disks, filesystems, network), `blackbox_exporter` probes endpoints, and `cadvisor` or the kubelet expose container metrics. Applications use a client library (Go, Python, Java and others) to expose their own.
- **Alertmanager** (port 9093): receives firing alerts from Prometheus, groups, deduplicates, silences and inhibits them, and routes by label to receivers such as email, a chat service or a paging provider.
- **Grafana** (port 3000): queries Prometheus (and other sources) and draws dashboards; its provisioning mechanism loads data sources and dashboards from files so that they can be kept in version control.

### The data model and metric types

A sample is a float plus a timestamp, in a series identified by the name and labels, for example `node_cpu_seconds_total{cpu="0",mode="idle"}`. There are four metric types. A **counter** only goes up (or resets at restart): requests served, bytes sent. A **gauge** moves both ways: memory in use, queue length. A **histogram** counts observations in buckets (`_bucket{le="0.5"}`) with `_sum` and `_count`, allowing quantile estimation; a **summary** computes quantiles in the client. The text format is lines of `name{labels} value`, preceded by `# HELP` and `# TYPE` comments.

### PromQL essentials

Selectors choose series: `up{job="node"}`, with matchers `=`, `!=`, `=~`, `!~`. A range selector such as `[5m]` gives a window. The key function is `rate(counter[5m])`, the per-second average increase over the window with counter resets handled; `irate` uses the last two points and is for volatile graphs; `increase()` gives the total over the window. Aggregation uses `sum by (label)`, `avg without (label)`, `topk`. For histograms, `histogram_quantile(0.99, sum by (le) (rate(x_bucket[5m])))` gives a percentile. Useful host queries, which mirror the sysstat columns in LNX-307-T02:

```promql
# CPU busy fraction per host
1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))
# memory actually available
node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
# disk time busy (the iostat %util equivalent)
rate(node_disk_io_time_seconds_total[5m])
# RED: request rate, error ratio, p99 latency
sum(rate(http_requests_total[5m]))
sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))
```

The first expressions are the USE method (LNX-307-T01) written as queries, the last three are RED.

### Rules and alerts

Rule files hold two kinds of rules in groups. A **recording rule** precomputes an expensive expression and stores it as a new series (convention `level:metric:operations`). An **alerting rule** has a name, an expression, a `for` duration, labels and annotations:

```yaml
groups:
- name: host
  rules:
  - alert: HostMemoryPressure
    expr: rate(node_vmstat_pgmajfault[5m]) > 100 and node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes < 0.1
    for: 10m
    labels: {severity: page}
    annotations:
      summary: "Memory pressure on {{ $labels.instance }}"
      runbook_url: https://wiki.example.org/runbooks/memory-pressure
```

An alert whose expression is true is *pending* until the `for` period passes, then *firing*; the delay suppresses blips. Annotations carry the human text and the runbook link (LNX-307-T01). Kubernetes documentation includes an example of alerting from a state-metrics exporter, with the same structure [src: kubernetes-docs ad9ae5c590741233]. Rules are validated with `promtool check rules` and tested with `promtool test rules`, which feeds synthetic series into the rules and asserts the alerts that result; these can be run in CI. The configuration is checked with `promtool check config`, and a running server can reload with a SIGHUP or an HTTP call when `--web.enable-lifecycle` is set.

Alertmanager's configuration has a `route` tree matching on labels (`severity`, `team`), `group_by` and timing (`group_wait`, `group_interval`, `repeat_interval`), `receivers`, `inhibit_rules` (suppress a downstream alert when a source alert fires, such as host-down hiding service alerts on that host) and silences created in the UI or API. The Red Hat documentation covers a related path, which sets up PCP with Grafana and its notification channels on RHEL [src: rhel-10-docs 32e16980793b377a].

### Good alert design

The Prometheus guidance is to page on symptoms that users feel, to keep the count low, and to link alerts to dashboards [web: prometheus.io]. Cause alerts (disk filling, certificate expiry) belong to a ticket-level severity unless the time left is short; `predict_linear` can alert on a disk that will fill in four hours. The **absent** alert (`absent(up{job="x"})`) and a watchdog alert that always fires and is monitored by an external dead-man's-switch address the question of who watches the watchers. The pattern is: instrument, scrape, record, alert, route, document.

## Assessment: the good, the bad and the ugly

The good: the model is simple, debuggable (open `/metrics` in a browser), and has a vast ecosystem of exporters and integrations with Kubernetes. PromQL is expressive for aggregations across labels. The pull model gives a free liveness signal. Alert rules are code, reviewable, testable with `promtool`, and stored with the service they watch. Grafana gives non-experts readable pictures, and its provisioning makes dashboards reproducible.

The bad: Prometheus is a single-node store by design; long retention, high availability and global views require Thanos, Mimir or similar. Cardinality is the main way to hurt yourself: a label with unbounded values (user ID, URL path with parameters, container ID) multiplies series and exhausts memory. Counters need `rate()`, and many newcomers graph raw counters or take an `avg` of percentiles, which is statistically meaningless. Histogram buckets chosen badly give wrong quantiles. Pull does not suit short-lived jobs (a Pushgateway exists, with caveats) or targets behind NAT. Scrape intervals of 15 to 60 seconds miss brief spikes, so they complement the finer detail of the host tools.

The ugly: alert fatigue and ownership. Large rule sets accumulate alerts that fire constantly and are routinely silenced; thresholds copied from blog posts do not fit the workload. Dashboards proliferate until nobody trusts any of them. The monitoring stack itself needs security: exporters expose detailed system information, the Prometheus and Alertmanager APIs have no authentication by default (use a reverse proxy with TLS or the built-in basic-auth and TLS web configuration), and Grafana needs account hygiene. Upgrades change metric names between exporter versions (`node_exporter` 0.16 renamed most), which silently breaks queries and alerts, so the tests above matter. Finally, silences and inhibitions can hide real problems if forgotten, so expire them.

## Applications beyond this domain

The data model and discipline carry to many places. In Kubernetes the entire control plane, the kubelet and the pods expose Prometheus metrics, and the horizontal pod autoscaler can scale on custom metrics derived from them. Databases, message brokers and storage systems ship exporters. Network devices are reached through the SNMP exporter. The same alerting ideas (symptoms, severity routing, inhibition) occur in incident management tools. Dimensional metrics and recording rules appear in cloud-native services such as Amazon Managed Service for Prometheus and Google Cloud's managed Prometheus, and OpenTelemetry metrics follow the same label model (to verify per vendor). In business and application analytics, product teams use counters and histograms for signups and checkout times. Industrial and IoT monitoring uses the same scrape-and-store ideas with different protocols. The `for`-clause concept, hysteresis for stability, applies in any control system.

## Examples

**Install on one host.** On a Debian or Rocky host: install `prometheus` and `prometheus-node-exporter` (packages), edit the file `prometheus.yml` to hold a job named `node` with `static_configs: [{targets: ['localhost:9100']}]`, run `promtool check config prometheus.yml`, start the services, open port 9090, and query `up`. Add Grafana from its repository, add a Prometheus data source with URL `http://localhost:9090`, and import a community node dashboard.

**A RED alert with a runbook.** The rule `alert: HighErrorRatio` with expr `sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m])) > 0.02`, `for: 10m` and an annotation linking the runbook fires, goes to Alertmanager, is grouped by `service`, and is routed to the pager receiver for `severity=page`. A `promtool test rules` file feeds two minutes of 1% errors and ten of 5% and asserts the alert is pending at the second minute and firing at minute twelve.

**A failing example: cardinality.** A developer adds `user_id` as a label on a request counter. A week later, the server's resident memory has grown from 3 GB to 40 GB, queries time out and the server is killed by the OOM killer (LNX-307-T08). `topk(10, count by (__name__)({__name__=~".+"}))` shows the offender. The fix is to remove the label, put the identifier in logs (LNX-307-T04) or traces, and add a `sample_limit` or `label_limit` on the scrape job to stop a repeat.

**A failing alert.** A rule used `rate(errors_total[1m])` with a one-minute window and a 15-second scrape interval. Two samples fall in the window only some of the time, producing gaps. The common guidance is to make the range at least four times the scrape interval. The alert flapped until the window was widened.

## Related problems and ideas

Alternatives include Zabbix and Nagios-family tools for host and service checks, InfluxDB with Telegraf for push, VictoriaMetrics as a compatible and more efficient store, and commercial platforms. Performance Co-Pilot with Grafana is Red Hat's supported path on RHEL. The Grafana stack extends the model with Loki for logs (LNX-307-T04), Tempo for traces and Pyroscope for continuous profiling, all indexed by the same labels. SLO tooling (Sloth, Pyrra) generates burn-rate rules from objectives. Not yet mainstream: native histograms in Prometheus 3 with exponential buckets, which replace pre-set buckets with high-resolution automatic ones (to verify the release status); OpenTelemetry as the sole instrumentation API; eBPF-based collection agents that emit metrics without code changes (LNX-307-T05).

## Active research

Open questions revolve around cost and cardinality (how to limit series without losing dimensions), efficient storage encodings (Gorilla-style compression and its successors), and query performance over long ranges. Prometheus 3.0 (released in late 2024, to verify) changed the UI, enabled UTF-8 metric names and improved OpenTelemetry ingestion. Research on alert quality studies how to decrease noise (alert correlation, learned baselines, seasonal thresholds), and on anomaly detection using forecasting on metric series; results are mixed and operators often prefer simple, explainable thresholds. Another area is end-to-end verification of the monitoring pipeline itself.

## Future direction

The direction is toward unified telemetry: OpenTelemetry for emission, native histograms for latency, Prometheus-compatible stores that are horizontally scalable, and one query surface across metrics, logs and traces. Alerting will lean on service-level objectives and burn rates rather than raw thresholds, and rule sets will be generated and tested as code. Expect agentless eBPF collection and more integration of pressure metrics. Watch the releases of Prometheus, Alertmanager and Grafana for breaking changes, and keep exporter and rule versions pinned and tested. In an enterprise estate, the question is increasingly who runs the long-term store, not whether to collect.
