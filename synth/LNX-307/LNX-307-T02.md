# Reading the counters: vmstat, iostat, mpstat, pidstat and sar from the sysstat family

## Define the problem

Before any metrics server, tracer or profiler is installed, a Linux host already keeps a large set of counters. The kernel counts CPU ticks in each mode, pages scanned and swapped, sectors read and written per block device, packets per interface, context switches, interrupts and much more, and it exposes them as plain text under `/proc` and `/sys`. The problem this slice addresses is turning those raw cumulative numbers into answers: is the machine CPU-bound, memory-starved, disk-bound or network-bound, which process is responsible, and was it also like this last Tuesday?

Three things make the raw files hard to use directly. The counters are cumulative since boot, so a single reading says nothing about the present; you need two readings and a division by the interval. The counters are scattered across many files with different formats. And what happened an hour ago is gone unless something recorded it. The tools in this topic solve those three problems: they sample twice and compute rates, they present related counters in one table, and (in the case of `sar`) they keep history.

The scope is the classic command-line toolbox that is available on almost every server: `vmstat` from the procps package, and `iostat`, `mpstat`, `pidstat`, `sar` and the collector scripts from the sysstat package. Later topics build on it with metrics servers (LNX-307-T03) and tracing (LNX-307-T05). The aim is not memorising every column but knowing which command answers which question and what normal looks like. It follows the USE checklist from LNX-307-T01: each tool is a way to read utilisation, saturation or errors for a resource.

## History and approaches

The earliest approach was reading kernel memory. On the Unix systems of the 1970s, programs like `ps` and `iostat` opened `/dev/kmem` and used the symbol table to find kernel structures, which tied each tool to a specific kernel build and required privilege. `vmstat` and `iostat` appeared in the BSD and System V lineages in the 1980s and gave the familiar one-line-per-interval format; `sar`, the System Activity Reporter, came from System III and System V and was the first widely used tool to record activity to a daily file for later reporting.

The Linux kernel took another route: a text interface under `/proc`, introduced in the 1990s and extended continuously. `/proc/stat` exposes per-CPU time in categories, `/proc/meminfo` and `/proc/vmstat` expose memory and paging, `/proc/diskstats` exposes per-device block statistics, and `/proc/net/dev` exposes interface counters; the manual page for `proc_vmstat` documents the memory counters [src: man-pages 3fab052962ba4513]. Tools could now be written in portable user-space code. Sebastien Godard's sysstat project, started in 1999, reimplemented the System V tool set for Linux, and its source and releases live on GitHub today [web: github.com]. The `vmstat` and `top` tools came with the procps project.

Several approaches coexisted afterwards, each with failures. Interactive monitors (`top`, later `htop` and `atop`) are good for a live view but have no history and are unreliable for short bursts that finish between refreshes. Always-on collectors such as `sar` keep history but at coarse resolution (ten minutes by default), which misses spikes. Large monitoring systems (Nagios, Zabbix, later Prometheus) added fleets and alerting but not necessarily the detail of per-process and per-device columns. Performance Co-Pilot (PCP), which Red Hat supports and documents in its tuning guide, archives hundreds of metrics at one-second granularity and was meant as the answer to the resolution problem [src: rhel-10-docs 4e8e2d0876c6c6f8].

A technical problem shaped the tools: the definition of disk utilisation. `iostat -x` reports `%util` as the fraction of time that at least one request was in flight. That was a sound measure for a single-spindle disk, but with SSDs and NVMe devices that serve many requests in parallel, 100% no longer implies saturation. Later versions of sysstat changed some column names (`avgqu-sz` became `aqu-sz`, `rrqm/s` stayed) and removed `svctm`, because the number could not be computed in a meaningful way; the manual for the version in use is the authority (to verify the exact release of each change). The lesson that pushed the field forward is that a counter's meaning depends on the hardware generation, so a column must be read with an understanding of how it is computed.

## Current state

### The family and what each answers

All of the tools take the pattern `command [options] interval [count]`. Without an interval they print averages since boot (an almost useless number for a long-running machine), so the first habit is always to give an interval. With an interval, the first line is still the since-boot average in `vmstat`, `iostat` and `mpstat`, and it should be discarded.

**`vmstat 1`** prints one line per second summarising processes, memory, swap, block I/O, system and CPU. Important columns: `r` (runnable tasks, a saturation signal for CPU when it exceeds the core count), `b` (tasks in uninterruptible sleep, typically waiting on I/O), `swpd`, `free`, `buff`, `cache`, `si` and `so` (swap in and out per second, the saturation signal for memory), `bi` and `bo` (blocks in and out), `in` and `cs` (interrupts and context switches per second), and the CPU split `us`, `sy`, `id`, `wa`, `st`. The manual describes the fields and the `-a`, `-d`, `-s`, `-S` and `-w` options [src: man-pages c10554b75879533b]. A high `wa` means that CPUs are idle while tasks wait for I/O; a high `st` means a hypervisor is taking CPU time from the guest, which matters in the VIRT pathway.

**`mpstat -P ALL 1`** shows the same CPU split per core. This distinguishes an eight-core machine with a single core at 100% (one saturated thread) from one with all cores at 12% (evenly spread load). It also splits out `%irq`, `%soft` (softirq, often network receive), `%steal` and `%guest`.

**`iostat -xz 1`** (extended statistics, hide idle devices) shows, per device, reads and writes per second (`r/s`, `w/s`), throughput (`rkB/s`, `wkB/s`), average request size, average queue size (`aqu-sz`), average wait (`r_await`, `w_await`, in milliseconds) and `%util`. Throughput and IOPS tell you the load; `await` tells you what the application experiences (queue plus service time); queue size tells you saturation. `iostat -c` and `-d` select the CPU and device parts, `-p` adds partitions and `-h` gives human-readable output (to verify availability in older releases).

**`pidstat`** answers the next question, which process. `pidstat -u 1` gives per-process CPU use, `-r` memory (page faults, resident set), `-d` disk I/O per process, `-w` voluntary and involuntary context switches, `-t` threads, and `-p PID` or `-C name` restrict the targets [src: man-pages 12623c1823037255]. A process with a high involuntary context-switch rate is being pre-empted because it is competing for CPU; a high voluntary rate means it is blocking often.

**`sar`** is the historian. Called as `sar -u 1 5` it samples live; called as `sar -u -f /var/log/sa/sa14` or `sar -s 09:00:00 -e 10:00:00` it reads recorded data. Its selectors include `-u` (CPU), `-r` (memory), `-S` (swap), `-B` (paging), `-b` (I/O summary), `-d` (block devices), `-n DEV|EDEV|TCP|ETCP|SOCK` (network), `-q` (run queue and load), `-w` (context switches and task creation), `-W` (swap pages) and `-A` (everything). `sar` can also print pressure stall data in newer versions through `--psi` options (to verify the option names against the installed release).

### Recording history

Collection is done by `sa1`, which invokes the `sadc` data collector and appends a record to the day's binary file, and `sa2`, which writes a daily text report; both are described in the sysstat manual [src: man-pages 39a03547d0a2aaa2]. On Red Hat family systems a systemd timer, `sysstat-collect.timer`, runs the collector every ten minutes and `sysstat-summary.timer` runs the summary daily, with data in `/var/log/sa/` and retention set by `HISTORY` in `/etc/sysconfig/sysstat`. On Debian and Ubuntu the package installs a cron job or timer and collection must be enabled by setting `ENABLED="true"` in `/etc/default/sysstat`. The collection interval is the one thing most worth changing: ten minutes hides short spikes, so many sites reduce it to one minute (override the timer) or, for finer detail, use `sadc` with a one-second interval during an investigation. Files are binary and tied to the sysstat version, so `sadf` is used to convert them to text, CSV, JSON or XML: `sadf -j /var/log/sa/sa14 -- -u` gives JSON for CPU.

### Workflow: from symptom to process

A well-practised sequence takes about two minutes and follows the USE method (LNX-307-T01). `uptime` for load trend, `vmstat 1 5` for the overall picture (queue, swap, wait), `mpstat -P ALL 1 3` for core balance, `iostat -xz 1 3` for disks, `sar -n DEV 1 3` for interfaces, then `pidstat 1 3` (all processes) and `pidstat -d 1 3` to name the heavy process. Brendan Gregg popularised a ten-command variant for the first sixty seconds on a host, built from these same tools plus `free`, `dmesg` and `top` [web: brendangregg.com]. The generalised pattern is: sample, compute rates, compare with a baseline, pivot from system to device to process.

## Assessment: the good, the bad and the ugly

The good: these tools are installed or one package away on any distribution, need no daemon, put little load on the machine and produce text that is easy to script and to paste into a ticket. They have decades of documentation and shared vocabulary. The `sar` history is a powerful after-the-fact tool; an engineer who is called a day late can still see yesterday's pattern if the collector was on. The cost of the recorded data is a few megabytes per day.

The bad: resolution and memory. Ten-minute averages smooth a one-minute disaster into a modest blip. Cumulative counters can wrap or reset (after a reboot or a module reload), and a sampling pause (a stalled VM) makes a rate look wrong. Process tools see only what exists at the sample instant, so short-lived processes escape `pidstat`; `execsnoop` from the bcc tools (LNX-307-T05) or process accounting catches them. The tools show symptoms in one host only and say nothing about distributed causes. Misreadings are common: treating `free` memory as the health measure when the kernel is meant to use spare memory as cache (the `available` figure in `free` or `MemAvailable` in `/proc/meminfo` is the right one), reading load average without the context of how many cores exist, or reading `%util` on a parallel device as saturation.

The ugly: container and virtual boundaries. Inside a container, `/proc/stat` and `/proc/meminfo` normally describe the whole host unless a shim such as lxcfs is used, so `vmstat` and `top` report numbers that do not match the container's limits. The cgroup files (`cpu.stat`, `memory.stat`, `io.stat`, `pressure`) are the right source (LNX-307-T08). In VMs the guest cannot see the hypervisor's contention except as the `steal` column, and `iowait` is an unreliable sign of anything since it counts idle time with outstanding I/O (a quirk documented in discussions of the kernel accounting; to verify). Timing issues also matter on tickless kernels: CPU accounting is sampled in older configurations and exact in others. Finally, version drift between sysstat releases changes field names, which breaks scripts that parse text; machine-readable `sadf -j` output reduces that risk.

## Applications beyond this domain

The pattern of sampling cumulative counters twice and dividing by the interval is general. Prometheus does this when `rate()` is applied to a counter (LNX-307-T03), and its counter-reset handling mirrors the wrap problem above. SNMP monitoring of routers computes interface rates the same way. Databases publish cumulative statistics views (PostgreSQL's `pg_stat_*`, MySQL's status variables) that are meaningless without deltas, and tools like `pg_stat_statements` extensions require the same subtract-two-snapshots discipline. Storage arrays and cloud providers report IOPS, throughput and queue depth with the same relationships, so the reasoning about `await` and queue size carries over to cloud block volumes. The `sar`-style daily archive is the ancestor of every time-series database, and the recommended practice of keeping baseline data from healthy periods applies to any monitoring system.

## Examples

**Memory pressure.** `vmstat 1` shows `si` and `so` in the hundreds of kilobytes per second, `free` shrinking, `b` growing and `wa` rising. This is the signature of swapping: the machine is saturated on memory, and the next step is `pidstat -r 1` to find the process with the largest resident set, then checking whether a limit or a leak applies (LNX-307-T08 covers cgroup limits and OOM).

**Disk saturation on a database host.** `iostat -xz 1` shows one device at 98% `%util`, `w_await` at 40 ms and `aqu-sz` at 12, while `vmstat` shows a modest `wa` of 25%. `pidstat -d 1` identifies a backup job doing writes. Throttling the job or moving it off peak resolves it. Had the device been NVMe, the 98% would not be conclusive; the await and queue size would be the deciding numbers.

**Using the history.** A user reports slowness around ten past three the previous afternoon. `sar -u -s 15:00:00 -e 15:30:00 -f /var/log/sa/sa14` shows the CPU idle fell to near zero at 15:10, and `sar -q` for the same window shows a run queue of 40. `sar -n DEV` shows nothing unusual. The conclusion is a CPU spike from a scheduled job, which `journalctl --since` then ties to a specific timer.

**A failing example.** An administrator ran `iostat` with no interval, saw 2% `%util` and concluded the disk was healthy while users were reporting delays. The single report was the average since boot, on a machine that had been up for 200 days. Running `iostat -xz 1` showed the live 99%. The error was reading a cumulative average as a current value. The lab asks you to compute rates from two snapshots by hand to build the instinct.

```bash
# sample CPU for 5 seconds and print only busy%, using plain /proc/stat
a=($(head -1 /proc/stat)); sleep 5; b=($(head -1 /proc/stat))
idle=$(( b[4]-a[4] )); tot=0; for i in {1..8}; do tot=$(( tot + b[i]-a[i] )); done
echo "busy: $(( 100*(tot-idle)/tot ))%"
```

## Related problems and ideas

A neighbouring approach is the interactive monitor family: `top` (procps), `htop`, `atop` (which records history with per-process accounting and can reveal short-lived processes), and `glances`. `perf stat` and the tools in LNX-307-T05 answer questions on how the CPU is spending time (cycles, cache misses), which counters cannot. `ss` and `nstat` provide detailed TCP counters, and `/proc/pressure` supplies saturation. Fleet-wide, node_exporter (LNX-307-T03) exposes the same `/proc` data over HTTP, so a Prometheus query on `node_disk_io_time_seconds_total` is the networked equivalent of `iostat`'s utilisation. PCP offers a coherent archive and a `pmrep`-style CLI and is documented by Red Hat [src: rhel-10-docs 4e8e2d0876c6c6f8]. In the container and cloud world, cAdvisor and the kubelet export per-cgroup versions. Not yet mainstream: always-on one-second continuous profiling and metrics at sub-second resolution, kept cheaply by pushing the sampling into eBPF programs.

## Active research

Work on the accuracy of utilisation and wait measures continues. Kernel developers have discussed better block-layer accounting for multi-queue devices (the `io_ticks` field and its sampling), and per-cgroup I/O latency statistics. The pressure stall mechanism is being extended and used as the signal for user-space memory managers such as systemd-oomd (LNX-307-T08). There is research on low-overhead always-on collection, including sampled and compressed time series and on-host aggregation, and on automated baseline and anomaly detection over such archives. Open questions are how to represent saturation for parallel devices in one number, and how to handle accounting across virtualisation layers so that a guest's steal and a host's idle can be reconciled.

## Future direction

The classic tools will stay, since they are small, scriptable and universal, but their role will shift to being the first, local view. Expect more JSON output options (`sadf -j` already; `iostat` and `mpstat` have JSON output in recent sysstat) so that results can be piped to other tools, and more support for pressure metrics. The trend in distributions is towards enabling a recorder by default (a sysstat timer, or the PCP daemon `pmlogger`) with shorter intervals. Observers should watch the kernel's accounting changes and the replacement of `%util` semantics for parallel devices, and note version differences between enterprise distributions, which keep older sysstat releases than the project's current one.
