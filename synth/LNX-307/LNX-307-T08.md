# Running out of memory, and limiting resources with cgroups v2

## Define the problem

Memory is the one resource on a Linux machine that cannot be shared by waiting. A busy CPU only slows its users down, and a busy disk queues requests, but when physical memory and swap are both exhausted the kernel has nothing to give and must take something back. Linux makes this harder by promising more than it has: by default it allows processes to allocate more virtual memory than exists (overcommit) on the bet that most of it will never be touched. When the bet fails, an allocation or a page fault cannot be satisfied and the kernel's last resort is the **out-of-memory (OOM) killer**, which picks a process and ends it. To an operator this looks like a service that vanished with no error of its own, only a line in the kernel log.

Two linked problems follow. The first is **diagnosis**: finding out that a kill happened, which process was chosen and why, who actually consumed the memory, and whether the cause was a leak, a misconfiguration, a genuine capacity shortfall or a limit set too low. The second is **control**: how to stop one workload from taking the whole machine's memory, CPU, I/O or process slots, which is the job of control groups (cgroups). This slice covers the mechanics of the OOM killer, the cgroup version 2 interface for memory, CPU, I/O and PIDs, the systemd and container front ends to it, the pressure information that predicts trouble, and the early-kill daemons that try to act before the kernel does. It connects to LNX-310 (containers) and LNX-308 (virtualisation), where the same limits are applied to containers and guests.

## History and approaches

Early Unix systems handled memory exhaustion by refusing `malloc` and by swapping whole processes. Linux's virtual memory manager from the 2.0 and 2.2 era introduced overcommit, lazy allocation and a rudimentary OOM killer (`oom_kill.c`, 1998 and a much-quoted kernel-mailing-list analogy likening overcommit to an airline that sells more seats than exist; to verify the attribution). The selection heuristic ("badness") has been rewritten several times: it weighs how much memory a process is using, how long it has run, and whether it is privileged, and then admits a user-controlled adjustment: `/proc/PID/oom_score` shows the current score and `/proc/PID/oom_score_adj` (from -1000 to +1000) shifts it, with -1000 making a process immune [src: man-pages b43a629c249e6308] [src: man-pages 8ffbb178897ea949]. The earlier `oom_adj` is obsolete. Its failure mode was that it often killed the wrong thing, a large but innocent database, or an important daemon that merely had a big footprint, while the actual leaking process was small relative to the total.

Policy knobs came next. The sysctl `vm.overcommit_memory` accepts heuristic (0, default), always (1) and strict accounting (2, with `vm.overcommit_ratio`), and strict mode makes allocation fail early instead of killing later, at the price of breaking programs that reserve big address ranges (Java, Go and databases commonly do). `vm.panic_on_oom` turns an OOM into a panic, which clusters use to fail over quickly and which pairs naturally with kdump (LNX-307-T06). `vm.swappiness`, `vm.min_free_kbytes` and watermarks influence when reclaim begins.

**Control groups** were added to the kernel in 2007 (Paul Menage and Rohit Seth at Google, originally "process containers"), and cgroup **v1** made one hierarchy per controller (memory, cpu, blkio, pids and so on). This gave flexibility but created inconsistent semantics: controllers could not cooperate, such as accounting buffered writeback I/O against the memory cgroup that dirtied the pages, and each controller had its own interface and quirks. Tejun Heo's **cgroup v2** (unified hierarchy, declared stable in Linux 4.5 in 2016) uses a single tree, with a controller enabled per subtree through `cgroup.subtree_control`, a rule that processes live only in leaves, consistent file names, and delegation to unprivileged users. systemd became the owner of the tree on most distributions, and RHEL 9, Fedora (31 onward), Debian 11 and Ubuntu 21.10 use v2 by default. The Rocky guide on migrating to v2 describes how to check and enable it on the Red Hat family [src: rocky-docs 79e5c84365a643a4].

The v2 memory controller offered finer limits than v1. Alongside a hard limit it has a throttle (`memory.high`) and protections (`memory.min`, `memory.low`) [web: docs.kernel.org]. The v1 "soft limit" was replaced by these, and the swap interface changed (`memory.swap.max`, no combined mem+swap limit). Later features include **PSI** (pressure stall information, 2018, Johannes Weiner at Facebook), the group-kill option `memory.oom.group`, and user-space OOM daemons. Facebook's `oomd` (2018) used pressure to kill a victim *before* the kernel's OOM killer, since the kernel only acts when allocation has already failed and the machine may have been thrashing for minutes; its design became `systemd-oomd`, which monitors cgroups with `ManagedOOMSwap=` and `ManagedOOMMemoryPressure=` settings [src: man-pages 313b1482226b50c1]. Others include `earlyoom` (simple, popular on desktops and small servers) and `nohang`. Kubernetes layered its own approach: kubelet eviction by node pressure thresholds before the kernel acts, with memory QoS using `memory.high` on cgroup v2 [src: kubernetes-docs 40e8b6b11cf395e1].

The pattern: **account per group, set limits and protections per group, observe pressure, act early in user space, let the kernel's killer be the last line**.

## Current state

### Seeing a kernel OOM kill

The kernel logs a block beginning with `Out of memory: Killed process 4321 (java) total-vm:... anon-rss:... file-rss:... shmem-rss:... oom_score_adj:0`, preceded by an `invoked oom-killer` line with the allocation's flags and `order`, the memory zone statistics, and a table of tasks with their RSS and score. Find it with `journalctl -k -g 'Out of memory'`, `dmesg -T | grep -i -E 'killed process|oom'`, or `/var/log/messages`. Two variants matter: a **global** OOM (the machine is out; `constraint=CONSTRAINT_NONE`) and a **cgroup** OOM (`constraint=CONSTRAINT_MEMCG`, with the line `Memory cgroup out of memory`, meaning a limit was hit though the host has memory to spare). For services under systemd, `systemctl status` reports `Result: oom-kill`, and the cgroup's `memory.events` file shows counters (`oom`, `oom_kill`, `oom_group_kill`). A killed process leaves no application log entry because it gets SIGKILL, so absence of a shutdown message is itself the clue.

Reading the table answers the diagnosis questions: which process had the biggest `rss` (the victim is not always the culprit); whether shared memory or tmpfs is counted (`shmem-rss`, and `df /dev/shm`); whether swap was off or full (`Free swap`); and which zone was short (`Normal` versus `DMA32`, where fragmentation and high-order allocations, `order:3` or more, can fail even with free memory in total). A slow rise in `vmstat` `si/so` and in `/proc/pressure/memory` usually precedes the event (LNX-307-T02).

### cgroup v2 mechanics

Check the version with `stat -fc %T /sys/fs/cgroup` (`cgroup2fs` means v2) and the available controllers in `cat /sys/fs/cgroup/cgroup.controllers`. On a systemd system each service has a directory under `/sys/fs/cgroup/system.slice/UNIT.service/`, each user session under `user.slice`, and containers under their own subtree. Core files in each group directory:

| File | Meaning |
|---|---|
| `cgroup.procs`, `cgroup.controllers`, `cgroup.subtree_control` | members, available and enabled controllers |
| `memory.current`, `memory.peak`, `memory.stat` | present use, high-water mark, detailed breakdown (anon, file, kernel, slab) |
| `memory.min`, `memory.low` | hard and best-effort protection from reclaim |
| `memory.high` | throttle threshold: above it the group is slowed and forced to reclaim, never killed by this alone |
| `memory.max` | hard limit: when reached and reclaim fails, the OOM killer runs inside the group |
| `memory.swap.max`, `memory.swap.current` | swap limit and use |
| `memory.oom.group` | when 1, the whole group is killed together |
| `memory.events` | counters: `low`, `high`, `max`, `oom`, `oom_kill` |
| `memory.pressure`, `cpu.pressure`, `io.pressure` | PSI for this group |
| `cpu.max`, `cpu.weight`, `cpu.stat` | quota and period (`max 100000`), share (default 100), usage and throttling counts |
| `io.max`, `io.weight`, `io.stat` | per-device bytes and IOPS limits; weights; stats |
| `pids.max`, `pids.current` | process and thread limit |

The semantics are summarised in the kernel's admin guide [web: docs.kernel.org]: `memory.high` throttles, `memory.max` kills, the `min` and `low` values protect. A well-designed service uses all three: `memory.low` as a floor for important services, `memory.high` slightly below the maximum so that a leak slows down and becomes visible in `memory.events` instead of causing a kill, and `memory.max` as the backstop. For the CPU, `cpu.max` of `200000 100000` allows two CPUs' worth per period; hitting it shows up as `nr_throttled` and `throttled_usec` in `cpu.stat`, a common cause of container latency (LNX-310). The io controller requires a block scheduler and, for `io.max`, works on whole devices identified by `major:minor`.

### Front ends: systemd and containers

The systemd resource-control settings map directly to these files [src: man-pages 9489ddb2015d0cb9]: `MemoryMin=`, `MemoryLow=`, `MemoryHigh=`, `MemoryMax=`, `MemorySwapMax=`, `CPUQuota=`, `CPUWeight=`, `IOWeight=`, `IOReadBandwidthMax=`, `IOWriteBandwidthMax=`, `TasksMax=`, and the `OOMPolicy=` and `OOMScoreAdjust=` settings that choose whether a unit stops when one of its processes is OOM-killed (`stop`, `kill`, `continue`). For an experiment without writing a unit:

```bash
systemd-run --scope -p MemoryMax=200M -p MemorySwapMax=0 -p MemoryHigh=150M stress-ng --vm 1 --vm-bytes 400M
systemctl set-property myapp.service MemoryMax=1G CPUQuota=150%      # persistent via drop-in; --runtime for temporary
systemd-cgtop                                                         # top-like view of cgroups
systemd-cgls                                                          # the tree
```

Containers set the same files. Docker's `--memory` writes `memory.max`, `--memory-reservation` the protection, `--cpus` writes `cpu.max`, `--pids-limit` writes `pids.max`. Kubernetes `limits.memory` becomes `memory.max`, and a requests/limits pair determines the QoS class and the `oom_score_adj` of its pods [src: kubernetes-docs 0630f36b300dcf32]. This means an OOM kill of a container is a cgroup OOM at its limit, regardless of free memory on the node.

### User-space early killers

`systemd-oomd` reads PSI and swap use for cgroups where `ManagedOOMMemoryPressure=kill` is set and kills the heaviest descendant cgroup when pressure exceeds `DefaultMemoryPressureLimit` (60% default) for `DefaultMemoryPressureDurationSec` (30 s) [src: man-pages e6b434dee3a3b604]. It is enabled on Fedora and Ubuntu desktops. `earlyoom` kills when free memory and swap fall under percentage thresholds.

The generalised diagnostic pattern: **find the event, find the scope (global or cgroup), find the top consumer from `memory.stat` or the task table, decide between fixing the workload and raising the limit, and then alert on pressure, not on the kill**.

## Assessment: the good, the bad and the ugly

The good: cgroups v2 provide isolation and accounting that make multi-tenant hosts possible, with one consistent interface that systemd, container runtimes and Kubernetes all use. The throttle-before-kill design of `memory.high` turns a hard failure into a graceful degradation. PSI gives a measure of actual harm rather than raw utilisation. `memory.oom.group` avoids half-killed applications with some workers dead. The kernel log entry contains a full account of what happened.

The bad: the kernel killer is a blunt instrument. Its choice reflects size, not value. It acts late, after the system may have been thrashing, which is why interactive hosts can freeze for minutes before the kill. Page cache and `memory.current` include reclaimable file memory, so naive alerts on `memory.current` approaching `memory.max` cause false alarms; `memory.stat` `anon` and the working set are better. Setting `MemoryMax` too tight turns a transient peak into a kill loop under `Restart=always`. Limits are not applied to kernel memory consistently (slab and socket buffers are accounted, but some kernel allocations are not), and tmpfs and shared memory are charged to the creating cgroup in ways that surprise people. Swap behaviour is a recurring debate: with swap disabled, memory pressure escalates faster to kills; with a slow swap device, a system thrashes instead.

The ugly: containers and the Java runtime. A JVM that sizes its heap from host memory rather than the cgroup limit will exceed `memory.max`; modern JVMs (since 10 and 8u191, to verify) read the cgroup limit, but off-heap and native memory still push usage above the heap setting, so containers die with exit code 137 while the heap looks fine. The same applies to Go's runtime before its memory limit setting and to anything that mmaps. cgroup v1 and v2 interfaces differ, and tools or agents written for v1 (older monitoring agents and some Hadoop or JVM versions) silently misreport. Mixing hybrid mode causes confusion. Memory accounting differences between "working set" in Kubernetes and `memory.current` lead to disagreements between dashboards. The OOM score adjustments set by Kubernetes mean that on node-level OOM the kernel prefers burstable and best-effort pods, which matches the QoS design but surprises teams who set no requests.

Mitigations: set requests and limits deliberately; use `memory.high` below `memory.max` to get early warning; alert on `memory.events` increments and PSI (LNX-307-T03); set `oom_score_adj` for critical daemons (sshd, the monitoring agent) so that they are last to go; keep some swap for latency smoothing on general-purpose servers and none on latency-critical containers; use `OOMPolicy=` and `memory.oom.group` for services whose workers must live or die together; and capture a `vmcore` or a heap dump when an OOM is part of a pattern (T06).

## Applications beyond this domain

Hierarchical resource limits with protection and borrowing show up wherever shared capacity is divided: Kubernetes ResourceQuota and LimitRange, Linux traffic control, cloud autoscaling groups, database resource groups (MySQL, Oracle resource manager), and JVM or Go runtime memory limits that use the same throttle-before-kill idea. The pressure-as-signal approach appears in storage (queue depth) and in Android's low memory killer daemon (`lmkd`), which uses PSI to kill background apps. The cgroup accounting design underlies container security boundaries and billing in container clouds, and the same model is used by systemd's user slices to protect desktop sessions from runaway processes. In virtualisation (LNX-308) the balloon driver and host-side cgroup limits on QEMU processes follow the same logic, including the host-side OOM that ends a guest's QEMU process.

## Examples

**Reading a kill.** `journalctl -k -g killed` shows `Out of memory: Killed process 2210 (java) ... anon-rss:3812340kB`, preceded by `oom-kill:constraint=CONSTRAINT_MEMCG,... oom_memcg=/system.slice/shop.service`. The scope is the unit's cgroup, so the host had free memory. `systemctl show shop -p MemoryMax,MemoryCurrent` gives MemoryMax=4G and the heap setting `-Xmx3g` plus metaspace, threads and direct buffers exceed 4G. Fix: raise the limit to 5G, cap direct memory and add `MemoryHigh=4500M` so the next growth is visible as `high` events.

**A safe experiment.** `systemd-run --scope -p MemoryMax=100M -p MemorySwapMax=0 python3 -c 'x=bytearray(300*1024*1024); print(len(x))'` allocates beyond the limit and is killed; `journalctl -k -n 20` shows the cgroup OOM and the scope's `memory.events` shows `oom_kill 1`. The lab for this topic does the analysis from a recorded log and writes the unit settings.

**Throttling instead of killing.** With `MemoryHigh=80M` and `MemoryMax=120M`, the same program slows down as it approaches 80M, `memory.events` `high` counters rise, and the process survives longer, which is the behaviour a service should have.

**A failing example.** A team set `MemoryMax=512M` on a database in a unit with `Restart=always`. Under a batch import the kernel killed it, systemd restarted it, the import resumed, and it was killed again: a loop that looked like instability to the application owners and a clean restart to systemd. Metrics showed memory never above 512M because it was killed at that line. The cure was understanding the working-set need (about 1.5G), raising the limit, adding `memory.high` and alerting on `oom_kill` (T03).

**cgroup CPU throttling.** A latency-sensitive service in a container with `cpus: 1` had 99th-percentile spikes every 100 ms. `cpu.stat` showed `nr_throttled` rising: bursts above the quota paused all its threads until the next period. Raising the quota or using `cpu.weight` shares without a quota solved it.

## Related problems and ideas

Related approaches include hard-partitioned memory with hugepages and NUMA pinning (LNX-308, VIRT pathway), memory ballooning and free page reporting in guests, `zswap` and `zram` for compressed swap that help under pressure, transparent hugepage tuning (khugepaged stalls), and DAMON for access-pattern-based reclaim. Proposals for a more intelligent kernel OOM policy include BPF-programmable OOM handlers (discussed on the mailing lists; to verify status), per-cgroup OOM priorities and cgroup-aware victim selection (`memory.oom.group` was the first step). For CPU there is the `cpu.max.burst` setting and for I/O the `io.cost` model, both of which target the same fairness problem. Application-level approaches (arena limits, backpressure and load shedding) avoid the kill altogether. Kubernetes memory QoS, swap support (alpha in 1.22, beta in 1.28 as limited swap; to verify current state) and in-place pod resizing change how limits are managed.

## Active research

Open problems include predicting memory exhaustion from pressure and trend data early enough to act, deciding which workload to sacrifice using value rather than size, and improving accounting accuracy for shared pages, kernel memory and page cache across cgroups. The kernel community is working on BPF hooks for OOM decisions, better memory.reclaim proactive reclaim interfaces (`memory.reclaim` file), and tiered memory with CXL, where limits must apply per tier. Google and Meta have published results on proactive reclaim and swap offload using PSI-driven agents (Meta's Senpai, Google's zswap-based fleet management; to verify details). Student and industry research also compares reactive OOM daemons for desktops and servers by measuring recovery time.

## Future direction

Expect cgroup v2 to be the only mode in new distributions, with v1 removed or deprecated (systemd announced removal plans for v1 support; to verify the release), tighter defaults in desktop and server editions that enable `systemd-oomd`, and pressure-based autoscaling in orchestrators. Proactive reclaim agents and CXL memory tiers will change how `memory.high` is used. The cluster scheduler and the node will cooperate more on QoS, and OOM events will be exported as first-class metrics. For operators, the practical future is simple: always know your limits, alert on pressure and `oom_kill` events, and rehearse the diagnosis path.
