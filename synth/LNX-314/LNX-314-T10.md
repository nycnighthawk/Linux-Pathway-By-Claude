# Threat detection in production: from signals to a response you can run

## Define the problem

The earlier slices of this course add controls and sensors: hardened nodes, minimal RBAC, admission policy, signed images, encrypted Secrets, audit logs, Falco, sandboxes and segmentation. In production those pieces produce a continuous stream of events, and what matters then is the human and organisational system around them. Someone must decide which signals deserve attention, connect events from different sources into a story, decide what to do about a suspected compromise of a workload that may be one of hundreds of identical replicas, preserve evidence from containers that vanish when deleted, and recover without trusting anything the attacker touched. Few teams rehearse any of that, and the first real incident is also the first time the runbook is tested.

The problem has features that make it different from traditional host monitoring. Workloads are ephemeral: the container that did something suspicious may be gone before the alert is read, and with it the file system, the memory and the process list. Identity is layered: a node, a Pod, a service account, a cloud role and a human each appear in different logs under different names. Scale means that a detection which fires on one container in a thousand matters, and a detection which fires on one thousand containers needs triage tooling, not eyes. And the response actions are different: killing a Pod is easy and may destroy evidence, while cordoning a node, revoking a service account token or a cloud role, isolating a namespace with a network policy and taking a checkpoint are cluster-specific operations that need permissions prepared in advance.

This slice is the course's closing synthesis and is deliberately practical and light on new mechanisms. It covers the structure of a detection programme (threat model, coverage map, detection content, triage, response), the most useful detection scenarios for clusters, cloud-provider and managed detection services, evidence preservation and containment steps for a suspected compromised Pod and node, exercises to test detection, and the measures that tell a team whether it is getting better. It is delivered as an operations guide with checks, since its skills are procedural.

## History and approaches

Security operations grew up around networks and servers. The model of a security operations centre (SOC) built on a SIEM collecting logs from firewalls, intrusion detection sensors, servers and applications, with analysts triaging alerts and following playbooks, dates from the early 2000s. It assumed relatively stable assets, central logging and an attacker who had to cross a perimeter. Endpoint detection and response (EDR) products extended visibility onto each machine from about 2013. Cloud adoption added new log sources (cloud audit trails and flow logs) and new detection services run by the providers.

Containers and orchestration stressed each of those assumptions. Early container security tooling concentrated on image scanning and compliance, because those were tractable, with runtime visibility trailing. The NIST application container security guide (SP 800-190, 2017) listed the risk areas still used today (image, registry, orchestrator, container, host) and recommended runtime monitoring for container behaviour and network activity, noting that traditional tools did not see inside containers or understand their ephemeral nature [src: nist-sp800-guides f844adcf658844a8] [src: nist-sp800-guides a65ce128cf64bf06]. The guide also gives planning advice on containment, such as treating containers as replaceable and rebuilding from known-good images rather than repairing in place [src: nist-sp800-guides c1e370b99a0abc1c] [src: nist-sp800-guides b5ec34589cc2e260].

A second thread was the shared vocabulary of attacker behaviour. MITRE's ATT&CK framework for enterprise attacks, started in 2013 and extended with a containers matrix and a cloud matrix, gave defenders a list of tactics and techniques with observed examples. Microsoft's threat matrix for Kubernetes (2020) and its successors mapped container-specific techniques such as exposed dashboards, exec into container, writable hostPath mounts, cluster-admin binding, access to the cloud metadata endpoint and cryptomining deployments to the same stages. Detection engineers use these as a coverage checklist: for each technique, is there a rule, and has it been tested.

Third, the detection content itself became shareable. Sigma rules describe log-based detections in a vendor-neutral YAML format that can be translated for many SIEMs; Falco's rules and plug-ins are maintained in public repositories; cloud providers publish detection catalogues. The shift from product-defined alerts to detection as code, rules in a repository, reviewed, tested against recorded data and deployed through a pipeline, mirrors software engineering practice.

Fourth, response had to be re-thought. In a conventional incident, the analyst isolates a host and images its disk. For a Pod, isolation means a network policy applied by label, which an attacker with API permissions might remove, or cordoning and tainting the node, or deleting the workload's permission to talk to the cloud. Evidence capture became a kubelet feature: a checkpoint API, built on CRIU, introduced as alpha in 1.25 and advanced since (stability to verify), saves a running container's state to an archive for later analysis, while tools like kubectl debug with ephemeral containers allow live inspection of a Pod without changing its image. Guidance from the cloud providers and the Kubernetes community converged on a pattern: label the suspect Pod so that a quarantine network policy isolates it, remove it from its Service and its controller (so it is not replaced and not restarted), preserve its data, and only then terminate [web: cloud.google.com].

Public incident reports from the last several years show what real attacks look like in clusters: exposed management interfaces leading to cryptomining workloads, leaked credentials used from outside to create privileged Pods, supply chain compromise through a malicious image or a CI token, and cloud metadata theft followed by use of node credentials. They are usually noisy in at least one place. The Kubernetes security checklist stresses logging and auditing as part of baseline hygiene, and notes the need to keep logs outside the cluster [src: kubernetes-docs 3033f3f0a859eb6e].

The pattern that emerged is a detection programme as a living engineering practice: threat-informed coverage, detection as code, rehearsed response with prepared access, and measured outcomes.

## Current state

**A threat model first.** Start from the assets (customer data in the database, the CI credentials, the cloud account, the cluster itself) and the realistic adversaries (external attackers exploiting an exposed service, a malicious or compromised insider, a supply chain actor). List the ways each could reach the assets in this cluster and rank them by likelihood and impact. The result is a short list of scenarios to detect, usually fewer than twenty. A programme that begins with a catalogue of every available rule drowns; one that begins with five scenarios and covers them well is useful within a month.

**Scenario-led detection.** A typical starter set, each with its data source: a shell or a downloaded executable in a running container (node sensor); an outbound connection to a mining pool or a known bad address (flow logs and node sensor); a new privileged Pod, hostPath mount or host-network Pod outside the platform namespace (audit log); a new cluster-admin binding or a change to RBAC outside the pipeline's identity (audit log); use of a service account token from a source address outside the cluster (audit log with source IP); access to the cloud metadata address from a Pod (flow logs, node sensor); a cloud API call by a node role that a node should never make (cloud audit trail); exec into a production Pod by someone not on call (audit log); image pulled from an unexpected registry (admission log, node log); and a change to admission webhook configurations (audit log). Each rule is documented with what it means, what normal looks like, how to check whether it is a false positive, and what to do next.

**Cloud and managed services.** Providers offer threat detection that watches their own control-plane telemetry: AWS GuardDuty has EKS audit log and runtime monitoring features, Google Cloud's Security Command Center has container threat detection, and Microsoft Defender for Containers covers AKS and others. They add provider-side knowledge (reputation of addresses, known malicious images, behavioural models over many customers) for a fee, and are a sensible base layer; they do not replace rules for your own business logic or your own policies. Check what each covers, what log retention it implies, and how findings reach your triage queue.

**Correlation and triage.** The unit of work is an incident, not an alert. Correlate by identity (the service account, the Pod, the node, the source IP, the cloud principal) and by time. A useful starting point is a timeline for a suspect Pod: image and digest, the deploying identity, the node, the audit events on its service account, the node sensor events with its container ID, and the flows it opened. Because identity differs across logs, enrichment that maps container ID to Pod, Pod to owner and owner to team saves most of the time. Triage notes should record the verdict and reason so tuning has data.

**Containment.** A prepared containment ladder, from least to most disruptive: add a quarantine label to the Pod so a pre-installed deny-all network policy selects it (the policy exists beforehand; the response is to label); detach the Pod from its Service by changing its labels so it is not serving traffic and the controller creates a replacement; revoke or rotate the service account's credentials, and the cloud role, if there is any chance it was exposed; cordon and, if node compromise is suspected, drain and isolate the node; and rotate cluster-level secrets and certificates if the control plane may be affected. Each rung needs a named owner and tested permissions. Deleting the Pod is a last step after evidence capture, because the controller will restart it from the same, possibly vulnerable image.

**Evidence preservation.** Capture, in order of volatility: the Pod's spec and events, the node and container logs, the audit log excerpt, the container's process list and network connections (through an ephemeral debug container sharing the process namespace, or the node), the filesystem diff of the writable layer (via the runtime on the node), a memory image or a checkpoint if the cluster supports it, and a snapshot of the node's volume if the node is suspect. Write the artefacts to a store the compromised workload cannot reach, with hashes and a record of who collected what and when. Capture is a skill to practise because some steps require node access that normal engineers do not have.

**Recovery.** Rebuild from known-good sources: rebuild and redeploy the image from the verified pipeline, rotate every credential the workload could read (mounted Secrets, environment variables, cloud roles, tokens), recreate nodes from the image and not repair them, and verify through the audit log that persistence mechanisms created by the attacker (new RBAC bindings, CronJobs, DaemonSets, webhooks, static Pod manifests) are removed. Review how the attacker got in and close the entry point before restoring service.

**Exercises.** Detections that were never triggered by a real event are guesses. Run controlled emulation: Atomic Red Team and Stratus Red Team replay techniques in a test environment, Kubernetes-specific tools such as kube-hunter and peirates-style exercises, and purple team sessions where red and blue sides work together and every missed detection becomes a ticket. Game days that practise the containment ladder with a deliberately compromised test workload reveal missing permissions and stale runbooks.

**Measuring.** Useful measures are coverage (the share of the prioritised techniques with a tested detection), time to detect and time to contain in exercises and real events, the false-positive rate per rule and the share of alerts that lead to action, and the age of unresolved findings. Track them as trends and review the lowest-performing rules monthly.

**Generalised pattern.** Detection is an engineering loop: model the threat, write and test the detection, run it, measure its quality, rehearse the response, and feed lessons back into prevention.

## Assessment: the good, the bad and the ugly

The good: scenario-led detection on top of audit logs and a node sensor catches the majority of the common attack patterns seen in public reports. Containment by labelling is fast and reversible when prepared. Cloud detection services reduce the work of building a baseline. Exercises are cheap in a test cluster and reveal problems quickly.

The bad: detection cannot be complete, and attackers who understand the environment avoid the known signatures. Alert fatigue and staffing limits are the actual constraint in most teams, not tooling. Managed service findings vary in quality and their logic is hidden. Evidence preservation is tedious and often skipped under pressure, leaving an incident report that says "we deleted the Pod". Ephemeral workloads with short lives produce alerts about things that no longer exist. Response permissions are either too broad (everyone can delete everything) or too narrow (nobody can reach the node at three in the morning).

The ugly: the attacker may live where the sensors do not look, or may disable them. Control plane compromise in a managed service is invisible except through the provider's logs, which arrive late. Insiders and compromised CI systems act through legitimate paths and look normal. A cluster full of long-standing exceptions makes any anomaly hard to see. Data protection law and customer contracts impose notification deadlines that start when an incident is suspected, so the incident process must include legal and communication roles from the first hour. And teams frequently learn that their audit logs, the source of truth for an investigation, were retained for seven days, never exported, or did not cover the resource that mattered.

## Applications beyond this domain

The same programme structure fits any production environment: threat model, scenario list, detection as code, rehearsed containment, evidence handling and metrics are the standard model for SOC and incident response work in enterprise networks, cloud accounts and SaaS applications. Site reliability engineering practices such as blameless post-incident reviews, game days and error budgets carry directly over, and many teams run security and reliability incidents through the same tooling. Evidence handling follows digital forensics principles (order of volatility, chain of custody, hashing) that apply to any computing system. Deception technology, such as canary tokens and honeypot services, is used in networks and cloud accounts as well as clusters and gives high-confidence alerts with little tuning.

## Examples

**A cryptomining incident.** An alert from the node sensor reports a process started from a file in /tmp in a web container, followed by a connection to a mining pool port. The responder labels the Pod to apply the quarantine policy; the Service stops sending traffic to it, and the Deployment starts a replacement. She captures the Pod's events, logs and the writable layer, takes a checkpoint, and then scales the compromised ReplicaSet to zero. Audit queries show the Pod's service account made no API calls beyond its normal ones, so the incident is contained to the workload. The root cause is an unpatched library in the image, rebuilt and redeployed after the attack path is confirmed, and every Secret the Pod mounted is rotated.

**Token theft.** The audit log shows a CI service account listing Secrets cluster-wide from an address outside the company's ranges, then creating a privileged DaemonSet. The responder revokes the account's token by deleting and recreating the service account, deletes the DaemonSet after capturing its spec, checks nodes for the Pod's containers, rotates credentials the DaemonSet could read, and reviews the CI system for the leak.

**A failing example.** A team has many detections but no tested containment. When a real alert arrives, the on-call engineer deletes the Pod immediately, the controller recreates it with the same image, the attacker's persistence in a mounted volume survives, and the evidence of the initial access is gone. The post-incident review adds a prepared quarantine policy, a runbook with the capture steps and a game day every quarter.

## Related problems and ideas

Neighbouring problems: vulnerability management and patching (preventing the entry point), secrets management after an incident, backup and disaster recovery for the cluster, and legal and communications processes for breach notification. Alternative approaches to detection include anomaly detection from baselines of each workload's behaviour, deception and canary resources, network detection through flow analysis, and immutable infrastructure policies where any change to a running container is itself an alert. Newer ideas include automated response playbooks driven by high-confidence detections (Falco Talon, SOAR integrations), attack path analysis tools that combine RBAC, network and cloud IAM graphs to show which footholds lead to which assets, and AI-assisted triage that summarises related events, which is promising and unproven for accuracy.

## Active research

Research and open projects cover behavioural detection for container workloads (system call and network baselines), tamper-resistant sensors and logs, forensic readiness features in Kubernetes (the checkpoint and restore work), and shared benchmarks that score detection coverage against emulated attacks. There is active study of attacker behaviour in real cluster compromises using honeypot clusters run by researchers, which provides data on the speed of discovery and typical tooling. Open questions include how to evaluate detection quality without exposing environment details, how to detect compromise of managed control planes, and how to trade cost against retention for high-volume event streams.

## Future direction

Expect cloud and cluster vendors to bundle more detection and response by default, detection-as-code pipelines with replay testing to become common, and richer forensic primitives (checkpointing, node snapshots on demand) to be available through standard APIs. Regulation will tighten requirements for incident reporting and logging in several regions (specific rules and deadlines: to verify for the jurisdictions that apply). The practical advice is stable: a few well-tested scenarios, logs kept outside the cluster for as long as the law and the threat model require, response permissions prepared in advance, and regular rehearsal.
