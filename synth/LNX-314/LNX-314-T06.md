# Software supply chain security: signatures, SBOMs and admission checks

## Define the problem

A container image is the end of a long chain. Source code written by the team and by thousands of strangers is compiled with tools the team did not write, combined with base images and system packages from distributions, built on machines run by a CI service, pushed to a registry, pulled by a node, and run. Each link can be attacked, and an attacker who controls any one of them runs code in production without ever touching the application's own source. The cluster, at the end, sees only a name and a tag.

Two questions follow. First, where did this artefact come from, and was it altered on the way: a question of identity, integrity and provenance. Second, what is inside it, so that when a new vulnerability is announced in a library, the team can list every image that includes it within minutes and not days: a question of inventory. The tools for the first are digital signatures and attestations; for the second, a software bill of materials (SBOM) and vulnerability matching. Neither is useful if it only exists in a pipeline report. The cluster must be able to check a signature and an attestation at the moment of admission and refuse an image that fails policy, otherwise the signature is decoration.

The problem also has a practical difficulty that earlier code-signing efforts hit: key management. A signing key is a long-lived secret, which someone must protect, rotate, revoke and distribute to every verifier. Most open source maintainers and many internal teams cannot do that well, so signatures were rarely produced and rarely checked. A workable solution needs signing to be cheap and verification to be policy-driven. This slice covers the threat model and the main attacks, image digests and why tags are not identity, Sigstore and cosign signing (key-based and keyless), attestations and in-toto, SBOM formats and generation, the SLSA framework, and enforcement at admission with Kyverno, policy-controller and similar tools. Vulnerability scanning is treated as the consumer of an SBOM, not as its own subject.

## History and approaches

Supply chain attacks long predate containers. Package managers have been abused through typosquatting (names one keystroke from popular ones), account takeover of maintainers, and malicious updates, and the incident list is a catalogue of different links: the event-stream package in 2018, where a new maintainer added a payload targeting a cryptocurrency wallet; the SolarWinds build system compromise disclosed in December 2020, which inserted a backdoor into signed updates; the Codecov uploader script modification in 2021; the Log4Shell vulnerability in December 2021, which was not an attack but showed how few organisations knew where Log4j ran; and the xz-utils backdoor found in March 2024 after a multi-year social engineering campaign against a maintainer [web: openssf.org]. SolarWinds mattered for the design of everything that followed: the artefact was correctly signed, so signature checking alone would have passed, and the problem was an untrusted build environment.

Early container integrity relied on registry access control and on digests. A tag such as app:1.4 is a mutable pointer; whoever can push to the repository can move it. A digest, the SHA-256 of the image manifest, names the content and cannot change without the name changing. Referring to images by digest gives integrity relative to a trusted reference, but not any statement about where the content came from. Docker Content Trust, based on the Notary project and The Update Framework (TUF), added signatures to image tags; it required running a separate server and managing root keys and saw little adoption. The Red Hat family took a different route with GPG-based simple signing, where signature files are stored beside the registry and verified by the container tooling on pull according to a policy file [src: rhel-10-docs 9b6bac4e19e12abb].

Sigstore, an open source project announced in 2021 under the Linux Foundation, changed the economics. Its premise is that signing should need no long-lived keys. The components are cosign, the client that signs and verifies artefacts and stores the signature as an OCI object next to the image; Fulcio, a certificate authority that issues a short-lived certificate (valid for minutes) bound to an identity proved through an OpenID Connect login, for example a GitHub Actions workflow identity or a person's email; and Rekor, a public append-only transparency log that records the signature, so that a verifier can check that a signature was made while the certificate was valid even after it expires. This is "keyless" signing. A verifier no longer needs a key: it needs a policy that names the expected identity and issuer, such as the release workflow of one named repository reached through one named OIDC issuer, and checks the certificate chain, the log entry and the signature [src: kubernetes-docs f5b7581d47ea20ec]. The Kubernetes project itself signs its release images and verifies them in this way, and documents the commands for users.

In parallel, the attestation idea matured. Signing says who built or approved something; an attestation is a signed statement about an artefact, with a typed predicate: that it was built by a given system from a given source revision (provenance), that it contains a given list of components (an SBOM), that it passed a vulnerability scan or a test suite. The in-toto project defined the statement format and the DSSE envelope used to sign it. Cosign can attach attestations to images, and Docker's build tooling now generates provenance and SBOM attestations at build time and stores them with the image index [src: docker-docs 4abb0fc0b13a896e] [src: docker-docs 6b0f5cdedf5e0be8].

SBOM formats came from two communities. SPDX, from the Linux Foundation, began as a licence compliance format and is now an ISO standard (ISO/IEC 5962); CycloneDX, from OWASP, began for security use with vulnerability and dependency graph support, and became an Ecma standard. Tools to produce them (Syft, Trivy, the Docker build integration, language-specific generators) work by scanning an image's file system and package databases, or by observing a build. Government pressure accelerated adoption: the United States executive order on cybersecurity in May 2021 set out requirements for software sold to federal agencies, including SBOMs, and similar rules are appearing in the European Union through the Cyber Resilience Act [web: nist.gov].

SLSA (Supply-chain Levels for Software Artifacts, pronounced "salsa"), proposed by Google and moved to the OpenSSF, offers a graded checklist. Version 1.0 of the build track defines levels by what the build provides: level 1, provenance exists; level 2, the provenance is generated by a hosted build service and signed; level 3, the build runs in an isolated, hardened environment where the build steps cannot forge the provenance. The point of the levels is to name the specific attack classes each defends against and give teams a ladder.

The pattern that emerged is end to end: sign at build with an identity tied to the pipeline, attach provenance and SBOM as attestations, store everything beside the image by digest, and verify at admission against a policy that names the expected identities.

## Current state

**Identity of an image.** The unit of trust is the digest. A tag may be used as a convenience in manifests, but a policy engine or a mutating policy should resolve it to a digest at admission or in CI so that the value that was verified is the value that runs. Image references that differ in tag but share a digest are the same content; references with the same tag but different digests are different.

**Signing with cosign.** In keyless mode, running cosign sign against an image digest from a CI job that has an OIDC token makes the tool request a certificate from Fulcio for that identity, sign the image's digest, upload the signature to the registry as an artefact with a tag derived from the digest (or as an OCI referrer in newer layouts) and record the signature in Rekor. In key mode, a key pair is generated or held in a cloud KMS, an HSM, or a hardware token, and the signature is verified with the public key. Key mode is simpler for air-gapped environments and avoids dependency on public Fulcio and Rekor, at the cost of key management. A private Sigstore stack (own Fulcio and Rekor) is possible for organisations that cannot use the public instances.

**Verification.** A verifier gets the image digest, finds the signatures stored beside it, checks them against a trust root (Sigstore's public root distributed via TUF, or the organisation's own keys) and applies the identity policy. For keyless signatures the policy has two required fields: the certificate identity (a subject string or a pattern, for example the exact URL of a release workflow at a ref) and the issuer (the OIDC provider). Policies that only check "some valid Sigstore signature exists" are worthless, because anyone can obtain a valid certificate for their own identity.

**Attestations and SBOM.** Cosign attest wraps a JSON predicate in an in-toto statement for the image digest, signs it and stores it. A verifier retrieves it with a predicate type and can run policy over its content. For SBOMs the policy might require that no component appears in a banned list or that every component has a licence from an allowed list; for provenance, that the builder identity is the organisation's builder and the source repository matches the expected one. BuildKit can emit these attestations during the build with flags, without a separate step, stored as extra manifests in the image index [src: docker-docs 4abb0fc0b13a896e].

**SBOM generation.** Two approaches differ in what they see. A scan of the finished image sees what is present: operating system packages from package manager databases, language packages from lock files and manifests, and sometimes binaries by signature. A build-time generator sees the dependency resolution as it happens, and so can include build tools and detect vendored or statically linked code more reliably. Neither is complete: statically linked Go or Rust binaries without embedded build information, copied binaries, and vendored C sources escape file-scan detection. An SBOM is an inventory with known error, not a proof. Its main use is matching: feed it to a vulnerability scanner and to a store that can list which images contain a given package at a given version.

**Reproducible and minimal builds.** Reproducible builds, where building the same source twice produces bit-identical output, allow independent parties to verify that a published binary corresponds to its source; Red Hat and others describe the work needed for container images, such as fixed timestamps and normalised file ordering [src: rhel-10-docs 744ecf44350178de]. Minimal base images (distroless, scratch, Chainguard-style images) shrink the SBOM and the vulnerability surface. Pinning base images by digest with an automatic updater lets teams review and test updates.

**Admission-time checks.** A policy engine receives each Pod creation, resolves image references, fetches signatures and attestations from the registry, verifies them against the configured trust policy, and allows or denies. Kyverno's verifyImages rule supports keyless identity matching, key-based verification, attestation checks with conditions over the predicate, and mutation of the Pod's image to the verified digest. The Sigstore policy-controller defines a ClusterImagePolicy resource with glob patterns for image names, authorities (keys or keyless identities) and optional attestation policies in CUE or Rego; it is enabled by namespace label. Others include Ratify (for Notation and cosign signatures, used with Gatekeeper), Connaisseur and cloud-specific services such as binary authorization on Google Cloud. All of them check at admission, so the earlier points about admission blind spots apply: running Pods are not re-checked, static Pods are unseen, and the verifier needs registry reachability [src: kubernetes-docs 435da3d7214243dd].

**Generalised pattern.** Provenance is a chain of signed statements, each bound to the digest it describes and to the identity that made it; a verifier holds a policy about identities and expected statements, not a list of keys; the decision happens at the last moment before use.

## Assessment: the good, the bad and the ugly

The good: keyless signing removed the biggest adoption barrier, since no one has to protect a key, and the transparency log gives public evidence of what was signed and when. Digest pinning and signature policies close the mutable-tag hole. Attestations make requirements checkable and move conversations from claims in documents to evidence in the registry. Docker and BuildKit generating SBOMs and provenance by default shifts effort from teams to tooling.

The bad: a signature proves identity, not quality. A signed image can contain malware if the signing identity is compromised or malicious; the SolarWinds case is the standing lesson. Verification adds a dependency on registries and, for keyless, on external services for the trust root, with availability and privacy consequences (the log is public, so identities and image names are visible). SBOMs vary in quality, and formats and tools disagree on package identifiers, which makes matching imprecise, with false positives and false negatives. Policy is hard to write correctly: a certificate identity pattern that is too loose lets in another repository's workflow, and one that is too strict breaks a release. Teams get signing working on one pipeline and leave every other image path (third-party charts, base images, operators) unchecked.

The ugly: the unsigned long tail. Most images in a real cluster come from upstream projects that do not sign, or sign with varying schemes, so an enforce-everything policy either blocks needed software or needs a growing exception list that defeats it. Transitive trust is another sore point: you can verify the image you build, but your base image and its packages were built by someone else, and a vulnerability scanner reading an SBOM tells you what is present, not what is exploitable. The vulnerability reporting stream is noisy; VEX (vulnerability exploitability exchange) statements, which say a known vulnerability does not affect a given product, are a response but are early in adoption. Running unverified admission in audit mode forever is common. Registry compromise matters less than before for integrity (digests and signatures defend it) but is still a route for denial of service, and attackers can sign their own malicious image with their own identity, so the policy must name allowed identities rather than accepting any signer.

## Applications beyond this domain

The same chain-of-custody logic is used in package ecosystems: npm and PyPI now support trusted publishing and provenance attestations tied to the CI identity, and Maven Central requires signatures. Linux distributions have long signed packages and repository metadata (GPG in apt and rpm), and secure boot extends a chain of signatures from firmware to the kernel and modules. Certificate Transparency, which Rekor is modelled on, applies the append-only log approach to web certificates. Firmware, mobile app stores and automotive software update systems use TUF-style metadata with threshold signatures and key rollover. The SBOM concept comes from manufacturing's bill of materials and appears in hardware (CBOM for cryptography, AI bills of materials for models and datasets). Reproducible builds are central to Debian, Arch Linux and Bitcoin Core, which use independent rebuilds to detect compromised build hosts.

## Examples

**Signing and verifying in CI.** A release workflow builds an image, pushes it, records the digest, and runs cosign sign on the digest, with the job's OIDC identity. A second job attaches the SBOM generated by the build as an attestation. In the cluster, a Kyverno policy applies to production namespaces: images from the company registry must carry a cosign signature whose certificate identity matches the repository's release workflow on the main branch, issued by GitHub's OIDC issuer, and must have an SBOM attestation. The policy mutates the tag to the verified digest.

**Incident response with an SBOM.** A new critical vulnerability appears in a compression library. The team queries the SBOM store for the package and finds eleven images, three of which run in production. Without SBOMs the same search would have meant scanning every image in the registry and reading build files. The remediation list is ready within the hour, though two images that vendor the library in source form were not on it, and were found only later when the application owners remembered.

**A failing example.** A policy requires "any valid cosign signature" on images in production. An attacker who has obtained write access to the registry pushes a trojaned image with the same tag, signs it with their own email via the public Sigstore service, and the policy passes it. The fix is to constrain the certificate identity and issuer to the organisation's pipeline, to deploy by digest, and to remove registry write access from anything but the release identity.

## Related problems and ideas

Neighbouring problems: base image selection and update cadence, dependency pinning and review (lock files, Dependabot-style updates and their review burden), CI hardening (ephemeral runners, least-privilege tokens, pinned actions by commit), secrets in build logs, and protection of the source repository (branch protection, signed commits, required reviews). Alternatives to signature-based trust: build everything from source in-house with hermetic builds (Bazel, Nix, Guix), run a curated internal mirror that admits only reviewed upstream artefacts, and use a software composition analysis service that blocks risky packages at download time. Newer ideas: the Notary Project's Notation with X.509 trust stores for organisations that prefer a conventional PKI; VEX documents to prune scanner noise; reachability analysis that checks whether vulnerable code is actually called; and transparency logs for builds, in which independent parties rebuild and publish matching hashes.

## Active research

Open work includes making SLSA provenance verification routine (policy languages and library support to check the builder identity and source), safe handling of the long tail of unsigned third-party software, and the quality of SBOMs, with research measuring how much real SBOMs agree across tools and how often they miss components. Reproducible build efforts continue across ecosystems, and some work aims at bootstrappable builds that start from a tiny auditable seed. Sigstore development covers trust root distribution (TUF), monitors that watch the transparency log for unexpected signatures of an organisation's identities, and support for non-OIDC identities. Researchers also study social attacks on maintainers, as in the xz case, and how metadata such as maintainer activity could flag risk. Open questions: how consumers should value attestations from builders they cannot audit, how to revoke trust in an identity after the fact, and how to keep verification available during registry or Sigstore outages without failing open.

## Future direction

Expect signature and provenance checks to become defaults in registries, base image catalogues and orchestrators, and policy libraries for common patterns to replace hand-written rules. Regulation will push SBOM and provenance from optional to required for vendors in several markets (the EU Cyber Resilience Act and US federal procurement rules are the main drivers; exact dates and scope: to verify). Language ecosystems will make provenance for packages normal, narrowing the unsigned tail. Referrers-based storage of signatures and attestations in registries will replace tag conventions. Which version of SLSA, SPDX and CycloneDX is current, and Sigstore component status and service-level commitments for the public instance: to verify before relying on them in an environment.
