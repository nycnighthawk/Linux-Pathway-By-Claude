# Encrypting Secrets at rest in Kubernetes

## Define the problem

Every Kubernetes object lives in etcd, and by default Secret objects are stored there with nothing more than base64 encoding, which is a text format and not a protection. Whoever can read the etcd data directory, a backup of it, a snapshot, or the etcd network port can read every Secret in the cluster: service account tokens, image pull credentials, database passwords, TLS private keys. A stolen disk image, an exposed backup bucket, a misconfigured etcd with no client authentication, or an administrator with access to the control plane machine but no business reading application secrets each give the same result.

Encryption at rest is the control that makes that data useless to someone who sees the storage but not the keys. Doing it well raises more questions than the headline suggests. Which resources are encrypted: only Secrets, or also ConfigMaps and custom resources that carry credentials? Which cipher and mode, and what happens when the key leaks or ages? Where does the key live: in a file on the same machine as the data, which defeats most of the purpose, or in a key management service that the API server calls? What do existing data and backups look like after a key change? How do you check that encryption is real, not merely configured? And what does it not protect against, because the API server decrypts on read, so anyone with API access to Secrets still sees plain text?

This slice covers the API server's encryption configuration, the available providers (identity, AES-CBC, AES-GCM, secretbox, and KMS v2), the envelope scheme that KMS providers implement, rotation of keys, verification, and the boundary of the protection. Distribution of secrets into Pods, external secret stores and CSI drivers are touched on as the alternative architecture. Etcd's own transport security belongs to the cluster hardening slice.

## History and approaches

In the first releases there was no encryption at rest at all. The common advice was to protect etcd with network and file permissions, to restrict who could read Secrets with RBAC, and to encrypt the volume under the control plane nodes. Disk encryption addresses the stolen-disk case but not the backup or snapshot case or an attacker with a shell on the node, because the volume is unlocked while the machine runs. Early users who needed more used external stores directly, with Vault the best known, and fetched credentials at Pod start rather than storing them in the cluster.

Encryption at rest arrived as an API server feature (alpha in 1.7, stable much later) configured by a file given to the server with a flag. The file lists, per set of resources, an ordered list of providers. Writes always go through whichever provider is listed first. For reads, the API server examines a prefix stored in front of each value, written in the form k8s:enc:<provider>:v1:<key name>:, and picks the matching provider and key, falling back to identity (no encryption) for values with no prefix. This design makes migration possible, since old plain values stay readable while new values are written encrypted, and it also defines the standard rotation procedure [src: kubernetes-docs e7daeb9ab914d710].

The provider set evolved. Identity means "no encryption" and exists to read old data and to turn encryption off. AES-CBC with PKCS#7 padding and AES-GCM were the first real ciphers, with keys held in the configuration file. The documentation records a reason to be cautious about AES-GCM: the nonce is random and a key can be safely used for only a limited number of writes before collision becomes likely, so it requires rotating keys frequently, whereas CBC has no such issue though it provides no authentication by itself [src: kubernetes-docs 165d4d5f8bd40e47]. Secretbox, built on XSalsa20 and Poly1305 from NaCl, offers authenticated encryption without the nonce problem and became the recommended choice among local-key providers. All three share a weakness: the key is in a file on the control plane host, usually next to the data it protects, so a compromise of the host or a copy of both files undoes the protection.

KMS providers address that. In the envelope scheme, the API server generates a data encryption key (DEK) for each write or for a period, encrypts the object with it, and asks an external key management service to wrap the DEK with a key encryption key (KEK) that never leaves the service. The wrapped DEK is stored with the object. A plug-in process on the control plane node speaks gRPC to the API server and relays to the cloud or hardware KMS. The first version of the API (KMS v1) called out to the plug-in for every operation, generating a new DEK per write, which created load on the KMS and latency on every Secret read. KMS v2 changed this: the plug-in reports a key identifier and status, the API server derives a local DEK cache keyed by that identifier, and the number of KMS calls fell from one per operation to a handful per rotation. V2 went stable in the 1.29 release and v1 was deprecated afterwards [src: kubernetes-docs d394e10ef3c7d281] [src: kubernetes-docs 58266907a4648f6e]. Managed services followed: EKS envelope encryption with AWS KMS, GKE application-layer secrets encryption with Cloud KMS, and AKS with Key Vault. Vendor-neutral plug-ins exist for Vault and for hardware security modules through PKCS#11.

Two practical improvements made operation easier. The encryption configuration can be reloaded without restarting the API server, with the server watching the file [src: kubernetes-docs 57672580a7348bec]. And the storage version migration feature, with a controller and an API, can rewrite all objects of a resource so that every value is re-encrypted with the current key, replacing the older advice to run a get-and-replace over all Secrets in a shell loop [src: kubernetes-docs d5b750f44b2db600].

The emerging pattern: use a KMS v2 provider where a key service exists; fall back to secretbox or AES-CBC with careful key handling where it does not; automate rotation and verification; and keep secrets out of the cluster store entirely when the platform allows.

## Current state

**The configuration object.** A file of kind EncryptionConfiguration (API group apiserver.config.k8s.io) holds a list of resources entries. Each has a list of resource names (secrets, configmaps, or a custom resource in group-qualified form, with wildcard forms available in recent releases) and an ordered providers list. Example providers are aescbc with keys, secretbox with keys, aesgcm with keys, kms with a name, an endpoint (a unix socket) and a timeout, and identity. The API server flag that names the file is --encryption-provider-config, with a second flag to enable reload [src: kubernetes-docs e7daeb9ab914d710]. A key entry has a name and a base64 secret of 16, 24 or 32 bytes for AES, and 32 bytes for secretbox.

**Read and write rules.** Writes use the first provider. Reads use whichever provider matches the stored prefix, trying others in order for values without a recognised prefix. So an operator who wants to start encrypting puts the real provider first and identity last; one who wants to stop puts identity first and keeps the real provider second until all data is rewritten. Placing identity first by accident makes writes plain, which is the most common misconfiguration, because everything appears to work.

**Envelope encryption with KMS v2.** The API server, for each resource type, asks the plug-in for status, which includes a key ID and a health flag. When the key ID changes, the server notices, generates a fresh DEK, and asks the plug-in to encrypt it (wrap it) under the current KEK; objects written afterwards carry the wrapped DEK and the key ID. For reading, the server unwraps the DEK once per distinct wrapped value and caches the result. The cache is why latency and quota use stay low [src: kubernetes-docs 5a8436a87e677bee]. The plug-in must be a long-running process available before the API server starts, typically a static Pod or a systemd unit, and it holds the credentials to the remote KMS. The documentation describes the gRPC service and the integration with the remote service for implementers [src: kubernetes-docs 6b761a4c8ff818a0].

**Verifying.** The reliable test is to look at the stored bytes, not the API. Create a Secret, read its key straight from etcd with etcdctl, and check the value starts with the expected prefix and is not readable text [src: kubernetes-docs f7d110d30a27dea0]. For KMS, the check is also to confirm that the plug-in log shows an encrypt call and that the key ID in the stored value matches the active key [src: kubernetes-docs dc00b7f90fda7f47]. Metrics from the API server count encryption configuration reloads, key IDs in use and KMS call errors, and are what alerts should watch.

**Rotation.** A single-server rotation is a change of order. The sequence for local keys on a control plane with several API servers is: add the new key at the end of the keys list on every server and restart or reload each, so that all servers can read it; move the new key to the front so that writes use it, restart all servers again; rewrite every stored Secret (with the migration controller, or by reading and replacing each object) so that old ciphertext is replaced; and only then remove the old key. Skipping the first step is the classic fault: a server that has not seen the new key meets a value written by a peer that has, and cannot decrypt it. For KMS v2, rotation of the KEK in the remote service changes the key ID that the plug-in reports; the API server picks up the new key for new writes and keeps reading old data with the old wrapped DEKs, as long as the old KEK version remains available in the service, so rewriting is again needed before the old version is disabled [src: kubernetes-docs 73946b7229fcfe70].

**Turning it off.** Decrypting everything again is an explicit procedure: place identity first, keep the real provider second, rewrite all objects, then remove the real provider [src: kubernetes-docs ade26eb855cf9919]. The documentation also gives a way to determine whether encryption is currently active at all [src: kubernetes-docs c11024ac52cac5bc].

**Beyond the API server.** Encryption at rest in the API server protects etcd contents, snapshots and backups made from etcd. It does not protect the plain text in the memory of the API server, in Pods that mount a Secret as a volume (the kubelet places the data in a tmpfs on the node), in environment variables, or in logs. The security guidance for Secrets lists related measures: restrict RBAC access to Secrets, avoid wildcards in rules, prefer short-lived credentials, keep Secret manifests out of repositories, and consider external secret stores [src: kubernetes-docs b46b35365c7554aa] [src: kubernetes-docs 16ae0ae94f63efda].

**Generalised pattern.** Layered keys. A small, strongly protected key (in a KMS or hardware module) wraps many short-lived data keys; data keys are cached locally to avoid calling the key service on the hot path; ciphertext carries an identifier of the key that produced it; rotation adds a key, switches writes, rewrites data and retires the old key.

## Assessment: the good, the bad and the ugly

The good: the feature is built into the API server, supported by every managed service, and a KMS v2 provider gives the property that matters most, a key that the control plane host never holds. The prefix design makes migration and rotation incremental. Reload without restart and the migration controller removed the most error-prone manual steps. The performance cost with KMS v2 is small.

The bad: the default is off, and many installations never turn it on. Local-key providers keep the key where the data is, so they protect only against copies of the data without the configuration, which is useful for backups and weak against a compromised control plane node. Only the resources listed in the configuration are encrypted, and teams forget ConfigMaps that hold credentials and custom resources that hold tokens. A rotation needs care with several API servers, and a mistake turns a data-protection feature into an availability incident: a value that no server can decrypt makes the object unreadable, and unlike most failures it cannot be fixed by restarting. Encrypting etcd has no effect on who can read Secrets through the API.

The ugly: key loss is data loss. If the key file disappears with no copy, or the KMS key is deleted or its permissions revoked, every encrypted Secret is gone, including the ones needed to bring the cluster back, because the cluster's own components also use Secrets. Backups of etcd are only restorable with the keys of the moment they were taken, so key retention policy must follow backup retention. A KMS outage at the wrong moment prevents the API server from reading Secrets that are not in its cache, and cold start of a control plane depends on the KMS being reachable, which makes the key service a hard dependency of cluster recovery. A circular dependency appears when the KMS plug-in's credentials are themselves stored as a Kubernetes Secret, or the plug-in runs as a Pod that the API server needs in order to start. Verification is easy to skip because everything works whether or not encryption is active, and drift occurs when a new control plane node is built from an old template without the flag.

## Applications beyond this domain

Envelope encryption is the standard design in cloud storage and databases: object stores, volume encryption, transparent database encryption and backup tools all wrap per-object or per-file data keys under a master key in a key service, mainly because it lets bulk encryption happen locally and rotation of the master key happen cheaply. LUKS in Linux uses the same idea at the block layer with a volume key wrapped by passphrase-derived keys held in key slots, which allows changing the passphrase without re-encrypting the disk. The key-identifier-in-ciphertext approach shows up in JSON Web Encryption headers, in Tink's key sets and in age and sops file formats. The rotation pattern of adding, switching, rewriting and retiring applies to signing keys, database credentials and TLS certificates. The caution about nonce reuse in AES-GCM is general, and is why misuse-resistant constructions such as AES-GCM-SIV and XChaCha20-Poly1305 are popular in newer designs.

## Examples

**Enabling secretbox on a self-managed cluster.** An administrator writes a configuration with a single resources entry for secrets whose providers are secretbox with key1 first, and identity second. After a restart, new Secrets are written with the prefix naming secretbox and key1, while old plain Secrets still read. The administrator runs the storage migration for secrets so that old values are rewritten, checks a sample key in etcd with etcdctl and sees the prefix and binary data, and finally leaves identity at the end of the list for safety until a later cleanup. The key file is copied into the team's sealed backup with the same retention as etcd snapshots.

**KMS v2 on a managed service.** A team turns on envelope encryption on a managed cluster with a customer-managed key. The control plane wraps data keys with that key. When the team's security group schedules a rotation of the key every year, the new key version is used for new data keys; the old version remains enabled until a rewrite job has run. When an engineer later disables the old key version by mistake before the rewrite, Secrets written under it fail to decrypt, and the incident is fixed by re-enabling it.

**A failing example.** An administrator wants to rotate a key on a three-node control plane. She swaps the keys in the file on the first node, restarts it, and moves on to the second. During the window, the first node writes with key2 while the other two only know key1. A controller on the second node reads a Secret written by the first and receives a decryption error; it retries and floods the log, and a deployment stalls. The correct sequence adds key2 as a trailing key everywhere first, so every server can decrypt, and promotes it only afterwards.

## Related problems and ideas

Neighbouring problems include securing etcd transport and access (client certificates, network isolation), encrypting backups separately, and encrypting data in application databases. Alternatives that avoid storing secrets in the cluster: the external secrets operator, which syncs from a cloud secret manager into Secret objects (still stored in etcd), the Secrets Store CSI driver, which mounts secrets directly into Pods from Vault or a cloud store without creating a Secret, and workload identity so that no static secret exists at all. Sealed Secrets and sops encrypt secrets in Git so that repositories do not carry plaintext, which addresses the GitOps source and not etcd. Further out: confidential computing for the control plane, so that even the cloud operator cannot read memory, and attestation-gated keys that a KMS releases only to a control plane running measured code.

## Active research

Work in progress includes stronger formats for stored values (authenticated encryption with associated data tying ciphertext to the resource's key and name, so that moving a value to another key fails), better observability of key use, and rotation automation that tracks which objects still carry an old key. The Kubernetes community continues to refine the KMS API, for example more efficient status reporting and support for hardware-backed keys. Studies of real clusters keep measuring how many leave encryption off, and how many etcd backups sit in storage with weak access control. Open questions include safe cold-start ordering for a control plane that depends on an external KMS, graceful degradation when the KMS is down, and encryption of resources by default in distributions without breaking upgrades.

## Future direction

Expect managed services and distributions to enable encryption by default, with KMS v2 the normal path and local keys reserved for small or air-gapped clusters. Automation will fold rotation into upgrades, using the migration controller to rewrite data and the status API to confirm that the old key is no longer referenced. Short-lived and external credentials will reduce the number of Secrets in etcd. Stability levels and exact release numbers named here (KMS v2 stable, KMS v1 deprecation and removal timeline, reload behaviour, wildcard resource names in encryption configuration): to verify in the Kubernetes release notes; provider-specific features and key policies: to verify with each cloud's documentation.
