# Detecting attacks in a cluster: Falco and Kubernetes audit logs

## Define the problem

Prevention fails. A policy has a gap, a dependency has a flaw nobody knew about, a credential leaks, or a legitimate user is phished. The security of a cluster therefore also depends on noticing when something that should not happen is happening, quickly enough to act and with enough evidence to understand afterwards what was touched. The question is where to observe. Kubernetes gives two vantage points that complement each other. The control plane sees every API request: who asked, what for, on which object, and what the answer was. The node sees what processes actually do: which programs start, which files they open, which connections they make, and which system calls they issue. An attacker who has a shell in a container leaves almost nothing in the API log, because everything after the first exec happens inside the node. An attacker who steals a token and uses it from outside leaves nothing on the node, because everything happens through the API.

Three problems follow. First, getting complete and tamper-resistant records from each vantage point into a place the attacker cannot reach. Second, deciding what is suspicious: raw audit data and system call streams are enormous, and most of what happens is ordinary. A detection system needs a language for rules that match events with container and Kubernetes context (which Pod, which image, which namespace), exceptions for the many legitimate matches, and a priority for each. Third, routing alerts to people and automation without drowning them, since a detection that produces hundreds of false positives per day is turned off in a month.

This slice covers the Kubernetes audit mechanism (policy, levels, stages and backends), the principal API events that deserve a rule, Falco as the reference node-level detector (drivers, rule syntax, outputs, plugins), the use of Falco on audit events, and the operating practice of tuning. Forensics after an incident and threat hunting across the fleet are covered in the closing slice of the course.

## History and approaches

Host intrusion detection predates containers by decades. Tripwire checked file hashes, auditd and the Linux audit subsystem recorded system calls by rule, and OSSEC and later Wazuh combined log analysis with integrity checking. These tools were machine-centric: they knew processes and users, not Pods and namespaces, and tracked a few hundred long-lived hosts, not thousands of short-lived containers. The Linux audit subsystem, in particular, can log system calls but generates verbose records and costs performance at high volume.

Containers made the old model awkward and created a chance for a new one. Because every container runs on a shared kernel, a single sensor at the kernel boundary sees everything every container does. Sysdig built a system call capture tool in 2013 around a kernel module and a filter language that could name containers, and in 2016 its engineers released Falco as an open source rule engine on that capture. The project entered the CNCF in 2018 and moved through the maturity levels afterwards (graduation status and date: to verify) [web: falco.org]. Over time the sensor changed form. The original driver was a kernel module, which requires matching kernel headers and carries the risk that a module bug crashes the machine. An eBPF probe followed, and then a "modern" CO-RE eBPF driver that relies on kernel type information to run across kernel versions without compiling for each; in recent releases it is the default (version to verify). In parallel the project built a plugin system, so that the same rule engine can consume other event sources: cloud audit logs, GitHub events, and the Kubernetes audit log.

Other projects explored neighbouring designs. Tracee, from Aqua Security, uses eBPF to produce events and signature-based detections. Tetragon, from the Cilium project, is built around eBPF programs that can not only observe but also enforce, killing a process or blocking a call in the kernel, with policies expressed as Kubernetes resources. KubeArmor combines observation with enforcement through AppArmor, SELinux or BPF-LSM. Commercial platforms bundle sensors, cloud data and response automation. The shared pattern is that eBPF makes it possible to attach safe in-kernel programs to system call entry points, tracepoints and security hooks without a kernel module.

The audit side has its own history. The API server has supported audit logging since the 1.7 era, first in a simple form with a single log file and flags, and then with an advanced design (stable in 1.12) built on an audit policy file, multiple stages per request, multiple backends and event batching [src: kubernetes-docs efe78f3796c1d6bb]. Managed Kubernetes services expose audit logs through their own logging products, with different retention and format details.

Lessons from breaches made detection a standard recommendation. Public reports of cluster compromises through exposed dashboards, kubelets and weak credentials, including cryptomining campaigns that started processes in containers within seconds of gaining access, show a common signature: an exec into a Pod, a download of a binary, an outbound connection to a mining pool, a new privileged Pod or DaemonSet. Each of these is visible to one of the two sensors. The MITRE ATT&CK containers matrix and the Microsoft threat matrix for Kubernetes organised these stages (initial access, execution, persistence, privilege escalation, credential access, lateral movement, impact) and now serve as a checklist to map rules against [web: attack.mitre.org].

The emerging pattern: two complementary streams (API audit and node events) feeding a rule engine with workload context, with rules curated and tuned like code and alerts routed to a system that can correlate and act.

## Current state

**Kubernetes audit mechanics.** Each API request passes through up to four stages: RequestReceived (when the request arrives), ResponseStarted (headers sent, for long-running requests such as watch), ResponseComplete, and Panic. The audit policy, a file given to the API server, is an ordered list of rules; the first rule matching a request determines the level. Levels are None (not logged), Metadata (who, what, when, response code, but not bodies), Request (adds the request body) and RequestResponse (adds the response body). Rules match on users, groups, verbs, namespaces, resources and subresources, non-resource URLs, and can omit stages [src: kubernetes-docs b146a29c899f7c8d]. A good policy logs requests to Secrets, ConfigMaps and TokenReviews at Metadata (so that secret contents never enter the log), writes to RBAC and workload resources at Request or RequestResponse, drops noisy read traffic from system components, and ends with a catch-all Metadata rule.

**Backends.** The log backend writes JSON lines to a file with flags for path, maximum age, backups and size; the webhook backend sends batches of events to an HTTP endpoint. Both can batch, with parameters for buffer size, throttling and timeouts, and the documentation explains truncation of large entries [src: kubernetes-docs 479a561095751148] [src: kubernetes-docs 6f62deff4c890176] [src: kubernetes-docs a5a03a04b7e4c2f5]. In production the file is shipped off the node by a log agent, or the webhook points at a collector, so that an attacker who obtains control of the node cannot erase it. Because audit entries reveal request metadata for admission mutations as annotations, a reviewer can also see which webhook changed an object [src: kubernetes-docs b6d065e2ce4c2536]. The DISA STIG requires audit records of specified events and states what must be captured [src: disa-stig 31c728ecdbbe5d07].

**Events worth a rule.** A short list covers a large share of real incidents. Exec, attach and port-forward on Pods (verb create on pods/exec and pods/attach) by anyone but a defined set of operators. Creation of Pods or workload controllers that request privileged mode, host namespaces or hostPath, and any change to the Pod Security labels on a namespace. Creation or modification of ClusterRoleBindings and RoleBindings, especially those referring to cluster-admin. Reads of Secrets by unusual identities, and listing of all Secrets across namespaces. Requests from anonymous or unauthenticated users that were allowed. Service account token creation through the TokenRequest API for powerful accounts. Edits to webhook configurations, to CoreDNS and to the aws-auth or equivalent identity mapping objects. A burst of 403 responses from one identity, which marks scanning.

**Falco architecture.** A driver in the kernel captures system call events (and, with the modern driver, selected tracepoints) and passes them through a ring buffer to a user-space process. In user space, libraries enrich each event with state: file descriptor tables, the container runtime's metadata (container ID, image, labels) and, via the Kubernetes API or the runtime's metadata, Pod name, namespace and labels. The rule engine evaluates each enriched event against the loaded rules and passes matches to outputs. Falco runs as a DaemonSet with host access to /proc, the kernel interface and the container runtime socket, and requires privileges that make it itself a sensitive workload.

**Falco rules.** A rules file is YAML with four item types: rule (name, description, condition, output, priority, tags, and optionally enabled and source), macro (a named condition fragment), list (a named set of strings) and exceptions inside rules. A condition is a boolean expression over event fields, for example the event type (evt.type), the process (proc.name, proc.cmdline, proc.pname), the file (fd.name), the network connection (fd.sip, fd.sport), the user (user.name), and context (container.id, container.image.repository, k8s.ns.name, k8s.pod.name). Macros make rules compact: container, spawned_process, open_write and similar. The output field is a template with fields. The default ruleset, maintained by the project and divided into maturity levels (stable, incubating, sandbox), covers shells in containers, writes under /etc and /bin, reading sensitive files such as /etc/shadow, outbound connections from unexpected binaries, privilege escalation primitives, kernel module loading, the Docker socket mounted into a container, and many more.

**Outputs and routing.** Falco emits alerts to stdout, a file, syslog, or HTTP, or through gRPC. Falcosidekick fans out to dozens of destinations: chat tools, incident tools, SIEMs, message queues, object storage and serverless functions; Falco Talon and similar projects add response actions such as labelling or deleting a Pod and applying a network policy. For high-confidence rules, automated response (terminate the Pod, cordon the node) can follow, with attention to whether termination destroys evidence.

**Falco on audit events.** The k8saudit plugin lets Falco read Kubernetes audit events from a webhook or from a file and evaluate rules written over audit fields (ka.verb, ka.target.resource, ka.user.name, ka.target.namespace and so on). One engine and one alert pipeline then cover both vantage points. The ruleset for audit events is separate and has rules for exec into Pods, privileged Pod creation, anonymous access allowed, secrets listed and cluster-admin bindings.

**Generalised pattern.** Collect from at least two layers (control plane requests and node behaviour), enrich with workload identity, match with reviewed rules that include exceptions, route to a store the attacker cannot write to, and measure signal quality (alerts per rule, share actioned) as an engineering metric.

## Assessment: the good, the bad and the ugly

The good: both sensors are close to ground truth. The API audit log is complete, because all state change passes through the server, and Falco sees behaviour regardless of what the image claims to be. The cost of audit logging at Metadata level is modest. The Falco rule language is readable by non-specialists, the default rules encode community knowledge, and the CNCF-level community is large. eBPF drivers avoid the kernel module's operational risk.

The bad: rule quality decides everything. Default rules fire in normal operations of real clusters (package managers during image builds, init scripts that write to /etc, health-check shells, debugging sessions) and need tuning with exceptions, or the alert stream is noise. Context enrichment depends on container runtime integrations that lag behind new runtimes and can be missing for short-lived containers, which start and finish before metadata is fetched. Event drops at high load are a real possibility: if the ring buffer overruns, events vanish, and Falco reports drop counts that must be monitored. A system call sensor costs CPU, typically a few percent on busy nodes and more with broad rules. The audit log does not include request bodies for Secrets at Metadata level by design, so it can show that a Secret was read and by whom, but not which value.

The ugly: detection can be blinded. An attacker with root on the node can often kill the sensor, unload the probe, or evade it by paths the rules do not model, such as using an unmonitored system call for the same effect (the detection gap known as system call coverage). Rules written against specific tool names (xmrig, nc) are trivially evaded by renaming a binary. Attackers who understand the audit policy can operate through resources logged only at Metadata level. Audit logs written to the control plane node's disk disappear with the node in an incident and may be tampered with before they ship. Managed services decide which audit events you see, in what delay and for how long, and some delay delivery by minutes. Finally there is the human limit: the stream is only useful if someone reads it, and the typical failure is a quiet period during which a tuned-away rule hides the one true alert.

## Applications beyond this domain

The two-vantage-point design is the same one used in traditional security monitoring: network detection plus endpoint detection, API gateway logs plus workload telemetry. Cloud providers' audit trails (CloudTrail, Cloud Audit Logs) record management API calls in exactly the way the Kubernetes API audit does, and Falco's plugin system consumes them with the same rule language. The Sigma rule format, used to share detection logic for log sources in SIEMs, is the same idea with a different syntax, and eBPF-based observability tools (Pixie, Cilium Hubble, Parca) share the sensor technology for performance and networking rather than security. Operating system audit frameworks (Linux auditd, Windows event tracing, macOS endpoint security) provide the host-level equivalents, and incident response teams treat their output the same way: normalised, shipped off-host, searched by timeline.

## Examples

**Cryptominer in a compromised pod.** A web application with a remote code execution flaw is exploited. The attacker downloads a binary into /tmp and runs it. Falco's rules for a shell spawned in a container, for executing a file from a writable directory, and for an outbound connection to a known mining pool port fire within seconds, with the Pod name and image in each alert. The responder sees no corresponding API audit events, which confirms that the attacker has not touched the control plane, scales the Deployment to zero and snapshots the node's evidence before it is reclaimed.

**Stolen token.** A CI token leaks into a public repository. An attacker uses it from an external address to list Secrets in all namespaces, then creates a ClusterRoleBinding. Nothing happens on any node. Audit entries show the service account user, the source IP, a list verb on secrets with no namespace, and a create on clusterrolebindings, each response 200. A Falco rule on the audit stream or a SIEM query on the same logs raises the alert, and the entries give the incident team the exact sequence and timing.

**A failing example.** A team enables all default Falco rules on day one. In the first week the pager rings 400 times, mostly for a deployment tool that writes under /etc inside containers, and a log rotation shell. Engineers mute the channel. A month later a genuine shell in a production container is among the alerts and nobody reads it. The recovery plan is to start with a short list of high-confidence rules, add exceptions as code reviewed in pull requests, track alerts per rule and the fraction actioned, and expand only when the first set is quiet.

## Related problems and ideas

Neighbouring problems include fleet-wide log management (retention, search, cost), network flow observation (Hubble, VPC flow logs) for lateral movement, vulnerability management as the preventive counterpart, and forensics: preserving container filesystems and memory from ephemeral workloads. Alternative enforcement-capable designs (Tetragon, KubeArmor, BPF-LSM) can stop an action instead of alerting after the fact, at the price of false-positive blocks. Honeypots and deception: decoy Secrets, tokens and services whose use is a certain alert, which sidestep the tuning problem. Machine-learning anomaly detection, based on per-workload baselines of system calls and network patterns, is offered by several vendors but is not yet mainstream in open source because of false positives and explainability.

## Active research

Work in progress includes lowering the cost and loss rate of kernel event capture, more precise attribution of events to containers in the presence of runtimes like gVisor and Kata (where the sensor sees the sandbox boundary, not the guest), and tamper resistance of sensors (attestation of the running probe, protection of the agent process). Academic and industry groups study detection of container escape techniques, and evaluate how rule sets perform against attack emulation frameworks that replay known techniques (for example Atomic Red Team and the Stratus Red Team). Others work on rule portability across engines and on building sequence-aware rules that correlate API and node events for one incident. Open questions: how to share tuned rules and exceptions across organisations without leaking environment details, how much baseline learning is safe to trust, and how to measure detection coverage honestly.

## Future direction

Expect eBPF drivers to be the only drivers in practice, with richer built-in context and lower overhead, and the audit pipeline to move toward standard schemas that make cross-source correlation straightforward. Enforcement and detection will converge in tools that can do both with one policy, with detection mode as the rollout step. Managed services will offer more control-plane audit data by default. Rule maintenance will resemble software development: tests that replay recorded events, review of exceptions and versioned rule sets.
