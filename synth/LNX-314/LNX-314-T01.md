# Hardening the cluster itself: benchmark audits and the metadata endpoint

## Define the problem

A Kubernetes cluster is a set of privileged daemons that trust one another through certificates, flags and files. The API server, etcd, the controller manager, the scheduler and the kubelet on every node each expose a network surface, each read a configuration that can be loosened by a single flag, and each run with enough authority that compromising one of them usually means compromising the cluster. Most security problems in the first years of Kubernetes were not clever exploits. They were defaults and leftovers: a kubelet listening on a port that accepted unauthenticated requests, an API server reachable from the internet with anonymous access enabled, an etcd port open to the node network, a dashboard bound to a powerful service account. Attackers scanned for these and found thousands.

Two questions follow for anyone operating a cluster. First, how do you know whether the control plane and node components are configured the way a careful operator would configure them, and how do you keep knowing as versions change and people edit manifests? Second, even if every Kubernetes component is configured correctly, the machine under the cluster is usually a virtual machine in a cloud, and the cloud offers every process on that machine a link-local HTTP service, the instance metadata endpoint, which hands out credentials for the machine's identity. A Pod that can reach that address can often act as the node. Hardening the cluster therefore has a component part (configuration audit) and a boundary part (what the workload network can reach on the infrastructure beneath).

This slice covers both. It teaches how a configuration benchmark is structured, how an automated checker such as kube-bench maps a benchmark onto flags and files, how to read its output and decide what to fix, which settings matter most on each component, and how to cut workloads off from the node's cloud identity with network rules and with provider features. It stops at the cluster edge: workload identity, RBAC, admission and runtime detection have their own slices.

## History and approaches

Early guidance came as prose. The Kubernetes documentation grew a page on securing a cluster that lists the controls in rough order: restrict API access, restrict kubelet access, control what workloads may do, protect etcd, keep audit records [src: kubernetes-docs 7df18d8bc3675dfd]. Prose is a poor control, because it cannot be run. Teams that followed it did so inconsistently, and an auditor had no way to compare a cluster to a standard other than reading flags by hand.

The first systematic answer was the benchmark. The Center for Internet Security published consensus configuration benchmarks for operating systems well before containers, and a Kubernetes benchmark followed within a few years of the project's start, organised by component: control plane configuration files, API server arguments, controller manager, scheduler, etcd, worker node files and kubelet arguments, and a policy section covering RBAC, service accounts, network policies and secrets handling. Each item has a number, a rationale, an audit command and a remediation, and is marked as automated or manual and as scored or not. In parallel, government bodies produced their own checklists. The United States defense security guide for Kubernetes lists each finding with a severity, a check text and a fix text, and many items match the community benchmark almost line for line, for example requiring that anonymous authentication is switched off on both the API server and the kubelet [src: disa-stig ecc675762fe3a205] [src: disa-stig 405cc11927d77e92]. The NSA and CISA hardening guidance, first published in 2021, took a threat-led view: supply chain, malicious insiders and external attackers, with the same pattern of controls [web: media.defense.gov].

A benchmark nobody runs is still prose, so tooling followed. The kube-bench project from Aqua Security reads the benchmark as YAML test definitions and executes them on a node, checking process arguments, file permissions and ownership, and configuration file keys, then prints pass, fail, warn or info per item with the remediation text [web: github.com]. Its first versions tracked one benchmark version for all clusters, which broke on managed services where the control plane is invisible to the customer; later versions added targets for EKS, GKE and AKS, and a version auto-detection that selects the benchmark matching the cluster version. Parallel tools include kubescape, which scores clusters against several frameworks including NSA guidance and runs from outside as well as inside, and Trivy's cluster scanning mode. A different line of attack is policy as code applied before configuration reaches nodes, discussed in the admission slice.

Several failures shaped the current practice. The kubelet is the clearest. In older releases its read-write port accepted requests without authentication by default, and the exposure was widely abused through the exec and run endpoints, which let an unauthenticated caller run commands in any container on the node. The Kubernetes documentation now documents the kubelet authentication and authorization modes and warns that, absent explicit settings, a kubelet can accept anonymous requests and allow them, so production clusters should enable webhook authorization and disable anonymous access [src: kubernetes-docs 54dbad96306941b8] [src: kubernetes-docs 85eae54a4ef9781e]. Kubeadm and distribution installers now set these safely, but hand-built clusters and old images still carry the defaults. The API server bypass guidance spells out the remaining routes around the API: the kubelet API, etcd, and the node-local ports that skip API server authorization entirely [src: kubernetes-docs 25fdcc8eb293b5d4].

The metadata endpoint has its own history. Cloud providers expose instance data and credentials at a link-local address so software on the machine can obtain temporary keys without baked-in secrets. That is convenient for a VM and dangerous for a node full of other people's code. In 2019 a major breach of a financial institution used a server-side request forgery flaw in a web application firewall to make the host fetch role credentials from the metadata service, a case that pushed Amazon to introduce a session-oriented version of the service (IMDSv2), which requires a PUT to obtain a token, adds a hop limit on the response, and refuses requests carrying forwarding headers [web: docs.aws.amazon.com]. Google's metadata server requires a header that a simple SSRF often cannot set, and Azure's requires a similar header and rejects forwarded requests. Kubernetes-specific mitigations came later: egress network policies that block the address, metadata concealment features such as GKE Workload Identity's metadata server proxy, and EKS Pod Identity or IAM roles for service accounts, which give each Pod its own identity so that node credentials need not be reachable at all.

The emerging pattern is audit-then-lock: define a baseline from a benchmark, measure it automatically on a schedule and at build time, treat drift as an incident signal, and separately close the infrastructure doors that workloads should never touch.

## Current state

**The benchmark structure.** The CIS Kubernetes Benchmark, in its current numbering, has five areas. Section one covers the control plane node: file permissions and ownership for the API server, controller manager, scheduler and etcd manifests and their data directory, and the kubeconfig and PKI files. Section two covers etcd arguments, including client certificate authentication, peer authentication and a dedicated certificate authority. Section three covers control plane configuration beyond arguments: authentication, logging and audit policy. Section four covers worker nodes: kubelet configuration file permissions, anonymous authentication, authorization mode, client CA, read-only port, protection of kernel defaults, event record limits, certificate rotation. Section five covers policies: RBAC and service accounts, Pod security standards, network policies, secrets, extensible admission control, and general policies such as the default namespace and the security context of workloads. Items are scored or not scored, and automated or manual. Section five is mostly manual, because policy is about what a team intends, not a flag.

**How kube-bench works.** The tool ships a configuration directory with one folder per benchmark version, each holding YAML files per node role (master, node, etcd, controlplane, policies). A test group contains checks; each check has an audit command, a set of tests such as a flag comparison or a file permission mask, and the remediation text. At runtime it detects the cluster version, picks the benchmark, finds the binaries by name, builds the audit command (for example, a process listing filtered for the API server), evaluates, and emits results. It runs as a job in the cluster, as a container on a node with the host process namespace and key directories mounted read-only, or as a plain binary on the host. Output formats include human text, JSON and JUnit, and a summary line gives counts of pass, fail, warn and info. A fail means the audit command ran and the condition was unmet. A warn usually means the item is manual or the tool could not decide. An info is explanatory.

**Reading results.** The useful skill is triage. Failures fall into three bins: true misconfigurations on self-managed nodes (fix them), items that do not apply because the platform manages that layer (record the justification), and items the team deliberately rejects with a compensating control (record and review). Managed Kubernetes services publish their own shared-responsibility documents; on those, the node section is the part you can change, and the control plane section is a question for the provider. A report that goes from raw output to a signed-off exception list is the real artefact; a screenshot of a green summary is not.

**Highest-value settings.** Ordering by risk, an operator should be sure of the following. The API server has anonymous authentication off or limited, uses RBAC and node authorization, has the admission plugins that matter enabled, writes audit logs, and uses TLS toward etcd and the kubelets. The kubelet has anonymous authentication off, authorization mode Webhook, a client CA for the API server's certificate, the read-only port disabled, and rotation of serving certificates on. etcd accepts only authenticated clients on a port not reachable from workloads, and its data directory is owned by the etcd user with restrictive permissions. Static Pod manifests and kubeconfig files are owned by root and not writable by others, since whoever can write a static manifest on a control plane node can run anything. Secrets are encrypted at rest, which has its own slice. Nodes expose as few other ports as possible; the cluster's own documentation lists the ports each component needs [src: kubernetes-docs a7ba72546380ab23].

**Metadata protection, mechanics.** Three layers work together. At the provider layer, require the hardened metadata protocol: on AWS, enforce IMDSv2 and set the response hop limit to one on nodes so that traffic from a Pod, which crosses an extra network hop, cannot obtain a token; on GCP, enable workload identity so Pods see a restricted metadata server and not the node's service account; on Azure, use workload identity and restrict instance metadata access. At the network layer, add a default egress policy for workload namespaces that denies the link-local range, with explicit allowances for DNS and the actual dependencies. Policy engines that support a cluster-wide policy, such as Cilium's, allow the deny rule to be defined once for all namespaces. At the identity layer, remove the reason workloads would want node credentials: give each service account a way to obtain its own scoped cloud identity, and give nodes only the minimum permissions needed to pull images and register.

**Generalised pattern.** For any privileged substrate, keep three things separate: a measurable baseline (a benchmark run on a schedule), a boundary that workloads cannot cross (network and identity), and the narrowest identity the substrate itself needs.

## Assessment: the good, the bad and the ugly

The good: benchmarks give a shared vocabulary and a reproducible score, and kube-bench turns an afternoon of flag reading into a one-minute job that can run in a pipeline. Fixes for the highest-risk items are cheap flags. The metadata mitigations are well understood, and a deny rule on the link-local range works on every provider with a policy-capable network plugin.

The bad: benchmarks follow the Kubernetes release train with a delay, so a freshly upgraded cluster may be audited against a benchmark written for an earlier version, and flag names change between releases. Passing a benchmark says the knobs are set, not that the cluster is safe; the policy section cannot know whether your RBAC roles are sensible. Scores invite gaming: teams tune to turn red items green, sometimes by weakening operations (for example disabling features) when a documented exception would be better. Managed services complicate the picture, since half the control is invisible. kube-bench running in a container needs generous host mounts and can itself be a risky privileged workload if left running.

The ugly: configuration drift. A cluster passes in March, an engineer enables the read-only kubelet port in April to debug a metrics gap and forgets, and no one sees until the next scan. Static checks have a blind spot around runtime state, for example a flag set in a configuration file that is overridden by a command line argument, or the reverse; reading the live process arguments, as kube-bench does, is better than reading only files, but dynamic kubelet reconfiguration paths and operator-managed nodes can still surprise. The metadata story has an ugly corner too: hop limits break software on the node that legitimately needs the endpoint through a container, such as a node-level agent running in a Pod with host networking, and a blanket deny can break cloud provider controllers that run inside the cluster. Every metadata fix needs a test that the intended callers still work. Open issues include benchmark coverage of newer features such as user namespaces, structured authorization configuration and sidecar containers, plus uneven coverage of non-kubeadm distributions.

## Applications beyond this domain

The structure of a benchmark, a numbered set of verifiable controls with rationale, audit and remediation, is the same one used for operating systems (the CIS Linux benchmarks and the OpenSCAP content behind DISA STIGs), databases, cloud accounts and network devices. Tools like OpenSCAP and Ansible hardening roles apply the same audit-then-remediate loop to hosts, and the Linux pathway's earlier compliance course uses it for RHEL. Compliance regimes such as PCI DSS and FedRAMP ask for evidence of exactly these checks, so a scan report doubles as audit evidence.

The metadata-endpoint lesson generalises to any ambient authority: a link-local credentials service, a Unix socket for a container runtime, a mounted Docker socket, a host path. Each lets code in a low-trust position act with a higher-trust identity because of where it runs rather than who it is. The remedy is the same each time: remove the reachability, require an unforgeable token that SSRF cannot supply, or replace ambient authority with an identity issued per workload. SPIFFE identities, cloud workload federation and short-lived certificates apply the last idea outside Kubernetes.

## Examples

**A routine run.** On a kubeadm control plane node, an operator runs the benchmark as a job against the control plane target and gets a summary with a few failures. One reads that the scheduler's profiling endpoint is enabled; the fix is a flag in the static Pod manifest, and the kubelet restarts the Pod when the file changes. Another reports that the permissions on the controller manager kubeconfig are looser than the benchmark wants; a chmod fixes it. A third warns about a manual item (audit log retention) which the operator marks as covered by the log pipeline and records the reasoning.

**A failing example.** A team scans only the worker node target and reports success. Their control plane is a managed one, but they also run a self-hosted etcd on separate machines, which the scan never touched, and it listens on a node-network address with no client authentication. Everything in the scan was true and the cluster was still exposed. The lesson is to list every component first and match each to a target before trusting a summary.

**Metadata.** A Pod running a web application with an SSRF bug is asked to fetch a URL pointing at the link-local address. With default settings on a node with the older metadata protocol, the response contains a role name and then a set of temporary keys. With the hardened protocol and a hop limit of one, the first request, which needs a token obtained with a PUT, either cannot be made through the SSRF primitive or its reply is dropped after crossing the extra hop. With an egress policy that blocks the range, the connection never starts. The three layers fail independently, which is why all three are used.

## Related problems and ideas

Neighbouring problems include node hardening below Kubernetes (immutable and minimal operating systems such as Bottlerocket, Flatcar or Talos reduce the surface a benchmark must audit), certificate management for the control plane, and supply chain integrity of the control plane images. An opposing approach to checking configuration after the fact is to generate it from a known-good source: managed clusters, cluster API templates and declarative node images keep drift small because nodes are replaced and not edited. Mid-stream ideas include verifying that a node booted a known image through attestation with a TPM, and confidential nodes that encrypt memory so a hypervisor-level adversary sees nothing. Less mainstream are proposals to move the benchmark's checks into the API itself, as conditions on node and component objects reporting their security posture to the control plane.

## Active research

Work in progress spans several fronts. The Kubernetes security community and the CIS working group continue to track benchmark versions to releases, with open questions about how to express checks for configuration delivered through structured files instead of flags. Research on drift detection looks at continuous compliance using eBPF to observe actual kubelet and API server behaviour instead of declared settings. Studies of internet-exposed clusters, run by security vendors and academic groups, keep measuring how many control planes, kubelets and etcd instances answer unauthenticated requests, and the numbers are still non-zero. On metadata, cloud providers are refining token binding so that stolen credentials cannot be used from another machine, and academic work examines SSRF-to-metadata chains in serverless and container platforms. Open questions: how much of a benchmark can be proven by configuration alone, how to score managed control planes fairly, and how to avoid alert fatigue from hundreds of low-severity findings.

## Future direction

Expect benchmarks to be published more often and to ship machine-readable content (OSCAL profiles are the lead candidate) so that scanners and policy engines consume them directly. Per-Pod cloud identity is becoming the default, shrinking the value of the node credential until the metadata endpoint can be blocked for all workloads without a compatibility cost. Upstream Kubernetes continues to move risky settings from flags to validated configuration files and to tighten defaults, so some checks will vanish as safe behaviour becomes the only behaviour. Release cadence matters here: a new minor version arrives roughly every four months, so a benchmark mapped to a version that is more than a few releases old should be treated as stale. Dates for specific benchmark releases and provider deprecations: to verify against the publishers at the time of study.
