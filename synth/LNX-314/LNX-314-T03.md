# AppArmor, seccomp and shrinking the kernel attack surface

## Define the problem

A container is a process with a restricted view of the system, not a machine. It shares the kernel with every other container on the node and with the node's own services. Namespaces hide other processes, mounts and networks, cgroups limit consumption, and a reduced set of capabilities removes some privileges. None of those mechanisms limits which kernel code the process can reach. The kernel exposes several hundred system calls, a large set of pseudo-filesystems under /proc and /sys, device nodes, and dozens of subsystems reachable from the system call interface, from the socket families to the performance and tracing interfaces. A bug in any of them is a bug that a malicious process in a container can try to trigger, and a kernel exploit from inside a container is a break-out because the kernel does not know the container exists.

The slice therefore asks what a defender can do on the node, short of using a different isolation technology, to lower the odds that a compromised process finds a usable kernel flaw or misuses a legitimate interface. Two Linux mechanisms do most of the work. Seccomp filters the system calls a process may make, with the choice of allowing, denying with an error, or killing. AppArmor, a Linux security module, restricts what a process may do to files, capabilities, network sockets and some other operations by matching it to a path-based profile. Neighbouring controls (dropping capabilities, no_new_privs, read-only root filesystems, masked and read-only paths in /proc and /sys, and user namespaces) complete the picture. The challenge is applying them in Kubernetes: the profile must exist on the node, it must be selected by the Pod, and it must be strict enough to matter without breaking the application.

This slice covers how the kernel features work, what the container runtime does by default, how Kubernetes selects profiles, how to write and test a custom profile, and how much protection each layer really adds. SELinux gets passing mention as the alternative module on Red Hat family systems. Stronger isolation by sandboxed runtimes is covered in a later slice.

## History and approaches

Early container runtimes gave the process the whole system call table. The original seccomp, introduced in Linux 2.6.12 in 2005, was an all-or-nothing mode that allowed only read, write, exit and sigreturn, which suited a compute-farm use case but not general programs. In 2012 the kernel gained seccomp mode 2, where a process installs a filter written as a classic BPF program that inspects the system call number and arguments and returns a verdict [src: man-pages 851272490f524459]. The first adopters were browsers: Chrome built its sandbox on it, and OpenSSH used it for privilege separation. Docker integrated seccomp in 2016 with a default profile that blocks a few dozen calls, the ones that are rarely needed by applications and have a record of kernel bugs: kexec, module loading, key management, the ability to change the clock, and so on. The default has worked well as a baseline, while custom profiles written for single applications remained rare because producing one is laborious.

AppArmor came from the Immunix project, was acquired by Novell, then moved into the mainline kernel in 2.6.36 (2010) and is the default module on Ubuntu, Debian and SUSE. Its profile language describes what a named program may read, write, execute and what capabilities and network access it has, using file paths with globs. The Docker default profile for AppArmor denies writes to sensitive parts of /proc and /sys, mounting and ptrace of other profiles. Red Hat systems use SELinux instead, which labels objects and applies type enforcement; container runtimes there apply a container type with a unique category pair per container, so a compromised container cannot read another container's files [src: kubernetes-docs 7d92f37c149a40e7].

Kubernetes took a while to make these first-class. For years AppArmor was selected through an annotation on the Pod, with a key naming the container, an artefact of the early design, and seccomp the same way until a field in the security context replaced the annotation. The feature was stable but sprawling: the node's profile had to be loaded by an out-of-band process, the Pod would fail or silently run unconfined depending on the runtime if it was not, and defaulting was not available. Recent releases added a proper field for AppArmor in the security context and reached general availability in the 1.30 line (exact version to verify), with the same types as seccomp: RuntimeDefault, Localhost and Unconfined [src: kubernetes-docs 8466d636da5cf394]. For seccomp, the kubelet gained a flag to make the runtime's default profile the default for all workloads on the node and not only those that ask for it; the Kubernetes documentation describes enabling it and the compatibility checks to do first [src: kubernetes-docs d2257c1318a62c41] [src: kubernetes-docs 5aef32ec34873095]. The Pod Security Standards were then updated to require seccomp RuntimeDefault or Localhost at the restricted level, making the old unconfined default something that a policy rejects [src: kubernetes-docs fff16678dc6bf879].

On the tooling side, the Security Profiles Operator from the Kubernetes SIG automates the node distribution problem: it installs profiles as custom resources on every node, can record a workload's actual system calls with an eBPF or log-based recorder, and generates seccomp or SELinux profiles from the recording. Projects such as bane, Inspektor Gadget's seccomp advisor and Falco-based generators try to do the same for AppArmor and for system call lists. Across the same period the kernel community kept finding bugs that profile-based defence blunted: several privilege escalation bugs in rarely used system calls or socket families could be reached by an unprivileged process only if the filter allowed them, and the default seccomp profile blocked a number of them before fixes shipped. The reverse also happened: bugs in calls that every program needs (io_uring is the oft-cited example, which several vendors disabled in their sandboxes) show that filters can only remove surface that the application does not need.

The emerging pattern: start from the runtime default everywhere, narrow with generated profiles for the workloads that matter, add mandatory access control for file and capability restrictions, and treat the sum as defence in depth beside, not instead of, kernel patching and stronger isolation for untrusted code.

## Current state

**Seccomp mechanics.** A filter is a small BPF program attached to a thread with the seccomp system call, and it is inherited by children and cannot be removed. Each system call entry runs the filter, which sees the call number, the architecture and up to six raw arguments (but not the content behind pointers) and returns an action: allow, return an errno, send a signal, kill the process or thread, log, or notify a user-space supervisor. A process must either hold the capability to install a filter or have set no_new_privs, which stops execve from gaining privilege through setuid binaries or file capabilities; that bit is why unprivileged containers can use seccomp at all. Filters stack, with the most restrictive verdict winning. Because arguments are numbers, filters are good at excluding calls and flags (for example the clone flags that create new user namespaces) and weak at path checks, which is AppArmor's job. The classic traps are time-of-check problems with pointer arguments, which is why seccomp is not used to filter paths, and architecture confusion, where a 32-bit call number on a 64-bit kernel must be handled explicitly.

**Seccomp in Kubernetes.** A Pod or container sets securityContext.seccompProfile with type RuntimeDefault (use the container runtime's built-in profile), Localhost (a JSON file stored under the kubelet's seccomp directory on the node, referenced by relative path) or Unconfined. The default profile in containerd and CRI-O is derived from Docker's. The kubelet flag for seccomp defaulting makes RuntimeDefault apply when the Pod does not say otherwise. Typical breakage from enabling it is small: a few applications that need a blocked call, such as certain debuggers using ptrace, or tracing tools, fail with a permission error; strace of the failing call identifies it, and either a custom profile or an exception for the workload follows [src: kubernetes-docs 82b5cf03c5c2e9b6].

**AppArmor mechanics.** A profile attaches to a program by path or by name and operates in enforce or complain mode. It lists rules for file access with permissions (read, write, append, execute with transition modes, link, lock, mmap exec), capabilities, network families and types, mount and signal and ptrace control, and can include shared abstractions. Profiles compile to a binary form loaded by apparmor_parser into the kernel's policy; the module checks the profile when the process makes an access, as part of the Linux security module hooks, after normal permission checks. Because rules are path-based, a hard link or a bind mount can give the same file another name, and the module accounts for some of this but not all, which is the usual argument for the label-based approach of SELinux. For containers the runtime applies a profile with a name chosen per container; the default profile is generated from a template and loaded by the runtime at start or by the node's package.

**AppArmor in Kubernetes.** The Pod selects AppArmor with a field in the security context specifying RuntimeDefault, Localhost with a profile name that must be loaded on the node, or Unconfined. The kubelet checks that the node supports it and that the named profile is loaded before the container starts. Distribution of Localhost profiles is the awkward part and is usually done with a DaemonSet that loads files, the Security Profiles Operator, or by baking profiles into node images [src: kubernetes-docs 3a83f7f6f9788860]. If the node lacks AppArmor, as on distributions that use SELinux, the Pod spec is accepted but not enforced unless an admission policy rejects it.

**Other attack surface reducers.** Dropping all capabilities and adding back only what is needed removes most privileged operations; the security context supports an explicit drop and add list [src: kubernetes-docs 6b4a338102d5bb98]. Setting allowPrivilegeEscalation to false sets no_new_privs. A read-only root filesystem stops persistence in the image layer. Non-root users and user namespaces (which map container root to an unprivileged host user) reduce the value of any escape. The runtime masks paths such as /proc/kcore and makes /proc/sys read-only inside the container. On the node, sysctls such as kernel.unprivileged_userns_clone and user.max_user_namespaces, kernel.unprivileged_bpf_disabled and kernel.kptr_restrict reduce reachable interfaces, and a minimal kernel configuration without unused subsystems (and module loading locked after boot) shrinks the code that can be attacked.

**A measurable idea of surface.** The effective attack surface is the set of kernel entry points reachable by the workload. Teams can estimate it by recording which system calls and which files an application uses in test (strace, eBPF recorders), comparing to the list allowed, and tracking the difference. A tight profile for a typical web service might allow around a hundred calls out of more than three hundred.

**Generalised pattern.** Apply least privilege at the interface between a process and the kernel: a deny-by-default filter on calls, a path- or label-based policy on objects, and a minimal set of privileges, with profiles generated from observed behaviour and verified by tests before enforcing.

## Assessment: the good, the bad and the ugly

The good: the defaults are cheap and already built. RuntimeDefault seccomp costs almost nothing in performance, blocks a meaningful list of dangerous calls, and breaks very few applications. AppArmor and SELinux have decades of operational history. Custom profiles for a high-risk workload, such as one that parses untrusted files, can reduce the kernel surface sharply. The Pod Security Standards put seccomp in the required set, so a cluster-wide policy turns good practice into the default.

The bad: seccomp filters see numbers, not meaning. They cannot tell a harmless open from a malicious one, and a profile must either allow a call everyone needs or break the program. Profile writing is laborious, and profiles drift as applications and libraries change: a new libc version starts using a different call and the strict profile breaks it in production. AppArmor profiles depend on paths inside the container's mount namespace, and a profile written for one image breaks on another layout. Both mechanisms are host-dependent: a Pod specifying a Localhost profile that is not on a particular node fails to start there, which complicates scheduling and autoscaling. SELinux and AppArmor cannot both be enforced on one host in the usual setup, so the decision is made by the distribution.

The ugly: the protection is only as good as the weakest allowed call. Kernel bugs reachable through the calls that every application needs are not stopped. The history of container escapes shows this: several breakouts used features that the default profile allowed, or capabilities that a Pod was granted, or mounts of the host's runtime socket. A profile in complain mode that nobody reads gives a false impression of coverage, and Unconfined is one line away in any Pod spec unless an admission policy forbids it. Observability is also thin: a denied system call by seccomp returns a plain error that an application may log as an unrelated failure, so the cause can take hours to find unless audit logging of seccomp actions is enabled. And profile generators record only what the test run exercised, so rare code paths (error handling, certificate renewal, log rotation) get cut and fail later.

## Applications beyond this domain

Seccomp filters protect far more than containers. Browsers sandbox renderer processes with them, and so do OpenSSH, Firefox, Android's app zygote, Flatpak and systemd units via the SystemCallFilter option, which uses system call groups such as @system-service to avoid listing every call. Landlock, a newer unprivileged Linux security module, lets a program restrict itself to a set of file paths and is gaining adoption as a programmer-friendly alternative to AppArmor for self-sandboxing. OpenBSD's pledge and unveil express the same ideas in two simple calls and influenced Linux designs; FreeBSD's Capsicum and macOS's sandbox profiles are siblings. Language runtimes and WebAssembly runtimes apply the same principle of exposing only an explicit set of host functions. Serverless platforms use seccomp plus microVMs to isolate tenants. The recurring lesson is that a small, stable interface between untrusted code and the kernel beats an attempt to find every bug behind it.

## Examples

**Enabling the default.** A cluster operator enables seccomp defaulting on a pilot node pool. Most workloads start without change. A debugging sidecar using ptrace fails with an operation-not-permitted error, and the team gives only that Pod a Localhost profile that adds the one call; everything else keeps the default. The change is rolled to other pools after a week with no further incidents.

**A custom profile.** A service that converts uploaded documents is a high-risk parser. The team records its system calls under test using the Security Profiles Operator, keeps the list, adds the calls for its crash handler found in a second run, and sets the default action to return an error for everything else. A later library update starts calling a new, harmless system call during start-up; the Pods crash-loop and the team learns to run the recorder against each new image before promotion.

**A failing example.** A security team writes an AppArmor profile that denies writes to /etc and /usr for a web server container, tests it in complain mode and enforces it. A month later a deploy that rotates TLS certificates writes to /etc/ssl for the first time, fails and takes the service down. The profile was correct for observed behaviour and wrong for the application. The fix was to allow that directory explicitly and to add a certificate rotation step to the profile's test plan.

## Related problems and ideas

Neighbouring controls include capabilities and user namespaces (covered in earlier container courses), kernel lockdown and module signing for the node, and eBPF-based enforcement. Alternatives to filtering are stronger isolation, covered in the sandboxed runtime slice, and kernel minimisation with unikernels or minimal kernels. Newer mechanisms: Landlock for self-sandboxing, BPF LSM programs that implement custom policy in eBPF and are used by tools like Tetragon and KubeArmor, and seccomp user notification, where a supervisor process decides on certain calls on behalf of the filter (used to allow mount in an unprivileged container, for example). Experimental ideas include automatic profile synthesis by static analysis of binaries, and per-request seccomp profiles that tighten after an application finishes its start-up, so that initialisation needs a wide set of calls and the steady state a narrow one.

## Active research

Work is under way on automatic system call filtering from static and dynamic analysis, with studies measuring how much of the system call interface typical images use and how well generated profiles survive updates. Kernel developers continue to harden the interfaces most often abused: restricting unprivileged user namespaces and io_uring, adding Landlock features, improving seccomp performance (the constant-time action cache for allowed calls) and extending the notification mechanism. The Security Profiles Operator community works on profile lifecycle management across node pools. Open questions include how to express and verify profiles as part of a software bill of materials, how to ship them with the image so they follow it, and how to measure the real reduction in exploitability, since attack surface by count of calls is a crude proxy.

## Future direction

Expect RuntimeDefault to become the effective default in distributions and managed services, and AppArmor and seccomp fields to be treated as table stakes in policy checks. Profile generation from recording is moving into CI pipelines so that a profile is an artefact built and tested with the image. Landlock and BPF-based policy will take over some of the work of path-based modules for self-confinement. For the highest-risk workloads the trend is to combine these filters with microVM or user-space kernel isolation.
