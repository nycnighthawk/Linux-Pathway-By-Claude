# Minimal RBAC and controlled access to the Kubernetes API

## Define the problem

Everything in Kubernetes happens through the API server. Operators deploy by creating objects, controllers react to objects, the kubelet reports node and Pod state through objects, and an attacker who has stolen a credential reads Secrets and creates Pods through the same door. The question this slice addresses is who may do what to which objects, and how to keep that answer small enough to reason about as a cluster grows from one team to dozens.

Authorization in Kubernetes is additive and by default silent. Role-based access control, the mode almost every cluster uses, has no deny rule: a subject can do whatever the union of its bindings allows, and the union is hard to see because bindings live in many namespaces, in cluster-wide objects, in Helm charts and in operators that install their own roles. Over time three kinds of excess accumulate. People and automation receive the broad built-in roles because they are quick. Service accounts, which every Pod can mount, pick up permissions that no human reviews. And a few verbs hide more power than their names suggest, so that a role which looks harmless is in fact a path to cluster administrator.

The gap is therefore both conceptual and practical. Conceptually, administrators need a model of which permissions are equivalent to others (reading Secrets, creating Pods, impersonating, binding roles). Practically, they need a way to find what a subject can really do, to produce roles that are narrow but still work, and to remove the automatic credentials that Pods carry. This slice covers authentication sources at a level needed to reason about subjects, the RBAC object model, escalation paths, minimisation technique, service account hygiene, and the review tools that audit the result. Admission policy and workload confinement are separate slices.

## History and approaches

The earliest Kubernetes releases authorised with a static policy file of one JSON object per line, read by the API server at startup. Changing it meant restarting the control plane, and the file could only grant, never describe roles. Attribute-based access control (ABAC) followed the same file model and was never ergonomic. In the meantime, many clusters ran with an authorizer that allowed everything because the alternative was inconvenient, and service accounts effectively held administrator rights in tutorials and early Helm releases, a pattern that attackers exploited when a single Pod was compromised.

RBAC arrived as an alpha API and became the recommended mode around the 1.8 release; it is now the standard in distributions and managed services. The design is small. A Role or ClusterRole lists rules of API groups, resources, resource names and verbs. A RoleBinding or ClusterRoleBinding attaches a role to users, groups or service accounts. A ClusterRole bound with a RoleBinding is limited to one namespace, which allows reuse of roles across namespaces. Aggregated ClusterRoles collect rules from others by label so that custom resources can extend the built-in view, edit and admin roles. A few protections were built in from the beginning: a user cannot create or update a role binding that grants more than they already hold unless they hold the special bind or escalate verb [src: kubernetes-docs 268394581b16bc3a].

Then came the sobering years. Reviews of real clusters kept finding the same things: the cluster-admin role bound to broad groups, wildcard rules, default service accounts with extra rights, long-lived service account tokens stored as Secrets and copied into CI systems and laptops. The Kubernetes project's own good-practice guide now lists the dangerous permissions explicitly: listing or getting Secrets, creating workloads that can mount Secrets or run privileged, creating tokens for service accounts, granting roles, impersonation, and the ability to modify the node or the webhook configurations [src: kubernetes-docs 9963d3670f7dd002]. The documentation also states a plain rule that avoids a common confusion: list access on Secrets reveals their content just as get does, and watch does too.

Credentials changed in parallel. Originally, each service account had a Secret holding a non-expiring JWT that the kubelet mounted in every Pod. That token was valid until the service account was deleted, even if the Pod died, and anyone who read it could use it from anywhere. The bound service account token projection replaced it: the kubelet requests a token through the TokenRequest API that is tied to the Pod and to an audience, expires, and is refreshed on disk [src: kubernetes-docs 366926b9febabde0]. Since the 1.24 release the control plane no longer auto-creates the legacy Secret, and long-lived tokens exist only if someone creates them on purpose [src: kubernetes-docs a8843c14d2b57512]. Mounting is still on by default for each Pod, so the question shifted to whether a Pod needs any API credential at all.

Tools grew around the review problem. The built-in kubectl auth can-i answers a point question, including with impersonation. Community tools answer broader ones: kubectl-who-can finds subjects with a given permission, rakkess prints a matrix of a subject's rights per resource, rbac-police and KubiScan search for risky rules and paths to cluster-admin, and audit-based generators such as audit2rbac or Kyverno's reports produce a first role from observed requests [web: github.com]. Managed services added mapping layers between cloud identities and Kubernetes groups, so that the cluster's RBAC now depends on cloud IAM and the review has to cross both.

The emerging pattern: narrow roles built from observed need, no standing human administrators, no ambient credentials for Pods that do not need them, and continuous review through queries and diffs, not annual audits.

## Current state

**Subjects and authentication.** Kubernetes has no user object. A request arrives with a credential that an authenticator maps to a username and a list of groups: client certificates (the subject common name becomes the user and organisation fields become groups), bearer tokens from service accounts, OIDC identity tokens verified against an external provider, webhook token review, or an authenticating proxy. Anonymous requests are mapped to a special user and group and are allowed or denied by the same RBAC rules. Anything the authenticator cannot revoke needs care: a client certificate cannot be revoked in standard Kubernetes except by waiting for expiry or replacing the certificate authority, so certificates should be short-lived and not used for people. OIDC with groups from the identity provider is the preferred human path because access ends when the provider disables the account.

**The authorization pipeline.** A request passes authentication, authorization, then admission. The API server evaluates its configured authorizers in order; the usual chain is Node (limits kubelets to objects for their own Pods) then RBAC. Each request is described by attributes, the user and groups, the verb, the API group, the resource, subresource, name and namespace; the verb is one of get, list, watch, create, update, patch, delete, deletecollection, plus special ones such as bind, escalate, impersonate and approve [src: kubernetes-docs e35a6a64e7f84f83]. Subresources have their own entries, so that "pods/exec", "pods/log" and "pods/portforward" can be granted apart from "pods", and a rule for "pods" does not give exec. The self-checks are SelfSubjectAccessReview, behind kubectl auth can-i, and SubjectAccessReview for others [src: kubernetes-docs ed01f4d6ff74255a].

**Equivalent permissions.** A minimiser's key knowledge is which grants are as strong as cluster-admin, or close to it. Creating Pods (or any workload controller) in a namespace lets the holder mount any Secret and any service account token in that namespace, and run on a node with whatever the namespace's admission settings permit. Reading Secrets across a namespace includes service account tokens if legacy tokens exist. Creating a TokenRequest for a privileged service account yields its identity. Impersonation yields the impersonated identity. The bind and escalate verbs, or the right to create role bindings together with a role that already contains the target rights, allow self-promotion. Writing to nodes or to the validating and mutating webhook configurations lets one subvert enforcement. Editing a ClusterRole that is aggregated into admin changes every admin. The practical approach is to treat these as the privileged tier and give them to as few subjects as possible.

**Minimisation technique.** Start from the job, not from a built-in role. List the exact API calls a human or program makes. Give each its group, resource, subresource and verb, add resourceNames where objects are fixed (a ConfigMap read by name, for example), and bind in the narrowest scope: a RoleBinding in one namespace rather than a ClusterRoleBinding. Prefer many small roles over one large one, and name them after the duty. Avoid wildcards in verbs, resources and groups; a wildcard silently covers resources created by later installs of operators and CRDs. Use the built-in view role for read access with care, because it does not include Secrets, but remember that aggregated rules from CRDs can extend it. For people, use groups mapped from the identity provider; for automation, one service account per workload, never the default one. Remove or restrict default bindings that distributions create where they exceed the need, such as the broad discovery rights given to unauthenticated users, which exist only for compatibility.

**Pod credentials.** Set automountServiceAccountToken to false on the service account, or on the Pod, for any workload that does not call the API; most application Pods do not. Where a workload needs the API, mount the bound token with a short expiry and a specific audience, project a token for external systems instead of storing a secret, and give the account only the rules it needs. For the kubelet itself, the Node authorizer and the NodeRestriction admission plugin limit each kubelet to its own node and its own Pods.

**Review loop.** Three questions, asked regularly: who holds cluster-admin and equivalent rights (query the bindings, include groups); which service accounts can read Secrets or create Pods; and which roles contain wildcards or the escalation verbs. Run these as scheduled jobs and as pull-request checks on manifests, and compare to the previous run. A role that changed since the last review should show up as a diff with the requester's justification.

**Generalised pattern.** Access control for a system with a single powerful control plane works best when subjects are federated from an external identity authority, grants are additive and attached to duties, credentials are short-lived and bound to a context, and the equivalence classes of privilege are known so reviewers can concentrate on them.

## Assessment: the good, the bad and the ugly

The good: RBAC is declarative, auditable, and enforced uniformly by the API server for every client. The escalation checks stop a casual user from creating a role binding beyond their own rights. Bound service account tokens removed an entire class of credential theft in which a token stolen from a dead Pod stayed useful for years. kubectl auth can-i with impersonation makes it easy to test a role before shipping it.

The bad: there is no deny rule and no negative test in the model, so narrowing a role is only ever by omission, and the sum of bindings is hard to see without tooling. Roles have no concept of conditions such as time, source address or object labels; fine-grained attribute rules need admission policy or an external authorizer. Resource names do not help with create, list or watch requests, since the name is not known at create time and list returns everything the rule allows. Role definitions are verbose, and teams give up and apply wildcards. Rule changes take effect at once, but a token already issued continues to carry its identity until it expires, so revocation is as slow as the token lifetime.

The ugly: Secrets reading and Pod creation are so powerful that many "namespace admin" arrangements are secretly cluster-wide admin once a cross-namespace service account token is in a Secret. Operators and Helm charts are the largest source of surprise: an operator installed by a team often needs cluster-wide rights to custom resources and sometimes to Secrets, and whoever can edit the operator's deployment can use those rights. CI systems often hold a kubeconfig with administrator rights because it was the quickest way to deploy; that file becomes the real root credential. Cloud identity mapping hides some of the picture, as the effective rights come from a cloud IAM role and a mapping file in the cluster. Another awkward fact is that the discovery roles bound to unauthenticated users expose API metadata, which some scanners flag and which cannot always be removed without breaking tooling. Open issues include aggregated roles that quietly broaden built-ins after a CRD install, and the absence of first-class tooling in core Kubernetes to answer "who can do X" without a third-party plugin.

## Applications beyond this domain

The same shape appears in every cloud IAM system: a principal, an action, a resource, and additive policy documents, with the same recurring failures (wildcards, inherited broad roles, long-lived keys). Lessons from RBAC review therefore transfer directly: map equivalent permissions, split read from write, scope to resource, prefer federated identity to static keys. Database role systems and Linux sudo rules share the pattern of command-level grants where some commands are privileged because they can spawn shells, as in a sudo rule for an editor that allows escape to a shell. Privilege-escalation analysis of Active Directory (the path-finding approach used by BloodHound) is the same graph problem as finding paths from a compromised service account to cluster-admin, and several Kubernetes tools borrow the graph method.

## Examples

**A narrow role that works.** A deployment pipeline needs to update the image of one Deployment named web in the shop namespace. The role grants get and patch on deployments with resourceNames [web] in apps, and get, list, watch on replicasets and pods for the rollout wait; it is bound to the pipeline's service account by a RoleBinding in the shop namespace only. The pipeline cannot create a Deployment, touch another namespace, read a Secret, or exec into a Pod. Testing uses kubectl auth can-i with impersonation for both a permitted and a denied action.

**A failing example.** A monitoring stack asks for a ClusterRole that grants get, list and watch on all resources, "to scrape metrics". That rule includes Secrets. Anyone who can run a Pod under the monitoring service account, or exec into one, can read every secret in the cluster. The fix is to enumerate the resource kinds the scraper reads (pods, nodes, endpoints, services, and the metrics non-resource URL) and exclude Secrets explicitly by listing only what is needed.

**An escalation path.** A developer can create RoleBindings in their namespace and holds the built-in edit role. They cannot bind cluster-admin because of the escalation check. They can, however, create a Pod that mounts the namespace's deployer service account token, which belongs to a role bound across the cluster for convenience. Using that token they now act as the deployer. Nothing in RBAC was bypassed; the weakness was the existence of a powerful service account whose token any workload creator could mount, and the fix is to confine that service account to its own namespace and keep the deployer out of the developer namespace.

## Related problems and ideas

Neighbouring problems include admission policy for attributes RBAC cannot see (the next slices), network access to the API server (restricting the endpoint to known address ranges, private control planes), audit logs for evidence of use, and secret storage. Alternative authorizers: ABAC, webhook authorizers that call an external policy engine such as OPA, and the structured authorization configuration introduced in recent versions that lets an operator chain several authorizers and attach CEL conditions. Ideas still at the edge include just-in-time access, where a human requests a short-lived binding that expires on its own, with approval recorded in a ticket; access request controllers exist as open source projects. Another is continuous least-privilege generation, comparing a subject's granted verbs to the verbs observed in the audit log over a month and proposing a smaller role. Some projects take a graph database approach to the whole cluster and cloud account to detect attack paths.

## Active research

Current work includes the Kubernetes project's authorization improvements (selector-aware authorization and CEL-based conditions in newer releases, which narrow list and watch requests by label or field), and ongoing debate about whether deny rules belong in the core model. Academic and industry studies analyse thousands of public Helm charts and operators for excessive permissions and find systemic over-privilege. Researchers apply static analysis to generate minimal roles from controller source code, and fuzzing to find escalation paths. Open questions: how to express an operator's permissions so they follow the custom resources it manages and not the cluster, how to review the interaction of cloud IAM and Kubernetes roles as one system, and how to make short-lived access ergonomic enough that engineers stop keeping standing keys.

## Future direction

Expect bound and audience-restricted credentials to become the only form, with workload identity federation replacing stored kubeconfigs in CI, and stronger defaults that mount tokens only when asked. Conditional authorization will probably move from admission webhooks to the authorizer chain as the structured configuration matures. Tooling is converging on query-style review (who can do X, what changed since last week) with reports exported as code-review checks. Features named above arrived across several recent minor releases; exact versions and their stability levels: to verify in the Kubernetes changelog at the time of study.
