# Admission control for Pods: Pod Security Admission and policy engines

## Define the problem

RBAC answers who may create a Pod. It says nothing about what is in the Pod. A subject allowed to create workloads can ask for a privileged container, mount the host's filesystem, share the host network, run as root, add capabilities or use an image from anywhere. Each of those turns a compromise of one application into a compromise of the node, and from the node, of the cluster. The question for a platform team is how to make the unsafe request impossible, or at least visible, for the tenants it hosts, without writing a custom controller for every rule.

The place to answer it is admission. After a request is authenticated and authorised, and before the object is stored in etcd, the API server runs it through admission controllers that can mutate it, reject it, or both. This is the only point where every create and update of every object passes through one code path, which is why nearly all cluster-wide guardrails live there. The problem splits into three layers. First, a baseline for Pod security that every cluster should have, expressed as a small number of named standards that people can understand and compare. Second, general policy beyond Pods: required labels, allowed registries, resource limits, banned fields on Services and Ingresses, naming rules, and constraints that depend on other objects. Third, operations: how policies roll out without breaking running workloads, how exceptions are granted, how results are reported, and how the admission layer avoids becoming an outage or a bypass.

This slice covers the admission pipeline, the built-in Pod Security Admission with its three levels and three modes, the policy engines Kyverno and OPA Gatekeeper, the in-tree ValidatingAdmissionPolicy that uses the Common Expression Language, and the failure modes that matter in practice. Supply chain checks and runtime detection use the same mechanism but are treated in later slices.

## History and approaches

The first Pod-level control was the PodSecurityPolicy (PSP), a cluster resource with a list of constraints (privileged allowed or not, host namespaces, volume types, run-as user rules, capabilities, seccomp and AppArmor profiles) and an admission plugin that matched a Pod to a policy the requester was authorised to use. PSP was powerful and confusing. A Pod was admitted if any policy the user or its service account could "use" accepted it, and the policy could also mutate fields, so the outcome depended on the alphabetical order of policies and the RBAC bindings that selected them. It had no dry-run mode, no easy way to see what would break, and no sane rollout. Many clusters left it off, and many that turned it on added a permissive policy for everyone. The project deprecated it in Kubernetes 1.21 and removed it in 1.25 [src: kubernetes-docs 3363fececec9fa49].

The replacement kept the idea of named policies and dropped almost everything else. The Pod Security Standards define three cumulative levels: privileged, which is unrestricted; baseline, which blocks the known privilege escalations such as host namespaces, privileged containers, most added capabilities, hostPath volumes and unsafe sysctls, while remaining compatible with most applications; and restricted, which follows current hardening practice, with non-root execution, dropped capabilities, seccomp profile set, and no privilege escalation [src: kubernetes-docs cbb6eaddc62c6dba]. The documentation explains deliberately why there is no level between privileged and baseline: finer gradations would multiply the combinations that people must reason about [src: kubernetes-docs 721060d594c9c521]. The built-in Pod Security Admission (PSA) controller, beta in 1.23 and stable in 1.25, applies a level to a namespace through labels, in three modes: enforce rejects, audit records a violation in the audit log, and warn returns a warning to the client. Each mode has its own level and an optional version pin, so a team can enforce baseline today while auditing and warning against restricted [src: kubernetes-docs 66d145e299a9f921].

Alongside, external policy engines had already appeared. The Open Policy Agent project, a general policy engine with the Rego language, was embedded in Kubernetes by Gatekeeper, which installs a validating webhook that evaluates Constraint resources instantiated from ConstraintTemplates written in Rego. Kyverno took the opposite language choice: policies are Kubernetes resources written in YAML with pattern matching and, later, CEL expressions, with rule types for validate, mutate, generate and verify images, and built-in reporting. Other tools (jsPolicy, Kubewarden with WebAssembly modules) offered different language trade-offs. Their strength was flexibility: any attribute of any object, joins with other cluster state, mutations such as injecting default security contexts, and generation of companion objects like default NetworkPolicies per namespace. Their cost was a webhook in the request path.

The webhook cost showed up in incidents. Admission webhooks are called synchronously by the API server, so a slow or unavailable webhook delays or blocks requests. A webhook configured to fail closed with a broad match that includes the namespace in which the webhook itself runs can deadlock: the Pod for the webhook cannot be recreated because the webhook is not there to admit it. Operators learned to exclude system namespaces, set tight timeouts, run several replicas, and choose the failure policy per rule. The project's own guidance on webhook practice emphasises idempotent mutations, validating the final state after mutation, and failing open only where the risk is understood [src: kubernetes-docs 053c98c277e038f1] [src: kubernetes-docs 3715460125669f22].

The most recent branch is moving policy into the API server itself. ValidatingAdmissionPolicy lets an administrator define a policy as a resource containing CEL expressions, with parameter resources for tunable values and a binding that selects where it applies, with no webhook. It graduated to stable in 1.30, evaluating in-process with cost limits, audit annotations and a configurable failure policy [src: kubernetes-docs 84ea856072eea75f] [src: kubernetes-docs 69ce758bb03a1cbf]. A mutating counterpart is following through alpha and beta stages (stability to verify). Kyverno and Gatekeeper have adopted CEL-based rule types or generation of VAP resources from their own policies, which blurs the former boundary between "built-in" and "external".

The emerging pattern: the built-in PSA covers the common Pod baseline for every cluster with almost no operational cost; in-process CEL policy covers simple validation rules; an external engine is added where mutation, generation, cross-object lookups, image verification or rich reporting are required.

## Current state

**The admission pipeline.** A write request passes authentication, authorization, then mutating admission (built-in plugins and mutating webhooks, which may be called more than once if a later webhook changes an object), schema validation, then validating admission (built-in plugins, validating policies and validating webhooks), and finally persistence. Mutating and validating policies and webhooks see the object and the old object for updates, the user info and, for webhooks, the dry-run flag. Reads are never subject to admission, and neither are requests that bypass the API, such as static Pods on a node, which the kubelet creates from files without admission checks beyond mirror object creation.

**Pod Security Admission.** The controller is compiled into the API server and enabled by default. A namespace carries labels of the form pod-security.kubernetes.io/enforce, audit and warn, each set to a level, with optional -version labels pinning the standard to a Kubernetes minor version so that later tightening of a level does not break workloads on upgrade [src: kubernetes-docs 66d145e299a9f921]. The controller checks Pods and the Pod templates inside workload objects (Deployments, Jobs and so on), but enforcement happens only on Pod creation, so a Deployment can be created and then fail to create its Pods; the warn and audit modes on the workload object give the early feedback. Exemptions, configured on the API server by admission configuration file, name usernames, runtime classes or namespaces to skip, which is how system namespaces are handled. The recommended rollout, from the migration and namespace guides, is to label namespaces with audit and warn at the target level first, read the results, fix workloads, then switch on enforce [src: kubernetes-docs 6458d401a21fae1c] [src: kubernetes-docs c4c781b285afd146]. Dry-run label changes also report which existing Pods would violate the new level.

**What the levels check.** Baseline rejects host namespaces (network, PID, IPC), privileged containers, capabilities beyond a short allowed list, hostPath volumes, host ports, unsafe proc mount, sysctls outside a safe set, an AppArmor or SELinux setting that weakens confinement, and a seccomp profile of Unconfined. Restricted adds: volume types limited to a safe list, no privilege escalation, running as non-root with a non-zero user, a seccomp profile set to RuntimeDefault or Localhost, and all capabilities dropped with at most NET_BIND_SERVICE added back [src: kubernetes-docs a1541abe1c2951b8]. A workload that passes restricted can be assumed not to hold the usual shortcuts to host access.

**Gatekeeper.** Two custom resource kinds carry the model. A ConstraintTemplate defines a new constraint kind with a parameter schema and Rego code, and a Constraint creates an instance with match rules (kinds, namespaces, label selectors) and parameters, such as the list of allowed registries. Gatekeeper's admission webhook evaluates new objects, and an audit controller periodically scans existing objects and writes violations into the status of constraints. A library of templates covers common cases. Its enforcement actions are deny, warn and dryrun. Data sync can replicate selected objects into the policy's data cache, which allows rules that look at other objects, such as uniqueness of an Ingress host.

**Kyverno.** A ClusterPolicy or namespaced Policy holds rules with match and exclude selectors and one of: validate (pattern matching, deny conditions with JMESPath, or CEL), mutate (patches or strategic merge), generate (create or synchronise resources in response to a trigger), or verifyImages (check signatures and attestations). The admission controller runs as a webhook, a background controller applies policy to existing resources, and a reports controller writes PolicyReport resources in the standard format. Kyverno policies can enforce the Pod Security Standards with a built-in rule type, and the `validationFailureAction` field chooses audit or enforce. Exceptions are separate PolicyException resources with their own RBAC, so granting an exemption is itself an authorised and auditable act.

**ValidatingAdmissionPolicy.** The policy object has matchConstraints (resources and operations), optional paramKind, validations (CEL expressions with messages), matchConditions to skip requests, auditAnnotations, and a failurePolicy. A binding object selects the namespaces or objects and the parameter resource, and sets validationActions among Deny, Warn and Audit. CEL expressions are type-checked against the API schema at definition time and run with a bounded cost, which is why there are no timeouts and no network failures [src: kubernetes-docs 0d6ebd599dce5e46] [src: kubernetes-docs 8ee80d1fc20113b5].

**Generalised pattern.** Express security rules as declarative policy evaluated at one choke point, with three separate decisions made per rule: where it applies, what happens on a violation (deny, warn, audit), and who may be exempt. Roll out by audit, then warn, then deny.

## Assessment: the good, the bad and the ugly

The good: PSA is small, understandable and nearly free. Three levels fit on a page, labels are visible in every namespace listing, and the warn mode catches a bad manifest at kubectl apply. Kyverno's YAML policies lower the barrier for platform teams that do not want to learn Rego, and its mutation and generation features remove whole categories of boilerplate. Gatekeeper's template and constraint split gives a reusable policy library with a rigorous language. VAP removes the webhook failure modes, runs in microseconds, and needs no extra deployment.

The bad: PSA is coarse by design. It cannot permit a single extra capability or a hostPath limited to one directory, and one exception means moving the whole namespace to a looser level or using an exemption. It checks Pods only, nothing else. Webhook-based engines add latency to every matched request, add components to patch and monitor, and can take the cluster down if they are misconfigured. Rego has a real learning curve and can be hard to test, while YAML policy languages become unreadable at higher complexity, and complex CEL strings in YAML are hard to maintain. Policy sprawl is another cost: hundreds of rules with unclear owners and a growing pile of exceptions.

The ugly: bypass paths. Admission does not see static Pods, does not run on reads, and cannot undo objects that existed before the policy was installed, which stay in place until rescheduled; a policy engine that only checks at admission will report a clean cluster that is full of old violations unless a background scan is turned on. Mutating webhooks interact: two mutations on the same field can fight, and a validating policy that ran before a later mutation validated the wrong object. The fail-open versus fail-closed choice is real and uncomfortable: fail closed gives an outage when the engine is down, fail open lets everything through when it is down, and an attacker who can overload the webhook can choose the second. Policies that look at labels are only as strong as the ability to set labels, so a tenant who can edit a namespace's labels can lift its own PSA level, which means namespace label edits must be restricted by RBAC and checked by a policy. Finally there is audit blindness: warn-mode messages vanish in CI logs, and audit annotations in the API server log are rarely read, so "we are in audit mode" can last for years.

## Applications beyond this domain

Admission-style policy is the same idea as a policy enforcement point in access control systems, a pre-commit hook in version control, or a gate in a deployment pipeline. Terraform and cloud infrastructure use the same engines: OPA and Conftest check plans before apply, Sentinel does it in a commercial product, and cloud governance services enforce organisation policies at account creation. API gateways run policy on requests for authorisation and rate limiting. Databases apply row-level policy at query time, and operating systems apply mandatory access control at system call time. The shared design questions carry over: where is the choke point, what is the policy language, how do you test and roll out a policy, and who owns exceptions. CEL in particular is used far beyond Kubernetes, in Google Cloud IAM conditions, Envoy and Firebase rules.

## Examples

**Namespace rollout.** A platform team labels every tenant namespace with warn and audit at restricted, and enforce at baseline. The next deployment of a service that runs as root prints a warning in the developer's terminal: it lists the container and the failing checks. The team fixes the image to run as a non-root user and sets the seccomp profile. After two weeks without warnings the namespace gets enforce at restricted. A batch job team asks for an exception for a job that needs a hostPath; the platform team moves only that job to a dedicated namespace at baseline.

**A Kyverno policy.** A rule matches Pods and denies images not drawn from the company registry; a second rule mutates Pods to add the seccomp RuntimeDefault profile where unset; a third generates a default-deny NetworkPolicy in each new namespace. A PolicyException with narrow match grants a monitoring agent permission to use hostNetwork, reviewed through a normal pull request.

**A failing example.** A team installs a fail-closed validating webhook with a match on all Pods and no namespace exclusion, hosted on a Deployment in the same cluster. A node pool upgrade evicts the webhook Pods; the controller cannot recreate them because every Pod creation, including the webhook's own, is sent to the webhook, which does not exist. The API server returns timeouts and the cluster cannot schedule anything. Recovery needs deleting the webhook configuration with direct access to the API. The permanent fixes: exclude the policy engine's namespace and kube-system, use a short timeout, run replicas with anti-affinity and a PodDisruptionBudget, and prefer in-process policy for rules that do not need it to be external.

## Related problems and ideas

Neighbouring problems: image provenance at admission (the supply chain slice), runtime enforcement of the same properties (Falco, KubeArmor, Tetragon), and drift detection for objects that policy cannot reach. Alternatives to admission include enforcement in the CI pipeline (conftest, kubeconform with policy bundles, Kyverno CLI), which catches problems earlier but can be bypassed by anyone with cluster credentials, and a controller that corrects drift after the fact. Not yet mainstream: the Gateway API's policy attachment pattern, the Kubernetes Policy working group's PolicyReport format, mutating admission by CEL, and machine-checked policy verification (proving that two policies are equivalent or that one implies another). Multi-cluster policy distribution, with a central repository synchronised by a GitOps tool and per-cluster parameter bindings, is common practice in larger organisations.

## Active research

Open work includes performance and safety of CEL evaluation (cost estimation, the strict cost enforcement features), the design of mutating policy without webhooks, and policy testing: unit tests for Rego (opa test), the Kyverno test command, and the VAP community's tools. Researchers study misconfiguration at scale, measuring how many clusters run without any Pod-level policy, and the effect of default-on admission controls. Another thread analyses interactions among mutating webhooks, which are order-dependent and can reach different results under reinvocation. Open questions: a standard portable policy format across engines, how to express exceptions with expiry, how to measure policy coverage, and whether PSA levels should be refined to track new Linux features such as user namespaces.

## Future direction

The built-in route is expanding: more CEL libraries, mutating policy, namespace-scoped policy variants and better reporting, which will shrink the set of cases that need an external webhook. Pod Security levels are revisited with each Kubernetes release as new risky fields appear, and version pinning keeps upgrades predictable. External engines are specialising on lifecycle features (generation, cleanup, image verification, exceptions with approval) and on multi-cluster management.
