# Sandboxed container runtimes: gVisor, Kata Containers and RuntimeClass

## Define the problem

Ordinary containers share the host kernel. Seccomp, AppArmor and dropped capabilities narrow what a process can ask of that kernel, but the kernel itself, with its millions of lines of code and hundreds of system calls, remains the boundary between a malicious tenant and everyone else. For most first-party workloads that trade-off is acceptable. It is not acceptable for code that the platform operator did not write and cannot review: customer-supplied functions in a serverless platform, build jobs that compile arbitrary repositories, notebooks, continuous integration runners for pull requests from strangers, plug-ins, and multi-tenant clusters where tenants are different companies. A single kernel vulnerability reachable through any allowed system call gives such a tenant the whole node.

The remedy is a stronger isolation boundary, one with a much smaller attack surface than the host kernel's full interface, at some cost in performance and compatibility. Two designs dominate. A user-space kernel (gVisor) intercepts the workload's system calls and implements them in a memory-safe program that itself talks to the host through a narrow set of calls. A micro virtual machine (Kata Containers, Firecracker-based runtimes) runs the Pod inside a lightweight VM with its own guest kernel, relying on the hypervisor and hardware virtualization as the boundary. Both are exposed to Kubernetes through the same mechanism: a RuntimeClass, a cluster-scoped object that names a runtime handler configured in the container runtime on the nodes, which a Pod selects with a single field.

This slice covers the threat the designs address and the ones they do not, how each design works at the level of architecture, how Kubernetes selects and schedules a sandboxed Pod (handler, overhead, scheduling constraints), the compatibility and performance costs, and how to decide when the extra isolation is worth it. It is a short, depth-two slice: the goal is informed selection and correct configuration, not an internals tour of either project.

## History and approaches

The earliest isolation answer was the virtual machine itself. Public clouds ran each customer in a VM and every tenant had a kernel of its own. That model is sound but heavy: VMs boot in seconds to minutes, carry hundreds of megabytes of memory overhead, and make fine-grained scaling expensive. Containers solved density and startup time by sharing a kernel, and their weaker boundary was accepted as a trade. Platforms that ran untrusted code, notably serverless providers, wanted both properties, and several projects started around 2015 to 2018 to get them.

Intel's Clear Containers and the Hyper project's runV each wrapped containers in minimal VMs with a stripped guest kernel and an optimised boot path; in 2017 they merged into Kata Containers under the OpenStack Foundation (later the Open Infrastructure Foundation). A Kata Pod is a lightweight VM: the Kata runtime starts a hypervisor (QEMU, Cloud Hypervisor, Firecracker or others), boots a minimal kernel and root file system, and runs an agent inside the guest which starts the containers of the Pod inside the VM. The Pod is the unit of the VM, so all containers in a Pod share one guest kernel. Communication with the host goes through virtio devices and a shared file system (virtio-fs) for images [src: cilium-docs 7ac09b395b481b50].

Firecracker, written by Amazon and open-sourced in 2018, is a minimal virtual machine monitor written in Rust that backs AWS Lambda and Fargate. It deliberately supports a handful of devices and boots in a fraction of a second, with a small memory footprint. By itself it is not a container runtime; projects such as firecracker-containerd and Kata's Firecracker mode connect it to the container ecosystem.

gVisor came from Google, open-sourced in 2018 and used behind several of its serverless and managed Kubernetes products. Its runtime, runsc, presents the OCI runtime interface. Inside, the Sentry process is an application kernel written in Go that implements most Linux system calls, process and memory management, networking (its own TCP/IP stack called netstack) and file systems for the sandboxed processes; a companion process, the Gofer, mediates file access. The sandboxed workload's system calls are intercepted, through ptrace in the earliest platform, then through KVM, and in current releases mainly through a seccomp-based trap mechanism (the "systrap" platform) that avoids requiring virtualization hardware. The Sentry itself runs under a strict seccomp filter and accesses the host through a small number of system calls, so an attacker who escapes the workload's view reaches the Sentry, not the host kernel [web: gvisor.dev].

Kubernetes support evolved in step. Early on, switching the runtime meant configuring a whole node or cluster, which left no way to mix trusted and untrusted work. The RuntimeClass resource (alpha in 1.12, beta in 1.14, stable in 1.20) solved this by letting a Pod choose a named runtime configuration through runtimeClassName. A RuntimeClass names a handler, which must correspond to a runtime registered in the container runtime's configuration on each node that supports it. It can declare overhead, the resources the sandbox itself consumes, so the scheduler and quota include them, and scheduling constraints (node selector and tolerations) that confine Pods of that class to nodes that have the runtime [src: kubernetes-docs 08c93efd2da6cfff] [src: kubernetes-docs f83dda3d746e2669] [src: kubernetes-docs 3da8fa30af10671b].

Experience with deployments brought several realisations. Compatibility was the first: a user-space kernel cannot implement every system call and kernel feature identically, and the set of unsupported behaviours (some ioctls, certain /proc and /sys entries, some networking and filesystem features, eBPF, perf) breaks applications that rely on them. VM-based sandboxes have better compatibility, because the guest kernel is a real Linux, but need nested virtualization or bare metal hosts when run inside a cloud VM, and they limit access to host devices such as GPUs. Performance was the second: system-call-heavy and file-system-heavy workloads can be several times slower in gVisor, while VM sandboxes pay at startup and in memory. Observability was the third: node-level tools (Falco, eBPF sensors, tcpdump on the host) see the sandbox boundary, not the guest's processes.

The pattern emerging: sandbox only the workloads that need it, use RuntimeClass to make the choice declarative and policy-enforceable, and keep ordinary containers, hardened with the earlier slices' controls, for the rest.

## Current state

**RuntimeClass.** The object has a name, a handler (a string that maps to a runtime name in containerd's or CRI-O's configuration), an optional overhead with podFixed resources, and optional scheduling with nodeSelector and tolerations. Pods set spec.runtimeClassName. If a Pod refers to a class that does not exist, or whose handler is not configured on the node, the kubelet fails to start the Pod and reports the error as an event. Using the scheduling field makes the Pod land only on nodes that carry the matching labels, usually a dedicated node pool; tolerations let those nodes carry a taint so ordinary Pods stay away. Overhead is added to the Pod's resource requests for scheduling and cgroup sizing, and shows up in quota calculations [src: kubernetes-docs 08c93efd2da6cfff].

**Node configuration.** The operator installs the runtime binaries and shims, then registers a handler in the CRI runtime's configuration, for example a runtime entry named for gVisor pointing at the containerd shim for runsc, or entries named for Kata with a chosen hypervisor. The runtime configuration files select hypervisor, kernel and guest image paths, default memory and CPU, and shared file system mode. Managed clusters, such as GKE Sandbox, expose the choice with a node pool option and create the RuntimeClass automatically.

**gVisor in practice.** The Sentry intercepts each system call from the workload, applies its own implementation, and, when the workload needs real I/O, makes a restricted set of host calls. Networking can run through netstack (strong isolation, lower throughput) or pass through to the host network stack (faster, weaker). File access goes through the Gofer, with caching options trading performance for consistency. Because the sandbox is a normal process on the host, Pod density is close to ordinary containers; memory overhead is tens of megabytes per sandbox. Checkpoint and restore support exists. Debugging uses runsc subcommands (runsc debug, boot logs, strace emulation) and the runtime's own logs.

**Kata in practice.** Each Pod gets a VM. The guest kernel is a stripped Linux kernel that the Kata project builds; the guest sees virtio block, network and file system devices. Memory can be hot-plugged to track Pod limits, and CPU likewise. Startup is on the order of a few hundred milliseconds to about a second with optimised configurations, and memory overhead is on the order of tens to a couple of hundred megabytes per Pod depending on hypervisor and configuration (figures vary and need measurement on your hardware: to verify). Nodes need hardware virtualization exposed, which on public clouds means bare metal instances or nested virtualization. The Kata project also underlies the Confidential Containers work, where the guest runs in a hardware-protected VM (AMD SEV-SNP or Intel TDX) and the image is pulled and decrypted inside the guest so that even the host operator cannot read it.

**Interaction with Pod Security and policy.** The Pod Security Standards state plainly that sandboxed Pods are a different problem: the levels describe what a container can do to a shared kernel, and the documentation notes that a sandboxed runtime changes what those settings mean, without defining a separate level [src: kubernetes-docs 5f7ecd74634e8d6f]. Policy engines can enforce that Pods in certain namespaces must set a runtimeClassName from an allowed list, or that untrusted namespaces cannot run without one. Seccomp and AppArmor settings in the Pod spec may have limited effect in a VM sandbox, because the host sees only the hypervisor process.

**Choosing.** The decision rests on a threat model and a cost budget. If the main risk is a vulnerability in the host kernel's less-used system calls, gVisor shrinks that attack surface sharply, and the risk shifts to the Sentry and the host calls it needs. If the main risk is a full kernel compromise, a VM boundary with a minimal hypervisor is stronger and compatible with unmodified Linux binaries, at a higher resource and operational cost. Neither protects against an application bug that leaks data through the application's own legitimate channels, nor against a compromised credential.

**Generalised pattern.** Make the isolation boundary a named, selectable property of the workload (a class), keep the scheduling and resource accounting consistent with its overhead, and apply it to the workloads whose trust level warrants it.

## Assessment: the good, the bad and the ugly

The good: the boundary is materially stronger than a shared kernel with filters, and the class mechanism makes it easy to apply selectively and to enforce by policy. The designs have production history at large providers running mutually untrusting tenants. gVisor needs no virtualization hardware and has near-container density; Kata runs standard Linux workloads unmodified. Both integrate with ordinary Kubernetes objects and images.

The bad: compatibility and performance are real. A user-space kernel has unimplemented or divergent behaviour, so applications must be tested, and syscall- or file-heavy workloads (databases, builds with many small files) slow down, sometimes drastically. VM sandboxes cost memory, start time and node flexibility. Both reduce the usefulness of node-level security tooling. Device access (GPUs, special hardware, host paths) is limited or absent, and some Kubernetes features interplay awkwardly: hostNetwork, privileged mode and certain volume types do not make sense or are restricted. Operational burden rises: another runtime to install, patch and monitor, separate node pools, and separate debugging procedures.

The ugly: a sandbox is not a guarantee. gVisor and the hypervisors have had vulnerabilities, and an escape of the sandbox lands in a host process that may run with more privilege than one expects. Running a VM-based sandbox inside a cloud VM with nested virtualization combines two layers of isolation with a performance penalty and a larger and less-tested hypervisor surface. Misconfiguration is common: a RuntimeClass with a handler that no node has silently excludes Pods from scheduling or fails them, and a Pod that omits the class runs unsandboxed with no warning unless policy requires it. Overhead accounting is easy to get wrong, causing evictions or overcommitment. The shared file system (virtio-fs, Gofer) path is a recurring source of both performance problems and bugs. Finally, teams assume that sandboxing makes seccomp, RBAC and network policy unnecessary; it only addresses the kernel-sharing risk.

## Applications beyond this domain

The same designs power serverless and function platforms (Lambda with Firecracker, Cloud Run with gVisor), CI and sandbox-as-a-service offerings that run untrusted builds and notebooks, and online code execution services. Browsers use the same layered idea in their process sandboxes, with OS-level confinement beneath a language runtime. WebAssembly runtimes provide a capability-based sandbox at the language level and are used in plug-in systems and edge platforms. Mobile operating systems isolate apps with per-app users and mandatory access control and, in some cases, virtualization-based protection of security-critical code. Qubes OS applies the VM-per-task model to desktops. In each case the lesson is that the boundary should be as small and as simple as the workload tolerates.

## Examples

**A sandboxed node pool.** A platform team that runs customer-submitted build jobs creates a node pool with the gVisor runtime configured, labels the nodes, and taints them. A RuntimeClass named gvisor with that node selector and a matching toleration is created. A Kyverno policy requires every Pod in the builds namespace to set runtimeClassName to gvisor. A build that uses a rarely implemented system call fails; the team files the compatibility issue, adds a retry on an ordinary pool for that single project, and records the exception.

**Overhead matters.** A Kata RuntimeClass declares an overhead of 160 MiB of memory and a quarter CPU. A Pod requesting 256 MiB is scheduled as if it needed about 416 MiB, and the namespace quota shows the larger number. Without the overhead field the nodes were overcommitted and Pods were evicted under load.

**A failing example.** A team rolls out a RuntimeClass named secure and tells developers to add it to their Pod specs. Three months later an audit finds half the workloads in the namespace without the field, because the Deployment templates were copied from older ones. Nothing had enforced it. The fix is an admission policy that denies Pods in the namespace without an allowed runtimeClassName, plus a default injected by a mutating policy.

## Related problems and ideas

Related approaches include user namespaces for Pods (mapping container root to an unprivileged host user, now maturing in Kubernetes), which reduce the impact of an escape without a new runtime; rootless containers; Linux kernel hardening and live patching; and nodes dedicated per tenant, which sidestep the shared-kernel problem with plain VMs. Unikernels and library operating systems build the application and a minimal kernel into one image. Newer ideas: confidential containers with hardware memory encryption, WebAssembly-based Pods through runtimes such as runwasi, and Landlock-style self-sandboxing by applications. Some platforms combine layers, running gVisor inside a VM, to reduce the blast radius of a bug in either.

## Active research

Work covers the performance of user-space kernels (reducing interception cost with newer platforms and with io_uring-like batching), better file system sharing for VM sandboxes (virtio-fs improvements, DAX), and fast restore of sandboxes from snapshots for serverless cold starts. Security research studies the attack surface of hypervisor device models and the Sentry's own system call implementations, with fuzzing of both. The Confidential Containers community works on attestation-driven image decryption and policy. On the Kubernetes side, SIG Node works on better support for sandbox lifecycle in the CRI and on pod-level resource accounting with overhead. Open questions include a portable definition of what a sandbox guarantees, how to monitor activity inside the boundary, and how to express sandbox requirements in the Pod Security Standards.

## Future direction

Expect sandboxed runtimes to move from a specialist option to a standard choice for multi-tenant and untrusted-code platforms, with managed services offering them as a checkbox, faster restore and smaller memory overhead, and policy libraries that tie namespaces to classes. User namespaces and sandboxing will be used together. Hardware-backed confidential VMs will broaden Kata's role.
