# Automating IdM with ansible-freeipa

## Define the problem

An IdM domain is state: users, groups, hosts, HBAC rules, sudo rules, DNS zones, password policies, and the servers
and replicas themselves. The `ipa` command and the web UI change that state interactively. For one administrator and a
dozen objects that is fine. For a team, an audit requirement, several environments (development, staging,
production) that should hold the same policy, and servers that must be rebuilt after a failure, interactive changes
fail in predictable ways. Nobody remembers who added the sudo rule that lets a contractor restart the database. The
staging policy differs from production in ways nobody can list. A rebuilt replica lacks the CA role because the person
who installed the original forgot the flag.

The goal of automation here is **desired state in version control**: a repository describes what IdM should contain,
a tool brings a domain to that state idempotently, and a second run changes nothing. Shell scripts of `ipa` commands do
not give this, because `ipa user-add` fails when the user exists and each script must handle every combination of
present and absent. `ansible-freeipa` provides it as Ansible roles and modules that compare what exists with what
you declared, and only then change the difference.

This slice covers installation of the collection, the role set for deploying servers, replicas and clients, the module
set for objects, the inventory and secret handling, the rules of idempotence and check mode, and the patterns that make
a policy repository maintainable. It builds on LNX-301-T06 (the objects automated here) and needs Ansible basics.

## History and approaches

Early automation of FreeIPA was shell. The `ipa` CLI is a client of a JSON-RPC API, and administrators wrapped it
in bash, relying on exit codes (the code for "no modifications to be performed" is 1, a trap in scripts that use
`set -e`). The next step used the JSON-RPC API from Python, directly or through the `python-freeipa` library, with
custom reconciliation logic per project. The Ansible community provided the `community.general.ipa_*` modules (user,
group, host, hbacrule, sudorule, and a few others), which cover a limited subset of objects and speak to the server
over HTTP with a session cookie.

The `ansible-freeipa` project, started by Red Hat and FreeIPA developers around 2017, took a different path: modules
that wrap the same internal API as the `ipa` command and run on a host inside the domain (typically an IdM server or
client), plus roles that run the installers (`ipa-server-install`, `ipa-replica-install`, `ipa-client-install`)
with parameters from inventory variables. Its modules are idempotent by design and support `state: present`,
`absent`, `enabled`, `disabled`, with `action: member` to manage membership lists without redefining the object. Early
releases were a git checkout with a roles directory, which users cloned and referenced by path. Later releases became
installable through Ansible Galaxy and through an RPM, and in RHEL 10 the RPM installs only the collection format
under the name `freeipa.ansible_freeipa`; module names must be written with the collection prefix, or covered by
`module_defaults` to keep playbooks short [src: rhel-10-docs 181a48c68bac2a7e]. From RHEL 10.1 this collection is
also reachable under the Automation Hub name `redhat.rhel_idm`, so that playbooks written for either source run
[src: rhel-10-docs e9a1da70b9949d7d].

Partial successes and pitfalls recur in the history. Playbooks that mix `community.general.ipa_*` modules and
ansible-freeipa modules in one repository confuse operators because the argument names differ. Role-based server
installation worked well in labs but required explicit vault management of the directory manager and admin passwords.
Playbooks that depended on a Kerberos ticket on the control node broke when the ticket expired halfway through a long
run. The lesson, adopted in the documentation, is to run modules on a managed IdM host with `ipaadmin_password` supplied
from a vault, or with a keytab, and keep the control node thin.

## Current state

**Installing and structuring.** On a RHEL-family control node: `dnf install ansible-freeipa` (collection under
`/usr/share/ansible/collections/ansible_collections/freeipa/ansible_freeipa`). Elsewhere:
`ansible-galaxy collection install freeipa.ansible_freeipa`, which fetches the same content from Galaxy. Red Hat's
guide requires Ansible 2.15 or later on the control node [src: rhel-10-docs 92c904673863b9d7]. Managed hosts need Python and, for the
modules, the IPA client libraries (installed with `ipa-client` or `ipa-server`), because the modules import the same
Python code as the CLI. A typical repository layout:

```text
inventory/hosts.yml        # ipaserver, ipareplicas, ipaclients groups plus group_vars
group_vars/all/vault.yml   # ansible-vault encrypted: ipaadmin_password, ipadm_password
playbooks/install-server.yml
playbooks/policy.yml
policy/users.yml hbac.yml sudo.yml dns.yml
```

**Roles for deployment.** Roles map to the installers and take the installer's options as variables:

- `ipaserver`: installs the first server. Variables include `ipaserver_domain`, `ipaserver_realm`,
  `ipaserver_setup_dns`, `ipaserver_forwarders`, `ipaserver_auto_forwarders`, `ipaserver_setup_ca`,
  `ipaserver_no_hbac_allow` (which skips creating the `allow_all` rule, a useful security default), plus the
  passwords `ipaadmin_password` and `ipadm_password`.
- `ipareplica`: for hosts listed in the `ipareplicas` inventory group, with `ipareplica_setup_ca`,
  `ipareplica_setup_dns` and `ipareplica_setup_kra`, and `ipaserver` named by `ipaserver` or the inventory
  structure. The role's `ipa_server_*` values can be set per host so each replica takes the right roles.
- `ipaclient`: enrols hosts, either by admin credentials (`ipaadmin_principal`, `ipaadmin_password`), by a
  one-time password per host (`ipaclient_otp`) or a keytab, with `ipaclient_mkhomedir` and `ipaclient_no_ntp`
  options.
- `ipabackup`: runs `ipa-backup`, copies backups off-host, and restores.
- `ipasmartcard_server` and `ipasmartcard_client`: set up smart-card authentication (LNX-301-T10).
- `ipahealthcheck`, `ipatopology` and others added across releases (to verify the current list against the installed version).

The inventory declares topology: hosts in `[ipaserver]`, `[ipareplicas]`, `[ipaclients]`, with `ipaserver_domain`
and `ipaserver_realm` in `[ipaserver:vars]`. A playbook is then `- hosts: ipaserver / roles: - role:
freeipa.ansible_freeipa.ipaserver / state: present`, followed by plays for replicas and clients. Order matters: replica plays
run after the server, client plays after DNS records exist.

**Modules for objects.** The module set mirrors the `ipa` command families: `ipauser`, `ipagroup`, `ipahost`,
`ipahostgroup`, `ipaservice`, `ipadnszone`, `ipadnsrecord`, `ipadnsconfig`, `ipahbacrule`, `ipahbacsvc`,
`ipahbacsvcgroup`, `ipasudorule`, `ipasudocmd`, `ipasudocmdgroup`, `ipapwpolicy`, `ipaconfig`, `ipaautomember`,
`ipaselinuxusermap`, `ipatrust`, `ipaidview`, `ipaidoverrideuser`, `ipaprivilege`, `ipapermission`, `iparole`,
`ipaserver` (checks topology, does not install), `ipatopologysegment`, `ipavault`, `ipacert` and more. Each module takes
`ipaadmin_principal` and `ipaadmin_password` (or a ticket), the object name, its attributes, and `state`. Examples:

```yaml
- hosts: ipaserver
  become: false
  gather_facts: false
  module_defaults:
    freeipa.ansible_freeipa.ipahbacrule: {ipaadmin_password: "{{ ipaadmin_password }}"}
    freeipa.ansible_freeipa.ipasudorule: {ipaadmin_password: "{{ ipaadmin_password }}"}
  tasks:
    - freeipa.ansible_freeipa.ipahbacrule:
        name: db-ssh
        hostgroup: [dbservers]
        group: [dba]
        hbacsvc: [sshd]
        state: present
    - freeipa.ansible_freeipa.ipahbacrule:
        name: allow_all
        state: disabled
    - freeipa.ansible_freeipa.ipasudorule:
        name: dba-restart
        group: [dba]
        hostgroup: [dbservers]
        allow_sudocmdgroup: [pgctl]
        state: present
```

Red Hat's documentation presents the same pattern with an action group, `freeipa.ansible_freeipa.modules`, to set
the admin password once for every module in a playbook, and it works through the HBAC and sudo scenario where `jane`
reaches only one host, `john` another, and the `admins` group everything
[src: rhel-10-docs 9984e8569c711253].

**Idempotence and check mode.** Each module reads the current object, computes the difference with the arguments, and
changes only attributes that differ, reporting `changed: false` if none do. The consequences are important in practice.
Attributes you do not mention are left alone, so a task is not a full definition of the object. Lists such as
`group:` are replaced as a whole on `state: present` unless `action: member` is used, in which case they are
added or (with `state: absent`) removed; mixing the two styles without care deletes members. Module `check_mode`
support exists for most modules (`ansible-playbook --check --diff`), which is how policy reviews work in CI. Removal is
explicit (`state: absent`), which means a policy repository that only lists present objects will never clean up; to
get pruning, query the domain (for instance with the `ipa` CLI, or the `ipaconfig`/`find` style modules
[src: rhel-10-docs 92c904673863b9d7]) and compare with the repository, or accept that deletions are manual steps.

**Secrets.** `ipaadmin_password` and `ipadm_password` go in `ansible-vault` files or an external secret manager
via lookup plugins; with `no_log: true` on tasks that print them. A better pattern for unattended runs is a dedicated
automation user with a narrow role (IdM RBAC: a role containing only the privileges for HBAC and sudo
management), authenticated by keytab, instead of `admin`. Client enrolment with one-time passwords (`ipaclient_otp`) avoids
distributing the admin password to hosts at all.

**Execution context.** The modules authenticate through the server's API. `ipaapi_context: server` means run on an
IdM server with root, using the local LDAP socket; `client` (default) runs on an enrolled client using the user's
credentials. Runs fan out through `hosts:`; for objects, target a single server (`run_once: true`), since replication
carries the change to the others. Long playbooks should use `ipaadmin_password` rather than a pre-obtained ticket, as
tickets expire.

**Testing a policy repository.** Treat the repository like code. A cheap pipeline has three stages. First, `yamllint`
and `ansible-lint` catch syntax and module-argument mistakes, including collection names written without the prefix.
Second, a throwaway domain (two containers or virtual machines running the `ipaserver` role) receives the full policy;
the job asserts that a second run reports no changes and that `ipa hbactest` returns the expected verdicts for a table
of user, host and service combinations kept next to the rules. Third, the same playbook runs with `--check --diff`
against production for the reviewer. The HBAC verdict table is the most valuable artefact: it turns a rule change from
"looks right" into an executable statement, and it catches the classic regression where a new rule re-enables broad
access. Keep module arguments in plain data files loaded with `include_vars`, so that adding a rule is a
data change that needs no playbook edit, and keep one task per object type so that failure messages name the type.

**Related automation on the AD side.** For direct AD joins (no IdM), Red Hat provides the `ad_integration` system role,
which is the equivalent of the `ipaclient` role for AD members, with a note that IdM environments should use
ansible-freeipa [src: rhel-10-docs 157d2e05d2589a03].

**Generalised pattern.** Describe desired state declaratively; run an engine that reads, diffs and applies; keep the
description in version control; review changes as diffs; run the engine regularly to detect drift. This is the
infrastructure-as-code loop, applied to an identity domain.

## Assessment: the good, the bad and the ugly

**Good.** The same playbook that built a lab builds production, so tests of policy changes in staging are
meaningful. Pull requests become the audit trail for access policy: who proposed the HBAC change, who approved it.
Rebuilding a replica becomes a repeatable job. Idempotence means that running the policy playbook nightly acts as
drift detection (`changed` results point at manual edits). Module coverage is broad, so most of the web UI's surface
is reachable. Because the modules reuse the IdM Python libraries, behaviour matches the CLI.

**Bad.** The modules are not stand-alone API clients: they need Python IPA libraries on the managed node and a version
compatible with the server, so a control node with a different Python or IPA version can fail with import errors.
Naming and parameters differ subtly from the CLI (`allow_sudocmdgroup` versus `--sudocmdgroups`). List replacement
versus membership actions is the commonest source of bugs. Large domains make full-policy runs slow, since each
object is a round trip. Documentation is spread between the project's README files, the Red Hat guides and the
collection's module documentation. The roles for server installation do not upgrade or maintain servers over their
lifetime, so version upgrades remain manual procedures.

**Ugly.** Vault passwords committed in clear in a forgotten inventory. Playbooks that run as `admin` and become
the weakest link in the domain, since whoever controls the CI runner controls all identities and the CA. Drift
between declared and actual policy that goes unnoticed because the playbook only lists what to add and never runs
`--check` on a schedule. Deleting a group in the repository without realising that rules reference it, which is rejected by the server
or, worse, removes dependent memberships. The `ipaserver` role will happily reinstall over a half-failed install
if inventory variables change, which can destroy a domain; mitigate with explicit guards and a separate
"bootstrap" playbook that is not part of the regular run.

Mitigations: least-privilege automation identity; separate bootstrap and policy playbooks; `--check --diff` in the pull
request pipeline and a scheduled drift job; `no_log`; tests in a throwaway domain (containers or VMs) before merge;
pin the collection version and the Ansible version in a requirements file.

## Applications beyond this domain

The reconciliation pattern is the heart of Kubernetes controllers and Terraform: declare, plan (diff), apply. The
RHEL system roles generalise it to firewalls, SELinux, time and storage, with `ad_integration` as the AD sibling of
`ipaclient`. Any directory-like service with an API (LDAP, GitLab groups, cloud IAM, Grafana teams) can be managed in
the same style, and `ansible-freeipa` is a good worked case of wrapping an imperative CLI as idempotent modules. The
discipline of policy as code, with review, tests and drift detection, is the same one used for firewall rules and for
Kubernetes RBAC.

## Examples

**Bootstrap and policy.** Inventory: `ipa1.example.com` in `[ipaserver]`, `ipa2` and `ipa3` in `[ipareplicas]`, with
`ipaserver_domain=example.com`, `ipaserver_realm=EXAMPLE.COM`, `ipaserver_setup_dns=true`, `ipaserver_forwarders=[10.0.0.1]`
and `ipaserver_no_hbac_allow=true`. `ansible-playbook -i inventory install.yml` runs the server and replica roles,
then clients. A second playbook, `policy.yml`, creates `dba` users and groups, the `db-ssh` HBAC rule and the sudo rule.
Re-running `policy.yml` shows zero changes.

**Failing: member list replaced.** A task sets `ipagroup: name: dba, user: [alice, bob]` with the default
`state: present`, and an administrator earlier added carol by hand. The task removes carol. Using `action: member` for
membership edits, or listing every member in the repository, resolves it. The check run (`--check --diff`) would have
shown the change.

**Failing: import error.** Running `ipauser` from a laptop control node fails with `ModuleNotFoundError: No module
named 'ipalib'`. The module executes on the target, and the target is an unenrolled host. Point `hosts:` at an IdM
server or client and set the context properly.

**Failing: ticket expired.** A long playbook starts with a Kerberos ticket from `kinit admin` on the target, and tasks near the end
fail with `Ticket expired`. Supply `ipaadmin_password` through the vault so each module authenticates itself, or use
a keytab.

**Drift detection.** A nightly pipeline runs `ansible-playbook policy.yml --check --diff` and fails the job if any
task reports `changed`. A manual HBAC edit made during an incident at 02:00 is surfaced the next morning and either
adopted into the repository or reverted.

## Related problems and ideas

Alternatives: `community.general.ipa_*` modules for small jobs; the `ipa` CLI in scripts with explicit existence
checks; Terraform providers for FreeIPA (community-maintained, uneven); Puppet and Salt modules for IPA; and operators
that sync identity from an HR system (SCIM or LDAP sync) so that users never appear in a playbook at all. A common
architecture splits responsibilities: people and group membership flow from an HR or IGA system through scripts, while
HBAC, sudo and DNS stay in Git with ansible-freeipa. Related problems include managing the Ansible control node's
own identity (see LNX-301-T02 for keytab-based authentication) and extending IdM to Windows hosts
(LNX-302-T08).

## Active research

Project work includes keeping module parity with new FreeIPA versions, more modules for newer objects (certificate
mapping rules, external IdP configuration, passkeys), better support for check mode and diff output, and tests that
build a real IdM domain in CI. The move to the `redhat.rhel_idm` and `freeipa.ansible_freeipa` namespaces is
part of an ongoing consolidation [src: rhel-10-docs e9a1da70b9949d7d]. Open questions: how to prune unmanaged
objects safely, how to model secrets better than static passwords, and whether to expose a declarative API on the server
itself.

## Future direction

Expect further alignment between the upstream collection and Red Hat's Automation Hub name, and more roles for
operational tasks (health checks, backup rotation, upgrades). RHEL 10.1 made the IdM-to-IdM migration tool a fully
supported feature (`ipa-migrate`), which fits automated environment cloning [src: rhel-10-docs 181a48c68bac2a7e].
Watch the collection's release notes at the upstream project, the minimum Ansible version (2.15 in the current RHEL
guide), and changes to FreeIPA API versions that modules track.
