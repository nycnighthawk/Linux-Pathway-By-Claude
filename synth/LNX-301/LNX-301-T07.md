# Trusting Active Directory from IdM: a cross-forest trust

## Define the problem

An organisation with a Windows Active Directory forest and a population of Linux servers has two ways to give the Linux
estate central identity. It can join every Linux host directly into AD (LNX-301-T04, T05), which makes AD the single
authority and leaves Linux administrators with no place to put Linux-specific policy. Or it can run a Linux-native
identity server (IdM, LNX-301-T06) and let it make friends with AD. The second path wins when the Linux team wants
its own HBAC rules, sudo rules, SSH key store, certificate authority and POSIX attributes without asking the AD team
for schema changes, or when Linux is run by a different business unit with a different security regime.

The cross-forest trust is the mechanism that lets both populations coexist. Users who live in AD log in to IdM-managed
Linux hosts with their AD passwords and Kerberos tickets; IdM never stores their credentials and AD never needs to
know about the Linux hosts. The hard parts are specific: AD speaks SIDs, IdM speaks POSIX IDs, so a mapping has to be
decided; the two KDCs must trust each other's cross-realm tickets; DNS must route queries for each namespace to
the right authority; and the permission system must let AD groups map to IdM groups for HBAC and sudo.

Failure looks like: `id user@ad.example.com` works on the IdM server but not on clients; the trust shows as
established but AD users cannot get a Kerberos ticket for a Linux service; a user logs in but cannot sudo because the
group membership came through the wrong path; or the trust is deleted by a Windows administrator who did not
recognise the trusted-domain object. This slice covers the architecture, setup, the identity and policy mapping, and
the most useful verification commands. It is a supervised, manual lab (a real Windows forest is required) as
in LNX-301-T05.

## History and approaches

Before trusts, mixed environments used one of three patterns. The first, a *shadow directory*, synchronised AD
users into the Linux directory with a tool such as the 389 DS **WinSync** plug-in: password changes in AD were
captured with a Password Sync service on each domain controller, and users were copied into the Linux side. It worked
but doubled every identity, required agents on DCs, and broke whenever a schema or attribute changed. The second was
the **Kerberos cross-realm trust** between an MIT realm and AD, a one-way trust configured with `netdom`: tickets
crossed realms, but identity (names, groups, UIDs) did not, so a separate user database was still needed on the
Linux side, and group authorisation, which in AD is carried in the PAC, was unavailable. The third was to join every
host to AD with winbind or an agent (T04).

The FreeIPA 3.0 release (2012) added the *cross-forest trust* with a design that treated AD as a separate forest and
IdM as another, using Samba's trust-related code on the IdM side. The IdM server presents itself to AD as a forest
with a single domain. A forest trust links the AD forest root to the IdM domain, and Windows can therefore treat the
IdM domain like any other foreign forest, with SID filtering and name suffix routing in force, and the IdM Kerberos
KDC handles AD users' cross-realm tickets and consumes the PAC to learn their group SIDs. Identity for AD users is
exposed through the IdM server itself: SSSD on IdM clients asks the IdM server (via an extended operation or a
compat tree) rather than contacting AD directly, so the clients never need an AD account or even a route to AD.

Partial successes and limits are documented in Red Hat's planning material. IdM supports **one-way trusts** in which
IdM trusts AD, so AD users reach IdM resources; **two-way trusts** are supported, but because IdM does not
implement the global catalog service AD expects, IdM users cannot be given access to AD resources in general, so a
two-way trust is functionally almost the same as one-way [src: rhel-10-docs fa38c2a3f33671b1]. Besides forest trusts,
IdM can set up an **external trust** to a single AD domain, rather than the forest root
[src: rhel-10-docs ce9fb61afd9c78ae]. The implementation uses Samba for the trust object and for the RPC channel to
AD, which led to a recognisable design of "trust controllers" and "trust agents".

Lessons that pushed the field: copy no secrets across directories; keep identity lookups server-side to avoid
firewall and DNS complexity on clients; treat the SID as the stable identity and POSIX IDs as a local view; and give
administrators a single command to create and verify the trust.

## Current state

**Roles of IdM servers.** A *trust controller* is an IdM server that runs the Samba components needed to
establish a trust, answer AD's Netlogon and RPC calls and authenticate AD users. A *trust agent* is a server that can
resolve AD identities for clients but does not process Kerberos for AD users. An ordinary IdM server does neither, so
clients of that server see no AD users. IdM requires at least one controller; in multi-site topologies, add controllers
or agents at each site and place AD DCs in the same site, because lookups follow site affinity
[src: rhel-10-docs 2f4bc7d5d78aef63].

**Prerequisites.** Both sides need working DNS for each other. The IdM DNS gets a forwarding zone:
`ipa dnsforwardzone-add ad.example.com --forwarder=10.1.0.10 --forward-policy=only`, and the AD DNS gets a conditional
forwarder for the IdM domain. The two domains must be different DNS namespaces (not parent and child of each other),
and the NetBIOS names and SIDs must be unique. Times must agree to within five minutes. The following ports must be
open from the IdM controller to the AD DCs and back: DNS 53, Kerberos 88 and 464, LDAP 389 and 636, the global catalog
3268 and 3269, RPC endpoint mapper 135, SMB 445, NetBIOS 137-139 where needed, and the dynamic RPC high ports (49152
to 65535 by default on current Windows, narrowed by firewall policy). The IdM server should use `server-role-find`
to list its roles.

**Configuring IdM as a trust controller.**

```text
dnf install ipa-server-trust-ad
ipa-adtrust-install --add-sids          # prompts for admin password, NetBIOS name, SIDs
ipa dnsrecord-find example.com | grep -i _ldap._tcp.Default-First-Site-Name._sites.dc._msdcs
```

The installer starts Samba's `smb` and `winbind` services for the trust only (not for file sharing), creates the
`cn=ad,cn=trusts` containers, generates a SID for the IdM domain, and adds the SID-related attributes to existing
users and groups (the `--add-sids` argument, or run `ipa config-mod` and the SID generator task afterwards). Check the
firewall (`firewall-cmd --add-service=freeipa-trust`) and confirm that SRV records for `_kerberos._tcp`,
`_ldap._tcp` exist under the IdM domain, because AD looks them up when talking back.

**Creating the trust.**

```text
kinit admin
ipa trust-add --type=ad ad.example.com --admin Administrator --password
ipa trust-show ad.example.com
ipa trustdomain-find ad.example.com
ipa trust-fetch-domains ad.example.com
```

The administrator account used is only for creating the trust object on both sides, and a shared secret is stored
in the trust, so the AD password is not kept. The default `--range-type` for the AD domain is `ipa-ad-trust`, meaning
IdM allocates a UID/GID range for the AD domain and derives IDs from the RIDs of AD SIDs, which is the same idea as
SSSD's ID mapping (LNX-301-T08). The alternative `--range-type=ipa-ad-trust-posix` makes IdM read the `uidNumber` and
`gidNumber` attributes that AD already stores (Identity Management for UNIX), and requires the range to be consistent
with those values; the choice cannot be altered cheaply later. `--two-way=true` creates a two-way trust. On success,
the domain appears in `ipa trustdomain-find` with its sub-domains (child domains of the AD forest), and the forest
topology is fetched on demand.

**What AD users get.** An AD user such as `jsmith@ad.example.com` becomes visible through IdM clients with the fully
qualified name; `id jsmith@ad.example.com` shows UID in the IdM-allocated range and groups including AD groups
mapped by SID. Login uses `ssh jsmith@ad.example.com@client.example.com`, with passwords verified through the IdM KDC
which proxies the cross-realm authentication, or Kerberos single sign-on when the user holds an AD TGT: the client
obtains `krbtgt/EXAMPLE.COM@AD.EXAMPLE.COM`, a cross-realm TGT issued by AD, then a service ticket from the IdM KDC.
Client `krb5.conf` has `[capaths]` entries (generated by `ipa-client-install` or SSSD's krb5 helper) so the
client knows the path of trust, and `auth_to_local` rules map `jsmith@AD.EXAMPLE.COM` to the IdM name.
Check with `klist` after `kinit jsmith@AD.EXAMPLE.COM` then `ssh -K`.

**Authorisation for AD users.** HBAC and sudo rules in IdM can name only IdM groups. To use AD identities in them,
create a non-POSIX **external group** that holds AD members (`ipa group-add --external ad_admins_external`,
`ipa group-add-member ad_admins_external --external 'ad.example.com\Domain Admins'`) and a POSIX group that contains
the external group (`ipa group-add ad_admins`, `ipa group-add-member ad_admins --groups=ad_admins_external`). The POSIX
group then appears in `ipa hbacrule-add-user --groups=ad_admins` or in sudo rules. AD users may also receive IdM
overrides (`ipa idoverrideuser-add 'Default Trust View' jsmith@ad.example.com --shell=/bin/zsh --sshpubkey=...`),
which set shells, home directories and SSH keys on the Linux side without touching AD. ID views and overrides apply
per client or client group, and are a staple of migrating existing hosts with hard-coded UIDs. Default behaviour is
that AD users in the trust receive an automatically generated home like `/home/ad.example.com/jsmith`.

**Verification and health.** `ipa-healthcheck --source=ipahealthcheck.ipa.trust` runs the trust tests; an empty list `[]`
means no findings, and Red Hat recommends running it on every IdM server when diagnosing
[src: rhel-10-docs bce5884685ef72dc]. Other checks: `ipa trust-show` should list `Trust status: Established and
verified`; `ipa trust-fetch-domains`; `wbinfo --online-status` and `wbinfo -u` on the controller; `sssctl domain-list`
and `sssctl domain-status ad.example.com` on a client; `kvno host/client.example.com@EXAMPLE.COM` from an AD user's
credentials; and on AD side `Get-ADTrust` or the Active Directory Domains and Trusts console, `netdom trust` for
validation. If the controller reports `Trust verification failed with error: NT_STATUS_...`, the NT status code
usually points at DNS (`NT_STATUS_NO_SUCH_DOMAIN`), time or RPC ports.

**Samba's part.** The `net` tool on the trust controller exposes the underlying operations, for instance `net rpc
trustdom list` to show trust relationships; its manual page describes the family of trust-domain subcommands and the
way a trust account is created [src: samba-docs 02c3b224d7f7f733]. The `idmap_ad`, `idmap_rid` and `idmap_autorid`
back ends are Samba concepts for the same mapping choice that IdM makes with its own ranges
[src: samba-docs 1f2e710347fbfea6] [src: samba-docs a29f71b32557d26f] [src: samba-docs 3be468ed7476d800].

**Generalised pattern.** Federate identity, not credentials. Each domain stays authoritative for its own principals.
A trust broker translates identifiers (SIDs to local IDs) and maps remote groups to local roles at the boundary.
Authentication is delegated by cross-realm tickets, and authorisation is evaluated locally on the translated
identity.

## Assessment: the good, the bad and the ugly

**Good.** Linux administrators get full control over Linux policy without schema changes in AD. AD users keep one
password and have SSO to Linux. Clients need no AD enrolment, no AD ports, and no per-host computer account, so
there is nothing to clean up in AD when hosts come and go in autoscaling groups. Security teams on both sides keep
ownership of their directory. The trust can be monitored from one place, and IdM overrides allow flexible
per-host attributes.

**Bad.** The architecture has many moving parts: Samba on the IdM server, additional DNS configuration on both
sides, a firewall matrix, SID generation tasks and the range design. IdM trust controllers are more exposed than other
servers because they run SMB and RPC services. Some AD features are not reachable from IdM users (no global
catalog), so a two-way trust has limited use. Nested group expansion and group-policy-based access in AD are not
evaluated by IdM clients, so rules must be re-expressed as IdM HBAC. Versions matter: trust support on new
Windows Server releases follows a lag, and security hardening (RC4 retirement, PAC validation changes) breaks trusts
until patched. Documentation for administrators from the Windows side is thin.

**Ugly.** The ID range choice is close to irreversible: changing from `ipa-ad-trust` to a POSIX-attribute based range
after files have been written changes every owner. Trusts established with a weak trust password (older than AES) or
with RC4 only enforce lower security and fail when Windows changes defaults. A rogue or mistaken delete of the trust
object on the AD side leaves a half-broken state where IdM thinks the trust exists. AD users added to external groups
by SID, not by name, are hard to audit in a Linux CLI. Replication of trust data between IdM servers happens, but
some state (the SSSD caches, the Samba secrets database on the controller) is local, so a rebuilt controller needs
a re-run of `ipa-adtrust-install`. During outages of the AD DCs, logins of cached users continue only as far as the
SSSD cache on the client allows, and the first login of a new AD user fails.

Mitigations: use `ipa-healthcheck`, two trust controllers per site, name the AD-facing groups consistently
(`ad_<role>_external`), document the range design, restrict the SID filtering lists, run lab tests before each
Windows or IdM major update, and keep a runbook with `ipa trust-show`, `wbinfo`, `sssctl` and `kvno` steps.

## Applications beyond this domain

The pattern of a transparent identity federation with local policy mapping appears in OIDC federation (identity
providers and relying parties), SAML federation in higher education (eduGAIN), cloud workload identity federation
(a Kubernetes service account assuming an AWS role), and multi-forest AD itself. The SID-to-local-ID derivation reappears
in user namespace ID mapping for containers (`/etc/subuid`, `newuidmap`) and in Samba's idmap back ends. Cross-realm
Kerberos shows up in Hadoop clusters that trust a corporate realm. Rootless container tooling and audit baselines,
which reference `newuidmap` and `newgidmap`, share the idea that numeric IDs are a local view of an identity
[src: compliance-as-code 05e0cd3d47262a67].

## Examples

**A working trust, end to end.** IdM domain `example.com` (realm `EXAMPLE.COM`, servers `ipa1`, `ipa2`); AD forest
`ad.example.net`. On `ipa1`: `ipa-adtrust-install --add-sids`; DNS forward zone for `ad.example.net`; on the AD DC, a
conditional forwarder to `ipa1`. `ipa trust-add --type=ad ad.example.net --admin Administrator --password`. `ipa
trust-show` reports established. `ipa-adtrust-install --add-agents` is not needed for the clients of `ipa1`; for a
remote site, `ipa-adtrust-install` is run on a second server. On a client, `id jsmith@ad.example.net` returns UID
`1820401105` (RID plus the range base). The AD group `Linux Admins` is added to `ad_admins_external` and
`hbacrule` `ad-ssh` allows `ad_admins` on `sshd` for `all` hosts. `hbactest --user=jsmith@ad.example.net
--host=client.example.com --service=sshd` returns `Access granted`.

**Failing: DNS.** `ipa trust-add` returns `Cannot find specified domain or server name`. The IdM server resolves
`ad.example.net` by the generic resolver which has no forwarder; fix with a forward zone, and test with `dig SRV
_ldap._tcp.dc._msdcs.ad.example.net @127.0.0.1` on `ipa1`.

**Failing: clients see no AD users.** `id jsmith@ad.example.net` works on `ipa1` but not on `client2`. `client2` was enrolled
against `ipa3`, which is an ordinary IdM server, not a trust agent. Run `ipa-adtrust-install` on `ipa3` (to make it
a controller) or point `client2` at an agent with `ipa-client-install --server`. Check with `ipa server-role-find
--role='AD trust agent'`.

**Failing: SID filtering and groups.** After a Windows security patch, AD users lose group membership on Linux. The PAC
signature fails because the trust uses RC4. Reset the trust password after raising the trust's supported encryption
types (`ksetup /SetEncTypeAttr` or `netdom trust ... /EncryptionTypes`), then `ipa trust-fetch-domains` and
`systemctl restart sssd` on controllers (to verify the exact Windows commands against the current guidance).

**Failing: user is in a group but sudo is denied.** The group is only an external group. The sudo rule referenced it
directly; sudo rules accept POSIX groups only. Nest the external group in a POSIX group and use that.

## Related problems and ideas

Other ways to bridge AD and Linux: direct join with SSSD or winbind (T04 and LNX-302-T02) which gives GPO access and
simplest operations for AD-led shops; AD with Samba-based DCs and no trust; a one-way Kerberos cross-realm trust
for services only; or Entra ID (formerly Azure AD) login for Linux VMs through its extension, with IdM kept for
non-cloud assets. Related ideas: ID views and ID overrides to migrate to or from AD without renumbering;
external IdP support in IdM so that users sign in via an OIDC provider and then receive a Kerberos ticket; and
PKINIT and smart cards across trusts (LNX-301-T10). A question to ask early: does the Linux estate need its own identity
authority? If not, joining is simpler.

## Active research

Work in the FreeIPA and Samba projects concentrates on keeping trusts functional as Microsoft tightens Kerberos
(PAC validation, enforcement of AES, removal of RC4 and NTLM), on supporting Windows Server's newer forest
functional levels, and on making the trust controller role safer by reducing the exposed surface of the Samba
components. Researchers examine the security of cross-realm tickets and the risk of SID history abuse across
trusts. Open questions: whether a global catalog service for IdM will ever land to make two-way trusts useful, and
how best to give Linux a first-class view of AD group policy.

## Future direction

Expect gradual move away from NTLM and RC4 on trusted paths, which will require updated trust passwords and AES
trust types in existing deployments (to verify the dates for each Windows Server release). IdM and Samba packages
will track the AD changes with lag, so the practitioner's watch-list includes release notes of both, Microsoft's
Kerberos hardening timeline, and the IdM Healthcheck trust checks that surface problems before users notice them.
External IdP integration will likely lessen the need for AD trusts in cloud-first organisations.
