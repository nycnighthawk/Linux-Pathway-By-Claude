# Joining Linux to a Samba Active Directory domain with realmd and adcli

## Define the problem

An Active Directory domain is more than a user list. It is DNS records that tell clients where services live, an LDAP
tree that stores users, groups and machine accounts, a Kerberos realm that issues tickets, and a set of remote
procedure call interfaces for machine enrolment and password change, all knit together by conventions about names and
time. A Linux host that wants to be a first-class member must do four things: find the domain controllers, create or
reuse a **computer account** with a secret only that host and the domain share, store that secret as a Kerberos
keytab, and configure the identity and authentication stack (SSSD, nsswitch, PAM, Kerberos) to use the domain.
Doing it by hand means editing `krb5.conf`, `sssd.conf`, `nsswitch.conf`, PAM files and the keytab, in the correct
order, with matching names. People make mistakes there, and each mistake produces a login failure that points
nowhere near the cause.

`realmd` and `adcli` exist to compress this to a few commands, with a consistent result that SSSD can use. The
second half of the problem is the server. Many sites, labs and CI systems cannot or will not run Windows Server, but
need a real AD-compatible domain to test against or to run in production: Samba 4 provides a domain controller that
speaks the same LDAP, Kerberos and RPC dialects. The slice here is therefore two-sided: provisioning and checking a
Samba AD DC enough to be joined, and joining a Linux member to it with `realm join`, `adcli join` and the SSSD AD
provider. Joining a genuine Windows domain adds permission and policy concerns, handled in LNX-301-T05; Samba member
servers using winbind are in LNX-302-T02.

Failure shapes: `realm discover` finds nothing because the client's resolver does not point at a DC; `realm join`
fails with a Kerberos error because the clock is wrong or the crypto policy forbids the encryption type the DC uses;
the join succeeds but `id user@domain` returns nothing because SSSD cannot reach LDAP or the ID mapping range is
exhausted; logins work for a week and then stop because the machine password rotated and the keytab was not updated.

## History and approaches

Early AD integration for Linux used Samba's `winbindd` with `net ads join`. Samba 3 could join an NT domain, then
(from 3.0, 2003) an AD domain as a member server, using `net ads join` to write the machine account and
`pam_winbind`/`nss_winbind` for users. It worked and is still supported, but is configured from `smb.conf` with
idmap back ends that are easy to get wrong, a separate stack to the rest of the Linux identity world.

Vintela Authentication Services and other commercial agents did the same for enterprises, and the open-source answer
from Likewise (`likewise-open`, with `domainjoin-cli`) was popular on Ubuntu for years before being abandoned.
`sssd` entered with its AD provider in the 1.9 era (2012) and became the Red Hat default path; `realmd` (Stef Walter,
2012) was written as a D-Bus service and command-line tool that discovers a domain and picks the right set of
packages and configuration, so that administrators and installers do not need to know whether it is SSSD or
Samba. `adcli` (also by Stef Walter) is the library and command that actually performs the join and password update
against AD, creating the computer object and managing the keytab. That separation matters: `realm join` is a
front-end, `adcli` is the engine, and SSSD is the consumer.

The server side has its own history. Samba 3 could not be a domain controller for AD. A decade of work by Andrew
Tridgell and the Samba Team, driven by the reverse-engineered Windows protocol documents published by Microsoft
after the 2007 EU settlement, produced Samba 4.0 in December 2012 with a full AD DC: LDAP (via a built-in LDB
database), Kerberos (embedded Heimdal), DNS, and the RPC services. The Heimdal base meant lagging behind MIT features;
a build option for MIT Kerberos arrived in the 4.7 to 4.9 period and became a supported alternative, though Red
Hat does not ship Samba as a DC package (to verify for the current release) [src: archwiki 91acf37df973d803]. Domain
functional levels were raised release by release; Samba 4.x supports Windows Server 2008 R2 level fully and later
levels with caveats (to verify the present state).

Lessons the field took from these approaches are visible in the tools: recognise the domain by DNS, never trust
manual config for secrets, automate the machine account lifecycle, and treat the ID mapping decision as architectural
(decide once, because UID changes after the fact break file ownership).

## Current state

**Prerequisites that cause most failures.** The client must resolve the domain through a DNS server that serves the AD
zone (the DC itself, or a forwarder chain that reaches it); time must be within five minutes (chrony pointing at the
DC or the same source); and the client needs outbound reachability to the DC on DNS 53, Kerberos 88 and 464, LDAP 389
and, for a Windows forest, the global catalog on 3268, plus SMB 445 for some join steps. The Rocky Linux guide
presents this list and the NetworkManager command to set the DC as the resolver
[src: rocky-docs 2309082eef6d21e8].

**Discovery.** `realm discover ad.example.com` queries SRV records (`_ldap._tcp.dc._msdcs.ad.example.com`,
`_kerberos._tcp...`), probes with CLDAP, and prints the realm name, domain name, whether the domain is configured,
the `server-software` (active-directory or ipa), `client-software` (sssd or winbind) and the required packages. The
`server-software` field identifies a Samba DC as active-directory, since it advertises the AD service roles. Common
output on a fresh machine is `configured: no` plus a package list that `realm join` installs on demand.

**Samba DC provisioning, in short.** The server is created with `samba-tool domain provision --use-rfc2307
--realm=AD.EXAMPLE.COM --domain=AD --server-role=dc --dns-backend=SAMBA_INTERNAL`. The `--use-rfc2307` option adds
the RFC 2307 POSIX attributes (`uidNumber`, `gidNumber`, `loginShell`, `unixHomeDirectory`) to the schema so that
numeric IDs can be stored. The built-in DNS is simplest; BIND9_DLZ is the alternative when DNS must be shared with
other zones. After the provision, `/var/lib/samba/private/krb5.conf` is copied to `/etc/krb5.conf`, the service
`samba-ad-dc` is started, and checks run: `host -t SRV _ldap._tcp.ad.example.com`, `kinit administrator`,
`smbclient -L localhost -U%` and `samba-tool domain level show`. Users are added with `samba-tool user create`. The
Arch wiki walks the full provisioning path with the DNS and DHCP-integration variants
[src: archwiki df2e16483017fa5e].

**Joining with realmd.** The commands are short.

```text
realm discover ad.example.com
realm join --user=administrator ad.example.com
id alice@ad.example.com
realm list
```

`realm join` does the following in order: it discovers the domain, installs missing packages, writes `/etc/krb5.conf`
fragments, obtains a TGT as the join user, creates the computer account through `adcli`, writes
`/etc/krb5.keytab` with `host/` and `<HOSTNAME>$` principals, generates `/etc/sssd/sssd.conf` with the AD provider, and
adjusts nsswitch and PAM through `authselect` (or `pam-auth-update` on Debian). Useful options:
`--computer-ou='OU=Linux,OU=Servers,DC=ad,DC=example,DC=com'` places the account in an organisational unit;
`--os-name`, `--os-version` set the stored operating-system attributes; `--user-principal` sets the account's UPN;
`--membership-software=samba --client-software=winbind` selects the Samba stack instead of SSSD; `--one-time-password`
joins using a pre-staged account; `-v` prints everything. The RHEL documentation and the Rocky guides both describe
this flow, and note that after joining, `getent passwd administrator@ad.example.com` is the standard first test
[src: rhel-10-docs a971298263db2a05] [src: rocky-docs ea9dea3e2e1b4fc4].

**What adcli does directly.** For automation or for hosts without realmd, `adcli info ad.example.com` shows
discovery results; `adcli join -D ad.example.com -U administrator --domain-ou=... --host-fqdn=host.ad.example.com`
creates the account and keytab; `adcli update` rotates the machine password and refreshes the keytab (SSSD calls the
same logic on a schedule, controlled by `ad_maximum_machine_account_password_age`, 30 days by default); `adcli
delete-computer` removes the account. Because adcli creates the account with a random password, no human ever sees
the machine secret. Kerberos-secured join requires the encryption type negotiated with the DC. When a Samba or
Windows DC supports only AES, the client crypto policy must allow AES; when an older DC offers RC4 only, RHEL's
`update-crypto-policies --set DEFAULT:AD-SUPPORT` re-enables it at a documented security cost
[src: rocky-docs 1df1064a4ac8c009].

**What SSSD does afterwards.** The generated `sssd.conf` looks like this:

```text
[sssd]
domains = ad.example.com
services = nss, pam

[domain/ad.example.com]
id_provider = ad
access_provider = ad
ad_domain = ad.example.com
krb5_realm = AD.EXAMPLE.COM
realmd_tags = manages-system joined-with-adcli
cache_credentials = True
fallback_homedir = /home/%u@%d
default_shell = /bin/bash
ldap_id_mapping = True
use_fully_qualified_names = True
```

`ldap_id_mapping = True` (the default) makes SSSD derive UIDs from the user's SID: each domain receives a slice of a
large range (200000 values by default, starting at `ldap_idmap_range_min` 200000), and the same SID gives the same
UID on every SSSD host with the same configuration. Setting it to False makes SSSD use the `uidNumber` and
`gidNumber` stored in the directory, which is how a Samba DC provisioned with `--use-rfc2307` normally works
[src: rhel-10-docs e5f6fffc0c7e3e8a]. This choice, and its consequences for file ownership across hosts, is the main
design decision of the whole join; it has its own topic in LNX-301-T08.

**Access control after joining.** By default, `access_provider = ad` honours the AD account state (disabled,
expired). Local restrictions come from `realm permit` and `realm deny`: after `realm permit alice@ad.example.com`
the domain becomes default-deny except for listed users and groups (`-g` for groups, `--all` to reset). Red Hat
recommends this default-deny style over a blanket permit [src: rhel-10-docs 81ffb979125be312]. Finer control uses GPO
evaluation (`ad_gpo_access_control`, enforcing by default in recent releases but with a Samba DC the GPO file shares
must be reachable over SMB, which makes it a frequent source of denied logins with a message about `SYSVOL`).

**Differences when the DC is Samba.** Samba does not implement a true global catalog on port 3268 in the Windows
sense; SSSD copes because it falls back to port 389 (`ad_enable_gc = False` avoids the delay). Some Windows-only
attributes and tokenGroups behaviours are incomplete, so group resolution that depends on `tokenGroups` can differ.
The `msDS-SupportedEncryptionTypes` defaults and the Heimdal/MIT Kerberos choice on the DC affect which enctypes
the client can use. SYSVOL replication between Samba DCs is not DFS-R; a manual or rsync approach is required
(LNX-302-T03). None of this changes the client commands; it changes which options are needed to quiet warnings.

**Generalised pattern.** Joining is a bootstrap of trust: discover the authority over DNS, authenticate as someone
allowed to enrol machines, create a machine identity with a random secret, store the secret where only root reads it,
and have a resolver daemon use it to act on the machine's behalf. The same sequence appears in `ipa-client-install`
(LNX-301-T06).

## Assessment: the good, the bad and the ugly

**Good.** A join is a minute of work for an administrator, with one command and reproducible output. Hosts become
usable in AD with SSO, group-based `sudo` and `ssh` access, and no passwords stored locally. Samba as a DC means a
real AD can run in a lab or small company on Linux hardware, patched through normal channels, without per-user CAL
licensing. The split of realmd, adcli and SSSD means each can be debugged alone: `realm discover` tests DNS and
discovery, `kinit -k 'HOSTNAME$@AD.EXAMPLE.COM'` tests the keytab, `getent passwd` tests the full identity path.

**Bad.** The default experience hides assumptions: that DNS is correct, that the host name is a valid FQDN with at
most 15 characters in its NetBIOS form (a longer hostname is truncated and can clash), that the join account has
permission to create computer objects, and that the host's `/etc/hosts` does not map its name to `127.0.1.1`. Debian-family
hosts with that entry generate the wrong principals. Ubuntu, RHEL and SUSE differ in package names and in how
`authselect`, `pam-auth-update` and `pam_mkhomedir` are managed. `realm join` leaves behind a keytab and an AD object;
if the host is reinstalled with the same name without `realm leave` or deleting the object, rejoining fails or
reuses an account with surprising permissions. With Samba, upgrade paths for the DC are narrow: you must upgrade one DC
at a time and keep schema and functional-level changes in step.

**Ugly.** The machine account password is the host's identity. Anyone with root on the host can read the keytab and
act as the machine in the domain; in AD this is also a path to enumerate users and, with weak delegation settings,
to escalate. Machine password changes that fail silently (the DC unreachable at rotation, a snapshot restored to an
older state) lead to the `trust relationship failed` symptom after weeks. Cloning a VM image that was already
joined produces two machines with one identity and flapping Kerberos keys. Time drift on virtualised guests, and
home-directory creation without `oddjobd` or `pam_mkhomedir`, produce further surprises. Samba DC administrators face
the extra ugliness that Microsoft's changes (for instance enforcement of PAC signatures and channel binding
requirements for LDAP) may reach Linux members before the Samba release that supports them.

Mitigations: pre-stage computer accounts in a defined OU with a delegated join account, use `--one-time-password`
or a short-lived join credential in kickstart or cloud-init, keep the join credential out of images, monitor
`sssctl domain-status`, and add `realm leave --remove` to decommission.

## Applications beyond this domain

The discovery-by-SRV-record idea is used by Kubernetes, SIP and XMPP clients, mail autoconfiguration and cloud
service meshes: publish a service in DNS, let clients find it. The machine-enrolment pattern (a privileged
principal creates an identity and a secret, the machine keeps the secret in a protected file) appears in Puppet and
Chef certificate signing, SPIFFE/SPIRE node attestation, `cloud-init` registration with a configuration server and
`kubeadm join` tokens, the last of which the Kubernetes docs describe with the same one-time-token logic
[src: kubernetes-docs 0b226da1572d0d43]. A Samba DC is also a general LDAP-plus-Kerberos server that many
non-Windows products (Apache, Postfix, GitLab, Jenkins, Proxmox) authenticate against.

## Examples

**A clean join.** A Rocky Linux 9 host points its resolver at the Samba DC (10.0.0.2), `chronyc sources` shows the DC
as its time source, `realm discover ad.example.com` prints `type: kerberos`, `server-software: active-directory`,
`client-software: sssd`. `realm join -U administrator ad.example.com` prompts for the password and returns. `realm
list` shows `configured: kerberos-member`. `getent passwd alice@ad.example.com` returns a UID in the mapped range;
`ssh alice@ad.example.com@host` succeeds, and the home directory is created because `oddjobd` is running.

**Failing: encryption type.** `realm join` aborts with `KDC has no support for encryption type`. The DC offers only
RC4 for a legacy account, or the client policy has removed RC4 while the DC lacks AES keys for the join account. The
fix in order of preference is to reset the account password on the DC (which generates AES keys), raise the account's
supported-enctypes attribute, and only then lower the client policy. This failure follows upgrades.

**Failing: stale name.** A reinstalled host called `app01` is joined again, `adcli` reports `Insufficient access` when it
tries to modify the existing object. Delete or reset the old computer object on the DC with `samba-tool computer
delete app01`, or join with `--computer-ou` to a different location with a delegated account.

**Failing: time.** `kinit` for the join account returns `Clock skew too great`; `realm join` prints the same. Fix time
first, always, and note that VMs resumed from sleep exhibit it.

**Provision and test loop (lab shape).** Start `samba-ad-dc`, create user `alice` with `samba-tool user create`, add an
RFC 2307 UID with `samba-tool user edit`, join a second machine, and check that the UID that SSSD reports matches
`uidNumber` when `ldap_id_mapping = False`, and differs when it is True. The contrast makes the mapping choice concrete.

## Related problems and ideas

Alternatives to `realmd`: `adcli` alone for scripted joins; `net ads join` with winbind, whose strengths are SMB
file-server membership; `sssd-ad` with `ad_provider` options and the older `ldap`+`krb5` pair for manual
control; the commercial agents (One Identity Authentication Services, Centrify, now Delinea). Alternatives to Samba on the
server side: genuine Windows Server (LNX-301-T05), FreeIPA with a trust (LNX-301-T07), or a hosted directory. If the
need is only SSH access to cloud instances, certificate-based SSH avoids directory integration entirely. Experimental
directions include Microsoft's Entra Domain Services as a managed LDAP/Kerberos front, and Linux-specific Entra ID
integration for login (an agent that uses device identity and OIDC) which replaces the join with device registration.

## Active research

Samba's team works on supporting newer Windows domain functional levels, on removing the Heimdal dependency in favour
of MIT Kerberos for the DC, and on tracking Microsoft's security hardening (PAC and channel-binding enforcement).
SSSD developers work on the AD provider's handling of GPO policy, on passkeys and smart cards, and on the Kerberos
KCM credential cache. Open questions include how Linux members should cope with Microsoft's phase-out of RC4 and
NTLM, and how to attest machine identity in autoscaling fleets without a shared join secret.

## Future direction

Microsoft has announced the staged disabling of NTLM and RC4 in Windows Server (to verify the current schedule), which
will push every Samba and Linux member to AES-only operation and make crypto-policy troubleshooting a core skill. Samba
4.2x is the current line (exact version to verify at the time of the course), with continued work toward MIT-based
DCs. Expect `realm join` to gain more provisioning hooks and for Red Hat, which supports joining but not hosting a
Samba DC, to keep pointing server-side needs at IdM. A practitioner should watch crypto policy defaults, Samba release
notes about functional levels, and the SSSD AD provider's GPO handling.
