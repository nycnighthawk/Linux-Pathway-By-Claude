# SSSD, nsswitch and PAM: how a Linux host learns who you are

## Define the problem

A Linux machine has to answer two different questions, often many times per second. The first is about identity:
which numeric UID belongs to the name `alice`, which groups she is in, where her home directory lives, and which
login shell to start. The second is about authentication and authorization: does the person typing really know
Alice's secret (or hold her smart card or Kerberos ticket), and is she allowed onto this particular host right now?

On a single standalone box both answers sit in local files (`/etc/passwd`, `/etc/group`, `/etc/shadow`). In an
organisation, the authoritative answers live elsewhere: an LDAP directory, a Kerberos realm, Active Directory or an
IdM (FreeIPA) domain. The engineering problem is to let every program on the host (`login`, `sshd`, `sudo`, `ls -l`
resolving owners, cron, a web server) get consistent answers from those remote authorities. That has to hold when
the network is slow or absent, it must not hand passwords to each application, and changing the back end must not
require rebuilding the applications.

This slice covers the three cooperating layers that solve it on modern Linux:

- the **Name Service Switch** (nsswitch), which decides where identity lookups go;
- **Pluggable Authentication Modules** (PAM), which decide how an application proves and checks a user;
- **SSSD**, the daemon that serves both layers from remote directories, with caching.

It also covers **authselect**, the tool that keeps the first two configured in step. Joining a domain (`realm`,
`adcli`) and IdM server administration are separate topics.

Failure in this area is very visible. Logins hang for minutes when a directory is unreachable. A
mis-ordered PAM stack can lock out root, or let an empty password through. A stale cache can show the wrong group
membership long after an administrator removed it.

## History and approaches

**Hard-wired lookups (1970s–1980s).** Early Unix C libraries read the flat files directly. Each new data source
(NIS/YP from Sun, then DNS for host names) was bolted into libc with its own special cases. The problem space was
small: one site, one source, always reachable.

**The switch abstraction (early 1990s).** Sun introduced a configurable switch, later adopted by GNU libc as NSS, in
which `/etc/nsswitch.conf` lists, per database (`passwd`, `group`, `hosts`, and so on), an ordered set of service
modules. Each module is a shared library such as `libnss_files` or `libnss_ldap`. This separated the question of
*what* is looked up from *where*. It covered identity only, and every process loaded the modules into its own
address space.

**Pluggable authentication (1995 onwards).** Sun's design for PAM (published as OSF RFC 86.0) applied the same idea
to authentication. An application calls a fixed API, and a per-service policy file (today `/etc/pam.d/<service>`)
stacks modules into four chains: `auth`, `account`, `password` and `session`. Control flags (`required`,
`requisite`, `sufficient`, `optional`, and the bracketed result-action form) say how each module's verdict affects
the chain. This let sites add one-time passwords, Kerberos or smart cards without patching `login` or `sshd`. The
curated PAM material in this catalog walks through how real `system-auth` stacks combine `pam_env`, `pam_unix`,
`pam_pwquality`, `pam_faillock` and `pam_deny`.

**Directly connected modules (late 1990s–2000s).** The obvious way to reach a directory was a module per protocol:
`nss_ldap` and `pam_ldap` (PADL), `pam_krb5`, and Samba's `winbind` with `pam_winbind` for Windows domains. Each
covered a slice of the problem well, but they shared structural weaknesses:

- the LDAP client ran inside every calling process, including setuid programs and long-lived daemons, which
  raised both memory and security concerns;
- there was no shared cache, so a busy host repeated the same directory queries, and an unreachable server stalled
  logins;
- laptops could not log in offline, so users kept a separate local account;
- identity and authentication sources were configured in different files, and drift between them was common.

`nscd` added a process-wide cache for identity, but it knew nothing about authentication and had well-known
staleness problems.

**Lessons that shaped the next step.** Keep the network client out of the calling process, cache both identity and
credentials in one place with explicit expiry, support several domains at once, and generate the PAM and nsswitch
files from a small set of known-good profiles instead of hand-editing them.

## Current state

**SSSD as the broker.** SSSD (first released in 2009 and made a default Fedora package soon after) runs as a set of
daemons. Responder processes talk to clients: `nss`, `pam`, `sudo`, `ssh`, `autofs` and `pac`. One back-end
process per configured *domain* talks to the authority through *providers*. The client side is deliberately thin:
`libnss_sss` (named `sss` in `nsswitch.conf`) and `pam_sss.so` only forward requests over a local socket. All
directory and Kerberos traffic happens in SSSD, and the results land in an on-disk cache.

A domain section in `sssd.conf` selects providers independently:

- `id_provider` decides where users and groups come from (for example `ldap`, `ipa`, `ad`, or `proxy` to wrap a
  legacy NSS module);
- `auth_provider` decides how passwords are verified (often `krb5`, or the same as the ID provider);
- `access_provider` decides who may log in (for example `simple`, `ad` with GPO evaluation, or `ipa` with HBAC
  rules);
- `chpass_provider` decides where password changes go.

The FreeIPA client configuration in the catalog shows all four pointed at `ipa`, with credential caching enabled so
that a disconnected laptop can still authenticate.

**How a login flows.**

1. `sshd` asks PAM to authenticate `alice`. The `auth` chain, as generated by authselect's `sssd` profile, tries
   local `pam_unix` for local users, then `pam_sss` for directory users.
2. `pam_sss` hands the credentials to SSSD. SSSD obtains a Kerberos TGT, or binds to LDAP, and on success stores a
   salted hash so that an offline login can be checked later.
3. The `account` chain asks SSSD whether access is allowed (HBAC rules, AD GPO, expiry). The `session` chain sets
   up limits, the home directory and the systemd user slice.
4. Meanwhile `getpwnam("alice")` from any process goes through nsswitch to `sss`, and is answered from the memory
   cache or the on-disk cache, or fetched from the back end if it is stale.

**authselect.** Rather than hand-editing `system-auth`, `password-auth` and `nsswitch.conf`, current RHEL-family
systems select a profile (`local`, `sssd`, `winbind`) plus features (`with-mkhomedir`, `with-faillock`,
`with-smartcard`, `with-fingerprint`). Site-specific needs go in a custom profile cloned from a stock one, so that
package updates don't overwrite them. authselect writes PAM and nsswitch files only. It does not configure the
daemon behind them, which is why selecting the `sssd` profile on a host where SSSD isn't running leaves only local
users able to log in. The RHEL guide warns about exactly this, and a compliance rule in the catalog checks that the
active profile still includes the required password-quality, history, lockout and `pam_unix` modules.

**Generalised pattern.** The three layers form a broker architecture:

- a stable client API (NSS calls and the PAM API);
- a thin, policy-free shim (`libnss_sss`, `pam_sss`);
- a privileged broker that owns protocol clients, caching and policy (SSSD);
- a configuration generator that keeps the shims consistent (authselect).

The same shape appears elsewhere. `systemd-resolved` sits behind the `resolve` nsswitch module for DNS, and
container runtimes delegate image pulls to a daemon. In each case, the value comes from moving network state out of
every caller into one place that can cache, retry and enforce policy.

**Structural evaluation.**

| Aspect | Strength | Limitation | Mitigation |
|---|---|---|---|
| Caching | Offline logins; fewer directory queries | Stale group membership; cached credentials outlive revocation | `entry_cache_timeout`, `offline_credentials_expiration` (STIGs require short limits when smart cards are used), `sss_cache -E` after changes |
| Isolation | Network clients out of setuid programs | SSSD becomes a critical single daemon; if it hangs, logins hang | Run SSSD unprivileged where supported (a CAC rule checks this), watchdog, monitor `sssctl domain-status` |
| Multi-domain | AD, IdM and LDAP side by side | Name collisions and ID-mapping choices (algorithmic vs POSIX attributes) are hard to undo | Decide ID mapping before the first join; use fully qualified names in mixed forests |
| PAM stacking | Fine-grained, auditable policy | One wrong control flag changes security posture; `nullok` lets empty passwords through | Use authselect profiles and compliance scans; keep a root console open while testing |
| Transport | Kerberos and LDAP with TLS | Plain LDAP leaks credentials and attributes | Hardening baselines require StartTLS or LDAPS for the LDAP provider |

**Operational risks** to rehearse in labs:

- a clock skewed by more than Kerberos tolerance breaks authentication silently;
- DNS SRV records that point at a dead domain controller cause long timeouts;
- after a group change, users keep the old memberships until the cache expires or is flushed;
- hand-edited PAM files that authselect overwrites on its next run.

**Applicability beyond logins.** The same plumbing serves `sudo` rules stored in IdM, SSH public keys and host keys
from the directory (`sss_ssh_authorizedkeys`), automount maps, smart-card and passkey authentication, and Kerberos
single sign-on into `sudo` through `pam_sss_gss`. The catalog's IdM material shows the last of these.

## Related and opposing views

- **Winbind instead of SSSD for AD members.** Samba's `winbindd` serves NSS and PAM directly and is required when
  the host is also a Samba file server that must match Windows ID mapping exactly. SSSD's `ad` provider is simpler
  for pure clients. Mixed setups run both, with winbind for file serving and SSSD for logins. Choosing between them
  is a recurring design decision in the Mixed Environments course.
- **`nss-pam-ldapd` (`nslcd`).** This is a lighter, LDAP-only broker that still has users who want minimal
  dependencies. Fedora's authselect proposal explicitly left it out of the default profiles because SSSD covers its
  use cases.
- **`systemd-homed` and `systemd-userdb`.** These treat a user record as a self-contained, signed, portable JSON
  object that is served over Varlink. NSS reaches it through `libnss_systemd`. They target personal devices more
  than enterprise directories, but they show a different philosophy: identity carried with the home directory
  rather than fetched from a central server.
- **Cloud and OIDC identity.** In cloud estates, operators increasingly avoid long-lived directory accounts on
  servers. Logins go through short-lived SSH certificates or OIDC-backed tools, and sometimes through SSSD's newer
  identity-provider (`idp`) support for external OAuth 2.0 providers. These shift the trust question from "is this
  password right" to "is this token fresh and correctly scoped".

## Future direction

- **Passwordless by default.** Passkey and FIDO2 support in SSSD and IdM, and smart-card policies, are moving
  password checks to a fallback role. Expect compliance baselines to keep raising the bar on multi-factor
  authentication for privileged accounts.
- **Less privileged daemons.** SSSD has been moving towards running as an unprivileged user with capabilities, and
  hardening guides already check for it.
- **Fewer moving parts per host.** authselect-style profile management (now the only supported way on RHEL) pushes
  administrators away from hand-built PAM stacks, which makes drift detection and automation (Ansible system roles)
  practical.
- **Identity federation at the edge.** Expect broader use of external IdP integration and short-lived credentials,
  with SSSD acting as a translation layer rather than the system of record.
