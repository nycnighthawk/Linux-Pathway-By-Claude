# FreeIPA and IdM: a Linux-native identity domain with replicas, HBAC and central sudo

## Define the problem

A Linux shop that wants single sign-on, central policy and certificate issuance, but does not run Windows servers,
faces an assembly problem. The pieces exist as separate open-source projects: an LDAP server (LNX-301-T01), a Kerberos
KDC (LNX-301-T02), DNS, a certificate authority, an NTP source, SSSD on the clients (LNX-301-T03). Wiring them yields
a system with four administration surfaces, four backup procedures and many ways to make the parts disagree. Active
Directory gives Windows organisations this integrated package; Linux needed an equivalent that treats POSIX concepts
(sudo rules, SSH keys, automount maps, SELinux user maps) as first-class directory data.

FreeIPA, and its Red Hat product form Identity Management (IdM), is that package. The questions it answers are
operational: how do I add a host and a user once and have all the pieces learn about them; how do I say "the `dba`
group may log in to the `db-*` hosts only, via ssh, and may run `systemctl restart postgresql` as root" in one
place; how do I add a second server so that the loss of the first does not stop logins; how do I replace the
certificates before they expire; and how do I repeat the whole thing in a test lab. Failure here looks like a
replication topology that has split into two islands, a client that cannot find a KDC because DNS SRV records are
stale, an HBAC rule left at the default `allow_all` so that restricted access is not actually restricted, or a CA
whose renewal master died.

The slice covers the architecture, the server and replica installation steps, host-based access control (HBAC)
and sudo rules as the two policy features that tie Linux logins to central data, and the supporting commands for
checking them. Trust with AD is LNX-301-T07; automation with ansible-freeipa is LNX-301-T09.

## History and approaches

The 1990s answer to the integration problem was NIS with Kerberos and plenty of cron jobs, then "OpenLDAP plus MIT
Kerberos plus Samba", configured by hand and documented in dozens of how-tos. Red Hat's Directory Server (from the
Netscape lineage, released as open source in 2005 as Fedora Directory Server and now 389 Directory Server) offered
the LDAP part with a graphical console, but the glue stayed manual. In 2007 the FreeIPA project started at Red Hat
(Simo Sorce, Karl Wirth and colleagues) to deliver a pre-integrated identity, policy and audit server for Linux
and Unix, shipping version 1 in 2008 and a much larger version 2 in 2010. Version 2 added a CA (Dogtag), a
rule-based HBAC, sudo rules in the directory, and the `ipa` command and web UI as unified interfaces. The design
principle was that an administrator operates on high-level objects (users, hosts, rules) and the system keeps LDAP
entries, Kerberos principals, DNS records and certificates in agreement.

Several earlier ideas failed or only partly worked. Plain `sudoers.ldap` stored sudo rules in LDAP, but each client
needed the `sudo-ldap` build and its own LDAP configuration; the approach got little traction until SSSD offered a
sudo responder fed by cached rules. Host-based access control had existed as `pam_access` with static files,
or as the `host` attribute in LDAP, but rules had no groups, services or time limits. The first FreeIPA releases
offered multi-master replication only between servers of the same version, so upgrades needed discipline; the
topology was hand-managed with `ipa-replica-manage` until FreeIPA 4.3 (2015) introduced the managed topology
graph with replication agreements as visible objects. The CA had a single "renewal master" whose loss complicated
certificate renewals, a role that remains an operational concern. External DNS integration worked but left stale
SRV records; the integrated BIND with the LDAP back end (`bind-dyndb-ldap`) later became a supported pattern.

IdM gained its own client in SSSD's `ipa` provider, replacing the manual `ldap`+`krb5` configuration; clients are
joined with `ipa-client-install`. Over time features migrated outward: SSSD gained the sudo responder (1.9), the
`ipa-client` learned host certificate requests through `certmonger`, and cross-realm trust with AD (T07) arrived in
FreeIPA 3.0 (2012). More recently RHEL 10 documentation notes that IdM-to-IdM migration through the `ipa-migrate`
command is fully supported from 10.1, that the ansible-freeipa package became an Ansible collection, and that
SSSD can run dynamic DNS updates over TLS [src: rhel-10-docs 181a48c68bac2a7e].

The pattern: integrate the identity, authentication, naming and certificate services under one object model; use
replication to avoid a single point of failure; push policy to clients by letting SSSD read it with the user's
own credentials; and treat the whole as an appliance-like product with a tested installer.

## Current state

**Components.** An IdM server runs several daemons:

- *389 Directory Server* (`dirsrv@REALM`), holding the DIT under `dc=example,dc=com` and the replication
  changelogs, with two suffixes, the main one and `o=ipaca` for the certificate system.
- *MIT Kerberos KDC* (`krb5kdc`) and `kadmind`, with the `ipadb` plugin that reads principals from LDAP, so that a
  user created in LDAP is already a principal.
- *Apache httpd*, serving the JSON-RPC API behind the `ipa` command and the web UI, and the `ipa-custodia` service for
  secret exchange between servers.
- *Dogtag Certificate System* (`pki-tomcatd`), the CA that issues host, service and user certificates, with an
  optional KRA for key archival.
- Optional *BIND* with the `named-pkcs11` or `bind-dyndb-ldap` DNS back end, *chronyd* and `ipa-dnskeysyncd` for DNSSEC.
- *SSSD*, *certmonger* and `oddjobd` on every machine, including servers.

**Installing the first server.**

```text
dnf install ipa-server ipa-server-dns
ipa-server-install --realm=EXAMPLE.COM --domain=example.com --ds-password=... --admin-password=... \
    --setup-dns --forwarder=10.0.0.1 --no-reverse --unattended
kinit admin ; ipa user-find
```

Preconditions: a static IP, an FQDN as the hostname that resolves forward and reverse to it (the installer checks),
sufficient entropy, the right firewall services (`freeipa-ldap`, `freeipa-ldaps`, `dns` with the Kerberos ports),
and at least 2 GB of RAM for a small installation (to verify the current minimum). The domain name should be a
subdomain you own, and the realm is conventionally the upper-cased domain; neither can be changed later. Options
`--setup-dns`, `--setup-adtrust`, `--no-ntp` and `--external-ca` pick optional components; `--pkinit-cert-file` or
the default self-signed PKINIT enables smart-card flows.

**Replicas and the topology.** A replica is created by joining a host as a client and promoting it:

```text
ipa-client-install --domain=example.com --realm=EXAMPLE.COM
ipa-replica-install --setup-ca --setup-dns --forwarder=10.0.0.1
ipa topologysuffix-verify domain
ipa topologysegment-find domain
```

The two servers hold replication agreements called **segments** in the `domain` suffix (and `ca` for the
certificate suffix). Replication is multi-supplier: both servers accept writes and propagate them, resolving
conflicts by timestamp on attribute changes, so a user created on `ipa1` appears on `ipa2` within seconds.
`ipa topologysegment-add domain ipa2-to-ipa3 --leftnode ipa2.example.com --rightnode ipa3.example.com` links two
replicas; topologies should be at least two connections per server and no more than four, and no server should be
more than a few hops from another. The `ipa-replica-manage list`, `del` and `force-sync` commands remain for
diagnosis. Server roles (CA, DNS, KRA, AD trust controller) are listed with `ipa server-role-find`. Exactly
one server is the **CA renewal master**, a role that `ipa config-mod --ca-renewal-master-server` moves. Removing a
dead server must go through `ipa server-del`, which cleans the topology and the DNS records; deleting only the
host leaves ghosts in the replication metadata. The RHEL documentation pairs a proof-of-concept path with
a planning chapter that advises how many replicas and where to put them
[src: rhel-10-docs 3f9e7676c9c93273].

**Client enrolment.** `ipa-client-install` (or the `ipa_client` Ansible role) discovers the server by DNS, asks for an
administrator or a one-time password, creates the host entry, issues a keytab, configures SSSD with
`id_provider = ipa`, adds `sudoers: files sss` and `ssh` integration (the `sss_ssh_knownhostsproxy` and
`sss_ssh_authorizedkeys` helpers that serve host keys and user keys from the directory), and starts certmonger for
the host certificate. `ipa host-add --ip-address=... --random` pre-creates a host with a one-time password for
unattended installation. The manual alternative is documented in the Arch wiki
[src: archwiki 495a9b7db2f7fcce] [src: archwiki 70e53b66633db3d8].

**HBAC: who may log in where, by which service.** A rule has a user category, a host category and a service
category, each either explicit (lists of users, groups, hosts, host groups, services, service groups) or the special
`all`. PAM on the client calls `pam_sss`, whose `access_provider = ipa` evaluates the rules for that user and host.
A rule created by default, `allow_all`, grants everything to everyone, and a freshly installed server therefore has
no effective access control until it is disabled.

```text
ipa hbacrule-add db-ssh --desc dba-ssh-to-databases
ipa hbacrule-add-user db-ssh --groups=dba
ipa hbacrule-add-host db-ssh --hostgroups=dbservers
ipa hbacrule-add-service db-ssh --hbacsvcs=sshd
ipa hbacrule-disable allow_all
ipa hbactest --user=alice --host=db1.example.com --service=sshd
```

`hbactest` prints which rules matched and why, and is the correct first step for any "permission denied after
authentication succeeded" ticket. Rules apply to PAM services (`sshd`, `login`, `su`, `sudo`, `gdm`), so you can
let someone ssh but not use a console. Service names and groups are `hbacsvc-find` objects. Time-based
restrictions are not available in HBAC (to verify for current versions); use group membership timing by automation
instead. Failed HBAC evaluation shows as a PAM `Permission denied` after the password is accepted, and SSSD logs
list the rules considered at debug level 6 in `sssd_example.com.log`. The Ansible modules `ipahbacrule` and
`ipahbacsvc` create the same objects declaratively [src: rhel-10-docs 9984e8569c711253].

**Sudo rules: central privilege policy.** A sudo rule names users (or groups), hosts (or host groups), commands (or
command groups), and an identity to run as, plus options.

```text
ipa sudocmd-add /usr/bin/systemctl
ipa sudocmdgroup-add pgctl ; ipa sudocmdgroup-add-member pgctl --sudocmds=/usr/bin/systemctl
ipa sudorule-add dba-restart --desc dba-pg-restart
ipa sudorule-add-user dba-restart --groups=dba
ipa sudorule-add-host dba-restart --hostgroups=dbservers
ipa sudorule-add-allow-command dba-restart --sudocmdgroups=pgctl
ipa sudorule-add-option dba-restart --sudooption '!authenticate'
```

On the client, `/etc/nsswitch.conf` needs `sudoers: files sss`, and `sssd.conf` has `sudo` in its `services` list;
`ipa-client-install` sets both. SSSD downloads the rules for the user and host (an initial full refresh and then
smart refreshes every few minutes: `sudo_provider = ipa` fetches them with the host's credentials), caches them
and answers `sudo` from the cache even when the server is offline. `sudo -l` shows the matched rules; clear the
SSSD sudo cache with `sss_cache -R` or `sss_cache -E` when debugging. Precedence follows the sudoers rules, namely
the last match wins unless `sudoOrder` is set. A command is matched literally, including arguments, unless
you add a wildcard. Leaving a command group's path ambiguous (`/bin/systemctl` versus `/usr/bin/systemctl` on a
merged-/usr system) is the commonest cause of a rule that exists yet never applies.

**Other policy objects.** Role-based access control (privileges, permissions and roles) delegates IdM administration
itself, for instance a helpdesk that can reset passwords but not touch HBAC. Password policy has global and
per-group variants (`ipa pwpolicy-add dba --maxlife=60 --minlength=14 --priority=10`) with lockout counters
replicated carefully so that the failed-attempt count is per server and may differ. Automember rules add hosts and
users to groups on creation. Netgroups and automount maps serve legacy clients [src: rhel-10-docs f3badd83b8a8b177].
ID views override user attributes per client group, used in migration and trust cases (LNX-301-T08). OTP tokens
(`ipa otptoken-add`) allow two-factor auth with Kerberos pre-auth.

**Health and recovery.** `ipa-healthcheck` (from the `ipa-healthcheck` package) runs dozens of checks for
replication, certificates, file permissions and DNS; run it from cron or a timer and alert on non-zero. Backups
come in two kinds: `ipa-backup` (a full or data-only archive on one server) and, more important operationally,
other replicas. Restoring from backup of one server in a replicated environment requires re-initialising the
others; a replica is a better recovery source than a backup. `ipa-replica-manage re-initialize --from=ipa1` and
`ipa-csreplica-manage` repair broken suffixes.

**Generalised pattern.** The reusable shape is an integrated control plane where operators edit declarative policy
objects, a replicated store keeps them available, and agents on endpoints pull the policy with a machine credential
and enforce it locally, with a cache to survive disconnection.

## Assessment: the good, the bad and the ugly

**Good.** One installer produces a working realm, with a web UI and a CLI that map to a documented JSON-RPC API,
which makes everything scriptable. Multi-supplier replication gives availability with no external cluster
software. Central HBAC and sudo with a test command (`hbactest`) are better than file-based configuration
management for audit. Certificates for hosts and services issue and renew automatically via certmonger, which removes
a class of expiry outages. SSH keys held in the directory make `authorized_keys` management disappear. The same
framework is supported commercially by Red Hat and available upstream, so skills carry over.

**Bad.** It is a large system and it is opinionated: DNS names and realm are fixed at install, sizing is a
non-trivial exercise, and 389 DS plus Dogtag plus Kerberos mean three subsystems to troubleshoot. Upgrades must go
replica by replica with matching or adjacent versions, and mixed-version operation is supported only for a limited
window. HBAC and sudo semantics differ subtly from local files, so engineers learn another policy language. Debugging
login problems needs the client side (SSSD debug) and the server side (`/var/log/dirsrv/`, `/var/log/krb5kdc.log`,
`/var/log/httpd/`) together. The documentation stresses a supported upgrade matrix (to verify), and there is
vendor-specific behaviour in each distribution, such as the Debian packages of FreeIPA lagging Fedora's.

**Ugly.** Replication topologies degrade silently. A segment can be broken for days while each server serves
slightly different data; the visible symptom is a user who can log in on one host but not another. Time skew
between servers makes conflict resolution lose recent changes. The CA renewal master problem recurs: if that server
is lost, certificate renewals stop until another is promoted, and the first symptom appears months later when
a sub-CA or service certificate expires, taking the web UI, LDAPS or the KDC with it (PKINIT certificate).
Restoring an old backup into a live topology reintroduces deleted users. Default settings leave `allow_all` on
and anonymous LDAP binds permitted for read access to non-sensitive attributes. Sizing the default `dirsrv`
cache against memory is manual. Because every client trusts the IdM CA, compromise of the server is compromise of
all hosts, so server hardening and a dedicated, small administrative group are not optional.

Mitigations: at least two replicas per site with the CA role on two of them, `ipa-healthcheck` alerts, tested
`ipa-backup` and disaster-recovery steps, disable `allow_all` on day one, per-group password policies, and a
documented process for replacing the renewal master.

## Applications beyond this domain

The same architecture appears wherever an inventory and a policy must be pushed to many nodes. Puppet and Ansible
with a signed-inventory model are cousins; Kubernetes RBAC and OPA policies are declared centrally and enforced by
agents, with caching on the node; SPIRE and cloud IAM issue short-lived machine certificates, as certmonger does. The
HBAC data model (subject, resource, action, with category `all`) resembles ABAC engines and firewall rule sets.
Certificate lifecycle with certmonger (`getcert list`, tracking, auto-renewal) is useful even without IdM, for any
service certificate, and the ansible-freeipa modules are an example of idempotent infrastructure code for identity.
The Ansible module catalogue also covers sudo rule and netgroup objects with the same idempotent approach
[src: rhel-10-docs f3badd83b8a8b177].

## Examples

**A small production topology.** Three servers: `ipa1` and `ipa2` in the primary site with CA, DNS and KRA roles,
`ipa3` in the second site with DNS only. Segments: ipa1-ipa2, ipa2-ipa3, ipa1-ipa3. Clients prefer same-site servers
by DNS locations, and fall back through SRV priorities. A nightly `ipa-backup --data --online` runs on `ipa1` and a
timer runs `ipa-healthcheck --failures-only`. Adding a fourth server is a join and a promotion and one new segment.

**Applying policy.** The DBA example above ends with `ipa hbactest --user=alice --host=db1.example.com
--service=sshd`, which should print `Access granted: True` with matched rule `db-ssh`; the same test for `web1`
prints `False` with `Unmatched rules: db-ssh`. On `db1`, `sudo -l -U alice` shows the `dba-restart` rule after
`sss_cache -E`. The lab for this topic checks the policy objects as an LDIF-like export: the commands are
simple, the interpretation is what is graded.

**Failing: allow_all left in place.** The security review asks why a contractor in group `web` can ssh into
the database host. The `db-ssh` rule is correct; `allow_all` is still enabled. `ipa hbactest` for the contractor
reports matched rule `allow_all`. Disabling it fixes the leak and exposes other broken access (cron jobs using
`crond` service names) that a gradual rollout must handle.

**Failing: split replication.** Users created on `ipa2` do not appear on `ipa3`. `ipa topologysegment-find domain`
lists segments, but `ipa-replica-manage list` shows `ipa3` last update stale, and the 389 error log reports
`Replication bind failed: Can't contact LDAP server` because `ipa3`'s LDAP certificate expired. Renewing the
certificate through `getcert resubmit`, then `ipa-replica-manage force-sync --from=ipa2`, restores data flow.
`ipa-healthcheck` would have flagged both the expiring certificate and the agreement.

**Failing: sudo path mismatch.** A rule allows `/bin/systemctl`; on the client `/bin` is a symlink to `/usr/bin` and
sudo records the resolved path. The rule never matches. Adding both paths, or using a command group with the real
path, solves it.

## Related problems and ideas

Alternatives within the open-source Linux world include a hand-built OpenLDAP with Kerberos (LNX-301-T01 and T02),
389 Directory Server on its own, Samba AD (LNX-301-T04) which offers GPOs and Windows compatibility but no native
sudo or HBAC, Keycloak for web single sign-on in front of any of them, and Univention Corporate Server or
Authentik/Zitadel as products with different design points. Evolving ideas include replacing LDAP-based policy with
declarative GitOps stores whose state compiles to local files, and replacing passwords with passkeys and
certificate-based SSH, where IdM acts as the CA. The related problem of Linux machines in a Windows forest is solved
either by direct join (T04, T05) or by a trust (T07). The related problem of hosted identity (Entra ID, Okta) sits
outside this ecosystem but can be bridged by IdM's external IdP support for OAuth2 device-flow Kerberos pre-auth.

## Active research

Upstream FreeIPA development covers replacing the older LDAP-based PKINIT with certificate-based
schemes tied to the IdM CA, passkey authentication, improved HSM support for CA keys (marked as fully supported in
recent RHEL documentation [src: rhel-10-docs 181a48c68bac2a7e]), post-quantum readiness of the CA, and
integration with external identity providers through Kerberos pre-authentication using OAuth2. Researchers and operators
study replication convergence under partitions and the interaction of 389 DS conflict resolution with
application-level semantics. Open questions: how to apply fine-grained ABAC on top of group-based HBAC, and how to
reduce the cost of the Dogtag subsystem for small deployments.

## Future direction

Expect IdM to keep tracking RHEL: version 10 brought collection-format ansible-freeipa, supported IdM-to-IdM
migration and DNS-over-TLS updates, and further hardening of crypto policy defaults (to verify per minor release). The
direction is toward less manual topology management, wider use of external IdPs and passkeys, and managed lifecycle
for the CA. Watch FreeIPA release notes, distribution package availability (Fedora, RHEL, Rocky, Alma, and Debian
freeipa packages), and any change to the supported replica count and version-skew policy.
