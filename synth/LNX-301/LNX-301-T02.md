# Kerberos, keytabs and GSSAPI SSH: proving identity without sending a secret

## Define the problem

Passwords have two structural weaknesses on a network. Every service that checks one must either see it or hold a
verifier derived from it, so a compromised web server, mail server or SSH daemon becomes a password collector. And a
human who must retype the password for every connection either types it hundreds of times a day or stores it in
scripts, which is worse. Directory binds (LNX-301-T01) have exactly this shape: the secret travels to the server, and
the server's only protection is the TLS channel around it.

Kerberos addresses a precise requirement: let a user prove their identity to many services, once per working period,
over a hostile network, without any service ever receiving the user's long-term secret, and let the services prove
themselves back. The same machinery has to support unattended programs (a backup job, a daemon mounting an NFS share)
that cannot type a password, which is what keytabs are for. And it has to plug into applications through a stable
programming interface so that each program does not implement the protocol itself, which is the Generic Security
Services API (GSSAPI).

Failure here has a distinctive feel. A ticket "works" until the clock on a host drifts by five minutes and then every
login fails with `Clock skew too great`. SSH asks for a password even though a valid ticket exists, because the
client asked for a service name that the KDC does not know. A keytab silently stops working after a password reset
because its key version number is stale. This slice teaches the protocol well enough to predict those failures, shows
how to run and use a realm with MIT Kerberos (`kdb5_util`, `kadmin`, `kinit`, `klist`, `ktutil`), and ties it to
GSSAPI single sign-on for OpenSSH. Active Directory and FreeIPA use the same protocol with extensions; they are
covered in LNX-301-T04 and T06.

## History and approaches

The problem was first made urgent at MIT's Project Athena in the mid-1980s: thousands of workstations, a campus
network, and student accounts, with the explicit threat that anyone on the Ethernet could read traffic. Steve Miller
and Clifford Neuman designed Kerberos there, built on the key-distribution scheme of Needham and Schroeder (1978) with
timestamps added to resist replay. Versions 1 to 3 were internal; version 4 escaped MIT in 1989 and was widely used,
but had real flaws: weak DES-only encryption, a byte-order-dependent message format, no cross-realm hierarchy beyond
pairwise links, and a ticket structure that let an offline attacker mount dictionary attacks against any password
without ever talking to the KDC.

Version 5 (RFC 1510 in 1993, replaced by RFC 4120 in 2005) fixed these with ASN.1-encoded messages, negotiable
encryption types, forwardable and renewable tickets, and pre-authentication, which forces a client to prove it knows
the key before the KDC returns anything crackable. Later work added the Generic Security Services API (RFC 1508, then
RFC 2743/2744), the Kerberos GSS mechanism (RFC 4121), SPNEGO negotiation (RFC 4178) so that applications can pick
Kerberos or NTLM on the fly, PKINIT (RFC 4556) for smart-card and certificate-based initial authentication, and FAST
armoring (RFC 6113) to protect pre-authentication exchanges inside a tunnel.

Microsoft shipped Kerberos 5 as the default authentication protocol of Windows 2000 and attached its own PAC
(Privilege Attribute Certificate) to tickets to carry group SIDs. That decision made Kerberos ubiquitous in
enterprises but created a compatibility surface: Linux services in an AD realm must understand the PAC or at least
ignore it politely. The Heimdal implementation (from Sweden, 1990s) and MIT's own code base diverged over the years,
and distributions mostly settled on MIT krb5 for the server side, though Samba AD DC has historically embedded Heimdal
and later added an MIT option.

Cryptographic history is the other thread. DES was deprecated and eventually disabled by default; RC4-HMAC (the
`arcfour` type, used by Windows for compatibility) has been retired step by step; AES with HMAC-SHA1 (`aes256-cts`
and `aes128-cts`) became the baseline and AES with HMAC-SHA2 types (RFC 8009) arrived for new deployments.
Distributions now ship crypto policies that remove weak types, which makes old keytabs and trusts fail loudly after
upgrades.

Partial successes are instructive. Kerberos for NFS (`sec=krb5`) works but is regarded as hard to deploy. SSH GSSAPI
authentication has been in OpenSSH through patches and then mainline code for years, but its key exchange variant
(`gss-keyex`) remains a distribution patch rather than upstream, which is why some builds support it and some do
not. Cross-realm trust works best inside one organisation and poorly between unrelated ones, because every pair needs
shared keys and agreement on policy.

The pattern that emerges: a small, well-guarded key distribution centre, a standard application interface, and
automation that renews tickets and rotates keys, with every convenience feature (forwarding, renewal, delegation)
treated as a risk to be limited by policy.

## Current state

**The protocol in three exchanges.** A realm is an administrative domain with an upper-case name, usually the DNS
domain: `EXAMPLE.COM`. The Key Distribution Center (KDC) has two logical halves sharing one database: the
Authentication Service (AS) and the Ticket Granting Service (TGS). A **principal** names a user (`alice@EXAMPLE.COM`)
or a service instance (`host/web1.example.com@EXAMPLE.COM`, `nfs/files.example.com@EXAMPLE.COM`).

1. *AS exchange.* Alice's client sends an AS-REQ naming `alice` and the ticket-granting service `krbtgt/EXAMPLE.COM`.
   With pre-authentication, the request carries a timestamp encrypted under a key derived from her password (or a
   PKINIT certificate signature). The KDC returns a Ticket-Granting Ticket (TGT), encrypted under the `krbtgt` key so
   that only the KDC can read it, and a session key encrypted under Alice's key. The client decrypts the second part;
   if the password was wrong, decryption fails locally and no password ever crossed the network.
2. *TGS exchange.* To reach `host/web1.example.com`, the client sends the TGT plus an authenticator (name and
   timestamp encrypted with the TGT session key) to the TGS. The KDC returns a service ticket encrypted under the
   service's long-term key, plus a fresh session key.
3. *AP exchange.* The client presents the service ticket and a new authenticator to the application server. The
   service decrypts the ticket with its key, which it holds in a **keytab**, checks the authenticator, and has
   authenticated Alice. With mutual authentication it returns a proof that it, too, could read the ticket.

Every step depends on time, because authenticators carry timestamps. The default tolerated skew is five minutes
(`clockskew` in `krb5.conf`), and a replay cache on services rejects reuse of an authenticator.

**Client configuration.** `/etc/krb5.conf` has `[libdefaults]` (`default_realm`, `dns_lookup_kdc`,
`dns_canonicalize_hostname`, `rdns`, `default_ccache_name`, `permitted_enctypes`), `[realms]` (KDC and admin servers)
and `[domain_realm]` (mapping hosts to realms). With `dns_lookup_kdc = true`, clients find KDCs by SRV records
(`_kerberos._udp.example.com`), which is how AD and IdM are normally discovered. Credential caches may be files
(`FILE:/tmp/krb5cc_1000`), directories (`DIR:`), the kernel keyring (`KEYRING:persistent:UID`, the RHEL default) or
`KCM:` (a daemon, managed by SSSD).

**Everyday commands.**

- `kinit alice` obtains a TGT; `kinit -k -t /etc/krb5.keytab host/web1.example.com` does so from a keytab, with
  `-l`/`-r` for lifetime and renewable lifetime and `-f` for a forwardable ticket; `kinit -c <ccache> -S <service>`
  asks for a particular service ticket.
- `klist` lists the cache; `klist -e` adds encryption types; `klist -k /etc/krb5.keytab` lists keytab entries with key
  version numbers (`-K` shows keys, which is why a keytab is as sensitive as a password).
- `kdestroy` deletes the cache; `kvno host/web1.example.com` fetches a service ticket and prints the key version,
  which is the quickest test that the KDC knows the name.
- `KRB5_TRACE=/dev/stderr kinit alice` prints a step-by-step trace of KDC discovery, pre-auth and failures. It is the
  most useful debugging switch in the MIT stack.

**Running a KDC.** With MIT krb5: install `krb5-server` (or `krb5-kdc`/`krb5-admin-server`), set the realm in
`/etc/krb5.conf` and `/var/kerberos/krb5kdc/kdc.conf` (Debian: `/etc/krb5kdc/`), then `kdb5_util create -s -r
EXAMPLE.COM` builds the database and writes a stash file with the master key. `kadmin.local` administers it locally
without a password: `addprinc alice`, `addprinc -randkey host/web1.example.com`, `ktadd -k /tmp/web1.keytab
host/web1.example.com`, `modprinc`, `delprinc`. The ACL file `kadm5.acl` controls remote kadmin. `systemctl enable
--now krb5kdc kadmin` starts the services. A second KDC is configured as a replica with `kpropd` receiving a
`kdb5_util dump` pushed by `kprop` on a cron schedule; KDC replicas are read-only for password changes. Always open
UDP and TCP 88 and TCP 464 (kpasswd) and 749 (kadmin).

**Keytabs.** A keytab is a file of (principal, key version, encryption type, key) tuples. Services read it to decrypt
tickets, and unattended jobs use it with `kinit -k`. `ktadd` (kadmin) fetches keys **and rotates them**: running it
again invalidates the earlier copy, so each host must have its own principal, or all copies must be pulled together.
`ktutil` merges and edits keytabs (`rkt`, `wkt`, `list`). Permissions: root-owned, mode 0600 for
`/etc/krb5.keytab`; for a service that drops privileges, a dedicated keytab file readable by that user, referenced
from the service's configuration. The host keytab is created automatically by `ipa-client-install` and `realm join`.

**GSSAPI and SSH.** OpenSSH exposes Kerberos through two knobs. On the server, `GSSAPIAuthentication yes` lets
clients log in with a service ticket for `host/<fqdn>`, `GSSAPICleanupCredentials yes` removes the cache at logout,
and `GSSAPIStrictAcceptorCheck yes` (default) forces the acceptor name to match the host name the client used. The
`sshd` process reads `/etc/krb5.keytab`, so the host key must be present. On the client, `GSSAPIAuthentication yes`
enables it and `GSSAPIDelegateCredentials yes` forwards the ticket to the remote shell; use `-K`/`-k` or
`ssh -o GSSAPIDelegateCredentials=yes`. Authorisation is still separate: the Kerberos principal must map to a local
account, via the `.k5login` file in the target home directory, `auth_to_local` rules in `krb5.conf`, or, more usually,
SSSD resolving the same name through the directory (LNX-301-T03). On Windows, the Microsoft documentation of
OpenSSH Server describes the same `GSSAPIAuthentication` option for AD-joined servers
[src: ms-learn-adds 60750b9578831cc5]. The Ansible and Arch pages list the keytab-plus-GSSAPI recipe for
`host/<fqdn>` [src: archwiki 5e3170d85c55a2e9].

**Hardening note.** Security baselines disagree in a way worth understanding. Red Hat and DISA STIGs for general
servers require `GSSAPIAuthentication no` and `KerberosAuthentication no` unless the site needs them, to shrink the
attack surface of sshd [src: disa-stig 8a6bd63dadb68295] [src: disa-stig bd4c598035a16561]. Directory-joined estates
turn GSSAPI on deliberately and disable password logins instead. The correct reading is not that one rule is wrong:
the baseline assumes no Kerberos realm, and a realm member overrides it with documented exceptions
[src: compliance-as-code 6ebbd515250c3411].

**Generalised pattern.** The reusable shape is a ticket broker issuing short-lived, scoped credentials against a
shared secret store, with applications talking to an abstraction (GSSAPI) rather than the protocol. Anything that
follows this shape (OAuth token issuers, cloud STS) shares Kerberos's operational concerns: clock accuracy, key
rotation, and the blast radius of the broker's own key.

## Assessment: the good, the bad and the ugly

**Good.** Passwords stay out of services; compromise of a web server does not leak user passwords. Single sign-on
reduces prompts and the habit of reusing passwords. Authentication is mutual, so clients can detect a fake server.
Tickets expire, so a stolen cache has a bounded window. Keytabs let daemons authenticate without human secrets.
Delegation (forwarding) lets a front-end act for the user toward a back-end under policy. GSSAPI makes it cheap for
application authors: the same code path covers Kerberos, NTLM (through SPNEGO) and others.

**Bad.** It is name-and-time sensitive. A forward and reverse DNS mismatch changes the service name the client builds,
and canonicalisation settings (`rdns`, `dns_canonicalize_hostname`) have changed their defaults across releases, so a
setup that worked in one distribution release can fail in the next. Clock skew beyond five minutes fails every
exchange. KDC availability is a hard dependency: when all KDCs are down, new tickets cannot be issued and existing
ones expire. Cross-realm trust needs careful capath configuration. Debugging is hard without `KRB5_TRACE`, because
client error messages are terse and the KDC log is on another host.

**Ugly.** Keytabs are long-lived, unencrypted, password-equivalent secrets. A leaked `/etc/krb5.keytab` lets an
attacker impersonate the host indefinitely until the key is rotated, and the attacker can then request tickets to any
service that trusts that machine. Known attack classes target Kerberos in AD: AS-REP roasting of accounts without
pre-authentication, Kerberoasting service accounts whose tickets are encrypted under weak RC4 keys, unconstrained
delegation abuse, and forged tickets ("golden" with the `krbtgt` key, "silver" with a service key). Old defaults
linger: RC4-only service accounts, `allow_weak_crypto`, and `ssh -K` forwarding a TGT to hosts that do not deserve it.
Kernel keyrings and KCM change where tickets live and surprise administrators who look in `/tmp`. On the human side,
password change flows through `kpasswd` or `passwd` over port 464 are often missed in firewalls.

Mitigations: AES-only enctypes, mandatory pre-authentication, `krbtgt` rotation procedures, per-host keytabs, a
protected-users group in AD, constrained delegation, shorter ticket lifetimes, and monitoring for unusual
service-ticket requests.

## Applications beyond this domain

Kerberos is the authentication layer under NFSv4 with `sec=krb5p`, CIFS/SMB mounts (`mount.cifs -o sec=krb5`),
PostgreSQL's `gss` method, Apache `mod_auth_gssapi`, Hadoop and Kafka in secured clusters, LDAP SASL/GSSAPI binds
(`ldapsearch -Y GSSAPI`), CUPS, `sudo` via `pam_sss_gss`, and web browsers using SPNEGO against intranet sites. The
KDC-issued short ticket pattern reappears in AWS STS, OAuth2 access tokens and SSH certificates: a trusted issuer
signs a short-lived assertion so that long-term secrets do not travel. The libvirt and QEMU documentation show
SASL (which can use GSSAPI) protecting hypervisor sockets and VNC [src: libvirt-docs c6a193cd32c54561]
[src: qemu-docs 14e0d339198fc908], an example outside the identity domain.

## Examples

**Successful: keytab-based SSH for a service host.** On the KDC: `kadmin.local -q "addprinc -randkey
host/web1.example.com"`, then `ktadd -k /root/web1.keytab host/web1.example.com`; copy the file securely to the host
as `/etc/krb5.keytab` (mode 0600). On the host, set `GSSAPIAuthentication yes` in `sshd_config` and restart. From a
client with a valid TGT, `ssh -o GSSAPIAuthentication=yes web1.example.com` logs in without a password if the
principal maps to a local user. `klist` afterwards shows a new `host/web1.example.com` service ticket, which proves
the path actually used Kerberos rather than falling back to keys.

**Failing: password prompt despite a ticket.** The client holds a ticket for `alice@EXAMPLE.COM` but connects to
`web1` by short name or by a CNAME. The client canonicalises or not, builds a principal such as
`host/web1.example.com` or `host/www.example.com`, the KDC lacks it, and GSSAPI quietly falls back. `ssh -vvv`
shows `Unspecified GSS failure ... Server not found in Kerberos database`. The fix is to connect by the real FQDN,
add an alias principal, or set the `dns_canonicalize_hostname` option deliberately.

**Failing: skew.** A VM resumed from a snapshot with an old clock gets `KDC reply did not match expectations` or
`Clock skew too great`; `chronyc makestep` restores service. A time-sync dependency belongs in the monitoring list
(LNX-302-T05 treats AD time).

**Failing: stale keytab.** After `ktadd` is run a second time on the KDC, the host's keytab holds an old key version.
`klist -ke` on the host shows `kvno 3` while `kvno host/web1.example.com` on a client reports 4; services answer
`Decrypt integrity check failed`. Re-export and replace the keytab.

## Related problems and ideas

Alternatives to the shared-secret ticket model include public-key SSH certificates signed by a CA (no KDC needed,
revocation by short lifetime), TLS client certificates with mTLS, and OIDC tokens for web applications. Within the
Kerberos family, Heimdal remains in some distributions and in Samba. Cross-platform SPNEGO is the usual way a Linux
browser or `curl --negotiate` authenticates to a Windows intranet site. Newer ideas: **FAST armoring** so that
pre-authentication and password guesses cannot be captured on the wire; **OTP and two-factor flows** such as FreeIPA's
`otp` auth type; **PKINIT** for smart cards (LNX-301-T10); and **constrained delegation with S4U2Proxy** to limit what a
front-end can do on behalf of users. A different line of thought rejects centralised keys altogether and relies on
device-bound credentials such as WebAuthn passkeys, with Kerberos adopted only for legacy access.

## Active research

Work on MIT Kerberos concentrates on crypto agility (HMAC-SHA2 enctypes, elliptic-curve PKINIT), on safer GSS
message parsing after a series of CVEs in token handling, and on better client behaviour against slow or half-dead
KDCs; the 1.22 line includes ECDH support in PKINIT and a rewrite of GSS per-message token parsing [web: web.mit.edu].
Researchers study attacks on delegation and PAC validation, and the integration of post-quantum signatures in
certificate-based pre-authentication is under discussion. Open questions include how to make keytab protection
hardware-backed (TPM-bound keys), how to monitor ticket abuse at scale, and how long RC4 compatibility can remain for
old Windows trusts.

## Future direction

Expect further removal of weak encryption types and of DES-era code, stronger default `rdns` and canonicalisation
behaviour, and more automation around ticket-less client flows (SSSD handling renewals, KCM for credential caches in
containers). Microsoft has staged enforcement for PAC validation and RC4 retirement in Windows Server through 2025 and
2026 (to verify the final enforcement dates). The MIT 1.22 series was released in August 2025 with 1.22.2 following in
January 2026 [web: web.mit.edu]. For practitioners, the watch-list is crypto-policy changes in distribution releases,
any move toward hardware-bound keytabs, and PKINIT with elliptic curves.
