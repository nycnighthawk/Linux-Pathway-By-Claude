# Joining Linux to a genuine Windows Active Directory

## Define the problem

The Linux host that joins a Samba lab domain meets few obstacles. The same command aimed at a production Windows
domain meets an organisation: a security team that decides who may create computer objects, a domain controller
fleet with hardening policies the lab never had, group policy objects that may or may not apply to Linux, multiple
sites and forests, and a Windows administrator who has never heard of `realm` and wants to know exactly what the
Linux machine will do to the directory. The technical task is the same as in LNX-301-T04: discover, enrol, store a
keytab, configure SSSD. The difficulty is everything around it.

Four questions must be answered before any command runs. What identity will perform the join, and what rights does
it have? Where will the computer object live, and who owns it afterwards? How will UIDs and GIDs be assigned, given
that file ownership on the Linux side will depend on the answer for years? And which controls on the domain side
(LDAP signing, channel binding, encryption-type policy, protected users, logon workstation restrictions, GPO-based
access rules) will touch the host? A mismatch on any of these produces symptoms that look like Linux bugs while the
cause sits in Active Directory.

This slice is a manual, supervised procedure rather than an automated one because the sandbox cannot host a
licensed Windows DC. It covers the permission model, the join variants (online with `realm`/`adcli`, pre-staged,
offline), post-join verification, and how to work with the AD team. It assumes the direct-integration pattern; the
alternative of running IdM with a trust is in LNX-301-T07, and the broader operational view of Linux in an AD estate
is LNX-302-T10.

## History and approaches

Windows 2000 introduced Active Directory with a Kerberos realm named after the DNS domain, dynamic DNS registration of
SRV records and a domain-join procedure that creates a computer account with a machine password changing every 30
days. Linux hosts were at first seen as foreign objects: Samba 3 joined as a member server, and nothing else was
standard. The first widely used non-Samba approach was Services for UNIX (SFU) and later the "Identity Management for
UNIX" role, which added `uidNumber`, `gidNumber` and `unixHomeDirectory` editing to the Users and Computers tools,
with an NIS server component. NIS server on a domain controller was then deprecated and removed in Windows Server 2012
R2, but the RFC 2307 attributes remained in the AD schema and still serve as an approach to explicit POSIX IDs.

Commercial agents (Quest Vintela, Centrify, Likewise) filled the Linux gap in the 2000s with proprietary clients and
per-seat licences, and with GPO-like management for Unix. They worked but built dependency on a vendor and were slow
to follow distributions. Red Hat's route was SSSD with its AD provider and the `realmd` front-end, so that the
open-source stack matched the commercial clients on core features. Hardening changes from Microsoft shaped the
history: NTLM weaknesses led to Kerberos preference; LDAP signing and channel binding advisories (2019, enforcement
phases 2020 onward) altered client requirements; RC4 and DES were removed from default policies in steps. Each wave
broke some Linux clients that had worked for years, and each was fixed by an SSSD or Samba release plus
configuration.

An important partial success is offline domain join (`djoin.exe`, Windows 7 and Server 2008 R2). A privileged
administrator provisions the computer account and obtains a blob that carries the machine secret; the joining
machine applies the blob without contacting a DC or holding any domain privileges. Samba added the same APIs in
4.15 (`net offlinejoin provision` and `requestodj`) [src: samba-docs 57d8129793fea55f], and Microsoft's documentation
recommends the offline approach because it minimises the rights needed and lowers exposure
[src: ms-learn-adds b09ec2f9ac71f083]. Linux does not consume Microsoft's blob directly but a Linux admin can emulate
it with a pre-staged account and a one-time password join in `realm join --one-time-password`.

Lessons: separate the enrolment right from general administration; avoid user-based machine-account quota; stage
accounts; and make the whole operation scriptable so that it stays reviewable.

## Current state

**Who may join, and how.** In AD, a joining user needs a right to create or reuse the computer object. Microsoft
documents two scenarios. In the first, the account does not exist and the join creates it with an LDAP add under the
user's credentials; the user needs either the "Add workstations to domain" right, controlled by the domain attribute
`ms-DS-MachineAccountQuota` (default 10 machines per user), or the ability to add computer objects inside the
  target OU. The vendor discourages the quota route, since every ordinary user becomes able to create objects
[src: ms-learn-adds eb81f2b1d123048d]. In the second scenario the object already exists, and the joiner needs rights
to modify it, specifically reset password, write the account restrictions, DNS host name and service principal name
attributes, and validated writes to the DNS host name and SPN. Admin teams commonly delegate a dedicated service
account with "Create Computer objects" on a `Linux` OU, nothing more [src: ms-learn-adds b09ec2f9ac71f083].

**Pre-flight checks on the Linux host.** Run through the same prerequisites as with Samba: DNS served by the
domain's DNS (`resolvectl status` or `nmcli` to see which), host FQDN set with `hostnamectl set-hostname
app01.corp.example.com`, no `127.0.1.1` alias, time sync by `chronyd` against the domain or a common source, and
packages `realmd sssd adcli krb5-workstation oddjob oddjob-mkhomedir samba-common-tools`. Test reachability of DNS 53,
Kerberos 88, kpasswd 464, LDAP 389 and 3268 (global catalog), LDAPS 636 and 3269, and SMB 445 with `nc -zv`. AD
sites matter: SSSD finds the closest DC through the client's site, which is determined by its IP address in
the AD subnets; if the subnet is not defined, the host will pick distant DCs and logins are slow (`ad_site` forces a
site).

**Online join.**

```text
realm discover corp.example.com
realm join -v -U svc-linuxjoin --computer-ou='OU=Linux,OU=Servers,DC=corp,DC=example,DC=com' corp.example.com
realm list
klist -ke /etc/krb5.keytab
id jsmith@corp.example.com
```

Without `--computer-ou`, the object lands in the default `Computers` container, which many organisations do not
manage. Inspect the keytab output: it should hold `host/app01.corp.example.com`, `host/APP01`, `APP01$` and
`RestrictedKrbHost/...` principals with AES types. Check `sssctl domain-status corp.example.com` and, where
available, `sssctl user-checks jsmith` for a one-shot test of NSS, PAM and access control.

**Pre-staged and one-time-password join.** The AD team creates `APP01$` in the right OU and sets an initial password.
The Linux admin runs `realm join --one-time-password='...' corp.example.com` (or `adcli join --one-time-password`),
which uses the machine account's own password to authenticate as itself and then replaces it with a random one,
giving enrolment without any user credentials on the host. Red Hat's `ad_integration` system role automates both
variants for fleets, for use when there is no IdM [src: rhel-10-docs 157d2e05d2589a03]. Password handling still
matters: pass the one-time secret from a secrets manager, not from the command history.

**Managed service accounts without join.** For a single service that only needs to read AD (a reporting tool, an
application that does LDAP lookups), Red Hat describes using a Managed Service Account instead of a full domain
membership, so the host does not become a domain member at all [src: rhel-10-docs 8394ffb031c251cb]. The result is a
smaller trust footprint. It is a design option that belongs in the discussion with the AD team.

**ID mapping choice.** For a Windows-owned directory, the default ID mapping from SID is the lowest-effort path and
consistent between SSSD hosts, but the mapping is not what Windows or the NFS server knows. If the organisation
already stores POSIX attributes (via Identity Management for UNIX or a provisioning tool), set `ldap_id_mapping =
False` and let SSSD read `uidNumber`/`gidNumber` from AD, ideally with those attributes published to the global
catalog [src: rhel-10-docs e5f6fffc0c7e3e8a]. Every user without the attributes becomes invisible to Linux in that
mode, so a data audit comes first. The detail and the tradeoffs belong to LNX-301-T08.

**Domain-side controls to expect.**

- *LDAP signing and channel binding.* Domain controllers may require signed LDAP or TLS channel binding. SSSD
  negotiates SASL/GSSAPI with signing and sealing by default for its AD LDAP queries, so it normally copes; custom
  `ldapsearch` scripts with simple binds fail until they use `-Y GSSAPI` or LDAPS.
- *Encryption types.* Computer accounts have `msDS-SupportedEncryptionTypes`. If the domain allows only AES, the
  host must request AES; SSSD sets this on the account at join. On RHEL, the system-wide crypto policy governs allowed
  enctypes and `update-crypto-policies --set DEFAULT:AD-SUPPORT` exists for legacy RC4 domains.
- *Group Policy.* The SSSD AD provider reads the GPO list of the host's OU and evaluates the interactive and remote logon rights
  settings, which it maps onto PAM service names. A GPO written
  for Windows that denies a group can lock Linux users out. The option `ad_gpo_access_control` has three modes:
  `disabled`, `permissive` (log only) and `enforcing`. Use `permissive` during rollout, then `enforcing`.
- *Machine password aging.* AD does not enforce a rotation on non-Windows machines, but SSSD renews at its configured
  interval (`ad_maximum_machine_account_password_age`). Account lifetime and "stale computer" cleanup scripts run by
  AD teams can delete an object that has not logged on, which they identify by the `lastLogonTimestamp`; a Linux
  server that only uses user logons may appear idle.
- *DNS updates.* SSSD can register the host's A and PTR records (`dyndns_update = True` by default under the AD
  provider, with secure dynamic updates). If the zone forbids this, set `dyndns_update = False` and ask for static
  records.
- *Protected Users and logon restrictions.* Members of Protected Users cannot use NTLM or long-lived TGTs; users with
  "Log on to" workstation limits (`userWorkstations`) will fail on Linux unless the host name is listed.

**Verification checklist.** After a join: `realm list` shows `configured: kerberos-member`; `kinit -k APP01$` obtains a
ticket; `getent passwd` and `getent group` return a domain user and group; `id` shows nested groups; `ssh` as an AD
user logs in using the password and with GSSAPI from a client that holds a TGT; `sudo -l` shows expected rules if the
site uses AD groups in sudoers; `journalctl -u sssd` and `/var/log/sssd/sssd_corp.example.com.log` (debug level 6) show
the DC chosen; the AD team confirms the computer object, its OU, operating-system attributes and SPNs; and a
`realm leave` followed by a rejoin has been rehearsed on a throwaway host.

**Generalised pattern.** Enrol least-privilege, stage identities, bind to a policy engine owned by someone else, and
verify through both the client's and the authority's views. The same governance logic applies to joining a cloud
tenant or an MDM system.

## Assessment: the good, the bad and the ugly

**Good.** The result is single sign-on for every AD user, immediate lifecycle control (a disabled AD account is
disabled on Linux, subject to cache), group-based access, and no separate Linux user database. The tooling is stable
and supported by Red Hat, SUSE, Canonical and the community. Because AD is also a Kerberos KDC, Kerberised services
(NFS, SMB, SSH) join the same trust network.

**Bad.** Identity ownership is contentious. UID decisions are made once and are hard to change. AD teams view
Linux as a risk and may impose naming restrictions (NetBIOS 15-character limits, OU conventions). Policy collisions
(GPO logon rights) cause confusing denials. Documentation scatters across vendors; the Windows side's names for
settings differ from SSSD's. Troubleshooting needs two administrators: one with SSSD logs, one with Event Viewer on
the DC (Security events 4768, 4769 and 4771 for Kerberos, 4624 for logons).

**Ugly.** A leaked or over-privileged join account is a foothold in the domain. Overly broad delegation (for example
domain admin used for joins) shows up in security audits and sometimes in intrusions: attackers search for join
credentials in kickstart files and shell history. Machine-account quota left at its default lets any user create a
machine that then appears in privileged paths. A Linux host trusted for delegation may later let an attacker
impersonate users to other services. Hardening campaigns such as RC4 removal appear as sudden login failures for
long-running servers whose machine passwords were last set under old policy: the password must be rotated
(`adcli update` or `net ads changetrustpw`) so that AES keys exist.

Mitigations: delegated join account with only OU create rights, short-lived credentials, one-time-password joins,
`ad_gpo_access_control = permissive` in a pilot, explicit `access_provider = simple` with group lists if GPO is not
trusted, regular `klist -ke` audits, and written runbooks that both teams have read.

## Applications beyond this domain

The delegated-enrolment-plus-secret pattern shows in cloud: AWS Systems Manager hybrid activations, Azure Arc
onboarding service principals, Kubernetes bootstrap tokens (compare `kubeadm join`, whose token and CA hash are
analogous to one-time passwords and trust anchors [src: kubernetes-docs 0b226da1572d0d43]) and MDM enrolment profiles.
Windows nodes joined to a Kubernetes cluster use the same style of join command and need their own gMSA
configuration for pods that authenticate to AD. Offline provisioning of secrets (djoin blobs) resembles
pre-generated cloud-init seeds and TPM-sealed enrolment. The compliance baselines that reference LDAP and Kerberos
settings (DISA STIG and the open compliance content) apply the same logic to hardening a joined host
[src: compliance-as-code db8839c5dad585d0].

## Examples

**A successful, governed join.** The AD team creates `svc-linuxjoin` with rights to create computer objects in
`OU=Linux,OU=Servers`. Operations run `realm join` from a kickstart `%post` using a one-time vault lease for the password.
Afterwards the account's password is rotated. The computer objects appear in the OU, GPO links on that OU enable
SSH-rights policy, and Linux logons are limited to the `Linux-Admins` and `Linux-Users` groups with `realm permit -g`.

**Failing: insufficient access when rejoining.** An app server is rebuilt. `realm join` returns `Insufficient access`
because the old `APP01$` object exists in another OU, owned by the Windows team, and the delegated account cannot
modify it. The fix is not a more powerful account: ask the AD team to move or delete the object, or use a new name.

**Failing: logins denied by policy.** After the join, `jsmith` authenticates (the password is accepted) but `ssh`
closes the connection. `sssd_corp.log` shows `GPO-based access control denied`; a GPO linked to the Servers OU grants
logon right only to `Domain Admins` for the `sshd` service mapping. Setting permissive mode shows the matches; the proper
fix is a GPO in the Linux OU and an agreement with the AD team.

**Failing: DNS.** The Linux host's `/etc/resolv.conf` is managed by cloud-init to a cloud resolver. `realm discover`
fails with `No such realm found`. The right fix is a conditional forwarder for `corp.example.com` in the VPC
resolver; changing the host's resolver fixes only that host.

**Failing: signing.** A custom script uses `ldapsearch -x` with a bind DN, and the DC returns
`Strong(er) authentication required`. LDAP signing is enforced. Replace with `-Y GSSAPI` after `kinit`, or use
LDAPS (port 636) with the domain CA in `TLS_CACERT`.

## Related problems and ideas

Alternatives to joining the host: IdM with a cross-forest trust (LNX-301-T07), which keeps Linux policy in IdM and
needs no AD object per host; Entra ID based Linux login for cloud VMs; certificate-based SSH with identities issued
from an HR system; and LDAP-only integration (SSSD `ldap` provider with a bind account) for read-only needs, which
loses Kerberos SSO. Related problems: smart-card login against AD certificates (LNX-301-T10), Kerberos for NFS and SMB
(LNX-302-T04, T09), AD DNS and time (LNX-302-T05), and automated lifecycle of machine accounts as hosts come and go in
autoscaling groups. Microsoft's Windows LAPS manages local administrator passwords for Windows; there is no official
Linux client, so Linux root-password rotation uses other tools.

## Active research

Research and engineering effort concentrates on removing long-lived secrets from host enrolment (attested identities
from TPMs and cloud instance metadata), on detecting abuse of delegation and computer-account takeover, and on
tracking the tightening of Windows Kerberos (PAC validation, RC4 and NTLM removal). SSSD work addresses passkey and
FIDO2 sign-in, better offline behaviour, and GPO evaluation; Samba work addresses compatibility with the same Windows
changes. Open questions: how to give auditors one view of both Windows and Linux access, and how to expire stale Linux
computer objects safely.

## Future direction

Expect AES-only domains and NTLM-off policies to become default at Windows Server's pace (to verify the dates for
each release), more cloud-managed directories reachable by LDAPS and Kerberos proxy, and a gradual shift of Linux
login toward OIDC and passkeys with AD kept for file services and legacy applications. A practitioner should keep an
eye on SSSD release notes, Microsoft's KB articles on Kerberos and LDAP hardening, and distribution crypto-policy
changes, since each can break a join that worked yesterday.
