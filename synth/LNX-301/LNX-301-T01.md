# LDAP servers and clients: a directory that every host can ask

## Define the problem

A fleet of Linux hosts needs one place to ask questions that change slowly but must be answered the same way
everywhere: who is user 2041, which groups does she belong to, which hosts may she log into, what is the public SSH key
of this service account, where is the mail server for this domain. Copying `/etc/passwd` to every machine solves this
for five hosts and fails at fifty: the copies drift, a departed employee survives on the one box nobody pushed to, and
a password change needs a push to every machine.

The directory is the answer to that gap. It is a network database tuned for the opposite workload from a transactional
SQL store: many reads, few writes, hierarchical data, schema-defined attributes, and replication that tolerates a site
being offline. The Lightweight Directory Access Protocol (LDAP) is the common wire protocol for talking to such a
database, and an LDAP server is the thing that stores entries and enforces who may read or change them.

Failure in this domain has a recognisable look. A client cannot resolve a user because the search base is wrong or the
server certificate does not match the name in the URI. Logins take thirty seconds because the client waits on a dead
replica. A bind works for an administrator and fails for a service account because an access rule hides the
`userPassword` attribute. A group lookup returns nothing because the `memberUid` attribute is expected by one schema and
`member` by another. This slice covers the LDAP data model, how an OpenLDAP server stores and protects it, how a client
is configured and tested with `ldapsearch`, and how all of this connects to the rest of the course, where SSSD
([LNX-301-T03](lesson:LNX-301-T03)) and Kerberos ([LNX-301-T02](lesson:LNX-301-T02)) sit on top of it.

## History and approaches

Before directories there were flat-file databases distributed by hand, then Sun's NIS (Yellow Pages), which broadcast
maps to clients on a LAN. NIS was simple and fast to deploy, but it had no encryption, no fine-grained access control
and a single trust domain per broadcast network; anyone who could reach the server could fetch the password map and
crack the hashes offline. NIS+ tried to fix this with authentication and tables, but its complexity doomed it outside
Sun shops.

The International Telecommunication Union's X.500 standard (1988) described a global, hierarchical directory with a
heavy OSI protocol stack, DAP. Almost no one deployed DAP on the Internet. At the University of Michigan in 1993,
Tim Howes and colleagues defined a lightweight gateway to X.500 that spoke over TCP; that is LDAP version 1. LDAPv2
followed (RFC 1777), and LDAPv3 (RFC 2251, 1997, now consolidated in RFC 4510 through 4519) added SASL
authentication, referrals, extensible controls and, with StartTLS (RFC 2830), channel security. Netscape's server
lineage became Red Hat Directory Server and later the open 389 Directory Server; the University of Michigan code was
the ancestor of OpenLDAP, started in 1998 as a fork.

Linux integration came by the nss_ldap and pam_ldap modules, written by Luke Howard (PADL). They worked but
embedded LDAP code into every process that looked up a user, so a hung server stalled `ls -l`, caching was crude, and
reconnection logic lived in a library loaded into `sshd`, `cron` and `sudo`. The Debian handbook documents this
generation of setup, where `libnss-ldapd` and `nslcd` mediate NSS lookups; `nslcd` is a local daemon that holds the
connection, a small step toward the separated design that SSSD later perfected [src: debian-handbook 260619cf95495740].

Server software had its own failures. OpenLDAP up to 2.3 configured slapd from a text file, `slapd.conf`, which needed
a restart for any change. Version 2.4 introduced the dynamic `cn=config` tree (the `slapd-config` format), so access
rules, schemas and databases are entries edited at run time [src: man-pages eecc4840c43e57a3]. The old Berkeley DB
back ends (`bdb`, `hdb`) wore out as BDB's licence changed and its recovery behaviour caused corruption after crashes;
Howard Chu's LMDB-based `mdb` back end replaced them in 2.4.x and became the only supported general-purpose database in
2.5 and later. Replication went from the one-way `slurpd` push to `syncrepl` (RFC 4533), where the consumer pulls
changes, and later to multi-provider (formerly multi-master) set-ups.

The emerging pattern is a split of responsibilities: a directory server owns the data; clients speak LDAPv3 over TLS;
a local caching daemon owns the connection and the cache; Kerberos or a password bind owns authentication; and
higher-level suites (FreeIPA, Active Directory) package all of these with one administration surface.

## Current state

**The data model.** An LDAP directory is a tree, the Directory Information Tree (DIT). Each node is an entry, named by
a Distinguished Name (DN) such as `uid=alice,ou=people,dc=example,dc=com`. The leftmost component is the Relative
Distinguished Name (RDN), which must be unique among siblings. An entry has attributes, each with one or more values,
and one or more `objectClass` values that decide which attributes are required (MUST) and allowed (MAY). A schema is
the set of attribute type and object class definitions; OpenLDAP ships `core`, `cosine`, `inetorgperson` and `nis`
(which carries `posixAccount`, `posixGroup` and `shadowAccount`, the RFC 2307 account attributes). Matching rules
determine how comparisons behave: `uid` is case-insensitive, `userPassword` is an octet string.

**Operations.** The protocol has bind (authenticate), search, compare, add, modify, modify DN, delete, extended
operations (StartTLS and password modify, RFC 3062) and unbind. A search has four decisive parameters: the base DN, a
scope (`base`, `one`, `sub`), a filter such as `(&(objectClass=posixAccount)(uid=alice))` and the list of attributes
to return. Many client failures reduce to a wrong base, a wrong scope or a filter that the schema does not match.

**Server side with OpenLDAP.** The daemon is `slapd`. On RHEL-family distributions OpenLDAP servers were removed from
the default repositories from RHEL 8; Red Hat points users to its own Directory Server or to IdM, while Debian and
Ubuntu package `slapd` and Alpine, Arch and SUSE keep it (to verify per release). In upstream, OpenLDAP 2.6 is the
long-term-support line and 2.7 the current feature line [web: ldap.com] [web: openldap.org]. A minimal modern install
creates a database entry under `cn=config`, an `mdb` backend, and a suffix:

```text
olcDatabase: {1}mdb
dn: olcDatabase={1}mdb,cn=config
objectClass: olcMdbConfig
objectClass: olcDatabaseConfig
olcDbDirectory: /var/lib/ldap
olcSuffix: dc=example,dc=com
olcRootDN: cn=admin,dc=example,dc=com
olcAccess: {0}to attrs=userPassword by self write by anonymous auth by * none
olcAccess: {1}to * by group.exact=cn=dirsys,ou=groups,dc=example,dc=com manage by users read
olcDbIndex: uid,uidNumber,gidNumber,memberUid eq
```

Three details here matter in practice. First, access rules (`olcAccess`, or `access to` in the legacy `slapd.conf`
[src: man-pages 533b7b8553cebe07]) are ordered and the first matching `to` clause wins, so the numeric index inside
braces is semantically important; inserting a broad rule ahead of a narrow one silently exposes data. Second, the
`peercred` identity (SASL EXTERNAL over a local socket) is how root on the server administers `cn=config` over the `ldapi:///` UNIX socket without a
password, using SASL EXTERNAL. Third, indexes are not optional at scale: a filter on an unindexed attribute turns a
search into a full database scan, and the symptom is one CPU pinned during login storms. `slapd.log`-style
debugging uses `olcLogLevel: stats` for one line per operation, which is the right default.

Configuration is changed with `ldapmodify -Y EXTERNAL -H ldapi:///`, data is loaded with `ldapadd`, and `slapcat` plus
`slapadd` dump and restore offline, a backup method that does not need the server to be reachable. Password hashes in
`userPassword` should be salted (`{SSHA512}` in older setups, or `{ARGON2}` through the contributed module in newer
ones). The `ppolicy` overlay supplies lockout and history; `memberof` and `refint` maintain reverse group membership and
referential integrity; `syncprov` is what makes a server a replication provider.

**Transport security.** An LDAP bind sends the password in clear unless the channel is protected. Two mechanisms exist:
`ldaps://` on port 636, which wraps the whole connection in TLS and was never standardised but is universal, and
StartTLS on port 389, an extended operation that upgrades an existing connection. Both need a server certificate whose
subject alternative name matches the hostname the client uses; configure `olcTLSCertificateFile`,
`olcTLSCertificateKeyFile` and `olcTLSCACertificateFile` on the server, and set `olcSecurity: ssf=128` or
`olcSecurity: tls=1` to refuse weak or plaintext sessions. Hardening guides for Red Hat and Ubuntu make this point
about SSSD back ends too: an LDAP provider that does not require TLS is a finding [src: compliance-as-code db8839c5dad585d0].

**Client side.** The OpenLDAP client library reads `/etc/openldap/ldap.conf` (or `/etc/ldap/ldap.conf` on Debian)
with `URI`, `BASE`, `TLS_CACERT`, `TLS_REQCERT` and `SASL_MECH` options; per-user overrides in `~/.ldaprc` are possible
[src: man-pages 15f05b58adb9c9e5]. The command-line tools then work as follows:

- `ldapsearch -x -H ldaps://ldap.example.com -b dc=example,dc=com '(uid=alice)' uidNumber gidNumber` does a simple
  (`-x`) anonymous search. `-D <binddn> -W` supplies a bind DN and prompts for the password; `-Y GSSAPI` authenticates
  with a Kerberos ticket instead; `-LLL` strips the LDIF noise; `-ZZ` insists on StartTLS and aborts if the upgrade
  fails (a single `-Z` carries on without it).
- `ldapwhoami -Y EXTERNAL -H ldapi:///` prints the identity the server sees, which is the fastest way to debug access
  control.
- `ldappasswd` calls the password-modify extended operation so the server hashes the value itself.
- `ldapmodify`, `ldapadd`, `ldapdelete` and `ldapmodrdn` apply LDIF change records.

Login integration for NSS and PAM is normally done by SSSD with `id_provider = ldap`, covered in
[LNX-301-T03](lesson:LNX-301-T03), whose `ldap_uri`, `ldap_search_base` and `ldap_tls_reqcert` options correspond
one-to-one to the client concepts above. The older `nslcd`/`libnss-ldapd` pair remains in Debian and is a reasonable
choice for a single-purpose server that only needs lookups.

**Generalised pattern.** A directory deployment has four parts: schema and DIT design (where do people, groups, hosts
live), a server with access control and replication, a client library with TLS trust, and a caching resolver that
turns directory entries into POSIX identities. Failures localise to one of those four, which is how to debug.

## Assessment: the good, the bad and the ugly

**Good.** LDAP is an open, widely implemented standard; every language has a client. Reads are fast, especially on
LMDB with correct indexes: tens of thousands of searches per second on commodity hardware is ordinary. A single
change reaches all clients, and `syncrepl` gives read scaling and survives a provider outage. Access control by
attribute and by identity lets a service account read hashes of nobody while a host account reads only its
subtree. The tools are scriptable and LDIF is diffable text, so directory state can live in version control.

**Bad.** The schema language and the protocol are unforgiving. A typo in an `olcAccess` clause can lock out the
administrator or leak hashes, and there is no dry run. Plain OpenLDAP provides no web interface, no user lifecycle
policy, no built-in Kerberos, no DNS and no certificate management, so a team that starts with "just LDAP" ends up
building a bad FreeIPA. Two group models coexist (`posixGroup` with `memberUid` listing names, and `groupOfNames` with
`member` listing DNs), and clients disagree on which to read; SSSD's `ldap_schema` of `rfc2307` versus `rfc2307bis`
chooses between them. Nested groups are not transparent: plain search does not expand them, so applications that need
transitive membership must use `memberof` overlays or AD's `LDAP_MATCHING_RULE_IN_CHAIN`.

**Ugly.** Anonymous binds left enabled expose the user list and sometimes hashes. Clients with `TLS_REQCERT never`
(or `ldap_tls_reqcert = never` in SSSD) accept any certificate, which turns TLS into decoration against an active
attacker; the setting survives in many fleets because a certificate once failed in testing and nobody reverted it.
Replica certificates that expire silently break replication and, after a TTL, logins. The `userPassword` attribute, if
readable by `by * read`, lets any authenticated user harvest salted hashes for offline cracking. Back-end indexes missing
on `memberUid` produce the login-storm symptom described above. Operational ownership is also unclear: directory teams,
Linux teams and security teams each own part of the stack, and no one tests failover until it fails.

Mitigations are standard: ship the `cn=config` LDIF in version control, test `olcAccess` changes with `slapacl -b
<dn> -D <binder> <attribute>` before applying them, monitor `cn=Monitor`, back up with `slapcat` on a schedule and
restore-test it, keep two replicas with distinct certificates and alert on certificate expiry.

## Applications beyond this domain

The directory idea (tree-structured, attribute-based, read-heavy, replicated) appears well outside user login.
Active Directory is an LDAP and Kerberos directory plus Microsoft extensions, so every LDAP client skill transfers
directly to AD troubleshooting ([LNX-301-T04](lesson:LNX-301-T04)). Mail servers (Postfix virtual maps, Dovecot user
databases), RADIUS and VPN gateways, sudo (`sudoers.ldap`, now mostly replaced by SSSD sudo rules), automount maps,
SSH public keys (`sshPublicKey` with `AuthorizedKeysCommand`), network devices and Kubernetes dashboards all authenticate
against LDAP simply by being told a URI, a base and a bind DN. The libvirt documentation shows the same SASL machinery
used to protect a hypervisor's management socket [src: libvirt-docs c6a193cd32c54561]. LDAP's search filter syntax and
tree model also survive in Active Directory Federation, SCIM provisioning and cloud identity "LDAP interface" products
that expose a hosted user store to legacy applications.

## Examples

**A working client probe.** Given `ldap.example.com` with certificates from an internal CA, a first check is:

```text
ldapsearch -x -ZZ -H ldap://ldap.example.com -b ou=people,dc=example,dc=com -LLL '(uid=alice)' dn uidNumber loginShell
```

If this returns the entry, the transport, trust and base are sound and what remains is SSSD or NSS configuration. If
it prints `Can't contact LDAP server (-1)` the failure is below LDAP: DNS, firewall or TLS. `ldapsearch -d1` prints
the library trace, and a certificate name mismatch appears there before anything else.

**A failing example: invisible hashes.** An administrator adds the rule `to * by * read` ahead of the `userPassword`
rule. Binds still work, because authentication itself bypasses read ACLs for the entry being bound, so the change
looks harmless. A user then runs `ldapsearch -x -D uid=bob... -W '(uid=alice)' userPassword` and obtains Alice's
hash. The cause is rule order; the fix is to put the narrow rule first and verify with `slapacl`.

**Another failure: the wrong group schema.** A directory populated from an Active Directory export uses `member: <DN>`
attributes. The Linux client is configured for RFC 2307, so it reads `memberUid` and finds nothing: `id alice` shows
only the primary group. Setting `ldap_schema = rfc2307bis` in SSSD (or `ldap_group_member = member`) corrects it.

**Replication.** Two providers with `syncprov` and `olcSyncrepl` stanzas pointing at each other, each with a distinct
`olcServerID`, form a multi-provider pair. Writes to either side converge; conflicting writes are resolved
last-writer-wins on entry CSNs, so applications should write to one node at a time behind a load balancer's health
check, which preserves the benefit (survival) without the surprise (silent overwrites).

## Related problems and ideas

Alternatives for the same job exist at different levels. NIS survives in legacy networks and should be treated as a
migration task. 389 Directory Server offers a web console, multi-supplier replication and a packaged lifecycle with
Red Hat's Directory Server and FreeIPA as its main consumer. Kerberos with SSSD's `files` provider handles
authentication without any directory. Samba acting as an AD domain controller supplies LDAP, Kerberos and DNS together
([LNX-301-T04](lesson:LNX-301-T04)), and Samba's `idmap_ldap` and `idmap_rfc2307` back ends store or read POSIX IDs
from an LDAP server [src: samba-docs 7f93815b1a6832b5] [src: samba-docs 0c75c95fe1f8e958]. Cloud-hosted identity
platforms (Entra ID, Okta, Google Workspace) expose SAML and OIDC rather than LDAP; for Linux logins they are bridged
with an agent or a "secure LDAP" gateway, accepting the extra moving part.

Less mainstream ideas include lightweight authorisation by SSH certificates instead of directory-held keys, and
declarative directory state: keep the LDIF in Git and apply it with a reconciler, treating the server as a cache.

## Active research

Work is moving on three fronts. Password hashing in directories is being modernised (Argon2 support in OpenLDAP
contributions, discussion of removing weak schemes). Replication correctness, including conflict-free replicated data
types as a way to make multi-provider writes deterministic, is an academic and vendor topic with practical impact on
LDAP-style data. The third front is attack surface: research on LDAP injection, NTLM relay to LDAP in AD environments
(which is why LDAP signing and channel binding are enforced on Windows Server), and unauthenticated denial of service
bugs in parsers. Open questions include how to give applications fine-grained, auditable access without handing them
a service account that reads everything.

## Future direction

OpenLDAP 2.6 carries a long-term-support commitment from the project, while 2.7 delivers new features on a shorter
cycle [web: ldap.com] (exact patch numbers to verify at deployment time). Distribution trends point to fewer people
running a hand-built OpenLDAP and more using IdM/FreeIPA, 389 Directory Server or a hosted directory, with plain LDAP
retained as a protocol that applications consume. Expect TLS 1.3-only defaults, stricter certificate-name checks, and
passkey or OIDC front ends in front of directories rather than replacing them. A practitioner's watch-list: the end of
life of 2.5 (January 2027, to verify), the removal of obsolete back ends, and SSSD's growing set of LDAP-related options
as it absorbs more of the client work.
