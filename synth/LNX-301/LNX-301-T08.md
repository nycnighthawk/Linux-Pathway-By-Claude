# ID mapping and SSSD troubleshooting with sssctl

## Define the problem

Linux identifies a user to the kernel by a 32-bit number. Files record the UID of their owner, NFS servers compare UIDs
between hosts, containers map UIDs through namespaces, and quotas and process accounting all count in these numbers.
A directory identifies a user differently: Active Directory by a variable-length Security Identifier (SID) such as
`S-1-5-21-1004336348-1177238915-682003330-1105`, a generic LDAP server by a DN, FreeIPA by a UUID plus POSIX
attributes. Something has to decide that Alice is UID 1105-something on every machine she touches, today, after a
reinstall, and after the directory team reorganises. That is the **ID mapping** problem, and it sits under every
file permission in a directory-integrated estate.

The mapping has to be stable (a given user always gets the same number, on every host), unique (two users never share a
number, nor does a domain user collide with a local user or with a container's subordinate range), and cheap to
operate. If the directory stores POSIX numbers, someone must own them and ensure uniqueness. If numbers are
computed, the computation must be identical on every client, or file ownership silently differs between
machines.

The second half of the topic is what to do when it fails. A login that works on host A fails on host B; `id`
shows the right user but no groups; a file created last year now belongs to a number nobody can resolve; changes
to the directory take hours to show up. The SSSD toolbox for diagnosis (`sssctl`, the log files, cache tools, the log
analyser) makes these problems tractable, but only for someone who knows what each daemon does. This slice covers the
mapping algorithm and its configuration, the alternatives (POSIX attributes in the directory, ID views), and a
practical troubleshooting method built on `sssctl`.

## History and approaches

The oldest approach is to let administrators assign numbers by hand and store them in the directory: RFC 2307 defines
`uidNumber` and `gidNumber`, and NIS maps carried the same data for decades. Uniqueness was a convention, kept
in a spreadsheet or by a script, and collisions happened at mergers. FreeIPA solved this inside its own domain with
**Distributed Numeric Assignment** (DNA): each server owns a block of numbers and hands out the next one,
and replicas request new blocks when theirs run low.

Active Directory had no POSIX numbers originally. Windows Services for UNIX added the attributes as schema
extensions and the "Identity Management for UNIX" tools to edit them, but only some organisations populated them.
Samba's winbind therefore introduced **idmap back ends**: `tdb` (allocate on first sight, stored locally, not
identical across hosts), `ldap` (store the allocation centrally), `rid` (compute from the relative ID in the SID
plus a base), `ad` (read the POSIX attributes from AD), `autorid` (slice the domain space automatically), and
`rfc2307` (read from an RFC 2307 LDAP directory) [src: samba-docs 7f93815b1a6832b5] [src: samba-docs 0c75c95fe1f8e958]. The
earliest default, `tdb`, produced different numbers on different member servers, which is one of the classic
failures: an NFS export from one winbind host mounted on another showed the wrong owners.

SSSD took the algorithmic route in its AD provider (2012): hash the domain SID to pick a **slice** within a large
range, then add the RID of the object to the slice's base. Because the algorithm depends only on the SID and
shared configuration, every SSSD client computes the same numbers without a coordinator. Red Hat's documentation
describes the resulting property: the same user has the same UID and GID on every system that uses the same
mapping approach, and the user's entry is created in the SSSD cache on first login
[src: rhel-10-docs a971298263db2a05]. For estates that already hold POSIX attributes in AD, SSSD offers the other mode
(`ldap_id_mapping = False`), best combined with publishing the attributes to the global catalog
[src: rhel-10-docs e5f6fffc0c7e3e8a]. IdM-with-trust uses the same idea inside its own server
with IdM-managed ranges (LNX-301-T07), and ID views came as an escape hatch for migrations.

On the tooling side, SSSD in the early years was debugged with `debug_level` in `sssd.conf`, a service restart,
and reading logs with `grep`. `sss_cache`, `sss_debuglevel` and `sss_seed` arrived in the 1.x series. In SSSD 2.x the
`sssctl` command gathered these into one tool, with an additional log analyser (`sssctl analyze`) that follows a
request through the responder and data provider logs [src: rhel-10-docs cd3d5a976a957d28]. The pattern: a
collision-free, coordinator-free default, an escape hatch for explicit numbers, and tooling to inspect what the
daemon thinks.

## Current state

**The mapping algorithm.** Given a domain SID, SSSD computes a 32-bit murmur3 hash of it, and takes the hash modulo the
number of available slices. The range of IDs it may use is bounded by `ldap_idmap_range_min` (default 200000) and
`ldap_idmap_range_max` (default 2000200000), cut into slices of `ldap_idmap_range_size` (default 200000). Slice
number n starts at `range_min + n * range_size`; a user's UID is that base plus the RID (the last component of the SID),
modulo the slice size. If two domains hash to the same slice, SSSD moves the second to the next free slice, which is why
the order in which domains are first seen matters when the SID hash collides (and why `ldap_idmap_autorid_compat`
exists to reproduce Samba's autorid layout). With about 10,000 slices, collisions for a few domains are rare; with
a RID above 200000 the user falls out of the slice and is skipped with a log message, so large domains need a
bigger `ldap_idmap_range_size`. Changing the size on an existing deployment changes every number, which is why it is
decided at the start. On a mixed fleet with winbind, you either use the same algorithm
(`idmap_autorid` with a compatible flag) or agree on explicit numbers.

**Explicit POSIX attributes.** With `ldap_id_mapping = False`, SSSD reads `uidNumber`, `gidNumber`,
`unixHomeDirectory` and `loginShell` (names configurable through `ldap_user_uid_number` and friends). Entries without a
number are not visible on Linux. Duplicates are the directory's problem: SSSD logs and ignores or fails the colliding
entry. `min_id` and `max_id` in the domain section filter out numbers outside a safe range, which is a useful guard
against a directory handing out UID 0 or a number that collides with local system accounts (below 1000, depending on
the distribution's `UID_MIN`).

**Names.** The mapping of names matters as much as numbers. `use_fully_qualified_names = True` is required for
multi-domain setups and is the default for AD joins, so users appear as `alice@corp.example.com`.
`full_name_format` sets the shape, `default_domain_suffix` allows short names for a primary domain,
`case_sensitive = False` is the default for the AD and IPA providers. `override_homedir`, `fallback_homedir`
and `override_shell` provide Linux-side values; `override_gid` forces a primary group.

**What SSSD caches.** SSSD keeps the identity cache in `/var/lib/sss/db/cache_<domain>.ldb`, a transactional LDB
database, with an in-memory fast cache in `/var/lib/sss/mc/`. The key timers are `entry_cache_timeout`
(5400 seconds by default for most entries), `entry_negative_timeout` (15 s), `refresh_expired_records` and the
offline credential cache controlled by `cache_credentials` and `offline_credentials_expiration`. After a change
in the directory the client does not see it until the entry expires or is invalidated. `sss_cache -E` (invalidate
everything), `sss_cache -u alice` and `sss_cache -g wheel` mark entries stale without deleting them, so SSSD
refreshes them on the next request, and the cached credentials survive for offline logins. `sssctl cache-expire`
is the newer equivalent; `sssctl cache-remove` stops the service, deletes the cache databases and restarts, which is
the nuclear option if the cache is corrupt.

**sssctl, subcommand by subcommand.**

- `sssctl domain-list` shows the configured domains; `sssctl domain-status <domain>` prints whether SSSD is online
  or offline, which server it is using for each service (LDAP and KDC), and, with `-o`/`-a`, the list of active and
  discovered servers. This is the first command to run for "logins are slow" or "all lookups fail".
- `sssctl user-checks <user> [-s <pam-service>] [-a auth|acct|...]` runs the NSS lookup, group resolution and
  an `acct` PAM request together, then prints what the PAM stack concluded: the single best test of the question "will
  this user be able to log in?". It reports the number of groups and the access control outcome.
- `sssctl config-check` validates `sssd.conf` and the snippets in `/etc/sssd/conf.d/`, flagging unknown options and
  type errors before a restart takes the service down.
- `sssctl debug-level <n>` changes the logging level at runtime for all components without a restart. The default is
  2, which records only serious failures; levels up to 3 add larger failures, and 8 or more is extremely verbose.
  Red Hat suggests 6 as the working starting point for authentication problems
  [src: rhel-10-docs 684b170437628bd6]. Set `debug_level` persistently per section (`[nss]`, `[pam]`,
  `[domain/...]`) in `sssd.conf` for reproducing intermittent bugs.
- `sssctl logs-fetch /tmp/sssd-logs.tar` archives the logs; `sssctl logs-remove` truncates them before a clean
  reproduction.
- `sssctl analyze request list` and `sssctl analyze request show <id>` read the debug logs and reconstruct the chain
  of a client request across the NSS or PAM responder and the data provider, so that one lookup can be followed from
  entry to reply; they require debug level 7 or above for the logs to carry the needed entries
  [src: rhel-10-docs cd3d5a976a957d28] [src: rhel-10-docs 35447c2e81fcdc2f].
- `sssctl access-report` (where supported) lists which users may access a client under the domain's access
  rules, and `sssctl cert-show` and `cert-eval-rule` evaluate smart-card certificate mapping rules, which
  matters for LNX-301-T10 [src: rhel-10-docs 8c081e6941dbb28f].

**The log files.** `/var/log/sssd/` has one file per process: `sssd.log` (the monitor), `sssd_nss.log`,
`sssd_pam.log`, `sssd_<domain>.log` (the backend or data provider, where LDAP and Kerberos conversations
appear), and `krb5_child.log`, `ldap_child.log`, `selinux_child.log`, `p11_child.log` for the helpers that run with
privilege separation. A user lookup flows `sssd_nss` to `sssd_be` and, on a cache miss, to LDAP. If `sssd_be` shows
`Offline` mode, the first step is why the connection to the server failed: DNS, time, TLS name or credentials.

**A troubleshooting method.** Work from the outside in, one layer at a time:

1. *Does the OS see it?* `getent passwd alice@corp.example.com` and `id alice@corp.example.com`. If this fails, look
   at `/etc/nsswitch.conf` (`passwd: files sss`), whether `sssd` runs (`systemctl status sssd`), and SELinux.
2. *Is SSSD online?* `sssctl domain-status corp.example.com`. Offline means a connection problem, not an identity
   problem.
3. *Is it the cache?* `sss_cache -E`, repeat the lookup. If the result changes, the data was stale; adjust timers
   rather than flushing by habit.
4. *Is it the mapping?* Compare `id` for the same user on two hosts. Different numbers mean different mapping
   settings or different SSSD versions of `ldap_idmap_*` options. `sssctl` has no direct command for numbers; use
   `ldbsearch -H /var/lib/sss/db/cache_<domain>.ldb name=alice@...` to see the cached `uidNumber`, and the
   domain SID by `wbinfo -n` or a directory query.
5. *Is it access?* `sssctl user-checks alice -a acct -s sshd`. A failure after a successful lookup means HBAC,
   `simple_allow_groups`, GPO, `realm permit` or an expired account.
6. *Is it authentication?* Set `debug_level = 6`, repeat the login, and read `krb5_child.log` for
   `Client not found in Kerberos database`, `Preauthentication failed`, or `Clock skew`.

**Generalised pattern.** The reusable ideas are: compute identifiers deterministically from the identity's stable
key when you can; reserve explicit assignments for when you must; cache with explicit invalidation; and build the
diagnosis tool around the same layering as the system (responder, data provider, helper process).

## Assessment: the good, the bad and the ugly

**Good.** Algorithmic mapping needs no coordination and no changes in the directory; two hosts installed a year
apart compute identical numbers. Explicit mapping gives complete control and matches non-Linux consumers (NetApp,
Solaris, legacy NFS). The `sssctl` tool reduces mean time to diagnose, and the analyser makes opaque log
files readable. The cache makes logins survive an outage.

**Bad.** The two mapping modes are mutually exclusive in practice: switching later renumbers everyone. Hosts that mix SSSD
algorithmic mapping, winbind `rid` mapping and explicit attributes will disagree on numbers without any error being
raised. A directory migration (renaming the domain or moving users to another domain) changes SIDs or
domain names and therefore mappings. Documentation for the hash and slice algorithm is thin outside the man page,
which makes capacity planning for several large domains guesswork. Debug logs are large (hundreds of megabytes at
level 9) and can contain sensitive data; storing them requires a retention plan.

**Ugly.** Silent ownership drift. The files that a user created before a mapping change belong to a number that now
resolves to a different person or to nobody, and nothing complains. NFS root squash and quota systems keep numeric IDs. A
slice collision between two domains merges identity spaces, and one user can read another domain's user's files.
Range exhaustion (RIDs above the slice size) leaves a subset of users unmapped, and the error is a log line, not a
login message. SSSD's negative cache makes a freshly created account look nonexistent for 15 seconds or more, which
confuses provisioning scripts that check immediately. The ldb cache can corrupt after a power loss and the symptoms
are bizarre (`id` showing a half-filled entry). Overriding with `ldap_id_mapping = False` while some AD users have
attributes and others do not yields a population split that looks random to the users affected.

Mitigations: decide the mapping model in design, record it with the domain SID, and test with two hosts before rollout;
record `ldap_idmap_range_size` and `range_min` in configuration management; use `min_id`/`max_id`; add a check
comparing `id` for sentinel users across hosts; alert on `sssctl domain-status` offline state; and keep
`sssctl logs-fetch` in the on-call runbook.

## Applications beyond this domain

ID translation between identity spaces is general: user namespaces map container UIDs to host ranges through
`/etc/subuid` and `/etc/subgid`, and rootless container guides describe the allocation of these ranges in the
same terms of start and count [src: rocky-docs fbe900c5e0339b1d]. NFSv4 `idmapd` maps names to numbers between
servers, and the same drift problem appears when the domain names differ. Cloud IAM maps external identities
to local roles at a boundary. Tools such as `rsync --usermap`, `chown --from`, and `find -uid` drive migrations of file
ownership. In observability, tracing a request through responder and provider logs (what `sssctl analyze` does) is
the same technique as distributed tracing: attach an identifier at the front and correlate it across processes.

## Examples

**Same user, two numbers.** Host `app1` was joined with SSSD defaults; `app2` was joined with `net ads join`
and winbind using `idmap config * : backend = tdb`. `id alice@corp` returns 886201105 on `app1` and 3000012 on `app2`.
A shared NFS directory created from `app1` appears owned by an unknown UID on `app2`. The fix is to choose one model
(SSSD on both or an explicit `idmap_ad` mapping with the same range) and to fix the files with `find /data -uid 3000012
-exec chown ...`.

**Ldap attributes, half populated.** The domain has `uidNumber` for 40 of 200 users. After `ldap_id_mapping = False`, only
those 40 are visible. `sssctl user-checks bob` reports `user not found`. The corrective action is data work in the
directory or a return to algorithmic mapping, together with a planned renumbering. The failing check is cheap: a
sentinel LDAP query that counts users without `uidNumber`.

**Debugging a slow login.** Logins take 20 seconds. `sssctl domain-status corp.example.com -a` lists three servers, one of
which is unreachable (firewall change). SSSD waits for each connection to time out before trying the next
(`ldap_network_timeout` 6 seconds by default, `dns_resolver_timeout`). Setting `ad_server` or `ldap_uri` to the
reachable DCs, fixing the AD site, or restoring the route fixes it. A debug log at level 6 would show the
repeated `Marking server as not working`.

**Tracing a denied login.** `sssctl analyze request list -v` shows the NSS and PAM requests, and `sssctl analyze
request show 5` prints that the PAM `acct` stage failed in the `sssd_be` with `Access denied by GPO`. Without the
tool, finding the same lines takes a manual search across four files.

**Cache confusion.** An administrator adds Alice to group `wheel` in the directory. `sudo -l` on the client does not show
it for 90 minutes because the group membership was cached with the default `entry_cache_timeout`. `sss_cache -u alice`
makes the next lookup go to the server. The longer-term answer is to shorten the timeout for groups used in
authorisation or to expect the delay.

## Related problems and ideas

Alternatives to SSSD's approach: winbind's idmap back ends, with `autorid` as the most similar; FreeIPA's DNA ranges;
SCIM-provisioned local accounts (the directory pushes local users into each host) with no mapping needed; and
`systemd-userdbd` with `nss-systemd`, which can serve users from JSON records and drop-ins and supports dynamic
UIDs for services. Related questions: how to make containers share IDs across hosts (ID-mapped mounts on newer kernels),
how to migrate file ownership at scale (`chown -R` versus ID-mapped filesystem mounts via `mount_setattr`), and
how to keep a record of where each UID was ever used. Proposed ideas include UIDs derived from identity UUIDs in a 64-bit
space (not accepted by the kernel interfaces, which are 32-bit) and avoiding local numeric identity by authorising
over Kerberos principals at the application layer.

## Active research

SSSD developers are working on better observability (the analyser, structured logging), on scaling the identity cache
for very large directories (millions of entries, with lazy refresh and the in-memory cache), and on passkey and
FIDO2 authentication stages that need new debugging aids. The kernel community has been extending ID-mapped mounts so
that mapping can be applied per mount instead of per file. Open questions: a standard way to carry stable POSIX IDs
in federation protocols, and whether directory vendors will adopt a common attribute for it.

## Future direction

Expect ID-mapped mounts and user namespaces to reduce the number of hosts that need domain numbers at all (containers
get a private view), and expect SSSD to grow more built-in checks (`sssctl` as a doctor tool). RHEL 10 documentation
continues to treat `sssctl` as the first-line tool and documents the analyser and log-level workflow
[src: rhel-10-docs 684b170437628bd6]. Watch SSSD release notes for changes in default timeouts and for the
interaction of the `ad` provider with Windows hardening (to verify per version).
