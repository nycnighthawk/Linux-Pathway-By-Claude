# Profiling with perf and flame graphs

## Define the problem

A program that is correct but slow, or one that consumes more CPU than it should, cannot be fixed by reading code and guessing.
Programmers are poor at predicting where time goes: the loop they suspect is cheap, and the line nobody noticed runs ten million
times. Modern machines add layers of surprise: instruction and data caches, branch predictors, memory bandwidth, lock contention,
system calls, page faults and the scheduler, so that the cost of an operation depends on its context. Optimising without
measuring risks wasted effort and, worse, complicated code that is no faster.

Profiling answers the first question every performance investigation has: where is the time (or the cache misses, or the
allocations) actually spent? On Linux the principal tool is `perf`, a front end to the kernel's performance-events subsystem,
which can sample a running program with little overhead, count hardware events and trace kernel activity. Flame graphs are
the visualisation that made sampled stacks readable at a glance. This topic, taught at a "functional" level, covers the working
loop: choose a method, collect a profile, read it, change one thing, measure again. It includes the alternatives that work where
`perf` does not (instrumenting profilers such as callgrind and gprof), the preconditions that make stacks usable (frame pointers or unwind tables,
symbols), and the interpretation errors that mislead. Correctness debugging (LNX-220-T04) and memory-error tools (LNX-220-T05) answer other questions.

## History and approaches

Early profiling was by instrumentation. The compiler inserted a counting call at the start of each function (`gcc -pg`), and `gprof`
(1982) combined call counts with periodic sampling of the program counter to produce a flat profile and a call graph. This was
easy but intrusive: it measured only the program's own code, missed time in shared libraries and the kernel, and distorted
small functions. Valgrind's `callgrind` tool followed the other route of simulating the machine, giving exact instruction counts and
call relationships without recompilation, at a slowdown of tens of times, with `callgrind_annotate` and KCachegrind to read the results
[src: bootlin-training b38d2ff074d0b706].

Sampling profilers changed the picture. Instead of counting every call, a timer or a hardware counter interrupts the program at intervals
and records where it was; with enough samples the distribution converges on the truth, and the overhead is small and
controllable. The first system-wide tool on Linux was OProfile (2002), which used performance counters but needed a kernel module and
a daemon. In 2009 the kernel gained the unified `perf_events` interface, and the `perf` tool was shipped in the kernel tree by Ingo Molnar,
Thomas Gleixner and others. It could sample any process or the whole system, use the CPU's performance monitoring unit (PMU)
for cycles, instructions, cache misses and branch mispredictions, and count software events (context switches, page faults) and
tracepoints. Other tools, such as SystemTap, `ftrace` and later eBPF-based tracers (`bcc`, `bpftrace`), complemented sampling with event tracing and
in-kernel aggregation.

Visualisation was the missing piece. Text reports of a thousand stacks are tedious. Brendan Gregg introduced flame graphs in 2011 while working
on a MySQL performance problem: stacks are aggregated, and each distinct call path is drawn as a stack of boxes whose width is proportional to the
number of samples that include it. The x-axis is not time but the alphabetical order of frames, so identical paths merge; the y-axis is stack depth.
The widest boxes near the top are what consumes the CPU. The tooling is a pipeline: a profiler produces stacks, a collapse script such as
`stackcollapse-perf.pl` turns each stack into a line `frame;frame;frame count`, and `flamegraph.pl` renders an interactive SVG. The format of
"folded stacks" became a lingua franca that many tools read and write, including `speedscope`, `inferno` (a Rust port), `py-spy` and `async-profiler`.
Variants include differential flame graphs, off-CPU flame graphs (time spent blocked rather than running) and icicle graphs, upside-down.

A problem that held back practical profiling for years was stack unwinding. A sampling tool must reconstruct the call chain from a snapshot of registers
and the stack. Compilers on x86-64 began omitting the frame pointer register (`-fomit-frame-pointer`) at optimisation levels, which freed a register but
broke the cheap method of walking a linked list of frames. Alternatives are DWARF-based unwinding (`perf record --call-graph dwarf`, which copies stack
bytes and is expensive), the kernel's ORC unwinder for kernel stacks, and last-branch-record (LBR) hardware. Eventually, several large distributions
decided to enable frame pointers again in their default builds, accepting a small cost for a large improvement in profiling quality (Fedora and Ubuntu did this
in 2023 and 2024, to verify the exact releases). The compact SFrame format is the intended long-term answer.

The pattern that emerged is "sample first, trace when needed": a low-overhead sampling profile finds the hot code, counters explain why it is slow, and
targeted tracing or instrumentation investigates specific behaviour.

## Current state

`perf` is a command with subcommands. `perf stat ./prog` runs a program and prints counts for cycles, instructions, branches, branch-misses,
context switches and page faults, together with instructions per cycle (IPC), which is a quick indicator of whether the program is compute-bound or
stalled on memory. `perf record` samples: `perf record -F 99 -g ./prog` samples at 99 Hz (an odd number avoids lock-step with periodic timers) and records
call graphs. `perf record -a -g -- sleep 30` samples every CPU for 30 seconds, `-p PID` attaches to a running process and `--cgroup` restricts a recording to a
control group, such as one systemd unit. The result is written to `perf.data`. `perf report` (with `--stdio` for plain text or an interactive TUI) shows the
distribution by symbol, shared object or command, and `perf annotate` shows the hot instructions with source. `perf top` is a live view
[src: man-pages b0533e98a170e180], and the manual page of `perf record` lists the event, sampling and call-graph options [src: man-pages 45283ccfe5b69368].
`perf script` dumps raw samples for processing, and `perf trace` is a strace-like tracer. `perf list` shows the events available on the machine;
`perf record -e cache-misses` or `-e cpu-clock` selects one. In virtual machines and containers, hardware counters may be unavailable, in which case
`perf` falls back to the software clock event, and the kernel setting `kernel.perf_event_paranoid` (and capabilities such as `CAP_PERFMON`) controls who may profile
what; many container platforms block the system call entirely, so profiling often happens on the host or in a privileged debug container.

To get readable results the binary needs symbols (not stripped, or with matching debug files as in LNX-220-T01) and a usable unwinder: build with
`-fno-omit-frame-pointer` (and `-g` for line-level annotation) or collect with `--call-graph dwarf`. Optimisation level should be the one you ship, usually `-O2`,
because profiling `-O0` code measures something else. Inlined functions disappear as separate frames unless debug information lets the tool expand them.
Just-in-time compiled and interpreted languages need extra help: Java and Node.js can write perf map files (`/tmp/perf-PID.map`), Python 3.12 added
support for the perf trampoline so that Python function names appear in stacks.

The flame graph workflow is: `perf record -F 99 -g -- ./prog`, then `perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg`, and open the SVG in a browser,
where clicking zooms into a frame and searching highlights matches. How to read it: look for wide plateaus at the top edge, as those are functions
that were on-CPU themselves; follow them down to see who called them; compare a box's width with the whole to get a percentage. A tall narrow tower is deep
recursion, not cost. Bootlin's training materials include a short exercise that profiles a system with `perf` and FlameGraphs, which shows the approach on an
embedded target [src: bootlin-training 55f25cd3e30a237b].

When `perf` is unavailable, the same loop works with other tools. `valgrind --tool=callgrind` counts instructions exactly and is deterministic, which also makes it a
good basis for regression tests of performance (the lab relies on this); `callgrind_annotate` prints functions by cost, and `--tree=caller` or KCachegrind show callers.
`gprof` needs `-pg` at compile and link time. Language-specific profilers (`cProfile`, `py-spy`, Go's `pprof`, `cargo flamegraph`) produce folded stacks or pprof files.
`strace -c` and `ltrace -c` summarise system and library calls; `/usr/bin/time -v` gives resource totals; `perf trace -s` summarises per-syscall latency.

The generalised pattern is a measurement cycle with a stated hypothesis: define the workload and a metric, take a baseline, profile, form a hypothesis from the
widest frames, change one thing, repeat the measurement and keep the change only if the metric moves beyond noise.

## Assessment: the good, the bad and the ugly

The good side is that `perf` is cheap, ubiquitous on distribution kernels and covers the entire system from one tool: user code, libraries, kernel, interrupts. A
sampling profile at 99 Hz costs a percent or two, which makes it safe in production. Flame graphs compress thousands of stacks into a picture that a newcomer can read in
a minute. Hardware counters explain causes (cache misses, mispredictions) that source code does not show. Deterministic tools like callgrind give repeatable numbers
that suit automated checks.

The bad side is interpretation. A profile shows where time is spent, not whether that time is avoidable, and a function with a large share may simply be doing the necessary work.
Sampling has statistical error, so small percentages need many samples. Skid in hardware sampling attributes cost to an instruction slightly after the culprit. Missing frame pointers produce truncated
or bogus stacks, flame graphs of stripped binaries show hex addresses, and an on-CPU graph does not show time spent waiting on locks, I/O or network, which needs off-CPU analysis. Optimisation can
shift the bottleneck instead of removing it, and measuring on a noisy shared machine produces misleading differences.

The ugly side is the environment. Virtualised and containerised systems often lack PMU access, laptops change frequency with load and temperature, and turbo modes make
repeated runs inconsistent; benchmark discipline (pinning CPUs, fixed frequency governor, warm-up runs, multiple repetitions) is laborious. Security hardening of `perf_event_paranoid` hinders developers
in locked-down hosts. Profiling code with heavy inlining and link-time optimisation yields frames that do not match the source structure. And some of the most expensive costs, such as page faults from memory
allocation patterns or kernel lock contention, only appear when the tool also samples kernel stacks.

## Applications beyond this domain

The sample-and-aggregate idea is used in continuous profiling services that sample production fleets (Google-Wide Profiling, Parca, Pyroscope, Datadog and the OpenTelemetry profiling signal).
Flame graphs are used for more than CPU: allocation, memory-leak, off-CPU, lock, disk I/O and network graphs are all aggregations of stacks with a weight. Browsers' developer tools show flame-chart views of JavaScript;
database engines produce profiling output as plan trees with times; game developers use frame-based profilers with the same idea of hierarchical timing. In operations, the "USE method" (utilisation, saturation, errors) and
the "RED method" guide what to measure before profiling, and capacity planning uses the same counters. Hardware performance counters also underpin side-channel research and energy estimation.

## Examples

A first example is a service that burns 80 percent of a core while idle. `perf top -p PID` shows that most samples are in a function that polls a queue with a zero timeout. A flame graph confirms the stack,
and the fix is to block on the queue, which drops CPU use to near zero. A second example is a data-processing tool that takes ten seconds: `perf stat` shows an IPC of 0.3 and a high cache-miss rate; `perf record` shows the
time in a hash lookup, and the cause is a table too large for cache with a poor hash function. Changing the layout, not the algorithm, produced the speedup. The lab for this topic uses a simpler case, a quadratic duplicate counter, and callgrind so that it works on any host.
It then proves the fix by showing five times fewer instructions executed.

A failing example is the flame graph made from a release binary built with `-fomit-frame-pointer`: the stacks are one or two frames deep and the graph is a flat row of unrelated boxes. Re-recording with
`--call-graph dwarf`, or rebuilding with frame pointers, restores the structure. A second failing example is a "benchmark" that compares two builds on a laptop one after the other: the second ran after the machine heated up and throttled, so the difference measured
temperature, not code. Alternating runs and using instruction counts instead of wall time removes this effect.

## Related problems and ideas

Profiling depends on the toolchain knowledge of LNX-220-T01 (symbols, debug files, frame pointers, `-O` levels) and on build integration (LNX-220-T02) to make a profiling configuration. The debugger tools of LNX-220-T04 and the
sanitizers of LNX-220-T05 answer correctness questions; sanitizers distort timing, so never profile a sanitized build. Valgrind's `massif` and `heaptrack` look at memory use, and `ltrace` shows library calls. For services under
systemd (LNX-220-T08), cgroup-scoped recording isolates one unit, and `systemd-cgtop` gives a first view of resource use. Language toolchains (LNX-220-T07) have profilers that feed the same viewers. The performance
effect of library choices and relocation costs links back to LNX-220-T03, because dynamic symbol resolution contributes to start-up time.

Alternatives and complements include eBPF-based profilers that aggregate stacks in the kernel, tracing frameworks (LTTng, `ftrace`, `trace-cmd`), `bpftrace` one-liners, hardware trace (Intel PT, Arm CoreSight) for exact instruction histories, and
the older instrumentation approach of manual timers and counters in code. Statistical methods such as "coz" causal profiling estimate how much a speedup of one region would improve overall throughput, an idea not yet mainstream.

## Active research

Research and engineering focus on making profiling pervasive: continuous, fleet-wide profiling with negligible overhead; standard formats for profiles (pprof, the OpenTelemetry profiles signal) and for unwinding
(SFrame, with kernel and toolchain support landing across 2024 and 2025, to verify per-distribution availability); unwinding of stacks without frame pointers in eBPF; better attribution through inlining and LTO; and
off-CPU and wall-clock profiling that combines scheduler tracepoints with stacks. Researchers also work on causal and differential profiling, automated performance regression detection in continuous integration, machine-learning-based
anomaly detection on profile data, and energy profiling, which uses hardware counters such as RAPL (Running Average Power Limit) to attribute joules to code.

## Future direction

Expect frame pointers or SFrame to be normal in distribution builds, which will make `perf record -g` work out of the box for everything. Profiling will move toward being always on in production with a few percent
overhead budget, with profiles stored beside metrics and traces. Flame graphs will keep their role, extended by differential and time-aware views. For the working developer, the plan is: state the workload and metric, use
`perf stat` for a quick characterisation, a sampled flame graph to locate the cost, a counter or tracing tool to explain it, and an automated benchmark (or an instruction count) to guard the gain.
