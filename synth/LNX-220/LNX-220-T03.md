# Shared libraries, sonames and pkg-config

## Define the problem

Programs reuse code, and the cheapest way to reuse it is to share one copy among many programs. A shared library saves disk
and memory, and, more importantly for maintainers, it allows a fix in one place to reach every program on the system
without rebuilding them. That benefit has a cost that every Linux developer meets sooner or later: the program built today
must find, at some later time and on a possibly different machine, a library that is compatible with the one it was built
against. "Compatible" is a statement about the binary interface, not about the source: sizes of structures, meanings of
function arguments, the set of exported symbols.

Three questions follow. How does a library announce its own identity and compatibility, so that the loader can pick the
right file? How does a consumer learn, when it compiles, which headers and libraries to use? And how does a library author
change the code without breaking the programs already built against it? Soname versioning answers the first and third
question; `pkg-config` answers the second. This slice covers library file naming, the linker's and loader's search rules,
symbol visibility and versioning, ABI checking, and the metadata files for consumers. Building the objects themselves is
LNX-220-T01; the way a distribution package expresses library dependencies is touched by LNX-220-T10.

## History and approaches

The first Unix libraries were static archives copied into each executable. When disks and memory were small, the
duplication of the C library in every program mattered, and systems such as SunOS and System V introduced shared
libraries in the late 1980s. Linux began with `a.out` shared libraries whose load addresses were allocated from a global
list, and the move to ELF and the position-independent code model removed that fragile registry. Versioned file names then
carried the compatibility story: a library named `libfoo.so.1.4.2` is the real file, `libfoo.so.1` is the soname that
programs record, and `libfoo.so` is a development symlink that exists only so the compiler's `-lfoo` can find it. Red Hat's
guide to creating C libraries with GCC walks through exactly these three names and how `-Wl,-soname` sets the middle one
[src: rhel-10-docs c48817f679eb7224].

The weakness of soname versioning is that it has one dimension: the number changes when the interface breaks, and nothing
describes partial compatibility. Large libraries such as glibc needed finer control, so GNU ld gained symbol versioning
through version scripts: each exported symbol is tagged with a version node such as `GLIBC_2.34`, a library can keep an
old implementation under an old version tag while a new one appears under a new tag, and a program records which version
tags it needs. This allowed the C library to evolve for decades under one soname. The price is complexity, and the
well-known message that a version tag is "not found" when running a new binary on an old system. Other platforms went
different ways: Windows had "DLL hell" because the system directory held a single copy of each name, the Side-by-Side
assemblies were the fix, and macOS uses install names and framework bundles. Linux distributions rely on package
metadata to enforce that a package providing `libfoo.so.1` is installed whenever a package requires it, which Debian's
shlibs and symbols files and RPM's automatic dependency generator formalise [src: man-pages 3c22043a6c086c74].

The consumer side evolved too. Early programs shipped `foo-config` scripts that printed flags, and each library invented
its own. `pkg-config` (created by James Henstridge around 2000 for GNOME) standardised this with `.pc` files stored under
standard directories: a text file with variables, a name, a version, a `Requires` list and `Cflags` and `Libs` lines. It
became the base of nearly every Unix build system's dependency discovery, and `pkgconf`, a compatible reimplementation
without the glib dependency, replaced it in many distributions. Autotools wrapped it in the `PKG_CHECK_MODULES` macro, as
described in Bootlin's training notes [src: bootlin-training e5d7af26725efb71].

Finally, the problem of detecting accidental breaking changes got attention. Distributions realised that after a
"harmless" update many programs stopped working, because a library changed structure layout without changing its
soname. Tools that compare two versions of a library by their exported symbols and type layouts, `abidiff` from libabigail
and the ABI Compliance Checker, were created so that maintainers could verify an update before release; the manual page of
libabigail explains the concepts of the comparison [src: man-pages 488a6d3dffca9655]. The emerging pattern is to treat the
binary interface as a published, checkable artefact that has its own version number and its own tests.

## Current state

A shared object has a SONAME entry in its dynamic section, which is set at link time with `-Wl,-soname,libfoo.so.1`. When a
program is linked against `-lfoo`, the linker finds `libfoo.so` (the linker name), reads its soname, and stores the soname,
not the file name, in the program's `DT_NEEDED` list. At run time the dynamic loader looks for a library with that soname.
The loader searches in a defined order: the `DT_RPATH` of the program if there is no `DT_RUNPATH`, then `LD_LIBRARY_PATH`,
then `DT_RUNPATH`, then the cache file `/etc/ld.so.cache` and finally the default directories `/lib` and `/usr/lib`. The
cache is rebuilt by `ldconfig` from the directories in `/etc/ld.so.conf` and `/etc/ld.so.conf.d/*.conf`, and `ldconfig`
also creates the soname symlinks for libraries it finds [src: man-pages afd31ce8d4400857]. In an installed package the real
file and the soname symlink are in the library package, and the `libfoo.so` link plus headers are in the development
package, which is why a missing header or `-lfoo` error is cured by installing `-devel` or `-dev`.

A run path can be embedded in the binary: `-Wl,-rpath,'$ORIGIN/../lib'` records a directory relative to the executable, so
an application bundle can ship its private libraries without touching system configuration. `$ORIGIN` must reach the
linker unexpanded, which is why quoting matters in a Makefile (`$$ORIGIN`). `patchelf` and `chrpath` can edit the entry in
an existing binary. `LD_LIBRARY_PATH` is for debugging and wrappers, not for deployment, and `LD_PRELOAD` forces a library
in front of others, which is both a useful interposition tool and a sign of trouble if found where nobody expects it.
`ldd` shows which files would be loaded, `readelf -d` shows the entries without executing anything (running `ldd` on an
untrusted program can execute it on some systems), `ldconfig -p` prints the cache, and `LD_DEBUG=libs` traces the search.

The author of a library controls the exported surface. By default every non-static symbol is exported, which leaks
implementation details and slows start-up. Compiling with `-fvisibility=hidden` and marking public functions with a
macro that expands to `__attribute__((visibility("default")))` shrinks the dynamic symbol table to the real interface.
A version script passed with `-Wl,--version-script=libfoo.map` can both limit exports and attach version nodes. The rule
for evolution is: adding a function is compatible; changing a signature, removing a function or changing the layout of a
public structure is not, and requires a new soname or a versioned symbol. Opaque pointers (a declared-but-undefined
`struct foo`) with accessor functions are the standard way to leave room to change the layout.

On the consumer side a `.pc` file looks like variables followed by fields: `prefix`, `libdir`, `includedir`, then `Name`,
`Description`, `Version`, `Requires`, `Libs` and `Cflags`. `pkg-config --cflags --libs foo` produces the options,
`--modversion` the version, `--exists` and `--atleast-version` test conditions, and `--static` includes private
dependencies. The environment variable `PKG_CONFIG_PATH` adds search directories, and `PKG_CONFIG_SYSROOT_DIR` and
`PKG_CONFIG_LIBDIR` support cross builds. CMake's `pkg_check_modules` and Meson's `dependency()` both consult it. Build
systems such as Meson and CMake can generate the `.pc` file for a library. The generalised pattern is that a library
is an interface plus metadata: a name and version for the loader, a set of exported symbols, and a description file for
compile-time consumers.

## Assessment: the good, the bad and the ugly

The good part is that the mechanism works at distribution scale. Thousands of libraries are updated daily on a typical
distribution without rebuilding every dependent program, because maintainers respect the soname rule. Security fixes in
OpenSSL or zlib propagate quickly, and a bundled `$ORIGIN` path lets vendors ship exceptions where necessary. Tools
exist for every step of diagnosis, and `pkg-config` has made build files shorter and more portable.

The bad part is that the ABI is easy to break by accident. Adding a field in the middle of a public struct, changing an
enum's underlying type, switching a compiler's C++ standard library or changing the size of `time_t` can all break
consumers without changing a source-level interface. Version bumps are manual and depend on discipline. `pkg-config` has
no concept of a build-time ABI check, and `.pc` files go stale when installed into one prefix and moved. Bundling libraries
helps stability but moves the security-update burden from the distribution to the vendor; this is a real argument in
packaging debates, and it explains why distributions discourage vendored copies.

The ugly part is the interaction of search rules. Two copies of a library with the same soname, one in `/usr/lib` and one
in a vendor directory, lead to programs that behave differently on two hosts, and `LD_LIBRARY_PATH` set in a login
script poisons every child process. Symbol interposition means that a library's internal call can bind to a definition in
the executable, which is a feature that surprises library authors until they use `-Bsymbolic` or hidden visibility.
`dlopen` plugins loaded with `RTLD_GLOBAL` can leak symbols into other plugins. Setuid programs ignore `LD_LIBRARY_PATH` for
good security reasons, and developers who test with a wrapper script and deploy as setuid find that it stops working.

## Applications beyond this domain

Soname-style versioned contracts are present wherever independently released components meet. The Linux kernel guarantees a
stable system-call ABI to user space while permitting its internal module interface to change freely. Python wheels use
`manylinux` tags to say which glibc a compiled extension requires, a direct descendant of the versioned-symbol problem,
and Rust's `cargo` uses semantic versions with the compiler enforcing source compatibility, but crates compiled
statically avoid the runtime ABI issue. Web APIs use version prefixes for the same purpose, and plug-in systems use
interface versions in manifests. Protocols with schema evolution, such as protocol buffers, state rules for compatible
changes that are the wire equivalent of the rule that additions are safe and changes are not. The `.pc` file concept resembles
`pkg-config` equivalents in other ecosystems (CMake config packages, Python's `sysconfig`, Rust's `build.rs`
discovery, `go env`), all answering the question of where headers and libraries live.

## Examples

A concrete build uses `cc -fPIC -shared -fvisibility=hidden -Wl,-soname,libvec.so.1 -o libvec.so.1.2.0 vec.c`, followed by
`ln -s libvec.so.1.2.0 libvec.so.1` and `ln -s libvec.so.1 libvec.so`. `nm -D --defined-only libvec.so.1.2.0` should list
only the public functions. A `vec.pc` file then lets another project compile with
`cc app.c $(pkg-config --cflags --libs vec)`. The lab for this topic covers precisely this sequence, plus a check that an
internal helper does not leak.

A compatible update example: version 1.2 adds `vec_norm()` and keeps the soname `libvec.so.1`. Old programs continue to run
and new programs can use the added function. A breaking update example: version 2.0 changes `vec_dot` to take a `size_t` count
instead of `int`. The soname becomes `libvec.so.2`, the package name changes or the old files are kept in a compat
package, and both versions can be installed side by side because their sonames differ.

A failing example is the loader error about a shared object file that cannot be opened, naming `libfoo.so.3`. A program
was built on a developer laptop against a library under `/opt/foo/lib`, relying on an `LD_LIBRARY_PATH` exported in the
shell profile. Under systemd the environment is clean and the service fails. `ldd` shows `not found`, and the cure is to
install the library into a directory in the cache, add a drop-in file in `ld.so.conf.d` and run `ldconfig`, or to relink
with an `$ORIGIN` run path. Another failing example involves two libraries that both define `parse()` and a plug-in that
calls the wrong one because of global symbol binding; `LD_DEBUG=bindings` reveals which definition won.

## Related problems and ideas

The packaging side of the problem, where RPM and Debian derive dependencies from sonames, links to LNX-220-T10 and the
earlier LNX-104 source-build material, where `DESTDIR` staging and `ldconfig` were first met. The first topic of this
course, LNX-220-T01, explains the ELF fields (`DT_NEEDED`, `DT_SONAME`, `DT_RUNPATH`) that this topic manipulates, and
LNX-220-T04 (debuggers) shows how to break on a symbol before the library has been loaded. Sanitizers
(LNX-220-T05) rely on interposing allocation functions through the same mechanism as `LD_PRELOAD`.

Alternatives to the shared model include static linking, which removes the runtime question at the cost of rebuilding
for every library fix, and per-application bundles as in Flatpak and container images, where each application carries a
complete user-space. AppImage and snap place their own runtime next to the program. Nix gives each package a path derived
from a hash of its inputs, so two versions never conflict. Non-mainstream proposals include link-time "ABI locks" that
refuse to link against a different layout, and language-level ABI stability work such as the debate about the C++
ABI break in the standardisation committee.

## Active research

Research and engineering effort concentrate on automated ABI regression detection in continuous integration, with
`abidiff` and `libabigail` increasingly used by distributions to block accidental breaks. Large programs explore
reducing start-up time by minimising relocations, using prelinking-like ideas in a randomisation-friendly way, and
direct binding. Debian's work on the 64-bit `time_t` transition showed the cost of changing an interface type across
the whole archive. There is also interest in making dependency metadata inside binaries machine readable, such as ELF
package metadata notes that record the package and version for each binary so that crash reports can be matched with
the right debug files (to verify the current coverage across distributions).

## Future direction

Expect more tooling around ABI checks at release time and wider use of symbol versioning outside glibc. The move of many
new system components to Rust makes exported C interfaces, with their stable headers and generated `.pc` files, the
boundary that matters. Distributions continue to debate bundling versus sharing, and image-based deployments (bootc,
containers) reduce the need for one machine to satisfy many programs at once. The skills that remain are reading
`readelf -d`, understanding the search order and writing a careful public header.
