# Debugging native programs: gdb, core dumps and valgrind

## Define the problem

A native program that misbehaves gives few clues. It may stop with a one-word message from the shell, such as a
segmentation fault, produce wrong output without any message, hang, or slowly consume memory until the kernel kills it.
The cause is usually far from the symptom: a pointer was freed in one module and used in another, a buffer was
overwritten by a neighbour, a lock was taken in the wrong order. Printing values and rerunning is slow and changes the
program's timing and memory layout, which can make the failure vanish. A developer needs to observe a process or a record
of its death, find the point where the state first became wrong, and distinguish a bug in the program from a bug in
the library or the build.

Three families of tool cover most of the ground on Linux. A debugger (GDB, and its LLVM counterpart LLDB) controls a
running process or reads a crashed one, showing stack frames, variables and memory. A core dump is a snapshot of a dead
process, which allows the investigation to happen later and elsewhere, which matters for production crashes you cannot
reproduce on demand. A dynamic binary instrumentation tool such as Valgrind runs the program on a synthetic CPU and checks
every memory access, finding errors that did not crash the program this time. This topic, at the highest depth in the
course, covers all three, the ways of making binaries debuggable (debug symbols and debuginfo services), remote and
non-interactive use, and the habits that make a debugging session short. Compile-time instrumentation (sanitizers) is its
own topic, LNX-220-T05, and kernel debugging is outside this course.

## History and approaches

Debugging on Unix began with `adb` and `sdb`, assembler-level tools that could set breakpoints and examine memory but had
little knowledge of source code. `dbx` on BSD and System V added source-level symbolic debugging. Richard Stallman wrote
GDB in 1986 as part of the GNU project, and it has since become the standard debugger on Linux, with support for dozens of
architectures, remote protocols and languages. Its model, a command-line interface over the `ptrace` system call,
has proved durable. Front ends such as DDD, Emacs GUD, the Text User Interface (`-tui`), and later IDE integrations through
the GDB/MI machine interface and the Debug Adapter Protocol wrapped the same engine. LLDB, the debugger of the LLVM
project, arrived in 2010 and became the default on Apple platforms. `rr`, from Mozilla, introduced practical record and
replay on Linux by recording non-deterministic inputs and then allowing reverse execution, which defeats the "it only
fails once" problem for the user-space cases that it supports.

The debug information that debuggers read evolved as well. The `stabs` format gave way to DWARF, which describes types,
variables, inlining and line tables. Early practice was to ship binaries with symbols or not at all. Distributions solved
the size problem by separating debug data into debuginfo packages, and the build-ID note made the match between a binary and
its debug file exact. Because installing debuginfo packages by hand was tedious, the `debuginfod` service was developed
so that GDB and other tools can fetch the right file over HTTP by build ID on demand. Red Hat's debugging chapter
explains how the debugger reads symbols and how to inspect state in GDB [src: rhel-10-docs 866fa8e80f98c6a3].

Post-mortem debugging has its own history. Core files date from the earliest Unix; the kernel writes the memory image of
a process that dies from certain signals. For decades the default was a file named `core` in the current directory, which
was of little use for daemons (no write permission, no space, no way to find it). Linux added a configurable pattern
(`/proc/sys/kernel/core_pattern`) that can name files with the executable and process IDs or pipe the dump to a helper.
Distribution helpers followed: Fedora's ABRT and later `systemd-coredump`, which stores compressed dumps and metadata that
`coredumpctl` lists and opens in GDB [src: man-pages d8a4a5a7fa2e1dd4]. The manual page for core files documents the
signals that produce them, the size limit, and the pattern's format specifiers [src: man-pages a1b12fce289181f9].

Memory-error detection went through several generations. Libraries such as Electric Fence and `dmalloc` replaced the
allocator to catch overruns, which only found errors near heap blocks. Purify was a commercial tool that instrumented
object code. Valgrind, created by Julian Seward and first released in 2002, did the same without recompiling, by translating
machine code to an intermediate form and adding checks. Its `memcheck` tool tracks which bytes are addressable and which
are defined, and reports invalid reads and writes, use of uninitialised values, use after free and leaks. Compile-time
tools (AddressSanitizer, 2011) later offered similar findings with much less slowdown, and Valgrind's other tools
(`callgrind`, `massif`, `helgrind`, `drd`) address profiling, heap profiling and threading errors. Bootlin's material shows
Valgrind and its `vgdb` connection with GDB in use [src: bootlin-training b38d2ff074d0b706].

The pattern that emerged is layered evidence: make each build debuggable by design, collect post-mortem state automatically
when it fails in the field, and run instrumentation in test to catch problems before then.

## Current state

A debuggable build uses `-g` (and `-g3` for macro information), usually with `-O0` or `-Og` during development, and keeps
frame pointers or unwind tables so that backtraces work. At `-O2` the debugger can still work, but variables are
"optimized out", lines jump, and inlined functions appear as pseudo-frames. For release builds, the debug data goes to
separate files linked by build ID (LNX-220-T01), and `debuginfod` clients can be enabled with the `DEBUGINFOD_URLS`
environment variable.

GDB's work divides into running, stopping, looking and changing. `gdb ./prog` loads the program, `run args` starts it and
`start` stops at `main`. Breakpoints are set with `break file.c:42` or `break func`, conditional ones with `if`, and a
`watch` expression stops when a value changes (using hardware debug registers where possible). Execution control uses
`next`, `step`, `finish`, `until` and `continue`. State is examined with `bt` (and `bt full`), `frame N`, `info locals`,
`print expr`, `x/16xb addr` for raw memory, `info registers`, `info sharedlibrary` and `info threads`. `thread apply all bt`
gives every stack in a multi-threaded process, which is the first command to run on a hang. `catch` stops on system calls,
signals, or C++ exceptions. GDB can run commands from a file or in batch mode (`gdb -batch -ex run -ex bt ./prog`), which
makes it useful in scripts and continuous integration. It can attach to a running process with `gdb -p PID`, subject to the
kernel's `ptrace_scope` setting under the Yama security module, and it can debug remotely: `gdbserver :2345 ./prog` on a
target and `target remote host:2345` on the host, the setup used for embedded and container work [src: bootlin-training 6b4a807a7a3cc677].
GDB has a Python API for pretty-printers and custom commands, which is how standard library containers display readably.

For crashed programs, a core file is an ELF file of type `CORE`. Its notes record registers per thread and the process
status, and its load segments hold memory contents. `gdb ./prog core` reconstructs the stack at the time of death, provided
that the same executable and libraries (matched by build ID) are available. Whether a core is written depends on the
resource limit (`ulimit -c`), the kernel's `core_pattern`, the executable's permissions, and the filesystem. A pattern that
begins with a pipe symbol sends the dump to a helper program; on systemd machines this is `systemd-coredump`, so
`coredumpctl list`, `coredumpctl info` and `coredumpctl debug` replace file hunting [src: man-pages d8a4a5a7fa2e1dd4]. In containers
the pattern is a host-wide setting, which is a frequent source of confusion. A running process can be snapshotted without
killing it by `gcore PID` (part of GDB). Red Hat's guide shows how to debug a crashed application from a core and how
to obtain the missing debug packages [src: rhel-10-docs 1d1f1d2922dc6bb7], and Bootlin's course shows the same workflow for embedded targets [src: bootlin-training 5aec839300c31324].

Valgrind is used by prefixing the command: `valgrind --leak-check=full --track-origins=yes ./prog`. Memcheck prints each
problem with a stack trace for the access and another for the allocation or free. Typical messages: "Invalid read of size 4"
(overrun or use after free), a warning that a conditional branch depends on uninitialised data, "Mismatched free", and the
leak summary with categories: definitely lost, indirectly lost, possibly lost and still reachable. `--error-exitcode=N`
turns findings into a failing status for tests, `--suppressions=file` hides known third-party noise, and `--gen-suppressions`
helps to write them. Programs run 10 to 50 times slower, so test inputs must be small. `--vgdb=yes` allows GDB to attach to the
Valgrind-hosted process and stop at the first error. Callgrind records instruction counts and call graphs for
`kcachegrind`, which bridges to the profiling topic (LNX-220-T11), and Massif records heap usage over time. Helgrind
and DRD detect data races and lock-order errors in threaded programs.

The generalised pattern is observation at three moments: during execution (breakpoints, watchpoints, tracing), after
death (core files and unwinding), and under instrumentation (shadow state that makes invisible errors visible).

## Assessment: the good, the bad and the ugly

The good side is that the toolset is complete, free and scriptable. GDB works on stripped programs with separate symbols,
across architectures, for local and remote targets. Core files let a rare production crash be examined later, and
`debuginfod` solves most symbol logistics. Valgrind needs no recompilation and finds whole classes of bugs
deterministically, including uninitialised reads, which many other tools miss.

The bad side is that optimisation, threads and deep abstraction make observation harder. Optimised code reports
"value optimised out" for variables the compiler kept in a register or removed. Breakpoints in inlined code appear in many
places. Debugging threaded or signal-driven programs changes timing. C++ templates and Rust generics produce long symbol
names, and the debugger needs the matching pretty-printers. Valgrind's slowdown, its limited support for newer
instructions on some processors and its false positives with custom allocators or unusual stack tricks lead teams to
use sanitizers by default. A frequent error is to debug a different binary than the one that crashed: after a rebuild
the addresses differ, and the core is useless without the exact executable.

The ugly side is operational. Cores can contain secrets (keys, passwords, personal data), so they need restricted
permissions and retention rules; many security baselines disable them or restrict `systemd-coredump` storage. Setuid
programs do not dump by default, a dump may be truncated by the size limit, and a pipe-based pattern fails silently
if the helper is missing. `ptrace` is blocked by default in some container profiles and in locked-down environments, which
prevents `gdb -p` and `strace` unless the capability is granted. Watchpoints on many locations are slow, and a data race is
often not reproducible under the debugger.

## Applications beyond this domain

Post-mortem analysis applies in many fields. The Linux kernel uses the same concept with `kdump`, which captures a
memory image after a panic and analyses it with `crash` or GDB; the same workflow of dump, matching debug symbols and a
backtrace applies. Language runtimes have their equivalents: Java thread and heap dumps, Go's goroutine dump on `SIGQUIT`, Python's
`faulthandler` and `py-spy dump`, and Windows crash dumps. Container and Kubernetes work uses ephemeral debug containers
to attach tools next to a failing process, and `strace` and `ltrace` offer system-call and library-call traces when a
debugger is unnecessary. In data pipelines, record-and-replay and deterministic simulation testing carry the idea of
reproducing a failure by capturing its inputs. Even outside software, flight recorders and incident timelines follow the
same principle of having evidence captured before the fault.

## Examples

A segmentation fault example: a program prints a fault message. Build with `-g -O0`, run `gdb -batch -ex run -ex bt ./prog`,
and read the output: frame zero names the function and the source line, the caller frames show the path to it. `frame 1`
then `info locals` and `print *ptr` show that a lookup returned a null pointer which was not checked. The fix is a check
and a decision about what the caller should do. The lab uses a program that crashes in exactly this way and asks you to
keep both a live backtrace and one read from a core file.

A hang example: a daemon stops answering. `gdb -p PID`, then `thread apply all bt`, shows one thread waiting in
`pthread_mutex_lock` inside a function that another thread already holds while it waits for the first thread's work.
That is a lock-order inversion. A single `gcore` before restarting the service preserves the evidence for later study.

A memory error example: a program prints correct results on the developer machine but corrupts data on a customer's.
Valgrind reports "Invalid write of size 1" with a stack that ends in `strcpy`, and a second stack showing a heap block
of 8 bytes that was allocated in the constructor. The copy was longer than the buffer. A failing debugging example is the
program that disappears from under the debugger: with ASLR disabled and different environment size, the stack layout changes
and the overflow lands on different bytes. GDB disables ASLR by default for this reason, and `set disable-randomization off`
restores the production behaviour for cases that depend on it.

## Related problems and ideas

The prerequisite for all of this is the toolchain knowledge from LNX-220-T01 (debug sections, stripping, build IDs). The
sanitizers of LNX-220-T05 replace many Valgrind sessions by instrumenting at compile time, and fuzzing (LNX-220-T06) is
an excellent source of crashing inputs that GDB then explains. Profiling with `perf` (LNX-220-T11) answers where time is
spent, while this topic answers why behaviour is wrong; Valgrind's `callgrind` sits in both. Services under systemd
(LNX-220-T08) get their cores through `systemd-coredump`, and the environment of a unit (limits, `LimitCORE=`) determines
whether a dump occurs. Packaging (LNX-220-T10) decides whether the debuginfo packages exist for the shipped binary.

Alternative and complementary tools include `strace` (system calls), `ltrace`, `perf trace`, eBPF-based tracing with
`bpftrace`, and logging with structured fields. `rr` provides reverse debugging, and the Pernosco service builds a
searchable database from `rr` recordings; Undo's LiveRecorder is a commercial counterpart. Time-travel debugging, omniscient
debugging and statistical fault localisation are ideas not widely deployed in Linux practice, though `rr` shows that they can
be made practical for ordinary software.

## Active research

Current work includes making record-and-replay cheaper and more widely applicable, including support for newer CPU
features and for multi-threaded programs with fewer constraints. The GDB project has been improving its handling of
multi-target debugging, DWARF 5 and the parsing speed of large debug-info sets through background indexing. Debuginfod
continues to expand to more distributions and to include source files and, in newer versions, an index for symbol queries
(to verify the exact feature set per release). Researchers are studying automated crash triage and deduplication using
stack signatures, and fuzzing and sanitizer reports are being fed into reproduction minimisers. Hardware features such as
Intel Processor Trace and Arm's trace extensions give instruction-level histories at low overhead.

## Future direction

Expect debugging to move toward "capture first, analyse later": always-on lightweight tracing, automatic core retrieval
with symbol servers, and reproducible environments for replay. More teams will run sanitizers in continuous integration
and keep Valgrind for cases where recompilation is impossible. For Rust and Go services, the equivalent habits are
backtraces with symbols, the `RUST_BACKTRACE` variable and goroutine dumps, and the native GDB skills still apply
when the problem crosses into C libraries. A learner who masters `bt`, `info locals`, `thread apply all bt`, a core file
workflow and a clean Valgrind run can handle most real incidents.
