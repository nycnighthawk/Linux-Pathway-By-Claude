# D-Bus services and XDG conventions

## Define the problem

Processes on a Linux machine need to talk to each other and to share a few conventions about where things live. The
conversation problem is local inter-process communication with structure: a desktop component asks the network manager
for the connection state, a session program asks the system whether the battery is low, an application asks a
background service to open a file or show a notification. Pipes and sockets can carry such messages, but each pair of
programs would have to invent its own protocol, its own discovery rule (which socket path?) and its own access control
(who may ask?). The filesystem problem is smaller but just as common: where may a program put its configuration, its
caches, its data and its runtime state for one user, so that backups, clean-up tools, sandboxes and users can find them?

D-Bus answers the first problem with a message bus that offers naming, typed method calls, signals, properties, introspection
and policy, together with on-demand activation of services. The XDG Base Directory Specification answers the second with
a small set of environment variables and defaults. Together they define how well-behaved Linux applications meet the
user session. This topic, at an intermediate depth, covers the bus model, how to call and expose services, the activation
files, the main XDG directories and how both concepts interact with systemd and with sandboxes such as Flatpak. Service
lifecycle options belong to LNX-220-T08, and packaging of the files to LNX-220-T10.

## History and approaches

The first desktop environments solved communication in their own ways. KDE used DCOP, a simple daemon-based protocol,
while GNOME built on CORBA through ORBit, which was heavy and fragile. Both teams wanted something smaller, and in 2002
Havoc Pennington, Alex Larsson and Anders Carlsson started D-Bus under the freedesktop.org umbrella, with the message
bus design that has survived. It first served desktop integration (HAL, NetworkManager, notifications) and then moved
into the system: the system bus carried messages between privileged daemons and unprivileged clients with a policy that
decides who may own a name and who may call it. Many early desktop services have been replaced or merged, but
the bus remains the standard control plane for session and system components.

A parallel line of work addressed performance and security. The reference implementation, `dbus-daemon`, is a user-space
router, so each message crosses the daemon and costs two context switches. The Linux kernel developers proposed kdbus in
2013 to move the bus into the kernel, but the project was rejected for inclusion and abandoned in 2015. The practical
outcome was `bus1` as a research design and, in user space, the faster `dbus-broker` (2017) that Fedora and later others
adopted as the default implementation. The systemd project also created `sd-bus`, a client library with a simpler design
than libdbus, and the `busctl` tool, whose manual page describes the introspection and call commands
[src: man-pages 202a1a19d2c42f7c]. Other client libraries include GDBus (part of GLib), QtDBus, the Python `dbus-python`
and `dbus-next`, and `zbus` for Rust.

Alternatives to D-Bus have appeared over time: Varlink, a simple JSON-over-socket protocol that systemd and other projects
are adopting for new interfaces; gRPC and plain Unix sockets for application-specific services; and the portals concept of
Flatpak, which defines a small set of D-Bus APIs so that a sandboxed program can ask the user for a file or a screenshot.
The lessons from this evolution: a bus is valuable for discovery and policy, and its cost is acceptable for control
messages but not for bulk data, which should travel over a passed file descriptor.

The directory conventions had a separate history. Traditional Unix programs wrote dotfiles directly into the home directory
(`~/.programrc`), which cluttered it, made backups and sandboxing awkward and offered no place for caches that may be
deleted. The freedesktop.org XDG Base Directory Specification (2003, with updates over the years) defined the split by
purpose, with environment variables that override the defaults, and later versions added the state directory and rules
for permissions. The systemd `file-hierarchy` documentation describes the system-level counterpart that these
directories sit beside [src: man-pages 78e8977565f7d624].

## Current state

D-Bus has two kinds of bus. The system bus is one per machine (socket `/run/dbus/system_bus_socket`) and requires policy files in
`/usr/share/dbus-1/system.d/` or `/etc/dbus-1/system.d/` to let a service own a name or to let clients call it. The session
bus is one per login session, with its address in `DBUS_SESSION_BUS_ADDRESS`, usually a socket under `XDG_RUNTIME_DIR`
(`/run/user/UID/bus`), which `pam_systemd` sets up for each login [src: man-pages 59b62910641a0023]. On a headless host you can start a
throw-away session bus with `dbus-run-session -- command`, which is how automated tests and the lab use it.

A connection to the bus gets a unique name (like `:1.42`) and can request well-known names such as `org.freedesktop.Notifications`
in reverse-domain form. A service exposes objects identified by paths (`/org/example/Lab`) that implement interfaces
(`org.example.Lab`). Interfaces contain methods, signals and properties, each with a type signature from a small set
(`s` for a string, `i` for a 32-bit integer, `a` for an array, `a{sv}` for a dictionary of variants, `(...)` for a structure). The
standard interfaces `org.freedesktop.DBus.Introspectable`, `Properties` and `ObjectManager` are implemented by most
libraries. Introspection returns an XML description, so tools can explore a service without documentation. A signal is a
broadcast that clients subscribe to with a match rule.

The command-line tools are the way into all of this. `busctl list` shows names and their owners; `busctl tree NAME` lists object paths;
`busctl introspect NAME PATH` prints interfaces and members; `busctl call NAME PATH IFACE METHOD SIG ARGS` calls a method;
`busctl get-property` and `set-property` access properties; `busctl monitor` watches traffic; `--user` selects the session bus
and `--system` the system bus. The manual page documents the argument formatting rules by signature
[src: man-pages 2cf4fa9d676bd18b] and the options [src: man-pages f3d3d2fb77d581b2]. `gdbus` from GLib and `dbus-send` do
similar work, and `d-feet` and `bustle` are graphical explorers.

Activation allows a service to start on demand. A file with the suffix `.service` placed in `share/dbus-1/services/` (session) or
`share/dbus-1/system-services/` (system) under any directory in `XDG_DATA_DIRS` has a `[D-BUS Service]` section with `Name=`, `Exec=`
(or `SystemdService=` to delegate to systemd) and, for the system bus, `User=`. When a client sends a message to a
name that has no owner, the bus finds this file, starts the program and holds the message until the program takes the name.
For services that run under systemd, `Type=dbus` with `BusName=` waits for the name to appear, and the bus file uses
`SystemdService=` so that activation goes through the manager and gets its resource controls.

Writing a service means choosing a library, requesting a name, registering objects and running the main loop. In GDBus,
`g_bus_own_name` and `g_dbus_connection_register_object` with introspection XML do this, and the method-call handler
returns values by `g_dbus_method_invocation_return_value`. In Rust, `zbus` derives the interface from annotated traits; in Python,
`dasbus` or `dbus-next` do the same job with decorators. Good services emit `PropertiesChanged` signals instead of making clients poll,
exit when idle if they were activated on demand, and validate arguments, since any local program that passes policy can call them.

The XDG specification defines these locations. `XDG_CONFIG_HOME` (default `~/.config`) is for user configuration;
`XDG_DATA_HOME` (`~/.local/share`) is for user data such as icons and desktop files; `XDG_STATE_HOME` (`~/.local/state`) holds
state that survives restarts but is not worth backing up, such as logs and history; `XDG_CACHE_HOME` (`~/.cache`) is for
disposable data; and `XDG_RUNTIME_DIR` (`/run/user/UID`) is a per-session directory with mode 0700 for sockets and pipes,
created at login and removed at logout. The search lists `XDG_CONFIG_DIRS` (default `/etc/xdg`) and `XDG_DATA_DIRS` (default
`/usr/local/share:/usr/share`) provide system-wide defaults in order of priority. A program should read from the user directory first
and then the list, write only to the user directory, create directories lazily with mode 0700, and treat a variable that holds a relative
path as unset. Libraries help: `g_get_user_config_dir()` in GLib, `QStandardPaths` in Qt, `platformdirs` in Python, the `directories` crate in
Rust, and `os.UserConfigDir` in Go. Related conventions include desktop entry files (`.desktop`) that describe applications, the icon theme
specification, and MIME associations, all found through `XDG_DATA_DIRS`. Flatpak sets these variables inside the sandbox so that each
application has private directories under `~/.var/app/ID`, while the metadata file describes which of the bus names and
directories it may reach [src: man-pages 86ed0c6875a51f97].

The generalised pattern is "names and locations by convention": a stable name for the service, a search path for its description files, per-user
directories chosen by purpose, and tools that can introspect what is there.

## Assessment: the good, the bad and the ugly

The good side is that these conventions turned a mass of bespoke arrangements into something a developer can learn once.
Introspection makes services self-describing, signals and properties give event-driven designs, bus activation removes the need
to start helpers in advance, and policy files give a central place to review who can talk to what. The XDG split gives users
a reliable answer to which files hold configuration, which can be deleted and which belong in a backup and sandboxing tools can map the
categories to permissions.

The bad side is cost and surface area. The bus is not meant for large payloads or high message rates, and a service that blocks
in a method handler stalls its callers until the reply timeout (25 seconds by default). Any process in the session can usually talk to
any session service, so the session bus is not a security boundary between a user's own programs; sandboxes use filtering proxies
(`xdg-dbus-proxy`) to restrict access. The type system and the signatures are unforgiving for newcomers, and different libraries
expose slightly different behaviours around properties and error mapping. XDG compliance is voluntary, and many programs still write dotfiles.

The ugly side includes broken environments. Under `sudo` or `ssh` there may be no session bus, so a command that works at
the desktop fails with a message about being unable to autolaunch a bus. `XDG_RUNTIME_DIR` can be missing in cron jobs and in
containers, which makes programs fall back to `/tmp` with different permissions. Name collisions and stale service files
for removed packages cause activation to start the wrong binary. Programs that hard-code `~/.config` ignore overrides and
fail in sandboxes. A service that exits during activation without taking its name makes the bus return a timeout error to the
client, which is hard to diagnose without `journalctl` or `busctl monitor`.

## Applications beyond this domain

The pattern of a name-routed message bus with typed interfaces and introspection is shared by many systems: Android's Binder
and its service manager, macOS XPC and Mach ports, ROS topics in robotics, MQTT and message brokers in industrial and
cloud settings, and the kernel's Netlink families. Varlink and gRPC use similar introspection to generate clients. The activation idea
is also found in systemd socket units and in serverless platforms that start a function on the first request. XDG's separation of config,
data, state and cache is mirrored by macOS's `~/Library` layout and Windows' `AppData\Roaming` and `Local`, and
by the twelve-factor rule that config is separated from code. Tools that package applications for several platforms
need exactly this mapping.

## Examples

A first example is calling the system's notification service from a shell: `busctl --user call org.freedesktop.Notifications
/org/freedesktop/Notifications org.freedesktop.Notifications Notify susssasa{sv}i "demo" 0 "" "Hello" "Body" 0 0 5000`. The signature
string is the hard part; introspection shows it. On a headless host the call fails because nothing owns the name, which demonstrates
the difference between a missing service and a bad call.

A second example is the lab service: a GDBus program that owns `org.example.Lab`, is described by a one-file activation entry,
and reads a greeting from `$XDG_CONFIG_HOME/lab/greeting`. A private session bus is started with `dbus-run-session`; the first
`busctl call` triggers the start of the server, and the answer shows both mechanisms: the name was resolved by bus activation and the
configuration came from the XDG directory chosen by the environment variable.

A failing example: a developer tests a service as root with `sudo ./server` and it works, but under the real session it fails to own its
name. The bus policy for the system bus denies the name for that user, and the fix is a policy file that allows ownership for the service's
user. Another failing case is a program that stores its cache under `XDG_CONFIG_HOME`, so that a "clean up caches" tool never
touches it and a configuration backup grows to gigabytes. Moving it to `XDG_CACHE_HOME` fixes both.

## Related problems and ideas

The service lifecycle belongs to LNX-220-T08: `Type=dbus` and `BusName=` are the bridge, and `systemd-run --user` creates transient
user services in the same session. Packaging (LNX-220-T10) installs `.service` activation files, desktop entries and metainfo
into the right `share/` directories, and Flatpak manifests list the bus names an application may own or talk to, so a
packager must know the D-Bus names the program uses. GUI programs (LNX-220-T12) use D-Bus for accessibility (AT-SPI), notifications, portals
and single-instance activation (`GApplication` registers a name on the session bus and forwards a second launch to the first). The C
library and file-descriptor passing concepts connect to LNX-220-T03 in that a client library is a shared library with a
versioned interface.

Alternatives and extensions: Varlink for new system APIs, direct Unix sockets with SO_PEERCRED for simple authenticated peers, `sd-bus`
for a simpler C client, `dbus-broker` for a faster router, the portal APIs for sandbox-friendly requests, and a generated
interface via `gdbus-codegen` that produces C stubs from XML. Experimental ideas include capability-based IPC where possession of a
handle is the permission, as in some microkernel systems and in Cap'n Proto, and kernel-assisted designs proposed after kdbus.

## Active research

Engineering effort is directed at replacing parts of D-Bus use inside the system with Varlink to remove the dependency on a
running bus during early boot, improving `dbus-broker` and policy handling, and hardening access for sandboxed programs through portals,
including the permission store and the global shortcuts, camera and screen-capture portals. The XDG specifications evolve through
the freedesktop.org process: the state directory was added in version 0.8, and recent work looks at a standard for
`XDG_BIN_HOME`-style locations and for user-directory handling (to verify what has been accepted). Security researchers examine
confused-deputy problems in services that act on behalf of callers.

## Future direction

Expect more system APIs to be offered on both D-Bus and Varlink for a long transition, with sandboxed applications pushed to use
portals instead of broad bus access. Programming libraries will increasingly generate bindings from interface descriptions,
and more services will be socket-activated and idle-exit. For a developer today, the stable approach is to use a high-level
library, define interfaces carefully (they are an API), follow the XDG directories through the library helper rather than hard-coded
paths, test with a private session bus, and inspect everything with `busctl`.
