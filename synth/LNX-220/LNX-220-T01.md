# Compilers, binutils, linking and the ELF format

## Define the problem

A C program starts life as text files, and the machine can only execute a set of numbered bytes arranged so that a kernel
loader can map them into an address space. Something has to turn one into the other, and it has to do it for projects
with thousands of source files written by different people at different times. The solution on Linux is a pipeline of
small tools that all agree on a single file format, the Executable and Linkable Format (ELF). A developer who understands
the pipeline can read an error such as an undefined reference, a missing shared object or a "version not found" message
as a statement about a specific stage, instead of as noise. A developer who does not will change flags at random until
the message goes away.

The gap this topic fills is the space between "I can type `gcc main.c`" and "I know what each stage produced and why my
binary behaves as it does". Failure takes familiar forms: a link that works with one library order and not another, a
binary built on a new distribution that refuses to start on an older one, a release build that is fast but cannot be
debugged because the symbols were thrown away, a program without the hardening flags that the distribution expects. This
slice covers the compiler drivers (GCC and Clang), the binutils programs that inspect and edit objects (`as`, `ld`,
`ar`, `nm`, `objdump`, `readelf`, `objcopy`, `strip`), the way a linker resolves symbols and applies relocations, and the
ELF structure that the kernel and the dynamic loader consume. Build orchestration (make, CMake, Meson) belongs to
LNX-220-T02, library naming and versioning to LNX-220-T03, and debuggers to LNX-220-T04; this topic provides the
vocabulary all three rely on.

## History and approaches

Early Unix produced `a.out` files, a simple header followed by text, data and a symbol table. The format worked while
programs were statically linked and small. It struggled when shared libraries appeared, because a shared object needs
position-independent code or fixed load addresses, and `a.out` had no good place to describe dynamic relocation. Linux
spent its first years on `a.out` shared libraries whose load addresses were allocated by hand from a registry, an
arrangement that scaled badly. System V Release 4 had introduced ELF around 1989, and the Linux distributions moved to it
in the middle of the 1990s together with a new C library generation. Other systems took different routes: Windows kept
PE/COFF, macOS uses Mach-O, and WebAssembly defined its own module format, but the three roles of every format are the
same, namely describing sections for the linker, describing segments for the loader and carrying symbols.

On the compiler side the GNU Compiler Collection dominated for two decades. A notable partial failure was the 1990s split
between the official GCC line and the experimental EGCS fork; the fork's faster development won, and the two were
reunited in 1999 under the new governance. In 2003 a research project at the University of Illinois produced LLVM, and
Clang, a C-family front end built on it, followed in 2007. Clang offered fast compilation, readable diagnostics and a
library design that let editors and analysers reuse the parser. Apple's adoption made it a production tool, FreeBSD made
it the system compiler, and the Linux kernel gained the ability to build with it after years of patches. The competition
helped both projects: GCC's diagnostics improved noticeably, and Clang acquired many GNU extensions and options so that
existing code would build.

Linkers followed a similar arc. The classic GNU `ld` is correct and flexible, driven by linker scripts, but slow on
very large programs. The `gold` linker (2008) was a faster ELF-only design that eventually lost support to LLVM's `lld`
and, later, to `mold`, which uses aggressive parallelism and became popular for incremental developer builds around 2021.
The compiler vendors also added link-time optimisation so that optimisation could see across translation units, at the
cost of longer links and harder debugging. Security shaped the defaults over the same period. Address space layout
randomisation was only useful if executables were position independent, so distributions began enabling PIE by default
in the middle of the 2010s. Relocation read-only (RELRO) protections hardened the global offset table after start-up,
and a lazy-binding mechanism that was a performance feature became a security liability, because writable function-pointer
tables are an attractive target [web: redhat.com]. The lesson the field drew is that the build pipeline is also a security
boundary, and that sensible defaults belong in the compiler driver and in the distribution packaging, not in each project.

The pattern that emerged is a stable contract with swappable parts. The compiler driver, assembler and linker exchange ELF
relocatable objects; any linker that understands the format can replace another; and the same objects feed the loader,
the debugger and the profiler. Distribution toolchains such as Red Hat's GCC Toolset add a further layer, shipping
newer compilers in parallel with the system compiler so that applications can use modern language features without
changing the base operating system [src: rhel-10-docs 56836a28262d53e2].

## Current state

When you run `gcc` you are running a driver that coordinates several programs. The preprocessor expands includes and
macros into one translation unit; the compiler proper turns that into assembly text; the assembler produces a
relocatable object file with the suffix `.o`; and the linker combines objects and libraries into an executable or shared
object. The driver switches in your options at each step. `-E` stops after preprocessing, `-S` after generating assembly,
`-c` after assembling, and none of them links. Clang behaves the same way and accepts most of the same options, which is
what makes the two interchangeable in many build systems [src: man-pages 0bd44e96249512bd]. Optimisation level
(`-O0` through `-O3`, plus `-Os`), debug information (`-g`), warnings (`-Wall -Wextra`) and the language standard
(`-std=`) are properties of the compile step; hardening choices such as `-fstack-protector-strong`, `-D_FORTIFY_SOURCE`,
`-fPIE` and, since GCC 14, the convenience option `-fhardened` combine several protections [web: gnu.org].

An ELF relocatable object has sections: `.text` for code, `.data` and `.bss` for initialised and zero-initialised
variables, `.rodata` for constants, plus a symbol table, a string table and relocation sections. A relocation is a note
saying that at a given offset the final address of a named symbol must be patched in, using a particular formula. The
compiler cannot know where a function in another file will end up, so it leaves a placeholder and a relocation. `nm` lists
symbols with a type letter (`T` for code defined here, `U` for undefined, `D` and `B` for data), `objdump -d` disassembles,
and `readelf -S`, `-s` and `-r` show sections, symbols and relocations. `objcopy` copies and transforms objects, and
`strip` removes symbols and debug data. The tools in this family come from the GNU binutils package, and the LLVM project
ships compatible `llvm-nm`, `llvm-objdump` and `llvm-readelf`.

The linker's job has three parts. First, it resolves symbols: every undefined symbol in one object must be matched with a
definition in another object or in a library. Objects named on the command line are always included. A static archive
(`libx.a`, built with `ar`) is a bag of objects, and the linker pulls in a member only when it satisfies a symbol that is
currently undefined. This is why library order matters for archives: a library listed before the object that needs it
contributes nothing. Second, it lays out sections: input sections of the same kind are merged and assigned addresses
according to a linker script, usually the built-in default. Third, it applies relocations to the merged image. When the
inputs include shared objects the linker does not copy their code; it records a `DT_NEEDED` entry naming each required
library by its soname and leaves symbols to be bound at run time [src: man-pages dc440ad2f3998640].

The result is described twice. Section headers serve tools like the linker, `objdump` and `strip`, and are optional at
run time. Program headers describe segments for the kernel: loadable segments (`PT_LOAD`) with their permissions, an
interpreter segment (`PT_INTERP`) that names the dynamic loader, a dynamic segment (`PT_DYNAMIC`) with tags such as
`DT_NEEDED`, `DT_SONAME`, `DT_RUNPATH` and `DT_FLAGS`, a stack permission marker (`PT_GNU_STACK`) and, for hardened
binaries, `PT_GNU_RELRO`. The kernel's `execve` maps the load segments, finds the interpreter, maps that too and starts
at the interpreter's entry point. The interpreter (`ld-linux-x86-64.so.2` on x86-64) loads the needed libraries,
performs relocations and then jumps to the program's entry point, which runs C start-up code and finally `main`. Its
search rules and environment variables are documented in its manual page [src: man-pages afd31ce8d4400857].

Calls from the program into shared libraries go through the procedure linkage table and the global offset table. With
lazy binding the first call lands in a stub that asks the loader to resolve the symbol and patches the table; later
calls jump straight to the target. `-Wl,-z,now` (or `LD_BIND_NOW=1`) forces every symbol to be resolved at start-up, and
together with `-Wl,-z,relro` it allows the table to be made read-only before `main` runs, a combination called full RELRO.
Building as a position-independent executable (`-fPIE -pie`) lets the kernel place the program at a random address,
and the generated code reaches its data through program-counter-relative addressing instead of absolute addresses.

Debug information lives in `.debug_*` sections in DWARF format. Because it is large, distributions split it from the
installed binary: `objcopy --only-keep-debug` writes a separate file, `strip` shrinks the executable and
`--add-gnu-debuglink` (or a build-id note, `-Wl,--build-id`) lets debuggers find the right file again. Debuginfo packages
and the `debuginfod` service serve those files by build ID, which is how a stripped production binary can still be
debugged. The generalised pattern is: compile to a relocatable form that defers address decisions, record symbolic
information, defer decisions again to link time and then to load time, and keep a side channel of metadata for tools.

## Assessment: the good, the bad and the ugly

The good part is stability and inspectability. Every stage leaves an artefact that standard tools can examine, so a
failure can be located: compile errors in one file, undefined symbols at link time, unresolved libraries at start-up,
crashes after that. ELF is extensible through notes and custom sections, which is how build IDs, hardening markers, BPF
programs and kernel modules all fit in. Toolchains are open, portable and cross-compilable. A single GNU or LLVM
installation can target dozens of architectures with the same options.

The bad part is the amount of implicit state. Symbol resolution depends on link order for archives, on which libraries
are found first and on interposition rules that let an executable's definition override a library's. `--as-needed` and
`--no-undefined` change behaviour in ways that surprise people. The C and C++ one-definition rule is not checked by the
linker, so two different functions with the same name in different libraries can silently coexist, and a wrong one wins.
Optimisation exploits undefined behaviour, so a program that "worked" at `-O0` may break at `-O2`; the compiler is not
wrong, the program was. Long link times for large C++ programs and for LTO builds are a daily cost, which partly explains
the success of faster linkers.

The ugly parts are mostly about compatibility. A binary built against a recent glibc records versioned symbols, and the
loader refuses to start it on a system whose glibc lacks them, with a message naming `GLIBC_2.xx`. The common fixes are to
build on the oldest supported distribution, to build in a container that matches the target, or to link statically
against musl, each with a trade-off. Mixing compilers can break the C++ ABI, and mixing libstdc++ and libc++ certainly
does. Stripped binaries are hard to debug unless the debug files were saved at build time. Reproducible builds need
fixed timestamps, paths and ordering, and many projects still embed `__DATE__` or build directories in their outputs.

## Applications beyond this domain

The idea of an object format with symbols and relocations reappears in many places. Kernel modules are ELF relocatable
objects that the kernel's own loader links into a running kernel, and a module that fails to load with an unknown symbol
is facing the same problem as a failed link. eBPF programs are compiled by Clang into ELF objects whose relocations are
resolved by the loader library against kernel and map information. Firmware and bootloaders are often linked with
custom linker scripts to place code at fixed addresses, which is the same linker doing a different job. Rust and Go emit
objects or call the system linker, so the same inspection tools work on their binaries; Go can also produce a fully static
executable without the system linker. Containers and "static binaries for the cloud" depend on understanding which
parts of a program are really bound at run time. In security work, checking for PIE, RELRO, stack canaries and the
executable-stack marker on a binary is a routine audit that is done with `readelf` alone.

## Examples

A first example is an undefined reference caused by order. Compiling `gcc main.c -lm` works, while `gcc -lm main.c`
fails on systems that link with `--as-needed` or use a static `libm.a`: the linker reaches `-lm` before any symbol is
undefined, drops it and later cannot find `sqrt`. The remedy is to list libraries after the objects that use them. The
diagnostic is `nm main.o | grep ' U '`, which shows exactly what must be satisfied.

A second example is the effect of the hardening flags. Build a two-file program with `-O2 -g -fPIE -pie`, then run
`readelf -h` and see the type `DYN` (a PIE) instead of `EXEC`. Add `-Wl,-z,relro,-z,now` and `readelf -lW` shows a
`GNU_RELRO` segment while `readelf -dW` shows `BIND_NOW`. The accompanying lab asks you to produce and verify these
properties, and to split the debug data into a file reachable by `.gnu_debuglink`.

A failing example comes from distribution upgrades. A vendor ships a binary compiled on a current release; a customer on
an older enterprise release sees "version `GLIBC_2.38` not found". `objdump -T app | grep GLIBC_` lists the versioned
symbols the program needs, and the highest one defines the minimum system. The fix is a build environment with an older
glibc or a container image that matches the target, which is also how the Red Hat toolset images and Rocky or Alma
build roots are used [src: rhel-10-docs c48817f679eb7224]. A subtler failure is a program that crashes in a library while
the only available stack trace shows hex addresses: someone stripped the binary and discarded the debug file, and
without a build ID the symbols cannot be recovered.

## Related problems and ideas

Package building (LNX-220-T10) uses the same compile and link steps inside a clean build root and splits the debug files
into separate packages, so what you learn here explains the contents of `-debuginfo` and `-dbg` packages. Library
naming, sonames and `pkg-config` (LNX-220-T03) are the other half of linking. Debugging (LNX-220-T04) uses the symbol and
line tables created by `-g`, and the sanitizers in LNX-220-T05 are compiler options that insert instrumentation at
compile time and a runtime library at link time. Build systems (LNX-220-T02) decide which flags reach each stage. For
Rust, Go and Python (LNX-220-T07), the question is where their toolchains meet the native one: Rust's `cargo` calls the
system linker, and Python extension modules are shared objects loaded by `dlopen`.

Alternative approaches include static linking with a minimal C library such as musl for easy deployment, unikernels that
link an application with only the operating system parts it needs, and bundling libraries with `$ORIGIN`-relative run
paths. Prelinking, which pre-computed relocations to speed up start-up, was once popular and was abandoned as
randomisation and faster loaders made it unhelpful. Post-link optimisers such as BOLT reorder code using profile data.
Package-level approaches such as Nix and Guix avoid system-wide libraries entirely and give each program an exact closure
of dependencies [web: nixos.org].

## Active research

Work continues on faster and more incremental linking, including parallel linkers and ways to avoid relinking when a
small part changes. Link-time optimisation is moving toward cheaper "thin" variants that scale to very large programs.
Profile-guided optimisation and feedback-directed layout, deployed at the scale of data centres, show that code placement
matters for instruction-cache behaviour. Hardening research examines control-flow integrity, shadow stacks and
pointer authentication, which need compiler, linker and loader support together; the Linux kernel and glibc are adding
support for hardware shadow stacks on recent processors (to verify the exact release status per architecture).
Reproducibility research aims for bit-identical builds across machines, and formats like the compact SFrame unwind
format aim to make stack traces cheaper for profilers without the full DWARF cost (to verify adoption in distributions).

## Future direction

Expect GCC and LLVM to keep a rhythm of one major release per year, each with new language standard defaults; GCC 15
moved the default C dialect to C23, and teams that carry old code will see new warnings and errors. Distributions are
tightening defaults, so options like `-fhardened`, frame-pointer retention for better profiling and stricter
treatment of implicit function declarations become normal. Memory-safe languages will link into mixed programs more often,
which puts a premium on a clean C ABI at the boundary. For a learner, the durable skills are the inspection commands:
`readelf`, `nm`, `objdump` and `ldd` will still tell you what a binary is, whatever fashion the compiler follows.
