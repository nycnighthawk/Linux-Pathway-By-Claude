# GUI applications (GTK and Qt) under Xvfb

## Define the problem

Graphical programs are awkward to build and test on servers and in continuous integration, because they expect a display, an input
device and often a desktop session. A build machine has none of these. A developer who maintains a GTK or Qt program still has to
run its tests, take screenshots for documentation, check that it starts, and sometimes drive it with synthetic input, all without a
person at a screen. Likewise, a systems engineer who needs to run one graphical tool on a remote machine, such as an installer, a
vendor configuration utility or a browser used for rendering, needs a display that nobody is looking at.

The answer on Linux is to separate "the program draws" from "a screen shows it". A display server accepts drawing requests over a socket;
a virtual one, Xvfb, keeps the framebuffer in memory instead of sending it to hardware. This topic is intentionally at an introductory depth.
It covers what a Linux graphical stack consists of, how a GTK or Qt application finds its display, how to run one headlessly, how to take
a screenshot or test a window, and where Wayland changes the picture. It does not teach GUI programming; the program in the accompanying lab
uses plain Xlib to keep dependencies small, and the same environment variables and tools apply to toolkit-based programs.

## History and approaches

The X Window System (MIT, 1984) separated the application from the display with a network protocol. A program, the X client, connects to
an X server, which owns the screen, keyboard and mouse, and sends drawing requests and receives events. Because the connection is just a
socket, a client can run on a different machine from the display, which was the basis of thin clients, and the same property is what allows a
display with no hardware behind it. Toolkits appeared above the protocol: Motif and Xt, then Qt (1995) and GTK (1997, born for the GIMP image editor).
Window managers and compositors are separate clients that decorate and arrange windows. The result was flexible and also complicated, with
a chain of libraries (Xlib, XCB, toolkit, theme engines) between a program and the pixels.

Headless use appeared early. The X.Org sample server includes `Xvfb`, the "virtual framebuffer" server, which implements the whole protocol but renders into memory.
Test teams used it in the 1990s for regression runs of graphical programs, and wrappers such as `xvfb-run` (a Debian script) automated the steps
of starting a server on a free display number, setting the authorisation cookie and cleaning up. Other X servers followed the same
idea: `Xvnc` (TigerVNC) serves a virtual display that a remote user can see, `Xephyr` nests an X server in a window, and `Xdummy` uses a dummy video driver so that
GPU-accelerated programs can run without monitors. Automation tools sit on top: `xdotool` sends synthetic keys and clicks, `xwd`, `import` and `scrot`
capture screenshots, and accessibility interfaces (AT-SPI) allow frameworks such as Dogtail and LDTP to find widgets by name.

The model changed with Wayland (2008). In Wayland the compositor is the display server, clients draw into buffers that they share with it, and input is delivered
only to the focused client. The design removed much of the X protocol's global state, which improved security (one client can no longer read another's windows
or keystrokes) and rendering consistency, and it made some things that used to be easy, such as screenshots, remote display and synthetic input, subject to
explicit permission through portals. GNOME and KDE now default to Wayland sessions, and X applications keep working through XWayland, a
rootless X server inside the compositor. Bootlin's material on the embedded graphics stack describes the layers, from kernel mode setting and the Mesa 3D drivers
to Wayland and the toolkits above [src: bootlin-training 4bb78b806dea94c0], and shows the role of the Wayland protocol [src: bootlin-training 28c3324316aa97db].

For headless Wayland there are equivalents: a compositor with a headless backend (`weston --backend=headless`, or `sway` with `WLR_BACKENDS=headless`,
or the Mutter test mode), plus tools such as `grim` for screenshots and `wtype` for input in wlroots-based compositors. Toolkits also offer "no display" back ends:
Qt has the `offscreen` and `minimal` platform plugins that render without any window system, and GTK 4 can render to an image through its Cairo or
GSK renderers when driven by a test harness. The lessons are that the separation of application and display makes automation possible, that the security model of the
newer protocol deliberately limits what a script may do, and that test code should use the toolkit's own testing support wherever possible.

## Current state

A graphical Linux application starts by locating its display. For X11 the environment variable `DISPLAY` (such as `:0` or `:99`) names the server's socket, and an
authorisation file (`XAUTHORITY`) holds the cookie. For Wayland the variable `WAYLAND_DISPLAY` names a socket under `XDG_RUNTIME_DIR`. GTK selects a backend with `GDK_BACKEND`
(for example `x11` or `wayland`, in preference order), and Qt with `QT_QPA_PLATFORM` (`xcb`, `wayland`, `offscreen`, `minimal`, `vnc`). If neither display is reachable the
program prints an error such as "cannot open display" and exits, which is the usual failure in cron jobs, containers and services.

Running under Xvfb is mechanical. `xvfb-run -a -s "-screen 0 1280x720x24" command args` starts an Xvfb on a free display number, sets `DISPLAY` and the authority file for the command, and
stops the server when the command ends. Running `Xvfb :99 -screen 0 1280x720x24 &` and exporting `DISPLAY=:99` gives a long-lived display instead, which is what
a continuous-integration job or a service unit typically uses, along with a lightweight window manager if the application needs focus handling or window decorations. Screenshots come from
`import -window root shot.png` (ImageMagick), `xwd -root`, `scrot`, or from the application itself (GTK's `gtk_widget_snapshot`, Qt's `QWidget::grab`), and the pixel can
be checked with image tools, as the lab does. Synthetic input uses `xdotool` (key, click, windowfocus) or the XTEST extension. Information about windows comes from `xwininfo -tree -root`, `xprop`
and `wmctrl`. GPU use is replaced by software rendering: Mesa's llvmpipe (`LIBGL_ALWAYS_SOFTWARE=1`) provides OpenGL on the CPU, which Xvfb also uses through its GLX support, so
programs with OpenGL content run, slowly.

Toolkit programs generally want extras: a session D-Bus (LNX-220-T09), started with `dbus-run-session -- command`, or GTK prints warnings and some features (settings, accessibility
bridge, single-instance behaviour) fail; `NO_AT_BRIDGE=1` silences the accessibility bridge when not needed; `GSETTINGS_BACKEND=memory` avoids needing dconf; fonts must be installed or text
renders as empty boxes; and `XDG_RUNTIME_DIR` must exist with mode 0700 (see the XDG conventions of LNX-220-T09). A typical test command is
`xvfb-run -a dbus-run-session -- pytest tests/gui` or `xvfb-run -a ctest`. Qt tests commonly use `QT_QPA_PLATFORM=offscreen`, with no X server at all, while QTest and `QSignalSpy`
drive widgets directly. GTK tests use `GtkTest` utilities or the Python bindings with a pytest fixture that spins the main loop.

Packaging and deployment add more. A desktop application ships a `.desktop` file, an icon and AppStream metadata in `share/`, so that menus and software centres can show it. As a
Flatpak (LNX-220-T10), it declares `--socket=wayland` and `--socket=fallback-x11` and `--device=dri`, and the sandbox then forwards the correct sockets. Debugging graphical programs
follows the usual tools (LNX-220-T04): attach `gdb`, use `G_DEBUG=fatal-criticals` to make GLib warnings stop the program, `GTK_DEBUG=interactive` for the inspector, `QT_LOGGING_RULES` for Qt logs,
and `xtrace` or `WAYLAND_DEBUG=1` to see protocol traffic. The generalised pattern is to supply a display, a session bus and a runtime directory as a fixture, and then to treat the GUI program
as any other process under test.

## Assessment: the good, the bad and the ugly

The good side is that a graphical test setup costs little: one package for Xvfb, one wrapper command, and standard image tools. It runs on any container and requires no GPU, so continuous
integration can exercise the real application, catch start-up crashes (which are common after dependency updates) and produce screenshots. The same environment supports documentation
screenshots and visual regression comparison. Remote use is also feasible: Xvfb with a VNC server turns a headless host into a desk that a person can attach to, which suits legacy
vendor installers.

The bad side is fidelity and flakiness. Software rendering is slower and differs subtly from GPU output, so pixel-exact comparisons fail between machines unless fonts, themes and renderers
are pinned. Without a window manager, focus, decorations and stacking behave differently from a desktop, and some toolkits assume one. GUI tests are timing sensitive, because events and redraws
are asynchronous, so fixed sleeps cause intermittent failures and the right approach is to wait for a condition. Wayland-only features do not run on Xvfb at all, and testing Wayland needs a compositor.

The ugly side is the long tail of environment dependencies. Missing fonts, missing locale data, a lack of a session bus or an unset `XDG_RUNTIME_DIR` produce odd warnings or crashes that look unrelated.
The X authorisation model is easy to get wrong, and exposing an X server to the network without authentication gives anyone full control of the display and its keyboard. Leaked Xvfb processes and stale lock files
(`/tmp/.X99-lock`) accumulate on shared runners. Screenshot and input automation under Wayland is deliberately restricted, so scripts that worked under X need rewriting with portals or compositor-specific tools.

## Applications beyond this domain

The principle of a headless rendering target is general. Browsers run in headless mode for tests and PDF generation (Chromium and Firefox have flags for it, and often use the same virtual display
mechanisms underneath), mobile emulators render to virtual screens in continuous integration, game engines have dedicated servers with no rendering, and video encoders in the cloud use virtual displays to
capture applications. Remote desktop and VDI products stream a virtual display to a client, and cloud gaming does the same with GPU frames. Accessibility testing uses the same semantic tree that screen
readers use. Software-rendered graphics (llvmpipe, SwiftShader) are also used in sandboxes where GPU access is forbidden. Even document conversion pipelines (LibreOffice headless) rely on the idea that a GUI
program can be run as a service with no screen.

## Examples

A first example is the lab program: a window created with Xlib, mapped with a red background, run under `xvfb-run`, and captured with `import`. The pixel at (10,10) is red and a pixel outside the
200 by 100 window is not, which proves that the window was actually drawn on the virtual display. The only parts specific to the toolkit are the calls; the surrounding fixture would be the same for GTK or Qt.

A second example is a GTK application test in continuous integration: the job installs `xvfb`, `dbus-x11` and fonts, then runs `xvfb-run -a dbus-run-session -- meson test -C build`. A failing example is the
first run, in which the tests abort with "cannot open display" because the job called the test binary directly; the wrapper provides `DISPLAY`. A third example is a Qt test with `QT_QPA_PLATFORM=offscreen`, in which a widget is
created, a button click is simulated with `QTest::mouseClick`, and a `QSignalSpy` verifies that the signal fired, with no X server at all.

Another failing example shows the security model: a script that tries to capture the screen with `import -window root` under a Wayland session gets a black image or an error, because the
compositor does not let arbitrary clients read other clients' buffers. The fix is to use the screenshot portal, or the compositor's own screenshot tool, or to run the test under a headless compositor and capture
through its protocol. A fourth is a leaked server: a CI job is cancelled and leaves `Xvfb :99` running with a lock file, and the next job fails to start a server on the same number; `xvfb-run -a`, which picks a free number, avoids it.

## Related problems and ideas

The toolchain topics apply unchanged: the dynamic linker finds GTK or Qt libraries by the rules of LNX-220-T03, and `pkg-config` provides compile flags for them (`pkg-config --cflags --libs gtk4`). Build
and test targets for GUI code are registered through LNX-220-T02, sanitizers and fuzzers (LNX-220-T05, LNX-220-T06) work on GUI programs although event loops need harnesses for entry points such as file
loaders, and profiling (LNX-220-T11) works through `perf` with the rendering threads visible in the flame graph. The session bus and XDG directories that toolkits need are explained in LNX-220-T09, and
packaging of desktop files and sandbox permissions is in LNX-220-T10. Language bindings (LNX-220-T07), such as PyGObject, PySide and gtk-rs, share the same display variables.

Alternatives include web-based interfaces for tools that need no native look, the command line or an API for automation, terminal user interfaces (ncurses, `ratatui`), and cross-platform frameworks such as Electron or Flutter
that bring their own rendering. Non-mainstream approaches include display servers streamed over the network at the protocol level (Wayland's `waypipe`, RDP via `xrdp`, and Broadway, the GTK back end that renders into a
browser).

## Active research

Work in this area is about making Wayland automation practical: the RemoteDesktop and ScreenCast portals, the libei and EIS input-emulation protocols, and test-oriented compositors. Accessibility standards are being
re-based on D-Bus-free or Wayland-friendly mechanisms. Toolkits have moved to GPU-based scene-graph renderers (GTK 4's GSK, Qt Quick's RHI) that need Vulkan or OpenGL, so software fallbacks and virtual GPU
drivers (virgl, venus) are being improved for virtual machines. Visual regression testing and perceptual image comparison are active topics in testing research, as is automated GUI exploration with
model-based and machine-learning agents.

## Future direction

Expect Wayland to be the primary session for desktop distributions, with X11 kept for legacy clients through XWayland, and headless testing to move toward compositor-based fixtures, so Xvfb will gradually become a compatibility tool. Qt and
GTK will keep offering offscreen or headless back ends for tests. For the learner at this introductory level the lasting skills are small: know which environment variable names the display, be able to start a virtual one, capture and inspect
its output, supply a session bus and runtime directory, and recognise that automation rights are narrower under Wayland.
