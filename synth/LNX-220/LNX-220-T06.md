# Unit tests, coverage and fuzzing

## Define the problem

Software changes constantly, and each change can break something that used to work. The only affordable defence is to
run checks automatically and often. For native code the checks fall into three layers that answer three different
questions. Unit tests ask whether the code does what the author expected on inputs the author thought of. Coverage
measurement asks how much of the code those tests actually exercised, which shows what remains unchecked. Fuzzing asks what
happens on inputs nobody thought of, by generating enormous numbers of them and watching for crashes, hangs and sanitizer
reports. The first protects against regressions, the second against false confidence, and the third against the
hostile or merely strange inputs that real programs eventually receive.

Programs that read files, packets, command-line arguments or messages from other processes have a particularly
broad input space, and parsers written in C are a classic source of security faults. The gap this topic fills is a working
practice for such code: how to structure it so it is testable, how to build, run and read coverage, and how to write a
fuzz harness, run it with libFuzzer or AFL++, keep a corpus and turn a crash into a regression test. Debugging the crash
(LNX-220-T04), instrumenting the build with sanitizers (LNX-220-T05) and wiring the targets into a build system
(LNX-220-T02) are separate topics that this one depends on.

## History and approaches

Automated testing for C began with assertions and hand-written driver programs that printed "ok". Frameworks arrived as the
practice matured: the xUnit family (originally Smalltalk, then JUnit) led to C and C++ frameworks such as CUnit, Check, Unity
(for embedded targets), Google Test, Catch2 and, in the GNOME and systemd worlds, GLib's test framework and Meson's `test()`
integration. Linux's own practice is instructive: the kernel gained kselftest for running user-space tests against a kernel
and KUnit for unit tests inside it, and the kernel documentation explains the reasons for in-kernel unit tests: fast
feedback, isolation and the ability to test code that has no user-visible interface [src: kernel-docs 830bbf8868ff2391]. The Test Anything Protocol
(TAP) gave tools a common line-based result format that Perl, `prove` and many harnesses understand.

Coverage measurement began with the `gcov` tool, which GCC supports through `--coverage` (equivalent to
`-fprofile-arcs -ftest-coverage` at compile time and `-lgcov` at link time). Compiling produces `.gcno` notes about the
control-flow graph, and running the program writes `.gcda` counters; `gcov` merges both into annotated source with a
count per line. The GCC manual describes the options, and the QEMU project documents using gcov in its test setup
[src: qemu-docs 4091ee6ccdc4ea30]. Front ends such as `lcov` and `gcovr` produce HTML or Cobertura XML for continuous
integration, and LLVM offers source-based coverage (`-fprofile-instr-generate -fcoverage-mapping`, reported by
`llvm-cov`), which tracks regions and branches more precisely. For decades coverage was argued about as a goal; the settled
view is that low coverage reliably indicates untested code, while high coverage proves little by itself.

Fuzzing began as a random-input experiment. In 1988 Barton Miller's class at Wisconsin piped random bytes into Unix
utilities and found that a surprising fraction crashed; repeated studies in 1990, 1995 and later showed the effect persisted.
Pure random input, however, rarely gets past a parser's first check. Dumb mutation fuzzers flipped bytes in valid
samples. The next step was feedback: Michał Zalewski's American Fuzzy Lop (AFL, 2013) instrumented the program to
record which edges of the control-flow graph each input visited and kept the inputs that found new edges, steering the mutation
towards depth. Within a year it had found bugs in nearly every widely used parser. LLVM's libFuzzer (2015) took the same
idea in-process: the fuzz target is a function that is called millions of times per second in one process, with coverage
guidance from SanitizerCoverage, avoiding the cost of starting a process per input. Honggfuzz, and later AFL++ (a community
continuation of AFL with better scheduling, custom mutators and many instrumentation modes) built on the same pattern.
Google's OSS-Fuzz (2016) runs fuzzers continuously for hundreds of open-source projects and reports bugs to maintainers,
and has found tens of thousands of defects. The Rust ecosystem adopted `cargo fuzz` and Go built fuzzing into `go test` in 1.18.
Meanwhile, kernel fuzzing took its own path with syzkaller, which generates system-call programs, and the KCOV facility that
exports coverage from the kernel to user space [src: kernel-docs a0c85328e8ebe2ac]. Virtual machine monitors such as Cloud Hypervisor and
Firecracker document fuzz targets for their device emulation, an example of fuzzing applied to security boundaries
[src: cloud-hypervisor-docs 93f4f0bdbd4b653a].

The lessons are that unit tests need to be fast and deterministic so they run on every change, that coverage is
a map rather than a score, and that coverage-guided feedback turned fuzzing from a stunt into a routine, near-automatic technique.

## Current state

A unit-test setup for a C project has a few standard pieces: a library of the code under test separate from `main()`, a test
program that links it, and a registered test command. The test program uses assertions or a framework and exits non-zero on
failure. Meson registers it with `test('name', exe)` and runs `meson test`; CMake uses `enable_testing()` and
`add_test()` with `ctest`; make uses a `check` target. Design for testability means keeping pure logic apart from I/O,
passing dependencies as arguments, and exposing parsers that take a buffer and a length rather than a file descriptor.
Run the tests under the sanitizers of LNX-220-T05 in at least one configuration.

For coverage, build a separate configuration with `--coverage -O0`, run the tests, and call `gcov` (or `gcovr`, `lcov`) in
the build tree. Lines that never ran are marked with a hash sign, and branch information is available with `-b`. The
result is useful in two ways: it points to the untested error paths, and as a gate it prevents coverage from silently
dropping. A meaningful target is to cover the error returns and boundary conditions rather than to chase 100%.
Optimised builds distort line mapping, so coverage is measured at `-O0`. When many processes write the same `.gcda`
files, `GCOV_PREFIX` and merging options keep them separate.

A fuzz harness is a function with a fixed signature, `int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size)`, that
feeds the input into the code under test and returns zero. It must be deterministic, avoid global state that grows,
must not call `exit()` for normal conditions, and should be fast. libFuzzer builds are made by compiling the target with
`-fsanitize=fuzzer` (which adds coverage instrumentation and links the driver), usually with `address,undefined`:
`clang -g -O1 -fsanitize=fuzzer,address,undefined fuzz.c parse.c -o fuzz`. Running `./fuzz corpus/` explores, writes new
interesting inputs into the corpus, and on a crash writes a `crash-<hash>` file. Useful options include `-max_len`, `-timeout`,
`-jobs`/`-workers` for parallelism, `-dict` for a token dictionary, `-runs=0` to replay a corpus as a regression test,
and `-merge=1` to minimise a corpus. The same harness works with AFL++ by compiling with `afl-clang-fast`, which provides
the driver, or by using AFL++'s libFuzzer-compatible mode. AFL++ runs as an external process: `afl-fuzz -i seeds -o out -- ./target`
with a persistent mode to avoid fork costs, a parallel master and secondary workflow and its status screen. A project without
Clang can use a standalone driver that replays files and generates random inputs, which is what the lab uses.

The generalised pattern for fuzzing is a loop: pick an input from the corpus, mutate it, run it under instrumentation,
keep it if it reached new coverage, record it if it crashed. The corpus is an asset: seeds of valid files give a head start, a
dictionary of keywords helps with text formats, and structure-aware mutators or grammar-based generation help with strongly
structured inputs. Crashes should be deduplicated by stack trace, minimised with `-minimize_crash=1` or `afl-tmin`,
reproduced under GDB (LNX-220-T04), fixed, and added to the repository as a permanent regression test file that the unit
tests replay.

## Assessment: the good, the bad and the ugly

The good side is that this stack is cheap, automatable and effective. Unit tests with sanitizers give rapid feedback;
coverage gives an objective map; a few hours of fuzzing reliably finds crashes in a new parser; and continuous fuzzing
(OSS-Fuzz, or a nightly job) keeps finding regressions. The three layers complement one another: tests supply seeds for
the fuzzer, fuzzer crashes become tests, coverage shows whether fuzzing reached the code of interest.

The bad side is that all three depend on judgement. Tests that mirror the implementation prove nothing, and tests with
timing or ordering dependence become flaky and are ignored. Coverage measures execution, not verification; a line can run without any assertion on its result.
Fuzzing struggles with checksums, cryptographic signatures and compressed or encrypted inputs, where blind mutation
almost always fails the first check; a harness must bypass or recompute the checksum. State-heavy code (network
protocols, file systems) needs a harness that drives sequences, not a single buffer. Fuzzers also find only what a
detector notices: without sanitizers, a heap overflow that does not crash passes silently.

The ugly side includes harnesses that cause side effects (writing files, opening sockets), slow harnesses whose throughput is a few
executions per second, memory leaks that make the fuzzer run out of memory, and "fuzz blockers" such as huge allocations, which
produce out-of-memory reports that are not bugs. Teams may add fuzz targets that are never run, or ignore crashes
because reproducing needs a large input; with no regression test the bug returns. Coverage gating can encourage
meaningless tests written to reach a number. Finally, an exhaustive fuzzing campaign proves nothing about absence of
bugs, though many managers take it as a certificate.

## Applications beyond this domain

Unit testing, coverage and fuzzing apply to every language. Python uses `pytest` and `coverage.py` and has Atheris
for fuzzing; Rust uses `cargo test`, `cargo llvm-cov` and `cargo fuzz`; Go has `go test -cover` and native fuzzing. Property-based
testing, as in QuickCheck and Hypothesis, is the same concept as fuzzing with a typed generator and a stated invariant.
Differential testing compares two implementations on the same inputs, which is how compilers, regular-expression
engines and JSON parsers are cross-checked. The concept of feedback-driven generation underlies smart-contract fuzzers
and protocol fuzzers, and compilers are fuzzed by program generators such as Csmith. The kernel's selftests, KUnit,
KCOV and syzkaller give the same layers inside the kernel. In hardware design, coverage-driven verification is the
standard approach. Security teams reuse corpora and fuzz harnesses to triage vulnerabilities and to qualify patches.

## Examples

A small `key=value;` parser illustrates the cycle. Unit tests check a pair, two pairs, the maximum count and the
malformed cases, and `gcov` shows that the "value too long" branch is never executed, which reveals that the code has no such
branch at all. A harness of six lines calls the parser with a small output array. With address and undefined-behaviour
sanitizers on, a few seconds of fuzzing finds a long value overflowing a 16-byte field. The reproducer is saved, the
parser is fixed to reject long values, and the file is added to the test suite. That is the exercise in the lab for this topic.

A larger example is a project that reads image files: it collects a few dozen small valid files as the corpus, writes a
harness that decodes each input and discards the pixels, builds with libFuzzer and ASan, and runs `-fork=8` overnight in
continuous integration. In the morning there is a crash with a heap overflow in the palette handling, plus a timeout
from a pathological dimension header. A failing example is a harness for a signed-message parser that never gets beyond the
signature check: coverage shows only the first function being reached, and the fix is a build option that skips signature
verification in fuzzing builds, a standard technique that the project must guard so it is never enabled in production.

Another failing case is flaky tests: a test that sleeps for 100 ms and then checks a counter fails once in a hundred runs,
and the team learns to retry the pipeline. The cure is to replace sleeps with explicit synchronisation or fake clocks. The best
practice is to treat a flaky test as a bug reported against the test.

## Related problems and ideas

This topic builds on the compile and link options of LNX-220-T01 and the build integration of LNX-220-T02; both
`--coverage` and `-fsanitize=fuzzer` are flags that must reach every file of the target. LNX-220-T05 covers the
sanitizers that give fuzzing its detection power, and LNX-220-T04 covers reproducing and diagnosing the crashes. Language
toolchains (LNX-220-T07) have their own built-in test and fuzz commands, and packaging (LNX-220-T10) runs the tests during
the build (`%check` in RPM, `dh_auto_test` in Debian) so that a package cannot be produced if tests fail. Profiling
(LNX-220-T11) shares one idea with coverage, instrumented counters, but answers a performance question.

Alternatives and extensions include mutation testing (deliberately altering the code to see whether tests notice),
symbolic and concolic execution (KLEE, SymCC) that solve path constraints, grammar-based and structure-aware fuzzing,
snapshot fuzzing of whole virtual machines, and formal verification for the highest assurance. Hardware-assisted
tracing allows coverage of closed-source binaries (AFL++ QEMU mode and Frida mode). These approaches are complementary
rather than opposed, with cost and learning curve rising as one moves toward them.

## Active research

Fuzzing research is among the most active fields in software security. Topics include better scheduling of seeds and
mutation operators (power schedules), machine-learning-guided mutation, directed greybox fuzzing that aims at a given code
location such as a patch, hybrid fuzzing that calls a solver when the fuzzer is stuck, and fuzzing stateful systems such as network
servers and file systems. Evaluation methodology is a concern: the community has published papers on how to compare fuzzers
reliably, with repeated trials and fixed time budgets. Large language models are being used to write harnesses and seeds
automatically, and OSS-Fuzz has reported experiments with generated targets (to verify the current results and scope). On the testing
side, research examines test flakiness, test-suite minimisation and selection, and automatic oracle generation.

## Future direction

Expect fuzzing to become a standard step in continuous integration for anything that parses input, with harnesses written
alongside code, and with continuous services running them over long periods. Build systems will provide first-class fuzz and
coverage configurations. AFL++ and libFuzzer will continue to share the harness interface, and more languages will
offer built-in fuzzing. For the learner, the lasting habits are: separate parsing from I/O, write the unit tests first and
read the coverage map for gaps, write one fuzz harness per input format, run it under sanitizers, and convert every
crash into a permanent regression test.
