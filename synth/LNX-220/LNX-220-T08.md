# systemd integration: sd_notify, socket activation and journald

## Define the problem

A long-running program on a Linux host is rarely started by hand. It is started at boot, restarted after failure, ordered
after the things it needs, limited in resources and watched. Doing that well requires a conversation between the program
and whatever starts it. The manager must know when the program is really ready, because "the process exists" is not the same
as "it accepts requests". It must hand over resources the program needs at start-up, in particular listening sockets, in a
way that lets the program be restarted without dropping connections. And the program's messages must land in a place where
operators can find them, with a severity, a source and a time attached.

For several decades the answer was the classic daemon: fork twice, detach from the terminal, write a pid file, redirect or
close the standard descriptors, open its own log file or call `syslog`. Each step existed to work around the absence of a
supervisor. The gap this topic fills is how to write a service that cooperates with a modern init system instead. The scope is the
interfaces of systemd that a program author uses: readiness and status notification (`sd_notify`), receiving sockets from
the manager (socket activation), logging to the journal, and the unit-file options that tell the manager how to treat the
program. Writing and operating units from an administrator's viewpoint belongs to the system administration courses;
here the viewpoint is the application developer's.

## History and approaches

Early Unix init ran a shell script per service, and `inetd` (1986) introduced a notable idea: one super-server listens on
many ports and starts the right program when a connection arrives, passing the connection as standard input and output.
This saved memory when machines were small, and it implemented what is now called socket activation, but it started a new
process for every connection, which was slow for busy servers, and the later `xinetd` added access control. The model of
a supervisor that also owns the sockets was set aside until systemd revived it.

SysV init scripts handled boot ordering with numbered links and, later, dependency headers. They started services strictly
in sequence or relied on shell backgrounding, and a script could not know whether a daemon was ready: the convention
was that the daemon double-forks and the parent exit signals success, which says only that it got far enough to fork.
Supervisors such as `daemontools`, `runit`, `s6` and `supervisord` took a different route and ran daemons in the foreground,
restarting them on exit, which removed the daemonisation code and the pid files. Upstart (2006) added event-based starts.

Lennart Poettering and Kay Sievers started systemd in 2010 with several ideas at once. Services are started in parallel,
driven by dependencies. Sockets, and also D-Bus names, paths and timers, can trigger services on demand, in the manner of
`inetd` but passing the listening socket itself so that one process serves many connections. Control groups track every
process of a service. Notification gives the manager an exact readiness signal. The manager also collects the output of
services. The `daemon(7)` manual page records the contrast: it lists the many steps a traditional daemon performs and the
reduced set that a new-style daemon needs [src: man-pages 02d282ea3104ced1]. The reaction was mixed: administrators criticised the breadth of the
project and its departures from Unix conventions, and several distributions split over it, but within about five years
nearly all mainstream distributions had adopted it. Other init systems (OpenRC, runit, s6) remain in use, so portable
programs keep the traditional options.

The journal was the next piece. `syslog` offered a text message with a facility and priority and no structure; log rotation and
filtering were added by other tools; and the connection between a message and the service that issued it was by
convention only. The journal (`systemd-journald`) stores entries as sets of fields, among them `MESSAGE`, `PRIORITY`,
`_SYSTEMD_UNIT`, `_PID` and any additional field the program supplies, and it collects the standard output and error
of services as well as messages from `syslog` calls and its native protocol [src: man-pages c662f69f8b0c34e6].
Reading is done with `journalctl`, which can filter by any field [src: man-pages dfef590a9ad9be3e]. The result is that an
application can log by writing lines to standard error and still be filtered by unit and severity.

The lesson from this history is that supervision is better than self-daemonisation: foreground processes, explicit readiness,
sockets owned by the manager and logs captured from standard streams make programs simpler and the system more
observable. The pattern that emerged is the "new-style daemon", in which the program does one job and the manager does the
lifecycle work.

## Current state

A new-style service runs in the foreground, does not fork into the background, does not write a pid file, and logs to
standard error or to the journal. It declares its behaviour to the manager with `Type=` in its unit file. `simple` means the
service is considered started as soon as the process is forked. `exec` waits until the program has been executed. `forking`
is for the legacy daemon style. `oneshot` is for commands that run to completion. `notify` makes the manager wait until
the service sends the readiness message, and `notify-reload` also lets it report a configuration reload. The
`systemd.service` manual page describes these types and their options [src: man-pages 96ae521c06b6db50].

Readiness works through the `sd_notify` protocol. The manager creates a datagram socket and passes its path in the environment
variable `NOTIFY_SOCKET`. The service sends text datagrams of `KEY=VALUE` lines to it. The commonly used keys are `READY=1`
(start-up finished), `RELOADING=1` and `STOPPING=1`, `STATUS=text` (shown in `systemctl status`), `MAINPID=` (for services
that fork a different main process), `WATCHDOG=1` (the heartbeat when `WatchdogSec=` is set), `ERRNO=` and `FDSTORE=1` (store
a file descriptor in the manager). `NotifyAccess=` controls which processes of the service may send. The C library
`libsystemd` offers `sd_notify()` and `sd_notifyf()`, but the protocol is simple enough that it is implemented by hand in
shell with `systemd-notify`, in Python, Go and Rust [src: man-pages 97755d491fbdf47c]. Programs run outside systemd see no variable
and the calls are no-ops, so the same binary works everywhere.

Socket activation uses a `.socket` unit that has `ListenStream=`, `ListenDatagram=`, `ListenFIFO=` or similar options. The manager
opens and binds the socket and starts the matching service when traffic arrives, then passes the descriptors through the
environment: the variable `LISTEN_FDS` holds the count, `LISTEN_PID` the pid that the descriptors are intended for, and
`LISTEN_FDNAMES` the names (from `FileDescriptorName=`). The first descriptor is number 3. A careful service checks that
`LISTEN_PID` equals its own pid before trusting the variables, because a child process or an exec of a different program
would otherwise inherit them. `sd_listen_fds()` does this and optionally clears the variables. With `Accept=no` (the usual
setting) the service receives the listening socket and accepts connections itself; with `Accept=yes` the manager accepts and
starts a service instance per connection, like `inetd`. The tool `systemd-socket-activate` lets a developer test a program
from the command line, without installing units [src: man-pages 61682bbae33b5d68].

The benefits are several. Services start on demand and, by contrast, can start early because the sockets exist before the
service. Restarting or upgrading a service loses no connections because the kernel queues them on the manager-owned socket.
Dependencies between services on sockets disappear, since clients connect before the server is up. Privilege separation
improves: the manager can bind a privileged port or a socket with particular permissions and the service need not run as root.

Logging has three paths. Writing to standard output or standard error is captured by default (`StandardOutput=journal`). Prefixing a
line with `<N>` where N is a syslog level, for example `<3>` for errors and `<6>` for information, sets the priority, as defined
by the `sd-daemon` conventions. Programs that want structured fields call `sd_journal_send()` with `KEY=value` strings, or write
the native protocol to `/run/systemd/journal/socket`. Operators then run `journalctl -u name -p err -b`, `journalctl -o json`, or
`journalctl FIELD=value`. Rate limiting (`LogRateLimitIntervalSec=`), per-service namespaces and size limits in
`journald.conf` protect the system. The tool `systemd-cat` pipes arbitrary command output into the journal.

Finally there are the unit options that make a program a good citizen: `Restart=on-failure` with `RestartSec=`, `User=` or
`DynamicUser=`, hardening such as `ProtectSystem=`, `PrivateTmp=`, `NoNewPrivileges=` and `CapabilityBoundingSet=`, resource
limits (`MemoryMax=`, `TasksMax=`), `StateDirectory=`, `RuntimeDirectory=` and `ConfigurationDirectory=` that create and own
directories with correct permissions, and `LimitCORE=` for crash dumps (LNX-220-T04). The command `systemd-analyze security name`
scores a unit's exposure. The generalised pattern is a contract: the program states readiness, accepts resources from its
parent and logs to standard streams, and the manager does everything else.

## Assessment: the good, the bad and the ugly

The good side is how much code disappears. A service that follows the contract does not daemonise, does not manage pid
files, does not rotate logs and can be restarted without an outage. Readiness notification removes sleep-based start-up
races between dependent services. The journal gives uniform, structured, filterable logs with trusted metadata
(the sender's unit and pid are recorded by the system, not claimed by the sender). Socket activation makes on-demand
services practical, and the hardening directives provide a sandbox for a few lines of configuration.

The bad side is portability and complexity. The mechanisms are specific to systemd, so programs aimed at other init systems or
at BSD need alternative paths; the usual solution is to implement the small protocols directly and make them optional.
Debugging a unit that fails to start requires knowing the manager's states, `systemctl status`, `journalctl -xe` and
`systemd-analyze verify`. Journal files are binary, so a damaged disk or a missing tool is a problem, and
queries on very large journals can be slow. The size of the documentation and the option set is itself an obstacle.

The ugly side includes the details that cause real outages. `Type=notify` with a program that never sends `READY=1` waits
until `TimeoutStartSec=` and is killed. A forgotten `NotifyAccess=` hides notifications sent by a child process. A service that
forks and loses `LISTEN_PID` matching ignores its sockets. Passing descriptors with `exec` in a wrapper script breaks the
pid match, so the shell must `exec` the program. Inherited descriptors that are not close-on-exec leak into children.
Programs that log multi-line messages end up with a journal entry per line, and unrestricted logging can flood the
rate limit and drop real messages. Containers complicate matters because a unit inside a container needs access to the
host's journal or its own manager.

## Applications beyond this domain

The idea of a supervisor that owns resources and hands them over appears in other places. Launchd on macOS has
socket activation with a similar environment-passing protocol, and Kubernetes liveness and readiness probes serve the same
goal of reporting when a process is ready, using HTTP checks instead of datagrams. Zero-downtime upgrades of web servers use
the same trick of inheriting listening descriptors (nginx binary upgrade, Envoy hot restart, Einhorn). Container
orchestration and systemd's `systemd-nspawn` and `portablectl` use the same unit semantics. Structured logging pipelines in cloud
environments (JSON lines with fields, collected from standard streams) follow the journal's model, and the Twelve-Factor
principle of treating logs as an event stream is the same idea as logging to standard error.

## Examples

A first example is a small TCP service that is both activated and notifying. The `.socket` unit has `ListenStream=/run/app.sock`.
The program starts, checks that `LISTEN_PID` matches its pid and that `LISTEN_FDS` is 1, builds a server object from descriptor 3, sends
`STATUS=waiting` and `READY=1`, and serves. A unit with `Type=notify`, `NotifyAccess=main` and `Requires=app.socket` completes the
setup. The lab for this topic has you write this program in Python using only the protocol and a grader that plays the
manager, and it checks that the program refuses a foreign `LISTEN_PID`.

A second example is a reload. With `Type=notify-reload` and `ExecReload=` unset, `systemctl reload` sends `SIGHUP` and the program
sends `RELOADING=1` with a monotonic timestamp, rereads its configuration, and then `READY=1`; units that depend on it
wait for completion.

A failing example: a service is configured with `Type=notify` but written with a library that was compiled without
systemd support. `systemctl start` hangs for 90 seconds and then reports a timeout, and the journal shows the process running
fine. The fix is to use `Type=simple` or to add the notification. A second failing example is a service that logs
`Error: ...` on stderr and then cannot be filtered by priority, because every line is priority 6. Adding `<3>` prefixes, or using
`sd_journal_print(LOG_ERR, ...)`, fixes it, as the severity then appears in `journalctl -p err`.

## Related problems and ideas

The debugging of services (LNX-220-T04) depends on getting cores through `systemd-coredump` and on `LimitCORE=`. Packaging
(LNX-220-T10) installs unit files with macros in RPM (`%systemd_post`) and helpers in Debian (`dh_installsystemd`), which is how a
unit gets enabled and restarted on upgrade. The D-Bus services of LNX-220-T09 are another activation path: a bus name can start
a service on demand, and `Type=dbus` waits for a name to appear. Profiling a running service (LNX-220-T11) uses the same cgroup
that systemd creates, so `perf record -a --cgroup` can scope a measurement to one unit. Sanitizers (LNX-220-T05) need their
options in `Environment=`.

Alternatives include writing a classic daemon for portability, using a different supervisor (`runit`, `s6`) that has its own readiness
file-descriptor protocol, and running services as containers managed by Podman Quadlet or Kubernetes. Quadlet turns a
`.container` file into a unit, merging the two approaches. User services (`systemctl --user`) run the same model for a login session.

## Active research

Work on the systemd interfaces themselves includes the extension of the notify protocol (for example to pass file
descriptors and to carry more precise reload semantics), the Varlink interfaces that replace D-Bus for some system services,
and the structured logging "fields" of the journal for use in observability pipelines. There is also active work on
confining services further with new sandboxing options and on the interaction with cgroup v2, memory pressure
notifications (PSI) and the `systemd-oomd` service. Observability research looks at turning journal data into
metrics and traces cheaply with OpenTelemetry bridges (to verify the maturity of the available exporters).

## Future direction

Expect further growth in sandboxing options that applications are expected to adopt by default, wider use of
credentials and encrypted per-service secrets, and a gradual move of system interfaces from D-Bus to Varlink. Portable
libraries in other languages will keep implementing the protocols so that Rust and Go services get readiness and socket
activation without C. For the working developer, the plan is to write for the foreground, report readiness only when ready,
accept sockets from the manager, log to standard error with priorities, and test with `systemd-socket-activate` and
`systemd-analyze` before a release.
