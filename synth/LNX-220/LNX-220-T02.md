# Build systems: make, CMake and Meson

## Define the problem

A program of any size consists of many source files, generated files, libraries and options, and the question "what must be
rebuilt now?" has to be answered correctly every time a file changes. Rebuilding everything is correct but wastes minutes
or hours; rebuilding too little produces a binary that mixes old and new code, which is the worst failure because it is
silent. A build system holds the description of how outputs depend on inputs and executes the smallest set of commands
that brings every output up to date. On top of that core job it must also cope with variation between machines (compiler
names, library locations, optional features), with out-of-tree builds, with installation into a prefix or a staging
directory, with cross-compilation, and with running tests.

The gap this topic fills is practical fluency: reading and writing a Makefile that tracks header dependencies, knowing why
projects generate Makefiles or Ninja files with CMake or Meson instead of writing them, and being able to diagnose a build
that is wrong, slow or not reproducible. The scope is the three tools that account for most native Linux projects. Compiler
and linker behaviour is the subject of LNX-220-T01, and the installed library layout is the subject of LNX-220-T03; this
topic concerns the layer that decides which commands run and with which options.

## History and approaches

`make` was written by Stuart Feldman at Bell Labs in 1976 after he watched colleagues waste time on stale binaries. Its
model, a graph of targets with prerequisites and recipes, driven by file modification times, has barely changed. It
covered the core problem well and left several parts open: it has no knowledge of C headers, so projects listed
dependencies by hand and got them wrong; it has no notion of configuration; and its recipes are shell strings with
tab-indented syntax and a macro language that grew by accumulation. Variants responded in different directions: GNU make
added pattern rules, functions and parallel execution (`-j`), BSD make took a different include model, and Plan 9's `mk`
tried to tidy the syntax.

The portability problem was attacked by the GNU Autotools in the early 1990s. Autoconf generates a `configure` script
that probes for compilers, headers and functions, and Automake generates Makefile templates from a short description. The
result is the famous `./configure && make && make install` sequence that let one source tree build on dozens of Unix
variants. Its costs were slow configuration, a macro layer that few people mastered and generated files that hid the logic.
Bootlin's training notes on Autoconf, Automake and `pkg-config` show how much structure a developer must learn to use it
properly [src: bootlin-training e5d7af26725efb71].

Two generations of alternatives followed. Recursive make, where each directory has a Makefile that invokes the others, was
shown to be unreliable in Peter Miller's 1997 paper "Recursive Make Considered Harmful" because no single invocation sees
the entire dependency graph; non-recursive layouts and tools that read the entire graph followed. SCons, Waf and others
described builds in a general-purpose language, which gave power but often slow startup and unfamiliar idioms.
CMake, developed at Kitware from 2000 for the Insight Toolkit, took a different approach: a declarative description of
targets in `CMakeLists.txt` that is translated to native build files (Makefiles, Ninja, Visual Studio projects). Ninja,
written by Evan Martin at Google for Chromium, is an intentionally minimal executor with fast start-up that is meant to
be generated rather than written by hand. Meson, started by Jussi Pakkanen in 2013, used a restricted non-Turing-complete
language and Ninja from the start, and GNOME, systemd and Mesa moved to it. Google's Bazel and Meta's Buck chose
hermetic, content-addressed builds that give correctness and remote caching at the cost of adopting their whole model.

The lessons are consistent. Dependencies must be discovered automatically, not listed by humans. Generation and execution
should be separate steps, with a fast executor and a convenient frontend. Configuration should be cached and
inspectable. Builds should happen outside the source tree so that several configurations can coexist. Those lessons
define the common pattern: describe targets, configure into a build directory, execute with Ninja or make.

## Current state

GNU make evaluates a Makefile in two phases. In the first it reads all rules and variables and builds the dependency graph;
in the second it walks the graph, compares modification times and runs recipes for targets that are out of date. A rule has
the shape `target: prerequisites` followed by tab-indented commands. Variables hold flags (`CC`, `CFLAGS`, `CPPFLAGS`,
`LDFLAGS`, `LDLIBS`), and automatic variables name the parts of a rule: `$@` is the target, `$<` the first prerequisite
and `$^` all of them. Pattern rules such as `%.o: %.c` describe a family of targets, and a target that is not a file, such as
`clean` or `test`, is declared with `.PHONY` so that a file of the same name cannot confuse make. The standard options
are `-j N` for parallel jobs, `-n` to print without running, `-k` to keep going after errors, `-C dir` to enter a
directory and `-B` to force a rebuild. POSIX specifies a subset, and the portable core is documented in the standard's
make page [src: man-pages 287bba00a1fd39da]. Red Hat's guide to creating C applications introduces make with a small
multi-file example [src: rhel-10-docs 98fd244a74499bba].

The essential technique for C is automatic header dependencies. The compiler can write a dependency file as a side
effect: `-MMD -MP` produces `foo.d` next to `foo.o`, listing every header the translation unit included and, with `-MP`,
adding empty rules for the headers so that deleting one does not break the build. The Makefile then ends with
`-include $(OBJ:.o=.d)`. With that pattern a changed header rebuilds exactly the objects that included it. A second
essential practice is order-only prerequisites (`| dir`) for creating output directories without touching timestamps, and
a third is honouring the conventional variables so packagers can override them: `PREFIX`, `DESTDIR`, `CFLAGS` from the
environment, and `install` rather than `cp` for copying with modes.

CMake works in a different shape. The developer writes `CMakeLists.txt` with `project()`, `add_executable()`,
`add_library()`, `target_include_directories()`, `target_link_libraries()` and `install()`. The modern style is
target-based: properties such as include paths and compile definitions are attached to a target with a visibility keyword
(`PRIVATE`, `PUBLIC`, `INTERFACE`), and they propagate to consumers through linking. Configuration is `cmake -S . -B build`,
building is `cmake --build build -j`, installing is `cmake --install build --prefix /usr/local` with `DESTDIR` honoured
for staging, and `ctest --test-dir build` runs tests registered with `add_test()`. The cache file `CMakeCache.txt` stores
variables such as `CMAKE_BUILD_TYPE` and `CMAKE_INSTALL_PREFIX`, and `-D` options set them. `find_package()` locates
dependencies through config files or find modules, and `pkg_check_modules()` bridges to `pkg-config`. `CMAKE_EXPORT_COMPILE_COMMANDS`
writes `compile_commands.json`, which editors and analysers (LNX-220-T05) use to learn the exact compile commands.
Toolchain files describe cross-compilation. Presets (`CMakePresets.json`) record agreed configurations.

Meson's description is `meson.build`, with a deliberately small language: `project()`, `executable()`,
`shared_library()`, `dependency('name')` (which uses `pkg-config` or CMake behind the scenes), `install_headers()`,
`test()`, and option declarations in `meson.options`. The workflow is `meson setup build`, `meson compile -C build`,
`meson test -C build` and `meson install -C build`, with `DESTDIR` supported and `--prefix` set at setup. Meson refuses
in-tree builds by design, handles `b_sanitize`, `b_coverage` and `b_lto` as options, supports cross files, and
reads dependencies from "wrap" files for subprojects. For libraries it can write the `.pc` file itself through the
`pkgconfig` module, which links this topic directly to LNX-220-T03.

The generalised pattern is a pipeline: a human-written declarative description, a configure step that probes the host and
records choices in a cache, a generator that emits a low-level plan, and an executor that incrementally runs the plan.
Tests and installation are further targets of the same graph.

## Assessment: the good, the bad and the ugly

The good side is that incremental builds are cheap and, when dependencies are complete, correct. Make is everywhere, needs
no installation, and a short Makefile is a clear form of documentation for what a project does (`make test`, `make
install`). CMake is the de facto standard for C and C++ libraries, with first-class support in IDEs and package
managers. Meson is quick to read, and its restricted language makes build files easier to review. Ninja makes the
execution phase fast enough that the configure step becomes the visible cost. All three support out-of-tree builds,
parallelism and `DESTDIR` staging, which is what distributions need.

The bad side is that all three depend on correct declarations. A missing dependency produces a build that works on
a clean machine and breaks incrementally, or the reverse. Make's timestamp model fails when clocks skew or when a tool
rewrites a file with an old date; it also cannot notice that the compiler flags changed unless you make the flags a
dependency. CMake's language is unusual and historically inconsistent, with variables that behave as global state, and
old-style projects that set `CMAKE_C_FLAGS` globally compose badly. Meson's restrictions occasionally force
awkward workarounds for unusual generated files. Environment leaks remain a problem: `CFLAGS` in the environment
affects the first configure but is stored in the cache for later runs, which surprises people.

The ugly side includes recursive make in old projects, `configure` scripts that cache wrong answers, hand-written
`install` rules that ignore `DESTDIR`, and builds that download dependencies at build time and therefore cannot run in
the network-less build roots of package builders. Parallel builds expose missing ordering between rules, producing
failures that appear one time in twenty. A practical mitigation is to run `make -j` regularly in continuous
integration and to enable "warn on unused" and dependency tracing options where available, and to keep a clean-build
job beside the incremental one.

## Applications beyond this domain

The graph-and-timestamp idea appears wherever derived artefacts depend on sources. Static site generators, documentation
builders and data pipelines (DVC, Snakemake) use the same logic with files as nodes. Container image builders cache layers
by content, a cousin of Bazel's content-addressed approach. Continuous-integration systems run job graphs with
dependencies, and package builders such as `rpmbuild` and `dpkg-buildpackage` run a build system inside a controlled
environment. Language-specific tools (Cargo, Go, npm) are build systems with a package manager attached. Kernel
configuration (Kconfig) and the kernel's Kbuild are specialised Makefile frameworks that show how far make can be stretched
when a project is willing to invest in conventions [web: kernel.org].

## Examples

A minimal Makefile for two sources shows the whole technique. It sets `CPPFLAGS += -MMD -MP`, derives the object list from
`$(wildcard src/*.c)`, links with `$(CC) $(LDFLAGS) -o $@ $^`, compiles with a pattern rule that writes into an `obj/`
directory created by an order-only prerequisite, includes the `.d` files and declares `clean` phony. Changing a header
then rebuilds only the sources that include it, and `make -n` after a successful build prints nothing to run. The lab for
this topic asks you to write this Makefile and prove the header behaviour, then to write the equivalent
`CMakeLists.txt` with an install rule and check a staged `DESTDIR` install.

A CMake example is a library with a consumer: `add_library(vec SHARED src/vec.c)` followed by
`target_include_directories(vec PUBLIC include)` means any target that links `vec` automatically gets the include path.
For a staged build, `DESTDIR=$PWD/stage cmake --install build` places files under `stage/` while the compiled-in prefix
remains the configured one, which matches the behaviour you meet in LNX-104 for source installs.

A failing example is a build that always relinks. The cause is a phony or directory target listed as a prerequisite of
the program; make treats it as always out of date. Another is an object that never rebuilds after a header change
because the Makefile has no `-MMD`. The command `make -d` or `make --trace` shows the decisions, and `make -n -W file` asks
what would run if a file had changed. For Ninja, `ninja -d explain` prints why each step is considered dirty, and
`ninja -t graph` outputs the graph for inspection. In CMake, `cmake --build build --verbose` shows the full compile
commands, which is the quickest way to discover that a flag did not arrive.

## Related problems and ideas

Dependency discovery is shared with package management and with `pkg-config` (LNX-220-T03), and with the language
toolchains of LNX-220-T07, where Cargo and Go take over the whole graph. Testing, coverage and fuzzing (LNX-220-T06) are
built as extra targets with extra flags, typically through options such as `-DCMAKE_BUILD_TYPE=Debug` or Meson's
`-Db_sanitize=address`. Packaging (LNX-220-T10) wraps a staged install into RPM or DEB files, so a build that honours
`DESTDIR` is a prerequisite for a clean package. Compiler caches such as `ccache` and distributed builders such as
`distcc` accelerate repeated compilation without changing correctness rules.

Opposing views include hermetic build tools (Bazel, Buck2, Pants) that insist that every input be declared and that
actions run in a sandbox; their guarantees allow remote execution and caching, but adopting them means
rewriting build files and often vendoring dependencies. Nix and Guix take the same stance at package level. On the other
side, a "just a shell script" camp argues that small projects need only a short script. Experimental ideas include
build systems with "early cutoff" and "suspending" schedulers as described in the "Build Systems à la Carte" paper, which
classifies tools by their scheduler and rebuilder strategies.

## Active research

Research on build systems studies correctness (are declared dependencies complete?), incrementality (how little can be
rebuilt?) and cost (how to share caches safely between users). Tools that trace file accesses to find missing or excess
dependencies have shown that large real projects contain many undeclared dependencies. C++ modules change the
dependency picture: compiling a module interface produces an artefact that other files need first, so the build graph is
discovered dynamically; CMake and Ninja gained "dyndep" support for this, and uptake is still maturing (to verify
the current state per compiler). Remote caches and remote execution are making builds faster for teams, and
research into reproducibility asks how to make every action's output depend only on declared inputs.

## Future direction

CMake continues to raise its minimum policy versions, and recent releases add presets, file sets and better package
handling; Meson keeps expanding its module set and its Rust support. Projects such as the Linux distributions are moving
more packages from Autotools to Meson or CMake, and Ninja remains the common back end. Expect more builds to run in
sandboxes with no network access, making vendored or pinned dependencies the norm, and to see more `compile_commands.json`
consumers. The portable advice holds: keep the description declarative, keep dependencies automatic, honour `PREFIX`,
`DESTDIR` and the standard flag variables, and have continuous integration do a clean build.
