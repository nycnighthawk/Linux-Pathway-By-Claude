# C, Rust, Go and Python toolchains

## Define the problem

A Linux developer rarely writes in one language. System components are in C, newer infrastructure in Rust and Go, and glue,
tests and tooling in Python. Each language ships its own way of building, managing dependencies, testing and producing a
deliverable, and each meets the operating system at a different place. The practical questions are the same for all of
them. How do I get the compiler or interpreter and keep several versions side by side? How do dependencies get
declared, fetched, locked and verified? What does the build produce: a dynamically linked binary, a static one, a source
tree plus an interpreter? And how do these results fit into a Linux distribution's expectations for packaging,
security updates and reproducibility?

The gap this topic fills is a comparative view. A reader who knows the C toolchain from LNX-220-T01 can understand the
others by asking where each places the decisions that C leaves to the linker, the loader and the package manager. The
scope covers the four ecosystems most seen on Linux: the system C toolchain, Rust with `rustup` and Cargo, Go with its
single `go` command and module system, and Python with interpreters, virtual environments and packaging tools. It does not
cover each language's design, only the tools and the contract with the operating system.

## History and approaches

C's approach was minimalism: the language defines nothing about building or dependencies, so the operating system and
Unix tools filled the vacuum with `make`, libraries in standard directories, header search paths and later `pkg-config`
(LNX-220-T02, LNX-220-T03). Dependencies are the distribution's problem, and that arrangement worked well because one
set of libraries serves the whole system, and security updates arrive through the package manager. Its weakness is that
a project cannot say precisely which versions it wants, and building on a different distribution means discovering what
differs.

Scripting languages took a different path. Python began with interpreters installed system-wide, and libraries were put
into a shared `site-packages`, which led to conflicts between applications that needed different versions of one library.
`easy_install`, then `pip` (2008), added fetching from the Python Package Index; `virtualenv` (2007) introduced isolated
environments per project, which the standard library adopted as `venv` in Python 3.3 [src: python-docs 1829f6a13de30326].
Packaging passed through several formats (eggs, wheels, `setup.py`) before settling on `pyproject.toml` with pluggable
build back ends and standard metadata, which makes `pip install` and the build step independent of one tool. Modern
tools such as `uv`, `poetry` and `pipx` build on this foundation. Distributions then had to deal with the rule
that system tools use the system Python while projects use their own; recent standards (PEP 668) let distributions mark
the system environment as "externally managed" so `pip` refuses to install into it unless the user asks for another
location.

Go (released 2009) was designed by people tired of long C++ builds. It put everything in one tool: `go build`,
`go test`, `go fmt`, `go vet` and a module system that arrived in Go 1.11 (2018) to replace the early GOPATH layout. Modules
record versions in `go.mod` and hashes in `go.sum`, use "minimal version selection" to choose versions
deterministically, and are fetched through a proxy and a checksum database. Go builds statically linked executables by default
for pure Go programs, which made it a favourite for container images and command-line tools, and cross-compiling
requires only setting `GOOS` and `GOARCH`.

Rust (stable in 2015) put equal emphasis on safety and on tooling. `rustup` installs and switches toolchains and targets
(stable, beta and nightly channels), and Cargo handles building, dependencies from crates.io, tests, benchmarks,
documentation and publishing, with a `Cargo.lock` that pins the dependency graph for applications. The Rust Book explains the
concepts of packages, crates and workspaces [src: rust-book f5d1d294f12663f9] and the release channels with the
role of nightly builds [src: rust-book c79998a35efce339]. Rust links to the system C library by default and uses the system
linker, so its binaries carry `DT_NEEDED` entries for libc, while targets based on musl give fully static programs.

The lessons that the ecosystems arrived at independently are: lock files make builds repeatable; isolating
dependencies per project avoids conflicts; checksums and transparency logs guard against tampering; and a single driver
command lowers the cost of good practices such as running tests. The unresolved tension is between this approach, in
which every project carries its own pinned dependency tree, and the distribution model in which one maintainer updates a
shared library for everyone. Distributions package Go and Rust applications by vendoring dependencies or by splitting them
into per-crate packages, and the choice is controversial.

## Current state

The C toolchain is installed by the distribution (`gcc`, `make`, `binutils`, `libc6-dev` or `glibc-devel`), and Red Hat
supplies newer compilers in parallel through GCC Toolset packages and a container image so that application builds do
not disturb the base system [src: rhel-10-docs 56836a28262d53e2]. Cross-compilation uses a toolchain with a target prefix such as
`aarch64-linux-gnu-gcc` and a sysroot; Bootlin's training materials describe how such toolchains are built and
selected [src: bootlin-training 5232758a33e1b9c3].

For Rust, `rustup` installs into the home directory (`~/.cargo`, `~/.rustup`), so it needs no root. `rustup toolchain install`,
`rustup default`, `rustup target add x86_64-unknown-linux-musl` and a `rust-toolchain.toml` file in the project select the
compiler. `cargo build --release`, `cargo test`, `cargo clippy`, `cargo fmt` and `cargo doc` cover the daily tasks. The
`Cargo.toml` file lists dependencies with version requirements; `Cargo.lock` pins exact versions and is committed for
applications. Build scripts (`build.rs`) detect native libraries, using `pkg-config` through a crate, and the `-sys`
crates wrap C libraries. Static linking of the C runtime is selected with `-C target-feature=+crt-static`, or by building
for a musl target. Binaries are large by default because of debug information and monomorphised code; release profiles
with `strip`, `lto` and `opt-level` options reduce them. For offline or packaged builds, `cargo vendor` copies all
dependencies into the tree and `--locked` or `--frozen` refuse to touch the network.

For Go, installation is a tarball unpacked to `/usr/local/go` or a distribution package; versions in `go.mod` can trigger
automatic toolchain downloads since Go 1.21. Commands are `go mod init`, `go get`, `go build`, `go run`, `go test`, `go vet`,
`go install` and `go work` for multi-module workspaces. Environment variables control behaviour: `GOOS`, `GOARCH`,
`CGO_ENABLED`, `GOFLAGS`, `GOPROXY`. When cgo is enabled and the program uses a C library or the system resolver, the
result is dynamically linked against libc, and with `CGO_ENABLED=0` the binary is static and the Go resolver is used. The
race detector (`go test -race`) uses the same runtime as ThreadSanitizer, and `go build -trimpath -ldflags="-s -w"` produces
smaller and more reproducible binaries. `go vendor` and `-mod=vendor` give offline builds.

For Python on Linux, the first rule is to leave the system interpreter to the system. A project gets its own environment with
`python3 -m venv .venv`, which creates a directory with a `pyvenv.cfg`, a `bin/python` that points to the base interpreter, and an
empty `site-packages`. `pip install -r requirements.txt` or `pip install .` fills it, and `pip freeze` or a lock file
records versions. Packaging metadata lives in `pyproject.toml`; `python -m build` produces a source distribution and a wheel;
`pipx` installs command-line tools in isolated environments. Packages with C extensions compile against the interpreter's
headers (`python3-dev`) or are distributed as prebuilt wheels with a platform tag (`manylinux`) naming the oldest glibc
they support. Extensions are shared objects loaded with `dlopen`, so the library search rules of LNX-220-T03 apply to
them. A script can be made an application with a shebang line (`#!/usr/bin/env python3`), a zipapp, or a bundler such as PyInstaller.

The generalised pattern is a four-part contract. A toolchain manager chooses a version. A project file declares
dependencies and build settings. A lock file pins exact content. A build command produces either a native artefact (and the
question is how static it is) or a source artefact with an interpreter (and the question is which interpreter and
environment). Linux integration then asks how that artefact is installed, updated and supported: a service
(LNX-220-T08), a package (LNX-220-T10), or a container.

## Assessment: the good, the bad and the ugly

The good side is productivity and repeatability. Cargo and Go modules give new contributors a one-command build, lock
files make results repeatable, and the standard test commands make quality checks routine. Static binaries from Go or
musl-based Rust deploy as one file with no library dependencies, which suits containers and appliances. Python's virtual
environments end most version conflicts, and wheels remove the need for compilers on the target. The system C toolchain
remains the most widely understood, with the strongest tooling for debugging and profiling (LNX-220-T04, LNX-220-T11).

The bad side is the supply chain. Pinned dependency trees carry hundreds of transitive packages, each with its own
maintainers; a vulnerable library inside a statically linked Go or Rust binary is not fixed by the distribution's
library update, and the application must be rebuilt. Tools such as `cargo audit`, `govulncheck` and `pip-audit` read the
lock files to find affected programs, and software bills of materials make this inventory visible. Build-time
networks are also a risk: a build that fetches code during compilation cannot be reproduced and is blocked in many
packaging environments. Python's environment handling is the most fragmented, with several competing front ends, and
mixing `pip` into system directories can break the operating system's own tools.

The ugly side is the boundary between languages and the system. A statically linked Go program that needs name resolution may
behave differently from one using the system resolver and its `nsswitch.conf` configuration. Rust programs pull in glibc symbol
versions from the machine that built them. Python wheels built on a recent distribution fail to import on an older one, and
extension modules compiled against one Python minor version do not load in another. Cross-compiling C libraries for a
Rust or Go program needs a matching sysroot and linker, which is often the hardest part. And all of this needs disk: a full
Rust or Go toolchain with caches takes gigabytes in a continuous-integration worker.

## Applications beyond this domain

The same four-part contract appears in other ecosystems: Node's `package.json` with `package-lock.json`, Java's Maven or
Gradle with a repository and a lock, Ruby's Gemfile and bundler, PHP's Composer. Container images are a fifth kind of lock: a
digest pins the exact content, and a Containerfile (LNX-220-T10) is a build recipe. Nix and Guix generalise it to the
whole system. Mixed-language projects use build systems that call these tools: CMake can drive Cargo through helper
modules, Meson has native Rust support, and Bazel rules wrap them. The idea of toolchain selectors (`rustup`, `pyenv`,
`asdf`, `mise`, and `update-alternatives` for C compilers) also applies in operating systems when several versions of one
tool must coexist. In security and compliance work, the lock file and SBOM approach serves licence tracking and incident
response.

## Examples

A first example shows the linkage differences that matter for deployment. The same "hello" program is built four ways:
`cc` produces a dynamic executable with an interpreter segment and a `libc.so.6` entry; `cc -static` has neither;
`rustc` with `-C target-feature=+crt-static` yields a static PIE; and `CGO_ENABLED=0 go build` yields a static binary. `readelf -lW`
and `readelf -dW` verify each claim. The lab for this topic repeats this exercise and adds an isolated Python
environment, so that you can see the difference between "ships its runtime", "needs the system runtime" and "needs an interpreter".

A second example is a service that wraps a C library. A Python program uses `ctypes` or `cffi` to call `libz`, and a Rust
program uses the `flate2` crate with a system or bundled zlib. The first needs the shared library installed and found by the
loader, while the second can compile its own copy; the packager must decide which, and the answer decides who ships the
security update.

A failing example is a CI job that builds a Go tool with cgo enabled on a recent runner and deploys the binary to an older
host: it fails with a message about glibc symbol versions. Setting `CGO_ENABLED=0` fixes it if no C code is needed, and
otherwise the build moves into a container matching the target. A second failing example is `pip install` on a distribution
that marks its Python as externally managed: the command is refused, and the right response is a virtual environment, not
the override flag.

## Related problems and ideas

Compiler and linker behaviour from LNX-220-T01 explains why Rust and Go binaries look the way they do. Build systems
(LNX-220-T02) increasingly orchestrate the language tools rather than replacing them. Library naming (LNX-220-T03) is
needed for Python extensions and Rust `-sys` crates. Sanitizers (LNX-220-T05) have per-language entry points, such as the
nightly-only `-Zsanitizer` in Rust and `-race` in Go, and fuzzing (LNX-220-T06) has `cargo fuzz`, native Go fuzz tests and
Atheris. Packaging (LNX-220-T10) deals with what to do about vendored dependencies, and services (LNX-220-T08) are the
usual way to run any of these programs.

Alternatives and opposing views include distribution-first packaging, in which each Rust crate or Go module is a separate
package and the whole archive uses one version of each library, versus upstream-first, where a program ships with its locked
dependencies. Other options are compiling Python to native code (Cython, Nuitka, mypyc), shipping a self-contained
interpreter bundle, or using WebAssembly components as a portable deliverable. The C++ world has Conan and vcpkg, which bring
package managers for native libraries, a gap that C has never closed.

## Active research

Work in progress includes reproducible builds across all four ecosystems, with efforts to verify binaries by rebuilding
independently, and supply-chain integrity: signed releases, provenance attestations (SLSA), trusted publishing for PyPI and
crates.io, and transparency logs. Python continues work on a free-threaded interpreter without the global lock and on an
experimental JIT compiler, both aimed at the performance problem, with the free-threaded build becoming officially
supported in Python 3.14 (to verify the packaging status of extension wheels). Rust is working on a stable ABI story for
dynamic linking, improving compile times through parallel front ends and alternative code generators, and on the
presence of Rust in the Linux kernel and in system components. Go explores profile-guided optimisation, and better
version selection for toolchains.

## Future direction

Expect more of the Linux base system to be written in Rust, with Rust in the kernel now an accepted part of the tree and
more distributions packaging Rust-based replacements for core utilities. Python packaging is converging on
`pyproject.toml` and faster tools written in Rust. Lock files and SBOMs will become required deliverables in regulated
settings. For the working developer the sound habits are: pin and lock, build in clean environments, check the linkage
of what you ship, keep the toolchain in the project's configuration, and be explicit about who is responsible for updating
every dependency inside a shipped binary.
