# Sanitizers and static analysis

## Define the problem

C and C++ give programmers direct control of memory, and they give the compiler permission to assume the programmer never
makes certain mistakes. When a mistake happens anyway, the language does not stop the program. An array write past
its end changes a neighbouring object; a pointer used after its memory was returned goes on working until the
allocator reuses the block; a signed integer that overflows may be optimised in ways that make the program
behave differently at different optimisation levels. These are the defects behind a large share of security
vulnerabilities in native software, and they are notoriously hard to find by testing, because the program often seems
to work and the damage appears later and elsewhere.

The need is for tools that make the invisible visible. There are two broad kinds. Dynamic tools, the sanitizers, instrument
a running program and stop it at the first violation with a precise report. Static tools, the analysers and linters, read
source code and reason about all possible executions without running anything. They find different defects and have
different costs, and a sound practice uses both, together with compiler warnings. This slice covers the compiler-based
sanitizers (AddressSanitizer, UndefinedBehaviorSanitizer, ThreadSanitizer, MemorySanitizer and LeakSanitizer), the compiler
warnings that act as the first level of static checking, and the static analysers available on Linux (GCC's
`-fanalyzer`, Clang's analyser and `clang-tidy`, `cppcheck`, and the kernel's Sparse, Smatch and Coccinelle). The
debugger and Valgrind (LNX-220-T04) are the older, uninstrumented route to the same problems, and fuzzing
(LNX-220-T06) is the usual way to drive sanitized programs with hostile input.

## History and approaches

The earliest approach to memory errors was careful code review and a lot of luck. Tools that replaced `malloc` with a
checking variant, such as Electric Fence and later `libduma`, found heap overruns by placing guard pages next to blocks,
which was effective but caught only some errors and cost a page per allocation. Commercial binary instrumentation, in
particular Purify in the 1990s, showed that comprehensive checks were possible but expensive. Valgrind (2002) delivered the
same breadth for free using dynamic translation, with a slowdown of an order of magnitude or more [src: bootlin-training b38d2ff074d0b706].

The breakthrough in practicality came from Google, where Konstantin Serebryany and colleagues built AddressSanitizer (2011).
Instead of translating machine code at run time, the compiler inserts checks around memory accesses, and a runtime library
keeps "shadow memory" in which every eight bytes of application memory are summarised by one byte describing how many of
them are addressable. Red zones around allocations and a quarantine that delays reuse of freed memory let the runtime
detect overflows and use after free. The measured slowdown was about two times, which made it feasible to run entire test
suites and, eventually, fuzzers under instrumentation. ThreadSanitizer (data races), MemorySanitizer (uninitialised reads)
and UBSan (a list of checks for behaviour the language leaves undefined) followed within the same family, and GCC
implemented compatible versions using the same runtime. The GCC manual lists these options together with the finer
`-fsanitize=` sub-checks [src: man-pages 0bd44e96249512bd].

Static analysis has an older history. `lint` was written at Bell Labs in 1978 to flag suspicious C that the compiler
accepted. Commercial tools (Coverity, Klocwork, PREfast) later used path-sensitive analysis, and Coverity's scans of open
source projects demonstrated that even mature code contained real defects. The weakness of those tools was false positives
and cost. The open-source answers included `splint` (little maintained now), `cppcheck`, the Clang Static Analyzer (a
symbolic-execution engine built into the LLVM project), and `clang-tidy`, which runs a large set of rule-based checks and
can apply fixes. The Linux kernel developed its own families: Sparse, used for annotations such as `__user` and
`__iomem`, Smatch, which does flow-sensitive checks, and Coccinelle, which matches and rewrites code patterns using
semantic patches. The kernel's testing guide explains where each fits [src: kernel-docs 476f861ff5a229f1]. GCC added its own
analyser, `-fanalyzer`, in GCC 10 (2020), initially targeting C; its coverage of C++ has been less complete.

Compilers themselves became the most widely used analysers. Warning sets such as `-Wall -Wextra`, `-Wformat=2`,
`-Wshadow` and `-Wconversion` catch many problems at no extra cost, and fortification through `-D_FORTIFY_SOURCE` adds
checks on libc buffer functions. Governance documents have caught up: NIST's control catalogue lists static code analysis
among developer testing activities that organisations are expected to apply [src: nist-sp800-53 8f0748c4eae71bde].

The pattern that emerged is layered. The compiler warns on the way in; sanitizers catch what executes in tests and fuzzing; a
static analyser looks at paths the tests did not reach; and the results feed continuous integration so that regressions are
blocked.

## Current state

Enabling a sanitizer is a compile-and-link option: `-fsanitize=address` for ASan, `-fsanitize=undefined` for UBSan, `-fsanitize=thread`,
`-fsanitize=memory` (Clang only) and `-fsanitize=leak`. Add `-g` so reports contain file and line, `-fno-omit-frame-pointer`
for faster unwinding, and a low optimisation level such as `-O1` for the best precision. ASan and UBSan combine in one
build (`-fsanitize=address,undefined`); TSan cannot be combined with ASan, and MSan needs every dependency to be
instrumented as well. Behaviour is tuned through environment variables, such as `ASAN_OPTIONS`, `UBSAN_OPTIONS`,
`TSAN_OPTIONS`. Typical settings: `detect_leaks=0` where `ptrace` is unavailable, `halt_on_error=1`,
`abort_on_error=1` to produce a core, `print_stacktrace=1` for UBSan, and `symbolize=1` with
`ASAN_SYMBOLIZER_PATH` pointing to `llvm-symbolizer`. By default UBSan continues after a report, and
`-fno-sanitize-recover=all` makes it stop, which is what tests usually want [src: man-pages 8c388923ddbca412].

An ASan report has a fixed shape: the error type (`heap-buffer-overflow`, `stack-buffer-overflow`, `heap-use-after-free`,
`global-buffer-overflow`, `double-free`, `stack-use-after-return` when enabled), the access with its size and address, the
stack at the point of the bad access, and then where the block was allocated and, for use after free, where it was freed.
The remainder is a shadow memory dump with the offending bytes marked. Reading a report is the skill: the top frame in
your own code is usually the place to start, and the allocation stack tells you what the intended size was. UBSan reports
a single line per finding, naming the file, line and kind: `signed integer overflow`, `shift exponent too large`,
`null pointer passed as argument`, `load of misaligned address`, `index out of bounds for type`. Options such as
`-fsanitize=undefined,integer` or `-fsanitize=float-cast-overflow` widen the set, and Clang has "unsigned-integer-overflow"
as a non-UB but often interesting check.

Static analysis comes in several forms. Warnings are controlled by flags, and a project that builds with `-Wall -Wextra
-Werror` in continuous integration stops many defects at the door. GCC's `-fanalyzer` explores paths inside and across
functions and reports double free, use after free, leaks, null dereferences, uninitialised values and certain
buffer problems with a path that explains how the bug is reached. Clang's analyser is run as `scan-build make` or
`clang --analyze` and produces an HTML report with the path highlighted; the Arch wiki page on Clang describes its
use [src: archwiki 54b832af4e529543]. `clang-tidy` is driven by a `compile_commands.json` file (from CMake or Meson, see LNX-220-T02)
and a configuration of checks (`bugprone-*`, `clang-analyzer-*`, `cert-*`, `performance-*`, `modernize-*`), and can apply
automatic fixes. `cppcheck` is independent of the compiler and quick to adopt. Kernel developers run `make C=1` for Sparse and the
Coccinelle scripts under `scripts/coccinelle`.

The cost of each approach should guide its placement. Sanitizers need executions, so their power equals the power of the
tests or fuzzers that exercise the code; they have no false positives to speak of for ASan, UBSan and TSan, but one run
covers only one path. Static analysers cover many paths without executions but produce false positives, so they need a
baseline and a suppression discipline. The generalised pattern is defence in depth for defects: cheap checks always on,
expensive precise checks on a schedule, results tracked over time.

## Assessment: the good, the bad and the ugly

The good news is the leverage. ASan found thousands of bugs in Chrome, Firefox and the Linux ecosystem soon after it
appeared, and continues to. Running a unit-test suite under ASan and UBSan is cheap enough to do on every commit. Reports are
precise and self-explanatory in a way that an eventual segmentation fault is not. Static analysers find defects in code
that no test reaches, such as error-handling paths, and compiler warnings are free.

The bad news is coverage and compatibility. A sanitizer sees only what runs; it does not find a bug on a path no test
takes. ASan does not detect all uninitialised reads (that is MSan's job), it uses substantial memory, and the combination
of sanitizers with some tools is not supported: Valgrind and ASan do not mix, and `ptrace`-based LeakSanitizer fails in
containers that block `ptrace`. Sanitized builds are not security hardening: they change the memory layout and are meant for
testing, not for shipping, although a hardened variant (HWASan on Arm, or "GWP-ASan" sampling) is used in production. Static
tools can overwhelm a team with warnings about old code, and a policy of "fix everything" may stall adoption.

The ugly parts include false negatives that give false comfort, third-party libraries that are not instrumented
and so hide errors at the boundary, custom allocators that bypass the red zones (arena allocators allocate large blocks that
ASan considers fine, unless manual poisoning calls are added) and suppression files that grow without review. Undefined behaviour
that "works" can become a bug at the next compiler release, so a clean sanitizer run on today's compiler is not a
proof. The same code may behave differently under GCC and Clang, so running both in continuous integration is a cheap
way to find portability defects.

## Applications beyond this domain

The idea of shadow state that records the validity of each unit of memory is used by hardware too. Arm's Memory Tagging
Extension attaches a small tag to pointers and to memory granules, and the CPU checks that they match, which is
effectively ASan implemented in silicon and is already used in Android and some servers. CHERI capability hardware puts
bounds into pointers themselves. The Linux kernel has its own sanitizers: KASAN (address), KCSAN (data races),
UBSAN, KMSAN, and `kmemleak`, which use the same compiler instrumentation in kernel mode. Language runtimes in
managed languages perform similar checks by design: Rust's borrow checker proves in the compiler what ASan finds at run time,
Go's race detector is built on the TSan runtime, and Java's JIT inserts bounds checks. For other fields, property-based and
mutation testing use the same philosophy of increasing the chance that a latent flaw becomes visible.

## Examples

A first example is an off-by-one in a loop that fills a heap buffer with `i <= n`. The program prints the right answer
and passes its tests. Compiled with ASan it stops and reports a write past a 16-byte region, naming the function and line
and the allocation site; the fix is a one-character change. The lab for this topic uses exactly this bug and a
signed-overflow bug, and requires saved reports and a clean run of the fixed version.

A second example is a use after free in a callback: a handler keeps a pointer to a request object that the main loop frees on
timeout. Production crashes are rare and random. An ASan run of the integration tests reports `heap-use-after-free` and
prints both the free stack (the timeout path) and the later read stack (the handler), which is everything needed to
change the ownership design.

A third example shows UBSan finding a portability bug: `1 << 31` on a signed int, or a `memcpy` into a misaligned
`uint32_t *`, which works on x86 and traps on some other processors. A failing example is a team that builds with ASan but
links a hand-written pool allocator for their own objects; ASan sees nothing wrong with a write within the pool block
that belongs to another object. The cure is to add `ASAN_POISON_MEMORY_REGION` annotations to the pool or to disable the
pool in test builds.

## Related problems and ideas

Sanitizers are build options, so they depend on the build-system knowledge in LNX-220-T02 (Meson's `-Db_sanitize=address,undefined`,
CMake's flags on a target) and on the toolchain mechanics in LNX-220-T01. They produce reports that GDB can break on
(`break __asan_report_error`, or `abort_on_error=1` plus a core, see LNX-220-T04). Fuzzing and coverage in
LNX-220-T06 run sanitized targets by default, because a fuzzer without a sanitizer only notices crashes. For services under systemd (LNX-220-T08)
you can set `ASAN_OPTIONS` in the unit's `Environment=` to test a deployment configuration. For the Rust
and Go toolchains in LNX-220-T07, `cargo` nightly offers `-Zsanitizer`, Go has `-race` and `-msan` and `-asan` flags,
and mixed programs need the sanitizer runtime to be consistent.

Alternatives and complements include Valgrind (no recompilation, slower), `libFortify`-style hardening, bounded-pointer
C dialects (Checked C and Fil-C, which aim to make C memory safe at higher cost), memory-safe rewrites in Rust, and
formal verification tools such as Frama-C and CBMC (bounded model checking) that prove properties for selected code. Symbolic execution
engines (KLEE) generate inputs that reach paths. These are not mainstream in application development, though CBMC is
used in AWS libraries and KLEE in research [web: llvm.org].

## Active research

Active areas include making sanitizers cheaper for production (sampling allocators and hardware tagging), improving the
precision of static analysers with better path merging, summaries and machine-learning-assisted triage of reports, and
combining analysis with fuzzing so that a static warning is confirmed by a generated input. GCC's analyser keeps gaining
checks, notably for C++ and for common library semantics (to verify the current status in GCC 16). The Clang community
works on "-fbounds-safety", an annotation-based extension for bounds checking in C aimed at adoption in large
code bases (to verify availability in upstream releases). Work on defining and shrinking undefined behaviour in the C
and C++ standards, including the C23 and C++26 efforts on "erroneous behaviour" and contracts, changes what a tool must report.

## Future direction

Expect hardware memory tagging to move from phones to servers and to be paired with allocators that sample for heap
errors in production. Memory-safe subsets and compiler flags that make bound checks default (the C++ standard library
"hardening" modes, for example) will reduce the exposure of existing code. Static analysers will increasingly be part of the
compiler and the editor, with results updated as you type. For learners, the stable habits are: compile with warnings as
errors in continuous integration, always run the unit tests once with ASan and UBSan, keep reports and suppressions in the
repository, and read the first frame of a report before anything else.
