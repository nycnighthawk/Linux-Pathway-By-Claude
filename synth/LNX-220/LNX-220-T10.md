# Packaging applications: RPM, DEB, Flatpak and OCI images

## Define the problem

A program is useful only when somebody else can install it, run it, update it and, when necessary, remove it without
leaving a mess. The developer's build output is a directory of files built against particular libraries on a particular
machine. Turning that into something deliverable raises a set of questions. Which files go where, and who owns them? Which
other software must be present, at which versions? How is the result signed and verified? How do upgrades preserve
user configuration and restart services? How can the same source be rebuilt next year by someone else and yield the
same package? And what, if anything, should isolate the program from the host?

Linux has not settled on a single answer, because the audiences differ. System administrators want native packages that
integrate with the distribution's dependency solver, security updates and audit tools. Desktop users want applications that
are independent of the distribution release and that run in a sandbox. Operators of servers want an immutable image that
runs identically on a laptop, in a continuous-integration job and on a cluster. This topic compares the four formats that cover
these audiences: RPM (Red Hat family), DEB (Debian family), Flatpak (desktop applications) and OCI images (containers).
The gap it fills is understanding what each format records and promises, so that an application can be shipped in the
right one, or in several, from the same staged install tree that LNX-220-T02 produces.

## History and approaches

The earliest software distribution on Unix was a tarball and a README, with an install script if the author felt generous.
Tarballs carry no metadata: no dependency list, no ownership of files, no way to uninstall except by remembering which files
were added. Slackware's simple package tools added little more. The next step, in 1993 to 1995, was the package manager: the Debian
project's `dpkg` and the `rpm` tool created at Red Hat each defined an archive format with a control section (name, version,
dependencies, scripts) and a payload, plus a local database of installed packages with file lists. Together with a
higher-level tool that resolves dependencies from repositories (`apt` in 1998, later `yum` and `dnf`, and `zypper` for SUSE),
this became the standard way of managing a Linux system, as LNX-104 explained from the administrator's side.

Packaging as a craft evolved separately. A source package records how to build binary packages from upstream sources: a
spec file in RPM and a `debian/` directory in Debian, with the build run in a clean environment (`mock` for RPM, `sbuild` and
`pbuilder` for Debian) so that undeclared dependencies show up as failures. RPM's spec has sections for preparation
(`%prep`), build (`%build`), install into a build root (`%install`), tests (`%check`), the file list (`%files`) and
scriptlets, with macros for standard directories. Red Hat's packaging guide documents the workspace layout and the
`rpmbuild` flow [src: rhel-10-docs 5a3fe705d95ebe44], including how `%files` directives mark configuration files, documentation and
ownership [src: rhel-10-docs 6adc0a9985a1ea11]. In Debian, `dpkg-buildpackage` runs the `debian/rules` makefile, which in
modern packages delegates to the `debhelper` toolkit [src: man-pages f697120f62aa7639], and `dpkg-deb` assembles the archive from a
prepared tree [src: man-pages 6caf592acb469fe2]. The Debian Administrator's Handbook explains building a first package, including
a simple one made from a file archive [src: debian-handbook 574478474db5b32b]. Policy documents (the Debian Policy, the
Fedora Packaging Guidelines) specify what a good package does, and distributions run automated checks (`lintian`, `rpmlint`).

By the 2010s the native model showed its limits for application delivery. A native package depends on the distribution's
library versions, so a vendor must build one package for each release of each distribution, and users of a stable distribution
wait years for new application versions. Early answers were bundles (AppImage), per-user installers and "snap" packages
from Canonical (2014) with a sandbox and a store. Flatpak, from Alexander Larsson and others around 2015 (formerly xdg-app),
chose a decentralised design: applications are built against a versioned runtime (such as the Freedesktop or GNOME runtime), stored in
an OSTree repository that deduplicates files, installed per user or per system, and run in a sandbox made of namespaces and
seccomp, with the permissions declared in the application's metadata. The manual pages describe the commands and the metadata
file format [src: man-pages 6506fcc9a2e41e69], and `flatpak run` options override permissions at launch
[src: man-pages 79b0cd88d5f89128].

Containers took a different path. Linux namespaces and control groups made it possible to run a process with its own view of
the filesystem and network. Docker (2013) popularised an image format built from stacked filesystem layers and a simple
build recipe, the Dockerfile. Interoperability needed a standard, and the Open Container Initiative (2015) defined the runtime
specification, the image specification and the distribution specification. An OCI image is a manifest that points to a
configuration (architecture, operating system, entry point, environment, and a list of `diff_id` digests of the uncompressed layers)
and to compressed layer archives, all addressed by the SHA-256 of their content. Tools implementing the standard include Podman,
Buildah and Skopeo (the Red Hat guide describes how they combine) [src: rhel-10-docs 145c37c5c9b3be7b], Docker, containerd and
BuildKit. The same format now carries more than application images: bootable operating-system images (the "image mode" of RHEL
builds a system from a Containerfile) [src: rhel-10-docs 5fef671c1802a8a7].

The pattern across all four is the same. A package is a set of files with metadata, addressed by a name and version,
distributed through a repository and verified with signatures or content digests. They differ in how much of the environment
they bring along: native packages bring none and depend on the system, Flatpak brings a runtime reference and a sandbox, and OCI
images bring the whole user space.

## Current state

An RPM is built from a spec file and sources with `rpmbuild -ba name.spec` (source and binary) or `-bs` (source only), usually in
a clean build root through `mock`. The spec's header declares `Name`, `Version`, `Release`, `License`, `Summary`, `Source0`,
`BuildRequires` (build-time dependencies) and `Requires` (run-time dependencies; library dependencies are added automatically from sonames
and `pkg-config` files). The `%install` section installs into `%{buildroot}` using the macro paths (`%{_bindir}`, `%{_unitdir}`), and `%files` lists
what belongs to the package with attributes such as `%config(noreplace)`, `%doc` and `%license`. Scriptlets (`%post`, `%preun`) are avoided or
standardised through macros such as `%systemd_post`. Signing uses `rpmsign` with a GPG key, and repositories are indexed with
`createrepo_c`. The `rpmbuild` manual page lists the stages and options [src: man-pages c758e94a127367ce], and Red Hat's guide covers
building binary and source packages step by step [src: rhel-10-docs 30d08043079bbbeb].

A DEB source package has `debian/control` (source and binary stanzas with `Build-Depends`, `Depends`, `Architecture`),
`debian/rules`, `debian/changelog` (which defines the version), `debian/copyright` and the `compat` or `debhelper-compat` level. The common build is
`dpkg-buildpackage -us -uc` or `debuild`, in a clean `sbuild` chroot. Binary packages contain a `control.tar` (control file, scripts, checksums) and a
`data.tar` (the files). For a hand-made package, a staged tree with a `DEBIAN/control` file is converted by
`dpkg-deb --root-owner-group --build`, which makes files owned by root. Dependencies on libraries are generated by `dh_shlibdeps` from the sonames
of the linked libraries (see LNX-220-T03). Debug symbols go to separate `-dbgsym` packages from `dh_strip`, matching the build-ID mechanism of
LNX-220-T01. `lintian` checks policy, and `apt-ftparchive` or `reprepro` make repositories.

A Flatpak application is described by a manifest (YAML or JSON) naming the application ID in reverse-DNS form, the runtime and SDK with
versions, the permissions (`finish-args`, such as `--share=network`, `--socket=wayland`, `--filesystem=xdg-documents:ro`, `--talk-name=` for D-Bus
names as discussed in LNX-220-T09), and a list of modules, each with its sources and build system. `flatpak-builder` builds
into a sandbox without network access (sources are downloaded first and checksummed), commits to an OSTree repository, and
`flatpak build-bundle` creates a single-file bundle. Users add a remote and install; updates are delta-based. Applications ship `.desktop`
files and AppStream metainfo so that software centres can list them. Flathub is the main public repository.

An OCI image is built with a recipe (Containerfile or Dockerfile) through `podman build`, `buildah` or `docker build`. Each instruction that
changes the filesystem makes a layer, so the order matters for caching: dependencies first and source last. Multi-stage builds compile in one image
that holds the toolchain and copy only the result into a small final image, which is the standard way to keep compilers out of
runtime images; static or minimal-base programs (Go, Rust with musl, or "distroless" bases) run in an image with a few megabytes. The result
is addressed by a digest; tags are mutable names that point to digests, so deployments should pin digests. Images are pushed to
registries and signed with tools such as `cosign` or with `sigstore` and the policy files of containers-image. Key options at run time include the
user (avoid root), read-only root filesystems, dropped capabilities and resource limits. Because an image contains a user space, security
updates are delivered by rebuilding, which is why vulnerability scanners and software bills of materials are part of the workflow.

The generalised pattern is: stage an install tree with `DESTDIR` or a prefix; describe the metadata (identity, version, dependencies, entry points,
permissions); build in a clean environment; sign; publish in a repository; and let a client verify and install. The differences between formats
are the answers to three questions: who resolves dependencies, how much is isolated, and what is the unit of update.

## Assessment: the good, the bad and the ugly

The good side of native packages is integration: one dependency solver, one security-update channel for all libraries, file ownership
tracking, verification (`rpm -V`, `debsums`) and decades of policy about what a package may do. Flatpak gives distribution-independent desktop
software with a real sandbox and automatic updates. OCI images give excellent repeatability and a huge ecosystem of base images and tooling,
and they are the common currency of cloud deployment.

The bad side is cost and divergence. Native packaging requires learning two or more systems, and the policy rules are strict; a vendor wanting to
support five distributions maintains five recipes. Bundled formats duplicate libraries, which increases disk use and moves security-update
responsibility to the application maintainer: a Flatpak runtime is updated centrally, but libraries bundled into the application are not.
Container images accumulate vulnerabilities silently as base layers age. Sandboxes only help if the permissions are narrow, and many applications
request broad access (`--filesystem=host`) for convenience. OCI layers also leak: a secret copied in one layer and deleted in the next is still in the earlier layer.

The ugly side includes scriptlets with side effects that fail halfway and leave a system broken, config-file handling
during upgrades (`.rpmnew`, `.dpkg-dist` conflicts), dependency solving failures with multiple repositories, ABI breakage that a packager failed to
notice, and non-reproducible builds that embed timestamps and paths. In containers, running as root, mutable tags such as `latest`, and shipping
build tools in the final image are persistent bad habits. Packaging a program that downloads its dependencies during the build (npm, cargo, go) conflicts
with the offline build rules of distributions, which is a significant source of friction; vendoring is the usual compromise.

## Applications beyond this domain

The package idea (content plus metadata, addressed by name, version and digest) is universal. Language ecosystems (PyPI wheels, crates, npm)
are packages with their own dependency solvers; Helm charts and Kubernetes operators package cluster applications; Terraform modules and Ansible
collections package infrastructure; browser extensions and mobile apps are packages with permission manifests that closely resemble Flatpak's. OCI is now
used beyond container images to store Helm charts, WebAssembly modules, SBOMs and signatures in registries, since a registry is a good content-addressed store. Operating system
updates are delivered as images in Fedora Silverblue and CoreOS (OSTree, rpm-ostree), ChromeOS and Android's A/B updates, extending the
same ideas to the whole base system. In supply-chain security, the manifest of digests and the provenance attestation around a build are a standard control.

## Examples

A first example turns the staged install tree of a small command-line tool into an RPM and a DEB. For RPM, a spec with `%install` doing
`make install DESTDIR=%{buildroot} PREFIX=%{_prefix}` and a `%files` section listing `%{_bindir}/hello` and the licence file, built with `rpmbuild -ba`.
For DEB, a `debian/` directory with `debhelper-compat`, a two-line `rules` file calling `dh $@` and a control file. Both run
the program's tests in `%check` or `dh_auto_test`, which ties back to LNX-220-T06. The lab for this topic builds the DEB straight
from a staged tree with `dpkg-deb`, since that needs no repository or build chroot, and assembles an OCI layout by hand to
show where the digests come from.

A second example is the Flatpak manifest for a GTK application: runtime `org.gnome.Platform` at a pinned version, `finish-args` with `--socket=wayland`,
`--socket=fallback-x11` and `--share=ipc`, and one `meson` module with a git source pinned to a tag and commit. Permissions
are reviewed with `flatpak info --show-permissions`, and a tester narrows them with `flatpak override --user --nofilesystem=home`.

A third example is a two-stage Containerfile: the first stage uses a Go toolchain image to build with `CGO_ENABLED=0`, the second starts from an empty
or minimal base, copies the binary, sets a non-root `USER` and an `ENTRYPOINT`. The final image is a few megabytes and has no shell for an attacker to use. A failing
example is the "works on my machine" RPM that omitted a `BuildRequires`: it builds on the developer's machine, which has the header installed, and fails
in `mock`. The clean build root exists to catch exactly that. A second failing example is a Debian package whose `postinst` script calls a tool
from an optional package; on a minimal system the upgrade aborts halfway. Using `Depends`, or guarding the call, fixes it.

## Related problems and ideas

This topic consumes the output of the build system (LNX-220-T02), relies on library metadata (LNX-220-T03) for automatically generated dependencies,
and on debug-info splitting (LNX-220-T01) for `-debuginfo` packages. Unit files and the post-install helpers for systemd services link to LNX-220-T08,
D-Bus activation files and XDG desktop entries to LNX-220-T09, and the language toolchains of LNX-220-T07 influence whether vendoring or per-module packaging is
chosen. LNX-104 gave the administrator's view of the same tools: querying, verifying and repairing packages.

Alternative approaches include Nix and Guix (functional, reproducible package stores with per-package closures), AppImage (a single executable
file with a mounted filesystem), Snap, `systemd-sysext` and `portable services` (overlay images for system extensions), `ostree` and `bootc` (the whole operating
system as an image), and Homebrew-style per-user package managers. Each makes a different trade-off between sharing and isolation. Experimental or
non-mainstream proposals include content-addressed distribution of individual files across packages, WebAssembly components as a portable unit,
and "source-first" approaches where users rebuild everything from verified sources.

## Active research

Active topics are reproducible builds (the Reproducible Builds project tracks the share of packages that rebuild bit for bit in Debian and other
distributions), supply-chain security (SLSA provenance, in-toto attestations, Sigstore signatures, SBOM formats such as SPDX and CycloneDX), and
bootable-container workflows for operating system delivery. Flatpak and the portal system keep developing finer permissions and better
handling of system services. In OCI, work covers lazy pulling of large images (eStargz and similar), artifact references for signatures
and attestations, and new compression such as zstd (to verify the support level in each runtime). Package managers research better dependency
solving and faster metadata, for example the move to libsolv-based solvers and to compact metadata formats.

## Future direction

Expect the base operating system itself to become an image in more deployments, with applications delivered as containers or Flatpaks and native
packages reserved for the base. Signed provenance and SBOMs will become mandatory deliverables for software sold to regulated customers, and
reproducibility will be treated as a security property. For the developer the practical advice is to keep the staged install clean and
`DESTDIR`-aware, to write the metadata once in a reusable form, to build only in clean environments, to pin versions and digests, and to
choose the format by audience rather than by habit.
