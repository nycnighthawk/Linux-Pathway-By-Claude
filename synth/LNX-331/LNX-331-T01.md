# Character devices, file_operations and ioctl: the simplest kind of driver

## Define the problem

User programs reach hardware and kernel services through files. A program opens a path under `/dev`, reads and writes bytes, and sends control requests. The kernel must route those operations to code that knows the device, enforce permissions, deal with concurrent users, and cope with bad pointers from user space without crashing. A driver author needs the smallest interface that lets a stream-like device (a serial port, a sensor, a random number source, a control channel for a virtual machine) be driven by ordinary programs.

The character device is that interface. It models a device as an unstructured stream or a set of control points, in contrast to block devices that move fixed-size blocks through the page cache and network devices that move packets through the network stack.

## History and approaches

**Everything is a file.** Unix presented devices as special files with a major and minor number: the major selected a driver, the minor an instance. Early Linux kept a static table of majors assigned by a central registry, which is why the well-known numbers (memory devices on major 1, ttys on 4, and so on) are still listed in the kernel documentation.

**Dynamic numbers and udev.** Static assignment did not scale to thousands of devices. Drivers began to request numbers dynamically with `alloc_chrdev_region`, and user space tooling (devfs, then `udev`) creates device nodes under `/dev` according to events from the kernel, so a node appears when a device class is registered.

**The misc device.** Many small drivers need one node and no special major. The `misc` framework hands out minors under a shared major (10) and creates the node automatically; a driver fills a `struct miscdevice` with a name, a minor (or `MISC_DYNAMIC_MINOR`) and a `file_operations` table, and calls `misc_register`. For a first driver this removes the bookkeeping.

**file_operations.** The central structure is a table of function pointers: `open`, `release`, `read`, `write`, `llseek`, `unlocked_ioctl`, `compat_ioctl`, `mmap`, `poll`, `fasync` and others. The VFS calls the entry that matches the system call. Over the years the table gained alternatives such as `read_iter` and `write_iter` (vector-based I/O) and `uring_cmd` for the io_uring interface.

**ioctl.** Reads and writes carry data; control actions such as setting a baud rate or querying a device state do not fit. `ioctl(fd, cmd, arg)` is the catch-all. It has a poor reputation because commands are opaque numbers and argument layouts differ, so the kernel introduced a convention, the `_IO`, `_IOR`, `_IOW` and `_IOWR` macros, that packs a direction, a size, a type letter and a sequence number into the command so that tools and compat layers can reason about them. Alternatives with more structure include sysfs attributes, netlink and, more recently, `io_uring` commands.

## Current state

### Registering a device

A minimal driver is a module (see the course on out-of-tree modules) that, in its init function, registers either a misc device or a character-device number range with a `cdev`. The `file_operations` structure ties the node to the handlers. `module_init` and `module_exit` run on load and unload; `MODULE_LICENSE` declares the licence. A device exposed this way appears in `/dev` when `udev` handles the event, with permissions set by rules, not by the driver (though a misc device can suggest a mode).

### open and release

`open` runs when a process opens the node. A driver may check permissions or exclusivity, allocate per-open state and store it in `file->private_data` for later calls. The `inode` provides the device numbers. `release` runs when the last reference to the open file is dropped; it frees the state. Note the distinction: `fork` duplicates descriptors that share one open file, so `release` runs once, after every duplicate is closed.

### read and write

`read(struct file *, char __user *buf, size_t count, loff_t *ppos)` returns the number of bytes provided, zero for end of data, or a negative errno. Rules that matter in practice:

- Never touch a `__user` pointer directly. Use `copy_to_user` and `copy_from_user`, or helpers such as `simple_read_from_buffer`, which validate the range and handle faults. These functions return the number of bytes *not* copied, so a non-zero result means `-EFAULT`.
- A short transfer is legal. The caller must loop. A read that returns zero tells the caller the stream ended, so a device that has no data right now must either block (the default), return `-EAGAIN` when the file was opened non-blocking, or both depending on `O_NONBLOCK`.
- The offset belongs to the open file. Stream devices ignore it; buffer-like devices use and advance `*ppos`. Implement `llseek` (or `no_llseek`) to match.
- Blocking uses a wait queue: sleep with `wait_event_interruptible` on a condition, wake it from the code that produces data, and return `-ERESTARTSYS` if a signal arrives so the call can restart or fail with `EINTR`.

### poll and asynchronous notification

For `select`, `poll` and `epoll` to work, the driver implements `poll`, which registers the wait queue with `poll_wait` and returns a mask of ready events (`EPOLLIN`, `EPOLLOUT`, `EPOLLERR`, `EPOLLHUP`). A driver that supports blocking reads but not poll will hang event-driven programs.

### ioctl design

The handler is `unlocked_ioctl`, called without the old big kernel lock, so the driver must do its own locking. Commands are defined in a public header with the convention macros, for example `_IOR('k', 1, int)` for a command that returns an int. The handler switches on the command, uses `copy_to_user` and `copy_from_user` on the argument, validates every value it reads, and returns `-ENOTTY` for commands it does not know (the historical code for "inappropriate ioctl for device"), `-EINVAL` for a bad argument and `-EFAULT` for a bad pointer. Struct arguments need care: use fixed-size types (`__u32`, `__u64`) and explicit padding so a 32-bit process on a 64-bit kernel sees the same layout, or provide `compat_ioctl` that translates. Once a command is in a released kernel it is part of the user-space ABI and cannot change; the documentation on ioctl numbers records the assigned type letters to avoid collisions.

### Concurrency and lifetime

Several processes can open the same node and call it at once, so shared device state needs a lock. A driver that can be unplugged or unloaded must not free state while a call is in progress: reference counting on the device object, or `devm_` managed resources and the kernel's file-operation protection when removing a cdev, stops use after free. A system-call handler may sleep, so a mutex is the normal choice, unlike the interrupt handlers discussed later in this course.

### Testing without hardware

Because the interface is a file, a driver can be exercised from a shell (`echo`, `cat`) or a small C program, in a virtual machine. The behaviour of the handlers (return values, offsets, error codes) can also be modelled and tested in user space before the code is moved into a module, which is what this topic's lab does with a small shim for `copy_to_user`.

## Assessment: the good, the bad and the ugly

**The good.** The model is simple and universal: any language can open a file. Permissions, namespaces and tooling (strace, shell redirection) work with no extra effort. A misc device with a few operations fits in under a hundred lines.

**The bad.** ioctl is untyped and under-documented. Every driver defines its own commands, which makes introspection and security review hard (seccomp filters must whitelist individual command numbers). Getting blocking, signals, poll and non-blocking mode right is surprisingly fiddly, and the same mistakes recur across drivers.

**The ugly.** Compat layers for 32-bit callers, structures with implicit padding, and drivers that interpret pointers in the argument incorrectly are a long-running source of security bugs. Unbounded copies and use of user values as array indices give memory corruption. A character device left world-writable by a careless udev rule gives every local user access to a privileged control channel.

## Applications beyond this domain

- **Virtualisation**: `/dev/kvm` is a character device, and every action on a virtual machine is an ioctl on a file descriptor; the same style of interface (`KVM_CREATE_VM`, `KVM_RUN`) is the basis of the hypervisor course later in this pathway.
- **GPU and accelerator drivers** expose command submission through ioctls on device nodes.
- **Security tools** such as seccomp filters and Landlock policies filter by device and command number.
- **Embedded sensors and buses** (GPIO, I2C, SPI) are usually exposed through character devices that userspace libraries wrap.
- **Other operating systems** have the same pattern: device nodes with control requests (for example, FreeBSD and macOS device interfaces), differing in detail.

## Examples

**A counter device.** A misc device `/dev/counter` increments a counter on each write and returns its value on read. `read` returns the decimal text with `simple_read_from_buffer`, so repeated reads at advancing offsets work, and a second `cat` sees end of file.

**A reset ioctl.** An `ioctl(fd, MY_RESET)` clears the device buffer. A tool running under a seccomp filter gets `EPERM` because the filter allows `read` and `write` but not `ioctl`; the fix is to allow that command number by value.

**A short write.** A program writes 100 bytes into a buffer device that holds 64. The driver stores 64 and returns 64; the program loops and writes the rest, which returns `ENOSPC`. A buggy driver returns 100 and silently drops 36 bytes.

**A 32-bit caller.** A structure containing a `long` has different sizes on a 32-bit process and the 64-bit kernel. A conversion in `compat_ioctl`, or a redesign with fixed-width fields, fixes it.

## Related problems and ideas

- **Device model, sysfs and platform drivers** (next topic) give a driver a place in the hierarchy and a way to expose attributes without ioctls.
- **Interrupts and workqueues** supply the events that wake blocked readers.
- **Locking** governs the shared state in the handlers.
- **Memory allocation and DMA** appear when devices move data.
- **Netlink, sysfs, configfs and io_uring commands** are the other kernel/user control interfaces; each is better than ioctl for some uses.

## Active research

Work in this area includes safer ways to write drivers (Rust abstractions for misc and character devices), tooling to describe ioctl interfaces so fuzzers can generate valid calls (syzkaller's descriptions), and moves to replace ioctl with structured interfaces such as `io_uring` command passthrough. Static analysis for missing `__user` annotations, uninitialised copies and compat mismatches continues (to verify the state of Rust misc device support in current kernels).

## Future direction

New drivers increasingly prefer sysfs for simple attributes, netlink for structured configuration and io_uring commands for high-rate submission, leaving ioctl for legacy and a few well-understood control paths. Rust drivers will wrap the same VFS hooks with ownership rules that make the user-pointer and lifetime mistakes harder to write.
