# Character devices, file_operations and ioctl: the simplest kind of driver

## Define the problem

Programs reach hardware and kernel services through files. A process opens a path under `/dev`, reads and writes bytes, and sends control requests. Behind that ordinary-looking interface the kernel has real work to do. It must route each operation to the code that knows the device, enforce permissions, cope with several users at once, and survive bad pointers handed over by a program that may be hostile or merely buggy. A driver author needs the smallest interface that lets a stream-like device (a serial port, a sensor, a random-number source, a control channel for a virtual machine) be driven by ordinary programs in any language.

The character device is that interface. It models a device as an unstructured stream or as a set of control points. That distinguishes it from the block device, which moves fixed-size blocks through the page cache, and from the network device, which moves packets through the network stack. This essay builds the idea in the order a driver author meets it: the history that made devices into files, the structure that connects a file to driver code, the rules for moving data safely, and the awkward control channel, ioctl, that grew beside the data path.

## History and approaches

### Everything is a file

Unix presented devices as special files carrying a *major* and a *minor* number. The major selected a driver and the minor selected one instance of the device. Early Linux kept a static table of major numbers assigned by a central registry, which is why the well-known numbers (memory devices on major 1, terminals on 4) still appear in the kernel's documentation. The idea paid off immediately: every tool that could read a file could read a device, and permissions on the node controlled access.

### Dynamic numbers and udev

Static assignment did not scale to thousands of devices. Drivers began to request numbers dynamically with `alloc_chrdev_region`, and user-space tooling took over the creation of nodes: first devfs, then `udev`, which creates a node under `/dev` in response to events from the kernel. A node therefore appears when a device class is registered, and its owner and mode come from rules, not from the driver.

### The misc device

Many small drivers need one node and no special major number. The `misc` framework answers that need: it hands out minors under a shared major (10) and creates the node automatically. A driver fills a `struct miscdevice` with a name, a minor (or `MISC_DYNAMIC_MINOR`) and a `file_operations` table, and calls `misc_register`. For a first driver this removes the bookkeeping and leaves only the behaviour.

### The operations table

The central structure is a table of function pointers: `open`, `release`, `read`, `write`, `llseek`, `unlocked_ioctl`, `compat_ioctl`, `mmap`, `poll`, `fasync` and others. The virtual file system calls the entry that matches the system call a program made. Over the years the table gained alternatives, `read_iter` and `write_iter` for vector I/O and `uring_cmd` for the io_uring interface, but the pattern, a table that a driver fills in and the kernel dispatches through, has not changed.

### Control requests and ioctl

Reads and writes carry data, but actions such as setting a baud rate or querying a device's state do not fit that model. `ioctl(fd, cmd, arg)` became the catch-all. It has a poor reputation, because commands are opaque numbers and argument layouts differ from driver to driver. The kernel introduced a convention, the `_IO`, `_IOR`, `_IOW` and `_IOWR` macros, which pack a direction, a size, a type letter and a sequence number into the command so that tools and compatibility layers can reason about it. Alternatives with more structure exist: sysfs attributes, netlink and, most recently, `io_uring` commands. The lesson from this history is that the first interface to be invented is rarely the one that stays the best, and that the first one stays in use for decades.

## Current state

### Registering a device

A minimal driver is a module that, in its init function, registers either a misc device or a range of character-device numbers with a `cdev`. The `file_operations` structure ties the node to the handlers. `module_init` and `module_exit` run on load and unload, and `MODULE_LICENSE` declares the licence. A device exposed this way appears in `/dev` when `udev` handles the event, with permissions set by rules (a misc device can suggest a mode).

### open and release

`open` runs when a process opens the node. A driver may check permissions or exclusivity, allocate per-open state and keep it in `file->private_data` for later calls, and the `inode` gives access to the device numbers. `release` runs when the last reference to the open file is dropped and frees the state. The distinction matters: `fork` duplicates descriptors that share a single open file, so `release` runs once, after every duplicate has been closed, and not once per `close` call.

### read and write

`read(struct file *, char __user *buf, size_t count, loff_t *ppos)` returns the number of bytes provided, zero for end of data, or a negative error number. Four rules govern nearly every implementation.

- Never touch a `__user` pointer directly. Use `copy_to_user` and `copy_from_user`, or helpers such as `simple_read_from_buffer`, which validate the range and handle faults. These functions return the number of bytes *not* copied, so a non-zero result means `-EFAULT`.
- A short transfer is legal, and the caller must loop. A read that returns zero tells the caller the stream has ended, so a device with no data *right now* must either block (the default), return `-EAGAIN` when the file was opened non-blocking, or do either according to `O_NONBLOCK`.
- The file offset belongs to the open file. Stream devices ignore it, while buffer-like devices use and advance `*ppos`. `llseek` (or `no_llseek`) should match.
- Blocking uses a wait queue: sleep with `wait_event_interruptible` on a condition, wake the queue from the code that produces data, and return `-ERESTARTSYS` if a signal arrives so the call can restart or fail with `EINTR`.

### poll and asynchronous notification

For `select`, `poll` and `epoll` to work, the driver implements `poll`, which registers the wait queue with `poll_wait` and returns a mask of ready events (`EPOLLIN`, `EPOLLOUT`, `EPOLLERR`, `EPOLLHUP`). A driver that supports blocking reads but not poll will hang any event-driven program that uses it.

### ioctl design

The handler is `unlocked_ioctl`. The name records that it runs without the old big kernel lock, so the driver must do its own locking. Commands are defined in a public header with the convention macros: `_IOR('k', 1, int)`, for example, defines a command that returns an integer. The handler switches on the command, uses `copy_to_user` and `copy_from_user` on the argument, validates every value it reads, and returns `-ENOTTY` for commands it does not know (the historical code for "inappropriate ioctl for device"), `-EINVAL` for a bad argument and `-EFAULT` for a bad pointer. Structure arguments need care: use fixed-size types (`__u32`, `__u64`) and explicit padding, so that a 32-bit process on a 64-bit kernel sees the same layout, or provide `compat_ioctl` to translate. Once a command appears in a released kernel it is part of the user-space ABI and cannot change, and the kernel's table of ioctl numbers records the assigned type letters to prevent collisions.

### Concurrency and lifetime

Several processes can open the node and call it at once, so shared device state needs a lock. A driver that can be unplugged or unloaded must not free state while a call is in progress: reference counting on the device object, managed (`devm_`) resources, and the kernel's protection for removing a cdev prevent use after free. A system-call handler may sleep, so a mutex is the normal choice, unlike the interrupt handlers discussed later in this course.

### Testing without hardware

Because the interface is a file, a driver can be exercised from a shell with `echo` and `cat`, or from a small C program, inside a virtual machine. The behaviour of the handlers (return values, offsets, error codes) can also be modelled and tested in user space before the code moves into a module, which is what this topic's lab does with a small shim for `copy_to_user`.

### The generalised pattern

A table of operations, filled in by the driver and called by a generic layer; per-open state held in a private pointer; every transfer across the user boundary checked; and one escape hatch (ioctl) for everything that does not fit a byte stream. The same pattern, a generic layer dispatching through a table of function pointers, describes block drivers, network drivers and file systems, the other topics of this course.

## Assessment: the good, the bad and the ugly

**The good.** The model is simple and universal: any language can open a file. Permissions, namespaces and tools such as `strace` and shell redirection work with no extra effort. A misc device with a few operations fits in under a hundred lines, and a student can read all of it.

**The bad.** ioctl is untyped and under-documented. Each driver defines its own commands, which makes introspection and security review hard, since a seccomp filter has to allow individual command numbers. Getting blocking, signals, poll and non-blocking mode right together is surprisingly fiddly, and the same mistakes recur in driver after driver.

**The ugly.** Compatibility layers for 32-bit callers, structures with implicit padding, and drivers that misinterpret pointers inside an argument are a long-running source of security bugs. An unbounded copy, or a user-supplied value used as an array index, gives memory corruption. A character device made world-writable by a careless `udev` rule gives every local user a privileged control channel.

## Applications beyond this domain

- **Virtualisation.** `/dev/kvm` is a character device, and every action on a virtual machine is an ioctl on a descriptor derived from it. The same style (`KVM_CREATE_VM`, `KVM_RUN`) underlies the hypervisor course later in this pathway.
- **GPU and accelerator drivers** expose command submission through ioctls on device nodes.
- **Security tools** such as seccomp and Landlock policies filter by device and by command number, so a reader who understands the interface understands the policy.
- **Embedded buses.** GPIO, I2C and SPI are usually exposed through character devices that user-space libraries wrap.
- **Other operating systems** have the same pattern: device nodes with control requests, as in FreeBSD and macOS, differing in detail.

## Examples

**A counter device, step by step.** A misc device `/dev/counter` increments a counter on each write and returns its value on read. In `read`, the driver formats the number as text and returns it with `simple_read_from_buffer`. The first `cat` gets the text and the file offset advances to its length; the second read at that offset returns zero, so `cat` stops. Reopening the file resets the offset and shows the new value. Writing the driver took one structure, three functions and a registration call.

**A reset ioctl blocked by policy.** An `ioctl(fd, MY_RESET)` clears the device buffer. A tool running under a seccomp filter gets `EPERM`, because the filter allows `read` and `write` but not `ioctl`. The correct fix is to allow that one command number by value, not the whole system call.

**A short write.** A program writes 100 bytes to a buffer device that holds 64. A correct driver stores 64 and returns 64; the program loops and writes the rest, and the second call returns `ENOSPC`. A buggy driver returns 100 and silently drops 36 bytes, and nobody notices until data is missing.

**A 32-bit caller.** A structure containing a `long` has different sizes in a 32-bit process and in the 64-bit kernel, so the kernel reads the wrong fields. A conversion in `compat_ioctl`, or a redesign with fixed-width fields, fixes it. The second is better, because it removes the need for a translation to maintain.

## Related problems and ideas

### Related

- **The device model, sysfs and platform drivers** (the next topic) give a driver a place in the hierarchy and a way to expose attributes without ioctls.
- **Interrupts and workqueues** supply the events that wake blocked readers.
- **Locking** governs the shared state in the handlers.
- **Memory allocation and DMA** appear as soon as a device moves bulk data.

### Opposing approaches

- **sysfs attributes** hold that a single value should be a file, readable and writable with a shell and documented in one place. They are self-describing and need no special tools, but they handle one value at a time and are awkward for atomic multi-field changes.
- **netlink** gives structured, extensible messages with attributes that older and newer programs can ignore or understand. It is the standard for networking configuration and is heavier to implement than an ioctl.
- **io_uring commands** let a driver accept high-rate, asynchronous submission through the same ring as file I/O, which suits accelerators and storage. They are newer and less widely known.
- **User-space drivers** (VFIO, UIO, FUSE) move the device logic out of the kernel altogether, trading some performance and some safety margin for easier development and containment of bugs.

## Active research

Work in this area includes safer ways to write drivers, with Rust abstractions for misc and character devices; tooling that describes ioctl interfaces so that fuzzers such as syzkaller can generate valid calls; and moves to replace ioctl with structured interfaces. Static analysis for missing `__user` annotations, uninitialised copies and compatibility mismatches continues. The current state of Rust support for misc devices should be checked against the kernel release in use.

## Future direction

New drivers increasingly prefer sysfs for simple attributes, netlink for structured configuration and io_uring commands for high-rate submission, leaving ioctl for legacy and a few well-understood control paths. Rust drivers will wrap the same hooks with ownership rules that make the user-pointer and lifetime mistakes harder to write. For a learner, the interface remains the best first driver precisely because everything in it, a table, a private pointer, a checked copy, appears again in the harder topics.
