# eBPF internals and sched_ext: safely extending the kernel with verified programs

## Define the problem

The kernel is hard to change. Adding a feature means writing C that runs with full privilege, going through review and waiting for a release and then for distributions to ship it. Loadable modules shorten the path but carry the full risk: a bug is a kernel crash or a security hole, and every kernel version needs a rebuild. Yet operators need to observe and adjust kernel behaviour on production machines, quickly, with confidence that a mistake will not take the host down.

eBPF is the kernel's answer: a small virtual machine inside the kernel that runs programs supplied by user space, guaranteed by a verifier to terminate and to touch only memory they are allowed to. `sched_ext` pushes the same idea to its extreme, letting a BPF program *be* the CPU scheduler.

## History and approaches

**Classic BPF.** The Berkeley Packet Filter of 1992 was an in-kernel interpreter for tiny filter programs applied to packets, as used by `tcpdump`. It had two registers and no loops.

**Extended BPF.** Around 2014 (year and kernel version to verify) Alexei Starovoitov extended the design into a general-purpose, 64-bit virtual machine with eleven registers, a call interface and maps. The in-kernel interpreter was supplemented by a just-in-time compiler that turns programs into native code on the main architectures, so execution runs at near-native speed. Program types spread from packet filters to tracing (kprobes, tracepoints, perf events), security (seccomp, LSM), cgroup hooks, networking (tc, XDP, socket operations) and more.

**Safe by verification.** Instead of sandboxing at run time, the kernel checks the program once at load: it explores all paths, tracks the type and range of every register and stack slot, rejects out-of-bounds accesses, uninitialised reads, unbounded loops (bounded loops are allowed since 5.3, and helpers such as `bpf_loop` offer iteration with a verified bound) and pointer leaks. Verified programs may call only kernel-provided *helper functions* and, more recently, *kfuncs* (kernel functions exposed to BPF with type information).

**Portability.** Compiled BPF programs need the kernel's data structure layouts. BTF (BPF Type Format) is compact type information embedded in the kernel, and CO-RE (compile once, run everywhere) relocations let `libbpf` adjust field offsets when loading, so one binary runs across kernel versions (covered in the system-programming course).

**Beyond hooks to policy.** Later features let BPF *implement* kernel policy: TCP congestion control (`struct_ops`), scheduler behaviour and more. The `struct_ops` mechanism fills a table of kernel callbacks with BPF programs, which is the technique behind `sched_ext`.

## Current state

### The machine

A BPF program sees registers `r0` to `r10`: `r0` holds the return value and helper results, `r1` to `r5` carry arguments (and are clobbered by calls), `r6` to `r9` are callee-saved and `r10` is a read-only frame pointer into a 512-byte stack. Instructions are fixed 8-byte slots (with a 16-byte form for 64-bit constants): arithmetic, loads and stores, jumps, calls and exit. Programs are loaded with the `bpf(2)` system call, which takes the instruction array, a licence string (some helpers are GPL-only), the program type and BTF data. A successful load returns a file descriptor; attaching creates a *link*, which keeps the attachment alive and can be pinned to the BPF filesystem.

### The verifier in outline

The verifier first checks the control-flow graph (no unreachable code, no invalid jumps), then simulates execution along every path with abstract state. For each register it knows a type (scalar, pointer to context, pointer to a map value, pointer to the stack, pointer to a packet, a trusted kernel object and so on) and, for scalars, a possible range and known bits. Conditional branches refine ranges (after `if (x < 16)`, `x` is known to be below 16 on one side), so a bounds check by the program proves an access safe. Pointers that may be NULL (map lookup results) must be tested before use. State pruning merges equivalent states to keep the work bounded, with a complexity limit on the number of instructions processed; hitting the limit is a common reason for rejection.

A verification failure comes with a log of the register states along the rejected path, which is how developers diagnose it. The lab for this topic builds a miniature of this process with five register types and a handful of instructions.

### Maps, helpers and communication

Maps are kernel data structures shared between programs and user space: arrays, hash tables, per-CPU variants, LRU hashes, tries, ring buffers (`BPF_MAP_TYPE_RINGBUF`), and queue-like types. Programs update counters and send events; user space reads them through the `bpf` syscall. Helpers cover time, random numbers, current task information, perf output and probing memory safely. Tail calls and function calls let programs be composed. Spin locks, timers and kernel objects with reference tracking (acquire and release must pair, which the verifier enforces) extend what programs can do.

### Security model

Loading BPF requires privilege (`CAP_BPF` plus `CAP_PERFMON` or `CAP_NET_ADMIN` as needed), and unprivileged BPF is disabled by default on most distributions because of side-channel and verifier-bug risk. The JIT hardens against speculative execution and constant blinding is available. The verifier has been the source of vulnerabilities, since a bug in it can convert a malicious program into arbitrary kernel read and write, so it is a heavily fuzzed and reviewed component.

### sched_ext

`sched_ext` (merged in Linux 6.12, to verify) is a scheduler class whose policy is supplied by a BPF program. The kernel keeps the mechanics (context switching, accounting, CPU hotplug, the interface to tasks) and delegates decisions. A scheduler fills a `struct sched_ext_ops` with callbacks:

- `select_cpu`: pick a CPU when a task wakes, and optionally dispatch it straight away;
- `enqueue`: a task becomes runnable; put it into a *dispatch queue* (DSQ), either the global one, a per-CPU local one or a custom queue the scheduler created;
- `dispatch`: a CPU has run out of work; move tasks from custom queues to its local queue;
- `running`, `stopping`, `quiescent`, `runnable`: lifecycle notifications for accounting;
- `init` and `exit`: set up queues and report why the scheduler ended.

Helpers (kfuncs) such as `scx_bpf_dsq_insert`, `scx_bpf_dsq_move_to_local` and `scx_bpf_create_dsq` implement the operations. Safety comes from the framework: if the BPF scheduler misbehaves (a runnable task is not scheduled within a watchdog timeout, or the program returns errors), the kernel ejects it and falls back to the default scheduler, so a faulty scheduler degrades instead of hanging the machine. The project's `scx` repository provides sample schedulers (simple, central, and production-quality ones) and tools to load them, and `sched_ext` can be switched on and off at run time, with per-task opt-in through the scheduling policy.

Why it matters: schedulers for specific workloads (game and desktop latency, batch throughput, cache-aware placement) can be developed and deployed without rebuilding the kernel, and experiments run in hours. Large operators use it to try policies on fleets.

### Tooling

`bpftool` lists, dumps and loads programs, maps and links, shows JIT output and BTF; `libbpf` and language bindings (Rust `aya` and `libbpf-rs`, Go `cilium/ebpf`) handle loading; `bpftrace` offers one-liners for tracing; `clang` compiles C to BPF bytecode. The kernel's self-tests for BPF are large and are the reference for supported behaviour.

## Assessment: the good, the bad and the ugly

**The good.** eBPF gives observability and control with no kernel rebuild and with a safety guarantee strong enough to run in production. It performs well thanks to JIT and in-kernel data collection, and it has an active ecosystem. `sched_ext` shortens scheduler experiments from months to days and contains failures.

**The bad.** Writing programs that satisfy the verifier is a skill: code that is obviously correct may be rejected, and compilers can reorder code into patterns the verifier cannot follow. The interface (helpers, kfuncs, program types) changes between kernel versions, so portability depends on CO-RE and careful feature checks. Debugging inside the VM is limited.

**The ugly.** The verifier is a large, complex piece of kernel code that must be right for the security model to hold, and bugs have been exploited. Misuse of BPF by malware (rootkits, evasion) is a documented concern. `sched_ext` schedulers can be unfair or starve tasks, and the watchdog is a coarse backstop; correctness of policy is the author's job.

## Applications beyond this domain

- **Cloud-native networking and security**: load balancing, network policy, runtime security monitoring and observability products use eBPF at scale.
- **Performance engineering**: continuous profiling and latency tracing in production.
- **Virtualisation**: BPF programs filter and account guest traffic on the host (tc and XDP on tap and veth devices), and tracing of KVM exits uses the same probes.
- **Other platforms**: eBPF for Windows and standardisation efforts show the model spreading; the instruction set is documented in an IETF draft (to verify its status).
- **Operating-system research**: safe extensibility as a design principle, compared with microkernels and language-based safety.

## Examples

**A rejected program.** A tracing program reads a field of a task structure through a pointer from a helper. The verifier rejects it with a message that the pointer may be NULL at that instruction. Adding a check before the read, or using the CO-RE read helper, fixes it.

**A counter per process.** A program attached to a tracepoint increments an entry in a hash map keyed by process ID; a user-space tool reads and prints the top entries every second.

**A minimal sched_ext scheduler.** The sample "simple" scheduler puts every runnable task onto one global queue and lets each CPU pull from it, a first-come-first-served policy implemented in a few dozen lines. Loading it with the loader tool switches the system's scheduling; closing the tool returns control to the default scheduler.

**A watchdog ejection.** A scheduler that forgets to dispatch a queue leaves tasks runnable but never run; after the timeout the kernel disables it and logs the reason, and the machine continues on the default scheduler.

## Active research

Research and development include verifying the verifier (formal proofs of its abstract domains), faster and more precise range analysis, support for larger programs and loops, safe memory allocation for BPF programs, arena maps, more `struct_ops` hooks, and new scheduler designs built on `sched_ext`. Studies of verifier bugs and of program portability continue (to verify current work).

## Future direction

Expect more kernel policy to move to BPF (schedulers, memory management hooks, I/O control), better developer tools for diagnosing verifier rejections, richer type information for kfuncs, and a widening set of operating systems implementing compatible runtimes.
