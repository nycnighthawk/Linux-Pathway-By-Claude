# eBPF internals and sched_ext: safely extending the kernel with verified programs

## Define the problem

The kernel is hard to change. Adding a feature means writing C that runs with full privilege, passing review, waiting for a release, and then waiting again for distributions to ship it. Loadable modules shorten the path but carry the full risk: a bug is a kernel crash or a security hole, and every kernel version needs a rebuild. Yet operators need to observe and adjust kernel behaviour on production machines, quickly, with confidence that a mistake will not take the host down.

eBPF is the kernel's answer: a small virtual machine inside the kernel that runs programs supplied by user space, with a *verifier* that guarantees they terminate and touch only memory they are allowed to. `sched_ext` pushes the same idea to its extreme, letting a BPF program *be* the CPU scheduler. This essay follows the idea from a packet filter with two registers to a verified general-purpose machine, explains how the verifier works, and ends with the scheduler class that is built on top.

## History and approaches

### Classic BPF

The Berkeley Packet Filter of 1992 was an in-kernel interpreter for tiny filter programs applied to packets, as used by `tcpdump`. It had two registers and no loops. Its great idea was to ship a small program to the data, not copy every packet to the program.

### Extended BPF

Around 2014 (year and kernel version should be checked), Alexei Starovoitov extended the design into a general-purpose, 64-bit virtual machine with eleven registers, a call interface and maps. A just-in-time compiler turns programs into native code on the main architectures, so execution runs at near-native speed. Program types spread from packet filters to tracing (kprobes, tracepoints, perf events), security (seccomp, LSM), cgroup hooks, networking (tc, XDP, socket operations) and more.

### Safe by verification

Instead of sandboxing at run time, the kernel checks the program once, at load. It explores all paths, tracks the type and range of every register and stack slot, and rejects out-of-bounds accesses, uninitialised reads, unbounded loops and pointer leaks. Bounded loops have been allowed since 5.3, and helpers such as `bpf_loop` offer iteration with a verified bound. A verified program may call only kernel-provided *helper functions* and, more recently, *kfuncs*, which are kernel functions exposed to BPF with type information.

### Portability

Compiled BPF programs need the kernel's data-structure layouts. BTF (BPF Type Format) is compact type information embedded in the kernel, and CO-RE (compile once, run everywhere) relocations let `libbpf` adjust field offsets when it loads a program, so one binary runs across kernel versions. This is covered in the system-programming course.

### From hooks to policy

Later features let BPF *implement* kernel policy: TCP congestion control (through `struct_ops`), scheduler behaviour and more. The `struct_ops` mechanism fills a table of kernel callbacks with BPF programs, and it is the technique behind `sched_ext`. The pattern across the history: first a filter, then a tracer, then a policy engine, each step trusting the verifier with more.

## Current state

### The machine

A BPF program sees registers `r0` to `r10`. `r0` holds the return value and helper results. `r1` to `r5` carry arguments and are clobbered by calls. `r6` to `r9` are callee-saved, and `r10` is a read-only frame pointer into a 512-byte stack. Instructions are fixed 8-byte slots (with a 16-byte form for 64-bit constants) covering arithmetic, loads and stores, jumps, calls and exit. Programs are loaded with the `bpf(2)` system call, which takes the instruction array, a licence string (some helpers are GPL-only), the program type and BTF data. A successful load returns a file descriptor. Attaching creates a *link*, which keeps the attachment alive and can be pinned to the BPF filesystem.

### The verifier in outline

The verifier first checks the control-flow graph, rejecting unreachable code and invalid jumps. It then simulates execution along every path with abstract state. For each register it knows a type (scalar, pointer to context, pointer to a map value, pointer to the stack, pointer to a packet, a trusted kernel object and so on) and, for scalars, a possible range and the bits that are known. Conditional branches refine ranges: after `if (x < 16)`, `x` is known to be below 16 on one side, so a bounds check written by the program proves an access safe. Pointers that may be NULL, such as the results of map lookups, must be tested before use. State pruning merges equivalent states to keep the work bounded, and a complexity limit on the number of instructions processed means that hitting the limit is a common reason for rejection.

A verification failure comes with a log of the register states along the rejected path, which is how developers diagnose it. The lab for this topic builds a miniature of this process with five register types and a handful of instructions.

### Maps, helpers and communication

Maps are kernel data structures shared between programs and user space: arrays, hash tables, per-CPU variants, LRU hashes, tries, ring buffers (`BPF_MAP_TYPE_RINGBUF`) and queue-like types. Programs update counters and send events, and user space reads them through the `bpf` system call. Helpers cover time, random numbers, current-task information, perf output and safe probing of memory. Tail calls and function calls let programs be composed. Spin locks, timers and kernel objects with reference tracking, where acquire and release must pair and the verifier enforces it, extend what programs can do.

### Security model

Loading BPF requires privilege (`CAP_BPF` plus `CAP_PERFMON` or `CAP_NET_ADMIN` as needed), and unprivileged BPF is disabled by default on most distributions because of side-channel and verifier-bug risk. The JIT hardens against speculative execution, and constant blinding is available. The verifier has been the source of vulnerabilities, since a bug in it can turn a malicious program into arbitrary kernel read and write, so it is among the most heavily fuzzed and reviewed components of the kernel.

### sched_ext

`sched_ext` was merged into Linux 6.12 (the release should be checked). It is a scheduler class whose policy is supplied by a BPF program. The kernel keeps the mechanics (context switching, accounting, CPU hotplug, the interface to tasks) and delegates decisions. A scheduler fills a `struct sched_ext_ops` with callbacks.

- `select_cpu` picks a CPU when a task wakes, and may dispatch it straight away.
- `enqueue` is called when a task becomes runnable, and puts it into a *dispatch queue* (DSQ): the global one, a per-CPU local one, or a custom queue the scheduler created.
- `dispatch` is called when a CPU has run out of work, and moves tasks from custom queues to its local queue.
- `running`, `stopping`, `quiescent` and `runnable` are lifecycle notifications for accounting.
- `init` and `exit` set up queues and report why the scheduler ended.

Helpers (kfuncs) such as `scx_bpf_dsq_insert`, `scx_bpf_dsq_move_to_local` and `scx_bpf_create_dsq` implement the operations. Safety comes from the framework. If the BPF scheduler misbehaves, for example a runnable task is not scheduled within a watchdog timeout or the program returns errors, the kernel ejects it and falls back to the default scheduler, so a faulty scheduler degrades the machine instead of hanging it. The project's `scx` repository provides sample schedulers (simple, central, and production-quality ones) and tools to load them. `sched_ext` can be switched on and off at run time, with per-task opt-in through the scheduling policy.

It matters because schedulers for specific workloads (latency for games and desktops, throughput for batch jobs, cache-aware placement) can be developed and deployed without rebuilding the kernel, and experiments run in hours. Large operators use it to try policies on fleets.

### Tooling

`bpftool` lists, dumps and loads programs, maps and links, and shows JIT output and BTF. `libbpf` and language bindings (Rust `aya` and `libbpf-rs`, Go `cilium/ebpf`) handle loading, `bpftrace` offers one-liners for tracing, and `clang` compiles C to BPF bytecode. The kernel's BPF self-tests are large and are the reference for supported behaviour.

### The generalised pattern

Accept untrusted code, check it *once* with a static analysis that is conservative, then run it at full speed with a narrow set of permitted calls, and keep a kill switch for the cases the analysis cannot cover. The same structure underlies WebAssembly sandboxes and language-based safety systems.

## Assessment: the good, the bad and the ugly

**The good.** eBPF gives observability and control with no kernel rebuild and with a safety guarantee strong enough for production. It performs well thanks to the JIT and to in-kernel data collection, and it has an active ecosystem. `sched_ext` shortens scheduler experiments from months to days and contains failures.

**The bad.** Writing programs that satisfy the verifier is a skill: code that is obviously correct may be rejected, and compilers can reorder code into patterns the verifier cannot follow. The interface (helpers, kfuncs, program types) changes between kernel versions, so portability depends on CO-RE and careful feature checks. Debugging inside the virtual machine is limited.

**The ugly.** The verifier is a large, complex piece of kernel code that must be right for the security model to hold, and bugs have been exploited. Misuse of BPF by malware, in rootkits and for evasion, is a documented concern. `sched_ext` schedulers can be unfair or starve tasks, and the watchdog is a coarse backstop; the correctness of the policy is the author's job.

## Applications beyond this domain

- **Cloud-native networking and security.** Load balancing, network policy, runtime security monitoring and observability products use eBPF at scale.
- **Performance engineering.** Continuous profiling and latency tracing run in production.
- **Virtualisation.** BPF programs filter and account guest traffic on the host (tc and XDP on tap and veth devices), and the tracing of KVM exits uses the same probes.
- **Other platforms.** eBPF for Windows and standardisation efforts show the model spreading, and the instruction set is documented in an IETF draft (its status should be checked).
- **Operating-system research.** Safe extensibility is a design principle that can be compared with microkernels and with language-based safety.

## Examples

**A rejected program, step by step.** A tracing program reads a field of a task structure through a pointer returned by a helper. The verifier simulates the path and finds that, at the load instruction, the pointer may be NULL, so it rejects the program with a message that names the instruction and the register state. Adding a check before the read, or using the CO-RE read helper, fixes it. The log is the teaching tool: it shows exactly what the verifier believed.

**A counter per process.** A program attached to a tracepoint increments an entry in a hash map keyed by process ID. A user-space tool reads the map every second and prints the top entries, so the kernel does the counting and user space only the reporting.

**A minimal sched_ext scheduler.** The sample "simple" scheduler puts every runnable task onto one global queue and lets each CPU pull from it, a first-come-first-served policy implemented in a few dozen lines. Loading it with the loader tool switches the system's scheduling, and closing the tool returns control to the default scheduler.

**A watchdog ejection.** A scheduler that forgets to dispatch a queue leaves tasks runnable but never run. After the timeout, the kernel disables it and logs the reason, and the machine continues on the default scheduler.

## Related problems and ideas

### Related

- **Tracing and debugging** (earlier courses) share probes and maps with BPF tools.
- **XDP and the network driver** (the previous topic) are program attachment points.
- **Locking and RCU**: BPF maps use RCU and per-CPU data, and programs run in contexts with the restrictions covered earlier.
- **seccomp-bpf** (system-programming course) uses classic BPF for system-call filters.

### Opposing approaches

- **Loadable kernel modules** give full power and full risk. They suit hardware drivers, and they cannot offer the safety that lets BPF run on production hosts without review.
- **Rust for Linux** (the next topic) reaches for safety by the type system, at compile time and for code that is part of the kernel. BPF checks the code at load time and for code supplied from outside. The two are complementary.
- **User-space policy and daemons.** Many controls can be implemented in a user-space program that reads kernel state and writes settings. That is safer and slower, and it cannot make per-event decisions at kernel speed.
- **Language runtimes and WebAssembly in the kernel.** Other safe-extension designs exist, with different trade-offs between expressiveness, speed and the size of the trusted verifier or runtime.

## Active research

Research and development include verifying the verifier, with formal proofs of its abstract domains, faster and more precise range analysis, support for larger programs and loops, safe memory allocation for BPF programs, arena maps, more `struct_ops` hooks, and new scheduler designs built on `sched_ext`. Studies of verifier bugs and of program portability continue; current work should be checked against recent conference proceedings.

## Future direction

Expect more kernel policy to move to BPF (schedulers, memory-management hooks, I/O control), better developer tools for diagnosing verifier rejections, richer type information for kfuncs, and a widening set of operating systems implementing compatible runtimes. A learner who understands the verifier's idea, tracking what is known about each value along every path, will recognise it in many other safety tools.
