# Page allocator, slab, vmalloc and the DMA API: where kernel memory comes from

## Define the problem

Kernel code needs memory in many shapes. It may want a few dozen bytes for a small object, a page for a buffer, a megabyte that hardware must see at contiguous physical addresses, or a large table that only the CPU touches. It needs that memory fast, from any context including interrupt handlers, on machines with many CPUs, and without fragmenting the physical address space so badly that large requests start to fail. It must also know which memory a given device can reach, because some devices have narrow address lines, and it must keep the CPU's caches and the device's view of memory consistent.

No single allocator suits all of this, so the kernel layers several. This essay builds the picture from the bottom: how physical pages are managed, how small objects are carved from them, how large ranges are made contiguous in virtual address space, and how the DMA API connects memory to devices.

## History and approaches

### Zones and the buddy system

Physical memory is managed in pages, commonly 4 KiB. The page allocator groups free pages into blocks of 2^order pages and keeps a free list for each order. Allocation splits a larger block when needed, and freeing merges a block with its buddy, so contiguous space is rebuilt whenever possible. *Zones* partition memory by address constraints: a low zone for old devices that can address only 16 MiB, a zone addressable with 32 bits, the normal zone and, on some configurations, zones for movable pages and device memory.

### Slab allocators

Handing out whole pages is wasteful for small objects. Jeff Bonwick's slab idea, from Solaris, keeps caches of equally sized objects, so that allocation is a pointer pop and initialised objects can be reused. Linux has had three implementations: SLAB, SLUB (the default since 2.6.23, with per-CPU freelists and lower overhead) and SLOB for tiny systems. SLAB and SLOB have since been removed in favour of SLUB, and the exact release should be checked. `kmalloc` sits on a set of general-purpose caches in size classes.

### Virtually contiguous memory

Large allocations of physically contiguous pages fail when memory is fragmented. `vmalloc` assembles individually allocated pages into one contiguous range of *virtual* addresses by editing page tables. That is slower and uses TLB entries, but it succeeds when physically contiguous memory is not available. `kvmalloc` tries `kmalloc` first and falls back to `vmalloc`.

### DMA and the changing meaning of a physical address

Early drivers cast pointers to physical addresses and gave them to devices. IOMMUs, bounce buffers, cache-incoherent architectures and devices with narrow address ranges made that wrong. The DMA API abstracts it: the driver describes a device's capabilities and asks for memory or for a mapping, and the implementation chooses the right zone, remaps through an IOMMU if there is one, and manages cache maintenance.

### Contiguous allocator and memory cgroups

CMA reserves a region for devices that need large contiguous buffers, such as cameras and video codecs, while letting movable pages use it when it is idle. Memory cgroups account kernel allocations to the cgroup that triggered them (`__GFP_ACCOUNT`), so containers' kernel memory use can be limited. The pattern across the history: each layer was added to fix a failure of the one below it (waste, fragmentation, address constraints, coherence).

## Current state

### The page allocator

`alloc_pages(gfp, order)` returns a `struct page`, or a folio, the newer unit that represents one or more contiguous pages. `__get_free_pages` returns a kernel virtual address, and `__free_pages` and `free_pages` release. The order is the base-2 logarithm of the number of pages, with a maximum on the order of ten (4 MiB blocks with 4 KiB pages), so very large requests need CMA or vmalloc. Per-CPU page lists make order-0 allocations fast and nearly lock-free.

`/proc/buddyinfo` lists the number of free blocks of each order per zone, which shows fragmentation at a glance: plenty of free memory in low orders and none in high orders means that big contiguous requests will fail. Compaction migrates movable pages to rebuild higher-order blocks, and `/proc/pagetypeinfo` shows how pages are classified by mobility.

### GFP flags

Flags tell the allocator what it may do and where memory may come from.

- `GFP_KERNEL` is the normal flag. It may sleep, start reclaim and write back pages, so it is for process context with no spinlock held.
- `GFP_ATOMIC` may not sleep, may dip into reserves, and may fail more often. It is for interrupt context and for code under spinlocks.
- `GFP_NOWAIT` does not sleep, does not use reserves, and fails quickly.
- `GFP_USER` and `GFP_HIGHUSER_MOVABLE` are for user-visible pages.
- Zone modifiers `__GFP_DMA` and `__GFP_DMA32` select low zones; modern drivers should use the DMA API instead.
- Behaviour modifiers include `__GFP_ZERO` (zero the memory), `__GFP_NOWARN`, `__GFP_RETRY_MAYFAIL`, `__GFP_NORETRY` and `__GFP_ACCOUNT`.

Code in the I/O path must not recurse into the filesystem or block layer when reclaiming. That was historically expressed with `GFP_NOFS` and `GFP_NOIO`; the preferred modern form marks a scope with `memalloc_nofs_save` and `memalloc_noio_save`, so that every allocation inside it behaves correctly.

### Slab and kmalloc

`kmalloc(size, gfp)` returns physically contiguous memory of at least that size. `kzalloc` zeroes it, `kmalloc_array` and `kcalloc` check the multiplication for overflow, `krealloc` resizes, and `kfree` releases and accepts NULL. For many objects of one type, a driver creates a cache with `kmem_cache_create(name, size, align, flags, ctor)` and then uses `kmem_cache_alloc` and `kmem_cache_free`. Dedicated caches give better locality, per-type statistics in `/proc/slabinfo` (and the `slabtop` tool), and hardening options such as separate caches for user-copyable data and per-type isolation in recent kernels.

Debugging aids include `CONFIG_SLUB_DEBUG` with the `slub_debug=` boot options, which adds red zones and poisoning; KASAN, which detects overflows and use after free on slab objects; and `kmemleak`, which finds leaked objects by scanning memory for pointers. Managed allocations (`devm_kzalloc`) tie memory to a device and free it automatically on removal, as in the device-model topic.

### vmalloc and ioremap

`vmalloc(size)` returns virtually contiguous, physically scattered memory, suitable for big tables that only the CPU uses. It may sleep, and it is not usable for DMA by devices that need physical contiguity, although a device with scatter-gather support and the right mapping can still use it. `ioremap` maps *device* memory (registers, BARs) into kernel virtual space with the right cache attributes. It is a different thing from `vmalloc` even though both use the same kind of address space. `kvmalloc` is the usual choice for arrays whose size depends on user input, since it handles both small and large sizes.

### The DMA API

First the driver declares what the device can address, with `dma_set_mask_and_coherent(dev, DMA_BIT_MASK(32))` and a fallback to a smaller mask if it fails. Then there are two families of mapping.

- **Coherent (consistent) mappings.** `dma_alloc_coherent(dev, size, &dma_handle, gfp)` returns a CPU pointer and a bus address in `dma_handle`. The CPU and the device see each other's writes without explicit maintenance, and on non-coherent architectures the kernel uses uncached or write-combined mappings to achieve this. They suit long-lived shared structures such as descriptor rings.
- **Streaming mappings.** For buffers that already exist, `dma_map_single(dev, ptr, size, direction)`, or `dma_map_sg` for scatter-gather lists, returns a bus address and transfers ownership to the device. The CPU must not touch the buffer until `dma_unmap_single`, or until `dma_sync_single_for_cpu` hands it back temporarily. The direction (`DMA_TO_DEVICE`, `DMA_FROM_DEVICE`, `DMA_BIDIRECTIONAL`) selects the cache operations. Always check the result with `dma_mapping_error`.

The rules are firm. Use the DMA API on the device structure, and never pass the result of `virt_to_phys` to a device. Do not DMA to stack memory, or to vmalloc memory without mapping each page. Align and size streaming buffers to cache lines on non-coherent systems. With an IOMMU, the bus address is an I/O virtual address, and an out-of-range device access faults instead of corrupting memory. Without one, a device with a narrow mask may be served through a bounce buffer (`swiotlb`), which costs a copy.

### Observing and failing

Failure paths must be handled. A `GFP_KERNEL` request can still fail for high orders, and `GFP_ATOMIC` often does under pressure. The out-of-memory killer acts on user processes when reclaim fails, but a kernel allocation that cannot be satisfied returns NULL, and a driver that ignores that crashes. Fault injection (`failslab`, `fail_page_alloc`) exercises these paths in testing.

### The generalised pattern

Choose by *shape*: pages for bulk, slab for many small objects of a kind, vmalloc for large virtual ranges that the CPU alone touches, and the DMA API for anything a device touches. Choose flags by *context*: may this code sleep? The same two questions, what shape and what context, organise nearly every allocation decision in the kernel.

## Assessment: the good, the bad and the ugly

**The good.** The layering gives each need an appropriate tool. Per-CPU caches make the fast paths scale, and tools such as `slabtop`, `buddyinfo`, `kmemleak`, KASAN and fault injection make behaviour visible.

**The bad.** The number of allocation functions and flags is large, and the wrong choice (a sleeping allocation in atomic context, the wrong zone) gives bugs that appear only under memory pressure. Fragmentation makes large contiguous allocations unreliable on long-running systems. DMA correctness depends on the architecture and IOMMU configuration, which a developer's test machine may not have.

**The ugly.** Cache-coherence errors corrupt data silently on architectures that need maintenance. A DMA into freed memory writes over someone else's data and raises no fault. Missing `dma_mapping_error` checks, double unmaps and mismatched directions show up only on particular hardware. Slab memory is a favourite target for exploitation, which is why allocators gained freelist hardening and randomisation.

## Applications beyond this domain

- **User-space allocators** (glibc malloc, jemalloc, tcmalloc) reuse the same ideas: size classes, per-thread caches and slab-like arenas.
- **Hypervisors** manage guest memory with huge pages and ballooning and use allocators that care about contiguity for efficient nested paging. The DMA and IOMMU rules apply to device assignment.
- **Containers** and memory cgroups account kernel memory to workloads.
- **Embedded video and camera pipelines** depend on CMA for contiguous buffers. Bootlin's embedded kernel training covers these topics with labs [src: bootlin-training e6ecf9b848fe95b8].
- **Databases and network stacks** tune around NUMA placement and huge pages.

## Examples

**An atomic allocation.** An interrupt handler needs a small descriptor and calls `kmalloc(sizeof(*d), GFP_ATOMIC)`. When memory is tight the call returns NULL, and the handler drops the event and increments a counter instead of dereferencing a null pointer.

**A descriptor ring, step by step.** A driver allocates a 4 KiB ring with `dma_alloc_coherent` and gets back a CPU pointer and a bus address. It programs the bus address into the device's base register, fills ring entries from the CPU, executes a write barrier so the entries are visible, and then writes the doorbell register. Each step has a reason, and leaving out the barrier gives a device that reads stale descriptors on some machines only.

**A streaming transmit.** A network driver maps each outgoing buffer `DMA_TO_DEVICE`, stores the returned handle in a descriptor, and unmaps it in the completion path. Forgetting the unmap leaks IOMMU space; unmapping with the wrong direction on a non-coherent CPU invalidates the wrong cache lines.

**Fragmentation.** On a host with weeks of uptime, a driver's order-8 `GFP_KERNEL` allocation fails although gigabytes are free. `buddyinfo` shows no free blocks above order 4. Switching to `kvmalloc` plus scatter-gather, or reserving CMA at boot, removes the dependency on contiguous memory.

## Related problems and ideas

### Related

- **Locking and context** (earlier topics) decide which `gfp` flag is legal.
- **PCI drivers** use the DMA API for descriptors and data.
- **KASAN, kmemleak and fault injection** find allocation bugs.
- **NUMA placement** in the system-programming course decides which node's memory is used.

### Opposing approaches

- **Static allocation.** Embedded and safety-critical code often avoids dynamic allocation after start-up. It removes failure paths and fragmentation, at the cost of fixed limits and wasted memory.
- **Pre-allocated pools (mempools).** A driver that cannot fail, such as one in the writeback path, reserves objects in advance. It guarantees progress and holds memory that might be used elsewhere.
- **Huge pages and reservation.** Instead of fighting fragmentation at run time, a system reserves huge pages at boot. It is predictable and inflexible.
- **User-space I/O frameworks.** Frameworks that manage their own pinned, huge-page-backed memory (hugepage pools in DPDK) bypass the kernel's allocators to avoid mapping costs, at the price of complexity in the application.

## Active research

Work includes memory-tagging-based hardening, the conversion of kernel interfaces from pages to folios, memory tiering for CXL and persistent memory, better compaction, per-cgroup slab accounting and hardened allocators with type-based isolation, plus Rust allocation abstractions with fallible APIs. The status of each should be checked against recent kernel releases.

## Future direction

Expect continued migration from pages to folios, more type-segregated allocation as a security measure, DMA mappings tied to IOMMU domains by default, and allocation interfaces that make failure explicit in the type signature. The ideas a learner should keep are stable: allocate by shape and by context, handle the failure, and let the DMA API, not a physical address, describe memory to a device.
