# Kernel performance regressions: finding out why the new kernel is slower

## Define the problem

A functional regression announces itself with an error. A performance regression does not: the new kernel is simply slower, by a few percent or by a factor, on some workload and some hardware. The people who notice it are operators comparing fleets, benchmark services, or developers measuring their own change. Nothing crashes, so the evidence is numbers, and numbers are noisy: CPU frequency, caches, other tenants, memory placement and run-to-run variance can hide a one percent loss or fake a five percent one.

The task has four parts: show that the regression is real, show where the time goes, find the change that caused it, and decide what to do. Each needs different tools, and mistakes in the first part waste the rest.

## History and approaches

**Benchmarks as regression tests.** Kernel developers have long run macro-benchmarks (kernel compile times, database and web workloads, `hackbench`, `netperf`, `fio`) and micro-benchmarks (`lmbench`, `will-it-scale`, `stress-ng`) on release candidates. Intel's 0-day and LKP robot runs a large matrix of benchmarks on patch sets from mailing lists and branches and reports regressions by mail, often within days. Other labs (distribution QA, cloud providers, Phoronix-style test suites) publish comparisons.

**Profiling tools.** `perf` (merged in 2.6.31) became the standard sampling profiler: hardware performance counters trigger samples with the program counter and optionally the call stack; `perf stat` counts events, `perf record` and `perf report` find hot functions, `perf diff` compares two profiles. Brendan Gregg's flame graphs made stack samples readable, and differential flame graphs show where a profile changed. `ftrace` and `bpftrace` complement sampling with exact event timing and off-CPU analysis (why threads wait).

**Bisection with a threshold.** The same `git bisect` as for functional bugs works if the oracle is a benchmark run with a pass threshold, repeated enough times to be reliable.

**Systematic methodologies.** Gregg's USE method (utilisation, saturation, errors per resource) and top-down microarchitecture analysis (for example Intel's TMA) provide checklists that avoid staring at the wrong layer.

## Current state

### Establish that the regression is real

- **Control the environment.** Fix CPU frequency governor and turbo (or measure them), disable or pin SMT, pin the benchmark to CPUs and memory nodes with `taskset` and `numactl`, stop noisy services, use the same firmware, microcode, kernel configuration and compiler. Differences in configuration (a debug option on, a security mitigation changed) are the most common false regressions. Compare `/proc/cmdline` and `/sys/devices/system/cpu/vulnerabilities/*` between kernels.
- **Repeat.** Run each side many times, interleaved, and compare distributions, not single numbers. Report mean, standard deviation and a confidence interval, or use a statistical test; a difference smaller than the run-to-run spread is not evidence.
- **Reduce the benchmark.** Find the smallest workload that still shows the effect, because it makes everything after it faster.
- **Check the whole machine.** `vmstat`, `iostat`, `mpstat` and `turbostat` show whether the slowdown is CPU, I/O, memory or frequency, and whether it is the same on other hardware.

### Locate where the time goes

1. **Counters.** `perf stat -d` reports cycles, instructions, IPC, branch and cache misses, context switches and page faults. A drop in IPC with the same instruction count points at stalls (memory, locks); more instructions point at more work.
2. **Sampling.** `perf record -g -- workload`, then `perf report` or a flame graph. Compare shares of samples per function between the good and bad kernel (shares, because total sample counts differ with run length). `perf diff` automates it. The lab in this topic does this by hand with two summaries.
3. **Callers and context.** If a function like a spinlock slow path grows, the question becomes who is calling it more: `perf record -g` gives call graphs; `perf report --no-children` or `--children` and caller views show them. For lock contention, `perf lock` and `lockstat` show which lock and which call sites.
4. **Off-CPU time.** If the workload is slower but CPU use falls, threads are waiting: use scheduler events, `offcputime` from the BCC or bpftrace collections, or `perf sched`, to see what they wait for (locks, I/O, timers).
5. **Tracing for exact counts.** `ftrace` function counts or `bpftrace` histograms show how many times a function ran and how long it took.

### Typical causes

- **Locking changes**: a lock made global or coarser, a different spinlock algorithm, contention that only appears at high core counts (the queued-spinlock slow path in the lab data).
- **Memory management**: changes to allocators, page reclaim, THP behaviour, NUMA balancing, cgroup accounting.
- **Scheduler changes**: load balancing and wake-up placement alter cache locality and latency.
- **Security mitigations**: speculative-execution fixes cost cycles on system calls and context switches; their defaults depend on CPU model and kernel version. `mitigations=off` on a test machine helps to diagnose, never to ship.
- **Debug and configuration**: lockdep, KASAN, tracing options or `CONFIG_PREEMPT` choices.
- **Compiler and toolchain**: inlining and layout changes can move a benchmark by several percent without any code change.
- **Hardware and firmware**: microcode updates, power settings, kernel's handling of new CPU features.

### Find and fix the change

With a stable reproducer, bisect: build each candidate, run the benchmark enough times, and mark good or bad by comparing to a threshold set with the measured noise in mind. The commit found may be an unrelated cleanup that changed inlining or cache-line alignment; check with `perf annotate`, `pahole` for structure layout (padding and false sharing) and by reverting the commit on the bad tip. A report to the maintainers should include: benchmark and exact command, hardware and firmware, kernel versions and configs, the measured effect with confidence, the profile evidence and the bisected commit. The kernel's regression policy gives such reports weight, and a maintainer may revert or fix.

## Assessment: the good, the bad and the ugly

**The good.** A mature toolkit exists: counters, sampling, tracing and visual comparison are all in the tree and freely available. Automated bots catch many regressions before release. A clear methodology turns a vague complaint into a specific function and a specific commit.

**The bad.** Performance is multi-dimensional: a change that speeds one workload slows another, so one benchmark does not settle "regression". Noise, thermal and firmware effects mean results do not transfer between machines. Bisecting is slow when each step takes an hour.

**The ugly.** False regressions from environment drift waste maintainer time; real regressions only appear at scale (hundreds of cores, large memory) that few developers can test. Mitigation trade-offs are contested. Benchmark results quoted without configuration are not reproducible, and sometimes a bisected commit is "innocent" and only moved an alignment.

## Applications beyond this domain

- **Cloud and virtualisation operators** compare guest and host kernels for performance after every update; the cost of exits, interrupts and paravirtual devices appears in the same profiles.
- **Database and web service tuning** uses the same top-down approach on applications.
- **Compilers and runtimes** have continuous performance tracking with the same statistical methods.
- **Capacity planning** needs reliable baselines for each software release.
- **Hardware design** validates microarchitecture changes with performance regression suites.

## Examples

**A lock slow path.** A network benchmark loses 10% throughput. Profiles show the queued-spinlock slow path rising from under 2% of samples to over 25%. Callers point at a dequeue function. The bisected commit restructured the wait loop; a fix restores the fast path.

**A configuration mismatch.** A "regression" disappears when the benchmark runs with the same kernel configuration: the new kernel was built with `CONFIG_DEBUG_PREEMPT` enabled.

**A mitigation.** A system-call-heavy benchmark slows by 8% on a certain CPU after an update. `cat /sys/devices/system/cpu/vulnerabilities/*` shows a new mitigation enabled by default for that CPU model. The decision is policy, not a bug.

**Noise.** Two runs differ by 4%. Fifty interleaved runs show a standard deviation of 3% and no significant difference; the developer saves a day of bisection.

## Related problems and ideas

- **git bisect** (first course) with a benchmark oracle.
- **Debugging tools** (ftrace, lockdep, printk) explain mechanisms once the function is known.
- **Locking and RCU** (earlier topic) explain most contention regressions.
- **Memory allocation** and **NAPI** topics describe common hot paths.
- **eBPF** tools collect data with low overhead in production.

## Active research

Research directions include statistical methods for detecting small regressions in noisy data with few runs, automated root-cause localisation from profile differences, continuous benchmarking in CI with change-point detection, performance models of locks and schedulers at high core counts, and tools that explain the effect of code layout changes on performance (to verify the state of each).

## Future direction

Expect performance testing to be part of the patch pipeline by default, with robot reports and automatic bisection, and with standard formats for benchmark metadata so results are comparable. More analysis will come from hardware counters and top-down methods built into `perf`.
