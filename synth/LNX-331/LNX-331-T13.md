# Kernel performance regressions: finding out why the new kernel is slower

## Define the problem

A functional regression announces itself with an error. A performance regression does not: the new kernel is simply slower, by a few percent or by a factor, on some workload and some hardware. The people who notice are operators comparing fleets, benchmark services, or developers measuring their own change. Nothing crashes, so the evidence is numbers, and numbers are noisy. CPU frequency, caches, other tenants and memory placement, along with ordinary run-to-run variance, can hide a one percent loss or fake a five percent one.

The task has four parts: show that the regression is real, show where the time goes, find the change that caused it, and decide what to do. Each part needs different tools, and mistakes in the first waste the rest. This essay takes the parts in that order and builds a method from them.

## History and approaches

### Benchmarks as regression tests

Kernel developers have long run macro-benchmarks (kernel compile times, database and web workloads, `hackbench`, `netperf`, `fio`) and micro-benchmarks (`lmbench`, `will-it-scale`, `stress-ng`) on release candidates. Intel's 0-day and LKP robot runs a large matrix of benchmarks on patch sets from mailing lists and branches and reports regressions by mail, often within days. Other labs, among them distribution quality-assurance teams, cloud providers and public benchmark suites, publish comparisons.

### Profiling tools

`perf`, merged in 2.6.31, became the standard sampling profiler. Hardware performance counters trigger samples with the program counter and, optionally, the call stack. `perf stat` counts events, `perf record` and `perf report` find hot functions, and `perf diff` compares two profiles. Brendan Gregg's flame graphs made stack samples readable, and differential flame graphs show where a profile changed. `ftrace` and `bpftrace` complement sampling with exact event timing and with off-CPU analysis, which asks why threads wait.

### Bisection with a threshold

The same `git bisect` that finds functional bugs works if the oracle is a benchmark run with a pass threshold, repeated enough times to be reliable.

### Systematic methodologies

Gregg's USE method (utilisation, saturation and errors, per resource) and top-down microarchitecture analysis, such as Intel's TMA, provide checklists that avoid staring at the wrong layer. The progression across this history: first measure total time, then sample to find the hot spot, then bisect to find the commit, then use a method so that each step is chosen and not guessed.

## Current state

### Establish that the regression is real

- **Control the environment.** Fix the CPU frequency governor and turbo (or measure them), disable or pin SMT, pin the benchmark to CPUs and memory nodes with `taskset` and `numactl`, stop noisy services, and use the same firmware, microcode, kernel configuration and compiler. Differences in configuration, such as a debug option left on or a security mitigation changed, are the most common false regressions. Compare `/proc/cmdline` and `/sys/devices/system/cpu/vulnerabilities/*` between kernels.
- **Repeat.** Run each side many times, interleaved, and compare distributions, not single numbers. Report mean, standard deviation and a confidence interval, or use a statistical test. A difference smaller than the run-to-run spread is not evidence.
- **Reduce the benchmark.** Find the smallest workload that still shows the effect, because it makes everything after it faster.
- **Check the whole machine.** `vmstat`, `iostat`, `mpstat` and `turbostat` show whether the slowdown is CPU, I/O, memory or frequency, and whether it is the same on other hardware.

### Locate where the time goes

1. **Counters.** `perf stat -d` reports cycles, instructions, IPC, branch and cache misses, context switches and page faults. A drop in IPC with the same instruction count points at stalls on memory or locks, while more instructions point at more work.
2. **Sampling.** `perf record -g -- workload`, then `perf report` or a flame graph. Compare shares of samples per function between the good and bad kernels, shares because total sample counts differ with run length, and let `perf diff` automate it. The lab for this topic does the comparison by hand with two summaries.
3. **Callers and context.** If a function such as a spinlock slow path grows, the question becomes who is calling it more. `perf record -g` gives call graphs, and `perf report --no-children` or `--children` and the caller views show them. For lock contention, `perf lock` and `lockstat` show which lock and which call sites.
4. **Off-CPU time.** If the workload is slower but CPU use falls, threads are waiting. Scheduler events, `offcputime` from the BCC or bpftrace collections, or `perf sched` show what they wait for: locks, I/O or timers.
5. **Tracing for exact counts.** `ftrace` function counts or `bpftrace` histograms show how many times a function ran and how long it took.

### Typical causes

- **Locking changes.** A lock made global or coarser, a different spinlock algorithm, or contention that appears only at high core counts, such as the queued-spinlock slow path in the lab data.
- **Memory management.** Changes to allocators, page reclaim, THP behaviour, NUMA balancing or cgroup accounting.
- **Scheduler changes.** Load balancing and wake-up placement alter cache locality and latency.
- **Security mitigations.** Speculative-execution fixes cost cycles on system calls and context switches, and their defaults depend on the CPU model and kernel version. `mitigations=off` on a test machine helps to diagnose, and is never to be shipped.
- **Debug and configuration.** Lockdep, KASAN, tracing options or `CONFIG_PREEMPT` choices.
- **Compiler and toolchain.** Inlining and layout changes can move a benchmark by several percent without any code change.
- **Hardware and firmware.** Microcode updates, power settings, and the kernel's handling of new CPU features.

### Find and fix the change

With a stable reproducer, bisect: build each candidate, run the benchmark enough times, and mark good or bad by comparing to a threshold set with the measured noise in mind. The commit found may be an unrelated cleanup that changed inlining or cache-line alignment. Check with `perf annotate`, with `pahole` for structure layout (padding and false sharing), and by reverting the commit on the bad tip. A report to the maintainers should include the benchmark and its exact command, the hardware and firmware, the kernel versions and configurations, the measured effect with its confidence, the profile evidence and the bisected commit. The kernel's regression policy gives such reports weight, and a maintainer may revert or fix.

### The generalised pattern

Prove it is real, narrow it to a function, narrow it to a commit, explain the mechanism, and report with evidence. The same funnel, from symptom to mechanism, applies to any performance problem in any system.

## Assessment: the good, the bad and the ugly

**The good.** A mature toolkit exists: counters, sampling, tracing and visual comparison are all in the tree and freely available. Automated bots catch many regressions before release. A clear methodology turns a vague complaint into a specific function and a specific commit.

**The bad.** Performance is multi-dimensional: a change that speeds one workload slows another, so one benchmark does not settle what counts as a regression. Noise, thermal effects and firmware mean that results do not transfer between machines. Bisecting is slow when each step takes an hour.

**The ugly.** False regressions from environment drift waste maintainer time, and real regressions that appear only at scale, with hundreds of cores and large memory, are hard because few developers can test there. Mitigation trade-offs are contested. Benchmark results quoted without their configuration are not reproducible, and sometimes a bisected commit is innocent and has only moved an alignment.

## Applications beyond this domain

- **Cloud and virtualisation operators** compare guest and host kernels for performance after every update, and the cost of exits, interrupts and paravirtual devices shows up in the same profiles.
- **Database and web-service tuning** uses the same top-down approach on applications.
- **Compilers and runtimes** have continuous performance tracking with the same statistical methods.
- **Capacity planning** needs reliable baselines for each software release.
- **Hardware design** validates microarchitecture changes with performance regression suites.

## Examples

**A lock slow path, step by step.** A network benchmark loses 10% throughput. Profiles show the queued-spinlock slow path rising from under 2% of samples to over 25%, which says that something is contending. Call graphs point at a dequeue function. Bisection finds a commit that restructured the wait loop, and a fix restores the fast path. Each step narrowed the question: is it real, which function, which caller, which commit.

**A configuration mismatch.** A regression disappears when the benchmark runs with the same kernel configuration: the new kernel had been built with `CONFIG_DEBUG_PREEMPT` enabled. A comparison of the two configuration files would have shown it in a minute.

**A mitigation.** A system-call-heavy benchmark slows by 8% on a certain CPU after an update. Reading the files under `/sys/devices/system/cpu/vulnerabilities/` shows that a new mitigation is enabled by default for that CPU model. The decision is one of policy, not a bug.

**Noise.** Two runs differ by 4%. Fifty interleaved runs show a standard deviation of 3% and no significant difference, so the developer saves a day of bisection.

## Related problems and ideas

### Related

- **git bisect** (the first course) with a benchmark as the oracle.
- **Debugging tools** (ftrace, lockdep, printk) explain mechanisms once the function is known.
- **Locking and RCU** (an earlier topic) explain most contention regressions.
- **Memory allocation and NAPI** (earlier topics) describe common hot paths.

### Opposing approaches

- **Do not chase small regressions.** A small slowdown may be the price of a feature or a security fix. Some argue that the kernel should accept it, and that effort is better spent on large effects. The counter-view holds that small losses compound across releases.
- **Whole-fleet monitoring instead of lab benchmarks.** Production telemetry sees real workloads on real hardware, which a lab cannot. It is noisy and slower to bisect, and it finds the regressions that matter to someone.
- **Microbenchmarks versus application benchmarks.** Microbenchmarks isolate a mechanism and mislead about whole-application effect. Application benchmarks reflect users and hide the cause.
- **Formal performance models.** Instead of measuring, some research derives expected performance from a model of locks and caches. The approach scales poorly to real code, and yet it explains why the measured results look as they do.

## Active research

Research directions include statistical methods for detecting small regressions in noisy data with few runs, automated root-cause localisation from profile differences, continuous benchmarking in CI with change-point detection, performance models of locks and schedulers at high core counts, and tools that explain the effect of code-layout changes on performance. The state of each should be checked against recent conference proceedings.

## Future direction

Expect performance testing to be part of the patch pipeline by default, with robot reports and automatic bisection, and with standard formats for benchmark metadata so that results are comparable. More analysis will come from hardware counters and top-down methods built into `perf`. The durable skill is the funnel: a claim is not a regression until it survives repetition, and not understood until it is tied to a mechanism.
