# Rust for Linux modules: a second language for the kernel

## Define the problem

The kernel is written in C, and a large share of its serious bugs are the kind that C makes easy: use after free, double free, out-of-bounds access, unchecked errors, missing unlocks, data races and integer overflows. Static analysers, sanitizers and review catch many of them, but each class costs real security patches year after year. Drivers are the largest and least reviewed part of the tree, and the part most often attacked through buggy hardware or malicious input.

The proposal behind Rust for Linux is to let new driver code be written in a language whose type system rules out many of those classes at compile time, while keeping the performance and control that a kernel needs. That takes more than a compiler flag. The kernel has no standard library, has its own allocator and locking rules, and offers thousands of C interfaces that safe code can reach only through carefully designed wrappers. This essay builds the idea in four steps: why a second language was proposed, how it entered the tree, what the bridge between the two languages looks like, and what Rust does and does not change in a driver.

## History and approaches

### The case for a safer language

Memory-safety bugs are a recurring majority of vulnerabilities in large C and C++ code bases, a finding reported by several major vendors. The kernel community had long discussed alternatives. C++ was rejected for reasons of runtime and conventions, but Rust, with no garbage collector and no runtime, looked workable.

### The path in

Rust for Linux began as an out-of-tree project in 2020, with Miguel Ojeda as its leading maintainer. After several rounds of patch series and discussion at the Linux Plumbers Conference and the Maintainers Summit, basic infrastructure was merged for 6.1 in late 2022 (the release should be checked), and the set of abstractions has grown with each release. At first the support was labelled an experiment, and the project has since moved toward treating it as a regular part of the kernel; the current status should be confirmed in the kernel's own documentation.

### Early drivers

Notable Rust drivers and prototypes include an Android Binder implementation, the Apple GPU driver for Asahi Linux, GPU drivers for other vendors (Nova for NVIDIA GPUs and Tyr for Arm Mali), block and network PHY drivers, and the `rnull` sample block device. The pattern is *new* drivers, not rewrites of core code, because a new driver can adopt the abstractions from the start, with no legacy to carry.

### Debate and policy

The effort raised objections: extra maintenance for C maintainers whose interfaces Rust wraps, build requirements, and doubts about long-term support. The policy that emerged keeps C maintainers in control of C interfaces and puts the burden of the Rust bindings on Rust developers, with the aim that Rust code does not block C changes. The policy has been disputed in specific cases, and its current form should be read from the project's documentation and recent discussion. The history shows a general lesson: a technical change to a shared code base is also a negotiation about who bears the cost.

## Current state

### How it fits into the build

`CONFIG_RUST` enables the support. It requires a specific range of `rustc` versions, `bindgen` (which generates Rust declarations from C headers) and, in practice, a Clang or LLVM-based toolchain for certain features. `make LLVM=1 rustavailable` reports whether the tools are adequate. The minimum versions are documented in the kernel's process documentation and move with releases. The Rust code builds against `core` and `alloc`-like pieces maintained within the tree and not against the full standard library, because the kernel provides its own memory management and has no threads in the usual sense. `make rustdoc` builds API documentation for the abstractions, and `make rust-analyzer` generates project files for IDE support.

### The structure

- **`rust/kernel/`** is the `kernel` crate, the safe abstractions. It contains allocation types (`KBox` and `KVec`, with fallible allocation), `Arc` reference counting, locks (`Mutex`, `SpinLock`) that *own* the data they protect, `Opaque` and `ARef` for C objects, device and driver registration traits, PCI, platform and DRM abstractions, `miscdevice`, I/O mappings with bounds-checked access, and error types that mirror `errno`.
- **`rust/bindings/`** holds raw, `unsafe` bindings generated by `bindgen`. Drivers do not call these directly.
- **`rust/macros/`** holds procedural macros such as `module!`, which declares module metadata and the init and exit hooks.
- **`samples/rust/`** holds small working modules, including a minimal "hello" module and miscdevice and platform-driver samples.

A module has a recognisable shape: a `module!` declaration with the type, name, author, description and licence; a type that implements the `kernel::Module` trait, whose `init` returns `Result<Self>`; and a `Drop` implementation that serves as the exit hook. Logging uses `pr_info!` and its relatives, or `dev_info!`.

### What Rust changes in driver code

- **Ownership and RAII.** A resource acquired in `probe` is a value, and when it goes out of scope, `Drop` releases it. Error paths need no explicit cleanup, which removes the leaks and double frees of C goto chains.
- **Locks own data.** In `Mutex<T>` the data is reachable only through a guard obtained by locking, and the guard unlocks when dropped, so forgetting to lock or unlock does not compile.
- **Absence is a type.** `Option<T>` forces handling of the "not found" case, and `Result<T, E>` with the `?` operator makes ignoring an error visible.
- **Lifetimes and the borrow checker** reject references that outlive their owner, which is the dangling-pointer bug.
- **Checked arithmetic and bounds-checked indexing** make overflow and out-of-range access explicit.
- **`Send` and `Sync`** mark what can cross threads, so data races on shared mutable state are rejected in safe code.

None of this removes the need for `unsafe`. Talking to hardware (register access through raw addresses), calling C functions, and implementing the abstractions themselves all require it. The rule is to confine `unsafe` to small blocks, each with a `// SAFETY:` comment stating why its preconditions hold. Reviewers audit those blocks, and the rest of the driver is safe code. The lab for this topic asks which bug classes are removed by which mechanism, and which remain.

### Fallibility and panics

Kernel Rust differs from application Rust in two ways. Allocation must be fallible, so `Box::new` is replaced by variants that return `Result` on failure, since there is no global allocator that aborts. And a `panic!` is a kernel bug, because it reports and kills the task or oopses depending on configuration. Code therefore uses `Result` for all expected failures, and the project is working to make panics rarer by avoiding indexing and `unwrap` calls in kernel code.

### Writing and testing a driver

A new driver typically implements a bus trait (for example the platform or PCI driver trait), provides an ID table and a `probe`, and registers through a `module_platform_driver!`-style macro. Where a needed abstraction is missing, the developer adds it to the `kernel` crate, which means designing a safe API over a C interface and getting the C subsystem maintainer to review it. Tests use the same tools as for C code (virtual machines, KUnit, kselftest), and KUnit supports Rust doctests and tests in the kernel crate.

### The generalised pattern

Keep a small trusted core of `unsafe` code that establishes invariants, and expose it through an interface whose types make the invariants impossible to violate in safe code. The same structure underlies the safe abstractions of every systems language that has an escape hatch.

## Assessment: the good, the bad and the ugly

**The good.** Whole classes of memory and concurrency bugs are rejected at compile time in safe code. Drivers become more declarative, with less error-path boilerplate. Strong typing documents ownership and locking rules that in C live in comments. Early Rust drivers report fewer defects of the targeted kind.

**The bad.** The abstractions cover only part of the kernel, so many drivers cannot be written yet. The toolchain requirements, build time and a second language raise costs for maintainers and contributors. Mixed-language review needs people who know both. Safe wrappers can be wrong, and a bug in an `unsafe` block affects every user of the abstraction.

**The ugly.** Disagreements about process and maintainership have been public and bruising, and some maintainers have stepped back from Rust-facing interfaces. Churn in C interfaces breaks bindings, and the question of who fixes it is not always settled. The language itself, with its feature gates and compiler-version dependence, is still moving.

## Applications beyond this domain

- **Hypervisors and virtual machine monitors.** Firecracker, Cloud Hypervisor and the rust-vmm crates are written in Rust for the same safety reasons on the user-space side, and the Firecracker documentation lists the guest kernel features it needs [src: firecracker-docs eaa6832031a86735]. Safer kernel-side drivers complement them.
- **Operating-systems research and products.** Rust is used in several kernels and low-level systems (Redox, and parts of Windows and Android).
- **Embedded and safety-critical systems** adopt Rust for memory safety with no runtime.
- **Security engineering.** Memory-safe languages are part of national and industry guidance on reducing vulnerability classes.
- **Education.** Mapping each C bug class to its Rust mechanism is a useful exercise for any systems programmer.

## Examples

**A hello module.** A sample module logs a message in `init` and another in `drop`. Loading and unloading it shows the pair in `dmesg`. The module declares its licence in the `module!` macro, and leaving it out is a compile error.

**A guarded counter.** A driver stores a counter in `Mutex<u32>`. Incrementing requires `let mut g = m.lock(); *g += 1;`, and the lock is released at the end of the scope. There is no way to read the counter without holding the lock, so the C bug of forgetting to take it cannot be written.

**An error path.** `probe` allocates a buffer, maps registers and requests an interrupt, each of them a value with a destructor. When the interrupt request fails and `?` returns the error, the buffer and the mapping are released automatically, in reverse order, with no cleanup code in `probe`.

**An `unsafe` audit.** Reviewers of a new PCI abstraction check each `unsafe` block's `SAFETY` comment: that the address is within the mapped BAR, that the mapping outlives the accessor, and that the type matches the register width.

## Related problems and ideas

### Related

- **Memory allocation and DMA** (an earlier topic) are exposed through fallible and typed APIs.
- **Locking and RCU** (an earlier topic) map to lock types that own data, while RCU abstractions are still evolving.
- **KASAN, lockdep and fuzzing** still apply to Rust code, because `unsafe` blocks and C interfaces remain.
- **Formal verification** of kernel code is a complementary line of work.

### Opposing approaches

- **Keep writing C, with better tools.** Static analysis, sanitizers, `__counted_by` annotations, scope-based cleanup and stricter compiler warnings narrow the gap without a second language. Critics of Rust argue that this is cheaper and that C talent is plentiful. Supporters reply that the tools reduce the bug classes but cannot rule them out.
- **eBPF.** Another route to safer extension, which uses verification at load time instead of types at compile time. It suits small programs from outside the kernel, and not full drivers.
- **C++ or other languages.** Rejected in the past for runtime and convention reasons, and sometimes proposed again, so the choice of Rust is not unanimous even among those who want a safer language.
- **Microkernels and user-space drivers.** If a driver runs outside the kernel, its bugs cannot corrupt kernel memory whatever the language. This costs context switches and a different architecture.

## Active research

Research and engineering cover making the abstractions complete enough for GPU and network drivers, compile-time checking of lock order, reducing the use of `unsafe` through better type design, formal modelling of the abstractions' safety contracts, panic-free subsets of the language, and shared build infrastructure with C, including cross-language inlining with link-time optimisation. The state of each is moving and should be checked against current LWN coverage.

## Future direction

Expect a growing share of new drivers in Rust, more subsystems offering official abstractions, requirements pinned to distribution-packaged compilers, and clearer rules for which interfaces C maintainers must keep compatible. The core of the kernel will remain C for a long time. For a learner, the transferable skill is the design of a safe interface over an unsafe one.
