# Rust for Linux modules: a second language for the kernel

## Define the problem

The kernel is written in C, and a large share of its serious bugs are the kind C makes easy: use after free, double free, out-of-bounds access, unchecked errors, missing unlocks, data races and integer overflows. Static analysers, sanitizers and review catch many, but each bug class costs real security patches year after year. Drivers are the largest and least reviewed part of the tree, and the part most often attacked through buggy hardware or malicious input.

The proposal behind Rust for Linux is to let new driver code be written in a language whose type system rules out many of those classes at compile time, while keeping the performance and control a kernel needs. That needs more than a compiler flag: the kernel has no standard library, its own allocator and locking rules, and thousands of C interfaces that safe code can only use through carefully designed wrappers.

## History and approaches

**The case for a safer language.** Memory-safety bugs are a recurring majority of vulnerabilities in large C and C++ code bases, a finding reported by several major vendors. The kernel community had long discussed alternatives; C++ was rejected for reasons of runtime and conventions, but Rust, with no garbage collector and no runtime, looked workable.

**The path in.** Rust for Linux was started as an out-of-tree project (2020), with Miguel Ojeda as the leading maintainer. After several patch-series rounds and a discussion at the Linux Plumbers and Maintainers Summits, basic infrastructure was merged for 6.1 (late 2022, to verify), and the set of abstractions has grown each release. Initially the support was labelled an experiment; the project has since moved towards treating it as a regular part of the kernel (to verify the current status).

**Early drivers.** Notable Rust drivers and prototypes include an Android Binder implementation, the Apple GPU driver for Asahi Linux, GPU drivers for other vendors (Nova for NVIDIA GPUs, Tyr for Arm Mali), block and network PHY drivers and the `rnull` block device sample. The pattern is new drivers, not rewrites of core code.

**Debate and policy.** The effort raised objections: extra maintenance for C maintainers whose interfaces Rust wraps, build requirements, and doubts about long-term support. The policy that emerged keeps the C maintainers in control of C interfaces and puts the burden of the Rust bindings on Rust developers, with the aim that Rust code does not block C changes (this has been disputed in specific cases, to verify).

## Current state

### How it fits into the build

`CONFIG_RUST` enables the support; it requires a specific range of `rustc` versions, `bindgen` (which generates Rust declarations from C headers), and, in practice, a Clang or LLVM-based toolchain for certain features. `make LLVM=1 rustavailable` tells whether the tools are adequate. The minimum versions are documented in the kernel's process documentation and move with releases. The Rust code builds with `core` and `alloc`-like pieces maintained within the tree, not the full standard library, since the kernel provides its own memory management and has no threads in the usual sense. `make rustdoc` builds API documentation for the abstractions, and `make rust-analyzer` generates the project files for IDE support.

### The structure

- **`rust/kernel/`**: the `kernel` crate, the safe abstractions: allocation (`KBox`, `KVec` with fallible allocation), `Arc` reference counting, locks (`Mutex`, `SpinLock`) that *own* the data they protect, `Opaque` and `ARef` for C objects, device and driver registration traits, PCI, platform and DRM abstractions, `miscdevice`, I/O mappings with bounds-checked access, and error types mirroring `errno`.
- **`rust/bindings/`**: raw, `unsafe` bindings generated by `bindgen`. Drivers do not call these directly.
- **`rust/macros/`**: procedural macros such as `module!`, which declares module metadata and the init and exit hooks.
- **`samples/rust/`**: small working modules, including a minimal "hello" module and miscdevice and platform driver samples.

A module looks like: `module! { type: MyModule, name: "my_module", author: "...", description: "...", license: "GPL" }`, a type implementing the `kernel::Module` trait whose `init` returns `Result<Self>`, and a `Drop` implementation for cleanup (the exit hook). Logging uses `pr_info!` and friends or `dev_info!`.

### What Rust changes in driver code

- **Ownership and RAII.** A resource acquired in `probe` is a value; when it goes out of scope, `Drop` releases it. Error paths need no explicit cleanup, which removes the leak and double-free bugs of C goto chains.
- **Locks own data.** In `Mutex<T>` the data is reachable only through a guard obtained by locking, and the guard unlocks when dropped, so forgetting to lock or unlock does not compile.
- **Absence is a type.** `Option<T>` forces handling of the "not found" case. `Result<T, E>` plus the `?` operator makes ignoring an error visible.
- **Lifetimes and the borrow checker** reject references that outlive their owner, which is the dangling pointer bug.
- **Checked arithmetic and bounds-checked indexing** make overflow and out-of-range access explicit.
- **`Send` and `Sync`** traits mark what can cross threads, so data races on shared mutable state are rejected in safe code.

None of this removes the need for `unsafe`. Talking to hardware (register access through raw addresses), calling C functions, and implementing the abstractions themselves all need it. The rule is to confine `unsafe` to small blocks, each with a `// SAFETY:` comment stating why the preconditions hold. Reviewers audit those blocks; the rest of the driver is safe code. The lab in this topic asks which bug classes are removed by which mechanism, and which remains.

### Fallibility and panics

Kernel Rust differs from application Rust in two ways. Allocation must be fallible, so `Box::new` is replaced by variants that return `Result` on failure; there is no global allocator that aborts. And a `panic!` is a kernel bug (it reports and kills the task or oopses depending on configuration), so code uses `Result` for all expected failures, and the project is working on making panics rarer by avoiding indexing and unwrap calls in kernel code.

### Writing and testing a driver

A new driver typically implements a bus trait (for example the platform or PCI driver trait), providing an ID table and `probe`, and registers with the `module_platform_driver!`-style macros. Where a needed abstraction is missing, the developer adds it to the `kernel` crate, which means designing a safe API over a C interface and getting the C subsystem maintainer to review it. Tests use the same tools as C code (virtual machines, KUnit, kselftest); KUnit supports Rust doctests and tests in the kernel crate.

## Assessment: the good, the bad and the ugly

**The good.** Whole classes of memory and concurrency bugs are rejected at compile time in safe code. Drivers get more declarative, with less error-path boilerplate. Strong typing documents ownership and locking rules that in C live in comments. Early Rust drivers report fewer defects of the targeted kind.

**The bad.** The abstractions cover only part of the kernel, so many drivers cannot be written yet. The toolchain requirements, build time and a second language raise costs for maintainers and contributors. Mixed-language review needs people who know both. Safe wrappers can be wrong; a bug in an `unsafe` block affects every user of the abstraction.

**The ugly.** Disagreements about process and maintainership have been public and bruising, with maintainers resigning or declining to review Rust-facing interfaces in some cases. Interface churn in C breaks bindings, and the "who fixes it" question is not always settled. The language itself (feature gates, compiler version dependence) is still moving.

## Applications beyond this domain

- **Hypervisors and virtual machine monitors**: Firecracker, Cloud Hypervisor and the rust-vmm crates are written in Rust for the same safety reasons on the user-space side; the Firecracker documentation lists the guest kernel features it needs [src: firecracker-docs eaa6832031a86735]. Safer kernel-side drivers complement this.
- **Operating systems research and products**: Rust is used in several kernels and low-level systems (Redox, parts of Windows and Android).
- **Embedded and safety-critical systems** adopt Rust for memory safety with no runtime.
- **Security engineering**: memory-safe languages are part of national and industry guidance on reducing vulnerability classes.
- **Education**: the exercise of mapping each C bug class to its Rust mechanism is useful for any systems programmer.

## Examples

**A hello module.** A sample module logs a message in `init` and another in `drop`. Loading and unloading it shows the pair in `dmesg`. The module declares its licence in the `module!` macro; omitting it is a compile error.

**A guarded counter.** A driver stores a counter in `Mutex<u32>`; incrementing requires `let mut g = m.lock(); *g += 1;`, and the lock is released at the end of the scope. There is no way to read the counter without the lock.

**An error path.** `probe` allocates a buffer, maps registers and requests an interrupt, each a value with a destructor. When the interrupt request fails and `?` returns the error, the buffer and mapping are released automatically.

**An `unsafe` audit.** Reviewers of a new PCI abstraction check each `unsafe` block's SAFETY comment: that the address is within the mapped BAR, that the mapping outlives the accessor, and that the type matches the register width.

## Related problems and ideas

- **Memory allocation and DMA** (earlier topic) are exposed through fallible and typed APIs.
- **Locking and RCU** (earlier topic) map to lock types that own data; RCU abstractions are still evolving.
- **eBPF** is another route to safer extension, using verification instead of types.
- **KASAN, lockdep and fuzzing** still apply to Rust code.
- **Formal verification** of kernel code is a complementary line of work.

## Active research

Research and engineering cover making the abstractions complete enough for GPU and network drivers, compile-time checking of locking order, reducing the use of `unsafe` through better type design, formal modelling of the abstractions' safety contracts, panic-free subsets of the language, and shared build infrastructure with C (cross-language inlining with LTO). The state of each is moving and should be checked against current LWN coverage (to verify).

## Future direction

Expect a growing share of new drivers in Rust, more subsystems offering official abstractions, requirements pinned to distribution-packaged compilers, and clearer rules for which interfaces C maintainers must keep compatible. The core of the kernel will remain C for a long time.
