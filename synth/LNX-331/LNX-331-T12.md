# Bring-up on a real board: from power-on to a shell on new hardware

## Define the problem

A new board arrives, or a prototype of one: a processor, memory, flash and a handful of peripherals, and no operating system that knows about it. The task is to make Linux run on it. Everything the emulator hid is now the developer's job: the order in which clocks, power rails and pins must be set up; the exact memory timings; the boot ROM's rules about where it looks for code; the voltage levels of a debug connector; hardware errata; a flash that must be programmed by some tool. And when it fails, nothing prints.

Bring-up is the discipline of making that process systematic. The principle is to get one reliable way of seeing what happens (a serial console), then one reliable way of loading new code (a fast iteration loop), then to add one subsystem at a time while keeping the loop short.

## History and approaches

**Board support code.** Early embedded Linux ports put board-specific C files in the kernel for every product. The arm tree in particular accumulated hundreds of such files, which led to the move to device tree: the board is described in data, and one kernel image supports many boards. Bring-up work today is therefore mostly writing a `.dts` file, plus bootloader configuration, plus the occasional driver fix or new driver.

**The boot chain.** Most SoCs follow a similar sequence. A mask ROM in the chip runs at reset and looks, according to pins or fuses, for a boot image on an SD or eMMC card, SPI flash, USB or network, and loads it into on-chip RAM. That first stage (often U-Boot's SPL, or a vendor loader) initialises DRAM and loads a larger bootloader into it. The bootloader (U-Boot, barebox, or a UEFI implementation such as EDK2 on server-class boards) initialises further hardware and loads the kernel, a device tree and optionally an initramfs, then jumps to the kernel. Secure boot, trusted firmware layers (for example Arm Trusted Firmware) and a secure OS may sit in between.

**Tools for visibility.** The serial console is the first and most important. When it is silent, a JTAG or SWD debug probe allows stopping the processor and examining memory and registers; logic analysers and oscilloscopes show signals; a bench power supply with current measurement shows whether the board draws plausible power.

**Fast iteration.** Flashing a card for every build is slow. The standard solution is network boot: the bootloader fetches the kernel and device tree from a TFTP server, and the kernel mounts its root filesystem over NFS or from an initramfs. This turns a build-test cycle into seconds. Bootlin's embedded Linux training builds this setup in its labs, first on QEMU, then on real boards [src: bootlin-training f3a97ec6e8a54058].

## Current state

### A bring-up sequence

1. **Read the documentation and the schematic.** Know which UART the console is, the boot-source pins, the voltage domains, the reset and power-on sequence, and the DRAM part. If a vendor reference or evaluation board exists, start from its device tree and bootloader and change only what differs.
2. **Establish the console.** Connect a USB-serial adapter at the board's logic level (3.3 V is common, 1.8 V and 5 V exist; a wrong level can damage the board or adapter), ground first, TX to RX and RX to TX. The usual settings are 115200 baud, 8 data bits, no parity, one stop bit. Power the board and capture output with a terminal program (`picocom`, `minicom`, `screen`) from the start so early messages are not lost.
3. **Get a bootloader running.** Build U-Boot for the board (many boards have a `*_defconfig`), place SPL and U-Boot where the boot ROM looks, and watch for the banner. If nothing appears, check the boot-source pins, the image format the ROM expects (some require a header), the console pin mux and clock settings in SPL.
4. **Boot a kernel the fast way.** In U-Boot configure the network (`setenv ipaddr`, `setenv serverip`), fetch with `tftpboot` the kernel image and DTB, set `bootargs` with `console=` and `root=`, and start with `booti` (arm64) or `bootz` (arm32), passing the DTB address. `fdt addr` and `fdt print` inspect the blob in memory.
5. **See early kernel output.** Add `earlycon` with the right UART type and address (for example `earlycon=uart8250,mmio32,0x...`) and a `console=` for the full driver. If the kernel starts but prints nothing, the DTB's `chosen/stdout-path` or clocks for the UART are the likely cause.
6. **Bring up subsystems one at a time.** Memory (check the reported size against the DRAM part), clocks and reset controllers, pin control, GPIO, interrupt controller, timers, then buses (I2C, SPI), storage (SD, eMMC), Ethernet, USB and so on. After each step, boot, check `dmesg` for errors and for deferred probes (`/sys/kernel/debug/devices_deferred`), look at the clock tree (`/sys/kernel/debug/clk/clk_summary`) and pin usage (`/sys/kernel/debug/pinctrl/`).
7. **Persist.** Once the board boots, move the kernel and DTB into the permanent boot medium, build a root filesystem with Buildroot or Yocto, and write down the procedure so it is repeatable.

### Writing the device tree

The board file includes the SoC's `.dtsi` and adds what the board adds: memory node, `chosen` node with `stdout-path`, enabled peripherals (`status = "okay"`), regulators and their constraints, pin configuration groups (`pinctrl-0`) for each peripheral, GPIO assignments for LEDs and buttons, PHY and transceiver settings, and clock overrides. Bindings document the required properties; `dt-validate` checks them. Most bring-up bugs are device-tree bugs: a missing regulator, the wrong pin group, a PHY reset GPIO with the wrong polarity, a clock that is gated.

### Typical failure modes by stage

| Stage | Symptom | Likely cause |
|---|---|---|
| ROM | no output at all, board draws little current | wrong boot-source setting, image missing or malformed, power rail off |
| SPL | banner, then hang | DRAM timing or training failure, wrong clock |
| Bootloader | prompt works, kernel will not load | wrong load address, network not configured, image format |
| Kernel early | output stops after "Starting kernel" | wrong DTB, missing `earlycon`, wrong console device |
| Kernel late | panic or missing devices | deferred probes, missing regulators or clocks, wrong pins |
| Userspace | no init or root | root filesystem or NFS options wrong |

### Safety and care

Work with the board unpowered when connecting probes. Check logic levels before connecting a serial adapter. Use a current-limited bench supply for prototypes. Protect against static. Do not flash bootloader images that are unverified into the only boot medium of a board that cannot be recovered; keep a recovery path (USB boot mode or a switchable boot source).

## Assessment: the good, the bad and the ugly

**The good.** With a vendor reference, a mainline device tree and U-Boot, a new board can often run Linux in a day. The tools (serial, TFTP, `earlycon`, sysfs debug files) are cheap and universal. The skills transfer to any board, and the work is visible as a small number of text files.

**The bad.** Documentation can be incomplete or under NDA, errata surprise even good engineers, and mainline kernel support lags for new SoCs, so vendor trees fork. Debugging without a console, or when DRAM is not up, needs special equipment and patience. Hardware and software defects interact: a flaky power rail looks like a kernel bug.

**The ugly.** Vendor kernels with thousands of out-of-tree patches, device trees that do not pass validation, bootloaders that are closed binaries, and update paths that were never designed. Time can vanish on a fault that turns out to be a single swapped wire or an incorrect pull-up.

## Applications beyond this domain

- **Server and cloud hardware** bring-up for arm64 platforms follows the same chain with UEFI and Arm Trusted Firmware.
- **Virtualisation labs**: new boards are tested with KVM on arm64 once Linux boots, and QEMU board models let developers prepare device trees before silicon arrives.
- **Industrial and automotive systems** add certification, secure boot and update-in-the-field requirements to the same steps.
- **Hobbyist and education boards** (Raspberry Pi class) make the sequence accessible for learning.
- **Hardware security research** uses the same visibility tools to study boot chains.

## Examples

**A silent board.** A prototype shows no output. The developer measures current (low), finds the boot-source straps set to a missing SPI flash, switches them to SD and gets the SPL banner.

**A wrong DTB.** The kernel prints nothing after `Starting kernel`. Adding `earlycon` with the address from the board's UART node shows messages and a complaint about an unknown machine; the DTB was for a sibling board.

**A missing regulator.** The Ethernet driver defers forever. `devices_deferred` names the PHY; the regulator that powers it is absent from the device tree. Adding the regulator node and its `vin-supply` link fixes the probe.

**A network boot loop.** The developer edits the device tree, rebuilds, copies the DTB to the TFTP directory and resets the board: the cycle takes under a minute.

## Active research

Areas of activity include better board-lab automation (remote power control, serial capture and flashing for CI), upstream support for new SoCs and the validation of device trees against schemas, firmware standardisation (UEFI and device tree on Arm, SystemReady), and open boot firmware efforts such as coreboot-style stages and open DRAM training (to verify the status of each).

## Future direction

Expect more boards to boot a mainline kernel from day one, with vendors submitting device trees and drivers earlier, and more standardised firmware interfaces that let one distribution image boot on many boards. Remote board farms will make hardware testing routine for upstream developers.
