# Bring-up on a real board: from power-on to a shell on new hardware

## Define the problem

A new board arrives, or a prototype of one: a processor, memory, flash and a handful of peripherals, and no operating system that knows about it. The task is to make Linux run on it. Everything the emulator hid is now the developer's job. There is an order in which clocks, power rails and pins must be set up, exact memory timings to get right, a boot ROM with its own rules about where it looks for code, voltage levels on a debug connector, hardware errata, and a flash that must be programmed by some tool. And when it fails, nothing prints.

Bring-up is the discipline of making that process systematic. The principle is to get one reliable way of seeing what happens (a serial console), then one reliable way of loading new code (a fast iteration loop), and then to add one subsystem at a time while keeping the loop short. This essay develops the principle in that order, after a short history of why bring-up today means writing data, not code.

## History and approaches

### Board support code

Early embedded Linux ports put board-specific C files in the kernel for every product. The Arm tree in particular accumulated hundreds of such files, which led to the move to the device tree: the board is described in data, and one kernel image supports many boards. Bring-up work today is therefore mostly writing a `.dts` file, plus bootloader configuration, plus the occasional driver fix or new driver.

### The boot chain

Most systems on a chip follow a similar sequence. A mask ROM in the chip runs at reset and looks, according to pins or fuses, for a boot image on an SD or eMMC card, SPI flash, USB or the network, and loads it into on-chip RAM. That first stage (often U-Boot's SPL, or a vendor loader) initialises the DRAM and loads a larger bootloader into it. The bootloader (U-Boot, barebox, or a UEFI implementation such as EDK2 on server-class boards) initialises further hardware and loads the kernel, a device tree and optionally an initramfs, then jumps to the kernel. Secure boot, trusted firmware layers (Arm Trusted Firmware, for example) and a secure OS may sit in between. Each stage exists because the previous one has too little memory or too little knowledge to do the next job.

### Tools for visibility

The serial console is the first and most important tool. When it is silent, a JTAG or SWD debug probe allows stopping the processor and examining memory and registers. Logic analysers and oscilloscopes show signals, and a bench power supply with current measurement shows whether the board draws plausible power.

### Fast iteration

Flashing a card for every build is slow. The standard solution is network boot: the bootloader fetches the kernel and device tree from a TFTP server, and the kernel mounts its root filesystem over NFS or from an initramfs. That turns a build-and-test cycle into seconds. Bootlin's embedded Linux training builds this setup in its labs, first on QEMU and then on real boards [src: bootlin-training f3a97ec6e8a54058]. The lesson of the whole history is that the speed of the loop, more than any single technique, decides how fast bring-up goes.

## Current state

### A bring-up sequence

1. **Read the documentation and the schematic.** Know which UART is the console, the boot-source pins, the voltage domains, the reset and power-on sequence, and the DRAM part. If a vendor reference or evaluation board exists, start from its device tree and bootloader and change only what differs.
2. **Establish the console.** Connect a USB-serial adapter at the board's logic level (3.3 V is common, 1.8 V and 5 V exist, and a wrong level can damage the board or the adapter), with ground first, then TX to RX and RX to TX. The usual settings are 115200 baud, 8 data bits, no parity, one stop bit. Power the board and capture output with a terminal program (`picocom`, `minicom`, `screen`) from the start so early messages are not lost.
3. **Get a bootloader running.** Build U-Boot for the board (many boards have a `*_defconfig`), place SPL and U-Boot where the boot ROM looks, and watch for the banner. If nothing appears, check the boot-source pins, the image format the ROM expects (some require a header), and the console pin mux and clock settings in SPL.
4. **Boot a kernel the fast way.** In U-Boot, configure the network (`setenv ipaddr`, `setenv serverip`), fetch the kernel image and DTB with `tftpboot`, set `bootargs` with `console=` and `root=`, and start with `booti` (arm64) or `bootz` (arm32), passing the DTB address. `fdt addr` and `fdt print` inspect the blob in memory.
5. **See early kernel output.** Add `earlycon` with the right UART type and address (for example `earlycon=uart8250,mmio32,0x...`) and a `console=` for the full driver. If the kernel starts but prints nothing, the DTB's `chosen/stdout-path` or the clocks for the UART are the likely cause.
6. **Bring up subsystems one at a time.** Start with memory (check the reported size against the DRAM part), then clocks and reset controllers, pin control, GPIO, the interrupt controller and timers, then buses (I2C, SPI), storage (SD, eMMC), Ethernet, USB and so on. After each step, boot and check `dmesg` for errors and for deferred probes (`/sys/kernel/debug/devices_deferred`), and look at the clock tree (`/sys/kernel/debug/clk/clk_summary`) and pin usage (`/sys/kernel/debug/pinctrl/`).
7. **Persist.** Once the board boots, move the kernel and DTB onto the permanent boot medium, build a root filesystem with Buildroot or Yocto, and write down the procedure so that it is repeatable.

### Writing the device tree

The board file includes the SoC's `.dtsi` and adds what the board adds: a memory node, a `chosen` node with `stdout-path`, enabled peripherals (`status = "okay"`), regulators and their constraints, pin-configuration groups (`pinctrl-0`) for each peripheral, GPIO assignments for LEDs and buttons, PHY and transceiver settings, and clock overrides. Bindings document the required properties, and `dt-validate` checks them. Most bring-up bugs are device-tree bugs: a missing regulator, the wrong pin group, a PHY reset GPIO with the wrong polarity, or a clock that is gated.

### Typical failure modes by stage

| Stage | Symptom | Likely cause |
|---|---|---|
| ROM | no output at all, board draws little current | wrong boot-source setting, image missing or malformed, power rail off |
| SPL | banner, then hang | DRAM timing or training failure, wrong clock |
| Bootloader | prompt works, kernel will not load | wrong load address, network not configured, image format |
| Kernel early | output stops after "Starting kernel" | wrong DTB, missing `earlycon`, wrong console device |
| Kernel late | panic or missing devices | deferred probes, missing regulators or clocks, wrong pins |
| Userspace | no init or root | root filesystem or NFS options wrong |

### Safety and care

Work with the board unpowered when connecting probes. Check logic levels before connecting a serial adapter. Use a current-limited bench supply for prototypes, and protect against static. Do not flash unverified bootloader images into the only boot medium of a board that cannot be recovered, and keep a recovery path (a USB boot mode or a switchable boot source).

### The generalised pattern

Make failure *visible* first, make iteration *fast* second, and add capability in *small, verified steps* third. A table of symptoms by stage turns a silent board into a short list of suspects. The same method serves server firmware, phone bring-up and FPGA soft cores.

## Assessment: the good, the bad and the ugly

**The good.** With a vendor reference, a mainline device tree and U-Boot, a new board can often run Linux in a day. The tools (serial, TFTP, `earlycon`, the sysfs debug files) are cheap and universal. The skills transfer to any board, and the work is visible as a small number of text files.

**The bad.** Documentation can be incomplete or under NDA, errata surprise even good engineers, and mainline kernel support lags for new SoCs, so vendor trees fork. Debugging without a console, or when the DRAM is not up, needs special equipment and patience. Hardware and software defects interact: a flaky power rail looks like a kernel bug.

**The ugly.** Vendor kernels carry thousands of out-of-tree patches, device trees do not pass validation, bootloaders are closed binaries, and update paths were never designed. Time can vanish on a fault that turns out to be a single swapped wire or an incorrect pull-up.

## Applications beyond this domain

- **Server and cloud hardware.** Bring-up for arm64 platforms follows the same chain, with UEFI and Arm Trusted Firmware.
- **Virtualisation labs.** New boards are tested with KVM on arm64 once Linux boots, and QEMU board models let developers prepare device trees before silicon arrives.
- **Industrial and automotive systems** add certification, secure boot and update-in-the-field requirements to the same steps.
- **Hobbyist and education boards**, of the Raspberry Pi class, make the sequence accessible for learning.
- **Hardware security research** uses the same visibility tools to study boot chains.

## Examples

**A silent board, step by step.** A prototype shows no output. The developer measures the current, finds it low, reads the schematic and finds that the boot-source straps select a SPI flash that is not fitted. Switching them to SD gets the SPL banner on the console. The sequence is the method: measure, read, change one thing, observe.

**A wrong DTB.** The kernel prints nothing after `Starting kernel`. Adding `earlycon` with the address from the board's UART node shows messages and a complaint about an unknown machine, because the DTB was for a sibling board.

**A missing regulator.** The Ethernet driver defers for ever. `devices_deferred` names the PHY, and the regulator that powers it is absent from the device tree. Adding the regulator node and its supply link fixes the probe.

**A network boot loop.** The developer edits the device tree, rebuilds, copies the DTB to the TFTP directory and resets the board. The cycle takes under a minute, so ten experiments fit into the time one SD-card flash would take.

## Related problems and ideas

### Related

- **The device model, device tree and platform drivers** (an earlier topic) provide the vocabulary.
- **arm64 cross-build and QEMU virt** (the previous topic) is the rehearsal for this step.
- **Boot testing and CI** can include boards in a lab for regression runs.
- **Yocto and Buildroot** automate the root filesystem and image creation.

### Opposing approaches

- **Use a vendor's kernel and be done.** It is the fastest way to a working product and the slowest way to a maintainable one, since security updates and new kernel features become the team's own work.
- **Emulate first, hardware later.** A board model in QEMU lets software be developed before silicon exists. It captures the structure, not the errata, and a model can be wrong in the same way as the driver written against it.
- **Open firmware stages.** Efforts such as coreboot-style stages replace closed vendor loaders with open ones, at the price of reverse-engineering DRAM training and vendor secrets.
- **Treat the board as a black box with UEFI and ACPI.** Server-class Arm platforms that follow standards boot a generic distribution image with no board-specific work, which is the ideal that device-tree boards are far from.

## Active research

Areas of activity include better board-lab automation (remote power control, serial capture and flashing for CI), upstream support for new SoCs and the validation of device trees against schemas, firmware standardisation (UEFI and device tree on Arm, SystemReady), and open boot-firmware efforts including open DRAM training. The status of each should be checked against current project pages.

## Future direction

Expect more boards to boot a mainline kernel from day one, with vendors submitting device trees and drivers earlier, and more standardised firmware interfaces that let one distribution image boot on many boards. Remote board farms will make hardware testing routine for upstream developers. For a learner, the sequence in this essay is the durable part: console, loader, fast loop, then one subsystem at a time.
