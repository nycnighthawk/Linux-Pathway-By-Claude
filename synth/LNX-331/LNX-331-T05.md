# Kernel locking: spinlocks, mutexes, RCU and lockdep

## Define the problem

The Linux kernel runs on many CPUs at once. The same code path can be entered from a system call on one CPU, an
interrupt handler on another, and a softirq or workqueue on a third, and preemption can stop a thread in the middle
of an update. Any shared structure (a list of network devices, a page-cache tree, a scheduler run queue) must stay
consistent under all of those interleavings. The constraints are tight:

- some contexts **cannot sleep** (hard interrupts, code holding a spinlock, regions with preemption disabled), so
  they need locks that wait by spinning;
- other contexts hold a lock across I/O or memory allocation, where spinning would waste a CPU for milliseconds;
- read-mostly data (routing tables, module lists, file descriptor tables) is read millions of times per second and
  written rarely, so even an uncontended atomic operation per read becomes a scaling bottleneck on large machines;
- a wrong lock order anywhere can deadlock the whole machine, and the bug may need a rare interleaving to show up.

This slice covers the main primitives (`spinlock_t`, `raw_spinlock_t`, `rwlock_t`, `struct mutex`,
`rw_semaphore`), the read-copy-update (RCU) mechanism, how PREEMPT_RT changes their meaning, and the lockdep
validator. Memory barriers and atomics come up only where they explain a primitive. Per-CPU data and lock-free
structures are separate topics.

## History and approaches

**The Big Kernel Lock (1996, Linux 2.0).** SMP support began with one global lock taken on kernel entry. It was
correct and easy but serialised the kernel. The next fifteen years were spent breaking it into fine-grained locks,
and the last users were removed in 2.6.39 (2011).

**Spinlocks and interrupt masking.** Fine-grained locking started with spinlocks plus variants that also disable
local interrupts or bottom halves (`spin_lock_irqsave`, `spin_lock_bh`). A spinlock is cheap when uncontended and
safe in any context, but it wastes CPU time when held long and forbids sleeping while held. Ticket and then queued
(MCS-style) spinlocks fixed fairness and cache-line bouncing under contention.

**Sleeping locks.** Semaphores served as general sleeping locks until `struct mutex` arrived in 2.6.16 (2006), with
stricter semantics: a single owner, owner-only unlock, and no recursion. The strictness enabled optimistic spinning
(waiting briefly while the owner is still running) and better debugging. `rw_semaphore` covers read-heavy cases
where holders may sleep.

**RCU (merged 2002, 2.5 series).** Paul McKenney and colleagues brought read-copy-update into Linux. Readers take
no lock and write no shared memory: they mark a read-side critical section (`rcu_read_lock()`), dereference
pointers with `rcu_dereference()`, and finish. A writer publishes a new version with `rcu_assign_pointer()`, then
waits for a *grace period* (until every CPU has passed through a quiescent state) before freeing the old version,
either synchronously or through `call_rcu()`. Reads scale perfectly. The cost moves to writers and to memory, which
must hold old versions until the grace period ends.

**Real-time pressure (2004 onwards).** Ingo Molnar's -rt patch set showed that long non-preemptible spinlock
sections dominated worst-case latency. Its answer was to turn most spinlocks into sleeping, priority-inheriting
`rt_mutex` locks, and to make RCU readers preemptible (with McKenney's preemptible RCU). Pieces such as
`rt_mutex`, threaded interrupts and preemptible RCU merged over many years. PREEMPT_RT itself was merged for Linux
6.12 in September 2024.

**Lockdep (2.6.18, 2006).** Molnar and Arjan van de Ven added a runtime validator that records lock *classes* and
the order in which they are taken, along with the IRQ state at the time. It reports any cycle in the dependency
graph the moment the second ordering is first seen, without waiting for the deadlock to happen.

**Lessons.** Correct-but-global locking does not scale. Fine-grained locking scales but needs tooling to stay
correct. For read-mostly data, the cheapest reader is one that synchronises with nothing, which pushes the cost of
consistency onto writers and onto time.

## Current state

**Choosing a primitive.**

| Need | Primitive | Rules |
|---|---|---|
| Short critical section, may run in IRQ context | `spinlock_t` (with `_irqsave`/`_bh` as the contexts require) | No sleeping while held; keep it to tens of instructions |
| Must spin even on PREEMPT_RT (scheduler, low-level IRQ code) | `raw_spinlock_t` | Rare; only for code that truly cannot sleep |
| May sleep while held (allocation, I/O, `copy_from_user`) | `struct mutex` | Process context only; one owner; owner unlocks |
| Many readers that may sleep, few writers | `rw_semaphore` | Writers can starve readers' latency; prefer RCU if the reads don't sleep |
| Read-mostly pointer-linked data | RCU, often with a spinlock or mutex serialising writers | Readers must not block (unless using SRCU); free only after a grace period |
| Wait for an event, not a resource | `struct completion` | Pairs `wait_for_completion` with `complete` |

**What PREEMPT_RT changes.** On an RT kernel, `spinlock_t` and `rwlock_t` become sleeping locks built on `rt_mutex`,
with priority inheritance. A low-priority holder is boosted while a high-priority task waits, as the catalog's Rocky
RT material explains when it describes how a blocked task is tracked against its lock owner. Code that is legal on
a normal kernel (taking a `spinlock_t` with interrupts hard-disabled, or inside a `raw_spinlock_t` section) becomes
a "sleeping in atomic context" bug on RT. This is why the kernel documents a lock *nesting* order across types
(raw spinlocks innermost, then spinlocks, then sleeping locks) that must hold on every configuration. The same
priority-inheritance idea is available to user space through `FUTEX_LOCK_PI`.

**RCU in practice.** The mental model: a reader observes the old version or the new one, and never a partially written object.
Correct use needs three things:

1. readers stay inside `rcu_read_lock()`/`rcu_read_unlock()` and do not keep pointers after leaving;
2. writers publish with `rcu_assign_pointer()` after the new object is fully initialised;
3. reclamation waits with `synchronize_rcu()`, `call_rcu()` or `kfree_rcu()`.

Variants cover special needs: SRCU allows readers to sleep, Tasks RCU serves tracing trampolines, and
`rcu_read_lock_bh` and `_sched` flavours have been folded into the main implementation. Newer code increasingly uses
scope-based guards (`guard(rcu)()`, `scoped_guard(spinlock, &lock)`) built on the compiler's cleanup attribute, so
the unlock cannot be forgotten on an error path.

**Lockdep in practice.** Enabled through `CONFIG_PROVE_LOCKING`, lockdep tracks every lock class, the classes held
when it is acquired, and whether it is ever taken in hard IRQ, soft IRQ or with interrupts enabled. It reports:

- AB-BA inversions, even when the two orders occur minutes apart in different tasks;
- IRQ-safety violations (a lock taken in interrupt context and also taken elsewhere with interrupts enabled);
- recursion and releasing a lock that is not held;
- suspicious RCU usage (`CONFIG_PROVE_RCU`), such as dereferencing an RCU pointer outside a read-side section.

Annotations such as `lockdep_assert_held()`, `might_sleep()` and nesting subclasses (`spin_lock_nested`) make
intent checkable. Lockdep costs memory and CPU time, so it runs in debug and CI kernels, syzbot and KernelCI rather
than in production.

**Generalised pattern.** Kernel locking combines three reusable ideas. *Context-matched waiting* means spinning
where you cannot sleep and sleeping where you can. *Asymmetric synchronisation* (RCU) means making the frequent
operation free and the rare one expensive. *Order validation* (lockdep) means checking a global invariant (an
acyclic lock order) from local observations. The same ideas appear in databases (MVCC is a relative of RCU), in
user-space RCU (liburcu), and in thread-sanitiser lock-order checkers.

**Limitations and risks.**

- Spinlock sections that grow over time harm latency on normal kernels and become RT bugs.
- RCU readers that run too long delay grace periods, which leads to memory growth and RCU stall warnings.
- Lockdep only sees orders that actually execute in testing. Coverage gaps hide real deadlocks, and the class
  model can produce false positives that need annotation rather than a code change.
- Priority inheritance does not cover every primitive (completions, wait queues), so RT designs still need
  careful thought.

## Related and opposing views

- **Lock-free and per-CPU structures** (`seqlock`, per-CPU counters, `llist`) avoid locks for specific patterns,
  but they are harder to verify and limited in what they can express.
- **Rust in the kernel** encodes which lock protects which data in the type system, with guard objects that
  make holding the lock a precondition for access. Supporters see it as moving lockdep-class bugs to compile time.
  Sceptics note that it does not remove the need for RCU and ordering reasoning, and that it adds friction across
  the C boundary.
- **Formal tools** such as the Linux-kernel memory model (LKMM, `herd7`) and model checkers verify the ordering
  claims behind RCU and barriers. They complement lockdep's runtime checks rather than replacing them.
- **Coarser locking for simplicity.** Some maintainers prefer one well-understood mutex per subsystem over many
  small locks, and accept lower scalability in return for fewer bugs.

## Future direction

- With PREEMPT_RT in mainline, checking whether code might sleep inside a spinlock section on RT becomes part of everyday
  review, and lockdep's RT-aware checks (such as wait-type validation) matter more.
- Scope-based cleanup guards are spreading through the tree and should reduce unlock-on-error bugs.
- Rust lock abstractions will grow alongside RCU bindings, which should make protection rules explicit in new
  drivers.
- Expect continued work on RCU for very large machines (lazy callbacks for power saving, faster expedited grace
  periods) and on cheaper lock debugging that can run in more test fleets.
