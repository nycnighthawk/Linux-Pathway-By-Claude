# Kernel locking: spinlocks, mutexes, RCU and lockdep

## Define the problem

The Linux kernel runs on many CPUs at once. The same code path can be entered from a system call on one CPU, an interrupt handler on another and a softirq or workqueue on a third, and preemption can stop a thread in the middle of an update. Every shared structure, whether a list of network devices, a page-cache tree or a scheduler run queue, must stay consistent under all of those interleavings. The constraints pull in different directions, and a good account of kernel locking is an account of how four of them are reconciled.

- Some contexts **cannot sleep**: hard interrupts, code holding a spinlock, regions with preemption disabled. They need locks that wait by spinning.
- Other contexts hold a lock across I/O or memory allocation, where spinning would waste a CPU for milliseconds. They need locks that wait by sleeping.
- Read-mostly data (routing tables, module lists, file-descriptor tables) is read millions of times a second and written rarely. For that data even one uncontended atomic operation per read becomes a scaling bottleneck on large machines.
- A wrong lock order anywhere can deadlock the whole machine, and the bug may need a rare interleaving to appear.

This essay covers the main primitives (`spinlock_t`, `raw_spinlock_t`, `rwlock_t`, `struct mutex`, `rw_semaphore`), read-copy-update (RCU), how PREEMPT_RT changes the meaning of each, and the lockdep validator. Memory barriers and atomics enter only where they explain a primitive. Per-CPU data and lock-free structures are separate topics.

## History and approaches

### The Big Kernel Lock

SMP support began in 1996, with Linux 2.0, as one global lock taken on kernel entry. It was correct and easy, and it serialised the kernel: a second CPU could do almost nothing in the kernel while the first held the lock. The next fifteen years went into breaking it into fine-grained locks, and the last users were removed in 2.6.39 in 2011.

### Spinlocks and interrupt masking

Fine-grained locking began with spinlocks, together with variants that also disable local interrupts or bottom halves (`spin_lock_irqsave`, `spin_lock_bh`). A spinlock is cheap when uncontended and safe in any context, but it wastes CPU time when held for long and forbids sleeping while held. Ticket locks, and then queued (MCS-style) spinlocks, fixed fairness and cache-line bouncing under contention.

### Sleeping locks

Semaphores served as general sleeping locks until `struct mutex` arrived in 2.6.16 (2006) with stricter semantics: a single owner, unlock only by the owner, and no recursion. The strictness enabled optimistic spinning, waiting briefly while the owner is still running, and better debugging. `rw_semaphore` covers read-heavy cases where holders may sleep.

### RCU

Paul McKenney and colleagues brought read-copy-update into Linux in 2002, in the 2.5 series. Readers take no lock and write no shared memory. They mark a read-side critical section with `rcu_read_lock()`, dereference pointers with `rcu_dereference()`, and finish. A writer publishes a new version with `rcu_assign_pointer()`, then waits for a *grace period*, until every CPU has passed through a quiescent state, before freeing the old version, either synchronously or through `call_rcu()`. Reads scale perfectly. The cost moves to writers and to memory, which must hold old versions until the grace period ends.

### Real-time pressure

From 2004, Ingo Molnar's `-rt` patch set showed that long non-preemptible spinlock sections dominated worst-case latency. Its answer was to turn most spinlocks into sleeping, priority-inheriting `rt_mutex` locks, and to make RCU readers preemptible with McKenney's preemptible RCU. Pieces such as `rt_mutex`, threaded interrupts and preemptible RCU merged over many years, and PREEMPT_RT itself was merged for Linux 6.12 in September 2024.

### Lockdep

Molnar and Arjan van de Ven added a runtime validator to Linux 2.6.18 in 2006. It records lock *classes* and the order in which they are taken, along with the interrupt state at the time, and it reports a cycle in the dependency graph the moment the second ordering is first seen, with no need to wait for the deadlock to happen.

### The lessons

Correct but global locking does not scale. Fine-grained locking scales but needs tooling to stay correct. For read-mostly data, the cheapest reader is one that synchronises with nothing, which moves the cost of consistency onto writers and onto time.

## Current state

### Choosing a primitive

| Need | Primitive | Rules |
|---|---|---|
| Short critical section, may run in IRQ context | `spinlock_t` (with `_irqsave` or `_bh` as the contexts require) | No sleeping while held; keep it to tens of instructions |
| Must spin even on PREEMPT_RT (scheduler, low-level IRQ code) | `raw_spinlock_t` | Rare; only for code that truly cannot sleep |
| May sleep while held (allocation, I/O, `copy_from_user`) | `struct mutex` | Process context only; one owner; owner unlocks |
| Many readers that may sleep, few writers | `rw_semaphore` | Writers can starve readers' latency; prefer RCU if the reads do not sleep |
| Read-mostly pointer-linked data | RCU, often with a spinlock or mutex serialising writers | Readers must not block (unless using SRCU); free only after a grace period |
| Wait for an event, not a resource | `struct completion` | Pairs `wait_for_completion` with `complete` |

### What PREEMPT_RT changes

On a real-time kernel, `spinlock_t` and `rwlock_t` become sleeping locks built on `rt_mutex`, with priority inheritance: a low-priority holder is boosted while a high-priority task waits, as the Rocky real-time material explains when it describes how a blocked task is tracked against the owner of its lock [src: rocky-docs 66c83fa7537d0882]. Code that is legal on a normal kernel, such as taking a `spinlock_t` with interrupts hard-disabled or inside a `raw_spinlock_t` section, becomes a "sleeping in atomic context" bug on RT. That is why the kernel documents a lock *nesting* order across types (raw spinlocks innermost, then spinlocks, then sleeping locks) that must hold in every configuration. The same priority-inheritance idea is available to user space through `FUTEX_LOCK_PI`.

### RCU in practice

The mental model is that a reader sees either the old version or the new one, and never a half-written object. Correct use needs three things.

1. Readers stay inside `rcu_read_lock()` and `rcu_read_unlock()` and do not keep pointers after leaving.
2. Writers publish with `rcu_assign_pointer()` after the new object is fully initialised.
3. Reclamation waits, with `synchronize_rcu()`, `call_rcu()` or `kfree_rcu()`.

Variants cover special needs. SRCU allows readers to sleep, Tasks RCU serves tracing trampolines, and the `rcu_read_lock_bh` and sched flavours have been folded into the main implementation. Newer code increasingly uses scope-based guards (`guard(rcu)()`, `scoped_guard(spinlock, &lock)`) built on the compiler's cleanup attribute, so that an unlock cannot be forgotten on an error path.

### Lockdep in practice

Enabled through `CONFIG_PROVE_LOCKING`, lockdep tracks every lock class, the classes held when it is acquired, and whether it is ever taken in hard IRQ, soft IRQ or with interrupts enabled. It reports:

- AB-BA inversions, even when the two orders occur minutes apart in different tasks;
- IRQ-safety violations, where a lock is taken in interrupt context and also elsewhere with interrupts enabled;
- recursion, and releasing a lock that is not held;
- suspicious RCU usage (`CONFIG_PROVE_RCU`), such as dereferencing an RCU pointer outside a read-side section.

Annotations such as `lockdep_assert_held()`, `might_sleep()` and nesting subclasses (`spin_lock_nested`) make intent checkable. Lockdep costs memory and CPU time, so it runs in debug and continuous-integration kernels, in syzbot and in KernelCI, and not in production.

### The generalised pattern

Kernel locking combines three reusable ideas. *Context-matched waiting* means spinning where one cannot sleep and sleeping where one can. *Asymmetric synchronisation*, as in RCU, makes the frequent operation free and the rare one expensive. *Order validation*, as in lockdep, checks a global invariant (an acyclic lock order) from local observations. The same ideas appear in databases, where multi-version concurrency control is a relative of RCU, in user-space RCU (liburcu), and in thread-sanitiser lock-order checkers.

### Limitations and risks

- Spinlock sections that grow over time harm latency on normal kernels and become bugs on RT.
- RCU readers that run too long delay grace periods, which leads to memory growth and RCU stall warnings.
- Lockdep sees only the orders that actually execute in testing. Coverage gaps hide real deadlocks, and the class model can give false positives that need an annotation and not a code change.
- Priority inheritance does not cover every primitive (completions and wait queues, for example), so real-time designs still need careful thought.

## Assessment: the good, the bad and the ugly

**The good.** The kernel has a rich set of primitives matched to contexts, and RCU gives reads that scale to hundreds of CPUs. Lockdep catches whole classes of deadlock before they ever happen, which is rare among large code bases.

**The bad.** The range of choices is wide and the rules are subtle. A wrong context choice shows up only on some paths, and an RCU mistake (a pointer used after the read-side section) produces a use-after-free that appears once in a million runs.

**The ugly.** Lockdep's coverage depends on the tests that run. Lock-ordering rules are mostly social knowledge, written in comments, and a patch that adds a lock in the wrong place can pass review. Over time, the interplay of RT rules, RCU flavours and IRQ states has made some subsystems hard for newcomers to change safely.

## Applications beyond this domain

- **User-space programs** use the same ideas: liburcu brings RCU to applications, and thread sanitisers check lock order.
- **Databases** use multi-version concurrency, in which readers see a consistent snapshot while writers prepare the next one, which is the same asymmetry as RCU.
- **Real-time and safety-critical systems** adopt priority inheritance to bound blocking, in kernels and in real-time operating systems.
- **Hypervisors** have their own locking hierarchies, and KVM's code follows the same rules, which is why a virtualisation developer reads this topic.
- **Language runtimes** (garbage collectors, concurrent maps) use epoch- and hazard-pointer schemes that are close relatives of RCU.

## Examples

**An AB-BA deadlock found by lockdep.** One path takes lock A and then B; another takes B and then A. Each path runs fine on its own, and a stress test might never deadlock. On the first run in which both orders have executed, lockdep prints the two stack traces and the cycle. The fix is to choose one order and document it.

**A reader that sleeps under RCU.** A driver calls `msleep` inside `rcu_read_lock()`. On a lightly loaded machine nothing happens; on a busy one the grace period stalls, a warning appears, and memory grows because callbacks wait. The fix is SRCU, or taking a reference to the object and leaving the read-side section before sleeping.

**A list that is read without a lock.** A routing table is a linked list read on every packet. Readers use `list_for_each_entry_rcu`, and a writer holds a mutex, unlinks an entry with `list_del_rcu`, and frees it with `kfree_rcu`. A reader that was walking the list at the moment of removal finishes safely, because the memory stays valid until the grace period ends.

**A spinlock that sleeps on RT.** A driver takes a `spinlock_t` and calls a function that allocates with `GFP_ATOMIC`. On a normal kernel this is fine. On PREEMPT_RT, which turns the lock into a sleeping lock, allocation under it is a bug, and the debug configuration prints the warning.

## Related problems and ideas

### Related

- **Interrupts and softirqs** (the previous topic) define the contexts to which the lock rules apply.
- **Memory barriers and the kernel memory model** explain why the primitives work.
- **Per-CPU data and atomics** avoid locks for counters and caches.
- **Debugging with ftrace, KASAN and KCSAN** finds the races that lockdep cannot see.

### Opposing approaches

- **Lock-free and per-CPU structures** (`seqlock`, per-CPU counters, `llist`) avoid locks for specific patterns. They are harder to verify and limited in what they can express.
- **Rust in the kernel** encodes which lock protects which data in the type system, with guard objects that make holding the lock a precondition for access. Supporters see it as moving lockdep-class bugs to compile time. Sceptics note that it does not remove the need for RCU and ordering reasoning and that it adds friction across the C boundary.
- **Formal tools** such as the Linux-kernel memory model (`herd7`) and model checkers verify the ordering claims behind RCU and barriers. They complement lockdep's runtime checks and do not replace them.
- **Coarser locking for simplicity.** Some maintainers prefer one well-understood mutex per subsystem over many small locks and accept lower scalability in return for fewer bugs.

## Active research

Current work includes formal verification of RCU and of the memory model, tools that find data races dynamically (KCSAN) and statically, lockdep extensions for real-time wait types, Rust abstractions for locks and RCU, and RCU tuning for very large machines. The details should be checked against recent kernel documentation and conference proceedings.

## Future direction

- With PREEMPT_RT in mainline, checking whether code might sleep inside a spinlock section on RT becomes part of everyday review, and lockdep's RT-aware checks, such as wait-type validation, matter more.
- Scope-based cleanup guards are spreading through the tree and should reduce unlock-on-error bugs.
- Rust lock abstractions will grow alongside RCU bindings, which should make protection rules explicit in new drivers.
- Expect continued work on RCU for very large machines (lazy callbacks for power saving, faster expedited grace periods) and on cheaper lock debugging that can run in more test fleets.
