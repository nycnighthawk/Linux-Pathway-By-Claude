# arm64 cross-build and boot on QEMU virt: a second architecture without the hardware

## Define the problem

A kernel developer today works on an x86 laptop but ships code for arm64 servers, phones, laptops and embedded boards. Code that is correct on one architecture can break on another: memory ordering is weaker on Arm, pages can be 16 or 64 KiB, interrupts come from a different controller, devices are described by a device tree instead of ACPI tables, and the boot protocol differs. A change to a generic driver must at least build and boot on the other architecture, and a change to architecture code must be tested there.

Real arm64 hardware is not always at hand, and each board needs its own bring-up. A *virtual* arm64 machine, defined for guests rather than imitating a product, gives a uniform target: QEMU's `virt` machine. Together with a cross-compiler it lets a developer build and boot arm64 kernels on any host in minutes.

## History and approaches

**Cross-compilation.** Building for a different architecture means using a compiler that runs on the build machine (the host) and emits code for the target. GNU toolchains encode this in a *triplet* prefix such as `aarch64-linux-gnu-`. The kernel build selects the target through `ARCH` and finds the compiler through `CROSS_COMPILE`, which is prepended to tool names (`gcc`, `ld`, `objcopy`). LLVM is architecture-agnostic: one `clang` can target everything, and `make LLVM=1 ARCH=arm64` needs no prefix, only the right target triple, which the kernel build supplies.

**Emulation with QEMU.** QEMU's system emulation models whole machines. For arm64 there are models of real boards, but the `virt` machine, introduced for KVM and testing, is a deliberately simple platform: a GIC interrupt controller, a PL011 serial port, virtio devices over MMIO and PCIe, a real-time clock, a flash for firmware and a device tree or ACPI tables generated on the fly. Because it matches no hardware, a generic kernel configuration with virtio drivers boots on it. The QEMU documentation for the RISC-V `virt` machine shows the same recipe of defconfig, cross compiler and direct kernel boot [src: qemu-docs 50a3d06e573ba01e].

**Acceleration.** On an arm64 host with KVM, QEMU runs guest code natively, at near full speed. On x86 hosts it uses TCG, which translates instructions and is several times slower but fully capable, so a cross-architecture boot test of a kernel takes seconds to a minute.

**The Image and the boot protocol.** arm64 kernels are loaded as a flat `Image` with a 64-byte header, specified in the kernel's booting document. The header gives text offset, image size, flags (endianness, page size, placement) and a magic number. The bootloader (or QEMU's `-kernel`) loads the image, passes the address of the device tree blob in a register, and jumps to it with the MMU off, in a specific exception level and with caches in a defined state. UEFI boot is the standard route on servers; the kernel can also be built with an EFI stub so firmware loads it as an EFI application.

**Reference platforms.** Embedded training, such as Bootlin's labs, uses QEMU to run U-Boot and a kernel on an emulated board before real hardware, showing the same bring-up steps without risk [src: bootlin-training e6ecf9b848fe95b8].

## Current state

### Toolchain

On Debian and Ubuntu, `gcc-aarch64-linux-gnu` (with `binutils-aarch64-linux-gnu`) installs the cross tools; `qemu-system-arm` provides `qemu-system-aarch64`. Also needed are the usual build dependencies (make, flex, bison, bc, libssl and libelf development packages) and, optionally, `ccache`. Fedora and other distributions package equivalents; `clang` with `lld` offers an alternative via `LLVM=1`.

### Building

```
export ARCH=arm64
export CROSS_COMPILE=aarch64-linux-gnu-
make defconfig
make -j$(nproc) Image dtbs modules
```

The result is `arch/arm64/boot/Image`, uncompressed; `Image.gz` and the other formats are alternatives that some loaders prefer. `vmlinux` in the build root is the ELF with symbols for debugging. The `defconfig` for arm64 is a broad, distribution-like configuration that includes virtio and the PL011 console, so it boots on `virt` as is; for faster builds, a trimmed configuration produced from a fragment (see the Kconfig topic) is preferable. Out-of-tree builds with `O=` keep one source tree for several architectures. Modules built for arm64 are installed into a root filesystem with `INSTALL_MOD_PATH`.

A common mistake is mixing build outputs: after switching `ARCH`, a tree that was configured for x86 must be cleaned or built in a separate `O=` directory, because the configuration and generated headers are architecture-specific.

### Booting on `virt`

A typical command:

```
qemu-system-aarch64 -M virt -cpu cortex-a57 -smp 2 -m 1G -nographic \
  -kernel arch/arm64/boot/Image \
  -initrd rootfs.cpio.gz \
  -append "console=ttyAMA0 earlycon panic=-1" -no-reboot
```

Notes: `-cpu` selects the emulated core (`max` enables all features QEMU can emulate; with KVM use `host`); the console device on `virt` is the PL011 UART, which appears as `ttyAMA0`, not the `ttyS0` of x86; `earlycon` prints messages before the full console driver is up and is invaluable when nothing appears; `-M virt,gic-version=3` selects the interrupt controller generation (the default depends on the QEMU version and acceleration, to verify); `-M virt,virtualization=on` exposes the virtualisation extensions to the guest so it can run its own hypervisor; `-M virt,secure=on` adds the secure world. No device tree needs to be given: QEMU builds one and passes it automatically, and `-machine dumpdtb=virt.dtb` writes it out for inspection with `dtc -I dtb -O dts`.

The root filesystem can be an initramfs with statically linked arm64 binaries (BusyBox), or a disk image attached as a virtio block device with `root=/dev/vda`. To populate a root filesystem on an x86 host, `qemu-user-static` with `binfmt_misc` lets `chroot` run arm64 programs transparently, so a `debootstrap --foreign` or a container image can be unpacked and configured without booting.

### What to check in a first boot

The kernel banner and `Booting Linux on physical CPU` line, the detected CPU features, the timer and GIC messages, `earlycon` output before `console` takes over, the mount of the initramfs and the start of `init`. A hang before any output usually means the console argument is wrong or the Image header was misread; a panic about no init means the boot worked and only the root filesystem is missing, as in the earlier boot-testing course.

### arm64-specific points for driver and kernel authors

- **Memory model**: arm64 is weakly ordered, so code that depended on x86's stronger ordering needs barriers; this is a real source of bugs found only on Arm.
- **Page size**: kernels may use 4 KiB, 16 KiB or 64 KiB pages and 39, 48 or 52-bit virtual addresses; code that assumes 4096 breaks.
- **Interrupts**: the GIC (v2, v3, v4) with SPIs, PPIs and LPIs (MSI) in place of the x86 APIC.
- **Exception levels**: EL0 user, EL1 kernel, EL2 hypervisor, EL3 secure monitor; the kernel can run at EL2 (VHE) for efficiency with KVM.
- **Firmware services**: PSCI for CPU power control, SMCCC calls, and either device tree or ACPI.
- **Cache maintenance** and non-coherent DMA on some SoCs matter to the DMA API.

### Debugging

Run QEMU with `-s -S` and attach `gdb-multiarch` (or an `aarch64-linux-gnu-gdb`) to port 1234: `target remote :1234`, `file vmlinux`, `hbreak start_kernel`. The `scripts/gdb` helpers, ftrace, KASAN (which works on arm64, including a hardware tag-based mode) and the other tools of the first course apply unchanged.

## Assessment: the good, the bad and the ugly

**The good.** A cross build plus QEMU gives any developer a second architecture in minutes, with no board and no risk. The `virt` machine is simple, stable and well supported. CI systems build and boot-test dozens of configurations this way, which catches most portability errors before merge.

**The bad.** Emulation under TCG is slow, and it does not reproduce all hardware behaviour (timing, cache effects, errata, vendor-specific devices). `virt` has no GPU, no real clock tree and none of a vendor's peripherals, so board-specific drivers cannot be tested there. Toolchain version mismatches and stale build trees cause confusing errors.

**The ugly.** Silent boot failures with no output are hard to diagnose without `earlycon` and knowledge of the boot protocol. A kernel that boots under emulation may fail on silicon because of a missing erratum workaround or a firmware difference. Cross-compiling user-space for the root filesystem pulls in a second ecosystem of libraries.

## Applications beyond this domain

- **Cloud and servers**: arm64 instances are widespread; testing guests, containers and hypervisors on `virt` with KVM reproduces cloud environments.
- **Virtualisation development**: KVM on arm64 is developed and tested largely with QEMU `virt`, including nested virtualisation.
- **Embedded Linux**: the same steps lead to a real board: replace `virt` with the board's device tree and bootloader.
- **Mobile and Android kernels** build with the same cross tools and LLVM.
- **CI for portable software**: running tests under emulated arm64 catches architecture assumptions in user-space code as well.

## Examples

**First boot.** A developer builds arm64 `defconfig`, boots it with an initramfs holding BusyBox, and sees a shell prompt on the serial console. Running `uname -m` prints `aarch64`.

**No output.** The same command with `console=ttyS0` prints nothing. Changing the argument to `ttyAMA0` and adding `earlycon` shows the boot log.

**Header check.** A script reads the Image header with the lab's parser and reports a 64 KiB page kernel; the bootloader's load address assumption was for 4 KiB pages, explaining a failure to start.

**A weak-ordering bug.** A driver passes tests on x86 but rarely reads stale data on arm64. Adding the proper `smp_store_release` and `smp_load_acquire` pair or a `readl` with its barrier fixes it.

## Active research

Work includes faster cross-architecture emulation (better TCG, multi-threaded translation), confidential computing on Arm (Realm Management Extension, CCA) and its QEMU support, memory tagging (MTE) for kernel hardening, large page sizes and virtual-address ranges, and standardising platform descriptions across device tree and ACPI (to verify the status of each).

## Future direction

Expect arm64 to remain a first-class kernel target alongside x86, with more CI on virtual platforms, wider LLVM-only builds, and confidential-computing guests that boot through the same paths with additional firmware layers.
