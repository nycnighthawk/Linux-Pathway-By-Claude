# The device model, sysfs, platform drivers and device tree: how drivers find their hardware

## Define the problem

A character device answers the question of how user space talks to a driver. A prior question is how the driver finds its hardware in the first place. On a PC, buses such as PCI and USB enumerate their devices and report identifiers, so the kernel can ask what is present. On an embedded board, the processor's peripherals sit at fixed addresses and nothing announces them. The kernel nevertheless needs one uniform way to describe devices, to match them to drivers, to bind and unbind them, to manage their power, and to show their state to administrators, whatever bus they are on.

Before a common model existed, each bus had its own conventions, so power management, hotplug and device naming were reinvented for every one. The Linux device model removes that duplication: every device is an object of one family, sits on a bus, is handled by a driver, belongs to a class, and is visible in a filesystem tree. This essay follows the model from the problem that created it, through the platform bus and the device tree that solved the board-description problem, to the working pattern of a driver's `probe` function.

## History and approaches

### The 2.5 redesign

For the 2.5 development series, Patrick Mochel's driver model introduced `struct device`, `struct device_driver` and `struct bus_type`, along with kobjects, the reference-counted object type that underlies them, and `sysfs`, a memory-based filesystem that mirrors the object tree. The first motivation was power management: to suspend a machine safely the kernel needed a tree of devices, so that children could be suspended before their parents. The other benefits followed from having the tree.

### Hotplug and udev

The kernel emits *uevents* (device added, removed, changed) over a netlink socket. The user-space daemon `udev` receives them, loads the modules that match a device's alias, creates the `/dev` nodes and runs administrator rules. Modules advertise what they handle through a device table (`MODULE_DEVICE_TABLE`), which becomes an alias in `modules.alias`. That is how a newly seen device pulls in its driver automatically, without anyone running `modprobe`.

### Platform devices, and why they grew

Hardware that no bus discovers needed a home, and the kernel gave it a pseudo-bus called the platform bus. Board code registered `platform_device` structures in C, with resources (memory ranges and interrupts) listed by hand. Each board needed its own file in the kernel tree, and the Arm architecture alone accumulated hundreds of them. Around 2011 the Arm maintainers objected to the growth, and the project moved to describing hardware as data and not as code (the year should be checked against the kernel history).

### The device tree

The device tree, borrowed from Open Firmware, is a text description (`.dts`) compiled to a binary blob (`.dtb`) by the `dtc` compiler and passed to the kernel by the bootloader. The kernel parses it into nodes and creates platform devices, and other bus devices, from them. A single kernel image can then boot many boards, each with its own blob. On x86, ACPI tables play the same role, and on Arm servers both can exist. To keep descriptions consistent, each node type is documented as a *binding*, and bindings have moved from prose to machine-checkable YAML schemas validated by `dt-schema` tools, so a board file can be checked against the drivers' expectations at build time. The pattern across the whole history: first the kernel hard-codes knowledge of the hardware, then the knowledge moves into data, then the data gets a schema.

## Current state

### The objects

- A **bus** (`struct bus_type`) defines how devices and drivers match, through its `match` function, and how probing starts.
- A **device** (`struct device`) represents one instance and is embedded in a bus-specific type such as `struct platform_device` or `struct pci_dev`.
- A **driver** (`struct device_driver`) provides `probe` and `remove` callbacks and identification tables.
- A **class** groups devices by function (input, net, tty) regardless of the bus, which gives the view under `/sys/class`.
- **kobjects and ksets** supply naming, reference counting and the sysfs directory structure. A driver rarely handles them directly.

When a device and a driver are on the same bus and match, the core calls `probe`. Binding is one-to-one: a device has at most one bound driver. Matching runs when a device is added and when a driver is registered, so loading a module later still binds the devices that were waiting. An administrator can unbind and bind by hand through sysfs files in the driver's directory, which is useful for testing and for handing a device to a different driver.

### sysfs

`sysfs` is mounted at `/sys`. Directories correspond to kernel objects and files to attributes. `devices/` holds the full device tree, `bus/` and `class/` give views of it, `module/` holds parameters, and `kernel/` various settings. The convention is *one value per file*, in readable text, so scripts can handle them. A driver adds attributes with the `DEVICE_ATTR_RW` and `DEVICE_ATTR_RO` macros, writes show and store callbacks, and attaches attribute groups to the device. The preferred way is through the driver structure's `dev_groups`, which makes the attributes appear before the uevent is emitted, so `udev` rules can rely on them. Attributes are part of the ABI, so new ones are documented under `Documentation/ABI/`.

### Platform drivers

A platform driver fills a `struct platform_driver` with `probe`, `remove` and a `struct device_driver` that carries a name and an `of_match_table` (for the device tree) or an `acpi_match_table`. `module_platform_driver` generates the registration code. In `probe`, the driver typically does five things in order.

1. It obtains resources from the device: `platform_get_resource`, or the managed helper `devm_platform_ioremap_resource`, for a memory range, and `platform_get_irq` for an interrupt number.
2. It reads properties with `device_property_read_u32` and its relatives, which work for both the device tree and ACPI.
3. It allocates its state with `devm_kzalloc`.
4. It acquires clocks, regulators, GPIOs and resets, using the `devm_` variants.
5. It registers with its subsystem: a misc device, an input device, a network device.

The `devm_` ("device managed") family attaches each resource to the device, and the core releases them in reverse order when probe fails or the device is removed. That removes most error-path cleanup code and a class of leaks. A `probe` may also return `-EPROBE_DEFER` when a resource, such as a clock supplied by another driver, is not yet available. The core retries once other drivers have bound, which is how drivers cope with arbitrary load order.

### Device tree basics

A node has a name with an optional unit address (`serial@10000000`), properties and child nodes. A few properties matter in nearly every file.

- `compatible` is a list of strings, from most specific to most general, such as `"vendor,model-v2", "generic-type"`. The kernel matches drivers against the strings in order, so a board can name its exact chip and still use a generic driver.
- `reg` gives address and size cells; their interpretation depends on the parent's `#address-cells` and `#size-cells`.
- `interrupts` and `interrupt-parent` name the interrupt lines and the controller they connect to.
- `status`: absent or `"okay"` means the node is used; `"disabled"` means the kernel creates no device. Boards use it to switch off unused peripherals.
- `clocks`, `resets`, `gpios`, `pinctrl-*`, `dmas` and other phandle references connect nodes to each other.

Overlays (`.dtbo`) modify a base tree at boot or at run time, which is how add-on boards and expansion headers are supported. The tools are `dtc` (compile and decompile), `dtc -I dtb -O dts` (to show what a board really passes), `/proc/device-tree` or `/sys/firmware/devicetree` (the live tree), and `dt-validate` (schema checks). The kernel ships many `.dts` files under `arch/*/boot/dts`.

### Virtual machines and discovery

QEMU's `virt` machines for arm64 and RISC-V generate a device tree at start and pass it to the kernel, which is why a generic defconfig boots on them. On x86, QEMU provides ACPI tables and PCI. Either way the guest discovers its virtio devices through the same device model, which is the reason this topic matters beyond embedded boards.

### Debugging binding problems

If a device does not appear, work through a short list. Check its `status`. Compare `compatible` with the driver's table, using `/sys/bus/platform/drivers/<name>` and the `modalias` files. Look for deferral in `/sys/kernel/debug/devices_deferred`. Enable dynamic debug for the driver core. Check that the module is built and that its alias exists. `dmesg` prints probe failures with the error code.

### The generalised pattern

Describe the hardware as data; let a bus match descriptions to drivers; let the driver acquire resources through managed helpers and register with a subsystem; let the core undo everything in reverse order on failure. The pattern appears in every subsystem that discovers things at run time.

## Assessment: the good, the bad and the ugly

**The good.** One model gives hotplug, power management, naming, binding and a self-describing filesystem to every device. The device tree lets one kernel serve many boards and moves board data out of C. `devm_` reduces error-path bugs, and sysfs gives scripts structured access.

**The bad.** The model has many layers, and understanding a binding failure requires knowing all of them. Device-tree bindings are an ABI between firmware and kernel, so changes have long-term costs. The sysfs rule of one value per file pushes richer interfaces elsewhere.

**The ugly.** Probe-ordering problems, circular dependencies between suppliers and consumers, and loops of deferred probing can make a board fail in confusing ways, though `fw_devlink` now tracks dependencies from the tree and orders probing. Vendor kernels carry large private device trees that never reach the mainline, so the same chip is described differently in different trees. A wrong `reg` or `compatible` produces silent absence and not an error message.

## Applications beyond this domain

- **Embedded Linux and single-board computers.** Every board support package is, at heart, a device tree, a bootloader and a defconfig, and Bootlin's training labs walk through these steps for QEMU and real boards [src: bootlin-training e6ecf9b848fe95b8].
- **Virtualisation.** Hypervisors build a device tree or ACPI description for a guest, and tools such as `libvirt` and QEMU expose virtio devices through it.
- **Firmware and bootloaders** such as U-Boot use the same device-tree format for their own drivers.
- **Other operating systems.** FreeBSD and Zephyr also use the device tree to describe hardware.
- **Security.** Device nodes and sysfs attributes are an attack surface that sandboxes restrict.

## Examples

**Disabling a peripheral.** A board file marks the second UART `status = "disabled"`. The kernel creates no device, `/dev/ttyS1` does not exist and no driver probes. The change is one line of data and no code.

**A compatible fallback.** A node lists `"acme,rtc-v1", "dallas,ds1307"`. No driver knows the first string, so the generic DS1307 driver binds through the second. If the chip later needs a quirk, a driver for the first string can be added without touching boards that already work.

**A deferred probe, step by step.** An Ethernet driver needs a clock from a clock controller that loads later. At first probe, the clock request returns "not ready", the driver returns `-EPROBE_DEFER`, and the core puts the device on a deferred list. When the clock controller binds, the core retries the Ethernet driver, the clock request now succeeds, and the driver finishes. Nobody had to order the modules.

**Rebinding by hand.** To give a PCI device to a test driver, an administrator writes the device's address to `unbind` in the old driver's sysfs directory and then to `bind` in the new one. The device is now served by different code, with no reboot.

## Related problems and ideas

### Related

- **Character devices** (the previous topic) are what a platform driver often registers.
- **PCI drivers** (the next topic) use the same model with a different bus.
- **Interrupts and DMA** are resources the driver requests in `probe`.
- **ACPI, configfs, debugfs and netlink** complement sysfs for configuration and debugging.
- **Rust drivers** use the same probe model through abstractions.

### Opposing approaches

- **Board files in C.** The older approach, one C file per board, is explicit and checked by the compiler, but it does not scale and it ties the kernel image to a board. Its criticism is the reason the device tree exists.
- **ACPI everywhere.** Some argue that Arm servers and even embedded boards should use ACPI as x86 does, since it has a real specification process and a method language. Critics find that it embeds code in firmware and that firmware bugs cannot be fixed by the kernel. The two descriptions currently coexist.
- **Self-describing buses.** The ideal of USB or PCI, where the device announces itself, makes a static description unnecessary. It is not available for memory-mapped peripherals inside a system-on-chip, so a description is unavoidable there.
- **Runtime discovery by probing.** Old ISA drivers poked at addresses to see what answered. That was fragile and sometimes harmful, and no one wants it back.

## Active research

Work includes better dependency tracking so that probing is ordered without deferral, schema validation of all device trees, overlays that can be applied safely at run time, and Rust bindings for driver registration and device properties. Studies of driver bugs on hot-plug and unbind paths, where removal races with use, continue; the specifics should be checked against recent kernel releases.

## Future direction

Expect all bindings to be described by schemas, more reliance on `fw_devlink` and managed resources, and more drivers written once against generic property interfaces that serve both device tree and ACPI. Discovery for virtualised devices will remain via virtio over PCI, MMIO or similar transports. The practical lesson for a learner is that the model is stable even as the details change: a driver finds its resources, validates them, registers, and lets the core clean up.
