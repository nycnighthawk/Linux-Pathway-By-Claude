# The device model, sysfs, platform drivers and device tree: how drivers find their hardware

## Define the problem

A character device answers the question of how user space talks to a driver. A prior question is how the driver finds its hardware. On a PC, buses such as PCI and USB enumerate devices and report identifiers. On an embedded board, the processor's peripherals sit at fixed addresses and nothing announces them. The kernel needs a uniform way to describe devices, match them to drivers, bind and unbind them, manage power and expose their state to administrators, whatever bus they are on.

Before a common model, each bus had its own conventions, so power management, hotplug and device naming were reinvented for each. The Linux device model unifies them: every device is an object of one family, on a bus, handled by a driver, grouped in a class, and visible in a filesystem tree.

## History and approaches

**The 2.5 redesign.** For 2.5, Patrick Mochel's driver model introduced `struct device`, `struct device_driver` and `struct bus_type`, along with kobjects, the reference-counted object type behind them, and `sysfs`, a memory-based filesystem that mirrors the object tree. It was first motivated by power management: the kernel needed a tree of devices to suspend children before parents.

**Hotplug and udev.** The kernel emits uevents (device added, removed, changed) over a netlink socket. User-space `udev` receives them, loads modules matching a device's alias, creates `/dev` nodes and runs rules. Modules advertise what they handle with a device table (`MODULE_DEVICE_TABLE`), which becomes aliases in `modules.alias`; this is how a newly seen device pulls in its driver automatically.

**Platform devices.** For hardware that is not discovered by a bus, the kernel introduced a pseudo-bus called the platform bus. Board code used to register `platform_device` structures in C, with resources (memory ranges, interrupts) listed by hand. Each board needed its own file in the tree, and in the 2000s arm alone accumulated hundreds. Around 2011 (year to verify) the arm maintainers objected to the growth and the project moved to describing hardware in data.

**Device tree.** Borrowed from Open Firmware, the device tree is a text description (`.dts`), compiled to a binary blob (`.dtb`) by the `dtc` compiler and passed to the kernel by the bootloader. The kernel parses it into nodes and creates platform devices (and other bus devices) from them. A single kernel image can then boot many boards, each with its own blob. On x86 ACPI tables play the same role, and on server arm systems both exist.

**Bindings and schemas.** To keep descriptions consistent, the project documents each node type as a "binding", and the bindings have moved from prose to machine-checkable YAML schemas validated by `dt-schema` tools, so a board file can be checked against the drivers' expectations at build time.

## Current state

### The objects

- A **bus** (`struct bus_type`) defines how devices and drivers match (its `match` function) and how probing starts.
- A **device** (`struct device`) represents one instance, embedded in a bus-specific type such as `struct platform_device` or `struct pci_dev`.
- A **driver** (`struct device_driver`) provides `probe` and `remove` callbacks and identification tables.
- A **class** groups devices by function (input, net, tty) regardless of bus, giving a view under `/sys/class`.
- **kobjects and ksets** supply naming, reference counting and the sysfs directory structure; a driver rarely handles them directly.

When a device and a driver are on the same bus and match, the core calls `probe`. Binding is one-to-one: a device has at most one bound driver. Matching runs when a device is added and when a driver is registered, so loading a module later still binds existing devices. Drivers can be unbound and bound by hand through sysfs files (`unbind` and `bind` under the driver's directory), which is useful for testing and for handing a device to a different driver.

### sysfs

`sysfs` is mounted at `/sys`. Directories correspond to kernel objects and files to attributes: `devices/` is the full device tree, `bus/` and `class/` provide views, `module/` has parameters and `kernel/` various settings. The convention is one value per file, readable text, so tools and scripts can handle them. A driver adds attributes with `DEVICE_ATTR_RW` or `DEVICE_ATTR_RO` macros, show and store callbacks, and attribute groups attached to the device (preferably through the driver structure's `dev_groups`, which makes them appear before the uevent is emitted so udev rules can rely on them). Attributes are an ABI, so new ones are documented in `Documentation/ABI/`.

### Platform drivers

A platform driver fills a `struct platform_driver` with `probe`, `remove` and a `struct device_driver` carrying a name and an `of_match_table` (for device tree) or `acpi_match_table`. `module_platform_driver` generates the registration boilerplate. In `probe` the driver:

1. obtains resources from the device: `platform_get_resource` or the managed helper `devm_platform_ioremap_resource` for a memory range, `platform_get_irq` for an interrupt number;
2. reads properties with `device_property_read_u32` and friends (works for both device tree and ACPI);
3. allocates its state with `devm_kzalloc`;
4. acquires clocks, regulators, GPIOs and resets with `devm_` variants;
5. registers with its subsystem (a misc device, input device, network device).

The `devm_` ("device managed") family attaches each resource to the device, and the core releases them in reverse order when probe fails or the device is removed, which removes most error-path cleanup code and a class of leaks. A `probe` may return `-EPROBE_DEFER` when a resource (a clock or regulator supplied by another driver) is not yet available; the core retries once other drivers have bound. This is how drivers cope with arbitrary load order.

### Device tree basics

A node has a name with an optional unit address (`serial@10000000`), properties and child nodes. Key properties:

- `compatible`: a list of strings, from the most specific to the most general, such as `"vendor,model-v2", "generic-type"`. The kernel matches drivers against the strings in order, so a board can name its exact chip yet still use a generic driver.
- `reg`: address and size cells; the interpretation depends on the parent's `#address-cells` and `#size-cells`.
- `interrupts` and `interrupt-parent`: the interrupt lines and the interrupt controller to which they connect.
- `status`: absent or `"okay"` means the node is used; `"disabled"` means the kernel creates no device. Boards use it to switch off unused peripherals.
- `clocks`, `resets`, `gpios`, `pinctrl-*`, `dmas` and other phandle references that connect nodes.

Overlays (`.dtbo`) modify a base tree at boot or at run time, which is how add-on boards and expansion headers are supported. Tools: `dtc` compiles and decompiles; `dtc -I dtb -O dts` shows what a board really passes; `/proc/device-tree` (or `/sys/firmware/devicetree`) exposes the live tree; `dt-validate` checks against schemas. The kernel ships many `.dts` files in `arch/*/boot/dts`.

### Virtual machines and discovery

QEMU's `virt` machines for arm64 and RISC-V generate a device tree at start and pass it to the kernel, which is why a generic defconfig boots on them (as the boot-testing topic of the previous course showed). On x86, QEMU provides ACPI tables and PCI. Either way the guest discovers its virtio devices through the same device model.

### Debugging binding problems

If a device does not appear: check `status`, check `compatible` against the driver's table (`/sys/bus/platform/drivers/<name>` and `modalias` files), look for `-EPROBE_DEFER` in `/sys/kernel/debug/devices_deferred`, enable dynamic debug for the driver core, and check the module is built and its alias exists. `dmesg` prints probe failures with the error code.

## Assessment: the good, the bad and the ugly

**The good.** One model gives hotplug, power management, naming, binding and a self-describing filesystem to all devices. Device tree lets one kernel serve many boards and moves board data out of C. `devm_` reduces error-path bugs, and sysfs gives scripts structured access.

**The bad.** The model has many layers, and understanding binding failures requires knowing all of them. Device tree bindings are an ABI between firmware and kernel, so changes have long-term costs. sysfs attribute rules (one value per file) push richer interfaces elsewhere.

**The ugly.** Probe ordering problems, circular dependencies between suppliers and consumers, and `-EPROBE_DEFER` loops can make a board fail in confusing ways, though `fw_devlink` now tracks dependencies from the tree to order probing. Vendor kernels carry large private device trees that never reach the mainline, so the same chip is described differently in different trees. A wrong `reg` or `compatible` produces silent absence rather than an error.

## Applications beyond this domain

- **Embedded Linux and SBCs**: every board support package is, at heart, a device tree, a bootloader and a defconfig; Bootlin's training labs walk through these steps for QEMU and real boards [src: bootlin-training e6ecf9b848fe95b8].
- **Virtualisation**: hypervisors build a device tree or ACPI description for a guest, and tools such as `libvirt` and `qemu` expose virtio devices through it.
- **Firmware and bootloaders** such as U-Boot use the same device tree format for their own drivers.
- **Other operating systems**: FreeBSD and Zephyr also use device tree to describe hardware.
- **Security**: device nodes and sysfs attributes are an attack surface that sandboxes restrict.

## Examples

**Disabling a peripheral.** A board file marks the second UART `status = "disabled"`. The kernel creates no device, `/dev/ttyS1` does not exist and no driver probes.

**A compatible fallback.** A node lists `"acme,rtc-v1", "dallas,ds1307"`. No driver knows `acme,rtc-v1`, so the generic DS1307 driver binds through the second string.

**A deferred probe.** An Ethernet driver needs a clock from a clock controller that loads later. Its probe returns `-EPROBE_DEFER`; once the controller binds, the core retries and the driver succeeds.

**Rebinding by hand.** To hand a PCI device to a test driver, an administrator writes the device address to `unbind` in the old driver's sysfs directory and to `bind` in the new one.

## Related problems and ideas

- **Character devices** (previous topic) are what a platform driver often registers.
- **PCI drivers** (next topic) use the same model with a different bus.
- **Interrupts and DMA** are resources the driver requests in `probe`.
- **ACPI**, **configfs**, **debugfs** and **netlink** complement sysfs for configuration and debugging.
- **Rust drivers** use the same probe model through abstractions.

## Active research

Work includes better dependency tracking so probing is ordered without deferral, schema validation of all device trees, overlays that can be applied safely at run time, and Rust bindings for driver registration and device properties. Studies of driver bugs on hot-plug and unbind paths (races between removal and use) continue (to verify specifics).

## Future direction

Expect all bindings to be described by schemas, more reliance on `fw_devlink` and managed resources, and more drivers written once against generic property APIs that serve device tree and ACPI. Discovery for virtualised devices will remain via virtio over PCI, MMIO or similar.
