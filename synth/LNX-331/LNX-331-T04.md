# Interrupts, softirqs, workqueues and timers: running code when something happens

## Define the problem

Hardware does not wait for software. A network card has received a packet, a disk has finished a transfer, a timer has expired. The processor must stop what it is doing, run code that deals with the event, and resume, without losing the event and without letting the handler run so long that other events are lost. At the same time, dealing with an event often needs things that a handler cannot safely do: take locks that may sleep, allocate memory that may have to wait, and talk to slow buses.

The kernel's answer is to divide the work into stages. A tiny part runs immediately, in *interrupt context*, under strict rules. The rest is deferred to a context where the rules are looser. Understanding which stage a piece of code runs in, and what it may do there, is the single most important skill for writing correct kernel code, and this essay builds it from the first idea (split the work in two) up to the table that tells a driver author which mechanism to choose.

## History and approaches

### Top and bottom halves

Early Linux split interrupt handling into a *top half*, the handler that runs with interrupts disabled for that line and does the minimum, and a *bottom half* that runs later with interrupts enabled. The original single bottom-half mechanism serialised everything, so only one bottom half could run at a time across the whole machine. The replacement, during the 2.4 and 2.6 series, gave per-CPU softirqs and tasklets, which scale with the number of processors.

### Softirqs and tasklets

A softirq is a statically defined handler (network receive and transmit, block completion, timers, RCU, scheduler balancing). It runs on the CPU that raised it, either right after a hard interrupt returns or in the per-CPU `ksoftirqd` thread when load is high. Tasklets are built on softirqs and add serialisation per tasklet. Both run in *atomic context* and cannot sleep. New drivers are discouraged from using tasklets, and the kernel has been removing them in favour of threaded interrupts and workqueues.

### Workqueues

A work item is a function queued to run in a kernel thread. Because it runs in process context, it can sleep, take mutexes and allocate memory with `GFP_KERNEL`. The concurrency-managed workqueue implementation (2.6.36) provides worker pools per CPU and unbound pools, and it replaced earlier designs in which each subsystem kept its own threads.

### Threaded interrupts

The real-time project pushed the idea that handlers should run in threads, so that they can be scheduled and prioritised like other work. `request_threaded_irq` splits a handler into a quick function (the *primary handler*, in hard interrupt context), which checks whether the device raised the interrupt, and a *thread function* that does the rest in a dedicated kernel thread. Many drivers now use threaded handlers where they once used a tasklet or a workqueue.

### Timers

Kernel timers (the "timer wheel") call a function after a given number of jiffies, in softirq context. High-resolution timers (`hrtimer`) give nanosecond-scale precision, driven by the hardware clock-event device. Delayed work combines a timer with a work item, so the callback runs in process context after the delay. The system-wide tick can be turned off on idle or isolated CPUs (dynamic ticks), which matters for power and for real-time work. The pattern across this history: first a single global mechanism, then one per CPU, then one that can sleep, because each step removed a limit that the previous design imposed.

## Current state

### Hard interrupts

A driver requests a line with `request_irq(irq, handler, flags, name, dev_id)`, or the managed `devm_request_irq`. The `dev_id` pointer is handed back to the handler and is how the kernel tells sharers apart. The handler has the signature `irqreturn_t handler(int irq, void *dev_id)` and returns `IRQ_HANDLED` if the device raised the interrupt, `IRQ_NONE` if not (so the kernel can detect spurious or stuck lines), or `IRQ_WAKE_THREAD` to run the thread function.

Four rules govern a hard handler.

- It cannot sleep: no mutexes, no `GFP_KERNEL` allocation, no `copy_to_user`, no `msleep`.
- It must be short: read the status, acknowledge the interrupt in the device (otherwise a level-triggered line fires again at once), take minimal data, and defer the rest.
- It may use spinlocks, and any lock shared with process context must be taken there with interrupts disabled (`spin_lock_irqsave`, or `spin_lock_irq` when the context is known), so that the handler cannot interrupt a lock holder on the same CPU and deadlock.
- `IRQF_SHARED` requires every sharer to handle the same line and to check its own device.

`/proc/interrupts` is the view: per-CPU counts, controller type, trigger mode and the names of users. Affinity can be set through `/proc/irq/N/smp_affinity`, and `irqbalance` spreads the load. With MSI-X, a device can have one vector per queue, so each CPU handles its own queue.

### Softirq and tasklet context

Code running in softirq, tasklet or timer-callback context has no process behind it, so it also cannot sleep. Hard interrupts can interrupt it, but other softirqs on the same CPU cannot. Locks shared with softirq context use `spin_lock_bh`, which disables softirq processing locally. The network stack's receive path runs here, and NAPI (a later topic) combines polling with interrupts to bound the work.

### Workqueues

`INIT_WORK(&w, fn)` prepares an item, `schedule_work(&w)` queues it on the system workqueue, and `queue_work(wq, &w)` uses a driver's own queue, created with `alloc_workqueue` and flags such as `WQ_UNBOUND` (not tied to a CPU), `WQ_HIGHPRI`, `WQ_MEM_RECLAIM` (for queues used in memory-reclaim paths) and `WQ_FREEZABLE`. `INIT_DELAYED_WORK` and `schedule_delayed_work` add a delay. Before freeing the object that contains a work item, call `cancel_work_sync` or `flush_work`; otherwise a worker can run on freed memory. A work item may be queued again while it is running, and only ordered queues guarantee that it does not run concurrently with itself on different CPUs, so handlers should not assume more.

### Threaded handlers

With `devm_request_threaded_irq(dev, irq, quick_fn, thread_fn, IRQF_ONESHOT, name, dev_id)`, the quick function can return `IRQ_WAKE_THREAD`. `IRQF_ONESHOT` keeps the line masked until the thread finishes, which is required when no quick function acknowledges the device. The thread function can sleep, so it is the natural place to talk to devices over I2C or SPI. Passing `NULL` as the quick function makes the kernel use a default one.

### Timers

`timer_setup(&t, callback, flags)` initialises a timer. `mod_timer(&t, jiffies + msecs_to_jiffies(50))` arms or re-arms it. A call named `del_timer_sync` in older kernels (renamed `timer_delete_sync` in recent ones; check the target kernel) stops the timer and waits for a running callback on another CPU, and it must not be called from the callback itself. Timer callbacks run in softirq context. For precise timing, use `hrtimer_init` and `hrtimer_start` with a `ktime_t`, and a callback that returns `HRTIMER_NORESTART` or `HRTIMER_RESTART`. `msleep` and `usleep_range` sleep in process context, while `mdelay` and `udelay` busy-wait and are allowed in atomic context for short delays only.

### Choosing a mechanism

| Need | Mechanism |
|---|---|
| acknowledge the device, record a status | hard handler |
| high-rate per-CPU work that may not sleep | softirq (usually through NAPI or an existing subsystem) |
| work that may sleep after an interrupt | threaded handler or workqueue |
| something later, short and non-sleeping | timer |
| something later that may sleep | delayed work |
| precision below the tick | hrtimer |

### Testing and debugging

`/proc/interrupts` and `/proc/softirqs` show the counts. `ftrace` has events for interrupt entry and exit and for work execution (the `irq`, `workqueue` and `timer` groups). Lockdep notices a lock taken in both interrupt context and process context without interrupts disabled. `CONFIG_DEBUG_ATOMIC_SLEEP` reports sleeping in atomic context with a `BUG: sleeping function` warning, the first diagnostic every driver author meets. In a virtual machine, the edu device from the previous topic can raise an interrupt on demand, which gives a safe test case.

### The generalised pattern

Do the minimum that must happen *now* in the most restricted context, record what is needed, and hand the rest to a context with more freedom. The same two-stage idea appears in network receive (hard interrupt, then softirq, then protocol processing in process context) and in storage completion.

## Assessment: the good, the bad and the ugly

**The good.** The staged design keeps latency low while allowing arbitrarily complex follow-up work. Per-CPU softirqs scale on many-core machines, workqueue pools remove the need for each driver to manage its own threads, and the debugging options check the context rules mechanically.

**The bad.** There are many mechanisms with overlapping uses, and the rules for each differ. The wrong choice shows up only on specific paths, typically as a sleeping-in-atomic warning on a rarely taken branch. Tasklets and workqueues both have a history of use-after-free bugs when an object is freed while work on it is pending.

**The ugly.** An interrupt storm from an unacknowledged level-triggered line can lock up a machine. Priority inversion arises when a thread handler runs at low priority. Heavy softirq load pushes work to `ksoftirqd` and increases latency unpredictably. Real-time kernels change which code is atomic, so code that assumes a spinlock disables preemption can break there.

## Applications beyond this domain

- **User-space event loops** reproduce the same split: a quick event callback and deferred processing. The lesson, that long work in a handler starves others, carries over exactly.
- **Embedded and real-time systems** depend on bounded interrupt latency, with threaded handlers and priorities.
- **Hypervisors** inject virtual interrupts into guests and use timers for the guest clock. KVM's timer and interrupt-controller emulation mirror the hardware mechanisms described here.
- **Network and storage performance tuning** uses interrupt affinity, coalescing and queue-per-CPU designs.
- **Microcontroller firmware** uses interrupt service routines with the same restrictions.

## Examples

**A completion interrupt, step by step.** The edu device raises an interrupt when its factorial is done. The hard handler reads the interrupt status, writes the status back to acknowledge it, stores the result and calls `complete()` (or wakes a wait queue). The process that issued the ioctl is asleep on that completion; it resumes and returns the value. The handler did four small things and no more.

**A sleeping bug.** A handler calls `mutex_lock` because the same lock is used in the ioctl path. The kernel prints a sleeping-in-atomic warning. The fix is a threaded handler, so the lock is taken in a context that may sleep.

**A deadlock with interrupt locks.** Process context takes `spin_lock(&dev->lock)` and an interrupt arrives on the same CPU. The handler takes the same lock and spins for ever, because the holder cannot run until the handler returns. Using `spin_lock_irqsave` in process context fixes it, and lockdep would have reported the pattern the first time it ran.

**A timer for a watchdog.** A driver arms a two-second timer when it starts an operation and cancels it on completion. If the callback runs, it logs a timeout and schedules a reset work item, because the reset needs to sleep and a timer callback cannot.

## Related problems and ideas

### Related

- **Locking** (the next topic) gives the rules for sharing data between these contexts.
- **NAPI** (the network drivers topic) blends interrupts with polling.
- **RCU** callbacks run in softirq context and must also not sleep.
- **Interrupt controllers and affinity** control which CPU takes each interrupt.

### Opposing approaches

- **Polling.** Instead of interrupts, a driver or application checks the device in a loop. It removes interrupt overhead and latency jitter, and it burns a CPU. High-rate designs (busy-polling sockets, io_uring polling, user-space network stacks) choose it deliberately, and NAPI is a hybrid.
- **Real-time Linux (PREEMPT_RT).** It converts most hard interrupt handlers and many softirqs into threads, trading a little throughput for bounded latency. It contradicts the classical picture in which a handler runs with interrupts off, which is why code that assumes that picture can break.
- **Doing it all in the handler.** For extremely simple devices a long handler is easier to reason about than a deferred design. It works until the load rises, and it cannot talk to anything that sleeps.

## Active research

Research and development include lowering interrupt latency on real-time kernels, polling designs for fast devices, better CPU isolation (`nohz_full`), reducing softirq pressure with threaded network processing, and Rust abstractions that encode the context rules in types, so that sleeping inside an atomic section fails to compile. The state of the Rust work should be checked against recent kernel releases.

## Future direction

Expect further removal of tasklets, more threaded interrupt handling, and more type-system help for the context rules. Hardware improvements such as interrupt virtualisation (posted interrupts, APICv, GICv4) continue to move interrupt delivery to guests without hypervisor involvement. The rule that stays constant is the question to ask of any piece of code: in which context does this run, and what is it allowed to do there?
