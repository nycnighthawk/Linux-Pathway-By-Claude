# Network drivers and NAPI: moving packets without drowning the CPU

## Define the problem

A network interface card turns signals on a wire into packets in memory, and packets in memory into signals. A modern card handles millions of packets per second. If each received packet raised an interrupt that the CPU had to service, the machine would spend all its time entering and leaving interrupt handlers, and under heavy load it could do nothing else: a failure called receive livelock, where the system is busy but delivers no useful work. On the transmit side, the driver must queue frames fast, tell the stack when the card is full and recover buffers when the card is done.

A network driver therefore has to cooperate with a stack that wants batching, backpressure and fairness, while exploiting hardware features: multiple queues, checksum and segmentation offload, interrupt moderation.

## History and approaches

**One interrupt per packet.** Early drivers copied each frame in the interrupt handler and passed it up. At 100 Mbit/s this was acceptable; at gigabit rates, receive livelock became a measured problem on Linux and other systems.

**NAPI.** The "New API", introduced around the 2.5 series (authors and release to verify), turned reception into a mix of interrupts and polling. The first interrupt disables further receive interrupts for that queue and schedules a poll function in softirq context. The poll function processes packets from the ring up to a budget, and when the ring drains it re-enables interrupts. Under low load the system behaves like interrupt-driven; under high load it behaves like a polled system, with bounded work per round and fairness between devices.

**Generic offloads.** Segmentation offload lets the stack hand the driver one large buffer that the card splits into frames; generic receive offload (GRO) merges consecutive packets of a flow into one before the stack processes them. Checksum offload lets the hardware compute or verify checksums. Receive-side scaling (RSS) hashes flows to separate hardware queues, each with its own interrupt and CPU.

**XDP and kernel bypass.** The eXpress Data Path runs an eBPF program in the driver's receive path, before an `sk_buff` is allocated, to drop, redirect or modify packets very early. AF_XDP and DPDK-style user-space drivers bypass the kernel stack. The kernel's reply is to make the in-kernel path faster, with page pools and batching.

**Virtual networking.** `virtio-net` gives virtual machines a paravirtual NIC, sharing rings with the host (`vhost-net` in the kernel or `vhost-user` in a user-space switch); the guest driver is an ordinary network driver using NAPI. Linux bridges, veth pairs and macvlan make software devices with the same driver interface.

## Current state

### The driver interface

A network driver allocates a `struct net_device` (`alloc_etherdev_mq` for Ethernet with several queues), fills a `struct net_device_ops` table and registers it with `register_netdev`. Key operations:

- `ndo_open` and `ndo_stop`: bring the interface up and down: allocate rings, request interrupts, enable NAPI, start the queues.
- `ndo_start_xmit`: called by the stack with an `sk_buff` to transmit. The driver maps the buffer for DMA, writes a descriptor and tells the card. If the ring fills, it stops the queue (`netif_stop_queue`) and wakes it (`netif_wake_queue`) from the completion path, which is how backpressure reaches the stack. It returns `NETDEV_TX_OK` (or `NETDEV_TX_BUSY`, discouraged).
- `ndo_set_rx_mode`, `ndo_set_mac_address`, `ndo_change_mtu`, `ndo_get_stats64`, `ndo_tx_timeout`, `ndo_bpf` for XDP, and others.

Ethtool operations (`ethtool_ops`) expose settings and statistics to `ethtool`: link state, ring sizes, offload flags, interrupt coalescing, statistic counters.

### Receive with NAPI

The driver registers a poll function with `netif_napi_add`. In the interrupt handler it disables the queue's interrupt in the device and calls `napi_schedule`. The kernel runs the poll function from the network softirq with a budget (commonly 64 for default weight, set by the driver and system parameters). The poll function:

1. Processes up to `budget` completed descriptors. For each, it builds an `sk_buff` around the data (often by wrapping a page from a page pool with `build_skb` or `napi_build_skb` to avoid copies), sets the protocol with `eth_type_trans`, fills checksum and hash information, and passes it up with `napi_gro_receive`.
2. Refills the ring with fresh buffers.
3. If it processed fewer packets than the budget, it calls `napi_complete_done` and re-enables the device interrupt. Otherwise it returns the budget, and the kernel polls again without an interrupt.

A poll function must never return more than the budget; doing so is a bug the core checks for. Memory for receive buffers is replenished in the poll function to avoid starving the ring, with a fallback if allocation fails.

### Transmit completion and queues

Completed transmit descriptors are cleaned in the same NAPI poll (or a separate one), unmapping DMA buffers and freeing `sk_buff`s with `napi_consume_skb`. Multi-queue devices have one transmit queue per CPU or flow group so cores do not contend on a lock; the stack picks a queue with a hash. Byte queue limits (BQL) bound how many bytes may be in flight to keep latency low.

### Interrupt moderation and affinity

Interrupt coalescing delays an interrupt until several packets arrive or a short timer expires, trading latency for CPU time. Adaptive schemes (dynamic interrupt moderation) adjust it by traffic. Each queue's MSI-X vector is assigned to a CPU through affinity, and RSS spreads flows, so receive processing scales with cores.

### Testing and observation

`ethtool -S` shows driver statistics, `ip -s link` shows counters, `/proc/net/softnet_stat` shows per-CPU softirq processing and budget exhaustion (the "time squeeze" column), and tracepoints (`net:*`, `napi:napi_poll`) show polling. In virtual machines, a driver for `virtio-net` can be read as the simplest complete example; `tcpdump` and `pktgen` (a kernel traffic generator) provide test load, and `veth` pairs allow a driver-free test of the stack's behaviour.

## Assessment: the good, the bad and the ugly

**The good.** NAPI makes the same driver efficient at low and high load, bounds latency, and gives fairness. The framework hides most queueing and offload work, so a basic driver is largely descriptor handling. Batching (GRO, page pools, `skb` bulk free) gives large performance gains without driver changes.

**The bad.** High-performance drivers are intricate: descriptor ring bookkeeping, memory ownership between CPU and device, barriers and error recovery. Offload and feature interactions produce subtle bugs (checksum or segmentation errors under particular tunnels). Budget and coalescing tuning are workload-specific.

**The ugly.** A ring that is never refilled leaves a card silently dropping packets. A lost wake-up of a stopped queue freezes transmission. Hardware bugs and errata force drivers to carry workarounds. Under overload, softirq work moves to `ksoftirqd`, which can add jitter.

## Applications beyond this domain

- **Virtualisation**: virtio-net, vhost and SR-IOV virtual functions all appear to the guest as ordinary NICs; understanding rings, interrupts and NAPI explains guest network performance and the role of vhost.
- **Cloud and data-centre networking**: XDP load balancers and packet filters run in the driver path.
- **High-frequency trading and telecom** use kernel bypass for latency.
- **Storage networking** (NVMe over TCP, iSCSI) rides the same stack.
- **Embedded gateways** tune interrupts and offloads on small CPUs.

## Examples

**A burst.** A card receives 100 packets in a microsecond. One interrupt masks the queue and schedules NAPI; the poll function takes 64, returns the budget and is called again for the other 36; when it sees an empty ring, it re-enables the interrupt. Only one interrupt was taken for 100 packets.

**A frozen queue.** A transmit completion handler forgets to call `netif_wake_queue` after freeing descriptors; the stack believes the device is full and the interface stops sending. A watchdog calls `ndo_tx_timeout`, which resets the device.

**A silent drop.** `ethtool -S` shows a growing `rx_no_buffer` counter: the poll function failed an allocation and did not refill the ring. A fallback that retries refilling at the next poll fixes it.

**Offload mismatch.** Packets through a VXLAN tunnel arrive with bad checksums at the receiver because the driver claimed a checksum offload that the card does not support for encapsulated traffic. Clearing the feature bit for tunnels with `ethtool -K` is a workaround; the driver fix reports the capability accurately.

## Related problems and ideas

- **Interrupts and deferral** (earlier topic): NAPI is the softirq pattern at its most developed.
- **DMA API** (earlier topic): descriptors and buffers.
- **eBPF and XDP** (next topics) attach to the driver receive path.
- **Queueing disciplines** (`tc`) shape what reaches `ndo_start_xmit`.
- **Virtio** specifications define the guest/host ring protocol.

## Active research

Research and development include zero-copy receive and transmit, io_uring networking, offloading the stack to smart NICs, better congestion control and queue management in the kernel, and reducing per-packet overhead with batching. Rust network driver abstractions are an early area (to verify the state of in-tree Rust network drivers).

## Future direction

Expect more pages-based receive paths, large packets (BIG TCP) and device memory transfers (devmem and similar zero-copy schemes), more programmability in drivers via XDP, and offload to DPUs.
