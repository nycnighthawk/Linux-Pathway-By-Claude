# Network drivers and NAPI: moving packets without drowning the CPU

## Define the problem

A network interface card turns signals on a wire into packets in memory, and packets in memory into signals. A modern card handles millions of packets per second. If each received packet raised an interrupt that the CPU had to service, the machine would spend all its time entering and leaving interrupt handlers, and under heavy load it could do nothing else. That failure has a name, *receive livelock*: the system is busy, yet it delivers no useful work. On the transmit side, the driver must queue frames fast, tell the stack when the card is full, and recover buffers when the card is done.

A network driver therefore has to cooperate with a stack that wants batching, backpressure and fairness, while it exploits hardware features such as multiple queues, checksum and segmentation offload, and interrupt moderation. This essay follows how the interrupt-per-packet design failed, how NAPI replaced it with a mix of interrupts and polling, and how the structure of a driver today follows from that answer.

## History and approaches

### One interrupt per packet

Early drivers copied each frame in the interrupt handler and passed it up. At 100 Mbit/s that was acceptable. At gigabit rates, receive livelock became a measured problem on Linux and other systems: throughput rose with load, peaked, and then fell, because interrupt handling consumed all the CPU time that the rest of the stack needed.

### NAPI

The "New API", introduced around the 2.5 series (authors and exact release should be checked), turned reception into a mix of interrupts and polling. The first interrupt disables further receive interrupts for that queue and schedules a poll function in softirq context. The poll function processes packets from the ring up to a *budget*, and when the ring drains it re-enables interrupts. Under low load, the system behaves like an interrupt-driven one. Under high load it behaves like a polled system, with bounded work per round and fairness among devices. The lesson was general: interrupts are good for infrequent events and polling is good for frequent ones, so a design that can switch between them gets both.

### Generic offloads

Segmentation offload lets the stack hand the driver one large buffer that the card splits into frames. Generic receive offload (GRO) merges consecutive packets of a flow into one before the stack processes them. Checksum offload lets the hardware compute or verify checksums. Receive-side scaling (RSS) hashes flows to separate hardware queues, each with its own interrupt and CPU. Each of these moves a per-packet cost to hardware or amortises it over a batch.

### XDP and kernel bypass

The eXpress Data Path runs an eBPF program in the driver's receive path, before an `sk_buff` is allocated, to drop, redirect or modify packets very early. AF_XDP and DPDK-style user-space drivers bypass the kernel stack entirely. The kernel's reply has been to make the in-kernel path faster, with page pools and batching.

### Virtual networking

`virtio-net` gives virtual machines a paravirtual NIC that shares rings with the host (`vhost-net` in the kernel, or `vhost-user` in a user-space switch), and the guest driver is an ordinary network driver using NAPI. Linux bridges, veth pairs and macvlan create software devices with the same driver interface.

## Current state

### The driver interface

A network driver allocates a `struct net_device` (`alloc_etherdev_mq` for Ethernet with several queues), fills a `struct net_device_ops` table and registers it with `register_netdev`. The key operations are these.

- `ndo_open` and `ndo_stop` bring the interface up and down: allocate rings, request interrupts, enable NAPI and start the queues.
- `ndo_start_xmit` is called by the stack with an `sk_buff` to transmit. The driver maps the buffer for DMA, writes a descriptor and tells the card. If the ring fills, it stops the queue (`netif_stop_queue`) and wakes it (`netif_wake_queue`) from the completion path, which is how backpressure reaches the stack. It returns `NETDEV_TX_OK`; returning `NETDEV_TX_BUSY` is discouraged.
- `ndo_set_rx_mode`, `ndo_set_mac_address`, `ndo_change_mtu`, `ndo_get_stats64`, `ndo_tx_timeout` and `ndo_bpf` (for XDP) cover the rest.

The `ethtool_ops` table exposes settings and statistics to the `ethtool` command: link state, ring sizes, offload flags, interrupt coalescing and counters.

### Receive with NAPI, step by step

The driver registers a poll function with `netif_napi_add`. In the interrupt handler it disables the queue's interrupt in the device and calls `napi_schedule`. The kernel runs the poll function from the network softirq with a budget, commonly 64, set by the driver and system parameters. The poll function does three things.

1. It processes up to `budget` completed descriptors. For each, it builds an `sk_buff` around the data (often by wrapping a page from a page pool with `build_skb` or `napi_build_skb`, to avoid copies), sets the protocol with `eth_type_trans`, fills in checksum and hash information, and passes the packet up with `napi_gro_receive`.
2. It refills the ring with fresh buffers.
3. If it processed fewer packets than the budget, it calls `napi_complete_done` and re-enables the device interrupt. Otherwise it returns the budget, and the kernel polls again with no interrupt.

A poll function must never return more than the budget, and the core checks for it. Receive buffers are replenished inside the poll function so the ring is not starved, with a fallback if allocation fails.

### Transmit completion and queues

Completed transmit descriptors are cleaned in the same NAPI poll, or in a separate one, which unmaps DMA buffers and frees `sk_buff`s with `napi_consume_skb`. Multi-queue devices have one transmit queue per CPU or flow group, so cores do not contend on a lock, and the stack picks a queue with a hash. Byte queue limits (BQL) bound how many bytes may be in flight to keep latency low.

### Interrupt moderation and affinity

Interrupt coalescing delays an interrupt until several packets arrive or a short timer expires, trading latency for CPU time. Adaptive schemes (dynamic interrupt moderation) adjust the setting to the traffic. Each queue's MSI-X vector is assigned to a CPU through affinity, and RSS spreads flows, so receive processing scales with the number of cores.

### Testing and observation

`ethtool -S` shows driver statistics, `ip -s link` shows counters, `/proc/net/softnet_stat` shows per-CPU softirq processing and budget exhaustion (the "time squeeze" column), and tracepoints (`net:*`, `napi:napi_poll`) show polling. In virtual machines, the driver for `virtio-net` can be read as the simplest complete example. `tcpdump` and `pktgen`, a kernel traffic generator, provide test load, and `veth` pairs allow a driver-free test of the stack's behaviour.

### The generalised pattern

Take an interrupt to learn that work exists, then switch interrupts off and poll in bounded batches until the work is gone, then switch them back on. The pattern works wherever a high-rate source meets a limited consumer: storage completion queues, USB, and high-rate sensors.

## Assessment: the good, the bad and the ugly

**The good.** NAPI makes the same driver efficient at low and high load, bounds latency, and gives fairness. The framework hides most queueing and offload work, so a basic driver is largely descriptor handling. Batching (GRO, page pools, bulk `skb` freeing) gives large performance gains without driver changes.

**The bad.** High-performance drivers are intricate: descriptor-ring bookkeeping, memory ownership between CPU and device, barriers and error recovery. Offload and feature interactions produce subtle bugs, such as checksum or segmentation errors under particular tunnels. Budget and coalescing tuning are workload-specific.

**The ugly.** A ring that is never refilled leaves a card silently dropping packets. A lost wake-up of a stopped queue freezes transmission. Hardware bugs and errata force drivers to carry workarounds. Under overload, softirq work moves to `ksoftirqd`, which can add jitter.

## Applications beyond this domain

- **Virtualisation.** virtio-net, vhost and SR-IOV virtual functions all appear to the guest as ordinary NICs, so understanding rings, interrupts and NAPI explains guest network performance and the role of vhost.
- **Cloud and data-centre networking.** XDP load balancers and packet filters run in the driver path.
- **High-frequency trading and telecommunications** use kernel bypass for latency.
- **Storage networking** (NVMe over TCP, iSCSI) rides the same stack.
- **Embedded gateways** tune interrupts and offloads on small CPUs.

## Examples

**A burst, step by step.** A card receives 100 packets in a microsecond. The first one raises an interrupt, which masks the queue and schedules NAPI. The poll function takes 64 packets and returns the budget, so the kernel calls it again. The second call takes the remaining 36, sees an empty ring, completes NAPI and re-enables the interrupt. One interrupt was taken for 100 packets.

**A frozen queue.** A transmit completion handler forgets to call `netif_wake_queue` after freeing descriptors. The stack believes the device is full, and the interface stops sending. A watchdog calls `ndo_tx_timeout`, which resets the device.

**A silent drop.** `ethtool -S` shows a growing `rx_no_buffer` counter: the poll function failed an allocation and did not refill the ring. A fallback that retries the refill at the next poll fixes it.

**Offload mismatch.** Packets through a VXLAN tunnel arrive with bad checksums at the receiver, because the driver claimed a checksum offload that the card does not support for encapsulated traffic. Clearing the feature bit for tunnels with `ethtool -K` is a workaround, and the driver fix reports the capability accurately.

## Related problems and ideas

### Related

- **Interrupts and deferral** (an earlier topic): NAPI is the softirq pattern at its most developed.
- **The DMA API** (an earlier topic) governs descriptors and buffers.
- **eBPF and XDP** (the next topic) attach to the driver's receive path.
- **Queueing disciplines (`tc`)** shape what reaches `ndo_start_xmit`.
- **Virtio** specifications define the guest-host ring protocol.

### Opposing approaches

- **Pure polling and kernel bypass.** DPDK and similar frameworks dedicate cores to poll the card from user space. They deliver the lowest latency and the highest rates, and they give up the kernel's stack, its tools and sharing of the CPU.
- **Pure interrupts with strong moderation.** Hardware coalescing alone, with no polling in the driver, is simpler and works for modest rates, but it cannot adapt to bursts the way NAPI does.
- **In-kernel fast paths (XDP).** The compromise: stay inside the kernel and driver, but run a verified program before the heavy stack is invoked, so the common case is cheap.
- **Offloading the whole stack.** Smart NICs and DPUs run parts of the network stack on the card, so the host sees fewer packets. The price is another operating environment to manage and secure.

## Active research

Research and development include zero-copy receive and transmit, io_uring networking, offloading the stack to smart NICs, better congestion control and queue management in the kernel, and reducing per-packet overhead with batching. Rust network-driver abstractions are an early area, and the state of in-tree Rust network drivers should be checked against the current kernel.

## Future direction

Expect more page-based receive paths, large packets (BIG TCP) and device-memory transfers (devmem and similar zero-copy schemes), more programmability in drivers through XDP, and offload to data-processing units. The lasting idea for a learner is the hybrid: interrupts for the quiet times, polling for the busy ones, and a budget that keeps one device from monopolising the CPU.
