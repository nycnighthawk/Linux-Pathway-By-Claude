# The VFS and a simple filesystem: one interface for many ways of storing files

## Define the problem

A Linux system mounts many kinds of filesystem at once: ext4 on the root disk, XFS on data volumes, FAT on a USB stick, NFS from a server, `tmpfs` in memory, `proc` and `sysfs` that store nothing at all. Programs use the same system calls on all of them: `open`, `read`, `write`, `stat`, `readdir`, `rename`. The kernel therefore needs a layer that defines what a filesystem is, caches the common work (name lookups, file data, metadata), enforces permissions and leaves each implementation only the parts that are really specific to its format or protocol.

That layer is the virtual filesystem switch, VFS. Writing a simple filesystem is the standard way to learn it, because a small filesystem needs only a handful of operations and shows how the generic layer calls into a driver.

## History and approaches

**A common interface.** Sun introduced the vnode/VFS design in the 1980s to support NFS beside the local filesystem, and System V and BSD derivatives adopted variants. Linux's VFS (from the early 1990s, when the Minix filesystem gave way to ext) has four central objects that descend from Unix tradition.

**Object-oriented C.** Each object has a table of function pointers that the filesystem fills in. The VFS code calls through the table without knowing the type. This is the same pattern as `file_operations` for character devices.

**Caches in front of everything.** The *dentry cache* maps names to inodes so path lookup rarely touches storage; the *inode cache* holds metadata; the *page cache* holds file data and is the reason repeated reads are fast and writes are asynchronous. Filesystems take part in these caches rather than owning them.

**Libraries for simple cases.** Many in-memory and synthetic filesystems share helper code, `libfs`, which provides directory operations, lookups and `simple_fill_super`. `ramfs` is only a few hundred lines, and `tmpfs` extends it with swap and size limits. `debugfs`, `configfs`, `sysfs` (via `kernfs`), `procfs` and cgroupfs are all filesystems that present kernel state.

**FUSE and user space.** The Filesystem in Userspace interface forwards VFS requests to a user-space daemon over `/dev/fuse`, which makes a new filesystem a program instead of a kernel module. It trades performance and some semantics for safety and ease of development. Network and cloud filesystems commonly use it.

**New mount API.** The old `mount()` system call with a string of options gave way to a staged interface (`fsopen`, `fsconfig`, `fsmount`, `move_mount`) that backs the in-kernel `fs_context` structure. A new filesystem registers a context initialiser instead of a `mount` callback.

## Current state

### The four objects

- **super_block**: one per mounted filesystem instance. It holds the block size, the root dentry, the filesystem type, and the `super_operations` table (allocate and free inodes, write back, sync, report statistics, remount).
- **inode**: one per file or directory, holding mode, owner, size, timestamps, link count and a pointer to `inode_operations` (`lookup`, `create`, `mkdir`, `unlink`, `rename`, `getattr`, `setattr`, `permission`) and, for regular files, `file_operations` and an `address_space` with `address_space_operations`.
- **dentry**: a name inside a directory pointing at an inode (or marked negative if the name does not exist). The kernel keeps dentries in the dcache; the filesystem creates them in `lookup` by calling `d_add` or `d_splice_alias`.
- **file**: one per open file description, holding the position and flags, and a pointer to `file_operations` (`read_iter`, `write_iter`, `llseek`, `iterate_shared` for directories, `fsync`, `mmap`).

### Registration and mounting

A filesystem module declares a `struct file_system_type` with a name, an `init_fs_context` function and a `kill_sb` function, and registers it with `register_filesystem`. After that, `mount -t name` finds it. Mounting calls the context's `get_tree`, which for a filesystem with no backing device is `get_tree_nodev`, and then `fill_super` initialises the superblock: set magic number and block size, assign `s_op`, create the root inode with `new_inode` and `d_make_root`. For a disk filesystem, `get_tree_bdev` opens the block device first, and `fill_super` reads the on-disk superblock through the buffer cache or `sb_bread`.

### The minimal set of operations

A read-only filesystem on a block device needs:

1. `fill_super`: validate the superblock and set up the root.
2. `lookup` in directory inode operations: scan directory data for a name, find the inode number, read the inode (`iget_locked`, `unlock_new_inode`), and attach it to the dentry.
3. `iterate_shared` in directory file operations: emit each entry with `dir_emit`.
4. File data: either `read_iter` implemented with `generic_file_read_iter` plus `read_folio` or `readahead` in `address_space_operations`, which map a file offset to a disk block and submit the read.
5. `getattr` is usually handled by generic code once the inode is filled in.

A read-write filesystem adds allocation (bitmaps or extents), `create`, `mkdir`, `unlink`, `rename`, `write_begin` and `write_end` (or `iomap` operations), `write_inode` or dirty-inode tracking, `fsync`, and, if it wants crash safety, a journal or copy-on-write scheme. The page cache holds dirty pages; the writeback code calls the filesystem to write them out.

### The TinyFS exercise

The lab in this topic does the reading half in user space for a made-up format: a superblock, an inode table with direct block pointers, and directories made of fixed-size entries. The functions it asks for are the same ones as the kernel list above: find the inode, collect data from blocks while respecting the file size, search a directory by name, and report errors with the right classes (`ENOENT`, `ENOTDIR`, `EISDIR`).

### Concurrency, caches and consistency

VFS holds per-inode locks (`i_rwsem`) around directory changes and file writes, and the dentry locks and reference counts keep names valid. A filesystem must follow the documented lock order and must not assume anything the VFS has not guaranteed. A name that does not exist becomes a *negative dentry*, remembered so a repeated lookup is cheap. Rename is the hardest operation: it must be atomic with respect to other lookups, and cross-directory rename has a dedicated lock ordering. After a crash, a journaling or log-structured filesystem replays or ignores incomplete changes; others rely on `fsck`.

### Building and testing

A filesystem can be developed as a module (see the modules topic) and tested in a virtual machine with a loop device or a disk image created by a `mkfs`-like tool the developer writes. The community test suite for filesystems, `xfstests` (also called `fstests`), runs hundreds of generic tests against any mounted filesystem, checking POSIX behaviour, crash consistency and corner cases. Fuzzing with corrupted images is the other pillar: mounting untrusted images has produced many security bugs, so any filesystem that may be mounted from removable media must treat its on-disk data as hostile.

### Alternatives and hybrids

Overlay filesystems (`overlayfs`) stack a writable upper layer on read-only lower layers and underpin container images. `fuse` offers user-space filesystems. `9p` and `virtiofs` share a host directory with a guest and are the standard for virtual machines; virtiofs uses the FUSE protocol over a virtio queue and shared memory for speed. Network filesystems implement the same VFS tables over a protocol.

## Assessment: the good, the bad and the ugly

**The good.** The VFS lets a new filesystem be a few hundred lines of code that benefit from the generic caches, permission checks and system call layer. Helper libraries cover synthetic filesystems, and `xfstests` provides a shared quality bar.

**The bad.** The interface is large and its rules, especially for locking, reference counting and rename, are intricate and only partly documented. A subtle mistake produces rare corruption or deadlock. Moving APIs (page to folio, the new mount API, iomap) mean example code ages quickly.

**The ugly.** Mounting corrupted or malicious images is a long-standing attack surface. Some filesystems have effectively one maintainer. Semantics differ between filesystems at the edges (timestamps resolution, case folding, rename flags, behaviour after a crash), and applications that rely on a particular filesystem's behaviour break elsewhere.

## Applications beyond this domain

- **Containers**: overlayfs, bind mounts and mount namespaces are VFS features and provide the file isolation containers rely on.
- **Virtual machines**: virtiofs and 9p give guests access to host directories; image formats such as qcow2 sit below the guest's filesystem.
- **Observability and control**: debugfs, tracefs, cgroupfs and sysfs expose kernel state as files.
- **Data engineering**: understanding page cache, readahead and `fsync` explains database durability and performance.
- **Security tools** use fanotify and LSM hooks at the VFS boundary to monitor file access.

## Examples

**A read-only image driver.** A developer writes a module that mounts a TinyFS image through a loop device. `ls` triggers `lookup` and `iterate_shared`; `cat` triggers reads through the page cache. A corrupt image with an out-of-range block pointer is rejected in `inode` read with an error instead of reading beyond the device.

**A synthetic filesystem.** A driver exposes counters as files in a new filesystem built on `libfs`: `simple_fill_super` takes a table of names, sizes and operations, so no on-disk format exists.

**A rename race.** Two processes rename directories into each other's trees; the VFS's rename lock and ancestor checks prevent a loop in the directory graph, which a naive implementation would allow.

**A crash test.** `xfstests` writes data, calls `fsync`, simulates power loss with a device-mapper target and checks that the filesystem is consistent after replay.

## Related problems and ideas

- **Memory allocation and the page cache** (previous topic) underpin file data.
- **Block layer and I/O scheduling** carry the reads and writes below the filesystem.
- **Locking** (earlier topic) governs inode and dentry state.
- **Security modules and permissions** hook in at the VFS layer.
- **Persistent memory and DAX** let filesystems bypass the page cache.

## Active research

Active work includes crash-consistency testing with tools that explore failure points, formal verification of small filesystems, copy-on-write designs and zoned-storage support, large folios in the page cache, safer filesystem implementations in Rust, and shared filesystems for virtual machines with lower overhead (to verify the state of Rust filesystem work).

## Future direction

Expect larger folios everywhere, `iomap`-based I/O in more filesystems, the new mount API as the only mount path, and more filesystems implemented in Rust or in user space where safety matters more than raw speed.
