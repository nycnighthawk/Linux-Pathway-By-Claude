# A PCI driver for the QEMU edu device: from enumeration to registers, interrupts and DMA

## Define the problem

Most devices in servers, desktops and virtual machines hang off PCI or its descendant PCI Express. A driver for such a device has to recognise it by identifier, switch it on, find where its registers live in the address space, program it, receive its interrupts and sometimes let it move data to and from memory on its own. A beginner needs a device where all of that is possible but nothing is dangerous. The QEMU `edu` device exists for exactly this: a small, documented virtual PCI device with an identifier register, a liveness check, a factorial engine, interrupts and a DMA engine. It does nothing useful and teaches the whole lifecycle.

## History and approaches

**The bus.** PCI arrived in the early 1990s as a 32-bit shared parallel bus with configuration space for automatic enumeration. PCI Express replaced the shared bus with point-to-point serial links but kept software compatibility: the same configuration header, the same base address registers and the same driver model, with extended configuration space and new capabilities.

**Configuration space.** Each function has a 256-byte (or 4096-byte on PCIe) configuration space. It starts with a vendor ID and device ID, class code, revision, and base address registers (BARs) that tell the system how much address space the device wants. Firmware or the kernel assigns addresses; the driver reads the result. Capability lists in the space describe optional features: MSI, MSI-X, power management, PCIe link control, advanced error reporting and more.

**Interrupts.** Legacy PCI uses four shared interrupt pins. Message-signalled interrupts (MSI and MSI-X) replace the pins with memory writes to a special address, which allows many independent vectors per device and removes sharing. Modern drivers request vectors through one helper and let the kernel choose the best mode.

**Direct memory access.** A device moves data by acting as a bus master. The kernel's DMA API hides address translation, IOMMUs and cache coherence: the driver asks for memory and a *bus address* for the device, rather than using a physical address.

**User-space alternatives.** `UIO` and `VFIO` expose a device's registers and interrupts to user space; VFIO adds IOMMU-based isolation and is the basis of device assignment to virtual machines. Many modern drivers for accelerators and network cards are written partly or wholly in user space this way.

**The edu device.** QEMU's educational device was written for a university course on device drivers and has been part of QEMU since 2.4 (to verify). It is enabled with `-device edu` and appears as PCI vendor `0x1234`, device `0x11e8`. Its documentation lists the registers and behaviours that the driver exercises.

## Current state

### Looking at the hardware

From a shell in the guest: `lspci -nn` lists devices with vendor and device IDs; `lspci -vv` shows BARs, capabilities, the bound kernel driver and interrupt mode; `/sys/bus/pci/devices/0000:00:04.0/` has `vendor`, `device`, `class`, `resource` (the BAR ranges), `irq`, `driver` (a symlink once bound) and a `resourceN` file per BAR that user space can `mmap`. `setpci` reads and writes configuration registers. With QEMU, `-device edu` adds one device to a machine that has a PCI bus; Linux sees it without any special configuration.

### The driver skeleton

A PCI driver defines an ID table with vendor and device IDs (`PCI_DEVICE(0x1234, 0x11e8)`), exports it with `MODULE_DEVICE_TABLE(pci, ...)` so udev can autoload the module, and fills a `struct pci_driver` with `name`, `id_table`, `probe` and `remove`. `module_pci_driver` generates registration. The core calls `probe` for each matching function with a `struct pci_dev`.

### Probe, step by step

1. **Enable the device.** `pcim_enable_device(pdev)` turns on memory and I/O decoding, wakes the device and arranges automatic disabling on removal (the `pcim_` prefix means managed).
2. **Become bus master** with `pci_set_master` when the device does DMA.
3. **Claim and map BARs.** `pcim_iomap_regions` (or `pcim_iomap_region`) reserves a BAR and maps it, returning an address usable with `readl` and `writel`. Never dereference the pointer: the accessor functions provide the right barriers and byte order (PCI registers are little-endian, so on big-endian CPUs they swap).
4. **Check the device.** Read the ID register and fail with `-ENODEV` if it is not what you expect; do a liveness test and record the revision.
5. **Set the DMA mask** with `dma_set_mask_and_coherent`, giving the address width the device can generate (the edu DMA engine handles 28 bits, so a mask of 28 bits is appropriate, to verify in its documentation).
6. **Allocate interrupts.** `pci_alloc_irq_vectors(pdev, 1, 1, PCI_IRQ_ALL_TYPES)` obtains one vector of whatever type is available; `pci_irq_vector` returns its Linux number to pass to `devm_request_irq`.
7. **Register an interface to user space**, for example a misc device exposing `read`, `write` and `ioctl` as in the first topic of this course.

If any step fails, the managed helpers release what has been acquired, and `probe` returns the error.

### Talking to the registers

The edu device offers: an ID register (`0x00`), a liveness register (`0x04`) that returns the bitwise complement of what is written, a factorial register (`0x08`) that computes `n!` after a write and clears a busy bit in the status register (`0x20`) when done, an interrupt status and acknowledge pair, and a DMA engine with source, destination, count and command registers. The driver writes `n` and either polls status, always with a bounded loop, or enables the completion interrupt and sleeps until the handler wakes it. Register offsets and semantics should be checked against the QEMU documentation of the device (to verify).

Because a PCI write is *posted*, a write may not have reached the device when the CPU continues. To make sure it has, read back from the same device (a "flush read"). Ordering between registers and memory (descriptors in RAM, doorbell in a register) needs explicit barriers, which `writel` provides relative to earlier memory writes and `writel_relaxed` does not.

### Interrupts

The handler runs in interrupt context with locking and sleeping restrictions (the next topic details them). It reads the interrupt status register, acknowledges the cause, records the result and wakes a waiter. A handler for a shared legacy line must return `IRQ_NONE` if its device did not raise the interrupt. For long work, use a threaded handler (`devm_request_threaded_irq`) or schedule a workqueue.

### DMA

The simplest safe pattern is a *coherent* buffer from `dma_alloc_coherent` (or the managed variant), which returns both a CPU pointer and a bus address; the driver programs the bus address into the device registers. For existing buffers the *streaming* API (`dma_map_single`, `dma_unmap_single`, and the `dma_sync_*` calls) moves ownership between CPU and device and handles cache maintenance. The edu DMA engine copies between device-internal memory and a bus address, with a command register that starts the transfer and sets a direction and an interrupt option; the driver should poll a status bit or wait for the interrupt, and only then read the buffer.

### Testing in a VM

Run the guest with `-device edu` (and `-device edu,dma_mask=...` as documented), load the module, check `dmesg` for the probe message and exercise the device through its user-space interface. For driver developers, `-trace` options in QEMU show every register access, which makes bugs in the sequence of operations visible from the host side. Tracing, KASAN and lockdep from the debugging topic of the previous course apply here as well.

## Assessment: the good, the bad and the ugly

**The good.** PCI offers uniform enumeration, resources and interrupt handling, so one driver pattern applies across thousands of devices. The managed `pcim_` and `devm_` helpers make the probe path short. An emulated device lets learners and testers experiment with no hardware, and QEMU's tracing shows the device's side of every access.

**The bad.** Real devices have errata, quirks and undocumented behaviour that simulated ones lack, so skills transfer only partly. Posted writes, barriers and DMA coherence are easy to get subtly wrong and show up as rare, load-dependent failures. Documentation for real hardware is often incomplete.

**The ugly.** A driver that polls without a bound can hang a CPU forever; a wrong DMA address can corrupt arbitrary memory when no IOMMU is present; a handler that does not acknowledge the interrupt causes an interrupt storm that disables the line. Hot-unplug races between the remove path and in-flight I/O are a persistent source of bugs.

## Applications beyond this domain

- **Virtualisation**: virtio devices appear on a PCI bus (`virtio-pci`), so understanding BARs, capabilities and MSI-X explains how guests find paravirtual devices; the same enumeration underlies device assignment with VFIO.
- **Accelerators, NICs and storage controllers** all follow the same probe and interrupt pattern, with larger queues and DMA descriptors.
- **Firmware and hypervisors** enumerate PCI in the same way.
- **Security research** studies malicious or buggy devices and the IOMMU's role in containing them.
- **Embedded systems** with PCIe root complexes use the identical driver interface.

## Examples

**Reading an ID.** After `modprobe edu_demo`, the log shows `edu: id=0x010000ed` and a liveness check passing. If the ID check had failed, probe would return `-ENODEV` and `lspci -k` would show no bound driver.

**A factorial through ioctl.** A user program calls an ioctl with `n = 10`; the driver writes the register, waits for completion and returns 3628800.

**A stuck busy bit.** A tracing session shows the driver polling status 1000 times and returning `-ETIMEDOUT`: the device never cleared the bit because the driver wrote to the wrong offset. QEMU's trace of register writes reveals it.

**Interrupt mode.** `lspci -vv` shows MSI enabled with one vector for the device, and `/proc/interrupts` shows the count increasing per completion.

## Active research

Research areas include formally verifying driver and device interactions, fuzzing drivers against emulated malicious devices (QEMU-based device fuzzers), IOMMU-based isolation and confidential-computing guests that treat the host-provided devices as untrusted, and Rust abstractions for PCI drivers that encode lifetimes of BAR mappings in types (to verify the status of Rust PCI support).

## Future direction

Expect more driver code to treat the device as untrusted input, more use of managed resources and Rust abstractions, and more devices exposed to guests through virtio and VFIO rather than emulated legacy hardware.
