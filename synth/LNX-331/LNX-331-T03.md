# A PCI driver for the QEMU edu device: from enumeration to registers, interrupts and DMA

## Define the problem

Most devices in servers, desktops and virtual machines hang off PCI or its descendant, PCI Express. A driver for such a device has to do a sequence of jobs. It must recognise the device by identifier, switch it on, find where its registers live in the address space, program it, receive its interrupts, and sometimes let it move data to and from memory on its own. A beginner needs a device where all of this is possible and nothing is dangerous.

The QEMU `edu` device exists for exactly that. It is a small, documented virtual PCI device with an identifier register, a liveness check, a factorial engine, interrupts and a DMA engine. It does nothing useful, and that is the point: every line of the driver is about the bus and the device, not about an application. This essay builds the driver in the order a real one is built, and explains at each step the reason for the rule.

## History and approaches

### The bus

PCI arrived in the early 1990s as a 32-bit shared parallel bus with a *configuration space* that allowed automatic enumeration. PCI Express replaced the shared bus with point-to-point serial links but kept software compatibility: the same configuration header, the same base address registers and the same driver model, with extended configuration space and new capabilities. A driver written for a 1990s card therefore has the same skeleton as one for a current accelerator.

### Configuration space

Each function has a configuration space of 256 bytes, or 4096 on PCI Express. It starts with a vendor ID and device ID, a class code, a revision and *base address registers* (BARs) that tell the system how much address space the device wants. Firmware or the kernel assigns addresses and the driver reads the result. A list of *capabilities* describes optional features: MSI, MSI-X, power management, PCI Express link control, advanced error reporting and more.

### Interrupts

Legacy PCI uses four shared interrupt pins, which forces drivers to ask each device whether it was the one that interrupted. Message-signalled interrupts (MSI and MSI-X) replace the pins with a memory write to a special address, which allows many independent vectors per device and removes sharing. Modern drivers request vectors through one helper and let the kernel choose the best mode.

### Direct memory access

A device moves data by acting as a bus master. The kernel's DMA API hides address translation, IOMMUs and cache coherence: the driver asks for memory and for a *bus address* that the device can use, instead of using a physical address directly. Early drivers used physical addresses and broke on any machine with an IOMMU or a bounce buffer, and the API grew in response.

### User-space alternatives

`UIO` and `VFIO` expose a device's registers and interrupts to user space. VFIO adds IOMMU-based isolation and is the basis of device assignment to virtual machines. Many drivers for accelerators and network cards are now written partly or wholly in user space this way, and the history of PCI drivers is in part the history of choosing where the driver lives.

### The edu device

QEMU's educational device was written for a university course on device drivers and has been part of QEMU since version 2.4 (to verify). It is enabled with `-device edu` and appears as PCI vendor `0x1234`, device `0x11e8`. Its documentation lists the registers and behaviours that a driver exercises.

## Current state

### Looking at the hardware first

From a shell in the guest, `lspci -nn` lists devices with their vendor and device IDs. `lspci -vv` shows BARs, capabilities, the bound kernel driver and the interrupt mode. The directory `/sys/bus/pci/devices/0000:00:04.0/` holds `vendor`, `device`, `class`, `resource` (the BAR ranges), `irq`, `driver` (a symlink once bound) and one `resourceN` file per BAR that user space can map. `setpci` reads and writes configuration registers. With QEMU, `-device edu` adds one device to a machine that has a PCI bus, and Linux sees it with no special configuration.

### The driver skeleton

A PCI driver defines an ID table with the vendor and device IDs (`PCI_DEVICE(0x1234, 0x11e8)`), exports it with `MODULE_DEVICE_TABLE(pci, ...)` so that `udev` can autoload the module, and fills a `struct pci_driver` with `name`, `id_table`, `probe` and `remove`. `module_pci_driver` generates the registration. The core calls `probe` for each matching function with a `struct pci_dev`.

### Probe, step by step

1. **Enable the device.** `pcim_enable_device(pdev)` turns on memory and I/O decoding, wakes the device, and arranges automatic disabling on removal (the `pcim_` prefix means managed).
2. **Become bus master** with `pci_set_master` when the device performs DMA.
3. **Claim and map the BARs.** `pcim_iomap_regions` reserves a BAR and maps it, giving an address usable with `readl` and `writel`. Newer kernels deprecate the multi-BAR helper in favour of a single-region form, `pcim_iomap_region`, so the target kernel's documentation decides which to use. Never dereference the pointer directly: the accessors provide the right barriers and byte order, since PCI registers are little-endian and a big-endian CPU must swap.
4. **Check the device.** Read the ID register and fail with `-ENODEV` if it is not what was expected; do a liveness test and record the revision.
5. **Set the DMA mask** with `dma_set_mask_and_coherent`, giving the address width the device can generate. The edu DMA engine handles 28 bits, so a 28-bit mask is appropriate (check the device documentation).
6. **Allocate interrupts.** `pci_alloc_irq_vectors(pdev, 1, 1, PCI_IRQ_ALL_TYPES)` obtains one vector of whatever type is available, and `pci_irq_vector` returns its Linux number to pass to `devm_request_irq`.
7. **Register an interface to user space**, for example a misc device with `read`, `write` and `ioctl` as in the first topic of this course.

If any step fails, the managed helpers release what was acquired and `probe` returns the error.

### Talking to the registers

The edu device offers an ID register (`0x00`), a liveness register (`0x04`) that returns the bitwise complement of what was written, a factorial register (`0x08`) that computes `n!` after a write and clears a busy bit in the status register (`0x20`) when done, an interrupt status and acknowledge pair, and a DMA engine with source, destination, count and command registers. The driver writes `n` and then either polls the status register, always with a bounded loop, or enables the completion interrupt and sleeps until the handler wakes it. The offsets and semantics should be checked against QEMU's documentation of the device.

Because a PCI write is *posted*, it may not have reached the device when the CPU carries on. To make sure it has, read back from the same device (a "flush read"). Ordering between registers and memory, for example descriptors in RAM and a doorbell register, needs explicit barriers. `writel` provides them relative to earlier memory writes, and `writel_relaxed` does not.

### Interrupts

The handler runs in interrupt context, with restrictions on locking and sleeping that the next topic details. It reads the interrupt status register, acknowledges the cause, records the result and wakes a waiter. A handler for a shared legacy line must return `IRQ_NONE` if its device did not raise the interrupt. For long work, use a threaded handler (`devm_request_threaded_irq`) or schedule a workqueue.

### DMA

The simplest safe pattern is a *coherent* buffer from `dma_alloc_coherent`, or its managed variant, which returns both a CPU pointer and a bus address. The driver programs the bus address into the device registers. For buffers that already exist, the *streaming* API (`dma_map_single`, `dma_unmap_single` and the `dma_sync_*` calls) moves ownership between the CPU and the device and handles cache maintenance. The edu DMA engine copies between device-internal memory and a bus address, with a command register that starts the transfer, sets a direction and offers an interrupt option. The driver should poll a status bit or wait for the interrupt, and only then read the buffer.

### Testing in a virtual machine

Run the guest with `-device edu`, load the module, check `dmesg` for the probe message and exercise the device through its user-space interface. QEMU's `-trace` options show every register access, which makes mistakes in the sequence of operations visible from the host side. The tracing, KASAN and lockdep tools from the debugging topic of the previous course apply here too.

### The generalised pattern

Match by identifier, enable, map, check, configure, request interrupts, register an interface, and let managed resources unwind failures. The same seven steps, with larger queues and more capabilities, describe a network card, a storage controller or an accelerator.

## Assessment: the good, the bad and the ugly

**The good.** PCI offers uniform enumeration, resources and interrupt handling, so one driver pattern serves thousands of devices. The managed `pcim_` and `devm_` helpers make the probe path short. An emulated device lets learners and testers experiment without hardware, and QEMU's tracing shows the device's side of every access.

**The bad.** Real devices have errata, quirks and undocumented behaviour that a simulated one lacks, so skills transfer only in part. Posted writes, barriers and DMA coherence are easy to get subtly wrong, and the failures appear as rare, load-dependent faults. Documentation for real hardware is often incomplete.

**The ugly.** A driver that polls without a bound can hang a CPU for ever. A wrong DMA address can corrupt arbitrary memory when no IOMMU is present. A handler that does not acknowledge the interrupt causes an interrupt storm that disables the line. Hot-unplug races between the remove path and in-flight I/O are a persistent source of bugs.

## Applications beyond this domain

- **Virtualisation.** Virtio devices appear on a PCI bus (`virtio-pci`), so understanding BARs, capabilities and MSI-X explains how guests find paravirtual devices. The same enumeration underlies device assignment with VFIO.
- **Accelerators, network cards and storage controllers** follow the same probe and interrupt pattern, with larger queues and DMA descriptors.
- **Firmware and hypervisors** enumerate PCI in the same way.
- **Security research** studies malicious or buggy devices and the IOMMU's role in containing them.
- **Embedded systems** with PCI Express root complexes use the identical driver interface.

## Examples

**Reading an ID.** After loading the module, the log shows `edu: id=0x010000ed` and a passing liveness check. Had the ID check failed, probe would have returned `-ENODEV` and `lspci -k` would show no bound driver, which is the first thing to check when a driver seems to do nothing.

**A factorial through ioctl, step by step.** A user program calls an ioctl with `n = 10`. The driver writes 10 to the factorial register, enables the completion interrupt, and sleeps on a wait queue. The device computes, raises an interrupt, and the handler reads the status register, acknowledges the cause and wakes the sleeper. The driver then reads the result register and returns 3628800 to the program.

**A stuck busy bit.** A tracing session shows the driver polling the status register a thousand times and returning `-ETIMEDOUT`. The device never cleared the bit because the driver wrote to the wrong offset. QEMU's trace of register writes shows it at once, a debugging power that real hardware rarely offers.

**Interrupt mode.** `lspci -vv` shows MSI enabled with one vector for the device, and `/proc/interrupts` shows the count rising by one per completion.

## Related problems and ideas

### Related

- **Character devices** (the first topic) supply the user-space interface for such a driver.
- **Interrupts, workqueues and timers** (the next topic) cover the handler's context rules.
- **Locking** governs the state shared between handler and process context.
- **The DMA API and memory allocation** (a later topic) go deeper into buffers and mappings.

### Opposing approaches

- **VFIO and UIO.** A driver in user space avoids kernel crashes, can be written in any language, and is easier to debug, at the cost of interrupt latency and of access to kernel services. For high-rate devices, such as network cards driven by polling frameworks, the trade-off favours user space.
- **Do not use a driver: use a virtio device.** A guest that needs a fast NIC or disk usually should not emulate a PCI card with a custom driver at all. Virtio gives a standard queue interface, and a guest driver already exists.
- **Programmed I/O.** A simple device can be driven entirely with register reads and writes and no DMA. It is simpler to write and to verify, and it is wasteful for bulk data, which is why DMA exists.

## Active research

Research areas include formal verification of the interactions between drivers and devices; fuzzing drivers against emulated malicious devices, with QEMU-based device fuzzers; IOMMU-based isolation, and confidential-computing guests that treat host-provided devices as untrusted; and Rust abstractions for PCI drivers that encode the lifetime of BAR mappings in types. The status of Rust PCI support should be checked against the target kernel.

## Future direction

Expect more driver code to treat the device as untrusted input, more use of managed resources and Rust abstractions, and more devices exposed to guests through virtio and VFIO and fewer through emulated legacy hardware. For a learner, the edu driver's steps are the stable part: they change in names, not in order.
