# Running guests on Linux: KVM, QEMU, libvirt and the tools above them

## Define the problem

A processor runs one operating system at a time, and an operating system assumes it owns the machine: it programs the interrupt controller, edits page tables, talks to the disk controller and decides which task runs where. To run several such systems side by side, something has to trick each of them into believing it has exclusive hardware while keeping them from damaging each other or the host. That something is a hypervisor. The practical question for an administrator is not how a hypervisor works in the abstract but how to obtain a fleet of isolated guests, each with a defined amount of memory, CPU, disk and network, that can be created, started, inspected, copied and destroyed by scripts rather than by hand.

On Linux the answer is split across layers that grew separately. The kernel module **KVM** turns the processor's virtualisation extensions into a device node, `/dev/kvm`, that a user process can drive. **QEMU** is that user process: it emulates the board, the firmware interface, the disk and network controllers and the display, and it hands the CPU work to KVM. **libvirt** is a management daemon and API that remembers each guest as an XML description, starts QEMU with a matching long command line, applies security labels, wires up storage and networks, and offers one vocabulary to many hypervisors. **virsh** and **virt-install** are command-line clients of libvirt, and `virt-manager` or Cockpit are graphical ones. A beginner who meets all four names at once cannot tell which one is responsible for a failure, and that confusion is the gap this topic closes.

The failure modes show the stakes. A guest that starts without hardware acceleration runs perhaps one to two orders of magnitude slower and nobody is told. A guest started by hand with an ad hoc QEMU command line disappears from every inventory tool and shares a security context with the invoking user. A guest whose disk is attached with the wrong bus is slow, and a guest installed with a 'default' configuration may be impossible to migrate later because the machine type or CPU model was never pinned. Whether a host is "a KVM host" depends on a short checklist: the CPU flags, the kernel modules, the permissions on `/dev/kvm`, the libvirt daemons and their sockets, a storage pool and a network.

This slice covers the whole path from bare host to running, manageable guest: the architecture of the stack, the host preparation checks, the connection URIs, the lifecycle commands, the domain XML document that is the real source of truth, installation with `virt-install`, and the diagnostics that tell you which layer misbehaves. Templates and snapshots (T02), networking (T03), tuning (T04), migration (T05), containers (T06), nested virtualisation (T07) and cluster managers (T08) build on it.

## History and approaches

Early x86 virtualisation had a hard obstacle: the architecture contained instructions that behaved differently in user and kernel mode without trapping, so a guest kernel could not simply be run deprivileged and trapped on privileged operations. The first commercial products, from VMware in 1999, worked around this by scanning guest code and rewriting the troublesome instructions on the fly (binary translation). The Xen project, published in 2003, took the opposite route called paravirtualisation: modify the guest kernel to ask the hypervisor for privileged work through explicit calls. Xen was fast but needed modified guests, and it put a thin hypervisor under a privileged first guest (dom0), which made it a separate system to install and operate, as the Debian handbook still describes when it contrasts Xen with KVM [src: debian-handbook fa569c10be65971a].

Intel and AMD answered in 2005 and 2006 with hardware extensions (VT-x and AMD-V) that added a new execution mode in which a guest kernel runs at full privilege yet traps to the host on sensitive events. This is what made a small in-kernel component sufficient. KVM, written by Avi Kivity at Qumranet and merged into Linux 2.6.20 in early 2007, was exactly that: not a hypervisor with its own scheduler and memory manager, but a driver that exposes the virtualisation extensions and lets the ordinary Linux scheduler, memory manager and device model do the rest. A guest CPU is simply a thread of a normal process. This design decision explains most of what operators see today, from `top` showing guests as `qemu-system-x86_64` processes to cgroups and NUMA policy applying to guests unchanged.

QEMU predates KVM. Fabrice Bellard released it in 2003 as a dynamic binary translator that could emulate one processor architecture on another. Early KVM shipped its own patched fork (`qemu-kvm`) and the two were reunified by QEMU 1.3 around late 2012, after which `-enable-kvm` and later `-accel kvm` selected acceleration in the mainline emulator. A lesson of that period is that the emulator, not the kernel module, defines the visible hardware, so most "KVM bugs" are device-model bugs in QEMU.

Management tooling evolved in parallel and with less elegance. Raw QEMU invocations were unreadable and unrepeatable. Red Hat started libvirt in 2005 to provide one stable API above Xen, QEMU, LXC and later others, and `virt-manager` and `virt-install` grew from the same group. Earlier approaches left gaps: every hypervisor had its own CLI, shell scripts held the only record of a guest's configuration, and nothing enforced isolation beyond Unix permissions. libvirt answered with persistent XML definitions, sVirt (SELinux or AppArmor labels per guest so that a compromised QEMU process cannot read a neighbour's disk) and a socket API that remote clients can use. Commercial attempts such as Xen-based management stacks, RHEV and later oVirt took the same engine and put a cluster manager on top (T08). A partial success worth noting: libvirt's abstraction across hypervisors was only ever fully realised for QEMU/KVM, with Xen, LXC, VMware ESX, bhyve and Cloud Hypervisor drivers supported to varying depth, which is why current documentation is overwhelmingly about the QEMU driver [src: libvirt-docs fd5b4f560500daf9].

The lessons that pushed the field to today's shape are these. Keep the privileged in-kernel part small, because every line there is attack surface. Put device emulation in an unprivileged, confinable process, and over time move even that into purpose-built paths (virtio for paravirtual devices, `vhost` for in-kernel or userspace data paths, `vfio` for direct hardware assignment). Make configuration declarative and persistent, because a guest that exists only as a command line cannot be audited. And pin the platform-visible parts (machine type, CPU model) so that guests survive host upgrades. The emerging pattern is a three-tier stack: a kernel accelerator, a per-guest device-model process, and a management daemon that owns lifecycle and policy.

## Current state

**The pieces and how they cooperate.** `kvm.ko` plus `kvm_intel.ko` or `kvm_amd.ko` (on ARM64 and RISC-V the equivalent is built into the architecture support) expose the character device `/dev/kvm`. A user process opens it, creates a VM file descriptor with an ioctl, then creates one vCPU descriptor per virtual processor, and runs each vCPU by repeatedly calling the `KVM_RUN` ioctl. That call returns whenever the guest does something the kernel cannot complete alone, such as a port or memory-mapped I/O access to an emulated device, and the user process (QEMU) services the request and re-enters the guest. The kernel's own API documentation describes this set of ioctls on the VM, vCPU and system descriptors [web: docs.kernel.org]. Guest memory is ordinary anonymous memory of the QEMU process, registered with KVM as memory slots, which is why the host can swap, balloon, share or compact guest pages and why hugepages (T04) are a mapping choice and not a new subsystem.

QEMU supplies a machine model. On x86 the two common machine types are `pc` (the older i440FX chipset) and `q35` (a PCIe chipset), both versioned (for example `pc-q35-9.2`) so that a guest keeps a stable hardware layout when the emulator is upgraded; choosing the unversioned alias is a common source of surprises. Firmware is SeaBIOS or OVMF (UEFI), the latter required for Secure Boot and for many modern guests. For devices the preferred choice is **virtio**: a family of paravirtual devices (block, net, console, balloon, rng, vsock, filesystem) that speak a ring-buffer protocol the guest driver understands, avoiding the cost of emulating real hardware register by register.

libvirt is two things: a library with a stable C API and bindings, and a set of daemons. Historically one `libvirtd` handled everything. Current distributions ship a **modular** layout in which each driver has its own daemon (`virtqemud`, `virtnetworkd`, `virtstoraged`, `virtnodedevd`, `virtnwfilterd`, `virtsecretd`, `virtinterfaced`, `virtproxyd`) activated on demand by systemd socket units, and Red Hat's current documentation covers this arrangement for its virtualisation host [src: rhel-10-docs f305cb44ecd2559b]. A libvirt **connection** is identified by a URI. `qemu:///system` addresses the privileged system instance that runs guests as the unprivileged `qemu` user with SELinux labels; `qemu:///session` addresses a per-user instance with no network bridging privilege, convenient for experiments. A remote host is reached with `qemu+ssh://user@host/system`, which makes the client tools location-independent. A frequent beginner mistake is to run `virsh list --all` as an ordinary user, which connects to the session instance by default, and to conclude that the guests created as root have disappeared. `virsh -c qemu:///system` or `export LIBVIRT_DEFAULT_URI=qemu:///system` removes the ambiguity.

**Preparing the host.** The checklist is short and each item has a diagnostic.

- CPU support: `grep -E -o 'vmx|svm' /proc/cpuinfo | sort -u` shows the flag; BIOS or firmware may have it disabled even when the CPU has it.
- Kernel modules and device: `lsmod | grep kvm` and `ls -l /dev/kvm`. Access is normally controlled by the `kvm` group or an ACL.
- libvirt's own check: `virt-host-validate qemu` runs a list of probes (hardware virtualisation, `/dev/kvm`, cgroup controllers, IOMMU presence, secure guest support) and prints PASS, WARN or FAIL per line.
- Services: for modular installs `systemctl enable --now virtqemud.socket virtnetworkd.socket virtstoraged.socket` and companions; on monolithic installs `libvirtd.socket`.
- Resources: the `default` network (NAT through `virbr0`, dnsmasq for DHCP and DNS) and a `default` directory storage pool at `/var/lib/libvirt/images`.

The Rocky and Arch material covers the package set (`qemu-kvm`, `libvirt`, `virt-install`, `libguestfs-tools` on the Red Hat side; `qemu-system-x86`, `libvirt-daemon-system` on Debian and Ubuntu) and the group membership step that lets an ordinary user manage the system instance [src: rocky-docs b7c85dcf58087a8a] [src: archwiki 857221cad4f65079].

**The domain XML.** Everything about a guest lives in one document, the *domain*. Its root element carries `type='kvm'` (the value `qemu` means pure emulation without acceleration, and a guest silently defined that way is the classic slow-guest case). Under it, `name` and `uuid` identify the guest; `memory` and `currentMemory` give the ceiling and the present size, with a `unit` attribute; `vcpu` sets the count; `os` holds the machine type and architecture in `<type arch='x86_64' machine='pc-q35-9.2'>hvm</type>`, boot devices and optional `<loader>` and `<nvram>` for UEFI; `cpu` selects the model (`host-model` copies the host's capabilities in a migratable way, `host-passthrough` exposes everything including features that block migration, a named model is the most portable); `features` holds `acpi`, `apic` and Hyper-V enlightenments for Windows guests; and `devices` is a list of disks, interfaces, controllers, serial and graphics devices.

A minimal disk element names a file source and a target: `<disk type='file' device='disk'><driver name='qemu' type='qcow2'/><source file='/var/lib/libvirt/images/web1.qcow2'/><target dev='vda' bus='virtio'/></disk>`. Here `driver type` states the image format so libvirt never has to probe it (probing a raw image that a guest has written arbitrary bytes into is a historical security issue, and libvirt now refuses to guess), and `bus='virtio'` selects the paravirtual path. A network interface of `type='network'` with `<source network='default'/>` and `<model type='virtio'/>` attaches to the NAT network. A **domain is persistent or transient**: `virsh define file.xml` stores it under `/etc/libvirt/qemu/`, while `virsh create file.xml` starts it without storing. `virsh edit NAME` opens the stored XML in `$EDITOR` and validates on save, which is the safe way to change it; editing the file under `/etc/libvirt` directly is not picked up until the daemon rereads and is a known way to lose changes. Changes to a persistent definition normally apply at next boot. To change a running guest use `virsh attach-device`, `virsh setmem`, `virsh setvcpus` with `--live`, `--config` or both. libvirt also records the state in `/run/libvirt/qemu/NAME.xml`, and `virsh dumpxml NAME` prints the live XML, which for a running guest includes allocated details such as the PCI addresses and the VNC port.

**Lifecycle and inspection with virsh.** The verbs follow a regular scheme. `virsh list --all`, `virsh dominfo`, `virsh domstate --reason` and `virsh domblklist` inspect. `start`, `shutdown` (an ACPI request, which a guest may ignore), `reboot`, `suspend`/`resume` (pause the vCPUs, keep memory), `destroy` (a hard power cut despite the name; it does not delete anything) and `undefine` (remove the definition, with `--nvram` or `--remove-all-storage` for related state) change state. `virsh autostart NAME` links the guest into the autostart directory. `virsh console NAME` attaches to the serial console, which works only if the guest kernel has `console=ttyS0` and a getty on it. `virsh domifaddr NAME` lists guest addresses from the DHCP lease or, with `--source agent`, from the QEMU guest agent running inside. `virsh qemu-monitor-command NAME --hmp 'info status'` talks to the QEMU monitor for debugging, and the Arch material explains the QEMU-specific command line passthrough, with its warning that features outside libvirt's model are unsupported territory [src: archwiki 27d3252bb6e4d673]. `virsh domxml-to-native qemu-argv` prints the command line libvirt would use, useful for understanding, though the libvirt documentation warns that the result is not designed to be run by hand [src: libvirt-docs fd5b4f560500daf9].

**Installing a guest.** `virt-install` generates a domain XML from options, creates the disk, starts the guest and attaches a console. A representative invocation reads: `virt-install --name web1 --memory 2048 --vcpus 2 --cpu host-model --os-variant debian12 --disk size=20,format=qcow2,bus=virtio --network network=default,model=virtio --location <URL-or-ISO> --extra-args 'console=ttyS0' --graphics none`. The `--os-variant` value comes from the libosinfo database (`osinfo-query os`) and chooses sensible defaults for bus and model, as the Debian handbook explains [src: debian-handbook 459cdaa20479ee1a]; an unknown variant is now an error, not a warning. `--location` extracts a kernel and initrd from the installation tree so that kernel arguments (such as the serial console) can be passed, while `--cdrom` boots an ISO like real hardware. For images that are already installed (cloud images), `--import --disk path=...` skips the installer. `--print-xml` plus `--dry-run` produces the XML without creating anything, which is the best way to learn the mapping between options and elements, and the output can be committed to version control as the declarative record.

**The generalised pattern.** The pattern is a declarative desired-state document (the domain XML) held by a daemon that reconciles it with a per-instance sandboxed process, accessed over a socket by a thin CLI. The same shape recurs wherever a workload's definition has to survive the process that runs it.

## Assessment: the good, the bad and the ugly

**The good.** The stack is open and mainstream: the Linux scheduler, memory manager, cgroups and NUMA apply to guests with no special case, and tools such as `perf`, `top` and `pidstat` already work on the QEMU process. Because libvirt describes guests declaratively, definitions can be reviewed, diffed and regenerated. The API is stable over many years, and security isolation is layered: a guest runs inside a QEMU process, which libvirt confines with a dedicated Unix user, a per-guest SELinux or AppArmor label (sVirt), cgroup device and resource limits, and seccomp filters. Performance with virtio is close enough to bare metal that CPU-bound workloads lose a few percent, and I/O-bound ones lose less than most people expect when the paravirtual paths are chosen. Documentation is plentiful, and every major distribution carries the same components, so skills transfer.

**The bad.** The stack is wide, and responsibilities are blurred. The same symptom may have a cause in the CPU firmware, kernel, QEMU, libvirt or guest, and there is no single log: QEMU's stderr lands in `/var/log/libvirt/qemu/NAME.log`, libvirt's own messages in the journal (turn up detail with `log_filters` and `log_outputs` in `libvirtd.conf` or `virtqemud.conf`), and the guest has its own console. Defaults are tuned for convenience on a workstation (user-mode style NAT, a `default` pool, a VNC display on localhost), not for production. The XML format is verbose, with different spellings for the same idea (`type='kvm'` vs `<domain type='kvm'>` plus `<cpu mode=...>`), and there are many ways to configure hardware that look equivalent but differ in performance (IDE or SATA vs virtio, e1000 vs virtio-net, `cache=writeback` vs `none`). The old name `qemu-kvm`, the QEMU `-enable-kvm` flag and the modern `-accel kvm` appear in different vintages of documentation and a reader needs to know which is current.

**The ugly.** Several awkward behaviours are well known. `virsh destroy` sounds like deletion and is a power cut; it can corrupt a guest filesystem, and `virsh shutdown` with an unresponsive guest returns success without doing anything. Snapshot, migration and device hot-plug features each depend on state (machine type, CPU flags, storage format) fixed at definition time, so a guest defined with `host-passthrough` on a new CPU may not be movable to an older one. Running as `qemu:///session` hides guests from the system instance. Disk image locking (via `virtlockd` or `sanlock`) is optional and, when off, two hosts or two guests pointed at one image cause silent corruption. A guest that cannot start due to an SELinux denial reports a generic permission error, and the real message sits in the audit log; copying an image from a home directory to the pool without restoring its label is the standard way to trigger it (`restorecon -Rv`). Finally, security of the device model is a continuing fight: QEMU is millions of lines of C, and the QEMU security policy distinguishes between the virtualisation use case, where hardware-assisted guests with virtio devices are in scope, and the long tail of emulated legacy devices that are not [web: qemu.org]. Mitigation: use a minimal device set, `q35` with virtio, remove unused controllers, keep QEMU current, and treat legacy devices as untrusted.

## Applications beyond this domain

The three-tier structure appears elsewhere. Kubernetes with KubeVirt runs each VM inside a pod using the same libvirt and QEMU pair, and the KubeVirt guide shows operators how to run `virsh` inside the `virt-launcher` pod to inspect a guest [src: kubevirt-user-guide 4d79b7294a8f359a]; the declarative domain moves into a Kubernetes custom resource and the pod supplies the cgroup, network and storage plumbing. Cloud providers use KVM beneath their compute services: the AWS Nitro system and Google Compute Engine both run KVM-based hypervisors with a custom device model in place of stock QEMU (publicly documented by those providers [web: aws.amazon.com]). Firecracker and Cloud Hypervisor replace QEMU with a minimal Rust virtual machine monitor over the same `/dev/kvm` interface (see T07). Developer tooling uses it too: Vagrant's libvirt provider, `virt-builder` and `guestfish` images, Android emulator on Linux, and CI runners that boot a throwaway guest per job.

What carries over is the discipline: a small privileged core, an unprivileged per-instance process, a declarative record, and pinned platform identity. The same ideas appear in container runtimes (containerd shims and OCI spec as the declarative record), in systemd units (declarative state plus sandboxing directives) and in cloud-init (declarative first-boot configuration).

## Examples

**A first guest, working.** On a fresh Debian host, install `qemu-system-x86 libvirt-daemon-system virtinst` and add the user to the `libvirt` group. `virt-host-validate qemu` reports PASS for hardware virtualisation and `/dev/kvm`. `virsh -c qemu:///system net-start default` and `net-autostart default` bring the NAT network up. `virt-install --name lab1 --memory 1024 --vcpus 1 --os-variant debian12 --disk size=8,bus=virtio --cdrom debian.iso --network network=default,model=virtio` creates an 8 GiB qcow2 under the default pool and starts the installer. After installation, `virsh dumpxml lab1 > lab1.xml` captures the declarative record, and `virsh domifaddr lab1` shows the lease. The Rocky tutorial walks through the same first contact on an Enterprise Linux host, from tooling prerequisites to a defined guest [src: rocky-docs aefc7acaa7d01374].

**Slow guest, failing.** An engineer reports that a new guest takes minutes to boot and uses 100 % of one host core even when idle. `virsh dumpxml` shows `<domain type='qemu'>`. Cause: `/dev/kvm` was not accessible when the guest was created (the module was not loaded because virtualisation was disabled in firmware, or the service ran in a container without the device), so libvirt fell back to TCG, QEMU's emulator. Fix: enable VT-x in firmware, verify with `virt-host-validate`, and `virsh edit` the type to `kvm`; guests created before the repair must be re-edited. The lesson is that acceleration is a property of the definition, so verify it after creation with `virsh dumpxml NAME | grep "domain type"`, and `virsh capabilities` to see the guest types libvirt believes the host supports.

**Permission denied on an image, failing.** A guest definition points at `/home/alice/win.qcow2`. `virsh start` fails with a cannot-open-file error although file mode bits are permissive. `ausearch -m avc -ts recent` shows an `svirt_t` denial on a `user_home_t` file. Fix: move the file to a pool directory (or `semanage fcontext` and `restorecon`) rather than disabling SELinux. This demonstrates that sVirt is doing its job: the QEMU process may only touch files labelled for it.

## Related problems and ideas

Neighbouring problems are packaging a guest image (T02), giving it connectivity (T03), tuning (T04), moving it (T05) and running a large number of hosts (T08). Alternatives to the QEMU model include **Xen**, which still powers parts of some public clouds and uses its own toolstack; **bhyve** on FreeBSD, whose libvirt driver is under steady development, with session mode and TPM support added in the late 2026 releases [web: libvirt.org]; **VirtualBox** and VMware Workstation, which provide desktop-oriented products; and **Hyper-V**, which libvirt does not drive on Linux hosts. Lighter-weight alternatives remove most of QEMU's device model: Firecracker, Cloud Hypervisor and `crosvm` use virtio only and drop BIOS, USB and legacy emulation. The opposite end is **confidential computing**: AMD SEV-SNP and Intel TDX encrypt guest memory and protect it from the host, and Red Hat documents the guest side as supported and the host side as technology preview in RHEL 10 [src: rhel-10-docs 2f3c65da48e60d3a]. Another idea, still rough, is **virtiofs** for sharing a host directory with a guest through a FUSE-like channel over virtio rather than network filesystems; libvirt and the Arch material describe it, with shared memory backing as a prerequisite [src: archwiki 3c35dbbf0235e4ab].

## Active research

Work in progress concentrates on three questions. First, **a smaller attack surface**: rewriting device models in memory-safe languages (virtio-fs and vhost-user backends in Rust, the `rust-vmm` crates on which Firecracker and Cloud Hypervisor stand), moving QEMU's `qemu-storage-daemon` and `vhost-user` backends into separate confined processes, and Rust in QEMU itself, which began to appear in recent releases (to verify the current set of Rust-implemented devices). Second, **confidential and attestable guests**: SEV-SNP and TDX support in KVM, guest_memfd as a kernel interface for private guest memory, and attestation workflows that libvirt must expose. Third, **performance interfaces**: io_uring-based block back ends, `vhost-vdpa` and vDPA for hardware virtio, and live updating of the hypervisor.

Universities and vendors publish on KVM's side channels and speculative-execution mitigations, whose costs fall especially hard on virtualised workloads, and on formal verification of small hypervisor cores. Kernel developers continue the work on KVM for Arm, RISC-V and nested virtualisation on those architectures. A standing open question is how to give libvirt's declarative model a clean path to features that QEMU adds faster than libvirt can model them; the present answer is the `qemu:commandline` escape hatch and the experimental XML namespace, which both sides would like to retire.

## Future direction

Expect the modular daemon layout to be the only form in distributions' next releases, with the monolithic `libvirtd` kept for compatibility. libvirt has kept a monthly release cadence; the most recent release at the time of writing is 12.9.0 of 2 November 2026, and QEMU's stable series is 11.1 with 11.2 in release candidate [web: libvirt.org] [web: qemu.org]. QEMU keeps a roughly three-release-per-year rhythm, and machine types stay supported for a bounded number of releases, so a long-lived guest must be re-based onto a newer machine type deliberately. Watch for: Rust-written components entering QEMU's default device set, broader confidential-guest support (TDX and SEV-SNP host support moving out of preview in enterprise distributions), vDPA and DPU offload in cloud hosts, and KubeVirt becoming the default way many organisations schedule VMs. For the practitioner, the dependable investment is the vocabulary: domain XML, URIs, `virsh` verbs and the host validation checklist change slowly while the packages around them move on.
