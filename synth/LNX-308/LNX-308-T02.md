# Golden images, copy-on-write disks and offline customisation

## Define the problem

Creating one guest by running an installer is easy. Creating the fiftieth is a different problem, because an installer is slow, interactive, and nondeterministic: two installs made a month apart differ in package versions, in random identifiers and in the mistakes a person made along the way. What an operator wants is a **template**: a known-good disk image that can be duplicated in seconds, specialised for each new guest, and refreshed on a schedule. Alongside this sits a second need, **recovery points**. Before a risky upgrade one wants to freeze the state of a guest and be able to return to it, and when a guest is a build worker, one wants every job to start from the same clean state.

Three separate questions hide inside these needs. How do you store many nearly identical disks without paying full price for each? That is the job of copy-on-write image formats and backing files. How do you capture and restore a point in time, of the disk alone or of disk plus memory? That is the job of snapshots, and in QEMU's world there are several unrelated mechanisms that share the word. And how do you change the contents of a disk image, for instance to set a hostname, install a package or inject an SSH key, without booting it? That is the job of the libguestfs tools, `virt-customize`, `virt-sysprep` and `virt-builder`, and of first-boot agents such as cloud-init for the changes that can only happen once the guest is alive.

Failure looks like a guest cloned with the same machine identifier and SSH host keys as its source (so that two machines fight over a DHCP lease or an attacker who knows one key knows all), like a long chain of overlays that makes every read slower and every deletion impossible, like a snapshot that was believed to be a backup and was destroyed with the disk it sat on, or like a disk image modified on the host while the guest was running and now irrecoverably inconsistent. The scope of this slice is the qcow2 image, backing chains, libvirt snapshot types, cloning, the libguestfs customisation tools and the interplay with cloud-init. Network setup and migration of the resulting guests appear in T03 and T05.

## History and approaches

The oldest approach was the plain **raw** file: a byte-for-byte copy of the disk. It is simple and fast, nothing can be wrong with the format, and every copy costs the full size unless the filesystem is sparse and `cp --sparse` is used. QEMU's first own format, `cow`, and then `qcow` (2004), added copy-on-write and a base file but suffered from a limited feature set. qcow2 arrived in 2008 with reference counts, internal snapshots, optional compression and encryption, and it became the default because it allowed thin provisioning, a backing file and snapshots in one container. Experience taught its costs: metadata caching is needed or random I/O slows down badly, the format is fragmented over time, and the early qcow2 encryption scheme was weak (replaced by LUKS-in-qcow2 in 2.6-era QEMU, and the legacy mode is deprecated). Other hypervisors made other trade-offs: VMware's VMDK and Microsoft's VHDX are comparable but not interchangeable, and `qemu-img convert` translates among them.

Early snapshot approaches illustrate how easily a feature gets confused. **Internal snapshots** store the guest's state inside the same qcow2 file, taken by `qemu-img snapshot` offline or by the monitor `savevm` live. They are convenient (one file) but were long slow to take on a running guest, could not be used with raw images, and the live memory-state variant was fragile: a snapshot of a guest taken before a host CPU or QEMU upgrade may fail to restore. **External snapshots** make the existing disk read-only and create a new overlay on top; they are fast and work for any base format, but the state then lives across several files that must be tracked, and for years there was no good way to merge them back while the guest ran. libvirt's `virsh snapshot-create-as` had to cover both, and its documentation warned of incompatible combinations (for example memory snapshots with certain disk types). QEMU improved this with `blockdev-snapshot` and **block jobs**: `block-commit` merges an overlay into its base, and `block-stream` (libvirt's `blockpull`) pulls base content up into the overlay, both live. These became the foundation of live backup tooling too.

Image customisation had its own history. First came **loop-mounting** an image on the host (`mount -o loop`, or `kpartx` for partitioned images), editing files, and unmounting. It is fragile: it needs root, it exposes the host kernel's filesystem drivers to untrusted guest data (a malformed image can trigger kernel bugs), and it cannot handle LVM, encrypted or exotic filesystems cleanly. Richard Jones's **libguestfs** (from 2009) answered by launching a tiny throwaway appliance, a minimal Linux kernel and initrd run under QEMU, with the image attached as a virtual disk. All filesystem work occurs in the appliance, and the host talks to it over a channel. This isolates the host from malicious images and lets the tool read any filesystem Linux can, without root. Its command-line family includes `guestfish`, `virt-cat`, `virt-edit`, `virt-df`, `virt-ls`, `virt-resize`, `virt-sysprep`, `virt-customize` and `virt-builder`. The failure lesson is that offline modification works until a change depends on the running system (for example an installed package whose post-install script needs services), and cloud images pushed another approach, the guest reading configuration at first boot from a metadata source. **cloud-init**, which started on Ubuntu for EC2 and became the de facto standard, consumes `user-data` and `meta-data` from a drive labelled `cidata` or from a network endpoint. Rocky's cloud-init guide walks through building a golden image on that basis, from booting the base cloud image without user-data to a clean template [src: rocky-docs b235e66836bb4bc5].

The pattern that emerged: a **base image** that is generic and read-only, per-guest **overlays** that capture differences, offline **sanitisation** to remove identity, and first-boot **configuration** to add identity. Cloud platforms operate on this model, and so do the Kubernetes-oriented tools that derive from it (see Applications).

## Current state

**qcow2 internals.** A qcow2 file divides the virtual disk into clusters (64 KiB by default, configurable between 512 B and 2 MiB). Two levels of tables map a guest offset to a host-file offset: the L1 table points to L2 tables, and an L2 entry points at a data cluster or says that the cluster is unallocated, zero, or compressed. Unallocated clusters are read from the **backing file**, if any; otherwise they read as zero. Writes to an unallocated cluster allocate it in the top layer, copy-on-write style. A reference-count table tracks sharing, which is what makes internal snapshots cheap: a snapshot records a copy of the L1 table and increments reference counts, and later writes copy clusters instead of overwriting. The consequence for operators is that a qcow2 file grows on write and does not shrink on delete inside the guest unless the guest issues discards (`fstrim` with `discard='unmap'` on the disk driver) and the file is compacted by `qemu-img convert`. Preallocation modes (`metadata`, `falloc`, `full`) trade creation time and space for lower fragmentation and steadier latency.

**qemu-img operations that matter.**

- `qemu-img create -f qcow2 -b base.qcow2 -F qcow2 vm1.qcow2` creates an overlay whose backing file is `base.qcow2`. The `-F` option states the backing format explicitly; omitting it was once tolerated and now draws a warning and in new releases an error, because format probing of a backing file lets a guest-controlled header redirect reads. A relative path in the backing file name is resolved relative to the overlay's directory, which is what lets a pair of files move together.
- `qemu-img info --backing-chain vm1.qcow2` (add `--output=json` for scripts) lists every layer with virtual size, disk size, format and backing filename. It is the first command to run on a suspicious image.
- `qemu-img check` verifies metadata consistency; `qemu-img commit vm1.qcow2` writes the overlay into its backing file (changing the base, so it is destructive for anyone else who uses that base); `qemu-img rebase -b newbase.qcow2 -F qcow2 vm1.qcow2` points the overlay to a different base by copying the differences, while the unsafe `-u` mode only rewrites the pointer and is used after a base was moved or renamed.
- `qemu-img convert -O qcow2 -c in.img out.qcow2` copies, flattens a chain, compresses and drops unused space; `qemu-img resize` grows or (with `--shrink` and care) shrinks the virtual size, after which the partition and filesystem still need to be extended inside the guest.
- `qemu-img snapshot -c NAME disk.qcow2`, `-l`, `-a` and `-d` create, list, apply and delete internal snapshots on an offline image.

An important rule: a base that has overlays must never be written again. Booting the template itself, or running `qemu-img commit` from some overlay, changes what every dependent overlay sees and corrupts them. Mark templates read-only (`chmod a-w`), or lock them with the image locking that libvirt can enable, and never boot a template after it has children.

**libvirt snapshots.** `virsh snapshot-create-as NAME SNAP` with a running guest and no further options creates an internal snapshot (for qcow2 disks) of disk and, with `--live`, memory. With `--disk-only` it creates external snapshots: libvirt freezes the current disk as read-only, makes a new overlay, and records metadata in `/var/lib/libvirt/qemu/snapshot/NAME/`. Adding `--atomic` makes it all-or-nothing across several disks, and `--quiesce` asks the QEMU guest agent to freeze filesystems first so the on-disk state is consistent, which fails if the agent is not running. `virsh snapshot-list --tree`, `snapshot-info`, `snapshot-dumpxml` and `snapshot-revert` navigate; reverting is supported for internal snapshots, but libvirt's support for reverting to external snapshots has been incomplete for a long time and the common practice is to discard the overlay and recreate it. Merging an external snapshot back goes through `virsh blockcommit NAME vda --active --pivot` for the live case (the `--active` flag commits the running top layer and `--pivot` switches the guest to the merged image) or `blockpull` to flatten from the other direction. The metadata can be removed without touching the images with `virsh snapshot-delete --metadata`. A checkpoint is different from a snapshot: libvirt checkpoints track dirty blocks for incremental backup (`virsh checkpoint-create-as`, backup begin), and they apply to a disk's history, not to its restorable state.

**Cloning and templates.** `virt-clone --original TEMPLATE --name new1 --auto-clone` duplicates the XML with a new UUID, name, MAC address and disk path, and copies the disks (or, with a manual `--file`, uses the ones you give). A leaner approach for ephemeral guests is a linked clone: create an overlay of the template's disk and `virt-install --import`. libvirt guest domains can also be created from an XML template with substituted values by any text tool, and KubeVirt offers `VirtualMachineTemplate` objects that can capture storage state such as `DataVolume` snapshots and cloned disks, which Helm or Kustomize cannot, and which work on any Kubernetes cluster, not only on OpenShift [src: kubevirt-user-guide af9552a70a7be828]. KubeVirt's Tekton tasks also expose "create a VM from template" operations, some of which work only on OpenShift [src: kubevirt-user-guide 6be49ecab9231295].

**virt-sysprep, virt-customize and virt-builder.** `virt-sysprep -d NAME` or `-a image` runs a list of *operations* that remove machine-specific state from a guest that is shut down: the machine-id, SSH host keys, DHCP leases, logs, bash history, persistent udev network rules, user home caches, mail spool and package-manager caches. `virt-sysprep --list-operations` names them, and `--operations` or `--enable`/`--no-enable` select. It is the step between "I configured a guest" and "this disk is a template". `virt-customize -a image --install pkg,pkg --update --hostname web --root-password locked:disabled --ssh-inject root:file:/path/key.pub --run-command 'systemctl enable chronyd' --firstboot-command '...' --selinux-relabel` changes an image offline. Package installation runs the guest's own package manager inside the appliance, which needs network access (passed through user-mode networking in the appliance, enabled by default and disabled by `--no-network`). `--selinux-relabel` matters on SELinux guests: files created offline lack labels, and without a relabel the first boot may fail or drop into autorelabel. `virt-builder centos-stream-9 --size 20G --format qcow2 --install ... -o out.qcow2` fetches a signed, pre-built minimal image from a public index, resizes it, applies the same customisation options and writes the result. `virt-resize --expand /dev/sda2 old new` creates a bigger image and grows a partition during the copy. Running these tools needs the libguestfs appliance; `libguestfs-test-tool` diagnoses failures, and on systems where libvirt is used as the appliance backend (`LIBGUESTFS_BACKEND=libvirt`, the default on some distributions) the appliance runs as a libvirt guest with its own sVirt label, while `LIBGUESTFS_BACKEND=direct` launches QEMU directly, which is the choice inside containers and CI runners where libvirt is not present.

**cloud-init for the rest.** The offline tools set what can be set statically. Everything that depends on the instance (hostname, network config, users, keys, mounts) is better left to cloud-init reading a NoCloud seed: a small ISO or a vfat disk labelled `cidata` holding `user-data`, `meta-data` and optionally `network-config`. `virt-install --cloud-init` now generates one directly. The template is then prepared by installing `cloud-init`, running `cloud-init clean --logs` so the next boot counts as a first boot, and sysprepping.

**Generalised pattern.** An image pipeline is *build once, sanitise, freeze, instantiate cheaply, specialise at first boot*. Snapshots are a different axis: *capture state cheaply, discard or merge deliberately*.

## Assessment: the good, the bad and the ugly

**The good.** Overlays make thin copies almost free: a hundred guests derived from a 2 GiB template cost the template plus whatever each writes. Creating one takes milliseconds, which makes ephemeral test environments practical. The libguestfs tools work without root, without booting the guest and without exposing the host kernel to untrusted filesystems, and they cover almost every filesystem and partitioning scheme in use. `qemu-img info --backing-chain` gives an honest view of the structure. Live block commit and pull let a running guest be snapshotted, backed up and merged without downtime. A quiesced external snapshot is an acceptable basis for crash-consistent or application-consistent backup of a single host.

**The bad.** Overlay chains lengthen the I/O path: a read that misses the top layer walks down the chain, so a chain of ten gets slower, and metadata caches (`l2-cache-size`, `cache-clean-interval`) need tuning for large images. Internal snapshots on a qcow2 slow it, and deleting one leaves a file as large as it ever was. A snapshot is not a backup: it shares the disk and the host with the thing it protects, and a storage failure destroys both. External snapshot revert is clumsy, and libvirt's handling of chains where overlays have been moved leads to errors that require editing the XML or using `virsh blockcommit`. Offline customisation can only do what the appliance can: it cannot run a service that needs the live kernel, and its network access can differ from the guest's. Some images (for instance with encrypted root or exotic bootloaders) cannot be opened.

**The ugly.** Identity leakage is the commonest real incident: templates built by copying a configured guest and forgetting `virt-sysprep` yield clones with the same SSH host keys, the same `/etc/machine-id` (which systemd uses to derive DHCP client IDs and the journal directory, so two machines fight for one lease), the same LUKS or `fstab` UUIDs, and the same MAC when the XML was copied verbatim. A backing file path stored absolutely breaks when the directory is renamed; stored relatively it breaks when only one file is copied. Deleting a template while overlays exist frees nothing and breaks every child. `qemu-img commit` into a shared base silently modifies every sibling. Memory snapshots depend on the QEMU version and machine type, so a restore after host upgrade may fail, and Firecracker documents the same underlying issue: a saved state cannot be restored on a different architecture, nor reliably on another processor model of the same family, because the feature set the guest sees has to stay identical between saving and restoring [src: firecracker-docs 81e0c6e6162fe5b3]. Guest clocks, network connections and random-number state after resuming from a snapshot are also hazards; the same project notes that network connectivity after resume is not guaranteed, that snapshots taken during early kernel boot can crash on resume, and that restore latency is high on cgroups v1 hosts [src: firecracker-docs 8f78ef9104f3c5e5]. A resumed clone also repeats the random state of its source (VM generation ID devices exist to tell the guest to reseed).

Mitigations: rely on `virt-sysprep` plus cloud-init, mark templates read-only, keep overlay depth under three or four, flatten with `qemu-img convert` for long-lived guests, pair snapshots with off-host copies, and document which disks belong to which chain.

## Applications beyond this domain

The same layered, copy-on-write structure is the heart of container image storage: overlayfs layers play the role of overlays, a read-only image is a template, and the writable container layer is the overlay. Btrfs, ZFS and LVM thin snapshots apply the idea at the filesystem or volume level and can serve as the storage for VM disks directly (a ZFS clone of a zvol in place of a qcow2 overlay). Cloud providers sell it as machine images and snapshots, built from the same sysprep and first-boot concepts. CI systems restore a known snapshot before each run. Build farms for distribution compose (Fedora's and Rocky's image builders) build golden images by script. The Rocky openQA install guide shows a related use, where automated tests start from prepared disk images and compare screens, an extreme case of "same input, deterministic output" for operating systems [src: rocky-docs 7520b32e76279822]. Even microVM platforms use the idea: a Firecracker snapshot of a booted function runtime is cloned for each invocation, which is why their documentation spends so much space on CPU templates and snapshot versioning [src: firecracker-docs 599812e4e5df15bf].

## Examples

**A working template pipeline.** Start from a distribution cloud image `base.qcow2`. Run `virt-customize -a base.qcow2 --install qemu-guest-agent,cloud-init --run-command 'systemctl enable qemu-guest-agent' --selinux-relabel`. Run `virt-sysprep -a base.qcow2 --operations defaults,-ssh-userdir`. `chmod a-w base.qcow2`. For each new guest: `qemu-img create -f qcow2 -b /var/lib/libvirt/images/base.qcow2 -F qcow2 /var/lib/libvirt/images/web1.qcow2 20G`, then `virt-install --import --name web1 --disk path=...web1.qcow2 --cloud-init user-data=web1.yaml --os-variant debian12`. Guest creation takes seconds, the template is stored once, and each guest generates its own host keys at first boot.

**Safe upgrade with an external snapshot.** Before a guest's upgrade: `virsh snapshot-create-as db1 pre-upgrade --disk-only --atomic --quiesce`. After the upgrade is verified, merge: `virsh blockcommit db1 vda --active --pivot --verbose`, then `virsh snapshot-delete db1 pre-upgrade --metadata` and remove the old overlay file. If it fails, shut the guest down, discard the overlay and point the XML back at the base.

**Failing: committing into a shared base.** An engineer boots a template to apply patches, then discovers that three overlays from last month no longer mount their filesystems. The template changed under them. Recovery requires restoring the template from backup. Prevention is the read-only bit and a rule that patches create a new template version and new overlays.

**Failing: cloned identities.** A pool of ten guests derived from a configured guest all request the same DHCP lease and the router flaps between them. `cat /etc/machine-id` on each shows the same value. Fix: rebuild the template with `virt-sysprep` (which empties `machine-id`, so systemd regenerates it on boot) and recreate the guests.

## Related problems and ideas

Neighbouring problems include backup (libvirt's push and pull backup APIs and incremental checkpoints), deduplicating storage across hosts (Ceph RBD clones, which provide copy-on-write at the cluster level), and **image supply chain**: signing and scanning images, as `virt-builder` verifies its index and images with GPG. Alternatives to qcow2 are raw on LVM thin or ZFS zvols (no format overhead, snapshots by the storage layer, worse portability) and network block devices. Declarative OS images such as NixOS, Fedora CoreOS with Ignition, and `bootc` container-based images avoid the golden-image drift problem by rebuilding from a definition on each change; Packer builds images from a script in a repeatable way. Proposed approaches not yet mainstream include shipping VM images as OCI artefacts and booting them straight from a registry, and copy-on-write memory sharing between clones so that a hundred microVMs from one snapshot share most pages.

## Active research

Research and engineering centre on **fast restore**: userfaultfd-based lazy loading of memory snapshots so that a guest resumes before its whole memory image has been read, studied for serverless platforms; **snapshot safety**: making clones unique in entropy, time and identity, with VM generation IDs and the work to make guests react to a resume event; and **incremental and block-level backup** with dirty bitmaps, now part of libvirt's backup interface. QEMU developers continue work on the `blockdev` job model (replacing legacy drive options) and on the removal of deprecated qcow2 behaviours, such as backing format probing. Open questions include a stable cross-version format for CPU state in snapshots, which Firecracker's versioning notes show remains hard, and a standard for template metadata so that a pool of images can state its provenance, expected `cloud-init` datasource and required features.

## Future direction

Expect `virt-customize`-style offline editing to give way, for mainstream fleets, to image builders driven by declarative definitions (image-builder in Red Hat distributions, `mkosi`, Packer), with qcow2 remaining the exchange format. KubeVirt's template and storage-cloning work, including snapshot features tracked in its release notes, indicates a move of these concepts into the cluster layer [src: kubevirt-user-guide a9405d810cb2436b]. Watch the deprecation of qcow2 legacy encryption and unsafe image probing, wider use of `virtiofs`-rooted guests that need no disk image at all, and the standardisation of snapshot-restore as a primitive for sandboxes. For the practitioner the stable core is short: a read-only template, overlays with explicit backing formats, sanitise before freezing, and treat every snapshot as a short-lived convenience instead of a backup.
