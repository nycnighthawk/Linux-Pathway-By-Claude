# System containers: systemd-nspawn, LXC and Incus

## Define the problem

Full virtual machines give each workload its own kernel and a hardware-shaped boundary, and they pay for it: a kernel's worth of memory per guest, boot times of seconds, and a disk image per instance. Often the workload is a set of Linux processes that only needs to believe it has a machine of its own: its own init system, its own users and package set, its own network address, but happily sharing the host's kernel. A distribution maintainer wants to test a package build in a clean Debian tree. An administrator wants fifty isolated service environments on one server without fifty kernels. A developer wants to boot a different release of the distribution beside the one installed. The tool for this is the **system container**: an operating-system tree started in its own set of kernel namespaces, constrained by cgroups, and (unlike an application container) running a full init so that services, logins and package updates behave as on a normal machine.

The distinction from application containers (Docker, Podman running one process per container) matters for how the tools are chosen. An application container packages a single program and its dependencies and is meant to be replaced rather than administered. A system container is administered like a small server: you log in, install packages, run systemd units inside it, and keep it for years. The distinction from virtual machines matters for security and compatibility: containers share the kernel, so a kernel bug or a misconfigured privilege breaks isolation for all of them, they can run only Linux guests that fit the host kernel's ABI, and kernel-level features (loading modules, different kernel versions, custom sysctls) are not available per guest.

This slice covers the kernel building blocks, the three main tools in the Linux system-container space (systemd-nspawn with `machinectl`, the LXC library and tools, and Incus, which manages both containers and virtual machines), their configuration and the trade-offs of choosing a container over a VM. Docker and Kubernetes belong to the container courses. The user-facing problem is choosing the right isolation level for a workload and operating it safely: which privileges the container has, what it can see of the host, how its resources are limited and how it is networked.

## History and approaches

Isolation without full virtualisation is older than Linux. `chroot` (Unix V7, 1979) changed a process's view of the root directory but not its privileges or what else it could see. FreeBSD **jails** (2000) added process, network and user isolation in one concept; Solaris **zones** (2004) added resource control and a management model. On Linux the story is a sequence of partial solutions. **Linux-VServer** (2001) and **OpenVZ** (2005) delivered system containers through out-of-tree kernel patches; they were widely used for hosting but never merged, and the maintenance burden of patching each kernel release was the fatal weakness. The mainline path was slower and more principled: **namespaces** were added one resource at a time (mount 2002, UTS and IPC 2006, PID and network 2008, user 2013, cgroup 2016, time 2020), and **cgroups** (2007) supplied resource accounting and limits. **LXC** (2008, from IBM and others) was the first userspace toolkit to compose these mainline features into containers, with templates to build root file systems. **Docker** (2013) popularised application containers with layered images, trading the system-container model for a packaging one.

The systemd project took another path. Its `systemd-nspawn` tool began as a developer utility to run a distribution tree under `chroot`-like isolation for testing systemd itself, and it grew into a modest container manager, integrated with `machinectl`, `systemd-machined`, `importctl` (earlier `machinectl pull-*`), and with systemd-networkd and systemd-resolved. The Arch Wiki describes it as a *chroot on steroids*: it virtualises the file system hierarchy, the process tree, interprocess communication objects and hostname, makes kernel interfaces such as `/sys` and `/proc/sys` read-only, forbids changing network interfaces and the clock, and refuses device node creation, module loading and rebooting the host, and it observes that nspawn is simpler to configure than LXC or libvirt [src: archwiki e7124c1ebb1bbfa8]. A weakness is its scope: no image repository beyond downloads, no cluster, and a configuration model that is mostly "systemd units".

The LXC lineage faced a governance problem. The project's own management daemon, **LXD**, was written by Stéphane Graber and led by Canonical; it added a REST API, image servers, storage pools, clustering and, from 2019, QEMU virtual machines under the same interface. In 2023 Canonical moved LXD under its own umbrella, relicensed it with a contributor agreement and the former lead developers forked it as **Incus** in August 2023, with a first release in October 2023 and a long-term-support line afterwards. Rocky Linux's documentation records this history, notes that the licensing change meant the Linux Containers project could no longer supply container images to LXD, so that LXD images lack many RHEL-compatible distributions, and recommends Incus for a modern platform on the original LXD design [src: rocky-docs 9cec6779bb719934] [src: rocky-docs febbd215be17eb79]. This is an example of how an open-source lineage can split over licence and governance rather than technology, and of why the choice of tool needs a look at project health.

The lessons: containers became practical only when the isolation was built into the mainline kernel and not carried as patches; a *unprivileged* model (user namespaces mapping container root to an ordinary host user) came late and was a decisive security improvement; and tools that bring images, networks and storage under one API beat collections of scripts. The pattern is a kernel isolation toolbox with several userspace managers at different levels of ambition.

## Current state

**Kernel building blocks.** A system container is the combination of these features, none of which is container-specific.

- *Namespaces* give a process its own view of mounts (`mnt`), process IDs (`pid`), host and domain name (`uts`), SysV and POSIX IPC (`ipc`), network devices, addresses and routes (`net`), user and group IDs (`user`), the cgroup tree (`cgroup`) and clocks (`time`). `lsns`, `unshare` and `nsenter` inspect and use them directly, and `/proc/PID/ns/` holds handles.
- *cgroups v2* provide the limits (`memory.max`, `cpu.max`, `pids.max`, `io.max`) and accounting; systemd delegates a subtree to a container, which then manages its own children.
- *Capabilities* and *seccomp* restrict what root in the container may do, and **LSM** profiles (AppArmor, SELinux) confine it.
- *User namespaces* map UID ranges, so root inside is an unprivileged user outside. A container that is not user-namespaced is called privileged and its root is the host's root, subject only to capability drops, which is much weaker.
- *overlayfs, btrfs, ZFS or LVM thin* supply copy-on-write root file systems, enabling fast clones, as in T02.

**systemd-nspawn.** The root tree is a directory, a raw disk image or a btrfs subvolume under `/var/lib/machines/`, and `machinectl` is the front end. The nspawn manual page gives worked examples, among them fetching a verified Ubuntu tarball with `importctl pull-tar` and opening a shell in it with `systemd-nspawn -M`, and building a minimal Fedora tree with `dnf --installroot` [src: man-pages a03cb80ab74facaf]. Typical operations: build a tree (`debootstrap`, `dnf --installroot`, `pacstrap`, `mkosi`), run a shell in it (`systemd-nspawn -D /var/lib/machines/deb12`), boot it with its own init (`systemd-nspawn -b -D ... -M deb12`, or `machinectl start deb12` through the template unit `systemd-nspawn@.service`), then `machinectl list`, `machinectl login`, `machinectl shell`, `machinectl status`, `machinectl poweroff`, `machinectl clone` and `machinectl enable` (start at boot). Options such as `--private-users=pick` (user namespaces), `--network-veth` (a virtual Ethernet pair, with one end on the host named `ve-NAME`), `--network-bridge=br0`, `--network-macvlan=eth0`, `--bind`, `--bind-ro`, `--tmpfs`, `--capability`, `--drop-capability`, `--property=MemoryMax=1G` (any unit resource property) and `--system-call-filter` configure it, and the persistent form is a `/etc/systemd/nspawn/NAME.nspawn` file with `[Exec]`, `[Files]` and `[Network]` sections that carry the same settings. `systemd-detect-virt` reports `systemd-nspawn` inside, and the machine1 D-Bus interface documented in `org.freedesktop.machine1(5)` allows programmatic control [src: man-pages 1b2c52127a0cae78] [src: man-pages b2d7815c81bb11b9]. A common arrangement is veth networking with `systemd-networkd` on the host providing DHCP and masquerading for `ve-*` interfaces through the default `80-container-ve.network` file.

**LXC.** The library and its command-line tools (`lxc-create`, `lxc-start`, `lxc-attach`, `lxc-ls`, `lxc-stop`, `lxc-destroy`, `lxc-info`, `lxc-console`) keep each container in `/var/lib/lxc/NAME/` (or in the user's `~/.local/share/lxc` when unprivileged), with a `config` file of key-value lines (`lxc.rootfs.path`, `lxc.uts.name`, `lxc.net.0.type = veth`, `lxc.net.0.link = lxcbr0`, `lxc.idmap = u 0 100000 65536`, `lxc.cgroup2.memory.max = 1G`, `lxc.mount.entry`). The Arch material explains that configuration is per container, that the syntax changed with LXC 2.1 and that unprivileged containers add idmap lines and need subordinate ID ranges (`/etc/subuid`, `/etc/subgid`) and a veth quota for unprivileged users [src: archwiki 1b77d4cb4bc3ccce] [src: archwiki 5db092a77aa4561f]. Templates have been replaced by downloaded images (`lxc-create -t download`). LXC is a library first, the layer under LXD, Incus, Proxmox's container support and the older libvirt LXC driver.

**Incus.** A daemon (`incusd`) with a REST API, a CLI (`incus`), image servers, storage pools (dir, btrfs, ZFS, LVM, Ceph), networks (bridges, OVN), profiles, projects, clustering, and two instance types behind one set of commands: system containers (via LXC) and virtual machines (via QEMU). Examples: `incus launch images:debian/12 web1`, `incus launch images:debian/12 vm1 --vm`, `incus exec web1 -- bash`, `incus config set web1 limits.memory 1GiB limits.cpu 2`, `incus snapshot create web1 s1`, `incus copy`, `incus move` (including live migration for VMs and, with CRIU, containers), `incus profile edit`, `incus network create br-lan`, `incus storage create pool1 zfs`, `incus config device add web1 data disk source=/srv/data path=/data`. A fresh install runs `incus admin init` to create the default storage pool and bridge, and the user must belong to `incus-admin` (or `incus` for restricted access). Recent releases keep a monthly cadence with a long-term line: as of the 30 October 2026 release page, the current feature release is 7.6 and the current LTS is 7.0.2, supported until June 2031 [web: linuxcontainers.org]. The same release notes show how the project handles the container-versus-VM boundary, for example live-migrating VMs with QEMU's multifd and running virtio disks through a dedicated I/O thread, the same constructs described in T04 and T05.

**Choosing among them.** Use nspawn when the host runs systemd, you want a light, scriptable way to run a distribution tree for build or test purposes or a small number of long-lived service containers, and you prefer unit files to a daemon. Use LXC directly when embedding in another system or when you need fine control and minimal moving parts. Use Incus when you want a complete platform: images, API, clustering, VMs and containers under one interface. Use a VM (T01) when the workload needs its own kernel, a non-Linux OS, or a stronger boundary.

**Generalised pattern.** An OS tree plus a namespace set plus a cgroup subtree plus a capability and LSM profile equals a container. The managers differ in how much they remember (images, networks, storage) and expose (CLI, unit files, REST).

## Assessment: the good, the bad and the ugly

**The good.** Density and speed: a system container starts in a fraction of a second and uses memory only for its own processes. No emulated hardware or hypervisor is involved, so CPU and I/O run at native speed, and the host's page cache is shared, so many containers from the same image share their file pages. Administration is familiar, because ordinary tools work on the host: `ps` shows container processes, `top` and `systemd-cgtop` show their cost, and files in the container tree are visible from the host. Snapshots and clones on btrfs or ZFS are nearly instant. nspawn requires no extra daemon beyond systemd; Incus offers a complete lifecycle with one interface for containers and VMs. For development and CI, these are the lightest way to get a clean distribution environment.

**The bad.** Containers share the kernel, so the isolation is only as strong as the kernel's namespace and cgroup implementation and the policy applied. Features that act on the kernel are unavailable or awkward: loading modules, changing most sysctls, running a different kernel version, using device nodes, or running Docker inside (nested containers need extra permission). Resource views leak: `/proc/meminfo`, `/proc/cpuinfo` and `uptime` show the host unless a shim such as `lxcfs` (used by LXC and Incus) overlays container-specific values, so programs that size themselves from them misbehave. File-system quotas and user-ID mapping make shared directories with the host awkward. Live migration of containers is not mainstream because CRIU is complex. Tool maturity differs: nspawn lacks image management beyond simple download and has a small user base, LXC's raw tooling is spartan, and Incus's tracks fast-moving releases.

**The ugly.** Privileged containers: if the container's root is the host's root, an escape (a kernel vulnerability or a mistakenly bind-mounted socket or device) gives full host control. Many tutorials still create privileged containers, and the fix is user-namespaced containers by default, with `--private-users` in nspawn, `lxc.idmap` in LXC, and the Incus default of unprivileged instances. Another is the bind mount trap: mounting `/var/run/docker.sock`, `/dev` or a cgroup path writable into a container effectively hands over the host. Another is cgroup delegation: if a container manager and the host's systemd both think they own a cgroup subtree, resource accounting and limits conflict, which is why modern tools require cgroup v2 and delegation (`Delegate=yes`). Another is tool churn: LXD's relicensing and the Incus fork left users to choose and to migrate (`lxd-to-incus` exists for that). Another is a naming confusion: "LXC" means the userspace library, the project and, informally, any Linux container. Finally, a container is not a safe place for hostile code unless you accept the kernel's attack surface; the QEMU documentation draws the same line for VMs when it speaks of security boundaries, and for untrusted tenants the safe choice is a VM or a microVM (T07).

## Applications beyond this domain

The pieces recur throughout modern infrastructure. Kubernetes nodes run containers with the same namespaces and cgroups through containerd or CRI-O. Podman and Docker create the same isolation for application containers, with rootless modes based on user namespaces. systemd's own sandboxing directives (`PrivateTmp=`, `ProtectSystem=`, `DynamicUser=`) apply a subset of the nspawn mechanisms to ordinary services, so a hardened service is a light container. Flatpak and Bubblewrap use user and mount namespaces to sandbox desktop applications, and Chrome's sandbox does so for browser processes. Build systems such as mock (Fedora, Rocky), `sbuild` (Debian) and mkosi use nspawn or chroot-plus-namespaces to create clean build environments, and Arch's devtools use nspawn for package builds. Proxmox VE runs LXC containers beside VMs under the same web UI. The Rocky Linux books describe a complete Incus server for hosting both kinds of instance, with the same snapshot and copy facilities [src: rocky-docs 0a5fbbc406e5e34e]. Even the microVM world borrows from containers: Kata Containers presents a container interface over a lightweight VM, giving container workflow with VM isolation.

## Examples

**A throw-away Debian build environment with nspawn.** `debootstrap --include=systemd-container bookworm /var/lib/machines/bld http://deb.debian.org/debian`, then `systemd-nspawn -D /var/lib/machines/bld --private-users=pick --bind-ro=/srv/src:/src /bin/bash`. The shell sees a Debian tree, process 1 is bash, `ip link` shows nothing but loopback (no `--network-*` option), and writes outside the bind mount stay in the tree. To run it as a service with networking: create `/etc/systemd/nspawn/bld.nspawn` with `[Exec] Boot=yes PrivateUsers=pick`, `[Network] VirtualEthernet=yes` and `[Files] BindReadOnly=/srv/src:/src`, then `machinectl start bld` and `machinectl login bld`.

**Hosting services with Incus.** `incus admin init --auto`, `incus launch images:rockylinux/9 db1`, `incus config set db1 limits.memory=2GiB limits.cpu=2`, `incus config device add db1 pgdata disk source=/srv/pgdata path=/var/lib/pgsql`, `incus snapshot create db1 before-upgrade`. After a bad upgrade `incus snapshot restore db1 before-upgrade` reverts the container in seconds, an advantage over a VM.

**Failing: a container that thinks it has the host's memory.** A Java service in a container sizes its heap from `/proc/meminfo`, shows 64 GiB, while the cgroup limit is 2 GiB, and is killed by the kernel (as in the OOM material of LNX-307). Fix: enable `lxcfs` or use a runtime that reads cgroup limits, and set explicit heap sizes.

**Failing: root in a privileged container.** An administrator bind-mounts the host's `/etc` read-write into a privileged container for convenience, and a script running as root in the container edits `/etc/passwd` on the host. The incident is not a bug in the tools but a consequence of treating the container as a separate trust domain when it was not. The remedy is user-namespaced containers, minimal bind mounts and read-only where possible.

## Related problems and ideas

Neighbours include application containers and their orchestration, which solve packaging and scheduling, not machine emulation; **unikernels** and **microVMs** (T07), which keep the VM boundary but cut its overhead; **gVisor**, which interposes a user-space kernel written in Go between the application and the host kernel; and **Kata Containers**. Opposing views on isolation: those who regard the kernel as an adequately hardened boundary for same-tenant workloads, and those who insist on hardware boundaries for anything multi-tenant. Related ideas that are not yet mainstream: running whole system containers as systemd *portable services* or *sysext* images, immutable host systems with containers as the only mutable layer, **ID-mapped mounts** (kernel 5.12) that make shared file systems work with user namespaces without recursive `chown`, and checkpoint/restore as a general tool (CRIU, plus kernel work to ease it).

## Active research

The security of container isolation is the main research front: new syscalls and namespaces, the time namespace, user-namespace hardening (restricting unprivileged creation after a series of vulnerabilities, with distributions such as Ubuntu adding AppArmor-based limits), `seccomp` user notification for supervised syscalls, and `landlock` as an unprivileged sandbox. Resource isolation: better accounting for shared kernel memory and page cache, pressure stall information as a signal, and per-container views of `/proc` without FUSE shims. Incus and LXC projects work on VM and container parity (live migration, hot-plug, clustered storage), on OVN integration and on better dealing with confidential VMs. systemd continues to extend nspawn with `mkosi` for image building and `systemd-vmspawn`, a sibling that boots disk images as QEMU virtual machines with a similar interface. Open questions: how much of the isolation can be moved out of the shared kernel without paying the VM cost, and how to give an unprivileged user the power to create containers safely.

## Future direction

Expect system containers to keep sharing the stage with VMs, with managers that treat both uniformly (Incus today, Proxmox and others similarly). Rootless and user-namespaced operation becomes the default and privileged containers an exception requiring justification. cgroup v2 only, ID-mapped mounts and better kernel support for checkpoint and restore will smooth edge cases. Expect the nspawn family to grow toward image-based, verified deployments with `mkosi`, `systemd-sysext` and `vmspawn`. Watch the Incus long-term-support line (7.0 supported until 2031 according to the project's notices, to verify at the time of adoption), distribution packaging of Incus, and security advisories for user-namespace features. For the practitioner, the working rule is: containers for trusted same-kernel workloads, VMs for isolation; unprivileged by default; and limits set from the start.
