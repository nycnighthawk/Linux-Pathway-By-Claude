# Making guests fast and predictable: virtio, huge pages and CPU placement

## Define the problem

A default guest is a compromise. Its disk is a file read through the host's page cache, its network card is a software object, its memory is cut from the host in 4 KiB pages, and its virtual CPUs are ordinary threads that the host scheduler moves from core to core as it pleases. Such a guest works. It is also noticeably slower than the same workload on the hardware it runs on, and, more importantly for production, its speed varies from minute to minute because it competes with every other guest and with the host's own work. Two problems must be separated. The first is **throughput**: how much work per second a guest does, bounded by how cheaply its I/O and memory accesses cross the virtualisation boundary. The second is **predictability**: how little that figure changes under load from neighbours, which is a matter of where memory and threads live.

For the operator, the three techniques named in the title answer different parts. **virtio** replaces emulation of real hardware with a purpose-built paravirtual interface, which removes most of the cost of each I/O operation. **Huge pages** enlarge the unit in which memory is mapped, which removes most of the cost of translating guest addresses. **CPU pinning**, with its companions NUMA placement and dedicated I/O threads, fixes where the work runs so that caches stay warm and memory stays local. This slice is deliberately functional: it states what each knob does, how to enable it in libvirt and what to check afterwards, not the full theory of performance engineering. Rigorous measurement belongs to the observability course (LNX-307), and direct hardware assignment (VFIO, SR-IOV) to LNX-315.

Failure here is subtle. A guest tuned with the wrong settings does not crash; it simply wastes the effort, or it makes things worse. Pinning two busy guests to the same core halves both. Reserving huge pages for a guest that does not start leaves memory stranded and starves the rest of the host. A virtio driver missing in a Windows installer makes the disk invisible. So the skill is to verify each change, not just apply it.

## History and approaches

The first guests used full device emulation: QEMU pretended to be a real IDE controller, an RTL8139 or Intel e1000 network card and a VGA adapter. Emulation has a hard cost. Each register access of a real device is a memory-mapped or port I/O instruction, and each one causes a trap into the hypervisor (a VM exit), after which QEMU decodes it and updates its model. Sending one packet through an emulated e1000 takes dozens of such exits. The Xen project had already shown with paravirtual front-end and back-end drivers that giving the guest a driver that knows it is virtualised, and communicates in batches through shared rings, could cut the exits by an order of magnitude. Rusty Russell proposed **virtio** in 2007 to bring the same idea to KVM and, importantly, to unify the guests' side: one transport and a family of device types (block, net, console, balloon, entropy) that every hypervisor could implement, with the driver in the guest kernel mainline. It was standardised by OASIS (virtio 1.0 in 2016, later revisions to 1.3). Early virtio devices still ran in QEMU's userspace, so each notification caused an exit and a context switch to QEMU. The next step moved the data path of virtio-net into the kernel as **vhost-net** (2010) and later into separate processes with **vhost-user**, so that a packet no longer visited QEMU; this is the basis of DPDK-based switches. **vDPA** (vhost datapath acceleration) then let real hardware implement the virtio ring itself, appearing to the guest as ordinary virtio.

Memory has its own history. Hardware page tables for guests (Intel EPT, AMD NPT, 2008) removed the need for the hypervisor to shadow the guest's page tables, but a TLB miss now costs a two-dimensional walk, up to 24 memory references on a four-level scheme. The cure is larger pages: with 2 MiB or 1 GiB pages, the walk is shorter and the TLB reaches further. Linux first offered explicitly reserved **hugetlbfs** pages (2.6 kernel), which are pre-allocated, never swapped and need administrator setup, then **Transparent Huge Pages** (THP, 2.6.38, 2011) that promote 4 KiB pages to 2 MiB automatically. THP works without configuration but at a price: the khugepaged daemon and compaction can cause latency spikes, and fragmented hosts may not find contiguous memory. Database vendors recommended switching THP off for years, while virtualisation vendors recommended it on, and both were right in their setting. Reserved huge pages remained the choice where determinism matters, as for virtual network functions and databases.

CPU placement went through a similar arc. Early advice was to leave scheduling to the host. Non-uniform memory (a socket's cores are close to their own memory and far from the other socket's) made that costly: a guest vCPU on one socket reading memory allocated on another is slower and loads the interconnect. The kernel's **automatic NUMA balancing** (3.8, 2012) tries to migrate pages and tasks, but it reacts after the fact. Explicit control came through `taskset`, then cgroup cpusets and `numactl`, and in libvirt through `<cputune>` and `<numatune>`. Partial successes and lessons: pinning every guest to fixed cores gives excellent isolation but destroys the ability to overcommit and to rebalance; automatic balancing handles typical workloads but can surprise; and hyper-thread siblings share execution units, so pinning two vCPUs onto siblings of one core is not equal to pinning them onto two cores. Side-channel attacks since 2018 added a security argument for pinning and for not sharing sibling threads between mutually untrusting guests.

The emerging pattern is a **layered approach**: paravirtual devices everywhere; huge pages and pinning applied only to guests whose workloads justify the reserved resources; automatic mechanisms elsewhere.

## Current state

**Device types and virtio.** The RHEL documentation divides virtual devices into emulated ones (compatible with drivers designed for physical devices, but with notable cost), paravirtualised ones (virtio, requiring a driver that knows about the hypervisor) and assigned physical ones (passthrough), and advises choosing by performance, compatibility and functionality [src: rhel-10-docs cb46adb0d4cf0564]. In domain XML, the choice is made by the `bus` or `model` attribute: `<target dev='vda' bus='virtio'/>` for a disk, `<model type='virtio'/>` for a network card (or `virtio-net` with `<driver name='vhost'/>` to use the in-kernel back end, which is the default when the host module is available), `<video><model type='virtio'/></video>`, `<memballoon model='virtio'/>`, `<rng model='virtio'>` with a `/dev/urandom` back end to feed guest entropy, `<channel type='unix'><target type='virtio' name='org.qemu.guest_agent.0'/></channel>` for the QEMU guest agent, `<vsock model='virtio'>` for host-guest sockets, and `<filesystem type='mount' accessmode='passthrough'><driver type='virtiofs'/>` for shared directories, which requires shared memory backing. Linux guests carry the drivers (`virtio_blk`, `virtio_net`, `virtio_scsi`, `virtio_pci`) in the mainline kernel, so recent guests need no preparation. Windows guests need the **virtio-win** drivers: either attached as a second CD during installation so the disk shows up (the RHEL guide for Windows guests covers this driver installation [src: rhel-10-docs 5ddd4181f7ef81a9]), or installed afterwards. Choices within virtio storage: `virtio-blk` is simple and fast; `virtio-scsi` supports many disks per controller, discard and SCSI features and is chosen for large disk counts or for passing through SCSI commands. Disk driver options matter as much as the bus: `cache='none'` (O_DIRECT, skip the host page cache, the right default for files on a host with its own cache of guest data), `io='native'` with `cache='none'` or `io='io_uring'`, `discard='unmap'` so trimmed blocks are released, and `iothread='1'` to pin the disk's processing onto a dedicated thread. For networking, `<driver name='vhost' queues='N'/>` provides multiqueue so that several guest CPUs can transmit and receive in parallel, which then needs `ethtool -L eth0 combined N` inside the guest; KubeVirt's equivalent is `networkInterfaceMultiqueue`, which increases the number of vhost queues for virtio interfaces [src: kubevirt-user-guide 3dbc41e2ca6a0e43]. Modern Linux guests with virtio-net and vhost reach tens of gigabits on a host with decent NICs.

**Huge pages.** Two routes. For *explicit* huge pages the host reserves a pool: `sysctl vm.nr_hugepages=2048` for 2 MiB pages, or the kernel command line `default_hugepagesz=1G hugepagesz=1G hugepages=16` for gigabyte pages, which should be reserved at boot because contiguous gigabytes are rarely available later. `grep -i huge /proc/meminfo` shows `HugePages_Total`, `_Free` and `_Rsvd`, and `numactl -H` or `/sys/devices/system/node/node*/hugepages/` shows per-node pools. Per-node allocation matters on NUMA hosts. The guest uses them through the domain XML: `<memoryBacking><hugepages/></memoryBacking>` for the default size, or a `<page size='1' unit='G' nodeset='0'/>` entry to choose a size and guest NUMA node, as the libvirt format documentation describes; the same element can carry `<nosharepages/>`, `<locked/>` (pin memory so it cannot be swapped) and `<allocation mode='immediate'/>` [src: libvirt-docs a92c02bf59d4e36d]. The guest's memory size has to divide evenly by the page size, and the pool must contain enough free pages at start or the guest fails to start with an allocation error; huge pages do not overcommit, and Kubernetes documents the same property of its `hugepages-<size>` resource: pages are not overcommitted and a pod requesting them must also request memory or CPU [src: kubernetes-docs d68f4666003db4ef]. The *transparent* route needs only `cat /sys/kernel/mm/transparent_hugepage/enabled` to be `always` or `madvise` (QEMU requests huge pages for guest memory with `madvise`, so `madvise` mode suffices) and has no per-guest setting beyond the optional `memoryBacking` hints.

Verification: after a guest starts, `HugePages_Free` falls by the guest size divided by the page size, and `grep -i AnonHugePages /proc/<qemu-pid>/smaps_rollup` shows THP use.

**CPU pinning.** The libvirt `<cputune>` element holds per-vCPU affinity: `<vcpupin vcpu='0' cpuset='2'/>`, `<vcpupin vcpu='1' cpuset='3'/>`, `<emulatorpin cpuset='0-1'/>` (the QEMU main thread and its device emulation, which should run on other cores than the vCPUs) and `<iothreadpin iothread='1' cpuset='0-1'/>`. The number of `iothreads` is set by `<iothreads>1</iothreads>`, and a disk or controller is assigned to one with `<driver ... iothread='1'/>`. A tuning guide for Rocky Linux walks through the configuration of vCPU pinning in the domain XML, including finding the host topology with `lscpu -e` and `virsh capabilities` [src: rocky-docs 58cf90194b80f129]. The CPU topology exposed to the guest is set in `<cpu>`: `<topology sockets='1' dies='1' cores='2' threads='2'/>` with `mode='host-passthrough'` and, for latency-sensitive guests, `<cache mode='passthrough'/>` and `<feature policy='require' name='topoext'/>` on AMD. The guest will schedule better when its topology mirrors the pinning (a pair of host siblings presented as two threads of one core). `virsh vcpupin NAME` shows or sets pinning live (`--live`, `--config`), `virsh emulatorpin` and `virsh iothreadinfo` do likewise, and `virsh vcpuinfo` reports the physical CPU each vCPU last ran on; `ps -eLo pid,tid,psr,comm | grep qemu` shows the same from the host, and `taskset -pc TID` reads the affinity of a given thread. On the host, isolating the cores that guests use from the general scheduler (`isolcpus=`, `nohz_full=`, `rcu_nocbs=` on the kernel command line, or systemd `AllowedCPUs=` on `system.slice` and `user.slice`) prevents host tasks from landing on them; the `tuned` profile `virtual-host` and `cpu-partitioning` automate common settings.

**NUMA.** `<numatune><memory mode='strict' nodeset='0'/></numatune>` binds the guest's memory to the node where its vCPUs are pinned; `mode='preferred'` and `'interleave'` relax that. For guests larger than a node, `<cpu><numa><cell id='0' cpus='0-3' memory='8' unit='GiB'/><cell id='1' cpus='4-7' memory='8' unit='GiB'/></numa></cpu>` presents a virtual NUMA topology that the guest kernel then uses for its own placement, and `<memnode cellid='0' mode='strict' nodeset='0'/>` inside `numatune` maps each virtual node to a host node. The RHEL performance chapter tabulates which techniques suit which workloads (databases, network functions, HPC and others), with IOThreads, vCPU pinning, vNUMA and huge pages each marked as needed or not by use case [src: rhel-10-docs f634c5d41eea595b]. KubeVirt documents the same constructs for real-time VMs, where dedicated CPUs, NUMA and huge pages are specified in the VM manifest [src: kubevirt-user-guide e6bf177bd8c3a652].

**Verification and measurement.** Compare before and after with a controlled test: `fio` in the guest against the virtio disk, `iperf3` between guest and a host or peer, and `sysbench` or `stress-ng` memory tests, repeated several times so that variance is visible. On the host use `perf stat -e dTLB-load-misses -p <qemu-pid>` to see the effect of huge pages, `perf kvm stat` for exit counts and reasons (a guest dominated by `EPT_VIOLATION` or `IO_INSTRUCTION` exits has not got its paravirtual paths right), `pidstat -t -p <qemu-pid> 1` to see where each thread runs, and `numastat -p <qemu-pid>` to confirm that memory is where intended.

**Generalised pattern.** For any virtualised workload the performance levers are the same three: reduce the number of boundary crossings (paravirtual interfaces, batching, in-kernel or hardware data paths), reduce the cost of each translation (large pages), and control placement (affinity and locality). Each has a price: flexibility, density or complexity.

## Assessment: the good, the bad and the ugly

**The good.** virtio is nearly free to adopt: Linux guests have the drivers, libvirt's `--os-variant` already chooses virtio devices for most guests, and the gain is large, often a factor of several for storage and network latency compared with emulated hardware. Huge pages give a few percent to a few tens of percent on memory-intensive workloads and reduce the host's page-table memory for large guests. Pinning gives repeatable latency and removes noisy-neighbour effects for the pinned guests, and an I/O thread decouples disk processing from the main QEMU loop. All are expressed declaratively in the domain XML and visible with standard Linux tools.

**The bad.** Static placement costs density. Reserved huge pages are not available to anything else, so a host running half-idle pinned guests wastes memory and cores. Reserved pools must be sized and kept in step with guest definitions, and a mismatch is reported only when a guest fails to start. Pinning is host-specific: a definition that names cores 4-7 has to be edited when moved to a host with a different topology, which complicates migration (T05) and any template. Over-tuning is common: published examples copy the settings of network-function appliances to ordinary web guests. The hot-plug of vCPUs and memory interacts with both pinning and huge pages in awkward ways.

**The ugly.** Several traps recur. A Windows installer that cannot see its virtio disk is the standard first encounter with the driver issue. THP can produce latency stalls from compaction on fragmented hosts, and `defrag` settings (`/sys/kernel/mm/transparent_hugepage/defrag`) decide whether an allocation waits. Memory ballooning and huge pages do not mix well: a balloon cannot reclaim huge pages, so the balloon device is usually removed for tuned guests. Locked or huge-page-backed memory also defeats KSM page sharing and swap. On hosts with SMT, pinning vCPUs to both threads of a core and then running untrusted guests on the same core's siblings opens side-channel exposure, and the mitigation is either to schedule only one guest per core or to disable SMT, at a large capacity cost. Pinning without isolating host housekeeping lets the host's interrupts land on the "dedicated" cores, which is visible as jitter in latency histograms. And the emulator thread: if it shares a core with a busy vCPU, device emulation starves and the guest sees storage and network stalls despite perfect vCPU pinning.

**Operational challenge.** Documenting which cores and huge pages belong to which guest, and guarding the document with automation (a script that validates each definition against the host topology before `virsh define`), is the only reliable way to avoid double allocation.

## Applications beyond this domain

virtio is not limited to KVM: the same device types are implemented by Cloud Hypervisor, Firecracker (virtio block, net, vsock), crosvm, bhyve and even by some container sandboxes such as gVisor and Kata Containers, which use virtio-fs and virtio-vsock. The Cloud Hypervisor documentation, for instance, covers a virtual IOMMU that lets a guest protect memory against its own devices, and virtio data path acceleration with vDPA [src: cloud-hypervisor-docs 370aae2a6aab9292] [src: cloud-hypervisor-docs 8e87a9ac7bdc1d46]. Huge pages and pinning apply to any latency-sensitive Linux process: databases (PostgreSQL's `huge_pages`, Oracle), Java heaps, DPDK applications and real-time containers use the same hugetlbfs and cpuset facilities, and Kubernetes exposes them through the CPU Manager and the Topology Manager and as the `hugepages-<size>` resource. AWS describes its Nitro Sandboxes and KVM microVMs as built for isolation with a restricted device set, an example of the minimal virtio-based design applied to a different goal [src: firecracker-docs 1c830f9e0b27d08c]. The thinking transfers to any performance work: find the boundary crossings, find the translation costs and find where the work sits.

## Examples

**A database guest tuned step by step.** Baseline: a PostgreSQL guest with a SATA disk and e1000 NIC, measured with `fio` random 4 KiB reads and `pgbench`. Step one, convert the disk to `bus='virtio'` and the NIC to virtio with vhost: random-read IOPS roughly double and network latency falls, with no other change. Step two, `cache='none' io='native' discard='unmap'` and a dedicated `iothread`. Step three, on a two-socket host, pin the four vCPUs to four cores of node 0 with `numatune` strict on node 0, `emulatorpin` to node-0 housekeeping cores, and back guest memory with 1 GiB huge pages from node 0 (`vm.nr_hugepages` or boot parameters sized in advance). Re-measure after each step, and keep only those that improved the metric the application owner cares about. Typical outcome: the first two steps give most of the benefit, pinning mostly improves the 99th-percentile latency, and huge pages help the buffer-heavy workload.

**Failing: guest will not start with huge pages.** `virsh start db1` returns an error about being unable to allocate memory. `grep Huge /proc/meminfo` shows `HugePages_Free: 512` while the guest needs 4096 of 2 MiB pages (8 GiB). Another guest holds the rest. Fix: raise the pool (possible with `sysctl` only if memory is not fragmented, otherwise by reboot) or reduce the guest. The same lesson applies to Kubernetes pods requesting `hugepages-2Mi`: pages cannot be overcommitted.

**Failing: pinned guests got slower.** Two guests are each pinned to cores 2-5 by copying one XML into another. They fight for the same cores, each running at half speed, while cores 6-9 idle. `virsh vcpuinfo` on both shows the same physical CPUs, and `mpstat -P ALL` shows the unused ones. Fix: allocate disjoint sets per guest and record them. The lesson is that pinning is a resource allocation and needs a ledger.

**Failing: low network throughput despite virtio.** A guest with virtio-net and eight vCPUs reaches only 3 Gbit/s on a 25 Gbit link. `ethtool -l` in the guest shows one combined channel. Enabling `queues='8'` in the domain XML and `ethtool -L eth0 combined 8` in the guest spreads the load; `mpstat` shows the work distributed over CPUs.

## Related problems and ideas

Neighbours of this topic: direct device assignment (VFIO passthrough of NICs, NVMe, GPUs), where the guest owns the hardware and the host's paravirtual path is bypassed; SR-IOV; memory overcommit techniques (ballooning, KSM, free page reporting, zswap) that trade predictability for density; and CPU overcommit policies in the scheduler. Alternative approaches: unikernels and microVMs, which reduce what the guest does at the source; **vhost-user** with DPDK, which dedicates polling cores to the datapath and reaches line rate at the cost of busy-looping cores; **io_uring** back ends for QEMU's block layer; and virtiofs with DAX window to give a guest near-native file access through a shared mapping. Less mainstream: CXL-attached memory tiers and how guests and huge pages should use them, and kernel scheduling of vCPUs with awareness of the host (paravirtual scheduling hints, where the guest shares its priorities with the host).

## Active research

Open questions include how to automate placement so humans do not hand-write core numbers (the Kubernetes Topology Manager, the Nova and OpenStack placement service, and research on interference-aware schedulers); how to reduce the cost of translation without reserved memory (contiguous memory allocator work, multi-size THP in recent kernels, memory folios, and the `guest_memfd` work that also serves confidential computing); and how to make virtio itself faster and more secure, including the standardisation of virtio extensions, new device types, and hardening against malicious devices (relevant when the "host" is untrusted, as in confidential VMs). Work on vDPA, DPUs and the offloading of virtio to hardware is active among NIC vendors and the Linux networking community. Cloud providers publish results on steal time, noisy neighbours and the sizing of vCPU to core ratios; academic groups study vCPU scheduling that avoids lock-holder preemption inside guests.

## Future direction

Expect virtio to keep absorbing special-purpose interfaces (virtio-gpu with native contexts, virtio-fs, virtio-vsock, virtio-iommu, virtio-pmem), and vDPA to become the standard way to attach hardware that looks the same to every guest. On the memory side, multi-size THP and better compaction should make 'good enough' large-page backing automatic, leaving hugetlbfs for strict determinism. Expect more scheduling and placement to move from XML hand-tuning into managers (Kubernetes CPU and Topology managers, OpenStack, Proxmox, tuned profiles) and into guest-aware host scheduling. For students, the lasting advice is practical: use virtio from the start, introduce huge pages and pinning only when a measured requirement exists, record the allocations, and test after every change.
