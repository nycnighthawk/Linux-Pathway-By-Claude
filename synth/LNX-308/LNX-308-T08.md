# Managing many hypervisors as one: Proxmox VE, oVirt and their neighbours

## Define the problem

One KVM host with libvirt is manageable by hand. Ten hosts are not, and the difficulty is not typing speed. The questions an administrator now has to answer span machines: on which host should a new guest start, given free memory and storage? What happens to the guests when a host dies at three in the morning? How is a host patched without taking its guests down? How do ten hosts agree on which networks exist and which storage pools are shared? Who is allowed to create guests, and how many? Where are the backups, and who restores them? Each of these is a distributed-systems question disguised as an operations question, and the libvirt tools of T01 to T07 do not answer them: `virsh` knows one host (or one remote host) at a time, with no shared state, no scheduler and no way to decide that a host is dead.

A **cluster manager** for virtualisation closes this gap. It keeps one authoritative database of hosts, guests, networks, storage and users; presents it through a web interface and an API; schedules guests; moves them between hosts (T05); restarts them elsewhere after a failure; and automates backup and monitoring. Two open-source products have dominated the Linux KVM space for administrators who want a traditional virtualisation platform: **Proxmox VE**, a Debian-based distribution that bundles KVM/QEMU, LXC containers, its own cluster file system and optional Ceph storage; and **oVirt**, the upstream of Red Hat Virtualization, an engine-and-agent architecture built on libvirt and VDSM. Beyond them lie cloud platforms (OpenStack, Apache CloudStack) and Kubernetes-based approaches (KubeVirt, OpenShift Virtualization).

What failure looks like is specific. A cluster that loses its majority freezes configuration changes to avoid inconsistency. A cluster without working fencing restarts a guest on a second host while the first host still has it running, and two writers corrupt a disk. A management network shared with storage and migration traffic starves the heartbeat, and healthy hosts evict one another. A cluster manager chosen for a feature list turns out to have a shrinking community or a licence that changed. This slice is introductory (depth 1): it names the architecture and the concepts you must recognise, such as quorum, fencing, shared storage and the scheduler, and shows how Proxmox VE and oVirt implement them, without attempting to make you a cluster operator. Because it needs several machines, the exercise is a planning and reading guide.

## History and approaches

Cluster management for virtual machines began with proprietary products. VMware's VirtualCenter (2003), with vMotion and later HA and DRS, set the feature checklist that everything since has measured itself against: central management, live migration, automatic restart, load balancing, snapshots and templates. Open-source alternatives emerged in the mid-2000s in two lines. **Xen**-based tools (XenCenter, XCP, later XCP-ng) had their own pool-master model. On KVM, **Qumranet**, the company behind KVM, built a management product called SolidICE; Red Hat acquired Qumranet in 2008 and released it as **Red Hat Enterprise Virtualization (RHEV)** in 2009, then opened its management code as the **oVirt** project in 2011. At the same time, Proxmox Server Solutions in Vienna released **Proxmox VE** in 2008, built on Debian with OpenVZ containers (replaced by LXC in 2015) and KVM, with a design emphasis on simplicity: a web UI on every node and a multi-master cluster in which each host holds a replica of the configuration.

The two projects took opposite architectural paths, which is the central teaching point. oVirt has a **central engine** (a Java application with a PostgreSQL database, usually on a separate machine or a self-hosted engine VM running on the cluster it manages), and **agents** on each host (VDSM, the Virtual Desktop and Server Manager, a Python daemon that drives libvirt and storage). The engine owns the state; hosts are managed endpoints; high availability depends on the engine being up and on fencing agents reaching hosts. Proxmox VE has **no central server**. Each node runs the same services, and a user-space cluster file system, pmxcfs, replicates a small configuration database among them via the Corosync cluster engine, so the cluster state is distributed and any node can serve the UI. That choice makes small clusters easy to build and removes a single point of failure, but ties scaling and correctness to Corosync's quorum and latency limits.

The partial successes and failures of the period shaped the present. OpenStack (2010) took the cloud route, with separate services for compute, network, image and storage and a design for thousands of hosts; it succeeded among telecoms and large enterprises and failed to become the easy datacentre virtualisation platform that small organisations wanted, since it is complex to operate; the Rocky Linux material states that bluntly, calling OpenStack the most advanced replacement for vSphere and also the most complex, to be avoided unless you have a skilled engineering team with time [src: rocky-docs e354f74cdbcc35cd]. Apache CloudStack, in the same source, is presented as a simpler private-cloud portal with VPC support, direct migration from vSphere, and instances with over 35,000 hosts. Red Hat announced in 2022 that RHV would be retired in favour of OpenShift Virtualization, which runs KVM guests under Kubernetes through KubeVirt, and the oVirt project's community continued after Red Hat reduced its involvement. The oVirt site and blog report a long gap between releases and a new 4.5.7 in January 2026 after about two years, with the community and contributors from companies such as Oracle (whose Linux Virtualization Manager is oVirt-based) keeping it alive (to verify the current status before adopting) [web: ovirt.org]. Meanwhile, the 2023-2024 changes in VMware's ownership and licensing, widely reported in the trade press, produced a large wave of organisations evaluating KVM-based replacements, among which Proxmox VE gained the most visible share [web: pve.proxmox.com].

The lessons from these histories are practical. Pick a manager with a healthy community and a business model you can understand (subscription support, vendor backing, or a foundation). Prefer a simple architecture you can reason about under failure. Do not underestimate the importance of fencing and shared or replicated storage. The emerging pattern is a **control plane over libvirt/QEMU hosts**, differing in where its state lives (distributed file system, central database, or Kubernetes API) and how much it assumes about storage and networking.

## Current state

**Concepts every cluster manager shares.**

- *Membership and quorum.* A cluster must know which nodes are members and have a rule for making decisions when some nodes cannot talk to others. The rule is **quorum**: an action is allowed only if a strict majority of votes is reachable, so at most one partition can proceed. With three equal nodes, any two form a majority; with two nodes, losing either means the survivor cannot tell a dead peer from a broken link, and the usual fix is a third vote from a lightweight arbiter (Proxmox's QDevice, or a witness).
- *Fencing.* Before restarting a guest elsewhere, the cluster must be certain the failed host is no longer running it. Methods: **STONITH** (forcibly powering off the suspect node) by power or management controller (IPMI, iDRAC, iLO), **watchdog self-fencing** (a node that cannot prove it is healthy resets itself), or storage-based locks and leases. Without fencing, high availability is a risk.
- *Shared or replicated storage.* For a guest to restart on another node, the disk must be reachable there: NFS, iSCSI or Fibre Channel LUNs with a cluster file system or LVM, Ceph RBD, GlusterFS (declining), or storage replication such as ZFS replication with a window of data loss.
- *Scheduling and policy.* Placement by free resources and affinity rules, maintenance mode to evacuate a host, and live migration (T05) for the move.
- *Management network separation.* Heartbeat, storage, migration and guest traffic should travel on separate links or VLANs, so that a migration cannot starve the heartbeat.

**Proxmox VE.** It is distributed as an ISO installer or as packages on Debian, licensed under the GNU AGPLv3, with optional paid subscriptions that give access to the enterprise repository and support. The latest series at the time of writing is 9.2 (x86-64 released in May 2026), based on a Linux 7.0 kernel, QEMU 11.0, LXC 7.0, ZFS 2.4 and Ceph Tentacle, per the project's roadmap (to verify the exact versions when you install) [web: pve.proxmox.com]. Each node stores guest definitions under `/etc/pve`, a FUSE file system provided by `pmxcfs` and replicated through Corosync; VM configurations are plain text such as `/etc/pve/qemu-server/100.conf`, and `qm` (VMs), `pct` (containers), `pvesm` (storage), `pvecm` (cluster), `pveum` (users and permissions) and `ha-manager` are the command-line tools beside the web UI and REST API. Cluster basics from the administration guide: create with `pvecm create NAME` on the first node, join with `pvecm add IP` from others, inspect with `pvecm status` and `pvecm nodes`. Requirements include synchronised time, UDP ports 5405 to 5412 for Corosync, SSH between nodes, the same Proxmox version on all nodes, a latency under about 5 ms on the Corosync network (reliability is unlikely beyond roughly 10 ms with more than three nodes), and a dedicated NIC for it, with up to eight redundant links. Nodes need to be empty of guests when they join, since joining overwrites configuration in `/etc/pve`. With a lost quorum the cluster becomes read-only, so that no one can make conflicting changes, and `pvecm expected 1` is the emergency override that lowers the expected votes [web: pve.proxmox.com].

*Storage* types include local directory, LVM, LVM-thin, ZFS, NFS, CIFS, iSCSI, Ceph RBD, CephFS and Proxmox Backup Server targets, defined once in `/etc/pve/storage.cfg` and marked shared or not. Hyper-converged Ceph (storage and compute on the same nodes, managed from the web UI) is a signature feature. *Networking* uses Linux bridges (`vmbr0`), bonds, VLANs, and an SDN layer with zones (simple, VLAN, VXLAN, EVPN) and, in 9.2, additional fabric protocols such as WireGuard and BGP and a dry-run of SDN changes (to verify) [web: pve.proxmox.com]. *Backup* is built in: `vzdump` and scheduled jobs, and the separate Proxmox Backup Server with deduplication, encryption and incremental transfer. *High availability* is provided by two daemons: `pve-ha-lrm` on each node and a single active `pve-ha-crm` chosen by a lock in pmxcfs. Fencing is by watchdog: a node that loses quorum while running HA services stops feeding its watchdog and is reset after about 60 seconds, after which the cluster resource manager may restart the services elsewhere; the documented failover time is about two minutes. Hardware watchdogs are preferred, with the software `softdog` as a fallback. Resources are added with `ha-manager add vm:100`, placement is controlled by node affinity and resource affinity rules (which replace the older groups since version 9.0), maintenance mode can drain a node, and newer releases offer a dynamic load balancer in the cluster resource scheduler [web: pve.proxmox.com]. HA needs at least three nodes and shared or replicated storage.

**oVirt.** The **engine** (`ovirt-engine`, WildFly-based, PostgreSQL) provides the admin portal, VM portal and a REST API (and an SDK for Python, Go and Ansible roles). Hosts run `vdsmd`, which talks to libvirt and manages storage connections, and are added to **clusters** (a CPU-compatible group, which defines a CPU baseline for live migration), grouped into **data centres** (a shared storage and network domain). **Storage domains** are the central concept: data domains on NFS, iSCSI, FC or GlusterFS, with oVirt managing images and volumes as chains of qcow2 layers on block storage through LVM and its own lease mechanism (sanlock). A **SPM** (storage pool manager) host holds metadata responsibility for a data centre. Networks are logical objects mapped to host NICs, bonds and VLANs, with optional OVN integration. Fencing uses power-management agents (IPMI, iLO, DRAC and others) configured per host, and the engine restarts HA-flagged guests after a host is confirmed fenced. A *self-hosted engine* deployment puts the engine itself into a VM on the cluster, managed by `ovirt-ha-agent`, so a small cluster needs no separate machine for it. Installation is by `hosted-engine --deploy` on the first host. The 4.5 series runs on Enterprise Linux 8, with 4.5.7 adding support for newer operating systems and CPUs after a long pause (to verify against the release notes) [web: ovirt.org]. Because the engine holds all state, its database backup (`engine-backup`) is critical, and without a running engine, guests keep running but nothing can be managed or migrated.

**Comparison in brief.** Proxmox VE is easier to start, covers containers and Ceph out of the box, has built-in backup and a lean architecture, but depends on Corosync limits for large clusters and on a smaller set of enterprise integrations. oVirt offers a central model with data centre, cluster and storage domain hierarchy, richer role-based access and a mature API, but has a heavier installation, an uncertain roadmap after Red Hat's retirement of RHV and a smaller community. For large multi-tenant clouds the choices are OpenStack or CloudStack; for Kubernetes-centred organisations they are KubeVirt and OpenShift Virtualization, in which the VM definition is a Kubernetes object and the scheduler, storage classes and network attachments are those of the cluster (T05's decentralised migration applies [src: kubevirt-user-guide c00a980bca336fb5]).

**Generalised pattern.** A cluster manager is a replicated state store plus a membership protocol with quorum, a scheduler, a fencing mechanism and a per-host agent that turns desired state into libvirt and storage calls.

## Assessment: the good, the bad and the ugly

**The good.** A cluster manager reduces day-two operations from a collection of scripts to a documented product: web UIs for everyday tasks, APIs for automation, integrated backup and role-based access, rolling updates by migration, restart after failure. Proxmox VE in particular gives a small team an open, production-capable platform without a separate management server, with ZFS, Ceph, containers and backup integrated and a large community. oVirt provides a rigorous, enterprise-style model of data centres and storage domains with clean separation of roles. Both build on the same QEMU/KVM/libvirt core, so what you learned in T01 to T07 applies directly: the domain XML, CPU models, disk formats and migration flags are the same ones shown through different front ends.

**The bad.** Cluster software has requirements that are easy to underestimate: a reliable low-latency network for membership, shared storage with enough redundancy, out-of-band management for fencing, and homogeneous hosts. The learning curve is steeper than for a single host, and failures are harder to diagnose, as they cross hosts. Ceph in particular brings its own operational expertise. Versions must be upgraded in order and cluster-wide, and mixed versions are tolerated only during upgrades. Product limits matter: Proxmox's design assumes a modest cluster size (documented production clusters of 50 nodes and more exist, but latency and Corosync traffic grow with size), and its enterprise repository and support sit behind subscriptions, while the community repository is less tested. oVirt carries the weight of its history: a dated host operating system base, an engine that is a single logical point of management, and a smaller maintainer pool.

**The ugly.** Split-brain and fencing failures are the nightmare cases. Without proper fencing, an HA restart on host B while host A is still writing the same disk gives silent corruption; Proxmox's watchdog self-fencing means a transient network problem on the cluster network can reboot a node full of HA guests, which is correct behaviour and a surprise to the unprepared. Quorum loss on a cluster that is not read-only-tolerant freezes configuration changes, including starting guests (changing the expected vote count is an emergency measure that voids the guarantees). Sharing the Corosync network with storage or backup traffic yields evictions during a heavy backup window. Removing and re-adding nodes with the same IP or hostname leaves stale SSH keys and cluster certificates, which the documentation addresses with `pvecm updatecerts`, but which still catches administrators. Another ugly point is lock-in at the data layer: guest configs and storage layouts are portable in principle (qcow2 and raw disks, libvirt-like definitions) but moving between platforms requires conversion work. And business risk: product direction can change, as RHV's retirement showed, and dependency on a single sponsor is a risk to plan for.

## Applications beyond this domain

Quorum, fencing and lease-based locking, the heart of cluster management, are also the core of database replication (Raft and Paxos groups require a majority), distributed file systems, Kubernetes control planes (etcd quorum, node leases), and HA clusters built with Pacemaker and Corosync, the same group-communication engine Proxmox uses. Resource scheduling with affinity and anti-affinity is the same problem Kubernetes' kube-scheduler solves. Maintenance mode and drain are in every orchestrator. Hyper-converged storage with Ceph is a general pattern used far outside virtualisation. The oVirt/RHV to OpenShift Virtualization transition is an instance of a wider trend of running VMs as workloads of a container platform, reusing the platform's networking (Multus, OVN), storage (CSI) and GitOps tooling. Public clouds are, internally, the same architecture at much larger scale: a control plane, host agents, placement, live migration and fencing of failed hosts.

## Examples

**A three-node Proxmox cluster.** Install Proxmox VE on three hosts with two NICs each: one for management and guests, one dedicated to Corosync. On the first node: `pvecm create lab --link0 10.10.10.1`. On the others: `pvecm add 10.10.10.1 --link0 10.10.10.2` (and `.3`). `pvecm status` shows `Quorate: Yes` and three votes. Add a shared NFS or Ceph storage in the UI, create a VM on it, `ha-manager add vm:100`, then pull the power of the node running it: after the watchdog and fencing delay (a couple of minutes) the VM starts on another node. The exercise shows what the pieces do and what the failover time is.

**A two-node cluster with a QDevice.** Two hosts and a small VM on a third machine running `corosync-qnetd`; `pvecm qdevice setup IP` adds the arbiter vote, giving three votes. Switching off one node keeps quorum with two votes, so the survivor keeps working. Without the QDevice, the survivor would go read-only.

**An oVirt data centre.** Deploy a self-hosted engine with `hosted-engine --deploy` on the first of three hosts, add the other two in the admin portal, create an NFS data storage domain, create a logical network on a VLAN, build a template (the same idea as T02) and a pool of VMs from it. Configure power management on each host so that fencing works, and mark the VMs highly available.

**Failing: guests restarted twice.** A homemade HA setup uses a script that pings a host and starts its guests elsewhere when pings fail. A switch reboot makes the host unreachable for 30 seconds; the script starts the guests on a second host while the first still has them running on the same shared LUN. Both write; the filesystems break. A real cluster manager would first fence the host (power it off or ensure the watchdog resets it) and only then recover. The lesson is that detection is not fencing.

**Failing: quorum lost during maintenance.** An administrator takes down two nodes of a three-node Proxmox cluster for firmware updates at once. The remaining node loses quorum, `/etc/pve` turns read-only, and VM starts fail. Fix: update one node at a time, check `pvecm status` before the next, and plan maintenance so that a majority stays up.

## Related problems and ideas

Related problems are cluster-wide backup and disaster recovery across sites (replication with an agreed data-loss window, stretched clusters with a witness in a third location), monitoring of fleets (metrics from `pve-exporter` or oVirt's data warehouse), capacity planning and chargeback, and migration off another platform (with `virt-v2v`, Proxmox's import wizard for ESXi, oVirt's v2v integration, or CloudStack's UI-driven import). Alternatives to the VM-first cluster managers are Kubernetes plus KubeVirt, where the VM is a pod; **OpenStack**, whose services (Nova, Neutron, Cinder, Glance, Keystone) form a full cloud; **CloudStack**; **XCP-ng with Xen Orchestra**; **Harvester** (SUSE's hyper-converged infrastructure on Kubernetes, RKE2 and KubeVirt); **Incus clustering** (T06), which manages containers and VMs on a small cluster with a distributed database; and plain **Pacemaker** clusters managing libvirt domains as resources, which is the most flexible and least friendly choice. Proposed or newer ideas include GitOps-driven VM fleets with Terraform and Ansible providers for libvirt and Proxmox, and declarative cluster definitions where hosts are rebuilt from an image rather than patched.

## Active research

Research and engineering centre on scalable and predictable control planes: replacing Corosync's token ring limits with designs that scale, minimising the failover time (the detection and fencing delay of about two minutes in Proxmox is a floor that vendors are working to lower with faster, safer detection), improving dynamic scheduling (the cluster resource scheduler in Proxmox moves guests to relieve imbalance, and academic work studies migration-aware schedulers that account for the cost of moving), and software-defined networking at the host level (EVPN and VXLAN fabrics automated from the cluster manager). Storage research covers Ceph performance on NVMe, snapshots as volume chains on block storage (a technology preview in Proxmox at the time of writing, to verify), and storage-level fencing. In the Kubernetes world, KubeVirt developers work on storage live migration and cross-cluster migration, VM backup APIs and hotplug. The security community examines multi-tenant isolation on shared hosts and the attack surface of web consoles and APIs, which are privileged entry points to the whole fleet. Open questions: how much of the control plane should move to Kubernetes, how to automate fencing in clouds without BMC access, and how small organisations should plan for a platform whose sponsor may change.

## Future direction

Three trends can be stated with some confidence. First, the post-VMware migration wave continues to push KVM-based platforms, particularly Proxmox VE and Kubernetes-based stacks, toward enterprise features: richer backup and SDN, dynamic load balancing, and tighter integration with Ceph and external storage arrays. Second, the Red Hat line has moved to OpenShift Virtualization, with the community oVirt project continuing at a slower pace; anyone planning around oVirt should check its release cadence (4.5.7 appeared in January 2026) and the status of its main contributors before committing (to verify). Third, VM management converges with container management: the control plane, storage and network models of Kubernetes become the common substrate, with VMs as one workload type. For practitioners the durable knowledge is not a product's menus but the concepts: quorum, fencing, shared storage, scheduling and separation of traffic. Learn those on a small Proxmox lab, and you can evaluate any cluster manager.
