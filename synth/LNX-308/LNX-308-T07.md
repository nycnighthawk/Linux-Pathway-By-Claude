# Hypervisors inside guests, and virtual machines built for speed

## Define the problem

Two separate pressures push virtualisation in directions the classic QEMU and libvirt stack was not designed for. The first is **running a hypervisor inside a guest**. A developer wants to test a KVM-based deployment on a laptop, a continuous-integration service wants every job to boot throw-away VMs while the job itself runs in a VM from a cloud provider, a training platform wants to hand each student a lab host that can itself start guests, and a cloud tenant wants to migrate existing hypervisor images unchanged. Each of these needs the virtualisation extensions of the CPU to be available to code that is itself already virtualised, which the hardware does not provide for free. This is **nested virtualisation**: the physical host is level zero (L0), the guest that runs a hypervisor is L1, and the guests that L1 starts are L2.

The second pressure is the opposite: **making VMs so light that they can be used where containers are used**. A function-as-a-service platform runs code from thousands of mutually untrusting customers on shared servers and wants VM-grade isolation. Containers share a kernel, which is too weak a boundary for hostile tenants, and a conventional QEMU guest boots in seconds, carries tens of megabytes of device-emulation code and a large attack surface, and needs hundreds of megabytes of memory. The requirement is a VM that starts in about a tenth of a second, costs a few megabytes of overhead and exposes only the devices a workload needs. The Firecracker project defines its goal as microVMs that combine the security and workload isolation of traditional VMs with the speed and resource efficiency of containers, suited to multi-tenant services with minimal overhead [src: firecracker-docs 87458cb62cc23e5b].

The scope here is, for nesting: how the feature works, how to enable and verify it on Intel, AMD and ARM, what it costs, and where it is and is not supported. For microVMs: the architecture of Firecracker and its relatives (Cloud Hypervisor, crosvm, QEMU's `microvm` machine type), their API model, the jailer, and the places where they fit. Failure shows up as a nested guest whose `/dev/kvm` does not exist, a cloud instance that refuses to enable nesting, an L2 guest that runs at a fraction of expected speed, or a microVM service whose isolation is undermined because the process around the VMM was left unconstrained.

## History and approaches

Hardware virtualisation (VT-x, AMD-V) was designed for one level. A CPU in guest mode raises a VM exit when the guest executes a virtualisation instruction such as VMLAUNCH, and no mechanism lets that guest run its own guests directly. The first answer was for the L0 hypervisor to emulate the extensions in software: L1 believes it is controlling real VMX hardware, but each of its VMCS (virtual machine control structure) operations is intercepted and recorded by L0, which merges L1's wishes with its own to build the real VMCS used to run L2 (a "shadow" VMCS). Ben-Yehuda and colleagues at IBM Haifa published this scheme as "The Turtles Project" in OSDI 2010 and implemented it in KVM; the result, merged in Linux 3.x, reported overheads of a few to some tens of percent for nested guests with the hardware features of the time. It remained experimental for years: nested KVM was off by default, flagged unstable, and users hit bugs when the L1 hypervisor was anything other than KVM. Arch's wiki states the recipe from this period, still current on Intel: unload `kvm_intel`, reload with `nested=1`, and make it permanent through a modprobe configuration, with the same applying to AMD [src: archwiki 00e4728ed98ea453].

Cloud providers responded slowly because nesting complicates isolation and adds attack surface. Google offered it on Compute Engine from 2017 for Intel hosts, and Microsoft supported it on Azure for Hyper-V-based hosts in specific VM series. AWS held back for years; EC2 users who wanted to run KVM or Firecracker needed expensive bare-metal instances. The situation changed in February 2026, when AWS announced nested virtualisation for selected eighth-generation Intel virtual instance families (C8i, M8i, R8i), configured through CPU options at launch (to verify the current list of supported families, because AWS's documentation versions disagree) [web: aws.amazon.com]. For desktop users, Windows, macOS (on Apple silicon from M3 onwards with newer macOS, to verify) and Linux hosts each have their own nesting limits.

On the lightweight side, the starting point was the observation that QEMU's flexibility is exactly its cost. Its device model supports hundreds of devices, much of it legacy, and the security policy of the project itself separates the virtualisation use case, in which only a specific set of devices and a hardware accelerator are in scope, from everything else [web: qemu.org]. Intel's Clear Containers and Hyper's runV, around 2015, trimmed QEMU and the guest kernel to boot containers in a VM, and merged into **Kata Containers** in 2017. Google's **crosvm**, written in Rust for ChromeOS to run Linux apps in a VM, showed that a VMM could be small and memory-safe. Amazon's team built **Firecracker** from crosvm's ideas for AWS Lambda and Fargate, open sourced in November 2018 under Apache-2.0, and the shared Rust components were split out into the **rust-vmm** project, which Cloud Hypervisor (Intel, later Linux Foundation), Firecracker and others now use. QEMU responded with a `microvm` machine type (2019) that drops the PCI bus and most legacy devices. A parallel line was **unikernels** and library OSes, which shrink the guest as well as the VMM, but they never achieved wide adoption outside specific niches because applications must be rebuilt.

Lessons: isolation is mostly a function of how much code is reachable from the guest; a clean API beats a command line for large fleets; snapshotting a booted guest beats booting it again; and defence in depth (process confinement around the VMM) belongs in the design, since a VMM bug is the most likely escape path. The pattern is a *minimal VMM on KVM, wrapped in process-level sandboxing, controlled through an API, started from snapshots*.

## Current state

**Nested virtualisation on Linux hosts.** The L0 host's KVM module must expose the extension. On Intel the parameter is `/sys/module/kvm_intel/parameters/nested`; on AMD `/sys/module/kvm_amd/parameters/nested`. Recent kernels enable it by default on AMD and, since Linux 4.20, on Intel as well, but older or customised kernels may not, so the check is `cat` of the file (values `1`/`Y` mean enabled). To enable: `modprobe -r kvm_intel && modprobe kvm_intel nested=1`, made persistent with `options kvm_intel nested=1` in a file under `/etc/modprobe.d/`. The L0 must also give the L1 guest a CPU that has the virtualisation flag. The Arch Wiki's libvirt page states the only libvirt change needed is to set the CPU model to `host-model` or `host-passthrough` [src: archwiki 33006964f9049ad3]; with a named CPU model such as `Skylake-Server` the `vmx` flag is absent, and `/dev/kvm` will not appear in the guest. Inside the L1 guest, `grep -c -E 'vmx|svm' /proc/cpuinfo` should be non-zero, `lsmod | grep kvm` and `ls -l /dev/kvm` should succeed, and `virt-host-validate qemu` (T01) should pass. `systemd-detect-virt` reports what the machine is running on (for example `kvm`), and `systemd-detect-virt --vm` and `--container` separate cases, which scripts can use to decide whether to attempt nested use [src: man-pages b2d7815c81bb11b9]. In Cloud Hypervisor, nesting is a flag, `--cpus nested=on`, available on x86_64 (KVM and Microsoft hypervisor) and on aarch64 with KVM [src: cloud-hypervisor-docs 137ff06742b427d7].

Constraints: Red Hat's documentation states that in most environments nested virtualisation is only a Technology Preview on RHEL 10, and the one supported configuration is a Windows VM (L1) on a RHEL 9 or 10 host (L0) running WSL2 to create a Linux environment inside it [src: rhel-10-docs dea9920cb131a1b8]. That is an instructive statement of how little vendors will promise. Further, features that do not nest well: live migration of an L1 guest while it runs L2 guests, which is unsupported in many combinations; hardware passthrough into L2 (needs a virtual IOMMU, which Cloud Hypervisor's documentation discusses as protection for nested VMs [src: cloud-hypervisor-docs c79c3f0fb04b4d7a]); confidential-computing modes; and some performance counters. On ARM, nested virtualisation depends on the ARMv8.3 NV (or newer NV2) extension and on Linux KVM support that arrived in the 6.x series with platform support still partial (to verify).

**Cost.** Every VM exit from L2 goes first to L0, which decides whether to handle it or reflect it to L1; reflected exits cost several transitions. CPU-bound L2 work runs at near-native speed, since ordinary instructions do not trap. Workloads with many exits (heavy I/O, page-table changes, timer interrupts) can run several times slower. Good practice is to use virtio devices at every level, give L1 hugepage-backed memory (T04) so the extra address translation level costs less, and avoid nesting for latency-sensitive tests.

**Firecracker.** A Firecracker process is a single-VM VMM. It is written in Rust, uses KVM through rust-vmm crates, and offers a small, fixed device set: virtio block, virtio net, virtio vsock, a serial console, a minimal keyboard controller to reset, and (in recent versions) optional PCI transport, hotplug in developer preview, virtio balloon and entropy, with no BIOS emulation, no USB, no video, no GPU and no device passthrough. Guests boot a kernel directly (an uncompressed `vmlinux` or `bzImage`, with `boot_args`), skipping firmware. Configuration and control occur over a REST API served on a UNIX socket: `PUT /machine-config` (vCPUs, memory, SMT, huge pages), `PUT /boot-source` (kernel path, args, optional initrd), `PUT /drives/{id}` (`path_on_host`, `is_root_device`, `is_read_only`, rate limiter), `PUT /network-interfaces/{id}` (`host_dev_name` of a pre-created tap, `guest_mac`), `PUT /vsock`, `PUT /actions` with `action_type: InstanceStart`, plus `PUT /snapshot/create` and `/snapshot/load`, balloon and metrics endpoints. The same configuration may be passed as one JSON file with `--config-file`. Firecracker documents its design in layers: KVM and the VMM form the first boundary, and the process around the VMM is constrained with seccomp filters, cgroups and namespaces, with privileges dropped through the **jailer** binary that sets up a chroot, a new PID and network namespace, drops to an unprivileged UID and applies cgroup limits before executing the VMM [src: firecracker-docs 74c3f81f3cfd6646]. Because it is an API-driven VMM, orchestration is by code: a controller creates a tap device and an overlay of a root file system, starts a jailed process, sends the sequence of PUT requests and waits for the guest's vsock agent. Rate limiters on disk and network (token buckets) cap noisy tenants. A boot of a minimal Linux guest takes on the order of 125 ms, and the VMM memory overhead is a few megabytes, per the project's published targets (to verify against current numbers).

Snapshots make cold start almost disappear: boot once, run until the runtime is warm, snapshot, then restore copies per request. Section T02 discussed the constraints; the documentation insists that restores need the same CPU model (or a CPU template to mask features) and that network state, random-number state and clocks need repair after restore.

At the time of writing, Firecracker 1.18.0 (9 November, to verify the year) added **Nitro Sandboxes**, an alternative to KVM for launching isolated VMs on EC2 instances through the Nitro Enclaves driver and a new `PUT /enclave` API [web: github.com]. The documentation compares the two modes and says when each fits: a Nitro Sandbox suits workloads on instances where KVM is unavailable and the instance type can host enclaves, while KVM microVMs offer wider feature support such as snapshots and device models [src: firecracker-docs 96f5707701bf9c78] [src: firecracker-docs f10a8d6183e6523c].

**Related VMMs.** *Cloud Hypervisor* is a Rust VMM aimed at cloud workloads with a larger feature set: CPU, memory and device hotplug, vhost-user, VFIO passthrough, vDPA, live migration over TCP/TLS, Windows guest support and an optional virtual IOMMU. It runs on KVM and on Microsoft's hypervisor [src: cloud-hypervisor-docs 9ea5b6ef798906f6]. *crosvm* underlies ChromeOS and Android's protected VMs. *QEMU with `-M microvm`* gives a minimal x86 machine with virtio-mmio devices and no PCI, and `qemu-system -accel kvm -nodefaults` combined with explicit devices yields the same effect by hand. *Kata Containers* places a container's runtime into one of these VMMs behind the standard OCI/CRI interface, so Kubernetes pods are VM-isolated.

**Generalised pattern.** Isolation by reduction: remove everything the workload does not need from the device model and guest kernel; confine the monitor; control through an API; restore instead of boot.

## Assessment: the good, the bad and the ugly

**The good.** Nested virtualisation makes development and testing of virtualisation code practical on one machine or one cloud instance, with no special hardware; it permits tools that start VMs per job (for example CI runners that boot guests for isolation). Firecracker-style microVMs give hardware-boundary isolation at container-like density and start-up times; small code size reduces the attack surface that must be audited, and Rust removes whole classes of memory-safety bugs from the VMM. The API model suits automation. The same technology in the same form runs the biggest public serverless services, so it has been tested under real attack.

**The bad.** Nested virtualisation is slower and less supported than first-level virtualisation, with vendor support often experimental, and combinations that work on one provider fail on another. L1 hypervisors other than KVM are less well supported on Linux hosts. Nested guests often run without huge pages or with limited device options. Firecracker's minimalism is also its limitation: no GPU, no PCI passthrough, no USB, no Windows guests, no live migration, a limited device set and kernel configurations the user must build, so it fits stateless, short-lived Linux workloads and fits poorly with general server consolidation. It also lacks tooling: it does not manage images, networks, storage or schedulers, so a platform must be built around it. Snapshot restore has strict CPU compatibility.

**The ugly.** A nested hypervisor adds a second place where isolation can be broken: a vulnerability in L0's nested VMX emulation (several have been found in KVM's nested code over the years, including cases that allowed an L2 guest to attack L1 or L0) means that enabling nesting for untrusted tenants is a trade of risk for convenience, and cloud providers therefore restrict it. Performance counters, timing and clock behaviour in nested guests are strange: TSC scaling, steal time, and exits inside exits make benchmarks unreliable. A microVM service that skips the jailer, or runs the VMM as root with a broad seccomp profile, forfeits the defence-in-depth the design depends on. Snapshots of a running guest, restored many times, clone random-number generator state, so cryptographic secrets generated before the snapshot repeat in every clone unless the guest reseeds (VMGenID and VMClock devices address this). Network cloning is awkward too, because every restored microVM has the same MAC and IP unless the network namespace trick is used (see Firecracker's notes on clones). Finally, upgrade and support policy: Firecracker releases frequently and has changed snapshot formats between patch releases, so a fleet needs a process for invalidating or re-creating snapshots.

## Applications beyond this domain

Nesting and microVMs appear throughout cloud and developer infrastructure. Serverless platforms run function invocations in microVMs, and container-as-a-service offerings use them to isolate tenants' pods. Kata Containers and gVisor are used to harden Kubernetes clusters for multi-tenant use. CI providers use microVMs for secure build runners, including self-hosted runner controllers that spawn a Firecracker VM per job. Libvirt's own CI documentation describes using custom runners that boot a guest per job, with machine setup details [src: libvirt-docs 18bc1393c5b91336]. Android's virtualisation framework runs protected VMs on phones with crosvm. Security research uses nested hypervisors to analyse malware and to do hypervisor-level introspection: the lower hypervisor can observe a VM without the knowledge of the guest it runs. Education platforms hand out nested lab environments. Vendors of network appliances (virtual routers, firewalls) are routinely tested on nested KVM labs, such as GNS3 and EVE-NG setups, which need nesting to run appliance images inside a cloud VM. On the microVM side, the Firecracker documentation mentions use with container-image rootfs builds and snapshot-based functions, an architecture adopted by many sandboxes for AI code execution.

## Examples

**Enabling and verifying nesting on a lab host.** On an Intel L0, `cat /sys/module/kvm_intel/parameters/nested` prints `N`. Create `/etc/modprobe.d/kvm-nested.conf` containing `options kvm_intel nested=1`, stop all guests, `modprobe -r kvm_intel && modprobe kvm_intel`, and re-read the file: `Y`. In the L1 domain XML, set `<cpu mode='host-passthrough'/>`, boot the guest and inside it check `grep -o vmx /proc/cpuinfo | head -1` and `ls /dev/kvm`. Then install libvirt in L1, create an L2 guest and compare its boot and disk benchmarks with the same guest on L0 to see the overhead.

**A minimal Firecracker run.** Prepare a kernel image `vmlinux`, a root file system image `rootfs.ext4`, and a tap device `tap0` with an address. Write `vm.json` with `boot-source` (`kernel_image_path`, `boot_args: "console=ttyS0 reboot=k panic=1 pci=off"`), `drives` (`drive_id: rootfs`, `path_on_host`, `is_root_device: true`, `is_read_only: false`), `machine-config` (`vcpu_count: 2`, `mem_size_mib: 256`) and `network-interfaces` (`iface_id: eth0`, `host_dev_name: tap0`). Start with `firecracker --api-sock /tmp/fc.sock --config-file vm.json`; the guest boots in a fraction of a second and the serial console appears on the terminal. In production the same configuration is sent by an orchestrator through the socket, under the jailer.

**Failing: no `/dev/kvm` in the L1 guest.** The L1 domain uses `<cpu mode='custom'><model>Skylake-Server</model></cpu>`. `grep vmx /proc/cpuinfo` finds nothing even though L0 has nested enabled. Cause: a named CPU model does not include the virtualisation flag unless it is asked for. Fix: `host-passthrough`, or add `<feature policy='require' name='vmx'/>`.

**Failing: unreproducible keys after restoring snapshots.** A microVM-based function service restores a warm snapshot for every request. Two requests produce the same "random" session identifier, because the guest kernel's RNG state was captured in the snapshot. Fix: reseed on resume with VMGenID support or an agent that mixes in fresh entropy through vsock, and do not generate secrets before the snapshot point.

**Failing: cloud instance rejects nesting.** A launch with the nested option is refused for an instance type outside the supported list. The documentation of the provider (and versions of it) lists which families allow it; the practical fix is to select an allowed family or fall back to a bare-metal instance.

## Related problems and ideas

Neighbours include the use of **hardware enclaves** and confidential VMs (SEV-SNP, TDX) as a different answer to untrusted infrastructure, with trade-offs: they protect the guest from the host rather than the host from the guest, and nesting inside them is limited. **gVisor** reinterprets syscalls in a user-space kernel, trading compatibility and performance for a smaller attack surface without KVM. **WebAssembly** runtimes isolate at the language level, even lighter but with a restricted capability model. **Unikernels** (Unikraft, MirageOS) fold the OS into the application image and boot in milliseconds. **Library of host-side microvm tools**: Firecracker's ecosystem includes `firecracker-containerd`, `ignite` (archived), `Flintlock` and `Ops`. Not yet mainstream: **memory-sharing between restored clones** with copy-on-write so that hundreds of microVMs share most pages; **virtio-pmem and DAX** for sharing a read-only base image; `userfaultfd` lazy restore; and **trusted nested** schemes in which the L1 hypervisor is attested.

## Active research

Open topics: reducing the exit cost of nesting through hardware improvements and software hints (Intel's newer virtualisation features, shadow VMCS and enlightened VMCS for Hyper-V), making nesting safe enough for multi-tenant use through formal analysis and fuzzing of KVM's nested paths, and producing nested support for ARM and RISC-V where the hardware features are newer. For microVMs: faster restore (lazy loading with userfaultfd, snapshot compaction, prefetching working sets recorded from earlier runs), clone uniqueness (VMGenID, VMClock, entropy distribution), device hotplug on PCI-enabled microVMs, and per-VM memory elasticity with balloon and free-page reporting. The Cloud Hypervisor and Firecracker communities also work on confidential microVMs, on Windows and arm64 coverage, and on closer integration with Kubernetes. Academic work compares the isolation and startup of microVMs, containers and unikernels under serverless workloads, and examines the trade-off between sharing and isolation for snapshots of a function runtime.

## Future direction

Expect nested virtualisation to become routine on public clouds as providers add support to more instance families, probably still with restrictions and performance caveats, which makes CI based on KVM guests more portable. Expect microVMs to continue to spread under container interfaces (Kata, runtimes in Kubernetes) and for AI code-execution sandboxes. Firecracker's roadmap shows PCI transport and hotplug, huge-page-backed guest memory, snapshot refinements and the new sandbox mode for EC2, and the project releases roughly every one to two months, so version-specific behaviour should be checked against the release notes [web: github.com]. Confidential computing will gradually reach microVMs. For learners: practise enabling and testing nesting on a lab host, know the CPU flag and module parameters by heart, understand that the jailer and the seccomp filter are part of the product and not optional extras, and treat every snapshot as a cloning of secrets.
