# Moving a running guest between hosts without stopping it

## Define the problem

Hardware needs maintenance, load shifts, and failing components warn before they die. If a guest could only be moved by shutting it down, copying the disk and starting it elsewhere, every kernel update on a host would mean downtime for everything on it, and capacity planning would be a game of avoiding the busy hours. **Live migration** moves a running guest from one physical host to another so quickly that its users and its network peers hardly notice: connections stay open, memory contents survive, and the guest itself is paused for tens or hundreds of milliseconds at most. The problem is difficult because the state of a running machine is large, changes constantly, and has to be reproduced exactly on different hardware.

Four kinds of state must move. First, **memory**, often many gigabytes, which the guest keeps modifying while it is being copied. Second, **device and CPU state**: registers, interrupt controllers, timers, the internal state of every emulated or paravirtual device, which must be restored by a destination QEMU that understands the same layout. Third, **storage**: either the disk is reachable from both hosts (shared storage, so no data moves) or it has to be copied as well, while the guest keeps writing. Fourth, **network identity**: the guest keeps its MAC and IP address, and the switches and neighbours must learn that it now sits behind another port. A failure in any of these shows as an aborted migration (harmless, the guest keeps running on the source), a guest that resumes but is unreachable, or, worst, a guest that is running on both hosts at once and corrupts its disk.

For a learner on this course the scope is the mechanism and the commands: what libvirt does, which prerequisites make migration possible, how to run, monitor, tune and abort one, and how to reason about compatibility. Because this needs two hypervisors, the exercise is a guided one (see the lab guide). Migration between different hypervisor *products*, such as from VMware to KVM, is a related but different task, called conversion, and is described under Related problems. Cluster-level automation of migration (HA restart, load balancing) belongs to T08.

## History and approaches

Migration was first practised on mainframes, but the research that shaped the x86 version came from the Xen team in 2005. Clark and colleagues published "Live Migration of Virtual Machines" at NSDI, showing that iterative copying of memory pages with a short final stop could migrate a running web server with a downtime of 165 ms. Their *pre-copy* algorithm became the template: copy all memory while the guest runs, repeatedly copy the pages it dirtied in the meantime, and when the remaining set is small enough, pause the guest, send the last pages and the device state, and resume at the destination. VMware's vMotion (2003 product, 2005 widely available) followed the same idea. KVM's version arrived in 2007 shortly after its merge; QEMU implemented migration in its own streaming protocol over TCP.

Variations followed, each addressing a weakness of pre-copy. A guest that dirties memory faster than the network can send it never converges: the loop of dirty-page rounds does not end. **Post-copy** migration inverts the order: transfer the minimum state, resume the guest at the destination at once, and fetch missing pages on demand when the guest touches them (using the kernel's `userfaultfd` facility, merged in 2015 for this purpose). It guarantees completion in bounded time but has a heavy price: during the transfer, the guest's state is split between two hosts, so a network failure or the source's death at that point loses the guest. **Auto-converge** throttles the guest's CPU so it dirties memory more slowly; **XBZRLE** compression caches pages and sends only the changed bytes; **multi-threaded compression** (zlib, zstd) and **multifd** (parallel TCP connections that spread the memory over several streams) help throughput, since a single TCP connection rarely saturates a 25 or 100 Gbit link. **RDMA** transport removes most of the CPU cost. **Zero-page detection** and `-incoming defer` mechanisms refined the details.

Storage evolved separately. The simplest approach is shared storage, via NFS, iSCSI, Fibre Channel or a distributed system such as Ceph RBD, where migration moves only memory. Where none is available, QEMU's `drive-mirror` and block migration (`--copy-storage-all`, `--copy-storage-inc` in libvirt) copy the disks over the same connection; early versions were slow, hard to monitor and fragile. An important partial success was NBD-based migration (QEMU's built-in NBD server on the destination receiving a mirror), which became the supported transport and is what libvirt uses today, and which has been extended so that a guest can be migrated even though its disk and memory move to different networks.

Compatibility problems taught harder lessons. A migrated guest wakes up on a CPU that must offer every feature the guest already uses; if the guest saw AVX-512 on the source and the destination lacks it, the guest crashes with an illegal instruction when the next instruction using it runs. Machine types were introduced to freeze the virtual hardware layout across QEMU versions, and libvirt's CPU model comparison (`virsh cpu-compare`, `virsh hypervisor-cpu-baseline`) exists because of this. Live migration of guests with directly assigned hardware (VFIO devices) was impossible for years, since the device's internal state cannot be saved by QEMU; the kernel's VFIO migration interface (v2, 2023) and device-specific drivers from NIC and GPU vendors are now changing that. Cloud Hypervisor documents live migration of VFIO devices as an active capability for its VMM [src: cloud-hypervisor-docs 82816c2dd3b217b2].

The pattern that emerged is a negotiated protocol: the two sides check compatibility ahead of time, choose a transport and a strategy (pre-copy by default, post-copy as an escape hatch), converge under a downtime budget, and verify before releasing the source.

## Current state

**How libvirt migration works.** The client (virsh, or a management system) asks the source libvirt daemon to migrate a domain to a destination URI. Red Hat's guide describes the procedure and prerequisites for command-line migration: both hosts run KVM, can reach each other (verify with `ping`), and need compatible configurations; it distinguishes live migration, where the guest keeps running, from offline migration, where the guest is shut down and only its definition and storage move [src: rhel-10-docs 8e512842667e7a7a]. Migration proceeds in phases defined by libvirt's protocol versions (v3 is the default, with *Begin, Prepare, Perform, Finish, Confirm* steps): the source checks that the domain can migrate and dumps its XML; the destination prepares, creating the matching devices and starting QEMU in `-incoming` mode, waiting for a stream; the source performs the transfer; the destination finishes by resuming the guest (or kills it on failure); and the source confirms and destroys its copy, or resumes the guest if the destination failed. The two hosts must trust each other: the libvirt daemons authenticate over SSH, TLS or Kerberos, and the data stream is separate from the control connection.

**Topologies.** libvirt supports **managed direct** migration (`virsh migrate --live NAME qemu+ssh://dest/system`), where the client mediates and the libvirt daemons talk to each other; **peer-to-peer** (`--p2pt`/`--p2p`), where the source daemon connects to the destination itself, which is the right choice when the client cannot reach the destination; and **tunnelled** (`--tunnelled`), where the memory stream travels inside the libvirt connection instead of a separate QEMU connection, convenient when only one port is open but slower and incompatible with some features. Non-tunnelled migration opens a QEMU connection on a port in the range 49152-49215 on the destination, so a firewall must allow it.

**Essential `virsh migrate` options.**

- `--live` keeps the guest running; without it libvirt suspends the guest first.
- `--persistent` defines the domain on the destination; `--undefinesource` removes the definition on the source; `--copy-storage-all` or `--copy-storage-inc` copy disks that are not shared (the destination needs matching empty images pre-created for the `all` form, as `qemu-img create` with the same virtual size).
- `--compressed` with `--comp-methods xbzrle,zstd` and `--comp-zstd-level`; `--auto-converge` with `--auto-converge-initial` and `--auto-converge-increment`; `--parallel --parallel-connections N` (multifd); `--postcopy` allows later switching, and `--postcopy-after-precopy`.
- `--bandwidth MiB/s` caps the transfer; `--timeout` limits how long a live pre-copy may run before the guest is suspended or switched to post-copy (`--timeout-suspend`, `--timeout-postcopy`).
- `--tls` encrypts the QEMU data stream; without it, memory travels in clear text between hosts, which matters when the network is not trusted. `--xml` supplies an adjusted domain definition for the destination (for different storage paths or bridge names); `--migrateuri` and `--listen-address` choose the data endpoint, and `--dname` renames.
- `--abort-on-error`, `--unsafe` (bypasses disk-cache safety checks, which is how corruption is made), `--offline`, `--change-protection` (prevents changing the domain while it migrates).

Monitoring uses `virsh domjobinfo NAME` (a progress report with data processed, remaining, dirty rate, iteration count, downtime and bandwidth), `virsh domjobabort NAME` (cancel; the guest keeps running on the source), `virsh migrate-setmaxdowntime` (the downtime budget in ms), `virsh migrate-setspeed` and `virsh migrate-postcopy` (switch a running migration to post-copy). The libvirt manual for virsh groups these under domain commands, with the `migrate` family and the job commands described there [src: libvirt-docs ea254334c92f3e7f] [src: libvirt-docs 5eb6c36b25c63cee].

**Compatibility rules.** The libvirt QEMU driver documentation states that most migration compatibility problems arise from the guest CPU modes. With `host-model`, the destination CPU has to provide every feature the origin exposed, plus possibly more, and libvirt can check this before the migration begins; with `host-passthrough`, the host CPU is exposed as precisely as possible, which means libvirt cannot check compatibility in advance and the destination must be at least as capable, otherwise the guest may fail after it resumes [src: libvirt-docs 8dea4c37f352eaa7]. The robust approach in a heterogeneous fleet is a **named baseline CPU model**: compute with `virsh hypervisor-cpu-baseline` the common subset of all hosts' CPUs and use it in every definition (`<cpu mode='custom' match='exact'><model>Skylake-Server</model>...`). The other constraints are identical machine type (or a destination that supports the same versioned name), the same or a newer QEMU on the destination (backwards migration to older QEMU is not guaranteed), the same disk paths and names or an XML rewrite, the same network names or bridges, no host-specific devices (passthrough PCI devices, host USB), compatible huge-page or pinning settings available on the destination (T04), and synchronised clocks, since a guest's TSC frequency must be matched or scaled.

**Network continuity.** After the guest resumes, QEMU sends gratuitous RARP frames (announcements) so the physical switches update their forwarding tables. On networks with port security, sticky MACs or VLAN restrictions, this may fail, and the guest looks migrated but unreachable until the switch learns its location. The destination bridge must carry the same VLANs.

**Storage.** With shared storage, the destination must open the same image with the same cache mode (`cache=none` is required for safety on shared files unless `--unsafe`). Image locking (`virtlockd`, `sanlock`) stops two hosts from writing the same image at once and is handed over during migration. Without shared storage, `--copy-storage-all` mirrors each disk through an embedded NBD server on the destination, taking as long as the data takes to move and adding all subsequent guest writes to the stream.

**Beyond libvirt.** Cloud Hypervisor supports live migration over a TCP stream with TLS between hosts, or a UNIX socket between VMMs on the same host, using `send-migration` and `receive-migration` with parameters for the URLs, certificate directory and number of connections [src: cloud-hypervisor-docs a6f0a0f6a4fc0d97] [src: cloud-hypervisor-docs 429e81253dacd2a1]. KubeVirt drives libvirt migration through a `VirtualMachineInstanceMigration` object and recently introduced a decentralised form that moves VMs across namespaces or between entire clusters, aimed at workload balancing, maintenance and faster restores [src: kubevirt-user-guide c00a980bca336fb5]. Proxmox VE, oVirt and OpenStack Nova wrap the same QEMU mechanism (T08).

**Generalised pattern.** Move state from a live system while it changes, converge under a time budget by iterating, stop briefly for the last difference, verify at the destination, and only then release the source.

## Assessment: the good, the bad and the ugly

**The good.** Migration makes planned maintenance routine: evacuate a host, update it, return the guests. The downtime is short enough for most services; established TCP connections survive. Pre-copy is safe by construction, since until the final step the source has the authoritative state, so any failure leaves the guest running where it was. The tuning options (compression, multifd, auto-converge, post-copy) cover a wide range of guests, and `domjobinfo` gives honest numbers. Combined with shared storage or NBD copying, it needs no special hardware. Security hardening (TLS, authenticated daemons) is available.

**The bad.** It needs homogeneity. The CPU, machine type and QEMU versions must line up, and a heterogeneous data centre must fix on a lowest-common-denominator CPU model, giving up newer instructions. It consumes network bandwidth, which can disturb other traffic, and the guest slows down during migration because dirty-page tracking and throttling cost CPU. Large guests with heavy write activity (an in-memory database) may never converge, and a guest with 1 TB of memory takes a long time even at line rate. Passthrough devices and some confidential-computing features block migration. Storage copy doubles the load on the disks. It also needs two-sided preparation: matching bridges, matching storage paths, open ports, trusted keys.

**The ugly.** Post-copy's risk is real: if the connection breaks during the post-copy phase, the guest's memory is split, and neither host can resume it; libvirt puts the domain in a *paused (post-copy failed)* state and the guest may be lost, which is why post-copy is requested only on reliable, dedicated networks. A migration with `--unsafe` and non-shared caches can produce silent data corruption. Clock jumps after resume cause trouble for applications that assume time is monotonic or for cluster software with short timeouts; the QEMU guest agent can be asked to set the time after migration. Split-brain (the same guest running on both hosts after a faulty manual intervention) is the catastrophic outcome and is the reason image locking exists; manual `virsh start` of a definition on another host while the original is alive is a typical way to create it. A guest with a very high dirty rate reports an ever-growing remaining count; the operator must decide among raising the downtime budget, throttling, or post-copy. Finally, **testing** migration is neglected: a guest that cannot migrate is usually discovered during an emergency evacuation, when a host fails or is draining, rather than in a rehearsal.

## Applications beyond this domain

Checkpoint and restore also supports **container migration**: CRIU (Checkpoint/Restore In Userspace) freezes a process tree and re-creates it elsewhere, which Podman and LXC/Incus expose as `podman container checkpoint` and `lxc move` with live options; the iterative dirty-page copy appears there as well. Databases use log shipping and replica promotion rather than moving the process, the same goal by another route. Cloud providers use live migration to patch hosts without notice: Google Compute Engine's maintenance model is built on it, and AWS and Azure use variants of memory-preserving host updates. Serverless platforms use snapshot and restore to start functions rapidly, sharing the page-fault-driven lazy loading used by post-copy. Network function virtualisation uses migration plus vhost-user state transfer to move virtual routers. The Rocky Linux material on options after VMware shows the business drivers: organisations compare KVM-based managers on exactly the ability to do live migration and migrate guests from VMware [src: rocky-docs 8e2ed3d3f52de089]. The underlying idea, convergent iteration with a bounded final pause, appears in online schema migration, live resharding of databases and garbage collectors.

## Examples

**A routine shared-storage migration.** Two hosts, `hv1` and `hv2`, share an NFS directory for images and have the same bridge `br0` and the same CPU generation. On `hv1`: `virsh migrate --live --persistent --undefinesource --verbose web1 qemu+ssh://hv2/system`. While it runs, `virsh domjobinfo web1` from a second terminal shows memory processed climbing and the iteration counter; `ping web1` from outside shows at most one lost reply. After completion `virsh list` on `hv2` shows `web1` running and on `hv1` nothing.

**Migration with local disks.** The guest's image is on local SSD on each host. Pre-create on `hv2` an empty qcow2 of the same virtual size and path (`qemu-img create -f qcow2 /var/lib/libvirt/images/web1.qcow2 20G`), then `virsh migrate --live --copy-storage-all --persistent --undefinesource --parallel --compressed web1 qemu+ssh://hv2/system`. The transfer takes as long as moving 20 GiB plus memory, and storage dirty blocks are re-sent.

**Failing: the guest crashes after migrating.** Migration reports success, but the guest immediately panics. The guest used `host-passthrough` on a host with AVX-512; the destination had a different CPU generation without it. Since libvirt cannot verify `host-passthrough` before a migration, the check never ran. Fix: use a named baseline CPU model across the cluster, and run `virsh cpu-compare` or `virsh domcapabilities` against each host before adding it to a pool.

**Failing: migration never finishes.** A guest running an in-memory cache dirties 800 MB/s while the link carries 1 GB/s, and the setting `migrate-setmaxdowntime` is 50 ms. `domjobinfo` shows the remaining data oscillating but never dropping under the threshold. Options in order of safety: raise the downtime budget to a few hundred ms, enable `--auto-converge`, add `--parallel` for throughput, or if the network is dependable use `--postcopy` with `virsh migrate-postcopy` when the timeout expires. Abort with `virsh domjobabort` if none is acceptable.

**Failing: unreachable after success.** The guest runs on the destination but nothing outside reaches it. `tcpdump` on the destination bridge shows replies but no inbound requests; the upstream switch's port security remembered the MAC on the old port for 300 seconds. Fix: disable sticky-MAC behaviour for hypervisor ports or enable fast learning, and verify with a rehearsal.

## Related problems and ideas

Related tasks: **conversion between hypervisor products** (VMware to KVM) with `virt-v2v` (a libguestfs tool that converts the disk format and replaces drivers) or `qemu-img convert` together with driver injection; backup and restore as a cold alternative; **disaster recovery** with replication such as Ceph RBD mirroring, which does not preserve memory; and evacuation under failure, where a cluster manager restarts guests on surviving hosts after fencing the failed one, which resumes from disk, not from memory (HA, T08). Alternative approaches to high availability do not move the guest at all: **lock-step fault tolerance** (VMware FT, and the COLO project in QEMU, which runs two copies and compares output) or application-level clustering. Proposed ideas: migration of confidential guests (AMD SEV-SNP and Intel TDX need an attested migration agent that can transfer encrypted state), live-updating the hypervisor in place (kexec-based approaches that keep guest state across host kernel updates), and **memory disaggregation**, where guest memory lives in a CXL pool so that "migration" means re-attaching the same memory to another host.

## Active research

Active topics are making migration finish for guests that dirty memory quickly (machine-learning-predicted dirty rates, adaptive throttling, compression offload to accelerators such as Intel QAT and DSA, which QEMU supports), reducing downtime for guests with VFIO devices (the kernel's VFIO migration v2 interface, vendor drivers for NICs, DPUs and GPUs, the question of dirty tracking in the IOMMU), and migration of confidential VMs. The QEMU developers continue refinements to multifd (including migration over multiple network paths and with zero-copy send), to postcopy preemption (separating the channel used for urgent page requests), and to the hardening of the migration stream, which carries trust implicitly and has been a source of vulnerabilities. Researchers study how to keep a migrating guest's performance from collapsing (workload-aware scheduling of migrations, migration under a power cap) and how to coordinate many simultaneous migrations (evacuating a rack) without saturating the network.

## Future direction

Expect to see stable support for migrating guests with directly assigned network and GPU hardware in mainstream QEMU and libvirt, further automation of CPU baseline computing in management layers, and migration between clusters as a first-class operation in Kubernetes-based virtualisation, following the decentralised migration design. Hardware offload of compression and copying will reduce CPU cost. Confidential guests will gain attested migration, probably first in cloud-provider stacks. Live host update techniques may reduce the need for migration as a maintenance tool for hosts, although evacuation remains the safe default. For the practitioner: build and test migration paths before they are needed, keep hosts homogeneous or baseline the CPU model, never rely on `--unsafe`, and practise reading `domjobinfo`.
