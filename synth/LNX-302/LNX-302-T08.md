# One automation tool for two operating systems: Ansible managing Windows from Linux

## Define the problem

A team that already automates its Linux servers with Ansible is asked to take over a block of Windows servers: domain members, file servers, a few application hosts. The tempting course is to leave them to a graphical console and a separate team with a separate toolbox. The cost shows up quickly in a mixed estate: patch windows are coordinated by phone calls, a change that touches both sides (a DNS record, a certificate renewal, a new service account used by a Linux application against a Windows database) needs two people and two processes, and the configuration of the Windows half is whatever someone last clicked. What is wanted is the property that made Ansible attractive for Linux, namely a human-readable description of the desired state, applied idempotently from a central control node over an existing transport, with no agent to install and keep alive.

A Windows host does not offer what a Linux host does. There is no Python interpreter on it, so the machinery that sends a Python module over SSH and runs it cannot work as it is. The shell is cmd or PowerShell, and its quoting rules differ from POSIX. Modules that manage packages, services, users, files and firewall rules must be rewritten against Windows APIs. The authentication story is different: WinRM uses Kerberos, NTLM or certificates and the encryption is bound to the authentication method, and a domain account is the normal identity. A command that reaches a second server on behalf of the first runs into the "double hop" problem, where the delegated credentials do not exist. Failure looks like a playbook that hangs on connection, a module that reports `changed` on every run, a task that works on the first host and fails with "access denied" the moment it touches a network share, or a certificate error that someone solves by turning validation off and never turns back on.

This slice covers the Linux control node's view of managing Windows: connection plugins and authentication, the module collections, inventory and variables for Windows groups, privilege escalation, domain tasks and a handful of recurring patterns. The general Ansible material (inventories, variable precedence, roles, vault) is covered in the automation course, and the PowerShell and OpenSSH topic in this course covers the target-side configuration of SSH.

## History and approaches

Michael DeHaan's Ansible, released in 2012, made agentless management by SSH mainstream on Unix. Windows was the glaring omission, because the design assumed SSH and Python. The first Windows support, in Ansible 1.7 (2014), written by Chris Church, chose a different design that carried the same philosophy: the control node connects through WinRM, which Microsoft had built into Windows for management, and modules are written in PowerShell, uploaded for each task and executed there. The `pywinrm` Python library gave Ansible a client for the WS-Management protocol and the authentication variants. Later versions added a collection of PowerShell module utilities (`Ansible.Basic` and friends), so that module authors could write modules with argument specs and check-mode support that mirrored the Python framework.

Earlier approaches for Windows configuration management had been different in shape. Group policy and System Center Configuration Manager were agent-based and Windows-only. Puppet and Chef ran agents on Windows nodes, with a pull model. PowerShell Desired State Configuration (2013) brought a declarative resource model and a local configuration manager but needed per-node push or a pull server. Salt used minions. Each made sense inside its ecosystem; few shared a language with the Linux half. What the WinRM approach offered was a single control plane for both, at the price of a more fragile connection layer and a smaller module set.

The partial failures were the connections. WinRM's default listener on HTTP port 5985 is not encrypted at the transport level (message-level encryption protects Kerberos and NTLM sessions), and Basic authentication over HTTP sends credentials in a reversible form; teams that disabled certificate validation to avoid trouble with self-signed certificates paid for it later. CredSSP, which delegates credentials to solve the double hop, widens the damage if the target is compromised. The `winrm` connection plugin's timeouts under load also gave it a reputation for flakiness, which the newer `psrp` plugin (PowerShell Remoting Protocol, also over WinRM, but with the native remoting stack) improved: the project's documentation lists faster operation, resilience to timeouts when the node is busy and better proxy support as its advantages [src: ansible-docs 563fd232908741b3]. The second shift was SSH. Microsoft shipped OpenSSH with Windows Server 2019, and Ansible supported it unofficially from version 2.8 and officially from 2.18, as its introduction to Windows management states, citing easier setup outside a domain, key-based authentication and faster file transfers [src: ansible-docs 7e358f412fba45c8]. The emerging pattern is a choice of three transports for the same modules, with SSH favoured where there is no domain and WinRM-based transports with Kerberos favoured inside one.

## Current state

### What is needed on both sides

The control node runs Linux or macOS with a current `ansible-core` and the collections: `ansible.windows` (core modules such as `win_copy`, `win_command`, `win_shell`, `win_service`, `win_feature`, `win_updates`, `win_user`, `win_regedit`, `win_reboot`, `win_package`, `win_stat`, `win_file`, `win_ping`), `community.windows` (a wider and less strict set, including IIS, scheduled tasks, DNS and DHCP helpers), and `microsoft.ad` (Active Directory objects: `domain`, `domain_controller`, `user`, `group`, `computer`, `ou`, `object_info`). Optional collections provide Chocolatey packaging (`chocolatey.chocolatey`). For Kerberos with WinRM, the control node needs `pywinrm` with the Kerberos extra, or `pypsrp` for PSRP, the system Kerberos libraries (`krb5-workstation` or `libkrb5-dev` for building), and a working `/etc/krb5.conf`. The target needs Windows Server 2016 or Windows 10 or later, which carries PowerShell 5.1 by default, so there is nothing to bootstrap besides enabling the transport; Ansible's documentation states that and ties support to each Windows version's extended support lifecycle [src: ansible-docs ab01ca46af5b5c41].

### Connections and authentication

The three supported connection plugins are `psrp`, `winrm` and `ssh` [src: ansible-docs 47c4ee41b815c81a]. Inventory variables select them:

```yaml
# group_vars/windows.yml
ansible_connection: psrp
ansible_port: 5986
ansible_psrp_protocol: https
ansible_psrp_auth: kerberos
ansible_psrp_cert_validation: validate
ansible_user: svc-ansible@ACME.EXAMPLE
```

For `winrm` the analogous variables are `ansible_winrm_transport` (`kerberos`, `ntlm`, `certificate`, `credssp`, `basic`), `ansible_winrm_server_cert_validation`, `ansible_winrm_scheme`. The authentication choice follows the environment. **Kerberos** is the right one in a domain: the control node obtains a ticket (`kinit svc-ansible@ACME.EXAMPLE`, or a keytab and a credential cache managed by the controller's own process), the target's service principal is `WSMAN/` or `HTTP/` on the machine account, the name in the inventory must be the canonical FQDN, and message encryption is automatic. It needs DNS and time to be right, as covered earlier in this course. **NTLM** works with local accounts and without a domain but is being restricted and does not delegate. **Certificate** authentication maps a client certificate to a local account, avoids passwords and is good for automation hosts. **CredSSP** forwards credentials and so solves the double hop, at a security cost, and should be limited to tasks that need it. **Basic** over HTTPS is the fallback for non-domain labs. With `ssh`, the variables are `ansible_connection: ssh`, `ansible_shell_type: powershell` (or `cmd`), and key authentication is configured as in the PowerShell and OpenSSH topic.

Whichever connection is used, server certificate validation should stay on. For a WinRM HTTPS listener, the practice is to issue the host certificate from the internal CA (the PKI topic of the security course explains the issuing side) and distribute the CA to the control node's trust store, set through `REQUESTS_CA_BUNDLE` or the plugin's CA trust variable.

### Escalation and the double hop

`become: true` with `become_method: runas` runs a task as another user, by default SYSTEM (`ansible_become_user: SYSTEM`) or an administrator account with password. It exists because some operations fail in the network logon session that WinRM creates (installing MSIs, using the Windows Update API, DPAPI, access to mapped drives), and running as a different logon type solves them. The double hop is a separate matter: in a network logon with Kerberos but no delegation, a task on server A cannot reach a file share on server B using the caller's identity. Options include `become` with an explicit username and password (the new logon has the credentials locally, so the second hop works), CredSSP, Kerberos delegation configured in the directory (constrained delegation, resource-based), or moving the data first through the control node with `fetch` and `win_copy`.

### Modules and idempotence

The Windows modules are written for idempotence and, in most cases, check mode. `win_feature` installs a role or feature by name and reports `changed` only if it was missing; `win_service` sets state and start mode; `win_updates` searches and installs updates by category and reboots on request; `win_regedit` sets values; `win_dsc` runs a DSC resource inside a task, which bridges to the large DSC resource ecosystem; `win_package` installs MSI or EXE packages by product ID; `win_shell` runs a PowerShell script and, by default, reports `changed` every time unless the playbook sets `changed_when`. The common mistake is the same as on Linux: using the escape hatch (`win_shell`, `win_command`) where a module exists, which destroys idempotence and check-mode accuracy. Because the Python `command` and `shell` modules cannot run on Windows, a playbook that mixes platforms uses the `win_` modules in a play whose `hosts` is the Windows group, or relies on `ansible.builtin.package` style generic modules only where they support Windows (few do).

Domain operations use `microsoft.ad`. A play that makes a Windows host a domain member with `microsoft.ad.membership`, creates an organisational unit and a service account with `microsoft.ad.ou` and `microsoft.ad.user`, and queries objects with `microsoft.ad.object_info` runs against a Windows DC or a management host with the ActiveDirectory module installed. These modules speak to AD through ADWS on Windows; against a Samba AD DC, where Active Directory Web Services is not provided, the AD modules do not apply, and a Linux-based play runs `samba-tool` through the command module on the DC, or uses `community.general.ldap_entry` and related LDAP modules (to verify module coverage against the Samba version in use) [web: docs.ansible.com].

### Structure of a mixed project

A practical layout has a single inventory with groups `linux` and `windows`, group variables for connection settings, roles that are platform-specific (`role_win_baseline`, `role_linux_baseline`) and playbooks that call both (for example a certificate rollout: a Linux play that renews with the internal CA and a Windows play that imports). Vault holds the service account's secret, as the vault topic of the automation course explains. A controller (AWX or the Red Hat automation controller) running a custom execution environment image with `pywinrm`, `pypsrp` and the Kerberos libraries avoids installing them on the user's workstation, and holds the Kerberos configuration in one place.

### The generalised pattern

Agentless configuration management for a platform without the original transport is built from the same parts: a way to carry a payload (WinRM, SSH), an interpreter on the target that the platform already has (PowerShell), a module library that expresses desired state, and a model of identity that maps cleanly to the platform's own (Kerberos accounts and run-as). That generalises to network devices (`network_cli`, `netconf`), to cloud APIs (modules that run on the control node), and to appliances.

## Assessment: the good, the bad and the ugly

The good. The same inventory, role structure, review process, lint and CI pipeline apply to both families. Central change history for Windows servers appears for the first time in many organisations. No agent is needed, and the target footprint is a PowerShell remoting endpoint that is already there. A mixed playbook can orchestrate a change that spans platforms in order, such as stopping an application on Linux, taking a Windows database offline, patching and rebooting each and starting them in the right order. Check mode and diff mode help review changes, and the module set covers the 80 percent that administrators automate (features, services, packages, registry, scheduled tasks, files, users and updates).

The bad. The Windows module set is smaller and younger than the Linux one, and some modules are thin wrappers that do not cover all options. Speed: each task uploads a PowerShell payload and starts a runspace, so a playbook with hundreds of tasks is slow compared with the same on Linux over a multiplexed SSH connection; pipelining does not apply to PowerShell, so the cost is paid per task, and strategies such as `free` or more forks only partly offset it. Authentication setup is fiddly the first time and has many failure modes. Reboots and updates need `win_reboot` with sensible timeouts and handling of the update cycle in which the host reboots two or three times. Windows-specific quoting (backslashes in YAML, `{{ }}` templating mixed with PowerShell `$()`) causes mistakes, and paths with backslashes inside double-quoted YAML strings are a recurrent source of errors.

The ugly. Silent insecurity. A configuration copied from a blog that sets `ansible_winrm_server_cert_validation: ignore` and `ansible_winrm_transport: basic` over HTTP works first time and stays forever. A second ugly is drift between what Ansible manages and what group policy manages: if both control the same registry key, the last writer wins on every run, producing a perpetual `changed` and a policy that flickers; the solution is to decide ownership per setting. A third is secret handling: service account passwords in inventory or logs (set `no_log: true` on tasks that handle them). A fourth is the client cost of Kerberos in the controller: tickets expire in ten hours, and a long-lived controller needs a renewal process or a keytab-based login in each job. Finally, Microsoft's changes to authentication (the move away from NTLM and the stricter channel binding on WinRM listeners) can break a working setup after an operating system update, so the pipeline should test the connection as its first task, with `win_ping`, in every run.

## Applications beyond this domain

The same arrangement of carrying a script payload over a management channel and executing it with the platform's own interpreter appears for network gear, where Ansible uses `network_cli` and device CLIs, and for cloud services, where modules run on the control host and call REST APIs. Kubernetes operators apply the same idempotent reconcile idea with controllers rather than a push tool. PowerShell DSC, Chef InSpec and Puppet's resource abstraction layer are alternative implementations of "describe state, converge, report". The security lessons carry over as well: choose the strongest authentication the platform supports natively, never turn off certificate validation to hide a name problem, and separate the identity that Ansible uses from any human administrator's.

## Examples

Worked example 1, a first contact. A control node with a Kerberos ticket for `svc-ansible` runs `ansible windows -m ansible.windows.win_ping`, with the inventory above. Success returns `pong`. A second command, `ansible windows -m ansible.windows.setup -a 'gather_subset=min'`, shows the facts (`ansible_os_family: Windows`, edition and PowerShell version). Both run over the chosen transport and test the whole path: DNS, time, ticket, listener, certificate.

Worked example 2, a baseline play for file servers:

```yaml
- hosts: windows_files
  tasks:
    - name: File server role present
      ansible.windows.win_feature:
        name: [FS-FileServer, FS-Resource-Manager]
        state: present
      register: feat
    - name: Reboot only when the role install asks for it
      ansible.windows.win_reboot:
      when: feat.reboot_required | default(false)
    - name: Time source is the domain hierarchy
      ansible.windows.win_service:
        name: w32time
        start_mode: auto
        state: started
```

Run twice, the second run reports no change, which is the test of idempotence. In check mode the plan can be reviewed first.

Worked example 3, a failing one: the second hop. A task copies a build artefact from `\\files\builds` to a web server with `win_copy` and `remote_src: true`. The play reports `Access is denied`, although the service account can open the share interactively. The network logon created by WinRM carries no credentials for the second server. Three fixes exist: `become: true` with `become_method: runas` and explicit credentials, constrained delegation configured on the web server's computer object, or a change of design in which the control node fetches the artefact and pushes it. The first is quickest and keeps the secret in vault.

Worked example 4, a failing one: the hanging connection. A play against new servers hangs for the connection timeout, then fails with `kerberos: Server not found in Kerberos database`. The inventory uses the IP address, and Kerberos needs a name for the service principal. Using the FQDN fixes it. A related symptom, `the specified credentials were rejected by the server`, indicates a wrong password or an account that is not allowed network logon, and `HTTPSConnectionPool ... certificate verify failed` points at the trust store, not at Windows. The decision to set validation to `ignore` is recorded as a risk with an expiry date if it is ever made, in a lab only.

## Related problems and ideas

Competing approaches are PowerShell DSC, which has a version 3 that runs cross-platform and is JSON-driven, and which can be used from Ansible through `win_dsc`; Group Policy for settings that a domain should enforce continuously rather than at playbook time; Microsoft Intune and Configuration Manager for desktop fleets; and Chocolatey or WinGet for packages. Agent-based tools such as Puppet and Salt offer pull models that handle disconnected nodes better. For events in the other direction, a Windows host that runs WSL and a Linux playbook inside is a development convenience. In Active Directory itself, Terraform has providers for AD objects, and Samba-based directories may be managed through `samba-tool` wrapped by roles. Not yet mainstream: policy-as-code frameworks that validate both the Ansible and the group policy side against a common baseline, and a push of Windows configuration through an OpenSSH-only management plane, so that no WinRM listener is needed at all.

## Active research

Ansible's development in this area is the move of the Windows connection plugins toward SSH and PSRP as first-class transports, the PowerShell 7 support work that allows modules to opt into the newer shell (documented through the `ansible_pwsh_interpreter` variable and module shebang conventions) [src: ansible-docs eb9824152b2ab67b], the maintenance of the AD collection, and better async and parallel behaviour on Windows. Security researchers continue to study WinRM and SSH on Windows as lateral movement paths, which feeds back into hardening advice. Open questions include how to provide Kerberos single sign-on for SSH-managed Windows hosts, how to test Windows roles in CI (Molecule has no native Windows driver, so teams use hosted Windows runners or cloud images), and how to keep module behaviour stable across Windows Server releases.

## Future direction

Expect SSH to become the default transport for non-domain Windows hosts and PSRP over Kerberos to remain the domain default, with WinRM's classic plugin in maintenance. Expect PowerShell 7 to become common on servers as the interpreter for modules that opt in, bringing the Windows and Linux module toolchains closer. For teams, the sensible steps are to pin collection versions, run `win_ping` in every pipeline, keep the control node's Kerberos configuration under change control, move off Basic and unvalidated HTTPS, and manage a Windows image with Packer plus Ansible so that the playbook converges a known base rather than a hand-built one. The date to watch is the lifecycle end of each Windows Server version that the project says it supports, since the module support window follows Microsoft's extended support (to verify per release) [web: docs.ansible.com].
