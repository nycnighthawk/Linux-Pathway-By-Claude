# Operating Linux inside a real Active Directory: policy, privilege, hardening and lifecycle

## Define the problem

The earlier topics in this course teach single mechanisms: a Samba share, a join, a DC, a Kerberos mount, a DNS record. A genuine enterprise is none of those things. It is a forest that has existed for fifteen years, administered by a Windows team with its own change process, security rules and audit requirements; it has several domains, a delegation model, tiered administration, certificate services, group policy covering thousands of objects, and a security group that watches for lateral movement. A Linux team that arrives in that estate does not get to design the directory. It must fit into it: obtain accounts and permissions through the directory team's process, adopt their naming, tolerate their policy changes, and meet their audit expectations, while keeping the Linux hosts patched, reproducible and manageable by the tools the Linux team already uses.

The problem therefore has several layers. **Enrolment**: how a machine joins without a human typing a domain admin password, and without ending up as a duplicate or orphan. **Authorisation**: which AD users and groups may log in where, may become root, may reach which data; and how that is expressed so that an auditor can read it. **Policy**: how much of the Windows-side configuration regime (password rules, lockout, logon rights, certificates, settings) applies to Linux hosts and by which mechanism. **Hardening and compatibility**: the directory team changes domain-controller defaults (LDAP signing, channel binding, encryption types, NTLM, Netlogon secure channel), and Linux members must survive each change. **Lifecycle**: machine passwords, keytabs, stale objects, decommissioning, cloned images and disaster recovery. Failure looks like a Linux fleet that all falls off the domain one Monday after a DC patch; engineers who have root everywhere because a group was nested wrongly; a security finding that a service account's password has not changed in nine years; or stale computer objects that nobody can safely delete.

This slice is integrative. It builds on the join, Kerberos, DNS and time topics and describes how a Linux team operates in an established AD: delegated join, access control through SSSD, sudo and SSH, group policy for Linux, certificate enrolment, the security changes that break members, and the operating model.

## History and approaches

In the first years of AD adoption by Unix shops (roughly 2000 to 2010), integration meant adding the Services for UNIX attributes to the schema, running `pam_krb5` and `nss_ldap`, and hoping. The control point was the Unix side: each host had its own `access.conf` or `ssh AllowUsers` list, `sudoers` was a file in configuration management, and the directory team saw a handful of service accounts. Commercial products (Centrify, Quest Authentication Services, now One Identity, and Likewise, whose open-source form became `likewise-open` and later the base for PowerBroker Identity Services) filled the gap with a vendor agent that joined the host, mapped identities, and in some cases extended group policy to Unix: the Centrify and Quest agents applied Unix-specific policy objects written into the AD. They offered what the native tools lacked (policy, roles, audit), at a licence cost and with a vendor lock-in, and the open-source world answered by growing SSSD, `realmd` and `adcli`.

The shift in the 2010s was that AD became the identity provider for far more than Windows: SaaS single sign-on, VPNs, network gear. Linux hosts were one more consumer, and the directory team wanted the same controls there as everywhere else. SSSD gained group-policy-based access control (`ad_gpo_access_control`) around version 1.15, evaluating the Windows logon-right policy (the console-logon and remote-desktop-logon rights, and their deny counterparts) for Linux logins, with a mapping of those rights to PAM service names. The Samba project added client-side group policy application (`samba-gpupdate`), and Ubuntu's Canonical released `adsys`, an agent that applies policy files from AD to Ubuntu hosts with its own administrative templates [web: ubuntu.com]. The partial successes were therefore: access control reading the Windows policy, and a modest set of Linux-specific settings applied from AD. The failures were attempts to put Unix configuration into AD wholesale, which resulted in schema extensions, in policy that only one vendor's agent understood, and in a Windows team that did not wish to be the owner of `sshd_config`.

Meanwhile the security environment around AD hardened sharply. The Zerologon vulnerability (CVE-2020-1472) forced enforcement of the Netlogon secure channel in 2021; the 2020 and later changes for LDAP signing and channel binding; the Kerberos PAC changes after CVE-2021-42278 and CVE-2021-42287 (the "noPac" attacks) and CVE-2022-37967; certificate-based authentication hardening after CVE-2022-26923; and the staged retirement of RC4 and NTLM. Each of these shipped as a Windows update with an initial compatibility mode and a later enforcement date, and each broke some non-Windows member that depended on the old behaviour, such as one doing simple LDAP binds, unsigned traffic or RC4-only keys (dates and enforcement phases to verify for the version in use) [web: learn.microsoft.com]. The pattern that emerged: treat the directory as a changing external platform, test against its next defaults before they arrive, and write down what each Linux service depends on.

## Current state

### Enrolment

At scale the join cannot depend on a person pasting an administrator password. Three patterns work. **Delegated join account**: the directory team creates an account with only the rights to create computer objects in one organisational unit (and to reset passwords on them), and automation uses it, with the secret in a vault, with `realm join --computer-ou='OU=Linux,OU=Servers,DC=acme,DC=example' -U svc-join`. **Pre-staged computer object with a one-time password**: the directory team creates the object (`adcli preset-computer`, or by script) and the new host enrols with `realm join --one-time-password=...`, leaving no standing credential on the host. **Keytab-based or certificate-based enrolment** where a bootstrap trust (a cloud instance identity, a signed token) authorises the join through a broker. Whichever is used, the host name must be unique and fully qualified, a computer object left over from a previous incarnation must be reused or removed deliberately, and a cloned image must join after cloning, not before.

### Access control: who may log in

The layers stack, and an auditor reads them in order. First, the directory: which AD groups exist for Linux access (for example `LNX-Admins-Prod`, `LNX-Users-Dev`), created and populated by the directory team's process. Second, SSSD's access provider: `access_provider = simple` with `simple_allow_groups = lnx-users-prod@acme.example` (managed through `realm permit -g`) or `access_provider = ad` with GPO evaluation. With `ad_gpo_access_control = enforcing` the machine's applicable GPOs are fetched from SYSVOL (SSSD reads them over SMB and LDAP), and the Windows logon-right policies decide, with PAM service mappings (`ad_gpo_map_interactive`, `ad_gpo_map_remote_interactive`, `ad_gpo_map_service`) saying that `sshd` is a remote interactive service and `sudo` an interactive one. `permissive` mode logs what would be denied without denying, and the right way to roll it out is permissive first, then enforcing after reading the journal. Third, the per-service layers: `sshd`'s `AllowGroups`, `pam_access`, the `ssh` login with GSSAPI (`GSSAPIAuthentication yes`, `GSSAPICleanupCredentials`), which gives single sign-on from a Windows workstation with PuTTY or the Windows OpenSSH client (when GSSAPI is available) and from other Linux hosts; and a login on the console [src: rhel-10-docs 54f139587f1f0b06].

Privilege follows. The default is to let an AD group (never individual users) become root through `sudoers` rules written in a file managed by configuration management: `%lnx-admins-prod@acme.example ALL=(ALL) ALL`, with the `@` form for fully qualified names and care for group names with spaces (escape them). Alternatives are `sudoRole` objects held in an LDAP source and delivered by SSSD's sudo responder (needs a schema extension in AD, which the directory team may refuse), or the IPA model of central sudo rules and host-based access control in IdM, which gives the Linux team a native tool with a one-way or two-way trust to AD so that AD users appear without touching the AD schema. Red Hat's hardening guidance for IdM illustrates the same principles that apply to any policy layer: disable the default allow-all rule, keep SELinux enforcing, map users to confined SELinux users, define custom roles for least privilege, and make sure that directory traffic uses TLS and that anonymous binds are off [src: rhel-10-docs 54f139587f1f0b06]. An enterprise running SELinux can also map AD groups to SELinux users through SSSD (`selinux_provider = ipa` is IdM only; for AD, `semanage login -a -s staff_u %group` works for group-to-label mapping through NSS names).

### Policy for Linux hosts

What can be configured from AD? Three levels. The Windows policies that are interpreted by SSSD (logon rights as above). Samba's `samba-gpupdate`, which applies the Samba-specific policy extensions (sudoers, scripts, certificate auto-enrolment, firewall, Kerberos, and others, depending on the version) from the machine's GPOs; it runs as a timer and can be restricted to a subset by `--rsop` for testing. Distribution agents such as `adsys` on Ubuntu, with ADMX templates installed in the directory's central store, and settings for privilege rules, scripts, certificates and mounts. In all three the Linux team needs the Windows team to import the templates and link the policy to the right OU, and a clear statement of precedence, because a Linux host also has configuration management. The sane division: AD policy for identity-related settings (who can log in, which certificate to enrol), configuration management for everything else, and no setting owned by both.

### Certificates, secrets and service accounts

Many estates run Active Directory Certificate Services. A Linux host can enrol through the Certificate Enrollment Web Services or the older RPC/DCOM route, using `certmonger` (`getcert request -c ...`) with a Samba or IPA CA helper, or through autoenrolment in `samba-gpupdate`, and renewal is automatic so the service certificate does not expire unattended. Machine keytabs are rotated by the join tools, and the agreed lifecycle is part of the runbook; a service account for an application (for example one that reads an LDAP directory or a database) should be a Group Managed Service Account (gMSA) where the platform supports it, and where not (most Linux applications) a normal account with a long random password in a vault, rotated on a schedule and with an owner. Windows LAPS handles local administrator passwords on Windows; for Linux local accounts, the equivalent is a rotation job writing to the vault.

### Surviving directory changes

A compatibility checklist for a Linux member of a hardened domain: LDAP over TLS (`ldaps://` or STARTTLS, with `ldap_id_use_start_tls = true` and the DC certificates trusted through the system store) so that signing and channel binding can be required without breaking SSSD; Kerberos only with AES keys (`klist -ke` on the keytab, `default_tkt_enctypes` unset or including AES in `krb5.conf`, and `msDS-SupportedEncryptionTypes` on the computer object set to AES-only); no NTLM dependencies (applications using `ntlm_auth`, or Samba with `ntlm auth` set permissively, should be inventoried); the Netlogon secure channel with strong keys for Samba-joined servers (`reject md5 clients`, and `server schannel = yes`, modern defaults); SMB signing on; the time and DNS dependencies from the earlier topic. The test is a staging domain controller or a test OU with the new GPO values applied and a Linux test host that runs the standard login, SSH, sudo, mount and application checks. For an estate that includes Samba DCs the same applies in reverse, since Windows clients tighten their requirements.

### Operating model

The working agreement between the teams, ideally in a document: which OU the Linux computers live in, naming conventions, who creates groups, what is requested through which ticket queue, who owns the DNS records, the maintenance windows for DC patching and what the Linux team monitors (`sssctl domain-status`, `klist -k` age, `chronyc tracking`, failed `realm` operations, the number of Linux computers in the OU compared with the CMDB). Disaster recovery needs thought: if the domain controllers are unreachable, SSSD's cache allows logins for cached users (`cache_credentials = True`, `offline_credentials_expiration`), and every fleet needs at least one local break-glass account whose key is stored offline and whose use is alarmed. Decommissioning removes the host from the domain (`realm leave`) and deletes the computer object and DNS records, which automation should do, and a periodic report of stale computer objects (no password change in 90 days) drives clean-up.

### The generalised pattern

Linux in an enterprise directory is one case of a standard integration problem: a foreign system adopts an external authority's identity, policy and change calendar. The pattern is least-privilege enrolment, authorisation expressed as group membership in the authority, local enforcement through standard hooks (PAM, NSS, sudo, sshd), a defined split of ownership between the authority's policy and local configuration management, and continuous testing against the authority's next change.

## Assessment: the good, the bad and the ugly

The good. Linux hosts that follow this model are boring in the best way. People log in with the same credentials as everywhere else; leavers lose access when the directory disables them; auditors can trace access to groups; certificates and secrets rotate; and the Linux team's tools still do the real work. The standards underneath (Kerberos, LDAP, DNS, NTP) are stable, and a team that can read `sssctl`, `klist` and `journalctl -u sssd` can diagnose most problems.

The bad. Two organisations with different cadences and priorities share one critical system. A DC hardening change that is routine for the Windows team may be an outage for Linux, and vice versa; the Linux team often learns of changes late. Documentation is fragmented between vendor documentation for each distribution, upstream project pages and Microsoft's pages, with different terminology. The GPO-based features are less mature on Linux than on Windows and vary by distribution, so they are hard to rely on as the only access control. Group nesting and token size are a recurring trap: a user in hundreds of nested groups has a Kerberos ticket too large for some clients or services (`MaxTokenSize`, HTTP header limits), and SSSD resolving nested groups slows logins.

The ugly. Orphans and drift. Computer objects of dead Linux hosts remain for years; keytabs for decommissioned systems remain valid; service accounts become the shared password of three teams. A privilege escalation path through AD is a Linux risk too: whoever can add themselves to the `LNX-Admins` group, or change the OU's inheritance, or reset a computer object's password, can become root on the hosts it governs; and a Linux server holds a machine keytab that is, from the directory's point of view, a credential of a domain member, so the compromise of a Linux host is a foothold in AD. This is why directory security teams classify member servers in a tier and why Linux hosts that hold domain credentials belong in the same protection scheme as Windows servers. The related threats are real and documented: Kerberoasting of service accounts with weak passwords, abuse of unconstrained delegation, relay attacks against LDAP and certificate services, and persistence through computer account password changes, which is why the 30-day machine password rotation and the strong-key policy matter. Finally, vulnerability management crosses the boundary: the Linux fleet's patch cycle must handle advisories for Kerberos, SSSD, Samba and `cifs-utils`, and a scanner's report must be validated against backported fixes rather than version numbers, as the distribution's own CVE guidance warns [src: rocky-docs ce6f79e2ec14c8a5].

## Applications beyond this domain

The same operating model governs Linux in any federated environment: Linux hosts under a cloud provider's identity service (OS Login, SSM, Entra login), Kubernetes nodes under a central OIDC provider, and appliances under a corporate SSO. In each, enrolment is automated with scoped credentials, authorisation is group-based, policy comes from two places (the central authority and local configuration management) with a defined split, and the platform owner changes defaults on a calendar that the Linux team must track. The tiering and blast-radius reasoning (a member server's credential is a credential in the directory) applies as well to secrets managers, certificate authorities and CI systems. The idea of testing next-version defaults in a canary before they reach production is the general principle behind staged rollouts of any shared infrastructure.

## Examples

Worked example 1, a rollout plan for 300 RHEL servers. The directory team creates `OU=Linux` with a delegated join account, three groups per environment (`-Users`, `-Admins`, `-Audit`), and links a GPO that denies interactive logon to everyone but those groups. The Linux team builds an image with the packages, a first-boot unit that runs `realm join --computer-ou=... --user=svc-join` fetching the secret from the vault, `authselect select sssd with-mkhomedir with-sudo`, and a configuration-management role that writes `sssd.conf` (`ad_gpo_access_control = permissive`, `use_fully_qualified_names = False` only if the estate is single-domain), `sudoers.d/lnx-admins` and an sshd drop-in. Staging runs for two weeks in permissive mode, with `journalctl -u sssd | grep -i gpo` reviewed daily; then enforcement is enabled by changing one variable.

Worked example 2, a failing one: the Monday outage. After the directory team's patching weekend, every Linux server rejects AD logins. `sssctl domain-status` says offline; the SSSD log shows `Strong(er) authentication required` on its LDAP bind. The domain controllers now require LDAP signing, and SSSD was configured with plain `ldap://` simple binds for a legacy attribute lookup. The immediate repair is `ldap_id_use_start_tls = true` and `ldap_tls_reqcert = demand` with the CA trusted, delivered by configuration management; the lasting repair is the staging DC test. Break-glass local accounts allowed the team in during the outage; its use was logged.

Worked example 3, a failing one: the wrong group got root. The sudoers line named `%Domain Admins`, but because `use_fully_qualified_names` was off and the group was resolved by short name, the name also matched a local group created years before with the same name and a different membership. Auditors found it from `sudo -l -U` output. The corrective actions: fully qualified group names in sudoers (`%domain\ admins@acme.example`), a check in the pipeline that rejects short names, and `getent group` verification as part of the change.

Worked example 4, a lifecycle failure. A hundred computer objects in `OU=Linux` have no logon for 400 days. Checking each against the CMDB shows sixty are retired hosts, thirty are cloned VMs that were never rejoined, and ten are live hosts that fell out of the domain after a power-off period. The cleanup uses a query of `pwdLastSet` older than 90 days, a ticket to the directory team for deletion of the retired ones, rejoin automation for clones, and a monitor that alerts when `net ads testjoin` or `sssctl domain-status` fails on any host.

## Related problems and ideas

The primary alternative is to give Linux its own authority and bridge to AD by trust: FreeIPA or Red Hat IdM as the Linux realm, with a forest trust to AD, so that AD users log in to Linux hosts without any Linux-specific object in AD, with HBAC rules, sudo rules, SELinux user maps, certificates and DNS controlled by the Linux team. The cost is another directory to run; the benefit is independence from the Windows team's cadence. Another alternative is cloud identity: Entra ID's Linux login extension for Azure VMs, or an OIDC-based PAM module, with AD synchronised upward. A third is to authenticate by SSH certificates issued by an internal CA after an SSO step, so that hosts need no directory membership at all and access is granted by short-lived credentials with named principals; this is attractive for large server fleets and cloud workloads, at the price of building the issuing service. On the policy side, newer ideas include compliance-as-code frameworks that express the AD-derived access rules in a profile checked by scanners (OpenSCAP and the Compliance as Code content) and zero-trust access brokers that replace shell logins with audited sessions.

## Active research

Work in progress includes SSSD and Samba changes for new Windows security defaults (LDAP channel binding, Kerberos PAC signatures and SID extensions, AES-only keys), certificate-based Kerberos (PKINIT) with strong mapping rules, passkey and FIDO2 login for Linux against IdM and, as it matures, against AD; the adsys and Samba GPO tooling for broader policy coverage; and Microsoft's stated plans for features that matter to non-Windows members, such as IAKerb, local KDC and restrictions on NTLM (verify the schedule for the Windows Server version in use) [web: learn.microsoft.com]. Open questions are how to give Linux fleets a policy channel that the directory team accepts as theirs, how to attest that a Linux host is in a known good state before it receives a machine ticket, and how to automate the end-of-life of machine credentials in estates with ephemeral hosts.

## Future direction

Expect a continuing tightening: NTLM restricted, RC4 removed, signed and bound LDAP universal, stronger certificate mapping, and Kerberos working in more disconnected cases. Expect Linux tooling to follow with defaults that assume AES, TLS and Kerberos-only. Expect more fleets to enrol by short-lived identity tokens rather than long-lived accounts, and to treat directory membership as one of several identity sources. For a Linux team in an AD estate the durable habits are: agree the operating model in writing with the directory team; use groups, never people, in every rule; roll out enforcement in permissive mode first; test every directory change in staging; keep a break-glass path; inventory every dependency on NTLM, RC4 and unsigned LDAP; and watch machine-account and keytab health as closely as disk space.
