# Serving Windows clients from Linux: the Samba file server

## Define the problem

A company that runs Windows desktops needs somewhere to keep shared documents, and a great deal of that somewhere is a Linux machine: cheaper to license, easy to automate, and often already holding the storage. The difficulty is that a Windows client does not speak "file sharing" in the generic sense. It speaks the Server Message Block protocol, a request-and-response dialect that carries opens, reads, byte-range locks, change notifications, security descriptors, named streams and more. A Linux host answers none of that out of the box. Its kernel offers POSIX files with an owner, a group and nine permission bits (optionally POSIX ACLs), while a Windows client expects an access control list of allow and deny entries, inheritance flags, ownership by a security identifier rather than a small integer, and case-insensitive names with special attributes such as "hidden" and "archive".

Three gaps follow. The first is the wire protocol itself: something on the server must implement SMB well enough that Explorer, `net use` and applications that open files with share-mode flags all work. The second is identity: a person logs in as `ACME\alice`, but the files on disk belong to uid 10001, and the server has to translate in both directions without letting one user read another's data. The third is semantics: locking, opportunistic locks (oplocks, now called leases), case folding, extended attributes and permission models must be reconciled with what a POSIX filesystem actually stores. Failure looks like a share that mounts but silently loses edits when two people open the same spreadsheet, files that show as owned by "Unix User\nobody", permissions that look right in the Linux shell but are denied on Windows, or a client that refuses to connect at all because the server only offers a protocol dialect the client has switched off for security.

This slice covers the Samba file server as a standalone or domain-member service: the daemons, the structure of `smb.conf`, how a share is defined, the two permission models (POSIX ACLs and Windows ACLs), authentication modes and the settings that matter for security. Joining a domain and choosing between identity back-ends is treated in the winbind and SSSD topic, and Kerberos on the client side later in this course.

## History and approaches

The story starts in 1991, when Andrew Tridgell, trying to mount a Unix directory on a DOS PC, reverse-engineered the SMB packets of the day by observation. He released the result as a server for Unix, which grew into Samba (the name is a pun on "SMB"). The project's description of itself, as a Windows interoperability suite that has served files and printers to SMB clients since 1992, is repeated in the Arch Wiki's introduction [src: archwiki ac2030952d130842] and in the Samba overview manual page [src: samba-docs 58229d1e0ba89a4d]. Early Samba was a flat file server using NetBIOS over TCP and a name service (`nmbd`) to answer the broadcast name queries that Windows for Workgroups relied on.

Earlier and parallel approaches each covered part of the need. NFS served Unix clients and never gained a mainstream Windows client; Novell NetWare and Banyan VINES offered Windows clients but a different server platform; Microsoft's own LAN Manager, then NT, owned the protocol. Appletalk and its Unix implementation Netatalk solved the same problem for Macs. The partial successes were products that bridged one pair of systems; the failures were the ones that required client software on every desktop, because users and administrators resisted installing and updating it.

Samba 2 (late 1990s) matured into a stable file and print server with domain-member abilities, and could act as an NT4-style primary domain controller with a local account database (`passdb`). Its weakness was that Windows 2000 had already moved to Active Directory, which combined LDAP, Kerberos and DNS, and Samba 2 and 3 could not be a domain controller in that world. Samba 3 added the ability to join an AD domain as a member, handled by `winbindd`, which kept file serving in step with enterprise identity. Samba 4 (2012) finally implemented the domain controller role itself; it is covered in a later topic. On the file-server side the notable evolution was in the protocol: SMB1 (also called CIFS) was chatty and, as the 2017 WannaCry and EternalBlue attacks showed, dangerous; SMB2 (Vista, 2006) cut the command set to a few dozen and added pipelining; SMB 2.1 introduced leases; SMB3 (Windows 8, 2012) added encryption, multichannel, persistent handles and later (3.1.1) pre-authentication integrity. Samba followed with SMB2 support in 3.6, SMB3 in 4.0 onward, and in current releases SMB1 is off by default on the server and the client; Red Hat's documentation likewise treats the old dialect as something to avoid [src: rhel-10-docs b072a90c7410c5d5].

The lessons that shaped today's design are practical. A generic file protocol without native identity fails; hence identity mapping and winbind. A server that stores Windows-only metadata in the wrong place breaks backup and restore; hence the VFS (virtual file system) module layer that can place ACLs and streams in extended attributes. A flat share with no inheritance model fails in large trees; hence support for NT ACLs. The emerging pattern is a user-space daemon that implements a foreign protocol on top of a native filesystem, with pluggable translation layers where the two models disagree.

## Current state

Samba today is packaged as several cooperating daemons. `smbd` handles the SMB connections: negotiation, authentication, file and print operations; it forks a process per client connection, so a bad request affects one session. `nmbd` provides NetBIOS name service and legacy browsing; modern deployments that use DNS can often leave it stopped (the manual page describes it as the name server for NetBIOS names [src: samba-docs ed6121f85cd9c820]). `winbindd` maps domain accounts to Unix identities and handles domain authentication when the server belongs to AD. A Samba AD domain controller runs a single `samba` daemon instead, with different internal servers, and shares are served by an embedded or separate `smbd`. The Samba manual pages separate these roles clearly [src: samba-docs d213ff7c091f43d6] [src: samba-docs dd6b7e7a32aeeb74].

### The configuration file

Everything lives in `/etc/samba/smb.conf`, an INI-style file with a `[global]` section for server-wide settings, `[homes]` and `[printers]` as special sections, and one section per share. The tool `testparm` parses the file and prints the effective configuration, and with `-v` shows defaults too; Red Hat's procedures use it after each edit [src: rhel-10-docs f27902c5782f5d3a]. After a change, `smbcontrol all reload-config` reloads without dropping sessions, though some parameters (the security mode, the workgroup) are only read at start. A minimal standalone server looks like this:

```ini
[global]
    workgroup = LAB
    server role = standalone server
    security = user
    server min protocol = SMB2_10
    server signing = mandatory
    log level = 1
    log file = /var/log/samba/%m.log
    max log size = 5000

[projects]
    path = /srv/samba/projects
    read only = no
    valid users = @staff
    force group = staff
    create mask = 0660
    directory mask = 2770
```

Here `%m` expands to the client's NetBIOS name, so each client gets its own log. `server role` replaces the older `security` setting for most purposes: `standalone server`, `member server` or `active directory domain controller`. The rules for expansion macros (`%U` user, `%S` service name, `%u`) are what make `[homes]` work: a single section that exposes each user's home directory as a share named after the user.

### Authentication modes

A standalone server keeps its own account database. Samba cannot use `/etc/shadow` hashes, because SMB authentication needs NT hashes (or Kerberos keys) that the Unix password format does not hold. So an administrator first creates the Unix account, then runs `smbpasswd -a alice` or `pdbedit -a -u alice` to add the SMB credentials to the `tdbsam` database (default backend, files under `/var/lib/samba/private`). `pdbedit -L -v` lists users, and `smbpasswd -e` and `-d` enable or disable. Guest access is a separate switch: `map to guest = Bad User` together with `guest ok = yes` on a share lets unauthenticated clients in as the `guest account` (default `nobody`), and the compliance guidance for hardened systems reminds administrators to avoid that on shares that hold anything of value [src: compliance-as-code 3516230fbade47b8].

As a domain member (`security = ads`), the server proves its machine identity to the DC and authenticates users with Kerberos or NTLM passthrough, and Unix identities for domain users come from `idmap config` rules. This is a topic of its own, but it matters here for one reason: in an AD domain, the file server's behaviour on the wire is decided by the domain's policy, not the file server's.

### Two permission models

Samba lets an administrator choose between enforcing POSIX permissions and enforcing Windows ACLs on a share. In the first, the server maps the Windows security dialog onto the owner, group and other bits, and optionally POSIX ACLs on the filesystem. The `force user`, `force group`, `create mask`, `directory mask`, `force create mode`, `inherit permissions` and `valid users` parameters adjust it. The advantage is that Linux tools (`ls`, `chmod`, `setfacl`) tell the whole story. The disadvantage is that the Windows security tab is an approximation: nested inheritance, deny entries and "special" permission combinations cannot be stored.

The second model stores NT ACLs. The `acl_xattr` VFS module keeps the full security descriptor in the extended attribute `security.NTACL` of each file, and Samba enforces it itself, while also checking the underlying filesystem permission, so the usual practice is to open the filesystem permission wide (the share root gets mode 0777 style access for the admin group) and let the NT ACL do the real work. The Red Hat procedure for Windows ACLs shows the pairing of `vfs objects = acl_xattr` with `map acl inherit = yes` and `store dos attributes = yes` [src: rhel-10-docs 01ee5b409b7efbf3]. Administrators then edit ACLs from a Windows machine in Explorer or with `icacls`, or from Linux with `smbcacls`, the `samba-tool ntacl` family, or `sambaacls` helper modules. The filesystem has to support extended attributes (mount option `user_xattr` on older ext4, default now; XFS supports them natively).

Other VFS modules deserve mention. `vfs_fruit` plus `streams_xattr` make a share friendly to macOS clients and Time Machine, with an important ordering rule: `fruit` must be listed before `streams_xattr` and the AAPL extension is negotiated at the first connection, so it must be enabled globally [src: rhel-10-docs 17cc2c9d2a0c2178]. `vfs_recycle` provides a rubbish bin, `vfs_full_audit` records operations to syslog, `vfs_shadow_copy2` exposes filesystem snapshots (btrfs, ZFS, LVM or a snapshot directory) as "Previous Versions" in Explorer, and `vfs_catia` handles characters that Windows forbids in file names.

### Security settings that matter

`server min protocol` and `client min protocol` set the oldest dialect allowed; SMB2_10 or SMB3 is a sensible floor. `server signing = mandatory` makes the server refuse unsigned traffic, defeating tampering and relay attacks at some CPU cost; the CIS-derived rules in the compliance project make the same demand for the client tools [src: compliance-as-code 3a514eb06db353c6]. `smb encrypt = required` (per share or global) forces SMB3 encryption. `restrict anonymous = 2` limits anonymous enumeration. `ntlm auth` can be reduced to `ntlmv2-only` or disabled on servers that join a Kerberos domain. `hosts allow` and `hosts deny` provide coarse source filtering, and a firewall should expose only TCP 445 (and 139 only when NetBIOS is required). Disabling root login to SMB shares is another hardening step the compliance content checks [src: compliance-as-code 847754d0f578e778]. SELinux needs the right context (`samba_share_t`) on shared directories, or the boolean `samba_export_all_rw` as a blunt tool, and `setsebool -P` makes it persistent; on Debian and Ubuntu AppArmor profiles for `smbd` play the equivalent role.

### The generalised pattern

The pattern is: a protocol server running in user space, translating a foreign protocol's semantics onto the host filesystem, with an identity mapping layer and a plugin chain for the places where the semantics do not match. The same shape appears wherever Linux pretends to be something else: an S3-compatible gateway in front of a filesystem, an FTP server with virtual users, an NFS server for macOS.

## Assessment: the good, the bad and the ugly

The good. Samba is mature, interoperable and fast. It serves tens of thousands of clients on commodity hardware; it integrates with AD without requiring a Windows server for file service; its command-line tools (`testparm`, `smbstatus`, `smbclient`, `net`) make it scriptable and its configuration is a text file that fits version control and configuration management. It can run in a container with a bind-mounted directory, and Docker's documentation even shows the reverse, mounting a CIFS share as a volume with a driver option [src: docker-docs 2bf2b51e9f32b532]. The VFS layer allows features, such as snapshots surfaced as previous versions, that many commercial NAS devices re-use (indeed many of them run Samba underneath).

The bad. The configuration is a large parameter space with historic synonyms and interacting defaults: a setting that is harmless alone changes meaning with another one (`force user` combined with `valid users`, `acl_xattr` combined with `inherit permissions`, which invalidates the model). Mixing the two permission models on a tree leads to confusing behaviour, since a `chmod` from Linux and an ACL edit from Windows both touch the same file. Case sensitivity is a recurring trap: the Windows view is case-insensitive while the filesystem is not, so Samba has to scan directories to match names (`case sensitive = auto` and the `preserve case` family exist; a very large single directory slows lookups). Locking is the other classic problem. SMB clients cache aggressively under leases; if a Linux process modifies the same file locally without going through Samba, the client's cache is stale. Samba's answer is `kernel oplocks` and leases integrated with Linux file leases, plus the advice that a share should be served by Samba only, never also by NFS or local processes, unless the sharing is read-mostly. Performance tuning options of the old school (`socket options`, `read raw`) are mostly obsolete and can hurt; the defaults and SMB3 multichannel tend to be better.

The ugly. Identity is the part that bites in production: a changed `idmap config` range on an existing server orphans every file's ownership. A server that is a domain member but whose clock drifts beyond five minutes cannot validate Kerberos tickets, so users suddenly get password prompts. A share on a filesystem that lacks xattr support silently loses ACLs and DOS attributes. Antivirus scanners on Windows that open every file over SMB produce load that looks like a Samba performance problem. Security history matters too: Samba has had critical vulnerabilities, including the 2017 `is_known_pipename` remote code execution (SambaCry) and the 2020 Zerologon exposure on domain controllers, which means patching a file server is not optional. Finally, the protocol landscape keeps moving: Microsoft documents that Windows Server 2025 and recent Windows 11 builds require SMB signing in more cases by default and are removing weaker authentication, so an old Samba configuration with `server signing = auto` and NTLM-only clients may stop interoperating after a Windows upgrade (the exact defaults vary by role and release; see Microsoft's SMB signing page, to verify) [web: learn.microsoft.com].

## Applications beyond this domain

The idea of a user-space translation server is general. FUSE filesystems, object-gateways, and the user-space NFS server Ganesha use the same split: a protocol front end, an abstraction layer, and a back end that is a regular filesystem. Samba's VFS stacking is a cousin of Linux's own layered filesystems, such as overlayfs and the device-mapper stack, with each module wrapping the next. The lessons about identity mapping carry to any bridge between namespaces: containers with user namespaces, NFS with `idmapd`, and cloud storage gateways each need a documented, stable mapping between two sets of identities, and each is easy to break by changing the mapping later. SMB itself appears outside file shares: named pipes carry DCE/RPC calls for printing and account management, and SMB over QUIC lets a share be reached over the internet without a VPN in Windows Server 2025 and recent clients (a Samba equivalent is under development, to verify) [web: learn.microsoft.com].

## Examples

Worked example 1, a departmental share. A team of twelve needs `\\files\projects`. On a Rocky or RHEL host the administrator installs `samba`, creates the group `staff` and the directory `/srv/samba/projects` (mode 2770, group `staff`), sets the SELinux context with `semanage fcontext -a -t samba_share_t '/srv/samba/projects(/.*)?'` followed by `restorecon -R`, adds the share section above, runs `testparm`, enables `smb` with `systemctl enable --now smb` and opens the firewall service `samba`. Each user gets `smbpasswd -a`. A check from another Linux host with `smbclient //files/projects -U alice -c 'ls'` proves the path before anyone tries Windows. This mirrors the procedure in the vendor docs and the community lab guides [src: rocky-docs 71af31337d743edf] [src: debian-handbook c9efee51bbbbaf76].

Worked example 2, a share with Windows ACLs. The administrator sets `vfs objects = acl_xattr`, `map acl inherit = yes`, `store dos attributes = yes`, makes the directory writable by the admin group, and then sets the NT ACL from Windows by connecting as a user that holds the `SeDiskOperatorPrivilege` right (granted with `net rpc rights grant "LAB\Domain Admins" SeDiskOperatorPrivilege`). After that, new folders inherit `Modify` for `LAB\staff` without any Linux-side `chmod`. `smbcacls //files/projects docs -U admin` shows the descriptor from the server's point of view.

Worked example 3, a failing one. A new share is created with `valid users = @staff` but users report "Access denied". The log at level 3 shows `NT_STATUS_ACCESS_DENIED` after a successful authentication. The cause: the share directory is `root:root 0755`, so Samba, running the session as alice, cannot write; `force create mode` and `create mask` do not fix this because they affect only new files. A second variant: SELinux denies the write, with an AVC message in the audit log, and the Linux permissions look right. A third: the user exists as a Unix user but has no SMB password, so authentication fails earlier with `NT_STATUS_LOGON_FAILURE`. The diagnostic order that works is: `testparm` (syntax), `smbstatus` (is the client connected, and as whom), the per-client log (which status code), `ls -ldZ` and `getfacl` (permissions and context), then the audit log.

Worked example 4, protocol mismatch. An old multifunction scanner can only talk SMB1 and fails to store scans on the new server, which has `server min protocol = SMB2_10`. The tempting fix is lowering the floor to NT1, which re-enables a protocol with known remote exploits for every client. The better fix is a dedicated, isolated share on a separate low-privilege instance or an SFTP or HTTPS upload target the scanner can use, or replacing the firmware; the decision is recorded as an exception with a review date.

## Related problems and ideas

Alternatives solve the same need with different trade-offs. NFSv4 with Kerberos (covered later in this course) is the natural choice between Linux systems and gives better POSIX semantics. WebDAV works through proxies and over the internet but has weaker locking. Cloud synchronisation products avoid the protocol problem by syncing files instead of sharing one tree. A clustered filesystem exports through Samba with CTDB (the clustered trivial database), which synchronises locking and identity tables between nodes so that several servers present one namespace. Another opposing approach is to run a real Windows file server and avoid the interop; that is simplest when licences are already paid, and costly when the estate is mostly Linux.

Newer ideas include SMB3 UNIX extensions, which let a Linux client see POSIX modes, symlinks and ownership directly instead of mapping them; Samba has enabled these by default in recent releases (4.23 per the release notes; to verify the exact version) [web: samba.org]. The Linux kernel's in-kernel SMB server, `ksmbd`, aims at higher throughput by running in the kernel, at the cost of a smaller feature set and a different security trade-off; it is a competitor for simple shares rather than a replacement for domain integration. `io_uring` support in Samba's VFS, SMB Direct over RDMA and multichannel point at performance for storage workloads.

## Active research

The open work is mostly in Samba's own repository and at the SambaXP conference. Topics include the replacement of the NetBIOS-era name service with DNS-only operation (removing the need for `nmbd`), better handling of the Windows security descriptors on filesystems with native NFSv4 or NT-style ACLs (ZFS, Btrfs, GPFS and CephFS integrations), SMB over QUIC server support, and modernising authentication: Microsoft's plan to restrict NTLM, with IAKerb and a local KDC as replacements for the cases where a client cannot reach a domain controller, means that Samba needs matching Kerberos features for non-domain situations (to verify the current Samba status) [web: learn.microsoft.com]. Separately, work on the `ksmbd` kernel server and on `cifs.ko` (the client in the Linux kernel, which gained POSIX extension support, compression and better reconnect handling) is documented in the kernel's own pages and the Samba lists. Open questions include how far a user-space server can match kernel server performance on NVMe, and how to retire NTLM without breaking appliances.

## Future direction

Expect stricter defaults. Microsoft's published roadmap to reduce NTLM (a staged plan that, per its documentation, makes signing mandatory for NTLM in later phases, with dates in 2026 and 2027 that should be checked before relying on them) will push mixed estates toward Kerberos everywhere, and Samba follows by tightening its own defaults (SMB1 off, signing required in more cases, weaker ciphers removed) [web: learn.microsoft.com]. Administrators should plan for: encrypted and signed SMB as the baseline, Kerberos for every domain-joined server, and certificate-authenticated SMB over QUIC for remote users. Watch the Samba release notes each quarter (the project issues a new minor version roughly every six months), the vendor changelogs of the distribution packages, and the CVE feed for `samba` and `cifs-utils`. For an operator the durable skills are the stable ones: reading `testparm` output, interpreting NT_STATUS codes, keeping identity mapping fixed, and testing a share from a Linux client before blaming Windows.
