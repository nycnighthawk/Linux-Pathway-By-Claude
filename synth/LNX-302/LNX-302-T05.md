# The two quiet dependencies of Active Directory: DNS and time

## Define the problem

Active Directory looks like a user database, but it behaves like a distributed system whose parts find each other through names and agree about the order of events through clocks. Those two foundations are DNS and time. When they are healthy nobody mentions them. When either one is wrong, the visible symptoms are far away from the cause: a Linux host cannot join the domain, a Kerberos login "fails with a bad password", a replication partner reports error 8524, group policy applies on some clients and not others, or users get prompted for credentials on a share that worked yesterday.

For DNS, the problem is that AD is not content with a plain name-to-address service. A client does not know the address of a domain controller; it asks for service location records (SRV records), for example which hosts offer LDAP for this domain, near my site, as domain controllers. The directory therefore requires a DNS zone that carries a specific set of SRV, A and CNAME records, kept current by the DCs themselves through secure dynamic updates, and queried by every member. The zone must be reachable from every machine that has to join or authenticate, and the machines' resolver must send queries for the domain to the DCs rather than to a general-purpose resolver that knows nothing of the internal zone. For time, the problem is Kerberos. Tickets carry a timestamp, and the KDC rejects any request whose clock differs from its own by more than a configured skew, five minutes by default. Replication and password change also depend on order, and a skew of hours can resurrect or lose a change. Every host in the forest, including Linux members and appliances, must agree about the time, and the agreement must be rooted in something the directory itself controls, since the Windows time hierarchy is defined by domain structure.

This slice covers DNS and time as they concern a Linux administrator in an AD estate: what the DNS zone must contain and how records get there, how Samba AD and Windows DNS differ, how a Linux client's resolver should be set up, how to synchronise time with `chrony` against a domain controller (including the signed-NTP socket in a Samba DC), and how to diagnose the mixed failures. Replication of the directory itself was covered in the previous topic.

## History and approaches

Before Windows 2000, Microsoft networks found each other through NetBIOS name broadcasts and WINS, a name server for flat 15-character names. Windows 2000 chose to build Active Directory on standard DNS, with the SRV record type defined in RFC 2782 (2000) as the service-location mechanism and the dynamic update protocol from RFC 2136 (1997) with a secured variant, GSS-TSIG (RFC 3645), for the clients to register themselves. This was a deliberate departure from the NetBIOS world, and it forced many Unix sites to confront their BIND installations: the first generation of advice was to delegate a subdomain to the Windows DNS servers, or to configure BIND to accept dynamic updates from the domain controllers, which meant either an open update policy (insecure) or a manually managed key. Neither was satisfying, and many sites ended up with a split-brain setup in which the internal zone lived on the Windows DCs and BIND forwarded to them for it.

On the time side, Unix had NTP since the 1980s (Dave Mills) while Windows used a simplified version, SNTP, inside a service called W32Time. The domain model assigned time authority by structure: every member syncs from the DC that authenticated it, every DC syncs from the DC of its parent domain or the PDC emulator, and the forest root's PDC emulator syncs from an external source that the administrator configures. This hierarchy was the first design in which the clock was a managed part of the directory. A complication arose when Windows clients began to expect their time source to sign the response, a feature known as MS-SNTP. A Linux time daemon that did not sign was ignored by domain-joined Windows machines. Samba 4 added a signing socket, so that `ntpd` (patched, from version 4.2.6) and later `chrony` (from 3.0) can ask the Samba process to sign the reply [web: wiki.samba.org].

Samba's own DNS history has two steps. Samba 4.0 supported only BIND9 using the DLZ (dynamically loadable zone) module that reads records straight out of the directory database. This removed the need for dynamic update machinery (the DC writes the records), but demanded a BIND build with DLZ support, the right permissions on the shared keytab, and a restart of BIND when the Samba database changed in certain ways. Samba also gained an internal DNS server, built into the same daemon, which avoids the extra process and is now the default. The documented back ends today are the internal server and BIND9_DLZ; the flat-file BIND mode and the "none" option are not supported for a DC, and in practice a DC admin chooses the internal server unless a feature (full recursion with caching and DNSSEC validation, views) requires BIND [web: wiki.samba.org].

The lessons from these years are blunt. Do not let the AD zone live in a DNS server that cannot handle secure dynamic updates and SRV records. Do not point clients at a resolver that does not know the zone, and do not mix the two kinds of resolver in one `resolv.conf`, since the resolver library treats the entries as equivalent and uses whichever answers first. Do not let the time hierarchy configure itself in a mixed estate; set it on purpose. The pattern that emerged is to treat the DCs as authoritative for both: DNS for the AD zones and time for the domain.

## Current state

### What the zone contains

A domain `acme.example` has a forward zone of the same name, plus `_msdcs.acme.example` (the forest root's delegated zone, which holds records keyed by DC GUID, so that replication partners can find a DC after it is renamed) and the AD-integrated application partitions `DomainDnsZones` and `ForestDnsZones`. The records that matter to a Linux administrator are these:

- `_ldap._tcp.acme.example`, `_kerberos._tcp.acme.example` and `_kerberos._udp.acme.example`, `_kpasswd._tcp.acme.example` (password change) and `_gc._tcp.acme.example` (global catalog), each listing every DC with its priority, weight and port.
- The same names with `dc._msdcs` between the service and the domain (`_ldap._tcp.dc._msdcs.acme.example`), which clients use to locate a DC specifically.
- Site-specific variants under `_sites`, for example `_ldap._tcp.Branch-A._sites.acme.example`, so that a client picks a DC in its own site first. Microsoft's description of DC location explains how the client finds its site and then queries the site-specific records [src: ms-learn-adds d586c23298dacee7].
- A and AAAA records for every DC and every member, and CNAME records in `_msdcs` named by the DC's GUID.

Verification is a short routine: `host -t SRV _ldap._tcp.dc._msdcs.acme.example` (or `dig`), `host -t SRV _kerberos._udp.acme.example`, `host dc1.acme.example`, and a reverse lookup of the DC address. Samba's guide uses the `host` tool for exactly these checks [web: wiki.samba.org]. A Windows DC also writes its records to the file `netlogon.dns` for manual import; the Samba equivalent is the `samba_dnsupdate` tool, which compares the DC's expected records with DNS and corrects them (`--verbose --all-names` shows the diff and repairs it).

### How records get there

The DC registers itself when its Netlogon service (in Samba, the `samba` daemon with `samba_dnsupdate`, run at start and by a timer) starts. Members register their A records either by sending a secure dynamic update (the Windows DNS client does this automatically; the Linux equivalents are `net ads dns register` from the Samba tooling, `realm join` plus SSSD's `dyndns_update = true`, or `adcli`'s update step), or through a DHCP server that updates DNS on their behalf. The update is "secure": the client authenticates with GSS-TSIG using its machine ticket, the DNS server checks the ticket against the machine account, and the record becomes owned by that machine. Only the owner (or an administrator) may change it later. This ownership rule explains a frequent problem: if a DHCP server first creates the record under its own identity, the machine itself will later be denied the right to update it. The Arch Wiki's DHCP-plus-dynamic-DNS recipe for a Samba DC uses an unprivileged AD account for the DHCP server and notes the conflict with Windows clients that try to update on their own, which is resolved with a group policy that disables client-side registration [src: archwiki 91acf37df973d803].

Manual operations use `samba-tool dns` subcommands: `zonelist`, `query <server> <zone> <name> <type>`, `add`, `update`, `delete`, `zonecreate` and `zonedelete`, `roothints`. For example, to create a reverse zone, `samba-tool dns zonecreate dc1 0.0.10.in-addr.arpa -U administrator`, and PTR records are then added by hand or by clients. Samba's DNS accepts only secure updates by default (`allow dns updates = secure only`).

### Samba internal DNS versus BIND9_DLZ versus Windows DNS

The Samba internal server is a simple authoritative-plus-forwarder. It answers for the AD zones and forwards everything else to the configured `dns forwarder`, a single parameter that can name more than one address; it does not recurse on its own for the internet and it does not cache heavily. That is fine for a typical office. BIND9_DLZ gives the DC a full-featured resolver at the price of more moving parts. Windows DNS is richer again: conditional forwarders, stub zones, aging and scavenging, DNS policies for split-horizon and geolocation, and DNSSEC signing. The practical difference most often noticed is scavenging: Windows can delete stale records after the no-refresh and refresh intervals (seven days each by default, when enabled); Samba's DNS does not perform scavenging and stale records of hosts that left the network are removed by an administrator or by a scheduled script, an omission that the Samba wiki's setup guide does not cover and that shows in estates with many laptops and short DHCP leases (to verify against the current release) [web: wiki.samba.org].

### The Linux client resolver

Rules for the member host: the resolver must send AD names to a DC, and only to DCs, unless a split configuration is used. A DC list in `resolv.conf` with the second entry an external resolver is a classic fault, because the stub resolver does not know which server is right for a name; an external answer of `NXDOMAIN` for an SRV query looks identical to a missing record. If `systemd-resolved` is in use (the default on Ubuntu and many others), route the domain to the DCs and the rest elsewhere with `resolvectl domain eth0 acme.example ~acme.example` and `resolvectl dns eth0 10.0.0.10 10.0.0.11`; verify with `resolvectl query -t SRV _ldap._tcp.acme.example` and `resolvectl status`. NetworkManager's `ipv4.dns-search` and `ipv4.dns` settings or a drop-in file for `systemd-resolved` make it persistent. On a Samba DC running on Debian or Ubuntu, the same stub resolver can occupy port 53 and block the DC's DNS service, so it is disabled on the DC itself [web: wiki.samba.org]. The member host also needs a fully qualified hostname within the domain, set with `hostnamectl set-hostname web01.acme.example`, because the join derives the machine name and the DNS registration from it.

### Time

Kerberos tolerates a clock skew of five minutes by default (the Windows security policy that sets the allowed clock-synchronisation tolerance, and `clockskew` in `krb5.conf`). Windows domain members use W32Time with the NT5DS type, which synchronises from the authenticating DC. The `w32tm` command shows and sets it: `w32tm /query /status`, `w32tm /query /source`, `w32tm /monitor`, `w32tm /resync`, and on the forest root PDC emulator `w32tm /config /manualpeerlist:"0.pool.ntp.org 1.pool.ntp.org" /syncfromflags:manual /reliable:yes /update`.

On Linux, `chrony` is the default daemon on the RHEL family and an option elsewhere. A Samba DC with signed NTP carries these directives (names exact, values illustrative): `server <upstream> iburst`, `makestep 1 3` (allow stepping the clock early on), `bindcmdaddress <own address>`, `allow 10.0.0.0/16` (who may query), and `ntpsigndsocket /var/lib/samba/ntp_signd`. The socket directory is created by Samba at first start and needs to be readable by the chrony user (group `chrony` or `_chrony`, mode 0750). A Linux member needs only `server dc1.acme.example iburst` and `server dc2.acme.example iburst`. For a VM host, time can also come from the hypervisor, but the virtual clock should be set to follow one source, not two: the Hyper-V integration time sync and a guest NTP daemon fighting each other produce oscillation. Checks: `chronyc tracking` (offset and stratum), `chronyc sources -v`, `timedatectl`, and for a Kerberos-specific look, `klist` with timestamps, and `kinit -V`. The Arch Wiki's Samba DC page describes the daemon configuration for the NTP part [src: archwiki 10c8afb601d5a00c], and community guides for joining a Rocky Linux host list time synchronisation among the preparation steps [src: rocky-docs b77891cfd2112a46].

### The generalised pattern

AD is a naming-and-time dependent system. The pattern for any component that joins it is: use the domain's resolver for the domain's names, discover rather than configure (SRV, not a fixed list of DCs), take time from the DCs, register own records by an authenticated update, and treat the zone as part of the directory rather than as a separate service.

## Assessment: the good, the bad and the ugly

The good. SRV-based discovery makes the estate self-organising: add a DC and clients find it; lose one and they fail over after a short timeout; site records keep traffic local. Secure dynamic update means no manual record maintenance for the common case. Because everything is standard DNS and NTP, ordinary tools (`dig`, `host`, `nsupdate`, `chronyc`) work and monitoring is easy.

The bad. The dependency is invisible and absolute. A resolver misconfiguration produces errors that mention Kerberos, LDAP or "domain not found", never DNS. The unowned or stale record problem, caused by DHCP or by a re-imaged machine presenting a new key, produces denied updates that nobody notices. Scavenging differences between Windows and Samba lead to stale records and wrong answers in round-robin. Time is bad in different ways: a VM restored from a snapshot or resumed after suspend has a clock that is minutes or days off until the daemon steps it, and a daemon configured with `makestep` only for the first few updates will slew too slowly or refuse to step later. NTP over Windows signed replies breaks when the DC's chrony cannot read the socket (a permissions mistake after a package update). Time zones are a silent distraction: Kerberos uses UTC, but a host whose hardware clock is set to local time while Linux assumes UTC shows a skew of a whole number of hours.

The ugly. Split DNS and DHCP. In large networks the internal zone name equals the public one (a "split-horizon" with a shared name), and a Linux host with VPN software that rewrites `resolv.conf` loses the internal view when the VPN comes up. DNS is also a security surface: unsigned dynamic updates, zone transfers to anyone, and a DC that answers recursive queries from the internet each appear in audits. A final ugly is renaming: neither Windows nor Samba can rename the AD DNS domain or Kerberos realm in place, so a choice of name made in a hurry (`.local`, which is also the mDNS suffix and collides with Avahi, or a name the company later loses) is permanent, and the fix is a new forest and a migration [web: wiki.samba.org].

## Applications beyond this domain

SRV-record service discovery is a general mechanism: XMPP and SIP use it for federation, Kubernetes exposes services and headless pods through cluster DNS SRV records, Consul and CoreDNS-based service meshes publish them, and email autoconfiguration uses them for submission servers. The cluster-DNS example is close to AD in spirit: a name service that is part of the cluster's control plane and fails the cluster when it fails. Time as a dependency recurs in TLS certificate validity, TOTP codes, Kerberos in Hadoop and Kafka clusters, database replication and distributed tracing, and in all of them the rule is to anchor on one trusted source, monitor the offset, and prefer slewing to stepping once the system is running. PTP and hardware timestamping serve the same purpose where microseconds matter, and cloud providers now offer a local time server reachable by a link-local address so that guests do not depend on the internet.

## Examples

Worked example 1, preparing a Linux host for the join. On `web01`, `hostnamectl set-hostname web01.acme.example`. Network configuration: `resolvectl dns eth0 10.0.0.10 10.0.0.11`, `resolvectl domain eth0 acme.example`. Check `host -t SRV _kerberos._tcp.acme.example` and `host -t SRV _ldap._tcp.dc._msdcs.acme.example`; both must list `dc1` and `dc2`. Set `server dc1.acme.example iburst` and the same for `dc2` in `chrony.conf`, restart, and run `chronyc tracking` until the offset is below a second. Only now run `realm join`, whose discovery step and Kerberos requests depend on every item above.

Worked example 2, a failing one: skew after a snapshot. A test VM is restored from a snapshot made three weeks ago. Users get `kinit: Clock skew too great while getting initial credentials`. Because `chronyc tracking` says the system is "not synchronised", the clock was stepped by hours and the daemon is waiting. `chronyc makestep` fixes the clock at once; adding `makestep 1 -1` to the configuration (or a `hwclock --hctosys` at boot, or the hypervisor's guest tools sync-after-restore setting) prevents the repeat. The error comes from the KDC reply, which contains its own time, and `kinit -V` shows the difference.

Worked example 3, a failing one: the second resolver. A server has the DC as the first nameserver and the office router as the second for "resilience". Most of the time everything works. During a DC reboot, queries fall through to the router, which answers `NXDOMAIN` for `_ldap._tcp.dc._msdcs.acme.example`, and `sssd` marks the domain offline and caches that for the next ten minutes. The correct resilience design is two DCs as the two nameservers, and the router (or another resolver) reached only through the DCs' forwarder.

Worked example 4, a stale and unowned record. After a hardware replacement the same host name now has a new machine account password, and its dynamic DNS update is rejected because the A record is owned by the old account's SID in a DNS ACL (visible with `samba-tool dns query dc1 acme.example web01 A`, and with ADSI Edit or the DNS manager security tab on Windows). Deleting the record with `samba-tool dns delete dc1 acme.example web01 A <old-address>` and rerunning `net ads dns register` or restarting `sssd` clears it. In DHCP-driven networks, the cause is more often that the DHCP service created the record, and the cure is to let one party own registration.

## Related problems and ideas

Related problems include the DNS side of hybrid identity: Microsoft Entra Domain Services and other managed AD offerings provide the zone in the cloud and require the on-premises or VPC resolvers to forward to it; Azure private DNS resolvers, Route 53 resolver rules and cloud DNS forwarding zones are the equivalent tools. FreeIPA integrates DNS in the same way, with the `_kerberos` TXT record (realm discovery) and the `ipa` SRV records, and IPA's trust with AD needs conditional forwarding both ways. An alternative to dynamic update is to provision records from configuration management or from an IPAM system, which gives control and audit at the cost of an additional process. On the time side there are other approaches: Roughtime and NTS (Network Time Security, RFC 8915, supported by chrony) authenticate time from external sources, which closes the gap that signed Windows NTP does not cover for the upstream links. A not yet mainstream idea is to drop dependence on synchronised wall clocks in Kerberos altogether, by using challenge-response variants, which would remove the skew rule but changes the protocol.

## Active research

Work in this area includes: the Samba DNS server's move toward better performance and fuller feature coverage (zone scavenging and DNSSEC are repeatedly requested); the standardisation and adoption of NTS for authenticated NTP; Microsoft's work on a more accurate and secure Windows time stack (the 2016 and later improvements to W32Time accuracy, and its stated plans around hardware timestamping); and Kerberos extensions that let clients obtain tickets when no DC is reachable (IAKerb and local KDC), which reduces how often a host needs DNS and time agreement with a domain controller at all. Research questions concern how to monitor skew and DNS correctness continuously across a fleet and how to alert on a gradual drift before it breaks authentication (to verify the vendor timeline for the new Kerberos features) [web: learn.microsoft.com].

## Future direction

Expect time to become more authenticated (NTS on upstream links, signed time between internal hosts) and DNS to move toward encrypted transports for the client-to-resolver hop, with DNS over TLS between internal resolvers; Windows Server 2025 includes support for DNS over TLS and HTTPS features in its resolver stack (to verify the exact roles) [web: learn.microsoft.com]. For Samba, the roadmap items worth tracking are the record-scavenging feature and the continuing alignment with Microsoft's DNS behaviour for new records types. For the administrator, the durable practice is to make DNS and time the first two checks in any directory problem, to put both under configuration management (resolver settings, chrony configuration, hostnames), to monitor offset and SRV record presence as ordinary metrics, and to document the single place where time enters the forest.
