# Running more than one Samba domain controller: replication, sysvol and health

## Define the problem

A directory with a single domain controller (DC) is a directory with a single point of failure. When that machine is rebooted for a kernel update, nobody can log in to anything that needs a fresh Kerberos ticket, group policy is unreachable, and DNS (which in AD is part of the directory) is gone. The remedy is a second DC, and then the real problem begins: two servers must hold the same data, accept writes at the same time, and converge afterwards without a human merging conflicts. Active Directory is a multi-master database. An administrator may reset a password on one DC while another administrator disables the account on a different DC; both changes must survive, and every DC must end up with the same winner for each attribute.

The gap this topic fills is how a Samba-based DC participates in that multi-master world, interoperating on the wire with Windows DCs (mixed forests are common during migrations) and with other Samba DCs. Four sub-problems follow. The directory partitions (domain, configuration, schema, and the two DNS application partitions) must be replicated by the directory replication service (DRS), which Samba implements as DRSUAPI. The topology (which DC pulls from which) must be generated and repaired automatically. The SYSVOL share, which holds group policy templates and logon scripts as plain files, is not part of the database at all, and is replicated by a different mechanism on Windows. And a handful of single-master roles (the FSMO roles) must be placed and, when a host dies, seized. Failure looks like a user whose password change works on one site and not another, a policy that applies on half the clients, a DC that has not replicated for a month and is then used for authentication, or a decommissioned DC whose records linger in DNS and in the directory and keep attracting clients.

This slice covers joining an additional Samba DC, inspecting and repairing replication, the SYSVOL gap and the FSMO roles. Initial provisioning of a domain, DNS and time are treated in the following topic.

## History and approaches

Windows NT4 had a primary controller and read-only backup controllers: one writable copy, replicated by a simple push. That model failed whenever the primary was unreachable (no password changes, no account edits) and when the wide-area link was thin. Windows 2000 replaced it with multi-master replication of the Active Directory database. The design borrowed from earlier distributed systems: each change receives an update sequence number (USN) local to the DC that made it, each DC tracks the highest USN accepted from each peer (the up-to-dateness vector), and attribute-level metadata records an originating DC, version and timestamp so that conflicts resolve deterministically, normally by higher version, then later timestamp, then originating DC identifier. Replication is pull-based inside a site over RPC with notification, and on a schedule between sites, with a component called the Knowledge Consistency Checker (KCC) computing the connection objects that make a ring or mesh with bounded hops [web: learn.microsoft.com].

For the Samba project the first aim in 2003 was only to understand it. Samba 3 could be a Windows-NT-style domain controller and an AD member, not an AD DC. Samba 4, which arrived after almost a decade of work, rewrote the directory as an LDB database (an LDAP-like store on top of the key-value library TDB, later with an LMDB option for large databases), implemented the Kerberos KDC (embedding Heimdal, and from 4.7 optionally MIT Kerberos in a separate build), and implemented the DRSUAPI protocol so that Samba DCs could replicate with Windows DCs. Early Samba 4 shipped with an inbound-only story: a Samba DC could join a Windows domain and pull data, but pushing or acting as the sole DC for a large forest had gaps; also no KCC was present, so the administrator wrote the connections by hand. A KCC was added (a Python implementation, `samba_kcc`, run periodically by the `samba` process) and later became the standard topology generator. Samba's tooling for inspection grew with it: `samba-tool drs showrepl`, `drs replicate`, `drs kcc`, `drs bind`, `drs options`, and the `visualize` family that draws the graph [src: samba-docs 663bc8cab793dd21].

What did not arrive was DFS-R, Microsoft's replication engine for SYSVOL (it replaced the older File Replication Service in Windows Server 2008 domains at the 2008 domain functional level). The documented position of the Samba wiki is that a Samba DC has no built-in SYSVOL replication, and the recommended pattern is a one-way copy from the DC that holds the PDC emulator role [web: wiki.samba.org]. The same wiki records that the older "classic upgrade" and other workarounds failed because ACLs on sysvol files were not preserved. The pattern that emerged: the directory data replicates natively, with a mature KCC, and the file part (SYSVOL) is handled outside the protocol, by convention and by scheduled jobs.

## Current state

### Joining and verifying

A Samba host is made an additional DC with `samba-tool domain join <realm> DC -U 'ACME\Administrator'`, run against an existing DC. Before the join, the resolver must point at an existing DC, the Kerberos client configuration must find the realm (`default_realm`, with `dns_lookup_kdc = true`), and the clock must be close to the existing DC's. The join accepts options that matter later: `--dns-backend=SAMBA_INTERNAL` or `BIND9_DLZ`, `--site=` to place the DC in a named AD site, `--option='dns forwarder=...'` (needed with the internal DNS server) and `--option="interfaces=..."` with `bind interfaces only`. After the join, the new DC is started with the `samba` service (not `smbd`, `nmbd` or `winbindd`, which the AD DC runs internally; a distribution's `samba-ad-dc` unit is the one to enable, with the member-server units masked) and the resolver is changed to point at itself and a second DC [web: wiki.samba.org].

Health is inspected with:

```bash
samba-tool drs showrepl                 # inbound and outbound neighbours, last attempt, last success, error codes
samba-tool drs showrepl --json | jq .   # same, machine-readable
samba-tool dbcheck --cross-ncs          # consistency check of the database; add --fix to repair
samba-tool domain level show            # domain and forest functional levels
samba-tool fsmo show                    # who holds which operations master role
samba-tool visualize reps               # text graph of repsFrom and repsTo
```

`showrepl` is the first tool a Samba administrator learns. For each naming context (`DC=acme,DC=example`, the configuration, the schema, `DomainDnsZones` and `ForestDnsZones`), it prints each inbound neighbour, the time of the last successful sync and the number of consecutive failures. Error numbers are Windows error codes: 8453 means access denied for replication (often a missing "Replicating Directory Changes" right or a bad machine account); 8524 means the DSA's DNS name could not be resolved (a DNS problem, the most common one); 1722 is "RPC server unavailable" (firewall or the daemon down); 8606 or 8240 relate to inconsistencies and lingering objects. The `visualize` subcommands, which take two modes (`ntdsconn` for the configured connections, `reps` for actual repsTo and repsFrom, `uptodateness` for replication lag) and can print a terminal distance matrix or a graphviz document, are intended for the question whether the live topology matches what the KCC intended [src: samba-docs 663bc8cab793dd21].

`samba-tool drs replicate <dest> <source> <naming-context>` forces a pull for one partition, `--full-sync` forgets the stored USN, and `samba-tool drs kcc` asks a DC to recompute its connections. Replication needs the following network access between DCs: TCP and UDP 53 (DNS), 88 (Kerberos), 135 (RPC endpoint mapper), 389 and 636 (LDAP), 445 (SMB), 464 (password change) and 3268 and 3269 (global catalog), plus the dynamic RPC range 49152 to 65535 unless Samba is told to use a fixed set.

### Conflict resolution and tombstones

Replication is state-based. An object deleted on one DC turns into a tombstone (a stripped record that keeps the GUID and deletion time) that replicates like any other change and is garbage-collected after the tombstone lifetime (180 days on forests created with Windows Server 2003 SP1 or later, 60 days on older ones). A DC that is offline longer than the tombstone lifetime and then reconnects can reintroduce deleted objects as "lingering objects", and replication with such a DC should be refused rather than repaired. Microsoft's strict replication consistency setting makes the DC refuse sources with lingering objects. In practice: a Samba DC that has been powered off for several months should be demoted and rejoined, not turned back on.

### SYSVOL

SYSVOL is a directory tree with the group policy templates (`Policies/{GUID}/...`) and logon scripts. A Windows DC replicates it with DFS-R. A Samba DC does not, so administrators use a designated source (usually the PDC emulator holder) and push to the others with `rsync -XAavz --delete-after`, run from cron or a systemd timer on the receiving DCs, since the extended attribute and ACL flags preserve the NT ACLs that Samba keeps in an extended attribute. After a sync, or in a new DC, `samba-tool ntacl sysvolreset` rewrites the ACLs on the tree to the defaults and `samba-tool ntacl sysvolcheck` verifies them. Because the copy is one-way, a policy edited on a non-source DC is overwritten at the next run; the discipline is to edit policy only on the source DC, which is where the Windows Group Policy Management Console should be pointed [web: wiki.samba.org]. For stronger guarantees, some sites use a bidirectional file-synchronisation tool or a shared storage path, though the wiki warns against clustered filesystems that depend on CTDB, since CTDB is not supported on an AD DC.

### FSMO roles

A handful of operations cannot be multi-master. The schema master and domain naming master exist once per forest; the PDC emulator, RID master and infrastructure master exist once per domain. The RID master hands out blocks of relative identifiers to each DC, so that two DCs never allocate the same SID for new objects. The PDC emulator is the authoritative time source, handles urgent password replication and account lockout propagation, and is the preferred target for group policy edits. `samba-tool fsmo show` lists the holders; `samba-tool fsmo transfer --role=all` moves them gracefully; `samba-tool fsmo seize` takes a role from a dead holder, after which the old holder must never return to service without being wiped, to avoid duplicate role holders [web: learn.microsoft.com]. The usual placement advice is to keep the roles together on a well-connected DC in the hub site and to keep the infrastructure master off a global catalog server unless every DC is a global catalog (a rule that applies to multi-domain forests; in a single-domain forest it does not matter).

### The generalised pattern

The structure is multi-master replication with a vector-clock-like version scheme, a topology generator that is itself replicated state, and a handful of roles that need a single decider. The file part rides outside the database and needs its own consistency story.

## Assessment: the good, the bad and the ugly

The good. Samba DCs replicate with Windows DCs and with each other using the same protocol, so a migration from Windows to Samba can proceed one DC at a time, and a mixed environment can run for years. The KCC builds the topology without hand configuration; the tools show everything in plain text; the database is small (a few hundred megabytes for tens of thousands of objects), and a new DC can be joined in minutes, which makes DCs easy to replace rather than repair. Backups are simple: `samba-tool domain backup online` (or `offline`, or `rename`) creates a tarball that can be restored to a new DC, and Samba's documentation encourages running several DCs rather than relying on one backup.

The bad. SYSVOL replication is manual and every operator forgets it once: the symptom is a user whose policy applies when they log on near one DC and not near another, because the second DC's `sysvol` has an older version number than the directory says. Samba's support of Group Policy is client-side (`samba-gpupdate`) and server-side hosting only; editing GPOs needs a Windows machine with RSAT, or the newer `samba-tool gpo` commands. Samba DCs do not support every Windows feature: no read-only DC feature set that matches Windows, the functional level is capped (domain level 2016 is the highest supported in recent releases, to verify), and Microsoft changes in newer schema versions may need manual schema extension. DNS is part of the problem: a Samba DC that is a DNS server for the zone also needs the SRV and CNAME records that make replication findable (the `_msdcs` GUID alias), and those records must be removed when the DC is retired. Upgrades are one at a time: running different Samba versions on DCs is supported only within narrow limits, so a rolling upgrade is a ritual of test, one DC, `showrepl`, next DC.

The ugly. Replication breaks silently if nobody looks. A DC with expired machine credentials, a DNS CNAME gone missing, a firewall rule changed, or a time skew beyond five minutes will stop pulling, and users notice only when their password change at one site is not honoured at another. The directory keeps working, which delays discovery. A second ugly truth is that Samba's own replication metadata is not always understood by Windows tools: `repadmin` run from Windows against a Samba DC mostly works, and `dcdiag` reports Samba-specific false negatives. Another is that demotion needs care: `samba-tool domain demote` removes the DC's objects, but a DC that was shut down and deleted without demotion leaves metadata that must be cleaned with `samba-tool domain demote --remove-other-dead-server=<name>`, DNS record deletion with `samba-tool dns delete`, and a check that no site or connection still refers to it. Finally the cross-version ugly: Windows DC schema or protocol changes (for example Windows Server 2025 enabling the new 32 KB database page size, a forest-level feature with a new functional level) require Samba support that may lag, so a mixed forest should not raise the functional level until Samba states compatibility (to verify) [web: learn.microsoft.com].

## Applications beyond this domain

Multi-master replication with deterministic conflict resolution appears in many places: Cassandra and Dynamo-style stores (vector clocks or last-writer-wins timestamps), CouchDB (revision trees), the Raft-free parts of LDAP (OpenLDAP's syncrepl multi-provider mode), collaborative editors based on CRDTs, and DNS zone transfers (a single-master design, which highlights the contrast). The up-to-dateness vector is the same idea as the version vectors in these systems. The idea that a role that cannot be multi-master is leased or transferred, as the RID master hands out identifier blocks, is analogous to the ID-range allocation in distributed databases, to Snowflake-style identifier generators, and to the leader lease in a consensus system. The SYSVOL gap illustrates a general operations rule: when a system replicates its database but not its adjacent files, the files need their own source of truth and a check that proves they are in step.

## Examples

Worked example 1, adding a second DC. The environment has one Samba DC `dc1` at 10.0.0.10. On `dc2`, install Samba with the AD DC packages and stop the member-server services. Set `/etc/resolv.conf` to the IP of `dc1`, make `kinit administrator@ACME.EXAMPLE` succeed, and run `samba-tool domain join acme.example DC -U'ACME\administrator' --dns-backend=SAMBA_INTERNAL --option='dns forwarder=10.0.0.1'`. Start the `samba-ad-dc` unit, switch the resolver on `dc2` to itself and on `dc1` to include `dc2`. Wait up to fifteen minutes for the KCC, then confirm with `samba-tool drs showrepl` on both DCs that all five naming contexts show a successful last attempt, and set up the rsync job for SYSVOL on `dc2` with `samba-tool ntacl sysvolreset` after the first copy [web: wiki.samba.org].

Worked example 2, a failing one: the stalled DC. `showrepl` on `dc2` reports for the `DomainDnsZones` context, 'last attempt failed, result 8524 (DNS lookup failure)'. A check of `host -t CNAME <guid>._msdcs.acme.example` on `dc2` returns nothing. The cause is that the CNAME record that allows others to find the DC by its database GUID was never registered, because the resolver on `dc2` pointed at an external server during the join. The fix is `samba_dnsupdate --verbose --all-names` (which recreates the records the DC should have), followed by `samba-tool drs replicate dc1 dc2 DC=DomainDnsZones,DC=acme,DC=example`. The lesson is the order of checks: DNS before Kerberos before firewall before database.

Worked example 3, failing the other way. A GPO edit made on `dc2` using RSAT vanishes overnight. `rsync` on `dc2` runs every five minutes from `dc1`'s read-only module with `--delete-after`, so the edit was overwritten. The corrected procedure is to point the GPMC at the PDC emulator, `dc1`, and to put a banner file in `dc2`'s sysvol that reminds editors. A deeper fix is to change the direction of the arrow when the PDC role moves, which is why the rsync target should be derived from `samba-tool fsmo show` and not written into the job by hand.

Worked example 4, retiring a DC. `dc3` is replaced by a rebuilt host with a new name. The administrator transfers any roles away (`samba-tool fsmo show` on the survivor), runs `samba-tool domain demote` on `dc3` while it is still reachable, then checks `samba-tool dns query dc1 acme.example @ ALL` for SRV and A records pointing at `dc3`, and clears them. If `dc3` died instead, `samba-tool domain demote --remove-other-dead-server=dc3` is run from a survivor and the roles are seized, as a last resort, with `samba-tool fsmo seize --role=...`.

## Related problems and ideas

Neighbouring problems are the same ones other directory systems face. Windows' DFS-R and the older FRS solve the file part with a different engine; running a Windows DC alongside a Samba DC only for SYSVOL purposes is an approach, and some sites keep one Windows DC for policy editing and as the SYSVOL source. FreeIPA uses 389 Directory Server multi-supplier replication with a topology managed by `ipa topologysegment-*`, and an IPA trust to AD avoids having two directories share a schema. A different approach is to avoid DC proliferation: a single DC plus a tested backup and a documented rebuild is a legitimate design for a small office that can tolerate an hour of downtime, though it is a conscious choice. Read-only DCs for branch offices exist in Windows; the Samba equivalent is only partial. Proposals not yet mainstream include a unified replication of SYSVOL content as an LDAP-backed object store, and git-based GPO deployment, where policy lives in version control and is rendered to the sysvol tree by a pipeline, giving history and review that DFS-R never had.

## Active research

Active work in the Samba project, visible in the release notes and the SambaXP talks, includes an LMDB database back-end to remove the size and locking limits of TDB, performance of the DRS client for large initial syncs, the KCC's handling of large site topologies, improved `dbcheck` that fixes more classes of inconsistency, support for newer functional levels and the Windows Server 2025 database format, and the integration of MIT Kerberos for features that Heimdal lacks (to verify per release). Questions open to the community include how to handle SYSVOL in a way that the Windows tools consider valid (a native DFS-R implementation is not on the roadmap), how to provide read-only DC functionality, and how to move to a point where NTLM is not needed by the DCs themselves.

## Future direction

Plan for gradual improvement rather than a leap. The 4.2x releases, issued roughly twice a year, keep tightening defaults and adding functional-level support, and an administrator should expect to schedule a DC upgrade pass twice yearly, always one DC at a time with `showrepl` and `dbcheck` between steps. Microsoft's changes in Windows Server 2025 (new forest and domain functional levels, the larger database page size, expanded security defaults) will arrive in mixed forests first, so any estate that mixes DCs should watch Samba's compatibility statements before raising levels (to verify) [web: learn.microsoft.com]. Operationally, treat DCs as replaceable: automate the join, automate the SYSVOL job and its monitoring, take online backups, test the restore, and alert on `showrepl` failure counts, because that is the one signal that predicts the worst outage.
