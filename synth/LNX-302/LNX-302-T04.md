# Reaching Windows and Samba shares from Linux without typing a password: SMB clients with Kerberos

## Define the problem

A Linux workstation or application server needs to read a share that lives on a Windows file server or a Samba server in an Active Directory domain. The easiest way to make that work is to put a user name and password in a file and hand it to `mount`. It also produces the worst security outcome: a long-lived secret on disk, shared by every process that touches the mount, unrelated to the person who is actually acting, and stale the day the password rotates. In a domain, the right answer already exists. The user (or the machine) holds a Kerberos ticket-granting ticket, and the file server accepts a service ticket for its `cifs/` service principal. Nothing secret crosses the wire in a form that can be replayed, the server learns who is calling, and access control lists on the share can name real people.

The problem is that the SMB client in the Linux kernel is a kernel component, and a kernel cannot run the Kerberos protocol. It cannot read a credential cache, query a KDC, or prompt anyone. The user-space SMB tools (`smbclient`, `smbget`, `rpcclient`, the Samba libraries) can do Kerberos, but their idea of where credentials live and which name to use for the server differs from the kernel client's. Several things must line up for a passwordless access: the client must have a valid ticket-granting ticket for the right realm; it must construct the service principal name from the name the user typed (not from an IP address, and not from a CNAME the server does not know); the server must hold a key for that principal; both clocks must agree within the skew; and, for a kernel mount, a helper must run in user space on the kernel's behalf and hand a security blob back. When one link fails, the usual symptom is a mount that asks for a password, falls back silently to NTLM, or fails with an error number that tells the administrator nothing.

This slice covers the two client paths: the user-space tools and the kernel `cifs` mount with `mount.cifs`, the upcall machinery in between, the options that choose security level and encryption, the multi-user mount that gives each person their own identity on a shared mount point, and the diagnosis of the common failures. The server side was covered with the Samba file server, and the domain membership and DNS foundations are in neighbouring topics.

## History and approaches

The early Linux SMB client, `smbfs`, spoke only NTLM-style password authentication using credentials supplied at mount time, and was removed from the kernel in the 3.x series after its maintainers stopped. The replacement, `cifs.ko`, began as Steve French's rewrite of the client for the CIFS dialect and gained SMB2 and SMB3 support from kernel 3.7 on. Initially, it too authenticated by password, either NTLMv2 or an unencrypted legacy mode that real-world administrators disabled. Kerberos arrived through a specific design: the kernel asks for a key from the kernel keyring subsystem, and the keyring's `request-key` mechanism runs a user-space program that builds the answer. The program for the SMB client is `cifs.upcall`, delivered with the `cifs-utils` package. The upcall receives the target host and the user identity, finds a ticket for the service `cifs/<host>` in the user's credential cache, optionally obtaining it from the KDC, and returns a SPNEGO blob that the kernel puts in its session-setup request. The manual page for the helper lists how it chooses the credential cache, the host name it asks for, and the keytab fallback [src: man-pages 4624dcc713614595].

Earlier or parallel approaches are worth knowing because they still turn up in estates. A `credentials=` file, with username, password and domain on three lines, mode 0600, is simple and common; it works for service accounts but it is a standing secret. Mounting through `pam_mount` at login time uses the typed password to mount for that session only, which works for password logins but not for single sign-on, where no password is ever typed. The Samba user-space tools had Kerberos earlier than the kernel, through GSSAPI, which allowed scripts to work with `smbclient -k` long before a mount would. The automounter combined with a keytab held by a service account gave unattended access for a machine, as in a backup server, and was often the first place that administrators discovered that the machine's cache expires after ten hours by default.

The failures of these approaches shaped the present design. Static password files leaked; mounts made by root exposed the share under root's identity to every local user, so a user who could read the directory could read what the file server believed only root could; and CNAME aliases used by administrators to make server names friendly broke Kerberos because the client asked for a ticket for the alias, which has no key on the server. The partial successes were the `multiuser` mount option (introduced with kernel 3.3), which presents a single mount point and creates a separate SMB session for each local user using that user's own credentials, and the integration of a central credential store (KCM in SSSD, or the kernel keyring) that kernel upcalls can find. The pattern that emerged: authenticate to the domain once, store the ticket where helpers can find it, let the kernel call a small trusted helper for each new session, and make the server authorise per-user.

## Current state

### The user-space tools

The Samba client tools take `-k` (older form) or `--use-kerberos=required` (the newer, more precise form, with `desired` and `off` as the alternatives) and then use whatever credential cache the Kerberos library finds. The sequence is `kinit alice@ACME.EXAMPLE`, then `klist` to see the ticket-granting ticket, and `smbclient -k //files.acme.example/projects -c 'ls'`. A successful session then appears in `klist` as a second ticket for `cifs/files.acme.example@ACME.EXAMPLE`; if it does not, the client authenticated by another mechanism. `smbget -k`, `rpcclient -k` and `net ads` subcommands use the same convention [src: samba-docs b7c00f537e76ee92] [src: samba-docs eb3181ca288d7f31]. The setting `client use kerberos = desired` in `smb.conf`, or in the dedicated `client.conf` file used by the libraries and the kernel helpers, changes the default for all tools. Because Kerberos is name-based, the client must be given a host name, not an address: `smbclient //10.0.0.20/projects -k` has no `cifs/10.0.0.20` principal to ask for and will fall back or fail.

### The kernel mount

A mount that uses Kerberos looks like this:

```bash
mount -t cifs //files.acme.example/projects /mnt/projects \
      -o sec=krb5,vers=3.1.1,cruid=1001,uid=1001,gid=1001,file_mode=0640,dir_mode=0750,seal
```

The options matter one by one, and the manual page for `mount.cifs` covers them in full [src: man-pages a8c83d4c0cc013ce] [src: man-pages 14bfe3de1a182020]:

- `sec=krb5` requests Kerberos authentication. `sec=krb5i` adds packet signing and `sec=ntlmsspi` is the password-based signed variant. In modern kernels the SMB3 signing and encryption negotiation is controlled by the dialect and by `seal`, so `krb5i` is mostly relevant to older dialects.
- `vers=3.1.1` pins the dialect. The default negotiation picks the highest mutually supported version, and the kernel's default minimum has been raised over time (the old SMB1 requires `vers=1.0` and is disabled by default in current kernels). Pinning helps to detect a server that downgraded.
- `cruid=<uid>` names the user whose credential cache the upcall should read. Without it, the upcall uses the uid that owns the mount, and for a root-initiated mount that is root, whose cache normally holds nothing. Newer kernels send a separate credential uid to the helper so the `uid=` mount option, which controls the file ownership, does not also select the cache.
- `uid=`, `gid=`, `file_mode`, `dir_mode` set the apparent ownership and mode, because without the Unix extensions the server's files have no meaningful Unix owner; `noperm` and `multiuser` change who enforces access.
- `seal` requests SMB3 encryption (AES in CCM mode for the earliest implementation of the option, with the server and dialect choosing GCM where available); it needs SMB 3.0 or later [src: man-pages a8c83d4c0cc013ce].
- `multiuser` creates a new SMB session for each local user who accesses the mount, using that user's own credentials. The kernel cannot prompt, so it works only with `sec=` values that require no password at that moment, such as `krb5`; each user must hold a ticket, or must have stored a password in the kernel keyring with `cifscreds add`. The option implies `noperm`, because the server now enforces access. A common pattern is to mount once as root with a machine keytab or a minimal "super-user" session for the mount itself and use `multiuser` for everyone who actually reads data.
- `actimeo=`, `cache=`, `nobrl`, `fsc`, `snapshot=` and handle options adjust caching, locking, local disk caching and previous-version access [src: man-pages 14bfe3de1a182020].

### The upcall chain

Three configuration pieces connect the kernel to Kerberos, and a missing one produces the typical mystery.

1. The `cifs-utils` package installs `/usr/sbin/cifs.upcall` and a request-key rule, usually in `/etc/request-key.d/cifs.spnego.conf` as a line of the form `create cifs.spnego * * /usr/sbin/cifs.upcall %k`, which the kernel's `request-key` mechanism consults when the cifs module asks for a key of type `cifs.spnego`. The sibling rule with key type `cifs.idmap` runs `cifs.idmap`, and is used for translating SIDs to uids when `cifsacl` is in play.
2. `/etc/krb5.conf` supplies the realm, the KDC discovery policy and the default credential cache. If it says `default_ccache_name = KEYRING:persistent:%{uid}` or `KCM:`, the helper finds the cache by the same rules as any Kerberos library. If it names a `FILE:` path, the helper reads the file as the target user; and for processes that were started with a special `KRB5CCNAME`, the helper normally probes the caller's environment (`--no-env-probe` turns that off).
3. A keytab on the client (`/etc/krb5.keytab`, from a domain join) lets the helper obtain tickets for the machine account when the user has none, so that a root mount in a boot-time `fstab` entry works unattended. The keytab path is adjustable with `--keytab` [src: man-pages 4624dcc713614595].

The helper builds the service principal from the host part of the UNC path. It does not use reverse DNS unless `--trust-dns` is given, a switch whose manual entry warns that it allows an attacker who controls DNS to make the client mount a different server [src: man-pages 4624dcc713614595]. The best practice is to use the server's canonical name, the one that matches its `cifs/` or `host/` service principal.

### Server names and principals

The server needs a key for `cifs/<name>`. On a Windows member server, the machine account carries `HOST/` principals that cover `cifs/`; adding a DNS alias needs extra service principal names registered on the machine account with `setspn -S cifs/alias.acme.example SERVER$` (a Microsoft troubleshooting article covers the CNAME case specifically) [src: ms-learn-adds 7079fdf410aff863]. On a Samba member, `net ads join` registers `host/` and `cifs/` principals; extra aliases are added in `smb.conf` with `additional dns hostnames` and by running `net ads dns register`, or by `net ads setspn add`. If the alias has no principal, the client's TGS request fails with `KRB5KDC_ERR_S_PRINCIPAL_UNKNOWN`, which tools surface as an access denied or silently downgrade to NTLM.

### Signing, encryption and client policy

The compliance rules that harden Linux clients ask for packet signing for both `smbclient` and `mount.cifs` [src: compliance-as-code 3a514eb06db353c6] [src: compliance-as-code 742daa68a363123b]. In `smb.conf` or `client.conf` the matching setting is `client signing = mandatory`, and `client smb encrypt = required` asks for encryption on all connections. The pairing with the server's `server signing` and `smb encrypt` settings decides whether the session comes up at all: a client that demands signing against a server that offers none fails with a protocol negotiation error such as `NT_STATUS_INVALID_NETWORK_RESPONSE` or `Protocol negotiation failed`, a message that community troubleshooting guides associate with a disagreement between minimum and maximum dialects on the two ends [src: archwiki 1ebe91298602954a].

### The generalised pattern

The structure is a kernel service that delegates authentication to a user-space helper, keyed by a credential cache that the user's login established. Elsewhere in Linux this is the same shape as the NFS RPCSEC_GSS upcall (`rpc.gssd`) and the `request-key` users such as `dns_resolver` and `nfsidmap`.

## Assessment: the good, the bad and the ugly

The good. When the plumbing is right, access is invisible to the user and strong: no stored secret, mutual authentication, tickets that expire and renew, and per-user identity on a shared mount. Auditing on the server shows real names. A fleet of Linux hosts joined to the domain gets this almost for free from the join (keytab, `krb5.conf`, SSSD cache). SMB3 encryption and signing add protection from other people on the network. `multiuser` makes one mount point per host behave correctly for many logged-in users, including through a terminal server.

The bad. The chain has many links, and each fails differently. Error reporting from the kernel is poor: a failed upcall shows up as `mount error(126): Required key not available` or `mount error(13): Permission denied`, and the real reason is in the helper's log (`cifs.upcall -d` writes to syslog or the journal) or in `klist`. Ticket lifetime is a recurring problem: tickets expire after ten hours by default, renewable for seven days, and a long-running service whose cache is a file that nobody renews finds its mount unusable the next morning; an existing session is not affected, but any new session, reconnect after a network blip or `multiuser` access by a new user needs a fresh ticket. The kernel client cannot refresh tickets itself. Automating renewal with `k5start`, `kinit -R` timers, SSSD's own renewal, or a systemd unit that uses a keytab for the service account is part of the job.

The ugly. Names. A DNS CNAME is the cause of more Kerberos failures than any other single thing: users type the friendly alias, the client requests a ticket for the alias, the KDC has no such principal, and the client falls back to NTLM (which works until the domain turns NTLM off, at which point a mount that worked for years stops). A second ugly is the identity shown in `ls -l`: unless the server supports the SMB3 Unix extensions, the Linux side invents ownership, so `ls -l` is cosmetic, and `chown` or `chmod` on the mount either fail or change nothing on the server. The `cifsacl` option, with `getcifsacl` and `setcifsacl`, shows the real descriptor and translates SIDs through the `cifs.idmap` upcall, but it needs the winbind or SSSD plug-in on the client to work. A third ugly is timing and caching: attribute caching (`actimeo`, default one second for attributes) and leases can show stale metadata, and a mount over a slow WAN link with `cache=strict` and short timeouts floods the server with metadata requests. Finally, the NTLM fallback hides misconfiguration: a mount that works with `sec=ntlmssp` only proves the password is right, not that Kerberos is set up, so tests should use `sec=krb5` explicitly and read `klist` afterwards.

## Applications beyond this domain

Every protocol that wants sign-on with no stored secret ends up in the same place. NFSv4 with RPCSEC_GSS does the same dance with `rpc.gssd` and keyring-style upcalls (the next topic in this course). PostgreSQL, Kafka, Hadoop, HTTP with SPNEGO (mod_auth_gssapi, curl `--negotiate`), SSH with `GSSAPIAuthentication` and LDAP SASL/GSSAPI all use service principals, keytabs and credential caches, and they share the failure modes of name mismatch, clock skew and expired tickets. The multi-user idea, one mount shared by many principals with the server doing the checks, appears in container storage drivers and in NFS with `sec=krb5` as well. The kernel-to-user-space upcall pattern also appears in DNS resolution for kernel mounts and in the user-mode helper that loads firmware.

## Examples

Worked example 1, an interactive user. Alice logs into a joined Linux desktop with her domain password; SSSD stores the ticket in the KCM cache. She runs `smbclient --use-kerberos=required //files.acme.example/projects -c 'ls'` and it works. She then mounts a share on demand with a user-level helper, or her administrator provides an `fstab` entry with `noauto,user,sec=krb5,cruid=%U`, `multiuser`, and `x-systemd.automount`. Accessing the path triggers the mount; `klist` now shows the service ticket for the file server.

Worked example 2, an unattended service. A nightly job on an app server reads a drop folder. The administrator creates a service account `svc-batch` in AD, exports a keytab with `ktutil` or `msktutil` (or uses `net ads keytab`), and runs the job from a systemd unit whose `ExecStartPre` is `kinit -k -t /etc/batch.keytab svc-batch@ACME.EXAMPLE`. The mount uses `sec=krb5,cruid=<uid of svc-batch>`. The keytab file is mode 0600 and owned by the service user, and a monitoring job checks `klist -s` and alerts on failure. The key for the keytab is rotated when the account password changes, which the runbook records.

Worked example 3, the failing one: the alias. A migration team publishes `\\files\` as a CNAME for a new Samba member `fs07.acme.example`. A Linux client mounts `//files/projects` with `sec=krb5`. The mount returns `Required key not available`. The checks: `klist` shows only the TGT; `cifs.upcall` debug output shows a request for `cifs/files.acme.example@ACME.EXAMPLE` and `Server not found in Kerberos database`. The fix is not to trust DNS (`--trust-dns`), which would be a weakened design, but to register the alias as a service principal on the file server (`net ads setspn add cifs/files.acme.example` or `setspn -S` on Windows), or to ask clients to use the canonical name. After the fix, `kdestroy`, `kinit` and a new mount succeed.

Worked example 4, the failing one: the cache. A cron job mounts and copies files on the first of every month and starts failing on the second day of the month it is deployed. The job runs as root with `cruid` of a user whose cache is `FILE:/tmp/krb5cc_1001` populated by a login that ended long ago. The ticket expired. The cure is a dedicated keytab-driven credential for the job and an explicit `KRB5CCNAME` created by the job's own `kinit -k` call, not a leftover cache.

## Related problems and ideas

The neighbouring problem on Linux is the same file share with a different client stack: GNOME's GVfs and KDE's KIO open SMB locations in user space through libsmbclient, taking the user's Kerberos cache without any kernel helper; this is often the path for desktops and avoids all the upcall questions. Another approach is to avoid a share mount altogether and have applications fetch via a gateway, an object API, or a sync client, which sidesteps SMB at the cost of more moving parts. NFSv4 with Kerberos offers the same single sign-on with POSIX semantics. A distinct idea is to stop using passwords at logon entirely with smart cards or passkeys, where Kerberos is bootstrapped by PKINIT (certificate) and the file-sharing layer is unchanged. Proposals that have not become mainstream include moving SMB authentication into the kernel with a loadable security module, and SMB over QUIC with TLS client certificates, in which the Windows side already supports certificate-based access that does not use Kerberos at all for the remote-user case (to verify client support in Linux) [web: learn.microsoft.com].

## Active research

The cifs client is under active development by its maintainers, with work reported in the kernel changelogs and at Samba and storage conferences: SMB3 POSIX extensions that carry Unix ownership and modes, compression of SMB3 traffic, better handling of reconnects with persistent handles, QUIC transport, and cleaner security upcalls. A recurring discussion is how to retire the keyring-based upcall in favour of a direct user-space daemon interface, since the existing design is inflexible in containers and in user namespaces. Questions that remain open are how to authenticate in a container that has no access to the host's credential caches, how to give non-domain clients a Kerberos-like identity when Microsoft's planned local KDC and IAKerb features arrive, and how to retire NTLM on the client without breaking appliances that have nothing else (to verify the timeline in the vendor's notices) [web: learn.microsoft.com].

## Future direction

Expect NTLM fallback to shrink. Microsoft has announced a staged plan to restrict NTLM in Windows and to make Kerberos work in more situations (for example when no domain controller is reachable), and Windows Server 2025 and recent Windows 11 raise signing requirements by default; Linux clients that relied on NTLM fallback or on unsigned sessions may start failing after server upgrades, so test against an upgraded server before the rollout, not after (exact schedule to verify) [web: learn.microsoft.com]. Meanwhile the Linux side moves toward the POSIX extension for SMB3, which makes ownership and modes real again, and toward modern ciphers such as AES-GCM and AES-256 variants. The practical advice stays constant: use canonical names, set `sec=krb5` explicitly, check `klist` and the helper's log first, give unattended jobs their own keytab-backed identity, and plan for ticket renewal as part of every deployment.
