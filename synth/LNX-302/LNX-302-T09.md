# Authenticated Unix file sharing: NFSv4 with Kerberos

## Define the problem

NFS was designed in the 1980s for a network of trusted workstations. In its classic form (the `AUTH_SYS` flavour), the client simply reports the uid and gids of whichever process is calling, and the server believes it. That is acceptable only if every machine that can reach the server is administered by people you trust, and if nobody on the network can forge a packet: root on any host that mounts the export can claim to be any user, and a laptop plugged into the right segment can claim to be anyone at all. Authorisation is therefore only as good as the least trustworthy client, and the identity model assumes that uid 1001 means the same person on every machine, an assumption that holds only when someone has kept numeric ids synchronised by hand or by directory.

The gap this topic fills is how to give NFS a real notion of "who is calling" without giving up its design as a POSIX network file system. In a mixed environment the question is sharper, because the directory that knows the people is usually Active Directory, whose key distribution centre (KDC) can issue Kerberos tickets for any service principal, including `nfs/server.example.com`. If the NFS server and clients can trust the AD KDC, a user who logged in once can access NFS exports without a password, the server learns the caller's principal rather than a number, and the traffic can be signed or encrypted. Failure shows up as mounts that hang at boot because the client has no credentials, files owned by `nobody` because the name-to-id mapping fails, sessions that stop working after ten hours when tickets expire, or clients that cannot connect because they and the server disagree about the security flavour or the encryption types the directory allows.

This slice covers NFS version 4 with the RPCSEC_GSS security flavours `krb5`, `krb5i` and `krb5p`, the services and keytabs they need on server and client, id mapping between principals and local users, configuration of exports and mounts, and typical failures. The previous topics covered the SMB side of the same estate; the choice between SMB and NFS is treated under related problems.

## History and approaches

Sun's NFS protocol (1984) had no authentication beyond the client's word. NFSv2 and v3 relied on separate auxiliary protocols (mount, lock manager, status monitor), each on its own dynamic port, and the whole family was a favourite of attackers: the mount daemon would hand out a file handle to anyone, file handles could be guessed on some servers, and firewalls struggled with the port dance. Sun added secure RPC with DES-based authentication (`AUTH_DES`, later `AUTH_KERB` in Kerberos-4 variants) but it was weak and badly deployed. The real fix was RPCSEC_GSS (RFC 2203, 1997), which layers the Generic Security Services API under ONC RPC. A service can then use any GSS mechanism (Kerberos 5 in practice) and ask for one of three protection levels per connection: authentication only (`krb5`), integrity protection of each call (`krb5i`), or full privacy by encryption (`krb5p`).

NFSv4 (RFC 3010 in 2000, revised as RFC 3530, then RFC 7530 for 4.0; 4.1 in RFC 5661 with parallel NFS and sessions; 4.2 in RFC 7862 with server-side copy, sparse files and labelled NFS) was designed with this in mind. It folds mount, locking and status into the main protocol on a single well-known TCP port, 2049, makes strong security mandatory to implement (though not mandatory to use), replaces numeric ids on the wire with strings of the form `user@domain`, introduces NFSv4 ACLs modelled on Windows rather than POSIX draft ACLs, and uses compound operations and stateful opens and delegations. On Linux, the supporting pieces arrived over several years: `rpc.gssd` as the client daemon that establishes GSS contexts on behalf of the kernel, `rpc.svcgssd` on the server (later replaced by `gssproxy`, and in current nfs-utils no longer a separate service), `rpc.idmapd` for the id mapping, then `nfsidmap` as a request-key upcall helper for the client. The Linux server learned to export with `sec=` flavours in `/etc/exports`, and the client learned `sec=krb5p` mount options [src: rhel-10-docs d65183c860c63966].

The approaches that came before or alongside are worth naming because they turn up in legacy networks. NIS (Yellow Pages) synchronised accounts and ids but offered no authentication of the NFS traffic. LDAP plus `pam_ldap` solved the id synchronisation. Firewalling and host-based export restrictions (`/etc/exports` with host lists and `root_squash`) reduced the exposure without removing it. Tunnelling NFS over SSH or IPsec protected the wire but not identity. AFS, with its own Kerberos-based model and global namespace, offered a stronger design that never became mainstream on Linux. The partial successes were `root_squash` (mapping remote root to `nobody`, still the default) and VPN-wrapped NFS; the failures were any scheme that depended on all clients being honest. The emerging pattern: authenticate with Kerberos, name people by principal, map names to local ids at the edge, and choose integrity or privacy by the sensitivity of the data.

## Current state

### Components

An NFSv4 Kerberos deployment has the following parts, each of which must be right:

- **A KDC** that knows both machines and users. In a mixed estate this is the AD domain, and the NFS server and clients are domain members, or at least have principals in the realm. A MIT or Heimdal KDC (FreeIPA) works the same way.
- **Server identity.** The server needs a service principal `nfs/nfs01.example.com@REALM` in `/etc/krb5.keytab`. Clients and server must agree on the canonical name; a DNS alias without its own principal fails as it does for SMB.
- **Client machine identity.** Each client needs a `host/client.example.com@REALM` principal in its keytab. It is used when the kernel needs credentials and no user ticket is available, notably to mount at boot before anyone logs in, and for some NFSv4.0 and 4.1 housekeeping operations; the Arch documentation notes that the machine principal is no longer mandatory for NFS 4.2 and that `host/` suffices, with no `nfs/` principal needed on a pure client [src: archwiki 0febf93d8e0a77b7].
- **Daemons.** On the client, `rpc-gssd.service` (started automatically when a keytab exists, as the vendor documentation notes) establishes security contexts for the kernel; `nfsidmap` handles id upcalls [src: rhel-10-docs d65183c860c63966]. On the server, `nfs-server.service`, `nfs-mountd` (the 4.x server still uses mountd for export management) and `gssproxy` for context handling. Recent nfs-utils also read `/etc/nfs.conf` for tuning, and an `exportd` daemon appears as the newer way to manage exports [src: man-pages dd22f2cf92e43b88].
- **ID mapping.** Names on the wire are `alice@example.com`; both ends map them to local users through NSS. The mapping domain defaults to the DNS domain and can be set in `/etc/idmapd.conf` (`Domain =`), and a `_nfsv4idmapdomain` TXT record can publish it; the manual pages describe the lookup order and the fact that recent clients use `nfsidmap` rather than the `rpc.idmapd` daemon [src: man-pages d25d4baf62098086] [src: man-pages 4e201d3ef2e200f8]. If the names fail to map, files show owner `nobody`.

### Setting up in an AD realm

For an AD KDC, the machine account of the NFS server is created by the domain join (`realm join`, `net ads join`, or `adcli join`) and its keytab is written during the join; `net ads keytab add nfs` (Samba tools) or `adcli`'s keytab update adds `nfs/` principals to the keytab and registers the SPN on the machine account. Older recipes generated keytabs for user accounts with `ktpass` on Windows, whose historical quirks (principal mapping, encryption type flags) are documented in community wiki pages on generating keytabs that AD accepts [src: archwiki 10db9aa9d3046743]. AD's encryption type policy matters: modern domain controllers prefer AES (`aes256-cts-hmac-sha1-96`, `aes128-cts-hmac-sha1-96`), and RC4 is being phased out, so keytabs must contain AES keys (`klist -ke` lists them), and `krb5.conf` should not restrict to `des` or `rc4` types.

The user mapping needs a source of Unix uids for AD users, which is the same decision as in the winbind and SSSD topic: SSSD with `ldap_id_mapping` or POSIX attributes, or winbind. Because the NFS server and clients need to agree about what `alice@example.com` maps to, they should use the same identity source, and the idmap should produce the same uid on all hosts (algorithmic mapping with identical ranges, or `uidNumber` from the directory).

On the server, an export looks like this:

```text
/srv/export/projects   *.example.com(rw,sync,sec=krb5p,no_subtree_check)
/srv/export/public     *.example.com(ro,sync,sec=krb5:krb5i:krb5p)
```

`sec=` lists the allowed flavours in preference order, separated by colons. `exportfs -rav` re-reads the file; `exportfs -v` shows what is active. In NFSv4 the clients mount paths relative to the server's pseudo-root: with modern servers, any export path is directly mountable (the `fsid=0` convention is no longer required, though it is still seen). Firewalling is easy: TCP 2049 only, for NFSv4, plus 111 only if v3 is allowed. The server should also reject v3 if it is not needed (`vers3=n` in `/etc/nfs.conf`), because NFSv3 with Kerberos does not cover the auxiliary protocols and leaves a weaker path [src: archwiki ab09ae29f342b109].

On the client:

```bash
mount -t nfs4 -o sec=krb5p,vers=4.2 nfs01.example.com:/srv/export/projects /mnt/projects
```

or the matching `fstab` line with `_netdev,x-systemd.automount`. The mount itself uses the machine credentials (root's access uses the machine's principal, which the Arch notes remind us), and every other user needs their own ticket: either from a login that obtained one (SSSD, `pam_krb5`), or from `kinit`; renewal by a tool such as `k5start` or SSSD is necessary because tickets last hours [src: archwiki 0febf93d8e0a77b7]. Choosing `sec=krb5p` explicitly makes the negotiation deterministic; the client otherwise takes the strongest flavour the server offers. The vendor list of mount options covers the performance and behaviour settings that combine with security options (`nfsvers`, `timeo`, `retrans`, `nosuid`, `noexec`, `lookupcache`) [src: rhel-10-docs e3954f90f8ff9db6].

### What each flavour protects

`krb5` authenticates the user for the session but sends data in the clear, so it identifies the caller and nothing more. `krb5i` adds a cryptographic checksum on every request and reply, defeating modification in transit. `krb5p` encrypts the payload, at a measurable CPU cost, which matters for large sequential transfers (throughput commonly falls by tens of percent on hardware without AES acceleration, to verify per platform). Newer kernels also support TLS for NFS via RPC-with-TLS (RFC 9289, `xprtsec=tls` in the mount options, with the `tlshd` daemon from `ktls-utils`), which encrypts the transport independent of the GSS flavour, though user authentication still uses `sec=`.

### ACLs and permissions

NFSv4 ACLs are managed with `nfs4_getfacl` and `nfs4_setfacl` from the `nfs4-acl-tools` package, and map imperfectly to POSIX ACLs on the server filesystem (ext4 and XFS store POSIX ACLs and the server translates, with some entries not representable). If the data is accessed from Windows by SMB at the same time, the better approach is a single filesystem exported through one protocol, or a filesystem with native NFSv4/NT-style ACL support, since double-protocol access to a POSIX filesystem leads to the permission mismatches described in the file server topic.

### The generalised pattern

The shape is again: a service that wraps its protocol in a GSS security layer, a keytab for the service, a keytab for the machine client, per-user credential caches, an id-mapping bridge between principal names and local numbers, and a policy of strength per resource. The same shape applies to Kerberised HTTP, databases and message brokers.

## Assessment: the good, the bad and the ugly

The good. It works and it is standard. A properly set-up estate gives per-user identity on a POSIX filesystem, single sign-on through the user's login ticket, optional encryption, no need for synchronised numeric ids when names map through a directory, a single firewall port, and the compatibility of NFSv4 with the broad range of Linux, BSD and commercial storage servers. Kerberos tickets expire and can be revoked by disabling the account, which is a far better offboarding story than `AUTH_SYS`. The pain of the old auxiliary protocols is gone.

The bad. The prerequisites are many and each fails differently: DNS names, reverse lookups, time, keytabs, encryption types, SPNs, id mapping, daemons, firewalls and `fstab` ordering. The error messages are poor: a failed GSS context shows as `mount.nfs: access denied by server while mounting`, `Permission denied`, or in the logs of `rpc.gssd -vvv` as `No credentials cache found`, `Key table entry not found` or `Server not found in Kerberos database` [src: archwiki 0e520093ce00924f]. User tickets expire; a long-running job loses access in the middle of the night unless renewal is arranged. Automounting and `systemd` interplay: a mount unit that starts before the network or before `rpc-gssd` hangs, and a mount at boot as root works while a user-level access works only after a ticket exists. Performance cost with `krb5p` is real.

The ugly. Identity mapping again: if the client and server resolve `alice@example.com` to different uids, access works but ownership is wrong; if the names fail to resolve at all, everything becomes `nobody`, and NFSv4 clients that cache the failure (the kernel keyring cache in `nfsidmap`) keep it until cleared with `nfsidmap -c` [src: man-pages 4e201d3ef2e200f8]. A second ugly is that NFSv4's id-mapping domain, the DNS domain by default, often differs from the Kerberos realm in an AD estate where the realm is upper-case and the DNS domain is a subdomain; the setting in `idmapd.conf` needs care. A third is the Windows side: Windows can be an NFS client or server (Services for NFS), but its default identity mapping uses a different mechanism (user name mapping), and an AD domain with SFU or RFC2307 attributes is usually required for sensible results. Finally, the old, wide-spread habit of `no_root_squash` on an exported home directory, combined with Kerberos, is a trap: the machine principal for root gets access to everything, so a compromised client with a keytab is a compromised export.

## Applications beyond this domain

RPCSEC_GSS and the idea of a GSS-wrapped, per-connection protection level show up in other protocols: SASL/GSSAPI for LDAP, SMTP and IMAP; the GSSAPI mechanism in SSH; HTTP Negotiate; PostgreSQL's `gss` authentication; Hadoop's secure mode; and Kafka's SASL_GSSAPI. In each, the three practical questions are the same: where is the service key, what is the client's identity source, and how are tickets renewed for a long-running process. The machine-credentials-plus-user-credentials arrangement for a mount is a template for other systems that need a service to act before any user has logged in (systemd units using keytabs, `k5start` daemons, Kubernetes CSI drivers for NFS with Kerberos). The id-mapping bridge is the same problem container user namespaces and cloud identity solve.

## Examples

Worked example 1, a minimal working Kerberised export on a RHEL-family pair in an AD realm. Both hosts are domain members (`realm join`). On the server: `net ads keytab add nfs -U svc-join` (or the equivalent `adcli` step) so the keytab holds `nfs/nfs01.example.com`; `klist -ke` shows AES keys. `/etc/exports` has the `sec=krb5p` line; `systemctl enable --now nfs-server`; `exportfs -v` confirms; `firewall-cmd --add-service=nfs --permanent` opens 2049. On the client: `systemctl status rpc-gssd` (running), `kinit alice`, `mount -t nfs4 -o sec=krb5p nfs01.example.com:/srv/export/projects /mnt/p`, `ls -l /mnt/p` shows `alice` as the owner of her files, and `nfsstat -m` displays the negotiated flavour in the options.

Worked example 2, a failing one: owner `nobody`. Files appear as `nobody nobody` although `kinit` succeeded. The `idmapd` domain on the server is `example.com` and the client's DNS domain is `corp.example.com`, so the name strings do not match. The fix is a common `Domain = example.com` in `/etc/idmapd.conf` on both, followed by `nfsidmap -c` on the client to clear the cached failures, or the `_nfsv4idmapdomain` TXT record to publish one value for the whole estate. A check with `nfsidmap -l` lists the cached keys.

Worked example 3, a failing one: the boot-time hang. A client mounts the share from `fstab` with `sec=krb5p`; at boot the system waits two minutes at the mount and continues without it. The logs show `rpc.gssd` unable to find credentials: the client lacks a `host/` principal in its keytab because it was cloned from an image joined before cloning. Re-joining the clone (`realm leave`, `realm join`) gives the machine its own account and keytab; adding `_netdev,x-systemd.automount,x-systemd.mount-timeout=30` keeps a missing server from blocking boot.

Worked example 4, a failing one: after ten hours. A nightly batch run under a user account reads a Kerberised NFS directory; it works for the first night and fails on the second. The user's ticket was obtained at login and has expired. Remedy: a service account with a keytab and a systemd unit that runs `kinit -k -t` before the job (or `k5start -b -K 60`), and a monitoring check on `klist -s`.

## Related problems and ideas

The most obvious alternative is SMB 3 with Kerberos, which this course covers on the other side: it offers Windows-native ACLs and clients but weaker POSIX semantics on Linux, unless the SMB3 POSIX extensions are used. For cluster workloads, parallel file systems (Lustre, GPFS, CephFS) use their own authentication or Kerberos variants, and Ceph's NFS gateway (NFS-Ganesha) exports CephFS with Kerberos. For containers, CSI drivers mount NFS on the node and rely on node-level credentials, which loses per-user identity entirely, so many container platforms use per-namespace exports with network restrictions. Other ideas include running NFS over TLS (`xprtsec`), which protects the wire without Kerberos for environments where only machine-level trust is needed, and NFS with labelled security (SELinux labels on NFSv4.2), which carries mandatory access control labels across the network. S3-compatible object storage and sync clients avoid the file-protocol question for some workloads.

## Active research

The Linux NFS project and kernel developers work on several fronts: RPC-with-TLS for transport security and the userspace helper `tlshd`; improvements to the NFS server's scalability (nfsd threads, the new netlink-based configuration interface that replaces `/proc` writes); session trunking and multipathing; the in-kernel handling of Kerberos contexts and key renewals; and the removal of legacy components (NFSv2 support is gone, and NFSv3 is under discussion for deprecation on servers). IETF work extends the protocol with newer pNFS layout types and with security considerations such as post-quantum readiness of the GSS layer. Open questions include how to make per-user Kerberos tickets work smoothly in containers and for non-interactive workloads, and how to simplify the chain of principals, keytabs, idmap and daemons into something an installer can set up unattended (to verify the status of specific kernel features against the release notes in use).

## Future direction

Expect the ease of setup to improve and the weak options to be removed: servers that refuse NFSv3 and `AUTH_SYS` by default, transport TLS becoming the baseline and `krb5p` kept for user-level confidentiality where required, and AD-integrated setups guided by `realm` and `ipa` tooling that create the principals automatically. Expect Kerberos in AD to lose RC4, so every keytab and client must hold AES keys, and expect the change in NTLM policy to push Windows and Linux file access further toward Kerberos on both protocols [web: learn.microsoft.com]. For an administrator, the stable practices are to standardise names and id sources first, test with a single client and `rpc.gssd -vvv` before scaling, set `sec=` explicitly on exports and mounts, automate the keytab lifecycle, monitor ticket and keytab age, and decide per data class whether `krb5i` or `krb5p` is required.
