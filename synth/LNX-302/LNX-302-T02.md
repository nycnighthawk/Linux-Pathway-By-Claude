# Joining Linux to Active Directory: winbind or SSSD

## Define the problem

A Linux server that stores or serves company data needs to know who the people in the Active Directory forest are. When `alice@ACME.EXAMPLE` opens an SSH session, or connects to a Samba share on this host, three separate questions must be answered. Is she who she says she is (authentication)? Which local uid, gid and group list does she get (identity)? And may she do the thing she asks (authorisation)? On Windows these questions are answered by the domain machinery, in which the machine itself holds an account in the directory, a machine password and a set of Kerberos keys. A Linux host has none of it until an administrator makes it a domain member.

The gap is that Unix and Windows disagree about what a user is. Unix identifies a user by a 32-bit integer and finds it through the Name Service Switch (`nsswitch.conf`) and the PAM stack. AD identifies principals by a security identifier (SID), a structured value of the form domain-prefix plus a relative identifier (RID), and authenticates mostly by Kerberos with NTLM as a legacy fallback. Something has to turn SIDs into uids (and back), cache answers so that a login does not need a network round trip, keep the machine account's password rotated, and do so while the directory is the sole source of truth. Failure modes are familiar: users who can log into Windows but not the Linux host; files whose owner shows as a number after a re-join; logins that work from the console and fail over SSH; a service that worked until the machine password lapsed or the clock drifted; the same person receiving different uids on two hosts and thus unreadable NFS data.

This slice covers the two supported ways a Linux host joins AD: Samba's `winbindd` with `net ads join`, and SSSD with `realmd` and the AD provider (`adcli` underneath). It covers the uid mapping choices that decide whether two hosts agree, and how to pick between the approaches. The file-serving side was covered in the Samba topic, and Kerberos on clients comes later.

## History and approaches

Before AD, a Unix box in an NT4 domain either ignored the domain or used the Samba `winbindd` daemon, introduced during the Samba 2.2 series by Tim Potter and colleagues, to resolve domain accounts through the NT domain RPC calls. When Windows 2000 replaced the NT4 domains with AD, the first generation of integration was a patchwork: PAM `pam_krb5` for authentication against the KDC; `nss_ldap` and `pam_ldap` from PADL to read the directory through LDAP; and the Services for UNIX (later "Identity Management for UNIX") schema extension, which added `uidNumber`, `gidNumber` and `loginShell` attributes to the directory so that LDAP could answer NSS queries. It worked, but each piece had its own configuration, DNS and Kerberos setup, and no piece managed the machine account. Passwords drifted, the LDAP connections were unauthenticated or used a fixed bind account, and the caching story was an `nscd` daemon that had never been designed for offline use.

Two projects emerged to fix this. Samba's winbind grew into a full domain member client: `net ads join` creates the machine account and writes the secrets database; `winbindd` talks to a domain controller using RPC and Kerberos, generates uids on demand through its `idmap` back-ends (`tdb`, `rid`, `ad`, `autorid`), and supplies the NSS and PAM modules `libnss_winbind` and `pam_winbind` [src: samba-docs 0d438cb1421361e3]. The other project, SSSD (System Security Services Daemon), began in Red Hat's FreeIPA effort around 2008, and was written to be a single daemon with a cache that offers offline login, with modular providers for LDAP, Kerberos, IPA and AD. Its AD provider (introduced with SSSD 1.9) either reads POSIX attributes from the directory or maps SIDs to uids by an algorithm, and `realmd` (2012) gave administrators a one-line `realm join` that discovers the domain, installs packages and writes `sssd.conf`.

The partial successes and failures taught several lessons. Using LDAP with POSIX attributes gave stable uids but demanded that someone populate `uidNumber` for every user, which turned the directory into a provisioning chore. Algorithmic mapping removed the chore but made uids a function of the SID, which differs for the same user if the domain is rebuilt. The `idmap_tdb` back-end allocated uids first come, first served from a local database, which meant two hosts disagreed; it remains acceptable only for a single server where files are never shared. The fact that these histories left debris in production is why identity-mapping decisions are described as one-way doors. The pattern that emerged is: join the host as a machine account, ask a local caching daemon to translate between SIDs and Unix ids, route NSS and PAM through that daemon, and choose the mapping algorithm once, on purpose, for the whole estate.

## Current state

### What a join does

Every approach starts the same way. DNS must locate the domain (SRV records such as `_ldap._tcp.dc._msdcs.<domain>`), time must agree within the Kerberos skew of five minutes, and the Kerberos client library needs a realm configuration, either explicit or discovered. The join then creates a computer object in the directory, sets its password, and records Kerberos keys in `/etc/krb5.keytab` (SSSD route, via `adcli`) or in the Samba secrets database `/var/lib/samba/private/secrets.tdb` (winbind route; `net ads keytab create` can also export a keytab). The vendor procedures for the Samba route list the packages, the `smb.conf` parameters and the join command in order, and they also show how to join through the realmd tool using Samba as the membership software [src: rhel-10-docs 659714f4b344de87]. Community guides show the same joining flow with Rocky Linux [src: rocky-docs 1df1064a4ac8c009].

### Winbind

The `smb.conf` of a winbind member sets `security = ads`, the NetBIOS `workgroup`, the Kerberos `realm`, and one `idmap config` stanza per domain. A typical pair for a single-domain estate with POSIX attributes in the directory reads:

```ini
[global]
    security = ads
    workgroup = ACME
    realm = ACME.EXAMPLE
    kerberos method = system keytab
    idmap config * : range = 3000-7999
    idmap config * : backend = tdb
    idmap config ACME : backend = ad
    idmap config ACME : schema_mode = rfc2307
    idmap config ACME : range = 10000-999999
    template homedir = /home/%U
    winbind use default domain = yes
    template shell = /bin/bash
    winbind refresh tickets = yes
```

The default domain `*` needs a writable back-end (`tdb`) for local and well-known SIDs such as `BUILTIN\Users`, while the real domain gets its own non-overlapping range. The idmap back-ends have distinct behaviours, documented in the `idmap_*` manual pages and the Red Hat procedures: `ad` reads `uidNumber` and `gidNumber` from the directory and fails for accounts that lack them; `rid` computes the id as the range base plus the RID, needs no directory attributes and gives the same answer on every host with the same `range`, but only for one domain per range and it cannot express a custom uid; `autorid` carves per-domain slices out of a big pool automatically, and it is the pick for multi-domain forests without POSIX data; `tdb` and `tdb2` allocate on first sight and are host-local; `idmap_ad` options are in its manual page [src: samba-docs cc15ba25e0ed3ecf] [src: rhel-10-docs 517384542632baf2]. PAM and NSS are wired up by `authselect select winbind with-mkhomedir` on RHEL-family systems, or `pam-auth-update` and the `libnss-winbind` package on Debian; `nsswitch.conf` gains `winbind` on the `passwd` and `group` lines [src: man-pages 334e14752c36746e].

Operational tools: `wbinfo -t` checks the trust secret with the domain controller, `wbinfo -u` and `wbinfo -g` list users and groups, `wbinfo -n alice` converts a name to a SID and `wbinfo -S` a SID to a uid; `wbinfo --ping-dc` and `wbinfo -a user%pass` test authentication [src: samba-docs 868c0e539ce21f70]. `net ads testjoin` and `net ads info` verify membership. `ntlm_auth` offers authentication to helper programs such as FreeRADIUS or Squid [src: samba-docs b9212bbc65b5f487]. `pam_winbind` has options (`krb5_auth`, `krb5_ccache_type`, `require_membership_of`, `mkhomedir`) that control whether a login obtains a Kerberos ticket and caches it [src: samba-docs 419bef2c71c4c720]. The daemon keeps its caches in `/var/lib/samba/*.tdb`; `net cache flush` clears the persistent cache and a restart clears the memory cache.

### SSSD

SSSD's configuration is in `/etc/sssd/sssd.conf`, readable only by root (mode 0600; the service refuses to start otherwise). Domain stanzas select `id_provider = ad`, `access_provider = ad` (or `simple` or `ad` with GPO), and whether to use `ldap_id_mapping = True` (the algorithmic mapping, default) or `False` (read POSIX attributes). The algorithmic mapping uses the domain SID hashed into one of many 200,000-id slices inside `ldap_idmap_range_min` and `ldap_idmap_range_max`; every SSSD host with the same defaults yields the same uids, which is the property that makes it attractive; changing the range or having two forests collide is the property that makes it risky. The other settings that matter: `use_fully_qualified_names`, `fallback_homedir = /home/%u@%d`, `default_shell`, `ad_gpo_access_control` (Group Policy-based logon rights, default enforcing in recent versions), `krb5_store_password_if_offline`, and `cache_credentials` for offline login. `realm join -U Administrator acme.example` does discovery, package selection and `sssd.conf` generation; `realm list`, `realm permit`, `realm deny` and `realm leave` manage login permission and membership. `sssctl domain-status`, `sssctl user-checks alice`, `getent passwd alice@acme.example` and `id alice@acme.example` are the first diagnostic steps; `sss_cache -E` invalidates cached entries; `journalctl -u sssd` and the logs under `/var/log/sssd` (with `debug_level = 6` per section) give detail.

The same join can also serve a Samba file server on the same machine. The documented arrangement is SSSD for identity and login, plus Samba's `security = ads` with `idmap config ... : backend = sss`, so that `smbd` asks SSSD for uids instead of running its own winbind idmap. That avoids two different uid assignments on one host, while still letting Samba hold its own machine keytab. The Red Hat guides present SSSD or winbind as the choice when Samba needs to join, and describe the IdM variant that uses FreeIPA with a trust to AD [src: rhel-10-docs e50dabd6b7d7f30e] [src: rhel-10-docs 7f48e44c117ffbb9].

### The generalised pattern

All variants share the same layering: a machine credential, a translating cache daemon, NSS and PAM clients, and a policy decision about id generation. The choice matrix is short:

- Pure Linux logins and no Samba file serving: SSSD, because it is the default in the major distributions, offers offline caching, GPO-based access control and fewer moving parts.
- A Samba file server that must serve Windows ACLs against domain users: winbind (or SSSD with the `sss` idmap back-end), joined with `net ads join`.
- A forest with several domains and no POSIX attributes: `autorid` (winbind) or SSSD's algorithmic mapping, accepting that uids are tied to the SID.
- An estate where uids must be stable across the rebuild of a domain, or with NFS data that predates AD: POSIX attributes in the directory (`rfc2307` schema), read by `idmap_ad` or `ldap_id_mapping = False`.

## Assessment: the good, the bad and the ugly

The good. Both stacks work, in production, at scale. A join takes minutes; domain users log in with their AD password and Kerberos tickets arrive automatically, enabling single sign-on to NFS, Samba and web services. The cache makes login tolerant of a DC outage. SSSD adds Group Policy-based access control and smart-card and certificate mapping; winbind provides the NTLM pass-through helper used by older proxy and RADIUS software. Because both read the same directory, the directory team keeps one place for joiners and leavers.

The bad. Two parallel systems exist, with different configuration languages, caches and failure modes. Documentation for each tends to point at the other tool whenever a feature is missing: winbind has no offline authentication cache comparable to SSSD, SSSD cannot perform some Samba-specific domain actions. Changing back-end after go-live changes uids and orphans file ownership, as every administrator learns once. The `idmap config` ranges are also permanent: ranges cannot overlap, and a range that is too small is discovered only when the pool runs dry. DNS is a persistent weak point: a host whose resolver does not know the domain's SRV records can fail with errors that read like Kerberos problems. SELinux and the file permission of `sssd.conf` produce quiet failures, and the PAM stack must be edited with `authselect`, not by hand, or the next package update rewrites it.

The ugly. Silent drift. The machine account password changes by default every 30 days (`machine password timeout` for Samba, `adcli`'s renewal handled by SSSD's `ad_maximum_machine_account_password_age`); a host that is powered off or cloned from an image keeps an old password and falls out of the domain with an authentication error that appears only at the next login. VM templates joined before cloning duplicate a machine identity (the clones fight over the same account), so the join belongs in first-boot automation. A DC that is demoted or replaced can leave winbind pinned to an address it no longer answers on. Clock skew beyond five minutes breaks Kerberos, and fallback to NTLM masks the breakage until NTLM is restricted. Finally, the policy side is moving: Microsoft has stated its intent to restrict NTLM and to tighten channel-binding and LDAP signing defaults on domain controllers, so a member that depends on simple LDAP binds or unsigned traffic should be upgraded before the DC change reaches it (see the Windows Server hardening notes, to verify specifics per version) [web: learn.microsoft.com].

## Applications beyond this domain

The same translation problem is solved wherever an external identity must be mapped to a local numeric id. Container user namespaces map a range of host uids to a container's uids; the `/etc/subuid` ranges play the same part as `idmap config` ranges and have the same collision hazards. NFSv4 `idmapd` translates `user@domain` strings to uids. Cloud instance agents (OS Login on GCP, SSM on AWS, Entra ID login on Azure Linux VMs) offer SSH logins for directory identities, and each has to choose an id mapping. Kubernetes OIDC claims are mapped to RBAC subjects, and OpenSSH certificates carry principals that are mapped to accounts by `AuthorizedPrincipalsFile`. The lesson that carries over is that identity federation is easy at login and hard at the filesystem, because files remember numbers.

## Examples

Worked example 1, a plain SSSD join on a RHEL-family server. The administrator checks `chronyc tracking` (time), `dig -t SRV _ldap._tcp.acme.example` (DNS), then runs `realm discover acme.example` to see which software `realmd` plans to use, followed by `realm join --user=svc-join acme.example`. After joining, `realm permit -g linux-admins@acme.example` limits who can log in; `id alice@acme.example` should show a uid in the SSSD range and a group list including nested groups. The hostname must be a fully qualified name within the domain or the automatic DNS update fails (a common cause of "joined but not registered").

Worked example 2, a winbind member serving files. The administrator sets `security = ads`, uses `idmap config ACME : backend = rid` with a 10000-999999 range, runs `net ads join -U svc-join`, enables `winbind`, selects the `authselect` profile, runs `wbinfo -t` and `getent passwd 'ACME\alice'`. A share with `valid users = @"ACME\file-editors"` then works. The second host in the estate uses the identical stanza so that the ids match and a shared NFS or backup restore keeps ownership.

Worked example 3, a failing join. `realm join` reports `Couldn't authenticate to active directory: SASL(-1): generic failure: GSSAPI Error: ... Clock skew too great`. The log in `/var/log/sssd` is empty because the failure came before SSSD started. The cause is that the virtual machine's clock was restored from a snapshot and chrony had not stepped it. The fix is `chronyc makestep`, then repeat. A second variant of the same symptom: `Preauthentication failed` is a wrong password or a locked service account; `KDC has no support for encryption type` means the host asks for an encryption type that the domain has disabled (RC4 versus AES settings); `Cannot find KDC for realm` means DNS.

Worked example 4, a silent failure after months. Logins for AD users start failing on a host that was left switched off for three months. `sssctl domain-status` reports the domain offline, `kinit -k` with the host keytab returns `Preauthentication failed`, and `net ads testjoin` (if winbind is in use) reports a failure of the secure channel. The machine password was rotated by the DC policy while this host was away; the fix is to rejoin with `realm join` or `net ads join` using the existing account (`--computer-name` reuse) and to put a monitoring check on `net ads testjoin` or `klist -k` age for hosts that might sleep for long periods. These examples follow the failure patterns documented by the vendor and in practitioner guides [src: rhel-10-docs 659714f4b344de87] [src: rocky-docs 1df1064a4ac8c009].

## Related problems and ideas

Related approaches fall into three classes. First, identity brokers other than AD: FreeIPA (and Red Hat IdM) gives Linux-native Kerberos, LDAP, DNS and certificate services and can join AD through a cross-forest trust, so that AD users appear on IPA clients without creating Linux accounts in AD. Second, "directory-light" approaches: `pam_ldap` with POSIX attributes only, or `nslcd` as a lighter LDAP cache; these are simple and fragile. Third, cloud identity (Entra ID, Okta, Google Workspace) with an agent on the host. A Kerberos-only variant, where only authentication is delegated and local accounts are provisioned by automation, avoids the id-mapping problem entirely at the cost of account lifecycle work; configuration management (Ansible) can create the local accounts from group membership. Newer ideas include replacing NSS plug-ins with a varlink or D-Bus user database (`systemd-userdbd`), so that user lookups are not tied to glibc's NSS, and passkey or certificate based logins that bypass the password.

## Active research

Recent upstream activity concentrates on: removal of the dependency on NTLM and RC4 in Samba and SSSD; support for Windows Server's changing defaults such as LDAP channel binding and signing; GPO handling in SSSD (`ad_gpo_*` options and the move toward more of the Windows policy surface); Samba's new local-KDC and IAKerb ideas that mirror Microsoft's plans; and a winbind rewrite to use a varlink interface (a new `winbind varlink service` parameter appeared in the 4.23 series, to verify) [web: samba.org]. Open questions include whether to retire the `nss` interface in favour of a user database API, how to represent AD's foreign security principals in a single-uid space, and how to make a machine identity survive cloning without human steps.

## Future direction

Expect SSSD to remain the default for logins and winbind to remain the choice for Samba-centric servers, with the `sss` idmap back-end narrowing the gap. Watch the Windows Server 2025 and later domain controller defaults (signing, channel binding, NTLM reduction), because a member that depends on a weak default will break on the DC upgrade, not on its own change. For the operator, the lasting recommendations are stable: decide the id-mapping strategy first and write it down; test with `getent` before any application; automate the join and the rejoin; monitor the machine-account health; and keep a host's time and DNS under configuration management.
