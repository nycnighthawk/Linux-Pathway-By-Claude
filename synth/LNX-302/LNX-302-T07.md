# Serving Windows desktops: domain-joined clients, mapped drives and shared printers

## Define the problem

The earlier topics describe the server side of a mixed estate. This one adopts the viewpoint of the Windows desktop that consumes it. A person sits down at a Windows 10 or 11 machine, signs in with a domain password, expects their home directory to appear as a drive letter, expects the department share to be there as well, and expects to print by choosing a printer from a list. None of that is built into Windows by magic: each expectation corresponds to a concrete mechanism that the administrator must provide, and when the domain controller and the file and print servers are Linux machines, the mechanisms must be provided by Samba, CUPS and group policy tooling.

Three problems are bundled together. First, **joining and managing the client**: a Windows machine has to find a domain controller, create a computer account, apply group policy, and prove its identity. If the DC is a Samba AD DC rather than a Windows Server, the question is what works, what does not, and which Windows features assume a Microsoft-only domain. Second, **connecting the user to data**: the logon process must map network drives or redirect folders from the right file server for the person and the site, and do it with single sign-on. Third, **printing**: a print job passes through several translation layers (application, Windows print subsystem and driver, spooler, transport, queue on the server, filter, and the printer's own language), and the Windows side wants to install a matching driver automatically when it connects to a shared printer. Failure looks like a machine that cannot find its domain, drive letters that appear for some users and not others, a printer that installs but prints garbage or prints nothing, or a printer installation that is silently blocked by a security change.

This slice covers the Windows client viewpoint of a Samba-based estate: domain join and policy; drive mapping and folder redirection; the Samba print server on top of CUPS; and the drivers and security settings that decide whether printers can be installed. Samba file services and Samba AD were covered earlier. Managing the Windows hosts as servers (PowerShell, OpenSSH, Ansible) is covered in the neighbouring topics.

## History and approaches

Windows for Workgroups (1993) introduced peer-to-peer file and printer sharing: a client browsed the network with broadcast-based name resolution and attached to a share by `net use`. The model of the idea that a share is a name and a printer is simply another share came from this era and persists: in SMB, a shared printer is a resource addressed like a share (`\\server\printername`) and the print protocol rides on the same connection, using the Spooler Subsystem RPC interface (spoolss) over a named pipe. Samba implemented this early, in the 2.x series, so that a Unix print queue could be reached by Windows clients, and it grew features such as automatic driver downloading from a special share named `print$`.

Windows NT domains made the client roles explicit. Policy at logon was done with system policies and logon scripts (`NETLOGON` share), and from Windows 2000 with group policy, a set of templates stored on the domain controllers in SYSVOL and applied by a client-side service. Samba 3 could serve logon scripts and profiles for NT-style domains; Samba 4 acts as an AD DC and holds the SYSVOL share, so a Windows machine joins it the way it joins a Windows DC, using the same dialog and the same protocols, and the policy objects are edited from a Windows machine running the Remote Server Administration Tools [web: wiki.samba.org]. Microsoft's own documentation of how a client finds its DC (DNS SRV records, site-aware, with NetBIOS as a fallback) applies unchanged [src: ms-learn-adds 804bad170341b7c4] [src: ms-learn-adds d586c23298dacee7].

On the printing side Unix systems used `lpd` and later CUPS (Common UNIX Printing System, 1999, adopted by Apple in 2002), which defines printers as queues speaking the Internet Printing Protocol and converts jobs through a filter chain into the printer's language (PostScript, PCL, raster formats). The traditional solution for Windows clients was: an application prints through a Windows driver that creates a job in PostScript or a raw printer language; the spooler sends it to the Samba server; Samba hands it to CUPS; CUPS either passes it through unchanged (if the job is already in the printer's language, a "raw" queue) or filters it. Early approaches installed a native Windows driver on each client and sent raw data; others used the generic PostScript driver on the clients and let CUPS convert (the model that Samba's old CUPS driver kit, `cupsaddsmb`, automated). The partial successes were networks in which a single driver was uploaded to the server's `print$` share and every client picked it up. The failures were the drivers themselves: the quality of Windows print drivers varied, 32-bit and 64-bit clients needed separate driver packages, the "point and print" function that silently installed a driver from a server ran code as SYSTEM, and in 2021 the PrintNightmare vulnerabilities (CVE-2021-34527 and relatives) exposed that design as an attack vector. Microsoft responded by requiring administrative rights to install drivers through point and print by default, which broke many "driver download from the server" setups until the administrator changed a policy or pre-installed drivers [web: learn.microsoft.com].

The pattern now: push the work toward standard protocols. IPP Everywhere and Mopria describe printers that publish their capabilities and accept standard document formats (PDF, PWG raster), so no vendor-specific driver is needed on either side, and Windows includes a class driver for them.

## Current state

### Windows client and a Samba domain

A Windows 10 or 11 client in a Pro, Education or Enterprise edition joins by setting the DNS server of the client to the DC address (the first requirement, as the DNS topic explains) and using System Properties, Settings or `Add-Computer -DomainName acme.example -Credential ACME\Administrator -Restart`. The Home edition cannot join. The Samba DC supports the join with computer account creation, machine password and Kerberos authentication. Group policy is stored in SYSVOL, so the point from the replication topic applies: SYSVOL is populated on the DC from a Windows administration host, edits should happen on the PDC emulator, and the permissions are reset with `samba-tool ntacl sysvolreset` after manual changes. Group policy objects are created and edited with the Group Policy Management Console from a Windows machine with RSAT installed (Samba also has `samba-tool gpo` subcommands to list, show, link and fetch policies, and a `samba-gpupdate` client for Linux members). The machine finds its policy by querying LDAP for the `gPLink` of its organisational unit and reading the `gPCFileSysPath` under `\\acme.example\SYSVOL`. Windows uses DFS referrals for the `\\acme.example\SYSVOL` path to find a DC close to the client, which depends on DNS and the site topology.

Two Windows security features commonly cause a Samba domain to misbehave. SMB signing: modern Windows clients and servers require signing in more situations than before, and a Samba DC or server with `server signing = auto` interoperates, while a Samba configuration forcing unsigned or SMB1-era behaviour does not (Microsoft documents the signing defaults per version, to verify) [web: learn.microsoft.com]. And Kerberos encryption types: Windows moves away from RC4, so machine and service accounts created by Samba must carry AES keys, a point handled by the `kerberos encryption types` and `msDS-SupportedEncryptionTypes` attributes.

### Drive letters and folders

Three mechanisms give the user their data. A **logon script** named in the user's `scriptPath` attribute and kept under the NETLOGON share can run `net use H: \\files\home%USERNAME%`; this is the oldest approach and still the simplest to reason about. **Group policy preferences** (Drive Maps) apply per user or per computer with item-level targeting by group, site or operating system, and are the common choice in a domain. **Folder redirection** moves Documents and Desktop to a server path, with offline files caching on the client. A fourth element, **DFS Namespaces**, offers `\\acme.example\data` as a single name that points at one or more targets; Samba can host a DFS root with `host msdfs = yes` and symbolic links of the form `msdfs:server\share` in a share root, serving a single-target namespace, but it does not implement DFS replication between targets. Each of these relies on single sign-on: the share is reached with the user's Kerberos ticket through the name used in the UNC path, which links back to the Kerberos topic: the client must use the host name that has a service principal, not a CNAME and not an IP address.

On the Samba server the home directories are published with the `[homes]` section (`browseable = no`, `read only = no`, a `path` or the Unix home directory) and a `%U`-based path. A typical share block for roaming profiles or home folders sets `create mask` and `directory mask` to match the ownership model, or uses `acl_xattr` and inheritance so that NT ACLs set from Windows are honoured, as covered in the file server topic.

### The Samba print server

The server-side print stack has these parts: CUPS, which owns the real queues; Samba's `smbd`, which exposes them over the spoolss RPC interface; and the two special shares `[printers]` and `[print$]`. A minimal configuration:

```ini
[global]
    printing = cups
    printcap name = cups
    load printers = yes
    cups options = raw

[printers]
    path = /var/tmp
    printable = yes
    browseable = no
    guest ok = no
    create mask = 0600

[print$]
    write list = @printadmin
    read only = yes
    path = /srv/samba/print-drivers
```

`printing = cups` selects the back end and `printcap name = cups` makes Samba read the queue list from CUPS. `cups options = raw` tells Samba to submit jobs unchanged, which fits the model where the Windows driver produces the printer's native language; the other model leaves the option out and lets CUPS filter. `[print$]` is the driver repository: administrators with the `SePrintOperatorPrivilege` right (or the `printer admin` parameter members) upload drivers into it with the Windows printer properties dialog or with `rpcclient` commands such as `adddriver` and `setdriver`; Samba keeps driver metadata in its registry database, and `rpcclient -c 'enumdrivers'` and `enumprinters` list what is known. The Samba manual page for `rpcclient` lists the spoolss command family, and the vendor documentation walks through the whole procedure, including the automatic driver download for Windows clients [src: samba-docs 2cd5f77d2679b6ac] [src: rhel-10-docs 66407e093dc6066b] [src: rhel-10-docs 00898662d6986235]. Since Samba 4.x the spoolss service can also run as a separate RPC daemon (`rpc_server:spoolss = external`, `spoolssd`), so a slow print driver upload does not block file serving. The parameters are documented among the `smb.conf` printing options [src: samba-docs 9462620c70168e53].

The CUPS side is administered with `lpadmin`, `lpstat -p -d`, `lpoptions`, and the web interface on port 631; its logs, `access_log`, `error_log` and `page_log`, are described in the `cupsd-logs` manual page, and the `error_log` is the first stop for a job that vanishes [src: man-pages a36071235176b854]. A queue defined with a driverless IPP URI and `-m everywhere` (`lpadmin -p lab1 -E -v ipp://printer.acme.example/ipp/print -m everywhere`) needs no vendor driver on the Linux side. Common failure messages in the filter chain, such as the "Filter failed" state that community guides document for particular vendors' devices, point at a missing or mismatching filter or PPD [src: archwiki 58d7d31a723191c0].

Hardening matters because print services are an attack surface. The compliance guidance recommends disabling printer sharing on machines that do not need it, and the CUPS browsing daemon `cups-browsed` should not run where it is not required, since the 2024 vulnerabilities in it (CVE-2024-47176 and the related issues) allowed a remote unauthenticated attacker to cause a printer to be added from a malicious URL; distributions responded with updated packages that removed the legacy discovery protocols [src: compliance-as-code 54b31d64d3a623c0] [web: ubuntu.com].

### Drivers and the Windows side

On the client, a shared printer is added by connecting to `\\print01.acme.example\lab1`. Windows then wants a driver. If the server's `print$` has a matching one, point and print downloads it, provided the client policy allows it; since the 2021 hardening, a standard user cannot install a driver from a server unless the administrator relaxes "Point and Print Restrictions", lists the approved servers, or the driver is already in the client's driver store (distributed by group policy, a software distribution tool, or the image). Packaging drivers, using one universal driver per printer family, and installing them centrally is the realistic approach. Microsoft's current direction is to prefer inbox IPP class drivers and to stop accepting new third-party V3 and V4 drivers on Windows Update; reports describe Windows Protected Print Mode, which blocks third-party drivers and uses only the IPP class driver with Mopria-certified printers, as an option for locked-down fleets (dates and details to verify against Microsoft's announcements) [web: learn.microsoft.com]. For a Samba print server that matters: a queue that publishes IPP with standard formats works on both Linux and a protected Windows client, while one that needs a vendor driver will not.

### The generalised pattern

The structure is: a directory that holds policy, a file service that holds the data and drivers, the client machinery that applies policy and maps resources by name and group, and a spooler chain with translation at each stage. The generalisation is push the variable parts (drivers, formats) to the edge and standardise the middle.

## Assessment: the good, the bad and the ugly

The good. A Linux server can serve a Windows office entirely with open-source components: Samba AD for identity and policy, Samba file servers for data, CUPS for printers, standard Windows tools for administration. Users see no difference. Costs fall (no server licences for the roles, though client access licensing questions are a legal matter outside this text), and the Linux side's automation, snapshots and monitoring apply to the whole stack. Driverless IPP printing removes the largest source of printing trouble.

The bad. Samba's AD DC does not implement every Windows server feature: no SYSVOL replication, no Windows-style read-only DCs, and the supported group-policy surface is the one the Windows client implements, so most policy works and server-side features that depend on Microsoft services (Certificate Services, Exchange, NPS) are outside. Printing is the worst-documented part of the stack. Samba spoolss supports the Windows 'v3' driver model reliably and the 'v4' model only partially, and the client-side security changes are a moving target. Drive maps and redirected folders depend on user and group naming staying stable. Logon scripts and preferences run only after the network and the Kerberos ticket are available, and a laptop that wakes up on Wi-Fi before the VPN will map nothing.

The ugly. Printer troubleshooting crosses six components and three vendors. A job can be accepted by the server and discarded by a filter; can print on the Linux side from `lp` and not from Windows; or can print from Windows once and fail after the next Windows update changes driver preferences. Duplicate and orphaned printer objects accumulate in AD if printers are published with `net ads printer publish` and never removed. Access control is split between three layers (the Samba `valid users`, the CUPS policy in `cupsd.conf`, and the NT ACL on the printer), and each denies in its own way. And the licence and lifecycle of vendor drivers, with PrintNightmare changes and Microsoft's push toward IPP class drivers, means a driver-based design built five years ago may break on a feature update without any change on the server side.

## Applications beyond this domain

A a name that a directory resolves to a service and that is attached at login is the shape of NFS automounter maps in NIS or LDAP (`auto.home`), of Kubernetes service discovery, and of cloud file services mounted at login by identity. Printing teaches an architectural lesson that reappears in storage, in graphics and in networking: a late-binding translation chain with a lowest-common-denominator exchange format (PDF or PWG raster for print, ONNX for models, OCI images for containers) beats per-device drivers. IPP itself is used beyond printers, for example for 3D printers and for cloud print gateways. Group-policy-style declarative configuration pushed to many clients shows up as MDM profiles on phones and laptops, as Kubernetes admission policy, and as configuration management for Linux fleets (Ansible, Puppet, SaltStack), which makes it natural to manage Samba-based policy and Linux hosts under one change process.

## Examples

Worked example 1, a new office printer. The administrator adds a networked printer with driverless IPP: `lpadmin -p floor2 -E -v ipp://10.0.2.40/ipp/print -m everywhere`, tests with `lp -d floor2 /usr/share/cups/data/testprint`, and reloads Samba (`smbcontrol all reload-config`) so the new queue appears in `[printers]`. On a Windows client in the domain: `Add-Printer -ConnectionName \\print01.acme.example\floor2`. If the server holds no matching driver, Windows chooses the IPP class driver. A group policy preference then assigns the printer to the users of the second-floor OU.

Worked example 2, a drive map by group. A GPO user preference maps `H:` to `\\files.acme.example\home\%LogonUser%` and `P:` to `\\files.acme.example\projects` only for members of `ACME\projects`. The administrator tests with `gpresult /r` and `gpupdate /force` on the client, then verifies on the server with `smbstatus -S` that the session came in through Kerberos (the `smbstatus` listing shows the authentication protocol and signing state in newer releases).

Worked example 3, a failing one: the print driver install is denied. After the monthly Windows update, standard users get a failure to connect with error code 0x0000011b or are prompted for administrator credentials when connecting to the shared printer. The server is unchanged. The cause is the client's Point and Print restriction, or in the 0x11b case an RPC authentication-level change that the Samba server's configuration does not satisfy because the Samba print server is not accepting the connection with privacy-level RPC (check `server signing` and the `smb ports` settings, and that the client connects by the canonical name). The solutions, in order of preference: pre-stage the driver on clients, move to IPP class driver queues, add the print server to the approved list in the Point and Print policy; and only as a last resort relax the policy, which reintroduces the attack surface.

Worked example 4, a failing one: garbage output. A queue printing from Windows produces pages of PostScript source text. The queue was defined with a PostScript driver on the client but the printer only speaks PCL, and the Samba share was set `cups options = raw`, so the job is passed unchanged. Removing the raw flag or switching the Windows queue to the printer's PCL driver restores output. The error log of CUPS and `lpstat -o` show whether the job went through the filters; the page log shows whether the job counted pages.

## Related problems and ideas

A related architecture avoids the print server on the client side with direct IP printing: each Windows client addresses printers by IP over IPP, and the server is not part of the data path, trading control and accounting for simplicity. Other approaches use print management products (PaperCut, uniFLOW, Microsoft Universal Print) that hold jobs until the user authenticates at the device, which is also a security measure. For desktops the large question is whether to manage them with group policy, with an MDM service such as Intune, or with both; a Samba AD DC supports the first only, and Microsoft's co-management path assumes a Microsoft cloud tenant. Alternatives to mapped drives include web-based file portals, sync clients and a Nextcloud or similar service in front of the same storage. On the Linux side, a related issue is the inverse: Linux desktops in the same estate using the `cups` queues and Kerberos tickets, a nice reuse of the same identity (see the earlier SMB client topic).

## Active research

CUPS is being rebuilt: the project's new generation separates the printer application model (Printer Applications, packaged as snaps or containers and exposing an IPP service for a legacy device) from the scheduler, so drivers become isolated applications rather than PPD files and filters; this direction, led by the OpenPrinting project, responds both to the driver problem and to the vulnerabilities of the old filter model. In Windows, the open questions include how the protected print mode will treat shared queues from non-Windows print servers, how fleets will print to devices that lack Mopria support, and how long the legacy driver model will be tolerated (to verify) [web: learn.microsoft.com]. In Samba, spoolss work is incremental, and group policy support for Linux clients (`samba-gpupdate`, Python `gpo` modules) is extended to more policy types over time.

## Future direction

Expect printing to move to IPP and standard formats, with vendor-specific drivers retreating to special-purpose devices. Expect Windows policy about driver installation to tighten rather than relax, and plan any new print server as an IPP service first. For identity and policy, expect Windows clients to continue demanding signed and encrypted SMB and Kerberos with AES, so a Samba estate should keep its version current. The long-term question for a mixed estate is whether the client management plane remains group policy against an on-premises directory or shifts to a cloud-managed model; for a Linux team, the sensible practice is to keep the Linux-hosted services standards-based (SMB 3, Kerberos, IPP, LDAP) so that either management plane can use them.
