# One remote shell for both worlds: OpenSSH and PowerShell 7 on Windows

## Define the problem

A Linux administrator who inherits a Windows server finds that almost nothing they know applies. There is no shell to log into, only a graphical console and Remote Desktop. Remote administration uses WinRM (the web-services management protocol) on ports 5985 and 5986 with Kerberos or NTLM authentication, and the scripting language is PowerShell, whose commands pass .NET objects rather than lines of text. An organisation that manages hundreds of Linux hosts through SSH keys, `scp` and automation tools has a reason to want a single mechanism for both kinds of machine: one port, one credential type, one audit story, one set of firewall rules, and, if possible, the same language for glue scripts on either side.

Two gaps stand in the way. The first is the transport. For years, Windows had no SSH server, and the third-party ones (Cygwin sshd, Bitvise, FreeSSHd) each had their own account model and were not integrated with Windows security, so file permissions, profile loading and service accounts behaved oddly. The second is the language. Windows PowerShell 5.1 is part of the operating system, closed to new features, and tied to .NET Framework on Windows alone. It cannot run on Linux, cannot be installed side by side with an update that breaks scripts, and its remoting is built on WinRM. Teams needed a PowerShell that could be installed on a Linux jump host and on a Windows server alike, versioned independently of the operating system, and able to speak over SSH.

This slice covers the pair that closes both gaps: the OpenSSH server and client that ship with Windows (and the upstream Win32-OpenSSH project), their configuration quirks, and PowerShell 7 with remoting over SSH. It also covers the differences from the Linux versions that surprise people (administrator keys, default shell, path syntax, permissions), and how Linux tools (plain `ssh`, `scp`, `sftp`, Ansible) interact with them. Ansible-specific management is the subject of a later topic, and the domain-level pieces (AD, Kerberos) of earlier ones.

## History and approaches

Windows PowerShell 1.0 appeared in 2006 as "Monad", Jeffrey Snover's design for an object pipeline that would make Windows administration scriptable at scale. Version 2 (2009) added remoting, built on WS-Management (WinRM), and from there the language grew with each Windows release up to 5.1 in 2016. In August 2016 Microsoft open-sourced PowerShell, ported it to .NET Core, and released it for Linux and macOS under the name PowerShell Core 6; version 7 (March 2020) unified the line, dropped the "Core" in the name, and became the supported release train with long-term-support versions on a three-year rhythm (7.2 LTS, 7.4 LTS and 7.6 LTS, the last built on .NET 10 and released in March 2026) [web: devblogs.microsoft.com]. It installs beside Windows PowerShell 5.1: `pwsh` starts version 7, `powershell.exe` still starts 5.1, and neither replaces the other.

The SSH story is a parallel one. After years of reliance on third parties, Microsoft announced in 2015 that it would port OpenSSH, and published the work as the open-source Win32-OpenSSH project. It shipped in Windows 10 (1809) and Windows Server 2019 as an optional feature, with the client on by default in recent Windows 10 and 11 builds, and the server as a "Feature on Demand" installed by `Add-WindowsCapability`. Microsoft's team continues to merge upstream OpenSSH changes into the Windows build and publish previews on GitHub, a stated investment area in the PowerShell team's own planning posts [web: devblogs.microsoft.com]. PowerShell 6 added the SSH remoting transport on top of this: instead of WinRM, `pwsh` starts an `ssh` process which in turn launches `pwsh -sshs` (a server mode that speaks the remoting protocol on stdin and stdout) on the target, so remoting needs only an SSH daemon and the `Subsystem` line.

Approaches that preceded this each left a gap. Telnet and the Windows `psexec` family offered unencrypted or ad hoc execution. WinRM with HTTP and Kerberos worked in a domain but was painful from Linux, where the PowerShell remoting client needed an additional NTLM or GSSAPI library (`gssntlmssp`) that distributions did not install by default, and where authentication to a non-domain host required Basic over HTTPS or certificates. Cygwin sshd worked but created a second set of user concepts. Orchestration tools added their own agents. The pattern that emerged is plain: use the same SSH daemon on every platform, and run a cross-platform shell behind it.

## Current state

### The OpenSSH server on Windows

Installation uses the optional capability and a service:

```powershell
Get-WindowsCapability -Online -Name 'OpenSSH.Server*' | Add-WindowsCapability -Online
Set-Service -Name sshd -StartupType Automatic
Start-Service sshd
```

The installer creates a firewall rule for port 22 (check it with `Get-NetFirewallRule -Name '*ssh*'`), and the Ansible documentation shows the same sequence along with the default-shell setting, noting that Ansible supports only the OpenSSH shipped with Windows, not the upstream package [src: ansible-docs d168f17568c60c69]. The server configuration file is `C:\ProgramData\ssh\sshd_config` (not under `/etc`), host keys are in the same directory (generated on first start of the service), and the service's name is `sshd`, with a companion `ssh-agent` service for key handling. After editing `sshd_config`, `Restart-Service sshd` applies it, and `sshd -T` prints the effective configuration for testing.

Four behaviours differ from Linux and cause most of the trouble:

1. **Default shell.** The initial shell for a session is `cmd.exe`. To make it PowerShell, set the string value `DefaultShell` under `HKLM:\SOFTWARE\OpenSSH` to the full path of the executable; the Microsoft documentation illustrates it with Windows PowerShell and says the setting does not apply to the client [src: ms-learn-adds 80d99c0236db2ebe]. For PowerShell 7 the value is `C:\Program Files\PowerShell\7\pwsh.exe`. A second value, `DefaultShellCommandOption`, controls the flag (`/c` by default for cmd) and matters when the shell is not cmd. A mismatch between the shell and the flag is the reason that `ssh host command` works under one shell and not another.
2. **Key authentication for administrators.** For an ordinary user, the public key goes in `C:\Users\<name>\.ssh\authorized_keys` as on Linux. If the account belongs to the local Administrators group, the default `sshd_config` ends with a `Match Group administrators` block that points `AuthorizedKeysFile` at `__PROGRAMDATA__/ssh/administrators_authorized_keys`, a single file for all administrators. The server is strict about its permissions: only SYSTEM and Administrators may have access, enforced with `icacls` (remove inheritance, grant `Administrators:F` and `SYSTEM:F`). A file with the wrong ACL is ignored, and the log shows a bad-ownership message, which Linux people read as "mode too open".
3. **Account names.** With a domain, the login name takes the form `user@domain` and the full command `ssh user@acme.example@server`, or `ssh 'ACME\user'@server` with quoting; the Microsoft first-use page shows the domain-qualified pattern [src: ms-learn-adds 7a798b2db3eccee0]. Local accounts are `server\user`. The server does not support GSSAPI Kerberos single sign-on in the Windows build in the way an `sshd` on Linux does; domain users authenticate with a password or a key (to verify against the current release) [web: learn.microsoft.com].
4. **Paths and files.** Paths in `scp` and `sftp` take the form `/C:/Users/alice/file.txt` or relative to the profile; file ownership and mode bits do not map to ACLs, so `chmod` is mostly cosmetic; line endings and quoting differ between `cmd` and PowerShell. Windows logs sshd events in the `OpenSSH/Operational` event channel (`Get-WinEvent -LogName OpenSSH/Operational`), and a debug run in the foreground with `sshd -d` as administrator helps in tests.

### PowerShell 7 in the picture

PowerShell 7 installs from an MSI, from `winget install Microsoft.PowerShell`, or from the Microsoft package repositories on Linux (`dnf install powershell`, `apt install powershell`). The MSI option to register with Microsoft Update matters on servers, since only that route gets security updates through the normal channel (to verify per release). Windows Server 2025 images contain 5.1 only, so a PowerShell 7 install is a deliberate step [web: devblogs.microsoft.com]. Enabling SSH remoting on the target adds a subsystem line to `sshd_config`:

```text
Subsystem powershell C:/Progra~1/PowerShell/7/pwsh.exe -sshs -NoLogo -NoProfile
```

The path uses the 8.3 short name because the Subsystem directive does not parse spaces reliably. The server is restarted, and then from any machine with `pwsh` and `ssh` the following work:

```powershell
Enter-PSSession -HostName win01.acme.example -UserName alice -KeyFilePath ~/.ssh/id_ed25519
$s = New-PSSession -HostName win01.acme.example -UserName alice
Invoke-Command -Session $s -ScriptBlock { Get-Service sshd | Select-Object Status, StartType }
Copy-Item -ToSession $s -Path ./report.csv -Destination C:\Data\
```

`-HostName` (with `-UserName`, `-KeyFilePath`, `-Port`) selects the SSH transport; `-ComputerName` selects WinRM. Objects returned by a remote script block are serialised and rehydrated on the caller as property bags, without methods (the usual "deserialized" prefix on the type name), which is the first difference a Linux scripter notices. Remote sessions can be persistent (`New-PSSession`) or one-shot, supported with several machines at once by passing an array to `Invoke-Command -HostName`, and `-ThrottleLimit` caps concurrency.

On a Linux host the same `pwsh` is a normal shell and scripting language. The language is cross-platform, with automatic variables `$IsLinux`, `$IsWindows` and `$IsMacOS` to select code paths; the module `Microsoft.PowerShell.SecretManagement`, JSON and CSV cmdlets (`ConvertFrom-Json`, `Import-Csv`) and `Invoke-RestMethod` make it a reasonable tool for gluing REST APIs to a Windows estate. Ansible illustrates the same relationship from another angle: its Windows modules are PowerShell, whose interpreter is chosen from the module's shebang or the `ansible_pwsh_interpreter` variable, and defaults to 5.1 on Windows unless a module asks for 7 [src: ansible-docs eb9824152b2ab67b] [src: ansible-docs 92ee265e0f0ca91f]. The connection plugin `ansible.builtin.ssh` with `ansible_shell_type=powershell` is the SSH route to Windows hosts, with WinRM and PSRP as alternatives.

### The generalised pattern

The structure is: a single authenticated, encrypted channel (SSH), a subsystem mechanism that lets the daemon start a purpose-built server process (an SFTP server, a PowerShell remoting server, or in other systems a Git or database protocol handler), and a shell or runtime that exists on both platforms. Anything that can run behind a subsystem can be reached the same way from Linux.

## Assessment: the good, the bad and the ugly

The good. One protocol and one port for the whole fleet. Key-based authentication and `ssh-agent` forwarding behave as on Linux, and bastions, jump hosts (`ProxyJump`), certificates signed by an SSH CA and agent-based logging apply to Windows too. The firewall change is a single rule. The same scripts using `pwsh` run on Linux automation hosts and on Windows servers; the engineering effort for cross-platform tooling falls. The client and server in Windows are real OpenSSH, so existing knowledge (`sshd_config`, `Match` blocks, `AllowGroups`) carries over, and Microsoft's integration of upstream security fixes is regular.

The bad. The Windows port lags upstream by some months, so new features arrive late (to verify the version shipped with a given build). The security model differs: users' keys, profile loading, token creation and the interaction with User Account Control mean that an SSH session as an administrator receives a full token without a prompt, which is convenient and also removes a layer of protection that interactive logins had. Remoting over SSH offers fewer features than WinRM: no Just Enough Administration endpoints through the SSH transport in the same way, no native Kerberos delegation, and the "double hop" problem (using the remote session's identity to reach a third server) is not solved by SSH key authentication, since no delegable credential exists. Sessions via the SSH subsystem load no profile unless the flags allow it, and the default shell setting is global to the machine, so a script that expects `cmd` breaks after the change.

The ugly. Permissions and quoting. A single stray inherited ACL entry on `administrators_authorized_keys` makes key login silently fall back to password, which an automation job without a password treats as a hang. Quoting of a command passed through `ssh host "..."` travels through three parsers (the local shell, the remote default shell and the program called), so a command that works on Linux fails because of `cmd.exe` quoting rules; the advice is to give the remote side a script file or use `-EncodedCommand`, or better, use PSRP-over-SSH sessions where arguments are objects. Another ugly is the update path: the Windows-shipped OpenSSH is updated by Windows Update, while the upstream package is updated by its installer, and a machine with both has two `sshd` binaries and one configuration directory. Finally the security posture: exposing port 22 on a Windows server with password authentication enabled is an invitation to the same brute-force traffic that Linux hosts have always had, so disable passwords (`PasswordAuthentication no`) once keys work, restrict with `AllowGroups`, and put it behind a bastion or a VPN.

## Applications beyond this domain

SSH subsystems are a general idea. SFTP is the best-known subsystem; Git over SSH, `rsync`, Ansible's SSH connection and Kubernetes' `kubectl port-forward` through bastions are the others, and the pattern of the daemon merely authenticates and then launches a helper wired to stdio recurs in LSP servers over SSH, in VS Code's remote-SSH server installation, and in database tunnelling. The wider lesson of PowerShell's open-sourcing is the cross-platform shell with a typed pipeline: Nushell, Elvish and the JSON-oriented tools such as `jq` pipelines answer the same question from the Unix side, and each has to decide how to carry structure across a remote boundary (serialisation, as PowerShell does, or text). Certificate-based SSH, in which an internal CA signs short-lived user certificates, is a general replacement for scattering public keys, and it works against Windows `sshd` as long as the `TrustedUserCAKeys` and `AuthorizedPrincipalsFile` options are set.

## Examples

Worked example 1, a first connection from Linux. On a Windows Server 2022 test host, an administrator installs the server capability, starts the service, opens the firewall rule, and sets the default shell registry value to `pwsh`. From the Linux workstation: `ssh alice@win01` with a password proves the path; `ssh-copy-id` does not work against Windows administrators, so the key goes in `administrators_authorized_keys` through an elevated session: `Add-Content -Path $env:ProgramData\ssh\administrators_authorized_keys -Value $key`, then `icacls $env:ProgramData\ssh\administrators_authorized_keys /inheritance:r /grant 'Administrators:F' /grant 'SYSTEM:F'`. `ssh -i ~/.ssh/id_ed25519 alice@win01 'Get-ComputerInfo | Select-Object OsName, OsVersion'` now returns the data without a prompt.

Worked example 2, a fleet inventory. A Linux jump host with `pwsh` installed runs one script against 200 servers of both kinds, selecting transports by an inventory column: `Invoke-Command -HostName $linuxHosts -UserName svc-inv -KeyFilePath $key -ScriptBlock { uname -r }` and the same command with `Get-CimInstance Win32_OperatingSystem` for Windows hosts. The results are collected as objects with the host name attached and written to a CSV file with `Export-Csv`. The script checks `$IsWindows` inside the script block when one block must serve both.

Worked example 3, a failing one: key login falls back to a password. The key is in `administrators_authorized_keys`, yet the client prompts for a password. `ssh -v` shows `Offering public key` and then `Authentications that can continue: password`. On the server the event log under `OpenSSH/Operational` says `Authentication refused: bad ownership or modes for file`. The file had been created by an elevated PowerShell session as a different owner and inherited the Users group's read access. Resetting with the `icacls` command from the previous example fixes it. A second cause of the same symptom is a key line with a Windows line ending or a BOM at the start of the file (from `Out-File` in Windows PowerShell 5.1, which writes UTF-16 by default), so the file should be written with `-Encoding ascii` or `utf8NoBOM` in version 7.

Worked example 4, a failing one: the subsystem. `Enter-PSSession -HostName win01` returns `The SSH client session has ended with error message: subsystem request failed on channel 0`. The `Subsystem powershell` line was added to the server configuration but used the long path with spaces, and the service was never restarted. Using the short path and `Restart-Service sshd` fixes it; testing the helper directly with `ssh win01 'pwsh -sshs'` should wait silently for input rather than print a banner.

## Related problems and ideas

Neighbouring problems include remote execution via WinRM, which remains the right tool inside a pure Windows domain where Kerberos delegation, JEA and constrained endpoints are needed; it is configured with `Enable-PSRemoting`, authenticated with Kerberos or NTLM, and encrypted by the transport in the HTTPS listener or by message-level encryption. Azure Arc, AWS Systems Manager and similar agents avoid inbound ports altogether by having the host call out to a control plane. Windows Admin Center and Server Manager are graphical alternatives. Desired State Configuration (DSC) version 3 is a cross-platform, JSON-driven configuration engine that can run on Linux. A related idea is the Windows Subsystem for Linux, where a Linux shell runs on the Windows host with its own `sshd`, which blurs the picture of who is the "Linux" half; for server management it is a convenience and not a replacement. Not yet mainstream: running the PowerShell remoting server as a long-lived service with token-based authentication rather than on demand through SSH; and using SSH certificates with Windows hardware-backed keys.

## Active research

The PowerShell team's published plans cover cross-platform improvements, a faster startup, and the DSC rewrite; the OpenSSH team continues to merge upstream releases and to improve the Windows-specific parts (ACL handling, ConPTY support, performance of `scp`). Security researchers examine how SSH changes the lateral-movement picture on Windows, where interactive logon types and token behaviour differ from WinRM, and how to audit key-based access. Open questions include how to provide Kerberos single sign-on over SSH on Windows in the way MIT-style GSSAPI offers on Linux, and how to avoid the double-hop limitation without enabling unconstrained delegation (to verify the current roadmap) [web: devblogs.microsoft.com].

## Future direction

Microsoft's trajectory is toward OpenSSH being a first-class and eventually default component on server editions and toward PowerShell 7 as the supported automation language, while Windows PowerShell 5.1 stays in maintenance. Expect the 7.6 LTS line to be the baseline for production through its support window, which ends in late 2028 according to the reports at release (to verify the date on Microsoft's lifecycle page) [web: devblogs.microsoft.com]. Mixed estates should plan to standardise on SSH with certificates for administrative access, keep WinRM for the places that need delegation or JEA, and keep a compatibility test in the build pipeline for scripts that still rely on 5.1-only modules. Practically: install `pwsh` side by side, put the `Subsystem` line and the shell setting in configuration management, manage `administrators_authorized_keys` with its ACL as code, and test the first connection from a Linux client as part of every Windows image build.
