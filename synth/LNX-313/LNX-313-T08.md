# Teaching the cluster a new trick: the controller pattern and a first operator with kubebuilder

## Define the problem

Kubernetes is built from control loops. A Deployment controller watches Deployments and keeps the right number of ReplicaSets alive, a ReplicaSet controller keeps the right number of Pods, and the kubelet keeps containers running as the Pod says. A person who runs a stateful application, such as a database cluster with replicas, backups, failover and version upgrades, performs a similar loop by hand: look at the current state, compare it with what is wanted, act, and repeat. The knowledge needed for that loop lives in runbooks and in the heads of operators. The question behind this slice is whether that knowledge can be written as software that runs in the cluster, uses the same API conventions as everything else, and lets users ask for the outcome they want instead of the steps to get there.

The operator pattern is the answer. The Kubernetes documentation describes it as a way to package, deploy and manage an application by extending the API with custom resources and writing controllers that act on them [src: kubernetes-docs b790d166a5d7af34]. A user creates an object of a new kind, for example a database with a size and a version, and the operator creates and maintains the underlying Pods, Services, volumes and Jobs, and reports status back on the object. The pattern does not need a special framework; any program that watches the API and reconciles will do. But writing a correct controller from scratch involves a large amount of repeated machinery: caches, work queues, retries, leader election, code generation for types, and manifests for permissions and for the definition itself.

Kubebuilder is a framework and command-line tool from the Kubernetes special interest group for API machinery that scaffolds this machinery, built on a library called controller-runtime. This slice explains the controller model well enough to write a correct reconciler, shows how kubebuilder organises a project, and covers the rules that separate a robust operator from one that works in a demonstration and fails in production. The learning goals are to read and write a reconcile function, to understand owner references, finalizers and status conditions, to test a controller without a full cluster, and to decide when an operator is the right tool.

## History and approaches

The idea of controllers as the heart of Kubernetes is as old as the system. Early users extended it with third-party resources, a short-lived mechanism replaced by custom resource definitions, which let a cluster serve a new API type from the same server and store without writing an aggregation layer. CoreOS popularised the operator name in 2016 with an operator for etcd and then for Prometheus, expressing the idea that a human operator's knowledge could be encoded as a controller. The Operator Framework followed, with a software development kit, a lifecycle manager for installing operators and a catalogue, and defined capability levels from basic install through upgrades, backups and auto-pilot behaviour, which became a common vocabulary for how much an operator does.

Two lines of tooling emerged. Kubebuilder, from the API machinery group, grew out of the experience of building the project's own controllers and focused on being a thin layer over client libraries, with code generation and a clear project layout. The Operator SDK, from the Operator Framework, adopted controller-runtime and kubebuilder's layout for Go operators and added options to build operators from Helm charts or Ansible playbooks, which suit teams that already have that content. Other approaches avoid writing a controller in Go: Metacontroller lets a webhook implement the reconcile logic in any language, KUDO and similar tools described operators declaratively, and Crossplane and kro compose existing resources into higher-level APIs with templates and little or no custom code. The documentation lists several of these under the heading of writing your own operator [src: kubernetes-docs b790d166a5d7af34].

The practical history is a catalogue of mistakes that later became documentation. Controllers written as edge-triggered handlers, reacting to events and not to state, missed changes when they were restarted and drifted from the truth. The Kubernetes community settled on level-triggered design: a reconcile function is called with the name of an object, ignores what event caused the call, reads the current state and drives it toward the desired state, and is safe to call at any time and any number of times. Controllers that updated their own status inside the reconcile loop triggered themselves in an infinite loop until predicates and the status subresource separated spec changes from status writes. Controllers that cached everything exhausted memory on large clusters until the cache was restricted by namespace or label. And controllers that deleted external resources on object deletion without finalizers leaked them whenever the controller was down at the moment of deletion.

## Current state

**Custom resources.** A CustomResourceDefinition declares a new kind, its scope, its versions and an OpenAPI schema, and the API server then serves and validates objects of that kind. Modern definitions use structural schemas and may include validation rules written in the Common Expression Language, evaluated by the API server, which removes the need for many validating webhooks. A status subresource separates the spec, which belongs to the user, from the status, which belongs to the controller, with separate permissions and without bumping the object's generation on status writes. Conversion between versions is handled by webhooks when the schema changes incompatibly, which is a concern for operators that live for years.

**The kubebuilder project.** The tool scaffolds a project with a main program that creates a manager, a directory for API types and a directory for controllers. The command for creating an API asks for a group, a version and a kind and generates a Go struct with spec and status fields, a reconciler skeleton and the registration code. Comment markers on the types and the reconciler drive code and manifest generation: markers on fields set validation such as minimum values and enumerations, markers on the type enable the status subresource and print columns, and markers on the reconciler declare the RBAC permissions the operator needs, from which the role manifests are generated. The build commands generate deep-copy code and manifests, install the definitions into the current cluster, run the controller locally against it, build the image and deploy it, which gives a fast development loop.

**The reconcile function.** A reconciler receives a request containing the namespace and name of an object and returns a result and an error. The usual structure is: fetch the object, returning without error if it is not found, since it was deleted; handle deletion through finalizers if the controller owns external state; compute the desired child objects from the spec; create or update each child, setting the owner reference so that the garbage collector deletes the children with the parent and so that changes to children trigger reconciliation of the parent; compute the status from observed state and update it through the status client; and return a result that may request a requeue after a delay if something is pending. An error return causes a retry with exponential back-off. The function must be idempotent: running it twice in a row must change nothing the second time.

**Watches and caches.** The manager runs shared informers that cache the objects the controller watches, so reads in the reconciler come from memory, not the API server, and may be slightly stale. The controller declares what it watches: its own kind, the kinds it owns, which map events on children back to the parent through the owner reference, and any other kinds with a mapping function. Predicates filter events, for example ignoring updates that change only the status. Because reads can be stale, a reconciler that creates a child and immediately lists children may not see it; the safe pattern is to rely on the next reconcile, which the child's creation event triggers.

**Owner references, finalizers and conditions.** An owner reference makes the child's lifetime depend on the parent. A finalizer is a string on the parent's metadata that blocks its deletion until the controller removes it, which gives the controller a chance to clean up external resources, such as a cloud volume or a database user, and then remove the finalizer so the object can go. Status conditions are a list of typed, timestamped statements, such as available or progressing, with a reason and message, following the convention used by the built-in resources, which allows generic tools and other controllers to read them. A field recording the generation that the status was computed from lets clients tell whether the status reflects the latest spec.

**Testing.** The framework includes an environment that starts a real API server and etcd locally without nodes, so tests can create objects and wait for the controller's effects; no controllers of the built-in resources run there, so Pods never become ready and the tests must set status by hand. Unit tests with a fake client run faster but do not exercise API server behaviour such as validation, defaulting and conflict handling. End-to-end tests on a kind cluster verify the deployed operator with its RBAC and image. The project's guide describes all three layers.

**Operations.** An operator is a Deployment with a service account. It needs the minimum permissions, which the RBAC markers document, leader election so that only one replica reconciles at a time, metrics and health endpoints, and resource limits. Upgrades of the operator must be compatible with existing objects and with the definition's versions; upgrades of the definition are cluster-wide and affect all users. Running many operators multiplies caches and watches, which has costs on the API server.

**When to write one.** An operator is justified when an application has operational logic that is repeated and error-prone, when users should work through a declarative API, and when the team can maintain the code for the life of the application. A Helm chart is enough when the task is installation and configuration; a plain controller is wrong when a few manifests suffice; a composition tool is enough when the logic is mapping one declaration to several resources.

## Assessment: the good, the bad and the ugly

**The good.** The pattern uses the platform's native idioms: declarative API, RBAC, events, watches and garbage collection. Users gain a high-level interface and operations gain reproducibility. The tooling removes most boilerplate, and the level-triggered model makes controllers robust to restarts and missed events. The separation of spec and status, the owner-reference mechanism and the finalizer protocol provide a vocabulary for correct behaviour.

**The bad.** An operator is a piece of production software that must be maintained, tested, versioned and secured, with all the costs that implies. The learning curve covers Go, the client libraries, the API conventions and the controller model. Operators need broad permissions to do their job, which makes them targets. API definitions are hard to change once users depend on them. And the number of operators in a cluster grows quickly, each with its own lifecycle, quirks and resource consumption.

**The ugly.** The notorious bugs are about concurrency and state. A reconciler that is not idempotent creates duplicate children on retries. A hot loop that updates an object on every reconcile triggers the next one and saturates the API server. A stale cache read after a write causes a conflict or a double create. A finalizer left on an object after the operator is uninstalled blocks namespace deletion forever, which administrators then clear by editing the object by hand. Deleting a definition deletes every object of that kind. And an operator that mutates the spec of a user's object to record state defeats the spec and status separation and conflicts with GitOps tools that keep reverting the change.

## Applications beyond this domain

The reconcile pattern is general. Configuration management agents, infrastructure-as-code controllers, cloud provider reconcilers and database schema migration tools all compare desired and actual state and act on the difference. It appears in distributed systems under the name of anti-entropy and in control theory as a feedback loop. Writing a controller teaches design habits that apply anywhere: make operations idempotent, treat observed state as the truth, handle partial failure by retrying, and keep desired state separate from computed state. Even a shell script that is run from a timer and converges a server to a described state is a small operator.

## Examples

A first example is a web application operator. The custom resource has a spec with an image, a replica count with a minimum of one, and optional host name, and a status with the number of ready replicas and a condition for availability. The reconciler creates a Deployment and a Service owned by the custom resource, updates them if the spec changes, creates an Ingress only if a host name is given, and sets the status from the Deployment's status. Running the reconcile function twice changes nothing the second time. If someone deletes the Service by hand, the owner-reference watch triggers a reconcile that recreates it.

A second example is a cleanup finalizer. The operator creates a database user in an external system when a custom resource appears and records the finalizer. On deletion, the API server sets the deletion timestamp and waits; the reconciler sees the timestamp, deletes the external user, removes the finalizer and returns. If the external system is down, the reconcile returns an error and retries, and the object stays in the terminating state, which is correct, because the cleanup is not done.

A third example is a test. A test starts the local API server environment, creates a custom resource with three replicas, waits until a Deployment with three replicas and the right owner reference exists, patches the custom resource to five replicas and waits for the Deployment to follow, sets the Deployment's status to ready to simulate the missing built-in controller, and waits for the custom resource's status to report five ready replicas. The test is deterministic because it waits on conditions, not on time.

A fourth example is the decision not to build one. A team wants to install a message queue with a standard configuration in many namespaces. A Helm chart with the values schema and a GitOps application set achieves it with no code to maintain. The team revisits the question only when they need automated failover and scaling logic that the chart cannot express.

## Related problems and ideas

This topic is the application-level counterpart of GitOps (T07): both are reconcilers, one for cluster configuration from Git and one for application state from custom resources. It builds on Pod design and probes (T01, T03), since the controller's children are ordinary workloads, and on packaging (T06), since the operator itself is usually delivered as a chart or a bundle. The administration course introduced CRDs and the operator concept; the security course covers the permissions model, admission control and the risks of powerful controllers. The observability topic (T09) applies to the operator's own metrics.

A concept to remember is that the status of a custom resource is an API. Other controllers, GitOps tools and humans will read it, so conditions, reasons and the observed generation deserve as much design as the spec.

## Active research

Active areas include declarative alternatives that generate APIs from schemas and expressions without code, validation and defaulting expressed in the API's own expression language so that webhooks become unnecessary, better test tooling and simulators for controllers, controllers that scale to very large object counts through sharding, support for server-side apply as the standard way to write children, and standards for operator packaging and discovery. The project layouts and library versions change between releases, so every version-specific command in a tutorial is "to verify" against the current kubebuilder book.

## Future direction

Expect more of the common cases to be handled by declarative composition and expression-based validation, with custom Go controllers reserved for logic that needs real code. The practices that last are the level-triggered mindset, idempotent reconciliation, careful use of finalizers and conditions, and a testing pyramid that includes the real API server.
