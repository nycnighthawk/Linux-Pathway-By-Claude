# Packaging an application: authoring, testing and releasing Helm charts

## Define the problem

A real application on Kubernetes is not one manifest. It is a Deployment, a Service, a ConfigMap, an Ingress or route, a ServiceAccount with its roles, perhaps a HorizontalPodAutoscaler and a PodDisruptionBudget, and a few Jobs, each with names and labels that must agree with each other. The same set has to be installed in several environments with different replica counts, hostnames, images and resource sizes, by people who did not write it, and later upgraded and rolled back. Copying a directory of YAML and editing it by hand for each environment does not scale: the copies drift, a change to one label requires edits in five files, and nobody can say which version of the application a cluster is running.

Two kinds of tool address this. Overlay tools such as Kustomize keep plain manifests and patch them per environment, so the base stays valid YAML. Templating and packaging tools such as Helm treat the manifests as templates with parameters, bundle them with metadata into a versioned archive called a chart, and track each installation as a release with a history. The Kubernetes glossary defines a Helm chart simply as a package of pre-configured Kubernetes resources that Helm manages [src: kubernetes-docs 5773ffac96345aeb], and the definition hides a lot: the chart is also a contract between the author, who decides what can be configured, and the operator, who decides what values to supply.

This slice teaches chart authoring and the engineering that makes charts trustworthy: structure, templating idioms, values and their schema, hooks, dependencies, testing at several levels, packaging and distribution, and the upgrade and rollback behaviour that operators rely on. It assumes the reader has used Helm to install a chart, which the administration course covered, and concentrates on writing one that others can depend on.

## History and approaches

Helm began in 2015 as a package manager for Kubernetes in the sense that Linux administrators understand: a way to install, upgrade and remove a bundle by name and version. The first version had a cluster-side component, Tiller, which executed releases with broad privileges and which became the project's most criticised design decision because it bypassed the cluster's role-based access control. Helm 3, released in 2019, removed Tiller and made the client talk to the API server with the user's own credentials, storing release records as Secrets in the release's namespace. It also introduced the version 2 chart format with dependencies declared in the chart metadata and added support for library charts, JSON schema validation for values, and, later, registries that store charts as OCI artifacts alongside container images. A new major version appeared at the end of 2025 with changes to the release mechanics and plugin system (to verify the release date and the list of changes against the project's announcement).

The alternatives shaped the field. Kustomize, integrated into kubectl, avoids templates by letting overlays patch a base, which keeps manifests valid and diffs readable, at the cost of weaker abstraction. Jsonnet and CUE and their derivatives give programming languages for configuration, with stronger typing and less string manipulation than YAML templates. Operators package behaviour, not just manifests. Platform tools such as Argo CD and Flux render Helm charts and Kustomize overlays in the cluster, so the choice of packaging is separate from the choice of delivery. Many organisations use Helm to consume third-party software and Kustomize or plain manifests for their own.

The history of failures in charts is long and mostly about templates. Text templating of a structured language means that indentation is part of the program, and many early charts produced invalid YAML for unexpected values. Charts exposed hundreds of values for every field of every object, which turned configuration into a second, worse copy of the Kubernetes API. Charts that generated passwords at each upgrade, with the random function, rotated credentials unexpectedly. Charts that put custom resource definitions in a templates directory broke upgrades, because Helm does not manage the CRD lifecycle the way people expect, and the project eventually recommended a dedicated directory with specific semantics. And charts that were installed from a repository without verification became a supply-chain exposure, which led to signing and provenance features and to OCI-based distribution with signature tooling.

Applying a Kubernetes manifest by hand works for one application and breaks for many, because the files differ slightly by environment. Templating tools appeared to fill that gap, and Helm became the most widespread, packaging manifests with defaults into a chart that is versioned and shared. Its competitors took other routes: Kustomize patches plain YAML with overlays, and some teams generate manifests from a programming language.

## Current state

**Chart structure.** A chart is a directory, or the archive made from it, with a metadata file, a default values file, a templates directory, an optional directory for custom resource definitions, an optional directory of dependency charts, an optional schema file for values, and documentation. The metadata file declares the API version of the chart format, the chart name, the chart version, which follows semantic versioning and identifies the packaging, and the application version, which is informational and identifies what is being deployed. The chart type is application by default, or library for charts that provide only named templates for others to include. Dependencies are listed with a name, version range and repository, and are resolved into a lock file and fetched into the charts directory. Conditions and tags on dependencies let the parent chart switch subcharts on and off by values.

**Templates.** Templates are written in the Go template language with the Sprig function library. The rendering context exposes the merged values, the release object with name, namespace and revision, the chart metadata, and the capabilities of the cluster. A handful of idioms cover most needs. A helpers file defines named templates for the chart's name, labels, selector labels and the service account name, so that every object uses the same strings; the project's conventions for labels, including the standard recommended labels, are part of what reviewers check. Conversion of a values subtree to YAML with a function, followed by an indentation function, avoids hand-formatting. The required function fails rendering with a message when a value is missing, which is better than rendering an invalid object. The include function, unlike the template action, returns a string that can be piped into other functions. The lookup function reads live cluster state during install and upgrade, which makes rendering nondeterministic and is empty during a dry run without a cluster, so it should be used sparingly and its limitations documented.

**Values and schema.** The default values file documents every option with comments and provides a working default. User values are layered with command-line files and individual overrides, and merged recursively for maps and replaced wholesale for lists. A schema file in JSON Schema format makes Helm validate the merged values at install, upgrade, lint and template time, which catches wrong types and missing required values early and doubles as machine-readable documentation. Good charts keep the value surface small: expose what an operator would reasonably change, offer an escape hatch for extra labels, annotations, environment variables and resources, and avoid exposing every field of the underlying objects.

**Hooks and tests.** An annotation turns a template into a hook that runs at a point in the release lifecycle: before or after install, upgrade, delete or rollback. Hooks are typically Jobs for migrations and checks. They are not part of the release's tracked resources in the usual sense, so their clean-up is governed by a deletion policy annotation, and a failing hook fails the operation. A hook with the test annotation is run by the test command after install and is the packaged form of a smoke test, such as a Pod that calls the application's health endpoint through its Service.

**CRDs.** Files in the dedicated CRD directory are installed before the templates on a first install, are not templated, and are not upgraded or deleted by Helm afterwards. This is a deliberate trade-off to avoid data loss, since deleting a definition deletes all its resources, and it means that CRD upgrades are a separate procedure: apply them with kubectl, with a separate chart, or with the delivery tool.

**Testing.** Testing has levels. Linting checks the chart's structure, the metadata, the templates for syntax and basic problems and the values against the schema. Rendering with the template command produces manifests that can be inspected, diffed against a stored expected output, or fed to schema validators for Kubernetes objects. Unit tests, usually through a plugin that lets tests assert on rendered documents for given values, check logic such as that an ingress appears only when enabled. Policy checks run the rendered output through admission-policy tools to confirm that security requirements hold. Integration tests install the chart into a throwaway cluster, run the packaged tests, upgrade from the previous released version to check upgrade paths and uninstall. The chart-testing tool automates detection of changed charts, version-bump checks, lint and install on a kind cluster, which is the standard pipeline for chart repositories. The administration course's lab environment for charts follows this progression.

**Packaging and distribution.** The package command creates a versioned archive; the index of a repository is a file that lists archives and their digests; OCI registries store charts as artifacts that are pushed and pulled by reference, with the same access control as images. Signing a chart with a provenance file proves who built it, and signing the OCI artifact with the same tools used for images links the chart into the supply-chain controls of the registry. Versioning discipline matters: the chart version must change whenever the chart changes, and a released version is immutable.

**Operations.** Installing with the upgrade command and the install flag makes deployment idempotent. The wait flag makes the command return when resources are ready, and the atomic flag rolls back on failure. Release state is stored as Secrets named for the release and revision, and the history limit controls how many are kept. Rollback re-applies an earlier revision's manifest as a new revision. Helm computes a three-way merge between the old manifest, the live state and the new manifest, so manual changes to a managed object may be kept or overwritten depending on the fields. A diff plugin that shows what an upgrade would change is a common safeguard.

### The generalised pattern: a chart is an interface

A good chart exposes a small, documented set of values and hides the rest. The generalised principle is that the values file is an API: it should be stable, validated against a schema, and changed only deliberately, with the chart version signalling compatibility. Tests apply at three levels: linting the templates, rendering them and checking the output, and installing into a test cluster to see that the release works.

## Assessment: the good, the bad and the ugly

**The good.** Helm gives a standard, widely understood unit of distribution, with versioning, dependencies, values with schema, lifecycle hooks and a release history. The ecosystem is large, so most third-party software is available as a chart. Charts can encode operational knowledge and sane defaults, and the testing tools make charts as testable as code.

**The bad.** Text templating of YAML is error-prone, and the language has limits that authors work around with ever more complex helpers. Charts accumulate values that nobody understands. The three-way merge has edge cases, and the release record in the cluster is a second source of truth beside Git. The CRD handling is surprising to newcomers. Version skew between the chart, the application and the cluster is common, and upgrade testing is rarely done. Many charts in the wild fail basic security checks by default, with root users, no resource limits and mutable tags.

**The ugly.** The worst incidents involve templates that quietly change identity or state. A change to a helper that alters a selector label makes an upgrade fail because selectors are immutable. A generated secret value that changes on each upgrade breaks every client of the application. A hook that is not idempotent runs a destructive migration twice. A default that points to the latest tag of an image makes two installs of the same chart version run different code. And a chart pulled from an unverified repository can contain anything, including privileged containers and cluster-wide permissions, which is why review of third-party charts is part of any production policy.

## Applications beyond this domain

The practices of charts apply to any configuration packaging. Linux distributions package software with metadata, dependencies, install and remove scripts and signatures, and the questions of versioning, repository trust and upgrade testing are the same. Infrastructure-as-code modules for cloud resources share the problem of exposing a small stable interface over a large underlying API. The idea of a values schema is the same as typed configuration in application frameworks. And the pipeline of lint, render, unit test, integration test, sign and publish is the standard shape of a software release.

## Examples

A first example is a chart for a web service. The chart has a Deployment, a Service, optionally an Ingress and a HorizontalPodAutoscaler, a service account and a test Pod. The helpers file defines the full name, the common labels and the selector labels. The default values file sets one replica, a pinned image tag taken from the chart's application version, resource requests and limits, a restricted security context, and switches for the optional objects. A schema file requires the image repository and rejects a negative replica count. The lint and template commands run in the build.

A second example is a unit test. A test file renders the chart with the ingress enabled and a host name and asserts that exactly one Ingress document exists with the right host and TLS secret, then renders it with the ingress disabled and asserts that none exists. A second test sets the autoscaler on and asserts that the Deployment omits the replica count so that the autoscaler controls it, a detail whose absence causes every upgrade to reset the replicas.

A third example is the release pipeline. On a tagged commit, the pipeline checks that the chart version has been bumped, lints, runs the unit tests, installs the previous released version into a kind cluster, upgrades to the new one, runs the packaged tests, packages and signs the chart, and pushes it to the registry. If the upgrade step fails, the release is blocked with the failing diff in the log.

A fourth example is recovery. An upgrade fails halfway because a hook Job fails. The operator reads the release history, sees the failed revision, checks the hook's logs, fixes the cause and runs the upgrade again. If the application is already damaged, the rollback command returns to the previous revision, and the operator confirms that the data migration, which the chart cannot undo, left the old version functional.

## Related problems and ideas

### Related

This topic depends on the configuration and security settings of T02, because a chart is largely a way to set them consistently, and on the rollout and probe topics, since the chart's defaults for strategy and probes become everyone's defaults. It leads directly to GitOps (T07), where a controller renders and applies the chart, and to operators (T08), which package behaviour that a chart cannot. In the administration course, Kustomize and Helm were compared and CRDs introduced; in the security course, signing and verifying charts is part of the supply chain.

A useful principle is that the values file is an API. Treat it as one: version it, document it, keep it small and stable, and break it only with a major version. Teams that apply that discipline find that most chart pain disappears.

### Opposing approaches

The opposing school says templating YAML with text substitution is fragile. Kustomize keeps manifests valid YAML and layers changes with patches, which is easier to read but less able to express conditions. Typed configuration languages, such as CUE or Jsonnet, offer stronger checking at the cost of another language to learn. Many teams use a combination: Helm for third-party software they consume, and overlays for their own manifests.

## Active research

Active areas include the new major version of Helm and its server-side apply, improved diffing and dependency handling, signing and attestation of charts as OCI artifacts, stronger typing of values and templates through schema generation, alternative configuration languages, and better CRD lifecycle management. Policy-as-code checks in CI for rendered output are becoming standard. Features and release numbers are "to verify" for the Helm version in use.

## Future direction

Expect charts to remain the dominant distribution format for third-party software while internal applications move to a mixture of Helm, Kustomize and typed configuration. Verification of provenance will become a default expectation, and upgrade testing will become part of every chart pipeline. The durable skills are writing small, schema-checked, secure-by-default charts, testing them at several levels, and releasing them as immutable, signed artifacts.
