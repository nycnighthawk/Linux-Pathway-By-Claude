# Designing a Pod: init containers, native sidecars and what they guarantee

## Define the problem

An application rarely runs alone. It needs its database schema to exist before it starts, a certificate fetched from a vault, a log shipper that reads its files, a proxy that handles its outbound calls, or a configuration reloader that signals it when a file changes. These helpers differ from the application in lifetime and in who owns them. Some must finish before the application begins, some must run for as long as the application does, and some must outlive it by a few seconds to drain a buffer. Packing them all into one container image would couple release cycles, privileges and failure modes whose concerns are unrelated to one another.

Kubernetes answers with the Pod: a group of containers that share a network namespace, can share volumes, and are scheduled, started and stopped as a unit. Within it, the documentation distinguishes the main application containers from helpers whose lifecycle differs, and offers two mechanisms for helpers. Init containers run to completion one after another before the application containers start. Sidecar containers, implemented as init containers with a restart policy of Always, start in order but then keep running beside the application and are stopped after it. The distinction sounds small and has large consequences for start-up reliability, for batch workloads, for graceful shutdown and for how the scheduler counts resources.

This slice teaches the mechanics precisely enough to predict what the kubelet will do. The goals are practical: choose between an init container and a sidecar for a given helper, write the manifest, compute the Pod's effective resource request, reason about start and termination order, and recognise the failure modes that follow from misusing either mechanism. It also introduces the older sidecar-by-convention pattern, because most existing manifests and most mesh and logging injectors still use it, and administrators need to read both forms.

## History and approaches

The multi-container Pod was part of Kubernetes from the first release, and the documentation presents it as the way to place tightly coupled processes together, with the co-located containers sharing storage and network [src: kubernetes-docs 9ff32fa374ee0083]. For some time the only way to run something before the application was to build it into the entrypoint script of the application image. That made images long-lived and brittle: a wait-for-the-database loop in a shell script could not be monitored, could not use a different image with different tools, and could not run with different privileges. Init containers appeared as a beta feature in 1.3 and reached stable status in 1.6, giving each preparation step its own image, its own resource settings and its own status in the Pod, and guaranteeing that they run to completion in order before any application container starts.

The sidecar pattern emerged without a platform feature. Teams added a second container to the Pod spec with the log agent, the proxy or the secrets refresher and relied on convention. Service meshes made the pattern ubiquitous by injecting a proxy container into every Pod through an admission webhook. The convention had known defects. Nothing ordered the start of the helper before the application, so an application that made a network call at start-up could do so before the proxy was ready, and the call failed. Nothing ordered the stop of the helper after the application, so a proxy that exited first cut off the application's last requests. And in Jobs and CronJobs, a long-running sidecar kept the Pod alive after the main container finished, so the Job never completed. Workarounds proliferated: shared files used as semaphores, shell loops, signals sent from the main container to its siblings, and wrapper binaries that exit when the main process does.

The platform response was the native sidecar feature. It was proposed as a small extension of init containers: an init container that declares a restart policy of Always starts in sequence like any init container, but the kubelet considers it started as soon as it is running (and, if it defines a startup probe, once that probe has succeeded) and does not wait for it to finish. It then keeps it running for the life of the Pod and restarts it if it fails. The feature appeared in alpha in 1.28, entered beta and on by default in 1.29, and was declared stable in 1.33 (to verify against the release notes of the version in use). The project's guide for adopting the feature shows how existing injectors and manifests can be converted and what changes in the Pod's behaviour [src: kubernetes-docs 8575940e0a862cd1].

Other platforms made different choices. Docker Compose expresses start order with dependency conditions on the health of other services, which is closer to the init idea but at the level of separate containers with their own lifecycles. Systemd units encode ordering with After and Requires directives and wait on readiness notification. The KubeVirt project, which runs virtual machines inside Pods, uses a hook sidecar mechanism that lets a helper container modify the virtual machine definition before it starts, an example of the sidecar idea applied to a platform component, not to an application [src: kubevirt-user-guide c366f15259e59932]. These comparisons are useful because they show the same three questions being answered everywhere: what must be ready first, what must keep running, and what must be stopped last.

## Current state

**Pod structure.** A Pod spec has three lists of containers: initContainers, containers and, added by the API at runtime, ephemeralContainers for debugging. All of them share the Pod's network namespace and may mount the same volumes. They do not share the process namespace unless the Pod sets the option to share it, they do not share the filesystem except through mounted volumes, and each has its own image, command, environment, resources, probes and security context. The Pod's phase summarises the state of all containers, and the status lists the state of each.

**Init containers.** Init containers run sequentially, each to completion with exit code zero, before the next starts. If one fails, the kubelet restarts it according to the Pod's restart policy: with Always or OnFailure the container is retried with exponential back-off, and with Never the Pod is marked failed. Application containers do not start until the last init container succeeds. The detailed behaviour page lists the reasons a Pod restarts its init sequence, including a restart of the sandbox, and notes that, because init containers can run more than once, they must be idempotent [src: kubernetes-docs 4eeb22f4d5d526ae]. Typical uses are waiting for a dependency, running a database migration, cloning a repository into a shared volume, rendering a configuration file from templates and secrets, setting kernel parameters in a privileged helper that the application itself must not be, and downloading a model or a dataset. Because they finish before the application starts, init containers can have much higher privileges and larger images than the application without that cost persisting while it runs, and a classic example computes a value and writes it to a shared volume or defines an environment variable through a file that the application reads [src: kubernetes-docs b04044eb39ea7169].

**Native sidecars.** A sidecar is declared in the initContainers list with restartPolicy set to Always. The startup sequence treats it as an init container: the kubelet starts it in its place in the list and moves on to the next entry once the container has started, or once its startup probe passes if it has one. Because the list is ordered, a proxy declared before a migration job is running when the job starts, and the job can use it. The sidecar then runs for the life of the Pod. Unlike an ordinary init container it may define liveness, readiness and startup probes; a readiness probe on a sidecar contributes to the readiness of the Pod. It is restarted independently if it exits, whatever the Pod's restart policy, which makes it suitable for helpers that must stay alive.

**Termination.** When the Pod is deleted, the application containers receive the termination signal and have the grace period to finish. Only after all of them have exited are the sidecars stopped, in the reverse order of their declaration. This guarantees that a proxy or log shipper is still alive while the application drains. For Jobs, the Pod is considered complete when the main containers finish; the kubelet then terminates the sidecars, and the Job completes, which removes the most common workaround. The documentation of the Pod lifecycle explains how container restarts, back-off and the termination sequence interact, and is the reference for the exact timers [src: kubernetes-docs 969d4f237f5b2acf].

**Resource accounting.** The scheduler computes the Pod's effective request from three terms: the sum of the requests of all application containers plus all native sidecars, and the largest request of any single ordinary init container, taking the larger of the two for each resource. Ordinary init containers do not add to the steady-state total because they have finished, but the largest of them determines the peak that must fit on the node during start-up. Sidecars, because they run alongside the application, are added to the sum, and a sidecar that starts before a later init container also counts against that init container's peak. The same arithmetic applies to limits and affects the quality-of-service class: for the Guaranteed class every container including init containers and sidecars must have equal requests and limits for CPU and memory.

**Patterns.** Three patterns recur. The sidecar extends the application with a function that runs next to it: a log shipper reading files from a shared volume, a proxy that terminates TLS or handles outbound traffic, a credentials refresher that writes a short-lived token to a shared memory-backed volume. The ambassador is a proxy that stands in for a remote service, so that the application talks to localhost. The adapter converts the application's output into a format the platform expects, for example translating an old metrics format. All three share a design test: if the helper has its own release cycle, its own resource needs or a different owner, it belongs in its own container, and if it must live and die with the application, it belongs in the same Pod.

**Boundaries.** A Pod is the unit of scheduling, so every container in it lands on the same node and scales together. A helper that several applications share, such as a cache, belongs in its own Deployment and Service or in a DaemonSet, not in each Pod. A helper that must run once per node rather than once per Pod is a DaemonSet. Two containers that must scale independently belong in different Pods, whatever their coupling in the code.

## Assessment: the good, the bad and the ugly

**The good.** Init containers give clean separation of preparation from execution with ordering the platform enforces and with separate images and privileges. Native sidecars fix the start order, the stop order and the Job-completion problems with a single field and no change to the helper's code. The scheduler's accounting is predictable and documented. The multi-container model keeps related processes in one unit with shared networking and storage, which simplifies configuration compared with distributed alternatives.

**The bad.** A Pod with many containers is harder to reason about: logs, resource usage and failures must be attributed per container, and kubectl commands need a container name. Sidecars add to every Pod's footprint, and a mesh proxy in each of hundreds of Pods is a visible cost. Init containers can make start-up slow, since they run in series and each pulls its image. The feature is new enough that older clusters, older injectors and some tools do not understand the restart policy on init containers, so manifests written for the native form fail on older versions, and tools that list containers by the old convention miss the sidecar entries.

**The ugly.** The sharpest problems are failure interactions. An init container that is not idempotent, for example a migration that inserts rows without a guard, causes damage when the kubelet restarts the sequence after the Pod sandbox is recreated. An init container that waits forever for a dependency leaves the Pod pending with a healthy-looking state, hiding an outage behind a string of retries. A sidecar with an overly strict liveness probe is restarted repeatedly, taking down the readiness of the whole Pod. A shared volume used as a semaphore between containers creates races that surface only under load. And resource accounting surprises people: a large init container for a one-off task raises the Pod's scheduling requirement for its whole life, so a Pod that needs a gigabyte at start-up reserves a gigabyte on the node forever unless the work is moved to a Job or a separate step.

## Applications beyond this domain

The same structure appears in process supervisors, in boot sequences and in deployment pipelines. A system boot has one-shot units that must finish before the target is reached and long-running services that must stay up, with ordering and readiness semantics expressed through unit dependencies, which is the same problem in different clothes. A deployment pipeline runs prerequisite steps in order and keeps supporting services alive during integration tests, a pattern that some CI systems model with service containers. Even in application code, the idea of a startup phase that must complete and a set of background tasks that must be shut down in reverse order of their start is a standard design for any server process.

## Examples

A first example is a web application that must not start until its database schema is current. The Pod has two init containers in order: the first waits until the database host accepts connections, using a small image with the network tools, and the second runs the migration tool from the application's own image with the credentials from a Secret. The application container starts only after both exit successfully. If the migration fails, the Pod stays in an init state and the event log shows the failing container, which is how an administrator finds the cause: the init status in the Pod description, then the log of that specific init container by name.

A second example is a log shipper. The application writes files to a shared volume of type emptyDir. A native sidecar mounts the same volume read-only and forwards the content. The sidecar is declared with the restart policy Always and a startup probe so that the application starts only after the shipper is ready. On deletion, the application drains first and the shipper stays alive until the application exits, so no final lines are lost. The effective request is the sum of the application and shipper requests, compared with the largest init request, and the manifest sets the shipper's memory limit conservatively because it runs for the life of the Pod.

A third example is a Job that needs a proxy to reach a database. With a convention-based sidecar, the Job never finishes because the proxy never exits, and teams add a shell script that kills the proxy at the end. With a native sidecar, the Job completes when the main container does. Converting means moving the proxy from the containers list to the init list with the restart policy and testing on a cluster of a version that supports the feature.

A fourth example is the migration of an injected mesh proxy. The platform team updates the injector to produce the native form, tests on a staging cluster with a Job and a Deployment, verifies shutdown ordering by watching the container exit times, and rolls the change out namespace by namespace. The rollback is switching the injector back, and a version check in the injector prevents the native form from reaching clusters that do not support it.

## Related problems and ideas

This topic is the base for the rest of the course. Configuration and security settings (T02) apply per container, so a sidecar can have a stricter security context than the application. Probes (T03) are the language in which a container reports its state, including the startup probe that gates sidecar ordering. Rollouts (T04) depend on readiness, which now includes sidecars. Jobs (T05) are where the sidecar completion problem was most painful. Observability (T09) is delivered in large part by sidecar agents or, increasingly, by node-level agents that avoid a sidecar in every Pod. In the networking course, mesh data planes that remove the sidecar entirely are the logical end of the same cost discussion.

An idea to hold on to is the principle of the smallest coupling that works: the helper goes in the Pod only if it must share the application's network, storage or fate. Everything else is better as its own workload, because it can then be scaled, upgraded and debugged on its own.

## Active research

Active areas include refinements to sidecar lifecycle (better control over termination ordering and over how long sidecars wait for the application), resource management for Pods that vary over their life (in-place resizing and the accounting of init containers in it), container-level restart rules that allow some containers to restart independently of the Pod policy, standard ways of declaring that a Pod's start depends on other Pods, and alternatives to sidecars for platform functions, such as node-level agents and eBPF. The status of each of these features changes by release and is "to verify" for the cluster in use.

## Future direction

Expect native sidecars to become the default form for injected helpers and for older conventions to fade out as the supported version window moves past 1.33. Administrators should audit their manifests and injectors for convention-based sidecars, learn to read the effective-request arithmetic, and make init containers idempotent and bounded in time as a matter of habit.
