# Running work that finishes: Jobs, CronJobs and the guarantees they do not give

## Define the problem

Much of what a system does is not a service. It is a database migration, a nightly report, a batch of thumbnails to render, a backup, a data import or a clean-up of old records. These tasks start, run for a while and end, and the platform must answer questions that a long-running service never raises. How many times must it run to count as done? What if it fails halfway: retry, give up, tell someone? What if two copies run at once and corrupt each other's output? What if the node it runs on disappears? What if it is supposed to run every night and the cluster was down for an hour at the scheduled time? And what becomes of the Pods, logs and objects it leaves behind?

A Deployment is the wrong tool for this, because it would restart a finished container forever. A bare Pod is also wrong, because nothing reschedules it if its node fails and nothing counts its completions. Kubernetes provides two controllers. The Job runs Pods until a specified number of them succeed, retrying failures within limits. The CronJob creates Jobs on a schedule written in the format that Unix administrators have used for decades. Together they cover a large share of batch needs, and a few fields in each decide whether a batch system is reliable or a source of silent data errors.

This slice explains how the two controllers work, the fields that govern retries, parallelism, deadlines and clean-up, the semantics of scheduling, including the guarantee that is explicitly not provided, and the practices that make batch work safe: idempotency, bounded runtime, visible failure and appropriate use of the older Unix tools when the cluster is not the right place. The learning goal is to write a Job or CronJob that does what the owner expects and fails loudly when it cannot.

## History and approaches

Batch scheduling predates containers by half a century. The Unix cron daemon reads a table of five time fields and a command, and runs the command whenever the clock matches; the cron(8) manual page describes the daemon's behaviour, including how it treats clock changes and what it does with missed runs after downtime [src: man-pages 8a908ae96b1f5f15]. Variants added jitter, random delays, run-after-boot rules and, in systemd, timers that can catch up on missed runs and that couple a schedule to a service unit with its own resource and logging controls; the Arch wiki's overview of timer units shows calendar and monotonic forms [src: archwiki 431d4715c41edfbb]. HPC schedulers on clusters of computers took another path, with queues, job arrays and fair-share allocation, which is the lineage of the Kubernetes batch ecosystem projects.

Kubernetes added the Job early, built on the same Pod machinery as everything else, and added the CronJob in a beta form that the project later replaced with a rewritten controller. The first CronJob controller ran as a periodic loop over all objects and had performance and correctness problems at scale; the second, an event-driven controller using a work queue, became the default in 1.21 and the original was removed. In the same period the Job gained features that matter to real batch work. Indexed completion mode gave each Pod a stable index, so that a fixed set of tasks can be spread across Pods without an external queue. The per-index back-off limit made a failing shard not consume the retry budget of the others. The Pod failure policy let the Job react to specific exit codes or Pod conditions, so a failure caused by a node being drained could be retried without counting against the limit while a failure caused by a bug could stop the Job at once. Suspending a Job allowed external queueing systems to admit work when capacity existed, which is the hook used by batch queueing controllers. Time zones for CronJobs arrived as a stable feature in 1.27, after a long period in which schedules were interpreted in the time zone of the controller manager. The exact stage of each feature depends on the release and is "to verify" for the cluster in use.

Failures in practice have a pattern. A CronJob scheduled every minute that takes five minutes piles up Pods until the cluster runs out of resources. A Job without a back-off limit, in the early releases where the default was effectively unbounded, retried a bug forever. Finished Jobs accumulated by the thousand in clusters that never cleaned them, slowing the API server and the controller's own reconciliation. A nightly job that ran twice, because the controller was restarted at the moment of scheduling, wrote duplicate rows, and the team discovered that the documentation had said at least once all along. And a long-running Job whose node was drained was restarted from scratch because nothing had saved progress.

Batch work predates containers, and cron is its oldest scheduler. Running jobs on a cluster adds new questions: where it runs, what happens if a node fails midway, how many copies may run, and how to clean up. The Job resource answers the first three by tracking completions and retrying failed Pods, and the CronJob adds a schedule on top. Over time the platform added indexed Jobs, a failure policy and time-to-live cleanup, each of which closes a gap users met in production.

## Current state

**Job spec.** A Job has a Pod template whose restart policy must be Never or OnFailure; Always is not allowed, because a Job's containers are expected to end. The completions field is the number of successful Pods required, and the parallelism field is the number allowed to run at once. If neither is set the Job needs one success. If only parallelism is set, the Job is a work queue in which Pods themselves decide when work is finished, and if completions is set the Job counts. Indexed mode, which sets a completion index in each Pod's environment and annotation, supports fixed task partitioning. The back-off limit, six by default, is the number of failures tolerated before the Job is marked failed, with exponential delay between retries capped at six minutes. The active deadline puts an upper bound on total run time regardless of retries, and when it passes, running Pods are terminated and the Job fails.

**Failure semantics.** With the restart policy OnFailure the kubelet restarts the container in the same Pod, which preserves local files in emptyDir volumes but counts toward the Pod's restart count; with Never, a failed Pod stays for inspection and the Job controller creates a new Pod, which is cleaner for debugging and uses more objects. The Pod failure policy has rules that match on container exit codes or on Pod condition types and take actions: fail the Job immediately, ignore the failure so it does not count toward the back-off limit, count it normally, or fail the index. This allows a precise policy: retry on disruption, stop on a known permanent error code.

**Clean-up.** Finished Jobs and their Pods remain until deleted. The time-to-live setting for finished Jobs tells a controller to delete the Job and its Pods a number of seconds after it finishes, which prevents accumulation while leaving time to read logs [src: kubernetes-docs 1412afbf4c0694ae]. CronJobs have their own history limits for successful and failed Jobs, by default three and one.

**CronJob spec.** A CronJob has a schedule, an optional time zone, a Job template, a concurrency policy, a starting deadline, history limits and a suspend flag. The schedule uses five fields, namely minutes, hours, the day of the month, the month and the weekday, with ranges, lists and steps, and shortcuts for hourly, daily and so on. When both the day-of-month and the day-of-week fields are restricted, the rule in classic cron is that either matching triggers the job, which surprises people expecting both. The time zone field takes a name from the standard database, and its absence means the controller's local zone, so explicit zones are recommended; daylight saving transitions can skip or repeat local times, and jobs scheduled in the hour that does not exist or repeats need thought.

**Concurrency and missed runs.** The concurrency policy has three values. Allow starts a new Job even if the previous one is still running, which is the default. Forbid skips the new run if the previous is active. Replace deletes the running Job and starts the new one. A skipped run still counts as a missed schedule. The starting deadline sets how late a Job may start, measured from its scheduled time; if the controller was down or busy past the deadline, that run is skipped. If a large number of schedules were missed, the controller refuses to start the CronJob and records an event rather than starting a flood of catch-up runs; the documentation lists the details under the limitations of the CronJob controller, which also states that a Job might be created twice or not at all in some conditions and that Jobs should therefore be idempotent [src: kubernetes-docs ad2a33a98ce5f842]. The concurrency policy page describes how the three values interact with the deadline [src: kubernetes-docs b3178c2a0165079e].

**What CronJobs promise.** The controller aims to create about one Job per schedule time, and the guarantee is at-least-once in practice with rare duplicate and rare missed runs. There is no exactly-once. Tasks must therefore tolerate duplicates, either by being idempotent or by taking a lock or lease, and must tolerate missed runs, either by being able to catch up on the next one or by an alert that notices the absence.

**Observability.** Success and failure appear in the Job's status, in the events and in the Pods. A failing CronJob is easy to overlook because nothing is red on a dashboard unless someone alerts on it. The common practice is an alert on the condition of a failed Job, on the time since the last success of a CronJob, and on a count of Jobs that are older than their expected run time. Metrics exporters for cluster state expose these.

**When not to use a CronJob.** For work that needs sub-minute precision, exactly-once semantics, dependencies between steps, long-running state or complex retries, a workflow engine or a queue-based worker is the better fit. For work tied to a node, such as rotating that node's logs, a DaemonSet with its own timer or the operating system's cron is simpler. The Kubernetes control plane is not a good place for a million tiny scheduled tasks.

### The generalised pattern: schedule, work and state kept apart

A CronJob decides when, a Job decides how many successes are needed and how many failures are tolerated, and the program decides what to do. State, such as which records are already processed, lives outside the Pod, because Pods are disposable. Jobs must therefore be idempotent, since the platform guarantees at-least-once execution, and concurrency policy decides what happens when a run overlaps the next.

## Assessment: the good, the bad and the ugly

**The good.** The Job abstraction solves retries, parallelism and completion counting with declarative fields and standard Pod semantics. The failure policy and index features make real batch pipelines possible without extra systems. The CronJob brings cron's familiar format into the cluster with resource isolation, per-run logs and the same security model as other workloads. Time zones and history limits remove most of the old surprises.

**The bad.** At-least-once is a weak guarantee for work that mutates state. The scheduling resolution is minutes and the start time has some jitter. The API server stores every Job and Pod, so frequent schedules create object churn. The cron syntax is compact and error-prone, with the day-of-month and day-of-week rule and time-zone effects. Failed CronJobs are silent by default. And the batch ecosystem is fragmented: queueing, fair-share and gang scheduling need add-on projects with their own APIs.

**The ugly.** The sharpest failures are the silent ones. A CronJob whose last run succeeded months ago and has since failed to be created, because the controller refused after too many missed schedules, and nobody noticed. A Job that exits zero after a handled error, so the system records success. A concurrency policy of Allow plus a slow database producing an ever-growing pile of overlapping runs that all slow the database further. A cleanup job with the wrong selector deleting live data. And clock and time-zone errors: a schedule intended in one zone interpreted in another, shifting a backup into peak traffic.

## Applications beyond this domain

Scheduled and batch work is universal. Every operating system has a scheduler for periodic tasks, and the same design questions, overlap, missed runs, logging and failure notification, are answered by systemd timers, anacron, cloud schedulers and workflow engines. The at-least-once plus idempotence principle is the foundation of reliable message processing and of distributed transactions generally. Index-partitioned parallelism is the same idea as job arrays in HPC schedulers. Even a developer's laptop benefits: the practices of running a task under a lock, bounding its runtime and sending failures somewhere visible are good advice for any cron table.

## Examples

A first example is a database migration run as a Job from the deployment pipeline. The Job has one completion, a back-off limit of two, an active deadline of ten minutes and a time-to-live of an hour after finishing. The pipeline waits for the Job's completion condition with a timeout. If the Job fails, the Pod's logs are still available for the hour, and the pipeline stops before deploying the application.

A second example is a nightly report. The CronJob uses an explicit time zone, a schedule at two in the morning on weekdays, the Forbid concurrency policy, a starting deadline of one hour, history limits of three successes and three failures, and a Job template with a back-off limit of three. The program writes its output to an object store using a file name derived from the scheduled date, so a duplicate run overwrites the same file. An alert fires if no successful Job completed in the last twenty-six hours.

A third example is a batch of image conversions. An indexed Job with a hundred completions and a parallelism of ten gives each Pod an index that selects a slice of the input list. A Pod failure policy ignores failures caused by node disruption and fails the Job immediately on a specific exit code that the converter uses for corrupt input. The team monitors the number of succeeded and failed indexes.

A fourth example is a diagnosis. A CronJob that should run every five minutes shows no recent Jobs. The events say it has missed too many start times. The controller had been unable to run for a period because of a control-plane outage, and the schedule is frequent. The fix is a starting deadline that bounds the catch-up window, so that after an outage the controller starts the latest run and skips the earlier ones, and an alert on the age of the last success.

## Related problems and ideas

### Related

This topic builds on Pod design (T01), where sidecars in Jobs were the motivating problem, and on probes and exit codes (T03), which determine what failure looks like to the controller. Resource requests (T02) matter more for batch than for services, because bursts of Pods can starve the cluster. The delivery topics (T06, T07) describe how Jobs, such as migrations and hooks, are sequenced within a release. The observability topic (T09) provides the metrics for alerts on missed and failed runs. In administration, quotas and priority classes govern how batch work coexists with services, and in the networking course, the same questions about retries and idempotency apply to calls between services.

A general idea is the separation of schedule, work and state: the CronJob decides when, the Job decides how many times, and the program decides what, with state kept outside the Pod. When these are kept separate, each can be changed and tested alone, and the system becomes easy to reason about when something goes wrong.

### Opposing approaches

The opposing approaches use dedicated systems. Workflow engines, such as Argo Workflows or Airflow, provide dependencies between steps, retries with state and visibility that plain Jobs lack. Queues with worker Deployments give continuous processing with back-pressure, and are a better fit for work that arrives at random than for work scheduled by the clock. Cron on a single host remains valid for small, non-critical tasks. The Job suits a bounded task with a clear end.

## Active research

Work in this area includes queueing and admission for batch workloads, with a Kubernetes-native job queue that holds Jobs suspended until quota is available, gang scheduling for tightly coupled parallel jobs, improvements to Job success policies that let a Job finish when a subset of indexes succeeds, better support for restarts that preserve progress, and tools for expressing workflows as graphs. The stable features listed above have different stages across releases, and any claim about the stage of a given field is "to verify".

## Future direction

Expect the Job API to grow toward richer completion and failure rules, queueing to become a standard layer for shared clusters, and CronJob users to rely more on explicit time zones and deadlines. The durable practices are idempotent tasks, bounded run time, automatic clean-up, alerting on absence of success and not only on failure, and honest recognition of what the platform does and does not promise.
