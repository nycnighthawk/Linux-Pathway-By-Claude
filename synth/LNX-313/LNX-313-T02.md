# Configuring a workload safely: ConfigMaps, Secrets, security contexts and resource limits

## Define the problem

The same container image must run in development, in staging and in several production clusters, with different database addresses, different credentials, different feature switches and different amounts of CPU and memory. Rebuilding the image per environment destroys the main promise of containers, which is that what was tested is what runs. The twelve-factor approach states the alternative: keep configuration outside the build and inject it at run time. Kubernetes provides objects for this, ConfigMaps for ordinary settings and Secrets for sensitive ones, and several ways to deliver them to a container: environment variables, command-line arguments, files in a mounted volume, or the API itself.

Each delivery method has behaviour that surprises people. An environment variable is fixed at container start, so a changed ConfigMap does not reach a running Pod; a mounted file is updated in place after a delay, but only if the application rereads it and only if it was not mounted through a path that blocks updates. A Secret is base64-encoded, which is not encryption, and by default is stored unencrypted in the cluster's key-value store, readable by anyone with the right to read Secrets in that namespace and by anyone with access to etcd backups. A security context can make a container run as root with every kernel capability or as an unprivileged user with none, and the difference between the two is the difference between a minor bug and a node compromise. Resource requests and limits decide where a Pod is scheduled, how much CPU it gets under contention, and which Pods are killed first when memory runs out.

This slice teaches the four topics together because they interact in the Pod specification and fail together in production. The learning goals are to choose the right delivery for each kind of setting, to understand how Secrets are stored and exposed and what to do about it, to write a security context that satisfies the restricted policy, and to set requests and limits that give the intended quality-of-service class without throttling the application unnecessarily.

## History and approaches

Early container deployments baked configuration into images or passed it through environment variables on the command line. Kubernetes added the Secret and ConfigMap resources in its first releases, with the Secret designed as a separate type so that access could be restricted by authorisation rules and so that the data could be kept in memory-backed volumes on the node instead of on disk. The distinction was about handling, not about cryptography: for years a Secret was stored in etcd as plain base64, and the project added encryption at rest as an optional feature of the API server, with envelope encryption through an external key management service following later. The documentation now carries an extensive list of good practices around Secrets, which exists because the default behaviour is easy to misuse.

External secret stores formed a parallel line of development. Vault, cloud secret managers and sealed encrypted manifests solve two different problems: where the authoritative secret lives and how it reaches the cluster. Controllers such as the External Secrets Operator synchronise values from a store into native Secrets, the Secrets Store CSI driver mounts them directly as files without creating a Secret object, and Sealed Secrets lets a team commit an encrypted manifest to Git that only the cluster can decrypt. The Docker ecosystem went through a similar progression, from environment variables to a secret mechanism that mounts values as files in a memory filesystem, with documentation that explains why files are preferred to variables [src: docker-docs 01c7f3acaeb89e80]. The common lesson is that environment variables leak: they appear in process listings, in crash dumps, in child processes, and in debug endpoints, while a file with restricted permissions can be controlled.

Security contexts grew out of Docker's own defaults. Containers started as root with a reduced set of capabilities and a default seccomp profile, which was safer than a plain process but gave an attacker who escaped the container root on the host. Kubernetes added fields for the user and group, for forbidding privilege escalation, for dropping capabilities, for a read-only root filesystem, for a seccomp profile and for SELinux and AppArmor labels. The Pod Security admission controller replaced the older PodSecurityPolicy API and defined three levels, privileged, baseline and restricted, which are the shared vocabulary for what a safe Pod looks like. The projected-volume documentation, for example, spells out how the security context interacts with file ownership of the mounted data [src: kubernetes-docs c0ece472ab3ca195].

Resource management began with simple requests and limits and acquired layers over the years. The kubelet maps requests to cgroup CPU shares and limits to CPU quota and memory limits, and assigns a quality-of-service class from the combination, which determines eviction order. The cgroup version changes details: version two adds memory pressure information and allows features such as memory throttling, and the project's handling of the older version has been moving toward deprecation (to verify the status in the version in use). Namespace-level controls, resource quotas and limit ranges, were added so that administrators could cap what a team may request and supply defaults for Pods that specify nothing; the quota documentation explains how to view and set them and how they interact with Pod creation [src: kubernetes-docs 6a6ea027945c909b].

Twelve-factor guidance of the early 2010s told developers to keep configuration out of the code and in the environment. Containers made that rule enforceable, since the image is fixed and the settings arrive at run time. Kubernetes responded with ConfigMaps and Secrets as named objects, and later added security contexts and admission rules, because separating configuration from images also separated the question of who may do what. Resource limits arrived from the other direction, as the scheduler's need to know how much each container might use.

## Current state

**ConfigMaps.** A ConfigMap holds key-value data, either as strings or, under a separate field, as binary data, with a size limit of one mebibyte. A Pod consumes it in four ways: as environment variables from selected keys or from the whole map, as command-line arguments through variable expansion, as files in a volume where each key becomes a file, or by reading the object through the API. Environment variables and arguments are resolved when the container starts. A volume mount of the whole ConfigMap is refreshed by the kubelet within a sync period, using an atomic symlink swap, but a mount that uses a subPath does not receive updates, which is a frequent surprise. Marking the ConfigMap immutable prevents changes, reduces load on the API server, and forces teams into the safer pattern of creating a new object and rolling the workload.

**Secrets.** A Secret has a type that determines the keys it must contain: the opaque default, a TLS pair, a Docker registry credential, a basic-authentication pair, an SSH key or a service-account token. Values are base64-encoded in the API, which only makes binary data representable. The security properties come from elsewhere. Access is controlled by authorisation: whoever can get or list Secrets in a namespace can read them, and whoever can create a Pod in the namespace can mount any Secret in it, which means that Pod creation rights are effectively Secret read rights. Encryption at rest is configured on the API server, with a provider chain that can use a local key or an external KMS; a cluster without it stores values in the clear in etcd and in every etcd backup. On the node, volume-mounted Secrets are held in a memory-backed filesystem and removed when the Pod goes away, whereas environment variables are copied into the process.

**Good practice for Secrets.** The consolidated advice is to enable encryption at rest, restrict access with narrow roles and namespaces, avoid listing and watching rights, prefer mounted files with restrictive modes to environment variables, rotate credentials and design applications to reread them, use short-lived credentials from an external identity system where possible, and never place real secrets in Git in plain form. For GitOps the choice is between encrypting values in the repository, referencing an external store, and generating secrets in the cluster.

**Security contexts.** A security context can be set for the Pod, which applies to all its containers, and for each container, which overrides it. The fields that matter most are the user and group IDs the process runs as, a flag requiring a non-root user, a group for volume ownership, a flag that forbids gaining privileges through set-user-ID binaries, the capability list to add and drop, the read-only root filesystem, the seccomp profile type, and the privileged flag. The restricted policy requires that containers run as non-root, disallow privilege escalation, drop all capabilities (adding back only the one for binding low ports), use the runtime's default seccomp profile or a custom one, and that volume types be limited to a safe set. The baseline policy forbids the worst settings such as privileged mode and host namespaces. Enforcement is by labels on the namespace that select the level and the mode: enforce, audit or warn. A migration path therefore starts in warn and audit modes to see what would fail.

**Resource requests and limits.** The request is what the scheduler reserves and what the container is guaranteed under contention; the limit is the ceiling. For CPU the limit is enforced by throttling: when the container uses its quota in a period it waits for the next one, which shows up as latency spikes in applications that burst, so many teams set CPU requests and omit CPU limits for latency-sensitive services. For memory the limit is enforced by killing: when a container exceeds it the kernel's out-of-memory killer terminates it, and the exit reason is visible in the status. The quality-of-service class is derived: Guaranteed when every container has equal requests and limits for CPU and memory, Burstable when at least one container has a request or a limit, and BestEffort when none has. Under node memory pressure the kubelet evicts BestEffort first, then Burstable Pods that exceed their requests, and Guaranteed last. Pods that specify no requests are risky neighbours, and a limit range in the namespace can supply defaults.

**Namespace controls.** A resource quota caps the total of requests, limits, object counts and storage in a namespace; once a quota on compute is present, Pods that do not specify the constrained resources are rejected, so quotas and default limit ranges are used together. A limit range sets default requests and limits and minimum and maximum values per container.

**Debugging resource and configuration problems.** The Pod description shows the last state and exit reason of each container, including out-of-memory kills. The events list scheduling failures with the resource that did not fit. For configuration, the container's environment and mounted files can be inspected with exec, and a missing ConfigMap or Secret key keeps the container in a creating state with an event naming the object. The debugging guide's example of a Pending Pod walks through reading the scheduler's message about insufficient resources [src: kubernetes-docs c02e6bb6a0f61efd].

### The generalised pattern: declare what the workload needs and may do

Every item in this topic is a statement that the platform enforces: settings the container reads, privileges it may hold, resources it may consume. The generalised habit is to start from the narrowest grant, which means a non-root user, a read-only filesystem, dropped capabilities and limits just above observed use, and widen it only with a reason. Settings should be named objects, versioned with the release, so that a change in behaviour has a matching change in the repository.

## Assessment: the good, the bad and the ugly

**The good.** The configuration objects keep images environment-independent and fit GitOps. Typed Secrets make intent explicit, volume mounts keep values off disk on the node, and the authorisation model allows narrow access. The security context fields give a precise vocabulary for least privilege, and Pod Security admission gives a cluster-wide, label-driven way to enforce it with a staged rollout. Requests and limits give both the scheduler and the kernel what they need to make fair decisions.

**The bad.** A ConfigMap change does not roll the workload, so applications run with stale values until restarted unless a tool computes a checksum annotation or the object is renamed with each change. Secrets are easy to misread as protected: base64 is encoding, and the default storage is unencrypted. The security context has many fields with non-obvious interactions, such as the order of user, group and filesystem group, the need for writable directories when the root filesystem is read-only, and images that assume root. Limits are often set by guesswork, and CPU limits throttle in ways that are hard to diagnose.

**The ugly.** The sharpest problems are combinations. A Secret mounted into a Pod with a broad service account that is also allowed to read all Secrets turns one compromised container into a namespace-wide credential leak. A privileged container with a mounted host path is a root shell on the node. A memory limit set below the application's real working set produces restart loops that look like crashes of the application. A quota without defaults silently blocks every Pod that omits limits, and the error message appears in the controller's events, not where the person who ran the command is looking. And environment variables from a ConfigMap that is deleted before the Pod restarts cause the container to fail at start with a message about a missing key, which turns a configuration clean-up into an outage.

## Applications beyond this domain

The same questions arise wherever software is deployed. Configuration management tools distinguish settings from secrets and encrypt the latter in the repository. Systemd offers credentials loaded from files, private temporary directories and a long list of sandboxing options that mirror the security context fields, such as dropping capabilities, restricting system calls and read-only filesystems. The least-privilege principle behind the restricted policy is the same as in the Linux hardening guides for services. Resource controls map directly onto control groups, whether the manager is Kubernetes, systemd or a container engine, so what an administrator learns here about shares, quotas and out-of-memory behaviour applies to every Linux workload.

## Examples

A first example is a web application with a settings file. The administrator creates a ConfigMap from a file, mounts it at the application's configuration directory as a volume without a subPath, and adds a checksum of the ConfigMap as an annotation on the Pod template, so that an update changes the template and rolls the Deployment. The rollout is visible in the revision history, and a rollback restores the previous settings with the previous Pods, which a live-editing approach would not.

A second example is a database password. The application reads it from a file at a fixed path. A Secret of the opaque type is mounted as a volume with a mode that only the application's group may read, and the container runs as a non-root user with a group that matches the volume's ownership setting. The service account of the Pod has no permission to read Secrets through the API. Rotation is performed by updating the value in the external store, letting the synchronisation controller update the Secret, and relying on the application to reread the file on a signal or on a timer.

A third example is making a legacy image pass the restricted policy. The namespace is labelled with audit and warn modes for the restricted level, and the warnings list the failing fields: runs as root, allows privilege escalation, no seccomp profile, capabilities not dropped. The team fixes the image to run as a numeric non-root user, sets the Pod's security context with the runtime default seccomp profile, drops all capabilities, forbids escalation, mounts writable directories as emptyDir volumes, and sets the root filesystem to read-only. After a clean audit period the label is changed to enforce.

A fourth example is sizing. A service shows high tail latency under load, and its metrics show CPU throttling in a large fraction of periods even though average usage is well under the limit. The administrator keeps the CPU request at the observed typical usage, removes the CPU limit for this service, keeps the memory request equal to the memory limit at the observed peak plus a margin, and verifies that tail latency improves and that the Pod's class is Burstable by design. For a batch workload that must not interfere with neighbours, the team keeps both limits and accepts the throttling.

## Related problems and ideas

### Related

This topic connects forward and backward. Pod design (T01) decides which container gets which context. Probes (T03) interact with limits, since a probe that times out because the container is throttled restarts a healthy application. Rollouts (T04) depend on configuration changes triggering new ReplicaSets. Helm and GitOps (T06, T07) are where values and secrets are managed in practice. The security course returns to admission control, workload identity, encryption at rest and supply-chain issues in depth, and the administration course covers quotas and autoscaling. In the Linux fundamentals, capabilities, namespaces, seccomp and control groups are the kernel features that these fields expose.

A general idea is that configuration is code with a different release cadence. It should be versioned, reviewed and rolled out gradually, and an immutable, named configuration object per release makes that natural. Treating a ConfigMap as a mutable file on a server brings back the problems that containers were meant to remove.

### Opposing approaches

The opposing positions concern how much the platform should police. Some teams prefer broad defaults and rely on image scanning and runtime detection, accepting more privilege for less friction. Others enforce strict admission policies that reject any Pod not meeting a baseline, which raises security and slows teams that must justify exceptions. Secrets raise a parallel debate: native Secrets are encoded, not encrypted, by default, so many sites move them to an external store and reference them by name. Each stance trades convenience against assurance, and a baseline enforced by policy is the common compromise.

## Active research

Development in this area includes volume-based secret delivery without a Secret object, short-lived projected tokens bound to a Pod and an audience, user namespaces for Pods so that root in the container maps to an unprivileged user on the node, in-place resizing of resource requests without restarting the container, memory quality-of-service improvements on cgroup version two, and policy as code with admission policies written in the API's expression language. Several of these are at different maturity levels in different releases and are "to verify" before use.

## Future direction

Expect the restricted level to become the practical default, user namespaces to make root-in-container less dangerous, external identity to replace long-lived stored credentials, and resource settings to be adjusted automatically from observed usage. For administrators the durable habits are to keep configuration out of images, to treat Secrets as sensitive data that needs encryption and narrow access, to run as non-root with dropped capabilities, and to base requests and limits on measurement, not habit.
