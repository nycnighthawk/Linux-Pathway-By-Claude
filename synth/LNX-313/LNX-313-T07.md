# Letting Git drive the cluster: GitOps with Argo CD and Flux

## Define the problem

Delivering to Kubernetes by running kubectl or helm from a pipeline has three weaknesses. The pipeline needs credentials with write access to every target cluster, which concentrates risk in the CI system. The state of the cluster is whatever the last commands left, so a manual change by an operator, a failed half-applied release or a deleted object goes unnoticed until it causes an incident. And nobody can answer, from a single place, what should be running right now, who changed it and why, or how to rebuild the cluster after a disaster.

GitOps is the answer that moved from a blog post to an industry practice. The desired state of the system is written declaratively and stored in a version-controlled repository. Software agents inside or beside the cluster pull that state, apply it, and keep comparing the live system with it, correcting or reporting any difference. The community behind it published four principles under the name OpenGitOps: the system is described declaratively, the desired state is versioned and immutable, approved changes are pulled automatically, and software agents continuously reconcile actual state with the desired state. Each principle removes one of the weaknesses above. Pull-based agents mean the cluster holds its own credentials and no external system needs write access. A repository history gives the audit log and the rollback. Continuous reconciliation turns drift from a hidden condition into a visible one.

This slice covers the two dominant open-source implementations, Argo CD and Flux, how they model applications and sources, how they handle ordering, drift, secrets and multiple clusters or tenants, how repositories are laid out, and what GitOps does and does not give. The learning goals are to write the resources that connect a repository to a cluster, to choose between the two tools for a given team, to design a repository layout that supports promotion across environments, and to recognise the failure modes of reconciliation.

## History and approaches

The term came from a 2017 article by the team at Weaveworks, who described running operations through pull requests, with an operator in the cluster applying the merged state. That team built Flux as the first controller of the kind. In parallel, engineers at Intuit created Argo CD, with a stronger focus on a user interface and application-level views. The two projects were both donated to the CNCF and both reached graduated status, and in 2019 the teams announced a plan to merge the projects that did not come to completion; each continued separately, and Flux was rebuilt as a set of composable controllers in a second major version known as the GitOps Toolkit. When Weaveworks ceased operations in 2024 the project remained alive under community and vendor maintenance, which is a useful reminder that a delivery tool is itself a dependency with a lifecycle.

The design difference between the tools is real. Argo CD is an application-centred system with a server, a repository component that renders manifests and a controller that compares them with live state. Its central resource is the Application, which names a source in Git, a Helm repository or an OCI registry, a path and revision, and a destination cluster and namespace. It offers a web interface, a command line, single sign-on and a role model, and it can manage many clusters from one control plane. Flux is a toolkit of Kubernetes controllers, each with its own custom resources: one fetches sources from Git, Helm repositories, OCI repositories or buckets, one applies Kustomize overlays, one installs and upgrades Helm releases, one sends and receives notifications, and optional ones update image tags in Git. It has no built-in interface and treats the cluster API as its interface. Teams that want a dashboard and a clear central view lean to Argo CD; teams that want building blocks that feel like part of Kubernetes and a strong multi-tenancy story lean to Flux, and a number of organisations run both for different purposes.

The history of practices is also instructive. Early adopters put application source and deployment manifests in one repository, which meant that every code change and every deployment change appeared in the same history, and promotion by branches produced merge conflicts that no one could review. The community converged on separating the application repository, which builds an image, from the configuration repository, which declares what runs, with an automated or manual commit that updates the image tag in the configuration repository. Secrets were the other early problem: a repository cannot hold plain secrets, and the solutions that emerged were encrypting values in the repository with a tool the controller understands, referencing an external store through a synchronisation operator, or keeping the secrets entirely outside Git.

The documentation of Kubernetes itself acknowledges the pattern in its canary task, which points at the idea of automating the promotion by a tool and not by hand [src: kubernetes-docs 31ea936a36006dc1], and the KubeVirt project documents a restore flow designed to work with GitOps, which illustrates that even stateful operations are being expressed declaratively [src: kubevirt-user-guide 69a513a76f7b3f6a].

## Current state

**Argo CD resources.** The Application resource has a source section, a destination section, a project and a sync policy. The source can be a directory of plain manifests, a Kustomize base or overlay, a Helm chart with values, or a plugin-generated output, and recent versions allow several sources in one application, for example a chart from one repository and values from another. The project resource groups applications and limits what they may deploy: which repositories, destinations and resource kinds are allowed. The sync policy can be manual, in which case the interface shows the difference and a person approves, or automated, with two important switches: prune, which deletes live objects that are no longer in Git, and self-heal, which reverts out-of-band changes. Sync options include creating the namespace, server-side apply, and respecting ignore rules for fields that other controllers write. Retry settings handle transient failures. Sync waves and resource hooks, set by annotations, order the application of objects within one sync, for example running a migration Job before the Deployment. Health assessment is built in for standard resources and extensible for custom ones. The ApplicationSet resource generates Applications from templates over generators such as lists, directories in a repository, clusters registered with Argo CD, or pull requests, which is the main tool for managing fleets and for preview environments.

**Flux resources.** A source resource such as a Git repository declares a URL, a branch or tag or commit, an interval and a credentials secret, and the source controller publishes an artifact. A Kustomization resource names a source, a path, an interval, whether to prune, a timeout and optionally health checks on objects whose readiness must be reached; it can also name other Kustomizations that it depends on, which provides ordering between layers such as infrastructure before applications. It can decrypt values encrypted with a tool such as SOPS, using keys stored in the cluster. A HelmRelease resource names a chart from a Helm or OCI repository, with values, upgrade and rollback policies and tests. The notification controller sends events to chat or webhooks and receives webhooks to trigger reconciliation sooner. The image automation controllers scan registries for new tags and commit updates back to Git, which closes the loop from build to deployment without a pipeline step.

**Reconciliation semantics.** Both tools run a loop: fetch the desired state at a revision, render it, compare it with the live state, apply the difference and report health. Interval and webhook settings control latency. Drift correction is the distinguishing feature from push pipelines, and it needs care: self-heal fights operators who make emergency changes by hand, so teams need a defined break-glass procedure, such as suspending reconciliation for one application. Pruning needs care too, because removing a manifest from Git deletes the live object, and for stateful objects that may mean deleting a volume; protective annotations or ownership rules prevent that. Fields set by other controllers, such as the replica count under an autoscaler or injected sidecars, must be excluded from comparison or the tool will report permanent drift.

**Repository layout.** A common layout has one repository for cluster configuration with directories for cluster-wide components, for tenant namespaces and for applications, and an overlay per environment. Promotion across environments is a commit or a pull request that changes the image tag or chart version in the next environment's directory, ideally with an automated check between steps. Using directories for environments, not long-lived branches, keeps diffs reviewable and avoids merge conflicts. A bootstrap step installs the controllers into a new cluster and points them at the repository, after which the cluster configures itself, which makes disaster recovery a matter of creating a cluster and running the bootstrap.

**Multi-tenancy and multi-cluster.** Argo CD can manage remote clusters from a central instance with credentials for each, or one instance per cluster, which trades central visibility against blast radius. Its projects and role-based access limit teams. Flux gives each tenant a namespace with its own sources and Kustomizations that apply under a service account with limited rights, so a tenant's repository cannot grant itself cluster-admin. Both can be combined with the cluster-creation tools to create fleets.

**Security.** The controllers are privileged: they can create any object in the clusters they manage, so their own installation and the repositories they trust are critical. Branch protection and required reviews on the configuration repository are the primary access control for production, and signed commits or signed OCI artifacts can be verified by the controllers. Secrets handling must be decided early. Credentials to the repository and registry should be read-only deploy keys or tokens. The controllers' own service accounts should be reviewed like any cluster-admin identity.

**Observability and notifications.** Both tools expose metrics and events about sync status, drift, durations and failures. A dashboard that shows applications that are out of sync, degraded or not reconciled for longer than expected is the baseline, and alerts on failed reconciliation for more than a short period catch the silent failures in which Git has a change that the cluster never received.

## Assessment: the good, the bad and the ugly

**The good.** GitOps gives an audit trail by construction, cheap rollback by revert, a clear answer to what should be running, self-healing against drift, and credential isolation, since clusters pull instead of being pushed to. It makes the cluster reproducible and the process reviewable, and both tools are mature, graduated and widely used. The pull model also scales: adding clusters adds agents, not pipeline complexity.

**The bad.** The model adds a layer of indirection and new failure modes: a change is not live when merged but when reconciled, and a broken manifest can block a whole sync. Secrets remain awkward. Promotion workflows, image-tag updates and ordering across applications need design that the tools provide only as building blocks. The tools differ in vocabulary and capabilities, so skills transfer only partly. Debugging means reading controller logs and events as well as the application's, and the interface of a GitOps tool can show a healthy status for a system that is functionally broken.

**The ugly.** The sharp edges involve deletion and conflict. An accidental removal of a directory from Git with prune enabled deletes production objects within minutes. Two controllers, or a controller and a human, fighting over a field cause an endless loop of apply and revert that looks like instability. A repository credential that expires silently stops all reconciliation, and Git continues to look authoritative while the cluster stagnates. A chart bump that includes a breaking change reaches every environment at once if the layout shares one reference. And the bootstrap repository is a single point of compromise: whoever can merge there controls every cluster.

## Applications beyond this domain

The reconcile-to-declared-state loop is the same pattern used by configuration management tools such as Ansible in pull mode, Puppet and Chef agents, and by infrastructure-as-code controllers that continuously apply cloud definitions. Operating systems with image-based updates apply the same idea to the host: declare the target image, let an agent move the machine to it, and roll back by returning to the previous one. Even Kubernetes itself is a reconciliation system, with controllers driving observed state to desired state, and GitOps simply extends the same loop to the question of where the desired state is stored. Code review on configuration, the key GitOps practice, applies to any infrastructure change.

## Examples

A first example is a minimal Argo CD application for a team. The Application points at a path in the configuration repository, targets a namespace on the local cluster, belongs to a project that allows only that repository and that namespace, and has automated sync with prune and self-heal and the option to create the namespace. A new commit that changes the image tag appears in the interface as out of sync for a few seconds and then as synced and healthy. When an operator scales the Deployment by hand, self-heal restores the declared replica count, so the operator learns that scaling goes through Git.

A second example is the same service in Flux. A Git source for the configuration repository with a one-minute interval and a Kustomization for the production path with prune on, a health check on the Deployment and a dependency on the Kustomization that installs the ingress controller. A webhook from the repository host triggers reconciliation immediately after a merge. Encrypted values in the repository are decrypted by the controller with a key that exists only in the cluster.

A third example is promotion. The build pipeline pushes an image tagged with the commit and opens a pull request that updates the tag in the staging directory. A merge deploys to staging. After automated smoke tests pass, a second bot opens a pull request for the production directory, which a human approves. Rollback of production is a revert of that one commit, and the audit trail shows who approved what and when.

A fourth example is a disaster-recovery rehearsal. The team creates a new cluster with the cluster-creation tool, runs the bootstrap command that installs the controller and points it at the configuration repository, and watches the infrastructure layer and then the applications reconcile in dependency order. The only manual steps are restoring the secrets key and the data from backups, which the runbook lists.

## Related problems and ideas

GitOps builds on packaging (T06), because what Git stores is usually a chart or an overlay, and on rollouts (T04), since progressive delivery controllers work with the delivery tool. It depends on secret handling (T02), which is the hardest part in practice. Operators (T08) are the other side: they reconcile application-level state, while GitOps reconciles cluster configuration, and the two use the same pattern at different layers. In the security course, the supply chain, signing and admission control are the controls that make a pull-based pipeline trustworthy, and in the administration course, RBAC and multi-tenancy are the foundation for tenant isolation.

An idea worth keeping is that Git is a good database for desired state because it is versioned, reviewable and decentralised, but it is a poor database for anything that changes by itself, such as replica counts under autoscaling or generated values. Separating what humans declare from what the cluster computes is the discipline that keeps GitOps calm.

## Active research

Active work includes OCI artifacts as the source of truth instead of Git, with signed and immutable configuration bundles, progressive delivery integrated into the delivery tools, better multi-cluster fleet management, policy checks on pull requests before merge, drift detection that distinguishes intended from unintended differences, and secret management without secrets in Git. Both projects release frequently, major versions have changed APIs, and any version-specific field name above is "to verify" against the version installed.

## Future direction

Expect GitOps to become the default delivery model for clusters, with OCI-based sources, stronger verification and fleet features built in, and with the two main tools continuing to coexist. The durable skills are designing repositories for promotion and review, making reconciliation observable, handling secrets deliberately, and writing a break-glass procedure before the first emergency.
