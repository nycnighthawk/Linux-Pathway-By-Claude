# Seeing inside a running application: Prometheus metrics and OpenTelemetry

## Define the problem

Probes tell the platform whether a container should receive traffic, and logs tell a person what one process said. Neither answers the questions that operating a service actually raises. How many requests per second is it handling, and what fraction fail? How long do the slowest one percent take? Which of forty microservices added the latency of that slow request? Is memory use growing slowly enough to be a leak or quickly enough to be an emergency? Did the new release change any of these numbers? To answer them an application must be instrumented: it has to count and time what it does, expose those measurements in a format a collector can read, and carry enough context between services that a single user request can be followed across them.

Observability work is usually divided into three kinds of signal. Metrics are numbers aggregated over time, cheap to store and good for alerting and trends. Traces record the path of one request through the system as a tree of timed spans, good for finding where time goes. Logs are discrete events with detail, good for the specifics of a failure. Prometheus has become the standard system for metrics on Kubernetes, and OpenTelemetry is the standard for generating and moving all three signals in a vendor-neutral way. The two are complementary and increasingly integrated.

This slice covers how an application exposes Prometheus metrics, what the metric types and naming rules are, how the cluster discovers and scrapes targets, the PromQL idioms behind dashboards and alerts, how OpenTelemetry's API, SDK, protocol and Collector fit together, how context propagation makes traces possible, and the operational costs, chiefly cardinality and sampling, that decide whether an observability system stays useful. The learning goals are to instrument a small service with metrics and traces, to write the scrape and alert configuration that a platform needs, and to reason about what to measure.

## History and approaches

Prometheus began at SoundCloud in 2012, inspired by Google's internal monitoring, and joined the CNCF as its second project after Kubernetes. Its design choices set it apart from earlier monitoring tools. It pulls: the server fetches metrics from an HTTP endpoint on each target at an interval, which makes target health a by-product of scraping and removes the need to configure every application with the server's address. It stores time series identified by a metric name and a set of labels, queried with a functional language, PromQL, that aggregates and transforms series. It has no clustering of its own; reliability comes from running two identical servers and long-term storage from remote-write to external systems. Service discovery integrates with the Kubernetes API, so targets appear and disappear with Pods.

The exposition format is plain text, one sample per line with labels, which made instrumentation trivial in any language and gave rise to a large library of exporters that translate the metrics of other systems, from the Linux kernel through the node exporter to databases and hardware. The format was later standardised and extended as OpenMetrics, which added exemplars that link a metric sample to a trace. The Prometheus Operator, a controller from the same ecosystem, introduced custom resources for servers, alert rules, service monitors and pod monitors, so that teams could declare what to scrape next to their application manifests; the packaged distribution that bundles it with dashboards and rules became the usual way to install monitoring on a cluster. A major release in 2024 changed defaults in the query engine and the UI, relaxed metric-name character rules and added a receiver for the OpenTelemetry protocol (to verify the exact version and flags).

OpenTelemetry arose from a merger of two earlier projects, OpenTracing and OpenCensus, in 2019, and is now one of the most active CNCF projects. It specifies an API that application code calls, an SDK that implements it with sampling, batching and exporting, a wire protocol called OTLP, semantic conventions that standardise attribute names such as the HTTP method and status, and a Collector, a standalone process that receives telemetry, processes it and exports it to backends. Its aim is that instrumentation is written once and the backend is a deployment choice. Tracing reached stability first, then metrics, and logs have followed; the stability of each language's implementation varies and is "to verify" for the one in use.

The failures in this field are as predictable as in any other. Teams that put user identifiers or request paths into metric labels created millions of series and exhausted memory in the server, the classic cardinality explosion. Teams that measured averages instead of distributions hid tail latency. Teams that instrumented tracing without propagating context across a queue or an HTTP client ended up with broken traces that began again at every hop. Teams that sent every span to a backend paid for storage of data nobody read. And teams with a monitoring system that depended on the cluster it monitored lost visibility in exactly the outage they needed it for.

Monitoring began with checks that asked whether a host was up. As systems became distributed, the questions turned to rates, errors and latencies across many instances, and a time-series approach emerged. Prometheus brought a pull model with labelled metrics and a query language, matching the dynamic membership of clusters. Tracing and structured logs joined it, and OpenTelemetry offered a common standard for producing all three kinds of signal.

## Current state

**Metric types.** Prometheus defines four types. A counter only increases, apart from resets at restart, and is queried through its rate. A gauge goes up and down and is read directly. A histogram counts observations into buckets with fixed upper bounds and also keeps a sum and a count, which allows server-side estimation of quantiles across many instances; a newer native form of histograms stores buckets more efficiently with dynamic resolution. A summary computes quantiles in the client and cannot be aggregated across instances, which is why histograms are preferred for latency. Naming conventions are part of the interface: lower-case words with underscores, a prefix naming the application, base units in the name (seconds, bytes) and a suffix for counters indicating a total. Labels distinguish dimensions of a metric, and the guidance is to use them for values with a small, bounded set, never for identifiers of unbounded origin.

**Exposing and scraping.** An application includes a client library, registers its metrics, and serves them on an HTTP path, conventionally on a dedicated port. The server's scrape configuration discovers Pods or Services through the Kubernetes API and selects them by labels and annotations, and relabelling rules turn discovery metadata such as namespace and Pod name into series labels. With the operator, a service monitor resource selects Services by label and names the port and path, and a pod monitor does the same for Pods directly. The cluster-level components expose their own metrics: the API server, the kubelet and its embedded container advisor for per-container CPU and memory, and the kube-state-metrics service, which turns the state of objects, such as the replicas desired and available in each Deployment, into series. The node exporter covers the host. A separate component, the metrics server, serves short-term resource usage to the autoscaler and to the top command and is not a monitoring system.

**PromQL and the signals that matter.** The functional idioms are few and powerful. The rate function over a counter gives a per-second increase over a window; summing by a label aggregates across instances; the histogram quantile function over summed bucket rates estimates a percentile; and comparisons produce alert conditions. Two method frameworks decide what to measure. For request-driven services the rate, errors and duration of requests, and for resources the utilisation, saturation and errors of each. The site reliability literature adds the four golden signals, latency, traffic, errors and saturation, which are the same ideas. Recording rules precompute expensive queries, and alerting rules with a for duration fire only when a condition persists, and the Alertmanager groups, deduplicates, silences and routes notifications. Alerting on symptoms that users feel, such as error budget burn rate, is preferred to alerting on causes such as CPU, which fire for harmless reasons.

**OpenTelemetry components.** The API is a thin interface with no behaviour unless an SDK is installed, which lets libraries instrument themselves without forcing a choice on applications. The SDK samples spans, batches telemetry and exports it by OTLP over gRPC on one well-known port or over HTTP on another. Resources describe the producer, with attributes for the service name, namespace and Pod, which can be populated from environment variables set in the Pod spec. The Collector has a pipeline model: receivers accept data in OTLP and other formats, processors batch, filter, add Kubernetes metadata and limit memory, and exporters send to one or more backends. It runs in two common patterns. As an agent beside the application, in a DaemonSet or a sidecar, it receives from local Pods and does cheap processing. As a gateway, a Deployment, it receives from agents and does heavier work such as tail-based sampling and fan-out. The OpenTelemetry Operator manages Collectors and offers auto-instrumentation: an annotation on a workload causes an init container to inject an agent for supported languages, which provides traces for common frameworks without code changes.

**Context propagation.** A trace is assembled from spans that share a trace identifier. The standard header carries a version, the trace identifier, the parent span identifier and flags, and every client, server, message producer and consumer in the path must read it on arrival and write it on departure. Proxies and meshes participate when configured to. Baggage carries additional key-value pairs through the same path. Sampling decides which traces are kept: head sampling decides at the start with a probability and is cheap, tail sampling decides after the trace is complete, by looking at errors and latency, and needs a gateway that collects whole traces.

**Linking signals.** Exemplars attach a trace identifier to a histogram sample, so that from a latency spike on a dashboard one can jump to an example trace. Log lines that carry the trace identifier allow the reverse jump. The semantic conventions give common attribute names, so a dashboard built for one service works for another. The Docker CLI's own instrumentation guide gives a compact illustration of the pieces in a different setting: a client emits spans over OTLP to a local collector, with the collector configured through a short file and the environment [src: docker-docs 71feed3590501efa].

**Costs and limits.** Prometheus memory grows with active series, and a series is a unique combination of name and labels, so the count is the product of label cardinalities. Retention on local disk is typically measured in days or weeks; longer retention and global queries need remote storage. Traces and logs are much larger than metrics, and sampling, retention policy and the choice of backend dominate cost. The monitoring system's own availability should be monitored from outside the cluster it watches.

### The generalised pattern: start from the question

Metrics, logs and traces answer different questions: metrics show that something is wrong and how much, traces show where in a request path, and logs show the detail. The generalised method is to decide which questions the on-call person must answer, then instrument for those, with service-level objectives defining what good means. Labels need discipline, since each distinct combination is a separate series and unbounded values, such as user identifiers, make the system expensive.

## Assessment: the good, the bad and the ugly

**The good.** Prometheus is simple to run and to instrument, integrates natively with Kubernetes discovery, and has a query language well suited to the questions operators ask. The exposition format is universal, and the exporter ecosystem covers nearly everything. OpenTelemetry gives vendor neutrality, a shared vocabulary and a way to correlate signals, and auto-instrumentation lowers the cost of a first useful trace to a few lines of configuration.

**The bad.** Both need design. Instrumentation that measures the wrong things yields dashboards that look rich and answer nothing. PromQL has a learning curve, and its subtle behaviours with rates and staleness catch newcomers. Prometheus does not scale horizontally by itself and does not store long histories without help. OpenTelemetry's surface is large, the stability of components varies across languages and signals, and configuration of the Collector is a program in its own right. Running the full stack of metrics, traces and logs adds several components to operate and secure.

**The ugly.** The worst incidents are cost and trust problems. A label that contains an unbounded value can take down a Prometheus server in an hour. A misconfigured sampling rate sends the whole fleet's traces to a paid backend and produces a surprise bill. A broken propagation path produces traces that are lies, with a missing hop that makes the wrong service look slow. An alert that fires constantly gets muted and then misses the real incident. Dashboards that mix rates and totals mislead without any error being reported. And telemetry can leak secrets and personal data through attributes and log lines, which makes the pipeline a compliance concern.

## Applications beyond this domain

Metrics, traces and logs apply to every production system, with or without Kubernetes. The Linux kernel and system tools expose their own counters through the proc filesystem, performance counters and tracing facilities, and projects such as Performance Co-Pilot bridge them into the same ecosystems; the manual page for the OpenTelemetry agent of that toolkit shows a kernel-oriented metric source being bridged to the common model [src: man-pages 81caadc2caa76c51]. The service-level objective practice of defining an indicator, a target and an error budget applies to any service. Distributed tracing ideas date back to Google's Dapper and apply equally to a monolith with several processes. And the habit of instrumenting at the edges, requests in and out, queries to databases and calls to other services, is useful in any software.

## Examples

A first example is instrumenting a small HTTP service. The service registers a counter of requests labelled with method, route template and status class, and a histogram of request durations in seconds labelled by route template, and serves them on a metrics port. It uses the route template, not the raw path, so the label set is bounded. A service monitor selects the Service by label and scrapes the port every fifteen seconds. A dashboard panel shows the request rate by status class and a second shows the ninety-fifth percentile latency computed from the histogram buckets.

A second example is an alert on error budget burn. The service level objective is that ninety-nine point nine percent of requests succeed over a month. A pair of alerting rules compares the error ratio over five minutes and over one hour against multiples of the budget and fires only when both exceed their thresholds, so that a brief blip does not page but a sustained burn does. The alert's annotation links to the dashboard and to the runbook.

A third example is a trace through three services. A frontend calls an API, which calls a database wrapper. The application code is untouched; annotations on the Deployments enable auto-instrumentation for the language runtime, and environment variables set the service name and the Collector address. The agent Collector on each node batches and forwards to a gateway, which applies tail sampling to keep all traces with errors and one in twenty of the rest. In the trace view, the database call is the long span, and a log line carrying the trace identifier shows a slow query.

A fourth example is a cardinality incident. A team added a label with the customer identifier to a request counter, and the Prometheus server's memory climbed until it was killed. The administrator finds the metric with the most series by querying the server's own statistics, drops the label with a relabelling rule at scrape time to stop the damage, and the team moves the per-customer view to logs and traces where high cardinality is acceptable.

## Related problems and ideas

### Related

This topic relies on Pod design and probes (T01, T03), because agents and exporters often run as sidecars and because a probe is the minimal form of telemetry. Rollout strategies (T04) use metrics for automated canary analysis, which is the most direct way that observability feeds delivery. GitOps (T07) can manage the monitoring stack itself, and charts (T06) package it. Operators (T08) expose their own metrics and status conditions. The networking course's eBPF and service mesh topics describe sources of telemetry that need no application changes, and the security course covers audit logs and the handling of sensitive data in telemetry.

An organising idea is to design observability from questions backwards. List the questions an on-call person must be able to answer in five minutes, and instrument and alert only to answer them. Telemetry that answers no question is cost without value.

### Opposing approaches

Opposing approaches include hosted observability services, which remove operational burden at a recurring cost and some loss of control, and sampling or event-based systems that store wide events instead of pre-aggregated metrics, trading storage for the ability to ask new questions later. Some teams argue that dashboards are overrated and alerts on symptoms matter more. The standardisation effort around OpenTelemetry is itself contested where vendors differ on support.

## Active research

Active developments include native histograms and more efficient storage in Prometheus, direct ingestion of OTLP metrics, continuous profiling as a fourth signal, eBPF-based zero-code instrumentation, better tail sampling, correlation of metrics, traces and logs by default, and standard conventions for the telemetry of AI workloads. The stability of specific components changes with releases and is "to verify" for the versions in use.

## Future direction

Expect OpenTelemetry to become the default instrumentation interface, with Prometheus-compatible backends as one of several destinations, and with auto-instrumentation and kernel-level collection reducing the need for code changes. The skills that last are choosing bounded labels, measuring distributions and not averages, propagating context everywhere, sampling deliberately, and alerting on user-visible symptoms.
