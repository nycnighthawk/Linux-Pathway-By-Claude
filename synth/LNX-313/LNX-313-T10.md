# The developer inner loop on Kubernetes: Tilt, Skaffold and dev containers

## Define the problem

Everything earlier in this course concerns the outer loop: building images in a pipeline, packaging them, delivering them through Git and observing them in production. A developer spends most of the day in a smaller cycle, the inner loop: change a line of code, build it, run it somewhere realistic, look at the result, repeat. On a laptop with an interpreter or a compiler this takes a second or two. Once the application depends on a container image, a cluster, configuration objects, several neighbouring services and a database, the naive loop becomes a build of an image, a push to a registry, an edit of a manifest, an apply, a wait for the Pod and a read of its log, which can take minutes. A developer faced with a five-minute loop does fewer iterations, tests less, and eventually stops running the code on the platform at all until a pipeline does it for them.

Two kinds of tooling attack the problem from complementary sides. Inner-loop tools for Kubernetes, chiefly Skaffold and Tilt, automate the build-deploy-watch cycle and shorten it, by rebuilding on file changes, syncing changed files into running containers, forwarding ports and streaming logs. Development-environment tools, chiefly dev containers, make the environment in which code is edited and built reproducible, so that every developer and the CI system use the same compilers, linters and versions. Both aim at the same goal, which is to make the distance between an edit and its effect on a realistic target as short as the distance on a laptop.

This slice describes the tools, their configuration formats, the techniques that give fast loops (incremental builds, file synchronisation, remote or local clusters, intercepting traffic) and the trade-offs between a local cluster and a shared one. The learning goals are to set up a project so that one command starts the whole stack with live updates, to choose between the major tools, to define a dev container that captures the toolchain, and to know which differences between development and production can mislead.

## History and approaches

The earliest approach was to avoid the cluster. Developers ran dependencies with Docker Compose or the language's native tools on their machine and mocked the rest. That was fast, and it diverged from production in ways that surfaced late: different networking, different configuration injection, no Kubernetes primitives such as probes, resource limits or service accounts. Local Kubernetes distributions narrowed the gap: minikube, then kind, k3s and k3d, which run a cluster in a container or virtual machine, and the desktop container products that bundle one. With a local cluster the manifests can be used unchanged, but the loop still needed automation.

Skaffold, released by Google in 2018, was the first widely used tool for the loop. Its model is a pipeline defined in a single file with stages for building artifacts, testing, deploying and port-forwarding, with a development mode that watches the source tree, rebuilds the affected artifact, redeploys and tails logs. It supports several builders, including Docker, Jib for Java, Cloud Native Buildpacks and ko for Go, and several deployers, including plain manifests, Kustomize and Helm, and its profiles let one file serve local development, CI and staging. Tilt, created by a company that was later acquired by Docker, took a different shape: a program, written in a Python dialect called Starlark, describes the resources, and a local server with a browser interface shows the state of each, its logs and its errors. Its distinguishing feature is live update, in which changed files are synchronised into a running container and a command is run there, skipping the image rebuild entirely, so the loop for an interpreted language approaches that of a local run. Other projects fill adjacent niches. DevSpace and Okteto combine building, syncing and remote development. Telepresence and mirrord connect a local process to a remote cluster by intercepting traffic to a service and sending it to the developer's machine, which suits applications with many dependencies that cannot all run locally. Docker's own tooling added a watch mode for Compose that synchronises files and rebuilds on changes.

The development-environment side has its own history. Teams wrote setup documents that rotted, then scripts that worked on one operating system, then virtual machines that were heavy, then containers used as build environments. The dev container specification, which began as a feature of one editor and was later published as an open specification, describes an environment in a JSON file: a base image or a build file, features that install tools into it, ports to forward, extensions and settings for supporting editors, lifecycle commands to run at creation and start, and mounts. The same file works in several editors, in hosted workspaces, in command-line tools and in CI, which gives one definition of the toolchain for every context.

The history is also one of recurring mistakes. Teams that point the inner loop tool at a shared cluster collided with each other and with whatever else ran there. Teams that rebuilt the full image for each change spent most of the day waiting for dependency installation, until they ordered Dockerfile layers by change frequency and used build caches. Teams that depended on live update for a compiled language found it brittle. And teams whose dev container diverged from the CI image hit the classic failure: it works in my container.

## Current state

**Skaffold.** The configuration file declares a build section listing artifacts, each with an image name, a context directory and a builder, and optional file synchronisation rules that copy matching files into running containers without a rebuild. A deploy section lists how to apply the result, for instance by naming manifests, a Kustomize directory or a Helm release with image references wired to the built tags. Port forwarding is configured for named resources. Profiles override sections for contexts such as the local cluster, with a different image repository or different values. The main commands are the dev command, which loops until interrupted and cleans up on exit, the run command for a one-shot build and deploy, the debug command that adds debugger support to the container, and the render command that prints the final manifests. Image tags are computed from the content so that unchanged artifacts are not redeployed, and the tool pushes to a registry unless the cluster is local and can load images directly.

**Tilt.** A Tiltfile calls functions to register image builds, YAML or Helm or Kustomize output, and resource settings. A build can be a standard Docker build with a live update specification: a list of steps that synchronise a local path into the container, run a command when certain files change, such as a package installation when the lock file changes, and restart the process. Resources can be grouped, labelled and ordered with dependencies, and local resources run host commands such as code generators and tests. The web interface shows the status and logs of each resource and links to the forwarded ports. Because the configuration is a program, it can read environment variables, call helper functions and load extensions from a shared repository, which is powerful for a team and a hazard when it grows complex.

**Choosing between them.** The two tools overlap. Skaffold is declarative, fits CI pipelines with the same file, and has strong support for particular builders and deployers. Tilt is programmatic, has a richer interactive interface and a more refined live-update model, and is a better fit for many-service systems where the developer wants to see and control individual resources. Teams choose by how much of the work is the single-service cycle compared with the multi-service orchestration, and by what their CI already uses.

**Techniques that make the loop fast.** Layering the Dockerfile so that dependency installation is cached and source copying comes last; using build caches and, for remote builds, a registry cache; using multi-stage builds so the final image is small and the build stage is cached; using a builder that produces layers without a Dockerfile for the language; synchronising files instead of rebuilding when the runtime supports reload; running the application with a file watcher inside the container; and keeping the cluster close, which for most people means a local one with a registry the cluster can reach without a push over the internet. Resource consumption of a local cluster matters: a laptop that runs a cluster, a database and a browser needs memory limits and a smaller set of services than production.

**Remote and hybrid development.** When the full system does not fit on a laptop, options are a namespace per developer on a shared cluster with the tool deploying into it, a per-developer virtual cluster that gives isolation inside a shared one, or a hybrid in which the process under development runs locally and the cluster routes selected traffic to it through an intercept. These patterns trade realism, isolation and cost. They also raise governance questions: quotas on developer namespaces, automatic clean-up of abandoned environments, and access to production-like data.

**Dev containers.** The configuration names an image or a build, a list of features that install common tools such as language runtimes, the docker client or the kubectl binary, a user to run as, forwarded ports, environment variables, mounts for caches and credentials, editor extensions and settings, and lifecycle commands: one run once on creation, one on each start, one when the editor attaches. A dev container can talk to the host's Docker daemon or to a cluster through a mounted kubeconfig, or include a nested cluster. The same definition can be used in CI so that the build uses the same toolchain as the developer, which removes a major source of surprises. Security considerations include which credentials are mounted, which extensions are trusted, and the fact that lifecycle commands execute code from the repository when the container is built.

**Where the loop meets the rest of the course.** The manifests or chart used in the loop should be the same ones the pipeline delivers, with overlays or profiles for differences, so that the inner loop tests the real packaging. Probes, resource limits and security contexts should be on in development, since turning them off hides the failures that production will show. Telemetry can be wired in locally with a lightweight collector so that traces are available during development.

## Assessment: the good, the bad and the ugly

**The good.** A fast inner loop on a realistic target catches integration errors early, shortens the time to understand a bug, and makes onboarding quick: a new developer clones, opens the dev container, runs one command and has the full stack. The tools are open source, run on laptops and in CI and reuse the same manifests as production. Live update and file sync make the loop for interpreted languages close to local speed.

**The bad.** The tools add configuration that must be kept in step with the real deployment. Live update is a different path from the production image, so a change that works in sync can fail in the built image. Local clusters consume memory and differ from production in networking, storage and load-balancer behaviour. Shared development clusters need governance. Dev containers need maintenance and can be slow to build, and they shift the question of where code runs to a layer that some developers find opaque. Tool vendors change ownership and direction, and the ecosystem of builders and deployers is large.

**The ugly.** The sharpest problems are drift and leakage. A team that develops only with live update never builds the production image until the pipeline, where the missing file or wrong permission appears. A Tiltfile that grows into thousands of lines is a second build system nobody owns. Developer namespaces that are never deleted fill a shared cluster. A dev container that mounts the whole home directory and the cloud credentials gives every extension and every lifecycle script access to them. And an intercept that routes production traffic to a developer's laptop is a data leak and an outage waiting for a network hiccup.

## Applications beyond this domain

The inner-loop idea is not specific to Kubernetes. Web frameworks have hot reload, mobile development has instant run, and data engineers use notebooks for the same reason. Reproducible development environments are used in embedded and kernel development, where cross-compilers and exact toolchain versions matter, and the same principle applies to a build container for any project that must be built identically by many people. The file-synchronisation approach is the idea behind remote editing over SSH, and the traffic-intercept approach resembles debugging by proxy in any distributed system.

## Examples

A first example is a service with a Skaffold file. The file lists one artifact built with a Docker build using the local cluster's image loading, one Kustomize deployer pointing at an overlay for development, a sync rule that copies the template directory into the container without a rebuild, and port forwarding for the service's HTTP port. The developer runs the dev command; a source change triggers a rebuild in seconds because the dependency layers are cached, and a template change updates the running container in under a second.

A second example is the same service in Tilt. The Tiltfile registers the image build with a live update that syncs the source directory into the container and runs the dependency installer only when the lock file changes, loads the manifests from a Helm chart with development values, forwards the port, and defines a local resource that runs the unit tests whenever source files change, with the output shown in the interface next to the service. A second service that the first depends on is registered with a dependency, so it starts first.

A third example is a dev container for a Go service. The definition uses a base image from the language vendor, adds features for the Docker client, kubectl and Helm, forwards the application port, installs the language server extension in the editor, runs the dependency download in the creation command and mounts the module cache as a volume for speed. CI uses the same image for the build and test jobs, so a version bump of the toolchain is one change in one file.

A fourth example is a hybrid setup. The team's twenty services do not fit on a laptop, so each developer has a namespace in a shared development cluster. The service under development runs locally with an intercept that sends requests for it from the cluster to the laptop and forwards its outbound calls into the cluster. A scheduled job deletes namespaces idle for a week, and a policy limits what each developer's service account can do.

## Related problems and ideas

The inner loop uses the artifacts described throughout the course: Pod designs and probes (T01, T03) should be present in development; configuration and security contexts (T02) too; Helm charts and overlays (T06) provide the manifests; GitOps (T07) is the outer loop the inner loop hands off to; and observability (T09) gives the developer the same visibility locally as in production. The administration course covers local cluster distributions and the resources they need, and the virtualization course picks up the same idea of reproducible environments in the form of image-based virtual machines.

The idea to keep is that the inner loop is a product with users: the developers. Its performance should be measured, for example as the time from saving a file to seeing its effect, and improvements should be made deliberately, because a platform whose inner loop is slow will be bypassed.

## Active research

Active developments include faster and more reproducible builders, remote build and cache services, ephemeral per-branch environments created from the same manifests, AI-assisted generation of manifests and dev container definitions, standardisation of the dev container specification across tools, and better integration between inner-loop tools and policy engines so that development environments obey production rules. The state of each tool and its ownership change often and are "to verify" before a team commits to one.

## Future direction

Expect the inner loop to converge on a few patterns: reproducible dev containers as the editing environment, content-addressed builders and caches for speed, file sync or hot reload for interpreted languages, and per-developer or per-branch environments on shared infrastructure for large systems. The enduring skills are measuring the loop, keeping development manifests the same as delivered ones, and treating the development environment as code that is reviewed and versioned.
