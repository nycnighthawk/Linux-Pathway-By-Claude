# Telling the truth about health, and finding out why it failed: probes, logs and kubectl debug

## Define the problem

A running process is not the same as a working service. A web server can be alive and unable to answer because its thread pool is exhausted. A database client can hold open connections to a database that vanished. A Java application can take ninety seconds to warm up while the container reports itself as started on the first second. The container runtime only knows whether the main process exists, so without help the cluster would send traffic to an application that is not ready, keep an application that is stuck, and kill an application that is merely slow to start. The platform needs the application's own statement of health, in a form that the kubelet can ask for repeatedly and act upon.

When something does go wrong, a second problem appears: the evidence is in a container that may have been replaced, in an image that contains no debugging tools, on a node the operator cannot log into. The good practice of building minimal images, without a shell, a package manager or network utilities, makes the problem worse. The cluster therefore needs ways to read logs that survive container restarts, to attach a temporary toolbox to a running Pod, and to copy a failing Pod into a debuggable form without disturbing the original.

This slice covers the three kinds of probes and the way each changes the platform's behaviour, the common mistakes in writing them, the logging path from container to the command line, and the debugging commands that add an ephemeral container, copy a Pod or open a shell on a node. The goal is a method: from the symptom reported by the status, choose the probe settings that would have prevented it, and choose the tool that finds the cause in a few minutes.

## History and approaches

Health checking existed before containers in load balancers and in process supervisors, which made the same distinction between a process that has started and a service that can answer. Kubernetes launched with liveness and readiness probes and later added a startup probe to handle slow-starting applications. Before the startup probe, the usual workaround for a slow application was a large initial delay on the liveness probe, which delayed detection of real failures for the entire life of the container. The startup probe disables the other two until it succeeds once, so a long start can coexist with a tight liveness check afterwards. Probe handlers also grew: the first versions ran a command inside the container or made an HTTP request or opened a TCP connection, and later the gRPC health-checking protocol was added as a native handler, so that services in that ecosystem no longer needed a sidecar binary to translate.

The history of misuse is as informative as the feature history. Early adopters pointed the liveness probe at an endpoint that checked the database, so that a database outage restarted every application Pod at once, converting a partial failure into a full one and keeping the application from recovering when the database returned. Others used the same endpoint for liveness and readiness, so that a temporary overload both removed the Pod from rotation and killed it. Teams set aggressive timeouts that fired during garbage-collection pauses or CPU throttling, producing restart loops that looked like application crashes. The documentation of the Pod lifecycle explains the restart policy and the back-off that follows repeated failures, and the init-container reference describes how a failing init container keeps the whole Pod from starting [src: kubernetes-docs 4eeb22f4d5d526ae].

Logging evolved from a decision. The container runtime captures what the process writes to its standard output and error streams, and the kubelet stores it as files on the node with rotation, which is why the platform's advice is to log to the streams and let an agent collect them, instead of writing log files inside the container. The command that reads those files, kubectl logs, asks the kubelet through the API server; it reads the current container's log, or with the previous flag the log of the last terminated instance, which is the one that matters in a crash loop. Cluster-level logging is not part of Kubernetes itself: a node agent or a sidecar ships the files elsewhere, and the platform's job ends at keeping the file available for a limited time.

Debugging tools moved from the node to the cluster API. The first way to debug was to exec into the container, which fails if the image has no shell. The second was to run a separate debug Pod with the same image and a different command, which does not reproduce a live failure. The ephemeral container feature added a container to an existing Pod after it has started, sharing its namespaces, with the toolbox of the operator's choice. The kubectl debug command wraps three workflows: adding an ephemeral container to a running Pod, creating a modified copy of a Pod for experimentation, and starting a privileged Pod on a node with the host filesystem mounted. The command reference describes each mode and its options [src: kubernetes-docs 091e5a9f0cdc8960]. The virtual machine world has its own variant of the same idea, in which the guest agent answers probes on behalf of the virtual machine, illustrating that the pattern is independent of what is inside the Pod [src: kubevirt-user-guide fc9e4048abdf5f80].

Early container platforms knew only whether a process was running. That was not enough: a process may run while deadlocked, or be alive but not yet ready for traffic. Probes grew to separate three states, whether the application is started, whether it is alive and whether it is ready, and each is answered by its own check. Logging followed the twelve-factor line of writing to standard output and letting the platform collect it, and debugging tools were extended to attach a temporary container to a running Pod, so that images could stay small.

## Current state

**The three probes.** The startup probe asks whether the application has finished starting. Until it succeeds the kubelet runs neither of the others, and if it fails beyond its threshold the container is killed and handled by the restart policy. The readiness probe asks whether the application can serve requests now. A failing readiness probe removes the Pod's address from the endpoints of its Services without restarting anything, and it keeps the Pod from counting as available during a rollout. The liveness probe asks whether the process is stuck in a state that only a restart will cure. A failing liveness probe kills the container, which then restarts according to the restart policy with exponential back-off, capped at a few minutes.

**Handlers and parameters.** A probe uses one of four handlers: a command executed inside the container whose exit status decides, an HTTP GET whose response code in the success range decides, a TCP connection attempt that must succeed, or a gRPC health check. Every probe has timing fields: an initial delay before the first check, a period between checks, a timeout for each check, a success threshold (which must be one for liveness and startup) and a failure threshold. Together they determine the maximum time to detect a failure or to allow a start, which is roughly the period multiplied by the failure threshold. A slow start of two minutes needs a startup probe whose period times failure threshold exceeds two minutes with a margin. The probe-level grace period for termination, a separate field, lets a failing liveness check stop the container faster than the Pod's overall grace period.

**What probes do not do.** Probes run on the node by the kubelet, so an HTTP probe connects to the Pod address, not through the Service. They do not retry within a period, and they share the container's CPU quota, so a throttled container can fail a probe while healthy. They cannot check dependencies on behalf of other Pods, and a readiness probe that depends on a downstream service couples availability across the call graph, which can turn a small outage into a cascading one. Probes for sidecars were covered with the Pod design slice: a native sidecar may have all three, and its readiness counts toward the Pod.

**Termination and readiness.** During shutdown the Pod receives the termination signal, while at the same time the control plane removes its address from endpoints, and the two happen asynchronously. Applications that stop accepting connections at once will drop requests that are still arriving at them from proxies that have not yet updated. The standard remedy is a short sleep in a pre-stop hook, or an application that continues serving for a few seconds after the signal while failing its readiness check, followed by a graceful drain.

**Reading logs.** The command that prints a container's log takes the Pod name and, for multi-container Pods, the container name with a flag. Useful options select the previous instance, follow the stream, limit by time or by number of lines, add timestamps, show logs of all containers or of Pods selected by label. For init containers the same flag selects them by name, and the debugging page for init containers shows how to read the log of one that failed [src: kubernetes-docs 74127e9e6df533de]. Log files on the node live under a directory named for the Pod, are rotated by the kubelet by size with a configurable count of files, and disappear with the Pod. A crash-looping container therefore needs its previous log read promptly and shipped off the node for anything longer than the life of the Pod.

**Status and events.** The Pod's description, which prints the state of each container, its last termination state, the exit code, the reason and the restart count, is often a faster route to a diagnosis than the logs. An exit code of 137 means the process received a kill signal, usually from the out-of-memory killer or a failed liveness check, and 143 means it exited on the termination signal. The events list adds scheduler decisions, image pull problems, probe failures with the response received, volume mount errors and evictions. Events are kept for a short time, so they should be read early and exported by a collector if history matters.

**Ephemeral containers and kubectl debug.** An ephemeral container is added to a running Pod through a dedicated sub-resource. It cannot have ports, probes or resource settings of its own, and once added it cannot be removed or changed; it lives until the Pod does. With the target option it joins the process namespace of a named container, so the operator sees that container's processes and, through the proc filesystem, its root filesystem. The copy mode creates a new Pod based on the original with changes the operator chooses, such as a different image, a different command, or process-namespace sharing, which allows experiments with a failing start-up command without touching the original. The node mode creates a Pod on the node with the host filesystem mounted at a fixed path and the host namespaces, so that the operator can read kubelet logs and inspect the runtime without an SSH connection. The cluster must have the feature enabled and the user must have the permissions on the Pod's ephemeral-containers sub-resource, which is often not granted by default, and the security policy of the namespace may forbid the capabilities a debug image wants.

**A method.** A reliable sequence is: read the Pod's status and events, then the current and previous logs, then, if the logs are silent, start an ephemeral container with a toolbox image to check the network, the files and the processes as the application sees them, and only then consider node-level inspection. At each step the operator should note what was learned, because the temptation to jump to the node is strong and usually unproductive.

### The generalised pattern: report honestly, observe separately

The platform acts on what a container tells it, so a probe is a message to the scheduler and the load balancer. A readiness failure removes a Pod from service, a liveness failure restarts it, and a startup probe holds the other two back while the application warms up. The generalised rule is that each check should test only what its action implies: liveness should reflect internal failure, not the state of a database, or one outage restarts every Pod. Observation tools, logs and an ephemeral debug container, sit beside the workload and do not belong inside the production image.

## Assessment: the good, the bad and the ugly

**The good.** Probes give the platform a precise, application-defined signal, and the three roles are well separated. Readiness-driven rollouts and Service membership make deployments safe without external coordination. The log path is simple and robust, because it uses files that the runtime and kubelet already manage. Ephemeral containers solve the problem of minimal images without forcing teams to ship tools in production images, and the copy mode allows safe experimentation.

**The bad.** Probes are easy to write wrongly and costly when wrong. There is no single correct set of values, and defaults are not tuned for any application. The log path has no retention beyond the node's rotation and no cluster-level search without extra components. Ephemeral containers are permanent for the life of the Pod and need permissions many clusters withhold, and some distributions' security policies block the debug image's needs. Debugging a problem that exists only on one node needs the node mode, which is powerful and therefore restricted.

**The ugly.** The worst probe failures are cascades. A liveness probe that checks a shared dependency restarts every Pod when the dependency blips. A readiness probe that fails under load removes Pods one by one, concentrating load on the rest until none are left, and the Service has no endpoints at the moment of greatest demand. A startup probe omitted for a slow application and replaced by a long liveness delay means a deadlocked process takes ten minutes to restart. Logging failures are quieter: a container that logs to a file inside the filesystem fills the writable layer and gets evicted without a trace in the stream, and a node that rotates logs too aggressively loses the only evidence of a crash. And a debug container with host namespaces left running on a production node is an unsupervised root shell.

## Applications beyond this domain

Health checking is a general pattern for any managed fleet. Load balancers in every cloud poll health endpoints and make the same trade-offs between detection speed and false positives. Process supervisors such as systemd support watchdog notifications and readiness notification so that dependent units wait for real readiness, not process start. The same lesson about dependency-checking probes appears in service-level objective design, where the health of a component should reflect its own ability to serve, not that of everything behind it. The debugging workflows resemble remote diagnostics on any production Linux system: attach to the namespaces of a process with tools such as nsenter, read the journal, trace system calls, and avoid changing state while looking.

## Examples

A first example is a slow-starting application that is killed repeatedly. The Pod description shows the container restarted with exit code 137 and an event that the liveness probe failed with a connection refused response. The application takes about ninety seconds to load data. The fix adds a startup probe on the same HTTP path with a period of five seconds and a failure threshold of thirty, which gives it up to two and a half minutes, and sets the liveness probe to a period of ten seconds and a failure threshold of three. After the change, the application starts, the liveness probe takes over and a real hang is detected in thirty seconds.

A second example is a crash loop with no output in the current log. The previous-instance flag shows a stack trace about a missing environment variable. The Pod description shows the variable's ConfigMap key was renamed in the same change. The fix is in the manifest, and the incident note proposes a template test that checks that every referenced key exists.

A third example is a minimal image with a network problem. The operator adds an ephemeral container with a toolbox image targeting the application container, then runs a name lookup and a connection test from the Pod's network namespace and sees that a name resolves to the wrong address because of a search-path issue. Because the ephemeral container shares the network namespace but not the filesystem, the operator reads the application's configuration through the process filesystem of the target. The container remains until the Pod is replaced, which the runbook notes.

A fourth example is a node-level symptom. Several Pods on one node fail their probes intermittently. The operator starts a node debug Pod, mounts the host root at its fixed path, reads the kubelet and runtime logs and finds the node under memory pressure with the kubelet evicting Pods. The follow-up is a request and limit review for Pods on that node, and the debug Pod is deleted when the work is done.

## Related problems and ideas

### Related

This topic builds on Pod design (T01) and on resource limits (T02), where throttling and memory limits are the main causes of false probe failures. It is the foundation for rollouts (T04), where readiness is the gate that lets a rollout proceed, and for Jobs (T05), where exit codes and back-off limits play the role that probes play for services. Observability (T09) generalises the idea from a binary signal to metrics and traces. In the administration course the node-level troubleshooting tools complement the cluster-level ones here, and in the networking course the DNS debugging guide shows a related toolbox approach with a test Pod [src: kubernetes-docs 5a9baee4c1c41732].

A principle that guides all of it is to have the application report its own state honestly, on a path that does not depend on others, and to keep the logging and debugging path separate from the production image. Both principles reduce the number of things that must work for an operator to find out what is wrong.

### Opposing approaches

The opposing view is that probes are a crude control. Some teams disable liveness checks altogether, because a poorly tuned one turns a slow day into a restart storm. Others prefer to let the application or a service mesh perform health checking with richer information, such as error rates, and feed that into routing. Shell access to production containers is another point of difference: many sites ban it in favour of debug containers and audit trails, while others keep it for speed in emergencies.

## Active research

Active work includes a way to restart a single container without restarting the Pod, container restart rules that depend on exit codes, better probe semantics for sidecars and for Pods that are being resized, a standard for structured logs at the platform level, and tooling that records the state of a Pod at the moment of a probe failure for later analysis. The ephemeral containers feature continues to change, with proposals for removing them and for resource accounting, and the status of each item is "to verify" for the version in use.

## Future direction

Expect probes to remain the main contract between application and platform, with better defaults, with the startup probe becoming standard for any application that takes more than a few seconds to start, and with debugging moving further toward the API and away from node access. Administrators should keep a short written checklist for the first five minutes of a failing Pod, review probes as part of code review, and grant the debug permissions deliberately, not by accident.
