# Releasing without downtime: rolling updates, blue/green and canary strategies

## Define the problem

A new version of an application has to replace the old one while users are still sending requests. The simplest approach, stopping the old version and starting the new, causes an outage for as long as the new one needs to start, and if the new one is broken, the outage lasts until someone notices and puts the old one back. Real services cannot accept that for every release, and teams that deploy several times a day cannot accept it even briefly. The release mechanism therefore has to do three things at once: keep enough capacity serving at every moment, detect a bad version before it reaches everyone, and make going back as cheap as going forward.

Those three needs pull in different directions. Keeping capacity argues for replacing a few instances at a time. Detecting a bad version argues for exposing only a small share of users to it and watching. Cheap rollback argues for keeping the old version running until the new one is trusted. Different strategies give different answers, and a team's choice depends on the cost of extra capacity, the speed of detection, the compatibility of data between versions and the tooling available. The strategies are also not mutually exclusive: a canary can use a rolling update to scale the new version, and a blue/green switch can be preceded by a canary.

This slice covers the three main strategies, how the Deployment controller implements the first and what building blocks exist for the other two, the settings that control speed and safety, the interaction with probes and disruption budgets, and the database and compatibility problems that no strategy can solve for you. The goal is to be able to pick a strategy for a given service, write the manifests for it, and predict what the cluster will do when a release goes wrong.

## History and approaches

Before orchestrators, releases were scripts that took a server out of a load balancer, updated it, tested it and put it back, one host at a time. The same pattern, now called a rolling update, was the first thing Kubernetes automated. The earliest mechanism was a client-side command that scaled one replication controller up and another down in steps, which broke if the client lost its connection. The Deployment resource moved the logic into a controller on the server, which manages ReplicaSets, one per version, identified by a hash of the Pod template. A rollout creates a new ReplicaSet, scales it up while scaling the old one down within bounds, and keeps the old ReplicaSets, with zero replicas, as the revision history that rollback uses.

Blue/green and canary releases came from the world of web operations and from continuous-delivery writing. Blue/green keeps two complete environments, one serving and one idle; a release deploys to the idle one, tests it, then switches traffic at the router, with rollback being a switch back. Canary releases, named for the miner's bird, send a small fraction of real traffic to the new version, compare its behaviour with the old, and increase the fraction if the numbers are acceptable. In early Kubernetes there was no built-in support for either, and the documentation described how to build them from the existing parts: the older replication controller documentation discusses running several release tracks side by side with a shared label so that a Service selects both [src: kubernetes-docs 7e2d0b6ffa4eb058], and the canary deployment task shows a stable and a canary Deployment behind one Service, where the ratio of replicas sets the share of traffic [src: kubernetes-docs a96d469adfeaac66].

That approach is simple and has well-known limits. The traffic share equals the replica share only if the proxy balances evenly across Pods, so a one-in-twenty canary needs twenty replicas, and fine-grained splits are impossible at small scale. There is no automatic analysis, so promotion and rollback are manual or scripted. Session affinity and long-lived connections skew the split. These limits drove two further developments. One was progressive-delivery controllers such as Argo Rollouts and Flagger, which add a Rollout resource or a canary controller that shifts traffic in steps through a Service mesh, an ingress controller or the Gateway API, queries a metrics system between steps and rolls back on failure. The other was traffic splitting in the networking APIs themselves: the Gateway API has weighted backends in its route definition, which gives an exact percentage independent of the replica count, as the networking course showed.

The failure history is a catalogue of assumptions. Teams that set an aggressive surge and no readiness probe replaced healthy Pods with ones that were not yet serving, causing brief outages during every release. Teams that relied on rollback found that the previous ReplicaSet no longer existed because the history limit was set to zero or because a manual scale had lost it. Teams that ran database migrations in the same step as the code discovered that the old Pods, still running during a rolling update, could not work with the migrated schema. And teams that adopted blue/green doubled their capacity bills at every release.

## Current state

**The Deployment strategy.** A Deployment has a strategy of RollingUpdate, the default, or Recreate. Recreate stops all old Pods before starting new ones, which is right only for workloads that cannot have two versions or two copies running at once, such as one holding an exclusive lock or a single-writer volume. RollingUpdate has two parameters. The maximum surge says how many Pods above the desired count may exist during the update, as an absolute number or a percentage. The maximum unavailable says how many may be missing. Both default to a quarter of the replicas, with the surge rounded up and the unavailable rounded down. Setting unavailable to zero with a surge of one gives a strictly capacity-preserving rollout that replaces one Pod at a time, at the cost of needing room for the extra Pod. Setting surge to zero and unavailable to one works in a fully packed cluster but reduces capacity during the rollout.

**What counts as available.** A new Pod counts as available once it is ready for the minimum ready time, a Deployment field that defaults to zero. Without readiness probes, a Pod counts as ready the moment its containers start, which defeats the purpose of the mechanism, and with a short or zero minimum ready time a Pod that becomes ready and then crashes quickly can let the rollout advance too far. A progress deadline, ten minutes by default, marks a rollout as failed if no progress is made, which is a status condition, not an action: the controller does not roll back by itself, so the operator or an external tool must react. The rollout status command waits and returns a failure code when the deadline passes, which makes it usable in a pipeline.

**Revisions and rollback.** Each Pod template change produces a new revision, and the revision history limit decides how many old ReplicaSets are kept, ten by default. The undo command scales the chosen previous ReplicaSet back up, which is a new rollout to an old template. Pausing a Deployment lets several changes be made and applied as one rollout. A scale operation or a change that does not alter the Pod template does not create a revision.

**Blue/green with plain Kubernetes.** Two Deployments, labelled by colour, run in parallel. A single Service selects one colour through its label selector, and the switch is a patch that changes the selector, which the cluster applies to the endpoints within seconds. Testing the idle colour uses a second Service or a port-forward. The advantages are an atomic switch and an instant rollback while the old colour remains. The costs are double capacity during the overlap, the need for the two versions to be able to share data, and caches or connection pools that have to warm up. With the Gateway API the switch becomes a weight change on the route.

**Canary with plain Kubernetes.** A stable Deployment and a canary Deployment share the label that the Service selects, and the canary has its own distinguishing label. The share of traffic is roughly the share of Pods that are ready. The canary task in the documentation shows the manifests and the procedure for completing the rollout by updating the stable Deployment and removing the canary, or for rolling back by deleting the canary [src: kubernetes-docs d17943752e0e932c]. The same document describes the rollback of a canary, which is deleting its Deployment and checking that the Service has only stable endpoints [src: kubernetes-docs 768a6c9214be1b23]. Because the split depends on replica counts and balancing, this is a coarse tool, suitable for a first step and for teams without a mesh.

**Progressive delivery controllers.** The Rollout resource in the progressive-delivery tools replaces the Deployment and adds a strategy section with steps: set a weight, pause for a time or for approval, run an analysis against metrics, then proceed. The analysis defines queries against a metrics backend with success conditions, such as an error rate below a threshold, and failing analysis aborts the rollout and returns traffic to the stable version. They integrate with traffic routers to apply exact weights, and they also support blue/green with a preview Service and an automatic or manual promotion. They are controllers installed in the cluster and so add a component to operate and a resource type that tools need to understand.

**Interaction with disruption budgets and autoscaling.** Rolling updates are not voluntary disruptions in the sense of the disruption budget, which governs evictions, so the budget does not slow a rollout, but a stalled rollout can leave the cluster at reduced capacity for a long time. The horizontal autoscaler changes the replica count during a rollout, and the Deployment controller scales both ReplicaSets proportionally, which is generally right but can surprise. Node drains during a rollout compete for the same capacity and should be avoided or coordinated.

**Compatibility.** For any strategy in which two versions run at the same time, which includes all of them in some period, the versions must tolerate each other's requests, messages and data. The standard technique for databases is expand and contract: first a release that adds new columns or tables and still works with the old schema, then a release that uses them, and finally a cleanup release once no old version remains. The same discipline applies to message formats, API contracts and cache keys.

## Assessment: the good, the bad and the ugly

**The good.** The rolling update is built in, automatic and safe when the readiness probe tells the truth, and it needs no extra capacity beyond the surge. Revisions make rollback a one-line operation. Blue/green is easy to understand and gives instant rollback. Canary limits the blast radius of a bad release to the share of traffic that reaches it, and with automated analysis it removes human attention from the routine case.

**The bad.** None of the strategies is free. Rolling updates mix versions for the whole duration, so compatibility is mandatory, and a bad release is only noticed by the probes' view of health, which may be blind to semantic errors. Blue/green costs capacity and does nothing about incompatible data. Plain-Kubernetes canaries are coarse and depend on balancing. Progressive-delivery tools need metrics that are good enough to base decisions on, and that is a significant engineering investment. The Deployment controller does not roll back on its own, so every pipeline needs a step that notices failure and acts.

**The ugly.** The worst cases combine rollout mechanics with data. A migration that drops a column while the old version still reads it breaks the old Pods in the middle of the rollout, and rollback does not help because the data have moved on. A readiness probe that returns success before the application has warmed its cache sends a share of traffic to slow Pods and appears as a latency regression with no failures. A canary receives requests from a few sticky clients, which makes its statistics meaningless. A rollout stuck at the progress deadline leaves a mix of versions in production for hours because no one is watching, and a pipeline that treats a timeout as success moves on. And a rollback to an old revision that includes an old, vulnerable base image reintroduces a known problem silently.

## Applications beyond this domain

These strategies are general release techniques. Operating system vendors stage updates to fleets in rings with health gates, which is a canary applied to machines. Content-delivery networks and mobile app stores roll out by percentage of users. Feature flags implement the same idea at the code level, decoupling deployment from release and allowing a gradual exposure that does not depend on infrastructure. Database and schema changes follow expand and contract regardless of orchestration. The Linux package ecosystems do a similar thing with staged repositories, and the same questions, what to monitor and who decides to proceed, apply.

## Examples

A first example is tuning a rolling update. A service with twelve replicas used the default surge and unavailable settings and showed a dip in capacity at each release. The team sets the surge to three and the unavailable count to zero, adds a minimum ready time of fifteen seconds, and verifies with the rollout status command that the Pods are replaced in batches of three, with the total ready count never falling below twelve. The change costs temporary room for three extra Pods, and the team confirms the nodes have it.

A second example is a blue/green switch for a service that cannot tolerate two versions mixed. The green Deployment is created with the new image and a distinct label, and reaches full readiness while receiving no traffic. A test Service selecting green is used for smoke tests. The production Service's selector is patched from blue to green, and the team watches error rates for ten minutes before scaling blue down to zero but keeping the Deployment definition, so a switch back needs only a patch and a scale.

A third example is a canary with the documented plain approach. A stable Deployment of nine replicas and a canary of one share the application label behind one Service, so about ten percent of requests reach the canary. The team compares error rates and latency for an hour and then updates the stable Deployment to the new image, which rolls it out, and deletes the canary. When the canary shows errors, deleting it is the rollback and takes seconds.

A fourth example is a schema change. The team splits one feature into three releases: the first adds a nullable column and writes to both the old and the new columns, the second reads from the new column, and the third drops the old one after confirming no old Pods remain. Each release uses a normal rolling update, and each one can be rolled back independently, which the original single-step change could not.

## Related problems and ideas

The strategies rest on earlier topics: readiness and startup probes (T03) are the signal that drives rollout speed; resource requests (T02) decide whether a surge fits; Pod design (T01) affects termination during replacement. GitOps (T07) is how rollouts are triggered and audited, and Helm (T06) is the packaging that carries the image tag and strategy settings. Observability (T09) provides the metrics that automated canary analysis needs. In the networking course, Gateway API weights and mesh routing provide exact traffic splits, and in the administration course, disruption budgets and node drains govern the interaction with maintenance.

A deeper idea is that deployment and release are different events. Deployment puts code on servers; release exposes it to users. Strategies, flags and traffic splitting are tools for separating them, and the more separate they are, the lower the risk of each.

## Active research

Current work includes more precise rollout controls in the Deployment (a way to pause at a percentage, better surge handling for Pods with long start times), the Gateway API's weighted routing and a standard for traffic splitting in meshes, tools that run analysis on traces and business metrics as well as error rates, automated detection of regressions from logs and profiles, and techniques such as shadow traffic and replay. Maturity differs between tools and releases, and any specific feature claim is "to verify" against the version in use.

## Future direction

Expect progressive delivery to become a standard layer, with the Deployment as the simple default and routing-level traffic splitting taking over canary and blue/green. The practices that last are the discipline of compatible changes, honest readiness probes, a recorded rollback path for every release, and a pipeline that treats a stalled rollout as a failure.
