# Building machine images with Image Builder and osbuild

## Define the problem

Every fleet starts with a first boot. Whether the machines are virtual machines in a private cloud, instances in a public cloud, edge devices or physical servers installed from media, someone has to produce the disk image or installer that carries the operating system and the site's baseline. Done by hand (install, configure, snapshot) this produces a "golden image" that nobody can reproduce: the steps are in an engineer's memory, the content cannot be inspected, and the image goes stale within weeks. A build tool that turns a *declaration* (these packages, these users, this firewall setting, this partition layout, this compliance profile) into a bootable artefact, the same way every time and in every format that the platforms need, replaces the hand-made image with a reviewable pipeline. In the Red Hat family that tool is **Image Builder** (RHEL image builder, built on the `osbuild` project and, in the cloud, offered as a hosted service); Fedora and CentOS Stream have the same code; other families have their own equivalents (Packer, KIWI, mkosi, live-build, Debian's `debos`, Yocto for embedded).

The problem for this topic is how to use such a builder well. How should the declaration be organised and versioned? Which parts belong in the image and which should be applied at first boot? How do you control which package versions go in (the snapshot and content-view topics apply here)? How are the outputs for different targets produced from one definition? How are images tested and published, and how does an image relate to the image-mode (bootc) approach of the previous topic? Typical failure modes are that images are built from whatever the public mirror served that day so that no two builds agree, secrets or credentials end up inside images, the image works on one hypervisor but not another because of missing drivers or `cloud-init` configuration, the builder is run on a developer's laptop with no record, and the image is published with no signature, no scan and no expiry.

The scope is the Image Builder workflow on Enterprise Linux and Fedora: installing the service, writing blueprints, choosing output types, using custom repositories and snapshots, adding customisations, building and downloading, testing, and connecting it to a delivery pipeline. It is a "know it and use it" topic, short on theory.

## History and approaches

Building system images has gone through several generations. The first was **kickstart-installed then captured** images: install a VM from a kickstart file, shut it down, copy the disk. Cloud platforms encouraged this because they needed disk images, and many organisations still have a script that does it. **Packer** (HashiCorp, 2013) generalised the pattern with builders for each platform and provisioners (shell, Ansible) that configured a temporary machine, then captured it; it is platform-neutral and widely used, but slow, and its output depends on whatever the provisioners did at the time. **Distribution tools** build images from package lists without booting a machine: Debian's `debootstrap`, `live-build` and `debos`; SUSE's **KIWI**; Fedora's `livemedia-creator` and `appliance-creator`; Arch's `mkarchiso`; the systemd project's **mkosi**; Yocto and Buildroot in embedded Linux, which compile everything from source.

**osbuild** (started around 2018 in the Weldr project and used by Fedora and Red Hat) took the distribution-tool approach and organised it as a pipeline of declared **stages**, each a small, reproducible operation (install RPMs into a tree, set locale, create users, write a systemd unit, build a filesystem, create a partitioned disk, convert to qcow2). A **manifest** describes the pipeline completely, down to the exact package versions and checksums, so that the same manifest produces the same image and every input is recorded. A separate component, **osbuild-composer**, takes a high-level request (a *blueprint*, an output type and a distribution), uses a dependency solver (`dnf-json`/`osbuild-depsolve-dnf`) to resolve package sets against the configured repositories, generates the manifest and runs osbuild workers locally or remote. The user-facing tools are the `composer-cli` command, a web interface in Cockpit (`cockpit-composer`) and, in the hosted offering, a console service. The Red Hat guide describes how to install the service, enable the socket and use the web console to create images from blueprints [src: rhel-10-docs 9a58bb8d586c31b4] and [src: rhel-10-docs d3394a0c89918944].

The system requirements are modest but not trivial, since building an image needs disk space for the package cache and the output, memory for the build VM stages, and a supported host operating system [src: rhel-10-docs 1e805d80e10353e8]. Builds run as root or via a service, so the host that runs the builder is a sensitive system.

A second generation of the tool targets container-based systems. **bootc-image-builder** is a container image that wraps osbuild: it takes a bootc container image and a small configuration file and produces disk images (qcow2, raw, AMI, VMDK, ISO). It reuses the stages but starts from the image rather than from a package list, which is what the previous topic's workflow requires. The newer `image-builder` command-line tool aims to unify the interface (to verify the status in your release).

The hosted counterpart is the service in Red Hat's console, which can push images directly to cloud accounts (AWS, Azure, Google Cloud) and is described, together with the preparing and uploading of cloud images from the local builder, in the RHEL documentation [src: rhel-10-docs 67d2bd6d49859e5f]. Public clouds also offer their own image pipelines (AWS EC2 Image Builder, Azure Image Builder), which orchestrate similar steps but are tied to one provider.

## Current state

**Installing and starting.** On a supported host, install `osbuild-composer`, `composer-cli` and `cockpit-composer`, enable `osbuild-composer.socket` and `cockpit.socket`, and add the user to the `weldr` group so that `composer-cli` can talk to the service without root [src: rhel-10-docs 9a58bb8d586c31b4]. Check with `composer-cli status show` and `composer-cli sources list`. Run the builder on a dedicated host or VM: it needs plenty of disk (tens of gigabytes free is a reasonable floor; confirm in the requirements section) and often network access to repositories.

**Blueprints.** A blueprint is a TOML file. A minimal one:

```
name = "site-base"
description = "Site baseline server"
version = "1.2.0"
distro = "rhel-10"

[[packages]]
name = "chrony"

[[packages]]
name = "tmux"

[customizations]
hostname = "template"

[[customizations.user]]
name = "ops"
key = "ssh-ed25519 AAAA... ops@example.org"
groups = ["wheel"]

[customizations.services]
enabled = ["chronyd", "sshd"]

[customizations.firewall.services]
enabled = ["ssh"]

[customizations.kernel]
append = "audit=1"
```

Other customisation tables cover filesystems (`[[customizations.filesystem]]` with mount point and minimum size), `files` and `directories`, locale, timezone, `ignition` or cloud-init data for some image types, repositories, `fips`, and a compliance profile from the OpenSCAP integration (`[customizations.openscap]` with `datastream` and `profile_id`, applying remediation at build time; check availability for your release, to verify). Version the blueprint in Git. Increment `version` when it changes so that `composer-cli blueprints` shows a history.

**Commands.**

```
composer-cli blueprints push site-base.toml
composer-cli blueprints depsolve site-base
composer-cli compose types
composer-cli compose start site-base qcow2
composer-cli compose status
composer-cli compose image <uuid>
composer-cli compose logs <uuid>
```

`depsolve` shows the exact packages that will be installed, which is a useful review step before a long build. `compose types` lists output formats for the distribution, typically `qcow2`, `vmdk`, `vhd`, `ami`, `gce`, `raw`, `tar`, `image-installer` (an ISO that installs the image), `edge-commit`, `edge-container` and `edge-installer` for the edge workflow, and others (the list changes between releases).

**Controlling content.** By default the builder uses the vendor repositories. To make builds repeatable, add *sources*: TOML files naming base URLs of your own mirror or snapshot, with `check_gpg` and keys, and `composer-cli sources add`. Point them at a snapshot or content-view path from the repository topics so that the image contains exactly the packages of a known date; the RHEL guide describes configuring repositories for image builder and the handling of overrides and system repositories [src: rhel-10-docs 3547624fa0f1810d]. Record the snapshot identifier and the blueprint commit in the image's metadata (a file in `/etc` or `/usr/share`, a cloud tag, or the compose metadata) so that an instance can be traced back to its inputs.

**Choosing which distribution to build.** Image Builder can build images for the host's own distribution and, with the right configuration, for others. The documentation covers selecting a distribution and how that interacts with the supported combinations, with the caveat that the builder host and target should be a supported pair [src: rhel-10-docs 3ee526b08c93ea0e].

**Image or first boot.** The test for whether a setting belongs in the image is whether it is the same for every machine built from it. Packages, enabled services, kernel arguments, audit rules, baseline security profile and agents belong in the image. Hostnames, IP addresses, machine identity, secrets, SSH host keys and role-specific configuration belong in first-boot provisioning, using `cloud-init`, Ignition, kickstart or configuration management. Generalise the image: remove the machine id (`/etc/machine-id` empty so it regenerates), the SSH host keys, DHCP leases and logs; the builder takes care of much of this, but custom steps can leave residue. Rocky Linux's lab material on customisation illustrates the idea of generalising a template and the defaults that a template should carry [src: rocky-docs 0bfc14645afa6fe8].

**Testing.** Treat the image as software. A pipeline should: build the image, boot it headless in a VM (libvirt or QEMU) with a test cloud-init seed, run assertions (services active, ports closed, `oscap` scan passes, agents register, a package inventory matches the expected list), then publish. Add a second test that boots the image after an upgrade of the repository snapshot, to catch breakage that appears only with newer packages. For cloud targets, import the image into a test account and launch it before releasing the image ID.

**Publishing and lifecycle.** Upload to image stores (Glance, vSphere content libraries, cloud image galleries, a registry for container-based outputs), tag with a version and snapshot, sign or checksum, and record an expiry: images older than a threshold (say 90 days) should not be used for new instances because they carry stale packages, and the gap is closed by rebuilding on a schedule even when nothing changed in the blueprint. Retire old images according to the retention rule from the snapshots topic. Image-based delivery adds the distinction between *build images that are used to create machines* (templates, from which hosts then patch in place) and *delivery images that are the update unit* (image mode). Image Builder can serve both.

**Security.** The builder host is a high-value target because it produces what runs everywhere: restrict access, log builds, keep the repositories and keys it trusts under change control, do not put secrets in blueprints (they are stored and visible), and scan built images. The package signatures verified by the builder are those of the repositories, so GPG checking should be on. The reproducibility offered by osbuild's manifests allows an independent party to rebuild and compare.

**Alternatives and complements.** Packer remains useful for platforms or flows that osbuild does not cover and for installing software that needs a running system. mkosi is attractive for Fedora, Debian and Arch images with systemd-centred workflows. KIWI covers SUSE. For Debian-family fleets, `debos`, `live-build` and cloud-image customisation with `virt-customize` and `cloud-init` are the common routes. Kubernetes-related VM platforms, such as KubeVirt, consume the same disk images as containerised disks, so one pipeline can feed several consumers [src: kubevirt-user-guide a7e7278e900479c3].

## Assessment: the good, the bad and the ugly

**The good.** A blueprint is a small, reviewable, versioned description of an image, which is a vast improvement over a hand-built golden image. The build is a function of the declared inputs, produces many output formats from one definition, resolves dependencies against the repositories you choose and can apply compliance profiles at build time. The command line and API are scriptable and fit pipelines. The integration with vendor support and cloud upload shortens the path to a running instance.

**The bad.** The blueprint language covers common customisations but not everything, and complex needs fall back on custom scripts, first-boot configuration or a different tool. Builds are slow and resource-hungry. Features differ between releases and between the on-premises and hosted services, and documentation lags behind. Support is strongest for Red Hat and Fedora distributions; building other distributions needs extra work. The depsolve against moving repositories makes builds non-repeatable unless the sources are pinned. Debugging a failed stage requires reading osbuild logs.

**The ugly.** The worst cases are cultural. A pipeline that produces beautiful images that nobody rebuilds, so that servers are launched from a year-old template and then patched on first boot for forty minutes; images with secrets or a shared `ops` key baked in; and builds that succeed on a laptop with an old cache and fail in CI. A further trap is mixing models: an image that is both a template for in-place patching and a delivery unit, with no rule about which changes go where.

**Assumptions.** Blueprint keys, output type names and tool behaviour reflect the cited documentation and the author's knowledge of recent releases and change frequently; confirm them against the release you run (to verify).

## Applications beyond this domain

The idea of building an artefact from a declarative description with pinned inputs is the same as container image builds, Nix derivations, Bazel targets and Terraform plans. Edge computing uses image builders to produce commit-based or container-based images for thousands of devices. Education and CI environments use them to produce uniform lab VMs. Kubernetes platforms use image builders (the Cluster API image-builder project, for instance) to make node images for each cloud. Security teams use them to produce hardened, scanned base images that other teams inherit, in the way application platform teams offer base container images.

## Examples

**Example 1: a first image.** Write `site-base.toml`, run `composer-cli blueprints push`, `depsolve` to review packages, `compose start site-base qcow2`, wait for `FINISHED` in `compose status`, download with `compose image`, and boot it with `virt-install --import` and a cloud-init seed. Log in with the key from the blueprint.

**Example 2: a repeatable build.** Add a source file `site-snapshot.toml` pointing at `https://repo.example.org/snapshots/2026-11-08/el10/baseos/` with `check_gpg = true`, disable the default sources for the build, and record the snapshot date in the image through a `files` customisation. Rebuilding next month with the same snapshot gives the same packages.

**Example 3: one blueprint, three targets.** Build `qcow2` for the private cloud, `ami` for the public cloud and `image-installer` for bare metal from the same blueprint, test all three in the pipeline and publish them with the same version.

**Example 4: the hardening profile.** Add the compliance profile customisation, build, then run `oscap xccdf eval` against a booted copy in CI and fail the pipeline if a rule that the profile should have fixed still fails.

**Example 5: a bootc image to disk.** Run bootc-image-builder with the registry image and a config TOML adding the `ops` user, to produce a qcow2 for a test VM, then boot it and check `bootc status`.

**Worked failure: the stale template.** A team builds an image once per quarter. A new instance boots, runs `dnf update` through cloud-init and applies 300 packages, including a kernel, then reboots, so services come up twice and health checks flap during scale-out. The fix is a weekly scheduled build from the current snapshot, a test stage and a policy that autoscaling groups use images no older than 14 days.

## Related problems and ideas

Image Builder links to **repositories and snapshots** (controlled inputs), **signing** (repository and image signatures), **bootc** (the container-native route), **provisioning** (kickstart, PXE, cloud-init and the next course's topics), **configuration management** (first-boot role configuration), **compliance as code** (profiles applied at build) and **SBOMs** (each build can emit one). On the virtualisation side, the same disk formats are consumed by KVM, vSphere and cloud platforms, and tools like `virt-customize` and `guestfs` tools can adjust an existing image without rebuilding it.

## Active research

Work in this area includes making builds bit-for-bit reproducible, unifying the front ends (`image-builder` replacing several CLIs), better support for partitioning and disk layout declarations, richer test frameworks for images, and integrating attestations and signing into the build so that a booted system can prove what it was built from. Another thread is the convergence of image building and container building, in which bootc images, disk images and installers are all products of one pipeline.

## Future direction

Expect image building to be a standard stage in infrastructure pipelines with the build host as managed as any production system, expect the declarative description to grow to cover more of the disk and first-boot configuration, and expect provenance and SBOM generation to be built in. For the operator, the lasting habits are to pin inputs, rebuild on a schedule, test every image by booting it, keep secrets out and make every instance traceable to a blueprint commit and a repository snapshot.
