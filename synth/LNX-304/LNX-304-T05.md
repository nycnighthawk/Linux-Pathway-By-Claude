# Dated repository snapshots: freezing, promoting and rolling back package state

## Define the problem

A package repository that follows upstream changes under your feet is not a basis for reliable operations. If two servers run `apt upgrade` or `dnf update` on different days, they receive different sets of packages, even when the commands and configuration are identical. If a test passes against Tuesday's repository, nobody can say whether the same packages will be on production on Friday. If an update breaks something, there is no earlier state to return to, because the repository now offers only the newest version. A **dated snapshot** answers all three: it is a frozen, named copy (or immutable view) of a repository at a moment in time, which clients can be pointed at and which never changes. With snapshots, naming the date of the frozen state says exactly what the fleet may install, a rollout is a series of pointer changes from one snapshot to the next, and a rollback is a pointer change in the other direction.

The term needs care, because "snapshot" has several meanings in infrastructure. Storage snapshots (LVM, Btrfs, ZFS, SAN) freeze the contents of a disk and are a tool for rolling a single machine back after an upgrade; the Red Hat documentation on managing system upgrades with logical-volume snapshots describes this machine-level approach, which complements but does not replace repository snapshots [src: rhel-10-docs 83b38ba5f6e33143]. Virtual machine snapshots freeze guest state and are covered in the virtualisation courses. A repository snapshot is different in kind: it freezes the *available software*, not the installed state of any machine. This topic is about the last of these, how they are made, named, stored, published, promoted and retired, and how they combine with the signing and repository topics before and after this one.

Typical failure modes are these: a "snapshot" implemented by a name that is later updated in place (a mutable tag); a snapshot taken from a mirror that was in the middle of a sync, so that it references packages that are not yet present; snapshots that are deleted to save disk while a production environment still points at them; snapshots whose signatures expire (the signed index is old, and clients reject it); snapshot sprawl, with hundreds of near-identical copies that nobody dares remove; no record of which snapshot each environment uses, so that an incident team cannot tell what was installed; and a security update that never reaches production because the production snapshot was frozen for a long time and nobody planned the next promotion.

## History and approaches

Archives of historical package states have existed for as long as distributions have kept old releases. Debian's `snapshot.debian.org` service, started by Peter Palfrader and maintained by the Debian system administrators, keeps copies of the archive taken at frequent intervals since 2005, with the explicit aim that a developer can retrieve the exact packages that were available on a given date, for example to bisect a regression or to rebuild an old package with its old build dependencies. Its URL scheme uses a timestamp, so that `snapshot.debian.org/archive/debian/20200101T000000Z/` is an apt-usable archive as it stood at that moment. Fedora keeps old releases and updates in its archive area; CentOS had a vault; Rocky and Alma keep old minor releases available (to verify the retention policy of each), and Ubuntu announced its own snapshot service for the archive in the 2020s (to verify the date and scope). These public services allow reproducibility but give the operator no control over what is in them, and they are not designed for an enterprise that wants to include its own packages or to apply a filter.

For private use the first approach was simply to copy a mirror directory: `rsync -a --link-dest=previous/ upstream/ today/` creates a new directory in which unchanged files are hard links to the previous one, so the disk cost of a snapshot is only what changed. This is cheap, understandable and works for both repository families because a repository is a directory tree. Its limits are that atomicity, signing and metadata consistency are left to the operator, and that hard links tie snapshots to one filesystem.

Purpose-built tools took the idea further. `aptly` made the snapshot a first-class object: a snapshot is an immutable, named set of package references created from a mirror, a local repository or another snapshot, and it can be merged with others, filtered, diffed (`aptly snapshot diff`) and published under a prefix with its own signature. Because packages live once in a pool and snapshots are lists of references, the cost of keeping many snapshots is small. In **Pulp 3** every change to a repository creates a new numbered *repository version*, so history is built in, and a *publication* freezes the metadata for one version; the distribution that clients use can be moved between publications, which is the promotion step. The Rocky Linux documentation on Pulp shows the chain of remote, repository, publication and distribution that makes this possible [src: rocky-docs 2723d5df6e4ca2e2] and [src: rocky-docs 297af38b177d0f71]. **Foreman and Katello** (the next topic) wrap Pulp with *content views*, which are named filtered selections of repositories that are published as numbered *versions*, and *lifecycle environments* (for example Dev, Test, Prod) to which a version is promoted. **Uyuni and SUSE Manager** use channels and "content lifecycle management projects" with similar semantics, and Ansible-driven approaches use the `rsync` method above.

A parallel line of work is the idea of **time-based pinning** at the client: instead of a frozen repository, the client asks a service for the archive "as of" a timestamp. The Debian snapshot service works this way, and some container-image builders use it to make builds repeatable by adding a date to every source line. This is simple but depends on the service staying available and keeps the operator at the mercy of the public archive's retention.

## Current state

**What to snapshot.** Snapshot every repository that feeds a machine you care about: the distribution's base and update repositories, third-party repositories (vendors, Kubernetes, Docker, monitoring agents), and your own. A snapshot taken of only one repository leaves the others moving; mixed states often produce dependency conflicts that appear only on production. Treat the *set* of snapshots as the release unit, and give it a single name such as `2026-11-08`.

**How to name them.** Use dates in ISO form plus an optional qualifier, such as `2026-11-08` or `2026-11-08-hotfix1`. Dates sort and explain themselves. Avoid names like `current`, `stable` or `latest` for the snapshots themselves; use those only for the *pointers* (see below), which are the mutable layer.

**Immutability and pointers.** The central design rule is two layers: snapshots are immutable, and environments are mutable pointers to snapshots. In file-based setups the pointer is a symlink (`channels/prod -> ../snapshots/2026-11-01`), and a promotion is `ln -sfn` (replace atomically with `mv -T` of a new link). In aptly it is `aptly publish switch` onto a different snapshot. In Pulp it is updating a distribution's publication. In Katello it is promoting a content view version. The pointer layer is the only thing that changes during a rollout, and the record of its history (who changed which pointer, when and why) is the audit trail.

**Creating a snapshot safely.** Sync the mirror completely; verify (a package count, a metadata check with `createrepo_c --check` or `dnf repoclosure`, or a `Release` signature check for Debian); then take the snapshot. Run the sync and snapshot in one job that fails closed: if the sync is incomplete, do not publish. Include the origin in the snapshot's description (the upstream URL, the time of sync and the checksums of `repomd.xml` or `Release`).

**Signatures.** A snapshot of a mirror contains the upstream signatures, which are valid until the upstream key expires or the signed index goes stale. For Debian, upstream `Release` files carry a `Valid-Until` field, and a snapshot older than that value fails `apt update` unless the client sets `Acquire::Check-Valid-Until "false"` (which is acceptable for a frozen internal snapshot but should be a conscious decision). The usual solution for an internal snapshot service is to **re-sign** with the organisation's own key, which clients trust instead of upstream's key. This turns the snapshot service into a trust anchor, so its signing key must be handled with the care described in the signing topic. For RPM repositories, `repo_gpgcheck` applies to the metadata signature, and package signatures remain the upstream's, so clients still need the upstream package keys.

**Promotion flow.** A typical flow has three or four stages. Every Monday the mirror syncs and a new snapshot, say `2026-11-09`, is created. It is pointed to by `dev` on Monday. After automated tests pass, `test` moves to it on Wednesday. After the canary group has run on it, `prod` moves to it the following week. Each move is a pointer change with a record. A security emergency uses an expedited path: an out-of-band snapshot with only the urgent packages, merged with the current production snapshot (aptly's `snapshot merge` or a Pulp copy) and promoted directly. The expedited path must exist before it is needed.

**Rollback.** Rolling back to the previous snapshot restores the *available* set but does not downgrade installed packages. For that, clients run `dnf downgrade` or `dnf history undo` (RPM) or install specific older versions with `apt install pkg=version` after pointing at the earlier snapshot. This is why a snapshot rollback is combined with a machine-level rollback (storage snapshots, image rollback) for critical systems, and why packages with database migrations or format changes need their own downgrade plan. State this limit in the runbook.

**Retention.** Keep, at minimum, the snapshots currently referenced by any environment, the previous one for each environment (the rollback target), and enough older ones to satisfy compliance and questions about what was running during a past incident (commonly the last 90 days weekly, plus quarterly beyond that, adjusted to your audit rules). Deletion must be preceded by a check that no pointer, image build or archived configuration refers to the snapshot; keep a ledger.

**Space.** With hard links or a pool, the incremental cost of a snapshot is only the new files, typically a few percent of the mirror per week for a base operating system, more for fast-moving third-party repositories (to verify against your own data). Without deduplication, a weekly full copy of a 300 GB mirror becomes 15 TB a year, which is why the file layout matters. Pulp with `on_demand` content and aptly's pool both deduplicate across versions.

**Client configuration.** Make the snapshot a variable in configuration management: the repository file or sources entry takes its URL from the environment name (`https://repo.example.org/channels/prod/el9/baseos/`), not from the date. Clients then follow the pointer and nobody edits date strings on machines. For ephemeral environments (CI, image builds), pass the snapshot date explicitly so that builds are reproducible: the same `Dockerfile` or Packer template run twice gives the same package set.

**Evidence and audit.** Record, for each environment and each date, the snapshot identifier. Combine this with the installed-package inventory (from `rpm -qa` or `dpkg-query` into a configuration database) and, if you generate software bills of materials, include the snapshot identifier in them. In an incident review, a reviewer can then verify a claim of the form: production followed one named snapshot for a given week, and that snapshot held a given version of a given package.

## Assessment: the good, the bad and the ugly

**The good.** Snapshots convert a moving target into a controlled artefact. They enable staged rollouts, repeatable builds, fast rollback of the *offered* state, and meaningful test results. They are cheap with the right storage layout and easy to explain to auditors. They make security patching deliberate: you know which snapshot is behind the latest advisories and by how many days.

**The bad.** Freezing has a cost: a snapshot that is not promoted regularly is an unpatched fleet, and a policy that makes promotions hard leads to long freezes and a growing vulnerability window. Snapshots do not roll back installed software or data, which surprises teams that expect them to. Re-signing creates a new key to protect. Combining several repositories into a consistent set takes care: a snapshot of the base repository from Monday and of a vendor repository from Thursday may be mutually inconsistent. Third-party repositories that rewrite history (a vendor re-publishes a package with the same version) break the assumption that a given version is a given file, and the checksum mismatch will show up at sync time.

**The ugly.** The ugly cases are social and operational: a team promotes by editing client files by hand, so the pointer layer is not authoritative; an emergency fix is installed from upstream directly "just this once", so that the fleet leaves the snapshot model; the snapshot server is single-instance and unmonitored; and nobody owns the rule for when old snapshots may be removed, so disks fill until someone deletes the wrong one.

**Assumptions.** The dates and scope of public snapshot services and the typical size increments are the author's recollection and the cited documents; verify them for your distribution and mirror (to verify).

## Applications beyond this domain

The same two-layer idea, immutable content plus mutable names, runs through container images (digests are immutable, tags move), Git (commits and branches), Nix (store paths and profiles), Terraform provider and module version locks, language lock files (`package-lock.json`, `Cargo.lock`, `poetry.lock`) and Kubernetes manifests rendered at a revision. CI systems pin base images by digest and package repositories by snapshot date for the same reason. On the storage side, the machine-level snapshot of the RHEL documentation, taken before an upgrade so that the system can be rolled back by merging the snapshot, is the counterpart for installed state [src: rhel-10-docs 83b38ba5f6e33143] and [src: rhel-10-docs 38ffa7abdc43ddd3]. Combining both gives a complete rollback: the repository pointer returns to the old state, and the machine returns to its pre-update disk state.

## Examples

**Example 1: hard-link snapshots of an RPM repository.** From a synced mirror directory `mirror/el9/` run `cp -al mirror/el9 snapshots/2026-11-01` after a verified sync, then `chmod -R a-w snapshots/2026-11-01`. A week later repeat with the new date. Create `channels/prod` as a symlink to the earlier snapshot and `channels/dev` to the newer one. Clients of `prod` see the old package set even after the mirror has moved on. Because the files are hard links, two snapshots with 99 % identical content use little more than one.

**Example 2: aptly.**

```
aptly mirror update bookworm
aptly snapshot create bookworm-2026-11-01 from mirror bookworm
aptly publish snapshot -gpg-key=KEYID bookworm-2026-11-01 prod/bookworm
# a week later
aptly snapshot create bookworm-2026-11-08 from mirror bookworm
aptly publish switch bookworm prod/bookworm bookworm-2026-11-08
aptly snapshot diff bookworm-2026-11-01 bookworm-2026-11-08
```

`snapshot diff` lists added, removed and changed packages, which is what a change review needs.

**Example 3: Pulp versions.** After each sync, `pulp rpm publication create` on the new repository version; to promote, update the `prod` distribution with `--publication` set to that publication; to roll back, set it to the earlier one. The CLI sequence follows the Rocky guide's structure [src: rocky-docs 297af38b177d0f71].

**Example 4: reproducible CI builds against a public snapshot.** For a build container based on Debian, set the sources to a `snapshot.debian.org` timestamped URL and record the timestamp in the repository beside the Dockerfile. Rebuilding the image months later reproduces the package set; updating the timestamp is a reviewed change.

**Example 5: promotion calendar.** Monday sync and snapshot; Tuesday automated tests on `dev`; Wednesday `test`; the next Tuesday canary group of 5 % of production; Thursday remaining production. A critical advisory skips the calendar through the expedited path and the record notes who approved it.

**Worked failure: the deleted rollback target.** To free space, an administrator deletes snapshots older than 30 days. A production environment had been held on a 45-day-old snapshot because of a change freeze. The next promotion fails and, worse, a rollback is impossible. The fix is a retention check that refuses to delete anything referenced by a pointer, and an explicit list of pointers in version control.

## Related problems and ideas

Snapshots depend on **repositories and signing** (the previous topics) and lead to **content views and lifecycle environments** (the next topic), **patch rings**, which decide which machines see which snapshot when, and **image-based delivery**, where the equivalent of a snapshot is an image digest. **Reproducible builds** need snapshots for build inputs. **Configuration management** carries the pointer to clients. **Vulnerability management** needs to know which snapshot each environment runs in order to answer "are we exposed?". **Disaster recovery** treats a snapshot store as a dependency to rebuild and back up, since it is the source from which machines are reinstalled. **Machine-level snapshots** of logical volumes or Btrfs subvolumes complement repository snapshots by providing rollback of installed state [src: man-pages 6fe3750c32e78144].

## Active research

Open topics include content-addressed, deduplicated archives that can serve any point in time cheaply, transparent logs of repository history so that clients can detect rewritten history, reproducible dependency resolution (a "lock file" for operating-system packages produced by the package manager itself, as language ecosystems have), and standards for describing a package set (SBOM-like manifests of a snapshot). The Debian reproducible-builds effort and the snapshot service are the best-known real-world infrastructure, and academic work on software supply-chain integrity studies how long vulnerable states persist in frozen environments.

## Future direction

Expect lock-file-like manifests for operating-system package sets to become common (a list of exact package versions and hashes rather than a date), expect image-based systems to reduce the need for per-machine package state, and expect snapshot services to be part of standard cloud mirrors. For the operator, the practical conclusion is to treat repository state as versioned data under change control: create snapshots automatically, promote them deliberately, and measure how old each environment's snapshot is. The measure that predicts trouble is not the number of snapshots but the age of production's pointer.
