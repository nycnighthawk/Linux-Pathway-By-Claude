# Running your own package repositories: createrepo_c, aptly and Pulp

## Define the problem

A package repository is a directory of packages plus an index that a client can read in one or two requests. Public distributions run huge ones, but an organisation also needs its own, for three distinct reasons. The first is to publish internal software, the site packages from the previous topics, to every machine. The second is to mirror upstream content locally, so that installs do not depend on the internet, so that bandwidth is spent once, and so that the content a machine sees can be controlled. The third is to freeze and promote content, so that the set of packages available on the day of a patch window is exactly the set that was tested. This topic covers the first two and the tools that implement them: `createrepo_c` for RPM metadata, `aptly` and the simpler tools `reprepro` and `apt-ftparchive` for Debian archives, `reposync` and `apt-mirror`-style tools for copying upstream, and Pulp 3 as a general content-management service for both families and for other content types. The third reason, snapshots, is the subject of the next topic.

Typical failure modes are practical. Metadata that does not match the files, for instance after packages are copied in without regenerating the index, gives checksum mismatches or "package not found" errors on clients. A mirror that syncs half-way and publishes its index before all packages arrive produces transient 404s. Unsigned repositories, or signed ones whose key was never distributed, force administrators to disable checks (the previous topic describes why this matters). A single repository directory grows without bound because nothing removes old versions. Disk fills because a full mirror of a distribution includes architectures and components nobody uses. A repository server that is a single machine with no redundancy becomes a hidden point of failure for every patch job, every kickstart and every image build in the company.

The scope here is the structure of both repository formats, the commands that create and update them, the choice between simple tools and a content-management server, mirroring policy (what to copy and how often), publication and atomicity (how to make an update appear all at once), signing integration, and capacity planning. The mechanics are small; the design decisions around them are where sites go wrong.

## History and approaches

**RPM repositories.** Early RPM distributions simply exposed a directory of packages over FTP or HTTP, and tools such as `apt-rpm` and `urpmi` built their own indexes. Seth Vidal's `yum` project introduced `createrepo` and the `repodata/` directory in the early 2000s: an XML description of every package (`primary.xml`, with name, version, checksums and dependencies; `filelists.xml`; `other.xml` with changelogs), compressed, plus `repomd.xml`, a small top-level file that lists these files with their checksums and timestamps. A client downloads `repomd.xml` first, learns which files to fetch and whether its cached copies are current. `createrepo_c`, a C rewrite begun in the early 2010s, is the standard tool today because it is much faster and also supports modules, delta packages and updateinfo, the metadata that carries security advisories. Repositories can also be built and updated incrementally (`--update`), so that only changed packages are re-read. The `reposync(1)` command, part of the DNF plugins, downloads all or part of a configured repository for local mirroring and can limit the download to the newest packages, to certain architectures, or to metadata only [src: man-pages 06a7cfc44bd589a2].

**Debian archives.** The Debian archive structure (`dists/<suite>/<component>/binary-<arch>/Packages`, with a `pool/` of files) is more elaborate than a flat directory, but a simple form is available: a *flat repository* in which `Packages.gz` and `Release` sit beside the `.deb` files and the source entry ends with a slash. The Debian Administrator's Handbook shows how to create such a repository with `dpkg-scanpackages` or the more capable `apt-ftparchive`, and describes why a proper archive generator is better for larger needs [src: debian-handbook 735ff8ff7daeb2a9]. `reprepro`, written by Bernhard Link, maintains a pool and the index files from a small configuration and signs automatically. `mini-dinstall` and `dak` (the real Debian archive software, powerful but heavy) are other options. `apt-mirror` and `debmirror` copy upstream archives.

**aptly.** `aptly`, begun by Andrey Smirnov around 2013 and written in Go, generalises these ideas for operators. It has *mirrors* (a local copy of a remote repository, optionally limited by filters on component, architecture and package name), *local repositories* into which you add your own `.deb` files, *snapshots* (immutable, named sets of packages, which are the building block for the next topic), and *publishing* of a snapshot or repository under a prefix, with signing. Because the commands are scriptable and the state is a database plus a content-addressed pool, aptly became the usual choice for teams that want repeatable Debian-family publication without running `dak`.

**Pulp.** The Pulp project began at Red Hat for the Satellite product and was rewritten as Pulp 3, with a plugin architecture: a core that handles tasks, storage and a REST API, and plugins for content types (`pulp_rpm`, `pulp_deb`, `pulp_container`, `pulp_python`, `pulp_file` and others). Its model has become a reference for repository management. A *remote* describes where to fetch content from. A *repository* is a versioned container: every change (sync, add, remove) creates a new immutable *repository version*. A *publication* is the set of metadata generated for one version, and a *distribution* maps a URL path to a publication, so that clients see a stable address while the content behind it moves forward or back. A walk-through for Rocky Linux shows this chain with the `pulp` command-line client: creating a remote, syncing it into a repository, publishing the new version and creating a distribution [src: rocky-docs 7c15ca2810fcd391], [src: rocky-docs 2723d5df6e4ca2e2] and [src: rocky-docs 297af38b177d0f71]. The single-container deployment described there is useful for trying things out, while production deployments split the API, content and worker services and use PostgreSQL, Redis and shared or object storage [src: rocky-docs 80c529013c248dc6]. Pulp is also the engine inside Red Hat Satellite and Foreman/Katello (the following topics), so learning its vocabulary pays twice.

**Alternatives.** Artifact managers such as Sonatype Nexus and JFrog Artifactory host both formats and many others, with proxying and caching features; Uyuni and Foreman provide full lifecycle management. Plain `rsync` of an upstream mirror, combined with an HTTP server, is still a valid approach for a site with one distribution and no need to filter.

## Current state

**Making an RPM repository.** Put the `.rpm` files in a directory and run `createrepo_c /srv/repo/el9/x86_64/`. This writes `repodata/`. After adding packages, run `createrepo_c --update` on the same directory. Useful options include `--checksum sha256`, `--compress-type zstd` (to verify support on the oldest client you serve), `--distro` and `--revision` to mark the build, `--groupfile` for package groups, and `--workers` for parallel reading. Security advisories are added as `updateinfo.xml` with `modifyrepo_c`. Sign `repodata/repomd.xml` as described in the signing topic. A client definition has `baseurl`, `enabled=1`, `gpgcheck=1`, `repo_gpgcheck=1` and `gpgkey`. To check a repository, `dnf --repofrompath=test,http://host/path --repo=test list available` works without editing system configuration, and `repoquery`, `repoclosure` and `createrepo_c --check-pkg-info` find missing dependencies or inconsistent metadata.

**Mirroring RPM content.** `reposync` with `--newest-only`, `--arch`, `--download-metadata` and `--delete` mirrors a repository defined in a `.repo` file [src: man-pages 06a7cfc44bd589a2]. The usual pattern is to sync into a working directory, run `createrepo_c` if the metadata was not downloaded, and then switch a symlink or snapshot directory so that publication is atomic. The upstream distribution's own `rsync` mirrors are the better choice for a full mirror, and the Rocky documentation shows the Pulp alternative. Note that for subscription-based distributions (RHEL) content comes from entitlement-protected CDN URLs and the mirror needs client certificates; for vendors such as Red Hat the mirroring tool of choice is the one in their management product (to verify per vendor terms).

**Making a Debian repository.** The least-effort option is a flat repository: place `.deb` files in a directory, run `dpkg-scanpackages . /dev/null | gzip -9 > Packages.gz` (or `apt-ftparchive packages .`), then `apt-ftparchive release .` to produce `Release`, and sign it into `InRelease`. For a proper pool/dists layout use `reprepro` (`conf/distributions` declares codename, architectures, components and `SignWith`; `reprepro includedeb bookworm file.deb` adds a package) or `aptly`:

```
aptly repo create -distribution=bookworm -component=main site
aptly repo add site hello-site_1.0-1_all.deb
aptly snapshot create site-2026-11-15 from repo site
aptly publish snapshot -gpg-key=ABCD1234 site-2026-11-15 internal
```

An `aptly mirror create -architectures=amd64 -filter='Priority (required)' bookworm http://deb.debian.org/debian bookworm main` followed by `aptly mirror update bookworm` gives a filtered mirror. Filters reduce a mirror from hundreds of gigabytes to something that fits a modest disk, but a filter that omits a dependency yields a mirror with unresolved packages, so the `-filter-with-deps` option or a dependency check is needed.

**Pulp in practice.** After installing Pulp and the CLI, the sequence is: create a remote (`pulp rpm remote create --name el9-baseos --url ... --policy on_demand`), create a repository (`pulp rpm repository create --name el9-baseos --remote el9-baseos`), sync (`pulp rpm repository sync`), publish (`pulp rpm publication create --repository el9-baseos`) and create a distribution (`pulp rpm distribution create --name el9-baseos --base-path el9/baseos --publication ...`). The `policy` option is a key decision: `immediate` downloads all packages at sync time, `on_demand` downloads a package only when the first client asks for it and then caches it, which saves disk at the cost of dependence on the upstream during installs, and `streamed` never caches. Because every change makes a new repository version, rolling back means pointing the distribution at an earlier publication, and snapshots come for free. Pulp can also be told to sign metadata with a *signing service*, which is a script that Pulp calls to sign the file, so the key can live elsewhere. Pulp supports content from several remotes in one repository and promotion by copying content between repositories.

**Publication and atomicity.** Clients may fetch while a publish is in progress. The safe pattern is to build the new tree beside the live one and switch with an atomic rename or symlink, to write the index files last, and to keep old metadata for a short time since clients may hold references to it. `aptly publish switch` and Pulp distributions implement this; a hand-built mirror must do it explicitly. The Debian side has the extra tool `by-hash` (`Acquire-By-Hash`) which names index files by their checksum so that a client never sees a mismatched set.

**Hosting.** A repository is static files, so any HTTP server (nginx, Apache, object storage with a CDN) serves it. TLS protects privacy but not integrity, because signatures do that. Set cache headers sensibly: `repomd.xml` and `InRelease` change often and should be revalidated, whereas packages are immutable and cacheable. At fleet scale put mirrors or caches near the clients (per site or per cloud region); a caching proxy such as `apt-cacher-ng` for Debian-family clients and a plain caching reverse proxy for RPM repositories can cut upstream traffic when a full mirror is not needed.

**Retention and cleanup.** Without a policy a repository keeps every version ever added. Decide how many versions to keep (`createrepo_c` has no retention logic itself; `repomanage --old` or `dnf repomanage` finds old versions, aptly's `repo remove` and Pulp's retain-version settings handle it). Keep every version that any pinned snapshot or lifecycle stage still refers to, or the rollback described in the next topics will fail.

**Monitoring.** Alert on age of `repomd.xml` or `InRelease` (a sync that stopped), on repository size, on failed syncs and on signature expiry. Test repositories end to end with a canary client that runs `dnf makecache` or `apt update` against the published URL.

## Assessment: the good, the bad and the ugly

**The good.** Both index formats are simple, public and fast; a repository is cheap to host and trivially cacheable. `createrepo_c` and `apt-ftparchive` are small, dependable tools with no daemon to run. aptly's snapshots and Pulp's immutable versions make publication reproducible and rollback cheap. A local mirror gives independence from upstream outages and a controlled place to apply policy.

**The bad.** The simple tools do not manage lifecycle: no history, no promotion, no cleanup. aptly's database can become inconsistent after interrupted operations and its publishing is single-writer, which complicates parallel CI. Pulp is a real service with a database, a queue and workers; upgrades between releases need care and it has more moving parts than a team with one custom repository needs. Mirrors of large distributions take hundreds of gigabytes and hours to sync, and the first sync needs bandwidth planning. Debian's flat repository is simple but loses the pool structure and the multi-suite features. Client behaviour differs: `dnf` caches metadata aggressively and `apt` has by-hash and pipelining options that change what an interrupted publish looks like.

**The ugly.** Hand-copying packages into a directory and forgetting to regenerate metadata is a routine cause of incidents. A mirror with `--delete` pointed at the wrong directory removes a repository. Mirroring a subscription-gated vendor repository without checking the licence can be a contractual problem. And a "temporary" repository created for one project, with no owner, key rotation plan or monitoring, becomes the production source of a hundred machines within a year.

**Assumptions.** Tool options and defaults (compression types, the exact Pulp CLI syntax, supported policies) change between releases; the examples reflect the cited documentation and the author's recollection of recent versions, and should be checked against the installed versions (to verify).

## Applications beyond this domain

The structure of a signed index over immutable content, served as static files, appears in container registries (manifest lists and content-addressed layers), in Helm chart repositories (`index.yaml`), in Python and npm mirrors, in Go module proxies and in Flatpak and OSTree repositories. Pulp's plugin model handles several of these with the same repository-version, publication and distribution concepts. The idea of promoting an immutable version through environments, which Pulp and Katello implement, is the same as promoting a container image tag through staging and production. Kubernetes itself moved its package repositories to new community-owned locations with one repository per minor release, and its documentation explains how to check which repository a node uses and how to switch to another, which is a good real-world illustration of why repository addresses must be treated as configuration under management [src: kubernetes-docs 6cf479414ab2c467] and [src: kubernetes-docs 34d9f146d7cab195].

## Examples

**Example 1: a small internal RPM repository.** Copy `hello-site-1.0-1.noarch.rpm` into `/srv/repo/el9/noarch/`, run `createrepo_c /srv/repo/el9/noarch/`, sign `repodata/repomd.xml`, and serve `/srv/repo` with nginx. A client file contains `baseurl=https://repo.example.org/el9/noarch/` and the verification options. After adding version 1.1, run `createrepo_c --update` and `dnf upgrade` sees it.

**Example 2: a flat Debian repository.** In `/srv/repo/deb/` place `.deb` files, run `apt-ftparchive packages . > Packages`, compress it, run `apt-ftparchive release . > Release`, sign into `InRelease`, and use `deb [signed-by=/etc/apt/keyrings/example.gpg] https://repo.example.org/deb ./` on clients.

**Example 3: a filtered Debian mirror with aptly.** Create the mirror with architecture and component limits, update it, snapshot it, publish the snapshot with your key, and point clients at the published prefix. Repeat the update and snapshot weekly; each publication is a new immutable set.

**Example 4: Pulp for a Rocky mirror.** Follow the remote, repository, sync, publication, distribution chain from the Rocky guide with `on_demand` policy to keep disk use low; test by pointing a client at the distribution URL. Rollback is a distribution update to the previous publication.

**Example 5: capacity estimate.** A site mirrors BaseOS and AppStream for one major release and one architecture. Allow a few hundred gigabytes for packages with all versions retained, an order of magnitude less with `--newest-only`, and plan for sync windows and for a second copy for snapshots (to verify against current repository sizes).

**Worked failure: the half-published mirror.** A nightly job syncs a mirror in place. At 02:10 the index has been replaced but 40 packages are still downloading. A patch job starting at 02:12 reports 404s for those packages and aborts. The fix is to sync into a staging directory, validate with `createrepo_c --check`, and then swap a symlink, so clients never see a partial state.

## Related problems and ideas

This topic leads into **dated snapshots** (freezing a view of a repository, covered next), **content views and lifecycle environments** in Katello, and **patch rings**, which rely on repositories that change in a controlled way. It depends on **signing**, because a mirror is only as trustworthy as its signatures. **Container registries and image mirrors** solve the same problem for another content type, and **proxy caches** (apt-cacher-ng, Squid) offer a lighter-weight alternative to a full mirror. **Reproducible builds** decide whether the packages in a repository can be rebuilt on demand. **Backup** matters too: the repository is derived data when it mirrors upstream, but the internal packages in it are not, and their sources and signing keys must be backed up.

## Active research

Work in this area concerns more efficient metadata (zstd compression, smaller or incremental index formats so that a client's refresh costs less), content-addressed storage for packages across distributions, verifiable and transparent repositories (transparency logs for package indexes), and better synchronisation protocols between mirrors than whole-directory rsync. Pulp's roadmap includes better support for large-scale deployments and new content types; Debian explores a successor to the `Packages` index format and more use of by-hash and signed-by-key mechanisms. Researchers and distribution teams also study mirror consistency and the effects of mirror lag on security updates.

## Future direction

Expect repositories to become more tightly tied to immutable versions and snapshots, with signature and provenance data stored beside the content. Expect Pulp-like repository-version semantics in more tools, and expect images (bootc, OSTree) to take over some of the roles that package repositories play for base systems, while packages remain the unit for software layered on top. For the operator, the durable skill is the discipline described here: build the new state aside, validate it, publish atomically, keep history, and write the retention policy down.
