# Katello content views and lifecycle environments for managed fleets

## Define the problem

Once an organisation has dozens or hundreds of Enterprise Linux machines, three questions keep returning. Which exact software may each machine install? Who decides when a new set of updates reaches which group of machines? How can anyone prove, afterwards, what a machine was offered at a given time? The previous topics gave the parts of an answer: repositories, signatures and frozen snapshots. A management platform joins those parts to a machine inventory, registration, entitlement and an approval workflow. In the Red Hat world that platform is **Red Hat Satellite**, and its upstream community project is **Foreman** with the **Katello** plugin. Katello supplies content management: it syncs repositories (using Pulp), organises them into products, freezes selections as *content views*, and promotes versions of those views through *lifecycle environments*. Foreman supplies host provisioning, inventory and reporting. SUSE's Uyuni and SUSE Multi-Linux Manager, Canonical's Landscape and Ansible-based approaches fill the same role for other platforms.

The practical problem is design, not installation. Content views can be built in ways that produce a large, slow, confusing system: dozens of overlapping views, filters that nobody can explain, promotion paths with too many stages, or a single view for everything that makes every change a fleet-wide event. The goal of this topic is to understand the object model, to build a small design that is easy to operate, and to know how the content flows into a registered host. The topic is rated as a "see it" exercise, meaning that it needs a Satellite or Katello server that most learners do not have. The material therefore concentrates on concepts, decisions, command-line examples and a planning exercise.

Typical failure modes: a content view that is published but never promoted, so hosts do not see the new content; hosts that are registered to the wrong lifecycle environment and therefore receive production updates a week early or a month late; a filter that excludes a package that other packages require, giving dependency errors on clients; a composite view that pulls in a component view version nobody expected; a missing repository in the view that blocks an in-place operating system upgrade (the Red Hat upgrade documentation makes this explicit for Satellite-registered systems, requiring the target repositories to be in the content view and in the activation key [src: rhel-10-docs 0454e83d367f2bf6]); sync plans that overload the server; and database and storage growth from keeping every version.

## History and approaches

Centralised package distribution for Red Hat systems started with Red Hat Network and its on-site product, Satellite, later built on the open-source **Spacewalk** project (2008). Spacewalk organised software into *channels* and let administrators clone a channel, which gave a crude snapshot. Satellite 5 and Spacewalk used a Java and Oracle/PostgreSQL stack, and their successors diverged: Uyuni forked Spacewalk and became the basis for SUSE Manager, while Red Hat rebuilt its product on Foreman and Katello (Satellite 6, 2014). The newer design separated concerns into Foreman (hosts, provisioning, configuration), Pulp (storage and sync of content, with Pulp 2 giving way to Pulp 3 in recent releases; see the earlier topic for the model), Candlepin (subscriptions and entitlement) and Katello (the glue that provides the content management API and UI).

The design principle Katello embodies is that *content is a versioned artefact and hosts consume a version through an environment*. The core objects are:

- **Product** and **repository**: a product is a group of repositories from one source (for example "Rocky Linux 9" or "Site software"), and a repository points at a upstream URL or holds uploaded packages. Repositories sync on a **sync plan** (daily, weekly) and can limit what they download using the download policy (immediate or on demand), the same choice as in Pulp.
- **Content view (CV)**: a named selection of repositories, optionally with *filters* that include or exclude packages by name, version or errata (by date range, by type such as security or bugfix, or by ID). A content view is a *definition*; nothing is delivered until it is *published*.
- **Content view version**: each publication creates an immutable, numbered version (1.0, 2.0 and so on; minor numbers can mark incremental updates) containing the exact packages that matched at that moment. This is the snapshot.
- **Lifecycle environment**: a named stage, for example Library, Dev, Test, Prod, arranged as a path. Library is the special first stage where synced content lands. A content view version is *promoted* to an environment, which makes it available there. An environment holds one version of each content view at a time.
- **Composite content view**: a view built from other content views (component views) at specified versions, useful for combining an operating system view maintained by one team with an application view maintained by another.
- **Activation key**: a reusable registration recipe tying a host to an organisation, a lifecycle environment, a content view, subscriptions and default repository settings. A host registered with a key sees only the repositories from that view version in that environment.
- **Errata and incremental updates**: Katello imports errata (advisories) from upstream, shows which hosts are applicable, and supports an *incremental update* that creates a new minor version of a view containing only selected errata, which can be promoted fast in an emergency.

Alternatives show different trade-offs. **Uyuni** and SUSE Multi-Linux Manager use *content lifecycle management projects* with sources, filters and environments, much like content views, with Salt as the agent. **Landscape** for Ubuntu provides repository profiles and mirror pockets. **Foreman without Katello** manages hosts and provisioning but leaves content to other tools. **Pulp alone**, with scripts for promotion as in the earlier topics, gives the same effect with more manual work and less accounting. **AWX/Ansible Tower** can run `dnf` against pinned repositories but has no content model of its own.

## Current state

**Architecture.** A Satellite or Katello server runs Foreman (Rails), Candlepin, Pulp and PostgreSQL, with Puppet or Ansible integration optional. Large sites add **Capsules** (Satellite's name for Smart Proxies), which are remote servers that mirror selected lifecycle environments and serve hosts at a site or region, so that WAN traffic crosses once. Hosts talk to the Capsule that fronts their location. Sizing is driven by the amount of content (disk for repositories and their versions), the number of hosts (concurrent registrations and updates) and the sync schedule, and vendor guidance lists CPU, memory and storage tiers (to verify for the version you install).

**Hammer CLI.** The `hammer` command mirrors the API and makes designs scriptable:

```
hammer product create --organization Site --name "Rocky 9"
hammer repository create --product "Rocky 9" --name baseos --content-type yum \
  --url https://dl.rockylinux.org/pub/rocky/9/BaseOS/x86_64/os/ --organization Site
hammer repository synchronize --product "Rocky 9" --name baseos --organization Site
hammer content-view create --name cv-base --organization Site
hammer content-view add-repository --name cv-base --product "Rocky 9" --repository baseos --organization Site
hammer content-view publish --name cv-base --organization Site
hammer content-view version promote --content-view cv-base --version 1.0 \
  --to-lifecycle-environment Dev --organization Site
hammer activation-key create --name ak-dev --lifecycle-environment Dev \
  --content-view cv-base --organization Site
```

Names of options vary slightly between releases; use `hammer <command> --help` on your version (to verify).

**Registration.** A host is registered with `subscription-manager register --org=Site --activationkey=ak-dev` (for Red Hat and compatible clients), which creates a host record, configures the yum repositories to point to the Satellite or Capsule URLs for that environment and view, and installs the `katello-ca-consumer` certificate. Katello also supports registration through a generated command (a `curl | bash` style script with a short-lived token, which is convenient but means the token's handling needs care) and through Ansible modules.

**Filters.** Filters are the most powerful and the most misused feature. An *include* filter limits the view to the listed content; an *exclude* filter removes matching content from an otherwise complete set. Errata filters by date ("everything up to the 15th") reproduce a point-in-time snapshot, which is the usual way to get dated behaviour from a mirror that tracks upstream. A package-name filter is a blunt instrument: excluding a library that other packages require breaks resolution on clients, so every filter set should be tested by installing and updating on a canary host. Keep filters few, documented and owned.

**Design guidance.** The following rules of thumb reduce complexity.

1. *One view per role, not per host.* Start with a single "base operating system" view and add application views only when a team needs a different update cadence.
2. *Few lifecycle environments.* Three or four (Dev, Test, Prod, or Canary and Prod) are usually enough; every environment is a promotion to remember. The path can be a straight line or have branches for separate business units.
3. *Composite views for combinations only*, with component versions pinned or set to "latest" deliberately. "Latest" means that publishing a component view alters the composite on its next publish.
4. *Automate publish and promote* from a pipeline using `hammer`, the API or the Ansible `foreman` collection, with a record of who approved each promotion.
5. *Clean up versions.* Set retention (keep the last N versions or those used by any environment) and run the cleanup task; unmanaged growth is the commonest operational problem.
6. *Use incremental updates sparingly* for emergencies. They create versions that diverge from the regular line and should be folded back by the next full publish.

**Patch windows.** Katello shows for each host the applicable errata, and the host's **errata status**. An *errata installation* can be scheduled from the UI or API (`hammer host errata apply`, or remote execution jobs) and combines with the lifecycle environment: promoting a view version to Prod makes its errata available, but only a job or a client-side `dnf` run installs them. Tie remote execution to the patch rings in the next topic.

**Upgrades of the operating system.** In-place upgrades with Leapp or Red Hat's upgrade tooling need the repositories for both the source and target versions to be in the host's content view and activation key, as the RHEL upgrade guide for Satellite-registered systems states, including the detail that enabling only the generic target-version repositories without the minor-version ones inhibits the upgrade [src: rhel-10-docs 0454e83d367f2bf6]. Plan the views for an upgrade campaign: a new view with both repositories, tested on a canary, then promoted.

**Image builder and image mode.** The RHEL image builder can use Satellite as the source of packages through custom repositories, which keeps image content aligned with content views [src: rhel-10-docs 3547624fa0f1810d] and [src: rhel-10-docs bae5dfd77cfe7fe1]. The same principle (build from a controlled snapshot) appears in the later topics on image-based delivery.

**Monitoring and backup.** Watch sync task failures, the age of the last successful sync of each repository, free disk on `/var/lib/pulp`, the PostgreSQL database size, the Candlepin subscription count and the Capsule sync status. Back up with the supported `satellite-maintain backup` (or `foreman-maintain` on the community version) and test a restore, because the server is the source of truth for host registration and content state.

**Non-Red Hat clients.** Katello can manage content for Rocky Linux and Alma clients (as yum repositories) and, with `pulp_deb`, Debian-family content in recent versions, with different feature maturity (to verify). Registration of non-Red Hat hosts uses a `katello-host-tools` style agent or a plain repository definition rather than `subscription-manager`.

## Assessment: the good, the bad and the ugly

**The good.** Content views make the snapshot-and-promote model into a product feature with an API, an audit trail and a user interface. Activation keys make registration consistent. Errata awareness lists the hosts that an advisory applies to, without extra tooling. Capsules scale content delivery across sites. Because Katello exposes everything through an API, a design can be code-reviewed and repeated across organisations.

**The bad.** The server is a heavy system with many components and a steep operating cost: upgrades, database tuning, storage growth and certificate management are non-trivial. Terminology is dense and inconsistent between versions, and the interface has changed. The model assumes hosts register to it, which is awkward for immutable images or short-lived machines that never register. Filters invite complexity, composite views complicate reasoning, and the promotion path is a straight line by default, so branching workflows require care. Capacity needs are large when many versions of big repositories are kept. Community Katello and commercial Satellite differ in versions, supported clients and fixes, so documentation from one does not always apply to the other.

**The ugly.** A single view for the whole company, republished by anyone with rights and promoted to production by a scheduled job, recreates the problem snapshots were meant to solve. Hosts left registered to the Library environment receive content straight from the sync. Capsule certificates expire. And an organisation that adopts the platform without deciding who approves promotions ends up with the same ad hoc patching, now recorded in a database.

**Assumptions.** The object model described is stable across recent versions, but command options, supported client types and sizing numbers are version-specific and come from the author's knowledge and the cited documentation. Check them against the release you run (to verify).

## Applications beyond this domain

Content views are an instance of the **promotion pipeline** pattern: build an immutable artefact once, then move it through environments with gates. The same shape appears in container registries (promote a digest from `dev` to `prod` repositories), Helm and GitOps (a commit hash promoted by merging to an environment branch), Terraform workspaces and release trains for mobile software. The vocabulary of *definition, version, environment and activation* maps onto any of them. The registration model (a host receives a recipe and then pulls what it is allowed to) is also the model of configuration management and of device management in general.

## Examples

**Example 1: a minimal design for 200 hosts.** One product per upstream (Rocky BaseOS, AppStream, EPEL, the site repository), one content view `cv-el9` with all four repositories and an errata date filter on the upstream ones, three environments Dev, Prod-Canary and Prod, and activation keys `ak-dev`, `ak-canary` and `ak-prod`. Weekly pipeline: sync on Sunday, publish on Monday, promote to Dev, then to Canary on Wednesday and Prod on the following Tuesday.

**Example 2: an emergency fix.** A critical advisory appears on Thursday. Create an incremental update of the current Prod version containing only the advisory's packages, promote it to Prod, schedule a remote execution job for the affected hosts, and at the next regular publish fold the advisory into the main line.

**Example 3: a composite view.** The platform team owns `cv-el9`, the database team owns `cv-pgsql`. A composite `ccv-db` combines the two at fixed versions, promoted by the database team. A change to `cv-el9` does not alter database servers until their composite is republished.

**Example 4: a registration check.** On a client, `subscription-manager identity` shows the organisation and environment, `dnf repolist` shows the repositories served for that view version, and `dnf updateinfo list` shows the applicable advisories. A host that shows Library as its environment is a defect to fix.

**Example 5: clean-up.** Keep the last five versions of each view plus any version in an environment. Run the clean-up task weekly and check disk use. Record the rule in the runbook so that nobody deletes versions by hand.

**Worked failure: the promoted-but-not-visible update.** An administrator publishes `cv-el9` version 12 and sees it in the Library, but Prod hosts report nothing to update. The cause is that publishing does not promote. The fix is to promote to the environment, and the lesson is to make the pipeline do both steps with a recorded approval between them.

## Related problems and ideas

The topic sits between **snapshots** (previous topic), which it productises, and **patch rings** (next topic), which decide when each environment is promoted. It depends on **registration, subscriptions and certificates**, on **provisioning** (Foreman builds hosts with kickstart and PXE, covered in the provisioning course) and on **configuration management** (Ansible roles run through remote execution). **Image-based delivery** replaces per-host content views with image versions but keeps the promotion idea. **Vulnerability management** tools read the same errata data. **Disaster recovery** of the management server is a topic in its own right, because a lost Satellite means losing the record of what each host was entitled to.

## Active research

Directions of active work include moving the content engine fully to Pulp 3 with better performance for very large repositories, simplifying registration with short-lived tokens and global registration templates, integrating image builds and bootc content with content views, richer reporting on host compliance and vulnerability exposure, and making the model work for hosts that are rebuilt rather than patched. Vendors also explore using the same inventory to drive upgrades between operating system major versions at scale.

## Future direction

Expect the content-view model to survive in simplified form: version-pinned content sets, promoted by pipeline, plus a registry-like view for images. Expect agentless or pull-based patching through image replacement to reduce the share of hosts that need per-host content management, while long-lived servers continue to need it. For the operator, the lasting lessons are to keep the object model small, to automate and record promotions, to give every host a clear environment, and to size and back up the server as a core service rather than a convenience.
