# Packaging for Debian and Ubuntu: debhelper, dpkg and clean-chroot builds

## Define the problem

The Debian family of distributions (Debian, Ubuntu, Mint and their derivatives) is common on servers, in containers and in cloud images, and its package format, the `.deb`, is the unit of software delivery there. An organisation that runs such systems faces the same needs described for RPM: it must package software the distribution lacks, patch or backport software the distribution has, and ship site tools and configuration as versioned, verifiable, upgradable units. The Debian approach to this is distinctive in two ways. Debian Policy, a long document maintained by the project, standardises how packages behave (file locations, maintainer scripts, configuration handling, dependency semantics) so that thousands of independently maintained packages interoperate. And the tooling for building has been shaped around a *convention over configuration* approach: a package describes what is special about it, and a toolkit called **debhelper** performs the routine work.

The problem this slice addresses is therefore how to turn upstream source into a policy-compliant `.deb` repeatably: how the `debian/` directory is laid out and what each file does, how debhelper drives the build through the `dh` command sequencer, how dependencies and version numbers are expressed, how the package is built in a clean environment so that its declared build dependencies are the only ones it used, and how the result is checked with `lintian` before publication. A package built carelessly can break a system on upgrade, overwrite administrator changes to configuration, leave files behind on removal, or depend on a library that is not installed on the target.

Typical failure modes: a package that builds only because the maintainer's machine had a development library installed; a `postinst` script that is not idempotent and fails on the second run; a conffile that is replaced on upgrade and discards the local edits; a version string that sorts below the one already installed so that apt never offers the upgrade; a binary that depends on a library through a stale `shlibs` entry; a source package that cannot be rebuilt because a download was part of the build. The scope covers source package formats, the `debian/` files, debhelper compatibility levels and `dh`, dependency substitution variables, version comparison, building with `dpkg-buildpackage`, `debuild`, `pbuilder` and `sbuild`, and checks. Signing and repositories appear in later topics, and the RPM counterpart in the previous one.

## History and approaches

Ian Murdock started Debian in 1993, and the first package tools (`dpkg`) came from Ian Jackson, who also designed the binary package format: an `ar` archive containing `debian-binary` (the format version), `control.tar.*` (metadata and maintainer scripts) and `data.tar.*` (the files). Early Debian packages were built by hand-written `debian/rules` makefiles, one per package, each implementing the same steps a little differently. The result was inconsistency, so in 1997 Joey Hess wrote **debhelper**, a collection of small commands (`dh_installdocs`, `dh_installinit`, `dh_strip`, `dh_compress`, `dh_shlibdeps`, `dh_builddeb` and many more), each doing one standard task and driven from `debian/rules`. Policy changes could now be implemented once in the helper, and packagers inherited them by rebuilding. A later layer, **CDBS**, tried to hide the rules file behind more makefile macros and has largely been abandoned. The most important simplification was `dh` (the sequencer, 2008): `debian/rules` shrank to a few lines, `%:` followed by `dh $@`, and the sequencer runs every debhelper command in the right order, with overrides for the few steps that need to differ (`override_dh_auto_configure:`).

Compatibility levels are the mechanism by which debhelper changes behaviour without breaking old packages. Each package states a level (today by writing `debhelper-compat (= 13)` in `Build-Depends`, which replaced the older `debian/compat` file), and newer levels switch on stricter defaults (for example, that `dh_installinit` handles systemd units, that `dh_auto_*` uses `--parallel`, and that the packages' files are processed in a specified order). The man page for debhelper describes the build-system options, the environment variables that govern behaviour, and the compatibility policy [src: man-pages a65b5c14503ff845].

Source packages also evolved. The original format 1.0 was a pristine tarball plus a single diff, which mixed packaging and upstream changes. Format **3.0 (quilt)** keeps the upstream tarball unchanged, the Debian-specific files in a `debian/` tarball or directory, and upstream modifications as separate patches in `debian/patches/` managed with a series file, so each patch can be documented, reviewed and sent upstream. Format 3.0 (native) is for software written by and for Debian. Another long-running trend was the **clean build environment**. In 2001 Junichiro Hasegawa's `pbuilder` created a base chroot tarball and unpacked it for each build; `cowbuilder` sped it up with copy-on-write; Debian's own build daemons use **sbuild** (Roger Leigh, 2000s), which drives schroot-managed chroots or newer back ends (`unshare`, containers) and records a build log. Rebuild tools use `mmdebstrap` and `debootstrap` to create the chroots. The Debian handbook walks through the maintainer path from rebuilding a package from sources, through modifying it, to becoming a maintainer [src: debian-handbook 7073eb742756eae4]. Its section on rebuilding shows `apt source`, `apt build-dep`, changing the source and calling `dpkg-buildpackage` [src: debian-handbook eb987c281240e727].

The packaging world around these tools changed too. Version control moved packaging into Git with `git-buildpackage` (`gbp`), which imports upstream releases, applies patches and builds; Salsa, Debian's GitLab, runs CI pipelines that include `lintian`, `autopkgtest` and reproducibility checks. **autopkgtest** (DEP-8) tests an installed package in a clean VM or container, which finds missing runtime dependencies that a build cannot. The Reproducible Builds project pushed `SOURCE_DATE_EPOCH`, deterministic archive ordering and the removal of build paths from outputs, and by the 2020s the majority of packages in Debian's stable releases rebuild bit for bit (the exact proportion should be checked against the project's dashboard, to verify). Ubuntu adds Launchpad, with Personal Package Archives (PPAs) that build uploaded source packages for several series, which is the closest equivalent to COPR.

## Current state

**The source tree.** A Debian source package for an upstream project `hello-site` version 1.0 is a directory containing the upstream files and a `debian/` subdirectory. The mandatory files are:

- `debian/control`: a source stanza (`Source`, `Section`, `Priority`, `Maintainer`, `Build-Depends`, `Standards-Version`, `Rules-Requires-Root`, `Homepage`) and one or more binary stanzas (`Package`, `Architecture`, `Depends`, `Description`). `Build-Depends` includes `debhelper-compat (= 13)` and every build tool and library header. In `Depends` the packager writes `${shlibs:Depends}, ${misc:Depends}`, substitution variables that the tools fill in from the analysis of the built files.
- `debian/changelog`: a strict format, one stanza per version, whose first line gives source name, version in parentheses, target distribution and urgency, and whose trailer line names the maintainer and date. The top stanza *defines the version being built*. `dch` (from `devscripts`) edits it: `dch -i` adds an entry, `dch -r` marks it for release.
- `debian/rules`: an executable makefile. The minimal form is `#!/usr/bin/make -f` and `%:` `dh $@`. Overrides adjust single steps.
- `debian/copyright`: machine-readable (DEP-5) licence information for the source and for packaging.
- `debian/source/format`: `3.0 (quilt)` or `3.0 (native)`.

Optional but common: `debian/<package>.install` (which files from the staging directory go into which package), `.dirs`, `.docs`, `.manpages`, `.service` (systemd unit, installed by `dh_installsystemd`), `.postinst`, `.prerm`, `.postrm` (maintainer scripts), `.conffiles` (generated automatically for files under `/etc`), `debian/patches/series`, `debian/watch` (upstream version tracking with `uscan`), `debian/tests/control` for autopkgtest and `debian/gbp.conf`.

**What `dh` does.** The sequencer maps a requested target to an ordered list of helper commands. `dh_auto_configure`, `dh_auto_build` and `dh_auto_test` detect the build system (autotools, CMake, Meson, Python setuptools, Makefile) and run it with the distribution's standard flags; `dh_auto_install` installs into `debian/<package>/` (or `debian/tmp`). The other helpers then handle documentation, manual pages, compression, stripping with separation of debug symbols (`-dbgsym` packages), dependency detection (`dh_shlibdeps` examines ELF files and writes `shlibs:Depends`), service files, maintainer-script snippets inserted at the `#DEBHELPER#` token, md5sums, and finally `dh_builddeb`. `dh_missing --fail-missing` makes an uninstalled file an error, which prevents a new upstream file from being silently left out. Overrides look like:

```make
#!/usr/bin/make -f
%:
	dh $@

override_dh_auto_install:
	dh_auto_install -- prefix=/usr
	install -D -m 0644 hello-site.conf debian/hello-site/etc/hello-site.conf
```

**Dependencies and versions.** `Depends` are required at install, `Pre-Depends` before unpacking (rare, for packages whose maintainer script needs them), `Recommends` are installed by default but may be skipped, `Suggests` are informational, `Conflicts`, `Breaks` and `Replaces` handle file moves and incompatibilities. Relations take version constraints (`(>= 1.2)`), alternatives with `|`, and architecture and build-profile qualifiers. The version of a package has the form `[epoch:]upstream_version[-debian_revision]`. Comparison treats letters and digits in alternating runs, and the tilde `~` sorts *before* the empty string, so `1.0~rc1` is older than `1.0`. This is the correct way to give pre-releases and backports versions that are lower than what follows: backports use `1.0-1~bpo12+1`, Debian security updates use `+deb12u1`. `dpkg --compare-versions 1.0~rc1 lt 1.0` tests a comparison in a script. A site that rebuilds a package for its own repository should use a suffix that sorts above the vendor's version for the same upstream release (for example `1.0-1+site1`), so that clients prefer it, and should plan its removal.

**Building.** The simplest build is `dpkg-buildpackage -us -uc -b` in the source tree, which produces `../hello-site_1.0-1_all.deb` and a `.changes` file listing the files of the upload; `-S` builds only the source package and `-A` only architecture-independent packages. `debuild` wraps it with `lintian`. Because the build runs on the current system, the result depends on what is installed on it. The clean alternative is a chroot or container builder: `sbuild -d bookworm hello-site_1.0-1.dsc` (after creating a chroot with `sbuild-createchroot`, or `mmdebstrap` with the `unshare` back end for rootless builds) installs only the `Build-Depends` closure, builds, and runs `lintian` and optionally `autopkgtest` and a piuparts install test. `apt-get build-dep` installs dependencies on the host for ad-hoc work, and `pbuilder`/`cowbuilder` with `--basepath` provide a similar flow. For multiple targets, `gbp buildpackage --git-pbuilder` or `gbp buildpackage --git-builder=sbuild` takes the source from Git.

**Inspecting and checking.** `dpkg-deb -I package.deb` prints control fields and scripts, `dpkg-deb -c` lists contents, `dpkg-deb -x` extracts, `dpkg -L` lists installed files, `dpkg -S /path` finds the owning package. `lintian` reports errors (E:), warnings (W:) and informational notes with a tag name, and `lintian-explain-tags` explains them; many sites run it with `--fail-on error,warning` in CI. `piuparts` installs, upgrades and removes in a chroot to catch maintainer script faults, and `autopkgtest` runs functional tests. Maintainer scripts must follow the Policy flow: they receive actions such as `configure`, `abort-upgrade` and `remove` as the first argument, must be idempotent, and should use the debhelper-generated snippets (`dh_installsystemd`, `dh_installdeb`) in place of hand-written logic; the manual page for `dh_installdeb` documents the substitutions available in maintainer scripts [src: man-pages 19fe0f30e77752ed].

**Configuration files.** Files under `/etc` shipped by the package are *conffiles*. On upgrade, dpkg compares three versions (the one originally installed, the one on disk, and the new one) and asks the administrator only when both the disk and the package versions changed; with `--force-confold` it keeps the local file, `--force-confnew` takes the new one. Packages that manage their configuration by other means (`ucf`, generated files) must still follow the principle that local changes are never discarded silently.

**The generalised pattern.** A Debian package build is: *source with declared dependencies and policy-defined metadata* → *deterministic helper pipeline* → *binary packages with substituted dependencies* → *lint, install and upgrade tests in a clean root* → *signed upload* (the topic that follows). The consistency comes from the shared helper pipeline and from Policy, which together make a package behave predictably for people who have never seen it.

## Assessment: the good, the bad and the ugly

**The good.** The model of a pristine upstream tarball, separate documented patches and a tool pipeline that applies policy gives packages that are consistent and reviewable. `dh` lets a simple package be built from a ten-line `debian/` directory. Clean builds, `lintian`, `piuparts` and `autopkgtest` are standard, free and well integrated, and the reproducible-builds effort has made bit-for-bit rebuilds a realistic expectation. The three-way conffile handling protects administrator edits better than most formats. The Debian handbook's guidance from source rebuild to maintainer is a practical entry point.

**The bad.** The learning curve is steep: a newcomer must learn Policy, the tools, the compatibility-level rules and a pile of conventions, and the same task can be done in several historically different ways, so older tutorials mislead. The `debian/` directory spreads one package's logic across many files. Policy compliance is a goal that sometimes conflicts with upstream's habits (bundled libraries, build-time downloads, prebuilt binaries), and the usual answer, repacking the tarball to remove files, adds work. Backporting to an older release can require rebuilding a chain of dependencies. Debian and Ubuntu differ in tooling, versions and defaults, so one `debian/` directory does not always serve both without adjustments.

**The ugly.** Maintainer scripts are the main source of real damage. A script that is not idempotent, assumes systemd is running, or calls a service that is not installed yet fails inside container builds and image creation, and a failed `postinst` leaves a half-configured package that blocks later upgrades until fixed by hand. Version arithmetic traps people: a missing epoch when upstream renumbers (2.0 followed by 1.9), the tilde confusion, and a local suffix that sorts below the vendor update so the site's patched package is silently replaced. The dependency substitution can hide errors: `${shlibs:Depends}` records what the build found, so a library loaded with `dlopen` is not seen and needs a manual `Depends`. Builds that touch the network, or depend on the host's timezone, locale or user name, fail to reproduce. Finally, tools that work on the host rather than in a chroot (`dpkg-buildpackage` alone) hide missing `Build-Depends` until another person builds the package.

**Mitigations.** Build only in a clean chroot or container (`sbuild`, `pbuilder`, `mmdebstrap`-based CI) and treat host builds as drafts. Run `lintian` with a failing threshold, `piuparts` for install, upgrade and removal, and `autopkgtest` for function. Use `dh_installsystemd` and the other helpers in preference to hand-written scripts. Version local rebuilds with a clear convention and test with `dpkg --compare-versions`. Keep `debian/` in Git with `gbp`, and write patch headers (DEP-3) saying why and whether sent upstream. Use `Rules-Requires-Root: no` and `fakeroot` so the build never needs root.

## Applications beyond this domain

Debian's packaging model has had influence outside the format. The clean-chroot build is the ancestor of container-based CI builders. The pristine-source-plus-patches discipline (quilt) appears in Fedora's patch handling, Gentoo's `PATCHES` array, Yocto's `.bbappend` patches and in Linux kernel stable-patch workflows. Debian's version comparison algorithm is used by tools beyond dpkg (apt, Ubuntu's Launchpad, vulnerability scanners that compare package versions against advisories, as the vulnerability topic of the previous course describes). The Reproducible Builds project's techniques are used across ecosystems. The DEP-5 machine-readable copyright format underlies licence-scanning tools, and `debian/watch` style automation for upstream tracking appears in Renovate and Dependabot. Ubuntu Core, and Debian-based container base images (the Docker `debian` and `ubuntu` images), are built from packages assembled with the same tools.

## Examples

**A first package.** A team packages `hello-site`, a single script and a config file. The `debian/` directory has `control` (with `Architecture: all`, `Depends: ${misc:Depends}`), `changelog` created by `dch --create`, `rules` with the `dh $@` line, `copyright`, `source/format`, and `hello-site.install` listing `hello-site usr/bin/` and `hello-site.conf etc/`. `dpkg-buildpackage -us -uc -b` produces a `.deb`, and `lintian` points out a missing manual page, which they add.

**Backport to an older release.** The distribution ships version 2.1 of a library; the site needs 2.4. The packager takes the newer source package from the next release, adjusts `Build-Depends` to what the older release has, changes the changelog to `2.4-1~bpo12+1`, and builds in an sbuild chroot for the older release. After testing, the package goes into the site repository at a priority that prefers it, and a ticket tracks removal when the release upgrades.

**A failing example: the host build.** A developer builds on a workstation that has `libssl-dev` installed but forgot it in `Build-Depends`. The CI builder, using sbuild, fails at configure. The fix is a one-line change in `control`, and the same CI job now guards against the class of error.

**A failing example: the non-idempotent postinst.** A `postinst` creates a user with `adduser` without checking for existence and runs `systemctl restart`. Installing in a container image fails because there is no systemd, and re-installing fails because the user exists. Replacing it with the debhelper-generated snippets (`dh_installsysusers`, `dh_installsystemd`) fixes both.

## Related problems and ideas

The closest neighbour is the RPM method of the previous topic, with differences in how patches, macros and build roots are handled. Other Debian-family approaches include **Ubuntu Snaps** (bundle-based, sandboxed packaging by Canonical) and **checkinstall** or **fpm**, which wrap an existing install into a `.deb` and bypass Policy, producing packages that work but cannot be rebuilt from source. **Nix** and **Guix** offer functional builds. **Alpine's APKBUILD** and **Arch's PKGBUILD** are simpler recipe formats with fewer guarantees. The `debootstrap` and `mmdebstrap` family makes minimal root file systems and is used to build container base images. Newer ideas include **source-only uploads with centrally built binaries** (which Debian requires for most uploads now, to be verified) and rebuilds by independent parties compared against the official binaries.

## Active research

Open questions revolve around reproducibility at scale (remaining sources of non-determinism, such as build paths and file ordering, and rebuilders' infrastructure for continuous verification), safe handling of language ecosystems' vendored dependencies in a Policy world, faster and better package formats (zstd compression in `.deb` archives, supported in dpkg since 1.21.18, to verify), and the formal verification of maintainer-script behaviour. Researchers have also studied the dependency graph of the archive for resilience and for installability, which the `dose` tools analyse, and the amount of software in the archive that is bundled.

## Future direction

Expect `debian/` packaging to continue its slow simplification: declarative files in place of shell scripts, `dh` sequencing, more automated upstream tracking, and CI that runs the whole quality pipeline on every commit. Expect rootless, container-based clean builds to become the default for sites outside the distribution. Expect signed provenance for builds and independent rebuild verification to become a normal publication step. For the operator who maintains a few site packages, the lasting practices are: build in a clean root, lint and test upgrade and removal, version carefully, and keep the packaging in version control with the reason for every patch.
