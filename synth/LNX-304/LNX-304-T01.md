# Building RPM packages that survive a clean room: spec files, rpmbuild and mock

## Define the problem

Software reaches a Linux fleet as packages, and a package is only as trustworthy as the process that made it. A tarball compiled on an administrator's workstation and copied to servers works until nobody can say which compiler, which headers and which patches produced it. The need is a repeatable recipe that turns source into an installable, upgradable, removable, verifiable artefact, together with a build environment that contains exactly what the recipe declares and nothing else. The RPM Package Manager answers with three pieces: a **spec file**, which is the recipe; **rpmbuild**, which executes it in staged phases; and **mock**, which runs rpmbuild inside a disposable chroot (or container) populated only from declared build dependencies.

For a fleet operator the problem has several sides. A vendor does not ship what is needed (a patched daemon, a site-specific agent, a backport, an internal tool) so the organisation must package it. The package must integrate with the system: files in the right places with the right ownership and permissions, configuration that is not overwritten on upgrade, services that are enabled and restarted correctly, dependencies that resolve, and a clean removal. The build must be reproducible across developers and CI, so that the binary installed in production can be traced to a source revision. And the resulting packages must be signed and published, which later topics cover.

Failure takes recognisable forms. A package built on a developer machine silently links against a library that exists there and not on servers, because the build was not isolated. A `%post` scriptlet that restarts a service fails on a fresh container install and leaves the package half installed. A configuration file marked wrongly is replaced on upgrade and an outage follows. A spec that bundles its own copy of a library hides a vulnerability from scanners. A release number that is not bumped means an upgrade is not offered. This slice covers the RPM file format at the level an operator needs, the structure of a spec file, the build phases, scriptlets and dependency handling, building in mock, the surrounding tooling (rpmlint, rpmdev, koji, COPR), and the practices that make builds repeatable. Signing, repositories and snapshots follow in later topics.

## History and approaches

Software installation on early Unix was `make install` into `/usr/local`, with no record of what was installed. Red Hat's RPM, written by Marc Ewing and Erik Troan in 1995 and extended by Jeff Johnson afterwards, introduced a database of installed files, versions and dependencies, and the idea of a *pristine source plus patches* recipe: the source archive stays untouched, local changes are patches applied in `%prep`, and the build is a script. The same philosophy appears in the Debian format the next topic covers. An RPM file consists of a lead, a signature header (with digests and signatures covering the rest), a header holding metadata (name, version, release, dependencies, file lists with digests, scriptlets, changelog) and a compressed cpio payload. Source RPMs (`.src.rpm`) carry the spec file, the source archives and the patches, so that anyone can rebuild.

Early practice built as root in the system's own file system, which produced two kinds of failure: a faulty `%install` could damage the build host, and a package could accidentally depend on whatever happened to be installed. Both led to **build roots**, an install prefix under the build directory (`%{buildroot}`) that stands for the future root file system, and then to **clean-room builds**: Red Hat's internal build system and then the open-source **mock** (from the Fedora project, 2005) build in a chroot that is created from a minimal package set plus the spec's `BuildRequires`. Distribution build systems wrap that idea in services: **Koji** (Fedora, CentOS and Rocky use it) schedules builds across builders and tags results into repositories, **COPR** gives individual users a hosted build and repository service, and the **Open Build Service** from SUSE builds RPMs and DEBs from one definition. Lessons that shaped current practice include the damage from builds that reach the network (a source tarball is downloaded during `%build` and nobody can verify it), the discovery that unversioned dependencies cause upgrade surprises, and the arrival of automatic dependency generators, which derive `Requires` from the ELF and script content of the package so that authors no longer list library dependencies by hand.

The format itself evolved. Compression moved from gzip to xz and then to zstd as the default in several distributions for speed; file digests moved from MD5 to SHA-256; signature schemes gained support beyond the original OpenPGP v3 signatures, with version 4.14 introducing stronger default digests and 4.19 and later adding groundwork for OpenPGP v6 and post-quantum material (the extent of the support should be confirmed against the release notes, to verify). Rich dependencies (`Requires: (foo if bar)`, introduced in 4.12) allow boolean expressions, and weak dependencies (`Recommends`, `Suggests`, `Supplements`) make optional relationships explicit. RHEL 10's release notes list the notable changes to RPM in its software-management chapter, which is the place to check when behaviour differs between releases [src: rhel-10-docs ef07d26f095b3f5f]. A parallel strand is **rpmautospec**, which generates release numbers and changelog entries from the Git history so that the spec no longer carries hand-maintained counters.

## Current state

**The workspace.** The conventional layout is a tree under `~/rpmbuild/` with `SOURCES`, `SPECS`, `BUILD`, `BUILDROOT`, `RPMS` and `SRPMS`. `rpmdev-setuptree` from the `rpmdevtools` package creates it, and the macro `%_topdir` can relocate it. Red Hat's documentation describes this workspace and how to configure the packaging environment [src: rhel-10-docs 5a3fe705d95ebe44]. A packager builds as an ordinary user and never as root.

**The spec file.** A spec has a *preamble* of tags, then *sections*. The key tags are `Name`, `Version`, `Release`, `Summary`, `License` (an SPDX expression in current Fedora and RHEL practice), `URL`, `Source0` (and further sources), `Patch0`, `BuildRequires`, `Requires`, `Provides`, `Conflicts` and `BuildArch`. Sections are `%description`, `%prep` (unpack and patch, usually `%autosetup`), `%build` (`%configure`, `%make_build`, `%cmake_build` and similar macros that apply the distribution's standard flags), `%install` (installs into `%{buildroot}` with `%make_install`), `%check` (run the test suite), `%files` (the exact list of files, with attributes), and `%changelog`. A minimal example:

```
Name:           hello-site
Version:        1.4.2
Release:        1%{?dist}
Summary:        Site greeting daemon
License:        MIT
Source0:        %{name}-%{version}.tar.gz
BuildRequires:  gcc, make, systemd-rpm-macros
Requires:       systemd

%description
A small daemon used by the site monitoring.

%prep
%autosetup

%build
%make_build

%install
%make_install
install -D -m 0644 hello-site.service %{buildroot}%{_unitdir}/hello-site.service

%post
%systemd_post hello-site.service
%preun
%systemd_preun hello-site.service
%postun
%systemd_postun_with_restart hello-site.service

%files
%license LICENSE
%doc README.md
%{_bindir}/hello-site
%{_unitdir}/hello-site.service
%config(noreplace) %{_sysconfdir}/hello-site.conf

%changelog
* Sun Nov 15 2026 Packager <pkg@example.com> - 1.4.2-1
- Rebuild for the site repository
```

`%{?dist}` appends the distribution tag (for example `.el10`) so the same spec builds distinct releases for different targets. File attributes matter: `%attr(mode,user,group)`, `%defattr`, `%dir` for directories the package owns, `%ghost` for files created at run time that should be tracked but not shipped, and `%config(noreplace)` to protect local edits, which are saved as `.rpmnew` or `.rpmsave` when the package changes the file. `%license` and `%doc` mark legal and documentation files. Paths use macros such as `%{_bindir}`, `%{_libdir}` and `%{_unitdir}` so that the spec works on any architecture and layout.

**Phases and commands.** `rpmbuild -bp` runs `%prep` only, `-bc` through `%build`, `-bi` through `%install`, `-bb` builds the binary RPMs, `-bs` builds only the source RPM and `-ba` builds both. The manual lists these stages and the order in which they run, as well as the `--rebuild` and `--recompile` modes that work from a source RPM [src: man-pages 8e85b0cf271c5956]. `rpmbuild -ba SPECS/hello-site.spec` produces `RPMS/x86_64/hello-site-1.4.2-1.el10.x86_64.rpm` and `SRPMS/hello-site-1.4.2-1.el10.src.rpm`, and Red Hat's chapter on packaging walks through building binary and source RPMs and verifying them [src: rhel-10-docs 30d08043079bbbeb]. Useful checks follow the build: `rpmlint` reports policy problems (missing license, unowned directories, hard-coded paths), `rpm -qpl package.rpm` lists files, `rpm -qp --requires` and `--provides` show the generated dependencies, `rpm -qp --scripts` prints scriptlets, `rpm -K` verifies digests and signatures, and `rpm -qp --changelog` shows the log. `rpmspec -P file.spec` expands macros, `rpmspec -q --buildrequires file.spec` lists build dependencies without building, and `rpmbuild --undefine=_disable_source_fetch` combined with `spectool -g` downloads sources named by URL (so downloads happen before the build, not during it).

**Dependencies.** Automatic generators scan the built files: shared-library `Requires` (as `libssl.so.3()(64bit)`), Python, Perl and pkg-config requirements, and `Provides` for libraries. The packager adds only what the generators cannot see: other packages used by scriptlets, runtime tools called by name, and the minimum versions needed. `BuildRequires` must list everything the build calls, including `gcc` and `make`, because mock's minimal chroot does not include them. Dynamic build requirements (`%generate_buildrequires` with `-r` in newer rpm versions, documented in the manual's section on dynamic build dependencies) let a language tool compute them from project metadata [src: man-pages efe9d46098c04f45].

**Scriptlets and triggers.** The four basic scriptlets (`%pre`, `%post`, `%preun`, `%postun`) run on install, upgrade and removal with an argument that counts instances of the package left after the operation: 1 on first install, 2 on upgrade, 0 on final removal. Scripts must be idempotent, quiet and safe in a chroot, because installers run them inside image builds and containers where systemd and a network are absent. Modern practice uses the macro family (`%systemd_post`, `%sysusers_create_compat`, `%tmpfiles_create`) and file triggers (`%transfiletriggerin`) rather than hand-written shell. `%verifyscript` and `%posttrans` run at other points, and `%triggerin` reacts to other packages being installed.

**Building in mock.** `mock -r rocky-9-x86_64 --rebuild hello-site-1.4.2-1.src.rpm` initialises a chroot from a configuration under `/etc/mock/`, installs the build group and the `BuildRequires`, builds, and writes results to `/var/lib/mock/<config>/result/` along with `build.log`, `root.log` and `state.log`. Key options include `--init` and `--clean`, `--no-clean` and `--cache` to speed iterations, `--shell` for a shell inside the chroot (to debug a failure), `--enable-network` for the rare case where a build needs one, `--bootstrap-chroot` (the default in recent versions, which uses a separate chroot to install the build chroot, avoiding host-version problems) and `--isolation=simple|nspawn` and the newer container-based `--use-bootstrap-image`. Users must belong to the `mock` group. A site normally defines its own config, derived from the vendor's, that adds the internal repository to the chroot's package sources, so internal libraries resolve.

**Hosted and fleet build systems.** Koji, COPR and OBS remove the need for developer machines to build releases at all: a signed-off commit triggers a build in a clean, logged environment, results are tagged and signed by a separate step, and the artefact flow is auditable. Smaller sites often use CI jobs that call mock, plus `createrepo_c` to publish, which the repository topic covers.

**The generalised pattern.** A reproducible package build has *pinned inputs* (verified source archive and patches), a *declared environment* (the build dependency set), an *isolated, disposable execution*, *standardised outputs* (named, versioned, signed packages with metadata) and *retained evidence* (logs, source RPM, build environment manifest). Each failure of repeatability traces to an input that was not pinned or an environment that was not declared.

## Assessment: the good, the bad and the ugly

**The good.** RPM is mature, widely supported across Enterprise Linux, Fedora, SUSE and others, and its database makes inventory and verification routine: `rpm -V` reports files whose digest, mode or owner differ from the package. The spec file is a readable record of how software is built, and the macro system carries distribution policy (compiler flags, hardening options, paths) so that packagers inherit best practice. Mock and its relatives give clean builds on a laptop. The source RPM guarantees that the exact inputs can be recovered. Dependency generation reduces human error.

**The bad.** The spec language is a macro processor layered on shell, with its own quoting rules and surprising behaviour: macros expand before the shell runs, `%` in a changelog or a shell command must be doubled, and conditionals (`%if`) hide logic that is hard to test. Learning the macro vocabulary takes time. The format has a steep curve compared with simply copying a binary. Builds that need the network (language ecosystems that fetch dependencies at build time, such as Go modules, Rust crates, npm) conflict with the clean-room model, and the usual response, vendoring dependencies into a source archive, produces large packages and complicates vulnerability tracking. Multilib and multi-architecture packaging add complexity. Scriptlet failures can leave the package database in an inconsistent state.

**The ugly.** The tension between distribution packaging policy and the pace of upstream software is constant: policy says build from source with system libraries, upstream ships a pre-built binary with its own dependencies. Reproducibility is only partly achieved: build paths, timestamps, user names and parallelism can all leak into the output, and while macros such as `%clamp_mtime_to_source_date_epoch` and the `SOURCE_DATE_EPOCH` convention help, a bit-for-bit identical rebuild needs deliberate effort (and is not always possible with current tools, to verify per package). Secrets sometimes find their way into spec files and source RPMs, which are then published. Release-number discipline fails: a rebuild without a bumped release is not offered to clients, and a rebuild with a lower release is never installed. Finally, there is a gap between "builds in mock" and "works": packages that build cleanly but fail on install because a runtime dependency was not listed, which only an install test in a fresh container reveals.

**Mitigations.** Always build in mock or an equivalent clean root, and make the CI job the only source of release artefacts. Pin source checksums (`sha256sum` in a `sources` file or `%{SOURCE0}` verification) and fetch before the build. Run `rpmlint` and an install-remove-upgrade test in a clean container. Use rpmautospec or a release policy enforced by CI. Keep spec files in version control with the sources of patches. Keep vendored dependency lists in the package metadata (`Provides: bundled(libfoo) = 1.2`) so that scanners can find them. Treat scriptlets as code that runs as root and review them.

## Applications beyond this domain

The pattern of declarative recipe plus isolated, reproducible build carries into many other systems. Container images are built from Dockerfiles or Containerfiles in an isolated builder, and the same arguments about pinned inputs and network access apply. Nix and Guix take the idea to its limit with hermetic, content-addressed builds. Language ecosystems use lock files for the pinning part. Debian's `sbuild` and Arch's `makepkg` with `devtools` implement the same clean-chroot idea for other formats. In embedded Linux, Yocto and Buildroot recipes do for entire firmware images what spec files do for packages. Supply-chain frameworks such as SLSA formalise the evidence a build must produce: provenance records naming source, builder and parameters. In regulated sectors a build record of this kind is a required artefact.

## Examples

**Packaging a small internal daemon.** A team writes the spec above, adds the systemd macros, builds with `rpmbuild -ba` locally for a first check, then builds in mock against `rocky-9-x86_64` with the internal repository added. `rpmlint` flags a missing manual page and an unowned directory; they fix the file list. An install test in a fresh container confirms that `%post` does not fail without systemd running. The CI job builds on each tag and publishes to the test repository.

**Rebuilding a vendor package with a patch.** A security fix is needed before the vendor publishes it. The operator fetches the source RPM, adds the patch with `Patch1:` and `%autosetup -p1`, bumps `Release` with a local suffix (`1%{?dist}.site1`), rebuilds in mock and publishes to a site repository with a higher priority. The changelog states the reason, and a ticket tracks removing the patch when the vendor update arrives.

**A failing example: the network in %build.** A Go project's spec runs `go build` with module downloads enabled. It works on the packager's laptop and in a CI runner with network, and fails in the build system, which blocks outbound traffic. The fix vendors the modules into a second source archive created and checksummed by a script, lists the bundled versions with `Provides: bundled()`, and builds offline.

**A failing example: the missing noreplace.** A package ships `/etc/app.conf` as plain `%config`. An update that changes the file overwrites local edits on some versions of the tool and silently replaces the file elsewhere, and a site loses its tuned settings. Using `%config(noreplace)` keeps the local file and writes the new default as `app.conf.rpmnew`.

## Related problems and ideas

The most direct neighbour is the Debian packaging method covered next. Other approaches include **Flatpak and Snap**, which bundle an application with its dependencies and sandbox it; **AppImage**, a single-file bundle; **language-native packaging** (wheels, crates, npm) which targets developers, not operators; **Nix and Guix** with their functional model; and **container images** as the unit of deployment. On the opposing side, some organisations skip packaging and deploy by configuration management copying files, which loses dependency tracking and verification. Newer ideas include **image-based systems** where the operating system is composed from packages once and shipped whole (covered later in this course), **reproducible builds** with independent rebuilders verifying publicly signed results, and **SBOM generation from the build** so that the package metadata and the vulnerability scanner agree.

## Active research

Work in this area concerns bit-for-bit reproducibility across the large package set of a distribution (the Reproducible Builds project tracks progress by distribution), safer handling of language-ecosystem dependencies in distribution builds (automatic vendoring with provenance), faster package formats and delta updates, and improved signing and digest algorithms. The rpm project itself is evolving its transaction and plug-in architecture and its handling of file digests and signatures for the next major version (the 6.x line, to verify its status). Researchers also study the security of scriptlets, since arbitrary code running as root during installation is a large attack surface, and propose declarative replacements.

## Future direction

Expect more of the build to be declarative: file triggers and sysusers and tmpfiles descriptions replacing shell scriptlets; dynamic build requirements; autochangelog and autorelease macros reducing manual bookkeeping. Expect hosted, attested builds with provenance to become the norm for any package that crosses a trust boundary, and reproducibility checks to join CI as a gate. Expect more sites to deliver software as images and containers, with RPM remaining the way the contents are composed. For the operator the durable practice is unchanged: build in a clean room from pinned inputs, test install and upgrade, and keep every artefact traceable to the source revision that produced it.
