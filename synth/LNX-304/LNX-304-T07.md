# Patch rings: staged updates, soak time, gates and rollback rules

## Define the problem

Patching is a trade between two risks. An update that is applied late leaves a known vulnerability open for longer; an update that is applied too fast, to every machine at once, can turn a regression into an outage of the whole fleet. The first risk is measured in days of exposure and is visible in scanner reports. The second shows up as an incident, sometimes a spectacular one: a faulty kernel, a changed default in a library, an agent that crashes at boot. Operators therefore avoid both extremes with a **ring** model: divide the fleet into groups, update the groups in order with a waiting period (the *soak*) between them, check health at each step, and stop when something is wrong. The idea is old (every careful administrator has patched "the test box first") but at fleet scale it needs to be written down as a policy that machines, people and tools can follow.

This topic concerns that policy. It asks how rings are defined and populated, how long each should soak, what health signals decide whether to proceed, how quickly each severity of vulnerability must reach production, how reboots and live patching fit in, how to handle exceptions, and what the rollback rule is when a ring fails. It builds on the repository and snapshot topics, because a ring is only meaningful if each ring sees a known, frozen set of packages, and it leads to the rollout topic at the end of this course, which scales the same idea to multi-week operations on big fleets.

Typical failure modes: rings that are defined by organisational charts instead of risk (the "test" group is not representative, so a bug appears first in production); a canary ring so small that a problem affecting one workload in fifty never shows; a soak time that is shorter than the problem's latency (a memory leak that takes three days to hurt); no health signal, so that "no complaints" is the gate; a ring order that updates a database primary before its replicas; a kernel update installed everywhere but never booted, so the exposure remains; an emergency patch that bypasses rings with no record; and a rollback rule that is untested, so that nobody knows whether going back is possible.

## History and approaches

Staged updates were first formalised in client operating systems. Microsoft's update model for Windows described *rings* explicitly (preview, targeted, broad, and similar names) with deferral periods set per ring, and its enterprise tooling lets administrators deploy to ring 0 (IT staff) first, then successively larger groups. The Microsoft guidance on secure administrative hosts, which is aimed at the machines from which domain controllers are managed, insists on a patch process that keeps those hosts current while testing first, which shows that the logic extends from desktops to critical infrastructure [src: ms-learn-adds b1457ca4fced8308]. In cloud services, the same idea is known as **canary releasing** and **progressive delivery**: release to a small slice of traffic, compare error rates and latency with the control, and widen if healthy. Site reliability engineering literature describes canaries, error budgets and automatic rollback as ways to bound the blast radius of change. In Kubernetes, rolling updates of Deployments with `maxUnavailable` and `maxSurge` limits, and the node-pool upgrade procedures of managed services (surge nodes, drain, cordon), are ring-like by construction.

For Linux servers, the early practice was manual: update the staging systems, wait, update production in the maintenance window. Automation arrived in two forms. Unattended mechanisms (`unattended-upgrades` on Debian and Ubuntu, `dnf-automatic` on Enterprise Linux) apply updates locally on a schedule, often only for security updates, and are appropriate for low-risk or ephemeral machines. Central orchestration (Katello and Satellite, Uyuni, Landscape, Ansible, Rundeck, or custom pipelines) decides *which hosts* may update *which version* *when*. With frozen repository snapshots, the ring becomes the statement of which snapshot a host follows: ring 0 follows this week's, ring 1 follows last week's and so on, so no further action by clients is needed. Katello's lifecycle environments and aptly's published snapshots map to this directly.

Vulnerability response added a second dimension: **time to remediate by severity**. Standards and guidance such as the CVSS scoring system, the Known Exploited Vulnerabilities (KEV) catalogue from the US cybersecurity agency, and compliance regimes (PCI DSS requires critical patches within a short stated period; US federal binding operational directives set fixed deadlines for KEV entries) turn the patch policy into service-level targets. Rocky Linux's documentation on CVE hygiene illustrates the basic discipline of knowing which CVEs affect which packages and tracking fixes [src: rocky-docs a72d02444de485f7]. A modern policy therefore has two clocks: the regular cadence (monthly or weekly rings) and the expedite path for actively exploited issues.

**Live patching** (kpatch on Enterprise Linux, Canonical Livepatch, kGraft/SUSE Live Patching) changes the reboot dimension: certain kernel fixes can be applied to a running kernel, which removes the need for an immediate reboot but not the need for an eventual one. Red Hat's description of the kernel and its update mechanics, and its guidance on installing security updates, show that the packages arrive by the normal tooling but take effect only for processes and kernels restarted after installation [src: rhel-10-docs 3f21157a1d66681a] and [src: rhel-10-docs 634ebdca4bc1a7d0].

## Current state

**Defining rings.** A usable scheme has four or five rings. A typical one is:

| Ring | Contents | Share | Purpose | Soak |
|---|---|---|---|---|
| 0 | lab and staging hosts, platform team's own systems | 1–2 % | catch breakage in packaging and boot | 1–2 days |
| 1 | canary: a representative slice of production, one or two nodes per service | 5 % | real workload signals | 2–4 days |
| 2 | early production: non-critical services, one failure domain | 20–30 % | scale effects | 3–7 days |
| 3 | main production, in failure-domain order | the rest | the bulk | by domain |
| 4 | the exceptions: systems with change freezes, certified stacks, appliances | varies | manual, scheduled with the owner | by agreement |

The percentages and soak times are starting points, not rules (to verify against your own risk and tolerance). Two constraints matter more than the numbers. First, each ring must be *representative* of the rings after it: if the canary has no host running the database engine, a database-related regression cannot be seen there. Second, redundancy must be respected: never have both members of a pair, or a quorum majority, in the same ring step (see the high-availability course); patch replicas before primaries, and one availability zone at a time.

**Populating rings.** Rings are attributes of hosts, stored in the inventory or in the management platform (host collections in Katello, groups in Ansible inventory, tags in a CMDB). Assign by service and failure domain, not by name. Automate the assignment so that a new host gets a ring on creation, and report hosts without a ring daily. Treat "no ring" as an alert.

**Gates.** Moving from one ring to the next needs a decision that is as automatic as possible. Useful health signals include: the update job's success rate; reboot success and time to return to service; the service-level indicators of the workloads (error rate, latency, saturation) compared with the pre-update baseline or with the unpatched control group; the count of failed systemd units; agent heartbeats; log error rates for the packages updated; and support tickets. Define the thresholds before the rollout, for instance an error rate that stays above baseline by half a percentage point for a quarter of an hour stopping the rollout. A gate that requires a human to look at a dashboard will be skipped under pressure, so automate the stop and let the human decide to continue.

**Soak and the problem of slow failures.** Time is a control in itself. A soak of a day or two catches boot failures, service crashes and configuration incompatibilities. Slow failures such as memory leaks, file-descriptor exhaustion, log growth or certificate-related issues need longer. Match the soak to the failure modes you have actually seen, and include at least one full business cycle (a month-end batch, a weekly report) before the biggest ring when that cycle exercises unusual code paths.

**Severity-driven timelines.** A policy table links severity to the maximum time from vendor release to production, for example: actively exploited and internet-facing: 48–72 hours, expedite path allowed to compress rings to hours; critical (CVSS 9 or higher, or vendor-rated critical): 7–14 days; important: 30 days; moderate and low: the regular cycle (typically 30–90 days). The numbers should come from your compliance obligations and risk appetite and are examples (to verify). Whatever the numbers, the policy should state how the expedite path works, who authorises it and what testing is cut.

**Mechanics on RPM systems.** `dnf updateinfo list security` shows applicable security advisories; `dnf upgrade --security` applies only those; `dnf upgrade --advisory=RHSA-2026:1234` targets one; `dnf needs-restarting -r` reports whether a reboot is needed and `dnf needs-restarting -s` lists services to restart; `dnf history` records transactions and `dnf history undo N` or `dnf downgrade` reverse them where possible; `dnf versionlock` pins packages that should not move. The RHEL notes on changes to RPM show that tools and defaults evolve between major releases, which a patching playbook must follow [src: rhel-10-docs ef07d26f095b3f5f].

**Mechanics on Debian systems.** `apt list --upgradable`, `apt-get -s upgrade` (simulate), `unattended-upgrade --dry-run`, `apt-mark hold` to pin, `needrestart` to list services using old libraries, `/var/run/reboot-required` as the reboot indicator, and `apt install pkg=version` to downgrade. Debian's `apt` cannot reverse a transaction as `dnf history undo` can, so the rollback plan leans on pinned versions and snapshots.

**Reboots and restarts.** Many security fixes (kernel, glibc, OpenSSL used by long-running daemons, systemd) take effect only after a reboot or a restart of the services that map the old library. A patch policy that ignores this measures installation, not remediation. Track *effective* patch state: the running kernel version versus the installed one, `needs-restarting` output and process-level library checks. Coordinate reboots with the service's redundancy: drain, update, reboot, health-check, return to service, then the next node.

**Orchestration.** For each ring, a job takes a host list, then for each host or batch: check preconditions (backup or storage snapshot taken, host healthy, not in a freeze), put it in maintenance (silence alerts, drain from the load balancer), apply updates from the ring's snapshot, restart or reboot as needed, run post-checks, and return it to service. The job fails closed: on a failed post-check it stops the batch and the ring. Ansible with `serial:` and `max_fail_percentage:` expresses this well; the same logic exists in Satellite remote execution and in Rundeck.

**Rollback rule.** Decide *beforehand* what happens when a ring fails. Options: stop and hold the ring while others stay behind (default); revert the ring's repository pointer to the previous snapshot so that no more hosts take the bad version; roll back affected hosts (storage snapshot revert, `dnf history undo`, image rollback); or fix forward with a new package. The rule must say who decides, how long they have, and what happens to rings already updated. Test the rollback on ring 0 regularly: an untested rollback is a hope.

**Exceptions and freezes.** Hosts that cannot take regular updates (a certified application stack, a vendor appliance, a system in a change freeze) are put in an exception ring with an owner, a reason and an expiry date, and the compensating controls are recorded (network isolation, virtual patching, extra monitoring). Exceptions that never expire become permanent risk.

**Measure.** Track time-to-patch by severity, percentage of hosts at the current snapshot, hosts with pending reboots older than N days, failed patch jobs, rollbacks, incidents caused by patching and the age of exceptions. Review monthly. The numbers show whether the rings are too slow (long exposure) or too fast (incidents).

## Assessment: the good, the bad and the ugly

**The good.** Rings bound the blast radius of a bad update while keeping exposure short; they turn an anxious, ad hoc activity into a predictable one. They fit naturally with snapshots and lifecycle environments, produce evidence for auditors and give engineers a clear answer about when their systems will be patched. Automated gates and orchestration make the process cheap enough to run weekly, which reduces the size and risk of each change.

**The bad.** Rings take work to define well and to keep representative as the fleet changes. Soak delays lengthen the time to full protection, which is the cost of safety; a policy that is too cautious can leave hosts exposed longer than an attacker needs. Health signals are imperfect, and some regressions are not visible in the metrics collected. Stateful and tightly coupled systems (databases, clusters) need ordering that a simple ring list does not express. Live patching gives a false sense of completion if the eventual reboot is not tracked. Teams with many exception systems find that the rings cover a smaller share of the fleet than the policy suggests.

**The ugly.** The worst patterns are the shadow paths: someone installs the fix by hand on production "because it is urgent" and the inventory no longer reflects reality; the canary ring is defined as "whoever volunteers"; or a gate is overridden every week and nobody questions it. Another is the freeze that becomes permanent: a host skipped for a quarter becomes a host that cannot be patched without a project. And a global "update everything now" button in the orchestration tool, available to many people, makes all the care in the ring design optional.

**Assumptions.** Ring sizes, soak times and severity deadlines in this text are illustrative and drawn from common practice and the compliance material the author knows; they are not standards, and each site should derive its own (to verify).

## Applications beyond this domain

The ring pattern is general: it is the way to roll out any change with a risk of regression to a large population. It is used for firmware and BIOS updates, for network device upgrades (one router in a pair at a time), for database engine upgrades (replicas first), for configuration changes through configuration management, for feature flags (percentage rollouts), for mobile app releases (staged rollouts in the app stores) and for Kubernetes control-plane and node upgrades. The Kubernetes distinction between control plane and nodes, and the version-skew policy limiting how far apart components may be, are the container-world form of ring ordering [src: cilium-docs a65fca7be5ca189f]. The same signals (error rate, latency, saturation) judge each.

## Examples

**Example 1: a weekly ring schedule.** Monday: the new snapshot appears in ring 0. Wednesday: after ring 0's checks pass, ring 1 (5 % canary) moves. The following Monday: ring 2. The Wednesday after: ring 3 in two failure-domain halves, a day apart. Ring 4 is scheduled with owners. A critical advisory on Thursday triggers the expedite path: ring 0 and 1 together the same day, ring 2 and 3 within 72 hours.

**Example 2: an Ansible rollout.** A playbook with `serial: "10%"`, `max_fail_percentage: 0`, pre-tasks that drain the host and check the freeze flag, a task that runs `dnf upgrade --security` against the ring's repository, a reboot task conditioned on `dnf needs-restarting -r`, and post-tasks that check the service's health endpoint and return the node to the pool. Any failure aborts the play.

**Example 3: a health gate.** A script compares the 15-minute error rate of ring 1 services with their previous seven-day baseline and exits non-zero if it is higher by more than a set margin, and the pipeline marks ring 2 as blocked until a human clears it.

**Example 4: a rollback rule.** A sustained breach of a service-level objective in ring 1 within 48 hours of patching makes the pipeline revert the ring 2 and 3 pointers to the previous snapshot and open an incident; the service owner then has 4 hours to choose between reverting ring 1 hosts (by storage snapshot) and fixing forward. Reverts on ring 0 are tested monthly.

**Example 5: effective patch state.** A query lists hosts whose running kernel (`uname -r`) differs from the newest installed kernel package, and hosts where `dnf needs-restarting -r` returns 1. These two lists, sorted by age, are the real backlog.

**Worked failure: the representative canary.** The canary ring contained twenty stateless web nodes. A library update changed the behaviour of a connection pool used only by the batch servers, which were in ring 3. The batch jobs failed on Friday night across the fleet. The fix to the *design* was a canary rule: at least one host from every service tier (including batch) in ring 1, and a service catalogue that is checked automatically for coverage.

## Related problems and ideas

Patch rings use **snapshots and lifecycle environments** (previous topics) as their mechanism, **monitoring and SLOs** as their gates, and **orchestration** as their engine. They connect to **vulnerability management** (what must be patched and how fast), **high availability** (what may be taken down together), **change management** (approval and freeze policy), **backup and recovery** (the rollback), **image-based delivery** (patching by replacing the image, with rings applied to image versions) and **chaos and game-day exercises** (testing the rollback). Immutable infrastructure replaces in-place patching with rebuild-and-replace, but the ring logic over *which instances get the new image first* is unchanged.

## Active research

Open questions include how to choose representative canaries automatically from workload telemetry, how to detect slow regressions earlier (statistical comparison of canary and control, automated canary analysis as in open-source tools such as Kayenta and Argo Rollouts), how to combine vulnerability exploitability data (KEV, EPSS scores) with ring policy so that urgency is data-driven, and how to extend live patching safely beyond the kernel to user-space libraries. Research on change-induced incidents shows that many outages follow a recent change, which supports the case for slower, more observable rollouts, though the evidence on optimal soak times is thin (to verify).

## Future direction

Expect patching to move from per-host package updates towards image or container replacement, which turns "ring" into a property of a deployment pipeline, and expect exploit-aware policies to replace fixed severity tables. Live patching and confidential-computing platforms will put more weight on attestation of what is actually running. For the operator, the durable practice is to write down the ring definitions, the gates, the severity clocks and the rollback rule, automate their enforcement, and rehearse the failure paths while the stakes are low.
