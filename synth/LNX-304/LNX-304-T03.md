# Signing packages and repositories, and rotating keys without breaking clients

## Define the problem

A package manager that installs whatever it downloads gives root-level code execution to anyone who can alter the bytes in transit, on a mirror, in a cache or in a build farm. Signatures are the answer: a publisher holds a private key, signs either each package or the repository metadata that lists the packages and their checksums, and every client holds the matching public key and refuses anything that does not verify. The problem for an operator of a fleet is not the cryptography, which the tools hide, but the lifecycle around it. Where do the signing keys live, who may use them, how do clients learn which keys to trust, what happens when a key expires or leaks, and how can a key be replaced on thousands of machines without a day on which every update fails?

Typical failure modes are easy to list. A repository key reaches its expiry date and every `apt update` or `dnf makecache` in the company starts to fail at once. A signing key is stored on a build server next to the code it signs, so a compromise of the server is also a compromise of the trust root. A team turns off signature checking (`gpgcheck=0`, `--allow-unauthenticated`, `[trusted=yes]`) to get around an import problem and never turns it back on. A new key is published on the project website but not signed or announced in a way that clients can authenticate, so the rotation itself becomes a way to attack. A distribution raises its minimum acceptable algorithm and an internal repository signed with an old hash is suddenly rejected. A key is revoked, but the revocation certificate never reaches the clients.

The scope of this topic is the signing model of the two big package families, the places where a client keeps its trusted keys, how to produce and verify signatures at package level and at repository level, how to generate and protect keys, and how to plan a rotation that has an overlap period and a way back. Mirrors, snapshots and repository construction are covered in the following topics, and the wider supply-chain material (SBOMs, signed provenance, container signatures) is treated in the security course. The aim here is that you can sign what you publish, make clients verify it, and replace a key on a schedule you chose rather than one the calendar chose for you.

## History and approaches

Cryptographic signatures on packages are as old as the major package formats. The RPM format has carried a signature header since its early releases, and its tooling grew around the OpenPGP standard and the GnuPG implementation: a publisher signs each package file, the signature covers the header and the payload digests, and a client with the public key checks it at install time. Red Hat and Fedora used one key per release series, shipped in a file in `/etc/pki/rpm-gpg/`, and a release-specific key meant that every major upgrade involved a conscious step of trusting a new key. The Debian family took a different route. For many years individual `.deb` files were not signed at all; instead the archive's `Release` file, which lists the checksums of the index files, which in turn list the checksums of the packages, was signed with the archive key. Signing the top of a hash tree is enough to authenticate everything below it, and it needs only one signature per publication rather than one per package. The `apt-secure` mechanism was introduced in the early 2000s and became the norm in the middle of that decade, and `apt-key`, a global keyring of trusted keys, was the user-visible tool for years.

Both models later converged on repository-level signing as the primary line of defence. In the RPM world, `createrepo` writes `repodata/repomd.xml`, which lists the metadata files and their checksums, and a detached signature `repomd.xml.asc` allows clients to set `repo_gpgcheck=1` so that metadata is authenticated, while `gpgcheck=1` continues to require signatures on the packages. The manual pages for the DNF and YUM configuration files document both options, along with the `gpgkey` setting that names where a client finds the public key for a repository [src: man-pages b1ffe55542f8152e]. [src: man-pages 254f148a958460d3] documents the same switches for the older tool. With both enabled, a hostile mirror cannot serve altered metadata, and it cannot serve a package that was signed by anyone but the publisher.

The Debian world moved away from the global keyring after its weaknesses became clear. Any key in the global keyring could vouch for any repository, so adding a key for one third-party repository meant trusting it for the distribution's own archive as well. The modern practice is to store each repository's key in its own file, usually under `/etc/apt/keyrings/` for administrator-installed keys, and to name the key in the repository's source entry with the `Signed-By` field, in either the one-line format or the newer deb822 `.sources` format. A key then authenticates only the repository that names it. Recent versions of `apt` print warnings for repositories that still rely on the global keyring and are expected to remove support for it (to verify the version in which `apt-key` is removed from your target release).

The cryptography beneath has also shifted. SHA-1 signatures, once ubiquitous, were deprecated by distributions in stages: the Debian family tightened `apt`'s acceptance of SHA-1 in releases from about 2021, and Enterprise Linux 9 moved its default policy against SHA-1 for signatures as well, with a system-wide crypto policy that can be changed with `update-crypto-policies`. RSA keys of 2048 or 4096 bits remained common, and EdDSA became the default in current GnuPG. The RHEL 10 documentation describes a new generation: RPM there can sign with Sequoia PGP as well as GnuPG, version 10.1 supports OpenPGP version 6 keys and a new RPM version 6 signature format, and a package may carry several signatures so that RPM versions understanding only the older format still find one they can check [src: rhel-10-docs dc768d248d0568a3]. The same chapter shows how to sign with post-quantum hybrid algorithms and states that earlier RHEL releases ignore the new signature type, which is exactly the compatibility concern a multi-version fleet has to plan around [src: rhel-10-docs 0c869993deb7a9ee].

Sigstore and related projects added a keyless approach in the 2020s, in which a short-lived certificate tied to an identity (a CI job, for instance) signs an artefact and the signature is recorded in a public transparency log. This is now common for container images and language packages, and some distributions experiment with it for packages, but the mainstream OS package ecosystems still rely on long-lived keys held by the publisher, so this topic concentrates on those.

## Current state

**Package signatures on the RPM side.** A signing key is an ordinary OpenPGP key created with `gpg --quick-generate-key` or `gpg --full-generate-key`, or with Sequoia's `sq key generate`. The public half is exported with `gpg --export --armor` into a file such as `RPM-GPG-KEY-example`. The RHEL documentation walks through installing `rpm-sign` and `pinentry`, creating the key, naming it for RPM by setting the `%_gpg_name` macro in `~/.rpmmacros`, and then adding the signature with `rpm --addsign` or the `rpmsign` command [src: rhel-10-docs 0c869993deb7a9ee]. Verification is `rpm --checksig` (short form `rpm -K`), and with `-v` it prints each digest and signature along with the key identifier, as in the sample output of the same chapter, where the key ID is the last eight hexadecimal digits of the fingerprint [src: rhel-10-docs dc768d248d0568a3]. A client must first import the public key, `rpm --import file`, which places it in the RPM database; until then the signature is reported as `NOKEY`. DNF imports keys named in a repository's `gpgkey=` line the first time they are needed, after prompting, unless the administrator has pre-installed them, which is the better practice for managed fleets since the prompt is a place where attacks and mistakes hide.

**Repository signatures on the RPM side.** A repository publisher runs `createrepo_c`, then signs `repodata/repomd.xml` with `gpg --detach-sign --armor`, writing `repomd.xml.asc` beside it. The repository file on clients carries `gpgcheck=1`, `repo_gpgcheck=1` and `gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-example`. The `gpgkey` value may be an HTTPS URL, but then the first import trusts whatever the TLS connection delivers, so the key should arrive by a channel you control, such as the configuration management system or a small package that installs only the key file. A frequent trap is that `repo_gpgcheck` defaults to off in most configurations, and a repository served without a signed `repomd.xml` fails as soon as it is enabled.

**Repository signatures on the Debian side.** The publisher produces `Release`, then either `InRelease` (a clear-signed version) or `Release.gpg` (a detached signature), using `gpg --clearsign` or `gpg --detach-sign`. Tools such as `reprepro` and `aptly` sign automatically when configured with a key ID. The client's source file names the key, for example a deb822 stanza with `Types: deb`, `URIs`, `Suites`, `Components` and `Signed-By: /etc/apt/keyrings/example.gpg`. The key file may be a binary keyring (dearmored with `gpg --dearmor`) or, in newer versions of `apt`, an ASCII-armoured `.asc` file. The `apt-secure(8)` manual page describes the verification model and the `Valid-Until` field of `Release`, which lets a publisher set a freshness limit so that a stale mirror cannot replay an old, vulnerable index indefinitely. `apt` also refuses to move a repository back to an older `Date` unless told to, which stops downgrade attacks to some degree.

**Per-package signatures on the Debian side.** Debian's own archive does not rely on per-package signatures: the `.changes` and `.dsc` files carry upload signatures from the maintainer, checked by the archive software, and installed packages are not re-checked by `dpkg`. Third-party sites can use `debsigs` and `debsig-verify` with policy files under `/etc/debsig/`, but this is rarely deployed and the tools are simple. In practice, a site that wants end-to-end package assurance on Debian should put its packages in a signed repository and make clients accept only that repository.

**Protecting the key.** Four guidelines hold across both families. First, the signing key should not be the identity of a person; create a role key such as "release signing" with its own passphrase or hardware token. Second, use a primary key kept offline for certification and a signing subkey with an expiry date (one to two years is typical), so that routine signing never exposes the primary key and renewal means extending or replacing a subkey. Third, if signing happens in CI, either use a hardware security module or a cloud key service reached through a signing proxy, or keep the secret in a store such as Vault with tight access controls (the secrets topic in the security course covers these systems), and log every signing operation. Fourth, generate and store a revocation certificate at the time of key creation (`gpg --gen-revoke`) and keep it offline: if the key is lost or stolen, the revocation certificate is what lets you tell clients to stop trusting it.

**Algorithms and policy.** Prefer EdDSA or RSA 4096 with SHA-256 or stronger. On Enterprise Linux, `update-crypto-policies --show` tells you the system policy, and a package signed with a disallowed algorithm will fail verification even though the key is imported. On the Debian family the `apt.conf` option `APT::Hashes::SHA1::Weak` and the corresponding `Sha1` policy options control acceptance. If your repository still uses 1024-bit DSA or SHA-1, plan the replacement now.

**Rotation in practice.** A key rotation is an update to a trust anchor, so it must itself be delivered through a channel that clients already trust. There are three common patterns. The first, often used by distributions, is to ship the next release's key in the current release's keys package, so that by the time the new key signs anything, clients already have it. The second is overlap: publish the new key while the old one still signs, sign the repository with both keys for a transition period (a repository can carry two signatures, and `Signed-By` or an apt keyring file can list several keys), then drop the old key from signing but leave it trusted for older packages, and finally remove it. The third, for emergency rotation after a compromise, is revocation: publish the revocation certificate through a trusted channel, issue a new key, and have clients replace the key file by configuration management. The Kubernetes project provides a recent public example of per-minor-version repositories with their own keys when it moved its package hosting to new locations in 2023, and its documentation tells users to fetch the key matching the repository they select [web: kubernetes.io].

**Failure and recovery.** `apt` reports `EXPKEYSIG` when the signing key has expired, `NO_PUBKEY` when it is not in the configured keyring and `BADSIG` when the signature fails to verify. `rpm` reports `NOKEY` or `BAD` in the `rpm -K` line. In an expiry incident, the publisher can extend the key's expiry date, re-sign the metadata and re-export the key; clients need the updated public key (which contains the new expiry), so the update must be delivered like a rotation. This is why monitoring the expiry of every signing key, with alerts a quarter ahead, is the simplest and most valuable control in this topic.

## Assessment: the good, the bad and the ugly

**The good.** Repository-level signing is cheap and effective: one signature per publication, verified by every client, defeats the most common attacks (malicious mirrors, compromised caches, on-path tampering). Package-level signatures in the RPM family give provenance that survives copying the file elsewhere, which matters for offline installs and for air-gapped sites. Separate keyrings per repository, now the default practice on the Debian family, reduce the blast radius of any one key. Hardware-backed keys and subkey hierarchies are well understood and supported by GnuPG and Sequoia.

**The bad.** Trust is bootstrapped manually. The first import of a key depends on a human or a script trusting a download, and there is no global directory to check. The OpenPGP ecosystem has poor tooling for revocation distribution: a revocation certificate is only useful if clients see it. Key expiry is a correct feature that nonetheless produces large outages, because clients cannot update a key they no longer trust. Compatibility across releases is fragile: a package signed with the new RPM version 6 format, or an algorithm that a policy forbids, is silently ignored or rejected by older clients, so a fleet with mixed releases needs dual signatures or separate repositories. Per-package signatures are missing on Debian, which makes offline verification of a single `.deb` awkward.

**The ugly.** The ugly cases are operational. Turning verification off to make an install work is common enough that scanners look for it. Storing the passphrase-less private key in the CI system's environment makes the signature meaningless. The public key delivered over the same HTTP connection as the packages proves nothing. Keys that live on one engineer's laptop produce an outage when that engineer leaves. And mirrors that rewrite metadata, for example to fix a path, break signatures in ways that tempt administrators to disable checks instead of fixing the mirror.

**Assumptions in this assessment.** The statements about defaults (`repo_gpgcheck` off, SHA-1 deprecation dates, the `apt-key` removal timeline) reflect the documents cited and the author's reading of vendor release notes; they change between releases and should be confirmed against the release you run (to verify).

## Applications beyond this domain

The same pattern, sign the index and let hashes carry the trust down the tree, appears in container registries (manifests signed with Notation or cosign), in Git (signed tags and commits, with allowed-signers files for SSH signatures), in firmware and boot (UEFI Secure Boot, covered in the security course, with its Platform Key, Key Exchange Key and signature database hierarchy, described in RHEL's image-mode documentation as a chain of delegations [src: rhel-10-docs c019f95883fcddc9]), in TUF-based update systems used by language ecosystems, and in DNSSEC, where a zone signing key is rotated under a key signing key with documented pre-publish and double-signature procedures. If you can run a clean key rollover for a repository, you can reason about each of these. The vocabulary of overlap, publication before use and a revocation path is the same everywhere.

## Examples

**Example 1: sign an RPM and verify it.** On a build host create a key, export it, point RPM at it and sign:

```
gpg --quick-generate-key "Example Release <release@example.org>" ed25519 sign 2y
gpg --export --armor "Example Release" > RPM-GPG-KEY-example
echo '%_gpg_name Example Release' >> ~/.rpmmacros
rpmsign --addsign hello-site-1.0-1.noarch.rpm
sudo rpm --import RPM-GPG-KEY-example
rpm -Kv hello-site-1.0-1.noarch.rpm
```

The final command lists the digests and the signature with the key identifier; altering one byte of the file makes it report a failure, which is a good way to see the check working.

**Example 2: a signed RPM repository.** Run `createrepo_c repo/`, then `gpg --detach-sign --armor repo/repodata/repomd.xml`, and publish the directory. On clients, write `gpgcheck=1`, `repo_gpgcheck=1` and `gpgkey=` into the repository file. Test by editing `repomd.xml` on the server: `dnf makecache` must now refuse it.

**Example 3: a signed APT repository with a keyring file.** Build the repository with `reprepro` or `aptly`, sign `Release` into `InRelease`, and place the dearmored key in `/etc/apt/keyrings/example.gpg`. Give the sources file `Signed-By: /etc/apt/keyrings/example.gpg`. A second repository with a different key cannot now vouch for this one.

**Example 4: a planned rotation.** In month 0 create the new signing subkey and publish a keys package containing both the old and the new public keys. In month 1, after the package has reached the whole fleet (verify with an inventory query), start signing with both keys. In month 4 stop signing with the old key. In month 6 remove the old key from the keys package and revoke it with its certificate. At every step you can roll back by one step, because the previous step's key set is still trusted.

**Example 5: an emergency.** The signing host is believed compromised. The response is to isolate it, publish the revocation certificate through the configuration management channel, generate a new key on clean hardware, distribute it the same way, re-sign the repository metadata (and the packages, for the RPM family), and rebuild anything built on the host after the suspected time. The exercise shows why the revocation certificate and a pre-agreed distribution channel must exist before the incident.

**Worked failure: the silent expiry.** A repository key created with a one-year expiry reaches its date on a Saturday. Clients show `EXPKEYSIG`, patch jobs fail, and the on-call engineer is tempted to set `trusted=yes`. The right response is to extend the expiry on the publisher, re-export, re-sign, and push the updated public key through configuration management while leaving verification on. The lasting fix is an alert ninety days before every expiry and a rotation rehearsal each year.

## Related problems and ideas

Package signing sits next to **repository mirroring and snapshots**, because a snapshot must preserve the original signatures or be re-signed by the operator's own key, a choice that changes the trust model (the next topics discuss it). It also relates to **reproducible builds**, which let independent parties check that a signed binary matches its source, and to **transparency logs**, which make a mis-issued signature detectable. **Secure Boot and module signing** use similar hierarchies at a lower layer. **Certificate authorities and TLS** protect the transport but not the content at rest, so they complement but do not replace package signatures. **Secrets management** solves where the private key lives. **Software bills of materials** describe the content of a package, whereas a signature says who vouches for it; a mature pipeline attaches both.

## Active research

Open work includes making keyless, identity-based signing practical for OS packages without giving up offline verification, post-quantum signature algorithms and hybrid schemes (the RHEL 10 documentation already describes hybrid signing, labelled as technology under development in places [src: rhel-10-docs dc768d248d0568a3]), and standard ways to distribute revocation and key-rollover information to clients. The OpenPGP working group's revised standard introduced version 6 keys and signatures, and the migration of tools such as GnuPG, Sequoia and RPM to it is ongoing. Academic and industry studies of package-manager security examine downgrade, replay and mirror attacks and compare the metadata protections of different tools; the TUF specification is the best-known framework for this and has been adopted by several ecosystems.

## Future direction

Expect repository-level signing with multiple signatures (classical plus post-quantum) to become the norm, expect package managers to warn loudly about unsigned or unauthenticated sources, and expect transparency logs and provenance attestations to become part of what a client can check before installing. For an operator the stable advice is independent of fashion: keep the signing key offline or in hardware, name keys per repository, schedule rotations before expiry, deliver trust anchors through a channel you control, and rehearse a revocation. The systems that fail are those that never exercised the rotation path until it was needed.
