# Image-based operating systems: bootc, image mode and rpm-ostree

## Define the problem

Package-based patching, which the previous topics described, has a hidden weakness: the state of a machine is the *history* of what was done to it. Two servers installed from the same kickstart a year apart, patched in different windows, with a few manual fixes in between, are not the same machine, even if the package lists look similar. Configuration drift, partial updates that fail half-way, packages added during an incident and never removed, and files changed under `/usr` are all consequences of treating a running system as a mutable thing. **Image-based** operating systems answer this by changing the unit of delivery. The operating system is built once, as an image, in a build pipeline; every machine boots that image; an update is a new image; a rollback is booting the previous one. The machine's state is, by construction, one image version combined with local configuration and data.

This topic covers the two technologies that matter most for Enterprise Linux and Fedora-family systems. **rpm-ostree** is a hybrid of a package system and a content-addressed file-tree store (OSTree) that gives atomic, transactional updates with rollback, and is the basis of Fedora Silverblue, Fedora CoreOS and earlier RHEL for Edge. **bootc** (bootable containers), used in Red Hat's **image mode for RHEL**, Fedora bootc and CentOS Stream bootc, takes the idea further: the operating system image *is an OCI container image*, built with the same tools as application containers (`podman build`, a `Containerfile`), pushed to a registry, and installed or updated on the host with the `bootc` command, which uses OSTree-like machinery underneath. The scope here is the model (what is immutable and what is not), the workflow (build, test, push, install, upgrade, roll back), the way configuration and state are handled, the security and compliance implications, and where the approach fits or does not.

Typical failure modes are specific to the model. A team tries to keep patching hosts with `dnf` as before and finds that `/usr` is read-only; a change made with a temporary overlay disappears at the next boot; configuration put in `/etc` conflicts with a new image's default after an update; a `/var` path that the image's content populated at build time is not refreshed on update because `/var` is persistent; a registry outage prevents hosts from fetching an update or a rollback target; a kernel argument changed on one host is lost at the next deployment; secrets baked into the image leak to everyone who can pull it; and a build pipeline without signing or provenance delivers a poisoned image to the entire fleet at once, since the unit of delivery is the whole system.

## History and approaches

The concept has many ancestors. Appliance-style systems with a read-only root and an A/B pair of partitions (ChromeOS, Android, network equipment, many embedded systems) swap the whole system on update and fall back on failure. **OSTree**, begun by Colin Walters around 2011 for GNOME's testing needs and developed under the libostree name, took a different path: it stores file trees in a content-addressed object store, like Git for operating-system trees, and deploys a commit by creating a directory of hard links to the shared objects, then pointing the boot loader at it. Two or more deployments can coexist at almost no extra disk cost, and switching is a boot-loader entry change. **rpm-ostree** joined RPM and OSTree: it composes an OSTree commit on a server from a set of RPMs (the *compose*), and on the client it can *layer* additional RPMs on top of the base image by creating a new local deployment. Fedora Atomic Host (2014), Fedora Silverblue (the desktop variant), Fedora CoreOS (merging CoreOS Container Linux and Atomic Host in 2018–2019), and RHEL for Edge used this stack. Other image-based Linux systems took other paths: Flatcar and the original CoreOS Container Linux used A/B partitions with a signed update payload; Ubuntu Core uses snaps as the unit of everything; SUSE's MicroOS and Aeon use Btrfs snapshots and transactional-update; NixOS and Guix use declarative, generation-based systems.

Meanwhile containers had normalised a different build and distribution toolchain: layered images described by a `Containerfile` or `Dockerfile`, stored in OCI registries, signed and scanned by tools that the whole industry understood. The insight behind **bootc** (around 2023, developed in the containers project) was that an operating system could be built and distributed with that toolchain. A bootc image is an ordinary OCI image that also contains a kernel, an init system, and everything needed to boot; `bootc` on the host pulls it with the container libraries, deploys it with the OSTree machinery (and, in newer releases, composefs for integrity-checked root filesystems), and manages updates, switching and rollbacks. The Red Hat documentation introduces image mode for RHEL as a way to treat the operating system as a bootc image that is built, rolled out and maintained with the same tools as applications [src: rhel-10-docs 3b3a3aef48026b4a]. It lists base images, the `bootc-image-builder` tool that converts an image into disk images (ISO, qcow2, AMI, raw) for installation, and the rules for what the image may and may not contain.

The different approaches compare as follows. *rpm-ostree with a compose* is a server-side build of OSTree commits from RPM manifests, mature, with the client side able to layer packages. *bootc* is a container-native build and update model, with the `Containerfile` as the definition and registry as the transport; rpm-ostree remains the engine underneath on Fedora and RHEL for some operations (and for layering on systems that still allow it). *A/B-partition systems* swap whole filesystems and need no content-addressed store, but cannot share space between versions. *Declarative systems* (Nix) offer finer reproducibility with a different packaging world. *Classic package management with configuration management* keeps the mutable model and relies on discipline and drift detection.

## Current state

**The filesystem contract.** The key idea of a bootc or OSTree system is a partition of the file tree by mutability. `/usr` is read-only and comes entirely from the image; it holds the operating system's programs, libraries and default configuration. `/etc` is writable, holds local configuration, and is handled with a **three-way merge** on update: the new image's defaults, the previous image's defaults and the local `/etc` are compared, so that local changes are preserved and new defaults appear for files not locally changed. `/var` is writable and persistent across updates; the image may provide initial content through `tmpfiles.d` or systemd units but does not overwrite existing data on updates. `/home` and `/root` live under `/var` (`/var/home`). `/boot` and the ostree repository are managed by the tools. Everything that needs to differ from the image (certificates, host keys, machine identity, site configuration) has to be placed in `/etc` or `/var` at provisioning time, or injected by configuration management, cloud-init, Ignition or Butane (Fedora CoreOS) or kickstart.

**Building an image.** A bootc image starts from a bootc base image (for example a RHEL, CentOS Stream or Fedora bootc image) and adds packages and configuration by ordinary container build steps:

```
FROM registry.example.org/base/rhel10-bootc:10.0
RUN dnf -y install chrony tmux site-agent && dnf clean all
COPY site/ /usr/lib/site/
COPY 10-site.toml /usr/lib/bootc/kargs.d/10-site.toml
RUN systemctl enable chronyd site-agent.service
RUN bootc container lint
```

The point of the final step is that `bootc container lint` checks the image against rules that make it bootable and updateable (for example, no content in places that the update would not manage). Changes to configuration are made as files in the image, usually under `/usr` (with defaults the host may override in `/etc`) rather than by editing `/etc` at build time, although the build may also place files in `/etc` as image defaults. The documentation of the kernel-argument mechanism shows a typical example: arguments are declared in drop-in TOML files under a `kargs.d` directory in the image, and bootc applies them on deployment, while the command line can also be edited on a running system with the `bootc` and `rpm-ostree` tools [src: rhel-10-docs e08522f0c099f423].

**Building disk images and installing.** An image in a registry is not yet a bootable machine. `bootc-image-builder` produces a disk image, ISO or cloud image from it, or `bootc install to-disk` (run from the container itself, privileged, against a target device) or `bootc install to-filesystem` installs directly. Provisioning-time customisation (users, SSH keys, hostnames) is passed with a config file for the builder or injected by cloud-init or Ignition. Disconnected environments use an ISO that embeds the container image, which the Red Hat documentation describes in its section on offline installation media that carry a container image [src: rhel-10-docs 25cb1d195a3b934e].

**Day-two operations.** The commands on a host are few. `bootc status` shows the booted, staged and rollback images with digests. `bootc upgrade` pulls the newest image for the current reference and stages it; the new deployment becomes active at the next reboot (`--apply` reboots). `bootc switch <image>` changes the reference, for example from a `stable` tag to a `candidate` tag, which is how rings move (see the patch ring topic) or how a host is rebased onto another image. `bootc rollback` marks the previous deployment as the one to boot next. A timer such as `bootc-fetch-apply-updates.timer` (name and defaults to be verified for the version) can check the registry and apply updates on a schedule. Health checks matter: **greenboot** and similar tools run checks after boot and trigger automatic rollback when they fail, which is the equivalent of the post-checks in a patch ring, and the Red Hat documentation for RHEL for Edge describes automatic provisioning and health-check features in the same family of tools [src: rhel-10-docs b60547b65fd8eedf].

**rpm-ostree operations.** On Fedora CoreOS, Silverblue and rpm-ostree-based RHEL systems: `rpm-ostree status` shows deployments; `rpm-ostree upgrade` stages the next; `rpm-ostree install pkg` *layers* a package into a new deployment (a practice to minimise, because layered packages must be rebuilt for each update and slow it down); `rpm-ostree override replace` swaps a base package; `rpm-ostree rollback` swaps the default boot entry; `rpm-ostree kargs --append=...` edits kernel arguments; `rpm-ostree usroverlay` mounts a temporary writable overlay on `/usr` for debugging that disappears at reboot. `ostree admin` provides lower-level control.

**Updates are transactional.** The new deployment is prepared completely and activated by a reboot, so a power failure during an update leaves the old system intact; there is no half-updated `/usr`. This is the strongest property of the model. The cost is that an update takes effect only after a reboot (kexec and soft-reboot optimisations in newer systemd and ostree releases can shorten it, to verify), which aligns with the patch-ring discipline of making reboot a planned step.

**Registries and signing.** Because the fleet's source of truth is a registry, treat it like the repository of the previous topics: pin by digest or by a controlled tag (`stable` moves through rings; `2026-11-08` is immutable), mirror it near the hosts, sign images (cosign or Sigstore, GPG signatures with `containers-policy.json` and `policy.json` verification on the host), generate and attach an SBOM and provenance attestations (build attestations are supported by container build tooling, as the Docker documentation describes [src: docker-docs 5d0f42f7ee32e343]), and configure the host's container policy to refuse unsigned images. The key lifecycle topics from earlier in this course apply to image signing keys unchanged.

**Compliance and security.** Because the image is built once and deployed many times, hardening is applied *at build time*: install a benchmark profile into the image by running OpenSCAP remediation or configuration management during the build, scan the built image, and fail the pipeline on findings. FIPS mode, for instance, must be enabled consistently with the kernel arguments and crypto policy in the image, and the compliance-as-code rule for enabling it describes the required steps [src: compliance-as-code c75c3d5ea98826b5]. The host keeps few moving parts, and file integrity checking becomes simpler: the content of `/usr` is known from the image digest, and composefs or fs-verity can enforce it. Secure Boot and sealed images extend the chain of trust from firmware to the image (the previous signing topic mentions the key hierarchy involved).

**Fit and limits.** The model suits fleets that are homogeneous or can be grouped into a few roles: edge devices, Kubernetes nodes, appliances, stateless services, container hosts and developer workstations. It fits less well with long-lived pet servers that carry many hand-installed third-party agents or vendor software that writes into `/usr` or `/opt` (although `/opt` and `/usr/local` handling is a documented issue to plan for), with software whose installers assume a mutable root, and with teams that have no build pipeline. Hybrid operation is common: the base is an image, and a small amount of local state is managed with configuration management. Plan for rebuild speed, because a CVE fix means rebuilding and re-releasing the image, and a slow pipeline translates directly to slow patching.

## Assessment: the good, the bad and the ugly

**The good.** Updates are atomic and reversible; all hosts of a role run the same bits, verified by digest; drift is reduced because `/usr` cannot be changed; builds use familiar container tooling and can be tested in CI by running the image as a container or booting it in a VM; rollback is a boot entry change; testing and promotion use the same pipeline concepts as applications; compliance is applied once and verified once. The model also shortens reprovisioning: replace the host rather than repair it.

**The bad.** Everything flows through a build pipeline, which must exist, be reliable and be secured. Updates need a reboot. Debugging on the host is harder when `/usr` is read-only and tools are missing (use toolbox or debug containers). Local package installs are discouraged, which frustrates users used to `dnf install`. State in `/etc` and `/var` still drifts and still needs configuration management. Image size and registry load grow with the number of hosts, mitigated by layered pulls and local mirrors. The ecosystem is young: bootc is evolving, with features such as composefs sealing marked as technology preview in vendor documentation, and details of commands and base images change between releases (to verify).

**The ugly.** Blast radius: a bad image released to the `stable` tag reaches every host that follows it, so rings and health-gated automatic rollback are not optional extras. Secrets or private data baked into the image become retrievable by anyone with registry access. Kernel arguments and firmware settings that are per-host fall outside the image and must be managed separately. Third-party closed-source agents that expect to modify the system at install time may not work, or work only if repackaged. And a team that moves to images but continues to log in and make hand changes with overlays and layered packages gets the complexity of both worlds.

**Assumptions.** The command names and options reflect the cited documentation and the author's knowledge of the projects at the time of writing; units, timers and the maturity of features differ across releases and between Fedora, CentOS Stream and RHEL (to verify).

## Applications beyond this domain

The same pattern, build an immutable artefact, sign it, distribute it through a registry, roll it out in rings and roll back by switching a pointer, is the model of container-based application delivery, of GitOps, of serverless function versions and of firmware over-the-air updates in cars and phones. Cloud providers' machine images (AMIs, golden images) are a coarser form of it. Kubernetes node operating systems (Talos, Flatcar, Fedora CoreOS, RHEL CoreOS in OpenShift) are image-based by design, with the cluster managing the rollout of new node images. The fixed address of `/usr`, the merge rule for `/etc` and the persistence of `/var` give a precise vocabulary for deciding what belongs in an image and what belongs to a machine.

## Examples

**Example 1: a first image.** Write the `Containerfile` above, build with `podman build -t registry.example.org/site/el10:2026-11-08 .`, run `podman run --rm -it <image> rpm -q chrony` as a smoke test, push, then turn it into a qcow2 with `bootc-image-builder` and boot it in a VM. Run `bootc status` on the VM and confirm the booted image digest.

**Example 2: upgrade and rollback.** Build and push `...:2026-11-15`. On the VM run `bootc upgrade`, then `bootc status` to see it staged, reboot, and check the new digest is booted. Run `bootc rollback`, reboot, and see the earlier image return. Local changes in `/etc` and data in `/var` survive both moves.

**Example 3: moving a ring.** Rings follow tags: ring 1 hosts track `:candidate`, ring 3 tracks `:stable`. Promoting is retagging the same digest from `candidate` to `stable` in the registry, after the health gate passes. A host can be moved with `bootc switch registry.example.org/site/el10:stable`.

**Example 4: kernel arguments.** Put `kargs = ["audit=1", "mitigations=auto"]` in `/usr/lib/bootc/kargs.d/10-site.toml` inside the image. After the next upgrade and reboot, `cat /proc/cmdline` shows them. A per-host exception is applied with the tool's kargs command, recorded in configuration management.

**Example 5: a debugging overlay.** On an rpm-ostree host, `rpm-ostree usroverlay` allows `dnf`-style experiments on `/usr` for the current boot only. The change is then written as a line in the `Containerfile` and the image rebuilt, so the fix reaches every host.

**Worked failure: the lost `/etc` edit.** A site file in `/etc` was changed in the build by a `RUN sed -i` on a file that the host also edits locally. After an update, the three-way merge keeps the host's local copy and ignores the image's change, so the fleet diverges. The fix is to ship such settings as drop-in files under `/usr` or in a `.d` directory that the application reads, rather than editing shared files.

## Related problems and ideas

This topic builds on **snapshots and promotion** (an image digest is a snapshot) and on **patch rings** (rings select image tags). It leads to the next topic, **Image Builder**, which produces images for package-based and image-mode systems, and to **Kubernetes node management**, **edge computing** and **immutable infrastructure** in general. It touches **secure boot and measured boot** (sealed images), **SBOM and provenance** (every image can carry them), **configuration management** (still needed for `/etc` and `/var`), **container tooling** (Buildah, Podman, Skopeo) and **storage** (composefs, fs-verity, Btrfs and LVM snapshots as alternatives). It also relates to **A/B updates** in embedded Linux (RAUC, SWUpdate, Mender) which solve the same problem for devices.

## Active research

The area is moving quickly. Active work includes composefs and fs-verity for verified root filesystems, sealed and signed unified kernel images, reducing the update-to-active delay with soft reboots, better handling of `/etc` merges and of per-host state, standard formats for attaching SBOMs and vulnerability exceptions to images, bootc support for more bases and architectures, and tooling to build derived images quickly and reproducibly. Parts of Red Hat's documentation label sealing as a technology preview, which shows how new some of these features are [src: rhel-10-docs c019f95883fcddc9].

## Future direction

Expect image-based delivery to become the default for container hosts and edge devices, and to spread to general servers as pipelines become standard. Expect the registry to become the central trust and distribution point for the operating system itself, with signatures, attestations and policy checks enforced at boot or update. Package managers will remain, mostly at build time, as the way to compose images, and the line between application and operating-system delivery will keep blurring. For the operator, the question to ask of any workload is which parts are image, which are configuration and which are data, and who owns the pipeline that changes each.
