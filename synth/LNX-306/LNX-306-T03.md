# cloud-init: first-boot configuration of instances, from datasource to final stage

## Define the problem

An image is the same for every machine built from it, and a machine is not. At first boot an instance must learn who it is (a hostname, an identity), how to reach the network (addresses, routes, resolvers), who may log in (SSH keys, users) and what role it plays (packages to install, files to write, a registration step with the configuration management system). If the image carried that knowledge, there would need to be one image per machine, which defeats the purpose of an image. If a human supplied it by logging in, the process would not scale and would be unrepeatable. The established solution is **cloud-init**, a program that runs very early in the boot of a Linux instance, looks for configuration data offered by the platform (the *datasource*), and applies it by running a set of configuration *modules*. It is the de facto standard first-boot agent for clouds (AWS, Azure, Google Cloud, OpenStack, DigitalOcean and many more), for virtualisation platforms (KVM and libvirt with a seed ISO, VMware, KubeVirt, LXD, Proxmox) and increasingly for bare metal. The same configuration format also drives Ubuntu's autoinstall (see the topic on unattended installation).

For the person who builds and runs fleets, cloud-init is both indispensable and treacherous. It is indispensable because almost every cloud image depends on it. It is treacherous because it runs once per instance, silently, before anyone is logged in; a mistake in a YAML file produces an instance that boots but cannot be reached, or that is reachable but half-configured; and the program has many modules and datasource-specific behaviours. The questions this topic answers: how the boot is organised into stages and what runs in each; how user-data, meta-data, vendor-data and network configuration differ; what the common configuration modules do; how cloud-init decides whether to run again; how to test and debug it, including on a laptop with no cloud; how to keep secrets and sensitive operations safe; and where cloud-init's job ends and the job of configuration management begins.

Typical failure modes: invalid YAML or a missing `#cloud-config` header, so the file is treated as a script or ignored; a `runcmd` entry with shell quoting that works in a terminal but not in the YAML list; ordering assumptions (a package installed after the `runcmd` that needs it); a reused instance-id so that cloud-init decides it has already run and skips everything; a network-config that disagrees with the interface names of the image and leaves the machine offline; secrets placed in user-data that any process on the instance can read from the metadata service; an image that was not cleaned before capture and so inherits the previous instance's host keys and machine identity; and a time-consuming datasource search at boot on a platform that has no metadata service, which delays boot by minutes.

## History and approaches

cloud-init began in 2008–2009 at Canonical, written by Scott Moser, to configure Ubuntu images on Amazon EC2: to take the instance's SSH public key from the metadata service and install it for the default user, and to run a user script. EC2's metadata service (a link-local HTTP endpoint at `169.254.169.254`) and user-data field set the pattern. Other clouds copied the endpoint, and cloud-init grew datasources for each. It was ported to other distributions (the Red Hat family adopted it for their cloud images), rewritten and extended in Python, and moved to a community project with an upstream in a public repository; the Rocky Linux documentation on cloud-init notes that the code is Python and describes the source landscape for contributors [src: rocky-docs 93d902c23577d7dd]. Today it handles dozens of platforms and distributions, with a modular architecture: datasources find the data, *handlers* process each part by type, and *modules* run in defined stages.

The alternatives show different philosophies. **Ignition** (CoreOS, Fedora CoreOS, RHEL CoreOS) runs once in the initramfs and *declares* the final state of disks, files and users; it is more deterministic and cannot be re-run, which suits immutable systems. **Combustion** (SUSE) and **Afterburn** fill similar roles. **Windows** has `cloudbase-init`. **Kickstart and preseed** configure at install time rather than first boot. **Packer and Image Builder** bake configuration into the image, leaving less to do at boot. **Configuration management agents** (Ansible pull, Puppet, Salt) can take over from the first minute, and cloud-init is often used just to install and register them. The trade-off is between flexibility and determinism: cloud-init is flexible and can be re-run in part, while Ignition is strict and one-shot.

The data model has three kinds of input. **Meta-data** comes from the platform and describes the instance (instance-id, hostname, availability zone, public keys). **User-data** is supplied by the person who launches the instance and is the main configuration channel. **Vendor-data** is supplied by the platform operator, so that a provider can add defaults. A fourth, **network-config**, describes interfaces and is read earlier than the rest. User-data can be in several formats: a `#cloud-config` YAML document; a script beginning with `#!`; a `#include` file listing URLs; a `#part-handler`; or a MIME multipart archive combining several. The KubeVirt documentation shows the same model in a Kubernetes context: a VirtualMachine definition carries cloud-init user-data and network-config in a volume of type `cloudInitNoCloud` or `cloudInitConfigDrive`, with examples for user data and for network configuration [src: kubevirt-user-guide 1faf55596b8b8b5f] and [src: kubevirt-user-guide 73b9745fe36b2016].

## Current state

**The boot stages.** cloud-init integrates with systemd and runs in four stages, each a unit:

1. *Generator*: a systemd generator decides whether cloud-init should run at all (it can be disabled with a `/etc/cloud/cloud-init.disabled` file or the `cloud-init=disabled` kernel argument).
2. *Local* (`cloud-init-local.service`): before the network is up, it locates a datasource that does not need the network (a seed ISO, a config drive, a file) and applies the network configuration.
3. *Network* (`cloud-init.service`): after the network is up, it finds network datasources (the metadata service) and runs the `init` modules (such as `growpart`, `users-groups`, `write-files`, `ssh`).
4. *Config* (`cloud-config.service`) runs modules such as `set-passwords`, `ntp`, `runcmd` preparation, `apt` and `yum` repository configuration and `package-update-upgrade-install`.
5. *Final* (`cloud-final.service`) runs `runcmd` scripts, `scripts-user`, and phone-home or reporting modules; it runs last so that other services can be ordered after it.

The Arch Wiki's description of the systemd integration, listing the units and their ordering, is a succinct reference for these services [src: archwiki e03dcaa48d657b89]. Because the stages are systemd units, you can order your own services after `cloud-final.service` to wait for first-boot configuration, which is how orchestration code waits for an instance to be ready, and `cloud-init status --wait` blocks until it is finished [src: rocky-docs 9fa0668b009153ac].

**Datasources.** cloud-init tries a configured list (`datasource_list` in `/etc/cloud/cloud.cfg.d`), checking cheap, local checks first. The common ones: *NoCloud* (a volume labelled `cidata` or `CIDATA` containing `user-data` and `meta-data`, or a kernel command line `ds=nocloud;s=http://host/path/`), *ConfigDrive* (OpenStack, volume labelled `config-2`), *Ec2*, *Azure*, *GCE*, *OpenStack*, *VMware*, *Oracle*, *DigitalOcean*, *LXD* and *None* as a fallback. Restricting the list to the platforms you use speeds boot and prevents the surprise of a network datasource search on a platform without one. The Rocky guide's "first contact" lesson uses NoCloud to show the structure: a directory with a `user-data` file and a `meta-data` file, packaged into an ISO with the label `cidata`, and attached to a VM; the `instance-id` in the meta-data is what cloud-init uses to decide whether it has run before [src: rocky-docs fa0b30287187ae29]. That makes NoCloud the method for laboratories, for bare metal and for every platform without a metadata service.

**A cloud-config example.**

```
#cloud-config
hostname: web01
fqdn: web01.example.org
manage_etc_hosts: true
users:
  - name: ops
    groups: [wheel]
    shell: /bin/bash
    sudo: "ALL=(ALL) NOPASSWD:ALL"
    ssh_authorized_keys:
      - ssh-ed25519 AAAA... ops@example.org
disable_root: true
ssh_pwauth: false
package_update: true
packages: [chrony, tmux]
write_files:
  - path: /etc/site/role
    permissions: "0644"
    content: |
      role=web
runcmd:
  - [systemctl, enable, --now, chronyd]
  - [sh, -c, "echo ready > /run/site-ready"]
```

Some points deserve comment. The first line `#cloud-config` is mandatory; without it the file is not parsed as configuration. Modules are named by top-level keys (`users`, `packages`, `write_files`, `runcmd`, `bootcmd`, `ntp`, `growpart`, `resize_rootfs`, `mounts`, `disk_setup`, `fs_setup`, `apt`, `yum_repos`, `ca_certs`, `power_state`, `phone_home`). `write_files` runs before `packages` in some stages and after in others, so a file that must follow a package installation should be written by `runcmd` or use the `defer: true` option (check your version). `runcmd` entries are run in order as a shell script, in the final stage, once per instance; `bootcmd` runs early on every boot. Using the list form `[cmd, arg]` avoids shell quoting; string form passes through `sh`.

**Network configuration.** The `network-config` file uses version 1 or version 2 syntax; version 2 resembles Netplan. It is read in the local stage and rendered into the distribution's own format (NetworkManager, systemd-networkd, ifupdown, netplan or sysconfig). The KubeVirt documentation includes an example of a version 2 network configuration for a VM [src: kubevirt-user-guide 73b9745fe36b2016]. Match interfaces by MAC address (`match: {macaddress: ...}` with `set-name`) so that the names are predictable, not by `eth0`, which varies. If network-config is absent, the datasource default is used, usually DHCP on the first interface.

**Idempotence and frequency.** cloud-init records state under `/var/lib/cloud/`. Module *frequency* is `once-per-instance` for most modules, `always` for some (such as `bootcmd` and `scripts-per-boot`) and `once` for a few. The `instance-id` from meta-data identifies the instance; when it changes (for example after cloning a VM with a new id), per-instance modules run again. `cloud-init clean --logs` removes state and logs so that the next boot behaves as a first boot, which is essential before capturing an image and is the way to retest changes on a running VM (`sudo cloud-init clean --logs` followed by a reboot) [src: rocky-docs 918c8063b363575a]. Creating the sentinel `/etc/cloud/cloud-init.disabled` stops cloud-init from running at all, while the `bootcmd` module is the place for the rare script that has to repeat at each boot.

**Debugging toolkit.** `cloud-init status --long` shows the stage and any errors; `cloud-init schema --system` or `--config-file user-data` validates configuration against the JSON schema and catches indentation or type errors before a boot; `cloud-init query` reads merged instance data (`cloud-init query ds.meta_data`, `v1.platform`); `cloud-id` names the detected datasource; `cloud-init analyze show` and `blame` give a timeline of module durations (useful to find a stage that stalls boot); logs are `/var/log/cloud-init.log` (debug) and `/var/log/cloud-init-output.log` (stdout and stderr of scripts); and `/run/cloud-init/` holds results and the instance data JSON. The Rocky troubleshooting guide organises these into a toolkit, beginning with `cloud-init status` and the wait option [src: rocky-docs 9fa0668b009153ac]. A reliable method is to reproduce the problem with a NoCloud seed in a local VM, where each iteration takes a minute.

**Use with images.** Packer, Image Builder and bootc builds put cloud-init in the image, set `datasource_list`, and clean it before capture. The Image Builder documentation lists how services are enabled in custom images, which is one way to make sure the four cloud-init units are enabled [src: rhel-10-docs 9a7f6a03fd6e9380]. Combining the two roles gives a rule of thumb: put what is the same for every instance of a role in the image (packages, baseline configuration), and put what differs per instance (hostname, keys, role label, registration token) in user-data. Some platform-specific modules are documented in the vendor docs; for instance Red Hat's Azure guide shows configuring swap with cloud-init on a RHEL Azure instance [src: rhel-10-docs 9283ef437e85859d].

**SSH and users.** cloud-init's `users` and `ssh_authorized_keys` are how most instances become reachable. The default user is defined in the image's `cloud.cfg` (for instance `cloud-user`, `ec2-user`, `ubuntu`, `rocky`). Platform key injection from meta-data (`public-keys`) lands in the default user's `authorized_keys`. The KubeVirt documentation shows static key injection through cloud-init on KubeVirt [src: kubevirt-user-guide 9b0d35e70831ec46]. Disable password SSH (`ssh_pwauth: false`), lock root (`disable_root: true`) and prefer keys. Generate fresh host keys on first boot (the `ssh` module does this unless disabled).

**Security.** User-data is **not secret**. On clouds it is retrievable by any process that can reach the metadata endpoint; on cloud platforms with the hop-limit feature (AWS IMDSv2) it is protected from containers but not from the instance's own processes. It is often logged by the platform, stored in the API, and visible to anyone who can read the instance's configuration. Do not place passwords or private keys in it. Pass a short-lived token or use the platform's identity (instance roles, workload identity, a vault agent login) and fetch the secret over an authenticated connection from `runcmd`. Validate what you download. Keep `/var/lib/cloud/instance/user-data.txt` readable only by root (the default), and delete sensitive scripts. Restrict metadata access from untrusted containers and web applications (SSRF is the classic route to metadata credentials).

**Bare metal and labs.** cloud-init works on machines with no cloud: attach a `cidata` ISO or USB stick, or add `ds=nocloud-net;s=http://provision.example.org/${serial}/` to the kernel command line from the PXE script. This lets the same user-data work for virtual machines and physical servers, and it connects the installer topics earlier in this course (Ubuntu autoinstall literally embeds cloud-init data) to first boot.

## Assessment: the good, the bad and the ugly

**The good.** One mechanism configures instances on nearly every platform, with a documented format and a schema, and with a wide set of modules for the ordinary needs of first boot. It separates image and instance configuration cleanly, supports re-runs for testing, and has good debugging tools. The NoCloud datasource makes it usable in labs and on bare metal. It is open source with a large user base and a regular release cycle.

**The bad.** It is a big program with many modules, and behaviour differs across versions and distributions; the same user-data may act differently on an older image. YAML is unforgiving. The "once per instance" model hides problems: the module ran and failed once, and now it will not run again unless state is cleaned. Ordering between modules is subtle. The time cost of the datasource search and Python start-up can be noticeable on slow systems. Debugging requires access to the instance, which the failed configuration may have prevented.

**The ugly.** Secrets in user-data are the commonest security mistake and one of the most consequential. Another is the snapshot of a configured instance used as an image without cleaning, producing a fleet with identical host keys and machine ids. A third is configuration that depends on timing: a `runcmd` that calls a service not yet available, passing in testing and failing under load. And configuration that grows in user-data into a hundred-line script is a sign that configuration management or a better image is needed.

**Assumptions.** Module names, defaults and the exact CLI commands reflect recent upstream releases and the cited guides; older images differ, and distribution packaging varies. Verify against the cloud-init version on your image (`cloud-init --version`) (to verify).

## Applications beyond this domain

The pattern of a first-boot agent reading a declarative document from a platform channel appears in Ignition, in Windows (`cloudbase-init`, unattend), in mobile device enrolment, in network equipment (ZTP), in Raspberry Pi imaging tools (which write cloud-init-style `user-data` to the boot partition) and in Kubernetes node bootstrap (kubeadm join data delivered by user-data). KubeVirt's startup-script documentation presents cloud-init as the standard for VMs inside Kubernetes, with the same file formats [src: kubevirt-user-guide 6366b4daf8eceae0]. The same design question, what is baked, what is injected, what is fetched with identity, applies in all of them.

## Examples

**Example 1: a seed ISO for a local VM.** Create `user-data` and `meta-data`, run `genisoimage -output seed.iso -volid cidata -joliet -rock user-data meta-data` (or `cloud-localds seed.iso user-data meta-data`), attach it as a second drive to a cloud image under libvirt, boot, and log in with the key from the user-data.

**Example 2: validate before boot.** `cloud-init schema --config-file user-data --annotate` prints the document with errors marked inline, which catches a mistyped key before any boot.

**Example 3: retest on a running VM.** After editing the seed, `sudo cloud-init clean --logs --seed`, change the `instance-id` in meta-data, power off and reattach the new seed, reboot and read `/var/log/cloud-init-output.log`.

**Example 4: waiting for readiness in automation.** An Ansible task or a deployment script runs `cloud-init status --wait` over SSH (or waits for a marker file written by `runcmd` as the last step) before running further configuration, so that the next step does not race with first boot.

**Example 5: registration without secrets in user-data.** User-data carries a one-time registration token with a five-minute lifetime and the URL of the configuration management server; `runcmd` installs the agent and registers using the token, which the server then invalidates.

**Example 6: PXE plus NoCloud.** The iPXE script adds `ds=nocloud-net;s=http://boot.example.org/ci/${serial}/` to the installer or live image, and the web service serves `user-data` and `meta-data` per machine, connecting provisioning to first boot.

**Worked failure: the instance that ignored its configuration.** A team cloned a configured VM to make ten new ones without changing `instance-id`. All ten came up with the same hostname and none ran `runcmd`, because cloud-init saw the instance-id it had recorded and skipped per-instance modules. The fix was a unique instance-id per clone (the hypervisor tooling generated it from the VM's UUID) and `cloud-init clean` in the template before cloning.

## Related problems and ideas

cloud-init sits between **image building** (Packer, Image Builder, covered next) and **configuration management** (Ansible, Puppet), and after **unattended installation** and **network boot**. It connects to **identity and secrets** (how an instance proves who it is), **networking** (netplan, NetworkManager), **storage** (growpart, resize, mounts), **cloud metadata services** (IMDS and its security), **virtualisation** (KVM, VMware, KubeVirt seed volumes) and **observability** (reporting boot time and failures). The infrastructure-as-code topic in this course supplies user-data from templates.

## Active research

Work in the project includes faster start-up (rewriting hot paths, reducing the datasource search time), better schema coverage and validation, improved network configuration across renderers, more secure handling of sensitive data, and support for more platforms. Wider efforts concern the trustworthiness of metadata (attestation of the platform to the guest, confidential VMs obtaining secrets without exposing them to the host) and standards for instance identity documents.

## Future direction

Expect declarative, one-shot approaches (Ignition-style) to gain share where images are immutable, expect cloud-init to continue as the common denominator for general-purpose Linux instances, and expect first-boot data to carry identity and attestation rather than secrets. For the operator, the lasting practices are to validate configuration with the schema tool, to keep user-data small and free of secrets, to clean images before capture, to limit the datasource list, to use unique instance-ids, and to test with a local seed so that each iteration is quick.
