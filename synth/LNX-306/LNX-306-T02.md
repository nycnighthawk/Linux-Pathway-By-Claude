# Network boot: PXE, iPXE and UEFI HTTP boot

## Define the problem

A server that must be installed or rebuilt from nothing has no operating system to run a tool from. Someone has to put a bootable thing in front of the firmware: a USB stick, a virtual media image on the baseboard controller, or a program fetched over the network. For more than a handful of machines, the network is the only option that scales. The firmware itself asks the network for a boot program, receives it, runs it, and that program fetches a kernel and an initial ramdisk and starts an installer, an image deployer or a diagnostic environment. The skills of this topic are the design and operation of that chain: DHCP that answers differently for different kinds of machine, a file server that the firmware can use, a bootloader that can be trusted and configured per machine, and an installer that learns from the boot arguments where to find its answer file and its packages.

The chain has many links and each can fail without a helpful message. The firmware may not send the extension that tells the server which architecture it is. The DHCP server may hand out the wrong file name to a UEFI machine. TFTP, the traditional file protocol of network boot, is slow and fragile over a routed network. The bootloader may not be signed for Secure Boot. The kernel may start but not find the network card driver and hang while looking for the installation source. The installer may boot and then install over the old disk because the answer file was not found. A machine in the wrong VLAN may boot someone else's installer. This is why network boot has a reputation for being finicky, and why the practice of staging, logging and testing the chain in virtual machines first is worth more than any single trick.

The scope here is: how the firmware discovers what to boot (DHCP options and the PXE protocol, UEFI HTTP boot), what to serve for BIOS and UEFI machines, how iPXE extends the firmware and why it is often chained, how to deliver per-host decisions (a menu, a script keyed on the MAC address or serial number), how to boot installers and image deployers from the network, how Secure Boot affects the chain, and how to secure and troubleshoot it. The installer side (Kickstart and similar files) was the topic before this one; first-boot configuration follows in the next.

## History and approaches

Booting from the network was first done with the Bootstrap Protocol (BOOTP) and RARP in the 1980s for diskless Unix workstations, using TFTP, the trivial file transfer protocol, to fetch a boot image. DHCP, which extended BOOTP, added options, and in 1999 Intel's **Preboot Execution Environment (PXE)** specification standardised how a network card's firmware asks a DHCP server for a boot program name (options 66 for the server name and 67 for the file name, together with the `next-server` field) and then loads it over TFTP. PXE is still the first stage on most servers. Its shortcomings are by now well known: TFTP uses UDP with small blocks and a lock-step acknowledgement, so large files (a kernel and an initrd of several hundred megabytes) take long and suffer from latency; PXE ROMs differ across vendors; and it assumes a network in which the DHCP server can reach the machine's broadcast domain.

The client states what kind of machine it is in DHCP option 93, the client system architecture: type 0 for classic BIOS, 7 and 9 for x86-64 UEFI, 11 for ARM64 UEFI, and others. A server must therefore be able to answer a different first-stage file to each kind of machine on the same subnet: a BIOS loader for legacy firmware and an EFI binary for UEFI x86-64. Option 60 carries a vendor class string beginning `PXEClient`, which a server can use to recognise network boot requests. A **proxyDHCP** arrangement lets a second server supply only the boot information (as dnsmasq can do) while the site's main DHCP server continues to hand out addresses, which is useful where the existing DHCP service cannot be changed.

**iPXE**, started by Michael Brown in 2010 as a fork of gPXE, which in turn came from Etherboot, is a network bootloader with HTTP, HTTPS, FTP, iSCSI and AoE support, a scripting language and DNS, and it can be used to replace or follow the vendor's ROM. The usual pattern is *chainloading*: the machine's PXE ROM loads iPXE over TFTP (a small file), iPXE does DHCP again, and, recognising itself by DHCP option 175, is told by the server to load a script over HTTP instead of repeating the first stage. This avoids the loop of loading iPXE forever, and it moves the heavy transfers to HTTP, which is faster and easier to load-balance, proxy and secure. iPXE scripts can make decisions based on the MAC address, the UUID or serial number, or a query to a web service that returns a script per machine, and they can verify images against a trusted certificate (`imgtrust`, `imgverify`).

The UEFI specification added native support in version 2.5 with **HTTP boot** (and HTTPS boot later), in which the firmware itself does DHCP, recognises a boot URL in the DHCP reply (when the vendor class is `HTTPClient`), downloads an EFI binary or even a disk image (an ISO) over HTTP, and runs it, without TFTP and without iPXE. Vendor support varies in quality, and HTTPS needs the server's certificate authority to be enrolled in the firmware, but where it works it is the simplest design. The Red Hat documentation for network installation describes the same two families: preparing a PXE installation source (a TFTP server and a DHCP configuration for BIOS and UEFI clients) and the HTTP boot method for UEFI [src: rhel-10-docs ffc7d6339b0a689a] and [src: rhel-10-docs 07531088d4c0bc56], and the automated installation guide shows how to start a Kickstart installation using PXE or HTTP boot [src: rhel-10-docs 5bfa053150bd55b7]. Debian's installation documentation lists netboot among the installation methods and describes the files needed [src: debian-handbook 51f6efabc6dc417b].

The last element of the history is **Secure Boot**. A UEFI machine with Secure Boot enabled only runs binaries signed by a key in its database, so network boot must start with a signed first-stage loader: the distribution's `shim`, signed by Microsoft's UEFI CA, which then verifies a signed GRUB or systemd-boot and a signed kernel. iPXE can be built with a signature acceptable to Secure Boot only if the project's binary is signed or the machine's database holds your key (the signing and secure boot topics in the security courses cover the key hierarchy). Many sites therefore use shim and GRUB netboot images from the distribution for UEFI Secure Boot machines and iPXE for the rest.

New designs push the model further. **Tinkerbell**, **Matchbox**, **MAAS** and **Foreman** provide services that combine DHCP, TFTP/HTTP, an inventory and a workflow engine, generating per-host boot instructions. **Image-based** deployment (bootc, discussed in the packaging course) can boot a live ISO over HTTP and write an image to disk; the RHEL image-mode documentation covers the case of a bootc ISO delivered through the PXE path [src: rhel-10-docs 66cc00a8085e4808].

## Current state

**The DHCP side.** A typical small design uses dnsmasq as DHCP and TFTP server. A configuration has the shape:

```
dhcp-range=192.0.2.100,192.0.2.199,12h
enable-tftp
tftp-root=/srv/tftp
dhcp-match=set:bios,option:client-arch,0
dhcp-match=set:efi64,option:client-arch,7
dhcp-match=set:efi64,option:client-arch,9
dhcp-match=set:ipxe,175
dhcp-boot=tag:bios,tag:!ipxe,undionly.kpxe
dhcp-boot=tag:efi64,tag:!ipxe,ipxe.efi
dhcp-boot=tag:ipxe,http://boot.example.org/boot.ipxe
```

Three ideas are in these lines. The client architecture decides which first-stage file is offered. The `ipxe` tag (option 175 present) marks a machine that is already running iPXE and should be given a script, not the loader again, which breaks the chainloading loop. And the script is an HTTP URL, which moves everything after the first small transfer to HTTP. ISC Kea and ISC dhcpd express the same with client classes (`if option arch = 00:07 { filename "ipxe.efi"; }`). Whatever the server, set a short lease for installer addresses, reserve addresses for known machines if your design uses MAC-based decisions, and restrict the DHCP service to the provisioning VLAN: a second DHCP server on a production network is a classic outage.

**The iPXE script.** A script served by HTTP looks like this:

```
#!ipxe
dhcp
set base http://boot.example.org/el9
kernel ${base}/vmlinuz inst.repo=http://repo.example.org/snapshots/2026-11-08/el9/baseos/ inst.ks=http://boot.example.org/ks/${mac}.cfg ip=dhcp
initrd ${base}/initrd.img
boot
```

Variables such as `${mac}`, `${uuid}`, `${serial}` and `${hostname}` let the script (or the web service that generates it) choose an installer and an answer file per machine. A dynamic endpoint such as `http://boot.example.org/boot?mac=${mac}&serial=${serial}` can return a script for an install, a rescue environment or `exit` (to fall through to the local disk), depending on a state machine: machines scheduled for provisioning get an installer; machines in service get `exit`, which is the key protection against an accidental reinstallation caused by a reboot with the network first in boot order.

**HTTP boot.** In UEFI HTTP boot mode the DHCP server returns the URL of an EFI binary as the boot file name, with vendor class `HTTPClient` in option 60 of the reply. Because the firmware downloads the file itself, it is possible to serve a signed shim and GRUB over plain HTTP in a trusted network, or over HTTPS if the firmware trusts the server certificate. Test the sequence on every hardware model in the fleet: some BMC consoles show "HTTP boot" entries only after a setting is enabled, and some firmware does not follow redirects.

**Installers and the kernel arguments.** Whatever the loader, the work ends in a kernel and an initrd with arguments. For Anaconda: `inst.repo=` (the installation source), `inst.ks=` (the answer file), `ip=` (network setup, `ip=dhcp` or a static form), `inst.sshd` and `inst.text`. The Red Hat guide describes the installation source and how the images are laid out on the server [src: rhel-10-docs ffc7d6339b0a689a]. For Debian: `auto=true priority=critical url=` and `netcfg/` arguments. For Ubuntu autoinstall: `autoinstall ds=nocloud-net;s=http://…/`. For a live-image approach (diskless or image deployer): a squashfs root over HTTP with `root=live:http://…` or `rd.live.image` options. Keep the installation tree and repository as versioned directories (for instance one per snapshot) so that the script selects a known set.

**Per-machine state and safety.** The central operational risk is reinstalling a machine that should not be touched. Mitigations: set the firmware to try the network only for machines marked for provisioning (via the baseboard controller, or by flipping a one-time boot flag with the IPMI/Redfish interfaces covered later in this course); make the boot service answer `exit` or the local-disk script for any machine not in the provision queue; require an explicit confirmation in the installer for non-empty disks; and log every boot request with MAC, serial and the answer given. Provisioning tools (Foreman, MAAS, Tinkerbell, Ironic) implement this as a state in the inventory, "build mode", which is switched off automatically after the first successful install.

**Security.** The provisioning network is trusted by installers and answers requests that can reach servers' disks, so treat it like a management network. Isolate it in a dedicated VLAN; use DHCP snooping and port security on the switches to stop rogue DHCP servers; serve boot files that are signed or whose checksums are published; prefer HTTPS between iPXE and the boot server with a CA compiled into the iPXE binary (you can build a custom iPXE with your trust anchor and with an embedded script that points at your server); keep answer files free of secrets; and put the TFTP service, if still needed, behind the same controls. Disable the network from the boot order on running servers where possible. Remember that anything the first-stage loader trusts, an attacker who controls DHCP can replace.

**Scale and performance.** TFTP serves only the first file; the rest goes over HTTP from a web server or a CDN-like cache, with the installation tree on fast local storage or a cached mirror of the repository snapshot. A 500-machine rack that boots simultaneously after a power event needs the HTTP server and the repository to deliver hundreds of megabytes each; stagger boots, use a local cache per rack, and use multicast-free methods. Block sizes and windowing options of TFTP (`tftp-max` and `--tftp-blocksize` in dnsmasq, RFC 2348 and 7440) give some improvement but are not a substitute for HTTP.

**Routed networks.** DHCP relays (`ip helper-address` on a router) carry DHCP across subnets, and the server selects the answer from the relay's gateway address (`giaddr`). Provide DHCP scopes and boot services in each site, or route to a central server, in which case HTTP boot over a WAN needs careful sizing.

**IPv6.** PXE over IPv6 uses DHCPv6 with option 59 (boot file URL) and the architecture type option 61. Support in firmware and in tools is uneven (to verify for your models); many sites keep a dual-stack provisioning network with IPv4 for boot and IPv6 afterwards.

**Troubleshooting method.** Work from the bottom: confirm the machine's switch port, VLAN and DHCP discover (`tcpdump -ni eth0 port 67 or port 68 or port 69`), check the offer's next-server and file name, check that TFTP serves the file (`tftp server -c get file`), then check the loader's output on the serial or virtual console, the HTTP access log for the script and kernel requests, and finally the installer's log (`/tmp/anaconda.log`, `journalctl` in the installer shell via `inst.sshd` or a debug console). Virtual machines with a UEFI firmware (OVMF) and a PXE or HTTP boot ROM reproduce most of the chain; libvirt with a network that has `<bootp file=…/>` and a TFTP root can test it without hardware.

## Assessment: the good, the bad and the ugly

**The good.** Network boot makes an empty machine installable without touching it, and it scales to thousands. DHCP options and iPXE give flexible per-machine decisions. HTTP removes TFTP's performance limits, and UEFI HTTP boot removes the middle loader. The ecosystem (dnsmasq, Kea, iPXE, Foreman, MAAS, Tinkerbell) is mature and free, and the same chain serves installers, image deployers and rescue systems.

**The bad.** The chain is long and fragile across firmware, and every vendor has quirks. TFTP is slow and unauthenticated. Secure Boot complicates custom loaders. DHCP must be correct for two firmware modes and for chainloading. Per-host state needs an inventory and a web service, which means the boot service becomes critical infrastructure. Debugging happens on consoles, often remotely over a BMC.

**The ugly.** Accidental reinstalls of production machines because network boot was first in the boot order and the provisioning service answered everyone; rogue DHCP servers from test labs that answer production boot requests; PXE-booted installers that trust any HTTP server because the repository URL was spoofable; and answer files fetched by anyone who guesses the URL.

**Assumptions.** Option numbers (93, 60, 59, 175) and the UEFI HTTP boot behaviour are as specified in the relevant RFCs and the UEFI specification and as documented by distributions; vendor firmware behaviour varies and should be tested on your hardware (to verify).

## Applications beyond this domain

The same pattern, minimal firmware that asks the network what to run and then fetches the rest over a normal protocol, is used for diskless thin clients and lab machines, for network equipment zero-touch provisioning (ZTP), for cloud bare-metal services (OpenStack Ironic, Equinix Metal's provisioning), for HPC clusters that boot nodes into RAM-based images, for edge devices that fetch images on first power-up, and for CI systems that reimage test machines before every job. Virtual machine platforms use the same ROMs (iPXE is the network boot ROM in QEMU).

## Examples

**Example 1: a lab PXE service in virtual machines.** Create a libvirt network with DHCP and TFTP enabled, a `bootp file` for the first-stage loader, serve `ipxe.efi` and `boot.ipxe`, create a UEFI VM with no disk image (network first), and watch it chain to your script and boot a rescue kernel.

**Example 2: per-host answer files.** The iPXE script requests `http://boot.example.org/ks/${mac}.cfg`. A small web service looks up the MAC in the inventory, renders the Kickstart template with the hostname and disk layout and returns it, or returns HTTP 404 if the machine is not scheduled, in which case the installer stops.

**Example 3: the safe default.** The boot endpoint returns `#!ipxe` followed by `exit` for every machine not in build mode. The inventory flips a machine to build mode when an operator schedules a rebuild and back when the machine registers after first boot.

**Example 4: HTTP boot for a rack of UEFI servers.** DHCP returns `http://boot.example.org/shimx64.efi` with option 60 `HTTPClient`; shim loads GRUB from the same directory, GRUB reads `grub.cfg-01-<mac>` over HTTP, and the kernel gets `inst.ks` from the Kickstart service.

**Example 5: capture and read the exchange.** On the provisioning host, `tcpdump -ni eth0 -vv port 67 or port 68` shows the discover, offer, request and acknowledgement with options; confirm that `option 93` is present in the discover and that the offer's `file` matches the architecture.

**Worked failure: the infinite loop.** A site's DHCP gave `ipxe.efi` to every UEFI client. The machines loaded iPXE, which did DHCP again, received `ipxe.efi` again, and loaded it again, forever. The fix was the option 175 match shown above, so that a machine already running iPXE receives a script URL instead.

## Related problems and ideas

This topic follows **unattended installation** (the answer files delivered here) and precedes **cloud-init** (first boot). It depends on **DHCP and DNS** services, on **switch configuration** (VLANs, DHCP snooping), and on **repository management** (the installation source). It connects to **Secure Boot and signing**, **baseboard management** (setting one-time boot and virtual media, later in this course), **bare-metal provisioning platforms** (Foreman, MAAS) and **image-based deployment**. In the virtualisation courses, the same ROMs and firmware options appear in the guest definition.

## Active research

Work includes making HTTPS boot reliable across firmware, with certificate enrolment through the BMC or a provisioning step; removing TFTP by default; measured and attested boot over the network, so that a provisioning service can check what the machine booted; confidential-computing machines whose firmware needs to be verified before receiving secrets; and new provisioning engines built around declarative workflows. The UEFI Forum and the IETF continue to refine the boot options for DHCPv4 and DHCPv6.

## Future direction

Expect HTTP(S) boot to replace TFTP, expect signed first-stage loaders and attestation to be standard, and expect provisioning to be driven by an inventory that tracks each machine's state from rack to retirement. For the operator, the lasting practices are to isolate and log the provisioning network, to make the default answer "boot from disk", to version every file the chain serves, to test in virtual machines and on each hardware model, and to keep the chain as short as the firmware allows.
