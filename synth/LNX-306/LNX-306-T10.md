# Provisioning Linux in public clouds: images, first boot, metadata and identity

## Define the problem

Everything in the earlier topics of this course has a cloud counterpart, with one large difference: nobody owns the hypervisor, the network that carries DHCP, or the boot path. A cloud virtual machine is created by an API call that names an **image**, a size, a network and some **user data**. The provider places it on a host, attaches a disk cloned from the image, and boots it. There is no installer to run, no PXE server to operate and no console cable. The operating system must therefore come from a prepared image, and everything that makes the machine unique (its name, keys, network settings, role) must arrive at first boot from the platform's own channels.

Provisioning in a cloud thus reduces to four linked problems. *Which image* runs, and who built and vouches for it. *How the image learns who it is* at first boot (the metadata service and the first-boot agent). *How the machine proves its identity to other services* without secrets baked into the image. And *how the fleet is described as code* so that it can be reviewed, reproduced and destroyed. The same questions apply whether the cloud is Amazon Web Services, Microsoft Azure, Google Cloud, or a private OpenStack installation.

Typical failures are well known. A custom image works on the builder's laptop but not in the cloud because it lacks the agent or drivers the platform expects. A machine boots but cannot be reached because the first-boot agent was not enabled, the datasource was not detected, or the network configuration was applied twice. Secrets placed in user data are readable by anything that can reach the metadata address. An unpatched image from a public catalogue is trusted because of its name. And a team clicks a fleet into existence in a console and then cannot rebuild it.

## History and approaches

Cloud provisioning grew from two inventions. The first was the machine image and the on-demand virtual machine, popularised by Amazon's Elastic Compute Cloud in 2006, where the Amazon Machine Image (AMI) is a template from which instances are launched; Red Hat's guide for AWS describes the path in terms of converting a RHEL image into an AMI, either through the image builder or by manual customisation, and then launching an instance from it [src: rhel-10-docs 4b5befa190ba4452]. The second was the **first-boot configuration agent**. Ubuntu's cloud-init, written to make images portable between clouds, reads user data and metadata from the platform and configures the machine; it became the default across distributions. The Rocky Linux guide presents the problem it solves as a bootstrapping conundrum: an image must be generic enough to clone, yet each clone must be configured before anything else can reach it [src: rocky-docs 74b4d7b5a5defc34]. Alternatives exist for other designs: Ignition (used by Fedora CoreOS and image-based Red Hat systems) runs once from the initramfs and cannot be re-run, which suits immutable systems; Red Hat documents delivering the Ignition file to bootc instances as ordinary instance user data on each cloud, with the Butane tool converting a human-written YAML file to Ignition JSON [src: rhel-10-docs 059c6bebfe887623].

The approaches to producing images follow from this. **Vendor marketplace images** are the fastest start and inherit the vendor's maintenance. **Custom images built by a pipeline** (the Packer topic) add hardening and local agents and are the norm in regulated environments. **Image builders** from the distribution (RHEL image builder, `bootc-image-builder` for container-based systems, Debian's `debian-cloud-images`) produce cloud formats directly. **Golden image versus bootstrap**: a golden image bakes in everything and starts quickly but must be rebuilt for each change; a thin image plus first-boot configuration is flexible but slow and depends on the network at boot. Most teams choose a middle position: bake the operating system, agents and hardening, and apply role and secrets at boot.

Infrastructure as code then describes the surroundings. OpenTofu and Terraform manage cloud resources through providers, one for each platform (the libvirt provider used in the previous topic is the same idea locally). Each cloud also ships a declarative template language of its own (CloudFormation, Azure Resource Manager and Bicep, Google Deployment Manager and its successor) (to verify current names), and each has a command-line tool (`aws`, `az`, `gcloud`) for imperative work.

## Current state

**Preparing an image for a cloud.** An image that is uploaded from outside must carry what the platform expects. Red Hat's Azure procedure illustrates the pattern: register the system, install `cloud-init` together with the platform's guest drivers and daemons (the Hyper-V packages in this case), and write cloud-init configuration files that integrate with the platform, such as the datasource selection and reporting settings. It also configures swap on the **ephemeral** disk and warns that this temporary storage is lost when the machine is deallocated or moved, so only disposable data belongs there [src: rhel-10-docs 6ad334f56d7b36de]. The same lesson holds elsewhere: every cloud has an agent, a set of drivers (paravirtual network and storage, on Amazon the Nitro network and NVMe interfaces, on Azure Hyper-V), a console type (serial), and rules about the boot mode (BIOS or UEFI) (to verify per platform).

For Google Cloud, Red Hat's documentation covers obtaining the system images and creating instances from them, registering the system and managing it [src: rhel-10-docs 3d20ccdb28cb42ae]. In every case the vendor documents the agent, the supported image formats (RAW or VHD or QCOW2 conversions, depending on the platform) and the upload procedure (to verify per cloud).

**First boot with cloud-init.** The service detects its **datasource** (EC2, Azure, GCE, OpenStack, NoCloud and many others), reads the platform's metadata and user data and applies them in stages, as described in the earlier cloud-init topic. Rocky's guide adds a useful detail on networking: cloud-init can accept a declarative network configuration, and on Azure the sample configuration disables applying the platform's network configuration so that the distribution's own tooling stays in charge [src: rocky-docs bf2c292f7b57cf76] and [src: rhel-10-docs 6ad334f56d7b36de]. Where a platform provides network data, decide deliberately which party owns the interface configuration, because two parties fighting over it is a classic first-boot failure.

The usual user data content is the same as on a local seed: a user with an SSH public key, the package list, a few files, and a command to join the configuration management system. Most platforms also inject the SSH key chosen at creation; relying on that platform key pair alone is convenient for a single administrator but is poor for teams and rotation, which is why central identity (SSH certificates or an identity provider) is preferred beyond the first boot (to verify per environment).

**The metadata service.** On the major clouds a link-local address (169.254.169.254 on Amazon, Google and Azure, with different paths and header requirements) serves instance data: identifiers, network details, user data and, importantly, **temporary credentials** for the instance's role. This is how machines obtain identity without stored keys, and it is also a prime target. The Kubernetes security guide states the risk directly: metadata services are normally reachable from pods on the node, can expose credentials of the node and provisioning data such as kubelet credentials, and enable escalation inside the cluster or to other cloud services. Its recommendations are to restrict permissions on instance credentials, to use network policies to block pods from the metadata address, and not to carry secrets in provisioning data [src: kubernetes-docs 2ba10b343a82c64a]. On Amazon the second-generation metadata service requires a session token obtained with a `PUT` request and can be set as mandatory, which defeats simple server-side request forgery against the endpoint; the setting is applied per instance or as an account default (to verify per release) [web: aws.amazon.com].

**Identity and access.** The principle is to give each machine a role with the least permissions needed, bound to the instance by the platform, so that applications fetch short-lived tokens instead of holding keys. Human access should use the provider's identity federation and multi-factor authentication; root account keys are never used for automation. Secrets are delivered from a secret manager at runtime, with the instance's role as the credential, rather than through user data, which on most platforms is readable by anyone with the instance's metadata access and is stored by the platform (to verify per cloud).

**Networking and placement.** A machine is created inside a virtual network with subnets, route tables and security groups or firewall rules. Public addresses are exceptions: administration through a bastion, a managed session service or a private connection is the norm. Placement across availability zones is part of the provisioning decision, not an afterthought, since that is where resilience comes from.

**Fleets and scaling.** Rather than creating machines one by one, clouds provide groups (Auto Scaling groups, managed instance groups, scale sets) that create machines from a template and replace unhealthy ones. The template references an image identifier, so a rollout of a new image is a template change followed by a rolling replacement. The Kubernetes documentation describes the same mechanism one level up: node autoscaling provisions nodes in response to scheduling pressure, with different autoscaler implementations doing the work [src: kubernetes-docs 1fdc4984ea6a3d79] and [src: kubernetes-docs 1a349b71ba078d33]. Images must therefore start without human help and register themselves (with the load balancer, with the configuration system, or with the cluster).

**As code.** A minimal OpenTofu configuration declares a provider and region, a data source that finds the latest approved image by filter, a network, a security group, an instance with `user_data` and an instance profile, and outputs. State is stored in a remote backend with locking; credentials come from the environment or a role, never from the file. Plans are reviewed before apply, as the earlier topic taught, and destructive changes (such as replacing a database host) need an explicit gate.

## Assessment: the good, the bad and the ugly

**The good.** An API-created machine takes seconds to minutes, can be created and destroyed in tests, and is rebuilt from code on demand. Identity bound to the instance removes a whole class of secrets. Image pipelines give a verifiable supply chain.

**The bad.** Each cloud differs in image formats, agents, metadata paths, networking terms and quotas, so a multi-cloud claim has real cost; portability exists at the level of cloud-init and OpenTofu syntax but not of resources. First boot depends on a network and a metadata service, which makes failures hard to see without a serial console or an instance log. Costs accrue silently from forgotten machines, unattached disks and data transfer.

**The ugly.** Credentials in user data, public storage buckets, instance roles with administrator rights, an unauthenticated metadata endpoint reachable through a vulnerable web application, and public images from unknown publishers are the recurring causes of cloud breaches. A second class is accidental persistence: data placed on the ephemeral disk, or a deletion of an instance with the boot disk set to be deleted, takes the data with it. A third is the unreproducible console-built fleet.

**Assumptions.** Package and file names follow the cited Red Hat and Rocky pages; metadata addresses, header names, format lists and account defaults follow the providers' public documentation as the author understands it and change with releases, so they are marked (to verify) and must be checked against the provider's current pages [web: aws.amazon.com] [web: cloud.google.com] [web: learn.microsoft.com].

## Applications beyond this domain

The same pattern, a generic artifact plus instance-specific data delivered by the platform at first start, is how containers receive configuration (environment, mounted config maps and secrets), how phones are provisioned by enrolment, and how IoT devices onboard. The metadata-credential pattern reappears in Kubernetes service account tokens and in workload identity federation between clouds.

## Examples

**Example 1: select the image by filter, not by identifier.** A configuration looks up the newest image from the organisation's own account with a given name prefix and a tag showing it passed the pipeline's tests, so that a patched image reaches new machines without editing the code.

**Example 2: user data for a web node.** The `#cloud-config` creates the admin user with a certificate authority line for SSH, installs `chrony` and the configuration agent, and runs the join command; no secret appears in it. The agent fetches its secrets later through the instance role.

**Example 3: preparing an Azure image.** Install `cloud-init` and the Hyper-V daemons, set the Azure datasource, enable reporting, put swap on the ephemeral disk through the documented disk setup, and test by creating an instance and reading the console and cloud-init logs [src: rhel-10-docs 6ad334f56d7b36de].

**Example 4: blocking pods from the metadata address.** A network policy denies egress from application namespaces to 169.254.169.254 while allowing the platform agents that need it, and instance roles are reduced to the minimum [src: kubernetes-docs 2ba10b343a82c64a].

**Example 5: an immutable image with Ignition.** For a bootc image on a cloud, write a Butane file, convert it to Ignition JSON and pass it as user data; the configuration runs once at first boot [src: rhel-10-docs 059c6bebfe887623].

**Worked failure: the leaked role.** A web application with a server-side request forgery flaw fetched an attacker-supplied URL. The attacker pointed it at the metadata address and received temporary credentials for an over-privileged role, which listed storage buckets and copied customer data. The corrective actions were to require the token-based metadata service, to cut the role down to one bucket and one action, to add egress filtering from the application tier, and to alert on role credentials used from outside the cloud.

## Related problems and ideas

This topic joins the **cloud-init**, **Packer** and **OpenTofu** topics of this course and extends them to hosted platforms; it relies on **repository mirrors and image pipelines** from the software-delivery course, **hardening baselines** from the security course, and **identity and secrets management**. It is the counterpart of **bare-metal platforms**: the lifecycle of a machine is the same, but the platform now owns the physical layer. The container and Kubernetes courses take the pattern one level higher with node pools and autoscaling.

## Active research

Open areas include confidential computing (encrypted virtual machine memory with attestation, so the provider cannot read the guest), workload identity federation across clouds, supply-chain provenance for images (signed builds, attestations, software bills of materials), and policy-as-code that checks plans before they are applied.

## Future direction

Expect immutable, signed, minimal images with first-boot configuration limited to identity and role, expect metadata services to demand tokens by default, and expect more provisioning to be reconciled by controllers (Cluster API, cloud operators) rather than run as one-shot scripts. For the administrator the stable skills are the same: build images in a pipeline, keep secrets out of images and user data, give machines narrow identities, and describe everything as code.
