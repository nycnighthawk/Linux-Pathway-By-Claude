# Infrastructure as code with OpenTofu and the libvirt provider

## Define the problem

Images and first-boot configuration make a machine reproducible, but a fleet is more than machines. It has networks, storage pools, volumes cloned from base images, several virtual machines of different sizes, addresses and names, and the relationships between them. Creating these by hand with `virt-install`, `virsh` and a pile of scripts has the usual failures: the steps live in a runbook that is out of date, a script that creates ten machines cannot safely be run again to create eleven, nobody can say what exists without looking at the hypervisor, and removing a test environment leaves orphaned disks. **Infrastructure as code** (IaC) answers these problems with a declarative description of the desired infrastructure and a tool that compares the description with reality, shows a plan of the differences, and applies them. The tool keeps a record, the *state*, of what it created, so that the next run can update or destroy exactly those objects.

**Terraform**, released by HashiCorp in 2014, defined this style. After HashiCorp changed its licence to the Business Source License in 2023, the Linux Foundation hosts **OpenTofu**, a community fork that remained open source (Mozilla Public License 2.0) and kept the language and workflow; its command is `tofu` where Terraform's is `terraform`. This course uses OpenTofu; nearly everything here applies equally to Terraform. The details of the licence change, of the fork's governance and of the version at which features differ should be verified when it matters to you (to verify).

The task of this topic is to use OpenTofu to provision virtual machines on a KVM host through **libvirt**, the same virtualisation layer used throughout the course, via the community **libvirt provider** (the widely used one is the `dmacvicar/libvirt` provider). The goal is a small, reusable configuration that creates a storage pool, a network, a base image volume, a set of VMs cloned from that image, a cloud-init seed for each (the previous topic) and outputs that downstream tools can use. Typical failure modes: state lost or shared incorrectly, so the tool tries to recreate everything or destroy someone else's resources; secrets in state files committed to Git; provider and tool versions drifting between engineers; plans applied without review; resources changed outside the tool (a VM edited with `virsh`), causing drift; cloud-init changes that force replacement of the VM; permission problems between the user that runs the tool, libvirt and the security module (AppArmor, SELinux) that confines QEMU; and IP addresses that the configuration needs but the provider only learns after boot.

## History and approaches

Early automation of virtual infrastructure was imperative: scripts that called `virsh`, `virt-install` or a vendor API, or kickstart-based tooling like `cobbler`. Configuration management tools (Puppet, Chef, Ansible) added modules for creating VMs and cloud instances, but they were designed for *configuring* hosts, not for tracking the lifecycle of the infrastructure itself. CloudFormation (AWS, 2011) was the first widely used declarative IaC system and was tied to one cloud. Terraform generalised the model across providers with a plugin architecture: a **provider** is a plugin that knows how to create, read, update and delete a family of resources through an API (AWS, Azure, Kubernetes, libvirt, DNS services, GitHub). A **resource** block declares an object; a **data** block reads something that exists; **variables** and **outputs** are parameters and results; **modules** package a reusable configuration. The tool builds a dependency graph from references between resources, creates things in order and in parallel where possible, and writes the result in a state file mapping configuration addresses to real object identifiers.

OpenTofu keeps this model and adds its own work: for example, state encryption in its 1.7 release in 2024 (to verify the version), a registry that serves providers independent of HashiCorp, and compatibility with the Terraform 1.5/1.6 era files. The libvirt provider, created by Duncan Macvicar (the `dmacvicar` account) and maintained by a community, exposes libvirt's objects as resources: `libvirt_pool`, `libvirt_volume`, `libvirt_network`, `libvirt_domain`, `libvirt_cloudinit_disk` (building the seed ISO from user-data, meta-data and network-config), `libvirt_ignition` for CoreOS-style systems, and data sources. A major rewrite of the provider's schema occurred in newer versions; resource and attribute names differ between 0.7.x and later lines, so pin the version and read the documentation for it (to verify).

Alternatives illustrate the choice. **Ansible** has `community.libvirt` modules and can create VMs, and it can drive the whole configuration, but it has no state and so it cannot easily delete what it no longer declares. **Pulumi** and the **CDK for Terraform** use general-purpose languages instead of HCL for the same model. **Crossplane** applies the model inside Kubernetes. **Vagrant** targets developer VMs with a simple file and providers including libvirt. **Cloud-provider tools** (CloudFormation, ARM/Bicep, Deployment Manager) are limited to one cloud. **KubeVirt** and **OpenStack** provide APIs of their own that Terraform can also call. The libvirt provider is a good teaching tool because it needs only a Linux laptop or server, but the same workflow applies to cloud APIs. The Red Hat documentation on Image Builder includes building Vagrant images for the libvirt back end, which links image building to this style of VM definition [src: rhel-10-docs 2daf7ac81172b2ff].

## Current state

**Workflow.** The core commands are `tofu init` (download providers and modules, create the lock file `.terraform.lock.hcl`), `tofu fmt` and `tofu validate` (format and check syntax), `tofu plan` (compute and show the changes), `tofu apply` (execute; `-auto-approve` only in controlled pipelines), `tofu destroy` (remove what the state records), `tofu output` (read outputs), `tofu state list/show` (inspect state), and `tofu import` or an `import {}` block (bring an existing object under management). Save plans (`tofu plan -out=plan.bin`) and apply that exact file in pipelines so that what was reviewed is what runs. `-target` exists, but using it routinely is a smell that the configuration should be split.

**A configuration for libvirt.** A minimal but realistic file set:

```
terraform {
  required_version = ">= 1.6"
  required_providers {
    libvirt = {
      source  = "dmacvicar/libvirt"
      version = "~> 0.7"
    }
  }
}

provider "libvirt" {
  uri = "qemu:///system"
}

variable "ssh_public_key" { type = string }
variable "vm_names"       { type = set(string) }

resource "libvirt_pool" "site" {
  name = "site"
  type = "dir"
  path = "/var/lib/libvirt/images/site"
}

resource "libvirt_volume" "base" {
  name   = "el9-base.qcow2"
  pool   = libvirt_pool.site.name
  source = "https://images.example.org/el9-base-2026.11.08.qcow2"
  format = "qcow2"
}

resource "libvirt_volume" "disk" {
  for_each       = var.vm_names
  name           = "${each.key}.qcow2"
  pool           = libvirt_pool.site.name
  base_volume_id = libvirt_volume.base.id
  size           = 21474836480
}

resource "libvirt_cloudinit_disk" "seed" {
  for_each  = var.vm_names
  name      = "${each.key}-seed.iso"
  pool      = libvirt_pool.site.name
  user_data = templatefile("${path.module}/user-data.tftpl", {
    hostname = each.key
    ssh_key  = var.ssh_public_key
  })
}

resource "libvirt_domain" "vm" {
  for_each  = var.vm_names
  name      = each.key
  memory    = 2048
  vcpu      = 2
  cloudinit = libvirt_cloudinit_disk.seed[each.key].id

  network_interface {
    network_name   = "default"
    wait_for_lease = true
  }
  disk {
    volume_id = libvirt_volume.disk[each.key].id
  }
  console {
    type        = "pty"
    target_port = "0"
  }
}

output "addresses" {
  value = { for k, d in libvirt_domain.vm : k => d.network_interface[0].addresses }
}
```

Several ideas in this file link to earlier topics. The base volume comes from an image built by Packer or Image Builder and published with a version in its name. Each VM disk is a copy-on-write overlay (`base_volume_id`), which keeps ten VMs cheap and makes creation fast. The seed is the NoCloud ISO of the cloud-init topic, generated from a template with the hostname and key per VM. `for_each` over a set of names makes the number of machines data, not code: adding a name adds a VM, and removing a name destroys only that one. The `wait_for_lease` setting lets the output show addresses, though it depends on a guest agent or DHCP lease visible to libvirt.

**State.** State maps resources to real objects and is the source of most operational risk. Local state in a file is fine for a lab; teams need a **remote backend** with locking, such as an S3 bucket with a lock table, a PostgreSQL database, or an HTTP backend, so that two people cannot apply at once and so that the state is shared and backed up. State contains attribute values, which can include secrets (passwords, keys, generated tokens), so it must be access-controlled and encrypted; OpenTofu's state encryption feature can protect it at rest (to verify). Never commit state to Git. Never edit it by hand; use `tofu state mv`, `rm` and `import` or the declarative `moved {}`, `removed {}` and `import {}` blocks.

**Variables and secrets.** Mark variables `sensitive = true` to keep them out of plan output (they remain in state). Supply values through `-var-file` files that are not committed, environment variables (`TF_VAR_name`), or a secrets manager data source. Keep the public SSH key as an ordinary variable; keep private material out of configuration entirely.

**Modules and structure.** Put reusable parts in modules (`modules/vm` that takes name, size, image and seed) and keep an environment directory per environment (`envs/dev`, `envs/prod`) with its own state and variable values. Avoid workspaces for long-lived environments, because they share a backend and hide differences. Pin module sources by version or Git tag. Keep the lock file in version control so that everyone uses the same provider builds, and update it deliberately with `tofu init -upgrade`.

**Drift.** Drift is the difference between the configuration or state and reality. `tofu plan` refreshes state from the provider and shows changes; `tofu plan -refresh-only` (the replacement for the old `refresh` command) reports drift without proposing changes to configuration. If a VM was modified by hand, either bring the configuration in line (and apply), or let the tool revert it. For attributes that legitimately change outside the tool (for example, addresses assigned by DHCP), use `lifecycle { ignore_changes = [...] }` sparingly. The drift topic later in this course addresses detection at the operating system level, which OpenTofu does not see.

**Lifecycle rules.** `prevent_destroy` guards critical resources, `create_before_destroy` changes the order of replacement, and `replace_triggered_by` forces replacement when something else changes. A change to a cloud-init seed typically forces a new seed ISO but does not re-run cloud-init in the existing guest (the instance-id is unchanged), so changing user-data on a running VM has no effect until the VM is replaced or the cloud-init state is cleaned. Decide whether a configuration change should replace the VM (immutable style) or be pushed by configuration management (mutable style); do not leave it ambiguous.

**Permissions and platform specifics.** The user that runs `tofu` needs access to the libvirt socket (membership of the `libvirt` group for `qemu:///system`, or a user-session URI `qemu:///session`), and the QEMU process must be able to read volumes in the pool path (file ownership by `libvirt-qemu` or `qemu`, and SELinux contexts on Enterprise Linux or AppArmor profiles on Debian family hosts). Remote hosts use `qemu+ssh://user@host/system`. Network resources use libvirt's NAT or bridge modes; the Red Hat documentation on virtual machine networks describes the connection types, such as NAT-based and bridged, which decide whether your VMs are reachable from outside the host [src: rhel-10-docs acb1a0a4cbf99581]. The libvirt project lists third-party integration modules for several languages and tools, which includes Terraform's provider [src: libvirt-docs eb9c22fed5172ea1].

**Pipelines and review.** In CI, run `fmt -check`, `validate`, a security scan of the configuration (tools such as `tfsec`/`trivy config`, `checkov` or policy checks in OPA/Conftest) and `plan`; post the plan as a review comment; apply only from the main branch after approval, using the saved plan file and credentials scoped to the environment. Keep a record of who applied what and when (the pipeline log). Test modules with `tofu test` (introduced in recent versions, to verify) or with a small environment created and destroyed in CI.

**The first-boot link.** Provisioning hands the machine over to cloud-init (the earlier topic) and then to configuration management. Use outputs (addresses, names) to generate an Ansible inventory or register machines in DNS. A common pattern is a `local-exec` or the `ansible` provider to run a playbook after creation; prefer asynchronous configuration (the VM pulls its configuration) over provisioners that make the plan depend on SSH access, and treat provisioner blocks as a last resort.

## Assessment: the good, the bad and the ugly

**The good.** Declarative infrastructure is reviewable, repeatable, diffable and reversible: a pull request shows exactly what will change, a new environment is another copy of the configuration with different variables, and teardown is `destroy`. The same workflow covers laptops, private clouds and public clouds. The ecosystem of providers and modules is large. For a team, the plan is a conversation tool and a safety check.

**The bad.** State is a liability to manage, and mistakes with it can destroy infrastructure. The provider for libvirt is community-maintained, with uneven coverage and API changes between versions; libvirt-specific behaviours (leases, qemu guest agent, permissions) appear as flaky waits. HCL is limited as a language, and complex logic gets awkward. Applying changes to long-lived stateful machines is risky: a replacement is a destruction. A tool that tracks creation does not track what happens inside the guest, so it is not a configuration management system. Licensing and governance changes in the ecosystem require attention.

**The ugly.** Real incidents come from state: a state file deleted or overwritten, so the next apply recreates machines that already exist (or fails halfway); two engineers applying at once without a lock; a `destroy` run in the wrong directory or workspace; secrets in state pushed to a public repository; and the "just this once" manual edit that makes the plan show a dozen unexpected replacements. A subtler one is applying a plan that was reviewed against an older state; always apply the saved plan.

**Assumptions.** Resource and attribute names are for the 0.7 line of the libvirt provider and OpenTofu 1.6 and later; they differ in other versions, and some features (state encryption, `tofu test`, `removed` blocks) arrived in particular releases (to verify).

## Applications beyond this domain

The workflow is the same for cloud accounts, Kubernetes clusters, DNS zones, monitoring dashboards, identity providers, GitHub organisations and SaaS configuration. Platform teams offer modules as a catalogue ("a standard VM", "a standard network") that application teams use. GitOps tools run the same plan and apply loop automatically against a Git repository. Teaching labs use it to create classroom environments for every student and to destroy them afterwards. The pattern of desired state, plan, apply and state is also the model of Kubernetes controllers and of configuration management in its declarative forms.

## Examples

**Example 1: three VMs from one base image.** Set `vm_names = ["web01", "web02", "db01"]`, run `tofu init`, `plan` and `apply`; each VM gets a copy-on-write disk and a seed with its own hostname; the output prints their addresses. Removing `web02` from the set and applying destroys only that VM, its disk and its seed.

**Example 2: a remote libvirt host.** Change the provider URI to `qemu+ssh://ops@kvm01.example.org/system` with an SSH key from the agent; everything else stays the same.

**Example 3: reviewing a plan in CI.** The pipeline runs `tofu plan -out=plan.bin`, converts it with `tofu show -json plan.bin`, runs policy checks (no VM with more than 16 GiB, only approved base images, no `prevent_destroy` removed), uploads the plan, and a reviewer approves the merge; a second job applies `plan.bin`.

**Example 4: adopting an existing VM.** An `import {}` block with `to = libvirt_domain.vm["legacy01"]` and the domain's UUID brings a hand-made VM under management; the plan then shows the differences between its real settings and the configuration, which you resolve before applying.

**Example 5: image upgrade by replacement.** Change the base volume's source URL to the next image version; the plan shows the base volume replaced and every VM disk recreated. Use a rolling approach (a variable listing which names use the new image) so that machines are replaced a few at a time, as in the patch ring topics of the packaging course.

**Worked failure: the lost state.** A laptop with the only copy of a local state file was reimaged. The configuration remained, so `apply` tried to create machines whose names already existed on the hypervisor and failed on the first collision, leaving half of the resources newly created and half missing from state. Recovery was by importing each existing object into a fresh state, then moving to a remote backend with locking and versioned storage.

## Related problems and ideas

This topic uses **images** (Packer, Image Builder), **cloud-init** (the seed volume) and **networking** (libvirt networks); it leads to **bare-metal management** (Foreman, MAAS), **cloud provisioning** (the same language for public clouds), **drift detection**, **configuration management** (Ansible, which configures what OpenTofu creates) and **policy as code**. It relates to **GitOps**, **secrets management**, **CI/CD**, **cost control** (cloud resources) and **disaster recovery** (rebuilding an environment from code and backups).

## Active research

Open topics include safer state handling (encryption, finer locking, state-free or state-light models), better drift detection and reconciliation loops that run continuously, higher-level abstractions (platform APIs) over provider-level resources, testing frameworks for infrastructure code, and policy engines that evaluate plans before apply. In the open-source ecosystem, work continues on provider registries independent of any single vendor and on compatibility between OpenTofu and Terraform as they diverge.

## Future direction

Expect infrastructure code to be tested and reviewed like application code, to run continuously through GitOps controllers, and to be abstracted behind internal platform catalogues. Expect hybrid use of declarative infrastructure for the creation of machines and declarative configuration or images for their content. For the operator, the lasting practices are to pin versions, store state remotely with locking and encryption, review saved plans, keep secrets out of code, and write small modules with clear inputs and outputs.
