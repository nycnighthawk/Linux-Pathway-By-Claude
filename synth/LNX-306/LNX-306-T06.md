# Bare-metal provisioning platforms: Foreman and MAAS

## Define the problem

The previous topics gave the parts of a provisioning chain: an answer file, network boot, first-boot configuration, an image, and code that declares machines. For virtual machines those parts can be assembled with a few scripts and a hypervisor API. Physical servers add a layer of difficulty. They arrive from a vendor and must be racked and cabled before anyone knows their serial numbers or MAC addresses. Their firmware has to be inspected and sometimes updated. Their power is controlled through a baseboard management controller (BMC) with its own network and credentials. They have disks and network cards that differ from machine to machine, and an answer file that assumes one disk name fails on another. And they are reused: a server is installed, repurposed, wiped and installed again, over years. A **bare-metal provisioning platform** is the system that keeps an inventory of these machines, discovers new ones, controls their power, boots and installs them according to a role, and tracks their state until they are retired.

Two open-source platforms dominate Linux practice. **Foreman**, with its content management plugin Katello (covered in the packaging course) and the commercial **Red Hat Satellite** built from it, comes from the Red Hat world and supports any distribution, with strength in Enterprise Linux. **MAAS** (Metal as a Service), from Canonical, comes from the Ubuntu world and treats a rack of servers as a pool of resources that can be allocated and deployed like cloud instances. A third family, **OpenStack Ironic** (and its Kubernetes counterpart Metal³), **Tinkerbell**, and **Matchbox**, serves cloud and cluster builders; the Linux-based **Fleet** of edge devices uses **FIDO Device Onboard** (FDO) and similar mechanisms. This topic is a "know the landscape" overview, graded at the lowest depth of the course, because learners rarely have racks to practise on; it concentrates on the model, the lifecycle and the decisions, and its exercise is a planning one.

The typical failure modes are organisational as much as technical. The inventory says one thing and the rack another, because nobody scanned the serial numbers. A discovered machine is installed with the wrong role because host names were matched by guesswork. A BMC is on the production network with a default password. Two provisioning servers answer the same DHCP request. A reinstall wipes a machine that was meant to keep its data. The platform itself becomes a critical single point of failure that nobody can rebuild. And the platform's templates drift from the repository snapshots and answer files that engineers actually use.

## History and approaches

Provisioning servers by network goes back to the diskless-workstation era, and the Linux versions of the idea included Cobbler (2008, by Michael DeHaan, who also created Ansible), which managed DHCP, TFTP, kickstart files and a repository mirror from one tool. **Foreman** began in 2009 (by Ohad Levy at Red Hat) as a lifecycle tool for Puppet-managed servers: a web interface and API over a database of hosts, with *smart proxies* that do the work near the machines (DHCP, DNS, TFTP, the Puppet certificate authority, BMC power control and template serving), *compute resources* (libvirt, VMware, EC2, OpenStack, Proxmox and others, so that the same workflow creates VMs and bare-metal hosts), *host groups* that bundle operating system, partition table, provisioning templates, Puppet or Ansible roles and parameters, and *provisioning templates* written in ERB that render Kickstart, preseed, AutoYaST, PXELinux, iPXE, GRUB and cloud-init files per host. Katello adds content management (products, repositories, content views, lifecycle environments), described in the packaging course, and Red Hat Satellite is the supported product that bundles both. The Red Hat web console documentation shows Satellite host management and monitoring integrated into the console, which gives an idea of how far the platform reaches into day-two operations [src: rhel-10-docs 83f3b91ce6c43dea].

**MAAS** started at Canonical around 2012, to make a large deployment of physical servers behave like a cloud: a **region controller** (the API, database and web interface) and one or more **rack controllers** (which provide DHCP, TFTP/HTTP boot and power control near the machines). A new machine that PXE boots is **enrolled** as "New", then **commissioned**: MAAS boots an ephemeral Ubuntu image on it that gathers hardware facts (CPU, memory, disks, network interfaces, serial numbers), runs commissioning and testing scripts (storage and memory tests, firmware checks), and records the results. A commissioned machine is "Ready" and can be **allocated** (reserved by a user or tag), **deployed** (installed with a chosen image, such as Ubuntu or CentOS or custom, partition layout and network configuration, using Curtin as the installer and cloud-init for the first boot), **released** (and optionally wiped) and returned to the pool. MAAS has tags, zones, resource pools, a CLI and API (so that Terraform and Juju can use it), and *KVM pods* for creating virtual machines on libvirt or LXD hosts.

**Ironic** is the bare-metal service of OpenStack, with drivers for IPMI and Redfish and deployment methods using a deploy ramdisk, and it can run standalone (without the rest of OpenStack). **Metal³** exposes bare metal as Kubernetes resources (`BareMetalHost`) and uses Ironic underneath. **Tinkerbell**, a CNCF project from Equinix Metal, models provisioning as workflows executed by an in-memory agent. **Matchbox** matches machines to configurations for Fedora CoreOS and Flatcar. The **Foreman** and **MAAS** line stands out for the breadth of operating system support (Foreman) and the cloud-like allocation model (MAAS). The differences in philosophy follow: Foreman is a *host lifecycle manager* (a host has an operating system and a configuration that the tool tracks continuously, including after installation), while MAAS is a *machine allocator* (it hands over a deployed machine and mostly steps back).

Another recent strand is secure **device onboarding** for edge equipment. The RHEL for Edge documentation describes **FDO** (FIDO Device Onboard), in which a device carries a voucher that identifies its owner, contacts a rendezvous server and then an owner onboarding server to receive credentials and configuration, without any pre-configuration in the field; the documentation lists the components and the workflow of an FDO system [src: rhel-10-docs 56b93d24dc76dcad] and [src: rhel-10-docs f5246a22583b3b42]. For data centre servers the equivalent is the combination of discovery and BMC credentials, but FDO's idea of an ownership voucher shows the direction of travel.

## Current state

**The lifecycle model.** Whatever the product, a server passes through the same states, and a platform exists to make the transitions safe:

1. *Racked and cabled*: asset tag, serial, port mapping recorded.
2. *Discovered or enrolled*: it PXE boots (or is added through its BMC) and appears in the inventory with its MAC addresses and facts. Foreman's discovery plugin boots a small discovery image and reports facts; MAAS enlists and commissions.
3. *Prepared*: BIOS and BMC settings, firmware updates, RAID configuration, hardware tests (memory, disks, network), and BMC credentials set to a site-specific value. Burn-in tests catch bad components before production.
4. *Ready or available*: in a pool, with no owner.
5. *Assigned and deployed*: given a role (host group or tag), an image or installation source (pinned to a snapshot), a network configuration and a first-boot configuration.
6. *In service*: managed by configuration management and patch rings.
7. *Repurposed or retired*: released, wiped (the secure wipe topic later in this course), and either returned to the pool or removed from the inventory and the asset records.

**Components.** The platforms need: an *inventory database* (hosts, interfaces, BMC addresses, roles); *DHCP, DNS and TFTP/HTTP services* under the platform's control (so that the answer to a boot request depends on the host's state: build now, or boot from disk); *power control* through IPMI or Redfish (the next topic) or a smart PDU; an *installation source* (repository, ISO or image); *templates* for the installers; and *credentials* management. Foreman delegates these to smart proxies; MAAS puts them in rack controllers. Both can integrate with an existing DHCP server only with effort, so a dedicated provisioning VLAN is normal.

**Foreman workflow in practice.** An administrator defines an operating system and its installation media (a pinned repository URL), partition tables and provisioning templates (starting from the stock templates in the distribution), a host group with these and the subnet, domain and smart proxy, then either creates a host (entering the MAC address, picking the group) and sets it in *build mode*, or uses a discovered host and *provisions* it. Foreman's DHCP smart proxy reserves an address, the TFTP proxy writes a per-host boot file, the host boots, the installer fetches the rendered Kickstart from Foreman, and at the end a callback (`built`) tells Foreman to leave build mode. A later reboot boots from disk, which is the safety property discussed in the network boot topic, implemented as state. Host parameters supply per-host values (for example an NTP server) into templates. Registration with Katello (activation keys) happens in the Kickstart `%post`. The `hammer` command-line tool and an API allow all of this to be scripted, and Ansible collections and Terraform providers exist for it.

**MAAS workflow in practice.** After installing MAAS (a snap or packages) with a region and rack controller, enable DHCP on the provisioning VLAN through MAAS, import boot images, and power on unknown servers set to PXE boot. They appear as New; set the BMC type and credentials (MAAS can often detect it, or you enter it), commission, review the hardware results, tag machines (`gpu`, `ssd`), and then deploy by CLI: `maas admin machines allocate tags=ssd`, `maas admin machine deploy $SYSTEM_ID distro_series=jammy user_data=@cloud-config.yaml`. Storage layouts (flat, LVM, bcache, RAID) and network bonds and VLANs are described per machine or by default rules. The same machines can be used through the Terraform MAAS provider as resources.

**Identity of machines.** Choose what identifies a host and stick to it: the BMC MAC address, the serial number from DMI (`dmidecode -s system-serial-number`), or an asset tag. MAC addresses of the installation network card are the usual key for DHCP, but they change when a card is replaced; serial numbers survive that. Foreman and MAAS both keep interface lists, so replacing a NIC is an update, and the templates should not hard-code interface names.

**Security.** The platform is the keys to the kingdom: it can reinstall every server and holds BMC passwords. Harden and isolate it: management and provisioning networks separate from production, access control on the web interface and API with a real identity provider (LDAP, OIDC), role-based permissions that separate "view" from "reinstall", audit logs, TLS everywhere, and secrets for BMCs rotated and stored in a vault. Restrict who can put a host in build mode, and treat that action as destructive and approved. Keep templates and host groups in version control (Foreman has export/import for templates, and the Foreman Ansible modules apply them from files). Back up the database and the configuration, and rehearse recovery: a platform that cannot be rebuilt in hours is a risk.

**High availability and scale.** Foreman scales by adding smart proxies per site and an external database; MAAS by adding rack controllers and a PostgreSQL cluster behind regions. Both documents describe tens of thousands of machines for large installations, but small sites do well with a single instance and good backups. Decide where each provisioning service lives so that a site that loses its WAN link can still reinstall a machine locally.

**Integration with the rest of this course.** The platform feeds machines into configuration management (the node registers with Ansible or Puppet), into content management (Katello) and into monitoring. It consumes images from Packer or Image Builder. It can create VMs on libvirt through compute resources (Foreman) or pods (MAAS), which overlaps with the OpenTofu approach of the previous topic; the sensible split is that the platform owns *physical machines and their lifecycle*, while infrastructure as code owns *logical resources and virtual machines* in a cloud-like layer, and each tool calls the other when needed (Terraform's MAAS provider is an example). The libvirt documentation lists provisioning among the applications built on it, which includes tools of this kind [src: libvirt-docs a610dbf454f61cc9].

**Alternatives and when they fit.** For a few servers, an Ansible playbook with a PXE container and a Kickstart is enough. For a data centre of Ubuntu servers treated as a pool, MAAS is a natural choice. For a mixed Enterprise Linux estate with content management and compliance, Foreman/Katello or Satellite. For Kubernetes clusters on metal, Metal³ or Cluster API with a provider. For OpenStack clouds, Ironic. For device fleets at the edge, FDO plus image-based updates.

## Assessment: the good, the bad and the ugly

**The good.** A provisioning platform converts racking into a pipeline: new hardware enrols itself, is tested, and is assigned and installed by a request. The inventory is accurate because it is created from the hardware itself. Both Foreman and MAAS are mature and scriptable, support IPMI and Redfish, and integrate with the configuration and image tools around them. State-based build mode makes accidental reinstall much less likely than a hand-run PXE server.

**The bad.** They are heavy systems to run and upgrade, with databases, several services and many settings. They require network design (VLANs, DHCP) that the data centre team must agree to. Hardware is messy: BMCs differ, firmware bugs affect discovery and power control, and custom RAID controllers need special handling. The learning curve is steep, and the line between what the platform does and what configuration management does is easy to blur. They tie you to their template languages and image formats.

**The ugly.** Default BMC credentials and exposed BMC networks. A platform with one administrator account shared by everybody. A provisioning template edited in the web interface and never recorded anywhere else, so that the live configuration cannot be reproduced. A "temporary" discovery setting that automatically installs any machine that appears on the network. And a failed upgrade of the platform with no backup, leaving a data centre unable to rebuild a failed server.

**Assumptions.** The component names (smart proxy, region and rack controller, commissioning) reflect current project documentation and the author's knowledge; commands and plugin names change between releases (to verify). This section is intentionally conceptual because the depth is low.

## Applications beyond this domain

The state-machine view of a physical asset (discovered, tested, ready, allocated, in service, retired) applies to laptops (MDM and zero-touch enrolment), network equipment (ZTP), mobile devices, cloud capacity and even IT asset management in general. The idea of ephemeral commissioning images that report facts is also used in HPC cluster tools, in Kubernetes node onboarding and in hardware testing labs. FDO's ownership vouchers parallel the supply-chain concerns of secure boot and attestation.

## Examples

**Example 1: Foreman host group.** Create an operating system "Rocky 9" with the installation media pointing at a repository snapshot, a partition table named "LVM thin", a Kickstart template based on the default, and a host group "web" with the subnet, domain, proxy and the Ansible role to run after install. Create a host by MAC address, set build mode, power-cycle through the BMC, and watch it install.

**Example 2: MAAS commissioning.** Power on five new servers set to PXE boot. They enlist as "New". Commission them; failing memory tests on one machine marks it as "Failed testing" and keeps it out of the pool until the DIMM is replaced. Tag the machines with NVMe drives, allocate three of them with that tag and deploy Ubuntu with a cloud-init file that registers the node with configuration management.

**Example 3: reinstall safety.** A host in service has build mode off. A mistaken network boot gives `exit` to the local disk and nothing is reinstalled. A change request switches build mode on for a named host, an approver sets it, and the platform logs who did it.

**Example 4: BMC password rotation.** The platform stores BMC credentials in a vault and rotates them quarterly through the Redfish API; the inventory shows the date of the last rotation per host; hosts older than the limit are reported.

**Example 5: recovery drill.** Restore the platform database and templates on a fresh VM from backup, point the DHCP relay at it, and reinstall one test server, timing the whole exercise.

**Worked failure: the double DHCP.** A test lab, connected by accident to the provisioning VLAN, ran its own DHCP server. Some production servers that rebooted that night received answers from the lab server and booted a lab installer. They were not reinstalled, because the lab server had no matching build state and the platform's answer was to boot from disk, but several machines lost their network configuration until DHCP snooping was enabled on the switch ports and the lab was moved.

## Active research

Work in this area includes declarative, Kubernetes-style bare-metal APIs (Metal³ and Cluster API), secure onboarding with attestation and ownership vouchers (FDO, DICE and TPM-based schemes), better firmware management and inventory through Redfish, and workflow engines for provisioning (Tinkerbell). There is also interest in integrating hardware health data and carbon or power data into scheduling decisions.

## Future direction

Expect provisioning to be driven by declarative inventories in Git, expect Redfish to replace IPMI almost entirely, expect attested onboarding to become the default for new hardware, and expect more of the operating system installation to be replaced by image deployment. For the operator, the lasting practices are to make the inventory the source of truth, to automate discovery and testing, to keep reinstall a deliberate and logged state, to protect the BMC network and credentials, and to be able to rebuild the platform itself.
