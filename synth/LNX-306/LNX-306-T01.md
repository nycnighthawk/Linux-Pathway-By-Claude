# Unattended installation: Kickstart, Debian preseed and Ubuntu autoinstall

## Define the problem

Every managed server begins with an installation, and the manual installation wizard is the least repeatable tool in the toolbox. A person who clicks through screens makes different choices on different days, forgets steps, and leaves no record of what was selected. When a fleet grows past a handful of machines, or when machines are rebuilt as a routine instead of repaired, the installation itself has to become a file: a declaration of the language, the disk layout, the packages, the users and the first commands, which an installer reads and executes without a human. That file can be reviewed, stored in version control, tested, and applied identically to a virtual machine, a bare-metal server or a cloud instance. This is the job of the answer files used by the three main installer families: **Kickstart** for Anaconda (Fedora, Red Hat Enterprise Linux and derivatives such as Rocky and Alma), **preseed** for the Debian installer, and **autoinstall** for Ubuntu's Subiquity installer. SUSE has AutoYaST and its successor Agama, and Windows has unattend files, but the three above cover most Linux fleets.

The problem for an operator is both technical and organisational. Technically: which settings must be in the answer file and which can be left to later configuration management; how to select and wipe disks safely; how to handle the network before the installer has a network; how to deliver the file to the installer (on the media, over HTTP, via a kernel argument or DHCP); how to keep secrets out of it; and how to make the first boot hand over to cloud-init, Ansible or an agent. Organisationally: who owns the files, how changes are tested, and how a file is kept in step with the repository snapshot it installs from, so that a rebuild next month produces the machine that was intended.

Typical failure modes are well known. A Kickstart file with `clearpart --all` and no disk filter erases the wrong drive on a server with several disks, and does so unattended. A plaintext root password in a file served over HTTP to the whole network. An installer that stops at a prompt because one option is missing, leaving a machine waiting forever in a rack. A preseed file that is ignored because it was loaded too late, after the question was already asked. A `%post` script that fails halfway and the machine reboots into a half-configured state because nobody checked the log. A template that works in a virtual machine but not on hardware because the disk is named differently. And answer files that are copied between releases without checking that options were removed or renamed.

The scope of this topic is the structure and content of the three answer-file formats, how to deliver and validate them, how to design them so they are safe and maintainable, and where their job ends and the job of configuration management, image building and cloud-init begins.

## History and approaches

Automated installation arrived early in Unix. Sun's JumpStart and IBM's NIM let administrators describe an installation for a class of machine. For Linux, the Red Hat installer Anaconda gained **Kickstart** in the late 1990s; its answer file is a plain-text list of commands (`lang`, `keyboard`, `timezone`, `rootpw`, `part` or `autopart`, `clearpart`, `network`, `firewall`, `selinux`, `reboot`), followed by sections introduced by percent signs (`%packages`, `%pre`, `%post`, `%onerror`, `%addon`), each ended by `%end`. The format is simple to read and diff, and the Rocky Linux documentation gives annotated examples, including a walk-through of a complete file for a recent release [src: rocky-docs 4ebfb4bb0e500d99] and a general introduction to the way Kickstart is used with Rocky [src: rocky-docs 6a8318628fb01eed]. Fedora ships `system-config-kickstart` historically and Anaconda writes `/root/anaconda-ks.cfg` after every installation, which is a useful starting point: do one manual installation, then copy the generated file and clean it.

Debian took a different route. The Debian installer is built on **debconf**, the same configuration database used by packages. Every question the installer asks has a name and a default, and an administrator can supply **preseed** answers, in the format `d-i owner question-name type value`, so that the question never appears. The Debian Administrator's Handbook shows preseeding as the method for automated installations, including how a preseed file is located by the installer through a boot parameter, from the installation media, or over the wire, and why timing matters: a preseed file fetched after the network is configured cannot answer the questions about the network [src: debian-handbook 42cf01f9de7a9c41] and [src: debian-handbook c918eb3798cd4c0e]. The handbook also describes Simple-CDD, a tool that builds a custom installation CD with packages and a preseed file embedded [src: debian-handbook 349fb44b3fc62bcb]. Preseed can also run commands at fixed points (`d-i preseed/late_command`) and select package sets with `tasksel` and `pkgsel`.

Ubuntu used preseed for years, then introduced **autoinstall** with the Subiquity server installer in the 20.04 era. Its answer file is YAML placed under an `autoinstall:` key in a cloud-init `user-data` document, which ties the installer to cloud-init in two ways: the same mechanism that configures cloud instances delivers the answers, and after installation the installed system can be configured further by cloud-init. Keys such as `version`, `locale`, `keyboard`, `identity`, `ssh`, `storage` (with `layout` for common layouts or a full `config` list), `packages`, `late-commands`, `error-commands` and `user-data` cover the structure. The installer is told to look for the file with kernel arguments (`autoinstall ds=nocloud-net;s=http://server/`) or from media labelled `cidata`.

The three formats embody different philosophies. Kickstart is **imperative and sectioned**: commands run in order and shell scripts are first-class. Preseed is **declarative at the level of questions**: it answers whatever the installer would ask, so a new installer version can introduce a question that stops the install. Autoinstall is **declarative YAML** with a schema and a validation step, and defaults to interactive for any section the file omits unless the `interactive-sections` list is empty. Newer designs go further: **Agama** (SUSE's new installer) and Fedora's work on web-based interfaces use declarative profiles (JSON or Jsonnet), and image-based systems largely replace the installer with an image plus first-boot configuration, so the role of Kickstart shifts to the edges: it is still used to install bootc images from ISO, and the Red Hat documentation shows how to inject a Kickstart file into an ISO built with Image Builder, or to build a bootable ISO with a Kickstart file and custom partitioning with `bootc-image-builder` [src: rhel-10-docs 3d305f69482f4e9a] and [src: rhel-10-docs c41ca5459b5690a6].

## Current state

**Kickstart anatomy.** A modern file for an Enterprise Linux server looks like this:

```
text
lang en_US.UTF-8
keyboard us
timezone UTC --utc
network --bootproto=dhcp --hostname=node01.example.org --activate
rootpw --lock
user --name=ops --groups=wheel --iscrypted --password=$6$...
sshkey --username=ops "ssh-ed25519 AAAA... ops@example.org"
selinux --enforcing
firewall --enabled --ssh
services --enabled=sshd,chronyd
ignoredisk --only-use=vda
zerombr
clearpart --all --initlabel --drives=vda
autopart --type=lvm
reboot

%packages
@core
chrony
%end

%post --log=/root/ks-post.log
echo "built $(date -u +%FT%TZ)" > /etc/site-build
%end
```

Several points matter. `ignoredisk --only-use` and `clearpart --drives` limit destruction to the intended disk; without them an unattended installation wipes every disk it can see. `rootpw --lock` disables the root password, relying on key-based access for a named administrator, and `--iscrypted` stores a hash rather than plaintext (the hash is still a secret that grants access if the account allows password login, so prefer keys). The `%packages` section should be minimal: `@core` or `@minimal-environment` plus what the role needs, with unwanted defaults removed using a minus sign. The `%post` section runs in a chroot of the installed system by default (`--nochroot` accesses the installer environment) and should log, because the output otherwise disappears. `%pre` can detect hardware and write an include file for the disk layout, which is how one file can serve both virtual machines (`vda`) and servers (`sda` or NVMe). The `%onerror` section and `inst.sshd` and `inst.debug` boot arguments help diagnose failures. Validate files with `ksvalidator` from the `pykickstart` package before using them; it knows the command set of each release and warns about removed options.

**Delivery.** The file reaches Anaconda in several ways: embedded in the ISO (as `ks.cfg` in the root, or via `mkksiso` or `xorriso` modifications), on a second volume labelled `OEMDRV` (which Anaconda detects automatically), or by a kernel argument `inst.ks=http://server/ks/node.cfg`, `inst.ks=nfs:...` or `inst.ks=hd:LABEL=...`. Network installations set `inst.repo=` to a repository, which should be a snapshot path from the repository topics so that an installation is repeatable. The PXE and HTTP boot topic that follows describes how those arguments are provided to machines that boot over the network; the Red Hat documentation for automated installations describes starting a Kickstart installation over PXE or HTTP boot [src: rhel-10-docs 5bfa053150bd55b7]. Serve per-host files from a small web service that generates the file from a template and the host's identity (MAC address, serial number, DHCP-supplied name), but remember that the file travels in plaintext unless you use HTTPS with a trusted certificate (the installer's trust store is limited; `inst.noverifyssl` defeats the point).

**Debian preseed.** A preseed file consists of lines such as:

```
d-i debian-installer/locale string en_US.UTF-8
d-i keyboard-configuration/xkb-keymap select us
d-i netcfg/choose_interface select auto
d-i mirror/http/hostname string repo.example.org
d-i mirror/http/directory string /snapshots/2026-11-08/debian
d-i partman-auto/disk string /dev/vda
d-i partman-auto/method string lvm
d-i partman-auto/choose_recipe select atomic
d-i partman/confirm boolean true
d-i partman/confirm_nooverwrite boolean true
d-i passwd/root-login boolean false
d-i passwd/username string ops
d-i passwd/user-password-crypted password $6$...
d-i pkgsel/include string openssh-server chrony
d-i finish-install/reboot_in_progress note
d-i preseed/late_command string in-target sh -c 'echo built > /etc/site-build'
```

The file is loaded by `auto url=http://server/preseed.cfg` (or `preseed/url`), from the initrd, or from the media. If the network is needed to fetch it, the network questions are asked before it is read; to avoid that, set `netcfg/*` values as kernel arguments or embed the file in the initrd. The `debconf-get-selections --installer` command on an installed machine shows the answers that were given, which is the preseed equivalent of `anaconda-ks.cfg`. The handbook notes that a preseed file is written for one installer release and reasoning from an old file to a new release should be checked against the documented questions [src: debian-handbook 42cf01f9de7a9c41].

**Ubuntu autoinstall.** A minimal user-data is:

```
#cloud-config
autoinstall:
  version: 1
  locale: en_US.UTF-8
  keyboard: {layout: us}
  identity: {hostname: node01, username: ops, password: "$6$..."}
  ssh: {install-server: true, authorized-keys: ["ssh-ed25519 AAAA..."], allow-pw: false}
  storage: {layout: {name: lvm}}
  packages: [chrony]
  late-commands:
    - curtin in-target --target=/target -- systemctl enable chrony
```

Subiquity validates the file against a JSON schema and the installation log is in `/var/log/installer/`. The installer pauses for confirmation of destructive storage actions unless the kernel argument `autoinstall` is present, which is a deliberate safety feature: without it the machine waits. Storage can be given as a layout or as an explicit list of curtin actions (disks, partitions, formats, mounts) for control. The `user-data` key inside `autoinstall:` carries cloud-init configuration for the *installed* system, which links to the cloud-init topic later in this course.

**What belongs where.** Keep the answer file to what the installer is best at: disk layout, a minimal package set, a first administrative account (or none, with a bootstrap key), the network setting needed for first contact, the repository, and a hook that hands over to configuration management (a `%post` or `late-command` that installs the agent, registers the host with an activation key or pulls an Ansible playbook). Everything else (service configuration, application packages, users beyond the first) belongs to configuration management, because that code runs repeatedly and converges, while an installer file runs once. A symptom of overloading is an answer file with hundreds of lines of shell: move it to a role.

**Security.** The answer file is sensitive even without secrets because it reveals the repository, accounts and layout. Do not embed shared passwords; if a bootstrap credential is unavoidable, make it single-use and rotate it at first boot. Use SSH keys. Serve files over HTTPS where the installer supports it, restrict the web service to the provisioning network, log which host fetched which file, and prefer a per-host token over a predictable URL. Keep the installation media and the kernel and initrd that the installer boots under integrity control, since a modified installer defeats every later control (the signing and secure boot topics in other courses apply here). Enable SELinux or AppArmor and the firewall in the file, so the host is never installed in a weaker state than its steady state.

**Testing.** Treat the file like code. Validate syntax (`ksvalidator`, the schema check in Subiquity, `debconf-set-selections --checkonly` for preseed), then run the installation in a virtual machine in CI with a serial console, a timeout and an assertion script that logs in after the first boot and checks that services are running, SELinux is enforcing, the partition layout is as expected and the log of `%post` is clean. KVM and libvirt make this fast enough to run per commit; this is the basis of the lab for this topic. Test for hardware differences separately, since disk names, network interface names and boot mode (BIOS versus UEFI) differ.

## Assessment: the good, the bad and the ugly

**The good.** Answer files turn installation into a reviewable, versioned, repeatable action. Kickstart is expressive, widely documented and supported by every Red Hat family tool; preseed integrates with a mature question system; autoinstall's schema and cloud-init integration give a consistent path from installer to first boot. Installing from a snapshot repository and a pinned file makes a rebuild equal to the original. These files also work with virtual machines, bare metal and cloud-like private clouds.

**The bad.** The formats are not portable: moving a fleet from one distribution family to another means rewriting every file. They are tied to installer versions, and options are removed or renamed between releases. Debugging is slow because a failed install is seen on a console, and the logs may be on a machine that did not finish. Preseed's question-based model makes forward compatibility fragile. Autoinstall's behaviour when keys are omitted can surprise (silent interactive prompts). Disk handling differs per platform and per hardware vendor, so one file seldom covers everything. And an installer-based flow is slow compared with deploying an image, which is why many sites now install once to produce an image and then clone it.

**The ugly.** Unattended wipes of the wrong disk are the worst failure, and the usual causes are `clearpart --all` without a drive filter and a server with an unexpected attached disk (a SAN LUN, a USB drive left in a port). Another is a provisioning network on which anyone can request a build and receive an answer file with credentials. A third is drift between the answer file and the rest of the lifecycle: the file installs the release that was current when it was written, then a long chain of automation hides that, and no one remembers how to build a host without it.

**Assumptions.** Option names and installer behaviour are described as in recent Fedora, Enterprise Linux 9 and 10, Debian 12 and Ubuntu LTS releases. They differ between releases, so check the documentation for the release you install (to verify).

## Applications beyond this domain

The answer-file idea recurs wherever a program asks questions: Windows unattend.xml and autounattend for Windows installation, macOS MDM enrolment profiles, Android zero-touch provisioning, network equipment ZTP (zero-touch provisioning), and container build files, which are answers to the question "what is in this image". The principle of separating what the installer does once from what configuration management does continuously is the same as the separation between image build and runtime configuration. In virtualisation, cloud providers' "user data" fields serve the same purpose as an embedded answer file.

## Examples

**Example 1: a first Kickstart from a manual install.** Install a VM by hand with the desired partitioning, copy `/root/anaconda-ks.cfg`, remove interactive leftovers, add `ignoredisk`, `rootpw --lock`, the `sshkey` and a `%post` that logs, run `ksvalidator`, then boot a fresh VM with `inst.ks=` pointing at the file and confirm that it finishes without prompts.

**Example 2: one file for two disk layouts.** A `%pre` section checks whether `/dev/nvme0n1` exists and writes `/tmp/disk.ks` with either `ignoredisk --only-use=nvme0n1` or `ignoredisk --only-use=sda`, and the main file contains `%include /tmp/disk.ks`.

**Example 3: preseed for a snapshot mirror.** Set `mirror/http/hostname` and `mirror/http/directory` to a dated snapshot path, so that installing the same file next month gives the same package set, then add `d-i apt-setup/security_host` for the matching security snapshot.

**Example 4: autoinstall under test.** Build a cidata ISO with `user-data` and an empty `meta-data`, boot a VM from the Ubuntu server ISO with `autoinstall` on the kernel command line and the cidata ISO attached as a second drive, then wait for SSH on the first boot with a timeout.

**Example 5: a hand-over hook.** A `%post` section installs the configuration management agent, writes a one-time token to a file with mode 0600, enables a first-boot unit that registers the host and then deletes the token and the unit. The answer file never contains the long-term credential.

**Worked failure: the wiped data disk.** A rack of storage servers was reinstalled with a Kickstart that said `clearpart --all`. The installer saw the RAID volume holding data as a regular disk and erased it, since the file had not limited the destination. The repair of the process: `ignoredisk --only-use` with a serial-based `%pre` selector that refuses to proceed if more than one non-removable disk of the expected size exists, and a rule that data disks are disconnected or masked by the controller during reinstall.

## Related problems and ideas

This topic leads directly into **network boot** (the next topic), where the file is delivered to bare-metal machines, **cloud-init** (the first-boot configuration that follows installation), **image building** with Packer and Image Builder (which use answer files to build a template once), **configuration management** (which takes over after the first boot), and **bare-metal lifecycle tools** such as Foreman and MAAS that generate answer files per host. It also relates to **repository snapshots** (the source of packages), **secrets handling** (how bootstrap credentials are issued) and **disk partitioning and encryption**, since a Kickstart or autoinstall file is where LUKS and LVM policies are first expressed.

## Active research

The installer space is changing. Anaconda is being reworked with a web-based interface and new storage code; SUSE's Agama uses declarative profiles; Fedora and Red Hat have moved towards image mode where installation is image deployment with a short Kickstart for site settings, and the same documents show how to deploy bootc images over PXE and how to use bootable container ISO files [src: rhel-10-docs 5689d8f56ec0112e]. Ubuntu continues to evolve autoinstall's schema and cloud-init integration. Research and practice also look at attestation of what was installed, so that a booted host can prove which answer file and which package set it came from.

## Future direction

Expect answer files to become smaller and to be generated from a higher-level inventory, expect installers to be thin loaders of images with a declarative profile for the residual site configuration, and expect more validation tooling that tests an installation in CI by default. For the operator, the durable practice is to keep the installation minimal and safe, to test every change on a virtual machine, to install from a pinned repository and to hand off to configuration management as early as possible.
