# Moving a server to the next major release: Leapp, other upgrade tools and the case for rebuilding

## Define the problem

Every Linux distribution release has an end date. A server that was installed on version N has to reach version N+1 before the vendor stops issuing fixes, yet the machine usually carries years of local state: tuned configuration, third-party packages, data on its disks, and applications whose owners would prefer never to touch them. Two broad answers exist. The first is an **in-place upgrade**, where the installed system is converted step by step into the new release while keeping its identity, data and configuration. The second is a **rebuild** (also called a migration or replace): a fresh machine is provisioned on the new release, configuration and data are carried over deliberately, and the old machine is retired.

This topic belongs to a course on provisioning and lifecycle because the choice is a lifecycle decision, not just a command. For an enterprise distribution in the Red Hat family, the supported in-place tool is **Leapp**, driven through the `leapp` command and usually packaged as `leapp-upgrade`. Its documentation for the move from RHEL 9 to RHEL 10 describes a sequence of preparation, a read-only assessment, an upgrade phase and a set of post-upgrade tasks [src: rhel-10-docs 2d0d67804fb9da5d]. A community rebuild of the same family takes the opposite line: the Rocky Linux documentation states plainly that the project does not support in-place upgrades between major versions, and that the correct route is a reinstall of the next major version [src: rocky-docs 28dfab47a0481169]. A student therefore needs both skills: how to run and read a Leapp upgrade, and how to make a defensible choice between upgrading and rebuilding.

The typical failures are consistent across vendors. The upgrade is attempted without a restorable backup. The assessment is skipped, or run once and not re-run after changes. Third-party repositories and kernel modules block the transaction halfway. The upgrade finishes but the application does not start, because its runtime moved from one major version to another. Monitoring and watchdog agents interrupt the critical phase. Or the machine ends in a half-upgraded state that neither release supports, and the only way out is the backup that nobody tested.

## History and approaches

Upgrading between major releases was historically the weak spot of Red Hat style distributions. Debian and its derivatives made `apt full-upgrade` across releases a normal, documented practice early on, supported by release notes and a policy of maintaining upgrade paths between consecutive stable releases (to verify against current Debian release notes). Red Hat's family treated each major version as a new product: installing again was the supported route, and in-place conversion was limited to a few tools such as the old `preupgrade-assistant` and `redhat-upgrade-tool`, which handled only some paths.

Leapp is the framework that replaced them. It began as a general framework for moving workloads between machines and then became the engine of in-place upgrades from RHEL 7 to RHEL 8, then 8 to 9, and now 9 to 10. The design has a few ideas worth knowing, because they explain the behaviour you see. Work is split into **actors**, small units with declared inputs and outputs (messages called models), that are scheduled by the framework in ordered **phases**. Early phases only collect facts and make checks. Later phases download and test the new packages, prepare a special boot environment, perform the transaction while the system is not running its normal services, and finish with cleanup. Because actors only communicate through messages, the report that the user reads at the end of the assessment is simply the collected output of the checks, each with a title, severity and recommended remedy.

The same engine was reused by the community. AlmaLinux's ELevate project, built on Leapp with an additional set of actors for repositories and signing keys, supports upgrades between several derivatives of the family (for example from CentOS 7 to an Enterprise Linux 8, and onward); exact supported source and target pairs change from release to release, so they have to be read from the current project page (to verify). Other distributions chose their own tools: Ubuntu has `do-release-upgrade` that follows the long-term-support cadence, Fedora has the `dnf system-upgrade` plugin with a reboot into an offline upgrade, and SUSE offers migration through `zypper` and registration services (all to verify per release). Image-based systems such as those built with bootc replace the question altogether: the next release is a new image and the "upgrade" is a switch to it with a rollback ready, which is covered in another course of this path.

## Current state

**The documented RHEL 9 to RHEL 10 sequence.** Red Hat's guide is organised in a way that matches how a careful administrator works: planning, preparing, assessing, upgrading and then post-upgrade tasks. The preparation chapter lists prerequisites before any command is run: the system must meet the planning conditions, any previous major upgrade must have its post-upgrade tasks finished, the machine must be registered with the subscription service or a Satellite server, and an optional best-practice article is recommended reading [src: rhel-10-docs 2d0d67804fb9da5d]. The procedure then covers steps such as unmounting file systems that are not needed for the upgrade and removing them from `/etc/fstab` so that they do not slow the process or expose unrelated data to third-party tooling, enabling the base and application stream repositories for the architecture, and installing the upgrade packages [src: rhel-10-docs 2d0d67804fb9da5d].

**The pre-upgrade assessment.** The command `leapp preupgrade` collects data about the machine, evaluates upgradability and writes a report. The guide says that this phase does not change the configuration, but that it does use working space under `/var/lib/leapp`, typically up to about 4 GB, and warns that with too little space the report may be incomplete. Its advice is to give that directory enough room or move it to a separate partition [src: rhel-10-docs 045df04f551602ac]. The report is a text file (and a JSON file alongside it in the log directory), and the web console can display it with a remediation workflow. Problems carry a risk level of high, medium, low or info, and some are **inhibitors**, which block the upgrade until they are resolved [src: rhel-10-docs 178648262a2cd6e5]. The guide insists that the whole report be read even when it lists no inhibitors, because it also contains recommended actions that protect the upgraded system, and it states a limit worth memorising: the assessment cannot simulate the entire upgrade, so a clean report does not guarantee a clean upgrade [src: rhel-10-docs 045df04f551602ac].

A notable detail is the **answer file**. In some configurations the framework needs a yes or no decision from a human, for instance whether to remove a module that the new release no longer provides. The report then contains a row about missing required answers; the administrator confirms the default through a remediation or sets a different value with the `leapp answer` command [src: rhel-10-docs 178648262a2cd6e5]. This is deliberate: the upgrade phase runs without a person present and cannot stop to ask, so every decision has to be recorded before it starts. Report processing can also be scripted, which matters at fleet scale because results from many machines can be compared to find the common blockers.

**Channel options.** For subscriptions with extended support the assessment and upgrade take a channel option, and for specialised real-time deployments an additional repository is enabled by name; SAP environments are directed to a separate guide [src: rhel-10-docs 178648262a2cd6e5]. The general lesson is that special products carry special procedures, and the generic page is not always the correct one.

**The upgrade itself.** The upgrade chapter lists prerequisites that are about the surroundings of the machine as much as the machine: the preparation was completed including a full backup, the report was reviewed and every issue resolved, and antivirus software was temporarily disabled and health checks configured, including IPMI watchdogs, so that they do not interrupt the process. A warning in the same section explains why: an interruption during a critical phase can cost the system [src: rhel-10-docs 3985e968b6816417]. That connects directly to the previous topic, because a hardware watchdog that resets a machine it believes is hung will reset one that is merely busy replacing its operating system.

The backup options named in the guide are a full backup with Relax-and-Recover, snapshots by logical volume management or splitting a RAID mirror, a virtual machine snapshot, and snapshot and rollback boot entries managed with the Boom utility [src: rhel-10-docs 3985e968b6816417]. In practice the order of preference is: a hypervisor or storage snapshot taken while the machine is quiet (fastest to restore), then a logical volume snapshot with a tested rollback path, then a file-level backup that has been restored at least once somewhere.

**Mechanics (to verify per release).** After `leapp upgrade` completes its first stage, the system is rebooted, either by passing the reboot option or by hand, into a temporary environment that holds the new packages' transaction. The machine may appear to hang for a long time on the console during this stage; the correct response is to watch the console (a serial-over-LAN session or a virtual console) and leave it alone. A log under `/var/log/leapp` records the run, and after the final reboot the machine starts the new kernel. The post-upgrade tasks then include reviewing leftover packages from the old release, configuration files that were replaced or saved next to the originals, repositories that were disabled, and applications that need to be rebuilt or reconfigured.

**Rocky and other rebuild-only paths.** The Rocky Linux page begins by stating that there are no supported in-place major upgrades, and its method is a controlled fresh installation on the new release, which can also be used to rebuild the same release with the same package set. Its caveats are broadly applicable: packages are renamed or removed between releases, repositories must be verified for the new release, hardware requirements may have risen, and every error during the process should be noted [src: rocky-docs 28dfab47a0481169]. The practical consequence is an inventory step: record installed packages, enabled services, configuration paths, users and data locations before the old machine goes away.

**Debian-family and others.** On Debian the supported upgrade changes the repository definitions to the next release and runs a minimal upgrade followed by a full one, after reading the release notes for the target release (to verify). Ubuntu's tool performs the same stages with guard rails such as checks for third-party sources and a recovery shell if the session drops (to verify). The common structure across all of these is: prepare, back up, remove or disable what is unsupported, switch the package source, upgrade in two stages, reboot and clean up.

## Assessment: the good, the bad and the ugly

**The good.** Leapp turns a manual and risky process into a repeatable one with a read-only rehearsal. A fleet can run the assessment everywhere, aggregate the reports and discover that one unsupported kernel module accounts for most of the blockers. A tested in-place path saves a great deal of effort for pet servers whose rebuild would be expensive.

**The bad.** The assessment is not a simulation, so a clean pre-upgrade run can still be followed by a failed upgrade. Time and disk space needs are large and hard to predict (several gigabytes in `/var/lib/leapp` and in `/boot`, and a long reboot). Third-party repositories, custom kernel modules, unusual storage layouts such as multipath or encrypted root, and software that is tied to a major version of a language runtime are the usual causes of trouble. Supported paths are narrow: the guide gives specific minor releases for source and target (9.8 to 10.2 in the version cited), so a machine that is two minor releases behind has to be updated first [src: rhel-10-docs 3985e968b6816417].

**The ugly.** A half-finished upgrade is the worst state: the machine has packages from two releases, no vendor supports it, and tools to repair it may be missing. Nothing in the process helps if there is no verified backup or snapshot. And a quiet failure is possible too: the upgrade finishes, the services start, and an application silently runs on a different library version with different behaviour. For this reason a test environment that clones the production machine (restored from the same backup) should perform the upgrade first, and the application's own tests should run against it.

**Decision criteria.** Upgrade in place when the machine is stateful and unique, the application is certified for the target release, a snapshot exists, and a maintenance window is available. Rebuild when the machine is stateless or can be made so, when it is part of a fleet built from code, when its drift is high or its history is unknown, or when the distribution does not support in-place paths. Rebuilding has a further advantage: the new machine is created by the same pipeline that provisions all others (Kickstart or cloud-init, then configuration management), so the upgrade exercises and improves that pipeline instead of one-off knowledge.

**Assumptions.** The command names and file locations follow the cited vendor guide for RHEL 9 to RHEL 10 and the general design of Leapp; the exact flags, log names and supported source and target versions change between releases and must be taken from the guide of the release in use (to verify). Statements on Debian, Ubuntu, Fedora, SUSE and AlmaLinux ELevate are summaries from public project documentation and should be checked before use [web: almalinux.org] [web: ubuntu.com] [web: debian.org].

## Applications beyond this domain

The same pattern, assess then rehearse then switch with a way back, shows up in database major-version upgrades (a dump and restore or a link-based in-place tool with a check mode), in Kubernetes control plane upgrades (one minor version at a time, with a plan step), in firmware updates with a staged slot and rollback, and in Windows domain controller upgrades, where a schema preparation step runs before the first new-generation controller joins and is available as a separate command when the installing account lacks the rights [src: ms-learn-adds abad2d798bfa59af]. The common thread is the dependency order: some component must be prepared first and the reversibility of each step must be known.

## Examples

**Example 1: a rehearsal on a clone.** Restore last night's backup of a production host into a test virtual machine on an isolated network, install the upgrade package, run `leapp preupgrade`, read `/var/log/leapp/leapp-report.txt`, fix each inhibitor, run it again until clean, then run the real upgrade on the clone and test the application. The time taken on the clone sets the window for production.

**Example 2: scripted triage across a fleet.** A script runs the assessment through Ansible on each host, collects the JSON report, and builds a table of inhibitor titles by number of hosts. The top three titles are the work plan: for example removal of an unsupported kernel module or a missing repository.

**Example 3: preparing the host.** Comment out data-only mounts in `/etc/fstab` as the guide suggests, check `df -h /var/lib/leapp /boot`, enable the required repositories, stop or exclude the watchdog and antivirus agents, take an LVM snapshot, then proceed [src: rhel-10-docs 2d0d67804fb9da5d] and [src: rhel-10-docs 3985e968b6816417].

**Example 4: the answer file.** After a preupgrade run, the report shows a question about removing a deprecated module. The administrator runs `leapp answer --section <section>.<question>=True` for that item, re-runs the assessment, and sees the row disappear [src: rhel-10-docs 178648262a2cd6e5].

**Example 5: the rebuild alternative.** On a Rocky host the team records installed packages (`rpm -qa --qf '%{NAME}\n' | sort`), enabled units, configuration under `/etc` that differs from package defaults (`rpm -Va` for files with changed contents), and users and data paths, then provisions the next major release with Kickstart and applies the recorded configuration through Ansible [src: rocky-docs 28dfab47a0481169].

**Worked failure: the watchdog.** A host with an IPMI hardware watchdog was upgraded without disabling it. During the long offline stage the watchdog daemon was not serving its heartbeat and the controller reset the machine midway through the package transaction. The host did not boot; recovery was a restore from snapshot, followed by a repeat with the watchdog disabled, as the guide's prerequisites say [src: rhel-10-docs 3985e968b6816417].

## Related problems and ideas

This topic follows the earlier ones in the course: the **Kickstart and cloud-init** pipelines that make a rebuild cheap, **Packer images** that carry the new release, and **bare-metal platforms** that can redeploy a host. It leads to **drift detection and secure wipe**, because a rebuild ends with the sanitised retirement of the old disks, and to **patch rings** in the software-delivery course, since an upgrade campaign is rolled out in waves exactly like a patch. It also touches **backup and restore**, which is the safety net of every method above, and **repository management**, because the upgrade only works when repositories for the target release are mirrored and pinned.

## Active research

Open work includes better prediction of upgrade failures from the assessment, container-based and snapshot-based rehearsal tooling, upgrade paths across more than one major version, and image-based upgrades with automatic rollback. Distribution projects also publish lists of known inhibitors and "to-do" actors, which are a good source of information about what the tool cannot yet handle (to verify).

## Future direction

The trend is away from mutating machines in place and toward replacing images: the next release is built once, tested centrally, and deployed to many machines, with in-place tools kept for stateful and legacy systems. Expect in-place upgrades to remain necessary for years, but expect the assessment and reporting parts to become more automated and the policy to be to rebuild whenever the host can be made stateless. For the operator the lasting skill is the discipline underneath both: inventory, backup, rehearsal, a controlled window and a verified way back.
