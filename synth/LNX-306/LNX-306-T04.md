# Packer: building machine images from code

## Define the problem

The earlier topics of this course install a machine and configure its first boot. A fleet that is built over and over needs one more link: a reusable *template* or *image*, built once from a definition, tested, versioned and then cloned or launched many times. Installing from scratch with Kickstart for every instance takes tens of minutes and fetches hundreds of packages each time; launching from a pre-built image takes seconds and gives every instance the same bytes. The difficulty is to produce that image in a way that is automated and repeatable rather than by hand. A template created by an administrator who installed a VM, tweaked it, and clicked "convert to template" cannot be rebuilt when the base release changes, and nobody can say what is in it.

**Packer**, from HashiCorp, is the best-known tool for this. It reads a declarative configuration, starts a temporary machine on a chosen platform, installs the operating system (using the answer files from the first topic) or starts from an existing image, runs *provisioners* (shell scripts, Ansible, file copies) over SSH, and then captures the result as an image for that platform: a VMware template, a QEMU qcow2 disk, an Amazon Machine Image, an Azure managed image, a Google Cloud image, an OpenStack image and many others. The same template can emit several formats in one run. The Rocky Linux documentation on automatic template creation introduces Packer as an open-source imaging tool: one configuration yields virtual machine images that already contain an operating system and extra software, whether the target is a private virtualisation platform or a public cloud [src: rocky-docs 169d120a5eebafc3].

The topic is about the practice: how to organise a template, how to make builds repeatable and secure, how to test the result, how to version and publish images, and how Packer relates to the alternatives (Image Builder in the packaging course, `virt-customize`, kiwi, mkosi, `docker build` for containers). The typical failure modes are these: an image that cannot be rebuilt because it depends on a download that has changed; credentials baked into a template (a build account's password, an SSH key, a cloud token) so that every instance has the same backdoor; an image that boots but carries the previous build's machine id, SSH host keys or DHCP leases; provisioners that succeed on the first run and fail when the mirror changes; a pipeline that publishes images without any test; images that accumulate forever because nobody retires them; and a template written for one hypervisor that is impossible to port because it uses its own tools throughout.

## History and approaches

Mitchell Hashimoto released Packer in 2013 as an answer to the "golden image" problem, with a plugin architecture: a **builder** (platform-specific: `amazon-ebs`, `qemu`, `virtualbox-iso`, `vsphere-iso`, `proxmox-iso` and others) creates the temporary machine and captures the image; a **communicator** (SSH or WinRM) connects to it; **provisioners** configure it; **post-processors** transform the output (compress it, convert it to a Vagrant box, record a manifest, upload it). Early configurations were JSON, as the Rocky guide's examples show, with `builders`, `provisioners` and variables as top-level keys [src: rocky-docs 924e2c577402149d] and [src: rocky-docs 1752bb891b36d8a4]. Since the 1.5 release in 2020, the preferred format is **HCL2**, the language shared with Terraform, with blocks (`source`, `build`, `variable`, `locals`, `packer`), functions, `for_each`-like dynamic blocks and typed variables. In the same period plugins moved out of the main binary: `packer init` downloads those declared in a `required_plugins` block, which pins versions and makes builds reproducible.

Packer is neither the only nor the first approach. **Capture after manual install** (clone a VM) is the baseline Packer replaces. **Cloud-native image builders** (AWS EC2 Image Builder, Azure Image Builder) offer managed pipelines tied to one provider. **Distribution builders** (osbuild and Image Builder for Red Hat, kiwi for SUSE, debos and live-build for Debian, mkosi for systemd-based distributions) assemble an image from packages without booting an installer, which is faster and more reproducible but is specific to a distribution family; the packaging course covers Image Builder. **Container builds** (`Dockerfile`, `Containerfile`) are the same idea for application images, and bootc extends it to the operating system. Packer's niche is the cross-platform, boot-the-real-installer approach: it produces what the platform's own installer produces, with whatever provisioners you need, on any hypervisor.

A licence note belongs here. Packer was released under the Mozilla Public License 2.0, a fact the Rocky guide records [src: rocky-docs 169d120a5eebafc3]. In 2023 HashiCorp moved its main products, including Packer and Terraform, to the Business Source License 1.1, which restricts use in competing commercial offerings. The community responded with a fork of Terraform, OpenTofu (the next-but-one topic), and discussions of forks for other tools; whether and how the licence affects your use is a question for your organisation's counsel, and the details of the current licence and of any forks should be checked (to verify). The templates described here are plain HCL and the concepts transfer.

## Current state

**Anatomy of an HCL2 template.** A file `el9.pkr.hcl` has the structure:

```
packer {
  required_plugins {
    qemu = { version = ">= 1.1.0", source = "github.com/hashicorp/qemu" }
  }
}

variable "iso_url"      { type = string }
variable "iso_checksum" { type = string }
variable "ssh_password" { type = string, sensitive = true }

source "qemu" "el9" {
  iso_url          = var.iso_url
  iso_checksum     = var.iso_checksum
  accelerator      = "kvm"
  headless         = true
  disk_size        = "20G"
  format           = "qcow2"
  http_directory   = "http"
  boot_command     = local.kickstart_boot
  ssh_username     = "packer"
  ssh_password     = var.ssh_password
  ssh_timeout      = "30m"
  shutdown_command = "sudo shutdown -P now"
}

build {
  sources = ["source.qemu.el9"]
  provisioner "shell" { script = "scripts/baseline.sh" }
  provisioner "shell" { script = "scripts/cleanup.sh" }
  post-processor "manifest" { output = "manifest.json" }
}
```

The elements map directly to the concepts of this course. `http_directory` serves a directory (containing the Kickstart or preseed file from the first topic) from a temporary web server that Packer starts, and `{{ .HTTPIP }}` and `{{ .HTTPPort }}` are filled in at run time. `boot_command` (here a local value that holds the keystrokes) types into the virtual console: the tab key to edit the boot entry, the text-mode flag and the `inst.ks=` argument built from the two HTTP placeholders, which tells the installer where its answer file is, the same mechanism that network boot uses. The installer finishes, reboots into the installed system, and Packer connects with the credentials that the answer file created. That build account is temporary: its password is a build-time secret supplied as a sensitive variable, and the cleanup step must remove the account or lock the password before capture.

**Commands.** `packer init .` installs plugins; `packer fmt` formats; `packer validate -var-file=el9.pkrvars.hcl .` checks syntax and references without building; `packer build -var-file=... .` runs the build; `PACKER_LOG=1` produces a detailed log; `-on-error=ask` pauses after a failure so that you can inspect the temporary machine instead of losing it. A build on a laptop with KVM acceleration can take ten to twenty minutes for a minimal Enterprise Linux image. Run builds headless with the VNC or serial console available for debugging.

**Provisioners.** The `shell` provisioner runs scripts; the `ansible` provisioner (and `ansible-local`) runs a playbook against the temporary machine, which lets you reuse the same roles that configure running servers; the `file` provisioner copies content. The Rocky guide's provisioner example installs requirements and cleans up after the installation, noting that cleaning the VM (removing SSH keys, clearing history) and adding extra packages is part of the job [src: rocky-docs 924e2c577402149d]. A good rule is to keep provisioners few and idempotent, move real configuration into an Ansible role or into the image build itself, and reserve shell scripts for the baseline and the clean-up.

**Clean-up (generalisation).** The last provisioner makes the image safe to clone. For a Linux image typically: remove the build user or lock its password and remove its authorized keys; truncate `/etc/machine-id` (so it regenerates), delete SSH host keys (`/etc/ssh/ssh_host_*`; sshd generates new ones on first boot), clear `/var/lib/dhclient`, NetworkManager state and persistent network rules, run `cloud-init clean --logs --seed` (see the previous topic), empty `/tmp`, `/var/tmp` and logs, clear shell history, run `dnf clean all` or `apt-get clean`, zero free space or use `fstrim` to improve compression, and sync. If you skip these steps, every instance shares an identity, which defeats security and may break DHCP, licensing agents and monitoring registration.

**Secrets and the build account.** Build-time secrets (the temporary password, a token to upload the image, a registry credential) must not appear in logs or in the image. Mark variables `sensitive = true`, pass them through environment variables (`PKR_VAR_ssh_password`) or a secrets manager and not in the repository, use SSH keys instead of passwords where possible (`ssh_private_key_file` with a temporary key generated for the run), and run builds in an isolated network. Check the final image with a secret scanner and make the clean-up step part of the tests.

**Pinning and reproducibility.** An image build depends on its inputs: the installation ISO (verify with `iso_checksum`; never `none`), the package repositories (use a dated snapshot, as in the packaging course, through the Kickstart's `repo` and `url` lines, so that a rebuild next month yields the same packages), plugin versions (in `required_plugins`), provisioner scripts and any downloaded files (verify checksums). Record the inputs in the image's metadata: the manifest post-processor writes build UUID, artifact IDs and custom data, and you can add the Git commit and snapshot date as image tags. Full bit-for-bit reproducibility is not realistic with Packer (timestamps, random identifiers), but *content* reproducibility, the same package set from the same inputs, is.

**Testing images.** Treat the image as software. After the build, boot a copy in a test environment and run assertions: services enabled, ports closed, kernel version, package inventory against an expected list, no leftover accounts (`getent passwd packer` empty), SSH host keys regenerated on second boot, and the compliance profile passes (`oscap` against the benchmark). Tools such as Goss, InSpec, ServerSpec and `testinfra` express these checks; a simple shell or Python script is enough to start. Test the cloud-init path by booting twice with different seeds and confirming that each instance gets distinct host keys and machine ids. Only then publish.

**Publishing, versioning and retirement.** Name images with a version and date (`el9-base-2026.11.08`), store them where the platform needs them (a vSphere content library, a Glance image, a cloud image gallery, an artefact repository for qcow2 files), keep the manifest and the checksums beside them, tag them with the source commit, and retire old images on a schedule so that nobody launches a year-old base. HCP Packer, the HashiCorp registry service, tracks image metadata and "channels" (such as `latest` and `production`) to which images are assigned, which is the same promotion idea as repository snapshots (to verify its current availability and terms). Many sites build the same with a CI job and a small database or file.

**Pipeline.** A mature pipeline runs on a schedule (weekly, to include security updates) and on change: `packer validate`, `packer build` on a build host with KVM or in the target cloud, tests, publication, notification, and cleanup of failed temporary resources (orphaned VMs and disks on clouds cost money and may hold data). Keep the template in Git, pin plugin versions and review changes like code. Build agents need credentials for the cloud or hypervisor; use short-lived credentials, a dedicated service account with only image permissions, and a separate network.

**Windows and other targets.** Packer builds Windows images with WinRM or OpenSSH as the communicator and `autounattend.xml` as the answer file, plus a sysprep step. The structure is the same; the details are in the vendor documentation.

**Alternatives in practice.** For Enterprise Linux and Fedora, Image Builder may be simpler and faster, because it does not boot an installer, and the packaging course shows it. For one-off modifications of an existing cloud image, `virt-customize` and `virt-sysprep` (libguestfs) edit the disk offline; for example, the KubeVirt user guide shows these tools used to inspect and modify disk images [src: kubevirt-user-guide a7e7278e900479c3]. For container workloads, build container images and let the platform's nodes stay generic. Use Packer where you need the real installer path on a particular hypervisor or cloud, or need the same procedure across several platforms.

## Assessment: the good, the bad and the ugly

**The good.** Packer gives a single, versioned definition for images on many platforms, reuses the answer files and provisioning code you already have, and makes the build a repeatable job. HCL2 is readable and testable (`validate`). Images speed up provisioning and reduce variation. The plugin ecosystem is wide and the community knowledge is deep.

**The bad.** Builds are slow because a full installer runs. Typed `boot_command` sequences are fragile (timing, firmware differences, a changed installer menu breaks them). Debugging is on a console. Reproducibility is partial. Licence and governance changes at the vendor level add uncertainty. Each platform's builder has its own options and quirks, so a "portable" template often grows platform-specific branches. And the model of provisioning a running VM over SSH invites unreviewed shell sprawl.

**The ugly.** Images with the build user and password still present; templates that download "latest" artefacts with no checksum; CI logs that print secrets; pipelines that leave temporary resources running up a cloud bill; and an image catalogue with hundreds of unlabelled templates. The worst is trust: an image that nobody can rebuild is an artefact you must trust blindly, and a compromised build host can poison every instance launched from its output.

**Assumptions.** Plugin names, option names and licence terms reflect the documents cited and the author's knowledge of recent releases and change; confirm against the Packer and plugin versions you run (to verify).

## Applications beyond this domain

The same idea (define, build, test, version and publish an artefact from code) is the base of container image pipelines, of infrastructure modules, of firmware build systems and of golden AMI programmes in cloud security teams. Compliance teams use Packer to create hardened bases that every project inherits. Education labs use it to generate classroom VMs, and CI systems use it to produce build agents with a fixed toolchain. Security teams scan the resulting images and sign them with attestations (the Docker documentation's policy templates for image attestation and provenance show the same ideas for container images [src: docker-docs e41e244b2fe938c8]).

## Examples

**Example 1: a first local build.** Install Packer and QEMU, write the template above with a minimal Kickstart in `http/ks.cfg`, run `packer init`, `validate`, then `PACKER_LOG=1 packer build -var iso_url=... -var iso_checksum=sha256:... .`. The output is `output-el9/packer-el9`, a qcow2 file that boots in libvirt.

**Example 2: a clean-up script.** `cleanup.sh` locks and removes the build user, truncates the machine id, removes SSH host keys, runs `cloud-init clean --logs --seed`, cleans the package cache and trims free space, then syncs; the final build log shows each step.

**Example 3: an Ansible provisioner.** Replace the baseline script with `provisioner "ansible" { playbook_file = "ansible/baseline.yml" }` so the image and running servers use the same hardening role, and test the role with the same CI.

**Example 4: a pinned build.** The variables file names a dated repository snapshot; the Kickstart's `url`/`repo` lines point to it; the manifest records the snapshot date and commit as custom data and the publishing job copies them to image tags.

**Example 5: an image test.** Boot the qcow2 with a NoCloud seed, wait for SSH, then run a script that checks `uname -r`, `systemctl is-enabled chronyd`, `ss -tlnp` (only SSH), `getent passwd packer` (absent) and a hash comparison of `/etc/ssh/ssh_host_ed25519_key` between two boots (they must differ).

**Worked failure: the shared host keys.** A team captured their images without removing SSH host keys. Every instance of the image presented the same host key, so a scanner flagged duplicates and host-key verification no longer distinguished machines. The fix was the clean-up script, a test that boots two instances and compares fingerprints, and a rebuild of every image in the catalogue.

## Related problems and ideas

This topic builds on **unattended installation** (the answer file Packer serves), **cloud-init** (the first-boot step the image must be prepared for), **repository snapshots** (inputs) and **Image Builder** (the alternative). ## Active research

Open directions include faster, more reproducible image creation without running an installer (image composition from packages, as osbuild and mkosi do), signing and attestation of images with build provenance, better test frameworks for machines, and the role of container-native OS images, which turn many Packer use cases into container builds. Industry discussion on licences and forks continues to affect tool choice.

## Future direction

Expect image building to be a routine CI job with signed outputs, expect more of the work to move to declarative composition tools, and expect Packer-style full-boot builds to remain for platforms and operating systems that need them. For the operator, the lasting habits are to pin inputs, clean before capture, test every image, version and retire images, and keep build secrets away from the image and the logs.
