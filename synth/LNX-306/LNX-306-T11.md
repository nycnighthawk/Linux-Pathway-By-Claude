# Working with real BMC and platform firmware: updates, trust and what cannot be simulated

## Define the problem

The earlier topics let a student practise out-of-band management with emulators and mock services. That is enough to learn the protocols and to test automation logic, but it hides the part of the job that makes physical servers different: the firmware is real, it is vendor-specific, it can be damaged by a bad update, and it sits below every control that the operating system provides. This topic covers what changes when the target is an actual board: how BMC firmware and the other platform firmware (system firmware, option ROMs of network and storage adapters, drive firmware) are identified, updated and verified, how trust in that firmware is established, and what risks and procedures follow.

The problem has a human side as well as a technical one. A firmware update is a change that cannot always be undone from the network, since a BMC that fails to start is also the tool that would have been used to repair it. A lab can hide this; a data centre cannot. The topic is therefore marked as hardware-dependent (depth 1): the aim is to know what to do and what to ask, and to practise on a safe test machine under supervision, not to learn flashing by trial.

The failure modes are concrete. An update is interrupted by a power loss or a reboot and leaves the BMC unresponsive. A firmware image from the wrong vendor or model is applied. An update is applied to a whole rack at once and a regression disables every management network port. Settings are lost because the update reset the BMC to defaults, and the BMC then comes back on the network with a default password. Or no one updates the firmware for years and a known vulnerability is exploited through the management port.

## History and approaches

Early servers had firmware on programmable memory chips that required physical access or a special boot disk to update. As BMCs spread, vendors added network update paths so that fleets could be maintained from a console: a web page upload, a vendor command-line tool, or a standard remote interface. The Rocky Linux IPMI guide names the per-vendor tools in common use: Dell's `racadm` and the repository manager, HPE's `ilorest` and its smart update manager, Supermicro's update manager and web interface, and Lenovo's `OneCLI` and XClarity [src: rocky-docs a5fa6b296f093991]. The Redfish standard later gave a uniform path through its update service, with a simple update action that takes an image location and a firmware inventory that lists installed versions, though vendors implement the details differently (to verify per vendor).

Two design families matter for safety. **Dual-image BMCs** keep two copies of the firmware and boot the new one on a trial basis, falling back to the old if it fails; this makes updates recoverable but is not universal, and some boards require an external programmer for recovery. **Single-image BMCs** write over the running code and depend on the update completing. Which family a model belongs to must be known before the work begins.

For system firmware (UEFI, formerly BIOS) the Linux ecosystem added a vendor-neutral channel: `fwupd` obtains firmware descriptions and images from a community-run distribution service (the Linux Vendor Firmware Service) and applies them through UEFI capsule updates, with a boot step that applies the capsule before the operating system starts. The Rocky QA test case describes the arrangement: install `fwupd` (plus the EFI companion package on the newest release) on a machine with Secure Boot enabled and check that the system briefly enters the firmware updater on the next boot before continuing normally [src: rocky-docs 1e31a075658e6714] and [src: rocky-docs 839262015d33d8be]. This route covers a growing set of vendors' devices, but servers still commonly use their vendor's own bundles and tools (to verify per model).

The open firmware approach is **OpenBMC**, discussed earlier, in which the BMC runs community-built Linux. It has a standard way to upload and activate images and supports signed images where a platform enables it. QEMU can emulate several of the system-on-chip families used in these BMCs and can start an OpenBMC image directly with a kernel and device tree, or from a firmware image, which allows testing of a build before it reaches a board [src: qemu-docs c546a50373a2929b]. A further family of QEMU boards models a platform **root of trust** processor, a small separate microcontroller that checks the BMC's own firmware before it is allowed to run, and QEMU can start such a machine from a Zephyr build to exercise that code [src: qemu-docs 2f3c672254b0a62d].

## Current state

**Identify before you update.** The first step is an inventory: which BMC model, which firmware version, what the update path is, and what the vendor says about the target version. In-band, the kernel's IPMI interface shows whether the BMC is present: the device node `/dev/ipmi0` exists after the right modules load, and kernel messages from the IPMI driver confirm the system interface was found [src: rocky-docs 08a570dff7e1867f]. Out-of-band, `ipmitool mc info` prints the firmware revision and manufacturer, and a Redfish query of the manager and the update service's inventory lists the versions for the BMC, BIOS and other devices (to verify per vendor). Record the result in the asset inventory, keyed by the serial number, so that campaigns can be planned by group.

**The vendor guidance, summarised.** The Rocky guide's warning is blunt: an interrupted update can leave the BMC unresponsive, in the worst case requiring replacement of the board. Its rules are general and good. Take firmware only from the server vendor's support site. Read the release notes first. Ensure stable power, with a UPS if there is one. Do not reboot or power off during the update. Back up the BMC configuration beforehand where the vendor tool allows [src: rocky-docs a5fa6b296f093991]. To these an operator adds: verify the checksum or signature of the file against the vendor's published value; confirm the model compatibility list; and confirm that the update order is respected where the vendor prescribes one (some require an intermediate version for old releases) (to verify per vendor).

**A change procedure for a fleet.** A sound campaign has stages. (1) *Classify*: group machines by model and current version. (2) *Test*: run the update on a sacrificial machine of each model, with console access (serial-over-LAN and a remote KVM) and a known recovery procedure, and confirm that the BMC settings, accounts, network, certificates and sensors survive or are re-applied. (3) *Pilot*: update a few production machines of low importance, wait, and review the logs. (4) *Waves*: widen in controlled steps, with a health check at the end of each (BMC reachable, version correct, event log clean, power control works). (5) *Stop rules*: a failure of any machine pauses the campaign. (6) *Record*: update the inventory with the new versions and the evidence.

The ordering inside one machine matters too. Typical sequences update the BMC first (so that later steps can be driven out of band), then the system firmware, then adapter firmware, then drive firmware, with the host's operating system rebooted as needed. Check the vendor's matrix for dependencies (to verify per platform). Do not combine a BMC update with other maintenance on the same host.

**After the update.** Check that the management network settings are the ones you configured and not defaults. Confirm that accounts and passwords are as expected: some updates reset the BMC to factory settings (an option often labelled "preserve configuration"), which leaves a default account on the management network until fixed. Re-run the security check of the earlier topic (disabled cipher suite 0, TLS certificate valid, unused services off). Confirm the time source and log forwarding.

**Trust in firmware.** Firmware is the base of the trust chain, and an attacker who can change it persists below the operating system. The NIST catalogue treats this as its own control enhancement: protect the integrity of boot firmware by verifying the integrity and authenticity of every update before it is applied and by stopping unauthorised processes from modifying it, because unauthorised changes to boot firmware may indicate a sophisticated attack and may result in permanent denial of service or persistent malicious code [src: nist-sp800-53 ca35cc3500f82996]. In practice, this means: use only signed images, so that the BMC and the platform firmware reject modified files; keep the signing keys under the vendor's control or, with open firmware, under your own protected process; enable the platform's measured and verified boot features where they exist (to verify per platform); and restrict who can start an update, since update capability is a high-privilege role in both IPMI and Redfish.

At the operating-system boundary, **UEFI Secure Boot** extends the chain: the Rocky documentation explains that without verification the firmware would execute any EFI program it finds, and that with Secure Boot the firmware runs only programs signed by trusted certificates, which establishes the start of a trust chain through the boot loader to the kernel [src: rocky-docs 757ee3816a2ef10f]. A compliance rule checks it with the `mokutil` command (`mokutil --sb-state`), noting that Secure Boot protects against rootkits and bootkits that act before the usual defences start [src: compliance-as-code 6239848544c7f6c8]. A fleet should treat the Secure Boot state, the key database and the firmware version as part of a host's recorded baseline, and detect drift (as in the previous topics).

**What simulation cannot teach.** Emulators reproduce protocol behaviour but not these things: the time a real update takes (often tens of minutes, with the BMC unreachable for part of it), the recovery paths when it fails, the vendor-specific update formats and tools, the effect of "preserve configuration" choices, hardware watchdog behaviour, thermal and fan control during a BMC restart (many servers run fans at full speed while the BMC is down), and the physical procedures (recovery jumpers, external programmers, replacement boards). The emulator is the place to write and test the automation; the test machine is the place to find out how the vendor really behaves.

## Assessment: the good, the bad and the ugly

**The good.** Firmware updates close real vulnerabilities, fix sensor and power-control bugs, and add features such as stronger authentication and Redfish coverage. Dual-image designs, signed updates and fleet tools have made updates much safer than they were.

**The bad.** The ecosystem is fragmented: every vendor has its own tools, bundles, ordering rules and quirks, and the metadata that would let a fleet tool plan updates automatically is incomplete. Release notes are often thin about security fixes. Updates need maintenance windows and sometimes reboots, which fight with availability goals.

**The ugly.** A bricked BMC on a remote machine with no alternative console; a rack updated at once because the pilot was skipped; an update that restored default credentials on an exposed management network; firmware images fetched from a mirror whose checksum was never verified. The sobering point of the vendor guidance is that this work has a physical cost when it goes wrong, which is why the stop rules and the sacrificial test machine are not optional.

**Assumptions.** The vendor tool names come from the cited Rocky guide; behaviours such as dual-image fallback, preserve-configuration options, update ordering and Redfish update-service details differ by vendor and model and are marked (to verify). Statements about fwupd, the Linux Vendor Firmware Service and DMTF's update service summarise public documentation [web: fwupd.org] [web: dmtf.org] [web: openbmc.org].

## Applications beyond this domain

Staged firmware rollout with a recovery path is the same problem as updating network switches, storage array controllers, drives, GPUs and DPUs, and field devices of all kinds. The trust-chain thinking (signed update, verified boot, hardware root of trust, measured state) is the model for phones, laptops and vehicle controllers. The inventory-driven campaign with stop rules is a general change-management pattern used for operating-system patching, as in the software-delivery course.

## Examples

**Example 1: inventory by script.** A job reads each host's BMC address from the platform, calls the Redfish manager and firmware inventory endpoints, and writes model, BMC version and BIOS version to a table; hosts are grouped to plan waves.

**Example 2: a pre-update checklist.** Release notes read; checksum verified against the vendor page; model on the compatibility list; configuration backed up; UPS healthy; serial-over-LAN session open; recovery contact and procedure confirmed; window agreed [src: rocky-docs a5fa6b296f093991].

**Example 3: a post-update check.** Version equals target; BMC network is the configured static address; accounts are the expected ones and the default account is absent; cipher suite 0 is disabled; event log has no new errors; power status and a sensor read work; the host boots and the operating system sees `/dev/ipmi0` [src: rocky-docs 08a570dff7e1867f].

**Example 4: testing an OpenBMC build in QEMU.** Start an Aspeed board model with the built kernel and device tree, wait for the web service, and run the Redfish tests from the earlier lab against it; only then flash a sacrificial board [src: qemu-docs c546a50373a2929b].

**Example 5: checking Secure Boot and the baseline.** `mokutil --sb-state` on each host and `fwupdmgr get-devices` (where fwupd is used) are collected into the baseline; a change in either is drift [src: compliance-as-code 6239848544c7f6c8].

**Worked failure: the whole rack.** A team updated BMC firmware on forty identical servers at once after a successful test on one. The new version reset the management network to DHCP; the management VLAN had no DHCP server, so all forty BMCs fell off the network. The servers kept running, but remote control was lost until staff reached each console and re-entered the settings by hand. The campaign procedure above (pilot of a few machines, waves, a check at the end of each, and a stop rule) would have limited the damage to the pilot group.

## Related problems and ideas

This topic completes the out-of-band thread: **BMC, IPMI and Redfish** gave the protocols, **bare-metal platforms** hold the inventory and lifecycle states, **drift detection** treats firmware versions as baseline items, and **secure wipe** uses drive firmware features that must themselves be current. It connects to the **security hardening** course (boot chain, Secure Boot, measured boot) and to **patch rings** in software delivery.

## Active research

Work in progress includes hardware roots of trust that verify BMC firmware before execution, remote attestation of firmware state, standard formats for firmware bills of materials, signed and reproducible OpenBMC builds, and recovery mechanisms that do not require physical access. The Aspeed root-of-trust boards that QEMU models are part of this direction [src: qemu-docs 2f3c672254b0a62d].

## Future direction

Expect update services to become uniform through Redfish and fwupd-like catalogues, expect signed firmware and attestation to be required by procurement, and expect the BMC to be patched like any other managed endpoint, in rings, with automated post-update checks. The skills that persist are careful inventory, staged rollout with stop rules, verification of what you install, and respect for the fact that this layer fails differently from software.
