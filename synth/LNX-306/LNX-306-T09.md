# The two ends of a server's life: detecting drift in service and sanitising storage at retirement

## Define the problem

A provisioned server starts life as a known quantity: a particular image, a particular configuration, a particular set of packages. From that moment it begins to diverge. An administrator edits a file during an incident and forgets to record it. A package is installed by hand. A service is enabled for a test and never disabled. An update changes a default. This divergence between what the platform believes a host looks like and what it actually looks like is **drift**. Drift is not only untidy: it makes behaviour unpredictable, makes rebuilds fail to reproduce the old machine, hides unauthorised change (including intrusion), and breaks compliance claims that were true on the day of installation.

At the other end of the lifecycle the problem is the opposite: the host is leaving, but its storage still holds data. Disks that are returned to a lessor, sold, reused for another tenant, or thrown away are a common route for data leaks, because deleting files and even reformatting leaves recoverable content. **Secure wipe** (the formal term is media sanitisation) is the discipline of making the data on retired or repurposed media unrecoverable to a defined standard, and proving that it was done.

The two halves are in one topic because they are the same control seen at two moments. Drift detection is continuous verification of the intended state during service; sanitisation is verified destruction of state at the end. Both depend on a recorded intention (a baseline, a policy) and on evidence (a report, a certificate). The typical failures are also parallel: a baseline that was never recorded, a check that runs but whose output nobody reads, a "wipe" that was a quick format, a wipe that was applied to the wrong device, and no record that links the action to the asset.

## History and approaches

Early drift detection was file-integrity monitoring. Tripwire (1990s) hashed system files and stored the hashes on read-only media, so that a later comparison could reveal tampering. AIDE, the Advanced Intrusion Detection Environment, follows the same idea as a free implementation. Red Hat's security guide describes it as a tool that checks files against an internal database and produces a report of changes since the last run [src: rhel-10-docs 1234e094abd9dcf1]. A second approach arrived with the kernel's Integrity Measurement Architecture (IMA), which works by comparing file hashes with values kept in extended attributes and can enforce policy, not only report; the guide compares the two, presenting AIDE as detection and IMA as detection plus prevention [src: rhel-10-docs 24f3425d42c528ba].

Configuration management introduced a different style: instead of looking for suspicious changes, declare the intended state and let the tool converge the machine to it. This made drift visible as a by-product, since the tool reports what it had to change. Ansible's check mode runs a playbook without making changes and reports what would have been altered, and its diff mode shows before-and-after comparisons; the two can be combined [src: ansible-docs bcb4d1e668c2a082]. Puppet's noop mode and Salt's test mode are the equivalent features (to verify per version). Terraform and OpenTofu detect drift in infrastructure by refreshing state and showing a plan, which was covered earlier in this course. Policy scanners, notably OpenSCAP with the SCAP Security Guide, compare a host to a security profile and are the standard drift check for compliance.

Sanitisation has its own history. The first approach was physical destruction. Then came software overwriting with patterns (the old multi-pass rituals), which was reasonable for magnetic disks. Flash storage changed the situation: a solid-state drive remaps blocks, keeps spare areas and wears its cells, so an overwrite from the operating system may never touch the physical locations that held the old data. The modern approaches are therefore **clear** (overwrite or logical erase, protecting against ordinary recovery), **purge** (using the device's own erase mechanisms or cryptographic erase, protecting against laboratory techniques) and **destroy** (physical destruction), the categories used in NIST Special Publication 800-88 on media sanitisation (to verify the current revision) [web: nist.gov]. The control catalogue SP 800-53 contains the requirement in family MP (media protection), where enhancement 6(1) requires that sanitisation and disposal actions be reviewed, approved, tracked, documented and verified, with the record listing who approved and performed the work, the media types, the method and the date, and the verification [src: nist-sp800-53 c3bc39c56882ec45]. Another enhancement requires that the equipment and procedures be tested at a defined frequency to show that the intended result is achieved [src: nist-sp800-53 19dbfc842a739b09].

## Current state

**Detecting drift with file integrity tools.** AIDE builds a database of file attributes and hashes according to rules, and `aide --check` compares the present state to the database. A check that finds differences prints a summary of added, removed and changed entries, then per-file details of which attribute changed. The Red Hat guide recommends scheduling the check at least weekly and ideally daily, for example through a cron entry [src: rhel-10-docs 1234e094abd9dcf1]. Two operational points matter. First, the database has to be updated after legitimate changes (such as patching), or every later report is noise; the update is a deliberate step by someone who has reviewed the change. Second, the database and the binary must be protected: an attacker who can rewrite the database can hide anything, so the baseline belongs on read-only or remote media, and the report should be sent to a system the host cannot alter. In a fleet built from images the database can be generated at build time and shipped with the image.

**Detecting drift with configuration management.** A scheduled run of Ansible in check mode with diff turned on gives a list of hosts and tasks that would change. The output is only as good as the modules: tasks that run raw commands, or modules without check support, report nothing, and the documentation says plainly that modules lacking check mode neither report nor act [src: ansible-docs bcb4d1e668c2a082]. Idempotent, declarative tasks are therefore required for the method to work. A common arrangement is a nightly check-mode run whose changed-task count per host becomes a metric: a host that reports changes every night has drift (or a non-idempotent task), and the trend is the signal.

**Detecting drift in packages and compliance.** `rpm -Va` verifies installed files against the package database and shows changed sizes, modes, owners and digests; `debsums` (or `dpkg --verify`) does the same on Debian systems (to verify per release). `dnf list --installed` or `rpm -qa` compared with a recorded baseline reveals manual installations. OpenSCAP scans compare configuration with a profile and produce a report. For container and image fleets the cheapest drift detection is none: hosts are replaced from a new image, and anything that was changed by hand disappears.

**What to do with drift.** There are three responses and the choice should be policy, not improvisation: *reconcile* (let the tool put the host back), *absorb* (the change was right, so put it in the code and the baseline), or *investigate* (the change is unexplained and may be hostile; preserve evidence before reverting). Automatic reconciliation of everything can destroy the evidence of an intrusion or an operator's emergency fix; automatic acceptance of everything defeats the purpose.

**Secure wipe: the choice of method.** The method depends on the medium and on what you control.

*Hard disks (magnetic).* A single full overwrite with zeros or random data is usually accepted as a clear method for modern drives. `shred` can overwrite a device (`shred -v -n 1 -z /dev/sdX`), and the QEMU documentation notes the same tool for erasing an image file that held a sensitive original [src: qemu-docs b2dc5f482935a0ba]. ATA drives also offer a firmware-level secure erase through `hdparm --security-erase`, which needs the drive unfrozen and a temporary password (to verify the exact procedure for the drive).

*Solid-state drives.* Overwriting from the host is unreliable because of remapping and spare area. Use the device's own sanitisation. `blkdiscard` issues discards to the whole device by default and, unlike the file-system `fstrim`, works directly on the block device [src: man-pages d798319ee580aa84]. Its secure option asks the device to erase every copy of the discarded blocks, including copies made by garbage collection, and requires hardware support; its zero-fill option writes zeros rather than discarding [src: man-pages 3d7bda05d98afe43]. Discard alone makes data unreadable through the normal interface on most drives but is not a certified purge, because the standard does not oblige the device to erase the cells at once (to verify per device).

*NVMe drives.* The `nvme-cli` tool offers `nvme format` with a secure-erase setting (user data erase or cryptographic erase) and `nvme sanitize` with block erase, overwrite or crypto erase, subject to the drive's declared capabilities, which `nvme id-ctrl` lists (to verify per drive) [web: nvmexpress.org]. The sanitize command is preferred where available because it runs to completion even after a power loss and is tracked in the drive's log page.

*Cryptographic erase.* If the data was always encrypted, destroying the key destroys the data. For LUKS volumes `cryptsetup erase` (the old name `luksErase`) removes all key slots, so that the master key can no longer be recovered from the header [src: man-pages 370669f38d6798ee]. This is fast, works for any size, and is the reason full-disk encryption is the best provisioning decision for retirement: the wipe becomes seconds, and a missed disk is still protected. It is only as strong as the original encryption and the secrecy of the keys, and copies of the header or key backups must be destroyed too.

*Hardware and the cloud.* Self-encrypting drives support cryptographic erase through the drive's own interface; the BMC or the storage controller may expose a wipe action (the previous topic). In a public cloud the customer cannot sanitise the physical media; the provider's attestation is what applies, and the customer's duty is to encrypt with its own keys and delete them.

**Proving it.** Whichever method is used, verification matters. For an overwrite, read back a sample or the whole device and confirm that it is all zeros (`cmp /dev/zero /dev/sdX` stops at the end of the device and reports the first difference), or check that a known pattern no longer appears. For cryptographic erase, confirm that `cryptsetup luksDump` reports no key slots. For a drive-level sanitise, read the drive's status log. The record then carries the asset tag, serial number, method, date, operator, tool version and result, as the NIST control specifies [src: nist-sp800-53 c3bc39c56882ec45].

## Assessment: the good, the bad and the ugly

**The good.** Both disciplines are cheap when planned at build time. A fleet built from code is mostly self-correcting, and drift reports then flag only the exceptions. Full-disk encryption with escrowed keys makes retirement fast and safe.

**The bad.** File-integrity tools generate noise on busy systems unless rules are tuned, so people stop reading them. Check-mode runs are blind to non-idempotent tasks. Wipe methods vary by device, firmware quality varies, and some drives falsely report completion or ignore commands; this is the reason the control requires testing of the process, not trust in it [src: nist-sp800-53 19dbfc842a739b09].

**The ugly.** The wrong-device wipe: a script receives `/dev/sda` and destroys the live system disk because the device names changed after a reboot. The remedy is to select devices by stable identifiers (serial number, WWN or `/dev/disk/by-id`), to refuse any device that is mounted or holds the root, and to require a confirmation that names the serial number. Another ugly case is the undocumented wipe: the work was done, but there is no record and the auditor must treat it as not done. A third is cloned drift: an image captured from a drifted host spreads the drift to the whole fleet.

**Assumptions.** Tool options and standards cited follow the vendor and project documents named; hardware behaviour differs by model and firmware, so drive-level commands must be validated on the device type in use (to verify). Statements about Puppet, Salt, hdparm, nvme-cli and NIST SP 800-88 summarise public documentation [web: nist.gov] [web: nvmexpress.org] [web: kernel.org].

## Applications beyond this domain

Baseline-and-compare is the idea behind database schema migration checks, Kubernetes GitOps controllers (which continuously compare cluster state to a repository), network configuration compliance tools and endpoint management. Sanitisation by key destruction is how mobile devices are wiped, how encrypted object storage handles deletion, and how backups can be made unrecoverable on request (the data-protection "right to erasure" is often implemented by deleting a per-customer key).

## Examples

**Example 1: a fleet drift report.** A nightly pipeline runs `ansible-playbook site.yml --check --diff` against all hosts, saves the output as JSON, and reports the number of changed tasks per host. Hosts with more than zero for three nights running open a ticket [src: ansible-docs bcb4d1e668c2a082].

**Example 2: AIDE in practice.** `aide --init` builds a new database, which is copied to a protected location and made the active baseline; `aide --check` runs daily from cron and mails the result to a central address; after a patch window an administrator runs `aide --update`, reviews the differences and promotes the new database [src: rhel-10-docs 1234e094abd9dcf1].

**Example 3: a retirement runbook for an encrypted host.** Verify the asset tag and serial number; run `cryptsetup erase` on the LUKS device; confirm with `cryptsetup luksDump` that no key slots remain; discard the whole disk with `blkdiscard` as an extra step; record the result; remove the machine's keys from the vault and its account from the provisioning platform [src: man-pages 370669f38d6798ee] and [src: man-pages d798319ee580aa84].

**Example 4: an NVMe purge.** `nvme id-ctrl /dev/nvme0` to read the sanitize capabilities, `nvme sanitize /dev/nvme0 --sanact=2` (block erase), then `nvme sanitize-log /dev/nvme0` until the status shows completion (to verify option names for the installed version) [web: nvmexpress.org].

**Example 5: verification of an overwrite.** After `shred -n 1 -z /dev/sdX`, run `cmp /dev/zero /dev/sdX`; the expected message is that the comparison reached the end of the device (the zero file never ends, so the message is about the device size) with no difference reported before it.

**Worked failure: the swapped device names.** A decommission script wiped `/dev/sdb`, which had been a retired data disk the day before but became the boot disk of a replacement host after the controller order changed. The wipe was started by hand from a shell history. The recovery was a rebuild from the image pipeline, and the script was changed to resolve the device by serial number and to refuse mounted devices.

## Related problems and ideas

This topic builds on the previous ones: **baremetal platforms** hold the inventory that ties an asset to a serial number, **BMC and Redfish** can reboot a host into a wipe image, and **Leapp and rebuilds** produce old hosts that must be retired. It connects to the **AIDE and OpenSCAP** topics of the security course, to **LUKS** in the storage course, and to **backup and restore**, since backups and snapshots are copies that also need sanitising. The cloud topic that follows covers provider-side media handling.

## Active research

Current work includes drift detection with machine-learned baselines, signed and measured boot to detect drift in firmware and boot chain, remote attestation of host state, and standardised, auditable drive sanitisation with verifiable proofs from the device. Research on flash forensics continues to refine which "clear" methods are enough for which media (to verify).

## Future direction

Expect immutable, image-based hosts to remove most configuration drift by design, attestation to extend drift detection below the operating system, and encryption by default to make cryptographic erase the standard retirement method, with a recorded key-destruction event as the evidence. The skill that lasts is to keep a baseline, to compare on a schedule, to decide in advance what to do with a difference, and to treat the end of a machine's life as a procedure with a record.
