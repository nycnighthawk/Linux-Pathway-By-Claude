# Teaching the API new nouns: custom resources, controllers and operators

## Define the problem

Kubernetes ships with a fixed vocabulary: pods, Deployments, Services, volumes. Real systems need other nouns. A database with replicas and backups, a TLS certificate that must be issued and renewed, a virtual machine, a cloud load balancer, an entire cluster: each has configuration that people want to declare, lifecycle logic that someone must run and status that someone must watch. Without a way to extend the API, those concerns live outside the cluster, in scripts and wiki pages and the heads of whoever knows how to fail the primary over safely, and they cannot use the cluster's authentication, authorisation, auditing, watches or tooling.

Two things have to be solved together. First, the API must be able to store and serve new object types, with schemas and versions, under the same rules as built-in ones. Second, something must act on those objects: create the pods, volumes and external resources they imply, and keep doing so as the world changes. A new type with no controller is a form with nobody reading it; a controller without a declared type is a script with hidden input.

This slice covers CustomResourceDefinitions (CRDs): what they define, structural schemas, validation, versioning and conversion, subresources and finalizers; the controller pattern and the operator idea that packages operational knowledge in a controller; how administrators install, upgrade and troubleshoot operators; and the risks they bring. Writing an operator with kubebuilder is a topic of the delivery course and appears here only as the model for reading one.

## History and approaches

The first extension mechanism was ThirdPartyResources, introduced in 2015 and widely used by early adopters such as CoreOS, whose etcd and Prometheus operators gave the idea its name. The CoreOS team described an operator as a software component that encodes a human operator's knowledge: it watches a custom resource that represents, say, an etcd cluster, and drives the actual cluster toward that description, handling scale, upgrade and backup. ThirdPartyResources had no schemas, poor versioning and several bugs, and were replaced by CustomResourceDefinitions in 1.7 (beta), which reached general availability in 1.16 together with structural schemas, defaulting and pruning of unknown fields. The aggregation layer offered the heavier alternative of running a whole separate API server whose endpoints the main one proxies, as the metrics server does.

Alongside came the libraries to write controllers. client-go's informers and work queues gave a standard shape: watch objects, cache them locally, enqueue keys of changed objects, reconcile each key. Frameworks built on them (the Operator SDK from Red Hat, kubebuilder from the API machinery group, and later controller-runtime as the shared base) generated scaffolding, CRD manifests from Go type annotations, webhooks and test environments. Operators for other languages and for no code at all appeared: Helm-based and Ansible-based operators in the Operator SDK, the Java Operator SDK, Kopf for Python, and declarative engines such as Crossplane compositions.

Competing approaches shaped the discussion. Admission webhooks can enforce rules but cannot create state. Configuration management (Ansible, Terraform) can create resources but does not react continuously. Helm charts install but do not operate. The operator pattern's claim is that continuous reconciliation of declarative intent is the right model for operations, and the Operator Lifecycle Manager from the OperatorHub ecosystem added catalogue, installation and upgrade management for operators themselves, with its own CRDs. KubeVirt is the instructive example for this course: its architecture review describes using CRDs and core primitives to turn virtual machines into Kubernetes-native objects, with an operator deploying and configuring each component and a per-machine launcher pod running the hypervisor process.

The pattern that settled: define the nouns with a CRD, store them in the same etcd, reconcile them with a level-triggered controller, report through a status subresource and conditions, protect deletion with finalizers, and distribute the whole as an operator deployed by a Deployment, OLM, Helm or GitOps.

## Current state

**The CRD object.** A CustomResourceDefinition names the API group, the kind in singular, plural and list forms, the scope (namespaced or cluster), and a list of versions. Each version has an OpenAPI v3 schema that must be *structural*: every field has a declared type, so the API server can validate, prune unknown fields and apply defaults. The Kubernetes documentation notes limits on this, such as when a field must preserve unknown content and how raw extension types behave. Beyond types, schemas can carry validation rules written in the Common Expression Language, which the API server evaluates on create and update; the documentation on admission webhook practice tells authors to prefer built-in validation and defaulting for custom resources over writing a webhook, because it is faster, safer and declarative. Printer columns control what `kubectl get` shows. Categories and short names make custom kinds easier to use.

**Subresources and status.** Enabling the `status` subresource splits the object's spec (what the user wants) from status (what the controller observes), with separate permissions, so a user cannot forge status and a controller does not trample the spec. The `scale` subresource lets generic tooling, such as the HPA, scale a custom resource. Conventions for `status.conditions` (type, status, reason, message, observed generation) let tools show readiness uniformly.

**Versions and conversion.** A CRD can serve several versions at once, with exactly one marked as the storage version. When versions differ in structure, a conversion webhook translates between them, deployed as a service the API server calls; a failing conversion webhook breaks every read of those objects, a point the versioning documentation makes by describing how the service must be deployed and trusted. Deprecation and storage migration are the author's duty: objects stored in an old version must be rewritten before that version is removed.

**Finalizers and garbage collection.** A finalizer is a string on an object's metadata that blocks deletion until a controller removes it; the controller uses the delay to clean up external resources, such as a cloud disk or a database, and then removes the finalizer. This is the asynchronous pre-delete hook the CRD documentation describes. Owner references tie dependents to an owner, so that deleting the owner garbage-collects the pods, services and volumes it created.

**The controller loop.** A controller watches its custom kind and the kinds it owns, receives events and reconciles: read the object, compare spec with the world, create or update dependents, update status, return. Reconcile must be idempotent, tolerate being re-run at any time, and not rely on a particular event ordering. Errors cause requeue with backoff. Leader election lets several replicas run with one active. The controller needs RBAC rights to everything it touches, and an operator that asks for cluster-admin has become a privilege-escalation path.

**Operators in practice.** An operator is delivered as a CRD set plus a controller Deployment with its RBAC, often in its own namespace and sometimes with admission webhooks. Installation methods include plain manifests, Helm, OLM and GitOps tools. KubeVirt documents an installation in which its operator creates a `KubeVirt` custom resource that triggers deployment of the virt-api, virt-controller, virt-handler and related components, and notes that choices in this resource, such as node placement and overlay storage for VM state, are made through its fields. The Containerized Data Importer, with its DataVolume resource, is another custom resource that other components depend on: a DataVolume imports a disk image into a PVC. Cilium's operator handles cluster-wide duties such as IP address management, separate from the per-node agent, showing the split between an operator for cluster tasks and an agent per node.

**Administering operators.** Day-to-day, an administrator lists what an operator offers with `kubectl api-resources` and `kubectl explain` against the CRD schema, inspects status conditions and events on the custom object, reads the operator's logs, and checks its leader lease. Upgrading an operator means upgrading its CRDs and controller, in an order its documentation prescribes, and Helm does not upgrade CRDs. Deleting a CRD deletes all objects of that kind, so protect them with RBAC and `kubectl delete crd` is a dangerous command.

## Assessment: the good, the bad and the ugly

The good: CRDs make the API genuinely extensible. A new type gets authentication, authorisation, audit, watches, namespacing, tooling support and ecosystem integrations (GitOps, backup, policy) for free. Operators capture hard-won operational knowledge, so a database can be created with a short manifest and failover handled by code. The declarative model fits GitOps: the database is a file in a repository.

The bad: quality varies enormously. A mature operator may encode years of experience; an immature one is a thin wrapper that works on the happy path and fails opaquely. Each operator adds a controller, CRDs and RBAC to maintain, and a cluster with forty operators has forty upgrade paths and forty sets of failure modes. CRDs share the datastore and API server capacity, and large numbers of custom objects or chatty controllers stress etcd and the watch cache. Schemas evolve, and breaking changes between operator versions can strand objects.

The ugly: lifecycle edges. Deleting a CRD cascades to its objects, and removing an operator before its custom resources leaves objects with finalizers that nobody will clear, stuck in Terminating forever. A broken conversion webhook, or a webhook with a failure policy of "fail" in the critical path, can block the creation of pods cluster-wide; the admission documentation lists good practices precisely because of such incidents. Operators with broad permissions are high-value targets. Reconcile loops fighting with other controllers or with humans produce flapping. Status that lies (a ready condition that is never updated) leads tools to proceed on false information. And an operator that assumes a version of the thing it manages (a particular database major version) fails in confusing ways when users bring their own.

Mitigations: use a defined schema with validation rules; prefer built-in validation to webhooks; set webhook timeouts, failure policies and namespace selectors that exclude system namespaces; test operator upgrades in staging including CRD changes; install operators with the least RBAC they document and watch namespaces narrowly; back up custom resources with the cluster; use finalizers deliberately and have a documented removal order when uninstalling.

## Applications beyond this domain

The reconcile pattern is the general control-theory idea behind thermostats, autopilots and network routing protocols: compare desired state with observed state and act on the difference, repeatedly. Cluster API manages Kubernetes clusters with it, Crossplane manages cloud resources and Argo CD manages deployments, all as controllers. Outside Kubernetes the same shape appears in Terraform's plan and apply, in configuration management convergence runs, in database replication managers and in Puppet's agents. The use of CRDs as a database-like store with schema, versioning and watch semantics is itself a general lesson: a consistent, watchable, access-controlled store with a uniform API is a powerful substrate, and several non-Kubernetes projects mimic it.

## Examples

Reading an unfamiliar operator: list its CRDs with `kubectl get crd | grep example.com`, explain a kind with `kubectl explain widget.spec`, look at one object with `kubectl get widget w1 -o yaml` and focus on `status.conditions`, then read the controller log filtered by the object's name. The events on the object usually name the failing step.

A typical operator-managed database: apply a short manifest declaring a three-member cluster, a storage size and a backup schedule. The operator creates a StatefulSet, Services, a ConfigMap, a Secret with generated credentials, a PodDisruptionBudget and a CronJob. If the primary pod dies, the operator promotes a replica and updates a Service. The administrator never edits the StatefulSet directly because the operator would revert it.

A failing example: an administrator removes an operator's Deployment and namespace to "clean up" and then cannot delete the namespace of the application it managed. The custom objects carry finalizers that only the operator would remove. The recovery is to reinstall the operator, delete the objects normally, and then uninstall; patching finalizers away by hand leaves the external resources they protected behind.

A second failing example: a validating webhook for a custom type runs in a pod that is itself created through the webhook. After a cluster restart, the webhook pod cannot start because the API server calls the unavailable webhook for the pod's own creation. The fix is a failure policy of ignore for that webhook or a namespace selector that exempts the webhook's namespace.

## Related problems and ideas

Aggregated API servers offer richer behaviour (custom storage, subresources) at higher cost. Crossplane and Cluster API compose custom resources into higher-level platform APIs. Kubernetes Resource Model functions and kpt treat manifests as data to be transformed. Policy engines (Kyverno, Gatekeeper) use CRDs for rules. The Operator Capability Model grades operators from basic install to full autopilot, a rough measure of maturity. Alternatives to Go operators lower the barrier: Helm-based, Ansible-based or Python operators, and expression-language-only approaches such as validation rules plus mutating policies that avoid webhooks entirely. Not mainstream yet are declarative controllers described as data, which a generic engine runs, removing the need for compiled operator code.

## Active research

The API machinery group works on declarative validation, on moving more webhook functions into in-process expression languages (validating and mutating admission policies), on streaming list responses and watch efficiency for large custom resource sets, and on safer CRD version migration. Operator authors study testing of reconcilers, including model checking and fault injection, and the community has produced academic work on bugs in operators, such as the finding that many failures arise from state-transition edge cases when events are missed or reordered. How to give operators least privilege automatically, and how to verify operator behaviour before running it in production, are open questions (to verify the current state of each feature).

## Future direction

Expect declarative validation and mutation through the API server to reduce reliance on webhooks, richer status and condition conventions, better tooling for CRD lifecycle (storage migration, upgrade safety checks), and platform engineering built on compositions of custom resources instead of tickets. Operators will continue to move from Go scaffolding toward higher-level frameworks and AI-assisted generation. For administrators the critical skills do not change: read the CRD and its status, know the uninstall order, and treat each operator as a piece of software with its own upgrade and failure behaviour.
