# Keeping the cluster's memory safe: etcd snapshots, restores and what they do not cover

## Define the problem

Everything Kubernetes knows about the world it is supposed to build lives in one datastore. Deployments, Services, ConfigMaps, Secrets, RBAC bindings, custom resources and the node and pod records the controllers write all sit in etcd. The worker nodes could be rebuilt from a template in an hour. The control-plane binaries could be reinstalled from packages. The only thing that cannot be recreated by reinstalling is the content of that database. If it is lost or corrupted and no copy exists, the cluster still runs the containers that were already started but nobody can say what they were for, and the whole desired state must be reconstructed from whatever is in Git, in people's heads and in the application teams' pipelines.

Backup of a consensus database looks easy and hides several sharp points. A copy of files from a running member's data directory is not guaranteed to be consistent. A restore that brings a cluster back to a point in time creates a split between what the database says and what the nodes actually run. A restore on one member of a three-member cluster does nothing useful unless the other members are rebuilt from the same snapshot. Backups contain every Secret, so a casual copy is also a data breach. And nobody knows whether a backup works until a restore has been rehearsed.

This slice covers what etcd stores and how it fails, taking and verifying snapshots, restoring a single-member and a multi-member cluster, the kubeadm-specific steps, the datastore's size quota and maintenance (compaction and defragmentation), protection of the backups, and the limits of an etcd backup compared with an application-level backup of volumes and objects. The architecture of the datastore is in T01 and encryption of Secrets at rest in the security course.

## History and approaches

etcd was started at CoreOS in 2013 as a small, reliable key-value store for cluster configuration and coordination, built on the Raft consensus algorithm that Diego Ongaro and John Ousterhout had published to be easier to understand than Paxos. It was donated to the Cloud Native Computing Foundation in 2018. Kubernetes adopted it from the beginning, and the early project used version 2 of the etcd API, which stored data in memory with a write-ahead log and exposed a hierarchical key model. Version 3, released in 2016, changed the storage engine to a persistent multi-version store on a B-tree database file, added transactions and efficient watches by revision and a flat key space; Kubernetes moved to it and the upgrade of datastore content from v2 to v3 became its own migration chore.

Backup practice evolved with the tooling. The first approach was to copy the data directory, which risks capturing a torn state. The `etcdctl snapshot save` command, which streams a consistent point-in-time snapshot from a live member, replaced it. For restore, the original `etcdctl snapshot restore` command was found to mix concerns of a client tool with operations on local files, so the project split offline operations into a separate utility, `etcdutl`, and marked the restore subcommand of `etcdctl` as deprecated, as the Kubernetes documentation still reminds administrators. The same utility checks a snapshot's hash and revision.

Alternative approaches to protecting a cluster appeared in parallel. Cloud providers snapshot the volume under a self-managed etcd, which Kubernetes' own failure-mode documentation lists as a mitigation for losing the datastore's storage, though it protects from disk loss and not from operator error that is already replicated. Tools such as Velero back up Kubernetes objects through the API server and use volume snapshots for persistent data, which makes them portable between clusters and protects individual namespaces; they do not restore the control plane itself. Declarative infrastructure takes yet another approach: if every object is in Git and applied by a GitOps controller, losing etcd is an inconvenience rather than a disaster, though Secrets, generated objects and in-cluster state still need separate handling. Managed Kubernetes services take the datastore away from the customer, who then relies on the provider's backups and on application-level backups.

Lessons: use the datastore's own snapshot mechanism, restore only with every API server stopped, treat backup as a pipeline with off-site copies and restore tests, and never assume that an etcd snapshot is a complete disaster recovery plan.

## Current state

**What is stored and how big it grows.** All API objects are keys under a common prefix, and etcd keeps a history of revisions so that watches can resume. Without compaction, history grows without bound, which is why the API server requests compaction at a regular interval, every five minutes by default. Compaction removes old revisions logically but does not return disk space; defragmentation rewrites the database file to reclaim it. The datastore has a size quota (two gibibytes by default, with a few gibibytes recommended as a maximum). When the quota is exceeded, etcd raises a NOSPACE alarm and the cluster becomes read-only until space is freed, compaction run, the fragments removed and the alarm cleared. Typical causes are runaway controllers, event floods and large objects such as huge ConfigMaps or custom resources.

**Taking a snapshot.** From a control-plane node or from inside the etcd pod, the command is `etcdctl snapshot save FILE` with the endpoint and the client certificate, key and CA, which under kubeadm live in `/etc/kubernetes/pki/etcd`. The command asks one member for a consistent snapshot of the database. The result is a single file with a hash. `etcdutl snapshot status FILE` prints the hash, revision, key count and size and is the cheapest sanity check. A snapshot taken from one member of a healthy cluster represents the whole cluster state at that revision, so one member suffices, but the endpoint should be a healthy member, not an arbitrary one.

**Protecting backups.** The snapshot holds Secrets in whatever form the API server stored them. If encryption at rest is not configured, they are plain text inside the snapshot, and even when it is, the key sits in the API server's configuration on the same machine. Backups therefore need encryption, restricted access and a retention policy, and the encryption key for Secrets must be backed up separately from the data it protects. The Kubernetes security guidance lists encryption of Secrets at rest among the measures to protect cluster components, and a backup that undoes that protection defeats it.

**Restoring, step by step.** The documented order for a cluster with running API servers is strict: stop every API server instance, restore the state on all etcd members, restart the API servers. The project also recommends restarting the scheduler, controller manager and kubelets so that they do not rely on stale data; during the restore the leader locks of the controllers expire and they restart themselves. For a single-member cluster under kubeadm the sequence is: stop the control-plane static pods by moving their manifests out of the manifests directory, run `etcdutl snapshot restore FILE --data-dir NEWDIR`, point the etcd manifest's `hostPath` for the data volume to the new directory (or restore into the old directory after removing it), return the manifests and let the kubelet restart the pods. The Kubernetes page also tells kubeadm users to set the data directory in the kubeadm ConfigMap so a later upgrade does not revert it.

For a multi-member cluster the same snapshot file must be restored on each machine, with the member's name, peer address and the full list of initial peers passed to the restore command, and a new cluster token so that the restored members do not rejoin the old identities. In practice many administrators restore one member, start it as a one-member cluster, and add the others as new members, which avoids the cluster-token details.

**What the restore leaves behind.** The snapshot reflects the cluster at the instant it was taken. Anything that happened later is gone from the records: Deployments created afterwards disappear from the API, while the pods they spawned may still run on nodes until the kubelets reconcile and kill them; PersistentVolumes provisioned after the snapshot exist in the cloud but not in the API, so they leak; nodes joined later find their records missing and their certificates may be rejected. The Kubernetes documentation on kubeadm upgrade failures, which lists recovery by restoring from backup, makes the same point from the other side: the restore is a rollback of the control-plane's belief, not of the world.

**Complements.** Etcd snapshots protect the control plane; Velero or the CSI volume snapshot API protect namespaces and volumes. The KubeVirt snapshot and restore documentation shows the second kind at work: a snapshot of a virtual machine requires a VolumeSnapshotClass and a CSI driver that supports snapshots, so even in a platform built on Kubernetes the data plane and the control plane are separate things to back up.

## Assessment: the good, the bad and the ugly

The good: snapshot and restore are single commands, the snapshot is a single file that is easy to ship off-site, and a rehearsed procedure takes minutes. The Raft design means that restoring a majority of members from the same snapshot gives a consistent cluster.

The bad: the restore needs a short full outage of the API. Every restore is a data loss event for the period since the last snapshot, so the backup frequency determines the recovery point; hourly snapshots mean up to an hour of changes disappear. Snapshots are coarse. If one namespace is deleted by mistake, a cluster-wide restore rolls back everybody else's changes too, which is why object-level backup tools are used for that case.

The ugly: the failure modes tend to be organisational. Backups are taken but never restored; the certificates needed to restore expired together with the cluster's; the snapshot sits on the same disk as the data and goes with it; the Secret encryption key was not saved; the person who knows the procedure has left. Version details bite as well: snapshots restore into the same major and minor version of etcd, so a backup from before an upgrade needs the old binary. The deprecated and moved commands cause old run books to fail. And in a stacked topology the ordinary reaction to trouble, deleting and recreating a failing member, can reduce a three-member cluster to a two-member one without anyone noticing, in which any further failure loses quorum.

Mitigations: schedule snapshots from a CronJob or a systemd timer with a pull from a trusted backup server; copy them off the node and off the site; encrypt them; record the etcd and Kubernetes versions in the file name; alert on backup age and on the NOSPACE alarm; run a restore drill into a scratch cluster every quarter and measure the time; keep the procedure in the runbook with the exact certificate paths.

## Applications beyond this domain

The snapshot-and-restore discipline applies to every consensus store: Consul snapshots, ZooKeeper data directories and transaction logs, and the Vault integrated storage snapshots all follow the same rules about quorum, offline restore and the loss of recent writes. The distinction between a physical backup of a database file and a logical one, familiar from PostgreSQL's `pg_basebackup` versus `pg_dump`, maps to etcd snapshot versus object-level export. The point that recovery time and recovery point must be agreed with the business is general disaster-recovery practice and appears in the Identity Management disaster-recovery guidance from Red Hat, which stresses preparation for replica loss and rehearsal. The compaction and defragmentation cycle is the same housekeeping as vacuuming in a multi-version database.

## Examples

A routine backup on a kubeadm control plane:

The command is `etcdctl snapshot save` with a destination file named after the date, run against the local member at port 2379 over TLS using the CA, server certificate and server key from the etcd pki directory, followed by `etcdutl snapshot status` with table output on the same file.

A successful restore drill: move the four static pod manifests out of the directory, wait until `crictl ps` shows no control-plane containers, run `etcdutl snapshot restore` into a new directory, edit the etcd manifest so its data volume points there, move the manifests back, and wait for `kubectl get nodes` to answer. Then check which Deployments exist and compare with the time of the snapshot.

A failing example: an administrator restores a snapshot while the API servers are still running. The API servers hold watch caches at a newer revision than the restored datastore, so controllers see an object history that goes backwards and behave erratically. The cure is the documented order: stop all API servers first, restore, then start them.

Another failing example: the NOSPACE alarm. A buggy operator creates a new Event every second, the database reaches its quota, and every write is refused. Reads still work, so dashboards look fine while nothing can be changed. The recovery is to stop the source, compact, defragment each member and disarm the alarm, and then to add alerting on database size.

## Related problems and ideas

Other platforms avoid etcd. k3s defaults to an embedded SQLite database or an external SQL database through an adapter, and its snapshots are of that store; OpenShift runs etcd with an operator that automates backup and encryption key management; managed offerings hide it. Ideas not in the mainstream include continuous streaming replication of the write-ahead log to object storage for near-zero recovery point, which etcd does not provide natively, and learner members and mirror makers that keep a standby cluster in another region. Application-level approaches such as the Velero backup hooks, volume group snapshots and immutable Git sources of truth address the part of recovery that an etcd snapshot cannot. A cluster can also be treated as cattle: rebuild it from code and restore only the workloads' data, which works well when everything of value is declared outside the cluster.

## Active research

The etcd project continues work on faster, safer maintenance operations (online defragmentation, compaction efficiency, storage engine memory use), on options for restoring that bump the revision so that watchers in a restored cluster resynchronise instead of misbehaving (to verify the exact flags in the current release), and on learner and downgrade support, which makes upgrading a datastore reversible. Research on Raft variants and on correctness testing, for example Jepsen-style analyses of etcd's consistency, shapes what operators can trust. Kubernetes work on storage version migration and on consistent reads from cache reduces load on the datastore and alters its size profile.

## Future direction

Expect the release line of etcd to continue to move toward easier downgrade and online maintenance, and Kubernetes distributions to add scheduled snapshot operators as a built-in feature. Cluster API controllers increasingly take etcd snapshots as part of control-plane lifecycle operations. For administrators the durable guidance is stable: decide an acceptable recovery point and time, automate the backup, move it off the cluster, protect the secrets in it and rehearse. Re-read the project documentation at each upgrade because the restore flags and the deprecation status of commands have changed more than once (to verify for your version).
