# Giving short-lived pods durable data: volumes, claims, classes and the CSI contract

## Define the problem

Containers are built to be disposable. A pod can be killed, rescheduled to another node and recreated from an image at any time, and the writable layer of its container disappears with it. Many useful programs, databases above all, need state that outlives any single pod, follows the pod to a new node or at least stays addressable, and does not depend on which cluster administrator happened to configure the disk. At the same time application authors should not have to know whether the disk is a cloud block device, an NFS export, a Ceph volume or a local SSD.

Failure takes several forms. Data is stored in the container filesystem and vanishes on restart. A volume is created in one availability zone and the pod is scheduled in another, so it never starts. A claim is deleted and the underlying disk is deleted with it, though it held the only copy of a production database. A volume fills up and cannot be grown without an outage. A shared filesystem is mounted read-write by two nodes whose software assumes exclusive access, and the data is corrupted. Two teams argue about who owns the disk when the project that created it is deleted.

This slice covers the storage objects (volumes, PersistentVolume, PersistentVolumeClaim, StorageClass), static and dynamic provisioning, access modes and volume modes, reclaim policy and binding behaviour, volume expansion, snapshots, the Container Storage Interface that standardises drivers, the topology problem, and the patterns for stateful workloads with StatefulSets. The details of particular storage back ends (Ceph, Longhorn and cloud disks) are beyond depth three, and backing up application data is mentioned only as it relates to snapshots.

## History and approaches

The first Kubernetes storage answer was in-tree volume plugins: the code to attach a Google persistent disk, an Amazon EBS volume or an NFS share lived inside the core Kubernetes binaries, and the pod spec referred to those back ends directly. That made each cloud's storage a core dependency, and made every bug fix wait for a Kubernetes release. The PersistentVolume and PersistentVolumeClaim objects separated the roles: an administrator, or a provisioner, supplies volumes; a user claims capacity by requirements without naming the disk. StorageClass, introduced to automate the supply, lets a claim name a class and have a volume created on demand, a design that mirrors how cloud consoles and libvirt storage pools already offered a pool abstraction that creates volumes within it.

Out-of-tree drivers came next. FlexVolume was an early executable-based plugin interface and proved awkward: it required files on every node and had limited features. The Container Storage Interface, a specification shared among Kubernetes, Mesos and others and designed by the storage special interest group with storage vendors, defined a gRPC contract between the orchestrator and a driver, with a controller service for provisioning, attaching and snapshots and a node service for mounting. It reached general availability in Kubernetes 1.13. A long migration then moved the in-tree cloud plugins to CSI drivers behind a translation layer, and the old plugin code was removed release by release. Alongside, the snapshot API (VolumeSnapshot, VolumeSnapshotClass) was added as custom resources with an external controller, and volume expansion, cloning and topology-aware provisioning followed.

Competing approaches shaped the options. Network filesystems such as NFS give shared access cheaply and with weak semantics. Distributed storage systems such as Ceph with Rook and Longhorn replicate blocks between nodes and provide storage that follows pods. Local volumes are fast and cheap and tie a pod to a node. Cloud block devices are reliable but zonal. Some platforms avoid persistent volumes altogether by treating databases as external managed services, so the cluster remains stateless. Virtual-machine platforms on Kubernetes need unusual things from storage: the KubeVirt documentation describes a hostpath provisioner and CSI overlay arrangements for VM state, because virtual disks require block devices, large sizes and sometimes shared access for live migration.

The pattern that emerged: decouple the claim from the volume; automate with classes; push every back end behind a narrow, versioned driver interface; and make topology a first-class input to provisioning.

## Current state

**Volumes and claims.** A pod's `volumes` list names sources such as `emptyDir` (scratch space tied to the pod's life), `configMap` and `secret` (projected files), `hostPath` (a node directory, which is a security and portability hazard) and `persistentVolumeClaim`. A PersistentVolumeClaim states a size, an access mode and optionally a StorageClass and a volume mode (filesystem or raw block). A PersistentVolume is the cluster-level object that represents an actual disk. The claim binds one-to-one to a matching volume, whose capacity must be at least the request, whose access modes include the requested mode, and whose class matches.

**Access modes.** ReadWriteOnce allows mounting read-write on one node (several pods on that node may share it); ReadWriteOncePod restricts it to a single pod; ReadOnlyMany allows many nodes to read; ReadWriteMany allows many nodes to read and write and is supported only by shared filesystems and some distributed back ends. Choosing the wrong mode is a typical source of pods stuck in ContainerCreating, with an event reporting a multi-attach error after a node failure, because the old node still holds the attachment.

**StorageClass and dynamic provisioning.** A class names a provisioner (the CSI driver), parameters specific to the back end (disk type, replication, encryption key), a reclaim policy and a binding mode. When a claim names the class, the external provisioner creates a volume and a matching PersistentVolume object and the claim binds. One class can be marked default so claims that name none get it. Volume binding mode `Immediate` creates the disk as soon as the claim exists; `WaitForFirstConsumer` waits until a pod using the claim is scheduled, then creates the disk in the right zone, which the storage class documentation recommends wherever volumes are tied to a topology segment.

**Reclaim policy.** When a claim is deleted, the volume's reclaim policy decides its fate. `Delete` removes the volume and the underlying disk; `Retain` keeps both for manual recovery, with the volume left in a Released state that cannot be claimed again until an administrator cleans it; recycling is obsolete. The documentation describes the lifecycle states (Available, Bound, Released, Failed) and a finalizer protection that stops a volume or claim that is in use from being deleted immediately. Because dynamically created volumes inherit the class's policy, the default `Delete` has destroyed data in more than one incident; production classes holding irreplaceable data often use `Retain`, with other protections around them.

**Expansion.** A class that sets `allowVolumeExpansion` permits increasing a claim's requested size. The driver grows the disk, and the file system is expanded either online or at the next mount depending on the driver. Shrinking is not supported. The Kubernetes documentation separates the two phases, and a claim can sit in a state where the disk has grown but the filesystem resize is pending.

**Snapshots and clones.** A VolumeSnapshotClass, analogous to a StorageClass, names the driver and deletion policy for point-in-time copies. A VolumeSnapshot object requests one; a VolumeSnapshotContent represents it. A new claim can use a snapshot or another claim as its data source. The KubeVirt snapshot feature depends on exactly this API and needs a class for the driver in use. Snapshots are crash-consistent at best unless the application is quiesced.

**The CSI contract.** A CSI driver ships as a controller deployment (with sidecar containers that watch the API and call the driver for provisioning, attaching, snapshotting and resizing) and a node DaemonSet (which registers with the kubelet, stages and publishes volumes into pod directories). Drivers register a CSIDriver object describing capabilities such as whether attach is required. A node reports how many volumes it can hold through CSINode. Understanding this split helps in troubleshooting: provisioning failures are in the controller sidecars' logs, mount failures in the node plugin and the kubelet.

**Stateful workloads.** A StatefulSet gives each replica a stable identity and a PersistentVolumeClaim created from a template, so a replica restarts with the same disk. Its claims are, by default, not deleted when the StatefulSet is scaled down or deleted, a deliberate safety that leaves orphan disks, and a retention policy field allows changing it. Spreading replicas across zones needs the topology-aware binding mode to keep each replica's disk near the pod.

## Assessment: the good, the bad and the ugly

The good: the claim abstraction works. Application manifests are portable between clouds, a class turns provisioning into a one-line request, and CSI means that a new storage product needs a driver, not a Kubernetes release. Snapshots, expansion and cloning give a consistent management vocabulary across very different back ends.

The bad: the abstraction hides real differences. Performance, durability, snapshot semantics and failure behaviour vary enormously between a local SSD, a zonal cloud disk and a replicated distributed system, and the claim says nothing about them. Access modes are advisory in some drivers. Zonal volumes tie pods to zones, so a zone outage with only zonal disks is an outage of the application. Stateful applications in Kubernetes inherit all the hard problems of their own replication, backup and upgrade, which the platform does not solve. Capacity management is manual: nothing automatically moves data when a node's disks fill.

The ugly: lifecycle accidents. A namespace deletion removes claims, and with the `Delete` reclaim policy the disks go too. A multi-attach error after a node crash can keep a pod from starting for minutes while the control plane waits to detach from the dead node. Retained volumes accumulate as orphans and cost money. Local-path provisioners that put data in a node directory work well in demos and lose the data when the node is replaced. File systems that fill silently cause applications to fail in odd ways; expansion that stalls halfway leaves a claim apparently large but a filesystem small. Drivers differ in how they behave under upgrade: an old version may not support a new feature of the controller sidecars. A Windows or SELinux-labelled node may refuse a mount because of relabelling or permission quirks.

Mitigations: choose classes deliberately and name them by capability (fast-zonal, shared-nfs); use `WaitForFirstConsumer` for topological volumes; set `Retain` or snapshot-based backups for critical data; monitor volume usage with kubelet metrics and alert before full; test node failure for stateful workloads; keep driver and sidecar versions within their compatibility matrix; and keep application-level backups, because replication is not backup.

## Applications beyond this domain

The claim-and-class split is the same idea as virtual machine disks drawn from libvirt storage pools: a pool defines how volumes are created and where, and guests simply receive a disk, as the libvirt management documentation shows with its pool commands. Cloud platforms have the equivalent in block storage volume types and quotas. The separation of control-plane provisioning from node-level mounting, and the narrow driver contract, is also the model of the container runtime and network interfaces, and of the Open Service Broker. The reclaim-policy dilemma, keep or delete when the owner goes away, is general resource lifecycle management and shows up in cloud resource tagging and garbage collection. Replicated block devices in distributed systems resemble the shared-disk and fencing issues in the enterprise high-availability course, where only one writer may own a device at a time.

## Examples

A dynamic claim in practice: a StatefulSet for a database with a `volumeClaimTemplates` entry requesting 20 GiB from a class with `WaitForFirstConsumer`. The first pod is scheduled to a node in zone b, the provisioner creates a disk in zone b, the claim binds and the pod starts. Later the node is drained; the pod moves to another node in zone b because the volume's node affinity restricts it, and the pod starts after the disk is detached and attached.

An expansion: `kubectl patch pvc data -p` with a larger request on a class that allows expansion; the claim shows a resize condition until the filesystem has been grown, and the pod sees the new size, sometimes only after a restart.

A failing example: an engineer deletes a test namespace that contains a claim for a database used by another team through a shared name. The class's reclaim policy was `Delete`, and the cloud disk disappeared. The recovery is a restore from the last snapshot or backup, which is why the policy and the backup are decided before the first write.

Another failing example: a pod stays in ContainerCreating after a node crash with a multi-attach error. The disk is still attached to the dead node; the controller must wait for the node to be declared unreachable and then detach, or an administrator forces the detach at the cloud level after confirming the node is really down.

## Related problems and ideas

Object storage, accessed through an API rather than a mount, avoids many of these issues for large data and is complemented by projects such as the Container Object Storage Interface that provision buckets by claims. Local persistent volumes with node affinity are used for databases that replicate at the application level and want raw speed. Ephemeral inline CSI volumes and generic ephemeral volumes give per-pod scratch disks from a class. Storage capacity tracking lets the scheduler consider the free space reported by drivers. Immutable and read-only root filesystems reduce the amount of writable state in the first place. Not yet mainstream: cross-cluster volume replication and consistent group snapshots of several volumes for multi-volume applications, which are in progress in the storage group (to verify their current stage).

## Active research

Work in the community covers volume group snapshots, changed-block tracking for efficient backup, volume attributes classes that let a claim change performance characteristics (IOPS, throughput) without recreating the disk, better handling of node shutdown and non-graceful failure so that volumes are detached sooner, and access-mode semantics that are enforced rather than advisory. Distributed storage research examines performance isolation between tenants and failure recovery times for replicated block devices. Operators of KubeVirt study how to meet virtual-machine disk needs such as live-migration compatible shared block storage.

## Future direction

Expect CSI to keep absorbing features (group snapshots, attribute classes, topology capacity), and the in-tree plugins to disappear completely. More platforms will offer a managed default class that already encodes sensible reclaim and expansion settings. Stateful data services will continue to move from hand-built StatefulSets to operators (T09) that handle backup, failover and upgrade. For the administrator the decisive skills remain understanding failure behaviour of the chosen back end and rehearsing recovery (to verify feature stages for your version).
