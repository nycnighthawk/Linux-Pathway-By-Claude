# Deciding where work runs and how much of it: requests, placement rules and autoscalers

## Define the problem

A cluster is a pool of machines of different sizes, locations and purposes, and a stream of workloads that need different amounts of CPU, memory, devices and disk. Someone must decide for each unit of work which machine runs it, and the decision must be fast, repeatable and honest about limits. Failure looks like a node running out of memory and killing the wrong process, a database placed beside a noisy batch job that steals its CPU, all replicas of a service landing on the machine that fails, a GPU node filled with web servers, or a cluster that sits at ten percent utilisation because everybody asked for more than they use.

Placement has two audiences with opposing interests. The platform operator wants high utilisation and the freedom to take nodes out of service. The application owner wants guaranteed resources, isolation from neighbours and availability across failure domains. Kubernetes mediates with a declarative vocabulary: the pod states what it needs (resource requests), what it tolerates, where it prefers or refuses to run (selectors, affinity, spread rules), and how important it is (priority). The scheduler turns those statements into a placement, and autoscalers change the number of pods and nodes as demand moves.

This slice covers resource requests and limits and the quality-of-service classes they produce, node selectors and node affinity, pod affinity and anti-affinity, topology spread constraints, taints and tolerations, priority and preemption, the horizontal and vertical pod autoscalers, node autoscaling, and the quota objects that bound a tenant. Disruption budgets are covered in T03, storage topology in T06, and the cloud-native extensions that add queueing and gang scheduling are mentioned only in passing.

## History and approaches

Scheduling at scale is older than containers. Borg priced resources with requests and limits and used priorities and preemption so that low-priority batch work could fill the gaps left by production services, and that vocabulary came directly into Kubernetes. The earliest Kubernetes scheduler was a simple predicate-and-priority pipeline: predicates filtered nodes, priorities scored them. Labels and node selectors came first, and were enough for a request to use only nodes with fast disks. They were too blunt for relations between pods, so affinity and anti-affinity arrived, along with taints and tolerations, which flip the direction of control: a node, not a pod, declares who may not land on it. Topology spread constraints followed when anti-affinity proved clumsy for spreading replicas evenly across zones. The scheduler was later rebuilt as a framework of plugins at defined extension points, which allowed profiles, custom scoring and out-of-tree schedulers, among them the second scheduler that KubeVirt documents for virtual machine placement.

On the demand side, autoscaling started with the Horizontal Pod Autoscaler driven by CPU utilisation, then extended to memory, custom and external metrics under the v2 API. The Vertical Pod Autoscaler recommends or applies request sizes. The Cluster Autoscaler added and removed nodes in cloud node groups when pods were unschedulable or nodes were idle, and the newer Karpenter project provisions nodes directly from pod constraints without pre-defined groups, which the Kubernetes node autoscaling documentation now treats as a general category: provisioning nodes that fit the pending pods' scheduling constraints. Event-driven scaling arrived through KEDA, which scales on queue length and other external signals, including scaling to zero.

Competing models shaped the thinking. Mesos' resource offers let frameworks pick, trading simplicity for flexibility. Slurm and other HPC schedulers think in queues, fair share and gang allocation, which Kubernetes lacked and has been approaching through Kueue and Volcano. Cloud instance groups and spot fleets scale machines by schedule or metric and know nothing about pods. The emerging pattern combines a rule-based placement language, priorities for triage, quotas for fairness and autoscalers that close the loop between pending pods and available nodes.

## Current state

**Requests, limits and QoS.** Each container may set a CPU and memory request and limit. The scheduler places pods using the sum of requests, never limits or live usage, and a node's allocatable capacity is its capacity minus system and kubelet reservations. At run time the kubelet maps these to kernel mechanisms: a CPU request becomes a relative weight in the control group hierarchy, a CPU limit a bandwidth quota that throttles the process when exceeded, a memory limit a hard ceiling whose violation triggers the out-of-memory killer. Pods are classified by their settings: Guaranteed when every container's requests equal its limits, Burstable when some request exists, BestEffort when none. When a node runs short of memory, the kubelet evicts in order of class and over-usage, and the kernel's OOM scores follow the same ordering, so a missing request is not harmless: it moves the pod to the front of the eviction queue. Namespaced LimitRange objects supply defaults and bounds, and ResourceQuota objects cap the sum of requests, limits and object counts per namespace.

**Placement language.** `nodeSelector` matches node labels exactly. Node affinity adds expressions and a split between required and preferred rules. Pod affinity and anti-affinity place a pod relative to other pods within a topology domain such as a node or zone; required anti-affinity across hostnames is the classic way to keep replicas on different machines, and the KubeVirt documentation on node assignment gives the same rules for virtual machines. Topology spread constraints state a maximum skew between domains, with a choice between refusing placement and merely preferring it. Taints repel pods from a node unless they carry a matching toleration; the three effects are NoSchedule, PreferNoSchedule and NoExecute, the last of which also evicts running pods, with `tolerationSeconds` to give them time. Kubernetes itself uses NoExecute taints to evict pods from unreachable nodes, and KubeVirt's node assignment guidance shows the combination of taints on dedicated nodes with tolerations on workloads that belong there. Node labels and taints together build dedicated pools such as GPU nodes, control-plane nodes and spot capacity.

**Priority and preemption.** A PriorityClass gives pods an integer rank. When a high-priority pod cannot be placed, the scheduler may preempt lower-priority pods to make room, respecting their grace periods. This is both the tool for protecting critical system pods and a hazard, because a high-priority workload can evict many pods. A related technique is overprovisioning: deliberately run low-priority placeholder pods that reserve headroom, which real workloads displace instantly, so the cluster has spare capacity without waiting for new nodes. The Kubernetes task on overprovisioning node capacity describes exactly this recipe.

**The scheduling cycle.** For each pending pod the scheduler filters the nodes (resources, ports, taints, selectors, volume topology, affinity), scores those left, and binds the pod to the best. Volume topology matters: a StorageClass with the binding mode that waits for the first consumer delays volume creation until a node is chosen, so that the volume is created where the pod will run rather than somewhere the pod cannot reach. Unschedulable pods retry with backoff, and the pod's events state which filters rejected which nodes, which is the first thing to read when a pod is Pending.

**Horizontal scaling.** The HorizontalPodAutoscaler runs in the controller manager. It reads metrics from the metrics API (served by the metrics-server add-on for CPU and memory, by adapters for custom metrics), computes the desired replica count from the ratio of current to target metric value, and updates the scale subresource of a Deployment or StatefulSet. It has stabilisation windows and rate limits (`behavior`) to avoid flapping. It requires resource requests, since utilisation is measured relative to the request. The Vertical Pod Autoscaler adjusts requests; combining it with an HPA on the same metric causes conflicts. In-place resource resizing for running pods is moving through the feature stages to avoid restarts (to verify the current stage).

**Node scaling.** When pods are Pending for lack of capacity, a node autoscaler adds nodes whose shape satisfies those pods' constraints, and removes underused nodes after draining them while honouring disruption budgets. The Kubernetes documentation states the constraint that matters: provisioning decisions are driven by pod scheduling constraints (resources, selectors, affinity, topology), so a pod whose rules no node shape can satisfy will never be fixed by scaling. Scale-down is conservative by default because it moves pods, and annotations let pods opt out.

**Quality of the signal.** Autoscaling is only as good as the metrics and requests under it. Requests set to defaults make the scheduler pack badly and the HPA misjudge. Requests set to peaks waste money. The usual cycle is to measure, set requests near typical usage, set memory limits equal to requests to avoid surprise kills, avoid CPU limits for latency-sensitive services because throttling hurts tail latency (a debated practice, to verify for your workload), and review with recommendations from the VPA in off mode.

## Assessment: the good, the bad and the ugly

The good: the placement language is rich enough to express nearly every real constraint, and it is declarative and visible. Requests plus quotas give multi-tenancy a sound basis. Priorities and preemption let a cluster run at high utilisation while still protecting critical services. The autoscalers close the loop, so a cluster can follow load without people in the loop.

The bad: the language is easy to misuse. Required anti-affinity at scale slows the scheduler, since each placement must check every other pod. Hard rules combine into unsatisfiable sets, and a Pending pod with eight constraints is a puzzle. Requests are guesses, and the scheduler treats guesses as facts, so utilisation looks full on paper while nodes idle. CPU limits and memory limits behave differently, which surprises people: exceeding the CPU limit slows a process, exceeding the memory limit kills it. Autoscalers react with delay: nodes take minutes to appear, so spikes must be absorbed by headroom.

The ugly: interactions. An HPA scaling up on a cluster without spare nodes only creates Pending pods. A node autoscaler removing a node that holds a pod without a budget causes an outage. A taint added to a node for maintenance without tolerations for the DaemonSets that matter silently removes logging or networking from it. Preemption cascades: a high-priority pod evicts a lower one, which cannot be placed, which preempts others in turn. Zones with unequal capacity make spread constraints behave oddly. Pods requesting more than any node's allocatable stay Pending forever with a clear event that nobody reads. And the memory accounting differences between the kubelet, the kernel and the application runtime (Java heaps, page cache counted against a cgroup) generate OOM kills that look random.

Mitigations: set requests on everything and enforce them with LimitRange and admission policy; prefer topology spread to hard anti-affinity; use PriorityClasses sparingly with a documented ladder; keep headroom with overprovisioning pods; test autoscaling with load; alert on Pending pods and on nodes whose requests exceed their usage by a wide margin.

## Applications beyond this domain

The scheduling problem is the generic bin-packing and constraint-satisfaction problem that appears in airline crew assignment, hospital operating-room scheduling and compiler register allocation; Kubernetes' filter-then-score design is a heuristic for it, valued because it is fast and explainable. The request-and-limit model matches how Linux services get resources from systemd slices and cgroups on a single host, as the kernel scheduling and resource-control material in the systemd and Red Hat documentation shows. Autoscaling control loops resemble thermostats and queue-length based capacity planning in telecommunications. Taints and tolerations are an access-control idea applied to capacity, comparable to firewall deny lists with exceptions. Priority with preemption is the model of real-time operating systems and of hospital triage.

## Examples

A three-replica web service that must survive a zone loss: a Deployment with CPU and memory requests, a topology spread constraint over the zone label with maximum skew one, a PodDisruptionBudget allowing one unavailable replica and an HPA targeting seventy percent CPU between three and twelve replicas. When load rises the HPA raises the replica count; pods that do not fit stay Pending; the node autoscaler adds a node in the zone with fewest pods; the spread constraint places new pods there.

A dedicated pool: GPU nodes tainted with a key and a NoSchedule effect, and only pods that tolerate the taint and request the device through a node selector and extended resource land there. A failing example: someone adds the toleration but not the selector, so ordinary pods with the toleration spread onto the expensive nodes. A taint keeps the wrong pods out; it does not attract the right ones.

A failing placement example: a pod stays Pending with the event that no node matched its volume node affinity. The StorageClass used immediate binding, the volume was created in one zone, and the pod's anti-affinity forced it into another. Waiting for the first consumer avoids the trap.

An OOM example: a container with a 512 MiB limit running a Java service reports exit code 137. The heap was sized to the node's memory, not the container's, and the kernel killed the process at the limit. Setting the runtime to respect the cgroup limit fixes it.

## Related problems and ideas

Batch and machine-learning workloads need gang scheduling (all or none), queueing and fair share, provided by Kueue, Volcano and similar projects. Descheduler evicts pods that have drifted into a poor arrangement after the cluster changed. Topology-aware scheduling for NUMA, CPU pinning and device topology is provided through the kubelet's CPU, memory and topology managers, and through dynamic resource allocation for GPUs. Scheduling virtual machines on Kubernetes (the virtualisation engineering course) uses the same rules with live migration as an additional lever. Multi-cluster schedulers, such as Karmada or Open Cluster Management placement, apply the same ideas across clusters. A different philosophy, used by some serverless platforms, hides placement completely and bills per invocation.

## Active research

Open questions include dynamic resource allocation as the general model for devices and shared accelerators, in-place pod resizing and its interaction with schedulers and autoscalers, scheduler throughput for clusters with very many pods, better bin-packing and consolidation algorithms for node autoscalers, carbon-aware and cost-aware scheduling, and learning-based prediction of demand. Researchers compare Borg-trace workloads with newer traces, and the scheduling special interest group evaluates plugin APIs for scoring and queueing. HPA research looks at predictive scaling and smoother behaviour policies.

## Future direction

Expect gang and queue semantics to become more standard in the batch ecosystem, dynamic resource allocation to replace device plugins for many use cases, and node autoscaling to converge on pod-constraint-driven provisioning as the default, with managed services exposing it. Resource resizing without restart should reduce the need for over-requesting. For the administrator, the durable habits are to measure real usage, to treat requests as a contract, and to test the failure and scaling paths before an incident does (to verify the stage of each feature in your release).
