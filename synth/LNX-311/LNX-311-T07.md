# Who may do what to the cluster: identities, permissions and the certificates that prove them

## Define the problem

The Kubernetes API is the control surface for everything in the cluster. Whoever can write to it can start containers on any node, read every Secret, and reconfigure the network. A cluster serves many different callers: human administrators, developers who should touch only their own namespace, continuous-delivery systems, controllers inside the cluster, node agents and workloads that need to ask the API a question. Each needs exactly the access its job requires. Too little and the pipeline breaks; too much and a stolen token or a bug in one application becomes control of the whole cluster.

Three separate questions have to be answered for every request. Who is calling (authentication)? Are they allowed to do this to this object (authorisation)? And, before the object is stored, is the request acceptable (admission, covered in the security course)? The first question has no single built-in answer in Kubernetes: there is no user database. Identities come from client certificates, tokens signed by the cluster, or an external identity provider, and the API server has to trust each of those sources. The second question has a built-in answer, role-based access control, but its power makes it easy to misconfigure.

The cluster's own components also authenticate to each other with certificates, and those certificates expire. A cluster that nobody has upgraded for a year is one day away from a total outage when the certificates of the API server and kubelets lapse together. This slice covers authentication sources, the service account mechanism, RBAC objects and their evaluation, practical least-privilege design and auditing, and the public key infrastructure of a kubeadm cluster including certificate signing requests and renewal. Hardening beyond RBAC is in the Kubernetes security course.

## History and approaches

Early Kubernetes authorisation was crude. A static password file and an attribute-based policy file, read at startup, mapped users to coarse permissions, and changing a rule meant restarting the API server. RBAC, introduced as alpha in version 1.3 and generally available in 1.8, replaced it with API objects that could be created, reviewed and audited like any other resource, and kubeadm made it the default. Attribute-based access control was deprecated, and webhook authorisation remained for integrations with external policy engines. Authorisation modes are chained: the API server asks each configured authoriser in order and takes the first decision other than "no opinion", and the Node authoriser, which restricts kubelets to the objects of pods bound to their own node, runs alongside RBAC.

Service accounts started as long-lived tokens stored in Secrets, mounted into every pod by default. That model leaked: a token never expired, was valid anywhere the API server was reachable and lived on in backups. The 1.12 to 1.22 releases introduced projected, bound tokens, issued through the TokenRequest API, tied to a particular pod and audience, short-lived and refreshed by the kubelet. Starting in 1.24 the controller stopped auto-creating the old Secret-based tokens. The documentation now describes service accounts as the identity of a workload and lists assignment of one to a pod through its spec as the standard route.

Human authentication varied. Client certificates were the simplest, supported from the start and used by kubeadm's admin kubeconfig, but they cannot be revoked short of replacing the certificate authority, a weakness that makes them poor for people. Static token files were similarly crude. OpenID Connect integration lets the API server trust an identity provider's signed tokens, with groups carried in claims, and is the usual choice for people in organisations that have one. Proxy authenticators and webhook authenticators serve managed platforms. Cloud services map their own identity systems, such as IAM roles, onto Kubernetes identities in their managed offerings.

For certificate management, the first generation was entirely manual, as in the Kubernetes the Hard Way tutorials, where the learner creates a certificate authority and signs each component's certificate by hand with a tool such as cfssl or openssl. kubeadm automated the standard set and added renewal commands. The certificates API (CertificateSigningRequest objects) gave the cluster a way for approved requests to be signed by the controller manager, which is how kubelets obtain their serving certificates and how an administrator can issue a certificate for a user. Outside the core, cert-manager grew into the standard way to issue and renew certificates for workloads from ACME servers and internal authorities.

The pattern that emerged is: identities are cheap to create and short-lived, permissions are additive and attached to roles instead of people, groups come from outside, and the cluster's own certificates are managed by tooling with an expiry calendar.

## Current state

**Authentication.** Every request carries a credential. The API server tries its configured authenticators and, when one succeeds, derives a username, a set of groups and optional extra fields. Authenticators include X.509 client certificates (the common name becomes the user, the organisation fields become groups), bearer tokens, service account tokens, OIDC tokens and webhook authentication. A request that matches none is anonymous, and the API server can reject anonymous requests entirely; the Kubernetes STIG includes findings on anonymous access and on the authentication modes enabled. Each authenticator can be switched on or off with API server flags or, in newer releases, through an authentication configuration file.

**Authorisation and attributes.** The request is described by attributes: user, groups, the verb (the read verbs, the write verbs, bulk deletion, plus special ones such as impersonate, bind and escalate), the API group, resource, subresource, namespace and name, or a non-resource URL. The Kubernetes documentation on authorisation lists how HTTP methods map to verbs, with a nuance worth remembering: `list` and `watch` on secrets return the contents, so a role that grants only list on secrets still discloses them. Authorisation modes are set by the `--authorization-mode` flag, normally `Node,RBAC`.

**RBAC objects.** A `Role` contains rules (API groups, resources, verbs, optionally resource names) within one namespace. A `ClusterRole` does the same cluster-wide and for non-namespaced resources, and can be bound within a single namespace to reuse its rules. A `RoleBinding` connects a Role or ClusterRole to subjects (users, groups, service accounts) within a namespace; a `ClusterRoleBinding` does it for the whole cluster. RBAC is purely additive, with no deny rules, so the effective permission of a subject is the union of all bindings. Aggregated ClusterRoles combine rules from labelled roles, which is how the built-in `admin`, `edit` and `view` roles pick up permissions for custom resources. The default roles include `cluster-admin`, which grants everything and should be bound to as few subjects as possible, and system roles used by components. Rules cannot be escalated: to create a role you must already hold its permissions, unless you hold the special `escalate` and `bind` verbs.

**Service accounts.** Each namespace has a `default` service account that pods use unless told otherwise. A pod chooses another through `serviceAccountName`, and can opt out of getting API credentials with `automountServiceAccountToken: false`. The kubelet requests a projected token for the pod, with an audience and an expiry, and mounts it as a file that it refreshes. A service account can be bound to roles like any other subject, and the principle of least privilege says to create a dedicated service account per workload, not to extend the permissions of `default`. When an external system needs a long-lived token, a Secret of the service-account-token type can still be created explicitly, but the documentation positions that as a last resort.

**Testing permissions.** `kubectl auth can-i VERB RESOURCE --as USER -n NAMESPACE` asks the API server for a decision, `kubectl auth whoami` shows the identity the server derived, and `kubectl auth can-i --list` shows what a subject may do in a namespace. Tools such as `rbac-lookup`, `kubectl-who-can` and audit-log analysis show reverse relationships, such as who can read secrets.

**Cluster PKI.** A kubeadm cluster holds a main certificate authority, a separate one for etcd and a front-proxy authority, under `/etc/kubernetes/pki`. It issues the API server's serving certificate (with subject alternative names for every address clients use), the API server's client certificates for etcd and for the kubelets, the controller manager and scheduler credentials embedded in kubeconfig files, and the admin kubeconfig. Leaf certificates last a year by default and authorities ten. `kubeadm certs check-expiration` lists the dates and `kubeadm certs renew all` renews them, after which the control-plane static pods must be restarted to load the new files. `kubeadm upgrade` renews them as a side effect. Kubelet client and serving certificates are rotated by the kubelet itself when rotation is enabled, using the certificates API.

**CertificateSigningRequests.** The `certificates.k8s.io` API lets a requester submit a PEM-encoded request with a requested signer and usages. An approver (a human with the right permission or an automated controller) approves it, and the controller manager's signer issues the certificate, which the requester retrieves from the object's status. The documentation also describes the built-in signers for kubelet client and serving certificates and the legacy unknown signer, and warns that the cluster signer's trust is broad, so approval permission is sensitive. To create a user who authenticates with a certificate, the standard recipe is to generate a key and request, submit a CSR, approve it, and bind a role to the user name in the certificate.

**Hardening notes.** The STIG checks that the API server and kubelet use client certificate authentication, that anonymous authentication is disabled where it is not needed, that RBAC is enabled, and that Secrets and kubeconfig files have restrictive permissions. These checks correspond to common real incidents.

## Assessment: the good, the bad and the ugly

The good: RBAC is declarative, uniform and auditable. Short-lived bound tokens close the worst leakage route. The same model covers humans, workloads and components, and `can-i` makes it testable. The certificates API provides a standard path for issuing credentials without handing the CA key around.

The bad: RBAC is easy to over-grant. Wildcards on verbs and resources, bindings to the `system:authenticated` group and use of `cluster-admin` as a convenience are common in tutorials and survive into production. Because there are no deny rules, one broad binding cannot be overridden. The permission model is also hard to review: effective access is the union across many bindings and aggregated roles, so finding every subject able to read secrets in a namespace takes tooling. Client certificates cannot be revoked, so a leaked admin kubeconfig remains valid until it expires or the authority is replaced. Unexpected escalation routes exist: the ability to create pods in a namespace grants access to every service account and Secret in that namespace by mounting them; permission to create role bindings or to impersonate others is administrator in disguise; permission to read nodes' proxy subresource can reach kubelets.

The ugly: expiry. A cluster created a year ago with kubeadm and never upgraded loses its control-plane certificates at the same time, the API server cannot talk to etcd or kubelets, `kubectl` itself fails because the admin certificate expired, and the recovery must be done from the node with files and static pods. Service account token changes have broken integrations that relied on old non-expiring tokens. Default service accounts were historically given too much by add-ons. Groups from OIDC tokens are trusted exactly as asserted, so a misconfigured identity provider mapping adds users to `system:masters`, a group that bypasses authorisation altogether.

Mitigations: set expiry reminders and renew or upgrade at least yearly; give each workload its own service account without extra rights and disable token automounting where the API is not used; bind roles to groups from the identity provider, not to individual users; never bind cluster-admin broadly; review bindings with tooling and audit logs; test least privilege with `can-i --as`; restrict who may create roles, bindings and certificate approvals; use short-lived credentials for people.

## Applications beyond this domain

Role-based access control predates Kubernetes by decades: the NIST RBAC model of the early 1990s, and the access-control rules in Identity Management as described in the Red Hat documentation, which also manages users, groups, hosts and access rules with explicit role-like constructs. Cloud providers' IAM policies are attribute- and role-based and use the same additive logic, with explicit deny added. The projected, audience-bound token follows the OAuth and OpenID Connect pattern of short-lived, scoped credentials, and workload identity federation with cloud providers reuses it. The certificate signing flow is the same as in any enterprise public key infrastructure: a request, an approval step and issuance by an authority, as in Active Directory Certificate Services or the FreeIPA stack covered in the enterprise course. Rotation and expiry calendars are the same operational concern in TLS for web servers and in code-signing keys.

## Examples

A read-only developer role for one namespace: a Role granting `get`, `list` and `watch` on pods, services, deployments and their logs, a RoleBinding to the group `team-a-dev` from the identity provider, and a test with `kubectl auth can-i delete pods --as dev --as-group team-a-dev -n team-a`, which must answer no.

A user certificate: generate an RSA or elliptic-curve key, create a certificate request whose subject carries the user name and group, submit it as a CertificateSigningRequest with the client-authentication usage and the kube-apiserver client signer, approve it with `kubectl certificate approve`, fetch the signed certificate and add it to a kubeconfig. Bind a role to the name. The certificate is valid for the period requested and cannot be revoked early, so keep it short.

A failing example: a CI pipeline uses the default service account with a binding to `edit` at cluster level added years ago. A compromised build job reads every namespace's Secrets. The remedy is a per-pipeline service account bound only in the target namespace, with token automounting disabled in jobs that do not call the API.

A second failing example: on the anniversary of cluster creation, every `kubectl` call returns a certificate-expired error. The administrator logs in to a control-plane node, runs `kubeadm certs check-expiration`, renews with `kubeadm certs renew all`, restarts the control-plane static pods by moving their manifests out and back, copies the refreshed admin kubeconfig and recovers; afterwards puts a calendar alert at thirty days before expiry.

## Related problems and ideas

Policy as code layers on RBAC: OPA Gatekeeper and Kyverno decide what may be created, not only who may create it. Fine-grained alternatives include attribute-based and relationship-based authorisation such as Zanzibar-style systems (OpenFGA, SpiceDB) and cloud IAM conditions. SPIFFE and SPIRE offer workload identities independent of the cluster for use across clouds. Short-lived credentials for people, through OIDC with device flow and tools such as kubelogin, avoid long-lived kubeconfigs. Multi-tenancy frameworks (virtual clusters, hierarchical namespaces) reduce the permissions one tenant needs. Certificate revocation remains weak; ideas include very short certificate lifetimes with automatic renewal instead of revocation lists.

## Active research

The auth special interest group works on structured authentication configuration, on extending authorisation to more attributes (field and label selectors in requests), on better workload identity binding such as tokens bound to node identity and on making certificate rotation of control-plane components fully automatic. Security researchers publish analyses of RBAC misconfiguration in public clusters and of privilege-escalation chains via workload permissions, and tools to visualise them. The question of how to make client certificates revocable or obsolete, and how to support external key stores, remains open (to verify the stage of each feature in your release).

## Future direction

Expect further reduction of long-lived credentials: bound, audience-scoped tokens everywhere, human authentication through the organisation's identity provider, and automated rotation of the cluster's own certificates. Authorisation will gain richer attributes and a configuration file model to replace flags. Managed platforms will keep integrating cloud identity into pod identity, which makes the question of mapping external roles to Kubernetes roles part of every design review. For an administrator the stable core remains least privilege through additive roles, a calendar for certificate expiry and regular review of who can do what.
