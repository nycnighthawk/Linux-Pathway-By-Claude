# Finding the broken layer: a method for troubleshooting Kubernetes

## Define the problem

A Kubernetes symptom rarely names its cause. A pod that never starts can be waiting on a scheduler decision, a node that is not ready, an image that cannot be pulled, a volume that will not mount, a secret that does not exist, a network plugin that has not assigned an address or an admission webhook that rejected the request. A Service that does not answer can be a missing selector, a pod failing its readiness probe, a rule not programmed on the node, a DNS answer that is wrong or a policy that blocks the traffic. The same words, "it does not work", map to a dozen layers owned by different components, and the tools at each layer differ.

The cluster's own design makes this both easier and harder. Easier, because everything is an object with a status, events and logs, and the API is uniform. Harder, because the layers stack: applications depend on pods, which depend on nodes, which depend on the kubelet, the container runtime, the network plugin and the control plane, which depends on etcd and certificates. When the API server itself is down, the main troubleshooting tool, `kubectl`, is gone, and the investigator must work from the node with systemd, the runtime and files.

This slice teaches a layered method and the commands and signals of each layer: application and pod, workload controllers, scheduling, nodes and the kubelet, container runtime, networking and DNS, storage, the control plane and etcd. It aims at the skills an administrator exam and a night shift both test: a fixed order of questions, quick reading of status and events, and knowing which logs exist where. Specific subsystems have their own slices (networking in LNX-312, security in LNX-314); this is the cross-cutting discipline.

## History and approaches

Early Kubernetes troubleshooting relied on `kubectl logs` and `kubectl describe`, with the cluster's behaviour largely opaque. Events, short-lived records the API server keeps for about an hour by default, were the main narrative of what controllers had done. Over time the project added structured conditions on nodes and pods, readiness gates, termination messages, probe results, ephemeral containers that let an operator attach a debugging container to a running pod without restarting it, and `kubectl debug` to create copies of pods or open a privileged shell on a node. Node problem detector turned kernel and runtime symptoms into node conditions and events. `crictl`, introduced with the container runtime interface, gave operators a runtime-neutral way to list containers and read logs on a node when the API is unavailable.

Approaches to diagnosis have competed. The *top-down* method starts with the user-visible symptom and walks inward: pod, Service, ingress, node, control plane. The *bottom-up* method checks infrastructure first: nodes ready, control plane healthy, DNS and network functioning. Practitioners converge on a divide-and-conquer hybrid: take the symptom, decide whether it is a problem of one object, of one node or of the whole cluster by comparing healthy and unhealthy instances, and then go deep in that area. Separately, observability stacks (metrics, logs and traces gathered centrally) replaced `ssh` and `grep` for many failures, and runbooks, game days and chaos testing became ways to rehearse. The kubeadm project's own troubleshooting guide collects the typical install-time failures, such as waiting for the control plane forever or a kube-proxy that was scheduled before the cloud provider initialised the node, which shows how many failures come from ordering and environment rather than from Kubernetes itself.

Environment-specific guides add detail. The Arch Wiki's Kubernetes page lists real issues, such as CoreDNS looping on a self-referencing resolver, a node remaining NotReady until a CNI plugin is installed and pod-to-pod failures under one network plugin with a particular firewall service. KubeVirt's review documents a day-two troubleshooting phase for virtual machines on the platform, and Cilium publishes troubleshooting for its BGP control plane. Windows nodes bring their own guide with different rules for networking and logging. The common lesson is that after a certain depth, the answer lives in a component's documentation, so the generic method must lead you to the right component quickly.

## Current state

**A first pass, in order.** Establish the scope: one pod, one workload, one node, one namespace, the whole cluster. Then check, from the outside in:

1. `kubectl get pods -A -o wide` and look at status, restarts, node placement and age.
2. `kubectl describe pod NAME` and read the events at the bottom and the container state, last state and exit code.
3. `kubectl logs NAME -c CONTAINER` and `--previous` for a crashed container.
4. `kubectl get events -A --sort-by=.lastTimestamp` for recent cluster narrative.
5. `kubectl get nodes` and `kubectl describe node` for conditions (Ready, MemoryPressure, DiskPressure, PIDPressure, NetworkUnavailable), capacity and allocated resources.
6. `kubectl get --raw='/readyz?verbose'` for the API server's own checks.

**Pod states and what they mean.** *Pending* with no node: scheduling failed; the event lists the filters (insufficient resources, taints, affinity, unbound claims). Pending with a node: the kubelet is working on it. *ContainerCreating* for long: image pull, volume attach or mount, or CNI sandbox creation; the events name which. *ImagePullBackOff* or *ErrImagePull*: wrong name or tag, missing credentials, registry unreachable or rate limited. *CrashLoopBackOff*: the container starts and exits; read previous logs and the exit code (small codes are application errors, 137 means a kill by signal 9, often the kernel memory killer, and 143 means a polite termination request). An out-of-memory reason in the last state, with code 137, points to the memory limit. *Running but not Ready*: the readiness probe fails; check the probe path and port, and the container's own logs. *Evicted* or *Terminating* forever: node pressure thresholds were hit, a finalizer is stuck or the node is unreachable.

**Debugging inside a pod.** `kubectl exec -it POD -- sh` works only if the image has a shell. For minimal images, `kubectl debug -it POD --image=busybox --target=CONTAINER` adds an ephemeral container that shares the target's process namespace, and `kubectl debug POD --copy-to=copy --container=app --image=...` makes a modified copy to experiment with. `kubectl port-forward` tests a pod or Service from your machine, and a throwaway pod with `curl` and `nslookup` tests the network from inside the cluster, which separates "the app is broken" from "the network path is broken".

**Services and DNS.** A Service with no endpoints has a selector that matches no ready pods: `kubectl get endpointslices -l kubernetes.io/service-name=NAME` shows who is behind it. Compare `kubectl get svc -o yaml` selectors with pod labels. Test DNS with a debug pod: the resolver configuration, the CoreDNS pods in the system namespace, and whether the cluster DNS Service has endpoints. The Arch Wiki's note on a CoreDNS loop shows a classic cause: the node's resolver file points at a local stub that loops back to CoreDNS, which the kubelet should replace with a clean resolver file.

**Nodes and the kubelet.** A node that is NotReady or Unknown has either lost contact with the API server (network, certificate, kubelet down) or is reporting a problem. On the node: `systemctl status kubelet` and `journalctl -u kubelet -e` are the primary sources. Frequent findings: the container runtime socket is unavailable; the kubelet and the runtime disagree on the cgroup driver; the node's clock is skewed so certificates look invalid; swap is on; the kubelet's client certificate expired or could not rotate; the node ran out of disk and the kubelet garbage-collects images and evicts pods under thresholds; PID or memory pressure triggered evictions; or the CNI configuration is missing so NetworkUnavailable stays true. The kubeadm troubleshooting guide covers the install-time variants and the case of a kubelet that cannot start because of certificate or configuration mismatches.

**The runtime.** `crictl ps -a`, `crictl pods`, `crictl logs ID`, `crictl inspect`, `crictl images` and `crictl info` talk to the same socket as the kubelet and work when the API server is unavailable. If `crictl` itself cannot connect, the runtime is down or its endpoint is misconfigured; check `systemctl status containerd` and its journal. Pod sandbox creation errors usually point to CNI.

**Network layer.** When pods on different nodes cannot reach each other, test in steps: pod to its own node, pod to another pod on the same node, pod to a pod on another node by address, then by Service. At each step the failure points to a layer: local CNI, the inter-node path (routing, tunnel, firewall, MTU), or kube-proxy and policies. The Arch Wiki records a case where a firewall service interfered with flannel; the principle is that the host's firewall and the cluster's packet rules both matter. Cilium's BGP and policy troubleshooting pages show plugin-specific diagnostics that follow the same ladder.

**Control plane.** If `kubectl` hangs or errors: check the API server endpoint and certificate expiry from the client; then on a control-plane node use `crictl ps` to see whether the static pods run, and read their logs through the runtime path described in the cluster troubleshooting documentation, which gives the locations of control-plane logs for both systemd-managed and container-managed setups. Controller manager and scheduler are healthy if their leader leases update (`kubectl -n kube-system get lease`). For etcd, `etcdctl endpoint health` and `endpoint status` with the client certificates show members, leader and database size, and the alarm list shows NOSPACE. Slow disks appear as warnings in the etcd log about slow fsync and as leader elections.

**Metrics and audit.** `kubectl top nodes` and `kubectl top pods` need metrics-server. The API server's request metrics (latency by verb, errors by code) and the audit log answer "who changed this and when", which is the usual question after an outage with no obvious cause. Admission failures are visible in the response to the user's request and in the API server log.

## Assessment: the good, the bad and the ugly

The good: the uniform object model and rich status mean most application problems are diagnosable from `kubectl` alone in minutes, and the event stream gives a narrative that other systems lack. `kubectl debug` and ephemeral containers solved the long-standing problem of debugging distroless images. The same method works across clusters and distributions, and the CKA-style practice of working through a fixed list of questions builds speed.

The bad: events expire after about an hour and are not guaranteed, so evidence disappears; logs of a deleted pod vanish unless collected centrally. Messages are sometimes unhelpful or misleading: a pod reports `Unschedulable` with a list of filter counts that needs careful reading, and a mount failure may show only a timeout. Failures in the control plane can make the investigative tool unavailable. Different layers use different tools and log locations, and managed services hide the control plane completely, so some steps are impossible and the provider's support must be involved.

The ugly: intermittent and cascading faults. A node under memory pressure evicts pods, which reschedule and load other nodes, which evict in turn. A DNS service saturated by `ndots` search-path expansion makes everything slow rather than broken. Conntrack table exhaustion drops connections only under load. Clock skew breaks certificates in ways that look like random authentication failures. A noisy neighbour or a throttled CPU limit causes latency without any error. Misdiagnosis is common: people restart pods and nodes, which clears symptoms and destroys evidence, and the problem returns.

Mitigations: use a written ladder and follow it; capture state before restarting (describe output, logs with `--previous`, a node's journal); ship events and logs centrally; monitor node conditions, restarts, pending pods, API latency and etcd health; keep a debug image and a node access path ready; rehearse control-plane failure with the API down; keep time synchronised and certificate expiry on a calendar.

## Applications beyond this domain

Layered fault isolation is the same method used in network operations (the OSI ladder), in site reliability engineering (the USE and RED methods: utilisation, saturation and errors per resource; rate, errors and duration per service) and in medicine (differential diagnosis: common causes first, then compare the sick with the healthy). The tools translate: `crictl` is to the runtime what `ip` and `ss` are to the network, `journalctl -u kubelet` is the same service-log reading as for any systemd unit in the enterprise course, and `kubectl debug node` is the container-era equivalent of a rescue shell. The practice of capturing evidence before remediation is general incident response: take the dump before the reboot.

## Examples

*A pod in CrashLoopBackOff.* The describe output shows the previous container run ended with an out-of-memory reason and code 137 against a 256 MiB limit. `kubectl top pod` shows usage near the limit. The fix is to raise the limit or fix the leak; a rollout with a larger limit and a watch on memory confirms it.

*A Service with no traffic.* `kubectl get endpointslices` shows no endpoints. The Service selector says `app: web` while the pods carry `app: webapp`. Correct the selector and traffic flows. A second variation: endpoints exist but are not ready because the readiness probe uses the wrong port.

*A NotReady node.* `kubectl describe node` shows Ready False, kubelet stopped posting status. On the node, `journalctl -u kubelet` reports failure to connect to the runtime socket; `systemctl status containerd` shows a failed unit after a configuration change that set the wrong cgroup driver. Fix the configuration, restart containerd and the kubelet and the node returns, while the pods that were bound there are recreated or recover according to their controllers.

*The API is down.* On the control-plane node, `crictl ps -a` shows kube-apiserver exited; its log says a certificate has expired. The fix is the renewal procedure from the access control slice, followed by restarting the static pods.

*Intermittent DNS failures.* Pods resolve names slowly. A debug pod shows many search-domain lookups per name; CoreDNS shows high load. Lower `ndots` in the pod's `dnsConfig` or use fully qualified names with a trailing dot, and consider node-local DNS caching.

## Related problems and ideas

Observability platforms (Prometheus, Loki, OpenTelemetry, Hubble) turn troubleshooting from interactive to retrospective, answering questions about the past. Automated root-cause analysis and AI assistants such as k8sgpt try to translate symptoms into causes; their output should be verified against evidence. Chaos engineering tools (Chaos Mesh, Litmus) inject failures to test detection and recovery. Time-travel debugging with eBPF captures syscalls and network flows without modifying workloads. Policy and static analysis (Kubescape, kube-linter, `kubectl-neat`) catch misconfigurations before deploy. The idea that clusters should be disposable, replaced by rebuilding instead of repaired, reduces troubleshooting for nodes but not for applications.

## Active research

Work in progress includes better pod and node lifecycle conditions that explain delays (for example pod readiness gates and scheduling readiness), richer events and the move to a new events API with longer retention, structured logging and contextual logging in Kubernetes components so logs can be correlated, tracing of API server and kubelet requests with OpenTelemetry, and improved `kubectl debug` profiles for nodes and hardened environments. Researchers study failure injection and incident data to understand why misconfigurations and upgrades cause outages, and build tools that simulate control-plane behaviour to predict cascades (to verify the feature stages in your release).

## Future direction

Expect more of the cluster's reasoning to be exposed as structured status, so tools can explain why a pod is Pending in plain terms, and tracing to become a standard part of the control plane. Managed platforms will hide more layers but also surface richer diagnostics through their consoles. The administrator's skills remain the method: narrow scope, read status and events, go layer by layer, collect evidence before acting, and change one thing at a time.
