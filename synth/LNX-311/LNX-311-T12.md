# When the cluster is big and old: scale limits, fleet management and surviving years of upgrades

## Define the problem

Most Kubernetes skills are learned on clusters of three to ten machines that are rebuilt whenever something goes wrong. Production reality is different in two directions at once. Some clusters grow to hundreds or thousands of nodes and hundreds of thousands of objects, where the control plane's own limits, the network's behaviour and the sheer number of moving parts change what is possible. Other clusters grow old: they were created years ago, have been upgraded through many minor versions, carry the sediment of past operators, abandoned custom resources and half-remembered workarounds, and are too important to rebuild casually.

The two problems share a character. They are problems of accumulation, not of mechanism: nothing in the daily operation is hard, but small inefficiencies or small risks multiply by the number of nodes, objects or years. An API call that costs a millisecond is fine until ten thousand controllers make it every second. A manual upgrade that takes an afternoon becomes a quarter's work across forty clusters. A deprecated API that nobody used for two years suddenly gates the next upgrade.

This slice is at awareness depth. It names the scale dimensions and the published limits, the parts of the control plane that saturate first, the techniques for operating fleets (many clusters) rather than single clusters, and the habits that keep a cluster upgradable for years. It does not teach tuning of any specific component in detail. It prepares the administrator to ask the right questions when a cluster grows past the sizes that tutorials assume.

## History and approaches

Early Kubernetes was explicit about its limits. The project's scalability work, driven by a special interest group, published thresholds that clusters are tested against: on the order of five thousand nodes, around one hundred and fifty thousand pods and a few hundred thousand containers, with per-pod and per-node ceilings and service-level objectives for API call latency and pod startup time (to verify the current figures on the project's scalability page). Teams that went beyond such numbers, such as large cloud customers and machine-learning platforms, published their experience: running many thousands of nodes required changes to etcd settings, API server flags, kubelet behaviour and networking, and sometimes moved large single clusters back to several smaller ones. Google has described managed clusters well above the tested thresholds for its own offering, using custom storage and control-plane changes that are not available to self-managed users.

Two strategies compete. *Scale up* keeps a single large cluster: it simplifies scheduling and service discovery, and fits workloads such as large training jobs that need many nodes in one network domain. It requires deep control-plane tuning, and the blast radius of any failure is the entire fleet. *Scale out* uses many smaller clusters: it limits blast radius, makes upgrades gradual and matches organisational boundaries, and it moves complexity into fleet management, multi-cluster networking and consistent configuration. KubeVirt's review for incubation describes its own scale approach through per-node components and distribution of work to the node, an example of designing components so that the central controller does not become the bottleneck as nodes multiply. The enterprise high-availability world took a different path: Pacemaker clusters, covered in the Red Hat high-availability documentation, are limited to small node counts by design, with fencing and quorum protocols that do not scale to hundreds of members, which illustrates why an orchestrator for thousands of nodes needed a different architecture built around a database and stateless controllers. At the other extreme, batch schedulers for supercomputers, such as Slurm, handle tens of thousands of nodes with a central controller, and the Rocky Linux documentation on deploying it shows how differently that world models resources, with allocations, queues and a controller that has no pod-style churn.

For upgrades over time, the first approach was the in-place rolling upgrade described earlier in the course, repeated every minor release. The accumulation of skew and deprecated APIs pushed teams toward alternatives: rebuild-and-migrate (blue-green clusters), immutable node images and cluster lifecycle controllers such as Cluster API, which roll machines declaratively. The kubeadm upgrade documentation describes the control-plane upgrade as a sequence that rewrites the static pod manifests and renews certificates, and that sequence is the building block the fleet tools automate. Compliance regimes added their own pressure: the STIG for Kubernetes includes findings about patch levels and supported versions, tying upgrade discipline to audit.

The pattern: bounded objects and bounded blast radius, automation of everything repeated, and a standing cadence of change so no upgrade is ever a big-bang event.

## Current state

**Where the control plane saturates.** Four resources tend to run out in a large cluster. First, etcd: write throughput and database size, with a recommendation to keep the dataset within a few gigabytes and to place etcd on fast, dedicated disks; some operators run a separate etcd for high-churn objects such as events. Second, the API server: list and watch operations that return large result sets, especially unpaginated or uncached lists, and controllers that poll; the watch cache and API priority and fairness features (which classify and queue requests so that one noisy client cannot starve others) mitigate it. Third, the controllers and scheduler: scheduler throughput is bounded, and the endpoint machinery (EndpointSlices rather than the old Endpoints object) was introduced to avoid sending huge updates for services with thousands of pods. Fourth, the nodes themselves: kubelet heartbeats are now lightweight lease updates instead of full status writes, which removed a large share of write load.

**Network and add-ons at scale.** Per-node components multiply. DaemonSets for networking, logging, monitoring and security each consume resources on every node and watch the API. kube-proxy in iptables mode has rule counts that grow with services and endpoints, making updates slow, which is why IPVS, nftables and eBPF replacements exist (the networking course covers them). DNS load rises with pod count, and node-local caching helps. The CNI's IP address management must have enough ranges per node, and cloud limits on routes, addresses and load balancers become constraints. Cilium documents scalability dimensions of its own, such as identity counts and the choice between different IPAM modes, and notes the multi-pool mode that lets clusters allocate pod addresses from several pools, which becomes useful when a cluster outgrows its original address plan.

**Operational limits that are about people.** At hundreds of nodes the probability that some node is failing at any moment is close to one. Hardware faults, kernel bugs, disk failures and network flaps are routine events, so operations become a pipeline: detection through node conditions and node problem detector, automatic cordon and drain, repair or replacement, and a ticket only for unexplained repeats. Fleet changes go through progressive delivery: canary a handful of nodes or one cluster, observe, then widen.

**Operating a fleet of clusters.** Practices include creating clusters from one declarative template (Cluster API, Terraform modules, managed-service APIs); managing add-ons and policy with GitOps from a single repository with per-cluster overlays; standardising versions into at most two or three supported minors; central observability that aggregates metrics and logs from all clusters; and a catalogue that records each cluster's owner, version, support end and add-on versions. Multi-cluster service discovery and traffic management (the Cilium Cluster Mesh feature covered in the networking course, service meshes with multi-cluster support) are optional layers on top.

**Keeping a long-lived cluster upgradable.** The disciplines are few and learnable. Upgrade every release, or at most every second, because skew limits and deprecation windows are calibrated to that rhythm. Track API deprecations continuously, with a scan in CI and the API server's metric of deprecated API requests. Keep add-on versions current and inside their compatibility tables, such as the Kubernetes version ranges that the network plugin publishes. Keep infrastructure as code so that the cluster could be recreated, and test recreation, because recreation is the fallback when an in-place upgrade fails. Keep a staging cluster that mirrors production in kind and number of add-ons. Clean up: delete unused CRDs, namespaces, orphaned PersistentVolumes and old API objects stored in earlier versions, and run the storage version migration for custom resources before dropping an old version. Rotate certificates on schedule. Retire nodes by age so that no machine lives longer than a bounded lifetime, which keeps drift and surprise low.

**Dynamic resources and new scheduling needs.** Large clusters increasingly run accelerators. The cluster-administrator guidance for dynamic resource allocation highlights that drivers and their resource slices add API objects and scheduling work and need attention to quotas and to driver upgrades, an example of new per-node data growing the control plane's load.

## Assessment: the good, the bad and the ugly

The good: Kubernetes' architecture does scale to thousands of nodes with known tuning, and the project invests in scalability tests and fixes. Techniques for fleets are mature: declarative cluster lifecycle, GitOps and progressive rollout. A disciplined cadence of small upgrades is cheap, predictable and safe.

The bad: published limits are tested for specific workload shapes; real workloads (many small services, heavy use of custom resources, lots of short-lived pods) hit limits earlier. Single large clusters concentrate risk, and tuning knowledge is specialised and fragile across versions. Multi-cluster adds networking, identity and configuration drift problems. A fleet makes each decision multiply: one bad add-on version is deployed everywhere. Observability and event data for large clusters is itself a scale problem and a major cost.

The ugly: slow accumulation. A cluster upgraded in place for five years has stored objects in old API versions, manual patches whose reason is forgotten, a CNI configured for a topology that no longer exists, and nodes of five different OS images. Its upgrade is a project nobody wants, so it is postponed, so it falls out of support, so it becomes riskier; this is the compounding cost of deferring maintenance. Another ugly area is cascading failure at scale: a restart of all nodes' kubelets at once produces a thundering herd of re-lists that overloads the API server, and a bad controller that writes in a loop fills etcd; a mass node event storm can take down the control plane that was meant to repair it. Operators of very large clusters protect themselves with API rate limits, priority and fairness configuration and staged rollouts.

Mitigations: set explicit budgets for object counts and watch growth; apply API priority and fairness to protect system traffic; run etcd on dedicated fast disks and monitor its size and latency; prefer EndpointSlices and node-local DNS; stagger node and kubelet rollouts; prefer more, smaller clusters unless a workload needs one large network domain; manage the fleet declaratively; make recreating a cluster a rehearsed procedure; and treat the support calendar as a standing project plan.

## Applications beyond this domain

Scale-out versus scale-up is the general trade-off of distributed systems, seen in databases (sharding), web services (cells), and supercomputing. Cell-based architecture, used by cloud providers to limit blast radius, is the multi-cluster strategy at another level. The compounding cost of deferred maintenance is the idea of technical debt, and the practice of continuous small updates is the same as in the operating-system patching discussed in the enterprise courses: keeping fewer versions in the field reduces risk. Fleet management with a declarative source of truth and progressive delivery is how large organisations manage servers, network devices and mobile applications. The thundering herd problem and the use of fairness queues to contain it are standard in networking and databases.

## Examples

A control-plane review at about four hundred nodes: the team observes API server request latency rising during deployments. The audit log and metrics show a monitoring agent listing all pods in the cluster every few seconds from each node. They switch the agent to a watch with a field selector for its own node, which reduces list load by an order of magnitude and flattens the latency.

A fleet upgrade plan: twelve clusters, three environments. The platform team upgrades the development cluster the week a minor is released, runs the conformance and application suites, upgrades staging two weeks later, and schedules production clusters in waves of three with a hold between waves. Each wave checks API deprecation metrics, node readiness and error budgets before proceeding.

A failing example: a team defers upgrades for eighteen months to avoid risk, then needs to move across three minors. Two beta APIs they use were removed along the way, a CRD's old version was dropped without storage migration and a network plugin release that supports both ends of the range does not exist, so they must upgrade the plugin in the middle of the sequence. The upgrade takes weeks. A cadence of one minor every quarter would have taken an afternoon each time.

Another failing example: a rolling restart of all nodes at once after a certificate renewal makes thousands of kubelets re-list their pods at once, the API server saturates and the controller manager loses its leader lease repeatedly. The fix is to restart in batches, and to configure the API priority and fairness levels so that system components are protected.

## Related problems and ideas

Federation proposals and their successors (Karmada, Open Cluster Management, Fleet) treat many clusters as one placement target. Virtual clusters and hosted control planes let many tenants share infrastructure with separate API servers. Cell-based architectures isolate failures at the application level rather than the cluster level. Research on large-scale scheduling asks whether a single scheduler can be replaced with sharded or distributed designs. Alternative orchestration designs for extreme scale, such as Borg itself or the batch systems in high-performance computing, show different trade-offs (a lower churn rate, stronger central control). Not mainstream: pluggable alternative storage backends for the API server and sharded API servers by resource type.

## Active research

The scalability community works on streaming list responses to cut API server memory use, on consistent reads served from the watch cache, on reducing etcd write amplification, on more efficient endpoint propagation and on scheduler throughput for batch-heavy clusters. Research on cluster failure studies examines incidents in large production fleets, and tools such as simulation of control plane behaviour aim to predict problems before deployment. In upgrade research, projects look at automatically translating manifests across API versions, and at verifying that a cluster is ready for a given upgrade. The open question for the field is how long a project can keep the single-cluster model competitive as workloads grow (to verify specifics for your version).

## Future direction

Expect fewer manual upgrade steps, more automatic migration of stored objects, longer-lived support branches under discussion in the community and managed services that absorb the fleet-wide chores. Hardware trends toward very large accelerator clusters will keep pushing the scale of single-network-domain clusters, and platform teams will build internal developer platforms that hide clusters behind higher-level APIs. For the administrator the advice is stable: know your numbers, bound blast radius, automate repeated work, keep every cluster inside its support window and recreate rather than repair when recreation is cheaper.
