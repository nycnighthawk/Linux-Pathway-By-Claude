# Changing a running cluster without stopping the applications on it

## Define the problem

A cluster that is never changed is a cluster that falls out of support. Kubernetes ships a new minor version about three times a year, each minor receives patches for a bounded window, and security fixes land only in supported lines. Meanwhile the operating system under every node needs kernel updates and reboots, the container runtime needs patching, certificates age, and hardware fails and is replaced. Each of these tasks takes capacity out of service, and some of them (a control-plane upgrade) touch the very components that decide where workloads run.

The difficulty is that the people who own the applications do not want to hear about any of it. An upgrade must keep the control plane available enough to make changes, keep application replicas serving while their node is emptied, respect promises such as a promise that most replicas stay available, and stay within the rules about which component versions may talk to which. Failure looks like a node drained so aggressively that a quorum-based database loses its majority, a control plane moved two minor versions in one step so that an API a workload relies on disappeared, or a half-upgraded cluster in which kubelets and the API server disagree about object schemas.

This slice covers the version-skew policy, the kubeadm upgrade sequence for the first and the remaining control-plane nodes and for workers, the node operations cordon, drain and uncordon, the eviction API and PodDisruptionBudgets that make draining safe, and the routines around them: backups, deprecation checks, addon and network plugin compatibility, and rollback options. Datastore restore is T04; scaling and very long-lived clusters are T12.

## History and approaches

The earliest Kubernetes upgrades were rebuilds. With clusters created from scripts, upgrading meant creating a new cluster and moving traffic, or running the same script with a new version and hoping state survived. Projects grew in-place tooling as the user base discovered that rebuilding stateful clusters was not acceptable. kubeadm acquired an upgrade command during the 1.x series, and the cluster lifecycle group documented a skew policy that evolved over time: the number of minor versions a kubelet may trail the API server grew from two to three as the release cadence slowed from four to three releases a year and the support window lengthened to about a year (to verify the exact window in the current release page).

Eviction and node draining went through their own history. Early `kubectl drain` simply deleted pods, which ignored application-level protection. The eviction subresource and PodDisruptionBudget objects were introduced so that voluntary disruptions go through a policy check: an eviction request is refused when it would leave fewer pods available than the budget demands. This turned drain from a blunt tool into a negotiation, and exposed a trap: a budget that can never be satisfied (for example `minAvailable` equal to the replica count) blocks every drain forever, which is the single most common cause of an upgrade that hangs.

Approaches to cluster upgrades now fall into four families. In-place rolling upgrade, the kubeadm default, upgrades control-plane nodes one at a time and then drains and upgrades workers in batches; it is cheap and keeps identities but accumulates drift. Replace-in-place by node pools, as in managed services and Cluster API, creates new nodes at the new version, drains the old ones and deletes them; it avoids upgrading an operating system under live workloads and gives a clean rollback by not deleting the old pool until the new one proves itself. Blue-green clusters stand up a second cluster and move workloads and traffic, the safest approach and the most expensive, mostly used for major platform changes. Automated reboot controllers, such as Kured, take the narrower problem of operating-system patching: they watch for a reboot-required marker, then cordon, drain, reboot and uncordon one node at a time under a lock. Hypervisor platforms have an analogue in maintenance mode with live migration; KubeVirt's documentation describes how a node drain triggers live migration of virtual machines instead of killing them, which depends on migrations being possible and on an eviction strategy set per virtual machine.

The pattern that settled: version-skew rules are strict and published; upgrades go one minor version at a time; stateful workloads are protected by disruption budgets and not by hope; and anything that must be rolled back must be backed up first, since a control-plane downgrade is not supported.

## Current state

**Skew rules.** The API server is the reference. The controller manager, scheduler and cloud controller manager may be one minor version older than the API server, never newer. The kubelet and kube-proxy may be older than the API server by up to three minor versions in current releases, never newer; `kubectl` may be one minor version either side. Multiple API servers in a highly available control plane may differ by at most one minor version during an upgrade, which is why the upgrade is done node by node. Two consequences for planning: upgrade the control plane first, then nodes; and never skip a minor version for the control plane, because API conversion and storage migration are tested only between adjacent versions (to verify for the target release).

**The kubeadm sequence.** First read the target version's release notes and the deprecation guide. Back up etcd and any critical configuration. Upgrade the `kubeadm` package on the first control-plane node, run `kubeadm upgrade plan` to see the available versions and the checks it performs, then `kubeadm upgrade apply vX.Y.Z`. This regenerates the on-disk pod definitions of the control-plane parts, renews certificates that are close to expiry as part of the upgrade (unless told not to), upgrades CoreDNS and kube-proxy and writes the new cluster configuration back to its ConfigMap. Because the kubelet restarts the static pods, the control-plane components restart automatically; the Arch Linux documentation adds a package-manager warning that `kubeadm upgrade apply` also overwrites the local kubelet configuration file from the cluster's ConfigMap, so that ConfigMap must be correct first. Then on that node cordon and drain, upgrade the `kubelet` and `kubectl` packages, restart the kubelet and uncordon. On each other control-plane node and worker, the command is `kubeadm upgrade node` rather than `apply`, followed by the same drain, package upgrade and uncordon steps. The network plugin and other add-ons are upgraded separately by their own procedures, and their compatibility matrix with the target Kubernetes version must be read first; the Kubernetes documentation on CNI troubleshooting shows one typical symptom of a version mismatch, an "incompatible CNI versions" error that stops pods from starting.

**Cordon, drain, uncordon.** `kubectl cordon NODE` marks the node unschedulable, which adds a taint so that no new pods arrive but existing pods keep running. `kubectl drain NODE` cordons and then evicts every pod it can through the eviction API, waiting for each to terminate. Typical flags are `--ignore-daemonsets`, because DaemonSet pods would be recreated at once on the same node, and `--delete-emptydir-data`, which acknowledges that local scratch data will be lost. Pods not owned by a controller are not rescheduled anywhere, so drain refuses them unless forced. After maintenance, `kubectl uncordon NODE` makes the node schedulable again. The drain respects each pod's termination grace period, which is also why a stuck application can make an upgrade crawl.

**Disruption budgets.** A PodDisruptionBudget names a set of pods by label selector and states either a minimum number that must stay available or a maximum number that may be unavailable. The eviction API evaluates the budget before removing a pod. The documentation's examples, for instance a replicated stateful application and a ZooKeeper ensemble, show the purpose: surviving the loss of a node requires that the quorum members are spread across nodes (anti-affinity) and that voluntary disruption removes at most one at a time, while the budget limits the pace of the drain to the pace at which replacements become ready. Budgets apply only to voluntary evictions, not to node crashes, and they do nothing for a single-replica workload except block it.

**Operating-system maintenance.** Kernel updates follow the same drain and reboot loop. Kured or similar tools automate it. On virtualised nodes with KubeVirt, a node placed in maintenance causes virtual machines whose eviction strategy permits it to be live migrated to other nodes first. Network plugins can have their own shutdown procedures: Cilium's BGP control plane guide describes how to withdraw routes before a node is stopped so that traffic is not blackholed.

**Rollback and recovery.** Rolling back a control plane across minor versions is not supported. The practical rollback is to restore the etcd snapshot taken before the upgrade onto control-plane nodes reinstalled at the old version, which is why the backup is a precondition and not a courtesy. Workers can be rolled back by reinstalling the older kubelet within the skew rules. Tearing down a node completely, as the Arch notes describe, resets the kubeadm state on that machine so that it can rejoin.

## Assessment: the good, the bad and the ugly

The good: with budgets, anti-affinity and replicas in place, a cluster upgrade is a non-event for applications. The procedure is mechanical and scriptable, the skew rules are explicit, and the API gives each step a visible state. Rolling upgrades of nodes in small batches make capacity loss predictable.

The bad: the control plane's single-minor-step rule makes catching up expensive. A cluster three versions behind needs three successive upgrades, each with its own breaking changes, and the support window means the cluster may have lost security patches before it finishes. Draining is only as safe as the weakest application: a single replica with no budget goes down, a budget with no slack hangs the drain, and a pod with a long termination grace period slows it. Add-ons lag: network plugins, ingress controllers, storage drivers and operators each have a compatibility matrix, and the cluster's version is bounded by the slowest of them.

The ugly: API removals. When a beta API is removed, manifests stored in Git stop applying, controllers that still use the old group fail, and objects already stored in etcd must have been migrated before the removal. The API server publishes a metric of requests to deprecated APIs, and tools such as pluto or kubent scan manifests and Helm releases; the sad case is the team that finds out on upgrade night. Another ugly area is state outside the cluster's view: local PersistentVolumes on a drained node make the pods using them unschedulable until the node returns; emptyDir data disappears; applications that cache node identity break on a new node. And drains interact badly with some workloads such as long-running batch jobs or virtual machines that cannot live migrate because of device passthrough or local disks.

Mitigations: read deprecation notices a release ahead; scan for removed APIs in CI; rehearse the upgrade on a staging cluster built the same way; set budgets with slack (`maxUnavailable: 1` rather than `minAvailable: N`); spread replicas by topology; keep an etcd snapshot per upgrade; upgrade one node first and watch; set a time limit on drain and investigate what blocks it instead of forcing with `--disable-eviction`, which bypasses budgets.

## Applications beyond this domain

Rolling maintenance under availability constraints is a general operational pattern. Database clusters such as Cassandra or Elasticsearch use rolling restarts with shard allocation control, which is the same idea as budgets. Load balancers use connection draining before removing a backend. Airline and hospital shift handovers follow it too: take one unit out of service only when its duties have moved. In software supply chains the skew policy resembles the compatibility rules of protocols with a version-negotiation window. The cordon concept is a taint, the same general mechanism that scheduling policy (T05) uses to repel workloads for other reasons. Blue-green deployments of whole platforms are the cluster-sized version of the application rollout strategies in the delivery course.

## Examples

A clean rolling upgrade of a three-control-plane, five-worker cluster from one minor version to the next: take an etcd snapshot, run the deprecation scan, upgrade the kubeadm package on cp1 and run `kubeadm upgrade plan` then `apply`, drain cp1 and upgrade its kubelet, then repeat with `kubeadm upgrade node` for cp2 and cp3. For workers, drain one node at a time, upgrade the packages, restart the kubelet, uncordon and wait for the node to be Ready and for the pods the budgets protect to return before moving to the next node.

A failing example: an engineer drains a worker and the command hangs. `kubectl get pdb -A` shows a budget with `minAvailable: 3` on a deployment of three replicas; the allowed disruptions column reads zero. The engineer must either scale the application up or loosen the budget, then retry; forcing the eviction would break the owner's promise.

A second failing example: an application uses the local-path provisioner and a PersistentVolume bound to one node. After drain the pod stays Pending because its volume can only be mounted on the cordoned node. The right response is to choose storage with node-independent replicas for anything that must survive maintenance, or to accept downtime for that workload deliberately.

A third: after a control-plane upgrade the cluster reports pod errors about an incompatible CNI configuration version. The network plugin's configuration used a specification version that the new runtime dropped; upgrading the plugin fixed it. This illustrates why add-on compatibility belongs in the upgrade checklist.

## Related problems and ideas

Immutable-node approaches avoid in-place operating system upgrades: node images are built, tested and rolled out as new nodes while old ones drain and disappear. Cluster API's machine deployments express the same as a declarative rolling update with surge and unavailability limits. Projects such as the system-upgrade-controller from the Rancher ecosystem upgrade k3s clusters by plans expressed as custom resources. Version-skew relaxation has been a recurring proposal: longer support windows, long-term-support branches and decoupled component versions all aim to reduce the pressure to upgrade, and the project has so far favoured the predictable three-per-year cadence with a longer skew allowance for kubelets. Another idea is live in-place kernel patching to avoid reboots, with limits on what it covers.

## Active research

Work in the community covers safer node shutdown (graceful node shutdown with priority classes, non-graceful shutdown handling for stuck pods on dead nodes), better eviction behaviour for pods stuck in termination, unhealthy pod eviction policies in budgets, and in-place pod resource changes that avoid restarts. The API machinery group studies automatic storage version migration to reduce the pain of API removals, and tooling for pre-flight detection of workloads that would break on upgrade. Researchers and practitioners publish studies of upgrade failures from incident databases; recurring patterns are version skew violations, add-on incompatibility and under-tested rollbacks.

## Future direction

Expect the project's policy to keep tightening: more automatic migration of stored objects, clearer machine-readable deprecation data, and kubeadm and Cluster API gaining first-class upgrade planning that evaluates budgets and skew before starting. Managed platforms will keep absorbing the control-plane step, leaving customers to schedule node and add-on upgrades. Watch the release calendar for the next minor and its support end dates, keep a standing calendar slot for upgrades, and prefer practising them often because small steps are safer than rare big ones (to verify the current calendar on the Kubernetes releases page).
