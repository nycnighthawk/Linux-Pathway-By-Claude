# Letting someone else run the control plane: managed Kubernetes on the three big clouds

## Define the problem

Everything in the earlier slices of this course is work: building the control plane, keeping etcd healthy, renewing certificates, upgrading in the right order, replacing failed machines at three in the morning. For many organisations that work does not differentiate their product, and the people who can do it well are scarce. Cloud providers answer with managed Kubernetes: the provider runs the API server, etcd and controllers as a service, customers get an endpoint and a kubeconfig, and the nodes are either machines the customer sees and pays for, or machines the provider also operates.

That bargain trades control for convenience, and the trade has consequences an administrator must understand. Who is responsible for what when a pod cannot reach the internet, a node is out of date or an upgrade breaks an application? How does a cluster user authenticate when the identity system is the cloud's and not Kubernetes' own? How do workloads get permissions to cloud services without storing keys in Secrets? What does a LoadBalancer Service do when the cloud, not MetalLB, answers it? What does it cost, and what happens when the Kubernetes version you run leaves support?

This slice surveys Amazon Elastic Kubernetes Service (EKS), Azure Kubernetes Service (AKS) and Google Kubernetes Engine (GKE) at the level the course needs: the division of responsibility, the node models, identity and access, cloud integrations through controllers and drivers, upgrade and support policies, and the main pitfalls. It is a survey because the three products change rapidly and each has its own documentation; the aim is to know the questions to ask and to recognise how each standard concept of this course shows up in each service. Hands-on cloud work is a manual guide because it needs paid accounts.

## History and approaches

Google, which built Borg, launched Google Container Engine, later GKE, in 2015, soon after Kubernetes 1.0, and for some years it was the reference managed offering. Microsoft introduced Azure Container Service with a choice of orchestrators in 2016, then dropped the others and renamed the product AKS in 2017 as Kubernetes won. Amazon came last, launching EKS in 2018 after pressure from customers who were running self-managed clusters on EC2 with kops and kubeadm, and who had been served until then by the proprietary Elastic Container Service. The three have since diverged in philosophy: GKE offers the most integrated and opinionated experience with release channels and an Autopilot mode where Google manages nodes and bills per pod; AKS integrates with Microsoft's identity and developer tooling and offers an Automatic mode with more preconfigured defaults; EKS offers building blocks, with managed node groups, Fargate for serverless pods and an Auto Mode that provisions and manages nodes with Karpenter-based machinery.

Approaches to the node question explain most of the product design. In *managed node groups*, the provider creates virtual machines in an autoscaling group from an image it maintains, and the customer chooses instance types and triggers updates. In *bring your own nodes*, the customer builds and patches the machine images and joins them to the cluster, which gives control and obligations equal to a self-managed cluster. *Serverless pods* (EKS Fargate, GKE Autopilot's pod billing model) abstract the node away and impose restrictions on privileged pods, host access and daemon sets. *Auto modes* sit in between: the provider runs nodes for you, with a defined set of managed add-ons for networking, storage and load balancing. The Kubernetes node autoscaling documentation describes the common thread: nodes are provisioned to fit the constraints of pending pods.

For identity, the first managed clusters used the cloud provider's credentials through client-go credential plugins, external programs that the kubeconfig invokes to obtain a token; the Kubernetes authentication documentation describes this plugin mechanism, and it is the reason `kubectl` for a managed cluster needs the provider's CLI installed (the well-known "no auth provider found" error in older clients came from the removal of built-in cloud auth providers from kubectl and its replacement by these external plugins). For workloads, providers created pod identity mechanisms: IAM Roles for Service Accounts and later EKS Pod Identity on AWS, Workload Identity on GKE, Microsoft Entra Workload ID on AKS. All of them rely on the same Kubernetes mechanism, the projected service account token with a custom audience, which the cloud's identity service trusts after federation with the cluster's issuer, so that no long-lived cloud key needs to sit in a Secret.

The pattern: the provider runs the control plane and an increasing share of the data plane; the customer defines workloads, policy and cost; identity federation replaces stored credentials; and Kubernetes versions follow a managed lifecycle with forced upgrades at the end.

## Current state

**The shared responsibility split.** In all three the provider operates the API servers and etcd, replicates them across zones, backs them up, patches them and offers a service level for availability of the control plane. The customer remains responsible for the worker nodes (to a degree that depends on mode), their operating-system patches in the managed node group model, the workloads, networking choices inside the cluster, access control, Secrets handling, cost and application backups. The control plane is not accessible for host-level debugging: no SSH to API server machines, no access to etcd, no direct editing of the static pod flags. Audit and control-plane logs are exposed through the provider's logging service, often off by default; enabling them is a deliberate step and a cost.

**Networking.** Each service has a default CNI integrated with the cloud network. On AWS the VPC CNI gives pods addresses from the VPC, which makes them routable but consumes subnet addresses and limits pods per node by the interface and address limits of the instance type; GKE uses alias IP ranges for pods and a dataplane based on Cilium in the newer Dataplane V2; AKS offers an overlay mode as well as direct virtual network addresses, and Cilium-based options. Services of type LoadBalancer trigger the cloud controller to create a cloud load balancer, as the Kubernetes Service documentation describes for the type: the provisioning is implementation-specific and annotations on the Service tune it. Ingress and Gateway API implementations typically use the provider's application load balancer through a controller you install or that the provider manages.

**Storage.** Each cloud ships CSI drivers for its block and file storage (EBS and EFS, Azure Disk and Files, Persistent Disk and Filestore), with default StorageClasses. Block volumes are zonal, so the topology and binding mode concerns from the storage slice apply directly; a node pool restricted to one zone cannot use a volume from another.

**Access.** Authentication to the cluster uses the provider's identity: IAM principals mapped to Kubernetes users through an access entry or ConfigMap on EKS, Microsoft Entra ID groups on AKS, Google identities and groups on GKE. Authorisation is still Kubernetes RBAC, though AKS and others can use the cloud's role system for it. A standard misconfiguration is leaving the public API endpoint open to the internet, or granting the creator of the cluster a hidden administrator mapping nobody tracks. Private clusters place the endpoint inside a virtual network, requiring a jump host, VPN or peering to administer.

**Workload identity.** A service account in a namespace is annotated or associated with a cloud role, and the cluster's OIDC issuer URL is registered with the cloud's identity service. A pod's projected token is exchanged for short-lived cloud credentials scoped to that role. Node-level credentials remain a risk: if the nodes' instance role is broad and metadata endpoints are reachable from pods, any pod can use it. Blocking pod access to the instance metadata service or requiring hop-limit controls is therefore part of hardening, covered in the security course.

**Versions and upgrades.** Providers publish a support calendar: each Kubernetes minor is supported for a limited time, then retired or moved into paid extended support. For EKS the figures reported in current comparisons are about fourteen months of standard support followed by up to twelve months of extended support at a higher hourly price, and for GKE about fourteen months on the regular channel with the Extended channel reaching twenty-four months for standard clusters but not for Autopilot; AKS publishes its own window and a long-term support tier (these numbers come from secondary comparisons and must be checked on the providers' pages before use; to verify). Upgrades of the control plane are triggered by the customer or scheduled by the provider; GKE release channels (rapid, regular, stable, extended) and maintenance windows and exclusions let the customer shape when upgrades occur; node upgrades roll nodes with surge settings and honour PodDisruptionBudgets, which is why the disruption-budget slice matters here. The skew rules still apply: the provider upgrades control planes ahead of nodes, and a node pool left behind eventually falls outside the permitted skew.

**Cost model.** There is usually a per-cluster hourly fee (a free tier exists on some), plus the nodes, load balancers, storage, egress and logging. The largest surprises are cross-zone data transfer, NAT gateway traffic, idle node capacity and the logging bill.

**Add-ons and extensions.** Providers manage a core set (CoreDNS, kube-proxy, the CNI, CSI drivers) as optional managed add-ons that they upgrade or at least version-match, and offer marketplaces of third-party tools. Policy and security services, such as pod security and image scanning, plug into the same cluster.

## Assessment: the good, the bad and the ugly

The good: for most teams a managed control plane is the correct default. It removes etcd, certificate and control-plane upgrade work, gives availability across zones, integrates identity and networking and lets a small team operate many clusters. Autoscaling nodes and managed upgrades make elasticity real. The standard Kubernetes API means skills and manifests transfer, with the CKA-style competencies in this course applying unchanged to the objects the customer controls.

The bad: portability is partial. Annotations on Services, Ingress classes, storage classes, identity wiring and networking all differ per cloud, so a manifest that works on one needs adaptation on another. Limits are hard: maximum pods per node, API endpoint rate limits, quotas on addresses. Some features lag upstream or are unavailable, and alpha feature gates cannot be enabled on a managed control plane. Costs are opaque and grow with scale, and the managed service's upgrade cadence imposes an external schedule on the application teams. Debugging a control-plane problem depends on the provider's support.

The ugly: shared-responsibility gaps. Teams assume that "managed" includes node patching, backups of persistent data or security hardening, and it does not. Version-support deadlines produce forced upgrades, with clusters moved automatically or charged a premium on an old version. Removing a deprecated API from a new version breaks workloads that nobody tested. Private networking misconfigurations leave clusters unreachable for the administrators. Identity mappings drift, so people who left the company retain access through an old cloud role. A control plane outage in a region is outside the customer's power to fix. And lock-in creeps in through every provider-specific controller and annotation.

Mitigations: read the shared responsibility documentation for the specific mode; turn on control-plane audit logging; restrict or privatise the API endpoint; use workload identity everywhere and block metadata access from pods; track the support calendar and automate upgrade rehearsals; set budgets and cost allocation tags; keep manifests in portable form with provider differences isolated in overlays; and keep application-level backups, because the provider backs up the control plane, not your data.

## Applications beyond this domain

The same division of labour appears in every managed service: managed databases, managed message queues and managed identity systems all take a stateful, operationally heavy component, run it behind an API and leave the customer with configuration, data and integration. The federated identity pattern used for pods is the OpenID Connect trust used by CI systems to obtain cloud credentials without static keys, and by the Azure and AWS federation features generally. Autoscaling nodes from pod constraints is the cloud-native version of capacity management in virtualisation clusters, and has parallels in the KubeVirt design that treats virtual machines as pods and lets the cluster autoscaler add hypervisor capacity. Support windows and forced upgrades mirror the lifecycle policies of operating system vendors and of enterprise distributions such as Red Hat Enterprise Linux and Rocky Linux, whose users plan around the end of a release in the same way.

## Examples

A first managed cluster, in outline: create the cluster with the provider's CLI or infrastructure-as-code in a private network, with one managed node pool across three zones and control-plane logging enabled; install the provider's CLI so kubectl's credential plugin can obtain a token; map an administrator group; verify with `kubectl get nodes` and `kubectl get pods -A`; create a LoadBalancer Service and watch the external address appear; create a service account bound to a cloud role through the workload identity mechanism and read an object-storage bucket from a pod without any stored key.

A failing example: a team enables public access to the API endpoint to let a CI system deploy, forgets to restrict it by source range and finds probing traffic in the audit log. The fix is to restrict by network, or use a private endpoint plus a self-hosted runner in the network.

Another: after a managed upgrade, an old Ingress object that used a removed beta API version stops being reconciled. The provider's upgrade insights had flagged it, but no one read them. The lesson is the same as for self-managed upgrades: scan for removed APIs before the upgrade.

Another: pods cannot get addresses on an AWS cluster using the VPC CNI because the subnets are exhausted by a large node pool. The remedy is custom networking with a secondary address range or prefix delegation, planned for in the address design.

## Related problems and ideas

Distributions such as OpenShift, Rancher, Tanzu and Talos-based platforms offer a managed-like experience on any infrastructure. Cluster API provides the same declarative lifecycle across providers, and tools such as Crossplane and Terraform manage the clusters as code. Hosted control planes (HyperShift, Kamaji) bring the managed model on-premises. Multi-cluster and multi-cloud management (Karmada, Fleet, Anthos-style products) try to hide differences; they carry their own complexity. Serverless container platforms (Cloud Run, Fargate on ECS, Azure Container Apps) drop Kubernetes in favour of simpler abstractions, and a legitimate decision for some teams is to not run Kubernetes at all. Sovereignty and exit strategy concerns lead to designs that stay portable by sticking to the open core APIs.

## Active research

Industry and academic work examines cost optimisation and right-sizing, carbon-aware scheduling across regions, multi-tenancy isolation in shared control planes and the security of workload identity federation. The providers are moving toward fully automatic modes (EKS Auto Mode, GKE Autopilot, AKS Automatic) where node lifecycle, security patching, scaling and add-on upgrades are handled by the platform, and the open question is how much configuration freedom survives. The release engineering of the upstream project and the providers' support windows, including a proposal in the community for a longer support period, remains under discussion (to verify the current state).

## Future direction

Expect the automatic modes to become the default for new clusters, deeper cloud identity integration with pod-level scoping, more policy and security baked into the platform, GPU and AI-workload features (dynamic resource allocation, fractional accelerators) arriving first on managed services, and further convergence on Gateway API for traffic. For administrators, the durable work shifts from running clusters to governing them: version calendars, cost, identity, policy and the application-level resilience that the platform cannot provide. Verify details of each service against its current documentation before relying on them, because they change monthly.
