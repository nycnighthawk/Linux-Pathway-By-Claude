# Packaging and varying Kubernetes manifests: Helm charts and Kustomize overlays

## Define the problem

A real application on Kubernetes is not one manifest. It is a Deployment, a Service, a ConfigMap, a ServiceAccount with roles, perhaps an Ingress, a HorizontalPodAutoscaler and a PodDisruptionBudget, and the same set must be installed in development, staging and production with different image tags, replica counts, hostnames and resource sizes. It must be installed by people who did not write it, upgraded without losing track of which objects belong to which version, and removed cleanly. Plain YAML files copied and edited per environment drift apart; shell loops with `sed` break on the first quoting problem; the cluster itself, which stores only the objects and not the files that made them, does not remember what belonged together.

Two needs are mixed in this problem. The first is distribution: an application author wants to hand a versioned, parameterised bundle to strangers, who need an install, upgrade and rollback story. The second is customisation: an operator wants to take manifests they do not own, or own and share across environments, and adjust them without forking. Failure shows as copy-pasted manifests that differ in forgotten ways between staging and production, charts whose hundreds of values nobody understands, upgrades that leave orphan objects behind, secrets committed in plain text, and templates that render invalid YAML only at three in the morning.

This slice covers the two dominant answers, Helm and Kustomize, how each works, how they differ and combine, how an administrator installs, upgrades, inspects and rolls back with them, and the surrounding practices: pinning versions, reviewing rendered output, handling secrets and relating them to GitOps. Authoring charts in depth, testing them and publishing is the application delivery course (T06 there); here the focus is on operating with charts and overlays written by others, as the CKA-style administration tasks require.

## History and approaches

The first approach to configuration was `kubectl create -f` on hand-written files, supplemented by labels and `kubectl apply`, which added a three-way merge between the last applied configuration, the live object and the new file. As clusters multiplied, projects emerged to generate manifests. Helm came out of Deis in 2015 and joined the CNCF; Helm 2 split the tool into a client and a server component, Tiller, running in the cluster with broad permissions, and Tiller became its best-known security weakness. Helm 3, released in 2019, removed Tiller, stored release state as Secrets in the release's own namespace so that ordinary RBAC applied, added a JSON schema validation hook for values and moved charts toward OCI registries. Helm 4 was released in November 2025, the first new major version in six years; its headline changes, as reported by the project and the CNCF, are a rebuilt plugin system that includes WebAssembly plugins, post-renderers as plugins, server-side apply support and improved resource waiting based on kstatus (to verify defaults and flags against the release notes before adopting).

Kustomize took a different path, started by Google engineers in 2017, intended as a template-free alternative. It treats manifests as data: a `kustomization.yaml` lists resources and transformations (name prefixes, labels, images, patches), and the tool emits modified YAML without any templating language. It was added to `kubectl` as `-k` in version 1.14 after a contentious debate, and the Kubernetes documentation on managing workloads lists it among the ways of organising resource configurations. The version embedded in `kubectl` lags the standalone binary, which has caused confusion about which features are available.

Other approaches fill the space around them. Jsonnet, Dhall and CUE offer real configuration languages with functions and types; ytt from Carvel pairs a YAML-aware templating with overlays; Timoni and cdk8s generate manifests from typed code; the older ksonnet died of complexity. KubeVirt's template mechanism, which lets a user stamp out virtual machines from a parameterised template, shows the same need reappearing for a particular resource family. Operators (T09) answer the question differently by moving application knowledge into a controller, and GitOps tools (T07 of the delivery course) apply the rendered result from a repository.

The pattern: templating (Helm) wins at distribution and parameterisation, and pays with a second language embedded in YAML; patching (Kustomize) wins at readability and adjustment of others' manifests, and pays with limits on what a patch can express. Most organisations use both.

## Current state

**Helm's model.** A *chart* is a directory or archive containing `Chart.yaml` (name, version, app version, dependencies), `values.yaml` (defaults), a `templates/` directory of Go templates enriched with the Sprig function library, optional `values.schema.json`, helper partials in `_helpers.tpl` and hooks. Rendering merges the chart's defaults with user values (`-f file`, `--set key=value`, later sources override earlier ones) and produces plain manifests. A *release* is an installed instance: Helm records each revision as a Secret named after the release in its namespace, which is what makes `helm history`, `helm rollback` and three-way diffs on upgrade possible. Charts are distributed from repositories (an index file plus archives) or, increasingly, from OCI registries addressed as `oci://` references, and can depend on subcharts, which receive values under their own key.

**Helm operations.** `helm repo add` and `helm search repo` find charts; `helm show values CHART` is the first thing to read, because it documents what can be changed; `helm template` renders locally without a cluster; `helm install NAME CHART -n NS --create-namespace -f values.yaml` installs; `helm upgrade --install` is the idempotent form for automation; `--atomic` and `--wait` roll back automatically if readiness is not reached; `helm diff` (a plugin) previews changes; `helm get values` and `helm get manifest` show what is deployed; `helm rollback NAME REVISION` returns to an earlier revision; `helm uninstall` removes the release's objects. Hooks let a chart run Jobs before or after install and upgrade, such as database migrations. Linting (`helm lint`) and rendering against a Kubernetes version help catch problems before the apply.

**Where Helm bites.** CustomResourceDefinitions in a chart's `crds/` directory are installed once and never upgraded or deleted by Helm, a deliberate safety that surprises people and means CRD upgrades need a separate step. Helm's three-way merge interacts badly with objects changed by other controllers or by `kubectl edit`. The values interface is the chart's contract: a chart with many hundreds of values, no schema and templates that silently ignore misspelled keys is hazardous, because a typo means the setting is simply not applied. Rendered output must be reviewed, particularly for third-party charts, which can request privileged settings or install cluster-wide roles.

**Kustomize's model.** A *base* is a directory with a `kustomization.yaml` that lists resource files or other directories. An *overlay* is another kustomization that refers to a base and adds transformations. Common fields: `namePrefix` and `nameSuffix`, `namespace`, `commonLabels`, `images` (change an image name or tag without editing the manifest), `replicas`, `patches` (strategic merge patches, which merge by the structure of Kubernetes objects, or JSON 6902 patches addressing paths) and `configMapGenerator` and `secretGenerator`, which create ConfigMaps and Secrets from literals or files and append a content hash to the name, so that changing the data changes the name and triggers a rolling update of workloads that reference it. `components` package reusable optional features. `kubectl kustomize DIR` renders; `kubectl apply -k DIR` applies; the documentation of the render command lists the options, including the load restrictor that by default stops a kustomization reading files outside its own tree. A `helmCharts` field lets Kustomize inflate a Helm chart and then patch the result, a common way to adjust a third-party chart without forking.

**Choosing.** For software you ship to others, or consume from others with a published chart, use Helm. For your own services across environments, Kustomize overlays are often clearer and keep manifests as real Kubernetes YAML. For third-party charts that need small changes, render with Helm, then patch with Kustomize or use post-render. In GitOps, Argo CD and Flux both render either; the reviewed artefact is the rendered output or the values and overlay in Git.

**Applying and pruning.** Whichever tool renders the manifests, the apply step decides what happens to objects that disappeared from the source. Plain `kubectl apply` leaves them alone unless pruning is requested with a label selector or an ApplySet, a feature that is still maturing; Helm deletes objects that the new revision no longer renders, because it knows its own release inventory; GitOps controllers prune only when configured to. Server-side apply records which manager owns each field, so that Helm, a controller and a human can each own different fields of the same object without trampling one another, and conflicts are reported instead of silently overwritten. Administrators should know which applier owns a namespace and avoid mixing two appliers in one.

**Secrets and supply chain.** Neither tool encrypts anything. Common additions are SOPS or sealed secrets with an operator that decrypts in-cluster, and external secrets operators that sync from a vault. Pinning chart versions and image digests, verifying chart signatures or provenance files, and scanning rendered manifests with policy tools are standard practices; OCI charts can be signed with the same tooling as images.

## Assessment: the good, the bad and the ugly

The good: Helm gives a huge ecosystem of ready packages, a clear install, upgrade, rollback and uninstall lifecycle and a place to record release history. Kustomize gives readable, diffable, template-free customisation that is built into `kubectl`. Used together they cover most needs. Both produce plain manifests that can be inspected before applying, which is the main safety net.

The bad: Helm templates are a text-templating language over a whitespace-sensitive data format, and indentation bugs (`nindent`) are an everyday experience. Charts vary widely in quality, and a chart's value names are its private API that changes between versions. Helm release state in Secrets can become large, and a failed release can be stuck in a pending state needing manual repair. Kustomize cannot compute: you cannot derive one value from another, such as sizing replicas from the number of zones, and complex patches become unreadable. Its embedded version in `kubectl` may lack features documented for the latest release.

The ugly: drift and ownership. When Helm owns an object and someone edits it, the next upgrade either reverts the edit or, with merge quirks, preserves it half. Applying the same object with Helm and Kustomize, or two releases claiming the same name, ends in ownership errors. CRD handling splits applications into two lifecycles. Templates that call `lookup` to read live cluster state render differently with `helm template` than on install, so what you reviewed is not what ran. Chart dependencies pull in another chart's defaults, including its own idea of security context. And secrets generated by `randAlphaNum` in templates change on every upgrade unless the template looks up the existing one.

Mitigations: always read `helm show values` and the rendered manifests for third-party charts; pin chart and image versions; use `--atomic`; keep values files in Git, one per environment; add a values schema in charts you author; run `helm diff` in review; avoid `lookup` in templates meant for rendering offline; handle CRDs deliberately in a separate step; use generators with hashes for ConfigMaps in Kustomize; keep overlays shallow.

## Applications beyond this domain

Helm's chart-and-values idea is the same as package managers with configuration (dpkg with debconf, RPM with macros) and as Ansible roles with variables, discussed in the enterprise automation course. Kustomize's base-and-overlay mirrors the layered configuration of Docker Compose override files, systemd drop-ins that patch unit files, and the cascade in CSS or in `/etc` configuration directories. Both embody the general split between a generator, which creates configuration from parameters, and a patcher, which edits existing configuration. The release record in a Secret is a form of the state file that Terraform keeps. The hashing of generated ConfigMap names parallels content-addressed build artefacts: change the content and the identity changes with it.

## Examples

Operating a third-party chart: add the repository, show the default values of the chart, write a small values file that overrides only what you need (storage class, ingress host, resource requests), render with `helm template` and read the output, then `helm upgrade --install` with `--atomic --wait` into its own namespace. A week later change a value and use `helm diff upgrade` first. If the upgrade misbehaves, `helm history` lists revisions and `helm rollback` returns to the previous one.

A Kustomize layout for an application: `base/` with a Deployment, Service and ConfigMap generator; `overlays/dev` setting a name suffix, one replica and a development image tag; `overlays/prod` setting three replicas, resource patches, and an HPA added as a resource. `kubectl apply -k overlays/prod` deploys prod; `kubectl diff -k` previews.

A failing example: a values override sets `ingress.hostname` but the chart expects `ingress.host`. Nothing errors, the ingress keeps its default, and traffic goes to the wrong name. A values schema in the chart, or reading the rendered manifest, would have caught it.

Another failing example: a team vendors a chart whose CRDs live in `crds/`, upgrades the chart across a CRD schema change and finds the new fields rejected, because Helm never updated the stored CRDs. The fix is to apply the CRDs from the new chart version with `kubectl apply --server-side` first.

## Related problems and ideas

Terraform and OpenTofu can manage Helm releases and Kubernetes objects declaratively with a state file; Pulumi and cdk8s generate them from general-purpose languages. Operators encode lifecycle knowledge that charts cannot. OCI artifacts as the universal distribution unit (charts, policies, Flux and Argo sources) reduce the need for separate repository protocols. Config tools like KRM functions run small programs over manifests as a pipeline, which is where Kustomize and kpt aim. Ideas not yet mainstream include a typed, validated package format with dependency resolution across charts (Timoni's modules, the Carvel package model), and server-side rendering via custom resources so the cluster, not a client, performs the templating.

## Active research

Helm 4 development continues around server-side apply defaults, the plugin system, reproducible chart builds, content-based caching and supply-chain provenance. The Kustomize and SIG CLI maintainers work on resolving the embedded version gap and on improvements to patch validation. Research on infrastructure-as-code analyses misconfigurations that templating hides; academic and industry scanners check rendered manifests against benchmark policies. How to represent configuration as typed data with composition and policy, without a Turing-complete templating language, remains an open design question.

## Future direction

Expect Helm 4 adoption to proceed gradually with a long support period for Helm 3, more charts published with signatures and schemas, and rendered-manifests-in-Git workflows to rise, because they make review straightforward and reduce surprises from template evaluation at deploy time. Server-side apply with field ownership should make coexistence between tools and controllers less fragile. For an administrator, the durable habit is to treat rendered YAML as the artefact under review, whatever generated it (to verify current versions on the Helm and Kubernetes release pages).
