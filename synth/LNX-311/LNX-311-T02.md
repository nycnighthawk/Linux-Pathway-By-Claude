# Bootstrapping a cluster with kubeadm and making its control plane survive failures

## Define the problem

A Kubernetes cluster is not one program but a set of cooperating processes that must trust one another, find one another and agree on a configuration before the first workload can run. Someone has to create a certificate authority and issue a dozen certificates with the right names, write kubeconfig files for each component, start etcd, start the API server with the right flags, hand every worker a credential it may use exactly once to introduce itself, install a network plugin and a DNS service, and do all of that identically on the second and third control-plane machine. Done by hand the procedure is long and error-prone; one wrong subject name in a certificate produces a cluster that almost works. Done carelessly, it produces a single control-plane node whose death erases the cluster's ability to change anything.

Two linked questions are therefore in scope. First, how does an administrator get from three freshly installed Linux machines to a conformant cluster reproducibly and with an auditable configuration? Second, how should the control plane be arranged so that losing one machine, one zone or one component does not stop the cluster from accepting changes, and how much redundancy is worth paying for? This slice covers host preparation, the kubeadm workflow for the first control-plane node, joining further control-plane and worker nodes, the stacked and external etcd topologies, the load-balanced API endpoint that makes high availability work, and the trade-offs among them. Upgrades (T03), etcd recovery (T04) and managed services (T11) are separate slices.

## History and approaches

Early Kubernetes clusters were built with shell scripts shipped in the project's own repository, such as the kube-up family, which targeted a handful of clouds and were notoriously hard to extend. Kelsey Hightower's Kubernetes the Hard Way, first published in 2016, deliberately replaced all automation with manual steps so learners would meet every certificate and systemd unit; it remains a teaching standard, and distribution projects such as the Rocky Linux documentation have adapted it with their own labs. Between those poles came a long list of installers: Kubespray, which drives Ansible; kops, focused on AWS; Rancher's RKE and later k3s and RKE2, which bundle a distribution; Talos and other immutable operating systems that expose Kubernetes through an API instead of SSH; and the vendor installers of OpenShift and others.

kubeadm was started in 2016 by the cluster lifecycle special interest group with a modest goal: be the building block, not the whole solution. It would do only the Kubernetes-specific bootstrap (certificates, kubeconfigs, static pod manifests, tokens, mandatory add-ons) and leave machine provisioning, networking choices and load balancers to the caller. It was declared generally available in version 1.13. Early kubeadm did not support multiple control-plane nodes; high availability was possible only by copying certificates between machines manually. The join workflow for additional control-plane nodes, with an encrypted bundle of certificates uploaded to the cluster, arrived later and became stable in the middle of the 1.x series. Cluster API grew out of the same group as the declarative way to build many clusters, using kubeadm underneath as one of its bootstrap providers.

Approaches to control-plane high availability diverged in two places. The first is topology. The *stacked* topology puts an etcd member on each control-plane node: simple, cheap and the kubeadm default, but a failing node costs one API server and one datastore member together. The *external* topology runs etcd on separate machines: it decouples the failure domains and lets each tier be sized separately, at the price of more machines, more certificates and more things to patch. The second divergence is how clients find an API server. Some installers rely on a cloud load balancer; others on keepalived and HAProxy on the control-plane nodes; others on kube-vip, a static pod that holds a virtual address with leader election; others on DNS round robin, which is simple and weak because clients cache. The KubeVirt project's own planning notes for production follow the same logic when they describe running its components on dedicated nodes: keep the control machinery away from noisy workloads and make placement an explicit decision.

Lessons that shaped the present approach: make bootstrap a configuration file, not a pile of flags, so it can be reviewed and repeated; make every credential short-lived or rotatable; and treat the API endpoint as an address that must outlive any single machine. kubeadm's `controlPlaneEndpoint` setting exists for this reason, because a cluster initialised against the first node's own address cannot later be promoted to high availability without reissuing certificates (to verify against the current release notes for the exact limitations).

## Current state

**Host preparation.** Every node needs the same baseline. A supported Linux distribution and a unique hostname, MAC address and machine identifier (cloned virtual machines are a classic source of two nodes with the same identity). Time synchronisation, because certificates and leases depend on it. Swap disabled, unless the node swap feature is deliberately configured. The kernel modules `overlay` and `br_netfilter` loaded, and the sysctls that let bridged traffic pass through netfilter and allow IP forwarding. A container runtime, usually containerd, configured with the systemd cgroup driver so that the kubelet and runtime agree on how resource groups are managed; a mismatch between the two is a well-known cause of nodes that flap. The packages `kubeadm`, `kubelet` and `kubectl` at matching versions, pinned so an unattended update does not move them. Firewall ports opened between the nodes: 6443 for the API server, 2379 and 2380 for etcd, 10250 for the kubelet and the other control-plane ports documented by the project.

**Initialising the first control-plane node.** `kubeadm init` runs ordered phases that can also be invoked one by one: preflight checks, certificate generation under `/etc/kubernetes/pki`, kubeconfig generation, kubelet start, static pod manifests for etcd and the control-plane components, waiting for the control plane to answer, uploading the configuration and kubelet configuration as ConfigMaps, labelling and tainting the node, creating a bootstrap token and installing the CoreDNS and kube-proxy add-ons. A configuration file (`kubeadm init --config`) records the choices: the Kubernetes version, the `controlPlaneEndpoint`, the pod and service subnets, the certificate subject alternative names and the kubelet settings. The Arch Linux notes show the contrast between the flag-only and the configuration-file route, and the Kubernetes documentation instructs administrators to prefer the file for anything beyond a trial because flags cannot express all the options.

Afterwards the cluster is alive but not usable: nodes report NotReady and CoreDNS pods stay Pending until a pod network plugin is installed, a symptom explicitly listed in the Arch troubleshooting material. The network plugin must be chosen with the pod CIDR in mind; the Arch notes and the Cilium documentation both stress that the CIDR given to kubeadm must match what the plugin allocates, and Cilium's kube-proxy replacement mode requires skipping the kube-proxy add-on at init time so the two do not fight over service rules.

**Joining nodes.** `kubeadm init` prints a join command with a bootstrap token and the hash of the cluster CA's public key. The token is a credential, valid for twenty-four hours by default, that allows a node to request a signed kubelet certificate; the hash lets the joining node verify it is talking to the right cluster before it trusts anything. Workers run `kubeadm join` with those two values. Additional control-plane nodes add `--control-plane` and the certificate key obtained from `kubeadm init --upload-certs`, which encrypts the shared PKI material and stores it in a Secret that expires after two hours. Joining a control-plane node also adds a stacked etcd member to the existing etcd cluster, so the order of joins matters and joining several at once is discouraged.

**The shape of a highly available control plane.** A common arrangement has three control-plane nodes with stacked etcd, one load-balanced virtual address in front of the API servers, and workers that reach the control plane only through that address. Three nodes tolerate one failure, because etcd needs a majority; five tolerate two but cost more writes and more machines. A load balancer needs health checks against the API server's readiness endpoint, not just a TCP check, so a half-started server is not given traffic. The load balancer itself is a component that must not be a single point of failure: two keepalived and HAProxy instances, kube-vip, or a cloud load balancer with its own redundancy. Controller manager and scheduler run on every control-plane node but only one instance of each is active, chosen by lease-based leader election, so the failover time is bounded by the lease duration.

**Placement of workloads.** By default control-plane nodes carry a taint that keeps ordinary pods away. On a three-VM learning cluster all three machines are control-plane and workers at once if the taint is removed, which is acceptable for a lab and risky in production because an application's memory pressure can starve etcd. Dedicated workers separate the concerns; the KubeVirt guidance on restricting its components to chosen nodes is a concrete example of the same practice.

**Security posture of the bootstrap.** The Kubernetes STIG includes findings about the permissions and ownership of the kubeadm configuration file and the kubelet configuration, which should be readable only by root; kubeconfig files grant cluster-admin and are the most valuable files on the control plane. Certificates issued by kubeadm last one year and the cluster CA ten years, a fact that makes certificate renewal a scheduled duty (T07).

## Assessment: the good, the bad and the ugly

The good: kubeadm is small, upstream-maintained and predictable. Its output is the same standard layout every Kubernetes engineer recognises, so documentation and tooling apply. Its phases are idempotent enough to rerun after a failed step, and a configuration file turns an install into a reviewable document. The stacked topology is simple to reason about and enough for most clusters.

The bad: kubeadm does not provision machines, load balancers, storage or networking, so the real work is around it. Every choice it leaves open (runtime, plugin, endpoint, certificate policy) must be made by the administrator, and wrong early decisions are costly to reverse. A cluster built without a control plane endpoint cannot easily be made highly available later. Stacked topology couples the failure of an API server and an etcd member; if two of three control-plane machines are lost together, say by a shared hypervisor or rack, the cluster loses quorum and becomes read-only or unavailable. External etcd avoids coupling but doubles the number of things to monitor, patch and back up.

The ugly: the failures that actually happen are mundane. Cloned virtual machines with the same product identifier join and then fight over one node identity. A swap partition re-enabled after a reboot stops the kubelet. A time skew makes freshly issued certificates look not yet valid. A bootstrap token expires while someone is on holiday and the new node cannot join, so the administrator must generate a new token and may find that the stored certificate key expired too. A firewall that drops port 2380 allows the first node to start but makes the second control-plane join hang at the etcd step. Quorum arithmetic is misunderstood: a team builds a two-node control plane believing it has redundancy, when it tolerates no failure at all and is less reliable than one node because either machine's loss stops writes.

Mitigations: use a configuration file under version control; automate host preparation with the configuration management tools from the enterprise course; test the join of a third control-plane node before declaring the cluster done; put the control-plane endpoint on a stable DNS name; monitor etcd leader changes and certificate expiry; spread control-plane nodes over failure domains that are really independent.

## Applications beyond this domain

The quorum rules that decide how many control-plane nodes to run are the same ones that apply to any Raft or Paxos system, from Consul and Vault clusters to distributed databases such as CockroachDB: odd member counts, majority commits, and the rule that failure domains must be independent for redundancy to be real. The bootstrap trust model, where a joining node proves knowledge of a short-lived secret and verifies the authority by hash, is the same pattern used by other cluster joins in software such as Nomad and some Linux high-availability stacks. Virtual IP failover with keepalived or kube-vip is the older VRRP idea, also used for routers and database proxies. Treating installation as a declarative document is the principle behind Cluster API, Terraform modules and image-based systems such as Talos.

## Examples

A working three-machine lab: three Debian or Rocky virtual machines named cp1, cp2 and cp3, a fourth address reserved for the API endpoint through kube-vip. On cp1, write a configuration file with `controlPlaneEndpoint` pointing at the virtual address, the pod subnet matching the chosen network plugin and the systemd cgroup driver, then run `kubeadm init --config kubeadm.yaml --upload-certs`. Install the network plugin, wait for CoreDNS to go Running, then run the printed control-plane join on cp2 and cp3, one after the other. Verify with `kubectl get nodes`, `kubectl -n kube-system get pods -l component=etcd` and `etcdctl member list` run from inside an etcd pod. Finally power off cp2 and confirm the API still answers and new Deployments still schedule.

A failing example: the same lab, but the administrator initialised cp1 without a control-plane endpoint, using the node's own address. cp2 joins fine as a worker, but when promoted to a control-plane node the join complains about certificate names, because the API server certificate lacks the shared address. The fix is to add the address to the certificate's subject alternative names, regenerate the API server certificate and update every kubeconfig that points at the old name; avoiding the whole exercise is the reason to decide the endpoint first.

A second failing example from the troubleshooting notes: after init the single node shows NotReady and CoreDNS is Pending. Nothing is broken; no network plugin has been installed. Another: CoreDNS crash-loops because the node's resolver file points to a local address that loops back to itself, a case documented on the Arch wiki and fixed by giving the kubelet a clean resolver file.

## Related problems and ideas

Single-node clusters (k3s, kind, minikube) answer the developer's version of the problem and are covered by the inner-loop slice of the application delivery course. Immutable operating systems (Talos, Flatcar with kubeadm, Fedora CoreOS) remove SSH and package managers from the equation and make nodes interchangeable. Cluster API and the managed control plane services (T11) turn "build a cluster" into an API call. Hosted control planes run the API servers as pods in a management cluster, trading independence for density. Some projects explore leaderless or embedded-database control planes (SQLite with Kine, dqlite) for edge sites where three machines are too many. Alternatives to a stacked etcd that are not mainstream include using a managed distributed database as the Kubernetes datastore through the Kine adapter, which gives up the native watch semantics in exchange for operational familiarity.

## Active research

The cluster lifecycle group continues to work on making kubeadm configuration versioned and strictly validated, on better support for external etcd managed by the etcdadm project, on in-place changes of the control-plane endpoint, and on reducing the privilege and lifetime of bootstrap secrets. Investigations into API server availability measure how long clients see errors during control-plane failover and what retry policies hide it. Work on node identity (binding a node's credential to hardware attestation) aims to make the join step resistant to a leaked token. How best to run etcd with lower disk requirements on small machines is still open, as is whether the stacked topology should stay the default. Because each of these moves with every minor release, treat concrete flag names as something to verify against the documentation for your version (to verify).

## Future direction

The trend is away from bespoke bootstrap scripts and toward declarative machine and cluster definitions reconciled by controllers: Cluster API, GitOps for cluster add-ons and image-based nodes whose only configuration is a document. Expect certificate rotation for the control plane to become more automatic, kube-vip style address management to move into the platform, and dual-stack and IPv6-only clusters to appear in default examples. For an administrator the durable skill is not the exact commands but knowing which decisions are hard to change later: the control-plane endpoint, the pod and service address ranges, the datastore topology and the runtime's cgroup driver. Decide those on paper first.
