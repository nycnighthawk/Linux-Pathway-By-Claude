# How a Kubernetes cluster is put together: one database, one front door and many reconcilers

## Define the problem

Running one container on one host is a solved problem. Running thousands of them across hundreds of machines, keeping each application at the replica count its owner asked for, replacing instances when hosts die, placing work where resources are free and letting operators change any of this without downtime, is not. The operator needs a single place to state what should exist, and a set of machinery that continuously makes the real world match that statement. Failure here is concrete: a node loses power and its workloads silently vanish; two schedulers place conflicting work on the same machine; a configuration change is half-applied and nobody can say which half; an administrator logs into hosts and starts processes by hand, so the next reboot erases the knowledge of what ran where.

Earlier tools covered slices of this. Configuration managers such as Puppet and Ansible described desired host state but did not place workloads or react to failures within seconds. Init systems and process supervisors restarted a process on one machine and knew nothing about other machines. Cluster resource managers of the Pacemaker family handled failover of a few named services between a few nodes, using fencing and quorum, but were not designed to schedule thousands of short-lived, resource-limited units. Batch schedulers handled queues of jobs, not long-running services with rolling updates and service discovery. The gap was a general, API-driven control system for fleets of containers, where the unit of work is declared, the cluster state is stored durably in one place and independent controllers do the converging.

This slice covers the architecture an administrator must hold in their head before touching anything else in the course: the control plane components (the API server, the datastore etcd, the scheduler, the controller manager and the cloud controller), the node components (the kubelet, the container runtime reached through the container runtime interface, and the service proxy), how they talk, where they run, which of them is critical to which failure, and how to read their state. Installation (T02), upgrades (T03), etcd backup (T04), scheduling policy (T05), storage (T06) and access control (T07) each get their own slice and are only previewed here.

## History and approaches

The lineage starts inside Google. Borg, described publicly in a 2015 paper, ran Google's production workloads with a central master called the Borgmaster, an agent on every machine called the Borglet and a separate scheduler that read the master's state. Omega, a research successor, tried a shared-state model where several schedulers made optimistic, transactional updates against one store, and its lesson, that the store and its consistency rules matter more than any single scheduler, survived into Kubernetes. The Kubernetes project was announced in 2014 and reached version 1.0 in July 2015, when it was donated to the newly formed Cloud Native Computing Foundation. Its architects kept the shape of Borg (a central API, per-node agents, a pluggable scheduler) but changed the model: everything is an API object with a spec and a status, and every behaviour is a controller watching objects, so the system could be extended by anyone without patching the core.

Competing approaches filled the same period. Apache Mesos offered two-level scheduling: the Mesos master offered resources to frameworks, and frameworks decided what to run, which suited heterogeneous workloads but pushed complexity onto every framework author. Docker Swarm, integrated into the Docker engine, was simpler to start but had a smaller extension surface and a single vendor behind it. Nomad from HashiCorp stayed deliberately small, a single binary with a scheduler and no mandatory sidecar ecosystem, and it remains in use where operators value that simplicity. OpenStack and the other infrastructure clouds solved virtual machine provisioning, not application convergence. Kubernetes won mainly because its object model was extensible through custom resources, because the project shipped with a conformance programme and because every large cloud vendor offered a managed variant.

The architecture itself went through painful changes that explain today's layout. Early releases bound the kubelet tightly to Docker, calling the Docker daemon directly, and the rkt project and later runtimes needed their own special cases in the kubelet source. The container runtime interface, introduced around 2016 and stabilised in following releases, defined a gRPC contract between the kubelet and any runtime, so containerd, CRI-O and others could be swapped in. In version 1.24, released in 2022, the built-in Docker shim was removed; clusters that had relied on it had to move to containerd or CRI-O or to an external adapter, and many administrators were surprised because their workloads' images kept working while their tooling that talked to the Docker socket on nodes stopped. Another long migration moved cloud-specific code out of the core binaries into a separate cloud controller manager, and storage drivers out of the tree into the container storage interface. Datastore history matters as well: Kubernetes started with etcd version 2, moved to version 3 with its watch and transaction features, and set limits (a default quota of roughly two gigabytes of datastore size, and a request size limit) after operators filled the database with oversized objects.

The pattern that emerged is this. Keep a small, strongly consistent store behind one API gateway. Make every other component a client of that gateway, never of the store. Express intent as declarative objects, and let level-triggered controllers compare what exists with what was requested. Push everything that varies between environments (runtimes, networks, storage, clouds) behind narrow interfaces.

## Current state

**The datastore.** All cluster state lives in etcd, a distributed key-value store that uses the Raft consensus algorithm. A write is acknowledged only after a majority of members have persisted it, which is why production clusters use three or five members: three tolerates one failure, five tolerates two, and even numbers add cost without adding fault tolerance. Kubernetes keys are namespaced under a prefix (by default `/registry`), every object carries a resource version taken from etcd's revision counter and clients can watch for changes from a given revision. etcd is the one component whose loss without a backup means losing the cluster's definition of itself, which is why a whole slice of this course (T04) concerns snapshots and restores. The project's own documentation lists the mitigations for datastore loss: highly available members, reliable storage underneath them and periodic snapshots, and it stresses restoring only with every API server stopped.

**The API server.** `kube-apiserver` is the only component that talks to etcd. It is a stateless, horizontally scalable HTTPS front end. A request passes through authentication (client certificates, bearer tokens, service account tokens, OIDC), authorisation (usually RBAC, see T07), a chain of admission controllers that can mutate or reject the object, validation, and finally persistence. It also serves watches, converts between API versions, hosts the aggregated and custom resource APIs, and writes the audit log. Because it is stateless, a highly available control plane simply runs several instances behind a load balancer; because every other component depends on it, its availability bounds the whole control plane's availability. Node components and controllers are all clients; none of them reach etcd directly, and security hardening guides such as the DISA STIG for Kubernetes check that each component's secure ports, protocols and client-certificate options are set so that only the API server may present itself as an etcd client.

**The controller manager.** `kube-controller-manager` bundles dozens of control loops in one process: the ReplicaSet and Deployment controllers, the node lifecycle controller that marks silent nodes NotReady and later evicts their pods, the endpoint and EndpointSlice controllers, the service account and token controllers, the garbage collector and many more. Each loop watches some objects through the API server, compares status with spec and issues the writes that close the difference. Because they are level-triggered, they repair missed events: after a restart a controller re-lists everything and reaches the same conclusion it would have reached had it never been down. Several replicas can run, but leader election through a lease object means only one is active.

**The scheduler.** `kube-scheduler` watches for pods that have no node assigned, and for each one runs a two-stage pipeline: filter out nodes that cannot host the pod (not enough CPU or memory, a taint without a toleration, a volume that lives elsewhere, affinity violations) and then score the remaining nodes and pick the best. Its only output is a binding written through the API server, naming the node. It never starts anything. That separation is why custom schedulers can run side by side with the default one, selected per pod by name, and why KubeVirt documentation shows how to deploy a second scheduler for virtual machine workloads. The scheduling framework offers extension points for plugins, which is how policies in T05 (affinity, spread, priorities) are implemented.

**The cloud controller manager.** When the cluster runs on a provider, a separate process holds the provider-specific loops: discovering node metadata, wiring route tables and provisioning load balancers for services of type LoadBalancer. On bare metal it is usually absent, which is why LoadBalancer services stay pending until a project like MetalLB is installed (T10 of the networking course).

**The kubelet.** On every node the kubelet is the agent that turns assigned pod specs into running containers. It watches the API server for pods bound to its node, asks the runtime to create sandboxes and containers, mounts volumes, runs probes, reports node and pod status, and enforces resource limits through cgroups. It also reads static pod manifests from a directory on disk, by default `/etc/kubernetes/manifests`. This is how kubeadm bootstraps a cluster: the API server, controller manager, scheduler and etcd are written as static pod manifests and the kubelet, which runs as an ordinary systemd service outside any container, starts them. The Kubernetes logging documentation draws exactly this line: the kubelet and the runtime are host processes, not containers, while the scheduler, controller manager and API server usually run as static pods and kube-proxy as a DaemonSet. The Arch Linux packaging notes point out a consequence, namely that the control plane binaries are not the ones installed by the operating system's package manager, so a distribution upgrade does not upgrade them.

**The container runtime and the CRI.** The kubelet speaks the container runtime interface, a gRPC API with two services: the runtime service (create and stop pod sandboxes and containers, exec, attach, port-forward) and the image service (pull, list, remove). The common implementations are containerd and CRI-O, both of which delegate the actual process creation to a low-level OCI runtime such as runc or crun, and optionally to sandboxed runtimes such as gVisor or Kata through RuntimeClass (see the security course). The kubelet finds the runtime through a Unix socket path, for example the containerd socket, and `crictl` is the debugging client that talks to the same socket. A node whose kubelet cannot reach its runtime reports itself NotReady, which is the first thing to check when a freshly joined node never becomes ready.

**The service proxy and the network plugin.** `kube-proxy` programs packet rules on each node so that virtual service addresses reach healthy pod addresses; some network plugins, notably Cilium in its replacement mode, take that job over completely. Pod-to-pod networking itself is provided by a plugin that follows the container network interface and is covered in the networking course. DNS inside the cluster is a deployment of CoreDNS in the system namespace.

**How a pod comes to life.** A user submits a Deployment. The API server authenticates, authorises, admits and stores it. The Deployment controller creates a ReplicaSet, whose controller creates pod objects without nodes. The scheduler binds each pod to a node. The agent on the chosen machine sees the binding, asks the runtime to pull the image and start the containers, then writes status back. Each step is a write to etcd followed by a watch notification, so an administrator who understands the chain can find where it stalled: no ReplicaSet means the controller manager is unhealthy, a pod stuck Pending with no node means the scheduler or a filter problem, a pod assigned but stuck ContainerCreating points to the kubelet, runtime, image pull or volume mount.

**The generalised pattern.** One strongly consistent store; one API gateway that is the only writer; independent controllers that each own a small slice of reality and converge it; and narrow plugin interfaces (CRI, CNI, CSI) for everything environment-specific. This is the control-loop pattern of a thermostat applied to infrastructure.

## Assessment: the good, the bad and the ugly

The good: the design degrades gracefully. If the control plane goes down, running containers keep running because the kubelet and runtime do not need it for existing pods; what stops is change, not service. Level-triggered reconciliation tolerates restarts, duplicate events and partial failures. The API is uniform, so tooling (kubectl, Helm, GitOps controllers, operators) works against every kind of object, including ones you define yourself. Because all state is in one store, backup and disaster recovery have one focus.

The bad: the control plane is heavy for small deployments. A highly available setup wants three control-plane nodes and a load balancer before any application runs. etcd is sensitive to disk latency and clock behaviour: slow fsync causes leader changes and API timeouts, so it prefers dedicated fast disks, and its size quota can be hit by chatty controllers or large objects, putting the cluster into a read-only alarm state until compaction and defragmentation. Version skew rules are strict: the kubelet may lag the API server by a few minor versions, kubectl by one, and the control plane components must be upgraded in an order, which is why upgrades are a slice of their own. Certificates created at install time expire, typically after a year, and a cluster that nobody upgraded for a year may fall over on the expiry date.

The ugly: operational knowledge is spread over several layers. A symptom such as pods that never start may live in the scheduler, the kubelet, the runtime, the network plugin or storage, and the answer lies in logs on different hosts. Static pods blur the line between "managed by Kubernetes" and "managed by the host": editing a manifest file restarts a control-plane component without any API call or audit trail. Deprecations are real; the Docker shim removal, the retirement of PodSecurityPolicy, and the removal of in-tree cloud and storage code each broke someone. Security posture inherits a large surface: any principal who can write to etcd, or who holds a kubelet credential with broad rights, can reach everything, so hardening guides spend most of their pages on those two.

Mitigations are well known. Run at least three etcd members on separate failure domains, monitor leader changes and commit latency, snapshot on a schedule and rehearse restores. Keep the API server behind a health-checked load balancer. Pin versions and follow the skew policy. Use a certificate renewal procedure and put the expiry date in monitoring. Collect logs from the kubelet and runtime centrally, because they run outside the cluster's own logging path.

## Applications beyond this domain

The reconcile-loop architecture escaped container orchestration. Operators and custom resource definitions (T09) apply it to databases, certificates and cloud resources: Crossplane and the cloud provider operators let you declare a managed database as a Kubernetes object, and a controller converges it. Cluster API treats whole Kubernetes clusters as declared objects. KubeVirt runs virtual machines as custom resources with a launcher pod per machine, a pattern the virtualisation engineering course revisits. GitOps tools (Argo CD, Flux) are controllers whose desired state sits in a Git repository. Outside Kubernetes the same idea appears in Terraform-style plan and apply cycles, in Chef's convergence runs, in HVAC thermostats and in the control loops of industrial automation; the carried-over lesson is to store intent separately from observation and compare them repeatedly rather than execute commands once.

## Examples

A worked healthy case: an engineer creates a three-replica Deployment. Within a second or two the API shows one ReplicaSet and three pods; the scheduler assigns them to three nodes; the kubelets pull the image and report Running. The engineer then powers off one node. After the node controller's grace period the node turns NotReady, pods on it are marked for eviction after a toleration timeout, the ReplicaSet controller creates replacements, and the scheduler places them on the remaining nodes. No human acted; each controller did its small part.

A failing case: after a power outage, the API server on a single-control-plane cluster does not come back because the etcd static pod manifest points to a data directory that was on a volume that did not mount. `kubectl` returns connection refused. The administrator, working on the control plane node itself, uses `crictl ps -a` to see the etcd container exiting, reads its log with `crictl logs`, finds the missing directory, fixes the mount, and the kubelet restarts the static pod without any API involvement. The lesson is that when the API is down, the only tools left are the node-level ones: systemd, the kubelet journal, `crictl` and the manifests directory.

A security example from the DISA benchmark: it checks that etcd requires client certificates and that the API server, scheduler and controller manager are configured with secure ports and protocols. An administrator who finds the etcd peer endpoint using plain HTTP on a private network has found a finding worth fixing, because the private network is exactly where an attacker with one compromised workload would be.

A commissioning example from the Kubernetes the Hard Way tutorials, such as the one Rocky Linux adapted: the learner generates a certificate authority, issues separate certificates for each component, writes systemd units for the API server, scheduler and controller manager and installs etcd by hand. Nothing in a kubeadm install is magic after that; kubeadm automates the same file layout.

## Related problems and ideas

HashiCorp Nomad and the older Mesos show that a scheduler does not need to be Kubernetes: Nomad pairs a leader-based server cluster with client agents and avoids a separate datastore by embedding Raft in the servers themselves. k3s and similar distributions replace etcd with SQLite or an external SQL database through an adapter, trading the strict Raft model for a lighter footprint on edge hardware. Virtual kubelet projects let a node object front something that is not a node at all, such as a serverless platform. Hosted control planes and projects like Kamaji or vCluster run control planes as pods inside another cluster, so tenants get many API servers cheaply. Alternative ideas that are not yet mainstream include peer-to-peer or datastore-less schedulers for very large fleets, and proposals to give the API server a pluggable storage backend with different consistency trade-offs. For comparison with cluster resource managers, the high availability course covers Pacemaker, whose fencing model solves a different problem (protecting shared storage from split brain) that Kubernetes mostly avoids by making pods disposable.

## Active research

Open questions the community works on include scaling the control plane past the tens of thousands of nodes where etcd write throughput and watch fan-out become the limit, with efforts such as watch caches, streaming list responses and consistent reads from cache. Scheduler research looks at gang scheduling for machine learning jobs (Kueue, Volcano, and the batch working group), dynamic resource allocation for GPUs and other devices, and topology-aware placement. Security research studies how to bind node identities to workloads more tightly and reduce the privilege of the kubelet credential. Academic work compares Borg, Omega and Kubernetes designs for resource efficiency, and reliability engineers publish incident reviews of control-plane failures. Version numbers move quickly: at the time of writing the project ships three minor releases a year and supports roughly the latest three, so check the release page for the current minor (to verify).

## Future direction

Expect continued shrinking of the in-tree footprint, further movement of features through alpha, beta and stable gates, and more declarative, API-driven management of the cluster itself (Cluster API, hosted control planes). The sidecar model is being reworked so that sidecar containers have defined start and stop ordering within a pod; dynamic resource allocation is maturing; and in-place pod resource resizing is moving toward general availability (to verify the exact release). Watch the Kubernetes enhancement proposals repository for graduations, the release notes of each minor for removals, and your distribution's support windows, because administrators carry the real cost of each deprecation.
