# Storage that lives in boxes and fabrics: hardware RAID, Fibre Channel SANs and multipath

## Define the problem

The earlier topics assumed that a disk is a device the operating system sees and controls. In many data centres it is not. A server may have a RAID controller that hides its physical drives behind virtual ones, and the operating system never sees a failed drive unless the controller says so. A server may have no local data disks at all and reach its storage through a **storage area network** of switches and adapters, to an array shared by hundreds of hosts. The same volume may be visible down four different cables, and without help, Linux treats those as four different disks.

Three questions follow, and this topic addresses them at orientation depth, because the equipment is rarely available in a lab. First, how does hardware RAID differ from the software RAID of the earlier topic, and what must an administrator know to work safely with it? Second, how does Fibre Channel storage reach a host: what names, zones and masks decide which LUNs a server sees? Third, how does Linux turn many paths to one LUN into one reliable device, survive the loss of a cable, adapter, switch or controller port, and still present a stable name? The answer to the third is **device-mapper multipath**. An administrator who meets this equipment should be able to recognise the parts, read the status, avoid the destructive mistakes, and know when to call the storage team. [src: rhel-10-docs 02a6eb025648f76e]

## History and approaches

Hardware RAID appeared when host CPUs were too slow to compute parity and when operating systems lacked software RAID. A controller card with its own processor, memory and (usually) a battery-backed write cache presents one or more **virtual drives** built from physical disks, with the RAID level, stripe size, rebuild policy and cache mode configured in the controller's firmware or vendor tool. The operating system sees an ordinary disk and needs only a driver. Software RAID later caught up in capability and often in speed, and for years the debate was between the controller's cache and monitoring conveniences on one side, and transparency, portability and lack of a proprietary format on the other. Many current servers offer both: a controller in RAID mode, or in "HBA" or "JBOD" mode that passes disks straight through to the operating system so that md, LVM, Btrfs or ZFS manage them. [src: debian-handbook 72345c943b3786b2]

Fibre Channel (FC) is the network built for SCSI storage. Its frames are delivered losslessly through credit-based flow control on dedicated switches (a **fabric**), with host bus adapters (HBAs) at the servers and ports on the array controllers. Every port has a World Wide Port Name (WWPN) and every node a World Wide Node Name (WWNN), 64-bit identifiers written like `21:00:00:24:ff:4c:9a:11`. The fabric adds **zoning**: the switch configuration says which WWPNs may talk to which, and the array adds **LUN masking**: it presents a given LUN only to listed initiator WWPNs. Together they play the role that IP addresses, VLANs and ACLs play on an iSCSI network. FC grew through speeds of 1, 2, 4, 8, 16, 32, 64 and 128 Gbit/s; FCoE carried the same frames over lossless Ethernet and never displaced FC; iSCSI and NVMe over Fabrics (including FC-NVMe) now compete for new deployments.

Multipath came from the need to remove single points of failure. A mission-critical server has two HBAs, connects each to a separate switch, and each switch to both controllers of the array: any one component can fail and the storage stays reachable. The cost is that the SCSI layer finds the same LUN once per path. Linux first had an `md` multipath mode, which is now deprecated in favour of the device-mapper based **multipath-tools**: a kernel target (`dm-multipath`) plus the `multipathd` daemon that discovers paths, groups them by the LUN's unique identifier (its WWID), watches their health, and presents a single `mpath` device. [src: man-pages 6dd328e7f2234d70]

The failures that shaped this area are mostly operational. Controller firmware that handed disks to the wrong volume after a replacement; foreign-configuration prompts at boot where choosing the wrong button destroyed an array; write caches with failed batteries that silently turned a write-back cache into data loss at the next power cut; zoning errors that exposed a LUN to two hosts that both mounted it read-write; and multipath configurations that disagreed with the array's failover model, producing "path flapping" that stalled I/O. The lessons are encoded in vendor tuning guides and in Red Hat's multipath configuration chapters. [src: rocky-docs 6586b3910e09da58]

## Current state

### Hardware RAID: what to know

Common controllers include Dell PERC, Broadcom (LSI) MegaRAID and HPE Smart Array. Concepts: **physical drives**, **drive groups** or **arrays**, **virtual drives** (the logical disks the operating system sees), **hot spares**, **stripe size**, **cache policy** (write-through, write-back, write-back only with a healthy battery or capacitor), **read-ahead**, **patrol read** (background media scan) and **consistency check** (parity verify). The operating system sees only the virtual drive, as `/dev/sdX`, with the driver in the kernel (`megaraid_sas`, `mpt3sas`, `hpsa`, `smartpqi`). Monitoring needs the vendor tool (`storcli64` or `perccli64`, `ssacli`) or the controller's management interface, because `smartctl` on the virtual drive says little: query individual disks with `smartctl -a -d megaraid,N /dev/sda` and the equivalent for other controllers. `lsscsi`, `lsblk -o NAME,MODEL,SIZE,ROTA` and `dmesg | grep -i raid` show what the OS sees.

Operational rules: know the cache mode and battery health before trusting write-back; keep controller firmware and the configuration backed up (export with the vendor tool); label the physical slots; replace a failed drive with the same size or larger and let the controller rebuild; never initialise or clear a configuration without confirming which disks hold data. The Rocky Linux recovery guide highlights the **foreign configuration** trap: when a controller finds disks carrying another configuration (after a controller swap, or moving disks between servers), it asks whether to **import** (keep the data) or **clear** (destroy the mapping and make the data unreachable). Choosing wrongly is irreversible, so confirm with the storage team and photograph the screen before pressing anything. File-system repair on top of a degraded or rebuilt virtual drive follows the usual rules (`xfs_repair`, `e2fsck`), after the controller state is healthy. [src: rocky-docs eaf133edcfd37d39] [src: rocky-docs 07510ea7049562db]

The choice between RAID and pass-through is a design decision: with hardware RAID, the controller's cache accelerates writes and the administrator replaces drives by hot-swap; with HBA mode, file-system checksums (Btrfs, ZFS) and software RAID provide integrity and portability. One failure domain deserves emphasis: the controller itself. A dead controller means a dead array until an identical or compatible controller reads the metadata. [src: archwiki c717377b7eda16d3]

### Fibre Channel: how a host sees a LUN

On the host: `ls /sys/class/fc_host/` lists FC adapters; `cat /sys/class/fc_host/host1/port_name` gives the WWPN to hand to the storage team; `port_state` shows `Online` or `Linkdown`; `/sys/class/fc_remote_ports/` lists array ports seen through the fabric; `systool -c fc_host -v` summarises (from the `sysfsutils` package); `lsscsi -g` lists SCSI devices with their host, channel, target and LUN numbers; `lsblk -S` shows the transport. To discover a new LUN: `echo "- - -" > /sys/class/scsi_host/host1/scan` (wildcards for channel, target, LUN) or `rescan-scsi-bus.sh` (from `sg3_utils`), and for a resized LUN, `echo 1 > /sys/block/sdX/device/rescan`. To remove a LUN before the array unmaps it: unmount, deactivate dependent layers (`blkdeactivate` unwinds LVM and md in order), `echo 1 > /sys/block/sdX/device/delete`. Removing a device that is still in use or that multipath still tracks causes I/O errors and hangs, so follow the order carefully. [src: man-pages ba1bd22b55bb9dc3]

On the array and fabric (not visible from Linux): zones in the switch, host groups and LUN masks on the array, and ALUA (asymmetric logical unit access) states per port group, which tell the host which paths are optimised (owning controller) and which are merely available.

### Device-mapper multipath

```bash
dnf install device-mapper-multipath          # apt install multipath-tools
mpathconf --enable --with_multipathd y       # RHEL: writes a default /etc/multipath.conf, starts the daemon
systemctl enable --now multipathd
multipath -ll                                # list multipath maps and their paths
multipath -v2                                # (re)create maps, verbose
multipathd show paths;  multipathd show topology
multipathd reconfigure                       # re-read the configuration without a restart
multipath -f mpatha                          # flush (remove) one map;  multipath -F flushes all unused maps
```

`multipath -ll` prints, for each map, a line with its name or alias, the WWID in parentheses, the vendor and product, then **path groups** with a priority and status, and under each group its paths with their `sdX` devices, SCSI addresses (`host:channel:target:lun`), device major and minor, and states such as `active ready running`. Healthy dual-path output has two groups for active/passive arrays (one `active`, one `enabled`) or one group with all paths for active/active arrays; `failed faulty` marks a dead path. The device appears as `/dev/mapper/mpatha` (or an alias or the WWID if `user_friendly_names` is off), and `/dev/disk/by-id/dm-uuid-mpath-<wwid>`; you must use that device, not the underlying `sdX` ones. [src: rhel-10-docs 02a6eb025648f76e]

The configuration file `/etc/multipath.conf` has sections:

```
defaults {
    user_friendly_names yes
    find_multipaths     yes
    path_grouping_policy group_by_prio
    path_selector       "service-time 0"
    failback            immediate
    no_path_retry       queue
}
blacklist {
    devnode "^sr[0-9]+"
    wwid    "3600508b1001c1234567890abcdef0000"      # the local boot disk
}
multipaths {
    multipath {
        wwid   360000000000000000e00000000010001
        alias  oradata
    }
}
devices {
    device { vendor "EXAMPLE" product "ARRAY" path_checker tur  prio alua  hardware_handler "1 alua" }
}
```

Settings that matter: `find_multipaths` (only create maps for devices with more than one path or on an explicit list, so that local disks are left alone), `user_friendly_names` and `alias` (naming), `path_grouping_policy` (`failover`, `multibus`, `group_by_serial`, `group_by_prio`, `group_by_node_name`), `path_selector` (`round-robin 0`, `queue-length 0`, `service-time 0`), `prio` (`alua`, `const`, `random`), `path_checker` (`tur`, `readsector0`, `directio`), `failback`, `no_path_retry` (`fail`, `queue`, or a retry count: how long I/O is queued when all paths are gone), `rr_min_io_rq`, `fast_io_fail_tmo` and `dev_loss_tmo` (when to give up on a lost FC port), and `blacklist` and `blacklist_exceptions`. Vendor-specific `devices` entries are built in for common arrays, so do not override them without the vendor's guidance; run `multipathd show config` to see the effective merged configuration. When the root file system is on multipath, enable it in the initramfs (`dracut` with `rd.multipath=default`, as listed in the `dracut.cmdline(7)` manual) and rebuild after changing the config. [src: man-pages 281cdffe9fa25b40] [src: rhel-10-docs 8b51d6044316aba4]

On top of the `mpath` device the usual layers apply: partition (kpartx creates `mpatha1`), LVM physical volume (with `multipath_component_detection` and a devices file that lists only the mpath device, never the underlying paths), file system, mounted with `_netdev` and `nofail` in fstab for non-boot volumes.

### Boot from SAN and clustering

A server can boot from an FC LUN: the HBA's firmware or the UEFI driver is set with the array's WWPN and LUN; the installer must be told to enable multipath at install time, or the root device will be one path and failover will not protect the system. Clusters use shared LUNs with fencing and a cluster file system or exclusive failover, as in the high-availability material of this curriculum. [src: rocky-docs 502048b210f24670]

### Troubleshooting order

First the physical layer (link lights, `port_state`, error counters in `/sys/class/fc_host/host*/statistics/`). Then name resolution: does the host's WWPN appear in the fabric zone and the array's host group? Then SCSI discovery (`lsscsi`, `dmesg`). Then multipath (`multipath -ll`, `multipathd show paths`, journal messages from `multipathd`). Then LVM and the file system. A frequent surprise is that a path appears healthy but returns I/O errors because ALUA state is `unavailable` on the standby controller; the `prio alua` setting and the right hardware handler fix that.

## Assessment: the good, the bad and the ugly

**The good.** Hardware RAID controllers with healthy battery-backed cache absorb write bursts and hot-swap drives with little operator skill, and shift parity work from the host. SANs give shared, centrally managed, snapshot-capable storage with proven availability, strong separation from the data network, and tight performance control. Multipath removes the cable, adapter, switch and controller port from the list of single points of failure, and the Linux implementation is mature, scriptable and well documented.

**The bad.** Everything is vendor-specific. Each controller and array has its own CLI, terminology, firmware lifecycle and failure behaviour; the operating system sees little of it. Hardware RAID creates lock-in to a metadata format. Debugging crosses organisational boundaries (server, network, storage teams). Multipath configuration is delicate: a wrong `path_grouping_policy` or `no_path_retry` produces stalls that look like application bugs. Costs are high, and FC skills are a specialist niche.

**The ugly.** Silent, irreversible actions. Clearing a foreign configuration. Replacing the wrong drive in a degraded array. Presenting a LUN to two hosts that both mount it. Removing an `sdX` device that multipath still tracks. Running with a failed cache battery while believing writes are protected. A resized LUN where the file system is grown before every path has been rescanned. And the organisational ugly: the storage team changes the zoning, and the server team learns of it through errors. [src: rocky-docs 6586b3910e09da58]

## Applications beyond this domain

The path-redundancy idea is general: bonded or teamed network interfaces, dual power feeds, redundant DNS servers and anycast are the same pattern of removing single points of failure. In virtualisation, hypervisor hosts commonly use FC or iSCSI shared datastores with multipath, and cloud providers hide the same mechanism behind their volume attachments. Storage drivers for containers have to cope with shared storage semantics, as the container runtime documentation on shared storage notes. Hardware RAID's cache logic reappears in SSD controllers and in storage appliances; zoning and masking reappear as network policy and as access control in object stores. Server-hardening guides treat firmware and out-of-band management interfaces on RAID controllers as part of the attack surface, with the same patching and credential rules as the host. [src: docker-docs 00a3f5a5ca82f3e9] [src: nist-sp800-guides 1fe219e108e897bb]

## Examples

**Check that a LUN has two healthy paths.**

```bash
multipath -ll
# a map shows ... status=active ... two paths each "active ready running"
multipathd show paths format "%d %t %T %o %c"
```

**Find the WWPNs to give the storage team.**

```bash
for h in /sys/class/fc_host/host*; do printf "%s %s\n" "$h" "$(cat $h/port_name)"; done
```

**Add a new LUN after the array has presented it.**

```bash
for h in /sys/class/scsi_host/host*; do echo "- - -" > $h/scan; done
multipath -r && multipath -ll | tail -n 12
```

**Retire a LUN cleanly.**

```bash
umount /srv/san && vgchange -an vg_san
multipath -f mpathb
# then remove each underlying path
echo 1 > /sys/block/sdc/device/delete; echo 1 > /sys/block/sdd/device/delete
```

**Give a LUN a stable name.** In `/etc/multipath.conf` add a `multipath` block with its `wwid` and an `alias`, then `multipathd reconfigure`; use `/dev/mapper/<alias>` in fstab or LVM.

## Related problems and ideas

This topic joins several others. **iSCSI** (earlier in this course) offers the same SCSI semantics over IP, and multipath applies to it the same way. **Software RAID and LVM** can replace a controller where portability matters, and LVM and multipath together require careful device filtering so that LVM never scans the underlying paths. **NVMe over Fabrics** brings native multipathing inside the NVMe driver (`nvme list-subsys` shows paths), with ANA (asymmetric namespace access) replacing ALUA. **Boot and install** matter, because root on multipath must be configured early. **Clustering and fencing** deal with LUNs visible to several hosts. **Monitoring and capacity planning**: array-level thin provisioning and snapshots complicate the numbers that `df` shows. **Change control**: zoning and masking changes need a process, since a mistake takes storage away from running servers.

## Active research

Development effort goes into NVMe multipathing and fabrics (native multipath, ANA, TCP and RDMA transports, discovery controllers and boot over NVMe-oF), better integration of multipath-tools with systemd and udev, and automation of storage provisioning through declarative APIs (Redfish, Swordfish) in place of vendor CLIs. Controller vendors are moving toward firmware that exposes more health data to the host through standard interfaces, and researchers examine failure statistics of drives and controllers to improve rebuild policies. FC itself continues to evolve in speed and in FC-NVMe, while Ethernet-based storage narrows the gap.

## Future direction

Expect the physical gear to be abstracted behind software: arrays and controllers managed through APIs and storage classes, NVMe over TCP and RDMA replacing SCSI-based SANs in new builds, and cloud block volumes taking over entirely for many workloads. Hardware RAID will keep a place in servers with local drives, but pass-through modes with software RAID or checksumming file systems are gaining ground where integrity and portability matter. Multipath knowledge stays valuable wherever shared storage exists. Whatever the technology, the administrator's checklist stays stable: know which layer owns redundancy, name devices by WWID or alias, back up configuration of controllers and fabrics, never run destructive controller actions without confirmation from the owner of the hardware, and rehearse a path failure while someone is watching. [src: rhel-10-docs 02a6eb025648f76e]
