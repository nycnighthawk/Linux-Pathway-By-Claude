# Making storage elastic: the logical volume manager, growth, snapshots and thin provisioning

## Define the problem

A partition is a fixed slice of one disk. It cannot grow past its neighbour, cannot span two disks, and cannot be rearranged while it holds a mounted file system. That rigidity is tolerable on a laptop and ruinous on a server whose data keeps growing, whose disks wear out and are replaced, and whose backup window shrinks every year. The administrator needs a layer between disks and file systems that lets capacity be pooled, handed out in convenient pieces, enlarged while in use, moved from a failing disk to a healthy one, and frozen at a point in time for backup or rollback.

Four distinct needs hide inside that wish. **Pooling**: treat several disks as one reservoir. **Resizing**: grow (and sometimes shrink) a volume without moving everything. **Relocation**: migrate data between devices without unmounting. **Point-in-time copies**: capture a consistent image quickly, even of a busy file system. Later needs came from virtualisation and containers: promising each tenant more space than physically exists (**thin provisioning**), and speeding slow disks with fast ones (**caching**). The price of flexibility is a new layer to understand, whose metadata, failure modes and naming are not those of the layers above or below it. [src: rhel-10-docs 64a1ae36b20210c4]

## History and approaches

The idea of a volume manager sits behind several Unix systems: HP-UX and AIX had logical volume managers in the late 1980s, and Linux's LVM1 followed that design. LVM2, the version in use today, was rewritten around the kernel's **device mapper**, a generic framework that builds virtual block devices out of tables of mappings (linear, striped, mirror, snapshot, thin, cache, crypt, verity and others). That separation matters: the kernel side (`dm-*` targets) knows how to map sectors, while the user-space side (`lvm`, `dmeventd`, and the tools) keeps the metadata and decides what table to load. The same device mapper underlies software encryption (`dm-crypt`, used by LUKS) and multipath, so the layers can be stacked. [src: archwiki e3431bb5bb0f85c5]

The first LVM2 snapshots were **copy-on-write snapshots of thick volumes**. Creating one reserves a separate area, and before the origin is overwritten, the old block is copied into that area. Snapshots are cheap to create but have well-known limits: each write to the origin triggers an extra copy (one read and two writes), several snapshots multiply that cost, the reserved area has a fixed size, and when it fills the snapshot becomes invalid and is lost. These failures drove interest in a better design.

**Thin provisioning** was the answer, and it arrived in LVM2 around 2012 from the `dm-thin-pool` target. A thin pool is a pair of hidden volumes, one for data and one for metadata; thin volumes inside it have a virtual size that may exceed the pool's real size, and blocks are assigned only when they are first written. Snapshots of thin volumes are themselves thin volumes sharing blocks with the origin, so taking one costs almost nothing and snapshots of snapshots are fine. The partial success: elegant and fast, but the pool is a single point of failure and a shared fate. If data or metadata space runs out the pool can be damaged, and repair is difficult. Docker's early default storage backend used device-mapper thin pools for container layers, and was later deprecated in favour of overlay file systems, partly because of the operational burden of exactly these pools. [src: docker-docs 07e3484dde3469d8] [src: man-pages 343411bfeab65875]

Other LVM2 features arrived as the kernel grew targets: mirrored and RAID logical volumes (`--type raid1`, `raid5`, `raid10`, using the MD code underneath), caching with a fast device (`dm-cache` and `dm-writecache`), and data deduplication and compression through VDO as a thin-pool data layer. A late change in how LVM discovers devices is also part of the history: classic LVM scanned every block device and filtered by regular expressions in `lvm.conf`, which was slow on systems with many disks and surprising when a clone or a multipath path exposed the same physical volume twice. Current releases use a **devices file**, `/etc/lvm/devices/system.devices`, that lists the devices this host is allowed to use, managed by `lvmdevices`. [src: rhel-10-docs fc3127cd5d9bed6b]

## Current state

### The building blocks

LVM stacks four concepts.

| Layer | What it is | Commands |
|---|---|---|
| **Physical volume (PV)** | A block device (disk, partition, MD array, loop device) initialised with an LVM label | `pvcreate`, `pvs`, `pvdisplay`, `pvresize`, `pvmove`, `pvremove` |
| **Volume group (VG)** | A pool formed from one or more PVs; divided into fixed-size **physical extents** (PEs), 4 MiB by default | `vgcreate`, `vgs`, `vgextend`, `vgreduce`, `vgsplit`, `vgmerge`, `vgremove`, `vgchange`, `vgexport`, `vgimport` |
| **Logical volume (LV)** | A block device carved from the VG's extents; contains a file system, swap, a database or another layer | `lvcreate`, `lvs`, `lvdisplay`, `lvextend`, `lvreduce`, `lvresize`, `lvrename`, `lvremove`, `lvchange`, `lvconvert` |
| **Logical extent (LE)** | The unit of mapping: each LE maps to a PE | (shown by `lvdisplay -m`, `lvs -o+devices`) |

The label sits in one of the first four sectors of a PV, followed by a metadata area holding the VG description in text form. Metadata is written to every PV in a VG, and backups are kept in `/etc/lvm/backup` (latest) and `/etc/lvm/archive` (history); `vgcfgbackup` and `vgcfgrestore` copy it explicitly. That redundancy is why a VG often survives the loss of a metadata area. The device nodes appear as `/dev/<vg>/<lv>` (symbolic link) and `/dev/mapper/<vg>-<lv>`, with hyphens in names doubled in the mapper form (VG `my-vg` and LV `data` become `/dev/mapper/my--vg-data`). `dmsetup ls`, `dmsetup table` and `dmsetup status` show the kernel's view. [src: archwiki eda39bb2b4790b21] [src: rocky-docs e4d0aa26bc212b45]

### Creating

```bash
pvcreate /dev/vdb1 /dev/vdc1                  # label the devices
vgcreate -s 4M vg0 /dev/vdb1 /dev/vdc1        # create the pool (-s sets the extent size)
lvcreate -L 20G -n data vg0                   # size in bytes with unit
lvcreate -l 100%FREE -n scratch vg0           # or in extents / a percentage
mkfs.xfs /dev/vg0/data
```

`lvcreate` options: `-L` or `--size` (bytes), `-l` or `--extents` (extents or `%VG`, `%FREE`, `%PVS`, `%ORIGIN`), `-n` name, `-i` stripes and `-I` stripe size, `--type` (`linear`, `striped`, `mirror`, `raid1`, `raid5`, `raid6`, `raid10`, `thin-pool`, `thin`, `cache`), `-m` mirror count, `-s` snapshot, `-V` virtual size (thin), `--thinpool`, `-a` activation, `--wipesignatures`, `-W`, `-Z` (zero the start). Placing a volume on specific devices is done by listing them at the end of the command. [src: man-pages 6fda01d0cd64e574]

### Growing

Growing is the headline operation. The three steps are: make room, extend the LV, extend the file system.

```bash
vgextend vg0 /dev/vdd1                         # add a disk to the pool (if needed)
lvextend -L +10G /dev/vg0/data                 # extend by an amount
lvextend -l +100%FREE /dev/vg0/data            # or take all remaining space
resize2fs /dev/vg0/data                        # ext4, online
xfs_growfs /srv/data                           # XFS, by mount point
lvextend -r -L +10G /dev/vg0/data              # -r (--resizefs) does both in one step
```

When the underlying disk has grown (a virtual disk was enlarged), the order is: extend the partition (with `sfdisk` or `growpart`), then `pvresize /dev/vdb1`, which makes the new space visible to the VG, then `lvextend`. `lvextend` also accepts `--poolmetadatasize` for thin pools. [src: man-pages 2a53528f0d4cbffd] [src: rhel-10-docs 61fdc628e0dec862]

Shrinking is the reverse and dangerous: file system first, then LV. For ext4: `umount`, `e2fsck -f`, `resize2fs dev newsize`, `lvreduce -L newsize`; or `lvreduce -r` which orchestrates it. XFS cannot be shrunk at all. Reducing an LV below the file system's size destroys data, and `lvreduce` asks for confirmation for that reason.

### Moving data and replacing disks

`pvmove /dev/vdb1` migrates all extents off a PV onto free extents of the same VG, online, restartable if interrupted (`pvmove` without arguments resumes). Typical disk replacement: `vgextend` with the new disk, `pvmove` off the old one, `vgreduce vg0 /dev/vdb1`, `pvremove /dev/vdb1`. The archive's "zero-downtime storage upgrade" example shows this applied to a live thin-provisioned system. `vgsplit` and `vgmerge` divide or combine VGs; `vgexport`/`vgimport` hand a VG over to another host. [src: archwiki 3647ee5654e090e1]

### Classic snapshots

```bash
lvcreate -s -L 5G -n data-snap /dev/vg0/data      # thick COW snapshot, 5 GiB change area
mount -o ro,nouuid /dev/vg0/data-snap /mnt/snap   # nouuid is needed for XFS clones
# back up from /mnt/snap, then:
umount /mnt/snap && lvremove -y /dev/vg0/data-snap
lvconvert --merge /dev/vg0/data-snap              # or roll the origin back to the snapshot
```

The size given with `-L` is the space reserved for changes, not the size of the volume. Watch `lvs -o+snap_percent`: at 100% the snapshot is invalid and unusable. A merge is deferred if the origin is open; it takes effect the next time the origin is activated. For a consistent image of a database, flush and freeze first (`fsfreeze -f /srv/data` then `fsfreeze -u`, or the database's own backup mode), because a snapshot is crash-consistent, not application-consistent. [src: man-pages fc5c9ecbdf76cddb]

### Thin provisioning

```bash
lvcreate --type thin-pool -n pool0 -L 100G vg0                 # data LV; metadata is sized automatically
lvcreate --type thin -n web -V 50G --thinpool pool0 vg0        # virtual size may exceed the pool
lvcreate --type thin -n db  -V 80G --thinpool pool0 vg0        # total virtual 130G on a 100G pool
lvcreate --snapshot -n web-before vg0/web                      # thin snapshot: NO size option
lvs -o+data_percent,metadata_percent,seg_monitor vg0
```

Key points from the reference manual: a size option on a snapshot request creates a thick COW snapshot instead of a thin one; thin snapshots carry the skip-activation flag, so `lvchange -ay -K vg0/web-before` is needed to activate them (change the default with `activation/auto_set_activation_skip` in `lvm.conf`, or per volume with `lvchange --setactivationskip n`); a snapshot can be merged into its origin with `lvconvert --merge`; the origin can be removed without affecting its snapshots; a thick LV can be converted into a thin LV in a new pool with `lvconvert --type thin`, which cannot be reversed. [src: man-pages a3cf469a68dd78e8] [src: man-pages 00faef7317406137]

**Never let a pool fill.** Pool data usage is `Data%`, metadata usage is `Meta%`, and both must be watched. `dmeventd` (started by `lvm2-monitor.service`) can run `lvextend --use-policies` when usage crosses the threshold set in `lvm.conf` under `activation/thin_pool_autoextend_threshold` (50 to 99; 100 disables it) and grows by `activation/thin_pool_autoextend_percent`. That only works if the pool is monitored (`lvs -o+seg_monitor`, `lvchange --monitor y`) and the VG has free extents. To manually grow: `lvextend -L +20G vg0/pool0`, and `lvextend --poolmetadatasize +1G vg0/pool0` for metadata. When the pool is full, writes fail or block (`lvchange --errorwhenfull y` makes them fail instead of queueing). Repair uses `lvconvert --repair vg0/pool0` and `thin_check`, `thin_repair`, `thin_dump` from `device-mapper-persistent-data`; success is not guaranteed. [src: man-pages f9b7aa98b90ad39a]

Discards matter: a thin pool only learns that blocks are free when a file system sends discards. Use `fstrim -v /srv/web` periodically (the `fstrim.timer`) or the `discard` mount option; the pool's `--discards passdown|nopassdown|ignore` controls whether discards also reach the underlying disks. The distribution documentation on TRIM explains the trade-off between continuous and periodic trimming. [src: rocky-docs 63fe05d687c337ed]

### Caching, RAID and VDO

`lvconvert --type cache --cachevol fast vg0/slow` attaches a fast LV as a cache (`dm-cache`; `--cachemode writethrough|writeback`); `lvconvert --splitcache` detaches it. LVM RAID creates md-style arrays inside LVM (`lvcreate --type raid1 -m 1 -L 10G -n mirror vg0`), checked with `lvchange --syncaction check`, repaired with `lvconvert --repair`. VDO pools compress and deduplicate (`lvcreate --type vdo`, or `--pooldatavdo y` on a thin pool), and are mostly worth it on specific workloads such as VM images.

### Discovery and activation

`pvscan`, `vgscan`, `lvscan` and `vgchange -ay` (activate) / `-an` (deactivate) are the manual controls; at boot, `lvm2-pvscan@.service` and udev rules activate VGs as devices appear, and early boot activates the root VG from the initramfs. `lvmdevices --adddev /dev/vdb1` and `--deldev` edit the devices file; `lvm.conf` `devices/filter` and `global_filter` remain for older configurations. `lvmconfig --typeconfig diff` shows the settings you have changed. `lvs -a -o+devices` displays hidden internal LVs such as `[pool0_tdata]` and `[pool0_tmeta]`. [src: rhel-10-docs e0c48347bc2949ec]

## Assessment: the good, the bad and the ugly

**The good.** LVM turns storage into a set of verbs: add, grow, move, snapshot, replace. Everything works online for the common cases: extending a mounted ext4 or XFS volume is routine, `pvmove` replaces a disk without a window, and a snapshot of a busy file system takes seconds. Thin snapshots make nightly rollback points and cloned test environments cheap; mirrored or RAID logical volumes give redundancy with the same tool. It is available on every general distribution, and the metadata is text that humans can read in a backup file. [src: debian-handbook dbc7c3d5ad15c7b2]

**The bad.** Shrinking is slow and risky, and XFS is one-way. Classic snapshots slow writes and can silently die when their reserved area fills. Overcommitted thin pools turn a capacity problem into an outage: one runaway writer fills the pool and every thin volume on it, not only the guilty one, fails. The layers hide each other: `df` shows a file system with room while the pool beneath is nearly full, and `lvs`, `vgs`, `pvs` all report different "free" numbers. Naming is confusing (the doubled hyphens in `/dev/mapper`), and the combination with partition tables, RAID and encryption means that a "disk full" question has to be answered at each layer. The thin-pool root volume can time out at boot when its pool is slow to activate, and the Arch notes record the fix for that case. [src: archwiki 7c3bfef8ab7494ad]

**The ugly.** Metadata damage and cloned disks. A VG whose metadata area is overwritten can be recovered from `/etc/lvm/archive` and `vgcfgrestore`, but only if the backup exists and the PV identifiers match, and the procedure is easy to get wrong under stress. Cloning a disk (a VM template, a block-level copy, a SAN snapshot) produces two PVs with the same UUID. If both are visible to one host LVM refuses or picks one at random, and activating the wrong copy corrupts data; the devices file exists largely to prevent that. Snapshot merges on a root volume require a reboot. Thin-pool metadata that is too small cannot be shrunk later and can be a blocker for growth. Finally, LVM does not replace backups: a snapshot lives in the same VG and dies with the same disks.

## Applications beyond this domain

Virtualisation is the largest consumer. libvirt can use LVM volume groups as storage pools and manages volumes with `virsh vol-create-as` and related commands, while QEMU's image tool converts between raw LVs and image formats; cloud and hosting platforms use thin LVs for per-guest disks and snapshots for templates. [src: libvirt-docs 7e0a632c8a49c25e] [src: qemu-docs 215783099be984dc]

Container platforms learned the same lessons: layered images need copy-on-write at the block or file level, and the device-mapper backend delivered it before overlay file systems took over. Enterprise virtual-desktop and VPS hosting use the pattern of one thin pool, one thin volume per customer and a snapshot as the backup, which the Arch documentation sketches for virtual private servers. [src: archwiki eafa402c3258592d]

Outside Linux the ideas recur: ZFS pools and datasets, Btrfs subvolumes, Windows Storage Spaces, SAN thin provisioning and cloud block storage snapshots are all answers to the same four needs, and their failure modes (full pool, snapshot sprawl, orphaned snapshots that cost money) match. Even samba's shadow-copy VFS module exists to present LVM snapshots to Windows clients as "previous versions", a direct application of the snapshot idea to a different protocol. [src: samba-docs 3a902fbf6796c971]

## Examples

**Build a volume group from two disks and a file system on it.**

```bash
pvcreate /dev/vdb /dev/vdc
vgcreate vg_data /dev/vdb /dev/vdc
lvcreate -n srv -l 80%FREE vg_data
mkfs.xfs -L srv /dev/vg_data/srv
mount /dev/vg_data/srv /srv
```

**Grow an XFS volume that is filling up, in place.**

```bash
vgs vg_data                                  # confirm free extents
lvextend -r -L +5G /dev/vg_data/srv
```

**Replace a failing disk without downtime.**

```bash
vgextend vg_data /dev/vdd
pvmove /dev/vdb
vgreduce vg_data /dev/vdb
pvremove /dev/vdb
```

**Take a snapshot for backup, then discard it.**

```bash
lvcreate -s -L 2G -n srv-snap /dev/vg_data/srv
mount -o ro,nouuid /dev/vg_data/srv-snap /mnt/snap
rsync -a /mnt/snap/ /backup/srv/
umount /mnt/snap && lvremove -y /dev/vg_data/srv-snap
```

**A thin pool for test environments, with rollback.**

```bash
lvcreate --type thin-pool -n tp -L 50G vg_data
lvcreate --type thin -n lab -V 40G --thinpool tp vg_data
lvcreate -n lab-clean --snapshot vg_data/lab      # before risky changes
lvchange -ay -K vg_data/lab-clean
umount /lab && lvchange -an vg_data/lab && lvconvert --merge vg_data/lab-clean   # roll back
lvs -o+data_percent,metadata_percent vg_data
```

**Recover a lost configuration.** `vgcfgrestore -l vg_data` lists archives; `vgcfgrestore -f /etc/lvm/archive/<file> vg_data` restores; then `vgchange -ay vg_data`. This needs the PVs to be present with their original UUIDs.

## Related problems and ideas

LVM is one of three ways to get flexibility, and the others are neighbours in this course. **Software RAID** (`mdadm`) offers redundancy below the volume layer and is often combined: MD arrays as PVs, LVs on top. **File systems with built-in volume management** (Btrfs, ZFS) fold pooling, snapshots and checksums into the file system, which removes the layer boundaries but ties data management to one file system. **Encryption** with LUKS can sit below LVM (encrypt the whole PV, one passphrase) or above (encrypt each LV separately); the choice affects what is visible without the key. **Multipath** presents one device for several paths, and LVM must be told to use the multipath device, not the paths. **Thin provisioning above LVM** is also found in hypervisors and arrays; stacking thin on thin hides the real utilisation and doubles the places that can fill up.

Related risks are space-accounting: quotas and reserved space per volume, alerting at 80% and 90%, and capacity planning that includes snapshot growth. A snapshot policy needs retention rules, or snapshots accumulate until the pool is full. Think also about boot and recovery: the root volume needs the LVM tools in the initramfs, and rescue media must be able to activate the VG.

## Active research

Current work focuses on making thin provisioning and caching safer and more observable. The `dm-thin` metadata format and its user-space tools are being hardened, with faster repair and better detection of space exhaustion; `dm-vdo` was merged into the mainline kernel, bringing deduplication and compression into the upstream device mapper. Zoned block devices need translation layers (`dm-zoned`, and file systems that write sequentially), which changes how logical volumes map extents. NVMe features such as namespaces and zoned namespaces overlap with what LVM does in software. In the user-space side, the devices-file model and `lvmdevices` replace regular-expression filters, and the separation of the LVM event daemon is being reworked. There is also continuing interest in **integrity and tamper evidence** (`dm-integrity`, `dm-verity`) as sub-layers beneath LVM RAID, to detect silent corruption that a mirror alone cannot resolve.

## Future direction

The pressure on LVM comes from two sides. Cloud providers resize volumes at the platform level and snapshot them in their own control plane, so on a cloud VM the guest often just needs `growpart`, `pvresize` and `lvextend -r`. Immutable and image-based operating systems favour fixed layouts and a declarative definition (systemd-repart style) over interactive volume manipulation. At the same time, file systems with native pooling are gaining ground on desktops. LVM persists where flexibility, mature tooling and distribution support matter: enterprise servers, virtualisation hosts and installers. Expect the practice to move toward automation (storage roles in configuration management that declare VGs and LVs), mandatory monitoring of thin pools, and snapshots used for short-lived rollback and backup, not as long-term archives. The durable skill is to think in layers: know which layer you are growing, shrink in the reverse order, watch the shared pool, and test a restore.
