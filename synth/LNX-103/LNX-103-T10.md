# Getting data back after it is gone: backup and restore with rsync, restic and borg

## Define the problem

Every layer covered so far in this course protects against one kind of loss. RAID survives a disk failure. LVM snapshots survive a bad upgrade. LUKS survives a stolen drive. None of them survives the loss that happens most often: a file deleted by mistake, a database corrupted by a faulty release, a ransomware run that encrypts everything it can write to, a fire or flood in the machine room, or a storage array that dies with its snapshots on it. For those, the only protection is a **separate copy, made at an earlier time, kept somewhere the original failure cannot reach**.

A backup is useful only if it can be restored, and that sentence hides most of the difficulty. The copy must be consistent (a database file copied while it is being written is worthless), complete (permissions, ownership, ACLs, extended attributes, links and special files), recent enough to meet the **recovery point objective** (how much work you can afford to lose) and fast enough to restore within the **recovery time objective** (how long you can be down). It must be affordable, which pushes toward incremental transfers and deduplication, and secure, which means encrypted if it leaves your control and protected against deletion by an attacker who has compromised the machine being backed up. And it must be verified, because an untested backup is an assumption. This topic covers the common Linux tools: `rsync` for efficient synchronisation, and `restic` and `borg` for versioned, deduplicated, encrypted repositories, plus the file-system dump tools. [src: nist-sp800-53 11b67359634f87c1]

## History and approaches

The earliest Unix backups used `tar` and `cpio` to write a tree to tape, and `dump` and `restore` to copy a whole file system at the block level by walking its inodes, with numbered **levels**: level 0 is a full backup, and a higher level contains everything changed since the last lower-level backup. The scheme survives in `dump` for ext2 to ext4 and in `xfsdump` for XFS, which also run by level and also record the files in an inventory. Tape drove the design: sequential access, incremental sets, and rotation schemes such as grandfather-father-son (keeping dailies, weeklies and monthlies) that dictate how long each copy is retained.

Disk-to-disk backup changed what was possible. **rsync**, released in 1996 by Andrew Tridgell and Paul Mackerras, made a remote copy cheap by sending only the differences: for each file that exists on both sides, the receiver computes rolling and strong checksums of fixed-size blocks, the sender finds matching blocks at any offset, and only the unmatched data crosses the network. Its option set became the vocabulary of Unix file synchronisation. A clever trick built on it, the **hard-link snapshot** (`--link-dest`), gives each backup run the appearance of a full copy while unchanged files are shared hard links to earlier runs, so that a month of daily snapshots costs little more than one copy plus the changes. Scripts built on that idea, from simple shell loops to `rsnapshot`, were the standard small-site solution for two decades. [src: rocky-docs 0671eff181d701d3] [src: rocky-docs d5322f86a48c8a0f]

The next generation changed the unit from the file to the **chunk**. **borg** (a fork of `attic`, 2015) and **restic** (2014) split every file into variable-sized chunks chosen by content (a rolling hash decides the boundaries, so that inserting a byte does not shift every later chunk), store each distinct chunk once, keyed by its cryptographic hash, and record each backup run as a **snapshot** (restic) or **archive** (borg) that lists which chunks make up which files. That gives deduplication within and across runs and across machines, cheap incremental backups, point-in-time restore of any run, and client-side encryption, because the repository is just a pile of encrypted blobs and indexes. They differ in detail: restic is a single static binary in Go with backends for local disks, SFTP, REST servers, S3-compatible stores and other clouds (directly and through `rclone`), and supports concurrent writers; borg is Python with a C core, uses an SSH-based remote protocol, has strong compression options, and has historically been faster on large datasets over SSH. The comparison and the tools' current versions change quickly. [src: archwiki bd382b590f1c41c4]

The failures that shaped practice are well known. Backups that were never tested and turned out unreadable. Backup servers that were reachable with the same credentials as the machines they protected, so ransomware encrypted both. Snapshots stored in the same pool as the original, dying with it. Databases backed up as raw files while running. Backups with no record of which key unlocks them. Compliance guidance responds with explicit controls: store backup copies separately, test restoration, and protect the confidentiality and integrity of the backup, as the NIST contingency planning family and the server security guide state. [src: nist-sp800-guides ddd4faa7129511e9]

## Current state

### Concepts every design needs

**The 3-2-1 rule** is the usual starting point: at least three copies, on two different kinds of media or systems, with one off-site (or logically isolated). A modern refinement adds one copy that is immutable or offline, so that an attacker with administrative access cannot delete it. **Types of backup**: full (everything), incremental (changes since the previous run), differential (changes since the last full), and snapshot-based (the repository presents each run as a complete tree and stores only new data). **Consistency**: for a file system, back up from a snapshot (`lvcreate -s`, a Btrfs read-only snapshot, or `fsfreeze`); for a database, use its own dump or backup mode (`pg_dump`, `mysqldump --single-transaction`, `pg_basebackup`), or quiesce it before the snapshot; for a virtual machine, use the hypervisor's live backup interface, which libvirt and QEMU document for full and incremental disk backup. **Retention**: keep dailies, weeklies and monthlies according to need, remembering that the oldest copy that matters is the one that predates your last undetected corruption. **Restore testing**: restore to a scratch location on a schedule and compare. [src: libvirt-docs 2af1bef9c156d8a5]

### rsync

```bash
rsync -aAXHv --numeric-ids /srv/data/ backup@vault:/backups/data/       # archive mode plus ACLs, xattrs, hard links
rsync -aAXH --delete --exclude='*.tmp' --exclude-from=/etc/backup.exclude /srv/data/ /mnt/usb/data/
rsync -aAXH -n --itemize-changes --delete /srv/data/ /mnt/usb/data/     # dry run: show what would change
rsync -a --link-dest=/backups/daily.1 /srv/data/ /backups/daily.0/      # hard-link snapshot
```

The option summary: `-a` (archive: `-rlptgoD`, which is recursive, preserve symlinks, permissions, times, group, owner, devices and specials), `-A` (ACLs), `-X` (extended attributes), `-H` (hard links), `--numeric-ids` (do not map names), `-v`, `-P` (`--partial --progress`), `--info=progress2`, `-n` (`--dry-run`), `-i` (`--itemize-changes`), `--delete` (remove files on the destination that no longer exist at the source; the dangerous one), `--delete-after`, `--exclude`, `--include`, `--exclude-from`, `--files-from`, `-c` (compare by checksum instead of size and time), `-z` (compress in transit), `--inplace`, `--bwlimit`, `-e 'ssh -p 2222'` (the transport), `--backup --backup-dir=DIR` (keep replaced files), `--link-dest=DIR`, `--rsync-path='sudo rsync'`, `--checksum-choice` and `--stats`. A trailing slash on the source path means "the contents of this directory"; without it, the directory itself is copied into the destination, and the difference between `src/` and `src` is the most frequent rsync mistake. Exit status 0 is success, 23 is partial transfer due to errors, 24 means source files vanished during the run (normal on a live system). The manual's option and example sections are worth reading in full. [src: man-pages bfc51d41fe1cc7b0] [src: man-pages c2f92e392691bb89] [src: man-pages fc5d377cc3d3c28f]

rsync is a synchroniser, not a backup system: without `--link-dest` or `--backup-dir` it keeps only the latest state, so an accidental deletion or encryption on the source propagates at the next run. Used with rotation and hard links it becomes a dependable simple backup, and Debian's handbook shows the classic approach with pre-run hooks and an SSH key restricted to a single command. [src: debian-handbook ad3d2771162d9676]

### restic

```bash
export RESTIC_REPOSITORY=sftp:backup@vault:/srv/restic/web
export RESTIC_PASSWORD_FILE=/root/.restic-pass            # mode 0600
restic init                                               # create the repository (asks to confirm the password)
restic backup /etc /srv/data --exclude-file=/etc/restic.exclude --tag nightly
restic snapshots                                          # list runs: ID, time, host, tags, paths
restic ls latest /srv/data | head
restic restore latest --target /restore --include /srv/data/report.txt
restic check                                              # verify structure; --read-data checks every blob
restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 12 --prune
restic diff <id1> <id2>;  restic stats;  restic mount /mnt/restic   # browse snapshots as a file system
```

Facts that matter: the repository is encrypted with AES-256 in counter mode with Poly1305-AES authentication, using a master key stored in key files that are themselves encrypted with a key derived from your password by scrypt; `restic key list|add|remove|passwd` manage passwords; there is **no recovery if the password is lost**. `restic backup` reads the paths, chunks files, uploads only chunks the repository does not already hold, and writes a snapshot. `forget` only removes snapshot records; `--prune` (or `restic prune`) deletes the data that no snapshot needs any more, which is slow and needs care with concurrent runs. `restic unlock` removes stale locks left by a crash. `restic copy` copies snapshots between repositories, which is how a second off-site copy is made. Supported backends include local paths, `sftp:`, `rest:` (restic's REST server, which can run append-only), `s3:`, `b2:`, `azure:`, `gs:`, `swift:` and `rclone:`. The `--exclude`, `--iexclude`, `--exclude-caches`, `--one-file-system` and `--files-from` options control what is read; `--read-concurrency` and `--pack-size` tune speed. [src: archwiki 032a400dd726a2e2]

### borg

```bash
export BORG_REPO=ssh://backup@vault/./borg-web
export BORG_PASSPHRASE_FILE=/root/.borg-pass                  # or BORG_PASSCOMMAND
borg init --encryption=repokey-blake2                         # or keyfile: key stays on the client
borg create --stats --compression zstd,6 ::'{hostname}-{now:%Y-%m-%d_%H%M}' /etc /srv/data --exclude '*.tmp'
borg list;  borg list ::host-2025-06-01_0200
borg extract ::host-2025-06-01_0200 srv/data/report.txt        # restore into the current directory
borg prune --keep-daily 7 --keep-weekly 4 --keep-monthly 12 --list
borg compact                                                    # reclaim space after prune (borg 1.2 and later)
borg check;  borg mount ::host-... /mnt/borg;  borg key export
```

Key facts: encryption modes are `none`, `authenticated` (integrity only), `repokey` (key stored in the repository, protected by the passphrase) and `keyfile` (key stored under `~/.config/borg/keys` on the client; **you must back up that key file**), each with a `-blake2` variant; `borg key export` makes a paper or file copy. Compression options include `lz4`, `zstd`, `zlib` and `lzma`, with levels. A repository can be restricted on the server side with an SSH `command="borg serve --append-only --restrict-to-path ..."` entry in `authorized_keys`, which stops a compromised client from deleting history; pruning is then done from a trusted machine. Borg 2 changes the repository format and command shapes, so follow the version you have installed. The Arch documentation covers installation, usage and restoration with both ordinary and mounted views. [src: archwiki a73d88b1a97ce7f5] [src: archwiki cff593a6e639be42]

### File-system dump tools

```bash
xfsdump -l 0 -L weekly -M media0 -f /backups/srv.xfsdump /srv     # level-0 dump of a mounted XFS
xfsdump -l 1 -f /backups/srv.l1.xfsdump /srv                      # changes since level 0
xfsrestore -f /backups/srv.xfsdump /restore                       # restore into a directory
xfsrestore -I                                                     # show the inventory of dumps
dump -0uaf /backups/boot.dump /boot                               # ext2/3/4: level 0, update /etc/dumpdates
restore -rf /backups/boot.dump                                    # rebuild into the current directory
```

These tools back up file systems (not partitions), keep attributes natively, and are what Red Hat's documentation describes for backing up and restoring XFS; an XFS dump must be taken from a mounted, quiescent file system (best from a snapshot). The documentation for ext4 gives the equivalent recipes for `dump` and `restore`. For whole-device or bare-metal recovery, `dd` or `ddrescue` copy blocks (useful for failing disks, wasteful otherwise), and the Relax-and-Recover (`rear`) family builds a bootable rescue image and a restore procedure. [src: rhel-10-docs 20f0594bde3532d9] [src: rhel-10-docs d49d385d79416ac3] [src: rhel-10-docs ce6cbc73a7b13460]

### Scheduling, monitoring and verification

A backup that is not scheduled and not monitored is a backup that stopped silently. Run it from a systemd timer (see the scheduling topic in the system administration course) with `OnCalendar=`, `Persistent=true` and `RandomizedDelaySec=`; a `.service` of `Type=oneshot` with `OnFailure=` pointing at a notification unit; and exit-code handling (`rsync` exit 24 is not a failure for a live system). Log to the journal. Send a heartbeat to a monitoring service on success, so that absence of the heartbeat alarms. Verify regularly: `restic check` or `borg check`; restore a sample into a scratch directory and compare with `diff -r` or `rsync -n --itemize-changes`; and rehearse a whole-system restore on a clean machine at least once a year.

### Security of the backups themselves

The backup server holds everything, so treat it as the most sensitive host. Prefer **pull** (the backup server connects to clients and has read-only access) or **append-only push** (clients can add but not delete); use separate credentials per client; encrypt before data leaves the machine (restic and borg do); keep the repository password and key in a place that does not depend on the system being restored; make one copy immutable (S3 object lock, a WORM appliance, an offline disk, `chattr +a` on a log-structured repository); and monitor for unexpected deletions or size changes. [src: nist-sp800-53 11b67359634f87c1]

## Assessment: the good, the bad and the ugly

**The good.** The open-source tools are mature and complementary. rsync is universal and transparent, and a hard-link snapshot scheme needs no special tools to restore: the backup is an ordinary directory. restic and borg make versioned, deduplicated, encrypted backups easy, with a handful of commands and good backends, and make off-site copies economical because only new chunks travel. dump-style tools preserve native attributes. All run unattended from timers and integrate with ordinary SSH access control.

**The bad.** Every approach has a trade-off. rsync keeps no history unless you build it, copies a file's changes only if the receiver has a version to compare, and has no encryption of its own. Repository tools make the repository a proprietary pile of blobs: a damaged index or a lost password can make everything unreadable, and restoring needs the tool, the key and a working network. Deduplication and encryption lengthen restore times, `prune` is heavy and can be slow on big repositories, and retention rules need thought. Consistency is not automatic: none of these tools quiesces a database for you. Initial backups of large data sets are slow, and restores are usually slower than backups.

**The ugly.** Backups fail quietly. A cron job that has been failing for months, an `--exclude` pattern that matches more than intended, a backup of an empty mount point because the volume did not mount, a `--delete` run with source and destination swapped, or a repository that is full and refuses writes are the typical stories, and the symptom is discovered at restore time. Ransomware that reaches the backup server through mounted shares or shared credentials destroys the safety net. Passwords lost with the system they protected make encrypted repositories into expensive noise. Restores that overwrite live data because the target path was wrong are the final insult; always restore to a scratch location first. [src: nist-sp800-guides ddd4faa7129511e9]

## Applications beyond this domain

The same machinery serves many other fields. Virtual machine and container platforms need image and volume backup: libvirt's live backup interface drives QEMU to produce full and incremental disk copies without stopping the guest, and Kubernetes backup tools such as Velero build on restic or similar libraries to back up persistent volumes. Database administration relies on logical dumps and continuous archiving with the same ideas of full, incremental and point-in-time recovery. Enterprise directory services have their own backup and restore doctrine, with system-state backups, authoritative and non-authoritative restore, and special rules for virtualised domain controllers, which illustrate that "restore" is a procedure and not only a command. Content-defined chunking and deduplication are also the heart of container image registries, software update systems (`ostree`, `casync`, `zsync`) and cloud storage, so a restic repository resembles a Git object store with encryption. [src: ms-learn-adds b9067808859c3876] [src: ms-learn-adds 6ab7f2d7d3829805]

Embedded and field devices use image-based backup and rsync-style delta updates, and developers use the same tools to move home directories between machines. [src: rocky-docs 5ee23342310eaa9d]

## Examples

**A nightly rsync snapshot rotation with hard links.**

```bash
#!/bin/sh
set -eu
SRC=/srv/data/; DEST=/backups/data
TODAY=$(date +%F)
rsync -aAXH --delete --numeric-ids --link-dest="$DEST/latest" "$SRC" "$DEST/$TODAY/"
ln -sfn "$TODAY" "$DEST/latest"
find "$DEST" -maxdepth 1 -type d -name '20*' -mtime +30 -exec rm -rf {} +
```

**The same data in restic, to a remote repository.**

```bash
restic -r sftp:backup@vault:/srv/restic/data init
restic -r sftp:backup@vault:/srv/restic/data backup /srv/data --tag nightly
restic -r sftp:backup@vault:/srv/restic/data forget --keep-daily 7 --keep-weekly 4 --prune
```

**A timer-driven backup unit.**

```ini
# /etc/systemd/system/restic-backup.service
[Service]
Type=oneshot
EnvironmentFile=/etc/restic.env
ExecStart=/usr/bin/restic backup /etc /srv/data
ExecStartPost=/usr/bin/restic forget --keep-daily 7 --keep-weekly 4 --prune
# /etc/systemd/system/restic-backup.timer
[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true
RandomizedDelaySec=10m
[Install]
WantedBy=timers.target
```

**Restore a single file safely.**

```bash
restic snapshots --path /srv/data
restic restore <snapshot-id> --target /tmp/restore --include /srv/data/report.txt
diff /tmp/restore/srv/data/report.txt /srv/data/report.txt
```

**Test a backup end to end.** Restore the latest snapshot into an empty scratch directory, then `diff -r /srv/data /scratch/srv/data` (differences should be only recent changes) and run `restic check --read-data-subset=5%`.

## Related problems and ideas

Backup shades into neighbouring ideas. **Replication** (DRBD, database replicas, `zfs send`, `btrfs send`) gives faster recovery and no history; it protects against hardware loss but copies a deletion as faithfully as a write. **Snapshots** give quick local history on LVM, Btrfs or ZFS but are not independent of the storage they sit on. **Archiving** differs from backup in intent: long retention, immutability and discoverability, usually with legal constraints. **Disaster recovery** adds the question of what to restore onto (bare metal, a cloud region) and how long people need to rebuild networking and identity first. **Data integrity** work (checksumming file systems, scrubs) tells you when a copy has gone bad, so that you restore from a good one. **Encryption** and **key management** apply to the backup as much as to the live data; the previous topic on LUKS covers the key lifecycle that also governs a backup repository. Finally, **restore drills** and runbooks are the human half: the best tool fails if nobody has ever practised using it.

## Active research

Work in this area includes better chunking and deduplication (faster content-defined chunking algorithms, lower memory use for large repositories), repository formats with stronger integrity and the ability to repair after partial loss (borg 2's redesign, restic's ongoing format work), support for immutable object storage with time-locks, compression tuned for backup workloads, and faster verification that does not read every byte. Kernel and file-system developers are adding facilities that make backups cheaper: change tracking in virtual-disk interfaces (dirty bitmaps in QEMU), reflink clones, and file-system send and receive streams. On the security side there is research into detecting ransomware activity from backup statistics (a sudden jump in changed data) and into verifiable, tamper-evident logs of backup operations.

## Future direction

The direction is toward backup as a continuous, policy-driven, immutable service rather than a nightly script. Snapshot-plus-chunked-repository workflows are replacing hand-built rsync rotations for most servers, while rsync stays indispensable for migrations and simple mirrors. Immutability and air-gap properties will be built in (object lock, append-only protocols), and restore verification will be automated: a scheduled job that restores a sample, checks it and reports. Cloud and container platforms will expose backup as API objects with retention policies, with the tools in this lesson as the engine underneath. The practical advice stays constant: decide RPO and RTO first; follow 3-2-1 with one immutable copy; back up from a consistent snapshot; encrypt and keep the key elsewhere; monitor for silence, not only for errors; and restore to a scratch location regularly so that the first restore is never the one that matters.
