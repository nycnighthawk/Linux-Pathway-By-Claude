# Turning blocks into files, and files into a place in the tree: ext4, XFS, Btrfs, fstab and mount units

## Define the problem

A partition or volume is still only an array of blocks. A user wants names, directories, permissions, timestamps, links, sparse files and the assurance that a power cut at a bad moment does not turn the whole tree into rubble. A file system is the on-disk structure and kernel code that provides that, and it has to do so with good performance for very different workloads: millions of small files, a few huge ones, constantly rewritten databases, write-once archives.

Two further jobs follow. The first is **creation and maintenance**: choosing a type, writing its structures (`mkfs`), checking and repairing it (`fsck`), changing its parameters (label, UUID, reserved space), growing it, and in a few cases shrinking it. The second is **attachment**: a file system does nothing until it is mounted, and a server must mount the right ones, with the right options, in the right order, on every boot, without a person at the console. Attachment brings its own questions. How do you identify a device in a way that survives renumbering? What happens to the boot when a disk is missing? How are network and local mounts ordered? How do options such as `noatime`, `nosuid`, `noexec` or `discard` change behaviour and security? The answer on modern Linux is a mix of the traditional table, `/etc/fstab`, and the unit files that systemd generates from it. [src: man-pages 2b17150307796823]

## History and approaches

Early Unix file systems stored a superblock, an inode table and data blocks in fixed positions. They were simple and slow: seeks between inodes and data, and a crash left the structures inconsistent until a full `fsck` walked everything. The Berkeley fast file system introduced cylinder groups to keep related data close together, and Linux's `ext2` followed that idea. The cost of ext2 was the full-check-after-crash model; on a disk of any size, `fsck` took minutes or hours.

**Journaling** was the first fix. `ext3` added a log to ext2 so that a crash needed only a replay of recent metadata changes. `ext4` kept the layout lineage but added extents (a range instead of a block list), delayed allocation, multi-block allocation, larger limits (1 EiB volumes, 16 TiB files with 4 KiB blocks), flexible block groups, and checksums for metadata (`metadata_csum`). It remains the default of Debian-family and many embedded systems because it is conservative, widely supported and has mature repair tools. The common journal modes are `data=ordered` (the default: metadata journalled, data written before the metadata that refers to it), `data=writeback` and `data=journal`. [src: man-pages 4bb928e6da65153a]

**XFS** came from Silicon Graphics for large files and parallel I/O. It divides a volume into **allocation groups** that can be worked on in parallel, uses B+trees for free space and inodes, allocates by extents, and keeps a metadata log, optionally on a separate device. For years it could be grown online but never shrunk, and that remains true. XFS became the default of Red Hat Enterprise Linux from version 7 onwards, so it dominates in RHEL-family fleets. Features that were opt-in became defaults as the tooling matured: version 5 on-disk format with checksums (`crc=1`), free-inode btree (`finobt=1`), and shared-extent copies (`reflink=1`). [src: rhel-10-docs 3ca353b65ad1d636]

**Btrfs** took a different path: copy-on-write trees, in which blocks are never overwritten in place and every change creates a new version of the tree, with checksums on data and metadata. That brought cheap snapshots, subvolumes, built-in multi-device profiles (RAID 0, 1, 10, with parity profiles still flagged as problematic), online scrubbing, transparent compression and send/receive replication. The partial success is well known: the feature set outran the stability of some parts (the RAID 5/6 profiles and some repair paths), Red Hat dropped it from RHEL 8 onwards, and SUSE and Fedora keep it as a default for root volumes. ZFS, which offers a similar model, stays outside the kernel for licence reasons. [src: man-pages 819bed9fe67f8ee6]

On the mounting side the history runs from a hand-edited `/etc/fstab` read by `mount -a` at boot, to device identification by stable labels and UUIDs (the `LABEL=` and `UUID=` forms, then `PARTUUID=` and `PARTLABEL=`), to the systemd approach of turning each fstab line into a `.mount` unit with dependencies, timeouts and on-demand `.automount` variants. The failure that shaped all of this is the missing disk at boot: an fstab line for an absent device used to hang the boot or drop into emergency mode, and `nofail` and `x-systemd.device-timeout=` exist to bound that. [src: man-pages 2b17150307796823]

## Current state

### The common ground

Every Linux file system is reached through the virtual file system layer, so the user-visible interface is the same. The distinguishing questions are: what are the limits, how does it grow and shrink, how does it recover, what does it cost to snapshot, and what repair tools exist.

| Property | ext4 | XFS | Btrfs |
|---|---|---|---|
| Grow online | yes (`resize2fs`) | yes (`xfs_growfs`, by mount point) | yes (`btrfs filesystem resize`) |
| Shrink | offline only (`resize2fs`, after `e2fsck -f`) | not supported | online |
| Snapshots | no (use LVM) | no (use LVM, or reflink copies) | yes, per subvolume |
| Checksums | metadata | metadata (v5) | data and metadata |
| Repair | `e2fsck` | `xfs_repair` (unmounted) | `btrfs check`, `scrub` |
| Label | `tune2fs -L`, `e2label` | `xfs_admin -L` | `btrfs filesystem label` |
| Typical home | general purpose, small VMs, boot partitions | large servers, databases, RHEL root | desktops, snapshots, container hosts |

### Creating and inspecting

```bash
mkfs.ext4 -L data -m 1 /dev/vg0/data        # label, 1% reserved for root
mkfs.xfs  -L data /dev/vg0/data             # -f overwrites an existing signature
mkfs.btrfs -L pool -d single -m dup /dev/vdb
```

ext4 options worth knowing: `-m` (reserved block percentage, default 5), `-O` (feature list), `-T` (usage type, which selects inode ratios from `/etc/mke2fs.conf`), `-N` (inode count) and `-E` (extended options such as `lazy_itable_init` and `stride`). The default feature set in current e2fsprogs is `has_journal, extent, huge_file, flex_bg, metadata_csum, 64bit, dir_nlink, extra_isize`, on top of the base `sparse_super, large_file, filetype, resize_inode, dir_index, ext_attr`. `dumpe2fs -h dev` shows the superblock, `tune2fs -l dev` shows tunables, `tune2fs -O ^has_journal`, `-c`, `-i` and `-m` adjust them, and `e2fsck -f` forces a check. [src: man-pages 7fc58d12b17ad303]

XFS options: `-L` label, `-b size=` block size, `-d agcount=` allocation groups, `-l size=` or `-l logdev=` for the log, `-m crc=1,reflink=1,finobt=1` metadata features, `-n ftype=1` directory entries with file type, and `-i maxpct=` (inode space limit). `xfs_info /mountpoint` prints geometry as `meta-data=`, `data =`, `naming =`, `log =` and `realtime =` lines with `isize`, `agcount`, `agsize`, `sectsz`, `bsize`, `blocks` and `crc`. `xfs_growfs` takes the mount point; `xfs_repair` needs an unmounted file system (`-n` for a check only); `xfs_admin -U generate` rewrites the UUID; `xfs_db` is the debugger; `xfsdump` and `xfsrestore` are native backup tools. [src: man-pages 6062bfc8a64031a6]

Btrfs commands are verb-oriented: `btrfs filesystem show`, `btrfs filesystem df /mnt`, `btrfs filesystem usage /mnt`, `btrfs subvolume create|list|delete|snapshot`, `btrfs balance start`, `btrfs scrub start|status`, `btrfs device add|remove`, `btrfs send | btrfs receive`, `btrfs property set`. Data and metadata profiles are chosen separately (`-d`, `-m`) and converted online with `balance -dconvert=raid1 -mconvert=raid1`. [src: man-pages 34ba43055c8e32ad]

### Growing

Growing is a layered operation, bottom up: enlarge the device (or logical volume), then the partition if there is one, then the file system. For LVM, `lvextend -r` or `--resizefs` runs the right file-system tool. By hand: `resize2fs /dev/vg0/data` (ext4; online grow is allowed, shrink is not), `xfs_growfs /srv/data` (XFS), `btrfs filesystem resize max /mnt` (Btrfs). Shrinking ext4 is offline: unmount, `e2fsck -f`, `resize2fs dev newsize`, then reduce the layer below. XFS needs a backup, a smaller new file system and a restore. [src: man-pages 6d75a8462fa49677]

### fstab

`/etc/fstab` has six whitespace-separated fields per line:

```
# device                     mount point  type  options              dump  pass
UUID=0c1d4a02-...            /            xfs   defaults             0     0
UUID=7fe8-3a1b               /boot/efi    vfat  umask=0077,shortname=winnt  0  2
/dev/mapper/vg0-data         /srv/data    ext4  noatime,nodev,nofail 0     2
nfs1:/export/home            /home        nfs   _netdev,nofail       0     0
```

1. **Device**: `UUID=`, `LABEL=`, `PARTUUID=`, `PARTLABEL=`, a `/dev/mapper/` path, a network spec such as `host:/path` or `//host/share`, or a pseudo file system name (`tmpfs`, `proc`).
2. **Mount point**: an existing directory, or `none` for swap. Spaces are written as `\040`.
3. **Type**: the file system type, or `auto`.
4. **Options**: comma separated. `defaults` means `rw,suid,dev,exec,auto,nouser,async`.
5. **dump**: 1 if the old `dump(8)` should back it up, otherwise 0.
6. **pass**: order of the boot-time check, 1 for root, 2 for others, 0 for none. XFS and Btrfs should use 0 because they have no boot-time `fsck`.

Common options: `ro`/`rw`, `noatime` and `relatime` (default; update atime only if older than mtime/ctime or a day), `nodiratime`, `nosuid`, `nodev`, `noexec`, `nofail`, `x-systemd.automount`, `x-systemd.device-timeout=`, `x-systemd.requires=`, `_netdev`, `discard` (continuous trim, usually replaced by a periodic `fstrim.timer`), `errors=remount-ro` (ext4), `data=ordered` (ext4), `inode64` (XFS, default on 64-bit), `pquota`/`uquota`/`gquota` (XFS quotas), `usrquota`/`grpquota` (ext4 quotas), `compress=zstd`, `subvol=` and `ssd` (Btrfs), `bind` and `remount`. Security baselines require `nosuid`, `nodev` or `noexec` on separate mount points such as `/home`, `/tmp`, `/var/tmp` and removable media. [src: man-pages 2b17150307796823] [src: disa-stig 1822a658f6ce3e92]

### Mount units

At boot `systemd-fstab-generator` reads fstab and writes a `.mount` unit per line in `/run/systemd/generator`. The unit name is the mount path with slashes turned into dashes and other characters escaped: `systemd-escape -p --suffix=mount /srv/data/my-dir` prints `srv-data-my\x2ddir.mount`. You can also write units by hand in `/etc/systemd/system`; the file must be named after the path, and contains:

```ini
[Unit]
Description=Data volume

[Mount]
What=/dev/disk/by-uuid/0c1d4a02-...
Where=/srv/data
Type=xfs
Options=noatime,nodev

[Install]
WantedBy=local-fs.target
```

Dependencies are automatic. A mount unit depends on the mounts of its parent directories and on the device; local mounts are ordered before `local-fs.target`, network mounts before `remote-fs.target` (when `_netdev` or a network file-system type is given). Failure matters: without `nofail`, a failed local mount makes `local-fs.target` fail and the system enters emergency mode. `x-systemd.automount` creates a matching `.automount` unit that mounts on first access, which speeds boot and tolerates slow or absent network shares; `x-systemd.idle-timeout=` unmounts after inactivity. `systemctl daemon-reload` is needed after editing fstab so that the generated units are rebuilt. `findmnt --verify` checks the file for syntax and unknown devices, `findmnt` shows the mounted tree, `mount -a` mounts everything not yet mounted (so it doubles as a test), `mount --fake` rehearses, and `systemctl status srv-data.mount` shows a unit's state. [src: man-pages 91df62502cfbb28b] [src: man-pages 8df942435f9086b3]

### Other attachment tools

`mount -o remount,ro /srv/data` changes options on a live mount; `mount --bind /a /b` makes a directory appear elsewhere; `mount --make-private`, `--make-shared` and `--make-rprivate` control propagation between mount namespaces, which is the root of many container surprises; `umount -l` detaches lazily, and `fuser -vm /mnt` or `lsof +f -- /mnt` finds what is holding a mount busy. `blkid`, `lsblk -f` and `findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS` read the state. [src: rocky-docs 7458db5dd178ecff]

## Assessment: the good, the bad and the ugly

**The good.** The ecosystem offers a clear division of labour. ext4 is predictable and has the most repair experience; XFS scales to large files and highly parallel workloads and has a strong online-grow story; Btrfs adds snapshots, checksums and flexible profiles in a single tool. The fstab-plus-generator arrangement means a text file that people already know produces units with proper dependencies. UUIDs and labels free administrators from device naming. `findmnt --verify` and `mount -a` provide a pre-reboot test that did not exist when the usual advice was "reboot and hope".

**The bad.** The asymmetries catch people out. XFS cannot shrink, so an oversized logical volume is a one-way decision. ext4 shrinking is offline, which turns a routine change into an outage. Btrfs usage reports are confusing: `df` shows something different from `btrfs filesystem usage` because data and metadata are allocated in chunks, and a full-looking filesystem may need a balance (not more disks). fstab lines default to being fatal: one typo or missing device without `nofail` gives an emergency shell at the next boot, often discovered long after the edit. The `dump` and `pass` columns survive as vestiges: `dump(8)` is rarely used, and `pass` is meaningless for file systems without boot-time check.

**The ugly.** Silent corruption and unclean shutdowns. A disk that lies about flush behaviour, a virtual disk with write caching on and no barriers, or a power loss on consumer flash can corrupt any journaling file system; journaling protects metadata consistency, not data, and not against failing hardware. Mount options also hide traps: `data=writeback` or `nobarrier` improve benchmarks by dropping guarantees, `discard` can add latency, and `noatime` on a mail spool or a program that reads atime breaks that program. Bind mounts and propagation settings across namespaces produce paths that look mounted from one place and not from another. The ordering of network mounts at boot (an NFS home that is needed before login, but the network is not up) is a perennial source of boot delays; the answer is `_netdev`, `nofail`, `x-systemd.automount` or a unit that depends on `network-online.target`. And on RHEL-family systems, SELinux labels are a separate layer: a restored or newly created file system can mount fine and still deny access until `restorecon -R` or a `context=` mount option is applied.

## Applications beyond this domain

File-system design ideas travel widely. Copy-on-write with checksums underlies container image layers (overlay file systems stack read-only layers under a writable one; older Docker setups used the device-mapper thin-pool storage driver for the same reason), virtual machine disk formats (qcow2 uses copy-on-write clusters and backing files), and database engines that never overwrite pages in place. Extent-based allocation and allocation groups appear in object stores and cloud block services. The mount namespace and propagation model is what lets containers, `systemd-nspawn` and `systemd`'s own sandbox options (`ProtectSystem=`, `ReadOnlyPaths=`, `BindPaths=`) give each service a custom view of the tree. Configuration management encodes fstab lines through roles (for instance the RHEL storage system role), and installers drive the same layouts from kickstart files. [src: rhel-10-docs 9ba43fbc832af3e0] [src: bootlin-training 3d8215424544b8e3]

Embedded systems choose differently: flash-specific file systems and read-only compressed images (SquashFS with an overlay for writes) matter more than raw speed, and the training material on filesystem optimisation shows how mount options such as `noatime`, commit intervals and journal settings are used to extend flash life. [src: bootlin-training 3d8215424544b8e3]

## Examples

**Create, mount, persist (the whole sequence).**

```bash
mkfs.xfs -L data /dev/vg0/data
mkdir -p /srv/data
blkid /dev/vg0/data                          # note the UUID
echo 'UUID=<uuid>  /srv/data  xfs  defaults,nodev,nofail  0 0' >> /etc/fstab
systemctl daemon-reload
mount -a && findmnt /srv/data
findmnt --verify
```

**Mount unit for a network share that must not block boot.**

```
//files/team  /mnt/team  cifs  credentials=/etc/smb.cred,_netdev,nofail,x-systemd.automount,x-systemd.idle-timeout=300  0 0
```

**Grow an ext4 and an XFS volume together.**

```bash
lvextend -r -L +10G /dev/vg0/data      # -r runs resize2fs or xfs_growfs
# or by hand
lvextend -L +10G /dev/vg0/data && xfs_growfs /srv/data
```

**Btrfs subvolume and read-only snapshot before an upgrade.**

```bash
btrfs subvolume create /mnt/pool/@home
btrfs subvolume snapshot -r /mnt/pool/@home /mnt/pool/@home-before-upgrade
btrfs scrub start -B /mnt/pool
```

**Find out why the machine went to emergency mode.**

```bash
journalctl -xb -p err | head
systemctl --failed
findmnt --verify --verbose
```

**Read the geometry.** `xfs_info /srv/data`, `dumpe2fs -h /dev/vg0/data | egrep 'Block size|features'`, `btrfs filesystem usage /mnt/pool`.

## Related problems and ideas

Stable naming is the first neighbour: `lsblk -f`, `/dev/disk/by-*`, and the question of whether labels are unique enough (two cloned disks with the same label or UUID can confuse booting). Quotas, ACLs and extended attributes (a later topic) are properties that a file system must support and that are switched on by mount options. Online defragmentation (`e4defrag`, `xfs_fsr`), trimming (`fstrim -av`, `fstrim.timer`), and scrubbing are maintenance ideas that exist because file systems age. The file-system choice also interacts with the layers below: thin-provisioned volumes need `discard` or periodic `fstrim` to give space back; RAID write holes matter more for file systems without their own checksums.

Another close relative is the question of **what belongs on its own file system**. The traditional answer is that `/boot`, `/boot/efi`, `/var`, `/var/log`, `/tmp`, `/home` and application data are separate so that a runaway log cannot fill the root and so that `nosuid,nodev,noexec` can be applied selectively. Security benchmarks encode that advice as numbered controls and, for RHEL 10, expect specific mount options on specific mount points. [src: disa-stig b7bab40f2d34c389]

## Active research

Work continues on several fronts. For ext4, the move toward large folios and better support for zoned devices and atomic writes. For XFS, online repair and online file-system checking (`xfs_scrub`), rebuilding of metadata from reverse-mapping information, and big-file and atomic-write improvements for databases. For Btrfs, stabilising the RAID 5/6 profiles, the block-group tree, better quota accounting (squotas) and RAID stripe-tree support for zoned devices. Across all of them, the research trend is the same: reduce the need for offline `fsck`, because a modern volume is too large for a long outage. Related kernel work includes `fs-verity` and `dm-verity` for tamper-evident read-only content, `fanotify`-based scanning, and the new mount API (`fsopen`, `fsconfig`, `fsmount`, `move_mount`), which replaces the single multiplexed `mount(2)` syscall with a stepwise one.

## Future direction

The probable direction is more automation and less manual fstab editing. Discoverable partitions and `systemd-gpt-auto-generator` already mount well-known partition types without an fstab line; `systemd-repart` and `systemd-makefs` create and format file systems from declarative definitions; image-based and immutable systems mount a read-only root with a writable overlay or a dedicated state volume. File systems themselves keep converging on the same list: strong checksums, cheap snapshots and clones, online repair, and a way to avoid the full-volume offline check. For the administrator the stable skills remain the same: pick the type by workload and tooling rather than fashion; identify devices by UUID or label; use `nofail` and timeouts for anything not required to boot; grow from the bottom up; and prove changes with `findmnt --verify` and `mount -a` before a reboot. [src: man-pages 60e61f298cdcd56a]
