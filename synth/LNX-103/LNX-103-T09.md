# Keeping data unreadable when the disk leaves your hands: LUKS2 and dm-crypt

## Define the problem

Disks are lost, stolen, returned under warranty, resold, seized and discarded. Laptops get left in taxis and servers get decommissioned with their drives still inside. File-system permissions protect data only while the operating system is in control; anyone who can attach the disk to another machine reads the raw blocks and ignores every permission. The remedy is **encryption at rest**: the stored bytes are ciphertext, and only someone holding a key can turn them back into data.

Doing that well is harder than choosing a cipher. The system must encrypt every block transparently under existing file systems, with performance close to unencrypted disks. The key must be derived from something a person can supply or a device can hold, and must resist guessing by an attacker who has the disk and unlimited time. More than one person or mechanism must be able to unlock the volume, and one of them must be removable without re-encrypting the data. Keys must be changeable. The volume must unlock at boot, possibly with no human present, without leaving the key where a thief would also find it. And the administrator must be able to recover if the header is damaged, which makes the volume permanently unreadable. LUKS (Linux Unified Key Setup) is the standard answer on Linux, built on the kernel's `dm-crypt`, and LUKS2 is its current version. [src: rhel-10-docs 6d8e0b81ed8cdef5]

## History and approaches

Early disk encryption on Linux used loop devices with ciphers selected by name and passphrases hashed in ad hoc ways, so each installation had its own incompatible format. The `dm-crypt` target of the device mapper gave a clean kernel mechanism: a virtual block device that encrypts writes and decrypts reads with a given cipher and key. What was still missing was a **standard on-disk format** that stored the parameters and allowed several passphrases. LUKS, specified in 2004 and implemented in `cryptsetup`, did that: a header at the start of the device holds the cipher, mode and hash, a randomly generated **master key** that encrypts the data, and up to eight **key slots**, each of which stores the master key encrypted under a key derived from one passphrase. Changing or removing a passphrase rewrites a key slot, not the data. The master key is spread across many stripes (anti-forensic splitting) so that overwriting a slot really destroys it.

LUKS2, introduced in 2018 and the default since `cryptsetup` 2.1, kept the idea and fixed limitations. Metadata is stored as JSON in two redundant copies, protected by checksums, so a single damaged sector no longer kills the volume. It supports up to 32 key slots, **memory-hard key derivation** (Argon2i and Argon2id) in place of the iteration-count-only PBKDF2 of LUKS1, labels and subsystem names, **tokens** (metadata that describes external keys, which is how TPM, FIDO2 and network-bound unlocking are stored), a configurable sector size (up to 4096 bytes), optional authenticated encryption through `dm-integrity`, and **online re-encryption**. A header is 16 MiB by default (a 16 KiB metadata area followed by the key slot area, with the data starting at a 16 MiB offset). [src: rhel-10-docs f1771958179fed55]

Other approaches coexist. Opal self-encrypting drives do the work in the drive's firmware, with weaknesses in some vendors' implementations that led distributions to prefer software encryption by default. File-level encryption (fscrypt, eCryptfs, gocryptfs) encrypts per file, exposing file sizes and directory structure to varying degrees. Windows BitLocker and macOS FileVault are the equivalents elsewhere. Full-disk encryption with LUKS remains the main choice for Linux servers, partly because it is independent of the file system: anything that can sit on a block device can sit on a LUKS device.

The failures and partial successes teach caution. Cold-boot attacks showed that keys sit in RAM while the volume is open. Evil-maid attacks target the unencrypted boot partition; Secure Boot and TPM-based measurement reduce that risk but do not eliminate it. Early LUKS1 volumes with low PBKDF2 iteration counts were cheaper to attack with GPUs, which motivated Argon2. And the most common real-world failure is not cryptographic: a lost passphrase or a damaged header with no backup, making data irretrievable by design. [src: archwiki cd0406f8e59c1f71]

## Current state

### The layers

The stack from the disk upwards is: **block device** (partition, logical volume, RAID array or file image), **LUKS header and data area**, the **dm-crypt mapping** opened as `/dev/mapper/<name>`, then the **file system, swap or LVM physical volume** on it. The kernel does the cryptography through its crypto API (hardware instructions such as AES-NI are used when present); `cryptsetup` is the user-space tool that reads headers, derives keys and tells the kernel what to map. `cryptsetup benchmark` reports the speed of ciphers and key derivation on the machine.

### Creating and using

```bash
cryptsetup luksFormat --type luks2 /dev/vg0/secure          # asks for a passphrase; DESTROYS existing data
cryptsetup open /dev/vg0/secure secure                      # alias: luksOpen; creates /dev/mapper/secure
mkfs.xfs /dev/mapper/secure
mount /dev/mapper/secure /srv/secure
# later
umount /srv/secure && cryptsetup close secure               # alias: luksClose
```

Useful `luksFormat` options: `--cipher aes-xts-plain64` (the default, with a 512-bit key meaning two 256-bit AES keys for XTS), `--key-size 512`, `--hash sha256`, `--pbkdf argon2id|argon2i|pbkdf2`, `--pbkdf-memory` (KiB), `--pbkdf-parallel`, `--pbkdf-force-iterations`, `--iter-time` (milliseconds spent deriving a key, default 2000), `--sector-size 4096`, `--label`, `--subsystem`, `--uuid`, `--key-file`, `--header` (store the header in a separate file, so that the device holds only ciphertext), `--integrity hmac-sha256` (authenticated encryption, which reduces performance and is still marked experimental in many releases) and `--batch-mode` (no confirmation prompt, for scripts). The RHEL documentation walks through creating and opening encrypted volumes, and its system role automates the same from a playbook, with the passphrase kept in an Ansible vault. [src: rhel-10-docs f1771958179fed55] [src: rhel-10-docs fa65f0689f79e14b]

### Key slots, tokens and the header

```bash
cryptsetup luksDump /dev/vg0/secure           # show version, UUID, segments, keyslots, tokens, digests
cryptsetup luksAddKey /dev/vg0/secure         # add a passphrase (asks for an existing one first)
cryptsetup luksAddKey /dev/vg0/secure /root/key.bin     # a key file as a second key
cryptsetup luksRemoveKey /dev/vg0/secure      # remove the slot that matches the passphrase you type
cryptsetup luksKillSlot /dev/vg0/secure 1     # remove slot 1 (needs another valid key)
cryptsetup luksChangeKey /dev/vg0/secure      # change a passphrase in place
cryptsetup luksHeaderBackup /dev/vg0/secure --header-backup-file /safe/secure.hdr
cryptsetup luksHeaderRestore /dev/vg0/secure --header-backup-file /safe/secure.hdr
cryptsetup luksUUID /dev/vg0/secure           # print the UUID
cryptsetup config /dev/vg0/secure --label DATA  # set metadata in LUKS2
```

`luksDump` shows: `Version: 2`, `Epoch`, `Metadata area`, `Keyslots area`, `UUID`, `Label`, `Flags`, **Data segments** (cipher `aes-xts-plain64`, sector size, offset 16777216 bytes), **Keyslots** (for each slot: key size, priority, cipher, PBKDF and its parameters, salt, anti-forensic stripes, area offset and length, digest ID), **Tokens** and **Digests** (the check that a derived key is the right one). Removing the last key slot makes the data unrecoverable, and `cryptsetup` asks you to confirm. Back up the header to a safe place **off the disk**, because the header is the one thing whose loss ends everything; the backup file itself is as sensitive as the keys it still protects, since it contains the encrypted master key and anyone who knew the old passphrase can use it. [src: man-pages 825e6a21f79457fd]

### Boot-time unlocking

Volumes that should open at boot are listed in `/etc/crypttab`, with four fields: a mapping name, the device (preferably `UUID=` of the LUKS container), the key source (`none` to prompt, or a file path) and options. Then an fstab entry refers to `/dev/mapper/<name>`:

```
# /etc/crypttab
secure   UUID=309f801a-11ee-466c-b6a4-1b21ba6b34d9   none   luks,discard
backup   UUID=...  /root/backup.key   luks,nofail,noauto
# /etc/fstab
/dev/mapper/secure  /srv/secure  xfs  defaults,nofail  0 0
```

Supported options include `luks`, `discard` (allow TRIM through the encryption layer; faster and gentler on flash, but it reveals which blocks are unused), `nofail`, `noauto`, `readonly`, `timeout=`, `header=` (detached header path), `keyfile-size=`, `keyfile-offset=`, `x-initrd.attach` (unlock in the initramfs, needed for root and for volumes needed early), `tries=`, `tpm2-device=`, `tpm2-pcrs=`, `tpm2-pin=`, `fido2-device=`, `token-timeout=`, `no-read-workqueue` and `no-write-workqueue` (performance tuning). `systemd-cryptsetup-generator` converts each line into a `systemd-cryptsetup@<name>.service`, so unlocking participates in dependency ordering, and for an encrypted root the initramfs must be rebuilt after changes (`dracut -f` or `update-initramfs -u`). If a key file is used for a non-root volume it must be on a file system that is already unlocked, mode 0400 and root-owned; a key file stored on the same disk gives little protection beyond the passphrase on the root volume. [src: man-pages 5abea6dbbfb2dd48] [src: man-pages 1cedb87b053fda57]

### Unlocking without a person

Servers cannot wait for a password at every reboot. Three mechanisms are common. **TPM2 binding** with `systemd-cryptenroll`: `systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 /dev/vg0/secure` stores a token in the LUKS2 header and a key in the TPM that is released only when the measured boot state (here PCR 7, the Secure Boot policy) matches; adding `--tpm2-with-pin=yes` requires a PIN as well. `--recovery-key` enrolls a generated recovery key you must store safely, `--fido2-device=auto` binds to a hardware token, and `--wipe-slot=` removes old slots. Crypttab then uses `tpm2-device=auto`. **Network-bound disk encryption (NBDE)** on RHEL uses Clevis on the client and a Tang server on the network: `clevis luks bind -d /dev/vg0/secure tang '{"url":"http://tang.example.com"}'` stores a token that lets the machine recover its key only while it can reach the Tang server, so a stolen machine that is powered on elsewhere stays locked. `clevis luks list -d` shows the bindings and `clevis luks unbind` removes one. **Key files in a sealed location** (a USB stick, a key on another volume) are the simplest and weakest. Whichever method is used, keep a passphrase or recovery key slot in addition, because TPM state, a changed firmware setting or an unreachable Tang server can make automatic unlocking fail. [src: man-pages f079537077801265] [src: archwiki 026a5fd2b12eb38b] [src: rhel-10-docs 48a1578e5f9c2ffc]

### Maintenance

`cryptsetup status secure` shows the active mapping (cipher, key size, device, offset, size); `dmsetup table --showkeys secure` would reveal the key and should not be run casually. `cryptsetup luksSuspend secure` freezes I/O and wipes the key from memory until `luksResume`, which laptops use for sleep. **Resizing** after the underlying device grows: `cryptsetup resize secure`, then grow the file system. **Re-encryption**: `cryptsetup reencrypt /dev/vg0/secure` changes the master key or cipher online, and `cryptsetup reencrypt --encrypt --reduce-device-size 32M /dev/vg0/plain` encrypts an existing device in place (it shifts the data to make room for the header and must never be interrupted without the recovery metadata). Periodic checks: `cryptsetup luksDump` for slot hygiene, and a header backup after every key change.

### Layering with LVM and RAID

Two orders are used. **LUKS on LVM** (one encrypted logical volume per use) gives separate keys and lets volumes be unlocked independently; unencrypted LVM metadata reveals the layout. **LVM on LUKS** (one big encrypted container holding a volume group) needs a single unlock and hides the structure, which is why installers choose it for laptops. On top of RAID, encrypt the array device so that each block is encrypted once; encrypting each member separately multiplies the CPU cost. Swap should be encrypted too, or left to zram (see the swap topic). [src: archwiki cd0406f8e59c1f71]

## Assessment: the good, the bad and the ugly

**The good.** LUKS2 gives strong, standard, file-system-independent protection that is transparent to applications and cheap on hardware with AES instructions. Several keys and tokens allow the same volume to be opened by a passphrase, a recovery key, a TPM and a network server, and any of them can be revoked without touching the data. Memory-hard key derivation makes passphrase guessing expensive, redundant JSON metadata makes the header resilient, and `cryptsetup` is well documented, widely deployed and scriptable. Online re-encryption allows retrofitting and key rotation.

**The bad.** The volume is only protected while locked. A running machine keeps the master key in kernel memory, so a stolen live server, a memory dump or a cold-boot attack bypasses it. There is no integrity by default: without `--integrity`, an attacker with write access to the ciphertext can corrupt or roll back blocks in ways the system will not detect. Encryption hides content but not that there is a LUKS volume, nor its approximate size, and with `discard` it leaks which blocks are free. Losing every key or the header makes data permanently unrecoverable, and the first thing a failing disk usually damages is the area near the start. Performance suffers on machines without AES acceleration, and stacking encryption under compressed or deduplicated storage defeats those savings.

**The ugly.** Unattended unlock is the hard problem, and every solution trades security for convenience. A key file on the root disk next to the volume it unlocks is little better than no protection; a TPM release tied to a PCR set that changes with every firmware update locks the owner out; a Tang server that is also compromised unlocks every client. Interrupted re-encryption, a `luksFormat` run on the wrong device (it succeeds instantly and destroys the file system), and header backups left lying in a world-readable directory are the incidents that actually happen. Forgotten crypttab entries also cause boots that wait for a passphrase on a machine with no console, and the fix is `nofail` or an explicit timeout. [src: rhel-10-docs 48a1578e5f9c2ffc]

## Applications beyond this domain

The same pattern, a master key protected by several independently revocable key-encryption keys, appears throughout security engineering: cloud key management services wrap data keys with master keys, password managers wrap a vault key with a passphrase-derived key, and TLS and SSH use long-lived keys only to bootstrap session keys. Memory-hard password hashing (Argon2) is the same defence used for login databases. Virtualisation and cloud platforms offer encrypted volumes: libvirt describes encryption of storage volumes in its volume XML so that a guest disk image is itself LUKS-formatted, and cloud block services encrypt at the provider while customers may add LUKS inside the guest for their own keys. [src: libvirt-docs 0c547cca19f2246f]

Compliance frameworks such as PCI-DSS, HIPAA and government baselines require encryption of data at rest for laptops and for portable media, and many make exceptions or demands for key management that map directly to the choices here (who holds the recovery key, where the header backup lives, how often keys are rotated). Confidential computing extends the idea to RAM, so that a running machine's memory is also encrypted. [src: rhel-10-docs fa65f0689f79e14b]

## Examples

**Encrypt a data disk, mount it now and at boot.**

```bash
cryptsetup luksFormat --type luks2 --label DATA /dev/vdb1
cryptsetup open /dev/vdb1 data
mkfs.ext4 /dev/mapper/data && mkdir -p /srv/data
UUID=$(cryptsetup luksUUID /dev/vdb1)
printf 'data UUID=%s none luks,nofail\n' "$UUID" >> /etc/crypttab
printf '/dev/mapper/data /srv/data ext4 defaults,nofail 0 2\n' >> /etc/fstab
systemctl daemon-reload && mount -a
```

**Add a second passphrase and verify the slots.**

```bash
cryptsetup luksAddKey /dev/vdb1
cryptsetup luksDump /dev/vdb1 | sed -n '/Keyslots:/,/Tokens:/p'
```

**Back up and test the header restore (on a copy).**

```bash
cryptsetup luksHeaderBackup /dev/vdb1 --header-backup-file /safe/vdb1.hdr
chmod 600 /safe/vdb1.hdr
cryptsetup luksHeaderRestore /dev/vdb1 --header-backup-file /safe/vdb1.hdr   # only if the header is damaged
```

**Bind to the TPM with a recovery key.**

```bash
systemd-cryptenroll /dev/vdb1 --recovery-key
systemd-cryptenroll /dev/vdb1 --tpm2-device=auto --tpm2-pcrs=7
# crypttab: data UUID=... none luks,tpm2-device=auto
```

**Try LUKS2 safely on a file.**

```bash
truncate -s 64M vault.img
cryptsetup luksFormat --type luks2 --batch-mode vault.img
cryptsetup luksDump vault.img | head
cryptsetup open vault.img vault && mkfs.ext4 /dev/mapper/vault
```

## Related problems and ideas

Encryption raises neighbouring questions. **Key management at scale**: who holds recovery keys, how are they escrowed, how is a departing administrator's slot revoked. **Secure erase**: with LUKS, destroying the header or all key slots is a fast cryptographic erase (`luksErase`), far quicker than overwriting terabytes, though not a substitute for physical destruction where policy demands it. **Integrity** (`dm-integrity`, `dm-verity`, `fs-verity`) addresses tampering rather than disclosure. **Boot-chain protection**: Secure Boot, measured boot, unified kernel images and signed initramfs close the gap in which the unencrypted boot code can be altered. **Performance**: AES-NI, the `no-read-workqueue` and `no-write-workqueue` options, and the interaction with RAID and thin provisioning. **Swap and hibernation**: hibernation writes memory, including keys, to swap, so encrypted swap with a persistent key is needed for it. **Backups**: backups of encrypted volumes are either of the plain contents (then encrypt the backup) or raw ciphertext (then the key is part of the restore plan); the backup topic returns to this. [src: man-pages 1cedb87b053fda57]

## Active research

Work on LUKS and dm-crypt includes performance (reducing workqueue overhead, using inline encryption hardware), authenticated encryption with `dm-integrity` that is robust and fast enough to enable by default, the choice of parameters for Argon2 under memory limits of early-boot environments, post-quantum considerations (symmetric AES-256 is considered resistant, but key-wrap and network-unlock protocols need review), better hardware-token support (FIDO2 with PIN and user verification, TPM2 policies signed against future firmware, `systemd-measure`) and measured boot with signed PCR policies, which let a key be released to any trusted kernel without re-enrolment after every update. Confidential-computing hardware (AMD SEV, Intel TDX) raises the question of what a guest treats as a trustworthy root of trust for unlocking.

## Future direction

The direction of travel is toward **unlock by hardware and policy rather than by typing**: TPM2 with signed policies, FIDO2 keys and network servers replace passphrases at boot, with a recovery key as the escape hatch. Disk layouts on image-based systems are becoming declarative, with encryption defined in the partition definitions (`systemd-repart` can create LUKS volumes), and integrity protection through dm-verity for the read-only system and LUKS for the writable state. Expect authenticated encryption to become more usable and the default parameters to continue shifting toward memory-hard derivation. The durable habits are simple and worth repeating: always keep at least two independent ways to unlock a volume; keep an off-disk backup of every header and refresh it after any key change; test the recovery path; and name devices by UUID so a changed device order never turns `luksFormat` into an accident. [src: rhel-10-docs 6d8e0b81ed8cdef5]
