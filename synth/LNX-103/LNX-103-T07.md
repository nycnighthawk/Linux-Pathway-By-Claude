# Using someone else's disk as your own: network file systems, NFS and SMB clients, and on-demand mounting

## Define the problem

Many files do not live on the machine that wants them. Home directories follow a user from workstation to workstation, build farms share a source tree, a department keeps its documents on a file server, a fleet of web servers needs the same uploaded media, and Windows users expect to reach the same directories from their own machines. A **network file system** lets one host (the server) export a directory tree and others (clients) mount it into their own tree, so that ordinary programs read and write it with ordinary system calls and never learn that it is remote.

That illusion has to be maintained against facts that local disks never face: latency and loss, a server that reboots while clients have files open, caches that disagree between machines, user identities that mean different things on different hosts, and a network that is not always up when a mount is wanted. The client administrator's problem is therefore concrete: choose a protocol (NFS for Unix-style sharing, SMB/CIFS for Windows interoperability), mount with the right options for safety and performance, authenticate, map identities and permissions sensibly, make the mount persistent without hanging the boot, and arrange for mounts to appear when needed and disappear when idle, which is the job of the automounter. [src: rhel-10-docs 427f3e6c210a988a]

## History and approaches

Sun Microsystems introduced NFS in 1984 as a stateless protocol over UDP: the server remembered nothing about clients, so a reboot was invisible apart from a pause, and a client simply retried. That design made recovery simple and caused its own problems: file locking and several semantics required auxiliary protocols (the lock and status daemons), and the client's cache could be stale by design. NFSv3 improved performance and allowed TCP. NFSv4 (2000, revised in 4.1 and 4.2) was a redesign that is stateful, runs over a single TCP port (2049), integrates locking, delegations, compound operations, strong security through RPCSEC_GSS and Kerberos, and a pseudo-root for exports; 4.1 added parallel NFS and session semantics, and 4.2 added server-side copy, sparse files and labelled NFS for SELinux. For a modern client the practical advice is to use v4.x unless something forces v3. [src: man-pages 6b65aed9c572c6c7]

SMB (server message block) grew out of IBM and Microsoft work on PC file and print sharing; CIFS was the name used for one dialect in the 1990s. The first versions were chatty, insecure and broadcast-driven. SMB2 (2006) reduced the protocol's chattiness; SMB3 (2012) added encryption, multichannel and transparent failover; SMB 3.1.1 added pre-authentication integrity. SMB1 is deprecated and disabled by default on current systems because of its weaknesses. On Linux, the kernel's `cifs` client (the module still carries the older name) and the `cifs-utils` helper (`mount.cifs`) implement the client side, and Samba implements the server side and domain integration. [src: man-pages b9203bd7895baae6]

Mounting also evolved. Early systems listed network file systems in fstab like local ones, with the result that a boot could hang for minutes if the server was down. The **automounter**, again from Sun, replaced static mounts with demand mounts: a daemon watches a directory and mounts the real file system when someone enters it, then unmounts it after a period of inactivity. Linux's `autofs` provides the kernel half and the `automount` daemon provides the user-space half, with map files (or LDAP and SSSD lookups) that describe what to mount where. Later, systemd offered a similar mechanism through `x-systemd.automount` options and `.automount` units, so there are now two ways to get on-demand mounts. [src: man-pages 99a7079af8a5986c]

The partial successes and failures are instructive. Statelessness made NFSv2 and v3 robust but weak at consistency and locking; hard mounts protected data integrity but hung processes in uninterruptible sleep when a server vanished; soft mounts avoided the hang and silently corrupted data. SMB1's long life through compatibility needs produced several famous worm outbreaks. Identity mapping, by numeric IDs in NFS and by SIDs in SMB, has been the quiet cause of more permission mysteries than any protocol bug. [src: archwiki f4fdcce975b11cbe]

## Current state

### NFS: the server side in brief

The server administrator lists exports in `/etc/exports`, one per line: a path and one or more clients with options in parentheses. `exportfs -ra` re-reads the file, `exportfs -v` shows what is exported with the effective options, and `showmount -e server` (v3 mountd) or a mount attempt tests access from a client. Common options: `rw` or `ro`, `sync` (reply after data is stable; the safe default), `async`, `no_subtree_check`, `root_squash` (default: map client root to the anonymous user), `no_root_squash`, `all_squash` with `anonuid=` and `anongid=`, `sec=sys:krb5:krb5i:krb5p`, `fsid=`, and `secure` (accept only reserved client ports). NFSv4 serves a single pseudo-file-system root, with exports bound below it. [src: rocky-docs b5b3c689953d9474] [src: rocky-docs 338829456e834354]

### NFS: the client

```bash
dnf install nfs-utils            # or apt install nfs-common
mount -t nfs4 files.example.com:/export/home /mnt/home -o rw,sec=sys
mount -t nfs  -o vers=3 files:/export/data /mnt/data         # forcing v3
showmount -e files                                          # exports visible via v3 mountd
nfsstat -m                                                  # effective options per mount
```

Options from nfs(5) that matter most:

| Option | Meaning |
|---|---|
| `vers=` / `nfsvers=` | protocol version: `4.2`, `4.1`, `4.0`, `3` |
| `proto=tcp` | transport (UDP is obsolete) |
| `hard` (default) / `soft` | retry forever (the call blocks) or give up and return an error after `retrans` attempts |
| `timeo=`, `retrans=` | request timeout in tenths of a second and retry count; with TCP the defaults are 600 and 2 |
| `intr` | historical and now ignored; a hung hard mount can be ended with `umount -f` or `-l`, or by killing the process with SIGKILL |
| `rsize=`, `wsize=` | transfer sizes; negotiated, usually leave alone |
| `nconnect=N` | several TCP connections per server for throughput, up to 16 |
| `sec=` | security flavour: `sys`, `krb5`, `krb5i`, `krb5p` |
| `ac`/`noac`, `actimeo=`, `acregmin=`, `acregmax=`, `acdirmin=`, `acdirmax=` | attribute cache behaviour |
| `lookupcache=` | directory entry caching: `all`, `none`, `pos`, `positive` |
| `cto`/`nocto` | close-to-open consistency, on by default |
| `bg` / `fg` | background retry of an initial mount that fails; v4 handles this poorly |
| `nosuid`, `nodev`, `noexec` | security options that apply to any mount |
| `_netdev` | tell init that the network must be up first |

Defaults can be set in `/etc/nfsmount.conf`. The client keeps its consistency promise as **close-to-open**: after a file is closed by one client, a client that opens it afterwards sees the changes; between those moments caches may differ. `noac` and short `actimeo` values trade performance for freshness. [src: man-pages 3efca8b5d704f2dc] [src: man-pages 15357372ba26ba06]

Server addresses should use the name that matches the Kerberos principal when `sec=krb5*` is used; NFSv4 maps owner names (`user@domain`) with `nfsidmap` and `/etc/idmapd.conf`, so a mismatch in the domain produces files owned by `nobody` on the client. The Arch documentation of NFS with Kerberos describes the keytab and service setup. Compliance guidance for NFS recommends security flavours stronger than `sys`, restricting the ports the server accepts, and mounting with `nosuid`; see the controls for the configuration your site follows. [src: archwiki d8625d1c521007ff] [src: compliance-as-code 9aeb52ecd2cb8360]

### SMB/CIFS: the client

```bash
dnf install cifs-utils                                    # or apt install cifs-utils
smbclient -L //files.example.com -U alice                 # list shares (from the samba-client package)
mount -t cifs //files.example.com/team /mnt/team \
  -o credentials=/root/.smbcred,uid=1000,gid=1000,file_mode=0640,dir_mode=0750,vers=3.1.1,seal
```

The credentials file has the lines `username=alice`, `password=...` and optional `domain=...`, mode 0600. Options from mount.cifs(8) worth knowing: `vers=` (`3.1.1`, `3.0`, `2.1`, `2.0`; avoid `1.0`), `sec=` (`krb5`, `krb5i`, `ntlmssp`, `ntlmsspi`, `none`), `seal` (encrypt traffic with SMB3), `uid=`, `gid=`, `forceuid`, `forcegid`, `file_mode=`, `dir_mode=`, `cruid=` (credentials of which user), `multiuser` (separate credentials per Linux user, with `sec=krb5` or credential caches), `nounix` and `unix` (POSIX extensions), `noperm`, `serverino`, `cache=` (`strict`, `none`, `loose`), `rsize=`, `wsize=`, `actimeo=`, `soft` (default is hard), `nobrl` (disable byte-range locks), `mfsymlinks`, `domain=`, `username=`, `password=` (visible in the process list: avoid it) and `guest`. Because Windows file systems do not have Unix owners, the mount presents all files as owned by the `uid=` and `gid=` given and with the stated modes, unless the Unix extensions or ID mapping are used, and mount.cifs documents how SIDs, UIDs and security descriptors are mapped. [src: man-pages 4cf1566d566dd167] [src: man-pages d3438ecfc88d0a8a]

Enterprise Linux clients often join a Windows domain with `realm join` and SSSD, after which user logins, Kerberos tickets and the `multiuser` option allow each user to access shares with their own identity. [src: rhel-10-docs 659714f4b344de87]

### Persistent mounts

In `/etc/fstab`:

```
files:/export/home   /mnt/home  nfs4  rw,sec=sys,_netdev,nofail,x-systemd.automount,x-systemd.idle-timeout=600  0 0
//files/team         /mnt/team  cifs  credentials=/root/.smbcred,uid=1000,gid=1000,_netdev,nofail,x-systemd.automount,vers=3.1.1  0 0
```

`_netdev` places the mount after the network is up (`remote-fs.target`), `nofail` stops a missing server from blocking the boot, and `x-systemd.automount` mounts on first access. For services that need the files, add `RequiresMountsFor=/mnt/home` to the unit. The Rocky documentation walks through mounting NFS shares step by step. [src: rocky-docs 889a69ac6fd74278]

### autofs

`autofs` is installed from the `autofs` package, enabled with `systemctl enable --now autofs`, and configured in `/etc/auto.master` (or files ending in `.autofs` under `/etc/auto.master.d/`):

```
# /etc/auto.master.d/net.autofs
/mnt/nfs   /etc/auto.nfs   --timeout=300
/-         /etc/auto.direct
```

An **indirect map** names subdirectories below a mount point; the **direct map** (the special `/-` mount point) names full paths. Map lines have the form **key [-options] location**:

```
# /etc/auto.nfs  (indirect)
projects   -fstype=nfs4,rw,sec=sys,nosuid   files.example.com:/export/projects
docs       -fstype=nfs4,ro                  files.example.com:/export/docs
*          -fstype=nfs4,rw                  files.example.com:/export/users/&

# /etc/auto.direct
/srv/archive  -fstype=nfs4,ro  files.example.com:/export/archive
```

The key `*` matches any name, and `&` in the location repeats the matched key, which gives home directories one-line configuration. The special option `-fstype=` selects a type other than NFS (for CIFS add `-fstype=cifs,credentials=...` with the location written as `://server/share`, with a leading colon), `-strict` treats mount errors as fatal for multi-mounts, and map options and master-map options are cumulative. Timeouts: `--timeout=N` in the master map (seconds of idleness before unmount; default 300), global defaults in `/etc/autofs.conf` (`master_map_name`, `timeout`, `browse_mode`, `logging`). Maps can come from files, executable programs (a file with the executable bit that prints the map entry for a key), NIS, LDAP or SSSD. Diagnose with `automount -f -v` (foreground, verbose), `systemctl status autofs`, `automount -m` (print the maps as the daemon sees them), and `journalctl -u autofs`. After editing maps, `systemctl reload autofs` re-reads them; a changed master map needs the reload before new mount points appear. [src: man-pages 3012728528658590] [src: man-pages b13ae9c8894ed197] [src: man-pages 51d9e56291d97e33] [src: rhel-10-docs fcebb1689589115d]

systemd's `x-systemd.automount` is the lighter alternative when you want on-demand behaviour for a few fixed mounts without installing another daemon; autofs wins when mounts are many, keyed by wildcard, or driven by a central directory service.

## Assessment: the good, the bad and the ugly

**The good.** Network file systems remove the need to copy data. NFSv4 is a mature, firewall-friendly protocol on a single port, with strong security options and good performance on modern networks (`nconnect`, parallel NFS, large transfer sizes). SMB3 offers encryption and signing and is the right choice when Windows clients are in the picture. The automounter makes shared home directories and project trees scale to thousands of entries with one wildcard line, avoids stale mounts, reduces boot dependencies, and costs nothing when idle.

**The bad.** The model hides the network until it fails. A hard-mounted share whose server vanishes leaves processes stuck in uninterruptible sleep, and `df` or `ls` in the wrong directory hangs a shell. Cache semantics are weaker than local: two clients can see different views for a short time, and applications that assume strict consistency or rely on file locking across hosts can misbehave. Identity is brittle: UID and GID numbers must match across hosts for NFS with `sys` security (or the idmap domain must), and SMB mounts flatten ownership. Options differ by protocol and version, and performance tuning (read-ahead, `rsize`, `nconnect`) is empirical. Performance of metadata-heavy workloads (compilers, package managers, untarring many small files) is far below local disk.

**The ugly.** Silent data hazards. `soft` NFS mounts can return write errors that applications do not check, and corrupt files without a trace. `sync` on the server versus `async` is a durability choice made in a file that clients never see. `no_root_squash` hands the root account of every client to the server's files. Plain-text passwords in `/etc/fstab` or on a command line are readable by other users. Firewalls and the older NFS helper daemons (rpcbind, mountd, statd) with random ports are a perennial source of tickets where a share is reachable from one subnet and not from another, and the troubleshooting guides list pages of cases such as unreliable connections from particular clients or performance cliffs caused by close-to-open flushing. Mount propagation and automounts also interact with containers: a bind mount of an automounted path can pin the mount forever or expose a path that is not yet mounted. [src: archwiki 015e3b7cd1483381] [src: archwiki 9681f1f31f43acce]

## Applications beyond this domain

Network file systems are infrastructure for several adjacent fields. Embedded development uses an NFS root file system for fast edit-compile-test cycles on a development board: the board boots a kernel that mounts its root over the network, so developers change the root file system on the host without reflashing, a workflow that training material demonstrates step by step. Kubernetes and container platforms use NFS and SMB as volume types for shared persistent storage, with CSI drivers that add provisioning and snapshots; the same issues of identity, locking and hard-mount hangs appear as pod startup delays. Virtualisation platforms use NFS and SMB datastores for virtual machine images. Scientific and rendering clusters rely on parallel file systems that build on the same client ideas (Lustre, GPFS, CephFS), and the Samba VFS modules for GPFS and Btrfs show how a server layer exposes file-system specific features to SMB clients. [src: bootlin-training 66775a74a078c374] [src: samba-docs 50e017520a0e305f] [src: samba-docs 6ab21090bfb06688]

Identity and directory services intersect through Kerberos and SSSD, which let NFS and SMB share the same login. Security teams see the topic as attack surface: file-sharing protocols are common vectors for lateral movement and ransomware, so hardening guides specify disabling the automounter when unused, restricting NFS to privileged ports and requiring strong security flavours. [src: compliance-as-code f89d469a6c3917c1] [src: compliance-as-code ee9ca1a4584a6ecd]

## Examples

**Mount a home-directory export and prove the mount options.**

```bash
mkdir -p /mnt/home
mount -t nfs4 -o sec=sys,nosuid,nodev files:/export/home /mnt/home
findmnt /mnt/home -o TARGET,SOURCE,FSTYPE,OPTIONS
nfsstat -m
```

**Home directories via autofs with a wildcard.**

```
# /etc/auto.master.d/home.autofs
/home  /etc/auto.home  --timeout=600
# /etc/auto.home
*  -fstype=nfs4,rw,sec=sys,nosuid  files.example.com:/export/home/&
```

Then `systemctl reload autofs` and `ls /home/alice` mounts only alice's directory.

**An SMB share with a credentials file.**

```bash
install -m 600 /dev/null /root/.smbcred
printf 'username=alice\npassword=secret\ndomain=EXAMPLE\n' > /root/.smbcred
mount -t cifs //files/team /mnt/team -o credentials=/root/.smbcred,vers=3.1.1,uid=1000,gid=1000
```

**A mount that must not block boot.** Use `_netdev,nofail,x-systemd.automount,x-systemd.mount-timeout=30` in fstab, then `findmnt --verify`.

**Diagnose a hung share.**

```bash
mount | grep nfs
nfsstat -c
ss -tn dst files.example.com
umount -f -l /mnt/home          # lazy, forced; last resort
journalctl -k | grep -i nfs
```

## Related problems and ideas

The neighbouring problems are authentication and naming (Kerberos, SSSD, ID mapping), service discovery (DNS, mDNS, DFS referrals), and file locking semantics across hosts (NFS byte-range locks, SMB oplocks and leases). Storage-side alternatives answer the same need differently: block protocols such as iSCSI (the next topic) give a client a disk and leave the file system to it, with no sharing between writers; replicated and distributed file systems (Ceph, GlusterFS, Lustre) scale out; object storage trades POSIX semantics for scale and is accessed by HTTP APIs, often through FUSE adapters such as s3fs or rclone mount. Backup and synchronisation tools (rsync, restic, covered later) avoid live sharing by copying. Another close issue is container storage: a pod that mounts NFS runs into the same permission and hang problems, which is why storage classes document `nfsvers`, `hard` and `nconnect` explicitly.

## Active research

Current NFS work covers faster transports (RDMA, `nconnect`, parallel NFS layouts), server-side copy and clone (NFSv4.2), labelled NFS for mandatory access control, improved locking and delegation, in-kernel TLS (RPC-with-TLS, which gives NFS transport encryption without Kerberos), and better cache behaviour for large directories. In SMB, the kernel client and `ksmbd` (an in-kernel SMB3 server) are active areas, along with SMB over QUIC, multichannel and RDMA, compression, and POSIX extension work to make the Linux-to-Linux SMB experience closer to NFS. For on-demand mounting, ongoing questions concern how automounts interact with mount namespaces and with systemd's own automount, and how to make idle unmounting safe with containers.

## Future direction

Expect convergence in a few directions. Encryption by default: NFS over TLS and SMB3 encryption lower the cost of securing traffic that used to be sent in the clear on "trusted" networks. Cloud-native storage drivers wrap NFS and SMB with provisioning and policy, so the client options in this lesson appear in storage class definitions instead of fstab lines. Object and distributed storage take over bulk and scale-out workloads, leaving NFS and SMB for shared home directories, tool trees and Windows interoperability. For administrators the lasting guidance is stable: use NFSv4.x or SMB3, name the options explicitly, prefer `hard` with `nofail` and automount to `soft`, keep credentials out of command lines, choose on-demand mounts for anything not required at boot, and test what happens when the server disappears before it does. [src: rhel-10-docs e3954f90f8ff9db6]
