# When memory runs short: swap partitions, swap files, compressed swap in RAM

## Define the problem

Physical memory is finite and programs are greedy. Some of what a process holds is cold: a pointer table it built at start-up, a library page it touched once, a cache it will not read again for hours. If that cold data stays in RAM it displaces something warm, such as file cache that would speed up the next read. Linux therefore needs somewhere to put anonymous pages (memory that has no file behind it) when memory is tight. That place is **swap**: a region on storage, or a compressed region in RAM, to which the kernel can write pages out and read them back on demand.

The administrator has to decide several things. Whether to have swap at all, and how much. Whether it should be a dedicated partition, a file on an ordinary file system or a compressed block device in memory. How to make it persistent. How aggressive the kernel should be about using it. How to protect its contents, since it may hold passwords and keys in clear. And how to reconcile it with other uses: hibernation needs swap big enough for the memory image, containers and orchestrators have their own ideas about memory limits, and an out-of-memory killer waits at the end if all the options fail. The topic is small compared with LVM or RAID, but it is a regular exam item and a common source of "the server is slow" tickets. [src: rhel-10-docs 3ca353b65ad1d636]

## History and approaches

Swapping began with whole-process swapping in early Unix, when a process was written out entirely to make room. Paging replaced it: the unit became the page, typically 4 KiB, and only individual pages move. For many years the received wisdom was "swap twice your RAM", a rule from a time when memory was measured in megabytes. Practice moved away from rules of that kind once servers had many gigabytes and the cost of paging to a rotating disk became obvious: a machine that starts to swap heavily stops being useful long before it runs out of space. Vendors now publish tables that scale swap with RAM and workload, and some cloud images ship with none.

The first Linux swap spaces were partitions marked with a swap type (0x82 on MBR; a dedicated GUID on GPT) and initialised with `mkswap`. Swap **files** came next, because a partition cannot be enlarged without repartitioning, while a file can be added in seconds. The kernel handles a swap file by mapping its blocks and writing to them directly, bypassing the file system, which introduced limits that surprised people: a file with holes cannot be used, and neither can a file on a copy-on-write file system without special handling. Preallocated files from `fallocate` were rejected on some file systems until XFS support arrived in kernel 4.18, and Btrfs support arrived in 5.0 for files with the no-copy-on-write attribute. [src: man-pages 7fbf5db8bf728638]

The compressed alternatives are younger. **zswap** is a compressed cache in front of an existing swap device: pages headed for swap are compressed and kept in RAM, and only evicted to disk when that pool fills. **zram** is a block device whose contents live compressed in memory, usable as the swap device itself with no disk behind it. Both trade CPU time for avoiding disk I/O, which pays off on machines with fast CPUs, slow storage or flash that should not be worn, and in small virtual machines and embedded boards. Distributions began turning zram on by default for desktops, and a systemd generator (`zram-generator`) made it a configuration file instead of a script. [src: archwiki 9a25eb5327f3bdeb]

Along the way there were partial successes and plain failures. Heuristics for when to swap (`vm.swappiness`) were tuned and retuned; swapping to network storage (NFS) is documented as unreliable; swap in containers was disabled by default in Kubernetes for years because the scheduler's memory guarantees assume that a pod either has the RAM or is killed, and swap support returned as an opt-in with documented risks. [src: kubernetes-docs 6beb98563f580e35]

## Current state

### What the kernel does

When free memory falls below thresholds, the kernel's reclaim code chooses between dropping clean file cache pages (cheap, can be re-read) and swapping out anonymous pages (needs a write). `vm.swappiness` (range 0 to 200 on current kernels, default 60) biases that choice: lower values prefer dropping file cache, higher values swap anonymous memory more readily; 0 does not forbid swap but makes it a last resort. Swap spaces have **priorities**: the kernel uses higher priority areas first and round-robins between areas of equal priority, so several devices at one priority are striped. `cat /proc/swaps` lists areas with type, size, used and priority, `swapon --show` formats it, `free -h` summarises, and `vmstat 1` shows the `si` and `so` columns (pages swapped in and out) that matter more than the used total. When nothing is left to reclaim the OOM killer selects a victim by score (`/proc/<pid>/oom_score`, adjusted with `oom_score_adj`). [src: man-pages 3a029112a67be315]

### Partition or logical volume as swap

```bash
mkswap -L swap0 /dev/vg0/swap          # write the swap signature; -U sets a UUID
swapon /dev/vg0/swap                   # activate now; -p 10 sets the priority
swapon --show
# persist
echo 'UUID=<uuid>  none  swap  defaults,pri=10  0 0' >> /etc/fstab
```

`swapoff /dev/vg0/swap` deactivates (it must be able to move pages back into RAM, so it fails or takes long if memory is short), `swapon -a` and `swapoff -a` act on every swap area listed in fstab, `swapon -s` is the old summary form. fstab options useful for swap: `pri=`, `discard` (or `discard=once` or `discard=pages`), `nofail`, `noauto`, `x-systemd.device-timeout=`. At boot, `systemd-fstab-generator` turns each swap line into a `.swap` unit, named after the device or file in the same escaped form as mount units (`dev-vg0-swap.swap`), and swap units are only available to the system manager. [src: man-pages b5f2e90dd29742e6]

### Swap file

```bash
dd if=/dev/zero of=/swapfile bs=1M count=2048 status=progress   # portable: no holes
# or: fallocate -l 2G /swapfile                                  # fine on ext4 and XFS 4.18+
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile  none  swap  defaults  0 0' >> /etc/fstab
```

Rules: root should own the file and nobody else should read it (swapon warns about looser modes), the file must have no holes (so not `truncate` and not `cp --sparse`), must not be on NFS, and on Btrfs must be created with the no-COW attribute and compression off. The helper `btrfs filesystem mkswapfile --size 2g /swap/swapfile` (btrfs-progs 6.1 and later) or `mkswap --file` (util-linux 2.41 and later) does this correctly. A swap file can also be resized by `swapoff`, enlarging and repeating `mkswap` and `swapon`. For hibernation to a swap file the kernel needs the file's physical offset: `filefrag -v /swapfile` shows it, and the boot arguments become `resume=UUID=<fs uuid> resume_offset=<first physical block>`. [src: man-pages 7fbf5db8bf728638]

### zram

```bash
modprobe zram num_devices=1                       # or let zramctl create one
zramctl --find --size 4G --algorithm zstd         # prints /dev/zram0
mkswap /dev/zram0 && swapon -p 100 /dev/zram0     # higher priority than disk swap
zramctl                                           # columns: NAME ALGORITHM DISKSIZE DATA COMPR TOTAL STREAMS MOUNTPOINT
```

The kernel interface is in `/sys/block/zram0/`: `comp_algorithm` (choose before setting size), `disksize` (the uncompressed capacity; the real memory used is the compressed size, typically 2 to 4 times smaller), `mem_limit`, `mm_stat` (a line of counters: original data size, compressed size, memory used, limit, maximum used, same pages, pages compacted), `reset`, and optional `backing_dev` to push idle pages to a disk. A `disksize` of half of RAM is the usual default in distributions. The persistent form is `zram-generator`, configured in `/etc/systemd/zram-generator.conf`, or a drop-in under `/etc/systemd/zram-generator.conf.d/`:

```ini
[zram0]
zram-size = min(ram / 2, 8192)
compression-algorithm = zstd
swap-priority = 100
fs-type = swap
```

`systemctl daemon-reload` and `systemctl start systemd-zram-setup@zram0.service` apply it. [src: archwiki 9a25eb5327f3bdeb]

### zswap

zswap is enabled with kernel parameters (`zswap.enabled=1 zswap.compressor=zstd zswap.zpool=zsmalloc zswap.max_pool_percent=20`) or at runtime through `/sys/module/zswap/parameters/`. It needs a real swap device behind it and is invisible to `swapon`; `grep -r . /sys/kernel/debug/zswap` shows its statistics. Choose zram for diskless or small machines, and zswap when you already have disk swap and want to cut the I/O, but do not run both for the same purpose.

### Protecting swap contents

Swap holds whatever the kernel pushed out, including secrets. Options: encrypted swap with a throw-away key (an `/etc/crypttab` line of the form `swap /dev/vg0/swap /dev/urandom swap,cipher=aes-xts-plain64,size=512`), swap on top of a LUKS volume that is unlocked at boot (but then hibernation needs a persistent key), `mlock()` for the secret itself, or zram only with no disk swap. Benchmarks such as the RHEL 10 STIG set requirements on how sensitive memory is handled; check the current control text for your profile.

### Sizing and tuning

There is no single answer, but the usual guidelines are: for a typical server, swap in the range from a fraction of RAM to equal to RAM; for database hosts, the vendor's guidance (some want very little); for hibernation, at least RAM size; for small memory-constrained VMs, zram plus a small disk swap. Vendor tables for RHEL give a progression by RAM size. Tune with `sysctl vm.swappiness=10` (persist in `/etc/sysctl.d/`), `vm.vfs_cache_pressure`, and `vm.min_free_kbytes` only with evidence. Per-cgroup control is available through `memory.swap.max` and `memory.swap.high` (and systemd's `MemorySwapMax=`), which lets one service be forbidden swap while others use it. [src: rhel-10-docs 7618cb99d42deed5]

## Assessment: the good, the bad and the ugly

**The good.** Swap turns a hard failure (the OOM killer) into a soft one (a slowdown), gives the kernel room to push idle pages out in favour of cache, and is necessary for hibernation. It is easy to add and remove while the system runs, and swap files make capacity adjustable without partitioning. zram gives real extra capacity from compression at a cost of CPU and is nearly free to configure; on desktops and small VMs it often removes the lag that appears at memory pressure.

**The bad.** Swapping to rotating disk is slow by orders of magnitude, and a system that is truly short of memory enters **thrashing**, in which it spends nearly all its time paging and responds to nothing. The kernel's reclaim is not aware of which application is latency-sensitive. Swap hides leaks: a service that grows slowly may swap for days before anyone notices. Compressed memory is not free capacity either: pages that do not compress (already compressed media, encrypted data) use their full size, and zram's data lives in RAM, so a workload that needs real memory gets none from it.

**The ugly.** Swap files on unsupported file systems fail in confusing ways: `swapon` refuses a file with holes, a file on Btrfs without no-COW, or a file on an unsuitable network mount, and the error text is short. Files created with `fallocate` sometimes work and sometimes do not. Hibernation with a swap file needs the right offset, and a resize invalidates it. Orchestrators complicate it further: cgroup-aware services see a memory limit and a separate swap limit, and Kubernetes support for swap has documented risks such as memory-backed volumes landing in swap and eviction logic that ignores it. [src: kubernetes-docs 3aa1fa6d20416000]

## Applications beyond this domain

The same ideas of paging cold data out and compressing what stays are found in many systems. Mobile operating systems use compressed memory in place of disk swap. Databases and caches implement their own buffer managers that decide what to evict, and tell the kernel to leave them alone (`mlock`, huge pages, `swappiness` guidance). Virtual machine monitors balloon guest memory and may swap guest pages at the host, which is why a guest can look healthy while the host thrashes. Container platforms must decide what happens once a memory limit is reached, and swap policy is part of that decision. Serverless platforms and microVM snapshotting go further and write the whole memory image of a guest to storage so it can be resumed later, which is the same idea as hibernation applied to a different unit. [src: kubernetes-docs 6beb98563f580e35]

On embedded boards, where flash is slow and wears out, zram is often the only swap used, and optimisation guides recommend it along with mount options that reduce writes. [src: archwiki 32f793636d883dcc]

## Examples

**Add 4 GiB of swap to a running server and keep it across reboots.**

```bash
dd if=/dev/zero of=/swapfile bs=1M count=4096
chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
printf '/swapfile none swap defaults 0 0\n' >> /etc/fstab
swapon --show && free -h
findmnt --verify
```

**Make zram the first-choice swap, with a disk file as the fallback.**

```ini
# /etc/systemd/zram-generator.conf
[zram0]
zram-size = ram / 2
compression-algorithm = zstd
swap-priority = 100
```

The swap file stays at default priority (-2 for the first automatic area), so zram fills first.

**Find out whether swapping is the cause of slowness.**

```bash
vmstat 1 5            # watch si/so, not just free memory
swapon --show
sar -B 1 3            # pgpgin, pgpgout, majflt/s if sysstat is installed
grep -E 'SwapTotal|SwapFree|Dirty' /proc/meminfo
```

**Remove swap safely.**

```bash
swapoff /swapfile && rm /swapfile       # then delete the fstab line
```

**Encrypted swap with a random key on every boot.** `/etc/crypttab`: `swap  /dev/vg0/swap  /dev/urandom  swap,cipher=aes-xts-plain64,size=512`; `/etc/fstab`: `/dev/mapper/swap none swap defaults 0 0`.

## Related problems and ideas

Swap belongs to the larger memory-management family: the page cache, the OOM killer, memory cgroups, transparent huge pages, NUMA balancing and the new multi-generational LRU reclaim. The **out-of-memory handling** question has user-space answers (`systemd-oomd`, `earlyoom`, `nohang`) that act before the kernel's last resort, using pressure-stall information (`/proc/pressure/memory`) to decide when a machine is in trouble. **Pressure-stall information** itself is worth knowing: it tells you the fraction of time tasks are stalled on memory, which is a better signal than "swap used".

On the storage side, a swap device is one more consumer of the layers in this course: an LVM volume can hold it, a RAID array can protect it (a failed swap disk can crash running processes), encryption can cover it, and thin-provisioned storage underneath will hold only the blocks that were actually written.

## Active research

Kernel work in this area includes reclaim algorithms that predict which pages are cold (the multi-generational LRU), better accounting of zswap and zram per cgroup, zswap writeback control so that idle compressed pages are pushed to disk rather than held forever, support for swapping large folios in one piece, and swap on faster media such as persistent memory or CXL-attached memory used as a slower tier. Operators are experimenting with proactive reclaim (`memory.reclaim`) driven by pressure information, and with tiered memory where cold pages move to cheaper memory without ever touching storage. Research on compressors tunes the trade-off between ratio and speed, and zstd and lz4 are common choices.

## Future direction

Expect swap to continue evolving from "a disk area for emergencies" into one tier in a memory hierarchy: fast RAM, compressed RAM, remote or CXL memory, then flash. Defaults will keep moving toward compressed swap in memory with a small disk-backed tail, with sizing driven by pressure metrics, and container platforms will extend swap awareness into scheduling with explicit per-workload limits. Administrators should hold on to a few durable habits. Measure paging activity instead of looking at swap used. Prefer swap files or logical volumes that can be adjusted. Verify a swap setup with `swapon --show` and `findmnt --verify` before a reboot. Keep secrets in mind by encrypting swap. And remember that the real fix for sustained swapping is memory, a leak fix or a smaller workload, not a bigger swap area. [src: rhel-10-docs 3ca353b65ad1d636]
