# Disks over the network: block storage with iSCSI targets and initiators

## Define the problem

NFS and SMB hand a client a file tree. Some clients want something lower: a raw disk. A database that manages its own file layout, a hypervisor that stores virtual machine disks, a cluster that needs the same volume visible from several nodes, a server that boots with no local disk: each wants a block device that behaves as though a drive were attached, but whose storage sits in a central array where it can be pooled, replicated, snapshotted and moved between hosts.

SCSI, the command set that Linux uses for most disks, was designed for a short parallel cable. The problem is to carry those commands over a network without losing the semantics that file systems depend on: ordered, reliable delivery, and write acknowledgements that mean the data is safe. Fibre Channel solved this with its own fabric and switches. **iSCSI** solves it with ordinary TCP/IP and Ethernet, which makes block storage affordable and routable, and shifts several problems onto the administrator: naming and discovery, access control, authentication, performance isolation, multiple paths for resilience, and ensuring that two hosts do not write the same volume at once. This topic covers both ends of the connection: the **target** that presents storage, and the **initiator** that consumes it. [src: rhel-10-docs 13d41ddc3ba56d84]

## History and approaches

The command set underneath, SCSI, dates from the 1980s as a standard bus for disks and other peripherals. Storage area networks of the 1990s extended it over Fibre Channel, which delivers lossless frames with dedicated hardware and a dedicated skill set. In the early 2000s the IETF standardised iSCSI (RFC 3720, consolidated in RFC 7143), which wraps SCSI commands in protocol data units carried over TCP, typically on port 3260. It arrived with promises of cheap SANs on commodity Ethernet, and for many small and mid-sized installations that proved true, while the first generation was criticised for CPU cost, latency and the temptation to share a congested network. Offload NICs (iSCSI HBAs) and faster Ethernet reduced the cost, and later RDMA transport extensions (iSER) removed most of the host overhead.

Linux's initiator, **Open-iSCSI**, is split into a kernel part and the user-space `iscsid` daemon with the `iscsiadm` management tool. On the target side Linux went through several implementations: iSCSI Enterprise Target and the user-space `tgt` first, then **LIO** (Linux-IO), which became the in-kernel SCSI target in version 2.6.38 and replaced the older ones in most distributions. The tool that configures LIO is **targetcli**, an interactive shell that presents the configuration as a tree of objects and saves it to a JSON file. [src: rhel-10-docs 72c83aa534bb8f9a]

Two later developments frame the current state. Virtualisation and cloud systems made block volumes over the network the normal way to attach disks, usually with their own protocols and drivers instead of iSCSI. NVMe over Fabrics, including the TCP transport, offers the same function with a command set built for flash and much lower overhead. iSCSI remains in wide use because it is everywhere: every enterprise array speaks it, every operating system has an initiator, and boot-from-SAN setups rely on it.

Failures and partial successes follow a pattern. Early deployments shared a network with general traffic and saw erratic latency; best practice moved to dedicated VLANs or interfaces. Security was an afterthought: iSCSI ships with weak authentication (CHAP) and no encryption, and was often protected only by network isolation. Mounting one LUN read-write from two hosts, believing that "shared storage" meant "shared safely", corrupted file systems across the industry, which is why cluster file systems, SCSI persistent reservations and fencing exist. [src: clusterlabs-docs 5aa7be7d2a9a9ffc]

## Current state

### Concepts and names

An iSCSI **target** is a named endpoint that exposes one or more **LUNs** (logical unit numbers), each a block device. An **initiator** is a client. Both have an **IQN** (iSCSI qualified name), of the form `iqn.YYYY-MM.reversed-domain:unique-string`, for example `iqn.2025-06.com.example:storage.disk1`; EUI and NAA forms also exist. A target has one or more **target portal groups** (TPGs), each with **portals** (IP address and port 3260) that clients connect to. A client first runs **discovery** (asking a portal which targets it offers) and then **login** (creating a session to a target). A **session** can have several TCP connections, and a LUN can be reached through several sessions (multipath).

### The target with targetcli (LIO)

```bash
dnf install targetcli                         # apt install targetcli-fb
systemctl enable --now target                 # restores the saved configuration at boot
targetcli
/> backstores/block create name=disk1 dev=/dev/vg0/lun1
/> backstores/fileio create name=file1 file_or_dev=/var/lib/iscsi/file1.img size=10G
/> iscsi/ create iqn.2025-06.com.example:storage.disk1
/> iscsi/iqn.2025-06.com.example:storage.disk1/tpg1/luns create /backstores/block/disk1
/> iscsi/iqn.2025-06.com.example:storage.disk1/tpg1/acls create iqn.2025-06.com.example:client1
/> iscsi/iqn.2025-06.com.example:storage.disk1/tpg1/portals create 192.0.2.10 3260
/> saveconfig
/> exit
firewall-cmd --permanent --add-port=3260/tcp && firewall-cmd --reload
```

**Backstores** are what back a LUN: `block` (a raw device or logical volume), `fileio` (a file, with optional write caching), `ramdisk` (memory, for testing) and `pscsi` (pass-through of a physical SCSI device). Creating a target also creates a default portal on all addresses on some versions; remove it if you want to bind only one. The **ACL** names the initiator IQN that may log in; with ACLs defined, an initiator that is not listed is refused, and creating the ACL maps existing LUNs to it. A read-only LUN is made by turning off automatic mapping and mapping manually. `ls` at any point displays the object tree; `saveconfig` writes `/etc/target/saveconfig.json`; `clearconfig confirm=True` deletes everything; `/> iscsi/ delete <iqn>` removes a target including its ACLs, LUNs and portals. Authentication with CHAP is set on the TPG or ACL (`set auth userid=... password=...`, with `set attribute authentication=1` on the TPG), and mutual CHAP adds `mutual_userid` and `mutual_password`. [src: rhel-10-docs 13d41ddc3ba56d84] [src: rhel-10-docs 72c83aa534bb8f9a]

### The initiator with iscsiadm (Open-iSCSI)

```bash
dnf install iscsi-initiator-utils             # apt install open-iscsi
systemctl enable --now iscsid iscsi           # iscsi restores sessions at boot
cat /etc/iscsi/initiatorname.iscsi            # InitiatorName=iqn.... must match the target's ACL
iscsiadm -m discovery -t sendtargets -p 192.0.2.10        # list targets offered by a portal
iscsiadm -m node -T iqn.2025-06.com.example:storage.disk1 -p 192.0.2.10 --login
iscsiadm -m session -P 3                      # verbose: shows the attached SCSI disk
lsblk; ls -l /dev/disk/by-path | grep iscsi
iscsiadm -m node -T iqn.2025-06.com.example:storage.disk1 -p 192.0.2.10 --logout
```

If the ACL on the target uses a custom name, set `InitiatorName=` in `/etc/iscsi/initiatorname.iscsi` to match and restart `iscsid`. `/etc/iscsi/iscsid.conf` holds the defaults for all nodes: `node.startup = automatic` (log in at boot; `manual` otherwise), `node.session.timeo.replacement_timeout` (seconds to wait for a lost session to return before failing I/O to upper layers; the default is 120), `node.session.auth.authmethod = CHAP`, `node.session.auth.username` and `node.session.auth.password` (and the `.username_in` and `.password_in` pairs for mutual CHAP), `node.conn[0].timeo.noop_out_interval` and `noop_out_timeout` (keep-alive pings), and queue depth and header and data digests. Per-node settings are stored in the database under `/var/lib/iscsi/nodes/` and changed with `iscsiadm -m node -T <iqn> -p <portal> -o update -n node.startup -v automatic`. `iscsiadm -m node -o delete` forgets a node. [src: rhel-10-docs 348b6b1a5aea7925] [src: rhel-10-docs fd697ad439af9b9b]

After login the kernel exposes the LUN as an ordinary SCSI disk, `/dev/sdX`. Device letters are unstable across logins, so use persistent names: `/dev/disk/by-path/ip-192.0.2.10:3260-iscsi-<iqn>-lun-0` encodes the path, and `/dev/disk/by-id/scsi-<wwid>` or `wwn-` names the volume itself, which is the right name when several paths exist. Rescan after the target adds or resizes a LUN with `iscsiadm -m session --rescan` or `echo 1 > /sys/block/sdb/device/rescan`.

### Using the LUN safely

The new device is an empty disk: partition or use it directly, create a file system or an LVM physical volume, and mount. Because the device appears only after the network and `iscsid` are up, the `/etc/fstab` line needs `_netdev` (and `nofail` unless the mount is required to boot), so that systemd orders it after `remote-fs-pre.target` and the iSCSI services:

```
UUID=<fs uuid>  /srv/san  xfs  defaults,_netdev,nofail  0 0
```

A LUN must have exactly one writer unless a cluster-aware file system or volume manager sits on top (GFS2, OCFS2, or clustered LVM with `lvmlockd`) and a cluster stack provides locking and **fencing**: the ability to cut a misbehaving node off from storage so that it cannot write stale data. ClusterLabs documents fence devices and timeouts as part of any shared-storage design. SCSI persistent reservations, which let the storage array refuse writes from non-owners, are another layer; hypervisors carry them through for live migration. [src: clusterlabs-docs 0b6632ca8ad60e4a] [src: qemu-docs 269dd6caad476ced]

### Multipath

Two portals on different networks present the same LUN twice, as two `sdX` devices. Writing to either is possible and dangerous. The device-mapper multipath layer (`multipathd`, `multipath -ll`; the final topic in this course) recognises that both are the same volume by WWID and presents one `/dev/mapper/mpathX`, handling failover and load spreading. For iSCSI with several paths, `replacement_timeout` is often lowered (for example to 5 seconds) so that multipath fails over quickly instead of waiting for the session to return.

### Booting from iSCSI

A diskless server can boot from a LUN. The firmware (iBFT, the iSCSI boot firmware table, or a PXE boot loader) provides the target details; the initramfs then logs in. With dracut, kernel arguments such as `rd.iscsi.initiator=`, `netroot=iscsi:...` and `ip=` configure the session, which the `dracut.cmdline(7)` manual lists along with `rd.iscsi.firmware`. The root file system must then be reachable before the system starts the full network stack, which is a common source of boot failures. [src: man-pages b3abfb6b79944f66]

### Troubleshooting checklist

On the initiator: can it reach the portal (`ping`, `nc -vz 192.0.2.10 3260`)? Does `iscsiadm -m discovery` list the target? Does login succeed (`journalctl -u iscsid`)? On failure with "authorization failure" check CHAP names and secrets; with "initiator failed authorization" check the ACL against `/etc/iscsi/initiatorname.iscsi`; with a login that succeeds but no disk, check LUN mapping on the target. On the target: `targetcli ls` for the tree, `dmesg` for LIO messages, and `/sys/kernel/config/target/` for the configfs view that targetcli manipulates.

## Assessment: the good, the bad and the ugly

**The good.** iSCSI uses ordinary Ethernet, gives a standard block device to any operating system, and is easy to set up on both sides on Linux (a few `targetcli` commands, a few `iscsiadm` commands). It integrates with LVM, multipath and clustering, is supported by every array on the market, and allows boot from SAN. For labs it is wonderful: a file on one VM becomes a disk on another within minutes, the way a virtual disk image attached to a hypervisor guest appears as a local drive.

**The bad.** It rests on a general-purpose network: latency, loss and congestion appear as storage stalls. Authentication is basic, traffic is unencrypted unless wrapped, and access control by IQN is name-based. Many layers (network, target, session, multipath, device-mapper, file system) must all be right, and diagnostics cross all of them. Performance tuning (jumbo frames, queue depth, number of sessions, `nconnect`-like multi-connection settings) is workload-specific. A block target also cannot share files between clients without a cluster file system.

**The ugly.** The worst outcomes involve two writers on a non-cluster file system, which produces silent corruption that is discovered much later, and sessions that vanish for a few seconds, which may freeze I/O for the full replacement timeout and make applications hang or fail. Stale device names after a re-login can cause a script to format the wrong disk. A mistyped `targetcli` command that exports a production logical volume to the wrong ACL gives another host full write access. CHAP secrets stored in `iscsid.conf` are plain text and need restrictive permissions. And "boot from SAN" setups fail in ways that look like network problems because the initramfs has less tooling than the full system.

## Applications beyond this domain

Block storage over IP appears throughout infrastructure. Virtualisation platforms attach virtual machine disks over iSCSI or similar protocols; libvirt models iSCSI as a storage pool type (a target and host in an XML pool definition) and as a disk source in domain XML, and desktop hypervisors can attach to iSCSI too. Kubernetes uses iSCSI volumes and CSI drivers built on the same initiator tools. Backup and disaster-recovery systems use iSCSI to present snapshots to a recovery host. The same two-sided model, a named target and an authorised initiator with discovery and login, appears in newer protocols (NVMe over Fabrics, with subsystem NQNs and `nvme discover`), so skills transfer. [src: libvirt-docs ecf8b7ae2ab670d5] [src: libvirt-docs 4e9b85954c720ac4] [src: virtualbox-docs 3e31cd09000a5fc6]

In clustering, shared block storage is the classic basis for failover services: two nodes see the same LUN, one mounts it, and the cluster manager moves ownership on failure, with fencing guaranteeing that the old owner is really gone. [src: clusterlabs-docs 5aa7be7d2a9a9ffc]

## Examples

**A lab SAN in two virtual machines.** On the storage VM, create a 10 GiB logical volume and a target; on the compute VM, log in and format.

```bash
# storage VM
lvcreate -L 10G -n lun1 vg0
targetcli backstores/block create name=lun1 dev=/dev/vg0/lun1
targetcli iscsi/ create iqn.2025-06.lab.example:san.lun1
targetcli iscsi/iqn.2025-06.lab.example:san.lun1/tpg1/luns create /backstores/block/lun1
targetcli iscsi/iqn.2025-06.lab.example:san.lun1/tpg1/acls create iqn.2025-06.lab.example:compute1
targetcli saveconfig

# compute VM
echo 'InitiatorName=iqn.2025-06.lab.example:compute1' > /etc/iscsi/initiatorname.iscsi
systemctl restart iscsid
iscsiadm -m discovery -t sendtargets -p 192.0.2.10
iscsiadm -m node -L all
mkfs.xfs /dev/disk/by-path/ip-192.0.2.10:3260-iscsi-iqn.2025-06.lab.example:san.lun1-lun-0
```

**Make the login permanent.** `iscsiadm -m node -T <iqn> -p 192.0.2.10 -o update -n node.startup -v automatic`, then add an fstab line with `_netdev,nofail`.

**Enable CHAP on the initiator.** In `/etc/iscsi/iscsid.conf`: `node.session.auth.authmethod = CHAP`, `node.session.auth.username = lab`, `node.session.auth.password = <secret>`, then `systemctl restart iscsid` and `chmod 600 /etc/iscsi/iscsid.conf`.

**Remove everything cleanly.**

```bash
umount /srv/san
iscsiadm -m node -T <iqn> -p 192.0.2.10 --logout
iscsiadm -m node -T <iqn> -p 192.0.2.10 -o delete
# on the target
targetcli iscsi/ delete <iqn>
targetcli backstores/block delete lun1
targetcli saveconfig
```

## Related problems and ideas

The immediate neighbours are **multipath** (several routes to one device, the last topic in this course), **LVM** (volumes on the LUN, or LUNs under volume groups), and **cluster file systems and fencing**. Alternatives to iSCSI include Fibre Channel and FCoE (same SCSI semantics on a dedicated fabric), **NVMe over Fabrics** (the modern, lower-overhead option over TCP or RDMA), **AoE** (ATA over Ethernet, layer 2 only), **Ceph RBD** and **DRBD** (distributed or replicated block devices that avoid a single array), and NFS or SMB when file semantics are enough. Related operational problems are queue-depth and latency tuning, network isolation with VLANs and jumbo frames, capacity and thin provisioning on the array (with discards passed through), and encrypting data at rest with LUKS on the initiator when the network and array are not trusted.

## Active research

Work in this area includes NVMe/TCP and RDMA transports that supplant SCSI-level overhead, multipath and failover semantics for NVMe (native NVMe multipath in the kernel), improved discovery and automatic connection management, TLS support for NVMe/TCP and for iSCSI-like transports, and storage disaggregation, where compute nodes mount remote flash as if it were local. Kernel developers continue to work on the SCSI target core (LIO) for correctness with persistent reservations and thin-provisioning commands, and on the block multi-queue layer so that remote devices can use many queues without lock contention. In the cluster field, fencing and quorum design is evolving toward faster failure detection with storage-based poison pill and watchdog mechanisms.

## Future direction

iSCSI will remain a stable, boring interface for existing arrays and for small, simple SANs, while new deployments move toward NVMe over TCP for performance and toward cloud-native volume services that hide the protocol behind CSI drivers. Expect configuration to move from interactive tools into declarative form (storage system roles, Kubernetes storage classes), and expect encryption and stronger authentication to become defaults rather than add-ons. For the administrator the stable lessons are these. Name devices by WWID or path, not by `sdX`. Mount with `_netdev` and `nofail`. Never give two hosts write access to the same LUN without a cluster stack. Test failure by pulling a network cable before production does it for you. And treat the initiator name, the ACL and the CHAP secret as the access control that they are. [src: rhel-10-docs 348b6b1a5aea7925]
