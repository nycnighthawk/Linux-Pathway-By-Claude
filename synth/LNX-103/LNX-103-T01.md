# Dividing a disk so that several owners can share it: partition tables, GPT and MBR

## Define the problem

A disk is a flat run of numbered sectors. Nothing in the hardware says which sectors belong to the boot loader, which to the operating system, which to swap and which to a second system. Someone has to write that agreement onto the disk itself, in a place and a format that firmware, boot loaders, kernels and repair tools can all find and trust before any file system is mounted. That agreement is the partition table.

The problem has three parts. The first is **description**: a small, fixed structure at a known location that lists each region's start, length, kind and (ideally) a name and a unique identity. The second is **discovery**: firmware must read it before an operating system exists, and a running kernel must learn about changes without a reboot. The third is **safety**: the table is the root of everything above it, so a lost or half-written table can make a healthy disk look empty. Over the years the field has also had to accommodate size (disks outgrew the original structure), sector size (drives that read 4096 bytes internally but report 512), alignment (a misaligned partition makes every write cost two) and boot (what firmware expects to find on the disk).

For an administrator the practical questions are concrete. Which label type should this disk carry, and how do I know what it carries now? How do I add, resize or remove a partition on a disk that is in use? How do I make the kernel notice? How do I name the partitions so that scripts keep working when device letters change? And how do I record the layout so that it can be rebuilt, audited or restored after a mistake? [src: rhel-10-docs 7daac40e988bdae4]

## History and approaches

The first widely used scheme lived in the first sector of the disk, the master boot record. Its 512 bytes held a small piece of boot code, four 16-byte entries describing partitions, and a two-byte signature (0x55 0xAA). Each entry stored a status byte, a type byte, and the start and length. Early entries used cylinder, head and sector coordinates, which stopped working as disks grew, so entries gained linear block addresses held in 32-bit fields. That choice fixed the ceiling: with 512-byte sectors, 2^32 sectors is 2 TiB, and no partition can start or end beyond it. [src: rhel-10-docs ed2faf33540fe9a7]

Four entries were too few, so one entry could be marked as an **extended partition** (type 0x05, later 0x0f for large disks) that contained a chain of further descriptors, each describing one logical partition. The result worked but was fragile: logical partitions were numbered from 5 regardless of how many existed, deleting one in the middle renumbered the ones after it, and a damaged link in the chain hid every partition beyond it. Type bytes became a tiny registry (0x83 for Linux data, 0x82 for swap, 0x8e for LVM, 0xfd for RAID autodetect, 0xef for an EFI system partition) maintained by convention rather than by any authority. MBR also kept no copy of itself; one bad write to sector 0 lost the table. [src: man-pages 12f7f7fe9b7e7ac8]

The GUID partition table came out of the EFI effort and became part of the UEFI specification. It replaced the single sector with a structure that is stored twice, checksummed, and sized for modern disks. A **protective MBR** remains in sector 0 with one partition of type 0xee covering the whole disk, so that old tools see a disk that is fully used instead of an empty one and do not offer to create something over it. The **primary GPT header** sits in LBA 1 and begins with the signature `EFI PART`; it records the revision, header size, its own checksum, the locations of the primary and backup headers, the first and last usable LBA, a disk GUID, the start of the entry array, the number of entries (128 by default), the size of each entry (128 bytes) and a checksum of the array. The **backup header and array** occupy the end of the disk, so damage at either end can be detected by comparing checksums and repaired from the other copy. Each **entry** holds a partition type GUID, a unique partition GUID, first and last LBA, attribute flags and a name of up to 36 UTF-16 characters. [src: rhel-10-docs ed2faf33540fe9a7]

Because type is a GUID rather than a byte, the registry stopped colliding: the Linux filesystem type is `0FC63DAF-8483-4772-8E79-3D69D8477DE4`, the EFI system partition is `C12A7328-F81F-11D2-BA4B-00A0C93EC93B`, a BIOS boot partition (for GRUB on a BIOS machine reading a GPT disk) is `21686148-6449-6E6F-744E-656564454649`, Linux swap is `0657FD6D-A4AB-43C4-84E5-0933C84B4F4F`, Linux LVM is `E6D6D379-F507-44C2-A23C-238F2A3DF928` and Linux RAID is `A19D880F-05FC-4D3B-A006-DF7D2B7F9B38`. The addressable size grew to 8 ZiB with 512-byte sectors and 64 ZiB with 4096-byte sectors. [src: rhel-10-docs ed2faf33540fe9a7]

The tools followed the formats. The venerable `fdisk` handled only MBR and was interactive; `cfdisk` added a menu; `parted` handled both and applied each command at once, which made it powerful and dangerous. `gdisk` and its scriptable sibling `sgdisk` grew up around GPT. Modern `fdisk` from util-linux now understands DOS, GPT, Sun, SGI and BSD labels, and its companion `sfdisk` reads a script describing the whole table, which suits automation. The failures along the way are part of the story. Writing a table to a disk in use used to mean a reboot, until the kernel gained the ability to re-read it (`BLKRRPART`, then the finer-grained `BLKPG` calls that `partx` uses). Partition alignment mistakes cost performance on RAID and 4K-sector drives until tools adopted a 1 MiB default. Hybrid MBR schemes that tried to keep two views of one disk consistent were a frequent source of corruption. The partial successes are clear: GPT solved size, resilience and identity, but the BIOS-versus-UEFI boot split means that the first partition on a disk still depends on how the machine boots. [src: man-pages f20ad56c3908f63c]

## Current state

A partitioned disk on a current Linux system presents its structure in four layers, and it helps to name them separately.

**On disk.** One label (protective MBR plus GPT, or a plain DOS MBR) and zero or more partitions. For GPT, a partition has an index in the array, a type GUID, a unique GUID (`PARTUUID` in the udev database), a name (`PARTLABEL`) and attribute bits. Bit 0 marks a partition the platform requires, bit 2 marks one that legacy BIOS can boot, and bits 48 to 63 are for the operating system's own use. For MBR, an entry has the active flag, a type byte and the start and length; the disk has a 32-bit disk identifier, and `PARTUUID` is formed from it and the partition number.

**In the kernel.** The block layer exposes the disk and each partition as a block device. `/proc/partitions` lists them with sizes in 1 KiB blocks, `/sys/block/<disk>/<disk><n>/` carries `start`, `size` and `partition` attributes, and udev creates stable symbolic links under `/dev/disk/by-id`, `by-path`, `by-uuid` (file system UUID), `by-partuuid` and `by-partlabel`. Numbering of device nodes is positional: `sda1` and `sda2` are by index, `nvme0n1p1` and `mmcblk0p1` add a `p` when the disk name ends in a digit. [src: rocky-docs 6b48df6038d460d9]

**In tools.** Listing and identification: `lsblk -f`, `lsblk -o NAME,SIZE,TYPE,PTTYPE,PARTUUID,PARTLABEL,MOUNTPOINTS`, `blkid`, `fdisk -l`, `sfdisk -l`, `sfdisk -F` (free areas) and `parted /dev/sdb print free`. Editing: `fdisk` (interactive; `g` creates a GPT, `o` a DOS label, `n` a partition, `t` sets the type, `d` deletes, `p` prints, `w` writes, `q` quits without writing), `sfdisk` (script in, table out), `gdisk` and `sgdisk` (GPT-first), and `parted` (immediate writes; `mklabel gpt`, `mkpart`, `resizepart`, `rm`, `align-check optimal 1`). Informing the kernel: `partprobe /dev/sdb` or `partx -u /dev/sdb` after the label is written to a disk in use, `blockdev --rereadpt`, and `udevadm settle` to wait for the device nodes. Wiping: `wipefs -a` removes signatures; `sgdisk --zap-all` destroys both GPT and MBR structures.

**In automation.** `sfdisk` is the tool that scripts best. Its input is a header and one line per partition:

```
label: gpt
unit: sectors

start=2048, size=2GiB, type=U, name="esp"
size=8GiB, type=L, name="root"
type=L, name="data"
```

The first lines set `label` (and optionally `label-id`, `first-lba`, `last-lba`); each partition line may give `start`, `size`, `type` (a GUID, a hex byte, or an alias such as `L` for Linux, `S` for swap, `U` for an EFI system partition, `V` for LVM, `R` for RAID), `uuid`, `name` and `attrs`. An omitted `start` means the next free sector aligned to 1 MiB, and an omitted `size` means the rest of the disk. `sfdisk -d /dev/sdb > layout.sfdisk` dumps an existing table in the same form, and `sfdisk /dev/sdc < layout.sfdisk` replays it, so a layout is a file that can be reviewed, versioned and applied to a new disk. Useful switches are `-n` (do everything except write), `-a` (append), `-N n` (change one entry), `--delete`, `-V` (verify), `-J` (JSON), `--part-type`, `--part-label`, `--part-uuid`, `-w auto|always|never` (signature wiping) and `--no-reread` (skip the in-use check, with care). Because `sfdisk` makes a backup of the overwritten sectors if asked with `-b` (writing `~/sfdisk-<dev>-<offset>.bak`), a hasty mistake can be undone. [src: man-pages 2f842b3c02b44e69] [src: man-pages 16963e713dc5d7a9]

**Alignment and sector size.** Start every partition on a 1 MiB boundary (sector 2048 on 512-byte sectors). That value is a multiple of 4096, of typical RAID stripe sizes and of most flash erase blocks. `parted /dev/sdb align-check optimal 1` and `cat /sys/block/sdb/queue/{logical_block_size,physical_block_size,optimal_io_size}` tell you what the device reports. A disk that is 4096 physical and 512 logical ("512e") works with 1 MiB alignment; a native 4096-byte ("4Kn") disk changes every sector-based number in the table, which is why `sfdisk -d` records `sector-size`.

**Boot dependencies.** On a UEFI machine the first partition is normally an EFI system partition (FAT, type `C12A7328-…`, mounted at `/boot/efi` or `/efi`) that holds the boot loader. On a BIOS machine with GPT, GRUB needs a 1 MiB **BIOS boot** partition for its second stage because there is no gap after sector 0 to embed it. On a BIOS machine with MBR, GRUB embeds itself in the gap before the first partition, which is one reason to start at 2048 and not 63. A disk that must boot on both kinds of firmware carries both partitions. [src: rhel-10-docs 7daac40e988bdae4]

## Assessment: the good, the bad and the ugly

**The good.** GPT is self-describing, redundant and checksummed. It removes the four-primary limit and the extended-partition chain, gives each partition a unique identity that survives device renumbering, and handles disks well past anything on sale. Partition names and UUIDs make `/etc/fstab` and boot arguments independent of probe order. A text dump of the table makes layouts reproducible, and a binary backup (`sgdisk -b`, `sfdisk -b`) is an inexpensive insurance policy.

**The bad.** The table is not a transaction. Writing it while the disk is mounted, then resizing a file system without matching the partition (or the reverse), is the classic way to destroy data. Tools disagree: `parted` writes immediately and cannot be abandoned with `q`, while `fdisk` buffers until `w`. Moving or growing a partition that is not last on the disk is manual work, and shrinking one is only safe if the file system has been shrunk first. Kernel re-reads fail with "device busy" when any partition is in use, so a layout change on a system disk usually means a reboot, or building the change on a different disk. Identical clones carry identical disk GUIDs and partition GUIDs, and two disks with the same GUID attached to one host produce confusing `/dev/disk/by-partuuid` links; `sfdisk --disk-id` or `sgdisk -G` regenerates them.

**The ugly.** Hybrid MBRs, which expose some GPT partitions through MBR entries so that old operating systems can see them, create two truths about one disk. Any tool that edits one without the other leaves the disk inconsistent. Dual-boot machines and firmware that insists on legacy entries still produce these. A second ugly area is silent damage: a disk whose primary GPT is overwritten (by a stray `dd`, an installer or an old tool that thinks the disk is empty) may still boot from firmware that reads the backup. The administrator then sees a mismatch only when a tool warns that the backup table is not at the end of the device, typically after the disk was cloned to a larger one. `sgdisk -e` or `parted` can move the backup structures to the new end. A third is naming: scripts that hard-code `/dev/sdb1` break when probe order changes, and a mistyped device name in a partitioning command is unforgiving. Always check `lsblk` and the serial number (`lsblk -o NAME,SERIAL,SIZE,MODEL`) before writing.

## Applications beyond this domain

The same pattern, a small checksummed table at a fixed location that names regions of a larger medium, appears wherever a store is shared. Flash devices in embedded systems carry partition maps (in a table in the boot loader, in the device tree, or in the on-flash MTD partition list) that tell the kernel where the boot loader, kernel, root file system and data live; board bring-up documentation describes preparing SD cards with exactly the tools used here. Virtual machine images are disks, so the same GPT and MBR structures live inside qcow2 and raw files, and tools such as `guestfish`, `virt-filesystems` and `kpartx` read them without booting the guest; KubeVirt documents the libguestfs route for exactly this. Cloud images grow their root partition at first boot with a script such as `cloud-init`'s growpart, which is just an automated `sfdisk -N` followed by a re-read. Containers and Kubernetes nodes use the same partition-table logic for node disks, while the container layers themselves live above in file systems. [src: kubevirt-user-guide a7e7278e900479c3] [src: bootlin-training f77df77b3ffd131a]

In data management the idea reappears as logical volumes, volume groups and RAID superblocks, and in databases as tablespaces. Understanding the partition table as a named, typed and checksummed map of regions prepares the ground for those later layers. [src: archwiki e3431bb5bb0f85c5]

## Examples

**Inspect a disk without changing it.**

```bash
lsblk -o NAME,SIZE,TYPE,PTTYPE,PARTTYPE,PARTUUID,PARTLABEL /dev/sdb
sfdisk -d /dev/sdb          # script form
sfdisk -F /dev/sdb          # free areas
```

**Build a GPT layout on an image file (safe to rehearse).**

```bash
truncate -s 8G disk.img
sfdisk disk.img <<'EOF'
label: gpt
start=1MiB, size=512MiB, type=U, name="esp"
size=2GiB, type=S, name="swap"
type=L, name="root"
EOF
sfdisk -V disk.img
```

**Add a partition to the end of a disk without touching existing ones.**

```bash
echo 'type=L, name="data"' | sfdisk -a /dev/sdb
partx -u /dev/sdb && udevadm settle
```

**Grow the last partition (disk was enlarged in the hypervisor).**

```bash
sgdisk -e /dev/sdb                  # move the backup header to the new end
sfdisk -N 3 --no-reread /dev/sdb <<< ',+'     # extend entry 3 to the end
partx -u /dev/sdb                   # tell the kernel
```

Then grow the file system or physical volume that lives inside.

**Back up and restore the table.**

```bash
sfdisk -d /dev/sdb > sdb.table
sgdisk -b sdb.gpt.bin /dev/sdb      # binary backup
sgdisk -l sdb.gpt.bin /dev/sdc      # load onto another disk
```

**Convert an MBR disk to GPT without touching the data.** `sgdisk -g /dev/sdb` (or `gdisk` with `w` in its conversion path) rewrites the structures in place when there is room for the 16 KiB array after the protective area; check `sfdisk -F` first, and take a binary backup. If the disk boots in BIOS mode, add a BIOS boot partition in the gap and reinstall the boot loader.

## Related problems and ideas

Partitioning is the lowest layer of a chain that continues upwards: file systems (next topic) decide how a partition's blocks hold files, LVM pools several partitions or disks into flexible volumes, software RAID combines partitions for redundancy, and LUKS encrypts a partition or volume. Each layer has its own metadata and its own risk of "growing at the wrong layer". The order of growth is always from the bottom up (device, partition, volume, file system), and the order of shrinking is the reverse.

Related ideas include **whole-disk use** (a file system or physical volume directly on `/dev/sdb`, with no table, which simplifies growth in virtual machines but makes the disk look empty to tools that probe only for tables and can be overwritten by an installer); **loop devices** and image files for rehearsing layouts (`losetup -fP --show disk.img` exposes the partitions as `loopXpN`); **device-mapper** mappings that carve a device without any on-disk table (`dmsetup`, `kpartx`); and **namespaces and zones** on NVMe, where one controller can present several namespaces that each carry their own table. Another is **zoned block devices**, where sequential-write zones constrain how partitions and file systems may be laid out.

Security-relevant ideas include secure erase and signature wiping (a deleted partition table leaves the data intact, so `wipefs` and `blkdiscard` are not data destruction), and firmware-level protections such as secure boot that interact with which partitions firmware will load code from.

## Active research

Open work around this layer is mostly about changing what a "disk" is. Zoned storage (SMR hard drives and ZNS solid-state drives) challenges the assumption that any block can be rewritten in place; kernel developers are extending the partitioning and file-system code paths to respect zone boundaries. Computational and key-per-IO storage ideas move parts of the translation layer from the drive into the host. In the boot area, discoverable partition specifications standardise partition type GUIDs for root, `/usr`, `/home`, verity data and signatures, so a system can assemble itself from a table without an `fstab`; this is the direction of systemd's `systemd-gpt-auto-generator` and `systemd-repart`, which declaratively grows and creates partitions at boot from definition files. Image-based systems (bootc, ostree, UKI-based designs) build on that idea. There is also continuing work on making partition changes safe online: `sfdisk --move-data` is an experimental attempt to move data together with the partition boundary. [src: archwiki 5d228ddf5b0d5062]

## Future direction

The trend is from imperative editing toward declarative layouts. A definition file that says what partitions should exist, with sizes, types and flags, is applied at install, first boot or image build, and a tool computes the difference. That fits both virtual machines (where the disk is resized from outside) and immutable operating systems (where the layout is part of the image). GPT will continue as the common format because UEFI requires it, while MBR remains for legacy BIOS boots and small removable media. Larger sectors (4Kn) and larger disks make alignment and table-size assumptions in old scripts more visible. The long-term administrator skill is therefore less about a particular tool and more about three habits: identify the right device by serial number and size before writing; keep a dump of the table under version control; and always treat the layers above and below a partition as part of the same change.
