# Finer control over who may use a file system and how much of it: quotas, access control lists and extended attributes

## Define the problem

The classic Unix permission model gives each file one owner, one group and three classes of access: owner, group, others. That is wonderfully simple and breaks down quickly. A project directory needs read-write access for two teams and read-only for an auditor, but a file has a single group. A web server must read a user's files without being in that user's group. A backup program needs to preserve a file's labels, capabilities and checksums that do not fit in nine permission bits. And a shared file system must not let one user, one group or one project consume every block and every inode while the rest wait.

Three mechanisms answer these needs, and they are related by implementation more than by purpose. **Quotas** limit consumption: bytes and inodes per user, group or project, with a soft limit that triggers a grace period and a hard limit that is enforced. **Access control lists** (ACLs) extend permissions to name additional users and groups on a single file, and give directories a template for new files. **Extended attributes** (xattrs) attach arbitrary name-value pairs to inodes; ACLs, SELinux labels and file capabilities are all stored as xattrs, so the third mechanism is the substrate for the second. The practical task is to enable, set, inspect and preserve them, and to know where they stop working: on file systems that do not support them, in archives and copies that drop them, and across network protocols that translate them badly. [src: man-pages d53e6703e491a95b]

## History and approaches

Quota support came to Unix in the 1980s with BSD, to stop students filling the shared disk; Linux first used a user-space `quotacheck` and the VFS quota interface with a single format, then added journaled quota formats as file systems grew past what the original 16-bit UID format could hold. The format names that still appear in tool options track that history: an original format, a second with 32-bit identifiers and 64-bit space, a third with 64-bit limits, plus remote and XFS variants. The XFS file system took a different road and implements quotas inside the file system itself, with its own tool, `xfs_quota`, and with a third dimension, **project quotas**, that limit a directory tree whatever the owner of its files. Ext4 later gained **native** quota support, in which the quota files are hidden system inodes managed by the file system (set at creation or with `tune2fs`), which avoids the old separate quota files and the race between mount and `quotacheck`. [src: man-pages f203af2e85af5e10]

Access control lists came through the POSIX 1003.1e draft, which was withdrawn but widely implemented. Linux adopted its model for ext2 and later all major local file systems: a **minimum ACL** is the traditional mode bits; an **extended ACL** adds named-user entries, named-group entries and a **mask** that caps the effective rights of everything except the owner and others. Directories can carry a **default ACL**, which new children inherit. The alternative that never became native on Linux is the NFSv4 ACL model, with allow and deny entries and many fine rights, found on Windows, NFSv4 servers and some other systems; tools exist to set it on NFS mounts, and Samba presents NTFS-like ACLs over the POSIX ones. [src: man-pages 163e8b1b0cb80d4b]

Extended attributes originated in IRIX and were added to Linux for ACLs. The kernel groups attributes into four namespaces: `user`, `trusted`, `security` and `system`. The partial success is that xattrs let new features (SELinux labels, file capabilities, integrity measurements, `ima` and `evm` hashes, container image layer metadata, application tags) share one mechanism without changing the inode layout. The failure mode is uneven support: tools that copy files drop them unless told otherwise, some file systems limit their size sharply, and network file systems may not carry all namespaces. [src: man-pages 0903f2b6f607a99b]

## Current state

### Quotas

A quota system tracks usage per **identity** (a UID, a GID or an XFS project ID) per file system, and enforces two limits for each of blocks and inodes. The **soft limit** may be exceeded for a grace period (7 days by default for the traditional tools); the **hard limit** is never exceeded. When a user passes the soft limit and the grace period expires, the soft limit becomes a hard limit until usage falls. Block limits are expressed in 1 KiB blocks by the classic tools.

**ext4, traditional tools.**

```bash
# /etc/fstab: add usrquota,grpquota (journaled: usrjquota=aquota.user,grpjquota=aquota.group,jqfmt=vfsv0)
mount -o remount /srv/data
quotacheck -cugm /srv/data          # create and scan the quota files (-c create, -u user, -g group, -m do not remount read-only)
quotaon -v /srv/data
edquota -u alice                    # opens an editor with soft/hard limits
setquota -u alice 800000 1000000 0 0 /srv/data      # block soft, block hard, inode soft, inode hard (blocks in KiB)
edquota -t                          # grace periods
quota -u alice                      # a user's view;  quota -s for human-readable
repquota -a                         # report for all quota-enabled file systems; -s human-readable
```

**ext4, native quota.** Create with `mkfs.ext4 -O quota -E quotatype=usrquota:grpquota` or convert with `tune2fs -O quota -Q usrquota,grpquota /dev/vg0/data`. The feature then shows in `dumpe2fs -h` as a `quota` feature with `User quota inode` and `Group quota inode` lines, and the mount options `usrquota` and `grpquota` activate enforcement; no `quotacheck` is needed. Project quotas on ext4 use `-O project` with `-Q prjquota`, directory flags set with `chattr +P -p <id>`, and the `prjquota` mount option. [src: man-pages ed14660a3d7aee62]

**XFS.** Quotas are chosen at **mount time** and cannot be turned on by remount: `uquota` (or `usrquota`), `gquota` (`grpquota`), `pquota` (`prjquota`) are the options, and the `noenforce` variants (`uqnoenforce` and similar) keep accounting without enforcing. Administration uses `xfs_quota` in expert mode:

```bash
xfs_quota -x -c 'limit bsoft=800m bhard=1g isoft=10000 ihard=12000 alice' /srv/data
xfs_quota -x -c 'report -h' /srv/data
xfs_quota -x -c 'quota -h alice' /srv/data
# project quota: a directory tree gets a project id, then a limit
echo '42:/srv/data/projects/web' >> /etc/projects
echo 'web:42' >> /etc/projid
# initialise the tree with its identifier
xfs_quota -x -c 'project -s -p /srv/data/projects/web 42' /srv/data
xfs_quota -x -c 'limit -p bhard=20g web' /srv/data
```

`xfs_quota` has user commands (`df`, `quota`, `help`, `quit`) and administrative commands available only with `-x` (`limit`, `report`, `timer`, `state`, `enable`, `disable`, `off`, `remove`, `project`). `/etc/projects` maps numeric project IDs to directory trees and `/etc/projid` names them. [src: man-pages ddc8d9f4c142af7b] [src: man-pages 1dcb6c8771be4588]

**Btrfs** has **qgroups** instead: `btrfs quota enable /mnt`, `btrfs qgroup limit 10G /mnt/subvol`, `btrfs qgroup show -reF /mnt`. They limit a subvolume, not a user, and carry known performance costs when many snapshots exist.

**How enforcement looks to users.** A write that would pass a hard limit fails with `EDQUOT` ("Disk quota exceeded"). A user over a soft limit sees a warning from `quota` and, if the system is configured, from a warning service (`warnquota`). Quota accounting counts blocks allocated to files **owned** by the identity, which includes extended-attribute space and, on some file systems, ACL blocks; hard links count once. The kernel interface is `quotactl(2)`, which `quota` tools use and which monitoring can call directly. [src: man-pages dd49e04fba2dc2a9]

### POSIX ACLs

```bash
getfacl report.txt                    # print the ACL
setfacl -m u:alice:rw,g:auditors:r report.txt        # add or change entries
setfacl -x u:alice report.txt                          # remove one entry
setfacl -b report.txt                                  # remove all extended entries
setfacl -R -m g:dev:rwX /srv/project                   # recursive; X sets execute only on dirs or already-executable files
setfacl -d -m g:dev:rwx /srv/project                   # default ACL: inherited by new children
setfacl -k /srv/project                                # remove the default ACL
getfacl -R /srv/project > acl.backup                   # backup
setfacl --restore=acl.backup                           # restore
```

Entry forms in the text syntax are `user::rw-` (owner), `user:name:rwx`, `group::r-x` (owning group), `group:name:r--`, `mask::rwx` and `other::---`, and default entries prefixed with `default:`. The **mask** limits the effective permission of named users, named groups and the owning group; when a named entry would grant more than the mask allows, `getfacl` prints an `#effective:` comment next to it. By default `setfacl` recalculates the mask as the union of those entries, unless a mask is given explicitly (`-n` suppresses recalculation, `--mask` forces it). `chmod g=...` on a file with an ACL changes the **mask**, not the group entry, which surprises people: a "restricted" group permission can silently cut a named user's rights, and the reverse. In a directory with a default ACL the process `umask` is not applied to new files; the default ACL decides. `ls -l` marks a file with an ACL by a `+` after the mode string. [src: man-pages 8d5f24ae8e95acc4] [src: man-pages ec9b6f2a4122d879]

ACL support depends on the file system: ext4, XFS and Btrfs have it built in (ext4's default mount options in `mke2fs.conf` include `acl` and `user_xattr`); NFS (v3) does not carry POSIX ACLs; NFSv4 maps a subset; Samba stores NTFS-style ACLs in an extended attribute through a VFS module or maps them to POSIX ACLs. Copy tools must be told to preserve them: `cp -a` and `cp --preserve=all`, `tar --acls` (and `--xattrs`), `rsync -aA`, `rsync -aX`. Security audit tools can check ACLs against a baseline, as in the AIDE configuration shipped with compliance content. [src: man-pages 37184978229b9da6] [src: compliance-as-code 1db79c113a959376]

### Extended attributes

```bash
setfattr -n user.project -v apollo report.txt
getfattr -d report.txt                  # dump user.* attributes
getfattr -d -m - report.txt             # dump all namespaces you may read (-m - matches every name)
getfattr -n user.project --only-values report.txt
setfattr -x user.project report.txt     # remove
getfattr -R -d -m - /srv/project > xattrs.dump;  setfattr --restore=xattrs.dump
```

The four namespaces: **user** (arbitrary data; access follows the file's permission bits; only allowed on regular files and directories, not on symbolic links or devices); **trusted** (visible only to a process with `CAP_SYS_ADMIN`); **security** (used by security modules and file capabilities: `security.selinux`, `security.capability`); **system** (kernel objects, notably `system.posix_acl_access` and `system.posix_acl_default`). The tools `setcap` and `getcap` manage `security.capability`; `ls -Z` and `restorecon` handle `security.selinux`. Size limits differ: ext4 stores small values in the inode and larger ones in one extra block, typically 4 KiB in total per inode; XFS and Btrfs allow values up to 64 KiB. Attribute space may count against quotas. Distinguish **extended attributes** from the unrelated **file attributes** set with `chattr` and listed with `lsattr` (immutable `i`, append-only `a`, no-dump `d` and others), which are inode flags. [src: man-pages d53e6703e491a95b] [src: man-pages d0d18c4eeaa8eb2f]

### Keeping them through copies

Extended attributes and ACLs vanish in transfer unless requested. `rsync -aAX` copies ACLs and xattrs; `tar --xattrs --acls --selinux` stores them (and the extraction side needs the same options and root privilege for the `security` and `trusted` namespaces); `cp -a` preserves them within one host; `mv` within a file system preserves everything and across file systems behaves as copy-and-delete. Backup tools differ and must be tested. [src: man-pages bfc51d41fe1cc7b0]

## Assessment: the good, the bad and the ugly

**The good.** These three tools remove the need for awkward workarounds. A project directory can give one group write access and another read access without inventing a combined group. Quotas keep a shared home or mail volume from being eaten by one user, and XFS project quotas allow per-application limits independent of ownership, which suits container storage. Extended attributes let security modules and applications annotate files without new file-system formats. Native ext4 quotas and XFS quotas enabled at mount remove the old `quotacheck` dance.

**The bad.** Complexity is hidden in the metadata. A file whose permissions look restrictive can be wide open through an ACL, and the `+` in `ls -l` is easy to miss. The mask makes `chmod` and `setfacl` interact in surprising ways, and recursive ACL changes on large trees are slow and easy to get wrong (the capital `X` and the default-versus-access distinction both trip people). Quota tooling is split across ext4, XFS and Btrfs with different commands and units, and a hard limit makes failures appear as unrelated application errors ("cannot write temporary file") rather than as a clear policy. Soft limits and grace periods are rarely monitored. Block quota counts allocated blocks, so sparse files and snapshots complicate predictions.

**The ugly.** Silent loss. A backup or copy that drops ACLs and xattrs restores a system whose labels, capabilities and permissions differ from the original, which can look fine until an SELinux denial or a missing file capability breaks a service. Mixed environments, with NFS or SMB sharing the same files as POSIX users, generate permission puzzles that no tool shows in one place. Quotas that are not enforced because the mount option was lost (on XFS, a remount does not enable them) give a false sense of safety, and stale `aquota` files give wrong numbers. Project IDs in `/etc/projects` that are out of sync with the directory flags quietly attribute usage to the wrong project. [src: disa-stig d3096b6bb9bae3aa]

## Applications beyond this domain

The same three ideas appear across systems. Cloud and container platforms apply storage quotas (Kubernetes ephemeral-storage limits, per-volume limits in managed services, XFS project quotas under container runtimes) so that one tenant cannot fill the node. Network file services map ACLs between models: Samba and its VFS modules translate between NTFS, NFSv4 and POSIX forms, and the extended attribute carrying the Windows descriptor is a good example of an xattr as an interoperability layer. Security frameworks depend on xattrs: SELinux labels, file capabilities and integrity measurement all live in `security.*` attributes, and file-integrity tools verify them. Object stores and application tagging mirror the same name-value pattern with different names (object tags, labels). [src: samba-docs 58229d1e0ba89a4d] [src: samba-docs 50e017520a0e305f]

Directory services bring the pattern into identity: access control entries in Active Directory carry allow and deny rights, and monitoring guidance for domain controllers shows how permission changes are watched there as a sign of compromise, the same reasoning that leads to auditing ACL and xattr changes on Linux servers. [src: ms-learn-adds 8fd9d65031785568]

## Examples

**Give the `dev` group working access to a shared tree, with inheritance, without changing the owner.**

```bash
mkdir -p /srv/project && chgrp dev /srv/project && chmod 2770 /srv/project
setfacl -m g:auditors:rX /srv/project
setfacl -d -m g:auditors:rX,g:dev:rwX /srv/project
getfacl /srv/project
```

**See the mask at work.**

```bash
touch f && setfacl -m u:alice:rw f && chmod g-w f && getfacl f   # alice's entry shows #effective:r--
setfacl -m m::rw f                                                  # restore the mask
```

**Limit one user to 1 GiB on ext4 with native quotas and verify.**

```bash
tune2fs -O quota -Q usrquota /dev/vg0/data
# fstab: /dev/vg0/data /srv/data ext4 defaults,usrquota 0 2
mount -a
setquota -u alice 900000 1000000 0 0 /srv/data
repquota -s /srv/data
```

**Cap an application directory at 20 GiB with an XFS project quota.** Mount with `prjquota`, create the `/etc/projects` and `/etc/projid` entries, run `xfs_quota -x -c 'project -s web' /srv/data`, then `xfs_quota -x -c 'limit -p bhard=20g web' /srv/data` and `xfs_quota -x -c 'report -p -h' /srv/data`.

**Tag and find files with xattrs.**

```bash
setfattr -n user.classification -v internal contract.pdf
getfattr -R -n user.classification --absolute-names /srv/docs 2>/dev/null | grep -B1 internal
```

**Copy a tree and keep everything.** `rsync -aAXH --numeric-ids /srv/project/ backup:/srv/project/` and, for a tarball, `tar --xattrs --acls --selinux -cf project.tar -C /srv project`.

## Related problems and ideas

Access control belongs to a larger set of layers: ownership and mode bits, ACLs, SELinux or AppArmor policy, capabilities, and container namespaces. The question "who can read this file?" has to be answered across all of them, and tools such as `namei -l`, `getfacl`, `ls -Z` and `capsh` each show one slice. Quotas connect to capacity planning, to alerting (`warnquota`, monitoring `repquota` output), and to snapshots, which can hold on to blocks that users believe they freed. Project quotas appear in container storage drivers that cap writable layers. Another neighbour is **immutable and append-only flags** (`chattr +i`, `+a`), which block even root until cleared, and **file integrity monitoring**, which compares the whole metadata set (mode, owner, ACL, xattrs, hashes) against a recorded state.

Interoperability is the other cluster. NFSv4 ACLs, Samba's `acl_xattr` module and POSIX ACLs only partially map onto each other, and a decision about where the authority for permissions lives (on the server file system, or in the sharing protocol) has to be made explicitly. [src: samba-docs 37184978229b9da6]

## Active research

Development continues around larger and safer quota accounting: project quotas on more file systems, faster Btrfs qgroup accounting (simple quotas) to avoid the cost of tracking shared extents, and quota support for namespaces and for user-mapped mounts, so that containers that map IDs see consistent limits. ID-mapped mounts also change how ownership and ACLs appear inside a container without rewriting files. In the metadata area, work on **fs-verity** and integrity measurement (IMA/EVM) builds on xattrs to tie file contents to signatures, and **richacl** efforts attempted to add a richer ACL model to Linux but have not been merged. Another active area is making user-space tools metadata-complete: archives and image formats that carry xattrs, ACLs and capabilities reliably, so that container images and backups restore exactly.

## Future direction

The trend is toward policy that is expressed once and enforced everywhere: labels and capabilities in xattrs checked by security modules; storage limits expressed per tenant or project and enforced by the file system or the platform, not by hand-edited quota files; and ACLs used sparingly where mode bits are not enough. Immutable operating systems and container images push toward fewer ad hoc permission edits and more declarative ownership. Administrators should expect quotas to be tied to project identifiers, ACLs to be tested by automation, and backup validation to include a metadata comparison, not just file contents. The habits that will remain: check `getfacl` instead of trusting `ls -l`; remember the mask; mount quota options explicitly and confirm with `repquota` or `xfs_quota report`; and prove that a backup restores ACLs and attributes by diffing `getfacl -R` and `getfattr -R` output. [src: man-pages 0903f2b6f607a99b]
