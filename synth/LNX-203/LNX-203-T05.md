# Python for operations: when the script outgrows the shell

## Define the problem

A shell script is the right tool until the work needs real data structures, error handling, parsing, concurrency or tests. The signs are familiar: associative arrays nested in strings, `awk` programs of twenty lines, `set -e` surprises, a retry loop with three levels of quoting, JSON built by string concatenation. Python is the usual next step for Linux administrators. It is installed on nearly every distribution (the package manager, the installer, firewalld, cloud-init and Ansible are all written in it), has a standard library covering files, processes, networking, JSON, logging and argument parsing, and reads like pseudocode. The problem is to use it well for operational work: scripts that other administrators can run on a different machine and trust, with predictable dependencies, correct handling of processes and files, useful error messages and exit codes, and logs that explain what happened.

This slice teaches the structure of an operational Python script, the standard-library modules that replace most shell pipelines (`subprocess`, `pathlib`, `argparse`, `logging`, `json`, `shutil`, `tempfile`), how to manage dependencies without breaking the system Python, and how to test the result. It builds on the previous slices: the care that quoting needs in shell becomes argument lists in Python, strict mode becomes exceptions, and bats tests become pytest.

## History and approaches

Python appeared in 1991 and became a staple of Unix administration in the early 2000s, taking over from Perl for new tools because of its readability. Distribution infrastructure moved to it: Red Hat's installer and `yum` (and later `dnf`) are Python, as are many Debian tools, Ubuntu's `cloud-init` and `netplan` front ends, and configuration-management systems such as Ansible and Salt. The migration from Python 2 to Python 3 was long and painful for the ecosystem; Python 2 reached end of life in January 2020, and all current distributions ship Python 3 as `python3`, with no unversioned `python` guaranteed. Red Hat distributions historically separated the interpreter used by system tools from the one offered to users, so that changing one would not break the other; Debian and Ubuntu take another route and mark the system interpreter as externally managed, which affects how packages are installed (see below).

Approaches to operations in Python fall on a range. At the small end is the one-off script run by hand. In the middle are command-line tools built on `argparse` or a library such as `click` or `typer`, with logging, configuration files and tests, installed with `pipx` or as a distribution package. At the large end are libraries and agents (Ansible modules, monitoring checks, custom exporters) that run unattended. Alternatives to Python in the same space include Go (static binaries, easy distribution, more code), shell (shorter for glue, weaker for logic), and Ansible itself when the task is a statement of how a host should end up, where a declarative playbook beats an imperative script. The practical rule from the previous slice stands: use shell for glue, Python for logic, and Ansible or another convergent tool for state.

## Current state

### The interpreter and its environment

Check what you have: `python3 --version` and `which python3`. Typical versions differ by distribution (Ubuntu and Debian ship recent releases, RHEL-family systems ship the version of their release and offer newer ones as separate packages), so a script that needs a language feature, such as the `tomllib` module (3.11 and later), says so and checks it. The shebang `#!/usr/bin/env python3` finds the interpreter in `PATH`, which makes scripts work in a virtual environment; scripts run by systemd or cron use an explicit path to the interpreter they were tested with.

Dependencies are the common source of trouble. Installing packages with `pip` into the system interpreter can overwrite files that the distribution's package manager owns, so current Debian-family and Fedora-family distributions mark the system Python as **externally managed** (PEP 668) and refuse such installs unless forced. The remedy is a virtual environment, created with the standard `venv` module: `python3 -m venv .venv`, then `.venv/bin/pip install -r requirements.txt` and `.venv/bin/python script.py` (activation is a convenience, not a requirement). Command-line tools meant for general use are installed in their own environment with `pipx install tool`. The module documentation describes what a virtual environment contains and how it relates to the base interpreter [src: python-docs 8e16ac5204b577ce]. Pin versions in `requirements.txt` or a lock file, or better, prefer the standard library and distribution packages (`python3-requests`, `python3-yaml`) for scripts that must run on managed servers without internet access.

### Structure of an operational script

A script that can be imported, tested and reused has a stable shape:

```python
#!/usr/bin/env python3
"""Rotate old logs."""
import argparse
import logging
import sys
from pathlib import Path

log = logging.getLogger("rotate")
LOG_FORMAT = "%(levelname)s %(message)s"

def rotate(directory: Path, keep: int) -> int:
    files = sorted(directory.glob("log.*"), key=lambda p: p.stat().st_mtime, reverse=True)
    removed = 0
    for old in files[keep:]:
        log.info("removing %s", old)
        old.unlink()
        removed += 1
    return removed

def parse_args(argv=None):
    p = argparse.ArgumentParser(description=__doc__)
    p.add_argument("directory", type=Path)
    p.add_argument("-k", "--keep", type=int, default=3)
    p.add_argument("-v", "--verbose", action="store_true")
    return p.parse_args(argv)

def main(argv=None) -> int:
    args = parse_args(argv)
    logging.basicConfig(level=logging.DEBUG if args.verbose else logging.INFO,
                        format=LOG_FORMAT, stream=sys.stderr)
    if not args.directory.is_dir():
        log.error("not a directory: %s", args.directory)
        return 2
    log.info("removed %d files", rotate(args.directory, args.keep))
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

The pieces matter. `main()` returns an exit status and is called inside the `__name__` guard, so the module can be imported by tests without side effects. `argparse` generates usage and error messages and exits with status 2 on bad arguments; it handles options, positional arguments, types, defaults, mutually exclusive groups and sub-commands (`add_subparsers`) [src: python-docs 673142fbe0398833]. Logging goes to standard error so that standard output stays clean for data.

### Files and paths: `pathlib` and friends

`pathlib.Path` replaces string concatenation with operators and methods: `Path("/etc") / "hosts"`, `.exists()`, `.is_file()`, `.read_text()`, `.write_text()`, `.glob("*.conf")`, `.rglob()`, `.stat().st_mtime`, `.unlink()`, `.mkdir(parents=True, exist_ok=True)`, `.resolve()`, `.suffix`, `.stem`, `.parent`. It deals with names containing spaces without any quoting [src: python-docs 32ea082253563a4e]. `shutil` provides copying, moving, `rmtree`, `disk_usage` and `which`. `tempfile.TemporaryDirectory()` and `NamedTemporaryFile` create scratch space that is cleaned up by a `with` block, the counterpart of `trap ... EXIT`. For atomic replacement of a configuration file, write to a temporary file in the same directory, flush and `os.fsync`, then `os.replace(tmp, target)`, so readers never see a half-written file. `fcntl.flock` provides advisory locks equivalent to `flock(1)`.

### Running other programs: `subprocess`

`subprocess.run` is the interface for calling commands and the most important module for operations code:

```python
import subprocess
result = subprocess.run(["systemctl", "is-active", "sshd"],
                        capture_output=True, text=True, timeout=10, check=False)
if result.returncode != 0:
    log.warning("sshd is %s", result.stdout.strip() or result.stderr.strip())
```

The rules: pass the command as a **list**, so no shell parses it and spaces and metacharacters in arguments are harmless; avoid `shell=True` unless you need shell features, and when you do, build the string with `shlex.quote` for each untrusted piece [src: python-docs 90fba8171df3a774]; set `timeout=` so a hung command cannot hang the script; use `check=True` to raise `CalledProcessError` on a non-zero status (or inspect `returncode`); use `text=True` (or `encoding=`) to get strings and `capture_output=True` for `stdout` and `stderr`; pass an `env=` dictionary to control the environment and `cwd=` to set the directory. To feed input use `input=`; to build a pipeline connect `Popen` objects or, more simply, run the stages separately and process the text in Python. The module documentation lists these arguments and the exceptions, including `TimeoutExpired` and `FileNotFoundError` for a missing program [src: python-docs fd79f842195be41d]. Where a Python library exists for the job (reading `/proc` with `psutil`, talking to an API with `requests`, reading JSON from `ip -j`), prefer it to parsing command output, for the same reason as in the previous slice.

### Data: JSON, YAML, CSV, configuration

`json.loads` and `json.dumps(obj, indent=2, sort_keys=True)` handle JSON; the machine-readable output of `ip -j`, `lsblk -J` and cloud CLIs loads directly. `csv` handles quoted fields correctly (the case where `awk -F,` fails). `configparser` reads INI files, including systemd-style and `.repo` files with some care, and `tomllib` (3.11 and later, read-only) reads TOML. YAML needs the third-party `PyYAML` (`yaml.safe_load`, never plain `load` on untrusted input). `dataclasses` give light typed records, and `datetime` with time zones (`zoneinfo`) covers timestamps; store and compare in UTC.

### Logging and errors

The `logging` module separates what happened from where it goes. A module-level `log = logging.getLogger(__name__)`, calls such as `log.info("x=%s", x)` (lazy formatting), levels (`DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`) and handlers decide the output. For scripts run by systemd, log to standard error and let the journal collect it; for long-running programs, handlers such as `RotatingFileHandler`, `SysLogHandler` and `logging.handlers.WatchedFileHandler` exist, and configuration can be loaded with `logging.config` [src: python-docs 0e34c75ed338014d] [src: python-docs a8656825179ff541]. For errors, catch the specific exceptions you can handle (`FileNotFoundError`, `PermissionError`, `subprocess.CalledProcessError`, `json.JSONDecodeError`), log a clear message and return a non-zero status; never use a bare `except:` that also swallows `KeyboardInterrupt`. Let unexpected exceptions propagate with a traceback, or log them with `log.exception`. Define exit codes for the callers (0 success, 1 failure, 2 usage, other values documented), because shell scripts, cron and systemd all react to them.

### Concurrency and network calls

For many independent tasks (checking a hundred hosts), `concurrent.futures.ThreadPoolExecutor` runs I/O-bound work in threads with a bounded pool, and `ProcessPoolExecutor` handles CPU-bound work; `asyncio` suits large numbers of concurrent network connections but needs async libraries. Always set timeouts on network calls (`urllib.request.urlopen(url, timeout=5)`, `requests.get(url, timeout=5)`), because the default is to wait forever. Retry with a bounded number of attempts and exponential back-off, and make operations idempotent so a retry cannot do harm.

### Quality: tests, types, style

`pytest` with fixtures such as `tmp_path`, `monkeypatch` and `capsys` is the standard test tool and plays the role bats plays for shell: build a temporary tree, call `main([...])` with arguments, and assert on the return value and the files. Type hints with `mypy` or `pyright`, a formatter such as `black` or `ruff format`, and a linter such as `ruff` or `flake8` catch many faults early. Package a larger tool with a `pyproject.toml` and an entry point so `pipx install .` gives a command, and keep scripts for one-off use in a `scripts/` directory under version control with the others.

## Assessment: the good, the bad and the ugly

**The good.** Python removes the quoting and splitting hazards of shell by using lists and objects, gives exceptions for error handling, and offers a large, documented standard library. Scripts are readable by newcomers, testable with ordinary tools, and portable across distributions when they keep to the standard library. The same language serves for a ten-line helper and a service, and the ecosystem (Ansible, boto3, kubernetes clients, psutil) is deep for operations work.

**The bad.** Startup time and memory are higher than for shell or a compiled tool, which matters for commands run thousands of times. Version and dependency management are a real burden on servers: the system interpreter may be old or externally managed, virtual environments multiply, and a script that works on a laptop can fail on a server for lack of a module. Processes are more verbose than in shell: a three-stage pipeline becomes ten lines. And `subprocess` can still be misused (`shell=True` with untrusted data is injection).

**The ugly.** Scripts that started as helpers and grew into untested services with hard-coded paths, global state, bare `except:` blocks and a requirements file from three years ago. Packages installed with `sudo pip install` into the system interpreter that later break the distribution's tools. Secrets passed on the command line (visible in `ps`) or written into logs. Time handling with naive datetimes that break on daylight-saving changes. And silent failures: a script that catches every exception, logs nothing and exits zero.

## Applications beyond this domain

The same skills carry across infrastructure work. Ansible modules and plugins are Python and follow the same structure (argument spec, exit with a result). Cloud automation uses Python SDKs (boto3 and its siblings), and the same script patterns run in serverless functions and CI jobs. Kubernetes operators and admission controllers are often written in Python or Go with the same testing approach, and monitoring exporters, backup tools and log processors are Python programs run as services (the final slice covers running them under systemd). Data-oriented tasks (reports from logs, inventory reconciliation) reuse the same standard-library modules, with pandas where heavy analysis is needed.

## Examples

**1. Run a command safely and parse JSON.**

```python
import json, subprocess
out = subprocess.run(["ip", "-j", "addr"], capture_output=True, text=True, check=True, timeout=10).stdout
for link in json.loads(out):
    if link.get("operstate") == "UP":
        print(link["ifname"], [a["local"] for a in link.get("addr_info", []) if a["family"] == "inet"])
```

**2. Find the largest files in a tree.**

```python
from pathlib import Path
files = [p for p in Path("/var/log").rglob("*") if p.is_file()]
for p in sorted(files, key=lambda p: p.stat().st_size, reverse=True)[:5]:
    print(f"{p.stat().st_size:>12,}  {p}")
```

**3. Atomic write of a config file.**

```python
import os, tempfile
from pathlib import Path
def write_atomic(target: Path, text: str) -> None:
    fd, tmp = tempfile.mkstemp(dir=target.parent, prefix=target.name + ".")
    try:
        with os.fdopen(fd, "w") as f:
            f.write(text); f.flush(); os.fsync(f.fileno())
        os.replace(tmp, target)
    except BaseException:
        os.unlink(tmp); raise
```

**4. Check many hosts in parallel with timeouts.**

```python
import socket
from concurrent.futures import ThreadPoolExecutor
def up(host):
    try:
        with socket.create_connection((host, 22), timeout=3): return host, True
    except OSError: return host, False
with ThreadPoolExecutor(max_workers=16) as pool:
    for host, ok in pool.map(up, ["web1", "web2", "db1"]):
        print(host, "up" if ok else "DOWN")
```

**5. A pytest test for the script above.**

```python
from rotate import main

def test_keeps_newest(tmp_path):
    import os, time
    for i in range(5):
        f = tmp_path / f"log.{i}"; f.write_text("x"); os.utime(f, (time.time() - i * 60,) * 2)
    assert main([str(tmp_path), "-k", "2"]) == 0
    assert len(list(tmp_path.glob("log.*"))) == 2
```

**6. Create an isolated environment for a script.**

```bash
python3 -m venv /opt/tools/.venv
/opt/tools/.venv/bin/pip install 'requests==2.*'
/opt/tools/.venv/bin/python /opt/tools/check_api.py --url https://example.org/health
```

## Related problems and ideas

- **Packaging and distribution.** `pyproject.toml`, entry points, wheels, `pipx`, distribution packages (RPM and deb) and containers; zipapps (`python -m zipapp`) for a single runnable file.
- **Secrets.** Read from files with restricted permissions, environment variables set by systemd (`LoadCredential=`), or a secrets service; never log them or put them on a command line.
- **Idempotence and state.** Compare desired and actual state, change only the difference, report what changed; this is what Ansible modules formalise.
- **Observability.** Structured (JSON) logs, metrics through a small exporter, and exit-status conventions for monitoring.
- **Python in other places.** Jupyter for investigations, `fabric` and `paramiko` for SSH, `psutil` for process and system information, `rich` and `click` for nicer interfaces.
- **Security of scripts.** Injection through `shell=True`, unsafe deserialisation (`pickle`, `yaml.load`), temporary-file races and over-broad privileges.

## Active research

The Python ecosystem keeps moving in areas that matter to operations: faster interpreters (the free-threaded build and the experimental just-in-time compiler in recent releases), much faster package installers and resolvers written in Rust, standardisation of lock files and of how scripts declare their own dependencies (inline script metadata that lets a tool create an environment on the fly), and better static typing. Supply-chain security is a major theme: signed releases, trusted publishing to the package index, software bills of materials and tooling that detects malicious packages. Distribution maintainers continue to refine how the system interpreter is separated from user environments, following the externally-managed model.

## Future direction

The probable course is that standalone scripts become self-describing (declaring the interpreter version and dependencies) and run in managed, isolated environments created by fast tools, while the standard library keeps covering the glue that administrators need. For the administrator the stable guidance is to keep scripts small and tested, rely on the standard library, treat dependencies as liabilities to be pinned and isolated, and move to a convergent tool when the job is describing state, not scripting steps. The course target is that a student can turn a shell script that has outgrown its form into a tested Python tool with argument parsing, logging, correct subprocess use and clean exit codes.
