# From a script to a managed job: systemd services and timers

## Define the problem

A script that works at the prompt is not yet an operational job. Once it must run every night, at boot, or whenever a condition holds, a handful of questions arise that the script itself cannot answer. Who starts it, as which user, with which environment and which resource limits? What happens if the previous run is still going? Where does its output go, and how does anyone find out it failed? How is it started by hand for testing, and how is it kept from damaging the system if it misbehaves? For decades the answer was cron plus conventions: a crontab line, a redirect to a log file, a lock file, an email from cron on error. The conventions worked, but each team reinvented them, and cron offers little beyond starting a command at a chosen minute.

systemd, which manages services on practically every current Linux distribution, provides these answers as part of the platform. A script becomes a **service unit** that describes how to run it (user, environment, limits, sandboxing, dependencies), and a **timer unit** that describes when. Output goes to the journal, failures are visible in `systemctl`, and the same unit can be started by a timer, by a person, by a socket or by another unit. This slice teaches how to turn a script into a unit, how to write and test a timer, how to use the sandboxing options to run it with least privilege, and how it compares with cron. It connects the shell and Python slices to the operating-system course on systemd.

## History and approaches

Periodic jobs on Unix began with cron in the 1970s, a daemon that reads tables of times and commands, with `at` for one-off jobs and `anacron` (for machines that are not always on) added later to run missed daily and weekly jobs. Init scripts, the shell programs in `/etc/init.d`, started services at boot; each one implemented its own start, stop, status and PID-file handling, and reliability depended on the care of the author. systemd, started around 2010 and adopted by the major distributions in the following years, replaced init scripts with declarative unit files, added dependency-based parallel startup, supervised processes through control groups, and later added timers, sockets, journald logging and sandboxing options. The adoption was contentious, but its unit model is now the common ground for administrators. The Rocky Linux administration guide introduces its architecture and unit types for newcomers [src: rocky-docs b09dc246f7a9689b], and the `daemon(7)` page contrasts the old-style daemon conventions with the new-style services that systemd expects [src: man-pages 13642beb4bd9d2ed].

There are several approaches to scheduling and running scripts. **cron** (and `anacron`) remains available and is fine for simple jobs, especially on machines without systemd. **systemd timers** are the native alternative with better logging, dependency control and sandboxing. **Orchestrators** (Kubernetes CronJobs, CI schedulers, Ansible Tower or AWX schedules, Airflow) are the right tool when jobs span machines, need retries with history, or depend on one another. **Transient units** created with `systemd-run` are a quick way to run a command under a unit's controls without writing a file, useful for tests and for one-off limits.

## Current state

### The service unit for a script

A unit file is an INI-style text file. For a job that runs, finishes and exits, the type is `oneshot`:

```ini
# /etc/systemd/system/backup.service
[Unit]
Description=Nightly backup of /srv/data
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
User=backup
Group=backup
ExecStart=/usr/local/bin/backup.sh --target /srv/backups
Environment=LANG=C.UTF-8
EnvironmentFile=-/etc/backup/backup.env
Nice=10
IOSchedulingClass=idle
TimeoutStartSec=2h
StateDirectory=backup
```

The command lines section of the manual explains the rules that differ from the shell [src: man-pages 8b137399fba38266]. `ExecStart=` needs an **absolute path** to the program and does not use a shell: there is no globbing, no `|`, no `&&`, no `$VAR` expansion in the shell sense (systemd has its own `$VAR` and `%`-specifier substitution). If shell features are needed, call the shell explicitly with `ExecStart=/bin/bash -c '...'`, or, better, put the logic in the script and keep the unit simple. The environment is minimal: `PATH` is a short default and nothing from a login shell is present, so scripts that work interactively fail under systemd when they rely on `PATH`, locale or variables set in `.bashrc`. Set `Environment=` or `EnvironmentFile=` (a leading `-` means "ignore if missing") and use absolute paths inside the script, or set `PATH` at its top.

The relevant types and behaviours: `Type=oneshot` waits for the command to exit and treats a non-zero status as failure (the unit becomes `failed`); `Type=simple` (the default) is for long-running programs that stay in the foreground; `Type=forking` is for old-style daemons; `Type=notify` is for programs that signal readiness. For long-running scripts add `Restart=on-failure` and `RestartSec=`. `SuccessExitStatus=` lists extra exit codes that count as success, and `TimeoutStartSec=` (or `RuntimeMaxSec=`) stops a runaway job. Standard output and error go to the journal by default (`StandardOutput=journal`), tagged with the unit name, so there is no log file to rotate [src: man-pages 9367e1477a4af7c2].

### Running with least privilege

The unit file is also where the script is confined. The options cost nothing and shrink the damage of a bug or a compromise:

```ini
[Service]
User=backup
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
ReadWritePaths=/srv/backups
StateDirectory=backup
CapabilityBoundingSet=
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6
```

`ProtectSystem=strict` makes the whole file system read-only for the service except the paths listed in `ReadWritePaths=` (and the directories the manager creates for it), `ProtectHome` hides home directories, `PrivateTmp` gives the job its own `/tmp`, `NoNewPrivileges` blocks privilege escalation through setuid programs, and an empty `CapabilityBoundingSet=` removes all capabilities. `StateDirectory=`, `CacheDirectory=`, `LogsDirectory=` and `RuntimeDirectory=` create directories under `/var/lib`, `/var/cache`, `/var/log` and `/run` owned by the service user, replacing `mkdir`/`chown` lines. `DynamicUser=yes` allocates a transient user for the run. The command `systemd-analyze security backup.service` scores the unit's exposure and lists which options would reduce it; use it as a checklist, not a goal of a perfect score. The options are described in the service and exec manual pages, and a restrictive set usually needs a round of testing to find which paths the script really writes.

### The timer unit

A timer is a second unit whose job is to start the service of the same name:

```ini
# /etc/systemd/system/backup.timer
[Unit]
Description=Run the nightly backup

[Timer]
OnCalendar=*-*-* 02:30:00
RandomizedDelaySec=15min
Persistent=true

[Install]
WantedBy=timers.target
```

The timer manual lists the keys [src: man-pages 8d3a5e0f79f72288]. **Realtime** timers use `OnCalendar=` with calendar expressions (`daily`, `weekly`, `Mon..Fri 09:00`, `*-*-01 04:00:00` for the first of each month, `*:0/15` for every 15 minutes). **Monotonic** timers count from an event: `OnBootSec=`, `OnStartupSec=`, `OnUnitActiveSec=` (since the unit last ran), `OnUnitInactiveSec=`. `Persistent=true` makes a calendar timer run once at start if a run was missed while the machine was off, which is what `anacron` provided. `RandomizedDelaySec=` spreads load across a fleet so that a hundred hosts do not hit a server at the same second. `AccuracySec=` (default one minute) allows systemd to coalesce wake-ups to save power; set it to `1s` where exactness matters. `Unit=` names the service when it is not the same name.

Install and inspect:

```bash
sudo systemctl daemon-reload                # after creating or editing unit files
sudo systemctl enable --now backup.timer    # start now and at every boot
systemctl list-timers --all                 # next and last run of each timer
systemctl status backup.timer backup.service
journalctl -u backup.service --since today
sudo systemctl start backup.service         # run it now, by hand, as the timer would
systemd-analyze calendar 'Mon..Fri 09:00'   # check an expression and see the next elapse
systemd-analyze verify /etc/systemd/system/backup.service
```

Enable the **timer**, not the service. A timer does not start a service that is still active, so overlapping runs do not happen by default: if the backup takes longer than the interval, the next trigger is skipped while the unit is running (the unit state `activating` or `active`). That removes most uses of lock files, though a script that can also be launched by hand should still guard against a second copy. The Arch wiki on timers gives worked examples of realtime and monotonic timers, and of running as a user, with notes on the differences from cron [src: archwiki d47c03e4f8703762].

### Testing and one-off runs with `systemd-run`

`systemd-run` creates a transient unit without a file. `sudo systemd-run --unit=test-backup --property=ProtectSystem=strict --property=ReadWritePaths=/srv/backups /usr/local/bin/backup.sh` runs the script under the same restrictions as the real unit, and `systemd-run --on-calendar='*:0/5' --unit=probe /usr/local/bin/probe.sh` creates a transient timer (the Arch wiki shows both) [src: man-pages 5158474221213001] [src: archwiki 211ac86c2686518a]. `--pty` gives an interactive terminal inside the unit's environment, which reproduces faults that appear only under systemd and not in your own shell. `--collect` removes the unit after it ends and `--wait` returns the exit status.

### Failure handling and notification

A failed `oneshot` shows as `failed` in `systemctl --failed` and the journal contains its output. To be told, add `OnFailure=notify-failure@%n.service` to the service, where that template unit runs a small script that sends mail, posts to a chat webhook or writes a metric; `%n` is the failed unit's name. Monitoring systems can also alert on `systemctl is-failed` or on the age of a success marker. Use `Restart=on-failure` only for jobs that are safe to repeat, and bound it with `StartLimitIntervalSec=` and `StartLimitBurst=`. Log from the script to standard error, one line per event, and let the journal add timestamps and unit names; `logger -t name` and `systemd-cat` are available for scripts that do not own their output.

### Comparison with cron

| Aspect | cron | systemd timer |
|---|---|---|
| Definition | one line in a crontab | two unit files |
| Logging | mail or redirect | journal with unit metadata |
| Environment | minimal, set by hand | minimal, set in the unit |
| Missed runs | skipped (anacron separate) | `Persistent=true` |
| Overlap | possible unless locked | not started while active |
| Dependencies | none | `After=`, `Requires=` and so on |
| Sandboxing and limits | none | extensive |
| Randomised delay | manual `sleep` | `RandomizedDelaySec=` |
| Availability | everywhere | systemd hosts only |

Cron is quicker for a one-line personal job, and its five-field syntax is universal; timers pay off for anything that needs logs, limits or dependencies.

## Assessment: the good, the bad and the ugly

**The good.** One platform provides scheduling, supervision, logging, resource control and sandboxing, so a script becomes a manageable job with a few dozen lines of declarative text. Testing is direct (`systemctl start`, `systemd-run`), history is in the journal, missed runs can be caught up, and fleets can be staggered. `systemd-analyze` supplies verification and a security review.

**The bad.** Two files per scheduled job feels heavy for small tasks. The unit syntax has many options, and their interactions (for example sandbox directives and the paths a script writes) are learned by failure. The minimal environment surprises people used to a shell. Timer accuracy defaults favour power saving, so "02:30" can mean 02:30:59. Differences between systemd versions mean that an option on a new distribution may not exist on an older one, which unit files should be tested against.

**The ugly.** Units copied between hosts without understanding: `User=root` with no sandboxing and `ExecStart=/bin/sh -c '... | ... &'` that forks into the background and loses supervision. Jobs that always exit zero so failures are invisible. Timers that are created but not enabled, and so never fire after a reboot. Scripts that write into the read-only parts of the system only when a rare branch runs and fail months later. Mixing cron and timers for the same job, giving duplicate runs. And alert fatigue from `OnFailure` hooks that mail on every transient network blip.

## Applications beyond this domain

The unit model reaches beyond scheduled scripts. Containers can be run as services (Podman can generate units, and Red Hat's documentation shows how to update containers automatically through systemd [src: rhel-10-docs de73c052e3c207a3]), socket-activated services start on demand, and user-level units (`systemctl --user`) schedule jobs for a single account without root. Kubernetes CronJobs and CI schedulers apply the same ideas (a schedule, a command, a concurrency policy, logs) at cluster scale, and the controls in a unit (resource limits, read-only file systems, capability bounding) have counterparts in container security contexts. The security practice of least privilege that `systemd-analyze security` encourages is the same as in AppArmor, SELinux and container policies.

## Examples

**1. A minimal timer for a script, every day at 03:00.**

```ini
# /etc/systemd/system/cleanup.service
[Service]
ExecStart=/usr/local/bin/cleanup.sh
Type=oneshot
```

```ini
# /etc/systemd/system/cleanup.timer
[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true
[Install]
WantedBy=timers.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now cleanup.timer
systemctl list-timers cleanup.timer
```

**2. Test the exact environment once, interactively.**

```bash
sudo systemd-run --pty --wait --collect -p User=backup -p ProtectSystem=strict /bin/bash
```

**3. See when an expression will fire.**

```bash
systemd-analyze calendar --iterations=3 'Mon..Fri *-*-* 08:30:00'
```

**4. A long-running script as a supervised service.**

```ini
[Service]
ExecStart=/usr/local/bin/queue-worker.py
Restart=on-failure
RestartSec=5
StartLimitIntervalSec=60
StartLimitBurst=5
```

**5. Notify on failure.**

```ini
# in backup.service
[Unit]
OnFailure=notify-failure@%n.service
```

```ini
# /etc/systemd/system/notify-failure@.service
[Service]
ExecStart=/usr/local/bin/notify.sh "%i failed"
Type=oneshot
```

**6. Review a unit's exposure.**

```bash
systemd-analyze security backup.service | head -20
```

## Related problems and ideas

- **Logging.** The journal's fields, `journalctl -u`, retention and forwarding connect to the monitoring course; also `logger` from scripts.
- **Secrets for jobs.** `LoadCredential=` and `SetCredential=` deliver secrets as files visible only to the unit.
- **Dependencies and ordering.** `After=network-online.target` and `Requires=` determine when the job may run.
- **Users and permissions.** A dedicated service account with only the access the job needs.
- **Resource control.** `CPUQuota=`, `MemoryMax=`, `IOWeight=` keep batch jobs from starving production services.
- **Idempotence and retries.** Safe re-runs and bounded restarts, as in the earlier slices.

## Active research

The systemd project continues to extend sandboxing (new filtering and confinement options appear in each release), credentials handling, and integration with the boot process and containers. Work on reproducible, declarative system images (image-based and immutable systems) treats units as the unit of configuration, and tooling to generate least-privilege profiles from observed behaviour is being developed, which would reduce the trial-and-error in writing restrictive units. Alternative supervision tools (s6, runit) remain in use in minimal systems and containers.

## Future direction

Expect scheduled work on single hosts to settle on timers wherever systemd is present, with orchestrators handling cross-host work, and with unit-level sandboxing becoming a normal baseline checked in review (`systemd-analyze security` in CI). The practical guidance is stable: keep the script small and testable, keep the unit declarative, run as a dedicated user with the narrowest file-system access that works, enable the timer, test with `systemctl start` and `systemd-run`, and send failures somewhere a person will see them. The course target is a student who can turn a script from the earlier slices into a timer-driven, confined, observable job.
