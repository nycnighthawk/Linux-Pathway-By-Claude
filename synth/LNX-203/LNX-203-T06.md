# Keeping operational code under control: Git workflow, history and review

## Define the problem

Scripts, unit files, configuration templates and playbooks change the behaviour of production machines, so a change to them needs the same care as a change to application code, and often more, because the failure shows up on a server rather than in a test run. Three questions come up again and again. What exactly changed, when and why (so that an outage can be traced to a change and the change reversed)? How do several people work on the same files without overwriting each other? And who checked the change before it reached a machine? A directory of scripts edited in place on a server answers none of these. Version control answers the first two, and a review step on top of it answers the third.

Git is the version-control system used almost everywhere in this space. This slice covers what a sysadmin needs: the model of commits and branches, a day-to-day workflow (branch, commit, rebase or merge, push, open a pull request), how to write commit messages and keep history useful, how to review a change to operational code, how to recover from mistakes with `reflog`, `revert` and `bisect`, and how repository settings (protected branches, required checks, signed commits) turn the workflow into a control. It connects to the earlier slices: the checks a pull request must pass are ShellCheck and the bats suite.

## History and approaches

Source control began with tools that tracked files one at a time (SCCS, RCS) and then with centralised servers (CVS, Subversion), where a single repository held history and developers checked out a working copy. Linux kernel development used a proprietary distributed tool for some years; when its licence changed in 2005, Linus Torvalds wrote Git in a few weeks to meet the kernel's needs: speed on a huge tree, a distributed model in which every clone holds the full history, strong integrity (every object is named by a hash of its content) and cheap branching. Mercurial appeared at the same time with similar ideas, and Git became the dominant tool as hosting services (GitHub, GitLab and others) grew around it and added pull requests, issue tracking and continuous integration.

Workflows are conventions on top of the tool. **Centralised workflow**: everyone pushes to one branch, simple and risky. **Feature branch workflow**: each change lives on a short-lived branch and reaches the main branch through review and merge, which is the common model for teams; the Rocky Linux documentation describes it step by step for contributors [src: rocky-docs 90f83916dda98e2f]. **Forking workflow**: contributors push to their own copy and ask the maintainers to pull, used for open-source projects. **Integration-manager and patch-based workflows**: the kernel and Git itself use mailing-list patches reviewed by subsystem maintainers, with long-lived integration branches; the `gitworkflows` manual page documents the model used for Git's own development, with branches that carry topics at different levels of stability and a policy of merging up as confidence grows [src: man-pages d95347477ca4a3c8]. **Trunk-based development**: very short-lived branches and continuous integration, with feature flags for incomplete work. **GitOps**: the repository is the source of truth for a system's desired state, and an agent applies it.

Operational teams usually choose the feature-branch workflow with required reviews and a protected main branch, and for infrastructure repositories sometimes add a promotion model (the same commit moves from a staging branch or tag to production).

## Current state

### The model in five facts

1. A **commit** is a snapshot of the whole tree with an author, a message and pointers to its parent commit or commits; it is identified by a SHA hash (currently SHA-1 by default, with SHA-256 repositories supported).
2. A **branch** is a movable name that points to a commit; `HEAD` says which branch (or commit) is checked out. Creating a branch costs almost nothing.
3. Three areas matter: the **working tree** (files on disk), the **index** or staging area (what the next commit will contain) and the **repository** (committed history). `git add` copies from the first to the second and `git commit` from the second to the third.
4. A **remote** is another copy of the repository; `git fetch` downloads its commits without changing your branches, `git pull` is fetch plus merge (or rebase), and `git push` uploads your branch.
5. History is a graph. **Merge** joins two lines with a merge commit (or fast-forwards if one is a direct descendant); **rebase** replays your commits on top of another base, producing a linear history and new commit IDs.

### Day-to-day commands

```bash
git status                       # what changed, what is staged
git switch -c fix/nginx-timeout  # new branch from the current one
git diff                         # unstaged changes; --staged for the index
git add -p                       # stage hunks interactively
git commit                       # opens the editor; -m for a one-line message
git log --oneline --graph --decorate -20
git fetch origin && git rebase origin/main
git push -u origin fix/nginx-timeout
```

Configuration lives at three levels (system, user in `~/.gitconfig`, repository in `.git/config`), set with `git config`; at minimum set `user.name`, `user.email`, `pull.rebase` (or `pull.ff only`), `init.defaultBranch` and, for signed work, `commit.gpgsign` with `gpg.format` set to `openpgp` or `ssh` [src: man-pages 1180245863489784]. Environment variables such as `GIT_DIR`, `GIT_WORK_TREE`, `GIT_SSH_COMMAND` and `GIT_AUTHOR_DATE` control behaviour in scripts [src: man-pages bb493c4d9b54b4f4]. A `.gitignore` keeps generated files and local secrets out of the repository; files that were committed once remain in history (see recovery below).

### Branching, merging and rebasing

Keep branches short-lived and focused on one change. Before opening a pull request, update the branch: `git fetch` then either `git rebase origin/main` (linear history, but rewrites your branch) or `git merge origin/main` (keeps the branch's history and adds a merge commit). Use `git rebase -i` to tidy the branch before review: reorder, squash fixups (`fixup`, `squash`), reword messages. The important rules about rewriting: never rewrite history that others have based work on (published shared branches), push a rewritten personal branch with `git push --force-with-lease` (which refuses if someone else pushed in the meantime) and never plain `--force`, and never rewrite the main branch. On the hosting service, the merge strategy (merge commit, squash or rebase-and-merge) is a team choice; squash merging gives one commit per pull request, which keeps the main history readable when branches contain many small commits.

### Writing commits that help later

A commit is a unit of reasoning: it should do one thing and the tree should work after it (so `git bisect` can use it). The message has a short imperative subject (about 50 characters, such as Raise proxy timeout), a blank line, and a body wrapped at about 72 columns that explains **why** the change was made and what it affects, since the diff already shows what. Conventions such as Conventional Commits (`fix:`, `feat:`, `docs:`) add machine-readable prefixes useful for changelogs; the kernel and many projects add trailers such as `Signed-off-by:` (the developer's certificate of origin), `Reviewed-by:` and `Fixes:`. Operational repositories benefit from linking to the ticket or incident and from stating the rollback (a note that reverting the commit restores the old timeout). Never commit secrets; if one is committed, rotating the secret is the fix, since removing it from history does not remove it from clones.

### Review

Review is where a second pair of eyes catches what the author missed. For operational code the review questions differ from those for application code:

- **Blast radius.** Which hosts or services does this affect, and does the change apply to all of them at once or in stages?
- **Reversibility.** How is it undone, and has the rollback been tried?
- **Safety.** For shell: strict mode, quoting, destructive commands guarded; for Python: subprocess use, error paths; for configuration: syntax check (`nginx -t`, `sshd -t`, `visudo -c`, `nft -c -f`), no secrets.
- **Idempotence and ordering.** Can it run twice, and does it depend on a step that may not have happened yet?
- **Evidence.** Test output, a dry run (`--check`, `--dry-run`, `terraform plan`), or a link to a staging run.
- **Scope.** One concern per change; unrelated edits go in separate pull requests.

Good reviews are specific and kind, separate blocking problems from suggestions, and the author keeps the change small so that review is quick. A short pull-request description (what, why, how tested, how to roll back) is part of the change. The QEMU project's guide to submitting changes shows a mature version of the same expectations: a clear title, a description that explains the reason, and a checklist of what was run [src: qemu-docs 2bdb39a02d36b432].

### Making the workflow a control

The hosting service enforces what convention only suggests: **protected branches** that forbid direct pushes and force-pushes to the main branch, **required reviews** (including review by code owners, listed in a `CODEOWNERS` file, for sensitive paths such as `/etc` templates and firewall rules), **required status checks** (ShellCheck, the bats suite, `yamllint`, `ansible-lint`, a `terraform validate`), **signed commits** where the policy demands, and an audit trail of who approved what. Local **hooks** (`pre-commit` framework, or `.git/hooks`) run formatters and linters before a commit, though they can be skipped, so the server-side check is the authority. Merge only when the checks are green; never skip a failing check by disabling it.

### Recovering from mistakes

Git rarely loses committed work, and the tools to recover are worth knowing:

- `git restore file` discards unstaged changes to a file; `git restore --staged file` unstages it.
- `git commit --amend` fixes the last commit (only if not yet shared).
- `git revert <commit>` creates a new commit that undoes an earlier one, the safe way to undo a change that has been published.
- `git reset --hard <commit>` moves the branch and discards changes, dangerous because it throws away uncommitted work; `git reset --soft` keeps changes staged.
- `git reflog` lists where `HEAD` has been, so a branch deleted or reset by mistake can be recovered with `git switch -c rescue <hash>` for a few weeks after the event (the reflog is local).
- `git stash` sets aside uncommitted work temporarily; `git cherry-pick` copies a commit to another branch.
- `git bisect start; git bisect bad; git bisect good <tag>` performs a binary search through history for the commit that introduced a fault, and `git bisect run ./test.sh` automates it, which is a strong reason to keep commits small and working.
- `git blame file` and `git log -S 'string'` or `git log -p -- path` trace why a line exists.

### Operations-specific uses

`etckeeper` puts `/etc` under version control and commits before and after package operations, giving a history of configuration changes on a single host. Infrastructure repositories (Ansible, Terraform, Kubernetes manifests, systemd units, nftables files) are normally reviewed and deployed from Git, and a deployment can pin to a tag or commit. Large binaries do not belong in Git (use Git LFS or an artifact store), and repositories should be small and focused, since cloning and history get slower as they grow.

## Assessment: the good, the bad and the ugly

**The good.** Git gives every change an identity, a message, an author and a place in a graph; branches make parallel work cheap; and the distributed model means history survives the loss of any copy. Combined with review and automated checks it gives operations the same discipline as software engineering: changes are small, discussed and reversible. The tool is fast, ubiquitous and well documented.

**The bad.** The command line is large and inconsistent, and a newcomer can get into states (detached `HEAD`, rebase conflicts, a merge in progress) that are confusing without a mental model of the graph. Rewriting history is powerful and dangerous. Defaults are not safe (`git push --force`, `git reset --hard`). Reviews are a human process and degrade when changes are large or when reviewers do not know the system; a "looks good to me" on a thousand-line change is not a control.

**The ugly.** Secrets committed to history and discovered years later; force-pushes to shared branches that destroy others' work; repositories where operational changes are made on the server and never committed, so Git no longer describes reality; merge conflicts in generated files resolved by taking one side blindly; review used as a rubber stamp to satisfy a policy; and long-lived branches that diverge until merging is a project. In some teams the main branch is protected on paper but administrators can bypass the protection, which defeats the audit trail.

## Applications beyond this domain

The same model and workflow appear in documentation (docs-as-code), data science notebooks and configuration of nearly every platform. GitOps tools reconcile Kubernetes clusters with a repository, and policy-as-code and infrastructure-as-code repositories use the same review and CI controls. Open-source contribution follows the fork-and-pull-request pattern, and the patch-based model of the kernel scales review across thousands of contributors. Compliance frameworks ask for change management evidence that a protected-branch, review and CI workflow provides directly: who approved, what was tested and when it was deployed.

## Examples

**1. A complete small change.**

```bash
git switch -c fix/rotate-keep-count
$EDITOR bin/rotate.sh
shellcheck bin/rotate.sh && bats test/
git add -p
git commit -m "rotate: fix keep count" -m "Default was off by one."
git fetch origin && git rebase origin/main
git push -u origin fix/rotate-keep-count
```

Then open the pull request with a description of what, why, how it was tested and how to roll back.

**2. Tidy a branch before review.**

```bash
git rebase -i origin/main     # mark small fix-up commits as 'fixup', reword unclear messages
git push --force-with-lease
```

**3. Undo a published change safely.**

```bash
git revert 3f2a9c1
git push origin main          # through the normal review path where required
```

**4. Find which commit broke a script.**

```bash
git bisect start HEAD v1.4
git bisect run bats test/backup.bats
git bisect reset
```

**5. Recover a branch deleted by mistake.**

```bash
git reflog | head
git switch -c rescue 8c1d0e2
```

**6. See why a line exists.**

```bash
git blame -L 40,60 bin/deploy.sh
git log -S'--force' --oneline -- bin/deploy.sh
```

## Related problems and ideas

- **Continuous integration.** Required checks make the workflow a control; the earlier slices supply ShellCheck and bats jobs.
- **Secrets management.** Scanners (`gitleaks`, `trufflehog`) in CI and pre-commit hooks, and external secret stores referenced by name.
- **Release and promotion.** Tags for releases, annotated and signed; branches or directories per environment; rollback by deploying an earlier tag.
- **Monorepo versus many repositories.** Trade-offs in ownership, review and tooling for infrastructure code.
- **Code ownership.** `CODEOWNERS` for sensitive paths, with a small group of required reviewers.
- **Documentation next to code.** READMEs and runbooks reviewed in the same pull request as the change.

## Active research

Work on version control includes better handling of large repositories (partial clone, sparse checkout, the commit-graph and multi-pack index features that speed up history operations), a gradual move to SHA-256 object names, improved merge strategies and conflict resolution, and alternatives that rethink the model (such as patch-theory systems and the Jujutsu tool, which can use Git repositories as a backend). Supply-chain security research focuses on signed commits and tags, the use of SSH and Sigstore-based signing, and provenance records that tie a deployed artifact to the exact commit and review. Studies of code review look at which practices catch defects and how to reduce reviewer fatigue, including automated assistance that proposes changes or summarises diffs.

## Future direction

Expect review and policy checks to become more automated: required checks that run linters, tests and policy engines, with human review reserved for design and risk. Repositories will increasingly be the interface for operations (GitOps), so the quality of history and review becomes a reliability concern. For the sysadmin the stable habits are small branches, clear messages, a protected main branch with required checks, rebase before review, revert rather than rewrite, and a habit of looking at the reflog before panicking. The course target is a student who can take a change from branch to merged pull request with passing checks, write a useful message, review a colleague's change with the questions above and recover from a mistaken commit.
