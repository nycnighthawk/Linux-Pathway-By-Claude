# Testing shell scripts with bats-core

## Define the problem

Shell scripts are code that changes real systems, yet they are usually the least tested code a team owns. The usual test is to run the script by hand on a staging machine and look at the output, which checks one path once and leaves no record. When someone edits the script a year later, nothing says whether the old behaviour still holds. The shell makes testing awkward for structural reasons: functions return a status and print text rather than return values, many scripts run `main` when loaded so they cannot be sourced safely, and the interesting effects (files written, services restarted, packages installed) happen outside the script. A test framework for shell has to run a command, capture its status, standard output and standard error, give each test a clean scratch directory, and report results in a form that humans and continuous-integration systems can read.

bats-core (the Bash Automated Testing System) is the framework most Linux teams use for this. This slice shows how to write tests in its format, how to structure a script so that it can be tested, how to isolate tests from the host with temporary directories and stub commands, how to use the assertion helper libraries, and how to run the suite in continuous integration. It builds on the previous two slices: scripts that follow strict mode and quote their expansions are far easier to test.

## History and approaches

Test frameworks for shell appeared early in the history of automated testing. The simplest approach, a script that runs commands and compares output with a stored file, is still common for command-line tools, and projects such as Git's own test suite are built on a shell harness of this kind. In 2011 Sam Stephenson published Bats, a small framework that turned a `.bats` file into a list of named tests written as ordinary shell with a few special words, and its readable syntax made it popular. The original project stopped receiving updates, and in 2016 and 2017 a group of maintainers began the community fork, bats-core, which has been the maintained project since. It keeps compatibility with the original file format and adds features such as per-file and per-suite hooks, parallel execution, formatters and a documented set of helper libraries [web: bats-core.readthedocs.io].

Other approaches exist. `shunit2` and `shellspec` offer xUnit-style and behaviour-style syntax. Python's `pytest` with `subprocess` or the `testinfra` plugin tests machines from outside, and is often the better tool when the logic is mostly data handling. Heavier approaches run the whole script in a container or virtual machine and check the resulting state with a tool such as `goss`, `inspec` or Ansible's own assertions. They answer a different question (does the system end up configured?) from unit-style tests (does this function return the right thing for this input?), and a mature repository usually has both. bats suits the lower layer: fast tests, no dependencies beyond bash, readable by the people who maintain the scripts.

The output convention behind bats is the Test Anything Protocol (TAP), a plain-text format from the Perl community in which each test produces a line beginning `ok` or `not ok` with a number and a description, preceded by a plan such as `1..4`. TAP is simple enough to be produced and consumed by any language and is the reason bats results can be fed into many reporters [web: testanything.org].

## Current state

### Installing and running

bats-core is packaged as `bats` in Debian-family distributions and in EPEL for Red Hat family systems, and can be installed from a release tarball or a git submodule (`install.sh /usr/local`), which pins the version in the repository and avoids differences between machines. Test files have the extension `.bats` and are run with `bats test/` (a directory), `bats -r test/` (recursively) or `bats file.bats`. Useful options include `--tap` (TAP output), `--formatter junit` (for CI dashboards), `--filter 'regex'` (select tests by name), `-j N` (run N tests in parallel when GNU `parallel` is installed), `--timing` and `--print-output-on-failure`. The exit status is non-zero if any test fails, which is all a CI job needs [web: bats-core.readthedocs.io].

### The test file

A `.bats` file is bash with one extension: a block introduced by `@test "description" { ... }`. Bats preprocesses the file, turning each block into a function, and runs each test in its own subshell with `set -e`-like behaviour: the first command that returns non-zero fails the test, which is why a test body reads like a sequence of assertions.

```bash
#!/usr/bin/env bats

setup() {
    TMP="$BATS_TEST_TMPDIR"
    cp "$BATS_TEST_DIRNAME/../bin/rotate.sh" "$TMP/rotate.sh"
}

@test "no argument fails" {
    run bash "$TMP/rotate.sh"
    [ "$status" -eq 2 ]
    [[ "$output" == *usage* ]]
}

@test "newest three stay" {
    for i in 1 2 3 4 5; do touch -d "$i days ago" "$TMP/log.$i"; done
    run bash "$TMP/rotate.sh" "$TMP" 3
    [ "$status" -eq 0 ]
    [ "$(ls "$TMP" | grep -c '^log\.')" -eq 3 ]
}
```

`run` executes a command, captures its exit status in `$status`, its combined output in `$output`, and the output split into lines in the array `$lines`. Because `run` itself always succeeds, the test must then assert on those variables. Newer versions add `run -1 cmd` (expect a given status and fail the test otherwise), `run --separate-stderr cmd` (fill `$stderr` and `$stderr_lines` separately) and `bats_require_minimum_version 1.5.0` to declare which features the file needs. A `skip "reason"` marks a test as skipped, which is useful for tests that need root or a tool that is not installed. The documentation on writing tests lists the special variables, such as `BATS_TEST_TMPDIR` (a fresh directory per test, removed afterwards), `BATS_FILE_TMPDIR`, `BATS_SUITE_TMPDIR`, `BATS_TEST_DIRNAME` and `BATS_TEST_NAME` [web: bats-core.readthedocs.io].

### Hooks

`setup` and `teardown` functions run before and after each test in the file; `setup_file` and `teardown_file` run once per file; and a `setup_suite.bash` file with `setup_suite` and `teardown_suite` functions runs once per run. Variables exported in `setup_file` are visible in tests. A failing `setup` fails the test, and `teardown` runs even when the test failed, so it is the place for cleanup that must happen. Keep hooks small, because a long setup hides what a test depends on.

### Making a script testable

A script that does its work at the top level can only be tested by running it as a whole. The standard refactoring is to move the logic into functions and guard the call to `main`:

```bash
#!/usr/bin/env bash
set -euo pipefail

keep_newest() {   # keep_newest DIR N
    local dir=$1 n=$2
    ls -1t -- "$dir" | tail -n +"$((n + 1))" | while IFS= read -r f; do rm -- "$dir/$f"; done
}

main() {
    [ $# -eq 2 ] || { echo "usage: ${0##*/} DIR N" >&2; exit 2; }
    keep_newest "$1" "$2"
}

if [[ "${BASH_SOURCE[0]}" == "$0" ]]; then main "$@"; fi
```

A test can then `source` the file, which defines the functions without running `main`, and call `keep_newest` directly:

```bash
@test "oldest files go" {
    source "$BATS_TEST_DIRNAME/../bin/rotate.sh"
    ...
    run keep_newest "$BATS_TEST_TMPDIR" 3
    [ "$status" -eq 0 ]
}
```

Note that `set -e` and `set -u` from the sourced file stay active inside the test, which is often what you want (the test sees the same strictness as production) but can surprise: an unset variable the test forgets to define aborts the test.

### Isolating tests from the host

Tests that modify the real system are dangerous and flaky. Three techniques keep them hermetic. First, point the script at a scratch directory (`BATS_TEST_TMPDIR`) through arguments or environment variables instead of hard-coded paths such as `/etc` or `/var`. Second, **stub external commands** by placing small scripts or functions earlier in `PATH`:

```bash
setup() {
    mkdir -p "$BATS_TEST_TMPDIR/bin"
    printf '#!/bin/sh\necho "$@" >> "%s/calls"\n' "$BATS_TEST_TMPDIR" > "$BATS_TEST_TMPDIR/bin/systemctl"
    chmod +x "$BATS_TEST_TMPDIR/bin/systemctl"
    PATH="$BATS_TEST_TMPDIR/bin:$PATH"
}

@test "restart is called once" {
    run bash script.sh
    [ "$(cat "$BATS_TEST_TMPDIR/calls")" = "restart nginx" ]
}
```

Third, for things that cannot be stubbed (mounts, network, services), run the suite as root inside a throw-away container or namespace, as the labs in this course do, and mark tests that need privileges with a guard that skips them elsewhere.

### The assertion libraries

Plain `[ ]` checks give poor failure messages. The bats-core organisation maintains helper libraries that are loaded with `load`: `bats-support` (output formatting and error reporting), `bats-assert` (`assert_success`, `assert_failure`, `assert_output`, `assert_line`, `refute_output`, `assert_equal`) and `bats-file` (`assert_file_exist`, `assert_dir_exist`, `assert_file_contains`). A typical header is:

```bash
setup() {
    load 'test_helper/bats-support/load'
    load 'test_helper/bats-assert/load'
}

@test "prints a greeting" {
    run ./greet.sh Ada
    assert_success
    assert_output 'hello, Ada'
}
```

`assert_output --partial text` matches a substring and `--regexp` a pattern. When a library is needed inside `setup_file` or `teardown_file`, it has to be loaded there, as the FAQ explains. The helper libraries are usually vendored as git submodules under `test/test_helper/` so that every developer and the CI job use the same versions [web: bats-core.readthedocs.io].

### Running in continuous integration

A CI job needs three steps: install bats (from a package, a pinned submodule, or an official container image), run `shellcheck` on the scripts, and run `bats --formatter junit` or `--tap`. Because tests run as ordinary bash, the job can use a matrix of images (for example one Debian, one Rocky) to catch portability faults such as GNU versus busybox utilities. Parallel runs (`-j`) require that tests do not share state; use `BATS_TEST_TMPDIR`, never fixed file names.

## Assessment: the good, the bad and the ugly

**The good.** The tests are shell, so anyone who maintains the scripts can read and write them, and there is almost nothing to learn beyond `@test` and `run`. TAP and JUnit output fit every CI system. Per-test temporary directories, hooks and stubbing by `PATH` make hermetic tests straightforward. A small suite around a script gives confidence to refactor, and writing tests often leads to the better structure (functions, a guarded `main`) that the earlier slices recommend.

**The bad.** bats tests inherit the weaknesses of shell: errors inside a test body are easy to hide (a failing command inside `$( )` or a pipeline does not fail the test unless you check), a missing assertion passes silently, and a `[ ]` test with an unquoted variable breaks in the same ways as in scripts. `run` merges standard output and standard error unless told otherwise. Mocking is manual, with nothing like the rich mock objects of other languages, and parallel execution depends on an external tool. The different bats-core versions have different features, so a test file written for the newest release may not run on the version in a distribution's repository, which is why pinning matters.

**The ugly.** Tests that touch the real system: a "unit" test that edits `/etc/hosts` or restarts a service leaves a mess when it fails halfway and teardown does not run (for instance, after a `kill -9`). Suites that need root cannot be run by every contributor, so they rot. Tests that depend on the ordering of earlier tests, on the time of day, on network access or on the host's locale fail intermittently and teach people to ignore failures. And a test suite for a script that is itself unmaintainable (global state, no functions, `eval` everywhere) can only exercise it as a black box; the real fix is the refactoring, not more tests.

## Applications beyond this domain

The same method applies wherever behaviour is exposed as a command line. Tests for command-line tools in any language can use bats: run the binary, assert on status and output. Infrastructure repositories test container entrypoints, installers and Helm hooks with it, and the Kubernetes-oriented `bats-detik` library adds assertions about cluster state. The structure (refactor for testability, stub the edges, assert on observable behaviour, run in CI) is the general recipe for testing glue code, whether in shell, Python or a configuration language. TAP is also used outside shell: many test runners can emit it, and CI systems display it.

## Examples

**1. A minimal first test.**

```bash
#!/usr/bin/env bats

@test "true succeeds" {
    run true
    [ "$status" -eq 0 ]
}

@test "false fails" {
    run -1 false
}
```

**2. Check standard error separately.**

```bash
bats_require_minimum_version 1.5.0

@test "usage goes to stderr" {
    run --separate-stderr ./tool.sh
    [ "$status" -eq 2 ]
    [ -z "$output" ]
    [[ "$stderr" == *usage* ]]
}
```

**3. A fixture directory per test.**

```bash
setup() {
    cd "$BATS_TEST_TMPDIR"
    mkdir conf logs
    printf 'level=debug\n' > conf/app.conf
}

@test "reads the config" {
    run "$BATS_TEST_DIRNAME/../bin/app.sh" conf/app.conf
    assert_output --partial 'debug'
}
```

**4. Skip when a precondition is missing.**

```bash
@test "mount works" {
    [ "$(id -u)" -eq 0 ] || skip "needs root"
    command -v mount >/dev/null || skip "mount not installed"
    run mount --version
    [ "$status" -eq 0 ]
}
```

**5. Run the suite and read the TAP output.**

```
$ bats --tap test/
1..3
ok 1 usage goes to stderr
ok 2 reads the config
not ok 3 keep newest three files
# (in test file test/rotate.bats, line 21)
#   `[ "$count" -eq 3 ]' failed
```

**6. Parameterised tests with a loop.**

```bash
for n in 0 1 5; do
    @test "keeps $n files" {
        run bash rotate.sh "$BATS_TEST_TMPDIR" "$n"
        [ "$status" -eq 0 ]
    }
done
```

The loop runs at file-parse time, so each iteration defines one more test with the interpolated name.

## Related problems and ideas

- **Static analysis and tests.** ShellCheck (previous slice) finds quoting and syntax faults without running the script, while bats finds logic faults; use both.
- **Test pyramids for operations code.** Fast bats tests for functions, container-based tests for whole scripts, and occasional end-to-end runs on a real machine.
- **Coverage.** Shell has no standard coverage tool; `kcov` can instrument bash with some effort, and teams often settle for checking that every function has a test.
- **Mocks and fakes.** Stubs in `PATH` suffice for commands; fake servers (a small Python HTTP server) stand in for APIs.
- **Contract tests for CLIs.** Pin the exit codes and the format of the output that other scripts and systemd units depend on.
- **Python equivalents.** `pytest` with `tmp_path` and `monkeypatch` plays the role that `BATS_TEST_TMPDIR` and PATH stubs play here (see the Python slice).

## Active research

Research on testing shell is a small but active part of the programming-languages community: symbolic execution of shell scripts to generate test inputs, mutation testing for shell (deleting a quote or a `set -e` to see whether a test notices), property-based testing for command-line tools and automatic extraction of the commands a script runs so they can be stubbed. In practice, the bats-core project continues to add features (the parallel runner, formatters, suite-level hooks, better reporting) and the surrounding library ecosystem grows. Container-based testing frameworks make it easier to run hermetic tests that need privileges.

## Future direction

Expect testing of operational scripts to become a normal requirement, not a luxury: repositories with scripts will carry a `test/` directory run in CI, with linting and formatting enforced beforehand. For scripts that outgrow bats, the natural move is to Python with pytest, keeping bats for thin wrappers and for tests of command-line contracts. The course target is a student who can take a script, restructure it so its functions are testable, write tests for success and failure paths with isolation and stubs, and run them in a pipeline.
