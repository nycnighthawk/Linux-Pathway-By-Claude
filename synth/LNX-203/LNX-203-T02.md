# Making shell scripts fail safely: strict mode, quoting and static analysis

## Define the problem

The shell's defaults are tuned for a person at a keyboard. Unset variables expand to nothing, a failing command lets the next one run, a pipeline reports only its last stage, and every unquoted expansion is split on white space and then expanded again as a glob. In a script these defaults turn small mistakes into damage: `rm -rf "$BUILD_DIR"/*` with an unset `BUILD_DIR` becomes `rm -rf /*`, a failed `cd` lets the script carry on in the wrong directory, and a file named `-rf` or `my report.txt` changes what a command means. The problem is not that the shell cannot be written safely; it is that safety is opt-in and spread over three habits: tell the shell to stop on errors, quote every expansion, and let a tool check what a human reviewer will miss.

This slice teaches those three habits, in the order they should be applied to a script: the options usually called strict mode (`set -e`, `set -u`, `set -o pipefail`) and what they do not catch, the rules of quoting and word splitting, and ShellCheck, the static analyser that detects most quoting and portability mistakes before the script runs.

## History and approaches

The Bourne shell had `set -e` from early on, and for decades the common advice was to put it at the top of every script. Experience showed that it behaved in ways that were hard to predict. The rule is that the shell exits when a simple command fails, except in a long list of contexts: in the condition of `if`, `while` and `until`; in any command of an `&&` or `||` list except the last; in a pipeline except the final stage; when the command's status is negated with `!`; and inside functions or subshells called in one of those contexts. Because the same function behaves differently depending on where it is called from, `set -e` is better understood as a safety net that catches forgotten checks than as a replacement for them. The bash manual defines the option together with `nounset` and `pipefail` in its section on builtins [src: man-pages a6898b4aef6ad39b].

`set -u` (nounset) turns the use of an unset variable into an error, which catches typos and the empty-path accident above, but in older bash versions it also made `"${array[@]}"` an error for an empty array, a quirk fixed in bash 4.4. `set -o pipefail` makes a pipeline fail if any stage fails, which fixes the case where `cmd | tee log` hides the failure of `cmd`. The combination `set -euo pipefail` became the standard header, popularised in the community by blog posts that called it "unofficial strict mode"; critics replied that it hides surprises (for example `set -e` does not stop on a failed command substitution inside an assignment to a declared local variable) and that it should be used knowingly.

On quoting, the first systematic guidance came from the Unix community's folklore and then from Greg Wooledge's long-running wiki, which documents the "pitfalls" section by section. Google's internal shell style guide, now public, makes quoting and `[[ ]]` mandatory and caps shell use at small scripts. Static analysis arrived with ShellCheck (a Haskell program by Vidar Holen, first released in 2012), which turned the folklore into numbered warnings with explanations, now run in editors, in continuous integration and in package-review pipelines. The alternative approach is to avoid the problem by avoiding shell: write scripts above a certain size in Python (see the Python slice), where lists are lists and failures raise exceptions.

## Current state

### Strict mode, option by option

Place these after the interpreter line:

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
IFS=$'\n\t'
```

- **`-e` (errexit)**: exit on an unchecked failing command. It does not fire in the contexts listed above, and it does not fire for a failure inside `$( )` used in an argument position. Rely on explicit checks for the commands that matter (`cmd || die "cmd failed"`).
- **`-u` (nounset)**: error on an unset variable. Use `${var:-}` where emptiness is legitimate, and `${var:?message}` to demand a value with a clear message.
- **`-o pipefail`**: the pipeline's status is the rightmost non-zero status. Remember that `grep -q` closing the pipe early can make an earlier stage die with SIGPIPE (status 141), so `producer | grep -q pattern` can fail under pipefail even though grep succeeded.
- **`-E` (errtrace)**: lets an `ERR` trap fire inside functions and subshells. Combine with `trap 'echo "line $LINENO: $BASH_COMMAND" >&2' ERR` for a poor man's stack trace.
- **`shopt -s inherit_errexit`** (bash 4.4 and later) makes command substitutions inherit `-e`.
- **`IFS=$'\n\t'`** removes the space from the field separators, reducing the damage of an unquoted expansion; it is a mitigation, not a substitute for quoting.

The pitfalls that survive strict mode are worth listing because they are asked in interviews and cause real outages. `local x=$(cmd)` hides the exit status of `cmd` behind the status of `local`; declare first (`local x; x=$(cmd)`). `cmd1 && cmd2` as the last line of a function makes the function return non-zero when `cmd1` fails even though nothing went wrong. `((count++))` returns status 1 when `count` was 0, so under `-e` it aborts; write `count=$((count + 1))`. A `while read` loop that reads from a pipe runs in a subshell, so its variable changes are lost. And `set -e` is ignored inside a function called as `if myfunc; then`, so the function's internal failures are silently skipped.

### Quoting and word splitting

After an unquoted parameter expansion or command substitution, the shell splits the result into words on the characters of `IFS`, then performs pathname expansion on each word that contains `*`, `?` or `[`. The rules live in the expansion section of the bash manual, which also defines the order of the other expansions (brace, tilde, parameter, arithmetic, command substitution, process substitution) [src: man-pages a4a6fb605c73a527]. Quoting suppresses both steps. The practical rules reduce to a few lines:

1. **Quote every expansion**: `"$var"`, `"$(cmd)"`, `"${arr[@]}"`, `"$@"`. The only common places that need no quotes are the right side of a plain assignment (`x=$y`), inside `[[ ]]` (except the right side of `==` and `=~` when you want literal matching), and as the word of a `case`.
2. **Use `"$@"`, not `$*` or `$@`**, to pass arguments through unchanged. `"$*"` joins them into one word and is only for messages.
3. **Use single quotes for text with no expansion** (`'$HOME'` is literal) and double quotes where expansion is wanted. Embedding a single quote needs `'\''` or `$'...'`.
4. **End option parsing with `--`**: `rm -- "$file"`, `grep -e "$pattern" -- "$file"`, because a name beginning with `-` is otherwise taken as an option.
5. **Prefix relative globs with `./`** when the names are untrusted (`for f in ./*`).
6. **Do not build commands in strings.** Put arguments in an array: `args=(--user "$u" --port 22); ssh "${args[@]}" host`. `eval` and `bash -c "$string"` re-parse text and turn data into code; if you must, use `printf '%q'` to escape each value.
7. **Handle awkward file names with null separators**: `find . -type f -print0 | while IFS= read -r -d '' f; do ...; done`, or `find ... -exec cmd {} +`.
8. **Never parse `ls`**; use a glob, `find` or `stat --printf`.

The Arch wiki's shell page notes how the family of POSIX-compliant shells differs from bash, which matters when a script claims `#!/bin/sh` and uses features that only bash provides [src: archwiki bd1c46847ae3bb8e]. In Python, the `shlex` module provides `quote()` for building a shell command line from untrusted values and `split()` for parsing one, which applies the same rules from the other side [src: python-docs 90fba8171df3a774].

### ShellCheck

ShellCheck parses the script and reports findings with a code (SCnnnn), a severity (error, warning, info, style) and a link to a wiki page that explains the problem and the fix. Typical use:

```bash
shellcheck script.sh
shellcheck -x -s bash -S warning scripts/*.sh
shellcheck -f gcc script.sh        # editor-friendly format; also json, checkstyle, diff, quiet
shellcheck -f diff script.sh | patch -p1   # apply the automatic fixes it offers
```

The shell is taken from the interpreter line or from a `# shellcheck shell=bash` directive, which matters because the same text means different things in `sh` and `bash`. A source file included with `. file` can be followed with `-x` and a `# shellcheck source=path` directive. Warnings are silenced one by one with a comment on the line above: `# shellcheck disable=SC2086`, ideally with a reason after it. Codes worth knowing by heart:

| Code | Meaning | Fix |
|---|---|---|
| SC2086 | unquoted variable may split or glob | quote it |
| SC2046 | unquoted command substitution | quote it or use an array |
| SC2006 | backtick command substitution | use `$( )` |
| SC2155 | `local x=$(cmd)` masks the status | declare, then assign |
| SC2164 | `cd` without handling failure | `cd dir \|\| exit` |
| SC2162 | `read` without `-r` | add `-r` |
| SC2015 | `A && B \|\| C` is not if-then-else | use `if` |
| SC2034 | variable assigned but unused | remove or export |
| SC2068 | unquoted `$@` or array expansion | quote it |

Installation is a distribution package (`ShellCheck` in EPEL for RHEL-family systems, `shellcheck` in Debian-family repositories) or a static binary. Companions are `shfmt` for formatting (a consistent style removes arguments in review) and `checkbashisms` (from the Debian devscripts package) to find bash features in scripts that claim POSIX. In continuous integration, run ShellCheck on every shell file the repository holds (including those without an extension, found by the interpreter line) and fail the build on warnings; pair it with the test framework of the next slice.

### A review checklist

Before a script is accepted: it starts with a correct interpreter line and strict mode; every expansion is quoted or justified; temporary files come from `mktemp` and are removed by a trap; destructive commands check their variables (`${dir:?}`); required tools are tested with `command -v` at the top; failures print to standard error and exit with distinct non-zero codes; and `shellcheck` reports nothing, or each disabled warning has a reason in a comment.

## Assessment: the good, the bad and the ugly

**The good.** Three habits remove most shell disasters at almost no cost. Strict mode turns silent failures into stops, quoting makes data stay data, and ShellCheck finds the remaining mistakes automatically with explanations that teach as they correct. Together they let a team write shell that reviewers can approve with confidence and that behaves the same when file names contain spaces.

**The bad.** Strict mode is not a language feature with clean semantics; it is a set of options with exceptions, and the exceptions differ by bash version. Teams copy the `set -euo pipefail` line without understanding it, then are surprised when a script still ignores a failure or when `pipefail` makes a harmless `SIGPIPE` fatal. ShellCheck cannot prove correctness: it does not know your data, can miss logic errors and, when run with too low a threshold, produces noise that teams silence wholesale. Quoting everywhere makes scripts noisier to read, and the few places where quoting must not be applied (for example a variable that holds several intentional words) need a comment or an array.

**The ugly.** Real scripts mix all of these hazards with external input: file names from users, text from APIs, variables from other scripts. Command injection through unquoted variables and `eval` is common in deployment code and has produced real vulnerabilities. A script that passes strict mode and ShellCheck can still be wrong about its inputs, its idempotence or its concurrency. Legacy scripts that predate these tools can be large enough that adding quotes everywhere is a project in itself, and changing behaviour (for example fixing the splitting of an argument that callers relied on) can break users.

## Applications beyond this domain

The same discipline applies wherever text is built into commands. Dockerfile `RUN` lines and CI configuration files embed shell, and a missing `set -e` there silently produces broken images; ShellCheck can lint scripts extracted from them. Python and other languages that call the shell need the equivalent care: pass argument lists to `subprocess.run` (with no `shell=True`) rather than building strings, and use `shlex.quote` when a shell is unavoidable. SQL injection and shell injection are the same class of fault, untrusted data crossing into code, and the remedy is the same: separate data from code, as with parameterised queries and argument arrays. Configuration-management and infrastructure tools that accept shell snippets (Ansible's `shell` module, Terraform provisioners) benefit from the same linting and quoting rules.

## Examples

**1. The empty-variable accident, and its fix.**

```bash
# dangerous: with BUILD_DIR unset this removes everything below /
rm -rf "$BUILD_DIR"/*
# safe: abort with a message if the variable is empty or unset
rm -rf -- "${BUILD_DIR:?BUILD_DIR is not set}"/*
```

**2. A failure hidden by a pipe.**

```bash
set -o pipefail
if ! dump_database | gzip > backup.sql.gz; then echo "backup failed" >&2; exit 1; fi
```

Without `pipefail` a failing `dump_database` is invisible because `gzip` succeeds.

**3. Arguments in an array, not a string.**

```bash
opts=(-o BatchMode=yes -o ConnectTimeout=5)
[ -n "${jump:-}" ] && opts+=(-J "$jump")
ssh "${opts[@]}" "$host" uptime
```

**4. Safe file iteration with spaces and newlines in names.**

```bash
find /srv/uploads -type f -mtime +30 -print0 |
    while IFS= read -r -d '' f; do rm -- "$f"; done
```

**5. Reading ShellCheck output.**

```
$ shellcheck deploy.sh
In deploy.sh line 12:
cp $src $dst
   ^--^ SC2086: Double quote to prevent globbing and word splitting.
```

The fix is `cp -- "$src" "$dst"`; the diff format (`-f diff`) can apply it automatically.

**6. A header that documents the choices.**

```bash
#!/usr/bin/env bash
# shellcheck shell=bash
set -Eeuo pipefail
shopt -s inherit_errexit nullglob
trap 'echo "error at line $LINENO: $BASH_COMMAND" >&2' ERR
```

## Related problems and ideas

- **Testing.** Static analysis and tests find different bugs; the next slice adds bats tests that run the script with controlled input.
- **Security of privileged scripts.** `sudo` scripts need a fixed `PATH`, no use of untrusted environment variables, and care with temporary files; see the sudo and PAM courses later in the path.
- **Portability.** `dash` and BusyBox `ash` run POSIX only; `checkbashisms` and ShellCheck's `shell=sh` mode find what breaks.
- **Idempotence.** Strict mode prevents running on after an error; idempotent steps make the re-run safe.
- **Logging and exit codes.** Distinct codes and messages on standard error make failures diagnosable by callers, including systemd and CI.
- **Code review habits.** A short checklist and an automated linter make reviews faster than reading for quoting by eye.

## Active research

The programming-languages community studies shell as a language: formal semantics for POSIX shell, verified parsers, and symbolic execution of scripts to prove properties such as a script never deleting outside its own directory. Tools that check scripts at scale have found that a significant fraction of scripts in package repositories contain quoting or error-handling faults, which motivates automated repair that applies safe fixes of the kind ShellCheck's diff output already offers. Alternative shells that fix the error semantics while accepting most existing scripts (with a strict mode that is a first-class feature, not a set of options) are under development, and several teams explore typed or structured-data shells.

## Future direction

Expect shell hygiene to move from convention to enforcement: linting and formatting as pre-commit and CI gates, strict-mode headers generated from templates, and larger scripts replaced by Python or a compiled tool where the language's limits bite. The skills in this slice stay useful regardless: knowing when each expansion splits, what `set -e` really guarantees, and how to read a ShellCheck finding. The course target is a student who can take an existing script, make it pass ShellCheck without changing its behaviour, and explain each change.
