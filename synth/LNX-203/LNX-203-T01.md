# Writing Bash that behaves: conditions, loops, functions and cleanup

## Define the problem

A Linux administrator spends the day running commands, and sooner or later the same sequence has to run again: on a hundred hosts, at three in the morning, or in an installer where nobody is watching. The shell is the natural place to automate it, because every tool the administrator already uses is a command. The difficulty is that an interactive shell forgives what a script cannot. A typo at a prompt is noticed at once; in a script it may be noticed a week later, when a variable was empty and a `rm -rf "$dir"/` removed more than intended. The language is built on text substitution rather than on typed values, exit statuses are the only error channel, and most of its quirks were set down before anyone wrote programs of thousands of lines in it.

This slice teaches the core of the language as a programming tool: how to test a condition and know what was tested, how to loop over files, lines and numbers without breaking on spaces, how to structure a script with functions and arguments, and how to clean up after a script that is interrupted. The next slice adds the safety discipline (strict mode, quoting, static analysis) and the one after that adds automated tests. The target is scripts that other people can read, run on a different distribution and trust at night.

## History and approaches

The first Unix shell, written by Ken Thompson, ran commands, redirected input and output, and not much more. Stephen Bourne's shell, which reached the world with the seventh edition of Unix in 1979, added the programming constructs still recognised today: `if`, `case`, `for`, `while`, here-documents, command substitution with backquotes and variables. The C shell (Bill Joy, late 1970s) offered a friendlier interactive experience and a syntax closer to C, but its scripting rules were awkward enough that the folklore advice was to avoid csh for scripts altogether. The Korn shell (David Korn, early 1980s) merged the interactive conveniences with the Bourne syntax and introduced arrays, arithmetic and the `$( )` form of command substitution. The POSIX standard, finished around 1992 and revised since, defined a portable subset based on the Bourne and Korn shells. Bash, begun by Brian Fox for the GNU project in 1989, implemented that subset and added extensions, such as arrays, `[[ ]]`, process substitution, associative arrays (version 4, 2009) and many more. The bash manual's own text lists each construct with its rules [src: man-pages eb2a3779521bbd45] [src: man-pages 049e840d08f1d01c].

Two traditions matured in parallel. One treated the shell as glue for portable scripts: write to the POSIX subset, test with a minimal shell such as `dash` (which several Debian-family distributions use as `/bin/sh` for speed), and avoid extensions. The other embraced bash on every machine and used its features to make scripts shorter and safer. Both are legitimate; the failure mode is mixing them, such as a script with a `#!/bin/sh` first line that uses arrays and breaks on Debian but works on RHEL, where `/bin/sh` is bash in compatibility mode. On macOS, an older bash version (3.2, frozen for licensing reasons) shows that "bash" itself is not a single target. Alternatives exist for tasks where the shell's weaknesses dominate: Python for data structures and error handling (see the Python slice), Perl in older environments, and configuration-management tools for convergent state. The practical rule is to stay in the shell when the work is mostly starting programs and moving their text, and to move to another language when you need nested data, many conditions or concurrency control.

## Current state

### Script anatomy and execution

A script starts with an interpreter line, `#!/usr/bin/env bash` or `#!/bin/bash`, so the kernel knows which program should run the file, and the file must have the execute bit (`chmod +x script.sh`). Running `bash script.sh` ignores the line and the bit. A script runs in a child process: changes it makes to the environment do not return to the parent, which is why `source file` (or `. file`) exists for files that should set variables in the current shell. Arguments arrive as `$1`, `$2`, and so on, `$#` is the count, `"$@"` is every argument as a separate word, and `"$*"` is all arguments joined into one string. The special parameters include `$?` (the exit status of the last command), `$$` (the process ID), `$!` (the last background job) and `$0` (the script name) [src: man-pages a48e3e34536e0e94].

Exit status is the contract between a command and its caller: zero means success and any other value, up to 255, means failure, with conventions such as 126 (found but not executable), 127 (not found) and 128 plus N (killed by signal N). Every test, loop condition and `&&`/`||` list in the shell is built on this.

### Tests

The shell has three ways to test a condition, and knowing which one you are using prevents most beginner bugs.

- **`test` and `[ ]`** are a command (a builtin and an external program) that takes arguments, which is why the spaces inside the brackets matter and why an unquoted empty variable breaks the expression: `[ $x = y ]` becomes `[ = y ]`. Operators include file tests (`-e` exists, `-f` regular file, `-d` directory, `-r -w -x` permissions, `-s` not empty, `-L` symbolic link), string tests (`-z` empty, `-n` not empty, `=` and `!=`) and integer comparisons (`-eq -ne -lt -le -gt -ge`). They are portable to every POSIX shell.
- **`[[ ]]`** is a bash keyword, not a command, so it does no word splitting or globbing on unquoted variables inside, supports `&&` and `||` within the brackets, pattern matching on the right of `==` (`[[ $f == *.log ]]`), and regular-expression matching with `=~` (the captured groups are placed in the array `BASH_REMATCH`). The bash manual lists its operators in the section on conditional expressions [src: man-pages 049e840d08f1d01c].
- **`(( ))`** evaluates an arithmetic expression and succeeds if the result is non-zero: `(( count > 10 ))`. Inside, variables need no `$`. `$(( ))` returns the value for use in a larger expression.

Beyond these, any command can be the condition: `if grep -q pattern file; then`, because the test is simply the exit status. `case` matches a word against glob patterns and is the cleanest way to dispatch on a string:

```bash
case "$1" in
    start|up)   do_start ;;
    stop)       do_stop ;;
    *.conf)     echo "config file given" ;;
    *)          echo "usage: $0 start|stop" >&2; exit 2 ;;
esac
```

The rocky-linux course on bash walks through `if`, `elif`, `else` and `case` with worked examples [src: rocky-docs a701d44162b60533]. Short-circuit lists are a compact form: `mkdir -p "$dir" && cd "$dir"`, and `command || { echo "failed" >&2; exit 1; }`. A trap for beginners is `a && b || c`, which is not an if-else: if `b` fails, `c` also runs.

### Loops

Four loop forms cover nearly all needs:

```bash
for host in web1 web2 db1; do ping -c1 "$host" >/dev/null && echo "$host up"; done
for f in /var/log/*.log; do [ -e "$f" ] || continue; gzip -k "$f"; done
for ((i = 1; i <= 5; i++)); do echo "$i"; done
while IFS= read -r line; do printf '%s\n' "$line"; done < input.txt
```

The first iterates over a list of words, and the second over a glob, which expands to the pattern itself when nothing matches (hence the `[ -e "$f" ] || continue` guard, or `shopt -s nullglob`). The third is arithmetic. The fourth is the standard way to read lines: `IFS=` stops trimming of leading and trailing white space, and `-r` stops backslash processing. Two pitfalls are common. First, piping into `while` runs the loop in a subshell in most configurations, so variables set inside it are lost (`cmd | while read ...` versus `while read ...; done < <(cmd)` with process substitution). Second, `for f in $(ls)` splits on white space and breaks on spaces in file names; use a glob or `find ... -print0` with `while IFS= read -r -d ''`. `until` is the same as `while` with the test reversed and fits "retry until this works" loops; `break` leaves a loop (with a number it leaves outer loops) and `continue` skips to the next iteration [src: rocky-docs 5acb7e4aeddfee10] [src: rocky-docs 15ab71941b7cc867]. A retry loop with a limit is a standard construction:

```bash
for attempt in 1 2 3 4 5; do
    curl -fsS "$url" -o out.json && break
    sleep $((attempt * 2))
done
```

### Functions and arguments

A function is declared with `name() { ...; }` and called like a command. Arguments are `$1`... inside it, and `local` limits variables to the function (without it they are global, an easy way to leak state). A function returns a status with `return N` (0 to 255) and returns data by writing to standard output, which the caller captures with `$( )`. Functions can be defined before the "main" code and the script ends with `main "$@"`, which keeps the top-level tidy and makes the file source-able for testing. The bash manual's section on functions states the rules, including that the function body is a compound command and that `return` outside a function or sourced script is an error [src: man-pages eb2a3779521bbd45].

For options, `getopts` handles short flags with arguments portably:

```bash
while getopts ":hv:n" opt; do
    case $opt in
        h) usage; exit 0 ;;
        v) level=$OPTARG ;;
        n) dry_run=1 ;;
        :) echo "option -$OPTARG needs a value" >&2; exit 2 ;;
        \?) echo "unknown option -$OPTARG" >&2; exit 2 ;;
    esac
done
shift $((OPTIND - 1))
```

Long options (`--verbose`) need hand-written `case` loops or the external `getopt` from util-linux, whose behaviour differs between implementations.

### Variables, arrays and expansions

Parameter expansion is the shell's built-in string toolkit: `${var:-default}` (use a default), `${var:=default}` (assign it), `${var:?message}` (abort with a message if unset or empty), `${var#prefix}` and `${var##prefix}` (remove the shortest or longest matching prefix), `${var%suffix}` and `${var%%suffix}` (the same for suffixes), `${var/pat/repl}` (replace), `${#var}` (length), `${var^^}` and `${var,,}` (upper and lower case in bash 4 and later). Indexed arrays (`arr=(a b c)`, `"${arr[@]}"`, `${#arr[@]}`) keep words intact where a plain string would split them, and associative arrays (`declare -A map; map[key]=value`) provide lookups in bash 4 and later. `mapfile -t lines < file` reads a file into an array. The expansion rules, including the order in which expansions occur and what splits on what, are the heart of the bash manual and the source of most quoting bugs (covered in the next slice) [src: man-pages a4a6fb605c73a527].

Here-documents (`<<'EOF'` with quotes prevents expansion) generate multi-line text; command substitution `$(cmd)` strips trailing newlines; `printf` is more predictable than `echo` for output with formats or leading dashes; and `mktemp` creates temporary files or directories without race conditions.

### Traps and cleanup

`trap 'commands' SIGNAL...` registers a handler. The pseudo-signal `EXIT` runs on any exit, including after `exit`, a fatal error or a received `TERM` (provided the handler ends the script rather than continuing), which makes it the right place for cleanup. `ERR` runs when a command fails (subject to the same exceptions as `set -e`), and `DEBUG` and `RETURN` exist for tracing. `trap - EXIT` removes a handler. Signals that need special treatment are `INT` (Ctrl-C) and `TERM` (the default signal of `kill`); `KILL` and `STOP` cannot be trapped. The builtin commands section of the bash manual defines `trap` and its signal names [src: man-pages 22281786621f8b28].

```bash
#!/usr/bin/env bash
tmp=$(mktemp -d) || exit 1
cleanup() { rm -rf -- "$tmp"; }
trap cleanup EXIT
trap 'echo "interrupted" >&2; exit 130' INT TERM
# ... work in "$tmp" ...
```

Note the exit code 130 convention (128 plus signal 2) and the `--` that ends option parsing in `rm`. Lock files and background jobs are cleaned the same way: store the process IDs and kill them in the handler. `wait` waits for background jobs, `$!` gives the last one, and `wait -n` (bash 4.3 and later) returns when any job ends, which gives a simple bounded parallelism pattern.

### Debugging

`bash -x script.sh` (or `set -x` in a region) prints each command after expansion, prefixed by `PS4` (default `+ `); setting `PS4='+ ${BASH_SOURCE}:${LINENO}: '` adds the file and line. `bash -n script.sh` parses without running. `set -v` prints lines as read. For long-running scripts, `logger -t myscript "message"` writes to the system log (journald) and is easier to follow than redirected files.

## Assessment: the good, the bad and the ugly

**The good.** The shell is everywhere, needs no installation and composes with every Unix tool. For a short script that starts programs, tests their status and moves text between them, it is the shortest and most readable form. Functions, arrays, parameter expansion and traps are enough to structure scripts of a few hundred lines in a way that other people can read. Exit statuses give a uniform, if minimal, error protocol, and `bash -x` is a surprisingly good debugger.

**The bad.** Everything is a string, and the shell parses text again after substitution; missing quotes turn data into code or into the wrong number of words. Error handling is opt-in: by default a failed command is ignored and the script continues. Portability is partial: bash features break under `dash`, and utilities differ between GNU and BSD implementations (`sed -i`, `date -d`, `readlink -f`). Data structures are weak, with no nested arrays and awkward handling of binary data or null bytes. The behaviour of `set -e` has so many exceptions that experienced authors treat it as a safety net, not a control mechanism.

**The ugly.** Scripts live far longer than intended. A fifty-line helper becomes a deployment system with thousands of lines, no tests and a bus factor of one. Parsing human-oriented output (`ls`, `ps`, `df`) with `awk` and `cut` is fragile and breaks when locale, column widths or the tool version changes. Security issues hide in quoting mistakes (injection through file names and variables), temporary files in predictable paths, and `sudo` calls that pass untrusted input. Cleanup is skipped on `kill -9`, leaving locks and half-written files, so scripts that matter must be idempotent and restartable.

## Applications beyond this domain

The same constructs run in many other places. Container builds use shell in `RUN` lines and entrypoint scripts, where `exec "$@"` hands over the process ID. Continuous-integration systems run shell steps, and their failures follow the same exit-status rules. Package maintainer scripts (`%post` in RPM, `postinst` in Debian) are shell with extra constraints, such as running as root during installation and needing to be idempotent. systemd units start commands through `ExecStart=`, which does not use a shell unless asked, so shell features need an explicit `sh -c`. Kubernetes probes, init containers and CronJobs run shell commands. Ansible's `shell` and `command` modules wrap the same commands and expose the exit status as `rc`. The testing slice in this course shows how to test shell with `bats`, and the final slice turns scripts into services and timers.

## Examples

**1. A safe, readable skeleton.**

```bash
#!/usr/bin/env bash
set -euo pipefail
usage() { echo "usage: ${0##*/} [-n] host..." >&2; exit 2; }
dry_run=0
while getopts ":n" o; do case $o in n) dry_run=1 ;; *) usage ;; esac; done
shift $((OPTIND - 1))
[ $# -gt 0 ] || usage
main() {
    local host
    for host in "$@"; do
        if (( dry_run )); then echo "would check $host"; else ping -c1 -W2 "$host" >/dev/null && echo "$host up" || echo "$host DOWN"; fi
    done
}
main "$@"
```

**2. Read a table of users and act on each line.**

```bash
while IFS=: read -r name _ uid _ _ home shell; do
    (( uid >= 1000 )) || continue
    [ -d "$home" ] || echo "missing home for $name"
done < /etc/passwd
```

**3. Retry with backoff and a cap.**

```bash
retry() {  # retry N command...
    local n=$1 i; shift
    for ((i = 1; i <= n; i++)); do "$@" && return 0; sleep $((i * 2)); done
    return 1
}
retry 4 curl -fsS https://example.org/health
```

**4. Cleanup that always runs.**

```bash
lock=/var/lock/job.lock
exec 9>"$lock"
flock -n 9 || { echo "already running" >&2; exit 1; }
tmp=$(mktemp -d); trap 'rm -rf -- "$tmp"' EXIT
```

**5. Bounded parallelism.**

```bash
max=4
for h in "${hosts[@]}"; do
    ssh -o BatchMode=yes "$h" uptime &
    (( $(jobs -rp | wc -l) >= max )) && wait -n
done
wait
```

**6. A test that fails loudly.**

```bash
need() { command -v "$1" >/dev/null || { echo "missing tool: $1" >&2; exit 127; }; }
need jq; need curl
```

## Related problems and ideas

- **Quoting and strict mode.** The next slice covers the practices that make everything above safe.
- **Text processing.** `awk`, `sed`, `jq` and `yq` take over once the logic needs fields or structure (slice 4).
- **Idempotence.** A script that can run twice without harm is easier to schedule and to recover; use checks before changes (`[ -e ] ||`, `mkdir -p`, `ln -sfn`).
- **Concurrency.** `flock`, background jobs with `wait`, and `xargs -P` or GNU `parallel` for fan-out.
- **Interactive versus non-interactive shells.** Startup files, `PATH` in cron, and `set +o history` differences cause faults where a command works at the prompt yet fails under cron.
- **Process management.** Signals, `exec`, subshells versus braces, and `disown` link scripts to the process model in the operating-system courses.

## Active research

Research and engineering work around shell is mostly about making it safer without replacing it. Static analysis (see the next slice) and formal descriptions of shell semantics, including executable specifications of POSIX shell and verified parsers, show that the language can be given a precise meaning even though the original grammar was informal. Newer shells (Oils, with its OSH and YSH variants, and others) try to keep compatibility while repairing quoting and error semantics. Projects that translate shell to safer languages, and tools that trace scripts to find which commands read and write which files for parallelisation or build caching, are active in the systems community. Containers and immutable images have reduced how much shell is needed on running hosts, but the build-time and operations use remains.

## Future direction

Bash will remain the default scripting language for Linux operations, because it is installed, compatible and sufficient for glue. The direction of improvement is practice rather than syntax: scripts that declare their requirements, run under static analysis and tests in continuous integration, and are replaced by a more structured language when they outgrow a few hundred lines. For this course the aim is that a student can write a script of that size with correct tests, loops, functions and cleanup, explain each exit status path, and know when to stop writing shell.
