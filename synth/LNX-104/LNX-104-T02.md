# Managing Debian-family systems: dpkg, apt, sources, pinning and holds

## Define the problem

A Debian or Ubuntu host takes its software from archives published by the distribution and, often, by third parties. Three recurring questions decide whether that host stays predictable. Where does a given package come from, and is that source the one intended? When two archives offer different versions of the same package, which one wins, and how does an administrator change the winner? And how does a package stay at the version that has been tested, while the rest of the system moves forward? Without answers, a routine `apt upgrade` can replace a database server with a major version nobody validated, or pull a library from a backports archive into a system that was meant to follow only stable.

The Debian toolchain splits the work in two layers, as RPM systems do. `dpkg` is the low-level program that unpacks `.deb` files, runs maintainer scripts and records what is installed; it does not fetch anything or resolve dependencies. `apt` (with its older companions `apt-get` and `apt-cache`) reads the configured sources, downloads package indexes, chooses versions according to priorities, resolves dependencies and calls `dpkg` to do the installation [src: debian-handbook 933b29fec88d275f]. This slice covers both layers as used on Debian 12 and 13, Ubuntu 22.04 and 24.04, and derivatives: how sources are declared, how versions are chosen and pinned, how a package is held, and how to inspect and repair the state. Repository trust (keys and signatures) gets its own topic and is only mentioned here where the source syntax requires it.

## History and approaches

`dpkg` appeared in 1993 as a shell script by Ian Murdock and was rewritten in Perl and then in C by Ian Jackson and others. It established the model Debian still uses: a package is an `ar` archive containing `control.tar` (metadata and maintainer scripts `preinst`, `postinst`, `prerm`, `postrm`, plus `conffiles` and `md5sums`) and `data.tar` (the files). Debian's policy documents the version syntax, `[epoch:]upstream_version[-debian_revision]`, and the rules for comparing versions, which `dpkg --compare-versions` implements.

The missing piece, as on RPM systems, was dependency resolution and download. Early on, `dselect` provided a full-screen selection interface and a method for fetching; it was powerful and widely disliked. APT (the Advanced Package Tool), developed from 1998 by Brian White, Jason Gunthorpe and others for Debian 2.1, replaced it for most users. APT's decisive ideas were a shared package-index format (`Packages` files), a solver that treats the installed system plus the request as a set of constraints, and a pin and priority system that lets one machine follow several archives at once. The same engine was later reused by other distributions, including a port that served RPM systems (`apt-rpm`).

Several approaches coexisted and competed. `aptitude` offered a better interactive solver and tracked automatic versus manual installation; APT eventually absorbed that idea, and `apt-mark` and the `APT::Get::AutomaticRemove` machinery now do it. The `apt` command (introduced in 2014 with APT 1.0) combined the most common `apt-get` and `apt-cache` verbs with progress bars and friendlier defaults, but stayed deliberately unstable in output format; scripts are advised to use `apt-get`, `apt-cache`, `dpkg-query` and similar tools. For sources, the one-line format in `/etc/apt/sources.list` was the rule for twenty years. Its limits were clear: no way to attach a key to one source (every trusted key applied to all of them), no per-source options without a bracket syntax, and awkward multi-suite entries. APT 1.1 introduced the deb822 format in `.sources` files, with `Signed-By:` binding a key to a source; apt 2.x deprecated the global `apt-key` trusted keyring in favour of per-source keys, and Debian 13 and Ubuntu 24.04 ship deb822 as the default [src: kubernetes-docs 66b7c329a52779f7].

Pinning has had a mixed record. It was designed for a good purpose, mixing stable with a few newer packages, but Debian's own documentation has long warned against building a system from several suites by pinning, because dependencies drag in huge numbers of packages. The lesson that emerged is to use pinning narrowly, typically for one package or one source, and to prefer backports or separate containers for broad needs. The overall pattern is evolution from loose conventions toward explicit, per-source, machine-readable declarations.

## Current state

### dpkg: the database and the verbs

The installed-state database lives in `/var/lib/dpkg/`: `status` (one stanza per package with fields `Package`, `Status`, `Version`, `Architecture`, `Depends`, `Conffiles`, `Description` and more), `available`, `info/` (per-package `.list`, `.md5sums`, `.conffiles` and maintainer scripts) and `lock` and `lock-frontend`. The main commands are:

```bash
dpkg -i foo_1.0_amd64.deb         # install or upgrade a local file (does not fetch dependencies)
dpkg -r foo                       # remove, keep configuration
dpkg -P foo                       # purge: remove including configuration
dpkg --configure -a               # finish interrupted configuration of unpacked packages
dpkg -l 'lib*ssl*'                # list: first column "ii" installed, "rc" removed but config left, "hi" held
dpkg -L foo                       # files owned by a package
dpkg -S /usr/bin/ssh              # which package owns this file
dpkg -s foo                       # status stanza (also dpkg-query -s)
dpkg -C                           # audit: find packages left half-installed
dpkg -V foo                       # verify installed files against the md5sums (dpkg 1.17+)
dpkg --get-selections             # state selections; dpkg --set-selections applies them
dpkg --print-architecture         # native architecture; --add-architecture i386 adds a foreign one
dpkg --compare-versions 1:2.0-1 gt 1.9-5 && echo newer
dpkg-query -W -f='${Package}\t${Version}\t${Status}\n' 'openssl*'
dpkg-divert --add --rename --divert /usr/bin/foo.real /usr/bin/foo
dpkg-reconfigure tzdata           # rerun the package's debconf configuration
```

The `-l` listing is selected with the `dpkg-query` family, which also supports a custom `-W -f` format; the `${...}` field names match the control fields, and the man page lists the full set [src: man-pages ab0fd4c32dfd6f36]. `dpkg` does not understand repositories; if `dpkg -i` complains about unmet dependencies the usual follow-up is `apt-get -f install` (or `apt install -f`), which lets APT fetch the missing pieces. Configuration file prompts during upgrades can be answered in advance with `--force-confdef` (take the default if one exists) and `--force-confold` (keep the local file), options that unattended upgrades rely on [src: debian-handbook 7e17c1113b9c089d]. Exit codes and `--force-*` options are numerous; `dpkg --force-help` lists them, and most of them (such as `--force-depends` or `--force-overwrite`) should be avoided outside rescue work.

### apt: configuration and commands

APT reads `/etc/apt/apt.conf` and the drop-in directory `/etc/apt/apt.conf.d/`, where each file contributes configuration items written in a C-like syntax, for example `APT::Install-Recommends "false";`, `APT::Get::Assume-Yes "true";`, `Acquire::http::Proxy "http://proxy.example:3128";`, `Acquire::Retries "3";` and `Dpkg::Options { "--force-confold"; };`. The tool `apt-config dump` prints the effective configuration. Day-to-day verbs:

```bash
apt update                        # refresh package indexes from every source
apt list --upgradable             # candidates for upgrade
apt upgrade                       # upgrade without installing new or removing packages
apt full-upgrade                  # (apt-get dist-upgrade) may add and remove to satisfy dependencies
apt install nginx                 # latest candidate version
apt install nginx=1.24.0-2ubuntu7 # a specific version
apt install -t bookworm-backports foo   # take foo from a given release or suite
apt install --no-install-recommends foo # skip Recommends:
apt remove foo | apt purge foo | apt autoremove [--purge]
apt show foo                      # description, Depends, Recommends, Suggests, sizes
apt search 'web server'; apt-cache search -n nginx
apt-cache policy foo              # installed, candidate and every version with its priority
apt-cache depends foo; apt-cache rdepends --installed foo
apt-get -s install foo            # simulate (also apt install --simulate)
apt-get download foo; apt changelog foo
apt-mark showmanual; apt-mark auto foo; apt-mark manual foo
```

`apt-cache policy` is the single most useful command for diagnosing version choices: it shows, for each package, the installed version, the candidate (the version `apt install` would choose) and the priority and origin line of each available version [src: debian-handbook 933b29fec88d275f]. Locks protect the database: `/var/lib/dpkg/lock-frontend`, `/var/lib/dpkg/lock`, `/var/lib/apt/lists/lock` and `/var/cache/apt/archives/lock`. A "Could not get lock" message normally means another `apt`, `dpkg` or the unattended upgrade timer is running; check with `fuser` or `lsof` before deleting a lock file.

### Sources

Sources are declared either as one-line entries or in deb822 stanzas. One-line form in `/etc/apt/sources.list` or `/etc/apt/sources.list.d/*.list`:

```
deb [signed-by=/etc/apt/keyrings/example.gpg arch=amd64] https://deb.example.org/apt stable main
deb-src http://deb.debian.org/debian bookworm main
```

The deb822 equivalent in `/etc/apt/sources.list.d/example.sources` has the fields `Types:` (`deb`, `deb-src`), `URIs:`, `Suites:`, `Components:`, `Architectures:`, `Signed-By:` and optionally `Enabled: no`. Suites are archive paths below `dists/`: release names (`bookworm`, `noble`), aliases (`stable`), and pockets such as `bookworm-updates`, `bookworm-security`, `bookworm-backports`, `noble-updates` and `noble-security`. Components are `main`, `contrib`, `non-free` and `non-free-firmware` on Debian, and `main`, `universe`, `restricted` and `multiverse` on Ubuntu. At `apt update`, APT downloads and verifies `InRelease` (or `Release` plus `Release.gpg`), then the `Packages` index for each component and architecture into `/var/lib/apt/lists/`. The `Release` file carries `Origin`, `Label`, `Suite`, `Codename`, `Date`, `Valid-Until`, `Architectures`, `Components` and checksums, and the `NotAutomatic` and `ButAutomaticUpgrades` flags that matter for pinning. Compliance baselines check that only official distribution repositories are configured, which is a sources review in practice [src: compliance-as-code b84372c67fd33124].

### Priorities and pinning

Every available version of a package gets an integer priority; APT installs the version with the highest priority, and among equals the highest version number. Defaults are 500 for an ordinary source, 990 for the source named by `APT::Default-Release` or `-t`, 100 for the installed version and for sources marked `NotAutomatic` (such as backports, flagged so that nothing upgrades from them unless asked), and 1 for sources flagged `NotAutomatic` with no `ButAutomaticUpgrades`. A priority of 1000 or more forces installation even when it means a downgrade, 100 to 999 is only chosen if no higher-priority candidate exists and the package is not installed, and a negative priority forbids the version [src: debian-handbook 4c6b7269d2f96a81].

Custom pins live in `/etc/apt/preferences` or `/etc/apt/preferences.d/<name>` (file names without a dot suffix, or with `.pref`). A stanza has three fields:

```
Package: nginx nginx-*
Pin: release n=bookworm-backports
Pin-Priority: 700

Package: *
Pin: origin "packages.example.org"
Pin-Priority: 100

Package: libssl3
Pin: version 3.0.*
Pin-Priority: 1001
```

Selectors for `Pin: release` use `a=` (archive, e.g. `stable`), `n=` (codename), `v=` (version), `c=` (component), `o=` (origin), `l=` (label); `Pin: origin` takes a host name; `Pin: version` takes a version glob. Test every change with `apt-cache policy <pkg>`, because small mistakes (a missing blank line, two stanzas matching) are common and silent. A conservative recipe for adding a backport: leave backports at its default low priority and install a chosen package with `apt install -t bookworm-backports foo`; this pulls only the dependencies that need newer versions.

### Holds

A **hold** tells `dpkg` and `apt` not to upgrade, remove or reinstall a package until the hold is released. The preferred commands are `apt-mark hold foo`, `apt-mark unhold foo` and `apt-mark showhold`; they set the dpkg selection to `hold`, visible as `hi` in `dpkg -l` (equivalent to `echo "foo hold" | dpkg --set-selections`). Holds are simple and blunt: a held package can block `apt full-upgrade` when a dependent package needs a newer version, and the hold hides security updates. Pinning with a priority of -1 on future versions, or a version-specific pin, gives finer control but the same trade-off. Package managers on both families expose this as "version lock": `dnf versionlock` has the same intent. For unattended upgrades, `/etc/apt/apt.conf.d/50unattended-upgrades` defines `Unattended-Upgrade::Allowed-Origins`, `Package-Blacklist`, `Automatic-Reboot` and mail settings, and `20auto-upgrades` turns the periodic jobs (`APT::Periodic::Update-Package-Lists`, `APT::Periodic::Unattended-Upgrade`) on.

## Assessment: the good, the bad and the ugly

What works well: the two-layer design makes failures easy to localise; `Packages` indexes and `apt-cache policy` expose the decision inputs; pinning and `-t` allow mixing archives without hand-editing; the deb822 format with `Signed-By` limits the damage a stolen or wrong key can do; and unattended upgrades with a security-only origin list keeps fleets patched with very little effort.

What works badly: the `apt` front end changes output between releases and warns that it is not stable for scripting. Pinning syntax is easy to get wrong and fails silently. Holds are global and invisible in normal listings unless you look for them. Maintainer scripts can prompt, so non-interactive runs need `DEBIAN_FRONTEND=noninteractive` and the `--force-conf*` options, and a prompt that fails halts a whole upgrade. Package indexes can lag behind mirrors, and a mirror that is mid-sync yields "hash sum mismatch" errors. Third-party repositories frequently publish their own `Packages` for a stable suite name, so they can replace distribution packages whenever their priority or version is higher.

The ugly parts: mixed-suite systems built by pinning create the "frankendebian" problem, where upgrading in either direction becomes unsafe. The old `apt-key` interface left a global trust store that is being phased out in stages, with deprecation warnings in recent releases and removal planned (to verify per release). `dpkg -V` is weaker than RPM verification because it only checks the md5 sums recorded in the package, and sums are not recorded for every file. Locks left behind by a crashed process, a dpkg database stuck with half-configured packages, and conffile prompts in remote sessions are the failures operators meet most often. On Ubuntu, `snap` packages installed by `apt` stubs (for instance the browser packages) blur the line between `apt` and another packaging system.

## Applications beyond this domain

The ideas reach well outside Debian. Priority-based version selection reappears in RPM's repository `priority=` and `dnf versionlock`, in pip constraints files and npm lockfiles, and in Kubernetes release channels. A source definition with an attached trust anchor (`Signed-By`) is the pattern used by container registries with signature policies, language ecosystem trusted publishers and firmware update channels. Holds are the same concept as version freezes in `Cargo.lock`, `requirements.txt` hashes and image digests in deployment manifests, and the pinning of base images in `Dockerfile` `FROM` lines or `apt-get install pkg=version` in container builds, where reproducibility matters more than being current [src: docker-docs 0641849f0a3e1b34]. `apt-get` and `dpkg` are also the core of Debian-based images, installers (`debootstrap`, `mmdebstrap`), live systems and embedded build systems.

## Examples

**Adding a vendor repository, safely.** The Kubernetes project documents installing its packages by creating a keyring directory, downloading the signing key, and writing a one-line source that names the key with `signed-by`, then running `apt update` and installing the tools [src: kubernetes-docs 66b7c329a52779f7]. The same pattern works for any vendor: store the dearmored key under `/etc/apt/keyrings/`, bind it to only that source, and avoid trusting it for the rest of the system. The same project publishes repositories per minor release, so switching minor versions means editing the source line, not just upgrading [src: kubernetes-docs 34d9f146d7cab195].

**Holding a pre-validated package.** An operations team has tested `containerd.io 1.7.x` with their cluster and wants kubelet and the container runtime to stay put during the nightly security job. They run `apt-mark hold kubelet kubeadm kubectl containerd.io` after installation, confirm with `apt-mark showhold`, and unhold deliberately during planned upgrade windows. The Kubernetes installation guide recommends the same hold for its own packages [src: kubernetes-docs a7c4e1f527ffcadb].

**A pin that goes wrong.** A server tracks `stable` and an admin adds a stanza with `Package: *` and `Pin: release a=testing` at priority 900 to get one newer tool. The next `apt upgrade` starts replacing libc and dozens of libraries with versions from testing. The correct response is to stop, run `apt-cache policy libc6`, see that the testing candidate has priority 900 against 500 for stable, remove the stanza, and use `apt-get -s dist-upgrade` to review the downgrade plan before executing it. Prevention is a narrow `Package:` line and a low priority such as 100, plus installing the needed version with `-t`.

**Finishing a broken install.** After a power loss, `apt install` reports half-configured packages. `dpkg --configure -a` completes configuration, `apt-get -f install` repairs dependencies, `dpkg -C` confirms nothing is left, and `apt-get check` verifies the dependency graph.

**A reproducible image.** In a Dockerfile, `apt-get update && apt-get install -y --no-install-recommends curl=7.88.1-10+deb12u8` followed by removal of the lists directory is a conventional layer: the update and install run together so that a stale cached index is not reused, and the version is pinned for repeatability [src: docker-docs 0641849f0a3e1b34].

## Related problems and ideas

Related issues include dependency hell and its repair (the dependency troubleshooting topic), trust and key management (the repositories topic), mirroring and snapshotting archives (`apt-mirror`, `debmirror`, `aptly`, and the Debian snapshot service at `snapshot.debian.org`) and Ubuntu's Livepatch and Pro services for extended security maintenance. Alternatives include holding the whole OS at a point in time by using a dated snapshot archive as the only source; image-based Debian derivatives (`bootc`-style projects, Vanilla OS, `ostree` on Endless OS); and functional package managers such as Nix running on top of Debian. Ideas on the edge of mainstream include the `apt` `Phased-Update-Percentage` field that Ubuntu uses to roll out updates gradually, and archive snapshot selection from a source stanza, which recent APT 3.x releases are adding (to verify).

## Active research

Work in this area includes the APT 3.0 series, which introduced the new `solver3` dependency solver and structured output improvements; Debian's reproducible builds effort, which makes it possible to verify that a binary package corresponds to its source; the Debian `snapshot` and `debian-installer` teams; and the study of supply-chain risks in third-party repositories. Open questions include how to give users finer trust scopes than a key per source (for example, limiting a source to specific package names), how to bring reproducibility into everyday upgrades without freezing security fixes, and how to make `apt` output stable enough for tools without freezing its user interface.

## Future direction

Expect deb822 to become universal and one-line entries to be deprecated over several releases, the legacy `apt-key` to disappear in a coming release, and the new solver to become the default after a long testing period; both Debian and Ubuntu publish release notes with these dates, which are worth checking before major upgrades (to verify). Archive snapshot support and finer trust scopes will make "pinned in time" sources a first-class option. For administrators the durable habits are: inspect with `apt-cache policy` before and after any source or pin change, keep pins narrow and low, keep holds documented in a ticket or configuration management with an owner and an expiry, simulate with `-s` before large transactions, and keep unattended security updates running for everything that is not held.
