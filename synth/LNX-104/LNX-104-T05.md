# Building software from source and understanding shared libraries

## Define the problem

Sometimes the package you need does not exist, is too old, or lacks a compile-time option. The remaining route is to download the source, build it and install the result. That route is easy to start and easy to get wrong. A build needs the right compilers, headers and development libraries; an install needs a location that will not collide with files owned by packages; and the resulting program needs to find its libraries at run time. When any step fails the symptoms are cryptic: a configure script stops with a missing header, a link step reports an undefined reference, or a binary that compiled cleanly dies at start-up with an error about a shared object it cannot open.

Two things have to be learnt together. One is the build procedure and the discipline around it: keep source builds apart from the package manager's files, record what was installed, and prefer making a package to leaving loose files behind. The other is how the dynamic linker finds and chooses shared libraries, because nearly every program on a Linux system depends on dozens of them, and nearly every source-build problem that survives compilation turns out to be a library problem. This slice covers the common build systems (Autotools, CMake, Meson), the installation layout (`PREFIX`, `DESTDIR`, `/usr/local`, `/opt`), shared and static libraries and their naming, the search rules of the dynamic linker (`ld.so`), the tools that inspect them (`ldd`, `readelf`, `ldconfig`, `pkg-config`), and the options for turning a source build into a package. Packaging details for specific formats belong to later courses.

## History and approaches

In the early Unix era, programs shipped with a hand-written `Makefile` that the user edited for their system. Variation between Unix flavours (different system calls, library names and header locations) made this unworkable, and the GNU project responded with **Autoconf** (1991, David MacKenzie) and **Automake**: the developer writes a short description, and the tools generate a `configure` script that probes the system and a portable `Makefile`. The familiar sequence of `./configure`, `make` and `make install` came from this. **Libtool** was added to hide the radical differences in how shared libraries are built on different platforms; a training course on Autotools describes it as a tool created to abstract those differences [src: bootlin-training 3ddb1beb727f2bf6].

Autotools solved portability at a price: slow configure runs, a macro language few developers enjoy and generated files that obscure the real logic. **CMake** (from Kitware, 2000) offered a declarative description that generates Makefiles or Ninja files, and became the default for C and C++ libraries. **Meson**, with Ninja as its backend, was created in 2013 to be faster and easier to read, and projects such as GNOME and systemd adopted it. Language-specific build tools (Cargo for Rust, Go modules, Python's `pip` and `pyproject.toml`) took over inside their ecosystems, with their own ideas about dependencies [src: rust-book f5d1d294f12663f9].

The installation question had its own history. Early administrators ran `make install` into `/usr`, mixing their files with the system's. When the next package upgrade overwrote or conflicted with them, the practice of putting local software under `/usr/local` became standard, with `/opt` for self-contained bundles. A partial success, `checkinstall` and later `fpm` and `stow`, tracked what an install wrote so it could be removed. A failure remained: `make uninstall` is not provided or not reliable in many projects. The lesson that emerged is to treat a source build as a way to create a package: build into a staging directory, and install the staged tree with the package manager. Both major distributions encode this: RPM builds from a spec file with sections for preparation, build and install that run in a clean build root [src: man-pages 18f69e3584a68d82] and Debian source packages build with `debhelper` and record library dependencies automatically [src: debian-handbook e783c09948a4470b].

On the shared library side, early Unix used static archives only. Shared libraries arrived in the late 1980s to save memory and allow updates without relinking. Linux first used the `a.out` format with a fragile address-assignment scheme, then moved to ELF with the dynamic loader `ld.so` and later `ld-linux.so.2`, with versioned sonames to allow incompatible versions to coexist. The recurring failure mode, known as "DLL hell" on other systems, is dealt with on Linux by versioning conventions and by the package system's dependency tracking. The emerging pattern: automated build descriptions, install into a staging area, and package the result.

## Current state

### The build procedure

A source build has four stages: fetch and verify, configure, compile and install.

```bash
# 1. fetch and verify
curl -LO https://example.org/foo-1.4.2.tar.xz
curl -LO https://example.org/foo-1.4.2.tar.xz.asc
gpg --verify foo-1.4.2.tar.xz.asc foo-1.4.2.tar.xz       # check the signature (key fetched separately)
sha256sum -c foo-1.4.2.sha256                             # or compare with a published checksum
tar -xf foo-1.4.2.tar.xz && cd foo-1.4.2

# 2. build dependencies (distribution packages, not source)
sudo dnf builddep foo                       # RPM: from the spec of the distribution's own foo package
sudo dnf install gcc make pkgconf-pkg-config  # or: dnf group install "Development Tools"
sudo apt build-dep foo                      # Debian: needs deb-src sources enabled
sudo apt install build-essential pkg-config

# 3. configure, compile, test
./configure --prefix=/usr/local             # Autotools; ./configure --help shows options
make -j"$(nproc)"
make check                                  # run the test suite if the project has one

# 4. install
sudo make install                           # or: make DESTDIR=/tmp/stage install
```

The fourth stage is where discipline matters. `make DESTDIR=/tmp/stage install` writes the whole install tree under a staging directory instead of the live filesystem, which is exactly what package builders do. `PREFIX` (or `--prefix=`) decides the path that gets compiled into the program, whereas `DESTDIR` only moves where files land during install. On the Rocky Linux systems-administration lab, building from source is taught as a complete exercise from unpacking to running [src: rocky-docs 7985fd9b86608351], and the prerequisites for a larger build, such as the toolchain and library headers, are listed in the kernel-building guide [src: rocky-docs c4fbe567c967187d].

CMake and Meson follow the same idea with different commands:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=/usr/local
cmake --build build -j
ctest --test-dir build
DESTDIR=/tmp/stage cmake --install build

meson setup build --prefix=/usr/local --buildtype=release
meson compile -C build
meson test -C build
DESTDIR=/tmp/stage meson install -C build
```

The compiler driver `gcc` (or `cc`) does preprocessing, compiling, assembling and linking; the RHEL guide to developing C and C++ applications explains the stages and basic options [src: rhel-10-docs c8c742e578d00a41]. The options that matter for library problems are `-I<dir>` (where to find headers), `-L<dir>` (where the linker looks for libraries at link time), `-l<name>` (link `libname.so` or `libname.a`), `-fPIC` and `-shared` (build a shared object), `-Wl,-soname,libfoo.so.1` (set the soname), and `-Wl,-rpath,<dir>` (embed a run-time search path). Packages ship their headers in separate **development** packages (`foo-devel` on RPM systems and `libfoo-dev` on Debian systems), which is why a missing header normally means a missing `-devel` or `-dev` package. `pkg-config --cflags --libs foo` reads the `.pc` file that a development package installs (in `/usr/lib64/pkgconfig`, `/usr/share/pkgconfig` or a path given by `PKG_CONFIG_PATH`) and prints the right flags.

### Shared libraries: names and files

A shared library appears under three names. The **real name** is the file with the full version, for example `libfoo.so.1.4.2`. The **soname** is what is recorded in the file's dynamic section and in every program linked against it, for example `libfoo.so.1`; it changes only when the library's binary interface breaks. The **linker name** is the unversioned `libfoo.so`, a symlink used at build time when you write `-lfoo`, normally shipped in the development package. `ldconfig` creates the soname symlinks from the real files and maintains the cache. Static libraries (`libfoo.a`, an `ar` archive of object files) are copied into the executable at link time and need no run-time lookup.

The ABI promise is carried by the soname and, in many libraries, by **symbol versioning** (version scripts, so a library can offer several versions of one function). Debian tooling tracks this precisely: `dpkg-shlibdeps` computes shared library dependencies of a package from the binaries it contains [src: man-pages 6512fb07621da8a8], and symbols files list which library version first provided each symbol so that dependency lower bounds stay as loose as possible [src: man-pages e6267c92009d5efe]. RPM generates its own `Requires:` entries for sonames automatically, which is what lets `dnf` find the package supplying `libssl.so.3()(64bit)`.

### How the dynamic linker finds libraries

When a dynamically linked program starts, the kernel loads the interpreter named in its header (`/lib64/ld-linux-x86-64.so.2` on x86-64), which reads the list of needed libraries (the `NEEDED` entries), finds each by soname and maps it. The search order, as documented in `ld.so(8)`, is: the `DT_RPATH` of the executable (only if there is no `DT_RUNPATH`), the `LD_LIBRARY_PATH` environment variable, the `DT_RUNPATH` of the executable, the cache `/etc/ld.so.cache`, and finally the default directories `/lib` and `/usr/lib` (or `/lib64` and `/usr/lib64`). Set-user-ID programs ignore `LD_LIBRARY_PATH` for safety. The cache is built by `ldconfig` from the directories named in `/etc/ld.so.conf` and the files in `/etc/ld.so.conf.d/*.conf`, plus the default directories. On Debian family systems `/usr/local/lib` is already listed through a file in that directory; on Red Hat family systems it normally is not, so a library installed there is invisible until a `.conf` file names the directory and `ldconfig` runs (to verify on the release in use).

```bash
ldd /usr/bin/foo                # list libraries a binary needs and where each was found; "not found" is the problem
readelf -d /usr/bin/foo | grep -E 'NEEDED|SONAME|RPATH|RUNPATH'
objdump -p /usr/bin/foo | grep -E 'NEEDED|RUNPATH'
nm -D --defined-only /usr/lib64/libfoo.so.1 | head      # exported symbols (nm -D needs no debug info)
ldconfig -p | grep libfoo        # what the cache knows
sudo ldconfig                    # rebuild the cache (after adding a library or a .conf entry)
echo /usr/local/lib | sudo tee /etc/ld.so.conf.d/local.conf
LD_DEBUG=libs /usr/bin/foo 2>&1 | head -40   # trace the search
LD_LIBRARY_PATH=/opt/foo/lib /opt/foo/bin/foo  # temporary override for one process
patchelf --set-rpath '$ORIGIN/../lib' /opt/foo/bin/foo   # embed a relative search path
file /usr/bin/foo               # architecture, dynamic or static, interpreter
```

`ldd` runs the dynamic loader on the target in some versions, so do not run it on untrusted binaries; `objdump -p` or `readelf -d` are safe substitutes. The preferred ways to make a private library findable are a `RUNPATH` with `$ORIGIN` (the directory of the executable), set at link time with `-Wl,-rpath,'$ORIGIN/../lib'`, or a dedicated `ld.so.conf.d` file. `LD_LIBRARY_PATH` is for debugging and wrapper scripts; exporting it globally changes which libraries every program picks and is a source of subtle breakage. `LD_PRELOAD` forces a library to load first and is used by debuggers, profilers and some attack techniques.

### Keeping source builds manageable

Choose a prefix that cannot collide with packages: `/usr/local` for software that should behave like part of the system, `/opt/<name>` or `/opt/<vendor>/<name>` for self-contained trees, and a home directory for per-user builds. With GNU Stow, each build installs into `/usr/local/stow/foo-1.4.2` and `stow foo-1.4.2` creates symlinks in `/usr/local`, so removing it is `stow -D`. The better route for anything on more than one machine is to wrap the build in a package. With RPM a spec file defines `%prep`, `%build`, `%install` and `%files`, and macros such as `%{_prefix}` and `%{buildroot}` keep paths consistent [src: man-pages 6974e0aeeb50b5de]; with Debian a `debian/` directory and `dh_make` start a source package [src: debian-handbook 4f2de358f011bbac]. A quick variant for local use is `fpm -s dir -t rpm -n foo -v 1.4.2 -C /tmp/stage .`, which packs the staged tree. Package builds should happen in a clean environment (`mock`, `sbuild`, `pbuilder`, or a container), so that missing build dependencies show up as failures.

## Assessment: the good, the bad and the ugly

What works well: the open build systems are consistent enough that a sequence of three commands builds most projects; the `DESTDIR` convention makes staging uniform; the dynamic linker's rules are documented and inspectable with `ldd`, `readelf`, `LD_DEBUG` and `ldconfig -p`; and the soname convention lets one library be upgraded without relinking its users when the interface stays compatible.

What works badly: build dependency discovery is manual, so building often means reading error messages and installing `-devel` packages one by one. Autotools projects need generated files that are sometimes missing from a git checkout (the need for `autoreconf -fi`). `make install` into the wrong prefix pollutes the system, and without a package there is no record of what to remove. Mixing a source-built library with distribution packages leads to two copies with the same soname in different directories, and which one a program uses depends on the search order, an issue that is difficult to see without `LD_DEBUG`. Security updates for source-built software are the administrator's problem: nothing alerts you that the copy under `/usr/local` carries a vulnerable library.

The ugly parts: setting `LD_LIBRARY_PATH` in a profile file as a quick fix; installing into `/usr` and overwriting package-owned files, which `rpm -V` or `dpkg -V` later flag; `RPATH` that points at a build directory and breaks when the build tree is deleted; and builds that bring their own bundled copies of libraries (vendoring), which defeats centralised patching. Reproducibility is also uncertain, since embedded timestamps, absolute paths and unordered file lists change the output between builds unless the project follows reproducible-build practice.

## Applications beyond this domain

The same concerns appear in container images, where a multi-stage build compiles in one stage and copies only the installed tree into a small final image; the official guidance for builds recommends cache mounts for package managers and build tools [src: docker-docs 710360d437169f7b], and security guidance for containers stresses image creation, testing and accreditation as stages with their own risks [src: nist-sp800-guides 6ca64565fd553532]. Language runtimes face the same library lookup issue: Python's `ctypes` loads shared libraries by name through the same dynamic linker and honours the same search rules [src: python-docs 96792a7769116775], and embedded build systems such as Buildroot and Yocto treat packaging as the only way to add software, with explicit library dependency tracking [src: bootlin-training de67583501dfbb68]. Reasoning about soname compatibility is also the basis for ABI checking tools (`abidiff`, `abi-compliance-checker`) used by library maintainers.

## Examples

**A configure failure.** Building a tool needing zlib stops with `zlib.h: No such file or directory`. The header belongs to the development package: `dnf install zlib-devel` on a Red Hat system or `apt install zlib1g-dev` on Debian. Re-running `./configure` finds it. The wrong fix is to copy `zlib.h` by hand into `/usr/include`.

**A start-up failure.** After `make install` into `/usr/local`, running the tool prints `error while loading shared libraries: libfoo.so.1: cannot open shared object file`. `ldd /usr/local/bin/foo` shows `libfoo.so.1 => not found`; `ls /usr/local/lib` shows the file exists. The directory is not in the cache. On a Red Hat family host the fix is `echo /usr/local/lib | sudo tee /etc/ld.so.conf.d/local.conf` followed by `sudo ldconfig`, then `ldconfig -p | grep libfoo` confirms.

**Two copies of one library.** A source-built application works on one host and crashes on another. `ldd` on both shows `libssl.so.3` resolved from different directories: one from `/usr/lib64` and one from `/opt/vendor/lib` through an `LD_LIBRARY_PATH` set in a profile script. `LD_DEBUG=libs` confirms the search order. The remedy is to remove the global variable and give the vendor binary a relative `RUNPATH` with `patchelf`, or to build it against the system library.

**Staging and packaging.** A team builds `foo` with `./configure --prefix=/usr`, `make`, `make DESTDIR=/tmp/stage install`, and runs `fpm` over `/tmp/stage` to produce an RPM. The package installs and removes cleanly, appears in `rpm -qa`, and is verified with `rpm -V`. The same procedure in a container build produces a reproducible artefact.

**Kernel build as a large source build.** A custom kernel follows the pattern at scale: dependencies first, then configuration, compile, then installation of modules and image, with distribution tooling able to produce a package (`make deb-pkg` on Debian, as the handbook shows) so the result is tracked [src: debian-handbook 19beafaeacf6544b]. The RHEL kernel documentation notes how the `kernel` package is itself a meta package that pulls in the pieces [src: rhel-10-docs a9daf3ba54a760d5].

## Related problems and ideas

Related problems include dependency resolution when building packages (the dependency troubleshooting topic), cross-compiling (separate sysroot, `--host` triplets, pkg-config wrappers), reproducible builds, hardening flags (`-fstack-protector-strong`, `-D_FORTIFY_SOURCE=2`, `-Wl,-z,relro,-z,now`, position-independent executables) that distributions apply through `dpkg-buildflags` and `%{optflags}`, and binary compatibility across distributions. Alternatives to building from source include distribution packages, third-party repositories, containers and Flatpaks, and language-level package managers with prebuilt wheels. Ideas that rethink the model are static linking with musl or in Go and Rust (no run-time library search at all, but updates need a rebuild), content-addressed stores (Nix and Guix, where each build has an exact dependency closure), and lazily loaded plug-in architectures with explicit ABI contracts.

## Active research

Active work includes reproducible builds across distributions and tools that rebuild packages independently to compare output; ABI stability measurement and tooling; the `RUNPATH` versus `RPATH` and security of dynamic loading, including restrictions on `LD_LIBRARY_PATH` and `LD_AUDIT` inside containers; build-system performance (Ninja, Bazel and distributed caches); and the debate over bundling versus sharing libraries and how vulnerability scanners should treat vendored code. Open questions include how to describe system dependencies in a way that every build tool and packager can share, and how to make library versioning meaningful when many languages cross the C ABI.

## Future direction

Expect Meson and CMake to continue to displace Autotools in new projects while Autotools remains in legacy software, more builds to run inside containers or hermetic sandboxes, reproducible builds to be a routine requirement for distributions, and hardening flags to tighten by default. Memory-safe languages will change which libraries matter, though most will still be consumed through the C ABI and the same loader rules. For the administrator the practice stays steady: verify the source, install development dependencies from packages, build with an explicit prefix, stage with `DESTDIR`, package the result, and diagnose library problems with `ldd`, `readelf` and `ldconfig -p` before touching `LD_LIBRARY_PATH`.
