# Where packages come from and why you trust them: repositories and signing keys

## Define the problem

Installing a package gives its maintainer code that runs as root, at install time through scriptlets and afterwards through whatever the package ships. The administrator is therefore deciding to trust a publisher, a download path and a build process in one step. Two separate questions follow. First, which repositories does this machine consult, and in what order and under what conditions? Second, how does it know that a package or an index fetched from a mirror is the one the publisher produced, unchanged, and not something a compromised mirror, a network attacker or a stale cache substituted?

The mechanism that answers the second question is cryptographic signing with OpenPGP keys. The mechanism that answers the first is the repository definition: a URL or mirror list, switches for enabling the source and requiring signatures, and a place for the public key. Mistakes in either are among the most common security findings on Linux hosts: repositories left open to unsigned content, `gpgcheck` disabled to silence an error, keys added to a global trust store when one source needed them, and third-party archives that quietly replace distribution packages. Compliance baselines treat these as high-severity findings for this reason [src: disa-stig c9e65d1e46b47065] [src: disa-stig 59f683a997d954dc]. This slice covers how RPM repositories (dnf) and APT archives are defined, how metadata and packages are signed and verified, how to import, inspect and rotate keys, and how to publish a small repository of your own. Building and promoting packages at scale belongs to a later course.

## History and approaches

The earliest Linux software distribution was a CD or an FTP directory. Integrity meant a published checksum next to the file, which defends against corruption but not against someone who can change both. Debian and Red Hat each added package signatures in the 1990s: RPM supported PGP signatures on individual packages early, and checking them was an option, often off by default.

Package signatures protect the file, but not the index. A mirror could serve an old index (a replay or "freeze" attack that hides security updates), a mixed index, or the right packages in a different combination. Debian's answer, introduced as **secure APT** in the mid-2000s, signs the archive's `Release` file, which carries checksums of all the `Packages` indexes, which in turn carry the checksum of each `.deb` [src: debian-handbook 0382b201752d27d0]. A single signature on `Release` (published as detached `Release.gpg`, later also as an inline-signed `InRelease`) covers the whole tree through a hash chain; the `Valid-Until` field limits replay. The RPM world kept package signatures as the primary mechanism and added optional signing of repository metadata later: the `repomd.xml` file may be signed (`repomd.xml.asc`) and clients check it when `repo_gpgcheck` is enabled.

Key distribution evolved with less success. Early practice was to download a key over HTTP and add it to a global keyring: `rpm --import` for RPM and `apt-key add` for APT. The global keyring meant any imported key could sign anything. Debian deprecated `apt-key` in APT 2.2 (2020) and moved to per-source `signed-by` pointers; RPM's `gpgkey=` in each `.repo` file always pointed to a key but the imported key still landed in one rpm database. Compromised mirrors and carelessly copied third-party instructions taught the same lesson: scope each key to the smallest source possible, fetch it over HTTPS, and verify the fingerprint through a second channel.

There were also partial successes. Transport security (HTTPS to mirrors) became common and protects privacy and catches casual tampering, but it does not replace signatures, since a mirror served over TLS can still be compromised; Debian long served its main archive over plain HTTP deliberately, with signature verification providing the integrity guarantee and caching proxies working well. Another partial success is TUF-style systems and sigstore for language registries, which add expiry, rotation and transparency, but Linux distributions have mostly stayed with OpenPGP. The emerging pattern is signed metadata with a hash chain, keys scoped per source, and expiry on everything.

## Current state

### The structure of a repository

An **RPM repository** is a directory tree served over HTTP(S), FTP or a file path. It contains the `.rpm` files and a `repodata/` directory built by `createrepo_c`. `repodata/repomd.xml` lists the other metadata files (`primary.xml.zst`, `filelists`, `other`, `updateinfo`, optionally `modules.yaml` and `comps.xml`) with their checksums; the metadata in turn lists each package with its checksum. Clients read `repomd.xml` first, then fetch what changed. A **Debian archive** has `dists/<suite>/Release`, `InRelease`, `Release.gpg`, per-component `Packages.xz` indexes by architecture, and a `pool/` directory holding the `.deb` files by source package name. In both families the client downloads the index, verifies it, and then verifies each package against the index (APT) or against its own signature (RPM), so a failure at any layer stops installation.

### RPM repositories with dnf

A repository is defined by a section in `/etc/yum.repos.d/*.repo`. The options come from the `dnf.conf` family of manual pages [src: man-pages 6137e9e04c972a87]:

```ini
[example-appstream]
name=Example AppStream $releasever - $basearch
baseurl=https://repo.example.org/el$releasever/$basearch/appstream/
# or: metalink=https://mirrors.example.org/metalink?repo=appstream-$releasever&arch=$basearch
# or: mirrorlist=https://mirrors.example.org/list?repo=appstream-$releasever
enabled=1
gpgcheck=1
repo_gpgcheck=0
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-example
priority=50
skip_if_unavailable=0
sslverify=1
```

Key options: `baseurl` (a list tried in order), `metalink` and `mirrorlist` (dynamic lists of mirrors, mutually usable with a fallback), `enabled`, `gpgcheck` (verify each package signature), `repo_gpgcheck` (verify the metadata signature), `gpgkey` (one or more URLs, `file://` preferred once the key has been vetted), `priority` (lower number wins), `module_hotfixes`, `exclude` and `includepkgs` (restrict what a repo may supply), `sslverify`, `sslcacert`, `sslclientcert` and `sslclientkey` for entitlement or mutual TLS, `proxy`, `username` and `password`, and `metadata_expire`. The variables `$releasever`, `$basearch` and `$arch` expand at run time. In `/etc/dnf/dnf.conf` the global options `gpgcheck`, `localpkg_gpgcheck` (check locally supplied rpm files, off by default) and `repo_gpgcheck` supply defaults, and baselines require package signature checking for both repositories and local packages [src: disa-stig f411fa458f0277f5]. The Rocky admin guide documents the same `.repo` directory and the main fields [src: rocky-docs 1e429449b4385e39].

Day-to-day commands:

```bash
dnf repolist [--all|--enabled|--disabled]
dnf repoinfo <id>                         # URLs, size, last update, expiry
dnf config-manager --add-repo https://repo.example.org/example.repo   # dnf-plugins-core (DNF 4)
dnf config-manager --set-enabled crb      # enable (or --set-disabled)
dnf --enablerepo=epel install htop        # one-off enable
dnf --disablerepo='*' --enablerepo=baseos list available
dnf makecache; dnf clean all              # refresh or drop cached metadata
dnf install epel-release                  # Extra Packages for Enterprise Linux (needs CRB on RHEL clones)
reposync --repo=baseos --download-metadata -p /srv/mirror  # mirror a repo locally
createrepo_c /srv/local-repo              # build metadata for a directory of rpms
```

EPEL, maintained by a Fedora special interest group, is the standard source of extra packages for the RHEL family; it does not replace base packages, and several baselines forbid it on regulated systems [src: rocky-docs 48ab1d956abb462c] [src: disa-stig 7a7ad6eeb350a1e9]. On DNF 5 systems, `config-manager` uses subcommands (`dnf config-manager addrepo --from-repofile=URL`, `setopt`), a difference worth checking when following older tutorials (to verify per release).

### RPM keys

Public keys live in the RPM database as pseudo-packages named `gpg-pubkey-<keyid>-<time>`. Standard vendor keys ship in `/etc/pki/rpm-gpg/`. Operations:

```bash
rpm --import /etc/pki/rpm-gpg/RPM-GPG-KEY-redhat-release
rpm -qa 'gpg-pubkey*'                      # imported keys
rpm -qi gpg-pubkey-fd431d51-4ae0493b       # shows the key text and, in many versions, its fingerprint
gpg --show-keys --with-fingerprint /etc/pki/rpm-gpg/RPM-GPG-KEY-example   # inspect before import
rpm -K package.rpm                         # check digests and signature (--checksig)
rpm -e gpg-pubkey-fd431d51-4ae0493b        # remove a key
rpmkeys --import ...; rpmkeys --checksig ...   # the same functions in the rpmkeys tool
```

A signature check output shows `digests signatures OK` when the package is intact and its signing key is imported; `NOKEY` means the signature is valid in form but the key is unknown; `BAD` means the content does not match. When `dnf` meets a repository with `gpgcheck=1` and an unknown key it prompts to import the key from `gpgkey` after showing the fingerprint. Confirm the fingerprint against the vendor's own site, and never answer `-y` to a key prompt in automation unless the key is pre-vetted. Compliance rules check that the vendor keys are present and correctly installed, for instance the distributor's own key on AlmaLinux or Fedora [src: compliance-as-code 536d0145fbae3108] [src: compliance-as-code d32945236341e057]. Signing your own packages uses `rpmsign --addsign` (or `rpm --addsign`) with the macros `%_gpg_name` and `%_gpg_path`; the RHEL packaging guide describes the procedure, including exporting the public key for clients [src: rhel-10-docs 0c869993deb7a9ee]. Cryptographic policy matters: on RHEL 9 and 10 the system-wide policy (`update-crypto-policies`) rejects SHA-1 signatures by default, which breaks old third-party packages until they are re-signed with SHA-256 or stronger (to verify per release).

### APT sources, keys and trust

APT verifies `InRelease` or `Release` with `Release.gpg` against the keys named for that source. The modern recipe, as in the Kubernetes install instructions, is to download the vendor's key, convert it to the binary keyring format if needed, store it under `/etc/apt/keyrings/`, and reference it in the source [src: kubernetes-docs 66b7c329a52779f7]:

```bash
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://repo.example.org/key.gpg | sudo gpg --dearmor -o /etc/apt/keyrings/example.gpg
sudo chmod 0644 /etc/apt/keyrings/example.gpg
gpg --show-keys --with-fingerprint /etc/apt/keyrings/example.gpg      # compare with the vendor's published fingerprint
sudo tee /etc/apt/sources.list.d/example.list <<EOF
# vendor repository, key scoped to this source only
deb [signed-by=/etc/apt/keyrings/example.gpg] https://repo.example.org/apt stable main
EOF
sudo apt update
```

In deb822 form the same intent is `Signed-By: /etc/apt/keyrings/example.gpg`, and ASCII-armoured `.asc` keys can be given inline or as a file without dearmoring on current APT. The distribution's own keys come in the `debian-archive-keyring` and `ubuntu-keyring` packages under `/usr/share/keyrings/` and `/etc/apt/trusted.gpg.d/`. Hardening baselines check that the key files are not world-writable, since anyone who can write a key file can authorise a source [src: compliance-as-code 14907b86a912c7e1]. Switch values worth knowing: `[trusted=yes]` disables verification for that source (acceptable only for a local directory you built yourself), `Acquire::AllowInsecureRepositories` and `Acquire::AllowDowngradeToInsecureRepositories` weaken the global default and should stay unset, and `apt-secure(8)` describes the model. The Kubernetes community keeps separate repositories per minor version and documents how to check which one a host uses, an example of treating repository identity as configuration that needs auditing [src: kubernetes-docs 6cf479414ab2c467].

### Running your own repository

For a handful of internal packages, `createrepo_c` plus a web server (or `file://`) is enough on the RPM side; sign the packages and optionally `repomd.xml` (`gpg --detach-sign --armor repodata/repomd.xml`). On the Debian side, `reprepro`, `aptly` and `apt-ftparchive` create `Packages` and `Release` files and sign them; `dpkg-scanpackages` and `dpkg-scansources` generate the `Packages` and `Sources` indexes, which is enough for a small local archive [src: man-pages 73fd91aa1eafd2a8]. A dedicated signing key should be generated on a machine that is not the build server, have an expiry date, and have its public part distributed in a package or through configuration management.

## Assessment: the good, the bad and the ugly

What works well: the hash chain from one signed file to every package is simple and has stood up for twenty years; per-source keys in APT and per-repository `gpgkey` in dnf make trust explicit; repository definitions are plain text, easy to audit and to push through configuration management; and mirror lists let distributions scale to millions of clients.

What works badly: key rotation is hard. A vendor that replaces its signing key must get every client to import the new key before the old one expires, and many setups discover this when `apt update` or `dnf` fails with `NO_PUBKEY` or `Key expired`. Documentation and blog posts continue to teach the deprecated `apt-key add` or `gpgcheck=0`. The RPM database is a single trust pool, so any imported key can in principle vouch for any repository's packages, unless the `.repo` file also restricts the repo. `repo_gpgcheck` is off by default on many distribution repositories, which leaves index replay possible against RPM mirrors, although package signatures still stop forgery.

The ugly parts: `curl | sudo bash` installers that add repositories and keys in one step; keys fetched over HTTP; mixed trust where a third-party repository publishes a package with the same name as a distribution package and a higher version; expired keys on long-lived images; and compliance fixes applied blindly (enabling `gpgcheck` on a repo whose packages are not signed breaks updates and leads someone to turn it off again). Time skew also breaks signature validity windows and `Valid-Until` checks.

## Applications beyond this domain

The pattern of signed index, hash chain to contents, per-source trust root and expiry appears wherever software is distributed. Container registries add image signatures with Sigstore `cosign` and policy engines; Python's PyPI and npm have moved toward trusted publishing and provenance attestations; firmware distribution uses LVFS metadata signed with PKCS#7 and GPG; Android and ChromeOS rely on signed update payloads and verified boot; Git has signed tags and commits. The lessons carry over: scope keys narrowly, verify fingerprints out of band, give signatures an expiry, and monitor for unexpected key or source changes. Repository mirroring and snapshotting, for reproducibility and for air-gapped sites, are used in the same ways for container base images and language packages. RHEL's image-builder documentation shows the same ideas applied when baking custom repositories and content views into images [src: rhel-10-docs 9040964dee647030] [src: rhel-10-docs 3547624fa0f1810d].

## Examples

**Adding EPEL to a Rocky host.** `dnf install epel-release` adds the `.repo` files and the key; enabling the CRB repository first (`dnf config-manager --set-enabled crb`) satisfies dependencies. `dnf repolist` confirms, and `dnf --disablerepo=epel upgrade` is the way to exclude it temporarily. On a hardened system the baseline may prohibit this step entirely, and the right answer is to file the exception rather than to bypass the check [src: rocky-docs 48ab1d956abb462c].

**A key that cannot be found.** `apt update` prints `NO_PUBKEY 1234ABCD5678EF90` for a third-party source. The tempting but wrong answer is `apt-key adv --recv-keys` or marking the source `[trusted=yes]`. The correct response is to find the vendor's documented key location, download over HTTPS, compare the fingerprint with the vendor's published value, store it in `/etc/apt/keyrings/` and add `signed-by` to that one source.

**Rotating a mirror key.** An internal repository's signing key is about to expire. The team generates a new key, publishes both keys in a `gpgkey=` list in the `.repo` file pushed by configuration management, rebuilds the repository with the new key, waits until hosts have imported it, and only then retires the old one. Hosts that missed the window fail with a signature error naming the key id, which is the cue to push the file again.

**An unsigned package from a vendor.** `rpm -K vendor.rpm` shows no signature. With `localpkg_gpgcheck=1` `dnf install ./vendor.rpm` refuses. The right path is to ask the vendor for a signed package or verify the file against a published hash and then install with `--nogpgcheck` for that one command, recording the exception; flipping `localpkg_gpgcheck` off globally is the wrong fix.

**Building a tiny local repo.** `createrepo_c /srv/local` after copying signed rpm files, a `.repo` file with `baseurl=file:///srv/local`, `gpgcheck=1` and `gpgkey=file:///srv/local/RPM-GPG-KEY-local`, then `dnf --disablerepo='*' --enablerepo=local install foo` verifies the full path on an offline machine.

## Related problems and ideas

Related problems include mirror health and geography (`fastestmirror`, `metalink`, `apt-transport-mirror`), signed repository content for compliance (SBOMs, advisories, `updateinfo`), key escrow and hardware-backed signing keys (HSMs, YubiKeys for OpenPGP), and long-term archives for audit. Alternatives and extensions include signing the whole repository state with TUF so that rollback and freeze attacks are provable; the Sigstore and Rekor transparency log for artefacts; reproducible builds, which let independent parties verify that a published binary matches its source regardless of who signed it; and content-addressed distribution (Nix, OSTree and container layers), where trust attaches to digests of content rather than to mutable repository state. A further idea, still debated, is to separate repository availability from signing so that the signing key never lives on an Internet-reachable server.

## Active research

Active areas include post-quantum signature schemes and the migration of OpenPGP to the new RFC 9580 format with modern algorithms (RPM and APT both work on support for newer key and signature formats, to verify per release); Sequoia-PGP as a safer implementation used in recent RPM and APT versions; reproducible builds as a second line of defence, a topic that gained urgency after the 2024 xz backdoor; measures against freeze and rollback attacks on mirrors; and transparency logs for package repositories. Open questions include how to automate key rotation without teaching users to trust new keys blindly, how to scope trust by package name rather than by whole repository, and how to keep trust decisions transparent in image-based and offline deployments.

## Future direction

Expect per-source key scoping to be the only supported model in APT, the older global keyring paths to disappear, SHA-1 signatures to be rejected nearly everywhere, and `repo_gpgcheck` or equivalent metadata signing to become the default in more distributions (dates vary by vendor, and release notes should be checked). Expect OpenPGP v6 signatures, hybrid post-quantum schemes and Sigstore-style attestations to appear alongside the existing keys. For administrators the durable habits do not change: keep the list of enabled repositories short and documented, verify each key's fingerprint from a second channel, keep `gpgcheck` enabled everywhere, set an expiry on keys you own, and review sources and key files in configuration management rather than by hand.
