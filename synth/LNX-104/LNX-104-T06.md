# When packages will not install: diagnosing dependency, conflict and library problems

## Define the problem

Package managers exist so that an administrator can say what is wanted and the system works out the rest. When that fails, the failure arrives as a wall of text: a package needs a capability nobody offers, two packages claim the same file, an upgrade would remove something essential, a lock cannot be taken, or a program starts and immediately complains about a missing library. Administrators who cannot read these messages tend to reach for the dangerous options (`rpm -e --nodeps`, `dpkg --force-all`, editing the package database by hand), which turn a recoverable situation into a broken system.

Dependency problems have a small number of root causes that repeat on every distribution. The repository set is wrong, so the needed package is not offered, is offered in the wrong version, or comes from a source with a different priority. The metadata is stale or inconsistent. The installed state is unusual: mixed releases, third-party packages, held or locked versions, packages with no repository left to supply them. The request itself is impossible: two requirements exclude each other. Finally, the package database can disagree with the filesystem after an interrupted transaction or a manual file copy, and run-time library resolution can fail even when package dependencies are satisfied. This slice gives a method for classifying a failure, the command set for each of the Red Hat and Debian families, the tools for library problems, the safe repairs, and the repairs to avoid. It builds on the earlier topics in this course: querying and history with `rpm` and `dnf`, `apt` priorities and holds, repository trust and the dynamic linker.

## History and approaches

Early packaging systems checked dependencies only at install time. A package was refused if its requirements were absent, and the user fixed that by hand: the original "dependency hell" was largely a download and ordering problem, which `yum`, `apt` and their successors solved by adding repositories and automatic fetching. The next problem was harder: with automatic fetching, the system must choose among alternatives. Debian's solver, designed for the `apt` project, is a heuristic resolver that scores solutions and explains failures as lists of unmet dependencies; `aptitude` added a more thorough search with backtracking and the ability to propose alternative solutions interactively. The RPM tools relied on a simple depth-first resolver in early `yum`, which could give surprising results and had no good way to say why a request was unsatisfiable.

The shift that matters for troubleshooting is the move of the Red Hat family to a SAT-based solver (`libsolv`, from SUSE) in DNF. A SAT solver treats installed packages, requests and repository contents as logical constraints, and either finds a consistent set or can report a minimal set of conflicting rules. DNF messages that begin with a line stating the problem and list a chain of requirements come from this machinery, and the `--debugsolver` option writes the whole problem to a directory for later analysis. Debian worked in parallel on better explanations and on a new solver in APT's 3.x series. A partial success has been gradual reduction of failures through policy: stable release repositories are consistent by construction, so most errors now come from outside them, such as third-party repositories, mixed suites or partial upgrades.

Library dependencies went through their own evolution. Static dependencies between packages were declared by hand; later systems derive them from the binaries. RPM runs **dependency generators** at build time that inspect each file and emit `Requires:` and `Provides:` entries for sonames, interpreters, Python distributions and Perl modules; `elfdeps` is the tool for ELF files and `rpmdeps` runs generators over arbitrary files, with a hidden debugging switch for the stage that builds the file classification [src: man-pages 8a356ce2fe1800b1] [src: man-pages fe38f839c55308de] [src: man-pages 3b0ec04500825dce]. Debian computes shared library dependencies with `dpkg-shlibdeps` and symbols files. Binary compatibility between library versions is measured by tools such as the libabigail suite, which compares the interfaces of two builds and reports changes that would break consumers [src: man-pages 30dd1091e8c2173e]. The lesson across the decades is that most dependency failures are information problems, not logic problems, and the first job is to collect the information that shows which layer failed.

## Current state

### A method

Work in a fixed order. First, read the first error, not the last; later lines are usually consequences. Second, classify the failure into one of six layers:

1. **Transport and metadata**: cannot reach a repository, checksum or signature errors, stale or half-synchronised mirrors.
2. **Offer**: the package or capability does not exist in the enabled repositories (wrong repository, disabled repository, wrong architecture or release, version not yet published).
3. **Selection**: the package exists, but priorities, excludes, version locks, holds, module streams or the `--best` rule prevent it from being chosen.
4. **Constraint**: the request is impossible: two packages conflict, a dependency needs a version that excludes another requirement, or an installed package pins an older library.
5. **State**: the local package database is inconsistent: half-configured packages, a lock held, missing files, a package whose repository is gone.
6. **Run time**: packages installed fine, but a program cannot find a library or finds the wrong one.

Third, reproduce without changing anything: use simulation (`dnf --assumeno`, `apt-get -s`), read-only queries, and the policy views. Fourth, change the smallest thing that fixes the layer. Fifth, record what was done, because the next incident will resemble it. Sixth, run a verification pass (`dnf check`, `apt-get check`, `dpkg --audit`, `rpm -Va` on the affected packages).

### Red Hat family: reading and resolving dnf failures

A typical solver failure begins with a problem statement, followed by indented reasons: a package needs a capability that nothing offers (a `nothing provides` line), two requests conflict (`conflicting requests`), a package cannot be installed alongside another already installed (`cannot install both`), or a package is held back by `best` mode because the newest version has unmet dependencies. The follow-up commands:

```bash
dnf provides 'libfoo.so.1()(64bit)'        # who offers the missing capability (repositories included)
dnf provides '*/libfoo.so.1'               # search by file path in repository metadata
dnf repoquery --whatprovides foo           # same question via repoquery
dnf repoquery --requires --resolve foo     # what foo needs and which packages satisfy it
dnf repoquery --whatrequires foo           # who needs foo (installed and available)
dnf repoquery --deplist foo                # dependencies and the candidate providers
dnf repoquery --unsatisfied                # installed packages with unmet dependencies
dnf repoquery --duplicates; dnf list --extras   # duplicate versions; packages not in any enabled repo
dnf repolist --all; dnf repoinfo           # is the needed repository enabled and healthy?
dnf install --allowerasing foo             # let the solver remove conflicting packages (review the list)
dnf install --nobest foo                   # accept an older version when the newest cannot be installed
dnf install --skip-broken foo bar          # (DNF 4) install what can be installed; --skip-unavailable in DNF 5
dnf distro-sync                            # align all packages with the repositories, up or down
dnf --debugsolver install foo              # writes ./debugdata for later study
dnf check                                  # local database problems: unmet dependencies, duplicates, obsoleted packages
dnf clean expire-cache; dnf makecache      # refresh metadata after a mirror problem
dnf versionlock list; dnf config-manager --dump | grep -i exclude   # hidden causes of selection failures
dnf module list; dnf module reset nodejs   # (DNF 4) module stream conflicts
```

The cases that account for most real failures on RHEL and its clones are these. The needed library lives in a repository that is not enabled by default (`crb` or `codeready-builder`, `AppStream` on a minimal install, `epel`); enabling it is the fix, and `dnf provides` finds the name. A third-party repository publishes a newer package that requires a newer library than the base provides, and `--nobest` or an `exclude=` line on the third-party repository is the correct response. Packages remain from the previous major release after an in-place upgrade, which shows in `dnf list --extras` and `rpm -qa | grep el8`. A package stuck on an old version because of `dnf versionlock`, an `exclude=` in `dnf.conf`, or a module stream not enabled. And metadata corruption or a lagging mirror, where `dnf clean all` followed by a different mirror resolves the problem. When two packages claim the same file, the transaction check reports a file conflict naming both packages; the cure is to remove or replace one of them and report the problem to the packager, not to use `rpm --replacefiles`.

Direct `rpm` operations are for recovery, not for routine work. `rpm -Va` shows damage, `rpm -q --whatrequires foo` shows dependents, `rpm --rebuilddb` repairs the database index, `rpm -e --justdb foo` removes only the database entry for a package whose files are gone, and `rpm -Uvh --oldpackage` installs an older file. The options `--nodeps`, `--force` and `--replacepkgs` bypass checks and leave the system in a state that the solver will later refuse to continue from. A package manager transaction left unfinished shows up in `dnf history` with a non-zero return; `dnf history undo` or `rollback` may help; the package `yum-utils` (or `dnf-utils`) provides `package-cleanup` for finding problems and duplicates, and the `dnf-plugins-core` plugin `needs-restarting` finds services still running old libraries after an update.

### Debian family: reading and resolving apt failures

APT failures read as a list of packages that are unmet: a package depends on a particular version of another that is not going to be installed, a package is not installable, or a package is held broken (a hold or pin prevents the needed change). Useful commands:

```bash
apt-get -s install foo                     # simulate and read the plan
apt-get check                              # verify the dependency graph of the installed system
apt --fix-broken install                   # (apt-get -f install) complete unmet dependencies
dpkg --audit                               # packages half-installed or unconfigured
dpkg --configure -a                        # finish interrupted configuration
dpkg -l | grep -v '^ii'                    # anything not in the plain installed state
apt-cache policy foo                       # installed, candidate, sources and priorities
apt-cache depends foo; apt-cache rdepends --installed foo
apt-cache showpkg foo                      # versions, reverse dependencies and provides
aptitude why foo; aptitude why-not foo     # why a package is or is not being installed (aptitude)
apt-mark showhold; apt-mark unhold foo     # holds as a hidden cause
apt-get install -o Debug::pkgProblemResolver=yes foo   # verbose solver trace
apt-file search libfoo.so.1                # which package ships a file (install apt-file, run apt-file update)
apt install --reinstall foo                # restore damaged files of an installed package
apt install foo=1.2.3-1                    # a specific older or newer version
dpkg --print-foreign-architectures         # multiarch: are :i386 or :arm64 packages in the mix?
```

`apt-get check`, `apt --fix-broken install` and `dpkg --configure -a` are the standard first-aid sequence when an installation was interrupted. The frequent causes are mixed suites after a careless pin or a partial release upgrade (shown by `apt-cache policy` listing candidates from several releases), a third-party repository publishing a package that conflicts with a distribution package, a version-specific dependency that cannot be satisfied because the archive carries only the newer version, a package marked `hold` that blocks an upgrade of something that depends on it, and a lock that is simply busy. When a lock error appears, identify the holder before doing anything else; tools such as `fuser` and `lsof` list the process using a lock file, as the Arch Linux troubleshooting guide demonstrates for a general case [src: archwiki c5c8f62c578c2154], and many such errors are an `unattended-upgrades` or `apt-daily` run that will finish by itself. If a package refuses to remove because its own `prerm` script fails, `dpkg --remove --force-remove-reinstreq` is the escape hatch, after reading the script in `/var/lib/dpkg/info/<pkg>.prerm`. The last resort of editing `/var/lib/dpkg/status` by hand exists but is rarely appropriate; `/var/backups/dpkg.status.*` holds recent copies to restore from.

### Library problems at run time

When the package layer is clean and a program still fails, the usual message names a shared object the loader cannot open. The Arch Linux troubleshooting page walks through the same steps used on any distribution: identify the library, find out what provides it, and check whether the file exists but sits outside the search path [src: archwiki c166f8566bf7d322]. The sequence is:

```bash
ldd /path/to/program | grep 'not found'    # which libraries are missing (or use readelf -d | grep NEEDED)
dnf provides '*/libfoo.so.1'               # RPM: package that ships it
apt-file search -x '/libfoo.so.1$'         # Debian: package that ships it
find / -name 'libfoo.so*' 2>/dev/null      # does it exist elsewhere on this host?
ldconfig -p | grep libfoo                  # is it in the loader cache?
LD_DEBUG=libs /path/to/program 2>&1 | head -50   # trace how the loader searches
rpm -V pkg  or  dpkg -V pkg                # was the library file damaged or removed?
```

The causes, in order of frequency: a package is missing (install the provider), the file exists in a directory the loader does not search (add a drop-in file in `/etc/ld.so.conf.d/` and run `ldconfig`, or give the program an `$ORIGIN`-relative run path), a symbolic link for the soname is missing or points to a removed version (`ldconfig` fixes the links), an architecture mismatch (a 32-bit program needs the 32-bit library, which on Debian means the `:i386` package and on RPM systems the `.i686` package), or an ABI break where the library exists but with different symbols (the program reports an undefined symbol or a missing version). For the last case compare the old and new library interfaces with `abidiff` from the libabigail suite, which lists added, removed and changed symbols and types [src: man-pages 30dd1091e8c2173e], and downgrade the library or rebuild the dependent program.

### Safe and unsafe repairs

Safe repairs change the inputs: enable or disable a repository, remove a stale pin or lock, refresh metadata, install the correct provider, reinstall the damaged package, downgrade or `distro-sync`, remove a third-party package that conflicts. Medium-risk repairs let the solver remove packages (`--allowerasing`, `apt full-upgrade`) and must be preceded by reading the list of removals; protected packages such as `systemd`, `glibc`, `kernel` and `sudo` appearing in a removal list are a signal to stop. Unsafe repairs bypass the checks: `rpm --nodeps`, `dpkg --force-depends`, `--force-all`, deleting files under `/var/lib/dpkg` or `/var/lib/rpm` by hand, copying libraries into `/usr/lib` and symlinking sonames manually. If one of them is unavoidable, take a snapshot first, write down what was bypassed and make the package state honest again afterwards with a reinstall.

## Assessment: the good, the bad and the ugly

What works well: the solvers are fast and give reproducible results; simulation modes show the plan without changing the system; query commands answer who provides, who requires and where a package came from; repositories of a single release are consistent, so errors usually point to something local; and the history and snapshot tools make mistakes recoverable.

What works badly: messages are verbose and the root cause is often several lines from the top. Solver output explains why the solver could not do something, but not always which of your configuration choices is to blame (an `exclude=`, a pin, a lock). Package databases do not record why a file was placed outside package control, so a hand-copied library looks like a missing dependency. Modular streams on RPM systems and mixed-suite pins on Debian systems create states that are legal but hard to reason about. Different front ends give different explanations for the same problem.

The ugly parts: the pull toward forcing the install; stale mirrors that cause intermittent failures that disappear on retry and teach people to ignore them; pre-release or EPEL packages that quietly replace base packages; vendor installers that drop libraries into `/usr/lib` or `/opt` without packaging them; and long-lived systems with a decade of in-place upgrades, in which leftovers from old releases cause obscure conflicts. An administrator also meets problems where the dependency is correct on paper but wrong in practice, because a package declares too loose a requirement and a newer library breaks it at run time.

## Applications beyond this domain

Dependency solving appears in every ecosystem. Language package managers (`pip`, `npm`, `cargo`, Go modules) use their own resolvers, with the same classes of failure: unsatisfiable constraints, conflicts between transitive requirements, a registry that does not offer the needed version, and local state that differs from the lock file. Kubernetes workloads declare dependencies between components and images, and a migration such as the removal of a container runtime shim shows how hidden dependencies surface only when a platform changes [src: kubernetes-docs e5a997a7acce6b3e]. Image builders and bootc workflows resolve dependencies once at build time, so run-time failures become build-time failures, which is a main reason to prefer them [src: rhel-10-docs 495fbd3b7942b63c]. Directory services and distributed systems face a version of the same question when a component is retired and every place that still refers to it must be cleaned up, as in the documentation for removing domain controllers from a domain [src: ms-learn-adds c2b18f17035f9954]. The diagnostic method, which separates "can I get it", "may I choose it", "does it fit" and "does it run", transfers to all of these.

## Examples

**A missing capability after enabling a vendor repository.** `dnf install vendor-agent` fails with a problem statement that a package needs `libcrypto.so.3()(64bit)`, but none of the providers can be installed. `dnf provides '*/libcrypto.so.3'` shows that the base package offers it, at a version older than the one the vendor requires, because the host is on an earlier minor release. `dnf repolist` shows the system is still using a pinned minor-release repository. The fix is to update the system to the supported minor release (`dnf upgrade`), not to install the library by hand.

**Held broken packages on Ubuntu.** `apt install foo-dev` reports that `foo-dev` depends on `libfoo1 (= 2.0)` but `2.1` is going to be installed. `apt-cache policy libfoo1` shows 2.1 as the candidate from `-updates` and 2.0 from the release pocket. Installing the specific older package with `apt install foo-dev libfoo1=2.0-1` is the quick path; the real cause is that the `-updates` pocket has a newer library whose development package has not yet been published, so waiting or filing a bug is the long-term answer.

**A hand-installed library hides a missing package.** A program prints a missing library message. `ldd` confirms it; `find` shows the library under `/opt/legacy/lib`, which the previous administrator used. The correct fix on a managed system is to find the supplying package (`dnf provides`, `apt-file search`) and install it, then retire the `/opt` copy; adding `/opt/legacy/lib` to the global search path would let the old copy shadow future system libraries.

**A half-finished upgrade.** A laptop lost power during `apt upgrade`. `apt install` refuses. `dpkg --audit` lists three half-configured packages; `dpkg --configure -a` finishes them; `apt --fix-broken install` pulls a missing dependency; `apt-get check` is clean; the earlier `apt upgrade` is re-run. Nothing was forced, and the sequence is the same on every Debian-family release.

**A forced removal.** An administrator ran `rpm -e --nodeps` on a library to get past a conflict. Several programs fail, `dnf check` reports unmet dependencies, and `rpm -Va` shows missing files. `dnf reinstall` of the library (or `dnf install` of the removed package) restores consistency; `dnf history list` shows nothing for the earlier `rpm` command because it bypassed `dnf`, which is why the forced path is hard to audit.

## Related problems and ideas

Neighbouring subjects are build-time dependency tracking (`BuildRequires`, `Build-Depends`, build environments such as `mock` and `sbuild`), reproducible environments (`dnf --installroot`, `debootstrap`, containers), fleet-level consistency (Satellite or Foreman content views and errata; Ansible modules that apply the same package list everywhere), and systematic approaches to binary compatibility (ABI checkers, symbol versioning). Alternatives include immutable image-based systems where the dependency set is fixed at build time, and functional package managers such as Nix and Guix, which allow several incompatible versions to coexist and thus remove most conflict failures at the cost of disk space and a different mental model. Less mainstream ideas include solvers that explain failures in terms of the user's configuration (which line caused the exclusion), minimal-change repair suggestions, and automated rollback when a transaction leaves the system unable to boot.

## Active research

Active areas include better solver diagnostics (DNF 5 and libsolv work on conflict explanations; APT's new solver and its output), explainable dependency resolution in language ecosystems, automated detection of ABI breaks in distribution updates using libabigail-style tools, and the use of reproducible builds to verify that a new package version is a compatible rebuild. Researchers study how often upgrades break dependents and how to predict that from symbol and interface differences, and how to model "soft" dependencies such as recommendations. Open questions include how to make solver failures actionable for non-experts, how to keep third-party repositories compatible with distribution packages over time, and how to coordinate library transitions across a large archive.

## Future direction

Expect better diagnostics in both families as DNF 5 and the new APT solver mature, more distribution tooling that runs ABI checks before an update is published, and growth of image-based systems in which a dependency failure shows up in a build pipeline instead of on a production host. Third-party repositories are likely to adopt stricter conventions (explicit compatible releases, no overlap with base package names). Administrators should keep a short checklist: classify the layer first, simulate before changing, check repositories, locks, holds and pins before blaming the solver, reach for the package that provides a capability rather than for a force option, and verify afterwards with `dnf check`, `apt-get check` and `ldd` on the affected programs.
