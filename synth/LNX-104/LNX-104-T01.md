# Managing RPM-based systems: querying, verifying and undoing changes with rpm and dnf

## Define the problem

A Linux host is, to a first approximation, a pile of files that came from somewhere. Which package owns `/etc/ssh/sshd_config`? Did someone edit `/usr/bin/sudo` after it was installed? What changed on Tuesday night when the machine started misbehaving, and can that change be reversed without rebuilding the host? Every one of these questions needs a record of what was installed, a way to compare disk against that record, and a way to move the system from one set of packages to another in a controlled step. Before package managers, administrators answered them with a notebook and a tarball.

On Red Hat family systems the answer is split in two layers. `rpm` is the low-level tool and file format: it installs, removes and inspects individual package files and keeps a database of what is on the machine. It knows nothing about repositories or about packages that are not yet downloaded. `dnf` sits on top: it reads repository metadata, solves dependencies across thousands of candidate packages, downloads what is needed, hands the work to the RPM library as one transaction and records that transaction in a history that can be listed and, within limits, reversed [src: man-pages a57fa9d713fd4ae1] [src: rhel-10-docs b405d00e8674820c]. This slice covers both layers on RHEL 9 and 10, Rocky and AlmaLinux, and Fedora: how to ask the system questions (query), how to ask whether files still match the vendor's record (verify), and how to review and revert changes (history and undo). It does not cover building packages, repository configuration or signing, which later topics take up.

The gap this fills is practical. An administrator who knows only `dnf install` can add software but cannot audit a host, cannot prove that a binary is intact, and tends to panic after a bad update. The query, verify and history tools turn the package database into an investigation instrument and a safety net.

## History and approaches

The first Linux distributions installed software by unpacking tarballs and hoping. Package managers appeared in the mid-1990s: Debian's `dpkg` in 1993 and Red Hat's `rpm` (originally `rpm` for "Red Hat Package Manager", later a recursive acronym) in 1995, with Marc Ewing and Erik Troan's design. RPM's central ideas were a single-file package with metadata, scripts and a payload; a database of installed packages; and verification of installed files against recorded size, mode, owner and digest. Those ideas are still how it works.

Early RPM had a famous weakness, "dependency hell": it would refuse to install a package whose requirements were missing, but it would not go and fetch them. Users downloaded packages by hand, one at a time, and sometimes forced installs with `--nodeps`, leaving broken systems. Several tools tried to close the gap. `up2date` (Red Hat) and `apt-rpm` (a port of Debian's resolver) worked but were tied to particular vendors. **Yellowdog Updater Modified**, `yum`, written at Duke University and adopted by Red Hat for RHEL 5 and Fedora Core, became the standard: it introduced repository metadata (`repodata`) published as XML and a simple command line close to the one administrators use today.

`yum` had its own limits. Its dependency solver was a bespoke algorithm, written in Python, that sometimes produced surprising results or ran slowly, and its internal API was hard to extend. The Fedora project replaced it with **DNF** ("Dandified Yum") from Fedora 18 onward as an option and as the default from Fedora 22, in 2015. The key change was moving dependency resolution to `libsolv`, a SAT-based solver created by SUSE for `zypper`, and later moving metadata handling into `libdnf` and `librepo`. RHEL 8 (2019) made `dnf` the default and kept `yum` as an alias, which is why `yum(8)` still exists and today describes `dnf` [src: man-pages a57fa9d713fd4ae1]. The older `yum` command remains available for scripts, and `yum2dnf(8)` documents the few behavioural differences (for example, which commands report failure through their exit status) [src: man-pages f537bf0eafaf3a76].

A parallel problem was the RPM database itself. For two decades it was a Berkeley DB in `/var/lib/rpm`, fragile after power loss and needing `rpm --rebuilddb` to recover. Fedora moved to a SQLite backend in version 33 (2020), RHEL 9 followed, and RPM 4.19 moved the default location to `/usr/lib/sysimage/rpm`. The RHEL 10 release uses that layout, and `/var/lib/rpm` remains as a symlink for compatibility.

The most recent generation is **DNF 5**: a C++ rewrite that replaces the Python front end, `libdnf` and the plugin set with a single `libdnf5` library and daemon-free command. Fedora 41 shipped it as the default in late 2024. RHEL 10 and its clones keep DNF 4 as the system tool, so the commands in this lesson are DNF 4 syntax with notes where DNF 5 differs (to verify against the minor release in use). The emerging pattern is steady: the low-level format has barely changed, while the solver, the metadata and the command line have been rewritten twice to be faster and more predictable.

## Current state

### The pieces

An RPM package file contains a header (name, epoch, version, release, architecture, requirements, provides, conflicts, file list with digests and attributes, scriptlets) and a compressed cpio payload. Installed packages are tracked in the RPM database; repositories are published as a directory of packages plus `repodata/repomd.xml`, which points to compressed metadata files (`primary`, `filelists`, `other`, optionally `updateinfo` for advisories and `modules`). `dnf` downloads this metadata, caches it under `/var/cache/dnf`, and keeps its own SQLite history in `/var/lib/dnf/history.sqlite` (path varies by DNF version).

The five-part package name is worth memorising: **name-epoch:version-release.architecture**, for example `openssl-1:3.2.2-6.el10.x86_64`. Epoch is an override that wins over version when a vendor needs to reset numbering; when it is zero it is omitted in most displays. Release carries the distribution tag (`el10`, `fc41`).

### Querying with rpm

`rpm -q` (and its long form `rpm --query`) is the read-only interface to the database. The main selectors and information options are:

```bash
rpm -qa                          # all installed packages
rpm -qa --last                   # newest installs first (shows install time)
rpm -q bash                      # is bash installed, and which version
rpm -qi bash                     # Name, Version, Release, Install Date, Signature, Summary
rpm -ql bash                     # files the package owns
rpm -qc openssh-server           # configuration files only (%config)
rpm -qd bash                     # documentation files
rpm -qR bash                     # requirements (also --requires)
rpm -q --provides bash           # capabilities this package supplies
rpm -q --whatprovides /bin/sh    # which installed package supplies a file or capability
rpm -q --whatrequires glibc      # which installed packages need this one
rpm -qf /etc/ssh/sshd_config     # which package owns this file
rpm -qp ./foo-1.0-1.x86_64.rpm   # inspect a package file (-p works with -i, -l, -R)
rpm -q --scripts bash            # scriptlets (pre, post, preun, postun, triggers)
rpm -q --changelog bash | head   # vendor changelog (shows CVE ids in many cases)
rpm -q --qf '%{NAME}-%{VERSION}-%{RELEASE}.%{ARCH}\n' bash
```

`--queryformat` (`--qf`) takes tags such as `%{NAME}`, `%{VERSION}`, `%{RELEASE}`, `%{EPOCH}`, `%{ARCH}`, `%{INSTALLTIME:date}`, `%{SIZE}`, `%{VENDOR}`, `%{BUILDHOST}`, `%{SIGPGP:pgpsig}` and `%{SOURCERPM}`; `rpm --querytags` lists them all. Format strings with array tags use square brackets (`[%{FILENAMES}\n]`), which repeats the line per element. `rpm -qa` is the starting point for inventories, and the query format makes the output stable for scripts.

### Querying with dnf

`dnf` queries repository metadata as well as the installed set, so it can answer questions about packages that are not installed:

```bash
dnf list installed | available | updates | extras | recent
dnf info nginx                      # description, size, repo, licence, URL
dnf search 'web server'             # name and summary only; --all also searches descriptions
dnf provides /usr/bin/dig           # which package (installed or not) supplies a path; wildcards allowed
dnf provides 'libssl.so.3()(64bit)' # a library capability
dnf repoquery --requires bash       # what bash needs
dnf repoquery --whatrequires glibc  # what needs glibc (installed and available)
dnf repoquery -l nginx              # files in an uninstalled package
dnf repoquery --installed --qf '%{name} %{from_repo}'  # where installed packages came from
dnf repolist --all                  # enabled and disabled repositories
dnf check-update                    # exit status 100 when updates exist, 0 when none, 1 on error
dnf updateinfo list --security      # advisories (needs updateinfo metadata)
dnf updateinfo info RHSA-2025:1234
dnf group list; dnf group info "Development Tools"
dnf needs-restarting -r             # is a reboot needed? (-s lists services to restart)
```

The `group` commands list and install package groups, with `--installed` and `--available` filters [src: man-pages 7b1119a946986aad]. Command options worth knowing are `-y` (assume yes), `--assumeno`, `--setopt=<key>=<value>` (one-off configuration override), `--enablerepo=` and `--disablerepo=`, `--refresh` (expire cached metadata), `-C` (cache only, no network), `--security`, `--bugfix`, `--advisory=<id>`, `--exclude=<pkg>`, `--allowerasing` (let the solver remove conflicting packages), `--best` and `--nobest`, `--skip-broken` and `--skip-unavailable` [src: man-pages 2df0563516661e7c]. Defaults live in `/etc/dnf/dnf.conf` under `[main]`, with keys such as `gpgcheck`, `installonly_limit` (kernels kept, default three), `clean_requirements_on_remove`, `keepcache`, `max_parallel_downloads`, `fastestmirror` and `exclude`; repository definitions live in `/etc/yum.repos.d/*.repo`.

### Verifying

Verification compares what is installed with what the package recorded. There are two checks. `rpm -V <pkg>` (or `--verify`) re-reads each file and compares size, mode, digest, device numbers, link target, owner, group, mtime and capabilities. Output is one line per discrepancy with a nine-character field, a dot meaning "matches" and a letter meaning "differs": `S` size, `M` mode (including type and permissions), `5` digest, `D` device major/minor, `L` readlink path, `U` user, `G` group, `T` modification time, `P` capabilities. A letter `c` (config), `d` (documentation), `g` (ghost), `l` (licence) or `r` (readme) follows for file category [src: man-pages a57fa9d713fd4ae1]. Missing files show as `missing`. Configuration files are expected to differ; a binary with `S.5....T.` is a red flag.

```bash
rpm -V openssh-server        # one package
rpm -Va                      # everything (slow; pair with grep -v ' c ' to skip config)
rpm -Vf /usr/bin/sudo        # package that owns this file
rpm -Vp ./foo.rpm            # compare package file contents with installed files
rpm --verify --nodigest ...  # skip digest checks of the header
```

The second check is about the package file itself, not the installed files: `rpm -K` (or `--checksig`) validates the package's digests and its GPG signature against keys imported with `rpm --import` (keys appear as `gpg-pubkey-*` packages, listed with `rpm -qa 'gpg-pubkey*'`). `dnf` does this automatically when `gpgcheck=1`; the next lesson covers keys and repositories. Compliance baselines such as DISA STIGs encode both checks as findings: verifying the hashes of system files against vendor values, requiring `gpgcheck`, and forbidding certain third-party repositories [src: disa-stig 1d604af3cdc1e04c] [src: disa-stig 7a7ad6eeb350a1e9] [src: compliance-as-code e9b3c83e6b77a249]. A verification pass is an integrity check against accidents and unsophisticated tampering, not a defence against an attacker with root, who can alter the database too; for that, use an offline baseline such as AIDE or a signed immutable image.

### History and undo

Every `dnf` transaction (install, upgrade, remove, group or module change, or the equivalent via `rpm`) is recorded with an identifier, user, date, the command line, the action counts and the package changes. The `history` command exposes it [src: rhel-10-docs 3d869c67fc1b5284]:

```bash
dnf history list                 # table: ID, command line, date, action(s), altered
dnf history list --reverse       # oldest first
dnf history info 42              # packages and actions of transaction 42 (also: last, last-1, 42..45)
dnf history undo 42              # reverse transaction 42: remove what it installed, reinstall what it removed, downgrade what it upgraded
dnf history redo 42              # repeat transaction 42
dnf history rollback 42          # undo everything done AFTER transaction 42 (return to state at end of 42)
dnf history userinstalled        # packages the user asked for explicitly
```

The three verbs differ in scope: `undo` reverses one transaction, `redo` repeats one, `rollback` reverses every transaction after a chosen point. Reverting an upgrade means installing the older version again, which needs that old package still available in a repository or in the cache; that is why mirrors that drop old versions (and `keepcache=0`) limit what `undo` can do [src: rhel-10-docs 05d1d38ce8d9280f]. Packages that run scriptlets, change database schemas or alter on-disk data (a database server, for instance) are not meaningfully undone by downgrading the binary. History also records install reason (`user`, `dep`, `weak`, `group`); `dnf mark install <pkg>` and `dnf mark remove <pkg>` change it, which controls what `dnf autoremove` is allowed to delete. Related commands include `dnf downgrade <pkg>`, `dnf reinstall <pkg>`, `dnf distro-sync` (align versions to the repositories, up or down) and `dnf versionlock add <pkg>` (from `python3-dnf-plugin-versionlock`). Where the history list shows a transaction that failed or was interrupted, `dnf history list` and `dnf history info` still return success exit codes in DNF 4 regardless of the transaction state; scripts should read the output [src: man-pages f537bf0eafaf3a76].

For a stronger safety net, pair `dnf` with a filesystem snapshot before large changes (`lvcreate -s`, `btrfs subvolume snapshot` or `snapper`), because history cannot restore data. On image-based systems (`bootc`, `rpm-ostree`) the equivalent is booting the previous deployment.

## Assessment: the good, the bad and the ugly

What works well: the database makes the answer to "what owns this file" or "what changed" a one-line command; verification is cheap and gives a precise signal; the solver is fast and its decisions can be inspected with `--debuglevel` and `dnf repoquery`; transactions are atomic at the RPM level (the whole set is checked and applied together, with a pre-transaction test); and `history` provides a decent audit trail.

What works badly: `undo` is only as good as the availability of old packages and the idempotence of scriptlets. Many users read it as a time machine; it is a best-effort inverse. `rpm -Va` yields noise because configuration files, `%ghost` files and files modified by legitimate tools differ by design, and prelinking or `%post` edits can trigger false alarms. `dnf` metadata caches can go stale, producing "no match" or checksum errors until `dnf clean all` and `dnf makecache`. Kernel-related and module-related transactions can be hard to reason about: modularity (AppStream streams) was deprecated in Fedora and is retained but de-emphasised in RHEL 10, so module commands may confuse readers of older tutorials.

The awkward parts: multiple front ends (`yum`, `dnf`, `dnf5`, `microdnf`, `rpm`, `zypper` on SUSE) have different option sets and exit-code conventions; DNF 4 and DNF 5 differ in plugin names, config keys and some output formats; `rpm --force` and `--nodeps` can make the database lie about reality; and the database can be damaged by interrupted transactions (recoverable with `rpm --rebuilddb` or, in the SQLite era, by restoring a copy). Running two package managers against the same database at once is prevented by a lock, but a stale lock after a crash needs manual cleanup. Security-wise, the verification features assume the database and the keyring are trustworthy.

## Applications beyond this domain

The same structure appears in other package ecosystems and in container images. A database of installed files with checksums, a transaction log and a solver is what `dpkg` plus `apt` do, what `apk` does on Alpine, `pacman` on Arch and `zypper` on SUSE, and what Nix and Guix do with stronger guarantees (immutable store, generations as rollback). The history/undo idea is generalised by filesystem snapshots (Btrfs and ZFS boot environments, `snapper`, `timeshift`), by image-based OS updates (`rpm-ostree`, `bootc`, ChromeOS, Android A/B updates) and by infrastructure as code, where "undo" becomes "apply the previous commit". Verification with digests reappears in `debsums`, in file-integrity monitoring tools (AIDE, Tripwire), in software bills of materials and in container image scanning, where `rpm -qa` output is the raw material for vulnerability matching: scanners read the RPM database inside an image to list components. Sets of compliance rules, such as the ones cited above, automate query and verify steps across fleets.

## Examples

**Who owns this file, and is it intact?** An incident responder finds a suspicious `/usr/sbin/sshd`. `rpm -qf /usr/sbin/sshd` returns `openssh-server-9.9p1-...`; `rpm -V openssh-server` prints `S.5....T.    /usr/sbin/sshd`, size, digest and mtime all differ. The binary is not what the vendor shipped. The next step is to preserve it for analysis, reinstall with `dnf reinstall openssh-server`, and look at how the file changed (which `rpm -V` cannot tell). Note the limits: if the attacker also rewrote the RPM database, the check passes, so run the same verification from a trusted rescue image.

**What changed last night?** A service broke after unattended updates. `dnf history list` shows transaction 87 at 02:10 from `dnf-automatic`; `dnf history info 87` lists `openssl-libs` and 31 other upgrades. After `dnf history undo 87` succeeds, the broken service works again. The administrator then excludes the package version (`dnf versionlock add openssl-libs`) and opens a bug.

**A failing undo.** The same `undo` on an older transaction fails with a message that a package is unavailable. The repository mirror removed the older version of one library, and `keepcache` was off, so nothing local provides it. The fix is to restore from a snapshot, or from a satellite or mirror that retains history, and the lesson for the build team is to keep old versions in internal mirrors.

**Inventory for an audit.** `rpm -qa --qf '%{NAME}\t%{VERSION}-%{RELEASE}\t%{VENDOR}\t%{INSTALLTIME:date}\n' | sort` produces a machine-readable list of installed software with vendor and install time, which can be compared across hosts or fed into a scanner.

**Checking a CVE fix.** On a clone distribution that backports fixes, version numbers do not reveal whether a CVE is closed. `rpm -q --changelog openssl | grep CVE-2024-XXXX` shows whether the vendor's changelog mentions it, and the distribution's CVE tracker confirms it [src: rocky-docs 1e1f354fe5c6e8a6].

## Related problems and ideas

Neighbouring problems include dependency conflicts (covered in the dependency troubleshooting topic), reproducible installs (kickstart, image builders, `dnf --installroot` for chroot builds), patch management at fleet scale (Satellite, Foreman/Katello, Pulp, `dnf-automatic`) and software provenance (SBOMs, signed repositories, Sigstore for artefacts). Alternatives that challenge the mutable-package model include image-based systems (`bootc`, Fedora Silverblue, CoreOS), where a new full image replaces the old and rollback is a reboot; functional package managers (Nix, Guix) that make every build input explicit; and container-only deployment where the host rarely changes. Ideas not yet mainstream include content-addressed package stores with deduplicated delta updates, transactional updates with atomic filesystem switch for traditional RPM hosts (as in openSUSE's `transactional-update`), and cryptographic transparency logs for repository content.

## Active research

Work in this area focuses on the DNF 5 rewrite and its plugin ecosystem; faster metadata (zchunk, which transfers only changed chunks, and libsolv speedups); RPM's evolution (the signature format work for modern algorithms and post-quantum signing readiness, per-package SBOM metadata, file-level `fsverity` signatures and reproducible builds); and integrity measurement (IMA, `fs-verity`) as a successor to `rpm -V` for runtime enforcement. Researchers and distribution engineers study how to make rollback dependable when packages carry state, and how to certify supply chains end to end. Open questions include how to keep a traditional package system and an image-based system consistent on the same host, and how to define a sound semantics for "undo" when scriptlets have side effects.

## Future direction

Expect DNF 5 to become the default across the RHEL family as the next major or minor releases adopt it; plan scripts to tolerate both (use `rpm` queries and `--qf` for stable output, and test `dnf history` parsing against both versions). Image-based and transactional deployment will absorb more server fleets, reducing the number of hosts where `dnf history undo` is the main recovery path, while `rpm -q` and `rpm -V` stay valuable for inventory and forensics. Signature and digest algorithms will move away from SHA-1 and 2048-bit RSA and toward SHA-256 and stronger keys; watch release notes for crypto-policy changes that make old keys or packages fail verification. Administrators should keep three habits whatever the tools: query before changing, snapshot before large transactions and test the undo path on a clone.
