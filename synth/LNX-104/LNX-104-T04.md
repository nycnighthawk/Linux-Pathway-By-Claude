# Distributing desktop applications with Flatpak: remotes, refs, installations and sandboxes

## Define the problem

Distribution packages are built for one release of one distribution. An application that needs a newer GTK, a different Python or a specific codec library has to wait for the next release, or its author has to publish packages for every distribution, or the user has to compile it. Fixed-release enterprise systems feel this most: a RHEL release freezes the desktop stack for years while browsers, mail clients and design tools move monthly. At the same time, a conventional package runs with the full privileges of the user who started it. A compromised media player can read the user's SSH keys and browser profiles, because the package system has no idea what the program should be allowed to touch.

Flatpak addresses both needs together. It delivers applications independently of the host distribution, bundled with or built against a shared **runtime**, and it runs each application inside a **sandbox** with declared permissions. The administrator's questions change accordingly: the questions become which remote supplies this application, whether that remote is trusted, which runtime the application needs, which permissions it will get, and whether it is installed per user or for the whole machine The topic also became an explicit certification objective for RHEL 10, because that release changes how some desktop applications are delivered [src: rhel-10-docs e90c10b10427bbab]. This slice covers the concepts (refs, remotes, installations, runtimes), the commands, remote configuration, permission overrides and the enterprise points an administrator needs. Building Flatpaks with `flatpak-builder` and the publishing side are mentioned only to explain the model.

## History and approaches

Several earlier attempts tried to make applications independent of the distribution. Static linking and tarball installs worked for self-contained programs but gave no updates, no sharing of libraries and no isolation. The Linux Standard Base (LSB) tried to define a common base that all distributions would provide; the LSB failed because distributions did not hold to it and vendors still had to test many combinations. Per-distribution third-party repositories worked but multiplied the packaging effort and still ran unconfined.

Containers inspired the next generation. Around 2013 to 2016 several projects pursued the idea: Ubuntu's Snap (Canonical), `AppImage`, and Alexander Larsson's `xdg-app`, renamed **Flatpak** in 2016. All three combine a distribution-neutral bundle with some form of isolation, but their designs differ in consequential ways. Snap uses a single store controlled by Canonical, squashfs images and AppArmor-based confinement; AppImage is a single executable file with no sandbox and no managed updates; Flatpak is decentralised (anyone can run a **remote**), built on OSTree for content-addressed storage and efficient delta updates, and uses `bubblewrap` (Linux namespaces) plus seccomp for confinement. Flathub, started in 2017, grew into the main shared remote. Fedora adopted Flatpak for its desktop editions and Silverblue, GNOME and KDE published runtimes, and the RHEL family offered Flatpak support in earlier releases as an optional desktop component (to verify per release). Reception was mixed. Critics pointed to larger disk use, uneven sandbox quality (many applications request broad filesystem access, which defeats isolation), and update latency for security fixes in shared runtimes. Supporters pointed to faster delivery and real isolation when permissions are narrow.

In RHEL 10 the status changed: the default delivery method for the Firefox and Thunderbird applications moved from RPM packages to Flatpaks [src: rhel-10-docs e90c10b10427bbab], and the release notes of the clone distributions show the same direction [src: rocky-docs 53b5dbb0453e906c]. The pattern behind these shifts is a split between a stable core operating system, delivered by packages or images, and fast-moving applications, delivered in sandboxed, independently updated units. The operating system layer itself is going the same way through image-based variants, an idea RHEL for Edge images already expressed [src: rhel-10-docs 875163e02e76a714].

## Current state

### The model

A **ref** names a deployable thing. Its full form is `kind/name/arch/branch`, for example `app/org.mozilla.firefox/x86_64/stable` or `runtime/org.freedesktop.Platform/x86_64/24.08`. `kind` is `app` or `runtime`; `name` is a reverse-DNS identifier; `arch` is the CPU architecture; `branch` is a channel or runtime version (often `stable`, or a year-based branch such as `24.08`). Extensions (locales, codecs, GL drivers, themes) are runtimes of the form `org.freedesktop.Platform.GL.default` and are installed automatically. A **runtime** is a shared set of libraries (Freedesktop Platform, GNOME Platform, KDE Platform) that several applications build against; an application is installed together with the runtime it needs, and several runtime versions can coexist [src: rocky-docs e08f378bb5563bc6].

A **remote** is a named OSTree repository (an HTTP(S) location, or an OCI registry) with a GPG key or other trust information. An **installation** is a location on the host where refs are deployed and where remotes are recorded: the default **system** installation (`/var/lib/flatpak`), the per-**user** installation (`~/.local/share/flatpak`), and optional named system installations declared in `/etc/flatpak/installations.d/*.conf` (for example a shared disk or a USB stick). Remotes belong to an installation: a remote added with `--user` is invisible to the system installation and the reverse. The remote definitions are stored in the `repo/config` file of each installation, and normally changed with `flatpak remote-modify` rather than by editing the file; system-wide remotes can be preconfigured by placing `.flatpakrepo` files in `/usr/share/flatpak/remotes.d/` or `/etc/flatpak/remotes.d/`, where the file under `/etc` wins when names collide [src: man-pages 468a74ac450e1e52].

### Commands

The command set is listed in the manual page, grouped into managing installed software, finding software, managing running applications, file access, permissions and building [src: man-pages 79b0cd88d5f89128]. The commands an administrator uses most:

```bash
# remotes
FLATHUB=https://dl.flathub.org/repo/flathub.flatpakrepo
flatpak remote-add --if-not-exists flathub $FLATHUB
flatpak remote-add --user --if-not-exists myrepo /path/or/URL/to/remote.flatpakrepo
flatpak remotes -d                      # list remotes with title, URL, options (-d = details)
flatpak remote-ls flathub --app         # applications offered (--runtime for runtimes)
flatpak remote-info flathub org.gimp.GIMP   # metadata, size, runtime, permissions
flatpak remote-modify --disable flathub     # or --enable, --prio=, --url=, --no-gpg-verify (avoid), --filter=FILE
flatpak remote-delete flathub

# installed software
flatpak search gimp
flatpak install flathub org.gimp.GIMP           # system installation by default when run as root or with polkit
flatpak install --user flathub org.gimp.GIMP    # per-user
flatpak install --noninteractive -y flathub org.gimp.GIMP
flatpak install --from https://example.org/app.flatpakref
flatpak install --bundle ./app.flatpak          # a single-file bundle (flatpak build-bundle)
flatpak list [--app|--runtime] [--columns=application,version,branch,installation]
flatpak info [--show-permissions] [--show-commit] org.gimp.GIMP
flatpak update [-y] [--appstream]               # all, or a named ref
flatpak uninstall [--delete-data] org.gimp.GIMP
flatpak uninstall --unused                      # remove runtimes nothing needs
flatpak history; flatpak repair [--user]        # log of operations; verify and fix local store
flatpak mask 'org.example.*'; flatpak pin org.freedesktop.Platform//23.08   # block updates; keep a runtime

# running applications and permissions
flatpak run org.gimp.GIMP; flatpak run --command=sh org.gimp.GIMP
flatpak ps; flatpak kill org.gimp.GIMP
flatpak override --user --nofilesystem=home org.gimp.GIMP     # per-app change
flatpak override --show org.gimp.GIMP
flatpak permissions; flatpak permission-reset org.gimp.GIMP
flatpak config --set languages 'en;de'         # installation-wide keys (languages, extra-languages, report-os-info)
flatpak create-usb /mnt/usb org.gimp.GIMP      # copy apps and runtimes to removable media for offline installs
```

`flatpak config` shows or changes installation keys: `languages` and `extra-languages` choose locale extensions, and `report-os-info` controls whether the OS name, version and architecture from `/etc/os-release` are sent to the remote [src: man-pages 1d3af251bb5222a3]. `flatpak create-usb` copies chosen refs and runtimes onto removable media, which is how disconnected sites supply updates [src: man-pages d54419600a882f8c]. The Rocky Linux desktop guide documents the same commands with examples of `flatpak list` output [src: rocky-docs 33db384730ad4186].

### Remote definitions and trust

A `.flatpakrepo` file is an INI file with a `[Flatpak Repo]` group, with keys such as `Title`, `Url`, `GPGKey` (base64-encoded public key), `Homepage`, `Comment`, `Description`, `Icon`, `DefaultBranch` and `NoDeps`; `flatpak remote-add` reads it and fetches the repository. A `.flatpakref` file describes a single application (with `Name`, `Branch`, `Url`, `RuntimeRepo` and `IsRuntime`) and, if the application's remote is not configured, offers to add it. Remotes have two trust layers. Content signatures: OSTree commits are signed with the GPG key stored in the remote's configuration (`gpg-verify=true` by default; `--no-gpg-verify` disables it and should not be used outside lab work). Transport: HTTPS. Commit metadata also contains the permissions the application requests, which Flatpak shows before installation. For enterprise registries, a remote may be an OCI registry (`oci+https://...`), where the registry's own authentication and image signatures apply; Red Hat delivers its application Flatpaks through its container registry with entitlement credentials (to verify the exact remote name and authentication method for the release in use). A **filter** (`--filter=FILE`) restricts a remote to an allow- or deny-list of refs, which lets an organisation expose a curated subset of a public remote.

### Sandbox and permissions

Each application runs in a fresh mount, PID and network-optional namespace created by `bubblewrap` (`bwrap`), with a seccomp filter, and with only the runtime and its own data directory (`~/.var/app/<app-id>/`) visible by default. Access to everything else is granted through permissions declared in the application's metadata and adjustable by `flatpak override`. The permission families are: `--share=network` and `--share=ipc`; `--socket=x11`, `--socket=wayland`, `--socket=pulseaudio`, `--socket=ssh-auth`, `--socket=session-bus` and `--socket=system-bus` (the last two are broad and weaken the sandbox); `--device=dri`, `--device=all`; `--filesystem=host`, `--filesystem=home`, `--filesystem=/path:ro`, `xdg-download` and the other `xdg-*` names; `--talk-name=` and `--own-name=` for D-Bus names (filtered by `xdg-dbus-proxy`); and `--env=`. Portals (`xdg-desktop-portal` with backends for GNOME, KDE and others) offer controlled access to files, printing, screenshots and the camera by asking the user at run time, which is why a well-built application needs few static permissions. Overrides live per user in `~/.local/share/flatpak/overrides/` or system-wide in `/var/lib/flatpak/overrides/`; `flatpak override --show` prints the effective override. The tools `flatpak info --show-permissions` and the permission store (`flatpak permissions`) reveal what an application can do, and a graphical tool, Flatseal, edits the same data.

### Enterprise administration

Installing system-wide software is controlled by polkit actions (`org.freedesktop.Flatpak.app-install`, `app-update`, `runtime-install`, `modify-repo`), so ordinary users can be allowed or forbidden to install, with or without a password. Automatic updates come from GNOME Software, from systemd timers or services shipped by distributions (for example Fedora's `flatpak-system-helper` and user update timers) or from a unit that runs `flatpak update --noninteractive -y`. Offline and air-gapped fleets mirror a remote with `flatpak create-usb`, or with `ostree` tooling and an internal HTTP server, and distribute a `.flatpakrepo` pointing to it. Disk use can be reviewed with `flatpak list --columns=size` and cleaned with `flatpak uninstall --unused`; the OSTree repository under `/var/lib/flatpak/repo` deduplicates files across refs, so the second application using the same runtime costs little. For image-based systems, preinstalling Flatpaks into an image is possible with the installer or image-builder tooling, which is the usual route on RHEL 10 for the default browser and mail application (to verify per release).

## Assessment: the good, the bad and the ugly

What works well: applications update independently of the OS; one build runs on many distributions; the shared runtime and OSTree storage keep duplication tolerable; remotes are cheap to define and to restrict; and the sandbox can really limit an application when permissions are narrow, with portals handling user-mediated access. A fixed-release operating system gains modern desktop applications without risking the base.

What works badly: the quality of the sandbox depends on the maintainer; many popular applications ask for `--filesystem=host` or `--socket=session-bus`, which makes the confinement largely cosmetic. Security fixes in a runtime need a new runtime version and a rebuild of every application using it, so an end-of-life runtime branch keeps vulnerable libraries on the machine. Integration problems appear in places where the sandbox hides the host: command-line tools cannot see Flatpak applications by default, browser extensions and native messaging hosts need explicit bridges, themes and fonts can differ from the host, and hardware access (printers, smart cards, GPUs, USB) needs permissions or portals. Disk use is higher than with native packages and can reach several gigabytes with multiple runtimes.

The awkward parts: system and user installations are separate worlds with separate remotes and runtimes, a frequent source of confusion when an application seems installed but cannot be seen. Enterprise policy is thinner than for RPM: there is no central equivalent of `dnf versionlock` beyond `mask` and `pin`, and auditing what is installed across a fleet needs custom collection from `flatpak list`. Software Bill of Materials and vulnerability scanning for Flatpaks is less mature than for RPMs. Finally, the split between the distribution's package manager and Flatpak means two update streams to monitor, and both appear in a compliance scope.

## Applications beyond this domain

The ideas apply wherever software must be delivered independently of the base system with isolation. Container images use the same layering of a shared base and application layers; Flatpak's OSTree store is the same content-addressed approach used in `rpm-ostree` and `bootc` for operating systems. Snap and AppImage solve overlapping problems with different trade-offs. Mobile platforms (Android, iOS) require per-application permissions and a store, and browser extensions and WebAssembly sandboxes use capability prompts much like portals. The portal idea (the user chooses a file in a trusted dialog and the application receives only that file) has been generalised in desktop sandboxes on macOS and Windows. In the server world, systemd unit sandboxing options (`ProtectSystem=`, `PrivateTmp=`, `DynamicUser=`) and container security policies apply similar least-privilege thinking to services.

## Examples

**Installing a desktop application for all users.** On a RHEL 10 or Rocky 10 workstation an administrator adds the Flathub remote file with `flatpak remote-add` and the `--if-not-exists` option, then runs `flatpak install flathub org.gimp.GIMP`, and verifies with `flatpak list --app --columns=application,branch,installation`. The installation column reads `system`, and users can launch the application from the menu without extra steps [src: rocky-docs e08f378bb5563bc6].

**Restricting an over-permissive application.** `flatpak info --show-permissions org.example.Editor` reveals `filesystems=host;`. The administrator creates a system-wide override, `flatpak override --nofilesystem=host --filesystem=xdg-documents org.example.Editor`, tests that file dialogs still work through the portal, and records the override in configuration management. If the application breaks, `flatpak override --reset org.example.Editor` removes the change.

**A "not found" that is a scope mistake.** A user added a remote with `--user`, then an administrator running `sudo flatpak install flathub org.gimp.GIMP` gets `error: Remote "flathub" not found`. The remote exists only in the user's installation. The fix is to add it for the system installation, or to install with `--user`; `flatpak remotes --show-details` run both ways shows the difference.

**Keeping a runtime.** A site standardises on an older runtime branch for a line-of-business tool. `flatpak pin org.freedesktop.Platform//23.08` stops automatic removal when the tool's update moves to a newer branch, and `flatpak mask` prevents the unwanted upgrade. A calendar entry tracks the runtime's end-of-life date so the pin does not outlive security support.

**An offline lab.** `flatpak create-usb /run/media/admin/STICK org.mozilla.firefox` copies the application and its runtimes; on the disconnected machine, plugging the stick in and running `flatpak install --sideload-repo=...` or using the desktop software tool installs from it [src: man-pages d54419600a882f8c].

## Related problems and ideas

Neighbouring problems include snap and AppImage management, native packages versus Flatpaks for the same application (a user may end up with both a distribution Firefox and the Flatpak, with different profiles), the maintenance of end-of-life runtimes, mirroring and curation of a remote, and desktop integration of sandboxed applications with the rest of the system. Alternative or complementary approaches include image-based operating systems that ship applications as Flatpaks and keep the base immutable (Fedora Silverblue, Kinoite and their derivatives, as well as RHEL image mode with `bootc`), distrobox and toolbox for development environments inside containers, Nix and Guix for declarative per-user environments, and OCI-based desktop application delivery. Proposals not yet mainstream include fine-grained permission prompts at run time for all sandbox-relevant resources, per-remote policy for allowed permissions (so that an application requesting `--filesystem=host` cannot be installed from the corporate remote), and signed provenance for builds.

## Active research

Work continues on Flatpak's own evolution (a preinstall mechanism for administrators, better enterprise policy and a successor to the Flathub build and publication pipeline), on portals for more resource types such as USB devices and global shortcuts, on stronger sandboxing through user namespaces and Landlock, and on supply chain protections for Flathub: verified publishers, reproducible builds, and build provenance attestations. Researchers study how often applications' declared permissions exceed what they need and how to tighten this automatically, and whether runtime-based sharing creates a security-update lag compared with distribution packages. Open questions include how to scan Flatpak applications for vulnerabilities in a way that compliance frameworks accept and how to manage thousands of desktops with per-application permission policy.

## Future direction

The trend in enterprise Linux is a stable base operating system with applications delivered as sandboxed units, so expect more first-party applications from distributions to move to Flatpak, as Firefox and Thunderbird did in RHEL 10 [src: rhel-10-docs e90c10b10427bbab]. Expect administrators to gain declarative control (preinstall lists, remote allow-lists, permission policy), to see Wayland-only sessions as the default (RHEL 10 drops the X.Org server session in favour of Wayland, which already affects sandbox permissions such as `--socket=x11`) [src: rocky-docs 53b5dbb0453e906c], and to rely more on image-based deployments where the Flatpak set is part of the image. For the next few years, a sound practice is to inventory remotes and installations, review permissions of what is installed, track runtime end-of-life dates, and treat Flatpak updates as part of patching, not as a separate desktop concern.
