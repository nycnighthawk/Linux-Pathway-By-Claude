# Linux in a real Windows Active Directory estate, with a trust

## Define the problem

A lab built on Samba is a faithful teaching tool, but production estates run Microsoft's own domain controllers, with their group policy, site topology, certificate services and security defaults. A Linux engineer must prove that the estate described as code also works against that real directory: hosts join, users sign in, services authenticate with Kerberos, and a cross-realm trust with an IdM domain behaves under the stricter rules. This slice covers testing on a genuine Windows domain, which most people cannot run in a shared pipeline because of licensing and hardware, so the work is done by hand on self-provided infrastructure and documented as evidence.

## History and approaches

Linux first joined Windows domains through Samba's winbind, which maps Windows identities into Unix ones inside Samba's own daemon. Later, SSSD took over most membership duties, using the adcli or realmd tools to create the computer account and keytab, and reading identities straight from the domain controller over LDAP. For the other direction, FreeIPA added a trust feature: the IdM domain and the AD forest trust each other, using Samba components on the IdM server to speak the Windows protocols. Each step reduced the need for software on the Windows side, and moved decisions about identity mapping, time and name resolution to the Linux administrator.

## Current state

### The parts

A genuine test needs a Windows server promoted to domain controller with DNS, at least one Windows member for comparison, and network reachability to the Linux hosts. For a trust, the forest functional level, name resolution between the two DNS zones (conditional forwarders or stub zones) and open ports for Kerberos, LDAP, SMB and RPC all need attention. Linux members join with a realm join, receive a keytab, and sign in using Kerberos with SSSD handling identity and the access filter.

### How the mechanism applies

The tests that matter are: join succeeds and the machine account has the expected attributes; an AD user logs in over SSH with a password and with a ticket; a group-based access rule works; a file share is mounted with the machine or user credentials; and after the trust is created, an AD user can authenticate to an IdM-enrolled host and be mapped to an identity with a stable numeric ID. Failures usually show in three places: the SSSD domain log, the Kerberos trace output from the client, and the Windows event log on the domain controller.

### Generalised pattern

Verify identity at three layers separately: name resolution and time, then authentication, then authorisation and ID mapping. Do not move up a layer until the one below is proven.

## Assessment: the good, the bad and the ugly

Testing on the real thing finds problems that Samba hides: stricter ticket encryption defaults, channel binding and LDAP signing requirements, and group policy that overrides local settings. The bad is cost and reproducibility: a licensed Windows lab cannot be created by an open pipeline, so results depend on notes and screenshots, and they decay when patches change defaults. The ugly includes encryption type changes that silently break older keytabs, SID-to-UID ranges that collide between two domains, and a trust that works from one direction only because of a DNS forwarder nobody wrote down.

## Applications beyond this domain

The three-layer discipline is how engineers debug any federation: SAML or OIDC between companies, cloud identity providers federated to an on-premises directory, and cross-organisation certificate trust. The practice of keeping manual evidence next to automated tests applies wherever a dependency cannot be reproduced in a pipeline.

## Examples

A worked example: the join succeeds but SSH login fails with an access-denied message. The SSSD log shows the user resolves but the group lookup returns nothing, because the domain controller denied anonymous-style queries after a signing policy change; the fix was to use the machine keytab for lookups. A failing example: a trust created in a rush used the short NetBIOS name for the AD side in a forwarder, so lookups worked only on the host where it was typed; recording the forwarder in the code and a test that resolves a name from both sides closed the gap.

## Related problems and ideas

Related problems include Linux-side group policy equivalents, certificate auto-enrolment on Linux, and printing. Alternative designs are plain winbind membership, or avoiding trust by giving each user one directory only. Emerging ideas include cloud-hosted directories with Linux login through a vendor agent and passwordless sign-in for hybrid users.

## Active research

Community and vendor work covers hardening defaults in both ecosystems and testing methods that script a Windows lab from images. Open questions are how to record manual lab runs in a way a reviewer can trust, and how to detect policy changes on the Windows side before they break Linux logins (to verify against vendor advisories).

## Future direction

Expect Kerberos encryption defaults to tighten further, more use of cloud-based identity with on-premises sync, and increasing support for certificate and passkey login in SSSD. Check the vendor's current security baselines before each test run (to verify).
