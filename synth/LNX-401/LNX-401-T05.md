# Taking the estate baseline to a public cloud

## Define the problem

An estate defined as code should be portable in its intent even if its hosting changes. Many organisations extend into a public cloud for capacity or recovery, and the Linux baseline, identity, repository and monitoring must follow. The problem is to deploy the same baseline to cloud instances, with cloud-specific parts (networking, instance identity, images) expressed separately, and to compare behaviour against the on-premises build. The slice relies on a real cloud account, so it is practised manually and graded from evidence.

## History and approaches

The first cloud workloads were lifted virtual machines. Cloud images with first-boot agents (cloud-init) made instances configurable on start, and infrastructure-as-code tools described networks and instances declaratively. Cloud providers added their own directory services and instance identity, and offered managed images with vendor tuning. Hybrid designs connect on-premises directories to the cloud with VPN links and replicas.

## Current state

### The parts

A cloud deployment has a network layer (virtual network, subnets, security groups), compute (instances from a hardened image), identity (instance roles for provider APIs, and the estate's own directory reached through a private link), a repository mirror reachable from the subnet, and monitoring that scrapes or receives metrics.

### How the mechanism applies

The code splits into an infrastructure module for the cloud and the same configuration roles used on premises, driven by a cloud inventory. Cloud-init sets hostname, keys and the first connection to configuration management. Directory enrolment uses a replica or a read-only path in the cloud network. Cost and security controls (tags, budgets, least-privilege roles) are set in code from the start.

### Generalised pattern

Separate what is provider specific from what is estate specific, and write comparisons that show where they differ.

## Assessment: the good, the bad and the ugly

Reuse of roles saves effort, and ephemeral instances are cheap to test. The costs are unexpected bills, differences in default kernels and agents, metadata service security, and latency to the on-premises directory. The ugly parts are leftover resources, public exposure by a mistaken rule, and long-lived credentials in the wrong place. Teardown must be part of the exercise.

## Applications beyond this domain

The module-plus-roles split is used for multi-cloud, for disaster recovery regions, and for edge deployments where the hosting differs but the application stack is the same.

## Examples

A worked example: the baseline is applied to three instances; the time source differs from the on-premises design and Kerberos fails until the provider's time service is configured. A failing example: a test environment left running for a week; a budget alert written in code caught it and the teardown play removed it.

## Related problems and ideas

Related topics are landing zones, cloud-native identity federation, and image pipelines per provider. Alternatives are managed directory services and fully managed configuration services.

## Active research

Areas include confidential computing for instances, workload identity without static keys, and policy checks on plans before apply (to verify).

## Future direction

Expect tighter integration of provider identity with Linux login, and more cost guardrails in code.
