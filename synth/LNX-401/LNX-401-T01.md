# An enterprise estate defined as code: identity, servers, repository and monitoring

## Define the problem

A mid-sized organisation runs a mix of Linux releases, a directory for users and hosts, a package source it trusts, and a way to see when something breaks. In most places these parts grew one at a time, by hand, and nobody can say what the whole looks like or rebuild it after a loss. The problem in this capstone is to describe an entire estate, in files under version control, so that a clean set of machines can be turned into that estate repeatedly and a reviewer can read what exists. The scope of this slice is the first build: a FreeIPA-based identity domain and a Samba-based Active Directory domain controller living side by side, six servers of mixed families that join them, an internal package repository, and a monitoring stack that watches all of it. Failure looks like a host that works only because someone typed a command years ago, a join that breaks at the next certificate expiry, or a dashboard that is blank on exactly the day it is needed.

## History and approaches

Early estates were built by installing each machine and editing files in place, with shell scripts as the only memory. Configuration management tools in the 2000s moved the desired state into declarative files, and later infrastructure tools did the same for the machines themselves. Directories followed their own path: NIS gave way to LDAP with Kerberos, and the Windows world standardised on Active Directory, which Samba later learned to implement as a domain controller. FreeIPA, shipped by Red Hat as IdM, bundled LDAP, Kerberos, a certificate authority, DNS and policy into one product so that Linux-first sites did not have to assemble these themselves. Each approach left a gap: hand building did not scale, scripts did not converge, and single-product directories did not talk to the other vendor's domain. The pattern that emerged is layered: provisioning creates the machine, configuration management describes its state, the directory supplies identity and policy, a repository supplies the exact package set, and monitoring closes the loop.

## Current state

### The parts

An estate as code has five planes. The identity plane has one IdM domain with at least a primary and a replica server, and a Samba AD domain controller for the Windows-style realm, joined by a forest or external trust so that users in one realm can reach services in the other. The compute plane has six servers, deliberately mixed, for example two from the Red Hat family, two Debian-family hosts and two others of a different release age, which forces the code to handle package, service and firewall differences. The repository plane is a mirror or snapshot of the distribution content plus internal packages, signed, published over HTTP and pinned to dated snapshots. The monitoring plane scrapes metrics and collects logs. The glue is an inventory and a set of roles in a configuration management tool, held in a Git repository.

### How the mechanism applies

The inventory names every host once, with groups for role, family and environment. Roles express intent: join a host to IdM with a client enrolment, or to AD with a realm join; configure SSSD; point package managers at the internal repository; install the node exporter and the log shipper; apply a baseline. Ordering matters: DNS and time must be right before Kerberos works, Kerberos before enrolment, enrolment before policies take effect. The code states these dependencies as plays in sequence, and uses secrets storage for the join credentials. A verification step at the end asks real questions: can a directory user log in over SSH with a ticket, does the repository serve the pinned snapshot, do all targets appear as up in the monitoring system.

### Generalised pattern

Describe the desired estate as data, derive every host's behaviour from its group memberships, run in a defined order, and finish with checks that read the same data to decide what to expect.

## Assessment: the good, the bad and the ugly

The strength is repeatability: the same files rebuild the estate, and a diff shows what changed. Reviews catch mistakes before they reach a server. The weak points are time and trust. DNS delegation between the IdM and AD realms is easy to get subtly wrong, and clock skew of more than a few minutes breaks Kerberos without a clear message. Bootstrap secrets are a chicken-and-egg problem: the tool that stores them has to be reachable before the directory exists. Mixed families create combinatorial test cost. The ugly part is state that lives outside the code: the CA key, directory data and replica agreements cannot be recreated from playbooks alone, so backups and documented recovery are part of the estate, not an add-on. Running two directories also doubles patching and certificate renewal duties.

## Applications beyond this domain

The same layered, data-first structure is used for cloud landing zones, where an account baseline, network, identity and logging are all declared and then verified. It is used for lab fleets in education, for edge sites that must be rebuilt without an expert on site, and for compliance regimes that ask for an inventory with evidence. What carries over is the habit of making the inventory the source of truth and writing checks that derive expectations from it.

## Examples

A worked example: a team declares eight hosts. The playbook joins six Linux servers to IdM, installs a replica on host two, and sets up a trust to the Samba domain. A user from the other realm logs in over SSH with a Kerberos ticket and lands on a Debian server, but not on a Red Hat one. The cause, found with the SSSD debug log, is a missing domain entry in a configuration template used only for that family. A second, failing example: the monitoring job was added last and scrapes by IP address; after a replica was rebuilt with a new address, the target silently disappeared and the alert for missing targets had never been written. The fix was to scrape by inventory name and to alert when the target count falls below the inventory count.

## Related problems and ideas

Neighbouring problems are bootstrapping trust (who provisions the first secret), disaster recovery for directory data, and drift between code and reality. Alternatives include Windows AD alone with Linux members, or an IdM-only estate with no Windows domain; both reduce moving parts if the business allows. Newer ideas include image-based hosts that carry their baseline inside the image, and pull-based configuration agents that replace push runs.

## Active research

Work continues on declarative directory management (so that users, groups and policies are also code), on automatic detection of drift between inventory and live systems, and on measuring how much of an estate's behaviour is actually exercised by its tests. Open questions include safe automated rotation of CA material and the best test boundary for multi-host plays (to verify against current practice).

## Future direction

Expect more image-mode hosts, passkey and smart-card login for administrators, tighter integration of policy as code with the directory, and wider use of OpenTelemetry-based collection next to metric scraping. Version details of IdM, Samba and the distributions change quickly; read the current release notes before pinning (to verify).
