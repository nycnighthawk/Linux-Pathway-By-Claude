# The lifecycle of an estate host: provision to decommission

## Define the problem

A server is not a thing that is built once. It is created, brought to a secure baseline, kept patched, moved to a new release, and finally removed with its data and credentials. If any step is manual or forgotten, the estate collects unknown machines: hosts with old keys, stale directory entries and accounts nobody owns. This slice covers the whole lifecycle as repeatable code, for the six mixed servers of the capstone, and the tests that prove each step.

## History and approaches

Hosts used to be installed from media and tuned by hand. Unattended installers (Kickstart, preseed, autoinstall) and network boot made installation scriptable, cloud images and cloud-init made first boot configurable, and image builders produced the same base everywhere. Hardening started as checklists, then became machine-readable profiles scanned and remediated by tools. Patching moved from individual updates to staged rings against dated repository snapshots. Major upgrades got dedicated tools for each family, and decommissioning stayed the neglected end for a long time, handled by deleting a virtual machine and hoping nothing remained.

## Current state

### The parts

Provisioning builds the machine from an image or an automated install and registers it in inventory, the directory and monitoring. Hardening applies a baseline profile and records the result of a scan. Patching consumes the pinned snapshot, rolls out in rings (a canary host first, then the rest) and checks health between rings. An upgrade moves a host to the next major release with the family's tool, after backups and a dry run. Decommissioning reverses registration: remove the host from the directory, revoke its certificates and keytab, remove monitoring targets and inventory entries, and wipe or destroy the storage.

### How the mechanism applies

Each stage is a separate entry point in the code, with its own check. Provision ends when a scan and a login test pass. Patch ends when the snapshot version on the host matches the target and services are healthy. Upgrade ends when the release file and kernel match the target and the baseline scan still passes. Decommission ends when queries to the directory, the certificate authority, the repository and monitoring all find nothing for the name.

### Generalised pattern

Make every lifecycle step idempotent, give it an explicit precondition and a postcondition check, and let the inventory state (for example a lifecycle field) drive which step runs.

## Assessment: the good, the bad and the ugly

Lifecycle code gives auditors a trail and gives operators a safe way to repeat work. The costs are test time and the risk that a hardening profile breaks an application. Rings lengthen patching but contain bad updates. Major upgrades remain the hardest: tools differ between families, third-party repositories block them, and rollback usually means restoring a snapshot. The ugly part is orphaned state: directory objects, DNS records, certificate serials and monitoring series survive a deleted machine unless the decommission code removes each one.

## Applications beyond this domain

The same stages apply to containers and cloud instances (build, scan, deploy, update, retire), to network devices, and to user accounts, where joiner, mover and leaver processes have the same shape. Software supply chains use staged rollouts and revocation the same way.

## Examples

A worked example: a canary host takes the new snapshot, a health check fails because a service depends on a library the update replaced, and the ring stops before the other five hosts are touched. A failing example: a host was decommissioned by deleting its virtual machine; months later its stale directory entry let an old keytab authenticate. The new decommission play removes the principal and revokes the certificate, and a test asks the directory and CA for the name.

## Related problems and ideas

Neighbouring problems are configuration drift, secure erase of disks, key management and license reclaim. Alternatives are immutable hosts replaced rather than patched, and image-mode systems updated as a whole. These shift upgrade effort from the host to the image pipeline.

## Active research

Work includes safer automated major upgrades, better rollback for package-based systems, and live patching coverage. Open questions are how to measure the safety of ring promotion rules and how to verify a wipe on virtual and cloud storage (to verify against current guidance).

## Future direction

Expect wider use of image-based updates with atomic rollback, more built-in baseline profiles, and tighter coupling between inventory state and policy. Verify current release lifecycles before planning an upgrade (to verify).
