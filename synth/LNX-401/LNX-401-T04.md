# Running the estate for thirty days

## Define the problem

An estate that passes its build tests can still fail in ordinary life: certificates expire, disks fill, a replica falls behind, a patch ring stalls, a user is locked out at the wrong time. Only time reveals these. The problem is to operate the estate for a defined period, record what happened, and show that routine duties, alerts and handovers work. The slice treats the operation period as a graded exercise that cannot be compressed into a CI run, so it relies on evidence kept by the operator.

## History and approaches

Operations practice grew from ad hoc firefighting to structured disciplines: service management frameworks that define incidents, problems and changes; site reliability engineering, which adds objectives, error budgets and blameless review; and on-call practices with runbooks. Game days and fault injection came later as ways to practise before real failures. Simulated operation periods are used in training because real production incidents cannot be scheduled.

## Current state

### The parts

A thirty-day run has a calendar of scheduled duties (patch rings, certificate checks, backup restore tests, access reviews), a set of injected or natural events, a log of alerts and responses, and a short review at the end. The monitoring stack provides the alert source; a ticket or journal records each action with time, cause, fix and follow-up.

### How the mechanism applies

The operator keeps a daily log with at least the alerts that fired, those that should have fired and did not, and manual actions taken. Each manual action is checked to see whether it should become code. Service level indicators are computed from the monitoring data, for example login success rate and repository availability, and compared to written objectives. Handover notes at weekly boundaries test whether another person could continue.

### Generalised pattern

Plan the duties, record the events, measure against stated objectives, and turn each repeated manual action into code or a runbook.

## Assessment: the good, the bad and the ugly

The exercise shows real gaps: noisy alerts, missing alerts, undocumented steps and fragile renewals. Its weakness is that simulated incidents are milder than real ones and that evidence is only as honest as the log keeper. Time is also a cost: a month cannot be compressed. The ugly part is alert fatigue, where a few flapping alerts hide a real one, and the temptation to fix problems by hand without recording them.

## Applications beyond this domain

Game days, disaster recovery drills, tabletop exercises for security teams, and apprenticeship rotations in hospitals and aviation use the same pattern of planned practice with recorded observations.

## Examples

A worked example: on day nine the repository mirror sync fails silently; the patch ring on day ten finds stale metadata. The review adds an alert on mirror age and a check before each ring. A failing example: the daily log shows the same disk-space alert dismissed five times; on day twenty-two the host fills and the directory replica stops. The follow-up is an automated cleanup and an alert on growth rate rather than on a threshold only.

## Related problems and ideas

Related ideas are error budgets, capacity planning, runbook automation, and chaos engineering. Alternatives include purely synthetic load generated by scripts, which is cheaper but misses human handling.

## Active research

Research and practice look at alert quality metrics, automated incident summaries, and the effect of on-call load on reliability. Open questions include how to grade operational judgement fairly (to verify).

## Future direction

Expect more automation of first response, wider use of service level objectives in small teams and better tooling for incident timelines.
