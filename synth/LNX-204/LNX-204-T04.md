# SELinux: labels, policy, booleans and reading denials

## Define the problem

Classic Unix permissions are **discretionary**: the owner of a file decides who may touch it, and every process runs with all the rights of its user. That is a poor fit for network services. A web server runs as an ordinary account, yet a flaw in a script it hosts gives the attacker everything that account can read or write: home directories of other users that happen to be world-readable, mail spools, and credentials in configuration files. Root-owned daemons are worse, since a compromise equals total control. Failure looks like a vulnerability in one service that becomes a whole-host breach, or a confined service that was never actually confined because someone wrote "disabled" in a configuration file during a late-night debugging session and left it there.

SELinux adds **mandatory access control** (MAC): a system-wide policy, which no user or process owner can override, decides what each *type* of process may do to each *type* of object, after ordinary permissions have already agreed. This slice covers the working model (labels, contexts, types, domains), modes and states, the day-to-day tools (`ls -Z`, `ps -Z`, `semanage`, `restorecon`, `setsebool`, `ausearch`, `audit2why`, `sealert`), booleans as policy switches, and a disciplined way to read denials. It uses the audit trail from LNX-204-T07, contrasts with AppArmor (LNX-204-T05), and the kernel-level mechanics sit in the KRN pathway.

## History and approaches

Access control research began with the Bell-LaPadula and Biba models in the 1970s and the "Orange Book" evaluation criteria in the 1980s. Commercial Unix variants with MLS labels existed but were expensive and rigid. The US National Security Agency prototyped the Flask architecture on Mach and then Linux, releasing SELinux in 2000 and getting it merged into mainline Linux 2.6 in 2003 through the Linux Security Modules (LSM) framework, which exists precisely so the kernel does not have to pick a single model. Red Hat shipped it in Fedora Core 2 and made it default in RHEL 4 with a *targeted* policy, which confines only a chosen set of network-facing daemons and leaves user sessions unconfined.

Early versions had a bad reputation. The first strict policies confined everything, so ordinary work failed with unexplained "permission denied" messages, and the common advice became "just turn it off". Partial successes followed. The targeted policy made the system usable, audit2allow and later `setroubleshoot` turned denials into plain-language advice, and the reference policy was split into modules that can be loaded at run time. The Android project adopted SELinux in enforcing mode in version 5, proving that a MAC policy could ship on hundreds of millions of devices. Alternatives developed in parallel: Smack (simplified labels, used in Tizen and automotive), TOMOYO (path-based learning), and AppArmor (also path-based, easier to write, adopted by Ubuntu and SUSE; LNX-204-T05). The lesson is that mandatory access control wins when it ships on and with default policy coverage, and loses when the first experience is a broken service with no readable explanation.

## Current state

**Labels and contexts.** Every process and every object (file, socket, port, inode, device) carries a security context, written `user:role:type:level`, for example `system_u:system_r:httpd_t:s0` for a process and `system_u:object_r:httpd_sys_content_t:s0` for a file. The component that matters most day to day is the **type**: in the targeted policy a typical rule says that processes of domain `httpd_t` may read files of type `httpd_sys_content_t`, plus optional allowances. A process type is conventionally called a *domain*. The SELinux *user* is a policy identity, not a Linux account; the *role* groups domains a user may enter, and the *level* (MLS/MCS range) is used for multi-level separation, and in containers and virtual machines a **category pair** such as `s0:c123,c456` is assigned per instance so two guests of the same type cannot touch each other's files (the libvirt/sVirt and container-runtime design; see LNX-204-T05 for the AppArmor counterpart and the virtualisation pathway).

**Access decision.** The kernel first applies ordinary permission checks and capabilities. If they allow, the LSM hook asks SELinux whether the source domain may perform the requested permission on the target type and object class (`file read`, `tcp_socket name_connect`, `process transition`). The answer is cached in the access vector cache. A denial is logged as an **AVC** message of type `AVC` in the audit log (`/var/log/audit/audit.log`) or via journal, giving the permission, the source and target contexts and the object class.

**Domain transitions.** A service runs in its own domain because of a *type transition*: when a process in `init_t` executes a binary labelled `httpd_exec_t`, policy specifies that the new process runs as `httpd_t`. This is why a binary installed in a nonstandard path or labelled wrongly runs in the wrong domain, often `unconfined_service_t` or `init_t`, and either has no protection or is denied everything.

**Modes.** `getenforce` and `sestatus` report the state. *Enforcing* applies the policy. *Permissive* logs what would be denied but allows it, useful for diagnosis. *Disabled* means the module is not loaded at all; switching back from disabled needs a filesystem relabel (`touch /.autorelabel` and reboot) because files created during the gap have no labels. `setenforce 0` toggles permissive until reboot, the persistent setting is in `/etc/selinux/config` (`SELINUX=enforcing`, `SELINUXTYPE=targeted`), and kernel arguments `enforcing=0` or `selinux=0` override at boot. A single domain can be made permissive with `semanage permissive -a httpd_t`, which is better than switching off the whole system. Red Hat releases enforce by default and RHEL documentation states how to switch modes and troubleshoot [src: rhel-10-docs cd9b97dcc84bec1a].

**File labels.** New files inherit the type of the parent directory, but moving a file preserves its old label, which is the single most common cause of denials (a file moved from a home directory into the web root keeps `user_home_t`). Policy contains a persistent mapping of path patterns to types (file-context rules). The commands: `ls -Z`, `stat -c %C`, `matchpathcon /srv/web`, `restorecon -Rv /srv/web` (reset labels from policy), `chcon` (temporary change, lost on relabel), and `semanage fcontext -a -t httpd_sys_content_t '/srv/web(/.*)?'` followed by `restorecon` (persistent). `semanage fcontext -l -C` lists local customisations. Network ports have the same duality: `semanage port -l | grep http` and `semanage port -a -t http_port_t -p tcp 8081` allow a service to bind a nonstandard port; `semanage login` and `semanage user` map accounts to SELinux users.

**Booleans** are run-time switches for optional parts of the policy, avoiding custom modules for common needs. `getsebool -a` lists them; `semanage boolean -l` adds descriptions and shows persistence; `setsebool -P httpd_can_network_connect on` sets one persistently (without `-P` it is lost at reboot). Typical examples: `httpd_can_network_connect_db`, `httpd_enable_homedirs`, `samba_enable_home_dirs`, `container_manage_cgroup`, `virt_use_nfs`. The Rocky Linux and Red Hat guides list the common ones and the tooling [src: rocky-docs 47a6be79819278b3] [src: man-pages ced2a0540b4aafee].

**Reading denials.** The disciplined workflow is: reproduce in a time window, then `ausearch -m AVC,USER_AVC,SELINUX_ERR -ts recent`, pipe into `audit2why` to learn the cause (a missing boolean, a wrong label, or a missing policy allowance), and only then choose a fix. `audit2why` classifies each record: "was caused by a boolean" with the name to switch, "missing type enforcement rule" meaning policy lacks the allowance, and for a label problem the context mismatch is visible in the target type. `sealert -a /var/log/audit/audit.log` (setroubleshoot) adds suggested commands. Only if no boolean, label, or port change fixes it should a local module be built: `audit2allow -M mylocal` creates a `.te` and `.pp`, and `semodule -i mylocal.pp` loads it; review the `.te` first, because audit2allow produces whatever allows the denial, including too much. Rocky's guide to `audit2why` shows the steps with sample records [src: rocky-docs d4878d7ecf0fc18d]. Some denials are *dontaudit*-hidden by policy; `semodule -DB` rebuilds without those rules to expose them, and `semodule -B` restores them.

**Policy types.** `targeted` is the default; `mls` provides multi-level security; `minimum` confines a few services only. `sepolicy` and `sesearch` query the policy: `sesearch -A -s httpd_t -t httpd_sys_content_t -c file`, `sepolicy generate` writes a template policy for a new service, and `sepolicy manpage -a` produces per-domain man pages that list the booleans and file types of each confined service [src: man-pages 32b738a396ccbc26]. System roles can automate booleans, file contexts and ports across hosts [src: rhel-10-docs ec5450ea4c054cd0].

The generalised pattern is **type enforcement**: a policy that grants capabilities to labelled domains, decided independently of identity, applied at every kernel hook, with an audit trail of refusals.

## Assessment: the good, the bad and the ugly

The good: SELinux contains a compromised daemon even when it runs as root, cuts the usefulness of many exploits (several kernel and application vulnerabilities are not exploitable under the targeted policy), and gives a clear audit trail. Because policy is global, an administrator can answer "what can this service touch?" with `sesearch` instead of reading code. It integrates with containers, virtual machines and systemd, and is mandatory in many certification baselines (DISA STIG demands enforcing mode with targeted policy) [src: disa-stig 648c66e1a91235ad].

The bad: the learning curve is real. Labels live in extended attributes, so backups and copies that drop xattrs (`cp` without `--preserve=context`, archives, some network filesystems) lose them; NFS and FUSE volumes need mount options (`context=`, `fscontext=`) or a boolean. Policy is very large and error messages cite types and classes, not intentions. Third-party software often ships no policy and runs unconfined or fails; a vendor's installer may write to unlabeled paths.

The ugly: the cultural habit of disabling it. Turning SELinux off removes a layer that mitigated entire classes of attack, and the system then drifts: after months of unlabelled writes, re-enabling it triggers a full relabel and surfaces dozens of mislabelled files. Blind `audit2allow -M` for every denial builds a policy that allows the very behaviour an attacker needs. The hidden `dontaudit` rules can make a failure with no log entry baffling. Context-dependent behaviour (a service works from a terminal but fails under systemd because the shell runs unconfined and the unit runs confined) trips new users. MLS and MCS categories add operational complexity that most sites avoid.

## Applications beyond this domain

Type enforcement ideas appear in container and sandbox policies: seccomp profiles list permitted system calls, Android uses SELinux domains per app, Kubernetes sets SELinux options and levels for pods, and cloud IAM gives roles to workloads rather than people. Deciding by the classification of subject and object, rather than by identity, is the same idea as network security zones and zero-trust segmentation. The audit-then-enforce workflow (permissive mode first) is used in WAF rollouts and AppArmor complain mode, and compliance content teaches it to auditors.

## Examples

Working example, a web server serving content from `/srv/web`: the page returns 403 although mode bits are fine. `ls -Zd /srv/web` shows `default_t`. Fix: `semanage fcontext -a -t httpd_sys_content_t '/srv/web(/.*)?'` and `restorecon -Rv /srv/web`. The change survives a full relabel, whereas a bare `chcon` would not.

Boolean example: a PHP application cannot connect to a remote database. `ausearch -m AVC -ts recent | audit2why` reports that the denial was caused by a boolean and names `httpd_can_network_connect_db`. `setsebool -P httpd_can_network_connect_db on` fixes it without custom policy.

Port example: nginx must listen on 8081 under a custom setup and fails to start. `semanage port -a -t http_port_t -p tcp 8081`.

Failing example: an admin moves a user's directory into `/var/www/html` with `mv`, finds the site broken, runs `setenforce 0` ("it works now"), and writes `SELINUX=disabled` to make the change permanent. The cause was a one-line `restorecon -R`. Afterwards a cron-created log file is never labelled and the next policy update misbehaves.

A second failing example: a container bind-mounts a host directory and gets "permission denied" even for root inside the container. The directory has `default_t`; relabel with `:z` or `:Z` on the mount for the runtime or label it `container_file_t` on the host. SELinux-aware container guides describe the same mechanism [src: bootlin-training 042d63bb19b9dc08].

## Related problems and ideas

SELinux sits between DAC and the audit trail. Authentication and lockout is LNX-204-T01, sudo's role-changing capability is LNX-204-T02 (sudo can switch SELinux role with `-r` and `-t`), SSH logins map to SELinux users (LNX-204-T03), firewall labels use `SECMARK` and `secmark` rules in nftables (LNX-204-T06), AVC records are searched with the audit tools of LNX-204-T07, integrity monitoring can record xattrs like `security.selinux` (LNX-204-T08), and compliance scanning checks mode and unconfined daemons (LNX-204-T09). Alternatives: AppArmor (LNX-204-T05), Landlock (unprivileged self-sandboxing from user space, merged in Linux 5.13), seccomp-bpf, namespaces with capabilities, and BPF LSM, where policy is a BPF program. The second family of ideas, not yet mainstream, is to replace sprawling policy with application-defined sandboxes and with eBPF-based runtime enforcement.

## Active research

Work includes policy simplification and analysis (finding unreachable or over-broad rules), automatic policy generation from observed behaviour with safeguards, the Linux Security Module stacking work that lets SELinux and other modules coexist, verification of kernel hooks, and enforcing policy for containers in a way that keeps pods isolated by default. Several groups are studying how to ship domain policy with the application (as part of image or package metadata) rather than only with the distribution. Open questions are usability of denial explanations, and how to keep policy and labels consistent in image-based and immutable systems where `/usr` is read-only (to verify).

## Future direction

Expect continued reduction of "unconfined" domains, tighter container defaults, and tooling that proposes the minimal fix first: boolean, then label, then port, then local module. Image-based RHEL deployments make labels part of the build. Watch the Fedora and RHEL release notes for policy changes, and the kernel's LSM stacking progress, which gradually opens the way for combining a MAC module with Landlock and BPF LSM on the same host.
