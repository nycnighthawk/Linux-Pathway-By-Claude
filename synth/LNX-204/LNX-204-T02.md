# Delegating privilege with sudo: policy, logging and failure modes

## Define the problem

Unix draws one hard line: user id 0 may do anything, everyone else is bound by file modes. Real operations need something in between. A database operator must restart one service, a deployment account must install one package, a helpdesk member must reset passwords but not read mail. Handing out the root password gives away far too much and leaves no trace of who did what; setuid helper programs each have to be audited as a security boundary of their own. Failure looks like a shared root password written in a wiki, a "temporary" rule that lets a user run an editor as root (and therefore any command), or a log in which every privileged action is attributed to the same account.

This slice covers `sudo` as the standard delegation tool: the policy language in `/etc/sudoers` and `/etc/sudoers.d/`, how authentication and timestamps work, how the environment is sanitised, how commands and sessions are logged, and the typical ways a rule is accidentally broader than intended. It builds on PAM (LNX-204-T01), because sudo authenticates through a PAM service, and on process and permission basics from LNX-102. Privilege that is not delegated through sudo, such as polkit actions and capabilities, is touched on only where it clarifies the design.

## History and approaches

Early Unix offered `su`, which required knowing the target's password, and setuid binaries, which granted a fixed power to anyone who could run them. Both are coarse. Sudo ("superuser do") was written at SUNY Buffalo in the early 1980s and was rewritten by Todd Miller in 1993, who still maintains it. It put a policy file between the user and the privilege, with logging. Competing designs followed. OpenBSD wrote `doas` in 2015 with a tiny configuration grammar to reduce attack surface, after concluding that sudo's feature set was a risk. Role-based systems such as RBAC in Solaris and SELinux roles (LNX-204-T04) tied privilege to named roles rather than command patterns. Linux capabilities split root into units such as `CAP_NET_BIND_SERVICE`, and polkit mediated actions requested by desktop and system services. Systemd later added `run0`, which asks polkit instead of reading a setuid binary [web: freedesktop.org] (to verify the exact release).

History also records sudo's failures. Because it is a large setuid program with an expressive parser, it has had serious bugs, among them a heap overflow in command-line handling disclosed in 2021 (the "Baron Samedit" flaw in CVE-2021-3156) and a chroot-option path issue in 2025 (CVE-2025-32463) (to verify). The lesson that followed was twofold. Policy mistakes matter more in practice than parser bugs, since a rule permitting a pager or an editor is effectively a root shell; and the amount of code running with privilege should be small. The first lesson produced the `NOEXEC` tag, `sudoedit`, and the habit of listing exact commands with exact arguments. The second produced a memory-safe rewrite, `sudo-rs`, which the Ubuntu distribution adopted by default from 25.10 and the 26.04 LTS [web: github.com] (to verify the current default per distribution).

## Current state

Sudo has a **front end** and pluggable **policy and I/O logging plugins**. The default policy plugin reads the sudoers file, which should be edited only with `visudo` because it syntax-checks before installing; a syntax error in a privileged policy file can lock every administrator out. Drop-in files under `/etc/sudoers.d/` (included with `@includedir`) let packages and configuration management add rules without editing the main file; files whose names contain a dot or end in a tilde are skipped, and they need mode 0440.

The grammar has four ingredients. **Aliases** name sets: `User_Alias`, `Runas_Alias`, `Host_Alias`, `Cmnd_Alias`. A **rule** reads *user host = (runas-user:runas-group) tags commands*, for example `%ops web1 = (root) /usr/bin/systemctl restart nginx`. **Tags** adjust behaviour per command: `NOPASSWD:`, `PASSWD:`, `NOEXEC:` (block the command from executing further programs through the dynamic linker or seccomp), `SETENV:`, `LOG_INPUT:` and `LOG_OUTPUT:`. **Defaults** set options globally or per user, host, runas or command. Matching is *last match wins*, so a later `!command` or a later broader rule can silently override an earlier narrow one; people must read rules from the bottom up. Negation of commands is mostly cosmetic: a user can copy a binary or use a different path, so security comes from a short allow list, not a deny list.

Command matching is precise. A bare path matches any arguments; a path followed by arguments matches exactly those; an empty-string argument `""` means "no arguments"; a trailing `sha256:` digest can pin a binary's contents. Wildcards in arguments are shell-style and do not stop at spaces, so a rule such as `/bin/cat /var/log/*` also permits `cat /var/log/../../etc/shadow`. The dangerous pattern is any permitted program that can spawn a shell or write arbitrary files: editors, pagers (`less`, `man`), `find`, `tar`, `awk`, interpreters, `systemctl edit`. The community-maintained GTFOBins catalogue lists these escapes [web: gtfobins.org] (to verify). `sudoedit` (or `sudo -e`) is the safe alternative for editing: the user's editor runs unprivileged on a temporary copy, and sudo writes it back.

**Authentication** is delegated to PAM under the service name `sudo`. The user normally proves their own identity (not root's), controlled by `Defaults rootpw`, `runaspw` and `targetpw`. A successful authentication is cached per terminal (`timestamp_type=tty` by default, with a default of five minutes) in timestamp files below `/run/sudo/ts`; `sudo -k` and `sudo -K` invalidate it. `requiretty`, `use_pty` and `visiblepw` shape the terminal handling; `use_pty` runs the command in a pseudo-terminal so a background process cannot inject keystrokes into the parent terminal.

**Environment handling** is a major protection. With `env_reset` (the default) most variables are dropped, `env_keep` and `env_check` list what survives, and `secure_path` fixes `PATH`. Variables like `LD_PRELOAD`, `LD_LIBRARY_PATH` and `PYTHONPATH` must never pass through, because they allow a user to load their own code into a root process.

**Logging** goes to syslog (the `authpriv` facility) or `logfile`, with lines recording the invoking user, TTY, working directory, target user and full command. With `log_input` and `log_output` the plugin records terminal sessions in `iolog_dir`, replayable with `sudoreplay`. In newer versions, `log_servers` can ship I/O logs to a remote `sudo_logsrvd`. When the Linux audit framework is enabled, sudo also emits `USER_CMD` records, which LNX-204-T07 shows how to search. `sudo -l` lists what the current user may run; `sudo -ll` is more verbose; `sudo -U user -l` shows another user's rights for administrators.

The generalised pattern is a **policy decision point with least-privilege grants**: a request (who, where, as whom, which command) is evaluated against ordered rules, executed with a sanitised environment, and recorded. The same architecture shows up in polkit rules, Kubernetes RBAC and cloud IAM.

**Rule grammar details that change outcomes.** A user specification reads user, host, run-as and tag-qualified command list. The tag `NOPASSWD:` applies to every command after it in the same list until a `PASSWD:` tag reverses it, so a tag placed on the first of several commands silently covers the rest; and if any entry for the host carries `NOPASSWD`, the user can also list their privileges without a password [web: sudo.ws]. `SETENV:` lets the caller keep the environment with `-E` and set variables on the command line that bypass the environment checks, so it should be reserved for trusted users; it is implied by `ALL` [web: sudo.ws]. `env_reset` is on by default and runs commands in a minimal environment, adding back only what `env_keep` and `env_check` allow; the manual itself warns that no list can name every dangerous variable, which is why the default is the recommendation [web: sudo.ws]. Credentials are cached for five minutes by default and per terminal, which `timestamp_timeout` and `timestamp_type` adjust; setting the timeout to 0 asks for a password every time, and a negative value never expires, which should not appear in a hardened file.

**Matching commands safely.** Wildcards in sudoers are not regular expressions. In the file-name part, `*` does not cross a slash, but in the argument part it matches slashes and spaces, so a rule such as `/usr/bin/cat /var/log/*` allows `cat /var/log/../../etc/shadow`. Since sudo 1.9.10 a command or its arguments may be written as a regular expression that begins with `^` and ends with `$`, which gives precise control; an empty `""` argument means the command may run only with no arguments [web: sudo.ws]. Negation is the other trap: `!root` matches nobody else, "ALL except these commands" almost never holds because relative paths such as `./useradd` can sidestep a negated path, and the manual discourages negated regular-expression command names [web: sudo.ws]. The safer expression of intent is a short allow list of specific commands, ideally with absolute paths and, for programs whose content you can pin, a digest in front of the path: `sha256:<hex or base64> /usr/local/bin/tool`. The manual cautions that a digest does not protect a binary the user can write, because it can be swapped between the check and the run [web: sudo.ws].

**Include files.** Policy split across `/etc/sudoers.d/` is read in lexical order, so a name beginning `1_` follows `10_`, and zero-padded prefixes avoid surprises. Files whose names end in `~` or contain a dot are skipped, which keeps editor backups and package leftovers from becoming policy; it also means that `50-admins.conf` is silently ignored, a failure mode that has surprised many administrators [web: sudo.ws]. `visudo` checks the main file by default and does not check included files unless asked with `-f`, nor does it catch duplicate alias definitions across files in the default mode, so a pipeline test should run `visudo -c` and also `visudo -cf` on each drop-in.

**Editing files without a shell.** `sudoedit` (or `sudo -e`) copies the target file to a temporary file owned by the invoking user, runs the editor as that user, and writes back as root. It is written without a leading path in rules, takes file names rather than options, and wildcards in the argument list do not match slashes, so `sudoedit /etc/nginx/*.conf` cannot reach `/etc/nginx/../shadow`; a regular expression can narrow the allowed set further [web: sudo.ws]. The mechanism removes the main reason for permitting editors as commands, since a shell escape from an editor run as root is a root shell. `sudoedit` also honours `SUDO_EDITOR`, `VISUAL` and `EDITOR` from the environment unless restricted, so an administrator who needs to restrict the choice sets `editor` in `Defaults` with the `env_editor` option off.

**Accountability settings.** `log_input` and `log_output` are off by default; when enabled, the command runs inside a pseudo-terminal and the session streams are stored under the I/O log directory, from where `sudoreplay` can list and play them back by user, command or date. `mail_badpass` mails the configured address after a wrong password. `noexec` asks the system to stop programs from starting others, which blocks simple shell escapes from dynamically linked programs, but only when sudo was built with support and the platform allows it [web: sudo.ws]. `use_pty` forces a new terminal for each command, which defeats an attack where a background process injects keystrokes into the invoking terminal after the command ends. For many hosts, `sudo_logsrvd` receives I/O logs over a TLS connection so that a user who gains root on one host cannot erase the record.

**Version history that matters to a policy author.** Several vulnerabilities in sudo itself set the practical rule that the program must be patched like any setuid root binary. A heap overflow reachable by any local user was disclosed in January 2021 as CVE-2021-3156, affecting sudo 1.8.2 through 1.9.5p1; a run-as parsing flaw of 2019 (CVE-2019-14287) allowed `-u#-1` to reach root through a rule that denied root; and in 2025 the `--chroot` and `--host` options produced CVE-2025-32463 and CVE-2025-32462, the former letting an unprivileged user cause sudo to load a library from a directory they control. Each was fixed in a point release, and each is a reminder that the broad option surface of the tool is attack surface.

## Assessment: the good, the bad and the ugly

The good: fine-grained, auditable, per-command delegation using the user's own credentials, so the root password can be locked or unknown. Rules can be shared fleet-wide with host and command aliases, and the same file works on every Unix. Configuration management tools can lay down `sudoers.d` snippets and validate them with `visudo -cf`.

The bad: the grammar is powerful but easy to misread. Last-match-wins semantics, per-command tags that do not carry over to following commands unless repeated, wildcard behaviour and the interaction between `Defaults` scopes produce surprises. `NOPASSWD` on broad rules eliminates the only barrier between a stolen session or a compromised user account and root. `sudo` does not constrain what the command does after it starts; any permitted command that is itself an interpreter makes the whole rule meaningless.

The ugly: an attacker who has the user's shell often has the user's `.bashrc`, so aliases and `PATH` games can capture the sudo password; the timestamp cache lets malware piggyback on a recent authentication from the same terminal; and a very long sudoers file accumulates stale entries that nobody dares delete. Centralised policies (LDAP, SSSD sudo provider, or FreeIPA sudo rules) add a lookup dependency: if the directory is unreachable, administrators may lose access. Keep one local break-glass entry. Scalability also suffers when each host holds a different copy; drift is hard to audit without compliance scanning (LNX-204-T09). Memory-safe reimplementation removes a bug class but also removes features (for example `sudo -E`, LDAP policy and some logging options), so migrations require testing [web: github.com] (to verify).

## Applications beyond this domain

Mediated, logged, time-limited elevation is general. Cloud platforms offer role assumption with session policies and expiry. Kubernetes uses `Role` and `ClusterRole` bindings, plus impersonation. Container tooling mirrors the pattern with capabilities dropped by default and re-added individually. Privileged-access-management products wrap sudo-like checks with approvals and session recording. The danger of broad wildcards is the same as an over-wide cloud IAM `*` permission, and the escape-through-an-interpreter problem is analogous to allow-listing a binary that has a built-in shell in a container policy.

## Examples

A tight operator rule. In `/etc/sudoers.d/10-webops`:

```
Cmnd_Alias NGINX = /usr/bin/systemctl restart nginx.service, /usr/bin/systemctl reload nginx.service, \
                   /usr/bin/systemctl status nginx.service
%webops ALL = (root) NGINX
Defaults:%webops log_output, !visiblepw
```

Validate with `visudo -cf /etc/sudoers.d/10-webops`, then test as a member with `sudo -l` and a command that should be denied.

A failing example: `%dev ALL=(ALL) NOPASSWD: /usr/bin/vim /etc/app/*.conf`. The wildcard allows any path under the directory including `../`, and vim can run `:!sh`, so the rule is root. The corrected version uses `sudoedit /etc/app/app.conf` with a fixed path and `NOEXEC`.

A second failing example: the file is saved with a trailing syntax error through `echo >>` instead of `visudo`; sudo then reports a parse error on every invocation and no one can obtain root. Recovery requires a console or rescue shell (and is why break-glass access matters). Related: a drop-in with mode 0644 is ignored with a warning, and a rule seems "not to work".

A third: a rule set per host name works in the lab but not in production because the host's `hostname` is a short name while the rule has a fully qualified name; `sudo -l` on the target host shows what actually matches.

The DISA benchmark and the open ComplianceAsCode rules check items such as requiring reauthentication, banning `NOPASSWD` and `!authenticate`, and restricting who may edit sudoers [src: disa-stig 0f36ce93c23d6afe] [src: man-pages 38d15e91381ac37f].

Policy review example: an ops team has `%ops ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart *`. Because `*` matches spaces and options in arguments, a member can run `sudo systemctl restart ssh --force --message=...`, and the wildcard also admits unit names the team was never meant to restart, such as `sshd.service`. The tightened form lists exact units: `%ops ALL=(root) NOPASSWD: /usr/bin/systemctl restart nginx.service, /usr/bin/systemctl restart postgresql.service`, or uses a regular expression anchored with `^` and `$`. A test in CI uses `sudo -l -U testuser` and a table of allowed and denied commands.

Drop-in naming example: a package installs `/etc/sudoers.d/90-app.conf`. The rule never applies, because the name contains a dot, and the failure is only noticed when the app's maintenance script asks for a password. Renaming it `90-app` and running `visudo -cf` on it fixes the policy.

## Related problems and ideas

Which user ends up as root is a PAM question (LNX-204-T01); whether sudo may be invoked over SSH from automation is controlled by key and certificate handling (LNX-204-T03); what a privileged process may touch is further limited by mandatory access control (LNX-204-T04 and LNX-204-T05); and the records of who ran what are searched with auditd (LNX-204-T07). Alternatives: `doas` for minimal policy, `su -c` for single-target use, polkit for desktop and service actions, systemd's `run0`, capability-bounded service units, and just-in-time access tools that issue short-lived SSH certificates instead of standing sudo rights (also LNX-204-T03). In containers (LNX-303 onward) sudo is usually unnecessary: run as a non-root user with explicit capabilities. Ideas not yet mainstream include approval workflows (two-person rules) integrated with sudo plugins and policy-as-code testing frameworks for sudoers.

## Active research

Current work includes the memory-safe sudo-rs project and its compatibility gaps, formal analysis of policy grammars (detecting shadowed or contradictory rules), centralised I/O log collection with integrity protection, and privilege-escalation detection from audit streams. Researchers also study "confused deputy" paths where a permitted binary reads environment, configuration or plugin directories under user control. Open questions concern how to express intent ("restart this service") in a way that cannot be broadened by argument tricks, which polkit and systemd unit-level delegation partly address.

## Future direction

Expect wider adoption of memory-safe implementations by default in some distributions, more use of `sudoedit`-style interfaces that perform one action instead of running a program, and a gradual shift from standing privilege to time-limited grants issued by identity systems. Watch your distribution's release notes for the default implementation and for sudo's own security advisories. Pair policy changes with a compliance scan so drift is visible (LNX-204-T09).
