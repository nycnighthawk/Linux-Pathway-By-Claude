# Triaging CVEs and errata on distribution-maintained systems

## Define the problem

New vulnerability identifiers arrive every day, and a scanner that lists them all produces a number nobody can act on. The administrator has to decide, for each one, whether it applies to *this* host, whether the distribution has already fixed it (often without changing the upstream version number), how urgent it is given exposure, and how to deploy the fix with acceptable risk. Failure looks like a scanner screaming about "OpenSSL 1.1.1k is vulnerable" on a host whose vendor backported the fix, a genuinely exploited flaw sitting unpatched because it was buried among two hundred low-severity findings, or a patch window that takes down a service because the update was applied untested.

This slice covers the vocabulary (CVE, CVSS, CWE, KEV, EPSS, vendor severity), the vendor advisory system (errata: security, bug-fix and enhancement advisories), how to read an advisory and check a host against it with `dnf` and `apt` tools, how backporting breaks naive version comparison, and a triage routine from alert to deployment and verification. It is the vulnerability-management counterpart to configuration compliance in LNX-204-T09 and uses the package tooling from LNX-104.

## History and approaches

Vulnerability naming was chaotic until MITRE's CVE list (1999) gave each flaw a common identifier, with the NVD (US National Institute of Standards and Technology) adding scores and product mappings. CVSS (since 2005; version 3.1 in 2019 and 4.0 in 2023) gave a severity number, which was soon over-trusted: base scores say how bad a flaw is in the abstract, not whether it can be reached on your host, and organisations that patched strictly by score patched a lot of irrelevant things while missing exploited ones. Enrichment efforts followed: CISA's Known Exploited Vulnerabilities (KEV) catalogue lists flaws seen exploited in the wild, EPSS (FIRST) estimates the probability of exploitation in the next thirty days, and SSVC (decision trees from CERT/CC and CISA) turns several inputs into an action category. The NVD itself has had backlog periods since 2024 in which many entries lacked analysis (to verify the current state), so vendor data matters.

Distribution practice evolved on a separate track. Enterprise distributions promise long-lived major releases with stable version numbers, so security fixes are *backported* into the shipped version: the package keeps `1.1.1k` but its release number or changelog says that the fix for a CVE is included. Red Hat issues RHSA, RHBA and RHEA advisories with CVE lists, severity ratings (Low, Moderate, Important, Critical) and OVAL and CSAF/VEX data; Rocky Linux republishes as RLSA with numbers that follow the upstream advisory [src: rocky-docs 4d8f350665bb166f]; Debian has DSAs and a security tracker with per-release status; Ubuntu has USNs and CVE pages with "released, needed, deferred, not-affected" states. Failures were of two kinds: naive scanners that compared upstream versions and produced false positives, and organisations that trusted "automatic updates" and skipped verification. Today's approach combines machine-readable vendor data with an exposure-aware triage policy.

## Current state

**Identify.** `dnf updateinfo list security` (and `--sec-severity=Critical`, `dnf updateinfo info RHSA-...`) lists applicable advisories; `dnf check-update --security`; `dnf upgrade --security` applies only security updates; `dnf history` records the transaction for rollback. On Debian family hosts: `apt list --upgradable`, `apt-get -s upgrade` to simulate, `unattended-upgrades` for automatic security updates, `needrestart` and `checkrestart`, and `debsecan` for CVE status against the Debian tracker. `rpm -q --changelog package | grep CVE-2024-...` and `apt changelog package` show whether a fix was backported. `needs-restarting -r` (dnf-utils) says whether a reboot is required, and `needs-restarting -s` lists services using outdated libraries.

**Read the advisory.** Fields to extract: affected packages and fixed versions (NVR or version-release), CVE list, severity, a description of the attack vector (network, local, requires a specific configuration or feature), known workarounds, and whether a reboot is needed. The Rocky guide explains how RHSA and RLSA numbers relate and where to find the advisory pages and build system data [src: rocky-docs 1e1f354fe5c6e8a6] [src: rocky-docs bdd0d749eceb2007].

**Verify "is this fixed?"** Do not compare the upstream version number. Check the vendor channel: advisory lists the fixed build, the OVAL definitions from the vendor encode a rule that any package older than a named build is vulnerable, and `oscap oval eval` evaluates them for the whole host (LNX-204-T09). The changelog check is the cross-check for false positives, which the Rocky guide recommends alongside `dnf updateinfo` when OVAL data lags [src: rocky-docs 37b72a826193d1a9]. Compliance content also contains a simple rule that software patches are installed [src: compliance-as-code e9b3c83e6b77a249].

**Decide.** A practical triage template asks: (1) Is the vulnerable component installed *and loaded or running*? (`ldd`, `lsof | grep deleted`, `systemctl status`). (2) Is the vulnerable feature or configuration enabled? (3) Is it reachable from where an attacker could be (internet, internal network, local user only)? Firewall policy (LNX-204-T06) and listening-socket inventory answer the exposure question. (4) Is it known exploited (KEV) or likely (EPSS high)? (5) What mitigations exist if patching must wait (disable a module, restrict access, an SELinux boolean or confined domain, LNX-204-T04, seccomp or AppArmor profile, LNX-204-T05)? (6) What is the blast radius of the patch itself? Typical service levels: critical and exploited within days (or hours for internet-facing), important within about two weeks, others in the normal monthly cycle; the numbers are policy, not law (to verify against your own framework). NIST's control on vulnerability monitoring requires remediation times based on risk [src: nist-sp800-53 31241e40a6655c01].

**Deploy.** Staged rollout: canary hosts, then rings; take a snapshot or rely on `dnf history undo`; restart services whose libraries changed; reboot for kernel, glibc and systemd updates, or use live patching where offered (kpatch/kernel livepatch, Canonical Livepatch, KernelCare) as a bridge, not a replacement. For hypervisors and container hosts, verify that guests and images are rebuilt: updating the host does not fix a vulnerable base image. **Verify:** re-run the scan, check the package version and that the process was restarted, and record closure.

**Reports and records.** Keep a register: CVE, hosts affected, decision (patch, mitigate, accept), owner, date, evidence. Accepted risks need an expiry. Fleet tools (Red Hat Insights and Satellite, Landscape, Uyuni, Foreman, Wazuh vulnerability detector, Trivy and Grype for images) automate collection.

The generalised pattern is **filter, enrich, decide, act, verify**, working from precise per-vendor data and local exposure instead of a global score.

**Prioritisation signals, and what each one answers.** Four signals are commonly combined, and each answers a different question. CVSS describes how severe the flaw is in the abstract; the 4.0 specification names its metric groups Base, Threat, Environmental and Supplemental, and a score reported by the NVD is normally the Base score only, so a team that wants a number about *its* hosts must add the Environmental part itself [web: first.org]. EPSS estimates the probability that exploitation activity will be seen in the next thirty days, published as a probability and a percentile and refreshed daily, which makes it a good filter for the long tail of high-severity flaws that nobody is exploiting [web: first.org]. The CISA Known Exploited Vulnerabilities catalogue records flaws with observed exploitation; each entry lists the date added, a due date, a note on ransomware use and a recommended action, and the whole catalogue downloads as JSON or CSV, which suits a scheduled job that joins it to the host inventory [web: cisa.gov]. Finally, SSVC is a decision tree rather than a score: it takes exploitation status, technical impact, whether exploitation can be automated, how widespread the product is in the organisation's mission and the effect on public well-being, and outputs one of four actions, Track, Track*, Attend or Act, each tied to how fast remediation should happen [web: cisa.gov]. The four tools do not compete. A workable rule is: anything on KEV and reachable is patched in the emergency window; high EPSS plus exposure is next; high CVSS with low EPSS and no exposure goes to the normal cycle with a recorded reason.

**Machine-readable "not affected".** The most valuable output of a vendor is often the statement that a CVE does not apply. VEX (Vulnerability Exploitability eXchange) documents express this as status per product: not affected, affected, fixed or under investigation, and a not-affected status carries a justification such as that the vulnerable code is not present or cannot be reached in the shipped configuration. Vendors publish them in the CSAF format alongside OVAL, and consuming them prevents a scanner from raising a finding against a package that is built without the vulnerable feature [web: access.redhat.com]. Treat a scanner finding that conflicts with a vendor statement as a question to resolve, not a result: either the scanner read the version string alone or the vendor data lags.

**Backport checks by hand.** When the tools disagree, the changelog decides. On RPM systems `rpm -q --changelog openssl | grep -i CVE-2024-XXXX` shows whether the installed build carries the fix, and `dnf updateinfo info --cve CVE-2024-XXXX` shows the advisory and fixed build; on Debian family systems `apt changelog pkg` or `zgrep CVE /usr/share/doc/pkg/changelog.Debian.gz` does the same, and the distribution's security tracker lists each release's status (fixed, vulnerable, not affected, ignored or postponed) per source package. The Rocky guide describes the same verification routes [src: rocky-docs 1e1f354fe5c6e8a6]. The comparison is on the vendor's package version and release, never on the upstream version number.

**Knowing whether the fix is live.** Installing a package does not change processes that already mapped the old library. After a library update, `needrestart` (Debian family) lists services that should be restarted, `dnf needs-restarting` lists processes using outdated files and `dnf needs-restarting -r` reports whether a reboot is required; `lsof | grep -i deleted` finds processes holding deleted copies of replaced libraries, which is the raw evidence behind both. For the kernel, compare `uname -r` to the newest installed kernel package; a patched host that still runs the old kernel is vulnerable. Record the check in the ticket, because "package updated" is not the same as "fix active".

**Service levels.** Many organisations state patch windows by class: for example, known-exploited and internet-facing within days, other critical or important within one to two weeks, moderate at the next cycle. The numbers matter less than being written down, owned, and measured: report the median and the ninetieth-percentile age of open findings by class and the count of accepted risks past their expiry. NIST's control for vulnerability monitoring and scanning (RA-5) frames the same duties of scanning, analysis, remediation and sharing [src: nist-sp800-53 31241e40a6655c01].

## Assessment: the good, the bad and the ugly

The good: vendor advisories are precise and machine-readable, backporting keeps stable systems stable, security-only updates reduce churn, and rollback tools exist. The combination of KEV and exposure data turns an unmanageable list into a short, defensible queue.

The bad: data sources disagree. The same CVE can be "Critical" upstream, "Moderate" for the vendor because a hardening setting blocks exploitation, and "not affected" on one release. Scanners differ in how they read distribution data, and the flaw may live in a statically linked binary or a language-ecosystem package (Python, Go, Java) that the distribution's tooling does not see. Reboots are costly, so kernel fixes are delayed.

The ugly: urgency without information. A new CVE with a logo and no patch yet puts pressure on teams to act, and mitigation advice may be incomplete. Patching blindly can break applications that depend on a bug or a removed behaviour. Third-party repositories (LNX-104) may carry newer versions of a package than the distribution and so bypass its security stream. And "we have no vulnerabilities" claims depend entirely on what the scanner can see: unpatched containers, firmware, appliances and forgotten test VMs usually hold the actual exposure.

## Applications beyond this domain

Triage by exposure and exploitability is used in application dependency management (Dependabot, Renovate with reachability analysis), container image scanning (SBOMs with VEX statements saying "not affected"), cloud misconfiguration prioritisation, and incident-response severity grading. The backport-versus-version problem recurs wherever vendors maintain long-term branches (Android security bulletins, Java vendor builds, enterprise databases). VEX and CSAF formats let a vendor publish that a component is present but not exploitable, which feeds back into automated triage.

## Examples

Weekly routine on an RHEL-family host: `dnf updateinfo list security`, `dnf updateinfo info --advisory RHSA-2026:XXXX` (placeholder), inspect the CVE list against KEV, apply to canary with `dnf upgrade --security -y`, run `needs-restarting -r` and restart affected services, then rescan with `oscap oval eval` against the vendor OVAL file and note the result in the register.

False-positive example: a scanner flags `openssl-1.1.1k` for a 2023 CVE. `rpm -q --changelog openssl | head` shows "Resolves: CVE-2023-xxxx" in a recent build with the same upstream version. The finding is closed with the changelog entry as evidence.

Failing example: a vulnerability affects a web library statically bundled into an application. The distribution's `dnf updateinfo` shows nothing to do; the scanner of package metadata sees nothing; the host stays vulnerable until the application vendor ships a new build. Another: the library `libfoo` is updated by the package manager, but a long-running daemon still maps the deleted old file; without a restart (found with `needs-restarting -s` or `lsof +L1`) the fix is not active.

Triage worked example: a new advisory lists a critical flaw in an image-parsing library. Step one: `rpm -qa | grep libfoo` shows it is installed on 340 hosts. Step two: `lsof -w | grep libfoo` and `systemctl` show that only 12 have a running service that loads it, and 3 of those face the internet. Step three: the KEV catalogue does not list it and EPSS is low, but a public proof of concept exists. Decision: patch the three exposed hosts in the emergency window, the remaining nine in the normal cycle, and record the 328 others as not affected by exposure, with a re-check date. The register captures the reasoning, so a later audit sees a decision, not an omission.

Failing example: a scanner flags a Java application for a library CVE because the file name `log4j-core-2.14.1.jar` matches, while the application bundles a patched, relabelled copy. The inverse also happens: a fat JAR hides an old copy inside another archive, and the package-based scanner sees nothing. Software composition analysis of the application, and an SBOM produced at build time, close the gap that distribution tooling cannot.

## Related problems and ideas

Configuration compliance is the other half of host assurance (LNX-204-T09). Mitigations rely on access control and network filtering (LNX-204-T04 to T06), integrity checks help detect exploitation after the fact (LNX-204-T08), and the audit trail supports incident scoping (LNX-204-T07). Repository trust and signatures are in LNX-104; for container images, the base-image rebuild cycle belongs to the container courses. Alternatives: immutable and image-based systems where the update is a new image (rollback is a boot choice), live patching, virtual patching with a web application firewall or intrusion prevention, and software bills of materials with continuous matching. Not yet mainstream: signed machine-readable "exploitability" statements from every vendor and automatic reachability analysis for native code.

## Active research

Work includes better exploit-prediction models (EPSS versions, community feeds), reachability analysis for dependencies, standardising VEX and CSAF so that vendors can state "not affected", the sustainability of vulnerability databases (the CVE programme's funding and the NVD's analysis backlog), and automated generation of safe mitigations. Open questions are how to score vulnerabilities in context (an organisation's own environmental metrics) and how to trust vendor severity.

## Future direction

Expect wider use of machine-readable advisories (CSAF) and VEX, more shift from patching in place to rebuilding images, and increasing pressure from regulation (for example the EU Cyber Resilience Act's reporting duties for products with digital elements, with obligations phasing in from 2026) (to verify). For the administrator, the durable skill is the routine: know what runs, read vendor data, weigh exposure, patch in rings and prove the result.
