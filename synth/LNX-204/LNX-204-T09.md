# Automated compliance scanning and remediation with OpenSCAP

## Define the problem

Every earlier topic in this course produces settings: a PAM stack, a sudoers file, an SSH policy, SELinux in enforcing mode, firewall defaults, audit rules, an integrity database. The question for an organisation is not whether one administrator can set them but whether five hundred hosts have them *all*, today, in the form an auditor or a customer contract demands, and whether anyone can prove it. Manual checklists drift, differ between reviewers, and are out of date on the day they are finished. Failure looks like an annual audit that discovers a third of the fleet never received a setting, a "hardening script" that passed once and quietly broke applications, or a report with four hundred findings and no way to know which matter.

This slice covers the Security Content Automation Protocol ecosystem on Linux: the standards (SCAP, XCCDF, OVAL, OCIL, CPE, CVE, CCE), the scanner `oscap` and its wrappers, the SCAP Security Guide content with its profiles (CIS, DISA STIG, PCI-DSS, ANSSI and others), tailoring, reports, and remediation as shell, Ansible or kickstart. Vulnerability (CVE) scanning with OVAL is introduced here and continued in LNX-204-T11.

## History and approaches

Security checklists began as documents: the Orange Book era guides, then vendor and government hardening guides, then CIS Benchmarks (consensus-based, from 2000) and DISA STIGs. Machine-readable checking started with scripts (Bastille Linux, Tiger, Lynis, CIS-CAT) that hard-coded checks into code, so each tool defined its own idea of "compliant". NIST then coordinated SCAP (first published 2009 as SP 800-126), which separates the *content* (what to check) from the *scanner* (how to evaluate): XCCDF carries the benchmark and profiles, OVAL expresses machine-checkable definitions, OCIL covers questionnaires, and CPE names platforms. OpenSCAP (Red Hat, 2008 onward) is the open-source reference scanner, and the SCAP Security Guide project, now ComplianceAsCode, generates content from a single YAML source.

Failures taught the field. XML content was hard to write and review, so quality varied; scanners ran out of memory on huge OVAL files (the RHEL documentation still warns about memory use) [src: rhel-10-docs 80038b4b11980b8f]; remediation applied without testing broke applications (disabling a service that was needed, locking accounts); and false positives eroded trust. Rule authors learned to attach human-readable rationale, severity, references (NIST controls, DISA STIG IDs, CIS numbers) and one remediation per rule. Alternatives and neighbours include Lynis (shell auditing), Chef InSpec and Goss (tests as code), Wazuh SCA policies, configuration management itself (Ansible roles that enforce hardening), and cloud posture management products.

## Current state

**Standards in one picture.** An XCCDF *Benchmark* contains *Rules* grouped into *Profiles* (a profile selects rules and sets parameters such as password length). Each rule references *checks*, usually OVAL definitions (tests on files, packages, sysctl values, services) or OCIL questions for manual items, and may carry *fixes* in shell, Ansible or Puppet form. A *data stream* bundles all components into one `ssg-<product>-ds.xml` file. Results are produced as XCCDF results (pass, fail, notapplicable, error, notchecked, unknown, informational, fixed) and ARF (Asset Reporting Format) bundles.

**Installing and finding content.** Install `openscap-scanner` (the `oscap` command) and `scap-security-guide` (content in `/usr/share/xml/scap/ssg/content/`). The content package is released with the distribution; SSG content for a platform is named like `ssg-rhel10-ds.xml`; Debian and Ubuntu ship `ssg-debian*` and `ssg-ubuntu*` through `ssg-base`, `ssg-debderived` and related packages (to verify per release). The RHEL guide describes the tools and the workflow for local scans [src: rhel-10-docs 6028c8077eeb32b0].

**Commands.**

```
cd /usr/share/xml/scap/ssg/content && oscap info ssg-rhel10-ds.xml   # list profiles
oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_cis_server_l1 \
     --results results.xml --report report.html ssg-rhel10-ds.xml
oscap xccdf eval --remediate --profile <id> ssg-rhel10-ds.xml
oscap xccdf generate fix --profile <id> --fix-type ansible --output fix.yml results.xml
oscap xccdf generate fix --profile <id> --fix-type bash   ssg-rhel10-ds.xml
oscap oval eval --results oval-results.xml definitions.xml
```

`--rule <id>` evaluates a single rule, `--tailoring-file` applies a tailoring file, and `--results-arf` writes ARF. `oscap-ssh` scans remote hosts, `oscap-podman` and `oscap-docker` scan containers and images, and offline scans work against a mounted file system. `scap-workbench` is a graphical front end for tailoring. In the kickstart installer, an OpenSCAP add-on applies a profile at install time, and image builders can produce pre-hardened images, which moves remediation to build time [src: rhel-10-docs baf1ec84b2771bfa].

**Tailoring.** Profiles are starting points. A tailoring file selects or deselects rules and changes variable values (for instance `var_password_pam_minlen`, `var_accounts_passwords_pam_faillock_deny`) without editing the signed content, so upgrades of content do not erase local decisions. Document every deselected rule with a reason: an exception register is the evidence an auditor reads.

**Remediation discipline.** Never remediate production with a profile for the first time. Scan, read the failures, test the remediation (Ansible `--check`, or on a staging clone), apply in stages, and rescan. Typical rules tied to this course include PAM modules and faillock settings (LNX-204-T01) [src: compliance-as-code 8fc26ecf88107679], sudo settings (LNX-204-T02), SSH daemon options (LNX-204-T03), SELinux state (LNX-204-T04), AppArmor modes (LNX-204-T05), firewall default policy (LNX-204-T06), audit daemon and rules (LNX-204-T07), AIDE installation and scheduling (LNX-204-T08), and TLS settings (LNX-204-T10). A remediation can break remote access (an SSH rule that disables passwords before keys are installed), so order and a break-glass path matter. Some rules cannot be remediated automatically (partitioning layout, for example), and are fixed at install time.

**Vulnerability checks.** OVAL definition feeds published by distributions (Red Hat, Ubuntu, Debian, SUSE, Rocky) list which package versions are fixed per advisory; `oscap oval eval` compares them with the RPM or dpkg database and produces a report, though definitions may lag and give false positives [src: rocky-docs 37b72a826193d1a9]. NIST's control on vulnerability monitoring frames the purpose and frequency [src: nist-sp800-53 31241e40a6655c01].

**Continuous use.** Run scans from a timer or configuration management and collect results centrally (Red Hat Satellite, Foreman with OpenSCAP plug-in, Ansible Automation, Wazuh). Treat failures as drift tickets, and keep results (ARF) as evidence.

The generalised pattern is **declare, check, report, remediate, re-check**, with a profile that separates policy (what the organisation wants) from mechanism (how to test and fix it).

## Assessment: the good, the bad and the ugly

The good: machine-readable, comparable results; one content base mapped to many standards (the same rule shows its CIS, STIG, PCI and NIST references); open-source content that anyone can inspect (and that this course cites many times); automatic remediation in the form administrators already use; reports usable as audit evidence. Scans are fast enough to run nightly.

The bad: profiles are *someone else's* risk decisions. A CIS or STIG profile applied unmodified can break applications (noexec on `/tmp`, stricter umask, removed packages), and "100 percent" is a number about the benchmark, not about security. OVAL results can lag or contradict distribution backports, and rules that check text patterns can be fooled by equivalent configurations (a setting in a drop-in file that the check does not read). Content differs across releases, so a profile named the same on two OS versions is not the same test.

The ugly: remediation scripts that run as root across a fleet can do large damage fast, and partial application (a reboot required) leaves hosts in mixed states. Scanners need root and read most of the system, so they are a sensitive target. Reports of hundreds of findings invite "checkbox compliance": exceptions and disabled rules to hit a score. Memory-hungry scans on small VMs fail halfway. Ultimately compliance is not security: a host can pass a profile while exposing an unpatched service, which is why vulnerability triage (LNX-204-T11) and the other controls of this course are needed.

## Applications beyond this domain

Policy as code with machine-checked results shows up in infrastructure testing (InSpec, Terratest), cloud governance (AWS Config rules, Azure Policy, Open Policy Agent and Gatekeeper in Kubernetes), and software supply-chain checks (SLSA attestations, OpenSSF Scorecard). Kubernetes uses the Compliance Operator, also built from ComplianceAsCode content, to run the same style of check on clusters and nodes [web: github.com]. The idea of tailoring a baseline with a documented exception register applies to any control framework (ISO 27001 statements of applicability, SOC 2 evidence).

## Examples

Scan and read: on a lab RHEL-family host, `oscap info` to find the profile ids, then `oscap xccdf eval --profile ... --report report.html ...ds.xml`. Open the report, filter on `fail`, and group by severity. For a rule such as the faillock check, the report shows the rule id, the rationale, the OVAL test with the file and pattern it inspected, and the proposed fix.

Remediation example: generate an Ansible playbook only for failed rules (`oscap xccdf generate fix --fix-type ansible --result-id "" results.xml`, flags per version), review the tasks, run with `--check --diff`, apply to a canary host, rescan, and record the delta. The DISA STIG baselines for RHEL 9 and 10 cover the same ground in rule form [src: disa-stig 2327364972dd570c].

Failing example: an engineer runs `oscap xccdf eval --remediate` with the STIG profile on a production database host over SSH. The SSH hardening rules disable password login and set client alive limits, the session drops, the host reboots into a state where the application's service account cannot read a newly restricted file. The playbook should have been tested on a clone and the order of rules (keys first) planned. Another failing example: a scan reports "pass" for a file-permission rule because a custom path is not covered; a hand-written OVAL check or an additional AIDE rule (LNX-204-T08) is needed.

## Related problems and ideas

Package-level patch compliance and advisory numbering: LNX-204-T11. Integrity: LNX-204-T08. Image-based hardening, where remediation happens during image build, links to LNX-104 (packages) and the virtualisation pathway. Alternatives: Lynis, InSpec, Goss, CIS-CAT (licensed), cloud posture tools. The compliance-as-code idea (rules, rationale, tests and fixes in one repository) is itself a model for team practice. Not yet mainstream: continuous compliance with signed attestations per host, and risk-based scoring that weights findings by exposure.

## Active research

Areas: moving content authoring to simpler formats (CEL, Rego, YAML-based) while keeping SCAP interoperability, better OVAL performance and memory behaviour, mapping of rules to control frameworks automatically, and automatic detection of rule conflicts between profiles. Researchers also work on verified remediation (prove the fix does not violate other rules) and on AI-assisted explanation of findings (to verify). Open questions: a stable machine-readable exception format, and trustworthy scoring.

## Future direction

Expect more profile coverage for new release streams (RHEL 10, Ubuntu LTS, Debian), deeper container and image scanning, and compliance expressed in the same workflow as infrastructure code. Watch for changes in SCAP standards under NIST's revisions and for the ComplianceAsCode release notes, because rule ids and variable names change over time and break tailoring files.
