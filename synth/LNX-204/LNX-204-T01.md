# Pluggable authentication: PAM stacks, password quality and lockout

## Define the problem

Every program that must decide whether a caller is who they claim to be, and whether a session may start, used to carry its own answer. A login program read the password file, a remote shell did the same thing slightly differently, and a screen locker did it a third way. Changing the policy meant changing and rebuilding programs, and a site that wanted a smartcard, a one-time code or a directory server had to patch every one of them. Failure looks like a password policy that applies to `passwd` but not to a web portal, a lockout that stops console guessing but not SSH guessing, or an upgrade that silently replaces a hand-edited configuration file and reopens a hole.

This slice covers the Linux answer: the **Pluggable Authentication Modules** framework, the two modules that enforce what a password must look like (`pam_pwquality`) and what happens after repeated failures (`pam_faillock`), and the tooling that keeps stack files consistent (`authselect` on Red Hat family systems, `pam-auth-update` on Debian family systems). It assumes the account and password file knowledge from LNX-101 and leaves the later steps of access control (sudo, LNX-204-T02; SSH policy, LNX-204-T03) to their own topics.

## History and approaches

The first approach was the monolith: each setuid program parsed `/etc/passwd` and, later, the shadow file itself. It worked on one machine with one kind of credential and collapsed when sites added NIS, Kerberos or tokens. Sun's answer, specified in an early-1990s design and published as an Open Software Foundation request for comments, was a layered interface where applications call a generic API and administrators pick implementations through configuration. Linux-PAM adopted the idea in the mid 1990s, and it became the default in practically every distribution.

Early PAM deployments had their own failures. Password strength was first checked by `pam_cracklib`, which linked a dictionary library and had a terse option syntax that every site tuned differently, and the module was eventually replaced by `pam_pwquality`, which shares its option names but reads a central configuration file. Lockout was first done by `pam_tally` and `pam_tally2`, which kept a binary counter file and were awkward to place correctly in a stack; they were removed from current Red Hat and Fedora releases in favour of `pam_faillock`, which stores per-user records in a directory and understands a "preauth" step. Hand-edited stack files were a second failure: package updates and tools such as `authconfig` rewrote them, so local changes vanished or were half applied. Red Hat answered with `authselect`, which treats the stack files as generated output of a named profile, and Debian-style systems used `pam-auth-update` snippets for the same reason.

The lesson across these changes is that the mechanism was never the weak point. The weak points were ordering mistakes, per-site tuning that did not survive upgrades, and counters that attackers could route around by choosing a different entry point. Today's design therefore combines a small set of shared stack files, a generated-configuration tool, and policy that lives in dedicated files such as `/etc/security/pwquality.conf` and `/etc/security/faillock.conf`.

## Current state

A PAM-aware program (SSH daemon, `login`, `su`, `sudo`, a display manager) names a *service*. At call time the library reads `/etc/pam.d/<service>` and walks the lines of four **management groups**. `auth` verifies identity and may set credentials; `account` decides whether a verified user may log in now (expired, locked, wrong time); `password` handles changing the authentication token; `session` sets up and tears down the login environment (limits, directories, audit records). Each line has a **control** that says how its result counts. `required` records a failure but keeps running, so an attacker learns nothing from timing about which module failed. `requisite` fails immediately. `sufficient` ends the group on success if nothing earlier failed. `optional` only matters if it is the lone module. The bracketed form, for example `[success=1 default=ignore]`, lets a module skip a number of following lines and is how the shipped stacks branch. `include` and `substack` pull in other files; the difference is that a failure inside a substack ends only the substack.

On Red Hat family systems the service files include `system-auth` and `password-auth`, which authselect writes from the active profile (`local`, `sssd` or `winbind`). Features are switched on with `authselect enable-feature with-faillock` and its siblings. Hand edits to generated files are detected and refused unless forced, so changes belong in a custom profile created with `authselect create-profile`. Debian-family systems use `common-auth`, `common-password`, `common-account` and `common-session`, regenerated from `/usr/share/pam-configs` by `pam-auth-update`.

**pam_pwquality** runs in the `password` group, usually as a `requisite` line before `pam_unix`. It measures a candidate password (length, classes of characters, similarity to the old one, dictionary checks through libpwquality, repeated and sequential characters, GECOS words) and either rejects it or lets it proceed. Options can be given inline (`minlen=12 retry=3`) but the maintainable place is `/etc/security/pwquality.conf` and drop-ins in `/etc/security/pwquality.conf.d/`. A key detail is the sign convention of the credit options: a positive `dcredit` means each digit earns a credit toward length, whereas a negative value means *at least this many* digits are required. `minclass` is the simpler alternative. By default the check does not bind root (root may override with a warning) unless `enforce_for_root` is set, and `local_users_only` limits the check to accounts defined in local files so directory-managed accounts follow the directory's policy. History of old passwords is a separate module, `pam_pwhistory`.

**pam_faillock** counts failed authentications per user in files under `/var/run/faillock` (tmpfs, so counters vanish on reboot unless `dir` points elsewhere). The stack uses three lines: an `auth` line with `preauth` placed before `pam_unix` to refuse a locked account without testing the password, an `authfail` line after it to record failures, and an `authsucc` line to reset the count on success, with an `account` line that enforces the lock for logins that skip the password stage. Settings that matter are `deny` (failures allowed), `fail_interval` (the sliding window), `unlock_time` (seconds until automatic unlock, or 0 for administrative unlock), `even_deny_root` with `root_unlock_time`, and `audit` to emit records. The `faillock` command lists a user's failure records and clears them with `--reset`. Because authentication results are produced in a different place than where they are counted, the same stack must be applied to every entry point; this is why both `system-auth` (consoles, sudo) and `password-auth` (SSH and other remote services) must carry the module.

The generalised pattern is a **policy chain with a shared state**: a declarative ordered list of independent checks, each returning a verdict, plus a store so that later requests see earlier outcomes. Correctness depends on order (preauth before the password check), on coverage (every door shares the chain) and on the verdict algebra (required versus requisite).

**A complete lockout stack, in order.** The documented sequence for the three faillock calls is worth stating as a whole, because the module does different work depending on where it sits [web: man7.org]. Reading top to bottom in the `auth` group: a `required` (or `requisite`) `pam_faillock.so preauth` line comes before any module that prompts for a secret, so a locked account is refused without a password test. Then the credential module (`pam_unix` or `pam_sss`) runs with a bracketed control such as `[success=1 default=bad]`. Next, `[default=die] pam_faillock.so authfail` runs only on the failure path and records the attempt; `sufficient pam_faillock.so authsucc` runs on success and clears the record; and a closing `requisite pam_deny.so` catches whatever remains. The `account` group also names `pam_faillock.so` (it takes only the `dir` and `no_log_info` options there), which is what makes the lock apply to key-based and other non-password logins that never reach the `auth` stack. Without `authsucc` the module cannot tell consecutive failures from scattered ones.

**Defaults and option semantics in `faillock.conf`.** The man pages say to prefer `/etc/security/faillock.conf` over command-line options, and command-line values override the file [web: man7.org]. The documented defaults are `deny=3`, `fail_interval=900` seconds and `unlock_time=600` seconds; `unlock_time=0` means never unlock automatically, so only `faillock --user NAME --reset` frees the account. `root_unlock_time` implies `even_deny_root`, `admin_group=NAME` extends the root treatment to a group, `dir` moves the records off tmpfs, and `local_users_only` stops the module from counting failures for directory-backed users, which avoids a user being locked both locally and in the directory [web: man7.org]. `silent` removes the informative messages that would otherwise behave differently for existing and non-existing accounts, so it is the enumeration-hardening switch; `audit` records the name attempted even when the user does not exist; `no_log_info` quiets syslog.

**Reading the counters.** `faillock` without arguments lists every user with records; `faillock --user alice` lists the individual failures with their time, source (service and tty or host) and a validity flag; `--reset` clears all records and `--user alice --reset` clears one. During an incident the useful question is whether failures come from one source, many sources against one account, or one source against many accounts. The first calls for a network block, the second for a decision about whether the lock helps the attacker more than it helps the owner, and the third is password spraying, which a per-user counter will not catch at all because each account sees only a few tries.

**Quality scoring, in practice.** `pam_pwquality` is a thin front for libpwquality, and the same library offers two command-line helpers: `pwscore` reads a candidate on standard input and prints a numeric score (or an error naming the failed rule), and `pwmake` generates a password of a requested entropy. They let a team test a policy file without changing anyone's password, for instance by feeding a corpus of previous bad choices through `pwscore` in a pipeline. The tunables of practical weight are `minlen`, `minclass`, the four `*credit` settings, `difok` (how many characters must differ from the old password), `maxrepeat`, `maxclassrepeat`, `gecoscheck` (reject words of more than three characters taken from the account's comment field), `badwords` for site-specific forbidden words such as the company name, and `dictpath` for the dictionary location [web: linux.die.net]. Mixing `minclass` with negative credits makes policy hard to predict, so pick one convention per site and document the sign. Keep in mind that the quality module sees plain text only at change time; the strength of the stored hash (`yescrypt` or SHA-512 with rounds) governs what an attacker gets after theft.

**What guidance asks for now.** NIST's digital identity guidelines call for a minimum length (eight characters for passwords chosen by the user, with a recommendation to allow at least 64), screening against lists of known-compromised or context-specific values, no composition rules and no scheduled expiry without evidence of compromise [web: pages.nist.gov]. A pwquality policy that matches this reads: a generous `minlen`, `dictcheck` on, `badwords` populated, and no `minclass`; compliance baselines that still require complexity can be met alongside it, and the tension should be recorded in a decision rather than resolved silently.

## Assessment: the good, the bad and the ugly

The good: a single place changes policy for every PAM-aware program, new factors (smartcards through `pam_sss`, U2F through `pam_u2f`, TOTP through `pam_google_authenticator`) can be added without touching applications, and compliance rules map neatly onto lines in the stack. The framework is also well understood by auditors, and rule sets such as the DISA STIG and the open-source ComplianceAsCode content name exact modules and ordering requirements [src: disa-stig 2327364972dd570c] [src: compliance-as-code 8fc26ecf88107679].

The bad: the configuration language is terse and positional, a single wrong control flag changes security semantics without any error message, and testing requires opening a second session so that a mistake does not lock the administrator out. Documentation of option syntax differs between modules, and the sign convention of the pwquality credit options surprises almost everyone.

The ugly: lockout is a double-edged control. A threshold of three failures within a short window lets an attacker who knows account names lock out every administrator, converting a confidentiality threat into an availability one; `even_deny_root` makes that sharper. Counters are per-host, so a fleet with central directory logins needs consistent configuration and, ideally, rate limiting at the network edge (see LNX-204-T06 for nftables rate limits and LNX-204-T03 for SSH-level `MaxAuthTries` and `LoginGraceTime`). Pre-authentication lockout also lets an attacker probe which usernames exist unless the module's `silent` option is set. Password complexity rules have been criticised for decades: composition rules drive predictable substitutions, while length and screening against known-breached lists matter more, which is the direction taken by current NIST guidance. Finally, a system that is managed partly by authselect and partly by hand ends up in drift; the tool will refuse to proceed, which is correct but surprising during an incident.

## Applications beyond this domain

The idea of an ordered chain of independent policy steps with a short-circuit algebra recurs in many places. Web frameworks use middleware chains for authentication and authorisation. The nftables ruleset has chains with accept/drop verdicts (LNX-204-T06) and SELinux/AppArmor sit after the DAC decision as additional filters (LNX-204-T04, LNX-204-T05). Kubernetes admission controllers chain validators in the same spirit. The pattern of locking after N failures inside a time window also appears in fail2ban and sshguard (log-driven, so they sit outside the authentication stack), in cloud identity providers and in hardware tokens that wipe after repeated wrong PINs. The preauth idea, refusing before the secret is checked, carries over to any rate limiter that must not become an oracle.

## Examples

A minimal Red Hat family change set, applied to a lab host: run `authselect select sssd with-faillock --force` or `authselect enable-feature with-faillock`, then write `/etc/security/faillock.conf` with `deny = 4`, `fail_interval = 900`, `unlock_time = 600` and `audit`, and `/etc/security/pwquality.conf` with `minlen = 14`, `minclass = 3`, `retry = 3` and `enforce_for_root`. Check with `authselect check`, `faillock --user alice`, and by trying three wrong passwords from a second terminal while the first stays open.

A failing example: an administrator pastes the three faillock lines into `system-auth` by hand with the `preauth` line *after* `pam_unix`. Failed logins are still counted by `authfail`, but a locked account keeps being tested against the password, so a correct guess after the threshold still succeeds on some versions and the log shows the lock but the login works. The STIG check text spells out the ordering requirement for exactly that reason [src: disa-stig bcef022f48695f83].

A second failing case: lockout is configured in `system-auth` only. Console attempts lock the account, yet an attacker guesses over SSH, which uses `password-auth`, indefinitely. The fix is to enable the feature through authselect so both generated files change together.

A third: a rootless container image bakes `pam_faillock` into its stack while `/var/run/faillock` is read-only; every login fails with a vague error. Reading `journalctl` or the audit log for the PAM message identifies the unwritable directory.

A hands-on guide in the Rocky Linux documentation walks through complexity rules and SSH lockout end to end and is a useful second implementation to compare with the Red Hat texts [src: rocky-docs 14c6acc794740ddd].

Spraying example: one source tries `Winter2026!` against two hundred local accounts, three tries each, over an hour. No account reaches `deny=3` inside the 900-second window, so faillock never fires and every failure only appears in the log. A detection rule that counts distinct usernames per source address, using the audit trail (LNX-204-T07), finds it; a network-level per-source limit (LNX-204-T06) or an SSH penalty setting (LNX-204-T03) slows it.

Lockout abuse example: a contractor's script retries a stale password every minute from a CI runner. The service account reaches `deny` and stays locked for `unlock_time`; because that account is the one the deploy pipeline uses, deploys fail until someone runs `faillock --user svc-deploy --reset`. The durable fix is to move the account to key-based, certificate-based or token-based access, not to raise the threshold.

## Related problems and ideas

Password hashing and storage (`yescrypt`, SHA-512 in `/etc/shadow`, `ENCRYPT_METHOD` in `login.defs`) decide how expensive offline guessing is once the shadow file leaks, and belong with the account-management material in LNX-101. Centralised identity (SSSD with FreeIPA or Active Directory) moves lockout to the directory; then `local_users_only` and directory lockout policy interact. Multi-factor authentication through PAM (`pam_u2f`, `pam_oath`) layers a second factor; SSH certificates and keys (LNX-204-T03) remove passwords from the remote path entirely, which is the strongest mitigation for password guessing. Privilege use after login is covered by LNX-204-T02, and every failure record can be shipped to the audit trail described in LNX-204-T07. Alternatives to PAM exist: BSD uses login classes and a different module system, and systemd's `systemd-homed` and `run0` change how sessions and privilege are created. Not yet mainstream: passwordless logins with passkeys, and a Rust-based PAM implementation experiments are being discussed (to verify).

## Active research

Work centres on replacing passwords rather than hardening them: FIDO2 resident keys for local login, SSSD support for passkeys and smartcard flows, and attestation. Password screening against breach corpora (k-anonymity services, local Bloom filters) is being integrated into quality checks. On the framework side, maintainers examine memory-safe rewrites of high-risk modules and the removal of legacy modules. Open questions include how to make lockout resistant to targeted denial of service (per-source-address counters rather than per-user) and how to present clear failure messages without turning them into user-enumeration oracles.

## Future direction

Expect the Red Hat generation of releases to keep authselect as the sole supported way to change stacks and to keep expanding profile features; Debian-family systems continue with `pam-auth-update`. NIST's digital identity guidance (SP 800-63B) already favours length and breach screening over composition rules and discourages forced periodic changes, and distribution defaults are slowly moving that way (to verify for each release). Watch for passkey support in graphical and console login, and for kernel-level or hardware-backed lockout (TPM dictionary-attack protection) replacing software counters.
