# The Linux audit framework: rules, records and retention

## Define the problem

Preventive controls (PAM, sudo, SELinux, firewalls) decide; they do not remember. After an incident, an administrator or an auditor must answer who changed a file, which command a service account ran, whether anyone touched a sensitive path, and when a policy change took effect, and the answer has to be believable, meaning it comes from the kernel and not from a log that the intruder could edit freely. Ordinary syslog files are written by processes with no tie to the events, include only what programs choose to say, and are easy to alter. Failure looks like a post-mortem with "we do not know", a log that filled the disk and stopped the system, or an audit rule set so broad that the real signal is buried.

This slice covers the Linux Audit framework: the kernel subsystem that emits records for system calls, file watches and security events; `auditd`, the daemon that writes them; `auditctl`, `augenrules` and rule files; the search and report tools `ausearch`, `aureport` and `aulast`; plugins for forwarding; and rule design. It is also where denial records from SELinux (LNX-204-T04), sudo (LNX-204-T02), PAM (LNX-204-T01) and AIDE reports (LNX-204-T08) become searchable evidence.

## History and approaches

Trusted Unix systems of the late 1980s defined audit requirements in the "Orange Book" criteria; commercial systems implemented them with proprietary trails. On Linux the early options were syslog and process accounting (`psacct`, `lastcomm`), which record commands without arguments, and `strace`-style tracing, which is far too heavy for production. Linux audit, added to the 2.6 kernel in 2004 by Red Hat engineers with contributions from IBM and others to meet Common Criteria (LSPP/CAPP) certification, put event generation into the kernel and decoupled the daemon. Later additions include the audit rules file split (`/etc/audit/rules.d/`), `augenrules`, the audit dispatcher (`audispd`) that was merged into `auditd` as plugin support in version 3, and containerisation fixes.

The first designs had visible failures. Rules written as "audit all `open` calls" produced gigabytes per hour and made the machine measurably slower; `-f 2` (panic on failure) could halt production when the disk filled; log rotation lost records; and records were written in a key-value format optimised for the kernel rather than humans, which led to the myth that audit logs cannot be read. Partial successes: rule sets published by standards bodies and the ComplianceAsCode project gave sites a vetted starting point, `ausearch --interpret` improved readability, and shipping to a central collector reduced tamper risk. Alternatives developed in parallel: eBPF tracing and runtime security agents (Falco, Tetragon, Tracee) that observe system calls with less overhead and richer context, `inotify` or `fanotify` watchers for files, and process accounting. The lesson was to log *intent*: audit specific actions that matter (identity, privilege, policy, time, sensitive files), not everything.

## Current state

**Pieces.** The kernel generates records into a netlink socket. `auditd` receives them and writes `/var/log/audit/audit.log`. Rules are loaded into the kernel with `auditctl` or, persistently, from files in `/etc/audit/rules.d/*.rules` merged by `augenrules --load` into `/etc/audit/audit.rules`. `auditd.conf` sets log location, size (`max_log_file`), rotation action (`max_log_file_action = rotate` with `num_logs`), what to do when space is low (`space_left`, `space_left_action`, `admin_space_left_action`, `disk_full_action`), `flush` and `freq` for durability, and `write_logs`. Compliance rules check several of these: how many logs are retained, flush priority, and plugin forwarding [src: compliance-as-code 8bef44791481229a] [src: compliance-as-code 017ca7f7d24b4103]. Signals: `SIGHUP` reloads configuration, `SIGUSR1` rotates logs, `SIGTERM` stops cleanly, and `service auditd restart` is not allowed through systemd on some systems, so use `augenrules --load` and `auditctl` instead (to verify per release) [src: man-pages e83140cbbc3db3d6].

**Rule types.** Control rules: `-b 8192` (backlog), `-f 1` (failure action: 0 silent, 1 printk, 2 panic), `-e 1` (enable), `-e 2` (immutable until reboot; changing rules then needs a reboot). Watches on paths: `-w /etc/passwd -p wa -k identity`, which logs writes and attribute changes, with `-k` setting a key used for searching. System call rules: `-a always,exit -S execve -F arch=b64 -F auid>=1000 -k exec`, which records every program execution by real login users once the call completes. File-system rules (`-F dir=`, `-F path=`) and fields such as `uid`, `euid`, `auid`, `exe`, `success`, `exit`, `perm` refine matching. `auid` (the login uid) is central: the kernel assigns it at login and it survives `su` and `sudo`, so it identifies the human behind the action. The order of rules matters: the first match decides; exclusions go first with `-a never,exclude`.

**Reading records.** An event is made of several lines sharing a serial number and timestamp: `SYSCALL` (what was called, success, ids), `PATH` (file names), `CWD`, `EXECVE` (arguments), `PROCTITLE` (hex command line), and message types such as `USER_AUTH`, `USER_LOGIN`, `USER_CMD`, `AVC`, `CONFIG_CHANGE`, `ADD_USER`, `ANOM_*`. Tools: `ausearch -k identity -ts today -i`, `ausearch -m USER_LOGIN --success no`, `ausearch -ua 1001`, and `aureport -au`, `aureport -x --summary`, `aureport --failed`. The `-i` flag interprets numeric ids and hex strings.

**Plugins and forwarding.** The plugin interface (configuration in `/etc/audit/plugins.d/`) forwards events to syslog (`audisp-syslog`), to a remote server (`audisp-remote`, TLS or Kerberos protected in newer versions), or to custom filters; `man auditd-plugins` explains the contract [src: man-pages 79f9815f2b2aaf4e]. Central collection protects the trail from a compromised host, and cooperates with log pipelines and SIEM.

**Rule sets.** The upstream `audit-userspace` source ships sample rule sets for CAPP, LSPP, NISPOM, PCI-DSS and STIG in `/usr/share/audit/sample-rules/`; a typical STIG-aligned set watches identity files, `sudoers`, time changes, module loading, mount operations, privileged commands (setuid/setgid binaries found with `find -perm /6000`), unsuccessful file access (EACCES and EPERM), deletions by users, SELinux policy changes, and login records (`/var/log/lastlog`, `faillock`). Red Hat's hardening documentation describes the practice of using the audit system to monitor the machine and the intrusion-risk reduction chapter lists related steps [src: rhel-10-docs 2f0b3d940bf18013] [src: rhel-10-docs 10be00386743dda7]. DISA's requirements spell out many of the exact watches [src: disa-stig 5b863bde33525498].

The generalised pattern is **append-only, structured event log fed by kernel hooks, with selective rules and out-of-host retention**.

**Loading rules and surviving a reboot.** Rules typed with `auditctl` last until reboot. Persistent rules live as fragments in `/etc/audit/rules.d/*.rules`, and `augenrules --load` concatenates them in lexical order into `/etc/audit/audit.rules` and loads the result, which is why sample sets are numbered (`10-base-config.rules`, `30-stig.rules`, `99-finalize.rules`). The last fragment contains `-e 2` so that the immutable flag is applied after everything else has loaded. `auditctl -l` prints what is loaded, one rule per line, `auditctl -s` shows the daemon's pid (zero means no daemon), the enabled flag, the failure mode, the backlog limit, the current backlog and the `lost` counter. A non-zero `lost` value means events were discarded because the kernel queue overflowed, and it is the first number to alert on [web: man7.org]. Defaults to know: the kernel's failure mode is 1 (print a message), the queue limit is small until raised with `-b`, and there is no rate limit unless `-r` is used. A host that starts processes before the daemon is running misses their audit context unless the kernel command line includes `audit=1`.

**Rule order is a design tool.** An event is decided by the first matching rule in a list, so suppressions belong above the broad rules they carve exceptions from. The `exclude` list filters whole message types before anything else (`-a always,exclude -F msgtype=CRYPTO_KEY_USER` silences a noisy type), the `user` list filters messages from user-space programs, and the `exit` list is where system-call and file rules live. A `task` list rule is evaluated at fork time and may only use fields known then. The syscall form is preferred over the older path watch: the manual marks `-w` and `-p` as deprecated for performance reasons and recommends converting them, for example `-a always,exit -F arch=b64 -F path=/etc/passwd -F perm=wa -k identity`, which needs an `arch` field because `perm` is evaluated per syscall table [web: man7.org]. A `path` rule cannot be a top-level directory and does not take wildcards; `dir=` watches recursively. Keep each rule key short (the limit is 31 bytes) and consistent so `ausearch -k` and `aureport -k` give clean summaries.

**What the daemon does when space runs out.** The `auditd.conf` settings that protect the host from its own log are `max_log_file` (size in MiB), `max_log_file_action` (`rotate`, `keep_logs`, `suspend` and others), `num_logs` (rotation disabled below 2), `space_left` and `admin_space_left` with their actions, and `disk_full_action` and `disk_error_action`. The permitted actions include `ignore`, `syslog`, `rotate`, `exec`, `suspend`, `single` and `halt`, with `email` allowed only for the two space-left settings, and the manual advises against `halt` for `space_left_action` [web: man7.org]. Pick the actions by asking what the host is for: a database server that cannot tolerate halting should send a syslog warning at `space_left`, rotate or suspend at `admin_space_left`, and rely on remote forwarding for the record. A regulated system that must not run unaudited uses `halt` or `single` and accepts the availability cost. `flush` defaults to `incremental_async`, which trades a small window of buffered records for speed; `data` or `sync` closes the window at a cost in disk writes. `log_format = ENRICHED` resolves user and group names and syscall names at write time, so records stay interpretable after the account is deleted; `name_format` adds a host identifier, which is essential once logs from many hosts meet in one store [web: man7.org].

**A starter policy that earns its volume.** A reasonable first set audits: writes and attribute changes to identity files, `sudoers` and `sshd_config`; the use of `sudo`, `su` and other setuid programs found by a scan; loading and unloading of kernel modules (`init_module`, `finit_module`, `delete_module`); changes to the system time; mounts; failed attempts to open files (`exit=-EACCES` or `-EPERM`) by real users; deletions of user files; and execution of programs from world-writable directories such as `/tmp`. Executions by every user (`execve` with `auid>=1000 auid!=unset`) give process history but multiply volume, so enable them on bastions and administrative hosts first. The `auid!=unset` clause matters: daemons started at boot carry an unset login uid and would otherwise match a rule meant for people.

## Assessment: the good, the bad and the ugly

The good: events come from the kernel, so they carry trustworthy identities, include the login uid, and cannot be suppressed by the audited process. Overhead is small for a focused rule set. The immutable flag (`-e 2`) defends the configuration against an intruder with root. Integration is deep: SELinux, PAM, sudo, SSH and user-management tools write typed records.

The bad: the log format is dense; one action spans multiple lines; and the same event can be duplicated in several record types. Rules are positional and syntax-specific, 32-bit and 64-bit calls need separate `arch=` lines, and some system calls differ across architectures. Disk use scales with whatever you audit; a rule on `execve` for all users in a build farm creates huge logs. Containers share the host kernel's audit stream, so container identity is awkward to determine without extra fields.

The ugly: audit can take the system down by design. With `-f 2` and a full disk, or a backlog overflow, behaviour ranges from lost events to a kernel panic; with `disk_full_action = halt` the machine stops. The immutable flag means a mistaken rule survives until reboot. Writing rules on a production host in a live session is easy to get wrong, so test in a lab. And the central weakness remains: a root attacker on the host can stop the daemon before it is immutable, or edit the local copy, so remote forwarding and signed archives matter. Nothing in audit tells you intent; you get actions, and interpreting them still takes a human or analytics.

## Applications beyond this domain

The pattern of kernel-sourced, structured, identity-bound event streams recurs in cloud audit logs (CloudTrail, Kubernetes audit policy with stages and levels), in database audit plugins, and in eBPF runtime security. The key idea of attributing every action to the original authenticated identity (auid) resembles request-ID and principal propagation in distributed tracing. Retention and forwarding policy are the same concerns as in any WORM or tamper-evident log store, and the selective logging versus noise trade-off is the central tuning problem of SIEM.

## Examples

Identity watch set in `/etc/audit/rules.d/50-identity.rules`:

```
-w /etc/passwd  -p wa -k identity
-w /etc/shadow  -p wa -k identity
-w /etc/sudoers -p wa -k scope
-w /etc/sudoers.d/ -p wa -k scope
-a always,exit -S execve -F arch=b64 -F euid=0 -F auid>=1000 -k priv_exec
```

Load with `augenrules --load`, confirm with `auditctl -l`, then run `useradd testuser`, and `ausearch -k identity -i` shows the writing process, the login uid of the administrator and the file. Add `-e 2` as the last line of the final rules file for production.

Investigation example: someone changed `/etc/ssh/sshd_config`. With a watch `-w /etc/ssh/sshd_config -p wa -k sshd_config`, `ausearch -k sshd_config -i` reveals the `exe`, `auid` and `tty`. Without the watch there is nothing to find, which is why watches are written before they are needed.

Failing example: a site audits every `open` call to be "safe". The log grows by gigabytes per hour, rotation discards week-old events, `backlog_limit` is hit, and the kernel logs "audit: backlog limit exceeded" and drops events: more logging produced less evidence. Another: rules written only for `arch=b64`; a 32-bit binary executes commands that go unrecorded.

Retention example: set `max_log_file = 50`, `num_logs = 10`, `max_log_file_action = rotate` and `space_left_action = email` or `syslog`, and ship a copy with `audisp-remote`, as compliance checks demand [src: compliance-as-code b219617ed8049d8c] [src: compliance-as-code bfffa2631b45e15a].

Noise tuning example: after enabling an execve rule, a build host writes several gigabytes per day. `aureport -x --summary` shows that three compiler wrappers account for ninety percent of the records. An exclusion `-a never,exit -F arch=b64 -S execve -F exe=/usr/bin/cc1` placed above the broad rule removes them, and the rule remains reviewable in version control with a comment explaining why.

Backlog example: during a package upgrade `auditctl -s` reports `lost 1812` and the backlog at its limit. Raising `-b` from 64 to 8192 and filtering a chatty rule stops the loss. The lesson is to alert on the `lost` counter, since a rule set that silently drops events provides false assurance.

## Related problems and ideas

Records for failed logins and lockouts (LNX-204-T01), `USER_CMD` from sudo (LNX-204-T02), SSH sessions (LNX-204-T03), AVC denials that LNX-204-T04 reads with `ausearch` and `audit2why` [src: rhel-10-docs 1fc0ebf7d2ab7bf1], AppArmor denials (LNX-204-T05, logged as `AVC` type via audit when auditd is running), nftables rule changes and `NETFILTER_CFG` records (LNX-204-T06), integrity events that an AIDE run explains after the fact (LNX-204-T08), and compliance scans that verify the rule set and daemon settings (LNX-204-T09). Neighbours: `journald` with `systemd-journal-remote`, `rsyslog` TLS forwarding, `fanotify`, Falco and Tetragon eBPF agents. Not yet mainstream everywhere: audit rule sets generated from policy, container-aware audit, and cryptographically chained logs.

## Active research

Topics include lowering audit overhead (BPF-based filtering in front of the audit subsystem), container and namespace awareness of audit records, structured JSON output (the `log_format = ENRICHED` option adds resolved names, and newer versions explore structured formats) (to verify), anomaly detection over audit streams, and tamper-evidence techniques such as hash chaining. Researchers also compare kernel audit with eBPF telemetry for completeness. Open questions: reliable event delivery under overload without halting the machine, and how to join audit with application logs.

## Future direction

Expect the audit daemon to keep its role as the compliance baseline, with growing coexistence with eBPF-based sensors that feed the same pipelines. Rule sets will track new kernel features (`io_uring`, `bpf`, `landlock` system calls). Check each release of `audit-userspace` for deprecations of plugin syntax and for options that change defaults (to verify). Practical advice: keep rules few and purposeful, test them, send events off-host, and review the reports regularly.
