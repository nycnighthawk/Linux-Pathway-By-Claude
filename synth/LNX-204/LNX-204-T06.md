# Hardening a host with nftables: default-deny, state, rate limits and safe rollout

## Define the problem

A server exposes whatever its daemons listen on. Some of those listeners are meant for the world (a web port), some for administrators only (SSH, monitoring), and some were never meant to be reachable at all (a database that bound to every interface after a packaging change, a debugging port, a metrics exporter). A host firewall closes the distance between "what is listening" and "what should be reachable". Failure looks like a service answering on a network where it was never supposed to, a scan that finds twenty open ports on a machine documented as having three, a flood of connection attempts that exhausts a daemon, or a firewall edit that cuts off the administrator and needs a console visit.

This slice covers the *hardening* side of nftables on a single Linux host: a default-drop input policy built from stateful rules, scoping of management access, rate limiting and dynamic blocklists, logging, ICMP and IPv6 details, spoofing and invalid-packet filters, and a rollout procedure that cannot lock you out. The language basics (tables, chains, sets, maps, counters) and the network-service design belong to LNX-201 and LNX-312, and this topic assumes them; here the questions are policy and operations. The curated corpus holds little on this topic, so the synthesis rests on the upstream nftables wiki and the distribution guides, which are cited inline.

## History and approaches

Linux packet filtering began with `ipfwadm`, then `ipchains`, then `iptables` (Netfilter, 1998 to 2001) with separate tools per family (`ip6tables`, `arptables`, `ebtables`). Hosts hardened with iptables accumulated rule files in which every rule was a linear match, extensions were separate kernel modules, and updating a ruleset meant flushing and reloading with a window of exposure. Tools such as `ipset` added fast set matching, and front ends (UFW, firewalld, shorewall, CSF) made rule writing friendlier but also introduced a second layer of state that could disagree with the kernel. Intrusion-response tools like `fail2ban` and `sshguard` parsed logs and inserted rules reactively.

nftables (merged in Linux 3.13, 2014) replaced the stack with one framework: a small in-kernel virtual machine, one syntax for IPv4, IPv6, ARP, bridge and inet (dual-stack) families, native sets and maps with timeouts, and **atomic ruleset replacement** so a new ruleset becomes active in one transaction. Distribution defaults migrated slowly: Debian 10 and RHEL 8 made nftables the backend, and the `iptables-nft` compatibility layer translates legacy command lines. Failures in the transition included mixed deployments where `iptables-legacy` and `nft` rules coexist and different components each own part of the ruleset, and container engines and orchestration agents that insert their own tables ahead of the administrator's.

The lesson that shaped hardening practice: a firewall is *policy as a whole*, so it must be loaded atomically, stored in one file, version-controlled and tested; exceptions must be explicit; and reactive blocking is a supplement, never the base.

## Current state

**Structure for a host firewall.** One `inet` table (covering IPv4 and IPv6) with a base chain on the `input` hook, priority `filter`, and `policy drop`. A host that does not route also gets a `forward` chain with `policy drop` (or nothing, with `net.ipv4.ip_forward=0`). `output` is usually `accept` on servers; strict environments (and many compliance baselines) also filter egress so that a compromised daemon cannot call home. A minimal safe skeleton, as seen in the distribution wikis, accepts loopback, accepts established and related traffic, drops invalid state, and then allows specific services [src: archwiki 26848e59f31b3926].

```
table inet filter {
  set mgmt4 { type ipv4_addr; flags interval; elements = { 10.20.0.0/24 } }
  chain input {
    # entry point for packets addressed to this host
    type filter hook input priority filter;
    # whatever no rule below accepts is discarded
    policy drop;
    # local traffic first
    iif lo accept
    ct state invalid drop
    ct state { established, related } accept
    ip protocol icmp icmp type { echo-request, destination-unreachable, time-exceeded } limit rate 10/second accept
    ip6 nexthdr icmpv6 icmpv6 type { echo-request, destination-unreachable, packet-too-big, time-exceeded, parameter-problem, nd-router-advert, nd-neighbor-solicit, nd-neighbor-advert } accept
    ip saddr @mgmt4 tcp dport 22 ct state new accept
    tcp dport { 80, 443 } ct state new accept
    counter log prefix "nft-drop: " level info limit rate 5/minute
  }
}
```

Key details. `ct state` relies on connection tracking; the first rules make established traffic cheap. IPv6 needs neighbour discovery and path-MTU messages, so dropping all ICMPv6 breaks the host. Protecting against spoofing uses reverse-path filtering (`fib saddr . iif oif missing drop`) or the `rp_filter` sysctl, and dropping packets from bogon ranges on public interfaces. `iifname` matches by name and is slower and flexible, `iif` matches by index and is faster but requires the interface to exist at load.

**Rate limiting and brute-force control.** `limit rate 10/second burst 20 packets` is a global token bucket. For per-source control use a *meter* or a set with dynamic elements: `ct state new tcp dport 22 add @ssh_tries { ip saddr limit rate over 3/minute } drop`, or declare a set with `flags dynamic, timeout` and add offending sources automatically, which the wiki's "dynamic blackhole" pattern demonstrates [src: archwiki bcc6319bd9d1359e]. Put the limiter *before* the accept rule for the same port. SYN-flood protection relies on kernel settings (`net.ipv4.tcp_syncookies=1`) and `synproxy` for high-rate services. Rate limits are an availability aid, not an authentication control; password lockout belongs in PAM (LNX-204-T01) and key-only SSH (LNX-204-T03).

**Logging.** `log` writes to the kernel log with a prefix; rate-limit it, because an attacker can fill disks through logging. Log only dropped input at the final rule, not accepted traffic. With `log group 1` the packet goes to `nflog` for `ulogd`, and the audit subsystem can record netfilter configuration changes (LNX-204-T07).

**Rollout without lockout.** Check syntax with `nft -c -f /etc/nftables.conf`. Keep a second session open. Schedule an automatic revert before applying (`systemd-run --on-active=2m nft -f /etc/nftables.conf.good` or `at now + 2 minutes`) and cancel it after confirming. Load atomically with `nft -f` (the file starts with `flush ruleset` only if you own the whole ruleset). Inspect with `nft list ruleset`, with `-a` for rule handles, and trace a packet with `nft monitor trace` after setting `meta nftrace set 1` on a test rule. Persist by enabling `nftables.service`, which loads `/etc/nftables.conf` (or `/etc/sysconfig/nftables.conf` on Red Hat family systems).

**Coexistence.** If firewalld or ufw is active, do not hand-write a competing ruleset; let one tool own the tables. Containers and Kubernetes agents add their own tables or chains (for example Docker's `DOCKER-USER` hook point in iptables compatibility); use `priority` and separate tables so that your drop policy is evaluated, and be aware that published container ports bypass `input` because they are forwarded, so restrict them in `forward` or with the engine's own settings.

**Verification.** From another host, run `nmap -sS -p- host` and compare to the intended list; `ss -tulpn` on the host lists what is listening; the difference is the firewall's job. OpenSCAP content has rules for default drop policy and firewall presence (LNX-204-T09).

The generalised pattern is **default deny with explicit, scoped, testable exceptions**, loaded atomically, observed through counters and logs.

**How several base chains combine.** Verdicts do not behave the way newcomers expect. A base chain's `accept` ends only that chain; the packet then continues to base chains registered later at the same hook, and a `drop` anywhere is final, with no further evaluation [web: wiki.nftables.org]. Chains at one hook run in ascending priority number, and the named priorities give the useful landmarks: raw at -300, connection tracking at -200, mangle at -150, destination NAT at -100, filter at 0, security at 50 and source NAT at 100 [web: wiki.nftables.org]. Two practical consequences follow. A hardening table at priority 0 cannot be overridden by another tool's later `accept`, so a drop-policy chain with a lower number than a container engine's chain stays authoritative for what it drops. And the reverse also holds: an administrator's `accept` does not protect traffic from a stricter chain somebody else installed at a higher priority number, which is the usual cause of a rule that "obviously allows" a port while the counter on it stays at zero. A `policy` applies only when a packet falls off the end of its own chain; a regular (non-base) chain reached with `jump` or `goto` sees traffic only through its caller.

**Atomicity, precisely.** `nft -f` reads the whole file, builds the new objects beside the live ones and swaps them in a single transaction, so there is never a moment with half a ruleset loaded [web: wiki.nftables.org]. Two details decide whether this saves you. First, a file without a leading flush adds rules on every reload, producing duplicates; the safe idiom flushes the table you own, in the same file, so the flush and the new rules land together. Second, `flush table` empties chains but not sets, so a stale set element or a changed set definition survives a reload unless the table is deleted and recreated or the whole ruleset is flushed. For a host where one team owns the entire firewall, `flush ruleset` at the top is correct; on a host shared with a container engine it also deletes the engine's tables, which is a classic cause of containers losing network access after a firewall reload. The compromise is to keep your rules in a uniquely named table, begin the file with `table inet host_fw` followed by `delete table inet host_fw`, which creates the table if it is missing and then removes it so the following definition always starts clean, and leave every other table alone.

**Sets that carry policy.** Named sets are referred to as `@name` and can be changed while the ruleset is live; they take the flags `constant`, `interval` and `timeout`, plus `size`, `gc-interval`, `auto-merge` and `counter` as options [web: wiki.nftables.org]. Interval sets hold ranges and CIDR blocks, and without `auto-merge` overlapping elements make the load fail, which is worth knowing before you paste in a threat feed. A concatenated type such as `ipv4_addr . inet_service` lets one set express allowed (source, port) pairs, replacing a long list of rules with one lookup. A verdict map goes further: `tcp dport vmap { 22 : jump ssh_in, 80 : accept, 443 : accept }` dispatches to per-service chains in one step [web: wiki.nftables.org]. Keeping the management ranges in a named set also means the firewall file never changes when the range does; an automation tool updates the set with `nft add element`.

**Per-source limits with dynamic sets.** The meter idea is expressed with a dynamic set that has a timeout. The wiki's SSH example declares a set of type `ipv4_addr` with `timeout 60s` and `flags dynamic`, then applies `ct state new tcp dport 22 update @my_ssh_ratelimit { ip saddr limit rate 3/minute } accept`. Each source address becomes an element with its own limiter, and the element vanishes after 60 seconds without traffic. Adding the port to the key (`ipv4_addr . inet_service`) gives a per-source, per-port limit. Connection counting works differently: it needs a dynamic set with no timeout (adding one produces an unsupported-operation error), and uses `add @my_connlimit { ip saddr ct count over 20 }` [web: wiki.nftables.org]. The two address different harms. A rate limit blunts guessing and scanning; a connection cap blunts a client that holds many sockets open. Note the polarity: `limit rate 3/minute` in an `accept` rule lets the first three through and lets the rule stop matching afterwards, so the packets that exceed the rate fall through to whatever follows, usually the policy drop. `limit rate over 3/minute` followed by `drop` says the same thing from the other side; choose one reading and keep it consistent across the file.

**Early drop on the ingress hook.** The `ingress` hook sees a packet immediately after the driver hands it up, before prerouting and before connection tracking spends memory on it. It exists in the `netdev` family from kernel 4.2, and from 5.10 in `inet`; the chain must name its device [web: wiki.nftables.org]. For a host that is under flood, dropping bogus sources there is cheaper than anywhere in the main path. For ordinary hardening it is optional, and the usual `input` chain remains the primary control.

**Egress and forward.** Most breaches that matter at the network layer involve a second step in which the compromised process calls out. An `output` chain with policy drop, then allowances for DNS to the resolvers, package mirrors, NTP and the monitoring endpoint, makes that step fail and produces a log line that can be alerted on. The cost is real: every new dependency needs a ticket. Teams usually enforce egress only on high-value hosts. Forward policy matters on hypervisors and Kubernetes nodes, where traffic for guests never touches `input`.

## Assessment: the good, the bad and the ugly

The good: one atomic, readable file; sets that make a thousand addresses as cheap as one; dual-stack rules with a single syntax; counters and traces that show what happened; and cheap rate limiting with the kernel doing the work. A default-drop input policy neutralises accidental exposure from new listeners, which is the most common real-world firewall win.

The bad: stateful firewalls cannot see inside encrypted traffic or application logic, so they do not replace service hardening. Rate limits can be evaded by distributed sources and can be abused to block legitimate users behind shared NAT. Policy that is correct today can be broken by an orchestration agent tomorrow, and nftables has no built-in rollback (the revert timer is a convention). Documentation of corner cases such as priorities of multiple base chains on the same hook is scattered.

The ugly: lockouts, covered above, and the "two firewalls" problem where firewalld and a hand-written table both exist and a reload by one wipes the other. Dropping ICMP wholesale (a cargo-cult rule) causes path-MTU blackholes that appear as hung SSH sessions on large packets. IPv6 forgotten entirely: an `ip`-only table leaves IPv6 wide open, which is why the dual-stack `inet` family is the default recommendation. A chain with `policy accept` and a final explicit `drop` can be defeated by a rule inserted after it. Time-based sets that expire during an incident remove blocks automatically, which is a feature until it is not.

A few measurable costs deserve mention beyond the qualitative ones. Each extra priority-ordered chain adds a pass over every packet, so many small chains from many tools cost throughput. Dynamic sets consume memory per element, and an unbounded set under a spoofed-source flood grows until `size` stops it, after which new sources are not tracked and so are not limited; setting `size` deliberately is a decision about which failure you prefer. Timeout and garbage-collection settings affect how long a legitimate user stays blocked after a mistake. Finally, the tool's JSON output (`nft -j list ruleset`) is the supported interface for automation, whereas screen-scraping the text form breaks across releases.

## Applications beyond this domain

Default-deny with scoped exceptions is the same posture as least-privilege IAM, Kubernetes NetworkPolicy (implemented by CNI plugins on nftables, eBPF or iptables), cloud security groups, and sudo rules (LNX-204-T02). Atomic replace-and-validate is the transaction model of declarative configuration systems and of `visudo`-style syntax gates. Dynamic sets with timeouts are the kernel version of rate-limiters in API gateways. The reactive blocklist idea is also at the heart of intrusion-prevention services, which differ by consuming reputation feeds.

## Examples

Server hardening change: write the skeleton above, test with `nft -c`, arm the revert timer, load, confirm a new SSH session from the management range works and one from elsewhere times out, cancel the timer, and enable the service. Verification output from `nft list ruleset` should show counters increasing on the SSH and HTTP rules and a few dropped packets at the end.

Brute-force example: add a per-source meter so more than three new SSH connections per minute from one address are dropped and the address is placed in a timed set for ten minutes; confirm with a loop of `ssh` attempts from a lab host and `nft list set inet filter ssh_tries`.

Failing example: the admin writes `tcp dport 22 accept` *above* `ct state invalid drop` and a rate-limit rule below it. All traffic to SSH bypasses the limiter, so brute-force protection is a no-op. Another: after adding the rule `ip protocol icmp drop`, large file transfers from some networks hang, because fragmentation-needed messages are dropped, and the symptom looks like an application bug.

The Arch wiki examples and the Red Hat hardened-image guidance share the same stateful skeleton, which is why the pattern is widely portable [src: archwiki 6ead4c5244e2a496] [src: rhel-10-docs baf1ec84b2771bfa].

Worked incident: a database package update changes its bind address from loopback to all interfaces. With the host firewall in place only the web ports and the management set are open, so the exposure is limited to the management range and the counter on the final log rule begins climbing from scanners. The security team learns about the listener from the drop log, not from a breach. Without the firewall the first notice is an external scan report.

Worked verification: after loading, run `nft list ruleset` and compare it with the committed file; run `nft -a list chain inet filter input` to see handles; send traffic from a permitted and a forbidden source; read the counters. To explain a drop, add `meta nftrace set 1` to a test rule and watch `nft monitor trace`, which prints each rule the packet visits and the final verdict. Keep the trace rule out of the committed file.

Container collision example: a host runs Docker and a hand-written default-drop `inet` table. Published container ports work regardless of the `input` policy because they take the forward path with address translation applied first. The administrator who needs to restrict who can reach a published port must add the restriction in the engine's own user chain or in a `forward` chain that is evaluated before the engine's accept, otherwise the policy drop in `input` is, correctly, irrelevant to that traffic.

## Related problems and ideas

Basics and service maps: LNX-201 and LNX-312 (service-map labs with nftables). SSH source restrictions pair with the SSH policy of LNX-204-T03; lockout counters with LNX-204-T01; labels on packets (`secmark`) can feed SELinux (LNX-204-T04); and the audit subsystem records changes and denied connections (LNX-204-T07). `ruleset` files should be covered by file-integrity monitoring (LNX-204-T08) and compliance checks (LNX-204-T09). Alternatives and neighbours: firewalld zones and policies on top of nftables, eBPF/XDP filtering for very high packet rates, cloud security groups, microsegmentation with CNI policy, WireGuard overlay networks that let the service listen only on a private interface, and port knocking (a weak control, not recommended). Not yet mainstream: policy-as-code verification of rulesets, and identity-aware host firewalls.

## Active research

Upstream work includes flowtables for fast-path forwarding, improved set types and concatenations, the `nft` JSON API for tooling, transactional guarantees and conflict handling when several managers edit the same ruleset, and eBPF-based enforcement. Researchers study firewall policy verification (shadowed or contradictory rules) and anomaly-based rate control. Open questions: safe coexistence of multiple controllers on one host, and the right abstraction for application-level policy (to verify).

## Future direction

Expect further retirement of the legacy iptables back end in distributions (the compatibility wrappers remain longer), more declarative management through configuration tools and system roles, and tighter integration with container networking. For administrators: keep one owner for the ruleset, keep it in version control, test with `nft -c` in CI, and rehearse the lockout recovery.
