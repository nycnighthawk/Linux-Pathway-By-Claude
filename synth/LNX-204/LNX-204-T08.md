# File integrity monitoring with AIDE

## Define the problem

Prevention fails sometimes. When it does, the intruder's first jobs are persistence and concealment: replace a system binary with a trojaned copy, add a key to a startup file, loosen a permission, hide a module. Package databases can say what *should* be installed, and audit rules (LNX-204-T07) can say who wrote a file *if* a watch existed beforehand, but neither answers the blunt question of what on this machine differs from the last state anyone trusted. Failure looks like a compromised host that passes every health check for months, an administrator who cannot tell a legitimate update from a tampered binary, or an alert stream so noisy that nobody reads the daily report.

This slice covers file integrity monitoring (FIM) with **AIDE**, the Advanced Intrusion Detection Environment: how its database and rule language work, how it is scheduled and reported, how to keep the baseline trustworthy, and where it fits next to package verification, audit and compliance scans. Higher-level host intrusion detection suites are only mentioned for contrast.

## History and approaches

Gene Kim and Eugene Spafford published Tripwire in 1992: record cryptographic hashes and attributes of important files in a database, store the database on read-only media, and compare later. The commercial Tripwire and an open-source Tripwire followed. AIDE appeared in 1999 as a free replacement with a similar model, and the Debian and Red Hat families packaged it. Other approaches covered parts of the problem: package managers can verify installed files against the package database (`rpm -V`, `debsums`), but they ignore files outside packages and an intruder can alter the package database too; Samhain and OSSEC/Wazuh added central management and real-time checks; `inotify` and `fanotify` give immediate notice but miss changes made while the watcher was down; read-only or verified root filesystems (dm-verity, image-based systems) prevent the change in the first place.

The failures were operational. Early deployments generated thousands of changes after each update because the baseline was not refreshed, reports were mailed and ignored, and the database and the binary lived on the same writable disk, so an attacker simply regenerated the database. The lessons: scope the monitored set carefully, update the baseline as part of patching, protect database and binary from the host being monitored, and send results where someone reads them.

## Current state

AIDE has three parts: the configuration `/etc/aide.conf` (Debian family: `/etc/aide/aide.conf` plus `aide.conf.d`), the database of recorded values, and the `aide` command with modes `--init` (build a new database), `--check` (compare), `--update` (check and write a new database), and `--compare` (compare two databases). The default database path is `/var/lib/aide/aide.db.gz` with a freshly initialised `aide.db.new.gz` that must be moved into place; the Red Hat guide walks through install, initialisation, checking, updating and keeping the database safe [src: rhel-10-docs 05eee5632735f901] [src: rhel-10-docs 1234e094abd9dcf1] [src: rhel-10-docs f0b5888e63bebe80].

**Rule language.** The configuration defines *attribute groups* and *path rules*. Attributes include `p` (permissions), `i` (inode), `n` (link count), `u`, `g` (owner and group), `s` (size), `m` (mtime), `c` (ctime), `a` (atime), `acl`, `selinux`, `xattrs`, `caps` and hash functions such as `sha256`, `sha512`, `sha3_256`. A group such as `NORMAL = p+i+n+u+g+s+m+c+sha512` is then attached to a path pattern (regular expression): `/etc NORMAL`, `/usr/bin CONTENT_EX`, `!/var/log` (exclude), `=/tmp` (match only that directory, not below), with `@@define` and `@@ifdef` macros. Monitoring should favour files that must not change: binaries, libraries, configuration, `/boot`, startup and scheduler directories, SSH and PAM and sudoers files (LNX-204-T01 to T03), the audit rules (LNX-204-T07), and the policy files of SELinux and AppArmor (LNX-204-T04 and T05). Exclude volatile areas (`/var/log`, `/var/cache`, `/proc`, `/run`, mail spools).

**Report and exit codes.** `aide --check` prints a summary (added, removed and changed counts) and detailed lists with attribute-level differences. The exit status is a bitmask: 0 for no difference, with bits for added (1), removed (2) and changed (4), and higher values for errors, so scripts can distinguish "differences found" from "failed to run". The `report_url`, `verbose` and `summarize_changes` options shape output.

**Scheduling and notification.** A systemd timer or cron job runs the check daily or more often and mails or syslogs the output; compliance rules ask for a periodic check and for notification of results [src: compliance-as-code 1ac27c413d2e517c] [src: compliance-as-code a116df2f0527636a]. The DISA benchmarks add that cryptographic mechanisms must protect the integrity of audit tools and that rules must cover the file attributes [src: disa-stig efed9d1e6a31f8f6] [src: disa-stig d727fb2529c14cd4].

**Keeping the baseline trustworthy.** Initialise on a freshly built, known-good host (or image) before it joins the network; copy the database and a checksum of the `aide` binary and configuration to read-only or off-host storage; run checks from a copy of the database that the host cannot rewrite, or store the database signed; run an `--update` after patching in a controlled step, reviewing the diff first; and keep the configuration under version control. Recent versions can sign the database with a key and verify it on load (to verify for each distribution's build).

The generalised pattern is **baseline and diff**: record a trusted state, later recompute and compare, and explain every difference. It depends on three trust anchors: a trusted initial state, a trusted comparison tool and an untampered baseline.

**How a path is matched.** The selection lines in the configuration come in three flavours: a plain regular expression (monitor and apply this group), a line starting with `=` (match only this exact directory level, not what is below), and a line starting with `!` (exclude). The matcher builds a tree that mirrors the directory structure, picks the deepest node that applies to a file, and uses the first matching rule within it; negative rules are tested last and only matter for files that would otherwise be added. An implicit start anchor is added to each expression, so `/etc` also matches `/etcetera`; anchoring single files with `$` avoids that. The manual's advice is to write general rules last and specific rules before them, and to test with `aide --verbose=255`, which prints which files were added or discarded and why [web: aide.github.io]. A rule set that is never exercised with a deliberate change fails silently, so the first test of any configuration is to touch a monitored file and confirm the report.

**Attributes that do the real work.** Macro groups are built by joining attribute names with `+`. The documented checksum choices include `sha256` and `sha512` along with older ones kept for compatibility; a compliance baseline names a strong hash, and the older `md5` and `sha1` should not carry the weight of a security control [web: aide.github.io]. `ftype` records the file type, so replacing a regular file with a symlink is caught even when the name is unchanged. For files that only grow, such as logs, the growing-size attribute (`S` for size and `>` as a predefined group) accepts appended data while still flagging truncation or rewriting, which lets an append-only log be monitored without constant alerts. `acl`, `selinux`, `xattrs` and `e2fsattrs` are compile-time features; a package built without them silently ignores those attributes, so check `aide --version` for the compiled-in list before relying on them to detect a changed label or capability [web: aide.github.io]. The `report_force_attrs`, `report_ignore_added_attrs`, `report_ignore_removed_attrs` and `report_ignore_changed_attrs` settings tune which changes are shown, which is better than excluding a path altogether when only one attribute (a timestamp) is noisy.

**A baseline in three layers.** A practical rule set separates the host into classes with different expectations. Binaries and libraries (`/usr/bin`, `/usr/sbin`, `/usr/lib*`, `/boot`) should change only at patch time, so everything including contents is hashed and any difference outside the patch window is an incident. Configuration (`/etc`) changes more often, deserves hashes and ownership, and benefits from excluding generated files such as caches and the DHCP lease. Variable data (`/var/lib`, `/home`, `/tmp`) is excluded or limited to permissions and ownership, because content changes constantly. A fourth class, trust anchors (`/etc/ssh`, `/root/.ssh`, `/etc/pam.d`, `/etc/sudoers*`, the audit rules, and the AIDE configuration itself), is checked with every attribute and reported in a separate section so reviewers see it first. The aim is a report short enough that someone reads it.

**Operating around patching.** Package managers record their own checksums, so `rpm -V` and `debsums` can verify installed files against what the package shipped without any baseline. They answer a different question (was this file changed since install) and miss newly added files, so they complement AIDE and do not replace it. After a patch window, the sequence is: run `aide --check` and read the differences; confirm that each changed path belongs to an updated package; run `aide --update`; move the new database into place, and copy it, with its checksum, to the protected store. The manual stresses that replacing the input database should be a deliberate manual step and not automated, because an automated replacement would also bless an attacker's changes [web: aide.github.io]. When many hosts run from one image, `aide --compare` on a central system, combined with `--init` on each host, compares databases across machines and identifies the outlier whose files differ from its peers [web: aide.github.io].

**Where host-based integrity monitoring stops.** A tool that runs inside the system it checks can be subverted by a kernel-level rootkit that hides modifications from every user-space program. The countermeasures sit lower in the stack: the kernel's Integrity Measurement Architecture can measure and appraise files at execution using signatures, `dm-verity` and `fs-verity` make a block device or file read-only with a verified hash tree, and secure boot with a measured boot chain anchors the first stage. Offline checking, by mounting the disk from a trusted environment, defeats user-space deception at a high operational cost. Many sites run AIDE for change detection and compliance, and use these mechanisms where tamper resistance matters.

## Assessment: the good, the bad and the ugly

The good: small, simple, open source, easy to script, and independent of the package system, so it detects changes to unpackaged files, ownership and permission drift, and hash-level tampering of anything covered. It gives a defensible answer for compliance requirements, and the attribute-level report shows precisely what changed (permissions, SELinux label, capabilities).

The bad: it detects, it does not prevent, and it detects only at check time; an intruder who acts and cleans up between runs, or who modifies only data in memory, is invisible. Checks of a large file system take noticeable time and I/O, and the first run after a major update is a flood of changes. Without reading the reports, AIDE is theatre. The database grows with the monitored set, and distribution defaults (for example `/usr` without exclusions) can be too broad or too narrow.

The ugly: the baseline problem. If the host is already compromised when AIDE is initialised, the attacker's files are "known good"; if the database is writable by the attacker, they regenerate it; and if the `aide` binary is replaced with one that prints "no changes", the whole system is blind. These attacks are why the database and tool must be verified from outside. Kernel rootkits can hide files from the very system calls AIDE uses to read them, so for high assurance, check from a separate boot environment or use measured boot with remote attestation. Reports during automatic updates are noisy, and teams tempted to widen exclusions weaken their own coverage.

Quantify the cost before choosing the scope. A full hash of a typical server's system directories takes minutes of disk reads and should run at low priority (`ionice` and `nice`, or a systemd unit with `IOSchedulingClass=idle`); hashing a multi-terabyte data volume is rarely worth it and mostly produces noise. Database size grows with file count, so monitoring `/usr` and `/etc` on a thousand-host fleet means a thousand databases to protect and compare, which is why many sites keep them centrally. The detection value is also bounded by the interval: a daily check leaves a day in which a modified binary runs undetected, and an attacker who changes a file and restores its timestamp is caught only by the content hash, not by the cheaper attributes, which argues for hashing the trust-critical paths even where size and mtime would be cheaper. Finally, remember that a clean report proves only that monitored files match the baseline; unmonitored paths, memory-only malware and changes made before the baseline was taken stay invisible.

## Applications beyond this domain

The baseline-and-diff idea is the foundation of configuration drift detection (Ansible check mode, Terraform plans, Kubernetes GitOps controllers that compare live and declared state), of image scanning against a signed manifest, of reproducible builds, and of measured boot where each stage's hash is compared to an expected value (TPM attestation). Integrity manifests also appear in package signing (LNX-104) and in container image digests. The `ostree` and `bootc` image-based systems make the monitored state the image itself, so the baseline is the image digest.

## Examples

Initialise and verify on a lab host: `dnf install aide`, `aide --init`, move `/var/lib/aide/aide.db.new.gz` to `aide.db.gz`, then `aide --check` should report no differences. Create a test change (`echo "# test" >> /etc/hosts`, `chmod 777 /usr/local/bin/tool`), and the next check lists the changed `/etc/hosts` with the size, mtime and hash differences, and the permission change with the old and new modes. Apply a patch set, run `aide --update`, review, and store the new database off-host.

Policy example: a custom rule file adds `/etc/ssh CONTENT_EX`, `/etc/pam.d CONTENT_EX`, `/etc/sudoers.d CONTENT_EX`, `/etc/audit CONTENT_EX` and excludes `/var/lib/aide` itself.

Failing example: AIDE is initialised after an unattended update has installed a backdoored package from a compromised third-party repository (see LNX-104 on signing). Every file is in the baseline and the check passes forever. Another: the nightly job runs but the mail goes to a decommissioned address, and the host shows three hundred unreviewed changes in a year, among them a modified `/etc/ld.so.preload`. The Debian handbook discusses the same detection concepts and the need to protect the reference [src: debian-handbook 59b7c1eebb57566b].

Reading a report: `Changed entries: /usr/sbin/sshd: SHA512 differs, Mtime differs` outside a patch window, together with an `sshd` package that shows no update in `dnf history` or `/var/log/apt/history.log`, is the textbook signal. The responder compares with `rpm -V openssh-server` or `debsums openssh-server`, preserves a copy of the file, and treats the host as compromised until shown otherwise.

False positive example: after a kernel update, `/boot` and `/lib/modules` show dozens of changes. Because the changes align with the package transaction, the reviewer accepts them and updates the baseline, noting the transaction id in the change record so the audit trail connects the two.

## Related problems and ideas

Audit watches (LNX-204-T07) tell who changed a file *when it happens*; AIDE tells *that* it changed, *between* checks. Both complement package verification (`rpm -Va`, `debsums -c`) and OpenSCAP checks of file permissions (LNX-204-T09). Compromise of SSH configuration (LNX-204-T03) or sudoers (LNX-204-T02) is a prime AIDE target. Mandatory access control (LNX-204-T04, T05) limits who can write protected files, and AIDE records the SELinux context and xattrs as attributes. Alternatives: Tripwire, Samhain, Wazuh syscheck, `fapolicyd` (allow-list execution, preventing unknown binaries from running), IMA/EVM (kernel-level measurement and appraisal of file hashes), and fs-verity. NIST controls on system integrity discuss why integrity verification belongs in a baseline [src: nist-sp800-53 0572dbedeac6173d].

## Active research

Work includes kernel-enforced integrity (IMA appraisal with signatures, fs-verity for per-file digests), remote attestation of whole-host state with TPMs (Keylime), better handling of immutable and image-based systems, and efficient incremental scanning with `fanotify`. Open questions: how to make baselines survive legitimate update flows without a human reviewing thousands of lines, and how to combine measurement with policy so that unknown changes block rather than alert.

## Future direction

Expect AIDE to remain the lightweight option for traditional hosts while image-based and attested systems shift integrity from "scan and diff" to "verify at load". Plan for signed databases, off-host storage of baselines and reports, and automated review of diffs against package changes. Check release notes for new attribute types and hash defaults (to verify).
