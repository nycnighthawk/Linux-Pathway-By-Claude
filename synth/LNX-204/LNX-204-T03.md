# Hardening OpenSSH and replacing key lists with certificates

## Define the problem

SSH is the front door of almost every Linux server, so it is both the most valuable and the most attacked service on the machine. Three things must be got right at once. The channel must resist eavesdropping and tampering (algorithm choice), only the intended people and machines may log in (authentication and authorisation), and the way trust is distributed must survive growth, since a list of public keys copied onto every host rots. Failure looks like password guessing that never stops, a leaked laptop key that still works on forty servers a year later, a user who answers "yes" to a changed-host-key warning because it happens every time a server is rebuilt, or an old cipher that a compliance scan flags on every host.

This slice covers server and client configuration (`sshd_config`, `ssh_config`), key types and authentication methods, restriction of what a successful login may do, and **SSH certificates**: short-lived credentials signed by a private certificate authority that replace per-host `authorized_keys` and `known_hosts` maintenance. It builds on key concepts from LNX-102 and on PAM from LNX-204-T01 (when `UsePAM yes`), and hands off TLS-based trust to LNX-204-T10 and network filtering to LNX-204-T06.

## History and approaches

Telnet and the r-commands sent passwords in clear and trusted source addresses. SSH 1 (1995) encrypted the channel but had protocol flaws, notably in its integrity check, and was abandoned for the SSH 2 protocol standardised by the IETF in the mid 2000s; OpenBSD's OpenSSH became the reference implementation. Trust in host keys was first handled by "trust on first use": the client records a key the first time it sees it and complains if it later changes. That works for pets and fails for rebuilt servers and autoscaled fleets, so users learned to ignore warnings, which is the very failure the scheme was meant to prevent. Publishing host key fingerprints in DNS (SSHFP records) helped only where DNSSEC was deployed.

Authentication followed a similar path. Passwords were replaced by public keys, and then key sprawl became the issue: `authorized_keys` files accumulate keys of former staff and old laptops with no expiry. Central directories (LDAP-stored keys through `AuthorizedKeysCommand`, FreeIPA) fixed distribution but not expiry. Kerberos with GSSAPI offered single sign-on in domains. OpenSSH 5.4 (2010) added **certificates**: a CA signs a public key together with a principal list, a validity interval, critical options and extensions, and servers need to trust only the CA key. Commercial and open tools (Netflix's BLESS, Facebook's work, Smallstep, HashiCorp Vault's SSH secrets engine, Teleport) wrapped this in workflows that issue certificates for minutes or hours after single sign-on.

Cryptographic hygiene has its own record of retirements: DSA keys, `ssh-rsa` signatures with SHA-1, CBC ciphers and weak MACs were removed or disabled by default over successive releases, and the compatibility fallout taught administrators to track defaults rather than freeze configuration. Recent releases pushed this further: OpenSSH 10.0 (2025) removed DSA support, made a hybrid post-quantum key exchange (`mlkem768x25519-sha256`) the default, and split pre-authentication code into a separate binary; later 10.x releases added a warning when a non-post-quantum key exchange is negotiated and tightened certificate principal matching (to verify details per release) [web: openssh.org].

## Current state

**Server policy** lives in `/etc/ssh/sshd_config` plus drop-ins in `sshd_config.d/`. On many distributions the first obtained value wins, so an early drop-in beats a later one, and `Include` order matters. Check the effective result, not the file, with `sshd -T` (extended test mode, which also accepts `-C user=...,host=...,addr=...` to evaluate `Match` blocks) and validate before reload with `sshd -t`. A reload keeps existing sessions, so you can test safely from a second connection.

Core directives for a hardened server: `PermitRootLogin no` (or `prohibit-password`), `PasswordAuthentication no`, `KbdInteractiveAuthentication no` unless used with PAM for a second factor, `PubkeyAuthentication yes`, `AuthenticationMethods publickey` (or `publickey,keyboard-interactive` to require two factors), `MaxAuthTries 3`, `LoginGraceTime 30`, `MaxStartups 10:30:60` (random early drop of unauthenticated connections), `AllowGroups ssh-users` (an allow-list is stronger than a deny-list), `X11Forwarding no`, `AllowTcpForwarding no` or a restricted value, `AllowAgentForwarding no`, `PermitTunnel no`, `PermitUserEnvironment no`, `ClientAliveInterval` with `ClientAliveCountMax` to drop dead sessions, and `Banner` for legal text. `DisableForwarding yes` is the compact way to switch off all forwarding. `Match` blocks scope exceptions, for example allowing password login only from the management network or forcing `ForceCommand` for a backup account.

**Algorithms**: `KexAlgorithms`, `Ciphers`, `MACs`, `HostKeyAlgorithms` and `PubkeyAcceptedAlgorithms` accept a list, a `+`, `-` or `^` prefix to add, remove or place first. Prefer removing items from the defaults over writing a whole list, because the defaults keep improving. On Red Hat family systems the system-wide **crypto policy** (`update-crypto-policies`, profiles DEFAULT, FUTURE, FIPS) sets OpenSSH's allowed algorithms through an include file, so compliance baselines tighten the policy rather than overriding each daemon [src: rhel-10-docs 50a4581cd9b18742]. Compliance content for FIPS-validated ciphers and MACs for the client and the server shows the expected values [src: compliance-as-code adb7584495c8ab69]. Prefer Ed25519 for user and host keys (`ssh-keygen -t ed25519`), RSA of at least 3072 bits when compatibility needs it, and FIDO2-backed `sk-` keys (`ed25519-sk`) when a hardware token should be required for each signature.

**Client policy** in `~/.ssh/config` or `/etc/ssh/ssh_config.d/`: `IdentitiesOnly yes` so the agent does not offer every key, `StrictHostKeyChecking`, `VerifyHostKeyDNS`, `ProxyJump` rather than agent forwarding for bastions, and `ControlMaster` with care. Agent forwarding exposes the agent socket on the remote machine to its root user; prefer `ProxyJump`.

**Restricting what a key can do** is written in front of the key in `authorized_keys`: `command="..."`, `from="10.0.0.0/8"`, `no-pty`, `no-port-forwarding`, `restrict` (switches everything off, then add back with `pty` and similar). Keep passphrases on user keys and put agents under a timeout.

**Certificates.** Create a CA key pair offline: `ssh-keygen -t ed25519 -f user_ca -C "user CA"`. Sign a user's public key with `ssh-keygen -s user_ca -I alice@example -n alice,deploy -V +8h id_ed25519.pub`, which produces `id_ed25519-cert.pub` carrying a key id, principals, a validity window and a serial. Inspect with `ssh-keygen -L -f id_ed25519-cert.pub`. The server trusts the CA with `TrustedUserCAKeys /etc/ssh/user_ca.pub` and decides which principals may log in as which account with `AuthorizedPrincipalsFile` (or `AuthorizedPrincipalsCommand`); by default a certificate principal must equal the account name when no principals file is set. Revocation uses `RevokedKeys` pointing at a key revocation list made with `ssh-keygen -k`, but the practical control is a short lifetime. Host certificates work in the opposite direction: sign the host key (`ssh-keygen -s host_ca -I web1 -h -n web1.example.org host_key.pub`), set `HostCertificate` in `sshd_config`, and place `@cert-authority *.example.org <CA pubkey>` in clients' `known_hosts`, so rebuilt servers present a valid certificate without any first-use prompt. Critical options such as `force-command` and `source-address` and extensions such as `permit-pty` can be baked into the certificate with `-O`. A Rocky Linux guide walks through CA setup and signing in detail [src: rocky-docs c8934adb30dcc901].

The generalised pattern is **delegated trust with expiry**: trust one small, well-guarded signing key; let it vouch for many short-lived identities; and verify a signed statement (identity, scope, time) rather than consulting a list on each host. TLS does the same with X.509 (LNX-204-T10).

## Assessment: the good, the bad and the ugly

The good: key-only authentication removes password guessing, certificates give expiry, centralised revocation by lifetime, per-principal scoping and removal of first-use prompts, and `sshd -T` makes configuration testable. OpenSSH defaults are conservative and improve every release, and the protocol's compactness and the tiny pre-authentication surface have given it an excellent security record.

The bad: configuration is first-match and drop-ins can defeat expectations; `Match` blocks apply to the end of the file or the next `Match`, so a directive placed after one is silently scoped; and a very strict algorithm list breaks old appliances, backup tools and network gear. CA private keys become a crown jewel: whoever holds the user CA can mint access to every host that trusts it. Principal handling is subtle, and a mismatch between the certificate's principal and the account produces only a terse log line on the server side.

The ugly: lockouts. Changing `AllowGroups` or authentication methods without a second open session is the classic way to lose a remote machine. Hardened ciphers combined with an old client yield "no matching key exchange method" errors that read like network faults. Agent forwarding to untrusted hosts lets their root user use your key while you are connected. Port changes and `fail2ban` reduce log noise but are not security controls; the control is not allowing passwords. Post-quantum defaults enlarge the key-exchange messages, which in rare cases breaks firewalls that mis-handle fragmented handshake packets (to verify).

## Applications beyond this domain

Certificate-based trust with short life is the same design as TLS client certificates, Kubernetes node and service certificates, SPIFFE identities, and cloud instance-metadata tokens. Git hosting supports SSH certificates for commit access; Ansible and libvirt use SSH as a transport and gain from the same CA (libvirt remote URIs of the form `qemu+ssh://` rely on an SSH trust setup) [src: libvirt-docs f85bdeb00635ab95]. `AuthenticationMethods` chains resemble multi-step authorisation policies in identity providers. The `restrict` plus forced-command idiom is how backup and deployment keys implement least privilege, a concept carried into sudo rules (LNX-204-T02).

## Examples

A hardened drop-in `/etc/ssh/sshd_config.d/10-hardening.conf`: `PermitRootLogin no`, `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `AuthenticationMethods publickey`, `AllowGroups sshusers`, `MaxAuthTries 3`, `LoginGraceTime 20`, `DisableForwarding yes`, `ClientAliveInterval 300`, `ClientAliveCountMax 2`, and a `Match Address 10.20.0.0/24` block that re-enables forwarding for the bastion network. Verify with `sshd -t`, `sshd -T | grep -i -E 'permitroot|passwordauth'`, reload, and test from a new terminal.

Certificate flow: build the CA offline; sign `alice` for eight hours with principal `alice`; copy `user_ca.pub` to servers and set `TrustedUserCAKeys`; on the server create `/etc/ssh/auth_principals/alice` containing `alice` and `ops`, and set `AuthorizedPrincipalsFile /etc/ssh/auth_principals/%u`. Alice logs in with the certificate; after eight hours the same key is rejected. `ssh -v` shows "Server accepts key: ... ED25519-CERT". Fleet-level pattern: a signing service issues the certificate after SSO, so the key never has to be a long-lived secret.

A failing example: the admin sets `PasswordAuthentication no` in the main file, but a distribution drop-in loaded earlier says `yes`; the first value wins and password logins keep working. `sshd -T` reveals it. Another: a certificate is signed with principal `alice` but the server uses `AuthorizedPrincipalsFile` that lists only `ops`; login fails and the server log says the principal is not listed.

A third: the default `PermitRootLogin` is set to prohibit-password, yet a host key was copied between machines in an image, so every clone presents the same identity; host certificates or first-boot key regeneration (`ssh-keygen -A`) fix the duplication.

## Related problems and ideas

Key distribution through FreeIPA, `AuthorizedKeysCommand` and SSSD; per-user two-factor with PAM modules (LNX-204-T01); network-level rate limiting and source filtering with nftables (LNX-204-T06); audit of logins and key use (LNX-204-T07); file-integrity coverage for `/etc/ssh` (LNX-204-T08); and compliance baselines that check these directives (LNX-204-T09). Alternatives to exposed SSH include bastions, VPNs, WireGuard overlays, session managers that broker access through an outbound connection, and zero-trust proxies; each moves where the authentication happens rather than removing the need. Not yet mainstream in all fleets: FIDO2-resident keys for every admin, SSHFP with DNSSEC, post-quantum hybrid certificates, and hardware-attested host keys.

## Active research

Post-quantum transition: hybrid key exchange is now default in OpenSSH, and signature schemes for certificates (hybrid ML-DSA with Ed25519 appeared experimentally in recent releases) are being evaluated (to verify) [web: openssh.org]. Researchers study traffic analysis against SSH keystroke timing (mitigated by obfuscation options added in 9.5), the "Terrapin" prefix-truncation attack on some cipher modes disclosed in late 2023 and mitigated by strict key exchange, and automated policy verification. Open questions include revocation at scale without lists, certificate transparency-like logs for SSH CAs, and attestation of hardware tokens.

## Future direction

Defaults will keep removing legacy algorithms: after DSA, expect further tightening of SHA-1 uses and finite-field Diffie-Hellman, and wider enforcement of post-quantum hybrids. Administrators should adopt short-lived certificates tied to SSO, keep CA keys in hardware or a managed signing service, and test configuration with `sshd -T` in CI. Watch release notes of OpenSSH and of your crypto policy tool each cycle, and plan for re-keying CAs on a schedule.
