# AppArmor: confining programs by path

## Define the problem

A program that has been compromised inherits everything its user can do. For a service, a smaller envelope is wanted: this daemon may read its configuration, write its own log, listen on one port and nothing else. Writing that envelope must be cheap enough that administrators actually do it, or the protection exists only on paper. Failure looks like a PDF viewer or browser exploit that reads SSH keys, a container that can write to the host's sensitive files, or a profile that was written once, forgotten, and silently stopped matching after the program moved.

This slice covers AppArmor, the Linux Security Module that confines programs by **file path and capability** and is the default mandatory access control (MAC) on Ubuntu, Debian and SUSE. It is the sibling of SELinux (LNX-204-T04); the contrast is part of the lesson. Container integration (Docker and Kubernetes profiles) is introduced here and developed in the container pathway.

## History and approaches

AppArmor began as Immunix SubDomain (late 1990s), was acquired and rebranded by Novell in 2005, was maintained by SUSE and later Canonical, and was merged into mainline Linux in 2.6.36 (2010). Its designers chose a path-based model because administrators already think in paths, whereas label-based models require every file to carry a type. The cost is that a path is not an identity: a hard link or a bind mount can present the same file under another name, so AppArmor checks the path used for the access and constrains mount and link operations in policy. Competing designs shaped it. SELinux gave strong guarantees with heavy policy work (LNX-204-T04). TOMOYO learned policy from behaviour. Smack used simple labels. Seccomp filters system calls instead of objects, and Landlock lets an unprivileged program restrict itself.

Early AppArmor policy suffered from two failures. Profiles written by hand were too broad or broke on updates, and profile loading at boot depended on ordering. The partial successes were the learning tools (`aa-genprof`, `aa-logprof`) that read denial logs and suggest rules, the `abstractions` include files that bundle common needs (`base`, `nameservice`, `ssl_certs`), and the shipping of enforcing profiles with distributions. Newer kernels brought policy stacking, user-namespace mediation (Ubuntu 23.10 and later restrict unprivileged user namespaces by profile) and finer network rules (to verify per release).

## Current state

The kernel part is the LSM; the userspace part loads compiled profiles with `apparmor_parser`. Profiles are text files in `/etc/apparmor.d/`, named after the binary path with slashes replaced by dots (`usr.sbin.nginx`). A profile attaches to a program by path (or by an attachment expression), can be in **enforce** mode (violations denied and logged), **complain** mode (violations allowed and logged, for learning), or **unconfined** (not loaded). `aa-status` summarises loaded profiles and which processes they confine; `aa-enforce`, `aa-complain` and `aa-disable` change modes; `apparmor_parser -r profile` reloads one, and systemd's `apparmor.service` loads all at boot. On Debian-family systems the packages are `apparmor`, `apparmor-utils` and `apparmor-profiles`.

Profile syntax is compact. Rules end with a comma:

```
#include <tunables/global>
profile myapp /usr/local/bin/myapp {
  #include <abstractions/base>
  capability net_bind_service,
  network inet stream,
  /etc/myapp/** r,
  /var/log/myapp.log w,
  /var/lib/myapp/** rwk,
  /usr/local/bin/myapp mr,
  deny /home/** rwx,
}
```

Permission letters: `r` read, `w` write, `a` append, `k` lock, `l` link, `m` memory-map executable, and for executing another program one of the transition modes. `ix` inherits the current profile, `px` transitions to the target's own profile, `ux` runs unconfined (to be avoided), and `cx` uses a child profile. Globs: `*` stays in a directory, `**` descends, `{a,b}` alternates. `deny` rules override allows and are silent in logs unless `audit` is added. Capabilities, network families, mount, signal, ptrace and dbus have their own rule types. A **hat** or child profile restricts part of a program differently, and a profile can be attached to a systemd unit through `AppArmorProfile=` in the unit file, an option documented among the execution settings [src: man-pages 74adb353ddbdf2bb].

The workflow for a new profile: `aa-genprof /usr/local/bin/myapp`, run the program through its normal functions in another terminal while the tool scans the audit log, answer the prompts (allow, deny, glob), finish, and then `aa-logprof` later as behaviour evolves. The Debian handbook describes enabling and creating profiles in this manner [src: debian-handbook 24497fcbd4b33bdd]. The profile can also be checked in compile-only mode with `apparmor_parser -Q` (or `-p` to print the parsed form), which makes a good CI test.

**Containers.** Docker loads a default profile (`docker-default`) for each container unless told otherwise; `--security-opt apparmor=<name>` selects a custom profile that you load on the host first with `apparmor_parser -r -W`. The profile applies to the container's processes from the host's kernel view, so rules refer to paths as seen inside the container's mount namespace (usually written with generous use of `deny` for `/proc` and `/sys` writes) [src: docker-docs d3507419a5802175]. Kubernetes expresses this through a pod's security context, with a field for a profile type and the name of a localhost profile; the profile must exist on every node where the pod could run [src: kubernetes-docs 8b66a06927c94fd4].

The generalised pattern is **allow-list confinement per program with a learning mode**: observe, then enforce.

**Inspecting what is confined.** Three views answer different questions. `aa-status` lists loaded profiles by mode and the processes each one confines. `cat /sys/kernel/security/apparmor/profiles` prints the kernel's own list with the mode in brackets, which is the ground truth when tools disagree, and the same pattern is how Kubernetes documents checking that a node holds a profile [web: kubernetes.io]. For a single process, `/proc/<pid>/attr/current` shows its label, and `ps -eZ` or `ps auxZ` adds the label to the process list; a process with the label `unconfined` is running outside any profile whatever the file system says. `cat /sys/module/apparmor/parameters/enabled` prints `Y` when the module is active.

**Profile structure beyond the first example.** A profile can carry flags: `profile myapp /usr/local/bin/myapp flags=(complain) { ... }` loads in complain mode regardless of the global mode, which makes a staged rollout declarative and reviewable in version control. `attach_disconnected` lets the profile apply to files reached through paths that are not connected to the root of the namespace, a common need for containerised and chrooted processes. Include files keep local changes out of packaged profiles: the shipped profile ends with `#include if exists <local/usr.sbin.nginx>`, so site rules go into `/etc/apparmor.d/local/usr.sbin.nginx` and survive a package update. Variables in `tunables/` (for example `@{HOME}` and `@{PROC}`) express path families without hard-coding them. Child profiles and hats are written as nested `profile name { ... }` blocks (or `^hat` blocks) reached through `cx` transitions or `change_hat`, which is how a daemon confines its worker or a CGI script differently from the parent.

**Beyond file access.** Rules exist for capabilities (`capability net_admin,`), network (`network inet stream,`), signals and ptrace between profiles (`signal (receive) peer=unconfined,`), mounts, pivot_root, D-Bus, and Unix-domain sockets. The `deny` qualifier takes precedence over any allow and is not logged unless prefixed with `audit`; the `audit` qualifier on an allow records successful accesses, which is useful for a sensitive file such as the key store. A rule with `owner` applies only to files the process's user owns (`owner /home/*/.config/myapp/** rw,`), which narrows an otherwise wide allowance. The rule `userns,` allows the process to create a user namespace, and Ubuntu uses that rule together with two sysctls (`kernel.apparmor_restrict_unprivileged_userns` and `kernel.apparmor_restrict_unprivileged_unconfined`) so that an unprivileged process creates a user namespace only when it runs under a profile that permits it or holds `CAP_SYS_ADMIN` [web: ubuntu.com]. The motive is that user namespaces give an unprivileged user a private set of capabilities, which has been the starting point for many kernel exploits. The feature was introduced as opt-in in 23.10 and ships enabled in the 24.04 LTS; applications that legitimately need namespaces, such as browsers and some sandboxes, receive a profile that grants only `userns,` and otherwise leaves the program unconfined.

**Policy compilation and caching.** Profiles are compiled to a binary form by `apparmor_parser` and cached, which is why the first load after an upgrade is slow and why a stale cache can mask an edit; `apparmor_parser -r` reloads and replaces the in-kernel version, and `-T` skips the cache. Failures at boot surface as a failed `apparmor.service`, so a syntax error in one profile can leave others unloaded. A pre-deployment test that runs `apparmor_parser -Q -K` over the directory (compile and check without loading) catches that error in CI.

**Kubernetes in current form.** A pod or container sets `securityContext.appArmorProfile` with a `type` of `RuntimeDefault`, `Localhost` (with a `localhostProfile` name) or `Unconfined`; the setting became stable in Kubernetes 1.31 and, if the named profile is not loaded on the node, the kubelet refuses the pod. The applied profile can be read back from inside with `cat /proc/1/attr/current`. Because the profile has to be present on every node that might run the pod, distribution is a deployment problem: DaemonSets or configuration management load profiles at node boot, and node labels or affinity keep pods off nodes where a profile is missing [web: kubernetes.io].

## Assessment: the good, the bad and the ugly

The good: profiles are readable by anyone who understands paths, complain mode makes iterative authoring practical, a profile can be a dozen lines, and distributions ship profiles for common daemons, browsers and tools. Overhead is small, and it is the easiest MAC to apply to a single application or container.

The bad: path-based rules do not follow data. Renaming, bind mounts and mount namespaces can change what path a file is accessed by, and policy must anticipate this. Profiles do not label files, so you cannot express a policy that follows the data itself, the way type enforcement can, for instance by making files created by one service unreadable to another. Coverage depends on who writes profiles: out of the box, only some services are confined, and third-party programs have none. Network control is coarse compared with nftables rules.

The ugly: a profile left in complain mode "temporarily" for years, and `ux` or `Ux` transitions granted to make a failure vanish. Reload is per profile, so a change in an abstraction shared by many profiles needs reloading all of them. Learning from logs can encode behaviour that already includes the attacker's actions if it is run on a compromised or abnormal workload. A kernel that lacks AppArmor (Red Hat family default builds) means the Docker profile flag is silently ignored; compliance rules therefore check both that the module is enabled and that profiles are in enforce or complain mode [src: compliance-as-code bdcb54ccac4fa42f].

Three limits deserve a plain statement. First, learning mode records whatever the program does while it is watched, including mistakes: if the training run included a malformed request that made the program read an unrelated directory, the generated profile will allow it. Review each suggested rule, prefer narrow globs to `**`, and treat any broad grant in a generated profile as a defect to explain. Second, a path model sees the name used for an access and not the object behind it. A hard link, a bind mount or a different mount namespace can present the same inode under a name the profile does not mention, and in either direction (an unexpected allow, an unexpected deny) the result is a surprise; the `link` permission and the mount rules exist to close the first, and testing inside the real container or namespace is the only reliable check for the second. Third, confinement attaches at execution: a process that was already running when the profile was loaded stays unconfined until it is restarted, so a profile rollout needs a service restart and a verification that `aa-status` lists the process under the profile. Profiles also constrain what a program may do, not whether the program is correct; a service that is allowed to read its database and write its log can still leak both through a logic bug.

## Applications beyond this domain

Confining a program to an allow-list learned from a trial run is the idea behind seccomp profile generators, OpenBSD's `pledge` and `unveil`, Flatpak and Snap sandboxes (Snap uses AppArmor, seccomp and cgroups together), and Android's per-app policy. The learn-then-enforce workflow also appears in firewalls that begin in log-only mode and in WAF onboarding. Systemd sandboxing options (`ProtectSystem`, `ReadWritePaths`, `CapabilityBoundingSet`) provide a different route to the same least-privilege goal and combine with a profile.

## Examples

Start a profile for a small daemon: install `apparmor-utils`, run `aa-genprof /usr/local/bin/myapp`, exercise the service, press `S` to scan the log, answer prompts, and save. Confirm with `aa-status | grep myapp`. Test by making the program try to read `/etc/shadow` and watch the denial in the journal (`apparmor="DENIED" operation="open" ...`). Roll out by keeping the profile in complain mode on a canary host for a week, then `aa-enforce`.

Failing example: a deploy script moves the program from `/usr/local/bin` to `/opt/myapp/bin`. The profile attaches by the old path, so the new binary runs unconfined and nothing reports a problem. A compliance scan or `aa-status` comparing expected and actual confinement exposes it. Another: a profile denies write to `/tmp/**` and the service silently fails to create a socket; the log line `operation="mknod"` names the missing rule.

Container example: build a profile that denies writes to `/proc/sys`, load with `apparmor_parser -r -W myprofile`, run `docker run --security-opt apparmor=myprofile ...`, and verify with `docker inspect`. The Docker guide shows the default profile and how to load a custom one [src: docker-docs 77350f01e365431e].

Rollout example for a fleet: store `usr.local.bin.myapp` in version control with `flags=(complain)`, deploy to all hosts, and collect `apparmor="ALLOWED"` lines with the host name for a week. A script groups the lines by profile and path. After the owner approves additions, the flag is removed in a single commit, so the profile moves to enforce mode on all hosts with a review trail. The same commit is checked in CI by compiling it.

Container verification example: with a pod using `type: Localhost` and `localhostProfile: k8s-deny-write`, `kubectl exec pod -- touch /tmp/x` fails with a permission error, `/proc/1/attr/current` prints the profile name with `(enforce)`, and the node's `dmesg` or audit log shows `apparmor="DENIED" operation="mknod"`. If the profile were missing on the node, the pod would not start, and that is the correct failure.

## Related problems and ideas

SELinux (LNX-204-T04) gives labels and stronger containment at a higher cost; most distributions pick one. Learning mode relies on the audit trail (LNX-204-T07). Sudo (LNX-204-T02) and SSH (LNX-204-T03) are what bring a user to a confined service. Integrity monitoring of `/etc/apparmor.d` is a standard AIDE rule (LNX-204-T08), and benchmark profiles check that all profiles are loaded (LNX-204-T09) [src: compliance-as-code bb7a242f0afd4f22]. Landlock, seccomp, and systemd sandboxing are neighbours; policy stacking aims to allow several of these at once. The Kubernetes security checklist lists AppArmor or SELinux as an expected node control [src: kubernetes-docs 7d92f37c149a40e7].

## Active research

Areas include LSM stacking in the kernel so container-specific policies coexist with the system one, mediation of user namespaces and io_uring, better policy generation from tracing (eBPF-based observers that propose profiles), and moving from path rules to hybrid path and label models. Questions remain about how to keep profiles current in rapidly released applications, and how to share profiles safely across a cluster.

## Future direction

Expect more distributions to ship confinement by default for desktop applications and to restrict user namespaces unless a profile permits them. Container platforms will treat the profile as part of the workload definition and verify it before scheduling. Watch the kernel's LSM stacking progress and distribution release notes for changes to default profiles (to verify).
