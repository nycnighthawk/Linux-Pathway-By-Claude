# Two kubeadm clusters on VMs with Cilium and Gateway API

## Define the problem

A platform team needs clusters it understands down to the node: how the control plane starts, how workers join, how pods get addresses and how traffic enters. Managed services hide these parts, which is convenient until something breaks. Two clusters are needed, not one, because upgrades, restores, cross-cluster traffic and blast radius cannot be practised on a single cluster. Failure looks like a cluster nobody dares rebuild, or an entry path that works by accident. This slice covers building two clusters on virtual machines with kubeadm, Cilium for networking and the Gateway API for ingress.

## History and approaches

Clusters began as hand-assembled sets of daemons, then installer tools (kubeadm, kops, kubespray) standardised bootstrap. Pod networking moved from overlays built on iptables towards eBPF data paths, of which Cilium is a prominent example. For traffic entry, the Ingress resource gave a minimal shared model, annotations filled its gaps in incompatible ways, and the Gateway API was designed to replace both with typed, role-oriented resources. Each stage traded simplicity for control. The pattern that emerged is a declarative cluster whose network and entry points are objects in the same API as the workloads.

## Current state

kubeadm initialises a control plane from a configuration file and prints a join credential for workers; a container runtime and the kubelet run on every node. Cilium is installed as the network plugin, can replace kube-proxy, and supplies network policy and flow visibility. The Gateway API adds GatewayClass, Gateway and route objects: the platform team owns the gateway, application teams attach routes. The two clusters use distinct pod and service ranges so they can be joined later. The virtual machines come from libvirt and cloud-init images described as code. A post-install check lists nodes as Ready, runs the Cilium status command and requests a hostname through a test gateway.

## Assessment: the good, the bad and the ugly

kubeadm is transparent and close to upstream; Cilium gives fast policy and good visibility; the Gateway API separates roles cleanly. The costs are many moving parts, version skew rules between components, kernel feature needs for eBPF, and certificate expiry that kubeadm only renews on upgrade or on request. A single control-plane node is acceptable for a lab and unsafe for production. The ugly part is silent misconfiguration: a route attached to a gateway that does not allow its namespace is simply ignored.

## Applications beyond this domain

Declarative bootstrap and typed traffic routing appear in service meshes, API gateways, cloud load balancer controllers and edge platforms. The role split, where the platform owns infrastructure objects and teams own routes, is a general multi-tenant design.

## Examples

A worked example: both clusters were created with the default pod range; later, cross-cluster routing failed because addresses overlapped, and the fix was a rebuild with distinct ranges, so ranges are now fixed first in the inventory. A failing example: a route for the shop application never received traffic because the gateway listener allowed routes from its own namespace only; reading the route status conditions showed the reason.
