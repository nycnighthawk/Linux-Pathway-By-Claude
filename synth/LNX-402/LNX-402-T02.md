# GitOps for platform and apps with Argo CD

## Define the problem

Once clusters exist, someone must decide how changes reach them. Running kubectl from laptops leaves no record, cannot be reviewed and drifts. The problem is to make Git the single source of truth for both the platform (controllers, policies, monitoring) and the applications, with an agent in each cluster that pulls the desired state and reports differences. Failure looks like a cluster that nobody can reproduce and a change nobody can trace to a person or a review.

## History and approaches

Deployment moved from manual commands to scripts, then to push-based pipelines that hold cluster credentials in the CI system. The GitOps idea, named around 2017, reversed the direction: an in-cluster controller pulls from Git and reconciles, so credentials stay in the cluster and the repository is the audit trail. Tools such as Argo CD and Flux implement it. Packaging tools (Helm, Kustomize) supply the templates the controller renders.

## Current state

Argo CD runs in a management cluster or in each cluster and watches Application resources that name a repository path, a revision and a destination. A common structure is an app-of-apps or ApplicationSet: one root object generates an application for each cluster and each component. Platform components are installed first (sync waves order them), then applications. Automated sync with pruning and self-heal keeps the cluster equal to Git; a diff view shows drift. Secrets are not stored in plain text: a sealed or externally referenced scheme is used. Repository layout separates platform, per-cluster overlays and application definitions.

## Assessment: the good, the bad and the ugly

The strengths are auditability, easy rollback by reverting a commit and a consistent way to rebuild a cluster. The weaknesses are the bootstrapping problem (who installs the controller), secret handling, the delay between commit and sync, and the large blast radius of a bad commit to a root application. Self-heal can fight an operator who is debugging in an emergency. The ugly part is that rendered output can differ from what a reviewer saw in the diff, so rendered manifests are worth reviewing too.

## Applications beyond this domain

The same reconcile-to-declared-state loop is used for infrastructure (Terraform controllers), for device fleets, for policy engines and for operating systems that update from an image reference.

## Examples

A worked example: a root application creates apps for two clusters; a change to the ingress gateway version is made in Git, the canary cluster syncs first and the second follows after a health check. A failing example: a pruning rule deleted a namespace because a path was renamed; the fix was to mark critical namespaces as protected and to review prune previews.

## Related problems and ideas

Related ideas are progressive delivery (canary and blue-green rollouts), policy gates on pull requests, and pull-based fleet management. Push-based pipelines remain valid where clusters cannot reach the repository.

## Active research

Active work includes multi-cluster scale for application sets, better secret management integration, and safer handling of large diffs (to verify).

## Future direction

Expect tighter integration between GitOps and supply-chain verification, so that only signed artefacts are reconciled, and more managed offerings.
