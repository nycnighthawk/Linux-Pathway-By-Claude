# Policy: PSA, Kyverno, signed images only

## Define the problem

By default a cluster lets a user with deploy rights run almost anything: privileged pods, images from any registry, containers as root. A platform must enforce rules about what may run, at the moment of admission, and must show developers a clear reason when a workload is refused. The problem is to combine the built-in pod security levels, a policy engine and image signature verification so that only approved, signed, least-privilege workloads start.

## History and approaches

Early clusters used PodSecurityPolicy, which was hard to use and was removed. Pod Security Admission replaced it with three levels (privileged, baseline, restricted) applied per namespace by label. Policy engines such as Kyverno and OPA Gatekeeper added custom rules. Supply-chain work (Sigstore and cosign) added signed images and attestations, which policy can verify at admission.

## Current state

Pod Security Admission enforces a level per namespace, with modes to warn and audit before enforcing. Kyverno policies, written as Kubernetes resources, validate, mutate or generate objects and can verify image signatures against a public key or keyless identity. The platform sets a cluster default level, exempts system namespaces explicitly, and ships policies through the GitOps repository with tests that apply sample workloads and expect accept or reject.

## Assessment: the good, the bad and the ugly

Policy at admission gives uniform control, fast feedback and an audit record. Costs are the risk of blocking the platform itself, policy sprawl, performance impact on admission webhooks and the failure mode of a webhook outage (fail open or closed). Signature checks only prove who signed, not that the content is safe. The ugly part is exceptions: each one weakens the model and tends to become permanent.

## Applications beyond this domain

The same pattern of admission control with signed inputs appears in cloud account guardrails, CI policy gates, and device attestation for network access.

## Examples

A worked example: a policy requires images from the internal registry with a valid signature; a developer deploys a public image and gets a clear denial message naming the rule. A failing example: a new policy denied the monitoring agent because it needs host access; the fix was a narrow, reviewed exception for that namespace.

## Related problems and ideas

Related topics are runtime security detection, network policy, secrets handling and software bills of materials. Alternatives are validating admission policies in the API server (CEL) that avoid external webhooks.

## Active research

Active work covers built-in CEL admission policy, attestation formats and keyless signing transparency (to verify).

## Future direction

Expect more of this logic to move into the API server itself, and signed provenance to become a normal deployment requirement.
