# Version upgrade and etcd restore drill

## Define the problem

A cluster that cannot be upgraded becomes a security liability, and one whose etcd cannot be restored is a single mistake from total loss. Kubernetes releases frequently and supports each minor version for a limited time, so upgrades are routine, and etcd holds every object in the cluster. The problem is to rehearse both on a live lab cluster: a minor version upgrade done in the supported order, and a restore of etcd from a snapshot after a deliberate failure, with proof that applications come back.

## History and approaches

Early upgrades meant rebuilding. kubeadm added an upgrade workflow, and the project documented version skew rules that say which components may differ by how much. Etcd backups started as copies of the data directory, and moved to consistent snapshots taken through the etcd API. Teams learned from outages that an untested backup is only a hope, which led to scheduled restore drills.

## Current state

An upgrade goes one minor version at a time: read the release notes, back up etcd, upgrade the first control plane node with the kubeadm plan and apply steps, then the other control plane nodes, then each worker after draining it, then the kubelet on each node. Afterwards check node versions, workload health and add-on compatibility. For etcd, a snapshot is taken with the etcdctl tool using the node certificates, verified, and copied off the machine. A restore creates a new data directory from the snapshot, points the static pod manifest at it, and restarts the control plane. All steps become scripts with a verification command after each.

## Assessment: the good, the bad and the ugly

The drill gives confidence and exposes hidden issues such as deprecated APIs still used by a manifest, an add-on that lags the new version or a backup that was never copied away. Risks include downtime during control plane restarts in a single-node lab, restoring stale data over newer state, and certificates that expire during a long upgrade window. The ugly parts are skipped minor versions, which are unsupported, and the mismatch between snapshot time and the state of external systems such as volumes.

## Applications beyond this domain

Rehearsed upgrade and restore applies to databases, directory servers, message brokers and any system with a leader and a state store.

## Examples

A worked example: the drill deletes a namespace, restores from a snapshot taken twenty minutes earlier, and finds that one deployment's newest revision is missing; the team records the recovery point and decides the snapshot interval is too long. A failing example: an upgrade stalled because an old API version was still referenced by a manifest in Git; the pre-upgrade deprecation check was added to the plan.

## Related problems and ideas

Related topics are backup of persistent volumes, disaster recovery across clusters, and managed upgrade channels. Alternatives to in-place upgrade are blue-green clusters and replacement of control plane machines.

## Active research

Work includes automated upgrade controllers, better deprecation detection and safer etcd operation (to verify).

## Future direction

Expect longer support windows to be debated, more automation of upgrades and wider use of replace-instead-of-patch control planes.
