# Week-long soak and chaos test

## Define the problem

Systems pass short tests and fail over time: memory leaks, certificate rotation, log growth, slow resource exhaustion. They also fail in ways that single tests do not reveal, such as when a node disappears while a deployment rolls. The problem is to run the platform under steady load for a week and to inject failures on a plan, recording whether it recovers by itself and how fast.

## History and approaches

Soak testing is old practice from hardware and telephony. Chaos engineering was articulated by large web operators who killed instances in production to prove resilience. Kubernetes tools such as Chaos Mesh and Litmus express experiments as resources: kill a pod, delay network traffic, fill a disk.

## Current state

A plan states the steady-state hypothesis (for example error rate below a threshold), the load, the experiments and the abort conditions. Load runs continuously. Experiments run on a schedule: pod kill, node drain, network latency between clusters, DNS failure, loss of a control plane node. Monitoring records the effect; each experiment is judged against the hypothesis. At the end the week's data is summarised with findings and fixes.

## Assessment: the good, the bad and the ugly

The test finds leaks, thin alerts and missing disruption budgets. Its limits are time cost, load that does not resemble real traffic and the risk of damage if abort rules are weak. The ugly part is the result that nobody acts on: findings need owners.

## Applications beyond this domain

Soak and fault injection apply to storage systems, databases, network equipment and any long-running service.

## Examples

A worked example: a node drain during a rolling update takes down both replicas because no disruption budget existed; a budget and anti-affinity are added. A failing example: memory grew slowly in the log shipper until the node evicted pods on day five.

## Related problems and ideas

Related ideas are game days, canary analysis, load modelling and resilience scoring.

## Active research

Research looks at automated experiment selection and at proof of resilience from limited tests (to verify).

## Future direction

Expect chaos experiments to move into CI for platform changes, with smaller, continuous tests.
