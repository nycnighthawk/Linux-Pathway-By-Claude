# Same platform on managed Kubernetes

## Define the problem

Most organisations eventually run Kubernetes on a managed service, where the provider operates the control plane. The platform built by hand must then move to a managed cluster without being rewritten. The problem is to deploy the same GitOps-defined platform and applications to a managed cluster, to find what differs (networking, identity, storage, upgrades, limits) and to compare cost and operational effort with the self-built clusters.

## History and approaches

First managed offerings arrived soon after Kubernetes itself, each provider adding its own network plugin, identity integration and add-on model. Portability came through the common API, through Helm and GitOps repositories, and through cloud-neutral infrastructure tools. Differences stayed in the surroundings: how nodes join, how workloads obtain cloud permissions and which add-ons the provider installs.

## Current state

A managed cluster is created with infrastructure code in the cloud account, with private networking, node pools and workload identity. The GitOps controller is bootstrapped in the new cluster and syncs the platform repository with a cluster-specific overlay. Provider-specific parts are isolated in that overlay: storage classes, load balancer annotations, identity mappings. The checks from the self-built clusters run again, and a comparison notes the differences found.

## Assessment: the good, the bad and the ugly

Managed clusters remove control plane work and give integrated upgrades and identity. The costs are less control (you cannot change control plane flags), provider-driven upgrade timing, extra cost for the service and lock-in through identity and networking. The ugly parts include add-ons that overlap with ones you run (two ingress controllers, two policy engines) and cost surprises from node pools and load balancers left running.

## Applications beyond this domain

The pattern of a portable core with provider overlays is the same as for multi-cloud applications, hybrid estates and edge deployments.

## Examples

A worked example: the Gateway API objects deploy unchanged, but the load balancer needs a provider annotation set in the overlay; the shared check suite finds the difference at once. A failing example: the platform controller was given broad cloud permissions through a static key; the fix was workload identity with a narrow role.

## Related problems and ideas

Related topics are multi-cluster management, cluster autoscaling, spot capacity and cloud cost management. Alternative: fully managed application platforms with no cluster access.

## Active research

Active work covers cluster autoscaler design, workload identity standards and multi-cloud cluster management (to verify).

## Future direction

Expect providers to take more of the platform layer (managed GitOps, policy, observability) and portability tests to matter more.
