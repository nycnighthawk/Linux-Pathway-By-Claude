# The container network interface: a small contract between runtimes and plugins

## Define the problem

When a pod starts, someone has to give it a network: create or join a namespace, attach an interface, assign an address, set routes and perhaps open firewall rules. When the pod stops, someone has to undo that and return the address to the pool. The container runtime is the natural place to trigger this, but runtimes should not each reimplement networking for every environment, and network vendors should not have to patch every runtime. Without a shared contract, each pairing of runtime and network implementation needs its own glue, and the cluster operator is locked into whichever pairs exist.

The contract has to be small enough that anyone can implement it, and strong enough to let independent pieces compose. It must define how the runtime tells a plugin what to do and for which container, how the plugin reports the result, how several plugins cooperate (one makes the interface, another allocates the address, a third adds port mappings or bandwidth limits), how errors are signalled and how versions are negotiated. Failure of the contract shows up in practice as pods stuck in ContainerCreating with a sandbox error, leaked addresses after crashes, configuration files in the wrong place or of the wrong version, and plugins that work alone but fail when chained.

This slice covers the container network interface (CNI): its specification, the lifecycle of a call, configuration and chaining, IPAM delegation, the reference plugins, how the container runtime and kubelet load it, and what it takes to write a minimal plugin yourself. The comparison of existing network plugins (T03) and the Services machinery (T04) build on it.

## History and approaches

The need appeared with the first wave of container runtimes. Docker had its own networking model, the container network model with libnetwork, built around drivers, networks and endpoints; CoreOS's rkt, started in 2014, needed something simpler and runtime-neutral and published the container network interface specification in 2015, modelled on small executables invoked per container, in the Unix tradition. Kubernetes considered both models and, after a short debate, chose CNI for its simplicity: libnetwork was tied to Docker and had its own control-plane assumptions. The Kubernetes documentation on network plugins now describes the project's choice, listing CNI plugins as the supported mechanism and noting the requirements the node has to meet, such as loading the loopback plugin and enabling bridged traffic visibility for iptables. The project joined the CNCF in 2017 and has its own maintainers and a reference plugins repository.

The specification evolved in versions. Early ones defined ADD and DEL with a JSON configuration on standard input and a JSON result on standard output. Version 0.3 added chaining through the `prevResult` field, so several plugins could cooperate. Version 0.4 added the CHECK operation to verify an existing attachment. Version 1.0 stabilised the format and removed the deprecated parts. Version 1.1 added STATUS, which lets the runtime ask whether the network is ready, and GC, which tells a plugin which attachments are still valid so it can clean up leaks. Throughout, compatibility was handled by the VERSION command and the `cniVersion` field.

Competing and complementary approaches filled the gaps. The network binding plugin mechanism of KubeVirt shows a different kind of extension: a plugin that decides how a virtual machine's interface is bound to the pod's network, deployed to the nodes and documented in its guide, with a passt-based plugin whose CNI component must be installed on the nodes; it builds on CNI instead of replacing it. Multus, a meta-plugin, calls several CNI plugins so a pod can have more than one interface. Container build tools such as BuildKit expose a CNI-based networking mode with a bridge configuration, which shows the contract being reused outside Kubernetes. Cilium and others also install their own CNI configuration files and binaries which merely forward to an agent over a socket, so the plugin executable is a thin client of a long-running daemon.

The lessons: keep the interface to a handful of verbs and a JSON document; let plugins be separate executables with no linking; compose by chaining and delegation; make deletion idempotent; and add lifecycle verbs (check, status, garbage collection) when reality shows leaks.

## Current state

**The contract.** A CNI plugin is an executable. The runtime invokes it with environment variables and the network configuration as JSON on standard input, and reads a JSON result on standard output; a non-zero exit with a JSON error object reports failure. The key environment variables are `CNI_COMMAND` (ADD, DEL, CHECK, VERSION, and in the newer specification STATUS and GC), `CNI_CONTAINERID`, `CNI_NETNS` (the path of the container's network namespace), `CNI_IFNAME` (the interface name to create inside it), `CNI_ARGS` (extra key-value pairs, which Kubernetes uses to pass the pod name and namespace) and `CNI_PATH` (where to find other plugins for delegation). The runtime creates the namespace and holds it; the plugin joins it.

**Operations.** ADD must create the interface in the namespace, configure it, and return a result listing interfaces, IP addresses with their gateways, routes and DNS settings. DEL must release everything that ADD acquired, and must succeed even if some of it is already gone, because runtimes call it on partially failed setups and after crashes. CHECK verifies that the attachment still looks as ADD left it. VERSION prints the supported specification versions. STATUS lets the runtime test whether the plugin is ready to serve ADD, which is how the kubelet's network-ready condition can follow reality. GC receives the list of valid attachments and removes the rest.

**Configuration.** A network configuration is a JSON object with `cniVersion`, `name`, `type` (the plugin executable's name) and plugin-specific fields, plus an optional `ipam` section naming an IPAM plugin. Files normally live in `/etc/cni/net.d`, and the plugin binaries in `/opt/cni/bin`. When a directory has several files the runtime uses the first in lexical order, which is why numbering prefixes such as `10-` and `05-` matter and why a stale file left by an uninstalled plugin can win and break the node. A *configuration list* (`.conflist`) names a chain of plugins: the runtime invokes them in order for ADD and in reverse order for DEL, passing each plugin the result of the previous one in `prevResult`, so a bridge plugin can create the interface, an IPAM plugin can assign an address, a portmap plugin can add hostPort rules and a bandwidth plugin can shape the interface.

**IPAM.** Address management is a separate plugin type so that interface plugins need not know how addresses are allocated. A main plugin calls its IPAM plugin, found through `CNI_PATH` and named in the `ipam.type` field, passing the same environment and configuration, and merges the returned addresses. Reference IPAM plugins include `host-local` (allocates from a range and keeps one file per address under a state directory on the node, ensuring uniqueness per host), `dhcp` (uses a helper daemon to run DHCP on behalf of the container) and `static`. Cloud-integrated plugins allocate from the provider's network, as the Cilium documentation on Azure IPAM shows, where address pools come from the cloud API instead of a per-node range. A common design is cluster-wide IPAM, where the controller assigns each node a pod subnet from the node's `podCIDR` field and the node-local plugin allocates from it.

**Reference plugins.** The containernetworking project maintains a repository of plugins: interface creators (`bridge`, `ptp`, `macvlan`, `ipvlan`, `host-device`, `vlan`, `dummy`), IPAM plugins, and meta plugins (`portmap` for hostPort, `bandwidth` for traffic shaping, `firewall`, `tuning` for sysctls, `sbr` for source-based routing). The `loopback` plugin brings up lo inside the namespace and is required by Kubernetes. The Docker BuildKit documentation shows a minimal use: a configuration file selecting the bridge plugin with a host-local IPAM range. This is the same arrangement described in the first slice of this course, now automated.

**How Kubernetes calls it.** The kubelet does not call CNI directly. It asks the runtime, over the CRI socket, to create a pod sandbox; the runtime (containerd or CRI-O) creates the namespace, reads the CNI configuration directory and invokes the plugin chain, passing the pod name and namespace in `CNI_ARGS`. Failure shows up as a sandbox creation event on the pod. When no valid configuration exists, the runtime reports the network as not ready and the node condition reflects it, which explains why a freshly initialised node stays NotReady until some network plugin is installed. Windows nodes have their own set of CNI plugins and limitations, which the Kubernetes Windows documentation lists.

**Writing a minimal plugin.** A plugin needs to do five things. Read the command from the environment and the JSON from standard input. For ADD, open the namespace path, create a veth pair (or other device), move one end into the namespace and name it as requested, assign an address (from configuration or by delegating to IPAM), add a default route, and optionally attach the host end to a bridge. Print a result with `cniVersion`, the interface list and the IP list. For DEL, remove the host-side device or the address reservation and succeed when already absent. For VERSION, print the list of supported versions. For anything else, print an error JSON with a code and message and exit non-zero. A shell script can do this with `ip` and `jq`, which is a good teaching exercise although production plugins are written in Go using the project's libraries, which handle version negotiation, chaining and namespace switching safely. The lab for this slice builds a plugin as a shell script and drives it with a small harness that sets the environment variables like a runtime would.

## Assessment: the good, the bad and the ugly

The good: the contract is small and has lasted. A plugin is easy to test, since it is a program with documented inputs and outputs, and any runtime can use any plugin. Chaining and IPAM delegation give composition without a framework. It has enabled a diverse ecosystem, from simple bridge setups to eBPF datapaths, while the runtime and kubelet stay unchanged.

The bad: the per-container executable model is slow and stateless in ways that matter at scale. Each pod start forks a process and may need to coordinate with a daemon. Plugins hold state in files on the node or in a daemon, and the specification said little about it until GC and STATUS were added. The contract covers only attachment and detachment of one interface: it says nothing about cluster-wide features such as network policy, Services or multi-cluster connectivity, which each plugin implements out of band. It has no notion of dynamic changes to a running pod's network, so reconfiguration needs a restart or a side channel.

The ugly: operational fragility. Stale configuration files in `/etc/cni/net.d` win over the right ones because of lexical ordering. A plugin version that emits an older result format breaks a chain that expects newer fields. Crashes between ADD and the runtime recording success leak addresses, filling the `host-local` pool until pods cannot start. The runtime may call DEL with a missing namespace, which plugins that assume it exists turn into errors and in turn into stuck pod deletion. Binaries missing from `/opt/cni/bin` after a node image change produce sandbox errors that mention only an executable not found. Multiple CNI installers on the same node fight over the configuration directory. And plugin binaries run as root with access to the host, so they are part of the trusted computing base of the node.

Mitigations: keep exactly one network plugin's configuration in the directory; remove files when uninstalling; use versions of the runtime and plugins that agree on the CNI version; make DEL tolerant; monitor address pool usage; use GC where supported; keep a test that creates and removes pods in a loop.

## Applications beyond this domain

The pattern of small executables with a documented environment and JSON protocol, chained by a configuration file, is the Unix filter model applied to infrastructure. It resembles CGI, Git hooks and credential helpers (including the kubelet's image credential provider and client-go credential plugins, which also run executables with a JSON exchange). The Container Storage Interface, a sibling contract, chose gRPC instead because storage drivers are long-lived and richer. The idea of an interface that separates mechanism from policy appears in the Linux kernel's own plugin points (netfilter hooks, eBPF), in the OCI runtime specification and in libvirt's network hooks. KubeVirt's network binding plugins and Multus use CNI as the substrate for specialised attachments, and build tools use it to give build containers networks without Kubernetes.

## Examples

A minimal bridge configuration, saved as a conflist in the CNI directory, naming the bridge plugin with `isGateway` and `ipMasq` enabled and `host-local` with a subnet range, followed by the portmap plugin with its capability for port mappings. With it, a runtime creates pods on a single node with the same network as in the hand-built lab, using the reference plugins.

Testing a plugin without a cluster: set `CNI_COMMAND=ADD`, `CNI_CONTAINERID=test1`, `CNI_NETNS=/run/netns/test1`, `CNI_IFNAME=eth0` and `CNI_PATH=/opt/cni/bin`, pipe a configuration to the plugin and read the JSON result; then run DEL with the same variables and confirm that the host side is clean. The project's `cnitool` automates this.

A failing example: a node stays NotReady after installing a new network plugin. The kubelet reports that no network is configured. The directory contains `10-calico.conflist` left from a previous experiment and `05-cilium.conflist`; the runtime picks the lexically first file, which refers to a binary that was removed. Deleting the stale file fixes it.

Another failing example: after a node crash, new pods fail with a message that the address range is exhausted. The `host-local` state directory contains files for addresses of pods that no longer exist. Cleaning the leaked files (or using a version with garbage collection) restores the pool; the lesson is that DEL cannot run for pods whose node crashed, which is why GC exists.

## Related problems and ideas

Multus and the Kubernetes Network Plugin Working Group's multi-network proposals address attaching more than one network to a pod. Device plugins and SR-IOV CNI give pods direct hardware interfaces. Dynamic resource allocation may eventually represent network interfaces as claimable devices. Alternatives to per-pod executables include in-process CNI implementations in runtimes and sandbox-aware designs such as Kata Containers, where the pod's network namespace is connected to a virtual machine through tap devices by an adapter. The proposal for a network readiness API and for informing the scheduler about node network capacity is ongoing. Not mainstream: replacing the executable protocol with a gRPC contract in a future specification, a direction discussed in the project but not adopted.

## Active research

The CNI maintainers work on the 1.1 features (STATUS and GC) and their adoption by runtimes, on stricter validation of results and on better multi-network support. The Kubernetes networking group studies how to expose multiple network interfaces and device-backed networks to pods and how to make network plugins' readiness visible to the scheduler. Security researchers examine the privilege of CNI binaries and the risks of arbitrary arguments in `CNI_ARGS`. Performance work compares the cost of per-pod plugin invocation with in-kernel or daemon-based fast paths, and investigates avoiding repeated work on pod churn (to verify which runtimes implement GC and STATUS in your versions).

## Future direction

Expect CNI to stay stable and boring, with incremental additions such as GC and STATUS in wider use, while higher-level pod networking features (multiple interfaces, device-backed networks, network policy APIs) develop in the Kubernetes API itself. Plugins will continue moving the heavy lifting into daemons and eBPF programs, with the executable as a thin shim. For an administrator, the useful skill is reading a conflist, tracing a failed ADD from the runtime's log to the plugin's stderr, and keeping the directory clean.
