# Load-balancer addresses without a cloud: MetalLB, BGP and FRR

## Define the problem

On a public cloud, creating a Service of type LoadBalancer causes the cloud controller to provision a balancer, allocate an address and update the Service's status with it. The Kubernetes documentation defines the type exactly that way: the API asks for a balancer and an external provider supplies one [src: kubernetes-docs 0372456244ec915d]. On bare metal, in a private data centre, or in a lab built on virtual machines, no provider exists, so the Service stays in the pending state forever. The cluster can still expose applications through NodePort Services, but node addresses are unstable, port numbers are in an awkward range, and nothing spreads load or removes a failed node from rotation.

The missing piece has two parts. First, something must hand out external addresses from a pool the operator owns and write them into Service status. Second, something must make the network deliver traffic for those addresses to a node that can serve them, and move that delivery when a node fails. The delivery problem is a routing problem, and it has two classical solutions that every Linux administrator already knows: answer address-resolution requests on the local segment so that neighbours believe the address lives on one node, or speak a routing protocol with the neighbouring routers so that they send traffic for the address to the nodes that announce it.

This slice teaches both through MetalLB, the most widely used implementation, and shows the alternative that comes built into some network plugins. Along the way it covers the Linux side of equal-cost multipath routing, the FRR routing suite that appears in both MetalLB and in the top-of-rack switches that peer with it, and the pitfalls around traffic policy and source addresses.

## History and approaches

Before dedicated tools, clusters on bare metal used a hardware load balancer configured by hand, a keepalived pair floating one address in front of the nodes, or a DNS round robin over node addresses. Each of these worked and each required work outside the cluster for every new Service. MetalLB, started in 2017 by a Google engineer and later adopted by the CNCF as a sandbox project, put both the address allocation and the announcement inside the cluster: a controller assigns addresses from configured pools, and a speaker on each node announces them using ARP and NDP for layer-2 mode, or BGP for routed mode. The early BGP implementation was a small native Go speaker supporting only the essentials. Later releases added an FRR-based backend, which brought a mature protocol stack with features such as BFD for fast failure detection, and the project shifted configuration from a single ConfigMap to a family of custom resources so that pools, peers and advertisements could be managed separately and validated at admission.

Other approaches fill similar needs. kube-vip provides a virtual IP for the control plane and for Services using ARP or BGP. Network plugins grew their own: Calico can advertise Service and Pod ranges over BGP, kube-router has done so for years, and Cilium offers a BGP control plane with resources that describe peers, advertisements and per-node configuration, and a layer-2 announcement feature of its own [src: cilium-docs 8c7720b6c73cc4c4]. Which of these to use is mainly a question of how many components the cluster already has: running MetalLB beside a plugin that has its own announcements means two systems writing to Service status and two systems that may both try to speak BGP from the same node, which is a recipe for conflicts.

The history of failures is mostly operational. Layer-2 mode concentrates all traffic for a given address on one node at a time, because only one speaker answers for it, so it provides failover but not load balancing, and failover time is bounded by how quickly clients and switches update their ARP caches. Switches with dynamic ARP inspection, or cloud networks that filter ARP, silently break the mode. BGP mode, in turn, depends on the router: some routers require explicit configuration for each neighbour, or limit the number of equal-cost paths, or hash flows in a way that sends all connections of one client to one node. And the combination of externalTrafficPolicy Cluster with ECMP routing causes an extra hop and source address translation, which hides the client's address from the application until the policy is changed to Local, at the price of having to announce an address only from nodes that have a ready endpoint.

## Current state

**Components.** MetalLB has a controller Deployment, which assigns addresses and updates Service status, and a speaker DaemonSet, which announces them. Both read custom resources in the metallb-system namespace. An IPAddressPool defines a set of addresses (a CIDR or a range), whether they are auto-assigned, and optional selectors that restrict which namespaces or Services may draw from the pool. A Service can ask for a pool or a specific address with an annotation or the standard loadBalancerIP-style request, and sharing one address between Services (on different ports) is allowed by an annotation that names the sharing key.

**Layer-2 mode.** An L2Advertisement resource selects the pools to announce at layer 2 and optionally the nodes and interfaces. For each address one speaker is chosen from the nodes that have a ready endpoint; that node answers ARP requests for IPv4 and neighbour solicitations for IPv6. The chosen node receives all traffic for the address, then the data plane (kube-proxy or the eBPF datapath) spreads it across Pods. Failover occurs when the memberlist-based failure detection removes the node, after which another speaker sends a gratuitous ARP to update neighbours. The mode needs nothing from the network beyond a shared segment, which makes it the right choice for labs and small sites. A prerequisite appears when kube-proxy runs in IPVS mode: strict ARP must be enabled, or every node answers ARP for every address and the whole mechanism breaks.

**BGP mode.** A BGPPeer resource describes a router: its address, autonomous system number, the local autonomous system number, optional password, hold time, BFD profile, and node selectors that decide which nodes peer with it. A BGPAdvertisement selects pools and says how to announce them: the prefix length of the aggregate, local preference, communities, and the nodes or peers that should carry the announcement. With the FRR backend, each speaker runs an FRR instance in the pod. Every node with a ready endpoint announces the address to its peers; the router installs one path per node and spreads flows over them with equal-cost multipath, which gives true load distribution, not just failover. Failure detection depends on timers: the default hold time would leave a dead node in rotation for tens of seconds, so BFD, which detects failure in under a second, is recommended where the router supports it. The MetalLB documentation calls out several compatibility traps (for example, that some configurations cannot combine certain options), and these should be read for the exact version in use.

**The router side with FRR.** FRR is the routing suite behind many software routers and several switch operating systems. A top-of-rack configuration is short: a router BGP block with the local AS, either explicit neighbour statements per node or a listen range with a peer group so that new nodes join automatically, an IPv4 unicast address family in which the neighbours are activated, a maximum-paths setting that permits equal-cost multipath, and prefix filters so that nodes can announce only the pool range. The Debian handbook's overview of dynamic routing is a good background on why a routing daemon replaces static routes at this scale [src: debian-handbook eeae081f0a252519]. On Linux hosts acting as routers, the kernel's multipath hash policy matters: the default hashes only on addresses, so all flows between two hosts take one path, and setting the policy to include layer-4 ports spreads connections.

**Traffic policy.** The Service field externalTrafficPolicy has two values. Cluster lets any node receive traffic and forward it to any endpoint, with an extra hop and source address translation. Local delivers only to endpoints on the receiving node, preserves the client source address, and, with BGP, causes only nodes with endpoints to announce the address. Local is therefore the preferred setting for services that need the client address, provided the endpoints are spread across nodes. The related health check node port lets an external balancer ask a node whether it has endpoints.

**Allocation internals.** Kubernetes itself tracks address assignment for cluster IPs and, in recent versions, uses a dedicated object to track allocations in the Service range; external load balancer addresses are a separate matter handled by the controller, and it is the controller's job to prevent duplicates [src: kubernetes-docs 0ef3dbc9e1238bc7].

**Operating.** Typical checks are: the Service has an external address; the speaker logs show the announcement; the router's BGP summary shows the session established and the prefix received; the routing table on the router lists all expected next hops; and a test client reaches the address. Upgrades of MetalLB should follow its release notes because configuration formats have changed more than once. Alerts should cover session state, the number of announced prefixes, and exhausted pools.

## Assessment: the good, the bad and the ugly

**The good.** MetalLB turns a cluster on ordinary hardware into one with cloud-like Service semantics with little infrastructure. Layer-2 mode is trivial to try. BGP mode gives real load balancing and fast failover with the same protocol the rest of the data centre already uses, and integrates with existing network operations: prefix filters, communities and route monitoring all apply. The custom resources are declarative and fit GitOps.

**The bad.** Layer-2 mode is not load balancing and has slow, client-dependent failover. BGP mode requires a cooperating network team, with all the process that implies, and routers vary in how many paths and how flexible hashing they support. The distinction between the native and FRR implementations, and between MetalLB's BGP and the BGP of the cluster's plugin, is confusing, and configurations do not carry over. Client address preservation needs the Local policy, which couples availability to endpoint placement.

**The ugly.** Two BGP speakers on one node (a plugin and MetalLB, or two MetalLB layers) fight for the same port and one silently fails. A router that applies per-packet hashing sends the packets of a single connection down different paths and breaks reassembly in odd ways. A leaked announcement of a pool that overlaps another network can blackhole traffic data-centre-wide, which is why prefix filters on the router side are part of the design, not an optional extra. In layer-2 mode, a switch that learns the address on two ports during failover can produce intermittent loss. And one often overlooked item: when the speaker pods restart together during an upgrade, announcements drop, so a rolling update with a pod disruption policy and graceful restart where supported is worth the effort.

## Applications beyond this domain

The same mechanisms are used for anycast services such as DNS and content delivery: several servers announce the same address, and the network sends each client to the nearest one. Linux hosts running FRR or BIRD announce service addresses to the fabric in many large networks without any container platform, and the routed-to-the-host design (a layer-3 network all the way to the server, with BGP unnumbered between server and switch) is a common data-centre architecture for avoiding layer-2 domains. Failover with a floating address and gratuitous ARP is the oldest high-availability pattern on Linux, in the form of VRRP and keepalived, and layer-2 mode is that pattern with a Kubernetes controller deciding who owns the address.

## Examples

A first example is a lab cluster with layer-2 mode. The operator creates an IPAddressPool with a small range from the lab's subnet outside the DHCP range and an L2Advertisement that selects it. A Service of type LoadBalancer receives the first address, and from another host on the segment the operator sees the ARP entry resolve to the announcing node's MAC address. Killing that node moves the entry to another node within seconds and the service continues, with new connections only, since existing ones were tied to the failed node.

A second example is a BGP design for a production rack. The top-of-rack switches are in AS 65000 and the nodes in AS 65010. A peer group on the switch with a listen range for the node subnet accepts new nodes; the nodes peer with both switches for redundancy, with BFD at a fraction of a second. The pool is a small prefix outside any other use, announced as a /32 per address, with a prefix filter on the switch that accepts only that range. The Service uses the Local policy so that the client address is preserved. The test is to drain one node and watch the switch routing table remove that next hop within a second while a load generator shows no failed new connections.

A third example is a diagnosis. A Service has an address but external clients cannot reach it. The operator checks the speaker log and sees no announcement. The reason is that the Service's endpoints are all on a node that is excluded by the advertisement's node selector, and the Local policy means there is nowhere to announce from. Fixing the selector, or changing the policy to Cluster, restores service, and the incident note records that a policy and a selector interact.

## Related problems and ideas

This topic is the entry point for the next ones in the course: BGP to physical switches (T13) generalises the router side, the multi-cluster design (T11) needs addresses reachable between clusters, and Ingress or Gateway controllers (T06) usually sit behind a LoadBalancer Service whose address comes from here. The eBPF datapath (T05) affects how traffic is spread inside the cluster after it arrives. Network policy (T07) must allow traffic from the announced address to the endpoints, and for traffic that preserves the client address the policy sees the real client.

A related architectural idea is routing as a platform primitive: if the data centre routes to the host, then Pod and Service addresses can be advertised directly, which removes overlays and gives the network team full visibility. This is the logical end point of the routed design in the CNI comparison (T03), and it moves complexity from the cluster to the fabric.

## Active research

Areas of development include better integration between Kubernetes Services and external routing, in which the Service API grows fields for load-balancer class and implementation-specific configuration, an Ingress and Gateway story that avoids a second layer of balancers, graceful restart and fast convergence of speakers during upgrades, BGP with unnumbered peering for simpler configuration, and segment-routing options for traffic engineering. The plugin projects continue to expand their BGP resources, and the migration path from separate speakers to integrated ones is an open concern. Facts about the version in which a field became stable are "to verify" for the exact release in use.

## Future direction

Expect load-balancer address management to become a standard part of the platform, whether through a cluster add-on or through the CNI, with BGP and BFD as the default for production and layer-2 as the on-ramp for labs. The administrator's lasting tasks are to pick a single owner of announcements in the cluster, to write the router side with filters and multipath from the start, to choose a traffic policy deliberately, and to test failover as a drill, not as an assumption.
