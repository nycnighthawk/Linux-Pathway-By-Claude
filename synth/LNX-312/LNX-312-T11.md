# Joining clusters into one network: Cilium ClusterMesh, global services and multi-cluster policy

## Define the problem

A single Kubernetes cluster is a failure domain, a scaling boundary and an administrative boundary all at once. Organisations outgrow it for ordinary reasons: they want applications in several regions for latency and resilience, they separate production from staging with hard walls, they split clusters by team or by compliance scope, and they migrate from an old cluster to a new one without a cut-over weekend. All of these produce the same technical question. A workload in one cluster needs to call a workload in another. By default it cannot do that by name, because DNS and Services are cluster-local, it cannot do it by address, because Pod CIDRs are usually reused between clusters and not routable, and it certainly cannot be governed by one policy, because each cluster enforces its own.

There are many answers, and they live at different layers. An ordinary load balancer or an API gateway at the edge of each cluster is the simplest: cross-cluster calls go over the public or private network like calls to any external service. A service mesh can federate trust and endpoints between clusters. A multi-cluster Service API in Kubernetes can export and import Services. And a network plugin can make the clusters look like one flat network. Cilium's ClusterMesh takes the last approach: Pods in different clusters can reach each other directly by address, global Services load-balance across clusters, and identity-based policy applies across the mesh.

This slice explains how ClusterMesh works and what it requires, builds a two-cluster test environment with kind, and covers the operational questions: addressing, certificates, failure behaviour, service affinity and policy. It is an introduction at medium depth, and every version-specific number in it is a candidate for "to verify" against the documentation of the release in use.

## History and approaches

The first multi-cluster proposal in Kubernetes was federation, in which a higher-level control plane pushed copies of resources to member clusters. It was complex, brought its own API server, and was abandoned in favour of simpler tools. The community then split the problem. Workload placement across clusters became the job of GitOps tools and of placement controllers. Service discovery across clusters became the multi-cluster Services API, which defines a ServiceExport resource in the exporting cluster and a ServiceImport that appears in the importing ones, plus a shared DNS domain for the cluster set, and which Cilium supports as an integration on top of its mesh, with prerequisites and a documented configuration [src: cilium-docs 15ad27f3ae5e7bfe]. Network connectivity across clusters was left to the network plugin, the cloud, or a dedicated tool such as Submariner, which builds tunnels between clusters, and which together with ClusterMesh and the multi-cluster modes of service meshes forms the set of options.

The design that ClusterMesh chose is state replication. Each cluster runs an API server component for the mesh with its own small key-value store, and each node's agent in every other cluster connects to it, over mutual TLS, to read the state it needs: which nodes exist, which endpoints and identities exist, and which Services are global. With that state in the local agent, the datapath can treat a remote Pod as it would a local one: it can route to it, enforce policy about it, and load-balance to it. The documentation describes this architecture and its limits, including how many clusters can be connected [src: cilium-docs 2fb4eb4288d17d27].

The partial successes and failures are in the prerequisites. Mesh connectivity requires non-overlapping Pod address ranges, which is cheap to plan at cluster creation and very expensive to fix afterwards; many clusters were built with the default range and cannot join without a rebuild or an address translation layer. It requires node-to-node reachability between clusters (the nodes must be able to exchange tunnel or routed traffic on the data-plane ports), which in cloud environments means peering and security-group rules, and it requires every cluster in the mesh to use compatible datapath settings and the same certificate authority. Teams that prepared the network first had a smooth first day; teams that tried to add the mesh to clusters with overlapping ranges did not.

## Current state

**Architecture.** Each cluster has a name and a numeric identifier, both set in the configuration. The identifier is part of the numeric security identity, which is how a Pod in one cluster is distinguished from a Pod with the same labels in another, and it must be unique in the mesh. The clustermesh API server Deployment in each cluster is exposed to the others with a Service (a LoadBalancer, a NodePort, or an internal address, depending on the environment). The agents in the other clusters authenticate to it with certificates issued by a shared authority. Connections and state are one-way per pair of clusters, so a mesh of three clusters has six directed connections, and a failure in one connection affects only what that connection carries [src: cilium-docs 2fb4eb4288d17d27].

**Requirements.** The documentation lists them [src: cilium-docs 49db6c9b00f0b00d]: unique cluster names and identifiers; non-overlapping Pod CIDRs in every cluster; node IP reachability between all nodes of all clusters (with the encapsulation or routing ports allowed); the same mode of routing and encapsulation in all clusters; and a shared root of trust for the mesh certificates. Service CIDRs may overlap, because Services are translated at the source cluster. Recent versions add options for the identity range so that a mesh can hold more clusters, at the cost of a larger identity space (to verify the supported counts).

**Global Services.** A Service becomes global by annotation in each cluster in which it should participate. When the same Service name and namespace carry the global annotation in several clusters, the agents merge their endpoints, and traffic to the Service's address in any of them may be sent to a backend in any of them [src: cilium-docs 32d1d0250870e6a5]. A related annotation allows a cluster to import without exporting, which supports migration and shared-service patterns. Service affinity influences the selection: local affinity prefers backends in the same cluster and falls back to remote ones if there are none healthy; remote affinity prefers other clusters; none balances across all [src: cilium-docs 390f577bd1d91d78]. The usual production choice is local with fallback, which gives resilience without paying cross-cluster latency in the normal case.

**Policy.** Because identities include the cluster, a policy can say which clusters a peer must be in. A rule can select endpoints by their cluster label, so that production in one cluster may not receive requests from the staging cluster even if the labels of the Pods are identical. Policies are enforced in the destination cluster, which is where the rule is stored, so each cluster must carry the policies for the workloads it hosts. The default of the mesh is permissive, in that identity sharing makes remote Pods look like local ones with the same labels, which is a reason to put cluster scope in the policy of any sensitive workload.

**Multi-cluster Services API.** The standard API is supported as an alternative front end to global Services. It creates the import objects and the clusterset DNS names, and it has the advantage of being portable across implementations and the disadvantage of being newer, so that field support and status reporting depend on the version (to verify). The documentation lists prerequisites such as the CRDs installed in all clusters and the DNS configuration to answer the cluster set domain.

**Test environment with kind.** A reproducible way to learn this is to create two kind clusters on one Docker network, each with a different Pod and Service subnet in its cluster configuration, with the default CNI disabled; to install Cilium in each with its cluster name and identifier and the same CA; to enable the mesh and expose its API server through a NodePort on the Docker network; and to connect the clusters with the command-line tool. Because kind nodes share the host bridge, node-to-node reachability exists out of the box. The main trap is the Pod subnet: kind's default is the same range in every cluster, which must be overridden before creation. Load-balancing across clusters is then tested by deploying a backend with a recognisable response in both clusters, annotating it as global, and calling it from a client in one cluster, watching the responses alternate and then fail over when the local backend is scaled to zero.

**Operations.** Useful checks are the mesh status command (are all clusters connected, are the endpoints being synchronised), the per-node view of remote clusters, the flow log with cluster names, and the metrics of the mesh API servers. Certificates are the recurring operational task: they must be rotated before expiry, and a mismatch between the authorities of two clusters breaks the connection with TLS errors that must be read in the API server log. Upgrades require version compatibility between clusters, which the documentation states as a skew policy, and the safe order is to upgrade one cluster at a time and watch the mesh status between steps.

## Assessment: the good, the bad and the ugly

**The good.** Once the prerequisites are met, the mesh gives direct Pod-to-Pod connectivity without gateways, global load balancing and failover without an external balancer, and one identity-based policy language across clusters, all with the same datapath as inside a cluster. It makes migrations pleasant, since a service can run in both clusters during the move. Observability extends too, because flows show cluster names.

**The bad.** The prerequisites are unforgiving: non-overlapping addressing, node reachability, shared PKI and matched datapath modes. The model is a flat network, which makes the blast radius of a compromised cluster larger than in the gateway model, since remote agents hold replicated state and Pods can send traffic to other clusters' Pods directly. Cross-cluster latency and egress costs are invisible to applications that do not know a call crossed a region. The tool is specific to one plugin, so a mixed fleet cannot use it, and clusters must be on a compatible version.

**The ugly.** The sharpest edges are about failure modes. A partition between clusters leaves each side with stale state about the other, and the datapath keeps sending traffic to endpoints that may be gone until the connection is declared lost. A global Service with a bad endpoint in one cluster spreads failures to callers in all of them unless health checks and affinity are set carefully. An overlap in address ranges discovered after deployment is painful because the Pod CIDR cannot be changed in place. And a team that treats the mesh as a convenience for cross-cluster calls, without using policy to restrict which clusters may talk, has effectively merged the security domains of the clusters.

## Applications beyond this domain

The pattern of replicating a small amount of state to every edge, and then deciding locally, is general: it appears in anycast content networks, in distributed databases that keep metadata at every node, and in cloud virtual networks that program peering. Cross-region failover with a preference for locality is the same logic as DNS-based global load balancing and as zone-aware routing inside one cluster. In the Linux world, a mesh of clusters resembles a VPN-connected set of sites whose routing is held by the endpoints, with the difference that identities and service names are part of the routing information.

## Examples

A first example is the two-cluster kind experiment. The operator writes two cluster configuration files that differ in the Pod and Service subnets and the cluster name, creates both, installs the plugin with a name and an identifier in each, copies the shared certificate authority from the first cluster to the second, enables the mesh in both, and connects them. The status command should list both clusters as connected. Deploying a service called rebel-base in both clusters with the global annotation, and calling it repeatedly from a client in cluster one, returns answers from both clusters.

A second example is a migration. The old cluster and the new one are joined, the application's Service is marked global in both, and the new cluster's copy starts with remote affinity so that traffic goes to the old one. The team scales up the new copy, flips affinity to local on the new cluster and keeps the old as fallback, then removes the annotation from the old cluster and decommissions it. At each step the rollback is an annotation change.

A third example is a policy for a shared database service. The database lives in a data cluster and is global, but its policy allows requests only from endpoints in the production cluster, selected by cluster label, and denies the staging cluster even for identical Pod labels. A test from a staging Pod shows a policy denial in the flow log, with the source cluster name in the record.

## Related problems and ideas

ClusterMesh builds on the datapath and identity model (T05), the policy language (T07), the DNS behaviour (T08), and the addressing and routing choices of the CNI comparison (T03). External addresses for the mesh API servers need a load-balancer address (T10). The mesh competes with and complements service-mesh multi-cluster modes (T09): the network-level mesh offers connectivity and identity, the service mesh offers L7 features and its own identity federation, and some designs use both. The security course covers certificate authority design for the shared root. Finally, the physical network team will be involved, since node-to-node reachability between sites is a routing and firewall question (T13).

An architectural idea worth discussing is the choice between flat and gateway-based multi-cluster designs. Flat gives simplicity of calls and loses the isolation of a chokepoint, while gateway-based gives isolation and loses transparency. Neither is right everywhere, and large organisations often use flat inside a trust zone and gateways between zones.

## Active research

Active areas include scaling the number of clusters in a mesh, reducing the state replicated to each node by filtering, richer service affinity with latency and load awareness, stronger default isolation between clusters in the mesh, standardising the multi-cluster Services API and its status model, and integration with cluster-fleet managers so that clusters join the mesh as part of provisioning. Limits and defaults change with releases, so every figure in this slice should be treated as "to verify".

## Future direction

Expect multi-cluster connectivity to become a standard feature of cluster platforms, with the Services API as the portable interface and plugin meshes as an optimised implementation, and with identity federation making cluster scope an ordinary label in policy. The practical advice is to plan addressing for the mesh on the day a cluster is created, to share a root of trust deliberately, and to write the policy that limits which clusters may talk before the first global Service is created.
