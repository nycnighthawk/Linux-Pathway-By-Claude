# Choosing a cluster network: Flannel, Calico and Cilium side by side

## Define the problem

The CNI contract explains how one node attaches one pod. It leaves open the larger question that decides how a cluster behaves: how do pods on different nodes reach each other, how are addresses divided among nodes, how is traffic between them carried across the physical network, and who enforces rules about which pods may talk? The Kubernetes network model requires that every pod can reach every other pod by its own address without translation, but says nothing about how to achieve it. Operators must therefore choose a network plugin, and the choice affects performance, observability, security features, failure behaviour, operational skill requirements and the possibility of changing later.

Three projects dominate the open-source field and illustrate three philosophies. Flannel offers the simplest possible overlay: carry traffic between nodes in tunnels and do nothing else. Calico treats the cluster as a routed network: advertise pod addresses with BGP or program routes, and enforce policy with a rich rule engine. Cilium puts an eBPF datapath in the kernel and builds identity-based security, service load balancing and observability on it. Wrong choices show up as clusters that cannot enforce the policies compliance requires, networks that fragment large packets because the overlay's overhead was not planned, or a rebuilt cluster eighteen months in because the plugin cannot do what the business later demands.

This slice compares the three on the dimensions that matter to an administrator: addressing and IPAM, encapsulation and routing modes, policy capabilities, service handling, encryption, observability, operational complexity and ecosystem. It also names the other options and the criteria for choosing. The next slices go deeper on kube-proxy (T04), eBPF and Hubble (T05) and policy (T07).

## History and approaches

Early Kubernetes networking on a cloud used the cloud's own routes: GCE's route table could hold a route per node for its pod subnet, which is routed networking without a plugin. On bare metal or across clouds that was unavailable, and overlays appeared. Flannel, created by CoreOS in 2014, assigned each node a subnet from a cluster range, stored the allocation in the Kubernetes API or etcd, and ran a daemon on each node that wrapped pod packets in VXLAN or UDP to reach other nodes. Its sibling approach, Weave Net from Weaveworks, added encryption and a mesh, but the company wound down in 2024 and the project is no longer maintained, a lesson about relying on a single vendor. The Flannel project stayed deliberately minimal and, as the Kubernetes addons page notes among its list, it provides only an overlay network; policy needs another component such as the combination called Canal, which pairs Flannel networking with Calico policy.

Calico, started by Metaswitch and then Tigera in 2014, took the opposite starting point: treat pods as endpoints on a routed IP network. Its agent Felix programs routes and iptables rules (later also an eBPF or nftables dataplane) on each node, and BIRD distributes pod routes using BGP between nodes and, optionally, with the data-centre network. Overlays (IP-in-IP, VXLAN) are available for environments where the underlay cannot learn pod routes. Its policy model, compatible with the Kubernetes NetworkPolicy API and extended with global and ordered policies, became a de facto standard for security teams.

Cilium, started in 2015 by Isovalent engineers who were Linux kernel networking developers, was built around eBPF: programs attached to kernel hooks that process packets at the network interface or socket level. It replaced iptables for service load balancing and policy, gave workloads identities derived from labels instead of IP addresses, added L7 awareness through an Envoy proxy running as a daemon set or inside the agent, and added flow visibility through Hubble. Its documentation describes the benefit of the Envoy deployment model in terms of sharing a proxy across pods, and its quick-start guides show installation on a fresh cluster. Cilium became a CNCF project and was graduated in 2023; it is the default dataplane in several managed Kubernetes services.

Other plugins fill niches. The AWS VPC CNI gives pods real VPC addresses; Azure CNI and GKE's native dataplane do the same on their clouds. Antrea uses Open vSwitch; kube-router runs BGP and IPVS in one binary; Multus attaches additional interfaces; OVN-Kubernetes serves OpenShift. For tiny clusters, k3s ships Flannel by default; for security-driven clusters, Calico and Cilium dominate surveys of production use.

The pattern: overlay simplicity at one end, routed transparency in the middle, programmable kernel datapath at the other. Many installations move along that line over time as requirements grow.

## Current state

**Addressing.** All three give each node a pod CIDR slice. Flannel reads the node's `podCIDR` assigned by the controller manager (the `--allocate-node-cidrs` setting) or manages its own lease table. Calico has its own IP pool resources, allows several pools, per-node blocks and allocation by namespace or node selector, and can reuse addresses across IPAM modes. Cilium supports cluster-scope IPAM, Kubernetes host-scope (the node CIDR), multi-pool IPAM with multiple pools selected by workload annotations, and cloud-specific IPAM using the cloud API, as its documentation for the Azure integration shows. The CIDR given to the cluster at creation (the kubeadm pod subnet in the Arch Wiki's configuration notes) must match what the plugin expects.

**Data path between nodes.** Flannel's default backend is VXLAN, which wraps the pod's Ethernet frame in UDP on port 8472, with a host-gateway mode that installs plain routes when all nodes share a layer-2 segment and a WireGuard mode for encryption. Calico's default is IP-in-IP or VXLAN depending on the version and setup, with a pure BGP routed mode with no encapsulation when the network supports it, and cross-subnet mode that uses overlays only between subnets. Cilium's default is a tunnel (VXLAN or Geneve) with native routing as the alternative, and optionally direct routing with BGP through its own control plane. Overlays cost MTU, CPU and some throughput; routed modes preserve pod addresses on the wire, which helps firewalls and observability and lets physical routers reach pods.

**Policy.** Flannel enforces nothing. Calico implements the Kubernetes NetworkPolicy API and adds its own resources for cluster-wide, ordered, allow and deny rules with selectors on namespaces, service accounts and CIDR sets, and it can apply policy to host interfaces. Cilium implements NetworkPolicy and adds its own resources that include identity-based and DNS-name-based rules, and L7 rules for HTTP, gRPC and Kafka enforced through Envoy; it also has host policies, which the Cilium documentation describes for protecting the nodes themselves. The Kubernetes documentation on declaring a network policy reminds users that policies have effect only when the cluster's network plugin enforces them; creating a policy on a Flannel-only cluster silently does nothing.

**Services and kube-proxy.** Flannel and Calico in their default modes leave Services to kube-proxy. Calico offers an eBPF dataplane that replaces kube-proxy. Cilium can replace kube-proxy entirely, as its quick-start documentation for kube-proxy-free operation shows: the cluster is created without the kube-proxy addon, the agent is told the API server address, and Services, NodePorts and load balancers are implemented in eBPF. The HostPort issue listed in the kubeadm troubleshooting guide, where hostPort mappings do not work with some plugins, is a reminder that features such as hostPort rely on the portmap chained plugin, which not every plugin installs.

**Encryption.** Flannel can use WireGuard in its backend. Calico offers WireGuard encryption between nodes (and IPsec in some versions). Cilium offers WireGuard and IPsec transparent encryption, with IPsec key rotation described in its documentation, plus mutual authentication features. Encryption protects traffic crossing untrusted links at the price of CPU and MTU, and it protects only traffic between nodes, not between a pod and its node's other pods.

**Observability and operations.** Cilium's Hubble provides flow logs, service maps and DNS visibility, with metrics from the agent documented in its metrics reference, which also reveals the amount of internal state the agent maintains (endpoints, identities, policy maps, BPF map pressure). Calico offers flow logs and a policy-testing tool in its commercial offering and basic metrics in the open-source one, and its `calicoctl` shows state. Flannel exposes little. Operationally, Flannel is a daemon set and a config map, Calico has a few components (Felix, an IPAM controller, optionally Typha as a fan-out cache for large clusters, BIRD), and Cilium has an agent with significant kernel requirements (a recent kernel and a set of kernel configuration options), an operator and optional Hubble relay. Troubleshooting follows the plugin's own tools.

**Installation and the CRI-O or containerd side.** All three install their CNI binary and configuration through an init container, and the runtime reads the configuration directory as the CNI slice explained. The Arch Wiki notes for CRI-O show where its network directory sits and the importance of deploying only one plugin's configuration. Quick-start guides for Cilium create a cluster (kind or managed) and install with the Cilium command-line tool or Helm; Calico and Flannel install from manifests or operators.

## Assessment: the good, the bad and the ugly

The good: Flannel is the easiest network to install and reason about, with almost nothing to go wrong; it is a sound choice for small, trusted clusters and learning. Calico's routed model is transparent, performs well, integrates with data-centre networks and has the most mature policy model. Cilium offers the richest set of features in one stack: service load balancing without kube-proxy, identity-based and L7 policy, encryption, multi-cluster connectivity and deep observability.

The bad: each has costs. Flannel lacks policy, observability and advanced features, so growing teams outgrow it and migration means rebuilding or a risky network switch. Calico's BGP and IP pools need networking knowledge, its multiple dataplanes create confusion about which features apply to which, and some advanced features are in the commercial edition. Cilium has the steepest learning curve and the highest demands: kernel versions, eBPF map sizing, many configuration options, and debugging that requires understanding eBPF concepts; bugs in the datapath are harder to inspect with standard tools. All overlays impose MTU management.

The ugly: switching the CNI of a running cluster is dangerous. Pods keep old interfaces and addresses; two plugins' configurations conflict; policies exist in one dialect and not in the other. Most migrations are done by building a new cluster, or by a careful node-by-node procedure with both plugins running side by side, which Cilium and Calico document. Another ugly truth is feature confusion: documentation of one dataplane mode is applied to another, a policy written in Cilium's dialect is applied to a Calico cluster and ignored, a "compatible" kube-proxy mode conflicts with the plugin's replacement. And vendor concentration risk exists, as the Weave Net example shows.

Mitigations: decide policy requirements first and pick a plugin that enforces them; test on a staging cluster with the actual kernel and cloud; plan the MTU; read the compatibility matrix with your Kubernetes version (Cilium's documents its supported ranges); pin versions; keep a runbook for the plugin's diagnostic tools; avoid changing the CNI in place.

## Applications beyond this domain

The three designs are three general ways to build virtual networks. Overlays (VXLAN, Geneve, GRE) are used by data-centre network virtualisation, VMware NSX, OpenStack Neutron and OVN, whose architecture manual describes logical switches and routers on top of tunnels. Routed designs with BGP to hosts are the pattern of large web-scale data centres that eliminated layer-2 spanning domains. Programmable kernel datapaths are used in load balancers (Katran, Cloudflare's systems), DDoS mitigation and observability tools such as Pixie and Tetragon. The identity-based policy idea mirrors zero-trust networking, where policy refers to workload identity and not to addresses. Virtual-machine platforms such as KubeVirt rely on whatever the pod network gives them and add their own binding options on top.

## Examples

A small team building a three-node learning cluster picks Flannel with VXLAN, installs one manifest and gets working pod networking in a minute. When a security requirement arrives for namespace isolation, they discover that NetworkPolicy objects have no effect and must add Calico in policy-only mode (Canal) or rebuild.

A data-centre cluster with a BGP-capable top-of-rack fabric chooses Calico in routed mode: each node peers with its switch, pod subnets are advertised, pods are reachable from the rest of the network without NAT, and policy uses ordered global rules to enforce a default deny. Troubleshooting uses `calicoctl node status` to check BGP sessions.

A platform team that needs service load balancing without kube-proxy, L7 policy, encryption and flow visibility builds clusters with Cilium: the cluster is created with kube-proxy skipped, Cilium is installed with the replacement enabled and Hubble on, and operators use `cilium status` and `hubble observe` to see traffic and drops.

A failing example: a team applies a NetworkPolicy denying all ingress to a namespace on a cluster with Flannel. Everything still works, so the team assumes it is secure, and passes an audit based on the manifest. A test with a probe pod would have shown the truth.

Another failing example: a team enables Cilium's kube-proxy replacement on a cluster that still runs kube-proxy. Both implement Service rules and conflicting behaviour appears in NodePort handling. The fix is to remove the kube-proxy daemon set and clean its rules.

## Related problems and ideas

Multi-network pods through Multus, multi-cluster connectivity (ClusterMesh, Submariner), service meshes with sidecar-free ambient data planes (T09), host networking for latency-critical workloads, SR-IOV and DPDK for line-rate packet processing, and Kubernetes-level changes such as the dual-stack API and the planned multi-network work all relate. Alternatives to the plugin per cluster include provider-native networks that give pods real VPC addresses with the limits of the cloud's address space. Ideas not mainstream include network-as-a-resource APIs in the Kubernetes core and a standard interface for policy across plugins, which Gateway API and the policy-assistant efforts pursue only in part.

## Active research

The projects work on faster datapaths (netkit devices, host-routing without netfilter, XDP load balancing), nftables dataplanes replacing iptables in Calico and kube-proxy, scalable identity management for tens of thousands of endpoints, sidecar-free service mesh features in the CNI, encryption without per-packet CPU cost, and policy models for admin and tenant roles (the AdminNetworkPolicy API from the network policy working group). Comparative studies of throughput and latency across plugins appear regularly, though results depend on kernel version, hardware and tuning, and vendor benchmarks should be treated with caution.

## Future direction

Expect convergence on eBPF or nftables dataplanes, cluster-scoped administrative policy resources in the Kubernetes API, and easier migration tooling. Managed services will continue to default to cloud-integrated or Cilium-based dataplanes. For an administrator the decision framework is stable: list required capabilities (policy, encryption, observability, kube-proxy replacement, BGP integration, multi-cluster), check kernel and platform constraints, pilot two candidates on a staging cluster, and plan for the fact that the choice is expensive to change (to verify current versions and feature status on each project's documentation).
