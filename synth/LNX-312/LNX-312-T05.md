# Moving the cluster datapath into the kernel with eBPF, and watching it with Hubble

## Define the problem

The previous slice showed that a Service in a default cluster is a pile of netfilter rules written by kube-proxy. That design works, but it has three costs that grow with the cluster. First, rule evaluation is sequential in the iptables mode, so every new Service lengthens the path of every connection and makes each update slower. Second, every packet passes through the full netfilter stack and connection tracking, even when the destination is a Pod on the same node. Third, the rules say nothing about which workload sent a packet, so both policy and troubleshooting are reduced to IP addresses that change whenever a Pod is rescheduled.

The eBPF approach attacks all three at once. Small verified programs are attached to hooks inside the kernel: the traffic-control layer of a network device, the earliest receive point of a driver (XDP), and the cgroup socket hooks that fire when a process calls connect or sendmsg. Maps shared with the user-space agent hold the Service table, the endpoint table and the policy verdicts, and a lookup in them takes about the same time whether there are ten Services or ten thousand. The programs can rewrite packets, redirect them to another interface without traversing the rest of the stack, and emit events that a user-space observer reads.

This slice answers four questions for an administrator. What exactly does it mean to replace kube-proxy with an eBPF datapath, and what has to be true of the kernel and the nodes? Which load-balancing features does it add (socket-level translation, direct server return, Maglev hashing, XDP acceleration), and what do they cost? How does the Hubble observability layer see the flows, and what can it answer that tcpdump cannot? And how do you diagnose a cluster in which the replacement is half-working? The treatment follows the Cilium implementation because it is the one with a complete public specification of this design, and it notes where Calico's eBPF mode makes different choices.

## History and approaches

The classic Berkeley Packet Filter was a small interpreter for tcpdump-style filters. The extended form added by the kernel community from 2014 onward has registers, maps and helper functions, and a verifier that proves a program terminates and touches only memory it is allowed to touch. The list of what a program may call is the helper-function set documented in the bpf-helpers manual page [src: man-pages 22627299cf6f6695], and the growth of that list is the real history: each release added a capability such as redirecting a packet to another device, reading a socket cookie or looking up a conntrack entry, and each one made a new kind of network function possible without a new kernel module.

Early cloud-native uses were observability and security tools that wanted a safe way into the kernel. The first networking attempts kept the iptables structure and merely accelerated parts of it. Cilium's early releases used eBPF for policy and for the pod-to-pod path while still relying on kube-proxy for Services. The decisive step was moving Service translation to the socket layer: instead of rewriting each packet after it leaves the process, the program attached to the connect call rewrites the destination address once, before the connection exists, so the packets that follow already carry the backend address and need no per-packet translation or reverse translation on the node. That idea, and the observation that the Service table could then be a hash map, gave the project its claim of a kube-proxy-free cluster.

Other approaches coexist. Calico added an eBPF dataplane as an alternative to its iptables one, with its own Service handling and the same goal of dropping kube-proxy. The Kubernetes project itself pursued a different cure for the same disease: the nftables mode of kube-proxy keeps the userspace agent but replaces long linear chains with set and map lookups, and the project discussed a new backend with a modest dependency footprint. Some environments solve the problem outside the cluster, with a cloud load balancer that sends traffic straight to Pod addresses. And service meshes treat the Service abstraction as just a name that their proxies resolve. The choice among these is a question of how much of the stack the operators want to own, which is exactly the trade-off the assessment section returns to.

Failures shaped the current design. Early eBPF datapaths hit kernel-version cliffs: a feature worked on one distribution's kernel and silently fell back on another, leaving clusters in a mixed state that was hard to reason about. Documentation grew explicit prerequisite tables and the agent grew start-up probes that refuse to enable a feature the kernel cannot support. Another partial success was external reachability: replacing kube-proxy at first covered cluster-internal Services, while NodePort and LoadBalancer addresses and host-network clients needed a second round of work, and source-address preservation for external traffic required new mechanisms that are covered below.

## Current state

**What replacement means.** With the kube-proxy replacement enabled, the agent on each node watches Services and EndpointSlices from the API and writes them into eBPF maps. It then attaches programs at three places [src: cilium-docs 41d4add1b34d956e]. The socket hooks handle traffic that originates inside the node's cgroups, including Pods and host processes, by translating the Service address at connect time. The traffic-control hooks on the external device handle traffic that arrives from outside for a NodePort, external IP or load-balancer address. And an optional XDP program on the external device handles the same traffic even earlier, before the kernel allocates a socket buffer. The kube-proxy DaemonSet must not run alongside this, which is why installation guidance says to skip it at cluster creation (kubeadm has a phase-skip option) or to delete it and clear its rules when migrating.

A subtle but important requirement is how the agent reaches the API server. Without kube-proxy there is no Service address for the API server at the moment the agent starts, so the agent is told the real address and port of the API server (or a stable load-balanced endpoint) through its configuration, normally the two Helm values named for the Kubernetes service host and service port. Forgetting them is the most common reason a freshly migrated cluster never becomes ready.

**Features.** The load-balancing mode can be SNAT, where the node rewrites the source so the reply returns through it, or DSR (direct server return), where the backend replies straight to the client and the node only forwards the request [src: cilium-docs 41d4add1b34d956e]. DSR avoids a hop for large responses but needs the backend's node to understand the dispatch metadata, which is carried in an IP option or an encapsulation header, so it interacts with MTU and with cloud networks that drop packets with options. The backend-selection algorithm can be a random pick or Maglev consistent hashing, which keeps most flows on the same backend when the backend set changes and is therefore preferred when several nodes load-balance the same external VIP. Client source-address preservation depends on the external traffic policy of the Service: with the Local policy the node delivers only to its own Pods and no SNAT is needed [src: cilium-docs 9f3813a2556d25cf]. Graceful termination is supported, so that connections to a terminating backend are allowed to finish while new ones go elsewhere [src: cilium-docs 41d4add1b34d956e]. Session affinity, topology-aware routing and the Service traffic distribution field are supported with differences by version that the compatibility tables record, and anything not listed there should be marked "to verify" before a design relies on it.

**Host routing and masquerading.** The faster path is not only about Services. When the BPF host-routing option is on, a packet leaving a Pod is redirected from the Pod's veth straight to the external device or to the destination Pod's veth without crossing the host's netfilter stack. Masquerading for traffic that leaves the cluster can also be done in eBPF, so the iptables chain that kube-proxy and the CNI would otherwise provide is not needed. Combined with native routing mode (no tunnel), this is the high-performance configuration, and it is also the one with the most prerequisites: recent kernel, a routable underlay for Pod addresses, and no other component that insists on iptables.

**Kernel prerequisites.** The documentation lists minimum kernel versions per feature, and the newer features need recent long-term kernels. Treat the table in the documentation for your exact version as authoritative, not any figure in this course (to verify for every release). The practical rule is that the full replacement with host routing, bandwidth management and XDP acceleration wants a kernel from roughly the last two LTS lines, which excludes some enterprise distributions' older kernels unless the vendor backports the features.

**Hubble.** Hubble is the observability layer built on the same datapath [src: cilium-docs 41d4add1b34d956e]. Each agent's datapath emits flow events (a verdict, the source and destination identities, the L4 ports, and when L7 visibility is on, parsed HTTP, DNS or Kafka records) into a perf ring. The agent exposes them over a gRPC API on the node. The relay component aggregates the per-node streams into a cluster-wide API, the command-line client queries it (filtering by namespace, Pod, verdict, protocol or identity) and the UI draws a service map from the same data. Metrics for flows, drops, DNS and HTTP can be exported to Prometheus. Because the flow carries identities, not just addresses, a dropped packet shows frontend to backend, with the policy as the reason, which is the answer an administrator wants, instead of two Pod IPs that no longer exist.

**Troubleshooting commands.** The agent's status command reports which features are active and whether the replacement is in strict mode. The service list command prints the translation table as the datapath sees it, and the BPF load-balancer list shows the raw map content. The troubleshooting section of the documentation [src: cilium-docs 204aa715fcced770] recommends comparing the Service seen by the API with the Service seen in the datapath, then testing from inside a Pod and from the host separately, because the socket hooks only fire for processes in the right cgroup and a test run from an unusual shell can bypass them.

## Assessment: the good, the bad and the ugly

**The good.** Lookup cost no longer grows with the number of Services, so large clusters see faster Service updates and less CPU in the kernel. Socket-level translation removes the per-packet NAT for in-cluster traffic and with it a class of conntrack-table pressure problems. DSR and Maglev give external load-balancing features that previously needed an external appliance or a separate load-balancer project. Identity-aware flow records collapse the debugging loop for policy issues from a capture, a correlation of addresses and a hunt for the right Pod to one query. And, importantly for security teams, one component both enforces and records policy, so the record and the enforcement cannot disagree.

**The bad.** The prerequisites are real. Kernel age excludes some fleets, and features silently absent on one kernel make otherwise identical clusters behave differently. The datapath is harder to inspect with the tools every Linux administrator already has: iptables-save shows nothing, tcpdump on the node shows the packets before or after translation depending on where it is attached, and the real state lives in maps that need the project's own tools to read. Failures in the verifier or a program load at upgrade time can leave a node in a degraded state that is not a Kubernetes-level error. The set of applications that expect netfilter hooks, such as host firewalls that assume iptables, certain intrusion tools and some legacy network-policy engines, may conflict with a datapath that bypasses netfilter.

**The ugly.** The sharpest trap is a half-migrated cluster: kube-proxy removed but the agent not given a reachable API address, or the agent enabled for replacement while old kube-proxy rules still exist on the nodes and capture some traffic first, so the same Service works from some Pods and not from others. Two controllers each believing they own Service translation is the cluster-networking equivalent of two DHCP servers. The second sharp edge is observability cost: full L7 visibility starts a proxy for the affected traffic, which adds latency and memory, and enabling it cluster-wide "to see everything" is a classic way to turn a diagnostic aid into an outage. The third is trust: the flow log is sensitive data (it reveals the communication graph of the whole cluster), so access to the relay needs the same care as access to the API server.

## Applications beyond this domain

The same machinery is used well beyond Kubernetes networking. Stateless L4 load balancers at large internet companies run XDP programs that hash flows to backends and forward them with encapsulation, which is the same family as Cilium's DSR and Maglev. DDoS filtering at the edge drops attack traffic at the driver, before the kernel spends memory on it. Runtime-security tools hook system calls and process events to enforce and report on behaviour, and performance tools use the same program types to profile production systems with low overhead. Even outside networking, the idea of a verified extension loaded into a running kernel has been adopted for schedulers and storage paths. For a Linux administrator, the practical outcome is that learning to read a map and a verifier error pays off in contexts far from container networking.

## Examples

Consider a migration of a kubeadm cluster to the replacement mode. The plan has five steps. First, confirm kernel versions on every node against the feature table and decide the mode: tunnel with SNAT is the most compatible, native routing with DSR the fastest. Second, record the API server's real address. Third, install the agent with replacement enabled and the API address set, while kube-proxy is still present, in a mode in which the agent coexists (the project documents a transitional setting). Fourth, verify from a Pod and from a host process that Service addresses translate through the datapath, and remove the kube-proxy DaemonSet. Fifth, flush the leftover rules on each node or reboot. Rollback is the reverse order, and since the mixed state is the dangerous one, the schedule should allow each stage to run for a full day before proceeding.

A second example is a debugging session with Hubble. A frontend intermittently gets timeouts calling a backend. The administrator filters flows by the two workloads and sees a mix of forwarded and dropped verdicts. The dropped ones carry a reason: policy denied for the new version of the frontend, whose labels differ from the old and are not covered by the backend's ingress rule. The fix is a label correction, and the same query confirms it by showing only forwarded verdicts afterwards. Without identity-aware flows, the same investigation involves reading a policy, listing Pod IPs and inferring which ones belong to which version.

## Related problems and ideas

Three neighbouring topics deserve cross-reference. NetworkPolicy semantics (T07) are implemented in the same maps, so what an identity can reach is a map lookup at the datapath. The nftables mode of kube-proxy in the previous slice is the competing in-tree answer to the scalability problem, and a fair comparison weighs its simplicity and stock tooling against the eBPF mode's performance. Service meshes (T09) overlap with the L7 capabilities, and the sidecar-free mode of several meshes relies on the same kernel facilities. Finally, bandwidth management and the Pod egress rate limiting implemented with an earliest-departure-time model sit in the same programs and are worth learning in the same breath.

A broader idea is the debugging cost of programmable kernels. The more logic lives in a map, the more the operator depends on the vendor's inspection tools, and the less a general Linux skill set transfers. Teams that adopt this datapath should treat the vendor's debugging commands, and the practice of capturing a sysdump before opening an issue, as part of the production runbook.

## Active research

Current work includes the netkit device type, which replaces the veth pair with a device whose driver can run the program directly and so shortens the Pod-to-host path; host-routing options that skip netfilter entirely; hardware offload of XDP programs to smart NICs; scalable policy for clusters with hundreds of thousands of identities; and better verifier ergonomics (larger program limits, loops with bounds, and kernel functions callable from programs). On the observability side, work targets cheaper L7 parsing, correlation of flow logs with traces, and standards for exporting flows. Some of the details move by release, so check the project roadmap and mark as "to verify" any statement about the version in which a feature became stable.

## Future direction

Expect the in-kernel datapath to keep absorbing functions that are now separate: load balancing, policy, bandwidth management and encryption in one set of programs, with the in-tree nftables mode as the conservative alternative for clusters that value stock tooling. For administrators the durable skills are the ability to read the prerequisite tables, to test from the right cgroup, to use the flow log as a first-class diagnostic and to plan migrations that never leave two controllers in charge of the same Service at the same time.
