# Controlling who may talk to whom: NetworkPolicy, cluster-scoped policy and Cilium L7 rules

## Define the problem

A fresh Kubernetes cluster is flat and open. Every Pod can open a connection to every other Pod and to every Service, in every namespace, and nothing in the base system says otherwise. For a single team's test cluster that is a convenience. For a shared production cluster it means that the compromise of one web front end gives an attacker a route to the database of an unrelated application, to the metadata service of the cloud, and to the internal admin interfaces of the platform itself. Perimeter firewalls do not help, because the traffic never leaves the cluster's overlay.

The security community's answer is micro-segmentation: declare, per workload, which peers may connect, and drop everything else at the node where the workload runs. Kubernetes provides the declaration format in the NetworkPolicy resource, but, deliberately, no enforcement. A cluster without a network plugin that implements the API accepts policy objects and ignores them, which is a quiet and dangerous failure. Beyond the standard API, plugins add richer languages: cluster-wide rules, explicit deny, selection by DNS name, and inspection of HTTP, gRPC, Kafka and DNS requests at layer 7.

This slice teaches the semantics of the standard policy precisely, because most mistakes come from misreading how rules combine, then moves to the cluster-scoped policy API that the SIG-Network community is building, then to the Cilium policy language. The goals are practical: write a default-deny baseline with the required exceptions, express an application's flows with the least privilege that works, test policy before and after applying it, and know which of three layers (standard, cluster-wide, vendor-specific) a requirement belongs to.

## History and approaches

Kubernetes introduced NetworkPolicy as a beta API early in its life, and it went to GA as networking.k8s.io/v1 in 1.7. From the beginning the design was intentionally minimal and additive. A policy selects a set of Pods in its own namespace. If any policy selects a Pod for a given direction, that Pod becomes isolated for the direction, and only traffic matched by some rule of some selecting policy is allowed. There is no ordering, no priority and no way to write a deny. That simplicity made the API easy to implement across plugins but hard to use for the cases an enterprise security team cares about, such as forcing all internet access through a proxy or letting platform monitoring always scrape every Pod.

Plugins responded in three ways. Calico, which had its own policy engine before the API existed, added global policy objects with ordering and explicit actions. Cilium added identity-based rules and, with an Envoy proxy in the datapath, rules for application protocols. Other projects (Antrea, OVN-Kubernetes, cloud-vendor plugins) added their own cluster-scoped objects. The result was powerful and entirely non-portable, so the community started the Network Policy API sub-project: first with AdminNetworkPolicy and BaselineAdminNetworkPolicy, which give cluster administrators rules that evaluate before or after the namespace-owned policies, with Allow, Deny and Pass actions, and later reorganised under a ClusterNetworkPolicy naming with tiers. The Cilium documentation already describes support for the tiered form and states the exact version dependencies [src: cilium-docs c32c8634fde5ef2d], and the status of the API (still alpha in some releases) should be marked "to verify" in any design document.

A longer history exists on the host side. Early cluster hardening relied on host firewalls and cloud security groups, which see node addresses, not Pod identities. The move from addresses to identities is the main intellectual shift: in Cilium, the identity is derived from the Pod's labels, so that a rule written for a label set stays true as Pods come and go, and the datapath compares numeric identities, not growing lists of addresses [src: cilium-docs ac28d4d9936660d9]. Calico reaches a similar effect by computing sets of addresses from selectors and programming them into ipsets.

Failures have been frequent enough to be part of the lore. Clusters that applied a deny-all egress policy and lost DNS, so that every application failed in a way that looked like an outage of the application. Clusters that wrote a rule with a namespace selector and a Pod selector as two list items, meaning an OR, when they meant an AND, and so opened the policy to every Pod in the selected namespace. Clusters that assumed Flannel enforced policy. And clusters in which health checks from the kubelet were blocked because the policy author forgot that the node itself is a traffic source.

## Current state

**The standard API.** A NetworkPolicy has a podSelector (empty means all Pods in the namespace), policyTypes (Ingress, Egress, or both), and lists of ingress and egress rules. An ingress rule has a from list of peers and a ports list; an egress rule has a to list and a ports list. A peer is one of a podSelector (in the policy's namespace), a namespaceSelector (every Pod in the matching namespaces), both together in the same list element (the Pods that match the pod selector inside the matching namespaces), or an ipBlock with a CIDR and exceptions. Ports have a protocol, a port number or name and, in recent versions, an endPort to express a range. The documentation's walk-through of declaring a policy shows the behaviour in practice [src: kubernetes-docs 85bdaa81416e823a].

**Combination rules.** Three rules explain nearly all behaviour. One: policies are additive and have no order. Two: a Pod is isolated for a direction as soon as one policy selects it with that policy type; before that it is open. Three: within a single from or to element the selectors are combined with AND, while separate elements are alternatives with OR. The idiom for a default-deny baseline is a policy that selects all Pods and lists the types with no rules. The idiom for the classic mistake is a stray dash in front of the second selector.

**What the standard API cannot express.** It cannot deny a specific peer, cannot express a priority, has no cluster-scope version, cannot match traffic to a DNS name or a Service, has no logging, and says nothing about L7. It also leaves a few semantic corners to the implementation: traffic from or to a Pod using the host network, traffic to the node's own address, and how to treat a source address rewritten by a Service. Anything that depends on these is "to verify" per plugin.

**Cluster-wide policy.** The administrator-oriented API places a cluster-scoped object ahead of namespace policy (for guardrails that developers must not override) and another behind it (for defaults that developers may override). Actions are Allow, Deny and Pass, the last of which hands the decision down to the next tier. Implementations may support only some of the fields, and the conformance profile defines which are core.

**Cilium policy language.** The CiliumNetworkPolicy resource and its cluster-wide twin use an endpointSelector for the Pods it protects and ingress, egress, ingressDeny and egressDeny rule lists [src: cilium-docs 1bcb71d55a8d41c5]. Peers can be selected by endpoints (labels), by entities (world, cluster, host, remote node, kube-apiserver), by CIDR, by Service, and by fully qualified DNS name or pattern for egress (the agent watches DNS answers and programs the returned addresses). Deny rules take precedence over allow rules. As in the standard API, a Pod is open until some rule selects it for a direction; after that it is default-deny for that direction. Policy audit mode records what would be dropped without dropping it, which is the safe way to roll out. Policies apply within the scope their selectors define; one of the documented pitfalls is that namespaced policy only affects endpoints in its own namespace even when the selector would match elsewhere [src: cilium-docs f0c6c1efc057b594].

**Layer 7 rules.** A port rule can carry an L7 section. When it does, the datapath redirects the matching traffic to the Envoy proxy in the agent, which parses the protocol and applies the rule: for HTTP, methods, path regular expressions, hosts and headers; for DNS, names and patterns; for Kafka, API keys and topics (support varies by version, to verify). The consequence is a policy that lets the frontend issue only GET requests below one path prefix of the backend and nothing more. The cost is that every matching connection traverses a proxy, so the rules are best scoped to the few flows that need them, and TLS traffic needs either termination at the proxy or inspection by other means, since the proxy cannot parse what it cannot decrypt.

**Host policy.** The same language can protect the nodes themselves: a clusterwide policy with a node selector controls access to node ports such as SSH, the kubelet and etcd, replacing the host firewall for these purposes [src: cilium-docs 56455137e60a8c7a]. It is powerful and risky: a policy that blocks the API server's path to the kubelet cuts off exec and logs.

**Testing.** Verification options form a ladder. A client Pod with curl and a server Pod give a black-box test for each intended flow and each forbidden flow. Hubble or the plugin's own flow logs show verdicts and reasons. Policy simulators and visual editors check a policy set offline. And in CI, a policy set can be exercised in an ephemeral cluster with a script that asserts the allowed and denied flows from a table.

## Assessment: the good, the bad and the ugly

**The good.** The standard API is portable, namespaced, and fits GitOps: policy lives beside the application manifests and travels with the namespace. Default-deny plus explicit allows gives a defensible security posture and a readable inventory of an application's dependencies. Identity-based enforcement removes the address churn problem. Cluster-wide tiers let platform teams set rules developers cannot override. L7 rules let a team limit a compromised client to the paths it legitimately uses, which blocks a whole class of lateral movement that L4 rules cannot.

**The bad.** The additive-only model makes some natural requirements awkward or impossible without extensions. The lack of logging in the standard API means a drop is invisible unless the plugin adds observability. Policies that mention both namespaces and Pods can be hard to review, and the AND/OR distinction is easy to misread. Writing complete policy for a large application by hand is slow, which tempts teams to leave namespaces open "for now". L7 policy introduces proxy cost and a dependency on the proxy's protocol support. Cross-plugin portability beyond the standard API is, today, minimal.

**The ugly.** The worst outcome is false confidence. A cluster whose plugin does not enforce policy, a policy whose selector matches nothing because a label was misspelt, a namespace policy applied to the wrong namespace, or a default-deny added only for ingress while egress remains open all produce clean-looking manifests and no protection. Another ugly case is the control-plane lockout: egress default-deny without an allowance for DNS, for the API server, or for the metrics path breaks things far from where the policy was applied, and ingress default-deny without the kubelet's probes marks healthy Pods as failed. A third is policy drift: policy added in the cluster by hand and never committed, so a rebuild comes up open.

## Applications beyond this domain

Micro-segmentation is a generic security idea that predates containers, and Kubernetes policy resembles host firewalls, cloud security groups and software-defined networking rules in data centres. The compliance frameworks that require boundary protection and information-flow control map to these rules: NIST SP 800-53's boundary protection control, for example, is the family under which default-deny network flows and managed interfaces are assessed [src: nist-sp800-53 43d5a9ca5c11ace1]. The identity-based approach also feeds into zero-trust architectures, in which the allow decision follows workload identity instead of network location, and into service meshes, where mutual TLS and authorisation policies serve the same purpose at the application layer.

## Examples

A first example is the standard baseline for a namespace named shop. Policy one selects all Pods and lists both types with no rules, which isolates everything. Policy two allows ingress to the web Pods from the ingress controller's namespace on port 8080. Policy three allows the web Pods to reach the API Pods on its port, and policy four allows the API Pods to reach the database Pods on 5432. Policy five allows all Pods to egress to the cluster DNS Pods in the system namespace on port 53 for both UDP and TCP. A test client run from each side confirms the allowed flows and the denied ones.

A second example is the AND/OR error. The author wants only the monitoring Pods of the monitoring namespace to scrape metrics. The first version of the policy lists a namespace selector and a Pod selector as two separate items, so any Pod in the monitoring namespace and any Pod with the monitoring label in the shop namespace may connect. The corrected version puts both selectors in one item. The difference is a single character at the start of a line.

A third example is an L7 rule. The backend exposes a read API and an admin API on one port. A CiliumNetworkPolicy allows the frontend identity to send GET requests to paths under the public prefix, and a second rule allows the batch identity to send POST requests to one import path. Everything else to that port is dropped at the proxy with an HTTP 403 for matching connections, and the flow log records the denied request with the method and path, which is how the team discovers a legitimate call they forgot.

A fourth example is a rollout in audit mode. The team enables audit mode on the namespace, applies the policy set, watches the flow log for would-be drops during a full business cycle, fixes each legitimate flow, and only then switches to enforcement. Rollback means switching the mode back, so the risk of the change is bounded.

## Related problems and ideas

Policy connects to nearly every other topic in the course. The datapath that enforces it is the subject of the eBPF slice (T05). DNS is the first thing a deny-all egress policy breaks, which links to the CoreDNS slice (T08). Mesh authorisation policies (T09) express the same intent at L7 using workload identities from certificates. Pod security settings (security course) limit what a compromised container can do on the node, and policy limits what it can reach, so the two layers are complementary. Finally, multi-cluster policy (T11) raises the question of how identity is shared across clusters.

A recurring design question is where to put the rule: in the application's namespace (owned by the team), in a cluster-wide guardrail (owned by the platform) or in the mesh. A workable convention is that guardrails and defaults are cluster-wide, application flows are namespace policy, and per-request authorisation is a mesh or application concern.

## Active research

The Network Policy API group continues to work on tiered cluster policy, on named references to Services and FQDNs, on logging fields that every implementation would share, and on a path towards a stable API. Plugin projects work on policy generation from observed traffic, on policy verification with static analysis (to answer "can A reach B" without sending packets), on handling of node and host-network traffic, and on policy for egress through gateways. Research on L7 identity is moving towards using workload certificates in policy, so that rules mention a cryptographic identity and not a label.

## Future direction

The probable end state is a stable cluster-scoped API with tiers, implemented by every major plugin, with the namespace API retained as the developer-facing layer, and L7 handled by meshes and proxies with identities shared between layers. For the administrator the stable practices are to start from default-deny with explicit exceptions, to roll out in audit mode, to test every allowed and denied flow in CI, and to review policy for the AND/OR and DNS traps before it reaches a cluster.
