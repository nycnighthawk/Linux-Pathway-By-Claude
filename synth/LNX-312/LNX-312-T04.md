# kube-proxy modes and Service types: turning a stable name into a moving set of Pods

## Define the problem

Pods in Kubernetes are disposable. They get a fresh IP each time they are rescheduled, they scale up and down, and
at any instant some of them are failing readiness checks. Clients, on the other hand, want one address that keeps
working. A **Service** is the contract that provides that address. The cluster still needs a data-plane mechanism
on every node that, for each packet aimed at the Service, picks a healthy backend, rewrites the destination, and
makes sure the reply comes back through the same translation.

That mechanism must:

- follow EndpointSlice changes within seconds, even when a cluster defines many thousands of Services;
- work for traffic that starts inside a Pod, on the node itself, or outside the cluster;
- respect policy such as session affinity, `externalTrafficPolicy: Local` (keep the client source IP, skip
  extra hops) and topology-aware routing;
- avoid adding measurable latency per packet, and avoid control-plane updates that freeze the node.

This slice covers the node-local translation (kube-proxy and its three Linux back ends) and the Service types
that sit on top of it: `ClusterIP`, `NodePort`, `LoadBalancer`, `ExternalName` and headless Services. CNI pod
routing, Ingress and Gateway API, and NetworkPolicy are separate topics, although they meet here.

## History and approaches

**Userspace proxy (2014–2015).** The first kube-proxy accepted connections in its own process and copied bytes to
a chosen backend. It was simple to reason about and could retry a failed backend, but every byte crossed into user
space twice, so throughput and latency suffered. It solved only the "stable address" part of the problem.

**iptables mode (default from 1.2).** kube-proxy stopped carrying traffic and became a controller that programs the
kernel. For each Service it writes NAT chains (`KUBE-SERVICES` → `KUBE-SVC-*` → `KUBE-SEP-*`). Backends are chosen
by a cascade of `statistic --mode random` matches, and conntrack keeps a flow pinned to its backend. Packets never
leave the kernel. Two structural costs appeared as clusters grew:

- rule matching for the first packet of a flow is linear in the number of Services, because iptables walks a list;
- updates were originally whole-table rewrites through `iptables-restore`, so a big cluster could spend seconds
  holding the xtables lock, during which other tools on the node stalled.

Later releases added partial syncs and minimum-sync intervals, which softened but did not remove the problem.

**IPVS mode (GA in 1.11).** To fix lookup scaling, kube-proxy programmed the kernel's IP Virtual Server load
balancer. IPVS keeps a hash table of virtual services and supports several schedulers (round robin, least
connections, source hashing). Lookups became constant-time and updates incremental. The catch was that IPVS still
needed iptables (through ipsets) for masquerading, NodePort handling and other edge cases, so administrators now
had two kernel subsystems to understand. Its behaviour also diverged from iptables mode in subtle ways, and SIG
Network found it hard to keep the two equivalent.

**eBPF replacements (2019 onwards).** CNI projects such as Cilium went further and removed kube-proxy entirely.
They attach BPF programs at the socket layer (rewriting `connect()` for in-cluster clients, so there is no
per-packet NAT at all) and at tc or XDP for traffic from outside, keeping Service tables in BPF maps. The catalog's
Cilium material shows a kubeadm install that skips the kube-proxy add-on and then validates that the agent has
taken over NodePort, LoadBalancer and externalIP handling.

**nftables mode (alpha 1.29, GA 1.33).** The upstream answer to iptables' limits without a CNI dependency.
nftables offers native sets and verdict maps, so a single lookup keyed on destination address, protocol and port
jumps straight to the Service's chain. Changes are applied as atomic, incremental transactions instead of
rewriting a whole table. It also aligns with distributions (RHEL among them) that have deprecated the legacy
iptables back end.

**Pattern across the eras.** Every step moved work either down (user space → netfilter → hash tables or BPF maps)
or towards diffs (full rewrite → partial sync → transactions). The data structure that holds the Service table
matters more than the translation itself.

## Current state

**Service types as layers.** It helps to think of the types as wrappers around each other rather than as
alternatives:

| Type | What it adds | Who implements it |
|---|---|---|
| `ClusterIP` | A virtual IP reachable inside the cluster; the base for all others | kube-proxy (or eBPF replacement) on each node |
| `NodePort` | The same backends exposed on a port (default range 30000–32767) of every node | kube-proxy, plus host firewall rules |
| `LoadBalancer` | An external load balancer that targets the NodePorts or the Pods directly | Cloud controller, MetalLB, or the CNI's LB-IPAM |
| `ExternalName` | A DNS CNAME only; no proxying | CoreDNS |
| Headless (`clusterIP: None`) | DNS returns Pod IPs directly; no virtual IP | CoreDNS; clients balance themselves |

**What each kube-proxy mode does for one packet.**

- *iptables*: the first packet of a new flow traverses `PREROUTING` or `OUTPUT` into `KUBE-SERVICES`, matches the
  Service's virtual IP and port, randomly picks a `KUBE-SEP` chain, and gets DNAT to a Pod IP. Conntrack handles
  every later packet of the flow and the reverse NAT for replies.
- *IPVS*: a dummy interface (`kube-ipvs0`) holds every virtual IP, so the kernel accepts the packet locally. IPVS
  picks a real server using its scheduler, while ipset-backed iptables rules handle masquerade and NodePorts.
- *nftables*: one `kube-proxy` table holds verdict maps from (IP, protocol, port) to per-Service chains, and
  per-endpoint chains do DNAT. Lookup cost no longer grows with the number of Services, and updates touch only the
  map elements that changed.

**Choosing a mode in 2026.** iptables remains the default for compatibility. nftables is the recommended choice on
recent kernels (5.13 or later), and some managed offerings now suggest it for new clusters. IPVS was deprecated in
Kubernetes 1.35, and its removal is scheduled for a later release. eBPF replacement is the choice when the CNI
already provides it and the team accepts a deeper dependency on that CNI.

**Generalised pattern.** This is a *distributed virtual IP* design: a control plane publishes desired mappings
(Service → endpoints), and every node holds a local copy of the table and enforces it at the earliest hook it can
reach. The same shape drives cloud VPC load balancers, service-mesh sidecars and Docker's own published-port NAT
(which, as the catalog's Docker material shows, now has an nftables back end too).

**Structural evaluation.**

| Concern | Detail | Mitigation |
|---|---|---|
| Conntrack dependence | All NAT modes need conntrack. Tables can fill under high connection rates, and stale UDP entries break DNS after a backend moves | Size `nf_conntrack_max`; kube-proxy flushes UDP entries on endpoint change; NodeLocal DNSCache |
| Source IP loss | `externalTrafficPolicy: Cluster` SNATs traffic arriving on a node without a local backend | Use `Local`, accepting uneven spread and needing health checks from the LB |
| Mixed rule owners | Host firewalls (firewalld, Docker) and kube-proxy write to the same hooks; priority mistakes drop traffic | Prefer nftables everywhere and audit tables with `nft list ruleset` |
| Mode drift | Behavioural differences between modes surprise migrations | Test with conformance and e2e suites before switching; migrate node pools gradually |
| eBPF lock-in | Replacement depends on kernel features and one vendor's agent | Pin kernel versions; keep a documented fallback to nftables mode |

**Applicability elsewhere.** The verdict-map technique applies to any large static-to-dynamic mapping on a Linux
host: per-tenant port forwarding, VPN gateways, or replacing hundreds of host firewall rules with one set lookup.
The catalog's ArchWiki and RHEL nftables material covers sets, maps and atomic rule replacement in that general
form.

## Related and opposing views

- **"Remove kube-proxy" (Cilium, Calico eBPF and similar).** Advocates argue that socket-level load balancing
  removes NAT for most in-cluster traffic and that one agent should own the whole data plane. Critics point to
  harder debugging (BPF maps instead of readable rules), kernel-version coupling, and operational dependence on a
  single project.
- **Service mesh.** Sidecar or ambient meshes (Istio, Linkerd) do layer-7 balancing, retries and mTLS. Some
  setups bypass the Service virtual IP entirely, which makes kube-proxy's job less central. Others see that as
  duplicated machinery.
- **Gateway API over `LoadBalancer` per Service.** Rather than one cloud load balancer per Service, shared gateways
  route by host and path. This changes how `LoadBalancer` is used without changing the node-local data plane.
- **Keep iptables.** Conservative operators keep the default because their tooling, runbooks and observability
  are built around iptables chains. The case is about operational familiarity rather than performance.

## Future direction

- nftables is expected to become the default mode once support across distributions and kernels is broad enough.
  The upstream KEP describes iptables as a long-term maintenance burden.
- IPVS removal will force IPVS users to move to nftables or an eBPF data plane over the next several releases.
- Expect continued work on traffic distribution (`trafficDistribution`, topology-aware hints), dual-stack and
  multi-network Pods, which put more state into the per-node Service table.
- Convergence on a single packet framework (nftables for rules, BPF for programmable hooks) should reduce the
  "who owns this hook" conflicts between container runtimes, host firewalls and Kubernetes.
