# From a stable name to a moving set of Pods: kube-proxy modes and Service types

## Define the problem

Pods are disposable. Each time one is rescheduled it gets a new address, scaling adds and removes them, and at any instant some are failing their readiness checks and should receive nothing. Clients want the opposite: one address and one port that keep working through all that churn. The Service object is the contract that provides it. The cluster still has to realise the contract in the data plane, which means that on every node something must recognise a packet aimed at a Service, choose a healthy backend, rewrite the destination, and make sure the reply is translated back so that the client sees an answer from the address it called.

That mechanism has demanding requirements. It must follow EndpointSlice changes within seconds even when the cluster has thousands of Services and hundreds of thousands of endpoints. It must handle traffic that begins in a Pod, traffic that begins on the node itself, and traffic that arrives from outside. It must honour options such as session affinity, the external traffic policy that preserves the client address, and topology hints that prefer nearby backends. It must add little latency per packet, and its updates must not stall the node. The documentation of the Service proxy design lists the proxy modes and the rules for virtual IP assignment that sit behind these requirements [src: kubernetes-docs db7e1105cbd24296].

This slice covers the node-local translation (kube-proxy and its three Linux back ends), the Service types layered on top of it (ClusterIP, NodePort, LoadBalancer, ExternalName and headless Services), and the failure cases that administrators meet: stale connection tracking, lost client addresses, rule ownership conflicts and mode migrations. Pod-to-Pod routing, Ingress, Gateway API and NetworkPolicy are separate topics in this course, though they meet the Service machinery at several points.

## History and approaches

**The userspace proxy.** The first kube-proxy accepted connections in its own process and copied bytes between the client and a chosen backend. It was easy to reason about and could retry on another backend when one failed, but every byte crossed between kernel and user space twice, so throughput and latency suffered. It solved only the stable-address half of the problem and was retired once the kernel-based modes matured.

**The iptables mode.** kube-proxy then became a controller that programs the kernel instead of carrying traffic. For each Service it writes NAT chains: a top-level chain matches the Service address and port, a per-Service chain picks an endpoint with a cascade of probabilistic matches, and a per-endpoint chain rewrites the destination. Connection tracking pins a flow to its backend after the first packet and handles the reverse translation. This design became the default and stayed so for years. Its costs grew with clusters. Matching the first packet of a flow walks a list, so latency rises with the number of Services. Updates used to rewrite the whole table through a restore command, which held the lock that every iptables user on the node shares, so large clusters stalled other tools for seconds at a time. Later releases added partial synchronisation and minimum sync intervals, which reduced but did not remove the effect.

**The IPVS mode.** To fix lookup scaling the project reused the kernel's IP Virtual Server, a layer-4 load balancer with hash tables and several schedulers, such as round robin, least connections and source hashing [src: kubernetes-docs 5151d1afdb03e387]. Lookups became constant time and updates incremental. The catch was that IPVS still depended on iptables and ipsets for masquerading and for the NodePort and external address cases, so administrators had to understand two subsystems, and the behaviour drifted from the iptables mode in small ways that the project found hard to keep equivalent. IPVS was therefore a partial success: it solved scale for the people who adopted it and left a maintenance burden for the project.

**The eBPF replacements.** CNI projects went further and removed kube-proxy entirely. As the previous slices described, a program attached at the socket layer rewrites the destination at connect time, and programs at the traffic-control or driver layer handle traffic arriving from outside, with the Service table stored in kernel maps instead of rule chains. The Cilium instructions show a kubeadm installation that skips the kube-proxy add-on and then validates that the agent has taken over NodePort, LoadBalancer and external address handling [src: cilium f4dbcccd4efa7874].

**The nftables mode.** The in-tree answer to the same problems, without a dependency on a specific plugin, is a back end built on nftables, which has native sets and verdict maps. A single lookup keyed on destination address, protocol and port jumps directly to the Service's chain, and changes are applied as incremental atomic transactions instead of rewrites. The mode appeared as an alpha feature in release 1.29 and became generally available in 1.33. It also fits the direction of distributions that have deprecated the legacy iptables interface, such as the Red Hat family, whose current documentation introduces nftables as the framework to learn [src: rhel-10-docs d5b240ebff205060]. A separate proposal deprecates the IPVS mode, and the project announced that deprecation for release 1.35 with removal scheduled for later releases (to verify the exact release when planning).

**The pattern across eras.** Each step moved the work either down the stack, from user space to the kernel's netfilter and then to hash tables or maps, or toward diffs, from full rewrites to partial syncs and then to transactions. The data structure that holds the Service table matters more than the translation itself.

## Current state

**Service types as layers.** It helps to see the types as wrappers around one another instead of alternatives.

| Type | What it adds | Who implements it |
|---|---|---|
| ClusterIP | A virtual address reachable inside the cluster; the base for the rest | kube-proxy, or an eBPF replacement, on each node |
| NodePort | The same backends on a port of every node, by default in the range 30000 to 32767 | kube-proxy plus host firewall rules |
| LoadBalancer | An external balancer aimed at the NodePorts or directly at Pods | A cloud controller, MetalLB, or the CNI's address management |
| ExternalName | A DNS alias only, with no proxying | CoreDNS |
| Headless (clusterIP None) | DNS returns the Pod addresses; there is no virtual address | CoreDNS; clients balance for themselves |

The Service reference describes each type and its fields, including the NodePort range and allocation rules [src: kubernetes-docs 2894c3a201815c41].

**EndpointSlices.** The control plane publishes backends as EndpointSlice objects, each holding up to a bounded number of endpoints, with conditions for ready, serving and terminating. kube-proxy watches them, and since each slice is small, a change in one Pod updates one slice instead of one enormous object, which is what made the old endpoints object unmanageable at scale. Slices can also be mirrored from legacy endpoint objects for applications that still write them [src: kubernetes-docs 8bc8fa921bc3f34b].

**What each mode does for one packet.** In iptables mode the first packet of a new flow reaches the top-level Service chain from the prerouting or output hook, matches the Service address and port, falls into a randomly chosen endpoint chain and is rewritten to a Pod address; conntrack handles every later packet and the reply. In IPVS mode a dummy interface holds all the virtual addresses so that the kernel accepts the packet as local, IPVS picks a real server with its scheduler, and ipset-backed rules cover masquerading. In nftables mode one table holds verdict maps from address, protocol and port to per-Service chains, and per-endpoint chains perform the rewrite, so lookup cost no longer grows with the number of Services and an update touches only the changed map elements. The lab for this topic builds that verdict map by hand.

**Choosing a mode.** The iptables mode remains the default for compatibility. The nftables mode is the recommended choice on recent kernels, with the project's documentation naming a kernel generation as a minimum (to verify the number for the version in use), and several managed offerings now suggest it for new clusters. IPVS is on a deprecation path. The eBPF replacement is the choice when the CNI already provides it and the team accepts the deeper dependency on that CNI and on newer kernels.

**Options that change behaviour.** The external traffic policy has two values. With Cluster, any node may take the traffic and forward it to any endpoint, with an extra hop and translation of the source address. With Local, a node serves only its own endpoints, keeps the client address, and reports through a health-check port whether it has any. Session affinity pins a client address to a backend for a configurable time. Topology-aware routing and the traffic distribution field let the proxy prefer endpoints in the same zone when enough exist. Terminating endpoints continue to receive traffic for existing connections and are skipped for new ones, which depends on the proxy implementing the termination conditions.

**Structural issues in every NAT mode.** All of the kernel NAT modes depend on connection tracking. Tables can fill under high connection rates, and stale UDP entries can break DNS after a backend moves, which kube-proxy mitigates by flushing entries for UDP endpoints that change. Host firewalls such as firewalld and the container engine write to the same hooks as kube-proxy, so ordering and priority mistakes drop traffic; the Docker documentation's description of its own nftables back end shows the same tables in a different product [src: docker 35f97bfc4f6b4b82]. Source address loss with the Cluster policy and mode drift during migrations complete the list, and the mitigations are in the assessment below.

## Assessment: the good, the bad and the ugly

**The good.** Every mode implements the same contract, so applications cannot tell the difference. The kernel-based modes keep packets out of user space, cost nothing when idle, and keep serving traffic while the kube-proxy process restarts, since the rules stay in the kernel. The nftables mode removes the main scaling problems of iptables without a new dependency, with readable rules and atomic updates. Service types compose cleanly, so a LoadBalancer is a NodePort is a ClusterIP, which makes behaviour predictable and debuggable layer by layer.

**The bad.** The modes behave subtly differently, so a migration is a behaviour change that conformance tests only partly catch. IPVS carries two subsystems and a deprecation. The iptables mode is slow to update and match at scale. Conntrack is a hidden shared resource with a fixed size. The Cluster policy loses client addresses, the Local policy gives uneven spread and needs health checks from the balancer, and neither is right for every service. Debugging in all modes means reading generated rules that no human wrote, and the eBPF modes replace readable rules by map contents that need the plugin's own tools.

**The ugly.** The worst incidents involve two writers on one hook. A host firewall reload that flushes the whole ruleset removes the chains kube-proxy installed, so Services stop working until the next sync, which can take a minute or more. A migration from iptables to nftables that leaves old chains behind creates a node where the old rules still match first. A conntrack table that fills under a connection storm drops new flows for every Service on the node at once. And a kube-proxy that cannot reach the API server because the Service for it is itself broken is a circular failure that needs a fix from outside the data plane.

## Applications beyond this domain

The idea of a distributed virtual address is general: a control plane publishes desired mappings, and every node keeps a local copy and enforces it at the earliest hook available. Cloud virtual private networks, service-mesh proxies and Docker's published-port translation have the same shape. The verdict-map technique applies to any large mapping from keys to actions on a Linux host: per-tenant port forwarding, VPN gateways, or replacing hundreds of host firewall rules with a single set lookup, and the distribution documentation on sets and maps covers it in that general form [src: archwiki 0d4166ac4fdb5b1c]. The same lessons about atomic replacement and ownership of hooks apply wherever more than one program wants to write packet rules.

## Examples

A first example is reading a Service on a node. For a ClusterIP Service, the administrator lists the nftables ruleset or the iptables NAT table, finds the match on the Service address and port, follows it to the endpoint chains and checks that the destinations match the ready addresses listed in the EndpointSlices. A mismatch means the proxy is behind the API, which points to a sync problem or an API connectivity problem.

A second example is a migration plan from iptables to nftables for a large cluster. The team checks kernel versions on all nodes, runs the project's conformance suite on a test pool in the new mode, then moves one node pool at a time by changing the kube-proxy configuration and replacing the nodes, which guarantees no old chains remain. Each pool runs for a day with metrics on proxy sync latency, connection errors and DNS failures before the next one moves. Rollback is the reverse and is practised on the test pool first.

A third example is the lost client address. A service behind a load balancer logs only node addresses. The Service uses the Cluster policy, so traffic that lands on a node without a local endpoint is translated. The team changes the policy to Local, spreads the endpoints across nodes with a topology constraint, and configures the balancer to use the health-check port so that nodes without endpoints leave rotation. The incident note records that the change moved the failure mode from lost addresses to uneven load.

A fourth example is the stale UDP flow after a DNS backend moves: queries to the old Pod vanish until the entry expires. The administrator confirms that the node still has a conntrack entry for the old destination, deletes it with the conntrack tool, and verifies that the proxy flushes UDP entries on endpoint changes in the running version. A node-local DNS cache removes the issue structurally.

## Related problems and ideas

This topic connects to every other slice of the course. The CNI contract and plugin comparison (T02, T03) supply the Pod network that Service traffic rides on. The eBPF slice (T05) is the alternative implementation. Ingress and Gateway (T06) and load balancer addresses (T10) sit in front of Services, and network policy (T07) applies to the translated destination in some plugins and to the original in others, which is a detail worth testing on the plugin in use. DNS (T08) provides the names for the same virtual addresses. The MTU and throughput slice (T12) measures what this machinery costs per packet.

A broader idea is the single owner of a hook. The simplest way to avoid conflicts between kube-proxy, the host firewall and the container engine is to give each its own nftables table with a documented priority, and to treat a ruleset flush as a destructive operation that needs a runbook entry.

## Active research

Work in progress includes the move of the nftables mode to the default, the retirement of IPVS, per-node and per-zone traffic distribution with better semantics, support for multiple Service CIDRs and dual-stack with consistent behaviour, and a proposal to give the proxy a smaller, more modular back-end interface so that more implementations can plug in. In the plugin world, the acceleration of Service handling in the driver and the extension of socket-level translation to more cases are the active threads. Release numbers in this slice come from the project's enhancement proposals and are "to verify" against the version in use.

## Future direction

The probable direction is nftables as the in-tree default, eBPF as the performance and feature option, and iptables and IPVS as legacy modes with decreasing support. The enduring skills are the ability to read a generated ruleset, to reason about connection tracking, to choose the traffic policy deliberately, and to migrate by node pool with measurements instead of by cluster-wide switch.
