# Service meshes: encrypted, authenticated service-to-service traffic with Istio ambient and Linkerd

## Define the problem

Once a cluster has dozens of services calling one another, the same list of cross-cutting needs appears in every application: encrypt traffic between services, prove who is calling, retry transient failures with sensible limits, time out slow calls, split traffic between versions, and produce request-level metrics and traces. Writing those features into each application, in each language, produces inconsistent behaviour and a permanent maintenance burden. Network policy (the previous slice) answers part of the question at layers three and four by address and identity of the Pod, but it neither encrypts the traffic nor understands a request.

A service mesh moves these functions out of the applications and into the platform. A data plane of proxies handles the traffic, a control plane distributes configuration and certificates, and the application is, ideally, unaware. The central security function is mutual TLS: each workload receives a short-lived certificate that carries its identity, both ends of every connection present certificates, the traffic is encrypted, and policy can be written in terms of who the caller is, not which address it came from.

The design question for the administrator is cost. A mesh adds components, latency, memory and failure modes, and requires the team to learn a new set of resources. This slice explains what the main designs do (the classic sidecar model, the Rust micro-proxy approach of Linkerd, and the newer ambient model of Istio), how mutual TLS and identity work, what to check before adopting one, and how to debug the common failures. It is intentionally a survey at medium depth, with the hands-on part limited to the configuration that a mesh needs from the cluster.

## History and approaches

The first generation of the idea was the library: Netflix's resilience libraries, Finagle at Twitter and similar frameworks put retries, circuit breakers and load balancing inside the application process, in one language. The step to a mesh came with the sidecar pattern. Linkerd 1, built on the JVM, and then Envoy, written in C++ at Lyft and donated to the CNCF, ran as a separate process beside each application and handled its traffic. Istio, announced in 2017 by Google, IBM and Lyft, combined Envoy proxies with a control plane. Linkerd 2 rewrote the project around a Rust micro-proxy and a deliberately small feature set, with security on by default.

Adoption brought lessons. Istio's early control plane was a set of several services with a reputation for complexity, and the project responded by merging them into a single binary, istiod, and by simplifying installation. Sidecars have costs that scale with the number of Pods: each Pod carries a proxy with its own memory and CPU, injection changes the Pod spec, and startup ordering and job termination caused well-known bugs, such as batch Jobs that never completed because the sidecar did not exit. Kubernetes added native sidecar containers, an init container with a restart policy, to fix lifecycle ordering. A different response was to remove the per-Pod proxy: Istio's ambient mode splits the data plane into a per-node secure-transport agent (ztunnel) and optional per-namespace or per-service L7 proxies called waypoints, and reached stable status in late 2024 (to verify the release number and the current feature gaps). Cilium also provides mesh-like features, with Envoy as a per-node proxy managed by the agent and L7 rules attached to its network policy [src: cilium-docs 584fd13a05cd02f2].

Standards efforts had mixed results. The Service Mesh Interface tried to define a vendor-neutral API and was later archived as the community moved to the Gateway API, whose GAMMA initiative allows routes to attach to Services and so to express mesh traffic management with the same objects used for ingress. SPIFFE, a specification for workload identity documents and the protocol to obtain them, became the common identity layer: Istio and others issue SPIFFE-compatible identities, and the independent SPIRE project implements the issuing side. The licensing story is also part of the history: in 2024 the main sponsor of Linkerd changed how stable release artefacts are distributed, with the open-source project continuing to publish edge builds and the vendor distributing stable builds under commercial terms for larger organisations (to verify the current terms before an adoption decision).

## Current state

**Identity and mutual TLS.** In every mesh the identity of a workload derives from its Kubernetes service account. The control plane acts as a certificate authority, receives a signing request from the proxy, validates the Pod's service-account token with the API server, and returns a short-lived certificate whose subject names the trust domain, the namespace and the service account in the form of a SPIFFE identifier. Lifetimes are measured in hours (a day by default in the common meshes, to verify), and rotation is automatic. The root of trust is either generated by the mesh (acceptable for tests) or supplied by the organisation, usually as an intermediate certificate signed by an offline root and managed with cert-manager. Rotating the root, or letting the intermediate expire, is the single most disruptive operation in a mesh and deserves a runbook and a calendar entry.

**Modes of enforcement.** Traffic can be mutual-TLS only or permissive. In Istio, a peer authentication resource sets the mode per mesh, namespace or workload; permissive mode accepts both plain and encrypted traffic and exists to allow gradual migration, while strict mode rejects plain text. Linkerd encrypts automatically between meshed Pods, with policy resources controlling which clients may reach which servers. Neither provides encryption for traffic to a workload that is not in the mesh, and neither authenticates an external client, so the ingress gateway, which terminates external TLS and then originates mesh traffic, is part of the trust design.

**Authorisation.** Authorisation policy states which identities may perform which operations on which workloads. At L4 a rule mentions an identity (a service account or a namespace) and a port. At L7, in a sidecar or waypoint, it can mention an HTTP method, path or header. Because the identity in the rule comes from a verified certificate, an attacker who has a Pod in the cluster cannot claim to be another workload by spoofing an address, which is the main security improvement over address-based network policy.

**Sidecar versus ambient.** In sidecar mode a proxy runs in each Pod, an init step or CNI plugin redirects the Pod's traffic through it, and the proxy handles both L4 security and L7 features. In ambient mode a ztunnel Pod on each node establishes encrypted tunnels between nodes using HBONE (an HTTP CONNECT-based tunnel carrying mutual TLS) on a dedicated port, and enforces L4 authorisation by identity. Only workloads that need L7 features get a waypoint, an Envoy deployment that processes requests for a namespace or a service account. The model reduces the resource cost of securing everything, avoids injection and restarts, and separates the lifecycle of the proxy from the application. Its limits are that L4 features are the default, that waypoint placement is an additional design decision, that traffic must be redirected to the node component with a CNI-level mechanism that has to coexist with the cluster's own CNI, and that the feature set was still catching up with the sidecar mode at the time of writing (to verify the gaps against the release notes).

**Linkerd.** The Linkerd data plane is a Rust proxy with a small configuration surface, injected as a sidecar. The control plane has a destination service, an identity service and a proxy injector. Policy is expressed in a few custom resources for servers, route policies and authorisation. The project's argument is operational: less to learn, less to break, low overhead, mutual TLS on by default. The cost is a narrower feature set than the Envoy-based meshes, with fewer extension points.

**Traffic management and observability.** All the meshes can do weighted routing, retries with budgets, timeouts, circuit breaking and fault injection, and all produce golden-signal metrics (request rate, success rate, latency) per workload without code changes. Many can export traces, though the application must still propagate the trace headers, which is a point that surprises new users.

**Operating a mesh.** Day-two work includes upgrades (control plane and data plane have a supported version skew), certificate management, resource sizing of proxies, debugging with the mesh's own diagnostic command, and a tested way to bypass the mesh for a workload that misbehaves. Capacity needs a budget: control-plane memory grows with the number of services and proxies, and every sidecar adds its own memory. Telemetry volume can be larger than the application traffic in some designs, so metric cardinality is something to constrain from the start.

A further consideration is how a mesh interacts with the cluster's job and probe machinery. Kubelet health probes originate from the node and carry no workload certificate, so strict mutual TLS needs either a probe rewrite performed by the injector or an exemption for the probe port. Batch workloads need the proxy to exit when the main container does, which is the problem native sidecar containers were designed to solve. Applications that open connections before the proxy is ready, typically at start-up, fail the first call unless the platform holds the application back until the proxy reports ready. These are small details in a design review and frequent causes of the first production incident after adoption, so a pilot should include a batch job, a probe, a start-up dependency and a long-lived streaming connection, not only a request-response service.

## Assessment: the good, the bad and the ugly

**The good.** A mesh gives uniform, identity-based encryption and authorisation with no application change, a consistent source of request-level telemetry, and a safe, declarative way to do progressive delivery. For organisations with compliance requirements that demand encryption in transit between all internal services, a mesh is often the quickest way to a defensible answer. Ambient mode lowers the cost of the first step, mutual TLS everywhere, to a per-node component.

**The bad.** A mesh is a large new dependency. It introduces a second layer of routing and a second place where traffic policy lives, next to the CNI and the ingress, and each layer can break the others. Debugging moves from tcpdump on a Pod to understanding proxies, certificates and redirect rules. Latency overhead is small per hop but adds up across long call chains. Not every workload fits: protocols that the proxy cannot parse, server-first protocols, and applications that terminate their own TLS need special handling, and host-networked workloads sit outside the mesh.

**The ugly.** The sharpest failures are in the lifecycle of certificates and of the proxies: an expired intermediate certificate stops all new mutual-TLS connections at once; a control-plane outage prevents new Pods from getting identities, while existing ones continue until their certificates expire; a version skew during upgrade leaves some proxies with configuration they cannot parse. Strict mode switched on cluster-wide before every workload is meshed makes health probes and legacy clients fail, and the symptoms (connection resets, no logs on the application side) point away from the cause. The other ugly truth is organisational: teams adopt a mesh for one feature, mutual TLS, and end up responsible for a platform whose other features nobody asked for. Recognising that cost early, and choosing the smallest option that meets the requirement, is the best advice in this slice.

## Applications beyond this domain

The same ideas appear outside Kubernetes. Identity-based mutual TLS between workloads is the core of zero-trust architectures at large companies, with SPIFFE-style identities issued to virtual machines and bare-metal services. Proxy-based traffic management predates meshes in the form of application delivery controllers and API gateways, and the sidecar pattern is used for logging agents and secret fetchers. The certificate-lifecycle practices (short lifetimes, automated rotation, offline roots) apply to any internal PKI, including the Linux hosts' own systems for service-to-service authentication.

## Examples

A first example is a staged rollout of strict mutual TLS. The team enables the mesh in permissive mode for one namespace, verifies in the telemetry that every client of each workload is meshed, fixes the exceptions (a cron job, a monitoring scraper, a legacy client), then flips the namespace to strict, observing error rates for a day before moving on. The rollback is flipping the mode back, which is instantaneous, and the plan names an owner and a time window.

A second example is an authorisation rule. The billing service should accept calls only from the checkout service account. The policy names the checkout identity as the allowed principal and the billing port, with default-deny for everything else. A test from a Pod with another service account is rejected at the proxy, and the same test with a spoofed source address is also rejected because the identity comes from the certificate.

A third example is choosing between designs. A team with a hundred small services wants encryption and basic metrics. The sidecar option adds a proxy to each Pod, increasing memory by a visible amount; the ambient option adds one agent per node and no change to Pods but needs the CNI chaining to be set up; the CNI-based option from a plugin the cluster already runs adds nothing new but offers fewer L7 features. The decision depends on the requirement list and on the maturity of each option on the cluster's kernel and CNI, and the team writes the criteria down before running the trial.

## Related problems and ideas

The mesh interacts with the ingress gateway (T06), because the gateway is the point where external TLS becomes mesh TLS, and with network policy (T07), which remains useful as a coarse and independent layer under the mesh. DNS (T08) provides the names the mesh resolves, and multi-cluster mesh designs (T11) must share a root of trust and make service endpoints reachable across clusters. Outside this course, the security course picks up certificate management, workload identity federation and supply-chain concerns.

An idea that links these is defence in depth with independent failure modes. Network policy fails closed on a different mechanism than the mesh, so using both means a bug in one does not remove all protection. That argument supports keeping both layers even when they overlap.

## Active research

Active work includes the sidecar-free modes (ambient in Istio, similar work in other projects), moving mesh data planes to eBPF and kernel TLS, the Gateway API's GAMMA profile for mesh routing, post-quantum key exchange in the proxy libraries, integration of workload identity with cloud IAM and with SPIRE, multi-cluster identity federation, and better tools to explain why a request was denied. Stability claims for each feature change from release to release and are "to verify" in any plan.

## Future direction

The probable direction is mesh capabilities delivered as part of the network layer, with security-by-default and L7 features on demand, and a standard route and policy API that works across implementations. The practical guidance for administrators stays simple: write down the requirement, adopt the smallest component that meets it, own the certificate lifecycle, and keep an independent network-policy layer underneath.
