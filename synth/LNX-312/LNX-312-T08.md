# Names inside the cluster: CoreDNS, search paths and the failures they cause

## Define the problem

Pods come and go and their addresses change with them, so applications cannot be configured with addresses. Kubernetes gives each Service a stable virtual address and a stable name, and expects applications to find each other by name. Something has to answer those names for every Pod in the cluster, quickly enough that a service call does not pay a noticeable penalty, reliably enough that a restart of one component does not take the whole cluster offline, and flexibly enough to forward names that are outside the cluster, such as the company's internal domains and the public internet, to the right resolver.

That something is a DNS server running as ordinary workloads inside the cluster, plus a convention for how each Pod's resolver configuration points at it. Because every network connection that starts with a name starts with a lookup, DNS failure looks like everything failing. A slow lookup looks like a slow application. And a lookup whose answers differ between two Pods, because one has a different search path or a different policy, looks like the most baffling kind of fault: the same code behaving differently in two places.

This slice covers what the cluster DNS publishes (which record types, for which objects), how the Pod's resolver configuration turns a short name into a series of queries, how CoreDNS is configured and extended, how to diagnose the failures that matter in practice, and the performance and resilience techniques (caching, node-local resolvers, autoscaling) that production clusters use. It also touches multi-cluster discovery, where the single-cluster assumption stops being true.

## History and approaches

Early Kubernetes used environment variables injected into each container to carry the address of every Service that existed when the Pod started. That scheme is still there and has the flaw that made DNS necessary: a Service created after the Pod does not appear. The first DNS add-on, kube-dns, combined three containers (a DNS server, a sidecar that watched the API, and a health and metrics helper) and was replaced in the later releases by CoreDNS, which became the default in kubeadm clusters and a graduated CNCF project. CoreDNS is a single Go binary organised as a chain of plugins: each plugin handles a part of query processing, and the configuration file, the Corefile, lists them per server block. The change brought lower memory use, one process instead of three, and a place to add behaviour without a patch to the server.

The history of the resolver side is a history of surprises. The Pod's resolv.conf contains a search list of the Pod's namespace, the Service domain and the cluster domain, and an option called ndots that defaults to five in a cluster. A name with fewer than five dots is first tried with each suffix of the search list before it is tried as written, so an external name like a public API host triggers several failed lookups for the internal domains before the right one. This was documented as a cause of latency and of load on the DNS Pods, and the standard advice is either to write fully qualified names with a trailing dot, or to lower ndots for workloads that mostly call external names, using the Pod's DNS configuration field.

Another long-running problem came from the interaction of DNS with the kernel's connection tracking. UDP queries from one Pod to the DNS Service address are translated by netfilter, and when two queries from the same socket (the IPv4 and IPv6 lookups sent in parallel by common libraries) race to create the connection-tracking entry, one of them could be dropped, which produced five-second delays while the resolver waited for a timeout. Mitigations arrived on all sides: kernel fixes, resolver options that serialise the two queries, running a node-local cache that talks to the Pods over a link-local address without connection tracking, and the eBPF datapaths that translate at the socket layer. The exact set of kernels with the fix, and the scenarios that remain affected, should be marked "to verify" before a node-local cache is dropped from a design.

Two partial successes complete the picture. Federation and then the multi-cluster Services API tried to let a name in one cluster resolve to endpoints in another. The multi-cluster API defines a ServiceExport and ServiceImport pair and a clusterset DNS domain; Cilium's ClusterMesh documentation describes how it integrates with this API and what its prerequisites are [src: cilium-docs 15ad27f3ae5e7bfe]. And the stub-domain feature of kube-dns, which forwarded selected domains to other servers, was carried over to CoreDNS as a forward block in the Corefile, a change that was simple technically but left many clusters with a stale configuration after upgrades.

## Current state

**Published names.** A Service gets an A or AAAA record at its name in the namespace and cluster domain, with the form service, namespace, the svc label and the cluster domain (cluster.local unless changed at install time). A headless Service, with no cluster address, instead returns the addresses of the ready Pods behind it, which is how stateful applications find their peers. Named ports get SRV records. Pods of a StatefulSet get stable names under the headless Service they belong to. Pods can also have an address-derived name under a pod label, and a Service of type ExternalName returns a CNAME to an outside host. These record types and the conditions for each are the core of the Kubernetes DNS specification, and the debugging guide uses them for its checks [src: kubernetes-docs acfb725dc2176d11].

**The Pod resolver.** The kubelet writes the Pod's resolv.conf from the Pod's DNS policy. The default policy, ClusterFirst, points the Pod at the cluster DNS Service with the search list and ndots described above. The policy named Default gives the Pod the node's resolver configuration, which is not "default" in the sense of the cluster default. A Pod on the host network that still needs cluster names uses a third policy, and None with explicit configuration gives the Pod exactly what the manifest specifies. Custom entries (extra nameservers, search domains, options such as ndots) are added with a DNS configuration section in the Pod spec.

**CoreDNS in a kubeadm cluster.** The installer deploys CoreDNS as a Deployment with two replicas behind a Service with a fixed cluster IP (the tenth address of the Service range by convention), and a ConfigMap that carries the Corefile. A typical Corefile has a single server block on port 53 with these plugins: errors and health for diagnosis, a ready endpoint, the kubernetes plugin that answers cluster names from the API, the prometheus plugin for metrics, a forward plugin that sends everything else to the resolvers of the node, a cache with a short time to live, a loop plugin that detects forwarding loops and a reload plugin that applies configuration changes without restart [src: kubernetes-docs 21ad06d7f86efc7b]. The kubernetes plugin needs permission to list Services, EndpointSlices and Namespaces; missing role bindings after a hand-edited upgrade show up as a Pod that runs but answers nothing, and the troubleshooting page has a step that checks exactly this [src: kubernetes-docs acfb725dc2176d11].

**Customisation.** Extra behaviour goes in the ConfigMap: another server block that forwards a corporate domain to the corporate resolvers, a hosts or file plugin for static records, rewrite rules, a log plugin during an investigation, and different cache settings. Two cautions apply. A mistake in the Corefile makes the new Pods crash and, because the reload plugin can apply an invalid file to a running Pod, the failure can appear later than the edit. And the forward plugin sends upstream queries from the Pod's address, so node-level firewalls and the node's own upstream resolver must allow that.

**Scale and tuning.** The tuning guidance covers replica count (scale with node count, not just request rate), memory limits sized to the size of the cluster, and the autoscaler that ships as an add-on and sets the replica count from node and core counts [src: kubernetes-docs 553ecac97b9aa78d]. For latency, the autopath plugin lets the server resolve the search-list expansion internally (at the cost of more API watch load and memory), and the node-local DNS cache is the common production answer. The node-local cache runs as a DaemonSet that listens on a link-local address on each node, answers from a cache, and forwards misses to the cluster DNS using TCP, which avoids the connection-tracking race and reduces cross-node traffic. Upgrading CoreDNS is a documented procedure that migrates the Corefile and warns about plugins removed or renamed between versions [src: kubernetes-docs 363a09eba9d84fb4].

**Multi-cluster and load balancing.** Where several clusters are connected, a global Service can resolve to endpoints in all of them, and the mesh implementation decides how traffic is balanced and what happens when the local endpoints are unhealthy [src: cilium-docs 32d1d0250870e6a5]. Names are still resolved by the local cluster DNS, which means the DNS add-on must be configured with the mesh's domain in addition to the local domain.

**Diagnosis.** The standard sequence uses a debug Pod with DNS tools. Resolve the API Service name from inside the cluster to test the whole path; read the Pod's resolv.conf to see which server and search list it uses; look at the CoreDNS Pods' status, logs and metrics; check the Service and endpoints for the DNS Service; test the upstream path from a CoreDNS Pod; and only then look at the CNI and policy. Each step isolates a layer, and the documented procedure follows that order.

## Assessment: the good, the bad and the ugly

**The good.** The cluster DNS is simple to reason about: a Service name resolves to a stable address, a headless Service resolves to Pod addresses, and a handful of record types cover everything. CoreDNS's plugin model makes it easy to add forwarding, caching and rewriting. The same component serves in clusters of every size, from a laptop to thousands of nodes, with known scaling steps. And because it is ordinary workload, it is observable with ordinary metrics and logs.

**The bad.** The search list and ndots setting create a hidden multiplier on queries, so a cluster's DNS load is often several times its application request rate for external names. The default of two replicas is a fine start and an outage waiting to happen at a few hundred nodes. DNS is one of the few services that every Pod depends on at nearly every request, and so a short disruption, such as a rolling update that restarts both replicas at once without a disruption budget, propagates through the whole cluster. Tuning is also scattered across three layers: the Pod spec, the Corefile and the node resolver.

**The ugly.** The notable failure modes are the following. Resolution loops: CoreDNS forwards to the node's resolver, which is itself the cluster DNS (a typical mistake with local caching resolvers on the node), so the server detects a loop and stops. The five-second stall from the connection-tracking race, which presents as random slowness that vanishes in testing. Policy lockouts: a default-deny egress policy that omits DNS. Silent truncation: large responses over UDP that are cut and retried over TCP when the path blocks the retry, which shows up for names with many records. Stale caches: a high time to live on negative answers keeps a new Service invisible for minutes. And a controlled-by-someone-else problem: when the node's upstream resolver is slow, every Pod inherits the slowness through the forward plugin.

## Applications beyond this domain

DNS-based service discovery is much older than Kubernetes. Consul, etcd-based registries and the DNS SRV mechanism standardised in the late 1990s served the same purpose, and large internet companies run similar systems with the same cache and TTL trade-offs. The search-list behaviour is a general property of Unix resolvers described in the resolver manual pages; the same ndots trap exists on any Linux host with a long search list. The node-local caching idea corresponds to the system-level resolvers used on desktop Linux distributions (systemd-resolved and others), and the loop problem is the same one that occurs when a local caching resolver is configured to forward to itself. Windows and Active Directory environments use SRV records for locating domain controllers, which is the same record type that Kubernetes publishes for named ports [src: ms-learn-adds 6530d6d52587b362].

## Examples

A first example is the diagnosis of a Pod that cannot resolve a Service. The administrator starts a debug Pod in the same namespace, resolves the API Service name and sees a failure with a timeout, not a not-found answer. Timeouts point to the path to the DNS Service, not to its content. The administrator reads the Pod's resolver file, confirms it points at the right cluster IP, resolves directly against one CoreDNS Pod address, which works, and resolves against the Service address, which does not. The Service has no ready endpoints because the readiness probe of both CoreDNS Pods fails after a Corefile edit. Reverting the ConfigMap fixes it.

A second example is the latency of an external call. A Java application calls a public API by name and shows hundreds of milliseconds in connection setup. A query log from CoreDNS shows five lookups per call, four of which fail with not-found because of the search list. The fixes in order of preference are to use the fully qualified name with the trailing dot, to set ndots to two in the Pod's DNS configuration, or to enable autopath. The team picks the first because it needs no cluster change.

A third example is a corporate domain. Applications call a database by its corporate name, which only the corporate resolvers can answer. The administrator adds a server block to the Corefile that forwards that domain to the corporate resolvers, tests from a debug Pod, and checks that the node firewall allows the CoreDNS Pods to reach those resolvers. A rollback is a revert of the ConfigMap, and the reload plugin applies it in about a minute.

## Related problems and ideas

DNS connects to almost everything else. NetworkPolicy must allow it (T07). The eBPF datapath can record DNS flows and, with the policy language, restrict egress by name (T05, T07). The service mesh has its own name resolution and often relies on the cluster DNS for the first step (T09). Multi-cluster discovery depends on what DNS can publish across clusters (T11). External-dns publishes the cluster's names to outside zones, the inverse of what CoreDNS does. And the node resolver, usually managed by systemd-resolved or NetworkManager, is an invisible dependency of the forward plugin.

A design principle worth teaching is to put DNS behaviour in one place. If the search list, the ndots value and the forwarding rules are each adjusted in a different layer by a different team, the result is a system nobody can reason about. Decide which layer owns each setting, document it, and test the whole chain after each change.

## Active research

Work in the CoreDNS community includes better handling of EndpointSlice-based records for large headless Services, cache and prefetch improvements, DNS over TLS and over HTTPS for upstreams, and metrics that help attribute load to the namespaces that cause it. In Kubernetes, the DNS specification continues to be refined, and there are proposals to ship a node-local cache as a default and to reduce the cost of the search list. The multi-cluster API for Services and its DNS integration is still evolving, and the exact version of each field, as well as which implementations are complete, is "to verify" before a design relies on it.

## Future direction

Expect the node-local cache pattern and socket-level translation to make the connection-tracking issue a legacy problem, DNS policy to move into the same language as network policy, and multi-cluster names to become routine. The enduring practices are to size the DNS Pods with the cluster, keep a disruption budget on them, keep names fully qualified where the call is external, and to maintain a short and reliable diagnostic runbook for the first ten minutes of a DNS incident.
