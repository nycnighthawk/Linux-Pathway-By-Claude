# Sizing the packet: MTU, encapsulation overhead and where throughput goes

## Define the problem

Every network link has a largest frame it can carry, and every layer of encapsulation uses part of that space for its own headers. On a plain Ethernet segment the usual limit for the IP payload is fifteen hundred bytes. When a cluster network wraps each Pod packet in a tunnel to carry it between nodes, the outer packet must still fit in the same fifteen hundred bytes, so the inner packet has to be smaller by exactly the size of the added headers. If the Pod's interface keeps the larger value, packets that fit inside the Pod do not fit on the wire, and what happens next depends on whether anyone along the path tells the sender.

The failure mode is notorious because it is selective. Small packets pass, so name lookups, pings, TLS handshakes of small certificates and short HTTP requests all work. Large packets are dropped, so a file download stalls after a few kilobytes, a large response hangs, a database connection freezes when a big query result begins, or a registry pull never finishes the biggest layer. The cluster appears healthy, monitoring that uses small checks is green, and the people debugging look at the application. An administrator who has met the pattern once recognises it immediately, and one who has not can lose days.

The second half of the problem is throughput. Encapsulation costs CPU in header processing and breaks some hardware offloads, the kernel's per-packet work dominates at high packet rates, and a design that is correct at one gigabit per second can be limiting at forty. The goal of this slice is to give a systematic method: compute the right MTU for each layer, check that the Pod, the tunnel device and the physical interface agree, measure with a repeatable tool, and know which settings move the numbers.

## History and approaches

The path-MTU problem is as old as IP. The original design lets routers fragment packets that are too large for the next link, which works but is slow and fragile, so IPv4 added the Don't Fragment bit and the Path MTU Discovery procedure, in which a router that cannot forward a too-big packet drops it and sends an ICMP message saying what size would fit. The sender lowers its estimate and retries. IPv6 removed router fragmentation altogether and made the procedure mandatory. The system works only if ICMP messages of that type get through, and for decades networks that filter ICMP wholesale have created black holes where the sender never learns the limit. The response was packetization-layer discovery (RFC 4821), in which TCP probes for a working size itself without relying on ICMP, available in Linux as a sysctl that is off by default or enabled only after a black hole is suspected (the exact default and the thresholds are in the kernel documentation and the tcp manual page [src: man-pages 1856464925d6ecbc], to verify per kernel).

Overlay networking made the problem ordinary. Each encapsulation adds a fixed overhead: VXLAN carries an inner Ethernet frame inside a UDP packet, adding an outer Ethernet header, an IP header, a UDP header and an eight-byte VXLAN header, for fifty bytes in the IPv4 case counted against the underlay MTU (the outer Ethernet header is not counted against the underlay's IP MTU, so the commonly quoted reduction for the Pod interface is fifty bytes since the inner Ethernet header is included in the payload). IP-in-IP adds only an outer IP header, twenty bytes. Geneve is similar to VXLAN with a variable-length options field, so its overhead is fifty bytes plus whatever options the implementation uses. WireGuard adds sixty bytes over IPv4 and eighty over IPv6. IPsec in tunnel mode adds a variable amount depending on cipher and padding. When overlays are stacked, such as an encrypted tunnel carrying a VXLAN-encapsulated frame, the costs add.

Plugins reacted by detecting and setting the right value automatically. Calico can derive the MTU of its interfaces from the underlay and the enabled encapsulations, Flannel reads the underlay's value and subtracts its backend's overhead, and Cilium computes the Pod MTU from the device MTU and its configured tunnel and encryption settings [src: cilium-docs 4de7c4cdefd0829b]. These defaults handle the common case and leave the unusual cases to the administrator: jumbo-frame underlays that are only partly jumbo, a cloud network with a smaller MTU than the standard, a virtual network that adds its own encapsulation under the node, and nodes whose different interfaces have different values.

Throughput work followed its own path. Early overlay implementations ran in user space and were slow. Kernel VXLAN support and then offload of tunnel segmentation to the network card raised the ceiling, and the generic receive and segmentation offloads let the kernel treat many packets as one for most of their trip through the stack. Routed designs (no encapsulation) remove the overlay cost. And the eBPF datapaths reduce the per-packet cost of Service handling and policy; the Cilium documentation describes acceleration of load balancing in the driver with XDP for NodePort and LoadBalancer traffic as one of the measures that raises the packet rate a node can sustain [src: cilium-docs 8516904bcf91a62c].

## Current state

**Layers and overhead.** The key computation is simple subtraction down the stack. Start with the MTU of the physical interface the tunnel uses. Subtract the overhead of each encapsulation in the path in the order they are applied. The result is the largest packet the Pod can send. For fifteen hundred and VXLAN over IPv4 this is fourteen hundred and fifty; for IP-in-IP, fourteen hundred and eighty; for WireGuard over IPv4, fourteen hundred and forty; for VXLAN carried inside WireGuard, fourteen hundred. With a nine-thousand-byte underlay the same numbers shift by the same overhead, so VXLAN gives eighty-nine fifty, provided every device in the path, including switch ports and virtual switches, really passes jumbo frames.

**The devices.** A Pod's traffic crosses several interfaces: the Pod's own end of the veth pair, the host end, possibly a bridge, the tunnel device (for example the VXLAN device named by the plugin), and the physical interface. The Pod interface's MTU is what the application sees and what TCP uses to choose the segment size. The tunnel device's MTU should be the underlay minus overhead. A mismatch can occur at any boundary: a Pod MTU larger than the tunnel device will cause drops at the tunnel, a tunnel device larger than the physical limit will cause drops on the wire, and a veth host end smaller than its Pod end causes silent loss at the first hop.

**TCP and MSS.** TCP announces a maximum segment size during the handshake, derived from the interface MTU minus the IP and TCP headers, forty bytes for IPv4 without options. If the Pod MTU is correct, the MSS is correct for the whole path through the cluster. Where the Pod MTU cannot be changed, for instance an application image or a legacy network that sets it, the fall-back is MSS clamping in the firewall, which rewrites the announced MSS in SYN packets so that senders use a smaller segment. Clamping fixes TCP and does nothing for UDP, which is why QUIC and DNS over UDP can still fail on a clamped path.

**Offloads and CPU.** Segmentation offload lets the kernel hand a very large buffer to the network device, which cuts it into wire-sized packets. Receive offload merges packets back. Tunnels complicate this because the device must understand the encapsulation to segment correctly; modern cards and drivers support it for VXLAN and Geneve, and the ethtool feature list shows which are enabled. A known class of problems is checksum offload on tunnel devices with certain kernel and driver combinations, in which the checksum of the inner or outer UDP packet is wrong and the receiver drops the packet silently, producing high latency or throughput collapse between nodes; the workaround that appears in plugin troubleshooting guides is to disable checksum offload on the tunnel device, and the affected combinations should be checked against current bug reports (to verify). The RHEL tuning guides on high-throughput transfers describe the related settings of ring buffers, interrupt coalescing and socket buffers that move numbers on fast links [src: rhel-10-docs 2eba6ec6e1ec3a38], and the guidance on UDP tuning covers the receive-buffer and packet-drop counters that matter for datagram-heavy workloads [src: rhel-10-docs 7357be6ae5837360].

**Measuring.** The standard tool is a client-server throughput tester run between Pods on different nodes, with parallel streams to fill a fast link and with a UDP mode for loss and jitter. A useful measurement plan has four runs: node to node (the ceiling), Pod to Pod on the same node (the software path), Pod to Pod across nodes (the overlay or routed path), and Pod to Service (the load-balancing path). The differences between the runs attribute loss to a layer. Latency is measured separately with small packets, since throughput tests do not show it. For packet-rate limits a test with small packets and many flows reveals per-packet costs that a bulk transfer hides. The tests must record CPU on both ends, since a run that saturates one core says the bottleneck is a single thread, not the link.

**Diagnosing a black hole.** The sequence is mechanical. Send a don't-fragment ping with a payload size that, with eight bytes of ICMP header and twenty of IP header, sums to the expected MTU, and step the size down until it passes; the largest passing size reveals the path limit. Run the same test between Pod and node, node and node, and across the tunnel to find the hop where it changes. Capture on the tunnel device and the physical device to see whether the large packets leave the node and whether ICMP errors come back. The tracepath tool reports discovered MTU per hop when ICMP works. If large packets disappear without any ICMP, a device on the path is dropping silently, and the fix is either the right MTU on both ends or clamping.

**Bandwidth management.** Beyond raw rate there is fairness. Some plugins can enforce per-Pod egress limits with an earliest-departure-time model in the datapath instead of a queueing discipline on each interface, and can select a newer congestion control algorithm for Pod traffic. These settings reduce tail latency for neighbours on a busy node, and each requires a recent kernel (to verify the supported versions).

## Assessment: the good, the bad and the ugly

**The good.** The arithmetic is exact and the tools are standard. When the value is derived automatically and the underlay is uniform, nobody has to think about MTU at all, and the cost of an overlay is modest on current hardware with offloads. Routed designs and eBPF paths reach near line rate on commodity servers. A written measurement plan turns performance arguments into numbers.

**The bad.** Defaults assume uniformity. A cluster that spans environments with different MTUs, such as nodes in a cloud with one value and on-premise nodes with another, has no single right answer for the Pod MTU and must use the minimum. Changing the Pod MTU on a running cluster usually needs a rolling restart of the Pods, because the interface is created at Pod start, so the fix is operationally heavy. Jumbo frames give up to a few tens of percent more throughput but need every device in the path to cooperate, and one misconfigured switch port reintroduces the black hole.

**The ugly.** The worst cases are silent. ICMP filtered by a firewall that was "hardened" without reading the standards, a cloud load balancer that drops fragments, a tunnel stacked inside another by a different team, and a monitoring system that checks only small requests together hide the problem until a large payload arrives, usually a software update or a database backup. Throughput regression after a kernel upgrade, caused by a changed offload default, shows up as an unexplained fall in numbers with no error. And the temptation to fix a black hole by raising the MTU on one side, instead of finding the true minimum, produces a configuration that works until traffic takes a different path.

## Applications beyond this domain

MTU behaviour is a general network-engineering topic. VPN deployments of every kind (site-to-site IPsec, WireGuard, SSL VPNs) face the same arithmetic and the same MSS-clamping fix. PPPoE links lose eight bytes and made the problem famous for home users. Virtual machine networks add encapsulation in the hypervisor, and storage over Ethernet and iSCSI have historically used jumbo frames for throughput. Content delivery networks and mobile networks tune the MSS and probe the path to avoid black holes. The measuring method applies to any link: establish the ceiling, add one layer at a time, and record the difference.

## Examples

A first example is a cluster using VXLAN over a fifteen-hundred-byte network that has an application image setting its own interface MTU to fifteen hundred through an init script. The symptoms are image pulls that hang on large layers. The administrator runs a don't-fragment ping between two Pods on different nodes, finds that 1422 bytes of payload pass and 1423 do not, calculating that the path limit is fourteen-fifty, and finds the Pod interface at fifteen hundred. Removing the script and restarting restores the default.

A second example is a throughput investigation. Node-to-node tests give nine point four gigabits per second on a ten-gigabit link. Pod-to-Pod across nodes gives six, with one core fully used on the receiving node. The administrator checks the offload features of the tunnel device and sees receive offload off because of a plugin default, enables it, and reaches nine point one. The record of the before and after numbers goes into the runbook with the kernel and driver versions.

A third example is the plan for a switch to jumbo frames. The administrator checks every switch port and virtual switch in the path, sets the physical interface to nine thousand on a subset of nodes, verifies large don't-fragment pings between them, changes the plugin's MTU setting, performs a rolling restart of the Pods and measures again. The rollback is the reverse order with the same checks.

## Related problems and ideas

This topic closes the loop with the CNI comparison (T03), where overlay and routed designs were first weighed: the MTU and CPU numbers in this slice are the quantitative side of that choice. The eBPF datapath (T05) changes the per-packet cost and offers XDP acceleration. The service mesh (T09) adds a proxy hop and sometimes an encrypted tunnel that reduces the available payload further. BGP to the fabric (T13) is the route to jumbo frames and to removing overlays. The first lesson of the course (T01) gave the namespace and veth view, where the MTU of each interface is visible and settable, and the virtualization course returns to the same arithmetic for virtual machine networks.

An idea that deserves attention is the idea of an MTU budget for the whole organisation. Instead of discovering values per cluster, the network team publishes one, with the encapsulations that may be stacked on it, so that every platform team can compute its Pod MTU from the same document.

## Active research

Active work includes automatic discovery of the MTU at runtime across heterogeneous paths, packetization-layer probing becoming the default for TCP and for QUIC, better offload support for tunnels in cards and drivers, generic segmentation for encrypted traffic, kernel bypass and XDP-based datapaths that avoid most of the stack, and netkit devices that shorten the path between Pod and host. Throughput claims from vendors are not directly comparable between hardware generations and kernels, so any figure used in a plan is "to verify" on the target hardware.

## Future direction

Expect better defaults and more automation, with plugins detecting and setting MTU across mixed environments, hardware offload covering more encapsulations, and routed designs becoming common, which removes most of the arithmetic. The administrator's skills remain the same: compute the budget, test with don't-fragment packets at each hop, measure in layers, and keep ICMP flowing.
