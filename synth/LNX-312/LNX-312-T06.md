# Getting HTTP traffic into a cluster: from Ingress to the Gateway API

## Define the problem

A Service of type LoadBalancer gives each application its own external address and its own cloud load balancer. That is simple and expensive: a hundred web applications would need a hundred load balancers, a hundred public addresses and a hundred certificate arrangements, and none of them could route by host name or URL path because the Service abstraction knows nothing about HTTP. What operators want is the model that web hosting has used for decades: a small number of shared entry points that terminate TLS, look at the host and the path, and forward each request to the right backend, with the rules owned by the teams who own the applications.

Kubernetes answered with the Ingress resource and a family of controllers that implement it. The answer worked and then hit a ceiling. Ingress describes only a small intersection of what proxies can do, so every controller invented annotations for the rest, and manifests stopped being portable. It also puts the infrastructure decisions (which address, which listener, which certificate) and the application decisions (which path goes where) in one object, so one team's edit can break another team's traffic. The Gateway API is the successor designed to fix these two problems, with typed fields in place of annotations and a role-oriented set of resources.

This slice explains both APIs, shows how a controller turns them into a proxy configuration, compares the main implementations, and gives a migration path. The learning goals are to read and write a route for either API, to say which component owns which decision, to debug the common failure (a route that is accepted by the API but never programmed), and to plan a migration that keeps traffic flowing.

## History and approaches

Before Ingress, applications used NodePort Services plus a hand-built load balancer, or one LoadBalancer Service per application. Ingress arrived as a beta API in the first years of Kubernetes and reached GA as networking.k8s.io/v1 in Kubernetes 1.19, after a long period in which the beta form was the de facto standard [src: kubernetes-docs bfa36fcb54f4486d]. The object defines rules (host, path with a match type, backend Service and port), a TLS section that names a Secret, and a class field that selects which controller should act. By design it is only a declaration: nothing happens until a controller is installed, and the project does not ship a default one, a point the documentation repeats in its controller overview [src: kubernetes-docs b1cf05fd83025f20].

The controller field filled with competing implementations: the NGINX-based community controller, the NGINX Inc. controller, HAProxy, Traefik, Envoy-based controllers such as Contour and Emissary, cloud-vendor controllers that drive the cloud's own layer-7 balancer, and others catalogued in the third-party list [src: kubernetes-docs 0fba34b42905cec2]. Because the API could not express rewrites, timeouts, header manipulation, canary weights, authentication hooks or non-HTTP protocols, each controller defined annotations, and an Ingress written for one controller was partly meaningless on another. Some projects added their own custom resources to escape the limits (Traefik's IngressRoute, Contour's HTTPProxy), which solved the problem for one controller and deepened the portability problem across them.

The Gateway API began in 2019 as a SIG-Network project, deliberately outside the core API so it could evolve faster: it is a set of CRDs installed in the cluster, with a conformance test suite that implementations run to claim support. It reached its first GA release in October 2023 with the GatewayClass, Gateway and HTTPRoute resources, and later releases promoted more features (gRPC routes, backend TLS, session persistence and others, with some still experimental, to verify against the current release notes). The design separates three personas: an infrastructure provider who defines classes of gateways, a cluster operator who creates Gateways with listeners and policies, and application developers who attach routes to those Gateways.

Failures and partial successes are instructive. The community Ingress controller based on NGINX was by far the most deployed implementation, and its very popularity turned its annotation set into a de facto standard that other tools tried to emulate. In late 2025 the Kubernetes project announced the planned retirement of that controller, with best-effort maintenance continuing for a short period and no further releases afterwards (to verify the exact dates in the announcement). Whatever the final timeline, the event is a lesson for any team: an Ingress controller is a dependency with a lifecycle, and a cluster whose entire traffic path rests on one volunteer-maintained project needs a migration plan before the date, not after it. The Ingress API itself is frozen rather than removed; the documentation says that it is no longer receiving feature work and points readers to the Gateway API [src: kubernetes-docs 4a7703e464376751].

## Current state

**Ingress objects.** An Ingress names an optional class, a default backend, and a list of rules. Each rule can specify a host (with a wildcard form) and a list of paths. A path has a type: Exact matches the full string, Prefix matches on path elements separated by slashes, and ImplementationSpecific leaves the interpretation to the controller. A TLS block lists hosts and the Secret that holds the certificate and key. The controller watches Ingress, Service and EndpointSlice objects and Secrets and renders a configuration for its data-plane proxy; many controllers send traffic straight to Pod addresses rather than through the Service, to allow session affinity and better balancing. The default controller is chosen by marking one IngressClass as the default; having two defaults is a misconfiguration the API server rejects at admission for newer versions and silently tolerates in older ones (to verify).

**Gateway API objects.** A GatewayClass names a controller. A Gateway requests listeners (port, protocol, host name, TLS mode and certificate reference) from one class and declares which namespaces may attach routes to them. A route (HTTPRoute, GRPCRoute, TLSRoute and the TCP and UDP routes in the experimental channel) names parent Gateways, match conditions, filters and backends. Filters are typed: request header modification, redirects, URL rewrites, request mirroring, and extensions that implementations may add by reference. Backends can carry weights, which gives portable canary and blue-green traffic splitting with no annotation at all. A ReferenceGrant is required whenever something in one namespace points at a Secret or a Service in another, which closes the loophole where an application team could point at another team's certificate. Status is a first-class part of the API: each object reports accepted, programmed and resolved-references conditions, and each parent reference has its own status per route, so a route's failure to attach is visible on the route instead of in a controller log.

**Controllers and their shape.** Most implementations are Envoy-based (Envoy Gateway, Contour, Istio's Gateway mode, Cilium's gateway and Ingress support), NGINX-based (the NGINX Gateway Fabric), or cloud-vendor managed. Cilium is a useful example of a design with a different data path [src: cilium-docs c747f99a0425e33b]: it implements both Ingress and Gateway API by deploying Envoy as a shared proxy that is steered by eBPF, so traffic to a Service created for a Gateway is redirected into the proxy at the node, preserving source identity for policy and for Hubble visibility. The documentation highlights that, because the proxy is part of the networking layer, ordinary network policy applies to traffic that goes through it, with the identity of the sender being the external world at the proxy's edge and the identity of the proxy at the backend side [src: cilium-docs da6942b882007500]. Whichever controller you pick, check three things: which GatewayClass it provides, which route types and filters it passes the conformance tests for, and how it obtains an external address (a LoadBalancer Service, a hostNetwork port, or a cloud integration).

**Certificates.** Both APIs reference a Secret of type kubernetes.io/tls. In practice the Secret is created and renewed by cert-manager, which has a controller for Ingress annotations and also integrates with the Gateway listener resource. The failure modes are the same in both APIs: a Secret in the wrong namespace, a certificate that does not contain the host name, an ACME challenge that cannot reach the cluster, and expired certificates.

**Migration tooling.** The ingress2gateway tool reads Ingress objects and provider-specific annotations and produces Gateway and HTTPRoute manifests. The Cilium documentation lists, annotation by annotation, which settings map to which filters in the new API and which have no equivalent yet [src: cilium-docs e524f860c14d553a]. Expect the tool to cover host, path and TLS but leave annotations such as rate limits, authentication callouts, custom snippets, and body-size limits for hand conversion, often through implementation-specific policy resources.

## Assessment: the good, the bad and the ugly

**The good.** The Gateway API gives a typed, portable, role-aware model. A platform team can own the Gateway and the certificates while application teams own their routes and cannot interfere with each other beyond what a listener allows. Weighted backends and header-based matching make canary releases a first-class feature. Status conditions make failures observable from the API. Conformance tests make it possible to switch implementation with some confidence. Ingress, for its part, remains very simple for simple needs, has a decade of tooling and documentation, and is supported by every serious controller.

**The bad.** The Gateway API is a bigger surface: more objects, a channel system (standard and experimental) that determines which CRDs to install, and version skew between the CRDs and the controller that can bite at upgrade time. Features that people rely on in annotations (authentication, rate limiting, WAF rules, custom Lua or snippets) are still outside the core API and appear as implementation-specific policy attachments, which reintroduces some non-portability. Documentation quality varies by implementation, and the conformance report of a controller needs reading, because "supports Gateway API" can mean standard-channel HTTP only. For Ingress, the problems are the ones already described: annotations, the lack of any role separation, and a frozen API.

**The ugly.** The worst failures involve silent partial acceptance. An HTTPRoute can be valid for the API server and still attach to nothing because the parent reference names the wrong Gateway, the listener's allowed-routes rule excludes the namespace, the host name does not match any listener, or a ReferenceGrant is missing. A second class is configuration injection: with Ingress, the snippet-style annotations of one popular controller let any user with permission to edit an Ingress inject arbitrary proxy configuration, which led to well-publicised vulnerabilities and a policy of disabling snippets by default. A third is the single point of failure: all north-south traffic goes through a few proxy Pods, so their resource limits, their rollout strategy, their PodDisruptionBudget and their connection draining behaviour decide how a cluster upgrade feels to users.

## Applications beyond this domain

The pattern of stating the intent in an object while a controller configures a proxy is the same one used by cloud application load balancers, API gateways and service meshes, and the Gateway API is explicitly designed to cover the mesh use case as well (the GAMMA initiative attaches routes to Services for east-west traffic). The persona model resembles the split between network engineers and developers in an enterprise: it encodes in an API who is allowed to change which part. Even outside Kubernetes, the weighted-route and header-match vocabulary is useful as a neutral way of writing canary rules for any proxy.

## Examples

A first example is the smallest useful Ingress: one host, two paths and a TLS Secret, backed by two Services. The administrator verifies it by checking the class, then the controller's Service for an external address, then resolving the host name to that address, and finally sending a request with the host header from a machine that cannot resolve the name yet. Each step isolates a layer: the API object, the controller's reconciliation, DNS, and the proxy's routing.

A second example is the same routing in the Gateway API. A platform team creates a Gateway with an HTTPS listener for a wildcard host and permits routes from namespaces carrying a particular label. An application team creates an HTTPRoute in its own namespace that names the Gateway, matches a host and a path prefix, and splits traffic ninety to ten between two versions of a Service. If the route's status shows no accepted condition, the team reads the reason on the parent reference: not allowed by the listener, a missing grant, or no matching listener.

A third example is a migration plan for a cluster that uses annotation-heavy Ingress objects. The plan lists every annotation in use across all Ingress objects, classifies each as translatable, policy-based or unsupported, installs the new controller beside the old one with a different class and a different external address, converts and tests one low-risk host, moves DNS with a short time to live, and keeps the old controller until logs show no traffic. The rollback is a DNS change, which is why the short time to live is set before the move.

## Related problems and ideas

Ingress and Gateway interact with several other topics. Certificate automation connects to the supply-chain and security themes of the security course. NetworkPolicy has to allow traffic from the proxy to the backends, and the identity of the proxy depends on the controller, which is why policy and ingress are designed together (T07). Service meshes (T09) take over the L7 role for east-west traffic and often provide their own ingress gateway built on the same API. Load balancer addresses on bare metal come from MetalLB or a BGP speaker (T10). Finally, DNS records for the entry point are usually automated by external-dns watching the same objects.

A distinct idea worth teaching is the difference between the L7 hop and the L4 hop. HTTP routing decisions belong in the proxy, but TCP and TLS passthrough routes are simpler and cheaper and sometimes preferable when the application terminates its own TLS or uses a protocol the proxy does not understand. The Gateway API's TLSRoute and TCPRoute exist for exactly that case, although both are on a slower track than HTTPRoute.

## Active research

Work in progress in the Gateway API community includes a more complete mesh story, standard policy attachment for timeouts, retries and authentication, native support for inference and AI-gateway traffic, multi-cluster gateways, and better tooling for conformance profiles and for migration from Ingress. Several implementations are exploring proxyless or ambient designs where the gateway role is split across a per-node component and a per-namespace waypoint. The exact graduation status of each feature changes with each release, so treat any statement about a feature being stable as "to verify" until checked against the current release notes.

## Future direction

Expect the Gateway API to become the default way of exposing HTTP and gRPC services, with Ingress surviving as a legacy interface that is read by tools and supported for years. Administrators should plan for three durable tasks: inventory what their controllers do beyond the plain API, learn the status conditions that explain why a route is not live, and treat the controller as a lifecycle-managed dependency with a tested replacement path.
