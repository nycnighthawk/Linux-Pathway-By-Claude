# Building a container network by hand: namespaces, veth pairs, a bridge and NAT

## Define the problem

A container is a process that believes it owns a machine. For networking, that belief means it has its own interfaces, its own addresses, its own routing table, its own firewall rules and its own set of listening ports, separate from the host and from every other container. Yet the process must still be able to reach the outside world, other containers must be able to reach it, and the host administrator must be able to publish selected ports from the outside. A container runtime therefore has to create an isolated network environment out of kernel parts and connect it, safely and quickly, to everything else.

Failure of this plumbing is the single most common class of container problem: a container that cannot resolve names, a published port that answers on localhost and nowhere else, two containers with the same address on the same bridge, traffic that leaves but never returns because no one translated the address, and mysterious drops because forwarding is disabled or a host firewall rule sits in the way. Anyone who has to debug container or Kubernetes networking needs to be able to rebuild what the runtime builds, because every higher-level scheme (Docker's default bridge, the CNI bridge plugin, the node side of most Kubernetes network plugins) is a variation on the same few primitives.

This slice builds that foundation with iproute2 and nftables and no runtime at all: network namespaces as the isolation unit, virtual ethernet pairs as the cables, a Linux bridge as the switch, addressing and routing inside the namespaces, source NAT for outbound traffic, destination NAT for published ports, and the verification and tear-down steps. It stays at the node level; connecting nodes into one cluster network (overlays, routing, plugins) is the following slices.

## History and approaches

Early Linux isolation had no network dimension. The chroot of the 1980s limited file views, and Linux-VServer and OpenVZ in the 2000s partitioned processes while sharing one network stack, so containers saw the host's interfaces and ports and had to be given distinct addresses by aliasing. Network namespaces arrived in the kernel in 2.6.24 (2008), after the other namespace types, as the piece that gave a process group a private network stack. `ip netns` made them convenient to name and enter; veth pairs, added around the same time, provided the cable between a private stack and the rest of the world; the Linux bridge, older than both, served as the switch. LXC combined these in 2008, and the Arch Wiki's page for systemd-nspawn and the manual page of the LXC configuration show how those tools still express the options: a container may share the host network, get a virtual ethernet pair attached to a bridge, get a macvlan interface on a physical NIC, or get a dedicated interface moved into its namespace.

Docker, introduced in 2013, popularised the default arrangement: a bridge on the host (docker0), one veth pair per container with one end in the container namespace and one on the bridge, a private subnet, masquerading for outbound traffic and iptables DNAT rules for published ports. Its documentation for rootless mode illustrates the price of removing privilege: without the ability to create bridges and manipulate host firewall rules, a rootless daemon needs user-space networking helpers (such as slirp4netns or pasta), and its troubleshooting notes list networking errors that arise from them. Swarm mode added overlay networks on top, with a distinct set of concepts (ingress, overlay and bridge networks) described in the Docker documentation. Kubernetes took a different decision: instead of embedding a network implementation in the runtime, it defined a model, in which every pod gets its own address, pods can reach each other without translation, and agents on a node can reach the pods on it, and delegated the implementation to plugins using the container network interface.

Alternatives and refinements appeared. Macvlan and ipvlan give containers addresses directly on the physical network without a bridge; they offer less overhead and no NAT, at the cost of switch port security issues and no host-to-container reachability by default. Tap devices connect microVMs and virtual machines in the same way veth connects containers, as the Firecracker documentation shows for its clone networking, and KubeVirt documents interface types for virtual machines with the same bridging ideas. Userspace stacks (gVisor's netstack, slirp) avoid kernel plumbing entirely. SR-IOV and DPDK bypass the kernel for performance. eBPF replaced parts of the bridge, iptables and NAT path with programs attached to veth and tc hooks, which Cilium's introductory documentation on its eBPF datapath explains.

The common lesson: a container network consists of five replaceable elements, which are isolation (namespace), connection (veth, macvlan, tap), switching (bridge or routing), addressing (IPAM) and reachability policy (NAT and filtering). Frameworks differ in which they choose; the elements remain.

## Current state

**Network namespaces.** A namespace has its own interfaces, addresses, routes, neighbour table, firewall tables, sockets and `/proc/net`, plus its own loopback, which starts down. `ip netns add NAME` creates a persistent one (a bind mount under `/run/netns`); `ip netns exec NAME COMMAND` runs a process inside; `ip netns del` removes the name, and the namespace vanishes when no process or mount holds it. Container runtimes create anonymous namespaces for the container's init process and bind mount them so that they persist; this is how a CNI plugin receives a path such as `/proc/PID/ns/net`.

**Virtual ethernet pairs.** `ip link add veth-a type veth peer name veth-b` creates two interfaces that behave as the ends of a cable: whatever enters one comes out of the other. `ip link set veth-b netns NAME` moves one end into the namespace. The end left in the host namespace is then attached to a bridge or given an address of its own. The pair is the unit of connection: one pair per container.

**The bridge.** A Linux bridge is a software switch. `ip link add br0 type bridge` creates it; `ip link set veth-a master br0` attaches a port; MAC learning and flooding work as on hardware. Giving the bridge an address (`ip addr add 10.10.0.1/24 dev br0`) makes the host a participant in the subnet and the default gateway for the containers. Options such as STP, VLAN filtering and `bridge-nf-call-iptables` affect behaviour; the last is important for Kubernetes because it makes bridged traffic visible to iptables, which needs the `br_netfilter` module.

**Addressing and routes.** Inside the namespace, bring up loopback and the veth end, assign an address from the bridge's subnet, and set the default route via the bridge address: `ip -n NAME addr add 10.10.0.2/24 dev eth0`, `ip -n NAME link set eth0 up`, `ip -n NAME route add default via 10.10.0.1`. Static assignment is acceptable by hand; runtimes use an IP address management (IPAM) component that reserves addresses from a pool and records them, which is what CNI IPAM plugins do.

**Forwarding and NAT.** For traffic from containers to the outside, the host must route between the bridge and the uplink: `sysctl -w net.ipv4.ip_forward=1`. The container addresses are private, so source NAT is needed: a masquerade rule in the `postrouting` hook rewrites the source address to the uplink's. With nftables this is a table of family `ip`, a chain of type `nat` at the postrouting hook, and a rule that masquerades packets from the container subnet leaving through anything other than the bridge. Connection tracking records the translation so that return packets are mapped back. For inbound traffic to a published port, a destination NAT rule in the prerouting hook (and output hook for locally generated traffic) rewrites the destination address and port to the container's, and the forward chain must allow it. The documentation in the Kubernetes network debugging guides shows these rules from the other direction, in the context of kube-proxy.

**Filtering.** Isolation between containers on one bridge is absent by default: they share a layer-2 segment and can talk freely. Rules in the forward chain, or separate bridges per network, restrict this. The host firewall frequently interferes: a default drop policy in forward, a firewall service that is unaware of the new bridge, and the interaction of two rule managers are the typical sources of the maddening state where every setting looks right and still nothing flows.

**Verification and tools.** `ip -br addr`, `ip route`, `bridge link`, `bridge fdb show`, `ip -n NAME addr` and `ip -n NAME route` show state. `ping` and `curl` from inside the namespace test reachability layer by layer: gateway, host uplink address, an external address, a name. `tcpdump -ni br0` and on each veth end locates where packets disappear. `nft list ruleset` and `conntrack -L` show translations. `ip netns identify` and `lsns -t net` map processes to namespaces. The Kubernetes debugging guides for Services and for Windows nodes include the same ladder of tests applied to cluster networking, such as the edge case where a pod cannot reach itself through its own Service address because of hairpin handling on the bridge.

**From manual to runtime.** What a runtime does at container start is exactly the sequence above, in order: create the namespace, create a veth pair, move one end, attach the other to a bridge, assign the address from IPAM, add the default route, add NAT or firewall rules, record the result. When the container stops it undoes them. In Kubernetes, the kubelet asks the runtime to create the pod sandbox, and the runtime invokes the CNI plugin chain to do this plumbing (T02).

## Assessment: the good, the bad and the ugly

The good: the primitives are simple, orthogonal and fast. They are in every Linux kernel, observable with standard tools, and they compose: the same bridge can serve containers, virtual machines through tap devices and nspawn containers. Knowing them removes the mystery from higher layers, since each plugin or runtime can be understood as a choice among these elements.

The bad: the bridge-plus-NAT model has structural limits. NAT hides container addresses, which breaks protocols that embed addresses, complicates logging (the source seen by a server is the host) and makes inbound connections to containers on other hosts impossible without port publishing. One bridge per host means containers on different hosts cannot talk, so a multi-host design needs overlays or routing. Published ports consume a shared port space on the host and require NAT rules that scale poorly as their count grows. The performance cost of the bridge, netfilter and conntrack path is real at high packet rates, and conntrack tables can fill.

The ugly: interaction with other rule managers. Docker, firewalld, ufw, libvirt and Kubernetes all write netfilter rules, and each assumes it owns the chains it creates. Restarting one may flush another's rules; an administrator's default drop policy in forward silently breaks containers; IPv6 gets missed, so a container has an address but no route. The `br_netfilter` setting leads to surprises when enabled or disabled. Overlapping subnets between a container network and a corporate VPN produce unreachable hosts. Rootless runtimes lose features: the Docker rootless notes explain networking errors and limits (no source address preservation, restricted ports below 1024, ICMP limitations). And hairpin cases, where a container reaches its own published port through the host address, fail or succeed depending on kernel flags.

Mitigations: pick one rule manager and document it; give each network a separate private subnet that does not overlap anything routable in your organisation; set forwarding and bridge sysctls in persistent configuration, not by hand; use named nftables tables owned by one tool; monitor conntrack usage; prefer routing or an eBPF dataplane when scale or source-address preservation matters.

## Applications beyond this domain

The same pieces appear in any virtual networking: libvirt's default NAT network for virtual machines is a bridge with dnsmasq and masquerade rules, as the enterprise virtualisation course shows; Firecracker's tap devices and clone networking follow the same pattern; test labs for network engineers use namespaces and veth pairs to emulate topologies without hardware (the approach of tools like Mininet and containerlab). Home routers are bridge, NAT and DHCP on an embedded Linux. The conceptual split into isolation, connection, switching, addressing and policy is a general model of network virtualisation, visible in OVN's architecture with logical switches and routers, in cloud virtual private networks and in the Windows container network modes that the Kubernetes documentation describes with their own names for the same functions.

## Examples

A complete manual network, run as root. Create a bridge named `lab0` with the address 10.10.0.1/24. Create two namespaces, `c1` and `c2`. For each, create a veth pair, move one end into the namespace and name it `eth0`, attach the other end to `lab0`, assign 10.10.0.2/24 and 10.10.0.3/24, bring everything up and set the default route to 10.10.0.1. From `c1`, ping the gateway, `c2` and the host's uplink address. Enable forwarding, add a masquerade rule for 10.10.0.0/24, and ping an external address from `c1`. Finally add a DNAT rule from host port 8080 to 10.10.0.2:80, start a listener in `c1` and fetch it from the host and from another machine.

A failing example: the pings between `c1` and `c2` work but `c1` cannot reach the Internet. The forward chain's policy is drop; the masquerade rule is present and counts no packets. Adding accept rules for traffic to and from the bridge fixes it. Reading the counters on each rule, not just the rule list, is the habit that locates such faults.

A second failing example: a published port answers from other machines but not from the host itself. The rule exists only in the prerouting hook, which does not see locally generated traffic. Adding the same translation to the output hook, or reaching the container through the bridge address, fixes it.

A third: two containers started by different tools both get 10.10.0.2 because each tool allocates from its own pool on the same bridge. The symptom is intermittent connectivity as the neighbour cache flips between MAC addresses. A single IPAM per bridge is the cure.

## Related problems and ideas

Macvlan and ipvlan networks give containers addresses on the physical network directly. Host networking removes isolation for speed. Rootless and unprivileged networking with pasta or slirp4netns trades performance for safety. User-space and unikernel stacks avoid the host stack. Source-based routing and policy routing allow multi-homed containers. Alternative filtering mechanisms (nftables sets and maps, eBPF with tc) reduce rule counts. Not mainstream yet are fully routed container networks with no bridge and no NAT at all, where each container's address is advertised by BGP from the host, a design that Calico and Cilium implement and the later slices on BGP cover.

## Active research

Work in the community covers faster veth paths (the eBPF host-routing optimisations that skip the bridge and netfilter), netkit, a kernel device designed as a faster successor to veth for containers, better unprivileged networking for rootless containers, and the migration from iptables to nftables as the kernel's preferred firewall interface. Researchers compare the overheads of namespaces, bridges and conntrack in microbenchmarks and in cloud-scale traces, and study the safety of the many concurrent writers to netfilter. How to give each container a network with strong isolation by default, without a performance penalty, is still open (to verify the stage of netkit and related features in your kernel).

## Future direction

Expect the plumbing described here to stay as the foundation, hidden under better tools: more of it moves into eBPF programs, more installations use nftables only and rootless networking improves. For administrators the durable skill is the ability to rebuild a container network by hand and to read each layer's state, because any higher-level plugin eventually reduces to it. Practice with namespaces in a disposable VM before debugging a real node.
