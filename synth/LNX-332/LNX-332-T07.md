# KVM internals: reading the exit path, changing it, and measuring the result

## Define the problem

To extend or fix a hypervisor you must know what happens between the moment a guest instruction faults and the moment the guest resumes. Where does an exit land in `kvm.ko`? Which handler runs? Which exits go to user space? When a guest is slow, the cause is rarely a single bug but an exit-heavy workload; to see it you need counters, traces and a way to rebuild a modified module and test it safely on a development host.

## History and approaches

KVM began as a small module with a hand-written x86 emulator and a shadow MMU. Over the years the code was split into generic parts (`virt/kvm`: VM and vCPU lifecycle, memslots, eventfds, the ioctl dispatcher) and architecture parts (`arch/x86/kvm`, `arch/arm64/kvm`, and others), and the x86 vendor modules (`kvm-intel` and `kvm-amd`) separated from the common `kvm` module. Debugging tools followed the code: first counters exported in debugfs (`/sys/kernel/debug/kvm`), then the `kvm_stat` script, tracepoints for every exit and entry, and `perf kvm` to record and report them. Developers learned that exit statistics, not CPU profiles of the guest, usually reveal virtualisation overhead, and that per-reason latency distributions matter more than averages.

## Current state

### The exit path

On x86 Intel, after the guest exits, the vendor module (`vmx.c`) reads the exit reason and dispatches through a table of handlers (for example for `CPUID`, `MSR_WRITE`, `EPT_VIOLATION`, `IO_INSTRUCTION`, `HLT`). Handlers either complete the work in the kernel (and the loop re-enters the guest immediately) or return a code telling the generic `KVM_RUN` ioctl to go back to user space with a populated `kvm_run`. The memory-management part handles nested-page faults (the MMU document in the kernel tree describes it), and emulation of instructions that the hardware cannot restart is done by an in-kernel x86 emulator.

### Building a modified module

On a development machine: install the kernel build tree matching the running kernel, change files under `arch/x86/kvm` or `virt/kvm`, build the modules only (`make M=arch/x86/kvm modules` against the tree, or a full tree build), unload the old modules (`rmmod kvm_intel kvm`), and load the new ones. Because the modules are tied to exact kernel symbols and configuration, a mismatch fails at load with a version or symbol error. A development workflow uses a nested guest or a spare machine, since a bug can crash the host.

### Observing exits

- **Counters**: `/sys/kernel/debug/kvm/*` and the `kvm_stat` tool (live or logged) count exits by reason.
- **Tracepoints**: the `kvm:` events (`kvm_exit`, `kvm_entry`, `kvm_mmio`, `kvm_pio`, `kvm_msr`, `kvm_apic`, `kvm_pv_eoi`) can be read through `trace-cmd`, `perf record -e` or `bpftrace`.
- **perf kvm**: `perf kvm stat record` followed by `perf kvm stat report` summarises exits by reason with count, share and time (min, max, mean). The report names the reason, so a dominant `EPT_VIOLATION`, `IO_INSTRUCTION` or `MSR_WRITE` line is readable at once. Time spent in `HLT` is guest idle time, not overhead, and has to be excluded from conclusions.

### Reading the numbers

The step after "which exit?" is "why?" An `EPT_VIOLATION` storm suggests page-by-page faulting or a small page size; use huge pages or pre-fault memory. High `IO_INSTRUCTION` or MMIO exits suggest an emulated device on a hot path; use paravirtual devices, ioeventfd or in-kernel back ends. Many `MSR_WRITE` exits to APIC registers suggest missing interrupt virtualisation features or timer programming; check the host's enabled features. A high `EXTERNAL_INTERRUPT` rate points at host interrupts landing on guest CPUs; pin them elsewhere.

### The pattern

Count, rank by time, exclude idle, find the cause for the top reason, change one thing, count again.

## Assessment: the good, the bad and the ugly

**The good.** Tracepoints cover every exit with low overhead when disabled; `perf kvm` gives a quick, comparable summary; the modular structure allows building and testing a change in minutes.

**The bad.** Exit reasons are architecture specific, the names differ between vendors, and tools lag new hardware. Tracing itself perturbs timing for high-rate exits. Kernel-module changes need an exact matching tree.

**The ugly.** Nested virtualisation changes what an exit means and doubles trace volume. A change in a hot path can pass tests and regress throughput by a few percent. Interface stability for user space is strict, but internal functions move between releases and out-of-tree patches rot quickly.

## Applications beyond this domain

- **Profiling other privilege boundaries**: the same trace-and-rank method applies to system calls, interrupts and hypercalls.
- **Cloud capacity analysis** uses exit counts to size noisy tenants.
- **Real-time tuning** looks for exits as latency sources.
- **Security monitoring** watches for unusual exit patterns.
- **Teaching**: reading the handler table is the quickest way to learn what the hardware reports.

## Examples

**An idle guest.** A report that shows `HLT` as the largest time share for an idle guest is correct and uninteresting.

**A slow database guest.** `IO_INSTRUCTION` leads by time after excluding `HLT`; the cause is a legacy IDE controller. Switching to virtio-blk with an ioeventfd removes most of those exits.

**A failing one.** A patch to a handler compiles but the module refuses to load: the module was built against a different kernel configuration, and `modprobe` reports a version-magic mismatch.

## Active research

Open areas include low-overhead continuous exit profiling in production, automatic attribution of exits to guest code, models predicting the cost of exits on new hardware, and verified, minimal hypervisor kernels (to verify the state of each).

## Future direction

Expect a steady move of hot exits out of the kernel into hardware, exposure of per-exit latency histograms through eBPF by default, and per-guest accounting that is stable across kernel versions.
