# KVM internals: reading the exit path, changing it, and measuring the result

## Define the problem

Anyone who wants to extend or fix a hypervisor must be able to answer a precise question: what happens between the moment a guest instruction faults and the moment the guest resumes? Where in the `kvm` module does that exit land? Which handler runs? Which exits go on to user space and which end in the kernel? The question matters in practice because a slow guest rarely has a single bug to blame. More often it has a workload that causes a great many exits of one kind, and the cure lies in understanding which kind, why, and how to make it rarer or cheaper.

To answer that, a developer needs three skills at once. The first is reading the source with a map of the structure in mind. The second is building a changed module and loading it on a machine where a crash will not be a disaster. The third is measuring: counters, traces and summaries that show where time goes. This essay develops them in that order, from the structure of the code, through the tools that grew around it, to a method for turning numbers into a decision.

## History and approaches

### A small module with its own emulator

KVM began as a compact module with a hand-written x86 instruction emulator and a *shadow* MMU that kept private copies of guest page tables. Everything lived in a few files, and a reader could hold the whole design in mind. As the project grew to support more architectures and more hardware features, the code was split. Generic parts moved to `virt/kvm`: the lifecycle of VMs and vCPUs, memory slots, eventfd plumbing, and the dispatcher for the ioctl interface. Architecture parts went to directories such as `arch/x86/kvm` and `arch/arm64/kvm`. On x86 the vendor-specific code separated into `kvm-intel` and `kvm-amd`, loaded on top of the common `kvm` module.

### Tools follow the code

Observability grew in the same order as the structure. Counters, exported through debugfs under `/sys/kernel/debug/kvm`, came first and were easy to read. A script, `kvm_stat`, then collected and formatted them. Tracepoints followed for every exit and entry, which made it possible to see the sequence of events and not only the totals. Finally `perf kvm` packaged the tracepoints into a record-and-report workflow, and made them comparable across runs. Developers who worked this way learned two lessons that still hold. First, the exit statistics, not a CPU profile of the guest, usually reveal virtualisation overhead. Second, per-reason latency distributions matter more than averages, because a rare slow exit can ruin tail latency while leaving the mean looking healthy.

## Current state

### The exit path

On Intel hardware, once the guest exits, the vendor code in `vmx.c` reads the exit reason and dispatches through a table of handlers, one per reason: `CPUID`, an MSR write, an EPT violation, an I/O instruction, `HLT`, and many others. A handler has two choices. It can finish the work in the kernel, in which case the loop re-enters the guest at once. Or it can return a code that tells the generic `KVM_RUN` ioctl to leave to user space with the `kvm_run` structure filled in. The memory-management side handles nested-page faults; the kernel documentation describes how it tracks and fills the second translation layer. Instructions that the hardware cannot restart by itself, such as some forms of I/O and memory-mapped access, go to an in-kernel x86 emulator that decodes and performs them.

### Building a modified module

The workflow on a development machine is concrete. Install the kernel source or build tree that matches the running kernel; change files under `arch/x86/kvm` or `virt/kvm`; build only the module directory, or a full tree if you prefer; unload the old modules (`rmmod kvm_intel kvm`, in that order) and load the new ones. The module is tied to the exact symbols and configuration of its kernel, so a mismatch fails at load with a version or symbol error, which is a safeguard and also a frequent annoyance. Experienced developers do this work inside a nested guest or on a spare machine, because a bug in a hypervisor can bring down the host.

### Observing exits

Three tools work in layers.

- **Counters.** The files under `/sys/kernel/debug/kvm` and the `kvm_stat` tool, run live or logged to a file, count exits by reason and show the rate.
- **Tracepoints.** The `kvm:` events (`kvm_exit`, `kvm_entry`, `kvm_mmio`, `kvm_pio`, `kvm_msr`, `kvm_apic`, and others) can be recorded with `trace-cmd`, with `perf record -e`, or from `bpftrace`. These show the sequence, and the details of each event.
- **perf kvm.** `perf kvm stat record` collects the exits while a workload runs, and `perf kvm stat report` summarises them by reason with count, share of events, share of time, and minimum, maximum and mean latency. Because the report names the reason, a line for `EPT_VIOLATION`, `IO_INSTRUCTION` or `MSR_WRITE` that dominates is readable at once. One caution: time spent in `HLT` means the guest was idle, which is not overhead, and conclusions must exclude it.

### Reading the numbers

The step after "which exit dominates?" is "why?", and the answers follow patterns.

- A storm of `EPT_VIOLATION` events suggests that memory is being faulted in page by page, or that small pages are making the second layer expensive. Huge pages or pre-faulting guest memory usually helps.
- High `IO_INSTRUCTION` or MMIO exit rates suggest an emulated device on a hot path. The cure is a paravirtual device, an `ioeventfd`, or an in-kernel back end.
- Many `MSR_WRITE` exits that target interrupt-controller or timer registers suggest that interrupt virtualisation is off or unavailable, or that the guest reprograms its timer constantly. Check which features the host has enabled (the next-but-one topic's subject).
- A high `EXTERNAL_INTERRUPT` rate means host interrupts are landing on CPUs that run guests. Pin them to other CPUs.

### The generalised pattern

The method is the same in each case: count, rank by time, exclude idle, find the cause of the top reason, change one thing, and count again. It is the ordinary discipline of performance work, applied to a boundary where the "function calls" are exits.

## Assessment: the good, the bad and the ugly

**The good.** Tracepoints cover every exit and cost very little when disabled. `perf kvm` gives a quick, comparable summary. The modular structure means a change can be built and tested in minutes, which makes experiments cheap.

**The bad.** Exit reasons are architecture specific and the names differ between vendors, and the tools lag new hardware, so a report on a fresh processor may show unnamed reasons. Tracing perturbs timing when exits are very frequent, so a trace can slow the workload enough to change the result. Kernel-module changes require an exactly matching tree and configuration.

**The ugly.** Nested virtualisation changes what an exit means: an exit seen by the outer hypervisor may be an emulated exit of the inner one, and trace volume roughly doubles. A change to a hot path can pass every functional test yet regress throughput by a few percent, a loss that only a careful benchmark shows. The interface to user space is held stable, but internal functions move between releases, so out-of-tree patches rot quickly and must be rebased with each kernel.

## Applications beyond this domain

- **Profiling other privilege boundaries.** The trace-and-rank method applies to system calls, interrupts and hypercalls in exactly the same way.
- **Cloud capacity analysis.** Operators use exit counts to find noisy tenants and to size hosts.
- **Real-time tuning.** Latency-sensitive guests look for exits as the source of jitter.
- **Security monitoring.** Unusual exit patterns, such as a burst of a rarely used reason, can indicate probing.
- **Teaching.** Reading the handler table is the quickest way to learn what the hardware reports, because each row is one architectural event.

## Examples

**An idle guest.** A guest that does nothing shows `HLT` as the largest share of time. That report is correct and uninteresting, and it demonstrates why idle must be excluded before any conclusion is drawn.

**A slow database guest, step by step.** A database inside a guest runs at half the speed of the same workload on bare metal. `perf kvm stat report` shows, after excluding `HLT`, that `IO_INSTRUCTION` leads by time, with thousands of exits per second to one port range. A look at the guest's device list shows a legacy IDE controller. Switching the disk to virtio-blk with an `ioeventfd` cuts the exit count by two orders of magnitude, and a re-run of the report shows `IO_INSTRUCTION` gone from the top. The method is the whole story: measure, identify, change one thing, measure again.

**A failing one.** A patch to a handler compiles cleanly, but the module refuses to load: `modprobe` reports a version-magic mismatch. The module was built against a different kernel configuration from the one that is running. The cure is to rebuild against the exact tree, not to force the load.

## Related problems and ideas

### Related

- **Hardware virtualization** (the first topic) defines the exits listed here.
- **Performance regressions** in the kernel pathway give the general method of sampling and bisection.
- **Tracing with ftrace and perf** in the earlier kernel course explains the tracepoint mechanism that `perf kvm` uses.
- **Interrupt and timer virtualisation** (a later topic) removes many of the exits found here.

### Opposing approaches

- **Guest-side profiling** takes the view that a hypervisor's costs show up as guest slowness and can be found by profiling the guest, with no trace of the host. It works for gross problems and fails for exit-heavy ones, because the guest cannot see the time it was not running.
- **Black-box benchmarking** compares whole-workload throughput between configurations without looking at exits. It is cheap and yields the number that matters to the customer, but it cannot say *why*, so it guides decisions less well than the exit report.
- **Microkernel and verified hypervisors** avoid the need for deep module debugging by making the core small enough to reason about. The price is a narrower feature set, and the performance questions return as soon as a device model is added.

## Active research

Open areas include low-overhead continuous exit profiling that is safe to leave on in production, automatic attribution of exits to the guest code that caused them, models that predict the cost of exits on new processors before they ship, and verified minimal hypervisor kernels. For each, current status should be checked against recent conference papers and the kernel mailing lists.

## Future direction

Expect a steady move of hot exits out of the kernel and into hardware, so that the exits worth profiling become fewer and subtler. Expect per-exit latency histograms exposed through eBPF as a matter of course, and per-guest accounting that stays stable across kernel versions. For the learner, the lasting skill is the method, since the names of exit reasons will change faster than the logic of measuring them.
