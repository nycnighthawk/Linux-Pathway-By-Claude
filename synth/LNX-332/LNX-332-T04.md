# Virtio: a standard way for a guest to talk to a virtual device

## Define the problem

Emulating a real network card or disk controller register by register works, but it is slow (each register access is an exit) and every guest needs a driver for the specific model. For a virtual device nobody needs to pretend: what is wanted is a fast, simple channel to move buffers between guest and host, with few exits, one driver per device class, and an interface that any hypervisor can implement.

## History and approaches

Early virtual hardware imitated real cards (an Intel e1000 network card, an IDE disk), which was compatible and slow. Xen's split-driver model used shared rings with an event channel. Rusty Russell proposed virtio (2008) as a common, hypervisor-neutral version of the same idea; Linux drivers for it appeared in 2.6.25. The specification was moved to OASIS, where version 1.0 (2016) fixed the little-endian layout and added the modern PCI transport; later versions added the packed ring, more transports and feature bits. The pattern that won: one small queue abstraction, a feature negotiation, and several transports (PCI, MMIO, channel I/O) carrying the same device types (net, block, console, vsock, filesystem, GPU and others).

## Current state

### Layers

A virtio device has a **transport** (how the guest finds it and signals it: a PCI function with capabilities, or a memory-mapped register window described in the device tree), a **device status** handshake (acknowledge, driver, features OK, driver OK), **feature bits** negotiated by both sides, a **device-specific configuration** area, and one or more **virtqueues** that carry data.

### The split virtqueue

A split virtqueue has three areas in guest memory, each an array of a size that is a power of two:

- the **descriptor table**: entries of address, length, flags and a next index; flags mark a buffer as chained (`NEXT`) and as device-writable (`WRITE`). A request is a chain: for a block read, a header the device reads, a data buffer the device writes, a status byte the device writes.
- the **available ring**: the driver puts the head index of each chain there and bumps a free-running 16-bit index.
- the **used ring**: the device puts the head index and the number of bytes it wrote, and bumps its own index.

The device keeps the last available index it saw; when the driver's index moves, it consumes the new entries, follows each chain, does the work, writes the used element and optionally interrupts the driver. Both sides use memory barriers where the specification requires them. Notification suppression flags (or event index fields) let each side tell the other it does not need to be signalled for every buffer, which cuts exits and interrupts.

### Indirect descriptors and the packed ring

Indirect descriptors allow a chain to live in a separate table, so a big request uses one slot. The packed ring (a feature) merges the three areas into one, with flags that mark descriptors available and used, for better cache behaviour.

### A back end in a VMM

The VMM maps the queue addresses (taken from the transport registers) through its guest-memory model, registers an eventfd for the guest's notification (an `ioeventfd` bound to the notify address) and one for interrupts (an `irqfd`), and runs a loop: wait for the eventfd, drain available chains, process, publish used entries, signal. All pointer values come from the guest and must be validated: bounds, loops in `next` chains, lengths, ring indices.

### The pattern

A shared ring of buffer descriptors plus two cheap notifications; negotiate features, then keep both sides lock-free. The same shape appears in `io_uring`, NVMe queues and many NIC rings.

## Assessment: the good, the bad and the ugly

**The good.** One driver family serves every hypervisor that implements the spec; throughput is high because the guest batches work and exits are rare; devices are simple to write.

**The bad.** The specification is large, with many optional features and transports; a back end must handle old drivers that skip features. Debugging needs a view into guest memory. Zero-copy and ordering rules (barriers) are easy to get wrong.

**The ugly.** The guest controls every number the device reads. Back-end bugs (a descriptor loop, a length that points outside RAM, an index that jumps) are the classic route from a malicious guest to the host. Hence validation, fuzzing and moving back ends into separate processes.

## Applications beyond this domain

- **Hardware offload**: real NICs and SSDs now implement virtio for direct assignment with a standard driver.
- **Container and sandbox runtimes** use virtio-fs, vsock and block devices.
- **Other ring protocols** (NVMe, io_uring, DPDK rings) reuse the same lock-free producer-consumer design.
- **Hypervisors beyond Linux** (bhyve, Cloud Hypervisor, VirtualBox) implement the same device types.
- **Embedded systems** use virtio over shared memory between cores or partitions.

## Examples

**A block read.** The guest builds a chain: header (read-only, request type and sector), data buffer (device-writable), status byte (device-writable). It publishes the head and notifies. The device reads the sector, writes the data and a zero status, records the total length written in the used ring and interrupts.

**Notification suppression.** A network driver under load disables used-buffer interrupts and polls; the device stops raising them and exits drop.

**A failing one.** A chain whose last descriptor's `next` points back to the first: a naive loop never ends and the vCPU or I/O thread hangs. The back end must stop after at most the table size and mark the device broken. The lab does this.

## Related problems and ideas

- **Device drivers and NAPI** (kernel internals) are the guest side of the same ring idea.
- **KVM ioeventfd and irqfd** connect the queue notifications to eventfds.
- **vhost** (next topic) moves the back end into the kernel or another process.
- **Memory barriers and lock-free queues** explain the ordering rules.

## Active research

Open topics include packed-ring and in-order optimisations, virtio over hardware offload and confidential guests (where bounce buffers are needed), formal verification of back ends, and fuzzers that generate hostile descriptor chains (to verify the state of each).

## Future direction

Expect more device classes (GPU, sound, input, memory), wider hardware implementations, and back ends written in memory-safe languages and running outside the VMM.
