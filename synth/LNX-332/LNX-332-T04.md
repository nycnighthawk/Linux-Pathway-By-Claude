# Virtio: a standard way for a guest to talk to a virtual device

## Define the problem

A guest that wants a disk or a network connection needs a device to talk to. The obvious answer, and the first one, is to pretend: emulate a real network card or disk controller, register by register, so that the guest's existing driver works unchanged. That path is compatible, and it is slow. Every access to a device register is an exit to the hypervisor, and a single packet may need dozens of register reads and writes. Each guest also needs a driver for the specific model chosen, which ties the virtual hardware to the history of physical hardware that nobody needs to imitate.

What a virtual device actually needs is much simpler: a fast channel to move buffers between guest and host, with few exits, one driver per device *class* (one for networks, one for block storage) instead of one per hardware model, and an interface that any hypervisor can implement. This essay builds that idea step by step, from the problem with imitation to the ring of descriptors at the centre of the design, to the back end a VMM must write to serve it, and ends with the security questions that arise because the guest is not trusted.

## History and approaches

### Imitating real hardware

The first virtual machines presented well-known cards. Intel's e1000 network card and the old IDE disk interface were popular choices because every operating system already shipped drivers for them. The approach has one great advantage, compatibility with anything, and two large costs. The first is speed, because each register access traps. The second is complexity on the host side: the hypervisor has to reproduce the card's quirks, including bugs that drivers have learned to work around.

### Split drivers and shared rings

Xen's split-driver model, published in the early 2000s, took the opposite approach. A front-end driver in the guest and a back-end driver in a privileged domain exchange requests through shared memory rings, and an *event channel* delivers notifications. The cost per request fell sharply, because a batch of requests needs only one notification. The weakness was that the design was tied to Xen.

### A common standard

Rusty Russell proposed virtio in 2008 as a hypervisor-neutral version of the same idea, with a paper that argued for a de-facto standard for virtual I/O, and Linux drivers appeared in the kernel at about the same time. The specification was later moved to OASIS, a standards body, where version 1.0 (2016) fixed a little-endian layout and defined the modern PCI transport that replaced the earlier "legacy" interface. Later versions added the packed ring format, more transports, more device classes and more feature bits. The pattern that won is easy to state: one small queue abstraction, a feature negotiation that lets old and new implementations coexist, and several transports (PCI, memory-mapped registers described by a device tree, and channel I/O on IBM mainframes) carrying the same device types: network, block, console, vsock, file system, GPU, sound, input and more.

## Current state

### Layers of a virtio device

It helps to picture five parts. The **transport** is how the guest discovers the device and signals it: on PCI, a function with a set of vendor-specific capabilities that point at regions of registers, and on small systems, a memory-mapped window described by the device tree. A **status handshake** moves the device through steps the driver writes: acknowledge (the guest has seen it), driver (the guest has a driver for it), features OK (the feature set is agreed), driver OK (ready to run). **Feature bits** let both sides advertise what they support, and the device and driver use only the intersection. A **device-specific configuration area** holds values such as a disk's capacity or a network card's MAC address. And one or more **virtqueues** carry the data.

### The split virtqueue

The virtqueue is the heart of the design. In its original ("split") form it consists of three areas in guest memory, each an array whose length is a power of two (256 is typical).

- The **descriptor table** has one entry per buffer: a guest-physical address, a length, flags, and the index of the next descriptor in a chain. One flag marks a descriptor as chained to another (`NEXT`) and another marks a buffer the *device* may write (`WRITE`), as opposed to one it only reads. A single request is a chain. For a block read, the chain is a header the device reads (request type and sector number), a data buffer the device writes, and a one-byte status the device writes.
- The **available ring** is where the driver puts the head index of each chain it wants processed, then bumps a free-running 16-bit counter.
- The **used ring** is where the device puts the head index of each chain it has finished, with the number of bytes it wrote, then bumps its own counter.

The device remembers the last available-ring counter it saw. When the driver's counter moves, the device takes the new entries, follows each chain, does the work, writes a used entry and, unless suppressed, interrupts the guest. The two sides never take a lock: each side writes only its own ring, and ordering is enforced with memory barriers at the points the specification names. *Notification suppression*, either flags or the more precise event-index scheme, lets each side tell the other that it does not need a signal for every buffer, which reduces exits and interrupts under load.

### Two refinements

Indirect descriptors let a chain live in a separate table, so a request with many fragments uses one slot of the main table. The packed ring, defined in a later version of the specification, merges the three areas into one array in which flags on each descriptor mark it available and used. It has better cache behaviour and needs fewer writes per request, and it comes at the cost of a more intricate wrap-around rule.

### What the VMM must build

On the host side, the back end of a virtio device in a VMM performs a short routine. It reads the queue addresses from the transport's registers, maps them through its guest-memory model, registers an `ioeventfd` bound to the transport's notification address so that a guest write signals a file descriptor without an exit to user space, and registers an `irqfd` so that signalling a descriptor injects an interrupt into the guest. A loop then waits for the first descriptor, drains every new chain from the available ring, processes each, publishes the used entries, and signals the guest. Every number read from guest memory is untrusted and must be validated: that an address is inside guest RAM, that a length does not run past it, that `next` indices stay inside the table and do not loop, and that ring indices have not moved by more than the ring size.

### The generalised pattern

The structure is a shared ring of buffer descriptors plus two cheap notifications, each side owning one direction, with feature negotiation to let implementations evolve. The same shape appears in `io_uring`, in NVMe submission and completion queues, and in network card rings: wherever two parties exchange work asynchronously and want to avoid locks and per-item system calls.

## Assessment: the good, the bad and the ugly

**The good.** One guest driver family serves every hypervisor that implements the specification, so guest images are portable between hosts. Throughput is high because the guest can batch many buffers per notification, and the device side is simple enough that a basic back end takes a few hundred lines.

**The bad.** The specification is large, with many optional features and several transports, and a back end must still serve older drivers that skip features. Debugging needs a way to look into guest memory at the moment of failure. Ordering rules, and zero-copy handling in particular, are easy to get subtly wrong, and the failures appear only under load.

**The ugly.** Every number the device reads came from the guest. A back-end bug (a chain that loops, a length that points outside RAM, an index that jumps) is the classic route from a malicious guest to the host. Hence the emphasis on validation, on fuzzing, and on moving back ends into separate processes with restricted privileges, which is the subject of the next topic. A smaller irritation is that older guests use the legacy interface, so a modern device often has to offer both.

## Applications beyond this domain

- **Hardware offload.** Network cards and storage devices now implement virtio in silicon, so a guest can be given a real device that speaks the standard protocol and needs no vendor driver.
- **Container and sandbox runtimes** rely on virtio-fs for shared directories, vsock for host-guest communication and virtio block for images.
- **Other ring protocols.** NVMe queues, `io_uring` and the rings of a DPDK application use the same lock-free producer-consumer idea, and a reader who understands one reads the others easily.
- **Hypervisors beyond Linux.** bhyve, Cloud Hypervisor and VirtualBox implement the same device types, which makes guests portable among them.
- **Embedded systems** use virtio over shared memory between processor cores or partitions that cannot share a bus, and the specification's transports were designed to allow it.

## Examples

**A block read, step by step.** The guest driver wants sector 2048. It builds a chain of three descriptors: a header (device-readable, with the request type "read" and the sector number), a 4096-byte data buffer (device-writable), and a status byte (device-writable). It writes the chain's head index to the next slot of the available ring, makes sure the descriptor writes are visible before the index update, bumps the available counter, and writes to the notification address. The device sees the counter move, reads the header, copies the sector into the data buffer, writes a zero status, records a used entry with a length of 4097, and signals the guest. The guest's interrupt handler reads the used ring, finds the head index and completes the request.

**Notification suppression under load.** A network driver receiving a million packets per second tells the device not to interrupt for every used buffer and polls the used ring instead. The device sees the flag and stops raising interrupts, so the exit rate drops by orders of magnitude. When traffic falls, the driver re-enables interrupts, and the device wakes it again for the next buffer.

**A failing one.** A hostile guest builds a chain whose last descriptor's `next` points back to the first. A naive back end that follows `next` until it sees a descriptor without that flag never stops, so an I/O thread hangs forever. A correct back end counts the descriptors it has visited, stops after at most the table size, marks the device as broken and refuses further work. The lab for this topic walks through exactly this case.

## Related problems and ideas

### Related

- **Device drivers and NAPI** in the kernel pathway are the guest side of the same ring idea, with the same preference for polling under load.
- **KVM `ioeventfd` and `irqfd`** (the KVM API topic) are what connects queue notifications to descriptors in the VMM with no exit.
- **vhost** (the next topic) moves the back end into the kernel or into another process.
- **Memory barriers and lock-free queues** explain why the ordering rules of the specification are what they are.

### Opposing approaches

- **Full emulation of a real device** remains the right answer when the guest cannot be given a virtio driver, such as an old operating system or a firmware stage that boots before drivers load. It trades speed for compatibility, and most hypervisors keep a few such models around.
- **Device assignment (passthrough)** gives the guest a real physical function through an IOMMU. Performance is as good as bare metal, but the guest is tied to the hardware, live migration becomes hard, and the host loses the ability to inspect or filter traffic.
- **Hypervisor-specific paravirtual interfaces** (Xen's split drivers, Hyper-V's VMBus) remain in service and have their own strengths, including integration with the host's management stack. Their weakness is the reverse of virtio's strength: each needs its own guest driver.

## Active research

Work is under way in packed-ring and in-order optimisations, which exploit the fact that many devices complete requests in the order they were submitted. A second area is virtio under confidential-computing guests, where the host cannot read guest memory, so buffers must pass through memory the guest has deliberately shared (bounce buffers) and the driver must treat the device as untrusted. A third is formal verification of back ends. A fourth is fuzzers that generate hostile descriptor chains, which now exist for several VMMs. The state of each should be checked against the current specification and project trackers.

## Future direction

Expect more device classes (GPU, sound, input, memory hot-plug), wider hardware implementations that make virtio the common interface between a guest and a SmartNIC or a storage controller, and back ends written in memory-safe languages and running outside the VMM. A longer-term question is whether the guest driver should trust the device at all: work on hardening drivers against hostile devices applies equally to hardware virtio and to confidential guests.
