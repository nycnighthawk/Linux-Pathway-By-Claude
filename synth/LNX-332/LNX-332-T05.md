# vhost and vhost-user: moving the virtio back end out of the VMM thread

## Define the problem

Virtio gave guests a fast and uniform way to talk to a device, but it left one question open: where does the back end run? In the simplest design it runs in a thread of the VMM. That thread pays for every packet twice. A kick from the guest arrives as an exit and a signal on a descriptor. The thread wakes, copies data between guest memory and the host's network or storage stack through system calls, and raises an interrupt back to the guest, which means another system call. At high rates, the wakeups, system calls and copies dominate the cost, and one thread can saturate a core long before the hardware is busy.

A second problem sits beside the first. Running a complicated device model in the same process as the rest of the VMM puts a large attack surface next to the guest boundary. If the network device's parser has a flaw, the attacker is already inside the process that holds all of the guest's memory and the VMM's own privileges. The task of this topic is to run the data path closer to the resource it serves, or in a separate and tightly restricted process, without changing anything the guest sees.

## History and approaches

### Back ends inside the VMM

QEMU's built-in virtio back ends came first. They are simple and keep all state in one process, which makes live migration and debugging straightforward. They also carry the double cost described above.

### Kernel back ends: vhost

To cut the overhead for networking, Michael Tsirkin and others merged **vhost-net** into Linux in 2010 (version 2.6.34). A kernel thread handles the virtqueues of a virtio-net device directly, reading and writing guest memory and the host's tap device or socket with no round trip through QEMU. The control path stayed in QEMU, which configured vhost through ioctls on a device node. Later kernel back ends followed for SCSI storage and for vsock. The idea behind all of them: let the VMM be the control plane, and let the kernel run the data plane.

### User-space back ends: vhost-user

Kernel back ends are fast, but a kernel is a poor place for experimental code, and some data planes, such as DPDK's user-space network stack or SPDK's storage stack, live in user space and poll hardware directly. The **vhost-user** protocol (2014) moved the same idea to a Unix domain socket. The VMM is the *front end*, a separate process is the *back end*, and they share guest memory by passing file descriptors over the socket. The same split now serves virtio-fs, through the `virtiofsd` daemon, and GPU, input and sound devices. The lesson across fifteen years is a pattern: keep the control plane in the VMM, and place the data plane wherever it runs best, including in a hardware device.

## Current state

### vhost in the kernel

The VMM opens the vhost device and claims it with `VHOST_SET_OWNER`. It then tells the kernel where guest memory is, through `VHOST_SET_MEM_TABLE`, which supplies a list of regions with guest-physical address, size and the VMM's own virtual address. For each virtqueue it sets the ring size, a base index, and the addresses of the three ring areas, along with two eventfds: a **kick** descriptor, bound as an `ioeventfd` so that the guest's doorbell write signals the kernel thread directly, and a **call** descriptor, bound as an `irqfd` so that the kernel thread can inject an interrupt directly. Features are negotiated through `VHOST_GET_FEATURES` and `VHOST_SET_FEATURES`. After that the kernel worker reads the rings, moves the data, and signals the guest without involving the VMM at all, and the VMM only returns to the picture for configuration changes and shutdown.

### vhost-user

The protocol turns the same operations into messages on a socket. Each message has a small header (a request code, flags that carry a version field and reply bits, and a payload size) and a payload. File descriptors, such as the shared memory regions and the kick and call eventfds, travel as ancillary data using `SCM_RIGHTS`. In outline a connection proceeds as follows.

1. The front end sends `SET_OWNER` and asks for the back end's feature bits with `GET_FEATURES`. In practice most front ends send the owner request first.
2. If the feature set includes the protocol-features bit, the front end asks for the back end's extension flags with `GET_PROTOCOL_FEATURES` and replies with the ones it will use through `SET_PROTOCOL_FEATURES`, and only then sends `SET_FEATURES` with the chosen virtio features.
3. It sends `SET_MEM_TABLE` with the region list and the memory descriptors, and the back end maps the same memory.
4. For each queue it sends the size, the base index and the ring addresses, then the kick and call descriptors, and finally enables the ring.

When the protocol-features extension has been agreed, many more messages become available: reading and writing device configuration, tracking in-flight requests so a restarted back end can recover them, dirty-page logging for live migration, and requests that the back end itself initiates toward its peer.

### What the VMM must provide

Guest memory must be shareable: it has to come from a file, from `memfd` or from hugetlbfs, and be mapped as shared. Live migration needs a dirty-page log so the VMM knows what the back end has written. The back end must also survive reconnection, since if it crashes the front end should be able to restart it and replay the queue state, which vhost-user supports through reconnect logic and the in-flight tracking above.

### The generalised pattern

A queue interface that can be attached to any consumer: a kernel thread, a polling user-space process, or hardware, with doorbells and interrupts expressed as file descriptors. The VMM becomes a broker for control and nothing more. Everything that follows in the pattern, from vDPA to hardware offload, extends the same idea one step further from the host CPU.

## Assessment: the good, the bad and the ugly

**The good.** Throughput rises and latency falls, host CPU use drops, a separate process can be sandboxed with a narrow `seccomp` filter and its own user identity, and one VMM can work with many back ends. A crash in the data path no longer takes the VMM, and the guest, with it.

**The bad.** There are more moving parts: sockets, shared memory, protocol versions and feature negotiation. A mismatch between what a VMM and a back end believe about a feature gives obscure failures that look like a stuck guest. Debugging crosses process boundaries and needs tooling on both sides. Memory must be shared, which excludes some memory-backing configurations.

**The ugly.** The back end maps all of guest memory, so it is as trusted as the guest's data, and a bug there is still a path to guest secrets. The kernel version also trusts ring pointers that the guest controls. Live migration requires the back end to save and restore its own state, which every implementation must do correctly. The protocol itself has collected optional extensions that not every implementation supports, so interoperability depends on which subset two programs happen to share.

## Applications beyond this domain

- **Software switches and storage stacks.** DPDK and SPDK use vhost-user to attach their user-space data planes to guests with little overhead.
- **Containers with virtio-fs** use the same process split for file systems, so the host's file system code does not run in the VMM.
- **Hardware offload.** SmartNICs and data-processing units implement the data path in hardware and present virtio to the guest, and the vDPA framework maps the vhost interface onto such devices.
- **Privilege separation** in other systems follows the same control-plane and data-plane division: an unprivileged process handles hostile input and passes only descriptors to a privileged one.
- **Testing.** Protocol-level fuzzers feed hostile messages to back ends, finding implementation bugs without needing a guest.

## Examples

**vhost-net, end to end.** A guest has a virtio network card served by the kernel. The VMM opens the vhost-net device, claims it, gives it the memory table, and passes a tap descriptor and the ring setup for the transmit and receive queues. From then on a kernel worker moves packets between the tap and the rings. When the guest sends, the doorbell write signals the worker's kick descriptor; the worker reads the descriptor chains, passes the packet to the tap, publishes the used entry and signals the call descriptor, and the guest sees an interrupt. The VMM thread is idle during all of this, and a packet needs no system call from user space.

**virtio-fs.** A daemon outside the VMM serves a directory tree. The VMM sends the vhost-user setup messages once, and from then on the daemon handles requests from the guest directly, reading the queue in shared memory. Because the daemon is its own process, it can run in a user namespace with a seccomp filter that allows only file-system calls, and a bug in a request parser cannot reach the VMM.

**A failing one.** A back end is started with a different feature set than the front end expects. Negotiation succeeds, because each side only advertises what it supports, but a rarely used ring flag is handled differently by the two. The guest then sees a queue that never completes. The lab for this topic parses a recorded message stream and reports malformed or out-of-order messages, a useful skill since a captured conversation is often the only evidence available.

## Related problems and ideas

### Related

- **Virtio** (the previous topic) defines the rings that both kinds of back end operate on.
- **Eventfd, irqfd and ioeventfd** are the doorbell plumbing that lets a kick or a call cross a process boundary without a system call per item.
- **Unix sockets and `SCM_RIGHTS`** show how descriptors, and therefore access to memory, can be handed from one process to another.
- **Poll-mode drivers** (DPDK, SPDK) explain why a back end often busy-polls: at high rates waiting for an interrupt costs more than checking a ring.

### Opposing approaches

- **Back ends inside the VMM** remain the better answer for small deployments and for migration simplicity, because all state is in one place and there is nothing to keep consistent across a socket. For low-rate devices, such as a console, the overhead of a separate process is wasted.
- **Device passthrough** (VFIO) gives the guest the hardware itself, so there is no back end to optimise. It offers the best raw performance and the least flexibility: no host-side filtering, harder migration, and one device per guest unless the hardware can be split.
- **Kernel back ends versus user-space back ends** is itself a live disagreement. Kernel vhost avoids context switches and is mature, but code in the kernel is hard to sandbox, so each new kernel device is a larger trusted base. User-space back ends are easier to confine and to write in a safe language, at the cost of copies and scheduling latency.

## Active research

Directions include vDPA and hardware offload, safe back ends in Rust (the `vhost-device` crates collect several), protocol extensions for live migration of back-end state, and limiting a back end's access to only the memory it needs instead of all of the guest. Interoperability testing between independent front-end and back-end implementations is also active. The state of each of these should be checked against the project repositories and the protocol specification, which change from release to release.

## Future direction

Expect more devices to run as separate processes, hardware doing the data path under the same interface, and shared tooling for conformance testing of back ends so that a new implementation can be certified against the specification instead of against one VMM. The long-run direction is that the VMM shrinks into a control-plane broker, and the data plane becomes a set of replaceable components behind a stable protocol.
