# vhost and vhost-user: moving the virtio back end out of the VMM thread

## Define the problem

A virtio back end that lives in the VMM's I/O thread pays for every packet twice: a kick from the guest wakes the thread through an exit and an eventfd, the thread copies data between guest memory and the host network or storage stack, then raises an interrupt. At high rates the thread, the system calls and the copies dominate. At the same time, running a complicated device model in the same process as the rest of the VMM puts a large attack surface next to the guest boundary. The problem is to run the data path closer to its resources, or in a separate, restricted process, without changing the guest.

## History and approaches

QEMU's built-in virtio back ends came first. To cut the overhead for networking, Michael Tsirkin and others merged **vhost-net** (Linux 2.6.34, 2010): a kernel thread that handles the virtqueues of a virtio-net device directly, reading and writing guest memory and the host's tap or socket, with no round trip through QEMU. The control path remained in QEMU, which configured vhost through ioctls on `/dev/vhost-net`. Later kernel back ends followed (vhost-scsi, vhost-vsock). For user-space data paths, such as DPDK or SPDK, **vhost-user** (2014) moved the same protocol to a Unix domain socket: QEMU acts as the front end and a separate process is the back end, sharing guest memory through file descriptors. The same split is used for virtio-fs (`virtiofsd`) and for GPU and input devices. The pattern: keep the control plane in the VMM, move the data plane to the place that is best at it.

## Current state

### vhost in the kernel

The VMM opens a vhost device, claims it with `VHOST_SET_OWNER`, tells it where guest memory is (`VHOST_SET_MEM_TABLE`), and for each virtqueue sets size, base index, ring addresses, and two eventfds: a **kick** fd (the guest's doorbell, bound as an ioeventfd) and a **call** fd (the interrupt, bound as an irqfd). From then on the kernel worker reads the ring, moves the data, and signals the guest without involving the VMM. Features are negotiated through `VHOST_GET_FEATURES` and `VHOST_SET_FEATURES`.

### vhost-user

The same operations are messages on a Unix socket. Each message has a small header (request code, flags with a version field and reply bits, payload size) followed by a payload; file descriptors, such as the memory regions and the kick and call eventfds, travel as ancillary data with `SCM_RIGHTS`. A typical session: the front end asks for the back end's features, sets the owner, sends the memory table (the back end maps the same memory), configures each ring (number, address, base), and passes the kick and call descriptors. When the front end and back end agree on the protocol-features extension, further messages (device configuration, in-flight tracking, dirty logging for migration, backend requests) are available.

### What it needs from the VMM

Guest memory must be shareable: allocated from a file, `memfd` or hugetlbfs and mapped shared. Live migration needs the dirty-page log. The back end must unmap and reconnect cleanly if it crashes, which vhost-user supports with reconnect logic.

### The pattern

A queue interface that can be attached to any consumer: kernel, user-space poll-mode process, or hardware, with doorbells and interrupts as file descriptors. The VMM becomes a control-plane broker.

## Assessment: the good, the bad and the ugly

**The good.** Throughput and latency improve, CPU use drops, a separate process can be sandboxed tightly, and one VMM can use many back ends. Crashes of the data path no longer take the VMM with them.

**The bad.** More moving parts: sockets, shared memory, version negotiation; a mismatch of features between VMM and back end gives obscure failures. Debugging crosses process boundaries. Memory must be shared, which excludes some setups.

**The ugly.** The back end maps all guest memory, so it is as trusted as the guest's data; a bug there is still a path to guest secrets (and the kernel version trusts the guest's ring pointers). Live migration requires the back end to save and restore state. The protocol has accumulated optional extensions that not every implementation supports.

## Applications beyond this domain

- **Software switches and storage stacks** (DPDK, SPDK) use vhost-user to attach to guests.
- **Containers with virtio-fs** use the same process split for file systems.
- **Hardware offload**: SmartNICs and DPUs implement the data path in hardware and present virtio to the guest; vDPA maps the vhost interface to such devices.
- **Privilege separation** in other systems follows the same control-plane/data-plane division.
- **Testing**: protocol-level fuzzers feed hostile messages to back ends.

## Examples

**vhost-net.** A guest NIC served by the kernel: the VMM passes a tap descriptor and the ring setup to `/dev/vhost-net`; the worker moves packets between tap and rings.

**virtio-fs.** A daemon outside the VMM serves the file system; the VMM sends vhost-user messages once and the daemon handles requests directly.

**A failing one.** The back end is started with a different set of feature bits than the front end expects; negotiation succeeds but a rarely used ring flag is mis-handled and the guest sees a stuck queue. The lab parses a message stream and reports malformed messages.

## Related problems and ideas

- **Virtio** (previous topic) defines the rings used by both back ends.
- **Eventfd, irqfd and ioeventfd** are the doorbell plumbing.
- **Unix sockets and SCM_RIGHTS** pass descriptors between processes.
- **Poll-mode drivers** (DPDK, SPDK) explain why the back end often busy-polls.

## Active research

Directions include vDPA and hardware offload, safe back ends in Rust (the `vhost-device` crates), protocol extensions for live migration of back-end state, and isolating the back end's access to only the memory it needs (to verify the state of each).

## Future direction

Expect more devices as separate processes, hardware doing the data path under the same interface, and shared tooling for conformance testing of back ends.
