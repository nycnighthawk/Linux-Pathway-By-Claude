# QEMU device models: objects, memory regions and tests without a guest

## Define the problem

A hypervisor is only useful if guests find the devices they expect. QEMU must provide hundreds of them: old and new network cards, disk controllers, serial ports, interrupt controllers, buses, USB, graphics, and many boards that combine them. Each device has registers with exact side effects, and the guest's driver depends on every one. The code runs inside the process that also holds the guest's memory, so a mistake is not merely a functional bug but a possible route to the host.

Adding a device therefore means several things at once. It must plug into the memory system, interrupt delivery, migration, the command-line options and the management interface, and it has to be shown to behave as the datasheet says. The last point is the hard one. A device cannot be proved correct by booting an operating system and hoping the driver exercises the corner cases, because a normal driver touches only the paths that normal hardware allows. This essay follows how QEMU's object model, memory API and test harness grew up to answer those pressures, and then works through a small device from the first line to the first test.

## History and approaches

### Hand-written devices and board tables

QEMU began in 2003 as a dynamic translator, a program that translated guest code to host code on the fly, with device code written by hand and a table of board configurations. That worked while the device count was small. As targets and devices multiplied, each device carried its own conventions for how it was created, configured and connected, and the same wiring code was copied again and again.

### A uniform object system

The **QEMU Object Model** (QOM), introduced from about 2011, gave every device the same skeleton: types registered at start-up, single inheritance, typed properties, and a tree of live objects that can be listed and modified at run time. A device became a *type* with a parent (a PCI device inherits from the generic PCI device type, for example), instance data and a few callbacks. The command line could then create any device by name and set any property, and management tools could inspect the same tree.

### The memory API

Early boards hard-wired their address maps. In 2012 the **memory API** replaced that with trees of `MemoryRegion` objects: a device creates regions that stand for its registers and RAM, and a board *maps* them into an address space, with the ability to alias, overlap and prioritise them. That one change made it possible to describe an IOMMU, a PCI window or a bank-switched ROM in the same terms.

### Testing without a guest

Early device tests booted a full guest and watched for the expected output. Those tests were slow, flaky, and dependent on the guest's drivers. **qtest**, introduced in 2012, took a different route: it exposes a simple protocol over a socket that lets a test program drive a QEMU instance in which no guest code runs at all. The test reads and writes guest memory and I/O addresses directly and checks the results. Helper libraries (libqos) later added canned access to common buses. The pattern that came out of this period: describe a device as a type with properties and memory regions, and test its register-level behaviour with a harness that plays the part of the driver.

## Current state

### A device as a QOM type

A device is a C structure that embeds its parent's structure, together with a `TypeInfo` that names the parent type (for a PCI device, `TYPE_PCI_DEVICE`), gives the instance size, and points to functions. A `class_init` function fills in the class: the vendor and device identifiers, the `realize` callback, a migration description and the property list. An `instance_init` function sets defaults. A `type_init` hook registers the type at start-up. The lifecycle has four steps worth remembering: construction, property setting, **realize** (where resources are allocated and the device becomes live) and **unrealize** (where it is torn down again). Devices attach to a bus and appear on the command line as `-device name,prop=value`.

### Registers, regions and interrupts

In `realize`, a device creates one or more memory regions with an operations table (`MemoryRegionOps`) of read and write callbacks, states which access sizes it supports, and registers each as a PCI BAR with `pci_register_bar`. From then on a guest access to that range lands in the callbacks. A device raises an interrupt through the bus with `pci_set_irq`, or through MSI helper functions, and issues DMA through address-space helpers that respect an IOMMU if one is present.

### A small example: the edu device

QEMU ships a teaching PCI device, called `edu`, that exists only to be a good first model. It has a version register, a liveness register that returns the bitwise complement of whatever was last written to it, a factorial unit that computes in a separate thread and then raises an interrupt, and a DMA engine. It is small enough to read in an hour, and it is the device that the driver exercises in the kernel pathway's PCI lessons, which makes it the guest-side partner of this topic.

### Migration, properties and reset

A `VMStateDescription` lists the fields that must be saved and restored for live migration. A device that omits a field passes every normal test and then fails after a migration in a way that is very hard to trace. Properties give the device a stable command-line interface, and a reset function returns its registers to their power-on values.

### qtest

QEMU started with the `qtest` accelerator creates the machine but runs no CPU. A test starts the process, connects to its socket and issues commands such as `readl address`, `writel address value`, `outb`, `inb` and `clock_step`; each is answered with `OK` and, for reads, the value. Test code usually calls C helpers (`qtest_readl`, or the `qpci_*` functions for PCI) in place of raw text, and then asserts register values and interrupt line state after every step. Because no guest software is involved, the tests are fast and deterministic, and QEMU's continuous integration runs hundreds of them.

### The generalised pattern

A type, a set of memory regions and a state description define the device; poking registers from outside and checking the results verifies it. The same pattern holds for any peripheral model, in any simulator.

## Assessment: the good, the bad and the ugly

**The good.** QOM and the memory API make devices uniform and inspectable, so a new device is mostly declarative and works with every board and tool that already exists. qtest allows precise tests of corner cases that no real driver would exercise, including partial and unaligned accesses.

**The bad.** The programming interface is large and has changed repeatedly, and the documentation lags the code, so copying a recent device is often a better guide than the text. A faithful model needs the hardware datasheet, which may be missing, incomplete or wrong. Devices that use threads, timers or bottom halves complicate locking, because the global lock that once protected everything is being reduced.

**The ugly.** Security. Guest-triggered bugs in device models, out-of-bounds register or DMA accesses and reentrancy through memory callbacks, have long been the main source of QEMU's own vulnerabilities. Many legacy devices are barely maintained and are still shipped. Migration compatibility across versions needs machine-type versioning and compatibility properties, so an old guest definition keeps meaning the same thing after an upgrade.

## Applications beyond this domain

- **Hardware and software co-design.** Device models serve as virtual platforms, letting driver developers work before silicon exists.
- **Fuzzing.** qtest-style harnesses power device fuzzers, both QEMU's own and flows built on other fuzzing frameworks.
- **Education.** The `edu` device and Arm sample boards are teaching tools for driver writing.
- **Embedded continuous integration.** Board models run firmware and kernel tests without hardware.
- **Other simulators.** SystemC virtual platforms and Renode use the same register-and-callback structure.

## Examples

**A register that reflects.** A test writes `0xdeadbeef` to the liveness register and expects to read `0x21524110` back, the bitwise complement. It then repeats with a partial write to check that the complement is computed on the whole register, not only the written bytes.

**Factorial and an interrupt.** A test writes 5 to the factorial register, enables the completion interrupt in the status register, advances the virtual clock until the worker thread finishes, and asserts that reading the result gives 120 and that the interrupt line is raised. It then clears the status bit and asserts the line drops.

**A failing one.** A model returns a value wider than the access size, or forgets to reset a status bit when asked. It boots and works, because Linux's driver reads only whole registers once. But a qtest that reads a register twice, or reads one byte of a four-byte register, exposes the fault. Tests that probe unaligned accesses, partial writes and DMA to the device's own registers have found real reentrancy bugs in shipped devices.

## Related problems and ideas

### Related

- **A PCI driver for the edu device** (kernel pathway) is the guest-side partner of this device model.
- **Virtio back ends** (earlier topics) are devices of the same kind with queues in place of registers.
- **Fuzzing and sanitizers** exercise the same callbacks with hostile input, and many of them reuse the qtest harness.
- **Live migration** explains why every register needs a place in the state description.

### Opposing approaches

- **Do not model the device in the VMM at all.** Out-of-process device protocols (vhost-user, and vfio-user for general PCI devices) hold that a device model should be its own process with its own sandbox, so a bug cannot reach the rest of QEMU. The price is a protocol and a context switch for every access.
- **Smaller VMMs with a few paravirtual devices** (the Rust VMMs of the previous topics) argue that the right number of device models is close to zero beyond virtio and a serial port, since the legacy zoo is where the vulnerabilities are. The reply from QEMU's side is that real deployments contain real, old operating systems that need the old devices.
- **Hardware-in-the-loop testing** holds that no model can capture all the behaviour of a real part, so tests should run against the hardware or a vendor's RTL simulation. Model-based testing is quicker and wider, but it cannot be better than the model.

## Active research

Current work includes coverage-guided fuzzing of device models, memory-safe device implementations (Rust in QEMU is an ongoing effort), formal models of register behaviour generated from machine-readable specifications, and tools that derive a software model from the hardware's RTL. Each is at a different stage, and the claims about them should be checked against the QEMU developer lists and recent conference talks.

## Future direction

Expect device code to move gradually toward generated or Rust implementations, stricter guards against reentrancy, and device models offered as separate processes so that a bug is contained. For a learner the practical conclusion is that the skills transfer: whatever the model's language, a type, regions, a state description and a harness that pokes registers from outside will still be the structure.
