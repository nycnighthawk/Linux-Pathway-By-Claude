# QEMU device models: objects, memory regions and tests without a guest

## Define the problem

A hypervisor is only useful if guests find the devices they expect. QEMU has to provide hundreds of them: old and new network cards, disk controllers, serial ports, interrupt controllers, buses, USB, graphics, and many boards that combine them. Each device has registers with exact side effects that guest drivers depend on, and the code runs inside the process that also holds the guest's memory. Adding a device means integrating with the memory system, interrupts, migration, command-line options and the management interface, and proving that it behaves as the datasheet says without booting a full operating system.

## History and approaches

QEMU began (2003) as a dynamic translator with hand-written device code and a table of board setups. As the number of devices grew, a uniform object system was added: the **QEMU Object Model (QOM)** (2011 onward), with types registered at start-up, inheritance, properties, and a tree of objects that can be inspected and created at run time. The memory API (2012) replaced hard-wired address maps with trees of `MemoryRegion` objects that devices register, so a board can map them, alias and overlap them. Device-specific tests started as boot tests of full guests, which are slow and flaky; **qtest** (2012) introduced a protocol over a socket that lets a test drive a QEMU instance with no guest at all, by reading and writing guest memory and I/O addresses directly, and later added libqos helpers for common buses. The pattern: describe a device as a type with properties and memory regions, and test its register-level behaviour through a harness that is the "driver".

## Current state

### QOM types

A device is a C structure and a **TypeInfo** describing its parent type (for a PCI device, `TYPE_PCI_DEVICE`), instance size, and function pointers: `class_init` sets up the class (vendor and device IDs, `realize`, migration description, properties), `instance_init` sets defaults. `type_init` registers it. The lifecycle matters: construction, property setting, **realize** (where resources are created and the device becomes live), and **unrealize**. Devices are placed on a bus and created from the command line with `-device name,prop=value`.

### Memory regions and interrupts

In `realize`, the device creates `MemoryRegion`s with read and write callbacks (the `MemoryRegionOps`) for its registers, specifying access sizes, and registers them as a PCI BAR with `pci_register_bar`. The guest's accesses to that range arrive in the callbacks. Interrupts are raised through the bus (`pci_set_irq` or MSI helpers), and DMA goes through address-space helpers that respect an IOMMU.

### A worked example: the `edu` device

QEMU includes a teaching PCI device, `edu`, with a version register, a liveness register that returns the bitwise complement of the last write, a factorial unit that works in a thread and raises an interrupt, and a DMA engine. It is small enough to read in an hour and is the model for the kernel-driver topic in the previous course.

### Migration, properties and reset

A `VMStateDescription` lists fields that must be saved and restored; a device that forgets one fails live migration subtly. Properties give a stable command-line surface; reset functions bring registers to their power-on values.

### qtest

Run QEMU with `-accel qtest`: the machine exists but no CPU runs. A test starts it, connects to a socket and sends text commands such as `readl addr`, `writel addr value`, `outb`, `inb`, `clock_step` and gets `OK` replies (reads return a value). Test code usually calls C helpers (`qtest_readl`, `qpci_*` from libqos) rather than text, and the test binary asserts register values and interrupt state after each step. Because no guest software is needed, tests are quick and deterministic, and they run in the project's continuous integration.

### The pattern

Type plus memory regions plus a state description; verify by poking registers from outside and checking the results.

## Assessment: the good, the bad and the ugly

**The good.** QOM and the memory API make devices uniform and inspectable; qtest allows precise tests of corner cases real drivers never exercise; a new device is mostly declarative.

**The bad.** The API surface is large and has changed repeatedly; documentation lags the code. Writing a faithful model needs the datasheet, which may be missing or wrong. Threads and timers inside devices complicate locking (the big QEMU lock and its replacements).

**The ugly.** Security: guest-triggered bugs in device models are the main source of QEMU vulnerabilities (out-of-bounds register or DMA access, reentrancy through memory callbacks). Many legacy devices are barely maintained and still shipped. Migration compatibility across versions needs machine-type versioning with compatibility properties.

## Applications beyond this domain

- **Hardware/software co-design**: device models serve as virtual platforms for driver development before silicon exists.
- **Fuzzing**: qtest-style harnesses power device fuzzers (QEMU's own, or syzkaller-based flows).
- **Education**: the `edu` device and Arm sample boards teach driver writing.
- **Embedded CI**: board models run firmware and kernel tests without hardware.
- **Other emulators and simulators** (SystemC, Renode) use the same register-and-callback structure.

## Examples

**Register behaviour.** A test writes `0xdeadbeef` to the liveness register and expects to read `0x21524110` back.

**Factorial and interrupt.** A test writes 5 to the factorial register, enables the completion interrupt in the status register, steps the clock and checks that the result reads 120 and the interrupt line is raised.

**A failing one.** A model that returns a value wider than the access size, or that forgets to reset a status bit, passes a boot but fails a qtest that reads a register twice. Tests of unaligned and partial accesses find reentrancy and bounds bugs.

## Related problems and ideas

- **PCI driver for the edu device** (kernel internals) is the guest-side partner.
- **Virtio back ends** (earlier topics) are devices of the same kind with queues.
- **Fuzzing and sanitizers** exercise the same callbacks with hostile input.
- **Live migration** explains why every register needs a place in the state description.

## Active research

Directions include coverage-guided fuzzing of device models, memory-safe device implementations (Rust in QEMU), formal models of device registers generated from machine-readable specifications, and tools that derive models from RTL (to verify the state of each).

## Future direction

Expect device code to move toward generated or Rust implementations, strict reentrancy guards, and device models provided as separate processes (vfio-user, vhost-user) so a bug is contained.
