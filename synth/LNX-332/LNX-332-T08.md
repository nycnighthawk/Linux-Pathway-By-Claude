# Testing a hypervisor: guest-side tests and ioctl-level tests

## Define the problem

A hypervisor is correct only if the guest cannot tell it from hardware (and cannot break out). The behaviour to check spans CPU instructions, control registers, page tables, interrupts, timers and the ioctl interface that user space uses. Booting an operating system exercises a small, well-trodden part of that space. Edge cases (an unusual instruction encoding, a nested paging permission, an interrupt arriving at an awkward moment) appear only in targeted tests. The problem is to build tests that run quickly, report clearly, cover corner cases and run on every patch.

## History and approaches

Early KVM testing ran full guests and watched for crashes. Two purpose-built suites followed. **kvm-unit-tests** (2010 onward, hosted outside the kernel tree) builds tiny freestanding guest binaries: each is a few hundred lines of C and assembly that sets up its own mode, performs an operation and checks the result, printing `PASS`, `FAIL` or `SKIP` lines to a serial port or a debug port; a runner launches each under QEMU with KVM. **KVM selftests** (in `tools/testing/selftests/kvm` in the kernel tree) take the opposite angle: a user-space program creates a VM through the ioctls, runs a small guest function in it and uses a "ucall" mechanism (a port or MMIO write that the host harness recognises) for the guest to report results, so the test is written in one C file as host code and guest code. Together they cover instruction-level behaviour and interface-level behaviour. The lesson: put tests where the failures are observable, and make them part of the review flow.

## Current state

### kvm-unit-tests

The tree has one directory per architecture; each test is built as a flat binary or ELF with a minimal startup file, a small library (page allocator, simple paging setup, a printf to the console), and an entry in a configuration file (`unittests.cfg`) giving the command-line arguments, required machine features, time limit and groups. A run script starts QEMU with a debug-exit device, so the guest can terminate the VM with a status; the runner decodes the status and the output into pass, fail, skip or error. Typical tests: `msr`, `vmx`, `svm` (nested virtualisation), `apic`, `pmu`, `eventinj`, `access` (page-table permissions) and `emulator` (instruction semantics).

### KVM selftests

Each test is a program using library helpers: create a VM with a given mode, add memory, create a vCPU, load a guest function, run it and loop on `KVM_RUN` handling exits and ucalls (`GUEST_ASSERT`, `GUEST_SYNC`, `GUEST_DONE`). Many tests use the KTAP output format of the selftest framework with `ksft_*` helpers, skip cleanly when a capability is missing (checked with `KVM_CHECK_EXTENSION`), and run in the kernel's selftest harness. Interface tests include state save and restore, dirty logging, memslot moves, `KVM_SET_MSRS`, the Hyper-V and Xen emulation, and nested state.

### Running and judging

Both suites need a host with KVM, and many tests need specific hardware (nested virtualisation, a PMU, a given CPU feature), so **skip** is a first-class outcome distinct from fail. The runner must separate a test that ran and produced a wrong answer from an environment that cannot run it, and from a QEMU process that died. Results feed continuous integration (the KVM maintainers' trees, distribution testing, and robots).

### The pattern

Small, deterministic guests; a channel (debug port, ucall, serial) for results; explicit skip conditions; one status that the runner can read.

## Assessment: the good, the bad and the ugly

**The good.** Fast, precise tests catch regressions before release; test code doubles as documentation of the architecture; selftests live with the kernel and run on every kernel build.

**The bad.** Coverage is uneven: hardware features that are scarce are poorly tested; tests are architecture specific and need experts; failures in nested setups can be timing dependent.

**The ugly.** Flaky tests on shared CI hardware, tests that pass on the emulator and fail on silicon (or the reverse), and the difficulty of proving an absence of guest escapes. A skipped test looks like a pass in a careless summary.

## Applications beyond this domain

- **Kernel testing generally** (kselftest, KUnit) uses the same skip-versus-fail discipline.
- **Firmware and emulator validation** reuses freestanding-guest tests.
- **Hardware bring-up** runs the same unit tests on silicon and on the emulator and compares.
- **Fuzzing** starts from these harnesses (a guest function plus a host driver).
- **Compliance and certification** suites for virtualization platforms follow the same pattern.

## Examples

**A selftest skip.** A test for a nested-virtualisation feature checks `KVM_CHECK_EXTENSION` first; on a host without it, the test prints a skip line with a reason and exits with the skip code.

**A unit test status.** A guest test exits through the debug port with code 0. QEMU's own exit status is derived from the written value, so the runner subtracts and shifts to recover the test's code.

**A failing one.** A test prints `FAIL` for one sub-check but the run exits with the success code because the guest forgot to propagate the failure count. The runner must read both the lines and the status. The lab does so.

## Related problems and ideas

- **KUnit and kselftest** (first kernel course) are the in-kernel counterparts.
- **Bisecting** a regression uses these tests as the oracle.
- **QEMU device tests (qtest)** test the user-space side with the same idea.
- **Continuous integration** decides how often tests run and how failures are triaged.

## Active research

Open areas include automatic generation of instruction tests from the architecture specification, differential testing between real CPUs and emulators, coverage-guided fuzzing of the KVM ioctl and exit paths, and confidential-guest testing where state is hidden (to verify the state of each).

## Future direction

Expect more tests to run in hardware-backed CI on every patch, wider use of generated instruction tests, and stronger tooling for nested and confidential guests.
