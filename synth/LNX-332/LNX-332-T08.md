# Testing a hypervisor: guest-side tests and ioctl-level tests

## Define the problem

A hypervisor is correct only if the guest cannot tell it from real hardware and cannot break out of it. The behaviour to check spans CPU instructions, control registers, page tables, interrupts, timers and the ioctl interface that user space depends on. Booting an operating system exercises only a small, well-trodden part of that space, because a mainstream kernel does what mainstream kernels do. The edge cases, such as an unusual instruction encoding, a permission corner in nested paging, or an interrupt arriving at an awkward moment, appear only when a test is built to provoke them.

The problem, then, is to build tests that run in seconds, report a clear verdict, reach the corners, and run on every patch. This essay follows how the two main suites for KVM grew from different starting points, how they work, and what a careful reader of their results must watch for.

## History and approaches

### Testing with whole guests

Early KVM testing ran complete guests and watched for crashes. That approach finds big regressions, such as a kernel that no longer boots, and nothing else. It is slow, depends on the guest's behaviour, and says little about *why* something failed.

### Two purpose-built suites

Two suites with complementary designs followed.

**kvm-unit-tests**, which began around 2010 and is hosted outside the kernel tree, builds tiny freestanding guest binaries. Each is a few hundred lines of C and assembly that set up their own CPU mode, perform an operation, and check the result, printing `PASS`, `FAIL` or `SKIP` lines to a serial or debug port. A runner starts each binary under QEMU with KVM and reads the outcome.

**KVM selftests**, in `tools/testing/selftests/kvm` in the kernel tree, take the opposite view. A user-space program creates a VM through the ioctls, runs a small guest function inside it, and uses a "ucall" mechanism (a write to a port or MMIO address that the host harness recognises) for the guest to report back. The host code and the guest code live in the same C file. Together the two suites cover instruction-level behaviour (what the guest sees) and interface-level behaviour (what user space sees). The lesson the authors drew: put each test where its failure is observable, and make the tests part of the review flow, so a patch that breaks one is caught before it merges.

## Current state

### kvm-unit-tests

The tree has one directory per architecture. Each test builds as a flat binary or ELF with a minimal start-up file and a small library: a page allocator, simple paging setup, and a `printf` to the console. An entry in a configuration file (`unittests.cfg`) gives each test's command-line arguments, required machine features, time limit and groups. The run script starts QEMU with a debug-exit device, so the guest can end the VM with a status code, and the runner decodes both the status and the output into pass, fail, skip or error. Typical tests include `msr`, `vmx` and `svm` (nested virtualisation), `apic`, `pmu`, `eventinj`, `access` (page-table permissions) and `emulator` (instruction semantics).

### KVM selftests

Each test is a program built on library helpers. It creates a VM with a chosen paging mode, adds memory, creates a vCPU, loads a guest function, and loops on `KVM_RUN` handling exits and ucalls. Inside the guest function the test uses macros such as `GUEST_ASSERT`, `GUEST_SYNC` and `GUEST_DONE` to check conditions and to hand control back at chosen points. Output follows the KTAP format of the kernel's selftest framework, with `ksft_*` helpers. A test checks for the capability it needs with `KVM_CHECK_EXTENSION` and skips cleanly when the host lacks it. The interface tests include state save and restore, dirty-page logging, memory-slot moves, MSR access, the Hyper-V and Xen emulation, and nested-virtualisation state.

### Running and judging

Both suites need a host with KVM, and many tests need specific hardware: nested virtualisation, a performance monitoring unit, a given processor feature. For that reason **skip** is a first-class outcome distinct from fail. The runner must separate three cases: a test that ran and produced a wrong answer, an environment that cannot run the test, and a QEMU process that died. Results feed continuous integration run by the KVM maintainers, distributions and automated test services.

### The generalised pattern

Small, deterministic guests; a channel for results (a debug port, a ucall, a serial line); explicit skip conditions; one status the runner can read. That recipe works for any component whose natural user is a machine, not a person.

## Assessment: the good, the bad and the ugly

**The good.** Fast, precise tests catch regressions long before a release. The tests also serve as executable documentation of the architecture, since a test that checks a rule states it exactly. Selftests live with the kernel and run on every kernel build, which keeps them in step with the interface.

**The bad.** Coverage is uneven: features that need scarce hardware are poorly tested, because few developers can run them. Tests are architecture specific and need people who know each architecture. Failures in nested setups can depend on timing, so they pass most of the time and fail occasionally.

**The ugly.** Shared continuous-integration machines make tests flaky. A test may pass on the emulator and fail on silicon, or the reverse. Proving the absence of a guest escape cannot be done by testing at all, since tests show the presence of bugs, never their absence. And a skipped test looks like a pass in a careless summary, so a green dashboard may hide the fact that the important half did not run.

## Applications beyond this domain

- **Kernel testing generally.** Kselftest and KUnit use the same skip-versus-fail discipline, and a developer who has written one kind finds the others familiar.
- **Firmware and emulator validation** reuse freestanding-guest tests to check behaviour that no operating system exercises.
- **Hardware bring-up.** The same unit tests run on silicon and on an emulator, and any difference between the two is a bug in one of them.
- **Fuzzing.** A guest function plus a host driver is the shape of a fuzzing harness, so these suites seed fuzzers for hypervisors.
- **Certification.** Compliance suites for virtualisation platforms follow the same pattern: many small checks, a clear status, an explicit way to say "not applicable".

## Examples

**A selftest skip.** A test for a nested-virtualisation feature first calls `KVM_CHECK_EXTENSION`. On a host without the capability, it prints a skip line with a reason and exits with the skip code, so a report shows "not run" and nobody reads silence as success.

**A unit-test status.** A guest test ends by writing zero to the debug-exit port. QEMU turns the written value into its own process exit status by an agreed rule (shift left and set the low bit), so the runner must subtract and shift to recover the test's code. If it forgets, every test appears to fail with an odd number.

**A failing one.** A test prints a `FAIL` line for one sub-check, but the run exits with the success code because the guest forgot to add the failure into the final status. A runner that reads only the exit status reports a pass. The runner must read both the lines and the status, and the lab for this topic builds one that does.

## Related problems and ideas

### Related

- **KUnit and kselftest** in the first kernel course are the in-kernel counterparts of these suites.
- **Bisecting a regression** uses these tests as the oracle, which makes their reliability a matter of everyone's time.
- **QEMU device tests (qtest)** test the user-space side of virtualisation with the same idea.
- **Continuous integration** decides how often tests run and how failures are triaged.

### Opposing approaches

- **Boot-based testing** argues that real operating systems are the real test: if Linux and Windows boot and run their own test suites, the hypervisor is good enough. The strength is realism and the weakness is the narrow coverage described above.
- **Formal verification.** Proof of properties of small hypervisors (isolation, correct emulation of selected instructions) provides a guarantee that no test can. It is expensive, limited in scope, and applies to a model, not to the shipping code on real silicon.
- **Differential testing against hardware.** Instead of writing expected results by hand, run the same code on a real CPU and on the hypervisor and compare. It needs no reference text, but it needs the hardware, and it finds only differences, not shared errors.

## Active research

Open areas include generating instruction tests automatically from the architecture specification, differential testing between real processors and emulators, coverage-guided fuzzing of the ioctl and exit paths, and testing confidential guests, where state is hidden from the host by design and the test harness itself must live inside the guest. The state of each of these should be confirmed from the project lists and recent papers.

## Future direction

Expect more tests to run on hardware-backed CI for every patch, wider use of generated instruction tests, and better tooling for nested and confidential guests. For a contributor the practical rule is already clear: a change to KVM that comes without a test is a request for the reviewer to do the testing.
