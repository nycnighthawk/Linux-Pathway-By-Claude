# VirtualBox from source: how a type-2 hypervisor is built and structured

## Define the problem

KVM and QEMU make virtualisation a feature of a general-purpose kernel. VirtualBox is a different design point: a hypervisor product that runs as an application on desktops (Windows, macOS, Linux, Solaris) and brings its own kernel driver, device models, management layer, GUI and command-line tool. Anyone who wants to change it, add a backend, debug a guest problem or write an automation tool needs to build it from source and understand how the layers fit. The questions are: how does the source tree divide, how is it built, what runs in the kernel and what in user space, and how do external programs control it?

## History and approaches

VirtualBox started at innotek (2007) as a closed product with an open-source edition; Sun and then Oracle acquired it. The **Open Source Edition (OSE)** is distributed under the GPL (version 3 for current releases, with a CDDL option for part of the code; check the licence files of the version in use) and forms the core; the **Extension Pack** (USB 2 and 3, remote display, disk encryption and other features) is proprietary and separate. The design differs from KVM: a small ring-0 driver (`vboxdrv`) provides the privileged entry to hardware virtualisation and memory pinning; the **VMM** (virtual machine monitor) code, with CPU emulation fallbacks, page management, interrupt and timer handling and the **PDM** (pluggable device manager), lives mostly in a library used by the VM process; devices are written against PDM interfaces. Early versions used raw-mode execution and software virtualisation for old CPUs; the project later dropped raw mode and relies on hardware virtualisation. The VM runs in an ordinary user process (`VBoxHeadless`, or the GUI's VM process), while a long-lived service (`VBoxSVC`) holds the registry of machines and settings.

## Current state

### Source layout

Under `src/VBox/` the main directories are (names to verify per version): `VMM` (core: CPU, memory management, interrupts, timers, the hardware virtualisation back ends, the NEM layer for host hypervisor APIs), `Devices` (PDM devices: chipsets, network, storage, audio, USB, graphics), `Main` (the COM-style API implementation and the XML settings), `Frontends` (the Qt GUI, `VBoxManage`, `VBoxHeadless`), `HostDrivers` (the kernel modules), `Additions` (guest additions: drivers and services inside the guest), `Storage` (disk image formats), `NetworkServices` and `Runtime` (IPRT, a portability library that provides threads, files, strings, and so on). The top-level build uses **kBuild** (a make-based system) with a configuration script that detects the toolchain and libraries and writes `AutoConfig.kmk` and `LocalConfig.kmk`, then `kmk` builds everything into an output tree.

### Building the OSE

On Linux one installs a compiler, headers for the running kernel (for the driver), development packages for Qt, libxml2, SDL and others, runs `./configure` with options to disable what is not needed (for example the GUI for a headless build, or the Qt frontend), sources the generated environment script and runs `kmk`. The kernel modules are built from the output tree against the kernel headers, installed and loaded; the result is run from the output directory. A full build takes a long time and several gigabytes; partial rebuilds are fast.

### Runtime architecture

`VBoxSVC` owns machine definitions and the global state; frontends and tools talk to it over a local COM interface (on Linux an XPCOM implementation, on Windows COM). Starting a VM spawns a VM process that loads the VMM library, opens `vboxdrv`, creates the virtual machine and its vCPU threads (EMT, emulation threads), and attaches devices. Device accesses arrive through the VMM's memory-mapped and port-I/O handlers into PDM devices; a device may use worker threads and asynchronous I/O.

### The Main API and the SDK

The **Main API** is described in an XML interface definition (`VirtualBox.xidl`) from which headers, bindings and documentation are generated. The **SDK** packages those, with samples, for C++ (COM or XPCOM), a web-service front end (`vboxwebsrv`), and bindings for Python, Java and others. Most automation (VBoxManage, Vagrant, test harnesses) uses this API: create a machine object, set attachments and properties, create a session, launch, and listen for events.

### The pattern

A privileged core as small as practical, a large user-space VMM and device layer, and a typed management API generated from a single interface description.

## Assessment: the good, the bad and the ugly

**The good.** Portable across host operating systems, mature device and storage support, rich management API, and a source tree where one can follow a device end to end.

**The bad.** Building is heavy and sensitive to toolchain and kernel header versions; the codebase is large and carries historical layers (raw mode remnants, 32-bit hosts); documentation of internals is thin and partly outdated. Features split between OSE and the Extension Pack surprise users.

**The ugly.** Host kernel driver compatibility: a new Linux kernel can break the module until patched; the driver is out of tree. Licence boundaries need attention (GPL OSE, proprietary pack). Security of a large user-space device model is only as good as its testing.

## Applications beyond this domain

- **Desktop virtualisation** for development and teaching, using the API for reproducible lab environments.
- **Test automation** that drives guests through the SDK.
- **Generated-API design**: an interface-definition language yielding multi-language bindings is a general pattern.
- **Build-system practice**: kBuild's separation of detection, configuration and per-target rules is reused in other large C/C++ code bases.
- **Cross-platform runtime libraries** such as IPRT illustrate how to keep a portable core.

## Examples

**A headless build.** Configure without the GUI, build `VBoxManage`, `VBoxSVC` and `VBoxHeadless`, load the driver, and start a VM from the command line on a server.

**An API script.** A Python script uses the SDK to create a machine, attach a disk and start it in headless mode, then waits for a guest-property event.

**A failing one.** The build stops while compiling the kernel module after a host kernel upgrade; the module sources use an interface that changed. The fix is a newer VirtualBox source drop or a local patch.

## Active research

Directions include isolating device models from the VM process, running on top of host hypervisor APIs (for example Windows Hypervisor Platform and macOS Hypervisor.framework) instead of an own driver, and supporting Arm hosts and guests (to verify the state of each).

## Future direction

Expect further reliance on host hypervisor interfaces instead of a custom driver where the platform offers one, Arm host support, and slimmer builds for headless server use.
