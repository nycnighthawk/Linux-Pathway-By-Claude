# VirtualBox from source: how a type-2 hypervisor is built and structured

## Define the problem

The topics so far treated virtualisation as a feature of a general-purpose kernel: KVM supplies the privileged core, and QEMU or a Rust VMM supplies everything else. VirtualBox is a different design point. It is a hypervisor *product* that runs as an application on desktops (Windows, macOS, Linux and Solaris hosts), and it brings its own kernel driver, its own device models, a management layer, a graphical interface and a command-line tool. Someone who wants to change it, to add a backend, to debug a guest problem, or to write an automation tool, must build it from source and understand how its layers fit.

Four questions organise the topic. How is the source tree divided? How is it built? What runs in the kernel, and what runs in user space? And how do outside programs control a running installation? This essay answers them in that order, after a short account of how the design came about, because the history explains several features that look odd today.

## History and approaches

### From a company product to an open-source core

VirtualBox began at the German company innotek in 2007 as a product with an open-source edition, was acquired by Sun Microsystems, and passed to Oracle with Sun's own takeover. Two parts of the product have always been distinct. The **Open Source Edition (OSE)** is released under the GPL (version 3 in current releases, with a permissive option for some parts of the code; the licence files of the version in use are the authority) and forms the core. The **Extension Pack**, which adds features such as USB 2 and 3 support, remote display and disk encryption, is proprietary and separate. Anyone building from source gets the former and not the latter, a fact that surprises users who then find a feature missing.

### An architecture built for portability

The design differs from KVM's in two respects. First, only a small amount of code runs in the host kernel. A ring-0 driver, `vboxdrv`, gives the rest of the system a privileged entry into hardware virtualisation and into memory pinning. Everything else runs in user space: the **VMM** library, which contains CPU emulation fallbacks, page management, interrupt and timer handling and the hardware-virtualisation back ends, and the **PDM**, the pluggable device manager, against whose interfaces the device models are written. Second, the whole stack is built to run on several host operating systems with the same code, so a portability layer, IPRT, supplies threads, files, strings and other primitives.

Early versions also executed some guest code in software, the so-called raw mode, to cope with processors that lacked hardware virtualisation. The project later dropped raw mode and relies on hardware assistance, though traces of the older design remain in the source. The virtual machine runs in an ordinary user process (`VBoxHeadless`, or the process the graphical interface starts), while a long-lived service, `VBoxSVC`, holds the registry of machines and their settings.

## Current state

### How the source is divided

Under `src/VBox/` the main directories are as follows (names should be checked against the version being built).

- `VMM` is the core: CPU handling, memory management, interrupts, timers, the hardware-virtualisation back ends, and a layer for host hypervisor interfaces, the native execution manager (NEM).
- `Devices` holds the PDM devices: chipsets, network cards, storage controllers, audio, USB and graphics.
- `Main` implements the management API and the XML settings.
- `Frontends` has the Qt graphical interface, the command-line tool `VBoxManage` and `VBoxHeadless`.
- `HostDrivers` holds the kernel modules.
- `Additions` holds the guest additions, the drivers and services that run *inside* a guest.
- `Storage` has the disk-image formats, `NetworkServices` the DHCP and NAT helpers, and `Runtime` is IPRT.

The top-level build uses **kBuild**, a make-based system with its own rule language. A configuration script detects the toolchain and libraries and writes `AutoConfig.kmk` and `LocalConfig.kmk`; the command `kmk` then builds everything into an output tree.

### Building the OSE, step by step

On Linux the sequence is as follows. Install a compiler, the headers of the running kernel (for the driver), and development packages for Qt, libxml2, SDL and the other libraries that the configuration step reports as missing. Run `./configure` with options to leave out what is not needed, for example the GUI for a headless build. Source the environment script it generates, and run `kmk`. Build the kernel modules from the output tree against the kernel headers, install and load them, and run the result from the output directory. A full build takes a long time and several gigabytes of disk, while a rebuild after a small change is quick, because kBuild tracks dependencies.

### Runtime architecture

`VBoxSVC` owns the machine definitions and the global state. Frontends and tools talk to it over a local COM interface: genuine COM on Windows, an XPCOM implementation on Linux. Starting a machine spawns a VM process, which loads the VMM library, opens `vboxdrv`, creates the virtual machine and its vCPU threads (called EMT, for emulation threads), and attaches the devices. A guest's access to a device arrives through the VMM's memory-mapped and port-I/O handlers at the matching PDM device, and a device may use worker threads and asynchronous I/O to avoid blocking the vCPU.

### The Main API and the SDK

The **Main API** is described in one XML interface definition, `VirtualBox.xidl`, from which headers, language bindings and documentation are generated. The **SDK** packages those with sample code for C++ (through COM or XPCOM), for a web-service front end (`vboxwebsrv`), and for Python, Java and other languages. Most automation, whether `VBoxManage`, Vagrant or a test harness, uses this API: create a machine object, set attachments and properties, open a session, launch, and listen for events.

### The generalised pattern

A privileged core as small as practical, a large user-space VMM and device layer, and a typed management API generated from one interface description. The same three-part split appears wherever a product must run across hosts with very different kernels.

## Assessment: the good, the bad and the ugly

**The good.** VirtualBox is portable across host operating systems and has mature device and storage support and a rich management API. Its source tree lets a reader follow one device from the guest's register write to the host's file system call, which makes it an excellent teaching code base.

**The bad.** The build is heavy and sensitive to the versions of the toolchain and the kernel headers. The code base is large and carries historical layers, such as raw-mode remnants and support for 32-bit hosts. Documentation of the internals is thin and in places out of date. The split of features between the OSE and the Extension Pack confuses users, and a source build is not a drop-in for the packaged product.

**The ugly.** Host-driver compatibility is a perennial cost: a new Linux kernel can break the module until it is patched, because the driver lives outside the kernel tree. Licence boundaries need attention, since the OSE is free software and the pack is not. And the security of a large user-space device model is only as good as its testing, the same concern that arose for QEMU.

## Applications beyond this domain

- **Desktop virtualisation for development and teaching.** The API makes reproducible lab environments easy to script.
- **Test automation.** Harnesses drive guests through the SDK, taking snapshots and restoring them between runs.
- **Generated-API design.** An interface-definition language that produces bindings in several languages from one source is a general pattern, used far outside virtualisation.
- **Build-system practice.** kBuild's separation of detection, configuration and per-target rules is the same discipline used in other large C and C++ code bases.
- **Cross-platform runtime libraries.** IPRT shows how to keep a portable core that hides the differences between host operating systems.

## Examples

**A headless build.** Configure without the GUI, build `VBoxManage`, `VBoxSVC` and `VBoxHeadless`, load the driver, and start a VM from the command line on a server that has no display. The result is a smaller binary set and a shorter build, which suits a continuous-integration machine.

**An API script, step by step.** A Python script imports the SDK bindings, connects to `VBoxSVC`, creates a machine object with a name and an operating-system type, saves its settings, attaches a disk to a storage controller, opens a session and launches the machine in headless mode. It then waits for an event, for example a guest property change that tells the script the guest has finished booting, and shuts the machine down. Every tool in the ecosystem is a variation of this sequence.

**A failing one.** After a host kernel upgrade, the build stops while compiling the kernel module: the module's sources use a kernel interface that changed. The fix is a newer source drop or a local patch to the module, and the lesson is that the driver is the part of the system that is most exposed to the host.

## Related problems and ideas

### Related

- **KVM and QEMU** (earlier topics) provide the comparison with a hypervisor that is part of a general-purpose kernel.
- **Device models and PDM** relate to QEMU's QOM devices, with a similar idea of typed interfaces and a lifecycle.
- **Interface definition languages and RPC** explain how the Main API is generated.
- **Out-of-tree kernel modules** in the first kernel course describe the packaging problem that `vboxdrv` illustrates.

### Opposing approaches

- **A general-purpose kernel as the hypervisor** (KVM) removes the need for a product-specific driver, and has a single maintenance path with the kernel. VirtualBox's answer is that a product needs the same experience on every host, including hosts that have no equivalent of KVM.
- **A self-contained appliance** (a bare-metal hypervisor with its own small kernel, as in some commercial products) trades portability for control of the whole stack. It avoids driver breakage but cannot use the host's desktop and tools.
- **Command-line-first tools** (libvirt with QEMU, or Vagrant over a provider) put the management layer in a separate, scriptable layer and treat the hypervisor as replaceable. VirtualBox's own typed API plays the same role from inside the product.

## Active research

Directions include isolating device models from the VM process so a flaw is contained, running on top of host hypervisor interfaces (the Windows Hypervisor Platform, and Hypervisor.framework on macOS) instead of an own driver, and supporting Arm hosts and guests. The state of each should be checked against the current release notes and the project's tracker, since support has changed from version to version.

## Future direction

Expect a growing reliance on host hypervisor interfaces in place of a custom driver where the platform offers one, Arm host support, and slimmer builds for headless server use. For a reader of the source, the lasting value is the structure: a small privileged core, a portable runtime, device models behind an interface, and a management API generated from a single description.
