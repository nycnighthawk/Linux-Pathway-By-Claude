# Patching a VMM's host-hypervisor backend: the VirtualBox KVM native execution manager

## Define the problem

VirtualBox historically shipped its own kernel driver to enter hardware virtualisation. That means a module that must track every kernel release, cannot coexist with other hypervisors that claim the CPU extensions, and cannot be signed or loaded on locked-down systems without extra steps. Most host operating systems now offer an official hypervisor interface (Windows Hypervisor Platform, macOS Hypervisor.framework, Linux KVM). The VMM can use that interface for guest execution and keep its own device models, management layer and user interface. The problem for a developer is to add or fix such a backend: map the VMM's internal operations onto another API, translate its exits and state, and test it, without breaking the other backends.

## History and approaches

VirtualBox had a **native execution manager (NEM)** layer for the Windows Hypervisor Platform and macOS Hypervisor.framework, to run under the host's hypervisor rather than its own driver; it is the model for an alternative backend. For Linux, a KVM backend for NEM was contributed by outside developers and merged in the 7.x series (details of which release and how complete it is: to verify). The approach is a back end selected at start-up: the VMM asks the backend to create the VM and vCPUs, map guest memory, read and write register state, run until the next exit, and inject interrupts; everything above (PDM devices, the debugger, saved state, snapshots) is shared. Other projects took the same decision: QEMU's accelerator interface (TCG, KVM, HVF, WHPX), and crosvm's hypervisor abstraction.

## Current state

### The backend contract

A backend provides roughly these operations: initialise and tear down the accelerator, create a VM, create and destroy vCPUs, register guest-physical memory ranges (and change or unmap them when the VMM remaps memory, for example for devices or video RAM), get and set CPU state (general registers, segments, control registers, MSRs, FPU and vector state), run a vCPU until an exit, deliver and cancel interrupts and NMIs, handle halt and wake, and report capabilities (what the host supports). Each requires a mapping from the VMM's own data structures to the host API's: register file layouts, the MSR list, CPUID results.

### Mapping KVM exits

The run loop calls `KVM_RUN` and translates each exit into the VMM's own event: port I/O to the I/O-port handler, MMIO to the memory handler, halt to the idle logic, shutdown to a triple-fault event, internal error to a fatal diagnostic, and signal interruption (`EINTR`) to a "check for requests" return. Anything unmapped is a bug to be reported with the raw exit reason, never silently ignored. State synchronisation is the subtle part: the VMM may need registers only when it handles an exit, so the backend keeps a dirty-state mask and transfers only what is needed.

### Working with a large code base

Reading code first: find where the NEM interface is declared, how an existing backend implements each operation, and how the build selects it (kBuild conditions). Make the change small, compile on a Linux host with KVM, run a known guest, collect logs (`VBoxHeadless` plus release logging flags, `VBoxManage debugvm`), and compare behaviour with the default backend. Hardware features such as CPUID leaves and MSRs often expose differences. Tests include booting several guests, snapshot and restore, hot unplug of a vCPU, and a guest that issues many I/O exits.

### Patching process

Keep the patch focused, follow the project's formatting, test with the project's tools, and send it through the channel the project uses (the VirtualBox community and its contribution process; to verify the current route).

### The pattern

An abstraction boundary between the generic VMM and the host-specific execution engine, with a table of operations, a mapped exit set, and a state-synchronisation policy.

## Assessment: the good, the bad and the ugly

**The good.** No separate kernel module to maintain; coexistence with other KVM users; the host's kernel does the privileged work and gets its security updates.

**The bad.** Differences between backends in features and performance; some VirtualBox features may be unavailable or slower on the new backend; testing multiplies across hosts and CPUs.

**The ugly.** Hidden coupling: code that assumed its own driver (raw-mode remnants, specific interrupt-injection behaviour, assumptions about when registers are valid). The contribution path for outside patches may be slow or unclear, and the interface changes between releases.

## Applications beyond this domain

- **Accelerator abstraction layers** in QEMU, crosvm and other VMMs follow the same design.
- **Portable emulators** use host APIs (Hypervisor.framework, WHPX) for speed.
- **Plugin and driver models** in other software use an ops table with a completeness check.
- **Open-source contribution practice**: reading a large code base, minimal patches, and testing against several configurations.
- **Migration between platforms**: porting a product from a custom driver to a platform API.

## Examples

**An exit mapping.** A KVM `KVM_EXIT_IO` record carries direction, port, size and count; the backend must call the VMM's I/O handler once per element and write the result back into the `kvm_run` data area for reads.

**A missing operation.** The backend table lacks the operation that sets the vCPU's debug registers; the debugger works on one backend and crashes on this one. A completeness check at start-up would have told the developer at once. The lab does this.

**A failing one.** A guest hangs on boot only on the new backend: the backend skipped a CPUID leaf that the VMM normally filters, and the guest's feature detection chose a path that needs an unsupported instruction.

## Active research

Directions include unifying accelerator interfaces across VMMs, cheaper state synchronisation between VMM and kernel, and shared test suites for backend conformance (to verify the state of each).

## Future direction

Expect VirtualBox and similar products to rely more on host hypervisor interfaces, with the custom driver kept for legacy platforms, and shared conformance tests for exit handling.
