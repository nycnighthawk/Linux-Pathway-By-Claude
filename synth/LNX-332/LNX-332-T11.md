# Patching a VMM's host-hypervisor backend: the VirtualBox KVM native execution manager

## Define the problem

VirtualBox historically shipped its own kernel driver to enter hardware virtualisation. That driver has to track every kernel release, cannot share the processor's virtualisation extensions with another hypervisor that claims them first, and on locked-down systems cannot be loaded without extra steps such as module signing. Most host operating systems now offer an official hypervisor interface: the Windows Hypervisor Platform, macOS's Hypervisor.framework, and KVM on Linux. A VMM can use that interface for guest execution and keep its own device models, management layer and user interface.

The problem for a developer is to add or fix such a backend. The task is to map the VMM's internal operations onto another API, translate its exits and its state, and test the result, all without breaking the other backends that the same code base supports. This essay builds the idea from the contract a backend must meet, to the translation of exits, to the practical work of changing a large code base, and ends with the points where such work goes wrong.

## History and approaches

### An own driver, and then host interfaces

VirtualBox's original design used its own ring-0 driver and, for old processors, software execution. The project later added a **native execution manager (NEM)**, a layer that lets the VMM run guests under the host's hypervisor rather than its own driver. NEM was built first for the Windows Hypervisor Platform and for macOS's Hypervisor.framework. It is the model for any alternative backend.

### A KVM backend for Linux

For Linux, a KVM backend for the NEM layer was written by outside developers and merged in the 7.x series. The exact release and how complete the backend is should be checked against the release notes of the version in use, since both have moved. The idea is a backend selected at start-up. The VMM asks it to create the VM and its vCPUs, map guest memory, read and write register state, run until the next exit, and inject interrupts. Everything above that boundary, including the PDM devices, the debugger, saved state and snapshots, is shared with the other backends.

### A pattern across projects

Other projects reached the same decision. QEMU's accelerator interface has separate implementations for its own translator (TCG), KVM, Apple's HVF and Windows' WHPX. The crosvm VMM has a hypervisor abstraction that hides which kernel interface sits beneath it. The common lesson is that execution is a *service* to the VMM, and an interface that names that service lets it be swapped.

## Current state

### The backend contract

A backend provides roughly these operations: initialise and tear down the accelerator; create a VM; create and destroy vCPUs; register ranges of guest-physical memory and change or remove them when the VMM remaps memory (for devices or video RAM, for example); get and set CPU state (general registers, segments, control registers, model-specific registers, floating-point and vector state); run a vCPU until an exit; deliver and cancel interrupts and non-maskable interrupts; handle halt and wake-up; and report capabilities, meaning what the host supports. Each operation needs a mapping from the VMM's own data structures to those of the host API: register-file layouts, the list of model-specific registers, and the results of CPUID queries.

### Translating KVM exits

The run loop calls `KVM_RUN` and translates each exit into one of the VMM's own events. A port-I/O exit goes to the I/O-port handler; an MMIO exit goes to the memory handler; a halt goes to the idle logic; a shutdown becomes a triple-fault event; an internal error becomes a fatal diagnostic; and an interruption by a signal (`EINTR`) becomes a return that says "check for pending requests". Anything not mapped is a bug to report with the raw exit reason and never to ignore silently.

The subtle part is **state synchronisation**. The VMM may need registers only when it handles a particular exit, while the kernel holds them between calls. Copying all state on every exit is correct and slow. A backend therefore keeps a mask of which groups of state are *dirty* or *known* on each side and transfers only what the next consumer needs. A bug in that mask produces a guest that works until some rare path reads a stale register.

### Working in a large code base

The work has a standard order. First read: find where the NEM interface is declared, how an existing backend implements each operation, and how the build selects a backend (the kBuild conditions that choose files). Then make the change small, compile on a Linux host with KVM, and run a known guest. Collect logs, with `VBoxHeadless` and the release-logging flags, and `VBoxManage debugvm` for debugging, and compare behaviour with the default backend. Differences often show first in hardware features such as CPUID leaves and model-specific registers. A sensible test set boots several guests, takes and restores a snapshot, hot-unplugs a vCPU, and runs a guest that produces many I/O exits.

### The patch process

Keep the patch focused, follow the project's formatting, test with the project's own tools, and send it through whatever channel the project currently uses. The exact route, the community forum and the contribution process, should be confirmed with the project before starting, because it has changed in the past.

### The generalised pattern

An abstraction boundary between the generic VMM and a host-specific execution engine, with a table of operations, a mapped set of exits, and an explicit policy for synchronising state. Where the table is incomplete, the code should refuse to start rather than fail later.

## Assessment: the good, the bad and the ugly

**The good.** There is no separate kernel module to maintain, so the maintenance burden falls to the host kernel. The backend coexists with other users of KVM on the same machine, and the host kernel's security updates apply to the part that does the privileged work.

**The bad.** Backends differ in features and in performance, and some VirtualBox features may be unavailable or slower on the new one. The test matrix multiplies across host operating systems and processor models. A contributor must work on a code base whose backends were not designed as equals.

**The ugly.** The hidden coupling is the worst part: code that assumed the project's own driver, with raw-mode remnants, specific interrupt-injection behaviour, and assumptions about when registers are valid. The contribution path for an outside patch may be slow or unclear, and the internal interface changes between releases, so a patch can rot while waiting.

## Applications beyond this domain

- **Accelerator abstraction layers** in QEMU, crosvm and other VMMs follow the same design, and a developer who understands one reads the others quickly.
- **Portable emulators** use host APIs (Hypervisor.framework, WHPX) for speed and keep their own devices.
- **Plugin and driver models** in other software use an operations table with a completeness check, which is a pattern worth stealing.
- **Open-source contribution practice.** Reading a large code base, making minimal patches, and testing against several configurations are the skills that carry to any project.
- **Migration between platforms.** Porting a product from a custom driver to a platform API is a recurring task wherever vendors begin to offer official interfaces.

## Examples

**An exit mapping, in detail.** A `KVM_EXIT_IO` record carries a direction, a port, a size, a count and an offset to the data. For an `out` instruction, the backend must call the VMM's port handler once for each element with the data from the record. For an `in`, it must write each result back into the data area before the next `KVM_RUN`, or the guest will read stale bytes. A backend that handles only a count of one works for most guests and breaks on string I/O instructions.

**A missing operation.** The backend table lacks the operation that sets the vCPU's debug registers. The debugger works on the default backend and crashes on this one. A completeness check at start-up, which compares the table against the list of required entries, would have told the developer at once. The lab for this topic builds exactly such a check.

**A failing one.** A guest hangs on boot only on the new backend. The backend skipped a CPUID leaf that the VMM normally filters, and the guest's feature detection chose a code path that needs an instruction the host does not provide. Comparing the CPUID output of the two backends, leaf by leaf, finds the difference in minutes.

### Opposing approaches

- **Keep the own driver.** The project can argue that its driver gives it complete control: features that a host interface does not expose, such as certain performance counters and nested configurations, remain available, and the behaviour is identical on every release. The price is the maintenance burden that motivated the change.
- **Use a different VMM instead of patching.** Where the only need is to run a guest on KVM, QEMU, Firecracker or Cloud Hypervisor already do so. Patching VirtualBox is justified only when its management layer, image formats and user base matter.
- **Out-of-process execution.** A third approach separates the execution engine into its own process with a stable protocol, so that VMM and engine can change independently. The idea is attractive and unproven at this scale, and the protocol itself becomes a new interface to maintain.

## Active research

Directions include unifying accelerator interfaces across VMMs, cheaper state synchronisation between VMM and kernel, and shared test suites for backend conformance that any VMM could run. The status of each should be checked against the project's tracker and mailing lists.

## Future direction

Expect VirtualBox and similar products to lean more on host hypervisor interfaces, with the custom driver kept for legacy platforms, and expect shared conformance tests for exit handling. For the learner, the transferable skill is the discipline of the contract: list every operation the VMM needs, map every exit, state the synchronisation policy, and check completeness before the first guest runs.
