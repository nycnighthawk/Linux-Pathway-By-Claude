# Upstreaming to KVM and QEMU: getting a change accepted

## Define the problem

A fix that works on your machine is not yet part of the project. Both KVM and QEMU are maintained by volunteers and company engineers who review by mail, apply strict style and testing expectations, and treat every line as something they will carry for years. A contributor has to find the right place and people, split the work into reviewable steps, explain the reason and the risk, accept criticism, and iterate. Failing at any step costs months, or leaves a private fork to maintain.

## History and approaches

KVM is part of the Linux kernel and follows the kernel process: patches by email to the `kvm` list (and architecture lists), sent to the maintainers found with `get_maintainer.pl`, collected in maintainer trees and merged in the next merge window; the process is described in the kernel's own documents. QEMU, developed as a separate project, also uses mailing lists (`qemu-devel`) with a patch-series workflow and a maintainers file. Both historically used plain-text mail; QEMU later added forge-based support for merge requests in parts of its flow (to verify the current policy). Both require a **Signed-off-by** line certifying the developer's right to submit the work (the Developer Certificate of Origin). Each has its own coding style: the kernel uses tabs and a documented style with a checker (`checkpatch.pl`); QEMU uses four spaces, a documented style and its own `checkpatch`. Over time, both projects added continuous integration, test requirements (selftests for KVM, qtest or functional tests for QEMU) and bots.

## Current state

### The workflow

1. **Research first.** Read the documents on submitting patches in the tree, search the list archives for earlier attempts and discussions, and read the maintainers file for the area.
2. **Make the change small and complete.** One logical change per patch; a series for larger work, ordered so that each patch builds and works; no unrelated cleanups. Add a test: a selftest or unit test for KVM, or a qtest or functional test for QEMU.
3. **Write the commit message.** A subject with a subsystem prefix (`KVM: x86: ...`, `target/i386: ...`, `hw/virtio: ...`) and a short imperative summary; a body that says what the problem is, why this fix, what the alternatives were and how it was tested; references to related commits (a `Fixes:` tag with a commit hash for a bug fix) and a `Signed-off-by:` line.
4. **Check it.** Run the style checker, build with warnings, run the project's tests, send to yourself first.
5. **Send it.** Use `git format-patch` and `git send-email`, or tools like `b4`, with a cover letter for a series; address it to the maintainers, with the relevant lists in copy.
6. **Respond to review.** Reply inline, in plain text, quote the relevant lines; accept or argue with evidence; send a new version (v2, v3) with a changelog below the three dashes; do not repost faster than reviewers can read.
7. **Follow through.** After acceptance, watch for bot reports and regressions.

### What reviewers look for

Correctness on all architectures and configurations; compatibility with live migration and saved state; security (guest-controlled values); no new user-visible behaviour without documentation; minimal API surface; maintainability; tests; and a clear explanation. For QEMU, also device model conventions (state descriptions, properties, machine-type compatibility). For KVM, also the stability promise of the user-space interface.

### The pattern

Small reviewable steps, tests and rationale with every change, structured email, and patience.

## Assessment: the good, the bad and the ugly

**The good.** The process is transparent: every comment is public and a patch is judged on its technical merits; the style tools catch much before a human sees it; maintainers give detailed feedback.

**The bad.** Review capacity is limited, so patches wait; email workflows are hard to learn, and inline replies require discipline; style rules differ between the two projects.

**The ugly.** A patch can stall without a reply; reviewers sometimes disagree; large features need years and many versions; maintainers may be unreachable. Tone can be blunt. A change that touches many areas needs several maintainers to agree.

## Applications beyond this domain

- **Any large open-source project** with mailing-list review (the kernel, GCC, Git, many toolchains) works similarly.
- **Pull-request projects** apply the same expectations through different tools.
- **Corporate engineering** benefits from small changes, explanations and tests.
- **Standards bodies** and RFC processes use iterative public review.
- **Documentation and translation projects** run on the same principles.

## Examples

**A one-line fix.** A missing check on a guest-supplied index in a KVM ioctl: the patch has a subject `KVM: x86: ...`, a body describing the failing input, a `Fixes:` tag and a selftest that reproduces it.

**A QEMU device fix.** A bounds check on a register write in a device model, with a qtest that writes the offending value.

**A failing one.** A series of five patches where patch 2 breaks the build and patch 5 undoes part of patch 3: reviewers ask for a reorganisation before reading the content. The lab flags several such mechanical problems.
