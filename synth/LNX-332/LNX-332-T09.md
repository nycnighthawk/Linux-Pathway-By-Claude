# Interrupts and timers for guests: from emulated APIC to posted interrupts

## Define the problem

Interrupts and timers are the most frequent events a guest sees. A guest kernel reprograms its timer many times a second, acknowledges every interrupt by writing a register, sends inter-processor interrupts to wake its other CPUs, and receives interrupts from its devices. If each of those actions is an exit that the hypervisor must emulate, the exits dominate the cost of running the guest, and the earlier topics have shown how expensive an exit is.

At the same time the semantics must stay exact. An interrupt must reach the right virtual CPU, in priority order, even when that CPU is not currently running on a physical one. A timer must fire when the guest asked, not when the host got around to it, and a guest that is paused and migrated must see time continue sensibly. The problem is to take the high-frequency, low-complexity part of interrupt and timer handling out of the hypervisor's path while keeping the rare, tricky cases correct.

## History and approaches

### Everything emulated in user space

The first design emulated the interrupt controller wholly in the VMM. QEMU's model of the local APIC was written for a software emulator and kept in user space, so each register access was an exit all the way to a user-space handler, and each interrupt was injected by an ioctl. It was correct and slow, and it made interrupt delivery from other host threads awkward, since every source had to reach the VMM process first.

### Moving emulation into the kernel

Placing the APIC model inside the kernel, the *in-kernel irqchip*, removed the round trip to user space for most register accesses, and made delivery from other kernel threads and from eventfds cheap. Paravirtual helpers followed: a paravirtual end-of-interrupt signal, and the `kvmclock` time source, which let a guest skip some exits by cooperating with the host. These improvements helped but kept the hypervisor in the path of every interrupt.

### Hardware assistance in stages

Hardware changes arrived in steps. Intel's **APIC virtualisation (APICv)** lets the processor virtualise reads and writes of most APIC registers, track the highest-priority pending interrupt in a virtual interrupt-request structure, and deliver interrupts to a running guest without an exit. **Posted interrupts** add a descriptor in memory where a device, or another CPU, can post a vector for a target vCPU. If the target is running, the hardware delivers the vector directly; if not, a notification wakes it on the host. AMD's equivalent is **AVIC**. For devices, **interrupt remapping** in the IOMMU, together with message-signalled interrupts, lets an assigned device's interrupt reach a guest vector with no hypervisor code on the fast path. The same sequence took place for timers: from a pure software emulation to the use of the processor's own preemption timer and, on newer parts, hardware-assisted deadlines. The pattern repeats the one from the first topic: a software mechanism is made faster by moving its common case into hardware and keeping the software for the corner cases.

## Current state

### Three delivery paths

1. **Emulated.** An interrupt source, such as an emulated device or an eventfd, calls into the in-kernel irqchip, which marks a vector pending for the target vCPU. At the next entry the hypervisor injects it. If the vCPU is running at the time, the hypervisor first sends a host inter-processor interrupt to force an exit, so that the injection happens promptly.
2. **APICv or AVIC.** The pending vector is written to a virtual interrupt-request register, and, if the target is running, a posted-interrupt notification vector goes to its physical CPU. The hardware processes the notification and delivers the interrupt to the guest with no exit. Guest writes to the end-of-interrupt, task-priority and interrupt-command registers are handled in hardware, or with a cheaper kind of exit.
3. **Device assignment.** The device's MSI or MSI-X message is routed, through interrupt remapping, to a posted-interrupt descriptor, so no host handler runs in the common case.

### MSI messages and routing

A message-signalled interrupt is just a memory write, and its two halves carry two kinds of information. The **address** says *where*: on x86 a fixed high prefix, then the destination APIC identifier and mode bits. The **data** says *what*: the vector, the delivery mode and the trigger mode. KVM keeps a routing table that maps a global system interrupt (GSI) number to either a pin on an emulated interrupt controller or an MSI message. An eventfd bound with `irqfd` to a GSI therefore turns into the right message for the right vCPU. When a guest changes an interrupt's affinity, it rewrites the device's message and the hypervisor updates the corresponding entry. Presenting enough destinations to a guest with many CPUs needs x2APIC mode (a 32-bit identifier) and an emulated IOMMU with interrupt remapping.

### Timers

The guest's local APIC timer, in TSC-deadline mode, is programmed by writing a deadline to a model-specific register. The hypervisor can implement it with a host high-resolution timer, with the processor's preemption timer while the guest runs, or with a hardware assist. Time sources, which include the TSC with scaling and offsetting, `kvmclock` and the Hyper-V reference time, must remain consistent through live migration: a guest that resumes on a host with a different TSC frequency must not see time jump.

### The generalised pattern

Keep the common path inside the hardware (virtual registers, a posted-interrupt descriptor, a notification vector) and fall back to injection through the hypervisor for the rare cases. The rare cases are the ones where the target is not running, where an interrupt must be queued for later, or where a feature is missing.

## Assessment: the good, the bad and the ugly

**The good.** Interrupt-heavy workloads see large drops in exits. Network and storage throughput rise, inter-processor interrupts get cheap, latency falls, and the design scales well with many vCPUs, because delivery no longer funnels through one host path.

**The bad.** The special cases are many: a vCPU that is not running, a blocked vCPU that needs a wake-up vector, an affinity change that races with delivery. Hardware support differs by processor model and by vendor, and some features were disabled by default or buggy on early silicon, so the fast path available on one machine may not exist on the next.

**The ugly.** Errata and security issues have appeared in interrupt remapping and in the posted-interrupt paths. Lost-wake-up bugs, where an interrupt is posted at the moment a vCPU goes to sleep and nobody wakes it, are the hardest to reproduce. Time drift in migrated guests is a recurring complaint. Nested virtualisation of these features is difficult and not always complete.

## Applications beyond this domain

- **Device passthrough in high-performance computing and network-function virtualisation** uses the same posted-interrupt paths for latency-sensitive devices.
- **Real-time systems** pin interrupts to chosen CPUs and rely on timer precision, so they use the same vocabulary and the same checks.
- **Bare-metal interrupt design**, including MSI-X, affinity and interrupt moderation, is where these ideas originated, and a good understanding of it is a prerequisite.
- **Other architectures** solve the same problem with similar structures: Arm's GICv4 can inject interrupts directly into a guest, and the RISC-V advanced interrupt architecture has a virtualisation-friendly design.
- **Monitoring** uses per-CPU interrupt counters to see how load is distributed and to find a CPU swamped by one device.

## Examples

**Encoding an MSI message.** A device with vector 0x41 and destination CPU 3 sends the address `0xfee03000` and the data `0x41` (fixed delivery, edge triggered). The high prefix `0xfee` marks the interrupt window, the 3 in the destination field names the CPU, and the data's low byte is the vector. The lab for this topic encodes and decodes such pairs, which is the best way to remember which bits mean what.

**An inter-processor interrupt, with and without help.** A guest CPU wakes another by writing to the interrupt-command register. Without hardware help that write exits, the hypervisor reads the target and vector, marks the interrupt pending on the target vCPU and, if it is running, kicks it. With APICv or AVIC the write is handled by the hardware, and if the target is running the interrupt is posted and delivered with no exit on either side. A guest that does thousands of such wake-ups per second sees the difference as a lower CPU cost.

**A failing one.** After a host kernel update, the feature is disabled because a module parameter default changed. The exits per second jump, and the network benchmark in the guest drops by a quarter. Reading the module parameters and the exit statistics (the previous topic's method) identifies the cause within a few minutes, while looking at the guest alone never would.

### Opposing approaches

- **Polling instead of interrupts.** High-performance systems such as DPDK and SPDK avoid interrupts altogether by polling devices from dedicated cores. The cost is a core that is always busy, the gain is predictable latency, and virtualised interrupt delivery becomes irrelevant for those devices.
- **Software-only emulation, kept simple.** A small VMM may prefer emulation in user space precisely because it is easy to reason about and to secure. For a handful of vCPUs and modest I/O the overhead is acceptable, and there are fewer hardware-dependent code paths to get wrong.
- **Paravirtual interrupt interfaces.** Hypervisor-specific mechanisms, such as paravirtual EOI or virtual-interrupt hypercalls, reduce exits through guest cooperation rather than silicon. They work on old hardware but need guest support, the same trade-off that appeared with virtio.

## Active research

Open questions include how to inject interrupts directly into confidential guests, where the hypervisor cannot see or change guest state; how to keep timers accurate through migration across hosts with different clocks; how to verify the posted-interrupt races formally; and how to make interrupt-heavy workloads perform well in nested virtualisation. The status of each should be checked against recent kernel and conference material.

## Future direction

Expect interrupt and timer assistance on every architecture, with the hypervisor handling only configuration, and routing described by interfaces shared with real hardware. Expect confidential-computing designs to reshape the model: when the host cannot be trusted to inject an interrupt honestly, the guest must be able to verify it. The practical consequence for a learner is that the *concepts* here (message address and data, routing, posting, deadlines) remain stable while the register names change with each generation.
