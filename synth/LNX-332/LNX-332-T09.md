# Interrupts and timers for guests: from emulated APIC to posted interrupts

## Define the problem

Interrupts and timers are the most frequent events a guest sees. A guest kernel reprograms its timer many times a second, acknowledges each interrupt by writing a register, sends inter-processor interrupts to wake other CPUs, and receives interrupts from devices. If every one of those actions is an exit that the hypervisor emulates, they dominate the cost of running the guest. At the same time the semantics must stay exact: interrupts must reach the right virtual CPU, in priority order, even when that CPU is not currently running.

## History and approaches

The first design emulated the interrupt controller entirely in user space (QEMU's APIC model), with every register access an exit and every interrupt injected by an ioctl. Moving the APIC emulation into the kernel (the in-kernel irqchip) removed a round trip to user space and made interrupt delivery from other host threads cheaper. Paravirtual helpers followed: a paravirtual end-of-interrupt and a kvmclock time source, so the guest could skip some exits. Hardware assistance came in stages. Intel's **APIC virtualization (APICv)** lets the CPU virtualise reads and writes of most APIC registers, track the highest-priority interrupt in a virtual interrupt-request structure, and deliver interrupts to a running guest without an exit. **Posted interrupts** add a descriptor in memory where a device (or another CPU) can post a vector for a target vCPU; if the vCPU is running the hardware delivers it directly, otherwise a wake-up notification tells the host. AMD's equivalent is **AVIC**. For devices, **interrupt remapping** in the IOMMU and the MSI mechanism let an assigned device's interrupt be routed to a guest vector without involving the hypervisor on the fast path. Timers moved the same way: a TSC-deadline timer mode, the VMX preemption timer for the hypervisor's own use, and later hardware support for guest timers.

## Current state

### Interrupt delivery paths

1. **Emulated**: an interrupt source (an emulated device, an eventfd) calls the in-kernel irqchip, which marks a vector pending on the target vCPU. On the next entry the hypervisor injects it. If the vCPU is running, the hypervisor must kick it with a host IPI to force an exit first.
2. **APICv or AVIC**: the pending vector is written to a virtual IRR, and, if the target is running, a **posted-interrupt notification** vector is sent to its physical CPU; the hardware processes it and delivers it without an exit. Guest register writes (EOI, ICR for IPIs, TPR) are handled in hardware or with a cheaper exit.
3. **Device passthrough**: the device's MSI or MSI-X message is routed, through interrupt remapping, to a posted-interrupt descriptor, so no host handler runs for the common case.

### MSI and routing

A message-signalled interrupt is a memory write: the **address** says where (on x86 a fixed prefix, then the destination APIC ID and mode bits) and the **data** says what (the vector, delivery mode and trigger mode). KVM keeps a **routing table** mapping a global system interrupt (GSI) number to either an interrupt-controller pin or an MSI message, so an eventfd bound with irqfd to a GSI turns into the right message for the right vCPU. Changing affinity inside the guest rewrites an entry. Virtualised MSI also needs a decision on how the hypervisor presents the interrupt controller: x2APIC with a 32-bit ID and an emulated IOMMU with interrupt remapping for guests with many CPUs.

### Timers

The guest's local APIC timer, in TSC-deadline mode, is programmed by a write to an MSR. The hypervisor can implement it with a host high-resolution timer, with the preemption timer while the guest runs, or with a hardware assist. Time sources (the TSC with scaling and offsetting, kvmclock, Hyper-V reference time) have to stay consistent across live migration.

### The pattern

Keep the common path inside the hardware: virtual registers, a posted-interrupt descriptor, and a notification vector; fall back to injection through the hypervisor for the rare cases.

## Assessment: the good, the bad and the ugly

**The good.** Large drops in exits for interrupt-heavy workloads (network, storage, IPIs), lower latency, and good scaling with many vCPUs.

**The bad.** Many special cases: a vCPU that is not running, a blocked vCPU that needs a wake-up vector, changes of affinity racing with delivery. Hardware features differ by CPU model and by vendor, and some are disabled by default or buggy on early silicon.

**The ugly.** Errata and security issues in interrupt remapping and posted-interrupt paths; hard-to-reproduce lost-wakeup bugs; time drift in migrated guests; nested virtualisation of these features.

## Applications beyond this domain

- **Device passthrough in high-performance computing** and NFV uses the same posted-interrupt paths.
- **Real-time systems** pin interrupts and rely on timer precision.
- **Bare-metal interrupt design** (MSI-X, affinity, moderation) is the source of the ideas.
- **Other architectures** (Arm GICv4 direct injection, RISC-V AIA) solve the same problem with similar structures.
- **Monitoring** uses interrupt counters to see load distribution.

## Examples

**An MSI message.** A device with vector 0x41 for destination CPU 3 sends address `0xfee03000` and data `0x41` (fixed delivery, edge). The lab encodes and decodes such pairs.

**An IPI.** A guest CPU wakes another with a write to the interrupt-command register. Without hardware help that write exits; with APICv or AVIC it is handled with a posted interrupt when the target is running.

**A failing one.** After a host kernel update the feature is disabled by a module parameter default; exits per second jump and throughput of a network benchmark drops. Reading the module parameters and the exit statistics identifies it.

## Active research

Open areas include direct injection for confidential guests, accurate timer virtualisation under migration, formal verification of posted-interrupt races, and interrupt-heavy nested workloads (to verify the state of each).

## Future direction

Expect interrupt and timer assistance on every architecture, with the hypervisor only handling configuration, and routing described by firmware-visible interfaces shared with real hardware.
