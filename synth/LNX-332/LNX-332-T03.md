# A Rust VMM from shared crates: memory map, kernel loader, devices

## Define the problem

The KVM interface gives a process a way to run a guest, but a process that merely calls `KVM_RUN` has a machine with nothing in it. To boot Linux, a VMM must supply a long list of building blocks. It needs bindings to the KVM calls, a model of guest memory that can be read and written safely, a loader that puts a kernel image and a command line where the boot protocol expects them, a description of the machine (memory map, interrupt routing), a few devices, and an event loop that waits for work. Every VMM needs the same dozen blocks, whether it targets a laptop or a server farm.

Written in C inside a single project, these blocks are hard to reuse, because each project fits them to its own structures. They also sit right next to a security boundary. A memory-safety bug in the code that emulates a serial port or a network card is a bug in a process that parses data from a hostile guest. The question this essay follows is how to share the common parts across several VMMs with different goals, and how to make the shared parts safe enough that sharing is a net gain.

## History and approaches

### One big program

QEMU grew as a single large program in C with an enormous device library. Its strength is breadth: it can emulate a vast range of machines and run almost any guest. Its weakness, for the purposes of this topic, is the same breadth. A guest-facing code base of millions of lines contains many devices that a given deployment never needs, and each is a potential flaw. The project has responded with sandboxing options, device trimming and a long-running effort to reduce what runs in the main process, but the starting point was a monolith.

### Small VMMs in Rust

Two projects showed that a VMM could be small, specialised and written in a memory-safe language. Google's crosvm, written for running guests on ChromeOS, supported only the devices that its use case needed. Amazon's Firecracker, which began as a fork of crosvm for serverless computing, reduced the device model even further to a handful of devices so that a guest could boot in a fraction of a second and the attack surface stayed small. Both projects found themselves rewriting the same blocks: KVM wrappers, guest-memory handling, boot loaders.

### Sharing as crates

The rust-vmm project, started around 2018 by engineers from several companies, turned the shared parts into independent packages ("crates") with their own versions, tests and maintainers. Firecracker and Cloud Hypervisor, both production VMMs, depend on them, as do research and teaching projects. The design rule that emerged is to split by function and to keep each crate small, so that a VMM can take what it needs and leave the rest. The alternative, a single framework that loads plug-ins, had been tried in other settings and tended to freeze its interfaces, because every plug-in depended on the framework's internals. Separate crates let each piece change at its own pace, at the cost of version management in the consumer.

## Current state

### The crates and what each does

- **kvm-ioctls** and **kvm-bindings** wrap the KVM interface. The bindings come from the kernel headers; the safe layer exposes types such as `Kvm`, `VmFd` and `VcpuFd`, and an enum, `VcpuExit`, whose variants correspond to the run-loop exit reasons that the previous topic introduced.
- **vm-memory** models guest memory as regions mapped in the process. Reads and writes go through address-checked methods that return an error for a bad address, which takes raw pointer arithmetic out of device code.
- **linux-loader** places a kernel (an ELF or compressed image on x86, a flat `Image` on arm64) and a command line into guest memory and fills in the boot parameters.
- **vm-superio** supplies legacy devices such as a serial port; **event-manager** and **vmm-sys-util** provide an epoll-based event loop and helpers around eventfds and similar primitives.
- **virtio-queue**, **virtio-device** and **vhost** handle virtqueues and the back-end side of virtio devices, covered in the next two topics.
- **vm-allocator**, **vm-fdt** and **acpi_tables** allocate addresses and interrupt lines and generate the device tree or ACPI tables that tell the guest what exists.

### Assembling a VMM, in order

1. Open KVM, create a VM, allocate guest memory regions with `vm-memory`, and register them with the kernel as slots.
2. Load the kernel and command line, then build the boot parameters and a memory map. On x86 the map must leave a hole for device windows below 4 GiB, so a guest with more than about 3 GiB of memory has RAM in two pieces.
3. Create vCPUs. For a 64-bit kernel on x86, set the registers for the entry point and build the page tables, the descriptor table and the control registers the protocol demands; on arm64 the setup is simpler, because the kernel entry convention needs a small register set and a device tree address.
4. Create the devices (a serial console, then a virtio block device and network device) and connect their interrupt lines and memory windows.
5. Run each vCPU in its own thread around the run loop, and send exits for port or memory accesses to the device that owns the address.

### The generalised pattern

A VMM is a machine description plus a dispatcher. Guest-physical addresses and interrupt lines are allocated once, recorded in a table, passed to the guest as firmware tables, and used afterwards to route exits. A change to a device's address must be made in the table, and the guest's view and the VMM's view of the table must agree. Nearly every early-boot mistake comes from disagreement between the two.

## Assessment: the good, the bad and the ugly

**The good.** Rust removes whole classes of memory-safety bugs from the code that handles guest-controlled data, which is where the largest exposure lies. The crate split lets VMMs reuse tested pieces, and the resulting binaries are small and start quickly. Reviews and fuzzing effort concentrate on shared code, so each user benefits from a bug found by another.

**The bad.** The crates are young, and their programming interfaces have changed between versions, so a VMM must pin versions and absorb breakage on upgrade. Device coverage is narrower than QEMU's, so a missing feature (a particular bus, the live migration of a given device) becomes work for the integrator. Some `unsafe` code remains at the edges, around the ioctls and the memory mappings, and it needs the same care as C.

**The ugly.** The memory-map and boot-protocol details are rarely held in one person's head, and small mistakes give silent hangs very early in boot, when no log exists. A missing reserved range, a command line past its length limit, a device window that overlaps RAM, or an initial ramdisk placed on top of the kernel's own decompression area each result in a blank screen. Debugging relies on a serial console and little else, so the first device a VMM builder writes is always the serial port.

## Applications beyond this domain

The idea of shared, versioned building blocks for a security-sensitive system is not limited to VMMs.

- Test harnesses, fuzzers and sandboxes written in Rust reuse the same crates for running a guest or a snapshot of one.
- Confidential-computing guests need a VMM of this size to keep the trusted computing base small, since the VMM may sit inside the trust boundary.
- Serverless and function platforms use micro-VMs assembled from these parts so that each invocation gets hardware isolation.
- Embedded and automotive hypervisors adopt the same crate boundaries, because they too want a small, safe, certifiable device layer.
- Teaching VMMs, a few thousand lines long, show the entire structure from loader to run loop, and they are an unusually clear way to learn how a PC is put together.

## Examples

**Booting a kernel with a serial console.** A minimal VMM allocates 128 MiB of guest memory, loads an uncompressed kernel at the address its loader reports, writes the command line `console=ttyS0`, attaches a serial device at port 0x3f8 and routes the output to the terminal. After the vCPU starts, the first sign of life is a line of text from the kernel's early messages. The distance between "no output" and "text on the screen" is typically a half-dozen small corrections, each found by adding a log line in the exit handler.

**A memory map with the hole.** Give the guest 4 GiB of RAM. The map must stop the first region at the start of the device window (commonly near 3 GiB), mark the window as reserved, and put the remaining 1 GiB above 4 GiB. The guest learns the layout from a table, on x86 the firmware's memory map as passed in the boot parameters. The lab in this topic builds such a map and checks it for overlaps and gaps.

**A failing boot.** The kernel prints nothing at all. The loader placed the command line over the initial ramdisk, so the kernel could not find it; or the `console=` argument names a device the VMM does not provide. The remedy is a layout check that prints every region and its owner, and the kernel argument `earlyprintk`, which writes to the serial port before the full driver loads.

## Related problems and ideas

### Related

- **The KVM API** (the previous topic) is what `kvm-ioctls` wraps; this topic is the same interface seen through a safer and more reusable layer.
- **Rust for Linux** in the kernel pathway shares the motivation of memory safety for code near a trust boundary.
- **Firmware tables** (device tree and ACPI) are how the guest learns the machine, and a VMM that writes them is doing the job of a small firmware.
- **Sandboxing**, including seccomp filters and jailer processes, is the other half of the security story, because safe code in a process with broad privileges is still a risk.

### Opposing approaches

- **A feature-complete monolith.** QEMU's defenders argue that users want one tool that handles every guest and every device, and that trimming it with build options and sandboxing gets most of the safety benefit without a rewrite. For heterogeneous fleets and legacy guests this argument is often correct.
- **Safe languages are not enough.** A second objection holds that language choice matters less than design: a small VMM written in C with a strict sandbox may be safer than a large one in Rust. The evidence so far suggests that the two measures add, not compete, but it does not show that Rust alone settles the matter.
- **Frameworks over crates.** Some argue that a single framework with a stable plug-in interface would reduce the integrator's burden. Experience with crate versions shows the burden is real, and the trade-off between stability and independent evolution remains unsettled.

## Active research

Open directions include formally checked VMM components, where the aim is a proof that the guest-memory layer never lets a device read outside its region; further splitting of device back ends into separate processes, each with its own sandbox; Rust bindings for newer KVM features, notably those for confidential guests; and generated test suites for the boot protocols on x86 and arm64. The state of each should be confirmed against the projects' own repositories, since they move quickly.

## Future direction

Expect the shared crates to settle around a smaller number of stable abstractions, so that upgrades become routine. Expect more of the device zoo to be written once and reused, with each device in its own process, and expect arm64 and RISC-V loaders to reach parity with x86. Over a longer period, the interesting measure is the size of the trusted part of a VMM: the smaller it becomes, the more the confidential-computing and micro-VM use cases look like one use case.
