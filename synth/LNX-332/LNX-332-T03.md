# A Rust VMM from shared crates: memory map, kernel loader, devices

## Define the problem

A VMM that boots Linux needs the same dozen building blocks as every other VMM: bindings to the KVM ioctls, a model of guest memory, a loader that places a kernel and command line where the boot protocol expects them, a description of the machine (memory map, interrupt routing), a few devices, and an event loop. Written in C inside one project, these blocks are hard to reuse, and memory-safety bugs in device code sit right next to a security boundary. The question is how to share the common parts, safely, across several VMMs with different goals.

## History and approaches

QEMU grew as a monolith in C with a huge device library. Google's crosvm (for ChromeOS, written in Rust) and Amazon's Firecracker (for serverless functions, a fork of crosvm) showed that a small VMM with few devices was both feasible and attractive for security. They shared code informally; the rust-vmm project (started around 2018) turned the shared parts into separately versioned crates that VMMs such as Firecracker, Cloud Hypervisor and others can depend on. The lesson: split by function, keep each crate small, and let each VMM assemble the pieces it needs. The alternative (one framework with plug-ins) had been tried in other projects and tended to freeze the API.

## Current state

### The crates and their jobs

- **kvm-ioctls and kvm-bindings**: safe wrappers over the KVM ioctls and the structure definitions generated from kernel headers (the layers `Kvm`, `VmFd`, `VcpuFd`, and the `VcpuExit` enum that corresponds to the run-loop reasons).
- **vm-memory**: guest memory as regions mapped into the process, with address-checked reads and writes; this removes raw pointer arithmetic from device code.
- **linux-loader**: places a kernel image (ELF or bzImage on x86, `Image` on arm64) and a command line into guest memory and fills the boot parameters.
- **vm-superio**, **event-manager**, **vmm-sys-util**: serial and other legacy devices, an epoll based event loop, and helpers such as eventfds.
- **virtio-queue**, **virtio-device**, **vhost**: virtqueue handling and the back-end side of virtio devices (next topics).
- **vm-allocator**, **vm-fdt**, **acpi_tables**: address allocation, device-tree and ACPI generation.

### Assembling a VMM

1. Open KVM, create a VM and the guest memory regions, then register them as slots.
2. Load the kernel and the command line, build the boot parameters and a memory map that includes the hole below 4 GiB reserved for device windows.
3. Create vCPUs; set up registers for the entry point and, on x86 for a 64-bit kernel, the page tables, GDT and control registers (or enter via the 32-bit protocol the loader supports).
4. Create devices (serial console, a virtio block and network device) and wire their interrupts and memory windows.
5. Run each vCPU in its own thread around the run loop, and dispatch exits for I/O and MMIO to the device that owns the address.

### The pattern

A VMM is a machine description plus a dispatcher: guest-physical addresses and interrupt lines are allocated once, recorded in a table, passed to the guest as firmware tables, and used later to route exits.

## Assessment: the good, the bad and the ugly

**The good.** Rust removes whole classes of memory-safety bugs from the device model, the crate split lets VMMs reuse tested code, and the resulting binaries are small and quick to start.

**The bad.** The crates are young and APIs change between versions; a VMM must pin versions and absorb breakage. Device coverage is narrower than QEMU, and a feature that is missing (a specific bus, live migration of a device) is work for the integrator. `unsafe` remains around the ioctl and memory-mapping edges.

**The ugly.** The memory-map and boot-protocol details are shared in nobody's head: small mistakes (a missing reserved range, a command line past its limit, an overlap of a device window with RAM) give silent hangs very early in boot. Debugging happens with a serial console and little else.

## Applications beyond this domain

- **Rust-based system components** reuse the crates for test harnesses, fuzzers and sandboxes.
- **Confidential-computing guests** need VMMs of this size to keep the trusted computing base small.
- **Serverless and function platforms** use micro-VMs built from the same parts.
- **Embedded and automotive hypervisors** adopt the same crate boundaries.
- **Teaching VMMs** show the structure with a few thousand lines.

## Examples

**Boot a kernel with a serial console.** A minimal VMM loads a kernel, writes a command line such as `console=ttyS0`, attaches a serial device at port 0x3f8 and prints guest output on the terminal.

**A memory map.** With 4 GiB of guest RAM, a map must stop the first region below the device window near 3 GiB and continue the remaining 1 GiB above 4 GiB. The lab in this topic builds such a map and checks overlaps.

**A failing boot.** The kernel prints nothing: the loader placed the command line over the initial ramdisk, or the console argument names a device the VMM does not provide. The remedy is a layout check and `earlyprintk`.

## Related problems and ideas

- **The KVM API** (previous topic) is what `kvm-ioctls` wraps.
- **Rust for Linux** (kernel internals) shares the memory-safety motivation.
- **Firmware tables** (device tree, ACPI) are how the guest learns the machine.
- **Sandboxing** (seccomp, jailer processes) is the other half of the security story.

## Active research

Open directions include formally checked VMM components, further splitting of device back ends into separate processes, Rust bindings for newer KVM features (confidential guests), and generated test suites for boot protocols (to verify the state of each).

## Future direction

Expect the shared crates to stabilise around a few core abstractions, more of the device zoo to be written once and reused, and arm64 and RISC-V parity with x86 in the loaders.
