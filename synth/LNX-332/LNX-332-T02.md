# The KVM API: turning the kernel into a hypervisor for a user-space program

## Define the problem

The processor extensions from the previous topic are privileged: only the kernel can execute the instructions that enter a guest. Yet a virtual machine monitor (VMM) needs a lot of policy that does not belong in a kernel: which devices exist, how a disk image is read, how a console reaches a terminal. The problem is to give an ordinary process a safe, narrow interface to the hardware's guest mode so that the privileged core is small and the rest can be written, debugged and sandboxed like any program.

## History and approaches

Early hypervisors put everything in one privileged layer (Xen's hypervisor plus a privileged domain), or modified a host kernel heavily. KVM (merged into Linux 2.6.20, early 2007) took a different path: make Linux itself the hypervisor. A kernel module exposes the hardware extension through a device node, the scheduler and memory manager are reused as they are, and each virtual CPU is an ordinary thread. A user-space program provided the devices; QEMU was adapted first and many others followed (kvmtool, crosvm, Firecracker, Cloud Hypervisor). The interface is a set of ioctls on file descriptors, documented in the kernel tree. The lesson that held: a small, stable, ioctl-based boundary with the device model outside the kernel lets many VMMs share one core and limits what a bug in a device can reach.

## Current state

### Three kinds of file descriptor

1. **The system descriptor**, from opening `/dev/kvm`. `KVM_GET_API_VERSION` returns the stable version (12 for a long time) and `KVM_CHECK_EXTENSION` asks whether a capability exists. `KVM_CREATE_VM` returns a VM descriptor.
2. **The VM descriptor.** It owns the guest's memory layout and the in-kernel devices. `KVM_SET_USER_MEMORY_REGION` binds a range of guest-physical addresses to a range of the VMM's own virtual memory (a slot), so guest RAM is just memory the process allocated with `mmap`. `KVM_CREATE_VCPU` returns a vCPU descriptor. Others create an in-kernel interrupt controller, irqfds and ioeventfds.
3. **The vCPU descriptor.** `KVM_SET_REGS` and `KVM_SET_SREGS` load registers, and `KVM_RUN` enters the guest. A shared structure, `struct kvm_run`, is mapped from the vCPU descriptor (its size comes from `KVM_GET_VCPU_MMAP_SIZE`); the kernel writes the exit reason and its details there.

### The run loop

A minimal VMM is a loop: load registers, call `KVM_RUN`, read `exit_reason`, act, repeat. The reasons a VMM must handle include `KVM_EXIT_IO` (port access, with direction, size and data), `KVM_EXIT_MMIO` (access to an address with no memory behind it), `KVM_EXIT_HLT`, `KVM_EXIT_SHUTDOWN`, `KVM_EXIT_FAIL_ENTRY` and `KVM_EXIT_INTERNAL_ERROR`. Many exits (page faults on mapped memory, `CPUID`, most MSR traffic) are handled inside the kernel and never reach the loop; this is why the user-space list is short. A signal or a timeout makes `KVM_RUN` return with `EINTR`.

### Setting up a guest

The classic first program allocates a page, copies a few bytes of machine code into it, registers it as guest memory at an address, points the instruction pointer there, puts the segment registers in a state the code expects (real mode is the simplest), and runs. The guest outputs a character with an `out` instruction, the VMM sees an I/O exit, prints the byte and resumes; a `hlt` ends the run. From this, Linux boots by adding the boot protocol (a kernel image, a command line, page tables and long mode or a firmware image).

### The pattern

Process owns memory; kernel owns CPU mode; every exit the kernel cannot resolve alone becomes a record in shared memory that the process interprets. The same shape appears in every KVM-based VMM.

## Assessment: the good, the bad and the ugly

**The good.** Small kernel footprint, reuse of the host scheduler and memory management, a stable interface, and a clean place to sandbox the device model (seccomp, namespaces, a separate user).

**The bad.** The interface is large in total (hundreds of ioctls, per-architecture differences, many capabilities) and the details of segment and control-register setup are unforgiving: a wrong flag gives `KVM_EXIT_FAIL_ENTRY` with a hardware code. Every exit to user space costs a system call round trip, so frequently touched devices need in-kernel paths.

**The ugly.** The guest is hostile input to the kernel: bugs in instruction emulation or MMU code have been exploitable. Compatibility promises mean old behaviour stays forever, and live migration depends on every piece of state being readable and writable through the API.

## Applications beyond this domain

- **The ioctl-plus-shared-memory pattern** is used by `io_uring`, DRM and many device drivers.
- **Sandboxes** reuse KVM for fast tests of untrusted code and for fuzzers that restore snapshots.
- **Emulators and consoles** use hardware assistance for same-architecture software.
- **Cloud micro-VM runtimes** are small VMMs written to this API.
- **Security research** drives the API directly to test hypervisor and firmware behaviour.

## Examples

**A first guest.** A page containing `mov $0x3f8,%dx; mov $'H',%al; out %al,(%dx); hlt` is mapped at address 0x1000. `KVM_RUN` returns an I/O exit for port 0x3f8 with the byte; the VMM writes it; the next `KVM_RUN` returns a halt exit.

**A memory-mapped device.** The VMM leaves a gap in guest-physical memory. An access in the gap produces `KVM_EXIT_MMIO` with address, length, direction and data; for a read the VMM fills the data field before resuming.

**A failure.** Real-mode code started with an instruction pointer in an unmapped slot gives a flood of EPT-related exits, or `KVM_EXIT_INTERNAL_ERROR` with an emulation-failure code. The cure is to check the slot layout and the code address first.

## Related problems and ideas

- **Hardware virtualization** (previous topic) supplies the exits this interface reports.
- **Memory-mapped I/O and port I/O** are what the guest does to reach devices.
- **Seccomp and sandboxing** shrink the VMM's exposure.
- **Signals and threads** in the VMM decide how a vCPU is interrupted.

## Active research

Directions include confidential-computing extensions to the API (private memory and guest-managed pages), faster exits through in-kernel handling and shared rings, safer languages for the VMM, and snapshot-restore of guests for fast start (to verify the state of each).

## Future direction

Expect the API to grow around confidential guests, richer per-vCPU state for live migration, and more handling pushed into the kernel for the busiest devices, with the user-space loop remaining the place where policy lives.
