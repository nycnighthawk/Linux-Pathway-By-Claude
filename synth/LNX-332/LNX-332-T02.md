# The KVM API: turning the kernel into a hypervisor for a user-space program

## Define the problem

The previous topic ended with a processor that can run a guest directly and return control at chosen events. That capability is privileged. Only code in the most privileged mode can execute the instructions that enter a guest, so a normal program cannot use it unaided. Yet building a working virtual machine takes a great deal of work that has nothing to do with privilege. Someone must decide which devices the guest sees, read a disk image from a file, connect a console to a terminal, apply a policy about how much memory the guest may use, and save the machine's state to disk. If all of that lived in the kernel, the privileged core would be large, hard to audit and tied to the kernel's release schedule.

The problem, then, is one of *division of labour*. The kernel should own what only it can do (switch the CPU into guest mode, hold the second layer of address translation, route interrupts quickly) and should expose that through a narrow, stable interface. A user-space program should own everything else, so that it can be written in any language, debugged with ordinary tools, and confined with ordinary sandboxing. This essay follows how the kernel's answer, the KVM interface, solved the division, how a minimal program uses it, and what remains uncomfortable about it.

## History and approaches

### Everything in one privileged layer

The first generation of x86 hypervisors placed the monitor in the most privileged layer and wrote their own scheduler, memory manager and drivers there. Xen's design, in which a small hypervisor runs beneath a privileged control domain that holds the real drivers, is the best-known example. VMware's early products took a second route: a kernel module and a user-space process cooperated, but the monitor was a large piece of proprietary code that did its own memory and device handling. Both approaches work. Both also duplicate the work that a general-purpose kernel already does well, such as scheduling threads fairly and managing physical memory, and both must maintain drivers for every machine they run on.

### Make the kernel the hypervisor

KVM, written at Qumranet by Avi Kivity and colleagues and merged into Linux 2.6.20 in early 2007, took the opposite view. A loadable module, `kvm` plus `kvm-intel` or `kvm-amd`, adds the hardware extension as a service of the existing kernel. A virtual CPU is a normal thread, which the usual scheduler places and preempts. Guest memory is an ordinary mapping in a normal process, which the usual memory manager swaps, merges and compacts. The device model stayed outside: QEMU was adapted first, since it already emulated a whole PC in software, and then a family of purpose-built VMMs followed, among them kvmtool, crosvm, Firecracker and Cloud Hypervisor.

### The shape of the boundary

The interface was made of file descriptors and `ioctl` calls, the same style used for many device drivers, and it was documented in the kernel tree from the start. The lesson that held for nearly two decades is that a small, versioned, ioctl-based boundary lets many VMMs share one privileged core while keeping device bugs on the unprivileged side. A flaw in an emulated network card then crashes or compromises a user process, not the kernel. The cost of that choice is that every operation the VMM must perform for the guest crosses the system-call boundary, a cost the later topics on virtio and vhost exist to reduce.

## Current state

### Three kinds of descriptor

The API arranges its calls around three descriptors, each created from the one before.

1. **The system descriptor** comes from opening `/dev/kvm`. `KVM_GET_API_VERSION` returns the stable interface version, which has been 12 for a very long time and which a program should check first. `KVM_CHECK_EXTENSION` asks whether a particular capability exists, which is how a VMM learns about optional features without version numbers. `KVM_CREATE_VM` returns the next descriptor.
2. **The VM descriptor** owns the guest's memory layout and any devices that live inside the kernel. `KVM_SET_USER_MEMORY_REGION` binds a range of guest-physical addresses to a range of the VMM's own virtual addresses, a *memory slot*. Guest RAM is therefore memory the process obtained with `mmap`, and the process can read and write it directly, which is how a loader copies a kernel into it. Other calls on this descriptor create vCPUs, an in-kernel interrupt controller, and the `irqfd` and `ioeventfd` connections that tie guest interrupts and doorbells to ordinary file descriptors. Dirty-page tracking for live migration also lives here.
3. **The vCPU descriptor** represents one virtual processor. `KVM_SET_REGS` and `KVM_SET_SREGS` load general and special registers; `KVM_GET_*` counterparts read them; `KVM_RUN` enters the guest. A structure, `struct kvm_run`, is mapped from the vCPU descriptor (its size comes from `KVM_GET_VCPU_MMAP_SIZE`), and the kernel fills it in with the reason the guest stopped and the details of what it wanted.

### The run loop

A minimal VMM reduces to a loop: set up registers, call `KVM_RUN`, read `exit_reason` from the shared structure, act on it, and repeat. The reasons that a simple VMM must handle are few. `KVM_EXIT_IO` reports a port access with its direction, size and data. `KVM_EXIT_MMIO` reports a read or write to a guest-physical address that has no memory behind it, with the address, length and data. `KVM_EXIT_HLT` reports that the guest halted. `KVM_EXIT_SHUTDOWN`, `KVM_EXIT_FAIL_ENTRY` and `KVM_EXIT_INTERNAL_ERROR` report conditions that usually mean something is wrong. The list is short because most exits never reach user space. Page faults on mapped memory, `CPUID`, most model-specific register traffic and the timer are resolved inside the kernel, and `KVM_RUN` returns only when the VMM's own judgement is needed. A signal sent to the thread, or a timeout, makes the call return with the error `EINTR`, which is how the VMM stops or pauses a vCPU from outside.

### The first guest, built up from nothing

The smallest useful program shows the whole interface in about sixty lines of C. It proceeds in order.

- Open `/dev/kvm`, check the API version, create a VM.
- Allocate one page of memory with `mmap`, copy a few bytes of machine code into it, and register the page as a slot at some guest-physical address.
- Create one vCPU and map its `kvm_run` structure.
- Set the segment registers to a state the code expects (real mode with a base of zero is the simplest), and point the instruction pointer at the code.
- Loop on `KVM_RUN`, printing any byte the guest writes to a port, and stop when the guest halts.

To turn that toy into a Linux boot, the VMM adds the boot protocol: it places a kernel image, a command line, and a small set of page tables in memory, switches the vCPU to long mode (or uses the 32-bit entry point the protocol defines), and provides either a firmware image or a table that describes the hardware. Everything beyond that point is devices, covered in the next topics.

### The generalised pattern

The process owns memory. The kernel owns processor mode. Every exit that the kernel cannot resolve alone becomes a record in memory shared with the process, which interprets it and decides what the guest sees. That pattern, a privileged engine that does the hard fast work and hands anything ambiguous up as a structured event, appears in every KVM-based VMM, whatever its language or size.

## Assessment: the good, the bad and the ugly

**The good.** The kernel footprint is small relative to the function delivered, because scheduling, memory management, cgroups, and power management come from the host. The interface is stable and versioned by capability, so a VMM binary built years ago keeps working. The device model sits in a process that can be confined with `seccomp`, namespaces, a separate user and a restricted file system, and that is a stronger position than a device bug inside the kernel would give.

**The bad.** The interface is large in total: hundreds of ioctls, per-architecture differences, and a long list of capabilities that behave differently across kernel versions. The details of segment and control-register setup are unforgiving. A wrong flag produces `KVM_EXIT_FAIL_ENTRY` with a hardware-specific code that means nothing until looked up in the processor manual. Every exit to user space costs a round trip through the system-call layer, so devices that the guest touches thousands of times a second need paths that stay inside the kernel (an in-kernel interrupt controller, `ioeventfd` for doorbells, vhost back ends).

**The ugly.** To the kernel, the guest is hostile input. Bugs in the instruction emulator, which handles the rare instruction the hardware cannot complete by itself, and in the MMU code have been exploitable more than once, and a kernel-level flaw defeats every sandbox on the user-space side. A second awkward point is compatibility: promises to old VMMs mean old behaviour stays forever, and live migration requires that every piece of state a guest can observe be readable and writable through the API. Whenever a new processor feature adds state, the interface needs a new ioctl and every VMM needs updating to save it.

## Applications beyond this domain

The same ioctl-plus-shared-memory style appears elsewhere in Linux. `io_uring` shares submission and completion rings with user space. The graphics subsystem passes command buffers through mapped memory. Many device drivers expose a descriptor whose ioctls configure a hardware engine and whose mapped memory carries the data. The pattern suits any case where a privileged component does work on behalf of a process but a long list of policy choices belongs to the process.

KVM itself is reused for tasks that have little to do with running a server operating system. Fuzzers use it to snapshot and restore a program's whole state quickly. Sandboxes for untrusted code place the code in a tiny guest. Cloud function platforms build micro-VMs, small VMMs written against this interface with a handful of devices. Researchers drive the API directly to explore how firmware and hypervisors behave under unusual register states.

## Examples

**A first guest, traced step by step.** Place a four-instruction program in a page (set the data register to 0x3f8, set the accumulator to the letter H, write that byte to the port, halt) mapped at guest-physical address 0x1000. Set the code segment to base zero, the instruction pointer to 0x1000, and the flags register to its required initial value. The first `KVM_RUN` returns with `exit_reason` equal to `KVM_EXIT_IO`, direction out, port 0x3f8, size one, and the data byte at an offset recorded in the structure. The VMM prints the letter and calls `KVM_RUN` again; the second call returns `KVM_EXIT_HLT`. Two exits, one printed letter: the entire interface at work.

**A memory-mapped device.** The VMM leaves a gap in the guest-physical layout and decides that the gap is a device. When the guest reads an address in the gap, `KVM_EXIT_MMIO` returns with the address, the length and a flag that says read. The VMM looks up which device owns the address, computes the value, writes it into the data field, and resumes; the instruction then completes as if memory had answered. For a write, the VMM reads the data field instead.

**A failure that teaches.** A first program starts a real-mode guest with the instruction pointer pointing into a region that was never registered as a slot. The first fetch faults in the second layer, no slot covers the address, and `KVM_RUN` returns with an internal error, or loops with a stream of exits that make no progress. The lesson is to check the slot layout and the code address before suspecting the processor state, and to log every exit during bring-up.

## Related problems and ideas

### Related

- **Hardware virtualization** (the previous topic) supplies the exits this interface reports.
- **Port and memory-mapped I/O** are the two ways a guest driver reaches a device, and each produces its own exit type.
- **Seccomp and sandboxing** reduce what a compromised VMM process can do, so they complete the isolation story.
- **Signals and threading** in the VMM decide how a running vCPU is interrupted, paused or snapshotted.

### Opposing approaches

- **Monolithic hypervisors** (Xen's own hypervisor, VMware ESXi's kernel) keep the scheduler and drivers in the privileged layer. They can tune the machine specifically for virtualisation and have a smaller attack surface in some respects, but they need their own driver ecosystem and hardware certification, which Linux already has.
- **Type-1 microkernel hypervisors** (the L4 family and others) argue that the privileged core should be tiny and formally analysable, and that everything, including drivers, should be unprivileged components. KVM's critics point out that the whole Linux kernel is now part of the trusted computing base; microkernel proponents answer that this base is far larger than it needs to be. The counter-argument, from KVM's defenders, is that Linux is the best-tested hardware abstraction available and that reuse beats purity in practice.
- **In-kernel device models** (the early vhost designs, and the in-kernel interrupt controllers) accept a larger kernel to remove user-space round trips. Each device that moves into the kernel gains speed and gives up some of the isolation that made the design attractive.

## Active research

Confidential computing is the largest current area: guests whose memory the host cannot read need extensions to the API, such as memory that the VMM can allocate but not map (the guest_memfd mechanism in recent kernels), and new exit types for guest-initiated sharing of pages. A second theme is faster exits, through handling more in the kernel or by exchanging events over shared rings. A third is writing the VMM in safer languages and splitting device back ends into their own processes, so that a compromise of one device cannot reach another. A fourth is snapshot and restore for fast start, where the goal is to resume a guest in milliseconds from a saved image. The status of each should be checked against the kernel documentation and mailing lists, since the interface moves with each release.

## Future direction

Expect the API to grow around confidential guests and richer per-vCPU state for migration, and expect more handling to move into the kernel for the busiest devices, while the user-space run loop remains the place where policy lives. Over a long horizon, the interesting question is how small the user-space side can become: projects that offer only a handful of devices, written in Rust and run under tight sandboxes, suggest that the answer is very small, and that the broad device zoo will be carried by separate processes rather than one monolith.
