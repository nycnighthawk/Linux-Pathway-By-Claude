# Hardware virtualization: how a CPU runs a guest and hands control back

## Define the problem

Every later topic in this course rests on one question: how can an operating system that was written to own a machine run as a guest on a machine it does not own? A kernel expects to execute privileged instructions, to edit the page tables that define its address space, to program the interrupt controller, and to read and write device registers. A hypervisor that hosts such a kernel must let the guest believe all of this is true while keeping the real control of the processor, memory and devices for itself. Three outcomes count as failure. In an escape the guest changes state that belongs to the host. In a silent wrong answer an instruction gives a different result than it would on bare metal, so the guest misbehaves in ways nobody can trace. In a cost failure everything works but runs so slowly that nobody adopts the design.

An essay on the hardware side has to begin with a simple observation: the guest does not need to be *watched* all the time, only *stopped at the right moments*. If the processor can run guest instructions directly, at full speed, and can be told in advance which events must return control to the hypervisor, then safety and speed stop being opposed. The rest of this essay follows how that idea was reached, how it is built today, what it costs, and where it is going. It covers the processor side only: the execution mode, the structure that holds guest and host state, the two-layer address translation, and the exit events. Software that organises those exits (KVM, a user-space VMM, device models) is the subject of the topics that follow.

## History and approaches

### The theory: what makes trapping enough

The earliest clear statement is the 1974 paper by Gerald Popek and Robert Goldberg. They separated instructions into *privileged* ones, which trap when run outside the most privileged mode, and *sensitive* ones, which read or change the configuration of the machine or behave differently depending on it. Their theorem says that a machine can be virtualised by simple trap-and-emulate when every sensitive instruction is also privileged. The guest then runs in a lower privilege level; whenever it attempts something sensitive, the processor traps; and a small monitor emulates the effect and resumes the guest. Mainframes of the era were designed this way, and the approach was productive for decades.

### The x86 problem

The x86 architecture of the 1990s violated the condition. A handful of instructions, such as reading the code segment's privilege level or popping the flags register, were sensitive but did not trap in user mode; they simply produced a different result or silently ignored part of the request. A guest kernel running in a lower ring would therefore observe the deception, or lose an update it believed it had made. Trap-and-emulate alone could not host an unmodified x86 operating system.

### Three software workarounds

Three answers appeared, and each shaped the vocabulary still used.

- **Binary translation.** VMware's first products, from the late 1990s, scanned guest kernel code just before running it and rewrote the troublesome instructions into safe sequences, while user-mode code ran directly. For memory, the monitor kept *shadow page tables*: private copies of the guest's tables that combined the guest's mapping with the host's. This worked on unmodified guests, but it was intricate, and every guest page-table edit forced the monitor to update the shadow copy.
- **Paravirtualisation.** The Xen project (published at SOSP in 2003) took the opposite view: change the guest kernel so that it asks the hypervisor for privileged operations through explicit calls. That was fast and relatively simple for the hypervisor, but it excluded closed-source guests and tied every guest kernel to one hypervisor interface.
- **Pure interpretation.** Emulators such as Bochs and early QEMU, which decode and execute each guest instruction in software, avoided the problem entirely and stayed far too slow for production.

The lesson the industry drew was that a correct software scheme could be built, but at the price of complexity and of the hypervisor sitting in the middle of operations that a guest performs thousands of times a second.

### Hardware assistance

Intel's VT-x and AMD's AMD-V arrived in 2005 and 2006. They added a new axis of execution: instead of squeezing the guest into a lower ring, the processor has a *guest mode* in which the guest kernel runs at its normal privilege level (ring 0 for its own kernel) and the hardware enforces the boundary. The hypervisor selects which events cause control to leave guest mode. That restored the Popek and Goldberg property by construction: anything the hypervisor cares about can be made to trap, whatever the instruction's original classification.

The first generation still used shadow page tables, and the monitor spent much of its time on exits caused by guest page-table edits. Nested paging, introduced as AMD's NPT in 2007 and Intel's EPT in 2008, moved the second layer of translation into the memory management unit and removed that source of exits. Later generations added tagged TLB entries (VPID on Intel, ASID on AMD) so that a guest switch does not flush the whole TLB, virtual interrupt controllers (Intel's APICv and AMD's AVIC), and support for running a hypervisor inside a guest. The pattern is consistent: each generation took a mechanism that software did slowly and made it a hardware feature, usually keeping the software path as a fallback for older parts.

## Current state

### Entering and leaving the guest

On Intel hardware, software turns on the extension and enters VMX operation with `VMXON`. Each virtual CPU has a **VMCS** (virtual-machine control structure), a region of memory whose layout the CPU defines but does not document at field level; software reaches it through `VMREAD` and `VMWRITE` after making it current with `VMPTRLD`. Its contents fall into four groups: the *guest-state area* (registers, segment state, control registers), the *host-state area* (what to load on exit), the *execution controls* (which events cause an exit) and the *exit-information fields* (why the last exit happened). `VMLAUNCH` enters a guest for the first time and `VMRESUME` continues it. On AMD hardware the equivalent is the **VMCB** (virtual-machine control block), a page that holds a control area and a state-save area, and the single instruction `VMRUN` loads the guest state from the block, runs until an *intercept* fires, and writes the guest state back.

The design is symmetric in outline and different in detail. Intel splits state between the VMCS and registers the hypervisor must save itself, and requires specific instruction sequences to manage the structure. AMD keeps nearly everything in the VMCB. Both let the hypervisor decide, per virtual CPU, what to intercept: which instructions, which exceptions, which I/O ports (through a bitmap) and model-specific registers, and whether external interrupts return control.

### What an exit looks like

When the guest does something that is intercepted, the processor stores the guest state, records a numeric reason plus any qualification data, loads the host state and resumes in the hypervisor. A few reasons matter in nearly every discussion on Intel: a `CPUID` instruction (reason 10), `HLT` (12), port I/O (30), an external interrupt (1), and an EPT violation (48). The hypervisor reads the reason, performs the emulation, adjusts the guest's instruction pointer when needed, and resumes. A full round trip costs on the order of a thousand cycles or more on recent parts (measure it on the target CPU before relying on a number). That figure is the reason for the whole design discipline that follows: make the common operations not exit at all, and make the remaining exits cheap to handle.

### Two-dimensional paging

With EPT or NPT, address translation has two layers. The guest's own page tables map guest-virtual addresses to guest-physical addresses, exactly as on bare metal. A second set, owned by the hypervisor, maps guest-physical addresses to host-physical addresses. When the TLB misses, the hardware walks the guest tables, but every guest-physical address it meets on the way, whether a table pointer or the final data page, must itself be translated through the second layer. With four levels on each side the worst case touches 24 memory locations, because each of the five addresses involved (four table pointers and the data) needs a four-level nested walk plus its own read. Several mechanisms exist to hide this cost: caches for the intermediate steps of a walk, large pages in either layer (a one-gigabyte host page can cover many guest-physical regions), and TLB tagging.

A guest-physical address that is absent from the second layer raises an **EPT violation** (on AMD, a nested page fault), which exits to the hypervisor. The hypervisor then has three choices: allocate and map memory (the lazy population of a guest's RAM works this way), treat the access as a device register and call an emulation routine, or reflect the fault into the guest if the guest's own tables are at fault. A related event, an **EPT misconfiguration**, signals deliberately invalid entries; hypervisors use it to trap accesses to memory-mapped devices cheaply.

### The generalised pattern

The structure repeats across architectures. The CPU offers a guest mode. A block of memory, owned by the hypervisor and interpreted by the CPU, holds the guest's state and the list of events to intercept. Memory has two translation layers, and the second belongs to the hypervisor. Control returns to software at every intercepted event, which provides the *policy hook*. Arm's EL2 with stage-2 translation, and the hypervisor extension of RISC-V, follow the same idea, with different names and different amounts of state kept in hardware. Every later topic in this course, from the `/dev/kvm` interface to virtio to VirtualBox's engine, is a way of organising the exit handling that this pattern requires.

## Assessment: the good, the bad and the ugly

**The good.** Compute-heavy guests run at close to native speed, because the instructions execute on the real CPU with no translation, and nested paging removed the largest remaining cost of memory virtualisation. The interface is architectural, so one hypervisor design serves a whole family of processors, and unmodified guests, closed-source ones included, work without changes.

**The bad.** Exits are expensive, so workloads with many of them (high-rate I/O, frequent timers, interrupt storms) lose a lot of throughput. That cost is the reason paravirtual devices exist, and the reason interrupt virtualisation was added. Nested paging makes a TLB miss costlier than on bare metal, so a hypervisor that fails to back guest memory with huge pages can see a measurable slowdown on memory-intensive code. The two vendors differ in field layout, instruction names and available features, so portable software carries two code paths, and some features exist on one vendor long before the other.

**The ugly.** The hypervisor depends on behaviour it cannot inspect. Processor errata appear as guests that fail only on one stepping. Speculative-execution side channels, including several that cross the guest boundary, forced mitigations such as flushing the first-level data cache on entry or disabling simultaneous multithreading for untrusted tenants, and those mitigations cost real performance. Nested virtualisation, where the guest is itself a hypervisor, multiplies exits: the outer hypervisor must emulate the VMCS operations of the inner one, so a single inner exit may cost many outer ones. Finally, some controls are documented only in the vendor manuals, in the precise and unforgiving language of reference text, and a mistake there shows up as a hang, not as an error message.

## Applications beyond this domain

The same two-layer structure reappears wherever a boundary must be enforced by hardware rather than by convention.

- **Micro-VMs and hardware-isolated containers.** A small guest kernel in a stripped-down virtual machine gives a boundary that a shared-kernel container cannot match, and the cost of starting one is now measured in milliseconds.
- **Security tooling.** Intercepting events lets software watch a guest from outside. Virtual-machine introspection tools, and kernel-integrity monitors in desktop operating systems, use a second translation layer to mark kernel memory read-only even against the kernel itself.
- **Operating-system features.** Virtualisation-based security in desktop systems places sensitive secrets in a small, isolated virtual world next to the main one, using nothing more than the facilities described above.
- **Emulators and debuggers.** Fast execution with hooks at selected events is exactly what a debugger or a record-and-replay tool wants.
- **Cloud platforms.** Multi-tenancy at scale rests on this boundary. The provider's trust in the tenant's code is low, and the processor mechanism is what justifies sharing a socket between them.

## Examples

**A CPUID exit, step by step.** A guest boots and executes `CPUID` to learn which features exist. The control field for that instruction forces an exit. The hypervisor reads the requested leaf from a saved register, looks up the value the operator chose to present (a model with some features hidden, for example, so that a migration to an older host is safe), writes the answer into the guest's registers, advances the saved instruction pointer by the length of the instruction, and resumes. The guest sees a CPU with exactly the features the operator selected. Total effect: one exit, a few hundred instructions of host code, and an observable change in the guest's world, which is the policy hook in its purest form.

**A device register.** A guest driver writes to the address of a device's control register. That address is not backed by RAM in the second layer, so the write faults, and the hypervisor receives an EPT violation with the faulting guest-physical address and the access type. It decodes the instruction (or uses decode information supplied by the hardware where available), calls the model of the device, and resumes after the write. If the same register were accessed one million times a second, the exit cost would dominate, which is exactly the situation virtio was invented to avoid.

**The page-walk arithmetic.** Suppose the guest uses four-level paging and so does the host. A guest-virtual access that misses the TLB must read four guest table entries. Each of those entries has a guest-physical address that must be translated through the host's four levels, costing four reads, plus the read of the entry itself, so each guest level costs five memory references, and the final data address needs four more host reads on top of its own access. Counting gives 4 times 5 plus 4, which is 24 references before the data. With one-gigabyte pages in the host layer, each nested walk shortens to two levels and the count drops sharply. That arithmetic is why a host configured with transparent huge pages and a guest memory backing of large pages is such a common recommendation.

**A failing one.** A machine reports the virtualisation flag in `/proc/cpuinfo`, but loading `kvm_intel` fails and `/dev/kvm` never appears. Firmware has switched the extension off (or a different hypervisor on the same host has already claimed it). The error message names the cause in the kernel log, and the fix is a firmware setting, not a software change. A second failure of the same family: two hypervisors that each need exclusive use of the extension cannot run at once, and the second one to start sees the first one's claim.

## Related problems and ideas

### Related

- **Memory management and page tables.** The second translation layer only makes sense to someone who understands the first. The kernel's own memory-management code, covered in the kernel pathway, supplies the vocabulary for both layers.
- **Interrupt handling.** What an interrupt controller does, and what a guest expects from it, explains why interrupt virtualisation became a separate hardware feature (the subject of the ninth topic in this course).
- **Processor security.** The side-channel research that produced mitigations for speculative execution is the reason that isolation of guest state is a living research area and not a solved problem.
- **Device assignment and IOMMUs.** Handing a physical device to a guest uses a related hardware unit that translates device addresses, completing the picture for DMA.

### Opposing approaches

Two alternatives deserve a fair hearing, because each is still the right answer somewhere.

- **Containers and namespaces** isolate by software rules inside a single kernel. They start faster, use less memory and have almost no overhead, but the isolation depends on the kernel's correctness: any kernel bug is a path out of the sandbox. The hardware boundary is smaller and simpler to reason about, which is why high-risk multi-tenant services combine both.
- **Paravirtualisation and software-only schemes** remain in use: Xen paravirtualised guests, binary translation in some emulators, and the language-level sandboxes of the web. They require cooperation from the guest or give up speed, but they run where the hardware extensions are absent or restricted, for example on a device whose firmware blocks them.
- **Unikernels and library operating systems** move the argument to the guest side: a single-purpose guest, linked with a thin runtime, removes most privileged operations and so most exits.

## Active research

Open questions cluster around five themes. The first is reducing the cost of exits, either by handling more events inside the guest or by batching. The second is **confidential computing**: AMD's encrypted-state extensions and Intel's trust domains make the guest's memory and registers opaque to the hypervisor itself, so the hypervisor becomes untrusted and the exit protocol changes accordingly. The third is the performance and correctness of nested virtualisation. The fourth is formal verification of small hypervisor kernels, where the aim is to prove the isolation property mechanically. The fifth is side-channel-safe scheduling, for example never co-scheduling two tenants on sibling threads. Groups at universities, the major CPU vendors and the cloud providers work on each; the state of each result should be checked against current papers before it is taught as settled.

## Future direction

The trend is that more of the hypervisor's job moves into hardware: interrupt and timer virtualisation, device assignment with isolation, and finer control over which exits are even possible. A second trend splits the hypervisor into a trusted part, which holds the guest's secrets, and an untrusted part, which still manages resources; that split drives the design of confidential-computing guests. A third is the spread of the same two-level structure to Arm servers and to RISC-V, which makes cross-architecture knowledge more valuable. Watch for new vendor extensions in each processor generation, for kernel support appearing in the release that follows, and for mitigation costs shifting as new side channels are found.
