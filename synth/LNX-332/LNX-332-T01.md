# Hardware virtualization: how a CPU runs a guest and hands control back

## Define the problem

A hypervisor must let an unmodified operating system believe it owns the machine while the host keeps control of the CPU, memory and devices. The guest kernel executes privileged instructions, edits page tables, programs interrupt controllers and touches device registers. Each of those actions must either be harmless, be made safe by the hardware, or be caught so software can emulate it. The failure modes are an escape (the guest changes host state), a silent wrong answer (an instruction behaves differently from bare metal), and a cost so high that nobody uses the result.

This topic covers the processor side: the extensions that make the guest run directly on the CPU, the structure that holds guest and host state, the second level of address translation, and the events (exits) that return control to the hypervisor. Later topics build software on it.

## History and approaches

**The classical condition.** Popek and Goldberg (1974) stated that an architecture can be virtualised by trap-and-emulate if every sensitive instruction (one that reads or changes machine configuration) is also privileged, so it traps in user mode. The original x86 broke this rule: some sensitive instructions silently behaved differently outside ring 0.

**Binary translation.** VMware's first products rewrote guest kernel code on the fly, replacing the troublesome instructions with safe sequences, and used shadow page tables for memory. It worked on unmodified guests but was complex and slow on workloads heavy in privileged operations.

**Paravirtualisation.** Xen (2003) changed the guest kernel to call the hypervisor explicitly. This was fast and simple for the hypervisor but needed a modified guest, which excluded closed-source systems.

**Hardware assistance.** Intel's VT-x and AMD's AMD-V (both around 2005 and 2006) added a new execution mode in which the guest runs at its normal privilege levels while the hardware enforces the boundary. Early versions still needed shadow page tables. Nested paging (AMD's NPT, Intel's EPT, around 2007 and 2008) moved address translation into the hardware, removing the largest source of exits. Later generations added virtual processor identifiers to avoid TLB flushes, interrupt virtualisation (APICv, AVIC), and support for nested virtualisation. The pattern: each generation took a costly software mechanism and turned it into a hardware feature with a software fallback (dates to verify).

## Current state

### Execution modes and state structures

On Intel, software enables the extension and enters VMX operation with `VMXON`. A guest runs under a **VMCS** (virtual-machine control structure), a memory region the CPU reads and writes through `VMREAD`, `VMWRITE`, `VMCLEAR` and `VMPTRLD`. Its fields fall into four groups: guest state, host state, execution controls and exit information. `VMLAUNCH` starts a guest, `VMRESUME` continues it. On AMD, the structure is the **VMCB**, and the instruction is `VMRUN`, which loads guest state from the block and runs until an intercept saves it back. In both designs the hypervisor chooses what to intercept: which instructions, which exceptions, which I/O ports and model-specific registers, and whether external interrupts exit.

### Exits

When the guest does something that is intercepted, the CPU stores the guest state, records a reason (and qualification data), loads host state and continues in the hypervisor. Typical reasons: `CPUID`, `HLT`, port I/O, MSR access, an external interrupt, a control-register write, and the memory-translation fault described next. The hypervisor handles the event, updates guest state, and resumes. The cost of one round trip is on the order of a thousand cycles or more (to verify per CPU), so the design goal is to make common operations not exit at all.

### Two-dimensional paging

With EPT or NPT there are two sets of page tables. The guest tables map guest-virtual to guest-physical addresses; the nested tables, owned by the hypervisor, map guest-physical to host-physical. On a TLB miss the hardware walks the guest tables, and every guest-physical address it meets (each table pointer and the final data address) has to be translated through the nested tables as well. With four levels on both sides a worst-case walk touches 24 memory locations, which is why page walk caches, large pages and TLB tags matter so much. A page absent from the nested tables causes an **EPT violation** (NPT fault) exit; the hypervisor allocates memory, emulates a device (for a memory-mapped register) or sends the fault to the guest.

### The pattern

Run guest code natively, intercept only what must be controlled, keep state in a hardware-defined block, translate memory in two layers, and let software decide the policy at each exit. Every later topic (KVM, QEMU, virtio, VirtualBox) is a way of organising that exit handling.

## Assessment: the good, the bad and the ugly

**The good.** Unmodified guests run at close to native speed for compute, and nested paging removed the biggest cost of memory virtualisation. The interface is architectural, so one hypervisor design serves many CPUs.

**The bad.** Exits are expensive and workloads with many of them (I/O, interrupts, timers) suffer; this drives paravirtual devices and interrupt virtualisation. Nested paging makes TLB misses costlier, so huge pages matter. The two vendors differ in detail (VMCS fields against VMCB layout, instruction names), so software carries two code paths.

**The ugly.** The hypervisor trusts hardware state it cannot inspect, and processor errata and speculative-execution side channels cross the guest boundary; mitigations (cache flushes on entry, disabled SMT) cost performance. Nested virtualisation multiplies exits and is hard to get right. Exact behaviour of rarely used controls is documented only in the vendor manuals.

## Applications beyond this domain

- **Containers with hardware isolation** (micro-VMs) rely on the same extensions for a strong boundary around a small guest.
- **Security tooling** uses the exit mechanism for introspection, kernel integrity monitors and sandboxing a browser or an enclave-like environment.
- **Operating-system features**, such as virtualisation-based security in desktop systems, reuse nested paging to protect kernel memory.
- **Emulators and debuggers** use hardware assistance for fast execution with hooks at chosen events.
- **Cloud platforms** depend on it for multi-tenancy at scale.

## Examples

**A CPUID exit.** The guest runs `CPUID` to ask about features. The CPU exits, KVM fills in the leaf with a value the VMM allowed, advances the instruction pointer and resumes. The guest sees a CPU that supports exactly the features the operator chose.

**A device register.** The guest writes to a memory address that is not backed by RAM. The nested tables have no mapping, so an EPT violation exits; the hypervisor decodes the access and calls the device model, then resumes.

**A failing one.** A machine where firmware disabled the feature: loading `kvm_intel` fails and `/proc/cpuinfo` shows the flag but `/dev/kvm` is missing. The fix is in firmware settings, not in software. Another: running two hypervisors that each want exclusive use of the extension.

## Related problems and ideas

- **Memory management and page tables** (kernel internals) are the basis for understanding what the second layer adds.
- **Interrupt handling** shows what an interrupt controller does that the hypervisor must emulate or virtualise.
- **Processor security** (side channels) is the reason guest-state isolation is a research topic.
- **Containers and namespaces** are the lighter alternative with a weaker boundary.

## Active research

Open areas include reducing the cost of exits, confidential computing (encrypted guest memory and state, where the hypervisor is no longer trusted), nested virtualisation performance, formal verification of hypervisor kernels, and side-channel-safe scheduling (to verify the state of each).

## Future direction

Expect more of the hypervisor's job to move into hardware (interrupt and timer virtualisation, device assignment with isolation), a split between trusted and untrusted hypervisor components for confidential guests, and wider Arm and RISC-V equivalents with the same two-level structure.
