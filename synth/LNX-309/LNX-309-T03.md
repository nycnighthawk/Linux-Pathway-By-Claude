# A lighter kind of high availability: a floating address with keepalived and health-checked balancing with HAProxy

## Define the problem

Many services do not need a full cluster manager. A web tier made of identical, stateless servers needs two things: clients must always find a working front door, and requests must go only to servers that are actually healthy. The first is the problem of a **floating (virtual) IP address** that moves between machines when one fails. The second is **load balancing with health checks**. On Linux the common answer pairs two small daemons: **keepalived**, which implements the Virtual Router Redundancy Protocol (VRRP) to move an address and can run health scripts, and **HAProxy**, a high-performance TCP and HTTP proxy that spreads requests over back ends and removes failed ones.

The pair is popular because it is simple to understand and to operate: each load balancer runs independently, with no shared storage and no fencing, and the only state that matters is who holds the address. But the simplicity has limits. There is no quorum, so a network partition can leave two machines both holding the address (VRRP split brain). The health of the *balancer* is judged only by what keepalived checks. Session state is lost on failover unless it is replicated or kept in the client. And clouds often forbid the protocol tricks that make it work on a LAN. This topic teaches the configuration, the failure modes and the choice between this design and the Pacemaker design of the first topic.

Red Hat's identity management documentation names exactly this use: when each configured RADIUS proxy points at a single server, a virtual IP solution can be built outside the product, with the `keepalived` daemon given as an example, so that multiple servers answer behind one address for high availability [src: rhel-10-docs 7b22af3cea567d9b].

## History and approaches

VRRP was designed in the 1990s so that two routers could share a default-gateway address. The current standard is RFC 5798 (VRRP version 3, covering IPv4 and IPv6) [web: rfc-editor.org]. Routers elect a **master** by priority; the master sends periodic advertisements to a multicast group (224.0.0.18 for IPv4); backups listen, and if advertisements stop for about three intervals, the highest-priority backup takes over and sends gratuitous ARP (or neighbour advertisements for IPv6) so that switches and neighbours learn the address's new location. Keepalived, started by Alexandre Cassen in 2001 and part of the Linux Virtual Server ecosystem, brought VRRP to ordinary servers and added health checking of the machine's own services. It can also drive the kernel's IPVS load balancer directly, but most modern deployments use it only for the address and put a proxy behind it.

HAProxy dates from the same period (Willy Tarreau, 2000). It is an event-driven proxy that runs in **TCP mode** (layer 4: it forwards bytes, which suits databases, TLS pass-through and anything non-HTTP) or **HTTP mode** (layer 7: it understands requests, so it can route by host name or path, rewrite headers, and check health with real requests). Alternatives include Nginx, Envoy, Traefik and cloud load balancers; in Kubernetes the same function appears as ingress controllers and service load balancers, and the Kubernetes documentation lists many of them as third-party options [src: kubernetes-docs 0fba34b42905cec2].

The design space has three common shapes. **Active/passive** keepalived with one address: one balancer serves, the other waits; simple and predictable, but half the capacity is idle. **Active/active** with two addresses and DNS round robin, or with two VRRP instances where each node is master of one: both work, and either can take over both addresses on failure; capacity planning must assume one node carries all. **Anycast or routed** designs advertise the same address from several balancers through BGP (with ECMP spreading flows); this scales further and is what large sites and Kubernetes bare-metal load balancers use, for example Cilium's control plane can advertise service virtual IPs and pod ranges to BGP peers [src: cilium-docs 258c81a5f258f694]. This course concentrates on the first shape and mentions the others.

## Current state

**keepalived configuration.** The configuration file `/etc/keepalived/keepalived.conf` has global settings and one or more `vrrp_instance` blocks. An instance names the interface, a `virtual_router_id` (a number from 1 to 255 that must match on the peers and be unique on that network segment), the initial `state` (MASTER or BACKUP, which is only a starting point because the priority decides), a `priority` (higher wins; the two nodes need different values), the advertisement interval, and one or more `virtual_ipaddress` entries. A typical pair:

```text
vrrp_script chk_haproxy {
    script "/usr/bin/pidof haproxy"
    interval 2
    fall 2
    rise 2
}
vrrp_instance VI_WEB {
    state BACKUP
    interface eth0
    virtual_router_id 51
    priority 100
    advert_int 1
    unicast_src_ip 192.168.10.11
    unicast_peer { 192.168.10.12 }
    virtual_ipaddress { 192.168.10.100/24 dev eth0 }
    track_script { chk_haproxy }
}
```

On the peer the priority is lower and the source and peer addresses are swapped. A health script that fails lowers the node's priority (when `weight` is set) or puts the instance in FAULT state (the default for a bare failing script), so the other node takes the address. Useful options include `nopreempt` (do not take the address back from a working master after recovering, which avoids a second interruption), `garp_master_delay` (wait before sending gratuitous ARP), notification scripts (`notify_master`, `notify_backup`, `notify_fault`) that run on state changes, and `unicast_peer` for networks that filter multicast, which includes many virtualised and cloud networks. Authentication via a shared password was part of VRRP version 2 but has been removed from the version 3 standard and is not a security control (to verify against the keepalived version in use) [web: keepalived.org]. The configuration can be tested with the program's configuration-check option (`keepalived -t`) in recent versions (to verify).

**Binding to an address you may not hold.** HAProxy must listen on the virtual address. On the node that does not hold it, the bind fails unless the kernel is told that non-local binds are permitted, with the sysctl `net.ipv4.ip_nonlocal_bind=1` (and `net.ipv6.ip_nonlocal_bind=1`), or unless HAProxy binds to a wildcard address. Also set `net.ipv4.ip_forward` only if the node routes traffic, and consider `arp_ignore` and `arp_announce` in direct-routing LVS setups (to verify).

**HAProxy configuration.** The file `/etc/haproxy/haproxy.cfg` has `global`, `defaults`, `frontend`, `backend` and `listen` sections. A frontend binds an address and port and chooses a back end; a back end lists servers and an algorithm (`balance roundrobin`, `leastconn`, `source`, `uri` and others). Health checks are set per server:

```text
defaults
    mode http
    timeout connect 5s
    timeout client 30s
    timeout server 30s
    option forwardfor
frontend web
    bind 192.168.10.100:80
    default_backend app
backend app
    balance leastconn
    option httpchk GET /healthz
    http-check expect status 200
    server app1 192.168.10.21:8080 check inter 2s fall 3 rise 2
    server app2 192.168.10.22:8080 check inter 2s fall 3 rise 2
```

A server is marked down after `fall` failed checks and up after `rise` successes; the interval and counts trade detection speed against flapping. `option httpchk` makes the check an HTTP request instead of a TCP connect, and the endpoint should test what matters (the database connection, not just that the process runs) without being so expensive that checks cause load. Other essentials: `stats socket` for the runtime API (drain a server with `set server app/app1 state drain`), `option forwardfor` and the PROXY protocol to pass the client's address to the back end, `maxconn` limits, TLS termination with `bind ... ssl crt <file>`, and `haproxy -c -f /etc/haproxy/haproxy.cfg` to validate before reload. The Kubernetes documentation explains why preserving client addresses matters when a proxy terminates the connection: the back end sees the balancer's address unless the proxy carries the original through headers such as Forwarded or X-Forwarded-For, or through the PROXY protocol (a HAProxy-defined protocol), whereas a packet-forwarding balancer keeps the source address [src: kubernetes-docs 98bf8bfd0ab759ca].

**Security and platform notes.** On SELinux systems the policy distinguishes what the proxy may connect to: the boolean `haproxy_connect_any` is off by default and a compliance rule requires keeping it disabled, so back-end ports must be labelled correctly (with `semanage port`) instead of enabling the boolean [src: compliance-as-code 78f2137fbcd01d2e]. Open the firewall for VRRP (IP protocol 112, or the `vrrp` service in firewalld) between the two nodes and for the service ports. Restrict the HAProxy stats page and runtime socket.

**Health of the balancer pair.** The track script should check what indicates real service: process presence is minimal; a local HTTP request through the proxy is better. Avoid scripts that are slow or that depend on other nodes, since a flapping dependency would move the address needlessly. Stagger intervals so that the master's detection time (advertisement interval times three plus skew) is acceptable: with a one second interval, failover is about three to four seconds, plus ARP convergence.

**The cloud caveat.** Public clouds usually do not pass VRRP multicast and do not honour gratuitous ARP the way a LAN does, because the virtual network controls address ownership. HA there uses the provider's mechanisms: a managed load balancer, or a cluster resource agent that calls the cloud API to move an address. Red Hat documents these for its HA add-on: on Azure, an internal load balancer with a health probe removes cluster nodes that stop responding [src: rhel-10-docs 932dec1bacf4b8e2]; on Google Cloud, the `gcp-vpc-move-vip` agent attaches an alias IP to the running instance and moves it between nodes [src: rhel-10-docs 027356731c014377]; on AWS, different agents apply for an internet-exposed address, a single-zone address and an address that moves between zones [src: rhel-10-docs 4d8173d8beb58692]. keepalived is therefore mostly an on-premises and private-cloud tool.

**Keepalived versus Pacemaker.** Pacemaker adds quorum, fencing and ordering of dependent resources, and suits stateful services. Keepalived has none of these, and suits stateless front ends or situations where split brain is tolerable. A hybrid is common: Pacemaker manages the address and HAProxy as resources (so address and proxy fail over together with proper constraints), or keepalived handles the address while the application tier is balanced by HAProxy and the database is a separate HA problem. A rule of thumb: if two nodes both holding the address would cause harm beyond some confused clients, add fencing and use a cluster manager.

## Assessment: the good, the bad and the ugly

**The good.** The design is easy to teach, test and automate. Failover happens in seconds, back-end failures are handled in the same time, and there is nothing to corrupt. HAProxy is fast, stable and observable (rich statistics, logs, runtime API), and zero-downtime reloads are supported. Capacity can be added by adding back ends.

**The bad.** The balancer pair is a point of complexity: two config files to keep in sync (use templates and configuration management), a health script to maintain, TLS certificates on both nodes, and a client-visible blip on failover. Long-lived connections are cut at failover. Stateful applications need session persistence or shared sessions. VRRP has no authentication in its current version and relies on network isolation.

**The ugly.** VRRP split brain from a one-way multicast filter or a switch that drops advertisements: both nodes hold the address, and clients get random service. A health script that is more fragile than the service it guards, causing needless failovers. Mismatched `virtual_router_id` between two clusters on one VLAN, so that two unrelated pairs fight. A reload that silently fails because the configuration was not validated. HAProxy health checks that report a server healthy because they test the web server and not the application behind it.

**Decision rules.** Use keepalived with HAProxy for stateless or externally-replicated services on networks you control. Use managed load balancers in clouds. Use Pacemaker where state, shared storage or strict ordering matters. Always validate configuration before reload and test failover by actually stopping the master.

**Assumptions.** Option names, defaults and the exact failover timing follow keepalived 2.x and HAProxy 2.x public documentation and common practice; they differ in older releases and are marked (to verify). The statements on VRRP history and RFC 5798 summarise the standard [web: rfc-editor.org] [web: keepalived.org] [web: haproxy.org].

## Applications beyond this domain

Floating addresses and health-checked pools are everywhere: Kubernetes services and ingress (kube-proxy, MetalLB and kube-vip announce service addresses by ARP or BGP), cloud load balancers, DNS-based failover, CDN edge pools, and database proxies in front of replicas. The principle that a balancer must remove a failed member quickly and add it back slowly (fast `fall`, slower `rise`) recurs in all of them, as does the need to preserve the original client address.

## Examples

**Example 1: a two-node active/passive pair.** Both nodes run keepalived and HAProxy; node A has priority 150 and node B has 100; the shared address is 192.168.10.100; the track script checks `pidof haproxy`. Stop HAProxy on A and watch the address appear on B with `ip addr show eth0`.

**Example 2: unicast on a filtered network.** Replace the multicast default with `unicast_src_ip` and `unicast_peer` entries and allow VRRP between the two nodes in the firewall.

**Example 3: a health-checked back end.** Three application servers behind `balance leastconn`, `option httpchk GET /healthz`, `check inter 2s fall 3 rise 2`; stop one and check `echo "show servers state" | socat stdio /run/haproxy/admin.sock`.

**Example 4: draining for maintenance.** Run `set server app/app1 state drain` through the runtime socket, wait for connections to end, patch the server, then `set server app/app1 state ready`.

**Example 5: Pacemaker-managed pair.** `pcs resource create vip IPaddr2 ip=192.168.10.100`, `pcs resource create lb haproxy op monitor interval=10s`, with colocation and ordering constraints, when proper fencing and ordering are wanted instead of keepalived [src: rhel-10-docs 4d8173d8beb58692].

**Worked failure: two masters.** A pair of load balancers used multicast VRRP on a VLAN where a switch update enabled multicast filtering. The advertisements stopped arriving; each node concluded that the other was dead and took the address. Clients were sent randomly to either node; because both proxied correctly to the same back ends, the fault went unnoticed for hours, until a stateful session feature failed. The remedy was unicast peers, an alert on any node holding the address when its peer also claims it (a script comparing the two nodes through an out-of-band check), and a test of failover after each network change.

## Related problems and ideas

This topic is the lightweight counterpart of **Pacemaker clusters**; it relies on **networking** (ARP, multicast, firewalls, sysctls) and **TLS** (certificate handling on balancers), and it feeds the **disaster-recovery** topic, since a front door that survives a node still has to survive a site. Back-end state is the subject of the **replication** topics. In Kubernetes courses the same function reappears as services, ingress and load-balancer controllers.

## Active research

Areas of development include eBPF and XDP based load balancers (Katran, Cilium, IPVS alternatives) that handle millions of packets per second, QUIC and HTTP/3 support in proxies, dynamic configuration through APIs instead of files, and hitless reloads. Health checking is moving toward outlier detection and active-passive combinations driven by service meshes (to verify current features).

## Future direction

Expect on-premises HA front ends to move toward routed designs (BGP with anycast) and toward proxies configured by APIs, with keepalived used where simple L2 failover is enough. Expect managed balancers in clouds to remain the default there. The essential skills stay: know who owns the address, check what matters, keep failover tested, and decide whether the situation tolerates two owners.
