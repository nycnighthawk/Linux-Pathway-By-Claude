# Real power fencing: management controllers, power switches, watchdogs and the proof that a node is dead

## Define the problem

Earlier topics built clusters that fence with a virtual machine manager, which is convenient in a classroom and almost nowhere else. A production cluster sits on physical servers or on virtual machines in a cloud, and the thing that must be switched off is real: a chassis with a baseboard management controller, a power supply plugged into a power distribution unit, or an instance that the provider's API can stop. The problem of this topic is to choose, wire, configure, verify and keep fencing that really works when a node has gone wrong in the worst way.

The reason is stated plainly in the project documentation. A node that stops answering has not necessarily stopped touching shared data. The only way to be sure the data is safe is to make the node truly offline before anyone else uses the data, and the commonest way to do that is to remove its power; this is the origin of the acronym STONITH [src: clusterlabs-docs 34221707dad6ccb5]. The same text warns that turning fencing off merely makes the cluster pretend that failed machines are powered down, which vendors may refuse to support and which stops you from testing real failures. Fencing also serves another purpose: when a service refuses to stop, the cluster escalates by taking the whole node out, so that the service can start elsewhere [src: clusterlabs-docs deea734e487d97e5].

Three questions then decide a design. What can cut the power or the access of a node when that node, its operating system and possibly its network are all misbehaving? Can that mechanism be reached by the surviving nodes when the problem is the very thing that stopped the cluster talking? And how will anyone know, before the first real incident, that the answer to both questions is yes? A fence device that was typed into a configuration and never exercised is a belief, not a control.

This topic is at an introductory depth. It surveys the device families, the independence rules, the topology feature that combines devices, the delay settings that prevent mutual execution in a two-node cluster, the watchdog approach that needs no external device, and the testing discipline. The hands-on exercise is a design review in plan form, because the guide cannot assume that a reader owns a rack of out-of-band hardware.

## History and approaches

Early high-availability clusters were built on pairs of servers with shared disks, and the first fencing devices were remote power switches: a network-controlled outlet strip, or a serial line to a power controller, that the surviving node could instruct to cut the outlet of its partner. Server vendors then added management processors that live beside the main board, accept commands even when the host is off, and offer power control, console access and sensors. The industry standardised their wire protocols in stages. The Intelligent Platform Management Interface came first and is still found everywhere, alongside vendor flavours such as the iLO, iDRAC and similar families. A later, web-friendly interface called Redfish uses HTTPS and JSON, which makes it easier to secure and to script (the fence agents for it are listed on the upstream agent repository [web: github.com]).

Storage people took a different road. If the aim is to protect shared data, one can cut the node's access to the data instead of its power. This is called fabric fencing: block the node at an intelligent network switch, or revoke its persistent reservation on a disk that supports SCSI-3 reservations. The cluster documentation classifies devices into exactly these two families, power fencing and fabric fencing, and lists intelligent power switches, IPMI and a hardware watchdog (alone or combined with shared storage acting as a poison pill) on the power side [src: clusterlabs-docs 2d6e41889c72986b]. A third family arose with virtualisation and cloud computing: the hypervisor or the provider API acts as the power switch, and there are agents that call those interfaces.

The watchdog idea comes from embedded systems. A hardware timer counts down; software on the machine must keep resetting it; if the software hangs, the timer expires and resets the machine. For clusters, the clever step was to make the node's own health in the cluster the thing that keeps the timer fed. A node that loses quorum, or whose cluster view stops being refreshed, stops feeding the timer and reboots itself. Red Hat describes this as watchdog-only fencing built on the SBD daemon, and as a poison-pill variant in which a message written to a shared block device tells the target to reboot itself [src: rhel-10-docs f917655ac5ec0c53] and [src: rhel-10-docs ab3144769bae4553]. The attraction is that no external device and no management network is needed. The price is trust in the watchdog hardware and in carefully ordered timeouts.

Two opposing instincts shaped practice. One says to use the best single device available and monitor it. The other says that every fence device is a component that fails, so a real design includes a second, independent way to remove a node. The topology feature of Pacemaker grew from the second instinct, and today the guidance of the leading vendors reflects it.

## Current state

### The three independence rules

The upstream documentation gives three rules that deserve to be memorised, because most failed fencing designs break one of them. The first: a fence device must not depend on the network that the cluster itself uses, since a shared link would then be the one weak spot of the recovery mechanism. The second: at least one device per node must not share power with the node, because a power cut to a host cannot be told apart from a lost network, and a controller that dies with its host cannot report that the host is dead. The third: no device may depend on the target working, which excludes anything that logs into the node and issues a shutdown; such devices may be tolerated in a test environment and never in production [src: clusterlabs-docs 5aa7be7d2a9a9ffc].

The consequence for common hardware is uncomfortable. An onboard management controller that shares the power feed and often the network port of its server can fail together with the server. The documentation says that such a controller leaves the cluster unable to recover and obliged to stop its resources to avoid split brain, and it sets out the exception: an agent that logs into the management processor of a node without touching the node itself is fine [src: clusterlabs-docs 2d6e41889c72986b]. In practice, designs use separate network segments for management traffic, power the management controller from the same feed but add a second device on another feed, or rely on a power distribution unit that is independent of the servers.

### Choosing the agent

Pacemaker talks to every device through a fence agent: a small executable that receives parameters and performs "off", "reboot", "on" or "status". Agents exist for IPMI-class controllers, for web-based management interfaces, for power switches and for cloud and virtualisation APIs. The names follow a pattern, fence_ followed by the device family; the upstream repository is the reference for which agents exist and which parameters each takes [web: github.com]. The practical advice is to start from the agent's own metadata, which lists its parameters, rather than from copied configuration, and to store credentials so that they are not visible in process listings or in shared configuration where that is possible (to verify against the version in use).

Three configuration ideas appear in almost every real device definition. The first is the host mapping: a single device often fences several nodes, so the cluster needs to know which port or which management address belongs to which node. The pcmk_host_list and pcmk_host_map attributes carry this information. The second is the network address of the controller, which must be one the surviving nodes can reach without passing through the cluster's own link. The third is the timeout and retry behaviour: a slow controller that takes a minute to respond needs a monitor and action timeout that allows for it.

### Topologies: more than one way to remove a node

A fencing topology lets the administrator combine devices. Each node has an ordered list of levels, numbered from one to nine. Pacemaker attempts the levels in ascending order. Inside a level, all devices must succeed for the level to pass; if any device fails, the level is abandoned and the next one starts. The operation ends when a level passes or when all levels have been tried [src: clusterlabs-docs 0da1f46b0fd46366]. The upstream text lists three typical uses: try the onboard controller first and a power switch if it fails; cut disk and network access together and fall back to power fencing if either action fails; or wait for a crash dump to finish before cutting power.

With pcs the structure is expressed with the level command. Red Hat's guidance on watchdog fencing shows the pattern: a primary agent at level one and the watchdog agent at level two for the same node [src: rhel-10-docs c4d2c048886a0552]. A good design has at least two levels that are independent in the sense of the rules above, for example a management controller first and a switched power outlet second, or a controller first and watchdog-based self-fencing second.

A level with two devices is useful in a different way. A server with dual power supplies on two separate power distribution units requires two outlets to be switched off, and switching only one would leave the server running. Putting both outlets into the same level tells the cluster that the node counts as fenced only when both have been switched off; the cluster must then also switch both on again afterwards, which is a detail worth testing (to verify for the agent in use).

### Delays and the duel in a two-node cluster

When the link between two nodes fails, both nodes are healthy, both lose contact with the other, and both decide to fence their partner. If each succeeds at the same moment, the cluster is dead. Red Hat's guidance calls this a race and offers three kinds of fencing delay [src: rhel-10-docs 6bd554d4bdddf5d7]. A static delay is a fixed pause set on one node's device with the pcmk_delay_base attribute: the node whose device has the delay is the one more likely to lose the race, so the delay belongs on the node that the administrator prefers to lose, normally the passive one. A dynamic delay uses the pcmk_delay_max attribute to add a random component, so that the loser is chosen by chance, which suits active/active designs with a single device. A priority-based delay uses the priority-fencing-delay cluster property so that the node holding the fewer or less important resources is fenced. The same text adds that bigger clusters need no delay, because quorum already settles who may fence.

### Watchdog fencing and its timeouts

SBD in watchdog-only mode needs a real watchdog device on each node, no other conflicting devices, and the sbd package; the procedure includes a test that deliberately resets the machine, which must be done before the daemon takes control of the device, since the test does not work afterwards [src: rhel-10-docs f917655ac5ec0c53]. For a two-node cluster Red Hat describes combining watchdog-only fencing with a quorum device, and it insists that three timeouts line up. The quorum device synchronisation timeout defaults to thirty seconds. The SBD watchdog timeout must not be smaller than that, or a delayed quorum update could allow split brain. The stonith-watchdog-timeout cluster property must be larger than the watchdog timeout, in the guide set to double it, so that the cluster waits long enough for the target to reset itself before it assumes the node is gone [src: rhel-10-docs 8cdd6491a683cc52]. The idea behind the doubling is simple: the survivor must not start the resource until the failed node has certainly had time to reboot itself.

Watchdog fencing may also be limited to nodes that have a working watchdog, using a visible fence_watchdog resource with a host list, while other nodes keep a different method, and then arranged as the last resort in a topology [src: rhel-10-docs c4d2c048886a0552].

### Testing: how to break a node honestly

The Red Hat documentation separates two tests. The first asks whether the cluster can run the device: the pcs stonith fence command invokes the configured fencing for a node on demand. If it fails, the documentation lists what to check: that a host map really names the node as the cluster calls it, that special characters in a user name or password have not been mangled by the shell, that the device is reachable under the exact address or name given in the configuration (testing by IP address when the configuration holds a host name proves nothing), and that logging in to the device by hand using its protocol works. It adds that the device's own logs and the system log may show what happened [src: rhel-10-docs fc49986bb8186a6a] and [src: rhel-10-docs 5a6c25ff23a917c7] and [src: rhel-10-docs ae1927b335926fc4].

The second test asks whether the cluster fences when it should, by causing a real failure. Suggested methods are to pull network or power cables, to block corosync traffic in both directions with the local firewall, or to crash the machine through the kernel's trigger file. The same page warns that merely disabling the interface of the local host is not a good test, because it does not resemble a typical real fault, and that a deliberate kernel panic can lose data, so resources should be disabled first [src: rhel-10-docs bdc0eb83afc6af20].

## Assessment: the good, the bad and the ugly

**The good.** Hardware fencing is deterministic: a switched-off node cannot write to a disk, and the survivors can proceed without guessing. Management controllers are available on nearly all server hardware, and watchdogs are present on most of it. Topologies make redundancy cheap to express. Dedicated testing commands let the administrator exercise the exact path the cluster will use.

**The bad.** Out-of-band hardware is a second system with its own failure modes: stale firmware, expired certificates, rotated passwords nobody updated in the cluster, a management VLAN that was renumbered. These failures are silent until the day fencing is needed. A cluster that cannot fence stops its resources by design, so the typical result is an outage rather than corruption, which is the right trade but still an outage. Power switches that do not report success reliably, or that take a minute to act, force long timeouts and slow failover.

**The ugly.** Shared fate hides in building infrastructure. Two nodes, their management controllers, and their only power switch might sit behind one circuit or one top-of-rack switch, so a single event removes the nodes and the device that would fence them. Watchdog fencing hides a different trap: a virtual machine or a board with a software-emulated watchdog may not reset hardware when the kernel hangs, so it looks valid and is not (to verify per platform). Finally, a test performed once at installation says nothing about the system a year later.

## Applications beyond this domain

The idea of removing a silent party through a route that never needs its cooperation appears throughout engineering. Distributed databases use leases and fencing tokens so that a stale leader cannot write after a new one is elected: the storage layer rejects requests carrying an old token, which is fabric fencing in software. Networks isolate a misbehaving device by disabling its switch port. Industrial and safety systems define conditions under which equipment reverts to a restricted safe mode, automatically or on command; the US security-control catalogue includes a control of that name, intended for critical missions where only selected functions run under degraded conditions [src: nist-sp800-53 47cf7f6c84b8ff86]. Cloud operators call instance termination through the provider's API the equivalent of pulling the plug, and automated remediation systems for fleets of servers rely on the same out-of-band control.

## Examples

### A two-node cluster with two independent levels

The listing below is a sketch, not a recipe for any particular hardware; parameter names differ by agent and version, so confirm them with the agent's help output (to verify).

```
# controller of each node, reached over a management network
pcs stonith create fence-n1-bmc fence_ipmilan ip=10.9.0.11 username=cluster password="$BMC_PASS" lanplus=1 pcmk_host_list=node1
pcs stonith create fence-n2-bmc fence_ipmilan ip=10.9.0.12 username=cluster password="$BMC_PASS" lanplus=1 pcmk_host_list=node2
# a switched outlet on a separate power feed as the second way
pcs stonith create fence-pdu fence_apc_snmp ip=10.9.0.50 pcmk_host_map="node1:1;node2:2"
pcs stonith level add 1 node1 fence-n1-bmc
pcs stonith level add 2 node1 fence-pdu
pcs stonith level add 1 node2 fence-n2-bmc
pcs stonith level add 2 node2 fence-pdu
pcs stonith level verify
```

The first level uses the controller, the second a power outlet that does not share a failure domain with it. If both nodes use the same outlet unit, check that the unit itself has independent power and a network path that does not cross the cluster link.

### Making the passive node lose the race

```
pcs resource defaults update resource-stickiness=100
pcs stonith update fence-n2-bmc pcmk_delay_base=10s
```

With this setting the controller of the second node waits ten seconds before acting, so in a split the first node fences first. Choose the node you prefer to lose, then confirm by experiment which node survives (to verify).

### The proof

```
pcs stonith fence node2          # does the configured device work?
pcs stonith history              # what did the cluster do, and when?
```

After the device test, perform one honest failure test: block corosync traffic with the firewall or pull the cluster-network cable, watch the survivor fence the other node, wait for resources to start, then repair and return the node. Record the time from failure to resource start, since the figure feeds the recovery-time objective of the previous topic.

### A review that needs no hardware

The lab for this topic is a plan file: fill in a short list of design decisions for a pair of servers with onboard controllers and a shared power distribution unit. The answers should come from the rules above: two independent levels, a management network separate from the cluster link, no login-to-the-node devices in production, a delay on the node to be sacrificed, a documented monitor of the device itself, and a recurring test.

## Related problems and ideas

Quorum decides who may act; fencing makes the action safe. The two are complementary, which is why topics on quorum devices and on shared storage keep returning to fencing. Resource-level fencing, where the cluster only blocks access to a replicated volume instead of killing the node, is the idea behind DRBD fence handlers. Split-brain handling in database clusters and the lease-based election in distributed stores solve the same problem inside software. Hardware management itself, the subject of a neighbouring course, covers the security of the controllers: dedicated networks, strong passwords, firmware updates and disabling unused interfaces. A fence device that is easy to attack is a remote power switch for the whole cluster.

## Active research

Open questions in this area concern trust in a world where the power-off path is itself software. Redfish adoption and the retirement of weaker legacy interfaces change what agents must support. Fleet operators study how often management controllers misbehave, and whether a fence request that times out should be retried against the same device or escalated. Research on distributed systems continues on fencing tokens and lease-safe designs that avoid the need for physical power control, particularly in clouds where the provider API is slow or rate limited (to verify against current provider documentation).

## Future direction

Expect more fencing through standard APIs and fewer through vendor-specific interfaces, more use of watchdog and poison-pill mechanisms in environments without physical controllers, and cluster software that reports the health of the fence path continuously instead of only at failure time. Monitoring of the fence device itself, including a periodic test that the credentials and the network route still work, is already available in the form of ordinary resource monitor operations and should be treated as mandatory. Organisations that practise failure drills, as the previous topic recommends, will find fence problems when they are cheap to fix.
