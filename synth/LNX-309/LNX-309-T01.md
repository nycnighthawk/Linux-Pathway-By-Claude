# Two-node and multi-node clusters with Pacemaker and Corosync, and fencing in a virtual lab

## Define the problem

A service on one machine stops when that machine stops. High availability (HA) is the engineering practice of arranging for another machine to take over fast enough that users barely notice, and of doing so without making things worse. The second clause is the difficult one. If a node merely *appears* dead (a network cable pulled, a kernel stalled for thirty seconds) and a second node starts the same database on the same disk, the two instances can write over each other and destroy data. The central problem of a cluster is therefore not starting services; it is **deciding safely** which node may run what, when the nodes cannot fully trust what they hear from one another.

The Linux answer, shipped by Red Hat, SUSE, Debian and others, is a stack with two main parts. **Corosync** is the membership and messaging layer: it keeps a list of which nodes are present, tells the layer above when that list changes, and counts votes to decide whether the group has **quorum**. **Pacemaker** is the resource manager: it holds the cluster configuration, computes where each resource should run given the membership, and starts, stops, monitors and moves resources. The administration tool in the Red Hat family is `pcs`; the Rocky Linux handbook describes Pacemaker as the part that manages resources such as virtual addresses, services and data, built from a small set of daemons, including a configuration database (the CIB), a cluster resource manager, a local resource manager, a policy engine and a fencing daemon [src: rocky-docs 502048b210f24670].

Typical failures are well known. A two-node cluster without fencing that runs a shared file system is one network blip from corruption. A cluster with fencing configured but never tested turns out, during a real outage, to be unable to power off the failed node, and refuses to start anything. Resource ordering is wrong, so the application starts before the address or the disk it needs. A rolling update breaks the cluster because the nodes run incompatible versions. Quorum is lost because three of five nodes sit behind the same switch. This topic teaches the model, the commands, and the habits that avoid those outcomes, using virtual machines and the `fence_virsh` agent so that failures can be provoked safely.

## History and approaches

Clustering on Linux began with Heartbeat in the late 1990s: two nodes, a serial cable or Ethernet link, and a script that moved an address. Heartbeat grew a resource manager (CRM), which in 2007 became Pacemaker, a separate project that could use either Heartbeat or the OpenAIS and later Corosync messaging layer as its transport. The Rocky guide still notes that Pacemaker uses Corosync by default and can use Heartbeat [src: rocky-docs 502048b210f24670]. Corosync today is the standard choice. The ClusterLabs community maintains both projects and their documentation, which the main Linux vendors package and extend.

The management tools have changed too. Early users edited XML or used `crm_resource` and `crm_attribute`; SUSE's `crmsh` offered a shell; Red Hat standardised on `pcs`, which also configures Corosync and distributes its configuration. The ClusterLabs tutorial introduces `pcs` as the interface for both Pacemaker and Corosync, with options such as `-f file` to work on a saved copy of the configuration instead of the live one, which lets an administrator prepare and review a change offline [src: clusterlabs-docs d9495e8372d22118]. The `pcs cluster cib` command shows the raw XML configuration and status, with its epoch counters, quorum flag and the node that currently coordinates decisions [src: clusterlabs-docs 7eddd26f1f027df1].

Approaches to HA differ in what they replicate. **Active/passive** clusters run a service on one node with another standing by, and move the service and its storage (shared disk, replicated block device, or a mount that can be taken over) on failure. **Active/active** clusters run several instances at once, which needs either stateless services or a cluster-aware file system or database; the next topic discusses storage. **Application-level HA** (a database's own replication, or a load balancer with health checks) avoids a general cluster manager altogether and is often simpler; later topics in this course cover both. A general manager like Pacemaker is the right choice when a service has dependencies that must start in order on the same node (an address, a file system, then a daemon), when failure detection must be tight, and when the same tool should handle many different resource types.

## Current state

**Architecture.** A Pacemaker cluster elects one node as the **designated controller** (DC). The DC's policy engine takes the configuration and the current state and computes a transition: an ordered list of actions. The DC sends actions to the cluster resource manager on each node, which hands them to its local resource manager to run the **resource agent**. The Rocky guide states the same chain: the policy engine calculates the steps, the DC executes them in the right order and relays instructions to other nodes through Corosync [src: rocky-docs 502048b210f24670]. Because the configuration is replicated to every node, the loss of the DC just causes a new election.

**Resources and agents.** A *resource* is anything the cluster manages, run through an agent that implements start, stop and monitor. Agent standards include OCF (the most common, with providers such as `heartbeat` and `pacemaker`), systemd units, LSB scripts and STONITH agents. The Rocky workshop creates a virtual address with `ocf:heartbeat:IPaddr2` and a web server with `ocf:heartbeat:apache`, giving the latter a monitor operation that runs every minute and checks a status URL [src: rocky-docs 8501536dfcf1d3cd]. Resources can be grouped (started in order, stopped in reverse), cloned (run on several nodes), or promotable (one or more instances hold a "promoted" role, used for primary/secondary data).

**Constraints.** Placement is controlled by three kinds of rule, all with numeric scores where INFINITY means "must" and a negative infinity means "never". *Location* constraints state where a resource may or should run; the ClusterLabs tutorial uses a score of 50 to prefer one node, noting that nodes need not be identical and that an administrator might even prefer the weaker machine so as not to worry about capacity after failover [src: clusterlabs-docs 756c166be59ec9f2]. *Colocation* constraints keep resources together or apart. *Ordering* constraints set start and stop sequences. The final configuration listing in the tutorial shows how these combine for an address, a clone of a distributed lock manager, a promotable data resource, a cluster file system and a web server: the file system is ordered after the lock manager and colocated with the promoted data, and the web server follows the file system and shares a node with the address [src: clusterlabs-docs 6c332f94a33ccf85].

**Setting up with pcs.** On each node, install `pacemaker` and `pcs`, open the firewall service for high availability, enable and start `pcsd`, and set a password for the `hacluster` user that `pcs` uses to talk between nodes. Then, from one node, authenticate with `pcs host auth`, create the cluster with `pcs cluster setup <name> <node1> <node2>`, and start and enable it with `pcs cluster start --all` and `pcs cluster enable --all`. The Rocky guide gives this exact sequence, including enabling the High Availability repository on Rocky and the warning to replace the sample password with a secure one [src: rocky-docs 9b30ec5aa420ca6f] and [src: rocky-docs 2c7741b156fd3f7f]. Status is shown by `pcs status`, which lists the stack, the current DC, whether the partition has quorum, the nodes online and the resources and where they run.

**Quorum.** Corosync's `votequorum` service gives each node a number of votes (normally one) and declares the partition quorate if it holds a majority. A partition without quorum must not run resources, which is how a minority of nodes stays out of the way after a split. A two-node cluster has no majority after a split, so Corosync offers a special `two_node` mode (with wait-for-all at start) that lets the survivor keep going; this is only safe together with fencing, because both nodes can believe they are the survivor. For odd and larger designs, a third vote helps. A **quorum device** (the `corosync-qdevice` and `corosync-qnetd` software) lets an external arbitrator host provide the tie-breaking vote for even-sized clusters; Red Hat documents installing `corosync-qdevice` on the cluster nodes and `pcs` plus `corosync-qnetd` on the arbitrator host [src: rhel-10-docs 8eccd9fa64abaed1], and managing it with commands such as `pcs quorum device update model algorithm=lms` and `pcs quorum device remove` [src: rhel-10-docs db94015d26a45e94]. For clusters spread over sites, where network failures between sites make nodes unable to verify each other, Pacemaker supports multi-site clusters using the Booth ticket manager, and the Red Hat chapter introduces it as the remedy for the split-brain risk across distance [src: rhel-10-docs efe3a8b997bc5f7e].

**Fencing and STONITH.** The ClusterLabs documentation is direct: an unresponsive node is not necessarily a stopped node, and the only way to be certain that data is safe is to make sure the node is offline before another node touches the data. Fencing is also used when a resource will not stop; the whole node is removed so that the resource can start elsewhere [src: clusterlabs-docs 34221707dad6ccb5]. The same material explains why this matters in terms of effects: a duplicated address makes traffic unpredictable, while shared data stores such as databases and clustered file systems end in corruption or divergent copies [src: clusterlabs-docs deea734e487d97e5]. Fencing is on by default, and the documentation warns that turning it off for production is inappropriate and that even test clusters without it cannot exercise genuine failure scenarios [src: clusterlabs-docs 34221707dad6ccb5]. Red Hat's NFS example adds a practical symptom: without a configured fencing device, the cluster by default will not start resources, and `pcs resource debug-start` followed by `pcs resource cleanup` is the way to test a resource's configuration outside the cluster's control [src: rhel-10-docs 04ed6496b1bcd4c6].

Fence devices come in two families. Power fencing cuts power (managed switches, IPMI, hardware watchdogs); fabric fencing cuts access to a resource (SCSI-3 persistent reservations on shared storage, intelligent switches that disable a port). The ClusterLabs guidance warns that an IPMI controller that shares power or network with its host fails along with it, so that the cluster cannot recover and must stop its resources; and that any "device" that relies on the target being up (an SSH login to the node) is unsuitable, since fencing is needed when the node is unresponsive [src: clusterlabs-docs 2d6e41889c72986b]. The last topic of this course returns to real devices.

**fence_virsh in a lab.** With virtual machines under libvirt, the agent `fence_virsh` connects (typically over SSH) to the hypervisor and runs `virsh` to power-cycle the guest. A typical definition uses `pcs stonith create <name> fence_virsh ip=<hypervisor> username=<user> identity_file=<key> pcmk_host_map="node1:domain1;node2:domain2"` (to verify option names against the agent's metadata, `pcs stonith describe fence_virsh`) [web: ubuntu.com]. The map links cluster node names to libvirt domain names. The agent depends on the hypervisor and must never be used in production, but it fits the lab: you can power-cycle a "failed" node, test that surviving nodes take over, and see what happens when fencing itself fails. The alternative `fence_xvm` with `fence_virtd` uses multicast or vsock and is common in KVM labs too (to verify per release).

**Operations.** Day-to-day commands: `pcs status` and `pcs status --full`; `pcs resource move`, `ban` and `clear` (which add or remove location constraints, so they must be cleared afterwards); `pcs node standby` and `unstandby` to drain a node for maintenance; `pcs resource cleanup` to forget failures once the cause is fixed; `pcs cluster stop` for orderly shutdown; and `crm_mon -1` for a one-shot status. Logs are in the journal for `pacemaker`, `corosync` and `pcsd`. The Rocky guide has a troubleshooting section that begins with the same checks (service state, name resolution, firewall, quorum) [src: rocky-docs 51433720553ea094]. Version compatibility matters in rolling upgrades: update one node at a time while it is in standby, and keep versions within the vendor's supported mix (to verify per release).

## Assessment: the good, the bad and the ugly

**The good.** The stack is mature, vendor-supported and flexible. It manages almost any resource through small agents, expresses real dependencies (address, disk, daemon in order) and has strong safety defaults: fencing on, quorum enforced, resources not started if fencing is missing. A well-built cluster fails over in seconds and, as important, refuses to act when it cannot do so safely.

**The bad.** The model has a learning curve: scores, constraints, clones and roles are easy to misconfigure, and bad constraint sets can cause surprising moves. Failover is not free: the application must recover from a crash (journal replay, cache warm-up), so client-visible downtime is usually tens of seconds, not zero. A cluster also adds a failure source: the cluster software itself can fail, or fence a healthy node after a transient network problem. Two-node clusters need extra care for quorum, and stretched clusters need Booth or similar.

**The ugly.** Fencing disabled "temporarily" and forgotten; a fence device that depends on the same power feed as the node; a split brain on shared storage; resource agents that report success when the service is actually broken; a monitor timeout shorter than a legitimate slow start so that the cluster restarts a healthy service forever; and a cluster whose procedures were never rehearsed, so that the first real failure is also the first test.

**Decision rules.** Use a Pacemaker cluster for stateful services with real dependencies on a shared or replicated block device or address. Prefer application-level replication with a simple front end for services that already support it. Prefer stateless designs behind a load balancer where possible. Never run without fencing when shared state exists.

**Assumptions.** Command names and behaviours follow the cited ClusterLabs, Red Hat and Rocky documents for current releases; option names for specific fence agents and defaults for `two_node` and timeouts differ across versions and are marked (to verify). The statement about SUSE `crmsh`, the history of Heartbeat and the `fence_xvm` details summarise public project history and documentation [web: clusterlabs.org] [web: ubuntu.com].

## Applications beyond this domain

The same ideas appear elsewhere. Kubernetes control planes use quorum (etcd needs a majority) and leases for leader election. Database clusters use consensus protocols and "witness" nodes to avoid split brain. Cloud load balancers with health checks and managed instance groups replace failed instances automatically, which is "fencing" by termination. Distributed locks and leases in application code use the same reasoning: a node that cannot prove it still holds the lease must stop. Red Hat's cloud guides apply the HA add-on on public clouds, with resource agents for moving cloud addresses and fence agents for cloud APIs, showing how the model carries over when the hypervisor is not yours [src: rhel-10-docs 4d8173d8beb58692].

## Examples

**Example 1: a two-node web cluster.** On two Rocky or RHEL nodes, create the cluster with `pcs cluster setup web server1 server2`, create the address with `pcs resource create vip ocf:heartbeat:IPaddr2 ip=192.168.1.12 cidr_netmask=24 op monitor interval=30s`, the web server with `pcs resource create site ocf:heartbeat:apache configfile=/etc/httpd/conf/httpd.conf op monitor interval=1min`, and bind them with `pcs constraint colocation add site with vip INFINITY` and `pcs constraint order vip then site` [src: rocky-docs 8501536dfcf1d3cd].

**Example 2: node preference.** `pcs constraint location site prefers server2=50` states a preference without forbidding other nodes; `pcs constraint` lists the result [src: clusterlabs-docs 756c166be59ec9f2].

**Example 3: a lab fence device.** On KVM hosts, create `fence_virsh` with a host map, test with `pcs stonith fence server2`, and watch the guest restart; then check that the cluster brings resources up on the surviving node afterwards.

**Example 4: planned maintenance.** `pcs node standby server1`, confirm that resources moved, update and reboot the node, then `pcs node unstandby server1`; with a preference constraint in place, resources may move back automatically unless stickiness is set.

**Example 5: a quorum device.** Install `corosync-qdevice` on the nodes and `corosync-qnetd` on a third host, add it with `pcs quorum device add model net host=<qnetd> algorithm=ffsplit`, and verify with `pcs quorum status` (to verify the option names) [src: rhel-10-docs 8eccd9fa64abaed1].

**Worked failure: the unfenced pair.** Two database nodes shared a disk through a cluster file system; fencing had been disabled during installation to get past an error and never re-enabled. A switch fault cut the heartbeat link while both nodes remained up. Each believed that the other had died and, with two-node mode on, kept quorum. Both mounted the file system read-write and ran the database. By the time operators noticed, files had been written inconsistently and a restore from backup was needed. With a fence device, the first node to act would have powered off the other before touching the disk, and the second would have been unable to continue.

## Related problems and ideas

This topic is the base for the rest of the course: **DRBD and GFS2** need the lock manager and fencing; **keepalived and HAProxy** solve similar address failover in a lighter way; **database replication** shows application-level HA; **DR drills** test what happens when the whole site goes; and **real power fencing** is the hardware counterpart of `fence_virsh`. It relies on **networking** (multicast or unicast links, redundant rings), **storage** (shared, replicated and multipath devices), **systemd** (resource agents of that type) and **BMCs** (a power fencing channel; see the provisioning course).

## Active research

Work continues on faster failure detection, better scalability of the policy engine and Corosync's knet transport (multiple links with failover), on remote nodes for large clusters (Pacemaker Remote), on fencing without special hardware (watchdog-based self-fencing and sbd), on integrating HA with cloud APIs and on cluster resource agents for containers. The same community also develops tooling for testing, such as simulated failures with `crm_simulate` and cluster test suites (to verify current tools).

## Future direction

Expect general-purpose HA clusters to remain for stateful enterprise workloads while new applications move to platforms (Kubernetes, managed databases) that embed their own failover. Expect fencing to rely more on watchdogs and cloud APIs, expect declarative configuration with automated testing, and expect cluster safety checks (is fencing on, is it tested, does quorum survive a rack loss) to be part of routine audits. The lasting skill is the reasoning: never start a second copy unless the first is certainly gone.
