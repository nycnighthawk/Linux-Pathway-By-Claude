# Application-level high availability: PostgreSQL streaming replication, promotion and the cost of lost writes

## Define the problem

The earlier topics protect a service by moving an address or a block device. A database can also protect itself: it already writes every change to a log, so a second server can receive that log and apply it. This is **application-level replication**. It has real advantages over block-level mirroring: the standby is a running server that can answer read queries, replication is aware of transactions (so a half-written page never matters), and the standby can be geographically far away. It also has costs that students must understand before they promise anything to an owner: replicated data can lag behind, a failover can lose the last committed transactions, a former primary cannot simply rejoin, and replication still copies mistakes.

PostgreSQL's built-in mechanism is **physical streaming replication**: the primary streams its **write-ahead log** (WAL) records to one or more standbys, which replay them continuously. Red Hat's database chapter explains the WAL as the record of every change to the data files, stored in the `pg_wal` directory and used mainly for crash recovery, with later sections showing how the same log supports backups, point-in-time recovery and high availability [src: rhel-10-docs e35a55b4b281bf55]. The student's goals here are to build a primary and standby pair, verify them, promote the standby, reason about **recovery point** (how much data may be lost) and **recovery time** (how long the service is down), and know which tools automate failover.

Typical failures: a standby that silently stops replicating because a WAL segment was removed before it was fetched; a failover to a standby that was behind; the old primary restarted after failover and accepting writes (a split brain at the application level); an application that keeps connecting to the old primary's address; and a replication setup that is trusted as a backup, so that an accidental `DROP TABLE` is faithfully applied everywhere.

## History and approaches

PostgreSQL gained **warm standby** through log shipping in version 8.2 (2006): archived WAL files were copied to another server and applied. Version 9.0 (2010) added **streaming replication** and a **hot standby** that could serve read-only queries; 9.1 added synchronous replication; 9.4 added replication slots and logical decoding; 10 introduced built-in **logical replication** (publications and subscriptions) (to verify the version history against the release notes) [web: postgresql.org]. The method has stayed the same in outline, with large improvements in tooling and monitoring.

Two kinds of replication exist and should not be confused. **Physical replication** copies the WAL byte for byte, so the standby is an exact binary copy of the whole cluster, same major version and architecture, read-only until promoted. **Logical replication** sends decoded row changes for chosen tables, can cross major versions, allows writes on the subscriber for other tables, and is the tool for migrations and selective copies; it is not a drop-in replacement for physical replication in HA because it does not carry sequences, schema changes or large objects by default (to verify) [web: postgresql.org].

Synchronisation modes trade safety for latency. In **asynchronous** replication the primary commits without waiting for any standby, so a primary crash can lose recent commits that never left it. In **synchronous** replication the primary waits for one or more named standbys before reporting a commit as successful (`synchronous_commit` and `synchronous_standby_names`), with levels from "remote write" through "remote flush" to "remote apply"; this gives a recovery point of zero for acknowledged commits at the price of added commit latency, and a stuck standby can block commits unless a quorum-style list such as `ANY 1 (s1, s2)` is used (to verify the syntax per version). The ClusterLabs material on multi-site clusters makes the same point more generally: sites are usually too far apart for synchronous communication and data replication, which creates problems of knowing whether a site is up, avoiding double starts, reaching quorum across sites and managing failover between them [src: clusterlabs-docs efed05cdebf768a3].

For automation there are three families. **Cluster managers** (Pacemaker with the `pgsql` or the newer PostgreSQL Automatic Failover (PAF) resource agent) treat the database as a promotable resource and integrate with fencing. **Purpose-built managers** such as Patroni (with a distributed store such as etcd or Consul for leader election), repmgr and pg_auto_failover run on the database hosts and promote a standby automatically. **Manual or scripted failover** is still common and perfectly respectable for small systems where an operator decides. Connection routing then uses a virtual IP (the previous topic), a proxy such as HAProxy checking which node is primary, PgBouncer, or the `target_session_attrs=read-write` option of the PostgreSQL client library with multiple hosts in the connection string (to verify).

## Current state

**Building the primary.** On the primary, edit `postgresql.conf`: `wal_level = replica` (the default in recent versions), `max_wal_senders` high enough for the standbys and backup tools, `max_replication_slots` if slots are used, `listen_addresses` to include the replication interface, and optionally `hot_standby = on` (the default) and `wal_keep_size` to retain WAL for slow standbys. Create a role with the `REPLICATION` attribute and a strong password (or better, a certificate), and allow it in `pg_hba.conf` with a line of the form `host replication replicator 192.168.20.0/24 scram-sha-256`. Reload the server. The Red Hat chapter describes the related archiving settings: `wal_level` at `replica` or higher, `archive_mode` turned on and an `archive_command` that copies each finished segment to safe storage [src: rhel-10-docs e35a55b4b281bf55].

**Creating the standby.** Stop any server on the standby host and empty its data directory. Take a **base backup** from the primary with `pg_basebackup -h primary -U replicator -D /var/lib/pgsql/data -X stream -R -P` (the `-R` option writes the connection settings and creates the signal file that makes the server start as a standby; `-X stream` includes the WAL needed for consistency). Red Hat's text on base backups notes that the tool accepts host and port options (or the `PGHOST` and `PGPORT` variables), that the cluster copy and the WAL segments named in the backup history file must be archived safely, and that older segments than those needed can be removed [src: rhel-10-docs 34d434e8069a020e]. Start the standby with `systemctl start postgresql`. Because `-R` writes `primary_conninfo` into `postgresql.auto.conf` and creates `standby.signal` (PostgreSQL 12 and later), the server enters recovery mode and streams from the primary; the cited Red Hat procedure for restoring from an archive still speaks of a `recovery.conf` file that is renamed when recovery finishes, which describes PostgreSQL 11 and earlier, so check the version in use (to verify) [src: rhel-10-docs 34d434e8069a020e].

**Verifying.** On the primary, `SELECT client_addr, state, sync_state, sent_lsn, replay_lsn, replay_lag FROM pg_stat_replication;` lists connected standbys, whether they are streaming, and lag in bytes and time. On the standby, `SELECT pg_is_in_recovery();` returns true; `pg_last_wal_receive_lsn()` and `pg_last_xact_replay_timestamp()` show progress. A simple test is to create a table and insert a row on the primary and read it on the standby. Monitoring should alert on state other than `streaming`, on lag above the agreed recovery point, on the oldest replication slot's retained WAL (an unused slot makes the primary keep WAL until the disk fills), and on archive failures.

**Replication slots and WAL retention.** A **replication slot** makes the primary retain WAL until the standby has received it, so a slow or temporarily disconnected standby does not fall off the end of the log. The danger is the same: a standby that is gone for good keeps the primary retaining WAL until the disk is full, so slots need monitoring and removal (`pg_drop_replication_slot`), and `max_slot_wal_keep_size` can cap the retention (to verify the version). The alternative is WAL archiving: if the standby has a `restore_command` pointing at the archive, it can catch up from archived segments even when the primary no longer has them, which is the robust design for standbys that may be down for long periods [src: rhel-10-docs e35a55b4b281bf55].

**Promotion.** A standby becomes a primary with `pg_ctl promote`, the SQL function `pg_promote()`, or `touch`-ing the trigger mechanism that the version supports. The server leaves recovery, starts a new **timeline**, and accepts writes. Applications must be redirected: move the virtual address, update the proxy, or let the client library find the writable host. Other standbys must be re-pointed at the new primary (`primary_conninfo`) and may need to follow the new timeline; if they have replayed WAL beyond the new primary's divergence point, they cannot follow and must be rebuilt.

**Rejoining the old primary.** After a failover the former primary has a history that may contain commits the new primary never received. It must not be started as a primary. Two ways back are available: rebuild it with a fresh `pg_basebackup`, or use **`pg_rewind`**, which rewinds the old primary's data directory to the point where timelines diverged and brings it to a state from which it can follow the new primary. `pg_rewind` requires `wal_log_hints` or data checksums to be enabled before the failure and access to the new primary (to verify the exact requirements). Whichever method is chosen, any transactions that existed only on the old primary are lost; the operations team should decide whether to export them first.

**Failover automation.** A fully automatic failover needs a reliable failure decision, which brings back the problems of the first topic: is the primary down, or is the network? Patroni uses a distributed consensus store: a node holds a leader lease; if the lease expires, a standby can take it, and the old leader, unable to renew, demotes itself, which is a form of self-fencing. Pacemaker uses quorum and STONITH. Either is acceptable when properly tested; a script that promotes whenever a ping fails is not. Define the **recovery point objective (RPO)** and **recovery time objective (RTO)** first: asynchronous replication with automatic failover typically gives an RPO of seconds and an RTO of tens of seconds; synchronous replication gives an RPO of zero for acknowledged commits.

**Backups remain.** Replication is not a backup. A dropped table, a faulty deployment or ransomware is replicated at once. Use continuous archiving with periodic base backups, which gives **point-in-time recovery**; Red Hat's chapter lists its advantages (a base backup need not be perfectly consistent because log replay corrects it, only `tar` is needed, and replay can stop at any chosen moment) and its limits (it restores a whole cluster, not a subset, and needs archive storage) [src: rhel-10-docs e35a55b4b281bf55]. Tools such as pgBackRest and Barman manage retention, verification and parallel restore (to verify). Logical dumps with `pg_dump` complement them but cannot replay WAL [src: rhel-10-docs e35a55b4b281bf55].

**Security.** Replication connections should be encrypted (`sslmode=verify-full`) and use their own role. Restrict `pg_hba.conf` to the replication network. On SELinux systems, review the PostgreSQL booleans: for example, the `postgresql_can_rsync` boolean is disabled by default and compliance rules keep it that way unless a base backup method truly needs it (to verify per policy) [src: compliance-as-code 39441d4ce500adfe].

## Assessment: the good, the bad and the ugly

**The good.** Streaming replication is built in, mature and well understood; a standby adds read capacity, supports zero-downtime maintenance by switchover, and is the foundation of nearly every PostgreSQL HA design. Switchover (a planned role change) is clean and quick; failover can be automatic and fast with proper tooling.

**The bad.** Asynchronous replication can lose data on failover; synchronous replication adds latency and can stall commits when the standby is unreachable. Physical standbys must match the primary's major version; upgrades need logical replication or `pg_upgrade` procedures. Standbys cannot take writes, so write scaling is unchanged. Failover tooling adds moving parts, each needing monitoring and testing.

**The ugly.** The old primary that restarts and takes writes. A slot that fills the disk. WAL archive gaps discovered only during recovery. A promoted standby that was far behind. Connection strings with a single host name that points at the dead machine. And the habit of treating a standby as a backup until the day a table is dropped.

**Decision rules.** Define RPO and RTO first, then choose the mode. Use asynchronous replication with archiving and tested failover for most services; use synchronous replication with at least two candidate standbys where data loss is unacceptable. Automate failover only with a quorum or fencing mechanism. Test a restore from backup regularly, separate from replication tests.

**Assumptions.** Parameter names and signal files follow current PostgreSQL releases (12 and later) as generally documented; older versions differ and the cited Red Hat chapter reflects some older syntax, so items are marked (to verify). Version history and the logical-replication limits summarise public PostgreSQL documentation [web: postgresql.org] [web: patroni.readthedocs.io].

## Applications beyond this domain

The same patterns recur in other systems: MySQL and MariaDB replication with GTIDs and semi-synchronous mode, MongoDB replica sets with elections, Redis replicas with Sentinel, etcd and ZooKeeper with consensus, and cloud-managed databases with multi-zone standbys. The questions asked are identical: how much can be lost, how long to recover, how a stale primary is prevented from writing, and how clients find the leader.

## Examples

**Example 1: a replication role and rule.** `CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD '...';` and `host replication replicator 192.168.20.0/24 scram-sha-256` in `pg_hba.conf`.

**Example 2: building a standby.** `pg_basebackup -h 192.168.20.11 -U replicator -D /var/lib/pgsql/data -X stream -R -P`, fix ownership and permissions, start the service, then check `pg_stat_replication` on the primary [src: rhel-10-docs 34d434e8069a020e].

**Example 3: a lag check.** `SELECT now() - pg_last_xact_replay_timestamp() AS lag;` on the standby; alert when it exceeds the recovery point objective.

**Example 4: promotion.** `sudo -u postgres pg_ctl promote -D /var/lib/pgsql/data` (or `SELECT pg_promote();`), move the virtual address, then re-point or rebuild the other standbys.

**Example 5: point-in-time recovery.** Restore the latest base backup, set `restore_command` to fetch archived WAL, set a recovery target time just before the mistake, create the recovery signal file, and start the server [src: rhel-10-docs 34d434e8069a020e].

**Worked failure: the returning primary.** After a storage fault, an automatic script promoted the standby. Operations fixed the old primary's disk and rebooted it; a systemd unit started it as a primary, and a batch job that still used the old address wrote for twenty minutes. The two servers then held different data for the same tables. The reconciliation took two days and some orders were re-entered by hand. The remedy was to disable automatic start of a failed primary until it is explicitly rewound or rebuilt, to fence it from the network, and to route clients through a proxy that checks the role.

## Active research

Areas of development include logical replication improvements (replicating DDL and sequences, parallel apply), consensus-based database clusters, faster failover with proactive checks, cloud-native operators for Kubernetes (such as CloudNativePG and Zalando's operator), and storage-level replication under the database in clouds. Research on formal verification of failover protocols has found real bugs in popular tools, which is the reason for the repeated advice to test failure scenarios (to verify).

## Future direction

Expect most new installations to use an operator or managed service that hides replication details, with the same concepts underneath. Expect synchronous quorum commit to become the default for important data, and expect more focus on recovery verification (automatic restore tests) than on replication itself. The enduring practice is to know the recovery point and time, rehearse the failover, and keep an independent backup.
