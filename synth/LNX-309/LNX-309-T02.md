# Giving a cluster its data: replicated block devices, cluster file systems and their hazards

## Define the problem

A cluster can move an address and restart a daemon in seconds, but a stateful service also needs its **data** on the node that takes over. There are only a few ways to arrange that. The data can live on a **shared device** that both nodes can reach (a SAN volume, a shared SAS enclosure), with the cluster ensuring that only one node uses it at a time. It can be **replicated** from one node to the other at the block level, so that each node has a private copy kept in step. It can be held by an **application-level replication** mechanism, such as a database's own streaming replication (the topic after next). Or it can live on a **network file system** served from elsewhere, which moves the availability problem to the server.

This topic covers the second approach and its extension. **DRBD** (Distributed Replicated Block Device) mirrors a block device over the network. A **cluster file system** such as **GFS2** (or OCFS2) lets several nodes mount the same block device read-write at once, using a **distributed lock manager** (DLM) to coordinate. Together they allow an active/active layout: both nodes serve the same files. The ClusterLabs tutorial introduces DRBD as network-based RAID-1, an answer for sites that cannot afford shared storage but still have to keep data in sync between machines [src: clusterlabs-docs 918903669a2809e2].

"Awareness" in the topic title is deliberate. These tools can be powerful and are widely deployed, but they are also unforgiving. A cluster file system mounted on two nodes without working locking and fencing is corrupted within minutes. A DRBD pair that is promoted on both sides after a network partition produces two divergent histories (a "split brain" in DRBD's own sense) that must be reconciled by discarding one. The student should leave able to explain what the pieces do, set up a lab, recognise when they are the wrong choice, and avoid the classic failures.

## History and approaches

DRBD was written by Philipp Reisner and Lars Ellenberg of LINBIT in the early 2000s, merged into the mainline Linux kernel in version 2.6.33 (2010) for the version 8 line. The newer DRBD 9 generation, with support for more than two nodes and a different configuration syntax, is still delivered as an out-of-tree module by many distributions and by LINBIT; the ClusterLabs tutorial says the core DRBD code is in the upstream kernel, but the utilities (and in current enterprise releases the newer module) come from third-party repositories, and uses the free ELRepo repository for the lab, with `kmod-drbd9x` and `drbd9x-utils` [src: clusterlabs-docs 177e09cfa85053cb]. Which package set is available differs by distribution and release (to verify).

Replication at the block layer is application-neutral: whatever file system or database sits on `/dev/drbdN` is replicated. The price is that the secondary side's copy is not usable while it is secondary, and that every write crosses the network before it is acknowledged under the safest protocol. DRBD supports three protocols. **Protocol C** (synchronous) completes a write only after both nodes have it on disk, and is the choice when no acknowledged write may be lost; the tutorial's sample configuration uses protocol C [src: clusterlabs-docs d0c119b06cf61e35]. **Protocol B** acknowledges when the peer has received the data in memory; **protocol A** (asynchronous) acknowledges after the local write and the send, and is used across long distances where latency would hurt, at the price of possibly losing the last writes on failover (to verify against the DRBD user's guide) [web: linbit.com].

Shared file systems have a longer history. Sistina's GFS (acquired by Red Hat) gave Linux its first widely used cluster file system; GFS2 replaced it and is in the mainline kernel, working with the DLM from the same cluster stack. Oracle's OCFS2 is another cluster file system in the kernel. Distributed storage systems (Ceph, GlusterFS) take a different approach with replicas spread over many nodes; they belong to the storage courses of this path.

The decision is old and still relevant: shared-nothing with replication (simple, safe, active/passive) versus shared-everything with a cluster file system (more complex, active/active). The ClusterLabs material states the requirement of active/active plainly: the data must be available at the same time on both machines. Pacemaker does not care how this is achieved, so a SAN would do, though DRBD allows more than one primary and is used in the tutorial for that reason [src: clusterlabs-docs 94051f8349ac6cd0].

## Current state

**Building a DRBD resource.** Each node needs its own backing block device of the same size, normally an LVM logical volume or a partition; the tutorial creates a small logical volume with `lvcreate --name drbd-demo --size 512M` on each node [src: clusterlabs-docs 77019e37394867a3]. A resource file such as `/etc/drbd.d/wwwdata.res` names the resource, a device number, internal metadata, one `on <host>` section per node with its disk and a node id, and a `connection` with each host's address and port (7789 in the example, which must be allowed through the firewall). The `net` section sets the protocol and options. The sample file has `protocol C`, `allow-two-primaries yes` (needed for active/active, not for active/passive), `verify-alg sha1` for online verification, and, importantly, `fencing resource-and-stonith` with `fence-peer` and `unfence-peer` handlers that call Pacemaker helper scripts [src: clusterlabs-docs d0c119b06cf61e35]. Those two settings integrate DRBD with cluster fencing: when the replication link fails, the handler asks the cluster to block the peer from becoming primary (by adding a constraint) and, if needed, fence it.

Initialisation follows a fixed order. On each node: write the configuration, run `drbdadm create-md <resource>` to write the metadata, load the module and run `drbdadm up <resource>`. `drbdadm status` then shows the role and disk state: the first node reports `Secondary` and `Inconsistent` with the peer `Connecting`, and after the second node comes up both connect. One side must then be declared the source of the initial synchronisation (`drbdadm primary --force <resource>` on the chosen node, for DRBD 9), after which the other side synchronises and the state becomes `UpToDate` on both (to verify the exact command for the installed release) [src: clusterlabs-docs 5bcf0a8fc16f6948]. A file system is created once, on the primary node, with `mkfs` on `/dev/drbdN`; the tutorial notes that the example uses xfs with no options and that production choices should suit the application [src: clusterlabs-docs cf2166ddabf1c9f6].

**Under Pacemaker.** The DRBD device becomes a *promotable clone*: an instance runs on every node, and one holds the promoted role. The tutorial queues changes in a file with `pcs cluster cib drbd_cfg` and `pcs -f drbd_cfg ...`, which is a good habit for any multi-step change, creates the resource with `ocf:linbit:drbd` and separate monitor operations for the promoted and unpromoted roles (at different intervals, which is required so that Pacemaker can tell the roles apart), and makes it promotable with `promoted-max=1`, `clone-max=2` and `notify=true`. The file is pushed to the live configuration only at the end [src: clusterlabs-docs 0977c95504a39de8]. The file system resource is then defined with the `Filesystem` agent, constrained to run where DRBD is promoted and ordered after the promotion [src: clusterlabs-docs c4154bd13cab8bcb]. A web server then follows the file system. The same chapter demonstrates failover with `pcs node standby`, which leaves Corosync and Pacemaker running but forbids resources on that node and so offers a clean way to simulate a failure and to prepare for maintenance [src: clusterlabs-docs 1b14f471cebe2799].

**Converting to active/active with GFS2.** The tutorial's active/active chapter sets out the steps. The file system must be cluster-aware, so xfs is replaced: install `dlm` and `gfs2-utils` (from the Resilient Storage repository on the enterprise distributions) on both nodes [src: clusterlabs-docs 1573e6cf1f89960c]. Stop the file system resource through the cluster so that its dependants stop in the right order, then create the new file system on the node that holds the DRBD primary role, with a command of the form `mkfs.gfs2 -p lock_dlm -j 2 -t <clustername>:<fsname> /dev/drbd1`: the lock protocol, a journal for each node and a lock table name that must start with the cluster name. The material warns that this erases the device and that running it on a node that is not primary gives a read-only error [src: clusterlabs-docs 37dafc0c34f90f6c]. Then update the resource (`fstype=gfs2`), add a cloned DLM resource, and add colocation and ordering constraints so that the file system starts only where and after the lock manager runs [src: clusterlabs-docs 553b72c78e458248]. Finally the DRBD clone is allowed two promoted instances, and the file system resource is cloned. The final configuration listing shows the whole chain: address, web server, promotable DRBD clone with both nodes promoted, a DLM clone and a file system clone [src: clusterlabs-docs 6c332f94a33ccf85].

**Fencing is part of the design.** The DLM freezes lock operations when it cannot confirm the state of a node that has dropped out, and resumes only after the cluster has fenced the node. This is by design: a hung node that could still write must not be allowed to. Therefore a cluster file system without working fencing will stall at best and corrupt at worst. In two-node clusters there is a second hazard: when the link between nodes fails, each may try to fence the other at once and both go down. Red Hat's documentation describes **fencing delays** to prevent this race: a static delay (the `pcmk_delay_base` attribute, possibly as a host map such as one node at zero seconds and the other at five), a random delay, and a priority-based delay (`priority-fencing-delay`) that favours the node running the most important resources. Delays are unnecessary in larger clusters because quorum decides who may fence [src: rhel-10-docs 6bd554d4bdddf5d7] and [src: rhel-10-docs efdc2f8df327ad8f].

**Operating DRBD.** Common commands are `drbdadm status` (or `drbdsetup status --verbose`), `drbdadm primary|secondary`, `drbdadm connect|disconnect`, `drbdadm verify <resource>` (online comparison of blocks, scheduled regularly, using the `verify-alg` setting) and `drbdadm invalidate` or `--discard-my-data` for resolving a split brain by sacrificing one node's changes. Metadata can be internal (end of the device) or external. Resizing and the use of LVM below DRBD are documented in the user's guide (to verify). Monitoring should watch the connection state, the disk state (`UpToDate`, `Inconsistent`, `Outdated`), resynchronisation progress and network throughput, because a resync after a long outage competes with production traffic (the `sync-rate` and dynamic resync controller settings help).

**Operating GFS2.** `gfs2_grow` extends a mounted file system; `gfs2_jadd` adds journals for new nodes (each node that mounts needs one); `fsck.gfs2` checks an unmounted file system on one node only; and `tunegfs2` changes parameters (to verify per release). Performance depends on lock contention: workloads where nodes work in different directories perform well, while workloads where nodes fight over the same files and directories suffer from lock traffic (the usual advice is to avoid many small writers in one directory, and to mount with `noatime`, `nodiratime`) (to verify). Backups, quotas and SELinux contexts need extra thought, and the supported node counts and sizes are limited by the vendor's support policy (to verify per release).

## Assessment: the good, the bad and the ugly

**The good.** DRBD makes two ordinary servers behave like a shared disk without a SAN; it is transparent to applications, in the kernel, and well documented. Synchronous replication gives a recovery point of zero for committed writes. GFS2 provides real shared access for the workloads that need it: shared web content, clustered services that need common files, and virtualisation with live migration on shared images (to verify).

**The bad.** Replication does not protect against mistakes: a deleted file or a corrupted table is faithfully replicated to the peer, so backups remain essential. Synchronous protocols add network latency to every write; asynchronous ones risk losing writes. Active/active needs a cluster file system with its overhead, support requirements and operational skill. Resynchronisation after outages can take hours on large volumes and leaves the pair vulnerable until it ends. Two-node designs need fencing delays and careful networking, ideally on a dedicated, redundant replication link.

**The ugly.** Split brain: the replication link and the cluster link both fail, each side is promoted, both accept writes, and the histories diverge; without automatic policies one side's data must be discarded. A cluster file system with fencing "temporarily" off. Promoting an out-of-date secondary during a failover (the `Outdated` state exists to warn about this). Running `mkfs` on the wrong device or node. Two clusters sharing one DLM lock table name. And the choice of GFS2 where a simple active/passive file system would have done: complexity bought without need.

**Decision rules.** If an application can be active/passive, use DRBD with a normal file system (xfs or ext4) and one primary at a time. Use a cluster file system only where concurrent access from multiple nodes is truly required, and then with fencing tested. Prefer application-level replication for databases where available. Consider the vendor's support matrix before choosing. Keep backups outside the replicated pair.

**Assumptions.** Commands and options follow the cited ClusterLabs and Red Hat documents and the DRBD 9 syntax they use; DRBD 8 syntax and the exact bring-up and sync commands differ and are marked (to verify). Kernel history and protocol semantics summarise public LINBIT and Linux documentation [web: linbit.com] [web: kernel.org].

## Applications beyond this domain

Replicated block storage is the idea behind cloud volume replication, synchronous mirroring in storage arrays, and the replicated volumes in Kubernetes storage systems (Longhorn, OpenEBS, Ceph's RBD mirroring). Distributed locking with fencing tokens is the same logic as leader election with leases. The tension between synchronous and asynchronous replication, and the recovery point it implies, recurs in database replication and disaster recovery, which the next topics address.

## Examples

**Example 1: a DRBD resource file.** A resource named `wwwdata` with `protocol C`, one `on` section per node naming the backing logical volume, and a `connection` listing the two addresses on port 7789; fencing set to `resource-and-stonith` with the cluster's helper handlers [src: clusterlabs-docs d0c119b06cf61e35].

**Example 2: bring-up.** `drbdadm create-md wwwdata && modprobe drbd && drbdadm up wwwdata` on both nodes; `drbdadm status` shows `Inconsistent` until the first synchronisation; promote one node to start it [src: clusterlabs-docs 5bcf0a8fc16f6948].

**Example 3: an active/passive stack.** Promotable DRBD clone, then a `Filesystem` resource colocated with the promoted role and ordered after promotion, then the service, then the address [src: clusterlabs-docs c4154bd13cab8bcb].

**Example 4: converting to GFS2.** Disable the file system resource, create `mkfs.gfs2 -p lock_dlm -j 2 -t mycluster:web /dev/drbd1` on the primary, update the resource's file system type, add the DLM clone and its constraints, allow two promoted instances, and clone the file system [src: clusterlabs-docs 37dafc0c34f90f6c] and [src: clusterlabs-docs 553b72c78e458248].

**Example 5: a fencing delay.** With one fence device for both nodes, set `pcmk_delay_base="node1:5s;node2:0s"`: fencing aimed at node1 waits five seconds, so in a link failure node1 fences node2 first rather than both firing at once [src: rhel-10-docs 6bd554d4bdddf5d7].

**Worked failure: the double primary.** A pair used `allow-two-primaries` for convenience with an xfs file system (not a cluster file system) and no fencing. After a replication-link flap, an administrator promoted both sides by hand to "bring the service back quickly". Both mounted xfs read-write; each wrote its own metadata. When the link returned, DRBD reported split brain and refused to connect. One node's data had to be discarded, and the files created there during the incident were lost. A cluster with `resource-and-stonith` fencing and one promoted instance would have blocked the second promotion.

## Active research

Work continues on DRBD with more than two replicas and with diskless nodes, on faster resynchronisation, on replication over RDMA and NVMe over fabrics, and on integration with Kubernetes through operators. Cluster file systems are being tuned for NVMe and for lock-scalability; the broader trend is toward distributed object and block stores instead of shared-disk designs (to verify).

## Future direction

Expect most new designs to prefer application-level replication or distributed storage, with DRBD kept for simple two-node enterprise stacks and edge sites, and GFS2 for niche shared-access needs. The reasoning stays valid in any form: know where the authoritative copy is, make sure only one party can write unless the file system is built for many, and prove that fencing works before trusting the data to it.
