# Ansible Vault: keeping secrets in version-controlled automation

## Define the problem

Automation needs secrets. A playbook that installs a database sets its administrator password; a role that joins a domain needs a service account; a template for an application embeds an API token. The whole value of configuration as code is that it lives in a repository where it can be reviewed, compared and rolled back, and that is exactly where a plain-text password must never be. The problem is therefore to let sensitive values travel with the code, available to the automation at run time, unreadable to anyone who only has the repository.

The failure shapes are familiar. A token committed once stays in Git history long after the file is cleaned. A shared password written in a README is eventually pasted into a chat. A playbook run with maximum verbosity prints a password argument into a CI log that dozens of people can open. A secret changed on one server but not in the automation is reverted by the next run. This slice covers Ansible's built-in answer, Ansible Vault, along with its limits and the surrounding practice: what it protects, what it does not, how passwords and labels are handled, and when an external secret manager is the better tool. The variable layers where encrypted values are placed are LNX-305-T01, and the templates that consume them are LNX-305-T02.

## History and approaches

The first generation of tools handled secrets by leaving them out: values lived on the central server (Puppet's master, Chef server, Salt master) and were delivered over the agent channel. That worked while the server was the authority, but the repository that described the system was still incomplete, and anyone with server access saw everything. Chef introduced encrypted data bags around 2011, using a shared secret file, and the later chef-vault added per-node public-key access. Puppet users adopted hiera-eyaml, which encrypts individual values inside YAML with public-key cryptography so that a diff still shows the structure. Salt supports a GPG renderer for pillar data.

Ansible's own approach arrived in version 1.5 (2014) with the `ansible-vault` command. In the original design, a whole file was encrypted with one password, and a playbook run was given that password. The cipher was AES256, and the file was wrapped in a text header so Git could store it. Single-file encryption had two drawbacks that experience exposed: a diff of an encrypted variable file showed nothing at all, and every variable in the file was hidden even when only one was secret. Ansible 2.3 (2017) added encrypting individual values, written inline in ordinary YAML with a `!vault` tag, and 2.4 added vault IDs, labels that let a project use several passwords (say, one for development and one for production) and let ansible choose among them. Separately, external managers matured: HashiCorp Vault (2015, the name is a source of confusion with Ansible Vault, and they are unrelated products), AWS Secrets Manager, cloud key vaults, and, for files in Git, Mozilla's SOPS and Bitnami's sealed secrets for Kubernetes. Lookup plugins in collections let a playbook ask these systems for a value at run time rather than storing it at all.

A mixed record follows. Ansible Vault is simple, has no server, and works offline, so it spread widely. It also encourages a workflow in which a team shares one password for years, in which the password sits in a plaintext file next to the repository, and in which rotating a leaked secret means re-encrypting dozens of files. The emerging pattern is a two-tier approach: use built-in vault for bootstrap material and for small teams, and move to a secret manager once the number of secrets, the number of people or the audit requirements grow.

## Current state

### The mechanism

`ansible-vault` has subcommands to `create` a new encrypted file in an editor, `encrypt` and `decrypt` existing files, `view` and `edit` them without leaving plain files on disk, `rekey` to change the password or label, and `encrypt_string` to produce a single encrypted value. An encrypted file begins with a header of the form `$ANSIBLE_VAULT;1.1;AES256`, or `$ANSIBLE_VAULT;1.2;AES256;label` when a vault ID is attached, followed by hexadecimal text in fixed-width lines. The cipher is AES-256 in counter mode with an HMAC-SHA256 authentication tag, and keys come from the password through PBKDF2 with a random salt (to verify exact iteration count in the current source) [web: docs.ansible.com]. The text form means an ordinary `git diff` shows only that a blob changed.

Inline encryption keeps most of a file readable:

```yaml
db_user: appuser
db_password: !vault |
          $ANSIBLE_VAULT;1.1;AES256
          6338613133316631643630...
```

generated with `ansible-vault encrypt_string --name db_password` and then pasted. Playbook and role code uses the variable as normal, and decryption happens when the value is read. Files in `group_vars/` or `host_vars/` can also be wholly encrypted, and Ansible decrypts them as it loads variables [src: ansible-docs c8419ff8f177af3f].

### Supplying passwords and labels

The password reaches ansible-playbook in one of four ways: a prompt (`--ask-vault-pass`), a file (`--vault-password-file`, or the `ANSIBLE_VAULT_PASSWORD_FILE` environment variable), an executable that prints the password on standard output, or, through vault IDs, any of those with a label: `--vault-id prod@prompt`, `--vault-id dev@~/.vault_dev`. When the file's mode is executable, Ansible runs it and, if its name ends in `-client`, passes the label with `--vault-id`, so one small script can fetch secrets from a keyring, a password manager or a cloud secret service [src: ansible-docs 624658be899f7a77]. Several `--vault-id` options can be given at once; ansible matches a file's label to the password carrying the same label and otherwise tries each in turn. A bare `--vault-id` with a source and no label works for one password [src: ansible-docs 0195f0931c71d90c]. `ansible.cfg` can set `vault_identity_list` so that an operator does not repeat the options. For passing a single password and identity forms see the corresponding reference pages [src: ansible-docs 3cf3482bf67b6a1b, ansible-docs 54c5cd1e27167714].

### Habits that make the mechanism safe

A convention widely used in role repositories is indirection. The plain file `group_vars/db/vars.yml` holds `db_password: "{{ vault_db_password }}"` and the encrypted `group_vars/db/vault.yml` holds `vault_db_password`. The names are greppable, reviewers can see which variables are secret, and a change of secret value is visible as a changed encrypted blob only in the vault file. Task-level `no_log: true` hides arguments and results from output and callbacks, which is essential for tasks that handle a password, with the trade-off that failures become harder to debug. Verbose flags (`-vvv`) can still show connection details, and facts or registered results may contain secrets, so tasks that register them need the same treatment. A `.gitattributes` entry with a textconv driver that runs `ansible-vault view` can give readable diffs locally for those who hold the key, though this exposes plain text in the user's pager, so use it deliberately.

For rotation, `ansible-vault rekey` re-encrypts under a new password or label. Rotating the password does not rotate the secrets; if the vault password leaked, the encrypted values must also change at their source, since old repository history still contains the old ciphertext.

### Where Vault sits among alternatives

Ansible can read secrets at run time through lookup plugins: `community.hashi_vault.hashi_vault_read`, cloud secret managers' lookups, and `community.sops` for SOPS-encrypted files. These keep the repository free of ciphertext and give central audit, short-lived credentials and revocation. The automation controller (LNX-305-T08) has its own credential store, with typed credentials injected into a job as environment variables or files and never shown in the user interface after entry [src: rocky-docs a352d066a4bc0826]. In every case the value ends up in memory on the control node, and then in a file or process argument on a managed node, so the transport and the target's file permissions remain relevant.

## Assessment: the good, the bad and the ugly

The good is operational simplicity. There is no server to run, no network dependency, nothing to bootstrap before the first run, and the encryption is uniformly integrated: any variable file can be encrypted, and the loader handles it. Inline `!vault` values keep diffs and reviews meaningful for the non-secret parts. Labels give cheap separation of environments.

The bad: it is symmetric, so every person or system that can decrypt can read every secret under that label, and there is no per-secret access control or audit log. Passwords are usually kept in a file whose protection decides the whole system's security. Rekeying is manual, and a departed team member who knew the password keeps access to old ciphertext in history. Search and review of secrets are poor, since ciphertext is opaque and identical plaintext encrypts differently each time because of the random salt, so moving a value between files shows as a diff.

The ugly: leakage paths outside the file. A secret rendered into a template at `0644` is readable by every local user. A password in a command-line argument of a `command` task appears in the process list, and `no_log` does not hide it from `ps` on the target. A debug task or a `-v` run prints values. A CI system that prints environment variables exposes a vault password stored in one. Another hazard is the changing internal type: in ansible-core 2.19 the internal class that represented an encrypted value was replaced by a new encrypted-string type, so custom plugins that checked the old class break (to verify which collections were affected) [web: docs.ansible.com]. And as the name suggests, Ansible Vault does not protect against an administrator of the control node: whoever can run the playbook can print the decrypted value.

## Applications beyond this domain

The same two-tier pattern appears across the container and cloud world. Kubernetes Secrets are base64, not encrypted, so teams add sealed secrets, SOPS with a KMS key, or an external secrets operator that syncs from a manager; Docker and Compose have their own secrets mechanism with a mount of an in-memory file [src: docker-docs ab627e9bfceb2a3a]. Git-crypt and transcrypt provide transparent file encryption for repositories. Linux itself has the same shape in smaller scale: LUKS keys, `systemd-creds` for service credentials, and kernel keyrings all separate the secret from the thing that uses it. What carries over from Ansible Vault is the idea of a label that names a key, which maps directly to key identifiers in KMS systems, and the discipline of rotating a key and the data it protects as two separate jobs. For Active Directory service accounts, the Microsoft guidance on tiered administration gives the matching rule that a credential should be usable only from the tier that needs it [src: ms-learn-adds 5957580d19befcd1].

## Examples

A small team has `inventory/group_vars/all/vault.yml` encrypted with label `prod`, containing `vault_smtp_password`. The matching `vars.yml` defines `smtp_password: "{{ vault_smtp_password }}"`. The playbook runs from CI with `--vault-id prod@.ci/vault-client`, where the client script reads the password from the CI platform's secret store and prints it. A task with `no_log: true` writes the password into `/etc/postfix/sasl_passwd` with mode `0600`, and a handler runs `postmap`.

A multi-environment example uses two labels: `dev` and `prod`. The same playbook is run with both `--vault-id` options in a developer's staging run, and with only `prod` in production. A developer without the `prod` password can still run everything in dev, and when the playbook meets a prod-labelled file without the matching password, it stops with a decryption error, not with an empty value.

A failing example: an engineer encrypts a value with `ansible-vault encrypt_string 'S3cret!' --name token` and the shell stores the secret in history. Another engineer adds a `debug: var=token` task to see why a login fails and commits it; the CI log now holds the token for everyone with read access. The remedy has three parts: use `--stdin-name` so the plain value never appears in the command line, remove debug tasks that print secrets, and rotate the token because it was exposed. A second failing example is the missing label: a file encrypted before labels were introduced has header version 1.1 and no label, which can be decrypted only by a matching unlabelled password, so a project that adopts labels needs a one-time `ansible-vault rekey --new-vault-id`.

## Related problems and ideas

Several related questions stand beside the tool. How should the vault password itself be managed? The honest answer is that every system has a root secret somewhere, and the choice is where. Options are an operator's password manager, a hardware token, a cloud KMS unwrapping a data key, or a controller's credential store. Another question is how to make secrets short-lived; dynamic credentials from HashiCorp Vault or a cloud's identity service (for example workload identity) eliminate the long-lived password and so most of the rotation work, at the cost of an extra service. A third is detection: scanning tools such as gitleaks and GitHub secret scanning find plaintext secrets that slipped past the vault.

Ideas outside the mainstream include encrypting to several recipients with public keys (as hiera-eyaml and SOPS do) so each person has an individual key and access is revoked by re-encrypting without that recipient, and confidential computing approaches where secrets are released to a node only after remote attestation. For Ansible specifically, public-key recipients for vault files have been discussed in the community more than once (to verify whether a design is accepted). The connection with identity management is direct: IdM and FreeIPA offer a vault for storing secrets under access control, and their Ansible modules can create and archive entries [src: rhel-10-docs 5a99affe30c81f85].

## Active research

Active work on the platform side includes the 2.19 data tagging system, which records that a value is encrypted and keeps that mark through templating so that results derived from a secret can be hidden or flagged. Research and industry reports on infrastructure-as-code security point out that hard-coded secrets are one of the most frequent smells in Ansible and Puppet code, and study detectors that combine pattern matching with variable-name heuristics. Open questions are how automation should prove that a value was never exposed in logs, how to detect secrets that flow into facts, and how to design per-recipient access without a server. Event-driven setups, where a webhook triggers a playbook, add the question of how to pass secrets to such short-lived runs safely [web: redhat.com].

## Future direction

Expect organisations to move from files and shared passwords to short-lived credentials issued per run, with Ansible reading them through lookups, or with the controller injecting them. The vault format remains stable and backward compatible, so existing files keep working, but guidance is moving toward minimising what is stored. Watch for official support of per-user keys, for continued work on type tracking of encrypted values, and for the secrets-management features of the automation platform. For practitioners, the minimal routine is: encrypt only what must be secret, use labels, use a client script not a file where possible, mark secret tasks `no_log`, keep file modes tight, scan repositories for leaks, and have a rehearsed rotation procedure.
