# Ansible inventories and the rules that decide which variable wins

## Define the problem

Configuration management starts with two questions that sound trivial and are not. Which machines are in scope, and what is true about each of them? A shell loop over a text file of names answers the first question badly and the second not at all. Real fleets are grouped along several axes at once: by role (web, database), by environment (development, production), by location (a region or a rack), by operating system family and by lifecycle state (being built, in service, being retired). The facts that differ between those groups, such as a package version, a listening port, a time server, a credential or a connection user, have to be written down once, in the most general place that is still correct, and overridden only where reality demands it.

An Ansible inventory is the answer to the first question: it is the list of managed nodes, arranged into groups, together with connection settings and variables. Variable precedence is the answer to the second: a deterministic ranking that says which definition is used when the same name is set in several places. Failure here is quiet and expensive. A play that reads the wrong value of a variable does not crash; it configures a production database with the staging port, or renders a template with a default that someone thought they had replaced. The gap this topic fills is the distance between running a playbook against one host and predicting, before the run, what every host will receive.

The slice covered here is the control-node side of Ansible 2.x and later (ansible-core 2.15 to 2.19 at the time of writing): static and dynamic inventories, group and host variables, patterns and limits, the ordered list of variable sources, how groups are merged, and the commands that let an operator inspect the outcome. Variables inside roles and playbooks are met again in LNX-305-T02 and LNX-305-T03; encrypted variables are LNX-305-T04.

## History and approaches

The oldest approach is the host list in a shell script. Tools such as `pdsh` and `dsh`, and later Capistrano and Fabric, kept a flat list of names or a role map in code. They executed commands in parallel but modelled no data, so every script rebuilt its own notion of "the web servers".

CFEngine, started by Mark Burgess in the early 1990s, introduced the idea that a node classifies itself into classes and that promises attach to classes. Puppet (2005) moved the classification to a central server: an external node classifier, and later the Hiera hierarchy, returned a set of classes and data for each node, and a key could be looked up through an ordered list of levels such as node, role, environment and common. Chef (2009) stored node attributes on a server and defined a long ladder of attribute levels (default, normal, override, automatic) with a separate rule for every combination. Salt (2011) split the data into grains reported by the minion and pillar data pushed from the master. In all four systems the node held an agent that checked in, so the inventory was implicitly the set of registered agents, and precedence was something you discovered by reading the server-side lookup code.

Ansible, released in 2012 by Michael DeHaan, took a different position: no agent and no server, only a file the operator controls. The first inventory was an INI-style file in `/etc/ansible/hosts`. Groups were headings, hosts were lines, and per-host variables were written inline. Two additions followed quickly: directories named `group_vars` and `host_vars` that put data in separate YAML files, and executable inventory scripts that print JSON, which made it possible to ask a cloud API for the current instance list. The EC2 script and its sibling scripts for other providers proved the model and also showed its weakness. They were slow, each needed its own cache, they were configured through side files whose format varied, and nothing validated their output.

Ansible 2.4 (2017) replaced scripts as the preferred mechanism with inventory plugins, which are ordinary plugins with a documented option set, a common cache layer and a `verify_file` hook that lets Ansible try several plugins on one source. The same release added YAML and `constructed` inventories, where groups are computed from host variables and facts, and the `ansible_group_priority` variable to settle merge conflicts between groups at the same depth. Variable precedence has its own history of partial fixes. Early releases documented a short list, then a long one; version 2.0 reworked the engine; the rule that facts rank below play variables and the rule that registered values rank above most others each surprised users; the `hash_behavior` setting that merges dictionaries instead of replacing them was declared discouraged and kept only for compatibility, with the `combine` filter recommended instead. The official documentation now presents 22 ranked levels, and it also publishes advice that makes the list almost irrelevant for everyday work: keep the number of places a variable lives small.

What emerged from these experiments is a pattern: data lives outside code, grouped by the dimension that varies; a fixed ranking picks the winner; and the inspection tool must be able to print the final merged result for one node. Ansible's ranking is deterministic but long, and later systems such as Docker Compose, Helm and Terraform each converged on a shorter ladder of the same shape [src: docker-docs ddd3d31c333b6201].

## Current state

### Inventory sources and layout

An inventory is any source that an inventory plugin can parse. The `-i` option, the `inventory` key in `ansible.cfg` or the `ANSIBLE_INVENTORY` environment variable names one or more sources, and a directory is treated as a set of sources that are all loaded. The common forms are the INI file, the YAML file, a plugin configuration file whose name ends in a suffix such as `aws_ec2.yml`, and an inline comma-separated host list for one-off work. Two groups always exist: `all`, which contains every host, and `ungrouped`, which holds hosts that appear in no other group. Groups can nest through `children`, so `prod` can contain `prod_web` and `prod_db`, and a host may belong to any number of groups [src: ansible-docs 931fa4fc4e4acb3b].

```yaml
# inventory/hosts.yml
all:
  vars:
    ansible_user: automation
  children:
    web:
      hosts:
        web01.example.org:
        web02.example.org:
          http_port: 8081
    db:
      hosts:
        db01.example.org:
    prod:
      children:
        web:
        db:
```

Connection behaviour is controlled by reserved variables: `ansible_host` (the address to connect to when it differs from the inventory name), `ansible_port`, `ansible_user`, `ansible_connection` (`ssh`, `local`, `docker`, `winrm` and others), `ansible_become` and its siblings, `ansible_python_interpreter`, and `ansible_ssh_private_key_file`. Because they are ordinary variables, they follow the same precedence rules as everything else, and that is why a group variable can change how a host is reached.

### Where variables live

Variables for hosts and groups can sit inline in the inventory, but the recommended layout puts them in `group_vars/<group>.yml` and `host_vars/<host>.yml` (or directories of the same name holding several files) next to the inventory or next to the playbook. The loader reads both locations, and the one beside the inventory ranks below the one beside the playbook at the same kind of level. The `group_vars/all` file applies to every host. Elsewhere in the ranking are role defaults and role vars, play-level `vars` and `vars_files`, task and block vars, facts gathered from the host, values created by `set_fact` or `register`, `include_vars`, and finally extra vars given with `-e` on the command line [src: ansible-docs e771953246c8371c].

The official ranking, from weakest to strongest, is: role defaults; inventory group vars (file or script); inventory `group_vars/all`; playbook `group_vars/all`; inventory `group_vars/*`; playbook `group_vars/*`; inventory host vars; inventory `host_vars/*`; playbook `host_vars/*`; host facts and cached `set_fact` values; play vars; play `vars_prompt`; play `vars_files`; role vars; block vars; task vars; `include_vars`; registered values and `set_fact`; role and `include_role` parameters; `include` parameters; extra vars. Command-line connection options such as `-u` sit below role defaults and are not variables at all, which is why an `ansible_user` set in a group beats `-u` [src: ansible-docs 094110d62efbfbcc]. The structure behind the list is simple. Generality grows downward (everything, then group, then host), locality grows upward (a single task beats a play, a play beats an inventory), and the operator's explicit command-line override outranks everything because it is the last thing a human typed.

### How groups merge

For one host, Ansible merges the group variable sets of every group the host belongs to, in a defined sequence: `all` first, then parent groups before child groups, and, among groups of the same depth, alphabetically by group name, so that the alphabetically last group wins. Setting `ansible_group_priority` on a group raises or lowers its position within its depth level; the default is 1, a higher number is applied later and therefore wins, and the variable only takes effect in inventory sources, not in `group_vars` files. Host variables then override all of that [src: ansible-docs 0f4db668a26720bb]. Dictionaries are replaced, not merged, by default. If a group defines `app: {port: 80, tls: false}` and a more specific group defines `app: {tls: true}`, the host sees only `tls`. The `combine` filter (with `recursive=true` when needed) is the supported way to build a merged result explicitly, usually under a new variable name so the layers stay visible.

### Patterns, limits and inspection

A pattern selects hosts from the inventory: `web` (a group), `web:db` (union), `web:&prod` (intersection), `web:!staging` (exclusion), `web*.example.org` (wildcard), `~web\d+` (regular expression) and `web[0:2]` (subscript). The command-line option `--limit` applies a further pattern to whatever the play requested, and it is the safe way to run a change on one canary host first. The `ansible-inventory` command is the inspector: `--graph` draws the group tree (with `--vars` it shows variables at each level), `--list` prints JSON, `--host name` prints the merged variables for one host, and `--yaml` or `--toml` changes the format. For checking a single value in a real play context, `ansible -m debug -a var=name host` works, and `ansible-config dump --only-changed` shows which configuration settings differ from defaults and where each one came from.

Configuration for the control node itself has its own search order: the `ANSIBLE_CONFIG` variable, then `./ansible.cfg`, then `~/.ansible.cfg`, then `/etc/ansible/ansible.cfg`; the first file found is used alone, with no merging. That detail matters when a project directory is world-writable, because Ansible ignores a local `ansible.cfg` there for safety.

### The generalised pattern

Strip the Ansible syntax and the design is a cascade: layered key-value sources, each tagged with a specificity, resolved by a fixed total order, with an inspection command that prints the resolved view and its origin. The same cascade appears wherever configuration is layered, and good practice is the same everywhere: define a default at the least specific layer, override as narrowly as possible, never rely on ordering that the reader cannot see.

## Assessment: the good, the bad and the ugly

What works well is the data-oriented design. Operators can version `inventory/` and `group_vars/` in Git, review changes as diffs, and test a change by limiting it to one host. Agentless connection means an inventory is usable the moment a host answers on SSH. The plugin interface lets the same playbooks run against a cloud-generated inventory, a CMDB export and a hand-written file. The `ansible-inventory --host` view gives a single place to ask what a node will see.

What works badly is the sheer count of levels. Twenty-two ranks are more than a human can hold, and each additional place a variable can be set multiplies the number of debugging paths. Several levels behave counter-intuitively: role `vars` outrank play `vars`, so a role author who writes a value there removes the caller's ability to override it with anything short of `-e` or a role parameter; `set_fact` values outrank almost everything else and persist for the rest of the play, so a fact set early can silently defeat inventory data; and host facts rank above inventory host vars, so a fact named like a user variable can shadow it. Same-depth group conflicts are resolved alphabetically, an implicit rule that breaks when somebody renames a group. The community's usual advice is to avoid depending on it: name variables distinctively (a role prefix), set each one in exactly one layer, and give conflicting groups explicit priority when unavoidable.

The awkward parts are mostly operational. Dynamic inventories depend on an external system, so a cloud API outage or a changed tag turns into an empty host list; a play against an empty pattern succeeds with nothing done, which is why pipelines should assert a minimum host count. Inventory caching saves minutes per run but keeps stale hosts. INI inventories parse inline variable values as Python-style literals while YAML inventories parse them as YAML, so the same text can yield different types. The 2.19 release added stricter typing and templating rules, which exposed latent bugs: values that used to be stringified silently now keep their native type, and undefined variables used in `vars_files` paths now produce warnings [web: docs.ansible.com]. Reported breakage in downstream tooling shows that even careful users were relying on old coercions [web: blog.ipspace.net].

Security is another edge. Inventory variables are often where secrets end up. Without encryption the values are in plain text in the repository (see LNX-305-T04), and `ansible-inventory --list` prints them unless they are vaulted. Connection variables from untrusted sources are also an injection path: a dynamic inventory fed from user-writable cloud tags can set `ansible_host` or `ansible_connection` to attacker-chosen values.

## Applications beyond this domain

The layered-override idea is general. Docker Compose ranks its environment sources (shell, `--env-file`, `environment`, `env_file`, image defaults) in a documented order [src: docker-docs ddd3d31c333b6201]. Helm combines chart defaults, successive `-f` values files and `--set` flags, with the last one winning. Kustomize overlays patch a base per environment. Terraform ranks `-var` flags, `*.auto.tfvars` files, `terraform.tfvars` and environment variables. systemd drop-in directories override the unit file shipped by the package, and the `systemctl cat` command shows every layer. CSS specificity, Hiera hierarchies and Chef attribute levels are older relatives. What carries over is the diagnostic habit: identify the layers, find the printer of the merged view, and confirm the origin of the final value rather than guessing.

Inventory itself recurs as the "service catalogue" in other tools. Prometheus service discovery, Kubernetes label selectors and Nagios host groups all select targets by attributes, and the Ansible `constructed` inventory, which derives groups from variables, uses the same idea as Kubernetes selectors. Understanding one makes the others quicker to read. For the container side of the same pattern, see how Compose profiles and Kubernetes namespaces slice a fleet (the CN pathway courses build on this).

## Examples

A first example is the clean case. A small shop keeps `inventory/production.yml` with groups `web` and `db`, `group_vars/all.yml` with `ntp_servers`, `group_vars/web.yml` with `http_port: 80`, and a `host_vars/web02.example.org.yml` file that sets `http_port: 8081` for a host in transition. Running `ansible-inventory -i inventory --host web02.example.org` prints `http_port: 8081`, and a play that templates a virtual host reads that value without any conditional logic.

A second example is the alphabetical trap. A host belongs to two sibling groups, `rack_a` and `edge`, and both define `log_level`. Nobody sets a priority. Today `rack_a` wins because it sorts later. After a reorganisation renames `edge` to `zone_edge`, the value silently flips on every edge host, and the next deployment changes the logging volume of production. The fix is either to define the variable in one group only or to set `ansible_group_priority` on the group that should win. The lesson is to treat any variable defined in two groups as a defect to be removed, not a feature.

A third, failing example mixes facts and variables. An engineer writes a role default `app_version: 2.3` and, in a task near the start of a play, `set_fact: app_version: "{{ app_version | default('2.3') }}"`. Because `set_fact` outranks inventory data, every later task sees the fact, and a later `-e app_version=2.4` is the only thing that overrides it. Inventory-based canary rollouts that depended on a `host_vars` override no longer work. The remedy is to give the computed value a new name, such as `app_version_effective`, and leave the input untouched.

A fourth example is a dynamic inventory in a cloud environment: an `aws_ec2.yml` plugin file lists regions, `keyed_groups` turn the `Role` tag into groups such as `role_web`, `compose` sets `ansible_host` to the private address, and `cache: true` with a cache plugin bounds API calls. A shell sanity check (`ansible-inventory --graph | grep -c role_web`) before the play guards against an empty selection. The infrastructure side of this pattern, where an image or provisioning tool emits the inventory, is in LNX-306-T10 (cloud provisioning).

## Related problems and ideas

Pull-based alternatives such as `ansible-pull`, Puppet agents and Salt minions turn the question around: the node fetches its own configuration, so the inventory is replaced by node self-classification. That trades central visibility for scale and for resilience when nodes are behind NAT. At the other extreme, immutable images built with Packer (LNX-306-T04) and declarative orchestrators (Kubernetes) reduce the number of per-host variables because hosts are replaced rather than edited, which shrinks the inventory problem to a small set of image parameters.

External sources of truth are a related idea: NetBox, a CMDB or a cloud tag taxonomy as the authoritative inventory, with Ansible reading it through a plugin and writing nothing back. The unresolved difficulty is ownership: two systems holding the same fact eventually disagree. Variable-source plugins that look up data from a secrets manager at run time, instead of storing it in the repository, address the plaintext-in-Git problem. LNX-305-T04 compares them with Vault. Composition with roles is covered in LNX-305-T03, where role defaults are deliberately the lowest rank so that every other layer can override them. System roles from Red Hat (LNX-305-T05) publish their variables as a documented interface, which is exactly what a precedence ladder needs to stay maintainable.

## Active research

The ansible-core 2.19 line introduced data tagging, a mechanism that attaches metadata such as origin (file and line), trust and vault-encryption state to values as they flow through templating. It improves error messages for undefined or mistyped variables and supports a trust model in which only strings from trusted sources are rendered as templates, which closes a class of template-injection attacks from inventory data [web: docs.ansible.com]. Open questions on the community forum include how custom plugins should declare trust, how to migrate inventories that relied on multi-pass templating, and whether the number of precedence levels can be reduced without breaking existing playbooks (to verify: no accepted proposal at the time of writing).

Academic and industrial work on configuration is wider. Studies of infrastructure-as-code defects repeatedly find that configuration values and conditionals are among the most common bug locations, which motivates linters (LNX-305-T06) and type-aware schemas for variables. Role argument specifications (`meta/argument_specs.yml`), validated at run time, are the practical outcome so far. Dynamic inventory at scale, with incremental updates and event-driven triggers, is under development in the event-driven Ansible project (to verify current scope).

## Future direction

Expect three trends. First, stricter templating and typing as the 2.19 model settles, with more warnings turning into errors in 2.23 and later; teams should test inventories against each new ansible-core release in a branch. Second, a continued shift from scripts to plugins and to collections that read authoritative systems, so the inventory file shrinks to a pointer. Third, more explicit interfaces: argument specs for roles and playbooks, schemas for host data, and pre-flight validation in CI. Anyone responsible for a fleet should watch the ansible-core porting guides on each release, the deprecation list that names the removal version, and the status of collections used for inventory, since those are maintained separately from the core and may lag a core release by months.
