# Playbooks: ordered tasks, change-triggered handlers, loops and templating

## Define the problem

Once an administrator knows which hosts are in scope (LNX-305-T01), the next problem is describing what should be true on them in a form that can be read, reviewed and rerun. A useful description has to do four things that shell scripts do poorly. It must run steps in a fixed order across many machines, with a defined behaviour when one step fails. It must separate what changed from what was already correct, so that a service restarts only when its configuration really moved. It must repeat a step over a list without copying text. And it must produce configuration files whose content depends on the host, such as a listen address, a list of upstream servers or a set of users.

A playbook is Ansible's answer: a YAML document that maps groups of hosts to ordered lists of tasks, each task calling a module with arguments. Handlers give run-only-on-change semantics, loops give iteration, and Jinja2 supplies expressions, conditions and file templates. The gap it fills is the one between ad hoc commands and a full programming language: enough control flow to describe real procedures, but a structure regular enough that tooling can lint it, a reviewer can read it and a check run can predict it. This slice covers the syntax and the execution model in ansible-core 2.15 to 2.19; roles and collections that package playbook content are LNX-305-T03, and the discipline of making tasks safe to repeat is LNX-305-T07.

## History and approaches

Before declarative tools, administrators scripted: a shell script per server type, copied by hand, edited in place with `sed`. Capistrano and Fabric added remote execution and named tasks to Ruby and Python code, but their unit was a command, not a desired state. CFEngine and Puppet went the other way. A Puppet manifest declares resources and their dependencies, and the agent builds a graph and applies it in a dependency order it computes. This is powerful, but it forces users to think in terms of a graph, and an ordering mistake shows up as a cycle or a missing relationship that the author never wrote down. Chef chose Ruby recipes that execute top to bottom, which is flexible but invites arbitrary programs.

Ansible's playbooks, introduced in 2012, took a middle path: declarative modules, imperative order. The author writes tasks in the order they should run, and each module is responsible for checking whether its target state already holds. The handler mechanism came from the same origin, borrowed from the notification relationships of Puppet and Chef in simplified form: a task can notify a named handler, and handlers run once, after the section that notified them. Early loops were a family of `with_*` keywords (`with_items`, `with_dict`, `with_subelements`), each backed by a lookup plugin. They worked but were an irregular dialect; version 2.5 introduced the uniform `loop` keyword with `loop_control`, and the `with_*` forms remain only for compatibility.

Two other design arguments played out in public. The first concerned reuse inside playbooks. The original `include` mixed static and dynamic behaviour, depending on context. Version 2.4 split it into `import_tasks` and `import_playbook` (processed when the playbook is parsed, so tags and conditions are applied to each imported task) and `include_tasks` and `include_role` (processed when reached at run time, so a loop or a variable can pick the file). The plain `include` was deprecated and removed in 2.16. The second argument concerned naming. Short module names such as `copy` and `yum` were global until collections arrived in 2.10 and the module name acquired a namespace; the fully qualified collection name, for example `ansible.builtin.copy`, is now the recommended spelling because it is unambiguous and because linters can check it.

Jinja2 was part of Ansible from the start, borrowed from the Python web world (Flask uses it). Its use in task arguments produced a long-lived design problem: Ansible rendered everything to strings, then guessed types back with a literal evaluation, which is why `"{{ port }}"` once gave a string where a number was expected. Optional native-type rendering (`jinja2_native`) appeared as a workaround and was eventually made the only mode in 2.19, together with a rewritten templating engine and a rule that only trusted template sources are evaluated [web: docs.ansible.com]. The history ends where several others do: a notation built for convenience grew control flow, and the maintainers then spent years making its behaviour precise.

## Current state

### The shape of a play

A playbook is a list of plays. A play names its target (`hosts:`), optional settings such as `become`, `gather_facts`, `vars`, `vars_files` and `serial`, and then up to five ordered sections, which run as pre-tasks, roles, tasks, post-tasks and handlers. Each task is a mapping with a module key and common keywords: `name` (a label that appears in the output), `when`, `loop`, `register`, `notify`, `tags`, `become`, `delegate_to`, `changed_when`, `failed_when`, `ignore_errors`, `no_log`, `until` with `retries` and `delay`, and `environment`. A play with no `name` on tasks works but is hard to read in output, and ansible-lint flags it (LNX-305-T06).

By default the linear strategy applies one task to all hosts in the current batch before the next task begins. `forks` (default 5) limits concurrent connections within a task, `serial` splits the host list into batches so that a rolling update touches a few machines at a time, and `max_fail_percentage` aborts a rolling update when too many hosts in a batch fail [src: ansible-docs 7cf6f07cec8977ba]. The `free` strategy lets each host run ahead independently. `run_once` executes a task on a single host of the batch, and `delegate_to` runs it elsewhere, which is the standard way to talk to a load balancer or to a database host on behalf of the target. Facts are collected by an implicit `ansible.builtin.setup` task unless `gather_facts: false`, and they are available as `ansible_facts`.

### Handlers

A handler is a task defined in the handlers section (or in a role's `handlers/main.yml`) and triggered by the `notify` keyword of another task, which names it or, with `listen`, names a topic. A handler runs only if the notifying task reported `changed`, runs at most once per play per host however many tasks notified it, and runs after the tasks section finishes, not immediately. Handlers fire in the order they were defined, not in the order they were notified. `meta: flush_handlers` forces pending handlers to run at that point, which is needed when a later task depends on a restarted service. If a task fails on a host, that host's pending handlers do not run unless `force_handlers` is enabled, and a handler notified from a skipped task is not queued [src: rocky-docs fd634b947f2d659c]. Handlers belong to the play or role that defines them; imported handlers behave as static content, while dynamically included ones are subject to the rules of the include [src: ansible-docs 22e8de31c5e08e8d].

### Loops, conditionals and blocks

`loop` takes a list. Each item is `item` inside the task, or a name chosen with `loop_control: {loop_var: x}`; the other controls are `label` (to keep large items out of the output), `index_var`, `pause` and `extended`. Dictionaries are iterated with the `dict2items` filter, and nested data with `subelements`, `product` or `zip` lookups and filters. `register` on a looping task stores a `results` list with one entry per item. `until` repeats a task until a condition on its own result holds, which is how a playbook waits for a service. `when` takes a Jinja expression without the braces, evaluated per host, and per item inside a loop. Typical conditions use facts (`ansible_facts['os_family'] == 'RedHat'`), registered values (`result.rc == 0`, `result is changed`), tests (`is defined`, `is failed`) and membership (`inventory_hostname in groups['db']`) [src: rocky-docs cbe81a3873a77b1b].

A `block` groups tasks so that keywords such as `when`, `become` or `tags` apply to all of them, and `rescue` and `always` sections give structured error handling in the manner of try, catch and finally. A failure in the block runs `rescue` for that host; `always` runs in both cases.

### Jinja2

Jinja2 is used at three levels. Expressions in `{{ ... }}` are evaluated inside task arguments and variables [src: ansible-docs c4981571d3e6d3ff]. Conditions in `when` and `failed_when` are bare expressions. Template files, rendered by `ansible.builtin.template` on the controller and copied to the target, can also use statements (`{% if %}`, `{% for %}`, `{% include %}`) and comments. Filters transform values: Ansible adds many to Jinja's own, for example `default` (with `omit` to drop an argument), `mandatory`, `combine`, `dict2items`, `map`, `select`, `selectattr`, `regex_replace`, `to_nice_yaml`, `password_hash`, `b64encode` and `ipaddr` (from the `ansible.utils` collection). Lookups such as `file`, `env` and `pipe` run on the controller. The template module accepts `validate` (run a checker on the rendered file before installing it), `backup`, `owner`, `mode` and `lstrip_blocks`-style whitespace settings; Ansible enables `trim_blocks` by default, so a newline after a statement tag disappears [src: rocky-docs 8c8d5ecf1fc5015a].

Two syntax traps recur. A YAML value that starts with a Jinja expression must be quoted, because the opening brace would otherwise parse as a mapping. And YAML 1.1 booleans (`yes`, `no`, `on`, `off`) are converted in unquoted values, so a literal string such as `no` or a country code must be quoted; modern style prefers `true` and `false`.

### The 2.19 changes in practice

After 2.19, nested template delimiters inside an expression are errors; a conditional that does not evaluate to a boolean is an error, where earlier releases treated a non-empty string as true; items that resolve to the omit placeholder are dropped from a loop; and `range()` returns a range object that must be wrapped in `list` if a list is wanted [web: docs.ansible.com]. Teams should run their playbooks under the new release in a branch before the platform images are upgraded.

## Assessment: the good, the bad and the ugly

The good: playbooks are readable to people who do not program, they run over plain SSH, and a name per task gives a log that reads like a checklist. The module contract (arguments in, `changed` and `failed` out) makes dry runs and reporting uniform. Handlers prevent needless service restarts, and the template module with `validate` makes configuration deployments safer than copying a file blind.

The bad: YAML plus Jinja is a programming language without the usual tools. Conditions and loops interact in ways that confuse: a `when` clause is re-evaluated for each item, a registered looping result has a different shape from a single result, and a skipped task registers a result that has `skipped` set but no `rc`. Filters chained across several lines are hard to debug, there is no debugger beyond `debug` tasks and `ansible-playbook -vvv`, and whitespace handling in templates produces off-by-one blank lines. Error messages historically pointed at the wrong line when YAML quoting was off, which 2.19 improves with origin tracking.

The ugly: handler timing. Because handlers run at the end of the play and not for hosts that failed, an incident can leave a configuration file changed but its service not reloaded. The next run sees no change and does not notify the handler again, so the service stays out of sync until someone restarts it. The mitigations are `meta: flush_handlers` after the change, `force_handlers`, or placing configuration and reload in a block with `always`. Another ugly area is performance. A play of 40 tasks against 500 hosts at 5 forks takes a long time, and fact gathering costs seconds per host. Practical remedies are raising `forks`, enabling SSH pipelining and ControlPersist, caching facts, using `gather_subset`, and avoiding `command` loops. Finally, `shell` and `command` break the contract: they always report changed unless the author adds `changed_when` or `creates`/`removes`, so a playbook full of them can never be shown to be clean (LNX-305-T07).

## Applications beyond this domain

Jinja2 is the same engine that renders Flask pages, Salt state files and Cookiecutter project templates, and the cloud-init user-data format accepts Jinja2 as a header option (see LNX-306-T03). Prometheus and Alertmanager use a different template language (Go templates) with the same purpose, as do Helm charts, and the cross-training is useful: variables, filters, conditionals and loops are the same concepts. Handlers resemble the observer pattern and Makefile dependency rules; systemd's `Restart=` and `ExecReload=` model a similar "reload when the configuration moved" relationship. The block, rescue and always trio matches try, catch and finally in programming languages and the compensating-action idea in workflow engines. The rolling `serial` pattern is the same as a Kubernetes rolling update with `maxUnavailable`, and both depend on a health check between batches (for Kubernetes, see the CN pathway).

## Examples

A minimal working play installs and configures a web server and restarts it only when the configuration changed:

```yaml
- name: Web tier
  hosts: web
  become: true
  vars:
    http_port: 8080
  tasks:
    - name: Install nginx
      ansible.builtin.package:
        name: nginx
        state: present
    - name: Render the site configuration
      ansible.builtin.template:
        src: site.conf.j2
        dest: /etc/nginx/conf.d/site.conf
        mode: "0644"
        validate: nginx -t -c /etc/nginx/nginx.conf
      notify: Reload nginx
    - name: Ensure service is enabled and running
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded
```

A loop example creates several users, each with a list of groups, and uses `loop_control.label` so the output shows only the name. A template example renders an upstream block from `groups['app']`, using a Jinja `for` loop over `hostvars[host]['ansible_host']`. A conditional example selects the package name by `os_family`.

A failing example shows the handler trap described above. A play changes `/etc/ssh/sshd_config` and notifies a restart handler, then a later task fails on a typo in a path. The handler never runs for that host. The operator fixes the typo, reruns the play, sees `ok` for the sshd task and no change, so the handler is not queued, and the daemon keeps running with the old configuration. The correction is to flush handlers right after the configuration task, or to design the template task with `validate: sshd -t -f %s` and keep risky tasks before it.

A second failing example is the bare-string condition: `when: "{{ enabled }}"` worked on old releases and was a warning for years; on 2.19 it produces an error about conditionals that need a boolean result, and the fix is `when: enabled | bool`.

## Related problems and ideas

The declarative alternative remains attractive: Puppet and Kubernetes manifests describe the end state and let the engine decide the order. The price is a more abstract model. Terraform and OpenTofu (LNX-306-T05) occupy the provisioning end, where the order is a graph of resources. Ansible can wrap either: a playbook that runs a Terraform plan, or a module that reads its state. For people who need real programming, Pulumi and CDK write infrastructure in general languages, while at the opposite extreme CUE, Dhall and Jsonnet aim to make data generation safe and typed without Turing-complete logic. Alternatives to Jinja inside Ansible have been suggested, such as a restricted expression language, but compatibility is the obstacle.

Closer to home, a related problem is choosing between inline modules. `lineinfile` and `blockinfile` edit part of a file and are fragile when the file's other content changes; `template` or `copy` owns the whole file and is safer when the playbook is the single source of truth. Split-brain between two writers of one file is the main reason to prefer full-file ownership or drop-in directories (for example `/etc/ssh/sshd_config.d/`). Relationships to other topics: variable inputs come from LNX-305-T01, secrets in templates from LNX-305-T04, and the use of loops and templates inside role-based packaging from LNX-305-T03.

## Active research

The most visible active work is the templating rewrite in ansible-core 2.19 and its follow-ups: tracking the origin of every value so error messages can name the source line, tagging values with trust and encryption state, and making the evaluation rules of conditionals and loops precise. Community forum threads document the open edge cases, such as plugins that build template strings dynamically and collections whose tests broke after upgrading, and a number of widely used collections were reworked to be compatible [web: forum.ansible.com]. Static analysis of playbooks is advancing in parallel: ansible-lint has added rules for risky Jinja patterns (LNX-305-T06), and research on defects in infrastructure code, much of it examining Ansible and Puppet repositories, continues to show that conditionals, string interpolation and mis-typed variables dominate. Natural-language assistance for writing playbooks, such as Red Hat's Lightspeed offering, is an open evaluation topic; accuracy and the safety of generated tasks are the main questions (to verify current product status).

## Future direction

Near-term, watch ansible-core 2.20 and later for the removal of items deprecated in 2.19 (the lenient `bool` filter handling is scheduled to become an error in 2.23) and for more performance work on templating, which the rewrite was intended to enable. Playbook authors can prepare by quoting booleans, using `| bool` explicitly, giving every loop variable a name, preferring `import_tasks` for static structure, and running ansible-lint with a profile that matches their publishing target. Longer term, the language may split in two directions: stricter, typed playbooks for shared content, and thinner playbooks that call into roles, collections and plugins written in Python, as the platform keeps moving complexity out of YAML.
