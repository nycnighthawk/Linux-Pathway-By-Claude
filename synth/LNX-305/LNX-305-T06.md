# Testing Ansible content: ansible-lint, Molecule and the test pyramid for automation

## Define the problem

Automation code changes real systems, usually as root, usually on many machines at once. It therefore deserves at least the quality controls that application code gets, and in practice it gets fewer. Playbooks are written in a language that is easy to start and hard to verify: a typo in a module argument is found only when the task runs, a conditional that is never true hides a branch forever, a role that works on one distribution fails on the next, and a change that was fine yesterday breaks tomorrow when a collection releases a new default. The gap that this topic fills is the lack of a repeatable, automated answer to two questions. Is this content written the way the community and the platform expect (style, safety, deprecations)? And does it do what it claims, on the platforms it claims to support, including on a second run?

The two tools covered answer these at different levels. ansible-lint is a static analyser: it reads playbooks, roles, collections and variable files, and reports rule violations without executing anything. Molecule is a test harness: it creates one or more disposable instances, runs the content against them, checks that a second run changes nothing, runs verification tasks and then destroys the instances. This slice covers their use in ansible-core 2.15 to 2.19 era projects (ansible-lint and Molecule 25 and later versions). The behaviour that Molecule tests, idempotence and check mode, is LNX-305-T07, and the role structure that it exercises is LNX-305-T03.

## History and approaches

Linting for configuration code started with Puppet (puppet-lint) and Chef (Foodcritic). For Ansible the first widely used tool was ansible-lint, begun in 2013 by Will Thames, which applied a Python rule per problem to a parsed playbook. It was adopted by Ansible Galaxy as a quality check and was later taken under the Ansible project. Over the years it grew from a few dozen opinionated rules to a platform with rule identifiers and tags, per-rule skip and warn lists, an auto-fix mode, a SARIF output for code scanning systems, a GitHub Action, and, since the 6.x releases, profiles: nested sets of rules that match a maturity target [web: docs.ansible.com]. Along the way the project solved two persistent problems of static analysis for a dynamic language: it learned to resolve roles and collections (installing requirements into a cache so that FQCN module references can be checked), and it learned to avoid false positives by supporting inline `# noqa` comments and a committed ignore file whose entries stay visible as warnings.

Testing for roles has a longer and more varied history. The first approaches were hand-built: a `tests/` directory in a role with a `test.yml` and an inventory, run manually. Test Kitchen with kitchen-ansible borrowed the Chef workflow of create, converge, verify and destroy. Serverspec and later Testinfra supplied assertions written in Ruby and Python. Molecule, begun by Cisco engineers and moved into the Ansible project around 2018, unified the lifecycle: scenarios in `molecule/<name>/`, a driver that creates instances (Docker, Podman, Vagrant, cloud APIs), a converge step that runs a playbook, an idempotence step that runs it again and fails if anything changes, and a verify step. Molecule 3 (2020) made large breaking changes, such as moving linting out and deleting the inline YAML-lint integration. Molecule 5 and 6 rebuilt the driver model: Docker, Podman, Vagrant and cloud drivers moved to a separate community plugin repository, the former delegated driver was renamed default, and the default verifier became Ansible itself rather than Testinfra [web: docs.ansible.com]. The calendar-versioned releases that followed track the supported ansible-core versions (only the latest two major versions are supported, according to the project documentation).

Alternatives have had a mixed record. Test Kitchen has faded for Ansible users because Molecule integrates natively; InSpec and Goss are used where the same assertions should validate systems built by different tools; `ansible-test` is the framework for collections and runs sanity, unit and integration tests, but it targets module development, not role behaviour. Many teams have only a CI job that runs `ansible-playbook --syntax-check`, which catches little. The lesson that emerged: a cheap static layer on every commit, a slower disposable-instance layer on every merge request, and a real-environment layer (check mode against staging, canary hosts) before production.

## Current state

### ansible-lint

`ansible-lint` takes paths or auto-discovers content in the working tree. It parses YAML with positions, applies each enabled rule and prints violations with a rule id and a short explanation, for example `fqcn[action-core]` (use the fully qualified module name), `name[missing]` (unnamed task), `yaml[truthy]` (use `true`, not `yes`), `no-changed-when` (a `command` or `shell` task with no `changed_when`), `command-instead-of-module`, `package-latest`, `risky-file-permissions`, `no-handler`, `var-naming[no-role-prefix]` (variables in a role should start with the role name), `jinja[spacing]` and `schema[...]` rules that validate files against JSON schemas. The tool exits non-zero when violations remain, which makes it usable as a gate.

Rules are grouped in profiles, each extending the previous: `min` (the content can be loaded), `basic` (common coding problems and formatting), `moderate` (readability and maintainability), `safety` (avoiding unreliable or risky patterns such as moving versions and unsafe shell pipes), `shared` (content intended for publication on Galaxy or Hub) and `production` (what is required for certified content) [web: docs.ansible.com]. A team picks one with `--profile` or a `profile:` key in `.ansible-lint`, and raises it as the codebase improves. The configuration file also supports `skip_list`, `warn_list` for violations reported as warnings, `enable_list` for opt-in rules, `exclude_paths`, `offline: true` for air-gapped runs, and `sarif_file`. The documentation recommends a `.ansible-lint-ignore` file over skip lists because ignored items remain visible. `ansible-lint --fix` rewrites what can be transformed safely, such as FQCNs, truthy values and key order, and it reformats YAML, so it should be run on a clean working tree and reviewed as a diff.

Typical integration places it in three spots: a pre-commit hook for fast feedback, a CI job that fails the merge request, and an editor integration through the Ansible language server. A good practice is to adopt the tool on a legacy repository by recording the current violations as ignored entries and forbidding new ones, then burning the ignore list down.

### Molecule

A Molecule project lays out `molecule/<scenario>/` inside a role or collection, each with `molecule.yml` (the configuration), `converge.yml` (the playbook that applies the content), `verify.yml` (assertions) and, optionally, `create.yml`, `destroy.yml`, `prepare.yml` and `cleanup.yml`. The `molecule.yml` names a driver, the platforms (instances, with groups for the generated inventory), the provisioner (always Ansible), a verifier and the sequences. The documented test sequence runs dependency resolution, cleanup, destroy, syntax check, create, prepare, converge, idempotence, side effect, verify, cleanup and destroy [web: docs.ansible.com]. The `molecule` command exposes each step: `molecule create`, `converge`, `idempotence`, `verify`, `login` (shell into an instance), `destroy`, `test` (the whole sequence) and `list`, and `molecule init scenario` makes a skeleton.

The driver model has two modes. With the default driver, Molecule does not create anything; the scenario supplies `create.yml` and `destroy.yml` playbooks, which can launch containers, virtual machines or cloud instances and write instance data to the state file. With the plugin drivers installed from the molecule-plugins package, a platform entry such as `image: quay.io/...` is enough and Molecule creates a Docker or Podman container, with options for privileged mode, systemd as PID 1 and mounted volumes, which are necessary for roles that manage services. A very light alternative is to use `ansible_connection: local` against the test runner itself in a throwaway container or VM, which runs without any driver at all.

The verify step is an ordinary Ansible playbook that gathers facts or runs `package_facts`, `service_facts`, `stat` and `command` tasks and asserts on results with `ansible.builtin.assert`. Idempotence is a first-class check in the sequence: Molecule runs converge a second time and fails if the callback reports any changed task, which is the cheapest way to enforce LNX-305-T07 as an everyday habit. A matrix of platforms (for example Rocky Linux 9, AlmaLinux 10, Debian 12 and Ubuntu 24.04) is declared as several platform entries or as GitHub Actions matrix jobs that pass an environment variable into `molecule.yml` through Jinja or `${VAR}` interpolation.

### Putting the layers together

A realistic pipeline for a role runs yamllint and ansible-lint at commit time, `molecule test` for the default scenario on every merge request on a container matrix, a second scenario with a full virtual machine for roles that touch the kernel, bootloader, SELinux enforcement or firewall rules that a container cannot show, and, outside Molecule, a scheduled job that runs the role in check mode against a staging inventory. For collections, `ansible-test sanity` and `units` are added. Linux System Roles uses a matrix of this kind against many releases (LNX-305-T05), with tests that run the role, verify, run it again for idempotence and then clean up.

## Assessment: the good, the bad and the ugly

The good: both tools are cheap to adopt, they speak Ansible natively and they surface real defects early. ansible-lint teaches idioms through its messages and makes review about substance, because style is automated. Molecule's sequence builds an evidence habit: nobody can claim a role is idempotent without showing the second run. Test scenarios double as executable documentation of supported platforms.

The bad: container tests are not systems. A container cannot test kernel parameters, services that need a full init, firewalls, SELinux in enforcing mode, mounts or network interfaces without privileged options, and those options change what is being tested. Tests that pass on a container may fail on the real machine. The test time grows with the platform matrix, and a slow suite is soon skipped. ansible-lint's rules reflect opinions, so on a legacy repository the first run can produce thousands of violations; teams that respond with a blanket skip list lose the benefit. Version churn is real: Molecule's driver changes in recent major versions broke many existing scenario files, and the lint profile composition changes between releases, which is why projects pin both tools.

The ugly: tests that pass vacuously. A verify playbook that checks only that a package is installed proves little, and a converge that uses `ignore_errors` or `failed_when: false` hides a real failure. Idempotence can be satisfied by wrapping non-idempotent commands in `changed_when: false`, which silences the check and the truth together. External dependencies (package repositories, container registries, time and DNS) make tests flaky, and a flaky suite trains people to rerun until green. Secrets for tests, such as cloud credentials for a cloud driver, introduce the problems of LNX-305-T04, and cloud instances created by a failed run can be left behind and billed.

## Applications beyond this domain

The same layering is general infrastructure testing practice. Static analysis for Dockerfiles (hadolint), Kubernetes manifests (kube-linter, kubeconform), Terraform (tflint, checkov) and shell (shellcheck) plays the role of ansible-lint, and profile or severity tiers appear in most of them. Disposable-instance testing appears as Terratest for Terraform, `kind` clusters for Kubernetes operators, Testcontainers for services and Packer plus InSpec for images (LNX-306-T04). The pattern of running the same change twice and requiring no diff on the second run is the same as the plan-must-be-empty check after apply in Terraform and the no-op reconcile in Kubernetes controllers; it is the central idea of declarative systems. Security-focused uses include policy-as-code checks of the kind ComplianceAsCode and OpenSCAP provide, and CI gates on SARIF reports in code scanning dashboards.

## Examples

A minimal static gate is a repository with a `.ansible-lint` containing `profile: safety` and a `.pre-commit-config.yaml` using the ansible-lint hook; the CI step is a single command `ansible-lint` that fails the build on any finding. A first run on an old playbook might report that `yum` should be `ansible.builtin.dnf`, that three tasks lack names, that a `shell` task piping `curl` into `bash` is risky and that a handler is invoked by a `command` result check instead of `notify`. Each is a real defect class: the first because short names are ambiguous, the second because unnamed tasks make logs unreadable, the third because pipes hide failures, the fourth because it reimplements the handler mechanism poorly.

A role test: `molecule/default/molecule.yml` declares a `default` driver (or the Podman plugin) with platforms for Rocky 9 and Debian 12 containers running systemd; `converge.yml` applies the role with `chrony_servers: [ntp1.example.org]`; `verify.yml` asserts that the package is present, the service is enabled and the rendered configuration contains the server line. `molecule test` reports `Idempotence completed successfully` when the second converge shows zero changes. A scenario that uses `ansible_connection: local` against the runner (a throwaway container) is the form used in the lab for this topic.

A failing example: a role task `ansible.builtin.command: useradd svc` with no `creates` and no `changed_when`. ansible-lint flags `no-changed-when` and `command-instead-of-module`; Molecule's idempotence step then fails because the second run exits with an error (the user exists) or, if guarded with `|| true`, reports a change every time. The repair is `ansible.builtin.user` with `state: present`, after which both tools are silent. A second failing case: a test passes in CI on containers but the role breaks on a real host because it writes `/etc/sysctl.d/` and the container ignores sysctl. The remedy is a second, VM-based scenario for that behaviour and a clear label of what the container scenario does not prove.

## Related problems and ideas

Property and policy testing approaches go beyond examples: instead of one converge-and-verify path, generate input variable combinations and assert invariants (for example that the second run is always a no-op). Conformance and compliance scanning complement testing by checking the live system against a benchmark (OpenSCAP, the ENT pathway). Mutation testing for infrastructure code, where a tool changes a task and checks that the tests notice, is still mostly an idea. Drift detection (LNX-306-T09) takes the test idea into production by running check mode on a schedule. Another neighbouring problem is data validation: `meta/argument_specs.yml` for roles (LNX-305-T03) and JSON schema checks for inventory data move errors from run time to load time, in the way types do in other languages. The decision between container and VM tests belongs to the same family as the choice of lab environments elsewhere in this curriculum (LNX-203 for scripting tests and LNX-312 for firewall rule tests offer comparable patterns).

## Active research

Work on the tools is active in three places. In ansible-lint, current development covers more rules for the 2.19 templating model, support for newer metadata schemas, better inline fix coverage and speed through caching, along with the language server for editors. In Molecule, the project has been simplifying around the ansible-native model, moving drivers into a plugin repository maintained by the community and tracking the two most recent ansible-core releases; maintainers' own comments in issue discussions show that how to treat external drivers is still debated [web: github.com]. In academic work, researchers analyse defects in Ansible and Puppet repositories and propose detectors for smells such as hard-coded secrets, suspicious comments and missing error handling; machine-learning-based generation of playbooks raises the open question of how to test generated code, with static analysis as a first filter (to verify specific recent papers).

## Future direction

Expect the static layer to take on more of the verification work, as typed variables, argument specs and the origin-tracked templating of ansible-core 2.19 give linters better information. Expect Molecule to stay a thin orchestration layer around plain playbooks, with environments moving toward ephemeral virtual machines and containers started by the CI system itself rather than by a driver. Watch the version support policy, since tools that support only two ansible-core versions force regular upgrades. A pragmatic plan for a team is to pin both tools, adopt a profile and raise it each quarter, require a Molecule scenario for every shared role, record what each scenario does and does not prove, and keep a path to test on a real virtual machine for roles that touch hardware-adjacent features.
