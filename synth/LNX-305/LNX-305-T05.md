# RHEL System Roles: a supported automation interface for the operating system

## Define the problem

Every site that runs Ansible against Linux ends up writing the same roles: time synchronisation, firewall rules, SELinux mode and booleans, network connections, storage layout, SSH daemon policy, log forwarding. Each team writes them slightly differently, bakes in assumptions about one release, and breaks when the next release changes a default, replaces a daemon (ntpd by chrony, network scripts by NetworkManager, iptables by nftables) or renames a package. The cost is not the first version but the maintenance across major versions and the knowledge that must be re-learned each time.

The problem RHEL System Roles solve is to supply, from the vendor, a tested set of roles with one stable variable interface for common operating system subsystems, so that a playbook written for one release keeps meaning the same thing on the next, and so that administrators describe what they want (an NTP server list, a firewall port, a volume layout) rather than how each release implements it. This slice covers what the roles are, how they are installed and called on RHEL 8 to 10 and compatible systems, the conventions that all roles share, and the limits. The mechanics of roles, collections and execution environments are in LNX-305-T03, and the variable and inventory side in LNX-305-T01.

## History and approaches

Before vendor roles, three kinds of sharing existed. Community Galaxy roles were free but of mixed quality and rarely tested across a full range of operating system releases. Vendor documentation gave command recipes, which administrators converted to playbooks by hand. Large organisations built internal baselines, often as a single huge role per host type with embedded `when` conditions on the distribution and version, which tended to rot as support for old releases was left in place.

The Linux System Roles project began around 2016 as a Fedora and Red Hat effort to write upstream roles for the subsystems that every Linux site configures, with a deliberate goal of one interface across releases. The upstream repositories live under the `linux-system-roles` organisation on GitHub, with each role also published on Galaxy and, later, bundled in the `fedora.linux_system_roles` collection; the site lists dozens of roles [web: linux-system-roles.github.io]. Red Hat packaged the stable subset as `rhel-system-roles` for RHEL 7 and 8 and supported it for subscribers, and as the `redhat.rhel_system_roles` collection for use with Ansible Automation Platform. Early on, roles were installed to `/usr/share/ansible/roles` under names like `rhel-system-roles.timesync`; later releases added the collection layout under `/usr/share/ansible/collections/ansible_collections/redhat/rhel_system_roles` [src: rhel-10-docs 270dee473d43738d].

The record has both successes and compromises. The `network` role first offered two providers (initscripts and NetworkManager) to bridge RHEL 7 and 8, which let one playbook span both but doubled the testing and made some options provider-specific; with RHEL 9 and 10 abandoning legacy network scripts, the NetworkManager path became the only supported one and nmstate-based features were added. The `storage` role had to cope with the danger of automating destructive operations; it introduced a safe mode that refuses to remove or reformat existing data unless the caller turns safety off explicitly. The `selinux` and `firewall` roles succeeded because their underlying tools already had declarative state. Roles for complex stateful systems (for example the `ha_cluster` role and database roles) remain more version-sensitive. The lesson that shaped the project is that an interface is worth the effort only when the role is tested continuously against every supported release and every provider, which is why upstream CI runs each role on a matrix of Fedora, CentOS Stream, RHEL and derivatives.

## Current state

### Contents and delivery

The set varies by release but includes roles for `selinux`, `timesync`, `firewall`, `network`, `storage`, `sshd` and `ssh`, `logging`, `metrics`, `kdump`, `certificate`, `crypto_policies`, `podman`, `cockpit`, `ha_cluster`, `postfix`, `systemd`, `journald`, `kernel_settings`, `nbde_client` and `nbde_server`, `tlog`, `vpn`, `ad_integration`, `rhc` (register to Red Hat services) and others [web: linux-system-roles.github.io]. On a RHEL control node the packages come from the AppStream repository: `dnf install rhel-system-roles` installs the collection and its documentation; documentation and example playbooks are installed under `/usr/share/doc/rhel-system-roles/<role>/`. On a managed node nothing is installed except what the role itself installs (for example `chrony` or `firewalld`); Python must be present, and an account with `sudo` rights is used by Ansible. The control node does not have to run RHEL; a Fedora or upstream installation of the collection also works [src: rhel-10-docs 270dee473d43738d].

### Conventions common to all roles

Every role follows a few conventions that make learning one role teach most of the others. All public variables start with the role name, such as `timesync_ntp_servers`, `selinux_state`, `selinux_booleans`, `firewall`, `storage_pools`, `network_connections`, `sshd_config`. Variables that begin with two underscores and the role name are internal and must not be set by callers. Complex settings are lists of dictionaries, each describing one object, so a playbook is a data description. Roles read distribution-specific values from `vars/` files chosen by distribution and version, and they perform the right action for the platform. Most roles let an entry say `state: absent` to remove an object; some also take a flag that makes the role replace the existing configuration instead of merging with it (to verify per role).

A playbook that sets the time servers is typically:

```yaml
- name: Time sync
  hosts: all
  vars:
    timesync_ntp_servers:
      - hostname: time.example.org
        iburst: true
  roles:
    - redhat.rhel_system_roles.timesync
```

The `timesync` role chooses between chronyd and, where still supported, ntpd, writes the configuration file and restarts the service when it changed [src: rhel-10-docs 3f4827b6c781432b]. The `selinux` role takes `selinux_state` (`enforcing`, `permissive` or `disabled`), `selinux_policy`, lists for booleans, file contexts, ports and logins, and offers `selinux_restore_dirs`. The `firewall` role takes a list of dictionaries with keys like `service`, `port`, `zone`, `state`, `permanent` and `runtime`; it warns about using `firewall` and direct firewall-cmd calls together. The `storage` role takes pools and volumes with disks, filesystem type, mount point, encryption and size, and the example documents in the guide show LUKS-encrypted volumes and shared LVM [src: rhel-10-docs e401f4524be92e47].

### Behaviour at run time

The roles are written to be idempotent and to support check mode where the underlying modules do; a second run should report no change (LNX-305-T07). A role that reboots or can disconnect the host, such as `network` changing the primary connection or `selinux` changing from disabled to enforcing, documents a reboot flag or a `selinux_reboot_required` fact that the playbook must act on with a reboot task. Roles can run against image mode (rpm-ostree) systems in two phases: packages are installed at image build time, and the role later only verifies them, with a helper script in each role listing the packages to bake in [src: rhel-10-docs 04b30e2fa4c09a6c].

### Variable layering with the roles

Because the roles are plain Ansible roles, the precedence ladder applies (LNX-305-T01): the roles' own defaults are the lowest rank, so group and host variables, play vars and `-e` can all override them. The recommended practice is to define the role's input variables in `group_vars` by function, and keep the playbook thin. Vault-protected values for roles that take credentials (for example `rhc` or `certificate`) follow LNX-305-T04.

## Assessment: the good, the bad and the ugly

The good: a single, vendor-supported, regularly tested interface for the commonest tasks; documentation and examples shipped with the package; a consistent naming scheme; compatibility across releases and with the CentOS Stream and Fedora upstream, so a team can prototype on free systems. The roles encode operational knowledge, such as which service must be restarted after a particular change or how to avoid locking oneself out, that would otherwise live in a senior administrator's head.

The bad: the roles are opinionated, and the interface is a subset. A feature that the role does not expose requires either a pull request upstream, a separate task after the role, or giving up the role for that subsystem. The generality makes some roles heavy; running `network` for one connection loads a lot of logic. Variable names are long, and nested lists can be awkward to override in a group hierarchy, since the replacement of a list in a more specific group replaces the whole list (LNX-305-T01). Upgrades of the `rhel-system-roles` package may change defaults, which is why release notes matter. And support applies to running the roles as shipped, not to local modifications.

The ugly: destructive operations and lockout risks. Applying a wrong storage definition on a host with data can destroy it unless safe mode is left on, and the one time a team turns it off globally to fix a failing play is the time the mistake happens. A `firewall` or `network` change that removes SSH access cuts the Ansible connection and leaves the host unreachable. Another awkward area is mixed management: if an administrator edits `/etc/chrony.conf` by hand on a host that the role manages, the next run overwrites the change, and if two roles claim the same file they fight. A final difficulty is expectation mismatch about scope: the roles configure the operating system, not application stacks, and they do not replace compliance tooling such as OpenSCAP remediation, though the two overlap (see the compliance content under the ENT pathway).

## Applications beyond this domain

The idea of a vendor-owned, stable, data-driven interface to operating system configuration appears elsewhere: Kubernetes operators expose a custom resource per subsystem and reconcile it; Windows has DSC resources and Group Policy; Puppet's supported modules and Chef's cookbooks from vendors fill the same role in other ecosystems; cloud providers publish baseline configurations for images. Standards bodies and compliance catalogues turn requirements into machine-readable form, which is the same move, and an automation role that sets chrony servers or SELinux mode is often the implementation of a control from a security guide [src: compliance-as-code c61368f371b3203a]. For the design lesson, the roles show how to publish an interface for a changing implementation: keep the data model stable, hide the provider, test the matrix, and document what you will not do. The same principle is the basis of `cloud-init` modules (LNX-306-T03).

## Examples

A baseline playbook for a new fleet applies four roles in order: `redhat.rhel_system_roles.timesync` with the site's NTP servers, `selinux` with `selinux_state: enforcing`, `firewall` with `ssh`, `https` and a custom port, and `sshd` with a hardened `sshd_config` dictionary. Host-specific changes live in `host_vars`. Running with `--check --diff` first shows which files would change; the second real run reports zero changes.

A storage example from the vendor guide creates a LUKS-encrypted volume by providing the disk, mount point, filesystem and an encryption passphrase through a vault-protected variable, then verifies the layout with a `command` task that runs `lsblk`; the document stresses that with the safe mode on, the role refuses to touch an existing filesystem [src: rhel-10-docs e401f4524be92e47].

A failing example: an operator adds `firewall: [{port: 8443/tcp, state: enabled}]` and forgets `permanent: true`. The port opens at runtime and closes at the next reload or reboot, and the failure appears days later. The role documents the `runtime` and `permanent` keys, but the omission is silent. A second failing example involves the `network` role changing the address of the interface Ansible is connected through: the play hangs, the connection drops, and the host stays on the new address. The advice is to test on a console-attached host, use a second management interface, and apply `network_connections` changes with a timeout and rollback approach if supported (to verify the options available in the installed version).

## Related problems and ideas

Compliance automation is the neighbouring problem. OpenSCAP and the ComplianceAsCode project generate Ansible remediation playbooks from security profiles, with per-rule tasks for the same subsystems that system roles manage; the two can conflict if both write the same setting, so teams choose one authority per setting. Another neighbour is the choice between roles and image-based configuration: bake time settings into the image (LNX-306-T04) and keep roles for what must vary at run time. The `rhc` role and the register-to-subscription flow link to repository management in LNX-104-T03.

Opposing views suggest that vendor roles add a layer to learn: administrators who know `nmcli` or `firewall-cmd` may find a thin custom role more transparent. The counter is the compatibility burden, which a team of any size feels in the second year. Emerging ideas include roles described by schemas so that tools can generate forms and validate input, and a "drift report" mode that compares the interface's data with the running system without changing it (LNX-306-T09 covers drift detection).

## Active research

The upstream project continues to add roles and to modernise existing ones: expanding nmstate use in the network role, supporting image mode for more roles, adding tests against newer distribution releases and handling the ansible-core 2.19 templating changes in all roles [web: linux-system-roles.github.io]. Questions under discussion on the project's channels include how to describe reboot requirements uniformly, how to expose provider-specific options without breaking the common interface, and how to give a role a safe dry run when the underlying tool lacks check mode (to verify the current status of each). On the research side, work on infrastructure code quality uses system roles as a large corpus of well-maintained roles with continuous testing.

## Future direction

For RHEL 10 and the AAP 2.6 lifecycle, expect the collection to remain the primary form, with image mode and pipelines that combine image build and run-time role application. Watch the release notes of each minor release for new roles and for changed defaults, and the upstream repositories for the next features before they reach the vendor package, typically within one or two minor releases. Practitioners should learn the shared conventions once, read the example playbooks installed with the package, test every change on a disposable host first, and treat the roles as the default for any subsystem they cover, writing custom code only for the gaps.
