# AWX and the automation controller: running Ansible as a shared service

## Define the problem

The command line is enough for one administrator. It stops being enough when a team shares automation. Who is allowed to run which playbook against which hosts? Where do credentials live, so that nobody has to hold the root SSH key on a laptop? Which runs happened last week, with what output, and who started them? How does a nightly patch job run without someone's terminal? How does a help-desk colleague restart a service through a button, without being given a shell? How do jobs scale beyond the forks of one machine, and reach networks that the central site cannot see directly?

A job-scheduling and access-control layer around Ansible answers these questions. In the Red Hat product it is the automation controller, part of Ansible Automation Platform (AAP); its open source upstream is AWX. This topic is at depth 2: the aim is to understand the model, the pieces and the operational consequences, well enough to read a controller's configuration and to know when a controller is warranted. The content that a controller runs is covered in LNX-305-T01 to T07, and the container images it uses to execute jobs are explained in LNX-305-T03.

## History and approaches

Before dedicated tools, teams ran playbooks from a shared bastion host under a service account, or from a CI system such as Jenkins. Both worked and both leaked: the bastion accumulated keys and local state, and Jenkins jobs held credentials as plain job parameters or plugins and gave little understanding of inventories or limits. Rundeck and, later, Semaphore targeted operations runbooks directly, with their own models of jobs and nodes.

Ansible's own answer was Ansible Tower, a commercial web service released in 2013 by AnsibleWorks (renamed Ansible, Inc.) and, after Red Hat acquired the company in 2015, packaged into the Red Hat portfolio. Red Hat open-sourced the upstream code as AWX in 2017. The early design ran each job in a Python virtual environment on the Tower node, with a Celery-based task queue, PostgreSQL and a Redis or RabbitMQ message bus. The weaknesses were scaling and isolation: virtual environments could not carry system libraries, a heavy job could starve the web tier, and reaching remote networks required a separate isolated-node mechanism.

The architecture was then reworked. Execution environments (container images, covered in LNX-305-T03) replaced virtualenvs; Receptor, an overlay network mesh, let the control plane dispatch work to execution nodes and hop nodes in remote sites; and containers groups allowed jobs to run as pods in a Kubernetes cluster. Automation controller 4.0 inside AAP 2 (2021) made this the platform architecture. AAP 2.4 added the event-driven Ansible controller, and AAP 2.5 (late 2024) introduced a platform gateway and a unified user interface, so authentication and authorisation are managed once for several components; AAP 2.6 followed in 2025 with monthly patch releases [web: docs.redhat.com]. The AWX Operator, built using the Kubernetes operator pattern (a custom controller that reconciles a declared resource into running components), became the way to deploy AWX on Kubernetes [src: kubernetes-docs 8cc33ceaf6e39967].

The community project has had a mixed record. In July 2024 the AWX repository announced that releases were paused during a large refactoring towards a pluggable, service-oriented design. The last tagged release remained 24.6.1 and the `awx.awx` collection had also not been released for more than a year in autumn 2025, which concerned users who depended on a regular upstream; maintainers said the modernisation was ongoing, with no schedule [web: forum.ansible.com]. Alternatives that grew in the gap include CIQ's Ascender, a downstream fork, and Semaphore UI for smaller teams. The lesson is practical: an upstream project is not a support contract, and a team that needs a stable, patched controller either buys the supported product or accepts the work of tracking an unreleased branch.

## Current state

### Objects and how they connect

The controller's data model is the best part to know. An **organization** owns everything else and is the unit of multi-tenancy. **Users** belong to **teams**; **role-based access control** assigns roles (admin, use, update, execute, read and others) per object, so a team may execute a job template without being able to read the credential it uses. A **credential** is a typed secret (machine SSH key, cloud API key, vault password, source control token, container registry login); values are stored encrypted and, after being saved, can be used by jobs but not read back by users. An **inventory** is a set of hosts and groups, either entered by hand or synchronised from an **inventory source** (a cloud, a VMware instance or a plugin) on a schedule (LNX-305-T01 describes the data model that these represent). A **project** is a source control repository (or a local path) holding playbooks and roles, updated before each run if configured. An **execution environment** is the container image used for a job. A **job template** ties together project, playbook, inventory, credentials, execution environment, limit, verbosity, tags, forks and options such as check mode; launching it creates a **job** with a log of events. A **workflow job template** links job templates (and approval nodes and inventory syncs) into a graph with success, failure and always edges. **Schedules**, **notifications** (email, Slack, webhooks) and **surveys** (forms that turn user input into extra variables) complete the set.

### Execution architecture

The control plane receives the launch request through the web UI or REST API (`/api/v2/`), writes the job to PostgreSQL and schedules it onto an **instance group**. A worker that is an execution node starts the job through ansible-runner inside a container created from the execution environment image; events stream back as JSON through Receptor and are stored and shown live. **Hop nodes** relay between networks; **container groups** create a pod for each job in a Kubernetes cluster. Capacity is expressed per instance as a number of forks or as a percentage of memory and CPU, and jobs queue when capacity is exhausted. Facts can be cached per host, and the platform can record a job's host summary (how many changed, failed) for reporting.

### Interfaces and automation of the controller itself

The controller is scriptable. The `awx` command-line client, the `awx.awx` or `ansible.controller` Ansible collections, and the REST API all create the same objects, so a platform team can store the controller's configuration in Git and apply it with playbooks (configuration as code). Webhooks from GitHub or GitLab can launch a template on a push, and a **provisioning callback** URL lets a newly booted host ask the controller to configure it, a pattern that cloud-init can start (LNX-306-T03). Logging aggregators export job events to external systems.

### What remains outside

A controller does not replace the discipline in the earlier topics. Its credential store is not a general secrets manager, though it can integrate with HashiCorp Vault, CyberArk and cloud services through credential lookup plugins (LNX-305-T04 discusses the trade-offs). Check mode and diff are options on the template, and results from a check run are only as good as the modules (LNX-305-T07). The execution environment must contain the collections that a project needs, or the job fails.

## Assessment: the good, the bad and the ugly

The good: central audit, one place for credentials, fine-grained access, scheduling and approval workflows, and a standard API. It lets people who are not Ansible users run vetted automation, and it keeps long jobs off laptops. Isolation through containers makes jobs reproducible; the mesh makes remote sites reachable without opening inbound ports from the centre.

The bad: the controller is a stateful service with a database, a message path and certificates, so it needs backup, monitoring, upgrades and capacity planning of its own. Upgrades across major platform versions have historically been multi-step. Debugging moves from a terminal to logs, events and container output, and failures in the container runtime, the registry or the mesh are new categories of incident. Role models can be clumsy, and objects accumulate. Licensing or subscription cost is a factor for the supported product.

The ugly: the temptation to put every manual task behind a button, creating a pile of job templates nobody owns; to store secrets in survey answers; to give broad `use` permission on a powerful credential, so a template that runs arbitrary playbooks from a project equals root on all inventory hosts for anyone who can edit the project. The controller is itself a high-value target: whoever controls it holds credentials for the fleet, so it belongs in the highest tier of an administrative model, patched promptly and with its own access carefully limited, in the spirit of tiered administration guidance [src: ms-learn-adds 5957580d19befcd1]. The upstream uncertainty described above is an operational risk for anyone building on AWX alone.

## Applications beyond this domain

The same shape is found wherever automation is centralised. CI and CD systems (GitLab, Jenkins, GitHub Actions with self-hosted runners) combine projects, credentials, schedules and runners; Rundeck and Semaphore are close cousins. Terraform Cloud and Spacelift offer inventories of workspaces, state and policy. Kubernetes controllers and operators run reconciliation loops in the cluster [src: kubernetes-docs 2b71bb64a0a5037d]. The mesh of control, execution and hop nodes mirrors the agent and relay design of monitoring systems such as Prometheus federation or Zabbix proxies. Patch-management consoles such as Red Hat Satellite and Foreman use Ansible roles as one of their remote execution back ends, and identity services such as IdM use Ansible modules for their own deployment [src: rhel-10-docs 30ca60972b1cd006]. What transfers is the pairing of a declarative job definition with a controlled execution plane.

## Examples

A platform team creates an organization per business unit. Each has a team of operators with `execute` on a "Patch Linux" job template that uses a project from Git, the group of managed hosts from a cloud inventory source, a machine credential for the `automation` user, and the standard execution environment. A survey asks for a limit pattern and a reboot flag. A schedule runs the template every Sunday at night in check mode, and a notification posts the diff summary to the team channel.

A second example is a workflow: sync inventory, run a pre-flight job, run `serial: 10%` rolling update, then an approval node waits for a person to confirm before the second site proceeds. The failure edge triggers a rollback job and a notification.

A failing example: a job template uses an execution environment that lacks the `kubernetes.core` collection; the job starts, the first task fails with a module-not-found error, and the output shows only that. The fix is to rebuild the image with the collection (LNX-305-T03), push it and update the template. Another failing example is the credential pitfall: an operator pastes a private key with Windows line endings into the credential field and every job fails authentication until it is corrected. A third: a project update fails because the Git token expired, and since the controller runs the project sync before each job, every template using that project fails at once.

## Related problems and ideas

Event-driven automation is the active neighbour: instead of a person or schedule launching a job, rules (rulebooks) match events from monitoring, webhooks or message queues and trigger playbooks; AAP includes an event-driven controller for this. GitOps tooling for Kubernetes (Argo CD, Flux) reconciles continuously from Git, a different model that suits declared cluster state. For provisioning at the bare metal edge, Foreman and MAAS (LNX-306-T06) can call Ansible. A competing view is that a controller is unnecessary: run `ansible-pull` from cron on each host, or run `ansible-playbook` from CI runners with a secrets manager and short-lived credentials, and skip the extra service. The right choice depends on scale, audit needs, and how many non-experts must run jobs.

## Active research

Open questions centre on the platform's future shape. The AWX refactoring towards pluggable services, the status of the community project and its relation to the supported product, and the deployment model on Kubernetes through the AWX Operator are under discussion on the community forum (to verify the state of the modernisation effort, since announcements through 2026 were not checked in detail) [web: forum.ansible.com]. Technical research topics include scheduling jobs on mesh networks with intermittent links, secure delivery of credentials to execution containers, fair sharing of capacity between tenants, and using event streams and large language model assistants to propose automation, with human approval as the safety control.

## Future direction

Expect continued consolidation of AAP components behind a gateway with a shared identity model, more event-driven features, and monthly patch cadence for the supported product, according to its release notes. For the open source line, watch the AWX repository's status notice and the Ansible forum for the next release and for any announced replacement. For practitioners: decide early whether a controller is needed; if it is, treat it as production infrastructure with its own backups and access tiers, keep its configuration in code, and pin the execution environments it uses.
