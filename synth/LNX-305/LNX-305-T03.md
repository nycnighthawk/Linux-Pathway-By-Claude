# Packaging Ansible content: roles, collections and execution environments

## Define the problem

A single playbook scales to a few dozen tasks and then becomes a liability. The same web server setup appears in three playbooks with small differences. A bug fix has to be copied by hand. Nobody knows which variables a block of tasks expects. A colleague in another team has already written a good PostgreSQL configuration, but it is a pile of files in a wiki. Meanwhile the control node itself, the machine that runs Ansible, becomes a configuration problem: one project needs a particular ansible-core version and a cloud SDK, another needs an older Python library, and the laptop that works for one breaks the CI runner for the other.

Three mechanisms address those three levels. A role packages tasks, handlers, defaults, files and templates behind a variable interface so that one unit of function can be reused. A collection packages roles together with modules, plugins and playbooks, under a namespace, with a version and a distribution channel. An execution environment packages the control node itself, as a container image holding ansible-core, the collections and their Python and system dependencies. The gap filled is the one between writing automation and being able to share it, version it and run it identically in many places. This slice covers the directory structures and commands of roles and collections, the consumer-side installation and trust questions, and the container-based runtime; the controller that schedules execution environments is LNX-305-T08, and the ready-made roles from Red Hat are LNX-305-T05.

## History and approaches

Reuse arrived in Ansible early. Roles, introduced in 2012 and stabilised in version 1.2, defined a fixed directory convention so that a play could say `roles: [common, web]` and the engine would load the tasks, handlers, variables and templates from known locations. Ansible Galaxy, launched in 2013, was a community hub for those roles, and `ansible-galaxy install` fetched a role from a GitHub repository into a roles path. Quality was uneven. Many roles were abandoned, names collided between authors, and a role often bundled assumptions about one distribution. Because roles could only carry YAML, extensions (modules, filters, lookups) had to be placed in the playbook tree or in a role's `library` directory, which made them private to one repository.

The core repository itself became a bottleneck. By 2019, thousands of modules and plugins lived in the single Ansible repository, maintained by a small team, with release cadence tied to the whole. The answer, completed in Ansible 2.10 in 2020, was the collection: a versioned archive containing any kind of content, published under `namespace.name` and installable independently. The core was reduced to ansible-core with the `ansible.builtin` collection, and the larger community package called `ansible` became a curated bundle of core plus selected collections. Red Hat added a certified channel (Automation Hub) with supported content. Making collections work forced a long migration: every module reference acquired a namespace, redirects (`meta/runtime.yml`) kept old short names working, and the `collections:` keyword in a play, which searched a list of namespaces, was later discouraged in favour of fully qualified names [src: ansible-docs 66583861f86ae39e].

Execution environments came out of operations pain. Ansible Tower and early AWX ran playbooks inside Python virtual environments on the controller. Each project could select one, but the venvs were mutable, differed between nodes, could not carry system libraries, and made upgrades risky. In 2020 and 2021 the project introduced container images as the execution unit: `ansible-runner` standardised how a playbook is run in a directory with defined inputs and outputs, `ansible-builder` built images from a definition file, and `ansible-navigator` gave developers a way to run the same image on a laptop that the controller would run in production. Automation controller 4.x and Ansible Automation Platform 2 made them the only runtime model. The approach echoes the broader move from long-lived hosts to images (LNX-306-T04), and it solved the venv drift problem at the price of a container build step and image storage.

## Current state

### Roles

A role is a directory with defined subdirectories, each optional: `tasks/main.yml` (the work), `handlers/main.yml`, `defaults/main.yml` (the lowest-precedence variables, meant to be overridden), `vars/main.yml` (high-precedence, internal constants), `files/` and `templates/` (found automatically by `copy` and `template` tasks inside the role), `meta/main.yml` (author, platforms, dependencies) and `meta/argument_specs.yml` (a machine-readable declaration of the role's inputs), plus `library/`, `module_utils/` and `tests/` [src: ansible-docs dd92d2c71f3d4f55]. `ansible-galaxy role init name` creates a skeleton. A play loads roles through the `roles:` keyword (evaluated before the play's own tasks, statically), `import_role` (static, at parse time) or `include_role` (dynamic, at run time, so it can sit in a loop or under a condition) [src: ansible-docs 41dbeca510388ff5].

Design rules follow from the precedence list covered in LNX-305-T01. Put every tunable in `defaults/` so that inventory, play and command line can override it; reserve `vars/` for values the role author does not expect to change; prefix every variable with the role name (`nginx_worker_processes` rather than `workers`) to avoid collisions in the single flat variable namespace of a play; and document inputs in `argument_specs.yml`, which makes Ansible validate types and required values when the role starts. Role dependencies in `meta/main.yml` run before the role, but they are discouraged for anything but trivial cases, because they hide ordering and run each dependency once unless told otherwise. To handle different distributions, a common pattern loads `vars/{{ ansible_facts['os_family'] }}.yml` with `include_vars` and `with_first_found`, giving a single task list with a per-OS data file [src: ansible-docs c12c7a794c146f75].

### Collections

A collection has `galaxy.yml` (namespace, name, version, dependencies, licence), `plugins/` with subdirectories per plugin type (`modules`, `filter`, `lookup`, `inventory`, `module_utils` and others), `roles/`, `playbooks/`, `docs/`, `tests/` and `meta/runtime.yml`. `ansible-galaxy collection init namespace.name` creates it, `build` produces a tarball and `publish` uploads it. Consumers list dependencies in `requirements.yml`:

```yaml
collections:
  - name: ansible.posix
    version: ">=1.5.0,<2.0.0"
  - name: community.general
roles:
  - name: geerlingguy.nginx
    version: 3.2.0
```

and install them with `ansible-galaxy collection install -r requirements.yml` (add `-p collections/` to keep a project-local copy, which `ansible.cfg` finds through `collections_path`). Installed collections live under an `ansible_collections/<namespace>/<name>` tree. The FQCN form `ansible.posix.firewalld` selects one explicitly [src: rocky-docs bfb89d7b6f6bb2a3]. `ansible-doc -l` lists plugins and `ansible-doc namespace.name.module` shows the documentation of one, including examples. Galaxy servers can be several (public Galaxy, Automation Hub, a private pulp-based instance), listed in order in `ansible.cfg`.

The trust model deserves attention because collections run with the privileges of whoever invokes them. Pin versions, review diffs when upgrading, use a private mirror in restricted networks, and, where supported, verify detached signatures (`--keyring` and `--signature` options of `ansible-galaxy collection install`, with a configured GnuPG keyring). The community bundle sits on a roughly semiannual cadence matching ansible-core releases, and only the latest releases of a core are tested against it [web: docs.ansible.com].

### Execution environments

An execution environment (EE) is an OCI image containing ansible-core, `ansible-runner`, a set of collections and the Python packages and system RPMs those collections need. The definition is a YAML file read by `ansible-builder`, schema version 3 recommended: it names the base image, lists collection requirements (a `requirements.yml`), Python requirements and system packages (`bindep.txt`), and can inject build steps. `ansible-builder build --tag my-ee:1.0` writes a build context and calls Podman or Docker. Red Hat publishes minimal and supported base images through its registry, and the community keeps a creator image. At run time, the controller starts a container from the image, mounts the project and inventory, runs `ansible-playbook` inside and streams events out through Receptor and runner. Developers use `ansible-navigator run site.yml --eei my-ee:1.0 --mode stdout` to run the same image from a workstation, or `--ee false` to use the host's Python [web: redhat.com].

Because the image fixes versions of everything, an execution environment turns the control-node setup into a build artifact: it can be scanned for CVEs, signed, stored in a registry and promoted through environments in the same way as application images. EEs also isolate credentials, since only the variables passed in reach the container. Ordinary projects without a controller still benefit from a smaller step: a `requirements.yml` and a virtual environment pinned by hash give most of the repeatability.

## Assessment: the good, the bad and the ugly

The good: a role with documented inputs and a test suite is the unit of reuse that makes teams faster. Collections let the same release of a module reach users without a core release, and namespaces end name collisions. Execution environments make "works on my laptop" go away for the control node and give auditors an image digest to point at.

The bad: the flat variable namespace. A role cannot declare private variables; everything shares scope with the play, so role prefixes are a convention, not a boundary. Defaults versus vars is misunderstood often: authors place tunables in `vars/` and users then cannot override them. Collections multiplied the number of things to track: a playbook may depend on ten collections, each with its own release rhythm and its own deprecations. The documentation and error messages around legacy short names, redirects and the `collections:` keyword are a recurring source of confusion.

The ugly: dependency and supply-chain risk. Installing a collection executes arbitrary Python on the controller during later runs; a transitive dependency can change under a loose version range. Build reproducibility of EEs is also limited by base image tags that move, so digests must be pinned. EEs can be heavy (hundreds of megabytes to over a gigabyte), and a one-line change to a collection means a rebuild and a push. Roles from Galaxy of unknown maintenance have caused real breakage when abandoned; linting and a role's own CI (LNX-305-T06) help only if the role has them. Finally, an old role that still uses `include` or relies on pre-2.10 module names may need a rewrite for current ansible-core.

## Applications beyond this domain

Role-plus-collection-plus-image is a three-level packaging pattern that other ecosystems share. A role resembles a Python module or a Helm subchart: a unit with defaults and a values interface. A collection resembles a language package, such as a PyPI distribution or a Go module, with a manifest, semantic versions and a registry. An execution environment resembles a build container used for CI, which fixes the toolchain independently of the developer's machine; the same idea drives devcontainers and Nix shells. The consumer-side trust practices (pin, mirror, verify signatures) are the same as for container images and OS packages, as covered in LNX-104-T03 on repositories and keys. The NIST control family on configuration management asks organisations to restrict which software can execute and to maintain a baseline, and a pinned collection set plus a signed EE is one concrete way to meet that [src: nist-sp800-53 b7054da3146a0d06].

## Examples

A small, typical role is `chrony` with `defaults/main.yml` listing `chrony_servers` and `chrony_makestep`, a template of `chrony.conf`, a handler that restarts the daemon, and a per-OS variable file naming the package and service (`chrony` and `chronyd` on Red Hat, `chrony` on Debian). A playbook then reads `roles: [{role: chrony, chrony_servers: [ntp1.example.org]}]`, with the group-level data coming from the inventory. The Red Hat `timesync` system role does the same job with a richer interface (LNX-305-T05).

A collection example: a team wraps its internal modules, a filter plugin and three roles into `acme.platform` 1.4.0, publishes it to a private Galaxy server, and pins `acme.platform:~1.4` in every project's `requirements.yml`. When 1.5.0 changes a filter, the pin protects the other projects until each team has upgraded on its own schedule.

An EE example: an `execution-environment.yml` (version 3) starts from a Red Hat minimal base, adds a requirements file listing `amazon.aws`, `kubernetes.core` and `ansible.posix`, a Python requirements file with `boto3` and `kubernetes`, and a `bindep.txt` with a system library. `ansible-builder build` produces the image, `ansible-navigator` tests it locally, and the controller pulls the same tag.

A failing example: a role stores its listen address as `address` in `vars/main.yml`. Another role in the same play also reads a variable named `address`. The later role silently takes the first role's value, and because `vars/` outranks inventory data, an operator's group variable has no effect. After renaming to `chrony_bind_address` and moving it to `defaults/`, the inventory override works. The same collision happens when a play uses `include_vars` into an unprefixed name. A second failing case is the short-name trap: a playbook that calls `firewalld` without a namespace works on a workstation with an old community install and fails in the EE that only contains `ansible.posix`.

## Related problems and ideas

Roles versus plain includes is a choice about boundaries. For project-specific glue, `include_tasks` is enough; roles earn their cost when there is more than one consumer. Another related approach is the Linux System Roles project, where many roles share one test and CI scaffold (to verify the details) (LNX-305-T05). Puppet modules and Forge, Chef cookbooks and Supermarket, and Salt formulas solve the same sharing problem, with lessons in module-level versioning and in the risk of enormous public indexes.

Neighbouring ideas not yet mainstream include content signing for roles (collections already have it), software bills of materials for EEs, and a collection dependency resolver that treats conflicts more strictly. A different direction is composing content by data, not code: generate playbooks from a schema or an API description. For the container side, `podman` and build-time scanning are covered in the CN pathway; for repository trust and key handling see LNX-104-T03.

## Active research

Work in progress on the Ansible project includes improvements to the collection dependency resolver, to signature verification, and to a unified way to describe content metadata, with collections adopting stricter sanity tests and argument-spec validation for modules (to verify the current roadmap on the community forum). The ansible-builder project moved through version 3 of its definition format and is exploring leaner builds that avoid copying large layers; ansible-navigator is receiving continued development as the preferred developer front end [web: redhat.com]. Academic studies of ecosystem health look at abandoned roles, transitive dependency depth and vulnerable Python packages in EEs. Open questions are how to verify the provenance of a built image end to end, and how to keep EEs small without removing the packages that a collection may need on rare code paths.

## Future direction

Expect content to continue moving into collections, and the ansible-core team to keep trimming what ships in the core. EEs will likely become the default way to run Ansible anywhere above one laptop; dates in the Red Hat lifecycle for the platform decide the pace of change for supported content, so watch the platform release notes (AAP 2.6 has monthly patch updates at the time of writing). For practitioners: build the habit of pinning versions, of writing `argument_specs.yml`, of testing roles against several distributions (LNX-305-T06) and of treating the control node as a built, versioned artifact.
