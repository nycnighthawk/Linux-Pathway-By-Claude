# Managing Windows hosts from a Linux control node with Ansible

## Define the problem

Most enterprises that run Linux also run Windows, and the people who automate one are asked to automate the other. Windows Server hosts domain controllers, file shares, line-of-business applications and desktop fleets, and a Linux-based automation team wants to patch them, configure services, install software and join machines to the directory using the same inventory, playbooks and approval flow as the Linux estate. The barriers are real. Windows does not offer SSH by default, its administration model is based on PowerShell, the registry, services and a security system built around Kerberos and NTLM, and Ansible's normal approach of copying a Python module to the target and executing it does not apply, since the target has no Python.

The gap that this topic fills is the set of connection methods, authentication choices, modules and habits that make Windows a manageable target of an Ansible control node, and the places where it still behaves differently. The slice is a depth-2 survey: enough to set up a working connection, run the main modules, read the common errors and know where the risks lie. It builds on inventory (LNX-305-T01) and playbooks (LNX-305-T02); the Windows facet of the controller is covered in LNX-305-T08, and the Linux side of directory integration appears in the identity courses of the enterprise pathway.

## History and approaches

Windows first appeared as an Ansible target in version 1.7 (2014), using Windows Remote Management (WinRM) and PowerShell modules, and it has been developed continuously since. The design principle is the same as for Linux, adapted: the control node connects, sends a small PowerShell module wrapper and its arguments over the connection, runs it with the PowerShell engine on the target, and receives JSON back. Modules are therefore written in PowerShell (with C# helpers in `module_utils`), and their names carry a `win_` prefix: `win_copy`, `win_service`, `win_feature`, `win_regedit`, `win_user`, `win_updates`. When collections were introduced, the Windows modules moved into `ansible.windows`, with a wider set in `community.windows`, and Active Directory modules in the `microsoft.ad` collection, which also supplies a modern domain-join and domain-controller workflow.

The connection layer has had several generations. The original `winrm` connection plugin uses the pywinrm library and the WS-Management protocol on port 5985 (HTTP) or 5986 (HTTPS) with authentication choices of Basic, certificate, NTLM, Kerberos and CredSSP. The `psrp` plugin, using the pypsrp library, speaks the PowerShell Remoting Protocol and is generally faster and supports a negotiate method that tries Kerberos then falls back to NTLM. The SSH connection plugin has been usable with Windows since Ansible 2.8, with official support documented from 2.18, once Microsoft's OpenSSH server became part of Windows Server; it needs an `ansible_shell_type` of `powershell` or `cmd` [web: docs.ansible.com]. The approaches have different strengths: WinRM is native and has the broadest authentication matrix; SSH unifies the transport with Linux and simplifies firewall and key management; PSRP gives richer output and better performance.

Alternatives and predecessors give context. Microsoft's own tools are Group Policy (central policy for domain-joined machines), SCCM or Configuration Manager and Intune for endpoint management, and PowerShell Desired State Configuration (DSC), a declarative engine with resources and a local configuration manager. Chef and Puppet have Windows agents. Ansible's agentless model needs an administrator account and open management ports instead of an agent. It integrates with DSC through the `win_dsc` module, and the combination of the two is a typical partial success: DSC resources provide the idempotent logic, and Ansible provides the inventory, ordering and orchestration. The failures of the early period were security shortcuts, such as enabling Basic authentication over plain HTTP or disabling certificate validation to get started, which turned test setups into permanent exposure.

## Current state

### Preparing a Windows host

A Windows target needs PowerShell 3.0 or later and a recent .NET Framework (versions supported are listed in the documentation for each core release), plus a configured WinRM listener or OpenSSH server. The documentation provides a helper script (`ConfigureRemotingForAnsible.ps1`) that sets up a listener for lab use; in production the recommended setup is an HTTPS listener with a certificate issued by the organisation's CA, and a firewall rule limiting access to the control node. The account is a local or domain administrator, or a member of groups allowed to use remoting, and Windows UAC applies to network logons of local accounts [src: ansible-docs 47c4ee41b815c81a].

### Inventory and connection variables

Windows hosts are kept in a group, and the group variables select the connection. A common set is `ansible_connection: winrm` (or `psrp` or `ssh`), `ansible_port: 5986`, `ansible_winrm_transport: kerberos` (or `ntlm`, `credssp`, `certificate`), `ansible_user`, `ansible_password` (vaulted, LNX-305-T04), and `ansible_winrm_server_cert_validation: validate`. The controller needs the Python packages `pywinrm` or `pypsrp`, and for Kerberos the system packages for Kerberos libraries and a configured `krb5.conf`, with the realm resolved through DNS or configuration. Using Kerberos with a Windows domain account is the preferred method in domain environments, since passwords are not sent and the identity is the domain account. These dependencies make the control node's setup an obvious candidate for an execution environment (LNX-305-T03). Connection plugins differ in a few ways: the SSH plugin cannot obtain a Kerberos ticket from an explicit username and password, so the ticket must exist before the play [web: docs.ansible.com].

### Modules and idioms

The module set covers the usual areas: files and templates (`ansible.windows.win_copy`, `win_template`, `win_file`), packages (`win_package` for MSI and EXE with product ids, `chocolatey.chocolatey.win_chocolatey`), services and scheduled tasks, features and roles (`win_feature`, with `include_management_tools` as the common option), registry, firewall rules, users and groups, shares, updates (`win_updates` with category filters and reboot handling), reboots (`win_reboot`, which waits for the host to come back) and arbitrary scripts (`win_shell`, `win_command`, `win_powershell`). As with Linux, the script modules report changed unless told otherwise, so they need the same care as `command` (LNX-305-T07). Facts are collected by `ansible.windows.setup` and include the OS caption, version, and domain membership [src: ansible-docs 35ec56b4dab0816e]. Paths use backslashes, which collide with YAML escapes: single-quoted or block-scalar values avoid the problem, and forward slashes work in many modules. Templates are rendered on the control node as usual, and a line-ending setting matters for files that Windows tools read.

Privilege escalation uses `become_method: runas`, with a `become_user` such as `SYSTEM` or a named account, and is needed for tasks that require an interactive-like token, and the "double hop" problem appears when a task on one Windows host must reach a second host with the connecting user's credentials. Kerberos delegation or CredSSP can address it, with security costs, and `become` with explicit credentials is the safer answer [src: ansible-docs 311a8935415e84cc].

### Directory integration

Windows automation is often directory work. The `microsoft.ad` modules create users, groups and computer objects, turn a server into a directory controller, and enrol a host in the domain. The Linux counterpart is joining RHEL to Active Directory with SSSD, `realmd`, or an IdM trust, both covered in the vendor guides and automatable with system roles, notably the `ad_integration` role (LNX-305-T05) [src: rhel-10-docs 4a6f2d598858d917]. Microsoft's guidance on tiered administration and privileged access workstations explains why the controller's credentials must be handled with care [src: ms-learn-adds 5957580d19befcd1].

## Assessment: the good, the bad and the ugly

The good: one language, one inventory and one workflow for both platforms; agentless operation; a mature module set for the daily tasks of patching, features, services, files and registry; and an official, documented position on SSH as a transport that lets Windows join the same key-based model as Linux. For many teams the single biggest win is the reuse of the controller (LNX-305-T08) with job templates for both platforms.

The bad: execution is slow compared to Linux because each task starts a PowerShell process and transfers a module; large plays benefit from PSRP and from fewer, larger tasks. Authentication has many options and many ways to fail: the clock skew that breaks Kerberos, SPN and DNS mismatches, an HTTP listener that was never converted, a certificate chain that the controller does not trust, NTLM disabled by policy, local accounts hit by UAC filtering. The module set is smaller than for Linux in niche areas, and modules for Windows features can differ by edition and version. Check mode support is uneven.

The ugly: security. Basic authentication over HTTP, `server_cert_validation: ignore` and shared administrator passwords in inventory files are common in tutorials and sometimes persist in production, sending credentials in clear or inviting man-in-the-middle attacks. CredSSP forwards credentials and so makes a compromised target a source of reusable credentials. A controller that can administer all Windows hosts with a domain administrator account is a target for credential theft and a violation of tiering; accounts should be scoped to the tier of the hosts they administer. Antivirus and endpoint protection may block the PowerShell content that Ansible sends. Windows hosts cannot be assumed to reboot cleanly from tasks, and updates that need several reboot cycles need loops with a limit. The platform also has changes that outpace automation: for example, features retired in a new Windows Server release.

## Applications beyond this domain

The pattern here is cross-platform orchestration through a native remote protocol. Network device automation uses the same idea with `network_cli`, `netconf` and `httpapi` connections for appliances without Python. The distinction between agentless transports (SSH, WinRM, APIs) and agents is the same as in monitoring (SNMP versus agents) and in patch management. Credentials and trust follow the same rules as everywhere: prefer an identity-based protocol (Kerberos, SSH certificates) over passwords, validate server certificates, and place the automation identity in the lowest tier that works. The lessons on mixing a declarative resource engine (DSC) with an orchestrator are repeated in Kubernetes (operators and Helm) and in Puppet plus Bolt. Kubernetes itself has Windows nodes and Windows containers with their own constraints on features, a reminder that the platform differences extend beyond Ansible [src: kubernetes-docs 25e4f031aa97764d].

## Examples

A minimal inventory group: `windows` hosts with `ansible_connection: psrp`, `ansible_psrp_auth: negotiate`, a service account in the vault, and HTTPS on port 5986. A first test is `ansible windows -m ansible.windows.win_ping`, which checks the full path (connection, authentication, PowerShell execution) and returns `pong`. A second is `ansible windows -m ansible.windows.setup -a 'gather_subset=min'` to see the facts.

A typical play installs the IIS role with `win_feature` (name `Web-Server`, `include_management_tools: true`), copies a site with `win_copy`, opens a firewall rule with `community.windows.win_firewall_rule`, and starts a service with `win_service`. A patch play uses `ansible.windows.win_updates` with `category_names` set to security updates, `reboot: true` and a retry loop around it. A directory play uses `microsoft.ad.user` to create accounts from a data file in the repository.

A failing example: a play works from the administrator's laptop and fails from the controller with a Kerberos error stating that the realm cannot be found. The causes found, in order, are a missing `krb5.conf` in the execution environment image, a DNS resolver that does not answer the SRV records for the domain, and a clock more than five minutes off. The fixes are to bake the Kerberos configuration into the image (LNX-305-T03), configure the resolver, and sync time with the domain (LNX-305-T05 `timesync`). Another: a task that maps a network share fails with access denied although the account has rights, because of the double-hop; adding `become` with explicit credentials solves it.

## Related problems and ideas

For endpoint fleets, Intune, Configuration Manager and Group Policy offer pull-based, agent-based management that scales to desktops, and Ansible mostly supplements them for servers and ad hoc operations. For provisioning, Windows images are built with Packer and sysprep and delivered with unattended answer files (LNX-306-T01), cloud-init-like tooling on Windows (cloudbase-init) mirrors LNX-306-T03. For compliance, Microsoft security baselines and the DISA STIGs provide benchmarks that automation can apply and check. A more radical view skips direct management: build immutable images and replace instances; or use Kubernetes with Windows nodes for suitable workloads. An unresolved design question is how far to push Windows toward Linux-style management: SSH-first, key-based, with PowerShell remoting only where needed, as Microsoft itself has been moving.

## Active research

Ansible work for Windows concentrates on transport and performance. The SSH connection became officially supported in 2.18; there is continuing work on the Windows-specific connection and shell plugins, on PowerShell module infrastructure, on the Windows collections, on running the control node itself in WSL or in containers where limitations apply (the docs warn that WinRM and PSRP connection plugins have limits on macOS), and on moving module authors toward C#-based helpers [web: docs.ansible.com]. Open questions include how to keep Kerberos manageable in containerised execution environments, how to provide consistent check-mode behaviour across `win_*` modules (to verify), and how to apply the 2.19 data tagging and trust model to Windows module arguments.

## Future direction

Expect SSH to become the default for new Windows Server hosts, with certificate- or key-based authentication, and WinRM kept for legacy and domain-integrated cases. Microsoft's own direction toward a modern agent and cloud management (Azure Arc and Intune) will affect which tool owns which task. Practitioners should plan three steps: standardise on an authenticated and encrypted transport, scope automation accounts by tier, and build the connection prerequisites into the execution environment. For further study, the official Windows guide, the `ansible.windows` and `microsoft.ad` collection pages, and the vendor guides for AD integration on RHEL are the core references.
