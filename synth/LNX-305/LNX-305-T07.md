# Idempotence and check mode: making automation safe to repeat and safe to preview

## Define the problem

Two questions decide whether an operator trusts automation enough to run it against production. If I run this twice, will the second run do any harm? And can I find out what it would change before it changes anything? The first is the property of idempotence: applying an operation once or many times leaves the system in the same state. The second is the ability to preview, which Ansible provides as check mode (a dry run, `--check`) with its companion diff mode (`--diff`).

Without these properties a configuration tool is a script with a nicer syntax. A script that appends a line to a file adds it again each run; a script that creates a user fails the second time; a service restarted on every run causes a brief outage at every scheduled execution; a change that cannot be previewed has to be reviewed by reading and reasoning, which fails when variables, facts and templates interact. The gap this topic fills is the discipline and the tooling by which every task describes a target state, reports honestly whether it had to change anything, and can be asked to report without acting. The slice covers modules, tasks and playbooks in ansible-core 2.15 to 2.19. Playbook structure is LNX-305-T02, automated verification of the property with Molecule is LNX-305-T06, and drift detection in production is LNX-306-T09.

## History and approaches

The word comes from mathematics: an operation f is idempotent when applying it twice equals applying it once. System administration borrowed it from several sides. Mark Burgess's work on CFEngine in the 1990s described convergence: a promise, repeatedly evaluated, drives a machine toward its stated state and then does nothing once it arrives. Steve Traugott and others in the early 2000s argued in the infrastructure community for congruence, the idea that machines of a class should be demonstrably identical. Puppet and Chef made the resource model central: every resource has a state the provider can test before acting. All of those systems had agents that ran every 30 minutes, so idempotence was not optional, because any non-idempotent resource would misbehave 48 times a day.

Ansible entered with a push model and ad hoc commands, in which idempotence is a convention of the module author, not a feature of the engine. Modules receive arguments describing the desired state (`state: present`, `state: started`), examine the target and return a result with a `changed` flag; the engine counts and colours the result. This means an Ansible playbook is only as idempotent as its least careful task. The `command` and `shell` modules are the standing exception: they run whatever they are given and report changed, unless the author adds `creates`, `removes`, `changed_when` or a pre-check. Early Ansible users built playbooks from shell commands and later paid for it; the community's rule of preferring a specific module over `command` grew from that experience [src: ansible-docs eba577f2cdf22960].

Check mode appeared in Ansible 1.1 (2013), after the first generation of tools had shown that Puppet's `--noop` was valued even though it was imperfect. In Ansible a module opts in by declaring support for check mode; the engine passes a flag and the module performs all of its tests but none of its changes. Diff mode followed to show how a file would differ. The approach has failed in instructive ways. Modules that did not support check mode were silently skipped, which gave a clean-looking preview that omitted the riskiest tasks. A task that depends on the effect of a previous task (a service restart after a package install) cannot be fully previewed, because the earlier step did not happen. And modules that look at runtime state, such as a handler that waits for a port, either lie or fail in check mode. The partial successes and failures converge on a few rules: write modules so that the check path is the same code as the real path up to the change; give tasks that cannot be previewed an explicit `check_mode` setting; and treat preview as strong evidence, not a proof.

Across tools the pattern is the same. Terraform made the plan a first-class artifact that is reviewed and then applied. Kubernetes `apply` computes a three-way patch and `--dry-run=server` validates against admission. Even a well-built admission webhook must be idempotent, since a request can be invoked more than once [src: kubernetes-docs e29c571322e9f5c1].

## Current state

### How the engine and modules cooperate

A module's result is a dictionary with `changed`, `failed`, optional `msg`, and module-specific data. The play recap summarises counts of `ok`, `changed`, `failed`, `skipped` and others per host. For the file-oriented modules, the logic is a compare: `copy` and `template` hash the rendered content against the destination and also compare mode, owner and group; `lineinfile` matches a regular expression and rewrites the line only when it differs; `package` asks the package manager whether the package is installed; `service` checks state; `user` compares attributes. Idempotence is thus implemented by each module as a read-compare-write cycle.

`command`, `shell` and `raw` skip the read-compare step. Safe usage adds one or more of: `creates` (skip if a path exists), `removes` (skip if a path is absent), a registered earlier check with a `when`, and `changed_when` to compute the changed state from the output or return code, for example `changed_when: "'created' in result.stdout"`. A `failed_when` can narrow what counts as an error. Modules such as `ansible.builtin.stat`, `find`, `slurp` and `package_facts` provide state for such conditions. The loop is: probe, decide, act, report.

### Check mode and diff mode

`ansible-playbook site.yml --check` sets check mode for the whole run; `--diff` prints a unified diff for modules that provide one (`copy`, `template`, `lineinfile`, `blockinfile`, `replace` and others); both together are the standard pre-change review. Each task can override: `check_mode: false` makes a task that only gathers information run even in a dry run (so that later tasks have real data), and `check_mode: true` forces a task to be a dry run always. The variable `ansible_check_mode` is true during a check run and can drive a condition such as skipping a task that cannot be previewed. `diff: false` on a task suppresses its diff, which is essential for tasks that handle secrets. The same options exist for ad hoc commands (`ansible -m ... --check`) [src: ansible-docs bcb4d1e668c2a082].

Behaviour has several details that matter in practice. A module that does not declare support for check mode is skipped, and the output says so [src: ansible-docs 9885e7074f7b4cb1]. Registered variables from a task in check mode contain the predicted result, and downstream conditions use them, so a downstream `when` can behave differently in a dry run than in a real run [src: ansible-docs 602b5fe9839a327c]. Handlers are notified for a predicted change and run in check mode too, and modules like `service` predict the state change, not execute it. Facts gathering and the `setup` module always run, and the `debug` module prints as usual.

### Writing idempotent tasks

The working rules are short. Describe state, not action: `package: state=present`, not `command: dnf install`. Use the narrowest module: `lineinfile` for one line, `blockinfile` for a managed block with markers, `template` for a whole file. Prefer owning a whole file or a drop-in over editing a shared one. Give `command` tasks `creates` or `removes` or a `changed_when`. Avoid `state: latest` for packages in steady-state automation, because it makes a run change whenever a repository updates, and so a repeat run is no longer a no-op (ansible-lint reports this as `package-latest`). Avoid time-dependent values in templates, such as a `{{ ansible_date_time.iso8601 }}` stamp, since it rewrites the file every run; use `ansible_managed` and a fixed comment. Use `register` plus `when: result is changed` sparingly; the handler mechanism does this better.

### Testing the property

The easy test is to run the playbook twice and require that the second recap shows `changed=0`. Molecule makes this a standard step (LNX-305-T06). A stricter test runs the play in check mode after a real run and expects no predicted changes; a mismatch between predicted and actual behaviour is itself a finding. For production, a scheduled check run with `--diff`, whose output is parsed for `changed` counts, becomes a drift report (LNX-306-T09).

## Assessment: the good, the bad and the ugly

The good: idempotence is the property that makes it safe to rerun after a partial failure, safe to schedule, and safe to use as a convergence tool; it turns a playbook into a description. Check mode reduces fear and allows approval workflows, where reviewers see a diff before a change window. With both, rollout can be staged: run on a canary, preview on the rest, apply in batches.

The bad: both are conventions that the engine cannot enforce. A role can be written with a dozen shell tasks and still look fine until the second run. Check mode is partial by design, and the places where it is least reliable, namely command-like tasks, dependent tasks, network operations and tasks that need a prior step's real effect, are exactly the risky ones. A preview that says 3 changes can hide a fourth that was skipped for lack of support. Diffs can be noisy when templates contain ordering that differs between runs (hash or dictionary order, unsorted lists), and huge when binary or large files are involved.

The ugly: false idempotence. `changed_when: false` silences a task that did change something, and a role full of them reports clean runs on a system that was altered. Order effects are another: two tasks that fight over the same setting, one writing 10, the next writing 20, produce a changed result on every run and no failure, a pattern that only the second-run test finds. External state introduces non-idempotence: tasks that call APIs to create objects may create duplicates when a name is not unique, and tasks that rotate credentials or generate keys must be given something to compare against. Even file modes and SELinux contexts can be sources of repeated change if two modules disagree on the intended value. And safety-critical edge cases exist: a check run that gathers real facts can still hit a production service (for example a `uri` task with a POST), unless the module respects check mode.

## Applications beyond this domain

Idempotence is a design pattern for distributed systems in general. HTTP defines PUT and DELETE as idempotent so that clients can retry after a timeout; payment APIs add idempotency keys so that a repeated request does not charge twice; message consumers deduplicate by id so that at-least-once delivery behaves like exactly-once. Database migrations track an applied-migrations table for the same reason. Kubernetes controllers are idempotent reconcilers, and the admission webhook guidance explicitly asks for idempotent mutation, since a request may be re-invoked [src: kubernetes-docs c92cc190b34a3d0b]. Package managers record installed versions so that `install` of an installed package is a no-op (LNX-104-T01). Terraform's plan/apply and `make`'s timestamp checks are the same read-compare-act loop. Dry-run flags are everywhere: `rsync -n`, `dnf --assumeno`, `kubectl --dry-run`, `terraform plan`, `git clean -n`. What carries over is the design discipline: represent the target as data, compare before acting, return an honest result, and offer a way to preview.

## Examples

A task that is naturally idempotent: `ansible.builtin.lineinfile` with `path: /etc/ssh/sshd_config`, `regexp: '^#?PermitRootLogin'` and `line: 'PermitRootLogin no'` changes the file once and reports `ok` thereafter. A playbook run with `--check --diff` shows the old and new line without touching the file.

A command made safe: initialising a database with `command: initdb ...` is guarded by `args: creates: /var/lib/db/PG_VERSION`. The first run reports changed and the second skips. For a command that has no marker file, a pair of tasks works: a `command: dbtool status` with `changed_when: false` and `check_mode: false` to read state, then `command: dbtool enable` with `when: "'disabled' in status.stdout"` and `changed_when: true`.

A preview that misleads: the play installs a package, then runs a `command` that calls the new binary. In check mode the package task only predicts installation, so the later `command` fails because the binary does not exist, or is skipped (command modules do not run in check mode unless forced). Reviewers see an error that will not happen in real life, or no row at all. The fix is `when: not ansible_check_mode` on the dependent task, or `check_mode: false` on a read-only probe task, accompanied by the knowledge that the preview of that step is not available.

A non-idempotent failure: a task writes `{{ ansible_date_time.iso8601 }}` into `/etc/motd` through `template`. Every run changes the file and notifies a handler that reloads a service, so the schedule triggers a daily reload and an on-call engineer wonders why the recap never shows zero changes. Replacing the timestamp with the fixed `{{ ansible_managed }}` string fixes it. The same symptom appears when a templated file iterates over `groups['web']` and the order of inventory hosts changes between runs; sorting the list (`| sort`) fixes it.

## Related problems and ideas

Convergence versus reconciliation is a theoretical neighbour: a push tool applies a change once, an agent applies repeatedly, and a controller watches continuously. Immutable infrastructure sidesteps idempotence by replacing the machine rather than repairing it (see LNX-306-T04), at the price of an image pipeline. The opposite risk is configuration drift in mutable machines, where manual changes are unseen until a run reveals or reverts them. Declarative-first tools (Terraform, Kubernetes) have idempotence by construction, because the engine, not the module author, computes the difference; Ansible has been moving partway there with modules that report a diff, with `ansible.utils` and `ansible.netcommon` resource modules for network devices (states `merged`, `replaced`, `overridden`, `deleted`, `gathered`, `rendered`, `parsed`) and with the 2.19 emphasis on typed data.

Ideas not yet mainstream include formal verification of playbooks (modelling tasks as functions on state and proving idempotence or detecting conflicting writers), and automated generation of check-mode-safe modules from schemas. Close at hand, asynchronous tasks add a wrinkle: a task started with `async` and polled later reports changed at completion, so preview and idempotence depend on the way the job is started [src: rocky-docs 5b31773117539c36].

## Active research

Researchers study the properties that infrastructure scripts should satisfy and tools that check them. Work from several groups on Puppet and Ansible has tried to detect idempotence violations and conflicting resource writes by static analysis, symbolic execution of simple state models, or by running the play twice in a sandbox and comparing states (to verify specific papers and tools). The Ansible community is looking at how modules should handle check mode when they query external systems, and what should be the standard for reporting a diff without secrets. A related active area is making check-mode results richer: for example, a module might return a structured description of the planned change in addition to a boolean.

## Future direction

The trend is toward making the safe behaviour the default and visible: lint rules that flag `command` without guards, test harnesses that include a second-run check, and platform features that run a preview before each production job and require approval. Watch ansible-core releases for work on check mode for more core modules and for better handling of variables registered in preview. For practitioners, adopt three habits: preview with `--check --diff` before every non-trivial change, require a second-run no-change test for every role, and treat any use of `command` or `shell`, `changed_when: false` or `ignore_errors: true` as a line needing a written reason.
