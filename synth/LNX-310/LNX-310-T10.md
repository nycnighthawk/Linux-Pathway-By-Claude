# Sandboxed container runtimes: gVisor, Kata Containers and microVMs

## Define the problem

A standard container is a process that shares the host kernel. Every system call it makes lands in the same kernel code, with the same bugs, that serves every other container and the host's own services. The boundary is the set of kernel checks (namespaces, capabilities, seccomp, labels), and a single flaw in a syscall handler, a filesystem or a driver can turn a compromised container into a compromised node. For workloads whose code the operator trusts, such as the company's own services, that residual risk is accepted. For code the operator does not trust, it is not: customers' functions in a serverless platform, build jobs from pull requests by strangers, plug-ins, notebooks, and code generated by AI agents. NIST's container guide spells out the point: containers share the kernel, so the isolation is weaker than that of virtual machines, and workloads of different sensitivity should be separated by stronger boundaries [src: nist-sp800-guides cbcc66d58eb7a404].

The need is a runtime that keeps the developer experience of containers (OCI images, the same CLI and Kubernetes API, fast start, small overhead) but replaces or hides the shared kernel attack surface. Two designs answer it. A **user-space kernel**, gVisor, implements the Linux system call interface in a memory-safe program and lets the host kernel see only a small, filtered set of calls from it. A **lightweight virtual machine**, as in Kata Containers and Firecracker-based systems, runs each pod or container inside a hardware-virtualised guest with its own Linux kernel, so the host kernel's exposure is the hypervisor interface, a far narrower one than the syscall table. This slice covers both, how they plug into container runtimes, what they cost and where each fails. It needs KVM for the VM approach, and this affects where labs can run.

## History and approaches

Before dedicated sandboxes, operators layered protections: seccomp profiles that block hundreds of syscalls, AppArmor or SELinux confinement, dropped capabilities, and user namespaces. These shrink the reachable kernel surface but never remove it, and every layer is still the host kernel enforcing rules on itself. Another approach was one VM per tenant with containers inside, which is strong but wastes memory and mixes lifecycle layers. Early attempts to get VM isolation at container speed were Intel's Clear Containers (2015) and Hyper's runV, which ran containers in tiny VMs with a stripped kernel and a stripped device model. In 2017 the two merged into Kata Containers under the OpenStack Foundation (now the OpenInfra Foundation), combining the Clear Containers runtime with runV's agent and hypervisor abstraction [src: archwiki e0389da3e57b5a2f].

Google took the other route. gVisor, open sourced in 2018, started as the sandbox of its App Engine second-generation runtimes and Cloud Functions, and is described by its authors as an application kernel written in Go that implements a large part of the Linux interface in user space [web: gvisor.dev]. Amazon built Firecracker (2018) to run AWS Lambda and Fargate, a very small virtual machine monitor in Rust that leaves out almost every legacy device and offers only a minimal set (virtio block and net, vsock, a serial console, a keyboard controller for reset). It is the VMM behind Lambda's microVMs, and Kata can use it as a backend [src: firecracker-docs f10a8d6183e6523c].

Lessons from this history: pure syscall-filter hardening reached a plateau; guest kernels in VMs added memory and start-up costs that needed engineering (shared memory-mapped root filesystems with DAX, templated or snapshotted VMs, and memory ballooning) before VM-based pods were practical at scale; and user-space kernels paid with compatibility gaps and syscall overhead, which constrained what could be run. The pattern that settled is the **shim v2** plug-in model of containerd and CRI-O: the sandboxed runtime appears as one more OCI-style runtime handler, and Kubernetes selects it per pod through `RuntimeClass`, so a single cluster mixes runc pods and sandboxed pods [src: docker-docs 806741c826027cc5].

## Current state

### Where they plug in

At the bottom of the stack described in topic T02, the low-level runtime receives an OCI bundle and starts the workload. A sandboxed runtime implements the same contract, but treats a request to start a container as a request to create a sandbox and place the container inside it. With containerd, the runtime handler is a shim named by convention: `io.containerd.runc.v2` for runc, `io.containerd.kata.v2` for Kata and `io.containerd.runsc.v1` for gVisor's `runsc`. Docker's documentation shows both the older approach of registering an alternative runtime in `daemon.json` (`"runtimes": {"runsc": {"path": "/usr/local/bin/runsc"}}`, then `docker run --runtime=runsc`) and the containerd shims, with a note that the shim to use is configured under the `runtimes` section [src: docker-docs e3d428b952542088] [src: docker-docs db63b1eae1bf139f]. For Podman, `--runtime /usr/bin/runsc` or `containers.conf` entries do the same [src: archwiki 905535a824c69608]. In Kubernetes, an administrator defines handlers in the CRI runtime's configuration and publishes them with an object like:

```yaml
kind: RuntimeClass
apiVersion: node.k8s.io/v1
handler: runsc
metadata:
  name: gvisor
scheduling:
  nodeSelector: {sandbox.example/gvisor: "true"}
overhead:
  podFixed: {memory: 120Mi, cpu: 100m}
```

A pod then sets `runtimeClassName: gvisor`. The `overhead` field makes the scheduler account for the sandbox's own memory and CPU, which matters for VM-based runtimes whose guest kernel and agent take a measurable amount [src: kubernetes-docs e23fee34c2f94cd6]. Sandbox pods are also part of Kubernetes' wider security guidance: the Pod Security Standards constrain what a container may ask for, and sandboxing is a complement for untrusted tenants, not a substitute [src: kubernetes-docs 5f7ecd74634e8d6f].

### gVisor

gVisor's `runsc` is an OCI runtime that creates a **sandbox**: a process group consisting of the **Sentry**, which acts as the guest kernel and implements system calls, signals, memory management, threading, the network stack (netstack, written in Go) and a virtual filesystem, and one or more **Gofer** processes that perform file access on behalf of the sandbox over a 9P-like protocol (newer versions also support a direct host-file path, `lisafs`, to reduce overhead). The application's system calls do not go to the host kernel. Instead, a **platform** redirects them to the Sentry. The default platform is `systrap`, which uses a seccomp `SECCOMP_RET_TRAP` rule to turn each syscall into a signal that the Sentry handles; the `KVM` platform lets the Sentry use hardware virtualisation to trap, offering best performance on bare metal but suffering in nested virtualisation; the older `ptrace` platform is slow and is being phased out [web: gvisor.dev]. The Sentry itself runs under a tight seccomp filter on the host, allowing only a few dozen host syscalls, so a compromise of the Sentry still faces the host kernel's limited exposed surface, and the Gofer is separately confined.

gVisor does not need hardware virtualisation (with `systrap`), which makes it deployable inside cloud VMs that disallow nested KVM. It does not implement every syscall, `/proc` entry or `/sys` file, so some software fails: programs that depend on rare ioctls, `perf_event_open`, certain `io_uring` features, raw kernel modules or kernel-version-specific behaviour; system-call-heavy workloads lose throughput because each call is handled in user space; and networking and file I/O can be slower than native, with the overhead depending on the workload and the file-access path. The project publishes compatibility notes and a syscall support table.

### Kata Containers

Kata runs each pod (the CRI sandbox) in a VM. The host side is a **shim** (`containerd-shim-kata-v2`), implemented in Go or, in the newer `runtime-rs`, Rust; it launches a hypervisor (QEMU, Cloud Hypervisor, Firecracker, or the built-in Dragonball VMM in the Rust runtime), boots a minimal guest kernel and a root filesystem or initrd built by `osbuilder`, and talks over **vsock** to a **kata-agent** inside the guest. The agent creates namespaces and cgroups *inside the guest* for each container of the pod and runs them with the same libcontainer-style code; from the guest's point of view, they are ordinary containers on an ordinary but private kernel. The host sees only a VMM process (one per pod) that holds a virtual CPU for each guest vCPU and the pod's memory [src: archwiki a8eaabb9084b2e93].

Details that matter: the container image's layers are made available in the guest by file sharing (`virtio-fs` is the default today; the older 9p is slower and deprecated) or, with the *devmapper* snapshotter, as block devices passed through virtio-blk, which improves I/O; networking connects the pod's network namespace on the host to the guest through a TC filter, macvtap or tap mirroring; resource limits are applied twice, to the guest's size and to the VMM process's cgroup; and the guest kernel's version is independent of the host's, so containers can see newer or older kernel features than the host provides. Kata integrates with Kubernetes through RuntimeClass and with Cilium and other CNIs after the pod networking setup is adapted to a VM [src: cilium-docs 7ac09b395b481b50]. Using it requires hardware virtualisation: `/dev/kvm` and, in a cloud VM, nested virtualisation or bare-metal instances; the host check is `kata-runtime check` (or `kata-ctl check`), and `ls -l /dev/kvm` plus `grep -E 'vmx|svm' /proc/cpuinfo` are the first things to look at.

### Firecracker and microVM platforms

Firecracker is not an OCI runtime by itself. It is a VMM that exposes a REST API over a Unix socket to configure vCPUs, memory, a kernel image, block devices and tap-backed network interfaces and then to start the guest; a `jailer` process puts Firecracker in a chroot, new namespaces and a cgroup, drops privileges and applies seccomp filters, so that even a VMM escape lands in a locked-down process [src: firecracker-docs 38339491a756dc4c]. Boot times in the low hundreds of milliseconds and per-VM memory overhead of a few megabytes are the design goals. It is deployed through `firecracker-containerd`, through Kata with the Firecracker backend, and through managed platforms such as AWS Lambda and Fargate, and fly.io-style machines. It requires KVM, and the project's documentation spells out the host setup, including how Firecracker's feature set compares with plain KVM and with Nitro enclaves [src: firecracker-docs f10a8d6183e6523c] [src: firecracker-docs 8c4d74c264473b5c].

### Choosing

A simple comparison guides selection. runc: shares the host kernel, lowest overhead, widest compatibility. gVisor: no guest kernel and no hardware requirement, good for stateless services and multi-tenant code, with compatibility and syscall-cost tradeoffs. Kata or Firecracker: strong hardware isolation and a full Linux kernel in the guest, so near-full compatibility, with costs in memory per pod, start time (hundreds of milliseconds to seconds) and the need for KVM. For the strongest guarantee, such as confidential computing with encrypted guest memory (AMD SEV-SNP, Intel TDX), Kata-based Confidential Containers add attestation and encrypted images.

## Assessment: the good, the bad and the ugly

The good: a sandbox lets the operator say, with evidence, that a kernel bug in the host's syscall layer does not by itself break tenant isolation. RuntimeClass makes adoption incremental and reversible, and the same images run unchanged. gVisor needs no KVM and starts in tens of milliseconds, Kata runs unmodified Linux binaries because the guest is Linux, and both have track records at scale (Google Cloud's serverless products and Lambda respectively).

The bad: overhead and compatibility. A Kata pod costs tens of megabytes of RAM for the guest kernel, agent and VMM, plus the memory the guest kernel uses for its own page cache, which duplicates the host's unless DAX or shared memory is used. Start-up is slower than runc by an order of magnitude. Devices are harder: GPUs, SR-IOV NICs and hostPath volumes need passthrough or file sharing, and `hostNetwork` and `hostPID` pods have no meaning inside a VM. gVisor's per-syscall cost and incomplete kernel make it unsuitable for some databases and anything that leans on exotic kernel interfaces; I/O-heavy workloads run slower. Observability tools that rely on host kernel hooks (eBPF programs, `perf`, `strace` of the host PID) see only the VMM or the Sentry, not the workload's own system calls, which complicates debugging as in topic T09. Sandboxing also shifts the risk instead of removing it: the hypervisor, the VMM and the Sentry are all code with CVEs.

The ugly: operational mismatches. Running Kata in a cloud VM without nested virtualisation fails at pod creation with an obscure error, and nested virtualisation costs performance and sometimes reliability. Misconfigured RuntimeClass names leave pods `ContainerCreating`, or worse, silently scheduled on nodes without the handler. A sandbox is not a policy: a privileged pod in a sandbox may have access to what the VM exposes, and mounts shared from the host through virtio-fs create a new attack surface at the file-sharing daemon. Isolation also does not stop attacks through the pod's legitimate channels: network access to the cloud metadata endpoint or credentials mounted into it. Covert channels and microarchitectural side channels (Spectre-class, cache attacks) cross VM and syscall boundaries, which is why multi-tenant clouds also schedule by tenant at the hardware level. The configuration of three layers (hypervisor, guest kernel image, runtime config) creates version-skew problems on upgrades.

## Applications beyond this domain

The same idea of narrowing the interface between untrusted code and the privileged substrate appears across computing. Browsers split renderers into sandboxed processes and run WebAssembly in a memory-safe engine; the Chromium sandbox on Linux uses namespaces and seccomp for the same reason as runc, and some products nest further isolation. WebAssembly runtimes (Wasmtime, WasmEdge) present a capability-based interface where the system-call surface is a small defined set (WASI), and are plugged into containerd with shims of their own. Android's `crosvm` and ChromeOS's use of VMs for Linux apps follow the microVM pattern; Qubes OS and Windows Sandbox use VMs to isolate applications. Unikernels are another form of reducing the guest to one application and a minimal kernel. In cloud platforms, "function as a service" isolation depends on microVMs. Confidential computing generalises the approach by also protecting the guest from the host.

## Examples

*Registering gVisor in Docker.* After installing `runsc`, `sudo runsc install` adds the runtime to `/etc/docker/daemon.json`, a daemon restart follows, and `docker run --rm --runtime=runsc alpine dmesg` prints boot-like messages generated by the Sentry, not by the host: a quick demonstration that the guest kernel is synthetic. `docker run --rm --runtime=runsc alpine uname -r` reports gVisor's emulated kernel version, which differs from `uname -r` on the host.

*Seeing a Kata VM from the host.* After `kubectl run` with `runtimeClassName: kata`, `ps aux | grep qemu` (or `cloud-hypervisor`) on the node shows a VMM process holding the pod's memory; `kata-runtime env` prints the configuration and paths; `uname -r` inside the pod prints the guest kernel, usually different from the node's. Host-side `crictl pods` still lists the pod with the Kata runtime handler.

*Check before you start.* `grep -c -E 'vmx|svm' /proc/cpuinfo` is non-zero when the CPU offers virtualisation; `ls -l /dev/kvm` shows the device and its group; `kata-ctl check` or `kata-runtime check` reports missing features. In a cloud VM, `systemd-detect-virt` returns the outer hypervisor, and a result such as `kvm` or `microsoft` without `/dev/kvm` means nested virtualisation is not enabled, which is the commonest reason a Kata pod will not start [src: man-pages b2d7815c81bb11b9].

*A failing example: wrong assumption of compatibility.* A team moves a Java service using `perf_event_open`-based profiling into gVisor and the profiler agent fails at start with an unsupported-syscall error that appears in the Sentry's log, not the application's. The runbook change is to run profiling pods on runc nodes in a trusted namespace while untrusted tenants use the sandbox class.

*A failing example: memory accounting.* A node with 64 GB schedules fifty Kata pods requesting 1 GB each and runs out of memory, because each VM also consumes about 150 MB for kernel, agent and VMM that the scheduler did not know about. Defining `overhead.podFixed` in the RuntimeClass (or lowering pod density) fixes the accounting.

## Related problems and ideas

Other approaches to the same problem include hardened shared-kernel designs (seccomp with strict allow-lists, Landlock policies, and the combination of user namespaces with LSMs that make the kernel attack surface smaller but not absent), kernel hardening work (`CONFIG_` options that reduce exposure, lockdown, restricted unprivileged BPF), separate VMs per tenant with containers inside, and language-level sandboxes (WebAssembly, V8 isolates). Related ideas: Nabla containers (rump-kernel based, now dormant), Unikraft unikernels, `libkrun` (a library that embeds a VMM in a process, used by Podman machine and by crun's microVM mode), and `youki` with Wasm handlers. Operationally adjacent are virtual-machine platforms for Kubernetes (KubeVirt) which run entire VMs as pods, with a different goal (running VM workloads) but overlapping technology [src: kubevirt-user-guide 97bde965cc21a1ab]. Not yet mainstream: per-request snapshot and restore of microVMs for sub-10-millisecond cold starts, and sandboxes that use hardware capability features (CHERI) to confine memory rather than virtual memory.

## Active research

Research and engineering focus on the cost side and on confidentiality. For VMs: faster boot by snapshotting and restoring a pre-warmed microVM, memory sharing between guests (page-cache sharing with DAX and virtiofs, KSM-like deduplication, free page hinting) and hot-plug of CPUs and memory so that a pod's VM grows as needed. For user-space kernels: making Sentry-to-host interaction cheaper, supporting more of the syscall surface (including parts of `io_uring` and GPU drivers for machine-learning workloads, an active area for gVisor), and rewriting hot paths in memory-safe languages. For confidential containers, work on remote attestation, sealed secrets that only decrypt inside an attested guest, and image pulling inside the guest so that the host never sees plaintext layers. Security researchers continue to look for escapes in VMM device emulation, virtio implementations and virtiofsd, and for microarchitectural leakage between co-resident guests.

## Future direction

Expect sandboxed runtimes to move from specialist to ordinary in multi-tenant and AI-agent platforms, where code generated at run time needs a strong boundary around it. Rust implementations (Kata's `runtime-rs`, Firecracker, Cloud Hypervisor, Dragonball) reduce memory-safety risk in the VMM layer. The OCI runtime specification keeps adding fields that VM-based runtimes need, such as hardware configuration objects for VMs in recent versions [web: github.com]. Kubernetes continues to expose isolation as a policy choice, with user namespaces for pods on the shared-kernel side and `RuntimeClass` plus pod overhead on the sandbox side. gVisor's default platform has already shifted from `ptrace` to `systrap`, and the `KVM` platform is best on bare metal [web: gvisor.dev]. For practitioners the stable guidance is to classify workloads by trust, use sandboxes for untrusted or multi-tenant code, check KVM availability early, measure with your real workload because overhead varies widely, and keep every other control (capabilities, seccomp, network policy) in place.
