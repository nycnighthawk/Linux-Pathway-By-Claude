# Container storage: overlayfs layers, volumes and SELinux labels

## Define the problem

A container needs a root filesystem that starts identical to the image, that thousands of siblings can share without each holding a full copy, that accepts writes without damaging the image, and that disappears with the container. Real applications also need data that outlives the container, files shared between containers, and configuration or secrets injected from the host. And on systems with mandatory access control, the kernel must still stop a confined container process from reading host files that it was not meant to see, even when an administrator has deliberately mounted a host directory into it.

Three mechanisms answer these needs and they interact in ways that cause most of the storage incidents operators see. A union filesystem, overlayfs on current Linux, stacks read-only image layers under a writable one. Volumes and bind mounts connect the container's mount namespace to directories that have a different lifetime. SELinux labels, enforced on every file access, decide whether the container's process type may touch those host files. This slice covers how overlayfs works and where it surprises, how Docker and Podman manage volumes and mounts, how the labelling options `:z` and `:Z` relate to SELinux types and categories, and the diagnosis of disk, permission and performance problems.

## History and approaches

The first Docker storage driver used AUFS, a union filesystem that never entered the mainline kernel, so distributions without it needed alternatives. Red Hat-family systems lacked AUFS and Docker added `devicemapper` (thin-provisioned block devices with copy-on-write at block level), first in a slow loop-mounted configuration and then as direct-lvm, whose operational complexity led many sites to data loss or full pools. Btrfs and ZFS drivers used native snapshots, giving good semantics but tying images to a filesystem. Overlayfs entered the mainline kernel in 3.18 (2014) as a union filesystem designed for the Linux VFS; Docker's first `overlay` driver, which hard-linked files between layers, consumed inodes quickly, and `overlay2` (2016) replaced it with a design that mounts many lower directories at once, needing kernel 4.0 or later for multiple lowers. `overlay2` has since been the default on mainstream distributions [src: docker-docs 2b21aac50759adb1] [src: docker-docs 665e9bf5d7a8b886].

Rootless containers pushed further. Kernel overlayfs refused unprivileged mounts until a user-namespace mode arrived in Linux 5.11, and until then Podman and rootless Docker used `fuse-overlayfs`, a user-space implementation, slower but available. The `vfs` driver, which copies each layer in full, remains the fallback for filesystems where nothing else works, at a heavy price in space and time. Recently, containerd's own snapshotters (`overlayfs`, `native`, `stargz`) have become the way Docker Engine 29 stores images on fresh installs, with the classic `overlay2` driver still described for existing installations. Composefs, from the Red Hat and GNOME ostree communities, adds a read-only erofs metadata image with an overlay on top and fs-verity digests, for deduplicated and verifiable layers.

For persistence, the earliest mechanism was a bind mount of a host path (`-v /host:/container`). Volumes (`docker volume create`), added in 2014, gave the engine a managed directory with its own lifecycle, drivers for NFS or cloud disks, and the ability to be pre-populated from the image. SELinux integration arrived because Red Hat wanted containers to be confined even when the user mounted host files; the Docker `:z` and `:Z` mount flags (2014, later in Podman and Buildah) relabel host content. Kubernetes generalised the idea: volume types in pods, PersistentVolumes with a security context that can set `seLinuxOptions` and `fsGroup` [src: kubernetes-docs 04bb3bc9f3d02ba1].

The partial successes: block-level copy-on-write gave strong isolation of file operations but poor space accounting. Overlayfs quirks (rename of directories, `st_dev`, hard link counts) caused years of application surprises and mostly fixed by options such as `redirect_dir`, `index` and `xino`. The lesson that emerged is that the root filesystem is disposable and cheap to copy-on-write, while state belongs on a mount with explicit ownership, and that labels must follow the data.

## Current state

### How overlayfs composes a root filesystem

An overlay mount takes one or more **lower** directories (read-only), an **upper** directory (writable) and a **work** directory (a scratch area on the same filesystem as the upper) and presents a **merged** view:

```bash
mkdir -p lower1 lower2 upper work merged
echo base > lower1/a ; echo more > lower2/b
sudo mount -t overlay overlay \
    -o lowerdir=lower2:lower1,upperdir=upper,workdir=work merged
```

In `lowerdir=lower2:lower1`, the leftmost is the top of the stack. A lookup returns the file from the highest layer that has it. Directories merge: entries from all layers appear together. Reading an unmodified file reads straight from the lower layer, with no copy and with the page cache shared among all containers using the same layer file, which is the main reason many containers on one image are cheap in memory.

Writing is where cost appears. The first modification to a file from a lower layer triggers **copy-up**: the whole file (not just the changed block, except with `metacopy` for metadata-only changes) is copied to the upper directory, then modified. A 2 GB database file touched once is copied once, a latency cliff that surprises people who put databases in the writable layer. Deleting a lower file creates a **whiteout** in upper, a character device with device number 0/0 and the file's name; deleting and re-creating a directory marks it **opaque** through an extended attribute (`trusted.overlay.opaque=y`), so lower content stays hidden. This is the kernel-level equivalent of the `.wh.` entries in OCI layer tarballs from topic T02, and unpackers translate between them. In rootless mode these markers use the `user.*` xattr namespace via the `userxattr` mount option, since an unprivileged process cannot write `trusted.*`.

Docker's `overlay2` stores each layer as a directory with `diff/` (the layer content), `link` (a short name), `lower` (the chain of short names), `merged/` and `work/`, under `/var/lib/docker/overlay2/`, with a directory `l/` of short symbolic links, because the kernel limits the length of mount option strings to one page, which would otherwise cap the number of layers. Podman and containerd use similar layouts in their own roots. `docker inspect <ctr> --format '{{json .GraphDriver.Data}}'` prints `LowerDir`, `UpperDir`, `WorkDir` and `MergedDir`, so the upper directory of any container can be examined on the host to see what it changed; `docker diff <ctr>` lists the same changes as A (added), C (changed) and D (deleted).

Requirements and limits: the backing filesystem must support `d_type` (XFS needs `ftype=1`, the default in modern mkfs) and xattrs; it should be ext4 or XFS, and XFS can enforce per-container size limits with `pquota` and `--storage-opt size=`. Not every filesystem can be the upper layer; NFS and some FUSE filesystems cannot. Because `rename(2)` of a directory that exists in a lower layer returns `EXDEV` unless `redirect_dir` is on, tools that rename directories inside a container could fail in the past. Inode numbers and `st_dev` may differ between a file before and after copy-up unless `xino` is enabled, which confuses `rsync`, backup tools and some build systems. Hard links across layers break after copy-up unless `index` is set. The Docker documentation summarises these compatibility points and its performance guidance [src: docker-docs 4e52edc803ae5b89].

### Volumes, bind mounts and tmpfs

A container's mount namespace can receive three kinds of attachments, selected by `-v` or the more explicit `--mount`:

- **Named volumes**: engine-managed directories (`/var/lib/docker/volumes/<name>/_data`, or `~/.local/share/containers/storage/volumes/<name>/_data` rootless). They bypass the storage driver, so writes go straight to the host filesystem at native speed. When an empty volume is first mounted over a directory that exists in the image, its content is copied in; a non-empty volume is not. A Red Hat tutorial shows creating one with `podman volume create` and sharing it between containers [src: rhel-10-docs dc959f85cd008461].
- **Bind mounts**: any host path, mounted as is. With `-v`, a missing host path is created as a root-owned directory, which is a silent source of mistakes; with `--mount type=bind,source=...,target=...`, a missing source is an error. `ro` makes it read-only. Mount propagation (`rprivate` default, `rslave`, `rshared`) decides whether later mounts under the source appear in the container.
- **tmpfs**: memory-backed, with `size=` and `mode=` options, used for `/tmp` and secrets, gone at stop.

Volume drivers add network or cloud storage. A `local` driver with `type=nfs` options mounts NFS on demand; plugins connect block storage. The `:ro`, `:z`, `:Z`, `:U`, `:idmap` and `:O` (overlay) suffixes modify behaviour in Podman. Compose and Quadlet reference named volumes, and `docker volume ls -f dangling=true` lists the ones no container uses. Clean-up commands are dangerous: `docker volume prune` and `podman volume prune` remove unreferenced volumes, and so does the `--volumes` flag of `system prune`.

Storage accounting uses `docker system df` or `podman system df`, which separates images, containers and volumes, and shows reclaimable space [src: rhel-10-docs 728036a3b40f7630]. Logs are a hidden consumer: the default json-file driver grows without a bound unless `max-size` and `max-file` are set.

### SELinux and containers

On Fedora, RHEL and derivatives, every process and file has a label of the form `user:role:type:level`. A container process runs as type `container_t`, with a level made of a sensitivity and two **MCS categories** such as `s0:c123,c456`, chosen randomly per container. The container's own layers, volumes and rootfs carry `container_file_t` labels with the same categories. SELinux policy allows `container_t` to read and write files of type `container_file_t` whose categories match its own, but not host types such as `user_home_t`, `var_lib_t` or `etc_t`. Two containers with different category pairs cannot read each other's files even with identical UIDs, which is how SELinux separates containers beyond namespaces.

A host directory bind-mounted without relabelling still carries its host type, so the container hits `Permission denied` though Unix permissions are right. `ausearch -m avc -ts recent` or `journalctl -t setroubleshoot` shows the denial with the source `container_t` and target type. The fixes, in order of preference:

1. `:Z` on the mount (`-v /srv/data:/data:Z`) relabels the content recursively to `container_file_t` with this container's private categories; no other container can use it. `:z` relabels to a *shared* label with no category restriction (`s0`), so several containers can use it.
2. Pre-label the directory permanently: `semanage fcontext -a -t container_file_t '/srv/data(/.*)?'` then `restorecon -Rv /srv/data`. This survives relabel operations and avoids recursive relabel at every start.
3. Narrow exceptions with `--security-opt label=type:my_container_t` (custom policy, possibly generated by `udica` from a container's `inspect` output).
4. `--security-opt label=disable` removes confinement for that container, and `--privileged` implies it. This is the last resort.

Warnings follow from the mechanism. `:Z` on a directory shared with other services (the user's home, `/var/lib`, `/etc`) rewrites labels beneath it and may break those services; on a large tree the recursive relabel at start is slow. Podman refuses `:Z` on some system directories for this reason. Kubernetes handles this with `securityContext.seLinuxOptions` and, in recent releases, a feature that mounts volumes with the right label option so that the kubelet need not relabel recursively (to verify) [src: kubernetes-docs 04bb3bc9f3d02ba1]. AppArmor-based distributions (Ubuntu, Debian, SUSE) use per-container AppArmor profiles instead and have no label stage, so the same mount works without flags; the flags are ignored there.

### Ownership, user namespaces and idmapped mounts

Ownership is the other half of permissions. In a rootless or `userns-remap` container, a file owned by UID 1000 on the host appears as `nobody` or as a subordinate ID in the container. `--userns=keep-id`, the `:U` volume flag that chowns the source into the container's mapping, `podman unshare chown`, and kernel *idmapped mounts* (Linux 5.12 and later; `:idmap` in Podman, `idmap` in OCI mount options) are the four tools. Idmapped mounts present the same inode with ownership translated, without changing the data on disk, which is the cleanest solution for shared directories [src: kubernetes-docs 3f263bd4ef1b0067].

## Assessment: the good, the bad and the ugly

The good: overlayfs makes starting a container as cheap as creating three directories, shares page cache between siblings, and keeps images immutable. Volumes give a clear boundary between disposable and durable state, and they are the fast path for write-heavy data. SELinux MCS labels give real, policy-enforced separation between containers and between containers and the host, beyond namespaces, and `:Z` makes it usable without writing policy.

The bad: copy-up penalises large files and is invisible in the image. A database or log written to the container layer is slow, grows the layer, and vanishes at removal, which is the number-one cause of lost data in early container deployments. Many layers slow metadata lookups. Overlayfs does not behave exactly like a native filesystem: `inotify` on lower files, `fsync` costs, `rename` and `st_dev` behaviours cause occasional tool failures. Disk usage is opaque: `df` inside a container shows the host filesystem, and a full `/var/lib/containers` or `/var/lib/docker` stops all containers and builds.

The ugly: labels and ownership produce errors that look unrelated to their cause. A permission error on a mount with correct `chmod` is usually SELinux; an "operation not permitted" from `chown` in a rootless container is usually a missing subordinate ID range; "no space left on device" with free blocks is inode or overlay metadata exhaustion. Recursive relabelling with `:Z` on the wrong directory can brick a host service. Volumes accumulate after `compose down` without `-v`, and pruning with `-a --volumes` on the wrong machine deletes data. NFS-backed volumes with root squash break chown in images that expect root. Snapshotter metadata that disagrees with the on-disk layers after a crash or a manual delete produces "layer does not exist" errors that need `docker system prune`, or in the worst case a wipe of the storage root. Security-wise, a writable bind mount of a host directory such as `/` or `/etc`, or of the container runtime socket, undermines every other control.

## Applications beyond this domain

Overlay-style union mounts predate containers and serve live CDs and installers (squashfs plus a writable overlay), embedded systems with read-only root partitions and a writable overlay for configuration, and OpenWrt's overlayroot. Image-based operating systems use the same idea: `ostree` and `bootc` systems deploy an immutable `/usr` and layer mutable `/etc` and `/var` over it, and composefs strengthens integrity. Copy-on-write snapshots for developer environments and CI caches use the same structure in Btrfs, ZFS, LVM thin pools and VM disk backing files. SELinux labels for data separation apply to virtual machines (sVirt uses the same MCS categories per guest, so two VMs cannot read each other's disks), to multi-tenant daemons and to systemd services. The volume-versus-ephemeral discipline is how stateless application tiers and stateful stores are separated in any cloud design.

## Examples

*Watching copy-up.* Run a container, `docker exec c sh -c 'dd if=/dev/zero of=/big bs=1M count=200'`, then `docker diff c` shows `A /big`. In the host path from `docker inspect`, `ls -l UpperDir/big` shows 200 MB. A second `docker exec c rm /usr/share/some/file` creates `UpperDir/usr/share/some/file` as a character device `0, 0`: `ls -l` displays `c--------- 0 0`, a whiteout.

*Hand-built overlay.* The `mount -t overlay` example above, with `touch merged/new; rm merged/a`, leaves `upper/new` and a whiteout `upper/a`, while `lower1/a` is untouched; unmounting and removing the upper directory returns everything to the base state, which is the entire rollback story of containers.

*Bind mount with SELinux.* `podman run --rm -v $PWD/site:/usr/share/nginx/html:ro nginx` on Fedora returns 403 from the web server; `ls -Zd site` shows `user_home_t`; `ausearch -m avc -ts recent` shows `container_t` denied `read`. Adding `:Z` (private) or applying `semanage fcontext` and `restorecon` fixes it, and `ls -Zd site` then shows `container_file_t:s0:c101,c909` for private or `s0` for shared.

*A failing example: database in the writable layer.* A team runs PostgreSQL in a container without a volume. Performance is acceptable at first, then checkpoints stall as copy-up and layer growth interact; a routine `docker rm` and re-create then loses the cluster. Declaring the data directory as a named volume keeps data across re-creation and bypasses overlay costs. The image's `VOLUME` instruction creates an anonymous volume as well, which many people only discover when `docker volume ls` shows dozens of orphaned volumes.

*A failing example: disk full.* A host reports `no space left on device` while `df` shows the application filesystem fine. `docker system df -v` reveals 80 GB of build cache and 30 GB of json-file logs from a chatty container. `docker builder prune --keep-storage 10GB` reclaims cache, and setting `log-opts` with `max-size=50m` and `max-file=3` in `daemon.json` prevents recurrence (recreate containers to apply to existing ones).

## Related problems and ideas

Alternatives to overlayfs for layers include native btrfs and ZFS snapshots, device-mapper thin pools, and per-image erofs with composefs. Lazy-pulling snapshotters (stargz, nydus, SOCI) mount layers from a remote registry on demand. User-space filesystems (fuse-overlayfs, `virtiofsd` for VM-shared directories) replace kernel code where privileges are limited. For state, CSI drivers in Kubernetes (topic of the cluster courses) provide dynamic volumes; local-persistent volumes and distributed filesystems (Ceph, Longhorn) address node loss. Encryption at rest of volumes (LUKS, fscrypt, per-pod encrypted volumes) and secrets via tmpfs or in-memory files follow the same mount model. The alternative design is not to use local storage: stateless containers writing to object stores and databases, which eliminates the issues at the cost of architecture.

## Active research

Current work includes making user-namespaced containers storage-friendly (idmapped layers so that pulled images need no chown pass, via `overlayfs` plus idmapped mounts in Linux 5.19 and later), integrity-checked images through composefs and fs-verity, and making copy-up cheaper through `metacopy`, and reflink-aware backends. Kernel developers continue to extend overlayfs semantics for rootless use and for lazy data (`overlayfs` with data-only lower layers). On the policy side, SELinux for containers is being refined with `container-selinux` updates, per-workload generated policy (udica), and Kubernetes work to avoid recursive relabelling on volume mount. Questions still open include accurate per-container disk accounting that includes shared layers fairly, quotas on rootless overlay, and safe sharing of one image store among many users.

## Future direction

Expect the containerd snapshotter model to take over from legacy storage drivers (Docker Engine 29 already defaults to it on fresh installs) [web: docs.docker.com], composefs to appear in image-based Linux distributions, and idmapped mounts to replace recursive `chown` in rootless and user-namespaced pods. SELinux handling in Kubernetes will keep reducing relabel overhead, so large volumes mount quickly. For operators, the lasting practice is simple: treat the writable layer as scratch, give every durable path a volume with explicit ownership, record the label strategy per path (`:Z`, `:z`, or a persistent fcontext), and monitor the storage root and log growth as production resources.
