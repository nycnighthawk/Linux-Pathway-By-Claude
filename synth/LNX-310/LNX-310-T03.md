# Podman without a daemon: rootless containers, pods and Quadlet

## Define the problem

The first generation of container tooling put a root-owned daemon between the user and the kernel. Anyone who could talk to its socket could start a privileged container, mount the host filesystem and become root, so access to the Docker group was root access in all but name. The daemon was also a single point of failure: restart it and every container depended on it, unless live restore was enabled. And containers were not part of the host's service model. They lived under the daemon's supervision, outside systemd's dependency ordering, journal and resource accounting, so an operator had two process managers with two restart policies and two logging paths on one machine.

Three needs follow. Ordinary users and CI jobs must be able to build and run containers with no privilege that they do not already have, so that a breakout lands in an unprivileged account. Related containers must be able to share a network identity and lifecycle, in the way Kubernetes pods do, so that a developer can rehearse a pod on a laptop. And a long-lived container must be a first-class system service, started at boot, ordered after its dependencies, restarted on failure and logged to the journal. Podman, with Buildah and Skopeo from the same `containers` project, is the tool that addresses all three on Linux. This slice covers its architecture, the rootless model with its limits, pods, the `kube play` bridge to Kubernetes YAML, and Quadlet, the declarative way of running containers under systemd.

## History and approaches

Podman began in 2017 as `kpod`, a debugging tool for CRI-O, and was renamed when it grew into a full engine. Its guiding idea was a CLI-compatible replacement for Docker with no daemon: each invocation forks the container's monitor, `conmon`, which stays alive as the container's parent and reports the exit code. The storage and image libraries (`containers/storage`, `containers/image`) were shared with CRI-O, Buildah and Skopeo, so images pulled by one tool were visible to the others. Red Hat made Podman the default container engine on RHEL 8, and `alias docker=podman` became a standard migration move. RHEL documentation presents Podman as a daemonless tool whose commands mirror Docker's [src: rhel-10-docs 91df60e5310f33f7].

Rootless operation took years to become comfortable. Early rootless containers relied on `fuse-overlayfs` because kernel overlayfs refused unprivileged mounts until Linux 5.11 and on `slirp4netns`, a user-space TCP/IP stack attached through a tap device, which was slow. Newer kernels allowed native overlayfs in a user namespace, and Podman 5.0 (2024) made `pasta` (from the passt project) the default rootless network backend, sending traffic through a user-space forwarder that maps sockets instead of reimplementing TCP, and keeping the source address of incoming connections, which `slirp4netns` could not [web: podman.io]. Podman 5 also dropped cgroup v1 support and moved to Netavark and Aardvark DNS as the only network stack, retiring CNI (to verify details) [web: github.com].

Integration with systemd went through three stages. First came hand-written unit files that called `podman run` and `podman stop`. Second was `podman generate systemd`, which produced a unit from an existing container; it worked but captured a snapshot of command-line options, so editing meant regenerating, and Podman deprecated it. Third is Quadlet, merged from a separate project into Podman 4.4 (2023). A systemd *generator* reads small declarative files and writes the real units at boot or `daemon-reload`, so the container definition is a configuration file in version control, not a script, and Podman can update how the units are produced without editing every deployment. In parallel, `podman play kube` accepted Kubernetes Pod, Deployment, PersistentVolumeClaim, ConfigMap and Secret YAML, giving a local runner for a subset of manifests.

The approaches that fell short are worth naming. Rootless Docker, available since 20.10, runs the whole daemon in a user namespace but keeps the daemon model, and carries limits such as no AppArmor and a restricted network setup [src: docker-docs 1c7adda4f19a83bf]. Docker Compose files on Podman, through the compatibility socket `podman.socket` and `podman-compose`, mostly work but depend on Docker API details. Kubernetes in a single machine (minikube, kind) gives the full API with a large footprint. Quadlet is the pattern that fits a single host: systemd for lifecycle, containers for packaging.

## Current state

### Architecture

Podman is a Go binary with no resident service. `podman run` pulls the image if missing (via `containers/image`), creates a layer in graph storage, writes an OCI `config.json`, invokes `crun` (default on recent Fedora and RHEL) or `runc`, and starts `conmon`, which keeps stdio, handles the exit file and writes logs. Containers are tracked in a BoltDB or SQLite state database under the user's storage root. Only commands that need to be long-lived have helpers: `podman system service` offers the Docker-compatible REST API on a socket for tools like Compose, `podman-auto-update.timer` checks registries, and `aardvark-dns` serves name resolution on user networks.

Configuration files follow a precedence: `/usr/share/containers/`, then `/etc/containers/`, then `~/.config/containers/`. The three main ones are `containers.conf` (engine defaults, default capabilities, runtime path, network backend), `storage.conf` (driver, graph root, run root), and `registries.conf` (search and mirrors; see topic T06). Rootless users get `~/.local/share/containers/storage` for images and layers and `$XDG_RUNTIME_DIR/containers` for runtime state.

### The rootless model

A rootless container is created by an ordinary account. Podman starts inside a user namespace that maps the invoking UID to container root (UID 0) and maps the rest of the container's IDs to a range of subordinate IDs listed for that account in `/etc/subuid` and `/etc/subgid`, in the format `user:start:count`. The setuid helpers `newuidmap` and `newgidmap` write the mappings, because an unprivileged process may only map its own ID by itself. A typical range is 65536 IDs, enough for the standard distribution image, and the lines can be checked with `podman unshare cat /proc/self/uid_map`. The Rocky and Arch documentation both describe the need for those ranges and give the configuration steps [src: rocky-docs 8c9e91096797f832] [src: archwiki 1510b1b5848f3e0f]. If ranges were added after containers were created, `podman system migrate` makes Podman re-create its pause process so that the new range takes effect.

The consequences are structural and the explanations follow from the namespace rules of topic T01. Files that the container writes in a bind mount appear on the host with ownership of a subordinate UID, so the host user cannot edit them without `podman unshare` to enter the mapping. Two options fix this at mount time. `--userns=keep-id` maps the invoking user to the *same* numeric UID inside, which suits development; `--userns=auto` allocates a distinct slice per container for isolation (root mode only). The volume suffix `:U` asks Podman to `chown` the source to the container user's mapped UID [src: archwiki a3f8907544d10cda]. Images that expect a specific UID work through these mappings.

Rootless limitations come from the same place. Ports below `net.ipv4.ip_unprivileged_port_start` (default 1024) cannot be bound without lowering the sysctl or using a high port and a proxy. ICMP echo needs `net.ipv4.ping_group_range` to include the user's group. Cgroup limits work only if the controller is delegated to the user's systemd slice (`/etc/systemd/system/user@.service.d/delegate.conf` with `Delegate=cpu cpuio memory pids` on older versions; current systemd delegates more by default). Without delegation, `--memory` is ignored with a warning. Rootless cannot create devices, load modules or configure host networking, and mounting new filesystems is limited to what unprivileged user namespaces allow. These limits are the security feature, not a defect.

Linger matters for services. A user's systemd instance stops when the last session ends. `loginctl enable-linger <user>` keeps it running so that rootless containers start at boot and survive logout. Without it, a Quadlet service that works in an interactive test disappears when the SSH session closes.

### Networks and storage

On a user-defined network, containers resolve each other by name through Aardvark DNS. `podman network create` makes a bridge with a subnet, and in rootless mode the bridge lives inside a *rootless network namespace* shared by all the user's containers, with `pasta` forwarding to the outside; published ports are bound by a helper (`rootlessport` or pasta's own forwarding). The default storage driver is `overlay`; on a filesystem without support, `vfs` copies each layer in full and is slow and large. Volumes are directories under the storage root, or named volumes of type `local`; `podman volume create` and `podman volume export` give portable archives.

### Pods

A pod is a group of containers that share namespaces, with an **infra** container (a pause process using the `catatonit` init by default) that holds those namespaces. By default a pod shares the network, IPC, UTS and cgroup parent, while PID sharing is optional, so containers see each other on `localhost`, the same port space and the same hostname. `podman pod create --name web -p 8080:80`, then `podman run -d --pod web nginx` and `podman run -d --pod web redis` places both into one network namespace, and the port mapping is declared on the pod, not on the member. `--share` selects which namespaces are shared. Resource limits can be set at pod level. `podman pod stop` and `podman pod rm` act on all members, and `podman pod ps` and `podman ps --pod` show the relation.

### Kubernetes YAML and `kube play`

`podman generate kube <pod>` writes YAML from a running pod, and `podman kube play file.yaml` creates pods, volumes and configmaps from it; `podman kube down` removes them. This is a deliberate subset of Kubernetes: Services, Ingress, RBAC and scheduling are absent, and probes and security contexts are mapped where there is an equivalent. It is useful for testing a manifest's container-level behaviour and for running a single-node Kubernetes-flavoured stack under systemd with a `.kube` Quadlet file.

### Quadlet

Quadlet is a systemd generator, `podman-system-generator`, invoked by systemd with the unit directories. It scans, for root, `/etc/containers/systemd/` and `/usr/share/containers/systemd/`, and for rootless `~/.config/containers/systemd/` and per-user directories under `/etc/containers/systemd/users/`. Files with the suffixes `.container`, `.pod`, `.volume`, `.network`, `.kube`, `.image` and `.build` become services named from the file: `web.container` becomes `web.service`, `data.volume` becomes `data-volume.service` [src: archwiki 1aff9f8491442ddb]. A first example:

```ini
# ~/.config/containers/systemd/web.container
[Unit]
Description=Static site
After=network-online.target
Wants=network-online.target

[Container]
Image=docker.io/library/nginx:1.27
PublishPort=127.0.0.1:8080:80
Volume=site.volume:/usr/share/nginx/html:ro,Z
Environment=TZ=UTC
ReadOnly=true
NoNewPrivileges=true
DropCapability=ALL
AddCapability=NET_BIND_SERVICE
AutoUpdate=registry
HealthCmd=curl -fs http://localhost/ || exit 1
Notify=healthy

[Service]
Restart=always
TimeoutStartSec=300

[Install]
WantedBy=default.target
```

The `[Container]` keys correspond to `podman run` flags, with the full list in `podman-systemd.unit(5)` [src: man-pages 81dccd4daa6aa1b2]. `[Unit]`, `[Service]` and `[Install]` are ordinary systemd sections, so `Requires=`, `After=`, resource directives like `MemoryMax=`, and `Restart=` are used as for any service. A reference to `site.volume` in `Volume=` creates a dependency on the generated volume service, so ordering is automatic. Pods use a `.pod` file, and each container sets `Pod=web.pod`. A `.kube` file with `Yaml=` runs `kube play` as a unit. `Notify=healthy` delays the "started" state until the health check passes, so dependants only start when the service is actually ready; plain `Notify=conmon` or the default reports success when the container process starts.

The workflow is: write the file; `systemctl --user daemon-reload`; `systemctl --user start web.service`; `systemctl --user status web`; `journalctl --user -u web`. To see what Quadlet generated or why a file produced nothing, run `/usr/lib/systemd/system-generators/podman-system-generator --user --dryrun`, which prints units and any errors. The `[Install]` section is processed by the generator, because generated units are transient: `systemctl enable` does not apply, and the `WantedBy=` line is what causes the unit to be started at login or boot.

Auto-update ties in: with `AutoUpdate=registry`, `podman auto-update` (driven by `podman-auto-update.timer`) pulls a new image for the same tag when its digest changes, restarts the unit, and, if the new container fails its start, rolls back to the previous image. Using `AutoUpdate=local` compares to the local storage for images built on the host.

## Assessment: the good, the bad and the ugly

The good: no daemon to patch, secure or crash; a root-free default; one process manager; drop-in familiarity; consistent with OCI. Quadlet files diff well, can be provisioned by configuration management or by `bootc` image-mode systems (see the RHEL image-mode documentation on shipping Quadlet files in an OS image), and show up in `systemctl list-dependencies`. Rootless gives meaningful defence in depth: even if a container escapes, the attacker is a normal user whose reach is limited by file permissions. Pods and `kube play` shorten the path to Kubernetes.

The bad: parity gaps. Compose features that rely on Docker Engine internals work less well through the compatibility socket; `podman-compose` is a separate Python reimplementation; Docker Swarm is absent. Performance in rootless networking is lower than the kernel bridge, though `pasta` has narrowed it. Debuggability changes: there is no single daemon log, so you look at `journalctl`, `conmon` processes, and the user's own storage. Per-user storage means ten users pulling one image store ten copies unless an additional image store is shared read-only.

The ugly: systemd and the user session. Forgetting `enable-linger`; `XDG_RUNTIME_DIR` unset in `su` or `sudo -u` shells so that `systemctl --user` reports "Failed to connect to bus"; stale `/run/user/<uid>` pause processes; and SELinux. On Fedora and RHEL a bind mount of a host path into a container is denied unless relabelled: `:Z` gives the content a private label for that container, `:z` a shared label for several; using `:Z` on a shared directory such as the user's home directory relabels everything beneath it and can break other services. Quadlet's own failure mode is silence: a typo in a key may be ignored by the generator and surface only in dry-run output, and a unit that depends on a `.network` file must reference it with the correct suffix. Auto-update with a floating tag turns an upstream mistake into your outage; pin the digest or the minor tag when stability matters more than freshness.

Two security issues deserve mention. Rootless does not remove kernel attack surface: a user namespace exposes code paths otherwise root-only, and some distributions restrict unprivileged user namespaces, which silently disables rootless mode. Second, the Podman project has published a steady flow of security fixes for archive extraction and volume symlink handling in recent releases, which shows the importance of updating the engine, not only the images [web: github.com].

## Applications beyond this domain

The same declarative-unit pattern is useful for any single host: edge devices, home servers and appliances, where Kubernetes is too large. `bootc` and image-mode operating systems embed Quadlet files in the image so the machine boots straight into its workload [src: rhel-10-docs 5317b08911c5100f]. Rootless Podman is the base of toolbox and Distrobox, which give a mutable development environment on immutable desktops such as Fedora Silverblue. In CI, rootless Buildah and Podman inside an unprivileged pod or job container allow image builds without a privileged runner. HPC sites and universities use the same user-namespace approach (Apptainer, Charliecloud) so that researchers bring their own stack. Outside the Linux world, the idea that a service manager should treat a sandboxed workload as a normal unit has analogues in Windows services running as containers and in FreeBSD jails managed by `rc`.

## Examples

*A first rootless container.* `podman run --rm -it docker.io/library/alpine id` prints `uid=0(root)`, and `ps -o user,pid,cmd -C sleep` on the host, with a long-running `sleep` instead, shows the process owned by the real user. `podman unshare ls -ln ~/.local/share/containers/storage` shows what the files look like from inside the mapping.

*A pod with a sidecar, then Quadlet.* `podman pod create -p 8080:80 --name app`; run an application container and a log shipper in it; `podman generate kube app > app.yaml` captures it; `podman kube play app.yaml` reproduces it elsewhere. To promote it to a service, place `app.kube` with `Yaml=app.yaml` and `[Install] WantedBy=default.target` into `~/.config/containers/systemd/`, run `daemon-reload`, and start `app.service`.

*A failing example: bind-mount permissions.* A developer mounts `./data` into a PostgreSQL container, and the container logs "permission denied" writing to the data directory, as the database runs as UID 999 inside, which maps to a subordinate ID outside, but `./data` is owned by the developer's own UID. Three repairs exist: `podman unshare chown 999:999 ./data`, the `:U` mount option, or a named volume where Podman handles ownership. On Fedora, the next error is an SELinux denial that `ausearch -m avc` shows, cured by `:Z`.

*Another failure: a service that vanishes.* A Quadlet container works from an SSH session and disappears hours after logout. `loginctl show-user $USER --property=Linger` returns `Linger=no`; `loginctl enable-linger` fixes it and the container returns at the next reboot.

*Dry run diagnostics.* A `.container` file with `Image=` missing yields no service; the generator's dry run prints a line such as a missing key error, and the unit is absent from `systemctl list-unit-files`.

## Related problems and ideas

The same needs lead elsewhere. Docker's rootless mode, `nerdctl` with rootless containerd, and Buildah's rootless builds overlap in capability. systemd's own `systemd-nspawn` and portable services run image-based services without OCI. Kubernetes distributions for a single node (k3s, MicroShift) trade footprint for the full API. Nomad and Docker Compose with systemd units are the alternatives for small fleets. Podman Desktop and `podman machine` extend the model to macOS and Windows by running a Linux VM. Ideas not yet mainstream include Quadlet-style generators for orchestration of multiple hosts through Ansible or `bootc` fleets, GitOps for single nodes using `podman auto-update` with signed images, and kernel-supported ID-mapped mounts that remove the need for recursive `chown`.

## Active research

Work in this area includes lowering the cost of rootless networking, since pasta is fast but still copies data through user space; making user-namespace creation safer, with LSM hooks that distinguish trusted callers from arbitrary processes; and improving storage sharing, for example additional image stores and composefs, which presents layers as a content-addressed read-only tree with an overlay on top so that identical files are shared on disk and verified by fs-verity. Podman release notes show steady work on checkpoint and restore with CRIU, on `podman machine` providers (WSL and Apple's virtualisation), on Quadlet keys (recent versions added `Umask`, `SetMountsDependency` and more) and on supply-chain checks [web: github.com]. Open questions include how to express multi-container dependencies and secrets in Quadlet without recreating Compose, and how far `kube play` should follow Kubernetes semantics.

## Future direction

Podman 6.x continues the 5.x line, which settled pasta, Netavark and SQLite state; the current stable releases are in the 6.2 series with parallel 5.8 security releases (to verify) [web: github.com]. Expect Quadlet to be the recommended way to run containers as services on RHEL-family systems, with further keys for builds and image pulls (`.build`, `.image` already exist), tighter `bootc` integration, and better tooling around `podlet` conversions from `podman run` commands [src: archwiki 1aff9f8491442ddb]. Rootless operation is expected to be the default for developer workflows and CI. For practitioners, the durable skills are the mapping model (`/etc/subuid`, `keep-id`, `:U`), the systemd user-instance rules (linger, `XDG_RUNTIME_DIR`), and reading generator output.
