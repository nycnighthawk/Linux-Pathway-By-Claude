# A container is a process: namespaces, cgroups v2 and capabilities by hand

## Define the problem

Operators want to run many programs on one kernel and have each behave as if it owned the machine: its own process tree, its own network stack, its own hostname and mount table, a bounded share of CPU and memory, and no power to harm its neighbours or the host. Virtual machines deliver that by emulating hardware and booting a second kernel per workload, which costs minutes of start time and hundreds of megabytes of memory. Plain Unix users and `chroot` deliver almost none of it. The gap is a way to give an ordinary process a private view of kernel resources and a hard budget, at the price of a process rather than a machine.

The Linux answer has no single "container" object. It is a recipe built from three independent kernel facilities. Namespaces change what a process can see. Control groups (cgroups) change how much it may consume. Capabilities, together with seccomp filters and mandatory access control, change what it may do. A container runtime is a program that applies those three, plus a root filesystem, to a process and then gets out of the way. Anyone who has debugged a container that will not start, leaks memory, or is able to read host files needs to hold this model, because every symptom maps to one of the three layers.

This slice builds that model from the bottom. It covers the namespace types and the system calls that create and enter them, the cgroup v2 hierarchy and its controllers, the capability sets and the interaction with user namespaces, and a hand-made container assembled from shell tools. Image formats, runtimes and orchestration come later in the course.

## History and approaches

Isolation began with `chroot` (Unix V7, 1979), which changes the apparent root directory and nothing else; a root process escapes it with a few lines of code, so it was a build convenience, not a boundary. FreeBSD jails (2000) added a separate process and network view per jail, and Solaris Zones (2004) added resource controls and brand support. Both were designed as whole-system features, which is why they were coherent but also why they arrived in the Linux world only as ideas.

Linux grew the pieces separately. Mount namespaces appeared in 2002 (kernel 2.4.19), then UTS and IPC namespaces (2.6.19, 2006), PID and network namespaces (2.6.24, 2008), user namespaces in a usable form (3.8, 2013), cgroup namespaces (4.6, 2016) and time namespaces (5.6, 2020). Each was designed by a different person for a different reason, and each could be used alone. Google contributed the original "process containers", renamed cgroups, in 2.6.24. Early products assembled the parts: OpenVZ and Linux-VServer shipped out-of-tree patches, and LXC (2008) was the first mainstream userspace tool to combine mainline namespaces and cgroups, using configuration files such as `lxc.cgroup2.devices.allow` to program the device controller [src: man-pages 2675e47be3e7113d]. LXC was powerful but pitched as a lightweight VM, with an init system inside.

Docker (2013) changed the audience, not the kernel features. It added a layered image format, a registry and a one-command developer workflow, and it treated a container as one application process instead of a small server. systemd-nspawn, rkt, and later Podman, CRI-O and containerd approached the same kernel interfaces with different management philosophies [src: archwiki aac1d8c540ceecce].

The partial successes taught hard lessons. cgroups v1 let each controller keep its own tree, so a process could be in different groups for memory and for CPU. Writing a tool that agreed on which container owns a process was painful, and the interaction between memory and writeback accounting was wrong because the two controllers could not see each other. Delegation to unprivileged users was unsafe. Capabilities, introduced in Linux 2.2 to split root into pieces, tended to collapse in practice: `CAP_SYS_ADMIN` became a catch-all, so granting it handed over nearly everything. Early containers also ran as real root on the host, and a breakout was a root compromise.

The pattern that emerged: use unprivileged user namespaces so that "root in the container" is an unprivileged UID outside; use one unified cgroup hierarchy (cgroup v2, declared stable in Linux 4.5 and the default in major distributions from about 2021) with a single writer, usually systemd; keep a short default capability list; and add a syscall filter. Kubernetes dropped dockershim and standardised on runtimes that speak CRI and run OCI bundles [src: kubernetes-docs 1bcce9f39a66dcce].

## Current state

### Namespaces

A namespace wraps one global kernel resource so that members of the namespace see an independent instance. Each process has one namespace of every type, visible as links under `/proc/<pid>/ns/` whose inode numbers identify the instance. Two processes share a namespace exactly when the links show the same inode.

| Type | Flag | Isolates |
|---|---|---|
| mount | `CLONE_NEWNS` | mount points and propagation |
| UTS | `CLONE_NEWUTS` | hostname and NIS domain |
| IPC | `CLONE_NEWIPC` | System V IPC and POSIX queues |
| PID | `CLONE_NEWPID` | process ID numbering |
| network | `CLONE_NEWNET` | interfaces, routes, firewall, sockets |
| user | `CLONE_NEWUSER` | UID/GID mappings and capability scope |
| cgroup | `CLONE_NEWCGROUP` | the view of the cgroup tree root |
| time | `CLONE_NEWTIME` | boot and monotonic clock offsets |

Three system calls do the work. `clone`/`clone3` creates a child in new namespaces, `unshare` moves the caller into new ones, and `setns` joins a process to an existing namespace through an open file descriptor from `/proc/<pid>/ns/`. The shell front ends are `unshare(1)`, `nsenter(1)` and `lsns(8)`. Some details deserve attention. A PID namespace takes effect for children, not the caller, which is why `unshare --pid` needs `--fork`; the first child becomes PID 1 and, as init of that namespace, gets special signal semantics: signals with default handlers are ignored unless it installs handlers, and when it exits the kernel kills every other member. A mount namespace starts as a copy of the parent's table, and on systemd hosts the root mount is `shared`, so mounts made inside would propagate back out; `unshare --mount` therefore makes the tree private by default and a runtime does `mount --make-rprivate /`. A network namespace begins with only a down loopback interface; a virtual Ethernet pair (`ip link add veth0 type veth peer name veth1`) with one end moved by `ip link set veth1 netns <ns>` is the classic way to connect it. A user namespace lets an unprivileged process obtain a full set of capabilities inside the namespace, with all permission checks on objects owned by that namespace evaluated against the mapping in `/proc/<pid>/uid_map`, whose lines read "inside-ID outside-ID length".

User namespaces own all other namespaces. A non-root process may create a user namespace and, within it, any other type, because the new capabilities are scoped to resources the user namespace owns. That single rule is what makes rootless containers possible. The same rule is also an attack surface: several kernel privilege escalations were reached by creating a user namespace and then exercising code paths that had previously been reachable only by root. Distributions respond with sysctls, for example `kernel.unprivileged_userns_clone` on Debian-family kernels, `user.max_user_namespaces` on RHEL-family ones, and in Ubuntu 23.10 and later an AppArmor restriction on unprivileged user namespace creation (to verify exact releases).

### Control groups v2

In cgroup v2 there is one tree, normally mounted at `/sys/fs/cgroup` as type `cgroup2`. Every process belongs to exactly one cgroup, shown in `/proc/<pid>/cgroup` as a line starting `0::`. Resource distribution follows a rule that is easy to state and easy to trip over: a controller must be enabled for children through the parent's `cgroup.subtree_control`, and a cgroup that has member processes cannot enable controllers for children (the "no internal process" constraint, which does not apply to the root). So a manager places processes only in leaves, and the interior nodes are pure resource allocators.

The common controller files are worth knowing exactly:

- `memory.max` is a hard limit; exceeding it triggers reclaim and then the OOM killer for that cgroup. `memory.high` is a throttle: allocation above it is slowed by reclaim, but nothing is killed. `memory.low` and `memory.min` protect memory from reclaim. `memory.swap.max` bounds swap, `memory.events` counts `oom` and `oom_kill` occurrences, and `memory.oom.group` makes the OOM kill take the whole group.
- `cpu.max` holds "quota period" in microseconds, for example `50000 100000` for half a core, or `max 100000` for unlimited. `cpu.weight` (1 to 10000, default 100) divides contested CPU proportionally. `cpu.stat` reports `nr_throttled` and `throttled_usec`, the first thing to read when a container with a quota is slow while the host is idle.
- `io.max` sets per-device caps as `MAJ:MIN rbps=... wbps=... riops=... wiops=...`; `io.weight` shares proportionally where the scheduler supports it.
- `pids.max` caps the number of tasks and is the defence against fork bombs.
- `cpuset.cpus` and `cpuset.mems` pin placement.
- `cgroup.freeze` freezes every task in a group, and `cgroup.kill` (Linux 5.14) kills them all atomically, which solves the old race of killing a group while it forks.

Delegation is the other half. A privileged manager can hand a subtree to an unprivileged user by changing ownership of the directory and the files `cgroup.procs`, `cgroup.subtree_control` and `cgroup.threads`. The user can then create descendants and move processes among them, but cannot exceed the parent's limits. systemd implements this with `Delegate=yes`, and rootless Podman relies on it. A container runtime picks a cgroup driver: with `systemd` it asks PID 1 for a transient scope or slice and lets systemd write the files, and with `cgroupfs` it writes the files itself. Mixing the two on one host produces two managers fighting over the same tree, a classic source of limits that silently disappear; the kubelet and its runtime must agree [src: archwiki 6fcf9bded3e264ad].

The cgroup namespace hides the position of a container in the host tree: inside it, `/proc/self/cgroup` shows `0::/` and the mounted view is rooted at the container's own group. This stops leaking host paths and prevents a process from walking upward.

### Capabilities, seccomp and LSMs

Root's traditional all-powerful status is divided into around forty capabilities, listed in `capabilities(7)`: `CAP_NET_BIND_SERVICE` to bind ports below 1024, `CAP_NET_ADMIN` for interface and firewall control, `CAP_SYS_ADMIN` (the large leftover), `CAP_SYS_PTRACE`, `CAP_CHOWN`, `CAP_DAC_OVERRIDE`, `CAP_SETUID`, `CAP_MKNOD`, `CAP_SYS_MODULE`, and so on [src: man-pages c34d5b261a4430d9]. Each thread carries five sets. The *effective* set is what the kernel checks. *Permitted* is the ceiling for effective. *Inheritable* governs what survives `execve` together with file capabilities. The *bounding* set limits what any execve can ever gain. The *ambient* set (Linux 4.3) lets an unprivileged program pass capabilities to a child without file capabilities. A runtime drops the bounding set to a short list; Docker's default list is 14 entries, including `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `KILL`, `NET_BIND_SERVICE`, `SETGID`, `SETUID`, `SETPCAP` and `SYS_CHROOT`, while `SYS_ADMIN`, `NET_ADMIN`, `SYS_MODULE` and `SYS_PTRACE` are absent (to verify the exact list per runtime version). `no_new_privs`, set with `prctl(PR_SET_NO_NEW_PRIVS)`, blocks setuid binaries and file capabilities from raising privilege and is a prerequisite for unprivileged seccomp filters.

Seccomp mode 2 attaches a BPF program that inspects the syscall number and arguments and answers with allow, errno, trap, kill, log or notify to a supervisor. Docker's default profile allows most syscalls and denies a few hundred dangerous or obsolete ones, such as `mount` without the right capability, `keyctl`, `bpf`, `kexec_load` and `ptrace` on older kernels [src: docker-docs b6a7b2e8af2d69d4]. AppArmor or SELinux adds path- or label-based rules that do not depend on UID. All three layers are independent: a process may have `CAP_SYS_ADMIN` yet fail `mount` because seccomp denies it.

### Building one by hand

A minimal container uses nothing but util-linux, iproute2 and a root filesystem. Take any extracted rootfs, for example from `debootstrap`, or from `podman export` of a stopped container, into `/srv/rootfs`.

```bash
# 1. a cgroup with budgets (needs root, systemd hosts: use a transient slice if you prefer)
sudo mkdir /sys/fs/cgroup/demo
echo "+memory +pids +cpu" | sudo tee /sys/fs/cgroup/cgroup.subtree_control >/dev/null  # may already be on
echo 100M  | sudo tee /sys/fs/cgroup/demo/memory.max
echo 64    | sudo tee /sys/fs/cgroup/demo/pids.max
echo "20000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max
# 2. namespaces, then confine the new root
sudo sh -c 'echo $$ > /sys/fs/cgroup/demo/cgroup.procs; exec unshare --pid --fork --mount --uts --ipc --net \
  --mount-proc=/srv/rootfs/proc chroot /srv/rootfs /bin/sh'
```

Even this toy exhibits the real structure. Production runtimes replace `chroot` with `pivot_root`, which moves the old root away and unmounts it so that no handle to it survives; they mount `/proc`, `/sys` (read-only), `/dev` as a tmpfs with a small whitelist of device nodes, mask paths such as `/proc/kcore` and `/proc/sysrq-trigger`, drop capabilities, set `no_new_privs`, install the seccomp program, and finally `execve` the user command. The OCI runtime specification encodes exactly this list [src: kubernetes-docs 5efa4faf20f519de]. For rootless, the sequence starts with `unshare --user --map-root-user`, or `newuidmap` and `newgidmap` helpers writing a range from `/etc/subuid`, so that a single account owns thousands of IDs inside.

## Assessment: the good, the bad and the ugly

The good: start in milliseconds, memory cost of a process, density limited by the kernel instead of by hypervisor overhead. Each control is orthogonal and inspectable with ordinary tools. A runtime is thin: `runc` is a small Go program plus a C stub. The same primitives serve systemd services, browsers (Chromium's sandbox uses namespaces and seccomp), Flatpak and build sandboxes.

The bad: the isolation boundary is the shared kernel. Every container can reach the same syscall surface, and one kernel bug is a boundary failure for all tenants. NIST SP 800-190 lists this first among host-OS risks and recommends, for mixed trust levels, either host separation or a stronger sandbox [src: nist-sp800-guides c5a04d9f3ceb0a33]. Isolation is also incomplete by construction. `/proc/meminfo`, `/proc/cpuinfo`, `uptime` and `nproc` show host values unless a tool such as lxcfs rewrites them, so JVMs and thread pools historically sized themselves to the host, not the cgroup. The kernel keyring, the clock (until time namespaces, partially), kernel log buffer, sysctls that are global, `/sys` entries and loaded modules are shared. Container UID 0 without a user namespace is UID 0 on the host for file ownership purposes.

The ugly: privilege flags. `--privileged` removes the capability, seccomp and device restrictions in one switch, and mounting the Docker socket into a container gives that container root on the host through the daemon API. Misconfiguration beats clever escapes in the field. Known engine-level breakouts, such as the `runc` `/proc/self/exe` overwrite (CVE-2019-5736), show that the runtime itself is part of the boundary; the fix was to re-execute through a sealed memory copy of the binary. Writable cgroup `release_agent` files in v1 gave another family of escapes (CVE-2022-0492) and were one reason v2 removed the feature. Rootless modes have their own limits: no binding below 1024 without a sysctl change, no cgroup limits unless delegation is configured, no `ping` on older kernels without a group range for `ping_group_range`, and slower networking via user-space helpers [src: docker-docs 1c7adda4f19a83bf]. Memory accounting also confuses people: page cache counts against `memory.max`, so a container with heavy file reads may sit near its limit with no leak, and `memory.current` is not the same as the working set operators want.

Operationally, the most frequent real-world failures are cgroup mismatches (limits set by one manager and reset by another), kernels that lack a controller (for example swap accounting disabled by default on some distributions until `swapaccount=1`, or `cpu` controller missing from `subtree_control` for realtime tasks), and unexpected OOM kills at the group boundary while the host has plenty of free memory.

## Applications beyond this domain

The same three layers appear wherever one machine runs code of unequal trust. systemd service sandboxing exposes them as unit options: `PrivateTmp=`, `PrivateNetwork=`, `ProtectSystem=`, `MemoryMax=`, `TasksMax=`, `CapabilityBoundingSet=`, `SystemCallFilter=` and `NoNewPrivileges=`; `systemd-analyze security` scores a unit by how many are used. Browsers sandbox renderers with user and PID namespaces plus seccomp. Flatpak and Snap run desktop applications in a mount namespace with portals for controlled access, and CI systems run each job in a throwaway namespace. HPC sites use Apptainer and Singularity with user namespaces so that scientists bring their own software without root. Android uses UID-per-app, seccomp and SELinux, which is the capability-and-LSM layer without namespaces. Outside Linux, FreeBSD jails, Solaris zones and Windows job objects with silos implement comparable bundles, which is a useful comparison when judging what is essential: a private view, a budget, and a bounded rights set.

## Examples

*Seeing the invariants.* Run `lsns -t pid`, start a container, and run it again: a new inode appears. From the host, `ls -l /proc/$(pgrep -n sleep)/ns/` shows the namespace inodes of the container's process; `nsenter -t <pid> -n ip addr` runs a host tool in the container's network namespace without any tool installed inside the image. `cat /proc/<pid>/cgroup` yields a path such as `0::/system.slice/docker-<id>.scope`, from which the limit files are one `cat` away.

*A memory limit at work.* With `memory.max` at 100 MiB and a program that allocates 200 MiB, `memory.events` shows `max` counts rising, then `oom_kill 1`, and the process dies with SIGKILL, exit code 137 as seen by a runtime. Setting `memory.high` to 80 MiB instead makes the same program slow but alive, because reclaim throttles it. The lesson is the difference between a throttle and a kill.

*A failing example.* A team sets `--cpus=1` on a latency-sensitive service and sees p99 spikes though host CPU is 20 percent used. `cpu.stat` shows `nr_throttled` rising: a multi-threaded service burst past the 100 ms quota in the first 10 ms and was frozen for the rest of the period. The remedy is a larger quota, a `cpu.weight` share instead of a hard cap, or fewer worker threads; the cause was a quota that is invisible from host-level CPU graphs.

*A capability trap.* A web server in a container needs to bind port 80 as a non-root user. Granting `CAP_NET_BIND_SERVICE` alone is the narrow fix; the shortcut `--privileged` works too, and also lets the process load kernel modules. A review that reads `capsh --print` inside the container, or `grep Cap /proc/<pid>/status` decoded with `capsh --decode=`, reveals which fix was applied.

*A rootless surprise.* `unshare --user --map-root-user id` prints `uid=0(root)`, yet `touch /etc/x` fails with "Permission denied". Inside the namespace the process is root, but the file is owned by the real root, which is unmapped there and shows as `nobody`. Understanding this explains both the safety of the model and why bind-mounted host directories arrive with odd ownership in rootless containers.

## Related problems and ideas

Whole-system virtualisation (KVM, covered elsewhere in the pathway) is the contrasting design: stronger isolation at the cost of a second kernel. Between the two sit sandboxed runtimes such as gVisor and Kata, covered later in this course, which accept some overhead to shrink what the shared kernel exposes. System containers (LXC, Incus, systemd-nspawn) keep the namespace model but run a full init. `chroot`-based tools remain useful for repairs and build roots. Alternatives to seccomp filters include Landlock (Linux 5.13), which lets an unprivileged process restrict its own filesystem and later network access with a ruleset it writes, and pledge/unveil on OpenBSD, which expresses a similar policy as promises. Resource accounting that tracks container-level memory and I/O more faithfully is the ongoing work around PSI (pressure stall information) files such as `memory.pressure`, which report time lost to contention and let userspace agents like systemd-oomd or `oomd` act before the kernel does.

## Active research

Kernel work in this area is mostly about shrinking trust and closing accounting gaps. ID-mapped mounts (5.12) let a mount present ownership translated through a user namespace, removing the need to recursively `chown` image layers for rootless and user-namespaced pods. The Kubernetes user namespace support for pods graduated in recent releases and makes container root an unprivileged host UID by default where enabled [src: kubernetes-docs 9d591ba077abacb2]. Open problems include kernel memory accounting that follows slab objects across cgroups, fair block I/O control on multi-queue NVMe, the cost of per-container BPF programs, and how to give containers a true view of their own limits through `/proc` without helper filesystems. Security researchers continue to look for escapes through new syscalls such as `io_uring`, which some sandboxes and distributions disable for unprivileged containers. Another research thread asks whether the namespace set is the right decomposition at all: proposals for a "container" object, or Landlock-like capabilities at object level, resurface periodically.

## Future direction

Expect cgroup v1 to leave the supported matrix: Docker Engine 29 marks it deprecated with support continuing until at least May 2029 [web: docs.docker.com], and current RHEL, Ubuntu and Fedora releases boot to v2 only or by default. Rootless-by-default is the direction for desktops and CI, helped by pasta and newer unprivileged networking helpers. The OCI runtime specification continues to add namespaces and kernel features as runtimes need them; version 1.3 added items such as network devices and memory policy objects, and a FreeBSD section (to verify details) [web: github.com]. Watch for time-namespace adoption by checkpointing tools, wider use of idmapped mounts, and Landlock-based default policies. The practical advice for the next several years is stable: understand the three layers, prefer user namespaces over privileges, let systemd own the cgroup tree, and treat a shared-kernel container as defence in depth rather than a hard tenant boundary.
