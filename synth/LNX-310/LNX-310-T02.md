# The OCI contract and the runtime stack beneath Docker and Kubernetes

## Define the problem

Once containers became popular, three kinds of parties needed to cooperate without knowing one another. Image authors wanted to build once and have any engine run the result. Registries wanted to store and serve content without understanding what it meant. Orchestrators wanted to start thousands of containers through one interface, regardless of whether the machinery below was Docker, containerd or something else. In 2014 there was no such agreement: Docker's image format, Docker's runtime behaviour and Docker's API were one bundle controlled by one company, rival formats (appc and rkt) were gaining followers, and Kubernetes embedded Docker-specific code in its node agent.

The problem is to define narrow, testable interfaces at the three seams of the stack: what an image is on disk and on the wire, how a prepared directory plus a configuration becomes a running isolated process, and how a node agent asks a daemon to pull images and run pods. Done well, the seams allow runtimes to be swapped, a hardened runtime to be selected per workload, and a registry to hold images from any tool. This slice covers the Open Container Initiative (OCI) image, runtime and distribution specifications, the Kubernetes Container Runtime Interface (CRI), and the runtimes that implement them: runc and crun at the bottom, containerd and CRI-O in the middle. It stops short of the image-building and registry operations that later topics treat.

## History and approaches

Docker's first releases (2013) drove LXC through its CLI, then replaced it with `libcontainer`, a Go library calling the kernel directly. Docker's image format v1 stacked layers by a parent-pointer chain with a JSON file per layer, and v2 (2014 to 2015) moved to content-addressed manifests and a registry API with digests, which fixed several integrity and concurrency problems of v1. CoreOS announced the App Container (appc) spec and `rkt` in December 2014, offering a daemonless alternative and a signed image format. The community feared a format war, and in June 2015 Docker, CoreOS, Google, Red Hat and others founded the Open Container Project, soon renamed the Open Container Initiative under the Linux Foundation. Docker donated its runtime code, which became `runc`, and its v2 image format, which became the basis of the OCI image spec. The runtime spec 1.0 and image spec 1.0 were released in July 2017, and the distribution spec 1.0 in 2021 [web: opencontainers.org].

Meanwhile the daemon was being split. Docker 1.11 (2016) factored the engine into `dockerd`, `containerd` and `runc`, and Docker later donated `containerd` to the CNCF, where it graduated in 2019 (to verify date). On the Kubernetes side, the kubelet originally linked Docker's client directly; rkt support was patched in separately, and the maintenance cost led to the Container Runtime Interface in Kubernetes 1.5 (2016), a gRPC API with an image service and a runtime service. Red Hat built CRI-O as a minimal CRI implementation that does only what Kubernetes needs, and containerd gained a CRI plugin. The `dockershim` adapter, which kept Docker Engine usable as a CRI runtime, was deprecated in Kubernetes 1.20 and removed in 1.24 [src: kubernetes-docs 1bcce9f39a66dcce]. Docker-built images still work, since they follow the OCI format; what ended was the Docker daemon as the kubelet's runtime.

The approaches that did not become the default are instructive. The appc spec was archived in favour of OCI and `rkt` ended as a project. LXC and libvirt-lxc remained for system containers [src: libvirt-docs 1d18a6ba3ebc32e3]. Docker's schema 1 manifests, which carried signatures in the manifest itself, were deprecated for being mutable and hard to validate. Alternative low-level runtimes arrived to address runc's weak points: `crun` (C, Red Hat, 2017 onward), faster to start and lighter in memory than a Go binary with a multithreaded runtime; `youki` (Rust); and sandboxed runtimes (Kata, gVisor) that implement the same OCI command interface while placing the workload behind a VM or user-space kernel. The emerging pattern is a stack of narrow, replaceable layers joined by specs and by a shim protocol.

## Current state

### The three OCI specifications

The **image specification** defines four artefacts. A *layer* is a tar archive (optionally compressed with gzip or zstd) describing a filesystem changeset against the previous layer: added or modified files appear normally, and deletion is expressed by a *whiteout* entry named `.wh.<name>`, with `.wh..wh..opq` marking an opaque directory that hides all lower content. An *image configuration* is JSON that holds the target architecture and OS, the `rootfs.diff_ids` (digests of the *uncompressed* layers), default `Cmd`, `Entrypoint`, `Env`, `User`, `WorkingDir`, `ExposedPorts`, `Volumes` and `Labels`, and a `history` array of build steps. A *manifest* lists the config blob and the ordered layer blobs, each as a descriptor holding `mediaType`, `digest` and `size`; an optional `subject` field links an artefact such as a signature to the image it describes, and `artifactType` distinguishes non-image artefacts. An *image index* maps platforms to manifests, which is how one tag serves `linux/amd64`, `linux/arm64` and others. Every blob is addressed by a digest such as `sha256:...`, so any holder can verify what they have received, and a tag is merely a mutable pointer to a digest. The layout on disk, `oci-layout` plus `index.json` plus `blobs/sha256/`, allows an image to be moved without a registry (`skopeo copy oci:dir:tag`).

The **distribution specification** standardises the HTTP API shared by Docker Hub, Quay, GHCR, Harbor and others: `GET /v2/<name>/manifests/<ref>`, `GET /v2/<name>/blobs/<digest>`, chunked or monolithic uploads under `/blobs/uploads/`, `GET /v2/<name>/tags/list`, and the referrers endpoint added in version 1.1 for listing artefacts that point at a subject. Because the registry sees only digests and media types, signatures, SBOMs and Helm charts can all be stored beside images.

The **runtime specification** describes a *filesystem bundle*: a directory holding a root filesystem and `config.json`. The config has `ociVersion`, `process` (args, env, cwd, user, capability sets, `noNewPrivileges`, rlimits), `root` (path, `readonly`), `mounts`, `hooks`, `annotations`, and a `linux` object that carries namespaces to create or join, UID/GID mappings, `cgroupsPath`, `resources` (memory, cpu, pids, block I/O, devices), `seccomp`, `maskedPaths`, `readonlyPaths`, `sysctl`, `rootfsPropagation` and `intelRdt`. The runtime is also specified as a command line and lifecycle: `create` builds the namespaces and mounts and leaves the user process waiting, `start` releases it, `kill` sends a signal, `delete` removes resources, and `state` prints JSON with `ociVersion`, `id`, `status` (`creating`, `created`, `running`, `stopped`), `pid` and `bundle`. Hooks (`createRuntime`, `createContainer`, `startContainer`, `poststart`, `poststop`) let outside tooling, for example a CNI plugin invoker or a GPU driver injector, act at defined points; since 1.3 a failing `poststart` hook makes the runtime fail (to verify the version) [web: github.com]. Version 1.1 added cgroup v2 support, time namespaces and seccomp notification, and 1.2 added ID-mapped mount options [web: github.com].

### Low-level runtimes: runc and crun

`runc` reads the bundle, forks into new namespaces, sets up the mounts, `pivot_root`s, applies cgroup limits, capabilities, seccomp and AppArmor or SELinux labels, and `execve`s the process. Its `runc init` stub re-executes itself from a sealed memory copy to defend against overwrites of its own binary. It is the reference implementation, the default in Docker, containerd and most CRI-O installs. `crun` implements the same bundle semantics in C, links `libcap`, `libseccomp` and `libsystemd` directly, and is the default in Podman on Fedora and RHEL. Its advertised benefits are smaller memory footprint, about half the container-start time in published benchmarks (to verify), and optional support for running WebAssembly modules through `libkrun` or WasmEdge handlers. The `runtime-tools` validation suite and the `oci-runtime` conformance tests are how third parties check compliance. Both runtimes take the same CLI form, so `podman --runtime /usr/bin/runc` and `docker run --runtime=runc` are practical comparisons on one host [src: archwiki 905535a824c69608].

### High-level runtimes: containerd and CRI-O

`containerd` is a daemon that manages the complete container lifecycle on one host through a gRPC API. Its major parts are the *content store* (blobs by digest), the *metadata* database, *snapshotters* (`overlayfs`, `native`, `btrfs`, `zfs`, and lazy-pulling ones such as `stargz` and `nydus`) which prepare the root filesystem from layers, the *runtime* layer, and *plugins* (CRI, image service, transfer service). For each container it launches a **shim**: a small long-running process, speaking the `containerd.runtime.v2` protocol over a ttrpc socket, which stays between containerd and the container. Shim v2 is a deliberate seam. `containerd-shim-runc-v2` runs runc; `containerd-shim-kata-v2` and `containerd-shim-runsc-v1` plug sandboxed runtimes into the same interface; one shim serves every container of a pod, so a pod of ten containers costs one shim and not ten. Because the shim, not the daemon, is the container's parent, `containerd` can be restarted without killing workloads. Docker Engine delegates to containerd; recent releases made the containerd image store the default for fresh installs, so images live in containerd's content store [web: docs.docker.com]. The Docker documentation lists the `runc` and `containerd` shims and describes how to register extra runtimes in `daemon.json` [src: docker-docs e3d428b952542088].

`CRI-O` is a CRI-only runtime designed so that its release number tracks the Kubernetes minor version. It uses `containers/image` and `containers/storage` libraries (shared with Podman, Buildah and Skopeo) for pulls and layers, `conmon` (or its Rust successor `conmon-rs`) as the per-container monitor, and the OCI runtime selected through a handler table in `crio.conf` [src: archwiki 4d3972d86827a9fc]. Kubernetes `RuntimeClass` objects name a handler, so a cluster can offer `runc` and a Kata handler side by side [src: kubernetes-docs 51bddeba8d44d9a6].

### The CRI

CRI is two gRPC services defined in a protobuf file. `RuntimeService` creates and stops pod sandboxes (`RunPodSandbox`, `StopPodSandbox`), creates, starts and stops containers inside them, runs `ExecSync`, streams `Exec`, `Attach` and `PortForward`, and reports status and stats. `ImageService` lists, pulls and removes images. The kubelet owns policy, such as probe schedules, restarts and eviction; the runtime owns mechanics. CNI plugins attach the sandbox network namespace that the runtime creates. For debugging at this layer `crictl` speaks CRI directly (`crictl ps`, `crictl pods`, `crictl images`, `crictl logs`, `crictl inspect`), and the pod-level object, the sandbox, is typically a "pause" container that holds the shared namespaces for the pod, which also reaps zombies as PID 1 when the pod shares a PID namespace.

### A generalised picture

```
kubelet / docker CLI / nerdctl / podman
        | gRPC (CRI) or REST (Engine API)
  containerd or CRI-O   (images, snapshots, sandboxes)
        | ttrpc (shim v2) or fork/exec of conmon
  shim / conmon          (parent of the container, keeps stdio, reports exit)
        | exec of the OCI command line
  runc / crun / runsc / kata-runtime
        | clone, mount, cgroups, seccomp
  kernel
```

Every arrow is a specification or a protocol, and every box can be replaced. The cost is more processes to inspect when something fails, which Topic T09 addresses.

## Assessment: the good, the bad and the ugly

The good: images built by Docker, Buildah, Kaniko or BuildKit run on containerd, CRI-O and Podman; a registry that implements the distribution spec stores all of them; digests give integrity and cache keys; the shim model lets runtimes evolve independently; and conformance tests keep implementers honest. The `config.json` is plain data, so a bundle can be generated, diffed and reviewed in a pull request. Switching a node from runc to crun, or a pod to a sandboxed runtime, is a configuration change.

The bad: the specs are minimal where the market is not. The image spec says nothing about build semantics, so Dockerfile behaviour is a de facto standard; the runtime spec says little about networking beyond "join this namespace", so CNI sits beside it; and media types multiplied (Docker schema 2, OCI, gzip, zstd, estargz), producing registries and tools that disagree about what they can store. Index and manifest-list handling differs: a multi-arch pull from a mirror may silently return a different platform than expected if the mirror flattens the index. Layer digests in a manifest are over *compressed* bytes while `diff_ids` are over uncompressed ones, and confusing the two is a recurring source of "digest mismatch" errors; recompressing a layer changes the image digest even though the content is the same. Reproducible builds require fixed timestamps and sorted tar entries.

The ugly: the runtime is a security-critical privileged program that parses untrusted data. Bugs such as the CVE-2019-5736 overwrite of the host `runc` binary, or the 2024 "leaky vessels" file-descriptor leak (CVE-2024-21626, where a working directory pointing at `/proc/self/fd/<n>` reached the host filesystem) were fixed by tightening how runc treats its own descriptors and paths (to verify years). Release notes of recent runc versions continue to carry fixes for symlink races in mount handling and in checkpoint restore [web: github.com]. Operationally, cgroup driver mismatches between kubelet and runtime, a shim left over after a crashed daemon, snapshotter metadata that disagrees with the disk, and image garbage collection racing with a pull are the daily failures. When Docker was removed as a Kubernetes runtime, scripts that mounted `/var/run/docker.sock` for builds or monitoring broke, and teams had to switch to `crictl`, `nerdctl`, Kaniko or BuildKit.

## Applications beyond this domain

Content addressing with a registry and a typed manifest has escaped containers. Helm charts, WebAssembly modules, Sigstore signatures, SBOMs, ML models and Terraform providers are now stored as OCI artefacts using the same distribution API, with `oras` as the general client. The shim idea, a small process per workload that can outlive its manager, is how `systemd` treats units and how Firecracker-based runtimes isolate microVMs. The idea of a declarative bundle consumed by a thin executor shows up in Kubernetes pod specs, in systemd unit files, and in Flatpak's runtime-plus-application layering. The CRI is the pattern that Kubernetes later copied for networking (CNI), storage (CSI) and device plugins: a gRPC contract that lets vendors compete underneath a stable orchestrator.

## Examples

*Inspecting an image without a runtime.* `skopeo inspect --raw docker://registry.example/app:1.4 | jq .` prints an index if the tag is multi-arch; picking the `linux/amd64` digest and repeating returns a manifest with a config and layers. `skopeo copy docker://registry.example/app:1.4 oci:/tmp/app:1.4` writes the layout, and `jq . /tmp/app/index.json` shows the descriptor. Hashing a blob with `sha256sum /tmp/app/blobs/sha256/<hex>` returns exactly its file name, which makes the integrity model concrete.

*Running a bundle by hand.* Export a root filesystem (`podman export $(podman create alpine) | tar -C rootfs -x`), run `runc spec` to generate a default `config.json`, edit `process.args` to `["/bin/sh","-c","echo hi; sleep 5"]`, set `process.terminal` to `false`, then `runc create demo`, `runc state demo`, `runc start demo`, and `runc delete demo`. Watching `status` pass through `created` and `running` explains why Kubernetes can report a container stuck in "Created".

*A failing example: runtime mismatch.* After an upgrade, pods on one node stay in sandbox creation with a shim or runtime-create error. `crictl inspect` shows the runtime handler `kata`, but the node's containerd config lacks the matching `runtimes.kata` stanza. The kubelet is healthy and the image pulls fine, so the clue is the sandbox creation error, not the image. The fix is the handler definition in containerd's config plus a restart, and a `RuntimeClass` check in the pod spec.

*A cgroup-driver failure.* A fresh kubeadm node using systemd as init flaps pods because containerd's `SystemdCgroup = false` while the kubelet uses `systemd`: both create hierarchies under different parents, and limits appear and vanish. The remedy is to set both to the same driver [src: archwiki 6fcf9bded3e264ad].

## Related problems and ideas

Daemonless designs (Podman, `nerdctl` with rootless containerd, Buildah) address the single-daemon failure mode and the root-socket problem, trading it for per-user storage and a monitor per container. Lazy pulling (estargz, SOCI, Nydus) tries to start containers before all layers arrive, since most images are mostly unread. Image distribution inside clusters has peer-to-peer proposals, Dragonfly and Spegel among them, which cache layers on neighbouring nodes. Unikernels and WebAssembly runtimes target the same workflow with a different sandbox; the `runwasi` shims plug them into containerd. Nix and Guix propose building images from a reproducible package graph rather than layered tar files. Another contested idea is whether `config.json` should be less permissive by default so that a mistaken `privileged: true` is harder to write.

## Active research

Current work concentrates on four problems. First, safe handling of untrusted images and bundles: the runtime and the unpacker must resist symlink and path races, and there is ongoing hardening using `openat2`, libpathrs and file-descriptor based mount APIs (to verify). Second, startup latency, through lazy pulls, shared snapshots and runtimes that skip work (crun and youki). Third, confidential containers: Kata combined with CoCo attestation, where the image is decrypted and verified inside a trusted guest, using OCI image encryption extensions. Fourth, artefact semantics: the referrers API, the `subject` field and signature or SBOM discovery are still being aligned among registries. Spec committees also discuss how to express new kernel facilities, for example more detailed network device assignment and CPU affinity for processes, some of which landed in the 1.2 and 1.3 runtime releases [web: github.com].

## Future direction

The runc project is working toward a 1.6 line that raises the Go requirement and removes deprecated APIs, with ongoing security patches visible through its release notes (to verify version numbers) [web: github.com]. containerd 2.x is the current major line and the transfer service is intended to replace ad-hoc pull code; Docker Engine 29 made the containerd image store the default on fresh installs [web: docs.docker.com]. In Kubernetes, CRI evolves through features such as image volume sources, user-namespaced pods and better stats, and runtimes like CRI-O track each release. For practitioners the stable bets are: treat digests as identity, keep the cgroup driver consistent, pin runtime versions with a security-update process, and pick the sandboxed handler per workload through `RuntimeClass` and not through a node-wide replacement.
