# Containerfile craft: small, reproducible, non-root images

## Define the problem

An image is the unit that gets shipped, scanned, pulled across networks, cached on nodes and attacked. Its recipe, called a Dockerfile or a Containerfile (the same format, the second name being the neutral spelling that Podman and Buildah prefer), determines how large it is, how long a build takes, how often the cache is hit, what an attacker finds inside after a compromise, and whether two builds a month apart yield the same thing. A naive recipe starts from a full distribution image, installs a compiler, copies the entire working directory, runs as root, and leaves package caches, build tools, shell history and sometimes credentials in the layers. The result is hundreds of megabytes or more, with hundreds of known vulnerabilities in packages the application never calls, and a trivially useful toolbox for an intruder.

Craft means solving five concrete problems at once. Keep build tools out of the runtime image. Make the cache work for you by ordering instructions by rate of change. Drop root and unneeded privileges so that a compromised process starts in a weak position. Remove everything the program does not need, down to the shell and package manager if possible. And make the result predictable: pinned inputs, a defined start command that handles signals, and a health indication. This slice covers the instructions and their semantics, multi-stage builds, running as non-root, minimal and distroless bases, and checks that prove the result.

## History and approaches

The Dockerfile format dates from Docker's first release in 2013, a short list of verbs (`FROM`, `RUN`, `COPY`, `CMD`) executed top to bottom, each producing a layer. Because every instruction became a layer permanently, the earliest advice was a list of tricks: chain commands with `&&` so that `apt-get update` and the cleanup are in the same layer, because deleting a file in a later layer only hides it. Images of 700 MB for small programs were common. Teams that cared wrote two Dockerfiles, one for building and one for running, with a shell script copying artefacts between them, or a "builder pattern" using a container that the CI job exported. Docker 17.05 added multi-stage builds in 2017, making that pattern a single file: several `FROM` lines, each beginning a stage, and `COPY --from=stage` pulls artefacts across [web: docs.docker.com].

Base images followed their own path. Ubuntu and Debian images of 70 to 120 MB were the default, then Alpine (about 5 MB, using musl libc and BusyBox) became the fashionable small base around 2015, bringing its own surprises: musl's DNS resolver, thread-stack and locale behaviours broke some applications, and Python wheels built for glibc did not install, forcing compile-from-source steps that swallowed the size savings. Red Hat's Universal Base Images (UBI, 2019) offered freely redistributable RHEL userland bases in standard, minimal and micro sizes. Google's distroless project (2017) went further, shipping images that contain the language runtime and CA certificates, timezone data and little else: no shell, no package manager. `scratch`, the empty image, hosts static binaries (Go, Rust with musl) with only the program and certificates. Chainguard and other vendors later offered minimal images built continuously from source with fast CVE patching.

Rootless and non-root operation evolved in parallel. Early images ran as root because it was easy, and many Docker Hub images still do. Security guides, Kubernetes pod security standards (which require `runAsNonRoot` in the restricted profile) and platforms such as OpenShift, which assign an arbitrary UID at run time, forced image authors to design for it [src: kubernetes-docs 5f7ecd74634e8d6f]. OpenShift's convention of group-zero ownership (`chgrp -R 0 dir && chmod -R g=u dir`) is a durable lesson: when the UID is unknown, grant permissions to the root *group*.

The failed or partial approaches are as instructive. Squashing layers (`--squash`) reduced size but destroyed cache sharing and removed history that scanners use. Minimal-but-undebuggable images shifted pain to operators, who responded with ephemeral debug containers. Alpine as default produced pain whenever glibc-linked binaries appeared. Long `RUN` chains made files unreadable. The emerging pattern is a multi-stage file whose last stage starts from a pinned minimal runtime, copies a small set of artefacts, declares a numeric non-root user and an exec-form entrypoint, and is validated by scanning and by running with a read-only root filesystem and all capabilities dropped.

## Current state

### Instruction semantics that matter

`FROM` begins a stage; `FROM image AS name` names it, `FROM scratch` starts empty, and `ARG` before the first `FROM` parameterises base choice. `RUN` executes in a temporary container and commits the changed files as a layer; the shell form goes through `/bin/sh -c`, the exec form (`RUN ["cmd", "arg"]`) does not. `COPY` copies from the build context or `--from=` a stage or image; `ADD` also unpacks local archives and fetches URLs, which is why `COPY` is preferred and `ADD --checksum=sha256:...` is for remote artefacts. `ENV` persists into the final image; `ARG` exists only during build but its values appear in `docker history`, so neither is a place for secrets. `WORKDIR` should be absolute. `USER` sets the user for later instructions and for the run, `EXPOSE` documents a port, `LABEL` adds metadata (`org.opencontainers.image.source`, `.revision`, `.version` are the standard keys). `HEALTHCHECK` defines a command and its timing for engines that evaluate it; Kubernetes ignores it in favour of probes. `STOPSIGNAL` selects the termination signal. `ENTRYPOINT` and `CMD` interact: ENTRYPOINT is the executable; CMD provides default arguments that `docker run image args` replaces. Always write them in exec form as JSON arrays. The shell form wraps the process in `sh -c`, which becomes PID 1, receives `SIGTERM` and often does not pass it on, so a "graceful" stop waits for the grace period and then ends in `SIGKILL`.

PID 1 matters because the kernel gives init special treatment: signals without a handler are ignored. A Go or Rust server handles `SIGTERM` explicitly; a Python or Node server may not. Containers that spawn children also need a process that reaps zombies; `--init` (Docker, using `tini`) or `catatonit` (Podman) injects one, and the Kubernetes pause container does the job at pod level. A wrapper script should finish with `exec "$@"` to replace itself with the application [web: docs.docker.com].

### Cache ordering

BuildKit and Buildah invalidate a layer when its instruction or its input files change, and then every later layer. So order from least to most volatile: base image, OS packages, language dependency manifests and install, then source, then build. A `.dockerignore` (or `.containerignore`) excludes `.git`, `node_modules`, build outputs and secrets from the context so that a change to them does not invalidate `COPY .` and so they cannot leak. BuildKit adds `--mount=type=cache` for package caches that persist between builds without being baked into a layer (see topic T04). `apt-get update` and `apt-get install` belong in one `RUN`, with `--no-install-recommends` and the removal of `/var/lib/apt/lists/*` in the same layer; `set -o pipefail` stops a failed download hiding behind a pipe [web: docs.docker.com].

### Multi-stage builds

```dockerfile
# syntax=docker/dockerfile:1
ARG GO_VERSION=1.24
FROM golang:${GO_VERSION}-bookworm AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN --mount=type=cache,id=gobuild,target=/tmp/gocache \
    GOCACHE=/tmp/gocache CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/app ./cmd/app

FROM gcr.io/distroless/static-debian13:nonroot
COPY --from=build /out/app /app
USER 65532:65532
EXPOSE 8080
ENTRYPOINT ["/app"]
```

The `build` stage carries a compiler of roughly a gigabyte, none of which reaches the final image of about ten megabytes. Stages that are unused are not executed by BuildKit, and `--target build` lets a CI job build and test only the first stage. A test stage can run unit tests during the build; a "dev" stage can add a shell and debugger on top of the runtime stage for troubleshooting. For interpreted languages the same shape applies: a builder stage creates a virtualenv or `node_modules` with compilers present, and the runtime stage copies the finished directory to a slim image with the same libc, since mismatched libraries are the main failure of this technique.

### Non-root by design

The safest run user is a numeric UID that exists with no login shell and owns only what it must write. In a Debian-based image: `RUN groupadd -r -g 10001 app && useradd -r -u 10001 -g app -s /usr/sbin/nologin app`, then `USER 10001:10001`. The numeric form lets Kubernetes verify `runAsNonRoot` without reading `/etc/passwd`. Application directories are owned by root and read-only to the app; only designated data and temp directories are writable by the app UID. Binaries are not writable by the user that runs them: an attacker who can overwrite the program survives restarts. For arbitrary-UID platforms, make writable directories group-owned by GID 0 with group write.

Non-root also means no binding of ports below 1024 without the `CAP_NET_BIND_SERVICE` capability or the `net.ipv4.ip_unprivileged_port_start` sysctl; listening on 8080 inside, and mapping outside, avoids the problem. Run-time hardening complements the image: `--read-only` with explicit `--tmpfs /tmp`, `--cap-drop=ALL`, `--security-opt no-new-privileges`, and `--pids-limit`. Images should work under all of these, and testing them is part of the craft. In Kubernetes the same settings appear in `securityContext`: `runAsNonRoot`, `readOnlyRootFilesystem`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `seccompProfile: RuntimeDefault` [src: kubernetes-docs 04bb3bc9f3d02ba1].

### Minimal and distroless bases

Choices form a ladder. A full distribution image has a shell, package manager and large package set, which is convenient and wide. A "slim" or minimal variant removes documentation and locales. UBI micro or Alpine reduce further, differing in libc: glibc (Debian, UBI) versus musl (Alpine). Distroless images contain the runtime pieces only, with families for static binaries, glibc-based apps (`base`), C++ (`cc`), Java, Node.js and Python, each in `:nonroot` and `:debug` variants that add a BusyBox shell, and the project signs images with Cosign keyless signing so consumers can verify them [web: github.com]. `scratch` is the end of the ladder: nothing but your files, so you must copy in CA certificates (`/etc/ssl/certs/ca-certificates.crt`) and time zone data if needed, and create `/tmp` yourself.

The trade is attack surface against debuggability. With no shell, `docker exec -it app sh` fails; the replacements are `kubectl debug` with an ephemeral container sharing the target's namespaces, `nsenter` from the host (topic T09), or the `:debug` image variant in non-production. Vulnerability scanners report fewer findings because packages are absent, and the SBOM is small and clear. Dynamic languages need more care because their runtime image carries libraries the application imports implicitly.

### Reproducibility and metadata

Pin base images by digest (`FROM image:1.2@sha256:...`), with a bot such as Dependabot or Renovate updating both the tag and the digest, since an unpinned tag changes silently and a digest-only reference cannot be read by humans. Pin language dependencies with lock files and use `npm ci`, `pip install --require-hashes`, `go mod download` with `go.sum`. Set a build date through `SOURCE_DATE_EPOCH` when tooling supports it, and add `org.opencontainers.image.*` labels. Verify the result by inspecting: `docker history --no-trunc`, `dive`, `podman image inspect`, and a scanner run (T08).

## Assessment: the good, the bad and the ugly

The good: the techniques are cheap and compound. Multi-stage builds usually shrink an image by an order of magnitude, speeding pulls and node starts; good cache ordering turns a ten-minute build into seconds; a non-root, read-only, capability-free container makes common exploit chains fail early. Distroless and scratch images give scanners almost nothing to flag, and the lack of tools frustrates both administrators and attackers who rely on `curl`, `wget` and a shell to stage payloads.

The bad: minimalism has costs. A missing shell makes ad hoc debugging impossible without another workflow. Static linking pushes responsibility for library patches to the application build, so a vulnerable library is fixed only after rebuilding, not by updating a distro package. musl-based images differ subtly in behaviour; performance-sensitive Python or Java on Alpine may run slower. Distroless images follow a Debian release train, and applications compiled for glibc versions must match. UID choices cause mount permission errors when volumes are owned by other IDs. Health checks require a binary inside the image (a `curl` that no longer exists), so a small health-check mode in the application itself is a common pattern.

The ugly: secrets and state. `COPY . .` without an ignore file copies `.env`, SSH keys and the `.git` directory, whose history contains old secrets. `ARG` and `ENV` values live in image metadata forever. A `rm` in a later layer does not delete the data from the earlier layer, which any `docker save` and `tar` extraction can read. Multi-stage builds protect only if the secret never entered a stage that is copied. Another ugly area is the "latest" tag: a build that was green yesterday fails today because the base moved, or worse, passes with an unvetted upstream change. Finally, running as non-root can be an illusion: an image with a `setuid` shell, `sudo`, a writable `/etc/passwd` or group-writable binaries gives root back. Scan for setuid files with `find / -perm -4000 -type f` in the final stage and remove the bits (`chmod a-s`).

## Applications beyond this domain

The multi-stage idea, building in a rich environment and shipping a thin artefact, is the general build/runtime split found in compiled-language packaging, in Nix's closures (which also include only referenced store paths), and in static site generators. The numeric-user discipline applies to systemd services (`DynamicUser=`) and to VM images. Minimalism echoes in unikernels and in Linux appliance builders (Buildroot, Yocto), where the point of removing components is the same: less to patch, less to attack. The pin-by-digest practice is the same as lock files and hash-pinned requirements, and as pinning GitHub Actions to commit hashes. OpenShift's group-zero convention shows that identity-agnostic file permissions are a portability technique for any platform that assigns users at run time.

## Examples

*A Python service, before and after.* The "before" file uses `python:3.12`, runs `pip install` after `COPY . .`, installs `build-essential` and runs as root; the image is 1.1 GB. The "after" uses a build stage (`python:3.12-slim` with compilers) to create `/opt/venv` from a hash-pinned `requirements.txt`, then a runtime stage on `python:3.12-slim` (or distroless `python3`) that copies `/opt/venv`, sets `PATH`, creates UID 10001, and runs `["python","-m","app"]`. Size falls to about 150 MB, and a source change rebuilds only the last layers.

*Checking what a build contains.* `docker history --no-trunc app:1` shows each instruction and layer size; `docker run --rm --read-only --cap-drop ALL --user 10001 app:1` proves the image works under restrictions; `podman image inspect --format '{{.Config.User}}' app:1` prints the declared user. In a scratch or distroless image, `docker export $(docker create app:1) | tar -t | head` lists the entire filesystem, a good measure of what an attacker could use.

*A failing example: signals.* A Node image uses `CMD npm start`. In Kubernetes, rolling updates take 30 seconds per pod since `SIGTERM` reaches `npm`, which does not forward it to `node`, so the pod is killed after the grace period. Using `CMD ["node","server.js"]`, adding `--init`, or handling the signal in code fixes it; logs also lose the last lines since the process did not flush.

*Another failure: certificates in scratch.* A Go service on `scratch` works in tests but fails in production with an unknown-certificate-authority TLS error because the image holds no CA bundle. Copying `/etc/ssl/certs/ca-certificates.crt` from the build stage, or using `distroless/static`, which includes it, fixes it.

*Arbitrary-UID platform.* An image whose `/data` is owned by UID 10001 fails on a cluster that assigns a random UID. Changing ownership to `10001:0` with `chmod g=u` fixes it, as the random UID always belongs to group 0.

## Related problems and ideas

Other ways to produce images without a Dockerfile include Buildah scripts, Cloud Native Buildpacks (detect the language and layer dependencies, with rebasing of the OS layer without rebuilding), Jib and `ko` (direct builds of Java and Go apps to registries), Nix `dockerTools` and `apko`/Melange (declarative apk-based assembly with SBOMs generated by construction). Rebasing, replacing the base layers of many images without rebuilding, tries to patch CVEs at fleet scale. Debugging without a shell is addressed by ephemeral containers, `nsenter`, and tools like `docker debug`. Policy as code (Conftest, Hadolint rules) lints Containerfiles in CI for missing `USER`, unpinned tags and `ADD` of URLs. Image slimming tools (SlimToolkit) trace which files are used at run time and drop the rest, which is aggressive and can remove files needed on rare paths.

## Active research

Current effort goes into reproducibility and into build provenance: making BuildKit and Buildah output bit-identical across machines, recording the exact inputs in SLSA provenance, and verifying that a deployed image corresponds to a source revision (see T08). Another strand is composefs and erofs-based images that give integrity-checked, deduplicated layers. The `SOURCE_DATE_EPOCH` rewrite of timestamps in layers, the rebuilding of base images with a fixed package snapshot, and language-level reproducibility (Go's toolchain, Rust's `--remap-path-prefix`) all feed that. Researchers also study which "bloat" actually matters for security: studies of container images repeatedly find that most reported vulnerabilities sit in packages that are never loaded, which supports trimming, but there is little consensus on how to prove a file unneeded. Unprivileged or "rootless" builds that need no `RUN` privileges are a related open area.

## Future direction

Minimal, continuously rebuilt bases from several vendors are becoming normal procurement items, and distroless images now track Debian 13 with Node.js 22, 24 and 26 and Java 17, 21 and 25 variants (to verify) [web: github.com]. Expect build tools to emit signed provenance and an SBOM by default, registries to display them, and admission controllers to require them. The Dockerfile format itself changes slowly, through BuildKit frontends such as `dockerfile:1` features (heredocs, `COPY --link`, build checks via `docker build --check`) and linting at build time. Expect non-root, read-only-root, drop-all-capabilities to be the default expectation of platforms, not an extra. A practitioner's checklist that will remain valid: pin the base by digest, split build from run, order by volatility, use numeric non-root users, use exec-form entrypoints, exclude the context, scan the result, and test under the restrictions you will run with.
