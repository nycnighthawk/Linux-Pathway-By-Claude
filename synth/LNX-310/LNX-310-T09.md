# Debugging containers: inspect, events, nsenter and the host's own tools

## Define the problem

A container that misbehaves is awkward to examine. The image may have no shell, no `ps`, no `ip`, no `curl`. The failure may leave no process to attach to, since the container exits in a fraction of a second. Logs may be lost with the container or never reach a file. The cause may sit in any of five places that look the same from outside: the image and its entrypoint, the runtime configuration (mounts, user, capabilities, limits), the network namespace, the kernel and its cgroup accounting, or the engine and runtime software itself. People who treat the container as a black box guess, rebuild the image with debug tools baked in, and ship the debug tools to production.

The skill this slice teaches is localisation: work out from a few cheap observations which layer is at fault, and then reach into that layer using the tool that fits. Three families of tools do the work. The engine's own commands (`inspect`, `logs`, `events`, `stats`, `top`, `diff`) read recorded state and report what the runtime did. Namespace tools (`nsenter`, `lsns`, `/proc/<pid>/...`) run host programs inside the container's view without anything installed in the image. And host observability (kernel log, cgroup files, journal, tracing) shows the resources that the container shares with everything else. The slice also covers Kubernetes ephemeral containers and the debugging of builds.

## History and approaches

Early Docker debugging was `docker run -it image sh` followed by guesses, and `docker exec`, introduced in 1.3 (2014), which starts a new process in the existing namespaces of a container. Before `exec`, administrators used `lxc-attach` or a bundled SSH daemon in the image, a pattern that duplicated every access-control and patching problem of a full server. `nsenter`, written for util-linux in 2012 (with a precursor in the `nsenter` helper of Jérôme Petazzoni), made it possible to join any set of a process's namespaces from the host, using `setns(2)` on the files in `/proc/<pid>/ns`, which works even when the container has no shell and does not need the engine to be healthy.

As images shrank (topic T05), debugging moved outward. Distroless and scratch images made `exec sh` impossible, so tools appeared to attach a toolbox from outside: `docker run --pid=container:<id> --net=container:<id> nicolaka/netshoot`, which starts a second container sharing the target's namespaces; the Docker CLI's `debug` command; and, in Kubernetes, *ephemeral containers* (alpha in 1.16, stable in 1.25), added to a running pod through the `ephemeralcontainers` sub-resource and driven by `kubectl debug -it pod --image=busybox --target=app`. The kubelet cannot restart or remove them, which is by design, as they exist for diagnosis only [src: kubernetes-docs 2398ed921cf0f476].

Events and state inspection grew from the engine's need to explain itself. `docker events` streams lifecycle changes (create, start, die, oom, health_status, kill) from the daemon; Podman provides a similar `podman events` with a journald or file backend, and Red Hat describes using it for auditing [src: rhel-10-docs a8c071343c4cc723]. Kubernetes added its own `Event` objects and pod conditions, which tie to the pod lifecycle phases and container states (`Waiting`, `Running`, `Terminated` with a reason and exit code) [src: kubernetes-docs 34a04049764a960e]. Tracing tools were adapted afterwards: `sysdig` and `csysdig` (container-aware capture of system calls, with filters on `container.name`), `strace` with `-f` through `nsenter` or on the host PID, and eBPF-based tools such as Inspektor Gadget and Tetragon, which add container and pod labels to events [src: man-pages d87bc71c87f52d32].

The approaches that did not scale: baking SSH servers or full toolboxes into images, running everything privileged "to be able to debug", and relying on `docker logs` as the only record. The pattern that emerged is layered: read state first (it is cheap and safe), enter namespaces second, trace last, and keep the production image minimal.

## Current state

### A triage order

A consistent order saves time. First ask the runtime what it thinks: is the container running, exited, restarting, or stuck in `created`? Second read its logs and exit code. Third look at its configuration for the facts that usually cause trouble (command, user, mounts, environment, limits, networks). Fourth look at the surrounding events, and last use namespace entry and tracing. Each step answers a narrower question than the last.

### Reading state: inspect, logs, ps, events

`docker inspect <ctr>` (or `podman inspect`) returns JSON; with `-f '{{...}}'` a Go template selects fields. The useful ones are:

- `.State`: `Status`, `Running`, `ExitCode`, `OOMKilled`, `Error`, `StartedAt`, `FinishedAt`, `Pid` and `Health` (with a log of the last probe outputs).
- `.Config`: `Image`, `Entrypoint`, `Cmd`, `User`, `Env`, `WorkingDir`, `Healthcheck`, `Labels`.
- `.HostConfig`: `Binds`, `Privileged`, `CapAdd`, `CapDrop`, `SecurityOpt`, `Memory`, `NanoCpus`, `PidsLimit`, `RestartPolicy`, `NetworkMode`, `Devices`.
- `.Mounts`, `.NetworkSettings` (IP address, ports, networks) and `.GraphDriver`.

Exit codes are information. `0` is clean; `1` is an application error; `125` means the engine failed to run the container (bad flag, invalid mount); `126` means the command was found but could not be executed (permissions, wrong architecture, noexec mount); `127` means command not found (a typo in `CMD`, a script with a wrong interpreter line, or a missing binary in a minimal image); `128 + n` means a signal `n`: `137` is SIGKILL (the OOM killer, or a stop timeout that ran out), `139` is SIGSEGV, `143` is SIGTERM. `OOMKilled: true` together with 137 settles the memory question; without that flag, 137 points to a `docker kill` or a timeout. A container that exits at once with 126 or 127 never gets to run `exec`, so the way to look inside is `docker run --rm -it --entrypoint sh image` (overriding the entrypoint), or `docker create` followed by `docker cp` and `docker export | tar -t`.

`docker logs --since 10m --timestamps -f <ctr>` shows what the main process wrote to stdout and stderr, as captured by the logging driver; `docker logs` does not work with drivers that do not keep local copies (`syslog`, `gelf`, `none`), a frequent surprise. `docker top` and `docker stats --no-stream` give process lists and resource use as the cgroup reports it. `docker diff` shows files changed in the writable layer, which exposes applications that write where they should not. `docker port` shows published ports. Podman's equivalents are almost identical, plus `podman ps -a --external` to list containers made by Buildah or CRI-O, `podman healthcheck run` to execute the probe now, and `podman logs` from the journal.

`docker events --since 1h --filter container=web --filter event=die` prints what happened, with attributes such as `exitCode` and `signal`; `--filter type=network` and `--format '{{json .}}'` help scripts. Events are the way to see a restart loop's rhythm: a `die` followed by `start` every few seconds reveals the interval and the exit code with no logs at all. In Kubernetes, the counterparts are `kubectl describe pod` (events at the bottom, with `Last State`, `Reason`, `Exit Code`), `kubectl logs --previous` for the last terminated instance, and `kubectl get events --sort-by=.lastTimestamp`.

### Entering namespaces: nsenter and friends

`docker exec` is the first choice if the image has the needed tool. When it does not, from the host as root:

```bash
pid=$(docker inspect -f '{{.State.Pid}}' web)         # podman inspect has the same field
sudo nsenter --target "$pid" --net ss -tlnp            # host's ss, container's network
sudo nsenter -t "$pid" -n ip addr                       # interfaces, addresses
sudo nsenter -t "$pid" -n -- tcpdump -ni eth0 port 5432 # capture on the container's NIC
sudo nsenter -t "$pid" --mount --pid ps aux             # mount + pid namespace: sees its /proc
sudo nsenter -t "$pid" --all sh                         # join every namespace; needs a shell in the image
ls -l /proc/$pid/root/etc/                              # read its filesystem from the host, no namespace
```

`nsenter` options select the namespaces: `-m` mount, `-u` UTS, `-i` IPC, `-n` network, `-p` PID, `-U` user, `-C` cgroup, `-T` time, and `-a` for all. A key technique is to enter only the namespace you need. Entering the network namespace alone keeps the host's filesystem and tools available, which is why `nsenter -n tcpdump` works on a distroless container. Entering the *mount* namespace changes `/`, so host tools disappear unless they are statically linked. Entering the PID namespace needs `-p` and a fresh `/proc` mount (`--mount-proc` for `unshare`, or enter mount and pid together) for `ps` to be consistent.

For a rootless container, the process is owned by the user, so `nsenter` must join the user namespace first: `podman unshare` gives a shell in the user namespace to inspect file ownership, and `podman top`, `podman exec` and `nsenter -U --preserve-credentials -t $pid` work for the user. For `podman`, `podman mount` mounts the container's root filesystem for reading, which is the equivalent of looking at a snapshot.

Supporting commands: `lsns` lists namespaces and their owners (`lsns -t net`), `readlink /proc/$pid/ns/net` identifies one, `cat /proc/$pid/cgroup` reveals the cgroup path (so that `systemd-cgls` and `systemd-cgtop` or `cat /sys/fs/cgroup/<path>/memory.events` give the resource view), `cat /proc/$pid/status | grep -E 'Cap|Seccomp|NoNewPrivs'` shows the effective security state, `capsh --decode=<hex>` turns the hex into names, and `ls /proc/$pid/fd` lists open files. For tracing: `strace -f -tt -p $pid -e trace=network,openat` on the host PID needs no entry at all, though in a user namespace you may need the same user or `CAP_SYS_PTRACE`; `perf` and `bpftrace` can filter on cgroup ID; `sysdig -pc container.name=web` captures with container context [src: man-pages d87bc71c87f52d32].

### Debug containers and ephemeral containers

When entering from the host is not possible (managed Kubernetes nodes, other tenants' nodes, rootless engines), the toolbox must come as another container sharing namespaces. With Docker: `docker run -it --rm --pid=container:web --net=container:web --cap-add SYS_PTRACE nicolaka/netshoot`. With Kubernetes: `kubectl debug -it pod/web --image=busybox:1.37 --target=app` adds an ephemeral container that shares the process namespace of the target container (when the runtime supports it), so `ps` and `/proc/1/root` expose the target's filesystem. `kubectl debug pod/web --copy-to=web-debug --container=app --image=app:debug` creates a copy of the pod with a changed image or command, which preserves the original for forensics. `kubectl debug node/n1 -it --image=ubuntu` starts a pod with the node's filesystem mounted at `/host`, a way to inspect the node that a privileged-node debugging guide for virtualisation stacks also describes [src: kubevirt-user-guide a8b9384ee2019069]. At the runtime level, `crictl ps -a`, `crictl inspect`, `crictl logs` and `crictl exec` skip the Kubernetes API and talk to containerd or CRI-O directly, which is the tool when the kubelet itself is the suspect.

### The engine's own diagnostics

When containers fail to start for reasons that are not in their logs, look at the engine: `journalctl -u docker` or `-u containerd`, `docker info` (storage driver, cgroup version and driver, runtimes, warnings such as swap limit support missing), `docker system events`, `dockerd --debug` through `"debug": true` in `daemon.json`, and the runtime's own output (`runc --debug` and its log file). Rootless failures usually print the missing prerequisite: subordinate IDs, no `newuidmap`, a missing cgroup delegation, no `/dev/net/tun` for slirp, or an unprivileged user namespace blocked by policy [src: docker-docs 1c7adda4f19a83bf]. For Podman, `podman --log-level=debug run ...` prints the OCI runtime invocation and the config it generated, which can be copied and run with `runc` or `crun` by hand to separate a Podman problem from a runtime problem.

### Common problems and where they show

*Memory.* `OOMKilled` in inspect or Kubernetes status, `dmesg -T | grep -i 'killed process'` with a `memcg` line naming the cgroup path, `memory.events` counters, and `memory.max` against `memory.current` all agree or disagree usefully. If the host log shows no kill but the container died with 137, a stop timeout or an external kill is the cause.

*CPU.* `cpu.stat` with growing `nr_throttled` explains latency under a quota with no host CPU pressure.

*Network.* From the host, `nsenter -n ip route`, `ss -tlnp`, `nft list ruleset` or `iptables -t nat -S`, and `conntrack -L` show what the container's stack and the NAT rules do. DNS failures in containers show up as `resolv.conf` inside pointing at an unreachable address (`nsenter -m -t $pid cat /etc/resolv.conf`), often because the host uses a local stub resolver at 127.0.0.53, which a container cannot reach, so the engine substitutes other servers [src: archwiki 52d1512a42d1affd]. Published port conflicts and firewall interplay are in the host's rules.

*Permissions.* `id` and `/proc/<pid>/status` for UID and capabilities, `ls -ln` on mounts for numeric owners, `ausearch -m avc -ts recent` for SELinux denials, `dmesg | grep -i apparmor` for AppArmor, and seccomp denials in the audit log or as `EPERM` in an `strace -f`.

*Start-up.* Containers stuck in `Created` often indicate a runtime-level failure after the engine finished its part: a hook, a failing mount, a missing device or a cgroup problem. `docker events` and the runtime debug log show the last step.

*Builds.* `docker buildx build --progress=plain --no-cache`, `--target <stage>` to stop at a stage and run it, and `BUILDKIT_PROGRESS=plain` make failing steps readable; a failed `RUN` can be reproduced by running the previous stage's image with the same command.

## Assessment: the good, the bad and the ugly

The good: the recorded state is rich and cheap, nothing in it needs the container to be alive, and the same JSON feeds scripts and monitoring. Namespace entry works regardless of what is in the image, which preserves the benefits of minimal images. Exit codes, `OOMKilled`, health logs and events make most start-up and crash problems diagnosable in a minute.

The bad: the layers hide each other. `inspect` shows what was configured, not what the kernel did; a configured memory limit can be ineffective if the controller was not delegated, so always verify at the cgroup file. Logs depend on the driver and rotation, and crash loops can discard the evidence of the first failure when a container is recreated rather than restarted. Different tools show different identities for the same process: the host PID differs from the in-container PID (usually 1), UIDs differ across user namespaces, and paths differ in each mount namespace; a path copied from inside does not exist outside. `docker exec` runs a *new* process that is not a child of PID 1, so it does not see the application's environment changes after start and has different signal behaviour.

The ugly: the debugging tools are themselves dangerous. Entering a container as root with `nsenter -a` and a full set of host capabilities escapes nothing but also bypasses the container's seccomp and capability limits, so a bug reproduced with the debugger attached may not reproduce without it, and sharing a PID namespace with a privileged debug sidecar exposes the target's memory and environment variables (including secrets) to the debugger. `--privileged` debug containers that mount the host root make a convenient backdoor if they are left running. Ephemeral containers cannot be removed from a pod except by deleting the pod, and they need RBAC, which should be given sparingly. Core dumps are another trap: `kernel.core_pattern` is global to the host kernel, so a container's crash may be piped to the host's handler (`systemd-coredump`, `apport`) in the host's namespaces, and the dump lands outside the container, not in its filesystem. Finally, debugging by restarting destroys the state that mattered: before `docker restart`, capture `inspect`, logs, `docker diff` and, if needed, `docker checkpoint` or `docker commit` of the dead container for later study.

## Applications beyond this domain

The same three-step approach (read recorded state, enter the relevant namespace, trace the kernel interface) applies to any isolated or virtualised workload. `nsenter` is how administrators debug systemd services with `PrivateNetwork=` or `PrivateTmp=`; `systemd-run --pty -p ...` and `machinectl shell` serve nspawn containers. For virtual machines, the equivalents are `virsh dumpxml` (configuration), `virsh domstats` and QEMU's monitor (state), and `virt-ls`/`guestfish` (read the filesystem offline), and the KubeVirt documentation shows the same ideas applied to the virt stack, such as launching QEMU under strace [src: kubevirt-user-guide 50d92ecb01029593]. The exit code convention (128 plus signal) is the ordinary shell convention and helps in any CI log. Event streams as a debugging aid also exist in systemd (`journalctl -f`), Kubernetes, `udevadm monitor` and `auditd`. Reading the process's view through `/proc/<pid>/root` is a generic technique for chroot-like environments.

## Examples

*Crash loop with no logs.* A container shows `Restarting (127)`. `docker inspect -f '{{.Config.Entrypoint}} {{.Config.Cmd}}' app` prints `[/entrypoint.sh] []`. `docker run --rm --entrypoint sh app -c 'head -1 /entrypoint.sh; ls -l /entrypoint.sh'` shows `#!/bin/bash` in an image with only BusyBox. Exit 127 was the missing interpreter, not a missing script: the fix is a correct shebang or the right base image.

*Network capture on a distroless service.* A service on a scratch image drops connections. On the host, `pid=$(docker inspect -f '{{.State.Pid}}' api)` then `sudo nsenter -t $pid -n tcpdump -ni any -w /tmp/api.pcap tcp port 8443` records packets with the host's tcpdump; Wireshark reveals the TLS alert and the certificate problem. Nothing was added to the image.

*Finding who killed it.* A worker dies every few hours with 137. `docker inspect` shows `OOMKilled: false`, `docker events --filter event=die` shows `signal=9`, and the stop command appears in the daemon log as a timeout: the container ignored `SIGTERM` (it runs under `sh -c`) during a deploy, and the engine escalated to `SIGKILL`. Fixing the entrypoint to exec form removes the symptom.

*A failing example: the limit that was not there.* A service set to `--memory=512m` grows to 4 GB on a rootless Podman host and takes the machine down. `podman inspect` shows `Memory: 536870912`, but `cat /sys/fs/cgroup/user.slice/.../memory.max` reads `max`, as the memory controller had not been delegated to the user's session. The fix is a systemd drop-in with `Delegate=memory pids cpu io` for `user@.service`, then a re-login, and a check of `memory.max` in the container's cgroup.

*A failing example: DNS only in containers.* Pods on a node resolve internal names but not external ones. `nsenter -t $pid -n -m cat /etc/resolv.conf` shows a forwarder that the node's firewall blocks from the container subnet; the host works because it uses another path. The fix is allowing the traffic or configuring the engine's DNS list.

## Related problems and ideas

Adjacent areas include continuous observability (metrics with cAdvisor and Prometheus, logs shipped by Fluent Bit or Vector, traces with OpenTelemetry), which answers questions about the past that live debugging cannot; eBPF-based runtime security and observability (Falco, Tetragon, Pixie, Inspektor Gadget), which see across all containers at once; core-dump handling and post-mortem debuggers; checkpoint and restore with CRIU (`podman container checkpoint`) to capture a failing process with its memory for offline study; and record-and-replay debuggers such as `rr`, which require specific perf counter access. Alternative designs avoid the problem: debuggable images built from the same Dockerfile with a `debug` target and a separate tag, and a policy that production pods never contain a shell. The idea of shipping `nsenter`-style entry as a platform feature, with auditing and time-limited access, is what managed Kubernetes offerings provide through session managers.

## Active research

Research and engineering effort focuses on making debugging safe at scale. Kubernetes is extending ephemeral containers, with profiles for debugging (`general`, `baseline`, `restricted`, `sysadmin`) so that a debug container gets the minimum capabilities, and node debugging through pods. The eBPF community works on tracing that is container-aware by default and keeps overhead low, including on-demand tracing of an individual pod. There is ongoing work on making `/proc` and `/sys` virtualisation more truthful for containers (lxcfs, cgroup-aware `meminfo` in the kernel proposals), which would reduce false diagnoses from tools that read host numbers. In security, projects study which debugging capabilities (ptrace, process memory reads) are safe to grant across container boundaries, and how to audit them. Checkpointing for failure analysis, and the timing and ordering of events across runtime, kubelet and API server, remain research topics for incident analysis tools.

## Future direction

Expect the debugging experience to move toward per-pod, time-limited, audited debug sessions rather than SSH to nodes, with standardised debug profiles and richer built-in events from runtimes (the runtime-spec work on hooks and failure reporting is one input). Docker and Podman will continue to unify `debug` commands that attach tool images, and the Docker documentation already recommends inspecting and debugging a running Compose stack with `exec`, `logs` and `ps` as the first move [src: docker-docs 959bca7e790ccce4]. Observability pipelines will carry container identity by default, so that it is possible to ask afterwards what a vanished container was doing at a given minute. The durable skills do not change: read state before touching anything, enter only the namespace you need, verify limits at the cgroup file, preserve evidence before restarting, and keep production images small and debug tools outside them.
