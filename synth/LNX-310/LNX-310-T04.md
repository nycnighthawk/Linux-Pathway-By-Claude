# Docker Engine, BuildKit and Compose: the developer-facing toolchain

## Define the problem

Containers are only useful if people can build them quickly, run them predictably and describe multi-container applications in a file that a colleague can run. The kernel features of topic T01 and the OCI specifications of T02 give the mechanism, but they offer no workflow: no way to turn a recipe into layers while reusing unchanged work, no cache that survives from one CI job to the next, no network that lets a web service find its database by name, no single command that brings up five services in a dependency order on a laptop.

Docker's contribution was the workflow. This slice covers the three parts that make up its toolchain today. The Engine is the long-running daemon with the client CLI, API, storage, networks and the integration with containerd and runc. BuildKit is the build backend that executes Dockerfiles as dependency graphs with caching, secrets and multi-platform output. Compose is the specification and plugin that describes a multi-container application in `compose.yaml`. The topic also asks when this stack is the right choice and what it costs in privilege and operational burden, because the daemon model and the rootless alternatives of T03 sit side by side in real fleets.

## History and approaches

Docker began inside dotCloud in 2013 and combined four ideas that were separately known: kernel isolation, a union filesystem for layers (AUFS first), a recipe format (the Dockerfile) and a public registry (Docker Hub). The classic builder executed Dockerfile instructions in order, committing a layer after each, and cached by comparing instruction text and parent. That design was simple and slow: it was serial, it built every stage of a multi-stage file whether needed or not, it kept secrets in layers if a developer was careless, and its cache was local to the host. Multi-stage builds (17.05, 2017) addressed image size, by letting a build stage produce artefacts that a later stage copies without carrying the compiler.

BuildKit, started by Tonis Tiigi in 2017 and merged into the Engine as an opt-in in 18.09, replaced the builder with a different execution model. Instructions are compiled by a *frontend* into LLB, a low-level build graph of content-addressed operations; the solver executes independent branches in parallel, skips unneeded stages, and caches each vertex by a checksum of its inputs. BuildKit became the default builder for Linux in Docker 23.0 (2023) and `docker buildx` became the default `docker build` entry point [web: docs.docker.com]. The reasons it replaced the older builder are practical: concurrency, a transfer of only changed context files, `RUN --mount` types for caches and secrets, and external cache backends.

Compose started as Fig (2013), a Python tool by Orchard that read a YAML file and ran containers; Docker acquired it and renamed it. Compose v1 was a Python script (`docker-compose`), v2 is a Go rewrite packaged as a CLI plugin (`docker compose`), and v1 reached end of life in 2023. The file format was split out as the Compose Specification, so other tools implement it, and the old `version:` key in files became obsolete. Alternatives that existed in parallel include Docker Swarm (built-in orchestration, now in maintenance mode in practice), Mesos and Nomad, and, as the clear winner, Kubernetes, which a developer can approach from Compose files through a conversion tool [src: kubernetes-docs b5770e42f5dc5a10].

The partial successes: Docker Desktop and the Docker Machine and Toolbox predecessors made Linux containers usable on Mac and Windows by hiding a Linux VM. The commercial licensing change for Docker Desktop in 2021 pushed many organisations to Podman Desktop, Rancher Desktop, Colima and Lima, which shows how much of the market depended on the packaging more than on the engine. The failure modes recur: images built with cached `apt-get update` layers months stale, `latest` tags that change under a deployment, and Compose files with passwords committed.

## Current state

### The Engine

`dockerd` listens on `/var/run/docker.sock` (a Unix socket owned by root and the `docker` group) and optionally on TCP with TLS. It exposes the Engine REST API, versioned (`/v1.44/...`), which the CLI, SDKs, Compose, CI runners and monitoring agents all use. Below it, containerd manages images and containers in the default `moby` namespace and runc executes them, as in topic T02. Docker Engine 29 made the containerd image store default for fresh installs, which brings lazy pulling, multi-platform images and attestations stored natively, and requires API v1.44 or later (the minimum was later lowered) [web: docs.docker.com]. The daemon's configuration lives in `/etc/docker/daemon.json`; important keys include `data-root`, `storage-driver`, `log-driver` and `log-opts` (the default `json-file` driver does not rotate unless `max-size` and `max-file` are set, which is a classic disk-fill failure), `live-restore` (keeps containers running while the daemon restarts), `userns-remap`, `default-ulimits`, `registry-mirrors`, `insecure-registries`, `iptables`, `ip6tables`, and `default-runtime` with `runtimes`.

Networking creates the `docker0` bridge for the default network and uses iptables or nftables rules for NAT and published ports. Drivers include `bridge` (user-defined bridges add DNS-based name resolution through an embedded resolver at 127.0.0.11), `host`, `none`, `macvlan`/`ipvlan` (containers on the LAN with their own addresses) and `overlay` for Swarm. Docker's firewall integration is a known surprise: published ports are DNAT-ed in the `nat` table and accepted by `DOCKER-USER` and `DOCKER` chains ahead of host rules, so a `ufw deny` rule on the host does not block a published container port. Binding to loopback (`-p 127.0.0.1:8080:80`) and managing policy in the `DOCKER-USER` chain are the controls. Recent releases offer experimental nftables support through the daemon's firewall backend option [web: docs.docker.com].

Storage splits into image layers under `data-root`, writable layers per container, and data kept in **volumes** (managed directories, driver-pluggable), **bind mounts** (host paths) and **tmpfs**; see topic T07. Resource limits map directly to cgroups: `--memory`, `--cpus`, `--pids-limit`, `--blkio-weight`. Restart policies `no`, `on-failure[:n]`, `always` and `unless-stopped` run through the daemon, which therefore acts as a simple process supervisor. Health checks defined in the image or at run time put a container into `starting`, `healthy` or `unhealthy`, but plain Engine takes no action on `unhealthy`; Compose and Swarm can order startup on it.

**The privilege model** is the central security fact. Membership of the `docker` group, or access to the socket, equals root: `docker run -v /:/host --privileged alpine chroot /host` is a root shell. Mitigations are rootless mode (daemon and containers inside a user namespace), `userns-remap` (container root maps to a subordinate ID on the host; some features such as the containerd image store are off by default in that configuration), socket proxies that allow only particular API calls, and never mounting the socket into application containers [src: docker-docs 1c7adda4f19a83bf].

### BuildKit

`buildkitd` is a daemon, embedded in dockerd or run separately, and it executes the build graph. `docker buildx` is the CLI that talks to it through *builder instances* and *drivers*. The `docker` driver uses the daemon's built-in BuildKit; the `docker-container` driver runs `moby/buildkit` in a container, which unlocks cache exporters and multi-platform builds; the `kubernetes` driver runs build pods in a cluster, optionally rootless; the `remote` driver attaches to an existing daemon [src: docker-docs 9fafe2d0e46b7dbc] [src: docker-docs 078166f031541ad1]. Configuration for the daemon lives in `buildkitd.toml`, covering registry mirrors, garbage-collection policy and worker settings [src: docker-docs cbcb41f6340a206d].

Features that change how Dockerfiles are written, enabled with the `# syntax=docker/dockerfile:1` first line so the frontend is pulled as an image and updated independently of the engine:

- `RUN --mount=type=cache,target=/root/.cache/pip` keeps a package cache across builds without putting it in a layer.
- `RUN --mount=type=secret,id=npmrc,target=/root/.npmrc` makes a secret available only during one instruction and absent from the image history; the secret is supplied with `--secret id=npmrc,src=$HOME/.npmrc`.
- `RUN --mount=type=ssh` forwards an SSH agent for private repositories.
- `RUN --mount=type=bind,from=build,source=/out,target=/in` reads files from another stage without copying them to a layer.
- Heredocs in `RUN` and `COPY`, `COPY --link` (layers independent of earlier ones, so rebasing is cheap), `ADD --checksum`, and `--chmod`.
- Build arguments `--build-arg` and `ARG` before `FROM`, and `--target` to stop at a stage.
- `--platform linux/amd64,linux/arm64` with `--push` builds a multi-architecture index. Cross-architecture steps run through QEMU user-mode emulation registered with `binfmt_misc`, which is slow, or natively through builder nodes of each architecture, or by cross-compilation inside the Dockerfile using `$BUILDPLATFORM` and `$TARGETARCH` [src: archwiki 5eb6b93a95459dfa].

Caching is where BuildKit pays off. Local cache invalidates by instruction text, and for `COPY` or `ADD` by the checksum of the files, so ordering matters: copy dependency manifests and install before copying source. For CI, where a runner starts clean, cache backends export and import cache metadata: `inline` (embedded in the image), `registry` (a separate cache image, `mode=max` to include intermediate stages), `local` (a directory), `gha` (GitHub Actions cache), `s3`, `azblob` [src: docker-docs 47e59f1fcc7e9c6e] [src: docker-docs 448338f6527488f8]. `docker buildx bake` reads an HCL, JSON or Compose file describing several targets, matrices and shared variables, and builds them in one invocation. BuildKit also produces provenance and SBOM attestations with `--provenance` and `--sbom`, which topic T08 uses.

### Compose

A `compose.yaml` has top-level `services`, `networks`, `volumes`, `configs` and `secrets`. A service names an `image` or a `build` context, and may set `ports`, `environment`, `env_file`, `volumes`, `depends_on`, `healthcheck`, `restart`, `deploy.resources.limits`, `profiles`, `command`, `user`, `cap_drop`, `read_only` and many more. A minimal example:

```yaml
services:
  web:
    build: .
    ports: ["127.0.0.1:8000:8000"]
    environment:
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/app
    depends_on:
      db: {condition: service_healthy}
    read_only: true
    cap_drop: [ALL]
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
    volumes: [dbdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 10
volumes:
  dbdata:
secrets:
  db_password:
    file: ./db_password.txt
```

Compose creates one default network per project, named after the project directory, and every service is reachable by its service name. `docker compose up -d`, `ps`, `logs -f`, `exec`, `run --rm`, `down` (add `-v` to delete named volumes) and `config` (print the fully resolved model, which is the first stop when interpolation misbehaves) are the daily commands. Variable interpolation reads the shell environment and a `.env` file next to the Compose file, with the documented precedence of shell over `.env` over defaults; several Compose v1 variables are unsupported in v2 [src: docker-docs 719e03aacd85fa71]. `depends_on` with `condition: service_healthy` orders startup, but only at start: Compose does not restart dependents if the database later fails. Multiple files layer via `-f base.yaml -f override.yaml`, and `compose.override.yaml` is read by default. Newer Compose features include `include` for modular files, `develop.watch` to sync or rebuild on file change, and `profiles` for optional services. Compose also accepts Docker-compatible sockets, so Podman users run it against `podman.socket` [src: archwiki b51a219f37bcda92].

## Assessment: the good, the bad and the ugly

The good: a gentle path from nothing to a running service; fast, parallel, cache-aware builds; secrets that stay out of image history; a Compose file that is simultaneously documentation and executable; a stable client API that a large ecosystem targets; and good multi-platform support. For a laptop or a single-server deployment, Compose is a reasonable production tool with `restart: unless-stopped`, health checks and a systemd unit to run `docker compose up`.

The bad: the daemon is a root-owned single point of failure and privilege. Compose is not an orchestrator: no rolling updates, no scheduling across hosts, no self-healing beyond restart policy. `depends_on` ordering is start-time only. The local cache can fill a disk: `docker system df` reports use and `docker builder prune` with `--filter until=` reclaims it. Cache-key subtleties cause wasted rebuilds; copying the whole source before installing dependencies invalidates the install layer on every change, and `ARG` values (even unused ones that appear in an instruction) affect keys. Unpinned base images, `apt-get install` without version control, and `curl | sh` in a `RUN` give builds that are not reproducible. The Docker documentation itself lists many `docker-compose` v1 settings that behave differently after migration.

The ugly: the socket. Mounting `/var/run/docker.sock` into CI jobs, dashboards or "Docker-in-Docker" helpers hands out root, and teams do it casually. Docker-in-Docker (`docker:dind`) needs `--privileged`. Firewall bypass by published ports, noted above, exposes databases to the network on hosts believed to be firewalled; the classic breach is `-p 5432:5432` on a cloud VM. Default `json-file` logs without rotation fill disks. `docker system prune -a --volumes` on the wrong host deletes data volumes of stopped services. Licensing and product changes around Docker Desktop and Docker Hub rate limits for anonymous pulls (introduced in 2020) have forced mirrors and credentials into CI. And the project's own deprecations (Docker Content Trust removed from the CLI in Engine 29, cgroup v1 deprecated, the `docker/docker` Go module superseded by `moby/moby` modules) mean that scripts need maintenance [web: docs.docker.com].

## Applications beyond this domain

BuildKit's graph-and-cache design is used far outside Dockerfiles. Frontends exist for other build languages; Earthly and Dagger build pipelines on the same solver; `docker/build-push-action` carries the model into CI; Bazel, Nix and Gradle share the idea of a content-addressed action cache. The Compose Specification is read by Podman, Kubernetes conversion tools (Kompose), Docker Desktop's extension tooling and some cloud services, so a Compose file works as an interchange format between local and managed environments [src: kubernetes-docs b5770e42f5dc5a10]. The split of CLI, daemon and API with a stable versioned REST interface is also the structure of libvirt, and of other systems where clients, scripts and dashboards must coexist. The principle behind `--mount=type=secret`, that credentials are delivered by a transient mount and not by a persisted artefact, applies to every build system.

## Examples

*A cache-friendly build.* A Python service rewrites `COPY . .` followed by `pip install -r requirements.txt` as `COPY requirements.txt .`, `RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt`, then `COPY . .`. Rebuilds after a source edit take seconds. `docker buildx build --progress=plain` prints `CACHED` per step to confirm. In CI, adding `--cache-from type=registry,ref=ghcr.io/org/app:cache --cache-to type=registry,ref=ghcr.io/org/app:cache,mode=max` makes a fresh runner behave like a warm one [src: docker-docs 4d068f1d1bb72f25].

*Multi-platform publish.* `docker buildx create --use --name multi --driver docker-container`, then `docker buildx build --platform linux/amd64,linux/arm64 -t registry.example/app:2.0 --push .` creates an index. `docker buildx imagetools inspect registry.example/app:2.0` lists each manifest; `docker run --platform linux/arm64` on an amd64 host uses QEMU to run it, which proves the image though not its speed.

*A failing example: leaked secret.* A Dockerfile contains `ARG NPM_TOKEN` and `RUN echo "//registry.npmjs.org/:_authToken=$NPM_TOKEN" > .npmrc && npm ci && rm .npmrc`. The token is gone from the final file system but remains in the layer that wrote it and in `docker history` as an argument. Replacing the build argument with `RUN --mount=type=secret,id=npm,target=/root/.npmrc npm ci` leaves no trace. The earlier token must still be revoked.

*Compose startup race.* A web service crashes at start with "connection refused" because the database accepts connections thirty seconds after its container is "running". `depends_on: [db]` alone only orders container creation. Adding a `healthcheck` on the database and `condition: service_healthy` removes the race, but the application should also retry connections, since the database can restart later.

*Firewall surprise.* A host with `ufw` set to deny incoming traffic runs `docker run -p 6379:6379 redis`. A scan from outside reaches Redis. `iptables -t nat -L DOCKER -n` shows the DNAT rule; the fix is publishing on `127.0.0.1`, or placing a DROP rule in the `DOCKER-USER` chain.

## Related problems and ideas

Alternative builders include Buildah (scriptable, Dockerfile-free builds that run rootless), Kaniko (builds in a Kubernetes pod without a daemon, now archived by its original maintainers, to verify), `ko` and Jib (language-specific builders that produce images without Dockerfiles), Cloud Native Buildpacks, and Nix's `dockerTools`. Compose competitors on a single host are Podman with Quadlet, k3s, and Nomad. For desktops, Podman Desktop, Rancher Desktop, OrbStack, Colima and Lima offer alternative VMs. Remote or ephemeral builders (BuildKit on Kubernetes, hosted builders with shared cache) address the problem of cold CI caches. The idea of treating Compose as the deployment format for small production systems, with Docker Swarm-like rollouts or with `docker compose` run by a CI job over SSH, is popular and informal.

## Active research

Open questions are mostly about supply chain and speed. How to make builds reproducible bit for bit, using fixed timestamps (`SOURCE_DATE_EPOCH`, supported by BuildKit's exporters), pinned inputs and deterministic layer ordering, is under active work in BuildKit and in projects such as `reproducible-containers`. Lazy pulling with `stargz`, `nydus` or SOCI tries to shorten the time from `docker pull` to ready, and the containerd image store makes these snapshotters easier to combine with Docker. Policy evaluation during builds (Docker's build policies feature, which lets a policy decide which base images or sources a build may use) is a new area [src: docker-docs b61c7482b581fe1e]. On the Compose side the community discusses how far to extend the Specification toward Kubernetes-like features, and how to represent GPUs and devices portably, since AI workloads depend on them.

## Future direction

Docker Engine releases now follow a major version per year (29 in 2025, with minor releases through 2026); the containerd image store, nftables and rootless improvements are the lines to follow, with cgroup v1 support ending no earlier than 2029 [web: docs.docker.com]. BuildKit continues to move features such as build policies and attestation handling into the default path. Expect more CI systems to treat the cache backend, the provenance attestation and the SBOM as one pipeline step. Compose is moving toward development loops (`watch`, `include`) and managed-environment export. For a Linux administrator, the pragmatic stance is that Docker's CLI and Compose files are an interface that every serious engine speaks, while the daemon is one implementation among several; learn the file formats and the cache model well, and treat the socket as a root credential.
