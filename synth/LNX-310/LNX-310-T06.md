# Registries, Skopeo and mirrors: moving images safely

## Define the problem

Every container start begins with a name such as `nginx:1.27` and ends with bytes on a node. In between sits a registry: a network service that stores content-addressed blobs and the small manifests that tie them together. Operators must answer practical questions that the image format alone does not settle. Where does an unqualified name resolve, and who decides? How does a client prove who it is, and how does a server decide what it may pull or push? What happens when the public registry is slow, rate limited, unreachable or compromised, or when the production network has no route to the internet at all? How can an image be copied between registries or into an air-gapped site while keeping its digest, its signatures and its platforms intact? And how do you keep a private registry from growing without bound?

This slice covers the registry protocol from the client's point of view, the client configuration in the containers and Docker ecosystems (`registries.conf`, `policy.json`, `daemon.json`, containerd's `hosts.toml`), authentication, mirrors and pull-through caches, `skopeo` as the tool for inspecting and copying images without a daemon, and the operational realities of running a registry. Signing and verification are the subject of T08 and are touched only where configuration meets them.

## History and approaches

Docker Hub (2013) was the first public registry and, because the CLI's default for names without a host was Hub, it acquired a gravitational pull that persists: the short names `ubuntu` and `alpine` mean `docker.io/library/...` in Docker, and a client that sends no explicit host reaches Hub. The original registry was a Python program; Registry v2 (2015) rewrote it in Go with content addressing, resumable uploads and a manifest model, and the code is now the CNCF Distribution project that other products embed, as `registry:2` or `registry:3`. Competing and complementary services followed: Quay, Harbor (VMware, then CNCF, adding vulnerability scanning, replication and RBAC), GitLab and GitHub registries tied to repositories, cloud registries (ECR, ACR, Artifact Registry), Artifactory and Nexus (universal repositories), and lightweight OCI-native servers such as zot.

Two lessons came from experience. First, depending on the public registry is a reliability and supply-chain risk. Docker introduced pull rate limits for anonymous and free accounts in 2020, and CI fleets sharing a NAT address suddenly saw `toomanyrequests` failures; the response was authenticated pulls, a pull-through cache, or mirroring base images into a private registry. Second, unqualified names are ambiguous. With a search list of several registries, `podman pull nginx` could be satisfied by whichever answered first, which is a name-squatting hazard. The containers tools therefore introduced *short-name aliases* and a `short-name-mode` (`enforcing`, `permissive`, `disabled`) so that ambiguous names prompt or fail instead of silently choosing, and Red Hat shipped an alias table for popular images [src: rhel-10-docs c7c17293eb4437e4].

Copying images historically meant `docker pull`, `docker tag` and `docker push` through a daemon, which re-compresses nothing but needs local storage, loses multi-arch indexes (a pull fetches only one platform) and can alter manifests. Skopeo, created at Project Atomic around 2016 for inspecting remote images without pulling, grew into the copy tool that reads and writes any supported transport and preserves manifests when asked. Its sibling `oc-mirror` (OpenShift) and `crane` (from go-containerregistry), `regctl`, and `oras` fill adjacent niches. The partial successes include Docker's `registry-mirrors` key, which mirrors only Docker Hub, and registry replication in Harbor; the failed pattern is the hand-edited `/etc/hosts` entry or retagging to `internal/` names that breaks digest pinning and provenance.

## Current state

### The protocol, as a client sees it

A registry speaks the OCI Distribution API under `/v2/`. The client does `GET /v2/`; a `401` with a `WWW-Authenticate: Bearer realm=...,service=...,scope=...` header begins a token flow: the client calls the realm (an auth service) with credentials and the requested scope (`repository:library/nginx:pull`), receives a short-lived token, and repeats the call with `Authorization: Bearer`. Basic authentication is used by simpler registries. Pulling is then `GET /v2/<name>/manifests/<tag-or-digest>` with an `Accept` header listing the manifest media types the client understands, followed by `GET /v2/<name>/blobs/<digest>` for the config and each layer; blobs may redirect to object storage (a `307` to a CDN or S3 URL) so the registry never serves the bytes itself. Pushing uses `POST /v2/<name>/blobs/uploads/`, a `PATCH` or `PUT` of data, a digest check, `HEAD` to skip blobs the registry already has, cross-repository mounts to avoid re-upload, and finally `PUT /v2/<name>/manifests/<ref>`. Tags are mutable pointers; digests are immutable names. A registry that supports the referrers API lists signatures and SBOMs attached to a subject digest.

### Client configuration

Podman, Buildah, Skopeo and CRI-O read the same files. `/etc/containers/registries.conf` (and drop-ins in `registries.conf.d/`, with per-user `~/.config/containers/registries.conf` taking precedence for rootless) is TOML in the v2 format. The important keys are:

```toml
unqualified-search-registries = ["registry.example.com", "registry.access.redhat.com"]
short-name-mode = "enforcing"

[[registry]]
prefix = "docker.io"
location = "docker.io"

[[registry.mirror]]
location = "mirror.internal:5000/dockerhub"

[[registry]]
location = "dev-registry.internal:5000"
insecure = true

[[registry]]
location = "registry.badvendor.example"
blocked = true
```

A `[[registry]]` block matches a name by `prefix`; `location` is where to actually fetch from, so a rewrite is possible (`prefix = "registry.k8s.io"`, `location = "mirror.internal/k8s"`). Mirrors listed under it are tried before the primary location, with `pull-from-mirror` selecting `all`, `digest-only` or `tag-only` (a digest-only mirror is safe because content is verified). `insecure = true` allows HTTP or untrusted TLS for a registry; `blocked = true` forbids it. The Red Hat guide explains editing the file as root and lists these settings [src: rhel-10-docs c7c17293eb4437e4]. Private CAs go under `/etc/containers/certs.d/<host:port>/` as `ca.crt`, with `client.cert` and `client.key` for mutual TLS (Docker uses `/etc/docker/certs.d/` similarly).

Signature policy lives separately in `/etc/containers/policy.json`: a default requirement (for example `insecureAcceptAnything` or `reject`) and per-transport, per-scope overrides such as `signedBy` or `sigstoreSigned`, with `registries.d/*.yaml` giving the signature store locations. The pairing is important: `registries.conf` decides where bytes come from, `policy.json` decides whether they are acceptable.

Credentials are stored by `podman login` and `skopeo login` in `${XDG_RUNTIME_DIR}/containers/auth.json` (cleared at logout, the safer default for rootless) or `~/.config/containers/auth.json`; `docker login` uses `~/.docker/config.json`. Both can point to credential helpers (`docker-credential-pass`, `-secretservice`, cloud helpers) that fetch tokens instead of storing base64 passwords in a file, and `REGISTRY_AUTH_FILE` selects a file. A base64 string is encoding, not encryption.

Docker's daemon has its own, narrower mirror feature: `registry-mirrors` in `daemon.json` applies to Docker Hub only, and `insecure-registries` lists plain-HTTP hosts. containerd (and so Kubernetes nodes using it) uses per-host directories, `/etc/containerd/certs.d/<host>/hosts.toml`, with `server`, and `[host."https://mirror"]` entries carrying `capabilities = ["pull", "resolve"]`, so a mirror can be pull-only. CRI-O reuses `registries.conf`. Kubernetes adds `imagePullSecrets` on Pods or ServiceAccounts, pointing to a Secret of type `kubernetes.io/dockerconfigjson`, and `imagePullPolicy` (`Always`, `IfNotPresent`, `Never`; the default is `Always` for `:latest` and `IfNotPresent` otherwise) [web: kubernetes.io].

### Skopeo

Skopeo is a daemonless CLI that works on *image references* with a transport prefix: `docker://` (a registry), `oci:` (an OCI layout directory), `dir:` (a simple directory with manifests and blobs), `docker-archive:` and `oci-archive:` (tar files), `containers-storage:` (Podman's local store) and `docker-daemon:`. The core commands, as described in the distribution documentation [src: ubuntu-server-docs 0a2e76f289069010]:

- `skopeo inspect docker://host/img:tag` shows config-derived metadata and layers; `--raw` prints the manifest or index untouched; `--config` shows the image configuration.
- `skopeo list-tags docker://host/repo` lists tags.
- `skopeo copy SRC DEST` transfers an image. `--all` copies every platform of an index, otherwise only the host's platform (or `--override-arch`) is taken, which is a common surprise. `--preserve-digests` keeps manifest bytes identical so that the digest is unchanged, and fails if a conversion would be needed; `--format oci|v2s2` forces a manifest type; `--src-creds`, `--dest-creds` and `--authfile` provide credentials; `--src-tls-verify=false` disables verification for a source (avoid it); `--sign-by` and `--sign-by-sigstore` sign during the copy; `--dest-compress-format zstd` recompresses.
- `skopeo sync --src docker --dest dir|docker image-or-yaml` mirrors a repository or a list of images from a YAML file, optionally with tag regexes, which makes mirroring a curated list a scheduled job.
- `skopeo delete docker://host/img@sha256:...` deletes a manifest on registries that allow it.

A Red Hat guide demonstrates copying from an external registry to an internal repository as the way to populate one [src: rhel-10-docs 035bdeb6ceed089a]. Because copy streams layer blobs between source and destination, no Docker daemon or local root is needed, and copy reuses blobs that the destination already holds.

### Mirrors and caches

There are three structural options. A **pull-through cache** (a registry in proxy mode: `proxy.remoteurl` in Distribution's configuration, or "proxy cache" projects in Harbor) fetches from the upstream on a miss and serves later pulls locally; it is transparent but depends on upstream for first access, and the Distribution proxy supports one upstream per instance. A **full mirror** pre-populates with `skopeo sync` or `oc-mirror`, which suits air-gapped sites where only an explicit list of images may cross the boundary. **Replication** (Harbor, Quay, cloud registries) copies projects between registries on a schedule or on push. Whichever is used, clients reach the mirror through the `registries.conf` or `hosts.toml` rewrite; pinning by digest makes that safe, since the client verifies the content whichever host served it.

### Running a registry

The minimum viable private registry is `registry:2` with a TLS certificate and htpasswd authentication, storing to a filesystem or object store, but production registries add authorization per repository, quotas, vulnerability scanning, signing policy and retention. Deletion needs thought: `DELETE` on a manifest removes only the reference, and storage is reclaimed by running garbage collection (`registry garbage-collect`), historically with the registry in read-only mode to avoid racing an upload. Large registries therefore apply tag-retention rules, such as keep the last ten tags and anything tagged as a release, and treat images deployed by digest as live.

## Assessment: the good, the bad and the ugly

The good: a small, well-specified protocol; content addressing makes mirroring and caching safe by construction; any OCI-compliant tool can talk to any compliant registry; and clients support layered configuration (system, user, drop-in). Skopeo makes cross-registry copy, inspection and air-gap transfer scriptable and daemon-free, and keeps digests when asked.

The bad: configuration is split across tools with different file formats and semantics. A Docker host's `daemon.json` mirror does not affect Podman; Podman's `registries.conf` does not affect containerd; Kubernetes nodes have the containerd or CRI-O configuration and `imagePullSecrets` besides. Mirrors that are slow or stale produce confusing errors, because the client may fall back to the origin and mask the problem, or the reverse. Tag-based mirrors drift from upstream; a tag that was updated upstream may remain old locally. Multi-arch handling is the favourite source of mistakes: `skopeo copy` without `--all` yields a single-platform manifest, and a mirror that cannot store indexes breaks ARM nodes. Registry garbage collection is manual in the base project, and storage grows with CI tags.

The ugly: credentials and trust. Long-lived tokens in CI, `auth.json` files committed or left in images, and base64 passwords in `imagePullSecrets` copied across namespaces are common leaks. `insecure = true` and `--tls-verify=false` start as quick fixes and live forever. Unqualified names resolve differently across hosts: a developer's `podman pull myapp` hits a different registry than the cluster's. Registry compromise or typosquatting of popular names is a real supply-chain vector, and any process that resolves tags at deploy time rather than digests is exposed. Public registry limits and policy changes (rate limits, retention of inactive images, plan changes) have forced emergency work on organisations that never planned for Docker Hub being unavailable. Exposing an unauthenticated registry on the internet leaks proprietary images, and accepts pushes that replace tags.

## Applications beyond this domain

The OCI registry model stores more than container images. Helm charts, Sigstore signatures and attestations, SBOMs, WebAssembly modules, Terraform and Flux configuration, policy bundles for OPA, and machine-learning model weights can all be pushed as OCI artefacts and referenced by digest, so one piece of infrastructure, with its authentication, replication and retention, serves them all. The mirror-and-pin pattern is the same as an internal package mirror for apt, PyPI, npm or Go modules; the skopeo `sync` job corresponds to `reposync` and `apt-mirror`. The token-based auth flow is widely used in other APIs. The idea that a name is resolved through a configuration layer that can rewrite the location without changing the identifier is also how DNS search lists, package repositories and `go env GOPROXY` work.

## Examples

*Inspect before you pull.* `skopeo inspect --raw docker://docker.io/library/alpine:3.21 | jq '.manifests[].platform'` prints the platforms of the index, and `skopeo inspect docker://docker.io/library/alpine:3.21 | jq -r .Digest` gives the digest to pin. Nothing was downloaded beyond JSON.

*Populate an internal registry.* `skopeo copy --all --preserve-digests docker://docker.io/library/alpine:3.21 docker://registry.internal/base/alpine:3.21` copies every platform and keeps the same digest. Comparing `skopeo inspect --format '{{.Digest}}'` on both sides proves it.

*Mirror configuration.* To make all Hub pulls on a build host go to an internal cache, add a `[[registry]]` block for `docker.io` with a `[[registry.mirror]]` to the cache, set `pull-from-mirror = "digest-only"` if the cache is only trusted for pinned references, and check with `podman pull --log-level=debug docker.io/library/alpine` which host was contacted.

*A failing example: rate limit.* A pipeline with fifty parallel jobs fails every morning with a `toomanyrequests` error, because all jobs pull base images anonymously from one egress IP. Authenticating with a service account lifts the limit, but the lasting fix is a pull-through cache in the build network and a base-image mirror, so builds do not depend on Hub at all.

*A failing example: wrong architecture.* A team mirrors `app:2.0` with plain `skopeo copy` from an amd64 workstation, and ARM nodes later report `exec format error`. The mirror has a single-platform manifest. Re-running with `--all` fixes it, and `skopeo inspect --raw` on the destination shows an index with both platforms.

*A name that means two things.* In an enforcing short-name configuration, `podman pull httpd` prompts or fails when two search registries have an `httpd`; the answer is to use a fully qualified name in Containerfiles and to keep the search list short.

## Related problems and ideas

Adjacent tools include `crane` and `regctl` (small registry clients), `oras` (artefacts), `cosign copy` and `cosign triangulate` for signature objects, `oc-mirror` for OpenShift release payloads and operators, Harbor for projects, replication, scanning and robot accounts, and `dragonfly` and `spegel` for peer-to-peer distribution inside a cluster so that a thousand nodes do not hit the registry at once. Lazy-pulling formats (estargz, SOCI) change what a pull means. An opposed design avoids registries for some purposes: `docker save | ssh host docker load`, or shipping OCI layouts on removable media for isolated networks, trading tooling for simplicity. Not yet mainstream are content-addressed discovery of artefacts through the referrers API as the only linkage between image and attestation, and transparency logs for registry content.

## Active research

Registry work is currently about attachments, scale and trust. The referrers API and the `subject` field standardise how signatures, SBOMs and attestations hang off an image, and a fallback tag schema exists for registries that lack the API, so implementations are still converging. Distribution v3 modernises the reference registry. Peer-to-peer and lazy pulling aim at start-up time for large images such as machine-learning stacks measured in gigabytes. Researchers study mirror poisoning and rollback attacks, where a stale or malicious mirror serves an old tag, and the defences are digest pinning and signed metadata with freshness (TUF-style) rather than TLS alone. Policy engines that evaluate registry, signature and provenance before admission are an active area in Kubernetes, and Docker's build policies bring a similar idea to the client side [src: docker-docs b61c7482b581fe1e].

## Future direction

Expect more organisations to treat the public registry as an upstream feed behind a corporate cache and to require digests and signatures on everything that runs. Short-name resolution will tighten toward fully qualified names. Tools will converge on referrers-based attachments, and registries will show provenance and SBOMs next to images. Cloud providers keep adding pull-through cache rules (ECR, Artifact Registry) that remove the need to run one. Client-side, containerd's transfer service and the `hosts.toml` model are the likely single point for Kubernetes mirror configuration. For an administrator, the stable skills are: qualify names, pin digests, mirror what you depend on, keep credentials short-lived and out of images, and verify mirrors with `skopeo inspect` instead of trusting that they work [web: distribution.github.io].
