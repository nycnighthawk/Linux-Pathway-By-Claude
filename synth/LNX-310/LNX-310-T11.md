# Windows containers: what is different, and what a Linux administrator must know

## Define the problem

Most of the containers in a mixed enterprise are Linux containers, but a good share of its older, business-critical software is not. .NET Framework web applications, services that depend on the registry, COM components, IIS sites and applications that need Active Directory authentication run only on Windows. Organisations that move to a container platform want those workloads to follow the same path as everything else: built from a recipe, stored in a registry, started by an orchestrator, scaled and replaced, instead of being hand-configured servers. A Linux administrator who runs the platform will meet these workloads, and needs to know what carries over, what does not, and where the platform's assumptions break.

The gap is that Windows has no equivalents of several Linux building blocks. There are no Linux namespaces and cgroups, no seccomp, no `unshare` or `nsenter`, no capabilities, and, most importantly, no stable system-call interface between user mode and the kernel, since Windows applications call libraries in user mode (Win32 and `ntdll`) and Microsoft changes the kernel interface between releases. These differences shape how Windows containers are built, versioned, isolated and scheduled. This slice, at a survey depth, describes the Windows container model, its isolation modes, the version-matching rule, the base images, the orchestration limits in Kubernetes, how Linux-trained staff can run and test them, and the main reasons to choose an alternative.

## History and approaches

Windows got containers later than Linux. Windows Server 2016 (and Windows 10 Anniversary Update, build 14393) shipped the first container support, developed with Docker, which ported its engine to the Windows host compute service (HCS). Microsoft's compute service wraps the kernel features that Windows added for the purpose: job objects extended into *server silos*, which give a group of processes a private view of the object manager namespace, file system, registry, network compartments and process ID space, and a layered file system filter driver (`wcifs`) that provides copy-on-write layers similar in spirit to overlayfs. Docker for Windows and the Docker Engine on Windows Server used this stack, and later `containerd` with the `hcsshim` library became the runtime that Kubernetes and others use, with a runtime shim for Windows analogous to the Linux shim v2. Windows layers use the OCI image format with a different `os` field and a layer format that includes both file and registry hives.

The original isolation model was **process isolation**: containers share the host's kernel. Because Windows user mode and kernel mode were designed to ship together, the containers' user-mode files (the base image) must be compatible with the host's kernel, and early releases enforced an exact match of build numbers, and for Windows Server 2016 even of revision numbers. The cost was painful: every monthly patch of the host could break images. Microsoft added **Hyper-V isolation**, where each container runs inside a small, optimised utility VM with its own Windows kernel, so the host and the image may differ in version, and also so that hostile tenants are separated by a hypervisor. For the later Windows Server releases, Microsoft relaxed the rule: revision numbers no longer need to match from version 1809 on, and Windows Server 2022 hosts can run Windows Server 2019 images only under Hyper-V isolation, while recent releases allow Windows 11 hosts to run Server 2022 images with process isolation [web: learn.microsoft.com].

Other approaches did not survive. Windows Server version 1709 and later "semi-annual channel" images, with a six-month cadence, produced a flood of base-image versions and ended; the long-term channels (ltsc2019, ltsc2022, ltsc2025) became the supported tags. Docker Swarm on Windows and Service Fabric hosted Windows containers early, before Kubernetes support for Windows nodes arrived (beta in 1.14, 2019, GA in 1.18; to verify), and the Docker Swarm role faded. Running Linux containers on Windows desktops used a Linux VM (Docker Toolbox, then Hyper-V and WSL 2 backends), and a short-lived LCOW (Linux Containers on Windows) mode embedded a utility VM per container; both address a different problem, which is running Linux software on a Windows machine, and must not be confused with Windows containers. The emerging pattern is that Windows containers are a compatibility tool for existing Windows workloads, run on Windows Server nodes under process isolation or on Hyper-V isolation for mixed tenancy, alongside a Linux-first platform.

## Current state

### Architecture and tools

A Windows container is created by the Host Compute Service from a set of read-only layers (a base image plus application layers) and a writable scratch layer. Namespacing is provided by silos: the container sees its own file system and registry (a registry hive overlay for the container), its own network ports and compartment, its own process and thread ID space and object-manager namespace. Resource controls come from job objects (CPU rate and weight, memory limits, process count, storage IOPS and bandwidth). There are no capabilities, no seccomp and no user-namespace remapping; privilege is controlled by the container's identity (`ContainerUser` is a low-privilege account, `ContainerAdministrator` is the default administrator) and by integrity levels and ACLs [web: learn.microsoft.com].

Windows container hosts run `containerd` (the recommended runtime with Kubernetes) or Docker Engine (`dockerd` as a Windows service, named pipe `\\.\pipe\docker_engine` in place of a Unix socket), and Mirantis Container Runtime. Tools: the same Docker CLI (`docker run`, `build`, `inspect`, `exec`), `ctr`, `nerdctl` and `crictl` for containerd; PowerShell cmdlets for features and networks (`Install-WindowsFeature containers`, `Enable-WindowsOptionalFeature -Online -FeatureName containers`); and HCS tooling for lower level diagnosis (`hcsdiag`, `Get-ComputeProcess`). BuildKit on Windows is supported in a limited form [src: docker-docs 544d4d55cc8758c6].

### Base images and versioning

Microsoft publishes four families on its container registry (`mcr.microsoft.com`): `windows` (the full API set minus server roles), `windows/server`, `windows/servercore` (a large subset with the full .NET Framework), and `windows/nanoserver` (the smallest, for .NET and Go and similar programs with no Win32 GUI or legacy components). The images run in size from about a hundred megabytes for Nano Server to several gigabytes for Server Core, so pulls are slow and node image caches matter. Tags must be explicit: Microsoft stopped publishing `latest` for these images in 2019. Tags look like `ltsc2022`, `ltsc2025`, `1809`, or a full build number such as `10.0.17763.437`, and one can request a specific cumulative update by KB number. Because no one rebuilds them for you, the application image should pin the tag and rebuild when the base image is patched.

The compatibility rule has three parts. With **process isolation**, the build number of the container's OS must match the host (with the Windows 11 and Server 2022 exception). With **Hyper-V isolation**, an image from the same or an older release can run on a newer host: a Windows Server 2025 host runs images from 2025, 2022, 2019 and 2016, but not the reverse, and a Windows Server 2019 host cannot run a 2022 image at all. Windows 10 hosts handle only Hyper-V isolation for older images. When the rule is violated, the engine fails the start with an error that the container's operating system does not match the host's, in a form that includes a hexadecimal HCS error code, and Kubernetes shows `CrashLoopBackOff` or `ContainerCannotRun` [web: learn.microsoft.com]. The remedies are rebuilding on a matching base, switching to `--isolation=hyperv`, or scheduling to a node with the right OS version (node labels and selectors).

Isolation modes are selected per container: `docker run --isolation=process ...` or `--isolation=hyperv`. Server hosts default to process isolation, and client hosts (Windows 10 and 11) default to Hyper-V isolation. In the process case, `docker top` and the host's `Get-Process` show the same process ID; in the Hyper-V case, the host shows only a `vmwp` worker process for the utility VM, and the container's processes are invisible from outside [web: learn.microsoft.com]. Hyper-V isolation needs hardware virtualisation and, when the host is itself a VM, nested virtualisation.

### Dockerfile, networking and storage differences

Dockerfiles for Windows use the same instructions, with Windows-specific habits: `SHELL ["powershell", "-Command", "$ErrorActionPreference = 'Stop';"]` changes the shell for `RUN`; paths use backslashes and drive letters (and escape characters need `# escape=\``); `USER ContainerAdministrator` or `USER ContainerUser`; and multi-stage builds, with a large SDK image to build and `nanoserver` or `servercore` to run, remain the way to reduce size. Features of Windows may be installed through `dism` or `Install-WindowsFeature` in a layer, or, for IIS, the `mcr.microsoft.com/windows/servercore/iis` image. Applications must write logs to stdout or use a tool such as LogMonitor that tails ETW, event-log and file sources to the console, because `docker logs` only sees the container's standard streams.

Networking uses the Host Networking Service (HNS) and Hyper-V virtual switches, with network drivers `nat` (default on a single host), `transparent`, `l2bridge`, `l2tunnel` and `overlay`. There is no `host` network mode in the Linux sense, no iptables, and published ports go through NAT rules in HNS. Containers get a vNIC and DNS from the host. Storage supports bind mounts of directories and named pipes (useful for talking to the Docker daemon from a container), volumes, and in Kubernetes `emptyDir`, ConfigMap and Secret volumes, with `hostPath` and SMB-based CSI options; there is no support for mount propagation, shared memory or sharing synchronisation objects with the host [web: learn.microsoft.com]. Group Managed Service Accounts (gMSA) give containers an Active Directory identity without joining the container to the domain, through a credential spec file. The credential-spec mechanism is the usual way a Windows container reaches SQL Server or file shares with integrated authentication.

### Windows in Kubernetes

Kubernetes treats Windows as a worker node type. The control plane must be Linux. Windows nodes run the `kubelet` and `kube-proxy` as services and a CNI plugin (Calico, Flannel with host-gw or VXLAN, or Cilium on Linux nodes only), with `containerd` as the runtime; the supported node operating systems in current releases are Windows Server 2022 and 2025. Only process isolation is supported by Kubernetes on these nodes, so the container images must match the node's build, which makes the node label and selector rule from the previous section part of normal operations. A pod is Windows-only: it cannot mix Windows and Linux containers; it declares `spec.os.name: windows` and a `nodeSelector` of `kubernetes.io/os: windows`, and usually a taint on Windows nodes and a matching toleration keeps Linux pods away. Many Linux-specific pod fields are rejected: `hostPID`, `hostIPC`, `seccompProfile`, `sysctls`, `fsGroup`, `runAsUser`, `runAsGroup`, container `privileged`, `capabilities`, `readOnlyRootFilesystem` and `allowPrivilegeEscalation`. `HostProcess` containers replace privileged ones for node administration. HugePages are not supported, and the kubelet on Windows reserves resources less strictly: node-allocatable enforcement and some eviction behaviours are not implemented, so a node can be over-committed [src: kubernetes-docs 5526aaf0ed241916] [src: kubernetes-docs 7a7da87d5af048b6].

Windows pod security differs: `RunAsUserName` selects the account, the pod security standards map less cleanly, and secrets are written as files on a volume with ACLs, not memory-backed tmpfs, because Windows has no tmpfs, and for that reason the Docker documentation notes that Swarm secrets on Windows are stored in clear on disk unless the host disk is encrypted [src: docker-docs ab627e9bfceb2a3a].

## Assessment: the good, the bad and the ugly

The good: legacy Windows applications gain image-based deployment, registries, orchestration and repeatable environments without being rewritten; a team can use the same Docker CLI, the same registry, the same Kubernetes API and CI patterns, and run both kinds side by side. Hyper-V isolation gives a hypervisor-strength tenant boundary (which on Linux needs Kata or similar), and server silos give the lighter option. Developers on Windows desktops can test locally with the same images.

The bad: images are large and slow to pull, which hurts scaling, since nodes cache layers and a new node pulls gigabytes. The version matching rule creates operational coupling between host patching and image rebuilding; a node image upgrade can strand workloads. Container-level security is thinner than on Linux: no capability dropping, no seccomp, no user namespaces, so process isolation relies on the kernel and on Microsoft's patching, and Microsoft's own guidance treats Hyper-V isolation as the choice for hostile multi-tenancy. Feature gaps in Kubernetes (no privileged mode, no Hyper-V isolation, no Linux-style resource enforcement, a Windows-only pod, fewer CNIs and CSI drivers, limited observability tooling) complicate platforms designed Linux-first. Licensing matters: Windows container hosts need Windows Server licences, and Hyper-V isolation consumes extra memory per container.

The ugly: operational surprises. Windows Update on a node changes the build and breaks process-isolated pods until images are rebuilt. Interactive debugging is clumsy without `nsenter`: you use `docker exec` or `kubectl exec` with PowerShell, ETW traces, `Get-ComputeProcess` and PerfView. Many applications assume a full desktop-like environment: services that use COM, GUI libraries, or Windows features unavailable on Nano Server do not run, and moving to Server Core inflates the image. Logs and event-log data are not in the standard stream by default. Active Directory integration through gMSA needs host configuration and domain administration, and a missing or misconfigured credential spec shows up as authentication failures at runtime. The ecosystem is smaller: fewer scanners support Windows images fully, fewer public images exist, and Linux-oriented tools (Trivy supports Windows to a degree, but Falco, Tetragon and eBPF tooling do not apply). And mixing Linux and Windows nodes in one cluster doubles the number of images, node pools, upgrade tracks and failure modes.

## Applications beyond this domain

The version-coupling problem generalises to any system where applications link against the host's user-space and the kernel interface is unstable: containers on macOS (via VMs), unikernels, and device-specific OS images in embedded work. The Windows hybrid approach, cheap shared-kernel containers for trusted workloads and utility VMs for untrusted ones, is the same trade made on Linux with runc versus Kata or Firecracker, and Microsoft's Hyper-V isolation is among the earliest production deployments of that choice. The credential-spec approach to identity, a service identity assigned by the platform without the workload joining a domain, parallels workload identity on Kubernetes, SPIFFE and cloud IAM roles for pods. Server silos and job objects show that a container is a set of per-process views plus limits, whatever the kernel: the same definition as in topic T01. Even outside containers, Windows Sandbox and Application Guard use the same utility-VM technology.

## Examples

*Running a process-isolated container and proving what isolation means.* On a Windows Server 2022 host, `docker run -d mcr.microsoft.com/windows/servercore:ltsc2022 ping -t localhost` then `docker top <id>` shows the process with a PID, and `Get-Process ping` on the host lists a process with the same PID: it is one kernel. Re-running with `--isolation=hyperv` and repeating the check, the host finds no `ping`, but `Get-Process vmwp` shows the VM worker. This is the Windows version of looking at `/proc/<pid>/ns` on Linux [web: learn.microsoft.com].

*A multi-stage .NET build.* The first stage uses an SDK image to `dotnet publish -c Release -o /out`, and the final stage starts from the ASP.NET runtime image on Nano Server (`mcr.microsoft.com/dotnet/aspnet:8.0-nanoserver-ltsc2022`), copies `/out`, sets `USER ContainerUser` and the entrypoint. The final image is a few hundred megabytes, against several gigabytes with Server Core.

*A failing example: version mismatch.* A pipeline builds an image on a `ltsc2022` runner and deploys it to an AKS or on-premises node pool that was upgraded to Windows Server 2025 last week. Pods go to `CrashLoopBackOff` with an HCS error reporting an operating-system mismatch. Remedies: rebuild on `ltsc2025`, or keep a separate node pool with the older build and route pods to it with a `nodeSelector` on the OS build label. The lasting fix is to build and deploy the base-image tag from the same variable that provisions the node image.

*A failing example: logs that vanish.* An IIS application writes to `C:\inetpub\logs` inside the container. `kubectl logs` is empty and the data disappears with the pod. Adding LogMonitor in the entrypoint to forward the log files and the event log to stdout, or mounting a volume for the log directory, fixes it.

## Related problems and ideas

The neighbouring problems are running Linux containers on Windows (WSL 2 and Docker Desktop, where a Linux kernel runs in a lightweight VM and Linux-style isolation applies inside it), and running Windows applications on Linux (Wine and Proton, which reimplement the API; or full VMs). Modernisation paths avoid Windows containers altogether: porting .NET Framework to modern .NET on Linux, using the Windows Compatibility Pack, or running Windows workloads in VMs with KubeVirt, which treats a Windows VM as a Kubernetes-managed object and so brings the Windows application into the cluster without containerising it [src: kubevirt-user-guide 63cbf64971401f4d]. WebAssembly runtimes offer another route for new code. Not yet mainstream: improving the user/kernel boundary stability so that process isolation across versions is routine (Microsoft's stated direction, which led to the relaxation that lets Windows 11 hosts run Server 2022 images), and Linux-style OCI features such as user-namespace-like mapping for Windows.

## Active research

Work in this area is mostly engineering within Microsoft and the Kubernetes Windows special interest group: widening the supported combinations of host and image versions under process isolation, supporting Hyper-V isolation under Kubernetes through the runtime class mechanism (a long-requested item), making `HostProcess` containers a route to node administration, improving networking performance and observability on HNS, reducing image size through new base images, and bringing the Linux security features of the pod security standards to Windows in some form. Security researchers study escape techniques through the silo and filter-driver layers, which differ from Linux ones, and the resistance of utility-VM isolation. A general open question is how much of the OCI runtime specification can be expressed for Windows; the specification has a `windows` section covering layer folders, network settings, resources and Hyper-V options, and the 1.1 and 1.2 releases extended process-level options such as CPU affinity to Windows [web: github.com].

## Future direction

Microsoft's documentation applies to Windows Server 2016 through 2025 and treats Windows 11 as a development host that can run Server 2022 and, from the 24H2 release, Server 2025 images under both isolation modes [web: learn.microsoft.com]. Kubernetes lists only Windows Server 2022 and 2025 nodes as supported at present, and its Windows documentation keeps narrowing the compatibility surface [src: kubernetes-docs f0d454ffe3e31ba6]. Expect a slow convergence: Windows containers stay a compatibility feature for workloads that cannot move; new workloads target Linux. The sensible plan for an administrator is to inventory which applications truly need Windows, keep them in a separate node pool with explicit version labels, pin and rebuild base images on a schedule tied to node patching, prefer Nano Server or modern .NET on Linux wherever possible, and evaluate KubeVirt or VMs when containerising would cost more than it saves.
