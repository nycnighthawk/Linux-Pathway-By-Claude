# Container supply chain: SBOMs, signatures and vulnerability scanning

## Define the problem

A running container is the end of a long chain: upstream source, language packages, a base image from a vendor, a build system, a registry, an orchestrator that decides to pull it. Compromise at any link reaches production, and the operator usually cannot see most of the chain. Three questions recur. What is inside this image, precisely enough to say whether a newly announced vulnerability affects it? Who built it, from which source, with which tools, and was the artefact altered afterwards? And are the known weaknesses in it serious enough, and reachable enough, to block a release?

Practical answers have three parts. A *software bill of materials* (SBOM) is a machine-readable inventory of components. A *signature* with an *attestation* binds an image digest to an identity and to claims about how it was made, so that a deployment gate can verify them. A *scanner* matches the inventory against vulnerability databases, and a policy decides what follows. This slice covers SBOM formats and generation, Sigstore's cosign for signing and verifying images and attaching attestations, Trivy as the representative open source scanner, and how the three connect in a pipeline and an admission policy. It places them in the broader frameworks of NIST guidance and SLSA, without treating those in full.

## History and approaches

Vulnerability management for packages is old: distributions published advisories and `apt` or `rpm` tracked versions, so the inventory was the package database. Containers broke this in two ways. Images contain packages from many sources (distribution packages, language ecosystems, copied binaries) and an image can be assembled by dozens of tools, so there is no single database. And images are immutable and deployed in large numbers, so the question shifted from whether a host is patched to which of thousands of images contain a given library.

Early container security was thin. Docker's own scanning service (Nautilus, 2016) and CoreOS Clair (2015) were the first layer-aware scanners, with Clair becoming the engine of Quay. Docker Content Trust, based on Notary v1 and The Update Framework (TUF), added publisher signatures to tags in 2015, but it relied on key management users found cumbersome, was Docker-specific, did not scale to automated CI, and has now been removed from the Docker CLI in Engine 29 [src: docker-docs 6820940db4b6c5c3] [web: docs.docker.com]. Signing with GPG through `skopeo`/`podman` and `signedBy` policies worked for Red Hat and enterprise estates but never became a general practice, partly because it needed a detached signature store.

Two events reshaped the field. The SolarWinds build compromise (2020) and later attacks on CI systems and package ecosystems (Codecov in 2021, event-stream, `ua-parser-js`, the xz backdoor of 2024) showed that attackers target build pipelines and maintainers, not just running code, and that Log4Shell (2021) showed how hard it was to find a library inside nested artefacts. The US Executive Order 14028 (2021) made SBOMs a procurement topic, and NIST guidance such as SP 800-218 (the secure software development framework) and supply-chain controls in SP 800-53 (the SR family) turned practices into requirements [src: nist-sp800-guides f09804ed00ebcf00]. On the technical side, Google's SLSA framework (2021) defined levels of build integrity, and the Sigstore project (2021, under the OpenSSF and Linux Foundation) offered free, keyless signing with transparency logging: Fulcio issues short-lived certificates tied to an OpenID Connect identity, and Rekor records the event in a public log [web: docs.sigstore.dev].

The scanners also matured. Trivy (Aqua, 2019) combined image, filesystem, repository, configuration and secret scanning in a single binary with an offline-capable database; Grype (Anchore) paired with Syft for SBOM generation; Clair was rebuilt; Docker Scout and cloud providers added hosted scanning. Their partial successes and failures are the same: they find known issues reliably but flood users with findings that are not exploitable, depend on database quality, and only inspect what they can enumerate. The emerging pattern is SBOM at build, signature and attestation at publish, verification and re-scan at admission and on a schedule.

## Current state

### SBOMs

Two formats dominate. **SPDX** (Linux Foundation, ISO/IEC 5962) grew from licence compliance and expresses packages, files and relationships. **CycloneDX** (OWASP) was designed for security use and adds services, vulnerabilities and VEX statements. Both can be JSON. Each component record should carry a name, version, supplier, hashes, and a **package URL** (`pkg:deb/debian/openssl@3.0.15-1?arch=amd64`) or CPE, which the scanner uses to match advisories.

Generators work by cataloguing: Syft and Trivy read the OS package databases (`/var/lib/dpkg/status`, `/lib/apk/db/installed`, the rpm database), language manifests and lockfiles (`package-lock.json`, `go.mod` embedded in Go binaries' build info, Python `.dist-info`, Java JAR manifests), and sometimes binaries. BuildKit can generate an SBOM during the build with `docker buildx build --sbom=true` through a scanner image (by default Syft-based), and store it as an *attestation* attached to the image index rather than inside the image, so a pull does not change [src: docker-docs 44ccc9a62ca2f108] [src: docker-docs 6b0f5cdedf5e0be8]. Generated SBOMs are only as complete as what the tool can see: files copied in without a package manager, vendored code and statically linked components may be missing. Generating the SBOM from the build context, where lockfiles exist, gives better coverage than scanning the finished image alone, and the strongest result comes from combining both.

### Attestations, provenance and SLSA

An **attestation** is a signed statement about a subject, in the in-toto format: the subject is an artefact digest, the `predicateType` says what is claimed (`https://slsa.dev/provenance/v1`, `https://spdx.dev/Spdx`, `https://cyclonedx.org/bom`, `https://cosign.sigstore.dev/attestation/vuln/v1`), and the predicate holds the data. The envelope is DSSE, which signs the payload together with its type. **SLSA provenance** records the builder identity, the source repository and revision, the build instructions and the parameters. SLSA levels describe how trustworthy that record is: level 1 requires that provenance exists, level 2 that it be generated by a hosted build service and signed, and level 3 that builds run in an isolated, tamper-resistant environment where the signing material is not accessible to the build steps. BuildKit's `--provenance=mode=max` records build arguments and a full description; GitHub Actions' artifact attestations and the SLSA generator workflows give level 3 provenance for supported setups.

### Cosign and Sigstore

Cosign signs OCI artefacts and stores the signature as an OCI object in the same repository. Historically the signature was a separate manifest under a tag derived from the subject digest, `sha256-<hex>.sig`; newer versions store a Sigstore *bundle* (a single JSON document with the signature, certificate chain, transparency log entry and timestamp) and can attach it through the referrers API, which makes offline verification possible. Cosign 3.x signs with the bundle format by default, verification accepts both forms, and a `bundle upgrade` command converts older material [web: github.com]. Always sign the **digest**, not a tag: `cosign sign registry.example/app@sha256:...`. Signing a tag signs whatever digest it points to at that moment and a later move of the tag means a verifier that looks up the tag sees a different image.

Keyless signing in CI: the job obtains an OIDC token from the platform (GitHub Actions, GitLab CI, Google Cloud), cosign makes an ephemeral key pair, Fulcio checks the token and issues a certificate of about ten minutes' life whose subject alternative name carries the workflow identity, the signature is made and logged in Rekor, and the private key is discarded [web: docs.sigstore.dev]. There is nothing long-lived to steal. Verification then asserts the *identity* and the *issuer*:

```bash
cosign verify registry.example/app@sha256:<digest> \
  --certificate-identity-regexp '^https://github.com/example/app/.github/workflows/release.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
cosign attest --yes --predicate sbom.spdx.json --type spdxjson registry.example/app@sha256:<digest>
cosign verify-attestation --type spdxjson registry.example/app@sha256:<digest> \
  --certificate-identity ... --certificate-oidc-issuer ...
```

Verification without those two flags is not a meaningful check: any valid Sigstore signature from anyone would pass. Key-based signing remains available (`cosign generate-key-pair`, `--key cosign.key`), and keys can live in a KMS or HSM (`--key awskms://...`), which suits private or air-gapped environments where the public Sigstore services are unreachable; a private deployment of Fulcio, Rekor and a timestamp authority is possible through a signing configuration. The Kubernetes project itself describes verifying its release images and binaries with cosign in this way [src: kubernetes-docs 459b256e4cbef9a6].

Alternatives include **Notation** (Notary Project v2, CNCF), which uses X.509 trust stores and trust policies, favoured on Azure and in organisations that run their own PKI; GPG-based signatures through Podman and Skopeo (`signedBy` in `policy.json`, which also supports `sigstoreSigned` for cosign material); and registry-native features such as ECR signing.

### Enforcing verification

Signing without verification is decoration. Enforcement points: Podman and CRI-O read `/etc/containers/policy.json` and refuse to pull images that fail the matching requirement. In Kubernetes, admission controllers verify before a pod is created: Kyverno `verifyImages` rules, the Sigstore `policy-controller`, Ratify with Gatekeeper, or Connaisseur. A typical policy requires a signature from a named workflow identity, requires a provenance attestation from a trusted builder, rejects tags and mutates them to digests, and exempts system namespaces explicitly. Verification also belongs in the build stage: before using a base image or a downloaded tool, check its signature, as the distroless project's published `cosign verify` command illustrates [web: github.com].

### Trivy

Trivy is a single Go binary with sub-commands for targets: `trivy image`, `trivy fs`, `trivy repo`, `trivy config` (Dockerfiles, Kubernetes manifests, Terraform), `trivy k8s`, `trivy sbom` (scan an existing SBOM), and `trivy rootfs`. Scanners are chosen with `--scanners vuln,secret,misconfig,license`. It downloads a vulnerability database (built from distribution advisories, the GitHub advisory database, NVD and others) as an OCI artefact from a public registry, caches it, and refreshes it daily. Important options:

- `--severity HIGH,CRITICAL` and `--ignore-unfixed` reduce noise to what is both serious and fixable; `--exit-code 1` turns findings into a failing CI step.
- `--format table|json|sarif|cyclonedx|spdx-json|template` selects output, SARIF feeds code-scanning dashboards.
- `--skip-db-update`, `--offline-scan` and `--db-repository` support air-gapped use with a mirrored database.
- `.trivyignore` lists accepted CVE IDs, and **VEX** documents (OpenVEX, CycloneDX VEX, CSAF) record that a product is *not affected* despite containing a vulnerable component, which is the right way to suppress a false positive with an auditable reason. `--vex` applies them.
- `trivy image --input image.tar` scans an archive with no daemon, and `--image-src podman,containerd,docker,remote` selects the source.

A typical gate: `trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 registry.example/app@sha256:...`. The tool's release notes show the realities of operating a scanner: frequent updates, base images rebuilt on new Alpine versions, dependency bumps for its own vulnerabilities, and recent mitigations after a certificate authority key compromise [web: github.com]. A scanner is software that is itself part of the supply chain, so pin its version and verify what you download.

## Assessment: the good, the bad and the ugly

The good: the pieces compose, they are open, and they cost little. A keyless signature removes key management from CI. Verification by identity expresses what operators want: a single workflow, run on a release tag in one repository, is the only producer of production images. SBOMs and attestations travel with the image in the registry, so audit data is not lost. Scanners are fast and integrate with CI, registries and Kubernetes operators, and re-scanning stored SBOMs lets an organisation answer "which images contain library X" within minutes of an advisory.

The bad: findings are not risk. A scan of a mainstream Debian-based image reports dozens of low and medium issues in packages the application never loads, and many with no available fix. Distribution backports break version comparison: a package version string that looks old may include the patch, and scanners that ignore the distribution's own security tracker produce false positives. The database depends on its sources' latency and quality, and different scanners disagree on the same image. SBOMs omit statically linked or copied-in components, and there is no ground truth for completeness. Signatures prove origin and integrity, not safety: a signed image built from a compromised dependency is still compromised. Unsigned base images from the public registry enter many builds unverified. Verification policies are brittle; a workflow file renamed changes the signing identity, and an overly broad regular expression for the identity silently trusts forks.

The ugly: operational reality. The transparency log and Fulcio are public services with availability limits, so pipelines that cannot tolerate a Sigstore outage need retries, caches or a private instance. Public Rekor entries reveal repository and workflow names, which some organisations treat as sensitive. Admission policies that block on unsigned images tend to be disabled during the first incident, and exemptions accrete. Alert fatigue leads teams to ignore scanner output. The documented compromise-handling releases and security advisories in cosign and Trivy themselves, including a verification bypass in legacy bundle handling fixed in 2026 releases, are a reminder that verification code is attack surface (to verify details) [web: github.com]. Tag-based references defeat everything above: a verified digest followed by a deploy by tag can still ship a different image.

## Applications beyond this domain

SBOM, attestation and signature verification apply to every artefact type that can be addressed by hash: Linux distribution packages (Debian and Fedora are experimenting with reproducible builds and signed provenance), language packages (npm and PyPI provenance through trusted publishing use the same Sigstore identity model), firmware images, Helm charts and Terraform modules stored as OCI artefacts, machine-learning model files, and the kernels and bootloaders of secure boot chains. Vulnerability matching by package URL is how Dependabot, Renovate and OSV-Scanner work for source repositories. The VEX idea, that the producer states which known CVEs do not apply, is relevant in any regulated sector, including medical devices and automotive software, where SBOMs are becoming required by regulation such as the EU Cyber Resilience Act. The keyless idea, an identity token swapped for a short-lived credential, is the same as workload identity federation for cloud APIs.

## Examples

*Generate and attach an SBOM.* `syft registry.example/app@sha256:... -o spdx-json > sbom.spdx.json` writes the inventory; `trivy sbom sbom.spdx.json --severity HIGH,CRITICAL` scans it without access to the image; `cosign attest --predicate sbom.spdx.json --type spdxjson ...` attaches it. `cosign tree registry.example/app@sha256:...` lists the signature and attestations stored beside the image.

*Gate a build.* A CI job builds with `docker buildx build --provenance=mode=max --sbom=true --push`, resolves the digest from the build output, signs it keylessly, scans it with `trivy image --exit-code 1 --ignore-unfixed --severity CRITICAL` and fails if a critical, fixable issue exists. The release job uses only the digest from this job's output.

*Verification policy at admission.* A Kyverno `ClusterPolicy` with a `verifyImages` rule matches `registry.example/*`, requires a keyless attestor with the issuer of the CI provider and a subject pattern limited to the release workflow of one repository, and sets `mutateDigest: true` so pods run by digest. A pod referencing an unsigned image from an unlisted registry is rejected with a message naming the missing signature.

*A failing example: signature checks that check nothing.* A team runs `cosign verify image` in CI with no identity flags and sees success, because the image was signed by someone, perhaps an attacker with a GitHub account. Adding `--certificate-identity` and `--certificate-oidc-issuer` makes the check real, and the first run with them fails because the release workflow had been moved into a reusable workflow whose path became the signer identity. The fix is to update the policy with the reusable workflow's reference.

*A failing example: the scan that lies.* A scanner flags `openssl 3.0.11` in a Debian image as vulnerable to a CVE fixed upstream in 3.0.12, though Debian has back-ported the fix into `3.0.11-1~deb12u2`. Comparing against the Debian security tracker, or using a scanner mode that trusts distribution advisories, shows it fixed. Recording the conclusion in a VEX statement makes the suppression reviewable.

## Related problems and ideas

Related efforts include reproducible builds (bit-identical rebuilds that let independent parties confirm a binary matches source), in-toto layouts that describe expected steps and functionaries across a pipeline, TUF for update metadata with freshness, OpenSSF Scorecard for assessing upstream projects, and runtime detection (Falco, Tetragon) that complements pre-deployment checks by watching behaviour. Opposing or different approaches: trusting a curated internal registry and signing nothing else; minimal-image vendors that rebuild everything from source daily and publish SBOMs by construction; and cloud-provider binary authorisation services. Ideas not yet mainstream include reachability analysis that determines whether a vulnerable function is called, attested VEX streams from upstream maintainers, and policy languages that combine provenance, SBOM contents and vulnerability data in one decision.

## Active research

Work in progress covers the quality of SBOMs (completeness metrics, minimum elements defined by NTIA and CISA), the semantics of VEX and how consumers should merge conflicting statements, reachability-aware scanning for Go, Java and JavaScript, and formal models of what SLSA levels guarantee. In Sigstore, the community is moving verification to a bundle format and a TUF-distributed trust root, adding Rekor v2 as a tile-based, cheaper log that accepts larger entries such as SBOM attestations, and improving offline verification and private deployments [web: github.com]. Researchers measure how many production images actually verify cleanly, how often tag moves occur, and how effective admission policies are. Open questions include the right governance of identities for fork-based contributions, key and identity recovery after a CI compromise, and how to attest to build steps that run on developer laptops.

## Future direction

Regulatory pressure will drive adoption: SBOM delivery requirements, the EU Cyber Resilience Act, and US federal guidance mean that signed provenance and SBOMs will be requested by customers. Expect default signing and provenance in build tools and registries, referrers-based attachment as the standard storage path, and cosign's bundle format to become the only format in new releases (the 3.x line already signs with it by default) [web: github.com]. Scanners will lean on VEX, on distribution-maintained advisories and on runtime reachability to cut noise, and will themselves be signed and pinned. The sensible baseline today is cheap: pin and verify base images, build with provenance and SBOM, sign digests keylessly or with KMS keys, verify by identity at admission, scan on build and on a schedule, and keep VEX statements for accepted findings.
