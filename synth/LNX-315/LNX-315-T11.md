# Tuning live migration so that it finishes, and finishes quietly

## Define the problem

Live migration moves a running virtual machine from one host to another while it keeps serving users. The promise is that a host can be drained for maintenance, load can be rebalanced and a failing node can be evacuated without an outage. The difficulty is physical. A guest's memory can be tens or hundreds of gigabytes and the guest keeps changing it while it is copied. Anything changed after being sent must be sent again. If the guest writes memory faster than the network can carry it, the copy never catches up, and the migration runs forever or is cancelled.

Administrators meet this as three practical symptoms. The migration never completes: progress shows the same number of megabytes remaining for an hour. The migration completes, but the guest freezes for seconds at the end, long enough to drop connections, trip a cluster heartbeat or fail a time-sensitive transaction. Or the migration completes only because the guest was slowed to a crawl, which hurts the service it was meant to protect. Tuning is the craft of picking, per workload, the trade-off between total time, guest-visible pause, guest slowdown and network load, and of knowing when no tuning will work and a different plan (a maintenance window, a different placement, application-level failover) is needed.

This slice covers the standard algorithm and its measurable quantities, the controls QEMU and libvirt expose, the KubeVirt equivalents, and a method for diagnosing a stuck migration. It builds on the earlier topics about memory pinning, hugepages and passthrough, which all change what migration can do.

## History and approaches

The first practical live migration, in research systems of the early 2000s, used the pre-copy method: copy all memory while the guest runs, then repeatedly copy the pages dirtied during the previous round, and stop the guest briefly to copy the last small set and the device state. Xen, VMware and KVM all adopted it. Its strength is safety: at every moment before the switchover, the source holds the complete current state, so a failure of the target or the network leaves the guest running where it was. Its weakness is non-convergence with write-heavy guests.

Several additions tried to fix that weakness. Throttling the guest's CPU so it dirties less is the idea behind auto-converge: the throttle starts small and grows until the copy rate overtakes the dirty rate [src: kubevirt-user-guide b9183a84cbd8de88]. Compressing pages, or sending only the changed parts of previously sent pages (delta encoding, called XBZRLE in QEMU), trades processor time for bandwidth. Using several network connections in parallel (multifd) lets a fast network be filled by many threads. Offloading compression to accelerators was added later [src: qemu-docs c7147f4bc8e80e9e]. The older multi-threaded compression feature has been removed in recent QEMU releases in favour of the multifd-based approaches (to verify against the QEMU version you run) [src: qemu-docs 65fed8ffb585034f].

A different strategy is post-copy: switch execution to the target early, then pull the remaining memory on demand when the guest touches a page that has not yet arrived, while a background stream pushes the rest. A page is never sent twice, so write-heavy guests no longer prevent completion, and the total traffic is lower [src: kubevirt-user-guide 343efe53d9b6f158]. The cost is risk and warm-up: during post-copy the up-to-date state is split between the two hosts, so failure of the network or the target in that window can lose the guest; and the guest at first stalls on each missing page. A hybrid approach starts with pre-copy for a bounded time and switches to post-copy only if the migration is not converging.

More recent work controls the guest's dirty rate more precisely. The dirty-limit mechanism, available since QEMU 8.1, uses the KVM dirty ring to measure each virtual CPU's page-dirtying rate and applies a per-CPU throttle so that only the busy CPUs are slowed, with less impact on others than a flat CPU throttle [src: qemu-docs b9a17a33df258725]. Combined with multifd for bandwidth and with postcopy where acceptable, it gives a richer toolbox [src: qemu-docs b6193f014a8ea329].

Failures recorded over the years: a migration that was left running for days over a congested link, hurting both ends; a post-copy migration abandoned half way over a flapping network, leaving a guest destroyed; compression that used so much CPU on the host that the migration slowed; and throttling that dropped a database below its service level so that the migration "succeeded" and caused an outage anyway.

## Current state

**Precopy model and its numbers.** Think of three rates: the page-dirtying rate of the guest, the transfer rate the network and source can sustain, and the final stop-and-copy time. The migration converges when the remaining dirty memory can be sent within the allowed downtime. Whether it will depends on: the memory size, the guest's working set and write rate, the usable bandwidth, and the configured maximum downtime. The migration monitor reports transferred and remaining bytes, the current dirty rate, throughput, the expected downtime and the iteration count; those numbers are the first tool for judging whether tuning can help [src: kubevirt-user-guide 235e406e3ea7eac0].

**The basic controls.** QEMU exposes parameters through its monitor, and libvirt wraps them in migration options. The main ones are: a bandwidth cap (so that the migration does not starve production traffic), a maximum downtime target (the pause the operator will accept at the end), a timeout after which the migration is aborted or switched to a stronger strategy, and options for how to move storage, whether to tunnel traffic through the management connection, and whether to encrypt it. A higher downtime target makes convergence easier at the cost of a longer pause. A bandwidth cap that is too low is a common cause of non-convergence, and one that is too high can disturb other tenants of the network [src: libvirt-docs aefdf541c311d25b] [src: rhel-10-docs ff8d08941286aea4].

**Auto-converge.** When enabled, QEMU throttles guest CPUs in steps if the transfer does not keep up, with initial and increment percentages and a maximum. It is simple and widely supported. Its price is guest slowdown that affects every thread in the VM, including the ones that were not writing memory, and its effect is poor if the guest's throughput matters more than the migration. It suits batch and moderately loaded guests and is a poor fit for latency-critical ones.

**Dirty limit.** A newer, more selective throttle. The operator sets an upper limit on the page-dirty rate per virtual CPU (or for all CPUs), and the throttle thread measures and slows only those CPUs that exceed it. It relies on the dirty-ring feature of KVM and so needs a sufficiently recent kernel and QEMU, and the guest memory tracking mode that it uses can have its own overhead [src: qemu-docs b9a17a33df258725] (to verify the versions and the libvirt support level on your distribution).

**Multifd.** Splits the memory stream across several connections and threads, so the migration can use a fast link, and works with some encryption and compression back ends. It is the first thing to enable on a 25 Gbit or faster network. Combined with postcopy, it accelerates only the precopy part: once the switch to postcopy occurs, page transfer uses the background channel again [src: qemu-docs b6193f014a8ea329] (to verify the minimum version, given in the project documentation as 10.1 for the combination).

**Compression and delta encoding.** XBZRLE keeps a cache of sent pages and sends only the differences when a page is dirtied again, which helps guests that modify the same pages in small ways; it needs a cache sized to the working set and adds CPU use. Accelerator-based compression through hardware libraries is documented for specific processors and cards. The older multi-thread compression option is gone from recent releases [src: qemu-docs efd495dbbd4bef68]. A compression that uses all host cores can slow down every other guest on the host, so cap its threads.

**Post-copy.** Enable the capability before the migration starts, then switch either manually at a chosen moment or automatically after a first pre-copy pass, or when a timeout is reached. KubeVirt documents the node-side prerequisites for this mode and its limitations; it also notes that post-copy needs special handling of memory (for example it does not combine with some memory backing choices) [src: kubevirt-user-guide 343efe53d9b6f158] [src: kubevirt-user-guide e0d221f600dddf5e] (to verify the exact exclusions). Use post-copy where finishing matters more than the risk: very write-heavy guests, emergency evacuation of a node that is expected to fail anyway (where the guest is at risk regardless), and when the network is reliable. Avoid it where the network is shaky or where losing the guest would be worse than losing time.

**Interaction with other features.** Guests with PCI passthrough cannot be migrated by the generic path. Some devices can be migrated with vendor-specific support, with VFIO device migration support in the kernel and QEMU, and with dirty tracking that must also cover the device's own writes to memory [src: qemu-docs 33bb217ed54cca2b] (to verify device and driver support). Guests using hugepages move in larger chunks, which changes dirty tracking granularity. Dedicated CPU pinning and NUMA topology must be satisfiable on the target. Storage moves separately when disks are not shared, and block migration multiplies the data volume and the time.

**KubeVirt and managed platforms.** KubeVirt exposes cluster-wide migration settings: concurrent migrations per node and per cluster, bandwidth per migration, the completion timeouts for pre-copy and post-copy, whether auto-converge and post-copy are allowed, and a dedicated migration network. Per-VM policies can override them for classes of machines. The eviction strategy decides whether a node drain triggers a migration. A migration that stalls past its timeout is aborted or switched, depending on settings. The status and cancellation facilities are accessible through the API [src: kubevirt-user-guide c42120914f835003] [src: kubevirt-user-guide 614d72225ae9bc6a].

**A method for tuning.**

1. Measure the guest first: memory size and the dirty rate under real load, with a test migration in a quiet period.
2. Check the network: usable bandwidth between the hosts, MTU, and whether the migration shares the link with storage or user traffic.
3. Enable multifd on fast links; set the bandwidth cap to a deliberate figure.
4. Set a downtime target based on what the application tolerates (measure the application's tolerance to a pause, not the hypervisor's default).
5. If the migration still does not converge, add selective throttling (dirty limit) where supported, or auto-converge where slowdown is acceptable.
6. Use post-copy as the last step for guests where completion is required and the failure risk is accepted.
7. If nothing works, change the plan: schedule the move for a quiet time, quiesce the workload, or move the application and not the VM.

## Assessment: the good, the bad and the ugly

The good. Live migration is a mature, mostly reliable capability, and the tuning options span a range from gentle to forceful. Multifd and dirty limit are real advances. Post-copy guarantees completion for the hardest guests. The monitoring data gives the operator facts. Platform policies let the same tuning be applied consistently across a fleet.

The bad. The controls are many, interact, differ by version, and have defaults that suit nobody in particular. Documentation lags features, and libvirt support follows QEMU support with a delay. Throttling harms the service that migration is meant to protect. Post-copy increases the blast radius of a network fault. Hardware features (passthrough, some confidential computing modes, certain CPU features) restrict or block migration, and the restriction is often discovered at the moment of need.

The ugly. The unattended maintenance drain that starts twenty migrations at once across a single link and makes every one of them fail. A guest that appears to migrate but whose application times out because the end-of-migration pause was ten seconds, not the milliseconds assumed. A fleet with mixed CPU generations where migration works until a particular host pair is used. A tuned configuration that was tested on an idle guest and never on one under load.

## Applications beyond this domain

The pre-copy versus post-copy trade-off is general: move data while it changes, either by repeated catch-up passes or by switching ownership early and fetching on demand. It appears in database replica promotion, in live storage migration, in container checkpoint and restore, in cache warming and in distributed file system rebalancing. Throttling the producer so a consumer can catch up is the same as back-pressure in networks and stream processing. The concept of a convergence condition, an overall rate comparison with a final small stop-the-world step, appears in garbage collectors and in database failover. Choosing a pause budget from the application's tolerance, and not from the tool's default, is a general reliability practice.

## Examples

Start a libvirt live migration with several controls (options as in recent libvirt; verify with `virsh help migrate`):

```bash
virsh migrate --live --persistent --undefinesource \
  --auto-converge --parallel --parallel-connections 4 \
  --bandwidth 1000 --postcopy --postcopy-after-precopy \
  --timeout 900 --timeout-postcopy db01 qemu+ssh://dest.example.org/system
```

Watch progress and raise the downtime allowance during a running migration:

```bash
virsh domjobinfo db01
virsh migrate-setmaxdowntime db01 500
virsh migrate-postcopy db01
```

A diagnosis walk-through. A 128 GB database guest never finishes. Look at the job information: if remaining memory oscillates around a constant, the dirty rate exceeds the effective bandwidth. Compare the measured dirty rate and the throughput. If the link is the limit, enable parallel transfers or raise the cap. If the dirty rate is the limit, try a selective throttle during a quiet period, or accept post-copy over a reliable link, or move the database through its own replication.

A second example, a drain policy. A cluster of sixteen nodes each hosting thirty guests, with one 25 Gbit migration network. Allow two migrations out of a node at a time and five in the cluster, set the per-migration bandwidth to a quarter of the link, enable multifd, auto-converge only for guests tagged as batch, and post-copy only for guests tagged as evacuable. Test the policy by draining one node under a synthetic load and record total time and the longest pause.

## Active research

Open topics include migration of guests with device passthrough using device-level state and dirty tracking, migration for confidential guests with encrypted memory and attestation of the target, hardware offload of copy and compression, scheduling migrations as a cluster-wide optimisation problem (which guest, in what order, over which link), predictive models of convergence that choose the strategy automatically, and cross-architecture or cross-hypervisor live moves. Work continues on making post-copy safer through recovery from network failures and through better use of preemption channels (to verify the state of each feature).

## Future direction

Expect more automatic selection: the platform measures the dirty rate and the link, picks parallelism, throttling and post-copy as needed, and reports the expected pause before it starts. Operators will define policies per class of workload and not per migration. Devices and confidential guests will become migratable with defined limits. Until then, the dependable skills are reading the migration counters, knowing what each control costs, and testing under load before the maintenance window and not during it.
