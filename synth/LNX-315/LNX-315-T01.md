# Handing a physical PCI device to a virtual machine: VFIO and IOMMU groups

## Define the problem

Virtual machines normally see emulated or paravirtual devices. An emulated network card or disk controller is a program in the hypervisor that pretends to be hardware; a paravirtual device (virtio) is a cooperative interface in which the guest knows it is virtual and talks to the host through shared memory rings. Both put the host's software between the guest and the work, and for some jobs that layer costs too much or hides the feature that matters. A graphics processor used for compute or rendering needs the vendor driver to talk to the real silicon. A high-speed network adapter doing packet processing cannot afford a copy through a software switch. A storage controller with vendor-specific features, an FPGA, a capture card, a smart NIC or an accelerator with its own firmware simply cannot be emulated at all.

The answer is to give the guest the real device: assign a PCI function to a single VM so that the guest's own driver programs it directly. That sounds simple and is hard to do safely. A PCI device can read and write host memory by direct memory access (DMA) without involving the CPU. If a guest controls a device, then the guest controls where the device writes, and a malicious or buggy guest could aim the device at the host kernel's memory or at another VM's pages. The device interrupts need routing to the right virtual CPU. And the hardware must be such that one VM's device cannot reach another device's registers through the PCI fabric, which is where the idea of IOMMU groups comes from.

This slice teaches how Linux solves the problem: the IOMMU as the hardware gatekeeper for DMA, the VFIO framework that exposes devices to user space safely, the IOMMU group as the unit of isolation, how a host is prepared (kernel parameters, driver binding, group verification), how libvirt and QEMU attach the device, and the typical failures: shared groups, reset problems, and memory pinning limits. SR-IOV, which splits a device into several assignable functions, is the next topic, and performance tuning is a later one.

## History and approaches

The earliest approach to assigning a device was the Xen paravirtual PCI backend, and then KVM's own pci-assign facility (2008 and after), which pinned the guest's memory, programmed the IOMMU, and injected interrupts through kernel code inside the KVM module. It worked, but it embedded device policy inside the hypervisor kernel module, was tied to KVM, and had no clean model for what could safely be shared. It was removed from the kernel once its successor matured.

The hardware side developed in parallel. Intel introduced VT-d and AMD the AMD-Vi IOMMU, hardware units that sit between devices and memory and translate device-visible addresses through page tables controlled by the host, so that a device can only reach memory the host chose to map for it. Interrupt remapping, a companion feature, stops a device from forging interrupts to arbitrary vectors. ARM has the SMMU, and other architectures have equivalents. Without an IOMMU, assigning a device to an untrusted guest is simply unsafe, which is why the feature is a hard prerequisite and why platforms with broken firmware tables were a long-running source of trouble.

VFIO (Virtual Function I/O), merged into Linux 3.6 in 2012 and designed by Alex Williamson, is the framework that replaced pci-assign. Its premise is that the kernel should not decide what a user-space driver does with a device, but must guarantee the IOMMU confines the device's DMA to memory the user process owns. The framework has three layers. The VFIO core and the bus drivers (vfio-pci for PCI) expose a device as a file descriptor with ioctls to read its regions (BARs, config space), map them, set up interrupts through eventfds, and reset it. The IOMMU backend (type 1 for x86 and ARM) lets the user process map and unmap memory for the device's DMA at chosen I/O virtual addresses, with the kernel pinning the pages. And the group abstraction ties the two together: the unit a user can open and attach to an IOMMU container is a group, not a device [web: kernel.org].

IOMMU groups come from a hardware fact. The IOMMU identifies devices by their bus, device and function number as seen in transactions, and in some topologies several devices cannot be told apart or can talk to each other without passing through the IOMMU. A PCI-to-PCI bridge that does not enforce access control, a multifunction device whose functions can reach each other, or a switch that lets peer-to-peer traffic flow below the IOMMU all form shared domains. The kernel computes the smallest sets of devices that the IOMMU can isolate from the rest and calls them groups; everything in a group must go to the same owner, so assigning one device to a VM means taking all of its group, or leaving the other members idle with a harmless stub driver. PCI Access Control Services (ACS) on bridges and switches is the feature that splits groups finely, and consumer motherboards often lack it on their downstream ports, producing large groups; the unofficial "ACS override" kernel patch forces the split, at the cost of the isolation guarantee [src: archwiki 95e379d23c0d7fe5].

Distribution tooling arrived through libvirt, whose node device API and the hostdev element in the domain XML manage the unbinding of the host driver and the binding of vfio-pci automatically in "managed" mode, and QEMU gained the vfio-pci device and, later, support for presenting an emulated IOMMU inside the guest, useful for nested assignment. Higher-level platforms built on the same plumbing: OpenStack Nova's PCI passthrough whitelist and flavor aliases, and KubeVirt's host device assignment with a device plug-in and permitted-host-devices configuration in the cluster resource [src: kubevirt-user-guide 2506bd9a44cae6fa].

Lessons accumulated about what goes wrong. Reserved memory regions (RMRR on Intel platforms) that firmware marks for the host's own use, typically for USB or management controllers, conflict with assignment and in some kernels block it unless a relaxed mode is chosen [src: archwiki 95e379d23c0d7fe5]. GPU assignment with the vendor driver meets features that detect virtualisation and refuse to run on consumer cards in older driver releases, and some devices fail to reset cleanly between guest uses (the "reset bug"), so a restart of the guest leaves the card unusable until the host reboots. Large-BAR devices need the guest firmware to support above-4-GiB address decoding. Each of these became a known checklist item.

The emerging pattern: the IOMMU group as the unit of assignment, a user-space owner that holds the device through a file descriptor rather than by kernel policy, and orchestration layers that expose assignable devices as schedulable resources.

## Current state

**Prerequisites on the host.** The platform firmware must enable the IOMMU (VT-d or AMD IOMMU, sometimes named "IOMMU" or "SVM" and "Above 4G decoding" in settings). The kernel must be booted with the IOMMU active: on Intel the parameter intel_iommu=on, and on AMD the IOMMU is on by default in recent kernels; many people also add iommu=pt to put host-owned devices in passthrough mode and avoid translation overhead for them. Verification is in the kernel log (lines that mention DMAR or AMD-Vi, and "IOMMU enabled") and in the existence of /sys/kernel/iommu_groups with numbered subdirectories. Without those, vfio refuses to bind.

**Reading the groups.** Each directory /sys/kernel/iommu_groups/N/devices lists the PCI addresses in group N. The standard first step is to enumerate all groups with the class and vendor of each device (lspci -nns on each address) and find the target. The ideal outcome is that the device (for a GPU, its video function and its audio function) is alone in the group, or shares it only with the matching functions and the upstream bridge. Devices that are PCI bridges and root ports are ignored by VFIO's checks and do not need to be moved. If other endpoint devices share the group (a SATA controller the host boots from), the options are to move the card to another slot that is wired to a different root port, change platform settings, accept an ACS override with the associated isolation loss, or pick different hardware.

**Binding to vfio-pci.** A device is assigned by detaching it from its normal driver and attaching vfio-pci. There are two ways. Dynamic binding, which libvirt's managed mode does at VM start and reverses at stop, writes to the device's driver_override attribute and to the driver bind interface, and works when the host does not need the device at all. Static binding gives the vendor and device ID to vfio-pci at boot (a module option or kernel parameter), so the host driver never claims the card; this is required for devices that the host driver would otherwise grab early or whose unbind causes trouble, such as a GPU used for the host console. The initramfs may need the vfio modules loaded before the graphics driver. The tool driverctl wraps the persistent form. After binding, lspci -k shows "Kernel driver in use: vfio-pci" for each function, and /dev/vfio/N appears for the group.

**Attaching to a guest.** In libvirt, a hostdev element of type pci with a source address names the device and, with managed set to yes, lets libvirt do the binding [src: rhel-10-docs 285f4569cf48a2f9]. QEMU's vfio-pci device takes the host address. The guest should use UEFI firmware (OVMF) for modern GPUs, the q35 machine type with PCIe topology that matches the device's expectations, and for large devices the firmware must handle 64-bit BARs. For PCIe devices that expect to be on a root port, libvirt's pcie-root-port controllers and the right slot choices matter for link speed reporting. Memory is pinned: QEMU asks VFIO to map all guest RAM for DMA so the pages cannot move or swap, so the process needs a locked-memory limit that covers guest RAM (libvirt arranges this) and large hugepage-backed guests map faster.

**Interrupts and resets.** MSI and MSI-X interrupts are delivered through eventfds that KVM connects to the guest's interrupt controller (posted interrupts and APICv make this efficient). Resets use the best available method (function-level reset, secondary bus reset, vendor-specific reset, or power state transitions); the kernel reports which are available in /sys/bus/pci/devices/ADDRESS/reset_method. Devices without a working reset can still be assigned but are unsafe to hand from one guest to the next without a host reboot.

**Variations.** Mediated devices (mdev) let a driver share one physical device among VMs by implementing a virtual device in the host driver, used for Intel GVT-g and NVIDIA vGPU; the VFIO group is then a software one. VFIO-user and vfio-user sockets move device emulation into separate processes. The vfio-platform driver handles non-PCI devices on ARM. For containers and cloud-native systems, the Container Device Interface and Kubernetes device plug-ins publish assignable devices as resources, and KubeVirt turns them into permitted host devices with resource names.

**Generalised pattern.** To give an untrusted party direct hardware access: require a hardware boundary on memory access (an IOMMU), define the isolation unit by what the hardware can enforce (the group), hand the device to one owner through a handle that the kernel can revoke, and pin and account for the memory the device can touch.

## Assessment: the good, the bad and the ugly

The good: near-native performance and full access to device features, with the host kernel still enforcing memory isolation. The model is clear: if the group is clean and the IOMMU is on, assignment is safe by construction. libvirt and cloud platforms automate the routine path, so a working GPU passthrough is a configuration exercise, not kernel work.

The bad: a passed-through device is gone from the host and from other guests, and the guest is no longer live-migratable in the normal sense, since device state lives in hardware that the hypervisor cannot save and restore (some vendors offer migration support for specific SR-IOV and vGPU devices, which is new and narrow). Snapshots, memory overcommit, ballooning and page sharing do not work with pinned memory. Hardware choice is constrained: boards with poor ACS support give huge groups, and consumer firmware has quirks. The guest driver must handle running with a hypervisor present, and vendor licensing for some data-centre features requires specific products.

The ugly: errors are cryptic and hardware-specific. A VM that hangs at boot with a black screen can be a reset bug, a firmware BAR problem, a wrong GPU in the primary slot, an RMRR conflict or a driver that refuses virtualisation. A mistake in binding can take the host's only display or boot disk away. A device with a firmware or bus-mastering flaw can crash the host through its DMA even when contained, as an IOMMU fault storm or a platform error that machine-check handling turns into a reboot. Security-wise, the guarantee covers memory isolation only: peer-to-peer DMA between devices in one group, or side channels through shared PCIe links, or malicious firmware on the device itself that persists across guests are all outside it. Untrusted guests with devices that have updatable firmware (GPUs, NICs) can reflash it, which is a real supply chain and persistence concern in multi-tenant clouds.

## Applications beyond this domain

User-space drivers use the same framework: DPDK and SPDK, the data-plane toolkits for packet and storage processing, open NICs and NVMe controllers through VFIO so that polling-mode drivers run in user space with IOMMU protection. Confidential computing relies on the same ideas of DMA control, since a device that can read guest memory breaks the confidentiality model unless the platform limits what the device may touch. Container platforms use device plug-ins that hand a GPU to a Pod. Thunderbolt and external PCIe enclosures use IOMMU-based DMA protection to defend laptops against malicious peripherals (kernel DMA protection on Windows and Linux's IOMMU settings for external ports). Hypervisors on other operating systems have equivalents: VMware's DirectPath I/O, Hyper-V's discrete device assignment, and Xen's PCI passthrough.

## Examples

**A GPU for a Windows workstation VM.** On a desktop with two GPUs, the administrator enables VT-d and above-4G decoding, boots with intel_iommu=on iommu=pt, and lists the groups; the second card and its audio function sit alone in group 14. She binds both functions to vfio-pci by vendor and device ID at boot, defines a q35 VM with OVMF firmware, adds both functions as hostdev elements and installs the vendor driver in the guest. Frame rates are within a few per cent of bare metal. After a guest crash the card will not reinitialise until the host reboots, which turns out to be a known reset limitation of that model.

**A shared group.** The same administrator tries the first GPU in the primary slot and finds it in a group with the chipset's USB controller and the SATA controller. Binding the whole group would give the guest the host's boot disk controller. She moves the card to the second x16 slot, wired to a CPU root port with ACS, where it is alone.

**A failing example.** A team enables passthrough for a NIC on a server and gets "group is not viable" errors when starting the VM. The group contains the NIC's second port, which the host still uses for management. VFIO insists that all endpoint devices of a group be bound to vfio-pci or to no driver. The fix is to use the other PCIe slot's adapter for management, or to move to SR-IOV, which creates assignable virtual functions that have their own IOMMU-visible identities.

## Related problems and ideas

Neighbouring problems: SR-IOV (next topic), virtual IOMMU in the guest for nested assignment and for user-space drivers inside a VM, mediated devices and vGPU licensing, GPU partitioning technologies (MIG on NVIDIA data-centre cards), and live migration of devices with vendor support in VFIO (the migration v2 uAPI). Alternatives to passthrough: virtio-based acceleration (vDPA, which gives a virtio-compatible interface backed by hardware so that guests need only the generic driver and migration remains possible), paravirtual GPUs (virtio-gpu with Venus or native context for Vulkan, VirGL for OpenGL), and remote GPU offload at the application layer. The IOMMUFD framework is replacing the older VFIO type 1 container in the kernel, giving a cleaner user-space API for nested translation and device-centric attachment.

## Active research

Active work covers IOMMUFD and its integration with QEMU and libvirt, nested translation (stage-1 in the guest, stage-2 in the host) for vIOMMU on x86 and ARM, device live migration through the VFIO migration interface including dirty page tracking in hardware, and confidential device assignment (PCIe TDISP and the trusted device models for SEV-SNP and TDX), which tries to let a confidential VM assign a device without the host reading the device's traffic. Researchers also study IOMMU performance (IOTLB behaviour and map/unmap cost) and attack classes against DMA isolation, including malicious devices and firmware. Open questions: how much device state can be saved generically, how to attest a device's firmware to a guest, and how to give fine-grained GPU sharing without vendor-specific kernels.

## Future direction

Expect IOMMUFD to become the default path, with libvirt and Kubernetes exposing finer-grained device choices, wider hardware-assisted migration for NICs and accelerators, and confidential assignment moving from demonstrations to product features. Cloud providers' shift to offload cards and DPUs places an IOMMU-enforced boundary at the heart of every instance. Kernel version thresholds and feature status for the items above (IOMMUFD, VFIO migration, TDISP support, vDPA maturity): to verify against kernel and QEMU release notes.
