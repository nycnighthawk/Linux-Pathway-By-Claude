# Virtual disk images: qcow2 internals, backing chains and block jobs

## Define the problem

A virtual machine's disk is a file, and the choices made about that file decide how much space it uses, how fast it is, how quickly new machines can be created, how snapshots and backups behave and what happens when something goes wrong halfway. A raw image, a byte-for-byte copy of a disk, is the simplest and fastest format, but it occupies its full size (unless the file system supports sparse files), has no snapshots, and offers nothing for cloning. Operators want more: thin provisioning, so a hundred-gigabyte disk that holds ten gigabytes of data costs ten; cheap clones from a template; snapshots that can be taken while the guest runs; incremental backups; compression and encryption; and the ability to move a disk from one storage system to another without stopping the guest.

The QEMU copy-on-write format, qcow2, provides these through a layered design: a mapping from guest addresses to file clusters that is allocated on demand, reference counts that allow clusters to be shared between snapshots, and a backing file that supplies data for regions the image does not yet contain. Together they make it possible to build chains, where a read-only base image is shared by many small overlays. The cost is complexity. A qcow2 file has internal tables whose corruption loses data, an overlay is useless without its backing files, long chains slow I/O and complicate operations, and the live operations that reshape a chain (commit, pull, mirror, backup) are asynchronous jobs that can fail partway. Understanding what the format guarantees, and how its tooling manipulates chains safely, is what separates routine virtual machine management from lost data.

This slice covers the qcow2 format structure at the level needed to reason about size and performance, the options that matter at creation, backing chains and their invariants, the offline operations (create, info, check, rebase, commit, convert, resize, amend), the live block jobs exposed by QEMU and libvirt (snapshot, commit, pull, copy or mirror, backup with dirty bitmaps), and the failure modes. Other formats (raw, vmdk, vhdx, vdi) and storage back-ends (LVM, Ceph RBD, NFS) are mentioned for comparison.

## History and approaches

Early virtualisation used raw files or raw block devices, and snapshotting was done below the guest, by the storage layer. QEMU's first copy-on-write format (qcow, 2004) added a cluster table and a backing file but lacked reference counts. Its successor qcow2 (2008, QEMU 0.10) added reference counting, which allowed internal snapshots, where the image holds several versions of the L1 table and clusters shared among them are counted. Version 3 (QEMU 1.7, 2013, selected with compat=1.1) added zero clusters, extended feature bits, lazy reference count updates for speed, and a header extension mechanism that later carried features such as dirty bitmaps, encryption headers and a data file name [src: qemu-docs a43ab904f510a7aa]. Later releases added compression with zstd as an alternative to zlib (5.1), extended L2 entries with subclusters (5.2), which reduce the cost of copy-on-write for small writes into large clusters, and the external data file option, where the image holds only metadata and the guest data lives in a separate raw file.

Alternative formats followed other designs. VMware's VMDK, Microsoft's VHD and VHDX, and VirtualBox's VDI each have their own thin provisioning and snapshot mechanisms, and QEMU can read and write most of them (conversion with qemu-img is the standard path between hypervisors). Raw files on a file system with sparse file support (and reflink copies on XFS or Btrfs) give thin provisioning and cheap clones without a format layer, which is attractive for performance. LVM thin volumes and Ceph RBD provide snapshots and clones in the storage layer, with qcow2 unnecessary in those deployments. The choice between a format-level feature and a storage-level feature recurs throughout the course: format-level is portable and needs nothing from storage, while storage-level is faster and has fewer moving parts.

Snapshots took several forms, and the differences caused years of confusion. Internal snapshots live inside the qcow2 file, taken with qemu-img snapshot or by the monitor, and record the disk state and optionally the VM state; they are convenient but tie history to one file and are mostly deprecated in management layers because of their poor interaction with block jobs and backups. External snapshots add a new overlay: the current image becomes a read-only backing file and new writes go to a fresh qcow2 on top. Libvirt supports this with a disk-only snapshot, creating the overlay atomically across all disks. External snapshots compose with backups and storage migration, but they lengthen the chain, and merging them back (a commit or a pull) became the central maintenance operation. The libvirt documentation describes both merge directions and the choice between a block commit, which merges the top into the base, and a block pull, which copies the base data into the overlay [src: libvirt-docs 6bfb2d73aac6a4d7] [src: libvirt-docs 3a1047aff38f2343].

Live block operations moved from ad hoc commands to a job framework. QEMU's block layer gained jobs (commit, stream, mirror, backup) with a common lifecycle: created, running, ready (for mirror and active commit, meaning source and target are in sync), pending, concluded, with a choice of automatic or manual finalisation and dismissal. The older drive-mirror and block-commit monitor commands persisted, and the newer blockdev-based commands let management software describe the graph of nodes explicitly. The QEMU documentation on live block device operations describes the mirror, commit and pull jobs, and the notion of a pivot, in which the guest switches to the new image at the end of a job [src: qemu-docs ec3686469abaeacd]. Libvirt maps these to virsh blockcommit, blockpull and blockcopy, with flags for active commit and pivot.

Backup took a similar path. Early practice copied the whole image or used snapshots plus rsync. Dirty bitmaps, persistent bitmaps stored in the qcow2 and updated by every write, record which clusters changed since a point in time, so a backup job can copy only those; the QEMU documentation walks through a push-mode incremental backup from a bitmap and the chaining of increments [src: qemu-docs 092c3ec919d7112b]. A pull model, in which an NBD export of the point-in-time image is offered to the backup tool, matured later and is what libvirt's backup API uses.

Lessons accumulated about the traps: an overlay records the backing file path and format as strings, so renaming or moving the base breaks the chain; the format of the backing file must be recorded and stated, because probing an untrusted image's format can be exploited (a raw file that looks like a qcow2 header can point to host files); long chains degrade because each read may traverse several layers; and a block job interrupted by a crash leaves the chain in a state that tools must inspect and resolve [src: libvirt-docs 3e23eaa1b1408929].

The emerging pattern: use a thin, shared, read-only base with short overlays, keep chains short by merging after snapshots or backups, make every operation explicit about formats, and use dirty bitmaps and block jobs for anything done while the guest runs.

## Current state

**Format structure.** A qcow2 file has a header (magic, version, backing file name and size, cluster size, virtual size, encryption method, the L1 table's size and offset, the refcount table's location, snapshot table, feature bits), then header extensions, then data. Guest address space is divided into clusters (64 KiB by default; between 512 bytes and 2 MiB). A guest address is translated through two levels: the L1 table, small and kept in memory, points to L2 tables, each one cluster in size and holding entries that give the file offset of a data cluster and flags (compressed, zero, copied). The refcount table and blocks track how many users each file cluster has; a count of one with the "copied" flag means it can be written in place, while a higher count (shared with a snapshot) requires copy-on-write. Reading an unallocated cluster returns zeros, or, if there is a backing file, the data from the backing file at that offset [src: qemu-docs 6d17a8062076f613].

**Consequences for size and speed.** A new image is tiny, a few hundred kilobytes, because tables are created on demand. Preallocation modes trade creation time for write speed: off (default), metadata (allocate L1/L2 and refcounts), falloc and full. A larger cluster size reduces metadata and helps sequential I/O but increases the write amplification for small random writes and the size of copy-on-write; extended L2 reduces that penalty by tracking subclusters. The L2 table cache is a notable tunable: for a large image with random access, the default cache covers only part of the file, so lookups cause extra metadata reads; the cache size can be raised or the cache-clean-interval used. Lazy refcounts speed up writes at the price of needing a repair after a crash. Compression (zlib or zstd) is per cluster and is applied by qemu-img convert, mainly for distribution images, not for running guests. Encryption in current QEMU uses LUKS inside the image.

**Backing chains.** An overlay is created with a backing file and an explicit format: qemu-img create -f qcow2 -b base.qcow2 -F qcow2 overlay.qcow2. The result is a file whose reads fall through to the base for unallocated clusters, and whose writes go to the overlay. Sizes may differ; an overlay larger than its backing reads zeros beyond the base's end. qemu-img info --backing-chain prints the chain; qemu-img map shows which layer owns each range; check validates the metadata of one image and reports leaks and corruptions with repair options. The invariants are that every file below the top must be treated as read-only while an overlay exists, and that the chain's recorded paths must resolve. Libvirt's domain XML can describe chains explicitly with backingStore elements, with the format of each layer stated [src: libvirt-docs 6b120660130ea6d3].

**Offline operations.** qemu-img rebase changes an overlay's backing file; in the safe mode it copies data so the content is preserved when the new base differs, and with -u (unsafe) it only rewrites the pointer, which is right when the new base is identical content at a new path and wrong otherwise. qemu-img commit merges an overlay's changes into its backing file (and empties the overlay), reversing the layering for the top layer. qemu-img convert copies or flattens an image and can change format, compress, enable subformats and skip zero regions: convert with no backing option produces a standalone image that contains the whole chain's data, and with -B keeps a chosen backing. resize changes the virtual size (growing is safe; shrinking needs the guest file system to be smaller first and the --shrink flag). amend changes options of an existing image, such as upgrading compatibility. snapshot manages internal snapshots. The tool's manual explains each subcommand and its cautions [src: qemu-docs b2dc5f482935a0ba].

**Live operations.** A disk-only external snapshot makes the current image the backing file of a new overlay while the guest runs; with libvirt, virsh snapshot-create-as --disk-only --atomic does it across all disks, and a quiesce option asks the guest agent to freeze file systems for consistency. Merging the chain while the guest runs uses block jobs: blockcommit with the active flag merges the top layer into its base while still taking new writes, and then a pivot makes the guest use the base directly; blockpull streams base data into the overlay so the backing dependency can be removed (useful when the base is on slow or remote storage); blockcopy (drive-mirror) copies the active image to a new location and pivots, which is how a disk moves between storage systems without downtime. Each job has a state to poll and, for those with a synchronised phase, an explicit completion step; an operator must not delete the old files until the job has concluded and the guest's XML shows the new path.

**Dirty bitmaps and backup.** A persistent bitmap in a qcow2 tracks writes since its creation or last reset. A backup job copies the changed clusters to a target and starts a new bitmap, giving incremental chains whose restore needs the full backup and each increment in order. With the pull model, the backup client reads from a read-only NBD export of a frozen view, which keeps the tool outside the guest path.

**Guest-visible integration.** TRIM and discard from the guest become hole punching or cluster deallocation in the qcow2 when the disk bus has discard enabled and the image allows it (discard=unmap on the driver). Zero writes become zero-flag clusters. Space reclamation therefore needs the guest to run fstrim and the whole stack to pass discard through. The qemu-guest-agent provides filesystem freeze for crash-consistent snapshots, and applications that need application consistency need their own quiescing.

**Generalised pattern.** Copy-on-write layers with a reference-counted mapping: cheap clones and snapshots from immutable lower layers, merge or flatten when layers accumulate, and keep an explicit record of what depends on what.

## Assessment: the good, the bad and the ugly

The good: qcow2 delivers thin provisioning, instant clones, snapshots, compression and encryption in a portable file, supported by every part of the QEMU and libvirt stack and by cloud image distribution (nearly all cloud images are qcow2 for this reason). External snapshots and block jobs make live storage management possible. Dirty bitmaps give efficient incrementals. Tools are scriptable and predictable.

The bad: performance lags raw images and block devices, especially for random writes to unallocated regions (allocation and metadata updates), with the gap narrowing as the format improved but not disappearing. Long chains cost I/O latency and make operations slow; each snapshot adds a layer. Metadata corruption affects everything at once. Many features interact: encryption with compression, internal snapshots with external ones, bitmaps with commits. An overlay on a shared base creates dependencies that are easy to forget, so deleting a base that "nobody uses" destroys dozens of VMs. Management tools differ in what they assume (some deprecate internal snapshots, some require them).

The ugly: a crash in the middle of a job, a power loss with lazy refcounts or an out-of-space event on the storage can leave an image needing repair, and repair (qemu-img check -r all) is best effort. Out-of-space is the typical production incident: thin provisioning promises more than the storage has, so a datastore fills, guests pause with I/O errors, and the fix is to free space under pressure. Backing-file path handling is fragile: absolute paths break when a pool moves, relative paths break when a file is copied alone, and format probing of backing files is a security hazard. Snapshot sprawl is typical: a forgotten snapshot from an upgrade grows for months and then a commit takes hours at a bad time. A merge operation that uses the wrong direction (commit instead of pull) removes the ability to roll back. And cloning a VM by copying an overlay without its base gives a file that cannot start.

## Applications beyond this domain

The layered, reference-counted copy-on-write pattern is used throughout storage: container image layers and overlay file systems (overlayfs, the layer stack of container images), file systems with snapshots and clones (ZFS, Btrfs, XFS reflinks, APFS), LVM thin pools, Ceph RBD clones and Git's object store (shared immutable objects, with deltas). Database engines use copy-on-write B-trees and multiversion concurrency. Backup systems use change tracking (VMware's CBT, Hyper-V's resilient change tracking, bitmaps in QEMU, journals in file systems) with the same incremental-chain logic. Cloud image catalogues and golden-image pipelines depend on cheap clones. The idea of an immutable base plus a writable overlay appears in live operating system images (squashfs with an overlay) and in immutable infrastructure.

## Examples

**Cloning from a template.** A base Debian image is prepared once, shut down and made read-only. For each new VM, the administrator creates an overlay (qemu-img create -f qcow2 -b debian.qcow2 -F qcow2 vm1.qcow2 20G), boots it with cloud-init data, and each clone uses a few hundred megabytes on creation. After a base security update, new VMs use a new base, while existing overlays continue to use the old one until rebuilt.

**Merging a snapshot chain live.** A VM has three snapshot overlays after upgrades. The administrator starts an active block commit of the top overlay into the one below, waits for the job to reach the ready state, pivots, and repeats for the next. Each step shortens the chain; when the chain is a single file the old overlays are deleted. Writes during the merge go to both layers, so the job converges.

**A failing example.** An administrator wants to reclaim space and runs qemu-img commit on an overlay after copying it to a backup disk, then deletes the base's original directory believing the merge made it redundant. The other forty VMs overlay on the same base, and every one fails to start. The recovery is from the backup of the base and an inventory of overlays (qemu-img info --backing-chain over each file), which the team now runs before any base is modified.

## Related problems and ideas

Neighbouring problems: storage migration and live block copy across data centres, thin provisioning monitoring and quotas, deduplication and compression at the storage layer, image format security (untrusted images and the parsers that read them), and consistency of snapshots with application state. Alternatives: raw on reflink-capable file systems, ZFS zvols with send and receive, Ceph RBD with layering, LVM thin snapshots, and VirtIO-FS or passthrough directories for data that needs no disk image. Ideas at the edge: the external data file mode, which combines qcow2 metadata with raw performance and direct host inspection of data; userspace block servers (qemu-storage-daemon, ublk) that run block jobs outside the VM process; and NBD or vhost-user-blk exports of images to other tools.

## Active research

Work includes faster metadata handling (lower write amplification for small random writes, caching of L2 tables, parallel I/O in the qcow2 driver), better crash consistency and checking, compression and encryption performance, and the block layer's multi-queue and iothread support. Backup research covers incremental chains with fewer restore dependencies (backup with periodic synthetic fulls), deduplicated backup formats, and consistent group snapshots across several disks and guests. Security work fuzzes image parsers and formalises the trust boundary between a guest's disk image and the host. Open questions: how to express storage topologies declaratively so that tools verify chains before any operation, how to cap chain length automatically, and how to make thin provisioning failures safe.

## Future direction

Expect qcow2 to stay the interchange format for VM images while production storage moves to raw volumes with storage-level snapshots, and the QEMU storage daemon to take over management of images. Libvirt's backup and snapshot APIs will keep moving toward the blockdev graph model and pull backups. Subclusters and zstd will become common defaults for newly built images. Specific version thresholds for features named here (extended L2, zstd, backup API, bitmap persistence, blockdev defaults in libvirt): to verify against the QEMU and libvirt release notes.
