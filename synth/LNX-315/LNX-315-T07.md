# Running VirtualBox beside KVM, and on top of it

## Define the problem

A Linux workstation or build server often needs two kinds of virtual machine at once. The distribution's own tooling, libvirt with QEMU, is what administrators use for server guests; VirtualBox is what a developer, a trainer or a Windows-focused team has used for years, with its own images, its own networks and its own scripts. When both are installed, the machine has two hypervisors competing for one scarce thing: the processor's hardware virtualization feature (Intel VT-x or AMD-V). Historically VirtualBox carried its own kernel module, vboxdrv, that took control of that feature for its guests, while KVM, the in-kernel hypervisor used by QEMU, took control of the same feature for its guests. Two owners cannot hold it at once.

The visible symptom is familiar to anyone who has tried: start a KVM guest, then try to start a VirtualBox guest and receive an error about virtualization being in use, or the reverse. A second symptom is a silent slowdown, where VirtualBox falls back to a mode without hardware assistance and a guest that was fast yesterday crawls today. A third, newer symptom comes from kernel changes that initialise hardware virtualization when the KVM module loads, so that VirtualBox cannot start any guest as long as KVM is present, even with no KVM guest running [web: gentoo.org].

The deeper problem is about trust and maintenance. A hypervisor in the kernel has a very large privilege. Every distribution kernel update risks breaking an out-of-tree module such as vboxdrv, and every Secure Boot machine needs that module signed. Using the kernel's own hypervisor for VirtualBox guests removes a whole class of these problems, because KVM is maintained with the kernel and the user-space part, VirtualBox, no longer needs a private kernel driver. This slice explains how the two coexist today, what the KVM backend for VirtualBox is, how mature it is (stated with care, because the facts are recent and moving), and how to decide which design to run.

## History and approaches

The first approach was exclusive ownership. Administrators picked one hypervisor per boot, unloaded the other's modules, and rebooted or reloaded when they switched. It works and is easy to explain, and it makes any workflow that mixes guests painful. Scripts that unloaded kvm_intel before starting VirtualBox appear in many wikis.

The second approach was nested placement: run one hypervisor inside a guest of the other. A KVM host runs a Linux guest, and VirtualBox runs inside that guest using nested virtualization, or the reverse. Nested virtualization needs support from the processor, the outer hypervisor and the guest, and has to be turned on explicitly in KVM [src: archwiki e894df6e8606caeb]. It isolates the two stacks cleanly at the price of speed and of an extra operating system to maintain, so it is an answer for experiments and for CI, not for daily desktop use.

The third approach, which became important on Windows and macOS first, was for the third-party hypervisor to use the operating system's own virtualization interface instead of a private driver. VirtualBox gained such a layer under the name native execution manager (NEM) so that it could run on top of the Windows hypervisor platform and, on macOS, Apple's framework. The same design had a prototype for Linux KVM in the code base for years, but it was not enabled by default and was not complete [web: virtualbox.org].

The fourth approach is a finished KVM backend. A German company, Cyberus Technology, published a fork of VirtualBox that runs guests through KVM instead of vboxdrv, and released it as open source in early 2024; its stated reasons are stronger host hardening for certified environments, better support for guest security features that depend on virtualization, and use of hardware features such as interrupt virtualization [web: cyberus-technology.de]. Its published claim is that VirtualBox guests can then run in parallel with QEMU or other KVM-based virtual machine managers on one host. In later reporting, work from this effort was said to be moving into the main VirtualBox code base and into development builds (to verify the present status, version and release channel before relying on it; the story was changing during the period this course was written).

Partial failures along the way are worth recording. Scripts that unloaded modules lost running guests when the order was wrong. Nested setups hid performance problems behind "it works" because the guest did boot. Early NEM-style backends supported fewer features than the native driver, so users who switched found missing nested virtualization, weaker graphics or absent CPU feature controls and switched back.

## Current state

**What the processor feature is and who may hold it.** On x86, VMX or SVM operation is entered per processor core by a hypervisor. KVM enables it through its vendor module, kvm_intel or kvm_amd. The older VirtualBox driver enables it for itself when a guest starts. Which one is running can be checked with the module list and with the kernel's virtualization capability files; the course's KVM material and the KubeVirt validation procedure describe the same checks for finding out whether a node is able to run guests at all [src: kubevirt-user-guide ca34487e7da61ef1] [src: kubevirt-user-guide c8d24367b4e4d314].

**Coexistence with the native driver.** In practice, a host that runs both uses one of three arrangements.

- Time-sliced: only one family of guests runs at a time. This is the classic case, and it is simple if the module-load order is controlled.
- Separated by a kernel parameter: since kernel version 6.12, the KVM module can be told not to enable virtualization when it loads, only when the first guest starts. The parameter is `enable_virt_at_load`, set to 0 in a modprobe configuration file, and distribution packagers have documented it as the fix for VirtualBox failing to start when KVM is merely loaded [web: gentoo.org] (to verify the exact kernel versions and default on your distribution). With that set, the two stacks still cannot run guests simultaneously, but they can be installed together and used alternately without unloading modules.
- Nested: described above.

**The KVM backend.** With the backend, VirtualBox's execution engine talks to /dev/kvm as QEMU does, so the processor feature is owned by KVM, which shares it between all of its guests. Several consequences follow.

First, simultaneous operation becomes possible: a QEMU guest and a VirtualBox guest on the same machine, each as a normal process using KVM, as the project's own description states [web: cyberus-technology.de].

Second, the out-of-tree kernel module disappears from the path for guest execution. The ongoing maintenance burden of rebuilding vboxdrv per kernel, and of signing it on Secure Boot hosts, shrinks for guest CPU execution. Networking helper modules and other pieces may still have a kernel footprint, which depends on the build (to verify per version).

Third, the user interface does not change in principle. The machine definition, VBoxManage commands, disk images and Guest Additions still work, because the backend replaces the execution engine, not the management or device model. A person who learned the previous topic keeps that knowledge. Saved states are reported to be portable between backends, but this has not been broadly validated and should be tested before it is trusted [web: linuxiac.com].

Fourth, features that were built around the native driver may be missing or different. Candidates to check are nested virtualization inside a VirtualBox guest, particular CPU feature masks, certain graphics acceleration modes, performance counters and host-side power management hooks. The project's own roadmap lists nesting and graphics as follow-up work, which means they were not complete in the first release [web: cyberus-technology.de].

**Distribution packaging and current availability.** The community has produced packages for some distributions that build the KVM-enabled variant, and the mainline project has begun to carry parts of the backend in its code base; both are recent (to verify the package, version and whether a release build includes it). Production users should treat it as a feature to qualify with their own guests and workloads, with a rollback to the native driver planned.

**Security view.** KVM is a small, widely reviewed kernel component with an active upstream and a large user base, and it carries hardening work that a private driver might not. The VirtualBox user-space process still handles complex emulated devices, so it remains an attack surface, but a compromise there lands in an unprivileged process, as with QEMU. Under the native driver, parts of device emulation run in a more privileged context. This reasoning is the main argument for the backend in hardened environments. Both stacks share the problem of CPU side-channel vulnerabilities, which are mitigated by the host kernel and microcode, not by the choice of user-space tool.

**Operating both stacks.** Whatever the arrangement, a few habits matter. Keep the two management worlds separate: libvirt owns its networks and storage pools and VirtualBox owns its host-only and NAT networks, so address ranges and bridge names must not collide. Give each stack separate disk image directories and never open the same image in both at once, since there is no shared locking between them. Document which stack owns the processor feature at boot. Compare the guests' CPU model and feature flags, because the same disk image may see different virtual hardware under each. When migrating a guest between stacks, use the export and conversion route described in the earlier VirtualBox topic and the image conversion tools in the storage topic, and expect to re-check device drivers inside the guest [src: libvirt-docs 404bd89fc2d03760].

## Assessment: the good, the bad and the ugly

The good. The KVM backend, where available, replaces a private privileged driver with the kernel's maintained one. It allows real simultaneous use of two hypervisor front-ends, which gives teams a path to keep VirtualBox-based tooling during a move to KVM. It reduces the Secure Boot and kernel-update friction of a third-party module. The kernel-level improvement of loading KVM without enabling virtualization until needed removes a long-standing conflict even for users of the native driver.

The bad. The backend is new, with a moving status and missing features at the edges. Packages and documentation are thin compared with the long-standing driver, so problems are harder to search for. Performance claims are not yet supported by independent benchmarks that this course could confirm (to verify with your own measurements). Version coupling between VirtualBox, kernel and distribution packaging is strict, and mismatches give errors that look like generic virtualization failures.

The ugly. Silent fallback is the worst failure: a guest that starts without hardware assistance because the processor feature was unavailable is slow, and the cause is not obvious to the person at the keyboard. Equally troublesome is the half-configured host: KVM loaded at boot with virtualization enabled, a VirtualBox install with a module that cannot start, and a user who "fixes" it by removing the wrong thing. A final trap is two stacks opening one disk image, which corrupts it without warning.

## Applications beyond this domain

The same problem appears wherever two systems want exclusive control of a single hardware facility. GPUs shared between a desktop compositor and a compute framework, a single hardware timer, a TPM claimed by two agents, a network card whose queues are partitioned between a kernel stack and a user-space polling driver: each needs an arbiter, and the winning pattern is to let the operating system own the facility and have applications request it through a stable interface. That is the argument for the KVM backend, and it is the same argument made for Windows and macOS hypervisor interfaces. The idea of enabling a feature on first use instead of at load time is the general lazy-initialisation fix for global side effects that conflict. Nested placement as a way to isolate incompatible stacks recurs in container-in-VM designs. Packaging a private kernel module is, more generally, the question of out-of-tree driver maintenance, which also touches GPU drivers, file systems and storage cards.

## Examples

Check which hypervisor modules are loaded and whether the processor offers the feature:

```bash
lsmod | grep -E 'kvm|vbox'
grep -c -E 'vmx|svm' /proc/cpuinfo
ls -l /dev/kvm
```

Allow both stacks to be installed together on a recent kernel without VirtualBox failing at start (file name is a convention; keep it in the modprobe directory):

```bash
echo 'options kvm enable_virt_at_load=0' | sudo tee /etc/modprobe.d/kvm-lazy.conf
```

Reboot or reload the kvm modules and confirm with the module parameter in sysfs. A diagnosis walk-through: a guest that starts but feels five to ten times slower than before. Look in the VirtualBox log for a line about the execution mode and whether hardware virtualization is in use; check for a competing hypervisor (a running KVM guest or a loaded module that took the feature); then decide whether to stop the competitor, use the lazy-enable option or move to a KVM-backed build.

A second example, a decision. A team has twelve Windows guests built as VirtualBox machines and a new set of Linux services in libvirt on the same hosts. Options: keep both with exclusive time slices (cheap, awkward); run VirtualBox inside a KVM guest (isolated, slower); qualify the KVM backend for the Windows guests, with a native-driver fallback (best long-term, needs a test plan); or convert the Windows guests to libvirt using the migration tools covered later in this course (end state, most work). A reasonable plan is the third option now with the fourth as a project.

## Active research

The open questions are practical. How complete will the backend become, and will it be included in release builds from the upstream project, not only in forks and development builds (to verify)? How does performance compare with the native driver and with QEMU on identical guests, using published benchmarks and not vendor statements? Can saved states move between backends reliably? Which security-relevant guest features, such as virtualization-based security on Windows guests, work with the backend? On the kernel side, the discussion about lazy enabling of virtualization, its default and its interaction with other consumers such as out-of-tree drivers continues, and the effect of that default on laptops and power use is of interest. Researchers also study isolation of device emulation by running it in sandboxed or separate processes, which both QEMU and VirtualBox communities have explored.

## Future direction

The probable direction is that user-space virtualization front-ends use the kernel's hypervisor on Linux, as they already do on other systems, with private kernel modules limited to compatibility. For administrators, that means fewer conflicts and a smaller set of host kernel concerns, and a gradual move of hybrid fleets toward a single hypervisor core with several management front-ends. Which front-end wins on a given workstation is a matter of tooling and team habit, not of the hypervisor. Plan for it by keeping machine definitions in scripts, images in portable formats and the choice of backend in one documented place, and verify any claim here that is marked as such before a production decision.
