# Guest firmware, trusted boot and confidential virtual machines

## Define the problem

A virtual machine starts with firmware, a program that runs before any operating system, initialises the virtual hardware, finds a boot device and hands control to a boot loader. That choice shapes what the guest can do. A legacy BIOS boots from a master boot record, limits disks to two terabytes in the classic scheme and has no standard way to verify what it loads. UEFI firmware boots from files on an EFI system partition, supports large disks and modern devices, keeps settings in non-volatile variables, and can verify that each stage of boot is signed by a trusted party, which is what Secure Boot means. Windows 11 requires UEFI, Secure Boot and a TPM. Many security baselines and cloud images assume them.

A second problem begins where the first ends. Even with a verified boot chain inside the guest, the guest trusts the host. The hypervisor, its administrators, anyone who can read host memory or attach a debugger to QEMU, can see and change everything the guest does. For a cloud customer running sensitive workloads on a provider's machines, or an organisation hosting regulated data on shared infrastructure, that trust is a business risk, and the guest's own measures cannot remove it. Confidential computing hardware answers by encrypting guest memory with keys the hypervisor cannot read, protecting guest register state and integrity, and providing an attestation protocol by which a remote party can verify what is running before releasing secrets to it.

This slice covers the firmware choices (SeaBIOS and OVMF), how UEFI variables and Secure Boot keys are stored and enrolled, virtual TPM devices, and confidential VM technologies (AMD SEV, SEV-ES, SEV-SNP and Intel TDX, with brief mention of IBM Secure Execution and ARM CCA): what each protects, how libvirt and QEMU launch such guests, how attestation works, and where the protection ends. Because the hardware is expensive and rare, the course treats this as a planning and verification topic with a guided exercise.

## History and approaches

Early QEMU shipped Bochs BIOS and later SeaBIOS, a free implementation of the PC BIOS, which remains the default for the i440FX machine type and boots legacy images with minimal fuss. The UEFI story began with Intel's EFI in the late 1990s and the UEFI Forum's standard in 2005. The open source implementation, TianoCore EDK II, was adapted for virtual machines as OVMF (Open Virtual Machine Firmware) around 2012, with builds for x86 and, as AAVMF, for ARM. OVMF is usually shipped as two files: a read-only code image and a per-VM variable store (NVRAM), which holds boot entries and Secure Boot databases. A guest with the code image alone cannot save settings, and sharing one NVRAM file between guests mixes their boot state, so libvirt copies a template to a per-VM file.

Secure Boot was designed for physical PCs. The firmware holds a platform key (PK), key exchange keys (KEK), an allowed-signature database (db) and a forbidden one (dbx). Boot loaders and drivers must be signed by something in db and not in dbx. In practice most distributions boot through a small shim signed by Microsoft's UEFI CA, which then verifies the distribution's boot loader and kernel with the distribution's own key. In virtualisation, the question is who provisions the keys. OVMF builds shipped with empty variable stores (Secure Boot off, setup mode) or with Microsoft's keys pre-enrolled, and libvirt and QEMU learned to describe firmware through JSON descriptor files that list the code path, the variables template, features (secure-boot, enrolled-keys) and the machine types supported, so that a tool can pick a matching firmware by capability instead of by file path. Libvirt's firmware autoselection reads these descriptors [src: libvirt-docs 0687a623bf59cf2a]. Secure Boot in QEMU needs the q35 machine type with System Management Mode enabled, because OVMF protects its variable store by running the update code in SMM so the guest operating system cannot write the flash directly.

The next building block is the TPM. A Trusted Platform Module is a small chip that holds keys, performs cryptographic operations and records measurements of boot components in platform configuration registers (PCRs). Measured boot has the firmware, boot loader and kernel each hash the next stage into a PCR before running it, so that the final state is a verifiable record of what booted, and keys can be sealed to a PCR state so that they are released only if the measurements match. For VMs, a software TPM, swtpm, emulates a TPM 1.2 or 2.0 and QEMU connects to it through a socket, presenting a TIS or CRB device; its state is stored in a directory that must persist and be protected, because it contains the TPM's keys. Libvirt manages the swtpm process and state, and KubeVirt exposes a persistent vTPM through the VM spec, with the state kept in a persistent volume [src: kubevirt-user-guide 89e2cbabacb2685a]. The virtual TPM is only as trustworthy as the host that runs it, since the host can read the state files and the emulator's memory.

Confidential computing began in hardware. AMD introduced Secure Encrypted Virtualization (SEV) with the first-generation EPYC processors in 2017: a memory controller engine encrypts each guest's memory with its own key, selected by an address-space tag, so the hypervisor reading RAM sees ciphertext. It did not protect register contents when the guest was descheduled, nor the integrity of memory (a malicious hypervisor could still replay, corrupt or remap pages), and several research attacks demonstrated the gaps. SEV-ES (2018) encrypts register state on VM exits. SEV-SNP (Secure Nested Paging, 2020, in third-generation EPYC) adds integrity protection through a reverse map table that stops the hypervisor from remapping a guest page, plus VM privilege levels, interrupt protection and a stronger attestation report signed by a chip-unique key. Intel's equivalent, Trust Domain Extensions (TDX), arrived in fourth-generation Xeon Scalable (Sapphire Rapids) processors: a trusted domain is a VM whose memory is encrypted and integrity-protected, managed by a signed, Intel-supplied module that runs in a new CPU mode and mediates between the VM and the untrusted host. IBM Secure Execution on Z and ARM's Confidential Compute Architecture are comparable designs. QEMU documents launch procedures for SEV and SEV-SNP guests and for TDX guests, including the firmware requirements [src: qemu-docs bcafb3b775995f3a] [src: qemu-docs cd21f89051ef9fc5].

Making this usable required changes across the stack. The guest firmware must be confidential-aware (OVMF built with SEV-SNP or TDX support, and a TDVF for Intel) and is part of the measurement. The guest kernel needs drivers for the secure interfaces, such as the shared and private memory conversion with the swiotlb bounce buffers for device I/O, since devices cannot DMA into encrypted memory. The host kernel needs the enabling code; upstream support for hosting SEV-SNP guests was long delayed outside of vendor kernels and landed in stages (version details: to verify), with TDX host support following. Libvirt and QEMU gained launchSecurity configuration, and KubeVirt documents SEV, SEV-SNP and IBM Secure Execution for VMs in Kubernetes [src: kubevirt-user-guide 11cd406ce3a3815e] [src: kubevirt-user-guide 1a7c1c2e32e8d0fc]. A newer format, IGVM (Independent Guest Virtual Machine), packages the guest's initial state and firmware in a portable file so that different hypervisors can launch the same measured guest [src: qemu-docs 70718d2b15d7bc5b].

Attestation is the difference between encryption and trust. At launch, the hardware computes a measurement of the initial guest contents (firmware, and for some configurations kernel, initrd and command line). The guest can request a signed report from the processor that includes this measurement and a user-chosen nonce, which a verifier checks against the vendor's certificate chain, then releases secrets (disk encryption keys, credentials) only to a matching guest. Projects and standards surround this: the Confidential Containers community builds a key broker and attestation service so that Pods in Kubernetes run inside confidential VMs and pull encrypted images; the IETF Remote Attestation Procedures (RATS) architecture defines roles; and the Confidential Computing Consortium within the Linux Foundation hosts projects.

The emerging pattern: boot with open firmware that you can measure, anchor trust in hardware-signed reports, bind secrets to attested measurements, and treat the hypervisor as untrusted for confidentiality while remaining trusted for availability.

## Current state

**Firmware choice.** Use SeaBIOS (the default) for legacy guests, quick tests and old operating systems. Use OVMF for UEFI guests: it is required for Secure Boot, for guests with disks above the MBR limits that boot from GPT, for Windows 11, for PCI passthrough of modern GPUs and for confidential guests. In libvirt, os firmware='efi' with the right machine type selects a descriptor-matched build; manual configuration names the loader and nvram template. The machine type (q35 for modern PCIe layout, i440fx for older ones) must be consistent with the firmware's feature needs.

**Secure Boot in guests.** The guest XML enables SMM (features smm state='on') and uses a loader marked secure='yes', with an NVRAM that already holds keys (an "enrolled-keys" template) or one that the administrator populates. Keys can be enrolled from inside the guest through the firmware's setup interface or with tools (virt-fw-vars from the virt-firmware project edits variable stores offline, and Linux's efi-updatevar and mokutil work in the guest). Organisations that run their own signing chain enrol a custom PK and db and sign their boot loaders and kernels. A guest started with Secure Boot on will refuse to boot unsigned loaders, which is the intended outcome and the usual explanation of a "no bootable device" message after enabling it.

**vTPM.** The domain XML tpm element with backend type emulator and a version (2.0) tells libvirt to launch swtpm with a state directory per VM. Persistent state is essential for BitLocker or LUKS-TPM sealing: a VM that loses its TPM state loses the sealed keys. The TPM interface should be CRB or TIS as the guest expects. For Windows 11 and for measured boot, enable the TPM together with Secure Boot. Migration needs the TPM state moved with the guest, which libvirt and swtpm support with shared storage or state transfer, but the details and the key protection depend on configuration.

**SEV, SEV-ES and SEV-SNP.** The host needs a CPU and firmware (BIOS and platform firmware) with SEV enabled, a kernel with the KVM SEV support and the ccp driver for the secure processor, a limited number of ASIDs (guest keys), and a QEMU and libvirt that support launchSecurity. For SNP, the host kernel must support SNP hosting and the guest firmware must be an SNP-capable OVMF. The domain XML defines launchSecurity with type sev or sev-snp, policy bits (no debugging, no key sharing, require ES) and optionally the guest owner's certificate and session for remote launch. Memory is encrypted per guest; the guest must use paravirtual devices with bounce buffers for DMA; features such as memory ballooning, page sharing and live migration are restricted (migration support is limited and specific to some configurations, with upstream work ongoing). Guests can generate attestation reports through a device node in the guest kernel.

**TDX.** The host needs a platform and firmware with TDX enabled, the TDX module loaded, a kernel with TDX host support, and QEMU with a tdx-guest object. The guest uses TDVF (Trust Domain Virtual Firmware) and a kernel with TDX guest support, and gets a quote through the TDX attestation interface: a report signed by the platform's quoting enclave for remote verification. Memory is encrypted and integrity-checked, with private and shared page conversion for virtio.

**Attestation and key release.** A relying party (a key broker) challenges the guest with a nonce; the guest obtains a report or quote from hardware, containing the launch measurement, platform security version, and the nonce; the broker verifies the vendor signature chain, checks revocation and TCB version, compares the measurement to a known-good value and releases a secret over a channel bound to the guest. The weak link is policy: a measurement is only meaningful if someone has published and reviewed the reference values for the firmware and kernel in the measured set, and updates change them.

**Scope of the protection.** Confidential VMs defend against a curious or malicious host administrator, other tenants and some physical memory attacks. They do not defend against bugs inside the guest, against the guest's own malicious software, against side channels that remain (several microarchitectural and fault-injection attacks on SEV and TDX have been published, with mitigations through microcode and firmware updates), or against denial of service by the host. The guest's I/O devices, including its disks and network, are untrusted channels unless the guest encrypts and authenticates them itself.

**Generalised pattern.** Separate trust in availability from trust in confidentiality; have hardware produce a signed statement of what is running; release secrets only after verifying that statement; protect data that leaves the trusted boundary with the guest's own cryptography.

## Assessment: the good, the bad and the ugly

The good: OVMF with Secure Boot and a vTPM gives a guest the same boot security as modern physical machines, and cloud images and Windows 11 expect it. Confidential VMs give a meaningful, hardware-backed reduction of trust in the hypervisor with modest performance cost (single-digit per cent for many workloads), and let customers run on shared infrastructure that they cannot inspect. Attestation lets secrets follow verified software and not network location.

The bad: the hardware is limited to recent server processors, firmware settings and kernel versions have to line up, and early deployments are fragile. Several operations that operators rely on (live migration, snapshots, memory introspection, ballooning, host-side debugging) are restricted or absent. Debugging a guest that the host cannot read is hard by design. The vTPM state is a sensitive file that needs backup and protection, and a lost state means a guest that cannot unseal its disk. Key enrolment and signing for Secure Boot add operational work, particularly for custom kernels and out-of-tree modules that must be signed. Attestation requires infrastructure (a verifier, reference values, certificate caching) that most organisations do not have.

The ugly: the security claims depend on a long list of components. The platform firmware, the secure processor firmware, the hypervisor's launch code, the guest firmware and the guest kernel are all in the trust or measurement path, and each has had vulnerabilities, with some published attacks that break confidentiality or integrity guarantees on specific generations through side channels, voltage glitching or interface bugs. A guest with the host's vTPM is not strongly protected against that host. Secure Boot has its own history of bypasses through vulnerable signed boot components, which are handled by revocation through dbx updates that can break old media. Cloud offerings differ in what they actually promise, with some confidential VM products encrypting memory but not offering verifiable attestation to the customer by default. And confidential does not mean correct: a signed, attested guest that contains a vulnerability is still vulnerable.

## Applications beyond this domain

Secure Boot and measured boot are standard on physical servers, laptops and phones, and the same signing and measurement chain appears in firmware update systems, automotive secure boot and embedded devices. TPM-sealed disk encryption (BitLocker, systemd-cryptenroll with LUKS, and similar) is the common application of PCR-bound keys. Confidential computing is applied to cloud databases, multi-party analytics, machine learning on sensitive data, blockchain nodes and key management services; confidential containers apply it at Pod granularity. Mobile phones use trusted execution environments (TrustZone, Secure Enclave) for payments and biometrics, and cloud HSMs and Nitro Enclaves offer isolation from the parent instance. The attestation pattern is used in device identity for IoT and in supply chain verification for software.

## Examples

**A Secure Boot guest for a hardened Linux image.** An administrator creates a q35 guest with OVMF, SMM on, and an NVRAM populated with a custom PK, KEK and db that contain the organisation's signing certificate. The boot loader and kernel are signed with the matching key in the image pipeline. The guest boots only the organisation's signed images. A developer who tries to boot an unsigned test kernel sees the firmware refuse it, and instead uses a separate unprotected profile.

**A confidential database VM.** A team launches an SEV-SNP guest with a policy that disallows debugging, using an SNP-enabled OVMF. At boot, an initrd stage contacts a key broker, which receives an attestation report, verifies the signature chain and measurement and releases the LUKS key for the data disk. A test confirms that dumping the host-side QEMU process memory shows only ciphertext. A later update of the guest firmware changes the measurement, and the broker rejects the guest until the reference values are updated, which the team treats as a feature.

**A failing example.** A team migrates a Windows 11 guest to a new host. The VM boots but BitLocker asks for the recovery key and Windows reports a TPM error. The VM's swtpm state directory had not been copied; the destination created a fresh TPM, so the sealed key could not be unsealed. The fix is to restore the old state files, and the process change is to treat the vTPM state as part of the VM's definition in backups and migration plans.

## Related problems and ideas

Neighbouring problems: measured boot for hypervisors themselves (host attestation with a physical TPM, as in Keylime), secure enclaves at process level (Intel SGX, now deprecated for client use and limited on servers), memory encryption without integrity (TME and AMD SME for whole-system protection against physical attacks), and trusted device assignment so that a confidential guest can use a GPU or NIC without exposing its data (PCIe TDISP, with NVIDIA's confidential computing modes on recent GPUs). Alternatives for tenant isolation without confidential hardware: dedicated hosts, sandboxed runtimes and encryption at the application layer. Ideas still developing: portable guest launch formats (IGVM), unified attestation services across vendors, confidential live migration, and reproducible, transparency-logged guest images so reference measurements can be audited.

## Active research

Work covers side-channel and fault-injection analysis of confidential VM hardware, attestation protocols and formal verification of launch flows, live migration of encrypted guests, performance of encrypted memory and bounce-buffered I/O, paravisor designs (a small trusted layer inside the confidential VM that exposes a standard interface to the guest OS, as used by some clouds), and trusted I/O for devices. The Linux community works on upstream host support for SNP and TDX, on a common guest attestation interface, and on measured direct boot. Open questions include how customers can verify cloud provider claims, how to keep reference measurements maintainable across frequent firmware updates, and how to reduce the trusted computing base.

## Future direction

Expect confidential VMs to become a standard offering on major clouds, with upstream kernel, QEMU and libvirt support maturing, unified attestation tooling, and trusted device assignment extending protection to accelerators. Confidential Containers will make Pod-level confidentiality easier to adopt. Firmware and key management for Secure Boot will move toward automated, signed update channels. Version and hardware-generation facts above (upstream kernel versions for SNP and TDX host support, QEMU releases, platform requirements, available cloud products): to verify against current documentation before planning.
