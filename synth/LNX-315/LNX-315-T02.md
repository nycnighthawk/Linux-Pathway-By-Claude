# SR-IOV: one physical device, many assignable functions

## Define the problem

Whole-device passthrough gives a guest the real hardware but uses up the device: one physical network card or accelerator serves one virtual machine. A host that runs fifty small VMs cannot buy fifty network cards, and a cloud provider cannot dedicate a port to each tenant. The software alternative is to share the device through emulation or a virtual switch in the host, which costs CPU cycles, adds latency and jitter, and limits packet rates because every packet crosses the host kernel or a polling thread. For workloads such as telecommunications packet processing, high-frequency trading, storage targets and machine learning, that overhead is the problem.

The PCI Express specification called Single Root I/O Virtualization, shortened to SR-IOV, lets one physical device present itself as many independent PCI functions. The device keeps one or a few physical functions (PF) that are fully featured and managed by the host, and offers a number of virtual functions (VF), lightweight PCI functions that each have their own configuration space, their own memory-mapped registers and queues, and their own PCI identity. Each VF can be assigned to a different VM with the same VFIO mechanism as a whole device, and the hardware itself divides the shared resources (queues, bandwidth, interrupts) among the functions and switches traffic between them. The guest then drives a VF with an ordinary driver, with near-native performance, while the host retains control through the PF.

This slice covers what the hardware offers, how a host enables VFs, how the PF and VFs are configured and constrained (MAC addresses, VLANs, rate limits, spoof checking), how a VF is attached to a guest with libvirt, QEMU and KubeVirt, how the same idea extends to GPUs and other accelerators, and the trade-offs against paravirtual networking, especially around live migration and security. Prior knowledge of VFIO and IOMMU groups from the previous slice is assumed.

## History and approaches

Network I/O virtualisation went through several generations. The first was full device emulation: QEMU implemented an Intel e1000 or a Realtek card in software, and guests used their standard drivers. It was compatible with everything and slow. The second was paravirtualisation: Xen's netfront and netback, and then virtio-net, replaced register-level emulation with a shared-ring protocol designed for virtual environments, with the vhost-net kernel module and later vhost-user with DPDK reducing the cost further. Virtio is the default choice because it is fast enough for most workloads and migrates easily. Its ceiling is the host's packet processing capacity.

The third generation put the sharing in hardware. Intel's VMDq and similar features gave each VM a hardware queue, but kept the driver in the host. The PCI-SIG standardised SR-IOV in 2007 as an extension to PCI Express, and network vendors (Intel, Broadcom, Mellanox, Solarflare, Chelsio) shipped adapters with tens to hundreds of VFs per port. Linux added SR-IOV support in the PCI core in 2.6.30, with a sysfs interface in which writing a number to the device's sriov_numvfs attribute creates that many VFs [web: kernel.org]. Within a few years, the combination of VFIO and SR-IOV was the standard way to deliver direct network access to VMs in telecom clouds and OpenStack deployments.

Experience brought an understanding of the limitations. Because a VF is real hardware, the hypervisor cannot see or filter the guest's traffic in software, so policy that the virtual switch used to do (security groups, traffic mirroring, VLAN tagging, overlay encapsulation) must move into the NIC. Vendors added embedded switches (eSwitch) in the adapter, with a representor model: each VF gets a representor netdev on the host, and the host's Open vSwitch can offload flows to the hardware, so the first packet of a flow goes through software and subsequent packets match in the NIC. Kernel interfaces (the devlink and switchdev modes, TC flower offload) evolved to manage this. Live migration was the larger problem: a VF holds state in hardware that the hypervisor cannot read, so early solutions were workarounds, such as bonding a VF with a virtio device in the guest and hot-unplugging the VF before migration, with the virtio device carrying traffic during the move. QEMU's "failover" feature automates the pairing through a standby virtio-net device with a matching MAC. Newer approaches add vendor-implemented migration support through the VFIO migration interface for specific hardware.

Beyond networking, the idea spread. NVMe controllers expose SR-IOV functions (the QEMU emulation documents experimental support for emulating VFs in an NVMe device) [src: qemu-docs 6bbf07c38c58701e], and QEMU gained a composable SR-IOV device model for building virtual SR-IOV-capable devices, useful for development and testing of drivers and orchestration code [src: qemu-docs 2dda08df7302450f]. For GPUs, sharing took two paths: time-sliced or software-mediated vGPU with a vendor driver on the host (mediated devices), and later hardware-partitioned designs in which newer data-centre GPUs present SR-IOV VFs, each with a slice of memory and compute, which KubeVirt documents for NVIDIA vGPU devices on SR-IOV-capable cards [src: kubevirt-user-guide 232e586f995a6fb8]. Intel's data centre GPUs and AMD's instinct line follow similar models.

Orchestration layers adapted. OpenStack Nova can schedule instances with SR-IOV ports (vnic_type direct) and a PCI passthrough whitelist. Kubernetes uses the SR-IOV network device plug-in, which advertises VFs as extended resources, and the SR-IOV network operator and Multus to attach them as secondary network interfaces to Pods; KubeVirt adds an sriov interface type for VMs [src: kubevirt-user-guide f509cff5017e16f9]. DPDK applications in containers consume the same VFs.

The emerging pattern: SR-IOV is the standard for performance-critical I/O in multi-tenant platforms, with the host controlling policy through the PF or eSwitch, and with paravirtual devices kept as the default for anything that needs mobility.

## Current state

**Hardware model.** A PCIe device advertises the SR-IOV extended capability, which reports the total and initial number of VFs it can support, the offset and stride that determine each VF's routing identifier, and the VF device ID. The PF is a normal function with a driver; the VFs appear only after the PF driver enables them. Each VF has its own BARs (a slice of the device's address space), and the device multiplexes queue pairs, interrupt vectors and sometimes memory among VFs. Resource limits are real: the device might support 64 VFs but only 8 queues each, or share a fixed number of interrupt vectors, so planning is by device datasheet.

**Enabling VFs.** On the host, the PF driver must support SR-IOV. The administrator writes the desired count to /sys/class/net/IFACE/device/sriov_numvfs (or to the PCI device's sriov_numvfs attribute for non-network devices); changing a non-zero count requires writing zero first. The kernel creates the VF PCI devices, a driver binds to them (the VF driver, such as iavf or mlx5_core, which would give the host a netdev), and each has its own IOMMU group (when the platform supports ACS on the PF's upstream port, which is why SR-IOV devices on server platforms behave better than consumer boards). To make the VF count persistent, a systemd unit, a udev rule or a NetworkManager and systemd-networkd option sets it at boot; systemd.link and systemd.network have [SR-IOV] sections for configuring VF MAC, VLAN, rate and trust from network configuration [src: man-pages 75551da44ea41263] [src: man-pages 4408090924dfc54a].

**Configuring through the PF.** Using ip link, the host sets per-VF parameters on the PF: the MAC address (so the guest cannot choose arbitrary ones unless trusted), a VLAN and QoS tag applied in hardware, a minimum and maximum transmit rate, spoof checking (drop frames with a different source MAC or VLAN than assigned), link state (auto, enable, disable) and trust (let the VF set promiscuous mode or change its MAC). These settings are the main security controls over a guest that has direct hardware access, and the defaults vary by driver, so they must be explicit.

**Attaching a VF to a guest.** With libvirt, there are two forms. As an ordinary hostdev of type pci, pointing at the VF's PCI address; or as a network interface of type hostdev, which lets libvirt set the MAC and VLAN on the PF before assignment so the guest's address matches what the network expects. A libvirt network of forward mode hostdev can define a pool of VFs attached to a PF, so domains ask for a pool and libvirt picks a free VF [src: rhel-10-docs 132161900cffd0dc] [src: libvirt-docs 31bf2db5419ca6f1]. In KubeVirt, a VM interface uses the sriov binding, and the network is a Multus network attachment definition that names the device plug-in resource. The VF's group must be viable (usually alone), and the guest needs the VF driver.

**GPUs and accelerators.** An SR-IOV-capable GPU is configured by the vendor's host driver or tools, which create VFs with a chosen profile (memory size, share of compute engines, number of display heads). Each VF is assigned to a VM like a network VF. The guest installs the vendor's guest driver, often licensed. Some stacks run in a hybrid mode where the host vendor driver mediates through mdev. KubeVirt documents preparing such devices on the node and exposing them through permitted host devices [src: kubevirt-user-guide 232e586f995a6fb8].

**Migration.** For network VFs, the common production pattern remains failover bonding (guest-visible virtio standby plus VF primary, with hot-unplug of the VF during migration). Some vendors and kernels now offer VFIO live migration for specific VFs, in which the device driver saves and restores state and tracks DMA writes. KubeVirt notes limitations and requirements for live migration with NVIDIA vGPUs, which depend on the card and driver combination [src: kubevirt-user-guide cb92d78e47058dbb].

**Representors and offload.** In switchdev mode on supported NICs, the PF and each VF have representor netdevs on the host; an Open vSwitch bridge connects the representors and uplink, and flows are offloaded to the NIC through TC. This restores centralised policy and overlay networking for guests that use VFs.

**Generalised pattern.** A privileged function controls a pool of lightweight functions that carry the data path; the control path (policy, identity, limits) stays with the host, and the data path bypasses it.

## Assessment: the good, the bad and the ugly

The good: line-rate performance with low and stable latency, and low host CPU use. Each VF has an IOMMU-isolated identity, so many tenants can share one adapter. The PF controls give meaningful guardrails (VLAN, MAC, rate, spoof check). DPDK and RDMA workloads inside guests work as on bare metal. It is a standard feature of server NICs and widely supported.

The bad: the number of VFs is limited and fixed by hardware, so density is lower than virtio's. The host loses visibility: tools that watch traffic in the host stack (tcpdump on the tap device, iptables, bridge filtering, conntrack-based security groups) do not see VF traffic unless offload and representors are set up. Live migration, snapshots and memory overcommit are constrained as for passthrough. Hardware and driver combinations differ in features and bugs, and firmware and driver versions matter. Cloud-init and similar metadata in the guest must configure the VF's driver and MAC consistently with what the host assigned.

The ugly: a trusted or misconfigured VF can send traffic that the host expects to control, and a malicious guest can attack through the device interface: frame-flooding the shared eSwitch, exhausting shared queues, exploiting the PF driver's mailbox protocol (the channel by which a VF asks the PF for services) or a firmware bug. The mailbox has been the source of PF driver vulnerabilities. Resetting a VF (function-level reset) while the PF serves other VFs can disturb them on weaker hardware. Interrupt vector and queue exhaustion lead to confusing partial failures after enabling many VFs. Mixed workloads suffer noisy-neighbour effects through shared PCIe bandwidth and on-device buffers, with no host-visible counters for some of them. And for GPUs, licensing and driver support tie the setup to a single vendor's supported matrix.

## Applications beyond this domain

SR-IOV appears wherever a shared device must give isolated, low-overhead access to many consumers. Cloud providers use SR-IOV or similar hardware virtual functions for enhanced networking and for NVMe storage offload on their instances, with custom cards that present virtual NICs and virtual NVMe devices to every guest. Smart NICs and DPUs generalise the idea by running the switching and storage stack on the adapter's own processors and presenting VFs (and now scalable functions) to the host. Containers use SR-IOV VFs moved into network namespaces for Pods that need hardware speed, with the SR-IOV CNI. Storage systems and HPC clusters use RDMA over VFs. The kernel's virtual function design also appears in ARM server platforms and in non-PCI buses.

## Examples

**Enabling VFs for a packet processing VM.** On a server with a dual-port 25 GbE adapter, the administrator writes 8 to the sriov_numvfs file for port 0, finds eight new PCI functions each in its own IOMMU group, and sets VF 0's MAC address, VLAN 120, a maximum rate of 10 Gbit/s and spoof checking on with ip link on the PF. A libvirt domain gets VF 0 as an interface of type hostdev with the same MAC and VLAN, runs a DPDK application with a poll-mode driver in the guest, and shows microsecond-level latency with no host CPU consumed.

**A failover pair for migration.** A database VM has a VF as primary and a virtio-net standby with the same MAC, presented as a failover pair to the guest. Before migration, libvirt unplugs the VF; traffic moves to the virtio path; the VM migrates; on the destination, a VF is plugged back in. Throughput dips for the duration but connections hold.

**A failing example.** A team enables 64 VFs on a card, assigns 40 to VMs and finds that VMs randomly lose network connectivity under load. The adapter's firmware reserves queues for all enabled VFs; with 64 enabled there were too few interrupt vectors per VF, so some VFs came up with a single queue and were starved. The recovery was to enable only as many VFs as were needed, to use the vendor's tool to set the queues per VF, and to document the cap in the capacity plan.

## Related problems and ideas

Neighbouring problems: vDPA, which puts a virtio-compatible control and data plane on hardware so that guests use the generic virtio driver, retaining live migration across vendors; scalable I/O virtualisation (SIOV) and Intel's Scalable IOV, which promise thousands of lightweight device instances per device with finer-grained sharing than SR-IOV; DPUs and smart NICs offloading the entire virtual switch; and virtio offload in cloud hardware. Software alternatives: vhost-user with DPDK and OVS-DPDK keeps paravirtual interfaces but moves processing to dedicated polling cores, often within 20 to 30 per cent of SR-IOV performance with all the flexibility of software. For storage, NVMe over Fabrics and user-space targets (SPDK vhost) play a similar role. For GPUs, time-sliced sharing, MIG-style hardware partitioning and API remoting compete on isolation and flexibility.

## Active research

Work covers standard live migration for SR-IOV devices (VFIO migration v2, dirty-page tracking in the device or the IOMMU, and the work to expose device migration as a vendor-neutral feature), safe PF-VF mailbox protocols and fuzzing of PF drivers, hardware offload of overlay networks and security groups, and performance isolation between VFs (rate limiting of PCIe traffic and cache partitioning). The confidential computing community is working on trusted device interface standards so that a confidential VM can use a VF without the host seeing its memory. Open questions: how to attest a VF's firmware to a tenant, how to meter a shared device fairly, and how to make the PF's attack surface small enough for hostile tenants.

## Future direction

Expect SR-IOV to remain the base mechanism for fast I/O for several years, with vDPA and DPU-based designs taking over where mobility and vendor neutrality matter, and Scalable IOV extending the number of instances per device. Hardware live migration will become more common for network and accelerator VFs. Kernel and driver support for devlink-based management and switchdev mode will unify configuration. Limits and features of specific adapters, kernel versions with migration support, and vendor-specific licensing for accelerators: to verify against vendor documentation and kernel release notes before planning purchases.
