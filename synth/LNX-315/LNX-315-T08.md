# Building virtual machine images as a repeatable pipeline

## Define the problem

A virtual machine is only as reproducible as the image it starts from. Most teams begin by installing an operating system by hand, patching it, adding the tools they like and then copying the disk. That first image becomes a pet: nobody remembers every step, the installer's choices are lost, and a security update to the base distribution means doing it all again from memory. When the fleet grows, the differences between machines become incidents. One has a different time zone, one a forgotten test account, one an old SSH host key shared with ten clones.

An image pipeline treats the disk image as a build product with a recipe, inputs, tests and a version. It has to answer several questions that hand-built images skip. What is the source of trust: a vendor's published cloud image, an installer ISO, or a distribution package set? How is the image customised: by driving an installer, by editing a disk offline, or by booting it and running configuration? What must be removed so that two machines made from the image do not share an identity? How is the per-instance configuration, such as hostname, keys, network address and user accounts, supplied at first boot without baking it in? And how does the same recipe produce artefacts for more than one hypervisor, such as a qcow2 file for KVM and a VDI or OVA for VirtualBox?

This slice covers three families of tools that answer these questions at different layers. Packer builds images by running a hypervisor and provisioning the guest. virt-builder and the libguestfs tools edit disk images without booting them. cloud-init configures an instance at first boot from data supplied by the platform. The three combine: a pipeline typically builds or edits a generic image, generalises it, and relies on cloud-init to individualise each copy.

## History and approaches

The earliest approach was the golden image. An administrator built one machine, cleaned it by hand and cloned the disk. It was fast and wrong in predictable ways: the clean-up was a checklist in someone's head, and each new base release started the checklist again. Windows administrators had a formal tool for the same problem, a generalisation step that removes machine identity before capture; Linux had no equivalent, and teams wrote shell scripts.

The second approach was unattended installation. Distribution installers accept answer files (kickstart for the Red Hat family, preseed for Debian and its relatives, autoinstall for recent Ubuntu server installs, and the unattended mode of VirtualBox's own command line). A build server boots the installer ISO in a hypervisor, serves the answer file and waits. This produces a clean image from the vendor's own installation path, at the cost of a slow build (a full install each time) and of a build that depends on the installer's quirks.

The third approach was the image builder that automates the second. Packer, from HashiCorp, defines a template that names a builder (QEMU/KVM, VirtualBox, VMware, cloud providers), the source ISO or image, the boot commands that drive the installer's first screens, a communicator (usually SSH) and provisioners that run once the guest is reachable, followed by post-processors such as converting formats or producing a Vagrant box [src: rocky-docs 4c77c7a7f1517845]. The same template language can target several platforms by listing several sources, which is how one recipe yields both a qcow2 and a VirtualBox image. The tool's licence changed to a source-available business licence in 2023, which led some organisations to review their dependence on it (to verify the present licence terms before adopting it in a regulated setting).

The fourth approach avoids booting for much of the work. libguestfs, a library for accessing and modifying disk images from user space without mounting them in the host, supports tools for inspecting, editing and customising images. virt-builder takes a base template from an index (signed, and downloaded on demand), copies it, and applies customisation options such as setting the root password, installing packages, uploading files, running commands, and setting the hostname, then writes the result in the requested format and size [src: kubevirt-user-guide a7e7278e900479c3]. virt-sysprep, in the same family, removes machine-specific state from an existing image [src: rocky-docs 0f2a78d494a9c860] [src: rhel-10-docs 622e3c7bef463ec3]. These tools are fast, need no running guest, and are easy to put in a shell script or CI job. Their limit is that they run commands inside a small appliance that mounts the image and cannot exercise the booted system.

The fifth approach is vendor and distribution image builders. Red Hat's image builder composes a blueprint of packages and customisations into images for several targets, including KVM guest images and Vagrant boxes [src: rhel-10-docs fc42566543c86177] [src: rhel-10-docs 2daf7ac81172b2ff]. The newer image-mode approach builds the operating system as a container image and converts it to disk images. These tie the recipe to one distribution's supported tooling, in return for a supported path.

Alongside all of these, cloud-init grew from a tool for public clouds to the de facto first-boot configuration agent. It reads data from a datasource, applies user-data modules (users, SSH keys, packages, files, commands), writes network configuration and marks the instance as configured by recording an instance identifier. Its NoCloud datasource reads a small seed: a volume labelled cidata holding files named user-data and meta-data, and optionally network-config, supplied as an ISO or a small FAT disk, a network URL, or a kernel command line [src: rocky-docs 747fa4f3cb995cd2] [src: rocky-docs fa0b30287187ae29]. This is how a bare hypervisor gets the same first-boot behaviour as a public cloud.

Failures along the way shaped the practice. Images captured with host keys and machine identifiers inside produced duplicated identities; the cure is generalisation. Provisioning with long shell scripts over SSH produced images no one could reason about; the cure is small, declarative steps and tests. Images with the build user and a known password left in for convenience reached production; the cure is to remove or lock build credentials as the last step. And builds that fetched "latest" at build time made last month's image impossible to reproduce; the cure is pinning inputs and checksums.

## Current state

**Layers and responsibilities.** A good pipeline separates three concerns. The base layer is the operating system and its updates, built rarely and carefully. The role layer adds the software a class of machine needs. The instance layer, applied at first boot, supplies identity and secrets. Putting a concern in the wrong layer causes trouble: instance data in the image leaks and duplicates; role software installed at first boot slows every start and depends on the network.

**Packer in practice.** A template declares required plugins and then source blocks and a build block. For KVM, a QEMU source names the ISO or an existing disk image, its checksum, disk size and format, accelerator, headless mode, the communicator credentials, and either boot commands that type into the installer or a seed served by an HTTP directory or a second drive. For VirtualBox the shape is the same with a different source type and an export format such as OVF. Provisioners then run shell scripts, upload files or call a configuration tool, and post-processors convert or compress. Good practice is to build from a vendor cloud image where one exists, because it is already generalised and it skips the installer; to pin the source checksum; to run the build headless in CI; and to finish with a clean-up provisioner that removes the build account, shell history, logs, SSH host keys and the machine identifier.

**virt-builder and libguestfs.** The workflow is: list available templates, build with options, optionally resize and convert. Customisation options cover passwords and SSH injection, package installation, file upload, arbitrary commands, a first-boot script, setting the hostname, relabelling for SELinux and truncating logs. Because the work happens offline, the customisation should be limited to what can be done without a running init system. For anything larger, boot the image once in a build step. virt-customize applies the same operations to an existing image, virt-resize changes size, virt-sysprep generalises, and virt-sparsify reclaims empty space. Checking the result with guestfish or virt-inspector lets a pipeline test an image without booting it. The trust in a builder template index rests on its signature, so the index key and the transport should be checked as part of supply-chain review.

**Generalisation.** Before an image becomes a template, remove or reset: the machine identifier file so each instance generates its own; SSH host keys so each instance creates new ones; the cloud-init instance state, so it runs again on the next first boot; persistent network interface naming rules and MAC-specific configuration; logs and shell history; package caches and temporary files; build credentials; and, where relevant, registration with a subscription service. The libguestfs sysprep operations list these as named, individually selectable operations, which makes the policy reviewable [src: rocky-docs 0f2a78d494a9c860].

**cloud-init in practice.** Three files make up a NoCloud seed. The meta-data file holds an instance identifier and a hostname. The user-data file normally starts with a header line marking it as cloud configuration and then holds YAML for modules: users with SSH authorised keys and sudo rules, packages and package updates, write_files for configuration, runcmd for one-off commands, and others [src: kubevirt-user-guide 1faf55596b8b8b5f]. The optional network-config file describes addresses, routes and DNS in a versioned schema. The seed is attached as a second disk or an ISO labelled cidata, or the same content is passed through the platform's own mechanism: libvirt and virt-install can attach it, Kubernetes-based platforms embed it in the VM definition [src: kubevirt-user-guide 73b9745fe36b2016]. cloud-init runs in stages tied to boot (a network-independent stage first, then network, then config and final), and it records the instance identifier so that changing the identifier in meta-data causes the configuration to run again on the next boot. A schema validation command exists in current cloud-init releases and belongs in CI to catch typos before they reach an instance (to verify the sub-command name for your version).

Security habits for user-data follow from its nature. It is stored in the seed or on a metadata service where other processes may read it, so it should hold public keys and bootstrap tokens with short lifetimes, not long-lived secrets. Plain-text passwords belong nowhere; hashed passwords are better than plain but still weaker than keys. Password login over SSH should be off in the image.

**Targeting both hypervisors.** The disk formats differ: qcow2 for KVM, VDI or VMDK for VirtualBox, and OVA or OVF for interchange. A pipeline can build once in a raw or qcow2 format and convert with the image tool; the conversion changes the container, not the contents, so drivers in the guest still matter. A Linux guest with virtio drivers and a generic initramfs boots on KVM, while on VirtualBox the emulated controllers differ and the initramfs must include drivers for them or be built in a hostonly-off mode (to verify per distribution). The first-boot seed is the portable piece: VirtualBox can attach a cidata ISO as an optical disk, and the guest's cloud-init finds it by label as it does on KVM. Vagrant boxes for VirtualBox, such as those Rocky Linux's QA process tests, wrap the same idea with a conventional SSH user and a Vagrantfile [src: rocky-docs 8f2238523a81f1e8].

**Testing images.** Treat the image as software. Tests that need no boot: the file list and installed package set, absence of build credentials, absence of host keys, correct size and format, checksums. Tests that need a boot: first boot completes, cloud-init status reports done with no errors, SSH works with the injected key, time sync and DNS work, the second boot does not rerun first-boot configuration, and a clone gets a different machine identifier. Run them in the pipeline against the actual artefact, then publish it with its checksum and a record of the inputs.

**Versioning and provenance.** Name images by the build date and the commit of the recipe, keep the inputs' checksums, store a package list and sign the artefact. Rebuild on a schedule, because the real security feature of an image pipeline is that last week's vulnerability is fixed by rebuilding, not by logging into each machine.

## Assessment: the good, the bad and the ugly

The good. A pipeline turns image creation into reviewed code. Vendor cloud images plus cloud-init remove the slowest and most fragile step, the installer. libguestfs tools are fast and can run unprivileged in CI. cloud-init gives the same first-boot behaviour on KVM, VirtualBox, public clouds and Kubernetes-based virtualization, so the instance layer is portable. Generalisation steps are named and auditable.

The bad. Packer's installer-driving boot commands are timing-sensitive and break with each installer release. Offline editing cannot run the guest's own package scripts reliably, so a package whose post-install needs a running system may misbehave. cloud-init is powerful and therefore easy to overload: scripts of hundreds of lines in runcmd recreate the unreviewable hand-built machine inside a YAML file. Differences between hypervisors' virtual hardware mean an image tested on one is not proven on the other. The licensing and governance of a build tool matter for long-lived pipelines.

The ugly. An image that still holds its SSH host keys, machine identifier or a build account, deployed a hundred times. A first-boot configuration that runs again after a clone because the instance identifier was not changed, or fails to run because it was not reset. A seed with the wrong volume label, which cloud-init ignores silently, leaving a machine reachable only through the build user. User-data checked into a repository with a token in it. A pipeline that pulls an unpinned base image so that a compromised or broken upstream flows straight into production.

## Applications beyond this domain

The pattern of a build recipe, a generalised artefact and instance-time injection is the same as container images with environment variables and secrets mounted at run time, as software supply chains with reproducible builds and provenance attestations, and as infrastructure-as-code where modules are written once and parameterised per environment. Layering, base then role then instance, is the same structure as container image layers and package-set composition in image-mode operating systems. Offline editing of an image without running it is the same idea as editing a container image's layers or a firmware image in a build tool. The notion of a first-boot agent keyed on an instance identifier appears in device provisioning for embedded and edge systems, where devices are built identically and claim their identity on first contact. Testing artefacts rather than recipes is the general principle behind verifying a released binary rather than the compiler flags.

## Examples

A minimal NoCloud seed (user-data and meta-data):

```yaml
#cloud-config
users:
  - name: ops
    groups: [sudo]
    shell: /bin/bash
    ssh_authorized_keys:
      - ssh-ed25519 AAAA... ops@example
ssh_pwauth: false
package_update: true
packages: [qemu-guest-agent]
runcmd:
  - systemctl enable --now qemu-guest-agent
```

```yaml
instance-id: web-001
local-hostname: web-001
```

Build a customised image offline, generalise it and use a backing file for fast test copies:

```bash
virt-builder debian-12 -o base.qcow2 --format qcow2 --size 10G \
  --install qemu-guest-agent --run-command 'ssh-keygen -A' --selinux-relabel
virt-sysprep -a base.qcow2 --operations defaults,-ssh-userdir
qemu-img create -f qcow2 -F qcow2 -b base.qcow2 test1.qcow2
```

Make the seed ISO and run a test instance (tool names may differ by distribution):

```bash
genisoimage -output seed.iso -volid cidata -joliet -rock user-data meta-data
virt-install --name t1 --memory 2048 --disk test1.qcow2 --disk seed.iso,device=cdrom --import --os-variant debian12
```

A diagnosis walk-through. A clone boots, but its configuration did not run. First check the cloud-init status and logs inside the guest to see whether a datasource was found. If none, look for the seed's volume label and whether the device is attached. If the datasource was found but modules did not run, compare the instance identifier with the one cloud-init recorded; a repeated identifier means "already done". Finally validate the user-data against the schema.

## Related problems and ideas

The storage topic in this course covers qcow2 backing chains used here for test copies. The VirtualBox topics give the export and unattended-install route on that platform. Migration from VMware, later in this course, uses the same libguestfs family to adjust drivers and boot configuration of an existing machine, and the Kubernetes virtualization topic uses cloud-init data and container-image disks as its first-boot mechanism. Configuration management tools such as Ansible fill the provisioner role and the line between "bake it" and "configure it at boot" is a recurring design question. Secrets management determines what can safely go in user-data.

## Active research

Open topics include reproducible image builds, where two builds from the same inputs give identical bits, which is hard because of timestamps, package metadata and random identifiers. Image provenance and signing, including attestation of what went into an image and verification at deployment, is an active area in supply-chain security. Image-mode operating systems that build from container images change who owns the recipe. Confidential computing (earlier in this course) requires images whose measurement is predictable, which pushes pipelines toward deterministic, minimal images. Finally, schema-checked and typed first-boot configuration, and a simpler subset of cloud-init for small systems, are being discussed in the community (to verify current proposals).

## Future direction

Expect image builds to move toward container-style tooling and declarative definitions, with offline editing for fast iterations and a booted test stage as the gate. cloud-init will remain the portable instance layer, probably with stricter validation. Teams that already separate base, role and instance layers, pin inputs, generalise explicitly and test the artefact will find each of these shifts cheap to adopt. Those that rely on a golden image and a checklist will find each of them expensive.
