# Moving virtual machines off VMware

## Define the problem

A virtual machine from VMware is a bundle of assumptions. Its disk is a VMDK file attached to a virtual SCSI or SATA controller that only VMware's hypervisor emulates. Its network card is a vmxnet3 or e1000 device. Inside, the guest runs VMware Tools, with drivers, a time-sync service and a graphics driver, and its boot configuration may name the controller drivers explicitly. Windows guests may also hold licence activations tied to the virtual hardware. Take the disk files alone to a KVM host and the machine may fail to boot, because the initial RAM disk lacks a driver for the new controller, or boot and fail to bring up its network, because the interface name changed.

Business pressure has made this problem urgent for many organisations. Changes in VMware's ownership and licensing from 2023 onwards led customers to review their dependence, and many began to plan moves to KVM-based platforms such as Red Hat Enterprise Linux with libvirt, OpenShift Virtualization, Proxmox, OpenStack or the oVirt lineage [web: broadcom.com] (to verify the current licence and packaging terms, which have changed repeatedly). The task is not one machine but hundreds or thousands, with dependencies, maintenance windows, application owners, compliance requirements and a business that does not want an outage.

A migration therefore has four layers of difficulty. The technical layer is converting a guest so it boots and performs on the target. The data layer is moving terabytes with limited downtime. The inventory layer is knowing what exists, what it depends on, what can be retired and what must be re-platformed. The people layer is scheduling, testing and rollback. This slice covers the first two in depth, with the tools that exist, and the others as the planning method that makes the tools useful.

## History and approaches

Migration between hypervisors is old. Physical-to-virtual conversion tools appeared with the first server virtualization, and virtual-to-virtual tools followed because every vendor wanted the competitor's customers. Three styles recur.

The first is the copy-and-fix manual method. Copy the disk, convert its format with the disk image tool, define a new machine, boot from a rescue image, rebuild the initial RAM disk with the right drivers, fix network configuration. It teaches the details and does not scale. Its main use is as a fallback when a tool fails.

The second is the converter tool. The libguestfs project created virt-v2v, which reads a guest from a foreign hypervisor, modifies the guest's disk offline so that it can boot on KVM, installs virtio drivers where possible, and writes the guest to a target such as libvirt, a local directory, OpenStack or oVirt [src: libvirt-docs 0a595278edeb180f] [web: libguestfs.org]. Related tools in the same family cover conversion of physical machines. This approach is the technical core of most Linux-based migration products, even where wrapped in a console.

The third is the managed migration service. Platform vendors built products that discover the source inventory, plan waves, map networks and storage, run the converter at scale and create machines on the target. For OpenShift Virtualization this is the Migration Toolkit for Virtualization, whose upstream project is called Forklift; other platforms have their own equivalents (to verify names and features for your release). These tools use the same conversion engine underneath, and add the orchestration that a spreadsheet and a shell script cannot.

A fourth approach, often forgotten, is not to convert at all. Applications that can be redeployed from configuration management or containers can be rebuilt on the new platform from images, which is cleaner than converting an old machine with years of drift. The image pipeline topic earlier in this course is the means. Data stores can be moved by replication at the application layer, which gives very short downtime and bypasses the hypervisor difference entirely.

History records recurring failures. Converting without testing the boot path, which yields a machine that starts into emergency mode. Leaving the old tools installed and finding they conflict with the new guest agent. Migrating at the weekend with no rollback and discovering at Monday that a licence tied to the old hardware has stopped working. And underestimating copy time: a long network copy of a large disk through the slowest transport turns a planned hour into a day.

## Current state

**What a conversion changes.** Conversion works on the guest's disks offline, in a small helper appliance, before the machine first boots on the target. For Linux guests it ensures the kernel and initial RAM disk contain the virtio storage and network drivers, rewrites configuration that names old devices, and removes or disables the vendor's guest tools where it can. For Windows guests it injects virtio drivers from a driver package into the offline system, and schedules installation of drivers and agents at first boot, which usually involves several reboots [web: libguestfs.org]. It does not reconfigure the guest's network addressing: a guest that used a static address keeps its configuration, and the interface name or MAC may differ on the target, so addressing is a post-conversion step to plan.

**Input paths from VMware.** There are several, with different speed and prerequisites [web: libguestfs.org].

- Through vCenter, using a libvirt connection that names the datacentre and host, the converter reads guest metadata from the management server. This is the easiest to set up and the slowest for bulk disk copy.
- With the VMware Virtual Disk Development Kit, a proprietary library that the operator must obtain separately, the converter reads disks through an NBD server plugin. It is usually the fastest option and adds a licence and download step. A thumbprint of the server certificate can be supplied to protect against interception, and newer versions can fetch it automatically if the openssl tool is available.
- Through the NFC protocol to the host or vCenter, with a non-proprietary NBD plugin, there is no proprietary library, at some cost in speed and in memory limits on the host's service, which can cause allocation errors with many parallel connections.
- From exported files: a VMX file with its VMDK disks, read locally, from an NFS mount or over SSH from the host; or an OVA archive exported from vSphere. The SSH path does not work when the guest has snapshots, and SSH is disabled by default on ESXi hosts.

In all paths the guest should be cleanly shut down. Converting from a running guest's snapshot is useful only for testing, because the disk would be crash-consistent and out of date at cutover. The vCenter role used must have the datastore and disk permissions, and a conversion service account of limited privilege is better than an administrator.

**Output paths.** The converter can create a libvirt domain on the local host, write disk files and a libvirt XML description into a directory, write disks with a boot script for QEMU, upload to oVirt or OpenStack, or write disk files with a Kubernetes-style YAML description as an experimental output for KubeVirt. Output format and allocation (raw or qcow2, sparse or preallocated) are options, and the choice follows the storage topic: qcow2 for flexibility, raw on good block storage for speed [src: rhel-10-docs c99ac708812430b5]. For KubeVirt, the common route is to write the disk to a volume and let a DataVolume or the platform's migration service present it to a VM, with the Containerized Data Importer used for upload [src: kubevirt-user-guide 1c1a570a3dd287eb].

**Prerequisites by guest type.**

Linux guests need a kernel recent enough for virtio, with minimum versions per distribution. A Xen paravirtual-only kernel must be replaced first. Disks encrypted with a key sealed to a TPM need an additional passphrase keyslot before conversion, since the TPM does not follow the disk. LVM and common file systems are handled. Dual-boot guests need an explicit choice of root.

Windows guests need a driver package from the virtio-win project, made available to the converter, with a documented location. Fast Startup and hibernation must be off in the guest so that the file system is clean. The system disk cannot be a dynamic disk. Older releases need support for the newer driver signing algorithm. VMware Tools removal is attempted but often needs to be finished by hand. BitLocker may require the recovery key after the virtual TPM and the platform measurements change. Activation may be triggered again by the changed hardware, so licensing owners should be told in advance. For Red Hat's supported Windows conversion, some Microsoft-signed components come through the vendor's channel [src: libvirt-docs 0a595278edeb180f].

**Customisation and first boot.** The converter accepts the same customisation operations as the image tools: run commands, upload files, install packages, set a hostname or inject SSH keys, and register first-boot scripts [src: kubevirt-user-guide fef0ebbae2e985c1]. Practical uses are installing the guest agent, applying network configuration for the new platform, removing monitoring agents that point at the old environment, and cleaning cached device configuration.

**Resources and performance.** Conversion time is dominated by the disk copy, and by network bandwidth between the source and the conversion host. Copies happen disk by disk by default, with an option for parallel copies. The conversion host needs temporary space for overlays, which should be fast local disk and not memory-backed file systems. Multiple simultaneous conversions against one vCenter can exhaust its HTTP session count and the host's NFC memory, and both limits are configurable on the VMware side. Network ports for vCenter reads (a management port and the HTTPS port) have to be open from the conversion host, and proxy settings in the environment may be ignored.

**Migration toolkits and waves.** A managed service adds several things: discovery of the source inventory; mapping of source networks and datastores to target networks and storage classes; validation of each VM against known blockers; scheduling in plans and waves; conversion workers running the engine in containers on the target cluster; progress reporting; and options for warm migration, where the bulk of the disk is copied while the source runs and a final delta is copied at cutover, using changed block tracking on the VMware side to minimise downtime (to verify availability and requirements per product release). Cold migration copies a powered-off guest and is simpler. A plan commonly pairs a pilot of low-risk machines, then waves ordered by dependency, with a rollback of the source until the target is accepted.

**Verification.** For every migrated machine, check: it boots without intervention; devices use virtio drivers; network addressing and DNS are correct; time sync works; the guest agent reports; services start in the right order; application tests pass; backup and monitoring have been repointed; the old tools are gone; performance is at least as good as before. Offline inspection tools can examine a converted disk without booting it, listing the detected operating system, installed applications and drivers, which turns the first check into an automated gate [src: rocky-docs 75135e06f109b9bd].

**Rollback and cutover.** Keep the source machine powered off but intact until acceptance. Avoid two live copies on the network at once, which causes address conflicts and duplicate application behaviour. Lower DNS time-to-live values before the window. Record the final source disk checksum or snapshot as evidence.

**Import of appliances and exported files.** Not every case involves a live VMware environment. Appliance archives in the Open Virtualization Format can be imported into other desktop and server hypervisors, VirtualBox among them, and custom VMDK images can be prepared and uploaded for cloud targets [src: virtualbox-docs 74c27d9d0cff8a0e] [src: rhel-10-docs 5faa305a28a3b78d]. These imports move the disk but do not fix the guest's drivers, so a converted-disk workflow is still needed for production machines.

## Assessment: the good, the bad and the ugly

The good. An open, scriptable converter exists and is maintained, with several input paths, support for Linux and Windows, and a clear model of what it changes. The same engine sits under commercial and open migration products, so skills transfer. Warm migration and replication reduce downtime. Moving through virtio drivers usually improves I/O performance over emulated hardware.

The bad. Windows conversion has many dependencies and gotchas: driver packages, activation, BitLocker, VMware Tools removal and multiple reboots. The fastest VMware input path relies on a proprietary library, which adds a download, a version constraint and a licence step. Network and storage mapping is manual in the absence of a managed service. Appliances and some enterprise features (distributed switch features, storage policy integration, vendor-specific virtual devices, fault tolerance clusters, snapshots as a backup method) have no one-to-one counterpart on the target, so each needs a design decision.

The ugly. Machines with passthrough devices, raw device mappings, clustered shared disks, or special licence dongles; these often cannot be converted by a tool and need an application-level move. Snapshots left in place for months, which slow copies and block some input paths. A conversion run during business hours against the production vCenter, exhausting its session limit. A static IP address configuration that quietly fails because the interface was renamed, leaving a migrated server running and unreachable. And scope creep, where the migration becomes a modernisation of everything and never finishes.

## Applications beyond this domain

Offline repair of a system image so that it boots on different hardware is the same problem as cloning a physical disk to a new machine, restoring a backup to dissimilar hardware, preparing cloud images for several providers and re-hosting an appliance. The wave-based plan, with discovery, dependency mapping, pilots and rollback, is the standard pattern for database migrations, mail system moves and cloud migrations. Warm migration, with a bulk copy followed by incremental deltas, is the same technique as database replication cutover and live migration inside a hypervisor. Treating "convert" and "rebuild" as alternatives per workload matches the usual rehost, replatform, refactor classification in cloud migration. The idea that a converter fixes the guest's view of hardware while leaving its configuration alone applies to any lift-and-shift.

## Examples

Convert a guest from vCenter with the VDDK transport and write it as a local libvirt guest (option names as in current releases, to verify):

```bash
virt-v2v -ic 'vpx://svc-migrate@vcenter.example.org/DC1/esx01?no_verify=1' \
  -it vddk -io vddk-libdir=/opt/vddk -ip /root/vc-pass.txt \
  web1 -o local -os /var/lib/images/converted -of qcow2
```

Convert from an exported OVA and write disks and XML to a directory:

```bash
virt-v2v -i ova /srv/export/app1.ova -o local -os /srv/converted
```

Check a converted disk without booting it:

```bash
virt-inspector -a /srv/converted/app1-sda | head -40
```

A diagnosis walk-through. A converted Linux guest drops to an emergency shell. Boot a rescue image or inspect the disk offline. Look for a missing virtio storage module in the initial RAM disk, a root device named by the old controller in the boot configuration, or an fstab entry using a device path. Regenerate the initial RAM disk with the virtio modules included, switch fstab to UUIDs, and test again.

A second example, wave planning. Three hundred machines: forty test machines (migrate first, as a pilot of the process); ninety stateless web servers (rebuild from images and retire the old ones); sixty databases (replicate at application level, short cutover); fifty Windows file and print servers (convert, with reactivation and BitLocker checks); sixty with special hardware or clusters (individual designs). The plan assigns an owner, a window and a rollback to each wave.

## Active research

Open areas include faster and more reliable bulk transfer: parallel reads, better use of changed block tracking, and non-proprietary access to VMware disks that matches the speed of the vendor library. Warm migration for Windows guests and for guests with unusual storage is less mature than for plain Linux guests. Automated discovery of application dependencies, so that waves can be derived and not guessed, is an active tooling area. Guest-side adaptation, such as reliably removing the old tools and reconfiguring networking, is partly solved by first-boot scripts and partly by hand. There is also work on migration to confidential and Kubernetes-native targets, where attestation and storage integration add constraints (to verify the state of these projects).

## Future direction

Expect migrations to be driven more by managed services and less by hand-run converter commands, with the converter engine remaining the common technical layer. The skill that endures is the ability to inspect and repair a guest offline and to plan waves. Teams that prepare images, inventories and test suites now will find the move cheaper whatever the target platform, and the same preparation makes the next move, from any platform, equally manageable.
