# Virtual machines as Kubernetes objects

## Define the problem

Many organisations run two platforms side by side. One is a virtualization stack for the machines that cannot be containerised: a vendor appliance, a Windows application, a database tuned for a particular kernel, a legacy service nobody dares to rewrite. The other is Kubernetes, where new applications are declared as objects, scheduled automatically, networked by policy and rolled out by pipelines. Two platforms mean two inventories, two access models, two networks, two backup tools, two skill sets and two budgets. Applications that mix both, a containerised front end with a virtual machine database, cross the boundary through gateways that someone must maintain.

KubeVirt addresses this by making the virtual machine a first-class object in Kubernetes. A VM is declared in YAML, stored in the cluster's database, scheduled to a node, given a network and storage through the same mechanisms as pods, and managed with the same tools. OpenShift Virtualization is Red Hat's supported distribution of the same technology inside OpenShift. The practical problem for an administrator is not only learning a new resource type. It is understanding what actually runs underneath (a normal QEMU and libvirt stack inside a pod), what Kubernetes concepts map cleanly onto virtualization (scheduling, labels, secrets, services) and where the mapping is awkward (live migration, persistent identity, stateful storage, performance isolation, nested privilege), so that one can decide which workloads belong there.

This slice covers the architecture, the main resources, storage and image import, networking, lifecycle and live migration, access to consoles, and operational concerns. It connects to the earlier topics in this course on pinning, hugepages and passthrough, because the same host features are requested through the VM specification, and to the next topic on migrating VMs from VMware, because KubeVirt-based platforms are a common destination.

## History and approaches

Before Kubernetes, the cloud platforms that managed virtual machines at scale, OpenStack among them, did so with their own schedulers and their own API. Containers arrived later and were scheduled by Kubernetes, and the first attempt to join the two was to run a hypervisor inside a container on a Kubernetes node, with an API extension to describe the VM. KubeVirt began as that idea at Red Hat in 2016 and 2017, and joined the Cloud Native Computing Foundation as a sandbox project, later moving to the incubating level (to verify the current maturity level) [web: kubevirt.io]. Its design choice was important: not a new scheduler, not a new hypervisor, but custom resources and controllers around the existing QEMU and libvirt, with Kubernetes doing scheduling.

Other approaches to the same goal exist. Kata Containers run a pod inside a lightweight VM for isolation, which is the opposite direction, containers in a VM, covered in the security course. Virtlet and similar early projects ran VMs as pods through the container runtime interface, with a runtime that translated container semantics into VM semantics; the approach fit the pod abstraction closely and limited VM features. Cluster API and OpenStack's own control of bare metal combine with Kubernetes at a higher level, with Kubernetes running on OpenStack VMs, not VMs running on Kubernetes. Harvester, based on a different set of components but also on KubeVirt, packages a hyperconverged virtualization platform with a Kubernetes control plane as an appliance.

Within KubeVirt, the API has evolved. Early versions used presets to share common settings between machines; these were replaced by instance types and preferences, which separate the size of a machine (CPU, memory, features) from the guest's preferred device model and firmware [src: kubevirt-user-guide 1217b30e9a8fd364]. Templates were added in OpenShift. Run strategies replaced a simple running flag, so that the intended lifecycle, always on, halted, started manually, or restarted only after failure, is explicit [src: kubevirt-user-guide 7ba865a808a10115]. Live migration moved from experimental to a normal operation with progress reporting and cancellation [src: kubevirt-user-guide 235e406e3ea7eac0]. Hotplug of disks, network interfaces and CPU was added step by step, with limitations documented per feature [src: kubevirt-user-guide 664361c5f46bc851] [src: kubevirt-user-guide eebd0d371b47bb71].

Partial failures are part of this history. Early adopters found that VM images had to be imported into persistent volumes before use and that the process was slow and fragile, which led to the Containerized Data Importer, now a standard companion [src: kubevirt-user-guide 1c1a570a3dd287eb]. Networking was another pain point: the pod network offers one IP per pod, which does not match VM expectations of several network interfaces, fixed MAC addresses and layer 2 adjacency, and this required secondary network support through the multi-network ecosystem. And clusters built for stateless containers lacked the shared storage that live migration needs.

## Current state

**Architecture.** KubeVirt installs a set of components into the cluster. A cluster-level API extension (virt-api) validates and serves the new resource types. A controller (virt-controller) watches virtual machine objects and creates the pods that realise them. A per-node agent (virt-handler, run as a DaemonSet) manages the VM on its node and reports state. Each running VM lives in a pod called virt-launcher, which holds the libvirt and QEMU processes, the VM's disks mounted as volumes, and its network plumbing. The unit of scheduling is that pod, so ordinary Kubernetes mechanisms (node selectors, affinity, taints and tolerations, resource requests and limits, priority classes) place VMs [src: kubevirt-user-guide 4ea5909cb2a928f4]. The cluster needs hardware virtualization on the nodes (or software emulation for tests), checked with the validation steps in the installation guide [src: kubevirt-user-guide c8d24367b4e4d314].

**Two resource levels.** A VirtualMachineInstance (VMI) is one running instance, comparable to a pod: it exists while the machine runs and carries the specification, status and the node it runs on. A VirtualMachine (VM) is the durable definition with a run strategy, which creates and deletes the VMI as the strategy dictates and holds the machine's identity across restarts. For most administration one works with the VM.

**The specification.** A VM template within the object lists CPU (cores, sockets, threads, model, dedicated placement), memory (with optional hugepages), firmware (BIOS or UEFI with Secure Boot, TPM and other options), devices (disks and their buses, network interfaces and their models, GPUs and other host devices), and a list of volumes that supply the disks. The same ideas the course covered for libvirt appear in new syntax: pinning through dedicated CPU placement, NUMA topology through passthrough of host topology, hugepages as a memory option, IOThreads policies, and virtio devices as the default. Instance types and preferences let one define named sizes and named guest profiles once and reference them from many VMs, so that a VM definition can shrink to a name, a preference and a disk [src: kubevirt-user-guide dc3bb41f2f06806e] [src: kubevirt-user-guide c7d8f1aee8906661].

**Storage and image import.** Disks come from volumes of several kinds: a persistent volume claim, a data volume, a container image used as a read-only or ephemeral disk, a cloud-init or sysprep source, config maps and secrets presented as disks, and an empty ephemeral disk [src: kubevirt-user-guide 56a54b9018e209a5]. The Containerized Data Importer adds DataVolumes: objects that describe a source (HTTP URL, registry image, upload, another PVC, a snapshot) and a target claim, and populate the claim before the VM starts, including cloning an existing volume [src: kubevirt-user-guide b1a788eea1a087fc] [src: kubevirt-user-guide 8b889a007efe6a40]. Large golden images are normally imported once and cloned for each new VM, using storage-level cloning if the storage system supports it. Volume mode matters: filesystem-mode volumes hold the disk as an image file, block-mode volumes expose a raw device and avoid a layer. The disk bus (virtio, SATA, SCSI) and cache and IO settings correspond to the options in the earlier storage topics [src: kubevirt-user-guide 1d6ffacdb357176a].

**Networking.** By default a VM attaches to the pod network. The binding method determines how: a masquerade binding NATs the VM behind the pod's address, which is simple and works with services and network policy but hides the VM's own address; a bridge binding on the pod network is more limited. For VMs that need real layer 2 connectivity, a second interface is attached through a secondary-network add-on using a network attachment definition that points at a host bridge, VLAN, SR-IOV virtual function or an overlay. Kubernetes Services and DNS can select VMs by label as they do pods [src: kubevirt-user-guide a52244796ce38db8]. SR-IOV attachment follows the same ideas as the earlier SR-IOV topic, with the extra step that the device is allocated by a device plugin [src: kubevirt-user-guide 7c0f6738bca538dd].

**Lifecycle.** The run strategy states the intent: always running, halted, manual control, restart on failure only, or run once. Start, stop and restart are operations on the VM object, with the virtctl client providing convenient commands, and a graceful stop sends an ACPI shutdown and waits for a grace period. Access to a console, a VNC display and an SSH tunnel is through virtctl and the API server, which means access control is Kubernetes access control: whoever may use the subresource may reach the console. Cloud-init and sysprep data are attached as volumes so the image pipeline from the previous topic applies unchanged [src: kubevirt-user-guide 1faf55596b8b8b5f] [src: kubevirt-user-guide 076da57c893ff3dd].

**Live migration.** A migration object (or the virtctl command) asks the system to move a running VM to another node. KubeVirt starts a target pod, the QEMU migration protocol copies memory while the VM runs, and the VM resumes on the target [src: kubevirt-user-guide b58e7cde3b6ea2f7]. Requirements follow from the earlier migration topic: shared storage that both nodes can access at once (a claim with a shared access mode, or a block-mode volume on shared storage), a network path with enough bandwidth, compatible CPU features between nodes, and no features that block migration such as passthrough of a PCI device or dedicated pinning settings that cannot be met on the target (to verify the current exclusion list). Migration also drives node maintenance: draining a node can trigger migration of the VMs on it, if the eviction strategy says so, and migration policies and bandwidth limits protect the cluster network. Status and cancellation are available through the API [src: kubevirt-user-guide 614d72225ae9bc6a].

**OpenShift Virtualization.** This is the product built from the upstream project and delivered as an operator on OpenShift, with a supported set of components, a web console with VM creation and migration views, templates for common guests, an operator-managed upgrade path and integration with the platform's storage, networking, monitoring and backup features [src: kubevirt-user-guide 2ace427c64e0562f]. Red Hat's documentation describes the same virtualization concepts as the Linux distribution documentation, because the engine is the same QEMU and libvirt [src: rhel-10-docs 9fde4e019813c153]. The product also provides a migration toolkit for moving VMs from other hypervisors, which is the next topic.

**Operations.** Treat the cluster like a virtualization host fleet. Plan node capacity in terms of VM memory, which is not overcommittable the way container memory sometimes is, plus per-VM overhead in the launcher pod. Set resource requests that match the guest, and use dedicated nodes (labels, taints) for VMs needing pinning or hugepages. Monitor VM metrics from the exported counters and from the guest agent. Back up the VM object and its volumes together, using snapshot and restore features and storage-level snapshots. Upgrade the operator and the cluster in an order the documentation prescribes, and test live migration before maintenance windows.

## Assessment: the good, the bad and the ugly

The good. One control plane, one API, one access model and one pipeline for containers and VMs. Declarative definitions in version control, reviewed like any other change. Re-use of the cluster's scheduler, secrets, network policy, observability and RBAC. A path for modernisation, where a VM and the containers around it live in the same namespace and talk through the same Services, and the VM can later be replaced by a container without the neighbours noticing. Instance types and DataVolume cloning make large fleets cheap to define.

The bad. The abstraction stack is deep: a problem may live in the guest, in QEMU, in libvirt, in the launcher pod, in the node agent, in the storage driver or in the network plug-in. The skills needed span virtualization and Kubernetes administration, and few teams have both. Storage is the hardest part: live migration needs shared storage with proper access modes; many clusters have storage built for stateless workloads. Network attachment for a VM that needs a real address on a VLAN demands extra components. Performance tuning is available but is scattered across the VM spec, node labels and host configuration. Some libvirt features lag, and features the earlier topics covered, such as device passthrough and confidential computing, have specific, version-dependent support (to verify for the release you run).

The ugly. A VM whose launcher pod is evicted or whose node fails, with a non-shared disk, loses its availability until storage is reattached. A cluster upgrade that drains nodes and migrates VMs, and a VM with a blocking feature that cannot be migrated, stalls the upgrade. Granting broad access to the VM subresources effectively grants console access to guests. A stateful VM treated like a disposable pod, deleted along with its namespace without its volumes protected. And an operator who assumes the pod's memory limit is a ceiling on the VM, when the guest's memory plus overhead is what the node has to supply.

## Applications beyond this domain

The pattern of extending the orchestrator with custom resources and controllers for a new kind of workload also underlies databases, message queues and machine learning pipelines on Kubernetes, and the design considerations are alike: the durable intent object, the instance object that comes and goes, the controller reconciling them, and the node agent doing privileged work. Unifying two inventories under one control plane is the same argument made for infrastructure as code across clouds. The "golden volume cloned per instance" pattern is the same as container image layers and as snapshot-based database branching. Treating console access as an API permission is the same lesson as exec access to pods, and the same audit and role design applies. Using live migration for planned maintenance links to rolling upgrades in other stateful systems.

## Examples

A minimal VM using an instance type, a preference and a data volume imported from an HTTP image (field names follow the current API, to verify against your version):

```yaml
kind: VirtualMachine
apiVersion: kubevirt.io/v1
metadata: {name: web1, namespace: demo}
spec:
  runStrategy: Always
  instancetype: {name: u1.medium}
  preference: {name: debian}
  dataVolumeTemplates:
  - metadata: {name: web1-root}
    spec:
      source: {http: {url: "https://images.example.org/debian-12.qcow2"}}
      storage: {resources: {requests: {storage: 20Gi}}}
  template:
    spec:
      domain: {devices: {}}
      volumes:
      - name: root
        dataVolume: {name: web1-root}
```

Operate it with the client:

```bash
virtctl start web1
virtctl console web1
virtctl migrate web1
kubectl get vmi,vmim
```

A diagnosis walk-through. A VM stays in the scheduling state. Describe the VMI and the launcher pod for events. The usual causes are no node with hardware virtualization or the needed label, insufficient memory for guest plus overhead, a volume that is not bound or still importing, or an affinity rule that cannot be met. Check the data volume phase before the VM, then the node resources and labels, then the taints.

A second example, workload fit. A team has an appliance VM, a Windows file server, three database VMs that rely on kernel parameters, and a hundred test VMs rebuilt nightly. The nightly test machines fit best, since they are cloned from a golden volume and disposable. The appliance fits if its network need can be met with a secondary network. The databases fit if the cluster provides shared, fast storage and pinning; otherwise leave them on the existing platform for now. The file server depends on storage and backup integration.

## Active research

Open areas include the memory and CPU overhead of the pod-plus-VM model and ways to reduce it; better scheduling for VMs, with awareness of NUMA, device topology and migration cost; storage designs that give VMs shared, snapshot-capable, high-performance volumes without a separate SAN; migration of VMs with passthrough or confidential features; and multi-cluster management with VMs moving between clusters. Security work looks at isolating the launcher pod's privileges, using user namespaces and hardened runtimes, and at confidential guests on Kubernetes, with attestation integrated into the cluster. Standardised, portable VM descriptions across KubeVirt and other platforms are also a topic of discussion (to verify current proposals).

## Future direction

Expect KubeVirt-based platforms to become a normal destination for enterprises leaving proprietary virtualization, with the product features (migration toolkits, templates, backup integration) maturing around the open core. The skills that matter are the combination of Kubernetes platform operation and hypervisor fundamentals. Teams should treat the first deployment as a storage and network design exercise, run a pilot with real workloads, test migration and failure modes before committing, and keep declarative definitions in version control so that they can move again.
