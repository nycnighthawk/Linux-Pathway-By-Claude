# Administering VirtualBox from the command line

## Define the problem

Most Linux administrators meet VirtualBox as a window: a manager, a wizard, a few clicks, a machine that boots. That picture hides the product's real shape. VirtualBox is a hypervisor with a stable programming interface, a set of background processes and a complete command-line client, and everything the window does is a call into that interface. The practical problem for an engineer is not making one VM but making the same VM repeatedly, on a build server with no screen, and being certain that last month's settings are what runs today.

Three gaps appear when people try. The first is reproducibility: a machine built by clicking has no record of what was chosen, and two colleagues clicking the same sequence still diverge on memory, storage controller type, network mode and firmware. The second is operation without a display: a CI runner or a rented server has no desktop, yet the guest must boot, be reachable, be inspected, be snapshotted and be thrown away. The third is the boundary between host and guest: shared folders, clipboard, time sync, graphics and guest-aware shutdown all depend on software running inside the guest, called Guest Additions, which has to match the host and survive guest kernel updates. Networking adds a fourth, because VirtualBox offers several modes that behave very differently, and the default one is the least useful for server work.

This slice teaches the administration surface: the object model behind the tool, creating and configuring a machine entirely with commands, running it headless, driving it from the host, choosing a network mode on purpose, and keeping Guest Additions healthy. It stays on Linux hosts and Linux guests. The next topic covers how VirtualBox sits next to KVM on the same machine, which changes several of these decisions.

## History and approaches

VirtualBox began as a product of a small German company and passed to Sun Microsystems in 2008 and then to Oracle in 2010 [web: virtualbox.org]. It was open-sourced under the GPL from the early days, with a separate Extension Pack under a different licence for features such as USB 2 and 3 support, remote display and disk encryption; that split has caused licence confusion in organisations that install both without reading the terms (to verify the current Extension Pack terms before any commercial use). In practice the split shaped the tooling too: the open-source edition is what Linux distributions package, while the pack is a manual download.

The first generation of administration was graphical, with a thin command-line tool added for scripting. As the product grew, the command-line tool became the complete interface and the window a client of the same service, so that anything one can click can also be commanded [src: virtualbox-docs 20896946c1bde86b]. Around it grew several approaches that people still use side by side.

The scripting approach calls VBoxManage directly from shell, accepting that the tool's output is text and that every option is a string. It is transparent and has no dependencies, and it is how most build scripts and teaching material work. Its weakness is that the script describes steps, not a desired state: running it twice creates a second machine or fails with a name clash.

The configuration-file approach hands the machine description to another tool. Vagrant, the best-known example, reads a Ruby file that names a base box and settings, and translates them into VirtualBox commands; the Rocky Linux project uses exactly this route to test its published images with BIOS, UEFI and Secure Boot variants [src: rocky-docs 8f2238523a81f1e8]. The box format is a packaged disk plus metadata, which makes sharing easy and makes the contents of a box a matter of trust in whoever built it.

The unattended-install approach, added to the command line in the 6.x series, lets VBoxManage detect an installation medium, generate an answer file for the guest installer, and run the whole install without a person at the console [src: virtualbox-docs 33a3d2da24c1bbd9]. This replaced a long tradition of hand-built kickstart or preseed files for the common distributions, at the price of less control over the answer file.

The management-layer approach puts VirtualBox behind a generic API. libvirt has long carried a VirtualBox driver, and a dedicated daemon exists for it in current releases, so that the same virsh and domain-XML workflow can address machines run by VirtualBox [src: libvirt-docs 404bd89fc2d03760] [src: libvirt-docs 7f6e91d75d0c0390]. Its documentation states a floor for supported versions, and the driver exposes only part of VirtualBox's feature set, so it is a convenience for mixed fleets, not a full replacement for the native tool.

Partial failures are instructive. Early scripts that assumed the GUI would be present failed in headless environments. Scripts that edited the machine definition file by hand ran into the rule that the service rewrites it. And whole teams lost days to Guest Additions that fell out of step with the host after a routine upgrade, because the guest kept running with a stale module until a graphical or clipboard feature broke. These are the failure modes the administration practice below is built to avoid.

## Current state

**The object model.** VirtualBox keeps a registry of machines, disks, DVD images and networks. Each machine has a name, a UUID, a settings file in a base folder and a state such as powered off, running, saved or aborted. Disk images are separate registered objects, so a disk can outlive a machine or be shared read-only by several. Commands refer to objects by name or UUID, which is why scripts should create machines with explicit names and register them in one step [src: virtualbox-docs 20896946c1bde86b]. The command-line tool talks to a service process; a graphical client and a web or API client talk to the same service.

**Creating a machine.** A scripted build has four stages. First create and register the machine with a name and OS type, which seeds sensible defaults for that guest family. Second adjust hardware with the modify command: memory, CPU count, firmware (BIOS or EFI), the chipset, the boot order, the graphics controller, and whether nested paging and I/O APIC are on [src: virtualbox-docs 4470be8b9eaff46c]. Third create a storage controller and attach media: a virtual disk created from nothing with a chosen format and size, and an optical image for the installer, using the storage commands [src: virtualbox-docs b2cbdb4ed36f3a6c]. Fourth set networking and boot. A good script ends with a dump of the resulting configuration so that a human or a test can compare it with expectation.

**Choosing a disk format and controller.** VirtualBox reads its own VDI format, VMDK and VHD, and with the right setting raw images. VDI is the native default and supports dynamic growth and snapshots. VMDK is the choice when the image must travel to other hypervisors. For the controller, the virtual SATA controller is the compatible default, an NVMe controller is available for guests that benefit from it, and a virtio-scsi controller exists in recent releases for guests with the driver (to verify availability on the version you run). The choice affects performance and which installer sees the disk without extra drivers.

**Headless operation.** The start command accepts a front-end type; the headless type runs the guest with no window at all and keeps it alive after the shell that launched it exits [src: virtualbox-docs 9044063f3f1e86a8]. That is the mode for servers and runners. Without a display, the console is reachable through a remote-display service if the extension is installed, through a serial port redirected to a file or a socket (which works without any extension), or simply through the network once the guest has an address. A serial console configured in both the machine settings and the guest kernel command line is the most dependable way to see early boot output when nothing else answers.

**Controlling a running machine.** The control command is the live remote: pause, resume, reset, power off, save state, send an ACPI power-button event for a polite shutdown, change a removable medium, attach or detach a network cable, and change some settings that are safe while running [src: virtualbox-docs b43291feeee58454]. A polite shutdown depends on the guest honouring ACPI events, which is one reason Guest Additions and a proper init system matter; a hard power-off is the fallback and can leave the guest file system dirty.

**Snapshots and clones.** A snapshot records disk and, optionally, memory and device state, and creates a differencing disk that holds changes from that point on [src: virtualbox-docs 4422173b64762e6e]. Restoring discards later changes. Chains of snapshots slow disk access and consume space, so they suit short experiments and not long-lived servers. A clone makes a new machine from an existing one; a full clone copies disks, a linked clone shares a parent snapshot and is fast and small but bound to its parent [src: virtualbox-docs b13c9b5be4740cb1]. Clones need new identities: a new MAC address policy decision, and inside the guest a new machine-id and host keys, or two machines will collide on the network and in logs.

**Import and export.** The export command writes a machine as an Open Virtualization Format appliance, a descriptor plus disks, optionally packed in a single archive; import reverses it [src: virtualbox-docs adb7ce325d7721d7]. This is the interchange route to other hypervisors, though device mappings differ and drivers may need attention in the target.

**Talking to the guest.** Two mechanisms let the host act without logging in over the network. The guest-property service stores key and value pairs that the guest can publish (its IP address, its Guest Additions version) and that the host can read or wait on [src: virtualbox-docs f1aff411f2c98795]. The guest-control service runs a program inside the guest, copies files in and out, and can trigger a Guest Additions update, all authenticated with a guest account [src: virtualbox-docs ec71282cc48313b1] [src: virtualbox-docs b4514c85e0812869]. Both need Guest Additions running in the guest. A script that boots a headless machine can wait on the property that publishes the address, then connect with ordinary SSH, which is more robust than polling a port.

**Guest Additions.** This is a set of drivers and services installed in the guest: a kernel module for shared folders and better video, a time-sync service, clipboard and drag-and-drop for graphical guests, and the services the property and control features use. On Linux the installer builds kernel modules against the running kernel, so the guest needs kernel headers and a compiler, and the build must be repeated after a kernel update; many distributions ship the guest side as a package that rebuilds through DKMS, which is the more maintainable path [src: rocky-docs 9bc1b323ed7f8d4a]. The versions need not be identical to the host but should be close, and a mismatch is the first thing to check when a feature stops working. Servers that need none of the graphics or clipboard features can run with only the minimum, or without the additions at the price of losing guest-aware shutdown and the property service.

**Networking modes.** The mode is chosen per virtual network adapter.

*NAT* gives the guest outbound access through the host's address with a private network behind it. Guests cannot be reached from outside unless ports are forwarded, which is a per-machine rule mapping a host port to a guest port. It is the default and is right for desktop-style guests that mostly call out. Several NAT guests cannot reach each other.

*NAT network* is the shared variant: several guests join one named private network with NAT to the outside, so they can talk to each other and still reach the internet, with forwarding rules defined on the network [src: virtualbox-docs e46f45d4f884673d]. It suits a small multi-node test bed that should not appear on the physical network.

*Bridged* attaches the guest to a host network interface so it gets an address on the real LAN. This is the mode for servers meant to be reached by others. Wireless interfaces and some network policies restrict it, and a bridged guest appears as another machine to the network team, which may be a policy matter.

*Host-only* creates a private network between the host and its guests, with a virtual interface on the host and an optional built-in DHCP server [src: virtualbox-docs 6f52be421c3b9191]. It is the usual way to give guests a stable address that the host can SSH to without exposing them. Combined with a second NAT adapter for outbound access, it is the most common two-adapter layout for a development guest.

*Internal network* connects guests to each other on a named switch with no host involvement, useful for isolating a lab. Generic and cloud-oriented modes exist for special cases.

On Linux hosts, VirtualBox needs its kernel modules loaded and, for bridged and host-only, network helpers with the privileges to create interfaces. Newer releases restrict which address ranges host-only networks may use through a configuration file, which surprises people who set a range outside the permitted one (to verify the range rule for your version).

**Host requirements.** The kernel module must be built for the running host kernel, which on a distribution with frequent kernel updates means DKMS or a repackaged module. Secure Boot hosts need the module signed, which is a common cause of "kernel driver not installed" errors after setup. Another hypervisor holding the hardware virtualization feature at the same time is the subject of the next topic.

## Assessment: the good, the bad and the ugly

The good first. The command line is complete, stable across many releases and scriptable without extra dependencies. The same tool works on every host operating system, so a script written on Linux runs on a developer's laptop elsewhere. The model of registered objects, differencing disks and clones is simple and well suited to disposable test machines. Unattended install makes a repeatable build possible with little ceremony. Headless mode and serial consoles make it viable on servers. For a developer who needs a desktop-like guest on a laptop, the mixture of NAT, host-only and shared folders is convenient in a way server-grade stacks are not.

The bad. Guest Additions are a recurring tax: a kernel module built per kernel, a version relationship with the host, and a failure that shows up as a missing feature and not as an error. VirtualBox's performance on I/O-heavy workloads generally trails a KVM guest with virtio devices (to verify with a benchmark on your hardware, since results vary by version and workload). Its virtualization of CPU features is narrower than KVM's, so features such as fine-grained CPU model control, NUMA topology, device passthrough and live migration are absent or limited. The licence split with the Extension Pack, and a different licence stance from the Linux virtualization stack, complicates use in some organisations. The libvirt driver covers only a slice of functionality.

The ugly. Scripts that parse human-readable output break when wording changes; the machine-readable output options exist and should be used. Editing a settings file while the service holds it open loses the edit or corrupts the registry. Snapshots used as backups grow without bound and then fail on merge when the disk is nearly full. Cloned machines that keep the same machine-id and SSH host keys silently break monitoring and trust. Bridged networking on wireless links fails in ways that look like a guest bug. And the "kernel driver not installed" state after a host kernel update, with Secure Boot on, can make a whole fleet of build runners unusable overnight.

## Applications beyond this domain

Several patterns carry over. The idea of a thin remote-control command on top of a long-running service is the same as libvirt with virsh, container engines with their client, and systemd with systemctl: the front-end is replaceable, the object model is the contract. Differencing disks that hold only changes appear in qcow2 backing chains, in container image layers, in copy-on-write file systems and in database write-ahead logs. The guest-property pattern, a small key-value channel the guest publishes into and the host waits on, matches cloud-init's phone-home, the QEMU guest agent and Kubernetes status conditions, and is the right way to avoid polling. A matrix of network modes by reachability (who can reach whom, in which direction) is the same decision that arises for container networking, for cloud VPC design and for lab firewalls. The Guest Additions version-skew problem is a general case of agent and driver compatibility between a host platform and software inside the guest, which also affects balloon drivers, VMware tools and hardware vendor agents.

## Examples

Create and start a headless Linux machine from nothing, assuming an installer image on disk:

```bash
VBoxManage createvm --name web1 --ostype Debian_64 --register
VBoxManage modifyvm web1 --memory 2048 --cpus 2 --ioapic on --nic1 nat --nic2 hostonly --hostonlyadapter2 vboxnet0
VBoxManage createmedium disk --filename ~/vm/web1.vdi --size 20480
VBoxManage storagectl web1 --name SATA --add sata
VBoxManage storageattach web1 --storagectl SATA --port 0 --device 0 --type hdd --medium ~/vm/web1.vdi
VBoxManage startvm web1 --type headless
```

Wait for the guest to publish its address, then connect:

```bash
VBoxManage guestproperty wait web1 /VirtualBox/GuestInfo/Net/1/V4/IP --timeout 120000
ssh admin@$(VBoxManage guestproperty get web1 /VirtualBox/GuestInfo/Net/1/V4/IP | awk '{print $2}')
```

Add a port-forwarding rule to a NAT adapter and snapshot before an upgrade:

```bash
VBoxManage modifyvm web1 --natpf1 "ssh,tcp,,2222,,22"
VBoxManage snapshot web1 take pre-upgrade --live
```

A diagnosis walk-through. A Linux guest has lost shared folders after a kernel update. First read the guest-property for the Guest Additions version to see whether the service runs at all. Then check that a module for the new kernel exists and that kernel headers are installed. If the guest uses DKMS, rebuild; if the additions were installed from the ISO, rerun the installer after installing build dependencies. Finally compare host and guest versions and update the guest through the control service if they have drifted.

A second example, networking choice. A three-node test cluster must reach the internet to pull packages, reach each other on fixed addresses, be reachable by SSH from the developer's laptop, and stay invisible to the office network. Use a NAT network for the nodes' outbound and mutual traffic, add a host-only adapter for the laptop's SSH, and give the host-only side a static assignment. Bridged would expose the nodes; plain NAT would isolate them from each other.

## Active research

Several directions are open. The ARM and Apple silicon support in recent releases changes where VirtualBox is used and which guests it can run, since x86 guests cannot be virtualized at full speed on ARM hosts; the maturity of that work is worth checking per release (to verify). The project's move toward a different, newer virtualization backend on some hosts is a live topic, in part because of the coexistence problems covered next. Security research on Guest Additions and on the shared-folder and graphics paths, which handle complex untrusted input, has repeatedly produced vulnerability reports, and a conservative operator treats the additions as part of the attack surface. Reproducible builds of guest images, with the Extension Pack excluded, are an open practical question for organisations that want a fully open toolchain. Finally, convergence on API-driven management (libvirt, Vagrant providers and cloud-style tooling) raises the question of how much native-tool knowledge remains necessary.

## Future direction

Expect the native command line to stay the stable base, since much automation depends on it, while higher-level tools hide it. The practical direction for server work is away from hand-run commands and toward declarative image and machine definitions, with VirtualBox used mostly for developer and test machines and KVM for production, though that is a judgement and not a fact about the roadmap (to verify against the project's current plans). Guest Additions are likely to keep shrinking in importance for server guests as more of the host-guest contract moves to standard channels such as virtio and the guest-agent protocol. A person who learns the object model and the network modes in this topic can move to any of those tools with little loss.
