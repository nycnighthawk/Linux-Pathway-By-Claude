# Tuning guests for predictable performance: NUMA, pinning, hugepages and I/O threads

## Define the problem

A default virtual machine runs well enough for most workloads and badly for a few. The ones that suffer share a trait: they are sensitive to latency and to memory locality. A database whose working set sits in a different NUMA node from the vCPUs that touch it pays a remote-access penalty on every cache miss. A low-latency trading or telecom application loses microseconds each time the host scheduler moves its vCPU thread to another core, or when an unrelated host process lands on the same hyperthread. A storage-heavy guest hits a ceiling because every disk request is processed by one thread in the hypervisor. A guest with a hundred gigabytes of RAM spends noticeable time in page table walks because the host maps its memory in 4 KiB pages.

The default scheduler treats a VM as a set of ordinary threads. A QEMU process has a thread per vCPU, one or more for I/O, one for the monitor and several helper threads, and the Linux scheduler places them where load balancing suggests. On a multi-socket server with several NUMA nodes and cache domains, that placement changes over time. Tuning means replacing the heuristic with a deliberate layout: which physical cores run which vCPUs, which NUMA node holds which guest memory, how the guest sees that topology, which threads handle disk and network I/O, and how memory is mapped.

This slice teaches the layout decisions and the libvirt and QEMU settings that implement them: reading the host topology, NUMA memory policy, vCPU pinning and emulator and IOThread placement, hugepages, CPU model and topology exposure, host kernel isolation for dedicated cores, and the choice and configuration of the guest disk bus (virtio-blk against virtio-scsi) with multiqueue and IOThreads. It stresses measurement, because tuning without a benchmark is guessing, and many well-meant settings lower throughput on workloads that did not need them. Hardware passthrough is covered in earlier slices and virtualisation features such as live migration in later ones.

## History and approaches

In the first years of KVM (2007 onwards) hosts were mostly single-socket or two-socket machines with uniform enough memory, and the Linux scheduler's behaviour was acceptable. As multi-socket servers with integrated memory controllers became standard (AMD Opteron from 2003, Intel Nehalem from 2008), each socket got its own local memory and the cost of a remote access rose to about 1.5 to 2 times the local latency, with lower bandwidth on the interconnect. Operating systems gained NUMA awareness: first-touch allocation, the numactl tool and later automatic NUMA balancing in the kernel (3.8 and after), which samples page accesses and migrates pages and tasks toward each other. Automatic balancing works for long-lived processes with stable access patterns and does poorly for large VMs, whose memory is allocated once and whose vCPUs the host sees only as threads.

Virtualisation stacks added manual controls. libvirt's numatune element sets a memory policy (strict, preferred, interleave) over a set of host nodes; cputune sets vCPU thread affinity to explicit host CPU lists, the emulator thread's affinity and IOThread affinity; the guest's own topology is declared with cpu topology and numa cells, so that a guest kernel can place its processes sensibly [src: libvirt-docs 6e29e3199db96971]. Upstream QEMU provides the same through -numa, -object memory-backend and -smp options. The Red Hat tuning guides describe the standard recipe, and Rocky Linux's guide walks through reading the topology with numactl and lscpu before pinning [src: rocky-docs 83e85f73b890763c] [src: rhel-10-docs f634c5d41eea595b].

Memory mapping has its own history. Transparent huge pages (THP), introduced in kernel 2.6.38, let the kernel back anonymous memory with 2 MiB pages automatically when alignment and availability allow, and for KVM they cut the cost of nested page table walks. Their drawback is background work: compaction and khugepaged scanning cause latency spikes, and fragmented hosts may not find contiguous memory. Explicit hugepages, reserved at boot or at runtime through hugetlbfs, give deterministic backing: 2 MiB pages, or 1 GiB pages on CPUs that support them (the pdpe1gb flag), which must usually be reserved at boot before memory fragments. A VM declares memory backing with hugepages in its XML, optionally per NUMA node, so that each guest node draws from the matching host node's pool.

Storage had parallel evolution. The first paravirtual disk, virtio-blk, presents each disk as a block device with a request queue; it is simple, very low overhead, and for years limited to a single queue processed by a single QEMU thread, which became the bottleneck as NVMe SSDs approached a million operations per second. Virtio-scsi, introduced in 2011, implements a SCSI host adapter on virtio, which brings standard features (many devices on one controller beyond the PCI slot limit, SCSI passthrough, persistent reservations, discard and write-same semantics) at the price of slightly more per-request overhead. The two later converged in capability: multiqueue support in both, with the number of queues set to the vCPU count so each vCPU submits on its own queue, and IOThreads, dedicated QEMU event-loop threads, so that disk processing runs outside the main loop and can be placed on chosen cores [src: qemu-docs 6b16e402ad00e246]. KubeVirt exposes both as disk buses, IOThreads as a policy, and NUMA and dedicated CPU placement through the CPU manager, with documented limits [src: kubevirt-user-guide 5b16ae51d41095cb] [src: kubevirt-user-guide a4a975f810cba97c].

Real-time and low-latency work added host-side isolation. The kernel boot parameters isolcpus, nohz_full and rcu_nocbs remove chosen cores from the general scheduler, stop the periodic tick when one task runs and offload RCU callbacks, so a pinned vCPU is not interrupted by housekeeping; tuned profiles (virtual-host, cpu-partitioning, realtime-virtual-host) package the settings. The KVM option to tell the guest its vCPUs have dedicated cores (kvm-hint-dedicated) changes how the guest idles, and halt polling in the host trades CPU time for wake-up latency.

The emerging pattern: describe the machine's topology to the guest honestly, bind guest resources to the host resources they should live on, keep housekeeping and I/O threads off the latency-critical cores, and verify with a benchmark that matches the workload.

## Current state

**Reading the host.** Start from facts: lscpu -e shows each logical CPU with its core, socket, NUMA node and cache IDs, so hyperthread siblings are visible as pairs. numactl --hardware lists nodes with their memory sizes, free memory and the distance matrix; numastat -c qemu-kvm shows how a running guest's memory is spread; virsh capabilities and virsh nodeinfo report the same through libvirt. A device also has locality: the NUMA node of a NIC or NVMe drive is in sysfs (numa_node), and a guest that does heavy I/O to it should run on that node. Without this information tuning is blind.

**Memory policy.** In the domain XML, numatune with memory mode strict and nodeset 1 makes all of the guest's memory come from node 1; allocation fails if the node lacks free memory, which is the correct behaviour when the layout matters. Preferred mode falls back silently, which hides problems; interleave spreads pages over nodes and suits guests larger than one node's memory. For guests spanning nodes, the guest topology declares NUMA cells with their memory and CPUs, and memnode elements bind each cell to a host node, so the guest kernel's NUMA balancer and allocator work with accurate distances.

**vCPU pinning.** The cputune element pins each vCPU to a host CPU (vcpupin vcpu='0' cpuset='12'), the emulator threads separately (emulatorpin) and IOThreads (iothreadpin). The common structure on a hyperthreaded host: take a set of whole cores on one NUMA node, give the guest the thread siblings together (so two guest vCPUs that are SMT siblings in the guest topology are siblings on the host, and the guest scheduler's SMT assumptions hold), and place emulator and I/O threads on separate cores or on the housekeeping cores outside the set. Avoid mixing pinned guests with unrelated host workloads on the same cores. Pinning removes migration overhead and cache thrash but also removes the scheduler's ability to balance, so one busy vCPU cannot borrow an idle core. A guest that does not use all its vCPUs wastes the pinned cores.

**CPU model and topology.** The cpu mode host-passthrough exposes the host's CPU model and features to the guest (best performance, but ties the guest to similar hosts for migration), while host-model gives a named model that libvirt expands on the host and keeps migratable within a family; custom models define a baseline across a cluster. The guest topology (sockets, dies, cores, threads) should reflect the real layout so that guest software sees correct cache sharing, and the cache element can pass through the host's cache information. Features such as invariant TSC, a stable clock source and the hypervisor hint flags matter for databases and trading systems.

**Hugepages.** Reserving hugepages is a host decision: at boot with hugepagesz and hugepages parameters, or at runtime through the sysfs files for each node (nr_hugepages in the node directory), which can fail if memory is fragmented. The guest declares memoryBacking hugepages, with per-node page sizes if desired, and optionally nosharepages and locked. Benefits are fewer TLB misses and cheaper nested page tables, typically a few per cent for memory-intensive workloads and more for very large guests; costs are that the memory is reserved and unusable by anything else, and that ballooning and overcommit no longer work for those guests. THP can be a middle path for guests that do not need deterministic behaviour, with the defrag setting chosen carefully.

**Host isolation.** Dedicated cores are produced with kernel parameters (isolcpus with domain,managed_irq flags, nohz_full, rcu_nocbs), IRQ affinity changes that keep device interrupts off those cores (irqbalance configured to ignore them, or manual smp_affinity), and tuned profiles that apply the set. Verify with measurements: a jitter test such as cyclictest in the guest, run for long enough to catch rare events, and perf or tracing on the host to see what interrupts the pinned cores.

**Disk buses and IOThreads.** The guest disk can be virtio-blk or virtio-scsi (or NVMe emulation, or an assigned NVMe device). Virtio-blk has the shortest path and the highest IOPS per CPU cycle for plain block devices; with the queues setting equal to the vCPU count and an IOThread assigned, it scales across vCPUs. Virtio-scsi is the choice when a guest needs many disks (a controller handles hundreds of targets, while each virtio-blk disk consumes a PCI slot), SCSI features (persistent reservations for clusters, UNMAP and WRITE SAME semantics, hot-plug of many devices), or consistent device naming; with multiqueue and an IOThread it comes within a few per cent of virtio-blk for most workloads. Cache mode none with aio native (or io_uring on modern kernels) avoids double caching in the host page cache and gives O_DIRECT semantics. Discard must be enabled end to end (guest filesystem, bus unmap option, image format, backing storage) for thin storage to reclaim space. An IOThread is an event loop with its own thread; the documentation explains why one loop for everything becomes the limit and how to spread devices across several [src: qemu-docs 6b16e402ad00e246]. In libvirt, the iothreads count and the iothread attribute on each disk driver assign them, and iothreadpin places them.

**Measure.** Benchmark before and after each change with the same workload. For CPU and memory: stream or the application's own test; for disk: fio with the real block size, queue depth and read-write mix, run in the guest against a file or device that matches production; for network and latency: sockperf or application latency histograms, watching tail percentiles (p99 and p999), not averages. Change one variable at a time and keep results with the exact XML.

**Generalised pattern.** Make locality explicit: map each resource class (CPU, memory, I/O) to a domain (core, node, thread), keep latency-critical work off shared or noisy resources, and prove each change with measurement.

## Assessment: the good, the bad and the ugly

The good: for the right workloads the gains are large and reproducible. Pinning with NUMA-local memory and hugepages typically brings a guest within a few per cent of bare metal for memory-bound work, and removes most latency outliers. Multiqueue virtio with IOThreads multiplies storage IOPS compared with a single-queue default. The knobs are well documented in libvirt and in distribution guides.

The bad: tuning has costs in flexibility and density. Pinned and hugepage-backed guests reserve resources, which lowers consolidation, disables overcommit and complicates scheduling in clusters (OpenStack needs flavor extra specs for pinning and NUMA, KubeVirt needs the static CPU manager policy and hugepage resources). Live migration of tuned guests requires the destination to have an identical layout, free dedicated cores and hugepages; tools can translate pinning on migration, but the plan must exist. Mistakes are silent: pinning two vCPUs to the same CPU, or placing the emulator thread on a vCPU's core, produces a slower VM with no error. Benchmarks on micro workloads mislead; a setting that raises one metric can hurt another.

The ugly: topology lies. A guest declares two NUMA nodes mapped to one host node, or a hyperthread layout that does not match the host, and its kernel makes decisions based on false distances. The host's own numbering of CPUs differs between machines and firmware versions (siblings can be adjacent or half the CPU count apart), so XML copied from another host pins the wrong cores. Features interact: automatic NUMA balancing on the host fights with manual placement unless disabled for the guest; THP compaction undermines latency goals; power management and frequency scaling (C-states, turbo) add jitter that no pinning can fix without firmware settings; SMT sibling noise from another tenant hurts both performance and, in security terms, exposes side channels, so cloud providers often give whole cores. Another trap is that the vCPU count and the I/O thread count compete with the host for cores, and a guest with sixteen busy vCPUs and four I/O threads on a twenty-core NUMA node leaves nothing for the host. And firmware or hypervisor updates change behaviour, so a tuned configuration needs a regression benchmark.

## Applications beyond this domain

The same locality principles apply to bare-metal servers (numactl and cgroup cpusets for databases, DPDK application placement with core masks and hugepages), to containers (the Kubernetes CPU manager and Topology Manager align CPU, memory and device allocations on one NUMA node), and to high-performance computing, where process placement and memory binding are fundamental. Real-time systems, game servers and audio production use isolated cores and reduced interrupts. Cloud instance families are defined by these properties: dedicated host and bare metal instance types, "dedicated CPU" plans with pinned vCPUs, and instances that expose the NUMA layout to the guest. Storage engines use the same multiqueue design in NVMe itself, which has per-CPU submission queues, and the virtio multiqueue approach mirrors it.

## Examples

**A database VM.** A server has two sockets of 16 cores with hyperthreading; node 1 has the NVMe drive. The administrator reserves 64 GiB of 1 GiB hugepages on node 1 at boot, isolates cores 16 to 31 on that node and their siblings with isolcpus and nohz_full, and defines a guest with 12 vCPUs (six cores, two threads each) pinned to six cores and their siblings, emulatorpin and iothreadpin to core 31, strict memory on node 1 with hugepages, host-passthrough CPU, and two NUMA-agnostic cells off. The disk is virtio-blk with queues set to 12 and one IOThread on the housekeeping core. A transaction benchmark shows throughput within 4 per cent of bare metal and p99 latency halved.

**Choosing a bus.** A file server VM needs to attach 40 data disks and use discard on thin-provisioned storage. Virtio-blk would need 40 PCI slots and extra bridges. The administrator uses one virtio-scsi controller with multiqueue and discard unmap, and measures a 3 per cent lower peak IOPS than virtio-blk on one disk, an acceptable price.

**A failing example.** A team copies pinning XML from a tuned host onto a new machine with a different CPU numbering. On the new host, CPUs 0 to 15 are the first threads of the cores and 16 to 31 are their siblings, but the XML pins vCPU pairs assuming adjacent siblings. The guest sees SMT siblings that are actually on different cores; its scheduler shares work badly, and the application runs 30 per cent slower than untuned. The error is found only by comparing lscpu output on both machines. They add a pre-flight script that validates pinning against the host topology.

## Related problems and ideas

Neighbouring problems: memory overcommit techniques (ballooning, KSM, free page reporting) that tuned guests give up; CPU frequency and C-state control; network tuning (multiqueue virtio-net, vhost threads, RSS and RPS), covered with networking; and cluster scheduling of pinned workloads, where Kubernetes' static CPU manager and Topology Manager do this for Pods and KubeVirt reuses it. Alternatives to manual pinning: automatic NUMA balancing for modest guests, cgroup cpusets managed by a systemd slice for groups of VMs, and cloud-style dedicated host or bare metal provisioning. Newer ideas: scheduler improvements for hybrid CPUs (performance and efficiency cores need explicit handling), CXL-attached memory tiers whose latency differs from local DRAM and appear as additional NUMA nodes, and io_uring passthrough and polling modes that reduce storage latency without dedicated threads.

## Active research

Open topics include hypervisor scheduling for noisy neighbours (core scheduling to restrict which tasks share hyperthreads, motivated by side-channel mitigation), memory tiering policy for guests with CXL and persistent memory, hugepage allocation under fragmentation (contiguous memory allocator work, folios and mTHP in the kernel that offer intermediate page sizes), NVMe virtualisation with direct queue assignment, and automatic tuners that learn a good layout from performance counters. Studies of virtual machine interference on shared caches and memory bandwidth (Intel RDT and AMD QoS allow partitioning) inform tenant isolation. Open questions: how much of the manual recipe a scheduler can learn, how to express intent ("latency sensitive") in a portable way across orchestrators, and how to keep tuned guests migratable.

## Future direction

Expect orchestrators to expose topology-aware placement as a first-class request, with libvirt and Kubernetes doing more of the translation between intent and pinning. Hardware trends (more NUMA domains per socket, chiplet designs with many L3 domains, hybrid cores, CXL memory) make careful layout more, not less, important. Virtio will keep adding queues and polling modes, and NVMe-style direct submission will blur the bus choice. Defaults such as multiqueue enabled automatically and IOThreads created per disk are already appearing in higher layers. Version-specific details (features of kernel multi-size THP, io_uring support in QEMU aio, virtio-blk multiqueue defaults, KubeVirt CPU manager requirements): to verify against current release documentation.
