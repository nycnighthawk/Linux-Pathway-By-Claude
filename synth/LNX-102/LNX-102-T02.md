# Running programs under control: processes, signals, priority and jobs

## Define the problem

A running system is a crowd of programs competing for a small number of processors, a fixed amount of memory and a shared terminal, and an administrator must be able to see that crowd, tell its members apart, ask them to stop, slow some down so others can finish, and clean up when they misbehave. The difficulty is that a program is not one thing. It is a process with an identity, a parent, a family of relatives that share a keyboard, a set of identities that decide what it may touch, and a priority that decides when it runs. Almost every day-to-day failure of a machine, from a hung job to a full process table, is a failure to understand one of those attributes.

Control also has to be asynchronous. A process cannot be consulted before it is interrupted, yet it must be given a chance to tidy up files and connections, so the system needs a message that arrives at an arbitrary moment and a convention for how the receiver responds. Equally, an administrator needs a way to make a job less aggressive without stopping it, because the batch run and the web server are both useful. The topic covers the vocabulary of processes, the signal mechanism, the priority scale, and the shell's job table that makes a terminal session manageable.

## History and approaches

The process model came from the earliest Unix: a new process is made by copying an existing one with fork and then replacing its program with an exec call. Every process has a parent that made it, and the identifier of that parent is preserved across the exec. This produces a tree rooted at the first process, and it gives rise to two classic pathologies. A child that ends before its parent reads the exit status becomes a zombie, an entry that holds only a status until the parent waits for it. A child whose parent ends first is adopted by the init process. Early systems relied on init to reap such orphans, and the reaping duty explains why a container's first process matters [src: rocky-docs 979e22fb2ca7e021].

Signals began as a crude way to kill a process and grew into a general notification system with a catalogue of numbered events. Each signal has a disposition that is one of default, ignore or catch; the default for each is one of terminate, ignore, terminate with a core dump, stop or continue. Different historic Unix families disagreed on numbering and on whether a handler stayed installed after delivery, which led to incompatible behaviour that the POSIX standard later tamed with the sigaction interface [src: man-pages b909e6bd7eefc020]. Real-time signals added queued, numbered, ordered delivery: Linux provides 33 of them numbered 32 to 64, but the threading library claims a couple, so programs must use the macro SIGRTMIN plus an offset and never a literal number [src: man-pages c8de9a163145c82e].

Job control arrived with the Berkeley systems, which let one terminal host several concurrent activities. The key idea was the process group and the session: processes in a pipeline form a group, the terminal has a foreground group, and only that group receives keyboard-generated signals and may read input. The shell keeps a table of jobs, one per pipeline, and offers commands to move jobs between foreground and background [src: man-pages d60f97413a9daae8]. Priority scheduling started with a single number per process, called niceness because a higher value means being nicer to others. Later kernels added scheduling classes for real-time work, with fixed priorities and, more recently, a deadline class with explicit budgets, and then control groups, which share processor time between groups of processes rather than between individual ones.

Not all of this worked well. The kill-by-number habit led to reuse hazards: a process identifier recycled between lookup and signal sends the message to a stranger, which motivated pidfd interfaces. Niceness proved a weak tool: it is only a hint to a fairness algorithm and does little for latency. Resource limits per process proved easy to circumvent by forking. These partial successes pushed administration toward service managers and control groups, which are the subject of later topics.

## Current state

Identity first. A process has a process identifier (PID), a parent identifier (PPID), a process group identifier and a session identifier. A child inherits the group and session of its parent, and all four survive an exec. Separately it carries credentials: a real, an effective and a saved-set user identifier, the same trio for groups, a list of supplementary groups, and a Linux-specific filesystem identifier used for file access checks. The setresuid and setresgid calls change all three at once, setgroups changes the list, and changes to the effective identifier are copied to the filesystem identifier automatically. Kernel-level threads each have their own credentials, but the thread library carries changes to all threads to meet the POSIX requirement [src: man-pages 3a684f09b4e16086] [src: man-pages 4cec4a0576e12462] [src: man-pages aff1d1fbb47dd7d6]. The effective identifier is what permission checks use, which is why a set-user-identifier program is dangerous: it starts with an effective identifier that differs from its real one.

To see processes, ps prints a snapshot, top and its relatives refresh continuously, and the /proc directory exposes one numbered subdirectory per process [src: rocky-docs 76786ad121fde5fb]. In ps output the state column uses single letters: R running or runnable, S interruptible sleep, D uninterruptible sleep (usually waiting on input or output and immune to signals), I an idle kernel thread, T stopped by a job-control signal, t stopped by a tracer, Z a zombie and X dead. In the BSD-style stat column extra characters appear: a less-than sign for high priority, N for low priority, L for locked pages, s for a session leader, l for multi-threaded and a plus sign for the foreground group [src: man-pages 65208f50d4d16c39]. The status file for each process also shows signal masks as bit fields named SigPnd and ShdPnd (pending for the thread and for the process), SigBlk (blocked), SigIgn (ignored) and SigCgt (caught) [src: man-pages 286db1d44b091b2b].

Signals are sent with kill, killall, pkill (which matches by name or attribute, as pgrep does) and from the keyboard. The kill command with no signal sends TERM, number 15, which a program may catch to clean up; KILL, number 9, cannot be caught or ignored and gives no chance to clean up, so it is a last resort [src: man-pages a70e52061b78e5c8]. The signals every administrator should know, with their numbers on the common x86 and Arm layouts, are HUP 1 (hang-up, conventionally "reload your configuration" for daemons), INT 2 (the interrupt from Ctrl-C), QUIT 3, KILL 9, USR1 10 and USR2 12 (application-defined), TERM 15, CHLD 17 (a child changed state), CONT 18, STOP 19 (cannot be caught) and TSTP 20 (the terminal stop from Ctrl-Z, which can be caught). The command kill -l prints the table for the machine in hand, which is worth doing because the numbering differs on some architectures. Signals are declared in the header signal.h, and the process-level handlers are installed with sigaction.

Job control sits on top. A command ending in an ampersand starts in the background; jobs lists the table with bracketed job numbers; Ctrl-Z stops the foreground job with TSTP; bg resumes it in the background and fg brings it forward; and a job is named with a percent sign and its number. Background processes are immune to keyboard signals and, if they try to read the terminal, are stopped. When the shell exits it normally sends hang-up to its jobs, which is why a long task should be started with nohup, within a terminal multiplexer, or as a service [src: man-pages d60f97413a9daae8].

Priority has two layers. The nice value ranges from -20, the highest priority, to 19, the lowest, with a default of 0 and values outside the range clamped. The system call setpriority takes a "which" argument (PRIO_PROCESS, PRIO_PGRP or PRIO_USER, declared in sys/resource.h), a "who" identifier and the new value, and by tradition only a privileged process may lower the number [src: man-pages 5e1ebae6f0241b91]. The command nice -n N prefix starts a program with N added to its niceness, defaulting to 10 if no number is given, and exits with 125, 126 or 127 to distinguish a failure of nice itself from a missing command [src: man-pages f5a2ad4e66a7b5da]. The command renice changes a running process: its options are -n for a relative change, --priority for an absolute value, and -p, -g and -u to interpret the following arguments as process identifiers, process groups or users [src: man-pages e7086b4fff22de69]. The sched family adds real-time classes chosen with chrt: SCHED_FIFO and SCHED_RR with fixed priorities, and SCHED_DEADLINE, configured through the sched_attr structure with fields sched_runtime, sched_deadline and sched_period in nanoseconds, with the kernel enforcing runtime no greater than deadline no greater than period [src: man-pages c14273e2d8611376]. Beyond niceness, control groups and the service manager's resource-control settings give each service a weighted share of the processor and hard memory caps, and the same mechanism backs container limits [src: docker-docs 42ef8fcc70affb95] [src: archwiki 3c48d097eda34f67].

## Assessment: the good, the bad and the ugly

The good is the economy of the model. Four numbers identify a process in its family, a table of a few dozen signals covers nearly every notification, and the same few commands work on every Linux machine. The TERM-then-KILL discipline lets well-written programs shut down cleanly and still gives the administrator a final answer. Because everything is visible under /proc, the tools are thin readers of kernel data, and scripts can do whatever the tools do.

The bad is that the abstractions leak. Niceness only shifts proportional weights between runnable tasks, so a nice 19 job can still make a machine sluggish if it saturates input and output or memory. A process in uninterruptible sleep ignores even KILL until the awaited operation returns, so some hangs cannot be cured by signals at all. Signal handlers have rules about what they may safely do, and many interrupted system calls fail with the error EINTR rather than restarting, a classic source of subtle bugs in programs and in shell scripts that run them [src: man-pages 572ac0b40a7f8509]. Process identifiers are reused, so a script that stores one and kills it later may hit the wrong target. Job control is a property of an interactive terminal, so it does not apply to scripts, cron jobs or services.

The ugly is the set of ways control turns into damage. Sending KILL to a database or a file-system worker risks corruption. Killing a parent can orphan children that continue to hold sockets and locks. A kill with a negative process number signals an entire process group, and a mistyped one can reach far more than intended. Running as the superuser makes every typo global. Fork bombs and runaway loops exhaust the process table, and without limits the administrator may be unable to start the shell needed to fix it. On a shared host the effective-versus-real identity distinction is also the foundation of a whole class of privilege-escalation bugs.

## Applications beyond this domain

Signals and process trees appear wherever programs are supervised. Container runtimes send TERM and then KILL to the first process of a container, so an image whose first process ignores TERM stops slowly, and the zombie problem moves inside the container when no process reaps orphans. Orchestrators implement graceful shutdown by combining a signal with a timeout. The Python standard library exposes the same identifiers and calls, with functions for waiting on children, forking, signalling and setting priority, and a resource module that exposes the per-process limits the kernel enforces [src: python-docs 0278856807427639] [src: python-docs 603379abda64ef86]. Language runtimes and threading libraries are built on the same primitives, and the low-level thread module shows how a thread differs from a process in sharing memory [src: python-docs 9c3a073319960044].

The scheduling ideas generalise too. Weighted fair sharing, reservations with budgets and priority classes appear in network traffic control, storage scheduling and cloud resource quotas. Capabilities, which divide root's power into separate pieces, are the same privilege-splitting idea applied to process credentials, and container runtimes drop most of them by default [src: docker-docs 6fb0eb5c4c14de04]. Even the interprocess communication mechanisms that processes use to cooperate, such as pipes, sockets and shared memory, extend the signal idea to carry data [src: debian-handbook 38ebd648c96e83f7].

## Examples

A first exercise reads a process fully. Pick a long-running process and gather its PID, PPID, group, session, state, niceness and signal masks with ps -o and with the status file. Then explain, from the numbers, which terminal controls it and what signals it would catch. This is a good way to learn that none of the fields are mysterious.

A second exercise is graceful and ungraceful termination. Start a small script that traps TERM and prints a message while removing a temporary file; send TERM and observe the cleanup; then start one that ignores TERM and see that only KILL ends it. Record exit statuses: a process ended by a signal reports a status of 128 plus the signal number in most shells.

A third exercise is job control at the keyboard. Start a long command, suspend it with Ctrl-Z, list jobs, send it to the background, bring a second job forward, and then close the terminal to see what hang-up does; repeat under nohup. The lab's frozen process, held with STOP and released with CONT, makes the same point without a terminal.

A fourth exercise measures priority. Run two identical processor-bound loops, one with nice -n 19, and compare their shares in top, then run them on separate cores and see that niceness no longer matters. Follow with renice -n 10 on the running pair.

A failing example is a zombie: write a parent that forks and never waits, see the Z in the state column and note that kill on a zombie does nothing; the fix is to signal or fix the parent. Another is the hung mount that leaves processes in D state: no signal helps until the device responds.

## Related problems and ideas

Neighbouring topics are the service manager, which supervises processes and cleans up their whole group, scheduled jobs, which run without a terminal, and resource accounting. Related ideas include process groups for killing a whole pipeline at once, subreapers and init-like supervisors that reap orphans, and per-user limits set in a limits configuration. The restriction on who may send signals is another neighbour: an unprivileged user may signal only processes with a matching real or effective user identifier, and capabilities can relax that. The sandboxing options of the service manager pursue the same goal at a larger scale [src: man-pages f0a7d26850475bfa].

Ideas for practice: send TERM first and wait, then KILL; use pgrep to preview what pkill would match; prefer a pidfile or a service manager to ad hoc lookups; run long tasks under a supervisor and not under an interactive job; start batch work with nice or ionice; and remember that the answer to a process that will not die is usually found in its state letter or its parent.

## Active research

Research and engineering here focus on making supervision safer and more precise. Process-descriptor interfaces, built around a file descriptor that stably refers to one process, remove the identifier-reuse race for signalling and waiting. The extended scheduler work replaced the older fairness algorithm with an earliest-eligible-deadline approach to improve latency, and pluggable schedulers written as eBPF programs are being explored so that policy can vary by workload. Pressure-stall information reports how much time tasks spend waiting for processor, memory or input and output, and user-space daemons use it to kill or throttle work before the machine thrashes. Research into energy-aware scheduling for heterogeneous processors and into core scheduling to prevent sibling-thread leaks also touches the subject.

## Future direction

Expect interactive process management to shift further from raw signals toward service-level operations, with the service manager owning the process tree and offering stop, restart and freeze verbs backed by control-group primitives. Descriptor-based process handles will gradually replace identifier-based signalling in libraries and tools. Scheduling will become more workload-aware, and priority will increasingly be expressed as service weights and latency targets rather than a niceness number. The vocabulary in this topic, parent, group, state, signal and priority, will survive because every one of these newer interfaces is a refinement of the same model, and the quickest way to diagnose a modern container or service problem is still to look at the process that is really running.
