# Tuning the running kernel: loadable modules, kernel parameters and what survives a reboot

## Define the problem

The kernel is the one program on a machine that cannot be restarted casually, yet it must adapt to hardware nobody knew about when it was built, to workloads with different needs, and to security policies that change. Two mechanisms make that possible. Loadable modules let code be added to or removed from a running kernel, so one generic image supports thousands of devices and file systems without carrying all the drivers in memory. Kernel parameters, exposed as tunable values, let an administrator change behaviour such as packet forwarding, memory pressure handling or log visibility while the system is up.

Both mechanisms raise the same administrative question: is a given change temporary or permanent? A value written into the live kernel takes effect at once and vanishes at the next boot; a value written to a configuration file takes effect at the next boot unless it is also applied now. Mistakes in either direction are common and costly. A fix applied only at runtime is forgotten at the next reboot, often at a bad hour, and a persistent change made without testing can leave a machine that does not boot or does not route. The topic covers how modules and parameters are inspected, changed and made permanent, and how to be sure which state a machine is really in.

## History and approaches

The earliest kernels were monolithic: every driver was compiled in, and changing hardware meant building a new kernel. That scaled poorly as the range of devices exploded. Loadable modules, introduced in the 1990s, allowed a driver to be built as a separate object file, inserted on demand and removed when unused. The first tools were primitive, with insmod to insert a file by path, rmmod to remove one, and lsmod to list them, none of which understood dependencies. A module that needed another had to be loaded manually after it, and the user had to know the order [src: man-pages 5927e9d38bf30b94] [src: man-pages cb5a47b35d957f0e].

The dependency problem led to a map and a smarter loader. The depmod program scans the module directory for the running kernel (under /lib/modules, in a directory named for the kernel release) and writes dependency and alias files; the modprobe program reads them, loads a module's dependencies first and applies local configuration. Kernel and user space cooperated on automatic loading: when a device appears, the kernel emits an event carrying an identifier such as a PCI or USB identifier, a user-space daemon looks it up in the alias table and loads the module. The modules-load documentation itself advises relying on this automatic loading instead of static lists, because most modern modules are prepared for it [src: man-pages 1643c7d207f99d89] [src: man-pages 6aa2b273f459d152].

Kernel parameters evolved separately. Early kernels were tuned by recompiling constants. Then a virtual file system, /proc, exposed values that could be read and written as files, and a subtree under /proc/sys became the standard place for tunables. A command and a configuration file, sysctl and sysctl.conf, applied settings at boot. Over time the single file became a set of drop-in directories read in a defined order, matching the other configuration systems that moved to the layered model [src: man-pages 7c24ad0cccec55b8].

Not everything worked. Unloading modules proved unreliable, since a module with live references cannot be removed and forcing it can crash the machine, so many drivers are simply never removed. Module parameters were originally passed on the command line or in a single configuration file, which became hard to maintain. Security concerns introduced signed modules and lockdown modes, partially breaking workflows that assumed arbitrary code could be inserted, and a switch that disables all further module loading until reboot. The archive of lessons is that modules are convenient but a security boundary: anything that can load one can run code in the kernel [src: archwiki d9f7e5219f10721e] [src: compliance-as-code a6bac1e481fdfe0f].

## Current state

A kernel module is an object file with the suffix .ko, often compressed (.ko.xz or .ko.zst), stored under /lib/modules/KERNEL-RELEASE/. Inside, it declares its identity with macros from the kernel header linux/module.h: MODULE_LICENSE, MODULE_AUTHOR, MODULE_DESCRIPTION, entry and exit functions registered with module_init and module_exit, and tunable parameters declared with module_param. Those declarations are what the inspection tools print. Module names have no extension, hyphens and underscores are interchangeable in every module command, and the file system representation of loaded modules is the list in /proc/modules and one directory per module under /sys/module, which holds the current values of parameters in a parameters subdirectory.

The inspection and control commands come from the kmod package. The command lsmod prints the loaded modules, their size and use count and the modules that depend on them [src: man-pages e3ad060560867dfd]. The command modinfo prints a module's declared fields: -F field selects one (author, description, license, parm, depends, alias, filename), -n shows the file name, -p the parameters, -k kernel gives information for a kernel other than the running one, and -0 separates values with a zero byte for scripts [src: man-pages 621c53900fb1d20a]. The command modprobe loads a module with its dependencies, and its options include -r to remove a module and unused dependencies, -a to load several, -n for a dry run, -v for verbose output, -c to print the effective configuration, -C to use another configuration directory, --show-depends to list what would be loaded, --first-time to fail if nothing needed to be done, and --ignore-install to bypass an install rule. Module parameters are given on the command line after the name as name=value pairs [src: man-pages 6336556ef56c4fa2]. For loading at runtime, the vendor manual stresses that these changes do not persist across a reboot and that active modules must not be unloaded, and that dependent modules must be removed first [src: rhel-10-docs 114b40897e645e95] [src: rhel-10-docs 3b8d535fd0458597].

Persistence for modules comes from three places. A file in /etc/modules-load.d with the suffix .conf lists module names, one per line, to load at boot through the systemd-modules-load service; comments start with a hash or a semicolon [src: man-pages 1643c7d207f99d89]. A file in /etc/modprobe.d with the suffix .conf holds directives that modprobe applies whenever it loads the module, by any trigger. The directives are alias (give a module another name, with wildcards allowed), options (module parameters, for example options bonding mode=802.3ad miimon=100), blacklist (ignore the module's internal aliases, so it is not loaded automatically by device matching, but an explicit modprobe still works), install (run a command in place of inserting the module, so install usb-storage /bin/false makes loading fail even when requested), remove (the same for unloading), and softdep (soft ordering constraints with pre and post lists). Files are read from /etc/modprobe.d, /run/modprobe.d, /usr/local/lib/modprobe.d and /usr/lib/modprobe.d in that order; once a given file name has been read, a namesake found in a later directory is skipped, and the full set is ordered alphabetically no matter where each file sits [src: man-pages dd5489ed983ce627] [src: man-pages 56853ed0660068cd]. The third place is the kernel command line, where module.parameter=value sets a parameter for a built-in or early-loaded module. A change that affects early boot also requires rebuilding the initial RAM image, since modules loaded there come from the image, not from /etc.

The parameters of the kernel itself are the files under /proc/sys, grouped by subsystem: kernel, vm (memory), net (networking), fs (file systems), dev and a few more. The key kernel.dmesg_restrict corresponds to /proc/sys/kernel/dmesg_restrict, and the separator in the name can be a dot or a slash. The command sysctl reads and writes them. Reading is sysctl key, or -a for everything, -n for the value only, -N for names only. Writing is sysctl -w key=value, which is runtime only. Loading from files is -p file (or the default /etc/sysctl.conf), and --system, which applies every system configuration file in the defined order; -e ignores unknown keys, -q is quiet and -r restricts to a pattern [src: man-pages cef3598d9d41f3b9]. Persistent settings live in files ending in .conf under /etc/sysctl.d, /run/sysctl.d, /usr/local/lib/sysctl.d and /usr/lib/sysctl.d, plus the legacy /etc/sysctl.conf. A file in /etc overrides one of the same name elsewhere, all files are sorted by name regardless of directory, and the last assignment of a key wins, so a name such as 99-local.conf applies after the vendor's 50-defaults.conf. The documentation recommends two-digit prefixes, the range 10 to 40 for vendor files in /usr and 60 to 90 for local files; a symlink to /dev/null in /etc masks a vendor file. Lines use key = value; a key may contain a glob, a leading minus on an assignment makes failures non-fatal, and an unknown key is logged at debug level and does not fail the service [src: man-pages e3520b3f6ad738fd] [src: man-pages 7c24ad0cccec55b8].

Some parameters exist only when a module is loaded. The bridge-netfilter keys under net.bridge appear only after the br_netfilter module is present, which is why container runtime setup guides tell administrators to load that module through a modules-load file and to set net.bridge.bridge-nf-call-iptables and net.ipv4.ip_forward through a sysctl file, and to verify with a read-back [src: kubernetes-docs 6df12801b90e30ae] [src: kubernetes-docs b42a32cc04a03541]. A related subtlety is that settings for per-interface keys under net.ipv4.conf are applied when the interface exists; a boot-time file may run before the interface appears, so baselines recommend re-applying network sysctls once the link comes up [src: compliance-as-code f5d6ae8e7e974fe7].

Verification is the last step of any change. After writing a file, apply it (sysctl --system or a restart of the corresponding service), read the value back, and, for anything that matters, reboot a test machine and read it again. For modules, modprobe the module, check lsmod and the parameter file under /sys/module, then confirm that the boot-time file lists it.

## Assessment: the good, the bad and the ugly

The good is the flexibility and transparency. One kernel image serves a vast range of hardware because the right module is loaded on demand. Parameters are plain files that can be inspected without special tools, changed immediately for experiments, and persisted with ordinary text files in layered directories. The introspection tools are consistent across distributions, and the same configuration mechanisms are used for services, which makes administration uniform.

The bad is that the same setting can come from several places and the order matters. A value set with sysctl -w is overwritten by a later file at the next apply; a file named too early loses to a vendor file with a later name; a module option in a modprobe file does not affect a module already loaded; a parameter for a module in the initial image needs the image rebuilt. The blacklist directive does not prevent loading by explicit request or as a dependency, a frequent surprise when hardening, whereas an install rule does. Hyphens and underscores are interchangeable in module names but not in the strings that appear in some logs, which complicates searches. Knowing whether a tunable is per-namespace matters in containers, where some keys are global and some are per network namespace.

The ugly is the combination of power and invisibility. A kernel module runs with full privilege, so loading an untrusted one is equivalent to giving away the machine, which is why signature enforcement, lockdown and modules_disabled exist. Forced removal of a module, or removal of one in use, can hang or crash the system. A wrong sysctl value can break networking or memory behaviour in subtle ways, for example disabling reverse-path filtering or enabling forwarding on a machine that should not route. A configuration that works because of an earlier manual change and is missing from the files fails only after the next reboot, usually discovered by someone else. Mistyped keys in a file are silently skipped.

## Applications beyond this domain

Containers and orchestration depend on exactly these mechanisms. Runtimes need packet forwarding and bridge filtering enabled, specific modules loaded for overlay storage and network drivers, and some sysctls allowed per pod while others are unsafe because they are global; the platform documents which sysctls it can set per pod and which need node-level configuration [src: kubernetes-docs e717e78fd2b503ab] [src: kubernetes-docs a702dadcbbd9f160]. Container engines tell administrators where a daemon fails to start because a module or sysctl is missing, and the same checks appear in networking troubleshooting guides [src: docker-docs cf4f92da7ffbea66] [src: docker-docs 2bdedc76f2aca3c9].

Security hardening uses the same levers. Baselines disable the unprivileged use of the eBPF syscall, enable reverse-path filtering, and prohibit loading modules for rarely used protocols; those are all sysctl and modprobe settings, and scanners check both the file and the live value [src: compliance-as-code dc5b2c01f0307def] [src: compliance-as-code 383a0488a06cc878]. Syscall filtering for containers has a parallel in the list of calls blocked by default [src: docker-docs b6a7b2e8af2d69d4]. In embedded work, module and parameter configuration is part of image building, and some systems carry a unit-level equivalent: the service manager's sandboxing options restrict the kernel interfaces a single service may touch [src: man-pages f0a7d26850475bfa].

## Examples

A first exercise is the module life cycle on a test machine. List modules, pick a small unused one, show its details with modinfo, load it with a parameter, confirm the parameter in /sys/module, remove it, and then ask modprobe to show its dependencies. Repeat with a module that has a dependent to see the refusal.

A second exercise is a persistent kernel parameter. Read the current value of vm.swappiness, change it with sysctl -w and read it back, then write a drop-in with a high prefix, apply with sysctl --system, reboot, and compare. Do the same for a value set at runtime and left out of the files, and show that it reverts. The lab for this topic builds the files in a scratch root and validates the key names against the running kernel.

A third exercise is blocking a module. Add a blacklist line and observe that automatic loading is prevented but modprobe name still loads it; then add an install rule that runs /bin/false and see that explicit loading fails too. Rebuild the initial image if the module is loaded early, and check.

A fourth exercise is the container prerequisite: load br_netfilter by a modules-load file, set the three keys by a sysctl file, and confirm at boot.

A failing example is a sysctl file whose name sorts before a vendor file that sets the same key, so the vendor value wins. Another is a bonding option placed in a file after the module was loaded. A third is a typo in a key name that is silently ignored.

## Related problems and ideas

Neighbouring topics are the boot process and initial image, which load early modules and carry their configuration; tuned profiles, which apply bundles of sysctl and other settings; security modules and mandatory access control; kernel updates, which require modules rebuilt for the new release (out-of-tree drivers managed by a dynamic framework); and secure boot, which requires signed modules and may require enrolling a key. Related are device events and rules in user space, which decide what gets loaded.

Ideas for practice: prefer automatic loading and use static lists only when needed; keep local settings in numbered files in /etc, never edit vendor files; use install rules, not blacklists, to truly forbid a module; always verify after applying and after a reboot; record each change with a comment saying why; keep a test machine for reboot checks; and keep sysctl files small and topic-based so that diffs are readable.

## Active research

Work in this area targets safety and observability. Module signing and kernel lockdown are being extended so that policies cover not only module loading but also other ways of reaching kernel memory. Live patching applies fixes to a running kernel without a reboot. Programmable kernel extensions through eBPF are replacing some modules for tracing, networking and scheduling, with verifiers that prove programs safe before they run. Research on configuration drift tracks what differs between the runtime and file state and suggests remedies, and on kernel configuration fuzzing finds parameters whose interactions fail. Per-namespace tunables continue to expand so that containers can be tuned without affecting the host.

## Future direction

Expect modules to be loaded more selectively, signed and verified by default, and the set of tunables a container can change on its own to grow. More behaviour will move from modules to safely sandboxed programs loaded through eBPF. Configuration will be generated and verified from declarative profiles, with tools that diff live state against the files and fail a build on drift. The runtime-versus-persistent distinction will not go away, since the kernel will always have a live state and a boot state, so the habit of changing, applying, reading back and rebooting a test machine stays valuable.
