# Where the operating system cannot help: firmware menus, consoles and the first minutes of a machine

## Define the problem

Some administration happens before the operating system exists or after it has stopped answering. The tools in the rest of this course all assume a shell, a network and a running service manager. A new machine has none of them. It has a firmware program in flash memory, a keyboard and screen (or a serial line, or a management controller), and whatever the firmware's authors decided to offer. A damaged machine may be in the same position, with a kernel that will not start and a network that is not configured.

The practical problems are specific. How do you get into the firmware menu to change the boot order, enable virtualisation extensions, set a boot password or turn secure boot on or off? How do you choose a boot device or a one-time boot entry without changing the default? How do you see boot messages and interact with a boot loader on a server that has no monitor, through a serial console, a management controller or a hypervisor's console? How do you set the keyboard layout so that the characters you type at a rescue prompt are the ones you intended? And how do you do all of this on a virtual machine, where the firmware and console are emulated and reached through the hypervisor instead of through physical keys? This topic is a short orientation to those places, so that the administrator is not helpless at the console.

## History and approaches

Firmware on personal computers began as the BIOS, a small program in read-only memory that tested hardware, offered a setup screen reached by a vendor-specific key at power-on (commonly Delete, F2, F10 or Escape) and loaded the first sector of a chosen disk. Setup screens varied wildly between makers, and the only common interface was a text-mode screen and a keyboard. Server vendors added remote management controllers, small computers on the motherboard with their own network port that expose the console, power control and virtual media over the network, in vendor-specific dialects and later through standard protocols.

The unified extensible firmware interface replaced the BIOS. It defines boot entries stored in non-volatile variables, a standard system partition, a shell, and optional secure boot that checks signatures before running loaders. It also made the firmware's choices visible to the operating system, which can list and edit boot entries, set the next boot only, or ask the firmware to enter its setup interface on the next restart. Boot managers took advantage of this: one popular small manager stores one file per entry in the system partition, reports its choices through the same variables, and integrates with the service manager's reboot command [src: archwiki bad20d9e4f4c7c6b] [src: man-pages 6d66fd03847d8711].

Consoles changed along the way. The first consoles were physical terminals on serial lines, which is why the kernel's console= argument still names serial devices such as ttyS0, with a speed and format like 115200n8. Graphical screens and virtual terminals followed, each switchable with a key chord, and then the virtual machine era restored the serial console in emulated form because it is easy to capture and script. Installation programs reflect this history: a graphical installer also offers text virtual consoles on other terminals, reached with Ctrl-Alt-F2 and friends, from which an experienced administrator can run commands during an install or an image deployment [src: rhel-10-docs 158cd74429990205].

The partial successes are instructive. UEFI standardised boot entries but not the setup interface, so vendors still differ in menus and key names. Secure boot raised the bar against tampering but complicated the use of third-party and custom kernels and modules. Management controllers made servers remotely operable but became attack targets, and their default credentials are a perennial incident cause. Installing a second operating system on the same machine often overwrote the boot loader, a failure the installation manual warns about, and recovering from it means booting rescue media and reinstalling the loader [src: debian-handbook fa0c756849c9cec1].

## Current state

To reach the firmware setup on a physical machine, you press the vendor's key during the first seconds after power-on, which is shown on the splash screen or in the manual. On a machine already running a UEFI system with the service manager, there is a more reliable route that does not depend on timing: systemctl reboot --firmware-setup restarts straight into the firmware interface, and systemctl reboot --boot-loader-entry=NAME restarts into a chosen boot loader entry once, leaving the default for later boots, with --boot-loader-entry=help listing the choices [src: archwiki bad20d9e4f4c7c6b]. The boot manager's own control command, bootctl, reports whether the machine is booted by UEFI and in which mode secure boot is, lists the entries and the firmware's boot variables, and installs or updates the manager. On any system, the existence of the directory /sys/firmware/efi tells you immediately whether the running system was started by UEFI or by legacy BIOS, and tools such as efibootmgr list and reorder the firmware's entries, and mokutil --sb-state reports secure boot.

What is configured in firmware, and why it matters to an administrator: the boot order and the one-time boot menu, which decide whether the machine starts from disk, network or removable media; virtualisation extensions for the processor, which must be on for hypervisors; secure boot and its key databases; the boot password and setup password; the power policy after a power loss; the serial console redirection, which sends firmware screens to a serial port; the clock; and, on servers, the settings of the management controller such as its network address and users. Changes are saved on exit and persist in non-volatile storage. A battery-backed or flash-stored setting survives power loss; if the settings battery fails the machine may forget them, one cause of a machine that suddenly boots from the wrong device and has the wrong date.

The boot manager's configuration is also console-related. In the small manager the file loader.conf sets the default entry (by glob on the entry file name, or @saved to remember the last choice in a firmware variable), the menu timeout, and whether to edit entries from the menu; automatically detected entries have fixed names such as the firmware's default loader, the EFI shell or another operating system [src: man-pages 6d66fd03847d8711]. Installing it after having booted in legacy mode is possible but requires telling the firmware to launch its file by path, either from a firmware shell or from the firmware setup, and some firmware falls back to the standard removable-media path if no entry exists [src: archwiki 585cd4872b9b8bf2].

The virtual console and keyboard come next. The kernel console is selected by one or more console= arguments on the kernel command line; the last one listed is where the primary messages and the rescue shell appear, and a serial argument looks like console=ttyS0,115200n8. The service manager's console setup service reads /etc/vconsole.conf for the keymap (KEYMAP=) and font, and as a last-priority fallback uses the keyboard layout reported by the boot loader from the firmware, matched by language tag against a table, with credentials, the configuration file and the kernel command line all overriding it [src: man-pages b59713e9ee37bc91]. The command localectl shows and sets the system locale and the keyboard mapping (set-keymap with a name such as us or de), and by default also converts the setting for the graphical server [src: man-pages ab05fe2f35aaec04]. On a text console, the usual virtual terminal switch is Ctrl-Alt with F1 to F6, and the debug shell the service manager can add appears on terminal 9.

For machines without a screen the options are the serial console, the management controller's remote console and, in virtual machines, the hypervisor's console. A serial console needs the firmware redirection setting, the console= argument for both loader and kernel, and a login service on the serial device; most distributions start one automatically when the argument is present. A management controller offers a network-reachable console, power on, power off and reset, and virtual media to attach an installation image, which is how a remote server is rebuilt. Hypervisors offer the same ideas: libvirt describes consoles and devices in its domain XML, and a virtual machine's firmware can be chosen between BIOS and UEFI per machine; some platforms can boot a guest directly from a kernel and initial RAM image supplied externally, with kernel arguments such as console=ttyS0 set in the machine definition, bypassing the guest's firmware and loader altogether [src: libvirt-docs 84f2163e2552b83a] [src: kubevirt-user-guide 2307b4a7478d96ec].

Physical access is also a security fact. Anyone at the console can boot other media, edit boot arguments or reset passwords unless firmware and loader passwords, disk encryption and secure boot are configured. The security guidance treats the console as part of the trust boundary: the point of requiring authentication for rescue shells and a loader password is to stop an attacker with the keyboard from walking in [src: disa-stig f84aeaec1b7d74b8] [src: ms-learn-adds e428de09d3cc3bd6].

## Assessment: the good, the bad and the ugly

The good is that a few mechanisms cover nearly everything. The one-time boot option, the firmware-setup reboot, the serial console, and the loader entry editor are enough to recover or rebuild a machine, and the operating system now exposes enough of the firmware's state that most of it can be inspected and scripted from a running shell. Virtual machines make the whole area safe to practise, since the console is a window and a mistake costs a snapshot.

The bad is the diversity and the lack of documentation at the moment you need it. The firmware key differs by vendor and model, menus differ in structure and wording, and some are hard to reach if the boot is fast or if a keyboard driver loads late. Settings that should be uniform, like the boot order, are interpreted differently. The console setup also splits across three places (firmware, loader and kernel), and a mismatch in speed or device produces a silent screen that looks like a hang.

The ugly is the combination of power and weak defaults. A firmware setup with no password lets anyone reorder the boot or disable secure boot. A management controller left on default credentials gives remote hardware-level control. Firmware updates can brick a machine if interrupted, and firmware bugs are patched slowly, if at all. A wrong change to boot variables can leave a machine unable to boot until it is reset from the setup screen. And a keyboard layout that differs between the firmware, the loader and the running system causes password prompts that cannot be typed correctly, a surprisingly common reason for a "lost" password.

## Applications beyond this domain

Out-of-band management and boot automation reach well beyond Linux. Data centre provisioning uses network boot and virtual media to install operating systems on bare metal at scale, with the management controller as the lever. Cloud providers expose serial console output and an interactive serial console as a first-class tool for diagnosing instances that fail to boot or to bring up networking. Image-based deployment onto bare metal from a boot environment, using a console to run the commands, is documented by vendors as a standard route [src: rhel-10-docs 158cd74429990205]. Embedded and single-board computers rely on serial consoles and boot-loader prompts as their main interface, and the same console= conventions apply.

Containers and virtual machines borrow the vocabulary of firmware: virtual machine definitions pick firmware type, boot order and console devices, and direct kernel boot skips firmware altogether. Security standards use the same ideas of a trusted boot path, signed firmware and physical-access controls, and the supply chain controls that cover firmware are part of that reasoning [src: nist-sp800-53 f09804ed00ebcf00].

## Examples

A first exercise is an inventory on a test machine or virtual machine. Determine whether it booted by UEFI, list the firmware's boot entries and secure boot state, print the kernel command line and the console devices, and read the keyboard and locale settings. Write each in a short report.

A second exercise is to enter the firmware setup deliberately: on a virtual machine, reboot using the firmware-setup option, find the boot order and secure boot pages, change the order, boot, and change it back. Note which key the virtual firmware advertises.

A third exercise is a one-time boot into a different entry: use the reboot command's entry option, confirm in the command line that the entry ran, and reboot again to show that the default is unchanged.

A fourth exercise is to set up a serial console: add a console argument for a serial device to the kernel command line, attach to the virtual machine's serial console from the host, and confirm that the boot messages and a login prompt appear there. Then break it on purpose with the wrong speed and recognise the symptom.

A failing example is a loader overwritten by the installation of another operating system, recovered with rescue media. Another is a keyboard layout mismatch that makes a correct password fail at the rescue prompt, solved by setting the keymap persistently with localectl.

## Related problems and ideas

Neighbouring topics are the boot chain and rescue modes, which begin where firmware ends; time, which is stored in the hardware clock firmware maintains; storage layout, in particular the system partition; and remote management and provisioning. Related problems include firmware update management, trusted boot and measured boot, and serial-over-network access to many consoles at once. Another is the physical security of racks and consoles.

Ideas for practice: record the setup key and the management address for each machine class; set firmware and loader passwords where physical access is possible; keep default credentials off management controllers and isolate their network; configure the serial console consistently in firmware, loader and kernel; set the keymap persistently; keep rescue media and a documented recovery procedure; use the one-time boot options instead of changing defaults; and practise on virtual machines before a real outage.

## Active research

Work here concerns trust and manageability. Open firmware projects and measured boot make the firmware itself auditable and attestable. Standard interfaces for out-of-band management, with secure defaults, aim to replace the vendor dialects. Research on firmware supply chains, on update mechanisms that cannot brick a device, and on confidential computing, where the firmware and loader are part of a measured chain that a remote party can verify, is active. Boot-time hardening, including signed unified images that remove the editable command line, reduces what a console attacker can do.

## Future direction

Expect the console to matter less for routine work and more for recovery, as fleets are rebuilt from images over the network and managed through attested, standardised controllers. Firmware settings will increasingly be read and set from the running system through standard interfaces, and the physical keyboard will be used mainly for first setup and emergencies. Virtual and cloud consoles will remain the practical tool for diagnosing boot failures. The orientation in this topic, knowing where the firmware setup is, how to boot something else once, how a console is selected, and how to keep the console secure, remains the safety net for everything else in the course.
