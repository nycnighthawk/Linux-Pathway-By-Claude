# From power switch to login prompt: the boot chain, the boot loader, rescue modes and regaining root

## Define the problem

When a computer powers on it contains nothing but firmware, and the operating system sits unmounted on a disk the firmware cannot interpret. Something must therefore find a kernel, load it into memory together with whatever drivers are needed to reach the real root file system, hand over control, and then bring up the services of a running system, all with no help from the operating system that is not yet there. Each link in that chain knows only a little about the next one, so each is a place where a machine can fail to boot, and when it does fail the usual tools are unavailable.

An administrator needs the boot process for three reasons. To change how a machine starts: add a kernel argument, pick a different kernel, choose a different target state. To repair a machine that will not start: a bad line in the mount table, a damaged initial image, a broken service blocking the boot. And to recover a machine whose credentials are lost, which means understanding how someone with the console can get root, and therefore how to prevent that for machines where physical access cannot be trusted. The same knowledge answers the security question, because anyone who controls the boot arguments can bypass the login system entirely.

## History and approaches

The PC boot sequence began with the BIOS, which loaded a single sector from the first disk. That sector held a tiny loader with no room for file-system code, so loaders became chains: a first stage in the master boot record that found a second stage, which knew enough about the file system to read a configuration file and a kernel. Early Linux loaders stored the physical disk location of the kernel and had to be rerun after every kernel update, a fragile arrangement that forgot nothing and forgave nothing. GRUB, the Grand Unified Bootloader, replaced this with a loader that understood file systems and read a text menu, so a kernel could be chosen interactively [src: rocky-docs 7e0d934eba9cfd98].

Firmware then changed. UEFI replaced the single sector with a firmware that reads a partition table and runs programs from a dedicated system partition, and it added secure boot, which allows only signed loaders to run. The loader became an ordinary program, and alternatives with simpler designs appeared that use the firmware's own file access instead of their own, and keep their configuration in small per-entry files [src: archwiki ed675993c502bb14] [src: man-pages 6d66fd03847d8711]. The second generation of GRUB, GRUB 2, was a rewrite with a modular design and a generated configuration, and it is the default on most mainstream distributions.

The kernel's own problem was drivers. The disk holding the root file system might need a module that lives on the root file system. The solution was an initial RAM disk: a small archive loaded alongside the kernel that contains just enough tools and modules to find and mount the real root. Early ones were block images; the current form is a compressed cpio archive unpacked into an in-memory file system, which is why it is called initramfs. It may itself run the service manager to manage early services, and it hands over to the real manager once the root is mounted. On shutdown a mirror image can come back to unmount the root last [src: man-pages 4db1cb1748689b53].

Approaches to recovery changed with the init system. Under the old model, passing a single-user flag on the kernel line gave a root shell at once. Under the service manager the equivalent became boot targets that stop at different points, with the emergency one reaching a shell earlier than the rescue one, and a kernel argument to choose the target. Where even that fails, the last resort is replacing the init program with a shell. The partial success of all of this was security: the same arguments that save an administrator let any attacker with the console reset the root password unless the loader or the target requires authentication.

## Current state

The boot chain on a modern machine runs in stages. Firmware initialises hardware and finds a boot target: on UEFI it runs a program from the EFI system partition, on legacy BIOS it runs the first sector. The loader presents a menu, loads the chosen kernel image (the compressed vmlinuz in /boot) and the initramfs into memory and passes a command line. The kernel initialises, unpacks the initramfs and runs its init, which locates and mounts the real root file system, then switches into it and executes the system manager as the first process. The manager reads its default target and starts the units that target pulls in. A single page of the manual describes this handover and the exit path in detail [src: man-pages 4db1cb1748689b53].

GRUB 2 keeps its settings in two places that administrators must not confuse. The file /etc/default/grub holds shell-style variables such as GRUB_TIMEOUT, GRUB_DEFAULT (often saved, meaning use the stored choice), GRUB_CMDLINE_LINUX (arguments added to every entry), GRUB_DISABLE_RECOVERY and GRUB_TERMINAL_OUTPUT. The generated grub.cfg, found at /boot/grub2/grub.cfg on Red Hat-family systems and /boot/grub/grub.cfg on Debian-family ones, must not be edited by hand, since it is rebuilt from the defaults and scripts. After changing a variable the administrator regenerates it, with grub2-mkconfig -o /boot/grub2/grub.cfg on the Red Hat family or update-grub on the Debian family [src: rocky-docs 7e0d934eba9cfd98]. Red Hat-family systems with the Boot Loader Specification keep one small file per kernel under /boot/loader/entries, and tools such as grubby change the arguments of one or all entries; the saved default is stored in an environment block manipulated by grub2-editenv and grub2-set-default. On UEFI systems a stub configuration under /boot/efi redirects to the main one. The compliance baselines require that grub.cfg be owned by root and, on high-assurance systems, that the loader itself require a superuser password [src: disa-stig 2f9fe3741d4b1526] [src: compliance-as-code 65c5e4dee052643d] [src: compliance-as-code 9aa3b7038e537ec8].

The kernel command line is a plain list of words, and many are read by systemd rather than the kernel. The most useful: systemd.unit= and rd.systemd.unit= to choose the target (for example rescue.target or multi-user.target) for the real system or the initramfs, systemd.debug_shell and systemd.default_debug_tty= to add a root shell on a console, systemd.mask= and systemd.wants= to mask or add units for one boot, systemd.show_status= and systemd.log_level= and systemd.log_target= for diagnostics, systemd.confirm_spawn to ask before each service, systemd.break= and rd.systemd.break= to pause at a named point and spawn a shell, and systemd.run= to run a command at boot. The kernel itself reads root=, ro and rw, console=, quiet, and others documented in its parameters list [src: man-pages 35849e506f83f23c]. In the menu, pressing e edits the current entry for one boot, the linux line is the one to change, and Ctrl-X or F10 boots the edited entry.

The boot-state targets differ by how much of the system they start. basic.target is the synchronisation point after early services: local file systems, swap, sockets and timers. rescue.target (single-user mode) starts basic.target and a root shell through the rescue.service unit with most local file systems mounted. emergency.target starts almost nothing: the root file system, usually mounted read-only, and a shell. multi-user.target is the full text-mode system and graphical.target adds a display manager; the default target is a symlink at /etc/systemd/system/default.target, set with systemctl set-default and queried with get-default. From a running system systemctl isolate rescue.target switches target in place, and systemctl rescue and systemctl emergency do the same with a wall message. The unit special.target documentation lists these and explains that basic.target is the synchronisation point for late boot [src: man-pages 995fc6d090fa1524] [src: rocky-docs facde96886055010] [src: archwiki a37456983366c10b].

Rescue shells require authentication, usually through the helper systemd-sulogin-shell, which asks for the root password. The compliance rule for RHEL checks that the rescue and emergency unit files contain an ExecStart line invoking that helper, either in the vendor unit or in a drop-in directory under /etc/systemd/system/rescue.service.d, but not in both [src: disa-stig f84aeaec1b7d74b8] [src: disa-stig c376139108447f61] [src: compliance-as-code 854ee20e5053d806]. This is exactly the setting that protects the machine from a console attacker who adds the rescue argument, and it is why a locked root account with no password makes rescue mode unusable until the setting is changed.

Resetting a lost root password on the Red Hat family follows a fixed sequence. At the menu press e, append rd.break to the linux line, and boot with Ctrl-X. The initramfs stops before switching root, with the real root mounted read-only at /sysroot. Remount it writable with mount -o remount,rw /sysroot, enter it with chroot /sysroot, set the password with passwd, and, because SELinux must relabel the changed shadow file, create the marker file with touch /.autorelabel, then exit twice to continue the boot. On a Debian-family system the equivalent is replacing the init program with init=/bin/bash on the kernel line, remounting root writable and running passwd. When the machine is encrypted the passphrase prompt comes first. These steps are the standard exam task and the standard emergency, and they work only because the console is trusted [src: archwiki 6a090b5885923e7d].

Keeping the initial image current is part of maintenance. On Red Hat-family systems the dracut command builds an initramfs for a kernel (dracut --force image kernel-version), lsinitrd lists its contents, and the kernel-install tool runs the steps when a package installs a kernel. On Debian-family systems the equivalent is update-initramfs. A missing or stale image is the usual cause of "cannot find root device" after a storage or driver change [src: man-pages f296d66efd3bcc17] [src: man-pages 8f8002806646e600]. Kernel crash dumps are another boot-time feature: the kdump mechanism reserves memory with the crashkernel argument and boots a small second kernel to save a core after a panic [src: rhel-10-docs 021df95d783d396a] [src: archwiki b28f916828a23dbe].

## Assessment: the good, the bad and the ugly

The good is that the chain is modular and inspectable. Every stage is a program reading a text configuration, the loader menu can be edited for one boot without touching disk, the initial image can be listed and rebuilt with ordinary commands, and the service manager records where the boot spent its time. Recovery paths exist at several depths, from a debug shell to a pause before switching root, so that almost any failure leaves a way in.

The bad is the number of independent configuration layers that must agree: firmware boot order, loader defaults, generated loader configuration, per-kernel entries, initramfs contents, the target symlink and unit files. Editing the wrong layer is the commonest mistake, for instance changing grub.cfg directly and losing the change at the next kernel update, or editing the defaults file and forgetting to regenerate. Differences between BIOS and UEFI paths, and between distribution families, make documentation transfer unreliable. Secure boot and encrypted disks add steps that tutorials omit, and a measured-boot setup can refuse a configuration change that would otherwise be harmless.

The ugly is that a boot fault takes the usual tools with it. A wrong fstab entry can drop the machine to the emergency shell on a remote server with no console. A kernel update with a missing driver in the initramfs yields a machine that cannot see its disk. The recovery path itself is a security hole when the console is reachable: rd.break, init=/bin/bash and an unprotected rescue shell give root to anyone who can type at the boot menu or power-cycle the machine. And self-inflicted outages are common: removing the default kernel, running the regeneration command with a wrong output path, or applying an overly hardened argument set.

## Applications beyond this domain

The same staged hand-off appears in other systems. Cloud virtual machines boot through the same firmware and loader chain, but often with a paravirtual console and metadata service, and cloud images set the serial console argument so that logs are visible in the provider's tooling. Containers skip the chain entirely and start the first process directly, which is why a recovery shell must be attached differently. Image-based operating systems use a read-only root, a boot loader entry per deployment and an automatic rollback if the new image does not report success, using the boot-complete target as the signal [src: man-pages 995fc6d090fa1524] [src: rhel-10-docs 6715a0dd2aa903d4].

Measured boot and remote attestation extend the chain of trust: each stage measures the next into a hardware register, and a verifier checks the measurements, which is the same chain with cryptography added [src: rhel-10-docs ae6052e23100c03c]. Embedded and network boot use the same stages with different transports: a kernel and initramfs fetched over the network, or a root file system exported by a server. Recovery media for every operating system follow the same logic of a minimal environment that can reach the real disk.

## Examples

A first exercise is to read the chain on a live machine. Print the kernel command line, list the entries in the loader configuration, find the initramfs for the running kernel and list its first screen of contents, and print the default target. Annotate each file with the stage that reads it.

A second exercise changes the boot configuration safely: add an argument to the defaults file, regenerate the configuration, confirm the change appears in the generated file, reboot, and verify it in the live command line. Then change the default target and confirm. The lab for this topic does the file-level part in a scratch root.

A third exercise is recovery practice on a disposable virtual machine: boot into rescue.target by editing the entry, then into emergency.target, and compare which file systems are mounted and whether the root is writable; then reset the root password with rd.break, including the relabel step, and prove the new password works.

A fourth exercise is hardening: require authentication for rescue mode with a drop-in, set a loader password, and verify that the edit prompt asks for credentials, then test that a legitimate administrator can still recover.

A failing example is a bad fstab line: add a nonexistent device without the nofail option, reboot, and recover from the emergency shell. Another is forgetting to regenerate after editing the defaults file. A third is skipping the relabel marker and finding that logins fail with a security-policy denial.

## Related problems and ideas

Neighbouring topics are the unit and target mechanism that does the late boot, kernel modules and parameters that the initramfs loads and applies, storage layout and the mount table, disk encryption unlock, and physical console setup. Boot performance is a related problem: the analyzer's blame and critical-chain views show which units delay the target. Fault tolerance is another: boot counting and automatic fallback entries pick the previous kernel after repeated failures, and A/B image layouts keep a known-good copy.

Ideas for practice: keep at least one older kernel installed; test every boot change on a disposable machine first; use nofail and device timeouts for non-essential mounts; keep console access (serial or hypervisor) documented for every server; protect the loader and rescue shell on machines whose consoles are exposed, and balance that against the need to recover; script initramfs regeneration after driver changes; and write the recovery sequence down before it is needed.

## Active research

Work in this area centres on trust and speed. Unified kernel images combine the kernel, initramfs and command line into one signed file so that the command line cannot be altered without breaking the signature, which closes the boot-menu edit route. Measured and remote-attested boot, with disk unlocking tied to the measurements, are in production use. Faster boot comes from loading the kernel straight from firmware, parallel initialisation and reducing the initramfs. Reproducible, minimal initramfs images generated from declarative descriptions, and boot managers with automatic bless-or-rollback based on health checks, are under active development. Firmware itself is the subject of work on open implementations and update mechanisms.

## Future direction

Expect the boot menu to become less editable and more verified: signed unified images, loader entries managed by the package system and no hand-edited arguments on production machines. Recovery will lean on automatic rollback and on remote consoles instead of someone at the keyboard. Password reset through the console will shrink to machines in controlled spaces, while fleets rely on re-provisioning. The mental model, firmware then loader then kernel then initial image then service manager, will remain the map for diagnosing every failure, and the skill of reading it layer by layer is the one that carries over.
