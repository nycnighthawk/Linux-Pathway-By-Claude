# Does it still work after a restart: the discipline of persistent configuration

## Define the problem

Almost every administrative command acts on a machine in two possible ways. It can change what is true right now, in the kernel's memory and the running service manager, or it can change what will be true the next time the machine starts, in files on disk. Many commands do one of these and not the other, a few do both, and the command's name rarely says which. The result is the most common and most embarrassing failure in system administration: a change that worked perfectly during the session, was never written down anywhere that survives, and disappeared at the next reboot, usually at night and usually discovered by a colleague.

The opposite failure is just as real. A change written to a file but never applied leaves a machine whose running state differs from its configuration, and the surprise arrives later, when someone restarts a service for an unrelated reason and picks up a configuration that was never tested. A third failure mixes them: a persistent change that is syntactically valid but wrong, such as a bad line in the mount table, which does not show itself until the machine tries to boot and stops at the emergency shell. The topic is the discipline for avoiding all three: know for every command which of the two states it touches, make the persistent change deliberately, check it without rebooting where possible, and then prove it with a restart.

## History and approaches

On the earliest Unix systems the distinction hardly existed, because the configuration was a set of shell scripts run at boot. To change the machine permanently you edited the script, and to change it now you ran the same command by hand. The two states were bridged by the administrator's memory, and the standard error was running the command and forgetting to edit the script. Later systems made the split explicit in tools: a command to set a kernel value now, and a file read at boot; a command to start a service now, and a separate action to link it into the boot sequence.

Different projects resolved the tension in different ways, and the differences are the source of most confusion. Some tools write both: a network configuration tool can modify a stored connection and apply it to the device in one step, or store it for later. Some offer an explicit flag for persistence, so the default is temporary and a flag makes it permanent: the firewall tooling applies rules to the running set unless asked to save them, and the SELinux boolean command has a persistence flag. Others use a separate verb: a service manager has start for now and enable for the next boot, with a combined form that does both. Some store the permanent setting and apply it by reloading, as with the host name, where the stored static name is the one that matters [src: rhel-10-docs adae638d7d364169].

The idea of testing persistence by restarting is old, but cloud computing made it cheap: with virtual machines and images, the reliable way to prove a configuration is to build a new machine from scratch and see that it works, which is the logic of immutable infrastructure. Then the service manager added a lighter option, a soft reboot, which restarts all of user space while leaving the kernel running and skipping firmware initialisation, so most configuration (units, mounts, services, user-space settings) can be proven in seconds, though not kernel arguments or hardware initialisation [src: rhel-10-docs 37b5a332a06a1f7e] [src: rhel-10-docs 7d155ccc4a79755a]. A further approach is to remove the question by making the persistent state the only state: configuration management tools and image-based systems write the files and derive the running state from them, so that a mismatch is an error.

Partial successes are many. A check of the files (syntax validators, dry runs) catches typos but not behaviour. A reboot catches behaviour but costs downtime. Configuration management catches drift but only for what it manages. The practical approach that emerged is layered: validate the file, apply it without a reboot, read the live value back, and finally prove it with a restart on a test machine before the change reaches production.

## Current state

The first skill is to classify commands. For each area an administrator touches, there is a runtime action and a persistent action, and the safe habit is to know both. For kernel parameters the runtime action is sysctl -w key=value and the persistent one is a file ending in .conf under /etc/sysctl.d, applied with sysctl --system. For kernel modules, modprobe loads now, while a file in /etc/modules-load.d loads at boot and one in /etc/modprobe.d sets options and blocks. For services, systemctl start and stop act now, while enable and disable change the symlinks that decide the next boot, and the --now flag does both together; masking is persistent and prevents starts of any kind [src: man-pages 33d74726723892ed]. For mounts, the mount command acts now and an entry in /etc/fstab (or a mount unit) acts at boot; after editing fstab the manager must reload so that its generated units are refreshed. For swap, swapon acts now and fstab persists. For the host name, hostnamectl set-hostname stores the static name in /etc/hostname and sets the transient one; the manual notes that services which read the name only at start must be restarted, or the machine rebooted, for the change to be seen everywhere [src: rhel-10-docs adae638d7d364169].

The pattern continues. For the firewall, rules added to the running configuration are lost on reload or reboot unless saved; the usual forms are adding with a flag that targets the permanent configuration and reloading, or adding at runtime and then copying the runtime configuration to permanent. For network settings, ip address and ip route changes are runtime only, whereas edits to the connection profiles of the network manager (and the command that modifies them) are stored and need a reactivation to apply. For SELinux, setenforce changes the mode now and the configuration file under /etc/selinux sets it at boot, and a boolean needs its persistence flag. For time zone and locale, timedatectl and localectl write files and change state together. For limits, the shell's ulimit affects only that shell and its children, whereas limits files and the service manager's Limit settings persist. For kernel command-line changes, editing the loader configuration and regenerating it persists, and only a reboot applies; the same holds for control-group version, which on the Red Hat family is switched with a kernel argument added to every entry and takes effect after a restart [src: rocky-docs 79e5c84365a643a4]. For power-key behaviour, a setting in the login manager's configuration (or a drop-in) persists, and the manager must be told to reload it to apply now [src: rhel-10-docs 111e8709b2f59fb3]. For the files themselves, permissions and ownership changes on a normal disk file system persist at once, because they are stored in the file system, while changes to files under /proc, /sys and /run do not.

The second skill is validating persistent state without rebooting. The mount table can be checked with findmnt --verify, which parses fstab and reports unknown file systems, missing devices and mount points and other mistakes, and mount -a mounts anything that is listed but not mounted, so a bad line fails now and not at boot [src: man-pages 49999d3dceb9fe64]. Unit files can be checked with systemd-analyze verify, and merged configuration can be printed with systemctl cat and systemd-analyze cat-config. Sudo rules are checked with visudo -c, and the sudoers drop-in with visudo -cf. The kernel parameter files are applied and read back with sysctl --system followed by sysctl key. The loader configuration can be regenerated and inspected before it is trusted. Cron and timer expressions can be tested with systemd-analyze calendar. Many tools offer a dry-run flag, such as modprobe -n or logrotate -d, and the habit is to use it every time.

The third skill is comparing the live state with the file state. For services, systemctl is-enabled reports the persistent state and systemctl is-active the runtime state, and a unit can be enabled but inactive or active but disabled, which is exactly the mismatch to look for; systemctl list-unit-files shows persistent state for every unit, and the flag --state=failed lists broken ones. For kernel parameters, comparing sysctl -a output with the union of the files reveals runtime-only differences. For modules, lsmod against the load lists. For the firewall, the runtime and permanent listings can be compared. The idea generalises to a small script that, for each item of a change, checks the persistent location and the live value and exits non-zero if either is missing; the lab for this topic asks the learner to write exactly that and to run it against a machine that kept its changes and one that did not.

The fourth skill is the restart itself. A full reboot proves everything but costs the most. A soft reboot restarts user space while the kernel keeps running, which proves unit files, mounts, services and user-space configuration quickly but not kernel arguments, module options for modules already loaded, or firmware settings [src: rhel-10-docs 37b5a332a06a1f7e]. Restarting only the affected service proves that service's configuration. A kexec reboot, which the power-key settings list among their options, loads a new kernel directly and skips firmware. Whichever form is used, the procedure is the same: record the expected state before, restart, then check the same items afterwards, and look at the journal for the boot (journalctl -b) for errors. For anything that blocks boot or reduces access, such as mounts, authentication of rescue shells and network configuration, the test must be done where a failed boot can be recovered, with a console or snapshot [src: disa-stig c376139108447f61].

## Assessment: the good, the bad and the ugly

The good is that the split is real and visible: the system keeps persistent configuration in files and live state in kernel and manager memory, and the tools exist to read both. Experiments are cheap because a runtime change is reversible by a reboot, which makes the runtime path a safe sandbox. Validators and dry-run flags catch a large fraction of persistent errors before they matter, and fast reboots make proof cheap.

The bad is that no single convention covers the tools. One command is temporary by default and another permanent; one needs a flag, another a separate verb, another a reload. Documentation frequently shows only the runtime form, because it is shorter. The file formats and directories differ by subsystem, and by distribution family. Some changes seem persistent but depend on a boot-time ordering that differs from the interactive session, for example settings for devices that appear after the file is read. Some persistence requires an extra regeneration step, such as rebuilding a loader configuration or the initial RAM image, and forgetting it leaves the file correct and the boot unchanged.

The ugly is the delayed consequence. A runtime-only fix hides the problem until the next maintenance window. A persistent edit with an error can prevent boot, and the machine may be remote. A change tested only with a service restart may fail on a full boot because of ordering, for instance a service that needs a mount or network that is not yet available at boot. A configuration that is correct on disk may be shadowed by another file with a later name that sets the same key. And drift accumulates quietly: the machine that has run for two years with hand-applied fixes may not boot into the state anyone thinks it has.

## Applications beyond this domain

The same discipline underlies immutable infrastructure and declarative operations. Image-based operating systems keep the running state derived from an image and apply updates by soft reboot or by switching to a new image, so a change that is not in the image does not exist after the next deployment [src: rhel-10-docs 37b5a332a06a1f7e]. Orchestrators distinguish a live object from its stored manifest and reconcile them continuously. Databases separate the running configuration of a server from its stored file and offer commands to persist runtime settings, with exactly the same failure mode. Network devices split a running configuration from a startup configuration, and the operator command to copy one to the other is famous for being forgotten.

Provisioning tools address the question by making configuration the source of truth. First-boot tooling writes users, files and units from declarative data so that a rebuilt machine is identical [src: archwiki 324bc15fd7f99a29]. Partition tools that run at boot can create or grow partitions from definition files, again deriving state from files [src: man-pages a299936ef96c78cf]. Compliance scanning checks both the file and the live value, since either alone can be wrong.

## Examples

A first exercise classifies commands. Make a table with columns for the area, the runtime command, the persistent command and the verification, and fill it in for ten areas: kernel parameters, modules, services, mounts, swap, host name, firewall, network connection, SELinux mode and a limit. Then check each entry on a test machine.

A second exercise applies three changes the wrong way, then the right way. Change a sysctl value with -w, start a service without enabling it, and mount a file system by hand. Reboot and list what was lost. Repeat with the files, the enable step and an fstab line, validate each with its checker before rebooting, and compare.

A third exercise writes a verification script that checks the persistent location and the live state of each item and exits non-zero on any mismatch, then runs it against a good and a bad machine. The lab for this topic uses two fixture directory trees to make this repeatable.

A fourth exercise compares restart forms. Make a change to a unit and prove it with a service restart, then with a soft reboot, then with a full reboot, and write down what each proved. Add a kernel argument and see which forms prove it.

A failing example is a bad fstab line without the nofail option, which stops the boot at the emergency shell; findmnt --verify would have caught it. Another is a firewall rule added at runtime only. A third is a file named so that it sorts before a vendor file and is overridden.

## Related problems and ideas

Neighbouring topics are the unit and drop-in mechanism, whose layered files make persistence explicit; the boot process, where some changes only apply at restart; kernel parameters and modules, where the runtime and file forms are a textbook case; and configuration management and immutable images, which turn the discipline into a pipeline. Related ideas include idempotent change scripts that can be run repeatedly, canary machines that take a change first, rollback by snapshot, and drift detection that compares the running system with its declared state.

Ideas for practice: write the persistent change first and apply it from the file; change one thing at a time; validate before applying and apply before rebooting; keep a log of changes with the reason; test on a machine that can be recovered; use the soft reboot for quick proof of user-space changes and the full reboot for anything involving the kernel, modules or boot arguments; and treat any change that exists only in memory as a defect to be fixed before the session ends.

## Active research

Work in this area addresses drift and reproducibility. Declarative and image-based systems aim to make the running state a pure function of a description, and research on reproducible builds extends this to the images themselves. Drift detection tools compare live state with desired state across fleets and are exploring ways to explain differences rather than just list them. Faster restart mechanisms, including soft reboot, kexec-based update and live patching, reduce the cost of proof. Verification by model-checking of configuration, and tools that predict whether a configuration will boot from the files alone, are active topics, as is language-model assistance for generating configuration, where the risk is a plausible command that is runtime-only.

## Future direction

Expect the runtime and persistent states to converge in tooling, with commands that edit the file and apply it together, and with systems that refuse to run with unrecorded changes. Fleet practice will move toward rebuilding from images instead of repairing in place, so that a reboot test becomes a deployment test. Soft reboots and similar techniques will make proof routine rather than exceptional. The administrator's checklist, classify the change, write it down, validate it, apply it, read it back and restart a test machine, will remain the same, because the underlying fact, that memory is temporary and files are not, does not change.
