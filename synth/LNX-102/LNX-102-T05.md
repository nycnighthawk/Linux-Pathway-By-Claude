# Keeping a record of what happened: the journal, syslog forwarding and log rotation

## Define the problem

A system that cannot explain what it did is a system that cannot be repaired, audited or trusted. Every daemon, the kernel and the boot sequence produce a stream of events, and somewhere those events have to be captured, labelled by origin and urgency, stored long enough to be useful, searched when something breaks, and eventually deleted. The difficulty is that the producers are many and unrelated, the consumers have different needs (a human reading the last minute of a failing service, a security team keeping a year of authentication events, a remote collector wanting everything in real time), and the disk is finite.

Logging therefore has three separable jobs. Collection means getting messages from programs and the kernel into a central place with reliable metadata: who sent it, when, from which unit, at what priority. Storage and search mean keeping them in a form that can be queried and that survives a reboot if required. Retention means bounding growth by rotating, compressing and expiring old data, without losing the lines needed for an investigation and without letting a runaway service fill the disk and take the machine down. The topic covers the three components that have shared these jobs on current Linux distributions and how they cooperate.

## History and approaches

The original mechanism was the syslog daemon of early BSD Unix. Programs called a library function to send a short text line, tagged with a facility (the category of the sender, such as the mail system, the kernel or an authorisation program) and a priority (a severity from emergency through debug), to a local socket. The daemon read a small configuration file of selectors and actions: messages matching a facility and priority were appended to a named file, sent to a terminal, or forwarded to another host over the network. The design was simple and universal, and it became an informal standard that nearly every network device and program learned to speak [src: debian-handbook e0d044a58c06991d].

The weaknesses were also simple. Messages were plain text without structure, so searching meant pattern matching. The facility and priority taxonomies were coarse and fixed. The transport was unreliable datagrams by default, so messages could be lost and could be forged. Timestamps carried no year or time zone. Nothing recorded the process identifier or the control group, so correlating a line with a service was guesswork. And logs from the early boot, before the daemon started, were lost.

Several successors improved on this. Rsyslog and syslog-ng kept the file model but added reliable transports, extended filters, encrypted relays, output to databases and message queues, and modular input and output. At the same time the systemd project introduced the journal, a binary, indexed, structured log collected by the journald daemon. It captures the kernel log, early boot messages, the standard output and error of every service, and syslog calls, and it adds trusted fields such as the unit name, process identifier and boot identifier that a sender cannot forge. The pragmatic result on most distributions was coexistence: journald collects everything, and rsyslog reads from it to write the traditional text files and to forward [src: rhel-10-docs e839c2b5288bbd5e] [src: archwiki 4cb8b03fe89c7148].

Rotation grew up in parallel. Text logs grow without limit, so a rotation tool was needed to rename the current file, start a new one, compress old ones and delete the oldest. The logrotate program, run daily from a scheduler, became the standard, driven by per-application policy files. The partial failures of this approach are well known: a program that holds its log file open keeps writing to the renamed file until told to reopen it, and a copy-and-truncate workaround can lose lines in the gap.

## Current state

On a current Red Hat-family or Debian-family system the picture is layered. The journal daemon collects from the kernel, the early boot, service output and the syslog socket, and stores the data in binary files; the rsyslog service reads syslog messages from the journal, sorts them by facility and priority according to its rules, and writes them to files under /var/log, and it can relay them to remote collectors [src: rhel-10-docs e839c2b5288bbd5e] [src: rocky-docs 9b9f8fafef416b6c]. Security baselines require that at least one logging service be active and that exactly one of the collectors be responsible for persistence, so that they do not conflict [src: compliance-as-code 7639c2e2571c7392] [src: compliance-as-code ddd4b38fa5f727ff] [src: compliance-as-code fccc39c90c7fa858].

The journal's configuration is in /etc/systemd/journald.conf and in drop-ins under /etc/systemd/journald.conf.d, in a [Journal] section. The setting Storage= takes volatile (memory only, under /run/log/journal), persistent (on disk under /var/log/journal, falling back to memory early in boot), auto (persistent if the directory already exists, volatile otherwise) or none (drop everything, though forwarding still works). A service switches from volatile to persistent after boot through a flush; the common way to make a machine keep logs across reboots is to set Storage=persistent, or on older setups simply create the /var/log/journal directory. Related settings bound the size and age: SystemMaxUse= and SystemKeepFree= for the persistent area, RuntimeMaxUse= and RuntimeKeepFree= for the memory area, SystemMaxFileSize= and SystemMaxFiles=, MaxRetentionSec= and MaxFileSec= for age and file rotation, Compress= for large entries, Seal= for forward-secure sealing of persistent files (which needs a key from journalctl --setup-keys), SplitMode= for per-user files, RateLimitIntervalSec= and RateLimitBurst= to stop a noisy service flooding, and ForwardToSyslog=, ForwardToKMsg=, ForwardToConsole= and ForwardToWall= for forwarding [src: man-pages ffe6b7ab0ac9d0b1].

Reading the journal is done with journalctl. Its most used options are -u UNIT to select a service, -b to select the current boot (with -b -1 for the previous one and --list-boots to enumerate), -k for kernel messages, -f to follow new entries, -n N for the last N lines, -p PRIORITY to filter by severity (a name or a number from 0, emerg, to 7, debug, which includes the more severe levels), -S and -U (--since and --until) with times such as "2026-11-14 10:00" or "1 hour ago", -g to grep a pattern, -o to choose an output format (short, verbose, json, json-pretty, cat and others), -r to reverse the order, --no-pager, and field matches such as _SYSTEMD_UNIT=name.service, _PID=123 or _UID=1000. Housekeeping options include --disk-usage to report space used, --vacuum-size=, --vacuum-time= and --vacuum-files= to trim, --verify to check file integrity, and --flush and --rotate to move and rotate. By default a non-privileged user sees only their own entries unless a member of the adm, wheel or systemd-journal group [src: man-pages e06b33f8803327be] [src: man-pages 6ef726cbd77b42de] [src: man-pages dfef590a9ad9be3e].

Rsyslog's main file is /etc/rsyslog.conf, with additional files included from /etc/rsyslog.d. A rule is a selector and an action. The selector is a facility and priority pair such as authpriv.*, mail.info or *.emerg, which can be combined with semicolons, negated with an exclamation mark and made exclusive with an equals sign; the facilities include auth, authpriv, cron, daemon, kern, lpr, mail, news, syslog, user, uucp and local0 to local7, the latter reserved for site-defined sources. The action is a file path (with a leading minus in the older syntax to skip synchronous flushing), a user or terminal, an asterisk for everyone, a forwarding target such as @host for UDP or @@host for TCP, or a module output. Modules provide the inputs and outputs: imjournal reads from the journal, imuxsock reads the syslog socket, imtcp and imudp receive from the network, omfile writes files and omfwd forwards. The newer RainerScript syntax supports conditional expressions and templates alongside the traditional lines, and mixing the two within a file is allowed [src: rhel-10-docs 736e668198bc6c08] [src: rocky-docs a0137e8267a883f9].

Rotation is configured by logrotate, which is normally started daily by a timer or by cron and reads the main file /etc/logrotate.conf plus policy files in /etc/logrotate.d. A policy names one or more log files and a block of directives. The common ones: daily, weekly, monthly or yearly to set the interval; rotate N for how many old copies to keep; size, minsize and maxsize to rotate by size; compress and delaycompress (leave the most recent rotated file uncompressed until the next cycle); missingok to ignore an absent file; notifempty to skip empty files; create mode owner group to make the new file; copytruncate for programs that cannot reopen their log; dateext for date-based suffixes; olddir to move rotated files; su user group to control ownership during rotation; sharedscripts to run scripts once for several files; and prerotate, postrotate and endscript to run commands around the rotation, such as telling the daemon to reopen its log [src: man-pages 147040756630419f]. State, the date of the last rotation of each file, is kept in a status file, normally /var/lib/logrotate/status. The command is tested with logrotate -d policy.conf (debug: print the actions and do nothing) and run for real with -f to force, -v for detail and -s to choose a different state file. A compliance rule checks that every log is covered by some rotation policy [src: compliance-as-code 32efe368bd988026].

## Assessment: the good, the bad and the ugly

The good is the combination of structure and compatibility. The journal gives trustworthy metadata, indexing that makes per-unit and per-boot queries fast, capture of output from services that never opened a log file, and automatic size bounds. The text path through rsyslog keeps decades of tooling, remote collection and compliance conventions working. Logrotate is small, predictable and policy-driven, and with a well-behaved daemon the cycle needs no attention.

The bad is the overlap and the defaults. Two collectors that both persist data can duplicate effort and disagree about retention. The journal's default may be volatile on some distributions, so a machine that crashes leaves no logs from before the reboot, which is the moment they are most needed. The binary format needs a special reader and is more sensitive to corruption than text. Facility and priority are coarse and set by the sender, so a program can log everything as debug or as error. Rotation's assumption that a program will reopen its log on a signal is false for many programs, and a missing postrotate hook is the most common reason a rotated log keeps growing under its old name.

The ugly is the loss and the leak. Rate limiting can silently drop a burst of messages exactly when a service is failing, and lines are lost without a visible trace except a single summary. Log forwarding over unencrypted UDP can be spoofed or dropped. Logs frequently contain secrets, such as tokens in URLs or passwords typed at the wrong prompt, and keeping them for long periods increases the exposure. A full disk because of an unrotated log can crash services, and a log directory that logrotate cannot read because of permissions fails silently except in the scheduler's own output. Deliberately tampering with local logs is the first step of many intrusions, which is why the forward-secure sealing option and remote copies exist.

## Applications beyond this domain

The same pipeline, produce, tag, ship, store, query, expire, is the heart of every observability stack. Cluster platforms write container output to files on each node and run a collector, as an agent on each node or as a sidecar container beside the application, to ship it to central storage; the platform's own documentation describes the node's log location and the sidecar pattern [src: kubernetes-docs dd9776636f8242ca] [src: kubernetes-docs 0a49c7bbb963d06a]. Virtual machine monitors write their logs to files or serial devices on the host, and their production guides cover how to handle the log files and serial consoles so that guest output does not flood the host [src: firecracker-docs 097703b092e50c64] [src: firecracker-docs 754aa2155ad7cc47]. Language libraries, including the Python standard logging module, mirror the facility and level concepts with handlers that write to files, sockets or syslog, and show up in the same pipelines [src: python-docs f6f74ace1a2a7705].

Security operations reuse the model too: audit trails, intrusion detection and change monitoring all depend on tamper-evident, centralised, retained logs, and the handbook's advice on detecting changes starts with the logs [src: debian-handbook 59b7c1eebb57566b]. Compliance regimes such as the security technical guides specify exactly which events must be recorded, for how long, and how they must be protected.

## Examples

A first exercise is to trace one message. Run logger with a chosen facility and priority, then find it in the journal with journalctl and the field filter, in the text file written by rsyslog, and on a remote collector if one exists. Note which fields each store has, and which were added by whom.

A second exercise is persistence. Check the current storage mode, make the journal persistent with a drop-in in journald.conf.d, restart the daemon, reboot a test machine, and list the boots. Then set a size cap and verify it with --disk-usage, and trim with --vacuum-size. The lab does the file part of this.

A third exercise is a rotation policy. Write a policy for an application log with weekly rotation, eight copies, compression and a postrotate hook, test it with logrotate -d, force it on a copy of the log, and check the rotated names, the mode of the new file and that the program writes to the new one. Repeat with copytruncate and compare what happens to lines written during the rotation.

A fourth exercise is routing: add an rsyslog rule that sends a local facility to its own file, send a test message, and confirm it appears there and also in the journal. Then forward the same facility to a second machine over TCP.

A failing example is a daemon that keeps writing to its old log after rotation because no reopen signal was sent; the file listing shows the deleted file still open. Another is a disk filled by a verbose service with no size limit. A third is a rate limit that hides a burst during an outage.

## Related problems and ideas

Neighbouring topics include time synchronisation, since logs are only useful if clocks agree; scheduled jobs, since rotation is one; auditing, which records security events through a separate kernel facility; and metrics and tracing, which complement logs. Structured logging, where applications emit key-value or JSON records, reduces the need for pattern matching and is supported natively by the journal's field model. Log shipping reliability, with queues, retries and back-pressure, is a related engineering concern.

Ideas for practice: decide centrally which collector persists and disable duplication; make the journal persistent on servers; set explicit size and age limits; give every application a rotation policy and test it with the debug flag; use unit and priority filters first and text search second; send critical logs to a remote host over a reliable, encrypted transport; keep clocks synchronised; and protect log directories with sensible modes and review what sensitive data the applications emit.

## Active research

Current work in this area concerns scale, structure and integrity. Log pipelines are moving toward structured, schema-aware records and efficient columnar storage so that years of data can be queried cheaply. Tamper evidence is pursued through forward-secure sealing, hash chains and remote attestation of log collectors. Rate limiting and sampling research aims to keep the informative lines while discarding repetition, and anomaly detection over logs, including language-model-based summarisation, is under active exploration, with the caution that generated explanations need verification against the raw lines. The kernel and eBPF ecosystem add low-overhead event streams that bypass text logging. Standards work continues on transport security and on common field vocabularies.

## Future direction

Expect logging to become more structured and more centralised, with the local journal as a buffer in front of a shipper and with text files an export format rather than the primary record. Retention will be set by policy and cost, with tiered storage. Integrity guarantees will strengthen as remote, append-only storage becomes the norm. The administrator's local skills stay useful because every pipeline still starts with a process writing to a descriptor, a collector tagging it, a retention rule bounding it and a human filtering by unit, time and priority to find the one line that matters.
