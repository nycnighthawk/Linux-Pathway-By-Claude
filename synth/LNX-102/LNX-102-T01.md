# Who is acting, and with what authority: accounts, groups, delegated privilege and password lifetime

## Define the problem

Every action on a multi-user machine must be attributable to someone and limited by what that someone may do. The kernel does not know people; it knows numbers. A process carries a user identifier and a group identifier, and every permission check compares those numbers to the numbers stored on files, sockets and other objects. All of the human-facing machinery in this topic exists to manage that mapping: which number belongs to which person or service, which other numbers they share, how they prove they are the person, and how a trusted few may borrow the powers of the most privileged number, zero.

Three separate problems hide inside that sentence. The first is bookkeeping: creating, changing and removing accounts consistently across several small files so that no file disagrees with another. The second is delegation: a team of administrators needs to run privileged commands without sharing the credentials of the superuser account, and without being given more power than the job requires. The third is time: a password that is correct today may leak tomorrow, so accounts need lifetimes, warnings, lock-outs after neglect, and a way to expire everything at once when someone leaves.

When these are done badly the symptoms are familiar. Two accounts share one number, so one person can read the other's files. A departed contractor's login still works two years later. An administrator has an unrestricted rule in the delegation file because narrowing it looked tedious, and one typo in that file locks every administrator out. A service runs as the superuser because nobody created an account for it. The topic is therefore a mix of data formats, commands and policy habits, and the course goal is to make the habits as automatic as the commands.

## History and approaches

Early Unix stored everything about a login in one world-readable text file with seven colon-separated fields: name, password hash, numeric user identifier, numeric group identifier, a free-text comment field, home directory and login shell. The original design assumed a friendly community and hardware too slow to guess hashes, so publishing the hashes seemed harmless. That assumption failed as soon as machines became fast and networks connected strangers. Anyone who could read the file could take the hashes away and guess offline [src: man-pages bf33ec55d447d494].

The partial fix, the shadow password suite, moved the hashes into a second file readable only by the superuser and left a placeholder character in the old file. The second file also gained fields for ageing: when the password last changed, the minimum and maximum age, a warning period, an inactivity period and an absolute expiry date, giving nine fields in all, the last reserved. Groups followed the same path with a companion file for group passwords and administrators [src: man-pages 986cac7e6b586374]. The old file stayed world-readable because every program that turns a number into a name needs it, which is why the split is a compromise: names stay public, secrets do not.

Delegation had its own history. The first approach was to share the superuser password, which destroys accountability: the log says root did it, never who. The second approach was a set-user-identifier helper such as the switch-user command, which still needs the target's password. The third and now dominant approach, the sudo program, lets a policy file say that named users or groups may run named commands as another user and be authenticated with their own password, with each invocation logged. The Debian handbook describes the same motivation: several administrators on one network, and sharing the root password opening the door to anonymous abuse [src: debian-handbook cfedd7328841ab3f]. Where sudo's plain-text policy did not scale, enterprise directories grew centrally managed equivalents with role-based access control, so that the rules live in one place and clients fetch them [src: rhel-10-docs 0785efca14bbed36].

Partial successes and failures run through all of this. The shadow suite's own configuration file, login.defs, once controlled almost all login behaviour, but much of that function has since moved into the pluggable authentication framework, and the page itself warns that the passwd, login and switch-user commands now consult the pluggable configuration instead [src: man-pages deda374cd8d6a3bc]. Administrators who tune only login.defs may believe a policy is in force that no program reads. Password expiry itself was a partial success: forced rotation catches abandoned credentials but encourages predictable passwords, and current guidance leans toward longer secrets, rotation on evidence of compromise and multi-factor authentication. The compliance corpus, however, still asks for a bounded lifetime, so administrators must hold both ideas at once.

## Current state

The account database today is four files in /etc. The user file has the seven fields above, with an x in the password field to say the hash lives elsewhere. The shadow file holds the hash and the ageing numbers. The group file has four fields: group name, an obsolete password field, numeric group identifier and a comma-separated member list. The group shadow file holds the group-level secrets and the lists of group administrators and members [src: man-pages 1578d8a916197da2] [src: rocky-docs 52fed9c345a0f270]. Dates in the shadow file are counted in days since 1 January 1970 in UTC, which is why raw values look like five-digit numbers.

A shadow entry reads left to right: login name, hash (an exclamation mark at the front means locked, an asterisk or any string that is not a valid hash means no password login is possible), last change, minimum age, maximum age, warning period, inactivity period, expiry date, and a reserved field. A last-change value of zero forces a change at the next login. An empty maximum age disables the warning and inactivity features as well, because they are measured from it. If the maximum is lower than the minimum, the user can never change the password at all [src: man-pages 986cac7e6b586374].

Accounts are created and edited with the shadow-utils commands. The creation command useradd takes, among others, -u for the numeric identifier, -g for the primary group (by name or number), -G for supplementary groups, -d for the home directory, -m to create it and -M to refuse to, -s for the login shell, -c for the comment, -e for the account expiry date, -f for the inactivity period, -r for a system account, -U to create a same-named private group, and -R to operate on a different root directory instead of the live system. Without -d the home directory is the base directory plus the login name; the base comes from -b or from the HOME entry of the defaults file /etc/default/useradd, falling back to the directory /home. The directory is made only if -m is given or CREATE_HOME is true in login.defs [src: man-pages 531435afb8c91726] [src: man-pages b92bb7913cc1cee9]. With only -D the command prints its defaults, and with -D plus -b, -e, -f, -g or -s it changes them; the compliance rule that locks accounts 35 days after password expiry is applied this way, with useradd -D -f 35 [src: disa-stig 8762ad61e1297f80].

The modification command usermod accepts the same attribute flags, and the one that trips people up is -G: alone it replaces the supplementary group list, and only with -a does it append [src: man-pages f34c4496572ae367]. Related commands are groupadd, groupmod and groupdel, userdel (with -r to remove the home directory and mail spool), gpasswd for group membership and administrators, newgrp to start a shell with a different primary group, and id and getent to read the result. The command getent passwd name asks the name-service switch, so it also returns accounts that come from a directory service and are not in the local file. The id command prints the numeric and named identity of a process, which is the value the kernel actually checks.

Password ageing is a per-user property edited with chage. Its options are -d for the last-change date (0 forces a change at next login), -m for the minimum days, -M for the maximum days, -W for the warning days, -I for the inactivity days after expiry before the account locks, -E for an absolute expiry date, and -l to list the values; -1 clears most of them. Dates may be given as YYYY-MM-DD or as day counts, and the tool reads them in UTC [src: man-pages 25521ad6854002d1]. System-wide defaults for new accounts come from login.defs: PASS_MAX_DAYS, PASS_MIN_DAYS and PASS_WARN_AGE for ageing, UID_MIN, UID_MAX, GID_MIN and GID_MAX for the ranges the allocator uses, and CREATE_HOME and USERGROUPS_ENAB for home directories and private groups. If PASS_MAX_DAYS is unset the value -1 applies, which disables the restriction [src: man-pages f119d0cab2969a11]. The key operational fact is that these defaults apply only to accounts created afterwards; existing accounts must be changed with chage, and the compliance guidance says exactly that, recommending a maximum between 90 and 360 days depending on the environment and a seven-day minimum with seven days of warning [src: compliance-as-code 3275880b8fefa8be].

Delegation is expressed in the sudoers file and in small files in a directory of drop-ins, edited with the visudo command, which locks the file and checks the syntax before it saves. On Red Hat-family systems the stock file grants full rights to the wheel group; on Debian-family systems the equivalent is the sudo group. The handbook adds that drop-in files should carry mode 0440 and that the main file must include the directory [src: debian-handbook cfedd7328841ab3f] [src: rhel-10-docs 95d6576a3ca3b5dd]. A rule has the shape who, where, as-whom and what: for example a group name prefixed with a percent sign, ALL for hosts, a runas user in parentheses, optional tags such as NOPASSWD, and a comma-separated list of absolute command paths. The sudo program authenticates the invoking user, matches the policy, runs the command as the target user and logs it. The manual page stresses that the real, not effective, user identifier of the caller selects the policy [src: man-pages 38d15e91381ac37f]. Security baselines require that sudo asks for the invoking user's password, which means the flags rootpw, targetpw and runaspw must be off [src: compliance-as-code 4d3161a115f8fc3c].

## Assessment: the good, the bad and the ugly

The good is that the model is small and legible. Four text files and a handful of commands cover local identity, and the formats are stable across decades and distributions. Because the files are text, they can be diffed, versioned and audited; because the commands accept a root directory option, the same tools can build the account database of an image or a container without touching the host. The delegation model gives accountability: with sudo the log names the human, passwords are personal, and rules can be scoped to single commands.

The bad is the number of places that must agree. Defaults in login.defs apply only to new accounts. Ageing set in chage must be applied to each existing account. Pluggable authentication, not login.defs, may enforce the real password rules. Group changes do not affect processes that are already running, so a user added to a group must log in again before the new membership appears. Command-path rules in sudoers are fragile: allowing a program that can spawn a shell, edit arbitrary files or run other programs grants far more than the line suggests, and wildcards in argument patterns can be abused. Sudo also changes the environment in ways that surprise scripts, so tools that work in a root shell may fail under sudo, and vice versa.

The ugly is the irreversible and the invisible. A syntax error in the delegation file written with a plain editor can remove every administrator's rights at once, which is why visudo and validation of drop-ins are not optional. An empty password field can allow login without any password unless the authentication stack blocks it. Deleting an account without handling its files leaves orphaned numbers that a later account may reuse, silently inheriting someone else's data. Service accounts with real shells and passwords are a favourite foothold. And the inactive-account problem is largely invisible without deliberate review, since nothing fails when a credential is simply never used, which is why audit rules ask for a lock after a fixed idle period [src: disa-stig 8762ad61e1297f80].

## Applications beyond this domain

The same pattern, a stable identifier mapped to a person plus a policy of delegated, logged, time-limited authority, appears throughout modern infrastructure. Cloud providers issue identities and roles with temporary credentials that expire on their own, which is password ageing implemented at the protocol level. Container platforms map users inside a container to unprivileged numbers outside through subordinate identifier ranges, and rootless runtimes depend on the same files and tools described here. Cloud-init drives the account tools at first boot, with a users module that can create accounts, groups, keys and sudo rules from a declarative file, so that a fleet's administrators are defined as data [src: rocky-docs c4a4d7ad0c7a15a7] [src: archwiki 2ae5a7c5504b808e]. Enterprise identity systems extend sudo rules to a directory so that rules, hosts and users live in one database [src: rhel-10-docs 1396e21a7c6ec561].

Outside Unix the ideas reappear: Windows directories talk about reducing standing privilege and securing administrator groups, which is the same instinct as scoping a sudo rule [src: ms-learn-adds b874a4fd09697bab]. Even the boot loader has the same pattern, since a password on the boot menu stops anyone with console access from editing kernel arguments, and compliance baselines treat it as part of identity control [src: compliance-as-code 9aa3b7038e537ec8].

## Examples

A first exercise builds a service account the careful way. Create a group with a fixed number, create the account with a fixed number, a nonstandard home and a nologin or specific shell, and set ageing in the same sitting. Run the creation commands against a scratch root with the root-directory option, then read the resulting passwd and shadow lines field by field and check each against the formats above. This is what the lab does.

A second exercise is delegation with the narrowest rule that works. Write a drop-in that lets one group restart one service as root without a password, set it to mode 0440, validate it with visudo -cf, then test as a member and as a non-member with sudo -l, which lists what the caller may run. Then try to widen the rule by passing extra arguments and see what the pattern really permits.

A third exercise is ageing audit: use chage -l on every human account, list those whose maximum is unlimited, and decide which to fix. Combine with a search of the shadow file for empty or unlocked password fields.

A failing example: add a user to a group with usermod -G and no -a, and notice the old supplementary groups vanish. Another: edit the sudoers file with an ordinary editor, introduce an unbalanced quote, and observe that sudo then refuses everything, with the only recovery through the superuser account or a rescue boot. A third: remove an account with userdel without -r, create another with the same number and read the previous owner's home directory as the new user.

## Related problems and ideas

Neighbouring problems include authentication policy beyond ageing, such as minimum length, complexity, history, lock-out after failed attempts, and multi-factor devices, all of which live in the pluggable authentication configuration and not in the account files. Related is privilege boundaries inside a process: the capability mechanism splits the superuser's power into pieces that can be granted separately, and the setpriv program can launch a command with only selected pieces [src: man-pages 2b85b0c4422256ab]. Another neighbour is secrets hygiene: files such as netrc hold credentials in the clear and must not be readable by group or others, a rule that compliance scanners check [src: compliance-as-code d6cdf3d3bb075f74].

Ideas for practice: prefer groups to individual rules, so that on- and off-boarding is a membership change; keep drop-in files small and named for their purpose; always validate before saving; treat unlimited-ageing and empty-password findings as defects; reserve numeric ranges for services and people separately; and script account creation so that every machine gets the same numbers. Where several machines must share identities, use a directory service or generate the files from one source, since numeric identifiers that differ between hosts break shared storage quietly.

## Active research

Work on local privilege management continues along several lines. One is replacing the set-user-identifier model with short-lived, scoped authority: systemd's run0 command asks the service manager to start a command as another user, with no set-user-identifier binary involved, and the polkit framework mediates the request [src: archwiki 3ea71e826d9e454a]. Another is memory-safe reimplementations of sudo and the shadow tools, motivated by the long history of bugs in privileged parsers. A third is passwordless authentication through hardware keys and certificates, which changes what ageing means. A fourth is formal analysis of policy languages so that a rule set can be proven to grant no more than intended, and tools that convert a policy into a normalised form for comparison already exist in the sudo distribution, as the compliance scanners that use them show.

## Future direction

Expect the local account files to remain, since the kernel interface that uses numbers is unchanging, but expect administrators to touch them less. Declarative provisioning at first boot, directory-managed rules and image-based systems will create accounts from data and check them continuously. Credentials will increasingly be short-lived and hardware-bound, with password ageing retained mainly for legacy accounts. Delegation will move toward narrower, auditable, time-boxed grants, possibly via the service manager instead of a privileged binary. The skills in this topic stay relevant because every one of those systems ends by writing a number into a process and a name into a log, and the administrator who understands the underlying fields can read what any of them did.
