# Describing and ordering the work of a machine: systemd units, targets, dependencies and overrides

## Define the problem

A booted machine is a graph of things that must be started in a sensible order, kept running, restarted when they fail, and stopped cleanly: file systems mounted, devices configured, network brought up, daemons launched, scheduled jobs armed. Somebody has to write down what each thing is, what it needs and what must come before it, and something has to turn that description into actions, quickly and repeatably, on thousands of different machines. The description must also be changeable by the local administrator without being lost when a package is upgraded, and it must be possible to ask afterwards why something started late or not at all.

Before a single manager took on this job, the answer was a pile of shell scripts run one after another, each with its own conventions for start, stop and status, and each responsible for its own supervision. The problem therefore has two halves: a declarative language for units of work and their relationships, and a manager that resolves the relationships into a transaction and runs it in parallel. This topic covers the language and the administrative habits that go with it, from unit types and dependencies to drop-in overrides and the commands that verify them. Boot-time targets and rescue modes are the neighbouring topic.

## History and approaches

The traditional System V approach numbered scripts by run level and executed them in sequence. It was simple and transparent but slow, because parallelism had to be arranged by hand, and fragile, because a script that forgot to supervise its daemon left no record of failure. Intermediate systems added dependency headers inside scripts so that a tool could compute an order, and event-based initialisers started services when hardware or other services announced themselves. Each helped, but each kept the script as the unit and the shell as the supervisor [src: debian-handbook 8383284510b38bd5].

The systemd project replaced the script with a declarative unit file and the sequential runner with a manager that becomes the first process on the machine. Its design ideas were socket activation (create the listening socket first and start the daemon when traffic arrives, which removes ordering problems between clients and servers), tracking every service in its own control group so that no stray child can escape, and describing relationships between units rather than a total order [src: rocky-docs 2eba0e14e56e9e7d] [src: debian-handbook 1aff509006591d1d]. The adoption was uneven. It was embraced by most large distributions, criticised for its scope and for departing from the one-tool-one-job tradition, and it left a compatibility layer that still runs legacy scripts. The disagreement was partly technical, about complexity and portability, and partly cultural, about how much a single project should own.

Several approaches to configuration were tried along the way. Early on, administrators edited the vendor's unit files directly, which worked until a package update replaced them or produced a conflict. The later and now standard approach is to leave vendor files in the packaged directory and layer local changes in drop-in directories, where small files override single settings. The related lesson learned from earlier systems is that a configuration that is merged from fragments needs a tool that shows the merged result, which is why the analyzer and the cat subcommand exist.

## Current state

The unit is the unit of configuration. Its type is given by its suffix: service, socket, target, device, mount, automount, swap, timer, path, slice and scope. A service describes a supervised process; a socket describes a listening endpoint that triggers a service; a timer arms another unit at a time; a path watches for file-system changes; a mount, automount and swap represent file systems and swap areas (usually generated from the fstab file); a slice is a node in the control-group tree used for resource control; a scope groups processes the manager did not start itself; and a target is a named synchronisation point without behaviour of its own. Instances of a template, written name@instance.service, let one file serve many cases, with the specifier %i expanding to the instance string.

Unit files are looked up in a fixed list of directories, with earlier entries winning. For the system manager the order, roughly, is the control directories under /etc/systemd/system.control and its runtime twin, transient units in /run/systemd/transient, then /etc/systemd/system, then /run/systemd/system, then generated units, and last the vendor locations: /usr/local/lib/systemd/system, then /usr/lib/systemd/system. The user manager has a parallel list under ~/.config/systemd/user and the XDG directories. The environment variable $SYSTEMD_UNIT_PATH overrides the list [src: man-pages 8bd44ea5a8f68ac2] [src: man-pages 5ff35b5eef3fb790]. Drop-ins live in a directory named after the unit with the suffix .d (for example nginx.service.d) and contain files ending in .conf. Drop-ins in /etc beat those in /run, which beat those in /usr/lib, and when several fragments have distinct file names they are sorted alphabetically as a single set, whichever directory holds them, so a name starting with a high number such as 90 applies last. A top-level directory such as service.d applies to every unit of that type, and for aliases the drop-ins of all names are read [src: man-pages 870ed81f05005297].

A unit file is an ini-style document with up to three sections that matter here. The [Unit] section carries generic information and relationships: Description= (a noun phrase used in status messages), Documentation=, the dependency options, and conditions. The [Service] section configures the process: Type=, ExecStart= and its companions ExecStartPre=, ExecStartPost=, ExecReload= and ExecStop=, Restart= with RestartSec=, timeouts, and the execution environment keys documented on the exec page, such as User=, Group=, WorkingDirectory=, Environment= and EnvironmentFile=. The [Install] section is used only when the unit is enabled or disabled, and holds WantedBy=, RequiredBy=, Alias= and Also= [src: man-pages 33d74726723892ed] [src: man-pages 96ae521c06b6db50].

Type= is the setting that most often decides whether a service behaves. The accepted values are simple, exec, forking, oneshot, dbus, notify, notify-reload and idle. With simple, the manager considers the unit started right after fork, before the binary is even executed, so a missing binary or a nonexistent user is still reported as success by the start command. With exec the manager waits until the binary has been run, which catches those errors and is the recommended choice for long-running daemons. With forking the main process is expected to exit after starting the real daemon, which the manager then adopts. The notify types wait until the service calls the sd_notify interface, and oneshot waits for the process to finish and suits tasks, not daemons [src: man-pages 9367e1477a4af7c2].

Dependencies come in two independent families that are easy to confuse. Requirement dependencies say what must also be active: Wants= is weak (a failing dependency does not fail this unit), Requires= is strong (if the dependency fails to start, this one fails, and stopping it stops this one), BindsTo= is stronger still, PartOf= propagates stop and restart in one direction, and Conflicts= says two units cannot be active together. Ordering dependencies, Before= and After=, say nothing about whether the other unit is pulled in; they only fix the sequence when both are in the same transaction. A unit that needs another running first needs both a requirement and an ordering line, the most common mistake being to write only one. Weak dependencies can also be created from the outside by placing a symlink in a .wants directory, which is exactly what enable does. Conditions such as ConditionPathExists= skip a unit silently when false, while their Assert counterparts fail it loudly. Many dependencies are added automatically from other settings, for example a mount depends on the units for its device and a service with Type=dbus acquires a dependency on the bus socket [src: man-pages 0646dfccd16ae427] [src: archwiki 5b819547af3ea0dc].

Targets are the grouping mechanism. A target such as multi-user.target pulls in the services of that state through its Wants and .wants directories, and orders itself after the ones it needs, and several well-known targets exist to anchor ordering: network.target means only that network management has started, whereas network-online.target waits until a connection is actually configured, and a service that must reach the network at start-up should order itself after the latter and want it. The difference is documented in the vendor manuals, and confusing the two produces services that start before an address exists [src: rhel-10-docs 3711f4dd2026361b] [src: rhel-10-docs bf12f21588d7d15c] [src: rocky-docs c72f2704379e51cb].

The command systemctl is the control interface. The state verbs are start, stop, restart, reload, try-restart and reload-or-restart; status shows state, the main process, control group and recent log lines; is-active, is-enabled and is-failed return exit codes for scripts; and list-units, list-unit-files and list-dependencies enumerate. Persistent settings use enable (create the symlinks named in [Install]), disable (remove them), mask (link the unit to /dev/null so that it cannot be started even as a dependency) and unmask; the --now flag combines enable or disable with start or stop, and a --root option applies the symlink changes to another directory tree. After a unit file or drop-in is changed on disk the manager must be told with daemon-reload. The edit subcommand creates a drop-in called override.conf in the right place and reloads automatically, edit --full copies the whole unit into /etc/systemd/system for modification, and --runtime puts the change in /run so that it disappears at reboot. The cat subcommand prints a unit with all its fragments in effective order, and show prints resolved properties [src: rhel-10-docs 3f0ae3118b37c5b7] [src: archwiki 670f27aba240920e].

A subtlety for drop-ins is how list-valued settings behave. Assigning to a list such as ExecStart= in a drop-in adds an entry, and since a normal service may have only one ExecStart, the drop-in must first assign it an empty value to clear the vendor's line and then give the new command. Scalar settings like Restart= or TimeoutStopSec= simply replace the earlier value. To check files, systemd-analyze offers verify (load the named files and report syntax errors, unknown keys and missing executables), critical-chain (the sequence that delayed a unit), blame (the time each unit took), plot and dot (graphs), and cat-config (print the merged configuration of a configuration file or unit with its drop-ins) [src: man-pages 98a42ac1c0d7d6dc].

## Assessment: the good, the bad and the ugly

The good is that the language is regular, introspectable and parallel. One syntax covers daemons, mounts, timers and sockets; the manager knows the dependency graph and can print it; failures are recorded with the exit status and the logs of that unit alone; and restart policy, sandboxing and resource limits are keys in the same file instead of code in a script. The drop-in mechanism gives a safe local override path, and the analyzer tooling makes whole classes of mistakes visible before a reboot.

The bad is the learning surface. There are hundreds of keys spread across several manual pages (unit, service, exec, kill, resource-control), and the interaction of requirement and ordering families is subtle. Defaults surprise: a unit without ordering lines may start in parallel with what it needs; a simple service reports success when its binary is missing; Requires without After starts both at once. Documentation for a given option is tagged with the version that added it, so a unit written for a recent manager may be silently ignored by an older one, since unknown keys are only warned about. Debugging a hang at boot means reading a graph and sometimes a cycle that the manager resolves by deleting a job.

The ugly parts are mostly operational. A dependency cycle between units is broken arbitrarily, producing different behaviour at each boot. Masking a unit that a dependency needs causes confusing failures. Editing a vendor file in place is overwritten at the next update, leaving the machine apparently configured but not so. Time-of-check changes, such as replacing a unit file without a reload, leave the manager running the old definition while the file on disk shows the new one, and the status line reports that the unit file changed on disk. Services that rely on network-online ordering can hang the boot if the network never comes up. And the manager's size and authority mean a bug there is a bug in the first process of the system.

## Applications beyond this domain

The unit model generalises beyond services. Container and virtual-machine management uses the same files: the libvirt daemon uses socket activation to start on demand and starts per-driver sockets from units [src: libvirt-docs 33f148ab5eaadc96]. Cluster resource managers face the same graph problem under different names, with constraint types such as ordering and colocation between resources [src: clusterlabs-docs ff2e96b54533aa89]. Networking projects install helper units for mounting special file systems or applying kernel settings once a link is up, as in the examples for mounting the BPF file system with a mount unit and for reapplying network sysctls after interfaces appear [src: cilium-docs e2c8f944b30a0afe] [src: compliance-as-code f5d6ae8e7e974fe7]. Embedded and image-based systems build minimal images whose first process is the manager with a handful of units, which is the shape used in training material for custom Linux builds [src: bootlin-training 56fa0a2558aa87b9].

Outside Linux, build tools such as make and package dependency solvers deal with the same pair of questions: what is required, and in what order. Declarative infrastructure tools reconcile desired state with actual state in the way the manager's start jobs do, and workflow engines express a graph of tasks with weak and strong edges. The lesson that requirement and order are separate axes recurs in every one of them.

## Examples

A first exercise is to read a real unit. Pick a common daemon, print it with systemctl cat, and annotate each key: what the process is, how it is started, when it counts as started, what it wants and what it is ordered after, and which target pulls it in. Then use list-dependencies in both directions and compare with the file.

A second exercise is a drop-in override. Take a vendor unit, set a different restart policy, a shorter stop timeout and an environment variable in a drop-in, and confirm the merged result with systemctl cat and systemd-analyze cat-config. Then reset ExecStart with an empty assignment followed by a new command, and note what happens if the empty line is omitted. The lab for this topic does this in a scratch root with the --root option.

A third exercise separates requirement from ordering. Create two small units where B wants A, first with no ordering, then with After=, and use systemd-analyze plot or the journal timestamps to see the difference. Then change Wants to Requires and make A fail to see propagation.

A fourth exercise is a service that needs the network. Compare network.target and network-online.target by logging the address at start and rebooting a test machine.

A failing example is a unit whose ExecStart uses a relative path, which the manager refuses; verify catches it. Another is the Type=simple service whose binary is missing, which starts "successfully" and then fails; switching to Type=exec exposes the error at start. A third is editing a unit and forgetting daemon-reload.

## Related problems and ideas

Neighbouring problems include timers and scheduled jobs, the boot sequence and rescue modes, logging, resource control through slices, and sandboxing options such as filesystem protection and syscall filtering. Template units and generators address the many-similar-things problem: a generator turns another configuration file, such as fstab, into units at boot. Socket activation and path activation are patterns for starting work on demand. Transient units, created by systemd-run, run a command as a unit without a file, which is handy for one-off resource limits.

Ideas for practice: never edit files under /usr/lib; use systemctl edit; always add both a requirement and an ordering line when one unit needs another running; prefer Type=exec or notify over simple; prefer WantedBy=multi-user.target for ordinary services; run systemd-analyze verify in review or CI; keep drop-ins small, named for their purpose, and numbered where order matters; and use the status output and the journal for the unit before searching further.

## Active research

Work on the service manager focuses on safer defaults and faster, more reproducible boots. Sandboxing options keep expanding, and an analyzer subcommand scores a service's exposure so that hardening can be measured. Image-based and immutable systems push the manager toward reading configuration from sealed, verified images, with factory defaults separated from local state. Efforts on boot-time analysis, parallel start of mounts, and integration with measured boot and secure attestation are active. Another strand is declarative definition of whole systems, where unit files are generated from a higher-level description and checked against the same analyzer. Alternative managers, often smaller and focused on containers, continue to explore different trade-offs between feature surface and simplicity.

## Future direction

Expect the declarative model to keep absorbing system functions, so that more of a machine's behaviour is a unit or a drop-in, and expect tooling to shift from hand-edited files toward generated and verified ones. Hardening will become the default posture: services will be expected to declare their sandbox, and baselines will check it. Configuration will increasingly live in layers, a read-only vendor layer, an administrator layer in /etc and a runtime layer in /run, and the habits taught here, override with drop-ins, verify before reload, separate requirement from order, will carry over unchanged to those layers.
