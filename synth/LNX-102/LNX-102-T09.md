# Matching the machine to the workload: tuned profiles and dynamic system tuning

## Define the problem

A general-purpose kernel ships with general-purpose defaults, and general-purpose is a compromise. A database server wants huge pages, a tight disk scheduler and a processor that never drops into a low-power state. A laptop wants the opposite. A virtualisation host wants a different memory policy again, and a latency-sensitive network appliance wants interrupts and scheduling pinned away from its worker cores. Each of these needs a dozen or more coordinated settings spread over the kernel's parameters, the processor governor, device attributes, boot arguments and sometimes a helper script. Setting them by hand once is feasible; setting them consistently on a fleet, switching between them, undoing them, and proving they are still applied is not.

The administrative problem is therefore one of packaging and verification. Settings that belong together must be named as a bundle, applied as a unit, applied again after a reboot, replaced cleanly by another bundle, and checked for drift when something else overrides one of them. The topic covers the TuneD service and its tooling, which is the answer given by Red Hat-family distributions, and sets it beside the plain mechanisms it is built on: sysctl files, sysfs attributes and kernel arguments.

## History and approaches

Performance tuning began as folklore. Administrators kept notebooks of sysctl lines, shell snippets that wrote to files under /sys, and boot arguments, and applied them by editing start-up scripts. The scripts had no common structure, no way to undo, and no way to tell whether a given setting was still in force. Vendors published tuning guides, long documents that told administrators which values to change for a database or a virtual host, and the guides went stale as kernels changed their defaults.

The first structured answer on the Red Hat family was a set of tuning profiles delivered by a daemon, TuneD. A profile is a directory with a configuration file in ini format that describes the target state in terms of plugins, one for each subsystem: processor, disk, network card, kernel parameters, device attributes, boot loader arguments and others. The daemon loads a profile, applies it, and on request restores the previous state. A dynamic mode was added so the daemon could monitor load on disks, networks and processors and adjust power-saving behaviour as the machine's activity changed [src: rhel-10-docs 8278741e81956dee].

Other approaches existed and still do. Pure sysctl drop-ins are simpler and sufficient when only kernel parameters matter. Boot-time tuning goes on the kernel command line. Desktop environments use a power-profile daemon with a few named modes. Cluster platforms have their own operators that apply node tuning declaratively. Configuration-management tools can enforce each setting individually, with no daemon. The partial successes are clear: TuneD made tuning shareable and verifiable, but a profile cannot do what the kernel does not expose, some effects need a reboot, and the dynamic mode is a heuristic that is not suited to every workload.

The failure mode that shaped the guidance is conflicting controllers. If TuneD, a power-profile daemon, a hand-written sysctl file and a hypervisor guest agent all try to set the same value, the last writer wins and nobody notices. Security guidance added a different caution: the daemon is functionality beyond what many systems need, and a hardened baseline asks that the package be absent unless an operational requirement is documented [src: disa-stig 231e3c869a175a96] [src: disa-stig 1046ef09ab2a753a].

## Current state

TuneD runs as a service, tuned, with the administrative command tuned-adm. The main commands are these. tuned-adm list prints the available profiles with a one-line summary each. tuned-adm active prints the profile currently applied. tuned-adm profile NAME activates a profile (several may be named to merge them). tuned-adm recommend prints the profile suggested for this hardware, chosen by rules in the profile library, for example one for virtual guests and another for physical servers. tuned-adm verify compares the current system state with the active profile and reports whether the settings match. tuned-adm profile_info shows what a profile contains. tuned-adm off turns tuning off and reverts what the daemon changed. The active profile name is stored in a file under /etc/tuned, so the choice survives reboots, and enabling the service at boot is a separate step done with systemctl enable --now tuned [src: rocky-docs e92546fa16d2eff0] [src: rocky-docs a218c98bcc463b45].

Profiles live in two directories. Vendor profiles are installed under /usr/lib/tuned, one directory each, with a tuned.conf inside; local and customised profiles belong under /etc/tuned, and when a local directory carries the name of a vendor one, the local copy wins. The standard set includes balanced (the default for general use), throughput-performance (for server workloads: high processor performance, larger read-ahead, settings that favour bandwidth), latency-performance (lower latency by keeping processors out of deep sleep states), network-throughput and network-latency (both build on the first two with network-specific kernel parameters), virtual-guest and virtual-host (for virtual machines and for the hosts that run them; the host profile turns on transparent huge pages and adjusts scheduling), powersave, accelerator-performance, and for specialised needs cpu-partitioning and realtime, which come from separate packages. The virtualisation guidance singles out virtual-host as the basic profile for a hypervisor and cpu-partitioning for latency-sensitive guests [src: rocky-docs a218c98bcc463b45].

A profile file has sections. [main] holds summary= (the one-line description) and include= (the name of another profile this one extends, applied first, so the child needs to state only its differences). [variables] defines named values, which can be loaded from external files and referenced as ${name} elsewhere. Then one section per tuning plugin. The common ones are [sysctl] (kernel parameters as key=value, the same keys as /proc/sys), [sysfs] (values written to files under /sys, for example block device attributes), [cpu] (the governor, for instance governor=performance, plus energy and performance bias options), [vm] (transparent huge pages), [disk] (read-ahead and scheduler per device), [net] (offload and coalescing), [modules] (module options), [bootloader] (extra kernel command line words through cmdline=, which take effect after a reboot), [scheduler] (processor affinity and priorities of tasks), [script] (a shell script run on start and stop) and [systemd]. Plugin sections can have a name suffix and a type and device filter to target a subset of devices, and an option value can be prefixed to add or remove tokens from an existing value, which lets a child profile append to an inherited list instead of replacing it. The plugin reference lists monitoring plugins (disk, net, load) that feed dynamic tuning, and tuning plugins that each take parameters populated from the profile [src: rhel-10-docs 8278741e81956dee].

A custom profile is usually the smallest useful artefact. Create a directory under /etc/tuned, write a tuned.conf whose [main] section includes a vendor profile, add the few settings to override, run tuned-adm profile on it, and confirm with tuned-adm active and tuned-adm verify. Some profiles need a variables file before activation: the cpu-partitioning profile reads a file in /etc/tuned in which the administrator sets isolated_cores and no_balance_cores, then the profile is activated and the machine rebooted so the kernel arguments take effect [src: rocky-docs 300f607d28c83aaa]. Because bootloader settings need a reboot, a profile that changes them is the one place where tuned-adm verify may legitimately report a pending difference until the next boot.

The RHEL 10 objective in the course scope concerns this workflow: select, apply, verify and customise profiles. The practical points are the same as on earlier releases, and two details are worth checking against current documentation (to verify): the list of shipped profiles changes between releases, and the integration with desktop power-profile interfaces has been reworked in recent versions. The skill to retain is the method: list, recommend, activate, verify, and read the profile to know what it really changes.

Tuned sits on top of the plain mechanisms, and those remain useful on their own. A single setting such as transparent huge pages can be changed at runtime by writing always, madvise or never to /sys/kernel/mm/transparent_hugepage/enabled, made persistent by a kernel argument, a unit that writes the file at boot, or a profile; the vendor manual lists all four options and notes that a runtime write does not survive reboot [src: rhel-10-docs 3e760cc36ac80b5a]. Network packet-drop guidance similarly offers profiles for persistence and tells the administrator to run the verify command because manual changes or other services may have overridden the values [src: rocky-docs e92546fa16d2eff0].

## Assessment: the good, the bad and the ugly

The good is the packaging. A profile is a small text file that names a workload, can be reviewed, versioned and shipped to a fleet, and applies a coordinated set of changes through one command. The include mechanism keeps local profiles short, the verify command makes drift visible, and the off command makes experiments reversible. Vendor-supplied profiles encode expert knowledge for common workloads, so a sensible baseline is one command away.

The bad is that a profile is only as good as its match to the workload. The names promise more than they deliver: throughput-performance is a set of reasonable defaults, not a guarantee, and a profile that helps one benchmark can hurt another. Effects are hard to attribute, because a profile changes many values at once. Some changes need a reboot or only affect devices present at activation time. Dynamic tuning adds a monitoring loop whose behaviour is heuristic. There is also overlap with other agents, such as power-profile daemons, guest agents and orchestration operators, and without discipline they overwrite each other.

The ugly is the combination of an invisible controller and a security stance. A daemon that rewrites kernel parameters and power states in the background can change a machine's behaviour without anyone changing a file that a reviewer would see, and a hardened baseline treats the package as unnecessary attack surface; the compliance check can fail a system simply for having it installed unless the requirement is documented [src: disa-stig 231e3c869a175a96]. Mistakes can also be severe: a wrong isolated-cores list can starve the operating system of processors, and a profile that disables power saving can raise heat and energy cost across a whole rack.

## Applications beyond this domain

The idea of a named, versioned bundle of tuning settings appears across infrastructure. Cluster platforms use node tuning operators that render profiles to nodes, and virtualisation management systems document performance profiles for hosts and guests. Some observability guidance for virtual-machine platforms lists the metrics that justify a profile change, because tuning without measurement is guessing [src: kubevirt-user-guide 1e46071781855220]. Database vendors and storage appliances publish "recommended settings" pages that are, in effect, profiles by another name, and tools that audit hosts against them are the analogue of the verify command.

The hardware side has the same structure: processors expose performance and energy preferences, memory systems expose huge-page and compaction policies, and network cards expose offload and interrupt moderation, and each ecosystem has a high-level knob that sets several low-level ones at once. Even build and compiler flag sets are profiles of a sort: optimisation levels are named bundles of many individual switches, and a reader of the compiler's manual sees the same tension between a convenient preset and the individual options [src: man-pages 0fdab8a5bafefb8a].

## Examples

A first exercise is to survey. Install the package on a test machine, run tuned-adm list and tuned-adm recommend, and read the tuned.conf of the recommended profile and of the one it includes. Make a table of which plugin sections each uses and which keys it sets.

A second exercise is to measure the effect of a change. Choose a simple workload, such as a repeated file copy or a memory-heavy loop, record its time under balanced, then under throughput-performance and latency-performance, and note which settings differ, with tuned-adm verify between runs. The goal is to see that effects are workload-dependent.

A third exercise is a custom profile: create a directory under /etc/tuned, include a vendor profile, override two sysctl keys and the processor governor, activate it, confirm that the keys are set in /proc/sys, and then switch to another profile and confirm they revert. The lab for this topic writes the profile in a scratch directory and parses it.

A fourth exercise provokes drift: activate a profile, change one of its sysctl values by hand, run verify and read the report, then re-apply and discover what changed it.

A failing example is a profile that includes a name that does not exist, so activation fails with a clear error. Another is a bootloader line added without a reboot, leaving verify reporting a mismatch. A third is a system on which the package is installed but the service is not enabled, so after a reboot the machine silently returns to defaults.

## Related problems and ideas

Neighbouring topics are kernel parameters and modules, which are what most plugins write; control groups and service-level resource limits, which are a finer-grained alternative for individual services; boot arguments and the initial image; power management; and capacity planning and measurement. The idea of dynamic versus static tuning recurs in autoscalers, adaptive query planners and congestion control, and the lesson is similar in each case: dynamic behaviour must be observable and bounded.

Ideas for practice: begin from the recommended profile and change the least; prefer a custom profile that includes a vendor one to editing the vendor one; record why each override exists; verify after every activation and after every reboot; keep one controller per setting; test power-hungry profiles for heat and cost; remove the daemon on machines where policy forbids it; and measure before and after with the workload that matters.

## Active research

Research and engineering in this area focus on automatic and safe tuning. Machine-learning-based tuners search the parameter space of databases and kernels for settings that improve a measured objective, with the difficulty that evaluation is slow and noisy and that gains are rarely portable between workloads. Intent-based approaches let the user state a target such as low latency or low energy and derive the settings. Work on energy-aware scheduling, on processor performance interfaces that give the hardware hints instead of fixed governors, and on pressure-stall metrics as inputs to tuning loops is active. There is also work on verifying configurations against a declared profile at fleet scale, and on detecting drift through telemetry.

## Future direction

Expect tuning to move from hand-chosen bundles toward measured, closed-loop control, with profiles becoming the starting point and telemetry-driven adjustment doing the rest, and expect desktop and server stacks to converge on shared interfaces for choosing a performance or power mode. Hardened baselines will keep demanding that such daemons be justified, so administrators will increasingly need to state the requirement and prove the effect. The method in this topic will hold up: pick a bundle, apply it, verify it, understand each setting in it, and keep exactly one authority over every value.
