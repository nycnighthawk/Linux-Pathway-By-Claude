# Bisect and fix a planted regression

## Define the problem

Between two releases a feature stops working and thousands of commits sit in between. Reading them is hopeless. The problem is to find the exact commit that introduced the regression efficiently and reliably, understand why it broke the behaviour and fix it in a way the maintainers will accept, with a test.

## History and approaches

Regression hunting began as manual narrowing. Version control systems added automated binary search, and git bisect made it routine. The kernel community added reporting practices for regressions and tracking by dedicated people, plus the rule that regressions in user-visible behaviour take priority.

## Current state

The investigator writes a reproducible test that returns pass or fail, marks a known good and a known bad commit, and lets bisect check out midpoints. Each step builds and runs the test; the result halves the range, so a thousand commits need about ten steps. Untestable commits (build failures unrelated to the bug) are skipped. After the culprit is found, the author reads the change, reproduces the failure with a minimal case, writes the fix, adds a regression test, and sends it with a Fixes tag naming the culprit and a report tag if someone reported it.

## Assessment: the good, the bad and the ugly

Bisection is powerful and nearly mechanical. It fails when the test is flaky, when the bug needs a combination of changes, when many commits do not build, or when a bad merge hides the culprit. The ugly part is time: every step is a kernel build and boot. Automation in a virtual machine with cached builds reduces it.

## Applications beyond this domain

The same technique applies to any versioned system: finding a performance regression in a database release, a misconfiguration in a configuration repository, or a bad data change in a versioned dataset.

## Examples

A worked example: a planted regression makes reads from a device return the wrong length. A script boots a kernel in QEMU and runs a small program; bisect finds the commit in eight steps, which changed a loop bound. The fix restores the bound and adds a test for the boundary case. A failing example: the first test script sometimes passed on the bad commit because of a race; making it run ten times fixed the bisect.

## Related problems and ideas

Related topics are flaky test management, automated bisection bots, delta debugging and regression tracking in the kernel.
