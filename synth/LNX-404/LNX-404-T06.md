# Multi-day syzkaller campaign

## Define the problem

Bugs in the kernel's system call interface are often found by input no human would write. A fuzzer that generates sequences of system calls can run for days and find crashes that unit tests never would. The problem is to set up and run such a campaign against a kernel build, triage what it finds, and report real bugs with reproducers.

## History and approaches

Kernel fuzzing started with simple random call tools. Syzkaller brought coverage guidance, a description language for system calls and automatic reproducer generation, and the public syzbot service has run it continuously on many trees, reporting thousands of bugs. Sanitizers in the kernel (KASAN, KCSAN, UBSAN) turn silent faults into crashes.

## Current state

A campaign has a manager that controls virtual machines, a kernel built with coverage and sanitizers, and a set of enabled system call descriptions. The manager starts VMs, fuzzes, restarts on crash and stores logs and reproducers. Over days, the investigator monitors coverage growth and the crash list, deduplicates reports by title, minimises reproducers and checks whether a crash is already known. Real findings are reported privately or publicly according to security impact.

## Assessment: the good, the bad and the ugly

Fuzzing finds serious bugs. Costs are compute time, configuration effort and triage load; many crashes are duplicates or known. The ugly part is reproducibility: some crashes depend on races that appear once.

## Applications beyond this domain

Coverage-guided system fuzzing is used for hypervisors, file systems, network stacks and firmware.

## Examples

A worked example: a campaign enables the descriptions for a subsystem, runs three days, and reports a use-after-free with a reproducer. A failing example: a misconfigured kernel without coverage ran for two days with no growth.

## Related problems and ideas

Related topics: KASAN and KCSAN, kernel CI, static analysis, and fuzzing hypervisors.

## Active research

Active work covers fuzzing for Rust code, better descriptions and use of large language models for descriptions (to verify).

## Future direction

Expect broader subsystem coverage and more integration with development workflows.
