# Driver for a QEMU device with KUnit tests

## Define the problem

Kernel code runs with full privilege and no safety net, so a driver must be developed against hardware that can be restarted, inspected and repeated. Real devices are scarce and costly to debug. The problem is to write a driver for a virtual device in QEMU, test its logic in the kernel's own unit test framework, and show that the pieces that talk to hardware are separated from the pieces that can be tested without it.

## History and approaches

Early drivers were tested by loading them on a spare machine. Emulators such as QEMU let developers define devices in software, and the edu teaching device was added to practise PCI driver writing. Kernel testing grew from ad hoc scripts to kselftest for user-space-visible behaviour and KUnit for in-kernel unit tests that can run on a user-mode build of the kernel or under QEMU. Mocking of hardware access became a common way to test driver logic.

## Current state

The driver binds to the PCI device by identifier, maps its register region, reads an identity register, and exposes a character device or sysfs files. Logic that does not need real registers (argument validation, state machines, timeouts, result decoding) is placed in functions that take an accessor, so KUnit tests can substitute a fake register file. Tests are written as cases with expected results, run by the framework, and reported in the kernel's test output format. The same driver is then loaded in a QEMU guest against the real device model for an integration check, with a user-space program exercising the interface.

## Assessment: the good, the bad and the ugly

Splitting hardware access from logic makes tests fast and deterministic, and finds bugs before the device model is involved. The cost is extra indirection and the discipline to keep it. KUnit cannot test interrupts, DMA or races well; those need the full guest. The ugly part is the gap between a device model and real silicon: QEMU devices are simple and forgiving, and a driver that passes on them may still fail on hardware with timing and errata.

## Applications beyond this domain

The same split of pure logic from register access is used for firmware, embedded drivers, network protocol stacks and file systems, and fake-device testing is used in user-space USB and storage stacks.

## Examples

A worked example: a driver reads the identity register, computes a factorial by writing to a register and waiting for a busy bit to clear, and returns an error on timeout. KUnit cases cover a valid input, an out-of-range input, a device that never clears the busy bit and a wrong identity value. A failing example: a driver that polled forever when the busy bit stuck; the timeout test found it before any hardware did.

## Related problems and ideas

Related topics are kselftest, syzkaller fuzzing, Rust for Linux drivers, and virtio as a standard device interface. Alternatives to a QEMU device include simulation frameworks and hardware-in-the-loop labs.

## Active research

Active work covers wider KUnit use, better fake hardware libraries and Rust abstractions with their own test support (to verify).

## Future direction

Expect more subsystems to require KUnit coverage for new code and more tooling to run it in CI.
