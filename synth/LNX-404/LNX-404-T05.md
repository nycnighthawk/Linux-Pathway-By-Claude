# Run on a real development board

## Define the problem

Emulators hide the details of real hardware: clock trees, regulators, pin multiplexing, timing and firmware. A driver or kernel build must finally run on a physical board. The problem is to boot your kernel on a real development board, get a serial console, load a device tree and verify your driver or change on the actual device, recording what differs from the emulator.

## History and approaches

Early embedded Linux relied on board-specific code compiled into the kernel. The device tree moved hardware description out of the kernel, and bootloaders such as U-Boot standardised boot flows. Cheap boards with serial headers and network boot made experiments practical.

## Current state

A typical setup has a serial adapter for the console, a bootloader that loads a kernel, device tree and root filesystem from network or storage, and a way to recover from a bad kernel (an SD card slot or a network boot fallback). The developer cross-builds the kernel, sets the device tree, boots and reads the console log and the kernel messages, then loads their change and tests it with the real hardware.

## Assessment: the good, the bad and the ugly

Real hardware reveals timing bugs and hardware quirks. It also adds risk: power and wiring mistakes, fragile bootloader setups and slow cycles. The ugly part is documentation gaps and board variants that behave differently.

## Applications beyond this domain

The same board bring-up process applies to embedded products, single-board computer clusters and industrial controllers.

## Examples

A worked example: a driver passes on QEMU but fails on the board because a clock was not enabled in the device tree; the console log shows a timeout and the fix is a node property. A failing example: a wrong serial voltage level damaged an adapter.
