# Profiling and flame graphs

## Define the problem

When a service is slow, intuition about the cause is often wrong. The problem is to measure where time is spent with a sampling profiler on a real workload, present it in a form that makes the hot code visible, and use it to decide what to change. This slice needs a quiet test machine and a repeatable load, so it is practised on shared hardware and recorded as evidence.

## History and approaches

Profilers began as instrumentation (gprof) that distorted behaviour. Sampling profilers using hardware counters and timers (perf, OProfile) reduced overhead, and Brendan Gregg's flame graph visualisation made stack samples readable by merging common stacks into widths proportional to time. eBPF-based profilers added low-overhead continuous profiling.

## Current state

A profile run records stack samples at a fixed frequency while a load generator drives the service, usually with frame pointers or debug information so that stacks resolve. The samples are folded and drawn as a flame graph where width is share of samples. The investigator reads from wide boxes at the top, forms a hypothesis, changes one thing and measures again with the same load. Off-CPU profiles show time spent waiting, and differential graphs compare before and after.

## Assessment: the good, the bad and the ugly

Flame graphs find surprising costs quickly and communicate well. Costs include missing symbols or broken stacks, sampling bias, noisy neighbours that corrupt measurements and the temptation to optimise a wide box that is not the bottleneck for users. The ugly part is measurement discipline: one run proves little, and a change that helps one workload may hurt another.

## Applications beyond this domain

Sampling profiles are used in databases, browsers, games, data pipelines and in cloud-wide continuous profiling.

## Examples

A worked example: a flame graph shows a quarter of samples in a logging call that formats strings that are discarded; guarding the call lifts throughput. A failing example: stacks ended at the first frame because the build omitted frame pointers; rebuilding with them restored depth.

## Related problems and ideas

Related ideas include tracing, latency histograms, USE analysis and performance regression tests in CI.

## Active research

Active work covers continuous production profiling, profile-guided optimisation and standard formats (to verify).

## Future direction

Expect profiling to be always on in production and diff-based checks on pull requests.
