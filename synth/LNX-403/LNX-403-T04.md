# Hardened systemd unit (ProtectSystem, seccomp)

## Define the problem

A service that handles network input will one day be exploited. What matters then is what the attacker can reach: the whole filesystem, every system call, all capabilities. The problem is to run the daemon with the least privilege it needs, using the sandboxing options of the init system rather than editing the program, and to check the result with tools instead of belief.

## History and approaches

Early hardening used chroot and a dedicated user. Linux added capabilities, namespaces, seccomp filters and mandatory access control, but each was awkward to configure per service. systemd exposed these as unit directives: filesystem protections, private temporary directories, system call filters, capability bounding and address family restrictions. A built-in analyser gives each unit an exposure score from those settings.

## Current state

A hardened unit runs as an unprivileged user (often a dynamic one), sets no-new-privileges, makes the system read-only except for named state paths, hides home directories and devices, restricts kernel interfaces, limits address families to what is used, denies writable executable memory when the program allows it, and allows only a system-call group suited to services. Capabilities are dropped, with the one needed for binding low ports given as an ambient capability or avoided by socket activation. The analyser lists remaining exposure and guides further tightening. Each setting is tested by running the service through its normal work and watching logs for denied calls.

## Assessment: the good, the bad and the ugly

These controls are cheap, declarative and reviewable. Costs include breakage when a feature needs a path or call that was blocked, the effort of finding the minimal set, and the false comfort of a good score on a service that still holds secrets. A filter that kills the process on a denied call is hard to debug without auditing mode. The ugly part is that options differ by systemd version, so a unit hardened on one release may fail to load on another.

## Applications beyond this domain

The same least-privilege approach applies to container security contexts, mobile application permissions, browser sandboxes and cloud role policies.

## Examples

A worked example: a daemon moves from a score in the unsafe range to a medium one by adding a dozen directives, with the service state directory declared writable and nothing else. A failing example: enabling a filter that denied a call used by the resolver library made the service die at the first lookup; the logs of the denied call revealed the fix.

## Related problems and ideas

Related topics are SELinux and AppArmor policy, capabilities, Landlock and container runtimes with seccomp profiles. Alternatives are running the service in a container or microVM.

## Active research

Active work covers easier generation of profiles from observed behaviour, Landlock use in services and standardised baselines (to verify).

## Future direction

Expect hardening defaults to become part of vendor packages and the analyser's scoring to evolve.
