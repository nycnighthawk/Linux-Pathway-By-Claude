# Packages: RPM, DEB, Flatpak, OCI

## Define the problem

Software reaches users as a package, and each platform wants its own. A service for several systems must be built once from one source tree and shipped as an RPM for the Red Hat family, a DEB for Debian and Ubuntu, a Flatpak for desktops and an OCI image for containers, with the same version, licence and metadata in all four. The problem is to keep four formats consistent and reproducible without four hand-maintained builds.

## History and approaches

Package managers appeared in the 1990s with tar archives plus scripts, then RPM and dpkg added databases and dependency solving. Flatpak and Snap added sandboxed application bundles with runtimes, and container images gave a portable root filesystem with layers described by the OCI specification. Build services (Open Build Service, Copr, Launchpad) and cleanroom tools (mock, sbuild) made builds reproducible.

## Current state

A single source tree carries the packaging for each format: a spec file, a debian directory, a Flatpak manifest and a Containerfile. Version and licence come from one place, ideally the build system, and a release script checks that all four agree. Builds run in clean environments in CI; the results are signed and published to a repository, a remote or a registry. Container images use multi-stage builds, a non-root user and a pinned base. Package scripts avoid network access and create service users the standard way.

## Assessment: the good, the bad and the ugly

Native packages integrate with the system's updates, signatures and dependency handling; Flatpaks and images ship dependencies privately and so are easy to run and heavy to patch. Costs are four sets of conventions, security update duty for bundled libraries and divergence between formats. The ugly part is drift: a fix in one packaging file never reaching the others, and unsigned or unpinned inputs that make builds unreproducible.

## Applications beyond this domain

The same single-source, multi-format release pattern is used for language packages (wheels, crates), mobile stores, firmware images and cloud machine images.

## Examples

A worked example: a release script reads the version from the build file, checks the spec, changelog, manifest and image label for the same number and fails otherwise. A failing example: the image ran as root and the DEB lacked the service user, so the two behaved differently in production; both now create the same unprivileged user.

## Related problems and ideas

Related topics are reproducible builds, software bills of materials, signing and repositories. Alternatives include language-native distribution and static binaries.

## Active research

Active work covers reproducible builds across distributions, signing with transparency logs and image-based operating systems (to verify).

## Future direction

Expect more image-based delivery, attested builds and tooling that generates several formats from one description.
