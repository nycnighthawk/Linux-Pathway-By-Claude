# Fuzzing and sanitizers in CI

## Define the problem

Programs written in C and similar languages fail on inputs their authors did not imagine, and the failures are often security flaws. Unit tests cover chosen cases; the problem is to explore the space of unchosen inputs automatically and to turn silent memory errors into loud failures. The practical question is how to run sanitizers and a fuzzer on every change so that a regression is caught in review and not in the field.

## History and approaches

Early fuzzing fed random bytes to programs and watched for crashes. Coverage-guided fuzzing (AFL, then libFuzzer and AFL++) added feedback from instrumentation so the fuzzer keeps inputs that reach new code. Sanitizers (AddressSanitizer, UndefinedBehaviorSanitizer, ThreadSanitizer, MemorySanitizer) were compiled into programs to detect memory errors, undefined behaviour and races at run time. Services such as OSS-Fuzz made continuous fuzzing of open projects routine, and CI systems learned to run short fuzzing jobs on pull requests.

## Current state

A fuzz target is a function that takes bytes and exercises the code under test; a corpus of seed inputs is kept in the repository. The build uses coverage instrumentation and sanitizers. CI has two lanes: a quick lane that runs the unit tests under sanitizers and replays the stored corpus and past crash files, and a time-boxed lane that fuzzes for minutes and uploads any crash as an artifact. Found crashes are minimised, fixed and added to the corpus as regression tests. Rust projects use cargo-fuzz and the language's own checks.

## Assessment: the good, the bad and the ugly

Fuzzing finds real bugs cheaply, and the replay lane makes fixes stick. The costs are build time, noise from false positives, targets that are too shallow to reach deep code, and nondeterminism: a crash found by a long run may not appear in a ten-minute job. Sanitizers slow programs and cannot be combined freely. The ugly part is grammar-heavy formats, where random mutation rarely produces valid input without a dictionary or structure-aware mutator.

## Applications beyond this domain

Coverage-guided testing is used for compilers, file format parsers, network stacks, kernels (syzkaller) and smart contract tools; sanitizers are used in browsers and databases.

## Examples

A worked example: a parser crashes on an input with a length field larger than the buffer; the fuzzer finds it in seconds, the minimiser reduces it to a handful of bytes, and the file joins the replay corpus. A failing example: a CI job ran the fuzzer but ignored its exit status, so crashes never failed the build; the job now fails on any crash and uploads the artifact.

## Related problems and ideas

Related topics are static analysis, property-based testing, mutation testing and formal verification. Alternatives to coverage-guided fuzzing are grammar-based generators and symbolic execution.

## Active research

Active work covers structure-aware fuzzing, fuzzing of stateful network protocols, and machine-learning guided mutation (to verify).

## Future direction

Expect fuzzing to be a standard pull request check for memory-unsafe code and more memory-safe rewrites that reduce the need.
