# A C or Rust epoll daemon with sd_notify and socket activation

## Define the problem

A network service has to start when needed, say when it is ready, handle many connections without a thread each, and stop cleanly when asked. Hand-written daemons used to do this with forking tricks, pid files and sleep loops, and each got something wrong: a client connecting during startup was refused, a manager guessed readiness, a restart dropped connections. The problem is to write a service in C or Rust that cooperates with the init system: it accepts a socket handed to it, reports readiness and shutdown state, and serves many clients from one event loop.

## History and approaches

Classic Unix daemons double-forked, detached from the terminal and wrote a pid file; inetd then took the listening socket and started a handler per connection, which was simple but slow. Event loops arrived with select and poll, and Linux added epoll for large numbers of descriptors. systemd generalised the inetd idea: the manager opens the sockets, starts the service when traffic arrives or at boot and passes the descriptors through environment variables, and a small notification protocol over a datagram socket lets the service report ready, reloading and stopping states. io_uring later offered an alternative completion-based interface.

## Current state

The service reads the number of passed descriptors and the target process id from the environment, checks that they refer to it, and uses descriptor 3 onwards as listening sockets. It registers them with an epoll instance in non-blocking mode, accepts in a loop until the call would block, and reads and writes per client with buffers. Once the loop is ready it sends a ready message to the notify socket named in the environment. Signals are handled through a descriptor in the same loop, so a termination request sends a stopping message, closes clients after finishing in-flight work, and exits with status zero. Rust versions use a crate for the event loop; the structure is the same.

## Assessment: the good, the bad and the ugly

The design gives zero-downtime restarts (the socket stays open in the manager while the service restarts), on-demand start, and accurate dependency ordering. The weaknesses are subtle: edge-triggered epoll needs reads until the call would block or data is lost, a slow client can stall a loop unless writes are queued, and a missing readiness message makes the manager wait until a timeout. Debugging is harder than with threads because state lives in the loop. The ugly part is portability: the protocol is specific to systemd and its relatives.

## Applications beyond this domain

The same pattern, a manager that owns the sockets and a worker that adopts them, appears in launchd on macOS, in inetd-style handlers, in container sidecar proxies and in hot-reload designs of web servers.

## Examples

A worked example: an echo daemon passes a listening socket from the manager, serves two hundred test clients from one thread and exits with status zero on a stop request; the readiness message arrives after the loop is registered, not before. A failing example: a daemon sent readiness at the top of main before binding; clients connected during startup and saw refusals, which moving the message fixed.

## Related problems and ideas

Related topics are thread-per-connection and thread-pool servers, io_uring, reactor libraries, and activation by D-Bus or path units. Alternatives to systemd's protocol include supervisor-managed foreground processes in containers.

## Active research

Active work covers io_uring for network servers, async runtimes in Rust and better observability of event loops (to verify).

## Future direction

Expect more services to be written as async runtimes on top of epoll or io_uring and more init-agnostic activation conventions.
