# Keeping a service reachable: HAProxy load balancing and keepalived VRRP

## Define the problem

A single server is a single point of failure and a single ceiling on capacity. To keep a service up while machines are patched or fail, clients must reach a stable address that is always answered by some healthy backend, and the system must notice a dead backend within seconds and stop sending it traffic. Two separate failures have to be covered. The backend may die while the front door is fine, which needs a **load balancer** with health checks. The load balancer itself may die, which needs a **floating address** that moves to a standby. Failure looks like clients that keep timing out on a dead backend, both load balancers believing they own the address (split brain), a failover that works but drops every session, or a standby that was never tested and does not start when needed.

This slice covers HAProxy as a layer 4 and layer 7 proxy and keepalived as the VRRP implementation that moves a virtual IP between two Linux nodes, plus the way the two are combined.

## History and approaches

Early scale-out used round-robin DNS: several A records for one name. It needs no extra box, but clients cache answers and nothing removes a dead address. Hardware load balancers from the 1990s added health checks and a virtual IP, at high cost. For redundancy, protocols such as Cisco's HSRP led to the standard **VRRP** (RFC 3768, revised as RFC 5798 for IPv6), in which routers on a segment elect a master by priority and the master answers for a shared virtual address. On Linux, the Linux Virtual Server project provided kernel load balancing (IPVS), and **keepalived** was written to manage IPVS pools and to add VRRP. **HAProxy**, started by Willy Tarreau in 2000, took the other route: a user-space event-driven proxy that parses requests, offers rich routing and health checks, and became the default software load balancer. Nginx and Envoy add proxy features of their own, and cloud providers sell the same function as a managed service.

The pattern that emerged on plain servers is a pair: **HAProxy on two nodes for balancing, keepalived to float a virtual IP between them**. HAProxy settles which backend serves a request; VRRP settles which node receives the request in the first place.

## Current state

### HAProxy

The configuration file is `/etc/haproxy/haproxy.cfg`, divided into sections: `global` (process-wide settings such as the stats socket and limits), `defaults` (inherited by later sections), `frontend` (what to listen on and which rules apply), `backend` (a pool of servers and a balancing algorithm) and `listen` (a frontend and backend combined) [web: docs.haproxy.org]. A minimal HTTP setup:

```
global
    log /dev/log local0
    maxconn 4000
    stats socket /var/run/haproxy.sock level admin mode 600

defaults
    mode http
    option httplog
    timeout connect 5s
    timeout client  30s
    timeout server  30s

frontend web
    bind 192.0.2.80:80
    bind 192.0.2.80:443 ssl crt /etc/haproxy/certs/site.pem
    option forwardfor
    acl is_api path_beg /api
    use_backend api if is_api
    default_backend app

backend app
    balance roundrobin
    option httpchk GET /health
    server app1 192.0.2.11:8080 check inter 2s fall 3 rise 2
    server app2 192.0.2.12:8080 check inter 2s fall 3 rise 2

backend api
    balance leastconn
    server api1 192.0.2.21:9000 check
```

`mode http` makes HAProxy parse requests and responses, enabling routing by path, host or header; `mode tcp` forwards bytes untouched, which suits databases, TLS passthrough and anything that is not HTTP. Balancing algorithms include `roundrobin`, `leastconn` (good for long sessions), `source` (hash of the client address), `uri`, `hdr(name)` and `random`; cookies or stick tables provide session persistence. `check` enables health checks; `inter`, `fall` and `rise` set the interval and how many failures or successes change the state. A check can be a plain TCP connect or an HTTP request through `option httpchk`. `option forwardfor` adds the client address in a header because the backend sees the proxy's address, and the PROXY protocol does the same for non-HTTP traffic.

Operations: `haproxy -c -f /etc/haproxy/haproxy.cfg` validates the file; `systemctl reload haproxy` starts new workers and lets old ones finish their connections; and the stats socket answers commands such as `show stat`, `show servers state` and `set server app/app1 state drain`, for example through `socat`. On an SELinux system a proxy that connects to backends on unusual ports needs the `haproxy_connect_any` boolean, which security baselines report if it is left on [src: compliance-as-code 78f2137fbcd01d2e], so prefer labelling the ports with `semanage port`.

### keepalived and VRRP

VRRP runs as IP protocol 112, sent to multicast 224.0.0.18 (ff02::12 for IPv6), by default every second. The router with the highest priority (1 to 254; 255 is the owner of the address) is master and holds the virtual router's MAC address and the virtual IP; the others are backups and take over when advertisements stop for about three intervals. Nodes in one virtual router share the same `virtual_router_id` (1 to 255 on a segment). A configuration pair in `/etc/keepalived/keepalived.conf`:

```
vrrp_script chk_haproxy {
    script "/usr/bin/pgrep haproxy"
    interval 2
    weight -30
    fall 2
    rise 2
}

vrrp_instance VI_1 {
    state BACKUP
    interface eth0
    virtual_router_id 51
    priority 100
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass s3cret
    }
    virtual_ipaddress {
        192.0.2.80/24 dev eth0
    }
    track_script {
        chk_haproxy
    }
    notify_master /usr/local/bin/vip-up.sh
}
```

`state` is only the initial state; the priority decides. The second node uses a lower priority. The tracked script lowers the priority by its `weight` when the check fails, which lets the standby win if HAProxy dies on the master. The notify hooks (`notify_master`, `notify_backup`, `notify_fault`) run scripts on each transition [web: keepalived.readthedocs.io]. `nopreempt` (with state BACKUP on both) stops the original master from taking the address back when it returns, avoiding a second interruption. Where multicast is blocked, as in many clouds, `unicast_src_ip` and `unicast_peer` send advertisements directly. After a failover the new master sends gratuitous ARP, so neighbours learn the new location quickly.

The HAProxy process must be able to bind to the virtual IP while it is on the other node. Set `net.ipv4.ip_nonlocal_bind=1` (or `net.ipv6.ip_nonlocal_bind` for IPv6) on both machines, or bind to all addresses and filter on the VIP in the frontend.

Checks: `ip -br addr show eth0` shows which node holds the VIP; `journalctl -u keepalived` records transitions; `tcpdump -ni eth0 proto 112` shows advertisements.

## Assessment: the good, the bad and the ugly

The good: both programs are mature, small and available everywhere. HAProxy sustains very high connection rates on modest hardware and exposes detailed statistics. VRRP failover takes a few seconds with no client changes, and the same pair works for TCP and HTTP services alike.

The bad: failover loses active connections unless sessions are replicated at the application level; HAProxy has no built-in state sync between nodes. Health checks only see what they test; a check that returns OK for a page that depends on a broken database sends traffic to a useless node. The two nodes need matching configuration, which people manage by hand until they drift.

The ugly: split brain. If the nodes lose sight of each other while both reach the clients, both claim the VIP and a duplicate ARP war follows. Multicast filtering on switches, mismatched `virtual_router_id` values on a shared segment, and VRRP traffic blocked by a host firewall are the usual causes. A tracked script that is wrong (for example matching its own process name) can flap the address constantly.

## Applications beyond this domain

The same two ideas, health-checked pools and a movable address, appear in cloud load balancers and in Kubernetes: a service has a stable address, and endpoints are removed when readiness probes fail. MetalLB announces service addresses with ARP or BGP, which is a VRRP-like answer for bare-metal clusters. Anycast DNS and content delivery networks advertise the same address from many sites with BGP and withdraw it on failure, a wider version of the check-and-withdraw loop. Database proxies and message brokers use HAProxy in TCP mode in front of replicas.

## Examples

A working example: two servers, lb1 (priority 110) and lb2 (priority 100), run HAProxy and keepalived with the files above. Clients use 192.0.2.80. Stopping HAProxy on lb1 makes the script fail twice, the priority drops by 30 to 80, lb2 becomes master within a few seconds and `ip -br addr` on lb2 shows the address.

A failing example: `systemctl restart haproxy` on the standby fails with an error about binding to the VIP. The nonlocal-bind setting is missing; with it set, HAProxy starts everywhere.

A second failing example: failover works in the lab, but in a virtual environment both nodes show MASTER. The hypervisor network drops multicast. Switching to `unicast_peer` addresses restores the election.

## Related problems and ideas

IPVS and keepalived's LVS mode do layer 4 balancing in the kernel; nginx, Envoy and Traefik cover proxying with different strengths; DNS-based global balancing handles several sites; BGP anycast and ECMP route to many nodes at once. Consul, etcd and Pacemaker provide cluster membership and fencing, which solve the split-brain problem VRRP cannot.

## Active research

Work includes lower-latency proxy paths with eBPF and kernel bypass, load balancing that adapts to server load rather than connection counts, and research on consistent hashing that keeps affinity stable while pools change. Standards discussions around HTTP/3 and QUIC change how proxies and balancers handle connection migration.

## Future direction

Expect HAProxy to keep adding HTTP/3, observability and runtime configuration through its API; keepalived keeps its role as the simple floating-address tool while orchestration platforms replace it in large deployments. Track the HAProxy long-term releases and the keepalived changelog.
