# Many routing worlds on one kernel: namespaces, veth pairs, VRF and policy routing

## Define the problem

One host often has to behave as several. A router carries customer networks whose address ranges overlap. A server has a management network that must never be reachable through the data interface. A container platform needs hundreds of isolated stacks, each with its own interfaces and firewall. A multi-homed machine must answer on the link a packet arrived on rather than on the default route. A single global routing table cannot express any of this: overlapping prefixes collide, the lookup depends only on the destination, and every process sees every interface.

This slice covers the four kernel mechanisms that split one machine into separate routing worlds or make the routing decision depend on more than the destination: **network namespaces**, **veth pairs** to connect them, **VRF** (virtual routing and forwarding devices) and **policy routing** with `ip rule` and multiple tables. It is the substrate under containers, many labs in this course, and most multi-tenant Linux routers.

## History and approaches

Classic Unix gave one routing table per machine. Linux 2.1 added **policy routing** (the routing policy database, RPDB), so that rules chosen by source address, incoming interface, TOS or firewall mark select among up to 255 tables; the tables are named in `/etc/iproute2/rt_tables` (the local, main and default tables are built in). That solved multi-homing but not overlap: all tables still shared one set of interfaces, sockets and firewall state.

Isolation came from **namespaces**, introduced for networking around Linux 2.6.24 and completed over the following years as part of the container work. A namespace gives a process its own devices, IPv4 and IPv6 stacks, routing tables, firewall rules, `/proc/net`, port numbers and abstract UNIX sockets [src: man-pages 63ba8e77f8a27b1c]. A physical device belongs to exactly one namespace, so something must connect namespaces to each other and to the outside; the answer was the **veth** pair, a virtual cable whose two ends sit in different namespaces and which can also feed a bridge towards a physical port [src: man-pages 63ba8e77f8a27b1c]. Firecracker's snapshot guide shows the idiom in daily use: one end of a veth stays in the namespace, the other end is given an address in the host namespace and serves as the gateway, which sidesteps clashing guest addresses [src: firecracker-docs 95b59392ff067a7a].

Namespaces are heavy when all you need is separate routing tables on a router. **VRF** (Linux 4.3 and later, based on the l3mdev mechanism) fills that gap: a VRF is a device that owns a routing table, and interfaces enslaved to it route only within that table, while processes, sockets and firewall remain shared. Alternatives remain in use: macvlan and ipvlan attach containers straight to a parent interface, with ipvlan L2 trunking a good fit when a switch is short of MAC table space [src: docker-docs 3045ea6b6f4616e6]. The emerging pattern is a choice by **scope of isolation**: policy routing when only the decision differs, VRF when routing tables must be separate but the process view can be shared, a namespace when the whole stack must be separate.

## Current state

### Namespaces and veth

```bash
ip netns add red
ip netns add blue
ip link add veth-r type veth peer name veth-r-h     # both ends start in the current namespace
ip link set veth-r netns red
ip -n red addr add 10.10.1.2/24 dev veth-r
ip -n red link set veth-r up
ip -n red link set lo up
ip addr add 10.10.1.1/24 dev veth-r-h
ip link set veth-r-h up
ip -n red route add default via 10.10.1.1
ip netns exec red ping -c1 10.10.1.1
ip netns list; ip netns identify $$; ip -n red route
```

`ip netns add` creates a named namespace by bind-mounting its handle under `/run/netns`; `ip netns exec NAME CMD` runs any command inside it, and `ip -n NAME` is the short form for ip itself. Processes reach a namespace by PID as well (`nsenter -t PID -n`), and a namespace disappears when its last process exits and its handle is unmounted; a named namespace therefore survives with no process in it. The loopback device starts down in a new namespace and must be brought up. To reach the world, enable forwarding in the host (`sysctl -w net.ipv4.ip_forward=1`) and add NAT or a route for the namespace's prefix on the upstream router. Sysctls under `net.*` are per namespace, so forwarding and reverse-path filtering are set separately in each.

Several namespaces on one segment attach to a bridge instead: create the veth pairs, put one end of each in its namespace and enslave the other end to a bridge in the host, as in the previous topic.

### VRF

```bash
ip link add vrf-a type vrf table 10
ip link set vrf-a up
ip link set eth1 master vrf-a
ip addr add 192.0.2.1/24 dev eth1
ip route add default via 192.0.2.254 vrf vrf-a    # lands in table 10
ip route show vrf vrf-a; ip -br link show type vrf
ip vrf exec vrf-a ping -c1 192.0.2.254
ip vrf exec vrf-a ssh admin@192.0.2.50
```

Enslaving an interface moves its connected routes into the VRF's table and sets up an l3mdev rule that sends lookups for that VRF there. `ip vrf exec` runs a command bound to the VRF, so its sockets use that table. Servers that should answer inside a VRF need to bind to it: many daemons support this with an option, and the sysctl `net.ipv4.tcp_l3mdev_accept` lets a listener in the default VRF accept connections that arrive through a VRF. Overlapping prefixes can coexist in different VRFs because each has its own table, and a pair of veth devices, or route leaking with `ip route add ... dev` between tables, joins them deliberately.

### Policy routing

```bash
echo 100 isp2 >> /etc/iproute2/rt_tables
ip route add default via 198.51.100.1 dev eth2 table isp2
ip route add 198.51.100.0/24 dev eth2 src 198.51.100.7 table isp2
ip rule add from 198.51.100.7 lookup isp2 priority 1000
ip rule add fwmark 0x2 lookup isp2 priority 1100
ip rule show; ip route show table isp2
ip route get 203.0.113.9 from 198.51.100.7 iif eth0
```

Rules are evaluated in priority order, lowest number first: rule 0 sends everything to the local table, 32766 to main and 32767 to default. The first rule whose selector matches and whose table holds a matching route wins; a rule can also be `prohibit`, `unreachable` or `blackhole`. Selectors include `from`, `to`, `iif`, `oif`, `fwmark`, `uidrange`, `ipproto`, `sport` and `dport`. A mark set by nftables or `SO_MARK` selects a table per flow. `ip route get` with `from` and `iif` shows the result of the lookup and is the first debugging tool. Asymmetric flows tend to fail reverse-path filtering (`net.ipv4.conf.*.rp_filter`), where loose mode (2) is the compromise, and a VRF or table needs its own default route or the traffic is dropped silently.

## Assessment: the good, the bad and the ugly

The good: all four are core kernel features with `ip` front ends, no extra daemons and near-zero overhead. A namespace is a sufficient lab for almost any network experiment: you can build a whole topology on a laptop with veth pairs, without virtual machines. VRF gives router-style isolation with ordinary Linux tools.

The bad: the pieces do not compose automatically. Firewall rules, sysctls and DNS configuration are per namespace; a resolver file inside a namespace comes from `/etc/netns/NAME/resolv.conf` when it exists. VRF-unaware daemons bind to the wrong table. Rules and routes added with `ip` vanish at reboot, so persistence needs the network manager or a unit file.

The ugly: policy routing failures are silent. A missing rule or table lookup gives no log message, only a dead flow, and the interplay with reverse-path filtering and connection tracking confuses even experienced people. A route that is correct in the main table can be shadowed by a lower-numbered rule. Cleaning up is also awkward: leaked veth devices and stale `/run/netns` entries remain after a crashed script.

## Applications beyond this domain

Containers are namespaces plus control groups; each pod or container gets a network namespace with a veth pair to a bridge or a CNI plugin. Kubernetes and Docker therefore expose exactly the objects described above, and rootless setups add a userspace network stack because an unprivileged user cannot create the host side of a veth pair. Service providers use VRFs for customer separation in carrier routers (the same idea as MPLS VPN routing instances). Test frameworks and network emulators build large topologies from namespaces. Policy routing underlies source-based routing for dual-ISP failover and for sending selected users or applications through a VPN.

## Examples

A working example: a host with two uplinks, `eth0` (default, address 192.0.2.7) and `eth2` (198.51.100.7). Replies to connections that arrive on `eth2` leave on `eth0` and are dropped upstream by anti-spoofing. Adding table `isp2` with its own default route and a rule `from 198.51.100.7 lookup isp2` makes replies leave from the interface they came in on.

A second example: two customers use 10.0.0.0/24. Two VRFs, each with one customer interface and its own default route, carry both without conflict; `ip route show vrf NAME` shows two different tables with the same prefix.

A failing example: a service started from a shell inside `ip vrf exec` works, but the same unit under systemd cannot connect. The unit runs in the default VRF; the fix is to bind it into the VRF or start it with `ip vrf exec` in `ExecStart`. Another failing example: a namespace can ping the host end of its veth but not the internet, because the host's forwarding sysctl is off or no return route exists for the namespace's prefix.

## Related problems and ideas

macvlan and ipvlan devices, bridges with VLANs, WireGuard and other tunnels used as interfaces inside a namespace, `nftables` marks, and eBPF-based forwarding (Cilium describes how BPF hooks in the networking stack replace parts of this machinery [src: cilium-docs 3b62a08165990e48]) are neighbours. Segment routing and MPLS go further by making the path a property of the packet. Routing daemons such as FRR understand VRFs and can distribute the per-VRF tables with BGP.

## Active research

Work includes lighter container isolation (per-container namespaces with fewer costs), faster namespace creation for serverless platforms, eBPF programs that bypass the netfilter path for namespaced traffic, and better observability: tying flows to namespaces, VRFs and rules in tracing tools. Open questions include how to persist VRF and rule state in a portable declarative form across distributions.

## Future direction

Expect eBPF to take over more of the forwarding decision while the policy database stays as the compatibility layer. Declarative front ends (NetworkManager, systemd-networkd, netplan) continue to add VRF and routing-policy sections, and `systemd-nspawn` and container runtimes keep refining default network setups. Track the kernel's l3mdev work and the netns-aware additions in each release.
