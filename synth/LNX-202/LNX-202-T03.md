# Getting IPv6 hosts configured: router advertisements, SLAAC and DHCPv6

## Define the problem

An IPv6 host that has just come up on a link knows only its link-local address. To talk beyond the link it needs a global address, a default router, usually DNS servers and sometimes more (a search domain, a boot file). IPv4 answered these with one protocol, DHCP, which carried the gateway too. IPv6 deliberately splits the job, and the split is the source of most confusion: the router announces prefixes and its own existence, hosts may build addresses themselves, and a separate DHCPv6 service may hand out addresses or only extra settings. Failure looks like a host with an address but no default route, a host with a route but no DNS, a printer that appears at a different address after every boot, or a network where IPv4 works and IPv6 quietly times out.

This slice covers router advertisements with `radvd` and the kernel, stateless address autoconfiguration (SLAAC), DHCPv6 and the way they are combined, with the Linux commands to observe each step.

## History and approaches

IPv4 hosts were configured by hand, then by BOOTP and DHCP. When IPv6 was designed (RFC 2460, 1998), the authors added **neighbour discovery** (RFC 2461, now RFC 4861) so that routers announce themselves and prefixes in router advertisements, and **stateless address autoconfiguration** (RFC 2462, now RFC 4862) so that a host forms its own address from the announced /64 prefix and an interface identifier, then checks it is unique with duplicate address detection. No server keeps state, which suits large or leaf networks. Early implementations built the identifier from the MAC address (modified EUI-64), and that exposed the hardware address and let a device be tracked between networks; RFC 4941 added temporary addresses and RFC 7217 stable but opaque identifiers. The Debian handbook describes the default as exactly this: with SLAAC active, the kernel finds routers and configures the interface by itself, and privacy extensions address the tracking concern [src: debian-handbook ca3af3faf2de9767].

Administrators who wanted central control and logs asked for a stateful service, so **DHCPv6** (RFC 3315, now RFC 8415) appeared in 2003. It has no gateway option, because only router advertisements carry the default router, so it must be paired with them. Two flag bits in the advertisement tie the two together: the M bit says addresses are available from DHCPv6, and the O bit says other settings are. Later, RFC 6106 (now RFC 8106) put DNS servers and search domains directly in router advertisements (the RDNSS and DNSSL options), so a network can run SLAAC alone with no DHCPv6 server. The emerging pattern is a choice among three designs: pure SLAAC with RDNSS, SLAAC plus stateless DHCPv6 for extra options, or managed DHCPv6 with router advertisements supplying the gateway.

## Current state

### The kernel and the router advertisement

A router sends advertisements periodically and in answer to router solicitations from hosts. Each carries the router lifetime (zero means not a default router), the M and O flags, an MTU option, and one or more prefix information options with an on-link flag (L) and an autonomous flag (A). A host applies SLAAC only to a prefix with A set and a 64-bit length. On Linux the host side is controlled by sysctls under `net.ipv6.conf.IFACE`: `accept_ra` (0 ignore, 1 accept when not forwarding, 2 accept even when forwarding), `autoconf`, `use_tempaddr`, `addr_gen_mode` and `accept_ra_defrtr`. A Linux router that forwards packets ignores advertisements unless `accept_ra=2`, which is the usual trap on a gateway with its own upstream.

```bash
sysctl net.ipv6.conf.eth0.accept_ra net.ipv6.conf.all.forwarding
ip -6 addr show dev eth0                 # scope link, global dynamic, temporary
ip -6 route show; ip -6 neigh show
rdisc6 eth0                              # send a solicitation, print advertisements
tcpdump -ni eth0 icmp6 and 'ip6[40] == 134'    # advertisements only
```

For servers that should keep a recognisable host part but still follow the prefix, `ip token set ::53 dev eth0` assigns a tokenised interface identifier, so the address is the advertised prefix plus the token and follows a renumbering [src: man-pages 424cebf79d50b52c].

### radvd

`radvd` is the standard advertisement daemon on Linux routers. Its configuration is one `interface` block with prefix, flag, route, RDNSS and DNSSL sub-blocks:

```
interface eth1 {
    AdvSendAdvert on;
    MinRtrAdvInterval 30;
    MaxRtrAdvInterval 100;
    AdvManagedFlag off;
    AdvOtherConfigFlag on;
    prefix 2001:db8:42:7::/64 {
        AdvOnLink on;
        AdvAutonomous on;
    };
    RDNSS 2001:db8:42:7::53 { AdvRDNSSLifetime 600; };
};
```

The router must also forward (`net.ipv6.conf.all.forwarding=1`) or `radvd` refuses to run. The RHEL guide notes that this daemon can announce only 64-bit prefixes, so another prefix length needs DHCPv6, and `radvdump` displays what is being sent [src: rhel-10-docs 7c6dbdb531caf0e0]. Without radvd, `systemd-networkd` can send advertisements itself from a `[IPv6SendRA]` section, and Kea or dnsmasq cover DHCPv6.

### DHCPv6 and how it combines

DHCPv6 clients use link-local source addresses, UDP port 546, and multicast to ff02::1:2 on server port 547. The exchange is Solicit, Advertise, Request, Reply, or Information-Request and Reply for stateless use. Clients are identified by a DUID, not a MAC address, which matters for reservations. Besides addresses (IA_NA) a server can delegate whole prefixes (IA_PD) to routers. The RHEL guide compares the two services: DHCPv6 can map identifiers to addresses and send further options but carries no gateway, while the advertisement service supplies the gateway and no other options [src: rhel-10-docs c575b1d6c8cd8156]. On the client side, NetworkManager selects the mode with `ipv6.method auto` or `dhcp`, and systemd-networkd with `DHCP=ipv6` plus `IPv6AcceptRA`. Because the DUID can be shared when images are cloned, per-connection DUIDs are sometimes configured [src: archwiki 9b6ece0b0a8c454c].

## Assessment: the good, the bad and the ugly

The good: SLAAC needs no server state and scales well; a router outage does not stop hosts that already have addresses. Host configuration is decentralised and robust, and dual addressing (link-local plus global plus temporary) is predictable once understood.

The bad: addressing information is spread over three mechanisms and every OS reads them a little differently. Android does not implement DHCPv6, so a managed-only network leaves those clients without addresses. Address tracking is hard: temporary and stable-privacy addresses mean logs show many addresses per host, so inventory and firewall rules should use identifiers other than the address. Multicast, which neighbour discovery needs, can be dropped by Wi-Fi access points and switches with aggressive snooping.

The ugly: filtering. A firewall that blocks all ICMPv6 breaks the whole scheme, because router discovery, neighbour discovery and path MTU discovery depend on it. A rogue advertisement from a laptop that has enabled sharing can become the default route for a whole segment, and RA Guard on the switch is the defence. Lifetimes also bite: a host keeps using stale prefixes until they expire, so renumbering needs advertisements with shortened lifetimes first.

## Applications beyond this domain

Neighbour discovery and advertisements are the same machinery that lets Kubernetes nodes learn routes in IPv6-only clusters and that container runtimes use when they hand out router-assigned addresses to macvlan and ipvlan networks [src: docker-docs a150a665767e28af]. Prefix delegation is how an ISP gives a home router a block that it splits across its own links, and the same idea is used by cloud providers that attach /56 or /64 blocks to instances. Tokenised identifiers and RDNSS-style configuration over advertisements appear in constrained-device and 6LoWPAN networks, where DHCP is too heavy.

## Examples

A working example: a lab router with `eth1` on 2001:db8:42:7::/64 runs radvd as shown, with the O flag on and a small DHCPv6 server returning only DNS information. A client on that link shows a global address derived from the prefix, a default route via the router's link-local address, and DNS from the server. `ip -6 route` lists `default via fe80::...`, a clue that the router is identified by its link-local address, not a global one.

A failing example: the same router with forwarding switched off at boot by a hardening profile. radvd exits at start, hosts keep link-local addresses only, and `rdisc6 eth1` returns nothing. `journalctl -u radvd` names the forwarding check.

A second failing example: a Linux gateway receives an upstream prefix by SLAAC but loses its default route after enabling forwarding. The cause is `accept_ra` falling back to 0 for forwarding hosts; setting it to 2 on the upstream interface restores it.

## Related problems and ideas

DHCPv6 prefix delegation with hierarchical routers, NAT64 and DNS64 for IPv6-only networks, 464XLAT on mobile networks, ULA addressing for internal networks, and the privacy trade-offs between stable, temporary and tokenised identifiers are neighbouring subjects. RA Guard, DHCPv6 Guard and ND inspection on switches address the security side. Proposals continue to discuss mandatory use of RDNSS, and of the PREF64 option that tells hosts where a NAT64 gateway lives.

## Active research

Measurement groups study how long hosts retain stale prefixes after renumbering, and how addressing practice differs across mobile, home and enterprise networks. Standards work covers router advertisement robustness against floods and spoofing, address assignment for mobile devices that join and leave quickly, and the trade-off between per-host /128 addresses and per-host /64 prefixes in data centres and Wi-Fi.

## Future direction

IPv6-only access networks with NAT64 are growing, which will push operators towards SLAAC with RDNSS and PREF64 rather than managed DHCPv6. Expect more distributions to configure clients with systemd-networkd or NetworkManager defaults that follow the advertisement flags exactly, and more attention to filtering that treats ICMPv6 as required infrastructure.
