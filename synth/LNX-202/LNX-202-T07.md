# Encrypted tunnels between Linux hosts: WireGuard and IPsec

## Define the problem

Two networks or hosts that must talk across an untrusted path, usually the Internet, need confidentiality, integrity and proof of who is on the other end. They also need the tunnel to behave like a network link: addresses at both ends, routes that point into it, and a path that survives changes of address and brief outages. Failure looks like a tunnel that shows as up but passes nothing, packets that vanish because the inner MTU exceeds what the path carries, a road-warrior laptop that loses its tunnel when it changes Wi-Fi network, a site-to-site link that works one way, or keys and certificates that expire unnoticed.

This slice covers the two tunnel technologies in common use on Linux servers: **WireGuard**, a small in-kernel tunnel with a fixed cryptographic suite, and **IPsec** with IKEv2, implemented on Linux by Libreswan or strongSwan. Application-layer VPNs (OpenVPN, TLS proxies) are mentioned only as comparisons.

## History and approaches

Early remote access ran over dial-up and PPTP, which proved weak. IPsec arrived in the 1990s as the standards-based answer at the IP layer: the ESP protocol (IP protocol 50) encrypts and authenticates packets, and IKE negotiates keys and algorithms over UDP ports 500 and 4500. It is interoperable with every router and firewall vendor, and also huge: many modes, algorithm suites and options. IKE version 1 was replaced by the simpler IKEv2 (RFC 7296). On Linux the kernel's XFRM framework applies the policies and keys, while a daemon negotiates them. The RHEL guides describe a Libreswan setup with certificates held in an NSS database, including a mesh in which every server holds a tunnel to every other server [src: rhel-10-docs 00436cbe78c5c8bf].

OpenVPN (2001) took the other path, tunnelling over TLS in user space. Easier to deploy than IPsec, but slower and still carrying a large configuration surface. **WireGuard**, written by Jason Donenfeld and merged in Linux 5.6 (2020), reacted to the complexity: about four thousand lines of kernel code, a network interface like any other, one fixed set of algorithms (Curve25519 for key agreement, ChaCha20-Poly1305 for encryption, BLAKE2s for hashing, in a Noise-framework handshake) and no negotiation. Peers are identified by public keys and the interface behaves as a stateless UDP endpoint. The pattern that emerged is **key-based, small and routed (WireGuard) versus standards-based and negotiated (IPsec)**, with IPsec still required for interoperability with other vendors and WireGuard preferred for Linux-to-Linux links, containers and mobile clients.

## Current state

### WireGuard

Each node generates a key pair, exchanges only public keys, and describes peers in a file:

```bash
umask 077
wg genkey | tee priv.key | wg pubkey > pub.key
```

```ini
# /etc/wireguard/wg0.conf on peer A
[Interface]
Address = 10.0.0.1/24
ListenPort = 51820
PrivateKey = <contents of priv.key>

[Peer]
PublicKey = <key of the far peer>
AllowedIPs = 192.168.20.0/24, 10.0.0.2/32
Endpoint = 203.0.113.102:51820
PersistentKeepalive = 25
```

`wg-quick up wg0` creates the interface, assigns the address and installs routes for the AllowedIPs; `systemctl enable --now wg-quick@wg0` makes it persistent. Without wg-quick the same is `ip link add wg0 type wireguard`, `wg setconf`, `ip addr add` and `ip link set wg0 up`; systemd-networkd also has a `[WireGuard]` section in `.netdev` files. The key concept is **cryptokey routing**: AllowedIPs is both a routing table (outgoing packets go to the peer whose list contains the destination) and an access list (incoming packets from a peer are accepted only if the inner source matches its list). The Arch guide shows the same layout for three peers, one of them with a dynamic address, which is possible because only one side needs an Endpoint [src: archwiki eb2306558869166e]. `Endpoint` is learned from the last valid packet, so a roaming peer is followed; `PersistentKeepalive` keeps a NAT mapping open for peers behind NAT.

`wg` (or `wg show`) prints each peer's key, endpoint, allowed IPs, last handshake time and byte counters; a peer that shows no handshake never completed its exchange, which is the first diagnostic [src: archwiki 7d09fd9138f64d23]. Handshakes repeat about every two minutes while data flows, and a peer is silent when idle. Open the UDP listening port in the firewall, and set the MTU to 1420 (or 1400 over IPv6 or PPPoE) on the interface. For a gateway, enable `net.ipv4.ip_forward`, add the forwarding rules and masquerading as needed, and add routes for remote networks via the AllowedIPs entries.

### IPsec with Libreswan or strongSwan

A site-to-site connection in Libreswan, in `/etc/ipsec.d/site.conf`:

```
conn site-b
    left=198.51.100.1
    leftsubnet=192.168.10.0/24
    right=203.0.113.2
    rightsubnet=192.168.20.0/24
    authby=secret
    ikev2=yes
    auto=start
```

with the pre-shared secret in `/etc/ipsec.d/site.secrets` (`198.51.100.1 203.0.113.2 : PSK ...`), or certificates and `authby=rsasig` for larger deployments. Commands: `systemctl enable --now ipsec`, `ipsec auto --add site-b`, `ipsec auto --up site-b`, `ipsec trafficstatus` and `ipsec status`; strongSwan uses `swanctl --load-all` and `swanctl --list-sas`. The Red Hat guide states that a populated line in the `trafficstatus` output shows the connection by name, and that an empty output means no tunnel [src: rhel-10-docs f3ac41b4d21820ab]. In tunnel mode (the VPN case) the whole original packet is wrapped; in transport mode only the payload is protected, as for host-to-host links. The kernel state is visible with `ip xfrm state` and `ip xfrm policy`. Firewalls must allow UDP 500, UDP 4500 (for NAT traversal), and the ESP protocol.

### Troubleshooting both

The RHEL troubleshooting guide offers a systematic order: confirm the tunnel exists, check whether a firewall drops IKE (repeated retransmission messages on `ipsec up` point to it), capture with `tcpdump -ni IFACE esp or udp port 500 or udp port 4500`, and compare both endpoints for mismatched IKE version, algorithms, subnets or keys. It also warns that IKE is encrypted, so capture shows only that packets flow [src: rhel-10-docs f3ac41b4d21820ab]. For WireGuard, UDP capture on the listening port shows handshake packets in clear but payloads encrypted; the useful view is the inner traffic on `wg0` itself.

## Assessment: the good, the bad and the ugly

The good: WireGuard is simple, quick to set up, fast, good at roaming, and its configuration fits on one screen. IPsec is a universal standard, supports certificates and large policy sets and is accepted by every vendor and cloud gateway. Both are in the mainline kernel.

The bad: WireGuard has no built-in user management, dynamic address assignment or revocation list; the configuration of many peers needs tooling. Static key pairs mean a stolen private key stays valid until removed. IPsec is verbose, has many interdependent settings, and interoperability failures between vendors arise from default algorithm lists and lifetime values that do not match. Neither handles path MTU well without tuning.

The ugly: NAT, MTU and routing. A tunnel that passes pings but stalls large transfers is nearly always an MTU problem. Overlapping subnets at the two sites need NAT or renumbering. IPsec policy-based tunnels do not appear as interfaces, so routing and firewalling them feels different from the routed model; the VTI or XFRM interface fixes this, at the cost of more configuration.

## Applications beyond this domain

WireGuard is used inside Kubernetes by Cilium for transparent encryption between nodes, and the Cilium documentation lists inspection and troubleshooting commands that carry over directly [src: cilium-docs 84803259e8f5216e]; Tailscale and Netbird build mesh networks and access control on top of it. IPsec protects traffic between cloud virtual private clouds and data centres, mobile carrier backhaul and IPv6 deployments. The concept of cryptokey routing, where a key identifies a peer and limits its addresses, appears in zero-trust designs and in service meshes with mutual authentication.

## Examples

A working example: two Linux servers at different sites, each with the file above, `wg-quick up wg0` on both and routes for the remote LAN. `wg show` reports a handshake within a few seconds of the first packet, and `ping 10.0.0.2` works. A host on LAN A reaches a host on LAN B once forwarding is on and LAN hosts route via the gateway.

A failing example: the ping works but `scp` hangs after the banner. `ping -M do -s 1400 10.0.0.2` fails while smaller sizes pass; lowering the interface MTU to 1380, or clamping the TCP MSS in the firewall, fixes it.

A second failing example: `ipsec auto --up site-b` loops with retransmissions. A packet capture shows IKE leaving the host and no reply; a firewall at the far end blocked UDP 500. After opening the ports, the tunnel comes up, and `ipsec trafficstatus` lists it.

## Related problems and ideas

OpenVPN, SSH tunnels, GRE and VXLAN (unencrypted overlays that can be wrapped in IPsec), MACsec for layer 2, TLS-based proxies, and mesh VPNs that coordinate WireGuard keys through a control server are the neighbours. BGP over a tunnel, ECMP across several tunnels, and policy routing to decide which traffic enters the tunnel connect this topic to the previous ones.

## Active research

Research includes post-quantum key exchange for both families (hybrid handshakes for WireGuard variants and for IKEv2, with RFC work on ML-KEM in IKE), formal verification of the WireGuard handshake, hardware offload of ESP and of WireGuard packet processing, and lighter peer discovery and NAT traversal methods. Studies compare throughput and latency of kernel and user-space implementations.

## Future direction

Expect post-quantum hybrids to enter IKEv2 first and to appear later in WireGuard-compatible tools. More distributions will ship WireGuard in their network managers, while IPsec remains the interoperability layer for site-to-site and cloud links. Track NIC offload support and kernel release notes.
