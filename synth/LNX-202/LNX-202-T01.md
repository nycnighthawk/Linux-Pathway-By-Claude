# Layer 2 on a Linux host: bridges, VLANs and bonds

## Define the problem

A server with more than one network port, or a hypervisor with many guests, needs more than one address on one wire. It has to join several ports into one logical link for capacity and failover, carry several isolated networks over a single cable, and connect virtual machines or containers to the physical network as if they were ordinary hosts. Failure looks like a link that flaps when one cable is pulled, a guest that cannot reach its gateway, traffic from one tenant that appears on another tenant's segment, or a bond that reports healthy while only one of its ports ever carries load.

This slice covers the three kernel building blocks that answer those needs: the **bridge** (a software switch), the **VLAN** device (802.1Q tagging) and the **bond** (link aggregation, including LACP between two Linux peers). It assumes the addressing and tooling of LNX-201 and stays on the Ethernet layer; routing between the resulting networks belongs to the next topic.

## History and approaches

Early multi-port hosts simply used one interface per network. Capacity was added by buying faster NICs, and redundancy by a second host. The first Linux answer to aggregation was the bonding driver, which appeared in the 2.x kernels as a port of an idea from other Unix systems; its modes ranged from simple round robin to hot standby. The IEEE standardised dynamic aggregation as 802.3ad, later folded into 802.1AX, so that two ends could agree on which ports belong together instead of trusting configuration on both sides to match. Linux gained the `802.3ad` bonding mode for it; later `teamd` offered a userspace alternative, which the RHEL family has since steered users away from in favour of the in-kernel bond [src: rhel-10-docs aac79091ad266bf0].

Switching in software began with the `brctl` tool and the bridge module, which learned MAC addresses per port and could run the spanning tree protocol. VLANs came with the 802.1Q tag and the `vconfig` tool, replaced by the `ip link ... type vlan` interface. For years the usual layout was a bridge per VLAN, each fed by a VLAN sub-interface of a bond. Linux 3.8 added VLAN filtering inside the bridge, so one bridge can hold many VLANs and each port can be assigned a set, which is how a hardware switch behaves. Alternatives sit beside this design: Open vSwitch offers a richer switch with its own database for ports, VLAN modes and bond modes [src: man-pages 884f084048aa421c], and macvlan or ipvlan devices skip the bridge for simple container attachment. The pattern that emerged is a **bond for the physical uplink, a bridge (or switch) for sharing it and VLAN tags for separation**, built in that order from the wire upwards.

## Current state

### Bonds

A bond enslaves ports (the kernel's older term is slave; documents now say port or member) and presents one interface. The mode decides behaviour. Round robin sends successive packets over each port and needs a matching group on the switch; active-backup keeps one port live and needs no switch support, announcing the new path with a gratuitous ARP after a failover; xor and broadcast need a group on the switch; 802.3ad negotiates with LACP and requires an LACP group on the peer; the transmit-balancing and adaptive modes need no switch support [src: rhel-10-docs aac79091ad266bf0]. Both systemd-networkd and NetworkManager expose the same list of mode names: 802.3ad, active-backup, balance-rr, balance-xor, broadcast, balance-tlb and balance-alb [src: man-pages 3a07a73854d9551c].

LACP between two Linux peers is the easiest way to learn the protocol, because both ends are visible:

```bash
ip link add bond0 type bond mode 802.3ad miimon 100 lacp_rate fast xmit_hash_policy layer3+4
ip link set eth1 down; ip link set eth1 master bond0
ip link set eth2 down; ip link set eth2 master bond0
ip link set bond0 up; ip link set eth1 up; ip link set eth2 up
cat /proc/net/bonding/bond0
```

`/proc/net/bonding/bond0` shows the mode, the transmit hash policy, the MII polling interval, each port's link state and, for 802.3ad, the aggregator ID of every port, the partner's system MAC and the actor and partner state flags. Ports with different aggregator IDs did not negotiate into one group, which is the usual sign of a mismatch. Monitoring defaults to polling the carrier; the driver's `miimon` parameter sets the interval in milliseconds and the Rocky guide notes that 100 ms suits most sites and can be lowered if failures are noticed too late [src: rocky-docs b37472a0a943ec9b]. systemd-networkd calls the same setting `MIIMonitorSec=` and defaults to disabled, so a networkd bond must set it [src: man-pages 3a07a73854d9551c]. `lacp_rate` selects how often LACPDUs are sent (slow means every 30 seconds, fast every second); `UpDelaySec=` and `DownDelaySec=` debounce flapping links.

The **transmit hash policy** chooses the outgoing port per flow. `layer2` hashes MAC addresses, `layer2+3` adds IP addresses, and `layer3+4` adds ports for the best spread, with the caveat that fragmented traffic can be reordered [src: rocky-docs 9ffb356c3109b324]. Because the hash picks a port per flow, a single TCP stream never exceeds one port's speed; a bond adds capacity only across many flows. The receiving direction is chosen by the peer's own hash, so both ends need appropriate settings.

### VLANs

A VLAN device is a child of a parent interface that tags frames with a 12-bit ID on the way out and strips the tag on the way in:

```bash
ip link add link bond0 name bond0.20 type vlan id 20
ip addr add 192.0.2.10/24 dev bond0.20
ip link set bond0.20 up
ip -d link show bond0.20      # detail: protocol 802.1Q id 20
```

IDs 1 to 4094 are usable; 0 and 4095 are reserved. The MTU of the child cannot exceed the parent's, and the tag costs four bytes, so a link carrying tagged frames at 1500-byte payload needs a path that accepts 1504-byte frames.

### Bridges with VLAN filtering

```bash
ip link add br0 type bridge vlan_filtering 1 stp_state 1
ip link set bond0 master br0
ip link set tap-vm1 master br0
bridge vlan add dev bond0 vid 20            # tagged on the uplink
bridge vlan add dev tap-vm1 vid 20 pvid untagged   # guest sees untagged frames
bridge vlan show
bridge fdb show br br0                      # learned MAC addresses per port
bridge link show
```

`pvid` assigns untagged ingress frames to a VLAN and `untagged` strips the tag on egress, making an access port; ports without those flags are trunk ports. The bridge learns source MACs into a forwarding database and floods frames with an unknown destination. With STP enabled it blocks redundant paths; with a bond underneath, STP is usually unnecessary because redundancy is hidden inside the bond. The RHEL guide for VMs shows the pattern of a bridge on top of an active-backup bond so that guests share the physical uplink and survive a port failure, while pointing out that a bridge alone offers no failover [src: rhel-10-docs 36a3cccb5feddb29]. NetworkManager builds the same stack with `nmcli connection add type bond`, `type bridge` and `type vlan`, and netplan describes it under `bonds:`, `bridges:` and `vlans:`.

## Assessment: the good, the bad and the ugly

The good: everything is in the mainline kernel, scriptable, observable through `/proc` and `bridge`, and fast enough for line rate on commodity hardware. One bridge with VLAN filtering replaces a thicket of per-VLAN bridges. LACP detects a port that is up but not passing partner traffic, which carrier polling alone cannot do.

The bad: flow hashing means uneven load, and one large transfer never uses more than one member. Mode mismatches fail quietly: a switch group configured static while the host speaks LACP can look half alive. MTU must match on parent, bond, bridge and VLAN children. Firewalls interact with bridges: bridged frames pass through the iptables hooks only when the br_netfilter module is loaded, which surprises people who expect layer 2 to be invisible to filtering.

The ugly: loops. A bridge that connects two ports of the same switch without STP floods frames until the network collapses. Changing a live bond over SSH can cut off the session, because the port must go down before it joins. The terminology around master, slave and port differs between kernel, tools and vendors, which makes searches and logs confusing.

## Applications beyond this domain

The same ideas appear wherever a switch is virtualised. Kubernetes nodes often use a bridge or a macvlan for pod attachment. Cloud hypervisors present guest NICs as ports on a software bridge, with VLAN or VXLAN tags for tenant separation. Hardware switches run the same LACP and spanning-tree protocols, so what you learn between two Linux peers transfers to an enterprise rack. Link aggregation also shows up in storage networks, where multipath I/O replaces it for iSCSI, and in Wi-Fi infrastructure that bonds uplinks for access points. The Rocky guides on VLAN passthrough for Intel and Marvell cards show the hardware side: a bridge with VLAN filtering only works if the NIC passes tagged frames to the host unchanged [src: rocky-docs cab2f7ce84c38659].

## Examples

A working example: two Linux hosts joined by two cables, each with an 802.3ad bond (`miimon 100`, `layer3+4`). `cat /proc/net/bonding/bond0` on both ends shows one aggregator ID for both ports, and a test with several parallel `iperf3` streams uses both cables; pulling one cable moves traffic to the other within a few polling intervals.

A failing example: the same hosts, but one end is set to `xmit_hash_policy layer2` with all traffic between two fixed MAC addresses. Every flow hashes to the same port, the second cable stays idle, and the bond looks healthy. The fix is to hash on IP addresses and ports, or to add parallel addresses.

A second failing example: a VM on `br0` cannot reach its gateway although the bridge shows the tap port. `bridge vlan show` reveals the tap port still has the default VLAN 1 while the uplink only carries VLAN 20; adding `pvid untagged` for VLAN 20 on the tap port fixes it.

## Related problems and ideas

Team devices, macvlan and ipvlan, Open vSwitch and the hardware-offloaded switchdev model all address parts of the same problem. VXLAN extends a layer 2 segment across layer 3 for data centres. Multi-chassis link aggregation (MLAG) lets one host bond to two different switches, which a plain 802.3ad bond cannot do without the switches cooperating. EVPN and shortest path bridging replace spanning tree in large fabrics.

## Active research

Work continues on offloading switching to NICs and switch ASICs through the kernel's switchdev interface, on fast bridge forwarding paths (including per-VLAN statistics and multicast snooping improvements), and on measuring how hash policies behave with encrypted or tunnelled traffic, where inner headers are hidden from the transmit hash. Open questions include fair load spreading for few large flows and standard behaviour for MLAG with different vendors.

## Future direction

Expect more of the bridge to move into hardware, with VLAN filtering and FDB handled by NIC or switch silicon while Linux remains the control plane. Teaming in userspace is declining; the in-kernel bond and the bridge are the stable platform. Watch kernel release notes for bridge VLAN options and for changes to bonding terminology and defaults.
