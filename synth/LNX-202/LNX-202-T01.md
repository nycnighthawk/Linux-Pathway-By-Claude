# Layer 2 on a Linux host: bridges, VLANs and bonds

## Define the problem

A server with more than one network port, or a hypervisor with many guests, needs more than one address on one wire. It has to join several ports into one logical link for capacity and failover, carry several isolated networks over a single cable, and connect virtual machines or containers to the physical network as if they were ordinary hosts. Failure takes recognisable forms: a link that flaps when one cable is pulled, a guest that cannot reach its gateway, traffic from one tenant that appears on another tenant's segment, or a bond that reports healthy while only one of its ports ever carries load.

This essay covers the three kernel building blocks that answer those needs. The **bridge** is a software switch, the **VLAN** device adds 802.1Q tagging, and the **bond** aggregates links, including LACP between two Linux peers. It assumes the addressing and tooling of LNX-201 and stays on the Ethernet layer; routing between the resulting networks is the next topic. The order of the essay follows the order of the build, from the wire upwards: first the bond, then the VLANs, then the bridge that shares them.

## History and approaches

### One interface per network

Early multi-port hosts simply used one interface per network. Capacity was added by buying faster cards, and redundancy by a second host. Neither answer scales, because each port is a separate point of failure and a separate address to manage.

### Aggregation

The first Linux answer to aggregation was the bonding driver, which appeared in the 2.x kernels as a port of an idea from other Unix systems, with modes that range from simple round robin to hot standby. The IEEE then standardised dynamic aggregation as 802.3ad, later folded into 802.1AX, so that two ends could *agree* on which ports belong together instead of trusting the configuration on both sides to match. Linux gained the `802.3ad` bonding mode for it. Later `teamd` offered a userspace alternative, which the RHEL family has since steered users away from in favour of the in-kernel bond [src: rhel-10-docs aac79091ad266bf0].

### Switching in software

Switching began with the `brctl` tool and the bridge module, which learned MAC addresses per port and could run the spanning tree protocol. VLANs came with the 802.1Q tag and the `vconfig` tool, which `ip link ... type vlan` replaced. For years the usual layout was a bridge per VLAN, each fed by a VLAN sub-interface of a bond. Linux 3.8 added VLAN filtering inside the bridge, so one bridge can hold many VLANs and each port can be assigned a set, which is how a hardware switch behaves.

### Alternatives beside the main line

Open vSwitch offers a richer switch with its own database for ports, VLAN modes and bond modes [src: man-pages 884f084048aa421c], and macvlan or ipvlan devices skip the bridge for simple container attachment. The pattern that emerged from all of this is a **bond for the physical uplink, a bridge (or switch) for sharing it and VLAN tags for separation**, built in that order from the wire upwards.

## Current state

### Bonds

A bond enslaves ports (the kernel's older term is slave, and documents now say port or member) and presents one interface. The mode decides behaviour. Round robin sends successive packets over each port and needs a matching group on the switch. Active-backup keeps one port live and needs no switch support, announcing the new path with a gratuitous ARP after a failover. Xor and broadcast need a group on the switch. The 802.3ad mode negotiates with LACP and requires an LACP group on the peer. The transmit-balancing and adaptive modes need no switch support [src: rhel-10-docs aac79091ad266bf0]. Both systemd-networkd and NetworkManager expose the same list of mode names: 802.3ad, active-backup, balance-rr, balance-xor, broadcast, balance-tlb and balance-alb [src: man-pages 3a07a73854d9551c].

LACP between two Linux peers is the easiest way to learn the protocol, because both ends are visible.

```bash
ip link add bond0 type bond mode 802.3ad miimon 100 lacp_rate fast xmit_hash_policy layer3+4
ip link set eth1 down; ip link set eth1 master bond0
ip link set eth2 down; ip link set eth2 master bond0
ip link set bond0 up; ip link set eth1 up; ip link set eth2 up
cat /proc/net/bonding/bond0
```

`/proc/net/bonding/bond0` shows the mode, the transmit hash policy, the MII polling interval, each port's link state and, for 802.3ad, the aggregator ID of every port, the partner's system MAC, and the actor and partner state flags. Ports with different aggregator IDs did not negotiate into one group, which is the usual sign of a mismatch.

Monitoring defaults to polling the carrier. The driver's `miimon` parameter sets the interval in milliseconds, and the Rocky guide notes that 100 ms suits most sites and can be lowered if failures are noticed too late [src: rocky-docs b37472a0a943ec9b]. systemd-networkd calls the same setting `MIIMonitorSec=` and defaults to disabled, so a networkd bond must set it [src: man-pages 3a07a73854d9551c]. `lacp_rate` is the rate this end asks its partner to use when sending LACPDUs, with slow (one every 30 seconds) as the default and fast one per second, so it does not change how often the local end transmits [web: docs.kernel.org]. `UpDelaySec=` and `DownDelaySec=` debounce flapping links.

The **transmit hash policy** chooses the outgoing port per flow. `layer2` hashes MAC addresses, `layer2+3` adds IP addresses, and `layer3+4` adds ports for the best spread, with the caveat that fragmented traffic can be reordered [src: rocky-docs 9ffb356c3109b324]. The kernel's bonding document names three more values. `encap2+3` and `encap3+4` run the flow dissector first, so a tunnelled packet is spread by its inner headers, which matters for the WireGuard and IPsec traffic of LNX-202-T07. `vlan+srcmac` hashes only the VLAN ID and the source MAC, an intended fit for a hypervisor bond shared by guests that each sit in their own VLAN when the switch has no LACP support. The same text states that `layer2+3` and `layer3+4` are not fully 802.3ad compliant, since fragments of one conversation can use different ports [web: docs.kernel.org]. Because the hash picks a port per flow, a single TCP stream never exceeds one port's speed, and a bond adds capacity only across many flows. The receiving direction is chosen by the peer's own hash, so both ends need appropriate settings.

### VLANs

A VLAN device is a child of a parent interface that tags frames with a 12-bit ID on the way out and strips the tag on the way in.

```bash
ip link add link bond0 name bond0.20 type vlan id 20
ip addr add 192.0.2.10/24 dev bond0.20
ip link set bond0.20 up
ip -d link show bond0.20      # detail: protocol 802.1Q id 20
```

IDs 1 to 4094 are usable, and 0 and 4095 are reserved. The MTU of the child cannot exceed the parent's, and the tag costs four bytes, so a link carrying tagged frames at a 1500-byte payload needs a path that accepts 1504-byte frames.

### Bridges with VLAN filtering

```bash
ip link add br0 type bridge vlan_filtering 1 stp_state 1
ip link set bond0 master br0
ip link set tap-vm1 master br0
bridge vlan add dev bond0 vid 20            # tagged on the uplink
bridge vlan add dev tap-vm1 vid 20 pvid untagged   # guest sees untagged frames
bridge vlan show
bridge fdb show br br0                      # learned MAC addresses per port
bridge link show
```

`pvid` assigns untagged ingress frames to a VLAN and `untagged` strips the tag on egress, making an access port, while ports without those flags are trunk ports. A bridge also accepts `vlan_protocol 802.1ad` and a VLAN device accepts `protocol 802.1ad`, which selects the provider (service) tag of stacked VLANs, and `vlan_default_pvid` changes the VLAN that new ports receive (1 unless set) [web: man7.org]. The bridge learns source MACs into a forwarding database and floods frames with an unknown destination.

STP is off until `stp_state` is set to a positive value. When it is enabled, the `stp_mode` option (new in recent iproute2) decides who runs it. `auto`, the default, calls the `/sbin/bridge-stp` helper to hand the bridge to a userspace daemon and otherwise uses the kernel's classic STP, `user` and `kernel` skip the helper, and the mode can only change while STP is off. The kernel exposes only per-VLAN-group (`mst_enabled`) state primitives and not an MSTP implementation, so rapid or multiple spanning tree needs a daemon such as `mstpd` [web: man7.org]. With STP enabled the bridge blocks redundant paths, and with a bond underneath STP is usually unnecessary because redundancy is hidden inside the bond. The RHEL guide for virtual machines shows a bridge on top of an active-backup bond, so guests share the physical uplink and survive a port failure, while pointing out that a bridge alone offers no failover [src: rhel-10-docs 36a3cccb5feddb29]. NetworkManager builds the same stack with `nmcli connection add type bond`, `type bridge` and `type vlan`, and netplan describes it under `bonds:`, `bridges:` and `vlans:`.

### The same stack as persistent files

Commands typed with `ip` vanish at reboot. With systemd-networkd, the bond, the bridge and the VLAN rules become files, and the key names mirror the options used above [web: freedesktop.org].

```ini
# /etc/systemd/network/10-bond0.netdev
[NetDev]
Name=bond0
Kind=bond
[Bond]
Mode=802.3ad
MIIMonitorSec=100ms
LACPTransmitRate=fast
TransmitHashPolicy=layer3+4
MinLinks=1

# /etc/systemd/network/11-bond-ports.network
[Match]
Name=eth1 eth2
[Network]
Bond=bond0

# /etc/systemd/network/20-br0.netdev
[NetDev]
Name=br0
Kind=bridge
[Bridge]
VLANFiltering=yes
STP=no

# /etc/systemd/network/21-bond0.network   (uplink is a trunk port of the bridge)
[Match]
Name=bond0
[Network]
Bridge=br0
[BridgeVLAN]
VLAN=20

# /etc/systemd/network/22-vm1.network     (guest port: untagged access port in VLAN 20)
[Match]
Name=tap-vm1
[Network]
Bridge=br0
[BridgeVLAN]
PVID=20
EgressUntagged=20
```

`networkctl status bond0` and `bridge vlan show` confirm the result. NetworkManager and netplan express the same objects under their own names, so the model in the head (ports, aggregate, switch, VLAN rules) matters more than the syntax. Two kernel options matter for failover testing. `min_links` keeps the bond's carrier down until that many ports are up, so a switch or router is not told that a crippled bond is healthy. `ad_select` chooses how the active aggregator is picked when several partners respond [web: docs.kernel.org].

### The generalised pattern

Aggregate below, separate in the middle, share above. Each layer solves one problem (capacity and failover, isolation, attachment), and a fault is found by asking at which layer the expectation first fails.

## Assessment: the good, the bad and the ugly

**The good.** Everything is in the mainline kernel, scriptable, observable through `/proc` and `bridge`, and fast enough for line rate on commodity hardware. One bridge with VLAN filtering replaces a thicket of per-VLAN bridges. LACP detects a port that is up but not passing partner traffic, which carrier polling alone cannot do.

**The bad.** Flow hashing means uneven load, and one large transfer never uses more than one member. Mode mismatches fail quietly: a switch group configured static while the host speaks LACP can look half alive. MTU must match on parent, bond, bridge and VLAN children. Firewalls interact with bridges, since bridged frames pass through the iptables hooks only when the `br_netfilter` module is loaded, which surprises people who expect layer 2 to be invisible to filtering.

**The ugly.** Loops. A bridge that connects two ports of the same switch without STP floods frames until the network collapses. Changing a live bond over SSH can cut off the session, because a port is reconfigured while it joins (most modes rewrite its MAC address to the bond's). The terminology around master, slave and port differs between kernel, tools and vendors, which makes searches and logs confusing.

## Applications beyond this domain

The same ideas appear wherever a switch is virtualised. Kubernetes nodes often use a bridge or a macvlan for pod attachment. Cloud hypervisors present guest NICs as ports on a software bridge, with VLAN or VXLAN tags for tenant separation. Hardware switches run the same LACP and spanning-tree protocols, so what is learned between two Linux peers transfers to an enterprise rack. Link aggregation also shows up in storage networks, where multipath I/O replaces it for iSCSI, and in Wi-Fi infrastructure that bonds uplinks for access points. The Rocky guides on VLAN passthrough for Intel and Marvell cards show the hardware side: a bridge with VLAN filtering works only if the NIC passes tagged frames to the host unchanged [src: rocky-docs cab2f7ce84c38659].

## Examples

**A working one.** Two Linux hosts are joined by two cables, each with an 802.3ad bond (`miimon 100`, `layer3+4`). `cat /proc/net/bonding/bond0` on both ends shows one aggregator ID for both ports. A test with several parallel `iperf3` streams uses both cables, and pulling one cable moves traffic to the other within a few polling intervals.

**A failing one.** The same hosts, but one end is set to `xmit_hash_policy layer2` with all traffic between two fixed MAC addresses. Every flow hashes to the same port, the second cable stays idle, and the bond looks healthy. The fix is to hash on IP addresses and ports, or to add parallel addresses.

**A second failure.** A VM on `br0` cannot reach its gateway although the bridge shows the tap port. `bridge vlan show` reveals that the tap port still has the default VLAN 1 while the uplink carries only VLAN 20. Adding `pvid untagged` for VLAN 20 on the tap port fixes it.

**A closing check.** Measure the bond as LNX-202-T10 describes, with several parallel flows and a look at the per-port counters (`ip -s link show eth1`), and compare the result with the hash policy. LNX-202-T11 covers what changes when the peer is a vendor switch, and LNX-202-T09 shows that ECMP routing makes the same per-flow choice through `net.ipv4.fib_multipath_hash_policy`.

## Related problems and ideas

### Related

- **Team devices, macvlan and ipvlan, Open vSwitch** and the hardware-offloaded switchdev model all address parts of the same problem.
- **VXLAN** extends a layer 2 segment across layer 3 for data centres, and is the reason tenant networks no longer depend on the physical VLAN limit of 4094.
- **Multi-chassis link aggregation (MLAG)** lets one host bond to two different switches, which a plain 802.3ad bond cannot do without the switches cooperating.

### Opposing approaches

- **Routing to the host.** A layer 3 design gives every host a routed uplink (or two, with ECMP) and uses no layer 2 across the fabric. It removes spanning tree and the large failure domain of a flat network, and it requires applications and addressing that tolerate it. The cost is that live migration and simple VLAN extension become harder.
- **EVPN and shortest path bridging** replace spanning tree in large fabrics with a control plane, and keep the tenant-facing illusion of one segment.
- **Containers without a bridge.** macvlan or ipvlan attach a container straight to the uplink, skipping the bridge's forwarding table. It is simpler and faster, and the host itself cannot talk to its own macvlan children without extra configuration.
- **Userspace teaming.** `teamd` offered per-port runners and finer logic in userspace. It is declining in favour of the in-kernel bond, but its argument, that policy belongs outside the kernel, resurfaces in Open vSwitch.

## Active research

Work continues on offloading switching to NICs and switch ASICs through the kernel's switchdev interface, on fast bridge forwarding paths (including per-VLAN statistics and multicast snooping improvements), and on measuring how hash policies behave with encrypted or tunnelled traffic, where inner headers are hidden from the transmit hash. Open questions include fair load spreading for few large flows and standard behaviour for MLAG across vendors.

## Future direction

Expect more of the bridge to move into hardware, with VLAN filtering and the forwarding database handled by NIC or switch silicon while Linux remains the control plane. Teaming in userspace is declining, and the in-kernel bond and bridge are the stable platform. Watch the kernel release notes for bridge VLAN options and for changes to bonding terminology and defaults.
