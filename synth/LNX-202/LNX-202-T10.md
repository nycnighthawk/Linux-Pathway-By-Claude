# Measuring whether a link really runs at line rate

## Define the problem

A 10, 25 or 100 Gb/s port is sold by its signalling rate, but applications see whatever the host, the driver and the path deliver. Someone has to answer whether the link achieves its rated bit rate, whether it sustains the packet rate that small frames demand, where the bottleneck lies when it does not, and whether a change (a new bond, a tunnel, a driver setting) helped. Failure looks like a test that reports a third of the expected speed because it used one TCP stream on one CPU core, a UDP test that blames the network for loss that was a full socket buffer, or a number that cannot be compared with last quarter's because the settings were not recorded.

This slice covers the method and tools for throughput and packet-rate measurement between Linux hosts, and for finding which resource limits them: link, CPU, interrupts, buffers or the other end.

## History and approaches

Early throughput tests copied a large file and timed it, which measured disks and protocol overhead as much as the network. `ttcp` (1984) and `netperf` introduced memory-to-memory tests, and iperf (2000s) became the standard for TCP and UDP throughput with a server and client mode; `iperf3` rewrote it with JSON output and a different control protocol. For packet-rate work, generators had to avoid the normal stack: the kernel module `pktgen`, then DPDK-based tools such as TRex and MoonGen, and hardware testers from vendors, which can send 64-byte frames at the full 14.88 million per second that a 10 Gb/s link allows.

The Red Hat guides describe the common practice for throughput tests: run `iperf3` in server and client mode between two hosts, make sure nothing else loads the link, and treat results as indicative because real applications use different buffer sizes [src: rhel-10-docs dd7feaf79b3bada6]. The Firecracker project documents a thorough example of reporting: a table by segment size and direction, the instance and kernel used, the number of parallel clients and the stated goal of saturating one emulation thread [src: firecracker-docs ba18cc0bacbea8df]. The pattern: **fix the method, vary one thing at a time, record everything, and read the counters on both ends**.

## Current state

### Method

State the question first: raw link speed, single-flow speed, small-packet rate, or application rate. Test the path in stages: host to host on a direct cable, then through the switch, then through the real path. Record NIC model, driver and firmware, kernel version, MTU, offload settings, bond mode and hash policy, CPU model and governor. Check the rated speed on both ends with `ethtool eth0 | grep Speed`; the RHEL procedure does the same before its tests [src: rhel-10-docs dd7feaf79b3bada6]. Make runs long enough to settle (30 to 60 seconds), repeat several times and report the spread, not one number.

### Tools and options

```bash
# server
iperf3 -s
# client: one stream, then several in parallel, then reverse direction, then both directions
iperf3 -c 192.0.2.20 -t 30
iperf3 -c 192.0.2.20 -t 30 -P 8
iperf3 -c 192.0.2.20 -t 30 -R
iperf3 -c 192.0.2.20 -t 30 --bidir
# UDP at a target rate, with loss and jitter figures
iperf3 -c 192.0.2.20 -u -b 9G -l 1400 -t 30
```

`-P` runs parallel streams, essential above 10 Gb/s because one TCP stream is bound to one core; `-R` reverses the direction; `-u -b RATE` sends UDP at a chosen rate; `-l` sets the buffer length; `-J` writes JSON; `-A` pins to a CPU; `-w` sets the socket buffer. iperf3 opens TCP port 5201 for control and uses it for data in TCP tests; a UDP test begins with that TCP control connection and then moves the data to a UDP socket bound to the same number [src: rhel-10-docs 8e9cd1239c333906]. UDP tests may need larger socket buffers (`net.core.rmem_max`, `wmem_max`) to avoid losses inside the host [src: rhel-10-docs 8e9cd1239c333906]. For faster links the Red Hat guide also states that the NIC should support accelerated receive flow steering and have it enabled [src: rhel-10-docs dd7feaf79b3bada6].

### Packet rate and arithmetic

On Ethernet each frame carries 20 bytes of preamble and gap on the wire. A 10 Gb/s link therefore carries at most 10 000 000 000 / ((64 + 20) × 8) = 14.88 million 64-byte frames per second, and about 812 000 frames per second of 1518 bytes. A host that reaches full speed with large frames but 10 percent of it with small ones is limited by per-packet cost, not by bits. Use `pktgen` or a dedicated generator for packet-rate tests, since iperf3 cannot send small packets fast enough.

### Finding the bottleneck

While the test runs, watch both ends:

```bash
mpstat -P ALL 1                # one core at 100% soft-irq or sys: per-queue CPU limit
sar -n DEV 1                   # rx/tx rates per interface
ip -s -s link show eth0        # drops, overruns, errors
ethtool -S eth0 | grep -Ei 'drop|miss|err|fifo'   # driver counters
nstat -az | grep -Ei 'retrans|drop'
cat /proc/interrupts | grep eth0
ethtool -l eth0; ethtool -g eth0                 # queues and ring sizes
```

Typical findings: one queue and one core saturated (spread with more RSS queues or interrupt affinity, or `-P` parallel streams); rx ring overruns (raise with `ethtool -G eth0 rx 4096`); retransmissions from a small switch buffer; MTU mismatch; a power governor holding the CPU slow; TLS or tunnels using the CPU. A bond adds capacity only across flows, so test a bond with several parallel streams that hash to different ports.

## Assessment: the good, the bad and the ugly

The good: with a clear method, a handful of commands finds most bottlenecks in minutes, and the numbers are comparable across years. iperf3's JSON output makes trends scriptable.

The bad: iperf3 results depend on the buffer, stream count, CPU placement and the other end; the same link gives very different figures with different settings. Virtual machines and shared hardware add noise, and a test between two guests tells little about the physical link.

The ugly: tests that load production links, results quoted without settings, UDP loss blamed on the network, and tuning copied from guides for a different NIC. Meeting a rated speed in a lab does not prove the real application will.

## Applications beyond this domain

The same discipline applies to storage and CPU benchmarking: define the question, fix the workload, record the environment, repeat and read the resource counters. Latency measurement uses the same principles with different tools (`ping`, `sockperf`, `perf`). Capacity planning, acceptance tests for new switches and SLAs between providers rely on repeatable throughput tests.

## Examples

A working example: two hosts with 25 Gb/s NICs on a direct cable. A single stream reaches about 9 Gb/s with one core at 100 percent; `-P 8` brings it near 24 Gb/s with the load spread over eight cores. The report records NIC, driver, MTU 1500, 8 streams, 30 seconds, three repeats.

A failing example: a UDP test at 10 Gb/s shows 8 percent loss and the team blames the switch. `nstat` shows receive buffer errors on the receiving host; after raising the socket buffer and using `-l 1400`, loss falls to zero, so the loss was inside the host.

## Related problems and ideas

Latency and jitter testing, TCP congestion control comparison (CUBIC and BBR), Wi-Fi throughput testing, and passive performance monitoring with flow data are neighbouring problems. Hardware offloads, jumbo frames and kernel bypass change the ceiling.

## Active research

Work on precise latency measurement with hardware timestamps, on congestion control for data centres, and on bounding measurement noise in virtualised and cloud environments continues, together with methods that test at line rate with commodity machines.

## Future direction

Expect 400 Gb/s links to move bottlenecks further into memory bandwidth and PCIe, and measurement tools to rely on kernel bypass and multi-queue generators. Standardised test reports are likely to become more common.
