# Dynamic routing on Linux with FRR: OSPF and BGP

## Define the problem

Static routes work until a link fails or a network is added. A router, a hypervisor host in a routed data centre or a Kubernetes node that has several paths needs to learn what is reachable, tell neighbours what it can reach, and switch paths within seconds of a failure, without anyone editing tables. Two jobs differ in scope: inside one organisation, routers share a topology map and each computes the shortest path (an **interior** protocol); between organisations, or between large internal domains, they exchange reachability along with policy about what to accept and advertise (an **exterior** protocol). Failure looks like a neighbour stuck in a half-open state, a route that is learned but never installed, a session that is up while no prefix is exchanged, or a flapping link that churns the routes of a whole site.

This slice introduces FRRouting (FRR), the routing suite for Linux, with OSPF as the interior protocol and BGP as the exterior one, at the level needed to bring up a small topology and read its state.

## History and approaches

Early networks used static tables and RIP, a distance-vector protocol limited to 15 hops with slow convergence. OSPF (RFC 2328, 1998) is link-state: every router floods descriptions of its links, builds the same map and runs shortest-path-first, converging fast, at the cost of more state and design care (areas, with area 0 as the backbone). BGP (RFC 4271) is a path-vector protocol that carries prefixes with attributes such as the AS path and local preference, and runs over TCP port 179. It has been the Internet's glue since the 1990s and moved into data centres, where eBGP on every link replaces the interior protocol.

On Linux, the Zebra project's routing daemons were the first open suite; Quagga forked from it, and FRR forked from Quagga in 2016 under the Linux Foundation. The Debian handbook states the lineage in these terms: FRR is the reference tool, descended from Quagga, which in turn came from zebra, and it kept the zebra name for the daemon that talks to the kernel [src: debian-handbook eeae081f0a252519]. Alternatives are BIRD, OpenBGPD (with `bgpctl` for status) [src: rocky-docs 28534e7e086aed54] and vendor routers. The pattern: **a daemon per protocol feeds one manager (zebra) that installs the winning routes in the kernel table**.

## Current state

### Structure and configuration

FRR is several daemons: `zebra` and `staticd` always run; others (`ospfd`, `ospf6d`, `bgpd`, `ripd`, `isisd`, and so on) are started individually [src: debian-handbook eeae081f0a252519]. Enable them in `/etc/frr/daemons`. On Debian, a daemon also needs its own `/etc/frr/<daemon>.conf` owned by the `frr` user with mode 0640, though current FRR versions read the unified `frr.conf` [src: debian-handbook eeae081f0a252519]. The interface is a router-style CLI, `vtysh`, with `show`, `configure terminal` and `write memory`; scripts use `vtysh -c 'show ip route'`.

```
! /etc/frr/frr.conf (excerpt)
router ospf
 ospf router-id 10.255.0.1
 network 10.0.12.0/24 area 0
 passive-interface default
 no passive-interface eth1
!
interface eth1
 ip ospf network point-to-point
 ip ospf hello-interval 2
 ip ospf dead-interval 8
!
router bgp 65001
 bgp router-id 10.255.0.1
 neighbor 192.0.2.2 remote-as 65002
 no bgp ebgp-requires-policy
 address-family ipv4 unicast
  network 198.51.100.0/24
  neighbor 192.0.2.2 activate
 exit-address-family
```

Checks: `show ip ospf neighbor` (states Down, Init, 2-Way, ExStart, Exchange, Loading, Full), `show ip ospf database`, `show ip route ospf`; `show bgp summary` (neighbour state and prefixes received), `show bgp ipv4 unicast neighbors 192.0.2.2 advertised-routes`, `show ip route bgp`. Enable forwarding in the kernel (`net.ipv4.ip_forward=1`), allow OSPF (IP protocol 89, multicast 224.0.0.5 and .6) and TCP 179 in the firewall. Modern FRR versions require a route map or `no bgp ebgp-requires-policy` before an eBGP session sends or accepts anything, a frequent reason that a session is Established with zero prefixes. For data-centre links, `neighbor eth1 interface remote-as external` brings up BGP unnumbered over link-local IPv6 addresses. BFD speeds up failure detection to hundreds of milliseconds; it must also be configured on the peer [src: cilium-docs 4a0a0e0a34d13f5b].

## Assessment: the good, the bad and the ugly

The good: one open-source suite on commodity Linux speaks the protocols that carry the Internet, with a CLI familiar to network engineers, and supports VRFs, EVPN and BFD. Failures are visible with ordinary tools.

The bad: configuration is order-sensitive and the defaults changed between versions, so older examples may not work. Routes for a protocol can lose to a lower administrative distance route from another source. Documentation for both the Debian and the upstream packaging varies in where files live.

The ugly: BGP is a trust system. A misconfigured filter can leak or hijack prefixes at global scale, and session resets during a software upgrade can drop traffic. OSPF with the wrong network type or MTU mismatch sticks in ExStart, which beginners rarely guess.

## Applications beyond this domain

Kubernetes load balancers such as MetalLB and the Cilium BGP control plane use BGP to advertise service addresses from nodes; the Cilium documentation describes how the control plane treats peers and link failures [src: cilium-docs 8b9a76a4ca1a117b]. Data-centre fabrics use eBGP with unnumbered links, and anycast services (DNS, CDN) announce one prefix from many sites. Hypervisor hosts advertise VM addresses so that the network needs no layer 2 stretch.

## Examples

A working example: two Linux routers joined by a point-to-point link, each running OSPF area 0 for the link and its LAN. `show ip ospf neighbor` on both shows Full; `ip route` on router A has the remote LAN with `proto ospf`; unplugging the link removes the route within the dead interval.

A failing example: the same pair, but one side has MTU 9000 and the other 1500. The neighbours stay in ExStart because database descriptions are dropped; matching the MTU, or setting `ip ospf mtu-ignore` as a stopgap, completes the adjacency.

## Related problems and ideas

IS-IS, RIP, BIRD, EVPN with VXLAN, segment routing, MPLS and RPKI route-origin validation are the neighbouring subjects. Static routes with health checks and VRRP are the simpler alternative for small sites.

## Active research

Research covers faster convergence without BFD, RPKI and ASPA deployment to harden BGP, intent-based configuration verified before deployment, and routing for AI training fabrics.

## Future direction

Expect wider use of BGP in server networks, more declarative configuration with validation, and growing RPKI enforcement. Track FRR release notes, since defaults change between versions.
