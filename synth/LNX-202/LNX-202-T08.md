# Packet capture at depth: tcpdump, tshark and where to capture

## Define the problem

When counters, logs and probes disagree with what users report, the only authority is the packets on the wire. Capturing them well is a skill with three parts: choosing the **point** where the capture is made, selecting only the traffic that matters so the capture neither loses packets nor buries the answer, and **analysing** the result, which means more than reading a summary line. Failure looks like a capture that shows nothing because it ran on the wrong interface, a capture full of impossible checksums and giant frames that mislead the reader, a ring of files that overwrote the minute of interest, or a conclusion drawn from a trace taken on the host that produced the problem rather than on the wire.

This slice goes beyond the basic capture of LNX-201: filters in the kernel and in the analyser, long-running captures, capture in namespaces, VLANs, bridges and tunnels, offload artefacts, TLS and encrypted traffic, and analysis with `tshark` (the command-line Wireshark) to produce numbers and tables.

## History and approaches

Packet capture began with the Berkeley Packet Filter in 1992: a small virtual machine in the kernel that runs a user-supplied filter program on each packet, so that only matching packets are copied to user space. `tcpdump` and the `libpcap` library grew on that base. Wireshark (first named Ethereal, 1998) added a graphical, layered decoder and a display filter language, and `tshark` brought the same decoder to the command line; the manual describes it as working much like tcpdump when run with no options and as using the pcapng format that Wireshark shares [src: man-pages 1d8f598f73aaaa65]. The Debian handbook sets the roles in the same way: tcpdump as the long-standing tool with terse output, Wireshark for protocol-layered analysis [src: debian-handbook 52e6abfc37728c2e].

Modern Linux added capture paths that avoid the cost or the blind spots of the classic one. Extended BPF (eBPF) programs run at several hooks; `xdpdump` captures packets at the XDP hook, including packets that an XDP program drops or modifies, which a normal capture cannot see; it records to a pcap file and has no filter or decode of its own, so it is paired with tcpdump for reading [src: rhel-10-docs 3e493bdcdd0f32c3]. Kernel features such as `AF_PACKET` ring buffers, port mirroring (SPAN) on switches and network taps move the point of observation. The pattern is: **choose the vantage point, filter early with BPF, record with a bounded buffer, analyse offline with a decoder**.

## Current state

### Where to capture

A capture on the host is made after the host's own transmit processing and before its own receive processing, so offloading hides or distorts what is actually on the wire. Typical vantage points: the physical interface (what arrives and leaves), a bridge port or a veth end (what a guest or namespace sees), a VLAN or tunnel device (the inner traffic), `lo` (local services), and the special device `any` (all interfaces together, with Linux cooked headers that lose the Ethernet details). In a namespace, run the tool inside it: `ip netns exec red tcpdump -ni veth-r`. For another machine, capture on a mirror port or tap, or over SSH with `ssh host tcpdump -U -w - ... | wireshark -k -i -`. A capture on one side proves what that side sent and received; capturing on both sides and comparing times shows where packets are lost or altered.

### Offload artefacts

With TSO, GSO and GRO the stack handles segments larger than the MTU and leaves checksum calculation to the NIC, so a host capture can show frames of 64 KiB and checksum errors on outgoing packets. These are not faults. For accurate sizes disable offloads while testing (`ethtool -K eth0 gro off gso off tso off`), or capture on the peer or a mirror port, and remember to restore the settings.

### tcpdump in depth

```bash
tcpdump -ni eth0 -s0 -w /var/tmp/web.pcap 'host 192.0.2.10 and tcp port 443'
tcpdump -ni eth0 -G 300 -W 12 -w '/var/tmp/cap-%H%M.pcap' 'not port 22'   # rotate by time, keep 12
tcpdump -ni eth0 -C 100 -W 10 -w /var/tmp/ring.pcap                     # rotate by size (MB)
tcpdump -ni eth0 -e -vv vlan and icmp           # link-level header, VLAN tag
tcpdump -ni eth0 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'
tcpdump -ni eth0 'ip6 and icmp6 and ip6[40] == 135'    # neighbour solicitation
tcpdump -nr web.pcap -A 'tcp port 80' | head
```

`-n` skips name lookups, `-s0` captures whole packets (the old default truncated at 68 or 96 bytes), `-w` writes a pcap file to be read later with `-r`, `-e` prints link-level headers, and `-c N` stops after N packets. Filters use BPF syntax: `host`, `net`, `port`, `portrange`, `proto`, `vlan`, byte offsets such as `tcp[13]`, and `and`, `or`, `not`. After a VLAN tag, BPF primitives need the `vlan` keyword first (`vlan and tcp port 80`). Dropped packets are reported at exit ("packets dropped by kernel"): if the number is above zero, raise the buffer with `-B`, use a narrower filter or write to a faster disk. Capturing needs the `CAP_NET_RAW` and `CAP_NET_ADMIN` capabilities; a packaged tcpdump is often run as root and drops privileges with `-Z`.

### tshark for analysis

`tshark` reads captures with `-r`, applies a **display filter** with `-Y` (a different, richer language than BPF, used after dissection), and prints chosen fields:

```bash
tshark -r web.pcap -Y 'tcp.analysis.retransmission' -T fields -e frame.time_relative -e ip.src -e ip.dst
tshark -r web.pcap -q -z conv,tcp                # conversations with byte and packet counts
tshark -r web.pcap -q -z io,stat,1,'COUNT(tcp.analysis.retransmission)tcp.analysis.retransmission'
tshark -r web.pcap -Y 'http.request' -T fields -e http.host -e http.request.uri
tshark -r web.pcap -q -z follow,tcp,ascii,0       # reassemble one stream
tshark -i eth0 -f 'udp port 53' -Y 'dns.flags.rcode != 0'     # capture filter plus display filter
tshark -r web.pcap -o tls.keylog_file:/tmp/keys.log -Y 'tls.handshake.type == 1'
```

The capture filter (`-f`) is BPF and runs in the kernel; the display filter (`-Y`) is applied afterwards. The expert fields `tcp.analysis.retransmission`, `tcp.analysis.duplicate_ack`, `tcp.analysis.zero_window` and `tcp.analysis.flags` summarise TCP problems. `-z` selects statistics (`conv,tcp`, `io,stat`, `endpoints,ip`, `http,tree`). Because TLS hides payloads, set `SSLKEYLOGFILE` in a client that supports it and give the file to tshark or Wireshark as above, which decrypts that session without breaking anyone else's security. `dumpcap` is the lean capture engine that Wireshark itself uses, suited to long, privileged captures. IPsec and WireGuard payloads stay opaque; capture the inner side on the tunnel device instead.

## Assessment: the good, the bad and the ugly

The good: BPF filtering in the kernel is fast and precise; pcap and pcapng files are portable across every tool, so one file can pass between a server, a laptop and a bug report. tshark turns captures into tables that can be scripted and compared before and after a change.

The bad: volume. A busy 10 Gb/s link fills a disk in minutes, and a capture on the same host as a busy service can itself drop packets or add load. Timestamps depend on the clock and on whether the NIC supports hardware timestamping, which matters for latency work. Display filters and capture filters use different syntax, which causes constant confusion.

The ugly: privacy and law. A capture contains credentials, personal data and, with key logs, decrypted sessions; storing, sharing and deleting it needs a policy. Offload artefacts, `any` cooked captures and bridge or VLAN tags produce misleading traces that look like faults. Captures from busy production hosts may be incomplete without anyone noticing unless the drop counters are read.

## Applications beyond this domain

The BPF virtual machine now lives far outside capture: it filters in firewalls, load balancers, tracing, security tools and the XDP fast path. The same method, capture at a chosen point, compare both sides and measure by field, applies to debugging any protocol: gRPC with its reflection tools, message brokers, database wire protocols and industrial buses all have dissectors. Service meshes and observability platforms collect flow records and packet samples at scale for the same ends. Forensic and intrusion detection systems (Zeek, Suricata) are built on the same capture path and keep long-term indices.

## Examples

A working example: users report slow uploads to a server. A capture on the server for a minute, `tshark -r up.pcap -q -z io,stat,1,...` with the retransmission counter, shows retransmissions climbing in bursts. A second capture on the client side shows the same segments leaving once and the server receiving them twice, so the loss is in the path; `mtr` to the server localises it to one hop.

A failing example: on a virtual host, a capture on the guest's tap device shows huge packets and checksum errors, and the analyst concludes the network is corrupting data. The offloads explain both; the trace taken from a mirror port shows normal 1500-byte frames with valid checksums.

A second failing example: a ring capture meant to catch an intermittent reset is configured with a size-based ring that is too small, and by the time the reset is noticed, the file is overwritten. The fix is a time-based rotation with enough files and a trigger script that copies the relevant file when the alarm fires.

## Related problems and ideas

NetFlow, IPFIX and sFlow summarise flows without full packets; `conntrack`, `ss -ti` and `nstat` expose kernel state; Wireshark's `editcap` and `mergecap` cut and join files; `tcpreplay` replays traces for testing; `pwru` and `perf trace` track where in the kernel a packet is dropped; Zeek turns packets into logs. Hardware taps and packet brokers help at high speed.

## Active research

Topics include capture and analysis at 100 Gb/s and above with kernel bypass, eBPF-based always-on capture with privacy filters, machine-learning detection on flow features, and analysis of encrypted traffic metadata without decrypting it. Wireshark's dissector development tracks new protocols such as QUIC, which hides more header fields from observers.

## Future direction

As QUIC and encrypted DNS spread, endpoint key logging and eBPF visibility inside the host will matter more than wire capture. Expect more integration between pcap analysis and structured logs, hardware timestamping and NIC-assisted filtering. Watch the pcapng specification and the Wireshark release notes.
