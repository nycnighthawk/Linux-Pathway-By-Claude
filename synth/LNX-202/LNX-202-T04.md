# Running DNS yourself: authoritative BIND9, recursive Unbound and DNSSEC

## Define the problem

Every service on a network depends on names. A site that runs its own DNS has to answer two different questions with two different roles: serving the records of its own zones to the world or to the LAN (the **authoritative** role), and resolving names on behalf of clients by walking the tree from the root (the **recursive** or **caching** role). Mixing the roles in one daemon on a public address is the classic mistake. Failure looks like an open resolver used in amplification attacks, a secondary server serving stale data because the serial number was not raised, a zone transfer open to anyone, a validating resolver that answers SERVFAIL for a domain that works elsewhere, or a signed zone that went dark when signatures expired.

This slice covers authoritative service with BIND9 (zones, transfers, access control, checking tools), recursive service with Unbound, and DNSSEC from both sides: signing a zone and validating answers. Client-side lookup and `systemd-resolved` were covered in LNX-201.

## History and approaches

DNS began in 1983 with BIND from Berkeley, which for two decades served as both authoritative and recursive server. Its early versions ran as root and carried a long history of vulnerabilities; version 9, developed by ISC, was a rewrite that can run under an unprivileged account and added DNSSEC support [src: debian-handbook 5de0425ce623de62]. The cache-poisoning attacks of 2008 showed that unauthenticated answers could be forged. DNSSEC, which signs records so a resolver can verify them, had existed since the late 1990s but remained little used; the Debian handbook still calls the standard complex and ties its slow adoption to that [src: debian-handbook 5de0425ce623de62]. The root zone was signed in 2010, which made validation practical for everyone.

The split into specialised daemons followed. NLnet Labs wrote Unbound as a small, secure validating recursive resolver, and NSD as an authoritative-only server; PowerDNS and Knot DNS arrived as alternatives. Distributions now treat Unbound as the default choice for a caching resolver, and the RHEL documentation presents it as a lightweight caching server with DNSSEC validation enabled by default and stronger spoofing resistance [src: rhel-10-docs 4a63316451d38c46]. In RHEL 10 the separate versioned application streams of BIND are gone and a single `bind` package provides version 9.18 [src: rhel-10-docs 56a73df0154c8489]. The pattern is **separate the roles**: authoritative servers hold zones and refuse recursion; resolvers cache and validate and hold no zones except local overrides; DNSSEC adds a cryptographic chain from the root down to each signed zone.

## Current state

### Authoritative BIND9

The main file is `named.conf`; zone data live in files such as `/var/named/example.lan.db`. A minimal authoritative server for one zone:

```
options {
    directory "/var/named";
    recursion no;
    allow-query { any; };
    allow-transfer { none; };
    dnssec-validation auto;
};
zone "example.lan" IN {
    type primary;
    file "example.lan.db";
};
```

The zone file starts with a `$TTL`, an SOA record (primary name, contact, serial, refresh, retry, expire, negative-caching TTL), NS records and then data. The **serial** must increase with every change or secondaries will not transfer; the date-based form YYYYMMDDnn is conventional. A Rocky Linux walk-through of a private server keeps forward and reverse zones in separate files and sets the zone type to master, the older word for primary [src: rocky-docs 50849512bf343e35]. Always check before reloading:

```bash
named-checkconf
named-checkzone example.lan /var/named/example.lan.db
rndc reload example.lan          # reload one zone; rndc status for the daemon
dig @127.0.0.1 example.lan SOA +norec
dig -x 192.0.2.10 @127.0.0.1
```

`named-checkzone` prints the loaded serial and OK on success [src: rocky-docs 0467c6cab81bdd6e]. For a secondary, `type secondary; primaries { 192.0.2.1; };` makes it pull the zone over AXFR (full) or IXFR (incremental), and the primary sends NOTIFY when the zone changes. Zone transfers should be restricted with `allow-transfer` and authenticated with a TSIG key. The compliance benchmark describes the method with a generated shared secret, an `allow-transfer` clause naming the key on the primary and a `server` statement with the key on the secondary [src: compliance-as-code 85fca9cdba88ca90]; its example uses an old HMAC-MD5 algorithm, so on current systems generate the key with `tsig-keygen` and use hmac-sha256.

Recursion should be opt-in. Arch's guide notes that its default configuration limits recursion to loopback to prevent amplification and shows an ACL for the LAN used in `allow-recursion` and `allow-query-cache` [src: archwiki 4dd9f6a143c673d6]. On an authoritative server open to the Internet, set `recursion no`.

### Recursive Unbound

```
server:
    interface: 192.0.2.53
    interface: 127.0.0.1
    access-control: 192.0.2.0/24 allow
    access-control: 127.0.0.0/8 allow
    hide-identity: yes
    hide-version: yes
    prefetch: yes
    cache-min-ttl: 60
    local-zone: "lab.example." static
    local-data: "router.lab.example. A 192.0.2.1"
forward-zone:
    name: "corp.example."
    forward-addr: 198.51.100.7
```

The default for `access-control` is to refuse everything except localhost, so a resolver for a LAN needs explicit entries. The root trust anchor is kept current by `auto-trust-anchor-file` (packaged as `/var/lib/unbound/root.key`); validation is on whenever a trust anchor is configured. Tools: `unbound-checkconf`, `unbound-control reload`, `unbound-control dump_cache`, `unbound-control flush example.org`, `unbound-anchor` for the anchor and `unbound-host -C /etc/unbound/unbound.conf -v example.org` for a validating test. Forwarding all queries to an upstream, instead of recursing, is done with `forward-zone: name: "."`; DNS over TLS to the upstream uses `forward-tls-upstream: yes` with addresses written as `ip@853#hostname`.

### DNSSEC in practice

A signed zone adds DNSKEY records (a key-signing key and a zone-signing key), an RRSIG signature over every record set, NSEC or NSEC3 records that prove a name does not exist, and a DS record in the parent zone that holds a hash of the child's key-signing key, which links the chain. A validating resolver starts from the root key, follows DS and DNSKEY down, and sets the AD flag when everything checks. A bad signature gives SERVFAIL.

```bash
dig +dnssec example.org SOA              # look for RRSIG and the ad flag in the header
dig +cd +dnssec example.org SOA          # checking disabled: if this works but plain fails, validation is the cause
delv @192.0.2.53 example.org SOA +rtrace # validation trace with the chain
dig example.org DS @a.gtld-servers.net   # what the parent publishes (use the real parent server)
```

BIND 9.16 and later signs automatically when a zone has `dnssec-policy default;` creating keys, rolling them and re-signing with no scripts; `rndc dnssec -status example.lan` shows the state. The operator's one manual step is to publish the DS record at the registrar or parent zone, shown by `dnssec-dsfromkey` or in the BIND log, and to remove the old one after a key-signing key rollover. The current default algorithm is ECDSA P-256 (algorithm 13).

## Assessment: the good, the bad and the ugly

The good: BIND is the reference implementation, with every record type and feature, a long operational history and good checking tools. Unbound is small, fast and safe by default. Modern BIND automates signing, so DNSSEC no longer needs a key management script.

The bad: a BIND configuration file is large and unforgiving, and one syntax error stops the server. Serial numbers are a manual step that people forget. DNSSEC raises the cost of mistakes: an expired signature or a stale DS record makes a domain unresolvable for validating clients only, so the fault looks intermittent. Response size grows, causing fragmentation and truncation over UDP, so firewalls must allow TCP port 53 and large UDP packets.

The ugly: open resolvers and open transfers; split-horizon DNS (different answers inside and outside) done with views, which doubles the configuration and the debugging; and registrar interfaces that make DS changes slow or error-prone. Software supplied by the distribution sometimes lags behind the policy features of the upstream release.

## Applications beyond this domain

The same signed-chain design underlies other trust systems: DANE uses DNSSEC to publish TLS keys and SSHFP records publish SSH host keys; email authentication (SPF, DKIM, DMARC) lives in DNS records; certificate authorities check domain control through DNS challenges for ACME. Service discovery in Kubernetes and in data centres rests on internal DNS servers, often CoreDNS or Unbound, and the same view and forwarding patterns apply. Resolvers with a local zone for blocklists (DNS filtering) are a policy tool for networks.

## Examples

A working example: a lab network runs BIND as primary for lab.example (recursion off, transfers restricted to the secondary by TSIG) and Unbound on the gateway as the recursive resolver, with a forward-zone sending lab.example to BIND. Clients ask Unbound; `dig router.lab.example` answers from BIND through Unbound and `dig +dnssec example.org` through Unbound returns the ad flag.

A failing example: after editing a zone, the secondary keeps serving the old data. `dig @primary lab.example SOA` and `dig @secondary lab.example SOA` show different serials, because the serial was not incremented. Raise it and run `rndc reload`; check that NOTIFY reaches the secondary.

A second failing example: a domain resolves through a public forwarder but returns SERVFAIL through the local Unbound. `dig +cd` returns an answer, so validation is failing; `delv` shows a signature that expired the day before. The owner of the zone must re-sign it; the local fix of disabling validation would remove the protection for everything.

## Related problems and ideas

Encrypted transports (DNS over TLS, HTTPS and QUIC) hide queries from the path, and Unbound can forward over them. Query name minimisation, aggressive NSEC caching, response rate limiting and DNS cookies reduce leakage and abuse. CoreDNS, Knot Resolver, PowerDNS Recursor and dnsmasq are alternative resolvers; NSD, Knot DNS and PowerDNS are authoritative alternatives. Catalog zones help secondaries follow primaries automatically. Multi-signer DNSSEC lets two providers sign one zone.

## Active research

Research covers measuring validation failure rates and the effect of larger signatures, post-quantum signature schemes for DNSSEC, automating the DS update through CDS and CDNSKEY records (RFC 8078 and 7344), and reducing resolver trust in third parties. Work on encrypted resolver discovery (DDR) and on how recursive resolvers behave under attack continues in the IETF and in operator groups.

## Future direction

Expect wider use of automatic key rollovers, parent-child DS automation by registries and more encrypted transport between resolvers and authoritative servers. Algorithm agility will be needed as post-quantum signatures arrive; their size will pressure the UDP limits. Track the BIND and Unbound release notes for changes to defaults.
