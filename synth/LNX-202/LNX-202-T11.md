# Where Linux meets hardware: vendor-switch LACP and SR-IOV

## Define the problem

Two pieces of hardware-specific knowledge sit at the edge of every Linux network design. First, a bond that works between two Linux peers must also work against a commercial switch, whose port-channel configuration, hash options and fallback behaviour differ by vendor. Second, virtual machines that need near-native network performance can be given a slice of the NIC itself instead of a software bridge port. Both need access to real equipment, which is why this topic is a guided exercise rather than a simulated lab. Failure looks like a bond with one working port and one dead port after a switch reconfiguration, a link that flaps during negotiation because one side is static and the other speaks LACP, or virtual functions that exist but cannot reach the network because the switch port does not allow their VLAN or MAC addresses.

This slice is an orientation at depth 1: what to ask, what to configure and what to check, with the details left to vendor manuals.

## History and approaches

Static link aggregation, called EtherChannel or a port group by vendors, was the original method: both ends are told which ports form the bundle, with no negotiation, so a wiring or configuration mistake silently black-holes traffic. IEEE 802.3ad (2000) introduced LACP to negotiate membership, and later became 802.1AX. Linux supports the standard in the 802.3ad bonding mode; the Red Hat bonding reference lists it as requiring an LACP port group on the switch and notes that its difference from balance-xor is exactly this protocol compliance [src: rhel-10-docs aac79091ad266bf0]. Servers that must attach to two switches use the vendor's multi-chassis scheme (MLAG, vPC, MC-LAG), which makes two physical switches present one LACP partner.

Virtualised I/O went through software bridges and paravirtual devices (virtio), then direct assignment of a whole PCI device, then **SR-IOV**: a single physical function (PF) is sliced into several virtual functions (VFs) that share configuration with the PF and can be handed to guests; libvirt describes the capability tree in which a NIC lists its VFs, and notes that the number of VFs differs by manufacturer [src: libvirt-docs 31bf2db5419ca6f1]. The systemd manual describes the benefit: for traffic leaving the host, a VF lowers latency and CPU use because packets skip the host network stack [src: man-pages 75551da44ea41263]. The pattern is **hardware offers partitions and aggregation; the operating system must still match the configuration of the device next to it**.

## Current state

### LACP against a vendor switch

Checklist for the Linux side: bond mode 802.3ad, `miimon 100`, `xmit_hash_policy layer3+4` or `layer2+3` to match traffic, and a deliberate `lacp_rate`. The `lacp_rate` option (`slow` or 0, the default, or `fast` or 1) is the rate at which this host asks the partner to send LACPDUs, every 30 seconds or every second, so it does not tell the Linux side how to read the switch; each end sets its own request [web: docs.kernel.org]. Know the hash policies: `layer2` and `layer2+3` are 802.3ad compliant, `layer3+4` is documented as not fully compliant because fragmented packets of one conversation can take two ports and arrive out of order, and `encap2+3` and `encap3+4` hash on inner headers for tunnel traffic [web: docs.kernel.org]. Other bonding options that matter against a switch are `min_links` (carrier only when that many links are up, which mirrors the Cisco min-links feature), `ad_select` (`stable`, `bandwidth` or `count`), `lacp_active` (`on` by default) and the recent `lacp_strict`, which when `on` forbids falling back to one active interface if no LACP partner answers; the default `off` keeps the fallback [web: docs.kernel.org]. On the switch: a port-channel (or LAG) with the matching member ports, mode active (or at least one side active), the same speed and duplex on every member, a trunk or access mode as the design requires, and the same allowed VLANs. Verification on Linux is `cat /proc/net/bonding/bond0`, looking for one aggregator ID across ports and the partner's system MAC, and `ip -d link show bond0`; on the switch, the vendor's port-channel summary should show members as bundled. A mismatch shows as a port in a different aggregator, or the switch showing members as individual or suspended. If servers must boot over the network before the bond exists, the switch's fallback option (a port forms an individual link when no LACPDUs arrive) is required, and PXE needs the primary NIC on an access VLAN.

Vendors name the same objects differently, which slows every conversation with a network team. The Linux bond is a port-channel on Cisco switches (the `channel-group N mode active` command on a member port also appears on Arista), an aggregated Ethernet interface (`ae0`) on Juniper, a LAG on many others and a trunk in older HP vocabulary, and the standard calls it a link aggregation group in IEEE 802.1AX. Mode `active` on the switch sends LACPDUs unprompted, `passive` only answers, and a pair that are both passive never form a group. When one host must bond to two switches, the pair has to present one logical partner (MLAG, vPC, stacking or similar); from the host the evidence is a single partner system MAC in `/proc/net/bonding/bond0` across both ports, and two different partner MACs means the switches are not cooperating and the bond has formed two aggregators, of which only one is active. The vendor commands above are quoted from general practice, not from a Linux document, so confirm them against the switch's own manual.

### SR-IOV

```bash
# BIOS/UEFI: enable VT-d or AMD-Vi and SR-IOV; kernel: iommu on (intel_iommu=on or amd_iommu=on)
lspci -nn | grep -i ethernet
cat /sys/class/net/eth0/device/sriov_totalvfs
echo 0 > /sys/class/net/eth0/device/sriov_numvfs   # change from a non-zero count only through 0
echo 4 > /sys/class/net/eth0/device/sriov_numvfs
ip link show eth0              # vf 0 .. vf 3 with MAC, VLAN, spoof check, trust
ip link set eth0 vf 0 mac 52:54:00:12:34:56 vlan 20 spoofchk on trust off
```

The kernel documents two ways for a PF driver to enable VFs: a driver module parameter (older) and a write to the sysfs file `sriov_numvfs`, which is the recommended method for new devices; writing 0 disables them again, and `sriov_drivers_autoprobe` controls whether a host driver binds each new VF automatically (set it to 0 when the VFs are meant for `vfio-pci`) [web: docs.kernel.org].

The PF driver creates VFs through `sriov_numvfs`; each VF appears as a PCI device that can be assigned to a guest with VFIO (`vfio-pci`) or through libvirt's `<hostdev>` or `<interface type='hostdev'>`. The PF keeps control of MAC, VLAN, rate and the anti-spoofing checks through `ip link set ... vf N`. systemd also supports VF creation and properties in `[SR-IOV]` sections of `.link` and `.network` files, with keys such as `VirtualFunction=` and `VLANId=`; `SR-IOVVirtualFunctions=` in a `.link` file's `[Link]` section sets how many VFs exist, and `[SR-IOV]` sections configure each one with the keys `VirtualFunction=`, `VLANId=`, `QualityOfService=`, `VLANProtocol=`, `MACSpoofCheck=`, `QueryReceiveSideScaling=`, `Trust=` and `LinkState=`. In a `.link` file such a section also creates the function; in a `.network` file the function must already exist (systemd 251 and later) [src: man-pages 75551da44ea41263]. The `ip link set ... vf N` form accepts more than the example shows: `max_tx_rate` and `min_tx_rate` for rate limiting, `trust on` to let a guest set its own MAC or enter promiscuous mode (needed by some virtual routers and by guests that run their own bridges), `spoofchk` and `link-state auto|enable|disable` to follow or force the physical link [web: man7.org]. Limits: the VF traffic bypasses host firewalls and bridges, and the number of VFs and the offloads are driver-specific. Live migration of a guest that owns a VF needs device support in addition to the libvirt step: Red Hat documents it only for a specific Mellanox generation (ConnectX-7 with minimum firmware, identical firmware and PSID on both hosts, a limit of four such VFs per physical function), using the `mlx5_vfio_pci` driver, the NIC's `switchdev` mode with Open vSwitch on the host, and no post-copy migration or virtual IOMMU in the guest [src: rhel-10-docs 53e46be136feb91a]. The `switchdev` eswitch mode is set with `devlink dev eswitch set pci/<address> mode switchdev`; it exposes one representor netdev per VF on the host, so the host's switch (OVS or the kernel bridge) sees each VF's traffic and can apply policy, which restores some of the visibility that plain SR-IOV removes. When SR-IOV and bonding are combined, the bond usually sits on the PFs and VFs are assigned per guest; guests may bond two VFs from different PFs for redundancy.

## Assessment: the good, the bad and the ugly

The good: LACP against a switch gives standard, negotiated redundancy with failure detection that works beyond carrier loss; SR-IOV gives near line-rate, low-latency guest networking and frees host CPU.

The bad: vendor defaults differ, so a configuration written for one switch does not transfer; VFs complicate migration, filtering and visibility.

The ugly: mismatched static and dynamic modes that half work, firmware or driver bugs that appear only under VF load, and hidden per-NIC limits that appear when the tenth VF is created.

## Applications beyond this domain

LACP's negotiation model recurs in other aggregation schemes; SR-IOV principles apply to GPUs, NVMe and accelerator sharing (multiple virtual functions of one device) and to smart NICs that offload switching to the card.

## Examples

A working example: a hypervisor connects two 25 Gb/s ports to a switch pair with MLAG. Linux runs 802.3ad with layer3+4 hashing; both switch ports are in one port-channel in active mode; `/proc/net/bonding/bond0` shows one aggregator. A failing example: the switch group is static; the bond shows the partner as unknown and only one port carries traffic. Guest NICs with VFs on VLAN 20 work only after the switch trunk allows that VLAN.

## Related problems and ideas

MLAG alternatives such as EVPN multihoming, DPDK and vDPA as other fast guest paths, and switchdev offload of the host bridge to the NIC are neighbouring approaches.

## Active research

Work on live migration with VFs, on offloading virtual switches to SmartNICs and on standard interfaces between guests and hardware (vDPA, virtio hardware offload) continues.

## Future direction

Expect more of the host switching function to move to NIC hardware with Linux as the control plane, and wider use of vDPA to keep guest portability while using hardware speed.
