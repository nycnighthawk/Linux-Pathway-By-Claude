# Handing out addresses with Kea DHCP

## Define the problem

A network with more than a few hosts needs a service that gives each machine an address, a gateway, DNS servers and sometimes a boot file when it connects, and takes the address back when the machine leaves. The service has to survive restarts without handing the same address to two machines, serve many subnets from one server through relays, pin addresses for servers and printers, and be changed without a restart. Failure looks like duplicate addresses after a crash, clients stuck on 169.254.x.x link-local addresses because the server never saw their broadcast, a pool that fills up because lease times are too long for a guest network, or a PXE client that boots the wrong image.

This slice covers the Kea DHCPv4 and DHCPv6 servers: configuration, leases, reservations, relays, hooks and high availability, plus how to check and observe a running server.

## History and approaches

BOOTP (1985) gave diskless machines an address and a boot file from a static table. DHCP (RFC 2131, 1997) added dynamic leases with renewal and a rich option space. For two decades the reference server was ISC DHCP (`dhcpd`), configured with a free-form text file and storing leases in a text file that the daemon rewrote. It was simple and widespread, and its monolithic design made scripting and live changes hard. Alternatives included dnsmasq (small networks, combined with DNS), the udhcp servers in BusyBox, and Windows or appliance servers.

ISC declared `dhcpd` end of life in 2022 and built **Kea** as its successor: a modular server with a JSON configuration, separate daemons for DHCPv4, DHCPv6 and dynamic DNS updates, a lease database that can be a file or a SQL server, a management API and loadable hook libraries. Distributions followed. The Red Hat documentation introduces Kea as a server where each protocol has its own configuration file and its own service [src: rhel-10-docs 89d5c8f99799e5eb], and the Rocky Linux 10 release notes state that Kea replaces the end-of-life ISC server and that the legacy DHCP client package is gone, with NetworkManager providing the client internally [src: rocky-docs c57535e06ed15980]. The pattern is **a small daemon per protocol, declarative configuration, pluggable storage and an API for everything else**.

## Current state

### Structure

On RHEL-family systems the files are `/etc/kea/kea-dhcp4.conf` and `/etc/kea/kea-dhcp6.conf`, run as the services `kea-dhcp4` and `kea-dhcp6` [src: rhel-10-docs 89d5c8f99799e5eb]. Debian and Ubuntu name the units `kea-dhcp4-server` and `kea-dhcp6-server`. A control agent (`kea-ctrl-agent`) exposes a REST interface, `kea-dhcp-ddns` sends dynamic DNS updates, and `keactrl` starts the set. A minimal DHCPv4 file:

```json
{
  "Dhcp4": {
    "interfaces-config": { "interfaces": [ "eth1" ] },
    "lease-database": { "type": "memfile", "persist": true, "lfc-interval": 3600 },
    "valid-lifetime": 3600,
    "renew-timer": 900,
    "rebind-timer": 1800,
    "subnet4": [
      {
        "id": 1,
        "subnet": "192.0.2.0/24",
        "pools": [ { "pool": "192.0.2.100 - 192.0.2.199" } ],
        "option-data": [
          { "name": "routers", "data": "192.0.2.1" },
          { "name": "domain-name-servers", "data": "192.0.2.53" },
          { "name": "domain-name", "data": "lab.example" }
        ]
      }
    ],
    "loggers": [ { "name": "kea-dhcp4", "output_options": [ { "output": "stdout" } ], "severity": "INFO" } ]
  }
}
```

A reservation is one more object under the subnet, in a `reservations` array: it holds an identifier (usually `hw-address` with the client's MAC), the `ip-address` to give and optionally a `hostname`. Kea's own parser accepts shell-style and C-style comments in the file, which plain JSON tools do not, so strip them before feeding the file to a generic JSON program. Kea listens on the interface named in `interfaces-config` and picks the subnet whose range holds the interface address, or, for a relayed request, the subnet that contains the relay address (giaddr). Check a file before applying it: `kea-dhcp4 -t /etc/kea/kea-dhcp4.conf`.

### Leases

A lease is the period in which the server has assigned an address to a client. The default `memfile` store keeps leases in `/var/lib/kea/kea-leases4.csv` and `kea-leases6.csv`; the Red Hat guide warns against editing those files by hand because Kea keeps the data in memory and rewrites the files on updates, on graceful shutdown, in periodic cleanup and when the API changes a lease [src: rhel-10-docs d9d4d78360326502]. The same guide lists MySQL and PostgreSQL back ends for sites that need shared storage or reporting; `kea-admin db-init` or `lease-init` creates the schema. Timestamps are in UTC. Lifetimes follow the three timers: after half the lifetime a client tries to renew with the server that gave it the lease (T1, `renew-timer`), at seven eighths it broadcasts to any server (T2, `rebind-timer`), and at expiry it must stop using the address.

### Operation and tools

```bash
kea-dhcp4 -t /etc/kea/kea-dhcp4.conf         # syntax and semantic check
systemctl reload kea-dhcp4                   # re-read config (SIGHUP) without dropping leases
journalctl -u kea-dhcp4 -f
curl -s -X POST -H 'Content-Type: application/json' http://127.0.0.1:8000/ \
     -d '{ "command": "lease4-get-all", "service": [ "dhcp4" ] }'    # needs the lease_cmds hook
dhcpdump / tcpdump -ni eth1 port 67 or port 68
```

For tests without a client, `perfdhcp` generates load and `dhclient -d -v eth1` or `nmcli connection up` shows the client side. Hook libraries add features: `lease_cmds` and `host_cmds` for managing leases and reservations through the API, `stat_cmds` for statistics, `ha` for high availability (hot standby, load balancing or passive backup between two servers), `flex_id` for non-MAC identifiers and `run_script` for external actions. Client classes match on vendor options and select options such as the boot file; PXE setups set `next-server` and `boot-file-name` per class. The DHCPv6 server uses `subnet6`, address pools and prefix-delegation pools (`pd-pools`) and identifies clients by DUID, which the previous topic described.

## Assessment: the good, the bad and the ugly

The good: configuration changes need no restart, the API makes automation straightforward, the SQL back ends allow several servers to share leases, and Stork (ISC's dashboard) gives monitoring. High availability is built in.

The bad: JSON is verbose, so large files are hard to read and review, and a missing comma stops the daemon; comments help but are lost whenever the file is rewritten through the API. Many features need hook libraries, some of which are only in paid or separately packaged forms depending on the distribution. The lease CSV store is not for multi-server use, and mixing the packaged defaults of different distributions is confusing.

The ugly: relays and broadcast. A request that comes through a relay with the wrong giaddr falls into no subnet and gets no answer, without much logging at INFO level. Raw sockets mean the server needs capabilities and does not work on interfaces that have no address. Reservations that overlap pools produce subtle conflicts. DHCP offers no authentication, so a rogue server on the same segment wins races; DHCP snooping on the switch is the defence.

## Applications beyond this domain

Lease-based allocation with timers and renewal is a pattern found in many systems: distributed locks, IPAM in cloud networks, Kubernetes node leases and the allocation of DHCPv6 prefixes to customer routers. Kea's hook design is used as a model for server extension in other infrastructure daemons. The same options and client classes carry over to automated provisioning, such as PXE and HTTP boot in installation servers, and to configuring phones and access points from option 66 and vendor classes. Compliance rules for hardened hosts also address the opposite case, where machines should not run a DHCP server at all, by checking that the Kea services are disabled and the package is removed [src: compliance-as-code aba7ce4852d07682].

## Examples

A working example: a lab gateway runs Kea DHCPv4 on `eth1` with the file above. A new client sends DISCOVER, gets an OFFER from 192.0.2.100 to .199, requests it and receives an ACK with a lifetime of one hour. `tcpdump` shows the four packets on ports 67 and 68, and the CSV file gains a line. The printer with the reserved hardware address always receives 192.0.2.20.

A failing example: after editing the file, `systemctl reload kea-dhcp4` fails silently and clients keep their old settings. `kea-dhcp4 -t` points to a trailing comma. The lesson is to test before reload and to keep the previous file.

A second failing example: a branch office behind a relay gets no addresses. The server log shows packets arriving but no matching subnet; the subnet was defined with the router's LAN address range, while the relay forwards with another interface address. Adding a subnet for the relay's network, or setting `relay` with the right address, fixes it.

## Related problems and ideas

dnsmasq and systemd-networkd's built-in DHCP server cover small networks. DHCP failover in the ISC sense and Kea's HA protocol differ, so mixed pairs are not supported. IPAM databases (NetBox and similar) can generate Kea configuration. Static addressing from cloud-init, router advertisements for IPv6 and network boot protocols such as iPXE overlap with it. DHCP over relay agents with option 82 carries port information for network access control.

## Active research

Work continues on faster lease databases at large scale, on safer high availability under split-brain and on DHCPv6 prefix delegation in service-provider networks, including accounting and fault handling. Standards work covers DHCP option cleanup, privacy of identifiers (random MAC addresses on phones make reservations unreliable) and the interaction with router advertisement flags.

## Future direction

Expect more distributions to ship Kea as the only DHCP server and to drop legacy client tools, as the Rocky 10 notes show. Declarative, API-driven management with Stork and IPAM integration should grow, and wider use of randomised client identifiers will push sites towards classes and options instead of hardware-address reservations.
