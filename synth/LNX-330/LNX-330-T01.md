# The kernel tree, its releases, stable and long-term branches, and maintainers

## Define the problem

The Linux kernel is one of the largest collaborative software projects in existence. Each release contains several million lines of code and takes in changes from well over a thousand developers, employed by hundreds of companies and working in dozens of time zones. Someone who wants to change the kernel, or merely to use it responsibly, faces questions that the code itself does not answer. Where does a change go, and who decides? Which tree is the right one to build against or to base a patch on? How long does a release receive fixes? When a bug is fixed upstream, how does the fix reach the older kernel that a distribution or a device ships? Who owns a given file?

Without a working model of the tree structure, the release rhythm and the maintainer hierarchy, a contributor sends patches to the wrong people, bases them on the wrong branch, reports bugs against kernels that no longer receive fixes, and misreads the version string of the machine in front of them. This slice gives that model: the layout of the source tree, the mainline and `linux-next` flows, the merge window and release candidates, stable and long-term-support (LTS) branches, the `MAINTAINERS` file and the subsystem tree hierarchy, and how downstream distribution kernels relate to all of it. It does not cover the patch submission mechanics (a later topic) or how to build a kernel.

## History and approaches

**Odd and even series.** Early Linux used a two-track numbering scheme. Even minor numbers (2.4, 2.6) were stable and odd ones (2.5) were development. This gave users a clear stable line but had a heavy price: the development series diverged for years, distributions backported features from it into the stable line, and a release such as 2.4 to 2.6 took far too long to arrive. Users of the stable series saw few new drivers; developers of the development series saw their work unused for years.

**The 2.6 time-based model.** In 2003 the kernel moved to a single mainline where new features continuously merge, and in 2005 the practice settled into a periodic release rhythm. Version 3.0 (2011) and 4.0 (2015) were renumbered for convenience when the minor numbers grew large, not because of any change in policy. The current numbering increments the major version when Linus Torvalds feels the minor number is getting unwieldy, so version numbers carry no compatibility meaning (to verify against the current release notes if a claim about numbering is needed).

**Merge window and release candidates.** A development cycle lasts about nine to ten weeks. In the first two weeks, the *merge window*, subsystem maintainers send pull requests of everything they have accepted, and Linus merges them. At the close of the window he releases `-rc1`. During the following weeks only fixes are accepted, with a new release candidate about each week (`-rc2`, `-rc3` and so on), until the code is judged ready, usually after `-rc7` or `-rc8`, and the final release is tagged. The next merge window then opens immediately. This rhythm made releases predictable and caps how long any change waits.

**Subsystem trees and the maintainer hierarchy.** The kernel is divided into subsystems (networking, filesystems, memory management, drivers by bus and class, architectures). Each has a maintainer and often a tree in git. Patches go to the subsystem's mailing list for review and, once accepted, into the subsystem maintainer's tree. Several levels of delegation exist: a driver maintainer, a subsystem maintainer, and sometimes an area maintainer above that, each sending a signed pull request upward. Linus is the top and merges the maintainers' trees. The `MAINTAINERS` file at the root of the source tree is the authoritative map from files to the people and lists responsible.

**linux-next.** Because many trees merge into mainline in a short window, conflicts and breakage between trees used to surface late. Stephen Rothwell started `linux-next` in 2008, a tree that is rebuilt daily by merging all subsystem trees that are intended for the next merge window. Build failures and conflicts show up there first. It is an integration test and is not a release; its tags are named `next-YYYYMMDD`. Maintainers are expected to have their trees in `linux-next` before the merge window opens.

**Stable kernels.** Mainline moves fast and does not receive fixes for old releases. Users, distributions and device vendors need kernels that stay stable. In 2005 Greg Kroah-Hartman and Chris Wright began the *stable* series: after a mainline release x.y, fixes that are already in mainline are selected and released as x.y.1, x.y.2 and so on. Stable rules require that a patch be small, fix a real bug that bothers people, already be upstream in mainline, and not add features. A stable branch is supported until the next mainline release has had a few stable updates, then marked end of life.

**Long-term support.** Some branches are selected for long maintenance. Historically these were announced as long-term series (2.6.16, 2.6.32, 3.2 and so on); today one release per year, normally the last of the year, becomes a *longterm* kernel with a stated end-of-life date, typically several years. The `kernel.org` releases page and the `releases.json` file list the current mainline, stable and longterm versions and mark end-of-life ones. Companies that need longer support, such as the Civil Infrastructure Platform for industrial users, take over selected LTS branches (the SLTS kernels) with their own commitments, while distributions backport selected fixes into their own kernels for the full life of a release.

**Security handling.** A private security list handles vulnerabilities, and since the creation of the kernel CVE numbering authority in 2024 the kernel project assigns CVE identifiers to many fixes after the fact, which led to a large number of identifiers per year. Fixes are submitted to mainline first and flow to stable with the usual tags, which makes the stable tree the main security delivery vehicle for upstream users (to verify the current CVE policy against the kernel documentation).

**Emerging pattern.** One continuously moving mainline on a fixed rhythm; subsystem trees feeding it; `linux-next` as integration test; stable and longterm branches that receive only fixes from mainline; and `MAINTAINERS` as the ownership registry. Downstream vendors build on one of the long-term branches and carry their own patches.

## Current state

**The source tree layout.** The top directory of a kernel source tree contains: `arch/` (architecture-specific code, one subdirectory per CPU architecture), `kernel/` (core scheduler, signals, time), `mm/` (memory management), `fs/` (virtual filesystem and filesystems), `net/` (protocol stacks), `drivers/` (the bulk of the code, by class and bus), `include/` (headers, with `include/uapi` holding the user-visible interface), `Documentation/` (the source of docs.kernel.org), `tools/` (user-space tools such as perf, selftests and bpftool), `scripts/` (build and checking helpers, including `checkpatch.pl` and `get_maintainer.pl`), `samples/`, `security/`, `crypto/`, `sound/`, `block/`, `lib/`, `init/`, `ipc/`, `virt/` (KVM generic code), and the top-level `Makefile`, `Kconfig`, `MAINTAINERS`, `COPYING` and `README`. Drivers account for most lines in the tree; the core is surprisingly small in comparison.

**Version strings.** `uname -r` shows something like `6.12.117-generic` or `6.12.0-55.el10.x86_64`. The first three numbers are the upstream version (major, minor, stable patch level). The suffix is a downstream identifier and often includes the distribution's build number and architecture. A distribution kernel named 6.12 may contain thousands of backported changes from later versions and differs from upstream 6.12.117. Therefore, "this bug exists in 6.12" needs a qualifier: upstream 6.12.x or the distribution's package. The `EXTRAVERSION` and `LOCALVERSION` make-variables and `CONFIG_LOCALVERSION` control the suffix of a locally built kernel.

**Release status as of 16 November 2026.** According to the `kernel.org` releases data fetched for this synthesis, mainline was at 7.4-rc3, the newest stable branch was 7.3.4, branch 7.2 had reached end of life at 7.2.15, and the longterm branches listed were 6.18, 6.12, 6.6, 6.1, 5.15 and 5.10, with `linux-next` at `next-20261113`. This is a snapshot; the live JSON at `https://www.kernel.org/releases.json` is the source of truth, and an exercise in this course parses a saved copy of it.

**Choosing a base tree.** Rules of thumb for a contributor:

- A *new feature or cleanup* is based on the maintainer's subsystem tree (named in `MAINTAINERS` under the `T:` field), or on mainline's latest `-rc` or release if no tree is given, and is aimed at the next merge window.
- A *bug fix for the current development cycle* is based on mainline's latest `-rc` and sent as a fix; maintainers send those during the release candidate weeks.
- A *fix intended for stable* carries a `Cc: stable@vger.kernel.org` tag (with an optional version range), a `Fixes:` tag naming the commit that introduced the bug, and lands in mainline first; the stable maintainers then pick it up or the submitter sends a backport. Fixes for older LTS kernels may need a manual backport when the code differs.
- Do not base work on `linux-next` branches. The tree is rebuilt daily and its history is not stable; use it only to test that your change integrates.

**Reading MAINTAINERS.** Each entry lists a subsystem name, `M:` maintainers, `R:` reviewers, `L:` mailing lists, `S:` status (Supported, Maintained, Odd Fixes, Orphan, Obsolete), `W:` web page, `Q:` patchwork URL, `B:` bug-tracker, `C:` chat, `T:` tree, and `F:` file patterns (with `X:` for exclusions, `N:` for regex patterns, `K:` for keyword patterns). The script `scripts/get_maintainer.pl <patch or file>` applies the file patterns to a patch and prints who should receive it. Entries marked Orphan have no maintainer, which tells a newcomer both that contributions are welcome and that review may be slow.

**Reading the git history.** The kernel's git history is the most informative documentation. `git log --oneline v6.12..v6.13 -- drivers/net/` shows what changed in one area between releases; `git blame` and `git log -S` locate when a line arrived; `git describe --contains <commit>` tells the first release containing it; `git tag --contains` lists releases (including stable) that include it. Commit messages follow a convention (a short subject prefixed by the subsystem, a body explaining why, and tags such as `Signed-off-by`, `Reviewed-by`, `Tested-by`, `Reported-by`, `Fixes`, `Cc`).

**Downstream kernels.** Distributions (Debian, Ubuntu, Fedora, RHEL and rebuilds, SUSE) ship kernels tied to a stable or longterm version, plus backports and their own patches, and a different support lifetime from upstream. Android's Generic Kernel Image program ties vendor kernels to upstream LTS branches. Embedded and appliance vendors often freeze a longterm version for years. The practical consequence is that a bug report from a distribution kernel goes first to the distribution, because upstream developers cannot work on a tree full of unknown patches, and that a person who wants to upstream a driver written against a vendor kernel must port it to current mainline.

## Assessment: the good, the bad and the ugly

**The good.** The model is predictable. A fixed rhythm makes planning possible, the merge window concentrates risk and the release candidate weeks concentrate stabilisation. The maintainer hierarchy scales review: a change is judged by people who know the code. `linux-next` finds integration problems early. Stable and longterm branches give users upstream-quality fixes without upstream feature churn. `MAINTAINERS` and `get_maintainer.pl` remove most guesswork about who should see a change. The history is public, complete and searchable.

**The bad.** The structure depends on people, and maintainers are a bottleneck: patches can sit unreviewed for weeks, orphaned areas get little attention, and maintainer burnout has been a recognised problem. Policies differ per subsystem (patch formats, trees, which tags, whether they use patchwork), so the general rules are a floor, not a script. Stable and longterm kernels carry fewer fixes than mainline, as only patches that reach the stable queue arrive, so a bug fixed upstream without the right tags may never reach LTS users. The version number is a poor guide to what code a distribution kernel actually contains.

**The ugly.** Downstream divergence is severe in some ecosystems. Vendor kernels with hundreds of thousands of out-of-tree lines age for years without receiving security fixes, and hardware vendors have a history of shipping devices with one kernel version and never updating. The large number of CVE identifiers produced for kernel fixes creates a triage burden for downstream security teams, who must decide which are relevant for their configuration. The merge window is a bursty process, and a fix that misses the window waits for the next cycle. Political and personal conflict on mailing lists has driven contributors away, and the kernel adopted a code of conduct in 2018 with a documented enforcement process. Long chains of pull requests make accountability diffuse when a regression is found, though the rule that regressions must be fixed or reverted is firm.

Mitigations: always check `releases.json` or `kernel.org` for the current state; base patches on the tree named in `MAINTAINERS`; tag fixes for stable correctly; report bugs against current mainline when possible and against the distribution's kernel when not; and treat any statement about "the kernel version" as incomplete until the distribution's patch level is known.

## Applications beyond this domain

- **Other large open source projects** copy parts of this model. The Git project's maintainer-run branches (`seen`, `next`, `master`, `maint`) mirror the integration and stable pattern, and the Linux model of delegated trusted maintainers and signed pull requests appears in the Rust, LLVM and many distribution projects in modified form.
- **Release engineering in industry**: time-based release trains (with feature freeze, release candidates and cherry-picked fixes into maintenance branches) are standard practice for browsers, Kubernetes (three minor versions supported), Python and others.
- **Supply-chain and compliance**: knowing which upstream commit fixes which vulnerability and which kernel contains it is a core task of vulnerability management; `git describe --contains` and stable changelogs support software bills of materials and CVE tracking.
- **Distribution and embedded maintenance**: backporting and carrying patches against LTS branches is a daily job for distribution kernel teams, Android, and embedded Linux builders.
- **Hypervisor and cloud engineering**: cloud providers and virtualization vendors track mainline KVM, vhost and driver changes in the same trees and decide what to backport to their guest and host kernels.
- **Open source governance research** studies the kernel as a case of hierarchical review at scale, with measurable effects of review on patch quality and time to merge.

## Examples

**Finding who to ask.** A developer has a fix for `drivers/net/ethernet/intel/e1000e/netdev.c`. Running `scripts/get_maintainer.pl 0001-e1000e-fix.patch` prints the driver maintainers, reviewers, the `netdev` and `intel-wired-lan` lists and the networking maintainers. The patch goes to those addresses, based on the networking tree named in the `T:` field, and not to Linus directly.

**Is a fix in my kernel?** An operator runs `uname -r` and sees `6.6.162`. A fix is described as part of upstream commit `abc123`. In a kernel tree, `git tag --contains abc123 | grep v6.6` lists stable tags that include it; if the first is `v6.6.140`, the operator's kernel contains it. On a distribution kernel with a name like `6.6.0-xyz`, the answer must come from the package changelog, since the upstream tag does not describe the package.

**A fix that never reached LTS.** A use-after-free fix lands in mainline in release 7.1 without a `Cc: stable` tag and without a `Fixes:` tag. Months later, a downstream user of 6.12 reports the same bug. The fix is identified, a backport is sent to the stable list with the original commit id, and it is released in the next 6.12 update. Adding the tags at submission time would have avoided the delay.

**Merge window timing.** A driver series is accepted by its maintainer in week 6 of the cycle, after `-rc5`. It cannot enter the current release, as only fixes are merged after the window, so it is queued in the maintainer's tree for the next merge window and appears in `linux-next` at once, meeting the requirement that code must be in `linux-next` before the window opens.

**A failing example: wrong base.** A contributor builds a patch on the latest `linux-next` tag and sends it with a context that does not apply to the maintainer's tree. The maintainer replies that the series does not apply and asks for a rebase onto the subsystem tree. The contributor loses a week and a review round. The lesson is to apply the series to the maintainer's tree locally before sending.

**EOL surprise.** A team ships a product on kernel 7.2 because it was the newest stable at design time. By the time of release the 7.2 branch has reached end of life, and no upstream fixes follow. The team should have chosen a longterm branch, or planned to track stable releases.

## Related problems and ideas

- **Alternatives to the mailing list model**: forge-based workflows (GitHub or GitLab pull requests) lower the barrier for newcomers but have different review dynamics; the kernel community has experimented with tools such as `b4` and `lore.kernel.org` to bridge the email workflow to modern tooling, covered in a later topic of this course.
- **Distribution kernel strategies**: rolling to the latest stable (Fedora, Arch), staying on an LTS with selective backports (Debian, Ubuntu LTS, RHEL), or taking enterprise backport work to the extreme (RHEL's long-lived kernels).
- **Live patching and backports at scale**: Kpatch, kGraft and livepatch allow applying security fixes without a reboot; the CIP and Android programs apply LTS discipline for long-lived devices.
- **Fork and out-of-tree models**: vendor trees, Android common kernels, and research trees (real-time patches that were upstreamed over many years as PREEMPT_RT) show the cost and eventual path for out-of-tree work.
- **Alternative operating-system governance**: the BSDs use a core-team and commit-bit model, with the base system developed in one repository, which makes a coherent release simpler and spreads maintainer review differently.
- **Memory-safe language adoption** through Rust for Linux illustrates how a controversial, cross-subsystem change moves through the hierarchy, discussed in the drivers course.

## Active research

Research on the kernel as a socio-technical system studies review latency and its effect on contributor retention, the reproducibility and sustainability of maintainer work, and automation that reduces load (bots that run `checkpatch`, build tests, the 0-day infrastructure, KernelCI and syzbot). On the technical side, work examines how to determine automatically which fixes should be backported (machine-assisted stable selection), how to track regression and bug reports (the regzbot project) and how to measure which parts of the tree are exercised by tests. Security research looks at the economics of CVE assignment for the kernel and the time from fix to deployment on downstream systems. The release numbers and policy figures named in this synthesis, including the exact LTS lifetimes, should be checked against kernel.org before they are quoted (to verify).

## Future direction

Expect the cadence of the cycle to continue unchanged, with the number of long-term branches and their lifetimes set by demand from industry programs (the Android and CIP efforts, and the recent extension of support periods). Expect more automation in review, testing and backport selection, and continued growth of Rust in new drivers with the associated process work. Contributors should plan around the merge window rhythm, use the current release status from kernel.org rather than from memory, and treat every version number as an upstream version plus a downstream distribution change set. For products, choose a longterm branch with an end-of-life date past the product's support horizon, and budget for tracking its stable releases.
