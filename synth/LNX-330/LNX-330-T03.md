# Boot testing with QEMU and virtme-ng: trying a kernel without risking a machine

## Define the problem

A kernel developer needs to answer one question many times a day: does the kernel I just built actually start, and does the change I made behave? Answering it on the development machine is dangerous, because a faulty kernel can hang the host, corrupt a filesystem or lose the session. Answering it on a spare physical machine is slow, because each cycle involves copying an image, rebooting and watching a console. And the answer must be machine-readable if it is to run in continuous integration.

The requirements are a disposable machine that starts in seconds, a way to hand it the freshly built kernel without installing anything, a console that can be captured, a way for the guest to report success or failure to the host, and some means of stopping a guest that hangs. Emulators and virtual machines meet all of these. The rest of this topic covers what that looks like with QEMU, the tools built on it, and the limits of testing in a virtual machine.

## History and approaches

**Real hardware and serial lines.** The oldest method is a second machine connected by a serial cable. The target boots the new kernel from a network server or a copied image, and the console is logged on the host. It tests real drivers and real timing, but needs a device per developer, a power switch that can be controlled remotely, and patience. Laboratories of such boards still exist (kernel CI systems run them), but they serve integration testing more than the inner development loop.

**Full-system emulation.** QEMU, started by Fabrice Bellard in 2003, emulates a complete machine in software, translating guest instructions on the fly. Because it can emulate other architectures, a developer on an x86 laptop can boot an arm64 or RISC-V kernel. The `-kernel` option loads a kernel image straight into guest memory, skipping a boot loader, which is the feature that made it a kernel developer's tool: no disk image, no installer, no bootloader configuration.

**Hardware-assisted virtualisation.** KVM, added to Linux in 2007, lets QEMU run guest code natively on the host CPU when the guest and host architecture match. A kernel boot then takes about as long as on bare metal. Where KVM is unavailable (for example inside a container without `/dev/kvm`, or on a CI runner without nested virtualisation) QEMU falls back to its translator, called TCG, which is slower but works anywhere.

**Paravirtual devices.** Emulating a real network card or disk controller in detail is slow. The virtio standard defines simple devices designed to be implemented by hypervisors, with matching guest drivers in the kernel. A test guest typically uses virtio for disk, network and entropy, plus a plain serial port for the console, which is why the guest kernel configuration in the previous topic enables those symbols.

**Wrappers that remove the boilerplate.** A bare QEMU command line for a kernel test has many parts: machine type, CPU, memory, console redirection, a root filesystem, kernel arguments. Projects grew up to hide that. `virtme` (by Andy Lutomirski) and its successor `virtme-ng` boot a kernel with the host's own filesystem shared into the guest read-only, so the guest has a full userland without building an image. `kvm-xfstests` and similar harnesses drive filesystem test suites in a VM. The kernel tree itself has `tools/testing/selftests/` and, for KUnit, a script that starts UML or QEMU for the developer.

Testing kernels used to mean a spare machine and a serial cable, and a mistake meant a reboot by hand. Virtual machines changed the economics: a guest that boots in seconds and can be killed without consequence turns kernel work into something close to ordinary programming. QEMU supplied the machine, direct kernel boot removed the need for a bootloader and an installed disk, and wrappers such as virtme-ng reduced the setup to one command. The effect on practice was large, because tests that were once run rarely, on expensive hardware, can now run after every change.

## Current state

### The minimal boot test

The smallest useful test needs four things on the QEMU command line: the kernel image (`-kernel`), kernel arguments (`-append`), a console (`-nographic` or `-serial`), and something to run as process one. For the console to appear, the kernel arguments must name the serial device, such as `console=ttyS0` on x86 or the platform's equivalent on other machines. Without a root filesystem the kernel boots, finds nothing to mount and panics with a message about being unable to mount root: for a smoke test, that panic text is itself a successful boot, since it proves that the kernel decompressed, initialised memory and drivers and reached the point of looking for userspace.

Machine and CPU selection matter. On x86, the default `pc` or `q35` machines work. On other architectures the machine type must be named; QEMU's per-board documentation lists, for each board, the kernel configuration known to boot and the command line to use. For example, the RISC-V `virt` machine documentation walks through `make defconfig` with `ARCH=riscv` and a cross-compiler prefix, and then boots the result with `-M virt` and a serial console [src: qemu-docs 50a3d06e573ba01e]. The `virt` boards, on RISC-V and arm64, are designed for guests: they expose virtio and a simple interrupt controller rather than imitating a real product, so a generic defconfig plus virtio drivers boots on them.

### Giving the guest a userland

A bare kernel needs a first process. The options are:

- An **initramfs**: a compressed cpio archive passed with `-initrd`. For tests a tiny archive with a statically linked `init` (or BusyBox) is enough. The kernel unpacks it into a memory filesystem and runs `/init`. This is the standard approach for kernel tests, because it is small, fast and fully controlled. A developer can also embed the archive into the kernel image with `CONFIG_INITRAMFS_SOURCE`.
- A **disk image** attached as a virtio block device, with `root=/dev/vda`. This is closer to a real system and is needed for filesystem and storage tests.
- The **host's own filesystem** shared with the guest, which is what `virtme-ng` does. It exports `/` using a paravirtual file-sharing protocol (9p or virtiofs), mounts it read-only as the guest root and overlays a temporary writable layer, so the guest has the host's tools, libraries and even the same home directory. The result is that one command, run in a kernel tree, can build nothing and still start the freshly compiled kernel with a shell. Its documentation describes running with the current tree's kernel by default and passing kernel parameters and a command to run; exact option names should be checked against the installed version (to verify).

### Reporting results

A script needs to know whether the guest passed. Three mechanisms are common.

1. **Console scraping.** The guest prints a line and the host script searches the captured serial log for it, with a timeout. This is simple and works with every machine, but it is fragile if kernel messages interleave with test output.
2. **The debug-exit device.** On x86 QEMU, `-device isa-debug-exit,iobase=0xf4,iosize=0x04` provides an I/O port; when the guest writes a value V to it, QEMU exits with status `(V << 1) | 1`. A test init can write to the port through `/dev/port` or a small helper, and the host reads the exit status directly. There are equivalents on other machines: semihosting calls on arm and RISC-V, the `sifive_test` finisher device on RISC-V virt boards, or power-off handling.
3. **A guest agent or shared file.** The guest writes a result file into a shared directory, or reports over a virtio-serial port or network, and the host reads it after exit.

Power control gives a fourth, blunt signal: a clean `poweroff` from the guest ends QEMU with status zero, while the `-no-reboot` option turns a guest reboot request (including the reboot after a triple fault or panic with a timeout set) into a QEMU exit, so a crashed kernel does not loop forever.

### Hangs, panics and timeouts

Every automated boot test needs a wall-clock timeout around QEMU, because a hung guest never exits. The kernel provides the other half: setting `panic=-1` on the command line makes the kernel reboot immediately after a panic (combined with `-no-reboot` this ends the run), and `CONFIG_PANIC_ON_OOPS`, or the `oops=panic` parameter, turns the first oops into a panic so a failure is not ignored. Lockup detectors and `softlockup_panic` convert some hangs into panics; `CONFIG_DEBUG_*` options and sanitizers add detail at the cost of speed.

### Debugging a guest

QEMU's `-s -S` options start a GDB server on port 1234 and hold the guest at its first instruction. GDB attaches with `target remote :1234`, loads symbols from `vmlinux` and breaks on any function. For this to be pleasant the kernel should be built with debug information and, on some kernels, with address-space layout randomisation disabled (`nokaslr` on the command line), so that symbol addresses match. The `scripts/gdb` helpers shipped with the kernel add commands such as listing modules and tasks (to verify per kernel version). The QEMU monitor allows inspecting devices and snapshots, and `-d` options log guest execution for deep investigation.

### Where this fits in CI

Continuous integration for kernels runs boot tests at scale. Distribution testing uses systems such as openQA, which boots installers and images in virtual machines and compares screenshots and console output against expectations; the Rocky Linux project documents how its testers query openQA through a command-line client [src: rocky-docs 25ee1f05506561b1]. Kernel-focused systems (KernelCI, 0-day, syzbot and others) build many configurations and boot them on emulated and real hardware. A project like QEMU itself recommends contributors test patches locally before relying on its shared CI [src: qemu-docs 6fd701aa9ba56dc9], the same discipline kernel developers follow.

### The generalised pattern: the disposable machine

The idea behind every technique in this topic is a machine that costs nothing to break. It has a kernel under test, a minimal root filesystem, a console that is captured by a script and an exit device or timeout that ends the run with a status. With these four parts, a boot becomes a function: inputs are a kernel and a command, the output is a log and a pass or fail result. Continuous integration, bisection and fuzzing are all this function called in a loop with different inputs. Learning to make the function reliable, with no hangs and no output lost, matters more than learning any single command line.

## Assessment: the good, the bad and the ugly

**The good.** A virtual machine boots in seconds, costs nothing, can be thrown away and can run on every developer's laptop and in every CI job. Serial and exit-code reporting make results machine-readable. Cross-architecture emulation lets one person test several CPU families. Reproduction is easy: a command line is a complete description of the test machine.

**The bad.** Emulation is not hardware. Timing, interrupt routing, memory ordering, DMA behaviour and device quirks differ, so a driver that works under QEMU can fail on silicon, and the reverse. TCG is slow and does not model every CPU feature or race window. KVM needs a host that exposes it, which many hosted CI systems do not. A test that passes in a virtual machine proves the code path ran, not that the hardware works.

**The ugly.** Flaky boots. Timeouts chosen too tight fail on a loaded runner; too loose, they hide hangs for an hour. Console output interleaves with test output and breaks scrapers. Shared host filesystems add their own failure modes. Test results depend on host kernel, QEMU version and CPU, so a bug that appears once in a thousand boots is expensive to chase. The remedy is to make the guest deterministic (fixed seeds, fixed memory and CPU count), log the full command line with every failure, and keep the timeout a deliberate decision.

## Applications beyond this domain

- **Testing operating-system installers and images**, as distribution projects do with openQA and similar tools.
- **Firmware and bootloader development**: U-Boot can be tested in QEMU emulating a board, with the SD card image attached, before touching hardware; the Bootlin training lab for this boots U-Boot on the `vexpress-a9` machine and checks that environment variables persist [src: bootlin-training e6ecf9b848fe95b8].
- **MicroVMs for production isolation**: Firecracker boots minimal guest kernels in a fraction of a second and documents which kernel features (ACPI, PCIe and virtio, among others) a guest kernel needs [src: firecracker-docs eaa6832031a86735].
- **Security research**: fuzzers boot thousands of short-lived guests to find kernel bugs, then replay a crashing input in a fresh guest.
- **Education**: a student can load a hand-written boot sector or a toy kernel with no risk, which is how this topic's lab works.

## Examples

**A smoke test.** A developer builds an x86 kernel with the guest configuration and runs QEMU with the kernel, a serial console and `panic=-1` under a 60-second timeout. The log shows the kernel version banner, driver initialisation and the expected "unable to mount root" panic. The script greps for the banner and the panic and calls the boot good.

**A test init.** The developer makes an initramfs whose `/init` runs a small test binary, prints `TEST: PASS` or `TEST: FAIL` and writes the matching value to the debug-exit port. The host script maps the exit status to the pass or fail of the CI job and saves the serial log as an artifact.

**A hang under TCG.** A test passes on the developer's machine with KVM and hangs on a CI runner without it. The log stops at a calibration delay message. The cause is a timeout that assumed native speed. The fix is a longer timeout when the accelerator is TCG and a log line that records which accelerator ran.

**An address mismatch in GDB.** A breakpoint at a function never hits, because the kernel randomised its base address. Adding the `nokaslr` kernel argument fixes it.

## Related problems and ideas

### Related

- **Kernel configuration** (the previous topic) determines what the guest can do: console, virtio and initramfs support must be built in.
- **Out-of-tree modules** (next topic) are usually tested by loading them into such a guest.
- **KUnit and kselftest** use the same machinery to run in-kernel and userspace tests.
- **Bisecting** a regression relies on a fast, automatic boot test to say good or bad at every step.
- **Snapshots and checkpointing**: saving a booted guest and restoring it is a way to skip boot time for repeated tests.

### Opposing approaches

There are two opposing ways of testing a kernel, and both remain in use. Real hardware reveals timing, firmware and device behaviour that emulation hides, and some bugs appear only there; device labs and board farms exist because of this. At the other extreme, user-mode builds and unit-test frameworks run kernel code without booting at all, which is faster still but exercises less. Virtual machines sit between the two. A thorough project uses all three, in order of cost, and treats a pass in a cheaper layer as permission to try a dearer one.

## Active research

Research and engineering effort goes to faster guest start (microVM-style direct kernel boot, snapshot restore, shared memory images), to deterministic replay of guest executions for debugging, to better hardware models for QEMU, and to fuzzing frameworks that coordinate many short guest runs with coverage feedback from the kernel. Rust-based virtual machine monitors such as Firecracker and Cloud Hypervisor are an active area for minimal device models.

## Future direction

Expect more tests to run in lightweight virtual machines by default, with the host's filesystem shared in, and expect CI systems to standardise on a small set of pass-fail signals (exit device, structured console lines). Nested virtualisation on hosted runners continues to improve, which makes KVM available in more places. Confidential-computing guests (AMD SEV, Intel TDX) add new boot paths that test systems will need to cover (to verify the state of QEMU support).
