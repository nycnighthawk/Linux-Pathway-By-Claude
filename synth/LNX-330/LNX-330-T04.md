# In-tree and out-of-tree modules: where kernel code lives and how it is built

## Define the problem

The kernel can load code at run time. That code, a loadable module, extends a running kernel with a driver, a filesystem, a network protocol or a debugging aid, without a reboot and without carrying every driver in the image. A developer must decide where such code lives and how it is built. Placing it inside the kernel source tree gives it the full build system, configuration options and the review process of the project. Keeping it outside the tree makes it independent, but the kernel offers no stable internal programming interface, so every kernel release can break it.

This topic explains how modules are built both ways, how they are loaded and versioned, what the licence and taint machinery does, and why upstream developers push for in-tree code.

## History and approaches

**Monolithic with modules.** Loadable modules arrived in the 1.x series in the mid-1990s (exact release to verify). Early modules were object files that a user-space program linked into the kernel; the modern mechanism, rewritten for 2.6 with kbuild, produces `.ko` files (kernel objects) that are linked against the kernel's exported symbols at load time and checked by a post-processing tool (modpost) at build time.

**Kbuild.** The kernel build system is built on GNU make, with variables such as `obj-y` for code built into the image and `obj-m` for modules. A directory's `Makefile` or `Kbuild` file lists objects. Multi-file modules name their parts with a `-y` or `-objs` variable. Configuration symbols appear inside the variable name, so `obj-$(CONFIG_FOO) += foo.o` builds a module when `CONFIG_FOO=m` and built-in code when it is `y`.

**External modules.** Kbuild supports a directory outside the tree via `M=`: invoke make in the kernel build directory with `M` pointing at the module source. The module's own Makefile typically has two halves, selected by whether `KERNELRELEASE` is set. When run by hand, it calls back into the kernel build directory; when included by kbuild, it only sets `obj-m` and flags.

**Dynamic kernel module support.** Distributions needed a way to rebuild third-party modules for each new kernel. DKMS (dynamic kernel module support, introduced by Dell) stores module source, rebuilds it on installation of a new kernel and registers the result. Some vendors instead ship prebuilt "kmod" packages tied to one kernel ABI.

**Stable and unstable interfaces.** The kernel's position, documented in its process guides, is that the user-space ABI is stable while internal interfaces change whenever needed. The project's answer to out-of-tree breakage is to get code merged: once in tree, whoever changes an interface fixes the users. This is the central incentive behind the upstream-first policy.

The module mechanism was added so that one kernel binary could serve many machines. Rather than compile every driver in, a distributor ships most as loadable objects and lets the system fetch what the hardware needs. That flexibility created a second world beside the main tree, since vendors and researchers could now ship drivers without upstream review. The history of out-of-tree code is a repeated cycle: a driver appears outside, becomes widely used, and the burden of keeping it working across kernel versions eventually pushes its authors to merge it.

## Current state

### A module in one screen

A minimal module defines an init function and an exit function, registers them with `module_init` and `module_exit`, and declares a licence with `MODULE_LICENSE`. Descriptive macros (`MODULE_AUTHOR`, `MODULE_DESCRIPTION`, `MODULE_PARM_DESC`) feed `modinfo`. Parameters declared with `module_param` appear under `/sys/module/<name>/parameters` and can be given on the command line when loading. Logging uses `pr_*` helpers or device-aware `dev_*` helpers, which attach the device name.

Because modules run in kernel space, there is no libc. Memory comes from `kmalloc` and friends, string helpers are the kernel's own, and an error in init is reported by returning a negative errno, which makes loading fail cleanly.

### Building out of tree

The standard command is `make -C /lib/modules/$(uname -r)/build M=$PWD modules`. The path is a symlink installed by the distribution's kernel-headers or kernel-devel package; it names a directory containing the configuration (`.config`), generated headers and the scripts needed to build modules. The headers must match the running kernel's version and configuration, or the result will refuse to load or misbehave.

A reliable Makefile layout:

- under `ifneq ($(KERNELRELEASE),)`: `obj-m := name.o`, plus `name-y := a.o b.o` for several files and `ccflags-y` for compiler flags;
- otherwise: a `KDIR` variable defaulting to the running kernel's build directory, and `all` and `clean` targets that call `$(MAKE) -C $(KDIR) M=$(CURDIR)`.

Two mistakes recur. If a module has several source files, listing them all in `obj-m` produces several modules, each missing symbols. And naming the module the same as one of its own objects (`foo.o` built from `foo.c` and `bar.c`) makes kbuild confuse the intermediate with the final object; the parts must have distinct names from the result.

Out-of-tree modules also need the kernel's `modules_install` step or a copy into `/lib/modules/<release>/extra`, followed by `depmod`, to be found by `modprobe`.

### Building in tree

Adding a driver to the tree means putting its source in the right subsystem directory, adding a `Kconfig` entry (with `depends on` the subsystem and, where appropriate, `tristate` so it can be a module), and adding a line to that directory's Makefile with the `CONFIG_` symbol. The configuration lesson in this course covers the Kconfig side. In-tree modules get kbuild's full machinery: they are built by a normal `make`, installed by `make modules_install`, signed if module signing is on, and covered by every maintainer's build tests.

A developer can rebuild only one directory: `make M=drivers/net/foo modules` (or the equivalent for a single object) avoids a full rebuild after the tree has been built once.

### Loading, dependencies and versioning

`insmod` loads one `.ko` file as given; `modprobe` loads by name, resolving dependencies recorded in `modules.dep` (generated by `depmod`) and applying options from `/etc/modprobe.d`. `lsmod` lists loaded modules, `modinfo` shows metadata and `rmmod` unloads one that is not in use. Symbols a module uses must be exported with `EXPORT_SYMBOL` (or the `GPL`-only variant); a module cannot call arbitrary kernel functions.

Compatibility between a module and a kernel is enforced by several checks. The `vermagic` string records kernel release and key configuration choices and must match. With `CONFIG_MODVERSIONS`, each exported symbol carries a checksum (CRC) of its type signature and the loader compares it, so a changed structure makes the module fail to load with a message about unknown symbols or version mismatch instead of crashing later. Module signing (`CONFIG_MODULE_SIG`) lets the kernel require a valid signature; with Secure Boot, distributions enforce it, and a developer's own module must be signed with an enrolled key or the check relaxed on a test machine.

### Licences and taint

`MODULE_LICENSE` is not decoration. Some kernel symbols are exported only to GPL-compatible modules, and the loader refuses a module with an incompatible licence string to use them. Loading a module that declares a non-free licence marks the kernel as tainted, shown in oops reports as a flag letter, and upstream developers will generally decline to debug a tainted kernel. Other events also set taint flags: forced module loading, out-of-tree module loading, and a module built with a different compiler. Reading `/proc/sys/kernel/tainted` gives the bitmask.

A missing licence declaration is reported at build time by modpost and results in a taint warning at load time.

### Debugging and developing modules

Fast iteration uses a virtual machine (see the previous topic): rebuild the module, copy it into the guest or share the build directory, and load it there so a crash costs nothing. `dmesg` shows `pr_*` output. Dynamic debug enables `pr_debug` calls per module at run time. Common failure messages include "Unknown symbol", "Invalid module format" and "disagrees about version of symbol", each pointing to a mismatch with the running kernel. The `Documentation` for loadable module support describes the parameters and tooling.

### The generalised pattern: the module is a contract with one kernel build

A loadable module is compiled against the headers, configuration and compiler of a specific kernel, and the loader checks that contract at insertion time through version information and symbol checksums. The generalised view explains the common failures. A module built against the wrong headers is refused or crashes; a module that uses an unexported symbol fails to link; a module built for a kernel with different options misbehaves. In-tree modules avoid the problem because they are rebuilt with the kernel, which is the strongest argument for merging. Out-of-tree modules accept the cost and manage it with DKMS-style rebuilds or per-release builds.

## Assessment: the good, the bad and the ugly

**The good.** Modules keep the kernel image small, allow hardware support to be loaded on demand, and make development fast: unloading and reloading a driver takes seconds. The kbuild interface for external modules is compact, and CRC versioning catches many incompatibilities early. In-tree code is built, tested and updated by the whole community.

**The bad.** Without a stable internal API, out-of-tree modules must track every kernel version, often with conditional code depending on the version. Header packages must exactly match the running kernel. Secure Boot and signature enforcement complicate local experiments. Unloading a module safely is hard: a driver must free every resource, and a reference leak leaves it permanently stuck.

**The ugly.** Vendor drivers shipped out of tree for years, patched against old kernels, taint the kernel and are frequently left unmaintained. DKMS builds can silently fail after a kernel update and leave the machine without network or storage drivers at the next boot. Licence games and proprietary shims cause long-running disputes. Kernel upgrades can break modules that worked the day before, with no warning other than a failed build.

## Applications beyond this domain

- **Linux distributions** use modules for hardware autodetection and for packaging proprietary or out-of-tree drivers (graphics, storage controllers, virtualisation guest additions).
- **Hypervisors** ship kernel modules (for example VirtualBox's host drivers), which makes the DKMS rebuild path an everyday operational concern for virtualisation users.
- **Container hosts** depend on modules for filesystems, networking and security modules, loaded on demand or blocked by policy.
- **Observability** tools historically used modules; eBPF now replaces many of those uses with a verified, safer mechanism.
- **Embedded systems** configure which drivers are built in versus modular to hit boot-time and memory targets, as in the Bootlin embedded kernel training.

## Examples

**A two-file module.** A developer has `main.c` and `util.c` and writes `obj-m := main.o util.o`. The build produces two `.ko` files, and loading `main.ko` fails with unknown symbols from `util`. The fix is `obj-m := hello.o`, `hello-y := main.o util.o`.

**A version mismatch after an update.** A DKMS module stops loading after a distribution kernel update. `modinfo` shows a `vermagic` for the old release. The headers for the new kernel were not installed, so DKMS built nothing. Installing them and re-running the DKMS build repairs it.

**A taint report.** A crash report shows the taint flag for a proprietary module. The upstream maintainer asks for a reproduction on an untainted kernel, so the developer reproduces the bug in a virtual machine without the module.

**An in-tree conversion.** A team upstreams its driver. After review it lands in `drivers/` with a Kconfig entry, and a later API change by another developer automatically updates it.

## Related problems and ideas

### Related

- **Kconfig and kbuild** (the previous topics) control whether code is a module.
- **Boot testing** supplies the disposable machine for loading experimental modules.
- **eBPF** and **kprobes** offer alternatives that do not require compiled kernel modules.
- **Rust for Linux** adds a second language for in-tree and eventually out-of-tree modules, with its own build integration.
- **Live patching** replaces functions in a running kernel, built as modules.

### Opposing approaches

The opposing positions here are about whether out-of-tree code should exist at all. The kernel community's long-standing view is that stable internal interfaces are undesirable, because they would freeze the design, so code outside the tree must follow changes at its own expense. Vendors argue that upstreaming is slow and that products must ship against fixed kernels. Programmable alternatives, such as eBPF, avoid the question by letting verified programs run in the kernel without a module at all. Each answer reflects a different weighting of safety, speed of delivery and freedom to change the kernel.

## Active research

Work includes safer kernel extension (Rust drivers, eBPF), reducing the cost of module signing and verification, lazy or faster module loading, and tooling to detect ABI breakage between kernel builds. Enterprise distributions maintain a list of symbols that they promise not to change (a "kABI" whitelist) so third-party modules can survive minor updates, at significant engineering cost.

## Future direction

Expect more driver code in Rust and more extension logic in eBPF, which reduces unverified C running in kernel space. Distribution policies on Secure Boot, lockdown and signing will continue to tighten what an out-of-tree module can do on a default installation. The upstream-first position is unlikely to change: in-tree remains the only way to have a driver maintained over time.
