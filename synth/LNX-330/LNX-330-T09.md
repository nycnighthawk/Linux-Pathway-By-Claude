# printk, dynamic debug, ftrace, KASAN and lockdep: seeing inside a running kernel

## Define the problem

Kernel code cannot be debugged like an ordinary program. There is no process to attach a debugger to in the usual way, a stopped kernel stops everything, the code runs in interrupt context and on many CPUs at once, and the worst bugs (memory corruption, deadlocks, races) do not fail where they are caused. A developer needs several instruments: a way to log what happened, a way to turn extra logging on without rebuilding, a way to trace which functions ran and how long they took, and detectors that catch whole classes of bugs the moment they occur instead of hours later.

The kernel ships such instruments. This topic covers five of the most used: `printk` for logging, dynamic debug for switchable logging, `ftrace` for tracing, KASAN for memory errors and lockdep for locking mistakes.

## History and approaches

**printk.** The oldest tool is the logging call. `printk` writes into a ring buffer in memory, from which the console, `dmesg` and the system logger read. It has been in the kernel since the beginning and is safe in interrupt context. Over the years it gained message levels, rate limiting, per-device helpers and, in recent versions, a lockless buffer design (with long-running work to make console output not block the caller).

**Debug prints without rebuilds.** Compile-time `#ifdef DEBUG` switches meant a rebuild for every debugging session. Dynamic debug, added around 2.6.30 (release to verify), turns each `pr_debug` and `dev_dbg` call into a patchable site that can be enabled at run time by file, function, module or line.

**Tracing.** Steven Rostedt's ftrace grew from the latency tracer in the real-time patch set and was merged in 2.6.27. It uses the compiler's function-entry hook (`-pg`, patched to no-ops at boot and enabled live) to record function calls, and it hosts a family of tracers (function, function graph, latency tracers) plus tracepoints and events. The same infrastructure underpins `perf`, `trace-cmd` and eBPF attachment. The tracefs filesystem is its control surface.

**Memory error detectors.** Tools such as `kmemcheck` ran the kernel in an emulator and were slow. KASAN (Kernel Address Sanitizer), contributed by engineers at Google and based on the compiler's AddressSanitizer, appeared in 4.0 and detects out-of-bounds accesses and use-after-free by tracking a shadow map of the memory state and instrumenting accesses at compile time. Sibling tools cover other classes: KMSAN for uninitialised memory, KCSAN for data races, UBSAN for undefined behaviour, and the SLUB debugging options.

**Lock validators.** Deadlocks reproduce rarely and are hard to analyse after the fact. Ingo Molnar's lockdep (2.6.18) records, for every lock class, which other classes were held when it was taken, and complains the first time an order is seen that could deadlock, even if the deadlock itself never occurs in that run. It also tracks interrupt-safety states. Lockdep is the reason a large part of locking bugs are found during development.

Kernel debugging grew by accretion in the same way as the rest. The first tool was the print statement, since the kernel has no friendly debugger. Over time came runtime control of messages, a function tracer that records calls without recompilation, memory checkers that catch bugs at the moment of occurrence, and a lock validator that reasons about orderings that have not yet deadlocked. Each tool reduced the distance between a bug and its cause, from guesswork to a trace that points at the line.

## Current state

### printk and the log

A message has a level from `KERN_EMERG` (0) to `KERN_DEBUG` (7). Most code uses wrappers: `pr_err`, `pr_warn`, `pr_info`, `pr_debug`, and, for drivers, `dev_err` and friends, which prefix the device name. `pr_*_ratelimited` and `printk_once` stop a loop from flooding the buffer. Format specifiers include kernel-specific ones such as `%pS` (symbol and offset for an address), `%pe` (an errno value as a name) and `%p` (a hashed pointer, so raw addresses do not leak). The console shows only messages whose level number is lower than the console log level; `/proc/sys/kernel/printk` holds four numbers, the first of which is that level, and `dmesg` shows the whole buffer with filters by level (`-l`), human time stamps (`-T` on supporting systems) and following (`-w`). Boot parameters such as `loglevel=` and `ignore_loglevel` change what appears early. Time stamps in the log are relative to boot, and `printk.time` controls them.

For crashes whose console output is lost, `pstore`, `netconsole` and the serial console are the usual ways to keep the last messages. Message formats are not a stable interface; scripts that parse them break.

### Dynamic debug

With `CONFIG_DYNAMIC_DEBUG`, every `pr_debug` and `dev_dbg` is a site recorded in a table. The control file lives in debugfs: `/sys/kernel/debug/dynamic_debug/control`. Reading it lists sites with their file, line, module and function; writing a query enables or disables them. A query is a set of filters followed by flag changes, for example `module foo +p` enables printing for the module, `file drivers/foo/core.c line 120-140 +pfl` enables a range with function name, line number flags, and `-p` disables again. Flags can add context to each message: `f` (function), `l` (line), `m` (module), `t` (thread id). Boot parameters (`dyndbg="..."`, or `foo.dyndbg=...` for a module) enable messages that fire early, before a shell exists. The cost of a disabled site is small, and it is why drivers use `dev_dbg` generously.

### ftrace

The interface is a directory, usually mounted at `/sys/kernel/tracing`. Key files: `available_tracers`, `current_tracer`, `tracing_on`, `trace` (the buffer, human-readable), `trace_pipe` (a streaming read that consumes), `set_ftrace_filter` and `set_ftrace_notrace` (which functions to trace), `set_graph_function` (the root of a call graph), `trace_options`, `buffer_size_kb` and the `events/` tree for tracepoints.

The common tracers: `function` records each call; `function_graph` records entry and exit with durations, which gives an indented call tree with timings; latency tracers measure the longest time with interrupts or preemption disabled. A typical session writes a function name to `set_graph_function`, selects `function_graph` in `current_tracer`, enables `tracing_on`, runs the workload and reads `trace`. Tracepoints (`events/sched/sched_switch/enable`, for example) give stable, structured events with named fields; `trace_printk` writes a message into the trace buffer, much cheaper than `printk`, useful for timing-sensitive debugging. `trace-cmd` and `kernelshark` record and view traces; `perf trace` and `perf record` use the same hooks; `bpftrace` and BPF programs attach to the same functions and tracepoints for custom aggregation. Kprobes and uprobes add dynamic probes on arbitrary instructions.

Tracing slows the kernel (function tracing a lot), and its output is large; filtering is the main skill. Some functions cannot be traced (the tracing code itself, early entry code) and are marked `notrace`.

### KASAN

Enable `CONFIG_KASAN` (with the generic mode for most debugging; software and hardware tag-based modes exist for arm64 deployments). The compiler instruments loads and stores; a shadow memory region records, for each eight bytes of memory, whether the bytes are addressable. Freed objects are quarantined, so use-after-free is caught for a while after the free; redzones around allocations catch overflows. The cost is memory (about one eighth for the shadow, plus quarantine) and speed (two to three times slower).

A report begins with a line giving the bug type and the function, such as `BUG: KASAN: slab-out-of-bounds in foo+0x..` or `slab-use-after-free`, then the access (read or write, size, address, task), a call trace, and information about the object: who allocated it and who freed it, with stack traces, plus a map of the shadow around the address. Reading it is a skill: the access function is where the bug manifested; the allocation and free traces tell who owns the memory and who let it go. Settings such as `kasan.fault=panic` turn a report into a panic for automated testing. Syzkaller, the kernel fuzzer, runs KASAN-instrumented kernels and many of its bug reports are KASAN reports.

### lockdep and friends

`CONFIG_PROVE_LOCKING` turns lockdep on. Each lock is a class (one per lock initialisation site); the validator builds a graph of orderings and checks every new edge for cycles, plus rules for interrupt contexts (taking a lock in an interrupt handler while also taking it with interrupts enabled elsewhere). A report names the locks, the acquisition stacks and shows a "possible unsafe locking scenario" with two CPUs interleaving, which is the simplest way to understand it. It also detects use of uninitialised locks, unlock of a lock not held and, with `CONFIG_DEBUG_ATOMIC_SLEEP`, sleeping in atomic context. Annotations (`lockdep_assert_held`, `might_sleep`) document requirements in the code and are checked on every run. Lockdep builds are slower, and lockdep disables itself after the first report in a boot, so one report hides later ones until reboot.

Other detectors: KCSAN finds data races with sampling watchpoints; KMSAN finds use of uninitialised memory (Clang only); UBSAN catches undefined behaviour such as shifts out of range; `CONFIG_DEBUG_LIST`, `DEBUG_OBJECTS` and `PROVE_RCU` check data structures and RCU usage. Such options are typically combined in a debugging configuration used in CI.

### A workflow

Reproduce the problem in a VM with a debug configuration; read the first splat, not the last; use dynamic debug to add detail; trace the suspect path with ftrace; confirm with a fix and re-run until clean. Capture the reproduction as a test (previous topics).

### The generalised pattern: observe, instrument, then check

The tools fall into three groups with a natural order of use. Observation (printk, dynamic debug, ftrace) shows what the code did. Instrumentation (KASAN, UBSAN, lockdep, KCSAN) changes the build so that a class of fault is detected immediately instead of corrupting memory silently. Reproduction, supplied by a test, makes either group useful by providing the same failure on demand. A disciplined debugging session starts with a reproducer, adds the cheapest observation that answers the question, and turns on a checker when the symptom suggests a memory or locking cause.

## Assessment: the good, the bad and the ugly

**The good.** The tools are in the tree, maintained with the kernel, and work in virtual machines and CI. KASAN and lockdep turn silent corruption and possible deadlocks into immediate, specific reports. ftrace shows what the kernel actually did, with low overhead when idle. Dynamic debug lets a driver keep rich debug logging with no cost in production.

**The bad.** Debug configurations change timing and can hide races or create false ones. Their slowdown makes some performance bugs unreproducible. Reports need practice to read and some are noisy: lockdep reports of rare or intentional patterns need annotations, and false positives exist. The default kernel of a distribution has these options off, so a bug report from a production system rarely contains a KASAN report.

**The ugly.** printk from the wrong place can itself cause deadlocks or flood the console; heavy logging in a fast path changes behaviour. A lockdep splat in a driver that you did not write is often caused by a different subsystem's rule, and the dependency chain spans modules. Because lockdep stops after the first complaint, one reboot can hide a second bug.

## Applications beyond this domain

- **Application debugging**: AddressSanitizer, ThreadSanitizer and similar compiler instrumentation in user space share ideas with KASAN and KCSAN.
- **Production observability**: tracepoints and eBPF underlie performance tools used in cloud operations.
- **Virtual machine monitors**: debugging KVM and device models uses the same tracepoints (KVM exposes tracepoints for exits, page faults and more) and enables lockdep in test kernels.
- **Embedded and real-time work** use latency tracers to prove worst-case scheduling delays.
- **Firmware and bootloader work** relies on the same discipline of early console output and serial logs, as the U-Boot QEMU lab in Bootlin's training shows [src: bootlin-training e6ecf9b848fe95b8].

## Examples

**Use-after-free found by KASAN.** A driver crashes sporadically. On a KASAN build, the first read of the sysfs file reports `slab-use-after-free` in the read function, with the allocation in probe and the free in remove: remove ran while a reader still held a pointer. The fix adds a reference count.

**A lockdep cycle.** Loading two modules in a particular order produces a possible-circular-locking warning naming two driver locks. One path takes lock A then B in registration; another takes B then A in a notification. Reordering or dropping a lock before the callback removes the cycle.

**Finding a slow path.** A request takes too long. With `function_graph` restricted to the read handler, the trace shows one callee taking most of the time, which narrows the review.

**Switching on messages at runtime.** An intermittent probe failure is investigated by enabling dynamic debug for the module with function names and line numbers, reproducing and reading `dmesg`.

## Related problems and ideas

### Related

- **Boot testing** supplies the machine; **KUnit and kselftest** supply the reproducer.
- **Bisecting** (next topic) finds which commit introduced the bug these tools expose.
- **Crash dumps** (`kdump`, `crash`) analyse memory after a panic.
- **eBPF** and **perf** extend tracing without rebuilding.
- **Static analysis** (sparse, Coccinelle, smatch) finds some of the same bugs without running the code.

### Opposing approaches

Opposing opinions exist about debuggers. Linus Torvalds has long been sceptical of interactive kernel debuggers, preferring that a developer read the code and think; others find GDB over QEMU or a crash-dump analysis invaluable, particularly for hangs and for post-mortem study. Tracing with eBPF and perf argues for observing production systems without rebuilding. The tools are complementary, and which one fits depends on whether the bug is reproducible, how costly a rebuild is and how much the problem changes when instrumented.

## Active research

Research and development include lower-overhead sanitizers for production (hardware memory tagging on arm64), better race detection, making printk lockless and safe in every context, more efficient trace buffers, and formal verification of locking rules. Fuzzing with sanitizers is a major source of kernel bug discovery, with coverage-guided tools producing a steady stream of reports.

## Future direction

Hardware-assisted tagging should make memory-safety detection affordable in production, and Rust code in the kernel reduces some classes of bug these tools find. Tracing will continue to converge on eBPF and tracepoints as the main interface, with tracefs retained for direct use. Expect more automation: systems that run debug-configured kernels on every patch and file the reports.
