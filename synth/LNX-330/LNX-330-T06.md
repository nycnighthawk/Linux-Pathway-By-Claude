# format-patch, b4, send-email and list etiquette: getting a change reviewed by email

## Define the problem

Linux kernel development is organised around plain-text email. A change is submitted as a patch in the body of a message, sent to the maintainers of the code and to mailing lists, and reviewed by replies that quote the patch inline. The approach looks old-fashioned next to pull requests, but it has properties the project values: anyone can review without an account on a hosting service, discussions are public and archived, tools can process messages mechanically, and there is no single vendor to depend on.

The cost is that the format is unforgiving. A patch that is wrapped by a mail client, sent as an attachment, missing its sign-off or addressed to the wrong people will not be applied. A contributor needs to know how to produce clean patches, how to send them without damage, how to run a series through several versions and how to behave on the list.

## History and approaches

**Patches by mail.** From the start, Linus Torvalds accepted patches as emails. The conventions that exist now (one logical change per patch, an explanatory description, a sign-off line) accreted over the 1990s and early 2000s. After a licensing dispute over a proprietary version control system in 2005, Torvalds wrote Git, and several of its commands were designed for this workflow: `git format-patch` writes each commit as a mail-ready file, `git am` applies mailbox files with authorship preserved, `git send-email` sends them.

**The Signed-off-by line.** In 2004 the Developer Certificate of Origin was adopted. A `Signed-off-by:` trailer states that the author has the right to submit the code under the project's licence. The kernel's submission document spells out the certificate's four clauses.

**Series and versions.** A feature that needs several steps is sent as a numbered series (`[PATCH 2/5]`). After review, revised versions follow, each with a `v2`, `v3` label and a note on what changed. Maintainers can compare versions and see that comments were addressed.

**Patch tracking.** Plain mail loses patches, so tools arrived to follow them: Patchwork (a web front end that collects patches from lists and tracks state), subsystem-specific bots, and the archive at lore.kernel.org, which stores most lists and is searchable and downloadable in several formats.

**The b4 tool.** Konstantin Ryabitsev, who works on kernel.org infrastructure, built `b4` to smooth the workflow for both sides. For maintainers, `b4 am` downloads a series by message-id from lore, collects review trailers (`Reviewed-by`, `Acked-by`, `Tested-by`) and produces a mailbox ready for `git am`. For contributors, `b4 prep` manages a series on a branch, `b4 send` sends it through a web endpoint or an SMTP server, and `b4 trailers` updates the commits with trailers received on the list. (Exact commands and author details should be confirmed in the tool's documentation.)

## Current state

### Producing patches

`git format-patch` is the basic generator. A typical call for a series is `git format-patch -v2 --cover-letter -o outgoing base..topic`. Options that matter:

- `-v N` labels the series version in subjects (`[PATCH v2 1/3]`).
- `--cover-letter` writes an empty message numbered 0; fill in its subject and body, because it is where the series is introduced and where the version changelog goes.
- `-s` adds a `Signed-off-by` for the committer; many people commit with `-s` instead.
- `--base=<commit>` records `base-commit:` at the end so reviewers and test bots know what the series applies to.
- `--to` and `--cc` add recipients; for a series the headers on the cover letter apply to the whole set when sent.
- `-o` writes into a directory instead of the working directory.
- `--range-diff`, `--interdiff` embed a comparison with the previous version, a good aid for reviewers.

Subject lines start with the subsystem prefix and a short imperative summary, for example `net: foo: fix NULL check on probe`. The commit message explains the problem, why the change is right and any alternative considered, in lines wrapped near 75 columns. Relevant trailers go at the end: `Fixes:` with a commit id and the subject of the commit that introduced a bug, `Cc: stable@vger.kernel.org` for fixes meant for stable branches, `Reported-by`, `Link:` and the sign-off. Changes between versions go below the three-dash line, so they are not part of the commit.

### Preparing a good series

Each patch should do one thing, build and boot on its own (so that bisection works), and not leave the tree broken in the middle of the series. Separating cleanup from behaviour change makes the second easy to review. A rule of thumb used by many maintainers: a patch should be reviewable in a few minutes. Large series are split into logical groups, or sent in rounds.

Before sending, run the checks from the previous topic and, where possible, a boot test of the result. Mention what testing was done, including hardware, if any; untested code should be marked.

### Sending

`git send-email` sends the files through SMTP. Configuration lives in the `sendemail.*` Git settings: server, port, encryption, user. A dry run with `--dry-run` prints what would go out. For a test, send first to yourself. Mail clients are the main source of corruption (wrapping, whitespace changes, HTML parts), which is why sending through `git send-email` is recommended. The kernel documentation lists mail client settings for those who must use one. Common free-mail providers restrict SMTP; `b4 send` offers a web-submission endpoint run by the kernel.org infrastructure team as an alternative to configuring SMTP (to verify the current requirements).

Addressing: put maintainers and reviewers from `get_maintainer.pl` in `To`, mailing lists in `Cc`. For a series, the cover letter and all patches go to the combined recipient list, and all replies should keep the threading headers so that the series appears as one thread.

### After sending

Reviews arrive as replies. Reply inline, under the quoted text, trimming everything you do not answer. Reply to each comment, either agreeing and noting a change or explaining why not. Do not argue by repetition; if a maintainer is unconvinced, rework or ask what would convince them. Wait before posting the next version: a common recommendation is a day or more, so that reviewers across time zones can respond, and to include all comments in one revision.

Trailers given in replies (`Reviewed-by: Name <addr>`) are added to the next version when the person has not asked otherwise. If a patch changes substantially, drop the old trailers and ask again. `b4 trailers -u` collects them from the archive.

If nobody answers for a couple of weeks, a polite reminder (reply to your own message with a short ping, maybe to a different set of reviewers) is accepted; repeated pings in short intervals are not. Merge windows and release candidates also affect when maintainers pick up patches.

### List etiquette

- **Plain text only**, no HTML, no top-posting: answer under the relevant quoted lines, trimming irrelevant text.
- **Be specific and technical.** Review comments address the code. Receiving criticism calmly is part of the process. The project's code of conduct applies on all lists.
- **Do not send private mail** about patches meant for public review; keep the discussion on the list so it is archived.
- **Reply to the right message** so threading is not broken; use the message-id with `--in-reply-to` when sending a new version into an old thread or, better, start a new thread with a link to the previous version.
- **Respect time.** Trim the cc list to those who need it, and do not cross-post to unrelated lists.

### Where patches go afterwards

A maintainer applies accepted patches to a subsystem tree, which appears in `linux-next` for integration testing and is sent to Linus Torvalds in a pull request during a merge window. The path from posting to a release can take weeks or months, with the final release marked by a candidate cycle as covered in the release-process topic.

## Assessment: the good, the bad and the ugly

**The good.** The mail workflow is open, scalable and tool-independent. Review is public; everyone can learn from it; history is preserved in archives; the patch is the unit of discussion, so reviewers comment on exactly what will be applied. `git format-patch` and `git am` keep authorship, and `b4` removes much of the mechanical effort for both sides.

**The bad.** Setup is a real barrier for newcomers: SMTP configuration, mail clients that corrupt patches and the unfamiliar conventions. Following a series across versions requires care. Patch tracking is imperfect, and patches are lost or overlooked on busy lists. There is no built-in CI gate, though bots increasingly provide one.

**The ugly.** Heated threads, unanswered patches and unhelpful drive-by comments damage morale; some maintainers are overloaded and their subsystems become bottlenecks. Mail providers change their authentication rules and break existing setups. Subsystems differ in preferences (some use their own bug trackers or accept pull requests from contributors), so the right behaviour has to be learned per area.

## Applications beyond this domain

- **QEMU, Git itself and many other projects** use the same mail workflow and their guidelines mirror the kernel's; QEMU's patch guide describes `git send-email` and the list as the only accepted route [src: qemu-docs 756b68f8079378ef].
- **Open-source communication habits** (inline replies, trimming, public reasoning) carry over to design discussions in any distributed team.
- **Corporate code review** benefits from the discipline of small, self-contained, bisectable changes with explanatory messages.
- **Legal provenance**: the sign-off model is copied by other projects as a lightweight contributor agreement.

## Examples

**A version two.** After a review, a contributor fixes two comments, rebases onto the maintainer's tree, regenerates with `-v2 --base=<commit>`, and fills in a changelog below the cover letter. The series goes to the same recipients and the old thread gets a link in the cover.

**A mangled patch.** A maintainer replies that the patch does not apply: the author's mail client replaced tabs with spaces. The author switches to `git send-email` and re-sends the same patch as `v2` with a note.

**A stable fix.** A fix includes `Fixes:` with the original commit and a `Cc: stable@vger.kernel.org` trailer. After it enters mainline, the stable maintainers pick it up automatically.

**A pull-and-collect.** A maintainer runs `b4 am` with the message-id of a series; the tool downloads the thread, adds the `Reviewed-by` trailers given in replies and writes a mailbox. The maintainer applies it with `git am` and tests.

## Related problems and ideas

- **Checks before posting** (previous topic) and **KUnit and kselftest** (following topics) are what a good cover letter reports.
- **Bisecting** works only if each patch builds, which is why series are structured as they are.
- **Pull requests** are used between maintainers and from some trusted contributors; the format is a signed tag with a summary.
- **Forges** such as GitHub and GitLab handle the same task differently, and some projects bridge them to mailing lists.

## Active research

Work on the contribution workflow focuses on lowering the entry barrier (web submission, `b4 send`, bridges that let a pull request become a mailed series), better tracking (lore-based tools, patch state), and bots that run builds and tests on every posted patch and report by mail. Studies of review practice on the kernel lists examine reviewer load and response time. These topics are discussed regularly at the Maintainers Summit and in LWN coverage (to verify specific proposals).

## Future direction

The core of mail and patches is likely to remain, with more tooling around it: automatic trailers, automatic CI results on lore, structured metadata in cover letters and web submission for those who cannot use SMTP. Calls for forge-based workflows continue, and some subsystems already use hybrids.
