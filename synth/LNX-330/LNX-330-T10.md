# git bisect a regression: finding the commit that broke it

## Define the problem

A kernel that worked last month no longer does. Between the two versions lie tens of thousands of commits from thousands of authors. Reading them is impossible, and the symptom (a hang, a lost device, a failed test) often says nothing about which subsystem is at fault. The project's rule is that a regression in user-visible behaviour is a bug to be fixed, usually by reverting the change that caused it; but a maintainer can only act on a specific commit.

Finding that commit is a search problem over a linear or branching history with a yes-or-no oracle: does this version have the bug? Binary search needs only a logarithmic number of tests. For about ten thousand commits it takes roughly fourteen builds and boots, which is a day of work at worst instead of months. `git bisect` automates the bookkeeping.

## History and approaches

**Manual search.** Before bisection tools, developers narrowed regressions by trying release candidates and patch sets by hand, then reading change logs. Patches arrived as a flat sequence from the maintainer, so a developer could split that sequence by hand, which was laborious.

**Git bisect.** When Git replaced the earlier version control system in 2005, a bisection command arrived within the first months, written to help kernel testers (the early design is credited to Linus Torvalds and implemented by others, to verify). It walks the commit graph, not a list, and handles merges by choosing commits that split the remaining candidates as evenly as possible.

**Scripted bisection.** `git bisect run` accepts a command and uses its exit status as the oracle, which turns a day of attention into a background job. The convention that exit status 125 means "this commit cannot be tested" lets a script skip commits that fail to build.

**Specialised tooling.** Distribution testers and CI systems run bisection automatically when a test starts failing: they build the range, boot each candidate in a VM and report the culprit to the author. The kernel community's reporting guidance asks reporters of regressions to bisect when they can, and a regression-tracking bot follows reports until fixed.

## Current state

### The commands

- `git bisect start <bad> <good>` begins, with one known bad commit and one known good one. Git checks out a commit in the middle.
- After testing it, `git bisect good` or `git bisect bad` marks it, and Git picks the next. `git bisect skip` removes a commit that cannot be tested from consideration.
- `git bisect run <command>` automates the loop. The command's exit status decides: 0 for good, 1 to 127 except 125 for bad, 125 for skip, and 128 or more aborts the search.
- When the search ends, Git prints the first bad commit and its message. `git bisect log` records the steps, `git bisect replay` repeats a saved log, `git bisect visualize` shows the remaining range in a viewer, and `git bisect reset` returns to the original branch.
- Custom terms (`--term-old`, `--term-new`, or `git bisect start --term-new=fixed --term-old=broken`) are useful when hunting for the commit that *fixed* something, where "good" and "bad" would confuse.

The result is the **first bad** commit, assuming the history has one transition from good to bad. That assumption is the core risk of any bisection.

### Bisecting a kernel

The range comes from tags: `git bisect start v6.12 v6.11`, where the first is bad and the second good. The test must be deterministic and cheap enough to repeat dozens of times. The usual loop:

1. Keep the configuration that reproduces the problem (copy `.config` from the failing build), and run `make olddefconfig` at each step so new options take defaults without prompting. Build only what is needed; `ccache` and reusing the build directory shorten rebuilds.
2. Boot the result somewhere safe: a virtual machine for software bugs, a test machine for hardware ones. The boot-testing topic covers the loop.
3. Decide good, bad or skip, and tell Git.

Time per step is dominated by the build, so the order of magnitude is minutes. A script can drive all of it: build, boot with a timeout, run a reproducer, return an exit status.

### Pitfalls

- **Unbuildable or unbootable commits.** Series applied in the middle of history may leave the tree broken for a few commits. Skip those; if too many are skipped, Git reports a range of possible culprits instead of one commit.
- **Flaky bugs.** If a failure occurs one time in ten, a single good result proves nothing. Run the reproducer enough times to be confident (and decide the number ahead of time), or write the script so that any failure in N runs counts as bad. A wrong answer at one step silently misleads every later step.
- **Different bug.** The symptom after the transition may differ from the one before it, so a script that tests the wrong symptom finds the wrong commit. Check that the failure at the end of the search matches the original report.
- **Merge commits.** A bisection that lands on a merge means the problem comes from the interaction of two branches or from a merge conflict resolution. Bisect inside the merged branches or inspect the merge diff. `--first-parent` bisects the mainline's merge commits first (to verify availability in older Git versions) and then drills down.
- **Config changes.** If the kernel configuration symbols themselves changed between versions, the old `.config` may hide the bug; a new option may be needed to reproduce.
- **Non-code causes.** Firmware, toolchain updates and user-space changes can mimic a kernel regression. Test the good and bad endpoints again with identical conditions before starting.
- **Dirty tree.** Do not leave local changes in the working tree: bisect refuses to switch commits with conflicting modifications, and carried-over edits invalidate results. Keep the test script outside the tracked files or stash patches that are needed at every step.

### After finding the commit

Verify by reverting the commit on the bad tip, or by checking that the parent is good and the commit is bad when tested again. Report to the author and maintainers (found with `get_maintainer.pl`) with the bisection log, the configuration and the failing symptom, on the mailing list that covers the subsystem. A good report includes how to reproduce, kernel versions, hardware, logs and the commit id. The reporting guide asks the reporter to mention that it is a regression, so the tracking bot picks it up. The usual outcome is a fix or a revert before the next release.

### Related searches

Bisection also finds when a *performance* regression arrived (with a benchmark oracle and a threshold), when a *test* first failed and when a bug was *fixed* (using the term options). Tools exist to bisect compiler or library versions the same way, and Git can bisect by file with `git bisect start -- <path>` to ignore commits that do not touch those paths.

## Assessment: the good, the bad and the ugly

**The good.** The method is cheap, logarithmic in the history length and mechanical. It converts a vague complaint into a precise pointer that a maintainer can act on, and a maintainer is much more likely to fix a bug when handed a culprit commit. Scripting it makes it automatic and repeatable.

**The bad.** Each step needs a full rebuild and boot, so a slow test or a flaky symptom makes it painful. A wrong good or bad answer at any step spoils the result without warning. The method cannot find bugs caused by the combination of two changes that are individually harmless, or by a configuration or environment change.

**The ugly.** Long skipped ranges give an inconclusive result. Merge commits can hide the real culprit. Bugs that only appear on one piece of hardware force the reporter to run all the builds there, often without the knowledge to judge intermediate states. Reporters who do not bisect, or bisect with a bad oracle, send maintainers on false trails.

## Applications beyond this domain

- **Any Git project** with a test suite: bisect locates the commit that broke a test, for example in distributions' packaging and in application development.
- **CI systems** run automatic bisection on failures and open issues against the author of the offending change.
- **Hypervisor and VM development**: a guest that stops booting after a host kernel or QEMU update is a classic case; bisect QEMU's own history the same way (its patch guide asks contributors to test before submission, which keeps history bisectable [src: qemu-docs 6fd701aa9ba56dc9]).
- **Performance engineering** uses bisection with a threshold on a benchmark result.

## Examples

**A regression after an upgrade.** A laptop's Wi-Fi stops working after moving from one release to the next. The user bisects the range with a script that builds, boots in the real machine and checks for the interface; the log names a commit in the driver; the maintainer replies with a fix a day later.

**A script with skip.** A test script returns 125 when the build fails, 0 if a reproducer passes ten times, and 1 if it fails once. The search ends in eleven steps, two of them skipped.

**A merge as culprit.** Bisect lands on a merge commit whose parents are both good. The conflict resolution dropped a line; `git show --cc` displays the combined diff and exposes it.

**A fix hunt.** A bug disappeared in a later release. The developer starts with `--term-old=broken --term-new=fixed` to find the commit that fixed it and decides whether it qualifies for the stable branches.

## Related problems and ideas

- **Boot testing** and **KUnit/kselftest** provide the oracle; **the debugging tools** explain what the culprit does wrong.
- **Release process**: the rule on regressions is why bisection results are acted on quickly.
- **Blame and history tools** (`git blame`, `git log -S`) answer who changed a line and when, without testing.
- **Reverts** are the default repair when a fix is not ready.

## Active research

Research and engineering work includes automatic bisection services that react to failing tests, ways to cope with flaky tests during search (statistical bisection that accounts for failure probability), bisection over *test-selection* spaces and delta debugging, which shrinks a failing input or patch set to a minimal one. Techniques for bisecting across multiple repositories (kernel and user-space) are also being explored (to verify specifics).

## Future direction

Expect bisection to be an automated, default response to a failing CI test, with the culprit mailed within hours. Better build caches and shared runners reduce the cost per step; probabilistic search will become more common for flaky failures. Human judgement remains needed to choose the oracle and read the result.
