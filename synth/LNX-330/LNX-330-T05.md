# checkpatch, get_maintainer, sparse and Coccinelle: the tools that check a kernel patch before a human does

## Define the problem

A kernel patch is read by maintainers who receive hundreds of messages a day. A patch that wastes their time with trivia, such as wrong indentation, a missing sign-off, an unnecessary cast or a mis-addressed email, is likely to be ignored. Meanwhile, the C language and the kernel's conventions leave plenty of room for mistakes that a compiler never reports: mixing byte orders, dereferencing a user-space pointer directly, forgetting to release a lock on an error path, or repeating an idiom that the project replaced years ago.

The kernel community therefore ships a toolbox in the source tree, and expects contributors to run it before posting. This topic covers four of its members: a style and policy checker (`checkpatch.pl`), a tool that finds the right recipients (`get_maintainer.pl`), a semantic checker for C (`sparse`) and a program-matching and transformation tool (Coccinelle).

## History and approaches

**Style by convention.** The earliest guidance was a coding style document and reviewers' habits. Reviewers repeated the same comments, which is the signal that a tool can do the job. `checkpatch.pl`, a Perl script in `scripts/`, grew to encode those habits: whitespace and indentation, line length, brace placement, spelling of common words, deprecated functions, and patch-format requirements.

**Finding the owner.** As the tree grew, the `MAINTAINERS` file became the registry of who owns which files. `get_maintainer.pl` reads it, matches the files a patch touches against `F:` patterns and prints maintainers, reviewers and mailing lists. By default it also consults the version-control history to suggest recent contributors to the same code.

**Sparse.** Linus Torvalds wrote sparse (a semantic parser for C) in 2003 as a checking front end. It understands kernel annotations such as `__user`, `__iomem`, `__rcu`, `__bitwise` and lock-context markers, which are empty for the compiler but meaningful to sparse. Byte-order types such as `__le32` and `__be32` are declared `__bitwise`, so sparse flags arithmetic on them without conversion.

**Coccinelle.** Developed at INRIA and the University of Copenhagen starting in the mid-2000s (exact year to verify), Coccinelle matches and rewrites C code semantically. Its language, SmPL (semantic patch language), looks like a unified diff with metavariables, so one description can find or change every occurrence of a pattern across thousands of files regardless of formatting. It found and fixed systematic bugs in drivers, and a library of scripts now lives in `scripts/coccinelle`.

**Everything else.** Compiler warnings (`make W=1`, `W=2`), static analysers, `clang-format`, `kernel-doc` validation, and checks for SPDX identifiers join the list. Continuous-integration bots run many of them on patches posted to the mailing lists.

## Current state

### checkpatch

Run it on a patch file (`scripts/checkpatch.pl 0001-fix.patch`), on a commit (`--git HEAD`, or a range) or on a source file (`-f file.c`). Messages are classed ERROR, WARNING and CHECK; `--strict` adds the CHECK class, which covers matters of taste that maintainers of some subsystems enforce. `--fix` and `--fix-inplace` can repair simple issues automatically. Options such as `--ignore` and `--types` select message types, and `--no-tree` allows running on a patch outside a kernel tree.

Typical findings: trailing whitespace; spaces where tabs are required; lines over the preferred width (80 columns historically, with a larger limit accepted now, to verify for your tree version); a missing `Signed-off-by` line; a commit message line that is too long; a suspicious macro lacking parentheses; use of an obsolete function with a named replacement; a missing blank line after declarations; a `printk` without a level.

The right attitude is to treat checkpatch as advice. A message that conflicts with surrounding code or a subsystem's convention can be ignored, but the patch description should say why. The tool does not parse C; it matches patterns on lines, so it produces false positives and misses real problems.

### get_maintainer

`scripts/get_maintainer.pl 0001-fix.patch` prints the recipients; `-f path` works on a file path; `--no-git` and `--no-git-fallback` limit it to the `MAINTAINERS` entries. The output marks roles in parentheses: `maintainer`, `reviewer`, `open list`, `moderated list`, `supporter`, and history-based `commit_signer` and `authored` roles. A section's `F:` entries are file patterns (a trailing slash means a directory tree, a `*` stays within one path component), and `X:` entries exclude files. `S:` states the status of the code, from Supported through Maintained, Odd Fixes and Orphan to Obsolete; an orphaned area has no maintainer to receive the patch, so the mailing list and a relevant subsystem maintainer take over.

Mail workflow: send to the maintainers (and the reviewers) in `To`, put mailing lists in `Cc`, and include the lists named by `L:` so that automated tools and other reviewers see the patch. For a series, every patch goes to the people matching any patch in the series, so the cover letter reaches all of them.

### sparse

Install the `sparse` package, then build with `make C=1` to check files that are recompiled, or `make C=2` to check all files. `CF=` passes extra sparse options. Output lines look like compiler warnings: `incorrect type in assignment (different base types)` for byte-order mix-ups, `incorrect type in argument 1 (different address spaces)` when a user pointer is passed where a kernel pointer is expected, and `context imbalance` when a function leaves a lock held or released on some paths.

When a check is right, fix the code (use `le32_to_cpu`, `copy_from_user`, a matched unlock). When the code is intentionally doing something unusual, the cast `__force` documents it. Adding sparse annotations to a new interface (`__user`, `__rcu`, `__must_hold`) improves checking for every caller.

### Coccinelle

A semantic patch has metavariable declarations followed by a diff-like rule. Metavariable declarations name the kinds of things to match (`expression`, `identifier`, `type`, `statement`). Lines prefixed with `-` are removed, lines with `+` are added, and the rest provides context. Because matching works on the control-flow of the code, `...` can stand for any code in between.

Kernel integration is through `make coccicheck`. The variable `MODE` selects what it does: `report` prints findings, `org` writes Emacs org-mode output, `context` shows context for review, `patch` generates a patch. `COCCI=` selects one script, and `M=dir` limits the scan to a directory. The scripts in `scripts/coccinelle/` are organised by category (API misuse, free of memory, locks, iterators), and many of them have each fixed dozens of bugs.

The value of Coccinelle is *collateral evolution*: when a core API changes, a semantic patch updates all callers consistently and can be posted with the change, which reviewers can verify by reading the rule instead of thousands of changed lines.

### How they combine

A common local routine before posting a series: build with `W=1` and with sparse (`C=1`) on both the default configuration and the configuration used for the change; run coccicheck on the touched directory; run checkpatch with `--strict` on every commit; and run `get_maintainer.pl` over each patch to build the recipient list. Maintainers commonly run the same checks themselves, and bots report failures on the mailing list.

## Assessment: the good, the bad and the ugly

**The good.** Automated checks catch routine problems before human time is spent, apply the same standard to everyone, and teach new contributors the conventions by example. Sparse finds real bugs that the compiler cannot (byte-order and address-space errors), and Coccinelle makes large mechanical changes safe and reviewable.

**The bad.** Checkpatch works by pattern matching and complains about code that is fine, so contributors sometimes alter good code to silence it. Sparse needs annotations to be useful, and many older interfaces lack them. Coccinelle has a learning curve, and rules need to be written carefully to avoid false matches. `get_maintainer.pl` is only as good as the `MAINTAINERS` entries; stale entries send mail to people who left years ago.

**The ugly.** "Fix checkpatch warnings" patches that change working code without purpose have long been a source of churn and maintainer annoyance; some subsystems explicitly reject them outside new code. A tool can also lend false confidence: a clean checkpatch run says nothing about whether the logic is correct.

## Applications beyond this domain

- **Other large C projects** use similar tools: QEMU ships its own `checkpatch.pl` derived from the kernel's, and its patch submission guide asks contributors to run it and to test locally before sending patches to the list [src: qemu-docs 6fd701aa9ba56dc9].
- **Static analysis in industry** uses semantic matching to find API misuse and enforce coding rules at scale.
- **Large-scale refactoring** in any language benefits from a rule-based transformation tool instead of regular expressions.
- **Open source onboarding**: running the checks first is the quickest way to learn a project's conventions.

## Examples

**Style only.** A developer posts a driver patch and a bot replies with checkpatch output: spaces used for indentation on three lines and a missing blank line after a declaration block. The author runs `--fix-inplace`, reviews the diff, and re-sends.

**An endianness bug.** `make C=1` reports an assignment between `__le32` and `u32` in a driver for a big-endian architecture. The fix wraps the value in `cpu_to_le32`. On a little-endian laptop the bug had never appeared.

**Sending to the right people.** A patch touches a network driver and its documentation. `get_maintainer.pl` lists the driver maintainer, the networking list and the documentation list. The author puts the maintainers in `To`, the lists in `Cc`, and does not add a random reviewer from history.

**A tree-wide change.** The kernel renames an argument convention for a helper. A semantic patch rewrites several hundred call sites; the commit message includes the rule, so a reviewer checks the rule and a few samples.

## Related problems and ideas

- **Patch formatting and mail** (next topic) is where `get_maintainer.pl` output is used.
- **KUnit and kselftest** test behaviour, where these tools check form.
- **Static analysis tools** such as smatch, clang's analyser and compiler plugins run beside sparse.
- **Code review practice** decides what tools cannot: whether a change is a good idea.

## Active research

Research on program matching and transformation continues around Coccinelle (scaling, new languages such as Rust and Python, assistance for writing rules). Others work on machine-assisted review, bug-finding with large language models run over patches, and checking of kernel locking and memory rules with formal tools. These approaches complement, and do not yet replace, the established scripts (to verify the current state of each).

## Future direction

Expect more checks to move into the compiler (Clang's thread-safety analysis and attributes already offer lock annotations that sparse markers approximate), more Rust-related lints for kernel code, and more bot-driven feedback on mailing lists, so contributors see results without running anything. Human review remains the scarce resource that these tools exist to protect.
