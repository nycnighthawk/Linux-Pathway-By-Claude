# kselftest: testing the kernel from the outside

## Define the problem

The kernel's contract with the rest of the world is its user-space interface: system calls, `/proc` and `/sys` files, ioctls, netlink families, signals, memory-mapping semantics. A regression there breaks applications, and the project's rule is that user-visible behaviour must not break. Unit tests that call internal functions cannot show that the interface still works end to end, because the interface is the combination of the entry code, the subsystem, locking, permission checks and error handling.

Testing the interface means running real user-space programs against a real running kernel, usually as root and sometimes with special hardware or configuration. The programs should be easy to write, small, part of the source tree so they track the code, and able to say clearly whether the kernel passed, failed, or lacked the feature under test.

## History and approaches

**Hand-run programs.** Developers have always written test programs to demonstrate a bug, and many were pasted into mailing-list messages. They were not collected, were run by no one else and depended on each reader's setup.

**LTP.** The Linux Test Project, an external suite that began around the turn of the century, collects thousands of tests for system calls, filesystems, networking and more. It is run by distributions and vendors, but lives outside the kernel tree, so new kernel features do not necessarily arrive with matching LTP tests.

**kselftest.** The in-tree suite under `tools/testing/selftests/` was introduced in the 3.x era (to verify the exact release), with the aim that a patch which adds or fixes an interface carries a test in the same series. Each subsystem has a directory with a Makefile and test programs; a top-level Makefile builds and runs them. Over time the subsystem directories grew to cover memory management, networking, BPF, cgroups, KVM, futexes, timers, seccomp, ptrace, filesystems and many more.

**Shared infrastructure.** Early tests printed results in different ways. A common header (`kselftest.h`) and later a harness (`kselftest_harness.h`) with a fixture-and-test macro style unified exit codes and TAP output. Runner scripts add timeouts, per-test logging and result aggregation. Companion frameworks fill gaps: KUnit for unit tests (previous topic), and, for BPF, the `test_progs` runner.

**Integration with CI.** Large kernel test farms (KernelCI, 0-day and distribution labs) build the selftests for each tested kernel and run them on hardware and in virtual machines, so selftests now serve as the main regression suite for user-visible behaviour.

## Current state

### The contract

A kselftest is a program or script. Its contract is simple:

- **Exit code**: 0 means pass; 1 means fail; 2 and 3 mean expected failure and unexpected pass (rarely used); 4 means skip. The runner treats a skip as not-a-failure, and CI reports it separately.
- **Output**: lines in the Test Anything Protocol, such as `ok 1 name` or `not ok 2 name`, with a plan like `1..N`. Diagnostic lines start with `#`. The skip form is `ok N name # SKIP reason`.
- **Self-checking**: a test must detect whether the kernel has the feature (a system call that returns `ENOSYS`, a missing sysfs file, a configuration option not enabled, insufficient privilege) and skip rather than fail. A test that fails on kernels that never claimed the feature adds noise to CI.

### Writing a test in C

A test includes `kselftest.h` for helpers (`ksft_print_header`, `ksft_set_plan`, `ksft_test_result_pass`, `ksft_test_result_fail`, `ksft_test_result_skip`, `ksft_exit_pass`, `ksft_exit_fail`, `ksft_exit_skip`), or `kselftest_harness.h` for a gtest-like style: `FIXTURE`, `FIXTURE_SETUP`, `TEST_F`, and `ASSERT_*` and `EXPECT_*` macros. The harness forks each test into its own process, so a crash fails one case and the next still runs, and it prints TAP. Variants allow one body to run under several configurations.

The Makefile for a directory lists programs in `TEST_GEN_PROGS` (built from C sources), scripts in `TEST_PROGS` (shell scripts that are run) and extra files in `TEST_FILES`, then includes `../lib.mk`. A `config` file in the directory lists kernel configuration options the tests need, which CI uses to build a suitable kernel. A `settings` file can raise the per-test timeout. A directory may also carry a `.gitignore` for build products.

### Running

From the top of a tree, `make -C tools/testing/selftests TARGETS=net run_tests` builds and runs one subsystem's tests. `TARGETS="size timers"` runs a list. The `kselftest-install` target copies built tests and a runner script into a directory (`kselftest_install`), which is how a test kit is shipped to a target machine that has no compiler; the runner there is `run_kselftest.sh`, with options to list and select tests and to set a timeout. Cross-building works with `ARCH` and `CROSS_COMPILE`, which is useful for embedded targets and virtual machines of another architecture.

Many tests need privileges (root, capabilities) or modify system state (network namespaces, mounts, cgroups). Good tests create their own namespaces or temporary directories and clean up; the run in a disposable virtual machine is the safest default, as discussed in the boot-testing topic. A few tests need kernel test modules from `lib/` (built with `CONFIG_TEST_*`) or a debugging configuration.

### Where tests fit with other tools

- Use **KUnit** for logic that can be tested in isolation with internal calls; use **kselftest** for what only exists through the user-space interface or needs the real scheduler, devices or timing.
- A fix for a bug reported by a fuzzer is often accompanied by a selftest that reproduces the reported sequence, so the regression stays fixed.
- Tests that require hardware are marked to skip when the device is absent.
- BPF has its own large framework under `tools/testing/selftests/bpf`, with a runner and many programs, reflecting that area's size and pace.

### Contribution practice

New interfaces are expected to come with a selftest in the same series; maintainers of several subsystems enforce it. A test should be deterministic, fast (seconds), robust to varying kernel configurations, and tidy: no leftover files, processes or mounts. The documentation recommends declaring the test's required configuration, naming tests clearly and keeping them independent of one another. Review uses the usual mail workflow.

## Assessment: the good, the bad and the ugly

**The good.** The tests live with the code, test the interface that users depend on and are runnable by anyone with a built tree or an installed kit. The shared contract (exit codes and TAP) lets CI systems collect results from hundreds of different programs. A selftest is also living documentation of how an interface is meant to be used.

**The bad.** Coverage is uneven: some subsystems have rich suites, others none. Tests may need root, special configuration or particular hardware, so a default run skips much. Selftests are not isolated by default, and a test that leaves state behind can disturb the next. Flaky, timing-dependent tests erode trust in the suite.

**The ugly.** A test that fails on a configuration where the feature is legitimately absent, or that depends on a particular distribution's user-space tools, produces failures that waste maintainers' time. Time-limited CI runs cut off long tests. Some test directories have grown their own helpers and conventions, so the tree is less uniform than the documentation suggests.

## Applications beyond this domain

- **Conformance suites** for other kernels and runtimes (POSIX test suites, container runtime conformance) use the same pass, fail and skip contract.
- **Hypervisor testing**: KVM has selftests that create virtual machines and drive them with ioctls, including tests that run tiny guest code, which ties directly to the virtualisation pathway.
- **Operating-system image qualification** at distribution labs runs kernel selftests as part of regression checks; projects such as Rocky Linux run automated QA with openQA [src: rocky-docs 25ee1f05506561b1].
- **Regression tracking**: the practice of attaching a reproducer to every bug fix applies to any software project.

## Examples

**A memfd test.** A kernel adds a new seal type. The patch series includes a selftest in the memory-management directory that creates a memfd, applies the seal and checks that the forbidden operation fails with `EPERM`. On older kernels the test sees `EINVAL` from the seal request and skips.

**A kit for a board.** A developer cross-builds the networking selftests, runs `make kselftest-install` and copies the directory to an arm64 board with no compiler. The runner script runs the selected tests and the output goes to a log that a CI job parses.

**A crash isolated.** A harness-based test case triggers a segmentation fault in user space. The harness reports that case as failed and continues with the next, where a flat program would have stopped at the first crash.

**A flaky test.** A timing test fails one run in fifty on a loaded CI machine. The maintainers replace a fixed sleep with a poll for the condition and a generous timeout.

## Related problems and ideas

- **KUnit** (previous topic) and **boot testing** (earlier) form the other two layers.
- **Fuzzers** such as syzkaller discover bugs; selftests keep them fixed.
- **Bisecting** (a later topic) uses a selftest as the good-or-bad oracle.
- **Sanitizers and lock checking** enabled in the test kernel turn silent corruption into failures.

## Active research

Directions include better selection of which tests to run for a given patch, cutting runtime in CI by test impact analysis, tracking flakiness statistically, standardising result schemas across labs, and generating tests from fuzzer reproducers automatically. KernelCI work on a common result format is an example (to verify the current state).

## Future direction

Expect selftests to become a normal gate for new interfaces, with more of them structured on the shared harness and with automatic reporting of results to patch authors. Rust and eBPF will add their own test forms. A stable machine-readable result format across the many frameworks remains a goal.
