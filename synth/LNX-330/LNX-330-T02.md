# Kconfig, defconfig, localmodconfig and cross-compiling: building the kernel you mean to build

## Define the problem

A kernel is not one program but a family. The same source tree builds for dozens of CPU architectures, thousands of boards and every combination of several thousand optional features, each of which can be compiled in, built as a loadable module or left out. A server kernel, a phone kernel, a minimal kernel for a virtual machine and a debugging kernel for a driver developer share most of the code but little of the configuration. Choosing the configuration is therefore a task in its own right, and it has to satisfy several constraints at once: features depend on other features, some choices exclude others, hardware must have its drivers, size and attack surface should stay small, and the result must build with the toolchain the developer has.

The configuration system must offer a way to describe the options and their relations (`Kconfig`), to record a particular choice (the `.config` file), to start from sensible defaults (`defconfig`, distribution configs), to shrink or tailor a configuration (`localmodconfig`, `localyesconfig`), to modify it in a repeatable way (fragments and `merge_config.sh`, `scripts/config`), and to drive a build whose output depends on the choice. On top of this the developer often builds for a different machine than the one they sit at, which means cross-compilation with the right toolchain and variables. This slice covers the Kconfig language and its behaviour, the common config targets, fragment workflows, the kbuild entry points, and cross and LLVM builds. Packaging, signing and booting the kernel are in other topics of this course.

## History and approaches

**Makefile switches.** Early kernels were configured by editing headers and makefiles. As options multiplied, `make config` appeared (2.0 era) with a long question-and-answer script that asked about every option in turn. It was tedious, error-prone and not repeatable, since a changed answer early on shifted the questions that followed.

**Kconfig.** For 2.5 the kernel adopted a declarative language, derived from a design by Roman Zippel, in which each option is a `config` entry with a type (`bool`, `tristate`, `int`, `hex`, `string`), a prompt, dependencies (`depends on`), reverse dependencies (`select`), defaults and help text. The `Kconfig` files live throughout the tree and are included hierarchically from the top-level `Kconfig`. The configuration tools evaluate these rules, so that the user can only reach states that satisfy them, and the result is stored in `.config`. Frontends (`menuconfig`, `nconfig`, `xconfig`, `gconfig`) provide interactive navigation over the same engine. Kconfig was later reused by other projects (Buildroot, BusyBox, Zephyr, U-Boot, coreboot) because of its general design.

**Tristate and modules.** The `tristate` type adds `m`: build as a loadable module. This lets one kernel image support much hardware without carrying all drivers in memory. Distributions ship nearly everything as modules and load what the hardware needs through `udev`, with an initial RAM filesystem to supply the drivers needed before the root filesystem is available.

**defconfig and the config proliferation.** Each architecture and many boards ship a default configuration in `arch/*/configs/`. Distributions maintain their own full configs. `make savedefconfig` writes a *minimal* configuration listing only the symbols that differ from Kconfig defaults, so the saved file stays small and reviewable and survives the addition of new options. The tree-wide effect was that most `defconfig` files are now minimal, and changes to the Kconfig defaults can change what an old defconfig means (to verify for the target version).

**Tailoring tools.** `make localmodconfig` takes the current configuration and the list of modules loaded on the running system (`lsmod`) and turns off every module that is not loaded, shrinking build time from hours to minutes. `localyesconfig` does the same but builds the loaded modules in. These are developer tools: the result works on the machine it was generated on, with the devices that were attached at the time, and may omit drivers for hardware that was not in use then.

**Fragments and scripted changes.** Maintaining many configurations by hand does not scale. `scripts/kconfig/merge_config.sh` merges small *fragment* files of `CONFIG_X=y` lines onto a base config and warns about overridden or unmet entries; `scripts/config` enables, disables and queries individual symbols (`--enable`, `--disable`, `--module`, `--set-str`, `--state`). The kernel's build targets also include merged configurations such as `make kvm_guest.config`, `make debug.config` and `make xen.config` (named fragments under `kernel/configs/`), allowing recipes like `make defconfig kvm_guest.config`.

**Cross-compilation.** Kernel developers rarely sit at the target machine. The `ARCH=` variable selects the architecture directory, and `CROSS_COMPILE=` supplies a toolchain prefix (such as `aarch64-linux-gnu-`). Debian and Ubuntu package cross toolchains (`gcc-aarch64-linux-gnu`), and `crosstool-ng` and Buildroot build them. Since about 2019, clang/LLVM can build the kernel for several architectures with `LLVM=1` (the whole toolchain, including `ld.lld`, `llvm-objcopy` and friends), which has the advantage that one compiler binary targets many architectures; Android and ChromeOS kernels build with clang as the default.

**Reproducibility and out-of-tree builds.** The `O=build_dir` option keeps build products out of the source tree, enabling several configurations from one source checkout. Work toward reproducible builds (fixed timestamps and build host fields through `KBUILD_BUILD_TIMESTAMP`, `KBUILD_BUILD_USER`, `KBUILD_BUILD_HOST`) lets different people produce identical binaries.

**Emerging pattern.** Describe options declaratively; keep configs minimal and layered (a base `defconfig`, plus named or local fragments); regenerate the final `.config` with `olddefconfig` so that dependencies and new symbols resolve consistently; build out-of-tree with an explicit architecture and toolchain; and make every step scriptable and repeatable.

Configuration is where the kernel's early success became a problem. In the 1990s the build had a few dozen options and a question-and-answer script; a decade later there were thousands of options with dependencies between them, and the old script could not keep them consistent. A purpose-built language, Kconfig, replaced it, with a menu front end and a solver that checks dependencies. Cross-compilation grew in parallel, because embedded developers needed to build for devices that could not host a compiler. Both topics are about the same thing, which is controlling the product of a build without editing source: what goes in, and for which machine.

## Current state

**The Kconfig language in practice.** A typical entry:

```
config VIRTIO_BLK
	tristate "Virtio block driver"
	depends on BLOCK
	select VIRTIO
	help
	  This is the virtual block driver for virtio.
```

The key rules are:

- `depends on EXPR` makes the symbol visible and settable only if the expression (using `&&`, `||`, `!`, symbols and comparisons) is true. A symbol whose dependencies fail is forced to `n`.
- `select SYM` forces another symbol on whenever this one is on, *ignoring that symbol's own dependencies*. This is powerful and dangerous; the kernel documentation warns to use it only on symbols without prompts and without dependencies of their own, or an unmet dependency can silently be bypassed (the build tools print an "unmet direct dependencies" warning).
- `imply` is a weak `select`: it suggests the symbol but allows the user to disable it.
- `default` sets the initial value; several defaults are evaluated in order. `range` limits numeric values. `visible if` and `if` blocks scope menus. `choice` groups mutually exclusive options. `menuconfig` creates a menu that is itself an option. Symbols with no prompt are only set by `select`, `default` or dependencies.
- Since 4.18 the language also has a macro facility (shell-like `$(...)`) used for toolchain feature probes: for example, an option can depend on `$(cc-option,-fstack-protector-strong)` so it is unavailable if the compiler lacks the flag.

**Reading a `.config`.** Lines of the form `CONFIG_FOO=y`, `CONFIG_FOO=m`, `CONFIG_FOO=123`, `CONFIG_FOO="string"` set values; `# CONFIG_FOO is not set` records an explicit `n`. The header comment records the kernel version and compiler used. A config produced by an older tree is brought up to date with `make olddefconfig` (accepts defaults for new symbols silently) or `make oldconfig` (asks about each new symbol) or `make listnewconfig` (lists them).

**Config targets.**

| Target | Effect |
|---|---|
| `make defconfig` | architecture default config from `arch/$ARCH/configs/` |
| `make <board>_defconfig` | a named default for a board or class |
| `make allyesconfig` / `allmodconfig` / `allnoconfig` / `randconfig` | extremes for build testing (everything, everything as module, minimal, random) |
| `make localmodconfig` | disable modules not currently loaded, from `lsmod` (or from `LSMOD=file`) |
| `make menuconfig` | text UI |
| `make savedefconfig` | write a minimal `defconfig` listing only non-default symbols |
| `make olddefconfig` | update an existing `.config` taking defaults for new symbols |
| `make kvm_guest.config`, `debug.config`, `xen.config` | merge a named fragment from `kernel/configs/` |
| `make help` | list targets for the architecture |

The `allyesconfig`, `allmodconfig` and `randconfig` builds are used heavily by maintainers and by automated test systems (0-day) to catch dependency and build errors across configurations.

**A small-kernel workflow for a virtual machine.** To build a kernel to boot in QEMU, start with `make defconfig` (or `make x86_64_defconfig`), merge the virtual machine fragment (`make kvm_guest.config`), enable the features needed (virtio block and network drivers, a 9p or virtiofs filesystem, serial console, devtmpfs), disable bulky debugging, run `make olddefconfig`, and build with `make -j$(nproc)`. The result is a kernel of a few megabytes that boots in a second or two. Tools such as `virtme-ng` automate this, as the next topic shows.

**Fragments and `scripts/config`.** A fragment file contains only the lines you want:

```
CONFIG_VIRTIO_PCI=y
CONFIG_VIRTIO_BLK=y
CONFIG_VIRTIO_NET=y
# CONFIG_DEBUG_INFO is not set
```

`scripts/kconfig/merge_config.sh -m .config fragment.config` merges it into `.config` (with `-m` writing only the merged file) and then `make olddefconfig` resolves dependencies. The critical point is the last step: a fragment entry whose dependencies are not satisfied does not produce an error. It is dropped silently when the dependencies are evaluated. `merge_config.sh` prints a warning for requested values that ended up different from what the fragment asked (a `Value requested…` warning); build scripts should treat this as a failure, not noise.

**Cross-compiling.**

```
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- defconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc) Image modules dtbs
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- INSTALL_MOD_PATH=out modules_install
```

Notes: `ARCH` and `CROSS_COMPILE` must be given to every make invocation (or exported or placed in the environment), because the config and the build both depend on them; mixing them yields confusing errors. The image name differs per architecture (`bzImage` on x86, `Image` on arm64, `zImage` on 32-bit ARM, `vmlinux` always as the uncompressed ELF); device tree blobs (`dtbs`) are needed on many ARM and RISC-V boards. With clang, `make LLVM=1 ARCH=arm64 ...` replaces `CROSS_COMPILE` for most cases (and `LLVM_IAS=1`, the default in modern trees, uses clang's integrated assembler). Build requirements are listed in `Documentation/process/changes.rst` (minimum versions of gcc or clang, binutils, make, bash, flex, bison, perl, openssl and so on); missing `libelf-dev`, `libssl-dev`, `flex`, `bison` and `bc` are the usual first failures.

**Useful build knobs.** `-j` for parallelism; `O=dir` for out-of-tree builds; `V=1` for the full commands; `W=1`, `W=2` for extra warnings; `C=1` to run `sparse`; `make compile_commands.json` (via `scripts/clang-tools/gen_compile_commands.py`) to feed editors; `make targz-pkg`, `make bindeb-pkg` or `make binrpm-pkg` to build packages; `make modules_install` and `make install` for installation (not needed for VM boot tests with `-kernel`); `ccache` or distributed compile to speed repeated builds; `make clean`, `mrproper` and `distclean` at increasing levels; `make -s` for quiet output.

### The generalised pattern: a configuration is a point in a constrained space

Every Kconfig tool, whether the menu, a defconfig, a fragment or a localised config, is a way of choosing a point in a space whose edges are the dependency rules. The generalised view makes the tools easy to compare: `defconfig` names a known good point, fragments move from one point by a small step, `localmodconfig` shrinks the point toward what a running machine uses, and the solver repairs anything inconsistent. Cross-compiling adds one more coordinate, the target architecture, and the compiler prefix is just how the build learns it. Seeing these as operations on a single object, the configuration file, explains why they compose and why mixing build trees for different targets in one directory corrupts them.

## Assessment: the good, the bad and the ugly

**The good.** The declarative language gives a machine-checkable description of thousands of options with dependency resolution, so inconsistent configurations are hard to reach. The target set covers common needs from a plain "boots somewhere" baseline to randomised build testing. Fragments and `scripts/config` make configuration scriptable and reviewable, and `savedefconfig` makes configs small and diffable. Cross builds with `ARCH` and `CROSS_COMPILE` or `LLVM=1` are straightforward once understood, and out-of-tree builds allow many configurations from one source.

**The bad.** The sheer number of options (well over ten thousand symbols) makes discovery hard; help text varies in quality and dependency chains are opaque. The silent dropping of unmet requests catches newcomers: a fragment that seems to enable a driver does nothing because a parent option is missing. `select` can bypass dependencies and produce builds that fail to link. `localmodconfig` omits hardware not present when it ran, causing surprises after hardware changes. Configs from different kernel versions are not portable without `olddefconfig` and review, as defaults change.

**The ugly.** Toolchain mismatches produce cryptic failures: gcc plugins, `CONFIG_*` options that probe the compiler at configuration time (so that a `.config` made with one compiler differs under another), missing host libraries, and a `.config` reused after a compiler upgrade can enable or hide options. Cross builds fail when only `ARCH` is set but not `CROSS_COMPILE` (the host compiler builds target code), or when stale objects remain from an earlier `ARCH` (the build directory must be cleaned or separated with `O=`). Randomised and all-yes builds expose very long build times and rare combinations that fail. Large debug configs (`DEBUG_INFO`, KASAN, KCOV) enlarge the kernel by an order of magnitude and slow boots and builds significantly. Module signing and Secure Boot settings embedded in distribution configs make a copied `.config` unbootable on locked-down machines. Kconfig's own corner cases (ordering of `default` lines, `choice` semantics, behaviour of `imply`) are subtle enough that even maintainers consult the documentation.

Mitigations: always run `make olddefconfig` after editing; check the final `.config` for the symbols you asked for (script it); keep fragments small and named for their purpose; build out-of-tree with an explicit `O=` per configuration; set `ARCH` and `CROSS_COMPILE` (or `LLVM=1`) in a wrapper script; record the compiler version with the config; and use `allmodconfig` or `randconfig` builds to test changes that touch Kconfig.

## Applications beyond this domain

- **Embedded Linux build systems.** Buildroot and the Yocto Project carry kernel config fragments per board and use the same Kconfig language for their own package selection; BusyBox, U-Boot, coreboot and Zephyr use Kconfig to express features, so the skill transfers directly to bootloaders and firmware.
- **Distribution packaging.** Distribution kernels are assembled from a base config plus architecture and flavour fragments, with strict checks that no config symbol changes unintentionally between releases (Fedora and Debian have tooling for this).
- **Continuous integration for kernels.** KernelCI and the 0-day bot build many configurations on many architectures for each tree, using the targets described here, with cross toolchains in containers.
- **Hypervisor and cloud kernels.** Minimal guest kernels (Firecracker, Cloud Hypervisor, Kata) are tailored configs with virtio and few extras to cut boot time and memory; a host kernel adds KVM, vhost and VFIO options. The fragment workflow in this topic is how those are produced.
- **Product security hardening.** Hardening guides (KSPP recommended settings, CIS benchmarks) are lists of config symbols, applied as fragments and verified with tools like `kconfig-hardened-check`.
- **Other software with feature flags.** Declarative feature models with dependencies and constraint solving appear in software product line engineering, Linux package build options (USE flags in Gentoo), and the C preprocessor feature matrices that Kconfig was designed to tame.

## Examples

**A fragment that silently does nothing.** A developer wants KVM on Intel hosts and writes `CONFIG_KVM_INTEL=y` into a fragment. After `merge_config.sh` and `olddefconfig`, the final `.config` shows `# CONFIG_KVM_INTEL is not set`. The warning a `Value requested…` warning shows the cause: its parents `CONFIG_VIRTUALIZATION` and `CONFIG_KVM` were not enabled. Adding them to the fragment makes it work.

**Shrinking a build.** On a laptop, `make localmodconfig` against the loaded modules produces a configuration with a few hundred modules instead of several thousand, cutting a full build from over an hour to a few minutes. A USB Wi-Fi adapter that was not plugged in at the time does not work in the resulting kernel. The developer plugs it in, reruns `localmodconfig` or enables the driver manually.

**A cross build.** On an x86-64 workstation: `make ARCH=arm64 LLVM=1 O=build/arm64 defconfig` then `make ARCH=arm64 LLVM=1 O=build/arm64 -j16 Image dtbs`. The output `build/arm64/arch/arm64/boot/Image` boots on `qemu-system-aarch64 -M virt`. Dropping the `ARCH` on the second command produces an x86 build with an arm64 configuration and a stream of errors.

**The select trap.** A driver `select`s a library symbol that has a prompt and depends on `BLOCK`. On a configuration with `BLOCK` disabled, the library is forced on anyway, and the build fails at link time. The build prints an `unmet direct dependencies` warning. The fix is to make the driver depend on the same conditions or to convert the library symbol to a promptless one.

**A failing example: stale objects.** A developer builds for x86, then runs `make ARCH=arm64 defconfig` in the same tree without cleaning. The next build reuses x86 objects and aborts with relocation errors. `make mrproper`, or separate `O=` directories per target, avoids it.

**Hardening as fragment.** A security team keeps `hardening.config` with `CONFIG_INIT_ON_ALLOC_DEFAULT_ON=y`, `CONFIG_FORTIFY_SOURCE=y`, `CONFIG_RANDOMIZE_BASE=y` and similar entries; CI builds with it on every kernel update and fails if any symbol is dropped in the final config.

## Related problems and ideas

### Related

- **Alternative config systems**: Buildroot-style menus for whole systems; Nix and Guix specify kernel builds as functional expressions; Yocto layers; none replace Kconfig for the kernel itself, but they wrap it.
- **Solver-based configuration**: tools such as `kconfiglib` (Python) and the research work on feature-model analysis use SAT solvers to find valid configurations, count the variability, and check for dead options.
- **Unified kernel images and build-time signing**: distributions combine the kernel, initramfs and command line into a signed image, moving config-time decisions into the boot chain.
- **Out-of-tree module builds** against a configured tree or installed headers, covered in the modules topic.
- **Build performance**: `ccache`, `sccache`, distributed builds (`distcc`), link-time optimisation options (`CONFIG_LTO_CLANG`) and unity builds trade build time for runtime speed or size.
- **Reproducible and hermetic builds**: containerised toolchains, pinned compiler versions and sandboxed builds keep results consistent over time; Bazel and Android's kernel build system (Kleaf) model the kernel build this way.

### Opposing approaches

The opposing approaches replace the kernel's own system with a wrapper or a model. Buildroot and Yocto treat the kernel as one component in a whole-system build and drive its configuration from their own recipes. Nix and Guix describe kernels as pure expressions whose output is fixed by their inputs, which delivers reproducibility the plain build does not. Research on feature models treats the option space as a formal object and uses solvers to analyse it. The kernel's own method remains the base because it is the one every maintainer understands, and the alternatives mostly generate its input files.

## Active research

Work on the configuration system and build includes formal analysis of Kconfig (detecting dead or unreachable options, unmet dependency bugs and the effect of `select`), automated generation of small kernels for a given workload (tools that trace which code runs and derive a config, as in work on kernel debloating and attack-surface reduction), faster builds (better incremental builds and link steps), reproducibility of kernel binaries across builders, and improved Rust and clang support in the build (the `rustc` toolchain for Rust for Linux). Another strand studies the effect of configuration choices on performance and security, using large configuration sampling on the tree. Specific tool names and results should be checked against current literature (to verify).

## Future direction

Expect continued movement to LLVM as a first-class toolchain, to Rust support in the build (with associated config symbols and toolchain probes), and to better reproducibility. The number of options will keep growing, which raises the value of minimal defconfigs, fragments and named configuration sets. For daily work, the stable skill is a scripted, repeatable recipe: base config, fragments, `olddefconfig`, verification that the requested symbols are in the final `.config`, and an out-of-tree build with explicit architecture and toolchain variables. Version-specific details such as the list of named fragment targets, the default of `LLVM_IAS` and the minimum compiler versions should be read from the documentation of the tree being built (to verify).
