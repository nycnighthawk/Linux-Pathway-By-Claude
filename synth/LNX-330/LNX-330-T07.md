# KUnit: unit tests that run inside the kernel build

## Define the problem

Most kernel code runs in a privileged environment that user-space test frameworks cannot reach: it calls internal functions that are never exported, depends on kernel data structures and has no libc. To test a hash function, a parser, a data structure or a subsystem helper, a developer used to write a throwaway module or run a whole kernel and poke it from user space. Both are slow, and neither produces output a tool can aggregate.

Unit testing needs a framework that lives in the kernel, can call internal (even static) functions, reports results in a machine-readable form, and can run quickly without hardware. KUnit is the kernel's answer. Its companion script runs the tests in a small kernel built to run as an ordinary process, so a developer gets feedback in seconds.

## History and approaches

**Ad hoc test modules.** Before a standard framework, kernel developers wrote modules with a `module_init` that ran checks and printed results to the log. Several in-tree self-tests (lib/test_*.c) follow this style. Each one invented its own output format and its own way to report failure.

**kselftest.** The `tools/testing/selftests` directory collects user-space programs that exercise kernel interfaces from outside. It is the right tool for system-call behaviour and end-to-end tests, and is covered later in this course. It cannot test an internal function that is not exposed to user space.

**KUnit.** Brendan Higgins and colleagues at Google proposed a unit-testing framework in 2018 and it was merged in the 5.5 release (to verify). It borrows from xUnit frameworks and from the Google Test style: test cases grouped in suites, assertion macros, setup and teardown functions, parameterised cases. The design goals include being easy to write, being able to run without special hardware and printing results in the Test Anything Protocol (TAP) so that existing tooling can parse them.

**User-Mode Linux.** UML is a port of Linux that runs as a user-space process (`ARCH=um`): the kernel is an ordinary executable with its own scheduler, and guest "devices" map to host files and sockets. It starts in a fraction of a second and needs no virtualisation support. KUnit's wrapper script chooses UML by default for that reason. It can also run under QEMU for other architectures when architecture-specific code is under test.

**Mocking and stubs.** Later releases added function redirection helpers ("static stubs") so a test can replace a function called by the code under test, and a fake-device framework for driver tests, which fills the gap between pure functions and hardware-dependent code.

## Current state

### Anatomy of a test

A test file is a C file in the kernel tree, conventionally named after the code with `_kunit.c` or `_test.c`, guarded by a Kconfig option that depends on `KUNIT`. A test has three layers:

- **Test case**: a function `static void name(struct kunit *test)` containing assertions.
- **Suite**: an array of cases created with `KUNIT_CASE(name)`, terminated by an empty entry, wrapped in a `struct kunit_suite` that gives the suite a name and optional `init` and `exit` functions (run before and after each case).
- **Registration**: `kunit_test_suite(suite)` registers the suite so it runs at boot (when built in) or at module load (when built as a module).

Assertions come in two families. `KUNIT_EXPECT_*` records a failure and lets the case continue; `KUNIT_ASSERT_*` records a failure and ends the case immediately, which is right when later lines would crash on the failed condition, for example a failed allocation. Macros cover equality (`KUNIT_EXPECT_EQ`, `_NE`), truth (`_TRUE`, `_FALSE`), pointers (`_NULL`, `_PTR_EQ`), strings (`_STREQ`) and memory (`_MEMEQ`), with variants that take a custom failure message. `KUNIT_FAIL` and `kunit_info` support custom reporting. Resources allocated with `kunit_kzalloc` are freed automatically when the test ends, even after an assertion aborts it.

Parameterised tests use `KUNIT_CASE_PARAM` with a function that generates parameters, so one case body runs against a table of inputs and reports each as a subtest.

### Because tests are part of the kernel

KUnit tests can include the file under test directly (`#include "foo.c"` is allowed for this purpose) and so call static functions. The framework itself is a kernel subsystem (`CONFIG_KUNIT`), and a test option should depend on it and default to off, with `CONFIG_KUNIT_ALL_TESTS` as a way to enable every test whose dependencies are met. The in-tree documentation advises writing tests for new code as part of the same series and recommends that tests do not depend on hardware, timing or global state, so they are deterministic.

### Running tests

The script `tools/testing/kunit/kunit.py` is the front end:

- `./tools/testing/kunit/kunit.py run` builds a UML kernel with the configuration in `.kunit/`, boots it, parses the output and prints a summary of pass, fail and skip counts.
- `--kunitconfig=<path>` supplies a configuration fragment listing the options for the tests of interest (many subsystems keep a `.kunitconfig` file in their test directory), which is much faster than building every test.
- A positional filter argument selects suites or cases by name glob.
- `--arch=<name>` selects another architecture and runs it under QEMU, for example for tests of architecture-specific code (the script ships a table of supported architectures and cross-compiler settings; check it for your tree).
- `--make_options`, `--build_dir` and `--jobs` control the build; `kunit.py parse` reads TAP output from a log or the standard input for results obtained elsewhere.
- `--raw_output` prints kernel output unfiltered, useful when a test crashes the UML kernel.

Without the script, the tests built into a kernel run at boot and print TAP to the console; modular tests run on `modprobe`, and a debugfs interface (`/sys/kernel/debug/kunit`, when enabled) makes results readable afterwards (to verify the layout in your version).

### Output

The output follows TAP version 14 with nested subtests: a top-level plan, one block per suite, and `ok` or `not ok` lines per case with diagnostic lines naming the file, line and expected versus actual values. The summary reports totals. CI systems use the same format, which is one reason KUnit results appear in KernelCI and in bots' mail on patches.

### Writing good tests

Practical rules: test one behaviour per case and name it after the behaviour, cover boundaries and error paths (not only the happy path), keep the tests independent of order and make them fast so they run for every patch. The effectiveness of a suite can be measured by mutation: deliberately break the code and see whether a test fails, as the lab for this topic does with a toy harness. Coverage tools, such as gcov support in UML builds, show which lines the tests execute (to verify the exact support).

When a test needs a collaborator, the options are to pass a fake (a small struct of function pointers), to use a static stub to redirect a call, or to use the fake-device helpers to create a device with a bound driver. A test that needs real hardware belongs elsewhere, in kselftest or in a driver test on a board.

## Assessment: the good, the bad and the ugly

**The good.** KUnit gives kernel developers the red-green loop that application developers take for granted: a test in a few lines, results in seconds, output in a standard format. Tests run on every developer's machine without hardware. Because they can call static functions, they can test internals directly, and tests for new code add a regression barrier for later changes.

**The bad.** UML is not a complete kernel: it has no real hardware, a different memory layout and, for a few features, no support, so a test of architecture-specific or timing-dependent code may not run there. Tests of code that depends on other subsystems require mocking, which has costs. Test coverage across the kernel is thin and uneven; many subsystems have no unit tests.

**The ugly.** Tests that read global state or rely on timing become flaky. Including `.c` files into tests is convenient but entangles the test with the file's internal layout, and refactoring then breaks the test. Build time for a UML kernel is still minutes for a cold build. Adoption depends on subsystem maintainers requiring tests, which they do not all do.

## Applications beyond this domain

- **Embedded and RTOS projects** apply the same pattern: a unit-test framework compiled into the firmware, run on an emulator, results parsed by a script.
- **Hypervisor and VMM development**: instruction emulators, device models and page-table code can be tested as pure functions; QEMU's test suite includes unit tests and qtest, which drive devices with a test protocol, and its patch guide asks contributors to test before submission [src: qemu-docs 6fd701aa9ba56dc9].
- **Safety-critical software** uses unit-test evidence and coverage as part of certification.
- **Teaching**: the mutation exercise (can your tests catch a deliberately wrong implementation?) works in any language.

## Examples

**A first test.** A developer adds `lib/foo_kunit.c` with three cases for a helper that parses a number from a string, a Kconfig entry `FOO_KUNIT_TEST` depending on `KUNIT`, and a `.kunitconfig` listing `CONFIG_KUNIT=y` and the new option. `kunit.py run --kunitconfig=lib/.kunitconfig` prints `ok` for all three in seconds.

**An assert versus an expect.** A case allocates a buffer and then compares contents. With `KUNIT_EXPECT_NOT_NULL` the case would continue and dereference null, crashing the UML kernel. Switching to `KUNIT_ASSERT_NOT_NULL` ends the case cleanly with a clear failure.

**A table-driven test.** A parser is tested with twenty input and expected-output pairs through a parameter generator. When one fails, the output names the parameter, which a flat loop would hide.

**A crash.** A test triggers a NULL dereference. UML prints an oops and the run is marked as crashed; `--raw_output` shows the backtrace. The author fixes the code under test, not the test.

## Related problems and ideas

- **kselftest** (next topic) tests the user-space interface of the kernel from outside.
- **Boot testing** (earlier) is the integration layer above KUnit.
- **Sanitizers** (KASAN, UBSAN, lockdep) can be turned on during KUnit runs, catching bugs the assertions never describe.
- **Fuzzing** explores inputs a developer did not imagine; KUnit suites often grow from fuzzer-found regressions.
- **Mutation testing and coverage** measure how good the tests are.

## Active research

Active areas include more faithful fakes and stubs for driver testing, better coverage reporting for kernel tests, running KUnit under more architectures and in CI at scale (including test-result aggregation across labs), and applying fuzzing and symbolic execution to the same test bodies. Rust code in the kernel has its own doctest-based integration with KUnit (to verify the current status).

## Future direction

The expectation is that new core code and bug fixes come with a KUnit test as a normal condition of review, and that CI systems run all the KUnit suites on every posted patch. As more drivers become testable without hardware, the share of kernel code with unit tests should grow from its current low base.
