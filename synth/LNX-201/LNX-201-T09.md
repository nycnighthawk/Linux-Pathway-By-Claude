# Wireless links and port-based authentication: Wi-Fi clients, WPA and 802.1X on Linux

## Define the problem

A wired port gives physical control: whoever can plug in already stands in the building. A radio signal reaches past the walls, so a wireless network has to decide who may join, hide what is sent from anyone listening, and obey national rules on frequencies and power. On a Linux laptop or an embedded device this adds new layers to the picture seen so far: a radio driver and firmware, a regulatory setting, an authentication handshake, and a supplicant daemon that carries it out before an IP address is ever requested. In offices and universities the same authentication model is also applied to wired switch ports, so a plug in the wall is not trusted either.

This slice is an introduction at the depth of a working administrator, not a wireless-engineering course. It covers how a Linux host joins a Wi-Fi network and with which security mode, what IEEE 802.1X adds (an authenticator in front of the network and a RADIUS server behind it), how to configure a client for EAP methods with NetworkManager, how to read the state with `nmcli`, `iw` and `rfkill`, and why servers often have wireless disabled altogether. Hands-on practice needs radio hardware, so the matching lab is a guided one.

## History and approaches

The original 802.11 standard appeared in 1997, with the 802.11b and 802.11a/g generations bringing the familiar 2.4 GHz and 5 GHz products. Its first security, WEP, was broken in the early 2000s, and the industry's Wi-Fi Alliance published WPA as a stopgap and then WPA2 (based on the 802.11i amendment, with AES-CCMP) in 2004. WPA3, announced in 2018, replaced the pre-shared-key handshake of personal networks with SAE (a password-authenticated key exchange that resists offline guessing) and added stronger suites for enterprise networks. Newer amendments add more bands (6 GHz) and higher speeds, with each generation also stepping up the minimum security.

Two models of authentication exist. **Personal** mode uses one shared passphrase; everyone who knows it shares a trust domain, and a leaked passphrase means changing it everywhere. **Enterprise** mode, built on IEEE 802.1X, authenticates each user or device individually through the Extensible Authentication Protocol (EAP, RFC 3748). Three roles take part: the **supplicant** (the client software), the **authenticator** (the access point or switch, which blocks traffic from the port until authentication succeeds) and the **authentication server**, normally RADIUS (RFC 2865 and its successors), which holds the accounts or checks certificates. EAP is a framework with several methods: EAP-TLS (client and server certificates, the strongest and most work to deploy), PEAP and EAP-TTLS (the server proves itself with a certificate and the user then proves themselves inside a TLS tunnel with a password, commonly MSCHAPv2 in PEAP), and a few others. The roaming federation eduroam is a well-known use of the model across institutions.

On Linux the client side has long been `wpa_supplicant`, a daemon that handles the 802.11 association and the EAP exchange, usually driven by NetworkManager, systemd-networkd or iwd rather than configured by hand. The authenticator side can also run on Linux with `hostapd`, and FreeRADIUS is the common open source RADIUS server. Red Hat's documentation walks through a lab arrangement of all three: FreeRADIUS configured for EAP, `hostapd` as the authenticator on a wired port, and a client tested against them [src: rhel-10-docs d5a11f1af9fe2b38] [src: rhel-10-docs 44c561e9f5398ea3]. Rocky Linux publishes FreeRADIUS guides that pair it with a database or with a Samba domain for the accounts [src: rocky-docs 8e95931c2de80f15] [src: rocky-docs c34d4c74ae3f9fb9].

## Current state

### The Linux wireless stack and its tools

Drivers register with the kernel's `cfg80211` and `mac80211` layers, and often need firmware from the `linux-firmware` package. Userspace tools:

- `rfkill list` shows radios blocked by software or by a hardware switch; `rfkill unblock wifi` clears a software block. A radio that is "hard blocked" needs the physical switch or key.
- `nmcli radio wifi on|off` toggles Wi-Fi in NetworkManager, and `nmcli device status` lists devices and their state.
- `iw dev` lists wireless interfaces; `iw dev wlan0 link` shows the current association (SSID, frequency, signal); `iw dev wlan0 scan` (as root) lists nearby networks; `iw reg get` shows the regulatory domain.
- `nmcli device wifi list` scans and prints networks with security type and signal; `nmcli device wifi connect "SSID" password "secret"` creates and activates a profile for a personal network.
- `wpa_cli` talks to a running `wpa_supplicant` for status and debugging; its debug log shows the EAP exchange.

Interface names follow predictable naming (`wlp3s0` rather than `wlan0`) on most distributions, so scripts should discover the name from `nmcli` or `iw dev`.

### The regulatory domain

Every country limits which channels and what transmit power may be used. The kernel enforces a regulatory database and the driver may self-limit further. On RHEL a udev rule runs a helper that sets the country from the environment, and if detection fails the administrator can store a country code in `/etc/sysconfig/regdomain` so the correct domain is applied at boot; Red Hat warns that setting it manually turns off automatic detection when travelling [src: rhel-10-docs 9ed471901b3317b3]. On other distributions the equivalent is the `wireless-regdb` package and `iw reg set XX` or a configuration entry for the supplicant or the network manager. A wrong domain is a common reason that some 5 GHz channels are missing from scans.

### Configuring 802.1X on a Wi-Fi profile

With NetworkManager, an enterprise profile is a normal Wi-Fi connection with the security mode set to `wpa-eap` and 802.1X properties added. Red Hat's procedure for PEAP with MSCHAPv2 sets the key management, the EAP type, the inner method and the identity in one command, because those four properties must be written together, and then stores the password and the authority certificate separately [src: rhel-10-docs 1a51759af9fec74d]:

```
nmcli connection modify wlp1s0 802-1x.eap peap 802-1x.identity alice \
    802-1x.phase2-auth mschapv2 wireless-security.key-mgmt wpa-eap
nmcli connection modify wlp1s0 802-1x.ca-cert /usr/local/share/ca-certificates/corp-ca.pem
nmcli connection modify wlp1s0 802-1x.password-flags agent-owned
nmcli connection up wlp1s0
```

Points that matter in practice:

- **Validate the server.** Without a configured CA certificate (`802-1x.ca-cert`, optionally a server-name match through `802-1x.domain-suffix-match`) a client will accept any access point presenting any certificate, and an attacker's lookalike network can harvest passwords. The documentation says explicitly that validating the authenticator improves security.
- **Where the password lives.** Stored in the profile it is readable by root in a plain file; the `password-flags` setting hands the secret to a keyring agent or asks on each connect.
- **The `wpa_supplicant` package** must be installed because NetworkManager delegates the EAP exchange to it.
- **EAP-TLS** replaces the password with files: `802-1x.eap tls`, `802-1x.client-cert`, `802-1x.private-key` (and CA), with the key file readable only by root. The same properties work on a wired profile; Red Hat's chapter for Ethernet gives the file-system-certificate variant [src: rhel-10-docs 6ebd03d88382a4f3].
- The RHEL network system role can apply the same settings across many hosts [src: rhel-10-docs 2bd416e42cd1ac61].

Debugging EAP failures follows a standard path: `journalctl -u NetworkManager -u wpa_supplicant` to see the reason, the RADIUS server's log (the authentication server states why a user was rejected), and, for TLS failures, certificate dates and chain. A known stumbling block on newer systems is a TLS library rejecting an old server's legacy protocol settings; Arch's wiki describes the symptom and the workaround, which weakens security and should be treated as a stopgap [src: archwiki 2d225a1bc718bb3d].

### The authenticator and server side (overview)

On the wired side, `hostapd` acts as an 802.1X authenticator for an Ethernet interface, relaying the client's EAP messages to the RADIUS server and opening the port when it gets an accept. Red Hat's course material shows how the authenticator's events can then drive firewall decisions, allowing traffic only for authenticated clients [src: rhel-10-docs a4e588afc20ebdfd]. On the RADIUS server, the EAP module defines which methods are enabled, which certificate it presents, and where users are looked up. A lab with a bridge and virtual interfaces can exercise this without radio hardware, but wireless access points normally run `hostapd` too, or a vendor controller plays the authenticator role.

### Security baselines

Servers and fixed hosts rarely need Wi-Fi, and compliance guides ask to turn it off. The DISA STIG rules for RHEL 9 and 10 require that wireless network adapters are disabled on systems with radios, with the check being `nmcli device status` for devices of type wifi and the fix being `nmcli radio all off` or blacklisting the driver module [src: disa-stig 44b8bc1d2af3cc34] [src: disa-stig 1f28693d713c98a5]. Where Wi-Fi is needed, baselines also expect enterprise authentication with server validation, and a recent security suite rather than WEP or TKIP.

## Assessment: the good, the bad and the ugly

**The good.** 802.1X gives per-identity access control and revocation (disable the account and the device loses access) and avoids a shared passphrase. The Linux stack is open and well covered by NetworkManager, so client configuration is a handful of `nmcli` properties, and the same properties apply to wired and wireless. Certificates with EAP-TLS remove passwords from the equation. WPA3 improves protection for ordinary passphrases.

**The bad.** Enterprise authentication needs a public key infrastructure, a RADIUS server and careful profile deployment, which is a large project for small sites. Client profiles that skip server validation are widespread and silently insecure. Drivers and firmware vary in quality, so a device that works well on one distribution may behave badly on another, and some chipsets lack firmware in free distributions. Roaming and power-saving behaviours produce hard-to-reproduce problems.

**The ugly.** Misconfigured clients that trust any certificate; shared passphrases that never rotate; captured handshakes cracked offline when a weak passphrase protects a WPA2 personal network; and rogue access points advertising a known SSID. Troubleshooting is made harder by encrypted traffic and by regulatory variation between countries.

## Applications beyond this domain

The 802.1X model also protects wired switches and virtual or VPN gateways, where an authenticator in front of a network port relays credentials to a back-end server. RADIUS is used for VPNs, for network device administration and for captive portals. Certificates and EAP-TLS ideas carry over to mutual TLS between services. IoT and embedded work uses Wi-Fi with pre-shared or certificate credentials, with the regulatory settings above. In education, eduroam shows federated identity across organisations with one set of credentials.

## Examples

**1. Join a personal network and check the link.**

```
nmcli radio wifi on
nmcli device wifi list
nmcli device wifi connect "Office-Guest" password "correct horse"
iw dev wlp3s0 link
```

**2. Switch Wi-Fi off on a server.**

```
nmcli radio all off
rfkill list
nmcli device status
```

The third command should show wifi devices as unavailable; to make it durable on a host that must never use radio, also blacklist the driver module.

**3. Set the regulatory domain.**

```
iw reg get
echo 'COUNTRY=DE' | sudo tee /etc/sysconfig/regdomain
```

Replace the country by the correct two-letter code for the site. After the next boot (or after the helper runs again) `iw reg get` should list that country.

**4. Add EAP-TLS to a wired profile.**

```
nmcli connection modify enp1s0 802-1x.ca-cert /opt/net/ca.pem
nmcli connection modify enp1s0 802-1x.eap tls
nmcli connection modify enp1s0 802-1x.private-key /opt/net/host.key
nmcli connection modify enp1s0 802-1x.client-cert /opt/net/host.pem
nmcli connection up enp1s0
```

**5. Watch an EAP failure.**

```
journalctl -f -u NetworkManager -u wpa_supplicant
```

Run the connection attempt in a second terminal and look for the stage where the exchange stops: association, EAP identity, TLS handshake, inner authentication.

## Related problems and ideas

- **Firewall and addressing after authentication.** Authentication only opens the link; DHCP, routing and firewalling follow, as in earlier slices.
- **VLAN assignment.** RADIUS can return a VLAN for each authenticated user, putting users in different network segments.
- **Certificates.** Expiry, trust stores (`update-ca-trust` on Red Hat family systems) and chain order cause many authentication outages.
- **Bluetooth and other radios.** `rfkill` covers them as well, and the same baseline rule on wireless peripherals applies.
- **Monitoring.** Capturing in monitor mode (see the `tcpdump` options in the previous slice) is possible on hardware that supports it, and it can break the association while active.

## Active research

Current work includes WPA3 deployment and transition modes, Wi-Fi 6E and 7 features such as multi-link operation, privacy features such as randomised MAC addresses and the trade-offs for network access control, and enterprise onboarding automation that provisions certificates to devices. In the Linux stack, `iwd` is an alternative to `wpa_supplicant` with simpler configuration, and there is ongoing work on integrating it with NetworkManager and systemd-networkd.

## Future direction

Expect passwords inside EAP to give way to certificates and passkey-like credentials, WPA3 to become the baseline, and device identity to be managed by provisioning systems rather than by hand. For administrators, the durable guidance is: validate the authentication server, prefer certificates, keep radios off on servers, set the regulatory domain, and read the supplicant and RADIUS logs together when authentication fails.
