# Choosing a path: routing tables, policy routing and hosts with several interfaces

## Define the problem

A host with one interface and one default gateway needs almost no routing knowledge. Everything changes with a second interface: a management network beside a production network, a storage VLAN, a backup link, a VPN, a bridge for virtual machines. The kernel must decide, for each outgoing packet, which interface and next hop to use, and for each incoming packet whether it arrived the way a reply would leave. When the decision is wrong, the symptoms are characteristic: a service reachable from one network but not another, replies leaving by a different interface than the one the request came in on (and dropped by a firewall that expects symmetry), two default gateways fighting over the same traffic, or a route that works until the next reboot.

A second set of problems comes from the host acting as a router: forwarding traffic between interfaces, translating addresses, running containers or virtual machines whose traffic must find its way out. This slice covers how Linux chooses routes (destination-based longest prefix match), how to read and edit the routing tables, static routes and their persistence, policy routing for source-based decisions, reverse-path filtering and the asymmetric-routing trap, enabling forwarding, link aggregation and bridging at the level needed to understand multi-NIC designs, and the tools for tracing a path. Dynamic routing protocols (BGP, OSPF) belong to a later course.

## History and approaches

Early Unix hosts routed with a single table maintained by the `route` command, with a "gateway of last resort" as the default. Routing protocols (RIP, then OSPF and BGP, running in daemons such as `routed`, `gated`, Zebra and later Quagga, FRR and BIRD) fed the same table on routers, while ordinary hosts stayed static. This worked as long as the destination address was the only input. Linux 2.1 added **policy routing**, designed by Alexey Kuznetsov along with `iproute2`: the kernel evaluates an ordered list of rules (selector on source address, incoming interface, firewall mark, TOS, UID) and each rule selects one of up to 252 named or numbered routing tables, each holding ordinary routes. The classic `route` command could see only the main table, which is why multi-table setups were invisible to people using the old tools.

Several approaches grew on top. Source-based routing handled multi-homed servers whose replies must leave by the interface that received the request. Multipath routing (ECMP) allowed several equal next hops, hashed per flow. Virtual routing and forwarding (VRF) devices provided separate routing domains within one kernel. Link aggregation (bonding, 2001; teaming, later superseded in the Red Hat family by bonding again) combined several NICs into one logical link. Bridges and VLANs added layer-2 structure. In the container era, per-pod addressing and overlay or native routing in CNIs made the host a router by default: Docker's bridge networks publish ports through NAT, but its direct-routing mode removes the translation and expects the network to know the container subnets [src: docker-docs f84c6aa5266c9bcd], and Cilium's native-routing mode lists requirements the underlying network has to satisfy [src: cilium-docs a93ac0cb264bf330]; the Kubernetes network model requires that pods can reach each other without address translation, which turns host routing into infrastructure [src: kubernetes-docs b14cff44584393a8].

One persistent failure runs through this history: administrators add a second default route to get the second NIC working and create two competing paths. Modern guides document the problem and its fix explicitly [src: rhel-10-docs ff831ee4d1e8c1e6]. The lesson is that destination-based routing cannot express a choice that depends on where the packet came from, and policy routing is the correct tool.

## Current state

### How Linux chooses a route

For each packet the kernel walks the **routing policy database** (RPDB): `ip rule show` lists the rules in priority order, by default `0: from all lookup local`, `32766: from all lookup main` and `32767: from all lookup default`. Each rule that matches selects a table, and the table is searched by **longest prefix match**: among routes whose prefix contains the destination, the most specific wins (`/32` over `/24` over `/0`); ties go to the lowest **metric**; if that also ties, the first route is used or, for multipath routes, the flow is hashed. If no route in a table matches, the walk continues to the next matching rule; if nothing matches, the packet is rejected with "network unreachable". The `local` table holds the host's own addresses and broadcasts; `main` is what `ip route` shows; `default` is normally empty.

```bash
ip route                              # main table
ip -6 route                           # IPv6
ip route show table all               # every table
ip route get 198.51.100.7             # the decision: next hop, interface, source address
ip route get 198.51.100.7 from 192.0.2.10 iif eth1    # decision for a specific source or input interface
ip rule show
```

A route line carries the destination (`default` or a prefix), `via` (next-hop gateway, which must itself be on-link), `dev` (interface), `proto` (who installed it: `kernel` for connected networks, `dhcp`, `static`, `ra`, `boot`), `scope` (`link` for directly connected, `global` otherwise), `src` (preferred source address), `metric`, and flags like `linkdown`. Kernel-installed routes for each configured prefix appear automatically when an address is added.

### Static routes

```bash
ip route add 10.8.0.0/16 via 192.0.2.254                  # through a gateway on a connected network
ip route add 10.9.0.0/24 dev eth1                         # on-link (no gateway)
ip route add default via 192.0.2.1 metric 100
ip route replace 10.8.0.0/16 via 192.0.2.253              # add or change atomically
ip route add blackhole 203.0.113.0/24                     # silently discard; also unreachable, prohibit
ip route add 10.8.0.0/16 nexthop via 192.0.2.254 weight 1 nexthop via 192.0.2.253 weight 1   # ECMP
ip route del 10.8.0.0/16
```

`ip route` changes last until reboot, so persistence belongs in the active network manager. For NetworkManager: `nmcli connection modify lan +ipv4.routes "10.8.0.0/16 192.0.2.254 100"` (destination, gateway, optional metric) followed by `nmcli connection up lan`; the RHEL guide gives a worked example of a network that needs static routes [src: rhel-10-docs c4b5211c5780866c]. For systemd-networkd, a `[Route]` section in the `.network` file with `Destination=`, `Gateway=`, `Metric=`, `Table=`, `Scope=`, `Source=` and `PreferredSource=` [src: man-pages 17268ff04c00fd9e]. For netplan, `routes:` entries with `to:`, `via:`, `metric:` and `table:`. Legacy Red Hat systems used `/etc/sysconfig/network-scripts/route-eth0` and Debian used `up ip route add ...` lines in `/etc/network/interfaces`. A route whose `via` address is not reachable through a connected route is rejected with `Nexthop has invalid gateway`: add the connected network first.

### Multiple default gateways and source-based routing

With two NICs on two subnets, a second default route in the main table does not make traffic use it; it adds an ambiguity that is resolved by metric or luck, and the result is that return traffic for one subnet leaves through the other gateway. The robust design is policy routing: give each interface its own table with its own default route, and add rules that select the table by source address.

```bash
# /etc/iproute2/rt_tables lists names:  100 mgmt   (optional; numbers work too)
ip route add 192.0.2.0/24 dev eth1 src 192.0.2.10 table 100
ip route add default via 192.0.2.1 dev eth1 table 100
ip rule add from 192.0.2.10/32 table 100 priority 1000
ip rule add iif lo oif eth1 table 100        # optional: traffic bound to the interface
ip rule show; ip route show table 100
```

NetworkManager can store the same thing in the profile: `ipv4.route-table 100` puts the connection's routes into table 100 and `ipv4.routing-rules "priority 5 from 192.0.2.0/24 table 100"` adds the rule; the RHEL guides show both the nmcli variant and the RHEL system role variant of sending one subnet's traffic out through a second gateway [src: rhel-10-docs 22c8e19c791559b8] [src: rhel-10-docs 7a88229f94e2a062]. In networkd, `[Route] Table=` plus a `[RoutingPolicyRule]` section does the same. Packet marks (`iptables -t mangle ... -j MARK` or `nft meta mark set`) with `ip rule add fwmark 0x1 table 100` allow routing by protocol or user rather than by source address.

**Reverse-path filtering** (`net.ipv4.conf.<if>.rp_filter`) drops packets whose source address would not be routed back out of the interface they arrived on. Values: 0 off, 1 strict, 2 loose (any route to the source suffices). Strict mode is the default on many distributions and breaks asymmetric designs (traffic in on one NIC, out on another, as with multihomed servers and some VRRP and ECMP deployments); set 2 on interfaces where asymmetry is by design. Related per-interface sysctls: `arp_ignore` and `arp_announce` (control which interface answers ARP for which address, fixing "ARP flux" where a host answers for its other NIC's address), `accept_local`, `log_martians` (log packets dropped for impossible sources, a useful diagnostic).

### Forwarding and NAT

A Linux host forwards packets between interfaces only if told to: `sysctl -w net.ipv4.ip_forward=1` and `net.ipv6.conf.all.forwarding=1`, made persistent in `/etc/sysctl.d/*.conf`. Enabling IPv6 forwarding disables acceptance of router advertisements on interfaces unless `accept_ra=2`. Firewall rules in the `forward` chain decide which forwarded flows are allowed, and masquerading or source NAT in `postrouting` rewrites private source addresses for traffic leaving through a public interface; this is the firewall topic's territory, but a router without forwarding is the most common reason a "gateway" host passes no traffic. Docker, libvirt and Kubernetes all enable forwarding and insert their own firewall rules.

### Link aggregation, bridges and VLANs

Several NICs can act as one: **bonding** modes include `active-backup` (one active, one standby, no switch support needed), `802.3ad` (LACP, needs switch configuration, hash-based load sharing per flow), `balance-alb` and `balance-tlb` (adaptive balancing without switch support). Create a bond with NetworkManager (`nmcli connection add type bond con-name bond0 ifname bond0 bond.options "mode=active-backup,miimon=100"` and enslave ports with `type ethernet ... master bond0`) or in the other stacks' files; inspect it in `/proc/net/bonding/bond0`. A **bridge** connects interfaces at layer 2, giving virtual machines and containers direct attachment to a physical network; the Linux bridge learns MAC addresses per port, and Docker's bridge driver builds on it [src: docker-docs d193fb2170b7a288]. **VLANs** (802.1Q) are subinterfaces, `eth0.100`, carrying tagged traffic; IPvlan and macvlan offer other ways to give virtual interfaces addresses on a physical segment [src: docker-docs 3045ea6b6f4616e6]. A tip from the Arch Wiki: traffic destined for the bridge itself can be accelerated by configuring the bridge's own interface, an example of tuning that applies to multi-NIC virtualisation hosts [src: archwiki aec65ab47f290d8e]. All of these show up as extra interfaces in `ip -br link`, and each can hold its own addresses and routes.

### Tracing a path

`ip route get` shows what this host will do. `traceroute -n host` (UDP by default; `-I` for ICMP, `-T -p 443` for TCP) shows each hop by increasing the TTL; `tracepath` discovers the path MTU as well; `mtr -n host` combines both continuously. Stars (`* * *`) mean the hop does not answer TTL-exceeded messages, not that traffic is lost; judge by whether later hops respond. `ping -I eth1 host` or `ping -I 192.0.2.10 host` tests a specific source interface or address, and the `-M do` option sets the don't-fragment bit for MTU probing [src: man-pages d4c7bfbd58dec926] [src: man-pages 0a0482a51c3ee41e]. `tcpdump -ni eth1 host X` on each interface shows whether the request arrived and where the reply left.

## Assessment: the good, the bad and the ugly

What works well: longest-prefix match plus a small ordered rule list is easy to reason about and very flexible; the same objects serve a laptop, a router, a container host and a switch; `ip route get` makes the kernel's decision explicit; and persistent configuration is available in every network manager.

What works badly: a second default route is the intuitive but wrong fix and is everywhere in forum answers. Reverse-path filtering defaults break correct asymmetric designs without a clear message unless `log_martians` is enabled. Policy routing is powerful but invisible to people who only run `route -n`, and rules and tables are not saved by the old tools. Persistence differs between stacks, so a host rebuilt on a different distribution loses its routes. ECMP and LACP hash per flow, so one large transfer cannot use two links.

The awkward parts: ARP flux on multi-NIC hosts; routes that vanish when the interface goes down and return with different metrics when it comes back; DHCP-supplied routes that override static ones; VPNs that install `0.0.0.0/1` and `128.0.0.0/1` halves to beat the default route; IPv6 default routes from router advertisements that appear with their own preference; and containers whose host networking changes the table underneath other services.

## Applications beyond this domain

Policy routing ideas recur in cloud route tables and security groups, in service-mesh traffic steering, in SD-WAN, and in Kubernetes network policies and egress gateways, where traffic from selected pods is steered through a specific node or IP; Cilium's egress gateway troubleshooting guide describes the same source-based selection problem at cluster scale. ECMP and bonding resemble load balancing at higher layers (L4 balancers, Kubernetes Services), with the same per-flow hashing trade-offs. Longest-prefix match is the foundation of firewall rule sets written as CIDRs, BGP route selection, and `ip rule`-like constructs in VPN products. The habit of asking what the kernel would do, using `ip route get`, carries into debugging of any overlay network.

## Examples

**Two NICs, one broken.** A server has eth0 192.0.2.10/24 (gateway .1) and eth1 198.51.100.10/24 (gateway .1). Someone added a second default route. Clients on the 198.51.100.0/24 side connect but time out: replies leave via eth0 and are dropped. Fix: table 200 for eth1 (`ip route add default via 198.51.100.1 dev eth1 table 200`, `ip route add 198.51.100.0/24 dev eth1 table 200`), rule `ip rule add from 198.51.100.10 table 200`, remove the second main-table default, test with `ip route get 203.0.113.5 from 198.51.100.10`.

**A route that does not survive.** `ip route add 10.8.0.0/16 via 192.0.2.254` fixed the connection until the weekly reboot. The route is recorded with `nmcli connection modify lan +ipv4.routes "10.8.0.0/16 192.0.2.254"`.

**Strict rp_filter drops valid traffic.** A host receives traffic from 203.0.113.0/24 on eth1, but its route to that network points out of eth0. `sysctl net.ipv4.conf.eth1.rp_filter` returns 1; with `log_martians` on, the kernel logs `martian source`. Setting 2 (loose) for eth1, or fixing the routes so the reverse path is symmetric, restores the traffic.

**Router without forwarding.** A gateway VM with two NICs passes no packets. `sysctl net.ipv4.ip_forward` shows 0. After setting 1 (and a firewall forward rule), packets cross; the persistent form goes in `/etc/sysctl.d/90-forward.conf`.

**Debugging a hop.** `mtr -n 198.51.100.7` shows loss at hop 4 that does not continue at hops 5 to 8: that router rate-limits ICMP and the path is fine. Loss that continues to the end is real.

**Bond failover test.** With `active-backup`, pulling the active cable shows the standby taking over in `/proc/net/bonding/bond0` (`Currently Active Slave`), and `ip -s link` on the bond shows no traffic gap beyond the miimon interval.

## Related problems and ideas

Neighbouring areas are dynamic routing (FRR, BIRD with BGP and OSPF; BGP-to-the-host in data centres), firewalling and NAT (next topic), traffic control and QoS (`tc`, queueing disciplines; the Debian handbook describes the principle of quality of service) [src: debian-handbook 327275469e076e73], VRRP and keepalived for gateway redundancy, anycast addressing, and overlay networks (VXLAN, WireGuard, GRE). Alternatives to host-level policy routing include putting the complexity on the network (one gateway, router-based policy), using separate VRFs or network namespaces per service, or running the workload in containers with their own namespace. Ideas still maturing include segment routing, eBPF-based routing and load balancing (XDP, Cilium), and intent-based network configuration that generates routes from declared policy.

## Active research

Active topics include multipath TCP and per-packet load balancing, fast reroute in the kernel (nexthop objects and resilient hashing), VRF and EVPN integration in Linux, eBPF forwarding paths that bypass parts of the stack, and routing in constrained or multi-access environments. Open questions include how to present policy routing state so that ordinary administrators see it by default, and how to coordinate route ownership between network managers, container runtimes and routing daemons on the same host.

## Future direction

Expect nexthop objects, VRFs and eBPF datapaths to be used more widely, more hosts to run routing daemons as part of a routed fabric, and persistent policy routing to be configured through declarative tools (NetworkManager profiles, NMState, system roles). IPv6 routing will receive equal attention as dual stack becomes normal. For administrators the durable approach is to design for symmetric paths, use one table per egress, avoid second default routes in the main table, enable `log_martians` while debugging, and always confirm the kernel's decision with `ip route get` before and after a change.
