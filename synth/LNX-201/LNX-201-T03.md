# Making network configuration persistent: NetworkManager, systemd-networkd and netplan

## Define the problem

Commands such as `ip addr add` change the running kernel and nothing else. A server needs its addresses, routes, DNS servers and link settings applied identically at every boot, after every cable or link event, and whenever a profile is edited, and it needs the configuration to be a file that people and tools can review, copy and version. Laptops add more demands: wireless networks, VPNs, roaming between networks and per-user permissions. Cloud instances add another: the network configuration is generated at first boot from metadata the platform provides. No single design fits all of these cases, and Linux distributions have settled on several, so an administrator must recognise which stack a machine uses, where its configuration lives, how to edit it safely and how to find out what it did.

This slice covers the three stacks the target distributions ship: **NetworkManager** with `nmcli` and `nmtui` (the default on the RHEL family, Fedora, SUSE desktops and Ubuntu desktops), **systemd-networkd** configured by `.network`, `.netdev` and `.link` files (common on minimal servers and containers), and **netplan**, a YAML front end on Ubuntu that generates configuration for either of the other two. It also notes the older ifupdown and ifcfg files that still appear on existing systems.

## History and approaches

Early Linux distributions configured networks with shell scripts. Red Hat used `network-scripts` driven by `/etc/sysconfig/network-scripts/ifcfg-eth0`; Debian used `ifupdown` and `/etc/network/interfaces`; SUSE had its own `ifup` tooling. These worked for static servers, since the configuration was a text file that a script turned into `ifconfig` or `ip` calls at boot. They did not cope with changing conditions: no state machine for a link that comes and goes, no handling of wireless networks that require authentication, and no coordination with DNS and routing when an interface changed.

In 2004 Red Hat started the **NetworkManager** project to make laptop networking work without manual steps; its aim was automatic detection, with a daemon that watches devices, holds connection profiles and reconfigures the stack when conditions change [src: rocky-docs c26486ec56fdea95]. Over time it gained support for Ethernet, Wi-Fi, mobile broadband, VPN, bonds, bridges, VLANs, teaming and later server features, and its command-line client `nmcli` (2010s) made it scriptable. With RHEL 7 (2014) NetworkManager became the supported tool on the Red Hat family, with the old ifcfg files kept as a storage format through a plug-in; with RHEL 9 the **keyfile** format became the default for new profiles, and RHEL 10 follows that direction, moving away from ifcfg (to verify per release) [src: rhel-10-docs 2e920ab4f554ed13].

Meanwhile systemd (2010 onwards) added its own network manager, **systemd-networkd** (2013), a small daemon driven by declarative files, designed for servers, containers and embedded systems where NetworkManager's desktop features are unnecessary. It handles static and DHCP configuration, bridges, bonds, VLANs, tunnels and routing policy and is paired with `systemd-resolved` for DNS (the next topic). Debian-family systems kept ifupdown for years and still offer it in the installer, though Debian's own handbook describes the configuration of the network through files and the commands to apply them [src: debian-handbook 256f619851e41dd6].

**Netplan** (Canonical, 2016) addresses a different problem: provisioning tools and cloud-init needed one declarative format that would work on desktops (NetworkManager) and servers (systemd-networkd). Netplan reads YAML from `/etc/netplan/`, generates native configuration for the selected back end in `/run/`, and hands over; it is not a daemon. The pattern is that configuration has moved from imperative scripts to declarative files that a long-running daemon (or a generator) turns into kernel state, with a clear separation between the persistent description and the runtime effect. The cost is that several competing stacks exist, and mixing them on one interface causes conflicts: two managers fighting for the same device are a classic source of address flapping.

## Current state

### Which stack is in use?

Check what is running and what is managing each interface:

```bash
systemctl is-active NetworkManager systemd-networkd networking    # networking = ifupdown on Debian
nmcli device status          # NetworkManager: DEVICE TYPE STATE CONNECTION
networkctl list              # systemd-networkd: IDX LINK TYPE OPERATIONAL SETUP
ls /etc/netplan/ /etc/network/interfaces /etc/sysconfig/network-scripts 2>/dev/null
```

Typical defaults: RHEL, Rocky, AlmaLinux and Fedora use NetworkManager with keyfiles; Ubuntu Server uses netplan with systemd-networkd, Ubuntu Desktop uses netplan with NetworkManager; Debian uses ifupdown unless the installer or the desktop selected NetworkManager; cloud images use cloud-init to write netplan or NetworkManager configuration; container hosts and minimal images often use systemd-networkd. Exactly one manager should own each interface; the others are told to ignore it (see unmanaged devices below).

### NetworkManager

NetworkManager separates **devices** (the interface hardware or virtual device) from **connections** (profiles: a set of settings that can be applied to a device). A profile has a name, a UUID, a type (`ethernet`, `wifi`, `bond`, `bridge`, `vlan`, `vpn`, `tun`), the interface it is bound to and groups of settings (`ipv4`, `ipv6`, `802-3-ethernet`, `connection`). Interactive tools are `nmtui` (text menus) and `nmcli`; graphical applets use the same D-Bus interface.

```bash
nmcli general status; nmcli general hostname web01
nmcli device status; nmcli device show eth0
nmcli connection show [--active]
nmcli connection add type ethernet ifname eth0 con-name lan \
      ipv4.method manual ipv4.addresses 192.0.2.10/24 ipv4.gateway 192.0.2.1 \
      ipv4.dns 192.0.2.53 ipv4.dns-search example.com ipv6.method disabled
nmcli connection modify lan +ipv4.addresses 192.0.2.11/24
nmcli connection modify lan +ipv4.routes "10.8.0.0/16 192.0.2.254"
nmcli connection modify lan ipv4.method auto          # back to DHCP
nmcli connection modify lan 802-3-ethernet.mtu 9000 connection.autoconnect yes
nmcli connection up lan; nmcli connection down lan
nmcli device reapply eth0        # apply modified settings without a full reactivation
nmcli connection reload          # reread profile files edited by hand
nmcli connection delete lan
nmcli device wifi list; nmcli device wifi connect SSID password 'secret'
nmcli -f NAME,UUID,TYPE,DEVICE connection show     # choose columns; -t terse, -p pretty
```

Property names are dotted `setting.property`; useful ones are `ipv4.method` (`auto`, `manual`, `shared`, `link-local`, `disabled`), `ipv6.method` (`auto`, `dhcp`, `manual`, `link-local`, `ignore`, `disabled`), `ipv4.addresses`, `ipv4.gateway`, `ipv4.dns`, `ipv4.dns-search`, `ipv4.routes`, `ipv4.route-metric`, `ipv4.never-default` (do not use this link as default route), `ipv4.ignore-auto-dns`, `connection.autoconnect`, `connection.autoconnect-priority`, `connection.interface-name`, `connection.zone` (firewalld zone), and the bond, bridge and VLAN settings. The Rocky Linux systems-administration lab walks through creating and editing profiles with `nmcli` step by step [src: rocky-docs 38548343e6411528]. Note that `nmcli connection modify` edits the stored profile; the running state changes only after `connection up` or `device reapply`, a common source of "my change did nothing".

**Profile files.** NetworkManager stores profiles in `/etc/NetworkManager/system-connections/` as `.nmconnection` keyfiles (INI format, mode 0600 and owned by root, otherwise ignored). The keyfile layout has a `[connection]` group (`id`, `uuid`, `type`, `interface-name`, `autoconnect`), `[ipv4]` and `[ipv6]` groups (`method`, `address1=192.0.2.10/24,192.0.2.1`, `dns=`, `routes`) and type-specific groups [src: rhel-10-docs 2e920ab4f554ed13]. Profiles can be created offline, for image builds, with `nmcli --offline connection add ...` printing the keyfile to standard output [src: rhel-10-docs 5058e2a6f5a89e63], and the RHEL image documentation notes that default images carry their network settings in the same way [src: rhel-10-docs 95fd3760aa554a4a]. Older `ifcfg-*` files can be converted with `nmcli connection migrate`.

**Daemon configuration.** `/etc/NetworkManager/NetworkManager.conf` and drop-ins in `/etc/NetworkManager/conf.d/*.conf` set daemon behaviour: `[main]` `plugins=keyfile`, `dns=default|systemd-resolved|none`, `rc-manager`, `no-auto-default=*`; `[keyfile]` `unmanaged-devices=interface-name:docker0;interface-name:veth*`; `[connectivity]` checks; `[logging]` level. To make an interface unmanaged temporarily, the RHEL guide shows `nmcli device set eth1 managed no` [src: rhel-10-docs fa37e0f598a0978f]. **Dispatcher scripts** in `/etc/NetworkManager/dispatcher.d/` run on events (`up`, `down`, `dhcp4-change`, `connectivity-change`) with the interface and action as arguments; the Rocky performance guide uses one to persist a queue-length setting that a plain `ip link set` would lose [src: rocky-docs 3d17413a66f5c662]. Logs go to the journal (`journalctl -u NetworkManager`, `nmcli general logging level DEBUG domains ALL` for a deep trace). Security baselines even include a rule that prevents non-privileged users from modifying network settings with `nmcli` through polkit [src: compliance-as-code 9914de387313f0c1].

### systemd-networkd

systemd-networkd reads three file types from `/usr/lib/systemd/network/` (vendor), `/run/systemd/network/` and `/etc/systemd/network/` (administrator; a file of the same name in `/etc` overrides the others). Files are processed in lexical order, so prefix names with numbers (`10-lan.network`), and for `.network` files the first one whose `[Match]` section matches the interface wins.

```ini
# /etc/systemd/network/10-lan.network
[Match]
Name=eth0

[Network]
Address=192.0.2.10/24
Gateway=192.0.2.1
DNS=192.0.2.53
Domains=example.com

# DHCP instead of static:
# [Network]
# DHCP=yes
```

```ini
# /etc/systemd/network/20-br0.netdev        # create a virtual device
[NetDev]
Name=br0
Kind=bridge
```

`[Match]` keys include `Name=`, `MACAddress=`, `Driver=`, `Type=`, `Property=`. `[Network]` keys include `Address=`, `Gateway=`, `DNS=`, `Domains=`, `DHCP=` (`yes`, `ipv4`, `ipv6`, `no`), `IPv6AcceptRA=`, `Bridge=`, `VLAN=`, `LinkLocalAddressing=`, `ConfigureWithoutCarrier=`; `[Route]`, `[Address]`, `[DHCPv4]` (for example `UseDNS=`, `RouteMetric=`) and `[Link]` (`MTUBytes=`, `RequiredForOnline=`) refine behaviour. `.link` files (processed by udev) control naming, MAC address and driver-level settings at device appearance, including offload switches [src: man-pages 216a6f12ac0f5282]. Operation:

```bash
systemctl enable --now systemd-networkd systemd-resolved
networkctl list; networkctl status eth0       # addresses, gateway, DNS, link speed, driver
networkctl reload                              # reread files, apply to links
networkctl reconfigure eth0                    # reapply one link
networkctl renew eth0                          # renew a DHCP lease
systemctl enable systemd-networkd-wait-online  # delay network-online.target until configured
journalctl -u systemd-networkd -b
```

`networkctl status` also shows the `Setup State` (`configured`, `configuring`, `failed`, `unmanaged`) and the `Operational State` (`routable`, `degraded`, `carrier`, `no-carrier`), which is how you see whether a file matched.

### netplan

Netplan files live in `/etc/netplan/*.yaml` (also `/run/netplan` and `/lib/netplan`), are merged in lexical order and must not be readable by others (0600, or netplan warns). A minimal server file:

```yaml
network:
  version: 2
  renderer: networkd          # or NetworkManager
  ethernets:
    eth0:
      dhcp4: false
      addresses: [192.0.2.10/24]
      routes:
        - to: default
          via: 192.0.2.1
      nameservers:
        addresses: [192.0.2.53]
        search: [example.com]
```

Other keys include `dhcp6`, `accept-ra`, `mtu`, `match: {macaddress: ...}` with `set-name`, `optional: true`, and device types `bonds`, `bridges`, `vlans`, `wifis`, `tunnels`. Commands: `netplan generate` writes backend files, `netplan apply` generates and applies them, `netplan try` applies and reverts after a timeout unless you confirm (the safe way to edit over SSH), `netplan get` and `netplan set` read and edit values, `netplan status` shows the combined state. Generated files appear under `/run/systemd/network/` or `/run/NetworkManager/system-connections/`; do not edit them. cloud-init writes `/etc/netplan/50-cloud-init.yaml` on first boot and may regenerate it, so persistent manual changes need cloud-init's network handling disabled with a file such as `/etc/cloud/cloud.cfg.d/99-disable-network-config.cfg` containing `network: {config: disabled}`. Container platforms care too: Docker's troubleshooting guide describes how netplan can override the network configuration for Docker's own interfaces and how to stop it [src: docker-docs b60f6e14218cb8a6].

### Safe change practice

Over a remote session, keep the old path alive: use `netplan try`, or `nmcli connection up` with a scheduled fallback (`at now + 5 minutes` job that restores the previous profile), or add a second address first and remove the old one afterwards. Back up the file before editing, validate (`netplan generate`, `nmcli connection reload && nmcli connection show lan`), apply, then verify with `ip -br addr`, `ip route`, `resolvectl status` and an actual connection test.

## Assessment: the good, the bad and the ugly

What works well: declarative files make network state reviewable and reproducible; NetworkManager handles changing conditions, Wi-Fi, VPNs and multiple profiles gracefully; systemd-networkd is small, predictable and fast to start; netplan gives cloud tooling a single schema; and both daemons expose their view through a client (`nmcli`, `networkctl`).

What works badly: several stacks coexist, with different property names for the same idea, so documentation is never fully portable. NetworkManager's split between the stored profile and the running state surprises people. systemd-networkd lacks features desktop users expect (Wi-Fi is available only with a helper; no VPN management), and netplan is only a generator, so errors surface as backend errors that name generated files, not the YAML. Boot-order issues with `network-online.target` cause services to start before the network is configured.

The awkward parts: two managers claiming one interface; cloud-init regenerating a file you edited; `nmcli connection modify` followed by no reapply; YAML indentation errors; MTU or offload settings that are accepted by one stack and silently ignored by another; and the migration from ifcfg files and `network-scripts` (removed in newer RHEL releases) that leaves old profiles behind.

## Applications beyond this domain

The pattern of a declarative description turned into running state by a reconciling daemon appears across infrastructure: Kubernetes controllers, configuration-management tools, firewalld and nftables rule sets, and systemd units. Network automation tools model the same layer: the NMState project expresses desired host networking as YAML for NetworkManager and is used by OpenShift to configure cluster nodes; Ansible roles such as `rhel-system-roles.network` and `netplan` modules drive the same files across fleets; cloud-init and Ignition generate them at first boot. Cluster networking plug-ins assume a stable host network below them, and IPAM components that assign node addresses must coordinate with whichever manager owns the interface [src: cilium-docs d10c5c5417d936b3]. The practice of testing a change with an automatic rollback (`netplan try`) generalises to any remote change to a path you depend on.

## Examples

**Static server on RHEL.** `nmcli connection add type ethernet ifname ens3 con-name lan ipv4.method manual ipv4.addresses 192.0.2.10/24 ipv4.gateway 192.0.2.1 ipv4.dns 192.0.2.53 ipv6.method disabled`, then `nmcli connection up lan` and `ip -br addr`. The keyfile `/etc/NetworkManager/system-connections/lan.nmconnection` now holds the profile and survives a reboot.

**A change that did nothing.** After `nmcli connection modify lan ipv4.dns 192.0.2.54`, `resolvectl status` still lists the old server. The profile is edited but not active. `nmcli device reapply ens3` (or `connection up lan`) applies it.

**Ubuntu server with a typo.** A netplan file with a tab instead of spaces makes `netplan apply` print a YAML error and leaves the old configuration active. With `netplan try`, a valid file that breaks connectivity is reverted automatically after 120 seconds, which saves a console visit.

**Two managers, one NIC.** A host runs NetworkManager and systemd-networkd with overlapping configuration; the address flaps every few minutes. `nmcli device status` and `networkctl list` both show eth0 as managed. The fix is to disable one daemon or mark the interface unmanaged in one of them (`unmanaged-devices=interface-name:eth0` for NetworkManager, or no matching `.network` file for networkd).

**Container bridge ignored by NetworkManager.** Docker's `docker0` and veth interfaces appear in `nmcli device status` and NetworkManager tries to set them up. A drop-in with `[keyfile] unmanaged-devices=interface-name:docker0;interface-name:veth*` keeps NetworkManager off them.

**Offline image build.** `nmcli --offline connection add type ethernet con-name lan ifname ens3 ipv4.method auto > lan.nmconnection`, copy into the image under `system-connections/` with mode 0600, and the first boot comes up configured [src: rhel-10-docs 5058e2a6f5a89e63].

## Related problems and ideas

Neighbouring subjects are DNS configuration (systemd-resolved and `resolv.conf`, the next topic), link aggregation and VLANs, wireless authentication, VPN integration, and the firewall zone assignments that NetworkManager can set per connection. Alternatives include `wicked` on SUSE, ifupdown with `ifupdown2` for switch-like features (Cumulus), `connman` on embedded systems, `dhcpcd` and `dhclient` standalone, `iwd` for wireless, and plain scripts for appliances. Proposals still moving include declarative state APIs (NMState, Netplan's own `set` interface) that diff desired against actual state, and Rust rewrites of DHCP clients and network daemons.

## Active research

Active work includes NetworkManager's move to a stronger DHCP implementation (an internal client replacing dhclient), IPv6-only and NAT64-aware settings (CLAT support for 464XLAT), better offline and image-mode support for bootc systems, the NMState and Netplan declarative APIs, systemd-networkd features for routing policy and SR-IOV, and handling of multi-link devices. Open questions include how to unify cloud metadata, image-time and runtime configuration in one model and how to make rollbacks robust when a change breaks the management path itself.

## Future direction

Expect keyfile profiles and declarative YAML to be the only supported formats on current enterprise releases, `network-scripts` and ifcfg to disappear, image-based and offline provisioning to grow, and `nmcli --offline` and NMState to be used in build pipelines. Ubuntu will keep netplan as the common layer while systemd-networkd and NetworkManager evolve behind it. Administrators should learn one stack deeply and recognise the others: find the owner of an interface first, change the persistent description, apply with a rollback path, and verify with the kernel's own view.
