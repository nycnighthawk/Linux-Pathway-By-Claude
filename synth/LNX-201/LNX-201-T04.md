# Turning names into addresses: the resolver, nsswitch, resolv.conf and systemd-resolved

## Define the problem

People and programs use names; networks use addresses. Every outbound connection that starts with a host name begins with a lookup, and that lookup can fail in ways that look like network failures: a service that is up but unreachable by name, a name that resolves to an old address, a short name that works on one host and not on another, a lookup that is fast for most names and takes five seconds for others. Diagnosing these needs a clear picture of the path a lookup takes inside the machine (which libraries, which files, which daemons), the path it takes outside (stub, recursive resolver, authoritative servers) and the places where caches hide changes.

Linux makes this harder than it looks because there are two lookup mechanisms. Applications normally call the C library function `getaddrinfo`, which consults a configurable list of sources (`/etc/hosts`, DNS, mDNS, directory services) in the order set by `/etc/nsswitch.conf`. Troubleshooting tools such as `dig` talk to DNS servers directly and ignore that configuration. A host name can therefore resolve in `ping` and fail in `dig`, or the other way round, and both are correct. On top of that, the DNS configuration itself has several owners: static files, DHCP, NetworkManager, systemd-networkd and `systemd-resolved`, each of which may write or replace `/etc/resolv.conf`.

This slice covers the resolution path on a Linux host, the files that control it, `systemd-resolved` and `resolvectl`, DNS basics needed to read results (record types, TTL, search domains), the query tools `getent`, `dig`, `host` and `nslookup`, and the common failure patterns. Running DNS servers is outside this course.

## History and approaches

The Internet started with a single file. The ARPANET kept a master `HOSTS.TXT` at the Network Information Center that every site downloaded; it contained name-to-address mappings and stopped scaling as the network grew. Paul Mockapetris designed the **Domain Name System** (RFCs 882 and 883 in 1983, replaced by RFCs 1034 and 1035 in 1987): a hierarchical, distributed database with delegation, so that each organisation runs servers for its own zone and resolvers walk the tree from the root. BIND, written at Berkeley, became the reference implementation. The file `/etc/hosts` survived as a local override, and the Unix resolver library (`resolv.conf`, introduced with 4.3BSD) became a stub: a list of recursive servers to send queries to, plus a search list for short names.

Name service switching came with Solaris and was adopted by the GNU C library: `/etc/nsswitch.conf` lets the administrator choose and order sources per database (`hosts`, `passwd`, `group`, `services`), which made it possible to add NIS, LDAP and later SSSD and mDNS without changing programs. The model is simple and slightly dangerous: a missing source in `hosts:` silently removes a feature.

Dynamic networks made static `resolv.conf` a problem. DHCP clients rewrote the file at each lease, VPN software rewrote it again, and the last writer won; split-horizon setups (internal names through the corporate server, everything else through the ISP) could not be expressed at all because the file has no concept of per-interface servers or per-domain routing. Workarounds appeared: `resolvconf` (Debian), `dnsmasq` as a local caching forwarder, the NetworkManager integration with it, and `unbound` as a local validating resolver. In 2014 systemd added **systemd-resolved**, a local daemon that keeps DNS servers per network link, routes queries by domain, caches answers, validates DNSSEC if asked, supports DNS over TLS and implements multicast name resolution (LLMNR and mDNS). Ubuntu enabled it by default in 2016 and Fedora in 2020; the Red Hat family's enterprise releases still keep static or NetworkManager-managed `resolv.conf` by default, so both worlds coexist [src: archwiki 173de1a636f3b33d].

Meanwhile, encrypted and alternative transports (DNS over TLS on port 853, DNS over HTTPS) moved queries off plain UDP, and application-level resolvers (browsers with built-in DoH) can bypass the system's configuration altogether. The common thread: resolution moved from a static list of servers to a policy-driven component that must know about links, domains and security, and operators now debug the component's decisions, not a file.

## Current state

### The path of a lookup

1. The application calls `getaddrinfo` (or `gethostbyname` in old code). The C library reads `/etc/nsswitch.conf`.
2. For the `hosts:` line, it tries each source in order. A typical line is `hosts: files dns myhostname`: `files` reads `/etc/hosts`, `dns` uses the stub resolver configured in `/etc/resolv.conf`, `myhostname` answers for the machine's own name. With systemd-resolved the line often reads `hosts: files resolve [!UNAVAIL=return] dns myhostname`, where `resolve` goes through the daemon's NSS module and the bracket expression stops the chain unless the daemon is unavailable.
3. In the DNS step, the library sends queries to the nameservers listed in `resolv.conf`, appending the search domains to names that have fewer dots than the `ndots` option (default 1), and returns both A and AAAA results.
4. The server answers from cache or performs recursion and returns records with a TTL.

Because step 2 depends on the NSS configuration, `getent hosts name` is the right test of what applications see; `dig name` tests DNS only.

### /etc/hosts, hostname and nsswitch

`/etc/hosts` maps addresses to names, one address per line, with canonical name first then aliases: `192.0.2.10 web01.example.com web01`. Debian-family systems traditionally add `127.0.1.1 hostname`, so the machine can find its own name without DNS. The hostname itself lives in `/etc/hostname` and is managed with `hostnamectl set-hostname web01.example.com`, which also sets the static, transient and pretty names; `hostname -f` prints the fully qualified name and relies on resolution. Changes to `/etc/hosts` take effect immediately, without a restart, for programs that call the C library. `/etc/nsswitch.conf` can be inspected with `getent hosts`, `getent ahosts` (returns all addresses and sort order) and `getent -s dns hosts name` to force one source.

### /etc/resolv.conf

The file the stub resolver reads has a small vocabulary:

```
search example.com corp.example.com
nameserver 192.0.2.53
nameserver 192.0.2.54
options timeout:2 attempts:2 rotate edns0 ndots:2
```

`nameserver` lines (at most three are used) are tried in order; `search` lists domains appended to short names, or `domain` for a single one (the last of `domain` and `search` wins); `options` include `timeout:n` (seconds per attempt, default 5), `attempts:n` (default 2), `rotate` (round-robin among servers), `ndots:n`, `edns0` (advertise larger UDP payloads), `single-request`, `use-vc` (force TCP) and `trust-ad`. Security baselines require at least two name servers on systems that use DNS, because a single server is a single point of failure [src: disa-stig fb12eb3d87271a07] [src: disa-stig 8698c70ed8193abd]. The Rocky Linux administration guide documents the file and its role within the network configuration [src: rocky-docs e15c47a5f7e69caa]. Who writes the file matters more than its contents: NetworkManager rewrites it from profile settings (`ipv4.dns`, `ipv4.dns-search`) unless `rc-manager=unmanaged`; `systemd-networkd` does not touch it (it feeds `systemd-resolved`); `dhclient` hooks may overwrite it. Check `ls -l /etc/resolv.conf`: a symlink to `/run/systemd/resolve/stub-resolv.conf` means systemd-resolved owns it, a symlink to `/run/NetworkManager/resolv.conf` means NetworkManager does, and a plain file is static. Never edit a generated file; change the source.

### systemd-resolved

`systemd-resolved` is a daemon (`systemctl enable --now systemd-resolved`) that listens on 127.0.0.53 (the **stub listener**, port 53 on the loopback) and offers lookups over D-Bus and the NSS module. It keeps DNS servers and search domains per link, receiving them from systemd-networkd, NetworkManager or `resolvectl`, and picks the servers for a query by matching the query name against the link domains. Four `resolv.conf` modes exist: **stub** (symlink `/etc/resolv.conf` to `/run/systemd/resolve/stub-resolv.conf`, which lists only 127.0.0.53, the recommended mode); **static** (`/usr/lib/systemd/resolv.conf`, same stub but no link domains); **uplink** (`/run/systemd/resolve/resolv.conf`, the real upstream servers, bypassing the stub, for programs that parse the file themselves); and **foreign** (a file managed by someone else). To adopt the stub: `ln -sf ../run/systemd/resolve/stub-resolv.conf /etc/resolv.conf`.

The command-line client is `resolvectl` (older name `systemd-resolve`):

```bash
resolvectl status                    # global settings, then per-link servers, domains, DNSSEC, protocols
resolvectl status eth0
resolvectl query example.com         # resolves and says which link, protocol and whether from cache
resolvectl query -t MX example.com; resolvectl query 192.0.2.10   # record type; reverse lookup
resolvectl dns eth0 192.0.2.53 192.0.2.54      # runtime per-link servers
resolvectl domain eth0 example.com '~corp.example.com'   # search domain and routing domain
resolvectl default-route eth0 yes
resolvectl llmnr eth0 no; resolvectl mdns eth0 yes
resolvectl dnsovertls eth0 opportunistic; resolvectl dnssec eth0 allow-downgrade
resolvectl statistics                # cache hits, transactions, DNSSEC verdicts
resolvectl flush-caches; resolvectl reset-server-features
resolvectl monitor                   # live view of queries and answers
```

A domain starting with `~` is a **routing domain**: queries for names under it go to that link's servers but the domain is not appended as a search suffix. `~.` makes a link the default route for all names. This is how split DNS works: a VPN link gets `~corp.example.com` and its internal servers, while everything else uses the uplink. Daemon-wide settings go in `/etc/systemd/resolved.conf` or drop-ins in `/etc/systemd/resolved.conf.d/*.conf`, section `[Resolve]`: `DNS=`, `FallbackDNS=`, `Domains=`, `LLMNR=`, `MulticastDNS=`, `DNSSEC=` (`yes`, `allow-downgrade`, `no`), `DNSOverTLS=` (`yes`, `opportunistic`, `no`), `Cache=`, `CacheFromLocalhost=`, `DNSStubListener=` (`yes`, `no`, `udp`, `tcp`), `ReadEtcHosts=`. Per-link values arrive from NetworkManager (`ipv4.dns`, with `dns=systemd-resolved` in `NetworkManager.conf`) or networkd (`DNS=` and `Domains=` in `.network` files, previous topic). The Arch Linux wiki describes the interplay with glibc, notably that software using `getaddrinfo` needs the NSS `resolve` module or the stub file, and the mDNS and DNS configuration options [src: archwiki 173de1a636f3b33d] [src: archwiki 843ab244c5f7701f]. Port 53 conflicts are common: running `dnsmasq`, `unbound`, a container runtime's DNS or a pi-hole on the same host requires `DNSStubListener=no` or binding to other addresses.

### DNS basics for reading results

A resolver query asks for a name and record type. Common types: `A` (IPv4 address), `AAAA` (IPv6), `CNAME` (alias; a name with a CNAME has no other data), `MX` (mail exchangers with preference), `NS` (zone's name servers), `SOA` (zone parameters and serial number), `TXT` (arbitrary text: SPF, DKIM, verification tokens), `PTR` (reverse lookup under `in-addr.arpa` and `ip6.arpa`), `SRV` (service location with priority, weight, port) and `CAA`. Every record has a **TTL** in seconds that caps how long caches (the resolved daemon, the recursive server, browsers, `nscd` or `sssd`) may keep it, which explains why a changed address appears at different times for different clients. Queries use UDP port 53 with EDNS0 (payloads up to about 1232 bytes by current recommendation) and fall back to TCP port 53 when the answer is truncated (the TC bit); firewalls that block TCP 53 produce intermittent failures for large answers. Encrypted transports use TCP 853 (DoT) or HTTPS (DoH). DNSSEC adds signatures (`RRSIG`, `DNSKEY`, `DS`) and the `AD` flag in answers that a validating resolver authenticated.

### Query tools

```bash
getent hosts web01                   # what applications get (nsswitch order, search list)
getent ahostsv6 example.com
dig example.com                      # full response with sections, flags, query time, server
dig +short example.com AAAA
dig @192.0.2.53 example.com MX       # ask a specific server (bypasses resolv.conf)
dig +trace example.com               # walk delegation from the root
dig -x 192.0.2.10                    # reverse lookup
dig +norecurse @192.0.2.53 example.com   # test the server's cache or authority only
dig +tcp +dnssec example.com
host -t txt example.com; nslookup example.com 192.0.2.53
resolvectl query example.com         # systemd-resolved's view, including cache
```

In `dig` output, the header flags matter: `qr` (response), `aa` (authoritative answer), `rd` and `ra` (recursion desired and available), `ad` (authenticated data) and `tc` (truncated); the status is `NOERROR`, `NXDOMAIN` (name does not exist), `SERVFAIL` (server could not answer, often DNSSEC or upstream failure) or `REFUSED`. `NOERROR` with an empty answer section means the name exists but has no record of that type, such as no AAAA.

## Assessment: the good, the bad and the ugly

What works well: the hierarchical design scales to the whole Internet; caching makes lookups cheap; nsswitch allows additional sources without touching applications; and systemd-resolved brings per-link servers, split DNS, DNSSEC and a local cache to a stub file that could not express any of them, with a single tool (`resolvectl`) that shows what it decided and why.

What works badly: there are many owners for the configuration, and the last writer wins unless the owner is chosen deliberately. Tools disagree: `dig` ignores nsswitch, `ping` ignores a server you pass to `dig`. Search domains plus `ndots` multiply queries, so a Kubernetes pod with `ndots:5` sends several lookups for each external name, a known performance cost. TTL-based caching leads to confusion during migrations, and negative caching (NXDOMAIN cached for the SOA minimum) outlasts a fix. Stub resolvers cannot fail over quickly: with a dead first server every lookup waits for the timeout.

The awkward parts: mixing a local stub (127.0.0.53) with containers, which inherit that address and cannot reach it from their own network namespace (runtimes therefore copy the uplink file instead); port 53 conflicts with other local resolvers; VPN clients that overwrite `resolv.conf`; applications with their own resolver (Go's pure resolver in some builds, Java caches, browsers with DoH) that ignore system policy; and `.local` names that collide between mDNS and DNS.

## Applications beyond this domain

DNS-based service discovery runs under cluster platforms (CoreDNS in Kubernetes, Consul, service meshes), under email (MX, SPF, DKIM, DMARC) and under certificate issuance (ACME DNS-01 challenges, CAA). The resolver ideas of per-scope routing and caching recur in HTTP proxy configuration (PAC files), in `nss` databases for users and groups served by SSSD, and in split-horizon cloud setups where private zones resolve only inside a VPC. DNS is also a security control surface: response policy zones, DNS filtering, sinkholes and threat detection watch queries, while exfiltration over TXT records is a known abuse that detection tools look for. Name resolution knowledge carries directly into certificate, mail and cluster troubleshooting.

## Examples

**Which answer does the application see?** `ping web01` works, `dig web01` returns NXDOMAIN. `getent hosts web01` returns 192.0.2.10 because `files` in nsswitch found it in `/etc/hosts`; DNS has no such record. Neither tool is wrong; the question is where the name should be defined.

**Slow first lookup.** Every connection to an internal host takes five seconds longer than expected. `resolvectl statistics` or `tcpdump -ni any port 53` shows the first query going to a dead server in `resolv.conf`. Removing it, or setting `options timeout:1 rotate`, fixes the delay.

**Split DNS for a VPN.** After connecting a VPN, internal names fail and external names work. `resolvectl status` shows the VPN link without DNS servers or a routing domain. `resolvectl dns tun0 10.0.0.53` and `resolvectl domain tun0 '~corp.example.com'` make queries for the internal domain use the VPN's server; the permanent form is in the VPN profile (NetworkManager `ipv4.dns` and `ipv4.dns-search` with a `~` prefix).

**A stale record.** A record's TTL was 86400 seconds; after changing the address, some clients still reach the old host for a day. `dig +norecurse @ns1.example.com name` shows the authoritative answer is correct, while `dig @resolver name` shows the old value with a decreasing TTL. The remedy is waiting, flushing the caches the operator controls (`resolvectl flush-caches`) and lowering TTLs before the next migration.

**Port 53 already in use.** A container DNS forwarder fails to start with an address-in-use error. `ss -ulpn 'sport = :53'` shows `systemd-resolved` bound to 127.0.0.53. Binding the forwarder to another address, or setting `DNSStubListener=no` in a drop-in and restarting the daemon, resolves the conflict.

**A broken symlink.** After a manual edit, `/etc/resolv.conf` is a regular file with a single stale server, ignoring the daemon. `ls -l` shows no symlink. Restoring the stub symlink returns control to systemd-resolved.

## Related problems and ideas

Neighbouring problems are local caching resolvers (`unbound`, `dnsmasq`, `bind` as a forwarder), DNSSEC deployment, DNS load balancing and geo-DNS, `mDNS` and `.local` service discovery with Avahi, directory-based name services with SSSD and LDAP, and time synchronisation, which breaks DNSSEC when the clock is wrong. Alternatives include running a validating resolver on every host, relying on DoH in the application layer (browsers), service meshes that do their own discovery, and static host files managed by configuration tools for small fixed fleets. Ideas not yet mainstream include Oblivious DoH and DNS over QUIC to improve privacy, SVCB and HTTPS records that carry service parameters, and encrypted client hello, which depends on DNS publishing keys.

## Active research

Active work covers DNS privacy and encrypted transports (DoQ, ODoH), measurement of resolver behaviour and failure modes, DNSSEC algorithm migration and key rollover automation, protection against cache poisoning and amplification attacks, SVCB and HTTPS record adoption, and systemd-resolved improvements such as better DoT handling and a richer cache. Open questions include how enterprise policy (filtering, split horizon, logging) coexists with encrypted DNS in applications, and how resolvers should expose their decisions to administrators.

## Future direction

Expect more distributions to adopt systemd-resolved as the default component, applications to use encrypted DNS more often, and DNS to carry more service metadata. The Red Hat family's enterprise releases continue to differ from Ubuntu's defaults, so administrators need both mental models. The durable practices are to learn which component owns `resolv.conf`, test with both `getent` and `dig`, keep at least two servers, use routing domains for split DNS instead of editing files, and lower TTLs ahead of planned changes.
