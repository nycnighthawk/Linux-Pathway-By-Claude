# Filtering packets on Linux: nftables rulesets and the firewalld zone model

## Define the problem

Every networked Linux host needs a policy that says which packets may enter, leave or cross it. On a server the policy is usually short (allow SSH from the management network, allow HTTPS from everywhere, drop the rest), but it must survive reboots, must not lock the administrator out while it is being changed, and must stay consistent when other software (containers, virtual machine managers, VPN daemons) also wants to add rules. The kernel provides the mechanism, a set of hooks in the packet path where rules can accept, drop, rewrite or count traffic. Administrators need a tool above that mechanism, and the difficulty is that Linux ships two layers of tooling with different goals.

The lower layer is nftables: a kernel framework plus the `nft` command that edits tables, chains, rules, sets and maps. It is precise and general, and it expects you to know the packet path. The upper layer is firewalld: a daemon that models a host's policy in terms of zones (trust levels attached to interfaces or source addresses), services (named bundles of ports) and policies (rules between zones), and that generates nftables rules from that model. A rule written with `nft` and a rule written with `firewall-cmd` can coexist in one kernel, and that coexistence is a main source of confusion. This slice teaches how each layer works, how to read the active ruleset, how to make changes permanent without losing access, and how to choose between them [src: rhel-10-docs 2ce527f473600c53].

## History and approaches

Linux packet filtering began with ipfw ports and then `ipchains` in the late 1990s. Netfilter and `iptables` arrived with kernel 2.4 and gave the long-lived model of tables (filter, nat, mangle, raw) holding chains of rules, with separate tools per protocol family: `iptables`, `ip6tables`, `arptables` and `ebtables`. That duplication was a pain point: every rule had to be written once per family, rules were matched linearly, and each change by `iptables` reloaded or rewrote large parts of the table. Tools such as `ipset` bolted on set-based matching afterwards.

nftables was merged into the kernel in the 3.13 series (January 2014) as a replacement with a single userspace tool, a small in-kernel virtual machine that executes rule bytecode, native sets and maps, and one `inet` family that handles IPv4 and IPv6 together. Most mainstream distributions then moved their defaults to it over several years; Red Hat's documentation treats nftables as the packet-filtering framework of the current releases and tells administrators who still hold iptables rules to translate them [src: rhel-10-docs d5b240ebff205060]. Compatibility tools exist for the transition: `iptables-nft` presents the legacy command syntax while storing rules in nftables, and `iptables-translate` and `iptables-restore-translate` convert existing rule sets into `nft` syntax [src: man-pages 51737087757c0963].

firewalld has a separate lineage. It came from Red Hat's Fedora in the early 2010s to solve a different problem: changing iptables rules by hand needed a full reload, which dropped established connections and left no clean place for network-aware software (such as NetworkManager) to say "this interface is a public network". firewalld introduced zones, a D-Bus interface and a split between the running configuration and the stored one. It first generated iptables rules and moved to an nftables backend in later releases; the current backend uses nftables, and RHEL-family hardening guides check for that setting explicitly [src: compliance-as-code 7c8755116838d26c]. The Arch wiki describes the same arrangement from a different distribution's point of view, which is useful evidence that the zone model is not RHEL-specific [src: archwiki 29b9b238aaf190c7].

Other approaches exist beside these two. Ufw (Ubuntu's front-end), `shorewall`, `iptables-persistent`, and Docker's own rule management are front-ends over the same kernel hooks; eBPF and XDP programs run earlier than netfilter and are used where throughput matters. The Arch wiki lists the front-ends that target nftables [src: archwiki f4fdcc253cbb8714], and Red Hat's chapter title for the area groups firewalld, nftables and XDP packet filtering in one place [src: rhel-10-docs 68a987f6d28f17b1].

## Current state

### The packet path and the nftables object model

Netfilter places hooks in the packet path. In nftables terms, a base chain attaches to one hook; the usual hooks are `prerouting` (before the routing decision), `input` (packets for this host), `forward` (packets routed through it), `output` (locally generated packets) and `postrouting` (after routing). The `netdev` family adds an `ingress` hook on a single device. Each base chain has a type (`filter`, `route` or `nat`), a hook, an integer priority that orders chains attached to the same hook, and optionally a default policy (`accept` or `drop`, default accept). A rule in a regular chain only runs when another rule jumps to it.

The object model is: a **table** belongs to one address family (`ip`, `ip6`, `inet`, `arp`, `bridge` or `netdev`) and contains **chains**, **sets**, **maps**, **flowtables** and **stateful objects** such as counters and quotas. A rule is a list of matches followed by a statement. Tables are user-named, so two programs can each own a table without touching the other's rules; this is the main structural gain over iptables, where the built-in tables were shared and global.

A first ruleset for a server shows the pieces. In one file:

```
table inet fw {
    chain in {
        type filter hook input priority 0; policy drop;
        iif lo accept
        ct state invalid drop
        ct state related,established accept
        ip protocol icmp accept
        ip6 nexthdr ipv6-icmp accept
        tcp dport 22 accept
    }
    chain fwd { type filter hook forward priority 0; policy drop; }
    chain out { type filter hook output priority 0; policy accept; }
}
```

The `inet` family makes the same rules apply to both IP versions. Connection tracking (`ct state`) is what makes the policy cheap: only the first packet of a connection is evaluated against service rules, and replies are accepted because they belong to a tracked flow. The ICMP lines matter more than beginners expect: IPv6 neighbour discovery and path MTU discovery are carried in ICMPv6, and a `drop` policy without them breaks IPv6 entirely.

### Working with `nft`

The commands used daily are:

- `nft list ruleset` prints every table in the format the parser accepts; `nft list table inet fw` and `nft list chain inet fw in` narrow it. Add `-a` to show each rule's numeric handle.
- `nft add table`, `nft add chain` (the braces carry the base-chain properties, and they need quoting in a shell), `nft add rule`, `nft insert rule` (put first or before a handle), `nft delete rule inet fw in handle 7`, `nft flush chain`, `nft delete table` change the live ruleset one object at a time.
- `nft -f file` loads a file. The load is **atomic**: either every command in the file takes effect or none does. `nft -c -f file` checks syntax and semantics without applying. A file that starts with `flush ruleset` and then re-declares everything is the cleanest way to replace a policy in one step.
- `nft monitor` streams ruleset changes and, with `trace`, shows the path of marked packets through the chains, which is the nftables replacement for sprinkling `LOG` rules.
- Sets and maps replace ipset: `nft add set inet fw admins '{ type ipv4_addr; flags interval; }'`, then `ip saddr @admins tcp dport 22 accept`. Verdict maps (`tcp dport vmap { 22 : accept, 80 : accept }`) turn a series of rules into one hashed lookup.
- NAT lives in chains of type `nat`: `masquerade` on a `postrouting` chain, `dnat to` on `prerouting`, `snat to` for fixed outbound addresses. The RHEL material on firewalld NAT shows the same ideas through zone settings [src: rhel-10-docs b07ccdbbdf63cc25].

Persistence is a distribution matter. Red Hat family systems ship `nftables.service`, which loads the file named in its unit (conventionally `/etc/sysconfig/nftables.conf`, which includes files under `/etc/nftables/`); Debian and Ubuntu ship `/etc/nftables.conf` and the same unit name. The ruleset in the kernel is a runtime object: if you edit it with `nft add rule` and never write it to a file, a reboot returns the old policy.

### firewalld: zones, services, policies

firewalld's model has a few nouns:

- A **zone** is a trust level with its own rules: the packaged ones include `drop`, `block`, `public`, `external`, `dmz`, `work`, `home`, `internal` and `trusted`. Each zone has a target (what happens to traffic that matches nothing: `default`, `ACCEPT`, `DROP` or `%%REJECT%%`), a list of allowed services, ports, protocols, source ports, ICMP blocks, rich rules and forwarding settings.
- An **interface** or a **source address range** is bound to exactly one zone. The zone for a packet is picked by source address first and by ingress interface second, and a default zone catches the rest. Newer releases add zone priorities for ambiguous cases [src: rhel-10-docs 161a3b04fccbfed6].
- A **service** is a named list of ports and helper modules in an XML file (`/usr/lib/firewalld/services/` for packaged ones, `/etc/firewalld/services/` for yours).
- A **policy** (introduced in the 0.9 series) governs traffic between zones or between a zone and the host, and it replaced most uses of direct rules for gateways; `firewall-cmd --new-policy` creates one. Packaged examples include the policy that lets the local host reach out and the policy that lets internal zones masquerade toward an external one.
- **Direct rules** are raw rules passed through; Red Hat documents them but treats them as a last resort [src: rhel-10-docs 8883f316611e8507].

Two configurations exist at the same time: **runtime** (what the daemon is enforcing now) and **permanent** (what is stored under `/etc/firewalld/`). A command without `--permanent` changes only the runtime; a command with it changes only the stored files and takes effect on the next `--reload`. Two shortcuts reduce mistakes: `firewall-cmd --runtime-to-permanent` writes the running configuration to disk, and `--timeout=<seconds>` on a runtime change reverts it automatically, which is the standard way to test a risky rule over a remote session [src: rhel-10-docs 627f8b9009568383].

The commands that cover most tasks:

```
firewall-cmd --state
firewall-cmd --get-active-zones
firewall-cmd --get-default-zone
firewall-cmd --list-all --zone=public
firewall-cmd --zone=public --add-service=https
firewall-cmd --zone=public --add-port=8443/tcp
firewall-cmd --zone=public --remove-service=cockpit
firewall-cmd --permanent --zone=internal --add-source=10.20.0.0/16
firewall-cmd --permanent --zone=external --add-masquerade
firewall-cmd --set-default-zone=public
firewall-cmd --reload
firewall-cmd --runtime-to-permanent
firewall-cmd --check-config
```

`firewall-cmd --panic-on` drops everything including established flows (use only on console), `--lockdown-on` restricts which programs may change the policy through D-Bus, and rich rules (`--add-rich-rule='rule family="ipv4" source address="192.0.2.0/24" port port="22" protocol="tcp" accept'`) give a readable single-rule syntax when the zone model is too coarse. `firewall-cmd --get-services` lists the packaged services, and `firewall-offline-cmd` edits the stored configuration when the daemon is not running.

### How the two layers interact

On a firewalld host the daemon owns tables it names itself (an `inet firewalld` table in the current implementation; check `nft list ruleset` on your system rather than trusting this text, as the table and chain layout is an implementation detail that has changed between releases). Your own `nft` rules go into a table with a different name, in a chain attached to the same hook with a chosen priority. Netfilter evaluates **every** base chain attached to a hook, and a packet must be accepted by all of them: an `accept` in one chain does not stop evaluation of the next chain. So a permissive custom table can never override a firewalld drop, while a custom `drop` is final no matter what firewalld says. That asymmetry explains most "I allowed the port, still blocked" reports on mixed systems.

The rule of thumb in Red Hat's guidance is to use one of the two as the policy owner on a given host, and to choose firewalld when zone-style policy fits and nftables directly when you need exact, scripted control [src: rhel-10-docs 2ce527f473600c53]. Docker and libvirt both insert their own rules; Docker's documentation covers how it integrates with firewalld and how published ports bypass host-level filtering unless handled [src: docker-docs 1852fc503db0c6bd], and its nftables material covers forwarding requirements [src: docker-docs 9ab5fcc5c2d31ec7]. The libvirt documentation describes the same pattern for the virtual network driver [src: libvirt-docs d01869b5a66db1a5].

### Compliance and hardening checks

Security baselines treat the firewall as a checked control: they ask that the firewall service is enabled, that the nftables backend is selected in `/etc/firewalld/firewalld.conf` (`FirewallBackend=nftables`), that a default zone exists, and that a table exists when nftables is used directly [src: compliance-as-code c4018cbd39a349c5]. Some baselines also require rate limiting against connection floods, which in nftables is a `limit rate` or `meter` expression, and in firewalld a rich rule with a limit [src: disa-stig 14735a6f5f63f8f4].

## Assessment: the good, the bad and the ugly

**The good.** nftables is one tool for all families, with atomic loading, native sets and maps, and a readable ruleset format that round-trips: what `nft list ruleset` prints can be fed back to `nft -f`. User-named tables isolate programs. firewalld gives a vocabulary that matches how people describe policy (untrusted interface, internal subnet), integrates with NetworkManager and Cockpit, supports runtime changes without dropping tracked flows, and gives a timeout-revert guard. The two layers together cover both teams that need a model and teams that need bytecode-level control.

**The bad.** The documentation is split. A tutorial written for `iptables` still dominates search results, and its commands may act on the compatibility layer rather than the real ruleset. The runtime-versus-permanent split in firewalld causes a steady stream of "it worked until reboot" and reports of changes lost after a reload incidents. Rules in nftables chains with the same hook interact by the all-chains-must-accept principle, which surprises people who expect first-match behaviour across tools. The `--permanent` flag position and the zone default (an omitted `--zone` means the default zone, not the zone of your interface) are quiet traps.

**The ugly.** Mixed ownership. A host running firewalld, Docker, a VPN client and a hand-written `nftables.service` file has four writers to the same hook, with different priorities and different restart behaviours. A `flush ruleset` in a hand-written file deletes the other writers' tables; a firewalld reload recreates its own tables but cannot repair what Docker injected. The IPv6 half is often forgotten: an `ip` table without a matching `ip6` table (or `inet`) leaves IPv6 open. Finally, remote lockout: any change over SSH that drops port 22 or the established-connection rule ends the session, and the only recovery is console access or a scheduled revert.

## Applications beyond this domain

Packet filtering ideas recur wherever traffic crosses a trust boundary. Kubernetes network policies and CNI plugins implement the same allow/deny logic in iptables, nftables or eBPF; Cilium describes an eBPF datapath that bypasses netfilter altogether for some paths [src: cilium-docs a93ac0cb264bf330]. Container hosts need forwarding and masquerade rules for bridge networks, covered in the Docker material above. Cloud security groups are zone-and-service policy rewritten as an API. Embedded routers, home gateways and appliances run nftables rulesets generated from web forms; OpenWrt's firewall is a front-end with the same zone idea as firewalld. Rate limiting, port knocking, transparent proxies (via `tproxy`), load-balancing with `dnat` plus maps, and connection tracking helpers are all ruleset techniques outside the plain "open a port" use.

## Examples

**1. Open HTTPS on a RHEL-family server, permanently, safely.**

```
firewall-cmd --zone=public --add-service=https --timeout=300
curl -sk https://localhost/ >/dev/null && firewall-cmd --runtime-to-permanent
firewall-cmd --list-services --zone=public
```

The first command is a five-minute experiment; the second commits it only if a test passes.

**2. Restrict SSH to a management network with a zone.**

```
firewall-cmd --permanent --new-zone=mgmt
firewall-cmd --permanent --zone=mgmt --add-source=192.0.2.0/24
firewall-cmd --permanent --zone=mgmt --add-service=ssh
firewall-cmd --permanent --zone=public --remove-service=ssh
firewall-cmd --reload
```

Packets from `192.0.2.0/24` match the `mgmt` zone by source; everyone else meets `public`, which no longer allows SSH. Verify with `firewall-cmd --get-active-zones` before closing your session.

**3. A hand-written nftables policy, tested then applied.**

Save the earlier ruleset (with `flush ruleset` as its first line) to `/etc/nftables.conf`, then run `nft -c -f /etc/nftables.conf` and, if it prints nothing, `nft -f /etc/nftables.conf`, followed by `systemctl enable --now nftables`.

**4. Rate-limit new SSH connections.**

```
nft add rule inet fw in tcp dport 22 ct state new limit rate over 10/minute drop
```

The rule goes before the accept rule in the same chain, so insert it with `nft insert rule` (or the handle-based `position` form) rather than appending.

**5. NAT gateway for an internal network.**

```
table ip nat {
    chain postrouting {
        type nat hook postrouting priority srcnat; policy accept;
        oifname "eth0" masquerade
    }
}
```

Combined with `sysctl net.ipv4.ip_forward=1` and a forward chain that accepts traffic from the internal interface, this gives a minimal router. In firewalld the equivalent is `firewall-cmd --permanent --zone=external --add-masquerade`.

**6. Debug a drop with tracing.**

```
nft add rule inet fw pre meta nftrace set 1
nft monitor trace
```

The first command assumes a `prerouting` chain of type `filter` exists; the second prints the chain traversal for flagged packets. Remove the rule when done, since tracing every packet has a cost.

## Related problems and ideas

- **Connection tracking.** `conntrack -L` and `/proc/net/nf_conntrack` show the state table that stateful rules read; the table has a size limit, and exhaustion looks like random drops.
- **Routing interaction.** `rp_filter` and policy routing decide whether a packet is dropped before the firewall sees it. See the routing slice.
- **SSH and service exposure.** The next slice (OpenSSH) is the most common thing a firewall rule protects, and a ProxyJump host is often the only machine with an open port.
- **SELinux and port labels.** Opening a port in the firewall does not let a confined service bind a non-standard port; `semanage port` is a separate control.
- **Network namespaces.** Each namespace has its own netfilter ruleset, which is why container tooling and labs can test `nft` rules without affecting the host.
- **XDP and eBPF.** Early-drop programs for DDoS mitigation sit below netfilter and are managed separately.

## Active research

Work is ongoing on making rule updates scale: incremental set updates, faster pipapo-style set lookups for ranges and concatenations, and flowtables that offload established flows to a fast path (software or hardware). Container networking projects are shifting from iptables to nftables backends and eBPF datapaths; the Docker documentation tracks that migration for its engine [src: docker-docs 9ab5fcc5c2d31ec7]. firewalld's own roadmap items include more policy-based configuration, better handling of multiple writers, and cleaner D-Bus APIs. Formal verification of rulesets and static analysis of "what can reach what" are active areas in the network-verification community, with tools that parse `nft` output.

## Future direction

The probable direction is more declarative, API-driven filtering with fewer hand-edited rule files: firewalld or Kubernetes policy as the interface, nftables or eBPF as the engine. For administrators the practical advice is stable: pick one policy owner per host; always keep a tested rollback (a `--timeout` or an `at` job that restores the old ruleset); keep IPv4 and IPv6 consistent; store the policy in version control; and verify the live ruleset with `nft list ruleset` after every change, because the live ruleset, not the config file, is the policy.
