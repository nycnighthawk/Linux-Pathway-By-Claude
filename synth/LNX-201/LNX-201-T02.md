# Inspecting and changing network state: ip, ss and ethtool

## Define the problem

When a connection fails, an administrator needs three kinds of facts quickly. What does this host believe about its own interfaces, addresses, routes and neighbours? Which sockets are open, who owns them and in what state? And what is the physical or driver-level condition of the link: speed, duplex, offloads, error counters? Without a dependable toolset, these answers come from guesswork or from programs that read stale or incomplete data. The Linux answer is a set of tools that talk to the kernel through the netlink interface and, for driver settings, through the ethtool ioctl and netlink API: `ip` for configuration and the kernel's network objects, `ss` for sockets and `ethtool` for the link.

The problem has two halves. The first is **reading**: producing an accurate picture, in a format that is readable at a glance or parseable by scripts. The second is **changing**: altering addresses, routes, link flags and driver settings at run time, knowing that such changes last only until reboot unless a persistent configuration (NetworkManager, systemd-networkd, netplan or ifupdown) records them. This slice covers the syntax, output and typical uses of the three tools, the retired tools they replaced (`ifconfig`, `route`, `arp`, `netstat`) so that old scripts can be understood, and how to make driver-level settings persistent.

## History and approaches

The original BSD-derived tools, collectively `net-tools`, appeared in Linux in the early 1990s: `ifconfig` to configure interfaces, `route` for the routing table, `arp` for the neighbour cache, `netstat` for sockets and statistics, `iwconfig` for wireless. They read `/proc` files and used ioctl calls. They served for two decades but had structural limits. `ifconfig` could show only one address per interface in its main line and used "alias" interfaces such as `eth0:1` for more, which hid the real model of several addresses per interface. It knew nothing about policy routing, multiple routing tables, network namespaces, VRFs or newer link types. `netstat` read large `/proc/net` tables slowly. The kernel gained a richer interface, **netlink**, a socket family in which user space and kernel exchange structured messages, and Alexey Kuznetsov wrote `iproute2` around it in the late 1990s: the `ip` command manages objects (links, addresses, routes, neighbours, rules, tunnels, namespaces), and `tc` manages traffic control. `ss` (socket statistics), part of the same package, reads sockets through the netlink `sock_diag` interface, which is faster and exposes more TCP internals than `/proc`.

`ethtool` has a separate lineage: Jeff Garzik's tool for querying and setting Ethernet driver parameters, using an ioctl interface that grew command by command. A netlink-based interface (ethtool netlink, Linux 5.6 onwards) now supports notifications and richer messages, and the tool uses it where available. Distributions deprecated `net-tools` over time. Red Hat dropped it from default installs with RHEL 7, Debian made it optional, and the package is no longer in the default set on modern systems, but muscle memory and old tutorials keep it alive. The lesson that emerged is the one familiar from other Linux subsystems: a flat text-oriented tool was replaced by an object-oriented tool on a structured kernel interface, and the new tool's output must be learned once, after which scripts can request JSON (`ip -j`) instead of scraping text.

Naming of interfaces had its own history. Early kernels numbered devices in probe order (`eth0`, `eth1`), which could change between boots. The udev "persistent net" rules of the 2000s tried to pin names to MAC addresses and caused problems with cloned virtual machines. In 2013 systemd and udev introduced **predictable network interface names** based on firmware or topology information (`eno1` for onboard, `ens3` for a PCI hotplug slot, `enp3s0` for PCI bus and slot, `wlp2s0` for wireless), with the kernel parameter `net.ifnames=0` restoring the old scheme; many cloud images use the latter.

## Current state

### ip

The general form is `ip [OPTIONS] OBJECT COMMAND`. Global options: `-4` and `-6` restrict the family, `-br` (brief) prints one line per object, `-c` colours, `-s` adds statistics (twice for details), `-d` details, `-j` and `-p` produce JSON and pretty JSON, `-o` one record per line, `-n NAME` runs inside a network namespace. Abbreviations work (`ip a`, `ip r`, `ip l`), but scripts should use full words.

```bash
ip -br link                      # one line per link: name, state, MAC, flags
ip -br addr                      # addresses per interface
ip addr show dev eth0            # full detail for one interface
ip -s link show eth0             # RX/TX packets, bytes, errors, dropped, overrun, carrier
ip link set eth0 up              # (down); also mtu 9000, promisc on, name newname, address MAC
ip addr add 192.0.2.10/24 dev eth0              # add an address (as many as needed)
ip addr add 2001:db8::10/64 dev eth0 valid_lft 3600 preferred_lft 1800
ip addr del 192.0.2.10/24 dev eth0
ip addr flush dev eth0           # remove all addresses (careful over SSH)
ip route                         # routing table
ip route get 8.8.8.8             # which route, source address and interface would be used
ip route add default via 192.0.2.1 dev eth0
ip route add 10.8.0.0/16 via 192.0.2.254 metric 100
ip neigh show                    # ARP and neighbour discovery cache with states
ip neigh flush dev eth0
ip maddr show                    # multicast memberships
ip rule; ip route show table all # policy routing (routing topic)
ip netns add lab; ip netns exec lab ip addr   # namespaces
ip link add br0 type bridge; ip link add link eth0 name eth0.100 type vlan id 100
ip link add veth0 type veth peer name veth1; ip link add dummy0 type dummy
ip monitor                       # live stream of link, address, route and neighbour changes
```

Reading the output. A link line shows `<BROADCAST,MULTICAST,UP,LOWER_UP>`: `UP` means the administrator enabled the interface, `LOWER_UP` means the carrier is present (a cable and a peer), and `NO-CARRIER` with `UP` indicates an enabled port with no link. `state UP`, `DOWN` or `UNKNOWN` (common for virtual devices) comes from the operational state. Address lines carry `scope global`, `scope link` or `scope host`, plus flags: `dynamic` (from DHCP or SLAAC, with a lifetime), `noprefixroute`, `tentative` (IPv6 duplicate address detection in progress), `deprecated` and `permanent`. The `-s` counters are cumulative; look for increasing `errors`, `dropped` and `overrun` as signs of faulty cables, congestion or ring-buffer exhaustion. Neighbour entries show `REACHABLE`, `STALE`, `DELAY`, `PROBE`, `FAILED` or `INCOMPLETE`; a gateway stuck in `FAILED` or `INCOMPLETE` means ARP or neighbour discovery gets no answer.

Changes made with `ip` are runtime only. They vanish at reboot or when a network manager reapplies its profile, which is a feature when experimenting and a trap when forgetting to persist.

### ss

`ss` lists sockets, by default only established non-listening connections. Core options: `-t` TCP, `-u` UDP, `-x` UNIX, `-l` listening, `-a` all, `-n` numeric (no name lookups), `-p` owning process (needs privilege for other users' sockets), `-4` and `-6`, `-s` summary counts, `-o` timers, `-e` extended (uid, inode), `-i` internal TCP information (round-trip time, congestion window, retransmissions), `-m` socket memory, `-H` no header, `-O` one line each.

```bash
ss -tulpn                        # listening TCP and UDP sockets with owning processes
ss -tn state established '( dport = :443 or sport = :443 )'
ss -tn dst 192.0.2.0/24          # filter on destination network
ss -s                            # totals by state
ss -ti dst 192.0.2.50            # TCP internals for one peer: rtt, cwnd, retrans
ss -tnp state close-wait         # sockets the application forgot to close
ss -xl                           # listening UNIX sockets
```

The columns are `Netid`, `State`, `Recv-Q`, `Send-Q`, local and peer address with port. For listening sockets `Recv-Q` is the current accept-queue length and `Send-Q` its limit (the backlog); for established connections `Recv-Q` is bytes received but not read by the application and `Send-Q` is bytes sent but not yet acknowledged. A growing `Recv-Q` on an established socket points at a slow application, and a full accept queue explains refused or slow new connections. Address notation tells where a service is bound: `0.0.0.0:22` accepts IPv4 on all addresses, `[::]:22` accepts IPv6 (and IPv4 unless v6only is set), `127.0.0.1:5432` only local clients. The filter language supports `dport`, `sport`, `src`, `dst`, `state` with named sets (`connected`, `synchronized`, `bucket`, `big`) and logical operators.

### ethtool

`ethtool DEVICE` shows supported and advertised link modes, the negotiated `Speed` and `Duplex`, `Auto-negotiation`, port type and `Link detected`. Further subcommands, as listed in the manual page synopsis [src: man-pages 73d10e8bdb1b5cc0] and options [src: man-pages a19cfcef7e8316c3]:

```bash
ethtool eth0                     # link state, speed, duplex, autonegotiation
ethtool -i eth0                  # driver, version, firmware, bus-info
ethtool -S eth0                  # driver statistics (rx_missed, rx_no_buffer, tx_timeout ...)
ethtool -k eth0                  # offload features: tso, gso, gro, rx/tx checksumming, lro
ethtool -K eth0 gro off          # change offloads
ethtool -g eth0                  # ring buffer sizes (current and maximum)
ethtool -G eth0 tx 4096 rx 4096
ethtool -c eth0; ethtool -C eth0 rx-usecs 50     # interrupt coalescing
ethtool -l eth0; ethtool -L eth0 combined 4      # number of queues (channels)
ethtool -a eth0                  # pause (flow control) settings
ethtool -s eth0 speed 1000 duplex full autoneg off   # force link parameters
ethtool -P eth0                  # permanent MAC address
ethtool -m eth0                  # SFP/QSFP module EEPROM (optics diagnostics)
ethtool -p eth0 5                # blink the port LED for five seconds
ethtool -t eth0 offline          # self-test (disruptive)
ethtool --show-fec eth0; ethtool -x eth0         # forward error correction; RSS indirection table
```

Typical diagnoses: `Speed: 100Mb/s` on a gigabit link suggests a bad cable or a pair issue; `Duplex: Half` with a partner forced to full means a duplex mismatch (autonegotiation off on one side), which causes collisions and late-collision counters; `Link detected: no` with the cable seated points to the far end or the port; counters such as `rx_missed_errors` or `rx_no_buffer_count` mean the kernel could not drain the receive ring fast enough, and increasing the ring buffers or spreading interrupts is the remedy. The Rocky Linux performance guide walks through packet drops caused by interrupt handling and undersized ring buffers and shows the corresponding ring-buffer tuning [src: rocky-docs 6071e986baf747b8] [src: rocky-docs 06076278d13065e1], and the Rocky administration guide notes `ethtool` as the standard way to view the properties of a card [src: rocky-docs 4719b3630ece4ebc].

Persistence is the usual catch: `ethtool` changes are lost at reboot. Three persistent mechanisms are common. NetworkManager stores ethtool settings in the connection profile and applies them when the profile activates; the RHEL guides show the nmcli properties for offload features, coalescing and channel counts [src: rhel-10-docs a4c21eb690b5594a] [src: rhel-10-docs 2bd549d476bea7a6] [src: rhel-10-docs 326614d38b4849ec]. `systemd.link` files (`/etc/systemd/network/10-eth0.link`) set offloads and other options in a `[Link]` section, for example the TCP segmentation offload switches, on device appearance [src: man-pages 216a6f12ac0f5282]. A udev rule or a oneshot unit calling `ethtool` is the fallback. For latency-sensitive or throughput-sensitive services Red Hat documents how coalescing settings trade one for the other [src: rhel-10-docs 673f58746400fb47].

### Legacy equivalents

| Old command | Replacement |
|---|---|
| `ifconfig -a` | `ip -s addr` and `ip -s link` |
| `ifconfig eth0 192.0.2.10/24 up` | `ip addr add 192.0.2.10/24 dev eth0; ip link set eth0 up` |
| `route -n` | `ip route` |
| `route add default gw 192.0.2.1` | `ip route add default via 192.0.2.1` |
| `arp -n` | `ip neigh` |
| `netstat -tulpn` | `ss -tulpn` |
| `netstat -s`, `netstat -i` | `ss -s`, `nstat`, `ip -s link` |
| `iwconfig` | `iw dev` and `iw link` |

Other data sources: `/proc/net/dev` (per-interface counters), `/sys/class/net/<if>/` (`operstate`, `carrier`, `speed`, `mtu`, `address`, statistics under `statistics/`), `nstat` and `/proc/net/snmp` (protocol counters such as retransmissions), `ip -s -s link` for error detail.

## Assessment: the good, the bad and the ugly

What works well: `ip` models the kernel's real objects, supports several addresses per interface and policy routing, and has machine-readable JSON output; `ss` is fast on hosts with hundreds of thousands of sockets and exposes TCP internals that explain slow connections; `ethtool` gives access to the driver and hardware facts that no other tool shows. Together they answer most "is it the host?" questions within a minute.

What works badly: the syntax of `ip` is terse and abbreviations invite ambiguity; options differ between iproute2 versions (a flag on a new system may not exist on RHEL 8); `ss` output columns are easy to misread (the meaning of `Recv-Q` and `Send-Q` depends on state); `ethtool` support varies by driver, and virtual NICs ignore many settings. Changes are not persistent by default, and the mechanisms to persist them differ by distribution.

The awkward parts: tools disagree with network managers, which may overwrite manual changes at any time; flushing addresses over an SSH session cuts off the administrator; forcing speed and duplex off on one end breaks autonegotiation on the other; offload settings (GRO, LRO, TSO) interact badly with bridges, routers and some virtualisation, so captured packets look larger than the wire MTU and confuse analysis.

## Applications beyond this domain

The netlink model reappears in many Linux subsystems (`tc`, `bridge`, `devlink`, `rdma` and the `nftables` API), so learning the shape of `ip OBJECT COMMAND` pays off elsewhere. Container and virtualisation platforms rely on these objects: `ip netns`, veth pairs, bridges and VLAN sub-interfaces are what Docker and Kubernetes CNI plug-ins create, and inspecting a container's network usually means `nsenter -t PID -n ss -tulpn` or `ip -n NAME addr`. The socket introspection ideas of `ss` carry into observability tooling, for example eBPF-based tracers and service meshes that report connection state. Driver tuning with `ethtool` and the interrupt and queue concepts behind it are the entry point to high-performance networking (RSS, XDP, DPDK) described in vendor performance guides [src: rhel-10-docs 9224781bf8b55def]. For learning, Bootlin's networking lab sequence builds up VLANs, bridges and loopback interfaces with exactly these commands [src: bootlin-training 201179fb79e78f98].

## Examples

**Which process owns port 8080?** `ss -tlnp 'sport = :8080'` prints the listener and, with privilege, `users:(("python3",pid=2310,fd=4))`. If the address is `127.0.0.1:8080`, remote clients cannot reach it however the firewall is configured; rebinding to `0.0.0.0` or the interface address is the application's setting.

**Why is the host slow to a particular peer?** `ss -ti dst 203.0.113.9` shows the connection with `rtt:180/12`, `retrans:0/37` and a small `cwnd:4`. The path is long and lossy; the fix is on the network, not in the host's configuration. A `Send-Q` that stays high with many retransmits tells the same story.

**A link negotiated at 100 Mb/s.** `ethtool eth0` reports `Speed: 100Mb/s`, `Duplex: Full`. `ethtool -S eth0` shows `rx_crc_errors` increasing. Replacing the patch cable restores 1000 Mb/s. Forcing `ethtool -s eth0 speed 1000 autoneg off` instead would have broken the link, because gigabit Ethernet requires autonegotiation.

**Adding and persisting a route.** `ip route add 10.8.0.0/16 via 192.0.2.254` works at once. After reboot it is gone, so the route is also written into the connection profile (`nmcli connection modify eth0 +ipv4.routes "10.8.0.0/16 192.0.2.254"`) and applied with `nmcli connection up eth0`.

**A failing neighbour.** Pings to the default gateway fail; `ip neigh show 192.0.2.1` prints `INCOMPLETE`. No ARP reply comes back: the gateway is down, in another VLAN, or the cable is wrong. `ip -s link` shows TX packets increasing and RX flat, which supports a one-way problem.

**Persistent offload change.** A bridge guest sees oversized frames in captures. `ethtool -k eth0` shows `generic-receive-offload: on`; `ethtool -K eth0 gro off` confirms the cause. The permanent fix goes into the NetworkManager profile as an ethtool property or a `.link` file.

## Related problems and ideas

Neighbouring problems are packet capture and analysis (tcpdump, Wireshark, the troubleshooting topic), traffic shaping with `tc` and queueing disciplines (fq_codel, cake), performance tuning of sockets and buffers (`net.core.rmem_max`, `net.ipv4.tcp_rmem`), and link aggregation with bonding or teaming. Alternatives include `nmcli` and `networkctl` for the managers' own view, `ip` wrappers in configuration management modules, and the older text tools for embedded systems where BusyBox ships only `ifconfig` and `route`. Ideas still maturing include declarative network state (the NMState project and netplan YAML) that describe the desired result and let a tool compute the `ip` commands, and eBPF-based observability that replaces polling counters with event streams.

## Active research

Active work includes the ethtool netlink interface (more commands, notifications, per-queue statistics and stable names for counters), standardised NIC statistics for the kernel (qstats), more precise TCP diagnostics (TCP info fields exported through `ss -i`), the hardware offload model for programmable NICs (devlink, switchdev, XDP hints), and tools to explain packet drops in the kernel such as `dropwatch` and the drop-reason framework. Open questions include how to keep a consistent namespace of statistics across vendors and how to give administrators a single view of the state that drivers, network managers and the kernel each hold in part.

## Future direction

Expect JSON output and netlink notifications to replace text scraping in tooling, driver counters to be standardised, `ethtool` features to move into persistent network manager configuration as first-class properties, and eBPF-based tools to complement `ss` and `ip -s` with per-flow visibility. Legacy `net-tools` will stay out of default installs. For administrators the durable habits are: look before changing (`ip -br addr`, `ip route get`, `ss -tulpn`, `ethtool`), change at run time to test, persist in the active network manager, and confirm with counters that the change helped.
