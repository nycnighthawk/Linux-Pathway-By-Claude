# Reaching hosts safely with OpenSSH: keys, jump hosts and port forwarding

## Define the problem

Almost every Linux machine an administrator touches is reached over a network, usually across networks they do not control. A remote shell therefore has to solve four problems at once: prove who the server is (so a hostile network cannot impersonate it), prove who the user is (without sending a reusable secret), protect the session from eavesdropping and tampering, and do all of this conveniently enough that people do not work around it. Beyond a shell, administrators need to move files, run single commands in scripts, and reach services that are not exposed directly: a database listening only on loopback, a web console in a private subnet, a host that has no public address at all.

OpenSSH is the implementation that nearly every Linux distribution ships. It provides the client `ssh`, the server `sshd`, the copy tools `scp` and `sftp`, and the key tools `ssh-keygen`, `ssh-agent`, `ssh-add`, `ssh-copy-id` and `ssh-keyscan`. This slice covers key-based authentication, the agent, the client configuration file, jump hosts with `ProxyJump`, the three kinds of port forwarding, and the server-side settings that decide what is allowed. Red Hat's documentation frames it as the standard tool for secure communication between two systems [src: rhel-10-docs cb66183ce4e5269d].

## History and approaches

The telnet and `rsh` family sent passwords and sessions in clear text and trusted source addresses. SSH (the protocol, version 1) was written in 1995 in response to a password-sniffing incident, and a version 2 protocol was later standardised by the IETF in the RFC 4250 to 4254 series (architecture, transport, authentication and connection layers). OpenSSH began in 1999 as a clean-room continuation from the OpenBSD project, based on the last freely licensed release of the original code; it is developed in OpenBSD and a separate portable release carries it to Linux and other systems.

Several design choices shaped later practice. Host authentication is by key, recorded on first contact in `known_hosts`, which is simple but gives the first connection a trust-on-first-use weakness. User authentication supports passwords, public keys, keyboard-interactive methods (used for one-time codes) and, in enterprise setups, Kerberos through GSSAPI. The connection layer multiplexes channels over one transport, which is why one TCP connection can carry a shell, forwarded ports and file transfers at once, and why connection sharing is possible.

Algorithms changed with the threat model. Ed25519 keys were added in the 6.x series and became the usual default for new keys; DSA host and user keys were dropped from default use; and the RSA signature scheme based on SHA-1 was disabled by default in the 8.x series, so very old clients and appliances may need explicit exceptions (to verify against the release notes for the exact versions). Jump hosts were handled for years by a `ProxyCommand` that ran `nc` or `ssh -W` on the bastion; the `-J` option and `ProxyJump` keyword were added later as a shorter form of the same idea, and the Arch wiki and Red Hat documentation present it as the preferred method [src: archwiki 21a45ddd1dbd9e85] [src: rhel-10-docs afa111c33714256f].

Competing approaches exist. Certificate-based SSH signs user and host keys with a certificate authority so that nothing needs distributing to `authorized_keys` or `known_hosts`. Session brokers and bastion products add recording and short-lived access. Zero-trust gateways and cloud shells hide the port altogether. Mosh adds roaming over UDP, and tools such as Kubernetes `kubectl exec` or KubeVirt's `virtctl ssh` wrap access in the platform's own authentication [src: kubevirt-user-guide 4369c6630b0c2c54].

## Current state

### Keys and the agent

A key pair is created with `ssh-keygen`. For a new key, `ssh-keygen -t ed25519 -C "laptop 2026"` is the default recommendation; the `-a` option raises the number of key-derivation rounds that protect the private key under its passphrase, and RSA keys, where required for compatibility, should use at least 3072 bits (`-t rsa -b 3072`). The private key is stored in `~/.ssh/id_ed25519` with mode 0600 and must have a passphrase; the public key `id_ed25519.pub` is a single line that goes into the server's `~/.ssh/authorized_keys`. `ssh-copy-id user@host` appends it with correct permissions. The server refuses keys if `~/.ssh` or `authorized_keys` is writable by others (controlled by `StrictModes`), which is the first thing to check when key authentication silently falls back to a password.

Typing the passphrase on every connection would invite people to remove it. `ssh-agent` holds decrypted keys in memory and answers signing requests over a socket named in the environment variable `SSH_AUTH_SOCK`; `ssh-add` loads keys (`ssh-add -l` lists them, `-t 4h` gives a lifetime, `-D` clears all). Setting `AddKeysToAgent yes` in the client configuration loads a key on first use. Arch's wiki describes agent options and how desktop sessions and systemd user units start one [src: archwiki fb1a0ceee948a815]. On servers the same mechanism supports agent forwarding (below).

`ssh-keygen` also manages the other end. `ssh-keyscan host` fetches a host's public keys for pre-seeding `known_hosts`; `ssh-keygen -F host` looks an entry up and `ssh-keygen -R host` removes it after a legitimate host rebuild; `ssh-keygen -lf file` prints a fingerprint for out-of-band comparison. Certificates: `ssh-keygen -s ca_key -I id -n alice -V +8h user_key.pub` signs a user key valid for eight hours for principal `alice`, and the server trusts the CA through `TrustedUserCAKeys` in `sshd_config`.

### The client configuration

`~/.ssh/config` (then `/etc/ssh/ssh_config` and files under `/etc/ssh/ssh_config.d/`) is read top to bottom, and for each option the **first** value obtained wins, so specific blocks must come before general ones. Typical content:

```
Host bastion
    HostName bastion.example.net
    User ops
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

Host db1 db2 app-*
    ProxyJump bastion
    User admin

Host *
    ServerAliveInterval 30
    ControlMaster auto
    ControlPath ~/.ssh/cm-%C
    ControlPersist 10m
    AddKeysToAgent yes
```

`Host` patterns select blocks; `Match` offers conditions such as `Match host db* user admin exec "test -f ..."`. `IdentitiesOnly yes` stops the client from offering every key in the agent, which otherwise can trip a server's authentication-attempt limit (`MaxAuthTries`). `ControlMaster` with `ControlPersist` shares one authenticated connection among later sessions, which makes repeated `ssh`, `scp` and Ansible tasks fast; `ssh -O check host` and `ssh -O exit host` query and close the shared master. Run `ssh -G host` to print the effective configuration after all blocks are applied, which is the best debugging aid for configuration questions.

### Jump hosts

A bastion (jump host) is a machine in front of a private network that accepts SSH from outside, so inner hosts need not be exposed. The modern form is one option:

```
ssh -J ops@bastion.example.net admin@db1.internal
```

or `ProxyJump bastion` in a `Host` block. Several hops are comma-separated (`-J hop1,hop2`). Unlike agent forwarding, a jump host only relays the encrypted stream: the client authenticates to the final host itself, end to end, so a compromised bastion cannot read the session or use the client's keys. The older `ProxyCommand ssh -W %h:%p bastion` achieves the same and remains useful when options differ per hop. Red Hat's guide shows the procedure for the current release [src: rhel-10-docs afa111c33714256f]. Combine with `ControlMaster` so a series of connections to inner hosts pay the bastion handshake once.

### Port forwarding

OpenSSH tunnels TCP through the encrypted channel in three forms:

- **Local forward** `-L [bind:]lport:rhost:rport`. A listener opens on the *client*; connections are carried to the server, which connects on to `rhost:rport`. Use it to reach a service that the server can see but you cannot: `ssh -L 5433:db.internal:5432 bastion` then `psql -h 127.0.0.1 -p 5433`.
- **Remote forward** `-R [bind:]rport:lhost:lport`. A listener opens on the *server*; connections are carried back to the client, which connects to `lhost:lport`. Use it to publish a local service through a reachable machine, or to let a remote host reach back to a development server.
- **Dynamic forward** `-D [bind:]port`. The client opens a SOCKS proxy; each application connection becomes a forward chosen at request time. It is a small, ad hoc VPN for browsers and tools that support SOCKS.

Useful companions are `-N` (no remote command, tunnel only), `-f` (go to background), `-o ExitOnForwardFailure=yes` (fail if a listener cannot be created), and `-g` or a non-loopback bind address (exposing the listener to other machines, which is rarely a good idea). On the server, `AllowTcpForwarding`, `GatewayPorts` (whether a remote listener may bind to other interfaces than loopback), `PermitOpen` and `PermitListen` limit what is possible. The man page's description section summarises the options that cover these behaviours [src: man-pages 73d5113ce401d017] [src: man-pages ce5ef8a7f11106aa]. Layer 3 tunnels (`-w`) exist but need `PermitTunnel` and root privileges and are better replaced by a real VPN.

Agent forwarding (`ssh -A` or `ForwardAgent yes`) lets the remote host use your agent's keys to authenticate onward. That is convenient and also risky: root on the intermediate host can use the forwarded socket for as long as you are connected. Prefer `ProxyJump`, which needs no agent on the bastion; if forwarding is unavoidable, enable it only for named hosts and confirm uses with `ssh-add -c` [src: archwiki e10d5e0f05975418].

### The server

Settings live in `/etc/ssh/sshd_config` and, on current distributions, in drop-in files under `/etc/ssh/sshd_config.d/` that are included near the top (so the first-obtained value wins again). The ones that matter in practice: `PermitRootLogin` (set to `no` or `prohibit-password`), `PasswordAuthentication no` once keys work, `PubkeyAuthentication yes`, `AllowUsers` or `AllowGroups`, `MaxAuthTries`, `LoginGraceTime`, `ClientAliveInterval` with `ClientAliveCountMax`, `AllowTcpForwarding`, and `Subsystem sftp`. Match blocks (`Match User backup`, `Match Address 10.0.0.0/8`) tighten or relax options for subsets, and `ForceCommand` with `ChrootDirectory` builds restricted accounts. Per key, the options in `authorized_keys` (`from="10.0.0.0/8"`, `command="..."`, `restrict`, `permitopen="host:port"`) bind one key to one purpose, which is how a backup key is limited to a single command.

Always validate before reloading: `sshd -t` checks syntax, `sshd -T` prints the effective settings (add `-C user=alice,addr=10.1.2.3,host=h` to evaluate Match blocks), and `systemctl reload sshd` (the unit is `sshd` on Red Hat family systems and `ssh` on Debian family ones) applies changes without disconnecting current sessions. Keep a second session open when changing authentication settings. Red Hat's hardening section collects typical settings for the server [src: rhel-10-docs 0c5d2f818c3c5b32], and Debian's handbook covers the same basics in its remote-login chapter [src: debian-handbook 9d3b72fd705e61e7]. On RHEL-family systems, a changed port also needs a firewall rule and an SELinux label (`semanage port -a -t ssh_port_t -p tcp 2222`), tying this slice back to the previous one.

### Troubleshooting

`ssh -v host` (up to `-vvv`) shows which keys were offered, which algorithms were negotiated and where authentication stopped. On the server, the journal (`journalctl -u sshd`) names the reason for rejection (permissions, unknown user, key type not allowed). Typical causes: wrong permissions on `~/.ssh`, a home directory on a filesystem with an SELinux context that blocks reading `authorized_keys` (`restorecon -R ~/.ssh`), a host key changed after a rebuild, a firewall drop that looks like a timeout versus a refusal that looks like an immediate error, and a client offering too many keys. Arch's wiki collects the refused-versus-timeout cases [src: archwiki 6a6621379cab015f].

## Assessment: the good, the bad and the ugly

**The good.** One small, audited tool replaces many insecure ones. Public-key authentication removes password guessing as an attack route. The channel model makes forwarding, multiplexing and file transfer cheap. The configuration file turns long command lines into names, and `ProxyJump` makes multi-hop access a single line without trusting the intermediate host. Certificates scale key management to large fleets.

**The bad.** Trust on first use means the first connection to a host is only as safe as the network path unless fingerprints are compared out of band or host certificates are used. Keys are long-lived by default and nothing expires them; `authorized_keys` files drift, and a departed employee's key can survive for years. The first-value-wins rule in configuration files and drop-ins surprises people who append overrides at the end. Passphrase-less keys on servers are common for automation and one stolen file gives full access.

**The ugly.** Agent forwarding to untrusted hosts; unlimited `AllowTcpForwarding` on servers that should only provide a shell, which turns any account into a way into the internal network; and remote forwards with `GatewayPorts yes` that expose a developer's laptop service to the internet. Host-key warnings are routinely silenced with `StrictHostKeyChecking no` and `UserKnownHostsFile /dev/null` in scripts, which removes the host authentication the protocol exists to provide. And a large fleet with unmanaged keys has no revocation story short of replacing every `authorized_keys`.

## Applications beyond this domain

The protocol and its ideas travel. Git over SSH uses the same keys and agent; Ansible and other automation tools open SSH connections (and rely on `ControlPersist` for speed); backup tools such as `rsync` and `borg` run over it. Kubernetes and virtualisation platforms expose SSH helpers (the KubeVirt guide describes `virtctl ssh` for virtual machines [src: kubevirt-user-guide 4369c6630b0c2c54]). Microsoft ships OpenSSH for Windows and documents the Windows-specific `sshd_config` arguments, so the same keys reach both platforms [src: ms-learn-adds 325d57ae79791ec4]. Network gear, storage appliances and embedded systems expose SSH for management. Hardware security keys can hold SSH keys (FIDO-backed key types) so that the private part never leaves the device. The idea of authenticated, encrypted multiplexed channels is also what later protocols such as QUIC and WireGuard-based tools pursue in different forms.

## Examples

**1. First-time key setup.**

```
ssh-keygen -t ed25519 -a 100 -C "alice@laptop"
ssh-copy-id -i ~/.ssh/id_ed25519.pub alice@server1
ssh -o PasswordAuthentication=no alice@server1 true && echo key login works
```

Only after the last command prints its message is it safe to disable passwords on the server.

**2. Reach a private database through a bastion.**

```
ssh -N -f -o ExitOnForwardFailure=yes -L 5433:db1.internal:5432 ops@bastion.example.net
psql -h 127.0.0.1 -p 5433 appdb
```

The tunnel is a local forward: the listener is on the laptop, the connection to the database comes from the bastion.

**3. Jump with a config block.**

```
Host *.internal
    ProxyJump ops@bastion.example.net
    User admin
```

After that, `ssh app1.internal` and `scp file app1.internal:/tmp/` both traverse the bastion.

**4. Publish a local service temporarily.**

```
ssh -R 8080:localhost:3000 demo@public.example.net
```

The remote end listens on its loopback interface on port 8080; with the server's default `GatewayPorts no` it is not reachable from outside, which is the safe default. A colleague on that host can open `http://localhost:8080/`.

**5. SOCKS proxy for browsing an internal network.**

```
ssh -D 1080 -N ops@bastion.example.net
```

Point a browser's SOCKS5 proxy at `localhost:1080` (and enable remote DNS through the proxy if internal names must be resolved on the far side).

**6. Restrict a backup key to one command.** In the server account's `authorized_keys`:

```
restrict,from="192.0.2.10",command="/usr/local/bin/backup-pull" ssh-ed25519 AAAA... backup@host
```

The `restrict` option disables forwarding, the pty and agent use, and `command` pins what the key can run. Here it names a small wrapper script that you write, which can inspect `$SSH_ORIGINAL_COMMAND` and run only the fixed transfer.

**7. Audit a server's effective configuration.**

```
sshd -T | grep -E '^(permitrootlogin|passwordauthentication|allowtcpforwarding|maxauthtries)'
sshd -T -C user=alice,addr=203.0.113.9,host=server1 | grep allowtcpforwarding
```

The second form shows what a particular user from a particular address would be allowed after `Match` blocks apply.

## Related problems and ideas

- **Firewalls and port exposure.** The previous slice restricts which sources may reach port 22; moving the port is obscurity, restricting sources is a control.
- **Host-key and identity management.** SSH certificates, `known_hosts` distribution through configuration management, and short-lived credentials from a broker.
- **Network debugging.** Distinguishing connection refused, timeout and reset (covered with `mtr`, `dig` and `tcpdump` in the next slice).
- **Multiplexing and automation.** Ansible's connection settings, `ControlPersist`, and parallel shells.
- **Privilege boundaries.** `sudo` policy on the remote end, and `PermitRootLogin` choices.
- **Alternative tunnels.** WireGuard and IPsec for full network connectivity; SSH forwards are per-port.

## Active research

OpenSSH development continues to focus on cryptographic agility and removal of weak defaults: hybrid post-quantum key exchange is now offered in releases of the portable edition, and the project has been phasing out older primitives in stages (check the release notes for the current default list). Other active areas include FIDO/U2F-backed keys, privilege separation hardening, agent restrictions (limiting where a forwarded key may be used), and better host-key rotation and certificate workflows. In the wider ecosystem, research and practice look at short-lived certificates issued from identity providers, SSH session recording, and the supply-chain risk of libraries linked into `sshd` on some distributions, which prompted widespread review of dependency chains.

## Future direction

Expect SSH to keep its place as the management channel of last resort while the access path around it becomes more automated: certificate or token issuance replaces hand-managed keys, bastions become brokers with logging, and hardware-backed keys replace passphrase-protected files. For a Linux administrator the durable habits are the same: ed25519 keys with passphrases, an agent with lifetimes, `ProxyJump` instead of agent forwarding, forwarding disabled on the server unless needed, `sshd -t` before every reload, and verified host fingerprints.
