# Finding where the network breaks: a layered method with mtr, dig and tcpdump

## Define the problem

"The network is down" is a symptom, not a diagnosis. A failing request can die at the link, at address assignment, at the default gateway, somewhere on the path, in name resolution, at a firewall, or in the service itself; and the person reporting it usually knows only that a page does not load or a command hangs. Troubleshooting is the discipline of dividing the path into stages and testing each in order until the first failing stage is found, then changing one thing and testing again. Done without a method it turns into restarting services at random and hiding the evidence.

Three tools carry most of the evidence on Linux. `mtr` combines `ping` and `traceroute` to show, hop by hop, where latency rises or packets vanish. `dig` queries DNS servers directly and shows what each one answered, with which flags. `tcpdump` captures packets at an interface and shows what actually crossed the wire, which settles disputes between "the application sent it" and "the network lost it". Around them sit `ip`, `ss`, `ping`, `curl`, `nc` and `resolvectl`, which answer the stage-by-stage questions. This slice teaches the sequence and how to read the output of each tool, with the commands an on-call administrator needs.

## History and approaches

The first tools date from the early Internet. `ping` was written in 1983 by Mike Muuss, using ICMP echo, and `traceroute` followed in 1987 (Van Jacobson), using a trick with the TTL field: send probes with a time-to-live of 1, 2, 3 and so on, and each router that decrements it to zero returns an ICMP time-exceeded message that names that hop. Matt Kimball's `mtr` (originally "Matt's traceroute") merged the two in 1997 into a live display with running statistics. `tcpdump` came from the Lawrence Berkeley laboratory in the late 1980s and is built on libpcap and the Berkeley Packet Filter, a small virtual machine in the kernel that evaluates a filter expression per packet so only matching packets are copied to userspace. `dig` arrived with BIND 9 as the successor of `nslookup`, whose behaviour was inconsistent and which had been marked deprecated; the Debian ecosystem packages it in `dnsutils` or `bind9-dnsutils` and Red Hat's in `bind-utils`.

Approaches differ in how deep they go. **Active probing** (ping, mtr, traceroute, `nc -zv`, `curl -v`) sends traffic and measures replies; it is quick but depends on the path allowing the probe, and ICMP is often rate limited or filtered. **Passive capture** (tcpdump, Wireshark, `tshark`) observes real traffic and so tests the real application, at the cost of volume and privacy. **Counters and state** (`ip -s link`, `ss -ti`, `nstat`, `conntrack`) are free and always on, but coarse. **Distributed tracing** and flow telemetry (sFlow, NetFlow, eBPF-based tools) answer the same questions at fleet scale. Platform vendors add their own: Kubernetes documents debugging a node with an ephemeral debug container that carries network tools [src: kubernetes-docs 32b7a9baf30796bf], and Cilium's troubleshooting guide uses its own observability to check peerings [src: cilium-docs 2d38433a4a585c1d].

## Current state

### A method: bottom up, one stage at a time

A course lab from Rocky Linux walks through the same ladder: check link state with `ip link show`, then reachability of the gateway, then a remote address, then a name [src: rocky-docs 1c0df21dd9efe0d6]. A fuller version, with the command that answers each question:

1. **Is the link up?** `ip -br link` shows `UP` and `LOWER_UP` states; `ethtool eth0` shows speed and "Link detected". Counters in `ip -s link show eth0` reveal errors and drops.
2. **Does the interface have an address, and the right one?** `ip -br addr`. A 169.254.x.x address means DHCP failed. For NetworkManager hosts, `nmcli device status` and `nmcli connection show` show which profile is active, and Rocky's administration guide recommends managing the configuration through NetworkManager's own commands rather than editing files [src: rocky-docs 21f9eea9cca7ad68].
3. **Is the default gateway reachable?** `ip route show default` names it; `ping -c3 <gateway>` tests it; `ip neigh show` should show it as REACHABLE (a FAILED entry means the ARP or neighbour-discovery exchange got no answer).
4. **Which route will a given destination use?** `ip route get 192.0.2.10` prints the chosen interface, next hop and source address, applying policy rules too.
5. **Can the host reach an address outside?** `ping -c3 1.1.1.1` (or any known address). If this works but names fail, the problem is DNS.
6. **Does name resolution work?** `dig`, below. Also `getent hosts name`, which follows the system's resolver order (`/etc/nsswitch.conf`) the way applications do, and `resolvectl query name` on systemd-resolved hosts.
7. **Is the service listening?** On the server, `ss -tlnp` shows listening TCP sockets and the processes that own them; on the client, `nc -zv host 443` or `curl -v https://host/` tests the TCP and TLS handshake.
8. **Is a firewall or security policy in the way?** The previous slice's tools: `nft list ruleset`, `firewall-cmd --list-all`. A refused connection (immediate RST) points to nothing listening or a reject rule; a timeout points to a drop rule or a missing return route.

Write down each result. The first failing step is where to look, and skipping steps wastes time.

### mtr

`mtr` runs repeated probes with increasing TTL and keeps statistics per hop. Interactive use opens a live table; for evidence, use report mode:

```
mtr -rwn -c 100 example.com
mtr -rwzn -c 100 example.com
mtr -rn -T -P 443 -c 100 example.com
```

`-r` prints a report and exits, `-w` shows full hostnames, `-n` skips reverse DNS (faster and avoids a DNS dependency during an outage), `-c` sets the cycle count, `-z` adds the AS number, and `-T -P 443` uses TCP SYN probes to a port instead of ICMP, which helps when the path treats ICMP differently from real traffic. The columns are `Loss%`, `Snt` (probes sent), `Last`, `Avg`, `Best`, `Wrst` and `StDev`.

Reading the table takes care:

- **Loss only on an intermediate hop, none afterwards** is nearly always ICMP rate limiting on that router: it answers probes to itself slowly but forwards traffic fine. Judge by the *last* hop and by hops after the suspect.
- **Loss that begins at a hop and continues to the end** marks a real problem at or just after that hop.
- **A latency jump that persists** from one hop onward shows where the delay is added (a long link, a congested queue, or a path asymmetry).
- **Rows of `???`** are routers that do not answer TTL-expired probes; they are common and harmless if later hops answer.
- A single trace shows one direction. Return paths can differ, so ask the other end to run `mtr` back for a complete picture.

`traceroute` and `tracepath` give the same hop list without statistics; the manual pages for `ping` and `traceroute` document the options in detail, including the use of UDP, ICMP and TCP probes and the size and TTL controls [src: man-pages d4c7bfbd58dec926] [src: man-pages 0a0482a51c3ee41e]. `ping -M do -s 1472 host` sends a packet with the don't-fragment bit and a given payload to find the path MTU, a common cause of a path where short packets pass and long ones stall.

### dig

`dig` sends a query and prints the reply with its header flags. The basic forms:

```
dig example.com
dig +short example.com A
dig @192.0.2.53 example.com AAAA
dig -x 192.0.2.10
dig +noall +answer example.com MX
dig +trace example.com
dig +norecurse @a.root-servers.net com NS
dig +tcp +dnssec example.com
```

A response has four parts: header, question, answer, and authority/additional sections, followed by statistics (query time, server, when). In the header, **`status`** is the result code: `NOERROR` (the query worked; an empty answer means the name exists but has no record of that type), `NXDOMAIN` (the name does not exist), `SERVFAIL` (the server could not get an answer, often a DNSSEC validation failure or an unreachable authoritative server) and `REFUSED` (policy). **Flags** matter too: `qr` marks a response, `rd` recursion desired (set by the client), `ra` recursion available (set by a resolver), `aa` authoritative answer (set when the data comes from the zone's own server), `ad` authenticated data (the resolver validated DNSSEC). A reply with `aa` came from the source of truth; a reply without it came from a cache, whose remaining lifetime is the TTL column in the answer.

Practical uses: compare what the system resolver and the authoritative server say (`dig example.com` versus `dig @ns1.example.net example.com`) to separate caching or split-horizon problems from publication problems; `dig +trace` follows delegation from the root and shows where the chain breaks; `dig +tcp` tests whether TCP port 53 is reachable, which matters for large answers and DNSSEC; `dig +short -x` checks reverse records for mail servers. Because `dig` talks to the server you name, it ignores `/etc/hosts` and the name-service switch; use `getent hosts` to see what applications see. On hosts that use systemd-resolved or NetworkManager's dnsmasq plugin, per-domain routing sends some names to different servers, which Red Hat's documentation describes for the NetworkManager variants [src: rhel-10-docs 6e2246ca9d54b877] [src: rhel-10-docs 9eb77d57a906e15d]; `resolvectl status` shows which server each link uses.

### tcpdump

`tcpdump` needs privileges (root or capabilities `CAP_NET_RAW` and `CAP_NET_ADMIN`). The structure of a command is options, then a filter expression in the Berkeley syntax:

```
tcpdump -i eth0 -nn host 192.0.2.10 and port 443
tcpdump -i any -nn -c 20 icmp
tcpdump -i eth0 -nn -s 0 -w /tmp/web.pcap port 80
tcpdump -nn -r /tmp/web.pcap 'tcp[tcpflags] & (tcp-syn|tcp-ack) == tcp-syn'
tcpdump -i eth0 -nn -A -s 0 'tcp port 80 and greater 100'
```

The options worth knowing: `-i` selects an interface (`-D` lists devices); `-n` and `-nn` turn off name and port-name lookups, which otherwise slow output and generate their own DNS traffic; `-c` stops after N packets; `-s 0` captures whole packets (modern versions default to a large snapshot length, but old scripts still use it); `-w` writes a pcap file for later reading with `-r` or Wireshark; `-e` shows link-level headers, useful for VLAN tags and MAC problems; `-v`, `-vv` add decoded detail; `-X` and `-A` print payload in hex or ASCII; `-G` and `-C` with `-W` rotate capture files for long-running captures. The manual page notes that the pseudo-interface `any` captures across all regular interfaces but not in promiscuous mode, and that capture can come from devices that do not go through the operating system's network stack [src: man-pages 047f04a04123f5ec]; its options section also covers monitor mode for Wi-Fi capture [src: man-pages 75316ebe2a4ea97a]. Capture on `any` also loses the Ethernet header on some link types, so use a specific interface when the link layer matters.

Filters work on protocol and address primitives (`host`, `net 10.0.0.0/8`, `port`, `portrange`, `src`, `dst`, `tcp`, `udp`, `icmp`, `arp`, `vlan`) combined with `and`, `or`, `not` and parentheses (quote the expression for the shell). Byte-offset forms such as `tcp[tcpflags]` reach into headers. The most common reading skills are on TCP:

- **SYN with no SYN-ACK** (flags `[S]` repeating, with growing gaps): the packet reaches the server's network but no answer returns, or nothing is listening and a drop rule hides it.
- **SYN followed by RST** (`[R.]`): the host answered that nothing is listening, or a reject rule fired.
- **Retransmissions and zero windows**: loss on the path, or a receiver that is not reading.
- **DNS queries with no reply**, or replies from an unexpected address: resolver outage or a split-path problem.
- **Fragmented or ICMP "need to fragment" packets**: an MTU problem.

Capturing at both ends and comparing is the strongest method: if a packet leaves the client but never arrives at the server, the fault is in between; if it arrives and the server never answers, the fault is at the server.

### Putting it together

A worked incident: a user cannot open `https://app.example.net`. `ip -br addr` and `ip route show default` look right; `ping` to the gateway works; `ping 203.0.113.20` works; `getent hosts app.example.net` returns nothing. So the break is at name resolution. `dig app.example.net` returns `SERVFAIL`; `dig @203.0.113.53 app.example.net` returns the record with `aa` set, so the authoritative server is fine and the local resolver is the problem. `resolvectl status` shows the link's DNS server is unreachable; a capture with `tcpdump -nn -i eth0 port 53` shows queries leaving with no replies. The fix is in the DHCP-provided or configured resolver, not in the application.

### Hardening and baselines

Troubleshooting tools are also attack tools, and baselines treat them accordingly: packet capture requires privilege, captures often contain credentials, and compliance guidance asks for limits on promiscuous interfaces and for rate limiting on network devices. Red Hat's IPsec chapter shows tool-based troubleshooting for another protocol (checking logs, listing security associations, capturing ESP traffic) in the same style [src: rhel-10-docs f3ac41b4d21820ab] [src: rhel-10-docs 78445bb2c923891e].

## Assessment: the good, the bad and the ugly

**The good.** The tools are small, scriptable and ubiquitous; the same three commands solve problems on a laptop, a VM and a router. `mtr` turns a vague complaint into a table; `dig` separates resolver from authority; `tcpdump` provides ground truth that no log can contradict. The layered method is cheap and teachable, and a written transcript of results makes handover and post-incident review straightforward.

**The bad.** Active probes measure what the path does with probes, not with your traffic: ICMP may be deprioritised or filtered, and ECMP may route the probe differently from a TCP flow. `mtr`'s intermediate-hop loss is easy to misread. `dig` bypasses the system resolver, so a correct `dig` answer does not prove applications will resolve correctly. `tcpdump` on a busy host can drop packets itself or fill the disk; filters are terse, and the BPF byte-offset syntax is easy to get wrong. Encrypted traffic (TLS, SSH, IPsec) hides the payload, so capture shows timing and handshakes but not content.

**The ugly.** Troubleshooting under pressure: changes made before evidence is saved, firewalls flushed to "test", captures left running, pcap files with passwords sitting in `/tmp`, and conclusions drawn from one-direction traces. Asymmetric routing, middleboxes that rewrite or drop selectively, and MTU black holes produce failures where small packets work and large ones do not, which look random until a capture shows the pattern. Privacy law and policy constrain capturing other people's traffic even on your own network.

## Applications beyond this domain

The method generalises: bisect the path, test each stage, compare both ends. The same skills carry into container and cluster debugging, where an ephemeral container with `tcpdump` and `dig` shares a pod's network namespace [src: kubernetes-docs 32b7a9baf30796bf], and into overlay or eBPF datapaths where equivalent tools exist (Cilium's guide, Open vSwitch's trace commands for virtual switches [src: man-pages 92176f8a918ea9ad]). `tcpdump` captures feed intrusion detection and protocol analysis; `dig` is the basis of DNS monitoring and DNSSEC validation checks; `mtr`-style probing underlies internet measurement and multi-region monitoring services. The method also applies to non-network systems: bisecting a build pipeline or an I/O stack uses the same logic.

## Examples

**1. Is it DNS or connectivity?**

```
ping -c2 192.0.2.10 && echo reachable
getent hosts www.example.org || echo name lookup failed
dig +short www.example.org
```

If the first succeeds and the others fail, the issue is resolution.

**2. Evidence for a provider ticket.**

```
mtr -rwzn -c 200 198.51.100.7 > mtr-$(date +%F-%H%M).txt
```

Attach the report; run the reverse direction from the far side if possible.

**3. Which DNS server answers, and who is authoritative?**

```
dig +short NS example.org
dig @ns1.example.org example.org SOA +norecurse
dig example.org SOA
```

Compare the serial numbers in the SOA records from the authoritative and recursive answers; a lagging recursive answer is caching.

**4. Watch a TCP connection being refused.**

```
tcpdump -nn -i eth0 'host 192.0.2.10 and tcp port 8080'
```

In a second terminal run `curl -m5 http://192.0.2.10:8080/`. A SYN answered by an RST line means a closed port; a SYN repeated with no reply points to a drop.

**5. Record then analyse later.**

```
tcpdump -i eth0 -nn -s 0 -G 300 -W 12 -w '/var/tmp/cap-%H%M.pcap' port 5432
tcpdump -nn -r /var/tmp/cap-0930.pcap 'tcp[tcpflags] & tcp-rst != 0' | head
```

A rotating ring of twelve five-minute files with a bounded disk cost; the second command finds resets.

**6. Path MTU probe.**

```
ping -c3 -M do -s 1472 192.0.2.10
ping -c3 -M do -s 1400 192.0.2.10
```

A failure at 1472 and success at 1400 means the path MTU is below 1500 (for example because of a tunnel); then find the limit and fix the tunnel or clamp the TCP MSS.

## Related problems and ideas

- **Routing and policy.** Wrong-interface replies, `rp_filter` drops and policy routing show up as asymmetric traces; see the routing slice.
- **Firewall verdicts.** `nft monitor trace` and counters complement packet capture by naming the rule that dropped a packet.
- **SSH diagnostics.** Distinguishing refusal from timeout is the first step in the OpenSSH slice's troubleshooting section [src: archwiki 6a6621379cab015f].
- **Time and TLS.** Handshake failures often come from wrong clocks or missing certificate chains rather than the network.
- **Performance rather than failure.** `iperf3`, `ss -ti` (congestion window, retransmits) and queue discipline statistics (`tc -s qdisc`) address slowness.
- **Wireless.** Capture in monitor mode and 802.1X logs, touched on in the final slice.

## Active research

The long-running trend is toward always-on, low-overhead observability: eBPF programs that count and sample packets in the kernel, flow telemetry exported to analysis systems, and tracing that links a packet to a process and a container. Work on encrypted DNS (DNS over TLS and HTTPS) complicates the use of `tcpdump` and `dig` as before, since the traffic is no longer visible on port 53; tooling is adapting with resolver-side logging and test clients. QUIC, which runs over UDP and encrypts most of its headers, changes what a capture can reveal compared to TCP. Research on active measurement, such as better hop-by-hop loss attribution and path discovery under ECMP (Paris traceroute and its successors), continues to refine what `mtr`-style tools can claim.

## Future direction

Expect more of the evidence to come from continuous telemetry rather than ad hoc commands, with the commands remaining as the sharp tool for a single host. Administrators who learn the layered method will adapt as protocols change: capture and probe at the layer where the symptom appears, compare both ends, and change one variable at a time. For this course the target skill is fluency in the eight-step ladder and the ability to read an `mtr` report, a `dig` header and a TCP handshake without looking up the meaning of each field.
