# epoll and io_uring: waiting on many things at once

## Define the problem

A server process may hold tens of thousands of open sockets, files and pipes, and almost all of them are idle at
any given moment. The program needs to learn cheaply which ones are ready, and then move data with as few kernel
transitions and copies as possible. One thread per connection wastes memory and scheduler time. Blocking calls in
a loop stall on the first slow peer. The problem has two parts:

- **readiness notification**: tell me which descriptors I can act on now without blocking;
- **operation submission and completion**: let me hand the kernel work (read, write, accept, fsync, open) and
  learn later that it finished, ideally in batches.

The cost model has to stay flat as the number of descriptors grows, work for both network and storage I/O, and
remain safe to expose to unprivileged processes. This slice covers `select`/`poll`, `epoll` and `io_uring` on
Linux. Thread pools, POSIX AIO internals and user-space runtimes (libuv, Tokio, Go's netpoller) are discussed only
as consumers.

## History and approaches

**select and poll (1980s).** Both take the full set of descriptors on every call. The kernel scans all of them and
the caller then scans the result. The cost is proportional to the number watched, not the number ready, so they
degrade badly beyond a few thousand connections. `select` also caps descriptors at `FD_SETSIZE`. These calls solve
readiness only.

**The C10K pressure (late 1990s).** The famous ten-thousand-connections challenge pushed every Unix towards a
stateful interface: register interest once, then ask only for events. FreeBSD added `kqueue`, Solaris added
`/dev/poll` and event ports, and Linux experimented with real-time signals before settling on `epoll` (2.5.44,
2002).

**epoll.** Three calls: `epoll_create1` makes an interest list held in the kernel, `epoll_ctl` adds, modifies or
removes a descriptor, and `epoll_wait` returns only ready entries. Two triggering styles matter in practice:

- *level-triggered* (default) reports a descriptor for as long as it stays ready, which is forgiving;
- *edge-triggered* (`EPOLLET`) reports only transitions, so the caller must drain the descriptor until `EAGAIN` or
  risk never hearing about it again.

Later flags (`EPOLLONESHOT`, `EPOLLEXCLUSIVE`) addressed thundering herds when many threads wait on one listener.
epoll made readiness scale, but each actual read or write is still its own system call, and regular files are
always "ready", so disk I/O does not fit the model.

**Linux AIO (2.5 era).** `io_submit`/`io_getevents` offered asynchronous I/O, but in practice it was asynchronous
only for `O_DIRECT` file access and could still block during submission. It covered storage poorly and networking
not at all, which made it a niche tool for databases.

**io_uring (5.1, 2019).** Jens Axboe's design replaced both with two ring buffers shared between user space and
the kernel: a **submission queue** (SQ) where the program places operation descriptors, and a **completion queue**
(CQ) where the kernel posts results. One `io_uring_enter` call can submit and reap many operations. With
`IORING_SETUP_SQPOLL` a kernel thread polls the SQ, and steady-state I/O can need no system calls at all. Its
opcode list grew quickly to cover networking, file system calls, timeouts, multishot accept and receive, buffer
rings, zero-copy send and receive, and pass-through commands for NVMe.

**Lessons.** Keeping state in the kernel between calls (epoll) beat rebuilding it each call (poll). Sharing memory
for queues (io_uring) beat paying a system call per operation. Every gain in reach also enlarged the kernel attack
surface, which is the lesson the security community drew from io_uring.

## Current state

**Readiness versus completion.** epoll is a *readiness* API: the kernel says "you could read now", and the program
performs the read. io_uring is a *completion* API: the program says "read into this buffer", and the kernel later posts
a completion carrying the byte count. The difference shapes code structure:

| Aspect | epoll | io_uring |
|---|---|---|
| Model | Reactor (react to readiness) | Proactor (react to completion) |
| Syscalls per operation | At least one per read or write, plus `epoll_wait` | Can be fewer than one, by batching or SQ polling |
| Disk files | Not meaningful (always ready) | Real asynchronous file I/O |
| Buffer ownership | Caller owns buffers until it calls `read` | Kernel owns the buffer until completion; caller must keep it alive |
| Ordering | Events per descriptor | Completions may arrive in any order unless linked |
| Maturity | Stable since 2002; universal | Fast-moving; features depend on kernel version |

**io_uring details that bite.** The man pages in the catalog make several behaviours explicit that new users trip
over:

- completions are not ordered. Each CQE carries the `user_data` the program set at submission, and that is the only
  reliable way to match results to requests;
- if the CQ fills, newer kernels advertise `IORING_FEAT_NODROP` and hold overflowed entries internally, but the
  program should still size the CQ for its peak in-flight work and watch the overflow counter;
- ordering between submissions is opt-in, through `IOSQE_IO_LINK` chains or drain flags;
- registered files and buffers avoid per-operation lookups but must be managed carefully as the program's
  descriptor table changes.

**epoll details that bite.** `epoll_ctl` registration is tied to the *open file description*, not the descriptor
number. A duplicated descriptor that stays open keeps generating events after the original is closed. Edge-triggered
loops that stop short of `EAGAIN` hang silently.

**Who uses what.** Event loops in libuv, nginx, Redis and Go's runtime rest on epoll. Storage engines and
high-performance proxies increasingly use io_uring, and Samba ships a `vfs_io_uring` module that sends file reads,
writes and fsyncs through a ring.

**Generalised pattern.** Both are instances of *amortising the boundary*: replace many small crossings of an
expensive boundary (here, user/kernel) with shared state plus batch transfer. The same idea appears in DPDK and
AF_XDP for networking, in NVMe's own submission and completion queue pairs (which io_uring's design echoes), and in
GPU command buffers.

**Security posture.** io_uring gives unprivileged code a large, fast-changing kernel interface that bypasses the
usual syscall boundary, so seccomp filters on individual syscalls cannot see the operations inside the ring. The
practical consequences for administrators:

- Google reported in 2023 that most kernel exploits submitted to its kCTF programme went through io_uring, and it
  disabled the interface on ChromeOS and production servers while restricting it on Android;
- Docker's default seccomp profile blocks the io_uring syscalls, and RHEL ships with the `kernel.io_uring_disabled`
  sysctl set so that it is off unless an administrator enables it;
- researchers have demonstrated rootkit-style tooling that does its work entirely through ring operations, which
  avoids syscall-based detection;
- new io_uring privilege-escalation CVEs continued to appear in 2026.

Mitigation means keeping io_uring disabled where it is not needed, limiting it to a trusted group through the
sysctl, keeping kernels current, and making sure runtime security tools can observe ring operations rather than
only syscalls.

## Related and opposing views

- **"epoll is enough for networking."** Many network servers are bounded by protocol work, not syscall overhead.
  For them, io_uring adds complexity and kernel-version risk for little gain. Benchmarks that favour io_uring
  often depend on batching patterns that real request/response traffic does not have.
- **Kernel bypass.** DPDK, SPDK and AF_XDP move I/O almost entirely into user space for the most extreme
  workloads, at the cost of dedicated cores and losing the kernel's networking features.
- **Thread-per-core runtimes.** Frameworks such as Seastar and Glommio pair one ring per core with a share-nothing
  design. Others argue that work-stealing runtimes on epoll are easier to program and good enough.
- **Restricting rather than removing.** One camp argues for disabling io_uring by default everywhere. Another
  argues for better observability and for io_uring-aware LSM hooks so that it can stay on safely.

## Future direction

- More opcodes for networking (zero-copy receive, better buffer rings) and storage pass-through, which narrow the
  gap with kernel-bypass stacks.
- Stronger policy controls: BPF-based filtering of ring operations (merged for Linux 7.0), LSM hooks, per-cgroup or per-container enablement, and security
  tooling that can trace ring activity.
- Language runtimes adopting completion-based I/O by default where it is enabled, while keeping epoll as a
  fallback for locked-down hosts.
- Continued tension between performance and attack surface, which will keep distribution defaults conservative.
