# File I/O, locking and mmap: moving bytes safely between processes and storage

## Define the problem

A program that keeps data on disk has to answer four questions that look simple and are not. How do I move bytes between my memory and a file efficiently? How do I know the bytes survived a crash or power loss? How do several processes, or several threads, share the same file without corrupting it? And when should I let the kernel map the file into my address space instead of copying through buffers? Each answer involves trade-offs between speed, safety and portability, and the failure modes are quiet: a short write that nobody checked, an `fsync` that was skipped, a lock that protects nothing because another process opened the file differently, a mapping that crashes the program when the file shrinks.

This slice covers the descriptor-based interface of Linux (`open`, `read`, `write`, `pread`, `pwrite`, `readv`, `writev`, `lseek`, `ftruncate`, `fsync`, `fdatasync`, `rename`), advisory locking (`flock`, POSIX record locks, open file description locks), and memory mapping (`mmap`, `msync`, `munmap`, `madvise`, `mremap`). It assumes local filesystems such as ext4 and XFS. Asynchronous I/O (`io_uring`, `epoll`) is covered in the next topic, and filesystem internals in the kernel courses.

## History and approaches

**Unbuffered descriptors.** Unix gave programs a small integer naming an open file and two calls, `read` and `write`, which move a byte count at a position the kernel tracks. This minimal design was stable for decades. Its weak points were that the shared offset made positioned access awkward in threads, and that a single call could return less than requested. Both stayed in the contract: a short read at end of file is normal, and a short write on a pipe, socket or full disk is possible.

**Stdio buffering.** The C library added `FILE *` streams, which batch small writes into large ones in user space. This is fast for text, but it adds a second layer of buffering that the kernel does not know about, so an `fflush` is not an `fsync`, and a crash loses whatever sat in the library buffer.

**Positioned and vectored calls.** `pread` and `pwrite` carry an explicit offset and leave the descriptor's position alone, which fixes thread safety for random access. `readv` and `writev` gather several buffers in one call. Later additions such as `preadv2` and `pwritev2` accept per-call flags (for example a no-wait hint), and `copy_file_range`, `sendfile` and `splice` move data between descriptors without a trip through user space.

**Durability.** Early systems wrote data lazily and recovered with a filesystem check after a crash. Journaling filesystems (ext3 and later, XFS) protected the filesystem's own metadata but not the application's data ordering. Applications learned the hard way that "write then rename" is not durable until the file and then its directory have been flushed. A well-known episode involved ext4's delayed allocation, which made an application's replace-by-rename pattern leave zero-length files after a crash, until the filesystem added heuristics for the common pattern. The lesson was that the application, not the filesystem, owns the definition of "committed". More recent work on `O_DIRECT`, `O_DSYNC` and `RWF_` flags gives finer control.

**Locking approaches.** The first mechanism was lock files created with `O_CREAT|O_EXCL`, which breaks when a process dies without removing its file. BSD `flock` locks the whole file and is tied to the open file description, so it follows the descriptor across `fork` and `dup`. POSIX record locks via `fcntl(F_SETLK)` lock byte ranges and work over some network filesystems, but they have two harmful quirks: they belong to the process rather than the descriptor, and closing any descriptor for the file drops all of the process's locks on it. Because threads share a process, POSIX locks do not exclude one thread from another. The Linux answer is open file description locks (`F_OFD_SETLK`), which have range locking like POSIX locks but the ownership semantics of `flock`; they were standardised later and are the recommended choice for multithreaded programs on Linux. Mandatory locking, an attempt to enforce locks against processes that ignore them, was removed from the kernel because it was unreliable and could be defeated by races.

**Memory mapping.** Mapping a file into the address space came from the BSD and System V lineage. It replaced copy-in and copy-out with page faults: the first touch of a page brings it from the page cache, and the data is then reachable as ordinary memory. It also introduced a new failure class, because I/O errors and file truncation turn into signals (`SIGBUS`) rather than return codes. Shared writable mappings and the page cache write-back interact in ways that application authors had to learn through experience with databases that either embraced mapping or explicitly rejected it.

**Emerging pattern.** Each step moved some responsibility to the application: explicit offsets, explicit durability points, explicit lock ownership. The stable design today is a small set of primitives plus a rule that the application must check every return value, loop on short transfers, and define its own commit protocol.

## Current state

**Descriptors and the page cache.** `open` returns a descriptor that refers to an open file description, which holds the offset, the access mode and status flags such as `O_APPEND`. Several descriptors can share one description (via `dup` or `fork`), and several descriptions can refer to one inode. Almost all ordinary I/O goes through the page cache: a write copies data into cached pages, marks them dirty and returns; background write-back later sends them to the device. A read first looks in the cache. This makes repeated access fast and makes the timing of durability unpredictable unless the program asks.

**Correct read and write loops.** A robust transfer loop repeats until the whole count is done, treats `EINTR` as retry, returns on zero from `read` as end of file, and treats any other error as final. For `write` a short count is possible with sockets, pipes, signals and full disks, and the next call then fails with the real error (such as `ENOSPC`). `O_APPEND` makes each write atomic with respect to the offset, so concurrent appenders from several processes do not overwrite each other, but writes of different processes may interleave at write boundaries; on local filesystems a single `write` is not split by other appenders.

**Durability tools.**

- `fsync(fd)` pushes the file's data and the metadata needed to find it to stable storage; `fdatasync` skips metadata not needed to read the data back, such as timestamps.
- Creating or renaming a file changes the directory, so the directory must be synced too: open it and call `fsync` on that descriptor.
- The standard replace pattern is: write a temporary file in the same directory, `fsync` the file, `rename` it over the target (atomic on one filesystem), then `fsync` the directory.
- `O_SYNC` and `O_DSYNC` make each write durable before it returns, at a heavy cost. `O_DIRECT` bypasses the page cache for the data, requires aligned buffers and sizes, and does not by itself make the write durable.
- An error from `fsync` is serious. Linux reports a write-back failure once; after the error is delivered the pages may be marked clean, so a retry can succeed without the data being on disk. Treat a failing `fsync` as a failure of the whole transaction. This behaviour was the subject of a widely discussed database incident, after which kernel and applications changed.
- Storage may lie below the filesystem. Write caches in drives and controllers need flush support to honour the promise; this is a property of the system, not of the call.

**Locking choices.**

| Mechanism | Granularity | Owner | Notes |
|---|---|---|---|
| `flock` | whole file | open file description | Simple; not reliable on all network filesystems |
| POSIX `F_SETLK` | byte range | process | Closing any descriptor of the file drops the process's locks; not for threads |
| OFD `F_OFD_SETLK` | byte range | open file description | Best fit for threaded Linux code |
| Lock file with `O_EXCL` or a `link` trick | name | creator | Stale after a crash; needs a recovery rule |

All of these are advisory: they exclude only processes that ask for the lock. A lock is released when the owner exits or closes, which makes crash recovery automatic and is the reason to prefer descriptor locks over lock files. Deadlock detection exists for record locks (`EDEADLK`), but a design with a single lock order is better.

**mmap in detail.** `mmap` creates a mapping of a file range into memory. Choices matter:

- `MAP_SHARED` writes reach the file through the page cache; `MAP_PRIVATE` gives copy-on-write pages that never reach the file. Anonymous mappings (`MAP_ANONYMOUS`) have no file and serve as memory allocation or as shared memory between a parent and its children.
- Protection flags (`PROT_READ`, `PROT_WRITE`, `PROT_EXEC`) are checked by the hardware and violations raise `SIGSEGV`.
- `msync(MS_SYNC)` plays the role of `fsync` for the mapped range; without it, dirty pages are written back on the kernel's schedule.
- `madvise` tells the kernel the expected access pattern (`MADV_SEQUENTIAL`, `MADV_RANDOM`, `MADV_WILLNEED`, `MADV_DONTNEED`, and for hugepages `MADV_HUGEPAGE`); `mlock` pins pages in memory.
- The file's length controls what is valid: touching a page beyond the end of file raises `SIGBUS`, and so does touching a page whose file was truncated by another process or whose backing I/O fails. Extending a file needs `ftruncate` or `posix_fallocate` before the pages are used.
- `mremap` resizes a mapping, and `fallocate` reserves space, which turns a late `ENOSPC` into an early failure.

**Choosing between read/write and mmap.** Mapping removes a copy and system call overhead for random access to large read-mostly data, and it is convenient for data structures that live in the file. Plain `pread` and `pwrite` give explicit errors, predictable memory use and easier handling of files that change size. For sequential streaming the difference is small. For writes with durability requirements the explicit path is usually easier to reason about, because errors come back as return values rather than signals.

## Assessment: the good, the bad and the ugly

**The good.** The descriptor model is small and uniform, so the same code works for files, pipes and sockets with differences confined to documented corner cases. The page cache hides device latency and merges writes without effort. `rename` is atomic, which makes consistent updates possible without a database. Locks are released automatically at process death. `mmap` provides zero-copy access and shared memory with the same machinery.

**The bad.** Durability is subtle and easy to get wrong because the fast path looks identical to the safe path until a crash. Advisory locking protects nothing against a process that ignores it. POSIX lock semantics are surprising enough that large projects have documented them as a hazard. Error reporting for write-back is delayed, so the failing call may be a later `close` or `fsync`, and the application must check both. `O_DIRECT` has alignment rules that vary by filesystem and device, and is poorly specified across kernels.

**The ugly.** Network filesystems weaken guarantees: `flock` is emulated or unsupported on some, close-to-open cache consistency means one client may not see another's writes at once, and `mmap` coherence is looser. The `SIGBUS` from a mapped file is awkward to handle, as the handler cannot easily resume and the failing instruction may be anywhere in the program. Mapping a file that others may truncate is a source of production crashes. Large mappings with page faults in latency-sensitive paths cause jitter that does not show up in `strace`, because no syscall occurs. Another unpleasant area is the interaction of `fork`, buffered streams and locks: a child inherits unflushed stdio buffers, and duplicating them on exit writes data twice.

Mitigations: wrap I/O in small helpers that loop and check; use a documented commit protocol; test crash recovery with fault injection or by killing the process at chosen points; prefer OFD locks; map read-only data and copy anything that must survive truncation; and always check `fsync` and `close`.

## Applications beyond this domain

- **Databases and key-value stores** use the same primitives with write-ahead logs: append to a log, `fdatasync`, apply, and checkpoint. SQLite documents precisely which syscalls and assumptions its atomic commit relies on. Some engines choose `mmap` for read paths, others reject it for the signal and control issues listed above.
- **Package managers and editors** use write-temp-then-rename to update files atomically, and lock files or `flock` to keep two instances from changing the same database.
- **Container image layers and build caches** rely on atomic rename and on content-addressed files whose partial state is never visible under the final name.
- **Shared memory IPC** (`shm_open` plus `mmap`) is the same mapping machinery applied to an in-memory file, which links this topic to the IPC topic later in the course.
- **Virtual machine disk images** are accessed with positioned I/O, `O_DIRECT` and flush requests that mirror guest `fsync` semantics; a hypervisor that ignores flushes risks guest data loss.
- **Distributed log systems** copy the pattern of append, flush and acknowledge at cluster scale, with the same question: when exactly is a record committed?

## Examples

**A safe config update.** An administrative tool must replace `/etc/app/app.conf`. It writes `app.conf.tmp` in the same directory, calls `fsync` on that file, `rename`s it over `app.conf`, then opens the directory and calls `fsync`. A crash at any point leaves either the old file or the new file, never a mixture.

**A short write nobody checked.** A logging helper calls `write(fd, buf, len)` once and ignores the result. On a full disk, the first call writes part of the line and returns a smaller count; the helper believes the line was written. The repair is a loop that continues from the offset and stops on error, plus reporting the failure.

**A lock that vanished.** A program takes a POSIX lock on a database file, then calls a library function that opens the same file to read its header and closes that descriptor. Closing drops the program's lock, and a second process enters the critical section. Switching to an OFD lock held on the program's own descriptor fixes it.

**A crash on a shrunk file.** A viewer maps a log file and displays it. A rotation job truncates the file; the viewer touches a page beyond the new end and dies with `SIGBUS`. The viewer needed to check the size before use or switch to `pread`.

**A failing durability test.** A test kills a process between the `rename` and the directory `fsync`. After reboot on some filesystems the old file reappears. This is acceptable if the protocol defines the update as not yet committed until the directory sync returned, and the program must not acknowledge to the user before that point.

**An append race.** Two processes append lines to one log opened with `O_APPEND`; lines remain whole. Without `O_APPEND`, each process tracks its own offset and lines overwrite each other. This is a quick experiment that makes the offset ownership concrete.

## Related problems and ideas

- **Copy-free movement.** `sendfile`, `splice` and `copy_file_range` (which can use reflinks or server-side copy) reduce copying; the kernel can clone extents on filesystems that support it.
- **Atomic multi-file updates.** Filesystems and libraries have proposed atomic write calls and transactional file APIs; none is universal on Linux. Applications use a database, a rename of a whole directory, or a snapshot instead.
- **Storage models without POSIX semantics.** Object stores, log-structured stores and copy-on-write filesystems with snapshots avoid in-place update, trading random write support for easy consistency.
- **Direct access to persistent memory.** DAX mappings bypass the page cache so loads and stores reach persistent memory directly; the application must then flush CPU caches with the right instructions, a new form of the same durability problem.
- **Userspace filesystems and file-based APIs** (FUSE, and virtual filesystems such as `/proc`) reuse the file interface for non-file things, which brings these semantics to unexpected places.
- **Alternatives to locks.** Leases (`F_SETLEASE`), `inotify` for change notification, and compare-and-swap on metadata are used where advisory locks are too weak or too heavy.

## Active research

Research and engineering effort concentrates on crash consistency: tools that explore the states a filesystem may leave after a crash and check an application's recovery code against them; formal models of what `fsync` guarantees on different filesystems; and checking tools that find missing flushes or ordering mistakes in widely used software. Another area is the semantics of write-back errors and how applications and the kernel should surface them. Persistent memory programming models, userspace storage stacks that bypass the kernel, and asynchronous interfaces that carry flush and ordering requests (linked operations in `io_uring`) are also active. Open questions include how to give applications a portable transactional primitive with acceptable cost, and how to make mapped-file errors recoverable. Specific tool names and results should be confirmed against current papers before being cited (to verify).

## Future direction

Expect more per-operation flags (`RWF_*`) that give the application control over durability and caching without whole-file modes, wider use of `io_uring` for batching I/O with explicit ordering, and continued work on atomic write support in filesystems and block devices (to verify the state of atomic-write support for the kernel version in use). Larger folios in the page cache and filesystem support for them change the cost of mapping and write-back, which may shift the balance between `mmap` and explicit reads. Applications will continue to carry their own commit protocols; the safe habit is to document the sequence, test it by killing the process, and treat each filesystem and storage layer as a part of the contract.
