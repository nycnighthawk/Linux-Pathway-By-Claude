# Signals, signalfd and timerfd: asynchronous events in a synchronous program

## Define the problem

A process normally runs one line after another. But the world pushes events at it at times it cannot predict: the user presses Ctrl-C, a child exits, a timer expires, a pipe reader goes away, an illegal instruction executes, an administrator asks for a graceful shutdown or a configuration reload. The program needs a way to learn of these events, react in a bounded and safe way, and return to what it was doing, without losing data and without corrupting its own state.

Signals are Unix's original answer. They deliver a small integer number to a process or thread and interrupt whatever it was doing to run a handler. The mechanism is old, cheap and unavoidable, since the kernel itself uses it for faults (`SIGSEGV`, `SIGBUS`, `SIGFPE`) and for terminal control. It is also hard to use correctly, because a handler can run between any two instructions, in the middle of `malloc`, while a lock is held. The problem has two halves: receiving signals safely, and generating timed events without depending on the signal model. This slice covers classic and real-time signals, `sigaction`, masks, async-signal safety, the self-pipe trick, `signalfd`, `sigwaitinfo`, POSIX timers, and `timerfd`. Terminal job control is touched on in the process topic.

## History and approaches

**Original signals.** Early Unix signals reset the handler to default on delivery and could be lost if a second signal arrived before the handler re-installed itself. System V and BSD diverged on whether interrupted system calls restart. Programs written for one behaved wrongly on the other, and the C standard's `signal()` function still leaves the details unspecified.

**POSIX reliable signals.** `sigaction` fixed the semantics: the handler stays installed, the signal is blocked during its own handler, a mask can block more signals, and flags select restart behaviour (`SA_RESTART`), extended information (`SA_SIGINFO`), no-reap of children (`SA_NOCLDWAIT`) and so on. Signal masks (`sigprocmask`, and `pthread_sigmask` for threads) let a program defer delivery during critical sections. Blocked signals stay *pending* and are delivered on unblocking, though standard signals do not queue: ten `SIGCHLD` while blocked produce one delivery.

**Real-time signals.** POSIX added signals numbered from `SIGRTMIN` that queue, carry a data value (`sigqueue`), and are delivered in order. They suit application-defined notifications but are rarely used because of the same handler hazards.

**Async-signal safety.** The standard lists the functions that may be called from a handler: roughly the thin system call wrappers (`write`, `_exit`, `kill`, `sigaction`...) and nothing that uses locks or global state such as `printf`, `malloc` or most of the library. The rule exists because the handler can interrupt the same function it calls. This limited toolbox made handlers do as little as possible, typically set a `volatile sig_atomic_t` flag and return.

**The self-pipe trick.** To bring a signal into a `select` or `poll` loop, programs wrote a byte into a pipe from the handler and watched the read end. This solved the race between checking a flag and sleeping in `poll`, but needed a pipe, a handler and care with non-blocking writes. `pselect` and `ppoll` offered an atomic mask change during the wait for the same purpose.

**Threads and signals.** A signal aimed at a process goes to any one thread that does not block it. Programs in practice block signals in all threads except one dedicated thread, which calls `sigwait`, or in all threads and read them via a descriptor. Signals caused by a fault go to the faulting thread.

**Timers.** `alarm` and `setitimer` deliver `SIGALRM`, with a single timer per process and no queueing. POSIX timers (`timer_create`, `timer_settime`) added many timers per process with a choice of clock (monotonic, boot time, real time), notification by signal or thread, and an overrun count for expirations missed.

**Descriptors for events.** Linux brought events into the descriptor world. `signalfd` (2.6.22) returns a descriptor that is readable when a blocked signal is pending; reading gives a fixed `signalfd_siginfo` record. `timerfd_create` (2.6.25) returns a descriptor that becomes readable when a timer expires, and reading yields the number of expirations since the last read. `eventfd` and `pidfd` followed the same idea. The effect is that signals, timers, sockets and child exits all fit in one `epoll` loop, with no handler.

**Emerging pattern.** Treat asynchronous notifications as input, not as interrupts: block the signals, read them synchronously, and keep real handlers only for fatal faults and last-resort cleanup.

## Current state

**Disposition and delivery.** Each signal has a disposition: default action (terminate, terminate with core dump, ignore, stop or continue), ignore, or a handler. `SIGKILL` and `SIGSTOP` cannot be caught, blocked or ignored. Standard signals are not queued, so a counter of events cannot be built from them; real-time signals queue up to a limit (`RLIMIT_SIGPENDING`). Signals are checked at the transition back to user mode, so a process running a long loop in user space gets the handler at the next scheduler or interrupt return, and a process blocked in a system call is woken.

**Handler rules.**

1. Install with `sigaction`, never `signal`, and set `SA_RESTART` unless the interruption is wanted. Even so, some calls (such as `epoll_wait`, `poll`, `nanosleep`, and calls with a timeout) fail with `EINTR` and never restart.
2. In the handler do only async-signal-safe things: set a flag of type `volatile sig_atomic_t`, write to a pipe or eventfd, call `_exit`. Save and restore `errno` if the handler calls anything that could change it.
3. Use `SA_SIGINFO` when you need the sender (`si_pid`, `si_uid`), the code (`si_code`) or the fault address.
4. Fault signals must not simply return: after a `SIGSEGV` from a bad access, returning re-executes the instruction. Legitimate handlers log, remove or fix the mapping, or exit (some runtimes use this for stack overflow or guard page tricks with an alternate stack from `sigaltstack`).

**Masks and waiting.** `sigprocmask` or `pthread_sigmask` blocks signals. `sigsuspend` atomically sets a mask and sleeps; `sigwaitinfo` and `sigtimedwait` pick pending signals synchronously without any handler. The usual daemon structure blocks `SIGTERM`, `SIGHUP`, `SIGINT`, `SIGCHLD` and similar in the main thread before creating any other threads (children inherit the mask), then reads them from a `signalfd`.

**signalfd.** Create with `signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC)` after blocking those signals with `sigprocmask`. Each `read` returns one or more 128-byte `signalfd_siginfo` records (`ssi_signo`, `ssi_pid`, `ssi_uid`, `ssi_code`, `ssi_int` and more). Notes: the signals must stay blocked, or the default action still happens; standard signals are coalesced as usual; the descriptor is inherited across `fork` and `exec` with the mask caveats; a signal read from the descriptor is consumed for the process that reads it, and thread targeting differs from handler delivery; a child process that execs inherits the *blocked mask* and so may start with signals blocked, which has hurt many shells and launchers (reset the mask before `exec`).

**timerfd.** `timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC)` and `timerfd_settime` with an initial value and optional interval. A `read` returns an 8-byte count of expirations since the previous read, which handles missed ticks without loss. `CLOCK_REALTIME` timers with `TFD_TIMER_ABSTIME` and `TFD_TIMER_CANCEL_ON_SET` detect wall clock jumps; `CLOCK_BOOTTIME` includes suspend; `CLOCK_BOOTTIME_ALARM` and `CLOCK_REALTIME_ALARM` can wake the system (they need `CAP_WAKE_ALARM`). The right clock is monotonic for intervals, real for calendar events.

**POSIX timers and others.** `timer_create` can deliver a signal with a value or start a thread; `timer_getoverrun` reports missed expirations. `setitimer` virtual and profiling timers count CPU time and drive profilers. For timeouts on blocking calls, prefer the timeout argument of `epoll_wait` or `poll`; for deadlines across a loop, keep one `timerfd` per deadline class or a priority queue and one timerfd for the earliest.

**Sending signals.** `kill(pid, sig)`, `kill(-pgid, sig)`, `tgkill` for one thread, `pthread_kill`, `sigqueue` with data, and `pidfd_send_signal`, which avoids PID reuse. Permission rules: the sender's real or effective UID must match the target's real or saved UID, or the sender has `CAP_KILL`. Signal 0 tests whether a process exists and can be signalled. `SIGPIPE` is the unusual case that arises from the program's own write to a closed pipe or socket; most servers ignore it (or use `MSG_NOSIGNAL`) and handle `EPIPE`.

**An event loop skeleton.** Block the signals; create a `signalfd` and a `timerfd`; add both and the sockets to one `epoll` instance; in the dispatch switch on the descriptor. A `SIGTERM` record starts a graceful stop, `SIGHUP` reloads configuration, `SIGCHLD` runs a `waitpid` loop, and the timerfd drives periodic work. No handler runs, so no async-signal-safety rule applies, and ordinary code (allocation, logging) is allowed.

## Assessment: the good, the bad and the ugly

**The good.** Signals are universal and cheap: every Unix, every shell and every service manager speaks them. `SIGTERM`, `SIGHUP`, `SIGCHLD` and `SIGINT` give a shared vocabulary for stopping, reloading and supervising. Converting them to descriptors removes most of the danger and lets one loop handle everything. `timerfd` makes timer expiry a first-class event with missed ticks counted, and gives monotonic and boot-time clocks that survive wall clock changes.

**The bad.** Standard signals carry almost no data and are coalesced, so a program cannot count events with them. Handler context allows so few operations that most useful work must be deferred. `EINTR` leaks into every blocking call and must be handled or avoided. Signal dispositions and masks are inherited in surprising ways: ignored stays ignored across `exec`, and blocked masks stay blocked, so a child of a program that blocked `SIGINT` cannot be interrupted. Multithreaded delivery to an arbitrary thread that leaves the signal unblocked is unpredictable unless the program sets it up.

**The ugly.** A handler that calls `printf` or `malloc` works in tests and deadlocks in production, once in a million runs. Fault handlers that return loop forever. `signalfd` interacts poorly with programs that also install handlers, and with libraries (a library that unblocks signals or installs its own handler for `SIGCHLD` breaks the application's assumptions). `signalfd` descriptors do not survive in a child as the parent's reading context, and moving them between threads changes who gets the signals. The `SIGCHLD` default of "ignore" differs from explicit `SIG_IGN`, which sets auto-reaping. Real-time signal queues can overflow silently under load. Debuggers and tracers (`strace`, `gdb`) intercept signals and may alter timing. Timers have their own gotchas: wall clock jumps, daylight saving changes and drift in naive "sleep then repeat" loops.

Mitigations: block signals early in `main`, before spawning threads; use `signalfd` or a dedicated `sigwait` thread; keep handlers to a flag or a one-byte write; reset masks and dispositions in children before `exec`; use absolute deadlines on monotonic clocks to avoid drift; write a test that sends each signal to the program while it is busy and idle.

## Applications beyond this domain

- **Service managers and supervisors** use `SIGTERM` for stop, `SIGKILL` for escalation after a timeout, `SIGHUP` for reload and `SIGCHLD` for supervision. The conventions are shared across nginx, sshd, PostgreSQL and many others (each defines its own extra meanings for some signals, which should be checked per program).
- **Language runtimes** hide signals behind their own abstractions: Go's `os/signal` channels, Python's `signal` module (handlers run in the main thread between bytecodes), and Rust crates built on `signalfd` or the self-pipe pattern. Garbage collectors and profilers also use signals to stop threads (stop-the-world with a signal to each thread), which makes handler safety a runtime issue.
- **Profilers and debuggers** rely on timer signals (`SIGPROF`) to sample, and on `SIGTRAP` and `SIGSTOP` for breakpoints and stop control.
- **Kernel analogues**: interrupts and softirqs are the kernel's asynchronous events, with their own rules for what may run in each context; the discipline for a signal handler is a small version of the discipline for an interrupt handler.
- **Event-driven systems in general** (GUI loops, network daemons) turn asynchronous input into a queue read by one loop, which is exactly the move from handler to descriptor.
- **Timers** appear in network stacks (retransmission), cluster managers (lease expiry), and rate limiters; the monotonic-versus-real clock decision is the same everywhere.

## Examples

**Graceful shutdown.** A server blocks `SIGTERM` and `SIGINT`, makes a `signalfd`, and adds it to `epoll`. On a record, it stops accepting connections, finishes in-flight requests, flushes logs and exits with status 0. A supervisor's escalating `SIGKILL` after a timeout is the backstop.

**A reload that races.** A handler for `SIGHUP` parses the configuration file and frees the old one. A request thread is using the old structure at that moment, and the program crashes. Setting a flag in the handler and applying the change at a safe point in the loop (or reading a `signalfd`) avoids it.

**Lost children.** A parent installs a `SIGCHLD` handler that calls `waitpid` once. Three children exit together, one signal is delivered, and two zombies remain. The handler must loop with `WNOHANG` until it returns zero or -1.

**A periodic task with a timerfd.** A monitoring agent creates a `timerfd` on `CLOCK_MONOTONIC` with a 10-second interval. After a laptop suspend, the read returns a count greater than 1 on `CLOCK_BOOTTIME` timers, so the agent knows it missed ticks and does one catch-up run rather than many.

**A failing example: the stuck child.** A launcher blocks all signals before spawning workers so it can read them with `sigwait`. The workers inherit the mask. Their `SIGTERM` handlers never run, so the supervisor has to use `SIGKILL`. The fix is to restore the old mask in the child before `exec`.

**Fault handler with an alternate stack.** A runtime catches `SIGSEGV` on stack overflow. Because the stack is exhausted, the handler must run on a stack registered with `sigaltstack` and flagged `SA_ONSTACK`, otherwise the handler itself faults and the process dies at once.

## Related problems and ideas

- **Alternative notification channels**: `eventfd` for user-space to user-space wakeups, `pidfd` for process exit, `inotify` for files, and `io_uring` completions for operations all aim to remove the handler context altogether.
- **Structured cancellation**: instead of killing a thread with a signal, runtimes pass a cancellation token that the code checks at defined points.
- **Signals in containers**: PID 1 in a namespace does not receive signals for which it has no handler unless they come from an ancestor namespace, which is why a container's init must install handlers for `SIGTERM`.
- **Exception-style handling of faults**: some languages convert `SIGSEGV` and `SIGFPE` into exceptions through handlers, which depends on knowing the exact faulting instruction.
- **Deterministic replay tools** record signal delivery points because signals are a main source of nondeterminism.
- **High-resolution timing**: `clock_nanosleep` with absolute times and real-time scheduling for jitter-sensitive work, covered further in performance topics.

## Active research

Concerns studied now include automatic detection of async-signal-unsafe calls in handlers (static analysers and runtime checkers), better modelling of signal delivery for testing concurrency and for fuzzing (injecting signals at arbitrary points to find races), safe user-space handling of faults for language runtimes (user fault handling with `userfaultfd` and restartable sequences), and how to make signal delivery cost low under mitigations and in virtual machines. Another area is limiting the signal surface for sandboxed programs (which signals a seccomp or container profile should allow). Particular results and tool names should be confirmed against current conference papers and kernel documentation before use (to verify).

## Future direction

New kernel interfaces keep pulling asynchronous events into descriptors: `pidfd`, `io_uring` timeout and signal-like operations, and extensions to `timerfd`. Language runtimes are shifting to channel-based or descriptor-based delivery, leaving real handlers to fatal faults. Programmers should treat any new code that does significant work inside a signal handler as a defect, design shutdown and reload around `signalfd` or `sigwait`, and prefer monotonic timers for intervals. Details such as the clock IDs accepted by `timerfd` and the privileges required for alarm clocks differ across kernel versions and should be checked in the manual page for the target (to verify).
