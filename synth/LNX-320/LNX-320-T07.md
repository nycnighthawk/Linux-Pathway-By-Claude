# Inter-process communication: pipes, Unix sockets with descriptor passing, shared memory and eventfd

## Define the problem

Processes are isolated on purpose: each has its own address space, descriptors and credentials. Yet real systems are built from cooperating processes: a shell and the programs of a pipeline, a browser and its sandboxed renderers, a display server and its clients, a database server and its workers, a service manager and the services it starts. Those processes need to exchange bytes, structured messages, open files and sockets, and notifications, and sometimes to share the same memory so that large data need not be copied at all.

The mechanisms differ along several axes, and a programmer must choose among them:

- **Data model**: byte stream, discrete messages, or shared memory with no message at all.
- **Naming and access control**: how do two unrelated processes find each other, and who is allowed to connect?
- **Capacity and blocking**: what happens when a producer is faster than a consumer?
- **Cost**: copies, system calls and wake-ups per message.
- **Capability transfer**: can a process give another an already opened file, socket or memory region, instead of a name that must be opened again with the receiver's own permissions?

This slice covers anonymous and named pipes, `socketpair` and Unix domain sockets including `SCM_RIGHTS` descriptor passing and `SO_PEERCRED` credentials, POSIX shared memory and `memfd`, `eventfd` for wake-ups, and a brief comparison with message queues and System V IPC. Network sockets are in the next topic; D-Bus and similar buses are discussed as consumers.

## History and approaches

**Pipes.** The Unix pipe (1970s) connects the output of one process to the input of another through a kernel buffer, and gave the shell its pipeline composition model. It is a one-way byte stream between related processes, because an anonymous pipe can be reached only by inheriting its descriptors. Named pipes (FIFOs) extended pipes into the file system so unrelated processes can open the same name.

**System V IPC.** AT&T's System V added message queues, semaphores and shared memory segments, identified by numeric keys and listed with `ipcs`. They are not descriptors, so they cannot be used with `select` or `poll`; they persist until explicitly removed, which leaks resources after crashes; and the permission model is its own. They remain in use in some legacy databases.

**BSD sockets and Unix domain sockets.** Berkeley sockets unified network and local communication. A Unix domain socket, bound to a path in the filesystem (or in the Linux abstract namespace), provides stream, datagram or sequenced-packet semantics between processes on one host, with file-permission-based access control. Two features made them the preferred local IPC: the kernel can tell the receiver the sender's credentials (process ID, user ID, group ID), and the sender can attach open descriptors to a message (`SCM_RIGHTS`), which the kernel duplicates into the receiver. The latter makes it possible to give another process access to an open file or socket without names or permissions problems, and it is the basis of capability-style designs.

**POSIX IPC.** POSIX specified message queues (`mq_*`), semaphores and shared memory (`shm_open`) with names that look like paths. On Linux, `shm_open` objects live on a `tmpfs` mounted at `/dev/shm`, so a shared-memory region is just a file mapped by several processes. The queues have limits on size and count, and are seldom used compared to sockets.

**Pipes with more capability.** Linux added `pipe2` with `O_CLOEXEC` and `O_NONBLOCK`, `O_DIRECT` packet mode, resizable buffers (`F_SETPIPE_SZ`), `splice`, `tee` and `vmsplice` to move data between descriptors without copying through user space, and later work that made pipe buffers a building block for `io_uring` and `sendfile` paths.

**Wake-up primitives.** Programs often needed only to say "something happened". Signals are awkward in event loops; a pipe works but wastes two descriptors and a buffer. `eventfd` (2.6.22) provides a single descriptor holding a 64-bit counter: writes add to it, reads return and reset it (or decrement it in semaphore mode), and it is pollable. Kernel subsystems use it for notification (KVM's irqfd and ioeventfd, vhost, `io_uring` completions), which made it a core mechanism of virtualization stacks.

**Anonymous memory files.** `memfd_create` (3.17) creates an anonymous file in memory with no name in any filesystem. It can be sized, mapped, sealed (`F_SEAL_WRITE`, `F_SEAL_SHRINK`, `F_SEAL_GROW`, `F_SEAL_SEAL`) and passed over a Unix socket. Sealing lets a sender hand over a buffer that it can no longer change, which solves the time-of-check to time-of-use problem when a receiver validates data in shared memory.

**Local buses.** Higher-level systems layered on sockets: X11's protocol, D-Bus, Wayland and many daemons use Unix sockets for control and shared memory or passed descriptors for bulk data. The pattern has been stable since: a small message channel for commands and a side channel for large buffers.

**Emerging pattern.** Use a Unix socket for control, credentials and capability passing; use shared memory (preferably `memfd`) for bulk data; use `eventfd` or the socket itself for wake-ups; use plain pipes for simple one-way byte flows between related processes.

## Current state

**Pipes.** `pipe2(fds, O_CLOEXEC)` returns a read end and a write end. The kernel holds a buffer of 64 KiB by default (16 pages), adjustable with `F_SETPIPE_SZ` up to a system limit. A write of at most `PIPE_BUF` (4096 bytes on Linux) bytes is atomic, so concurrent writers' records do not interleave. A full pipe blocks the writer (or returns `EAGAIN` in non-blocking mode); an empty pipe blocks the reader. When all write ends are closed, a read returns 0 (end of file); when all read ends are closed, a write raises `SIGPIPE` and fails with `EPIPE`. Hence the rule: **close the ends you do not use**, in every process that holds a copy, or an end of file never arrives. FIFOs are opened with `mkfifo` and `open`, where opening one end blocks until the other end is opened unless `O_NONBLOCK` or `O_RDWR` is used.

**Unix domain sockets.** `socket(AF_UNIX, SOCK_STREAM | SOCK_CLOEXEC, 0)` for a stream; `SOCK_DGRAM` for datagrams that preserve boundaries and are reliable locally; `SOCK_SEQPACKET` for connection-oriented messages with boundaries, which is often the best fit for structured protocols. `socketpair` creates two connected sockets without any name, convenient between a parent and a child. Addresses are filesystem paths (permissions of the socket file and its directory control who can connect, and the file persists after exit so must be unlinked) or abstract names starting with a null byte (no file, tied to the network namespace, no permission check beyond credentials). `SO_PEERCRED` returns the credentials the peer had when it connected; `SO_PASSCRED` and `SCM_CREDENTIALS` deliver credentials with each message; `SO_PEERSEC` and `SO_PEERPIDFD` expose the security label and a pidfd of the peer in newer kernels (to verify the version).

**Descriptor passing.** Use `sendmsg` with a `msghdr` whose ancillary data (`cmsghdr` with `SOL_SOCKET` and `SCM_RIGHTS`) carries an array of descriptors, with at least one byte of ordinary data in the message. The receiver calls `recvmsg` with room for ancillary data (`MSG_CMSG_CLOEXEC` sets close-on-exec on received descriptors) and gets fresh descriptor numbers that share the sender's open file objects. Points to check: the control buffer must be sized with `CMSG_SPACE` and read through the `CMSG_*` macros; truncation (`MSG_CTRUNC`) loses descriptors; each message can carry a limited number (`SCM_MAX_FD`, 253); a descriptor in flight counts against the receiver's limits and can be abused for denial of service if the receiver does not read, so the kernel garbage-collects cycles of in-flight descriptors.

**Shared memory.** `shm_open("/name", O_CREAT|O_RDWR, 0600)`, `ftruncate` to the size, `mmap(MAP_SHARED)` in each process, and `shm_unlink` when done. `memfd_create("name", MFD_CLOEXEC | MFD_ALLOW_SEALING)` avoids the global name; pass the descriptor over a Unix socket. Synchronisation is the programmer's job: shared memory has no built-in notion of "ready". Use process-shared mutexes and condition variables (initialised with `PTHREAD_PROCESS_SHARED` in the shared region), futexes directly, semaphores, or atomics with an `eventfd` for waiting. A ring buffer with a single producer and a single consumer using acquire/release atomics for the head and tail indexes needs no lock. Treat everything read from shared memory as untrusted input that can change while you look at it; copy it to private memory before validating, or seal it. Memory mapped by an untrusted process can be truncated underneath you (`SIGBUS`) unless the file was sealed against shrinking.

**eventfd.** `eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC)`. A `write` of an 8-byte integer adds to the counter; a `read` of 8 bytes returns the value and sets it to zero (or, with `EFD_SEMAPHORE`, returns 1 and decrements). It becomes readable when the counter is non-zero and writable when a write will not overflow, so it works in `epoll`. It can be shared across processes by passing the descriptor, and it is the usual way for a worker thread or process to wake an event loop.

**System V and POSIX queues.** `msgget`/`msgsnd`/`msgrcv`, `semget`, `shmget` and `mq_open` remain available. They do not integrate with descriptors (POSIX queues do appear as descriptors on Linux and can be polled). Prefer sockets for messaging.

**Security and policy.** A Unix socket's permissions are enforced at connection time via the file. Servers should check `SO_PEERCRED` before trusting a peer and must remember that a PID can be recycled (use a `pidfd` where possible). Descriptors received over a socket carry the access rights of the open file description, not of the receiving process, so receiving a descriptor can raise privilege: sandbox helpers use this deliberately, and servers must be careful what they accept. LSMs, namespaces and seccomp filters can restrict `connect`, `sendmsg` and the use of ancillary data. Abstract sockets are scoped by network namespace, which matters inside containers (to verify details for the target kernel).

**Choosing.**

| Need | Choice |
|---|---|
| One-way byte stream, related processes | pipe |
| Unrelated processes, simple names | Unix socket path |
| Message boundaries, ordered, reliable | `SOCK_SEQPACKET` or datagram |
| Pass an open file or socket | `SCM_RIGHTS` |
| Authenticate the peer locally | `SO_PEERCRED` |
| Large data, repeated access | shared memory plus an event channel |
| Cheap wake-up | `eventfd` |

## Assessment: the good, the bad and the ugly

**The good.** Everything on Linux that matters here is a descriptor, so one `epoll` loop can wait on pipes, sockets, `eventfd` and `pidfd` alike. Unix sockets give reliable ordered delivery, credentials and capability transfer at low cost. Shared memory has the lowest per-byte cost, with no copies. Closing a descriptor, or the death of the process, cleans up the kernel state, and files in the filesystem follow ordinary permission rules.

**The bad.** Pipes carry no message boundaries beyond the atomic-write rule, so protocols need framing. Shared memory moves all the hard problems (synchronisation, lifetime, validation, hostile writers) into the application. Named objects (FIFOs, socket files, POSIX shared memory and queues) outlive crashes and must be cleaned up. There is no portable way to wait on several IPC types at once outside Linux descriptors. System V IPC objects leak.

**The ugly.** A forgotten write end keeps a pipeline from ever finishing. `SIGPIPE` kills programs that never expected it. A server that does not read ancillary data leaks descriptors and eventually exhausts limits. Time-of-check/time-of-use races in shared memory have produced real security vulnerabilities in browsers and daemons. Stale socket files make a restart fail with `EADDRINUSE` until unlinked, and unlinking blindly can remove a live peer's socket. Abstract sockets bypass filesystem permissions and are visible to every process in the network namespace. Credentials can be misleading across PID namespaces unless translated by the kernel (as `SO_PEERCRED` does) and unless the receiver understands that the peer may have changed identity after connecting (for example via `setuid`).

Mitigations: close unused descriptors immediately after `fork`; use `O_CLOEXEC` everywhere; frame messages explicitly; use `SOCK_SEQPACKET` where boundaries matter; seal and copy shared buffers; design shared-memory formats with explicit versioning and size fields; handle `SIGPIPE` and `EPIPE`; unlink socket files at start only after checking that no server answers.

## Applications beyond this domain

- **Shell pipelines and build systems** use pipes for streaming and a jobserver (tokens in a pipe) for limiting parallelism across processes.
- **Display servers** such as Wayland use a Unix socket for protocol messages and pass buffers as shared memory descriptors, so clients draw into memory the compositor maps directly.
- **D-Bus** carries messages over Unix sockets with credential checks, and passes file descriptors as a native type for devices and files; systemd uses it and private sockets for control.
- **Browsers and sandboxes** split work into a privileged broker and a restricted renderer. The broker opens files and sockets the renderer is not allowed to open and passes them over a socketpair. This is the capability pattern in practice.
- **Service managers** hand pre-opened listening sockets to services (socket activation) and pass them by inheritance or `SCM_RIGHTS`.
- **Virtualization**: QEMU and vhost-user backends exchange file descriptors for guest memory and `eventfd` doorbells over a Unix socket, so a device implementation in another process maps guest memory and signals the guest without copying. This ties the topic directly to the hypervisor courses.
- **Distributed analogues**: the split of a small control channel from a bulk data channel appears again in RDMA and in storage protocols.

## Examples

**A pipeline that never ends.** A parent creates a pipe, forks a child that reads from it, and writes data. When it finishes, it closes its write end, but it still holds the read end open and, worse, a second child inherited the write end. The reader never sees end of file. The cure is to close every unused end in every process.

**A fd-passing broker.** A sandboxed worker asks a broker to open `/var/data/report.csv`. The broker validates the path against policy, opens the file read-only, and returns the descriptor with `SCM_RIGHTS` in a `sendmsg` carrying one status byte. The worker receives it with `MSG_CMSG_CLOEXEC` and reads the file without ever having permission to `open` anything.

**A shared ring with an eventfd.** Producer and consumer map a `memfd` region holding a ring buffer header (head, tail, capacity) and data. The producer writes entries, publishes the new head with a release store, and writes 1 to an `eventfd` if the consumer had marked itself sleeping. The consumer sleeps in `epoll`, wakes on the `eventfd`, reads the head with acquire semantics, and processes entries. A flag check before sleeping avoids a lost wake-up.

**A TOCTOU in shared memory.** A server maps a client-supplied buffer, checks that a length field is below a limit, and then uses the field again to copy data. The client changes the field between check and use, causing an out-of-bounds copy. The server must read the field once into a local variable, or have the buffer sealed before checking.

**A failing example: the stale socket.** A daemon crashes and leaves `/run/app.sock`. On restart `bind` fails with `EADDRINUSE`. A naive fix calls `unlink` unconditionally; when two instances start together, the second removes the first's live socket and both run, with clients connected to the wrong one. A safe start connects first; only if the connection is refused does it unlink and bind, ideally under a lock file.

**Peer credentials.** A privileged helper accepts requests on a Unix socket, reads `SO_PEERCRED`, finds UID 1000, and refuses an action reserved for root. The check came from the kernel and could not be forged by the client.

## Related problems and ideas

- **Message-oriented kernels and capability systems**: microkernels make IPC the central primitive and pass capabilities explicitly; Linux grew similar features piecemeal (`SCM_RIGHTS`, `pidfd_getfd`, seccomp user notification).
- **Kernel bypass IPC**: shared-memory transports in HPC and trading systems avoid even the system calls that sockets need, at the cost of busy-polling cores.
- **Bus-style IPC in the kernel**: attempts to merge D-Bus semantics into the kernel (kdbus, bus1) were rejected; user-space brokers remained, with `AF_UNIX` improvements instead. Binder, in Android's kernel, provides transaction-style IPC with object references and is also in the mainline tree.
- **Structured serialisation**: Protocol Buffers, FlatBuffers and similar formats attach schemas to messages sent over any of these channels, and zero-copy formats read directly from shared memory.
- **Cross-VM and cross-host variants**: `AF_VSOCK` gives a socket interface between a guest and its host, and carries the same programming model across the virtualization boundary.
- **Alternative: threads in one process**, giving up isolation for simplicity, or WebAssembly-style component boundaries enforced by a runtime.

## Active research

Research and engineering focus on making cross-process boundaries cheaper and safer: zero-copy transports with memory protection keys, hardware-assisted isolation inside a process as an alternative to IPC, fast capability-checked calls, and formal verification of descriptor-passing protocols in sandboxes. In the kernel, work continues on reducing the cost of `AF_UNIX` (garbage collection of in-flight descriptors was reworked after security reports), on `pidfd`-based peer identification, and on better limits and accounting for passed descriptors. Studies of vulnerabilities in IPC-heavy software, such as browsers, motivate verified message parsers and safer shared-memory idioms. Exact kernel changes and their versions need checking against release notes (to verify).

## Future direction

Expect `memfd` with sealing and `pidfd` to become the default building blocks for new designs, with named global objects declining. Wider adoption of `AF_VSOCK` and vhost-user will make the descriptor-passing and `eventfd` model the standard for virtualization devices. Rust and other memory-safe languages will move more parsing of shared data into verified libraries. New kernel interfaces will likely expose more credential and identity information safely (pidfd for peers, security labels) and tighten limits on descriptors in flight. Programmers should design new local services around a `SOCK_SEQPACKET` or stream socket with explicit framing, authenticate with peer credentials, and use shared memory only after measuring a need.
