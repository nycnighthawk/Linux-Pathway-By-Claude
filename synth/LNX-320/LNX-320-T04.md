# fork, exec, wait, sessions and daemons: creating and supervising processes

## Define the problem

Every useful Linux system is a tree of processes, and every program that starts another has to solve the same set of problems. How is a new process created and given the right program, arguments, environment and open files? How does the parent learn that it ended, and why? What happens to a process whose parent disappears? How is a long-running background service detached from the terminal that started it? How do job control, signals from the keyboard and process groups fit in? A wrong answer shows up as zombie processes, leaked descriptors that keep sockets open, services that die when the user logs out, and shells that hang waiting for a pipe that a stray child still holds.

This slice covers the classic trio `fork`, `execve` and `wait`; the variants `vfork`, `posix_spawn` and `clone`/`clone3`; process identity (PIDs, process groups, sessions, controlling terminals); orphan and zombie handling including subreapers and `pidfd`; and the daemon problem both in its traditional double-fork form and in its modern form under a service manager. Threads are covered in the pthreads topic, signals in their own topic, and containers and namespaces later in the course.

## History and approaches

**Creation by copying.** Early Unix created processes with `fork`, which duplicates the caller, and replaced the program with `exec`. Splitting creation and loading looked odd but proved powerful: between the two calls the child can change its own state, such as redirecting descriptors, dropping privileges or setting limits, using ordinary system calls instead of a large "spawn options" structure. A shell implements redirection exactly this way.

**The cost of copying.** Early implementations really copied the address space, which made `fork` expensive and wasteful when it was followed at once by `exec`. Copy-on-write fixed the memory cost: parent and child share pages marked read-only and the kernel copies a page only when one side writes. But copying the page tables of a large process still costs time proportional to its size, and a copy-on-write fork of a process with many gigabytes of mapped memory can pause it noticeably. This pushed several alternatives:

- **vfork** (BSD): the child borrows the parent's address space and the parent is suspended until the child calls `exec` or exits. Fast but dangerous: the child may do almost nothing before `exec`, because it shares the stack.
- **posix_spawn**: a library function taking file actions and attributes, standardised so that systems without cheap `fork` could implement it. glibc builds it on a `clone` variant with `CLONE_VM`-style sharing, avoiding the copy.
- **clone and clone3**: the Linux primitive underlying `fork`, threads and namespaces. Flags choose what is shared (address space, descriptor table, filesystem info, signal handlers, thread group) or created fresh (namespaces). `clone3` takes an extensible structure and can return a `pidfd` directly.

**Waiting and reaping.** The parent learns of a child's end through `wait`, `waitpid` and `waitid`. Until it does, the kernel keeps a small record (exit status, resource use) so the information is not lost; the dead child in that state is a zombie. This design guarantees that a parent can always fetch the status, at the price that a parent who never waits accumulates zombies. A `SIGCHLD` signal tells the parent that a state change happened, but signals coalesce, so a handler must loop on `waitpid(-1, ..., WNOHANG)`.

**Orphans and init.** When a parent exits first, its children are re-parented to PID 1 (or to the nearest ancestor marked as a *subreaper* with `prctl(PR_SET_CHILD_SUBREAPER)`), which reaps them. Init systems and container runtimes are written with this duty in mind; a program running as PID 1 inside a container that ignores it accumulates zombies.

**Sessions, groups and terminals.** Unix modelled a login as a session, with one session leader, one controlling terminal and, within the session, process groups. One group at a time is the foreground group of the terminal; the keyboard's interrupt and stop characters send signals to the whole foreground group, and `SIGHUP` goes to the group when the terminal closes. Job control in shells is built on `setpgid`, `tcsetpgrp` and `SIGTSTP`/`SIGCONT`.

**The daemon recipe.** To run in the background a process had to detach from its terminal. The traditional recipe: `fork` and let the parent exit (so the child is not a group leader); `setsid` to become leader of a new session with no controlling terminal; `fork` again so the process can never reacquire a terminal by opening one; `chdir("/")` to avoid holding a mount; reset `umask`; close all descriptors and reopen 0, 1 and 2 on `/dev/null`; write a PID file. Libraries wrapped this as `daemon(3)`. The recipe worked but was fragile: PID files go stale, a double fork hides the service's PID from its starter, and a restart policy needs a supervisor that can wait on its own child.

**Supervision.** Service managers (init scripts, then daemontools, runit, upstart and systemd) reversed the idea: the service stays in the foreground, the manager is its parent, and the manager tracks it, restarts it, collects its output and cleans up the whole group. systemd's documentation distinguishes "old-style" daemons, which do the traditional dance, from "new-style" daemons, which do not, and recommends the latter.

**Emerging pattern.** The field moved from a process that hides itself to a process that is a well-behaved child of a supervisor, and from implicit inheritance of descriptors to explicit control with close-on-exec flags, `closefrom`/`close_range`, and file actions.

## Current state

**fork.** `fork()` returns twice: the child's PID in the parent and 0 in the child. The child gets a copy of the descriptor table (sharing the open file descriptions), a copy of memory, the same signal dispositions and the same working directory and environment; it does not inherit pending signals, timers, record locks held by the parent, or other threads. In a multithreaded program only the calling thread exists in the child, so the child must call only async-signal-safe functions until it execs; locks held by other threads at the time of fork stay locked forever in the child, which is why `malloc` and `printf` after `fork` in threaded programs are dangerous (glibc takes care for its own allocator, but user locks are not handled).

**exec.** `execve(path, argv, envp)` replaces the program image. The PID remains. Descriptors stay open unless marked `FD_CLOEXEC` or opened with `O_CLOEXEC`, so a careless descriptor leaks into the new program. Signal handlers are reset to default, but ignored signals stay ignored and the signal mask is kept, which is a classic source of children that cannot be interrupted. Set-user-ID bits change the effective identity, and `AT_SECURE` makes the C library ignore dangerous environment variables. The `exec` family (`execl`, `execvp` and so on) only varies how arguments and path search are given. `fexecve` and `execveat` run a program from a descriptor.

**wait.** `waitpid(pid, &status, options)` waits for one child or any (`-1`). Status is decoded with `WIFEXITED`, `WEXITSTATUS`, `WIFSIGNALED`, `WTERMSIG`, `WIFSTOPPED` and related macros; a shell's `$?` of 128+n for a signal death comes from this encoding. `WNOHANG` polls, `WUNTRACED` and `WCONTINUED` report job-control changes, and `waitid` offers more precise options including leaving the child waitable. If `SIGCHLD` is ignored (or `SA_NOCLDWAIT` is set), children are reaped automatically and `wait` fails with `ECHILD` after all have ended, a trick that avoids zombies when the status is not needed.

**pidfd.** `pidfd_open(pid)` or `clone3` with `CLONE_PIDFD` gives a descriptor that refers to one process for its whole life, immune to PID reuse. It is pollable (readable when the process ends) so it fits in `epoll`, works with `waitid(P_PIDFD, ...)`, and supports `pidfd_send_signal`. This removes the race in which a PID is recycled between the lookup and the `kill`, and it lets event loops supervise children without a signal handler.

**posix_spawn and spawning patterns.** For the common case of starting a program with a few redirections, `posix_spawn` with file actions avoids both the copy cost and the post-fork hazards of a threaded program. For servers with large memory, prefer it or `vfork`-style helpers; for shells and tools that need arbitrary child setup, `fork` and `exec` remain. A common robust pattern reports exec failure to the parent: create a pipe with `O_CLOEXEC`, `fork`, in the child call `exec` and on failure write `errno` into the pipe and `_exit`; the parent reads the pipe, seeing end of file if `exec` succeeded (the descriptor closed by itself) and the errno if it did not.

**Sessions and groups.** `setsid()` creates a new session if the caller is not a group leader; the caller becomes session and group leader and has no controlling terminal. `setpgid` puts processes into groups; `kill(-pgid, sig)` signals a whole group, which is how a supervisor stops a pipeline. `getsid`, `getpgid` and `tcgetpgrp` inspect the state. A process in a background group that reads from the terminal receives `SIGTTIN`; one that writes with `TOSTOP` set receives `SIGTTOU`.

**Daemons today.** Under a service manager the recommended behaviour is simple: stay in the foreground, log to standard error or the journal, report readiness through a notification mechanism when startup is complete, handle `SIGTERM` as the stop request, and let the manager handle restarts and cleanup. Only when a program must run without a manager is the traditional daemonisation useful, and then it should: double fork, `setsid`, set `umask`, `chdir`, redirect the three standard descriptors, close the rest, and write the PID file atomically after the second fork. Control groups give the manager a reliable way to find and kill every process of a service, including children that escaped their parent.

**Limits and accounting.** `RLIMIT_NPROC`, the pids cgroup controller and `kernel.pid_max` limit how many processes exist; `fork` fails with `EAGAIN` when a limit is reached, and with `ENOMEM` when memory or overcommit policy refuses. Programs must handle both rather than assuming creation succeeds.

## Assessment: the good, the bad and the ugly

**The good.** The fork-then-exec split gives the child full control of its setup with ordinary calls. Copy-on-write makes `fork` cheap for small processes. The wait model never loses a status. Process groups and sessions give job control with little code. `pidfd` finally gives a stable handle for a process. Service managers make daemonisation largely unnecessary.

**The bad.** Inheritance by default is the root of many bugs: open descriptors, the signal mask, ignored signals, environment variables and resource limits all flow to children unless cleared. The `fork` of a multithreaded program leaves a child in a state where almost nothing is safe, yet the library offers `pthread_atfork` handlers whose use is itself fragile. Zombie handling requires every parent to take responsibility. `SIGCHLD` handlers that call `wait` once miss coalesced signals. PID reuse can cause a delayed `kill` to hit a stranger.

**The ugly.** `fork` of a large process stalls it while page tables are copied, and under memory overcommit limits a fork may fail even though the child would exec immediately; this surprises database and runtime authors. `vfork` rules are hard to obey, since any call that touches the stack in the child can corrupt the parent. The traditional daemon recipe has many steps whose purpose is no longer obvious, so imitated code often omits one (commonly closing descriptors or redirecting standard streams, which leaves a daemon holding the terminal's pipe so that an `ssh` session or a CI step never finishes). A process running as PID 1 in a container that does not reap becomes a zombie factory. Terminal handling (`SIGHUP`, `SIGTTOU`, orphaned process groups) has accumulated special cases that few programmers know in full.

Mitigations: open everything with `O_CLOEXEC`; use `close_range` or file actions to prune descriptors in children; reset the signal mask and dispositions before `exec`; use `pidfd` and `waitid` in event loops; use a process supervisor or a minimal init as PID 1 in containers; test spawn paths under `RLIMIT_NPROC` and low memory.

## Applications beyond this domain

- **Shells and build systems** are fork-and-exec engines. Their pipelines, redirection, job control and parallel builds (`make -j` with a jobserver passed through inherited descriptors) all rest on the same primitives.
- **Container runtimes** create processes with `clone3` and namespace flags; the init process of a container is the reaper of all its processes, and tools such as `tini` exist for that role.
- **Web servers and language runtimes** use pre-fork or worker models: a master process forks workers and replaces them on exit, with the master doing little more than `waitpid` and signal handling. The model also gives memory isolation between requests and crash containment.
- **Sandboxes and privilege separation** (OpenSSH, browsers) fork helpers that drop privileges or enter a seccomp filter, and communicate by passing descriptors.
- **Test frameworks** fork per test to isolate crashes and capture exit status.
- **Distributed systems** use the same supervisor idea: a parent restarts failed children, and a heartbeat plays the role of `wait`. Erlang-style supervision trees are a language-level version.

## Examples

**A shell pipeline.** For `a | b`, the shell creates a pipe, forks twice, in each child `dup2`s the pipe end onto standard output or input, closes the other ends, places both children in a new process group, execs, and waits for both. If it forgets to close the write end in the parent, `b` never sees end of file.

**A zombie farm.** A monitoring daemon spawns a helper script every minute with `fork`/`exec` and never calls `wait`. `ps` shows thousands of `<defunct>` entries until the PID limit is hit and `fork` fails with `EAGAIN`. Setting `SIGCHLD` to ignore, or reaping in a loop, ends it.

**A daemon that holds an ssh session open.** A start script runs `ssh host 'service-start &'`. The session never returns, because the background process still holds the standard output pipe that `ssh` waits to see closed. Redirecting the three standard streams to `/dev/null` (or `setsid` plus redirect) solves it.

**A leaked descriptor.** A server opens a listening socket without `O_CLOEXEC` and spawns a CGI-style helper. After the server restarts, the old socket stays open in a helper that is still running, so the port stays bound and the new server fails with `EADDRINUSE`.

**A failing example: fork in a threaded program.** A program with a logging thread calls `fork`; at that moment the logging thread holds an internal lock. The child tries to log before `exec`, blocks forever on the lock, and the parent waits forever. The fix is to call only async-signal-safe functions in the child, or to use `posix_spawn`.

**Subreaper.** A build tool sets `PR_SET_CHILD_SUBREAPER` so that grandchildren that double-fork away are re-parented to it, and it can wait for every process in the job before declaring the step finished.

## Related problems and ideas

- **Process creation without copying**: `posix_spawn`, `vfork` and proposals for a "clean-slate" spawn call with explicit lists of inherited resources aim to avoid the inheritance by default problem.
- **Handles instead of numbers**: `pidfd` extends the idea that a descriptor, not an integer, should name a kernel object; similar moves exist for mounts and namespaces.
- **Containers and VMs as a bigger boundary**: instead of supervising processes, a platform may supervise whole namespaces, cgroups or virtual machines, with the same needs for reaping and cleanup.
- **Unikernels and single-process systems** deny the problem by having no process creation at all.
- **Actor and green-thread runtimes** create units of work in user space at far lower cost, and give up the kernel's isolation and signal-based control.
- **Checkpoint and restore** (CRIU) treats a process tree as data to be saved and recreated, which reveals how much hidden state processes carry.

## Active research

Work in this area includes the cost and safety of `fork` for large programs (studies that argue it should be retired as a general-purpose primitive and replaced by explicit spawn APIs), kernel changes that speed up copying of page tables, ways to make process creation cheaper in microservice and serverless settings (snapshot-based cold starts), and improved handles and lifecycle tracking for processes (`pidfd` extensions, process-level cgroup operations). Operators and researchers also study the semantics of orphaned process groups and terminal handling for security, and tools that verify a spawn path closes everything it should. Which specific proposals have been merged should be checked against the kernel and glibc release notes (to verify).

## Future direction

Expect wider use of `pidfd` and `clone3` in libraries, so that event-driven programs supervise children through descriptors rather than signals, and gradual support in language runtimes for spawn APIs that avoid `fork` in large processes. Service managers will continue to replace hand-written daemons, with socket activation and readiness notification as standard. Container and sandbox runtimes will keep tightening what a child inherits. Programmers writing new code should assume the supervisor model, set `O_CLOEXEC` everywhere, and keep the traditional daemon recipe as a documented fallback rather than the first choice. Names and availability of newer calls such as `close_range` or `process_madvise` depend on kernel and glibc versions and should be checked against the target system (to verify).
