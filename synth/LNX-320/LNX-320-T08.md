# Sockets and non-blocking servers: serving many peers from few threads

## Define the problem

A server must accept connections from many clients, read their requests, write replies and keep working when some clients are slow, malicious or gone. A client must find a server by name, connect despite failures of one address family or one address, send data and cope with partial results. Between the application and the wire sit a protocol stack (TCP, UDP, IP), kernel buffers, a name resolver and the network itself, and each adds behaviours the programmer must respect: bytes in a stream have no message boundaries; a `write` that returns success has not been delivered; a peer can vanish without a goodbye; a slow reader backs the writer up; a flood of connections exhausts descriptors.

The question this topic answers is how to write the programs on both ends so that they are correct (every byte accounted for, every error handled), efficient (no thread per connection unless the load calls for it) and robust (limits, timeouts and orderly shutdown). It covers the Berkeley sockets API on Linux for TCP and UDP over IPv4 and IPv6, name resolution with `getaddrinfo`, the lifecycle calls (`socket`, `bind`, `listen`, `accept4`, `connect`, `shutdown`, `close`), key socket options, non-blocking I/O with partial reads and writes, backpressure, and the main server architectures. Readiness notification (`epoll`) and `io_uring` are in a previous topic; TLS and application protocols are out of scope; kernel network internals are in the kernel courses.

## History and approaches

**Berkeley sockets.** The sockets API appeared in BSD in the early 1980s and became the standard network interface. It models a communication endpoint as a descriptor, with calls specialised by address family and type. Because the descriptor is an ordinary file descriptor, `read`, `write` and `close` also work, and later `select` and `poll` could watch many sockets at once.

**One process or thread per connection.** The first servers forked per client (the pattern of `inetd` and early web servers) or created a thread per client. This is simple, since each handler can use blocking calls in straight-line code, and it isolates failures. It does not scale: stacks and scheduler cost grow with connections, and most connections are idle. The C10K discussion at the end of the 1990s stated this as an engineering problem.

**Event-driven servers.** The answer was one or a few threads using readiness notification and non-blocking sockets. nginx, lighttpd, Node.js and libevent-style libraries took this approach. Each connection becomes a state machine: waiting to read a request, parsing, writing a response, closing. The code is harder to write but cost per connection falls to a few kilobytes.

**Hybrid and multi-core designs.** A single event loop uses one core. Servers then ran one loop per core, either with worker threads sharing a listener or with separate processes. Linux added `SO_REUSEPORT` (3.9), which lets several sockets bind to the same port and has the kernel distribute incoming connections among them, avoiding the shared accept queue's contention and the "thundering herd" of all workers waking for one connection. Accept variants and `EPOLLEXCLUSIVE` addressed the same herd.

**Name resolution and dual stack.** Early programs called `gethostbyname` and assumed a single IPv4 address. IPv6 and multi-homed hosts led to `getaddrinfo`, which returns a list of candidate addresses in preference order for a given name and service, independent of address family. The lesson of the IPv6 transition was that clients must try more than the first address; a "Happy Eyeballs" algorithm (RFC 6555, revised by RFC 8305) races connections to IPv6 and IPv4 with a small delay to avoid long timeouts when one family is broken.

**TCP specification and behaviour.** TCP provides a reliable, ordered byte stream with flow control (receiver window), congestion control, and a connection setup and teardown. The current specification is RFC 9293. Linux implements many options beyond the specification: selectable congestion control algorithms, TCP Fast Open, `TCP_NODELAY`, keepalive tuning, user timeout, and autotuning of buffers. The behaviours that surprise programmers (Nagle's algorithm plus delayed acknowledgements adding 40 ms latency; the `TIME_WAIT` state; resets on unread data) all come from the protocol rather than from Linux.

**Zero-copy and offload.** `sendfile`, `splice` and `MSG_ZEROCOPY` reduce copying, and `io_uring` adds zero-copy send and receive. Hardware offloads (checksum, segmentation) are mostly invisible to the application but affect packet captures and measurement.

**Emerging pattern.** One event loop per core, non-blocking descriptors, explicit per-connection state with buffers and limits, kernel-assisted load distribution with `SO_REUSEPORT`, and timeouts everywhere.

## Current state

**Server lifecycle.**

1. Resolve the local address with `getaddrinfo(NULL, port, hints with AI_PASSIVE)`, or build a `sockaddr_in6` with `IPV6_V6ONLY` cleared to accept both families on one socket.
2. `socket(family, SOCK_STREAM | SOCK_NONBLOCK | SOCK_CLOEXEC, 0)`.
3. Set `SO_REUSEADDR` so a restart can bind while old connections sit in `TIME_WAIT`. (On Linux this does not allow two listeners on the same port; `SO_REUSEPORT` does.)
4. `bind`, then `listen(fd, backlog)`. The backlog bounds the queue of completed connections not yet accepted (capped by `net.core.somaxconn`); a separate queue holds half-open connections and is governed by SYN-cookie behaviour.
5. In the event loop, when the listener is readable, call `accept4(fd, NULL, NULL, SOCK_NONBLOCK | SOCK_CLOEXEC)` repeatedly until `EAGAIN`. Handle `EMFILE`/`ENFILE` (out of descriptors): keep a spare descriptor to accept and close, or temporarily stop accepting, otherwise the listener stays readable and the loop spins.
6. Close each connection explicitly, and handle `ECONNABORTED` and similar transient accept errors by continuing.

**Client lifecycle.** Resolve with `getaddrinfo`; for each candidate create a socket and `connect`. With a non-blocking socket, `connect` returns `EINPROGRESS`; wait for writability, then read `SO_ERROR` with `getsockopt` to learn the result. Retry the next address on failure, with a total deadline. Set `TCP_NODELAY` for request/response protocols that write small messages, and apply connect and read timeouts.

**Reading and writing without blocking.** A stream read returns any number of bytes from 1 up to the request, 0 on orderly shutdown by the peer, or -1 with `EAGAIN` (no data now), `ECONNRESET` (the peer reset), `ETIMEDOUT` (keepalive or user timeout failed), and others. A write can accept fewer bytes than offered. The server keeps per-connection buffers: an input buffer that accumulates until a full request is parsed, and an output buffer drained whenever the socket is writable. Only ask the loop for write readiness (`EPOLLOUT`) when the output buffer is non-empty; otherwise the loop wakes constantly because a writable socket is almost always writable. Use `MSG_NOSIGNAL` on `send` (or ignore `SIGPIPE`) so writing to a closed peer returns `EPIPE` instead of killing the process.

**Backpressure and limits.** If a client reads slower than the server produces, the output buffer grows. A robust server bounds it: stop reading from the client (or from the upstream source) when the buffer passes a high-water mark and resume below a low-water mark. Bound request size, header size, number of connections (per IP and overall), idle time and total request time. Without those limits, a slow-loris style client holds descriptors indefinitely, and a large request exhausts memory.

**Shutdown and close.** `shutdown(fd, SHUT_WR)` sends a FIN after data already queued, announcing that no more data will be sent while still allowing reads, which supports half-close protocols and clean final responses. `close` without it still delivers queued data in the normal case, but if unread data is in the receive buffer, Linux sends a reset instead of a FIN, which can destroy the client's unread response. A server that wants a graceful close of a connection that may have unread input should `shutdown(SHUT_WR)`, drain input for a short time, then `close`. `SO_LINGER` can force a reset or block on close and is rarely the right tool.

**Socket options that matter.**

| Option | Purpose |
|---|---|
| `SO_REUSEADDR` | bind during `TIME_WAIT` after restart |
| `SO_REUSEPORT` | several listeners on one port with kernel balancing |
| `TCP_NODELAY` | disable Nagle for latency-sensitive small writes |
| `TCP_CORK` / `MSG_MORE` | batch pieces into full segments, e.g. header plus `sendfile` |
| `SO_KEEPALIVE`, `TCP_KEEPIDLE/INTVL/CNT` | detect dead peers in long-lived idle connections |
| `TCP_USER_TIMEOUT` | bound how long unacknowledged data may stay |
| `SO_RCVBUF`, `SO_SNDBUF` | buffer sizes; setting them disables autotuning, so use with care |
| `SO_ERROR` | retrieve the result of a non-blocking connect |
| `IPV6_V6ONLY` | choose dual-stack or IPv6-only behaviour |
| `TCP_FASTOPEN` | send data in the SYN on repeat connections (to verify for the deployment) |

**UDP.** `SOCK_DGRAM` preserves message boundaries, gives no delivery guarantee and no ordering. A server reads with `recvfrom` or `recvmmsg` (batching), and must be ready for datagrams larger than its buffer (truncated unless `MSG_TRUNC` is handled), and for source-address spoofing (so authenticate or limit amplification). The application must supply its own retransmission and congestion control, which is the case for QUIC, built on UDP.

**Architectures.**

- Thread or process per connection: simple, bounded by memory; fine for hundreds of long-lived connections.
- Single event loop: no locks, one core, must never block; a slow handler stalls everyone.
- Event loop per core with `SO_REUSEPORT`: scales by core, with connections pinned to a loop; load can be uneven.
- Event loop plus worker pool for blocking or CPU-heavy work, communicating with `eventfd` or queues.
- Process supervisor with pre-fork workers and a graceful restart protocol (pass the listening socket to new workers).

**Observability.** `ss -tinp` shows sockets with per-connection TCP details (retransmits, round-trip time, congestion window, queues), `nstat` and `/proc/net/*` show counters, and `tcpdump` or `strace` show what crossed the wire and the API. A growing `Recv-Q` on a listener means the application is not accepting fast enough; a growing `Send-Q` on a connection means the peer or the network is slow.

## Assessment: the good, the bad and the ugly

**The good.** The API is uniform, portable across Unix systems, and well understood. Non-blocking sockets plus readiness notification serve very large numbers of connections on modest hardware. Kernel facilities (`SO_REUSEPORT`, autotuning, zero-copy paths) take on much of the scaling work. Diagnostic tools expose TCP internals in detail.

**The bad.** The stream abstraction hides message framing, so every protocol must define it and every implementation must handle partial reads. Error semantics are subtle: a successful `write` says only that the kernel accepted the bytes; delivery is known only from an application-level acknowledgement. Many defaults serve throughput, not latency. Edge cases around half-close, resets and `TIME_WAIT` cause hard-to-explain failures. Event-driven code splits logic into callbacks and state machines, which is harder to read and test than blocking code.

**The ugly.** Descriptor exhaustion makes an accept loop spin or a server drop clients silently. Slow clients and half-open connections consume resources for hours unless timeouts exist. A single blocking call in an event loop (a DNS lookup with `gethostbyname`, a disk read, a lock) stalls all clients; `getaddrinfo` is itself blocking and usually runs in a thread pool. Resets caused by closing a socket with unread data lose responses and confuse clients. IPv6 and IPv4 differences, firewalls and middleboxes that drop packets or idle connections silently, and path MTU black holes produce failures that the application cannot see directly. Security hazards include SYN floods, amplification through UDP, request smuggling by inconsistent framing, and unbounded buffers. Misconfigured `SO_REUSEPORT` without permission checks has allowed port hijacking by another process of the same user, which is why the kernel requires the same effective user for all sockets sharing a port.

Mitigations: set limits and timeouts at every stage; test with slow, half-closing, resetting and huge clients; run name resolution off the loop; keep a spare descriptor for accept failures; document and test the shutdown path; and monitor queues with `ss`.

## Applications beyond this domain

- **Web servers, proxies and load balancers** are the direct application, with the same loops, buffers and limits at larger scale. Reverse proxies add upstream connection pools and two-sided backpressure.
- **Databases and message brokers** serve thousands of client connections with per-connection state machines, and often use `SO_REUSEPORT` or a thread-per-core design.
- **Language runtimes** wrap the pattern: Go's netpoller multiplexes goroutines over epoll; Tokio and libuv do the same; Python's `asyncio` selects an event loop built on `epoll`. Their behaviour on slow clients and shutdown follows the same rules.
- **Virtual machine and container networking**: a hypervisor's user-space networking backend or a container proxy is a socket server relaying between descriptors; vsock provides the same API between guest and host.
- **Distributed systems** need the same attention to partial failure: timeouts, retries with backoff, and idempotent operations answer the question of whether a request that appeared to fail actually happened.
- **Peer-to-peer and real-time media** use UDP with application-level control, which tests the datagram side of the API.

## Examples

**A minimal non-blocking echo server.** The loop adds the listener to `epoll`, accepts until `EAGAIN`, reads each ready client into a buffer, writes it back, and when a write is partial, stores the remainder and asks for `EPOLLOUT`. It closes on read returning 0. That is the skeleton from which every server here is built.

**The accept spin.** A server reaches its descriptor limit; `accept4` fails with `EMFILE` but the connection stays in the queue, so the listener stays readable, and the loop spins at 100% CPU. Keeping an extra descriptor (open `/dev/null`) to close, accept and close the new connection, then reopen the spare, sheds load cleanly.

**Latency from Nagle.** A client writes a small request header and then a small body in two `write` calls. The second write waits for the acknowledgement of the first, which the server delays by up to 40 ms. Setting `TCP_NODELAY`, or assembling the message into one `write`, removes the pause.

**The reset that eats a response.** A server answers an HTTP request with an error and closes while the client is still uploading. The unread upload data triggers a reset and the client sees a connection error rather than the error page. The remedy is to stop reading, send the response, call `shutdown(SHUT_WR)`, drain briefly and then close.

**Non-blocking connect with fallback.** A client resolves `service.example`, gets an IPv6 address and an IPv4 address, starts `connect` to the first, and after 250 ms starts the second without cancelling the first; it keeps whichever completes first. This is the Happy Eyeballs approach, and it avoids a 2 minute stall when IPv6 is broken.

**A failing example: unbounded buffering.** A proxy reads from a fast upstream and writes to a slow client without a high-water mark. Memory use grows by gigabytes under a few slow clients and the out-of-memory killer ends the process. Pausing the upstream read at a threshold fixes it.

## Related problems and ideas

- **Alternatives to byte streams**: message-oriented transports (SCTP, QUIC) keep boundaries, multiplex streams without head-of-line blocking and move connection setup and encryption into one handshake; QUIC runs over UDP in user space.
- **Kernel bypass**: user-space stacks (DPDK, AF_XDP) skip the kernel for extreme packet rates, at the cost of reimplementing the protocol stack and losing the kernel's tools.
- **Structured concurrency and async/await**: language-level abstractions that present non-blocking I/O as straight-line code while a runtime runs the loop.
- **Service meshes and sidecars**: move retry, timeout, TLS and load-balancing logic out of the application and into a proxy next to it.
- **Alternatives to polling**: `io_uring` with multishot accept and receive, buffer rings, and registered files reduce system calls and copies; a completion model changes how buffers are managed.
- **Resilience patterns**: circuit breakers, load shedding, admission control and rate limiting address what to do when the server is overloaded.

## Active research

Active topics include congestion control algorithms for datacentre and wide-area paths (BBR and its successors, evaluated against loss-based schemes), improving TCP and QUIC behaviour on lossy or high-latency links, zero-copy receive and send paths in the kernel (devmem and `io_uring` zero-copy receive proposals), and per-core scaling of network stacks. Security research examines TCP/IP implementation weaknesses, off-path attacks, and denial-of-service defences. Application-level work studies how to make timeouts, retries and backpressure composable and correct, with fuzzing of protocol parsers and formal models of non-blocking servers. Which of these have reached the mainline kernel, and in which version, should be confirmed from release notes (to verify).

## Future direction

Expect wider use of `io_uring` in servers (multishot operations and zero-copy), growth of QUIC and HTTP/3 with user-space transports, kernel work to make per-socket and per-core behaviour more predictable, and hardware offload for encryption and segmentation. Memory-safe languages and verified parsers will take over more protocol handling. Servers will increasingly be deployed behind proxies and meshes that own timeouts and retries, but the application must still bound its own resources. The stable skills are unchanged: non-blocking descriptors, explicit buffers and limits, careful shutdown, and testing against misbehaving peers.
