# Syscalls, errno, glibc versus raw calls, and strace

## Define the problem

A user-space program cannot touch hardware, other processes or the page tables directly. Everything it wants from the machine, such as opening a file, creating a process, mapping memory or sending a packet, has to be requested from the kernel, which runs with privileges the program lacks. The system call interface is the narrow, stable doorway for those requests. It must satisfy several demands that pull in different directions:

- **Isolation.** The kernel must not trust a single pointer, length or flag it receives, because the caller may be buggy or hostile.
- **Stability.** Binaries built years ago must still run, so the kernel promises not to break the interface it exposes to user space.
- **Speed.** A busy server may cross the boundary millions of times per second, so the crossing and the common calls must be cheap.
- **Diagnosability.** When a call fails, the programmer needs a precise reason, and when a program misbehaves in production, an operator needs to see which calls it made without rebuilding it.

The gap this slice fills is the working knowledge that sits between "I call `open()`" and "the kernel executed a handler": what a syscall is, how failure is reported, why the C library sits in between and when to bypass it, and how to observe the traffic with `strace`. It covers x86-64 and arm64 Linux, the glibc wrapper layer, the `errno` convention, the vDSO fast path, and `strace` as the main observation tool. Writing new syscalls inside the kernel, `seccomp` filtering and `ptrace` internals are treated in other topics.

## History and approaches

**Traps into the kernel.** Early Unix systems used a software interrupt or trap instruction to switch from user mode to kernel mode. On 32-bit x86 Linux this was `int 0x80`, with the call number in a register and arguments in others. It worked but was slow, because interrupt delivery on x86 does a lot of bookkeeping that a deliberate call does not need.

**Faster entry instructions.** Intel introduced `sysenter` and AMD introduced `syscall`; both switch privilege level with a minimal fixed sequence. Because the right instruction depended on the CPU, Linux placed a small piece of kernel-provided code in every process, reached through the auxiliary vector, so that the C library need not know which instruction to use. That shim is the ancestor of today's vDSO. The 64-bit x86 ABI standardised on `syscall`, with the number in `rax`, the first six arguments in `rdi`, `rsi`, `rdx`, `r10`, `r8` and `r9`, and the result in `rax`. Arm64 uses `svc #0` with the number in `x8`.

**Return conventions.** Early Unix returned a small integer and set a global error code. The kernel side of Linux returns a negative errno value in the result register for failure; the C library converts that into the classic "return -1 and set `errno`" pattern. The reason is historical compatibility with POSIX. The cost is that a single global (later a thread-local) variable carries the error, which is easy to clobber.

**Threads force a redesign of errno.** With one address space shared by many threads, a global `errno` is a race. Modern glibc defines `errno` as a macro that expands to a thread-local location, so each thread has its own. This fixed correctness, but left a pitfall: any function called between the failing call and the check, including a `printf` in a log statement, can overwrite the value.

**Wrapper layers and their gaps.** The C library does more than rename the instruction. It adds cancellation points, restarts, argument conversion (for example mapping the library's 64-bit `off_t` onto the right kernel call on 32-bit systems) and sometimes emulates a call with a different one: `open()` is issued as `openat()` on current systems, and `fork()` is a `clone` variant with extra library bookkeeping for atfork handlers and locks. New kernel calls often appear long before a wrapper does. Examples are `futex`, `gettid` (late wrapper), `pidfd_open`, `io_uring_setup`, `memfd_create` and `statx` at various times. Programmers used the generic `syscall(2)` function in the gap, accepting the loss of type checking.

**Measurement tools.** Early tracers such as `truss` and `trace` on other Unix systems used special file interfaces. Linux's `ptrace` gave a general mechanism to stop a process at each syscall entry and exit, and `strace` grew on top of it. It was later extended with seccomp-assisted filtering, so that it stops only for selected calls, and with fault injection, so that a chosen call can be forced to fail for testing.

**Lessons pushed into the current design.** The lessons were: keep the number-to-handler table append-only and never reuse numbers; make new calls take a flags argument and a size-versioned structure (as `openat2`, `clone3` and `sched_setattr` do) so that they can grow without new numbers; return precise errors; and move hot, read-only calls such as time queries into user space with the vDSO.

## Current state

**The call path.** A wrapper loads the call number and arguments into the ABI's registers and executes the entry instruction. The CPU switches to kernel mode and jumps to the entry stub, which saves registers, applies mitigations configured for the system (page-table switching or speculation barriers, depending on the CPU), and indexes the table of handlers. The handler validates arguments. Pointers into user memory are never dereferenced directly; the kernel uses copy helpers that fault safely if the address is bad. On success the handler returns a non-negative value; on failure it returns a negative errno. The exit stub returns to user mode, first checking for pending signals, scheduler work and trace requests.

**errno in practice.** The kernel's errno values form a numbered set (`EPERM`, `ENOENT`, `EINTR`, `EAGAIN`, `EINVAL`, `ENOMEM`, `EACCES`, `EEXIST` and so on) shared with the library. glibc's wrapper checks whether the raw result lies in the error range, stores the positive value in the thread's `errno` and returns -1. Rules a programmer must follow:

- Read `errno` only immediately after a call that reported failure; success never resets it to zero.
- Save it into a local variable before calling anything else that may alter it, including logging and `free`.
- Treat `EINTR` as "interrupted, try again" for calls that can be interrupted by a signal handler, unless the handler was installed with restart behaviour. Handle `EAGAIN` and `EWOULDBLOCK` as the same condition on Linux.
- Convert it to text with `strerror_r` or the `%m` extension of glibc's `printf` family, and keep the numeric value for logs so it can be searched.
- Note that some functions outside the syscall layer report errors differently: the pthread functions return the error code directly and do not touch `errno`; `getaddrinfo` has its own error enum; `strtol` needs `errno` to be cleared before the call because zero is a valid return.

**glibc wrapper versus raw call.** Usually the right answer is to call the wrapper. It documents the contract, gets cancellation right, and handles architecture quirks. Reasons to use the generic `syscall()` function or a header-only helper:

1. The kernel offers a call that the installed library has no wrapper for yet, such as a new `io_uring` or `pidfd` operation, and the project cannot wait for the distribution.
2. A tool needs the exact kernel behaviour without library interposition, such as a sandbox helper or a debugger.
3. A runtime that does not use glibc, for example a static binary built against another libc, or a language runtime that issues calls itself, as Go does on Linux.

Pitfalls of the raw path: argument types are all passed as `long`, so a wrong width compiles quietly; the return value is the libc `syscall()` convention (-1 and `errno`); the call number constants differ per architecture; and cancellation points and `fork` handling are skipped. Calling `fork` via raw `clone` in a multi-threaded program can leave the library's internal locks in an inconsistent state in the child. The `syscall()` function is the sanctioned path; inline assembly should be reserved for tools that must avoid every library dependency.

**The vDSO.** Some calls need no privilege: reading the clock (`clock_gettime`, `gettimeofday`, `time`) and, on some architectures, `getcpu`. The kernel maps a small shared object, the virtual dynamic shared object, into each process and publishes a data page that it updates. The C library resolves these symbols to the vDSO versions when the clock source allows it, so a time query is an ordinary function call that reads memory. A consequence for `strace`: a program that calls `clock_gettime` thousands of times per second often shows no syscalls at all.

**strace as the observation tool.** `strace` starts a program, or attaches to a running process, and prints each syscall with decoded arguments, the return value and the symbolic errno. The options used in daily work:

- `-f` follows threads and child processes; without it, work done after `fork` or `clone` is invisible.
- `-e trace=` selects calls or classes such as `file`, `network`, `process`, `memory`, `desc` and `signal`; `-e` also accepts negation.
- `-o file` writes the trace to a file, which keeps it out of the program's own output.
- `-s N` raises the string-print limit; the default truncates payloads at 32 bytes.
- `-T` shows the time spent in each call, `-tt` or `-r` shows timestamps, and `-c` or `-C` produces a summary table with counts, errors and time per call.
- `-y` and `-yy` decorate file descriptors with the path or socket address; `-k` prints a stack trace for each call where support is built in.
- `-p PID` attaches; this requires ptrace permission, which depends on the `ptrace_scope` setting of the Yama security module and on capabilities.
- `--seccomp-bpf` (together with `-f`) makes the kernel stop the tracee only for selected calls, which cuts overhead greatly.
- `-e inject=` (fault injection) makes a chosen call fail with a chosen errno, or delays it, after a given number of invocations. It turns the question of how a program copes with a full disk into a repeatable test.

Reading a trace is a skill: look for the first failing call, for repeated `ENOENT` while searching paths (library or configuration lookup), for `EINTR` and `EAGAIN` storms, for large gaps in `-T` times, and for `ioctl` calls whose numbers explain device behaviour.

## Assessment: the good, the bad and the ugly

**The good.** The interface is stable. The kernel's rule is that a change which breaks a working user-space program counts as a bug in the kernel, so a binary compiled long ago keeps running. The convention for errors is uniform and the set of errno names is searchable. `strace` works on any process, needs no recompilation, and gives a truthful record of what crossed the boundary, so it settles arguments about what a program really does. The vDSO removes the cost of the most frequent read-only calls.

**The bad.** The `errno` convention is a single side channel; clobbering it by accident is a classic source of wrong messages in error paths. Many calls are overloaded with option flags whose combinations are poorly validated by older calls, which is why newer calls such as `openat2` insist on a versioned struct. Decoded output varies by `strace` version and architecture, and new calls or flags may appear as raw numbers on an old build. The same operation can look different between libc implementations, so traces from a musl-based container may not match the glibc ones used in training material.

**The ugly.** Tracing is not free: `ptrace`-based stops make a syscall-heavy program run many times slower, which changes timing and may hide or create races. Only one tracer can attach to a process at a time, so `strace -p` fails when a debugger or another tracer is already attached; containers often disable ptrace through seccomp profiles or capability sets, so the tool must be run from outside or the profile relaxed. Hardened systems restrict ptrace on non-child processes. Programs that detect tracing and change behaviour, or that run setuid, are awkward to observe. Raw `syscall()` use with wrong argument widths is silent on 64-bit machines and produces data-dependent failures on 32-bit ones. Finally, `strace` shows requests, not the reasons: a call that returns `EPERM` may have been denied by file mode, a capability, an LSM policy such as SELinux or a seccomp filter, and the trace does not say which. Mitigation: compare with audit logs, `dmesg` and the policy tools of each layer.

## Applications beyond this domain

- **Security sandboxes** treat the syscall table as the unit of policy. A seccomp filter allows or denies calls by number and arguments; the same list a tracer reads is what the filter matches. Container runtimes ship default profiles built from such lists.
- **Language runtimes** wrap or bypass the C library: Go issues calls itself and handles `EINTR` internally; Rust's standard library calls libc but offers `rustix` and similar crates that expose raw calls with typed arguments; Python exposes `os` functions that raise `OSError` carrying an errno.
- **Compatibility layers** such as gVisor and WSL1 re-implement the syscall interface in user space or another kernel, and rely on the stability promise to run unmodified binaries.
- **Observability** at scale replaces tracing a single process with kernel-side tools that watch syscall entry points system-wide with lower overhead (tracepoints and eBPF), and share the same vocabulary of call names and errno values.
- **The pattern itself**, a narrow versioned contract between an unprivileged client and a privileged service, with a signed integer or enum for errors, recurs in hypercalls from a guest to a hypervisor, in firmware service calls, and in RPC systems with status codes.

## Examples

**A missing configuration file.** A daemon exits at start with a vague message. Running `strace -f -e trace=file -o t.log daemon` shows a run of `openat` calls ending in `ENOENT` for `/etc/daemon.d/site.conf`, after which the program prints the message and exits. The file name was never in the message; the trace provides it.

**A clobbered errno.** A function opens a file, fails, calls a logging helper that formats the time with `localtime_r`, and then prints `strerror(errno)`. The message says "No such file or directory" even though the real cause was `EACCES`, because the logging helper's own internal lookup of the timezone file failed with `ENOENT` and replaced the value. The repair is to copy `errno` into a local immediately after the failing call.

**A raw call with the wrong type.** A tool calls `syscall(SYS_fallocate, fd, 0, offset, len)` where `offset` and `len` are `int` variables. On a 64-bit host they are sign-extended and work for small values; with sizes above 2 GiB, the int overflows before the call and the result is wrong. The wrapper would have used `off_t`. This is an example of the type loss in the raw path.

**A clock that does not show up.** A service claimed to be making a syscall per request to read the time. The trace had no `clock_gettime` entries. The process was using the vDSO, and the real syscall traffic came from `futex` and `epoll_wait`. The investigation moved to lock contention.

**A failing example: tracing and timing.** A latency test passed in a normal run and failed under `strace -f`, because `ptrace` stops inflated the time of each call. Using `-c` for counts, or `--seccomp-bpf` to stop only on `openat`, removed the distortion. The lesson is to choose the narrowest filter that answers the question.

**Fault injection.** `strace -f -e trace=write -e inject=write:error=ENOSPC:when=3+ ./backup` forces the third and later writes to fail, which shows whether the backup tool handles a full disk or loops. This tests an error path that is hard to reach otherwise.

## Related problems and ideas

- **Interface evolution without number sprawl.** Extensible structures with a size field, flag validation that rejects unknown bits, and the push to give every new call a flags argument aim at a future in which the table grows slowly.
- **Avoiding the crossing.** `io_uring` batches many operations in one submission; shared memory rings avoid per-operation crossings; the vDSO handles reads. User-space networking stacks bypass the kernel entirely and give up its protections.
- **Redirecting syscalls.** Syscall user dispatch lets a process (for example a compatibility runtime) trap and handle calls selectively; seccomp user notification lets a supervisor decide calls on behalf of a sandboxed process. Both are alternatives to emulating the whole interface.
- **Alternative observation.** `ltrace` watches library calls, `perf trace` and eBPF tools watch system-wide with lower overhead, and `bpftrace` can filter by errno. Record and replay tools capture traces for later deterministic analysis.
- **Alternative error models.** Exceptions or result types in language runtimes replace the errno side channel with values returned together with the result; some proposals would give the kernel a richer extended error report than a single number.

## Active research

Work on the syscall layer is continuous but mostly engineering rather than research. Questions currently being studied include how to keep entry and exit cheap while mitigations for speculative-execution attacks add cost; how to verify that a seccomp profile covers a program's real call set (profile generation from traces, static analysis of binaries and of libc usage); how to reduce the exposed surface for sandboxed workloads by removing little-used calls; and how to build tracers whose overhead is low enough to run continuously in production. Verification groups have examined formal models of the interface and of user-space copy rules. Which compatibility layers can reach complete fidelity, and how many calls real container workloads need, are open empirical questions (to verify the current figures before quoting them).

## Future direction

Expect new calls to keep arriving as extensible structures with flags, and for wrappers to appear in glibc with a lag of one or more releases, so that knowing the raw path stays useful. The pidfd family and `io_uring` have been growing steadily and are likely to absorb more operations. Observation tooling is moving towards kernel-side filtering and structured output; users of `strace` should watch for improvements in decoding of new calls and in seccomp-assisted filtering. Hardening trends (default-deny profiles, restricted ptrace) will make "just attach `strace`" less available in production, so operators should plan a sanctioned tracing path. Version-specific claims in this synthesis, such as option availability in a particular `strace` release, are marked for verification against the installed tool's manual page.
