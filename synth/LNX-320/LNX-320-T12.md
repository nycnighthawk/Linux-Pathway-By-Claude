# eBPF from user space: libbpf and CO-RE

## Define the problem

Operators and developers repeatedly need to ask the running kernel questions that no existing counter answers: which processes are executing which programs, how long do block I/O requests wait, who is dropping packets and why, which file does this latency spike come from. Before eBPF there were two unsatisfying options. A fixed kernel interface (`/proc`, `perf` counters, tracepoints with an external consumer) exposes only what kernel developers thought to provide. A kernel module can do anything, but it must be compiled for each kernel version, can crash or corrupt the system, and needs full privilege and trust.

eBPF (extended Berkeley Packet Filter) fills this gap: user space loads a small program that the kernel verifies for safety and then runs inside the kernel at chosen hook points, sharing data with user space through typed maps and ring buffers. It makes the kernel programmable for observability, networking, security and scheduling without recompiling or risking the stability of the host. The remaining engineering problem is portability. A BPF program that reads kernel structures sees different field offsets in different kernel versions and configurations; compiling it on the target at run time (the early BCC approach) needs compilers and kernel headers on production machines. CO-RE (Compile Once, Run Everywhere) with libbpf is the answer this topic teaches.

The slice covers the user-space side of eBPF: the program and map model, the build chain (clang to BPF object, skeleton generation), the libbpf loader, CO-RE field access and BTF, ring buffer events, attach types, permissions and the verifier's constraints on what can be written. The kernel-internal machinery (the verifier algorithm, JIT, helper implementation) belongs to the kernel courses.

## History and approaches

**Classic BPF.** In 1992 the BSD packet filter let `tcpdump` run a tiny register machine inside the kernel to select packets, instead of copying every packet to user space. Linux adopted it for sockets and later for seccomp (see the sandboxing topic). It was small, safe by construction (no loops, bounded programs) and limited.

**eBPF.** From 2014 the kernel gained an extended instruction set with ten 64-bit registers, a 512-byte stack, a verifier that proves termination and memory safety, a JIT for common architectures, maps for shared state, and helper functions as the only way to call kernel services. The `bpf(2)` system call loads programs and manages maps. Program types multiplied: socket filters, XDP (packet processing at the driver), traffic control classifiers, kprobes, tracepoints, perf events, cgroup hooks, LSM hooks, struct_ops (implementing kernel interfaces such as TCP congestion control and sched_ext schedulers), and more.

**BCC.** The BPF Compiler Collection made tools easy to write in Python or Lua with embedded C, compiled at run time by LLVM against the running kernel's headers. It produced many useful tools (`execsnoop`, `biolatency`, `tcpconnect`) but needed LLVM, headers and a lot of memory on each target, and broke when headers were missing.

**BTF and CO-RE.** BPF Type Format (BTF) is a compact description of the kernel's types, embedded in a kernel built with `CONFIG_DEBUG_INFO_BTF` and exposed at `/sys/kernel/btf/vmlinux`. With it, clang records field accesses in a BPF object as *relocations* (struct and field names, not offsets) in a `.BTF.ext` section. At load time libbpf matches those against the running kernel's BTF and rewrites the instructions with the correct offsets, sizes and existence checks. Compiling once on a development machine now works on kernels of different versions. A single header, `vmlinux.h`, generated from a kernel's BTF with `bpftool btf dump file /sys/kernel/btf/vmlinux format c`, replaces the need for kernel headers. The libbpf-bootstrap project and the "BCC to libbpf" porting guides documented the conversion, and many classic BCC tools were reimplemented as `libbpf-tools`.

**Skeletons and ring buffers.** `bpftool gen skeleton` generates a C header from the compiled BPF object, with typed accessors for programs and maps, so loader code is short and type checked. The BPF ring buffer (`BPF_MAP_TYPE_RINGBUF`, 5.8) replaced per-CPU perf buffers for event streams: one shared buffer, ordered events, reserve-and-submit without a copy, and efficient notification through `epoll`.

**Other language ecosystems.** Go libraries (cilium/ebpf), Rust (aya, libbpf-rs), and Python (bcc) offer loaders with the same underlying system call; CO-RE support, BTF handling and skeleton-like generation exist in several of them.

**Emerging pattern.** Write the kernel side in restricted C, compile with clang for the BPF target with `-g` for BTF, embed the object in a user-space program with a generated skeleton, load with libbpf, which performs CO-RE relocation, attach, and consume events through a ring buffer in an ordinary event loop.

## Current state

**The development flow.**

1. Generate `vmlinux.h` once (`bpftool btf dump ... format c > vmlinux.h`) and commit it, or use a minimal hand-written struct set with `__attribute__((preserve_access_index))`.
2. Write `prog.bpf.c`: include `vmlinux.h`, `<bpf/bpf_helpers.h>`, `<bpf/bpf_core_read.h>`, `<bpf/bpf_tracing.h>`; declare maps with the `SEC(".maps")` BTF-defined syntax; write functions with `SEC("tp/...")`, `SEC("kprobe/...")` or `SEC("fentry/...")`; end with `char LICENSE[] SEC("license") = "GPL";` (many helpers require a GPL-compatible licence).
3. Compile: `clang -g -O2 -target bpf -D__TARGET_ARCH_x86 -c prog.bpf.c -o prog.bpf.o`. `-O2` is required (the verifier rejects unoptimised output) and `-g` produces the BTF that CO-RE needs.
4. Generate a skeleton: `bpftool gen skeleton prog.bpf.o > prog.skel.h`.
5. Write `prog.c`: open the skeleton (`prog_bpf__open()`), set options and read-only data (`rodata`) before load, `prog_bpf__load()`, `prog_bpf__attach()`, create a ring buffer reader with `ring_buffer__new(map_fd, handler, ctx, NULL)` and loop `ring_buffer__poll()`; on exit `prog_bpf__destroy()`.
6. Run with privilege (see below) and handle `SIGINT` to clean up.

**Programs and hooks.** A *tracepoint* program attaches to a stable instrumentation point such as `syscalls/sys_enter_execve` or `sched/sched_process_exec`, with an argument layout described in `/sys/kernel/tracing/events/.../format`. Tracepoints are stable across versions, so prefer them. *kprobes* attach to nearly any kernel function by name; they are flexible but break when functions are renamed or inlined. *fentry/fexit* (BPF trampolines, 5.5) are faster and give typed arguments through BTF. *Raw tracepoints*, *uprobes* (user-space functions), *XDP* and *TC* (packets), *cgroup* hooks and *LSM* programs extend the same model to other domains.

**Maps.** Hash, array, per-CPU variants, LRU hash, stack traces, ring buffers, and others. Maps are created at load time, shared between programs, readable and writable from user space (`bpf_map_lookup_elem`) and pinned in `/sys/fs/bpf` to outlive the loader. Global variables in the BPF object (`.data`, `.bss`, `.rodata`) appear as array maps and are accessible via the skeleton.

**CO-RE access.** In BPF code, never dereference a kernel pointer directly unless the verifier knows its type (BTF-typed pointers in fentry programs or `bpf_core_cast`). Use `BPF_CORE_READ(task, real_parent, tgid)` for a chain of pointer reads with relocation, `bpf_probe_read_kernel` for raw copies, and `bpf_core_field_exists(struct task_struct, field)` and `bpf_core_type_exists` to adapt to kernels where a field is missing; `LINUX_KERNEL_VERSION` and the `__kconfig` externs read kernel version and configuration values. Field accesses are recorded as relocations; if the target kernel lacks the field and no existence check guards it, loading fails with a clear message in libbpf's debug output.

**The verifier.** Every program is checked before it can run. It must terminate (bounded loops are accepted since 5.3 and `bpf_loop` since 5.17), access memory only through checked pointers (a map value pointer must be tested for `NULL` before use; stack and packet accesses need bounds), never leak kernel pointers to unprivileged users, and stay within a complexity limit on the number of instructions it analyses (about one million processed instructions). Typical rejection messages are "invalid access to map value", "R1 type=scalar expected=fp" and "back-edge from insn". Tips: keep functions small, use `__always_inline`, bound loops with constants, zero-initialise structures before output (the verifier checks that padding bytes are initialised to avoid leaking stack content), and read the log with `LIBBPF_DEBUG` or `bpftool prog load` output.

**Running and permissions.** Historically loading needed root. Modern kernels split privileges: `CAP_BPF` for loading and map creation, `CAP_PERFMON` for tracing and reading kernel memory, `CAP_NET_ADMIN` for network program types; unprivileged BPF is disabled by default on many distributions (`kernel.unprivileged_bpf_disabled`). Memory accounting uses cgroup memory instead of the old `RLIMIT_MEMLOCK` on kernels since 5.11, but older systems still require raising the limit (`setrlimit(RLIMIT_MEMLOCK)`) before loading, and libbpf can do so itself in legacy mode.

**Debugging and tooling.** `bpftool prog list`, `bpftool prog show id N`, `bpftool map dump`, `bpftool prog dump xlated|jited`, `bpftool btf`, and `bpftool prog tracelog` (reading `bpf_trace_printk` output from `trace_pipe`) inspect the system. `bpf_printk` is for debugging only (limited and slow). `perf trace`, `bpftrace` (a high-level language for one-liners) and BCC tools remain good for quick analysis before writing a production tool.

## Assessment: the good, the bad and the ugly

**The good.** eBPF is safe enough to run in production, because the verifier rejects unsafe programs before they run, and dynamic enough to deploy without a reboot. CO-RE lets one compiled object serve many kernel versions, with small run-time footprint and no compiler on the target. Ring buffers and maps give efficient data transfer to user space with in-kernel filtering and aggregation, so overhead is often a few percent for tracing that would be impossible with full event capture. The ecosystem (bpftool, libbpf, language libraries, ready tools) is mature, and the same mechanism now powers networking (Cilium), security tooling (Falco-style, Tetragon), observability products and even scheduling (sched_ext).

**The bad.** The programming model is constrained and unusual: limited stack, no unbounded loops, no arbitrary function calls, helpers instead of a library, and verifier errors that are hard to read and depend on the compiler's output. A change in compiler version or optimisation can turn an accepted program into a rejected one. CO-RE needs a kernel with BTF; older or minimal kernels lack it (BTFHub provides external BTF for some). Hooks on kernel internals (kprobes) tie programs to internal names that change. The documentation is spread across kernel docs, libbpf docs, blog posts and examples, and APIs have evolved quickly.

**The ugly.** The verifier has had security bugs, which turned unprivileged or lightly privileged BPF into a source of local privilege escalation; this is why unprivileged BPF is disabled by default and why the capability split exists. Observability tools with kernel privileges are themselves attack surface, and a tracing program can read secrets from kernel memory. Programs may silently lose events when ring buffers fill (the producer must check for reserve failure and count drops). Differences between architectures (register names, `__TARGET_ARCH_*` macros, syscall wrappers with a wrapped `pt_regs`) complicate portable kprobe code. Overhead surprises occur: attaching to a very hot function (such as `schedule` or every `kmalloc`) can slow the system noticeably. A buggy program can still hurt performance even if it cannot crash the kernel. Packaging is awkward: container images that load BPF need privileges, mounted `/sys/kernel/btf` and often `debugfs` or `tracefs`.

Mitigations: prefer stable tracepoints and fentry; test on several kernel versions in CI (virtual machines with different kernels); use `bpf_core_field_exists` guards; count and report ring buffer drops; measure overhead; apply least privilege with `CAP_BPF` and `CAP_PERFMON` rather than full root; and keep `vmlinux.h` generation reproducible.

## Applications beyond this domain

- **Cloud-native networking and security**: Cilium uses eBPF for service load balancing, network policy and observability (Hubble); Tetragon and similar tools enforce runtime security policies in the kernel.
- **Observability and profiling**: continuous profilers sample stacks with perf-event programs, and tools such as `bpftrace` and the BCC and libbpf-tools collections provide latency and tracing utilities that production teams use daily.
- **Load balancing and DDoS mitigation**: XDP programs in front of the network stack drop or redirect packets at line rate (Meta's Katran, Cloudflare's mitigation systems).
- **Scheduling**: the `sched_ext` framework lets a BPF program implement a CPU scheduler, loaded at run time, which is covered later in the kernel course.
- **Virtualization**: tracing of KVM exits and I/O latency with BPF helps diagnose guest performance; Cloud and container platforms observe VMs and containers without agents inside them.
- **Other operating systems and runtimes**: eBPF for Windows and the idea of verified sandboxed extensions appear in other kernels and user-space runtimes (WebAssembly is a different but related approach to safe extension).

## Examples

**An exec tracer.** A tracepoint program on `sched/sched_process_exec` reads the new process's name, its PID and its parent's PID with `BPF_CORE_READ(task, real_parent, tgid)`, fills an event struct and submits it to a ring buffer. The user-space side prints one line per `exec`. The same object runs on kernels where `task_struct` layouts differ, because the parent access is relocated at load time.

**A latency histogram.** A pair of `fentry` programs on a block-layer function store a timestamp in a hash map keyed by request pointer, and on completion compute the delta and add it to a log-scaled histogram in an array map. User space reads the array once per second. No events leave the kernel, so overhead stays small even at high I/O rates.

**A verifier rejection.** A loop over a packet's bytes with a run-time bound fails with a "back-edge" or "unbounded loop" message. Rewriting with a constant maximum and an early exit passes. Another classic: using a map lookup result without a `NULL` check yields "R0 invalid mem access 'map_value_or_null'".

**A failing example: a missing field.** A tool reads `task->state` directly. On newer kernels the field was renamed to `__state`, and the program fails to load there. With CO-RE, the program checks `bpf_core_field_exists(task->__state)` and uses the old field otherwise, or relies on a stable tracepoint argument.

**A lost event.** Under a fork storm, `bpf_ringbuf_reserve` returns `NULL` because the buffer is full. The program ignores that, and the user-space report silently under-counts. Incrementing a drop counter in a map and printing it exposes the loss.

## Related problems and ideas

- **bpftrace and higher-level DSLs** trade flexibility for speed of writing; **BCC** remains useful for rapid prototyping, with the footprint cost.
- **Kernel modules and livepatch**: more power and more risk, per-version builds and no verification.
- **Dynamic tracing frameworks** such as ftrace, perf, SystemTap, DTrace (on other systems) address overlapping problems with different safety and flexibility trade-offs.
- **WebAssembly and other verified-extension runtimes** apply the same idea, safe untrusted code inside a privileged host, in user space and increasingly in kernels.
- **Alternative to kernel hooks**: user-space tracing with uprobes or USDT probes, and library-level instrumentation (OpenTelemetry), which lack kernel visibility but are portable.
- **Formal verification of the verifier and JIT** is a research area aimed at finding the kind of bug that caused earlier security incidents.

## Active research

Research and development focus on the verifier's soundness (formal models, differential testing and fuzzing with syzkaller and similar tools), on making the verifier more permissive without losing safety (better loop and range analysis, precision tracking), on extending the programming model (kfuncs, which allow BPF programs to call selected kernel functions; dynptrs for variable-sized data; arenas for shared memory; sleepable programs), and on tooling: improvements to BTF size and deduplication, stable ABI questions for kfuncs and struct_ops, and portability across architectures. Security research examines BPF as an attack surface and as a defence tool, including signed BPF programs and policy for who may load what. Which features exist in a given kernel should be confirmed from the kernel's BPF documentation and `bpftool feature probe` (to verify).

## Future direction

Expect eBPF to keep expanding beyond tracing and networking: schedulers, memory-management hints, storage and I/O hooks and security enforcement are all active. The user-space toolchain will gain more language bindings and higher-level frameworks, while CO-RE and BTF become the default delivery model. Kernels will make BTF available more widely, and signed or attested BPF programs will become more common in regulated environments. For practitioners, the durable skills are knowing which hook to choose (stable first), writing verifier-friendly code, measuring overhead, and handling lost data honestly. Exact kernel versions for features named in this synthesis are to verify against current documentation.
