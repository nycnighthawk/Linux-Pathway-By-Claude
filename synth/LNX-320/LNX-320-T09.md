# Capabilities, seccomp-bpf, namespaces and Landlock: shrinking what a process may do

## Define the problem

Classic Unix privilege is coarse. A process runs as some user; the user "root" may do anything, and any other user may do little. A program that needs one privileged act, such as binding port 80, setting the clock or reading a raw network packet, therefore ran as root with the power to do everything else, and any bug in it could be turned into full control of the machine. At the same time, programs that handle untrusted input (a document converter, a browser renderer, a network daemon, a container workload) need a way to be confined even when they hold ordinary credentials, because a flaw in them is probable over their lifetime.

The practical aim is *least privilege* and *defence in depth*: give each process only the powers it needs, remove the ability to reach most of the kernel's interface, hide most of the system's resources from it, and restrict what files it can touch, in layers that fail independently. Linux has no single sandbox switch. It offers a toolbox of mechanisms with different questions:

- *What privileged operations may this process perform?* Capabilities.
- *Which system calls, with which arguments, may it make?* seccomp-bpf.
- *Which instance of a system resource does it see?* Namespaces.
- *Which files and network ports may it reach, set by the process itself without root?* Landlock.

This slice teaches each mechanism's model, how they combine, and how to use them from C. Mandatory access control policies (SELinux, AppArmor), cgroup resource limits and full container runtimes are related but treated elsewhere in the pathway.

## History and approaches

**All or nothing root.** Early Unix distinguished only effective user ID zero from everything else. Set-user-ID programs (`passwd`, `ping`, `su`) were the way to grant one special action, and they accumulated a long history of privilege escalation bugs, since the whole program then ran as root.

**POSIX capabilities.** An abandoned POSIX draft (1.e) described splitting root's power into separate privileges. Linux implemented a version in the 2.2 kernel: about forty capabilities such as `CAP_NET_BIND_SERVICE`, `CAP_NET_RAW`, `CAP_SYS_TIME`, `CAP_CHOWN` and the very broad `CAP_SYS_ADMIN`. Each thread has several capability sets (permitted, effective, inheritable, bounding, ambient), and files can carry capabilities in an extended attribute. Early versions had practical problems: the inheritance rules made capabilities hard to retain across `exec`, and `CAP_SYS_ADMIN` became a catch-all for anything that did not fit elsewhere. Ambient capabilities (4.3) made it practical to run an unprivileged program with a chosen capability.

**chroot and jails.** `chroot` changes the process's idea of the root directory. It was never designed as a security boundary (a root process can escape it), but it inspired FreeBSD jails and Solaris zones, which combined filesystem, process and network isolation under one name.

**Namespaces.** Linux added namespaces one resource at a time starting with mount namespaces in 2.4.19 (2002): mount, UTS (hostname), IPC, PID, network, user, cgroup and time. A process belongs to one namespace of each type. In a PID namespace the first process sees itself as PID 1 and cannot see outside processes; in a network namespace it has its own interfaces and routing; in a mount namespace it has its own mount table. The user namespace (3.8, finished in 3.12) lets an unprivileged user create a namespace in which that user maps to root, with capabilities valid only over resources owned by that namespace. This made unprivileged containers and rootless tools possible. It also widened the kernel's attack surface, since unprivileged users could now reach code that formerly needed root, which is why many distributions restrict user namespace creation by policy or sysctl.

**seccomp.** The original seccomp mode (2005) allowed a process only `read`, `write`, `_exit` and `sigreturn`, enough for pure computation on already open descriptors. In 2012 Linux added seccomp-bpf (3.5): the process installs a Berkeley Packet Filter program that the kernel runs on every system call, with the architecture, call number and register arguments as input. The program returns an action: allow, kill the thread or process, return a chosen errno, deliver a trap signal, notify a tracer, log, or (later) forward to a user-space supervisor via the notification mechanism. Filters are inherited across `fork` and `exec` and can only be tightened by installing more filters. Setting the `no_new_privs` flag first allows an unprivileged process to install one, and ensures that setuid binaries cannot undo it.

**Seccomp in practice.** Chrome, OpenSSH, Firefox, systemd (`SystemCallFilter=`), Docker and Kubernetes all ship filters. Lists of allowed calls, developed by tracing, proved fragile: new libc versions use new calls (for example `openat2` or `statx`, `clone3`), so a profile that worked last year breaks, and compatibility rules such as returning `ENOSYS` for unknown calls let libraries fall back. Filtering on pointer arguments cannot work, because a filter sees only the pointer value, not the data it points to, and user memory can change after the check.

**Landlock.** Mandatory access control systems such as SELinux and AppArmor are set by an administrator. Landlock (5.13) lets an unprivileged process restrict itself: it creates a ruleset naming the kinds of access it handles (read, write, execute, remove, make files, truncate, and later network connect and bind), adds rules granting those accesses beneath certain directories or for certain ports, and enforces it. A restriction stacks with the system's policy and with earlier restrictions, and can never be lifted. It is designed for application developers to sandbox their own code and fills the gap that seccomp cannot cover, which is path-based decisions.

**Emerging pattern.** Sandboxes layer several mechanisms: drop capabilities, enter fresh namespaces, restrict file and network reach with Landlock or an LSM, and filter system calls with seccomp as the last line. Each layer is imperfect, so together they reduce risk.

## Current state

**Capabilities in practice.**

- Inspect with `getpcaps`, `capsh --print` or `/proc/PID/status` (`CapInh`, `CapPrm`, `CapEff`, `CapBnd`, `CapAmb`). `capabilities(7)` lists each capability and the system calls it governs.
- A thread acts with its *effective* set; the *permitted* set is the upper bound it may raise; the *bounding* set limits what `exec` can gain; the *inheritable* and *ambient* sets control what survives `exec` of an ordinary program.
- File capabilities (`setcap cap_net_bind_service=+ep /usr/bin/server`) replace setuid root for narrow needs. Systemd offers `AmbientCapabilities=` and `CapabilityBoundingSet=` for services.
- Drop what you do not need immediately after startup (`capset` or libcap's `cap_set_proc`), and drop from the bounding set to prevent regaining it. Run services as non-root users where possible. Beware that holding `CAP_SYS_ADMIN` is almost equivalent to root, and `CAP_SYS_PTRACE`, `CAP_DAC_OVERRIDE` and `CAP_SETUID` are likewise very strong.
- Containers receive a reduced default set; adding capabilities to a container (or `--privileged`) weakens isolation considerably.

**seccomp-bpf usage.**

1. Call `prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)`.
2. Build a filter: load the architecture field and verify it equals the expected audit architecture constant (otherwise another ABI, such as 32-bit on 64-bit, could bypass number checks); load the syscall number; compare against the list; return an action.
3. Install with `seccomp(SECCOMP_SET_MODE_FILTER, SECCOMP_FILTER_FLAG_TSYNC, &prog)` (the flag applies the filter to all threads) or the older `prctl(PR_SET_SECCOMP, ...)`.
4. Prefer an allow-list (default deny) for sandboxes; use a deny-list only to patch a known hazard in an otherwise unrestricted program.
5. Return `EPERM` or `ENOSYS` for calls that libraries probe and can live without; use `KILL_PROCESS` for calls that signal an exploit attempt. `SECCOMP_RET_LOG` helps develop a filter.
6. Use libseccomp to generate the BPF programmatically in real code; handwritten BPF is for learning and tiny filters.
7. `SECCOMP_RET_USER_NOTIF` forwards a decision to a supervisor process that can inspect memory and respond, enabling things like emulating `mount` for a container, with the caveat that a supervisor reading the target's memory has the same check-and-use race.

**Namespaces in practice.** `unshare(2)`, `clone(2)` with `CLONE_NEW*` flags and `setns(2)` create and join namespaces; the `unshare` and `nsenter` commands wrap them, and `/proc/PID/ns/*` shows which a process is in. A rootless sandbox usually does: `unshare(CLONE_NEWUSER)`, write `uid_map` and `gid_map` (and `setgroups` deny), then create mount, PID and network namespaces, `pivot_root` into a prepared directory, mount a fresh `/proc`, and `exec`. The PID namespace needs a proper init in the child (zombies accumulate otherwise). Capabilities gained in a user namespace apply only to resources owned by that namespace, so a fake root there cannot load kernel modules, but can mount tmpfs, create network devices in its own network namespace, and so on.

**Landlock usage.** Check the ABI version with `landlock_create_ruleset(NULL, 0, LANDLOCK_CREATE_RULESET_VERSION)`. Create a ruleset with the set of access rights to handle (`LANDLOCK_ACCESS_FS_READ_FILE`, `..._WRITE_FILE`, `..._EXECUTE`, `..._MAKE_REG` and so on, plus network rights in later ABIs). Add rules with `landlock_add_rule`, each naming a directory file descriptor (opened with `O_PATH`) and the rights allowed below it. Set `no_new_privs`, then call `landlock_restrict_self`. Anything not granted for a handled right is denied with `EACCES`. Handle older kernels by masking unsupported rights ("best effort") and deciding whether the sandbox is mandatory. Rights not listed in the handled set are unrestricted, so list everything you mean to control. Landlock does not restrict system calls that do not touch these resources, which is why it is combined with seccomp.

**Combining.** A common order inside a helper: open the files and sockets that will be needed; unshare namespaces and map IDs; set up mounts; drop capabilities and bound them; apply Landlock rules; set `no_new_privs`; install the seccomp filter last, because the setup itself needs calls the filter will forbid. Each step should be verified by a test that tries the forbidden action.

## Assessment: the good, the bad and the ugly

**The good.** The mechanisms are in the mainline kernel, usable by unprivileged programs (seccomp with `no_new_privs`, Landlock, user namespaces where allowed), and compose. Capabilities replace setuid root with narrow grants. Seccomp measurably reduces kernel attack surface: many kernel exploits depend on calls a sandboxed program no longer has. Namespaces provide the isolation at the core of containers. Landlock gives developers a way to confine a program to a few directories with a few lines.

**The bad.** There is no single coherent model. Each mechanism has its own vocabulary and failure behaviour, and they overlap awkwardly. Capabilities are coarse in places (`CAP_SYS_ADMIN`) and many are equivalent to root in practice. Seccomp profiles are brittle across libc and kernel upgrades and tell you nothing about arguments held behind pointers. Namespace sandboxes rely on dozens of correct setup steps; one mistake (a mount that leaks the host, a leftover descriptor, a writable `/proc/sys`) voids the isolation. Landlock covers a growing but still partial set of operations, and its ABI evolves by version.

**The ugly.** Each mechanism has had security bugs of its own. User namespaces expose complex kernel code (network configuration, mounts, netfilter) to unprivileged users and have been the starting point for many local privilege escalations, so some distributions disable unprivileged creation by default or gate it with LSM policy. Container escapes occurred through leaked descriptors, mishandled `/proc` paths and runtime bugs. Seccomp filters are subject to time-of-check/time-of-use if used with notifications. Compatibility problems are frequent: programs that probe for features fail unpredictably under a filter that returns the wrong errno, and profiles can silently deny a call needed only in a rare error path, which turns into a mysterious crash in production. A filter that does not check the architecture can be bypassed with a 32-bit syscall entry. Testing whether a sandbox really denies something requires deliberately attacking it, and sandboxes degrade silently when the kernel lacks a feature, unless the program checks the return value.

Mitigations: start from a deny-all filter built with libseccomp; check the architecture; use `SECCOMP_RET_LOG` or `strace` to build the profile and review it on each dependency update; verify each restriction with a negative test in the build; treat failure to install a sandbox as fatal; keep capability sets minimal and prefer non-root users; follow upstream guidance for rootless setups; and layer an LSM where available.

## Applications beyond this domain

- **Containers and Kubernetes**: runtimes combine namespaces, cgroups, capability dropping, seccomp profiles and LSMs. Pod security settings control which of these a workload gets.
- **Browsers**: Chrome and Firefox sandbox each renderer with namespaces and seccomp-bpf, and let a broker process open files for them via descriptor passing.
- **Service managers**: systemd units use `PrivateTmp`, `ProtectSystem`, `CapabilityBoundingSet`, `RestrictNamespaces`, `SystemCallFilter` and similar options, applying the same primitives declaratively. The course later builds a hardened unit from these.
- **Build and CI tools**: sandboxed builds (Bazel's Linux sandbox, Flatpak's bubblewrap) use user and mount namespaces to give hermetic views of the filesystem.
- **Virtualization**: QEMU and libvirt confine device-emulation processes with seccomp filters, namespaces and SELinux or AppArmor labels, so that a guest escape into the emulator lands in a small sandbox. Firecracker and Cloud Hypervisor apply per-thread seccomp filters from the start.
- **Language-level and WebAssembly sandboxes** pursue similar goals with capabilities in the runtime rather than the kernel; the idea of explicitly granted rights recurs.

## Examples

**Binding a low port without root.** A web server needs to listen on port 80. Instead of running as root, a unit grants `AmbientCapabilities=CAP_NET_BIND_SERVICE` and `User=www`. After bind, the process can drop the capability too. A compromise of the server then cannot read other users' files or load kernel modules.

**A filter that denies `mkdir`.** A converter that processes untrusted documents has no need to create directories. A seccomp filter returns `EPERM` for `mkdir` and `mkdirat`, and `KILL_PROCESS` for `ptrace` and `mount`. If an exploit tries to create a persistence directory, the call fails. The filter checks the architecture first so that the 32-bit syscall table cannot be used to bypass it.

**Rootless sandbox with `unshare`.** `unshare --user --map-root-user --mount --pid --fork --mount-proc sh` gives a shell that is root inside a new user namespace, sees only its own processes and cannot touch the host's files owned by other users. Running `ip link add` works inside a new network namespace but loading a kernel module fails, showing the limits of namespace-scoped capabilities.

**Landlock for a log processor.** A program that reads logs from `/var/log/app` and writes results to `/tmp/out` restricts itself to read below the first directory and write below the second before it parses anything. A bug in the parser that tries to open `/etc/shadow` or write into the home directory gets `EACCES`, even though the user could normally do both.

**A failing example: the profile that broke after an upgrade.** A service ran for a year under an allow-list built from a trace. After a base image update, glibc started using `clone3` for thread creation. The filter had `clone` but not `clone3`, and returned `EPERM`; the library does not fall back for `EPERM` (it falls back for `ENOSYS`), so every new thread failed. The fix was to allow the new call and to return `ENOSYS` as the default for unknown calls where fallback is intended.

**A namespace leak.** A sandbox helper created a new mount namespace but forgot to make mounts private, so a mount made inside propagated to the host. Setting propagation to private (`MS_REC | MS_PRIVATE` on `/`) is the first step after `unshare(CLONE_NEWNS)`.

## Related problems and ideas

- **Mandatory access control**: SELinux, AppArmor, Smack and Tomoyo apply administrator-written policy based on labels or paths, orthogonal to the application-driven mechanisms above.
- **eBPF-based enforcement**: BPF LSM programs and Cilium/Tetragon-style policies attach to hooks and make policy decisions, with more context than a seccomp filter.
- **Virtual machines and microVMs**: stronger isolation by a hypervisor boundary, at the cost of memory and start time. gVisor interposes a user-space kernel; Kata runs containers in lightweight VMs.
- **Capability-based operating systems**: designs such as seL4, Capsicum (FreeBSD, with `cap_enter`) and Fuchsia make explicit capabilities the only form of authority, a contrast with ambient authority in Unix.
- **Pledge and unveil** (OpenBSD): a simpler promise-based interface for self-restriction; Linux projects emulate it on top of seccomp and Landlock.
- **Memory-safe languages and compartmentalisation**: reduce the chance of compromise or split a program into compartments with different rights (privilege separation, as in OpenSSH).

## Active research

Work is ongoing on automatic generation of seccomp policies from static and dynamic analysis, with checks that a profile covers all paths a program can take; on verifying container runtimes and sandbox helpers; on reducing kernel attack surface by removing or lazily loading rarely used features; and on the safety of user namespaces, including per-namespace restrictions and LSM hooks on namespace creation. Landlock's roadmap extends coverage (network, scoping of signals and abstract sockets, more filesystem operations). Seccomp's user notification and the idea of filtering on file descriptor contents are explored for supervised sandboxes. Another strand studies speculative-execution attacks, which sandboxes cannot prevent by themselves. The version in which each Landlock right or seccomp feature arrived should be confirmed from the kernel documentation for the target system (to verify).

## Future direction

Expect more self-restriction by default in applications and runtimes, wider Landlock coverage and better library support (including in libraries such as Go and Rust crates that detect the ABI and degrade gracefully), tighter default seccomp profiles in container runtimes, and policy decisions moving to declarative service definitions. Distributions will keep adjusting the default for unprivileged user namespaces. For learners, the durable skills are: reason about what authority a process has, apply the narrowest grant at each layer, and test the denial paths as seriously as the allowed ones.
