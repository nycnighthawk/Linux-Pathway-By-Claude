# inotify, fanotify and netlink: asking the kernel to tell you what changed

## Define the problem

Many programs need to react to change rather than poll for it: an editor that reloads a file modified elsewhere, a build tool that re-runs when a source changes, a desktop that shows a new USB disk, a daemon that must know when a network interface goes down or an address is added, an antivirus scanner that must check each file before a process opens it. Polling is wasteful (it burns CPU and still misses short-lived changes) and slow (the reaction waits for the next poll). What the program wants is a subscription: tell me when this directory changes, tell me when a link goes down.

Two families of kernel interfaces answer that need on Linux. For file system events, `inotify` and `fanotify` report what happened to files and directories. For the state of the network stack and many other kernel subsystems, `netlink` provides a socket-based channel over which the kernel both answers queries and sends notifications. Together they let a user-space program stay in sync with the kernel's view of files, links, addresses, routes, neighbours and more without scanning. This slice covers the model, the event vocabulary, the reliability limits (queue overflow, races between watch and event), and typical use patterns. It does not cover kernel-internal event frameworks, `udev` rules in depth, or the audit subsystem.

## History and approaches

**Polling and `stat`.** Early tools compared modification times at intervals. The cost grows with the number of files, and renames or rapid modify-and-restore sequences are missed.

**dnotify.** The first Linux directory notification (2.4) used `fcntl(F_NOTIFY)` and signals. It needed one open descriptor per watched directory, which pinned the directory's filesystem against unmounting; it reported little detail; and signal delivery made it hard to use. It was a lesson in what not to build.

**inotify.** Added in 2.6.13 (2005), `inotify_init` returns one descriptor for a set of watches. `inotify_add_watch(fd, path, mask)` subscribes to events on a file or a directory's entries, and `read` on the descriptor returns a stream of `struct inotify_event` records (watch descriptor, mask, cookie, name length, name). It is pollable, so it fits an `epoll` loop. Limits are per user: the number of instances, watches and queued events (`/proc/sys/fs/inotify/`). Its shortcomings: watches are not recursive (the program must add one for each subdirectory and for directories created later); events name inodes' paths relative to the watch, not absolute paths; watches on a path can become stale after renames; and it does not report which process caused the event.

**fanotify.** Introduced in 2.6.36 and made usable in later kernels, `fanotify` was designed for scanners and indexers. Beyond notification it can deliver *permission events*: before an `open` or `exec` completes, the kernel blocks the operation and asks the listener to allow or deny it. Events carry an open file descriptor for the file concerned and the PID of the process involved, so a scanner can read the content and attribute the action. Marks can cover a single object, a whole mount, or a whole filesystem, which avoids per-directory watches. Later additions: `FAN_REPORT_FID` and `FAN_REPORT_DIR_FID`/`DFID_NAME` provide file handles and names so that events for creation, deletion and rename (which inotify reports, but older fanotify did not) can be seen without holding descriptors; `FAN_REPORT_PIDFD` returns a pidfd; and use is restricted for unprivileged users to the notification-only, FID-based subset on newer kernels (to verify the exact kernel version).

**Netlink.** For networking, the old interfaces were `ioctl` calls on sockets and parsing `/proc/net/*`, which was racy and limited. Netlink, a socket family (`AF_NETLINK`) introduced in the 2.2 era, carries typed messages between kernel and user space. Different *protocols* (`NETLINK_ROUTE`, `NETLINK_GENERIC`, `NETLINK_NETFILTER`, `NETLINK_KOBJECT_UEVENT`, `NETLINK_SOCK_DIAG` and others) cover different subsystems. `NETLINK_ROUTE` (rtnetlink) manages links, addresses, routes, neighbours, rules and queueing disciplines; the `ip` command is built on it. A request has an `nlmsghdr` with type, flags, sequence number and port ID, followed by a family-specific header and a list of attributes (type-length-value). Replies may be split in several messages ending with `NLMSG_DONE`; errors come as `NLMSG_ERROR` messages with a negative errno. Multicast *groups* deliver notifications of changes to subscribers (`RTMGRP_LINK`, `RTMGRP_IPV4_IFADDR`, and so on).

**Generic netlink.** Adding a new netlink protocol number for each subsystem was not sustainable, so Generic Netlink (`NETLINK_GENERIC`) multiplexes many *families* by name, resolved at run time through a controller family. Wi-Fi configuration (nl80211), team and WireGuard devices, devlink and many newer interfaces use it. Newer kernels describe families in machine-readable specifications, from which user-space code and documentation are generated.

**Device events.** The kernel announces hotplug events (a device added or removed) through `NETLINK_KOBJECT_UEVENT`; `udev` listens on this channel and applies rules. Programs that only need a few events can listen directly, though libudev or systemd's hardware database is the usual interface.

**Emerging pattern.** Subscribe to events by descriptor, plug them into the event loop, and treat the event stream as a hint that the world changed: after an overflow or a gap, resynchronise by reading the current state in full. Query and notification share one socket and one message format in the netlink case.

## Current state

**inotify usage.**

1. `fd = inotify_init1(IN_NONBLOCK | IN_CLOEXEC)`.
2. `wd = inotify_add_watch(fd, "/path", IN_CREATE | IN_DELETE | IN_MODIFY | IN_MOVED_FROM | IN_MOVED_TO | IN_CLOSE_WRITE | IN_ATTRIB)`. Watching a directory reports events for entries inside it (not subdirectory contents). Flags such as `IN_ONLYDIR`, `IN_DONT_FOLLOW`, `IN_EXCL_UNLINK` and `IN_MASK_ADD` refine behaviour.
3. Read into a buffer sized for several events (each `struct inotify_event` is followed by `len` bytes of name, null padded). Loop with the length field; never assume one event per read.
4. React: `IN_CLOSE_WRITE` is the usual "file finished being written" signal, whereas `IN_MODIFY` fires on every write. `IN_MOVED_FROM` and `IN_MOVED_TO` share a `cookie` to pair a rename. `IN_IGNORED` signals that a watch was removed (file deleted or filesystem unmounted). `IN_Q_OVERFLOW` means the queue overflowed and events were lost.
5. For a recursive watch, add watches for each existing subdirectory and for each `IN_CREATE | IN_ISDIR` event; because a directory could be filled between its creation and the arrival of the watch, scan it after adding the watch.
6. Raise `fs.inotify.max_user_watches` for tools that watch large trees; each watch costs kernel memory.

**Limits of inotify.** Events are generated for actions through the local kernel only. Changes made by another host through a network filesystem (NFS, SMB) are not reported; changes via `mmap` writes may not produce `IN_MODIFY`; `/proc` and `/sys` do not generate events reliably; and remote or FUSE filesystems depend on their implementation. Events for the same object can be coalesced when identical events are queued consecutively. Therefore inotify is an optimisation hint and a program that needs correctness (a backup, a sync tool) must still verify state by a scan, on start and after overflow.

**fanotify usage.** Initialise with `fanotify_init(FAN_CLASS_NOTIF | FAN_CLOEXEC | FAN_NONBLOCK, O_RDONLY | O_LARGEFILE)` for notification only, or `FAN_CLASS_CONTENT` or `FAN_CLASS_PRE_CONTENT` for permission events (these need `CAP_SYS_ADMIN`). Add marks with `fanotify_mark(fd, FAN_MARK_ADD | FAN_MARK_MOUNT, FAN_OPEN_PERM | FAN_CLOSE_WRITE, AT_FDCWD, "/mount/point")`. Each event gives `fanotify_event_metadata` with the event mask, a file descriptor (or none with FID reporting), and the PID. For permission events the listener writes a `fanotify_response` with `FAN_ALLOW` or `FAN_DENY`; if it fails to answer, the originating process stays blocked, so listeners must be fast, must never trigger events on themselves (use `FAN_MARK_IGNORED_MASK` or close descriptors promptly), and must handle the kernel's timeouts and the risk of deadlock if the listener itself needs access to the watched filesystem. A reasoned design keeps the scanner process out of the watched mount's critical path.

**netlink usage.** Open `socket(AF_NETLINK, SOCK_RAW | SOCK_CLOEXEC, NETLINK_ROUTE)`, `bind` with `nl_groups` for multicast groups or leave the port to the kernel for queries. Build requests with `NLMSG_*` macros; send `RTM_GETLINK`, `RTM_GETADDR`, or `RTM_GETROUTE` with `NLM_F_REQUEST | NLM_F_DUMP` to dump a table; read replies until `NLMSG_DONE`, checking `nlmsg_seq` and handling `NLM_F_DUMP_INTR` (the table changed during the dump and the dump must be restarted). Parse attributes with `RTA_*` or `NLA_*` iterators, checking lengths. A modifying request sets `NLM_F_ACK` to receive an acknowledgement or error. Receive buffer overflow shows up as `ENOBUFS` on `recv`: the process lost notifications and must resynchronise by dumping state. Libraries (libmnl, libnl, and language bindings such as `pyroute2`) hide the byte-level work, and `ip monitor` shows the notification stream.

**Newer netlink features.** Strict checking of request attributes (`NETLINK_GET_STRICT_CHK`), extended acknowledgements (`NETLINK_EXT_ACK`) that return error messages and the offending attribute, and listing of all multicast groups. These make misuse easier to diagnose; programs should set them.

**Uevent listening.** A socket on `NETLINK_KOBJECT_UEVENT` with a multicast group receives null-separated `KEY=value` strings for device add, remove, change and bind events. Messages from the kernel use group 1 and from `udev` group 2; trust only messages whose sender is the kernel (check `nl_pid` of the sender equals 0 on receive and that the credentials are root) because other processes can send to the group.

## Assessment: the good, the bad and the ugly

**The good.** Both interfaces are descriptor-based, so one event loop watches files, devices, links and sockets together. They remove polling, reduce latency and let tools scale to large trees. fanotify's mount-wide marks and permission events make on-access scanning possible without kernel modules. Netlink gives one coherent, extensible message format with strong typing of attributes, and `ip monitor`, `ss` and similar tools show that it supports complete management of the stack.

**The bad.** Neither interface is a reliable log: queues overflow and events are lost or merged. inotify is not recursive and carries limited context; fanotify's permission mode needs privilege and a careful design; behaviour differs across filesystem types. Netlink's wire format requires careful parsing with alignment and length checks; each protocol has its own conventions; and documentation was historically thin (the situation is improving with generated specifications). Message ordering across different sockets or groups is not guaranteed relative to each other.

**The ugly.** Races between "read the state" and "subscribe to changes" are easy to introduce: subscribe first, then dump, and reconcile duplicates. Editors that save by writing a temporary file and renaming over the original look like create, move and delete to a watcher, not a modification of the watched file, which breaks naive "watch this file" code (watch the parent directory instead). A listener that triggers its own events (writing a log inside the watched tree) loops. fanotify permission listeners that crash or stall freeze the system's file access to the watched mount. Netlink parsers that trust lengths have been a recurring source of vulnerabilities both in the kernel and in user-space daemons. Large watch counts consume unswappable kernel memory. Containers and namespaces change visibility: a listener sees events only for the mount namespace and network namespace it is in (for uevents and netlink), unless the program enters the other namespace.

Mitigations: treat events as hints and resynchronise after overflow; watch directories, not files; subscribe before dumping; set receive buffers large enough and handle `ENOBUFS`; use a library for netlink parsing; bound recursion and watch counts; keep fanotify handlers minimal with a timeout and a safe default; test with bursts (thousands of files created in a loop) to provoke overflow.

## Applications beyond this domain

- **Build and development tools**: file watchers in IDEs, test runners and static-site generators use inotify (or fanotify with FID reporting) for incremental rebuilds.
- **Security tools**: on-access antivirus, file integrity monitoring and EDR agents use fanotify; Falco-style systems and `auditd` use other hooks for similar goals.
- **Network management**: NetworkManager, systemd-networkd, `iproute2`, DHCP and routing daemons (FRR, BIRD), container networking plugins and service meshes use rtnetlink to configure and watch interfaces and routes.
- **Virtualization and containers**: runtimes create veth pairs, bridges and addresses through netlink; libvirt and QEMU helpers watch for interface changes; `devlink` and `ethtool` over netlink manage SR-IOV and NIC features.
- **Device management**: `udev` and `systemd-udevd` react to uevents to create device nodes and start services; mobile and desktop environments mount removable media in response.
- **Cloud and distributed systems**: file-change notification inside a node triggers agent behaviour (configuration reload), while the same principle at larger scale appears as watch APIs in coordination services and Kubernetes (the watch verb on resources).
- **Observability**: the `NETLINK_SOCK_DIAG` interface provides socket statistics for `ss`; `taskstats` and `connector` families report process events.

## Examples

**Watching a configuration directory.** A daemon watches `/etc/app/conf.d` with `IN_CLOSE_WRITE | IN_MOVED_TO | IN_DELETE`. Editors that save by rename produce `IN_MOVED_TO`, atomic-replace deploy tools produce `IN_MOVED_TO` as well, and plain writers produce `IN_CLOSE_WRITE`. The daemon debounces the burst for 100 ms and reloads once.

**A recursive watcher that misses a file.** A tool adds watches for each subdirectory. A script creates `a/b/c` and writes `c/file` immediately. The create event for `b` arrives, but by the time the tool adds the watch, `c` and `file` already exist and no event is queued for them. The fix is to scan after each added watch.

**An overflow.** A build creates 200,000 files in a burst. The inotify queue (default 16384 events) fills; the reader gets `IN_Q_OVERFLOW`. The tool falls back to a full rescan and continues. Raising `max_queued_events` helps but does not remove the need to handle the event.

**Interface down notification.** A routing agent binds a netlink socket to `RTMGRP_LINK | RTMGRP_IPV4_IFADDR`, reads `RTM_NEWLINK` messages, checks `IFF_UP` and `IFF_LOWER_UP` in the flags and withdraws routes when carrier disappears. After an `ENOBUFS` it issues an `RTM_GETLINK` dump to rebuild its view.

**A failing example: the stale dump.** A tool dumps routes and then subscribes to updates. A route changes between the end of the dump and the subscription and the tool never learns of it. The order must be subscribe first, then dump, then apply buffered updates that are newer than the dump.

**On-access scanning.** A scanner uses fanotify with `FAN_OPEN_EXEC_PERM` on a mount, reads the executable through the passed descriptor, and denies it when a signature matches. If the scanner itself runs from that mount without exclusion, the first scan of its own binary deadlocks.

## Related problems and ideas

- **Kernel-assisted tracing and observability**: eBPF programs attached to tracepoints, kprobes and LSM hooks observe file and network events in far more detail and with filtering in the kernel, at the price of privilege and complexity (see the eBPF topic).
- **Audit framework**: records security-relevant events into a reliable log with sequence numbers and backlog control, aimed at compliance rather than reaction.
- **Change journals on other systems**: Windows' USN journal and macOS FSEvents offer persistent, ordered change records, which are free of the overflow problem; Linux filesystems such as Btrfs and XFS offer snapshots and send/receive for efficient delta computation.
- **Reactive configuration**: systemd path units start a service when a file appears, using inotify under the hood; Kubernetes controllers use list-and-watch with resource versions to resynchronise.
- **Alternatives to netlink**: `/sys` and `/proc` files (text, simple, racy), `ioctl` (typed but fragile), and `io_uring` commands. Netlink's strength is multi-part atomic dumps and notifications.
- **User-space filesystems and notifications** (FUSE) can implement their own change events.

## Active research

Ongoing work includes making fanotify cover more of what inotify and auditing tools need (pre-content events for hierarchical storage and lazy loading, mount and namespace events), reporting events by file handle so that tools can follow renames across mounts, and hardening the permission path against deadlock. On the netlink side, the main activity is machine-readable family specifications and generated user-space code, richer extended acknowledgements, reduction of parsing bugs through stricter validation, and fuzzing of netlink handlers by projects such as syzkaller. Researchers also study how to give monitoring tools a lossless, ordered change feed at acceptable cost. Details about which kernel versions added each fanotify event type or restriction change should be confirmed from the current manual pages and release notes (to verify).

## Future direction

Expect fanotify to absorb more inotify use cases as FID-based reporting spreads, with unprivileged use for common cases, and expect user-space libraries to hide watch recursion and overflow recovery. Netlink will continue to move towards declarative specifications and generated clients, with new subsystems adopting Generic Netlink by default. Programs should plan for both being hints: subscribe, resynchronise, and keep a periodic reconciliation. For production agents, test overflow and namespace behaviour explicitly, and prefer maintained libraries to hand-written parsers.
