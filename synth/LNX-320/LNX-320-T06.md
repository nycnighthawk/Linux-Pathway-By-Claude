# pthreads, futexes, atomics and the memory model: sharing memory between threads

## Define the problem

A multithreaded program runs several streams of control inside one address space. This is attractive because threads share data directly, start faster than processes and use all cores. It is also where the hardest bugs in systems programming live. When two threads touch the same memory and at least one writes, the result depends on timing unless the program imposes order. Even code that looks correct on paper can fail, because compilers reorder and delete memory accesses, and processors buffer writes and let other cores observe them in a different order than the program wrote them.

Four needs follow. A program must create and manage threads and their lifetimes. It must provide mutual exclusion and waiting (locks, condition variables, barriers) that cost little when uncontended and do not burn CPU when contended. It must offer lock-free primitives, the atomic operations, for the hot paths where locks are too heavy. And it needs a precise rule for what a thread may observe from another, which is the memory model. Without that rule no program can be called correct, only "working so far".

This slice covers POSIX threads on Linux (the NPTL implementation in glibc), mutexes, condition variables and other synchronisation objects, the `futex` system call underneath them, C11 atomics and memory orders, and the common patterns and defects. Thread-safe I/O and event loops are in earlier topics; lock design inside the kernel is in the kernel courses.

## History and approaches

**Processes first.** Unix scaled by processes and by `fork`. Sharing was done with files and, later, shared memory segments. Message passing was easy to reason about, but the cost of copying and of context switches pushed programmers to threads.

**User-level and kernel-level threads.** Early thread libraries multiplexed many user-level threads on one kernel thread. They were cheap but could not use several processors and one blocking call stalled everything. Systems then moved to kernel threads, where each thread is scheduled by the kernel. Linux treated threads as processes sharing resources through `clone`. The first Linux implementation, LinuxThreads, used a manager thread, gave each thread a different PID and bent POSIX semantics on signals and process identity. It was replaced by the Native POSIX Thread Library (NPTL) in the 2.6 era, which uses one thread group per process with a common PID, the `futex` system call for blocking, and thread-local storage supported by the kernel and linker.

**Locks that sleep.** Early mutexes either spun (wasting CPU) or entered the kernel on every operation (slow). The futex idea (Fast Userspace muTEX) was to keep the lock state in user memory and make the system call only when the lock is contended. An uncontended lock or unlock is a single atomic instruction; only a thread that must wait calls `FUTEX_WAIT`, and only an unlocker who knows there are waiters calls `FUTEX_WAKE`. A well-known paper by Ulrich Drepper, "Futexes are tricky", catalogued the races and the mutex designs, and the design was refined over several kernel versions (requeue operations for condition variables, priority-inheritance futexes, robust lists).

**Atomics and memory models.** Hardware offered atomic read-modify-write instructions (compare-and-swap, fetch-and-add) long before languages gave them a meaning. Programmers used inline assembly, compiler builtins (`__sync_*`) and the kernel's own barrier macros. The Linux kernel wrote down its expectations in a long document about memory barriers. Java defined a memory model in 2004; C and C++ followed with C11 and C++11 atomics, which define atomic types, operations with a selectable memory order (relaxed, acquire, release, acquire-release, sequentially consistent) and a rule that a data race on a non-atomic object is undefined behaviour. This gave compilers and processors a contract: ordinary code may be optimised freely, and atomics mark the places where cross-thread order matters.

**Hardware differences.** x86 gives a fairly strong model (total store order): stores are seen in order, and loads can pass earlier stores to other addresses. Arm and POWER allow far more reordering, so code that happened to work on x86 can fail on Arm. This became important when servers began to move to arm64 and exposed years of latent races.

**Detection tools.** Dynamic data race detectors (ThreadSanitizer in compilers, Valgrind's Helgrind and DRD) check the happens-before relation at run time; the kernel has its own (KCSAN). Static annotations and lock-order checkers (the kernel's lockdep) catch potential deadlock before it happens.

**Emerging pattern.** Programmers prefer layered tools: message passing or per-thread ownership where possible, standard locks for shared state, and lock-free atomics only inside small, heavily tested pieces. The memory model is the base on which the library synchronisation is proved correct.

## Current state

**Threads.** `pthread_create` starts a thread running a function; `pthread_join` waits and collects a result; `pthread_detach` releases resources at exit; a thread ends with `return`, `pthread_exit` or cancellation. Attributes set stack size, detach state, scheduling and CPU affinity. Each thread has its own stack, signal mask, `errno`, and thread-local storage (`__thread`, `_Thread_local`, or `pthread_key_create`). A process-wide limit of threads exists (`RLIMIT_NPROC`, cgroup pids limit, virtual memory for stacks). Thread creation can fail with `EAGAIN`.

**Mutexes.** A `pthread_mutex_t` provides mutual exclusion. Types: normal, error-checking (returns an error on misuse), recursive (the same thread may re-lock). Attributes select process-shared mutexes (placed in shared memory), priority inheritance or protection protocols (for real-time systems), and robust mutexes (the next locker is told the owner died, with `EOWNERDEAD`). `pthread_mutex_trylock` and timed locks provide non-blocking variants. glibc's implementation uses a futex word with states for unlocked, locked and locked-with-waiters.

**Condition variables.** A condition variable lets a thread wait until a predicate over shared data becomes true. The pattern is fixed: lock the mutex; `while (!predicate) pthread_cond_wait(&cv, &m);` then act and unlock. The loop is required because waits can wake spuriously and because another thread may have consumed the condition between the signal and the wake. A signaller changes the data under the mutex and calls `pthread_cond_signal` or `broadcast`. Choose a clock for timed waits (`pthread_condattr_setclock`), usually monotonic.

**Other objects.** Read-write locks (many readers or one writer, with the usual starvation choices), barriers (wait for N threads), spinlocks (busy-wait; useful only for very short sections with no preemption concerns), semaphores (`sem_t`) and once-initialisation (`pthread_once`). The newer C11 threads API (`thrd_create`, `mtx_lock`) is thin over the same facilities.

**The futex underneath.** The `futex` system call takes the address of a 32-bit integer in user memory. `FUTEX_WAIT` checks that the word still has an expected value and, if so, puts the caller to sleep on a queue keyed by that address; the check and the sleep are atomic with respect to wakers, which is what removes the lost wake-up race. `FUTEX_WAKE` wakes up to N waiters. Variants add timeouts with absolute clocks, bitsets, requeueing waiters from a condition variable to its mutex without waking them all, priority-inheritance locking, and `FUTEX_WAIT_MULTIPLE`-style waiting on several words (newer kernels add a vectored interface). Process-private futexes skip a mapping lookup (`FUTEX_PRIVATE_FLAG`); shared ones hash on physical page and offset so that different processes can synchronise through shared memory. The skeleton of a simple mutex built on a futex has three states and is a standard exercise.

**Atomics in C11.** `<stdatomic.h>` provides `atomic_int` and similar types; `atomic_load`, `atomic_store`, `atomic_fetch_add`, `atomic_exchange` and `atomic_compare_exchange_weak/strong`. Each takes a memory order:

| Order | Meaning |
|---|---|
| relaxed | Atomicity only; no ordering with other accesses. Good for counters and statistics |
| acquire (loads) | Later accesses in this thread cannot move before the load |
| release (stores) | Earlier accesses in this thread cannot move after the store |
| acq_rel | Both, for read-modify-write |
| seq_cst | A single global order of all such operations; the default and the easiest to reason about |

The central pattern is publication: a producer writes data, then does a release store to a flag; a consumer does an acquire load of the flag and, if it sees the new value, is guaranteed to see the data. A compare-and-swap loop builds lock-free stacks, counters and queues, and brings the ABA problem (a value changes from A to B and back to A, fooling the comparison) and the need for safe memory reclamation (hazard pointers, epoch schemes, RCU).

**The model in one rule.** If two accesses to the same location conflict (one is a write) and are not ordered by a happens-before relationship, created by locks, thread creation and join, or release and acquire pairs on atomics, the program has a data race and its behaviour is undefined. A mutex unlock happens-before the next lock of the same mutex; `pthread_create` happens-before the start of the new thread; the end of a thread happens-before the return of its `join`. Declaring a variable `volatile` does not fix a race; it does not give atomicity or ordering for threads.

**Performance facts.** An uncontended mutex lock and unlock cost tens of nanoseconds. Contended locks cost a system call and a context switch, so lock convoys and false sharing (independent variables on one cache line, with each core invalidating the other's copy) can dominate. Lock-free code is not automatically faster; heavy contention on one atomic still bounces a cache line between cores. Per-thread data with occasional merging usually scales better than any shared counter.

## Assessment: the good, the bad and the ugly

**The good.** Threads give shared memory parallelism with a mature, portable API. The futex design makes the common case cheap and gives a safe route to build new primitives in user space. C11 atomics define behaviour across compilers and architectures, so lock-free code can be portable. Tools such as ThreadSanitizer find a large class of races with modest effort.

**The bad.** Data races are silent, rare and often absent from tests. A program may pass on x86 and fail on Arm because of weaker ordering. Deadlocks from inconsistent lock order, lost wake-ups from condition variables used without a predicate, priority inversion in real-time systems and signal-handling surprises are common. Relaxed atomics are easy to misuse: reasoning about orders other than sequentially consistent is difficult, and most programmers should not use them outside simple counters. Debugging by adding logging changes timing and can hide the bug.

**The ugly.** Memory-model corner cases remain: the formal C11 model has known flaws for relaxed atomics (out-of-thin-air values), and various proposals are still debated. `fork` in a threaded program is hazardous (see the process topic). Locks inside signal handlers deadlock. Thread cancellation is full of cleanup problems and is best avoided in favour of cooperative stop flags. Lock-free structures are notoriously hard to get right, and published algorithms have been found faulty after years. Very high thread counts waste memory in stacks and add scheduler overhead. Thread-local storage and dynamically loaded libraries have long had awkward interactions. Futex misuse (wrong size or alignment, mixed private and shared flags, waking without a changed value) causes hangs that look like kernel bugs.

Mitigations: keep the amount of shared mutable state small; give each piece of data one owner or one lock, documented in comments; always use the same lock order and let the lockdep-style tools check it; wait in a `while` loop over a predicate; default to sequentially consistent atomics and move to acquire/release only with a written argument; run the test suite under ThreadSanitizer and on Arm; and stress with random delays injected at synchronisation points.

## Applications beyond this domain

- **The Linux kernel** uses the same ideas with its own primitives: spinlocks, mutexes, RCU and per-CPU data, with the kernel memory model document and `READ_ONCE`/`WRITE_ONCE` marking racy accesses. The vocabulary here carries into the kernel courses.
- **Language runtimes** build their synchronisation on futexes or similar: Go's scheduler parks goroutines with futex-based primitives, the JVM and .NET use them, and Rust's standard library mutex uses futexes on Linux.
- **Databases and storage engines** use latches, reader-writer locks, and lock-free indexes and rely on memory ordering for correctness of their logs and buffer pools.
- **Lock-free queues in networking and logging** (ring buffers between a producer and a consumer thread, as in `io_uring` itself) use acquire/release publication and are often single-producer single-consumer to keep reasoning simple.
- **Virtual machines and hypervisors** care about the memory model because a guest observes the host's ordering; paravirtual locks avoid wasting time spinning on a vCPU that the host has descheduled.
- **GPUs and distributed systems** have their own models (scoped atomics, consistency levels), and the concepts of happens-before and linearizability transfer.

## Examples

**A counter and its cost.** Eight threads increment one shared integer one million times each. Unprotected, the result is wrong (lost updates). With a mutex it is correct and slow. With `atomic_fetch_add` relaxed it is correct and faster but still contends. With a per-thread counter summed at the end it is correct and scales. The three-way comparison shows the difference between correctness and scalability.

**A bounded queue.** A producer and a consumer share a ring buffer protected by a mutex and two condition variables (not-empty and not-full). The consumer waits in a loop on the predicate "count is zero". Using `if` instead of `while` fails when a second consumer steals the item between the signal and the wake.

**Publication with release and acquire.** Thread A fills a structure and then does `atomic_store_explicit(&ready, 1, memory_order_release)`. Thread B loops on `atomic_load_explicit(&ready, memory_order_acquire)` and then reads the structure. With relaxed orders the program is wrong even though x86 hides the fault; on Arm the consumer may read stale fields.

**A lost wake-up.** A hand-written mutex stores 0 or 1 and calls `FUTEX_WAKE` after every unlock without checking for waiters; the lock call tests the value, then sleeps without telling the unlocker. If the unlock slips between the test and the sleep, the waiter sleeps for ever. The design with three states (unlocked, locked, locked with waiters) and `FUTEX_WAIT` compare-before-sleep removes the window.

**A failing example: lock order.** Thread 1 locks A then B; thread 2 locks B then A. Under load both stop. A lock-order checker reports the cycle on the first run in which both orders occur, even if no deadlock happens in that run.

**False sharing.** Two threads update two different counters in adjacent array slots; throughput drops several times against padded counters because both slots share a 64-byte cache line. Aligning each counter to its own cache line restores speed.

## Related problems and ideas

- **Avoiding shared mutable state**: message passing between threads, actors, channels and immutable data, which move the problem from memory ordering to protocol design.
- **Transactional memory**: hardware and software proposals let a block of code run atomically and retry on conflict. Hardware support has been withdrawn or limited on several CPU generations, and software versions had high overhead.
- **Read-copy-update and epoch reclamation**: readers run without locks while writers publish new versions and wait for a grace period before freeing the old ones; used heavily in the kernel and available to user space in libraries.
- **Structured concurrency and async runtimes**: tasks on a small pool of threads with cooperative scheduling; they reduce thread counts and make lifetimes explicit but push the problem into the runtime.
- **Alternative models**: the Rust ownership rules prevent data races at compile time for safe code; formal models and model checkers (CDSChecker, GenMC, herd7) explore all legal executions of small programs.
- **Priority inheritance and real-time scheduling** for bounding the delay of high-priority threads that wait on locks.

## Active research

Active areas include fixing the relaxed-atomics semantics so that compilers and hardware can be both optimised and verified (the out-of-thin-air problem); verified concurrent data structures and memory reclamation; model checkers that scale to real code, including the kernel's memory model tools and the Linux-kernel litmus test suites; data race detection with lower overhead for production use; and the behaviour of concurrency on weakly ordered hardware, including studies of bugs that appeared when software was ported from x86 to Arm. Another thread is the design of user-space scheduling and synchronisation that cooperates with the kernel scheduler (restartable sequences, user-space notification of preemption) to reduce lock-holder preemption. ## Future direction

Expect more of the standard library to use futex-based primitives with improved fairness and lower overhead, new futex operations that wait on multiple words, and more programs written in languages that enforce data-race freedom. Arm and RISC-V servers will keep exposing ordering bugs, so testing on weak hardware will become routine. Standards work on C and C++ continues to refine atomics, with proposals for reclamation facilities and for hazard pointers and RCU in the C++ library. Developers should treat portable correctness as a requirement: write against the language memory model, never against the behaviour of one CPU.
