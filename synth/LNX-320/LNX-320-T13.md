# NUMA and cache effects: measuring where memory really is

## Define the problem

Programs treat memory as a flat array with uniform cost, and nothing in the code says otherwise. The hardware disagrees. A modern server core reaches data in a first-level cache in about a nanosecond, in a shared last-level cache in tens of cycles, and in main memory in around a hundred nanoseconds, and on a multi-socket machine memory attached to another socket is slower again. The same loop can run several times slower because its working set no longer fits in a cache, because two threads update variables that share a cache line, or because the memory was allocated on a different node than the CPU that uses it. These effects do not appear in correctness tests, they change with the machine, and they are invisible in the source.

A programmer therefore needs three abilities: to *predict* roughly what the memory system will do from the machine's topology; to *measure* it, with microbenchmarks and hardware counters, without fooling oneself; and to *control* placement of threads and memory with the tools the operating system offers. This slice covers the cache hierarchy and its observable effects (capacity cliffs, line size, associativity, prefetching, false sharing), NUMA topology and policy on Linux (`lscpu`, `numactl`, `mbind`, `set_mempolicy`, first-touch placement, automatic NUMA balancing), pinning with affinity, huge pages, and the discipline of measuring. Memory allocators, kernel memory management internals and virtual machine NUMA topology are treated elsewhere in the pathway, and the VIRT courses revisit placement for guests.

## History and approaches

**Flat memory.** Early computers had memory as fast as the processor. The speed gap opened in the 1980s and 1990s, and small fast caches between the two became standard. Programming models ignored them at first and relied on hardware to hide latency, which worked for sequential access and failed for pointer-heavy code.

**Cache-aware algorithms.** Blocking (tiling) of matrix algorithms, structure-of-arrays layouts, and sorting that works on cache-sized chunks reduced misses. The "cache-oblivious" family aimed at good behaviour at every level without knowing sizes. Ulrich Drepper's 2007 paper on memory for programmers collected the knowledge for working engineers and remains a standard reference, although hardware details have moved on.

**SMP and the shared bus.** Symmetric multiprocessors gave every CPU the same access time to all memory over a shared bus or switch. Scaling hit the bus limit, and cache coherence traffic became the cost of sharing: when one core writes a line, other cores' copies are invalidated, and shared data ping-pongs between caches.

**NUMA.** Non-uniform memory access systems attach memory to each processor socket (or chiplet group) and connect sockets with a fast interconnect. Local access is faster and has more bandwidth than remote access. Early NUMA machines (SGI, Sequent) were specialised; with AMD's Opteron (2003) and Intel's Nehalem (2008), multi-socket x86 servers became NUMA machines, and later single-socket chips with multiple chiplets (AMD EPYC) added NUMA-like effects inside a socket, configurable through settings such as NPS (nodes per socket).

**Operating system support.** Linux's NUMA support grew from the 2.4 and 2.6 kernels: a node-aware page allocator, memory policies (`mbind`, `set_mempolicy`; `MPOL_BIND`, `MPOL_PREFERRED`, `MPOL_INTERLEAVE`, `MPOL_LOCAL`), cpusets, the `numactl` and `libnuma` tools, and later *automatic NUMA balancing* (3.8 onward), which samples page accesses and migrates pages and tasks towards each other. Transparent huge pages reduce TLB misses; they interact with NUMA because a 2 MiB page lives on one node.

**Performance counters.** Hardware events (cache misses, remote accesses, cycles stalled on memory) are available through `perf`, and `perf c2c` reports cache lines contended between cores, which finds false sharing. Intel and AMD supply tools (VTune, uProf) with deeper detail.

**Emerging pattern.** Treat memory placement as part of the design: size working sets to cache levels, keep each thread's data local to it, pin threads, allocate memory on the node that will use it (first touch), and verify with counters rather than guesses. Hypervisors repeat the exercise for virtual machines (vCPU pinning, vNUMA).

## Current state

**Topology.** `lscpu` shows sockets, cores, threads, cache sizes and NUMA nodes with their CPU lists; `lstopo` (hwloc) draws the hierarchy; `numactl --hardware` prints nodes, their memory sizes and a *distance matrix* (10 for local, larger for remote; relative cost, not nanoseconds); `/sys/devices/system/node/node*/` and `/sys/devices/system/cpu/cpu*/cache/` give the raw data. Hyperthreads share a core's L1 and L2 caches. Cache line size is almost always 64 bytes on x86 (128 on some Arm and POWER designs).

**The cache cliffs.** A pointer-chasing benchmark walks a linked ring of random addresses over a working set of growing size and reports the time per step. Latency stays flat while the set fits in the L1 data cache, steps up when it spills into L2, steps up again for L3, and jumps to DRAM latency beyond. The steps reveal each cache's capacity (subject to associativity and prefetch effects), and the plateau heights give each level's latency. Random order defeats prefetchers; a sequential walk measures bandwidth instead. Measure with large page mappings or account for TLB reach, because translation misses add to the apparent latency.

**False sharing and true sharing.** When two threads write different variables on the same 64-byte cache line, the line moves between cores on every write, and the throughput of each falls by a large factor even though no data is logically shared. Padding or aligning per-thread data to the line size (`alignas(64)`, `__attribute__((aligned(64)))`) removes it. True sharing (many threads updating one counter) needs a different fix: per-thread partials combined later, or batching. `perf c2c record` and `perf c2c report` list the hottest shared lines and the code locations.

**NUMA policy.** Linux places a page on the node whose processor touches it first (the *first-touch* policy under the default `MPOL_LOCAL`), so initialisation by one thread can place a whole array on one node and leave other threads' accesses remote. Tools and calls:

- `numactl --cpunodebind=0 --membind=0 ./prog` runs on node 0's CPUs with memory only from node 0; `--interleave=all` spreads pages round-robin to balance bandwidth for shared data; `--preferred=N` falls back to other nodes if full.
- `mbind` and `set_mempolicy` set policy per region or per thread; `move_pages` migrates pages and reports where pages are.
- `taskset` and `sched_setaffinity` pin CPUs; cpusets and cgroup `cpuset` controllers do it for groups. Always check that the policy and the CPU set agree.
- `numastat` and `/proc/PID/numa_maps` show where a process's pages actually are; `numastat -m` and `/proc/vmstat` counters (`numa_hit`, `numa_miss`, `numa_foreign`, `numa_other`) show system allocation behaviour.
- *Automatic NUMA balancing* (`kernel.numa_balancing`) migrates pages and tasks at the cost of page faults used for sampling. It helps unpinned workloads and can hurt latency-sensitive or already pinned ones.

**Measuring properly.** A microbenchmark must: warm up (first-touch the memory, fault pages in); pin the thread (`taskset -c N`); fix the CPU frequency or at least report it; run long enough to average noise; repeat and report spread, not one run; defeat compiler optimisation (use `volatile` sinks or inspect the assembly); avoid reading uninitialised or page-zero shared memory; and compare against the hardware's published numbers or a known tool (`lmbench`, `mlc` from Intel, `stream`, `perf bench mem`, `likwid-bench`). For NUMA, run the same test with memory bound locally and remotely and compare. For production, use counters (`perf stat -e cache-misses,LLC-load-misses`, remote access events where available) and watch memory bandwidth, because many workloads are bandwidth bound.

**Huge pages.** Transparent huge pages and explicit huge pages (`hugetlbfs`, `MAP_HUGETLB`) reduce TLB misses for large working sets, a cost visible as a second step in latency plots. They can cause latency spikes from compaction (THP) and constrain NUMA placement and migration.

**Virtual machines.** A guest sees a virtual topology. Without vCPU and memory pinning aligned to the host's nodes, a guest's "local" memory may be remote. Hypervisors export vNUMA, support pinning, and may apply automatic balancing; the course revisits this later for KVM.

## Assessment: the good, the bad and the ugly

**The good.** The effects are measurable with simple tools and predictable from topology. A few rules (keep data local, avoid shared writes to one line, size working sets to caches, pin and bind) give large speedups without rewriting algorithms. Linux gives good controls and observability: policies, affinity, per-node statistics, perf counters and automatic balancing as a safety net.

**The bad.** Benchmarks are easy to get wrong: compilers delete code, prefetchers hide latency, frequency scaling and other tenants add noise, and a result on one machine does not transfer to another. Performance counters differ by CPU model and have limited slots; their names and meanings are vendor-specific. Policies interact: a task pinned to node 0 with memory interleaved over all nodes is neither local nor balanced. Automatic balancing introduces its own overhead and unpredictability.

**The ugly.** First-touch placement means that a parallel program whose initialisation runs on one thread gets all its memory on one node; the fix is a parallel initialisation that mirrors the parallel computation, which is easy to forget and invisible in profiles that show only CPU time. Containers and cgroup limits can confine CPUs but not memory placement unless the cpuset memory controls are also set. Memory-bound code scales with the number of memory controllers, not cores, so adding cores can slow things down. Hyperthreads share caches and can halve per-thread cache for cache-sensitive code. Chiplet designs expose NUMA inside a socket in ways that older tools and assumptions missed. Memory interleave settings in firmware can hide the NUMA topology from the operating system altogether, and a "single node" view can be a sign of that.

Mitigations: always print the topology and policy with every benchmark result; pin and bind for experiments; use first-touch-aware initialisation; use per-thread data with padding; check `numastat` and `numa_maps` after startup; keep automatic balancing in mind when comparing runs; and cross-check microbenchmarks against counters.

## Applications beyond this domain

- **Databases and in-memory stores** pin worker threads and memory per node, partition data by node, and often disable automatic balancing; MySQL, PostgreSQL and Redis deployment guides all discuss NUMA settings.
- **High-performance computing** uses MPI rank placement, OpenMP thread affinity (`OMP_PROC_BIND`, `OMP_PLACES`) and first-touch initialisation as standard practice, and benchmarks such as STREAM and HPL expose bandwidth limits.
- **Virtualization and cloud**: choosing instance shapes, pinning vCPUs, and exposing vNUMA to large guests (databases, SAP HANA) rely on the same measurements. This ties directly to the performance topic in the virtualization engineering course.
- **Network packet processing**: DPDK and similar frameworks place buffers and polling threads on the NIC's NUMA node to avoid remote DMA traffic.
- **Machine learning and GPU systems**: placement of data loaders relative to the PCIe root and GPU, and pinned host memory, follow the same locality rules.
- **Language runtimes and allocators**: NUMA-aware allocators (jemalloc arenas per node, tcmalloc variants) and garbage collectors (the JVM's NUMA flags) apply policy automatically.
- **Embedded and mobile**: big.LITTLE clusters have shared and private caches with analogous locality questions.

## Examples

**Reading a latency curve.** A pointer-chase run on a desktop CPU shows 1.2 ns up to a 32 KiB working set, about 4 ns up to 1 MiB, about 14 ns up to 32 MiB, and about 90 ns beyond. The steps match the cache sizes printed by `lscpu`, so the result is trusted. If a step were missing, the likely cause is a prefetcher (the walk was too regular) or huge page effects.

**False sharing.** Four threads increment their own counters stored in an adjacent array of 8-byte integers. The run takes 4.2 s. After aligning each counter to 64 bytes, it takes 0.5 s. `perf c2c` shows the single hot cache line before the fix and nothing afterward.

**First touch.** A two-socket server runs a parallel sum over a 64 GiB array initialised by `main` before spawning threads. Half the threads read remote memory and the job reaches only 60% of expected bandwidth. Initialising the array inside the parallel region, with the same thread-to-chunk mapping as the sum, places each chunk on its user's node and recovers the speed. `numa_maps` shows pages split evenly rather than all on node 0.

**Pinning a service.** A latency-sensitive daemon is started with `numactl --cpunodebind=1 --membind=1`, with its network interrupts steered to node 1 as well, because the NIC is attached there. The tail latency drops since no request touches remote memory or a remote interrupt handler.

**A failing example: interleave plus pinning.** An operator pins a process to node 0 CPUs but leaves a global `interleave=all` policy from a wrapper script. Half its memory is remote on every access, yet CPU utilisation looks normal. Only `numastat -p PID` reveals the placement.

**Automatic balancing as a surprise.** A benchmark's results differ by 20% between runs because automatic NUMA balancing migrates pages during the first minutes. Disabling it for the experiment (`sysctl kernel.numa_balancing=0`) or running long enough to reach steady state makes the comparison fair.

## Related problems and ideas

- **Memory-level parallelism and prefetching**: independent loads overlap their latency; software prefetch and hardware prefetchers hide it for predictable patterns, which pointer-chasing deliberately defeats.
- **Cache partitioning**: Intel RDT and AMD QoS (resctrl in Linux) assign cache ways and memory bandwidth to groups of tasks, limiting noisy neighbours.
- **Heterogeneous memory**: CXL-attached memory, persistent memory and HBM make nodes with no CPUs. Linux represents them as memory-only NUMA nodes with tiering (demotion and promotion by access frequency), an area of active kernel work.
- **Data-oriented design**: layout of data for the cache, as used in game engines and column stores, trades convenience for locality.
- **Lock-free and partitioned designs**: shared-nothing architectures and per-core data structures (as in Seastar) avoid cross-core traffic by construction.
- **Simulation and modelling**: roofline models relate arithmetic intensity to bandwidth and compute peaks, telling whether a kernel is memory- or compute-bound.

## Active research

Work includes memory tiering policies for CXL and heterogeneous memory (which pages to promote or demote, with what overhead), better NUMA balancing for large, mixed workloads and for virtual machines, cache and bandwidth partitioning for multi-tenant servers, accurate performance models of chiplet designs, and tools that automatically find false sharing and remote access hot spots from sampling data. Compiler and runtime research looks at data placement and layout transformations driven by profiles. Benchmarking research addresses reproducibility and the pitfalls of microbenchmarks. Specific kernel patches and hardware features mentioned in the literature should be checked against current documentation before use (to verify).

## Future direction

Memory systems will become more heterogeneous (CXL pools, high-bandwidth memory on package, more tiers), which makes placement policy more important and the single "local versus remote" model inadequate. Operating systems will increasingly manage tiers and cache partitions on behalf of applications, and tools will give clearer pictures of where memory is. Developers should expect to measure on the target hardware, record topology with every result, and treat any NUMA or cache claim without a measurement as a hypothesis. The measurements in this topic's guided lab are the pattern to follow on real hardware.
