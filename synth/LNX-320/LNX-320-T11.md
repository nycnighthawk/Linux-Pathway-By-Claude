# ptrace: controlling and observing another process, and building a tiny strace

## Define the problem

Debuggers, system call tracers, record-and-replay tools, sandbox supervisors and fault injectors share one need: to stop another process at chosen moments, read and change its registers and memory, and then let it continue, all without modifying the program. Normal process isolation forbids exactly this, so the kernel must provide a controlled exception: one process (the *tracer*) acquires authority over another (the *tracee*) under strict permission rules. The interface must deliver the tracee's events in an order the tracer can follow (system call entry and exit, signals, `exec`, `fork`, exit), keep the tracee's state consistent while it is stopped, and avoid letting a tracer subvert the system's security.

On Linux the mechanism is `ptrace(2)`. It is one system call with a long list of request codes, and it is the base of `gdb`, `strace`, `ltrace` and many others. This slice covers the model (attach, stop, resume), the requests needed to build a tracer for system calls, the options that make tracing robust for threads and children, and the permission and security limits. A working tiny `strace` is the practical goal: start a program, stop at each system call, print the call name and arguments, and print the result. Hardware debug registers, core dump analysis and kernel-side tracing (ftrace, eBPF) are mentioned only as alternatives.

## History and approaches

**Early debugging interfaces.** Version 6 Unix introduced `ptrace` for the debugger `adb`. It let a parent trace a child that asked to be traced, with a handful of requests to peek and poke memory and to single-step. The model stayed: the tracee stops, the tracer examines and modifies it through the call, and resumes it.

**Growth by accretion.** Linux added requests for registers, floating-point state, system call tracing (`PTRACE_SYSCALL`), attaching to arbitrary processes (`PTRACE_ATTACH`), and later options and events (`PTRACE_O_TRACEFORK`, `PTRACE_O_TRACEEXEC`, `PTRACE_O_TRACESYSGOOD` and so on) to follow children and distinguish stops. `PTRACE_SEIZE` (3.4) fixed a family of races in the attach logic and let the tracer attach without stopping the tracee. `PTRACE_GETREGSET` and `PTRACE_SETREGSET` with `NT_PRSTATUS` gave an architecture-neutral way to read registers. `PTRACE_GET_SYSCALL_INFO` (5.3) returns the syscall number, arguments and return value in a uniform structure, removing the architecture-specific register decoding that each tracer had needed.

**Criticism and the shape of the interface.** The call mixes many unrelated operations behind one function, has awkward semantics (tracees report events through `waitpid`, with stops encoded in the status bits), and is racy around attach and signals. Documentation describes surprising corners: a tracee that receives a signal stops and reports it, and the tracer must decide whether to pass it on; group stops and job control interact with it; and `SIGTRAP` is used for several meanings. Authors of tracers learned to rely on the options and on `PTRACE_O_TRACESYSGOOD`, which marks syscall stops with `SIGTRAP | 0x80` so they are not confused with a real `SIGTRAP`.

**Cheaper observation.** Because each traced event costs two context switches, `strace` slows syscall-heavy programs severely. Linux added `seccomp` filters that can cause the kernel to notify a tracer only for selected system calls (`SECCOMP_RET_TRACE`), and newer `strace` versions use this (`--seccomp-bpf`). Other tools avoid stopping the process: `perf trace` and `ftrace` read kernel tracepoints, and eBPF programs attached to syscall tracepoints aggregate in the kernel.

**Security hardening.** An open-ended power over another process is a prime attack target. The Yama security module added the `ptrace_scope` sysctl: level 0 permits tracing any process of the same user; level 1 limits tracing to descendants; level 2 requires `CAP_SYS_PTRACE`; level 3 disables attaching entirely. `PR_SET_DUMPABLE` and non-dumpable processes cannot be attached by unprivileged tracers; set-user-ID execution disables tracer privileges across `exec`. Container runtimes block `ptrace` by default in seccomp profiles on older kernels, and many allow it again on newer kernels where attach restrictions improved (to verify the status for the runtime in use). `process_vm_readv` and `/proc/PID/mem` give memory access under similar checks.

**Record and replay.** Tools such as `rr` use ptrace and hardware performance counters to record all non-deterministic inputs of a process and replay it exactly, allowing reverse debugging. They show how far the interface can be pushed and where its limits are (hardware counter requirements, handling of shared memory).

**Emerging pattern.** Use `ptrace` when you must stop and modify a process; use `seccomp` notification, eBPF, `perf` or `ftrace` when you only observe or filter. Keep tracer logic small and event-driven.

## Current state

**The model.** A tracee is in one of two states: running or stopped (*ptrace-stop*). While stopped, the tracer may use `PTRACE_PEEKDATA`/`POKEDATA` or `process_vm_readv` for memory, `PTRACE_GETREGS` or `GETREGSET` for registers, and `PTRACE_SETREGS` to modify them. The tracer resumes with `PTRACE_CONT`, `PTRACE_SYSCALL` (run to the next syscall boundary), `PTRACE_SINGLESTEP` or `PTRACE_LISTEN`. The tracer waits for events with `waitpid`, then decodes the status: `WIFSTOPPED`, the stop signal, and the event code in the high bits of the status (`status >> 16`).

**Becoming a tracer.** Two ways:

- *The tracee asks to be traced:* `ptrace(PTRACE_TRACEME)` in a child after `fork`, followed by `exec`. The kernel stops the child with `SIGTRAP` at the `exec`. The parent waits for that stop before issuing requests. This is how a tool starts the program it traces.
- *The tracer attaches:* `PTRACE_ATTACH` or the preferred `PTRACE_SEIZE` with options, on an existing PID. Permission is checked against credentials, capabilities, dumpability and Yama. `PTRACE_INTERRUPT` stops a seized tracee.

**Tracing system calls.** After setting `PTRACE_O_TRACESYSGOOD`, loop: `PTRACE_SYSCALL`, `waitpid`, and if the stop signal is `SIGTRAP | 0x80`, this is a syscall stop. Stops alternate between *entry* and *exit* for each call; the tracer must keep a flag toggling between them, or use `PTRACE_GET_SYSCALL_INFO`, which reports which kind of stop it is. At entry the registers hold the call number and arguments (on x86-64 the number is in `orig_rax` and the arguments in `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9`); at exit `rax` holds the result, negative errno for failure. The tracer may change the number or arguments at entry (to block or redirect a call) and the return value at exit (to fake a result), which is how fault injection works. `execve` is special: after it succeeds the registers describe a new program and an extra `SIGTRAP` stop may follow unless `PTRACE_O_TRACEEXEC` is set.

**Reading arguments.** Pointer arguments are addresses in the tracee. Use `process_vm_readv` (one copy, no stops needed for each word) or `PTRACE_PEEKDATA` in word-size units to read strings; stop at the terminating NUL and cap the length. Decode flags and structures per call using tables; a tiny `strace` can handle a handful of calls (`openat`, `read`, `write`, `close`) and print the rest as raw numbers.

**Following children and threads.** `PTRACE_O_TRACEFORK`, `TRACEVFORK`, `TRACECLONE` make the tracee report creation of children and automatically trace them, delivering a stop with the new PID in the event message (`PTRACE_GETEVENTMSG`). The tracer then must `waitpid(-1, ..., __WALL)` to receive events from all tracees, keep a table of per-thread state (the entry/exit flag, saved registers), and resume each separately. `PTRACE_O_EXITKILL` kills the tracee if the tracer dies, which prevents orphaned half-stopped programs. Threads of a tracee are traced one by one; each ptrace stop affects only one thread.

**Signals.** When the tracee receives a signal, it stops and the tracer sees a signal-delivery stop. The tracer resumes with the signal number as the data argument to pass it on, or with 0 to suppress it. Dropping every signal breaks programs; passing `SIGTRAP` blindly confuses debuggers. Distinguish by `PTRACE_GETSIGINFO` (the `si_code` tells a real signal from a ptrace-generated stop).

**Permissions and security.** The tracer must be allowed by `ptrace_may_access`: same UID with the Yama scope satisfied, or `CAP_SYS_PTRACE`. A tracee that executes a set-user-ID program is not given the extra privilege while traced by an unprivileged tracer. Only one tracer may be attached to a process at a time, so a debugger and `strace` cannot both attach. Seccomp filters on the *tracer* may prevent the call; containers frequently do this. With user namespaces, `CAP_SYS_PTRACE` is relative to the namespace.

**Building a tiny strace.** The outline:

1. `fork`. In the child: `ptrace(PTRACE_TRACEME)`, `raise(SIGSTOP)` (or rely on the stop at `exec`), then `execvp`.
2. In the parent: `waitpid` for the first stop; `ptrace(PTRACE_SETOPTIONS, pid, 0, PTRACE_O_TRACESYSGOOD | PTRACE_O_EXITKILL)`.
3. Loop: `ptrace(PTRACE_SYSCALL, pid, 0, sig)`; `waitpid(pid, &status, 0)`; if the process exited (`WIFEXITED`) or was killed, print the end and stop; if the stop signal is `SIGTRAP | 0x80`, toggle the entry/exit state; on entry read the syscall number (and arguments) and remember them; on exit read the return value and print `name(args) = ret`, translating negative values to `-1 ERRNO (message)`; other signals are passed on as the next resume signal.
4. Map numbers to names with a table generated from the kernel's headers for the architecture.

**Alternative uses.** The same skeleton, with a handler that changes registers at entry or exit, builds a fault injector (return `ENOSPC` for the third `write`), a sandbox (deny `connect`), or a record tool. A seccomp filter returning `SECCOMP_RET_TRACE` stops the tracee only for chosen calls, with the tracer reading the filter's data in the event message.

## Assessment: the good, the bad and the ugly

**The good.** One interface gives a debugger everything it needs, on any process, without recompilation. It exposes real registers and memory, so tools are faithful. The newer options and `GET_SYSCALL_INFO` make syscall tracers short and portable across architectures. The ability to rewrite calls and results makes fault injection and sandboxing possible with ordinary code.

**The bad.** The interface is hard to use correctly: stops are reported through `waitpid` with overloaded signal numbers and status bits; the entry/exit state must be tracked per thread; and attach races exist in the older request. The overhead is high (two context switches per call), so tracing changes timing and slows servers heavily. Only one tracer per process makes it impossible to run two tools at once, and a tracer that dies mid-stop can leave a tracee blocked unless `EXITKILL` or detach is used. Tracees see ptrace effects: syscalls are interrupted with `EINTR`-like behaviour in some cases and timing changes.

**The ugly.** Decoding is architecture specific, with different register names and numbering across x86-64, arm64 and 32-bit compatibility modes. A 32-bit process on a 64-bit kernel uses a different syscall table, and a tracer that does not check the personality will print wrong names; this is the same trap as in seccomp filtering. Reading strings via `PEEKDATA` is slow and racy (the tracee's other threads may change memory while one thread is stopped; while stopped, other threads keep running unless the tracer stops them too). Security checks have a long record of bugs: tracers can be abused for privilege escalation and for bypassing seccomp filters (`SECCOMP_RET_TRACE` depended on a trusted tracer), and so the interface keeps getting tightened, which sometimes breaks legitimate tools in containers and hardened systems. Anti-debugging programs exploit the one-tracer rule by tracing themselves.

Mitigations: use `PTRACE_SEIZE` with options; always set `PTRACE_O_EXITKILL`; check the syscall ABI per stop (`PTRACE_GET_SYSCALL_INFO` reports the architecture); read memory with `process_vm_readv`; use seccomp-assisted tracing for lower overhead; fall back to eBPF or `perf trace` when production overhead matters; and use Yama and capability policy to control who may trace.

## Applications beyond this domain

- **Debuggers** (gdb, lldb on Linux) are built on `ptrace` for breakpoints (inserting an int3 instruction and restoring it), single-stepping, watchpoints (via debug registers set with `POKEUSER`) and inspection of core and live state.
- **Tracers and profilers**: `strace` and `ltrace`; sampling profilers that stop a process to unwind its stack in some modes.
- **Sandbox supervisors and compatibility layers**: older gVisor and `proot` use `ptrace` to intercept system calls and redirect paths, which is how `proot` offers a fake root and chroot without privileges, at a performance cost.
- **Fault injection and chaos testing**: tools alter results to test error handling in software before failures happen in production.
- **Record and replay and reverse debugging**: `rr` for deterministic reproduction of flaky bugs and concurrency failures.
- **Anti-cheat and malware analysis**: monitoring programs for suspicious behaviour, and conversely malware that detects tracing.
- **Checkpoint and restore (CRIU)** uses `ptrace` (via a "parasite" code injection technique) to take control of a process and dump its state, tying this topic to container migration.

## Examples

**Counting calls.** A tiny tracer runs `ls`, counts each system call number seen at entry, and prints a table: `openat` many times, `getdents64`, `write`, and `exit_group`. Comparing the counts with `strace -c ls` checks the tracer.

**A wrong exit state.** A tracer prints each call twice with wrong results, because it missed the stop after `execve` and its entry/exit toggle is off by one. Using `PTRACE_O_TRACEEXEC` or `GET_SYSCALL_INFO` removes the guess.

**Following a shell pipeline.** Tracing `sh -c 'cat file | wc -l'` with only the initial PID shows nothing after the `fork`. With `PTRACE_O_TRACEFORK` and `waitpid(-1, __WALL)`, the tracer sees the children's calls, and records the pipe creation and descriptor duplication.

**Faking a failure.** At the exit stop of the third `write`, the tracer sets `rax` to `-ENOSPC`. The traced program sees a full disk and its error path runs, without any real disk filling up.

**A failing example: the container.** A user runs `strace -p 1234` inside a container and gets `Operation not permitted`. The runtime's seccomp profile disallows `ptrace`, or the container lacks `CAP_SYS_PTRACE`. The options are to run the tracer from the host, add the capability to a debug container deliberately, or switch to a tool that needs no ptrace (perf, eBPF).

**A 32-bit trap.** A tracer prints `mmap2` as `ioctl` for a 32-bit process on a 64-bit host because it uses the 64-bit table. Checking the architecture reported with the syscall info fixes the table choice.

## Related problems and ideas

- **Seccomp user notification**: lets a supervisor process make decisions for specific calls of a sandboxed process without stopping it for every call. It is better for policy, but it does not give register or memory access.
- **eBPF tracing and bpftrace**: low-overhead observation inside the kernel, with filtering, but not modification of the traced process (apart from limited helpers).
- **Dynamic binary instrumentation**: frameworks such as Valgrind, Pin and DynamoRIO rewrite code in the traced process itself rather than controlling it from outside, giving finer detail at high slowdown.
- **Kernel debugging**: `kgdb`, `kprobes`, `uprobes` place probes in running code with kernel support, and `uprobes` provide breakpoints in user programs without ptrace.
- **Virtualization-based introspection**: hypervisors can observe guest processes with no cooperation from the guest kernel, which is related to the VIRT pathway.
- **Process-introspection descriptors**: `pidfd_getfd` copies a descriptor from another process (with ptrace-level permission), and `process_madvise` acts on another process's memory.

## Active research

Research focuses on lower-overhead tracing (seccomp and eBPF assisted), on making ptrace-based sandboxes safe (TOCTOU defences when a supervisor inspects arguments), on deterministic replay for modern hardware including newer CPU performance counters and for multicore programs, and on better interfaces than a monolithic request multiplexer. Another thread studies the security of ptrace and its alternatives under container workloads, with proposals for finer permission models (per-process-tree ptrace permission, namespace-aware checks). Debugging support for new language runtimes (JIT, garbage collected) and for heterogeneous code stretches the model. Which proposals have been merged should be checked against the current kernel documentation (to verify).

## Future direction

Expect `strace` and similar tools to depend less on stopping the tracee, using seccomp-assisted and eBPF-assisted modes. Expect ptrace to stay the base for debuggers, with tighter default policy on hardened distributions and in containers, and with new, narrower interfaces for specific jobs (pidfd-based operations, seccomp notification) replacing some uses. For learners, the lasting value is the mental model of stops, events and registers, which transfers to hypervisor debugging and kernel tracing.
