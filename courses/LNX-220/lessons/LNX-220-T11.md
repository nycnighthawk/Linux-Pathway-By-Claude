# Profiling with perf and flame graphs

This lesson follows the topic synthesis `synth/LNX-220/LNX-220-T11.md`, which carries the sources and the history.

## What you will be able to do

- Run the measurement loop: workload, baseline, profile, one change, re-measure.
- Use `perf stat`, `perf record`, `perf report` and `perf top` and read the output.
- Produce and read a flame graph, and say what makes stacks unusable.
- Fall back to callgrind or gprof when `perf` is not available.

## The loop

State the workload and one metric (time, instructions, memory). Take a baseline several times. Profile. Form a hypothesis from the widest frames. Change one thing. Measure again and keep the change only if the metric moves beyond noise.
Profile the optimised build you ship (`-O2`), never a sanitized one.

## perf

```bash
perf stat ./prog                         # cycles, instructions, IPC, branch and cache misses
perf record -F 99 -g -- ./prog           # sample at 99 Hz with call graphs
perf record -a -g -- sleep 30            # all CPUs
perf record -p PID -g -- sleep 10        # a running process
perf report --stdio                      # distribution by symbol
perf annotate --stdio SYMBOL             # hot instructions
perf top -p PID                          # live view
```

Low instructions per cycle (below about 1) suggests stalls such as cache misses. Hardware counters may be missing in VMs; `perf` then falls back to software clocks. `kernel.perf_event_paranoid` and `CAP_PERFMON` control access; many containers block the call.

## Flame graphs

```bash
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
```

Each distinct stack is aggregated; box width is the share of samples that include the frame; the x axis is alphabetical, not time; height is depth. Look for wide plateaus at the top: those functions were on the CPU themselves. Follow them downwards to find the callers.
The intermediate text, folded stacks, has one line per stack (`main;a;b 42`), which many tools read.

## Making stacks usable

Build with `-fno-omit-frame-pointer -g`, or record with `--call-graph dwarf` (costly) or use LBR where available. Keep symbols (see [LNX-220-T01](lesson:LNX-220-T01)). Interpreted and JIT languages need extra support (perf map files, Python's perf trampoline).

## Without perf

`valgrind --tool=callgrind ./prog` counts instructions exactly and deterministically; `callgrind_annotate callgrind.out` ranks functions and KCachegrind shows callers. `gcc -pg` with `gprof` gives a flat profile. `strace -c` and `perf trace -s` summarise
system calls, `/usr/bin/time -v` gives resource totals.

## Worked example: a quadratic hot spot

A program prints the number of equal pairs in 4000 values. The callgrind report puts almost all instructions in `count_dups`, a double loop. Replacing it with sort-and-count-runs cuts the executed instructions by more than an order of magnitude with identical output.
Because callgrind counts instructions, the comparison is exact and can run in a test. A wall-clock comparison on a laptop would also measure thermal throttling.
