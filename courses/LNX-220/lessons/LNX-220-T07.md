# C, Rust, Go and Python toolchains

This lesson follows the topic synthesis `synth/LNX-220/LNX-220-T07.md`, which carries the sources and the history.

## What you will be able to do

- Install and select toolchains for C, Rust, Go and Python without touching the system ones.
- Say for each language how dependencies are declared and pinned and what the build produces.
- Predict whether a binary is dynamically or statically linked and verify it with `readelf`.
- Create an isolated Python environment and explain why it matters on a distribution.

## One contract, four ecosystems

Each ecosystem answers the same four questions: which toolchain version, which dependencies, which exact content (the lock), and what artefact comes out.

| | Toolchain | Declared deps | Lock | Output |
|---|---|---|---|---|
| C | distribution gcc/clang, GCC Toolset on RHEL | `pkg-config`, build system | none (distribution) | dynamic by default |
| Rust | `rustup`, `rust-toolchain.toml` | `Cargo.toml` | `Cargo.lock` | dynamic libc, static with musl or `crt-static` |
| Go | `go` tarball or package, `toolchain` line in `go.mod` | `go.mod` | `go.sum` | static when `CGO_ENABLED=0` |
| Python | system interpreter plus `venv` | `pyproject.toml` | requirements or lock file | source plus interpreter, wheels for extensions |

## Commands

```bash
# Rust
rustup toolchain install stable && cargo build --release --locked
rustc -O -C target-feature=+crt-static hello.rs
# Go
go mod init hello && CGO_ENABLED=0 go build -trimpath -o hello .
GOOS=linux GOARCH=arm64 go build
# Python
python3 -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt
python -m build        # sdist and wheel from pyproject.toml
```

Distributions mark their own Python as externally managed, so `pip install` into it is refused; use a virtual environment or `pipx`. Offline or packaged builds use `cargo vendor` and `-mod=vendor`.

## Check what you built

```bash
readelf -lW bin | grep INTERP        # present: dynamic, loaded by ld.so
readelf -dW bin | grep NEEDED        # shared libraries it needs at run time
file bin ; ldd bin                    # the same, readable
```

## Worked example: a Go tool that fails on an older host

Built on a recent runner with cgo enabled, the binary needs a newer glibc than the target has, and fails with a version error. `CGO_ENABLED=0 go build` produces a static binary if no C code is needed. If C is needed,
build in a container image that matches the oldest supported target. The same logic applies to Rust (target musl, or build on an older base) and to Python wheels, whose `manylinux` tag names the oldest glibc they support.
