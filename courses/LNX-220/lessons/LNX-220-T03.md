# Shared libraries, sonames and pkg-config

This lesson follows the topic synthesis `synth/LNX-220/LNX-220-T03.md`, which carries the sources and the history.

## What you will be able to do

- Build a shared library with the three-name layout and a correct soname.
- Hide internal symbols and decide whether a change needs a new soname.
- Describe the loader's search order and diagnose "cannot open shared object file".
- Write a `.pc` file and consume it with `pkg-config`.

## The three names

`libfoo.so.1.4.2` is the real file. `libfoo.so.1` is the soname, stored in the library and recorded in every program linked against it. `libfoo.so` is the linker
name used by `-lfoo`. The soname changes only when the binary interface breaks. In packages the first two live in the library package and the
third, with headers, in the `-devel` or `-dev` package.

```bash
cc -fPIC -fvisibility=hidden -shared -Wl,-soname,libvec.so.1 -o libvec.so.1.2.0 vec.c
ln -s libvec.so.1.2.0 libvec.so.1
ln -s libvec.so.1 libvec.so
nm -D --defined-only libvec.so.1.2.0
```

## What breaks the ABI

Safe: adding a function, fixing a bug inside a function. Not safe: changing an argument type, removing a function, reordering or resizing a public struct, changing an enum's
size. Use opaque structs with accessors so the layout can change. `-fvisibility=hidden` plus an export macro keeps the interface small; a linker version script
(`-Wl,--version-script=libvec.map`) can also attach version tags as glibc does. `abidiff` from libabigail compares two builds.

## Finding libraries at run time

Order from `ld.so(8)`: `DT_RPATH` when there is no `DT_RUNPATH`, `LD_LIBRARY_PATH`, `DT_RUNPATH`, `/etc/ld.so.cache`, then `/lib` and `/usr/lib`. `ldconfig` builds the cache from
`/etc/ld.so.conf` and `/etc/ld.so.conf.d/`. For a private bundle link with `-Wl,-rpath,'$ORIGIN/../lib'`.

```bash
ldd ./app | grep 'not found'            # do not run ldd on untrusted binaries
readelf -d ./app | grep -E 'NEEDED|RUNPATH'
ldconfig -p | grep libvec
LD_DEBUG=libs ./app 2>&1 | head
```

## pkg-config

```
prefix=/usr
libdir=${prefix}/lib
includedir=${prefix}/include

Name: vec
Description: Tiny vector library
Version: 1.2.0
Libs: -L${libdir} -lvec
Cflags: -I${includedir}
Requires.private: zlib
```

`pkg-config --cflags --libs vec` prints the flags; `--modversion`, `--exists` and `--atleast-version=1.2` test; `PKG_CONFIG_PATH` adds search directories. `Requires:` names other `.pc` packages whose flags are added to yours, because your public headers or API expose them; `Requires.private:` names packages needed only when linking statically: their compiler flags are still included, but their link flags are added only with `--static`. Meson and CMake
can read these files and Meson can generate them.

## Worked example: the service that cannot find its library

A program runs from the developer's shell because the profile exports `LD_LIBRARY_PATH`. As a systemd service it fails with a shared-object error. `ldd` shows `not found`.
The fix is to install the library where the cache covers it (a file in `/etc/ld.so.conf.d/` then `ldconfig`), or relink with an `$ORIGIN` run path. Two copies of one soname in
different directories explain "works on one host only": `LD_DEBUG=libs` shows which one was chosen.

## Connections

`DT_NEEDED`, `DT_SONAME` and `DT_RUNPATH` are ELF fields from [LNX-220-T01](lesson:LNX-220-T01). Build systems generate the symlinks and `.pc` files ([LNX-220-T02](lesson:LNX-220-T02)). Packaging turns
sonames into automatic dependencies ([LNX-220-T10](lesson:LNX-220-T10)). Python extension modules and Rust `-sys` crates are shared objects too ([LNX-220-T07](lesson:LNX-220-T07)), and sanitizers use the same preload
and interposition mechanisms ([LNX-220-T05](lesson:LNX-220-T05)).
