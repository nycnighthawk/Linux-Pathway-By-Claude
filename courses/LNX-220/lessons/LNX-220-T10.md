# Packaging apps: RPM, DEB, Flatpak and OCI

This lesson follows the topic synthesis `synth/LNX-220/LNX-220-T10.md`, which carries the sources and the history.

## What you will be able to do

- Choose a package format for an audience: administrators, desktop users or operators.
- Build a binary DEB from a staged tree and outline the RPM spec that does the same.
- Describe what a Flatpak manifest and an OCI image contain and how each is verified.
- Explain why clean build roots, pinned versions and digests matter.

## The common shape

Stage an install tree (`DESTDIR`), describe the metadata (name, version, dependencies, entry points, permissions), build in a clean environment, sign, publish and let a client verify and install. The formats differ in who resolves dependencies,
how much is isolated and what the unit of update is.

## RPM

`rpmbuild -ba name.spec`, ideally inside `mock`. Header: `Name`, `Version`, `Release`, `License`, `Summary`, `Source0`, `BuildRequires`, `Requires`. Sections: `%prep`, `%build`, `%install` (into `%{buildroot}`), `%check`, `%files`
(with `%config(noreplace)`, `%doc`, `%license`), `%changelog`. Scriptlets use macros such as `%systemd_post`. Sign with `rpmsign`; index repositories with `createrepo_c`.

## DEB

A source package has `debian/control`, `rules`, `changelog` and `copyright`; build with `dpkg-buildpackage -us -uc` or in an `sbuild` chroot; `dh_shlibdeps` fills library dependencies and `dh_strip` makes `-dbgsym` packages. For a hand-made package:

```bash
mkdir -p stage/DEBIAN
cat > stage/DEBIAN/control <<'X'
Package: hello
Version: 1.0
Architecture: all
Maintainer: You <you@example.org>
Depends: coreutils
Description: tiny example tool
X
dpkg-deb --root-owner-group --build stage hello_1.0_all.deb
dpkg-deb -I hello_1.0_all.deb ; dpkg-deb -c hello_1.0_all.deb
```

`--root-owner-group` stores the files as owned by root regardless of who built them.

## Flatpak

A manifest names the application ID (reverse DNS), runtime and SDK versions, permissions in `finish-args` (`--socket=wayland`, `--filesystem=xdg-documents:ro`, `--talk-name=...`) and modules with pinned sources. `flatpak-builder` builds in a sandbox
without network; users add a remote, install and receive delta updates. Check permissions with `flatpak info --show-permissions APP` and narrow them with `flatpak override --user`.

## OCI images

An image is a manifest pointing to a config and to layer blobs, all addressed by SHA-256. The config lists `diff_ids`, the digests of the uncompressed layers; the manifest lists the compressed blob digests and sizes; an index lists manifests. Build with a
Containerfile (`podman build`), use multi-stage builds to keep toolchains out of the final image, run as a non-root user, pin base images by digest and never copy secrets into any layer: a later layer that deletes a file does not remove it from an earlier layer.

## Worked example: "builds only on my machine"

An RPM that omitted a `BuildRequires` builds on the developer's box (the header is installed) and fails in `mock`, which holds only declared packages. That is exactly the purpose of a clean root. In the lab you verify an OCI layout by hand: edit one byte in the layer blob and the digest
no longer matches the manifest, so a runtime would refuse it.
