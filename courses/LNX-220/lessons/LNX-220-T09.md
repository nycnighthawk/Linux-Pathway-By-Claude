# D-Bus services and XDG conventions

This lesson follows the topic synthesis `synth/LNX-220/LNX-220-T09.md`, which carries the sources and the history.

## What you will be able to do

- Explain the system and session buses, names, object paths, interfaces, methods, signals and properties.
- Call and inspect a service with `busctl`, and start a throw-away session bus for tests.
- Write a bus activation file for a service.
- Place configuration, data, state, cache and runtime files in the correct XDG directory.

## The bus model

Two buses: the system bus (one per machine, policy in `/usr/share/dbus-1/system.d/`) and a session bus per login (address in `DBUS_SESSION_BUS_ADDRESS`, usually `/run/user/UID/bus`). A service owns a well-known name such as
`org.freedesktop.Notifications`, exports objects at paths (`/org/example/Lab`) that implement interfaces (`org.example.Lab`) with methods, signals and properties. Types use signatures: `s` string, `i` int32, `a` array, `a{sv}` dictionary,
`(si)` struct.

```bash
busctl --user list
busctl --user tree org.example.Lab
busctl --user introspect org.example.Lab /org/example/Lab
busctl --user call org.example.Lab /org/example/Lab org.example.Lab Echo s there
busctl --user get-property org.example.Lab /org/example/Lab org.example.Lab Greeting
busctl --user monitor org.example.Lab
dbus-run-session -- bash      # private session bus for tests
```

## Activation

A file `share/dbus-1/services/org.example.Lab.service` (searched in every directory of `XDG_DATA_DIRS`) contains:

```
[D-BUS Service]
Name=org.example.Lab
Exec=/usr/libexec/lab-server
```

A call to the name starts the program and holds the message until the name is taken. On the system bus, `SystemdService=` hands the start to systemd and `User=` selects the account.

## XDG directories

| Variable | Default | For |
|---|---|---|
| `XDG_CONFIG_HOME` | `~/.config` | user configuration |
| `XDG_DATA_HOME` | `~/.local/share` | user data, icons, desktop files |
| `XDG_STATE_HOME` | `~/.local/state` | logs, history, state worth keeping |
| `XDG_CACHE_HOME` | `~/.cache` | disposable data |
| `XDG_RUNTIME_DIR` | `/run/user/UID` | sockets and pipes, mode 0700, removed at logout |
| `XDG_CONFIG_DIRS`, `XDG_DATA_DIRS` | `/etc/xdg`, `/usr/local/share:/usr/share` | system search lists |

Read from the user directory first and then the list; write only to the user directory; create directories lazily with mode 0700; never hard-code `~/.config` (use `g_get_user_config_dir()`, `QStandardPaths`, `platformdirs`).

## Worked example: the config file that was not found

The lab service reads `$XDG_CONFIG_HOME/lab/greeting`. The grader sets `XDG_CONFIG_HOME` to a directory inside the lab, so a program that hard-coded `~/.config` would answer with the default greeting. The first `busctl call` also shows
activation: the name has no owner, the bus finds the service file through `XDG_DATA_DIRS`, starts the server, and the call completes. Over ssh or under cron there may be no session bus at all (`DBUS_SESSION_BUS_ADDRESS` unset); `dbus-run-session` or
`systemd-run --user` supplies one.
