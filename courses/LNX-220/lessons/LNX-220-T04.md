# gdb, core dumps and valgrind

This lesson follows the topic synthesis `synth/LNX-220/LNX-220-T04.md`, which carries the sources and the history.

## What you will be able to do

- Build a program so it can be debugged and run it under gdb interactively and in batch mode.
- Capture, store and read back a core dump, including with `coredumpctl`.
- Read a valgrind report and decide which finding to fix first.
- Choose the right tool for a crash, a hang and a silent memory error.

## Make the build debuggable

Use `-g` and `-O0` (or `-Og`) while debugging. Keep the debug data of release builds in separate files matched by build ID (see [LNX-220-T01](lesson:LNX-220-T01));
`DEBUGINFOD_URLS` lets gdb fetch it. At `-O2` variables may show as optimised out.

## gdb essentials

```
gdb ./prog                 run args | start | break file.c:42 | break func if n > 3
next | step | finish | until | continue
bt | bt full | frame 2 | info locals | print *ptr | x/16xb buf
watch counter | catch syscall write | info threads | thread apply all bt
```

Batch mode for scripts and CI: `gdb -batch -ex run -ex bt ./prog`. Attach with `gdb -p PID` (the Yama `ptrace_scope` setting may require root). Remote work:
`gdbserver :2345 ./prog` on the target and `target remote host:2345` on the host. ASLR is disabled inside gdb by default.

## Core dumps

A core is an ELF file of type `CORE` with registers and memory. Whether one is written depends on `ulimit -c`, `/proc/sys/kernel/core_pattern`, permissions and the
filesystem. On systemd machines the pattern pipes dumps to `systemd-coredump`:

```bash
coredumpctl list
coredumpctl info PID
coredumpctl debug PID          # opens gdb on the dump
gdb -batch -ex bt ./prog core.crash
gcore PID                      # snapshot a live process
```

For services set `LimitCORE=` in the unit ([LNX-220-T08](lesson:LNX-220-T08)). Cores can hold secrets: restrict permissions and retention.

## valgrind memcheck

```bash
valgrind --leak-check=full --track-origins=yes --error-exitcode=9 ./prog
```

Read each error from the top: the first stack is the bad access, the second is where the block was allocated or freed. Categories: invalid read or write, use of uninitialised values, mismatched free,
definitely, indirectly and possibly lost, still reachable. Expect a 10 to 50 times slowdown. `--suppressions=file` hides known third-party noise; `--vgdb=yes` lets gdb attach.

## Worked example: null pointer from a failed lookup

`gdb -batch -ex run -ex bt ./crash` prints frame 0 in `show()` at a source line. `frame 0`, `print r` shows `0x0`; `frame 1` shows the caller that passed an id that was not in the table. The fix is a check in
`show()`. Then `valgrind --leak-check=full ./fixed` reports a definite leak of the scratch buffer, which you free. A hang is different: `gdb -p PID` then `thread apply all bt` shows which threads wait on which lock.
