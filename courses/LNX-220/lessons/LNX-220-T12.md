# GUI applications (GTK and Qt) under Xvfb

This lesson follows the topic synthesis `synth/LNX-220/LNX-220-T12.md`, which carries the sources and the history.

## What you will be able to do

- Say how a GUI program finds its display and which variables select the backend.
- Run a graphical program headlessly with `xvfb-run` and take a screenshot.
- List what a toolkit needs besides a display: a session bus, a runtime directory, fonts.
- Explain why screenshots and synthetic input work differently under Wayland.

## How a program finds its screen

X11: `DISPLAY` names the server (`:0`, `:99`) and `XAUTHORITY` holds the cookie. Wayland: `WAYLAND_DISPLAY` names a socket in `XDG_RUNTIME_DIR`. GTK picks a backend with `GDK_BACKEND=x11` or `wayland`; Qt with `QT_QPA_PLATFORM`
(`xcb`, `wayland`, `offscreen`, `minimal`). With none reachable, programs exit with an error about the display.

## Headless on X

```bash
xvfb-run -a -s "-screen 0 1280x720x24" ./app                 # starts Xvfb, sets DISPLAY, cleans up
xvfb-run -a dbus-run-session -- ctest --test-dir build       # display plus session bus
Xvfb :99 -screen 0 1280x720x24 & export DISPLAY=:99          # long-lived display for CI or a service
import -window root shot.png                                  # screenshot (ImageMagick); also xwd, scrot
convert shot.png -format '%[pixel:p{10,10}]' info:           # read a pixel
xdotool key Return ; xwininfo -root -tree ; xprop            # input and window inspection
```

Software rendering (`LIBGL_ALWAYS_SOFTWARE=1`, Mesa llvmpipe) lets OpenGL programs run without a GPU. Qt tests can skip the display entirely with `QT_QPA_PLATFORM=offscreen`.

## What toolkits want besides a display

A session bus (`dbus-run-session`), a runtime directory (`XDG_RUNTIME_DIR`, mode 0700), fonts and locale data, and sometimes `NO_AT_BRIDGE=1` to quiet the accessibility bridge and `GSETTINGS_BACKEND=memory` to avoid dconf. Debug switches: `G_DEBUG=fatal-criticals`,
`GTK_DEBUG=interactive`, `QT_LOGGING_RULES`, `WAYLAND_DEBUG=1`.

## Wayland differences

Clients cannot read each other's windows or inject input, so `import -window root` and `xdotool` do not work against a Wayland session. Use the screenshot and remote-desktop portals, the compositor's own tools (`grim`, `wtype` for wlroots compositors), or run tests
under a headless compositor. Old X programs still run through XWayland.

## Worked example: the window that was never mapped

The lab program creates a window but, without a map call and a flush, nothing is drawn: the screenshot of the virtual display is black. After setting the background, mapping the window, flushing the connection and waiting a moment,
pixel (10,10) is red and a pixel at (250,200), outside the 200 by 100 window, is not. The fixture around it (display, bus, directory) is the same for GTK or Qt programs.
