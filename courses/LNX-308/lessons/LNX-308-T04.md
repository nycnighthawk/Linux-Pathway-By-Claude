# virtio, hugepages, CPU pinning (functional)

This lesson follows the topic synthesis `synth/LNX-308/LNX-308-T04.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Pick paravirtual devices and disk options that remove emulation cost.
- Reserve and request huge pages for a guest and confirm they are used.
- Pin vCPUs, the emulator thread and iothreads, bind memory to a NUMA node and check the result.

## Three levers

Performance of a guest depends on how often it crosses the virtualisation boundary (virtio and vhost), how costly each address translation is (huge pages) and where its threads and memory sit (pinning and NUMA). Apply each only when a measured need exists, and measure before and after: tuning without measurement often hurts.

## virtio

Emulated hardware traps on every register access; virtio devices talk through shared ring buffers in batches. In the XML: `<target dev='vda' bus='virtio'/>`, `<model type='virtio'/>` on the interface (with `<driver name='vhost' queues='4'/>`), a virtio balloon, rng and vsock where needed. Linux guests carry the drivers; Windows guests need the virtio-win drivers during install or afterwards. Disk options: `cache='none'` (skip the host cache), `io='native'`, `discard='unmap'`, `iothread='1'`. Multiqueue networking needs `ethtool -L eth0 combined 4` inside the guest too.

## Huge pages

Guest memory is mapped in 4 KiB pages by default; 2 MiB or 1 GiB pages shorten the two-level address translation and cut TLB misses.

```bash
sysctl vm.nr_hugepages=4096          # 4096 x 2 MiB = 8 GiB (1 GiB pages: reserve on the kernel command line)
grep -i huge /proc/meminfo           # HugePages_Total / _Free / _Rsvd
```

```xml
<memoryBacking><hugepages><page size='2048' unit='KiB' nodeset='0'/></hugepages></memoryBacking>
```

Reserved pages do not overcommit: if the pool is too small the guest fails to start. A memory balloon cannot reclaim huge pages, so remove it (`<memballoon model='none'/>`) on tuned guests. Transparent huge pages (`madvise` mode) need no per-guest setting but can add latency from compaction.

## Pinning and NUMA

```xml
<vcpu>4</vcpu><iothreads>1</iothreads>
<cputune>
  <vcpupin vcpu='0' cpuset='2'/> <vcpupin vcpu='1' cpuset='3'/>
  <vcpupin vcpu='2' cpuset='4'/> <vcpupin vcpu='3' cpuset='5'/>
  <emulatorpin cpuset='0-1'/> <iothreadpin iothread='1' cpuset='0-1'/>
</cputune>
<numatune><memory mode='strict' nodeset='0'/></numatune>
<cpu mode='host-passthrough'><topology sockets='1' cores='2' threads='2'/></cpu>
```

Find the host topology with `lscpu -e` and `numactl -H`. Keep the emulator and iothread off the vCPU cores, and isolate guest cores from the host scheduler (`isolcpus=`, or `AllowedCPUs=` on systemd slices). Pinning is a resource allocation: keep a ledger so two guests never share a core.

## Verifying

`virsh vcpuinfo NAME` and `virsh vcpupin NAME` show where vCPUs run; `numastat -p PID` shows where memory is; `perf kvm stat` counts exits by reason; `fio` and `iperf3` repeated several times show whether the change helped.

## Worked example: a guest that will not start

`virsh start db1` fails with an allocation error. `grep Huge /proc/meminfo` shows `HugePages_Free: 512` while an 8 GiB guest needs 4096 pages of 2 MiB (8 GiB / 2 MiB). Another guest holds the rest. Raise the pool (reboot if memory is fragmented), or shrink the guest. The same rule applies to a Kubernetes pod requesting `hugepages-2Mi`.
