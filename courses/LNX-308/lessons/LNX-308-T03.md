# VM networking: bridges, macvtap, VLANs

This lesson follows the topic synthesis `synth/LNX-308/LNX-308-T03.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Choose between a NAT network, a Linux bridge, macvtap and Open vSwitch for a guest.
- Write libvirt network and interface XML, including VLAN tags and DHCP reservations.
- Trace a frame from the guest NIC to its destination and find where it stops.

## The path of a frame

A guest's virtual NIC has a host end: a `tap` device (or a macvtap device) named like `vnet3`. The host decides what it is plugged into. Draw the same diagram you would for physical equipment: NIC, cable, switch, router, firewall.

| Model | libvirt | Guest visible from LAN | Notes |
|---|---|---|---|
| NAT network | `<forward mode='nat'/>` on a libvirt network (`virbr0`, dnsmasq) | no (needs port forwards) | works out of the box |
| Isolated | network with no `forward` | no | guests and host only |
| Routed | `<forward mode='route'/>` | yes if upstream routes back | no translation |
| Bridge | `<interface type='bridge'><source bridge='br0'/>` | yes | host IP moves to the bridge |
| macvtap | `<interface type='direct'><source dev='eth0' mode='bridge'/>` | yes | host cannot talk to the guest through `eth0` |
| Open vSwitch | `<virtualport type='openvswitch'/>` | yes | tunnels, mirroring, flows |

## libvirt network XML

```xml
<network>
  <name>labnet</name>
  <forward mode='nat'/>
  <bridge name='virbr10' stp='on' delay='0'/>
  <ip address='192.168.150.1' netmask='255.255.255.0'>
    <dhcp>
      <range start='192.168.150.100' end='192.168.150.200'/>
      <host mac='52:54:00:aa:bb:01' name='db1' ip='192.168.150.10'/>
    </dhcp>
  </ip>
</network>
```

Manage with `virsh net-define`, `net-start`, `net-autostart`, `net-dhcp-leases`, `net-dumpxml`. In a domain, `<model type='virtio'/>` selects the paravirtual card, `<bandwidth>` caps traffic, and `<filterref filter='clean-traffic'/>` blocks MAC, IP and ARP spoofing.

## VLANs

Three ways. A sub-interface plus a bridge per VLAN (`ip link add link eth0 name eth0.100 type vlan id 100`) works but multiplies objects. A single bridge with `vlan_filtering` and per-port membership acts as a managed switch: uplink as a trunk, each guest tap as an access port (`bridge vlan add vid 20 pvid untagged dev vnet3`; inspect with `bridge vlan show`). Or the guest tags its own frames and the host passes them through. Libvirt expresses an access tag as `<vlan><tag id='20'/></vlan>` in the interface.

## Diagnosing

1. In the guest: `ip addr`, `ip route`, ping the gateway.
2. On the host: `virsh domiflist NAME` for tap and MAC; `ip link show vnet3`; `bridge link` (is the port forwarding?).
3. `virsh net-dhcp-leases`; `tcpdump -ni vnet3` then `-ni br0` to see where frames stop.
4. `nft list ruleset` or `iptables-save`; `sysctl net.ipv4.ip_forward`.

## Worked example: the macvtap guest the host cannot reach

A backup agent on the hypervisor cannot connect to a guest attached with `type='direct'`, though every other machine can. The kernel sends macvtap frames straight out of `eth0` and does not loop them back to the host's own stack on that interface. Fix: add a macvlan interface for the host (`ip link add mv0 link eno1 type macvlan mode bridge`) and use it for host-guest traffic, or move the guest to a real bridge.
