## qcow2 and backing files

A qcow2 image maps guest offsets to file offsets through two table levels. A cluster that is unallocated in the top image is read from its **backing file**; a write allocates the cluster in the top layer (copy on write). One read-only template can therefore serve many thin overlays.

```bash
qemu-img create -f qcow2 -b base.qcow2 -F qcow2 vm1.qcow2 20G   # -F names the backing format
qemu-img info --backing-chain vm1.qcow2                          # every layer; add --output=json for scripts
qemu-img check vm1.qcow2
qemu-img convert -O qcow2 -c vm1.qcow2 flat.qcow2                # flatten, compress, drop unused space
qemu-img rebase -b newbase.qcow2 -F qcow2 vm1.qcow2              # copy differences onto a new base
qemu-img commit vm1.qcow2                                        # write the overlay INTO its base
```

Three rules. Always state the backing format with `-F`. Prefer relative backing names so the directory can move. And never write to a template that has children: booting it, or running `commit` from one overlay, silently changes what every other overlay sees. Make templates read-only.

## Snapshots

| Kind | How | Properties |
|---|---|---|
| Internal | `qemu-img snapshot -c NAME disk.qcow2` offline, `virsh snapshot-create-as DOM SNAP` live | one file; qcow2 only; slows the image; may include memory |
| External | `virsh snapshot-create-as DOM SNAP --disk-only --atomic --quiesce` | the current disk becomes read-only and a new overlay takes writes; any base format; state spans files |

`--quiesce` asks the guest agent to freeze filesystems, and fails if the agent is not running. Merge an external snapshot back while running with `virsh blockcommit DOM vda --active --pivot`, then remove the old files and `virsh snapshot-delete DOM SNAP --metadata`. A snapshot shares the disk with what it protects, so it is not a backup. Memory snapshots depend on the QEMU version and CPU model and may fail to restore after a host upgrade.

## Offline customisation

The libguestfs tools open an image inside a throwaway appliance, so they need no root, never boot the guest and keep malformed filesystems away from the host kernel.

- `virt-sysprep -a image` removes machine identity: `machine-id`, SSH host keys, DHCP leases, logs, shell history (`--list-operations` shows all).
- `virt-customize -a image --install pkg --hostname web --ssh-inject root:file:key.pub --run-command '...' --selinux-relabel` edits an image. The relabel matters on SELinux guests.
- `virt-builder` downloads a signed minimal image and customises it in one step; `virt-resize` grows partitions while copying; `virt-clone` duplicates a guest with new UUID, name and MAC.
- Set `LIBGUESTFS_BACKEND=direct` in containers and CI where libvirt is not present; `libguestfs-test-tool` diagnoses failures.

Instance-specific settings (hostname, keys, network) belong to cloud-init reading a `cidata` seed at first boot; prepare the template with `cloud-init clean --logs`.

## Worked example: ten clones

Build `base.qcow2` from a cloud image: `virt-customize --install qemu-guest-agent,cloud-init --selinux-relabel`, then `virt-sysprep`, then `chmod a-w`. For each guest: create an overlay, `virt-install --import --disk path=... --cloud-init user-data=web1.yaml`. Ten guests cost the template plus what each writes, and each generates its own SSH host keys at first boot. Skip the sysprep step and all ten share one `machine-id`, one set of host keys and, if the XML was copied, one MAC: the DHCP server and your security team will both notice.
