## Nested virtualisation

Level 0 (L0) is the physical host, L1 a guest that runs a hypervisor, L2 a guest of L1. The L0 hypervisor emulates the CPU's virtualisation instructions for L1, so L1 believes it controls real hardware. CPU-bound L2 work runs near native speed; every exit from L2 goes to L0 first, so I/O-heavy and page-table-heavy work can be several times slower.

```bash
cat /sys/module/kvm_intel/parameters/nested     # Y or 1 means on (AMD: kvm_amd)
echo 'options kvm_intel nested=1' | sudo tee /etc/modprobe.d/kvm-nested.conf
sudo modprobe -r kvm_intel && sudo modprobe kvm_intel     # all guests stopped
```

The L1 guest needs a CPU that carries the flag: in libvirt `<cpu mode='host-passthrough'/>` (or `host-model`). A named model such as `Skylake-Server` does not include `vmx`. Inside L1: `grep -c -E 'vmx|svm' /proc/cpuinfo`, `ls -l /dev/kvm`, `virt-host-validate qemu`. `systemd-detect-virt` tells scripts what they run on. Vendor support is thin: Red Hat lists nesting as a technology preview in most RHEL 10 setups; Red Hat documents the Windows WSL2 guest on RHEL as the one fully supported nested setup. Public clouds allow nesting only on selected instance families, so check each provider's list.

Risks: nested code paths have had vulnerabilities, so enabling it for untrusted tenants is a trade of risk for convenience; clocks and counters in L2 behave oddly; live migration of an L1 that runs L2 guests is often unsupported.

## Firecracker microVMs

Firecracker is a minimal virtual machine monitor written in Rust on KVM, built for serverless platforms: a guest boots a kernel directly in about 125 ms with a few megabytes of VMM overhead, and exposes only virtio block, net and vsock, a serial console and a reset controller. No BIOS, USB, GPU or passthrough. Defence in depth: KVM and the VMM are the first boundary; the process around the VMM is confined by seccomp filters, cgroups and namespaces, and the `jailer` starts it in a chroot as an unprivileged user.

Control is a REST API on a UNIX socket (`PUT /boot-source`, `/drives/{id}`, `/machine-config`, `/network-interfaces/{id}`, `/actions` with `InstanceStart`, `/snapshot/create`), or one JSON file:

```json
{
 "boot-source": {"kernel_image_path": "/srv/fc/vmlinux", "boot_args": "console=ttyS0 reboot=k panic=1 pci=off"},
 "drives": [{"drive_id": "rootfs", "path_on_host": "/srv/fc/rootfs.ext4", "is_root_device": true, "is_read_only": false}],
 "machine-config": {"vcpu_count": 2, "mem_size_mib": 256, "smt": false},
 "network-interfaces": [{"iface_id": "eth0", "host_dev_name": "tap0", "guest_mac": "06:00:AC:10:00:02"}]
}
```

Run with `firecracker --api-sock /tmp/fc.sock --config-file vm.json`; in production use the jailer. Snapshots remove cold start, but a restore needs the same CPU model (or a CPU template), and clones repeat the source's random state and network identity unless repaired. Related VMMs: Cloud Hypervisor (hotplug, VFIO, live migration, Windows), crosvm, QEMU's `microvm` machine, and Kata Containers on top.

## Worked example: no /dev/kvm in the L1 guest

L0 has nesting on, but `grep vmx /proc/cpuinfo` in L1 prints nothing. The domain XML uses a named CPU model. Switch to `host-passthrough` (or require the feature: `<feature policy='require' name='vmx'/>`), reboot L1, and the flag and `/dev/kvm` appear.
