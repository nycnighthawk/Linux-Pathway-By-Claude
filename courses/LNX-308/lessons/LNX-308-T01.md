# KVM/QEMU, libvirt, virsh, virt-install

This lesson follows the topic synthesis `synth/LNX-308/LNX-308-T01.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Say what KVM, QEMU, libvirt, `virsh` and `virt-install` each do, and which layer to suspect for a given symptom.
- Check that a host can run accelerated guests and connect to the right libvirt instance.
- Read and edit a domain XML document, and install, start, stop and inspect a guest.

## Four layers, one guest

**KVM** is a kernel module that exposes the processor's virtualisation extensions as `/dev/kvm`. **QEMU** is a user process that opens that device, emulates the rest of the machine (chipset, firmware interface, disks, network cards) and runs each virtual CPU as a thread. **libvirt** is a daemon and API that stores each guest as an XML document, starts QEMU with the matching command line, confines it with a per-guest security label and manages storage pools and networks. `virsh` and `virt-install` are clients of libvirt. Because a guest is an ordinary process, `top`, cgroups and NUMA policy apply to it unchanged.

## Preparing the host

```bash
grep -E -o 'vmx|svm' /proc/cpuinfo | sort -u     # CPU flag (firmware may still have it disabled)
ls -l /dev/kvm ; lsmod | grep kvm                # device and modules
virt-host-validate qemu                          # PASS/WARN/FAIL per probe
export LIBVIRT_DEFAULT_URI=qemu:///system        # the privileged instance
virsh net-list --all ; virsh pool-list --all     # default network and storage pool
```

Current distributions run one small daemon per driver (`virtqemud`, `virtnetworkd`, `virtstoraged`, ...) activated by systemd sockets; older ones run `libvirtd`. A common beginner mistake: an ordinary user's `virsh list --all` talks to `qemu:///session`, so guests created by root seem to have vanished. Name the URI.

## The domain XML

The XML is the source of truth. The parts you must recognise:

- `<domain type='kvm'>`: `qemu` here means slow, unaccelerated emulation.
- `<memory>`, `<vcpu>`: ceiling and count, with a `unit` attribute.
- `<os><type arch='x86_64' machine='pc-q35-9.2'>`: use a versioned machine type so the hardware layout survives upgrades.
- `<cpu mode='host-model'/>`: portable and close to the host. `host-passthrough` exposes everything but blocks safe migration checks.
- `<disk>` with `<driver name='qemu' type='qcow2'/>` and `<target dev='vda' bus='virtio'/>`: state the format, use virtio.
- `<interface type='network'>` with `<source network='default'/>` and `<model type='virtio'/>`.

`virsh define file.xml` stores a persistent guest; `virsh create file.xml` starts a transient one. Change a stored guest with `virsh edit NAME` (it validates on save), never by editing files under `/etc/libvirt` while the daemon runs. `virsh dumpxml NAME` shows the live document, including PCI addresses and the VNC port.

## Lifecycle with virsh

`virsh list --all`, `dominfo`, `domstate --reason`, `domblklist`, `domifaddr` inspect. `start`, `shutdown` (an ACPI request the guest may ignore), `reboot`, `suspend`/`resume`, `destroy` (a hard power cut, not a deletion) and `undefine` (remove the definition) change state. `autostart` starts the guest at boot. `virsh console NAME` needs `console=ttyS0` and a getty inside the guest.

## Installing with virt-install

```bash
virt-install --name web1 --memory 2048 --vcpus 2 --cpu host-model \
  --os-variant debian12 --disk size=20,format=qcow2,bus=virtio \
  --network network=default,model=virtio \
  --location https://deb.debian.org/debian/dists/bookworm/main/installer-amd64/ \
  --extra-args 'console=ttyS0' --graphics none
```

`--os-variant` (see `osinfo-query os`) picks sane device defaults. `--location` lets you pass kernel arguments; `--cdrom` boots like real hardware; `--import` skips the installer for a ready image. Add `--print-xml --dry-run` to see the document without creating anything: that output is what you commit to version control.

## Worked example: the slow guest

A new guest takes minutes to boot and burns a host core while idle. `virsh dumpxml web1 | grep "domain type"` prints `type='qemu'`: libvirt could not use `/dev/kvm` when the guest was created, so QEMU fell back to its emulator. Firmware had virtualisation switched off. Fix: enable it, confirm with `virt-host-validate qemu`, then `virsh edit web1` and set `type='kvm'`. Lesson: acceleration is a property of the definition, so verify it after creation.
