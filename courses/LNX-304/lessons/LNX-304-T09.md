# Image Builder

This lesson follows the topic synthesis `synth/LNX-304/LNX-304-T09.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Write an Image Builder blueprint and say what belongs in the image and what belongs at first boot.
- Build, download and test an image with `composer-cli`.
- Pin the package inputs with your own repository snapshot so that builds repeat.
- Place image builds in a pipeline with tests, publication and a rebuild schedule.

## How it works

`osbuild` runs a pipeline of small stages described by a manifest with exact package versions. `osbuild-composer` turns a blueprint plus an output type into that manifest, using a dependency solver against the configured sources. Front ends are `composer-cli`, the Cockpit web console and a hosted service. `bootc-image-builder` does the same for bootc container images.

## A blueprint

```
name = "site-base"
version = "1.2.0"
distro = "rhel-10"
[[packages]]
name = "chrony"
[[customizations.user]]
name = "ops"
key = "ssh-ed25519 AAAA... ops@example.org"
[customizations.services]
enabled = ["chronyd", "sshd"]
[customizations.kernel]
append = "audit=1"
```

```bash
composer-cli blueprints push site-base.toml
composer-cli blueprints depsolve site-base
composer-cli sources add site-snapshot.toml
composer-cli compose start site-base qcow2
composer-cli compose status ; composer-cli compose image <uuid>
```

## Image or first boot

Same on every machine: packages, enabled services, kernel arguments, audit rules, baseline profile. Differs per machine: hostname, addresses, identity, secrets, SSH host keys. Put the second group in cloud-init, Ignition, kickstart or configuration management, and generalise the image (empty machine id, no host keys). Never put secrets in a blueprint.

## Make builds repeatable

Add a source that points at a dated snapshot with `check_gpg = true`. Record the snapshot and blueprint commit inside the image. Rebuild on a schedule even when nothing changed, boot every image in CI, scan it, then publish with a version and an expiry.

## Worked example: the stale template

A quarterly image forced 300 package updates and a reboot on first boot of every instance. Weekly builds from the current snapshot and a 14-day maximum image age fixed it.
