## What you will be able to do

- Name the files in a `debian/` directory and say what each one controls.
- Build a binary and a source package with `dpkg-buildpackage` and inspect the result.
- Explain why `Build-Depends` must be complete and how a clean-chroot builder such as `sbuild` proves it.
- Version a package so that upgrades, backports and local rebuilds sort correctly.

## Anatomy

A `.deb` is an `ar` archive with three members: `debian-binary` (the format version), `control.tar.*` (metadata and maintainer scripts) and `data.tar.*` (the files). A source package is a `.dsc` description plus the upstream tarball and a `debian` tarball or a patch series.

```
debian/
  control        # source stanza (Build-Depends) and one stanza per binary package
  changelog      # version, urgency, distribution; the version comes from here
  rules          # makefile: dh $@
  copyright      # licence of every file
  compat or Build-Depends: debhelper-compat (= 13)
  install        # which files go to which package
  conffiles      # generated; marks files dpkg must not overwrite silently
  postinst  prerm  postrm   # maintainer scripts
  source/format  # 3.0 (quilt) or 3.0 (native)
```

A minimal `rules` file is two lines: the shebang `#!/usr/bin/make -f` and `%:` followed by a tab and `dh $@`. `dh` runs the standard sequence (`dh_auto_configure`, `dh_auto_build`, `dh_auto_test`, `dh_auto_install`, `dh_installdocs`, `dh_compress`, `dh_gencontrol`, `dh_builddeb`), and you override only the step you need with `override_dh_...` targets.

## Build and inspect

```bash
dpkg-buildpackage -us -uc -b      # binary only, unsigned (-S for source, none for both)
dpkg-deb -I pkg.deb               # control fields
dpkg-deb -c pkg.deb               # file list with modes
dpkg-deb -e pkg.deb DEBIAN-dir    # extract the maintainer scripts
lintian pkg.changes               # policy problems
dpkg -L pkg; dpkg -V pkg          # installed file list and verification
```

Files under `/etc` that a package ships are conffiles automatically with debhelper compat 3 and later. On upgrade, `dpkg` asks the administrator when both the local file and the packaged one changed, which is the counterpart of `%config(noreplace)`.

## Versions

A version is `[epoch:]upstream[-revision]`. Compare with `dpkg --compare-versions 1.0-1 lt 1.0-1ubuntu1`. The tilde sorts before everything, so `1.0~rc1` is older than `1.0`; use it for pre-releases and for backports (`1.0-1~bpo12+1`). An epoch is a last resort because it can never be removed.

## Maintainer scripts

`preinst`, `postinst`, `prerm` and `postrm` receive an action word (`configure`, `upgrade`, `remove`, `purge`) rather than a count. They must be idempotent and must work when a service manager is absent. Prefer the `#DEBHELPER#` token, which debhelper replaces with generated code for systemd units, alternatives and triggers.

## sbuild: the clean room

```bash
sbuild-createchroot --include=eatmydata bookworm /srv/chroot/bookworm-amd64 http://deb.debian.org/debian
sbuild -d bookworm hello-site_1.0-1.dsc
```

`sbuild` unpacks a minimal chroot, installs `build-essential` and your `Build-Depends`, builds, and discards the changes. A missing `Build-Depends` fails there instead of on a user's machine. Remember that `build-essential` packages (`gcc`, `make`, `dpkg-dev`) are implied and need no listing. Builds that fetch from the network break reproducibility; vendor and checksum the inputs.

## Worked example: works in my tree

A package passes on a developer laptop but fails in the build farm with a missing header. The `control` file never listed the development package, which the laptop had installed for another project. The `sbuild` log shows the failing `configure` step; the fix is one `Build-Depends` line. A second trap is a rebuild with the same version after a fix: the archive refuses it, and clients would not upgrade anyway, so add a changelog entry with a new revision.
