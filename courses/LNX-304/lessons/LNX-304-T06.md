# Katello content views

This lesson follows the topic synthesis `synth/LNX-304/LNX-304-T06.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Name the Katello objects and how content flows from a repository to a registered host.
- Design a small set of content views, lifecycle environments and activation keys.
- Explain why publishing is not promoting, and how emergencies use an incremental update.
- Set retention and monitoring for the content server.

## The object model

| Object | What it is |
|---|---|
| Product, repository | where content comes from, synced on a sync plan |
| Content view (CV) | a named selection of repositories, with optional filters; a definition |
| CV version | an immutable snapshot made by publishing (1.0, 2.0 ...) |
| Lifecycle environment | a stage on a path: Library, Dev, Test, Prod |
| Promotion | placing a CV version in an environment |
| Composite CV | a view made of other views at chosen versions |
| Activation key | registration recipe: environment, view, subscriptions |
| Capsule | a regional proxy that serves selected environments |

```bash
hammer content-view publish --name cv-base --organization Site
hammer content-view version promote --content-view cv-base --version 1.0 \
  --to-lifecycle-environment Dev --organization Site
subscription-manager register --org=Site --activationkey=ak-dev
```

## Design rules

1. One view per role, not per host.
2. Three or four environments at most.
3. Filters: few, documented, tested on a canary. An errata date filter reproduces a dated snapshot; a package filter can break dependencies.
4. Composite views only for combinations, with deliberate version pinning.
5. Automate publish and promote, with a recorded approval between them.
6. Keep the last N versions plus any in an environment; clean up on a schedule.

## Emergencies and upgrades

An incremental update makes a minor version holding only the chosen errata and can be promoted fast; fold it into the next full publish. For an in-place OS upgrade the target repositories must be in the host's view and activation key, or the upgrade is inhibited.

## Operate the server

Alert on failed syncs, the age of the last good sync, free disk under `/var/lib/pulp` and expiring certificates. Back up with the maintain tool and test a restore.

## Worked example: promoted-but-not-visible

Version 12 is published and visible in Library, but Prod sees nothing. Publishing does not promote. The pipeline should do both, with an approval recorded between them.
