## Anatomy

An RPM holds a signature header, a metadata header (name, version, release, dependencies, file list with digests, scriptlets, changelog) and a compressed cpio payload. A source RPM holds the spec, sources and patches, so anyone can rebuild.

```
Name:           hello-site
Version:        1.0
Release:        1%{?dist}          # bump on every rebuild of the same version
Summary:        Site greeting script
License:        MIT                # an SPDX expression
BuildArch:      noarch
Source0:        %{name}-%{version}.tar.gz
BuildRequires:  make               # everything the build calls: mock's chroot is minimal
%description
...
%prep       %autosetup
%build      %make_build
%install    install -D -m 0755 hello-site %{buildroot}%{_bindir}/hello-site
%check      ./hello-site | grep -q hello
%files      %license LICENSE
            %{_bindir}/hello-site
            %config(noreplace) %{_sysconfdir}/hello-site.conf
%changelog
```

Use path macros (`%{_bindir}`, `%{_unitdir}`, `%{_sysconfdir}`), never literal paths. `%config(noreplace)` keeps local edits and writes the new default as `.rpmnew`. Plain `%config` can overwrite or save a `.rpmsave` depending on how the file changed, which surprises operators.

## Build and inspect

```bash
rpmdev-setuptree                                   # ~/rpmbuild/{SOURCES,SPECS,...}
spectool -g -R hello-site.spec                     # download sources before the build
rpmbuild -bp|-bc|-bi|-bb|-bs|-ba hello-site.spec   # stop after %prep, %build, %install, binary, source, both
rpmlint RPMS/noarch/*.rpm                          # policy problems
rpm -qpl pkg.rpm; rpm -qp --requires pkg.rpm; rpm -qp --scripts pkg.rpm
rpm -V installed-package                           # digests, modes, owners against the database
```

Build as an ordinary user. Dependencies come from generators that scan the ELF and script content; add by hand only what they cannot see.

## Scriptlets

`%pre`, `%post`, `%preun`, `%postun` receive the number of instances of the package that will remain: 1 on first install, 2 on upgrade, 0 on final removal. Keep them idempotent, quiet and safe in a chroot or container, where systemd is absent. Use macro families such as `%systemd_post` and file triggers instead of hand-written shell.

## Mock: the clean room

```bash
mock -r rocky-9-x86_64 --rebuild hello-site-1.0-1.src.rpm
ls /var/lib/mock/rocky-9-x86_64/result/    # RPMs, build.log, root.log
mock -r rocky-9-x86_64 --shell             # debug inside the chroot
```

Mock installs the build group and your `BuildRequires` into a disposable root, so a package cannot silently depend on whatever your workstation has. A site config adds the internal repository so internal libraries resolve. Builds that need the network (Go, Rust, npm fetching at build time) break the model: vendor the sources in a checked archive instead.

## Worked example: works on my machine

A package builds on a laptop and installs on a server that then reports a missing library. The spec had no `BuildRequires` for the development package, which the laptop happened to have; a mock rebuild fails at configure and exposes it. The fix is to declare it and add an install-and-upgrade test in a fresh container. A second trap: a rebuild with an unchanged `Release` is never offered to clients.
