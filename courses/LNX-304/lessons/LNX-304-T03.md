# Signing and key rotation

This lesson follows the topic synthesis `synth/LNX-304/LNX-304-T03.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Sign packages and repository metadata and make clients verify both.
- Say where clients keep trusted keys on RPM and Debian systems.
- Protect a signing key with an offline primary, a subkey and a revocation certificate.
- Plan a key rotation with an overlap period and a way back.

## Two models

| | RPM family | Debian family |
|---|---|---|
| What is signed | each package, plus optionally `repomd.xml` | `Release` (as `InRelease` or `Release.gpg`) |
| Client switch | `gpgcheck=1`, `repo_gpgcheck=1`, `gpgkey=` | `Signed-By:` in the source entry |
| Key store | RPM database (`rpm --import`) | file in `/etc/apt/keyrings/` |
| Verify by hand | `rpm -Kv file.rpm` | `apt update` or `gpgv --keyring k.gpg InRelease` |

The Debian model signs the top of a hash tree: the signed `Release` lists the checksums of the index files, which list the checksums of the packages. One signature authenticates everything below it.

## Sign and verify

```bash
gpg --quick-generate-key "Example Release <release@example.org>" ed25519 sign 2y
gpg --export --armor "Example Release" > RPM-GPG-KEY-example
echo '%_gpg_name Example Release' >> ~/.rpmmacros
rpmsign --addsign hello-site-1.0-1.noarch.rpm
rpm --import RPM-GPG-KEY-example
rpm -Kv hello-site-1.0-1.noarch.rpm        # digests and signature
createrepo_c repo/ && gpg --detach-sign --armor repo/repodata/repomd.xml
gpg --clearsign -o InRelease Release        # Debian side
```

Until the key is imported, `rpm -K` reports `NOKEY`. Never fix a key problem by turning checking off (`gpgcheck=0`, `[trusted=yes]`).

## Protect the key

1. Use a role key, not a person's key.
2. Keep the primary key offline; sign with a subkey that expires in one to two years.
3. Generate a revocation certificate at creation (`gpg --gen-revoke`) and store it offline.
4. If CI signs, use a hardware module, a signing service or a vault with an audit trail.

## Rotate without an outage

Deliver the new key before it is used, sign with both keys for a transition period, stop signing with the old key, then remove and revoke it. Every step can be undone by going back one step. Ship keys in a small keys package or through configuration management, not over the same HTTP connection as the packages. Alert 90 days before every expiry: `EXPKEYSIG` on a Saturday is the classic outage.

## Worked example: the silent expiry

A repository key made with a one-year expiry lapses; every client fails with `EXPKEYSIG`. The fix is to extend the expiry, re-export the public key, re-sign, and push the updated key through configuration management. Setting `trusted=yes` hides the problem and removes the protection.
