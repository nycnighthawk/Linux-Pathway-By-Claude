# Regular expressions (BRE and ERE)

This lesson follows the topic synthesis `synth/LNX-101/LNX-101-T06.md`, which carries the sources and the history.

## What you will be able to do

- Read and write patterns in the basic (BRE) and extended (ERE) dialects used by `grep`, `sed` and `awk`.
- Predict what a greedy repetition will match, and restrict it with a bracket expression.
- Use groups and backreferences, and know which dialect needs backslashes for them.
- Recognise a pattern that can stall a backtracking engine, and know which tools are safe.

## What a pattern is made of

A regular expression describes a set of strings. It is not a shell glob: in a glob `*` means any run of characters, in a
regular expression it repeats the thing before it.

| Piece | Meaning |
|---|---|
| ordinary character | matches itself |
| `.` | any one character |
| `[abc]`, `[a-f0-9]`, `[^abc]` | one character from, or not from, a set; also classes such as `[[:digit:]]` and `[[:alpha:]]` |
| `^`, `$` | start and end of the line (positions, not characters) |
| `*`, `+`, `?` | zero or more, one or more, zero or one of the previous item |
| `{n}`, `{n,}`, `{n,m}` | exactly n, at least n, between n and m of the previous item |
| `( ... )` | group |
| bar between two choices | alternation: either choice |
| `\1`, `\2` | backreference: the same text the group matched |

## The two dialects

POSIX defines two syntaxes. The only difference you need to memorise is which characters need a backslash.

| Feature | Basic (`grep`, `sed`) | Extended (`grep -E`, `sed -E`, `awk`) |
|---|---|---|
| group | `\( \)` | `( )` |
| bounded repetition | `\{2,\}` | `{2,}` |
| one or more, zero or one | `\+` and `\?` (GNU extension) | `+` and `?` |
| alternation | a backslash before the bar (GNU extension) | the bar itself |

Use the extended form for readability. GNU tools accept both. Always put patterns in **single quotes** so the shell does
not expand them first.

## Matching rules

- Matching is **unanchored**: the pattern may match anywhere in the line unless you use `^` and `$`.
- Repetition is **greedy**: it takes as much as it can while still letting the whole pattern match. On a line with two
  quoted strings, `".*"` matches from the first quote to the last. Excluding the delimiter fixes it: `"[^"]*"`.
- Ranges such as `[a-z]` depend on the locale's collation order. Prefer the named classes.
- POSIX picks the **longest** match from the leftmost position; Perl-style engines take the first alternative that works.

## Worked example: from a first draft to a correct pattern

Goal: accept lines that are a date in the form `YYYY-MM-DD`.

```bash
grep -E '[0-9]{4}-[0-9]{2}-[0-9]{2}' dates.txt              # draft: also matches 2026-99-99 and longer lines
grep -Ex '[0-9]{4}-[0-9]{2}-[0-9]{2}' dates.txt             # -x: whole line only
grep -Ex '[0-9]{4}-(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[01])' dates.txt    # month and day ranges
```

For repeated words use a backreference:

```bash
grep -E '(^|[^[:alnum:]])([[:alnum:]]+) \2([^[:alnum:]]|$)' notes.txt
```

Note what the patterns do **not** do: they accept 2026-02-31. When a rule is about meaning, not shape, check it in code.

## Danger: patterns that can stall

Engines that implement backreferences by backtracking can take exponential time on some patterns. A repeated group of
repeated items followed by something that cannot match, such as `(a+)+$`, applied to a long run of `a` ending in `b`,
doubles its running time with each extra character. A global outage at a content-delivery company in 2019 was traced to
a single pattern of this kind. Defences: use a linear-time engine for patterns that come from outside, set match
timeouts, and cap input length. Use a real parser for HTML or nested formats; patterns cannot describe balanced nesting.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| `grep 'a|b'` matches nothing useful | In the basic dialect `|` is literal | `grep -E` or `\|` |
| The match is far longer than expected | Greedy repetition | Use `[^x]*` instead of `.*` |
| The pattern works on one machine only | Locale-dependent range | Use `[[:lower:]]` etc. |
| The shell mangled the pattern | It was not quoted | Single quotes around the pattern |
| A pattern accepts invalid data | Shape was checked, meaning was not | Validate values in code |

## Self-check

1. What do `a.*b` and `a[^b]*b` match on the line `a1b2b`?
2. Which dialect needs `\(` and `\)` for groups, and which does not?
3. Why is `^[0-9]{1,3}(\.[0-9]{1,3}){3}$` not a correct IPv4 validator?
4. Why can a backtracking engine stall on `(x+)+y` with a long input of `x` characters?
