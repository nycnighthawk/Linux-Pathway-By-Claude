# Getting help on the machine itself

This lesson follows the topic synthesis `synth/LNX-101/LNX-101-T10.md`, which carries the sources and the history.

## What you will be able to do

- Use the layers of built-in documentation in the right order: usage text, manual page, long manual, outside sources.
- Read a manual page: the synopsis notation, the sections, the exit status and the see-also list.
- Pick the right manual section when a name exists in several, and search by keyword when you do not know the command.
- Find out what kind of thing a name is, and what to do when documentation is not installed.

## Retrieval, not memory

A system has thousands of commands, and nobody remembers all their options. The skill is getting the exact, current
description from the machine, even on a server with no browser and no network. Documentation installed with the
software matches the installed version, which a web recipe written for another release may not.

Think of a stack that grows longer and slower as you go down:

| Layer | Command | Speed | Use it for |
|---|---|---|---|
| Usage text | `cmd --help` (or `-h`) | instant | which options exist |
| Manual page | `man cmd` | seconds | exact meaning, exit status, files |
| Long manual | `info cmd` | minutes | concepts, tutorials (GNU tools) |
| Outside | vendor docs, project sites | slowest | background, newer versions |

Start at the top. Many commands print the usage text to standard output, but some print it to standard error when you
give a bad option; try `cmd --help 2>/dev/null | head` to see which stream it uses.

## Manual pages

A page has a fixed layout: name, synopsis, description, options, then exit status, files, examples, see also. The
synopsis uses a compact notation:

| Notation | Meaning |
|---|---|
| `[ ... ]` | optional |
| `...` | may be repeated |
| a bar between words | alternatives |
| bold text | type literally |
| italic or underlined text | replace with your own value |

The reader is a pager. Press `/` and a word to search forward, `n` for the next match, `g` and `G` to jump to the start
and end, `q` to quit. Read the synopsis before the description, search the page for an option before scrolling, and
read the **exit status** section when you write scripts.

### Sections

The same word can be a command and a file format, so the page has a section number:

| Section | Holds |
|---|---|
| 1 | commands for ordinary users |
| 2 | system calls |
| 3 | library functions |
| 4 | special files (devices) |
| 5 | file formats and configuration files |
| 6 | games |
| 7 | conventions and overviews |
| 8 | administration commands |

`man passwd` shows the command; `man 5 passwd` shows the account-file format. `man -f passwd` (or `whatis`) lists every
section that has the name. `man -k word` (or `apropos`) searches names and descriptions, which is how you find a command
when you only know the task. It uses a prebuilt index, so on a new machine it may return nothing until the index is
built with `mandb`.

## Info, built-ins and what a name is

The GNU project favours hyperlinked manuals read with `info`. For the shell and core utilities they are longer and more
explanatory than the page. `info cmd --output=- | less` dumps one as plain text.

Shell **built-ins** such as `cd` are not separate programs and have no page of their own. Use `help cd` in bash; the
details are in the long page for the shell. To learn how the shell will read a name, ask it:

```bash
type -t cd        # builtin
type -t ls        # file, or alias if your shell defines one
type -a echo      # every meaning, in order of precedence
```

Then go to the right documentation: `help` for a built-in, `man` for a file, `alias` or `declare -f` for the others.

## More places

- `/usr/share/doc/<package>/` holds readme files, change logs and licence texts.
- Many tools have sub-command help, such as `git help commit` or `systemctl --help`.
- `kubectl explain pod.spec` prints the fields of an API resource from its schema.
- In minimal systems and container images the pages are often removed to save space; then you need the usage text, the
  package's documentation package, or another machine with the same version installed.

## Worked example: from a task to the right flag

You need to retry a failed copy five times.

```bash
man -k sync                    # find candidates by task; choose one
rsync --help | grep -i retr    # fastest: scan the usage text
man rsync                      # then search: /retr  and read the exit-status section
type -t rsync                  # confirm it is a program, so man is the right place
```

Write down, for three commands you use daily, one option you did not know about and when you would have wanted it.
Doing this regularly builds the habit of checking before guessing.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| `man` shows the wrong page | Name exists in several sections | `man -f name`, then `man 5 name` |
| "No manual entry" | Not installed, or it is a built-in | `type -t name`, `help name` |
| `man -k` returns nothing | The index is missing or stale | `mandb` |
| An option from a web post fails | Different version or distribution | The page on this machine |
| A flag behaved unexpectedly | Guessed from another tool | The page for this command |
| No pages in a container | Removed to save space | Usage text; install the docs package |
