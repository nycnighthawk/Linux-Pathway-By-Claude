# Redirection, pipes and tee

## What you will be able to do

- Name the three standard streams and say which file descriptor numbers they use.
- Send standard output and standard error to files, to each other or to nowhere, in the right order.
- Explain why `sudo echo x > file` fails and how `tee` fixes it.
- Report a pipeline's real status, and explain why a pipeline can look frozen.

## Three streams

A program does not open its own input and output. It inherits numbered handles, the **file descriptors**, from whoever
started it. By convention:

| Number | Name | Default |
|---|---|---|
| 0 | standard input | the keyboard |
| 1 | standard output | the terminal |
| 2 | standard error | the terminal |

The shell rearranges the handles before it starts the program, so the program never knows whether a stream is a file,
a terminal or another program.

## The operators

| Operator | Effect |
|---|---|
| `> file` | send standard output to the file, replacing it |
| `>> file` | append instead of replacing |
| `< file` | read standard input from the file |
| `2> file` | send standard error to the file |
| `2>&1` | make descriptor 2 a copy of descriptor 1 |
| `&> file` | bash shortcut: both streams to the file |
| `> /dev/null` | throw the output away |
| `<<EOF ... EOF` | here-document: feed the lines up to the marker as input |

**Order matters; redirections are processed left to right.**

```bash
cmd > all.txt 2>&1     # standard output goes to the file, then standard error follows it: both in the file
cmd 2>&1 > all.txt     # standard error is pointed at the terminal first; only standard output goes to the file
```

## Pipes and tee

A pipe connects the standard output of one command to the standard input of the next. Both run at the same time and the
kernel buffers the data between them; the writer waits when the buffer is full and the reader waits when it is empty. If
the reader exits early, the writer is told on its next write, which is how `head` stops a long producer.

`tee` copies its input to a file and to its own output, like a T-junction:

```bash
make 2>&1 | tee build.log | tail -5        # watch the end, keep everything
echo 'setting=1' | sudo tee -a /etc/app.conf >/dev/null
```

The second line shows why `tee` exists. In `sudo echo x > /etc/app.conf` the **shell** opens the file, as you, before
`sudo` starts. In the `tee` form the file is opened by `tee`, which runs under `sudo`.

## Exit status of a pipeline

By default the status of a pipeline is the status of its last command, so `false | true` reports success. Two tools help:

```bash
set -o pipefail          # any failing stage makes the pipeline fail
false | true; echo "$?"  # now prints 1
echo "${PIPESTATUS[@]}"  # the status of each stage of the last pipeline (bash)
```

## Worked example: a pipeline that looks frozen

```bash
ping -c 5 localhost | grep 'bytes from'          # lines appear as they arrive here, because ping is line-buffered
tail -f /var/log/syslog | grep error | cut -d' ' -f5-    # may show nothing for a long time
```

The second pipeline stalls because `grep` switches to block buffering when its output is not a terminal. Ask it to
flush each line:

```bash
tail -f /var/log/syslog | grep --line-buffered error | cut -d' ' -f5-
```

A second experiment: sort a file and redirect the output to the same file (`sort data > data`) on a scratch copy, and
explain why the file is empty afterwards. The shell truncated it before `sort` could read it.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| Errors appear on the terminal although you redirected | `2>&1` placed before the `>` | Order of the operators |
| Permission denied with `sudo cmd > file` | The shell opens the file, as you | `sudo tee file` |
| Progress seems frozen in a pipeline | Block buffering in a middle stage | `--line-buffered`, `stdbuf` |
| A variable set in a pipeline is gone | Each stage runs in a subshell | Read from a here-string or process substitution |
| The pipeline reports success after a failure | Only the last status is reported | `set -o pipefail`, `PIPESTATUS` |
| A file became empty | Output redirected to a file the pipeline also reads | Write to a new file, then move it |
