# Dependency troubleshooting

This lesson follows the topic synthesis `synth/LNX-104/LNX-104-T06.md`, which carries the sources and the history.

## What you will be able to do

- Classify a failure into one of six layers and pick the matching tool.
- Resolve unmet dependencies with `dnf`, `rpm`, `apt` and `dpkg` without forcing.
- Find what provides a missing library.

## A method

Read the first error, not the last. Then classify: transport and metadata, offer (not in any enabled repository),
selection (priority, exclude, lock, hold, stream), constraint (an impossible request), state (broken database or lock),
run time (a library cannot be found). Reproduce without changing anything (`dnf --assumeno`, `apt-get -s`), change the
smallest thing, record it, and verify with `dnf check`, `apt-get check` or `dpkg --audit`.

## Red Hat family

```bash
dnf provides 'libfoo.so.1()(64bit)'     # who offers the missing capability
dnf repoquery --requires --resolve foo
dnf repoquery --whatrequires foo
dnf repoquery --unsatisfied; dnf repoquery --duplicates; dnf list --extras
dnf repolist --all; dnf versionlock list
dnf install --allowerasing foo          # read the removal list first
dnf install --nobest foo; dnf distro-sync
dnf --debugsolver install foo; dnf check
dnf clean expire-cache; dnf makecache
```

Frequent causes: the needed repository (`crb`, `epel`) is not enabled, a third-party repository needs a newer library
than the base, packages remain from an older release (`dnf list --extras`), a lock or `exclude=`, a stale mirror.
`rpm -Va`, `rpm -q --whatrequires foo` and `rpm --rebuilddb` are recovery tools; `rpm --nodeps` and `--force` are not.

## Debian family

```bash
apt-get -s install foo; apt-get check; apt --fix-broken install
dpkg --audit; dpkg --configure -a
apt-cache policy foo; apt-cache depends foo; apt-cache rdepends --installed foo
apt-mark showhold; apt-file search libfoo.so.1
apt install foo=1.2.3-1; dpkg --print-foreign-architectures
```

Frequent causes: mixed suites after a careless pin, a third-party repository that conflicts, a hold, a lock held by the
unattended upgrade timer (identify the holder with `fuser` before deleting a lock), a half-finished upgrade.

## Library problems at run time

When the packages are fine but a program fails: `ldd prog | grep 'not found'`, find the provider with
`dnf provides '*/libfoo.so.1'` or `apt-file search libfoo.so.1`, check `ldconfig -p`, and look for an architecture
mismatch (`:i386` or `.i686`). An undefined symbol means an interface change; compare builds with `abidiff`.

## Safe and unsafe repairs

Safe: enable or disable a repository, remove a stale pin or lock, refresh metadata, install the right provider,
reinstall, downgrade, `distro-sync`. Medium: let the solver remove packages, after reading the list; stop if
`systemd`, `glibc` or the kernel appear in it. Unsafe: `rpm --nodeps`, `dpkg --force-depends`, `--force-all`, editing
`/var/lib/dpkg/status` or the rpm database, copying libraries by hand. Snapshot first if you must.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| nothing provides X | repository not enabled | `dnf provides`, `dnf repolist --all` |
| held broken packages | pin or hold blocks the needed change | `apt-cache policy`, `apt-mark showhold` |
| conflicting requests | two packages exclude each other | `--debugsolver`, `dnf repoquery --duplicates` |
| works after `--nodeps`, fails later | database no longer matches reality | `dnf check`, reinstall |
