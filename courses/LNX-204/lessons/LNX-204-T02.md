# sudo policy

This lesson follows the topic synthesis `synth/LNX-204/LNX-204-T02.md`, which carries the sources and the history.

## What you will be able to do

- Write sudoers rules with aliases, run-as users and tags, and read them in the order sudo does.
- Recognise rules that are root shells in disguise, and use `sudoedit` instead.
- Control environment, authentication caching and logging, including I/O logs.
- Validate changes safely with `visudo`.

## Why delegate

Unix has root and everyone else. Real jobs need something in between: restart one service, edit one file. Sharing the root
password gives away everything and hides who did what. sudo sits between the user and the privilege, checks a policy,
cleans the environment, runs the command and records it.

## The grammar

```
Cmnd_Alias NGINX = /usr/bin/systemctl restart nginx.service, /usr/bin/systemctl reload nginx.service
%webops ALL = (root) NGINX
Defaults:%webops use_pty, log_output
```

A rule reads *who where = (runas) command*. Tags such as `NOPASSWD:`, `NOEXEC:` and `SETENV:` change behaviour per command.
**The last matching rule wins**, so read from the bottom. A bare path allows any arguments; a path with arguments allows exactly
those; `""` means no arguments. Edit only with `visudo` (or `visudo -cf file` for a drop-in under `/etc/sudoers.d/`), because a
syntax error can lock every administrator out. Drop-ins need mode 0440, and names with a dot are skipped.

## Dangerous grants

Any permitted program that can start a shell or write arbitrary files makes the rule meaningless: editors, pagers (`less`,
`man`), `find`, `tar`, `awk`, interpreters, `systemctl edit`. Wildcards in arguments are not path-aware: `cat /var/log/*` also
matches `cat /var/log/../../etc/shadow`. Negated commands are cosmetic, since a binary can be copied. To let someone edit one
file, use `sudoedit /etc/nginx/nginx.conf`: the editor runs as the user on a temporary copy and sudo writes it back.

## Authentication, environment and logs

sudo authenticates through the PAM service `sudo` and normally asks for the *user's* password. The result is cached per terminal
(five minutes by default; `sudo -k` forgets it). `env_reset` (default) drops most variables, `env_keep` lists survivors, and
`secure_path` fixes `PATH`, so `LD_PRELOAD` and friends do not reach a root process. Commands go to syslog with user, tty,
directory, target user and full command line. `log_output` records sessions you replay with `sudoreplay`; the audit framework
adds `USER_CMD` records ([lesson](lesson:LNX-204-T07)). `sudo -l` lists your rights; `sudo -U user -l` lists someone else's.

## A worked example

A webops group should restart, reload and check nginx and edit its main config, nothing else.

1. Write `/etc/sudoers.d/10-webops` as in the grammar above, adding `sudoedit /etc/nginx/nginx.conf` to the alias.
2. `visudo -cf /etc/sudoers.d/10-webops`, then `chmod 440`.
3. As a member: `sudo -l` shows exactly four commands; `sudo systemctl stop nginx.service` is refused; `sudoedit` works.

A failing version: `%dev ALL=(ALL) NOPASSWD: /usr/bin/vim /etc/app/*.conf`. The wildcard allows `../`, and vim runs `:!sh`, so this is root.

## Connections

- sudo's authentication is PAM ([lesson](lesson:LNX-204-T01)); a stolen SSH session still needs the password unless `NOPASSWD`.
- Short-lived SSH certificates replace standing privilege for automation ([lesson](lesson:LNX-204-T03)).
- SELinux can confine what the elevated process does ([lesson](lesson:LNX-204-T04)); AIDE watches `/etc/sudoers*` ([lesson](lesson:LNX-204-T08)).
- The Rust implementation `sudo-rs` is the default on some distributions and omits some features; test before migrating.
