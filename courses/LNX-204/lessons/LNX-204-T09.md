# OpenSCAP scans and remediation

This lesson follows the topic synthesis `synth/LNX-204/LNX-204-T09.md`, which carries the sources and the history.

## What you will be able to do

- Explain how XCCDF, OVAL, data streams and profiles fit together.
- Run `oscap` scans, read the report and generate remediation as bash or Ansible.
- Tailor a profile without editing the shared content, and record exceptions.
- Apply remediation with discipline, and know what a compliance score does not prove.

## The standards in one picture

An **XCCDF** benchmark holds rules grouped into **profiles** (CIS, DISA STIG, PCI-DSS, ANSSI and so on). Each rule's check is usually an **OVAL**
definition (a machine-checkable test of files, packages, sysctls, services); some use OCIL questionnaires. A **data stream** file
(`ssg-<product>-ds.xml`, from the `scap-security-guide` package in `/usr/share/xml/scap/ssg/content/`) bundles everything. Results are
pass, fail, notapplicable, error, notchecked, informational or fixed.

## Commands

```
oscap info ssg-rhel10-ds.xml                                     # profiles in the stream
oscap xccdf eval --profile <id> --results r.xml --report r.html ssg-rhel10-ds.xml
oscap xccdf eval --profile <id> --tailoring-file site.xml ...
oscap xccdf generate fix --profile <id> --fix-type ansible --output fix.yml r.xml
oscap oval eval --results oval.xml definitions.xml               # vulnerability definitions
oscap-ssh, oscap-podman                                          # remote hosts and containers
```

`oscap` exits 2 when rules fail. The content comes from the ComplianceAsCode project, written in YAML with rationale, references and one
remediation per rule.

## Tailoring and exceptions

Profiles are someone else's risk decisions. A **tailoring file** selects or deselects rules and sets variables (minimum password length,
faillock deny) without touching the content, so updates do not erase local decisions. Record why each rule is deselected: that register is
the evidence auditors read.

## Remediation discipline

Scan first, read the failures, test the fix on a clone or in Ansible check mode, apply in stages, rescan. Order matters: an SSH rule that disables
passwords before keys are installed locks you out. Some rules (partition layout) cannot be fixed on a running host, so build hardened images instead.
Run scans from a timer and keep the results as evidence.

## A worked example

1. `oscap info` to find the CIS server profile id; scan with `--report`.
2. Filter the report on `fail`, group by severity, and for each failure read rationale and fix.
3. Generate an Ansible playbook from the results, run it with `--check --diff`, apply to a canary, rescan, record the delta.

A failing case: `oscap xccdf eval --remediate` with a STIG profile on a production database host over SSH. The session drops, a service account can no longer read a
restricted file, and nobody knows which of fifty changes did it. Another: a rule passes because the check looks in the main file while the setting is in a drop-in.
