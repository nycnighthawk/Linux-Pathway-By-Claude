# AppArmor profiles

This lesson follows the topic synthesis `synth/LNX-204/LNX-204-T05.md`, which carries the sources and the history.

## What you will be able to do

- Describe AppArmor's path-based model and compare it with SELinux labels.
- Read and write a profile: rules, permission letters, execute modes, `deny`, abstractions.
- Move a profile through complain and enforce modes and build one with `aa-genprof` and `aa-logprof`.
- Attach profiles to containers and systemd units.

## The model

AppArmor confines a program by the **path** it uses. A profile is attached to an executable path (or expression) and lists what
the program may do: files, capabilities, network families, signals, mounts. Modes: **enforce** (violations denied and logged),
**complain** (allowed and logged, for learning), unconfined (no profile). `aa-status` shows what is loaded and which processes are
confined; `aa-enforce`, `aa-complain`, `aa-disable` switch modes; `apparmor_parser -r file` reloads a profile; `apparmor_parser -Q -K file`
only parses it.

## Profile syntax

```
#include <tunables/global>
profile myapp /usr/local/bin/myapp {
  #include <abstractions/base>
  capability net_bind_service,
  network inet stream,
  /etc/myapp/** r,
  /var/log/myapp.log w,
  /var/lib/myapp/** rwk,
  /usr/local/bin/myapp mr,
  deny /home/** rwx,
}
```

Every rule ends with a comma. Letters: `r` read, `w` write, `a` append, `k` lock, `l` link, `m` map executable. Execute modes: `ix`
inherit, `px` use the child's own profile, `Px` the same with environment scrubbing, `ux` run unconfined (avoid). Globs: `*` stays in a
directory, `**` descends. `deny` overrides allows. Abstractions bundle common needs (`base`, `nameservice`, `ssl_certs`).

## Building a profile

`aa-genprof /usr/local/bin/myapp` starts a learning session: run the program through its normal jobs in another terminal, scan the log,
answer the prompts (allow, deny, glob), save. Later, `aa-logprof` updates the profile from new denials. Keep the profile in complain mode
on a canary for a while, then `aa-enforce`. Do not learn on a compromised or abnormal workload, or the profile will encode it.

## Containers and units

Docker applies `docker-default` unless told otherwise; load a custom profile on the host (`apparmor_parser -r -W profile`) and run with
`--security-opt apparmor=name`. In Kubernetes the pod's security context names a localhost profile that must exist on every node that
could run the pod. A systemd unit can select a profile with `AppArmorProfile=`.

## A worked example

1. `aa-genprof /usr/local/bin/report`; exercise the service; accept sensible rules.
2. Review the file: remove catch-alls such as `/** rwix`, replace blanket `capability,` and `network,` with named rules.
3. `apparmor_parser -r report.profile`, then `aa-status | grep report` and check `journalctl -k | grep DENIED`.

A failing case: a deploy moves the binary from `/usr/local/bin` to `/opt/report/bin`. The profile attaches by the old path, so the new
binary runs unconfined and nothing complains. Compare expected and actual confinement with `aa-status` or a compliance scan.
