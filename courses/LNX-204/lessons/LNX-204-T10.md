# TLS and openssl

This lesson follows the topic synthesis `synth/LNX-204/LNX-204-T10.md`, which carries the sources and the history.

## What you will be able to do

- Read an X.509 certificate: SAN, validity, key usage, basic constraints, chain.
- Generate keys and requests, build a small CA and issue a certificate with `openssl`.
- Diagnose chain, name and expiry failures with `openssl s_client`, `verify` and `x509`.
- Use the system trust store and crypto policy, and automate renewal.

## The model

A certificate binds a public key to names, signed by an issuer. Clients walk a **chain** from the leaf through intermediates to a trusted root
and check signatures, dates, name (the subjectAltName; the common name is ignored when SAN exists), purpose (`extendedKeyUsage=serverAuth`), and sometimes
revocation. Servers should send the leaf and intermediates, not the root. TLS 1.3 removed weak features and made forward secrecy mandatory; allow
1.2 and 1.3 only, prefer AEAD suites with ECDHE.

## Commands

```
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out key.pem
openssl req -new -key key.pem -subj "/CN=app.example.org" -addext "subjectAltName=DNS:app.example.org" -out app.csr
openssl req -x509 -new -key ca.key -days 3650 -addext "basicConstraints=critical,CA:TRUE,pathlen:0" -out ca.pem
openssl x509 -req -in app.csr -CA ca.pem -CAkey ca.key -CAcreateserial -days 90 -extfile ext.cnf -out app.pem
openssl x509 -in app.pem -noout -subject -issuer -dates -ext subjectAltName
openssl verify -CAfile ca.pem -untrusted inter.pem app.pem
openssl s_client -connect host:443 -servername host -showcerts
openssl x509 -checkend 1209600 -noout -in app.pem     # non-zero exit if it expires within 14 days
```

Match a key to a certificate by comparing the digest of both public keys. Option names differ between OpenSSL 1.1.1 and 3.x (providers, legacy algorithms,
`-copy_extensions`), so test commands on the version you deploy. OpenSSL 3.5 is a long-term-support line with post-quantum algorithms.

## Trust and policy

System anchors: `/etc/pki/ca-trust/source/anchors/` plus `update-ca-trust` (Red Hat family), `/usr/local/share/ca-certificates/` plus
`update-ca-certificates` (Debian family). Adding a private root lets that CA vouch for any domain on the host unless name constraints apply; for one
application, pin its own `cafile`. Red Hat family systems have system-wide `update-crypto-policies` (DEFAULT, FUTURE, FIPS, LEGACY). Keep keys mode 0600
and owned by the service. Automate issuance (ACME clients, `certmonger`), monitor expiry with a probe against the live port, and **reload the service**
after renewal, because many daemons read certificates only at start. Public certificate lifetimes are shrinking in steps, so automation is no longer optional.

## A worked example

1. Build a CA, then a server key and request with SAN `app.lab.example`, sign for 90 days with `-extfile`.
2. `openssl verify -CAfile ca.pem app.pem` succeeds; `openssl x509 -noout -ext subjectAltName` shows the names.
3. Run `openssl s_server -cert app.pem -key app.key -www` and connect with `openssl s_client -CAfile ca.pem -verify_hostname app.lab.example`.

Failures: a client reports a missing local issuer certificate because the server forgot to send the intermediate; a CN-only self-signed certificate is rejected
for a name mismatch; a renewal job fetched a new certificate but never reloaded the web server; client code disables verification (`-k`, `verify=False`), the
most common TLS bug.
