# nftables hardening

This lesson follows the topic synthesis `synth/LNX-204/LNX-204-T06.md`, which carries the sources and the history.

## What you will be able to do

- Build a default-drop, dual-stack host firewall with stateful rules.
- Scope management access with sets, rate-limit connection attempts and log drops safely.
- Apply a ruleset without locking yourself out.
- Explain how containers and other managers interact with your rules.

## Structure

One `inet` table (IPv4 and IPv6 together), a base chain on the `input` hook with `policy drop`, and rules in a deliberate order:
loopback, `ct state invalid drop`, `ct state { established, related } accept`, ICMP and ICMPv6, then specific services, then a
rate-limited log. A host that does not route also drops `forward` and sets `net.ipv4.ip_forward=0`. Strict sites filter `output` too.

```
table inet filter {
  set mgmt4 { type ipv4_addr; flags interval; elements = { 10.20.0.0/24 } }
  chain input {
    type filter hook input priority filter;
    policy drop;
    iif lo accept
    ct state invalid drop
    ct state { established, related } accept
    icmpv6 type { echo-request, packet-too-big, nd-neighbor-solicit, nd-neighbor-advert, nd-router-advert, time-exceeded, destination-unreachable, parameter-problem } accept
    ip saddr @mgmt4 tcp dport 22 ct state new accept
    tcp dport { 80, 443 } ct state new accept
    limit rate 5/minute log prefix "nft-drop: "
  }
}
```

ICMPv6 carries neighbour discovery and path-MTU messages; dropping it breaks IPv6. Dropping ICMP wholesale causes hung large
transfers. Rules run in order and `accept` ends evaluation, so a rate limit must sit **before** the accept it protects.

## Rate limits and dynamic sets

`limit rate 10/second burst 20 packets` is a token bucket. Per-source control uses a set with `flags dynamic, timeout` and
`add @set { ip saddr limit rate over 3/minute } drop`, or a timed blackhole set. Rate limits help availability; they are not
authentication, which belongs to PAM and SSH ([lesson](lesson:LNX-204-T01), [lesson](lesson:LNX-204-T03)).

## Safe rollout

1. `nft -c -f /etc/nftables.conf` checks syntax without applying.
2. Keep a second session open and arm a revert (`systemd-run --on-active=2m nft -f /etc/nftables.conf.good`).
3. `nft -f` loads the file atomically. Test a new session from allowed and disallowed sources, then cancel the revert.
4. `nft list ruleset` (add `-a` for handles) and `nft monitor trace` with `meta nftrace set 1` on a test rule explain behaviour.
5. Enable `nftables.service`; compare `nmap -sS -p-` with `ss -tulpn`.

Do not run firewalld, ufw and a hand-written ruleset at once. Container engines add their own tables; published ports are forwarded,
so they bypass `input` and need `forward` rules or engine settings.

## A worked example

A host exposes 22, 80 and 443 and should accept SSH only from the management range. Write the file above, check with `nft -c`, load with a
revert timer, confirm an SSH attempt from outside the range times out and that counters on the web rule grow. A failing version puts
`tcp dport 22 accept` above the `ct state invalid drop` and the limiter, so brute-force protection never runs.
