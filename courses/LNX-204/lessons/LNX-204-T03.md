# SSH hardening, SSH certificates

This lesson follows the topic synthesis `synth/LNX-204/LNX-204-T03.md`, which carries the sources and the history.

## What you will be able to do

- Harden `sshd_config` and verify the result with `sshd -t` and `sshd -T`.
- Choose algorithms by editing defaults rather than freezing lists, and know where crypto policy overrides them.
- Restrict what a key may do, and avoid agent forwarding.
- Create a certificate authority, sign user and host certificates and configure servers and clients to trust it.

## Hardening the server

Core directives: `PermitRootLogin no`, `PasswordAuthentication no`, `KbdInteractiveAuthentication no` (unless used for a second
factor), `AuthenticationMethods publickey`, `MaxAuthTries 3`, `LoginGraceTime 30`, `AllowGroups sshusers`,
`DisableForwarding yes` (or specific `AllowTcpForwarding`, `X11Forwarding`, `AllowAgentForwarding`), `ClientAliveInterval` with
`ClientAliveCountMax`, and a `Banner`. `Match` blocks scope exceptions and run to the next `Match`, so put them last.
Settings are **first obtained wins**, and drop-ins in `sshd_config.d/` are read in order, so a distribution drop-in can beat your
line. Always verify the effective value: `sshd -T` (with `-C user=...,addr=...` to test `Match`), and syntax: `sshd -t`. Reload
keeps live sessions, so test from a second connection before closing the first.

Algorithms: remove weak items from the defaults (`Ciphers -3des-cbc`) instead of writing whole lists. On Red Hat family systems
`update-crypto-policies` sets OpenSSH's allowed set. Prefer Ed25519 keys (`ssh-keygen -t ed25519`), RSA of 3072 bits when
required, and `ed25519-sk` for hardware-backed keys. Recent OpenSSH releases dropped DSA and made a hybrid post-quantum key
exchange the default (check release notes for your version).

Per-key restrictions in `authorized_keys`: `restrict,command="/usr/bin/backup",from="10.0.0.0/8"`. Clients: `IdentitiesOnly yes`
and `ProxyJump` rather than forwarded agents, since root on the bastion can use a forwarded agent socket.

## Certificates

A certificate binds a public key to a key id, principals, a validity window and options, signed by a CA key.

```
ssh-keygen -t ed25519 -f user_ca -C "user CA"                  # offline CA key
ssh-keygen -s user_ca -I alice@example -n alice,deploy -V +8h id_ed25519.pub
ssh-keygen -L -f id_ed25519-cert.pub                           # inspect
```

Server: `TrustedUserCAKeys /etc/ssh/user_ca.pub`. Which principal may log in as which account comes from
`AuthorizedPrincipalsFile /etc/ssh/auth_principals/%u` (one principal per line); without it, the principal must equal the
account name. Host certificates run the other way: `ssh-keygen -s host_ca -I web1 -h -n web1.example.org host_key.pub`, then
`HostCertificate` in `sshd_config`, and `@cert-authority *.example.org <CA public key>` in clients' `known_hosts`. Rebuilt servers
then present valid identities with no first-use prompt. Revocation is a `RevokedKeys` list, but short lifetimes do the real work.

## A worked example

1. Generate a CA key pair offline and copy `user_ca.pub` to the server.
2. Set `TrustedUserCAKeys` and an `AuthorizedPrincipalsFile`; add `deploy` to `auth_principals/alice`.
3. Sign Alice's key for eight hours; log in with `ssh -v` and look for the certificate being offered.
4. After eight hours the same key is rejected.

Typical failures: the principal does not match, so the server log says it is not listed; a distribution drop-in sets
`PasswordAuthentication yes` earlier than your file; `AllowGroups` changed with only one session open.

## Connections

- Passwords on the remote path are replaced by keys or certificates; PAM still applies with `UsePAM yes` ([lesson](lesson:LNX-204-T01)).
- Certificates are the SSH counterpart of X.509 ([lesson](lesson:LNX-204-T10)): trusted signer, short life, scoped names.
- Rate limits and source restrictions belong in nftables ([lesson](lesson:LNX-204-T06)); logins appear in audit ([lesson](lesson:LNX-204-T07)).
