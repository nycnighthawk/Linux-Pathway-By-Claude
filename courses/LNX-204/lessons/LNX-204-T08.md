# AIDE

This lesson follows the topic synthesis `synth/LNX-204/LNX-204-T08.md`, which carries the sources and the history.

## What you will be able to do

- Explain baseline-and-diff integrity monitoring and what it can and cannot prove.
- Write an `aide.conf` with attribute groups, rules and exclusions.
- Initialise, check and update the database, and read the exit status.
- Protect the baseline and tool from the host being monitored.

## The idea

Record a trusted state of files (hashes and attributes), later recompute and compare, and explain every difference. AIDE does this with a
configuration (`/etc/aide.conf`; Debian family `/etc/aide/aide.conf`), a database (`/var/lib/aide/aide.db.gz`) and four modes:
`--init` builds a new database (`aide.db.new.gz`, which you move into place), `--check` compares, `--update` checks and writes a new database,
`--compare` diffs two databases.

## Configuration

```
Mine = p+u+g+s+m+sha256         # attribute group
/usr/bin    Mine
/etc        Mine
!/etc/mtab                      # exclude
!/var/log
```

Attributes: `p` permissions, `u`/`g` owner and group, `s` size, `m` mtime, `c` ctime, `i` inode, `n` link count, `acl`, `selinux`, `xattrs`, `caps`,
and hashes (`sha256`, `sha512`). Rules are regular expressions on paths. Monitor what should not change: binaries, libraries, `/boot`,
`/etc` (SSH, PAM, sudoers, audit, firewall, SELinux and AppArmor policy), startup and cron directories. Exclude volatile areas.

## Reading results

`aide --check` prints a summary (added, removed, changed) and attribute-level details. The exit status is a bit mask: 1 added, 2 removed,
4 changed, and higher values for errors, so scripts can tell "differences found" from "failed to run". Run it daily from a systemd timer or
cron and send the output where someone reads it.

## Keeping the baseline honest

- Initialise on a freshly built, known-good host or image **before** it joins the network.
- Store the database, a checksum of the `aide` binary and the configuration where the monitored host cannot rewrite them (off-host or read-only).
- Update the baseline in a controlled step after patching, after reviewing the diff; store the new database safely.
- Remember the limits: it detects between checks, a kernel rootkit can hide files from the system calls AIDE uses, and a baseline taken on a compromised host blesses the compromise.

## A worked example

1. Install AIDE, `aide --init`, move `aide.db.new.gz` to `aide.db.gz`, copy it off-host. A check reports no differences.
2. Edit `/etc/hosts` and `chmod 777` a script. The next check lists the changed hash, size and mtime for the first and the old and new modes
   for the second.
3. After patching, review `aide --check`, then `aide --update` and archive the new database.

A failing case: the nightly report goes to a mailbox nobody reads; three hundred changes accumulate over a year, including a modified
`/etc/ld.so.preload`.
