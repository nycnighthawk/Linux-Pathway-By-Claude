# VFIO PCI passthrough and IOMMU groups

This lesson follows the topic synthesis `synth/LNX-315/LNX-315-T01.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Say why a device assigned to a guest needs an IOMMU, and what the IOMMU group guarantees.
- Prepare a host (firmware, kernel parameters, driver binding) and verify each step.
- Read a group listing and decide whether a device can be assigned, and attach it with libvirt.

## Why passthrough is risky

A PCI device does DMA: it writes to memory without the CPU. If a guest controls the device, the guest controls where it writes. The **IOMMU** (VT-d, AMD-Vi, ARM SMMU) translates device addresses through page tables the host controls, so the device can reach only memory the host mapped for it. Interrupt remapping stops forged interrupts.

## IOMMU groups

The group is the smallest set of devices the IOMMU can isolate from everything else. Reasons devices share a group: bridges without ACS, multifunction devices, peer-to-peer paths below the IOMMU. **All endpoint devices of a group go to one owner**, so assigning one device means the whole group, or leaving other members unbound. ACS on bridges splits groups; the ACS override patch splits them by force and gives up the isolation guarantee.

## Host preparation

1. Firmware: enable VT-d or IOMMU, and above-4G decoding for large BARs.
2. Kernel: `intel_iommu=on` (AMD is on by default in recent kernels), often with `iommu=pt` so host devices skip translation.
3. Verify: kernel log lines for DMAR or AMD-Vi, and numbered directories under `/sys/kernel/iommu_groups`.
4. List groups and find the target:

```bash
for g in /sys/kernel/iommu_groups/*; do echo "group ${g##*/}"; for d in $g/devices/*; do lspci -nns ${d##*/}; done; done
```

## Binding and attaching

Dynamic binding: libvirt `managed='yes'` unbinds the host driver at start and rebinds at stop. Static binding: `vfio-pci.ids=VENDOR:DEVICE,...` (or a modprobe option) so the host driver never claims the card, needed for GPUs the host would grab at boot. Check `lspci -k` shows `vfio-pci` and `/dev/vfio/N` exists.

```xml
<hostdev mode='subsystem' type='pci' managed='yes'>
  <source><address domain='0x0000' bus='0x01' slot='0x00' function='0x0'/></source>
</hostdev>
```

Use UEFI (OVMF) and `q35` for modern GPUs. All guest RAM is pinned, so overcommit, ballooning and normal live migration are off the table.

## What goes wrong

Shared groups; a reserved memory region (RMRR) conflict; a card that does not reset between guests (host reboot needed); a driver that detects virtualisation; the wrong GPU in the primary slot; a device with updatable firmware handed to an untrusted tenant.

## Worked example: "group is not viable"

A NIC port is requested for a VM, but the other port of the same adapter is the host's management link in the same group. Either move management elsewhere, use a different slot, or use SR-IOV virtual functions, which have identities of their own.
