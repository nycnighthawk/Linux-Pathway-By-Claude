# Firmware, trusted boot and confidential VMs

This lesson follows the topic synthesis `synth/LNX-315/LNX-315-T05.md`, which carries the sources, the history and the open research questions.

## What you will be able to do

- Pick SeaBIOS or OVMF for a guest and write the XML for UEFI with Secure Boot.
- Give a guest a persistent software TPM.
- Explain what SEV-SNP and TDX protect, what they do not, and how attestation releases a secret.

## Firmware choice

SeaBIOS is the default and suits legacy guests and quick tests. OVMF (UEFI) is required for Secure Boot, GPT boot disks, Windows 11, modern GPU passthrough and confidential guests. In libvirt, `<os firmware='efi'>` lets libvirt pick a matching build from the installed firmware descriptors.

## Secure Boot and the vTPM

Secure Boot in a guest needs SMM (`<smm state='on'/>`), a secure OVMF build and a variable store holding keys. Use the enrolled-keys template, or edit the store offline with `virt-fw-vars`.

A TPM is a `<tpm>` device with an `emulator` backend, version `2.0`; libvirt starts `swtpm` with a state directory per VM. Keep that state: if it is lost, BitLocker or LUKS keys sealed to it cannot be unsealed.

```xml
<os firmware='efi'><type machine='q35'>hvm</type>
  <firmware><feature enabled='yes' name='secure-boot'/></firmware></os>
<features><smm state='on'/></features>
<tpm model='tpm-crb'><backend type='emulator' version='2.0'/></tpm>
```

## Confidential guests

SEV, SEV-ES and SEV-SNP (AMD) and TDX (Intel) encrypt guest memory with keys the host cannot read. SNP and TDX add integrity: the host cannot replay or remap pages unnoticed. Hosts need firmware, kernel, QEMU and libvirt support, and guests need a matching firmware build (SNP-capable OVMF, TDVF) and kernel. libvirt describes the guest with `<launchSecurity type='sev-snp'>` and `cbitpos`, `reducedPhysBits` and `policy`.

## Attestation

Encryption alone proves nothing to a remote party. The guest asks the hardware for a signed report that holds the launch measurement and a nonce. A relying party checks the vendor signature chain and revocation, compares the measurement with a known-good value, and only then releases a secret over a channel tied to the report.

## What goes wrong

Missing SMM, so Secure Boot variables are exposed; TPM state deleted with the VM definition; an ASID limit that caps how many SEV guests run; a firmware that is not SNP-capable; trusting a guest image that was never measured; side channels that remain despite encryption; ordinary live migration, which does not work with encrypted memory.
