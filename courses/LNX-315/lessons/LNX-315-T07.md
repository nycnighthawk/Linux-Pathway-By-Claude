# VirtualBox beside KVM, and on top of it

This lesson follows the topic synthesis `synth/LNX-315/LNX-315-T07.md`, which carries the sources and the open questions. The KVM-backend facts are recent. What Oracle documents is narrow: its VirtualBox 7.2.2 change log (10 September 2025) says Linux hosts use KVM APIs on kernel 6.16.0 and newer for acquiring and releasing VT-x. The wider claims below (a full `/dev/kvm` execution engine, feature parity) are not in Oracle's change log, so treat them as what the lesson expects you to test, not as documented behaviour.

## What you will be able to do

- Explain why two hypervisors conflict over the processor's virtualization feature.
- Diagnose the common failure and apply the `enable_virt_at_load` fix.
- Compare the arrangements for running both stacks and pick one.

## The conflict

Hardware virtualization (VMX on Intel, SVM on AMD) is entered by one owner per core. KVM takes it through `kvm_intel` or `kvm_amd`. The native VirtualBox driver, `vboxdrv`, takes it for its own guests. If KVM already holds it, VirtualBox reports a VMX root mode error; the reverse also fails. A third symptom is a guest that starts without hardware assistance and runs very slowly.

## Arrangements

| Arrangement | Guests at once | Cost |
|---|---|---|
| Time-sliced | one stack only | module juggling |
| `enable_virt_at_load=0` | one stack only, but both installed | kernel 6.12 or newer |
| Nested (one hypervisor in a guest of the other) | yes | slower, extra OS |
| VirtualBox with KVM-mediated VT-x (7.2.2 or newer, kernel 6.16 or newer) | yes | new; only the VT-x handoff is documented, so test your guests |

The lazy-enable option goes in `/etc/modprobe.d/` as `options kvm enable_virt_at_load=0`. It stops KVM claiming the feature at module load, so VirtualBox can start when no KVM guest runs.

## The KVM backend

From VirtualBox 7.2.2, on a host kernel of 6.16.0 or newer, VirtualBox acquires and releases VT-x through KVM instead of taking it directly (Oracle change log). Because KVM owns the processor feature, QEMU and VirtualBox guests can run together. This lesson's expectation, which Oracle's change log does not spell out, is that management through VBoxManage, disk formats and Guest Additions stay the same. Saved-state portability and some features (nesting, graphics modes) need testing. On older kernels the earlier arrangements in the table still apply.

## Secure Boot

`vboxdrv` is an out-of-tree module. On a Secure Boot host it must be signed with a key enrolled through MOK. A KVM-backed guest path removes that module from guest execution.

## Habits

Keep libvirt and VirtualBox networks and image directories apart. Never open one disk image in both stacks. Record which stack owns the feature at boot. Qualify guests and keep a rollback.

## Self-check

1. Who holds VMX when VirtualBox says it cannot operate in VMX root mode?
2. What does `enable_virt_at_load=0` change, and what does it not?
3. Why can a KVM-backed VirtualBox run beside QEMU?
4. Why is a slow guest with no error dangerous?
5. Why open one image in only one stack?
