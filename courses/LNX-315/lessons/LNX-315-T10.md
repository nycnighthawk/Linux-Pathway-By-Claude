# Migrating from VMware with virt-v2v and migration toolkits

This lesson follows the topic synthesis `synth/LNX-315/LNX-315-T10.md`. Product names, licence terms and option names are marked (to verify) there.

## What you will be able to do

- Say what a conversion must change in a guest and what it leaves alone.
- Choose an input path from VMware and an output path for the target.
- Sort an inventory into convert, rebuild, application-level and individual cases, and plan waves with rollback.

## What conversion changes

A VMware guest expects emulated controllers and NICs and runs VMware Tools. `virt-v2v` edits the disk offline: it makes the initramfs contain virtio drivers, rewrites device references, tries to remove vendor tools and, for Windows, injects virtio drivers (from the virtio-win package) and installs them over several first-boot reboots. It does **not** reconfigure guest addressing; interface names or MACs may change.

## Input paths

| Input | Notes |
|---|---|
| vCenter (`-ic vpx://`) | easy, slowest for disk copy |
| VDDK (`-it vddk`) | usually fastest, proprietary library you obtain yourself |
| NFC | non-proprietary, port 902, memory limits on ESXi |
| VMX files, local or over SSH | SSH is off on ESXi by default; fails with snapshots |
| OVA | from vSphere only |

Shut the guest down cleanly. A converted snapshot is for tests only.

## Output paths

Local libvirt guest, a directory of disks and XML, QEMU script, OpenStack, oVirt, or (experimental) KubeVirt YAML. Choose qcow2 or raw per the storage topic.

## Prerequisites

- **Linux:** kernel new enough for virtio, no Xen PV-only kernel, a passphrase slot for TPM-sealed LUKS.
- **Windows:** virtio-win drivers, Fast Startup off, no dynamic system disk, BitLocker recovery key ready, expect reactivation, finish VMware Tools removal by hand if needed.

## Managed toolkits and waves

A toolkit (Migration Toolkit for Virtualization, upstream Forklift, for OpenShift Virtualization) adds discovery, network and storage mapping, validation, plans and waves, and optionally warm migration with changed-block tracking. Underneath it uses the same converter.

Sort each machine:

1. **Rebuild** stateless services from images.
2. **App-level** replication for databases.
3. **Convert** ordinary guests.
4. **Individual** design for shared disks, dongles, passthrough and raw device mappings.

Pilot first, then waves by dependency, with the source kept powered off until acceptance and DNS TTL lowered.

## Verify

Boots unattended, uses virtio, address and DNS right, agent reports, old tools gone, application tests pass, backup and monitoring repointed. `virt-inspector` can check a disk without booting it.

## What goes wrong

Emergency shell from a missing initramfs driver; static IP lost to a renamed interface; vCenter session limits hit by parallel jobs; snapshots left for months; reactivation surprises; two live copies on the network.

## Self-check

2. Why does conversion not fix static IP addresses?
3. Which machines should not be converted by a tool?
4. Why keep the source powered off but intact?
5. What does warm migration add?
