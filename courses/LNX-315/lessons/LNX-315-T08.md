# Image pipelines: Packer, virt-builder and cloud-init

This lesson follows the topic synthesis `synth/LNX-315/LNX-315-T08.md`, which carries the sources, history and failure cases. Tool-licence and sub-command details are marked (to verify) there.

## What you will be able to do

- Split an image into base, role and instance layers and say what belongs in each.
- Choose between Packer, virt-builder and a vendor image builder for a task.
- Write and validate a cloud-init NoCloud seed, and build a pinned base with a cheap overlay.

## The three layers

1. **Base**: the operating system and updates, built rarely, from a trusted and pinned source.
2. **Role**: software a class of machine needs.
3. **Instance**: identity, keys, hostname and network, supplied at first boot by cloud-init. Never bake these in.

## The tools

- **Packer** boots a hypervisor, drives an installer or starts from an existing image, runs provisioners over SSH and post-processes (convert, compress, box). One template can have a KVM source and a VirtualBox source.
- **virt-builder / virt-customize / virt-sysprep** (libguestfs) edit images offline in a small appliance: install packages, upload files, set keys, generalise. Fast, no running guest, but they cannot exercise the booted system.
- **Vendor image builders** compose supported images from a blueprint.
- **cloud-init** configures the instance at first boot from a datasource.

Prefer a vendor cloud image as the base: it is already generalised and skips the installer.

## Generalise before you capture

Reset the machine identifier, SSH host keys, cloud-init state, persistent network rules, logs, history, caches and build credentials. virt-sysprep lists these as named operations you can review.

## The NoCloud seed

A volume labelled `cidata` holds `user-data` (first line `#cloud-config`), `meta-data` (instance-id, local-hostname) and optionally `network-config`. Changing the instance-id makes cloud-init run again; a wrong label means the seed is silently ignored.

```yaml
#cloud-config
users:
  - name: ops
    ssh_authorized_keys: [ssh-ed25519 AAAA... ops@example]
ssh_pwauth: false
packages: [qemu-guest-agent]
```

Keep secrets out of user-data: it can be read by other processes. Use public keys and short-lived tokens.

## Two hypervisors

Build once, convert the container format (`qemu-img convert`) for VDI or VMDK. The seed is portable: VirtualBox can attach a `cidata` ISO as an optical disk. Test on each target, because virtual hardware differs.

## Test the artefact

Without booting: package list, no build credentials, no host keys, format and size, checksum. With a boot: cloud-init reports done, SSH with the injected key works, the second boot does not repeat first-boot work, and a clone gets a new machine-id.

## What goes wrong

Shared host keys across clones; a build account left in; an unpinned "latest" base; a seed with the wrong label; secrets in user-data; very long runcmd lists nobody can review.
