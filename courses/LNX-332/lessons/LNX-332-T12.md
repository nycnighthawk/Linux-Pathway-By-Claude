# Upstreaming to KVM and QEMU

This lesson follows the topic synthesis `synth/LNX-332/LNX-332-T12.md`. Process details (lists, forges, style limits) change; read the current documents in each tree (to verify).

## What you will be able to do

- Find the maintainers and lists for a change in KVM or QEMU.
- Write a commit message and split a change into a reviewable series.
- Send and revise a series, and answer review comments.
- Run the style checkers and attach a test.

## Workflow

1. Read the submitting-patches document in the tree; search the list archive.
2. Make small, ordered patches; each builds and works; add a test.
3. Subject `subsystem: summary`, a body with problem, reason, alternatives and testing; `Fixes:` for bugs; `Signed-off-by:`.
4. Run the checker; build with warnings; run tests.
5. `git format-patch` and `git send-email` (or `b4`), cover letter for a series, maintainers in To, lists in Cc.
6. Reply inline in plain text; send v2 with a changelog after `---`.

## Style differences

| | Kernel (KVM) | QEMU |
|---|---|---|
| Indent | tabs | 4 spaces |
| Checker | `scripts/checkpatch.pl` | `scripts/checkpatch.pl` in the QEMU tree |
| Tests | kselftest (KVM selftests) | qtest, functional tests |
| List | `kvm@vger.kernel.org` and arch lists | `qemu-devel@nongnu.org` |

## What reviewers look for

Correctness on all configurations, migration and saved state, guest-controlled input, documentation, small API surface, a test.

## Self-check

Try each question before you read the answers below.

1. Where do the changes between v1 and v2 go?
2. Which list receives a QEMU patch, and which a KVM patch?
3. What must every patch in a series do on its own?

### Answers

1. Below the `---` line of each patch and in the cover letter, not in the commit message.
2. `qemu-devel@nongnu.org` for QEMU; `kvm@vger.kernel.org` plus the architecture list for KVM.
3. Build and work, so bisecting through the series never hits a broken state.
