# Patching VirtualBox's KVM backend

This lesson follows the topic synthesis `synth/LNX-332/LNX-332-T11.md`. Which release carries the Linux KVM backend, and its completeness, must be checked in the source you use (to verify).

## What you will be able to do

- Explain why a VMM uses a host hypervisor API instead of its own driver.
- List the operations a backend must provide.
- Map KVM exits onto a VMM's events and handle the unmapped ones loudly.
- Plan a small, testable patch in a large code base.

## The backend contract

init/term, create VM, create/destroy vCPU, map/unmap guest memory, get/set CPU state, run until exit, inject and cancel interrupts, query capabilities.

## Exit mapping

| KVM exit | VMM event |
|---|---|
| IO | I/O-port handler (once per element, write result back for reads) |
| MMIO | memory handler |
| HLT | idle logic |
| SHUTDOWN | triple fault |
| INTR | check pending requests |
| INTERNAL_ERROR, FAIL_ENTRY | fatal diagnostic with the raw reason |

## State synchronisation

Keep a dirty mask: transfer registers only when the VMM needs them (on exit handling, snapshot, debugger).

## Patch workflow

1. Find the interface and a working backend; read how each op is implemented.
2. Make the smallest change; build with the project's build system.
3. Run a known guest; collect release logs; compare with the default backend.
4. Test snapshot/restore and vCPU hotplug.
5. Send the patch through the project's contribution route.

## Self-check

Try each question before you read the answers below.

1. Why would a VMM use KVM instead of its own kernel driver?
2. What should a backend do with an exit it cannot map?
3. Why keep a dirty mask for vCPU state?

### Answers

1. It can share the CPU feature with other KVM users and drops an out-of-tree module that must be built and signed.
2. Stop with a clear diagnostic that includes the raw reason, never ignore it.
3. Moving registers is costly, so they are synchronised only when the VMM needs them.
