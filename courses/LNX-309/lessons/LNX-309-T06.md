# Real power fencing

This lesson follows the topic synthesis `synth/LNX-309/LNX-309-T06.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Choose between power fencing, fabric fencing and watchdog fencing for a given cluster.
- Apply the three independence rules to a real wiring plan.
- Build a fencing topology with two independent levels, and set a delay so the right node survives a split.
- Test a fence device first with `pcs stonith fence`, then with a real failure.

## Vocabulary

| Term | Meaning |
|---|---|
| Power fencing | cut the power of the target (management controller, switched outlet, hypervisor or cloud API) |
| Fabric fencing | cut the target's access to storage or network instead |
| Fencing level | one step of a topology, tried in ascending order (1 to 9); all devices in a level must succeed |
| `pcmk_host_map` | tells a shared device which port or name belongs to which node |
| `pcmk_delay_base` | fixed pause before a device acts; put it on the device that fences the node you prefer to lose |
| SBD / watchdog | the node resets itself when it loses quorum or stops refreshing its cluster view |

## The three independence rules

1. A fence device must not depend on the cluster's own network.
2. At least one device per node must not share power with that node.
3. No device may depend on the target working (no "ssh in and shut down" in production).

An onboard controller that shares the node's power feed fails together with the node. Give it a second level on another feed.

## Topology sketch

```
pcs stonith level add 1 node1 fence-n1-bmc
pcs stonith level add 2 node1 fence-pdu
pcs stonith level verify
```

Level 1 failing makes Pacemaker try level 2. Two outlets for dual power supplies belong in the same level, because both must go off.

## Two-node duel

Both nodes may try to fence each other when only the link fails. Add `pcmk_delay_base` to the device that fences the node you can lose. Larger clusters need no delay because quorum decides.

## SBD timeouts

`stonith-watchdog-timeout` must exceed `SBD_WATCHDOG_TIMEOUT`, and the watchdog timeout must not be smaller than the quorum device sync timeout (30 s by default). Test the watchdog with `pcs stonith sbd watchdog test` before the daemon owns the device (it reboots the machine).

## Testing

1. `pcs stonith fence <node>` proves the cluster can use the device. Test by the same name or address that the configuration holds.
2. A real failure proves the cluster will use it: pull the cluster cable or block corosync traffic with the firewall. Do not just take the local interface down. A kernel panic test can lose data, so stop resources first.
3. Repeat on a schedule, and monitor the device itself.

## Self-check

1. Which three rules must a fence device satisfy?
2. What happens when a level-1 device fails?
3. Why does a two-node cluster need a fencing delay, and where do you put it?
4. Why is taking the local interface down a weak fencing test?
