# Pacemaker, Corosync and fencing

This lesson follows the topic synthesis `synth/LNX-309/LNX-309-T01.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Explain the roles of Corosync (membership, quorum) and Pacemaker (resource management).
- Build a two-node cluster with `pcs` and add an address and a service with ordering and colocation.
- Explain quorum, split brain and why fencing is mandatory when data is shared.
- Use `fence_virsh` in a virtual lab and know why it is not for production.

## The stack

| Piece | Job |
|---|---|
| Corosync | membership list, messaging, quorum votes |
| Pacemaker | holds the configuration (CIB), decides placement, runs resource agents |
| `pcs`/`pcsd` | command line and node-to-node service that configures both |
| Resource agent | script that starts, stops and monitors one resource (OCF, systemd, STONITH) |
| Fence device | removes a node from the cluster by force |

One node acts as designated controller and computes the plan; the plan is carried out on every node.

## Build it

```bash
# every node
dnf install pacemaker pcs && systemctl enable --now pcsd
firewall-cmd --permanent --add-service=high-availability && firewall-cmd --reload
passwd hacluster
# one node
pcs host auth node1 node2
pcs cluster setup web node1 node2
pcs cluster start --all && pcs cluster enable --all
pcs resource create vip ocf:heartbeat:IPaddr2 ip=192.168.122.50 cidr_netmask=24
pcs resource create site ocf:heartbeat:apache op monitor interval=1min
pcs constraint colocation add site with vip INFINITY
pcs constraint order vip then site
pcs constraint location site prefers node2=50
pcs status
```

Scores: INFINITY means must, a number means prefer, negative means avoid.

## Quorum

A partition may run resources only with a majority of votes. Two nodes have no majority after a split, so two-node mode keeps the survivor alive and depends on fencing. A third vote, a quorum device (`corosync-qnetd`) or a multi-site ticket manager (Booth) restores a safe tie-break.

## Fencing

A silent node is not necessarily stopped. Fencing forces it off before others touch shared data. With no fence device the cluster will not start resources. Power fencing cuts power; fabric fencing cuts access to storage or network. A BMC that shares power or network with the host is a weak fence device, and an SSH login to the node is no fence device at all.

In a lab: `pcs stonith create fence_lab fence_virsh ip=<hypervisor> pcmk_host_map="node1:vm-node1;node2:vm-node2" ...` then test with `pcs stonith fence node2`.

## Operations

`pcs status`, `pcs node standby/unstandby`, `pcs resource move` then `pcs resource clear`, `pcs resource cleanup`, `pcs constraint`, `journalctl -u pacemaker -u corosync`.

## Worked example: the unfenced pair

Fencing was disabled to get past an error and never restored. A switch fault cut the heartbeat; both nodes stayed up, both mounted the shared file system and wrote to it. Restore from backup followed. With fencing, one node would have powered the other off first.
