# DR drills

This lesson follows the topic synthesis `synth/LNX-309/LNX-309-T05.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Set RTO and RPO with the business and pick a recovery strategy that meets them.
- Describe the kinds of drill and run one with objectives, a timeline, validation and a review.
- Prove that a backup restores, and measure recovery time and data loss.
- Avoid the classic traps: untested backups, circular dependencies, failback surprises.

## Vocabulary

| Term | Meaning |
|---|---|
| RTO | longest tolerable time to a working service |
| RPO | longest tolerable window of lost data |
| Failover / failback | move to the recovery site / return to the primary |
| Reconstitution | return to a fully operational, known state |

## Strategies, cheapest to dearest

1. Backup and restore (RTO hours to days).
2. Pilot light: data replicated, compute started on demand.
3. Warm standby: a reduced running copy.
4. Hot site or active/active: full capacity in two places.

Objectives choose the rung. Backups must live where the disaster cannot reach and, ideally, cannot be deleted by an attacker with administrator rights.

## Kinds of drill

- **Tabletop**: walk the scenario on paper.
- **Component test**: restore a backup to a scratch host, fail over a database standby, put a cluster node in standby.
- **Sampling restore**: restore a sample of backup data and check the functions.
- **Full site failover** with real traffic, then failback.
- **Chaos exercise**: unannounced failure within safety limits.

## Running a drill

1. Objective, scope and success criteria (RTO, RPO).
2. Preparation: approvals, backout plan, observers, a clock.
3. Execution: follow the runbook; log each step and each deviation.
4. Validation: functional tests, data checks (row counts, latest transaction, checksums), dependants.
5. Failback and verify the primary is authoritative again.
6. Review: measured against target, findings with owners and dates, runbook fixes.

## Tools

ReaR for bare-metal restore, database replicas and archived logs for data, Pacemaker disaster-recovery clusters and Booth tickets for multi-site control, infrastructure as code for the recovery environment.

## Worked example: the key that burned

Backups were encrypted and the key lived in a secrets manager in the burned data centre. Recovery took nine days against an RTO of one. A drill that forbade any use of the primary site would have found it.
