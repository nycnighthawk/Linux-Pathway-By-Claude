# DRBD and GFS2 awareness

This lesson follows the topic synthesis `synth/LNX-309/LNX-309-T02.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Say how a cluster gets its data on the node that takes over, and compare shared, replicated and application-level options.
- Write a DRBD resource and run it under Pacemaker as a promotable clone.
- Explain what GFS2 and the distributed lock manager add, and why fencing is part of the design.
- Recognise split brain and the situations where these tools are the wrong choice.

## Where the data lives

| Approach | Example | Note |
|---|---|---|
| Shared device | SAN LUN | one node mounts at a time, or a cluster file system |
| Replicated block device | DRBD | network RAID-1, private copy per node |
| Application replication | PostgreSQL streaming | next topic |
| Network file system | NFS server | moves the problem to the server |

## DRBD in one page

- Backing device per node (an LVM volume is typical), same size.
- Resource file: `device`, `meta-disk`, `net { protocol C; fencing resource-and-stonith; verify-alg }`, `handlers` (fence-peer scripts), an `on` section per node with `node-id`, and a `connection`.
- Bring-up: `drbdadm create-md`, load the module, `drbdadm up`, choose the initial primary, wait for `UpToDate`.
- Protocols: C synchronous (no acknowledged write lost), B memory on the peer, A asynchronous (may lose the last writes).
- `drbdadm status` shows role and disk state: `UpToDate`, `Inconsistent`, `Outdated`.

## Under Pacemaker

The DRBD device is a promotable clone; the `Filesystem` resource is colocated with the promoted role and ordered after `promote`. Queue changes with `pcs cluster cib <file>` and `pcs -f <file> ...`, then push them in one go.

## GFS2

A cluster file system lets several nodes mount the same device. It needs the DLM, one journal per node, a lock table named `<cluster>:<fs>` and `-p lock_dlm`. DRBD then needs two promoted instances (`allow-two-primaries`). The DLM freezes until a lost node is fenced, so a cluster file system without working fencing stalls or corrupts.

Two-node clusters can fence each other at the same moment; a fencing delay (`pcmk_delay_base`, `priority-fencing-delay`) breaks the tie.

## When not to use them

- Active/passive suffices: use DRBD plus xfs or ext4.
- The application has its own replication: use it.
- Replication is not backup: deletes and corruption are copied too.

## Worked example: the double primary

Both nodes were promoted by hand with a normal file system and no fencing. After the link returned, DRBD reported split brain; one side's data had to be discarded. Fencing plus one promoted instance would have blocked it.
