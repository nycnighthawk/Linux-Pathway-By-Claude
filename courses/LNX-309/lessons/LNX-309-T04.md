## How it works

The primary writes every change to the write-ahead log (WAL). A standby connects, receives the WAL stream and replays it. A hot standby answers read-only queries. Promotion ends recovery and starts a new timeline.

| Mode | Commit returns when | Data loss on failover | Cost |
|---|---|---|---|
| asynchronous | the primary has written locally | the last commits may be lost | none |
| synchronous (`synchronous_standby_names`) | a named standby has the WAL (level set by `synchronous_commit`) | none for acknowledged commits | latency; a stuck standby can block commits |

Physical replication copies the whole cluster byte for byte (same major version). Logical replication copies selected tables and can cross versions.

## Build a standby

```bash
# primary: postgresql.conf   wal_level=replica  max_wal_senders=5
# primary: CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD '...';
# primary: pg_hba.conf       host replication replicator 192.168.20.0/24 scram-sha-256
pg_basebackup -h primary -U replicator -D /var/lib/pgsql/data -X stream -R -P   # on the standby
systemctl start postgresql
```

`-R` writes `primary_conninfo` and `standby.signal` (PostgreSQL 12 and later).

## Verify

```sql
-- primary
SELECT client_addr, state, sync_state, replay_lag FROM pg_stat_replication;
-- standby
SELECT pg_is_in_recovery();
```

Alert on state other than `streaming`, on lag above the recovery point, on archive failures and on slots that retain WAL for a standby that is gone.

## Failover

1. Decide that the primary is really gone (quorum or fencing; a ping is not enough).
2. Promote: `pg_ctl promote` or `SELECT pg_promote();`.
3. Move clients: virtual IP, proxy that checks the role, or client library with several hosts.
4. Re-point or rebuild other standbys.
5. Never restart the old primary as a primary: rebuild it with `pg_basebackup` or rewind it with `pg_rewind`.

Automation: Pacemaker with a PostgreSQL agent, Patroni, repmgr, pg_auto_failover.

## Backups still matter

A dropped table is replicated at once. Use continuous archiving (base backup plus archived WAL) for point-in-time recovery, and test restores.

## Worked example: the returning primary

An automatic script promoted the standby; after repair the old primary booted as a primary and a batch job wrote to it for twenty minutes. The cure: no automatic start of a failed primary, fence it, route clients through a role-checking proxy.
