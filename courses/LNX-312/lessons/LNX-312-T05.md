# eBPF datapath, kube-proxy replacement, Hubble

This lesson follows the topic synthesis `synth/LNX-312/LNX-312-T05.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Explain where eBPF programs attach for Service handling (socket, traffic control, XDP) and why lookups stay constant-time.
- Write the configuration that replaces kube-proxy and choose between SNAT and DSR, random and Maglev.
- Use Hubble to answer "who was denied, and why" and know what L7 visibility costs.

## How the replacement works

| Hook | Handles | Why it matters |
|---|---|---|
| cgroup socket (connect, sendmsg) | traffic from Pods and host processes inside the cluster | the destination is rewritten once, so no per-packet NAT or reverse NAT |
| traffic control on the external device | NodePort, external IP and LoadBalancer traffic from outside | rewrite plus forwarding without a trip through netfilter |
| XDP on the external device | the same traffic, earlier | drops or forwards before a socket buffer exists |

Services and EndpointSlices become entries in hash maps maintained by the agent. The agent cannot use a Service address to find the API server (no kube-proxy exists yet), so its configuration carries the real API address and port.

## Modes and trade-offs

- **SNAT** keeps replies flowing back through the entry node: simple, compatible.
- **DSR** lets the backend reply directly: fewer hops for big responses, but needs metadata in the packet (MTU and cloud-network implications).
- **Maglev** hashing keeps most flows on their backend when the backend set changes, which suits several nodes balancing one external address.
- **Native routing plus BPF host routing** is the fastest path and has the most prerequisites (recent kernel, routable Pod network).

## Hubble

Each agent records flow events with identities, verdict and (optionally) L7 fields. The relay merges node streams; the CLI filters them; the UI draws a service map; metrics go to Prometheus. L7 visibility starts a proxy for the traffic it covers, so enable it per policy, not cluster-wide.

## Worked example: half-migrated cluster

Symptom: Service works from some Pods but not others. Cause: kube-proxy rules remain on some nodes and capture traffic first. Fix: remove the DaemonSet, flush the leftover rules or reboot the node, confirm with the agent's service list that the datapath owns the table.
