## The problem in one picture

Pods come and go, and their IP addresses change with them. A client wants one stable address. A **Service** supplies
that address, a *virtual IP*: no interface owns it and no process listens on it. Instead, every node carries a copy of
the same translation table, and the kernel rewrites the destination of each packet aimed at the virtual IP into the IP
of a healthy Pod before the packet is routed.

Something has to keep those tables current as Pods start, stop and fail their readiness checks. That job belongs to
**kube-proxy**, one instance per node. It watches the cluster's records of Services and their endpoints, and it
programs the node's packet filter to match. kube-proxy does not carry the traffic itself, which is why a restart of
the agent does not break existing connections.

## Three ways to program the node

| Mode | Where the Service table lives | Cost of a lookup | Cost of an update |
|---|---|---|---|
| iptables | Long chains of rules, walked in order | Grows with the number of Services | Historically rewrites the whole table |
| IPVS | A hash table inside the IP Virtual Server balancer | Constant | Incremental |
| nftables | Maps and sets inside one table | Constant | Atomic and incremental |

Two ideas explain the table. The first is that **the data structure matters more than the translation**: all three modes
end in a destination rewrite, but only the last two avoid scanning a list for every new connection. The second is that
**conntrack remembers the choice**. The backend is picked for the first packet of a connection only, and the kernel's
connection tracking applies the same rewrite, in reverse, to the replies and to every later packet.

Some network plugins go further and replace kube-proxy with their own eBPF programs. The node-local idea stays the same:
a table of Services, enforced early.

## Service types are layers

The types are not alternatives; each one wraps the previous.

1. **ClusterIP** is the virtual IP, reachable inside the cluster. Every other type builds on it.
2. **NodePort** also opens the same backends on one port, in a high range, on every node.
3. **LoadBalancer** asks a cloud controller, or an add-on such as MetalLB, for an external balancer that sends traffic to the
   node ports or straight to the Pods.
4. **ExternalName** is only a DNS alias. Nothing is proxied.
5. A **headless** Service has no virtual IP; DNS answers with the Pod addresses and clients choose for themselves.

> When a Service seems to misbehave, find out first which layer you are looking at: the DNS answer, the virtual IP, the
> node port or the external balancer. The fault is almost always in exactly one of them.

## Anatomy of the nftables version

The lab models one Service with three pieces. Read them before you start; the lab asks you to write each one.

- A **verdict map** keyed by *(destination address, protocol, port)*. A hit returns a verdict such as `goto svc-web`.
  One lookup replaces a walk down a list of rules, however many Services exist.
- A **per-Service chain** that translates the destination. A `numgen random mod 2` expression draws 0 or 1, and a second
  map turns that number into a Pod address and port. A third Pod means `mod 3` and one more map entry.
- **Two base chains** that call the map: `prerouting` for packets that arrive from outside the node, and `output` for
  packets the node itself creates. Forget the second one and `curl` on the node cannot reach its own Services.

```bash
# What you will see when it works (on a node, as root)
nft list table ip kubeproxy_lab
```

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| Works from Pods, not from the node | The `output` hook is missing | Does the table have a chain on the output hook? |
| Client source IP lost | Traffic was source-translated for a node without a local backend | The Service's external traffic policy |
| Intermittent timeouts after a Pod moves | A stale conntrack entry for UDP | Conntrack entries for that destination |
| Rules from two tools fighting | A host firewall and kube-proxy share hooks | Priorities in `nft list ruleset` |
