# MTU, encapsulation overhead, throughput

This lesson follows the topic synthesis `synth/LNX-312/LNX-312-T12.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Compute the Pod MTU for any stack of encapsulations.
- Find a path MTU black hole with don't-fragment pings.
- Plan a four-run throughput measurement and attribute the loss to a layer.

## The arithmetic

Pod MTU = underlay MTU minus the sum of the overhead of every encapsulation, in order.

| Layer | Overhead (IPv4 outer) |
|---|---|
| IP-in-IP | 20 |
| VXLAN | 50 |
| Geneve | 50 plus options |
| WireGuard | 60 (80 over IPv6) |

1500 underlay: IP-in-IP 1480, VXLAN 1450, WireGuard 1440, VXLAN carried inside WireGuard over IPv4 1500 - 110 = 1390. A 9000 underlay needs every device in the path to pass jumbo frames.

## Finding a black hole

```bash
ping -M do -s 1422 10.1.2.3     # payload + 28 = packet size
tracepath 10.1.2.3              # discovered MTU per hop if ICMP works
```

Step the payload down until it passes. Compare Pod to node, node to node and Pod to Pod. Large packets vanishing with no ICMP means a silent drop: fix the MTU, or clamp the MSS (TCP only).

## Measuring

Four runs with a throughput tester: node to node (ceiling), Pod to Pod same node, Pod to Pod across nodes, Pod to Service. Record CPU on both ends. A single saturated core means a single-thread limit, not a link limit. Check offloads with `ethtool -k`.

## Worked example: image pulls hang

Small requests work, large layers stall. A don't-fragment ping passes at 1422 and fails at 1423, so the path limit is 1450, while the Pod interface is 1500. Fix the Pod MTU and restart the Pods.

## Self-check

1. Why do small packets pass and large ones fail?
2. What does MSS clamping fix and not fix?
3. What does an IPv6 router do with a too-big packet?
4. Why does changing MTU need a Pod restart?
5. What does a saturated single core tell you?
