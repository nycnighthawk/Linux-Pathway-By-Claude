# CoreDNS and service discovery

This lesson follows the topic synthesis `synth/LNX-312/LNX-312-T08.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Say which DNS records the cluster publishes for Services, headless Services and StatefulSet Pods.
- Count the queries a Pod sends for a name, given its search list and `ndots`.
- Read and extend a Corefile, and run the first-ten-minutes diagnosis.

## Names and records

| Object | Record |
|---|---|
| Service | A/AAAA at `svc.ns.svc.cluster.local` to the ClusterIP |
| Headless Service | A/AAAA with the ready Pod addresses |
| Named port | SRV |
| StatefulSet Pod | stable name under its headless Service |
| ExternalName Service | CNAME to the outside host |

## The Pod resolver

`ClusterFirst` (the default) points the Pod at the cluster DNS with the search list `ns.svc.cluster.local svc.cluster.local cluster.local` and `ndots:5`. A name with fewer dots than `ndots` is tried with each suffix first, then as written. `Default` means the node's resolver config, not the cluster default. `None` plus `dnsConfig` gives exact control.

## The Corefile

Typical plugins: `errors`, `health`, `ready`, `kubernetes` (cluster domain, `pods insecure`, `fallthrough`), `prometheus`, `forward . /etc/resolv.conf`, `cache`, `loop`, `reload`. Extra domains get their own server block with a `forward` to the right resolvers. Production adds a node-local cache and a disruption budget for the CoreDNS Pods.

## Worked example: slow external call

An external name with two dots costs four lookups: three failed search-suffix tries and one success. A trailing dot, `ndots:2` or `autopath` removes the waste. Check with a CoreDNS `log` plugin enabled temporarily.
