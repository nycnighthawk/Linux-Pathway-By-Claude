# MetalLB and BGP with FRR

This lesson follows the topic synthesis `synth/LNX-312/LNX-312-T10.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Choose layer-2 or BGP mode for a site and explain the failover of each.
- Write the MetalLB resources for a pool, an advertisement and a peer.
- Write the matching FRR router configuration, including multipath and prefix filters.

## Two parts of one problem

A LoadBalancer Service needs (1) an address from a pool the operator owns, written to Service status by the controller, and (2) delivery of traffic for that address to a node that can serve it. MetalLB's speaker does (2) either by answering ARP/NDP (layer 2) or by announcing the address over BGP.

| | Layer 2 | BGP |
|---|---|---|
| Needs | one shared segment | a router that peers |
| Load spread | none; one node owns an address | ECMP across nodes |
| Failover | seconds, client ARP caches | sub-second with BFD, else hold time |
| Gotcha | IPVS kube-proxy needs `strictARP` | router path limits, hashing, filters |

## Resources

`IPAddressPool` (addresses, auto-assign), `L2Advertisement` or `BGPAdvertisement` (which pools, how), `BGPPeer` (router address, ASNs, BFD profile). `externalTrafficPolicy: Local` keeps the client address and makes only nodes with endpoints announce.

## FRR side

A `router bgp` block with the local AS, a peer group with a listen range for the node subnet and `remote-as` of the nodes, `maximum-paths` for ECMP, and an inbound prefix list that accepts only the pool range.

## Worked example: nothing is announced

Service has an address, clients time out. The Service uses `Local`, all endpoints are on a node excluded by the advertisement's node selector. Fix the selector or change the policy.
