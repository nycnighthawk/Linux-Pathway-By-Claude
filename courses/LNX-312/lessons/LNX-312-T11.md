# Cilium ClusterMesh across two kind clusters

This lesson follows the topic synthesis `synth/LNX-312/LNX-312-T11.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- List the prerequisites of a ClusterMesh and check them before installing.
- Mark a Service global, choose an affinity and predict where traffic goes.
- Write cluster-scoped policy so that identical labels in another cluster are not trusted.

## How it works

Each cluster has a unique name and numeric ID. A mesh API server in each cluster exposes that cluster's nodes, endpoints, identities and global Services; agents in the other clusters read it over mutual TLS and program their own datapath. Remote Pods are then reachable directly by address and carry an identity that includes the cluster.

## Prerequisites

1. Unique cluster names and IDs.
2. Non-overlapping Pod CIDRs (Service CIDRs may overlap).
3. Node IP reachability between all nodes, with tunnel or routing ports open.
4. The same routing mode and encapsulation everywhere.
5. A shared CA for mesh certificates.

## Global Services

Annotate the same Service (same name and namespace) in each cluster with `service.cilium.io/global: "true"`. `service.cilium.io/affinity` is `local` (prefer local backends, fall back), `remote` or `none`. Production default: `local`.

## Policy

Select peers by cluster label so staging Pods with the same labels as production Pods are still denied. Store the policy in the cluster that hosts the destination workload.

## Worked example: join fails

`cilium clustermesh status` shows a TLS error for cluster b. The two clusters were installed with different CAs. Reinstall b with a's CA secret, then reconnect.
