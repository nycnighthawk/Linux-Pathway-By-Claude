# Pod Security Admission, Kyverno and Gatekeeper

This lesson follows the topic synthesis `synth/LNX-314/LNX-314-T04.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Place admission in the request path and say what it can and cannot see.
- Apply the three Pod Security levels with enforce, audit and warn, and roll them out without breaking tenants.
- Choose between Pod Security Admission, ValidatingAdmissionPolicy, Kyverno and Gatekeeper for a given rule.

## Where admission sits

authenticate → authorise → mutating admission → schema validation → validating admission → store. Admission sees writes only. It does not see reads, static Pods created by the kubelet, or objects that existed before the policy was installed.

## Pod Security Admission

Built in and on by default. Three cumulative levels: **privileged** (no limits), **baseline** (blocks known escalations: host namespaces, privileged containers, most capabilities, hostPath, unsafe sysctls) and **restricted** (non-root, dropped capabilities, seccomp set, no privilege escalation, a short list of volume types).

A namespace is labelled per mode:

```yaml
metadata:
  labels:
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/enforce-version: v1.30
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/audit: restricted
```

Enforcement happens when the Pod is created, so a Deployment can exist while its Pods are refused. Use warn and audit first, fix the findings, then raise enforce. Pin the version so a Kubernetes upgrade does not tighten a level underneath you. Restrict who can edit namespace labels, or tenants can lift their own level.

## Choosing a tool

| Need | Tool |
|---|---|
| Pod baseline for every cluster | Pod Security Admission |
| A simple validation (prefix, label, limit) with no extra component | ValidatingAdmissionPolicy (CEL) |
| Mutation, generation, image verification, reports, exceptions | Kyverno |
| A rigorous policy library, cross-object rules, Rego | Gatekeeper |

Webhook engines sit in the request path. Give them a short timeout, replicas, exclude their own namespace and kube-system, and choose fail-open or fail-closed per rule on purpose.

## Worked example: the deadlock

A fail-closed webhook with a match on all Pods runs in the cluster it guards. A node upgrade evicts it; no Pod can be created, including the webhook's own. Recovery needs direct access to delete the webhook configuration. Prevent it with namespace exclusions, probes and a PodDisruptionBudget.
