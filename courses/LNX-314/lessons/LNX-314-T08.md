# Sandboxed runtimes: gVisor, Kata and RuntimeClass

This lesson follows the topic synthesis `synth/LNX-314/LNX-314-T08.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Explain when a shared kernel is not enough and what each sandbox design puts in its place.
- Write a RuntimeClass with handler, overhead and scheduling, and select it from a Pod.
- Enforce its use with policy, and account for the overhead.

## Two designs

| | gVisor | Kata Containers (and Firecracker-based) |
|---|---|---|
| Boundary | a user-space kernel (the Sentry) that implements system calls and reaches the host through a narrow filtered interface | a lightweight VM with its own guest kernel; the hypervisor is the boundary |
| Compatibility | most Linux behaviour, with gaps (some ioctls, /proc and /sys entries, eBPF) | a real Linux kernel in the guest, unmodified binaries |
| Cost | syscall and file-heavy work slower; small memory overhead; no virtualization hardware needed | start-up time and memory per Pod; needs virtualization on the node |
| Node tools | see the sandbox, not the guest processes | see the hypervisor process |

Neither helps against a leaked credential or an application bug.

## RuntimeClass

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata: {name: gvisor}
handler: runsc                 # must exist in the node's CRI runtime configuration
overhead:
  podFixed: {cpu: 250m, memory: 120Mi}
scheduling:
  nodeSelector: {sandbox: gvisor}
  tolerations: [{key: sandbox, operator: Equal, value: gvisor, effect: NoSchedule}]
```

A Pod sets `spec.runtimeClassName: gvisor`. The scheduler counts requests plus overhead (a 500m/256Mi Pod is placed as 750m/376Mi). A class whose handler is not configured on the node makes the Pod fail to start.

## Enforce it

The Pod chooses the class; nothing forces it. Use an admission policy (a CEL rule that requires `runtimeClassName` in the namespace) or a mutating policy that injects it. Pod Security levels do not describe sandboxing.

## Worked example: the half-adopted class

A team published a class named `secure` and asked developers to use it. Three months later half the Deployments lacked the field because they were copied from old manifests. An admission policy that denies Pods without an allowed class would have caught it on day one.

## Self-check

1. Which design needs virtualization hardware on the node?
2. What does `overhead.podFixed` change for the scheduler and for quota?
3. What happens if the handler is missing on a node?
4. Why does a Pod without `runtimeClassName` run unsandboxed without any warning?
5. Which risks does sandboxing not address?
