# Production threat detection

This lesson follows the topic synthesis `synth/LNX-314/LNX-314-T10.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Turn the course's sensors into a small, tested detection programme driven by scenarios.
- Run a containment ladder that keeps evidence, and know what to capture first.
- Measure whether detection and response are improving.

## Start from a threat model

List the assets (customer data, CI credentials, the cloud account, the cluster) and the realistic adversaries (an exploited public service, a leaked token, a malicious image, an insider). Rank the paths. The result is a list of fewer than twenty scenarios. Detect five well before collecting hundreds of rules.

## A starter scenario set

| Scenario | Source |
|---|---|
| shell or downloaded binary run in a container | node sensor (Falco) |
| connection to a mining pool or bad address | flow logs, node sensor |
| privileged, hostPath or host-network Pod outside the platform namespace | audit log |
| new `cluster-admin` binding or RBAC change outside the pipeline | audit log |
| service account used from an address outside the cluster | audit log with source IP |
| a Pod reaching the cloud metadata address | flow logs |
| exec into a production Pod by someone not on call | audit log |

Provider services (GuardDuty, Security Command Center, Defender for Containers) add a base layer; they do not know your business rules.

## The containment ladder

1. Label the Pod so a pre-installed deny-all policy isolates it (the policy exists beforehand).
2. Change its labels so the Service and the controller stop treating it as theirs.
3. Revoke or rotate the credentials it could use: service account, cloud role, mounted Secrets.
4. Cordon, and if the node is suspect drain and isolate it.
5. Only after evidence capture, delete the Pod. The controller will recreate it from the same image.

## Evidence, in order of volatility

Pod spec and events; node and container logs; the audit excerpt; process list and connections from an ephemeral debug container; the writable layer; a memory image or kubelet checkpoint if available; a node volume snapshot if the node is suspect. Write to a store the workload cannot reach, with hashes and a note of who collected what.

## Recover and measure

Rebuild the image from the verified pipeline, recreate nodes instead of repairing them, remove persistence (RBAC objects, CronJobs, DaemonSets, webhooks, static Pod manifests), close the entry point first. Track coverage of prioritised techniques, time to detect and contain in drills, false-positive rate per rule, and age of open findings. Rehearse with emulation tools and quarterly game days.

## Worked example: the deleted Pod

An on-call engineer deleted the Pod at once; the controller recreated it from the vulnerable image; the attacker's file on a mounted volume survived and the initial access evidence was gone. A prepared quarantine policy and a capture runbook would have kept both.

## Self-check

1. Why is deleting the Pod a poor first step?
2. Which evidence is most volatile?
3. Why is the quarantine policy installed before the incident?
4. What does a cloud detection service not know about your cluster?
5. Which three measures show whether the programme is improving?
