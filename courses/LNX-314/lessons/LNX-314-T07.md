# Falco and audit logs

This lesson follows the topic synthesis `synth/LNX-314/LNX-314-T07.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Write an audit policy that records the right requests at the right level and keeps Secret contents out of the log.
- Name the API events that deserve an alert and detect them in an audit stream.
- Read and write a Falco rule with macros, an exception and a useful output, and tune it so the alert stream stays readable.

## Two vantage points

| Sensor | Sees | Misses |
|---|---|---|
| API audit log | every request: who, what, on which object, with what result | what happens inside a container after an exec |
| Falco (kernel events) | processes, files, connections, system calls with Pod context | a stolen token used from outside against the API |

An attack usually shows in one of them only. Run both.

## Audit policy

Each request passes the stages RequestReceived, ResponseStarted (long requests), ResponseComplete and Panic. The policy is an ordered list; the **first matching rule** sets the level: `None`, `Metadata`, `Request`, `RequestResponse`.

```yaml
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages: [RequestReceived]
rules:
  - level: None
    users: [system:kube-proxy]
    resources: [{group: "", resources: [endpoints, services]}]
  - level: Metadata
    resources: [{group: "", resources: [secrets, configmaps, tokenreviews]}]
  - level: RequestResponse
    resources: [{group: "", resources: [pods/exec, pods/attach]}]
  - level: Metadata
```

Ship the log off the node (file agent or webhook backend) so an attacker who owns the node cannot erase it.

## Events worth a rule

exec, attach or port-forward by someone who is not an operator; a binding to `cluster-admin`; a cluster-wide list of Secrets; an allowed anonymous request; a privileged or host-mounting Pod; a change to Pod Security labels; a burst of 403s from one identity.

## Falco in one rule

```yaml
- macro: allowed_shell_images
  condition: (container.image.repository in (registry.example/debug-tools))
- rule: Shell spawned in a container
  condition: spawned_process and container and proc.name in (sh, bash) and not allowed_shell_images
  output: "Shell in container (container=%container.id pod=%k8s.pod.name cmd=%proc.cmdline)"
  priority: WARNING
  tags: [container, mitre_execution]
```

A kernel driver (modern eBPF by default in current releases) feeds events to user space, where they are enriched with container and Pod metadata. Falcosidekick routes alerts; the `k8saudit` plugin lets the same engine read audit events.

## Tuning is the work

Start with a few high-confidence rules, add exceptions as reviewed code, and track alerts per rule and the share acted on. Watch the drop counter: a full ring buffer loses events silently.

## Worked example: the muted channel

All default rules were enabled on day one; 400 alerts in a week, mostly a deploy tool writing under `/etc`. The channel was muted, and a real shell a month later was never read. Fewer rules, exceptions in pull requests and a weekly signal review prevent it.

## Self-check

1. Which sensor sees a stolen token used from outside the cluster?
2. Why log Secrets at Metadata and not RequestResponse?
3. What does "first matching rule wins" mean for the order of audit rules?
4. How can an attacker evade a rule that matches the name `xmrig`?
5. What must you monitor to know Falco is not losing events?
