# AppArmor, seccomp and the kernel attack surface

This lesson follows the topic synthesis `synth/LNX-314/LNX-314-T03.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Explain what a container does not isolate: the kernel interface that every container shares.
- Select seccomp and AppArmor profiles for a Pod, and know which of them the node must already hold.
- Build a deny-list profile from observed behaviour and test that it blocks what you meant it to block and nothing else.

## What the kernel still exposes

Namespaces, cgroups and reduced capabilities do not limit which system calls a process makes. A kernel bug reachable from a container is a breakout. Two Linux mechanisms narrow the reachable surface:

| Mechanism | Decides on | Strength | Weakness |
|---|---|---|---|
| seccomp filter | system call number and raw arguments | cheap, inherited, cannot be undone | cannot see paths or pointed-to data |
| AppArmor (or SELinux) | files, capabilities, network families, mounts | understands objects | paths and labels need upkeep; node-specific |

Add `no_new_privs` (`allowPrivilegeEscalation: false`), dropped capabilities, a read-only root filesystem and a non-root user.

## In Kubernetes

```yaml
securityContext:
  seccompProfile: {type: RuntimeDefault}      # or Localhost with localhostProfile, or Unconfined
  appArmorProfile: {type: RuntimeDefault}     # field form; older releases used an annotation
  allowPrivilegeEscalation: false
  capabilities: {drop: [ALL]}
```

A `Localhost` profile must already be on the node (seccomp JSON under the kubelet directory, AppArmor profile loaded into the kernel). Ship it with a DaemonSet, the Security Profiles Operator or the node image. The kubelet can also make RuntimeDefault the default for Pods that say nothing.

## Writing a profile

1. Record what the application does under realistic tests (strace, an eBPF recorder, the Security Profiles Operator).
2. Start from the runtime default and deny the calls you know are dangerous for this workload, or build an allow-list from the recording.
3. Test normal operation, error paths, certificate renewal and log rotation, which a short recording misses.
4. Enable audit logging of seccomp actions so a denial is visible instead of looking like an unrelated error.

## Worked example: the profile that was right and wrong

An AppArmor profile that denies writes to `/etc` passed every test and took down a service during certificate rotation a month later. Profiles are only as complete as the behaviour they were built from. Put rotation, reload and failure handling in the test plan.

4. Which kernel features remain reachable even with a tight seccomp profile?
5. Why is `Unconfined` one line away, and what stops it?
