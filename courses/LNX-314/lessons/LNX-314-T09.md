# mTLS and segmentation

This lesson follows the topic synthesis `synth/LNX-314/LNX-314-T09.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Separate the two questions segmentation and mTLS answer, and use both.
- Build a default-deny baseline with NetworkPolicy and state what it does not do.
- Explain how workload identity is issued, and write an identity-based authorisation rule in a mesh.

## Why the default is dangerous

A Pod can reach any Pod, Service and node port in the cluster. One compromised container starts with that reach: scanning, default passwords, unauthenticated internal APIs. The attacker's sideways movement is cheap on a flat network.

| Control | Question | Layer |
|---|---|---|
| NetworkPolicy | may this workload open a connection to that one at all? | packets, by labels and namespaces |
| mTLS with identity | who is on the other end, and can anyone read or change the traffic? | connections, by certificate identity |

## Segmentation baseline

```yaml
kind: NetworkPolicy
metadata: {name: default-deny, namespace: shop}
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
```

An empty selector picks every Pod; no rules means nothing is allowed. Then add allows per tier (ingress controller to web, web to api, api to database) and **allow DNS egress** or nothing resolves. Policies are additive, with no deny and no priority; the plugin must implement the API; no L7 rules and no identity beyond labels. Use flow logs to write rules from observed traffic.

## Identity and mTLS

In a mesh, each workload's proxy (or node agent) gets a short-lived certificate whose name is a SPIFFE ID such as `spiffe://cluster.local/ns/shop/sa/api`, issued after the service account token is verified. Rotation is automatic. Istio's `PeerAuthentication` sets `PERMISSIVE` (accept both) or `STRICT` (mTLS only); `AuthorizationPolicy` allows or denies by source principal, namespace, method, path and port. Cilium can require mutual authentication per flow and encrypt node-to-node with WireGuard or IPsec (which authenticates nodes, not workloads).

## Things that quietly defeat it

- Several workloads sharing the `default` service account: the identity is meaningless.
- An allow rule that selects every Pod in every namespace.
- Plain-text paths: permissive mode, excluded ports, host networking.
- Whoever can create Pods in a namespace can run as any service account there.
- Expired or unmonitored certificates and CA roots.

## Worked example: Friday's default deny

Default-deny egress was applied to a namespace. DNS and the services the Pods call were not allowed, a rolling update stalled and the fix was a rollback. Put DNS and platform services into the standard namespace template and test in staging first.
