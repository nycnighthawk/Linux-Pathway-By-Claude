# Secrets encryption at rest

This lesson follows the topic synthesis `synth/LNX-314/LNX-314-T05.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Say what encryption at rest protects and what it does not.
- Read an `EncryptionConfiguration` and predict which provider is used for each write and each read.
- Rotate a key across several API servers without losing data, and check that the stored bytes are really encrypted.

## The problem in one paragraph

By default a Secret is stored in etcd as base64, which is only an encoding. Anyone with the data directory, a snapshot or a backup reads every Secret. Encryption at rest makes those copies useless without the key. The API server still decrypts on read, so RBAC remains the control for API access.

## The configuration

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources: [secrets]
    providers:
      - kms: {apiVersion: v2, name: cloud-kms, endpoint: unix:///var/run/kms.sock}
      - secretbox: {keys: [{name: key1, secret: <base64 of 32 bytes>}]}
      - identity: {}
```

- **Writes** use the first provider only.
- **Reads** pick the provider from the stored prefix `k8s:enc:<provider>:v1:<key name>:`; values without a prefix are read as plaintext.
- So identity first means new data is plaintext, which looks fine and is wrong.

| Provider | Key lives | Note |
|---|---|---|
| identity | none | no encryption; used to read old data or turn encryption off |
| aescbc, secretbox, aesgcm | in the file on the control plane host | protects copies of the data; weak if the host is compromised; AES-GCM needs frequent rotation because of nonce limits |
| kms (v2) | in an external KMS | envelope encryption: a data key wraps the object, the KMS wraps the data key |

## Rotating keys

With several API servers:

1. Add the new key **last** on every server, so every server can read it.
2. Move it **first**, so writes use it.
3. Rewrite every Secret (storage version migration), so no value uses the old key.
4. Remove the old key.

Promote on one server before the others can read it and a peer's value cannot be decrypted. Key loss is data loss: keep keys with the same retention as the etcd backups they open.

## Verify

Read the value from etcd with `etcdctl get` and check the prefix and the unreadable bytes. A working API says nothing, because it decrypts for you.

## Worked example: the rotation that stalled

A three-node control plane had keys swapped one node at a time. The first node wrote with key2 that the others did not know yet; controllers on the others met decryption errors and retried in a loop. Adding the key everywhere first would have avoided the window.

## Self-check

1. Which provider handles a write when the list is `[identity, aescbc]`?
2. What does the prefix of a stored value tell the API server?
3. Why must the new key be added last before it is promoted?
4. What does a KMS v2 plug-in hold that the API server host does not?
5. Why does encryption at rest not stop a user with `get secrets`?
