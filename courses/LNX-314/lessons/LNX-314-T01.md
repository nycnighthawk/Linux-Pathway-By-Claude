# Cluster setup: benchmark audits and metadata protection

This lesson follows the topic synthesis `synth/LNX-314/LNX-314-T01.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Explain how a configuration benchmark is organised and what an automated checker such as kube-bench actually inspects.
- Triage a failing report into fixes, platform-managed items and documented exceptions.
- Set the kubelet options that matter most and cut pods off from the cloud metadata address.

## Two problems, one lesson

Cluster components are privileged daemons whose safety depends on flags and files. The first problem is knowing that those settings are right and staying sure as the cluster changes. The second problem sits below Kubernetes: the machine hands every local process a credentials service on a link-local address, and a pod is a local process.

## The benchmark and the checker

A benchmark is a numbered list of controls. Each has a rationale, an audit command and a remediation, and is labelled automated or manual, scored or not. The CIS Kubernetes Benchmark groups them by component: control plane files, API server, controller manager and scheduler, etcd, worker node and kubelet, then a policy section on RBAC, service accounts, network policy and secrets.

kube-bench reads those controls from YAML, finds the running binaries, runs the audit commands and prints pass, fail, warn or info per item. Warn usually means a manual item or an undecidable check. On managed services only the worker section is yours to change, so pick the right target before you trust the summary.

```bash
kube-bench run --targets node                 # worker node checks
kube-bench run --targets master,etcd,policies # self-managed control plane
kube-bench run --json > report.json           # feed a pipeline
```

## The settings with the best return

| Component | Setting |
|---|---|
| kubelet | anonymous authentication off, webhook authentication with a client CA, authorization mode Webhook, read-only port 0, certificate rotation on |
| API server | anonymous access off or minimal, RBAC and Node authorization, audit log on, TLS to etcd and kubelets |
| etcd | client certificate authentication, not reachable from pod networks, data directory owned by its user |
| files | static Pod manifests and kubeconfig files owned by root, not writable by others |

## Metadata protection in three layers

1. Provider: require the session-based metadata protocol and a hop limit of one (AWS), or use workload identity so pods see a restricted metadata server (GCP, Azure).
2. Network: a default egress rule for workload namespaces that drops the link-local metadata address while allowing DNS and real dependencies.
3. Identity: give each service account its own cloud identity so nothing needs the node's credentials.

Test every layer from inside a pod, and also check that legitimate node-level agents still work.

## Worked example: a report with a surprise

A team scans the worker target only and reports a clean result. Their etcd runs on separate machines and listens on the node network without client authentication. Nothing in the scan was false; the scan simply never looked there. The fix is to list every component first, map each to a target, and keep the exception list next to the report.
