# RBAC minimisation and API access

This lesson follows the topic synthesis `synth/LNX-314/LNX-314-T02.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Read a Role or ClusterRole and say exactly what it lets a subject do.
- Recognise the permissions that are equivalent to cluster-admin and keep them to a few subjects.
- Build a narrow role from a job description, test it with impersonation, and stop Pods carrying API credentials they do not need.

## The model in one screen

RBAC has no deny. A subject can do the union of everything its bindings grant. A rule names API groups, resources (with optional subresources such as `pods/exec`), optional resource names and verbs. A RoleBinding attaches a role inside one namespace, even when the role is a ClusterRole. A ClusterRoleBinding attaches cluster-wide.

## The dangerous grants

| Grant | Why it is strong |
|---|---|
| get, list or watch on Secrets | list and watch return the content as well |
| create on Pods or workload controllers | the Pod can mount any Secret and service account token in its namespace |
| create on serviceaccounts/token | issues the identity of that account |
| impersonate, bind, escalate | become someone else or grant more than you hold |
| write on nodes or webhook configurations | subverts scheduling or enforcement |

## Minimising, step by step

1. List the API calls the job really makes (use a dry run, the audit log, or the tool's documentation).
2. Write one rule per resource with the exact verbs; add `resourceNames` where the object is fixed. Names do not constrain create, list or watch.
3. Bind with a RoleBinding in the narrowest namespace.
4. Test with `kubectl auth can-i --as=system:serviceaccount:shop:deployer patch deployments/web -n shop` for an allowed and a denied call.
5. Remove wildcards. A wildcard also covers resources installed later by operators.

## Credentials in Pods

Set `automountServiceAccountToken: false` on the service account or Pod unless the workload calls the API. Where it does, the kubelet projects a bound token that expires and is tied to the Pod. Do not create long-lived token Secrets unless a system outside the cluster truly requires one.

## Worked example: the monitoring rule

A monitoring chart asks for get, list and watch on every resource "to scrape". That includes Secrets. Replace it with the list of kinds the scraper reads (nodes, pods, services, endpoints plus the metrics non-resource URL).

## Self-check

1. Why does `list` on Secrets reveal their content?
2. A user cannot create a RoleBinding to cluster-admin. How can they still reach cluster-admin power?
3. What does `resourceNames` not restrict?
4. Which command tests a role before you ship it?
5. Why prefer OIDC groups over client certificates for people?
