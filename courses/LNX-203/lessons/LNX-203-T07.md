# Scripts as systemd services and timers

This lesson follows the topic synthesis `synth/LNX-203/LNX-203-T07.md`, which carries the history and the sources.

## What you will be able to do

- Turn a script into a `Type=oneshot` service with a restricted environment.
- Schedule it with a timer that survives downtime and spreads load.
- Test calendar expressions, verify units and read the logs of a run.

## A one-shot service

```ini
# /etc/systemd/system/backup.service
[Unit]
Description=Nightly backup

[Service]
Type=oneshot
User=backup
ExecStart=/usr/local/bin/backup.sh
ProtectSystem=strict
ReadWritePaths=/var/backups
NoNewPrivileges=yes
PrivateTmp=yes
```

`ExecStart` must be an absolute path. `Type=oneshot` makes the unit active until the command exits, so ordering and `systemctl start` wait for it. Sandboxing directives restrict what the script can touch: `ProtectSystem=strict` mounts the file system read-only except `ReadWritePaths=`, `PrivateTmp=yes` gives a private `/tmp`, `NoNewPrivileges=yes` blocks setuid escalation, and `DynamicUser=yes` allocates a transient account. `systemd-analyze security backup.service` scores the exposure. Environment comes from `Environment=` or `EnvironmentFile=`, not from your login shell.

## The timer

```ini
# /etc/systemd/system/backup.timer
[Unit]
Description=Run the nightly backup

[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true
RandomizedDelaySec=15min

[Install]
WantedBy=timers.target
```

A timer activates the service with the same name unless `Unit=` says otherwise. `OnCalendar=` takes calendar expressions (`daily`, `Mon..Fri 08:00`, `*-*-01 00:00`); `OnBootSec=` and `OnUnitActiveSec=` give monotonic timers. `Persistent=true` runs a missed activation after boot, `RandomizedDelaySec=` spreads machines apart and `AccuracySec=` allows coalescing. Enable the timer, not the service: `systemctl enable --now backup.timer`.

## Test and inspect

```bash
systemd-analyze calendar '*-*-* 02:30:00'    # normalised form and next elapse
systemd-analyze verify /etc/systemd/system/backup.service
systemctl daemon-reload                       # after editing unit files
systemctl list-timers --all
systemctl start backup.service                # run it now, by hand
journalctl -u backup.service -b               # output and status of the runs
```

A script run by systemd has no terminal, a minimal `PATH` and a different working directory, so use absolute paths and log to standard output or standard error, which the journal captures. A non-zero exit marks the unit failed (`systemctl status`, `systemctl --failed`); add `OnFailure=` to notify. Compared with cron, you gain dependencies, resource limits, sandboxing and journal logs; cron is still simpler for per-user jobs.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| Timer never fires | not enabled or the expression is wrong | `systemctl list-timers`, `systemd-analyze calendar` |
| Works by hand, fails as a service | different user, `PATH` or sandbox | `journalctl -u`, relax one directive at a time |
| Permission denied writing | `ProtectSystem=strict` without a writable path | add `ReadWritePaths=` |
| Edits have no effect | units not reloaded | `systemctl daemon-reload`, `systemctl cat` |
