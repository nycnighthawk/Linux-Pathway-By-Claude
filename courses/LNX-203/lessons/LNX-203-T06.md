## The branch workflow

Work on a branch cut from the shared line, commit in small steps, then update from upstream and publish.

```bash
git switch -c feature/fix-bug
git add -p && git commit
git fetch origin
git rebase origin/main          # replay your commits on top of the latest main
git push -u origin feature/fix-bug
```

`git fetch` updates the remote-tracking branches and changes nothing else; `git pull` is fetch plus a merge or rebase (`pull.rebase=true` chooses rebase). A merge keeps both lines and adds a merge commit; a rebase rewrites your commits so history is linear. Rebase only commits that nobody else has based work on. After rewriting a pushed branch you must update the remote with `git push --force-with-lease`, which refuses if someone else pushed in the meantime; never force-push a shared branch such as main. `git rebase -i origin/main` lets you reorder, squash (`squash`, `fixup`) and reword commits before review.

## Commit messages

A subject of about 50 characters in the imperative mood, no trailing period, a blank line, then a body that explains why the change is needed and what it affects, wrapped near 72 columns. `git commit -m "subject" -m "body"` writes both paragraphs. Atomic commits (one logical change each, tests included) make review and bisect easier.

## Bisect

Bisect does a binary search through history for the first bad commit.

```bash
git bisect start HEAD v1.0     # bad commit first, then good
git bisect run ./test.sh       # exit 0 good, 1 to 127 except 125 bad, 125 skip
git rev-parse refs/bisect/bad  # the first bad commit
git bisect reset               # go back to where you were
```

Without `run`, test each step yourself and answer with `git bisect good` or `git bisect bad`. Bisect checks out old versions of the tree, so the test script must exist at every commit it visits, or live outside the repository.

## Preparing for review

Review your own diff first (`git diff origin/main...HEAD`), run the tests and linters, and keep the change small and focused. `.gitignore` keeps build output and secrets out; if a secret was committed, rotate it, because rewriting history does not undo the exposure. Signed commits (`git commit -S`) and protected branches with required checks put policy where the server can enforce it.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| Push rejected as non-fast-forward | remote moved or you rewrote history | `git fetch`, rebase, then `--force-with-lease` if the branch is yours |
| Rebase stops with conflicts | overlapping edits | fix the files, `git add`, `git rebase --continue` (or `--abort`) |
| Bisect points at a merge or a nonsense commit | flaky test or skipped commits | make the test deterministic, use exit 125 for untestable commits |
| Lost commits after reset | they are still in the reflog | `git reflog`, then `git switch -c rescue <hash>` |

## Self-check

1. What does `git fetch` change and what does it leave alone?
2. Why is `--force-with-lease` safer than `--force`?
3. Which exit code tells `bisect run` to skip a commit?
4. What belongs in a commit body that the subject cannot hold?
