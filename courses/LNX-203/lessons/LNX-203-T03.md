# bats-core tests

This lesson follows the topic synthesis `synth/LNX-203/LNX-203-T03.md`, which carries the sources.

## What you will be able to do

- Write bats tests for a script, with set-up and clean-up.
- Assert on exit status, output and files with `run`.
- Judge a test suite by whether it fails when the code is wrong.

## Anatomy of a test file

Files end in `.bats`. Each `@test "name" { ... }` is a function run in its own process; it passes if every command in it succeeds (bats runs it with `set -e` semantics), so assertions are ordinary commands.

```bash
setup()    { script="$BATS_TEST_DIRNAME/../rotate.sh"; cd "$BATS_TEST_TMPDIR"; }
teardown() { :; }                     # runs after each test, pass or fail

@test "missing file exits 1" {
  run "$script" nope 3
  [ "$status" -eq 1 ]
  [[ $output == *"no such file"* ]]
}
```

`run cmd` stores the exit status in `$status` and the combined output in `$output` (and the lines in `${lines[@]}`); `run --separate-stderr` adds `$stderr`. `BATS_TEST_TMPDIR` is a fresh directory per test, `BATS_FILE_TMPDIR` is shared by a file, and `setup_file`/`teardown_file` run once per file. `skip "reason"` marks a test skipped.

## Running

`bats test/` runs every file in the directory, `bats -r` recurses, `--tap` prints TAP and `--filter 'regex'` selects tests by name. A non-zero exit means at least one test failed. The helper libraries `bats-support` and `bats-assert` add readable assertions such as `assert_success` and `assert_output`, but plain `[ ]` works with nothing installed.

## Good tests

Test behaviour that callers rely on: exit codes, messages on stderr, files created, idempotence. Give inputs distinct values so a wrong shift or swap shows. A cheap way to check a suite is mutation testing by hand: break the script on purpose (flip an exit code, change a limit) and confirm some test fails. A mutant that survives points at a missing test.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| Test passes with a bug present | assertion on status only, or nothing after `run` | add checks on files and output |
| Test fails only in the suite | shared state between tests | use `BATS_TEST_TMPDIR`, no fixed paths |
| `$output` contains unexpected text | `run` merges stderr into the output | `run --separate-stderr` |
| A failing command in the middle is ignored | it is inside a conditional | assert with `[ ]` or `run` |

## Self-check

1. What do `$status` and `$output` hold after `run`?
2. What is the difference between `setup` and `setup_file`?
3. Why give each fixture file different contents?
4. How would you check that your tests can fail?
