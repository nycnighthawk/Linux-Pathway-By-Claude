# NUMA and cache-effect measurement

This lesson follows the topic synthesis `synth/LNX-320/LNX-320-T13.md`. Cache sizes, latencies and counter names are specific to each CPU; the numbers in the lab are sample data, not a property of Linux.

## What you will be able to do

- Read the topology with `lscpu`, `lstopo` and `numactl --hardware`.
- Read a pointer-chase latency curve and name the cache level behind each step.
- Recognise false sharing and fix it, and confirm it with `perf c2c`.
- Choose and verify a NUMA policy: first touch, `numactl` binding, interleave.

## Predict

A first-level cache hit costs about a nanosecond, a last-level hit tens of cycles, DRAM around 100 ns, and remote-node DRAM more. `lscpu` shows sizes, `numactl --hardware` the node list and a distance matrix (10 is local; larger is relatively farther, not a number of nanoseconds).

## Measure

A pointer chase walks a random ring of addresses over a growing working set and reports ns per step: flat while it fits in L1, a step to L2, a step to L3, a jump to DRAM. Rules for honest results:

- Pin the thread (`taskset -c N`) and note the frequency governor.
- Warm up and first-touch the memory.
- Keep the compiler from deleting the loop.
- Repeat and report the spread; print the topology with the result.

## False sharing

Two threads writing different variables on one 64-byte line make the line bounce between cores. The fix is padding or alignment (`alignas(64)`). `perf c2c record` then `perf c2c report` finds contended lines. Many threads on one counter is true sharing: use per-thread partials.

## Control

| Tool | Effect |
|---|---|
| `numactl --cpunodebind=N --membind=N` | CPUs and memory on one node |
| `numactl --interleave=all` | pages spread over nodes for shared data and bandwidth |
| `taskset` / `sched_setaffinity` | CPU pinning |
| `numastat -p PID`, `/proc/PID/numa_maps` | where the pages really are |
| `kernel.numa_balancing` | automatic page and task migration |

Memory is placed on the node of the CPU that first touches it, so initialise in parallel with the same mapping as the compute.

## Worked example

A parallel sum over a 64 GiB array initialised by the main thread reaches only 60% of the expected bandwidth: all pages sit on node 0. Initialising inside the parallel region puts each chunk on its user's node. `numa_maps` shows the difference. The lab gives you sample measurements and asks for the conclusions and the command.

## What goes wrong

Measuring without pinning. Reading one run as the truth. Pinning CPUs but leaving an interleave policy. Forgetting that hyperthreads share a core's caches.
