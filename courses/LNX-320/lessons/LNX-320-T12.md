# eBPF from user space: libbpf and CO-RE

This lesson follows the topic synthesis `synth/LNX-320/LNX-320-T12.md`. Features such as kfuncs, `bpf_loop` and the privilege split depend on the kernel version; check the kernel BPF documentation and `bpftool feature probe` (to verify).

## What you will be able to do

- Describe the build and load chain: clang, BTF, skeleton, libbpf.
- Write a BPF program that reads kernel structures with CO-RE and sends events through a ring buffer.
- Explain what the verifier requires and how to read its complaints.
- Say which privileges loading needs and what a BPF program can hurt.

## The model

A BPF program is small verified code that the kernel runs at a hook. It talks to user space through maps. The `bpf(2)` call loads programs and maps; libbpf wraps it. Program types include tracepoints, kprobes, fentry/fexit, XDP, TC, cgroup and LSM hooks. Prefer stable tracepoints, then fentry; kprobes break when kernel functions are renamed.

## The build chain

```bash
bpftool btf dump file /sys/kernel/btf/vmlinux format c > vmlinux.h
clang -g -O2 -target bpf -D__TARGET_ARCH_x86 -c prog.bpf.c -o prog.bpf.o
bpftool gen skeleton prog.bpf.o > prog.skel.h
```

`-O2` is needed or the verifier rejects the code; `-g` produces the BTF that CO-RE uses. The user-space program opens, loads and attaches through the skeleton, then polls a ring buffer.

## CO-RE

Kernel structures differ between versions. With BTF, clang records field accesses by name as relocations in `.BTF.ext`, and libbpf rewrites the offsets at load time against `/sys/kernel/btf/vmlinux`. In code:

```c
pid_t ppid = BPF_CORE_READ(task, real_parent, tgid);
if (bpf_core_field_exists(task->__state)) { ... }
```

Mark your own struct copies with `__attribute__((preserve_access_index))` if you do not use `vmlinux.h`. Never dereference a kernel pointer directly; use `BPF_CORE_READ` or `bpf_probe_read_kernel`.

## Ring buffer and maps

`BPF_MAP_TYPE_RINGBUF` is one shared, ordered event buffer: `bpf_ringbuf_reserve`, fill the struct, `bpf_ringbuf_submit`. If reserve returns `NULL` the buffer is full: count the drop in a map. Other maps (hash, array, per-CPU) hold state and counters.

## The verifier and permissions

The verifier requires termination, checked memory access (test map lookups for `NULL`; bound packet and stack accesses), initialised output structures and a complexity limit. Keep functions small and loops bounded. Loading needs `CAP_BPF` plus `CAP_PERFMON` for tracing (or root); unprivileged BPF is usually disabled. License the object `GPL` for the helpers.

## Worked example

A tracepoint on `sched/sched_process_exec` fills `{pid, ppid, comm}` and submits it; user space prints one line per exec. The same object runs on kernels with different `task_struct` layouts because `real_parent->tgid` is relocated at load time. The lab asks you to write the kernel side and the check inspects the compiled object.

## What goes wrong

A map lookup used without a `NULL` check. A program built without `-g`, so no CO-RE. Reading a field that was renamed. Ignoring a full ring buffer. Attaching to a very hot function.
