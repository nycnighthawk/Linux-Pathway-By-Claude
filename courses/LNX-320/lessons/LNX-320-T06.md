## What you will be able to do

- Explain how a futex makes an uncontended lock free of system calls.

## Threads and the rule that matters

Threads share an address space but have their own stack, `errno`, signal mask and thread-local storage. The rule: if two threads access the same location, one of them writes, and nothing orders the accesses, you have a data race and the behaviour is undefined. Ordering comes from mutex lock and unlock, thread creation and join, and release and acquire on atomics. `volatile` gives none of it.

## Mutex and condition variable

```c
pthread_mutex_lock(&m);
while (!ready)                 /* a loop, not an if */
    pthread_cond_wait(&cv, &m);
use(data);
pthread_mutex_unlock(&m);
```

Waits can wake spuriously, and another thread may take the condition first, so the predicate is always re-tested. Change the data under the mutex, then signal.

## What a futex does

The lock word lives in user memory. Lock and unlock are atomic instructions with no system call while nobody waits. A waiter calls `FUTEX_WAIT` with the value it saw; the kernel sleeps it only if the word still has that value, which closes the lost wake-up window. An unlocker calls `FUTEX_WAKE` only if the word says there are waiters. A three-state word works: 0 unlocked, 1 locked, 2 locked with waiters.

## Atomics and memory order

| Order | Use |
|---|---|
| relaxed | counters and statistics |
| release store, acquire load | publishing data through a flag |
| seq_cst | the default when unsure |

Publication: write the data, then store the flag with release; the reader loads the flag with acquire and then reads the data. A compare-and-swap loop builds lock-free structures but meets the ABA problem and the need for safe reclamation.

## Performance

An uncontended lock costs tens of nanoseconds. Contention costs a system call and a context switch. Two counters on one cache line slow each other down (false sharing); align hot data per thread. Per-thread counters merged at the end usually beat any shared atomic.

## Worked example

Eight threads add to one counter. Without synchronisation the total is short. With a mutex it is right and slower. With a relaxed `fetch_add` it is right and faster. With per-thread counters it scales. The lab has you write a futex mutex and prove it correct under four threads.

## What goes wrong

`if` instead of `while` around `pthread_cond_wait`. Locking in different orders. Calling `fork` in a threaded program. Using relaxed atomics for publication. Sleeping on a futex without comparing the value.
