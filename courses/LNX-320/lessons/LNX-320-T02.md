## Descriptors, descriptions and the page cache

`open` gives a descriptor. Behind it is an open file description that holds the offset and flags, and `dup` or `fork` share it. Writes land in the page cache and return at once; the kernel writes them out later. So a successful `write` means "accepted", not "on disk".

A transfer loop repeats until the count is done, retries on `EINTR`, treats a `read` result of 0 as end of file and stops on any other error. `pread` and `pwrite` take an offset and leave the shared offset alone, which is what threads need.

## Making a change durable

| Call | Guarantee |
|---|---|
| `fsync(fd)` | data and the metadata needed to read it reach stable storage |
| `fdatasync(fd)` | the same, but skips metadata not needed to read the data |
| `fsync(dirfd)` | the directory entry (new name, rename) reaches stable storage |
| `O_SYNC` / `O_DSYNC` | every write is durable before it returns; slow |
| `O_DIRECT` | skips the page cache; needs aligned buffers; not a durability promise |

The replace pattern: write a temporary file in the same directory, `fsync` it, `rename` it over the target, then `fsync` the directory. A failing `fsync` must be treated as a failed transaction, because the kernel may report a write-back error only once.

## Locks

All Linux file locks are advisory: they bind only processes that ask.

- `flock` locks the whole file and belongs to the open file description.
- POSIX `F_SETLK` locks byte ranges but belongs to the process, and closing any descriptor of the file drops every lock the process holds on it. Threads do not exclude each other.
- `F_OFD_SETLK` locks ranges and belongs to the open file description. Prefer it in threaded code.

Locks vanish when the owner exits, which is why they beat lock files.

## mmap

`MAP_SHARED` changes reach the file; `MAP_PRIVATE` pages are copy-on-write. `msync` is the `fsync` of a mapping. A fault beyond the end of the file, or on a file that was truncated, raises `SIGBUS`, not an error code. Use `madvise` for access hints. Prefer `pread` when files may change size or when you need clean error handling.

## Worked example

Two processes append log lines. With `O_APPEND`, each `write` goes to the end of the file atomically and lines stay whole. Without it, each process uses its own offset and they overwrite each other. In the lab you write the safe replace function and the check watches the order of `fsync` and `rename`.

## What goes wrong

Ignoring a short write. Skipping the directory `fsync`. Closing a second descriptor and losing a POSIX lock. Mapping a file that another process truncates. Believing `O_DIRECT` means durable.
