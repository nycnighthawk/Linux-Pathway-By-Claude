# ptrace: build a tiny strace

This lesson follows the topic synthesis `synth/LNX-320/LNX-320-T11.md`. `PTRACE_GET_SYSCALL_INFO` needs Linux 5.3 or later, and containers often restrict `ptrace` (to verify on your system).

## What you will be able to do

- Start a traced program and follow its stops with `waitpid`.
- Tell syscall entry from syscall exit and read the number, arguments and result.
- Explain what `PTRACE_O_TRACESYSGOOD`, `PTRACE_O_EXITKILL` and the fork options do.
- State the permission rules and why `ptrace` is a high-value target.

## The model

A tracee is either running or in a ptrace-stop. While it is stopped the tracer can read and write its registers and memory. The tracer resumes it with `PTRACE_CONT`, `PTRACE_SYSCALL` (stop at the next syscall boundary) or `PTRACE_SINGLESTEP`, and learns about the next stop through `waitpid`.

## Starting the tracee

In the child, after `fork`: `ptrace(PTRACE_TRACEME)`, then `execvp`. The kernel stops the child with `SIGTRAP` at `exec`. The parent waits for that stop, then sets options:

```c
ptrace(PTRACE_SETOPTIONS, pid, 0,
       PTRACE_O_TRACESYSGOOD | PTRACE_O_EXITKILL);
```

`TRACESYSGOOD` marks syscall stops as `SIGTRAP | 0x80` so they cannot be mistaken for a real `SIGTRAP`. `EXITKILL` kills the tracee if the tracer dies.

## The syscall loop

```c
for (;;) {
    ptrace(PTRACE_SYSCALL, pid, 0, sig);   /* run to the next boundary */
    waitpid(pid, &st, 0);
    if (WIFEXITED(st) || WIFSIGNALED(st)) break;
    if (WIFSTOPPED(st) && WSTOPSIG(st) == (SIGTRAP | 0x80)) {
        /* entry, then exit, alternating: read the info */
    }
    /* any other stop is a signal: pass it on as 'sig' */
}
```

`PTRACE_GET_SYSCALL_INFO` fills a `struct ptrace_syscall_info` whose `op` is `PTRACE_SYSCALL_INFO_ENTRY` or `..._EXIT`. At entry it gives the number and arguments; at exit it gives the return value and an `is_error` flag. This avoids hand-written register code for each CPU. A negative result in the error range means `-errno`.

## Reading memory and following children

Pointer arguments are addresses in the tracee: use `process_vm_readv` or `PTRACE_PEEKDATA`. With `PTRACE_O_TRACEFORK` and friends the tracer also receives the children; then wait with `waitpid(-1, ..., __WALL)` and keep per-thread state.

## Permissions

You may trace your own children, subject to the Yama `ptrace_scope` setting, or any process with `CAP_SYS_PTRACE`. Only one tracer can attach at a time, so a debugger and `strace` collide. Container profiles may forbid the call.

## Worked example

Tracing `sh -c 'cat file | wc -l'` with only the first PID shows nothing after the `fork`. With the fork options and `waitpid(-1, __WALL)` you see the children and the pipe set-up. In the lab you trace a small helper and print each known call with its result.

## What goes wrong

Missing the extra stop after `exec` and toggling entry and exit wrongly. Forgetting to pass signals on. Using the 64-bit table for a 32-bit process. Tracing in a container that blocks `ptrace`.
