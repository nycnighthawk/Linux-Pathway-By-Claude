# fork, exec, wait, sessions and daemons

This lesson follows the topic synthesis `synth/LNX-320/LNX-320-T04.md`. Availability of `pidfd`, `clone3` and `close_range` depends on kernel and glibc versions (to verify on your system).

## What you will be able to do

- Spawn a program, report an `exec` failure to the parent and reap the child without leaks.
- Decode a wait status and say who caused a death.
- Explain sessions, process groups and the controlling terminal.
- Choose between a traditional daemon and a service under a manager.

## The trio

`fork` duplicates the caller: the child gets a copy of memory (copy-on-write), the same open file descriptions and the same signal setup. `execve` replaces the program but keeps the PID and every descriptor not marked close-on-exec. `waitpid` collects the exit status; until then the dead child is a zombie.

What `exec` keeps matters: ignored signals stay ignored, the signal mask stays, and leaked descriptors stay open. Open with `O_CLOEXEC` by default.

## Reading a status

| Macro | Meaning |
|---|---|
| `WIFEXITED` / `WEXITSTATUS` | normal exit and its code |
| `WIFSIGNALED` / `WTERMSIG` | killed by a signal |
| `WIFSTOPPED` | stopped (job control, with `WUNTRACED`) |

A shell reports 128+n for death by signal n.

## Reporting exec failure

Create a pipe with `O_CLOEXEC`. In the child, if `execve` returns, write `errno` into the pipe and `_exit`. The parent reads the pipe: end of file with no data means `exec` worked, because the write end closed on its own; four bytes mean `exec` failed and give the reason.

## Orphans, zombies, subreapers

When a parent dies its children go to PID 1 or to the nearest subreaper (`prctl(PR_SET_CHILD_SUBREAPER)`). A `SIGCHLD` handler must loop `waitpid(-1, &st, WNOHANG)` because signals coalesce. `pidfd_open` gives a descriptor for one process that is immune to PID reuse and works with `epoll`.

## Sessions and daemons

A session has one leader and at most one controlling terminal; process groups inside it let the terminal signal a whole job. `setsid` makes a new session without a terminal. The traditional daemon: fork, parent exits, `setsid`, fork again, `chdir("/")`, set `umask`, redirect 0, 1 and 2, close other descriptors, write a PID file. Under a service manager, do none of that: stay in the foreground and let the manager supervise.

## Worked example

A start script runs `ssh host 'service-start &'` and the session hangs. The background process still holds the standard output pipe. Redirecting the three standard streams, or using a manager, ends the hang. In the lab you write a spawn helper that avoids zombies, leaks and silent exec failures.

## What goes wrong

Never calling `wait`. Using non-async-signal-safe functions after `fork` in a threaded program. Descriptors leaking into children. `SIGCHLD` handlers that reap only one child.
