# epoll and io_uring

This lesson follows the topic synthesis `synth/LNX-320/LNX-320-T03.md`. `io_uring` opcodes and sysctl defaults change between kernels, and some hosts disable it; check `man io_uring_setup` and your kernel's settings.

## What you will be able to do

- Explain why `select` and `poll` stop scaling and what `epoll` changes.
- Write a correct edge-triggered loop that drains until `EAGAIN`.
- Contrast a readiness API (`epoll`) with a completion API (`io_uring`).
- State the security trade-off that makes some environments disable `io_uring`.

## Readiness

`select` and `poll` pass the whole descriptor set on every call, so the cost follows the number watched. `epoll` keeps the interest list in the kernel: `epoll_create1` makes it, `epoll_ctl` edits it, `epoll_wait` returns only the ready entries.

| Mode | Reports | Caller must |
|---|---|---|
| Level-triggered (default) | while the descriptor stays ready | read some, will be told again |
| Edge-triggered (`EPOLLET`) | on a change to ready | read and write until `EAGAIN`, with non-blocking descriptors |

`EPOLLONESHOT` disarms a descriptor after one event; `EPOLLEXCLUSIVE` reduces wake-ups when many threads wait on one listener. Regular files are always ready, so `epoll` does not help with disk I/O.

## Completion

`io_uring` shares two rings with the kernel: a submission queue that holds operation descriptors and a completion queue that returns results. One `io_uring_enter` can submit and reap many operations, and with `SQPOLL` a kernel thread may remove most system calls. Operations include reads, writes, accept, connect, send, receive, timeouts and more. You hand over buffers and learn later how many bytes moved. Buffer lifetimes become your problem: a buffer must stay valid until the completion arrives.

## Choosing

Use `epoll` for socket servers with many mostly idle connections, in a simple design that any recent kernel supports. Consider `io_uring` for high-rate storage and network I/O where batching pays, and where the deployment allows it. Large cloud operators have restricted it because of the kernel attack surface it exposes, so check policy (the `kernel.io_uring_disabled` sysctl, seccomp profiles).

## Worked example

An echo server uses a listening socket and many client sockets, all non-blocking. On a readable listener it accepts in a loop until `EAGAIN` and adds each client to the epoll set. On a readable client it reads until `EAGAIN`, writes back what it read, and removes the client when `read` returns 0. The lab asks you to finish such a loop with edge-triggered events.

## What goes wrong

Edge-triggered mode with a blocking descriptor or a single read per event: the loop stalls. Forgetting to remove a closed descriptor's state. Assuming `epoll` helps with files. Leaving a buffer on the stack while an `io_uring` operation is still in flight.
