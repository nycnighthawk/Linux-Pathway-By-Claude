## Metrics

| Type | Use | Query with |
|---|---|---|
| Counter | things that only grow (`..._total`) | `rate()` |
| Gauge | values that go up and down | directly |
| Histogram | latency and sizes, aggregable across instances | `histogram_quantile()` over summed bucket rates |
| Summary | client-side quantiles, not aggregable | rarely |

Names: `app_thing_unit_total`, base units (seconds, bytes). Labels hold small bounded sets (method, route template, status class); never user IDs or raw paths. Series count is the product of label cardinalities. A histogram with N buckets makes N+1 bucket series plus `_sum` and `_count` per label set.

## What to measure

Requests: rate, errors, duration. Resources: utilisation, saturation, errors. Alert on symptoms (error-budget burn) with a `for` duration, route through Alertmanager.

## OpenTelemetry

API in the code, SDK exports over OTLP (gRPC 4317, HTTP 4318). The Collector has receivers, processors (`memory_limiter`, `batch`, Kubernetes attributes) and exporters, deployed as an agent (DaemonSet or sidecar) and a gateway (tail sampling). Trace context travels in the W3C `traceparent` header; every hop must read and write it. Exemplars link a histogram sample to a trace.

## Worked example: Prometheus out of memory

A customer ID label created millions of series. Find the heaviest metric, drop the label with a relabel rule at scrape time, and move per-customer views to logs and traces.
