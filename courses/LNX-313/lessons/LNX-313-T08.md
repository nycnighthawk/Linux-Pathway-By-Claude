## The loop

A reconcile call carries only a name. It ignores which event caused it, reads current state, computes the desired state from the spec, creates or updates what differs, writes status and returns. Called twice in a row it changes nothing the second time.

| Step | Why |
|---|---|
| Fetch; if not found, return | the object was deleted |
| Deletion timestamp set: clean up, remove the finalizer | external state is not leaked if the operator was down |
| Create or update children with `ownerReferences` | garbage collection, and child events map back to the parent |
| Update status through the status subresource | the user owns spec, the controller owns status |
| Return a requeue only if something is pending | errors retry with back-off |

## kubebuilder in one screen

`kubebuilder init`, `kubebuilder create api --group G --version v1 --kind K`. Markers on types (`+kubebuilder:validation:Minimum=1`, `+kubebuilder:subresource:status`) and on the reconciler (`+kubebuilder:rbac:...`) feed `make manifests generate`. `make install run` runs it against the current cluster. Tests: fake client, then envtest (real API server and etcd, no built-in controllers), then kind for end to end.

## Pitfalls

Hot loops (writing status every time), stale cache reads after a write, leader election missing, finalizers left behind after the operator is uninstalled, mutating the user's spec.

## Worked example: a duplicate child

A retry created two Services. The reconciler listed children from a stale cache right after creating one. Fix: derive the child's name from the parent, `Get` it by name, create only when missing, and rely on the next reconcile.
