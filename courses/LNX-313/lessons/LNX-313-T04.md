# Rolling, blue/green, canary

This lesson follows the topic synthesis `synth/LNX-313/LNX-313-T04.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Tune `maxSurge`, `maxUnavailable`, `minReadySeconds` and the progress deadline from capacity numbers.
- Build blue/green and canary releases from plain Services and Deployments, and know their limits.
- Plan data changes so that two versions can run together.

## The Deployment controller

A rollout creates a ReplicaSet for the new Pod template (named by its hash) and moves replicas from the old one within bounds. Defaults: surge 25 percent (rounded up), unavailable 25 percent (rounded down), `minReadySeconds: 0`, `progressDeadlineSeconds: 600`, `revisionHistoryLimit: 10`. The controller never rolls back by itself; a stalled rollout only sets a condition. `kubectl rollout status` fails after the deadline; `kubectl rollout undo` scales an old ReplicaSet back.

| Goal | Setting |
|---|---|
| Never lose capacity | `maxUnavailable: 0`, `maxSurge: n` (needs room for n extra Pods) |
| Packed cluster | `maxSurge: 0`, `maxUnavailable: 1` |
| Single-writer workload | `strategy: Recreate` |

## Blue/green and canary

- **Blue/green**: two Deployments, one Service; switch by patching the Service selector; roll back by patching it back. Costs double capacity during overlap.
- **Canary (plain)**: stable and canary Deployments share the Service's label; traffic share is about the ready-Pod share, so a 5 percent canary needs 20 Pods in total.
- **Weighted routes** (Gateway API or a mesh) give exact percentages. Progressive-delivery controllers add steps and metric analysis.

## Compatibility

Two versions run together in every strategy. Use expand and contract for schemas: add, then use, then remove, in separate releases.

## Worked example: capacity dip

A 12-replica service loses capacity at each release. Set `maxSurge: 3`, `maxUnavailable: 0`, `minReadySeconds: 15`; confirm there is room for three extra Pods.
