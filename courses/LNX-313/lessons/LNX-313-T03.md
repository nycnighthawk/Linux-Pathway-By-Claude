# Probes, logs, kubectl debug

This lesson follows the topic synthesis `synth/LNX-313/LNX-313-T03.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Give each probe its job and set timing from the numbers, not from habit.
- Read status, events and logs (including the previous instance) in the right order.
- Add an ephemeral container, copy a Pod or debug a node, and know the permissions and risks.

## The three probes

| Probe | Failure means | Effect |
|---|---|---|
| startup | not started yet | other probes wait; kill after the threshold |
| readiness | cannot serve now | address removed from Service endpoints; no restart |
| liveness | stuck for good | container killed, restarted with back-off |

Detection time is about `periodSeconds x failureThreshold`. A start of two minutes needs a startup probe covering more than that.

## Rules that prevent cascades

- Liveness checks only the process itself, never a shared dependency.
- Readiness may reflect local overload, but a dependency check couples availability across services.
- Keep the timeout longer than a garbage-collection pause and a throttled period.
- Add a short `preStop` sleep so endpoints update before the process stops accepting.

## Finding the cause

1. `kubectl describe pod`: state, last state, exit code (137 killed, 143 terminated), events.
2. `kubectl logs POD -c NAME --previous` for a crash loop.
3. `kubectl debug -it POD --image=busybox --target=app` to share namespaces; `--copy-to` to experiment on a copy; `kubectl debug node/NAME` for the host (mounted under `/host`).

Ephemeral containers cannot be removed, have no probes or ports, and need the right RBAC.

## Worked example: killed during start

Exit 137, event "Liveness probe failed: connection refused", app needs 90 seconds. Add a startup probe (period 5, failure threshold 30) and keep liveness tight.
