# Pod design: init and sidecar containers

This lesson follows the topic synthesis `synth/LNX-313/LNX-313-T01.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Choose between an init container and a native sidecar for a helper.
- Write the manifest and predict start and stop order.
- Compute the Pod's effective resource request.

## Two mechanisms

| | Init container | Native sidecar |
|---|---|---|
| Declared in | `initContainers` | `initContainers` with `restartPolicy: Always` |
| Runs | to completion, in order, before the app | starts in order, then runs for the Pod's life |
| Probes | not allowed | liveness, readiness, startup allowed |
| Stops | already done | after the app containers, in reverse order |
| Typical use | wait, migrate, render config, fetch data | log shipper, proxy, credential refresher |

A native sidecar counts as started when it is running, or when its startup probe passes, then the kubelet moves to the next init entry. A convention sidecar (a second entry in `containers`) has no ordering guarantees.

## Effective request

effective = max( sum(app containers + sidecars), max over each ordinary init container of (its request + the sidecars declared before it) ). Same for limits and for QoS: Guaranteed needs requests equal to limits everywhere.

## Design test

Put the helper in the Pod only if it must share the application's network, storage or fate. Otherwise use its own Deployment, Job or DaemonSet.

## Worked example: Job never completes

A Job with a proxy as a second container hangs after the main container exits. Move the proxy into `initContainers` with `restartPolicy: Always`; the Job finishes when the main containers do. Requires a cluster version where the feature is stable (1.33 or later, to verify).
