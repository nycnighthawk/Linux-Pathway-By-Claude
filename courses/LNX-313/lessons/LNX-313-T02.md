# Config, Secrets, SecurityContext, limits

This lesson follows the topic synthesis `synth/LNX-313/LNX-313-T02.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Pick the right delivery method (env, args, volume, API) for a setting and know when it updates.
- Handle Secrets honestly: what base64 is, where they are stored, who can read them.
- Write a security context that passes the restricted level and set requests and limits that give the class you intend.

## Delivery methods

| Method | Updates in a running Pod | Notes |
|---|---|---|
| Environment variable | never | leaks into child processes and dumps |
| Command-line argument | never | via `$(VAR)` expansion |
| Volume (whole ConfigMap or Secret) | yes, after a sync delay | a `subPath` mount never updates |
| API read | on demand | needs RBAC |

An immutable ConfigMap or Secret cannot change; roll a new name instead. Add a checksum annotation to the Pod template so a config change rolls the Deployment.

## Secrets

Base64 is encoding. Protection comes from RBAC, encryption at rest on the API server and not putting them in Git in plain form. Whoever can create a Pod in a namespace can read every Secret there. Prefer mounted files with a restrictive mode; use an external store or short-lived credentials where possible.

## Restricted security context

`runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `seccompProfile.type: RuntimeDefault`, `readOnlyRootFilesystem: true` with `emptyDir` for writable paths. Enforce with namespace labels `pod-security.kubernetes.io/enforce: restricted`; stage with `audit` and `warn`.

## Requests, limits and QoS

Guaranteed: requests equal limits for CPU and memory in every container. Burstable: some request or limit. BestEffort: none. Memory over the limit is killed; CPU over the limit is throttled, which hurts tail latency. Quotas require Pods to state requests, so pair them with a LimitRange.

## Worked example: restart loop

A container restarts every few minutes with `OOMKilled` as the last reason. Its memory limit is below its working set. Raise the request and limit to the observed peak plus margin, then watch.
