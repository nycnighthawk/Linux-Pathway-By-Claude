## overlayfs

```bash
mkdir lower1 lower2 upper work merged
sudo mount -t overlay overlay -o lowerdir=lower2:lower1,upperdir=upper,workdir=work merged
```

The leftmost lower is on top. Reads come from the highest layer holding the file (page cache shared between containers on the same layer). The first write to a lower file triggers **copy-up** of the whole file into `upper`, a latency cliff for large files. Deletion of a lower file leaves a **whiteout**: a character device 0/0 with the file's name; an opaque directory carries `trusted.overlay.opaque=y` (`user.*` xattrs with `userxattr` for rootless). Docker's `overlay2` keeps layers under `/var/lib/docker/overlay2/<id>/{diff,link,lower,work,merged}` with short links in `l/` because mount options have a length limit. `docker inspect -f '{{json .GraphDriver.Data}}' c` prints `LowerDir`, `UpperDir`, `MergedDir`; `docker diff c` lists `A`, `C`, `D` changes. The backing filesystem needs `d_type` (XFS `ftype=1`) and xattrs; XFS with `pquota` allows `--storage-opt size=`.

## Volumes, binds, tmpfs

- **Named volume**: engine-managed directory, bypasses the storage driver, native speed, copied from the image on first use if empty.
- **Bind mount**: any host path. `-v` creates a missing source as a root-owned directory; `--mount type=bind` errors instead, which is safer.
- **tmpfs**: memory-backed, gone at stop.

Write-heavy data (databases, queues) belongs in a volume, never in the writable layer. `docker system df -v` shows image, container, volume and cache use; the json-file log driver grows without `max-size`.

## SELinux

A container process runs as `container_t` with two random MCS categories, for example `s0:c101,c909`; its files are `container_file_t` with the same categories. A host directory keeps its host type (`user_home_t`), so the container gets `Permission denied` although Unix modes are right. Find the denial with `ausearch -m avc -ts recent` or `journalctl -t setroubleshoot`. Fixes in order of preference:

1. `-v /srv/data:/data:Z` relabels for this container alone; `:z` for sharing between containers.
2. `semanage fcontext -a -t container_file_t '/srv/data(/.*)?'` then `restorecon -Rv /srv/data`, which survives relabels.
3. A narrow custom type (`--security-opt label=type:...`, policy from `udica`).
4. `--security-opt label=disable`, the last resort.

Never use `:Z` on shared trees such as `/home/user`, `/etc` or `/var/lib`. AppArmor distributions have no label step and ignore the flags.

## Ownership

In rootless or `userns-remap` containers a host file owned by UID 1000 shows as `nobody`. Use `--userns=keep-id`, `:U`, `podman unshare chown`, or `:idmap` (idmapped mounts, Linux 5.12 and later).

## Worked example: nginx returns 403 on Fedora

`podman run --rm -v $PWD/site:/usr/share/nginx/html:ro nginx` gives 403. `ls -Zd site` shows `user_home_t`; `ausearch -m avc -ts recent` shows `container_t` denied `read` on that type. Add `:Z`, or run `semanage fcontext` plus `restorecon`; `ls -Zd site` then shows `container_file_t`. For a shared site directory prefer the fcontext rule.

## Failure patterns

- A database in the writable layer: slow checkpoints and data lost at `docker rm`.
- `no space left on device` while `df` shows room: build cache and logs, or exhausted inodes.
- `chown` fails in a rootless container: no subordinate ID range.
- `docker volume prune` or `system prune --volumes` run on the wrong host.
