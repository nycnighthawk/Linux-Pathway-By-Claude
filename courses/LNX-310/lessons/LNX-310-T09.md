# Debugging: nsenter, inspect, events

This lesson follows `synth/LNX-310/LNX-310-T09.md`, which carries the sources and history.

## What you will be able to do

- Triage a failing container in order: state, logs and exit code, configuration, events, then namespaces and tracing.
- Read exit codes (125, 126, 127, 137, 139, 143) and `OOMKilled`.
- Use `nsenter` to run host tools in a container's network, mount or PID namespace.
- Use debug containers and ephemeral containers when the image has no shell.

## Triage order

1. **State**: `docker inspect -f '{{json .State}}' c` shows `Status`, `ExitCode`, `OOMKilled`, `Error`, `Pid`, `Health`.
2. **Logs and exit code**: `docker logs --since 10m -t c`. Remember logs vanish with some drivers.
3. **Configuration**: `.Config` (entrypoint, cmd, user, env), `.HostConfig` (binds, caps, limits), `.Mounts`, `.NetworkSettings`.
4. **Events**: `docker events --since 1h --filter container=c --filter event=die` shows restart rhythm and `exitCode`/`signal` with no logs at all. Kubernetes: `kubectl describe pod`, `kubectl logs --previous`, `kubectl get events --sort-by=.lastTimestamp`.
5. **Enter and trace** (below).

Exit codes: `0` clean; `1` application error; `125` the engine failed to run it; `126` found but not executable; `127` command not found (also a missing shebang interpreter); `128+n` signal `n`: `137` SIGKILL (OOM or stop timeout), `139` SIGSEGV, `143` SIGTERM. `OOMKilled: true` plus 137 settles memory; 137 without it points to a kill or timeout. A container that dies at once is inspected with `docker run --rm -it --entrypoint sh image`.

## nsenter

```bash
pid=$(docker inspect -f '{{.State.Pid}}' web)   # podman has the same field
sudo nsenter -t "$pid" -n ss -tlnp               # host's ss, container's network
sudo nsenter -t "$pid" -n tcpdump -ni eth0 port 5432
sudo nsenter -t "$pid" -m -p ps aux              # mount + pid namespaces
ls -l /proc/$pid/root/etc/                       # read its filesystem from the host
```

Flags: `-m` mount, `-u` UTS, `-i` IPC, `-n` network, `-p` PID, `-U` user, `-C` cgroup, `-a` all. Enter only what you need: the network namespace alone keeps the host's tools, so it works on a distroless image; entering the mount namespace replaces `/`. Rootless: use `podman unshare` or join the user namespace first. Helpers: `lsns -t net`, `cat /proc/$pid/cgroup`, `grep -E 'Cap|Seccomp|NoNewPrivs' /proc/$pid/status`, `strace -f -p $pid`, `sysdig -pc container.name=web`.

## No shell in the image

`docker run -it --rm --pid=container:web --net=container:web --cap-add SYS_PTRACE nicolaka/netshoot` shares the target's namespaces. Kubernetes: `kubectl debug -it pod/web --image=busybox:1.37 --target=app` adds an ephemeral container (not restartable, needs RBAC); `--copy-to` debugs a copy; `kubectl debug node/n1` mounts the node at `/host`. On the node, `crictl ps -a`, `crictl inspect`, `crictl logs` bypass the API server.

## Worked example: exit 127 in a loop

`docker ps` shows `Restarting (127)`. `docker inspect -f '{{.Config.Entrypoint}}' app` prints `[/entrypoint.sh]`. Running `docker run --rm --entrypoint sh app -c 'head -1 /entrypoint.sh'` shows `#!/bin/bash` in a BusyBox image: the interpreter is missing, not the script. Fix the shebang or the base. Evidence came from state and one run, with nothing installed in the image.

## Failure patterns

- A configured memory limit that is not in force: read `memory.max` in the cgroup, not the config.
- DNS failing only in containers: `nsenter -t $pid -n -m cat /etc/resolv.conf` shows an unreachable forwarder.
- Restarting before capturing `inspect`, logs and `docker diff` destroys evidence.
- A privileged debug sidecar left running exposes the target's memory and environment.
