# Sandboxed runtimes: gVisor, Kata (needs KVM)

This lesson follows `synth/LNX-310/LNX-310-T10.md`, which carries the sources and history.

## What you will be able to do

- Explain why a shared-kernel container is not a hard tenant boundary.
- Describe how gVisor (Sentry, Gofer, platforms) and Kata (VM per pod, agent, virtio-fs) differ.
- Register a runtime handler and select it with a Kubernetes `RuntimeClass`.
- Check whether a host can run VM-based sandboxes.

## Why

Every container shares one kernel and its syscall surface. A kernel flaw is a boundary failure for all tenants. For untrusted code (customer functions, CI from strangers, generated code) NIST's container guide recommends separating workloads of different sensitivity by VMs or equivalent. Two designs shrink what the host kernel exposes.

**gVisor** (`runsc`): a user-space kernel written in Go. The **Sentry** implements syscalls, memory, the network stack and a virtual filesystem; a **Gofer** does file access for it. A **platform** redirects the application's syscalls to the Sentry: `systrap` (default, via seccomp traps, works inside VMs), `KVM` (fast on bare metal), `ptrace` (slow, being removed). The Sentry runs under a tight seccomp filter. Cost: incomplete syscall and `/proc` support, higher per-syscall overhead.

**Kata Containers**: each pod runs in a lightweight VM with its own Linux kernel. A shim (`containerd-shim-kata-v2`) starts a hypervisor (QEMU, Cloud Hypervisor, Firecracker or built-in Dragonball), boots a minimal guest, and talks over vsock to the **kata-agent**, which creates the containers inside the guest. Image layers reach the guest by `virtio-fs` or block devices. Cost: tens of megabytes per pod, slower start, KVM required.

**Firecracker** is a minimal VMM (Rust) with a jailer that confines it; it is what runs AWS Lambda and can be Kata's backend.

## Plugging in

containerd shims are named `io.containerd.runc.v2`, `io.containerd.kata.v2` and `io.containerd.runsc.v1`. Docker can register an alternative runtime in `daemon.json` (`"runtimes": {"runsc": {"path": "/usr/local/bin/runsc"}}`) and run `docker run --runtime=runsc`. Kubernetes:

```yaml
kind: RuntimeClass
apiVersion: node.k8s.io/v1
metadata:
  name: gvisor
handler: runsc
overhead:
  podFixed: {memory: 120Mi, cpu: 100m}
scheduling:
  nodeSelector: {sandbox.example/gvisor: "true"}
```

A pod sets `runtimeClassName: gvisor`. `overhead` makes the scheduler count the sandbox's own memory; without it a node of 64 GB packed with 1 GB Kata pods runs out. The handler must also exist in the node's containerd or CRI-O configuration, or pods hang in `ContainerCreating`.

## KVM readiness

```bash
grep -c -E 'vmx|svm' /proc/cpuinfo     # CPU virtualisation
ls -l /dev/kvm                          # device and group
systemd-detect-virt                     # are we inside a VM already?
kata-runtime check                      # or kata-ctl check
```

Inside a cloud VM, a result such as `kvm` or `microsoft` with no `/dev/kvm` means nested virtualisation is off, the commonest reason a Kata pod will not start. gVisor with `systrap` needs no KVM.

## Worked example: choosing

A SaaS runs customer plugins as pods. Plugins are stateless HTTP handlers, so gVisor on a dedicated node pool with a `gvisor` RuntimeClass fits, with a tainted pool and a toleration. The same company's CI runs arbitrary build scripts needing full kernel features (Docker-in-pod): Kata, with `overhead` set and bare-metal nodes. Internal services stay on runc.

## Failure patterns

- A profiler needing `perf_event_open` fails in gVisor; the error is in the Sentry log, not the app.
- Host tools (eBPF, `strace` of the host PID) see only the VMM or Sentry, not the workload.
- A privileged pod in a sandbox is still privileged inside it.
- A sandbox does not stop abuse of legitimate channels such as the metadata endpoint.
