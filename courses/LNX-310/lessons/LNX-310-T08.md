## Inventory, claims, signatures

An **SBOM** lists components (SPDX or CycloneDX, JSON), each with a name, version and a package URL such as `pkg:deb/debian/openssl@3.0.15-1`. Generators (Syft, Trivy, BuildKit with `--sbom=true`) read package databases and lockfiles; they miss files copied in without a package manager. An **attestation** is a signed in-toto statement: a subject digest, a `predicateType` (SLSA provenance, SPDX, CycloneDX, vulnerability scan) and a predicate. **SLSA provenance** records who built what from which source; higher levels need an isolated builder whose signing keys the build steps cannot read. **VEX** states that a known CVE does not affect a product, with a justification, so a false positive can be suppressed in an auditable way.

## cosign

Signing identifies the **digest**, never the tag.

```bash
cosign sign --yes registry.example/app@sha256:<digest>
cosign verify registry.example/app@sha256:<digest> \
  --certificate-identity-regexp '^https://github.com/example/app/.github/workflows/release.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
cosign attest --yes --predicate sbom.spdx.json --type spdxjson registry.example/app@sha256:<digest>
cosign verify-attestation --type spdxjson ... registry.example/app@sha256:<digest>
```

Keyless signing: the CI job gets an OIDC token, Fulcio issues a certificate of about ten minutes tied to that identity, the signature is recorded in the Rekor log, and the private key is discarded. Verification without `--certificate-identity` (or its regexp) and `--certificate-oidc-issuer` proves nothing: any valid Sigstore signature would pass. Key-based signing (`cosign generate-key-pair`, `--key awskms://...`) suits air-gapped sites. cosign 3 signs with the Sigstore bundle format by default. `cosign tree` lists the signature and attestations stored with an image. Alternatives: Notation (X.509 trust stores) and GPG signatures with `signedBy` in `policy.json`. Docker Content Trust is gone from the Docker 29 CLI.

## Trivy

```bash
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 registry.example/app@sha256:<digest>
trivy image --format cyclonedx -o sbom.cdx.json app:1
trivy sbom sbom.cdx.json
trivy config .            # Dockerfiles, Kubernetes, Terraform
trivy image --vex vex.openvex.json app:1
```

It caches a vulnerability database (refresh daily, mirror it with `--db-repository` and use `--skip-db-update` offline). `.trivyignore` lists accepted IDs but gives no reason; VEX does. Scanners disagree because distribution back-ports keep an old version string while carrying the fix, so check the distribution's tracker. Pin the scanner's version and treat it as part of your supply chain.

## Pipeline and admission

Build with `--provenance=mode=max --sbom=true --push`; take the digest from the build output; sign it; scan it and fail on fixable critical findings; release by digest only. At admission, a Kyverno `verifyImages` rule or the Sigstore policy controller requires a signature from the release workflow identity, a provenance attestation, and mutates tags to digests. Podman and CRI-O enforce `policy.json` at pull.

## Worked example: a check that checks nothing

CI runs `cosign verify image` with no flags and passes, because someone signed it. Adding identity and issuer makes it fail until the policy names the reusable workflow that now performs the release. The first failure is the policy doing its job.

## Failure patterns

- Signing a tag, then deploying a different digest behind the same tag.
- A signed image from a compromised dependency: signatures prove origin, not safety.
- Alert fatigue from hundreds of unreachable low findings; filter by severity, fixability and VEX.
- Admission rules disabled in the first incident and never restored.

## Self-check

1. Why sign a digest rather than a tag?
2. What do `--certificate-identity` and `--certificate-oidc-issuer` assert?
3. What does a VEX statement give you that `.trivyignore` does not?
4. Why may a scanner flag an up-to-date Debian package?
5. Where is an SBOM attestation stored, and why not inside the image?
