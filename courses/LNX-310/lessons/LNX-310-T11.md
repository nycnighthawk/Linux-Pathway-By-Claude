# Windows containers

This lesson follows `synth/LNX-310/LNX-310-T11.md`, which carries the sources and history. It is a survey: you meet these workloads and must know where Linux assumptions break.

## What you will be able to do

- Contrast Windows server silos, job objects and the layered filter with Linux namespaces, cgroups and overlayfs.
- Choose process or Hyper-V isolation from the host and image versions.
- Name the base image families and the tag rules.
- List the main limits of Windows nodes in Kubernetes.

## Model

Windows has no namespaces, cgroups, seccomp or capabilities. The Host Compute Service builds a container from read-only layers plus a scratch layer, with **server silos** for private views of the file system, registry, network ports, object manager and process IDs, and **job objects** for CPU, memory, process count and I/O limits. Identity replaces capabilities: `ContainerUser` is low privilege, `ContainerAdministrator` the default. Runtime: containerd with `hcsshim` (recommended for Kubernetes) or Docker Engine (named pipe `\\.\pipe\docker_engine`). Images use the OCI format with `os: windows`.

## Isolation modes and versions

**Process isolation**: containers share the host kernel; `docker top` and host `Get-Process` show the same PID. **Hyper-V isolation**: each container runs in a utility VM with its own Windows kernel; the host shows only a `vmwp` process. Select with `docker run --isolation=process|hyperv`. Server hosts default to process, client Windows to Hyper-V.

Because Windows user and kernel mode ship together, a process-isolated container's image build must match the host build (a revision match is no longer needed from version 1809 on). Hyper-V isolation lifts this for older images: a Server 2025 host runs 2025, 2022, 2019 and 2016 images under Hyper-V, and 2025 and 2022 under process isolation; a 2019 host cannot run 2022 images at all; a Windows 11 host can run 2022 images with process isolation. A violation gives an error that the container OS does not match the host, with HCS code `0xc0370101`; in Kubernetes the pod shows `CrashLoopBackOff`.

## Images

`mcr.microsoft.com/windows` (full API minus roles), `windows/server`, `windows/servercore` (large; full .NET Framework, most roles), `windows/nanoserver` (smallest). `latest` is not published, so tags are explicit: `ltsc2022`, `ltsc2025`, `1809`, or a build number. Pull sizes run from about a hundred megabytes to several gigabytes. Dockerfiles use `SHELL ["powershell", ...]`, backslash paths, `USER ContainerUser`, multi-stage builds with an SDK stage and a Nano Server runtime stage. Logs must reach stdout (for example with LogMonitor) because IIS and event logs do not by default.

## Kubernetes

The control plane is Linux; Windows workers run `kubelet`, `kube-proxy` and a CNI; supported nodes are Windows Server 2022 and 2025. Only process isolation is supported, so images must match the node build. A pod is Windows-only: `spec.os.name: windows`, `nodeSelector: kubernetes.io/os: windows`, usually a taint and toleration. Rejected fields include `hostPID`, `hostIPC`, `seccompProfile`, `sysctls`, `fsGroup`, `runAsUser`, and container `privileged`, `capabilities`, `readOnlyRootFilesystem`, `allowPrivilegeEscalation`. `HostProcess` containers replace privileged ones. HugePages are unsupported and the kubelet does not enforce node-allocatable limits as on Linux. Active Directory identity uses a gMSA credential spec.

## Worked example: the node upgrade

A cluster's Windows pool moves from Server 2022 to 2025. Pods built on `ltsc2022` go to `CrashLoopBackOff` with an OS-mismatch error. Options: rebuild on `ltsc2025`; keep a 2022 pool and route by an OS-build node label and `nodeSelector`; or move to Hyper-V isolation where the platform allows it (not in Kubernetes). The lasting fix is to drive the image tag and the node image from one variable.

## Failure patterns

- A monthly host patch strands process-isolated images.
- Large images slow scale-out; node image caches matter.
- No `nsenter`: debugging uses `docker exec` with PowerShell, ETW and `Get-ComputeProcess`.
- Linux-only security tooling (eBPF, Falco) does not apply.
