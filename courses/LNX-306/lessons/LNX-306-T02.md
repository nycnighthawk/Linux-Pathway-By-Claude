# PXE/iPXE/HTTP boot

This lesson follows the topic synthesis `synth/LNX-306/LNX-306-T02.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Explain the chain from firmware DHCP request to a running installer.
- Configure a DHCP server to answer BIOS and UEFI clients differently and to break the iPXE chainload loop.
- Write an iPXE script that chooses an installer and an answer file per machine.
- Make "boot from disk" the safe default, and isolate and log the provisioning network.

## The chain

firmware → DHCP (option 93 says what the client is) → first-stage loader (TFTP, or HTTP in UEFI HTTP boot) → iPXE → script over HTTP → kernel and initrd with arguments → installer → answer file.

| Option | Meaning |
|---|---|
| 93 | client architecture: 0 BIOS, 7 and 9 x86-64 UEFI, 11 ARM64 UEFI |
| 60 | vendor class: `PXEClient` or `HTTPClient` |
| 66, 67 | server name and boot file name (and `next-server`) |
| 175 | present when iPXE itself is asking: serve a script, not the loader |
| 59 | boot file URL in DHCPv6 |

## dnsmasq in six lines

```
dhcp-match=set:bios,option:client-arch,0
dhcp-match=set:efi64,option:client-arch,7
dhcp-match=set:ipxe,175
dhcp-boot=tag:bios,tag:!ipxe,undionly.kpxe
dhcp-boot=tag:efi64,tag:!ipxe,ipxe.efi
dhcp-boot=tag:ipxe,http://boot.example.org/boot.ipxe
```

Without the `ipxe` tag a UEFI machine loads iPXE, asks again, receives iPXE again, and loops.

## An iPXE script

```
#!ipxe
dhcp
kernel http://boot.example.org/el9/vmlinuz inst.repo=http://repo.example.org/snapshots/2026-11-08/el9/baseos/ inst.ks=http://boot.example.org/ks/${mac}.cfg ip=dhcp
initrd http://boot.example.org/el9/initrd.img
boot
```

A web service can return this script, or `exit` for a machine that is not scheduled for a build.

## Safety and security

Default answer: boot from disk. Build mode is a state in the inventory that switches off after the first successful install. Isolate the provisioning VLAN, use DHCP snooping against rogue servers, prefer HTTPS with your own CA in a custom iPXE, keep secrets out of answer files, and log MAC, serial and the answer given.

## Troubleshooting from the bottom

`tcpdump -ni eth0 port 67 or port 68 or port 69`; check next-server and file name; fetch the file over TFTP by hand; read the loader's serial output; read the HTTP access log; then the installer logs.

## Worked example: the infinite loop

Every UEFI client was given `ipxe.efi`, loaded it, asked again, and received it again. The `ipxe` tag on option 175 and a script URL for such clients fixed it.
