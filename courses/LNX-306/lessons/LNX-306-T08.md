# Leapp and release upgrades

This lesson follows the topic synthesis `synth/LNX-306/LNX-306-T08.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Choose between an in-place upgrade and a rebuild, and justify the choice.
- Run the Leapp sequence: prepare, `leapp preupgrade`, read the report, answer questions, `leapp upgrade`, post-upgrade tasks.
- Read a report: risk levels, inhibitors and the answer file.
- Protect the process with backups, snapshots and a rehearsal on a clone.

## Two strategies

| | In place | Rebuild |
|---|---|---|
| Identity and data | kept | moved on purpose |
| Best for | unique, stateful hosts | fleet hosts built from code |
| Main risk | half-upgraded state | missed configuration or data |
| Tools | Leapp, `do-release-upgrade`, `dnf system-upgrade` | Kickstart, cloud-init, Ansible, images |

Rocky Linux documents that major in-place upgrades are not supported, and gives a reinstall procedure. Red Hat supports Leapp on defined minor-release paths.

## The Leapp sequence

```bash
dnf install leapp-upgrade          # after enabling the right repositories
leapp preupgrade                   # read-only assessment
less /var/log/leapp/leapp-report.txt
leapp answer --section <section>.<question>=True   # record a decision
leapp upgrade                      # then reboot into the upgrade environment
```

(Names and paths follow the RHEL 9 to 10 guide; check the guide of your release.)

## Reading the report

- Risk levels: high, medium, low, info.
- An **inhibitor** blocks the upgrade until fixed.
- Read the whole report even if there is no inhibitor.
- Questions with no recorded answer block the run, because the upgrade phase has nobody to ask.
- The assessment cannot simulate the whole upgrade: a clean report is not a guarantee.

## Prepare the surroundings

1. Full backup or snapshot, tested.
2. Space: about 4 GB under `/var/lib/leapp`, and enough in `/boot`.
3. Comment out data-only mounts from `/etc/fstab`.
4. Disable the antivirus and any health checks or hardware watchdogs for the duration.
5. Rehearse on a clone restored from backup; test the application afterwards.

## After the upgrade

Remove leftovers of the old release, review replaced configuration files, re-enable what you disabled, rebuild what depends on a language runtime, and run the application tests.

## Worked example: the watchdog

A hardware watchdog reset a machine in the middle of the package transaction because the daemon that feeds it was not running during the offline stage. The host did not boot and was restored from snapshot; the second attempt disabled the watchdog first.
