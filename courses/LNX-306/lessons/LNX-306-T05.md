# OpenTofu with libvirt provider

This lesson follows the topic synthesis `synth/LNX-306/LNX-306-T05.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Describe the OpenTofu workflow: init, plan, apply, destroy, and what state is.
- Write a configuration that creates a pool, a base volume, copy-on-write disks, cloud-init seeds and VMs on libvirt.
- Keep state, secrets and versions under control.
- Review plans, detect drift and decide between replacing and reconfiguring a machine.

## Concepts

| Term | Meaning |
|---|---|
| provider | plugin that talks to an API (here libvirt) |
| resource / data | an object to manage / something to read |
| state | the record mapping configuration to real objects |
| plan | the computed difference between configuration, state and reality |
| module | reusable configuration with inputs and outputs |

```bash
tofu init ; tofu fmt ; tofu validate
tofu plan -out=plan.bin ; tofu apply plan.bin
tofu plan -refresh-only ; tofu state list ; tofu destroy
```

## A VM from a base image

```
resource "libvirt_volume" "disk" {
  for_each       = var.vm_names
  name           = "${each.key}.qcow2"
  pool           = libvirt_pool.site.name
  base_volume_id = libvirt_volume.base.id
}
resource "libvirt_cloudinit_disk" "seed" { for_each = var.vm_names ... }
resource "libvirt_domain" "vm" {
  for_each  = var.vm_names
  cloudinit = libvirt_cloudinit_disk.seed[each.key].id
  disk { volume_id = libvirt_volume.disk[each.key].id }
}
```

`for_each` over a set makes the machine count data: remove a name and only that machine is destroyed.

## State, secrets, versions

Remote backend with locking and backups; state holds secrets, so restrict and encrypt it and never commit it. Mark variables `sensitive`. Pin the provider version and commit `.terraform.lock.hcl`. One directory and one state per environment.

## Drift and replacement

`plan -refresh-only` reports changes made outside the tool. Changing user-data does not re-run cloud-init in a running guest: decide whether a change replaces the VM (immutable) or is pushed by configuration management (mutable).

## Worked example: the lost state

A reimaged laptop took the only state file. `apply` collided with existing machines. Recovery: import each object into a fresh state, then a remote backend with locking and versioning.
