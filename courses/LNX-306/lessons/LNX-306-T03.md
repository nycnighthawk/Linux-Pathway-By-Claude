# cloud-init

This lesson follows the topic synthesis `synth/LNX-306/LNX-306-T03.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Say what runs in each cloud-init stage and where the configuration comes from.
- Write user-data, meta-data and network-config, and validate them before booting.
- Test on a laptop with a NoCloud seed, and debug with the status, schema, query and log tools.
- Keep secrets out of user-data and clean an image before capture.

## Inputs and stages

| Input | From | Used for |
|---|---|---|
| meta-data | the platform | instance-id, hostname, keys |
| user-data | whoever launches the instance | the main configuration |
| vendor-data | the platform operator | provider defaults |
| network-config | the platform or seed | interfaces (version 1 or 2) |

Stages: generator, local (before network: seed ISO, config drive, network config), network (`init` modules: users, write_files, ssh), config, final (`runcmd`, scripts). `cloud-init status --wait` blocks until final is done.

## A cloud-config

```
#cloud-config
hostname: web01
users:
  - name: ops
    groups: [wheel]
    ssh_authorized_keys: [ssh-ed25519 AAAA... ops@example.org]
disable_root: true
ssh_pwauth: false
packages: [chrony]
write_files:
  - {path: /etc/site/role, permissions: "0644", content: "role=web\n"}
runcmd:
  - [systemctl, enable, --now, chronyd]
```

`#cloud-config` on line 1 is required. Prefer list-form `runcmd` entries, which avoid shell quoting.

## NoCloud on a laptop

```bash
cloud-localds seed.iso user-data meta-data        # volume label cidata
cloud-init schema --config-file user-data --annotate
sudo cloud-init clean --logs                      # next boot is a first boot
cloud-init status --long ; cloud-init query ds.meta_data
less /var/log/cloud-init-output.log
```

Per-instance modules run again only when the `instance-id` changes. Clones need new ids and a cleaned template.

## Safe use

User-data is not secret: any process on the instance can read it from the metadata service. Pass a short-lived token or use platform identity and fetch secrets over an authenticated channel. Restrict `datasource_list`, keep per-instance data out of the image, and clean the image (`cloud-init clean`) before capture so host keys and machine id are fresh.

## Worked example: the ignored configuration

Ten clones of one VM kept the same `instance-id`, so cloud-init believed it had run and skipped `runcmd` on all of them. Unique ids per clone and a cleaned template fixed it.
