# Rust for Linux modules

This lesson follows the topic synthesis `synth/LNX-331/LNX-331-T10.md`. Rust support evolves each release; check `Documentation/rust/` and the minimum `rustc` version for your tree (to verify).

## What you will be able to do

- Check a tree and toolchain for Rust support and build the sample module.
- Read the structure of a Rust kernel module.
- Name the bug classes safe Rust removes, and the ones that need `unsafe`.
- Review an `unsafe` block's SAFETY comment.

## Build

```
make LLVM=1 rustavailable
make LLVM=1 menuconfig        # General setup -> Rust support
make LLVM=1 -j"$(nproc)"
make rustdoc ; make rust-analyzer
```

The tree uses its own `core`/`alloc` pieces and `bindgen` for C declarations. There is no standard library, no panicking allocation.

## A module

```rust
use kernel::prelude::*;

module! {
    type: Hello,
    name: "hello_rust",
    author: "A. Student",
    description: "A first Rust module",
    license: "GPL",
}

struct Hello;
impl kernel::Module for Hello {
    fn init(_m: &'static ThisModule) -> Result<Self> {
        pr_info!("hello from Rust\n");
        Ok(Hello)
    }
}
impl Drop for Hello {
    fn drop(&mut self) { pr_info!("goodbye\n"); }
}
```

## Layout

| Directory | Holds |
|---|---|
| `rust/kernel/` | safe abstractions (locks, `Arc`, allocation, devices, I/O) |
| `rust/bindings/` | raw generated `unsafe` bindings; drivers do not use them |
| `rust/macros/` | `module!` and friends |
| `samples/rust/` | working small modules |

## What Rust gives you

| C bug | Rust mechanism |
|---|---|
| leak or double free on an error path | ownership and `Drop` |
| forgotten unlock | lock guard |
| unlocked access to data | `Mutex<T>` owns the data |
| NULL dereference | `Option<T>` |
| ignored error | `Result` and `?` |
| dangling reference | lifetimes and the borrow checker |
| overflow, out-of-range index | checked arithmetic, bounds checks |
| data race | `Send` and `Sync` |

Not removed: raw hardware access, calling C, the abstractions themselves. Those use `unsafe` with a `// SAFETY:` comment saying why the preconditions hold.

## Kernel differences

Allocation is fallible and returns `Result`. A `panic!` is a kernel bug, so use `Result` for expected failures.
