# Device model, sysfs, platform drivers, device tree

This lesson follows the topic synthesis `synth/LNX-331/LNX-331-T02.md`. API names evolve; check `Documentation/driver-api/` in your tree (to verify).

## What you will be able to do

- Describe bus, device, driver and class, and how binding happens.
- Read and write sysfs, and add a device attribute.
- Write a platform driver with `probe`, `remove` and an `of_match_table`.
- Read a device tree node and predict which driver binds.

## The model in one picture

```
bus  --matches-->  device  <--bound to--  driver
 |                    |
 +-- class view       +-- sysfs directory with attributes
```

A device has at most one driver. Matching runs when a device appears and when a driver registers. Manual control:

```
echo 0000:00:03.0 > /sys/bus/pci/drivers/old/unbind
echo 0000:00:03.0 > /sys/bus/pci/drivers/new/bind
```

## sysfs rules

One value per file, text, documented in `Documentation/ABI/`. Add attributes with `DEVICE_ATTR_RW(name)` plus `name_show` and `name_store`, and attach them through `dev_groups` so udev sees them at creation.

## A platform driver

```c
static const struct of_device_id acme_ids[] = {
	{ .compatible = "acme,gpio-v1" }, { }
};
MODULE_DEVICE_TABLE(of, acme_ids);

static int acme_probe(struct platform_device *pdev)
{
	void __iomem *base = devm_platform_ioremap_resource(pdev, 0);
	if (IS_ERR(base)) return PTR_ERR(base);
	struct acme *a = devm_kzalloc(&pdev->dev, sizeof(*a), GFP_KERNEL);
	if (!a) return -ENOMEM;
	/* clocks, irqs, subsystem registration ... */
	return 0;
}
static struct platform_driver acme_driver = {
	.probe = acme_probe,
	.driver = { .name = "acme-gpio", .of_match_table = acme_ids },
};
module_platform_driver(acme_driver);
```

`devm_` resources are released automatically in reverse order. Return `-EPROBE_DEFER` when a supplier (clock, regulator) is not ready.

## Device tree

| Property | Meaning |
|---|---|
| `compatible` | strings, most specific first; first one a driver lists wins |
| `reg` | address and size cells |
| `interrupts` | lines, with `interrupt-parent` |
| `status` | absent or `"okay"` is used; `"disabled"` creates no device |
| `clocks`, `gpios`, `resets` | phandle references |

Tools: `dtc -I dtb -O dts`, `/proc/device-tree`, `dt-validate`. Overlays (`.dtbo`) patch a base tree.

## When a device does not bind

1. `status`? 2. `compatible` against the driver's table? 3. `/sys/kernel/debug/devices_deferred`? 4. Is the module built and its alias present? 5. `dmesg` for the probe error.

## Self-check

Try each question before you read the answers below.

1. A node has `compatible = "acme,gpio-v2", "acme,gpio-v1"` and the driver lists only v1. Does it bind?
2. A device never probes and `devices_deferred` lists it. What does that mean?
3. Why attach sysfs attributes through `dev_groups` instead of creating them after registration?

### Answers

1. Yes. The kernel tries the strings in order and the driver's v1 entry matches the second string.
2. Its probe returned `-EPROBE_DEFER` because a supplier such as a clock or regulator was not ready; find and fix the missing supplier.
3. Then they exist before the uevent is sent, so udev rules can read them.
