# Kernel performance regressions

This lesson follows the topic synthesis `synth/LNX-331/LNX-331-T13.md`. Tool options and defaults vary by kernel and perf version (to verify).

## What you will be able to do

- Decide whether a measured slowdown is real or noise.
- Use counters and sampling to find the function whose share of time grew.
- Narrow a regression to a commit and write a report maintainers can act on.

## Step 1: is it real?

- Same kernel config, command line, microcode, governor; pin CPUs with `taskset`/`numactl`.
- Run both kernels many times, interleaved. A difference below the run-to-run spread is not evidence.
- Compare `/proc/cmdline` and `/sys/devices/system/cpu/vulnerabilities/*`: a different mitigation or a debug option is the commonest false regression.

## Step 2: where does the time go?

```
perf stat -d -- ./bench          # IPC, cache misses, context switches
perf record -g -- ./bench        # sample with call stacks
perf report --no-children        # hot functions
perf diff before.data after.data # compare two profiles
```

Compare **shares** of samples per function, not raw counts, because the totals differ between runs. If CPU use falls while runtime grows, look off-CPU (`perf sched`, scheduler tracepoints, BCC or bpftrace tools).

## Step 3: who calls it?

A lock slow path that grows needs its callers: call graphs, `perf lock` or `lockstat` name the lock and call sites.

## Step 4: which commit?

`git bisect run` with a benchmark script that exits 0 or 1 against a threshold set from the measured noise. Then check the commit really is the cause: revert it on the bad tip, and look at `perf annotate` and `pahole` for layout or inlining effects.

## Typical causes

Locking changes, memory-management changes, scheduler placement, mitigations, debug options, toolchain and code layout, firmware.

## Reporting

Benchmark and exact command, hardware and firmware, both kernel versions and configs, effect size with confidence, profile evidence, bisected commit.

## Lab

`labs/LNX-331/perf-regression` gives two profile summaries; find the function whose share grew, the commit that touched its file, and the right next tool.
