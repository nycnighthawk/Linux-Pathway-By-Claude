# Spinlocks, mutexes, RCU, lockdep

This lesson follows the topic synthesis `synth/LNX-331/LNX-331-T05.md`. Details of PREEMPT_RT and lock API names vary by version (to verify).

## What you will be able to do

- Choose between a spinlock, a mutex, an RCU read-side section and a lock-free pattern.
- Match lock variants to the contexts that take them.
- Explain what lockdep checks and read its report.
- Predict how a PREEMPT_RT kernel changes the rules.

## Choosing

| Situation | Primitive |
|---|---|
| short critical section, may be taken in a handler or softirq | `spinlock_t` with `_irqsave` or `_bh` as needed |
| longer section that may sleep, process context only | `struct mutex` |
| read-mostly data, readers must be fast | RCU |
| a counter or flag | `atomic_t`, `READ_ONCE`, `WRITE_ONCE` |
| per-CPU data | per-CPU variables with preemption off while used |

Spinning holds the CPU, so never sleep while holding a spinlock. A mutex must be released by the task that took it and cannot be used in interrupt context.

## Lock variants and contexts

| Data touched from | Take it with |
|---|---|
| process context only | `mutex_lock`, or `spin_lock` |
| process and softirq | `spin_lock_bh` in process context |
| process and hard irq | `spin_lock_irqsave` in process context |
| handler only | `spin_lock` inside the handler |

## RCU in a few lines

```c
rcu_read_lock();
p = rcu_dereference(gp);
if (p) use(p->field);
rcu_read_unlock();

/* updater */
new = kmalloc(...); *new = *old; new->field = x;
rcu_assign_pointer(gp, new);
synchronize_rcu();       /* or call_rcu() */
kfree(old);
```

Readers never block and see either the old or the new version. The updater waits for a grace period before freeing.

## Lockdep

`CONFIG_PROVE_LOCKING` tracks lock classes and ordering edges. It reports an inversion the first time two orders are seen, even if no deadlock occurred, and it checks irq-safety rules. Reports name the locks and show a two-CPU scenario. It disables itself after the first report in a boot. Use `lockdep_assert_held()` and `might_sleep()` to document rules the code relies on.

## PREEMPT_RT

Spinlocks become sleeping locks built on rt-mutexes, and interrupt handlers run in threads. Code that assumes a spinlock disables preemption may break there. Use `raw_spinlock_t` only where true atomicity is needed.

## Self-check

Try each question before you read the answers below.

1. Data is shared between process context and a hard interrupt handler. How does process context take the lock?
2. Why can an RCU updater not free the old object right after publishing the new one?
3. What changes for spinlock users on a PREEMPT_RT kernel?

### Answers

1. With `spin_lock_irqsave`, so the interrupt cannot arrive on the same CPU and spin on a lock that CPU already holds.
2. Readers may still hold a pointer to it. Wait for a grace period with `synchronize_rcu` or `call_rcu` first.
3. Ordinary spinlocks become sleeping locks, so code that relied on them disabling preemption can break; use `raw_spinlock_t` only where needed.
