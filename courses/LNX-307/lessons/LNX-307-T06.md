# kdump and crash

This lesson follows the topic synthesis `synth/LNX-307/LNX-307-T06.md`, which carries the sources and the history.

## What you will be able to do

- Explain how kdump captures a kernel crash with a second kernel in reserved memory.
- Configure `crashkernel=`, `/etc/kdump.conf` and test with a deliberate crash.
- Take a first look at a vmcore with `crash` and read a panic and backtrace.

## How it works

A panicked kernel cannot be trusted to write its own memory out. kdump therefore boots a **second kernel**, loaded ahead of time with `kexec` into memory reserved by the boot parameter `crashkernel=`. The capture kernel sees the first kernel's memory as `/proc/vmcore`, filters and compresses it with `makedumpfile`, and writes it to a target, then reboots. Without the reservation there is no dump.

## Configure

```bash
dnf install kexec-tools            # Debian/Ubuntu: apt install linux-crashdump
kdumpctl estimate                  # suggested size
grubby --update-kernel=ALL --args="crashkernel=256M"   # or: kdumpctl reset-crashkernel
systemctl enable --now kdump ; kdumpctl status
```

`/etc/kdump.conf` chooses `path /var/crash` (or a dedicated filesystem, `nfs`, `ssh`), `core_collector makedumpfile -l --message-level 7 -d 31` (LZO compression; level 31 drops zero, cache, user and free pages) and `failure_action reboot`. Range form: `crashkernel=1G-4G:192M,4G-64G:256M,64G-:512M`. Sysctls decide what becomes a panic: `kernel.panic_on_oops`, `kernel.softlockup_panic`, `kernel.hardlockup_panic`, `kernel.unknown_nmi_panic`. Rebuild the kdump initramfs after kernel or storage changes.

## Test it

On a non-production system, in a window: `sysctl kernel.sysrq=1; echo c > /proc/sysrq-trigger`. The box reboots into the capture kernel, writes `/var/crash/<host>-<date>/vmcore` plus `vmcore-dmesg.txt`, then reboots again. For a hung VM: `virsh inject-nmi` with `unknown_nmi_panic=1`. Test after every kernel or hardware change; an untested kdump is a hope.

## First look with crash

```text
crash "$VMLINUX" /var/crash/<dir>/vmcore      # VMLINUX = debuginfo vmlinux matching the kernel
crash> sys        # version, panic string, uptime
crash> log        # kernel log up to the panic
crash> bt         # backtrace of the panicking task;  bt -a for all CPUs
crash> ps | grep UN ; kmem -i ; mod -S
```

Read in this order: `vmcore-dmesg.txt` or `log`, the panic string (NULL dereference, hard LOCKUP, Out of memory and no killable processes, hung_task), the `RIP` function plus offset, and any module name in brackets. A module name points at a driver; a matching vendor bug often exists. The debuginfo package must match the kernel exactly.

## Failure patterns

- `crashkernel` too small: the capture kernel runs out of memory and reboots without a file.
- kdump initramfs stale after an update: monitor `kdumpctl status` ([T03](lesson:LNX-307-T03)).
- Dumps hold secrets: treat them as sensitive.
- Hardware faults and watchdog resets never reach the handler; use `pstore`, serial console or `netconsole` ([T04](lesson:LNX-307-T04)).

An OOM-induced panic (`vm.panic_on_oom`, [T08](lesson:LNX-307-T08)) is a good reason to have a dump.
