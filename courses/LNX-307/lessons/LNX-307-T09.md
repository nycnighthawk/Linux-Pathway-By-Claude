# Reliable benchmarking

This lesson follows the topic synthesis `synth/LNX-307/LNX-307-T09.md`, which carries the sources and the history.

## What you will be able to do

- State a benchmark question and decision rule before running anything.
- Control and record the system under test, then repeat and report variance.
- Use `fio`, `iperf3` and CPU tests without measuring the cache, loopback or the load generator.

## Method

1. **Question and success measure**: "p99 below 5 ms at 20,000 IOPS for 8 KiB random 70/30 at queue depth 16" beats "is it fast".
2. **Characterise the real workload** (`iostat` request size, mix, concurrency; [T02](lesson:LNX-307-T02)).
3. **Control**: kernel and boot line, firmware, CPU governor (`cpupower frequency-info`, `tuned-adm active`), SMT, THP, NUMA (`numactl`), swap, background timers, fullness and preconditioning of SSDs. Record it beside the result.
4. **Isolate**: bypass the page cache (`--direct=1`) or use a set far larger than RAM; use two hosts for networks; pin CPU tests (`taskset`).
5. **Warm up** (`--ramp_time`) and run long enough for periodic effects.
6. **Repeat** at least three to five times, report median and spread, change one variable, interleave A and B.
7. **Observe while running** ([USE](lesson:LNX-307-T01) tools): name the limiting resource. This is "active benchmarking".
8. **Report** question, setup, versions, command lines, raw data, statistics, caveats.

## Tools and traps

```bash
fio --name=rr --filename=/dev/nvme1n1 --rw=randread --bs=4k --iodepth=32 --ioengine=io_uring \
    --direct=1 --runtime=120 --time_based --ramp_time=10 --group_reporting      # destroys nothing on reads only
iperf3 -s ;  iperf3 -c SERVER -t 30 -P 4                                         # compare -P 1 and -P 4
sysbench cpu --threads=4 run ; stress-ng --cpu 4 --metrics-brief
```

Traps: buffered I/O reading cache; writes to a real device (data loss); queue depth 1 sold as capability; loopback network tests; one TCP stream capped by one core's softirq (compare `-P`); governor `powersave`; sampling a mean when tail latency matters; **coordinated omission** (a closed-loop client slows when the server stalls and under-reports latency; use open-loop tools such as `wrk2`, `vegeta`, or HdrHistogram correction). Never average percentiles across runs; merge histograms. A difference smaller than the run-to-run spread is not evidence.

## Worked example

`fio --rw=read --bs=1M --size=1G` reported 2.1 GB/s on a SATA SSD rated 550 MB/s: it read the page cache. With `--direct=1`, a 50 GB file and 120 s it gave 520 MB/s and `iostat -x` agreed. Three `sysbench cpu` runs gave 4,800, 5,300 and 6,100 events/s until the governor was set to `performance`: then 6,080, 6,110, 6,095.

## Self-check

1. Why must a disk benchmark use `--direct=1` or a large file?
2. What is coordinated omission?
3. How many runs, and how do you report them?
4. Why watch `mpstat` during an `iperf3` test?
