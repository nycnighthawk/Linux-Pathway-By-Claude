## What you will be able to do

## The OOM killer

Linux overcommits memory. When an allocation cannot be satisfied and reclaim fails, the kernel kills a process chosen by `oom_score` (size, privilege), shifted by `/proc/PID/oom_score_adj` (-1000 immune, +1000 first). The log shows `invoked oom-killer`, zone statistics, a task table and `Out of memory: Killed process PID (name) ... anon-rss ...`.

```bash
journalctl -k -g 'Out of memory'      # or: dmesg -T | grep -i -E 'killed process|oom'
systemctl status UNIT                 # Result: oom-kill
cat /sys/fs/cgroup/system.slice/UNIT.service/memory.events    # oom, oom_kill counters
```

Scope matters: `constraint=CONSTRAINT_NONE` means the machine ran out; `CONSTRAINT_MEMCG` with `oom_memcg=/system.slice/shop.service` means a limit was hit while the host had memory. The victim is not always the culprit; read the `rss` column. Process killed by SIGKILL logs nothing itself, so a missing shutdown message is the clue. Exit code 137 in containers is the same event.

## cgroup v2

Check `stat -fc %T /sys/fs/cgroup` (`cgroup2fs`). One tree; controllers are enabled per subtree through `cgroup.subtree_control`; systemd owns it.

| File | Meaning |
|---|---|
| `memory.min` / `memory.low` | hard / best-effort protection |
| `memory.high` | throttle: slows and reclaims, never kills by itself |
| `memory.max` | hard limit: OOM kill inside the group |
| `memory.swap.max`, `memory.oom.group` | swap limit; kill the whole group together |
| `memory.events` | `low high max oom oom_kill` counters |
| `cpu.max` (`200000 100000` = two CPUs), `cpu.weight`, `cpu.stat` | quota, share, `nr_throttled` |
| `io.max` (`8:0 wbps=10485760`), `io.weight` | per-device limits |
| `pids.max` | process limit |
| `memory.pressure`, `cpu.pressure`, `io.pressure` | PSI per group |

systemd names: `MemoryMin= MemoryLow= MemoryHigh= MemoryMax= MemorySwapMax= CPUQuota= CPUWeight= IOWriteBandwidthMax= TasksMax= OOMPolicy= OOMScoreAdjust=`.

```bash
systemd-run --scope -p MemoryHigh=150M -p MemoryMax=200M -p MemorySwapMax=0 stress-ng --vm 1 --vm-bytes 400M
systemctl set-property myapp.service MemoryMax=1G CPUQuota=150%
systemd-cgtop
```

A good service sets `MemoryHigh` a little under `MemoryMax`: a leak slows down and shows in `memory.events` `high` instead of dying. Docker and Kubernetes write the same files (`--memory`, `limits.memory`). `systemd-oomd` and `earlyoom` act on pressure before the kernel does ([T01](lesson:LNX-307-T01) pressure files).

## Failure patterns

- `MemoryMax` too low with `Restart=always`: a kill loop that looks like instability.
- Alerting on `memory.current`, which includes reclaimable cache; use `memory.stat` anon and the working set.
- JVM native and direct memory beyond the heap setting, killed at the container limit.
- CPU quota throttling creating latency spikes (`nr_throttled`).

Alert on `oom_kill` increments and memory pressure ([T03](lesson:LNX-307-T03)); keep a dump or heap capture ([T06](lesson:LNX-307-T06)) for repeated events.
