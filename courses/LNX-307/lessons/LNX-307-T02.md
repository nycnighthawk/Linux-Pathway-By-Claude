# sysstat, vmstat, iostat, pidstat

This lesson follows the topic synthesis `synth/LNX-307/LNX-307-T02.md`, which carries the sources and the history.

## What you will be able to do

- Turn cumulative kernel counters into rates and say why the first report line is discarded.
- Choose between `vmstat`, `mpstat`, `iostat`, `pidstat` and `sar` for a question.
- Enable and read `sar` history, and name the process behind a disk or CPU problem.

## Counters become rates

The kernel keeps counters that grow from boot (`/proc/stat`, `/proc/diskstats`, `/proc/net/dev`, `/proc/vmstat`). One reading says nothing about now: you need two readings and a division by the interval. All the tools below do that for you when you give an interval. Without one they print the average since boot, which is nearly useless on a machine that has run for months. With an interval, the first line of `vmstat`, `iostat` and `mpstat` is still the since-boot average, so ignore it.

## The tools

| Command | Answers | Key columns |
|---|---|---|
| `vmstat 1` | overall CPU, memory, swap, I/O | `r` runnable, `b` blocked, `si`/`so` swap, `wa` I/O wait, `st` steal |
| `mpstat -P ALL 1` | is load spread over cores | per-core `%usr %sys %iowait %soft %steal` |
| `iostat -xz 1` | per-disk load and latency | `r/s w/s`, `rkB/s`, `aqu-sz`, `r_await`, `w_await`, `%util` |
| `pidstat -u/-r/-d/-w 1` | which process | CPU, memory faults, disk KB/s, context switches |
| `sar -u/-r/-d/-n DEV/-q` | what happened earlier | the same, from recorded files |

Read `await` as what the application feels (queue plus service time) and queue size as saturation. `%util` was designed for one-request-at-a-time disks; on NVMe and RAID it can reach 100% without saturation. In `free`, use the `available` column, not `free`: the kernel uses spare memory as cache on purpose. `wa` means CPUs are idle while tasks wait for I/O; `st` means a hypervisor is taking CPU time from this guest.

## Recording history with sar

The collector `sa1` runs `sadc` and appends to `/var/log/sa/saDD`; `sa2` writes the daily report. On RHEL family systems the timers `sysstat-collect.timer` (every 10 minutes) and `sysstat-summary.timer` do the work, and `HISTORY` in `/etc/sysconfig/sysstat` sets retention. On Debian and Ubuntu set `ENABLED="true"` in `/etc/default/sysstat`. Ten minutes hides short spikes: shorten the interval with a timer override.

```bash
sar -u -f /var/log/sa/sa14 -s 15:00:00 -e 15:30:00    # CPU, 3:00-3:30 pm on the 14th
sar -q -f /var/log/sa/sa14 -s 15:00:00 -e 15:30:00    # run queue and load
sadf -j /var/log/sa/sa14 -- -u                         # JSON for scripts
```

## Symptom to process in two minutes

`uptime` (trend) then `vmstat 1 5` (queue, swap, wait), `mpstat -P ALL 1 3` (balance), `iostat -xz 1 3` (disks), `sar -n DEV 1 3` (interfaces), `pidstat 1 3` and `pidstat -d 1 3` (the offender). This is the [USE method](lesson:LNX-307-T01) executed with counters. For the cause inside the process, move on to [tracing](lesson:LNX-307-T05); for fleet-wide history, see [Prometheus](lesson:LNX-307-T03).

## Worked example

`iostat -xz 1` shows `sdb` at 98% util, `w_await` 40 ms, `aqu-sz` 12. `vmstat` shows `wa` 25. `pidstat -d 1` lists `backup.sh` writing 90 MB/s. Throttle the job (an `io.max` limit, see [cgroups](lesson:LNX-307-T08)) or move it off-peak. The mistake to avoid: running `iostat` without an interval and reading the since-boot 2%.
