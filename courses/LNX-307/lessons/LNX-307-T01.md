## What you will be able to do

- Write a one-page runbook that links an alert to ordered checks, a decision and a rollback.

## Two questions, two methods

Troubleshooting without a method turns into guessing with whatever tool you know best. Two short rules replace that.

**USE** is for machines: for every resource, check **U**tilisation (how busy), **S**aturation (how much work is waiting) and **E**rrors (counted faults). Resources are CPUs, memory, disks, network interfaces, and also software limits such as file descriptors. Check errors first (quick, unambiguous), then saturation, then utilisation. Saturation matters most: a disk at 100% with no queue is healthy, a CPU at 60% with a long run queue is not.

**RED** is for services that answer requests: **R**ate (requests per second), **E**rrors (failed fraction) and **D**uration (a latency distribution, read as percentiles, never as a mean). RED tells you whether users are hurt and which service is guilty; USE then tells you which resource of that service's host is the cause. Details on tools are in [sysstat and friends](lesson:LNX-307-T02) and [Prometheus](lesson:LNX-307-T03).

## The USE table for Linux

| Resource | Utilisation | Saturation | Errors |
|---|---|---|---|
| CPU | `mpstat -P ALL 1` | `vmstat 1` column `r` above core count; `/proc/pressure/cpu` | `dmesg` machine-check lines |
| Memory | `free -m` (read `available`) | `vmstat` `si`/`so`; `/proc/pressure/memory` | OOM kills in `journalctl -k` |
| Disk | `iostat -xz 1` `%util` | queue size and `await`; `/proc/pressure/io` | kernel I/O errors, SMART |
| Network | `sar -n DEV 1` vs link speed | drops, backlog (`ss -ltn`), `nstat` | `ip -s link`, `ethtool -S` |
| Limits | `cat /proc/sys/fs/file-nr` | blocked tasks (`vmstat` `b`) | EMFILE or EAGAIN in logs |

Pressure files (`/proc/pressure/{cpu,memory,io}`) report the share of time tasks were stalled, with `some` (at least one task) and `full` (all non-idle tasks) lines averaged over 10, 60 and 300 seconds. They are the closest thing Linux has to a direct saturation number, and each cgroup has its own copy (see [OOM and cgroups v2](lesson:LNX-307-T08)).

## Runbooks

A runbook is the method frozen for one alert. Keep it to one page:

```text
Alert:   DiskQueueDeep on <host>        Impact: slow writes for services on this host
Checks:  1. iostat -xz 1 3   -> queue size above 4? (no: false alarm, stop)
         2. dmesg -T | grep -i 'i/o error'  -> yes: escalate to storage
         3. pidstat -d 1 5   -> who writes most? known job?
Act:     known job -> throttle it; unknown -> capture evidence, escalate
Rollback / owner / last verified: ...
```

Link it from the alert annotation (`runbook_url`), test it in a drill ([break/fix drills](lesson:LNX-307-T07)) and put a "last verified" date on it, because runbooks decay faster than systems change.

## Worked example

A web server is slow. Errors: `dmesg -T` and `ip -s link` are clean. Saturation: `vmstat 1` shows `r`=3 on eight cores, `si`/`so`=0, `b`=0. Utilisation: `mpstat -P ALL 1` shows one core at 100% and seven near idle. Reading: no resource is exhausted overall, but one thread is CPU-bound. Next step: `pidstat -u 1` to name it, then profile it ([strace, perf, eBPF](lesson:LNX-307-T05)). A host-wide "CPU 12% busy" average would have hidden this.

## Common mistakes

- Paging on a cause (CPU above 80%) instead of a symptom (latency, errors). See the alerting rules in [T03](lesson:LNX-307-T03).
- Reading load average as saturation without knowing the core count.
- Treating `%util` of a parallel device (NVMe) as proof of saturation.
