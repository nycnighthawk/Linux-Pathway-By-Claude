# Break/fix drills

This lesson follows the topic synthesis `synth/LNX-307/LNX-307-T07.md`, which carries the sources and the history.

## What you will be able to do

- Follow an eight-step troubleshooting method under time pressure.
- Diagnose the main fault families: service start, disk, network, slowness, boot, permissions, limits.
- Verify that a fix works and survives a restart, and write a short blameless debrief.

## The method

1. Define and reproduce the symptom exactly (`curl -sv`, `systemctl status`, `journalctl -u UNIT -b`).
2. Ask what changed (`rpm -qa --last`, `ls -lt /etc`, `last -x`).
3. Apply [USE](lesson:LNX-307-T01) to the host: errors first (`dmesg -T`, `journalctl -p err -b`).
4. Walk the dependency chain from the symptom down; test each link with the simplest tool.
5. Bisect: split the system and test the midpoint.
6. Change one thing at a time; keep a copy (`cp -a f f.orig`) and a command log.
7. Verify the outcome and persistence (restart and reboot); add a check to monitoring ([T03](lesson:LNX-307-T03)).
8. Write the cause, timeline and what would have detected it sooner.

## Fault families

| Symptom | First commands | Typical cause |
|---|---|---|
| Unit will not start | `systemctl status`, `journalctl -xeu`, `systemctl cat`, `systemd-analyze verify` | exit 203/EXEC bad `ExecStart`; 217/USER missing user; port taken; SELinux denial |
| Disk "full" | `df -h`, `df -i`, `du -xh --max-depth=1`, `lsof +L1` | inode exhaustion; deleted-but-open file; unrotated log |
| Network | `ip -br addr`, `ip route get`, `getent hosts`, `ss -ltnp`, `nft list ruleset`, `tcpdump` | wrong route, firewall, MTU, DNS |
| Slow | `vmstat`, `iostat`, `pidstat` ([T02](lesson:LNX-307-T02)), then tracing ([T05](lesson:LNX-307-T05)) | swap, runaway process, throttling, steal |
| No boot | `journalctl -b -1`, `/etc/fstab`, `dracut -f`, `rd.break` | bad fstab entry without `nofail`, stale initramfs |
| Permission denied | `namei -l PATH`, `ls -Z`, `ausearch -m avc` | missing x on a parent dir, SELinux |
| Limits | `ulimit -n`, `/proc/PID/limits`, `ss -s` | descriptors, PIDs, ports, [OOM](lesson:LNX-307-T08) |

Drills usually plant a visible fault that hides a deeper one: fix the unit path, then meet the busy port. Grade the **outcome** (service answers, unit enabled), not a particular command.

## Worked example

Symptom: the app is down after a config change. `systemctl status myapp` gives exit 203/EXEC: the path in `ExecStart` is wrong. Fix it with `systemctl edit myapp`, restart: second failure, "address already in use" in `journalctl -u myapp`. `ss -ltnp` names the other owner of the port. Change the app's port, not the other service. Check `systemctl is-enabled myapp` and fetch the page.

Rule of evidence: collect before you restart. A reboot that clears an OOM kill destroys the proof ([T08](lesson:LNX-307-T08)).

## Self-check

2. `df -h` shows 60% used but writes fail. Which two checks come next?
3. Why grade a drill on outcome, not on the fix?
4. What must you do before restarting a misbehaving production service?
