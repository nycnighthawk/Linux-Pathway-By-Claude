# Prometheus, Grafana, alerting

This lesson follows the topic synthesis `synth/LNX-307/LNX-307-T03.md`, which carries the sources and the history.

## What you will be able to do

- Describe the Prometheus data model and the four metric types.
- Write PromQL for USE and RED questions and use `rate()` correctly.
- Write alerting rules with `for`, labels and a runbook annotation, and route them with Alertmanager.

## Parts

Prometheus **scrapes** HTTP endpoints (`/metrics`) listed in `prometheus.yml`, stores samples in a local time-series database and evaluates rules. **Exporters** turn other systems into metrics: `node_exporter` (port 9100) for hosts. **Alertmanager** (9093) groups, deduplicates, silences and routes alerts. **Grafana** (3000) draws dashboards; its provisioning files keep dashboards in version control. The pull model gives a free liveness signal: when a scrape fails, `up` is 0.

A series is a name plus labels, e.g. `node_cpu_seconds_total{cpu="0",mode="idle"}`. Types: **counter** (only rises, use `rate()`), **gauge** (moves both ways), **histogram** (`_bucket`, `_sum`, `_count`, used for quantiles) and summary.

## PromQL you need

```promql
1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))     # CPU busy
node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes               # memory left
rate(node_disk_io_time_seconds_total[5m])                                 # like iostat %util
sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))   # error ratio
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))  # p99
```

The first three are [USE](lesson:LNX-307-T01) questions, the last two are RED. Use a range of at least four scrape intervals inside `rate()`. Never average percentiles. `rate(c[5m])` equals (last minus first) divided by the window seconds, after handling counter resets.

## Alerting rules

```yaml
groups:
- name: host
  rules:
  - alert: HighErrorRatio
    expr: sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m])) > 0.02
    for: 10m
    labels: {severity: page}
    annotations:
      summary: "5xx ratio above 2 percent"
      runbook_url: https://wiki.example.org/runbooks/high-error-ratio
```

A true expression is *pending* until `for` elapses, then *firing*; that hides blips. Page on symptoms users feel, keep the count low, and link every alert to a dashboard and runbook. Cause conditions (disk will fill in 4 hours: `predict_linear(...)`) are tickets unless time is short. Check with `promtool check rules` and test with `promtool test rules`. Alertmanager routes by label (`severity`, `team`), with `group_by`, `group_wait`, `group_interval`, `repeat_interval`, and `inhibit_rules` (host down hides its service alerts).

## Failure patterns

- A label with unbounded values (user id, URL with ids) explodes series and memory: the server may be OOM-killed ([T08](lesson:LNX-307-T08)).
- Renamed exporter metrics silently break alerts: test rules in CI.
- An alert on absence is needed too: `absent(up{job="x"})`, plus a watchdog alert.
- Counters graphed raw instead of through `rate()`.
