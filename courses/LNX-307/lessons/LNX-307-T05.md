# strace, perf, eBPF (bcc, bpftrace)

This lesson follows the topic synthesis `synth/LNX-307/LNX-307-T05.md`, which carries the sources and the history.

## What you will be able to do

- Use `strace` to find failing system calls, slow calls and hangs, and know its cost.
- Sample a process with `perf` and read a profile or flame graph.
- Run bcc tools and write bpftrace one-liners that aggregate in the kernel.

## Which tool, when

Counters ([T02](lesson:LNX-307-T02)) say which resource is stressed. These tools say what the software is doing. Pick the cheapest tool that can answer: `strace` for behaviour (which file, which call blocks), `perf` for where CPU time goes, eBPF for latency distributions and kernel events with low overhead.

## strace

```bash
strace -f -tt -T -o /tmp/app.trace ./app           # follow children, timestamps, time per call
strace -f -e status=failed ./app                   # only failing calls (ENOENT, EACCES ...)
strace -c -p 1234                                  # summary on exit: calls, errors, time
strace -p 1234 -e trace=network                    # attach to a running process
```

Look for `ENOENT` runs (config searched in many places), `EACCES` (permissions), a `connect` or `poll` that takes seconds (`-T`), many tiny `write` calls, and `futex` waits (lock contention). Attaching needs ptrace permission (`kernel.yama.ptrace_scope`, `SYS_PTRACE` in containers). `ptrace` stops the process on every call, so a busy service can slow by 10 times or more: never attach to a production process at peak without a plan.

## perf

```bash
perf stat -d ./app                       # IPC, cache and branch misses
perf record -F 99 -g -p 1234 -- sleep 30 ; perf report --stdio
perf trace -p 1234                       # syscall view with less overhead than strace
```

99 Hz avoids lockstep with timers. `-g` needs frame pointers or `--call-graph dwarf` to unwind stacks. A flame graph (`perf script | stackcollapse-perf.pl | flamegraph.pl`) shows share of samples as width, not time on the x axis. `perf` shows on-CPU time only: a thread waiting on a lock or disk needs off-CPU analysis. In a VM, hardware counters may be missing. `kernel.perf_event_paranoid` limits unprivileged use.

## eBPF: bcc and bpftrace

The kernel verifies small programs and runs them at probes (tracepoints, kprobes, uprobes), keeping aggregates in maps. Needs root or `CAP_BPF` plus `CAP_PERFMON`.

```bash
execsnoop ; opensnoop -p 1234 ; biolatency -D 10 1 ; runqlat 5 1 ; tcpretrans     # bcc tools
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'
bpftrace -e 'tracepoint:block:block_rq_issue { @bytes = hist(args->bytes); }'
bpftrace -l 'tracepoint:sched:*'
```

Tracepoints are stable interfaces, kprobes on internal functions are not. Filter early (`/pid == 1234/`), limit time (`timeout 20`), and aggregate in place (`count`, `sum`, `hist`) so only a summary crosses to user space. Unfiltered scheduler or network probes can add visible load. Treat BPF privileges as close to root.

## Worked example

A service fails at start with only "configuration error". Run the binary by hand: `strace -f -e status=failed ./svc --config /etc/svc.conf`. The last lines show `openat(... "/etc/svc/tls/server.key" ...) = -1 EACCES`. A permission problem, found in a minute. Another case: a job takes 4 s per request with 5% CPU. `strace -c -f -p` shows `poll` dominating and `-T -e trace=connect` shows a 3.0 s DNS wait: a resolver fix, not a code fix.
