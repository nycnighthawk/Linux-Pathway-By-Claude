# FreeIPA and IdM: replicas, HBAC and sudo rules

This lesson follows the topic synthesis `synth/LNX-301/LNX-301-T06.md`, which carries the sources and the history.

## What you will be able to do

- Name the parts of an IdM server (389 DS, KDC, Dogtag CA, httpd, optional DNS) and what each stores.
- Install a first server and a replica and read the replication topology.
- Write HBAC rules, test them with `ipa hbactest`, and disable the default `allow_all`.
- Write sudo rules that clients fetch through SSSD, and know why a rule may never match.

## Architecture in one paragraph

IdM integrates an LDAP directory, a Kerberos KDC (which reads principals from LDAP), a certificate authority, optional DNS and a web and JSON-RPC front end behind one object model. An administrator edits users, hosts and rules; the system keeps the parts in agreement. Clients run SSSD with `id_provider = ipa`, plus `certmonger` for host certificates, and pull policy with their own credentials.

```bash
ipa-server-install --realm=EXAMPLE.COM --domain=example.com --setup-dns --forwarder=10.0.0.1
ipa-client-install --domain=example.com --realm=EXAMPLE.COM
ipa-replica-install --setup-ca --setup-dns
ipa topologysegment-find domain
```

## Replicas and topology

Servers replicate multi-supplier through **segments** in the `domain` suffix, and in the `ca` suffix for the CA. Give each server at least two connections, no more than four, so that losing one server does not split the graph. Exactly one CA server is the **renewal master**; plan how to move that role (`ipa config-mod --ca-renewal-master-server`). Remove dead servers with `ipa server-del`, never by deleting the host. Prefer rebuilding a replica to restoring an old backup. Run `ipa-healthcheck` on a timer.

## HBAC

An HBAC rule joins users, hosts and PAM services. Access is granted if **any** enabled rule matches, so the default `allow_all` makes every other rule pointless until you disable it.

```bash
ipa hbacrule-add db-ssh
ipa hbacrule-add-user db-ssh --groups=dba
ipa hbacrule-add-host db-ssh --hostgroups=dbservers
ipa hbacrule-add-service db-ssh --hbacsvcs=sshd
ipa hbacrule-disable allow_all
ipa hbactest --user=alice --host=db1.example.com --service=sshd
```

`hbactest` names the matched and unmatched rules; use it first when a login is denied after the password was accepted.

## Sudo rules

A sudo rule names who, where and which commands, optionally with options such as `!authenticate`. Clients need `sudoers: files sss` and the `sudo` responder in SSSD; `ipa-client-install` sets both. Commands are matched literally, so on a system where `/bin` links to `/usr/bin` a rule for the wrong path never applies. Use `sudo -l`, and `sss_cache -E` while you test.

## Worked example

A contractor in group `web` can ssh into a database host. The `db-ssh` rule is correct. `ipa hbactest` for the contractor shows the matched rule is `allow_all`. Disabling it closes the hole, and also exposes other broken access, such as a cron job using the `crond` service, which you now add deliberately.
