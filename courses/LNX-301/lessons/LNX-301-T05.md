# Joining a genuine Windows AD

This lesson follows the topic synthesis `synth/LNX-301/LNX-301-T05.md`, which carries the sources and the history.

## What you will be able to do

- Choose a join identity and method that follows least privilege (delegation, pre-staging, one-time passwords, offline join).
- List the domain-side controls that touch a Linux member: LDAP signing, encryption types, GPO, DNS updates, sites.
- Write a join plan the AD team can approve and a rollback for it.
- Verify a join from both sides.

## What is different from a lab domain

The commands match [the Samba join](lesson:LNX-301-T04). The difference is ownership: another team runs the directory, and your join touches their objects and policy. Four decisions come before any command.

**Who joins.** A joining user needs the right to create or reuse the computer object. The default quota (`ms-DS-MachineAccountQuota`, ten machines per user) lets ordinary users create objects, and Microsoft discourages it. The usual answer is a service account with only *Create Computer objects* on one OU. Pre-staging goes further: the AD team creates `APP01$` and a one-time password, and `realm join --one-time-password` enrols the host without any user credential on it. Windows offline join (`djoin`) gives the same property, and Samba has `net offlinejoin`.

**Where the object lives.** Pass `--computer-ou`; the default Computers container is rarely managed.

**ID numbers.** Algorithmic SID-based mapping needs nothing from AD. Reading `uidNumber` needs data work first, because users without it are invisible to Linux.

**Which controls apply.** GPO logon rights are evaluated by SSSD (`ad_gpo_access_control`: `disabled`, `permissive`, `enforcing`). Pilot in `permissive`. LDAP signing makes plain `ldapsearch -x` fail; use `-Y GSSAPI` or LDAPS. Encryption types matter: a server whose machine password predates the removal of RC4 may have no AES keys until it is rotated (`adcli update`). DNS updates by SSSD (`dyndns_update`) need a zone that allows secure updates. If the client's subnet is not defined in an AD site, it picks distant DCs and logins crawl (`ad_site` overrides).

## Verification from both sides

```bash
realm list                              # configured: kerberos-member
klist -ke /etc/krb5.keytab              # host/ and HOST$ principals with AES
getent passwd jsmith@corp.example.com
sssctl domain-status corp.example.com
```

The AD team confirms the object in its OU, the SPNs and the operating-system attributes. Rehearse `realm leave --remove` on a throwaway host.

## Worked example

After a rebuild, `realm join` returns `Insufficient access`. An old `APP01$` sits in another OU owned by the Windows team; the delegated account cannot modify it. The fix is a request, not a stronger account: the AD team moves or deletes the object, or the host gets a new name.
