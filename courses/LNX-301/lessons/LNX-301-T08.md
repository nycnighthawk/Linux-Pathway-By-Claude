## Mapping

With `ldap_id_mapping = True`, SSSD hashes the domain SID to choose a slice inside a large range. The range starts at `ldap_idmap_range_min` (default 200000), each slice is `ldap_idmap_range_size` wide (default 200000), and a user's UID is the slice base plus the RID. For slice 3: 200000 + 3 x 200000 = 800000, so RID 1105 becomes 801105. A RID that does not fit the slice cannot be mapped and is logged; a bigger slice fixes it but renumbers everyone. With `False`, SSSD reads `uidNumber` and `gidNumber`; users without them are invisible, and `min_id`/`max_id` guard against dangerous values. Mixed hosts (winbind `tdb`, `rid`, SSSD) disagree without any error, which shows up as wrong owners on NFS.

## The toolbox

```bash
sssctl domain-list ; sssctl domain-status corp.example.com -o     # online? which servers?
sssctl user-checks alice -a acct -s sshd                           # NSS + PAM account result
sssctl config-check                                                # validate before restart
sssctl debug-level 6 ; sssctl logs-fetch /tmp/sssd-logs.tar
sssctl analyze request list ; sssctl analyze request show 5       # follow one request across logs
sss_cache -u alice ; sss_cache -E                                  # mark stale, keep credentials
sssctl cache-remove                                                # stop, delete caches, restart
```

Logs live in `/var/log/sssd/`: `sssd_nss.log`, `sssd_pam.log`, `sssd_<domain>.log` (LDAP and Kerberos conversations), and helper logs such as `krb5_child.log`. The default level records serious failures only; level 6 is a good start for authentication problems.

## A method

1. `getent passwd user@domain`: does the OS see it? If not, check nsswitch and the daemon.
2. `sssctl domain-status`: offline means a connection problem, not an identity problem.
3. `sss_cache -E` and repeat: if the answer changes, it was staleness.
4. Compare `id` on two hosts: different numbers mean different mapping settings.
5. `sssctl user-checks -a acct`: access rules after a successful lookup.
6. `debug_level = 6` and read `krb5_child.log` for authentication failures.

## Worked example

Logins take 21 seconds. `sssctl domain-status -a` lists three servers; `nc -z -w 3 dc2 389` fails. SSSD waits for each timeout before trying the next. Fixing the firewall, or setting `ad_server` to reachable controllers, removes the delay; the log line `Marking server as not working` would have shown it at level 6.
