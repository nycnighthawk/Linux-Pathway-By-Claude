## How it works

A directory is a tree of entries. Each entry has a distinguished name such as `uid=alice,ou=people,dc=example,dc=com`, one or more `objectClass` values and attributes whose types come from a schema. The server (`slapd` in OpenLDAP) stores the tree in an `mdb` database, answers LDAPv3 operations (bind, search, compare, add, modify, delete) and enforces access rules. Clients identify themselves with a bind: a simple bind sends a DN and password, a SASL bind (`-Y GSSAPI`, `-Y EXTERNAL`) proves identity another way.

A search has four inputs. The **base** says where to start, the **scope** (`base`, `one`, `sub`) how deep to go, the **filter** such as `(&(objectClass=posixAccount)(uid=alice))` what to match and the **attribute list** what to return. Most client failures reduce to a wrong base, a scope that is too narrow or a filter that the schema does not support.

## Protect the data

Access rules are ordered. `slapd` takes the **first** `to` clause that matches the request, so a broad rule placed ahead of a narrow one silently exposes data. A safe starting set:

```text
access to attrs=userPassword
    by self write
    by anonymous auth
    by * none
access to *
    by users read
    by * none
```

Test a rule before you rely on it: `slapacl -f slapd.conf -b uid=alice,ou=people,dc=example,dc=com -D uid=bob,ou=people,dc=example,dc=com userPassword/read` prints `DENIED` or `ALLOWED`. Add equality indexes for the attributes that logins search (`uid`, `uidNumber`, `gidNumber`, `memberUid`), because an unindexed filter scans the database.

## Protect the wire

A simple bind sends the password in clear unless the channel is protected. `ldaps://` wraps the connection in TLS from the first byte (port 636). StartTLS upgrades a connection on port 389 with an extended operation. The server certificate must match the name in the URI. On the client, `TLS_CACERT` points at the CA file and `TLS_REQCERT demand` makes a bad certificate fatal. `never` keeps the encryption but accepts any server, which defeats the purpose. With `ldapsearch`, `-Z` tries StartTLS and continues without it on failure; `-ZZ` aborts.

## Worked example

A directory exported from AD stores group members as `member: <DN>`. Linux shows only the primary group for `alice`. The client is reading `memberUid` (RFC 2307), while the data uses `member` (the bis layout). The fix lives in the client: tell SSSD to use `ldap_schema = rfc2307bis`. The first probe that localises this is a plain search with the same base and a filter for the group:

```bash
ldapsearch -x -ZZ -H ldap://ldap.example.com -b ou=groups,dc=example,dc=com -LLL '(cn=dba)' member memberUid
```

If `member` is filled and `memberUid` is empty, the schema setting is the issue, not the network.

## Backups and replication

`slapcat` and `slapadd` dump and restore through the files, so they work with the network down. Replication uses `syncrepl`; multi-provider pairs resolve concurrent writes by timestamp, so send writes to one node at a time and keep the other for reads and failover.
