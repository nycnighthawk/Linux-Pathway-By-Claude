# IdM to AD trust

This lesson follows the topic synthesis `synth/LNX-301/LNX-301-T07.md`, which carries the sources and the history.

## What you will be able to do

- Explain what a cross-forest trust gives and why IdM does not need to enrol hosts in AD.
- Distinguish trust controllers and trust agents, and one-way from two-way trusts.
- Choose an ID range type and understand why it is hard to change.
- Give AD groups access to IdM hosts through external groups wrapped in POSIX groups.

## The idea

The IdM domain presents itself to AD as a separate forest with one domain. A forest trust links it to the AD forest root. AD users keep their AD password and Kerberos; IdM clients resolve them through an IdM trust controller or agent, and the IdM KDC accepts cross-realm tickets. AD never stores an object per Linux host, and Linux policy (HBAC, sudo, SSH keys, certificates) stays in IdM.

## Roles

A **trust controller** runs the Samba components for the trust, can establish it and processes Kerberos for AD users. A **trust agent** resolves AD identities for clients but cannot process AD Kerberos requests. An ordinary IdM server does neither, so clients enrolled against it do not see AD users. Place at least two controllers, and one at each remote site.

## One-way and two-way

In a one-way trust IdM trusts AD, so AD users reach IdM resources. A two-way trust also lets IdM users authenticate to AD, but IdM has no global catalog, so they can reach only Kerberized services that need no access check. In practice a two-way trust adds little.

## Setup in outline

```bash
ipa-adtrust-install --add-sids
ipa dnsforwardzone-add ad.example.net --forwarder=10.1.0.10 --forward-policy=only
ipa trust-add --type=ad ad.example.net --admin Administrator --password
ipa trust-show ad.example.net
ipa-healthcheck --source=ipahealthcheck.ipa.trust
```

DNS must work both ways (conditional forwarders), time must agree, and ports 53, 88, 464, 389, 3268, 135 and 445 (plus high RPC ports) must pass. The ID range type defaults to `ipa-ad-trust` (derive from SIDs); `ipa-ad-trust-posix` reads `uidNumber` and `gidNumber` from AD. Pick once.

## AD groups in policy

HBAC and sudo rules take POSIX groups. Create a non-POSIX external group (`ipa group-add --external ad_admins_external`), add the AD group to it (`group-add-member --external 'ad.example.net\Domain Admins'`), and nest it in a POSIX group (`ipa group-add ad_admins`, then add the external group as a member). Use `ad_admins` in rules. Per-user overrides (`ipa idoverrideuser-add`) set shells and SSH keys on the Linux side only.

## Worked example

`id jsmith@ad.example.net` works on `ipa1` but not on a client of `ipa3`. `ipa server-role-find` shows `ipa3` is neither controller nor agent. Either enrol the client against a trust-capable server or run `ipa-adtrust-install` on `ipa3`.
