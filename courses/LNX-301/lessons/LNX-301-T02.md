# Kerberos, keytabs and GSSAPI SSH

## What you will be able to do

- Describe the AS, TGS and AP exchanges and say what is encrypted with which key.
- Create a service principal and a keytab with `kadmin.local`, and test it with `kinit -k -t`.
- Configure OpenSSH for GSSAPI single sign-on and map the principal to a local account.
- Diagnose clock skew, name mismatches and stale keytab key versions with `klist`, `kvno` and `KRB5_TRACE`.

## How it works

A realm (upper-case, usually the DNS domain) has a Key Distribution Center with two halves. The **AS exchange** gets a ticket-granting ticket: the client names itself, proves knowledge of its key through pre-authentication, and the KDC replies with a TGT sealed under the `krbtgt` key and a session key the client can open with the user's key. The **TGS exchange** trades the TGT plus an authenticator for a service ticket sealed under the service's key. In the **AP exchange** the client presents that ticket and a fresh authenticator; the service opens the ticket with the key from its keytab. No password reaches the service. Everything depends on time: authenticators carry timestamps and the default tolerance is five minutes.

## Everyday commands

```bash
kinit alice                                   # get a TGT
klist -e                                      # tickets with encryption types
kvno host/web1.example.com                    # fetch a service ticket, print its key version
klist -ke /etc/krb5.keytab                    # keytab entries with kvno and enctype
kinit -k -t /etc/krb5.keytab host/web1.example.com
KRB5_TRACE=/dev/stderr kinit alice            # trace discovery, pre-auth and errors
```

## Keytabs

A keytab holds long-term keys. Treat it as a password: root-owned, mode 0600, one principal per host. `ktadd` exports **and rotates** the key, so a second `ktadd` for the same principal makes the first file stale (`Decrypt integrity check failed`). `klist -k` shows the key version number; compare it with `kvno` from a client to find a stale copy.

## SSH with GSSAPI

On the server: `GSSAPIAuthentication yes`, `GSSAPICleanupCredentials yes`, `GSSAPIStrictAcceptorCheck yes`, and the host principal `host/<fqdn>` in `/etc/krb5.keytab`. On the client: `GSSAPIAuthentication yes` and, only for hosts you trust, `GSSAPIDelegateCredentials yes`. Authentication proves who the principal is; **authorisation** still needs an account. The principal maps to a local user through `.k5login`, `auth_to_local` rules or, in a managed estate, SSSD (see [SSSD, nsswitch and PAM](lesson:LNX-301-T03)). Hardening baselines often turn GSSAPI off by default; a realm member turns it on deliberately.

## Worked example

`ssh web1` asks for a password although `klist` shows a valid TGT. `ssh -vvv` ends with `Server not found in Kerberos database`. The client built `host/web1.example.com` from a CNAME and asked for `host/www.example.com`, which does not exist. Fixes: connect by the real FQDN, add an alias principal, or set the canonicalisation options deliberately. Confirm with `kvno host/www.example.com` (fails) and `kvno host/web1.example.com` (works).
