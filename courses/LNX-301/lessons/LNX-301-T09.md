# ansible-freeipa automation

This lesson follows the topic synthesis `synth/LNX-301/LNX-301-T09.md`, which carries the sources and the history.

## What you will be able to do

- Install the `freeipa.ansible_freeipa` collection and describe the roles for servers, replicas and clients.
- Write idempotent tasks for users, groups, hosts, HBAC and sudo rules with explicit `state`.
- Use `action: member` correctly and keep secrets in a vault.
- Run `--check --diff` as a drift detector.

## Why automate

Interactive `ipa` commands leave no record, and shell scripts of them fail when an object exists. ansible-freeipa modules compare what exists with what you declared and change only the difference. A second run reports `changed: false`.

## Pieces

Install with `dnf install ansible-freeipa` or `ansible-galaxy collection install freeipa.ansible_freeipa`; the guide asks for Ansible 2.15 or later. On RHEL 10 only the collection form is installed, so write `freeipa.ansible_freeipa.ipagroup`, or use `module_defaults`. Roles `ipaserver`, `ipareplica` and `ipaclient` wrap the installers and take their options as variables (`ipaserver_domain`, `ipaserver_realm`, `ipaserver_setup_dns`, `ipaserver_no_hbac_allow`, `ipaadmin_password`). Object modules mirror the `ipa` command families (`ipauser`, `ipagroup`, `ipahost`, `ipahbacrule`, `ipasudorule`, `ipasudocmdgroup` and many more). Modules import the IPA Python libraries, so they run on an IdM server or enrolled client, targeted at one server; replication spreads the change.

```yaml
- hosts: ipaserver
  gather_facts: false
  module_defaults:
    group/freeipa.ansible_freeipa.modules:
      ipaadmin_password: "{{ vault_ipaadmin_password }}"
  tasks:
    - freeipa.ansible_freeipa.ipagroup: {name: dba, state: present}
    - freeipa.ansible_freeipa.ipagroup: {name: dba, user: [alice], action: member, state: present}
    - freeipa.ansible_freeipa.ipahbacrule:
        name: db-ssh
        group: [dba]
        hostgroup: [dbservers]
        hbacsvc: [sshd]
        state: present
```

## Rules that prevent accidents

- Lists replace the whole value on `state: present`; use `action: member` to add or remove only the listed members.
- Always give `state`. Objects you do not mention are left alone, so removal must be explicit.
- Keep passwords in `ansible-vault`, set `no_log` where needed, and prefer a narrow automation account (an IdM role with only HBAC and sudo privileges) over `admin`.
- Separate the bootstrap playbook (installers) from the policy playbook that runs regularly; re-running an install role over a half-built domain is dangerous.
- Run `ansible-playbook policy.yml --check --diff` in review and on a schedule; any `changed` is drift.

## Worked example

A task sets `user: [alice, bob]` on `dba` without `action: member`; carol, added by hand during an incident, disappears. `--check --diff` in the pull request shows the removal before it happens. The repair is `action: member` (or listing carol in the repository on purpose).

## Self-check

1. Why does a module need the IPA Python libraries on the target?
2. What is the difference between `state: present` with a list and `action: member`?
3. How do you stop the admin password from living in Git?
4. What does a nightly `--check --diff` job tell you?
5. Why keep install roles out of the regular policy run?
