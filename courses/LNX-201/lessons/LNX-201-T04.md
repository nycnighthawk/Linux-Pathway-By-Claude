# Name resolution and systemd-resolved

This lesson follows the topic synthesis `synth/LNX-201/LNX-201-T04.md`, which carries the sources and the history.

## What you will be able to do

- Explain the lookup chain: the name service switch, `/etc/hosts`, then DNS.
- Read and change resolver settings with `resolvectl` and drop-in files.
- Debug a name that resolves for `dig` but not for an application, or the reverse.

## The chain

Applications call the C library, which reads `/etc/nsswitch.conf`. The `hosts:` line lists sources in order, for example
`hosts: files dns` (or `files mdns4_minimal [NOTFOUND=return] dns` on desktops). `files` is `/etc/hosts`; `dns` uses
the servers in `/etc/resolv.conf`; `resolve` asks systemd-resolved. `getent hosts name` follows this chain exactly like an
application. `dig` and `nslookup` talk to DNS only, so they ignore `/etc/hosts` and the switch.

## /etc/resolv.conf

`nameserver` lines (up to three are used), `search` and `domain` for short names, and `options` such as `timeout:1`,
`attempts:2` and `ndots:N` (a name with fewer dots than N is tried with search suffixes first). On systems with
systemd-resolved the file is usually a symlink to a stub (`127.0.0.53`) or to a file that lists the real servers.
Never edit a generated file; change the manager's configuration.

## systemd-resolved

```bash
resolvectl status                    # servers and domains per link
resolvectl query example.org         # resolve and show which link, protocol and cache answered
resolvectl dns eth0 192.0.2.53       # runtime change for one link
resolvectl domain eth0 '~lab.test'   # route lab.test queries to that link's server
resolvectl flush-caches
```

Global settings live in `/etc/systemd/resolved.conf` and drop-ins in `/etc/systemd/resolved.conf.d/*.conf`
(`DNS=`, `FallbackDNS=`, `Domains=`, `DNSSEC=`, `DNSOverTLS=`, `Cache=`). A domain with a leading tilde (`~lab.test`) is a
routing-only domain: queries under it go to that link's server and the name is not added as a search suffix. NetworkManager and
networkd push per-link servers and domains to resolved, so per-interface settings usually belong in their profiles.

## Reading results

`NOERROR` with no answer means the name exists but has no record of that type; `NXDOMAIN` means the name does not exist;
`SERVFAIL` points at the upstream server or DNSSEC validation. Compare the system resolver with the authoritative
server (`dig @ns1.example.net name`) to separate caching and split-horizon from publication problems.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| `dig` works, application fails | `/etc/hosts` or the switch order | `getent hosts name`, `nsswitch.conf` |
| Slow first lookup | dead first nameserver | `options timeout`, `resolvectl status` |
| Internal names fail only on VPN | routing domain missing | `resolvectl domain`, the VPN profile |
| Old address after a change | cache | TTL, `resolvectl flush-caches` |
