## Keys and the agent

```bash
ssh-keygen -t ed25519 -a 100 -C "alice@laptop"
ssh-copy-id -i ~/.ssh/id_ed25519.pub alice@server1
eval "$(ssh-agent)"; ssh-add -t 4h ~/.ssh/id_ed25519; ssh-add -l
```

The private key (mode 0600) needs a passphrase; the agent holds it in memory. The server refuses keys when `~/.ssh` or
`authorized_keys` is writable by others. `ssh-keygen -F host` looks up, `-R host` removes a `known_hosts` entry; `ssh-keyscan` fetches host keys.

## Client configuration

```
Host bastion
    HostName bastion.example.net
    User ops
Host *.internal
    ProxyJump bastion
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
Host *
    ControlMaster auto
    ControlPath ~/.ssh/cm-%C
    ControlPersist 10m
```

For each option the first value obtained wins, so specific blocks come first. `ssh -G host` prints the effective options.
`IdentitiesOnly yes` offers only the named key. `ssh -J ops@bastion target` is the command-line form of ProxyJump.

## ProxyJump versus agent forwarding

ProxyJump relays the encrypted stream: you authenticate to the final host yourself, so a compromised bastion sees only ciphertext.
Agent forwarding (`-A`, `ForwardAgent yes`) lets the intermediate host use your agent while you are connected; use it rarely.

## Port forwarding

| Form | Listener | Use |
|---|---|---|
| `-L lport:rhost:rport` | on the client | reach a service the server can see |
| `-R rport:lhost:lport` | on the server | publish a local service through the server |
| `-D port` | SOCKS proxy on the client | ad hoc proxy for many destinations |

Add `-N` (no command), `-f` (background) and `-o ExitOnForwardFailure=yes`. On the server `AllowTcpForwarding`, `GatewayPorts`
and `PermitOpen` limit forwards.

## Server settings

`/etc/ssh/sshd_config` and drop-ins in `sshd_config.d/`: `PermitRootLogin`, `PasswordAuthentication no` once keys work, `AllowUsers`,
`MaxAuthTries`, `AllowTcpForwarding`, `Match` blocks. Validate with `sshd -t`, inspect with `sshd -T`, reload without dropping
sessions, and keep a second session open when changing authentication. A changed port also needs a firewall rule and an SELinux label.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| Key ignored, password asked | permissions on `~/.ssh` | `ssh -v`, `journalctl -u sshd` |
| `Permission denied` after many keys | too many identities offered | `IdentitiesOnly yes` |
| Host key warning | host rebuilt or MITM | fingerprint out of band, then `ssh-keygen -R` |
| Timeout versus immediate refusal | firewall drop versus closed port | `ss -ltnp` on the server |
