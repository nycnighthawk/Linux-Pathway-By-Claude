# AWX and the automation controller

This lesson follows the topic synthesis `synth/LNX-305/LNX-305-T08.md`, which carries the history and the sources.

## What you will be able to do

- Name the objects of a controller and how they connect.
- Explain how a job is dispatched and where it runs.
- Decide whether a team needs a controller, and which one.

## Why a controller

Running playbooks from a laptop does not give a team shared credentials, access control, scheduling, an audit trail or a
button for people who are not Ansible users. AWX (the upstream project) and the automation controller (the component of Red
Hat Ansible Automation Platform) add a web UI, a REST API and a task engine around the same playbooks you already have.

## The objects

- **Organization**: the owner of everything else and the unit of multi-tenancy.
- **User, team, role**: role-based access control. A team can have Execute on a template without being able to read the credential it uses.
- **Credential**: a typed secret (machine, source control, vault, cloud, registry). It is stored encrypted, usable by jobs, never shown again.
- **Inventory**: hosts and groups, typed by hand or synchronised from a source such as a cloud ([inventory](lesson:LNX-305-T01)).
- **Project**: a Git repository (or local path) holding playbooks and roles.
- **Execution environment**: the container image the job runs in ([EEs](lesson:LNX-305-T03)).
- **Job template**: project, playbook, inventory, credentials, execution environment, limit, tags, forks, check mode, survey.
- **Workflow**: job templates, inventory syncs and approval nodes linked by success, failure and always edges.
- **Schedule, notification, survey, webhook**: when it runs, who is told, what a user can fill in, what triggers it from Git.

## How a job runs

A launch request (UI, API, CLI, webhook, schedule) creates a job in the database and queues it on an instance group. A worker
node starts the job with ansible-runner in a container from the execution environment image; events stream back as JSON over
Receptor and appear live. Hop nodes relay between networks, so remote sites need no inbound path from the centre. Container
groups run each job as a pod in Kubernetes. Capacity is counted in forks; jobs wait when it is full.

## Operating it

The controller is production infrastructure: PostgreSQL to back up, certificates, upgrades, capacity, monitoring. Keep its own
configuration in code with the `awx` CLI or the `awx.awx` and `ansible.controller` collections. Treat it as a top-tier asset:
whoever can edit a project or use a powerful credential can run code on every host in the inventory. Give Execute, not Use or
Admin, to people who only need to launch. Do not put secrets in survey answers. Run the first launch of a risky template in
check mode ([idempotence and check mode](lesson:LNX-305-T07)).

## Which one

Upstream AWX is an open source project without a support contract. Its repository announced a pause in releases in July 2024
during a large refactoring, and the last tagged release then was 24.6.1; maintainers said the work continues. No newer tag than 24.6.1 had appeared when this lesson was last checked, so look at the releases page for the current state. The supported product is the controller inside Ansible Automation Platform, with regular patch releases. A
small team may need neither: `ansible-playbook` from CI runners with short-lived credentials is a valid design.

## Worked example

One organization per business unit. The operators team has Execute on a "Patch Linux" template: Git project, cloud inventory
source, machine credential, standard EE, a survey for `limit` and a reboot flag. A schedule runs it every Sunday night in check
mode and posts the summary to chat. A workflow adds an inventory sync before and an approval node between sites. If a job
fails with module not found, the EE lacks the collection: rebuild the image, push, update the template.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| Module not found | collection missing from the EE | EE definition and tag |
| Every job fails at once | project sync failed (token expired) | project update output |
| Job waits forever | no capacity in the instance group | instance group, forks |
| Authentication fails | key pasted with wrong line endings | credential fields |
