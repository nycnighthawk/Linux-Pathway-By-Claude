# Roles, collections and execution environments

This lesson follows the topic synthesis `synth/LNX-305/LNX-305-T03.md`, which carries the history and the sources.

## What you will be able to do

- Lay out a role, give it a variable interface and an argument spec.
- Package roles and plugins as a collection, build it, install it and call it by its fully qualified name.
- Explain what an execution environment is and when to use one.

## Roles

A role is a directory with fixed subdirectories: `tasks/main.yml`, `handlers/main.yml`, `defaults/main.yml` (the interface:
lowest precedence, meant to be overridden), `vars/main.yml` (internal constants: high precedence), `templates/`, `files/`,
`meta/main.yml` and `meta/argument_specs.yml`. `ansible-galaxy role init NAME` creates the skeleton. Apply a role with `roles:`
(static, before the play's tasks), `import_role` (static, at parse time) or `include_role` (dynamic, usable in a loop or under
`when`).

Three habits make a role reusable. Prefix every public variable with the role name (`chrony_servers`), because roles share one
variable namespace with the play. Declare the inputs in `meta/argument_specs.yml` so wrong types fail early. Put per-platform
data in `vars/<os_family>.yml` and load the first file that exists, rather than scattering `when` clauses.

## Collections

A collection is a versioned package under a namespace: `namespace.name`. It holds `plugins/` (modules, filters, lookups,
inventory plugins), `roles/`, `playbooks/`, `docs/`, `galaxy.yml` and `meta/runtime.yml`. Commands:

```bash
ansible-galaxy collection init acme.tools
ansible-galaxy collection build src/acme_tools --output-path dist
ansible-galaxy collection install dist/acme-tools-1.0.0.tar.gz -p collections
ansible-galaxy collection install -r requirements.yml
ansible-doc acme.tools.banner        # for plugins; roles use ansible-doc -t role
```

Name content by its FQCN: `ansible.builtin.copy`, `ansible.posix.firewalld`, `acme.tools.banner`. Pin versions in
`requirements.yml` and keep a project-local `collections/` directory (set `collections_path`). Treat a collection as code
that runs with your privileges: review upgrades, mirror it privately, verify signatures where offered.

## Execution environments

An execution environment (EE) is a container image with ansible-core, ansible-runner, collections, Python packages and system
packages. It is described in an `execution-environment.yml` (definition version 3), built with `ansible-builder build`, and run
with `ansible-navigator run site.yml --eei IMAGE --mode stdout` or by the controller. It makes the control node a build artefact
you can scan, sign, pin by digest and promote like an application image.

## Worked example

A `banner` role has `banner_dest` (required), `banner_text` and `banner_repeat` (integer, default 1). A bad value such as
`-e banner_repeat=often` fails before any task runs because the spec says integer. The role goes into the collection
`acme.tools` 1.0.0; the playbook says `role: acme.tools.banner`; the project's `requirements.yml` pins `acme.tools:~1.0`, so a
future 1.1 change cannot surprise other teams until they choose to upgrade.

## How this connects

- Role defaults are the lowest rung of the ladder in [inventory and precedence](lesson:LNX-305-T01).
- Roles hold the tasks, handlers and templates of [playbooks](lesson:LNX-305-T02).
- Vendor roles in [RHEL System Roles](lesson:LNX-305-T05) are the same structure with a tested interface.
- [Molecule](lesson:LNX-305-T06) tests a role; the controller in [AWX](lesson:LNX-305-T08) runs jobs inside EEs.
- Pinning and signing follow the same trust ideas as repositories in LNX-104-T03; EEs are images, like LNX-306-T04.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| A role variable has no effect | defined in `vars/`, which outranks inventory | move it to `defaults/` |
| Two roles interfere | unprefixed variable names | prefix with the role name |
| Module not found in the EE | collection missing from the image | the EE definition |
| Different results after an upgrade | unpinned collection | `requirements.yml` versions |
