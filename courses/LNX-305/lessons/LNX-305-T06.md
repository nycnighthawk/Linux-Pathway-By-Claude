# ansible-lint and Molecule

This lesson follows the topic synthesis `synth/LNX-305/LNX-305-T06.md`, which carries the history and the sources.

## What you will be able to do

- Run ansible-lint, read a rule id, choose a profile and handle exceptions responsibly.
- Write a Molecule scenario that converges a role, checks idempotence and verifies the result.
- Say what a container test proves and what it cannot.

## ansible-lint

ansible-lint reads playbooks, roles and collections and reports rule violations without running anything. Each finding has
an id such as `fqcn[action-core]`, `name[missing]`, `yaml[truthy]`, `no-changed-when`, `command-instead-of-module`,
`package-latest`, `risky-file-permissions`, `var-naming[no-role-prefix]`. A non-zero exit code makes it a gate.

Rules are grouped in profiles, each including the one before: `min` (content loads), `basic` (common problems and style),
`moderate` (readability), `safety` (no risky or unreliable patterns), `shared` (publishable on Galaxy or Hub), `production`
(certified content). Pick one with `--profile` or in `.ansible-lint`:

```yaml
profile: safety
exclude_paths: [.venv/]
warn_list: [experimental]
offline: true
```

Prefer the `.ansible-lint-ignore` file over `skip_list` for accepted violations: the entries stay visible as warnings. A
`# noqa: rule-id` comment excuses one line. `ansible-lint --fix` rewrites what is safe to rewrite (module names, truthy
values, key order); run it on a clean working tree and read the diff. Adopt it on an old repository by recording today's
findings as ignored, forbidding new ones and burning the list down.

## Molecule

A scenario lives in `molecule/<name>/` inside a role or collection:

```text
molecule/default/molecule.yml   driver, platforms, provisioner, verifier, test_sequence
molecule/default/converge.yml   applies the role
molecule/default/verify.yml     asserts on the result
```

The full sequence is dependency, cleanup, destroy, syntax, create, prepare, converge, idempotence, side_effect, verify,
cleanup, destroy. The `idempotence` step runs converge again and fails if any task reports a change. Verify is a normal
playbook: gather state with `slurp`, `stat`, `package_facts`, `service_facts` or `command`, then `ansible.builtin.assert`.
Commands: `molecule test`, `molecule converge`, `molecule verify`, `molecule login`, `molecule destroy`.

Drivers create the instances. With the default driver you provide `create.yml` and `destroy.yml` (or set `managed: false`
and point the platforms at hosts that already exist, for example `ansible_connection: local`). Docker, Podman and Vagrant
drivers come from the separate `molecule-plugins` package. Molecule supports only the latest two ansible-core releases, so
pin both tools in CI.

## What a test proves

A container is not a machine: it does not show kernel parameters, a real init and firewall, SELinux enforcing, mounts or
network interfaces unless you run it privileged, and then you test something else. Say in the scenario what it does not
prove, and add a virtual-machine scenario for roles that touch those parts. A test that cannot fail proves nothing:
make verify check content, not just that a package exists, and try damaging the result to see that it fails.

## Worked example

A role starts with `command: touch ...` and `shell: echo configured >> run.log`. Lint reports `no-changed-when` and
`command-instead-of-module`; Molecule's idempotence step reports a change on the second converge because the log grows.
Replace them with `ansible.builtin.file` (state `touch`, modification time preserved) and `ansible.builtin.lineinfile`; add
explicit modes, prefix the variables with the role name, and fix `yes` to `true`. Lint is quiet and idempotence passes. Wrapping
a command in `changed_when: false` would also make idempotence pass, which is why a reviewer must read each such line.

## How this connects

- Molecule's idempotence step enforces [idempotence and check mode](lesson:LNX-305-T07) on every change.
- It exercises the structure from [roles and collections](lesson:LNX-305-T03); lint rules encode its conventions.
- Lint flags the habits in [playbooks](lesson:LNX-305-T02): unnamed tasks, `yes`, short module names, risky `shell`.
- Secrets used in tests follow [Vault](lesson:LNX-305-T04); the platform matrix idea is the one system roles use ([T05](lesson:LNX-305-T05)).
- Scripting tests for shell code are in LNX-203, and image tests with Packer in LNX-306-T04.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| Idempotence step fails | `command` or `shell` without a guard, timestamp in a template | the task named in the diff |
| Verify always passes | assertion too weak | change the output and rerun verify |
| Lint finds thousands of issues | first run on legacy code | ignore file, then burn down |
| Tests pass in CI, role fails on a host | container hides kernel or init behaviour | add a VM scenario |
