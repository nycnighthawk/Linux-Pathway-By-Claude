# Ansible Vault

This lesson follows the topic synthesis `synth/LNX-305/LNX-305-T04.md`, which carries the history and the sources.

## What you will be able to do

- Encrypt a file and a single value, and use them from a playbook.
- Use vault IDs (labels) and supply the password without leaving it on disk in the repository.
- Keep secrets out of logs, and say what Vault does not protect.

## What Vault is

Ansible Vault encrypts data at rest so it can live in Git. The cipher is AES-256 with an authentication code, and the key is
derived from a password. Encrypted text starts with a header: `$ANSIBLE_VAULT;1.1;AES256` or, with a label,
`$ANSIBLE_VAULT;1.2;AES256;label`. It is symmetric: anyone who can decrypt can read every value under that password.

```bash
ansible-vault create group_vars/prod/vault.yml
ansible-vault encrypt secrets.yml          # in place
ansible-vault view group_vars/prod/vault.yml
ansible-vault edit group_vars/prod/vault.yml
ansible-vault rekey --new-vault-id prod@prompt group_vars/prod/vault.yml
ansible-vault encrypt_string --vault-id prod@prompt --name db_password 'value'
```

`encrypt_string` makes a `!vault |` block that you paste into a normal YAML file, so only the secret value is hidden and
reviewers still read the rest of the file. Avoid giving the secret on the command line (it lands in shell history): use
`--stdin-name` and pipe it.

## Supplying the password

- `--ask-vault-pass` prompts.
- `--vault-password-file FILE` or `ANSIBLE_VAULT_PASSWORD_FILE` reads a file (keep it out of Git, mode 600). If the file is
  executable, Ansible runs it and reads standard output.
- `--vault-id label@source` attaches a label: `prod@prompt`, `dev@~/.vault_dev`, or `prod@client-script` where a script named
  `*-client` receives the label and can fetch the secret from a keyring or password manager.
- Several `--vault-id` options can be given at once; Ansible matches by label. `vault_identity_list` in `ansible.cfg` sets defaults.

## Habits that keep secrets secret

1. Indirection: `db_password: "{{ vault_db_password }}"` in a plain `vars.yml`; the real value in an encrypted `vault.yml`.
   Reviewers see which variables are secret; a grep finds them.
2. `no_log: true` on every task that handles a secret. Without it, `-v` output and callbacks print arguments.
3. Tight modes: render secret files with `mode: "0600"`. A secret in a `0644` file is readable by every local user.
4. Never put a secret in a command line argument of `command`: it shows in the process list.
5. Rotation is two jobs: `rekey` changes the password; changing the secret itself happens at its source. If the password
   leaked, old ciphertext in Git history stays readable, so rotate the secrets too.

## Worked example

`group_vars/all/vars.yml` holds `db_password: "{{ vault_db_password }}"`; `group_vars/all/vault.yml` is encrypted under the
label `prod` and holds `vault_db_password`. CI runs `ansible-playbook site.yml --vault-id prod@.ci/vault-client`, a script that
reads the password from the CI platform's secret store. The task that writes `/etc/app/db.conf` has `no_log: true` and
`mode: "0600"`. A developer without the `prod` password can still run the dev inventory with the `dev` label.

## When to use something else

Vault is simple and offline, which is why it is popular. At larger scale use a secret manager (HashiCorp Vault, a cloud key
vault, SOPS with a KMS key) through a lookup plugin, or the credential store of the controller in
[AWX](lesson:LNX-305-T08). They give per-secret access control, audit and short-lived credentials. The secret still arrives in
memory on the control node, so logging and file modes still matter.

## How this connects

- Encrypted values sit in the variable layers of [inventory and precedence](lesson:LNX-305-T01); the vault file is a normal
  `group_vars` file once decrypted.
- Templates and tasks from [playbooks](lesson:LNX-305-T02) use the values; add `no_log`.
- [System roles](lesson:LNX-305-T05) such as storage encryption and registration take secrets the same way.
- [ansible-lint](lesson:LNX-305-T06) can flag risky patterns; secret scanners catch leaks it cannot.
- The Windows hosts of [LNX-305-T09](lesson:LNX-305-T09) need vaulted passwords or, better, Kerberos.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| `Decryption failed` | wrong password or label | header label, `--vault-id` |
| Secret visible in CI log | missing `no_log`, `debug` task, `-vvv` | task keywords, log |
| Diff shows only a changed blob | ciphertext is salted | compare decrypted `view` output |
| Old secret still readable | password rekeyed, secret not rotated | rotate at the source |
