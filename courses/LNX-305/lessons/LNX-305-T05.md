# RHEL System Roles

This lesson follows the topic synthesis `synth/LNX-305/LNX-305-T05.md`, which carries the history and the sources.

## What you will be able to do

- Install the supported roles on a control node and find their documentation and examples.
- Drive a role from variables, following the conventions that all system roles share.
- Judge when a vendor role is the right tool and what can go wrong.

## What they are

RHEL System Roles are Ansible roles, shipped by Red Hat and developed upstream as Linux System Roles, that expose one stable
variable interface for common operating system tasks across releases. Examples: `timesync`, `selinux`, `firewall`, `network`,
`storage`, `sshd`, `logging`, `kdump`, `certificate`, `crypto_policies`, `podman`, `ha_cluster`, `ad_integration`, `rhc`.

```bash
sudo dnf install rhel-system-roles            # on the control node
ls /usr/share/doc/rhel-system-roles/timesync/ # README and example playbooks
```

The roles are available as the collection `redhat.rhel_system_roles` (and `fedora.linux_system_roles` upstream). Only the
control node needs the package; the managed nodes need Python, an account that can use `sudo`, and whatever packages the role
installs for itself.

## Conventions you can rely on

- Public variables start with the role name: `timesync_ntp_servers`, `selinux_state`, `selinux_booleans`, `firewall`,
  `storage_pools`, `network_connections`, `sshd_config`.
- Names that start with two underscores and the role name are internal. Never set them.
- Complex settings are lists of dictionaries; each dictionary is one object, often with `state: absent` to remove it.
- Per-platform differences are hidden inside the role. You describe the result, not the commands.
- A role does not edit itself: you copy no code. You change behaviour through variables, in `group_vars`.

```yaml
- hosts: all
  vars:
    timesync_ntp_servers:
      - hostname: time.example.org
        iburst: true
  roles:
    - redhat.rhel_system_roles.timesync
```

## Operating them safely

1. Run `--check --diff` first, then for real, then again: the second run must report no change ([idempotence](lesson:LNX-305-T07)).
2. Know the dangerous roles. `storage` can destroy data; keep its safe mode on. `network` and `firewall` can cut the SSH
   connection Ansible is using. `selinux` may need a reboot when you leave the disabled state. Test on a console-attached host.
3. Pick one authority per setting. If a hardening playbook, OpenSCAP remediation or a hand edit also manages the same file,
   the last writer wins and the next run reverts the other.
4. On image-mode (rpm-ostree) systems, packages are installed at image build time and the role only verifies them at run time.
5. Read the release notes when you upgrade the package: defaults can change.

## Worked example

A baseline playbook applies `timesync` (site NTP servers), `selinux` (`selinux_state: enforcing`), `firewall` (ssh, https and
one custom port, each with `permanent: true` and `runtime: true`) and `sshd` (a hardened `sshd_config` dictionary). Group
variables hold the data by function. On the first run, the check shows which files change; the second real run changes nothing.
A forgotten `permanent: true` on the custom port opens it only until the next reload, so the symptom appears days later.

## How this connects

- These roles are the product of the structure in [roles and collections](lesson:LNX-305-T03), with an argument spec and tests.
- Their variables are set in the layers of [inventory and precedence](lesson:LNX-305-T01); the role defaults rank lowest.
- Credentials for roles such as `rhc` or storage encryption belong in [Vault](lesson:LNX-305-T04).
- Linux System Roles tests every role on a release matrix, the practice described in [ansible-lint and Molecule](lesson:LNX-305-T06).
- The time, firewall and SELinux subjects themselves are covered in the networking and security courses; kickstart-time
  alternatives are in LNX-306-T01 and image-based ones in LNX-306-T04.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| SSH connection lost mid-play | `network` or `firewall` change removed access | out-of-band console; staged change |
| Setting reverted on the next run | two writers of one file | who else manages it |
| Port closed after reload | missing `permanent: true` | the firewall entry |
| Role fails on a new minor release | stale local copy of the role | package version, release notes |
