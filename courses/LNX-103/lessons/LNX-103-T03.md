# LVM: growing, snapshots and thin pools

This lesson follows the topic synthesis `synth/LNX-103/LNX-103-T03.md`, which carries the sources and the history.

## What you will be able to do

- Explain PV, VG, LV and extent, and where LVM keeps its metadata.
- Create, grow, move and snapshot volumes, and know which operations are dangerous.
- Set up a thin pool and keep it from filling.

## Building blocks

| Layer | Commands |
|---|---|
| **PV** (physical volume): a device with an LVM label | `pvcreate`, `pvs`, `pvdisplay`, `pvresize`, `pvmove`, `pvremove` |
| **VG** (volume group): a pool made of fixed-size extents, 4 MiB by default | `vgcreate -s 8M`, `vgs`, `vgextend`, `vgreduce`, `vgcfgbackup`, `vgcfgrestore` |
| **LV** (logical volume): carved from the VG's extents | `lvcreate`, `lvs`, `lvextend`, `lvreduce`, `lvremove`, `lvconvert` |

Metadata is text, stored on every PV and backed up in `/etc/lvm/backup` and `/etc/lvm/archive`. Device nodes:
`/dev/<vg>/<lv>` and `/dev/mapper/<vg>-<lv>` (hyphens in names are doubled).

```bash
pvcreate /dev/vdb /dev/vdc
vgcreate vg0 /dev/vdb /dev/vdc
lvcreate -L 20G -n data vg0              # or -l 100%FREE
mkfs.xfs /dev/vg0/data
```

## Growing, shrinking, moving

```bash
lvextend -r -L +10G /dev/vg0/data        # -r (--resizefs) also grows ext4 or XFS
pvresize /dev/vdb                        # after the underlying disk was enlarged
pvmove /dev/vdb && vgreduce vg0 /dev/vdb # empty a disk online, then drop it
```

Shrinking is file system first, then LV (`lvreduce -r`); XFS cannot shrink. Reducing below the file system size
destroys data.

## Snapshots

Classic COW snapshot: `lvcreate -s -L 5G -n snap /dev/vg0/data`. The size is the **change area**; when
`lvs -o+snap_percent` reaches 100% the snapshot is lost. Roll back with `lvconvert --merge vg0/snap`.

Thin pool (needs `dm-thin-pool`):

```bash
lvcreate --type thin-pool -n pool0 -L 100G vg0
lvcreate --type thin -n web -V 50G --thinpool pool0 vg0      # virtual size can exceed the pool
lvcreate --snapshot -n web-before vg0/web                    # no size option, or you get a thick snapshot
lvs -o+data_percent,metadata_percent vg0
```

Thin snapshots are skipped at activation; use `lvchange -ay -K`. **A full pool is an outage for every thin volume.**
Let `dmeventd` extend it: in `lvm.conf`, `activation/thin_pool_autoextend_threshold = 80` and
`activation/thin_pool_autoextend_percent = 20`; check monitoring with `lvs -o+seg_monitor`. Return space with
`fstrim` so the pool learns about freed blocks.

## Discovery

Current LVM uses a devices file (`lvmdevices --adddev`) instead of scanning everything; two PVs with the same UUID
(clones, multipath paths) must never both be visible.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| Snapshot became invalid | change area filled | `lvs -o+snap_percent`, size it larger |
| All thin volumes fail together | pool full | `lvs -o data_percent,metadata_percent` |
| Duplicate PV warnings | cloned disk or multipath paths | `pvs -o+uuid`, devices file |
| VG metadata damaged | overwritten area | `vgcfgrestore -l`, archive files |
