## Five separate artefacts

Compliance as code keeps five things apart so each can be reviewed and rerun alone.

| Artefact | Question | Where it lives |
|---|---|---|
| Policy / controls | what is required? | CIS, STIG or ANSSI controls files; XCCDF profiles |
| Check | how do we test it? | OVAL, template-generated checks, scripts |
| Remediation | how do we fix it? | generated Bash, Ansible, Kickstart, image blueprints |
| Tailoring and exceptions | what did this site decide? | tailoring file or `.profile`, exception register |
| Result | what was found? | XCCDF results, ARF, HTML report |

**SCAP** is the family of standards behind this: XCCDF (benchmarks and profiles), OVAL (machine checks), OCIL (human questionnaires), CPE (platforms), ARF (results). A **data stream** bundles them. The **ComplianceAsCode/content** project generates data streams, playbooks and scripts from YAML rules; each rule carries references to every standard that demands it, so one rule serves many profiles.

## Scan, report, fix

```bash
oscap info /usr/share/xml/scap/ssg/content/ssg-ubuntu2404-ds.xml        # list profiles
oscap xccdf eval --profile xccdf_org.ssgproject.content_profile_stig \
  --results results.xml --results-arf arf.xml --report report.html DATASTREAM
oscap xccdf generate fix --profile PROFILE --fix-type ansible --output fix.yml DATASTREAM
```

Results per rule are pass, fail, notapplicable, notchecked, informational, error or unknown. Read `notapplicable` carefully: a profile for the wrong release skips rules and still looks green. `oscap-ssh`, `oscap-podman` and `oscap-vm` reach hosts, containers and images.

Fix workflow: read the generated fix, run it on a staging clone, keep out-of-band access (console, snapshot), apply to a canary, rescan. Remediation can lock out administrators: a rule that restricts SSH groups without your group is a classic.

## Tailor, with reasons

A **tailoring file** or a source-tree `.profile` selects or deselects rules and sets variables without editing the data stream.

```yaml
documentation_complete: true
title: Site baseline based on CIS Level 1
extends: cis_server_l1
selections:
  # reason: print servers need mDNS discovery, owner print-team
  - '!service_avahi_disabled'
  - var_accounts_tmout=900
```

`autotailor` produces a tailoring file from the command line; `oscap xccdf eval --tailoring-file` uses it. Every deselected rule goes into an **exception register** with a reason, an owner and an expiry date, and the register belongs in version control next to the profile.

## Harden at build time

Hardening in the image beats remediation on running hosts. Kickstart can embed a scan with the OpenSCAP add-on, image builders accept a profile in the blueprint, and Packer or container builds can run the generated playbook. Rescan running hosts to find drift from the golden image. In Kubernetes, the Compliance Operator runs profiles against nodes and platform settings.

## What a green score does not mean

It means the rules in that profile passed, on that scanner and content version, as reported by the host itself. It says nothing about application flaws or architecture, and a compromised host can report itself clean. Record the content version, scanner version and tailoring with every result, sample ten rules by hand each cycle, and pair the scan with independent detection.

## Worked example: the stale content

A scan with the previous release's content gives 94 percent on a newer distribution. A third of the rules show notapplicable because their platform checks failed, and some check paths that moved. The score was high because rules were skipped. Fix: use the content built for the release, fail the pipeline when the notapplicable count jumps, and compare against the last known-good scan.
