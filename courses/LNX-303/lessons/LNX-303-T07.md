## What you will be able to do

- Explain how OVAL scanning, Trivy and an SBOM each answer part of the question "what is wrong with what I run?".
- Generate an SBOM and scan an image, a filesystem and a stored SBOM.
- Handle backports, unfixed findings and VEX statements without hiding real risk.
- Prioritise with exploitation data, not severity alone.

## The join

Vulnerability management joins two sets of data: **inventory** (what is installed, with stable identifiers) and **advisories** (what is known to be wrong, keyed to the same identifiers). Then it adds a **decision** and a **record** of it.

| Piece | Role | Examples |
|---|---|---|
| Inventory | list of components and versions | SBOM in CycloneDX or SPDX; `rpm -qa`; `dpkg-query -W` |
| Identifier | ties a component to advisories | package URL (purl), e.g. `pkg:deb/debian/openssl@3.0.15-1~deb12u1` |
| Advisory data | vendor feeds, ecosystem databases, NVD | OVAL, Debian tracker, OSV, GitHub advisories |
| Priority signals | likelihood of exploitation | CISA KEV list, EPSS score, exposure of the service |
| Decision record | why a finding was fixed or accepted | VEX status, ignore file with an expiry |

## OVAL with OpenSCAP

OVAL definitions are declarative checks, for example that a package is older than the fixed build in this distribution release. Because each vendor writes them from its own advisories, they respect **backports**: a fix applied to an older version number.

```bash
oscap oval eval --results oval-results.xml vendor-definitions.xml
oscap oval generate report oval-results.xml > oval-report.html
```

Verify findings before acting: compare the installed package changelog (`rpm -q --changelog`, `apt changelog`) and the vendor advisory, because definitions can lag the latest advisory state.

## SBOMs and Trivy

```bash
trivy image --format cyclonedx --output sbom.cdx.json IMAGE   # generate
trivy sbom sbom.cdx.json                                      # scan a stored SBOM
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 IMAGE   # CI gate
trivy image --vex vex.json IMAGE                              # suppress documented not-affected cases
trivy rootfs /                                                # a host
```

An SBOM generated at **build time** knows what went in; one reverse-engineered from a finished image misses vendored code and static binaries. Store the SBOM with the artefact and sign it. SPDX and CycloneDX are the two standard formats. **VEX** statements say, per CVE and product, *not affected*, *affected*, *fixed* or *under investigation*, with a justification.

## Prioritise

Sort by what is being exploited, then likelihood, then severity in context: known-exploited (KEV) first, then high EPSS, then CVSS adjusted for whether the service is exposed. A finding with no fix is not the same as no finding: keep it visible, apply the vendor's mitigation, and review it on a schedule. Rebuild images regularly so base-layer fixes arrive, and check the age of the vulnerability database: a stale database gives a clean scan that means nothing.

## Worked example: the backport

A generic scanner reports a critical OpenSSL flaw because the version string is lower than the upstream fix. The distribution's tracker shows the fix was backported into the installed build. Trivy and OVAL, which use the distribution's data, report nothing. The record is a note citing the tracker or a VEX `fixed` entry. No patch is needed. The reverse also happens: a clean generic scan on a vendored library the package manager does not know about.
