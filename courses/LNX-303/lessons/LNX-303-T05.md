# Falco, auditd advanced

This lesson follows the topic synthesis `synth/LNX-303/LNX-303-T05.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Design an audit rule set that is complete where it matters and bounded in volume.
- Make auditing tamper-resistant and notice when events are lost.
- Write and tune Falco rules with lists, macros and overrides.
- Choose which tool answers which question.

## Two tools, two questions

| | auditd | Falco |
|---|---|---|
| Question | what happened, provably? | what looks wrong, now? |
| Source | kernel audit rules on system calls and file watches | system call stream through eBPF (or a kernel module) plus plugins |
| Strength | complete, immutable mode, the `auid` of the original login survives `sudo` | readable rules, container and Kubernetes context |
| Weakness | flat multi-record text, overhead on broad rules | tuning effort, dropped events under load |

## auditd rules that last

```
-D                                   # clear old rules
-b 8192                              # kernel backlog
-f 1                                 # on overflow: printk (2 panics)
-w /etc/passwd -p wa -k identity     # writes and attribute changes
-w /etc/sudoers -p wa -k scope
-a always,exit -F arch=b64 -S execve -F auid>=1000 -F auid!=unset -k exec
-a always,exit -F arch=b32 -S execve -F auid>=1000 -F auid!=unset -k exec
-a always,exit -F arch=b64 -S init_module,finit_module,delete_module -k modules
-e 2                                 # immutable until reboot
```

Always write the `b32` twin, or a 32-bit binary runs unseen. `auid!=unset` excludes service accounts. Put files in `/etc/audit/rules.d/` and load with `augenrules --load`; test with `-e 1` before you commit to `-e 2`. Analyse with `ausearch -k exec -ts today -i`, `aureport -x --summary` and `aureport --anomaly`. Check `auditctl -s`: a non-zero `lost` means your record has holes. Ship the log off the host in real time, because a root attacker with a local log can edit it.

## Falco rules

A rule has a condition, an output and a priority. Lists and macros keep conditions readable.

```yaml
- list: shell_binaries
  items: [bash, sh, dash, zsh]
- macro: spawned_process
  condition: evt.type in (execve, execveat) and evt.dir = <
- rule: Shell spawned by a web server
  desc: A web server process started a shell
  condition: spawned_process and proc.name in (shell_binaries) and proc.pname in (httpd, nginx, apache2)
  output: Shell from web server (user=%user.name parent=%proc.pname cmd=%proc.cmdline container=%container.name)
  priority: CRITICAL
  tags: [host, container, mitre_execution]
```

Validate with `falco --validate file.yaml`. Keep local changes in `falco_rules.local.yaml` using `append` or `override`, so upstream updates still apply. Falcosidekick forwards alerts to chat, SIEM and queues. The modern eBPF driver needs a recent kernel with BTF and no compiler on the host.

## The tuning loop

Collect, normalise, decide, respond. Review the first week of output in staging, write exceptions for known-good behaviour (CI runners that spawn shells), keep them in version control, and send only high-priority alerts to people. Alert on drops: a quiet tool is not necessarily a healthy one. `execve` logs hold command lines, which may contain secrets, so decide retention and redaction.

## Worked example: the silent spike

A busy host runs a broad `open` rule with a small backlog. During a traffic spike the kernel drops events and `auditctl -s` shows `lost 41203`, but nobody alerts on that counter, so the attacker's activity during the spike is missing. Fix: narrow the rule to `auid>=1000` and failures only, raise `-b`, add an alert on `lost` increasing, and replay the incident to confirm coverage.
