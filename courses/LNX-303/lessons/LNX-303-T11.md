# Long-term compliance drift

This lesson follows the topic synthesis `synth/LNX-303/LNX-303-T11.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Name the causes of drift and decay and give an example of each.
- Choose among prevention, convergence, detection and replacement for a given fleet.
- Measure whether control is working and keep exceptions from becoming permanent.
- Plan for the lifecycle events that change compliance without any local edit.

## Drift and decay

**Drift** is the gap between the approved configuration and the real one. **Decay** is the opposite movement: the host stays the same and the standard moves.

| Cause | Example |
|---|---|
| operator change | a port opened to debug and never closed |
| software change | an update replaces a modified config (look for `.rpmnew`, `.dpkg-dist`) |
| automation conflict | two tools set the same value |
| environment | certificate, licence or key expires |
| standard change | a new benchmark version, a deprecated cipher, a changed crypto-policy default |
| platform change | firmware, hypervisor or distribution defaults change |
| lifecycle | the distribution release leaves support |

## Four strategies

1. **Prevent**: immutable images, read-only root, SELinux enforcing, IMA or fapolicyd, restricted sudo.
2. **Converge**: configuration management reapplies the desired state; its schedule sets the drift window. Log each repair as an event so the cause gets fixed.
3. **Detect**: scheduled OpenSCAP scans, file-integrity checks, package manifests against the image, comparison with the inventory.
4. **Replace**: rebuild hosts and images on a cadence (for example 30 days), so unknown change cannot accumulate. Drift moves into the image pipeline, so scan images at build time.

## Measure

Pass rate (state the denominator), mean time to detect and to remediate, drift events per host and the settings that drift most, host and image age, active exceptions and how many are overdue, and the age of the newest scan. A scanner or agent that goes silent is an incident: a fleet that reports 98 percent may be reporting on the hosts that still check in.

## Exceptions and ownership

Every exception records the rule, the reason, a compensating control, an owner and an expiry date, and is renewed only by an explicit review. The baseline has an owner and a review cycle; when CIS or DISA publish a new version, assess it, test on canaries and update the tailoring in the same change. Put baseline, tailoring and exceptions in version control.

## Calendar the predictable

Certificate expiry, key rotation, distribution end of life, cryptographic transitions, and Secure Boot revocation updates all change compliance on a known date. A fleet inventory with OS release, support end and image build date answers: which hosts leave support within six months?

## Worked example: the silent agent

A configuration-management agent stops on forty hosts after a server certificate expires. Only failures alert, so nothing fires, and the hosts drift for five months. The next audit finds them out of compliance. The fix is an alert on any host that has not checked in within a day, a calendar entry for the server certificate, and a monthly review of hosts with no scan result.
