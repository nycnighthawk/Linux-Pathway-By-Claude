# Suricata, fail2ban

This lesson follows the topic synthesis `synth/LNX-303/LNX-303-T06.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Write a fail2ban filter and jail, test the filter on a real log, and avoid banning the wrong address.
- Read and write a Suricata rule and update, test and tune a rule set.
- Choose a sensor position and say what encryption hides.
- Name the ways an attacker can turn these tools against you.

## Two vantage points

| | fail2ban | Suricata |
|---|---|---|
| Sees | what applications write to logs or the journal | packets on an interface or in a capture |
| Detects | repeated failures from one address | exploit patterns, protocol anomalies, bad domains, TLS fingerprints |
| Responds | bans the address through the firewall for a time | alerts, writes EVE JSON, or drops packets inline |
| Blind to | services that do not log, distributed low-rate attacks | encrypted payloads, traffic that never crosses the sensor |

## fail2ban in four files

Configuration is a **jail** that joins a **filter** (regular expressions with `<HOST>`), an **action** (ban and unban commands) and thresholds.

```ini
# /etc/fail2ban/filter.d/login-abuse.conf
[Definition]
failregex = ^<HOST> \S+ \S+ \[[^]]+\] "POST /login(\?\S*)? HTTP/[0-9.]+" 401

# /etc/fail2ban/jail.d/login-abuse.local
[login-abuse]
enabled   = true
filter    = login-abuse
logpath   = /var/log/nginx/access.log
maxretry  = 8
findtime  = 10m
bantime   = 1h
banaction = nftables-multiport
ignoreip  = 127.0.0.1/8 ::1 10.0.0.5
```

Test before you enable: `fail2ban-regex /var/log/nginx/access.log /etc/fail2ban/filter.d/login-abuse.conf` reports matched and missed lines. Operate with `fail2ban-client status login-abuse` and `fail2ban-client set login-abuse unbanip ADDR`. `bantime.increment = true` and the `recidive` jail punish repeat offenders.

## Suricata in outline

`/etc/suricata/suricata.yaml` sets `HOME_NET`, the capture method (AF_PACKET for passive, NFQUEUE for inline), threads, and outputs. `eve.json` carries alerts and metadata. `suricata-update` fetches rule sets and applies `disable.conf`, `enable.conf` and `modify.conf`. Test with `suricata -T` and replay with `suricata -r capture.pcap -l out/`.

```
alert http $EXTERNAL_NET any -> $HOME_NET any (msg:"LAB admin config probe"; flow:established,to_server; http.uri; content:"/admin/config.php"; nocase; classtype:web-application-attack; sid:1000001; rev:1;)
```

Header: action, protocol, source, ports, direction, destination. Options: the buffer (`http.uri`), the match (`content`, `pcre`), state (`flow`, `flowbits`), rate (`threshold`, `detection_filter`), and a unique `sid`; local rules use 1,000,000 and above. Disable offloads on the capture interface so reassembled packets stay within MTU, and watch the drop counters.

## Where it goes wrong

- **Proxies and NAT.** Behind a load balancer every request has the balancer's address, so the jail bans the whole site. Log the forwarded client address and ignore the balancer.
- **Log injection.** If a regex matches attacker-controlled text, an attacker can make you ban an address of their choosing. Anchor expressions on fixed fields.
- **IPv6.** One address per attacker is cheap; consider banning prefixes.
- **Encryption.** Payload rules are blind in TLS 1.3 and QUIC. Detection shifts to SNI, certificates, JA3/JA4 fingerprints, DNS and flow metadata.
- **Inline mode.** A bad rule that drops production traffic is worse than a miss. Run in alert mode first and promote rules one at a time.

## Worked example: the proxy ban

A site behind a load balancer enables a login jail. Every line in the log carries the balancer's address, so after five failures the jail bans the balancer and the site goes dark. Fix: log `X-Forwarded-For`, add the balancer to `ignoreip`, rerun `fail2ban-regex` on a day of logs, and keep SSH and the firewall's own rate limit as separate layers.
