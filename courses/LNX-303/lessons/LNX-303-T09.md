## The server model

Everything the server stores is encrypted with a data key, which is encrypted with a **master key**. At initialisation the master key is split with Shamir's secret sharing into **unseal key** shares. A restarted server is **sealed** until a quorum (say three of five) enters shares; with **auto-unseal** a cloud KMS, an HSM or a second server does it. After unsealing, clients authenticate and receive a **token** with a time to live and attached **policies**.

OpenBao is the open-source (MPL-2.0) fork of Vault made after HashiCorp moved Vault to the Business Source License in 2023; the CLI is `bao`, the API is under `/v1/`, and its 2.0 release was API compatible with Vault 1.14.9 without the Enterprise features, and later releases add and remove features independently, so read the OpenBao release notes before moving a Vault configuration across.

```bash
bao operator init -key-shares=5 -key-threshold=3     # prints shares and a root token once
bao operator unseal                                  # repeat until the threshold
bao policy write payments payments.hcl
bao auth enable approle
bao write auth/approle/role/payments token_policies=payments token_ttl=1h
```

## Policies

```hcl
path "secret/data/payments/*"     { capabilities = ["read"] }
path "database/creds/payments-ro" { capabilities = ["read"] }
path "sys/*"                      { capabilities = ["deny"] }
```

Capabilities: create, read, update, delete, list, patch, sudo and deny, and deny wins. KV version 2 puts data under `secret/data/...` and metadata under `secret/metadata/...`, a frequent source of policies that match nothing. Never leave the root token in use; revoke it and keep a break-glass procedure to generate a new one.

## Authentication and delivery

AppRole suits machines: a role id plus a secret id delivered by a trusted orchestrator, ideally response-wrapped and single-use. Kubernetes auth checks a pod's service-account token. JWT/OIDC suits CI. Delivery tools (an agent sidecar, Vault Secrets Operator, External Secrets Operator, Secrets Store CSI driver) keep the application unaware of the server. **Dynamic secrets** create a database user per lease and drop it at expiry. The **transit** engine encrypts for applications without exposing keys, and the **PKI** engine issues short-lived certificates (compare topic 1). Audit devices log every request; with audit enabled, the server stops serving if all devices fail, so configure two.

## sops and age

sops encrypts the values of YAML, JSON and ENV files and leaves keys readable, so diffs and reviews work. age provides simple modern key pairs.

```bash
age-keygen -o key.txt                       # prints the public recipient; keep key.txt secret
cat > .sops.yaml <<'EOF'
creation_rules:
  - path_regex: secrets/.*\.yaml$
    age: age1...recipient
EOF
sops encrypt --in-place secrets/app.yaml    # older releases: sops -e -i
SOPS_AGE_KEY_FILE=key.txt sops exec-env secrets/app.yaml './run-app'
```

Every recipient can decrypt the whole file, and removing a recipient does not revoke data already encrypted to them: rotate the secrets themselves. Put the identity file in a password manager or hardware-backed store and never commit it.

## Which one

| Need | Use |
|---|---|
| encrypted config in Git, no runtime service | sops with age |
| short-lived credentials, per-workload policy, audit | secrets server |
| certificates or encryption as a service | PKI and transit engines |
| both | sops for bootstrap data, the server for runtime secrets |

## Worked example: the committed key

A developer commits `key.txt` with a sops file; the repository later becomes public. Rewriting history is not enough: assume the key is exposed, generate a new one, re-encrypt, and rotate every secret in the old file. Prevent it with `.gitignore`, a pre-commit secret scanner, and identity files kept outside the working tree.
