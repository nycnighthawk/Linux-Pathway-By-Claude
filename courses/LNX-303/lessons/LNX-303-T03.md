# Secure Boot, signed modules

This lesson follows the topic synthesis `synth/LNX-303/LNX-303-T03.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Describe the chain from firmware to kernel module and name the key stores involved.
- Read the Secure Boot state of a machine and the keys it trusts.
- Enrol a local signing key and sign an out-of-tree module.
- Explain how revocation works and why it can break old media.

## The chain, link by link

1. **Firmware** checks the first loader against the **db** and refuses anything in the **dbx**. The key hierarchy is Platform Key (owner), Key Exchange Keys (who may update the databases), db (allowed) and dbx (forbidden).
2. **shim** is a small loader signed through Microsoft's third-party certificate. It verifies the next stage against the distribution's certificate and the **Machine Owner Key** list (MOK), and it checks **SBAT** generation numbers so a whole family of vulnerable loaders can be revoked in one entry.
3. **GRUB or systemd-boot** loads the kernel through shim's verification service.
4. The **kernel** carries its own keys. It accepts only modules signed by a key in its trusted keyrings, which include keys shim passes up from MOK.
5. **Lockdown** (`lockdown=integrity` or `confidentiality`, reported in `/sys/kernel/security/lockdown`) stops a privileged user from bypassing the chain by writing memory or loading code through `kexec`.

The initramfs is not signed by this chain. A **unified kernel image** (kernel, initramfs and command line in one signed file) closes that gap.

## Inspect

```bash
mokutil --sb-state                 # SecureBoot enabled / disabled
mokutil --list-enrolled            # MOK keys
mokutil --db ; mokutil --dbx       # firmware databases
bootctl status                     # systemd-boot view
cat /sys/kernel/security/lockdown  # none [integrity] confidentiality
modinfo -F signer some.ko          # who signed a module
fwupdmgr security                  # includes Secure Boot and dbx update state
```

## Sign an out-of-tree module

Create a certificate for code signing only, enrol it, then sign.

```bash
openssl req -new -x509 -newkey rsa:3072 -nodes -days 1825 -subj "/CN=Local module signing/" \
  -addext "basicConstraints=critical,CA:FALSE" -addext "keyUsage=critical,digitalSignature" \
  -addext "extendedKeyUsage=codeSigning" -outform DER -out mok.der -keyout mok.priv
chmod 600 mok.priv
mokutil --import mok.der          # asks for a one-time password; confirm in the blue MOK screen at next boot
/usr/src/linux-headers-$(uname -r)/scripts/sign-file sha256 mok.priv mok.der module.ko
```

DKMS and Debian's `kmodsign` do the signing step on every rebuild once the key paths are configured. If a module is rejected with `Key was rejected by service`, the key is not enrolled or the module was signed with a different key. Disabling Secure Boot is the wrong remedy: it removes protection for every other component.

## Revocation and its cost

A vulnerable signed binary is a bypass until revoked. Revocation means adding its hash or certificate to the dbx, or raising an SBAT level, usually through `fwupdmgr` or a distribution package. The price is that old installers and rescue discs stop booting. Microsoft's 2011 Secure Boot certificates (the KEK and the third-party UEFI CA that signs shim) reached their published expiry dates in 2026, and their 2023 replacements must be present in the firmware KEK and db. Firmware does not check the dates, so binaries already signed keep booting; the risk is a machine whose db lacks the 2023 CA, which will refuse shim and boot media signed only with the new key. Check with `mokutil --db` or `fwupdmgr security`, update the databases through `fwupd` or the vendor firmware, and confirm the steps in current vendor advisories. Microsoft's published dates are June 2026 for the KEK CA 2011 and the UEFI CA 2011, and October 2026 for the Windows Production PCA 2011; secondary sources differ by a few days within June, so take exact days from Microsoft's Secure Boot certificate expiration article (KB5062710).

## Worked example: the missing driver after an update

A server upgrades its kernel and the storage driver module no longer loads. `dmesg` shows the module was rejected; `modinfo -F signer` shows a one-off build key. The module had been built by hand with an ephemeral key. Fix: create a persistent code-signing key, enrol it with `mokutil --import`, rebuild through DKMS so every future kernel gets a signature, and record the key owner and expiry date in the asset register.
