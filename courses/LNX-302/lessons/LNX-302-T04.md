# SMB clients with Kerberos

This lesson follows the topic synthesis `synth/LNX-302/LNX-302-T04.md`, which carries the sources and the history.

## What you will be able to do

- Use `smbclient`, `smbget` and `rpcclient` with Kerberos instead of a password.
- Write a `mount.cifs` command or `fstab` line with `sec=krb5`, `cruid=`, `multiuser` and encryption.
- Explain the kernel upcall chain: `cifs.upcall`, `request-key`, credential cache and keytab.
- Diagnose the commonest failures: CNAME names, expired tickets, missing keys.

## The problem the kernel cannot solve

The kernel `cifs` client cannot run Kerberos: it cannot read a credential cache, ask a KDC or prompt. So it asks the keyring subsystem for a key of type `cifs.spnego`, and `request-key` runs a user-space helper, `cifs.upcall`, which finds the user's ticket for `cifs/<server>`, builds a SPNEGO blob and returns it. The user-space tools (`smbclient -k`, `--use-kerberos=required`) do Kerberos themselves with the same credential cache.

## Prerequisites in order

1. A valid TGT: `kinit alice@ACME.EXAMPLE`, then `klist`.
2. A server name, not an IP, matching a `cifs/` or `host/` principal. Use the canonical FQDN.
3. Clocks within five minutes.
4. `cifs-utils` installed, with the `cifs.spnego` rule in `/etc/request-key.d/`.
5. `/etc/krb5.conf` that finds the realm and a cache the helper can read.

## Mounting

```bash
mount -t cifs //files.acme.example/projects /mnt/projects \
  -o sec=krb5,vers=3.1.1,cruid=1001,uid=1001,gid=1001,file_mode=0640,dir_mode=0750,seal
```

| Option | Meaning |
|---|---|
| `sec=krb5` | Kerberos authentication (`krb5i` adds signing on older dialects) |
| `cruid=` | whose credential cache the helper reads (a root mount would otherwise look in root's) |
| `uid=`, `gid=`, `file_mode`, `dir_mode` | apparent ownership; the server's real owner is a SID |
| `vers=3.1.1` | pin the dialect to detect a downgrade |
| `seal` | SMB3 encryption (SMB 3.0 or later) |
| `multiuser` | a separate SMB session per local user, each with that user's credentials; implies `noperm`, because the server now enforces access |

A boot-time mount as root works from the machine keytab; per-user access needs each user's own ticket.

## Worked example 1: the CNAME

A team publishes `files` as a CNAME for `fs07.acme.example`. The mount with `sec=krb5` returns `Required key not available`. `cifs.upcall` debug output shows a request for `cifs/files.acme.example` and "Server not found in Kerberos database". Remedies: use the canonical name, or register the alias as an SPN on the server (`setspn -S cifs/files.acme.example FS07` on Windows, `net ads setspn add` on Samba). Do not switch on `--trust-dns`: it lets whoever controls DNS choose the server you authenticate to.

## Worked example 2: tickets expire

A nightly job fails on the second night. It uses a ticket cache from a login that ended; the ticket lived ten hours. Give the job its own keytab-backed identity (`kinit -k -t`) or let SSSD renew, and monitor `klist -s`.

## Policy knobs

`client signing = mandatory` and `client smb encrypt = required` in `smb.conf` or `client.conf` set the default for tools. A client demanding signing against a server that offers none fails negotiation. Test with `sec=krb5` explicitly: a mount that works with NTLM only proves the password, not the Kerberos setup.

## Common mistakes

- Mounting by IP address.
- Leaving `cruid` unset on a root-run mount.
- Assuming `ls -l` ownership is real. Without the SMB3 POSIX extensions it is invented; use `getcifsacl` with the `cifsacl` option to see the descriptor.
