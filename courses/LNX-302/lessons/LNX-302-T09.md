# NFSv4 with Kerberos

This lesson follows the topic synthesis `synth/LNX-302/LNX-302-T09.md`, which carries the sources and the history.

## What you will be able to do

- Explain why `AUTH_SYS` is not authentication and what RPCSEC_GSS adds.
- Choose between `krb5`, `krb5i` and `krb5p` for an export.
- Prepare principals and keytabs for server and client, and write the export and mount options.
- Fix the typical failures: names mapped to `nobody`, boot-time hangs, expired tickets.

## The weakness being fixed

With `AUTH_SYS` the client states a uid and the server believes it; root on any client can claim to be anyone, and uid 1001 must mean the same person everywhere. RPCSEC_GSS wraps each connection in a GSS context, in practice Kerberos 5, with three protection levels: `krb5` (authentication), `krb5i` (adds an integrity checksum on each call), `krb5p` (encrypts the payload, at a CPU cost). NFSv4 uses one port (TCP 2049), makes strong security mandatory to implement, and names owners as `user@domain` strings instead of numbers.

## The parts

- A KDC (the AD domain, or FreeIPA) that knows users and machines.
- Server: a keytab entry `nfs/nfs01.example.com@REALM` holding AES keys (`klist -ke`). For AD, `net ads keytab add nfs` or `adcli` also registers the SPN.
- Client: a `host/client.example.com@REALM` entry, used to mount at boot and before users log in. `rpc-gssd.service` runs when a keytab exists.
- Id mapping: both ends resolve `alice@example.com` through NSS. The domain defaults to the DNS domain; set `Domain =` in `/etc/idmapd.conf` or publish `_nfsv4idmapdomain`. Recent clients use `nfsidmap`.
- The same identity source and ranges on both ends, as in [T02](lesson:LNX-302-T02).

## Configuration

```text
# /etc/exports
/srv/export/projects   *.example.com(rw,sync,sec=krb5p,no_subtree_check)
/srv/export/public     *.example.com(ro,sync,sec=krb5:krb5i:krb5p)
```

`exportfs -rav` applies, `exportfs -v` shows. Open TCP 2049 only, and disable NFSv3 if unneeded: Kerberos does not cover its auxiliary protocols.

```bash
mount -t nfs4 -o sec=krb5p,vers=4.2 nfs01.example.com:/srv/export/projects /mnt/projects
```

Root accesses with the machine principal; every other user needs a ticket, from login (SSSD, `pam_krb5`) or `kinit`, renewed because tickets last hours. Name the flavour explicitly instead of letting the client pick the strongest on offer. NFSv4 ACLs use `nfs4_getfacl`/`nfs4_setfacl` and map imperfectly to POSIX ACLs.

## Worked example: files owned by `nobody`

`kinit` worked, yet files show `nobody`. The server's idmap domain is `example.com`, the client's DNS domain is `corp.example.com`, so the strings do not match. Set the same `Domain` on both, then clear cached failures on the client with `nfsidmap -c`; `nfsidmap -l` lists keys.

Second case: boot waits two minutes at the mount. `rpc.gssd -vvv` says no credentials: the client was cloned from an image joined before cloning, so it has no `host/` entry of its own. Rejoin the clone, and use `_netdev,x-systemd.automount,x-systemd.mount-timeout=30` so a missing server cannot block boot.

Third case: a nightly job works once, then fails. The user ticket expired. Use a service account with a keytab and `kinit -k -t` in the unit, and watch `klist -s`.

## Common mistakes

- Using a DNS alias with no principal.
- Keytabs with RC4 only against a domain that is retiring RC4.
- `no_root_squash` on an exported home directory: a compromised client keytab then compromises the export.
