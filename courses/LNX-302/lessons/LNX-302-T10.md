# Linux in a genuine AD estate

This lesson follows the topic synthesis `synth/LNX-302/LNX-302-T10.md`, which carries the sources and the history.

## What you will be able to do

- Enrol hosts without a standing administrator password and keep the computer objects tidy.
- Express who may log in and who may become root as group membership, and roll out enforcement safely.
- Decide what AD policy may configure on Linux and what stays with configuration management.
- Survive directory hardening changes (LDAP signing and channel binding, AES-only Kerberos, NTLM reduction).
- Write the operating agreement with the directory team.

## The shift in viewpoint

Earlier topics taught mechanisms. A real estate has a directory team, a change calendar and an auditor. You fit into their system: you request groups, you inherit their naming, and you suffer their patch weekends.

## Enrolment

- **Delegated join account** with rights on one OU only: `realm join --computer-ou='OU=Linux,OU=Servers,DC=acme,DC=example' -U svc-join`, secret from a vault.
- **Pre-staged object with a one-time password**: `adcli preset-computer`, then `realm join --one-time-password=...`; nothing lasting is left on the host.
- Join after cloning, never before. Unique names; reuse or remove old objects deliberately.

## Access and privilege

Layers, in the order an auditor reads them: AD groups for Linux access; the SSSD access provider (`simple_allow_groups`, or `ad` with `ad_gpo_access_control`); per-service rules (`AllowGroups` in sshd, `pam_access`); sudo rules naming groups, never people: `%lnx-admins-prod@acme.example ALL=(ALL) ALL`. Roll GPO access control out as `permissive`, read the journal, then switch to `enforcing`. Central sudo rules and host-based access control are available natively in FreeIPA/IdM, trusted to AD, without changing the AD schema. Keep SELinux enforcing and map users to confined SELinux users.

## Policy

Three levels exist: Windows logon-right policy read by SSSD; `samba-gpupdate`, which applies a set of Samba policy extensions; and distribution agents such as `adsys` on Ubuntu. The Windows team must import the templates and link the policy. Split ownership: AD policy for identity-related settings, configuration management for everything else, no setting owned by both.

## Surviving directory changes

Checklist for a Linux member of a hardened domain:

- LDAP over TLS (`ldap_id_use_start_tls = true`, DC certificates trusted) so signing and channel binding can be required.
- Kerberos with AES keys only: `klist -ke` on the keytab, no RC4-only settings in `krb5.conf`.
- No hidden NTLM dependencies (applications using `ntlm_auth`, permissive `ntlm auth`).
- SMB signing on, strong Netlogon secure channel for Samba members.
- DNS and time per [T05](lesson:LNX-302-T05).

Test each directory change on a staging DC with a Linux test host before it reaches production. Enforcement dates and phases differ by Windows release (to verify for the release in use).

## Lifecycle

Machine passwords rotate about every 30 days. Monitor `net ads testjoin` or `sssctl domain-status`, keytab age and `chronyc tracking`. Keep a local break-glass account with an offline key and an alarm on use. Decommission with `realm leave` plus deletion of the computer object and DNS records. Report computer objects whose password is older than 90 days.

## Worked example: the Monday outage

After a weekend of DC patching, every Linux server rejects AD logins; SSSD logs `Strong(er) authentication required` on its LDAP bind. SSSD used a plain `ldap://` simple bind. Immediate fix: `ldap_id_use_start_tls = true` with the CA trusted, pushed by configuration management. Lasting fix: a staging DC that gets each hardening change a week early. The break-glass account got the team in, and its use was recorded.

Second case: a sudoers line named `%Domain Admins` and matched a local group with the same short name. Use fully qualified group names, and make the pipeline reject short ones.

## Security stance

A Linux server holding a machine keytab is a domain credential. Whoever can add themselves to the Linux admin group, alter OU inheritance or reset the computer object's password gains root on those hosts. Treat Linux members in the same protection tier as Windows servers.
