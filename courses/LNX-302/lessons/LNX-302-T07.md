# Windows clients and printing

This lesson follows the topic synthesis `synth/LNX-302/LNX-302-T07.md`, which carries the sources and the history.

## What you will be able to do

- Join a Windows client to a Samba AD domain and apply group policy from a Windows administration host.
- Provide drive letters through a logon script, group policy preferences and DFS.
- Configure a Samba print server on CUPS with `[printers]` and `[print$]`.
- Explain why driver installation is restricted on modern Windows and choose an IPP-based design.

## The client side of the estate

A Windows Pro, Education or Enterprise client joins by pointing its DNS at a DC and using `Add-Computer -DomainName acme.example -Credential ACME\Administrator -Restart`. It finds a DC through SRV records, site-aware. Group policy lives in SYSVOL; the machine reads `gPLink` from LDAP and the files from `\\acme.example\SYSVOL` (so replication and the PDC-emulator discipline from [T03](lesson:LNX-302-T03) matter). Edit policy with the Group Policy Management Console on a Windows host with RSAT. Check on the client: `gpupdate /force`, `gpresult /r`.

## Drives and folders

| Mechanism | Notes |
|---|---|
| Logon script (`scriptPath`, NETLOGON) | oldest, simplest: `net use H: \\files\home\%USERNAME%` |
| Group policy preferences, Drive Maps | per user or computer, targeted by group or site |
| Folder redirection | Documents and Desktop on the server, cached offline |
| DFS namespace | one name, several targets; Samba serves a root with `host msdfs = yes` and `msdfs:` links but does not replicate between targets |

Use the file server's canonical name so Kerberos single sign-on works.

## The Samba print server

CUPS owns the queues; `smbd` exposes them through the spoolss interface and two special shares.

```ini
[global]
    printing = cups
    printcap name = cups
    load printers = yes

[printers]
    path = /var/tmp
    printable = yes
    browseable = no

[print$]
    write list = @printadmin
    read only = yes
    path = /srv/samba/print-drivers
```

`print$` is the driver repository; administrators upload drivers from the Windows printer properties dialog or with `rpcclient` (`adddriver`, `setdriver`, `enumdrivers`, `enumprinters`). `cups options = raw` passes jobs unchanged, which suits a native Windows driver; without it CUPS filters the job. Administer queues with `lpadmin`, `lpstat -p -d`; the CUPS `error_log` is the first stop for a vanished job. A driverless queue needs no vendor driver on Linux:

```bash
lpadmin -p floor2 -E -v ipp://10.0.2.40/ipp/print -m everywhere
```

## Why driver download is restricted

Point and Print installed server-supplied drivers as SYSTEM, which the 2021 PrintNightmare flaws turned into an attack path. Since then a standard user cannot install a driver from a server unless policy allows it, the server is on an approved list, or the driver is already staged on the client. Microsoft is also steering to inbox IPP class drivers (details and dates to verify): queues that publish standard IPP formats work everywhere, queues that need a vendor driver increasingly do not.

Hardening: disable printer sharing where unneeded and do not run `cups-browsed` on servers; its 2024 vulnerabilities allowed unauthenticated remote printer injection.

## Worked example: output is pages of PostScript

The Windows queue uses a PostScript driver, the printer speaks PCL, and the Samba share has `cups options = raw`, so nothing converts the job. Remove the raw option or install the PCL driver on the client. `lpstat -o` and the CUPS page log show whether the job passed the filters.

Second case: connecting fails with error `0x0000011b` after a monthly update. The server did not change; client RPC and Point and Print policy did. Prefer staging drivers or an IPP queue, and use the canonical server name.

## Common mistakes

- Home drive scripts that run before the network and ticket exist on laptops.
- Publishing printers into AD and never removing them.
- Three access layers (Samba, CUPS policy, NT ACL) denying independently; test each.
