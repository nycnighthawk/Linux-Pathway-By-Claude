# Ansible managing Windows

This lesson follows the topic synthesis `synth/LNX-302/LNX-302-T08.md`, which carries the sources and the history.

## What you will be able to do

- Pick a connection plugin (`psrp`, `winrm`, `ssh`) and an authentication method for a Windows group in the inventory.
- Write an idempotent play with `ansible.windows` modules and handle reboots.
- Explain the double hop and three ways to get around it.
- Recognise insecure shortcuts (Basic over HTTP, ignored certificates) and replace them.

## What is different from Linux

No Python on the target, a PowerShell payload per task, cmd or PowerShell quoting, and a Windows identity model. Targets run Windows Server 2016 or Windows 10 and later, which carry PowerShell 5.1, so there is nothing to install besides enabling a transport. Collections: `ansible.windows` (core modules), `community.windows`, `microsoft.ad` (directory objects), plus Chocolatey for packages.

## Connections

```yaml
# group_vars/windows.yml
ansible_connection: psrp
ansible_port: 5986
ansible_psrp_protocol: https
ansible_psrp_auth: kerberos
ansible_psrp_cert_validation: validate
ansible_user: svc-ansible@ACME.EXAMPLE
```

| Plugin | When |
|---|---|
| `psrp` | domain default over WinRM; steadier under load than `winrm`, better proxy support |
| `winrm` | older plugin, same protocol |
| `ssh` | non-domain hosts; key authentication; officially supported from Ansible 2.18; set `ansible_shell_type` |

Authentication: Kerberos in a domain (FQDN in the inventory, a ticket from `kinit` or a keytab, time and DNS right); NTLM for local accounts; certificate for passwordless automation; CredSSP only where delegation is unavoidable; Basic only over HTTPS in a lab. Keep certificate validation on and trust the internal CA on the control node.

## Idempotent modules

```yaml
- hosts: windows_files
  tasks:
    - ansible.windows.win_feature:
        name: [FS-FileServer]
        state: present
      register: feat
    - ansible.windows.win_reboot:
      when: feat.reboot_required | default(false)
    - ansible.windows.win_service:
        name: w32time
        start_mode: auto
        state: started
```

Run it twice: the second run must report no change. `win_shell` reports `changed` every run unless you set `changed_when`, so use a module when one exists. `win_dsc` reaches the DSC resource ecosystem. Use `microsoft.ad` against Windows DCs; Samba DCs do not provide Active Directory Web Services, so use `samba-tool` or LDAP modules there. Check which modules your collection version covers before relying on them.

## Privilege and the double hop

`become: true` with `become_method: runas` runs as SYSTEM or a named user and exists because some operations fail in WinRM's network logon (MSI installs, Windows Update, DPAPI). The double hop: a network logon has no credentials for a second server, so `win_copy` from a share fails with "Access is denied". Fixes: `become` with explicit credentials (kept in vault), constrained delegation on the target computer object, CredSSP for that task only, or fetch through the control node.

## Worked example: first contact and a hang

`ansible windows -m ansible.windows.win_ping` returns `pong` when DNS, time, ticket, listener and certificate all work. A play that hangs and then reports `Server not found in Kerberos database` used an IP address in the inventory; Kerberos needs the FQDN. `the specified credentials were rejected` is a password or logon-right problem; `certificate verify failed` is the control node's trust store, not Windows. Do not set validation to `ignore` to make the symptom go away.

## Common mistakes

- Group policy and Ansible both owning one registry key: perpetual `changed` and a flickering policy. Decide ownership per setting.
- Passwords in inventory or logs (use vault and `no_log: true`).
- A long-lived controller whose Kerberos ticket expired after ten hours.
