# Line-rate measurement

This lesson follows the topic synthesis `synth/LNX-202/LNX-202-T10.md`, which carries the history and the sources.

## What you will be able to do

- Plan a throughput test, run it with iperf3 and record what makes it repeatable.
- Compute line rate in packets per second and recognise per-packet limits.
- Find the bottleneck from CPU, interrupt and driver counters.

## Method

State the question (raw link, single flow, small packets, application), test in stages (direct cable, switch, real path), record NIC, driver, kernel, MTU, offloads, bond mode and CPU governor, run 30 to 60 seconds, repeat and report the spread.

```bash
iperf3 -s                                   # server
iperf3 -c 192.0.2.20 -t 30                  # one stream
iperf3 -c 192.0.2.20 -t 30 -P 8             # parallel streams
iperf3 -c 192.0.2.20 -t 30 -R               # reverse direction
iperf3 -c 192.0.2.20 -u -b 9G -l 1400 -t 30 # UDP at a target rate
```

One TCP stream uses one core, so fast links need `-P`. iperf3 uses TCP port 5201 for control. UDP tests may need larger socket buffers (`net.core.rmem_max`).

## Arithmetic

Each Ethernet frame costs 20 more bytes on the wire (preamble and gap). At 10 Gb/s: 10 000 000 000 / ((64 + 20) x 8) is about 14.88 million frames per second at 64 bytes and about 812 000 per second at 1518 bytes. Small-packet tests need `pktgen` or a dedicated generator.

## Finding the bottleneck

```bash
mpstat -P ALL 1                  # one core at 100% in soft-irq or sys
ethtool -S eth0 | grep -Ei 'drop|miss|err|fifo'
ip -s -s link show eth0; nstat -az | grep -Ei 'retrans|drop'
ethtool -l eth0; ethtool -g eth0 # queues and rings
```

Typical findings: one queue saturated (add queues, spread interrupts, use parallel streams), rx ring overruns (`ethtool -G`), MTU mismatch, power governor, or encryption overhead. A bond helps only across many flows.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| One stream reaches a fraction of the link | single-core limit | `mpstat -P ALL`, `-P N` |
| UDP loss blamed on the network | receive buffer too small | `nstat`, `net.core.rmem_max` |
| Results differ between runs | other traffic, power states | repeat, quiet the link |
| Fast with large frames, slow with small | per-packet cost | packets per second, queues |

3. What belongs in a test report besides the number?
4. How do you tell the network from the host as the cause of UDP loss?
