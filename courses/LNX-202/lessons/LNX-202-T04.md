## What you will be able to do

- Separate the authoritative and recursive roles and configure each.
- Write and check a zone, restrict transfers and recursion, and read the result with `dig`.
- Read a DNSSEC failure and know where to look.

## Authoritative BIND

```
options { directory "/var/named"; recursion no; allow-transfer { none; }; };
zone "example.lan" IN { type primary; file "example.lan.db"; };
```

A zone file has `$TTL`, an SOA record (primary, contact, serial, refresh, retry, expire, negative TTL), NS records and data. The serial must increase on every change or secondaries will not transfer. Check, reload, query:

```bash
named-checkconf; named-checkzone example.lan /var/named/example.lan.db
rndc reload example.lan
dig @127.0.0.1 example.lan SOA +norec; dig -x 192.0.2.10 @127.0.0.1
```

Secondaries use `type secondary; primaries { ... };`, are told of changes by NOTIFY and fetch with AXFR or IXFR; authenticate transfers with a TSIG key (generate it with `tsig-keygen`, use hmac-sha256).

## Recursive Unbound

```
server:
    interface: 192.0.2.53
    access-control: 192.0.2.0/24 allow
    hide-version: yes
    local-zone: "lab.example." static
    local-data: "router.lab.example. A 192.0.2.1"
forward-zone:
    name: "corp.example."
    forward-addr: 198.51.100.7
```

By default Unbound answers only localhost. Tools: `unbound-checkconf`, `unbound-control reload`, `unbound-control flush NAME`. A forwarder on a loopback address needs `do-not-query-localhost: no`.

## DNSSEC

A signed zone has DNSKEY, RRSIG and NSEC or NSEC3 records, and the parent holds a DS record that hashes the child's key-signing key. A validating resolver starts at the root key and sets the `ad` flag when the chain holds; a failure gives SERVFAIL.

```bash
dig +dnssec example.org SOA         # RRSIG and the ad flag
dig +cd +dnssec example.org SOA     # checking disabled: works if validation is the problem
delv example.org SOA +rtrace
```

BIND signs automatically with `dnssec-policy default;`; the manual step is to publish the DS record at the parent.

## Common failure patterns

| Symptom | Likely cause | First thing to check |
|---|---|---|
| Secondary serves old data | serial not raised, or NOTIFY blocked | `dig SOA` on both servers |
| SERVFAIL only through the validating resolver | expired signature or stale DS | `dig +cd`, `delv` |
| Resolver answers the whole Internet | recursion open to everyone | `allow-recursion`, `access-control` |
| Truncated answers, failures on large responses | TCP 53 or large UDP blocked | firewall |

## Self-check

1. Why should an authoritative server on a public address have recursion off?
2. What does `dig +cd` tell you?
3. What must you do after each zone change besides reloading?
4. Where does the DS record live and who publishes it?
