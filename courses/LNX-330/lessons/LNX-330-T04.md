# In-tree and out-of-tree modules

This lesson follows the topic synthesis `synth/LNX-330/LNX-330-T04.md`. Module build details change between kernel versions; check `Documentation/kbuild/modules.rst` in your tree (to verify).

## What you will be able to do

- Write a correct Makefile for an out-of-tree, multi-file module.
- Explain how `modprobe`, `depmod`, `vermagic` and CRC versioning decide whether a module loads.
- Read taint flags and say why `MODULE_LICENSE` matters.
- Decide when code belongs in the tree.

## A module and its Makefile

```
ifneq ($(KERNELRELEASE),)
obj-m   := hello.o
hello-y := main.o util.o
ccflags-y := -DDEBUG -I$(src)/include
else
KDIR ?= /lib/modules/$(shell uname -r)/build
all:
	$(MAKE) -C $(KDIR) M=$(CURDIR) modules
clean:
	$(MAKE) -C $(KDIR) M=$(CURDIR) clean
endif
```

- The first half runs when kbuild includes the file; the second half runs when you type `make`.
- List the parts of a multi-file module in `name-y`, never in `obj-m`. Listing each file in `obj-m` builds separate modules with unresolved symbols.
- The module name must differ from every one of its part names.
- `MODULE_LICENSE("GPL")` is needed: without it modpost warns and the kernel is tainted on load.

## Loading

| Tool | Does |
|---|---|
| `insmod x.ko` | loads one file, no dependency lookup |
| `modprobe x` | loads by name, with dependencies from `modules.dep` |
| `depmod` | rebuilds the dependency database after install |
| `modinfo`, `lsmod`, `rmmod` | inspect, list, unload |

A module loads only if `vermagic` matches the kernel and, with `CONFIG_MODVERSIONS`, the symbol CRCs match. Typical errors: `Invalid module format`, `Unknown symbol`, `disagrees about version of symbol`.

## Taint

`/proc/sys/kernel/tainted` holds a bitmask. Proprietary or out-of-tree modules and forced loads set bits, and maintainers often decline to debug a tainted kernel. Reproduce on a clean kernel in a VM.

## In tree or out

In tree: source in the subsystem directory, a Kconfig entry, a Makefile line with the `CONFIG_` symbol. Anyone who changes an internal interface fixes your driver. Out of tree: you track every release yourself, often with DKMS. Kernel policy keeps the user-space ABI stable and internal interfaces free to change.
