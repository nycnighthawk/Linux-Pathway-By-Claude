# Boot testing with QEMU and virtme-ng

This lesson follows the topic synthesis `synth/LNX-330/LNX-330-T03.md`. Option spellings can differ between QEMU and virtme-ng versions, so check `--help` on your install (to verify).

## What you will be able to do

- Boot a kernel in QEMU with `-kernel`, a serial console and a timeout.
- Give the guest a first process: initramfs, disk image or the host's filesystem.
- Report pass or fail to the host with the serial log or the debug-exit device.
- Turn panics and hangs into clean, bounded failures.

## The smallest boot test

```
timeout 60 qemu-system-x86_64 -nographic -no-reboot -m 512 \
  -kernel arch/x86/boot/bzImage \
  -append "console=ttyS0 panic=-1"
```

- `-kernel` skips the boot loader. `-nographic` sends the console to your terminal.
- `console=ttyS0` is required for kernel messages to appear; `panic=-1` reboots at once after a panic and `-no-reboot` turns that reboot into an exit.
- With no root filesystem the kernel panics when it cannot mount root. That panic proves the kernel started, so a smoke test can accept it.
- Without KVM QEMU uses TCG, which is much slower. Allow for it in timeouts.

## A userland for the guest

| Choice | Flag | Best for |
|---|---|---|
| initramfs | `-initrd rootfs.cpio.gz` | fast, controlled kernel tests |
| disk image | `-drive file=disk.img,if=virtio` and `root=/dev/vda` | filesystem and storage tests |
| host filesystem | `virtme-ng` | interactive work with full tools |

virtme-ng shares the host `/` into the guest read-only and adds a writable overlay, so one command in a kernel tree boots your build with a shell.

## Reporting results

1. **Serial scraping**: the guest prints a marker, the host greps the log. Simple, but output can interleave.
2. **Debug-exit**: add `-device isa-debug-exit,iobase=0xf4,iosize=0x04`. A guest write of V to port `0xf4` ends QEMU with status `(V << 1) | 1`. Writing `0x10` gives 33.
3. **Shared file or virtio-serial**: for richer results.

Other architectures use semihosting or a test-finisher device instead of the x86 port.

## Hangs and panics

- Always wrap QEMU in `timeout`.
- `panic=-1` plus `-no-reboot` ends the run on a panic. `oops=panic` makes the first oops fatal.
- Record the accelerator (KVM or TCG) and the full command line in every log.

## Debugging with GDB

Add `-s -S` to QEMU. In GDB run `target remote :1234` and `file vmlinux`. Build with debug info and boot with `nokaslr` so breakpoints land on the right addresses.

## Limits

A VM is not hardware. Timing, DMA and device quirks differ, and TCG hides some races. A pass means the code path ran, not that real devices work.

## Lab

`boot-exit`: finish a 512-byte boot sector so it prints a line on COM1 and makes QEMU exit with status 33 through the debug-exit port.
