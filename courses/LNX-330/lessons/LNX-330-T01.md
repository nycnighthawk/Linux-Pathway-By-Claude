# The kernel tree, releases, stable and long-term branches, and maintainers

This lesson follows the topic synthesis `synth/LNX-330/LNX-330-T01.md`. Release numbers change weekly; read `https://www.kernel.org/releases.json` for the live state and treat any number in this lesson as a snapshot (16 November 2026).

## What you will be able to do

- Read a kernel version string and say what is upstream and what is the distribution's.
- Place a branch on the map: mainline, `-rc`, stable, longterm, end of life, `linux-next`.
- Choose the base tree and the right tags for a feature and for a fix.
- Read a `MAINTAINERS` entry and find who should see a patch.

## The rhythm

A cycle is about nine to ten weeks. The first two weeks are the merge window: maintainers send pull requests and Linus merges. Then `-rc1`, a release candidate each week with fixes only, and the release after `-rc7` or `-rc8`. The next window opens at once. A change that misses the window waits for the next cycle.

## Branches

| Branch | What it is | Receives |
|---|---|---|
| mainline | Linus's tree | everything accepted for the cycle |
| `linux-next` | daily merge of subsystem trees (`next-YYYYMMDD`) | nothing; it is an integration test |
| stable `x.y.z` | fixes copied from mainline after a release | small fixes already upstream |
| longterm | one branch a year kept for years | the same, until its end-of-life date |
| end of life | no further updates | nothing |

Never base work on `linux-next`: its history is rebuilt daily.

## Version strings

`uname -r` shows `6.12.117-generic` or `6.12.0-55.el10.x86_64`. The first three numbers are upstream (major, minor, stable level); the rest is the distribution's. A distribution kernel named 6.12 can hold thousands of backports, so "the bug is in 6.12" needs a qualifier.

## Maintainers and tags

`MAINTAINERS` entries carry `M:` maintainers, `R:` reviewers, `L:` list, `S:` status, `T:` tree and `F:` file patterns. `scripts/get_maintainer.pl file-or-patch` applies them. Base a feature on the tree named by `T:`. A fix for stable carries `Cc: stable@vger.kernel.org` and a `Fixes:` tag, and lands in mainline first.

## Reading history

```bash
git log --oneline v6.12..v6.13 -- drivers/net/
git describe --contains <commit>
git log --oneline --grep='<commit>' v6.6..v6.6.162   # find the stable backport
git tag --contains <backport> | grep '^v6\.6'
```

A stable fix is a new commit with its own id: its message records the mainline commit ("commit <id> upstream"). So `git tag --contains` on the mainline id finds only mainline tags; search the stable branch for the id first, then ask which tags contain the backport.

## Worked example

An operator runs `uname -r` and gets `6.6.162`. A fix is upstream commit `abc123`. Searching the 6.6 stable history for `abc123` finds its backport, and `git tag --contains` on the backport shows `v6.6.140` first among the 6.6 tags. 162 is later, so the fix is included. On a distribution kernel the package changelog decides instead. In the lab you triage a saved `releases.json`.

## What goes wrong

Basing on `linux-next`. Forgetting the stable tag so the fix never reaches LTS. Shipping a product on a stable branch that goes end of life. Reporting a distribution kernel bug upstream.
