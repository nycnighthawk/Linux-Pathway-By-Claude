# git bisect a regression

This lesson follows the topic synthesis `synth/LNX-330/LNX-330-T10.md`. Option availability depends on your Git version (to verify).

## What you will be able to do

- Bisect a range of commits by hand and with `git bisect run`.
- Write an oracle script with the right exit codes, including skip.
- Avoid the common traps: flaky tests, unbuildable commits, merges, config drift.
- Report the culprit to the right people.

## The commands

```
git bisect start <bad> <good>     # e.g. v6.12 v6.11
git bisect good | bad | skip
git bisect run ./test.sh
git bisect log | visualize
git bisect reset
```

Exit codes for `run`: 0 good, 1 to 127 (not 125) bad, **125 skip**, 128 and above abort. About log2(N) steps: roughly 14 for 10 000 commits.

For hunting a fix, use `--term-old=broken --term-new=fixed`.

## The oracle script

```bash
#!/usr/bin/env bash
make olddefconfig && make -j"$(nproc)" || exit 125   # cannot build: skip
./boot-and-test.sh || exit 1                          # reproduces: bad
exit 0
```

Make it deterministic. For a flaky bug, count a failure in any of N runs as bad, and pick N in advance.

## Traps

| Trap | Remedy |
|---|---|
| half-finished commit does not build | exit 125 |
| failure one time in ten | repeat the test, decide the count first |
| different symptom at the end | compare with the original report |
| lands on a merge | inspect the merge diff or bisect inside the branches, `--first-parent` |
| config or firmware changed | re-test both endpoints under identical conditions |
| dirty tree | keep the script outside tracked files |

## After the search

Re-test the culprit and its parent, try reverting the commit on the tip, then report it: version range, config, hardware, symptom, log, bisect log and commit id, to the maintainers from `get_maintainer.pl` and the list, saying it is a regression.

## Lab

`bisect-run`: write the oracle `test.sh`, including skip for commits whose `app.sh` does not parse, bisect 24 commits and name the first bad one.
