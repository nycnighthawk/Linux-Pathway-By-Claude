# A real upstream review cycle

This lesson follows the topic synthesis `synth/LNX-330/LNX-330-T11.md`. Subsystem rules differ; always read the target subsystem's own notes (to verify).

## What you will be able to do

- Pick a first contribution you can test.
- Run the stages from reproduction to a merged commit.
- Triage review comments and plan a v2.
- Recover from silence, rejection and conflicting advice.

## The stages

1. **Choose** something you can test: a reproducible bug (syzbot reports come with reproducers), a driver for hardware you own, a verified documentation fix. Read the `MAINTAINERS` entry and recent list traffic.
2. **Reproduce** in a VM on the tree the maintainer uses.
3. **Change** as little as is correct. Commit message: cause, effect, why this fix.
4. **Check**: warnings, checkpatch, sparse, boot test, selftests, a second configuration.
5. **Send** with `git send-email` or `b4`; maintainers To, lists Cc, `--base`.
6. **Wait**: days to weeks. One polite reminder after about two weeks.
7. **Revise**: answer every comment, wait a day, send one new version.
8. **Land**: maintainer tree, `linux-next`, merge window, release; stable if tagged.
9. **Own it**: answer regression reports about your change.

## Triage of comments

| Kind | Action |
|---|---|
| structure (split, reorder) | fix |
| style nit | fix |
| real defect | fix, add a test if possible |
| good idea, wrong series | defer: acknowledge, do it later |
| approval trailer | accept; carry it only onto patches that did not change |
| impatience, off topic | no action |

`Reviewed-by` means the reviewer examined the patch and found no objection. Silence is not approval.

## Timing

Merge window: maintainers' trees are mostly closed to new features, fixes can still go in. Do not resend without changes and do not send the same patch to several maintainers separately.

## When things go wrong

- No reply: check recipients with `get_maintainer.pl`, check the archive, ping once.
- Approach rejected: ask what would be accepted.
- Reviewers disagree: summarise and ask the maintainer to decide.
- You broke something: reply fast, revert if needed.

## Self-check

Try each question before you read the answers below.

1. Two weeks after posting, nobody has replied. What are the steps before pinging?
2. A reviewer suggests a good idea that does not belong in this series. How do you respond?
3. Two reviewers ask for conflicting changes. What do you do?

### Answers

1. Check the recipients with `get_maintainer.pl` and the list archive to make sure the patch arrived, then send one polite reminder.
2. Acknowledge it, say you will do it separately, and keep the current series focused.
3. Summarise both positions on the list and ask the maintainer to decide.
