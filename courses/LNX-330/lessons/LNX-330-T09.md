## What you will be able to do

- Trace one function's call graph with ftrace.

## printk

Levels: 0 EMERG, 1 ALERT, 2 CRIT, 3 ERR, 4 WARNING, 5 NOTICE, 6 INFO, 7 DEBUG. A message reaches the console when its level number is **lower** than the console loglevel, the first number in `/proc/sys/kernel/printk`. So `echo 5 > /proc/sys/kernel/printk` shows warnings and worse. `dmesg -l warn,err` filters the buffer, `dmesg -w` follows it. Prefer `dev_err` in drivers, `pr_*_ratelimited` in loops, `%pS` for addresses, `%pe` for errors.

## Dynamic debug

```
echo 'module foo +p' > /sys/kernel/debug/dynamic_debug/control
echo 'file foo.c line 100-140 +pfl' > /sys/kernel/debug/dynamic_debug/control
echo 'module foo -p' > /sys/kernel/debug/dynamic_debug/control
```

Flags: `p` print, `f` function, `l` line, `m` module, `t` thread. At boot use `dyndbg="module foo +p"` or `foo.dyndbg`.

## ftrace

```
cd /sys/kernel/tracing
echo foo_read > set_graph_function
echo function_graph > current_tracer
echo 1 > tracing_on
./workload; cat trace
echo nop > current_tracer
```

`set_ftrace_filter` limits the `function` tracer. `events/<group>/<event>/enable` turns on tracepoints. `trace_pipe` streams. `trace-cmd` records to a file.

## KASAN report, in reading order

1. `BUG: KASAN: <type> in <function>`: type is slab-out-of-bounds, slab-use-after-free, etc.
2. `Read/Write of size N`: the access.
3. Call trace: how execution got there.
4. `Allocated by` and `Freed by`: who owns and who released the memory.

Cost is about 2 to 3 times slower. `kasan.fault=panic` helps automation.

## lockdep report

Names the lock classes, shows the existing chain `-> #1`, `-> #0`, and a two-CPU scenario. It fires on a *possible* deadlock, even if none occurred. It reports once per boot.

## Debug configuration for a VM

`CONFIG_KASAN`, `PROVE_LOCKING`, `DEBUG_ATOMIC_SLEEP`, `DEBUG_INFO`, `DYNAMIC_DEBUG`, `FTRACE`, `UBSAN`; add `KCSAN` or `KMSAN` in separate builds. Expect a slow guest.

## Self-check

Try each question before you read the answers below.

1. The console loglevel is 4. Does a `pr_warn` message reach the console?
2. In a KASAN report, which sections tell you who owned the memory and who released it?
3. Lockdep reported a possible deadlock but the system never hung. Is the report worth fixing?

### Answers

1. No. Warnings are level 4 and only levels lower than the console loglevel are printed, so you would need 5 or more.
2. The `Allocated by` and `Freed by` stack traces after the call trace.
3. Yes. Lockdep reports an inconsistent lock order that can deadlock under the right timing, even if it has not happened yet.
