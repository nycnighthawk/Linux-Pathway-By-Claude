# Helm and Kustomize

This lesson follows the topic synthesis `synth/LNX-311/LNX-311-T08.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Install, upgrade, inspect and roll back a Helm release, and review what it will apply.
- Build a Kustomize base and overlays with patches, images and generators.
- Choose between the tools and avoid silent configuration mistakes.

## Helm in operation

A **chart** has `Chart.yaml`, default `values.yaml`, Go-template `templates/`, optional `values.schema.json` and `crds/`. A **release** is an installed instance; each revision is stored as a Secret in the release namespace, which powers history and rollback.

```bash
helm show values bitnami/nginx > defaults.yaml    # read first: this is the chart's API
helm template web bitnami/nginx -f prod.yaml      # render offline and review
helm upgrade --install web bitnami/nginx -n web --create-namespace -f prod.yaml --atomic --wait
helm history web -n web
helm rollback web 1 -n web
helm get values web -n web ; helm get manifest web -n web
```

Later `-f` files and `--set` override earlier ones. Pin the chart version. Helm 4 (November 2025) rebuilt plugins, added server-side apply support and kstatus-based waiting; check defaults in the release notes. CRDs in `crds/` are installed once and never upgraded or removed by Helm: handle them with a separate `kubectl apply --server-side`.

## Kustomize

A directory with `kustomization.yaml` lists `resources` (files or other directories) and transformations. An **overlay** names a base and adds changes:

```yaml
resources: [../../base]
namespace: shop
images: [{name: web, newTag: "1.4.2"}]
replicas: [{name: web, count: 3}]
patches:
- target: {kind: Deployment, name: web}
  patch: |-
    - op: replace
      path: /spec/template/spec/containers/0/resources/limits/memory
      value: 512Mi
configMapGenerator:
- name: web-config
  literals: [LOG_LEVEL=warn]
```

Generated ConfigMaps get a content hash in the name, so a data change rolls the pods. `kubectl kustomize DIR` renders, `kubectl apply -k DIR` applies. The `kubectl` build can be older than the standalone binary.

## Choosing

Helm for distribution and parameterisation; Kustomize for readable per-environment changes on manifests you control; both together for third-party charts you need to adjust. Neither encrypts secrets: add SOPS, sealed secrets or an external secrets operator. In GitOps, review the rendered output.

## Worked example: the silent typo

An override sets `ingress.hostname` but the chart reads `ingress.host`. Nothing errors and the default hostname stays. A schema in the chart, or a diff of the rendered manifest, catches it. Always compare override keys with the chart defaults.

2. Why are generated ConfigMap names hashed?
3. What does `helm upgrade --install --atomic` give you?
4. Why does Helm not upgrade CRDs in `crds/`?
5. When do you choose Kustomize over Helm?
