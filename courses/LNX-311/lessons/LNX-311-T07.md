# RBAC, ServiceAccounts, certificates

This lesson follows the topic synthesis `synth/LNX-311/LNX-311-T07.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Explain authentication, authorisation and admission as three separate decisions.
- Write Roles, ClusterRoles and bindings for least privilege, and test them with `kubectl auth can-i`.
- Give a workload its own ServiceAccount, and manage the cluster's certificates and expiry.

## Authentication sources

There is no user database. The API server derives a user and groups from X.509 client certificates (CN is the user, O the groups), bearer tokens, projected ServiceAccount tokens, OIDC tokens or a webhook. Anything else is anonymous and can be refused. Client certificates cannot be revoked before expiry, so prefer OIDC for people.

## RBAC in one page

- `Role`: rules (apiGroups, resources, verbs, optional resourceNames) inside one namespace. `ClusterRole`: the same cluster-wide, or reusable in one namespace through a RoleBinding.
- `RoleBinding` / `ClusterRoleBinding` connect them to subjects: users, groups, ServiceAccounts.
- RBAC is **additive**: no deny rules; the effective access is the union of all bindings.
- Verbs include `get list watch create update patch delete` plus `impersonate`, `bind`, `escalate`. `list` and `watch` on secrets disclose the contents.
- Traps: wildcards, bindings to `system:authenticated`, `cluster-admin` for convenience, the right to create pods (a pod can mount any Secret and ServiceAccount in its namespace), the right to create bindings.

```bash
kubectl auth can-i delete pods -n shop --as system:serviceaccount:shop:ci
kubectl auth can-i --list -n shop --as-group team-a-dev --as dev
kubectl auth whoami
```

## ServiceAccounts

Pods run as the namespace's `default` ServiceAccount unless `serviceAccountName` says otherwise. Create one per workload, grant only what it needs, and set `automountServiceAccountToken: false` where the API is not used. Tokens are projected, audience-bound and short-lived; since 1.24 long-lived Secret tokens are no longer auto-created.

## Cluster certificates

kubeadm builds a cluster CA, an etcd CA and a front-proxy CA under `/etc/kubernetes/pki`. Leaf certificates last one year, CAs ten.

```bash
sudo kubeadm certs check-expiration
sudo kubeadm certs renew all     # then restart the control-plane static pods
```

`kubeadm upgrade` renews them as a side effect. For a user certificate: key, request, `CertificateSigningRequest` with the client signer, `kubectl certificate approve`, fetch from status, bind a role to the name. Approval permission is sensitive.

## Worked example: expiry day

Every `kubectl` call fails with an expired certificate. On a control-plane node, check expiry, renew, restart the static pods by moving manifests out and back, copy the refreshed admin kubeconfig. Then alarm at 30 days.
