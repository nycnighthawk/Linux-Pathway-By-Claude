# Architecture: API server, etcd, scheduler, kubelet, CRI

## What you will be able to do

- Name every control-plane and node component, say what each one owns and what it must never do.
- Trace a Deployment from `kubectl apply` to a running container and locate the stage where it stalled.
- Diagnose a control plane that is down using only node-level tools, and repair a static pod manifest.

## One store, one front door, many loops

Kubernetes keeps all cluster state in **etcd**, a Raft-replicated key-value store. Only **kube-apiserver** talks to etcd. It authenticates, authorises, runs admission, validates and persists every request, and it serves watches. Everything else is a client of the API server:

- **kube-controller-manager** runs many control loops (ReplicaSet, Deployment, node lifecycle, EndpointSlice, garbage collection). Each loop compares an object's spec with what exists and writes the difference.
- **kube-scheduler** watches for pods with no node, filters out nodes that cannot host them, scores the rest and writes a binding. It starts nothing.
- **kubelet** (every node) turns pods bound to its node into containers through the **container runtime interface** (CRI), mounts volumes, runs probes and reports status.
- **containerd or CRI-O** implement the CRI and call a low-level OCI runtime such as runc.
- **kube-proxy** (or a replacement such as Cilium) programs the node so Service addresses reach pods.
- The **cloud controller manager** holds provider-specific loops and is absent on bare metal.

Controllers are *level-triggered*: after a restart they re-list everything and converge, so missed events do not matter. The design degrades gracefully: with the control plane down, running containers keep running; only change stops.

## Where the pieces run

With kubeadm, the kubelet is a systemd service on the host. It reads **static pod** manifests from `/etc/kubernetes/manifests` and starts etcd, the API server, the controller manager and the scheduler from them. kube-proxy is a DaemonSet. Credentials live in `/etc/kubernetes/*.conf` and `/etc/kubernetes/pki`.

```bash
ls /etc/kubernetes/manifests          # the four control-plane static pods
sudo crictl ps -a                     # containers as the runtime sees them (works when the API is down)
sudo journalctl -u kubelet -e         # why a static pod did not start
kubectl get --raw='/readyz?verbose'   # API server checks, when the API is up
kubectl -n kube-system get pods -o wide
```

## How a pod comes to life

1. The API server stores a Deployment.
2. The Deployment controller creates a ReplicaSet; its controller creates pods with no node.
3. The scheduler binds each pod to a node.
4. The kubelet sees the binding, asks the runtime to pull and start containers, and writes status.

Find the stalled stage: no ReplicaSet means the controller manager is unhealthy; Pending with no node means a scheduling filter or a dead scheduler; ContainerCreating means kubelet, runtime, image pull or volume; a node that stays NotReady often cannot reach its runtime socket.

## Worked example: the API is down

After a power cut `kubectl` answers "connection refused". On the control-plane node, `crictl ps -a` shows the etcd container exited. `crictl logs` names a missing data directory because a volume did not mount. Fix the mount; the kubelet restarts the static pod by itself, and the API returns. No API call was needed because static pods are managed from disk.
