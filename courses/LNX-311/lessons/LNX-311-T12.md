# Hundreds of nodes; long-lived upgrades

This lesson follows the topic synthesis `synth/LNX-311/LNX-311-T12.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Name the first resources to saturate in a large control plane and the standard mitigations.
- Choose between one big cluster and many small ones.
- Plan a cadence that keeps every cluster in its support window.

## Where large clusters strain

The project tests against thresholds on the order of 5,000 nodes and 150,000 pods (check the current figures on the scalability page); real workloads hit limits sooner.

1. **etcd**: write rate and database size, disk latency. Keep data small, use dedicated fast disks, sometimes a separate store for events.
2. **API server**: unpaginated lists, polling controllers. Use watches with selectors, the watch cache and **API priority and fairness** so one noisy client cannot starve others.
3. **Controllers and scheduler**: throughput limits. EndpointSlices replaced giant Endpoints objects.
4. **Nodes and add-ons**: every DaemonSet watches the API on every node; kube-proxy rule counts grow with services; DNS load grows with pods; kubelet heartbeats are lease updates.

At hundreds of nodes something is always failing: automate detect, cordon, drain, replace.

## Scale up or scale out

One large cluster suits workloads needing one network domain and costs a bigger blast radius and specialist tuning. Many smaller clusters limit blast radius and allow gradual upgrades but need fleet management: one declarative template (Cluster API, modules), add-ons and policy by GitOps with per-cluster overlays, at most two or three supported minors, central observability, and a catalogue of owner, version and support end.

## Staying upgradable for years

- Upgrade every release or every other release; skew and deprecation windows assume it.
- Scan for deprecated APIs continuously; run storage version migration before dropping CRD versions.
- Keep add-ons inside their compatibility tables.
- Keep infrastructure as code and rehearse recreating a cluster.
- Delete unused CRDs, namespaces and orphaned volumes; bound node age.
- Roll out changes in canary waves and restart kubelets in batches (a thundering herd of re-lists can overload the API server).

## Worked example: eighteen months late

A team deferred upgrades for 18 months. Beta APIs vanished, a CRD version was dropped without migration and the network plugin needed an intermediate upgrade. A quarterly cadence would have cost an afternoon each time.
