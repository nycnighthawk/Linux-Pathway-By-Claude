# etcd backup and restore

This lesson follows the topic synthesis `synth/LNX-311/LNX-311-T04.md`, which carries the sources, the history and the failure cases.

## What you will be able to do

- Take, verify, protect and rotate etcd snapshots on a kubeadm control plane.
- Restore a single-member and a multi-member cluster in the right order.
- State what an etcd restore does not bring back, and what complements it.

## What etcd holds and how it fills up

All API objects live in etcd under one prefix, with a history of revisions. The API server compacts history every few minutes, but compaction does not shrink the file: **defragmentation** does. The database has a size quota (2 GiB by default). Past it, etcd raises the **NOSPACE alarm** and the cluster becomes read-only until you compact, defragment and clear the alarm. Typical causes: event floods, runaway controllers, huge objects.

## Taking and checking a snapshot

```bash
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /var/backups/etcd-$(date +%F).db
etcdutl snapshot status /var/backups/etcd-$(date +%F).db -w table
```

One healthy member is enough. Then:

- restrict the file mode (it contains every Secret);
- copy it off the node and off the site;
- keep the Secret-encryption key separately;
- record the etcd and Kubernetes versions;
- alert when the newest backup is too old.

## Restoring

Rule: **stop every API server, restore, then start them.** Restart scheduler, controller manager and kubelets afterwards so they drop stale state.

1. Move the static pod manifests out of `/etc/kubernetes/manifests` and wait until `crictl ps` shows the control plane stopped.
2. `etcdutl snapshot restore FILE --data-dir /var/lib/etcd-restored`.
3. Edit the etcd manifest so the data hostPath points to the new directory, and update the kubeadm ConfigMap's etcd data directory.
4. Move the manifests back; the kubelet starts the pods.

`etcdctl snapshot restore` is deprecated in favour of `etcdutl`. For several members, restore one, start it alone, and add the others as new members. Never restore only one member of a three-member cluster and leave the other two running old state.

## What a restore does not do

It rolls the control plane's *belief* back. Objects created after the snapshot vanish, but their pods may still run until kubelets reconcile; volumes provisioned later leak; later nodes may be rejected. Object-level and volume-level tools (Velero, CSI snapshots) cover namespace-sized mistakes and persistent data. GitOps repositories cover declared objects.

## Worked example: restore with the API servers running

Restoring while API servers still ran left their watch caches ahead of the datastore, so controllers saw history run backwards. Follow the documented order instead: all API servers off first.
