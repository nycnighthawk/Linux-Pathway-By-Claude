Linux Mastery Path

This curriculum takes a learner from zero to Linux mastery along one of four pathways: Enterprise Infrastructure, Cloud-Native Platform, Linux Software Development, or Kernel & Low-Level Systems. Every pathway shares one foundation trunk and then branches. Courses map to current certifications, labs are auto-graded on GitHub Actions wherever possible, and the same source builds the books. Facts were checked on 1 November 2026, and prices and free tiers change often.

One trunk, four pathways

Everyone takes the Stage 0–1 trunk. At Stage 2 the learner picks a pathway, and each pathway has its own core courses, electives, certification ladder and capstone. Pick a pathway to highlight it throughout the report.

Switching pathways

The trunk is about 280 hours and counts toward every pathway. Several Stage 2 courses are shared too: LNX-307 is core in all four, LNX-310 in three, and LNX-220/320 in both developer-facing pathways. Switching after Stage 2 usually costs only the pathway-specific Stage 3 courses.

Common pairings: Cloud-Native + Enterprise for platform teams running on-prem Kubernetes, and Developer + Kernel for systems programmers.

What GitHub Actions in a public repo gives you

  • Standard Linux runners for public repos have 4 vCPUs, 16 GB of RAM and a 14 GB SSD, free and unmetered.
  • Passwordless sudo and a real VM, so loop devices, network namespaces, nftables, Docker and privileged containers all work.
  • KVM hardware acceleration on Linux runners, so nested lab VMs, kubeadm clusters and freshly built kernels all boot inside a job. Kernel projects such as sched_ext and netdev already boot test kernels in CI with virtme-ng.
  • Multi-node Kubernetes with kind in containers, including CNI swaps (Flannel, Calico, Cilium) and two clusters side by side.
  • Up to 20 jobs at once on the Free plan, with up to 256 jobs per matrix, so one push can grade every lab on every distro, architecture or Kubernetes version.
  • Windows Server runners with admin rights, for PowerShell and OpenSSH-on-Windows labs.

What it cannot give you

  • A reboot of the runner itself. Do reboot and persistence checks inside nested VMs.
  • Persistence across days. Jobs are ephemeral and capped at 6 hours, so soak tests, long upgrades, multi-day fuzzing and drift have to run on a long-lived lab.
  • Networking between jobs. Each job is an isolated VM with no inbound connections, so a whole topology or cluster must fit inside one 16 GB runner.
  • A genuine Windows AD domain controller, because promotion needs a reboot. Use Samba AD DC in CI.
  • Restricted syscalls in default containers. io_uring, perf events and BPF labs need a VM or a privileged container.
  • Real hardware and trustworthy numbers. Vendor switches, physical devices for driver bring-up, BMCs and performance benchmarks are out of reach on shared runners.
  • Human processes. CI can't stand in for upstream patch review or a real on-call rotation.
  • Secrets on fork pull requests, so labs that need cloud keys or a RHEL subscription can't be graded on them.

Reference grading workflows

The learner forks the course repo and commits a solution. CI builds a clean environment, applies the solution and runs the lab's verifier. All three patterns use the KVM udev rule GitHub documents for hardware acceleration.

1 · Nested VM lab (systems pathways)

jobs:
  vm-lab:
    runs-on: ubuntu-24.04
    timeout-minutes: 45
    strategy:
      fail-fast: false
      matrix:
        lab:    [lnx102-timers, lnx103-lvm-extend, lnx204-selinux-port]
        distro: [almalinux-10, rocky-9, ubuntu-24.04, debian-13]
    steps:
      - uses: actions/checkout@v4
      - name: Enable KVM
        run: |
          echo 'KERNEL=="kvm", GROUP="kvm", MODE="0666", OPTIONS+="static_node=kvm"' \
            | sudo tee /etc/udev/rules.d/99-kvm4all.rules
          sudo udevadm control --reload-rules
          sudo udevadm trigger --name-match=kvm
      - run: sudo apt-get update && sudo apt-get install -y qemu-system-x86 cloud-image-utils virtinst libvirt-daemon-system
      - run: ./harness/boot-vm.sh "${{ matrix.distro }}" "labs/${{ matrix.lab }}"
      - run: ./harness/apply.sh "labs/${{ matrix.lab }}/solution"
      - run: ./harness/reboot-and-verify.sh "labs/${{ matrix.lab }}/verify"

2 · Kubernetes lab (Cloud-Native pathway)

jobs:
  k8s-lab:
    runs-on: ubuntu-24.04
    strategy:
      matrix:
        lab: [lnx311-etcd-restore, lnx312-netpol-default-deny, lnx314-psa-restricted]
        cni: [default, cilium]
    steps:
      - uses: actions/checkout@v4
      - uses: helm/kind-action@v1          # multi-node cluster from the lab's config
        with:
          config: labs/${{ matrix.lab }}/kind-config.yaml
      - run: ./harness/install-cni.sh "${{ matrix.cni }}"
      - run: kubectl apply -k "labs/${{ matrix.lab }}/solution"
      - run: ./harness/k8s-verify.sh "labs/${{ matrix.lab }}/verify"

3 · Kernel lab (Kernel pathway)

jobs:
  kernel-lab:
    runs-on: ubuntu-24.04
    timeout-minutes: 90
    steps:
      - uses: actions/checkout@v4          # learner's kernel tree or module
      - name: Enable KVM
        run: |
          echo 'KERNEL=="kvm", GROUP="kvm", MODE="0666", OPTIONS+="static_node=kvm"' \
            | sudo tee /etc/udev/rules.d/99-kvm4all.rules
          sudo udevadm control --reload-rules && sudo udevadm trigger --name-match=kvm
      - run: sudo apt-get update && sudo apt-get install -y build-essential flex bison bc libelf-dev libssl-dev qemu-system-x86
      - run: pip install virtme-ng
      - run: ./scripts/checkpatch.pl --strict -g HEAD   # style gate
      - run: vng --build --config .ci/lab.config        # build a minimal kernel
      - run: vng -- ./verify/in-guest.sh                # boot it; run KUnit, kselftest, module checks

    How the tiers fit together

    1. Public GitHub repo with hosted runners covers container, nested-VM, kind and virtme-ng labs at no cost. It is the default grader in every pathway.
    2. One self-hosted lab box (64 GB RAM) adds a genuine Windows AD DC, Katello, AWX, live migration, cluster soak tests, multi-day syzkaller runs and trustworthy benchmarks. Run it as an ephemeral self-hosted runner on a separate private repo, or require approval for fork PRs. Self-hosted runners are still free: GitHub's proposed $0.002/minute charge was postponed.
    3. Cloud free credits cover the managed-Kubernetes and cloud-provisioning topics. New AWS accounts get up to $200 in credits for up to 6 months.
    4. A small hardware kit is optional: a managed LACP switch for the infrastructure pathways, or an ARM development board for real driver bring-up in the Kernel pathway.

    Cost figures are planning estimates, not quotes. Hetzner raised prices twice in 2026, and its EX44 went from €42.30 to €47.30 a month in April. Server-auction listings rose only about 3%, which keeps the auction the cheapest rented option.

    Curating raw content into courses

    Courses are built from openly licensed source material plus original writing. Licences decide what can be adapted, what can only be paraphrased or linked, and what can appear in a book you sell. Sort sources into licence streams before writing a lesson.

    Licence streams

    • Stream A, CC BY-SA family plus CC BY (combine freely): RHEL docs, Rocky docs, Ubuntu Server docs, the Debian Handbook and Bootlin's kernel training materials (all BY-SA), plus Kubernetes docs (CC BY 4.0, which can be adapted into BY-SA). Publish course text as CC BY-SA 4.0.
    • Stream B, GFDL: ArchWiki and GNU manuals. Paraphrase or link, or keep a separate GFDL appendix.
    • Stream C, GPL/OSL copyleft: Ansible docs (GPLv3), Linux kernel Documentation (GPL-2.0) and the Linux Kernel Module Programming Guide (OSL-3.0). Link to them and write original lessons. Kernel code samples in your labs should be GPL-2.0 so they can be upstreamed.
    • Reference only: NC/ND works such as The Linux Command Line and CIS Benchmarks (which also feed kube-bench checks). Base commercial chapters on DISA STIGs, NIST and the Kubernetes docs instead.
    • Certification objectives are vendor copyright. Map objective IDs and don't reprint the lists.

    Raw-to-course recipe for each lesson

    1. Map. Start from the objective IDs the lesson must satisfy (for example CKA "Troubleshooting", RHCSA "configure Flatpak repositories", or the LFD103 chapter on patches).
    2. Gather. Pull 2–4 raw passages from Stream A sources and record their URL, licence and date in provenance.yml.
    3. Synthesise. Write original prose that explains why, compares tools and adds failure modes. Keep adapted passages short and tagged.
    4. Prove. Every command and code sample lives in a lab with a verifier, and CI runs it across the matrix (distros, Kubernetes versions, kernel architectures).
    5. Assess. Add a performance task graded in CI plus recall questions mapped to objective IDs.

    Certification alignment

    P means the course is primary preparation for that exam. S means it supports part of the blueprint. The Developer and Kernel pathways have few vendor exams, so a CI-verified portfolio (and, for kernel work, accepted upstream patches) carries more weight there.

    From courses to books

    The same Markdown source builds the course site, the lab repository and the books. Each book groups courses that share a certification target and a licence stream.

    Single-source pipeline, all on GitHub

    1. Repo layout: courses/<code>/lessons/*.md, labs/<lab>/{setup,task.md,solution,verify}, sources/ (mirrored raw text with licence metadata) and objectives/*.yml.
    2. Licence gate: CI reads each lesson's provenance and fails the book build if NC, ND, GFDL, GPL or OSL text feeds a CC BY-SA target. Code listings carry their own SPDX tags.
    3. Prose quality: Vale style lint, link check, and extraction of every fenced code block into the lab harness, so the book never shows code that wasn't run.
    4. Builds: MkDocs Material for the course site on GitHub Pages, and Pandoc or Quarto for PDF and EPUB. The attribution appendix and objective index are generated from metadata.
    5. Release: a Git tag publishes the books to GitHub Releases and pins dated lab images, Kubernetes versions and kernel versions, so each edition matches a reproducible lab.
